# Blobs: large values outside transactions

**Status: partly built.** References, the builder that cuts a stream into pieces, the verified reader, the hashing port, the error types and the service types exist in `packages/db-core/src/blob/` (§[References and pieces](#references-and-pieces), §[The node's blob service](#the-nodes-blob-service)); the piece store's interface, its in-memory implementation and the conformance suite every piece store runs exist in `packages/db-p2p/`, the piece store on files for Node hosts in `packages/db-p2p-storage-fs/`, the SQLite piece store for NativeScript in `packages/db-p2p-storage-ns/`, the IndexedDB piece store for browsers in `packages/db-p2p-storage-web/`, and the LevelDB piece store for React Native in `packages/db-p2p-storage-rn/` (§[The local store](#the-local-store)), so every storage package can hold blob pieces. Blob records, the sweep that deletes pieces no held blob needs, and the node's blob service exist in `packages/db-p2p/src/blob/` (§[Holds](#holds), §[The node's blob service](#the-nodes-blob-service)); the node takes a piece store (`NodeOptions.pieceStorage`) and exposes that service as `node.blobs`, on serving and client nodes alike. The blob protocol's framing, `stat` and `get` are built, and served on serving and client nodes, and so is the fetcher that brings a blob's missing pieces from the machines that hold them, through which `node.blobs` reads from other machines and probes a blob's cohort (§[Moving pieces between machines](#moving-pieces-between-machines)). Reference trees and the scope registry, which record in the database which committed rows reference which blobs, exist in `packages/db-core/src/blob/` with the readers that answer whether a blob is still referenced (§[Registering references](#registering-references)). An announcement is answered: the receiver reads committed state through the node's own transactor, takes the `responsible` hold, pulls the blob and sends `held` (`BlobAnnounceReceiver` in `packages/db-p2p/src/blob/announce-receiver.ts`), bounded per peer by `AnnounceLimiter` in `packages/db-p2p/src/blob/announce-limiter.ts`; a node can be told to take only what it wrote, pinned or read (`NodeOptions.blobs`'s `hold`), and a responsible node that reads a referenced blob keeps it (§[Placement, copying and durability](#placement-copying-and-durability)). The durable owed entry — one record per announced blob, naming the peers confirmed to hold it — and the pure rule that turns a cohort and a set of holders into a durability class exist in `packages/db-p2p/src/blob/owed-blob-ledger.ts` and `packages/db-p2p/src/blob/blob-durability.ts`, with the class stored on the blob record (§[Placement, copying and durability](#placement-copying-and-durability)). The drain that sends those owed copies is built, on serving and client nodes alike: `node.blobs.announce` takes the `owed` hold and records the entry, and `BlobCopyDrain` in `packages/db-p2p/src/blob/blob-copy-drain.ts` announces the blob to each owed member until every member that accepts blobs holds it, reporting each change of the blob's durability as an `onDurability` event and releasing the writer's hold at `full` (§[Placement, copying and durability](#placement-copying-and-durability)). The byte budget that keeps the blobs a machine holds only because it read them from growing without bound exists in `packages/db-p2p/src/blob/cache-budget.ts` (§[Lifetime](#lifetime)); the reference pass that releases `responsible` and `owed` holds does not. The two things reclaiming needs the read path to tell it are built, in `packages/db-core/src/network/struct.ts` and `packages/db-p2p/src/network/cohort-reachability.ts`: a block read says whether a machine other than the one answering vouched for the answer (`GetBlockResult.cohortConfirmed`, asked for in front of the answer by `BlockGets.awaitConsult`), and a node can ask whether it is the whole cohort of some blocks (`KeyNetworkCohortReachability.aloneFor`) (§[Lifetime](#lifetime)). SQL is built, in all four of its parts. The `blobref` column type, which the plugin registers and a table declares a column of (`BLOBREF_TYPE` in `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts`); and the blob service an application puts files through — `plugin.blobs` and `plugin.blobsFor(table)` (`SqlBlobService` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/sql-blob-service.ts`) — with the two SQL functions that read a reference's local state (`packages/quereus-plugin-optimystic/src/functions/blob-functions.ts`) and the owner labels its pins are held under (`packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts`), all §[SQL](#sql); the reference tree each table with a `blobref` column keeps in step with its rows, registered in the network's scope registry (`BlobReferenceMaintainer` in `packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts`, `BlobScopeRegistration` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-scope-registration.ts`, §[Registering references](#registering-references)); and the whole pin lifecycle, which is §[Committing a reference](#committing-a-reference) for every commit that reaches storage or the queue (`SqlBlobPins` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pins.ts`): the references a transaction adds are pinned on the writer when its commit starts, announced with the table's reference tree as their scope and unpinned once the commit lands, and unpinned if it is abandoned; a QUEUED transaction's pins are settled when the queue finishes with it (`settleQueued`); a pin no arm got to release — a process that stopped mid-commit, or an arm that kept a pin it could not release — is judged from committed state and finished (`reconcile`); and a blob put outside any transaction and never referenced loses its pin once it passes a holding period, 24 hours by default (`sweepUnstaged`, the registration's `blob_unstaged_holding_ms`). The reaction to a cohort change is built, which completes §[Placement, copying and durability](#placement-copying-and-durability): a second `RebalanceMonitor` watches the blob references this node keeps for the network and `BlobCohortReaction` in `packages/db-p2p/src/blob/cohort-reaction.ts` decides what to do when their cohorts change — announce a held blob to a member that joined its cohort, and drop a `responsible` hold only once enough current members answer that they hold the blob. What is left to build is reclaiming: the reference pass that releases a `responsible` or `owed` hold on a blob committed state no longer lists, §[Lifetime](#lifetime). It is the design of record for native large-value support (GitHub #63, and the Quereus side of the same request, gotchoices/quereus#40). Each section says what is to be built; the tickets that build it cite the section they serve.

A **blob** is an immutable sequence of bytes, such as a photo, a video or a document. A row holds a short **reference** to it. The bytes are stored and moved by their own subsystem: they are never encoded as JSON, never enter a transaction, a log entry or a consensus record, and are copied between machines in small pieces that can be resumed and checked one at a time.

In one sentence: **blobs are stored the way IPFS stores files, placed by FRET instead of provider records, fetched only by members of the network, and kept alive by the database** — a machine holds a blob for others exactly as long as a committed row references it.

## Why

A large value written through SQL today is a base64 string inside a row inside a transaction (`RowCodec` in `packages/quereus-plugin-optimystic/src/schema/row-codec.ts`). Measured in GitHub #63:

- **Time.** About 1.7 s per MB on loopback with no network in the way, nearly all of it JSON encoding, canonicalization, hashing and cloning of the whole value on every hop. Removing the repeated passes brought it to about 0.2 to 0.3 s per MiB on an in-process two-node mesh over memory storage; what remains is the encoding, hashing and storing the format needs on each machine ([internals.md §A transaction's size limit](internals.md#a-transactions-size-limit), *What a large value costs*).
- **Space.** Each value travels 2.75 to 3.4 times its size: base64, then once in the block it changes and again in the log entry that records the action. A transaction limited to `MAX_TRANSACTION_BYTES` (`packages/db-core/src/network/transaction-size.ts`) therefore holds about 2 MB of file data. The bench in [internals.md §A transaction's size limit](internals.md#a-transactions-size-limit) measures 3.3 to 4.0 times in legacy mode and 5.3 to 6.0 times in session mode, which also carries each value as hex in its SQL statement.
- **Slow links.** A transaction has one time budget whatever its size, and a retry resends all of it. On a cellular link through a relay, a 3 MB transaction never committed, and everything queued behind it waited.
- **Memory.** The whole value is materialized to read or write any part of it.

Sereus Chat works around this in the application (two content-keyed tables of chunk rows, one chunk per transaction). The workaround still pays the per-byte cost and the encoding, and cannot reclaim anything.

What this design does **not** change: an ordinary transaction is still limited to one frame ([internals.md §A transaction's size limit](internals.md#a-transactions-size-limit)), and its deadlines are still fixed (backlog `feat-link-deadlines-stretch-to-measured-response-time`). Blobs remove large content from transactions; they do not make large transactions work.

## Design principles

- **Content addressing, in IPFS's formats.** A reference is a content identifier (CID). Everything received is checked against it, so no signature, commit proof or trusted sender is needed to accept a piece, equal content is stored once, and what a node stores are ordinary IPFS blocks that IPFS tools can read.
- **Bytes stay bytes.** No base64, no JSON, no canonicalization and no cloning of content, in storage or on the wire. Content is hashed once when written and once when received.
- **Small, independent pieces.** A piece is the unit of storage, transfer, verification and retry. A transfer that stops loses at most the piece in flight.
- **Outside consensus.** The cohort agrees on the reference, which is an ordinary column value. No member votes on whether the bytes have arrived.
- **The database decides what is alive.** A machine stores a blob on another machine's behalf only when committed state references it, and stops when committed state no longer does. There is no lease to renew and no expiry clock.
- **Known but not here is an ordinary state.** A reference whose bytes are not on this machine is reported as such, with a reason, and can be fetched. It is never a missing-block error.
- **One placement rule.** The machines responsible for a blob are chosen the way a block's are: the key network's cohort at the blob's coordinate.
- **db-core stays network-free.** Formats, verification, reference trees and planning are pure logic in `db-core` behind ports; storage and transport bind in `db-p2p`, the split the cohort-topic subsystem uses (`packages/db-core/test/no-fret-import.spec.ts`).

## References and pieces

A blob is stored as an IPFS file is, with the parameters current IPFS tools use by default:

- **Pieces.** The content is cut into pieces of 256 KiB (the last one shorter). Each is a raw IPFS block, named by the SHA-256 of its bytes. 256 KiB is also the size Sereus Chat found workable on a cellular link through a relay.
- **List pieces.** A blob of more than one piece has a tree above its pieces: UnixFS file nodes (the `dag-pb` codec), each listing up to 174 children with their sizes, balanced, built until one node remains. A list piece is at most about 9 KB, about 50 bytes per link (measured, §[What this answers in GitHub #63](#what-this-answers-in-github-63)), and is stored and moved like any other piece.
- **The reference** is the CID of the root: version 1, SHA-256, written in lowercase base32. A blob of one piece is referenced by that piece's CID directly. A reference has exactly one accepted spelling, so references compare as strings: `parseBlobRef` in `packages/db-core/src/blob/blob-ref.ts` accepts a string of at most 128 characters only when it decodes as such a CID of a raw or dag-pb piece and re-encodes to the same string, and throws `BlobRefError` otherwise. A piece id (`PieceId`, the key of a piece in a store and on the wire) is spelt the same way; a link inside a list piece may be a version-0 CID, and is re-spelt as version 1 (`pieceIdOfCid`).

```
600 KiB file                       bafybei…   (the reference: CID of the list piece)
                                      │
                         list: [bafkrei…a 256K, bafkrei…b 256K, bafkrei…c 88K]
                                   │           │           │
                                  256K        256K        88K     raw pieces
```

One list piece covers about 44 MiB at these parameters, two levels about 7.4 GiB, three about 1.3 TiB.

Choosing IPFS's formats over a private one costs a little (a list piece is protobuf rather than bare hashes, and the size is in the root piece rather than in the reference) and buys three things: the formats and their edge cases are already specified and tested elsewhere; the libraries exist and are small (`multiformats`, already a dependency of `db-core`, plus the dag-pb and UnixFS codecs); and a node's pieces are valid IPFS blocks, so content can be exported to or imported from IPFS, and an IPFS transport could be added later without touching what is stored. A file put here has the same CID `ipfs add --cid-version 1` gives it: `buildBlob` in `packages/db-core/src/blob/builder.ts` gives files of 0, 1000, 262144, 262145, 174 × 262144 and 175 × 262144 + 1 bytes the references kubo 0.43.1 gives them, pinned by the vectors in `packages/db-core/test/blob-builder.spec.ts`. A list piece is encoded as kubo writes it (`encodeListPiece` in `packages/db-core/src/blob/list-piece.ts`): every link carries an empty name and its child's cumulative size, and the UnixFS data carries the file size and each child's size and no mode or time.

What is **not** taken from IPFS is its network: no public DHT, no provider records, no bitswap. Those have no notion of membership, which is the question a private database has to answer first ([Who may fetch and who may store](#who-may-fetch-and-who-may-store)).

**Verification.** `readBlob` in `packages/db-core/src/blob/reader.ts` yields a blob's bytes, or a byte range of them, in order, from any source of pieces (`PieceSource` in `packages/db-core/src/blob/pieces.ts`). It gets each piece and checks it against the CID that named it (`checkPiece` in `packages/db-core/src/blob/verify.ts`: the size first, so an oversized answer is refused without being hashed, then the SHA-256 digest), top down from the reference. A source that holds only pieces it has already checked says so (`verified`) and is not hashed again; its pieces are still sized and decoded. Because a list piece is written by whoever made the blob, the reader bounds a list piece before it requests anything under it: a piece of at most 1 MiB (`MAX_BLOB_PIECE_BYTES`), at most 1024 children per list piece (`MAX_BLOB_LIST_LINKS`) and at most 8 levels of list pieces, the root counting as one (`MAX_BLOB_LIST_DEPTH`), the three constants in `packages/db-core/src/blob/limits.ts`; child sizes that add up to what the parent declares, and each leaf exactly the size its parent declares; only the two codecs above, named by SHA-256; a total no larger than `Number.MAX_SAFE_INTEGER`; and a UnixFS file node that carries links and no content of its own. One function interprets a list piece's bytes (`decodeListPiece` in `packages/db-core/src/blob/list-piece.ts`), and it accepts any UnixFS file tree within those bounds, whatever piece sizes and fan-out made it. Anything else is a malformed blob, reported as corrupt (`BlobCorruptError` in `packages/db-core/src/blob/errors.ts`, whose reason names which rule failed); a piece the source lacks is reported as `BlobUnavailableError` with reason `not-here`.

Two of those rules are choices. A file node with content of its own is malformed: neither this builder nor `ipfs add --cid-version 1` (which writes raw leaves) makes one, so a file imported by an older IPFS tool without raw leaves, whose data sits inside dag-pb nodes, cannot be read here until it is added again with `--cid-version 1`. And a child declared to hold zero bytes is malformed. It looks harmless, but a tree can repeat one list piece at every position, and with zero-size children such a tree costs 1024 to the eighth power requests while declaring no bytes; with every child at least one byte, the pieces a whole read visits are bounded by the declared size times the depth, repeats included. Repeats themselves are legitimate (an all-zero file repeats both leaves and list pieces) and are read. A root's size is the sum of the sizes its children declare, each checked against what is under it, not the UnixFS `filesize` field, which `ipfs-unixfs` does not keep: the bytes served are exactly the verified bytes, and a root whose `filesize` disagrees is read at the size of its children, where kubo would report the other.

Bytes are yielded only once their piece and every list piece above it have passed these checks. A fault stops the read with nothing past it yielded, so a consumer that sees the error never takes a partial read for a whole one; the slices it already has were verified. A byte range requests only the pieces on its path (the root, the list pieces that cover the range, and the data pieces in it), so a range read judges only those: a fault in a part of the tree the range does not reach is not seen by that read. Three functions beside `readBlob` reach a tree the same way. `planBlobRange` lists the data pieces a range needs, with where each sits, requesting only the list pieces above them. `walkBlobPieces` lists every piece of a tree, or of the part covering a range, with whether the source holds it: it checks each list piece as a read does, hashes no data piece, and walks a repeated list piece once. `readBlobSize` reads the size from the root alone.

**Building.** A writer builds the tree bottom up from a stream, holding one piece and one partial list piece per level, and puts every piece after the pieces it names, one at a time, so a caller can store pieces as they arrive and the next piece waits for the previous put. The level logic is a class of its own (`BlobTreeAssembler` in `packages/db-core/src/blob/builder.ts`) that takes leaf links from any source, which [Extending toward a file system](#extending-toward-a-file-system) requires. A blob's routing key is the digest inside its reference (`routingKeyForBlob` in `packages/db-core/src/network/routing-key.ts`; [Placement, copying and durability](#placement-copying-and-durability)).

**Hashing** goes through one injected port (bytes in, 32 bytes out, asynchronous; `BlobDigest` in `packages/db-core/src/blob/digest.ts`). The default, `defaultBlobDigest`, uses the platform's native digest (`crypto.subtle`) where there is one and falls back to JavaScript (`@noble/hashes`), logging `blob:digest-fallback` once ([debugging.md §db-core sub-namespaces](debugging.md#db-core-sub-namespaces)). It does not use `multiformats`' SHA-256, whose browser build, the one React Native's bundler picks, calls `crypto.subtle` unchecked and so fails on Hermes unless the host has installed one. A `crypto.subtle` the host installed counts as native: the polyfill the React Native setup asks for (`packages/db-p2p/readme.md`, *Global polyfills*) is usually JavaScript, so on such a phone blob hashing is JavaScript-speed with no `blob:digest-fallback` line, and only a native implementation, or a digest supplied through the port, makes it fast. A host may supply its own (React Native), and a supplied digest is checked against the FIPS 180-2 known answers once when installed (`checkBlobDigest`, which rejects with `BlobDigestError`). Pure JavaScript hashing measured 19 s per MB on an older phone, so the port is not optional in practice.

## The local store

Each node keeps two things.

**A piece store.** A map from piece hash to bytes, immutable once written, behind a small interface of its own (`IPieceStore` in `packages/db-p2p/src/blob/piece-store.ts`): has, get, put, delete, list, bytes used, flush. It is deliberately not another logical store of `RawStoreDriver` (`packages/db-p2p/src/storage/raw-store-driver.ts`): that kernel JSON-encodes every value and stages writes in an in-memory overlay and a journal, which is right for small versioned records and wrong for megabytes of immutable bytes that need no cross-key atomicity. Each storage package supplies an implementation beside its block store (files, a SQLite table, an IndexedDB object store, a LevelDB key range read as bytes), and one conformance suite runs against all of them (`runPieceStoreConformance` in `packages/db-p2p/src/testing/piece-store-conformance.ts`, published as `@optimystic/db-p2p/testing/conformance`). A host passes it to the node as `NodeOptions.pieceStorage`, an instance or a factory, as it passes block storage and the key-value store, and closes it after the node stops: the node never closes it. The default is in memory (`MemoryPieceStore` in `packages/db-p2p/src/blob/memory-piece-store.ts`), with a `node-wiring` warning, since its pieces are lost on a restart that the records in a durable key-value store survive; `stat` then reports such a blob `unknown` and corrects its record. The store never hashes: a piece is written only after the blob service has checked its hash, and a put of a hash already present writes nothing. A piece is durable once a flush called after its put has resolved. The flush keeps the block store's flush contract (`RawStoreDriver.flush`) except its prefix rule: pieces are independent, so a crash may keep a piece and lose a put that resolved before it, and a caller that needs pieces stored before the record that names them awaits the flush before writing the record. A store whose engine cannot make earlier writes durable with one later call (IndexedDB, LevelDB) makes each put durable itself.

On a Node host the piece store is files: `FilePieceStore` in `packages/db-p2p-storage-fs/src/file-piece-store.ts`, under `optimystic-pieces/` in the same base path as the block store. Each piece is one file named by its id and holding exactly its bytes, with no JSON, write-ahead log or write group around it, filed in one of 1024 subdirectories named by two digest characters of the id, so no directory holds more than about a thousand files at a million pieces. A put writes the piece to `optimystic-pieces/incoming/`, syncs it, and renames it into place, so after a crash a piece is whole or absent, never truncated; a temp a crash left in `incoming/` is deleted on the next open. A flush syncs the directories whose entries changed. The block store's listing skips the piece directory, and its byte count includes it, which is why the two report one store identity.

On NativeScript the piece store is a table: `SqlitePieceStore` in `packages/db-p2p-storage-ns/src/sqlite-piece-store.ts`, one `pieces` table (piece id, bytes) in the same SQLite database as the block store, sharing its handle. A put is one autocommit statement that writes nothing when the id is present, outside the block store's write group, and a flush is one synced commit, which syncs the shared write-ahead log and with it every earlier write on the database. The block store's byte count is the database's page count, which includes the table, so the two report one store identity. A listing reads the table in pages of 1000 ids.

In a browser the piece store is an object store: `IndexedDBPieceStore` in `packages/db-p2p-storage-web/src/indexeddb-piece-store.ts`, one `pieces` store in the same IndexedDB database as the block store, sharing its handle, each piece stored by structured clone under its id. A put is its own transaction, strict where the browser honours the option, which checks for the id and writes nothing when it is present; a strict transaction completes only once the browser has put it on the disk, so a put that has resolved is durable and a flush has nothing to do. The block store's byte count is the origin's estimate (`navigator.storage.estimate()`), which includes the pieces, so the two report one store identity. A listing reads the store in pages of 1000 ids.

On React Native the piece store is a key range: `LevelDBPieceStore` in `packages/db-p2p-storage-rn/src/leveldb-piece-store.ts`, under its own tag byte (`TAG_PIECES` in `packages/db-p2p-storage-rn/src/keys.ts`) in the same LevelDB database as the block store, sharing its handle. Each piece is two keys, one holding its bytes and one its length, written and deleted together in one batch, so nothing but a read of the piece reads its bytes: `has`, the listing and the byte count read the length keys. A put writes nothing when the id is present, and is synced where the handle can sync, since a synced LevelDB write syncs only the log file it lands in and so one synced write at the flush would not cover pieces in older log files; a flush has nothing to do. `rn-leveldb` cannot sync yet, so on a phone the store reports `'process-crash'`, as the block store does. The block store's byte count covers the whole database, measuring the piece range from its length keys rather than reading the pieces, so the two report one store identity. A listing reads the length keys in pages of 1000.

**Blob records.** One small record per blob this node has a reason to hold, in the node's key-value store: the reference, its size once known, whether every piece is present, when it was last read, and its **holds** (below). Records are what make the node's set of blobs enumerable after a restart. Each is one JSON value under `optimystic-blobs/<reference>` (`BLOB_RECORD_KEY_PREFIX`, listed in `NODE_KV_NAMESPACES` so a file store sharing the block store's directory keeps it out of the block listing): `BlobRecord` in `packages/db-p2p/src/blob/blob-record.ts`, read and written by `BlobRecordStore` in `packages/db-p2p/src/blob/blob-record-store.ts`, which serializes the changes to one blob so that none is lost, never writes a record its decoder would refuse, and deletes a record whose last hold goes. Whether every piece is present is a hint the blob service corrects when it finds otherwise: `stat` trusts it while the root piece is here and walks the pieces otherwise, and a read that finds a piece missing sets it false, so the walk runs on the next `stat`. A record that does not decode (`BlobRecordFormatError`) stops every sweep until it is fixed or removed, since its holds cannot be read.

Piece bytes count toward the node's reported storage use, so capacity-driven decisions see them. They are counted once: a block store that already measures the whole directory or database it shares with the piece store has counted them, and the piece store's own figure is added only where it has not. `blockStoreCountsPieces` in `packages/db-p2p/src/storage/storage-monitor.ts` decides it by store identity: the piece bytes are left out only when the piece store's identity equals the block store's and the block store measures its bytes at all. Two spellings of one directory read as two identities, so such a node counts its pieces twice and reports itself fuller than it is.

### Holds

A node keeps a blob only while some hold names it. There are four kinds:

| Hold | Meaning | Released when |
|---|---|---|
| **pin** (with an owner label) | The application, or the SQL layer on behalf of an open or queued transaction, needs it here. | The owner unpins it. |
| **owed** | This node announced it and its cohort does not fully hold it yet. | Every cohort member that accepts blobs confirms it holds it. |
| **responsible** (with the scope it was verified under) | This node is in the blob's cohort, accepts blobs, and found the blob referenced by committed state. | The node leaves the cohort and enough others hold it, or the blob is no longer referenced ([Lifetime](#lifetime)). |
| **cached** | It was fetched for a read. | Evicted, least recently read first, to stay within a byte budget over the blobs held for reads alone (`BlobCacheBudget` in `packages/db-p2p/src/blob/cache-budget.ts`, sized by `NodeOptions.blobs`'s `cacheBudgetBytes`, 256 MiB by default; [Lifetime](#lifetime)). |

Pieces are shared between blobs. A piece is deleted only by a sweep that finds it in no held blob's tree and in no tree something is reading (below).

A record carries every kind of hold, at most one pin per owner and at most one hold of each other kind, each with the time it was taken. A `responsible` hold also records the scope the reference was last verified under, which is the scope the node re-announces the blob with when its cohort changes. This machine creates pins and `cached` holds so far; `owed` and `responsible` holds are taken by the copying work. The store already offers the `responsible` hold (`LocalBlobService.holdResponsible`, which takes the hold or replaces an existing one's scope and time and flushes before it resolves, beside `LocalBlobService.responsibleScope` and `LocalBlobService.responsibleRefs` in `packages/db-p2p/src/blob/local-blob-service.ts`). A stored scope obeys the same bound an announced one does (§[Moving pieces between machines](#moving-pieces-between-machines)), so a hold can never carry a scope the re-announce would refuse to send. This machine's pins are also readable back by owner (`BlobPinIndex` in `packages/db-p2p/src/blob/local-blob-service.ts`): the owner labels pinning one reference, and every pin whose owner label starts with a given prefix — which is how a caller that does not remember its own pins, such as the SQL layer naming each pin after the transaction holding the reference, finds them again after a restart.

A fetch takes the `cached` hold, creating the record when there is none, before it decides which pieces are missing, and writes to the store only through `BlobFetchStore` (`packages/db-p2p/src/blob/local-blob-service.ts`): the hold, each checked piece, the record's `size` as soon as it knows it (off the root list piece as soon as a plan reads it, and for a blob of a single piece — which has no list to read one off — off that piece's own length when the fetch ends), and the record's `whole` once the blob is all here. Nothing it writes is flushed; a crash loses pieces the next fetch brings again.

A pull started for an announcement is an ordinary fetch, so it takes that `cached` hold too, and it is left beside the `responsible` one. Nothing evicts a blob that holds anything but `cached`, so the extra hold changes nothing while the node is responsible; when `responsible` is later released the blob falls back to the cache budget exactly as a blob that was only read does. Rejected: removing `cached` once the pull finishes, which costs a write and would drop a blob a reader had also read the moment `responsible` went.

The sweep is `PieceSweeper` in `packages/db-p2p/src/blob/piece-sweeper.ts`. It lists every stored piece, walks every held blob's tree (`walkBlobPieces`) for the pieces present, and deletes the rest. Five things can make a piece live while it decides, and each is closed:

- **A put that has stored pieces but not yet written its record.** The put adds each piece's id to a shared set (`InProgressPieces`) before storing the piece, and takes its ids out only after its record is written.
- **A record written or changed after the sweep read the records.** Every record change is noted while a sweep runs, and the sweep walks those blobs again before it deletes.
- **A put storing a piece the sweep has just decided to delete.** Storing a piece and changing a record each hold a shared/exclusive gate (`SweepGate` in `packages/db-p2p/src/blob/sweep-gate.ts`) shared, and the sweep holds it exclusive from re-walking the changed records to its last delete, so such a put waits, then finds the piece absent and writes it again.
- **A fetch storing a list piece over a child already stored.** A child that a sweep's walk found with its parent absent is an orphan to that walk, and the fetch, finding the child present, never stores it again. So every piece a fetch stores notes its blob as a changed record inside the same shared hold, and the sweep walks the blob again before it deletes: by then the parent is there and the child is kept. A sweep that walked first deletes the child before the parent is stored, and the fetch asks for the child again.
- **A read or fetch in flight on a blob whose last hold has gone.** Such a blob has no record, so the pass over held blobs never reaches it, and its pieces are exactly what the read is reading. `LocalBlobService` counts the reads and fetches running against each reference (`inUse`, `inUseRefs` and `beginUse` in `packages/db-p2p/src/blob/local-blob-service.ts`): every `readThrough`, every `fetch`, and every fetch session `NodeBlobService` starts holds one for its duration, and the sweep takes those references as extra roots, inside the same exclusive phase as its re-walk of changed records, keeping every piece of their trees that is present. A session's own use covers the tail where a read has consumed its whole range and returned while the fetch is still confirming what it brought. The one window left is a read that begins after the sweep has read those references but before its deletes have finished — the pre-existing exposure of reading a blob nothing holds (the `NOTE:` at `NodeBlobService.storedPiece`); counting a use takes no gate so that it can be the first thing a read does, and the window it leaves is bounded by one delete phase.

A sweep whose records or trees cannot all be read deletes nothing. It runs a few seconds after the blob service starts (removing the pieces of a put a crash interrupted), after a record is deleted, and after a put that failed once it had stored a piece. Its deletes are not flushed: a delete a crash undoes leaves a piece the next sweep removes.

## The node's blob service

A node exposes one handle, `node.blobs`, declared on `OptimysticNodeAttachmentsBase` (`packages/db-p2p/src/optimystic-node.ts`), so serving and client nodes both carry it. A client has one because the machine a blob is put on holds its only copy until a row referencing it commits (*Nothing leaves the machine yet*, below), and a phone running as a client is the usual machine that picks a photo and puts it; it holds the blobs its own host pinned. Its interface is defined in `db-core`:

```ts
interface BlobService {
	/** Store a stream as a blob, pinned for `owner`. Resolves once every piece is durable on this node. */
	put(source: AsyncIterable<Uint8Array>, options?: BlobPutOptions): Promise<BlobPutResult>;
	/** What this node knows about a blob, without fetching content. */
	stat(ref: BlobRef, options?: { probe?: boolean }): Promise<BlobStat>;
	/** The bytes, or a range of them, in order; fetches what is not here unless told not to. */
	read(ref: BlobRef, options?: BlobReadOptions): AsyncIterable<Uint8Array>;
	/** Bring the whole blob here ahead of a read. */
	fetch(ref: BlobRef, options?: BlobFetchOptions): Promise<void>;
	pin(ref: BlobRef, owner: string): Promise<void>;
	unpin(ref: BlobRef, owner: string): Promise<void>;
	/** Tell the blob's cohort that committed state now references it, and where. */
	announce(ref: BlobRef, scope: BlobScope): Promise<void>;
	onProgress(listener: (event: BlobProgressEvent) => void): () => void;
	onDurability(listener: (event: BlobDurabilityEvent) => void): () => void;
}

interface BlobPutOptions { owner?: string; signal?: AbortSignal }
interface BlobPutResult { ref: BlobRef; size: number }
interface BlobReadOptions { offset?: number; length?: number; from?: 'anywhere' | 'here'; waitMs?: number; signal?: AbortSignal }
interface BlobStat { ref: BlobRef; size?: number; locality: 'here' | 'partial' | 'elsewhere' | 'unknown'; heldBytes: number; durability?: BlobDurability }
/** The id of the reference tree that lists the blob (see Registering references). */
type BlobScope = string;
```

- **`put`** reads the source one piece at a time, hashes and stores each, and never holds more than a piece and its list pieces in memory. It resolves when the blob is durable *here*, pinned for its owner (the label `default` when none is given, so a blob put without one is still held until it is unpinned). Nothing leaves the machine yet: no other machine can know the reference before a row carrying it commits, so there is nothing to gain by sending the bytes sooner.
- **`announce`** is what starts copying, once the reference is committed. The SQL layer calls it; an application writing collections directly calls it after its own commit.
- **`stat`** answers from local records. With `probe` it also asks the blob's cohort, which is what distinguishes `elsewhere` (someone reachable holds it) from `unknown`. The size is known once the root piece is here.
- **`read`** yields verified bytes. Pieces not held are fetched from other holders as the read reaches them, and kept under a `cached` hold. `waitMs` keeps a read trying while the bytes are still arriving somewhere; without it a read fails at the first piece nobody reachable holds.
- **Failures are typed** (`packages/db-core/src/blob/errors.ts`). `BlobUnavailableError` carries the reference, a reason and, when one piece was the problem, its id: `not-here` (the read said `from: 'here'`), `not-held` (every holder asked answered that it does not have it), `peers-unreachable` (some of them did not answer), `cohort-unreachable` (none could be asked). All four mean "not yet", and are the blob counterpart of `BlockUnavailableReason` in `packages/db-core/src/network/struct.ts`. `BlobCorruptError` means the blob is malformed, or a holder served bytes that fail verification and no other holder could supply them. `BlobRefError` means the string is not a reference.

Optimystic owns no file access. A host turns a picked file into a stream for `put` and writes the stream from `read` where it wants it.

**What is built.** `node.blobs` is a `NodeBlobService` (`packages/db-p2p/src/blob/node-blob-service.ts`) over two parts the node builds on both roles: a `LocalBlobService` (`packages/db-p2p/src/blob/local-blob-service.ts`), which answers from this machine alone, and the fetcher (§[Moving pieces between machines](#moving-pieces-between-machines)). `createLibp2pNodeBase` builds the local service over the node's piece store, its key-value store and `NodeOptions.blobs.digest` (the hashing port, used as given; checking it with `checkBlobDigest` is the host's call), starts it once the node has started, and stops it (a scheduled sweep cancelled, a running one awaited) after the fetcher and before the serving role and the transports when the node stops. `put`, `pin` and `unpin` are the local service's, and the blob protocol service answers a peer's `stat` from the local service too, so a peer's question never starts a probe of its own. A put stores and flushes every piece, then writes and flushes the record that pins the blob, so a put that resolved survives a crash with its pin. A read takes its pieces from the local store without hashing them again (`localPieceSource` in `packages/db-p2p/src/blob/local-piece-source.ts`, marked `verified`): every piece there was produced by this node's builder from the bytes themselves, or checked against its id by the fetcher before it was stored, and hashing every local read would cost a phone seconds per megabyte. A data piece the disk altered at its own length is therefore served unnoticed by a local read; list pieces are still decoded and bounded, and every size is still checked. A piece a read fetched is taken the same way, from the store the fetcher put it in after checking it against its id, so each fetched piece is hashed once.

- **`stat`** reports `here`, `partial` or `unknown` from the record and a walk of the pieces, and corrects a record wrong about whether the blob is whole. With `probe`, a blob this node knows nothing of (`unknown`) is asked of its cohort: the fetcher's candidates (`blobHolderCandidates` in `packages/db-p2p/src/blob/blob-holders.ts`) are sent the blob protocol's `stat` in parallel, each within one response timeout of the declared link (`LinkDeadlines` in `packages/db-p2p/src/rpc-deadline.ts`), and the first that holds it whole or in part makes the answer `elsewhere`; the others are no longer waited for. Silence, failures and no candidates leave `unknown`, never `elsewhere`. A local `partial` stays `partial`, since nothing a peer says could change it, and `here` asks nobody. `size`, `heldBytes` and `durability` are always this node's, and nothing is remembered between probes.
- **`read`** with `from: 'here'` reads this machine's pieces alone, and a piece that is not here fails it with `not-here`. Otherwise it reads through `LocalBlobService.readThrough` in `packages/db-p2p/src/blob/local-blob-service.ts`, which asks for a piece the store lacks instead of failing: the first such piece starts one foreground fetch of the read's whole range, which fetches ahead in batches while the read consumes, and the read waits for each piece it reaches. A read of a blob entirely here starts no fetch, takes no hold and looks up no cohort. A read that throws, or whose consumer stops early, ends its fetch; a request already sent finishes, and what it stores is kept. A read that consumed its whole range leaves its fetch to finish its confirming walk and, for a whole blob, mark the record whole. The read fails at the piece that needed it, with the fetch's error; stopping the node fails it at its next missing piece. Two reads of one blob at once start a fetch each, and the two share one request per piece.
- **`waitMs`**, on a read or a `fetch`, keeps the fetch asking while no reachable holder has a piece it needs: after a round of asking that leaves a piece missing, it waits and asks again, 500 ms at first and doubling to 8 s (`BLOB_WAIT_RETRY_INITIAL_MS` and `BLOB_WAIT_RETRY_MAX_MS` in `packages/db-p2p/src/protocol-limits.ts`), until `waitMs` has passed with no piece arriving. Each piece that arrives starts the time again, so a slow transfer that keeps delivering is not cut off. Without `waitMs` the fetch fails after its first such round: `not-held`, or `cohort-unreachable` when nobody could be asked.
- **`fetch`** brings the whole blob here as a foreground fetch, and resolves at once for a blob already whole here.
- **`announce`** takes the `owed` hold, records the owed entry and hands the blob to the node's copy drain, which is what makes `stat` report a `durability` and `onDurability` fire (§[Placement, copying and durability](#placement-copying-and-durability)).
- **`onProgress`** reports, after each piece stored by a fetch the service started (a read's or `fetch`'s), the pieces and bytes stored so far for that reference by every such fetch still running, and the size once the root piece is here. A reference's counts start again once its last fetch has ended. Pieces are told apart only by reference, so a piece stored by a fetch started on the fetcher directly is counted while one of the service's fetches of the same blob runs, and reported by nothing otherwise. `NodeBlobService.wireBytes` returns the blob protocol client's byte counts, for diagnostics.

`packages/db-p2p/test/blob-network-read.spec.ts` pins a read across two machines, with its probe and its progress, and a read that `waitMs` keeps alive until a holder has the blob; `packages/db-p2p/test/node-blob-service-probe.spec.ts` pins the probe settling on the first holder and giving up on a silent peer after one response timeout.

**A host with no libp2p node** holds a `SingleMachineBlobService` (`packages/db-p2p/src/blob/single-machine-blob-service.ts`) instead: a `LocalBlobService` for everything except `announce`, which keeps the blob rather than rejecting. It is what a SQL plugin whose transactor builds no node uses (§[SQL](#sql)), and what an application holding blobs beside a non-networked database uses. Its `announce` refuses a scope the wire would refuse, so a host that later moves to a node has nothing to re-check — every announce path, the wire client and each blob service that records a scope before it would be sent, refuses through the one `assertAnnounceScope` in `packages/db-p2p/src/blob/blob-protocol.ts`, so none can come to spell the rule differently; takes the `owed` hold, so the blob survives a restart and no sweep removes it; and, the first time, records and reports durability `local` — `accepting` 1, and `confirmed` 1 when the bytes are all here. That class never changes, because there is no cohort to copy to: `stat` reports `local` from then on, and the `owed` hold is released only by reclaiming, once the scope stops listing the reference (§[Lifetime](#lifetime), *An owed blob follows the same rule*). Announcing is serialized per reference, so two transactions committing one content-addressed reference at the same time report its durability once between them. `packages/db-p2p/test/single-machine-blob-service.spec.ts` pins the one announce, the silent re-announce, two announces in flight together, and the blob surviving its last pin.

**Open: replacing a corrupt piece.** A stored piece found corrupt (a malformed list piece, or a size that disagrees with its parent) fails the read with `BlobCorruptError` and stays stored: a put of a piece already present writes nothing, so putting the same file again does not repair it. Replacing it with a good copy from another holder is not built: the fetcher brings only pieces this node lacks.

These types are `BlobService` in `packages/db-core/src/blob/service.ts`, with the four the block above names but does not spell out: `BlobFetchOptions` (`waitMs` and `signal`, as for a read), `BlobDurability` (the class, `confirmed` and `accepting` counts over the members that accept blobs, and the `unconfirmed` members by peer id; see [Placement, copying and durability](#placement-copying-and-durability)), `BlobDurabilityEvent` (a reference and its durability) and `BlobProgressEvent` (a reference, the pieces and bytes fetched so far, and its size once the root piece is here; a put has no reference until it ends, so it reports none).

## Registering references

Liveness is a question about the database — "does any committed row reference this blob?" — so the database has to be able to answer it cheaply, for any blob, on a machine that knows nothing about the application's schema. Two ordinary tree collections make that possible.

**A reference tree** lists the blobs one collection references. Its entries are keyed by reference, then by whatever names the referrer (for a SQL table: primary key, then column), so "is this blob referenced here?" is a short range read, and many blobs are checked in one ordered pass. An entry is written and removed **in the same transaction** as the row that holds or drops the reference. `db-core` provides the helper that stages these entries; the SQL plugin is to use it for every table with a blob column, and an application writing collections directly uses it itself.

**The scope registry** is one small tree per network, at a well-known id, listing the ids of the network's reference trees. A reference tree is added to it once, when it is created, and removed when the collection that held the references is dropped, which makes the blobs it listed unreferenced there. It is how a storage node enumerates every place a reference could be without reading a schema catalog.

So a blob is not registered anywhere on its own. What is registered is the *reference*, as a side effect of the transaction that commits it, and a blob is alive while any registered reference tree lists it.

**Keys and entries.** Both are `Tree` collections keyed by an entry's first element under the default comparator, which orders strings by UTF-16 code unit as the SQL plugin's trees do, and each entry is a pair of strings, the shape of the plugin's rows, so the plugin can open them through its own collection factory. A reference-tree key is the reference, the character U+0000, then the referrer (`blobReferenceKey` in `packages/db-core/src/blob/reference-key.ts`, which refuses a string that is not a reference), and its entry is `[key, reference]`. A reference is lowercase base32, so it never contains U+0000: the first one in a key ends the reference, the referrer may be any string, and the keys of one reference are the one run from the reference plus U+0000 up to, not including, the reference plus U+0001 (`blobReferenceRange`), the runs in reference order. That holds even where one reference is a prefix of another, which cannot happen between valid references today, since all are 59 characters. `decodeBlobReferenceKey` splits a key back. A scope-registry entry is `[scope, scope]`.

**Staging.** `BlobReferenceTree` in `packages/db-core/src/blob/reference-tree.ts` wraps a reference tree. Its `stage`, `stageAdd` and `stageRemove` stage one action and never sync; the action (`blobReferenceAction`) upserts `[key, [key, reference]]` for an add and deletes the key for a remove, and is a pure function of the changes, so a validating member derives the same operations. The entries commit or roll back with whatever the caller commits the tree with:

- one collection: `tree.sync()`;
- with the rows: `tree.getCollection()` in the collection map of the caller's `TransactionCoordinator`, beside the row collections, so one commit carries all of them, as the SQL plugin commits its index trees;
- offline: `tree.getCollection()` passed to `OfflineQueue.enqueue` with the row collections, so it is sealed into the same entry.

A rollback drops the staged action with the caller's others. A change of reference is a remove of the old pair and an add of the new; nothing here reads the old value. `BlobScopeRegistry` and its id, `BLOB_SCOPE_REGISTRY_ID` (`optimystic/blob-scope-registry`), are in `packages/db-core/src/blob/scope-registry.ts`: `stageRegister` and `stageUnregister` stage into a caller's transaction, and `register` and `unregister` open, stage and sync in one step. Unregistering leaves the reference tree alone. A register racing an unregister of one scope ends as whichever commit is applied last; their callers, table create and drop, are serialized by the catalog.

**No guards.** Neither tree's entries carry a guard ([internals.md §Blob reference trees and the scope registry carry no guards](internals.md#blob-reference-trees-and-the-scope-registry-carry-no-guards)). An add is an upsert of a key fixed by reference and referrer with a value fixed by the key, and a remove is a delete of a fixed key that does nothing when the key is absent, so conflict replay and the offline queue's replay, which re-run them over newer committed state, leave the state each change describes. Two writers adding one reference from different referrers write different keys, and the row a referrer names carries the guard that refuses a racing change to it, as index entries rely on. The registry departs on purpose from guarding a registration `absentOrEqual`: an unguarded upsert of the fixed entry is never refused, so two machines registering one scope both commit and the registry holds one entry. `absentOrEqual` would add nothing, and it is counted in the offline queue's already-applied tally where reference entries are not, so an offline entry that registered a scope a rival had already registered, beside reference entries, would be reported `already-applied` although its references landed.

**The SQL plugin's use of both.** A table with a `blobref` column opens its reference tree through the plugin's own collection factory, at its collection's `/blobrefs` child, so the tree carries the factory's tree options and joins the per-transaction collection cache exactly as the table's index trees do; `BlobReferenceTree`'s constructor wraps that handle. The tree is then one more dirty tree and one more registered collection, which is what carries it on every commit route — the session coordinator, the legacy batch, the per-tree sweep and an offline queue entry — with no commit-route code of its own ([internals.md §A table's blob references](internals.md#a-tables-blob-references)). Staging is a pure function of the rows, the keys and the column list, which is what lets a validating member derive the same operations.

The registry is written at exactly two moments, both DDL: the `create table` of a table that has a `blobref` column, and the `alter table … add column` that gives a table its first one. Either refuses the statement when the registration cannot be confirmed, since a scope the registry does not list is one no storage node reads. `BlobScopeRegistration` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-scope-registration.ts` reads the registry first and registers only what it does not already list, remembering per (network, scope) what it has confirmed, so the steady state costs nothing. `drop table` unregisters, logging and continuing on failure — the blobs that tree lists then stay referenced, which keeps bytes rather than losing them. Hydrating a table registers NOTHING: a first touch writes only what the table owes ([internals.md §A first touch writes only what the table owes](internals.md#a-first-touch-writes-only-what-the-table-owes)), and a hydrated table's tree was registered by whichever machine created it. The gap that leaves — a tree missing from the registry because it was created by a build that registered nothing, or dropped on another machine while this one kept writing — is closed where it matters rather than by a registry read per table at every start: the pin lifecycle confirms the scope before any announcement names it, and a receiver only ever reads a scope it was told about, so a reference committed before its tree is registered is harmless until the announcement.

**Reading.** Two readers answer the questions copying and reclaiming ask, and each says whether its answer can be trusted. `BlobReferenceTree.listed` says which of a set of references a reference tree lists, in one ascending pass merged with the sorted references: one descent per reference, skipped for each reference the cursor already answers, rather than a scan of every entry between the first reference and the last. `BlobScopeRegistry.enumerate` lists every registered scope, and says whether the registry has ever been written. Both read through `readCommittedTree` in `packages/db-core/src/blob/committed-read.ts`, which opens a fresh handle with `Tree.open` on every call (two requests) and stages nothing into it: the handle adopts the newest committed revision it is told of, and a caller's own staged entries never leak into the answer. A tree never written reads as empty, and the read brings nothing into existence. An answer is **certain** exactly when the open and the read completed, neither threw `BlockUnavailableError` or `BlockPossiblyStaleError`, and the handle received no below-floor answer (`Collection.belowFloorAnswerCount`, see [internals.md §A block re-read after a refresh can be answered too old, and is never remembered](internals.md#a-block-re-read-after-a-refresh-can-be-answered-too-old-and-is-never-remembered)). Otherwise the reader logs `blob:read-uncertain` ([debugging.md](debugging.md)) and answers uncertain, keeping what it found, since a reference found listed is listed; any other error propagates. Two limits. A fresh handle floors only the blocks named by its log tail block's entries, so a block answered too old, last changed by an entry in an older log block, is not detected; that is the limit every reader in this system has, and the two passes a grace period apart under [Lifetime](#lifetime) are what cover it. And an absent answer that rested on asking nobody is not told apart here; reclaiming will add that.

**The node's reader.** A node deciding whether it may take a blob reads committed state through `BlobReferenceCheck.inScope` in `packages/db-p2p/src/blob/reference-check.ts`, over the node's own `NetworkTransactor`: registry first, so a scope the registry does not list is answered not listed without its reference tree being read, and then that scope's tree, any read it cannot trust answering uncertain rather than absent.

**Under transaction validation** these entries are derived, not asserted. A validating member re-executes the transaction's statements, and the plugin derives the reference-tree entries from the rows the statements change, as it derives index entries. A writer therefore cannot commit a row without its entry, or remove an entry while keeping the row: the operations would not match what the members compute. Members never check whether the bytes exist; that is not a deterministic function of the transaction. Where no member re-validates (no deployment does at pend today — backlog `feat-no-deployment-validates-transactions-at-pend`), a reference tree is exactly as trustworthy as an index tree: a writer the cohort accepts could falsify either.

## Moving pieces between machines

**Built:** the protocol, its framing and all four requests, on both ends; the fetcher (`BlobFetcher` in `packages/db-p2p/src/blob/blob-fetcher.ts`), which the node builds on both roles; and `read` from other machines and the `stat` probe, through `node.blobs` (`NodeBlobService` in `packages/db-p2p/src/blob/node-blob-service.ts`, §[The node's blob service](#the-nodes-blob-service)); and acting on a `held` that arrives — it adds its sender to the blob's owed entry and re-counts the blob's durability (`onHeld` in `packages/db-p2p/src/libp2p-node-base.ts` into `BlobCopyDrain.noteHeld`, §[Placement, copying and durability](#placement-copying-and-durability)), and one from a peer the network's membership predicate does not admit is dropped unread, as its announcement is.

One new protocol, `<prefix>/db-p2p/blob/1.0.0` (`buildBlobProtocol` in `packages/db-p2p/src/blob/blob-protocol.ts`), served by `BlobProtocolService` in `packages/db-p2p/src/blob/blob-protocol-service.ts` on serving and client nodes alike: a client holds the blobs its own host put, and until a row referencing one commits it holds the only copy (§[Placement, copying and durability](#placement-copying-and-durability)). It is the first protocol here that carries more than one frame per stream and the first that carries raw bytes, so it does not go through `ProtocolClient` (`packages/db-p2p/src/protocol-client.ts`), whose single reply and one-time resend assume a small request and answer: `BlobProtocolClient` in `packages/db-p2p/src/blob/blob-protocol-client.ts` shares only its dial step (`openStreamWithin` in `packages/db-p2p/src/protocol-client.ts`). Frames are length-prefixed (`readBlobFrames` and `sendBlobFrame` in `packages/db-p2p/src/blob/blob-frames.ts`). The first frame in each direction is a small JSON header, at most `MAX_BLOB_HEADER_BYTES` (16 KiB); a piece is one frame of raw bytes, at most `MAX_BLOB_PIECE_FRAME_BYTES` (1 MiB). A frame over its cap is refused at its length prefix, before its bytes are read. The limits are in `packages/db-p2p/src/protocol-limits.ts`.

| Request | Answer |
|---|---|
| `stat` — references | For each: `whole`, `partial` or `none`. |
| `get` — up to 16 piece CIDs | A header saying which are held, then one raw frame per held piece, in the order asked. |
| `announce` — a reference and its scope, 1 to `MAX_BLOB_SCOPE_CHARS` (1024) characters | `whole` (already held), `fetching` (will pull it), `declined` (does not take blobs), `not-responsible` (its own view of the blob's cohort does not include it) or `unreferenced` (it did not find the reference: the scope is not registered, does not list the blob, or could not be read). |
| `held` — a reference | Empty. Sent to a peer that announced, when the pull completes. |

**The frame sequence.** The requester sends its one header frame and closes its write side, then reads on. The responder reads that one frame and answers at once, without waiting for the requester's end of stream, and never reads a second frame. A `stat` names 1 to `MAX_BLOB_STAT_REFS` (64) references and is answered with one header frame, its holdings in request order, from what the responder holds itself. A `get` names 1 to `MAX_BLOB_GET_PIECES` (16) piece ids, none twice, and is answered with a header saying which are held, then exactly one frame per held piece in the order asked, then end of stream. A request the responder will not serve is answered `refused`: `malformed` for one that breaks a rule of the header codec, `busy` for a `get` over its allowance of `MAX_BLOB_INBOUND_GETS_PER_PEER` (2) streams at once per peer and `MAX_BLOB_INBOUND_GETS` (16) per node. The client refuses, before dialing, any request the responder would call malformed. A responder whose header said it held a piece that is gone when its turn comes (a sweep removed it in between) resets the stream, and the requester keeps the pieces that already arrived. The client's `get` resolves once the header is read and hands over each piece as its frame completes; it reads exactly the pieces the header named and then requires end of stream, so a missing piece is reported as `truncated` and a surplus frame as `extra frame`. The client verifies nothing: the fetcher checks each piece against its id before storing it.

**A sender of `announce` or `held` does not dial a peer whose protocol list lacks the blob protocol** (`blobAcceptanceOf` in `packages/db-p2p/src/blob/accepts-blobs.ts`, over `Libp2pKeyPeerNetwork.protocolSupport` in `packages/db-p2p/src/libp2p-key-network.ts`): such a peer, an older build (§[Compatibility](#compatibility)), fails the request at once with `BlobPeerRefusesError` rather than as a failed protocol negotiation. A peer not yet identified, whose list is empty, is dialed, and a refusal then arrives as that failed negotiation. `stat` and `get` are not checked here, since the fetcher already chooses its candidates among peers whose list names the protocol.

**Content moves by `get` only, and the receiver always pulls.** A node that wants a blob copied to another machine announces it; the other machine decides whether to take it and then fetches at its own pace. There is no push of content, so a node never has to accept, buffer or verify bytes it did not ask for, and there is one code path that receives and checks pieces.

**Answering an `announce`** is `BlobAnnounceReceiver.decide` in `packages/db-p2p/src/blob/announce-receiver.ts`, which reaches the cheapest answer first and reads committed state last:

1. A node configured `on-demand` (§[Placement, copying and durability](#placement-copying-and-durability)) answers `declined`, before any lookup.
2. An announcer the network membership predicate refuses is answered `unreferenced`, before any lookup. The inbound stream gate, when one is configured, already refused such a peer's stream; this covers a node given only the predicate.
3. A blob whose cohort, by this node's own view, does not include it is answered `not-responsible` — as is one whose cohort lookup fails, since responsibility is then undetermined and the announcer asks again.
4. An announcer over its allowance (§[Who may fetch and who may store](#who-may-fetch-and-who-may-store)) is answered `unreferenced`, with no read of committed state. The allowance is spent after the cohort check on purpose: an honest peer whose view of the cohort differs from ours spends none of it.
5. Only then is committed state read, under the node's shared read limit, and only the scope the announcement names (`BlobReferenceCheck.inScope` in `packages/db-p2p/src/blob/reference-check.ts`). Anything but a listed reference — an unregistered scope, a tree that does not list the blob, a read that cannot be trusted — is `unreferenced`.
6. The `responsible` hold is taken and flushed, and the blob is answered `whole` when it is already here and `fetching` otherwise, with the pull started and the announcer noted as awaiting `held`. The hold is durable before the answer leaves, so a node restarted after answering `fetching` still owes the pull and finishes it (`BlobAnnounceReceiver.resume`, which the node calls on its way up).

**The reference read is time-boxed to half a response timeout**, measured from the start of the decision so that waiting for a read slot counts. Both ends of a blob exchange abort a stream that moves no bytes for one response timeout (`ProgressDeadline` in `packages/db-p2p/src/blob/progress-deadline.ts`), and nothing moves while the receiver reads: a decision slower than that would reset the stream on both sides, so the read is given half the timeout and the answer frame the other half. A read that runs late is answered `unreferenced` — the same answer "could not read" gets, which the announcer already asks about again. A read that has **started** keeps its read slot until it finishes, so a slow read still counts against the node's read work; a read still **waiting its turn** when the budget runs out is dropped from the queue unrun. That is what keeps the four slots a bound on the node's work rather than a queue in front of it: announcements arriving faster than reads finish would otherwise pile up reads for answers already sent, and the node would spend its whole read allowance on decisions nobody is waiting for. Rejected: a keep-alive frame sent while reading, which is a wire change for a case the re-announcement already covers.

One pull runs per reference however many peers announce it. A second announcer joins the pull in flight and is sent `held` with the first; it is not added to that session's candidates, since a session fixes its known holders when it starts. A pull that gives up keeps the hold and the next announcement starts a fresh one. `held` is sent to each awaiting announcer the membership predicate still admits, once, and a send that fails is not retried: the announcer's own drain re-announces and is then answered `whole`.

**Fetching.** `BlobFetcher.start` brings here every piece a blob, or a byte range of it, lacks; it is the one code path that receives pieces. Each call is a session, which works from the top of the tree down:

1. It walks the range over this node's pieces (`walkBlobPieces`). A walk yields a list piece before its children and skips the subtree of a list piece that is absent, so its absent entries are the **frontier**: the missing pieces whose parent is here, or the root when it is missing. When nothing is missing the session ends there, having taken no hold, looked up no cohort and asked no peer.
2. Otherwise it takes the `cached` hold (§[Holds](#holds)) and walks again. The first walk ran under no hold, so a sweep may have removed pieces it saw; the hold protects whatever the second walk sees.
3. It asks holders in **rounds**. A round's candidates are `blobHolderCandidates` in `packages/db-p2p/src/blob/blob-holders.ts`: the caller's `knownHolders` first, then the blob's cohort, connected members first, less this node, malformed ids, peers the membership predicate refuses, banned peers and peers whose record does not list the blob protocol, with deprioritized peers last. They are found again each round, so a holder that connects while a session waits is asked.
4. A session sends one `get` at a time, of up to 16 frontier pieces in tree order, to the first candidate that has not yet answered for some of them. Each piece is checked against the id that named it (`checkPiece` in `packages/db-core/src/blob/verify.ts`), with the digest this node's store names its pieces by (`BlobFetchStore.digest`), and only then stored. A list piece makes its children known, so the session walks again after a batch that stored one, and only then.
5. Pieces a holder reports not held, and pieces a failed request did not deliver, go to the next candidate in the same round. A request fails on a dial failure, a stall, a refusal (`busy` included), a broken frame sequence or a reset; that holder is not asked again in the round, and the pieces it delivered before failing stay stored.
6. The round ends when every candidate has answered, or failed, for every frontier piece. The session walks once more. With nothing missing, a session for the whole blob records it as whole, and the session resolves. Otherwise the attempts at the first missing piece decide the failure (below). With `waitMs`, a session whose last piece arrived less than `waitMs` ago waits instead, 500 ms at first and doubling to 8 s (`BLOB_WAIT_RETRY_INITIAL_MS` and `BLOB_WAIT_RETRY_MAX_MS` in `packages/db-p2p/src/protocol-limits.ts`), and runs another round; a piece arriving resets both.

**A wrong piece.** Bytes that do not hash to their id are discarded, the peer that sent them is penalized once (`PenaltyReason.InvalidRestoration`, the reason the block repair paths use for content that fails verification), the rest of its answer is abandoned, and the session does not ask that peer again. Another holder supplies the piece. A list piece whose hash is right and whose structure is not fails the session with `BlobCorruptError` from the walk and penalizes nobody, since every holder would serve the same bytes.

**What a round that leaves a piece missing means** (`unavailableOutcome` in `packages/db-p2p/src/blob/blob-holders.ts`), judged from one attempt per candidate of the round, with each peer that served the piece wrong counted as `corrupt`:

| Attempts at the first missing piece | The session fails with |
|---|---|
| none, or every one unanswered | `BlobUnavailableError`, `cohort-unreachable` |
| some unanswered, the rest not held or wrong | `BlobUnavailableError`, `peers-unreachable` |
| some wrong, every other one not held | `BlobCorruptError`, `digest-mismatch` |
| every one not held | `BlobUnavailableError`, `not-held` |

**Resumption** follows from the pieces: each one is verified and stored as it arrives, so a fetch that is interrupted asks only for what is still missing, from the same peer or another. A session that fails or is cancelled keeps its hold and every piece it stored, and the next session plans against them. `packages/db-p2p/test/blob-fetcher.spec.ts` pins resumption, the penalty for a wrong piece, and one request per piece for two sessions fetching one blob at once.

**One request per piece.** A fetcher's sessions share one record of the pieces in flight (`PieceTraffic` in `packages/db-p2p/src/blob/blob-piece-traffic.ts`). A piece another session is fetching is awaited, not asked for again, and is asked for when that attempt ends without it, so two reads of one blob request each piece once. A session chooses its pieces only once it holds a stream (below), so a session waiting for a stream holds up no other session's pieces. A request already sent finishes even when its session is cancelled, since another session may be waiting on its pieces and what it stores is kept; only stopping the node aborts it.

**Deadlines follow progress, not size.** A `get` has no total time limit. Each end runs a `ProgressDeadline` (`packages/db-p2p/src/blob/progress-deadline.ts`) of one response timeout of the declared link (`LinkDeadlines` in `packages/db-p2p/src/rpc-deadline.ts`), pushed back by every chunk of bytes read or written rather than by whole pieces, and aborts the stream with `BlobTransferStalledError` when it fires. The sender writes a piece frame and, when the transport reports its buffer full, waits for it to drain under the same deadline (`sendBlobFrame`); it reads each piece from its store just before sending it, so it holds one piece plus what the transport buffers, never the whole answer. A dead path, a responder whose header promises a piece it never sends, and a requester that stops reading each fail within one timeout; a slow link that keeps delivering finishes. `packages/db-p2p/test/blob-protocol-stalls.spec.ts` pins the last two.

**What the receiver buffers.** The bound on the receiving side is the request, not one piece. libp2p queues every chunk that arrives on a stream ahead of its reader, and nothing on the receiving side pauses the sender, so one `get` stream can queue all of its pieces: 4 MiB for the 256 KiB pieces this design writes, 16 MiB for 1 MiB pieces from other tools. Pausing the stream was rejected as the bound: a paused libp2p stream holds what has already been granted to the sender up to its `maxReadBufferLength` (4 MiB by default) and then resets the stream, and the multiplexer's window for a fast stream can grow past that, which would reset honest transfers of 1 MiB pieces (the `NOTE:` at `readBlobFrames`).

**No prepared stream.** The blob protocol is not in the node's pool of streams negotiated ahead of the next request (`preparedStreamProtocols` in `packages/db-p2p/src/libp2p-node-base.ts`). That pool saves one negotiation round trip on a small request, which is negligible against a 16-piece `get`, and it would hold an idle blob stream open to each peer for 30 s after every request.

**Other traffic is not held up.** A fetch is foreground when someone is waiting on it (a read) and background otherwise (copying). A node opens at most one `get` stream per peer of each priority, and at most `MAX_BLOB_FOREGROUND_GET_STREAMS` (8) foreground and `MAX_BLOB_BACKGROUND_GET_STREAMS` (4) background streams in all (`BlobGetSlots` in `packages/db-p2p/src/blob/blob-get-slots.ts`), each carrying at most 16 pieces, so the stream multiplexer interleaves transaction and read traffic between pieces. The two priorities draw on separate allowances, so a read never waits for a background stream: it opens its own beside it, and a responder's allowance of two streams per peer (`MAX_BLOB_INBOUND_GETS_PER_PEER`) is one of each. A read waits behind background copying only for a piece already in a background request, which is at most 16 pieces and is ended by the progress deadline if it stalls (the `NOTE:` at `PieceTraffic`).

**Relays.** A circuit relay with stock limits resets a relayed stream after 128 KiB, less than one 256 KiB piece, and the client sees the stream's error. A blob cannot cross such a relay; the fetch fails, keeps what it stored, and resumes when a direct or unlimited path exists.

## Who may fetch and who may store

IPFS answers neither question: anyone may fetch a block from anyone who has it, and a node stores what its operator pins. Here both have answers.

**Fetching is limited to the network's members.** The blob protocol is gated by `authorizeInboundStream` like the four database protocols (`createInboundStreamAuthorization` in `packages/db-p2p/src/inbound-authorization.ts`), and a node fetches from, and announces to, only peers its network membership predicate admits. The protocol id carries the network's prefix, so two networks sharing a machine or a relay do not see each other's requests. Inside a network, any member can fetch any piece whose CID it knows, which is the same reach a member has over blocks. A network with no predicate is open, as it is for blocks.

**Storing is authorized by a committed transaction, not by who asks.** A node takes a blob on another's behalf only after reading committed state and finding the reference in the scope the announcement names, and only when that scope is in the registry and the node is in the blob's cohort. An announcement is a hint about where to look; it grants nothing. One from a peer the membership predicate refuses, or from a peer over its allowance, is answered `unreferenced` without any read. The right to make a network store bytes is therefore exactly the right to commit a row, which the network already governs.

**The allowance** is two numbers, both in `packages/db-p2p/src/protocol-limits.ts` and applied by `AnnounceLimiter` in `packages/db-p2p/src/blob/announce-limiter.ts`:

- `BLOB_ANNOUNCES_PER_PEER_PER_MINUTE` (600), counted in a fixed one-minute window per peer. Past it an announcement is answered `unreferenced` with no read. It is far above what an honest announcer sends: its drain examines at most 64 owed entries a pass with at least 15 s between passes (256 a minute), and the reaction to a cohort change announces at most 64 blobs a check with at least 60 s between checks. The window of a peer not seen for a minute is started again on its next announcement, so a quiet peer is never refused for traffic it sent long ago.
- `BLOB_REFERENCE_READS_IN_FLIGHT` (4), the reads of committed state the node runs at once across every peer together, with the rest waiting their turn — and dropped from that queue, unrun, if the announcement they would answer is answered first (§[Moving pieces between machines](#moving-pieces-between-machines)). Reader repair (§[Placement, copying and durability](#placement-copying-and-durability)) draws on the same four, so no number of announcing peers, and no number of local reads, raises the node's read work.

The node remembers at most `BLOB_ANNOUNCE_PEERS_TRACKED` (4096) peers' windows; a new peer past that evicts the window that started longest ago. A flood of fresh peer ids can therefore evict a real peer's window and let it send more than its allowance for a minute, which is why the read limit above, and not the per-peer count, is what bounds the work.

There is no access control finer than membership: a reference is not a secret within a network, and a member that knows a CID can learn whether the content exists. An application that needs more than that encrypts before `put`.

## Placement, copying and durability

**Who is responsible.** A blob's routing key is the digest in its reference; the key network turns it into a coordinate and a cohort exactly as it does for a block (`routingKeyForBlob` beside `routingKeyForBlock` in `packages/db-core/src/network/routing-key.ts`). A node may be configured not to take blobs it is merely responsible for (`NodeOptions.blobs`'s `hold`, `'on-demand'` against the default `'eager'`, in `packages/db-p2p/src/libp2p-node-base.ts`): such a node answers every announcement `declined` before any lookup, never takes a `responsible` hold, runs no reader repair, and holds only what it wrote, pinned or read. This is how a phone joins a group without storing every file in it.

**Copying.** `announce` records a durable **owed entry**: the reference, its scope, and the members known to hold the blob. **Built:** the entry itself, `OwedBlobLedger` in `packages/db-p2p/src/blob/owed-blob-ledger.ts`, one JSON value per blob under `owed-blobs/<reference>` in the node's key-value store (`OWED_BLOB_KEY_PREFIX`, listed in `NODE_KV_NAMESPACES`); the entry point, `node.blobs.announce`, which takes the `owed` hold and only then records the entry — so a crash between the two leaves a hold, never an entry announcing a blob nothing keeps — and resolves once the entry is durable and the blob's first durability has been reported, never waiting for a copy; and the drain itself, `BlobCopyDrain` in `packages/db-p2p/src/blob/blob-copy-drain.ts`, built on serving and client nodes alike, since a client is often the machine a blob was put on and the only holder of it until the cohort copies it. `NodeOptions.blobs`'s `copy` sets its schedule, in the same fields `NodeOptions.underReplicationDrain` sets the block drain's and with the same defaults; `copy: { enabled: false }` builds no drain at all, and then `node.blobs.announce` refuses rather than taking a hold on a blob nothing would ever announce — such a node still serves, fetches and holds blobs. It stores the **confirmed holders**, not the missing members: who is still owed is derived afresh from the cohort on each pass (`owed = accepting cohort members − holders − this node`), which is how the entry follows the cohort. A holder that leaves the cohort stays listed — a copy is a copy — and simply stops counting, since durability is counted over current members. Entries are not capped: they are bounded by the blobs this node announced, and §[Lifetime](#lifetime)'s reclaiming drops the entry of a blob whose scope stopped listing it. A drain announces the blob to each owed member that is connected, on start, when a peer connects or is identified, and on a timer while anything is owed, skipping passes during a detected partition. It is the same schedule, give-up rule and membership filter as `UnderReplicationDrain` (`packages/db-p2p/src/repo/under-replication-drain.ts`), and the two share that scheduling code rather than repeating it: `DrainScheduler` in `packages/db-p2p/src/repo/drain-scheduler.ts`. So the entry follows the cohort. A member is taken off the entry when it reports `whole` or sends `held`. A member that answers `declined` is remembered as declining until it next connects, and is not owed. A member that answers `not-responsible` or `unreferenced` is asked again on a later pass, under the give-up rule: the first means the two machines' views of the cohort differ for now, the second that the member has not seen the commit or could not read it. A member that answers `fetching` is re-announced on every later pass rather than given up on, since nothing but its `held` says whether the pull it started ever finished; one announcement a pass is the cost.

**Durability** is reported in the classes a commit uses (`DurabilityQuorum` in `packages/db-core/src/network/struct.ts`), counted over the cohort members that accept blobs, with the count beside the class:

- `unrouted` — the cohort could not be resolved.
- `local` — this node alone holds it, or fewer than a strict majority of the accepting members do. This is wider than a commit's `local`, because a commit is not acknowledged below a majority and a blob is usable from its first copy.
- `majority` — a strict majority of the accepting members hold it.
- `full` — every accepting member holds it, and at least one of them is not this node.

**Built:** the rule itself, `classifyBlobDurability` in `packages/db-p2p/src/blob/blob-durability.ts` — pure, over a cohort view and the set of known holders — and the class it reaches, stored on the blob record (`BlobRecord.durability`) so `stat` answers it and a restart does not re-emit an unchanged class. The order of the four classes is part of the rule: "nobody else accepts blobs" is checked before the arithmetic, so a cohort of just this node never reads as a strict majority of itself.

Each change is an `onDurability` event, and reaching `full` removes the owed entry and its hold. In a group where no other member accepts blobs the class stays `local` and the writer keeps the blob; readers fetch it from the writer on demand.

**Built:** the reporting, in `BlobCopyDrain` (`packages/db-p2p/src/blob/blob-copy-drain.ts`). Every path that can change a blob's durability — the first one `announce` reports, a pass, an arriving `held` — goes through one method, serialized per reference, so no class is written or announced twice; a change of the class *or* of how many members hold it is one event, since an application waiting for the bytes to be elsewhere cares about the count as much as the class. Reaching `full` writes the class on the record, deletes the owed entry and only then releases the `owed` hold, in that order: a crash part-way leaves at worst a hold with no entry, which keeps the bytes. Releasing that hold may delete the record outright when `owed` was its last hold — the writer has stopped holding the blob on the others' behalf — which is why `stat` on such a blob afterwards reports `unknown` with no durability rather than `full`.

**When the cohort changes.** A node's held blobs are enumerable from its records, so the cohort comparison `RebalanceMonitor` (`packages/db-p2p/src/cluster/rebalance-monitor.ts`) makes for blocks is made for blobs too, by giving it the routing key rule rather than a second copy of its logic (`RebalanceMonitorDeps` in `packages/db-p2p/src/cluster/rebalance-monitor.ts` is where the rule and the set of ids to watch are supplied). A member that joins a held blob's cohort is announced to. A node that leaves a blob's cohort drops its `responsible` hold only after confirming that enough current members hold the blob.

**Built:** the decision, `BlobCohortReaction.handleRebalanceEvent` in `packages/db-p2p/src/blob/cohort-reaction.ts` (named after the block counterpart it mirrors, `BlockTransferCoordinator.handleRebalanceEvent`); and the second monitor instance over blob references, wired in `packages/db-p2p/src/libp2p-node-base.ts` on a node that serves blocks with Arachnode and FRET present, from the same `NodeOptions.rebalance` settings as the block instance — one switch and one set of tuning for reacting to cohort changes. A client is in no cohort and never takes a `responsible` hold, so it gets no such monitor; its own announced blobs are followed by the copy drain on its own passes. Three things the comparison itself does not say:

- **What is watched** is the references whose record carries an `owed` or a `responsible` hold — the two holds that mean *kept for the network*. A pin and a `cached` hold are the machine's own business, so a node never announces a blob it merely read. The set is fed from the records as holds appear and go (`LocalBlobService.onHoldsChanged` in `packages/db-p2p/src/blob/local-blob-service.ts`) and re-derived at every start (`seedHeldBlobs` in `packages/db-p2p/src/blob/held-blob-seed.ts`), which also re-reports the holders the writer's owed entries already name, so a restart does not re-announce to members already known to hold the blob. A `responsible` holder has no such memory — the holders of a blob it did not write are recorded nowhere — so it announces once to its whole cohort after a restart, and each receiver answers `whole` without reading anything.
- **The release rule** counts only the new owners that accept blobs: the replication floor `RebalanceMonitor` uses for a block, capped by how many of them there are, and where there are none there is nobody else to keep the blob, so the hold stays. Only the `stat` answers count, never a reply to an announcement sent in the same pass, so the decision is made over one snapshot of the cohort. A hold whose release is not confirmed is retained and re-reported on the next check (`RebalanceMonitor.retainLost` in `packages/db-p2p/src/cluster/rebalance-monitor.ts`), so a node leaving a cohort that holds too few copies keeps the blob until enough current members hold it.
- **`fetching` satisfies growth**, as `whole` and `declined` do: the receiver has already taken a durable `responsible` hold and resumes its pull after a restart, and the `held` it eventually sends reaches the monitor as holder evidence through the drain. A member that will never hold the blob — one that declined, one that refuses the blob protocol, one the network membership predicate does not admit — is owed nothing either, since counting it owed would keep this node's hold for ever.

**Readers repair.** **Built:** `BlobAnnounceReceiver.keepAfterRead` in `packages/db-p2p/src/blob/announce-receiver.ts`, which `node.blobs` calls once a fetch it started has brought a blob whole here. A node that accepts blobs, is in the blob's cohort by its own view, does not already hold it `responsible`, and finds it referenced by some registered scope (`BlobReferenceCheck.anywhere` in `packages/db-p2p/src/blob/reference-check.ts`, read under the same limit of four reads at once) keeps it under a `responsible` hold under that scope. Anything else leaves the fetch's `cached` hold exactly as it is, and a read of a blob already held `responsible` reads no committed state at all.

## Committing a reference

The transaction that commits a row carries the reference and its reference-tree entry, and nothing else. Its relation to the bytes is:

- **The reference lands before the bytes move.** No member checks availability when it votes. Checking would tie consensus to bulk transfer, would make an offline commit impossible, and is not something every member can compute alike.
- **The writer keeps what it wrote.** While a transaction that references a blob is open or queued, the blob is pinned on the writer. When the transaction commits, the writer announces the blob and holds it as `owed` until its cohort fully holds it. So a committed reference is always backed by at least the writer's copy, and a reader that cannot reach it sees "not yet", not a broken file. **Built for every commit that reaches storage or the offline queue**, in `SqlBlobPins` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pins.ts`), which the transaction bridge calls from one place per commit route. What is pinned is the fold `addedReferences` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-reference-ledger.ts`) takes over everything the transaction's statements staged: the last change at each referrer — one row's one column, which holds at most one reference — and then the surviving adds, deduplicated per scope. So an insert and a delete of one row in one transaction pin nothing, an update from one reference to another pins only the new one, a primary-key move keeps the reference pinned, and a reference merely removed from a row committed earlier is never pinned. Each reference is pinned whether or not this machine holds its bytes: one copied from another row commits and reads as not held, and announcing it still tells its cohort where to look. Once the commit lands the writer announces each reference into the scope its table's reference tree names and then unpins — announce before unpin, so no instant leaves a committed reference with no hold here — and it drops the `unstaged` pin the bytes were put under. The release is awaited before the commit returns, so when a host's `await db.exec(…)` resolves every reference the transaction added has been announced and its durability already reported to every `plugin.blobs.onDurability` listener, which is what the two-commit pattern below waits on. A reference whose scope the network's registry does not confirm, and one whose announcement fails, KEEP their pin and are logged (`blob:pin-kept`): the bytes stay here and the release is retried later, which is a deferral rather than a loss.
- **A transaction that rolls back** leaves nothing behind anywhere else: its bytes never left the writer, and unpinning lets the writer's sweep remove them. **Built**: every reference pin the commit took goes, and so does the `put` pin of every blob the transaction put while it was open. An `unstaged` pin — the application's own hold on bytes it put OUTSIDE the transaction — is deliberately left in place, so a retry of the insert need not put the bytes again; the holding period bounds it instead.
- **A reader decides how long to wait.** `stat`, `read` with `waitMs`, and the typed reasons give an application what it needs to show "still arriving".
- **An application that wants the bytes on the network before anyone sees the reference** commits twice. It first commits a row that only holds the reference (an attachment row), which is what authorizes the cohort to store the blob. It waits for `onDurability` to report `majority` or `full`. Then it commits the row people act on (the message that shows the attachment). The second commit cannot land before the bytes are held by others, and no machine ever stored bytes that no committed row referenced. `packages/quereus-plugin-optimystic/test/two-node-blob-reference.integration.spec.ts` pins the whole pattern over two real machines: the announcement goes over the wire off the first commit, the other machine reads committed state and pulls the blob, durability rises past `local`, and the bytes are shown to be there before the second commit runs.

## SQL

The plugin registers a logical type, **`blobref`** (`BLOBREF_TYPE` in `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts`): text whose value must be a well-formed reference, by the one rule `isBlobRef` in `packages/db-core/src/blob/blob-ref.ts` applies. Anything else is refused as a type mismatch where it is written — an upper-cased or padded spelling of a real reference included, since a blob has exactly one accepted spelling — and NULL means the row references nothing. A column of that type is an ordinary value to the engine, to conflict resolution and to the wire: it is stored and compared as the text it is, so an index on it is an ordinary text index, and a `collate` other than BINARY is refused on it because the type's comparison ignores collations.

A build that does not have the type neither opens such a table nor writes a catalog record for one. The plugin refuses both, naming the table and the column, rather than letting the fallback type rules read the name `blobref` as a **`blob`** column — whose row codec base64-*decodes* every stored string, leaving the table silently and permanently wrong about its own contents. Refusing the *write* as well as the open is what keeps one such build from making the table unopenable for the builds that do have the type: a record it persisted would say the rows are `blob` where they were written as `blobref`, and every correct reader would then refuse the disagreement. A host that loads the plugin through `registerPlugin` gets the type with it; a host registering the plugin's parts by hand must register `plugin.types` as well as its `vtables` and `functions`.

```sql
create table Attachment (
	Id text primary key,
	Name text,
	ByteSize integer,
	Content blobref null
);
```

```ts
const { ref, size } = await plugin.blobs.put(fileStream);
await db.exec('insert into Attachment (Id, Name, ByteSize, Content) values (?, ?, ?, ?)', [id, name, size, ref]);
for await (const bytes of plugin.blobs.read(ref)) { /* … */ }
```

- **`plugin.blobs`** is the blob service for the plugin's default network — the one a table declared with no `using` clause binds to — and `plugin.blobsFor(table)` the service of the network a given table uses (`SqlBlobService` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/sql-blob-service.ts`). A reference means something only in the network whose machines hold the bytes. Each resolves its network on first use, so a host may still set the session's `default_vtab_args` after registering the plugin, and the network of a `network` transactor is not built merely because the plugin was registered. Two services over one network are separate objects over one store: they read the same blob records, hold the same pins and each receive the same events. A transactor with no libp2p node — `local`, `test`, `mesh-test`, or a custom one — gets a single-machine service instead (`SingleMachineBlobService` in `packages/db-p2p/src/blob/single-machine-blob-service.ts`), whose cohort is that machine alone, so a committed reference's durability stays `local`. Where its pieces and records live is the plugin's `blobStorageFactory`, in memory by default.
- **A put outside a transaction** (as in the example above) is pinned as `unstaged`, and that pin ends one of two ways. The COMMIT of a transaction that stages the reference releases it, the reference pin and then the announcement's `owed` hold taking over as what keeps the bytes here. Otherwise it is released once it passes a **holding period** — the registration's `blob_unstaged_holding_ms`, 24 hours by default — after which the writer's piece sweep takes the bytes. That is what bounds the upload a user cancelled, the insert that never ran, and the process that stopped in between: without it a put nothing ever referenced would be kept for ever. **Built**, in `SqlBlobPins.sweepUnstaged`, which runs on its own interval (a quarter of the holding period, never oftener than a minute and never rarer than an hour) rather than off a transaction's exit, since no transaction is going to answer for such a pin. No pin is ever expired while a transaction that has not finished is relying on its reference: one carrying a reference pin whose transaction is still live — which includes every QUEUED transaction, whose pins stay until the queue finishes with it — and one the open transaction's statements have staged and whose commit has not yet pinned it, which only that transaction's reference ledger knows about. A `sql-unstaged/<ms>` label this build cannot read is left pinned for ever and logged once (`blob:unstaged-unreadable`): releasing a pin whose meaning is unknown would drop somebody's bytes. The period is measured on this machine's own clock, the same limit §[Lifetime](#lifetime) states for the reclaim pass, so a clock moved backwards delays an expiry rather than bringing it forward.
- **A reference tree per table.** For a table with a `blobref` column the plugin maintains the table's reference tree, `<table>/blobrefs`, beside its index trees and staged the way `IndexManager` (`packages/quereus-plugin-optimystic/src/schema/index-manager.ts`) stages index entries, and adds it to the scope registry when the table is created or gains its first such column. Dropping the table removes it from the registry. `BlobReferenceMaintainer` in `packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts` is the index manager's counterpart: one call beside each of the six index calls an `update()` makes, so a row and the references it holds commit or roll back together. The entry names the row and column through `blobReferrer` — the table's framed primary key, then the column name framed as one more element — and the column by its stored NAME, not its position, since a catalog-only DROP COLUMN of another column renumbers positions. Two refusals keep the tree describing real rows: a DROP COLUMN of a `blobref` column, and a re-declare that changes a column to or from `blobref` or omits a persisted `blobref` column. Both say to drop and re-create the table, which is the only way to shed the entries honestly.
- **Pins follow the transaction.** A reference a transaction leaves added is pinned under the transaction's identity, and the pin is released when the transaction commits (after announcing the blob with the table's reference tree as its scope), rolls back, or, for a queued offline transaction, settles once the queue has finished with it (`SqlBlobPins.settleQueued`). A pin no arm got to release is finished by a reconciliation (`SqlBlobPins.reconcile`), and the `unstaged` pin of a blob nothing ever referenced by the holding-period sweep (`SqlBlobPins.sweepUnstaged`, the bullet above). **Every pin lives in the blob records, and what judges one is COMMITTED STATE and the pin's own label, never the offline journal**: the label carries the transaction and the scope, so a process that did not seal an entry itself finds what it owes by listing its pins, and nothing about blobs has to be journaled or remembered across a restart. The owner labels a pin is held under are built and read in one place, `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts`: `sql/<stampId>/put` for a put made while a transaction was open, `sql/<stampId>/ref/<scope>` for a reference that transaction committed into `scope`, and `sql-unstaged/<ms>` for a put made outside any transaction. Putting the scope in the label is what makes the blob records themselves the durable record of which transaction owes which pin under which scope, so nothing has to be added to the offline journal. What to know about when each pin is written and released:
	- **A reference pin is written when the COMMIT STARTS**, not by the first statement that stages the reference. Nothing reached from the vtab's `update()` may call the blob service at all: a validating member re-executes the same statements through `QuereusEngine` and has no bytes, so it must neither pin nor announce (§[Registering references](#registering-references), *Under transaction validation*). So the statement only RECORDS what it staged, and the commit pins. What this changes is bounded to a transaction left open longer than the `unstaged` holding period, and the sweep closes that by never expiring an `unstaged` pin whose reference an open or queued transaction has staged — for an open one by asking the transaction's reference ledger, which is the only thing that knows a staged reference before its commit pins it.
	- **A transaction that rolls back, or that is queued, leaves an `unstaged` pin in place.** Both only release what the transaction itself took. The reason is the same for each: a reference pin can be released without the row ever landing — a queued entry that later fails settles with whatever it committed, possibly nothing — and an `unstaged` pin is the application's own hold on bytes it put outside any transaction, so dropping it would lose bytes an immediate retry would have kept.
	- **A blob put INSIDE a transaction that the transaction never references loses its bytes when the transaction ends.** `begin; put(a); put(b); insert … values (a); commit` releases `b`'s pin and the sweep takes its pieces. That follows from pinning a put under the transaction's identity, and it is a footgun: to keep a blob no row references, put it outside any transaction, or pass an explicit `owner` and release that pin yourself.
	- **A put that outlives its transaction, and a put with an explicit `owner`, are not the transaction's to release.** The first leaves a stray `sql/<stampId>/put` pin that the restart reconciliation removes; the second is the host's own hold.
	- **A queued transaction's reference pins are released when the queue finishes with it** (`SqlBlobPins.settleQueued`), announced into their scope for the collections that committed and dropped for the ones that did not — a transaction that failed, was withdrawn, or committed only its other half. A pin whose scope cannot be confirmed in the registry, or whose announcement fails, is kept and logged (`blob:pin-kept`) for the restart reconciliation to retry. What the settlement reconciles against is COMMITTED STATE and the pins' own labels, never the offline journal: the label carries the transaction and the scope, so a process that did not seal the entry itself — one that restored it from the journal after a restart — finds what the transaction owes by listing its pins. Before announcing, the scope is confirmed in the network's registry; for a scope no table in this process backs any longer the registry is only READ, since registering a tree whose table has been dropped would keep its blobs for ever. The settlement touches the transaction's OWN pins only: an `unstaged` pin is left in place even for a reference whose row landed, where an online commit would drop it, because the queued route has the holding period as its remedy rather than the commit.

	- **What no arm got to finish, a RECONCILIATION finishes** (`SqlBlobPins.reconcile`). A pin written when a commit started and never released — the process stopped in between (after the pins were written and before the commit was sent, after it landed and before the release ran, or while a queued entry sat in the queue with no journal to restore it), or an arm KEPT it deliberately (`blob:pin-kept`) because its scope could not be confirmed or its announcement failed — is judged from COMMITTED STATE: the reference tree the pin's own label names either lists the reference or it does not. Listed: the scope is confirmed in the registry as a settling queued transaction confirms it, the reference is announced, and the pin goes. Certainly not listed: the pin goes without an announcement, because the transaction never committed that reference, or a later transaction removed it — and a removed reference is not the writer's to keep. Not readable with confidence: every pin of that scope is KEPT and `blob:reconcile-uncertain` is logged, and the next trigger tries again; nothing is ever dropped on an answer the reader could not trust. It runs after the offline queue's restore (so after `plugin.hydrate`, which awaits it), on every reachability wake, and when a network's blob store first resolves in this process — and it costs nothing at all unless some arm has kept a pin it could not release, since listing the pins means reading every blob record on the machine. A transaction still LIVE here is skipped: the open SQL transaction, and anything the queue or the journal's restore still holds. With a journal, the reconciliation does not run at all until a restore pass has completed, because until then a journaled transaction still on disk is in no queue and its reference is not yet listed, so judging it would release the pins of an entry that goes on to commit.
	- **A blob store has one writer per machine.** Two processes over one store both reconcile, and each one's idea of which transactions are live covers only its own, so one could release a pin the other's open transaction is relying on. Not guarded against: the blob storage a host hands the plugin (`blobStorageFactory`) is one machine's, as the block storage behind a `local` transactor is.

	  Built, all of it: for every commit that reaches storage or the queue, for a queued transaction's settlement, for the reconciliation after a restart, and for the holding period on a put nothing referenced (`SqlBlobPins`, §[Committing a reference](#committing-a-reference)).
- **SQL functions.** `BlobLocality(ref)` and `BlobSize(ref)` (`packages/quereus-plugin-optimystic/src/functions/blob-functions.ts`), both answered from the local `stat` with no probe, so neither waits on the network. Locality is `here`, `partial`, `elsewhere` or `unknown`; the size is NULL while the root piece is not here. NULL in gives NULL, and anything that is not a reference is a type mismatch. Both read the default network, since a scalar function has no table context — a host with tables on several networks reads `stat` through `plugin.blobsFor(table)`. Neither is for a written value: a validating member re-executing the statement would compute a different one. Content does not pass through SQL.

Existing `blob` columns are untouched: values stay inline, base64 in the row, and keep reading. Two further steps build on the explicit type and are separate work:

- **Out-of-line storage of plain `blob` values.** A `blob` value over a threshold is stored as a blob and its reference kept in the row, invisibly to SQL. This removes the size limit and most of the cost for existing schemas, but a row read then depends on a fetch.
- **Streaming through the engine.** Reading or writing a range of a column value by table, key and column needs an interface Quereus does not have (gotchoices/quereus#40).

## Lifetime

Nothing reclaims block storage today, so a blob that is never reclaimed is no worse than a base64 value in a row. Reclaiming is still designed in, because blobs are where the bytes are.

- **Referenced blobs are kept.** A `responsible` hold lasts while any registered reference tree lists the blob.
- **Unreferenced blobs are reclaimed by each holder on its own reading of committed state.** Every 6 hours a holder passes its held references against every registered reference tree. A blob listed nowhere at two passes a grace period apart (7 days by default) loses its `responsible` hold. No message from another peer deletes anything.
- **An owed blob follows the same rule.** A writer whose cohort never fully holds a blob would otherwise keep it for ever. The pass also covers owed entries: one whose scope has not listed the blob at two passes a grace period apart is dropped with its hold.
- **Only a certain answer counts.** A pass counts toward reclaiming only when every tree read was authoritative and confirmed current (the `certain` that `readCommittedTree` in `packages/db-core/src/blob/committed-read.ts` reports through `BlobReferenceTree.listed` and `BlobScopeRegistry.enumerate`). A read that fails, is flagged unavailable or possibly stale, was answered with a block older than the log names it, or cannot reach the registry counts as "still referenced". So does a read that rested on asking nobody, unless the node is alone by the test the offline queue's reachability gate applies (no known member missing, no bootstrap peer still awaited). Two halves answer that, and both are **built**: `GetBlockResult.cohortConfirmed` in `packages/db-core/src/network/struct.ts`, which the answering coordinator sets only when a cohort member other than itself vouched for the answer (absent means "not known to be confirmed", so an answer from a machine that cannot see its cohort reads as unconfirmed, and so does one from a peer that predates the field), with `BlockGets.awaitConsult` for a read that needs the consult made in front of the answer rather than behind it; and `KeyNetworkCohortReachability.aloneFor` in `packages/db-p2p/src/network/cohort-reachability.ts`, which says whether this node is the whole cohort of some blocks — stricter than `reachable`, which is also true when the cohort names another member, exactly the case in which an unconfirmed answer must not count. The pair is what the rule needs: a node that merely cannot see its cohort gets unflagged "absent" answers for collections it does not hold, and must not act on them, while a genuine one-machine deployment gets the same unflagged answers and may. And a registry that reads as absent on a node holding blobs counts as "still referenced", since the registry existed when those holds were taken. A machine that is partitioned, starting cold, or being fed old state keeps what it has.
- **There is nothing to renew.** A design in which writers periodically extend a blob's lease was rejected: it costs a transaction per blob per period for ever, and it fails toward data loss whenever the renewing machine is a phone that stayed offline. Here the row is the lease, and it lasts as long as the row does.
- **Cached blobs are evicted under a budget.** **Built:** `BlobCacheBudget` in `packages/db-p2p/src/blob/cache-budget.ts`, built by the node over its blob records and sized by `NodeOptions.blobs`'s `cacheBudgetBytes` (256 MiB by default; `0` keeps no such blob beyond the ones being read). What counts against the budget is every blob whose record holds `cached` and nothing else — a blob carrying any other hold is neither counted nor evicted, since counting it would make the budget evict blobs it *can* remove to pay for one it cannot. Such a blob counts at the blob's **full** size whether or not every piece of it is here, which over-counts a blob this machine holds only part of: the same direction the shared-piece over-count below takes, and the safe one, since it evicts sooner and so uses less storage. A cache-only blob whose size this machine never learned — its record carries no `size` — is evicted at the next enforcement rather than counted as nothing, whatever the total: a blob whose cost a machine cannot name is a blob whose cost it cannot bound, and a cache made only of such blobs would otherwise never be found to be over the budget however much disk its pieces took. It is a rare state, because a fetch writes the size as soon as it knows it (`BlobFetchStore.markPartial`), under the `cached` hold: off the root list piece the moment a plan reads it, before any other piece is transferred and whether or not the fetch asked for the whole blob or ever finished — so a blob this machine holds part of is sized without walking its tree — and, for a blob of a single piece, off that piece's own length when the fetch ends. What is left is a fetch that never got the blob's root piece, which holds nothing worth keeping, and the window between that piece arriving and the write, which a crash can catch. A 0-byte blob is not unsized: its record says `size: 0`, and it is counted and evicted like any other. Over the budget, those blobs lose their `cached` hold least recently read first (ties by reference, so the choice is deterministic) until the total is within it, and the piece sweep then removes what no remaining hold needs. A blob's last-read time is its record's, falling back to the time its `cached` hold was taken: a read writes its time only to a record that already exists, so the read that fetched a blob for the first time leaves none, and dating such a blob to the epoch instead would evict what the node has just paid the network for ahead of blobs read long ago. A blob with a read or a fetch in flight is never evicted — it is skipped when the eviction is chosen and asked about again immediately before the hold is removed — and the sweep keeps every present piece of a blob in use whether or not it still has a record ([Holds](#holds)). It is enforced after a read or fetch that pulled something, and once when the node has built its blob service so that a budget lowered across a restart is applied to what the last run cached; there is no timer, because the cache grows only through reads that fetch. A budget the evictions cannot reach — every remaining blob is being read — leaves the cache over budget until the next enforcement. This is local and needs no agreement.
- **A reference that outlives its bytes** is possible only where no reference tree lists it any longer: an old revision of a row read from history. Such a read reports the blob as not held.
- **Accepted limits.** A reference copied from another row into a transaction that then stays queued offline for longer than the grace period, on a machine that never held the bytes, can commit after every holder has reclaimed the blob; it then reads as not held. Dropping a table leaves its reference tree in storage, so re-creating a table of the same name registers the old tree again and keeps the blobs its old rows listed. And the grace period is measured on each holder's own clock, so a clock set forward shortens it.
- **Re-referencing is safe.** A row that comes to reference a blob others have reclaimed, or are about to, is committed by a writer that either holds the bytes (it just `put` them, and announces) or copied the reference from another row. In the second case the blob was referenced when it was copied, the new entry is visible to the next pass, and the two-pass rule keeps the holder from having dropped it in between.

## Extending toward a file system

This design gives blobs, not a file system: no names, no directories, no editing in place. A file system is expected to be built on top, with rows as the directory entries (a table of name, parent and a `blobref`), which already gives atomic rename and move, liveness by row, and partial reads. The design keeps four properties so that going further stays an addition and never a rewrite. They are requirements on the implementation.

- **Below the format layer, a blob is only pieces and links.** Storage, transfer, holds, the sweep, copying and reclaiming never interpret a piece. They reach a blob's pieces through one walk in `db-core`, and one function there decodes a list piece (`walkBlobPieces` and `decodeListPiece`, [References and pieces](#references-and-pieces)). Admitting another kind of node, such as a UnixFS directory, changes that function and the walk; a directory's root would then be held, copied and reclaimed as a file's is.
- **The reader accepts more than the writer makes.** Any UnixFS file tree within the reader's bounds is readable, whatever its piece sizes and fan-out. So a second way of cutting pieces (boundaries chosen from the content, so that an insertion does not shift every later piece) needs a new writer and no change to readers, stores or the wire.
- **Building a tree is separate from cutting pieces.** The code that assembles list pieces from a sequence of leaf links is usable on its own. An append or an overwrite can then make a new blob from an existing blob's leaf links plus new pieces, without reading the unchanged content again. Because pieces are shared, the new blob costs only its new pieces and list pieces.
- **The reference grammar is not narrowed to this writer's output.** A reference is any version-1, SHA-256 CID of a raw or dag-pb piece. A directory root is a dag-pb piece, so it would need no new kind of reference.

What an extension would still have to decide: whether a directory is rows or a UnixFS node (rows give transactions and per-file placement; a node gives one reference for a whole tree and import from IPFS, but places the whole tree on one cohort unless child files are treated as blobs of their own); how an editor names the blob it is splicing from; and file-system semantics that have no counterpart here, such as permissions finer than membership and locks. Editing a range of a column value through SQL is the Quereus work described under [SQL](#sql).

## Threats

What a member that the network admits, or a stranger, can and cannot do.

| Attack | Outcome |
|---|---|
| Fill other machines' storage by announcing blobs | Refused. A holder pulls only what a registered reference tree lists, so the attacker must commit rows, which is the network's existing write authority and leaves attributable rows that can be deleted. |
| Aim storage at one victim by choosing content whose hash lands in its cohort | Possible in principle (as it is for block ids), and bounded the same way: each blob needs a committed reference. |
| Flood announcements to make holders read reference trees | Bounded per peer at 600 a minute (`BLOB_ANNOUNCES_PER_PEER_PER_MINUTE`), past which an announcement is answered without reading anything, and bounded for the node as a whole at four reference reads at once (`BLOB_REFERENCE_READS_IN_FLIGHT`), which no number of peers raises. An announcement naming a scope the registry does not list costs that one registry read and no reference-tree read. |
| Make a live blob expire | Requires committing the removal of its references, which is deleting the rows. Feeding a holder stale or empty reads does not work: only certain answers count, twice, a grace period apart. |
| Serve wrong bytes | Detected at the piece, before it is stored. The peer is penalized once (`PenaltyReason.InvalidRestoration` in `packages/db-p2p/src/reputation/types.ts`, the reason existing repair paths use for unverifiable content): the stream is authenticated and the fault attributable. The fetch does not ask that peer again and asks another holder. |
| Craft a malformed tree to exhaust a reader | Bounded by the limits a reader applies before following any link. |
| Exhaust a holder's bandwidth with `get` | Bounded per peer and per node; pieces are small and a holder may refuse a peer that is over its allowance. |
| Learn whether known content exists in the network | A member can. Not treated as a secret; encrypt before `put` if it must be. |
| Fetch content without being a member | Refused at the stream, before any request is read. |

## Platforms and limits

- A piece this design writes (256 KiB) is below every per-value limit the storage backends are known to have, including NativeScript's 512 KiB threshold for large JNI results; the NativeScript piece store reads one piece per call, and the "512 KiB" `NOTE:` in `packages/db-p2p-storage-ns/src/ns-opener.ts` says when a run of larger pieces would matter. A reader accepts pieces of up to 1 MiB from blobs made by other IPFS tools, so every piece store must also store and return a piece of that size.
- React Native's LevelDB store reads values as text for the block store; its piece store reads bytes, under its own tag (`TAG_PIECES` in `packages/db-p2p-storage-rn/src/keys.ts`), and is measured from the length key beside each piece, so counting storage use reads no piece. It has not run on a device: its suite runs over `classic-level`.
- Browsers store pieces in IndexedDB; adding the `pieces` object store raised the database's version to 5 (`DEFAULT_DB_VERSION` in `packages/db-p2p-storage-web/src/db.ts`). A database at versions 1 to 4 gains the store, empty, with every record kept; a build asking for an older version cannot open a version 5 database.
- Blob records, owed entries and pieces survive a restart only when the host supplies a persistent key-value store and piece store. With the in-memory defaults, pins and unsent copies are lost when the process ends.
- The dag-pb and UnixFS codecs (`@ipld/dag-pb`, `ipfs-unixfs`) are dependencies of `db-core`, and pass the React Native bundle check (`yarn check:rn`) with no alias or shim.

## Compatibility

The change is additive. A node on an older build does not register the blob protocol; peers see that from its protocol list and treat it as a member that does not accept blobs. Stored data gains a piece store and new key-value namespaces, and loses nothing, so an older build's data opens unchanged. The upgrade suite (`packages/upgrade-check`) runs every release's fixture, on files and on LevelDB, with a piece store over the older data's location, stores a blob there and reads it back after a restart, checking that the older blocks list as they did; from the first release that ships blob storage, it also reads back a blob that release stored. A table that declares a `blobref` column cannot be opened by a plugin that predates the type; adopting the type is a schema change an application rolls out like any other. An application with references of its own (Sereus Chat's `chunks:1:` references) tells them from these by their prefix and keeps reading the old ones.

It is loopback with memory stores, so it measures the protocol and the hashing, not a link or a disk. - **Time.** A transfer took 5.5 to 10.5 ms per MiB on the reader, and the writer's put 1 to 1.6 ms per MiB (3.1 and 3.6 at 3 MiB in two runs). A value in a row costs 0.2 to 0.3 s per MiB to commit on an in-process two-node mesh over memory storage (§[Why](#why)), 19 to 55 times the transfer alone, and GitHub #63 reported 1.7 s per MB on file storage. The two are not the same work: the row figure includes the commit's consensus and both machines storing the value; the blob figure leaves out the small transaction that commits the row holding the reference, copying to the blob's cohort and a disk. The first read of each run took about twice as long as the rest (16 to 18 ms for 1 MiB, against about 9); the median absorbs it. A run during review, on the same machine, read 3 MiB at 9.7 ms per MiB, so the ranges are this machine's spread over one afternoon, not bounds.
- **Space.** A blob crossed the wire at 1.0005 to 1.0006 times its size, against 2.75 to 4 times for a value in a row in legacy mode and 5.3 to 6 times in session mode ([internals.md §A transaction's size limit](internals.md#a-transactions-size-limit), *What a large value costs*).
- **The overhead is more than a few kilobytes.** For a 16 MiB blob it is about 125 bytes per 256 KiB piece, so about 22 KB per 45 MiB, where this section expected a few kilobytes of list pieces. About 50 bytes of it is the piece's link in its list piece (its CID and size in dag-pb; the root of a 1 MiB blob is 208 bytes for four links). About 70 is asking for the piece and framing it: a `get` header names each piece by its 59-character id in JSON, the answer header carries a `true` for it, and its frame has a 3-byte length prefix. Each `get` adds 52 bytes of fixed header and length prefix, about 4 more per piece at 16 MiB, and at these sizes a read sends one for the root and then one per 16 data pieces, which is why a 1 MiB blob, fetched in two `get`s of one and four pieces, pays the most per MiB. The measured counts equal, to the byte, the frames that sequence of `get`s encodes to. The overhead is 0.05% of the content.
