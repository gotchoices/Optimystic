# Three facts, each stated three different ways

A design review on 2026-09-14 (prompted by `blocked/writer-and-servers-disagree-on-where-a-block-lives`) read the consistency docs side by side and found that the following are stated inconsistently. Each needs one authoritative statement, matching the code, and cross-references from the other places.

## 1. The bar for acknowledging a write

Three different bars appear:

- correctness.md Theorem 6: replicated on at least 75% of cluster peers before success is reported.
- cluster.md: promise phase needs a super-majority (0.75), commit phase needs a simple majority and the coordinator may return success as soon as majority commits arrive.
- correctness.md line 64: acknowledged only when a strict majority of the cohort reports its storage durably holds the revision.
- repo.md: phase 1 is floor(n/2)+1, labelled majority consensus.

The code (cluster-coordinator.ts and coordinator-repo.ts, see files above) does: promise needs ceil(0.75 × n) approvals; commit-phase consensus is > n/2 commit signatures and a shortfall does not throw; the acknowledgement to the writer is gated on durable holders > n/2 including self; n = 1 skips all of it. State exactly that, once, and derive the small-size consequences from it in a table: n=1 no quorum, n=2 both, n=3 all three, n=4 tolerates one absent.

## 2. The smallest supported group

correctness.md says K=3 is the minimum. cluster.md, architecture.md and optimystic.md say one and two are first-class. The code resolves minAbsoluteClusterSize to 2 in a real node while the interface default says 3. Settle on the "one and two are ordinary" position (already decided by ticket `small-cohort-arming-rule`) and remove or reword the K=3 claim.

## 3. What "network scale" means

The maintainer's intent (stated 2026-09-14): Optimystic is not built around one particular well-known network the way a public blockchain is; it is a substrate on which customers create networks, which may be tiny and private (a family's phones) or very large and public (a registry, a voting network). Both docs should say so plainly. Today architecture.md talks about millions of nodes and Arachnode rings, sereus's strands doc says "no assumption of a single world-wide DHT", and a reader can conclude either that huge networks are out of scope or that only huge networks are in scope. Neither is intended.

## 4. Smaller contradictions found in the same pass

- correctness.md line 540 item 10 ("block content integrity is unconditionally verifiable") contradicts Theorem 15 (it is not; block ids are not content hashes). Delete item 10 or point it at Theorem 15.
- repo.md line 287 and 313 claim cross-collection atomicity and rollback; correctness.md Theorem 3 says there is no cross-collection undo. repo.md should defer to Theorem 3.
- "cohort" means the block-replica set in cluster.md and a k≈16 topic cohort in cohort-topic.md; add a one-line disambiguation where each is introduced.
- `responsibilityK` appears in no doc; it is the redirect-skip threshold in `libp2p-node-base.ts` (default 1). Either document it in repo.md next to the redirect check or note that it is effectively unused.

## Done when

Each of the four facts above has one home and the other files link to it; the size table in internals.md agrees with the code sites named in `files:`; a grep for "75%" and "K=3" across docs finds only the authoritative statements.
