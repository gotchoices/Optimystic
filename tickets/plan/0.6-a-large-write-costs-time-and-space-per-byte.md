# A large write costs time and space per byte

Reported as GitHub #63 (Sereus Chat attachments; optimystic 1.26.0, two parties on loopback WebSockets, file storage).

## What happens

Each transaction inserts N rows of `BlobChunk (Hash text primary key, Bytes blob not null)` with 256 KiB of random bytes per row. Median commit time: one tiny row 48–126 ms; 1 value (0.26 MB) ~420 ms; 4 values (1.05 MB) 1.3–1.5 s; 8 values (2.1 MB) 3.7–3.9 s — about 0.6 MB/s, roughly 1.7 s per MB on loopback. One 4-value commit in three took 11–13 s instead of ~1.3 s, in two separate runs.

A CPU profile of one 8-value commit (4.9 s sampled, 83% busy), by self time: native hash `update` 11.7%, TextEncoder/TextDecoder 9.5%, db-p2p `encodeJson` 8.1%, db-core `canonicalJson` 7.8%, db-p2p `decodeJson` 7.2%, GC 6.8%, Quereus `uint8ArrayToHex` 5.0%, `encodeUtf8String` 4.4%, `structuredClone` 3.0%, `cloneDecoded` 2.1%, `jsonEncodedBytes` 2.9%.

Size: 16 values (4.2 MB raw) encode to 11.5–14.3 MB and are refused by `TransactionTooLargeError`. Base64 in JSON accounts for 1.33×; the rest suggests each value is carried two to two and a half times.

## What is already known

- docs/internals.md §A transaction's size limit states that a log entry repeats the data of the actions it records beside the blocks those actions change, so row data is counted roughly twice; that is the likely second copy. GitHub #61 measured ~2.2× for small text rows.
- The writer canonicalizes and hashes every touched block to declare its content digest (`describeTouchedBlocks`), and storage and the wire encode and decode JSON, so a large value passes through several whole-value serializations per commit. Which passes are avoidable, or could hash bytes rather than canonical JSON of base64, is not measured here.
- Related backlog: `debt-block-reads-copy-at-every-tracker-layer` (the clones), `7.5-block-compression` (under `backlog/enhancements`), `0.7-feat-a-transaction-larger-than-one-frame-can-commit` (the limit itself), and Quereus's native large-value request (gotchoices/quereus#40), which would move content out of transactions.

## Requirement

- Profile a large-value commit on the in-process mesh and attribute the time to passes; remove or cheapen the ones that are redundant (a value serialized, canonicalized or hashed more than once per commit on one machine).
- The resulting cost per MB and expansion factor are measured and stated in the docs.

Whether a value should be carried once per transaction (the log entry stops repeating content its blocks carry) is a log-format decision, parked as `blocked/a-log-entry-carries-a-value-once`; this ticket does not change the persisted log format.

The issue's follow-up (on a slow cellular link a ~3 MB transaction never commits, because each attempt has a fixed time budget and every retry resends everything) is an arm of backlog `feat-link-deadlines-stretch-to-measured-response-time`, not this ticket.
