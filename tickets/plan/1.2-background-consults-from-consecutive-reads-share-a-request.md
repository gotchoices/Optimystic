# Background consults started by consecutive reads share one request per peer

Source: GitHub sereus#60 (Node repro attached to the issue; cadre-core 1.22.0, Optimystic 1.27.0, Quereus 5.4.0).

## What was measured

Two parties share a workspace whose app declares N tables; both hold every collection. One party restarts its database while the other stays up, and counts the sync requests (`/db-p2p/sync`, the protocol the cohort consult travels on) the other serves:

| tables | requests served by the partner |
|---|---|
| 4 | 45 |
| 16 | 81 |
| 32 | 129 |
| 64 | 227 |

About 33 plus 3 per table, nearly all before the restarted database is writable, and none after. In the field (a 40-table app, two phones over a public relay) each restart of one party makes the other serve about 105 requests within 5 s; on a Galaxy S7 that is a burst of about 7 s at about 90% CPU, roughly 65 ms per request in Noise, yamux and request handling. A phone holding N workspaces pays this N times per start, and each partner pays its share. A cold start over a relay paid less (17 to 32), apparently because the partner was not yet connected when the reads ran.

## Why it happens here

The restarting app (Sereus's first-sync gate) reads each table once, serially, with a live read, which refreshes the table's trees through `Collection.update`. On a node in the block's cohort, a read of a held block is answered from the local copy, and the lazy read-repair window starts one background consult per held block per window behind it ([docs/transactions.md §Lazy read-repair window](../../docs/transactions.md#lazy-read-repair-window)). After a restart no block has a window stamp, so every block's first read starts a consult. The consults started by one read share a `ConsultRound` and so one request per peer, but a round is never shared across reads — the doc comment on `CoordinatorRepo.openConsultRound` says so deliberately, since coalescing concurrent reads would need a timer and the round's barrier keeps a one-block read at no added latency. Serial reads therefore cost one request each.

The reporter's suggestion (b), "ask for the latest revision of every block a launch needs in one request per peer, not one request per block", is the Optimystic half. Their suggestion (a), skipping the probe on a restart, is Sereus's own and is being handled there; it removes this workload's trigger but not the cost for any other embedder whose start-up reads tables one after another.

## Requirement

A background held-block consult — one that the read does not wait on — may be delayed briefly so that the consults started by reads arriving close together go to each peer in one request (up to the existing per-request block limit, `MAX_CONSULT_BATCH_BLOCKS`). In the restart shape above, the partner should serve a number of requests that does not grow with the table count, or grows far more slowly than one per table.

What must not change:

- **No read waits longer.** Only background consults are coalesced. A consult a read depends on — a block missing locally (the absence verdict), a held block under a floor above its copy, `'paranoid'` read-repair — keeps today's per-read round and barrier.
- **What a consult establishes is unchanged**: the window stamp, the unsettled-claim memo behind `unconfirmedAheadRev`, the `cohort-too-small` arming, repairs and the change events they emit. A coalesced consult judges each block against the copy its triggering read loaded, as today.
- **The bounds stay bounded**: at most one pass per block, and the slot count in `HeldBlockConsults` still bounds requests per peer.
- **Mixed versions**: a peer on an older build answers a batch's first block only, and the round already falls back to single requests for it (the `NOTE:` at `MAX_HELD_BLOCK_CONSULT_SLOTS`); coalescing must not make that fallback burst larger than it can be today.

The plan should state the delay and its trade: a longer delay coalesces more but leaves a stale copy unrepaired that much longer after its first read, which matters only for the reads after it, since the read itself was already served locally. It should also state whether the delay applies always or only while many background consults start in a short time.

## Not in scope

- Remembering window stamps across a restart. A restarted node cannot know what it missed while down, so its first consult per block is the price of correctness; this ticket is about how many requests carry it.
- Skipping the consult for reads that do not need it; `BlockGets.skipWindowConsult` already exists for that, and whether the Quereus plugin should expose it to a host is a separate question.
