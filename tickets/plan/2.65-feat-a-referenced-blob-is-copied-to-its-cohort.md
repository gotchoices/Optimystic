# A referenced blob is copied to its cohort

docs/blobs.md §Placement, copying and durability, "When the cohort changes": "A node's held blobs are enumerable from its records, so the cohort comparison `RebalanceMonitor` makes for blocks is made for blobs too, by giving it the routing key rule rather than a second copy of its logic. A member that joins a held blob's cohort is announced to. A node that leaves a blob's cohort drops its `responsible` hold only after confirming that enough current members hold the blob."

The earlier parts built the pieces: the monitor takes a routing rule and can re-report a lost id (`feat-blob-rebalance-monitor-takes-a-routing-rule`); receivers answer announcements and take `responsible` holds with their scope (`feat-blob-announcements-are-answered`); the writer's owed entry is drained until `full` (`feat-blob-owed-copies-are-drained`). This last part runs a second `RebalanceMonitor` over the blobs this node holds for the network and reacts to its events. When it lands, all of `docs/blobs.md` §Placement, copying and durability exists.

## What is tracked

The tracked set is the references whose record carries an `owed` or a `responsible` hold — the two holds that mean "kept for the network". Pins and `cached` holds are this node's own business and are not tracked: a node does not announce a blob it merely read.

- **Feed.** `BlobRecordStore` gains `onHoldsChanged(listener: (ref: BlobRef, holds: BlobHolds) => void): () => void`, called after every hold write is flushed (an error-isolated listener, like `StorageRepo`'s). The node wires it to `monitor.trackBlock(ref)` when the record has `owed` or `responsible`, else `monitor.untrackBlock(ref)` (`BlobHolds` is the record's hold shape from `feat-a-node-stores-blob-pieces`, with `responsible?: { scope }` from the announcement ticket).
- **Restart seed.** `seedHeldBlobs` in `packages/db-p2p/src/blob/held-blob-seed.ts`, modelled on `seedOwnedBlocksFromStorage`: subscribe the feed first, then enumerate the records (the record store's enumeration from `feat-a-node-stores-blob-pieces`) and track every one with `owed` or `responsible`; fire-and-forget off the start path, cancellable by the stop wrapper. Then, for each owed entry, `monitor.recordBlockHolders({ blockIds: [ref], holders: entry.holders })`, so the first check after a restart does not re-announce to members the writer already knows hold the blob. A `responsible` holder has no such memory and announces once to its whole cohort after a restart; receivers answer `whole` cheaply, bounded by `growthBlockBudget` per check.
- **Holder evidence.** `BlobCopyDrainDeps.onHolderConfirmed` (from the previous ticket) is wired to `monitor.recordBlockHolders({ blockIds: [ref], holders: [peerId] })`, so a `whole` answer or a `held` from the drain path also counts for growth.

## The monitor instance

In `createLibp2pNodeBase`, inside the rebalance block (it needs FRET and the `fretAdapter`, as the block monitor does), after the block monitor is built and only when the node has its blob service:

```ts
const blobMonitor = new RebalanceMonitor({
	libp2p: node, fret, partitionDetector, fretAdapter,
	trackedBlocks: heldBlobRefs,               // its own Set, never the block set
	keyNetwork, clusterSize: consensusConfig.clusterSize,
	// Every id in heldBlobRefs came from a blob record, so it is a parsed reference.
	routingKeyOf: id => routingKeyForBlob(id as BlobRef),
	logName: 'blob:copy'
}, options.rebalance);
```

It shares `options.rebalance` (tuning and `enabled`) with the block monitor: one switch for "react to cohort changes". It is constructed directly, not through `NetworkManagerService.initRebalanceMonitor`, which holds the block instance. A wiring failure is logged and non-fatal, as for the block monitor. Stop wrapper as for the block monitor. Expose `(node as any).blobRebalanceMonitor` for tests. Without FRET (arachnode disabled) the blob reaction is inert, as the block one is; the owed drain still follows the cohort on its own passes, so a writer's copies are unaffected.

## The reaction

`BlobCohortReaction` in `packages/db-p2p/src/blob/cohort-reaction.ts`:

```ts
export interface BlobCohortReactionDeps {
	selfId: string;
	membership?: NetworkMembershipGate;
	partitionDetector: Pick<PartitionDetector, 'detectPartition'>;
	records: BlobRecordStore;
	owed: Pick<OwedBlobLedger, 'get'>;
	acceptance: (peerId: string) => Promise<BlobAcceptance>;
	declining: Pick<BlobCopyDrain, 'isDeclining' | 'noteDeclined'>;
	announce: BoundBlobAnnouncer;
	/** `BlobProtocolClient.stat` bound to this node: one request per peer, per-ref `whole` | `partial` | `none`. */
	stat: (peerId: string, refs: readonly BlobRef[]) => Promise<ReadonlyMap<BlobRef, 'whole' | 'partial' | 'none'>>;
	log: Logger;
}

export interface BlobReactionResult {
	/** Lost refs whose release was confirmed; the caller drops the `responsible` hold. */
	released: BlobRef[];
	/** Lost refs not yet confirmed; the caller calls `retainLost`. */
	retained: BlobRef[];
	/** Per grown ref; no entry for a ref the reaction learned nothing about. */
	growth: Map<string, GrowthOutcome>;
}

export class BlobCohortReaction {
	constructor(deps: BlobCohortReactionDeps);
	handle(event: RebalanceEvent): Promise<BlobReactionResult>;
}
```

At most 4 refs are handled concurrently per arm (a small fixed constant in the module). During a detected partition `handle` changes nothing: every grown ref gets `{ satisfiedPeers: [], complete: false }` and every lost ref is retained, as `BlockTransferCoordinator` does.

**`gained`** — nothing, as for blocks: a tracked ref is already held here.

**`grown`** — for each ref and its newly co-responsible peers:

- The scope is the record's `responsible.scope`, else the owed entry's `scope`. With neither (the holds changed meanwhile), the ref gets `{ satisfiedPeers: all, complete: true }` and `grow:no-scope` is logged: there is nothing to announce under.
- A peer the membership gate refuses, whose acceptance is `refuses`, or that is remembered as declining is satisfied without a request: it is owed nothing.
- Each other peer is announced to. `whole`, `fetching` and `declined` (which also calls `noteDeclined`) satisfy it; `not-responsible`, `unreferenced` or a failed call do not.
- `complete` is true when every reported peer is satisfied. An incomplete outcome counts an attempt in the monitor (`recordGrowthOutcome`), so a failing announcement is re-detected on the next check and abandoned after `growthMaxAttempts` until the peer leaves the cohort and rejoins — the confirmation-driven path blocks use. `fetching` counts as satisfied because the receiver has already taken a durable `responsible` hold and resumes its pull after a restart; its `held`, when it comes, is evidence through `onHolderConfirmed`.

**`lost`** — for each ref whose record still has a `responsible` hold (a lost ref held only as `owed` needs nothing here: the owed drain follows the cohort, and the ref stays tracked):

- Candidates are `event.newOwners.get(ref)` filtered to peers the membership gate admits, whose acceptance is not `refuses`, and that are not declining.
- The required count is `min(event.floor, candidates.length)`. `event.floor` is the floor `RebalanceMonitor` already uses for releasing a block (`getCohortSize`); it is capped by the accepting candidates because an on-demand or older member can never hold the blob, and requiring it would keep the hold for ever even when every member that can hold it does. A required count of 0 — no new owner accepts blobs — retains the ref (`release:no-accepting-owner`): nobody else would keep it.
- `stat` the candidates (one request per peer covering every lost ref it is a candidate for). Count `whole` answers per ref. For each candidate not `whole`, announce under the hold's scope, so a member that has not heard of the blob starts pulling now rather than at its writer's next pass.
- Released when the `whole` count reaches the required count; retained otherwise. A `stat` or announce that fails counts as not `whole`.

The node's handler, mirroring the block one (`onRebalance` → reaction → feedback, the reaction hopped off the emit loop and a rejection logged, never unhandled):

```ts
blobMonitor.onRebalance((event) => {
	reaction.handle(event).then(async (result) => {
		for (const ref of result.released) await records.releaseHold(ref, 'responsible');  // the feed untracks when no owed hold remains
		for (const ref of result.retained) blobMonitor.retainLost(ref);
		for (const [ref, outcome] of result.growth) blobMonitor.recordGrowthOutcome(ref, outcome);
	}).catch((err) => { log('blob rebalance reaction failed: %o', err); });
});
```

(`releaseHold` stands for the record store's hold-removal method from `feat-a-node-stores-blob-pieces`, under whatever name it landed.) Releasing the `responsible` hold leaves the bytes to the sweep only if no other hold remains, so a node that also pinned or cached the blob keeps it.

## Edge cases & interactions

- **Leaving a cohort with too few holders.** The `responsible` hold stays, the ref is re-reported `lost` on later checks (`retainLost`, with the re-check timer armed), and the hold is dropped once enough current members answer `whole` (test).
- **A member joins a held blob's cohort.** Reported `grown`, announced to; a failed announcement leaves it unsatisfied and the next check re-reports it (test of the answer-to-outcome mapping; the monitor's re-report is pinned by its own suite).
- **On-demand or older members.** Satisfied without a request in `grown`; excluded from the release count in `lost` (test covers declined; inspection for `refuses`, which shares the filter).
- **Regaining responsibility while retained.** The monitor clears `releasePending` and reports growth as a first observation; the hold was never dropped. Inspection.
- **Partition.** No release and no announcement during a detected partition: the monitor suppresses its checks and the reaction re-checks before acting. Inspection.
- **Non-members.** Never announced to or counted (membership filter in both arms). Inspection.
- **Block replication unchanged.** The block monitor, its reaction and its owned-block set are untouched; the blob monitor has its own set and logger. The existing rebalance suites pass. Inspection plus the suites.
- **Writer and responsible holder at once.** A ref with both holds: `lost` releases only `responsible`; the ref stays tracked through `owed` until the owed drain reaches `full`. Inspection.
- **Holds edited during a check.** The reaction re-reads the record before acting on each ref; a ref whose hold vanished is skipped (no outcome entry, so the monitor's state is untouched). Inspection.

## Tests

`packages/db-p2p/test/blob-cohort-reaction.spec.ts`, over a real `BlobRecordStore` on `MemoryKVStore` and bound `stat` / `announce` doubles (the way the drain specs bind their transport):

- `lost`, floor 2, two accepting new owners: first `handle` with one `whole` → retained, the non-`whole` owner was announced to, the hold is still there; second `handle` with both `whole` → released; after the handler's release the record has no `responsible` hold.
- `grown` with four new peers answering `whole`, `fetching`, `declined` and `unreferenced` → `satisfiedPeers` the first three, `complete: false`, and the declining peer recorded through `noteDeclined`.

No end-to-end mesh test of the monitor: its check-and-report behaviour is pinned by the rebalance suites with the routing rule a pass-through, and the copying it triggers is pinned end to end by the drain ticket's two-node tests.

## Note from planning `feat-blob-announcements-are-answered`

The record's holds are an array (`BlobHold` in `packages/db-p2p/src/blob/blob-record.ts`), not an object with a `responsible?` field: the `responsible` variant is `{ kind: 'responsible', at, scope }`, read with `LocalBlobService.responsibleScope(ref)` and listed with `LocalBlobService.responsibleRefs()`. Every hold change must go through `LocalBlobService` (its private `changeRecord`, which the piece sweep relies on), not `BlobRecordStore` directly — so the hold-removal method and the `onHoldsChanged` feed belong on that path too. A pull for an announcement leaves the fetch's `cached` hold beside `responsible`.
