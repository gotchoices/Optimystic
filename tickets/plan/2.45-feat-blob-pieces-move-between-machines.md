# Blob pieces move between machines

docs/blobs.md designs native large-value ("blob") support. After `feat-a-node-stores-blob-pieces` `node.blobs` answers from this machine only, after `feat-blob-protocol-frames-stat-and-get` nodes can ask each other for pieces, and after `feat-blob-fetcher-verifies-and-resumes` a `BlobFetcher` brings missing pieces here, verified and resumable. This ticket makes `node.blobs` use the network as docs/blobs.md §The node's blob service defines: `read` fetches what is not here as the read reaches it and honours `waitMs`, `fetch` brings the whole blob here, `stat` with `probe` asks the blob's cohort, and `onProgress` reports pieces and bytes fetched. It also takes the measurement the last paragraph of docs/blobs.md requires and writes the result into the doc. With this ticket the backlog item `feat-blob-pieces-move-between-machines` is complete; `feat-a-referenced-blob-is-copied-to-its-cohort` depends on this slug.

## `NodeBlobService`

`packages/db-p2p/src/blob/node-blob-service.ts`. If `feat-a-node-stores-blob-pieces` already created `NodeBlobService` there as what `node.blobs` is, add the network paths below to it. Otherwise create it: a class implementing db-core's `BlobService` over a `LocalBlobService`, delegating `put`, `pin`, `unpin`, `announce` and `onDurability` to it unchanged, and change `OptimysticNodeAttachments.blobs` (`packages/db-p2p/src/optimystic-node.ts`) to `NodeBlobService`.

```ts
export interface NodeBlobServiceDeps {
	local: LocalBlobService;
	fetcher: BlobFetcher;
	client: BlobProtocolClient;
	/** The same candidate rule the fetcher uses (blobHolderCandidates' inputs). */
	holders: (ref: BlobRef) => Promise<string[]>;
	/** LinkDeadlines.responseTimeoutMs, the per-peer budget of a stat probe. */
	probeTimeoutMs: number;
}
export class NodeBlobService implements BlobService {
	constructor(deps: NodeBlobServiceDeps);
	/** Diagnostic: cumulative blob-protocol frame bytes this node sent and received (BlobProtocolClient.wireBytes). */
	wireBytes(): { sent: number; received: number };
}
```

`holders` is a closure built in `libp2p-node-base.ts` over `blobHolderCandidates` with the node's key network, membership gate, reputation and blob protocol id, so `stat` probing and fetching choose peers by one rule; if the fetcher ticket built `blobHolderCandidates` with a signature that takes those directly, pass it through rather than adding a second function.

### `read(ref, options)`

- `from: 'here'`: exactly `local.read(ref, options)` (it fails with `BlobUnavailableError` reason `not-here` at the first missing piece).
- Otherwise: start a fetcher session `fetcher.start(ref, { priority: 'foreground', offset, length, waitMs, signal })` and run db-core's `readBlob(ref, source, { offset, length, digest })` over a `PieceSource` whose `get(id)` returns `pieces.get(id)` when present, and otherwise awaits `session.stored(id)` and then returns `pieces.get(id)`. So the read yields bytes as soon as the pieces it reaches are stored, while the session fetches ahead in batches. A rejection of the session surfaces from the read at the piece that needed it: `BlobUnavailableError` with the session's reason, or `BlobCorruptError`. If the read finishes (or its consumer stops early) while the session is still running, abort the session through an `AbortController` chained to the caller's signal, so no fetching outlives the read beyond the batch in flight.
- Update the record's last-read time as `local.read` does, through the same `BlobRecordStore` call.
- If the blob is entirely here, no session is started, so a local read costs no cohort lookup. Check with the planner's "nothing missing" answer, which the fetcher's session already does at its step 1; starting a session that resolves at once is acceptable, but the session must not call `findCluster` in that case (the fetcher ticket's step 1 guarantees it).

The read hashes each fetched piece twice: once in the fetcher before storing it, once in `readBlob` when yielding it. Accepted: `readBlob` must check what it reads from disk (disk damage), and skipping the second hash for freshly fetched pieces would need the reader to trust a side channel. Record as a `NOTE:` at the `PieceSource` with the revisit condition "hashing shows in a profile of a read on a phone".

### `fetch(ref, options)`

`fetcher.start(ref, { priority: 'foreground', waitMs: options?.waitMs, signal: options?.signal }).done` — the whole blob, foreground, because an application awaiting `fetch` is waiting on it. Pass through whatever other fields `BlobFetchOptions` (db-core) carries that map onto `BlobFetchRequest`. Background priority is used only by `feat-a-referenced-blob-is-copied-to-its-cohort`.

### `stat(ref, { probe })`

- Without `probe`: `local.stat(ref)`.
- With `probe`: take `local.stat(ref)`; if its locality is `here`, return it. Otherwise ask every candidate from `holders(ref)` in parallel with `client.stat(peer, [ref], { signal })`, each under its own `AbortController` aborted after `probeTimeoutMs` (the client's own dial and progress deadlines also apply). If any peer answers `whole` or `partial`: a local `unknown` becomes `elsewhere`; a local `partial` stays `partial`. If none does, the local answer stands (`unknown` or `partial`). Failures of single peers are logged and ignored. `size`, `heldBytes` and `durability` always come from the local stat: a remote answer carries no size.
- The probe result is not remembered; each `probe` asks again.

### `onProgress(listener)`

Subscribe to `fetcher.onPieceStored`, and for each event emit a `BlobProgressEvent` for its reference with cumulative counts for this node: pieces and bytes fetched so far for the reference, and the blob's size once the root piece is here (from `local.stat`'s record or the fetcher's plan). Use the fields `feat-blob-references-and-verified-piece-trees` gave `BlobProgressEvent`. If that type lacks any of `ref`, `piecesFetched`, `bytesFetched` and `size?`, add them there. Counts are kept per reference in a `Map` and dropped when a session for that reference settles and no other is running, so they do not grow without bound. A listener that throws is logged and does not stop delivery to others.

## Wiring

In `createLibp2pNodeBase`, build `NodeBlobService` once the fetcher and client exist (post-start, beside the other key-network consumers) and set it as `attachments.blobs`. If `node.blobs` was previously assigned the local service before start, the attachment object assigned after start replaces it, which is the only assignment hosts observe (they read `node.blobs` after `createLibp2pNode` resolves).

## Measurement

- For sizes 1 MiB, 3 MiB and 16 MiB of random bytes (1 MiB and multi-MiB are the GitHub #63 shapes; 3 MiB is the transaction that never committed over a relay): `A.blobs.put`, then on B time `for await (const _ of B.blobs.read(ref))` from first call to last chunk, with B's piece store empty. Repeat N times (default 5, `N` env var) with fresh content each time, report the median.
- Report per size: ms per MiB, and bytes on the wire per MiB of content from `B.blobs.wireBytes()` (sent plus received, delta across the read). State in the output that this counts blob-protocol frames (length prefixes, headers, pieces) and not noise or yamux framing, which the transport adds beneath every protocol alike.
- Run it, and write into docs/blobs.md the numbers, the machine description in one phrase (CPU, OS, Node version), the date and the command, replacing the "expected cost" sentence of the last paragraph of §What this answers in GitHub #63. Compare against the doc's 1.7 s per MB and 2.75 to 3.4 times the size for the base64-in-a-row path. If a number is worse than the doc's expectation (wire size more than a few kilobytes per 45 MiB above the content), say so in the doc rather than rounding it away.

## Edge cases & interactions

- **`from: 'here'` never touches the network.** Delegates to the local service. Inspection.
- **Blob entirely here.** No `findCluster`, no stream. Inspection of the fetcher's step 1.
- **Read consumer stops early.** The session is aborted; the batch in flight finishes and its pieces are kept. Inspection.
- **Two reads of one blob at once.** One request per piece through the fetcher's in-flight map; both reads yield all bytes. Inspection (the assertion lives in the fetcher).
- **`waitMs`.** A read started before any holder has the bytes completes once a holder appears within `waitMs` of the last progress; without `waitMs` it fails at once with `not-held` (or `cohort-unreachable` with nobody to ask). Test.
- **Stat probe with every candidate silent.** The local answer stands; never `elsewhere` on silence. Inspection.
- **Stat probe on a node whose cohort is only itself.** No candidates; the local answer stands. Inspection.
- **Progress listener throws.** Logged, other listeners still called. Inspection.
- **Progress counts.** Dropped when the last session for a reference settles. Inspection.
- **Caller's signal.** Aborting `read` or `fetch` rejects with the signal's reason. Inspection.
- **Stock relay.** A fetch over a relay with stock limits fails after 128 KiB with `peers-unreachable` or `cohort-unreachable`, keeps what it stored, and resumes on a direct path (docs/blobs.md §Relays). Inspection; no relay test, since the relay behaviour is the relay's and the resume is pinned in the fetcher ticket.

## Tests

`packages/db-p2p/test/blob-network-read.spec.ts`, two real nodes over loopback TCP (`clusterSize: 2`, B bootstrapped to A, waiting until each is in the other's `findCluster` for a blob key), memory piece stores:

- *Read across machines, with progress*: A puts a 3-piece blob (600 KiB of deterministic bytes); B's `stat(ref)` is `unknown`, `stat(ref, { probe: true })` is `elsewhere`; B reads it and the bytes equal the input; B's `onProgress` reported 4 pieces (three data pieces and the list piece) with a final `bytesFetched` equal to their total size; afterwards B's local `stat` is `here`. One test, since these are the steps of one use.
- *`waitMs`*: B reads a reference nobody holds yet with no `waitMs` and gets `BlobUnavailableError` reason `not-held`; then B starts a read of the same reference with `waitMs: 10_000`, and 300 ms later A puts the content (the same deterministic bytes, so the same reference); the read completes with the right bytes. This pins that `waitMs` keeps a read alive while no holder has the bytes and that a holder appearing later is found by a new round.

No test for `fetch` (a session's `done`, already pinned by the fetcher tests) or for `from: 'here'` (the local service's).
