# The filesystem piece store

`feat-blob-piece-store-interface-and-memory-store` defines `IPieceStore`, the store for the immutable pieces a blob is cut into, and a conformance suite. This ticket implements it on the filesystem in `packages/db-p2p-storage-fs`, so a Node host keeps pieces across restarts. Each piece is one file holding exactly its bytes: no JSON, no write-ahead log, no write group (docs/blobs.md §The local store).

## Layout

```
<basePath>/
  write-ahead.log, store.lock, <block dirs>, <kv namespaces>   (FileRawStorage / FileKVStore, unchanged)
  optimystic-pieces/
    incoming/<16 hex>.tmp        a piece being written; cleared on open
    <xx>/<piece id>              one file per piece, named by its id, no extension
```

- `PIECE_DIRECTORY = 'optimystic-pieces'`, exported from `file-piece-store.ts`. The name follows the `optimystic-offline` key-value namespace's pattern, chosen so a collection id is unlikely to collide with it at the root, where block directories also live.
- **Fan-out.** `<xx>` is `id.slice(-3, -1)`: the two characters before the last. Every id has the same leading characters (`bafkrei`, `bafybei`: the CID version, codec and hash prefix), so the front cannot spread anything; the last character of a 36-byte CID in base32 carries only 3 bits; the two before it are digest bits. One level of 1024 directories keeps about a thousand files per directory at a million pieces (256 GiB). Rejected: two levels, which at small stores makes one directory per file.
- **Ids are checked before they become paths.** Every method first tests the id against `/^b[a-z2-7]{50,}$/` (a lowercase base32 CIDv1) and throws `RangeError` otherwise. `PieceId` is branded, but this keeps a path out of the filesystem whatever a future caller passes.

```ts
export const PIECE_DIRECTORY = 'optimystic-pieces';

export class FilePieceStore implements IPieceStore {
	readonly durability: StoreDurability = 'power-loss';
	/** Pieces go in `<basePath>/optimystic-pieces/`. Synchronous; the directories are created on first use. */
	constructor(basePath: string);
	/** `fileStoreIdentity(basePath)`: equal to a `FileRawStorage` over the same basePath, whose byte count measures the whole directory, pieces included. */
	storeIdentity(): StoreIdentity;
	// has, get, put, delete, list, bytesUsed, flush, close: IPieceStore
}
```

## Operations

Every operation first awaits a lazy, memoized `open()`: `mkdir -p` the piece root and `incoming/`, then delete every file in `incoming/` (logged as `incoming:cleared` with the count when non-zero). The memo is cleared if `open()` rejects, so the next call retries.

- **`put(id, bytes)`** — the atomic write:
  1. If the final file exists (`fs.access`), return: a present id writes nothing.
  2. `mkdir(fanDir, { recursive: true })`; when that call created the directory (it returns a path), mark the piece root dirty.
  3. Write `incoming/<16 random hex>.tmp` with `fs.open(…, 'wx')`, write every byte, `handle.sync()`, close. The random name comes from `crypto.randomBytes(8)`.
  4. `fs.rename(temp, final)`. If it fails with `EEXIST`, `EPERM` or `EACCES` and the final file now exists, another put of the same id won (Windows refuses to replace a file another handle has open): unlink the temp and return; log `rename:raced`. Any other failure: unlink the temp (ignoring `ENOENT`) and rethrow.
  5. Mark `fanDir` dirty.
  The piece's bytes are synced before the rename, so after a crash the final name holds either the whole piece or nothing; the directory entry itself becomes durable at the next `flush`. Rejected: deferring the file sync to `flush`, which would let a renamed file come back empty or truncated after a power cut, so a reader would see a corrupt piece instead of a missing one.
- **`get(id)`** — `readFileIfExists` (from `file-write-log.ts`), returned as a plain `Uint8Array` view over the buffer `fs.readFile` allocated (`new Uint8Array(buf.buffer, buf.byteOffset, buf.byteLength)`), which no one else holds.
- **`has(id)`** — `fs.access` on the final path; `ENOENT` is false, any other error propagates.
- **`delete(id)`** — `fs.unlink`, `ENOENT` ignored; mark `fanDir` dirty. Any other error propagates (on Windows a piece another handle is reading can refuse deletion; the caller logs and retries later).
- **`list()`** — `readdir` the root, keep two-character directories of the base32 alphabet (`/^[a-z2-7]{2}$/`, which excludes `incoming`), and for each, `readdir` it fully, then yield every name that passes the id test. A temp file is never yielded: temps live only in `incoming/`.
- **`bytesUsed()`** — the sum of `stat().size` over the files `list` would yield. Temps are excluded.
- **`flush()`** — take the dirty set (fan directories, and the root when a fan directory was created) and clear it, then `fsyncDir` each, root last. `fsyncDir` already swallows its errors and is a no-op on win32 (its `NOTE:` explains why), so flush cannot reject on its own; the store's `durability` is `'power-loss'` on the same footing as `FileBatchBackend`'s.
- **`close()`** — `flush()`. The store holds no handle between calls.

No store lock. `FileRawStorage` and `FileKVStore` share a lock through `FileWriteLog`; taking `acquireStoreLock` here as well would refuse the second taker in the same process. Content-addressed files written by rename need no log to stay consistent. Add a `NOTE:` at the class: two `FilePieceStore`s over one directory, in one process or two, are not supported — the second's `open()` deletes the first's in-flight temps, failing its put — and Invariant 5 of `packages/db-p2p/docs/storage.md` (one process per store) is what a host already keeps.

## Coexisting with the block store

`FileBatchBackend.walkBlockDirectories` skips `PIECE_DIRECTORY` at the root, beside `ROOT_KV_NAMESPACES`: build the root skip set as `new Set([...NODE_KV_NAMESPACES, PIECE_DIRECTORY])` (rename the constant `ROOT_SKIPPED_DIRECTORIES` and update its comment to name both). A piece directory holds no `meta.json`, so the walk would never list a piece as a block, but it would descend a thousand directories on every startup listing. `approximateBytesUsed` keeps walking the whole base path, pieces included, which is why `storeIdentity()` reports the base path's identity and `StorageMonitor` does not add the piece figure again (`blockStoreCountsPieces`).

The log namespace is `createLogger('pieces:file')`, i.e. `optimystic:db-p2p-storage-fs:pieces:file`.

## Edge cases & interactions

- **Crash mid-piece.** A temp in `incoming/` is never served, and the next open deletes it. Test (below).
- **Crash after rename, before flush.** The file is whole (synced before rename) or absent. By inspection of the write order.
- **Two puts of one id at once.** Both resolve; one file. On POSIX the second rename replaces an identical file; on Windows it may fail and is treated as the race above. By inspection; the conformance suite covers sequential repeats.
- **A get racing a delete.** `ENOENT` reads as absent. Inspection.
- **Hostile id.** A string with `/`, `..`, uppercase or a drive letter is refused before any path is built. Test (below).
- **A store at a base path no block store uses.** Its identity differs from the block store's, so `StorageMonitor` adds its bytes. Covered by `blockStoreCountsPieces`'s own test.
- **An older store directory with no piece root.** Created on first use; nothing else changes. Inspection; the upgrade suite's coverage of it belongs to `feat-every-storage-backend-stores-blob-pieces`.
- **A collection whose id's first segment is `optimystic-pieces`.** It would share the directory and be skipped by the block listing, the same limitation the key-value namespaces already carry (`FileKVStore.keyToPath`'s `NOTE:`); extend that note to name the piece directory.

## Tests

`packages/db-p2p-storage-fs/test/file-piece-store.spec.ts`:

- `runPieceStoreConformance('FilePieceStore', …, { persistent: true })`, each case in a fresh `fs.mkdtemp` directory, `reopen` returning a new `FilePieceStore` over the same base path, `cleanup` removing the directory.
- "a leftover temp is never served and is removed on open": put a piece, write a file into `optimystic-pieces/incoming/`, open a new store over the directory, call `list()`: only the piece; the temp file is gone.
- "refuses an id that is not a lowercase base32 CID": `get('../x' as PieceId)` and `put` of an uppercase id reject with `RangeError` and create nothing.

No new listing test: the skip is one condition beside the existing namespace skip, verified by inspection.
