# The `blobref` type, `plugin.blobs` and the blob SQL functions

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). This is the first of four parts of backlog `feat-sql-columns-hold-blob-references` (§SQL). It gives the SQL plugin the parts that need no reference tree and no pin lifecycle: the `blobref` column type, the blob service an application stores files through (`plugin.blobs`, `plugin.blobsFor(table)`), a single-machine blob service for transactors with no libp2p node, the pin owner labels every later part uses, and the two SQL functions. Later parts: `feat-blob-reference-trees-follow-sql-rows` (reference-tree maintenance), `feat-blob-pins-follow-sql-commits` (pins and announce through online commits), `feat-sql-columns-hold-blob-references` (offline queue, restart reconciliation, the `unstaged` holding period).

## The `blobref` logical type

New module `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts`:

```ts
import { PhysicalType, type LogicalType, type SqlValue } from '@quereus/quereus';
import { isBlobRef } from '@optimystic/db-core';

/** The name the type is registered under and the `affinity` a catalog record stores for its columns. */
export const BLOBREF_TYPE_NAME = 'BLOBREF';

export const BLOBREF_TYPE: LogicalType = {
	name: BLOBREF_TYPE_NAME,
	physicalType: PhysicalType.TEXT,
	isTextual: true,
	supportedCollations: ['BINARY'],
	validate: (v: SqlValue) => v === null || isBlobRef(v),
	compare: /* NULLs first as TEXT_TYPE orders them, then binary string order */,
};

/** Whether a column, in either the engine's shape (`logicalType`) or a catalog record's (`affinity`), is a blobref column. */
export function isBlobRefColumn(column: { readonly logicalType?: { readonly name: string }; readonly affinity?: string }): boolean;

/**
 * Throw a QuereusError (StatusCode.ERROR) naming `subject` unless the process-wide type registry resolves
 * `blobref` to BLOBREF_TYPE itself (`getType` from `@quereus/quereus`, compared by identity).
 */
export function assertBlobRefTypeRegistered(subject: string): void;
```

- No `parse`. A reference has exactly one accepted spelling (§References and pieces), so the type never rewrites a value; anything `isBlobRef` refuses fails Quereus's `validateValue` with its ordinary `Type mismatch for column 'x': expected BLOBREF` (StatusCode.MISMATCH). `collationAware` is left unset, so a key over the column is keyed BINARY (`pkKeyCollationName` in Quereus), and `semanticOrdering` is unset, so the column compares as stored text. This also means an index on a `blobref` column is an ordinary text index to the plugin's walk rules (`bytesOrderAsValues` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts`) with no change there.
- The row codec stores the string unchanged with no change: `RowCodec` treats any affinity other than BLOB/INTEGER/REAL/NUMERIC/BOOLEAN as text (`deserializeKeyPart` in `packages/quereus-plugin-optimystic/src/schema/row-codec.ts`). A NULL `blobref` references nothing.
- Name `BLOBREF` (upper case) matches the built-in convention (`TEXT`, `BLOB`), so the record's `affinity` reads `BLOBREF`; SQL spells it in any case.

**Registration.** `register` in `packages/quereus-plugin-optimystic/src/plugin.ts` returns `types: [{ name: 'blobref', definition: BLOBREF_TYPE }]` beside `vtables` and `functions`. `registerPlugin` (`@quereus/quereus/src/util/plugin-helper.ts`) registers types after vtables and functions, all before a host calls `plugin.hydrate`, and the registry is process-wide (`TypeRegistry` in `@quereus/quereus/src/types/registry.ts`), so every `Database` in the process sees it.

**A table hydrated or opened without the type registered.** Decided: refused loudly, never opened as something else. Two cases exist. With `strict_type_names` on (Quereus's default), Quereus itself refuses an unknown declared type. With it off, `inferType('blobref')` falls back by the affinity rules and the name contains `BLOB`, so the column would silently become a BLOB column whose stored strings the row codec base64-decodes. So:

- `OptimysticModule.hydrateCatalog` calls `assertBlobRefTypeRegistered(`table '${schema}.${table}'`)` for each stored record that has a column with `affinity` `BLOBREF` (case-insensitive), before `storedToTableSchema`.
- `OptimysticVirtualTable.doInitialize` calls it when any column of the resolved schema is a blobref column by its declared type (`declaredType` base, case-insensitive, equal to `blobref`) while its `logicalType` is not `BLOBREF_TYPE`, or when the record names `BLOBREF` affinity.

The error text says to load the plugin through `registerPlugin`, or to register `plugin.types` with `db.registerType` when registering its parts by hand (the plugin's own tests register `vtables` by hand; the new specs below register `types` too). A plugin build that predates the type cannot open such a table (docs/blobs.md §Compatibility); nothing to build for that, it is the same refusal from Quereus.

## Pin owner labels

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts`, the one place a label is built or parsed. Printable on purpose (they appear in records and logs):

```ts
/** A pin held for a transaction's reference committed into `scope` (a reference tree's collection id). */
export function transactionReferencePinLabel(stampId: string, scope: string): string; // `sql/${stampId}/ref/${encodeURIComponent(scope)}`
/** A pin held for a blob `put` while the transaction `stampId` was open. */
export function transactionPutPinLabel(stampId: string): string;                       // `sql/${stampId}/put`
/** A pin held for a blob `put` outside any transaction, at `putAtMs`. */
export function unstagedPinLabel(putAtMs: number): string;                              // `sql-unstaged/${putAtMs}`
export const TRANSACTION_PIN_PREFIX = 'sql/';
export const UNSTAGED_PIN_PREFIX = 'sql-unstaged/';
export function transactionPinPrefix(stampId: string): string;                         // `sql/${stampId}/`

export type ParsedPinLabel =
	| { kind: 'reference'; stampId: string; scope: string }
	| { kind: 'put'; stampId: string }
	| { kind: 'unstaged'; putAtMs: number };
/** `undefined` for a label this plugin did not write (an application's own owner, or `default`). */
export function parsePinLabel(label: string): ParsedPinLabel | undefined;
```

`StampId()` values are base64url, so they contain no `/`; the scope is URI-encoded so it contains none either. Why the scope is in the label rather than in the offline journal: the blob records are already the durable per-machine store of pins, so a pin that names its transaction and its scope is everything a later settle or restart reconciliation needs, with no change to `JournalEntryRecord` (packages/db-core/src/offline/journal.ts) and no decoding of journaled segments. One reference committed into two tables in one transaction is two pins. Only `parsePinLabel` and the builders are used in this part; the pin lifecycle is the next parts'.

## The pin index on the local blob service (db-p2p)

The plugin must find pins by owner after a restart (the `unstaged` holding period, reconciliation of a settle lost to a crash) and must find a reference's pins (to drop its `unstaged` pin once a transaction holds it). `BlobService` (docs/blobs.md §The node's blob service) has no enumeration, so this part adds one to the db-p2p services, not to the db-core interface:

```ts
// packages/db-p2p/src/blob/local-blob-service.ts (LocalBlobService, from feat-a-node-stores-blob-pieces)
export interface BlobPinIndex {
	/** The owner labels pinned on `ref`; [] when this node holds no record for it. */
	pinsOf(ref: BlobRef): Promise<string[]>;
	/** Every (reference, owner) pin whose owner label starts with `ownerPrefix`, in no promised order. */
	listPins(ownerPrefix: string): AsyncIterable<{ ref: BlobRef; owner: string }>;
}
```

`LocalBlobService` implements it from its `BlobRecordStore`; `NodeBlobService` (from `feat-a-held-blob-follows-its-cohort`, and from `feat-a-node-stores-blob-pieces` for its local half) inherits or forwards it. If either already exposes an equivalent, use it and name it here. `listPins` scans the records; add a `NOTE:` tripwire at it ("scans every blob record; if a machine ever holds enough blobs for a prefix query to show, index pins by owner prefix").

**`pin` of a reference with no record** must create the record with the pin (a statement may commit a reference copied from another row whose bytes are elsewhere). If `feat-a-node-stores-blob-pieces` made `pin` refuse that, change it here and say so in the handoff.

## A blob service with no libp2p node

`local`, `test`, `mesh-test` and custom transactors have no node and so no `node.blobs`. New in db-p2p, `packages/db-p2p/src/blob/single-machine-blob-service.ts`, exported from the package index:

```ts
export interface SingleMachineBlobServiceInit {
	pieces: IPieceStore;   // from feat-a-node-stores-blob-pieces
	kv: IKVStore;          // the blob records' store
	digest?: BlobDigest;
}
/** A BlobService whose cohort is this machine alone: LocalBlobService for everything except `announce`, `stat`'s durability and `onDurability`. */
export class SingleMachineBlobService implements BlobService, BlobPinIndex {
	constructor(init: SingleMachineBlobServiceInit);
}
```

Built by composition over `LocalBlobService` (not subclassing, so it depends only on that class's public surface). `announce(ref, scope)`: adds an `owed` hold to the blob's record through `BlobRecordStore` (its record type carries all four hold kinds from `feat-a-node-stores-blob-pieces`; if that ticket exposed operations for pins only, add the general add-hold and remove-hold beside them, which `feat-a-held-blob-follows-its-cohort` also needs), creating the record if none exists, flushes the key-value store, then emits one `onDurability` event in the `BlobDurabilityEvent` shape of `feat-blob-references-and-verified-piece-trees` with class `local` and a holder count of 1, the first time the reference is announced (a re-announce emits nothing). `stat` adds `durability` (class `local`, count 1) for an announced reference. The `owed` hold is never released by copying, since there is nobody to copy to; `feat-unreferenced-blobs-are-reclaimed` releases it when the reference is no longer listed, exactly as it releases a networked node's owed entry whose cohort never fully holds the blob (docs/blobs.md §Lifetime, "An owed blob follows the same rule"). Log namespace `optimystic:db-p2p:blob:store` for the announce line (`blob:announce-single-machine ref=… scope=…`).

## `plugin.blobs` and `plugin.blobsFor(table)`

**Backends in the collection factory** (`CollectionFactory` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`):

```ts
export type SqlBlobBackendService = BlobService & BlobPinIndex;
export interface BlobBackend {
	/** The transactor key (`${transactor}:${keyNetwork}`) this backend belongs to. */
	readonly key: string;
	readonly service: SqlBlobBackendService;
	/** The transactor of the same key: reference trees and the scope registry of this network are read and written through it. */
	readonly transactor: ITransactor;
}
/** One backend per transactor key, created on first use and shared by every table on that key. */
getBlobBackend(options: ParsedOptimysticOptions): Promise<BlobBackend>;
/** The backends resolved so far. */
resolvedBlobBackends(): BlobBackend[];
/** Called once per backend, the first time it resolves. Returns an unsubscribe. */
onBlobBackendResolved(listener: (backend: BlobBackend) => void): () => void;
```

Resolution, keyed and de-duplicated in flight exactly as `getOrCreateTransactor` is (a `blobBackendsInFlight` map, failure not remembered):

- `network`: resolve the transactor first (which builds or reuses the node), then `node.blobs` of the node under `getNodeKey(options)`. A node a host injected through `registerLibp2pNode` without `blobs` falls through to the single-machine arm, logged once (`blob:backend-single-machine reason=node-without-blobs`).
- `local`: `new SingleMachineBlobService(options.blobStorageFactory?.() ?? memory())`, where `memory()` is a `MemoryPieceStore` and a `MemoryKVStore` (`packages/db-p2p/src/storage/memory-kv-store.ts`).
- `test`, `mesh-test`, and a custom transactor: the single-machine service in memory.

`blobStorageFactory` is a new plugin-level option beside `rawStorageFactory`, read the same way (`resolveBinding` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` takes a function out of the registration config; add the field to `ParsedOptimysticOptions` in `packages/quereus-plugin-optimystic/src/types.ts`):

```ts
/** For a 'local' transactor: where blob pieces and blob records live. Both or neither persistent:
 * a persistent piece store over in-memory records loses every pin at restart, and the sweep then deletes every piece. */
blobStorageFactory?: () => { pieces: IPieceStore; kv: IKVStore };
```

Not passed to the `network` node built by `createNetworkTransactor`: that node gets the defaults `NodeOptions.pieceStorage` gives (and logs its own warning). Add a `NOTE:` there: "the plugin's own node keeps blob pieces and records in memory; if a host needs them persistent through the plugin, thread `blobStorageFactory` into `pieceStorage` and `kvStore` here".

**The service an application holds.** New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/sql-blob-service.ts`:

```ts
/** The BlobService `plugin.blobs` and `plugin.blobsFor` hand out: the backend of one transactor key,
 * resolved on first use, with `put`'s owner defaulted from the bridge's open transaction. */
export class SqlBlobService implements BlobService {
	constructor(resolve: () => Promise<BlobBackend>, bridge: TransactionBridge, now?: () => number);
}
```

- `put(source, options)`: `owner` is the caller's when given; otherwise `transactionPutPinLabel(stampId)` while `bridge.getCurrentTransaction()?.isActive`, else `unstagedPinLabel(now())`. This is what "pins on behalf of the current transaction" means while a transaction is open, and what docs/blobs.md §SQL calls `unstaged` otherwise.
- `stat`, `read` (an async generator that awaits the backend then delegates with `yield*`), `fetch`, `pin`, `unpin`, `announce`: delegate.
- `onProgress` and `onDurability`: listeners are kept in a set on the wrapper; the first subscription starts resolution (`void`, failure logged) and attaches one forwarding listener to the backend's service when it resolves; the returned unsubscribe removes the listener from the set. The precedent is `LateBoundCohortReachability` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/late-bound-reachability.ts`).

`register` returns:

```ts
/** The blob service of the plugin's default network: the transactor the registration config (and the session's default_vtab_args) bind a table declared without a `using` clause to. */
blobs: SqlBlobService,
/** The blob service of the network `table` uses. Throws QuereusError for a table that is not an Optimystic table. */
blobsFor: (table: string, schema?: string) => Promise<SqlBlobService>,
```

`plugin.blobs` resolves its options lazily, on first use, through a new `OptimysticModule.defaultBindingOptions(db, config)` that wraps `deriveDefaultOptions(config, sessionDefaultVtabArgs(db))` (the binding hydrate already uses for the catalog), because a host may set `default_vtab_args` after `register`. `blobsFor` resolves the table through `lookupOrInstantiate` (no initialization) and takes its `options`. One `SqlBlobService` per transactor key, cached in the plugin, so `plugin.blobs === await plugin.blobsFor(t)` for a table on the default network. A reference means something only in its own network (§SQL); nothing refuses a reference from another network at write time (see `feat-sql-columns-hold-blob-references`, "A table on another network").

## SQL functions

New module `packages/quereus-plugin-optimystic/src/functions/blob-functions.ts`: `createBlobLocalityFunction(blobs: SqlBlobService)` and `createBlobSizeFunction(blobs)`, registered in `register`'s `functions`:

- `BlobLocality(ref)`: `numArgs: 1`, `flags: FunctionFlags.UTF8` (not `DETERMINISTIC`: the answer changes as bytes move), `isAsync: true`, return type `TEXT_TYPE` nullable. NULL in gives NULL. Otherwise `parseBlobRef(arg)` (a non-string argument and a malformed string both throw `BlobRefError`), then `(await blobs.stat(ref)).locality` — `here`, `partial`, `elsewhere` or `unknown`. No `probe`: answered from local records only, so it never waits on the network.
- `BlobSize(ref)`: same flags, return type `INTEGER_TYPE` nullable; `stat(ref).size ?? null` (NULL while the root piece is not here, and for an unknown reference).
- A `BlobRefError` is raised as `QuereusError(message, StatusCode.MISMATCH, error)` so the SQL error carries the reason and keeps the original as `cause`.
- Both answer through `plugin.blobs` (the default network): a function has no table context. A host with tables on several networks reads `stat` through `plugin.blobsFor(table)` instead; README says so.
- Documented as not for writes: a validating member re-executing a statement whose written value came from `BlobLocality` would compute a different value (backlog note "BlobLocality written into a row").

## Edge cases & interactions

- **Malformed references.** Uppercase base32, a CIDv0, another codec or multihash, surrounding whitespace, a number: refused by `validate` on write (MISMATCH), and by both functions (MISMATCH with `BlobRefError` as cause). Verified by the `blobref-column.spec.ts` and `blob-functions.spec.ts` cases.
- **NULL.** Accepted in a nullable `blobref` column; `BlobLocality(null)` and `BlobSize(null)` are NULL. Test cases.
- **Type registered late or not at all.** `hydrateCatalog` and `doInitialize` refuse with the actionable error rather than opening a BLOB column (assertion at both seams). Test: a fresh `Database` that registers `vtables` but not `types`, hydrating a table with a `blobref` column, is refused; with `types` registered it hydrates and reads the value back unchanged.
- **`strict_type_names` off.** The same refusal (the assertion compares the resolved type by identity, not by whether Quereus resolved some type). Inspection.
- **Two `Database`s in one process.** The type registry is process-wide; registering the type again from a second `registerPlugin` logs Quereus's "Overwriting existing type" warning and replaces it with the same definition object. Harmless. Inspection.
- **`plugin.blobs` before any table exists.** Resolves the default network's backend on first use; for `network` that builds the node, as the first table would. Inspection.
- **Listener before resolution.** A durability listener subscribed before `plugin.blobs` resolved receives every event after resolution; an unsubscribe before resolution leaves nothing attached. Inspection against the late-bound precedent.
- **Injected node without `blobs`.** Single-machine service, logged once. Inspection.
- **Persistent records over memory pieces (`local`).** The option's doc says both or neither; no runtime check (the plugin cannot tell an `IKVStore` is persistent). Inspection.

## Tests

- `packages/quereus-plugin-optimystic/test/blobref-column.spec.ts`: one table (`Id text primary key, Content blobref null`) on the `test` transactor, plugin registered with its `types`. Cases: a well-formed reference (built with `buildBlob` over a few bytes, or a fixed vector from `feat-blob-references-and-verified-piece-trees`) inserts and reads back byte-identical; each malformed shape above is refused with `StatusCode.MISMATCH`; NULL inserts; hydrate into a second `Database` over the same storage works with `types` registered and is refused without.
- `packages/quereus-plugin-optimystic/test/blob-functions.spec.ts`: after `plugin.blobs.put` of a two-piece stream, `select BlobLocality(?), BlobSize(?)` answers `here` and the size; for a well-formed reference never put, `unknown` and NULL; for a malformed string, a MISMATCH error whose `cause` is a `BlobRefError`; NULL gives NULL. One more case pins `put`'s owner default: a put outside a transaction holds a pin `parsePinLabel` reads as `unstaged`, and a put between `begin` and `commit` one it reads as `put` for that transaction's `StampId()` (read through the backend's `pinsOf`).
- `packages/db-p2p/test/single-machine-blob-service.spec.ts`: `announce` emits exactly one `local` durability event with count 1 on the first call and none on a second; after `unpin` of the only pin, the blob is still held (the `owed` hold) and `stat` reports `here` with durability `local`.
