GitHub #52 (kjeib); `gh issue view 52` has the repro script. Numbers are the reporter's. Table `M (Id text primary key, T text not null)`, `index MT on M (T)`, 2,000 rows, Optimystic 1.23.0, Quereus 4.24.0, `transactor='test'`, median of 7 reads:

| query | memory table | Optimystic table |
|---|---|---|
| `order by T asc limit 10` | INDEXSCAN, 1.3 ms | SORT SEQSCAN, 22.1 ms |
| `where T > 't001990' order by T` | INDEXSEEK, 1.3 ms | SORT FILTER SEQSCAN, 13.4 ms |
| `where T > 't001990'` | INDEXSEEK, 0.9 ms | FILTER SEQSCAN, 11.9 ms |
| `where T = 't001000'` | INDEXSEEK, 0.9 ms | INDEXSEEK, 5.3 ms |
| `order by T desc limit 10` | SORT INDEXSCAN, 13.3 ms | SORT SEQSCAN, 21.4 ms |

Why it matters: Sereus Chat's message list is `select … from App.Message order by Timestamp desc, Id desc limit 100`. It takes 21 / about 100 / about 450 ms at 100 / 1,000 / 5,000 messages in Node, the same with or without an index on `Timestamp` or `(Timestamp, Id)`, and the reporter estimates a phone at about 5× that.

The secondary-index loop in `getBestAccessPlan` considers an index only when an `=` filter matches its leading column, and `orderingMatchesIndex` is applied only after an equality seek has chosen the index.

## Expected, in the reporter's order

1. An ordering-only index scan when `requiredOrdering` matches an index the tree can deliver in order (ascending BINARY text today, the case `orderingMatchesIndex` already treats as safe), with a `limit` stopping it early.
2. A range seek on a secondary index for the same safe cases.
3. Descending order through a reverse scan. The last row of the table shows a memory table does not get this either, so part of it may belong to Quereus. Find out whether this module can offer a descending ordering itself over a reverse tree scan. If Quereus has to change, send the exact change to `blocked/` as a dependency on the sibling repository, and let items 1 and 2 go ahead without it. The motivating query is descending, so say plainly what it gains from items 1 and 2 alone.

## Boundaries

Only orderings the stored key bytes really deliver. Numeric and descending value order depends on `debt-optimystic-true-key-ordering`, which is a separate decision about data on disk, and primary-key ranges are `debt-optimystic-pk-range-seek`; do not change key encoding here. An index key is `frame(indexValue) ‖ frame(primaryKey)`, so check that framing preserves value order for the cases claimed, including a value that is a prefix of another. Rows with a null indexed value must appear where the engine expects them, or the plan must not be claimed. A partial index holds only the rows its predicate admits, so it cannot serve an ordering over the whole table. A scan reading through an index must stay consistent under the read rules in `docs/internals.md` (one pinned view pair for a committed read, the throw-on-change contract for a live scan).
