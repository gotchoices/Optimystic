GitHub #44 (kjeib), comment of 2026-11-03; read it with `gh issue view 44 --comments`. The issue's original join case is reported fixed. This is the shape that remains. Numbers are the reporter's: sereus 1.20.0, optimystic 1.23.0, quereus 4.24.0.

```sql
select lei.entry_id, i.id, i.name, c.id, c.name, lei.source_bundle_id, b.name
from log_entry_items lei
join items i on i.id = lei.item_id
join categories c on c.id = i.category_id
left join bundles b on b.id = lei.source_bundle_id
where lei.entry_id in (?, ?, … 31 ids)      -- log_entry_items has an index on entry_id
order by i.name asc
```

```
memory:  HASH JOIN ← HASH JOIN ← HASH JOIN ← INDEX SEEK log_entry_items USING idx_log_entry_items_entry (the IN list)
strand:  JOIN ← JOIN ← JOIN ← FILTER lei.entry_id IN (…) ← SEQ SCAN log_entry_items,
         then INDEX SEEK items / categories / bundles USING primary, once per outer row
```

| ms (Node, 177 entries, 485 rows) | memory | strand | +1 node | +2 nodes |
|---|---|---|---|---|
| with `in (…31 ids…)` (72 rows) | 7 | 59–71 | 62–67 | 100–125 |
| same joins, no `where` (485 rows) | 15 | 15–16 | 17–18 | 17–19 |

On a Galaxy S7 (release build, 2 nodes) the query takes 7.2 s. The reporter offers a standalone repro on request; Sereus Health's bench reproduces it with `SYNTH=1 MODES=memory,strand NODES=2 WRITES=0 PLAN='history page items (History)' PLAN_EACH=1 node bench.mjs`, but a plain plugin-level plan check should reach the same plan.

## Expected

An `in` list on a secondary index's leading column, and on the primary key if it is not already handled, is served as one seek per listed value, so the outer side delivers only the matching rows and the join plan matches the one a memory table gets. Find out how Quereus's memory module receives and claims an `in` filter, and what the planner offers a virtual table for it. If Quereus offers nothing this module can claim, that is a dependency on the sibling Quereus repository, which goes to `blocked/` with the exact change proposed.

## Edge cases to carry into the implement ticket

Duplicate values in the list must not return a row twice. A `null` in the list matches nothing. Every `getBestAccessPlan` claim of a filter is a promise the engine trusts (see the comments on trusting the seek in `executeIndexScan`), so a claimed filter must be fully enforced, including under a non-binary collation and on a partial index. A list too long for one seek per value to beat a scan should still cost out as a scan.
