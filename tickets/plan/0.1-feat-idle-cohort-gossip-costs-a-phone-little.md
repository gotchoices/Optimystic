# Idle cohort gossip costs a phone little

GitHub [#49](https://github.com/gotchoices/Optimystic/issues/49), from Sereus (Taleus).

## Observed

On 1.19.0 the reporter ran a two-member strand of 18 tables tagged `optimystic.network_watch`. One member was a Galaxy S7 (Hermes) and the other a Node party, connected over a relay. While both were idle:

- **On the S7:** 15.6% of a 60 s sampling profile was inside `@noble/curves`' `ed25519.verify`. About 92% of that came from one path: `verifyPeerSig` ← `verifyGossipSig` ← `TransportCohortGossipBus.onInbound` ← `FretCohortGossipTransport.deliver`. The rest came from `FretCohortThresholdCrypto.collectFrom` and commit-proof approval counting. The JS thread was 100% busy, and the app's CPU dropped from 150–220% to about 30% when the Node party exited.
- **In Node:** each party received 108 gossip frames every 30 s (216 a minute) across 19 transport handlers, one coord engine per watched collection plus one. Each frame is verified once, after `isOurCoord`. One verify takes 2.4 ms in Node and about 40 ms on the S7.

The cost grows with the number of watched collections: each served coord signs and sends its own frame each round, and the receiver verifies each one on its own.

## Expected

On a strand whose records, willingness and load have not changed, idle gossip should cost a phone a small, roughly constant amount of CPU, not one signature check per watched table every few seconds. A real change must still reach the other members within today's bounds, and a member that has gone silent must still be noticed.

## Remedies the reporter proposed (any one helps; they compose)

- **Verify once, natively, off the synchronous path.** `peer-sig.ts` uses noble because the db-core verify ports are synchronous. The transport could verify a frame once in `deliver` with libp2p's async `publicKey.verify`, which on React Native can use a native Ed25519 (for example, `@serfab/cadre-rn`'s polyfill, sereus#33), and then hand the bus a frame already marked as verified.
- **One frame per member per round.** Carry all of a member's served coords in one signed frame per peer per interval, so the cost is one signature per round instead of one per topic. This needs a wire change and a fallback for members on older builds.
- **Back off when idle.** If nothing a frame would carry has changed since the last one, send less often.

## Open question

`willingnessHeartbeatMs` (default ~30 s) already throttles idle willingness-only rounds, yet the measured rate is about one frame per engine per 5 s, the tick rate. Check whether these idle rounds carry records, for example renewals touching `lastPing` on every tick and turning into gossip deltas, which would make "idle" gossip record-carrying every round. If so, the cheapest fix may be to not gossip a renewal that changes nothing a sibling needs.
