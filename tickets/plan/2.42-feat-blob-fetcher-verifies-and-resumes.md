# Blob fetcher: verify, resume, schedule

After `feat-blob-protocol-frames-stat-and-get` a node can ask a peer for up to 16 pieces of a blob and receive them as raw frames. This ticket builds `BlobFetcher`, the one code path that receives pieces: it works out which pieces a blob (or a byte range of it) still lacks here, picks holders from the blob's cohort, asks them in batches, checks every piece against the CID that named it before storing it, penalizes a peer that sends wrong bytes and asks someone else, resumes an interrupted transfer by asking only for what is missing, shares one fetch per piece between concurrent callers, and limits streams so background copying never holds up a read the application is waiting on. `feat-blob-pieces-move-between-machines` puts `node.blobs.read`, `fetch` and `stat` with `probe` on top of it; `feat-a-referenced-blob-is-copied-to-its-cohort` uses it with background priority to pull announced blobs.

## Module layout and types

`packages/db-p2p/src/blob/blob-fetcher.ts`:

```ts
export type FetchPriority = 'foreground' | 'background';

export interface BlobFetchRequest {
	priority: FetchPriority;
	/** Byte range; absent means the whole blob. Same meaning as BlobReadOptions. */
	offset?: number;
	length?: number;
	/** Peers known to hold the blob (an announcer, a peer that answered a stat); asked first, in this order, still filtered like every candidate. */
	knownHolders?: readonly string[];
	/** Keep retrying while no reachable holder can supply a missing piece, until no piece has arrived for this long. Absent or 0: fail after the first round that leaves a piece unavailable. */
	waitMs?: number;
	signal?: AbortSignal;
}

export interface PieceStoredEvent { ref: BlobRef; id: PieceId; bytes: number; peer: string }

/** One caller's fetch of one blob. */
export interface BlobFetchSession {
	/** Resolves when every piece the range needs is stored here; rejects with BlobUnavailableError, BlobCorruptError, or the signal's reason. */
	readonly done: Promise<void>;
	/** Resolves when `id` is stored here (at once if it already is); rejects when `done` rejects first. For a reader that consumes pieces as they arrive. */
	stored(id: PieceId): Promise<void>;
}

export interface BlobFetcherDeps {
	selfPeerId: string;
	client: BlobProtocolClient;
	blobProtocol: string;                                   // buildBlobProtocol(prefix), for peersServing
	keyNetwork: Pick<Libp2pKeyPeerNetwork, 'findCluster' | 'peersServing'>;
	membership: NetworkMembershipGate | undefined;
	reputation: Pick<IPeerReputation, 'reportPeer' | 'isBanned' | 'isDeprioritized'>;
	pieces: IPieceStore;
	records: BlobRecordStore;
	digest: BlobDigest;
}

export class BlobFetcher {
	constructor(deps: BlobFetcherDeps);
	start(ref: BlobRef, request: BlobFetchRequest): BlobFetchSession;
	onPieceStored(listener: (event: PieceStoredEvent) => void): () => void;
}
```

```ts
export const MAX_BLOB_BACKGROUND_GET_STREAMS = 4;
/** Most foreground `get` streams this node has open at once. */
export const MAX_BLOB_FOREGROUND_GET_STREAMS = 8;

```

## What a session does

`start` returns at once; the work runs in the background and settles `done`.

1. **Nothing missing.** Plan the range against the local store (step 3). If no piece is missing, resolve. No peer is asked and the cohort is not looked up.
2. **Hold before storing.** Before the first piece is stored, take a `cached` hold on the blob's record (creating the record if there is none), through `BlobRecordStore`. Pieces are fetched top down (a list piece before the pieces it names), so once the record holds the blob every stored piece is reachable from its reference through present list pieces, and the sweep of `feat-a-node-stores-blob-pieces` (which walks held blobs' trees) cannot delete it. No extra in-memory protection is needed. A failed or aborted session keeps the hold and the pieces it stored, which is what makes the next session resume; evicting cached blobs is `feat-unreferenced-blobs-are-reclaimed`'s.
3. **Plan.** Ask the range planner from `feat-blob-references-and-verified-piece-trees` (the function that, given a reference, a `PieceSource` and an optional range, reports the pieces the range needs and whether each is present) over the local piece store, and take the **frontier**: missing pieces whose parent is present, plus the root when it is missing, in tree order (left to right). Use whatever name that ticket exported; if it exposes only `walkBlobPieces`, use that for whole-blob sessions and add a range-limited planner to db-core in this ticket. A planner error that is a `BlobCorruptError` (a stored list piece that is structurally malformed, with a correct hash) rejects the session with it; nothing is retried, since another holder would serve the same bytes.
4. **Candidates** (`blob-holders.ts`, `blobHolderCandidates(...)`): `knownHolders` first in their order, then the members of `keyNetwork.findCluster(routingKeyForBlob(ref))` that are not already listed, connected peers before the rest. Remove self, any peer `admittedBy(membership, peer)` refuses (an assertion at this one filter: no other code path chooses a peer to fetch from), any peer `reputation.isBanned`, and keep only `keyNetwork.peersServing(blobProtocol, …)`. Peers `reputation.isDeprioritized` move to the end. A `findCluster` that throws is logged and treated as an empty cohort. Candidates are recomputed at the start of each round, so a holder that connects during a `waitMs` wait is found.
5. **Batches.** Take frontier pieces not already in flight (see dedupe) in tree order, up to `MAX_BLOB_GET_PIECES`, and ask the first candidate that has not yet answered "not held" for any of them and has not failed in this round. On the reply:
   - each piece frame: check it (below); good → `pieces.put(id, bytes)`, resolve its waiters, emit `PieceStoredEvent`, note progress time; bad → discard, `reputation.reportPeer(peer, PenaltyReason.InvalidRestoration, \`blob-piece ${id}\`)` once, mark the peer as having served corrupt bytes for this session (never asked again in it), log `fetch:penalized`.
   - ids the header lists as not held → record "answered not held" for that peer and piece; the piece goes back to the frontier for the next candidate.
   - a thrown `get` (dial failure, `BlobTransferStalledError`, `BlobPeerRefusedError`, `BlobProtocolError`, stream reset) → record "did not answer" for that peer for every piece of the batch not yet received; pieces already stored stay stored. Move the peer to the end for the rest of the round.
   After each batch, re-plan (a newly stored list piece exposes its children) and continue until the frontier is empty or every remaining frontier piece has been offered to every candidate.
6. **Round outcome.** Frontier empty → if the session had no range, mark the record whole with its size through `BlobRecordStore`; resolve. Otherwise classify the first unavailable piece in tree order with `unavailableOutcome` (below). If `waitMs` is set and less than `waitMs` has passed since the last piece was stored (or since the session started), wait `BLOB_WAIT_RETRY_INITIAL_MS`, doubling to `BLOB_WAIT_RETRY_MAX_MS`, capped by the time left, and run another round from step 3; else reject with the classified error.

**Checking a piece** before it is stored: its length is at most `MAX_BLOB_PIECE_FRAME_BYTES`, `digest(bytes)` equals the SHA-256 digest inside the piece id, and the id's codec is `raw` or `dag-pb`. Use the per-piece check `feat-blob-references-and-verified-piece-trees` exports; if it exports none, add `pieceMatches(id: PieceId, bytes: Uint8Array, digest: BlobDigest): Promise<boolean>` to db-core's blob directory. Structure (a list piece's links and sizes) is not judged here: the planner and the reader judge it from the stored piece, and a correct-hash piece with bad structure is the blob's fault, not the sender's.

**Classifying** (`unavailableOutcome` in `blob-holders.ts`, pure):

```ts
export type PieceOutcome = { peer: string; answer: 'not-held' | 'no-answer' | 'corrupt' };
/** What one unavailable piece's attempts in a round amount to. */
export function unavailableOutcome(candidateCount: number, attempts: readonly PieceOutcome[]):
	| { error: 'unavailable'; reason: 'not-held' | 'peers-unreachable' | 'cohort-unreachable' }
	| { error: 'corrupt' };
```

| Attempts this round | Result |
|---|---|
| no candidate at all | `cohort-unreachable` (none could be asked) |
| every candidate `no-answer` | `cohort-unreachable` |
| at least one `corrupt`, and every other candidate `not-held` | `BlobCorruptError` (a holder served bad bytes and no other holder could supply them) |
| any `no-answer`, the rest `not-held` or `corrupt` | `peers-unreachable` (a silent holder may still have it) |
| every candidate `not-held` | `not-held` |

The errors are db-core's `BlobUnavailableError(ref, reason)` and `BlobCorruptError` from `feat-blob-references-and-verified-piece-trees`. `not-here` is never produced here; it belongs to `read` with `from: 'here'`.

**Dedupe.** The fetcher keeps one `Map<PieceId, InFlight>` of pieces currently requested from some peer. A session that needs an in-flight piece does not request it again; it waits for that attempt, and on its failure takes the piece back into its own frontier. So two reads of one blob request each piece once, and `pieces.put` is called once per piece (a put of a present id writes nothing anyway, per `IPieceStore`). Assertion at the seam: before sending a batch, assert that no id in it is already in the in-flight map.

**Abort.** A session's `signal` rejects `done` and every `stored` waiter with `signal.reason` and stops the session from starting new batches. A batch already sent is left to finish (it is at most 16 pieces, bounded by the progress deadline), because another session may be waiting on its pieces and what it stores is kept anyway.

## Scheduling

`packages/db-p2p/src/blob/blob-get-slots.ts`, `BlobGetSlots`: per peer, at most one open `get` stream per priority; per node, at most `MAX_BLOB_BACKGROUND_GET_STREAMS` background and `MAX_BLOB_FOREGROUND_GET_STREAMS` foreground streams. `acquire(peer, priority, signal): Promise<() => void>` waits in FIFO order per pool; the release function is called in a `finally`. The two priorities have separate pools, so a foreground batch never waits for a background stream: it opens its own stream beside the background one, and the stream multiplexer interleaves them frame by frame. The alternative, one stream per peer shared by both priorities, was rejected because a read would then wait behind up to 16 background pieces; the server's allowance (`MAX_BLOB_INBOUND_GETS_PER_PEER = 2`) is sized for exactly one stream of each kind. A session's batches run one at a time per session (re-planning between them needs the previous batch's list pieces), while different sessions and priorities run concurrently up to the caps.

## Edge cases & interactions

- **Wrong bytes from one holder, right bytes from another.** The read succeeds, the bad piece is never stored, the bad peer is penalized once and not asked again in the session. Test.
- **Every holder serves wrong bytes.** `BlobCorruptError`; nothing stored for that piece. Covered by the classification table test.
- **Correct hash, malformed structure.** `BlobCorruptError` from the planner, no penalty, no retry. Inspection.
- **Interrupted fetch.** Pieces stored before the interruption stay; the next session plans against the local store and asks only for what is missing. Test.
- **Partial holder.** Pieces it lacks come back "not held" in its header and go to the next candidate in the same round. Inspection; the classification test covers the outcome.
- **Header lies / stalled stream.** Counted as `no-answer` for the unreceived pieces; the next candidate is asked. Inspection (the stall itself is pinned in the protocol ticket's tests).
- **Busy holder.** `BlobPeerRefusedError('busy')` is `no-answer` for the round; a later round may try it again. Inspection.
- **Refused by the membership predicate, banned, or not speaking the protocol.** Never dialed: one filter in `blobHolderCandidates`. Inspection.
- **Self in the cohort.** Removed. A blob whole here starts no network work. Inspection.
- **Solo node.** No candidates → `cohort-unreachable` at once, or after `waitMs`. Classification test.
- **Concurrent sessions on one blob.** One request per piece; second session waits on the first's in-flight attempt; the assertion at the batch seam. Inspection plus the assertion.
- **Foreground behind background.** Separate pools; a foreground batch to a peer with an open background stream opens its own. Inspection of `BlobGetSlots`.
- **Sweep during a fetch.** The `cached` hold is taken before the first `put` and pieces arrive top down, so every stored piece is reachable from a held reference. Inspection. A cache-eviction pass running during a fetch is `feat-unreferenced-blobs-are-reclaimed`'s to avoid; add a `NOTE:` at the hold saying eviction must skip blobs with a session in flight.
- **Crash mid-fetch.** Stored pieces are flushed by the piece store's own contract; the record with its cached hold may or may not have been flushed. If not, the next sweep may remove the orphan pieces, and the next read fetches them again. Accepted; inspection.
- **`findCluster` throws.** Empty cohort for that round, logged. Inspection.
- **`waitMs` with no progress.** Stops once `waitMs` passes with no piece stored; a piece arriving resets the clock. Exercised end to end in `feat-blob-pieces-move-between-machines`.

## Tests

- `packages/db-p2p/test/blob-holders.spec.ts`: `unavailableOutcome` over the five rows of the table, one case per row. This is the branching logic that decides which error an application sees.
- `packages/db-p2p/test/blob-fetcher.spec.ts`, real nodes over loopback TCP built with `createLibp2pNode`, `clusterSize` 3, connected to each other, each with a piece store passed through `NodeOptions.pieceStorage`:
  - *Wrong bytes*: node A's piece store is a small test decorator over `MemoryPieceStore` that returns one piece's bytes with a byte flipped; node C holds the same blob unaltered; node B starts a foreground session with `knownHolders: [A, C]`. `done` resolves, B's store holds the correct bytes for every piece, and B's reputation records one `InvalidRestoration` report against A.
  - *Resume*: nodes built with `rpcDeadlines: { responseTimeoutMs: 500 }`. Node A holds a blob of 8 data pieces under one list piece; a decorator over A's piece store counts `get` calls per id and holds the call for the fifth data piece on a promise the test controls. Node B's first session (A is the only holder) stalls on that piece, its progress deadline ends the stream, and `done` rejects with `BlobUnavailableError`; B's store holds the list piece and the first four data pieces. The test releases the held call and B starts a second session, which resolves. Every id was served by A once, except the held piece (twice: the stalled attempt and the retry). This pins that an interrupted fetch keeps what it stored and asks only for the rest. (Aborting B's signal would not interrupt anything: a batch already sent runs to its end.)
  The test helper that builds nodes and blobs is local to the spec file; `feat-blob-pieces-move-between-machines` may move it into a shared test helper if it needs the same shape.
