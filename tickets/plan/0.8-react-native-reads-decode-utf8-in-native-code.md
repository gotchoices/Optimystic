# React Native reads decode UTF-8 in native code

GitHub #51 (kjeib).

## Problem

Every block, transform, metadata and action-id read on React Native goes:
`rn-opener.ts` `get` → `native.getBuf(...)` → `new Uint8Array(...)` → `raw-store-codec.ts`
`decodeJson` / `decodeActionId` → `TextDecoder.decode` → `JSON.parse`. Hermes has no native
`TextDecoder`, so the decode runs in the host's JavaScript polyfill.

Reported measurements (Galaxy S7, Hermes debug build, optimystic 1.20.1, one offline-mode log-entry
save with 2 nodes): of the 2.66 s of fully busy JS thread before the first `pendMany`, ~740 ms was
`kv-raw-storage` / `cached-raw-storage` → `raw-store-codec` → the polyfill, the largest single item;
over the whole 45 s window, 2.4–2.8 s of self time. It applies to every read on React Native, offline
mode or not.

`rn-leveldb`'s `LevelDB` offers `getStr(key): string | null`; `put` and `WriteBatch.put` accept a
string value; iterators have `valueStr()`.

## What the plan must settle

1. **Does `getStr` decode UTF-8 exactly as `TextDecoder` does?** Read `gotchoices/rn-leveldb`'s
   `cpp/react-native-leveldb.cpp` (both organisation repos; a maintainer can change it). The values on
   disk are `TextEncoder.encode(JSON.stringify(v))`, so if `getStr` builds a JS string from the bytes
   as UTF-8, existing stores read correctly with no migration. Check non-ASCII (BMP and astral) and
   any truncation on embedded NUL. If it does not decode UTF-8 faithfully, that is an upstream change
   — route to `blocked/` with the proposed API, as `react-native-storage-syncs-once-rn-leveldb-can`
   did.
2. **Where the string path enters the interface.** Today values cross `RawStoreDriver` as
   `Uint8Array` and the codec is the single place bytes become objects (the clone-on-read invariant
   in docs/internals.md *Storage Returns References* rests on that). Options: (a) an optional
   string-returning read on the driver / KV store that `KvRawStorage` prefers when present, decoding
   with `JSON.parse` alone; (b) a value type of `Uint8Array | string` across the boundary; (c) a
   per-driver codec. Pick one and record why; keep the invariant structural (a string parsed fresh
   per read is still a fresh object). Prefer not widening every driver's types for one backend.
3. **The write-through cache** (`CachedStoreDriver`) caches encoded bytes. Decide what it caches
   on React Native so a cache hit does not reintroduce the JavaScript decode (caching the string is
   the obvious answer; bound its memory accounting accordingly).
4. **The journal.** Writes on this backend go through the journal
   (`react-native-storage-commits-groups-through-the-journal`); confirm which reads hit LevelDB
   values directly and which are served from journal records, and that both get the native path.
5. **Writes.** Optional: `put(key, string)` would skip `TextEncoder` too, but Hermes has a native
   `TextEncoder`, so measure before taking it on. Out of scope unless cheap and shown to matter.
6. **Iterators** (`rangeRevisions`, listings): use `valueStr()` where the value is decoded as JSON;
   key iteration stays on bytes.

## Edge cases & interactions (for the implement ticket)

- Existing stores written by earlier builds read identically (verify by a round-trip over the same
  bytes through both paths, including non-ASCII content).
- Other backends (fs, web, ns, memory) unchanged; the conformance suite
  (`src/testing/raw-storage-conformance.ts`) still passes against every driver, including the cached
  compositions.
- `yarn check:rn` still bundles and compiles under Hermes.
- The `TextDecoder` polyfill may still be needed for other code; the README's React Native section
  should say whether storage still requires it.
