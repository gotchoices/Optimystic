# Fewer consensus calls per write

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29), question 2. Split out of plan ticket `feat-fewer-relay-round-trips-per-write-and-read`; question 1 (stream reuse) is implement ticket `a-request-reuses-a-pre-negotiated-stream`, which halves the cost of each request but not their number.

## Where the four requests come from

Measured by the reporter on 1.12.1 (Node, two-member group, public relay): a one-row insert is 4 `/cluster` requests from the coordinating machine to the other member — pend ~290 ms (2 requests), commit ~300 ms (2, `path=one-round`). On phones the same write took 3.0–3.6 s per half.

A write is two consensus operations, each run by `ClusterCoordinator.executeClusterTransaction` (`packages/db-p2p/src/repo/cluster-coordinator.ts`):

- the **pend** operation (reserve the blocks, store the transforms), then
- the **commit** operation (promote them at the action's revision), which `NetworkTransactor.commit` (`packages/db-core/src/transactor/network-transactor.ts`) sends in one round when one coordinator covers every block (`commitInOneRound`).

Each operation has a **promise round** (members vote approve/reject/conflict/held on the record; the coordinator's own member pre-votes in process, `prevoteLocalPromise`) and a **commit round** (members sign the commit over the promise map; the coordinator pre-signs, `presignLocalCommit`, so in a cohort of three or fewer a remote member reaches a commit majority and applies on receipt). The third call per operation — the merged-record broadcast — is already skipped in a healthy small cohort (`broadcastMergedRecord` sends only to members that still need it). So 2 calls × 2 operations = 4 is today's floor for this shape, and the 1.11.0 changes (`commitInOneRound`, the pre-signed commit) are already in it.

## Candidate directions (none chosen yet)

The plan's job is to pick one (or decline all), with a correctness argument, and turn it into implement ticket(s). Starting points, with the first obstacle each meets:

1. **Piggyback the commit operation's promise round on the pend operation's commit round.** When the pend's commit round reaches a remote member, the next message that member will receive is the commit operation's promise round. Sending both in one request (pend commit-round record, then the commit-op record, processed in that order by the member) would make a write 3 calls. Obstacles: the commit operation is a separate `ITransactor.commit` call from db-core, issued only after `pend` returns, and its record is built from the pend's outcome (block digests, durability); the member's promise vote on the commit op reads the pended transform (`validateCommitOperations` → `StorageRepo.previewCommitDigest`), so it must run after the pend applied on that member; and a pend that is refused at apply (reported through `applyOutcomes`) must not leave a commit-op promise behind.
2. **Fold the promise and commit rounds into one call when the coordinator's member plus one remote member is the whole cohort** (two members). The remote would answer with its promise and its commit signature together. Obstacle: a commit signature covers the promise map (the commit hash's preimage includes the promises), so the coordinator cannot pre-sign its commit before it has the remote's promise, and the remote then holds one commit of the two a strict majority needs — it cannot apply on receipt, and the broadcast call comes back. Needs either a change to what a commit signature covers (a signed-layout change, which `BlockCommitProof` verification and stored proofs depend on — `packages/db-p2p/src/cluster/commit-proof.ts`, Theorem 14) or an argument that a member may apply on its own commit plus a promise super-majority in a two-member cohort.
3. **Fold pend and commit into one consensus operation** for a two-member cohort. Largest saving (4 → 2) and largest blast radius: the pend's durable reservation is what the race arbiter, the `held` vote, slot holds (Theorem 9) and the torn-action recovery (`Collection.completeOwnEntry`) are built on.

Whatever is chosen must be argued against `docs/correctness.md`: Theorem 1 (race resolution counts approve promise votes first — a round that changes when votes become visible changes who wins a collision), Theorem 6 (durability: the strict-majority storage acknowledgement and `applyOutcomes`), Theorem 9 (progress under contention), Theorem 14 (durable commit proofs: promise super-majority and commit majority, each signed over specific hashes), and the reconcile ordering in *A behind member actively reconciles* in `docs/internals.md`. Mixed-version cohorts must keep working (a member on the previous build receives whatever the new coordinator sends).

If the specification turns out to be silent on a question this raises — for example whether a two-member cohort may apply on fewer commit signatures than a strict majority — route that question to `blocked/` with proposed text rather than deciding it inside an implement ticket.

## Measure first

Land `a-request-reuses-a-pre-negotiated-stream` first and ask the reporter to re-measure (`message-latency.mjs` from the issue): if each request drops to one relay round trip, a write is 4 round trips, and the value of 4 → 3 must be weighed against consensus risk with that number in hand.
