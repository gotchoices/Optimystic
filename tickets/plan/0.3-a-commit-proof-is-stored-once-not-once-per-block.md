# A commit proof is stored once, not once per block

Reported as GitHub #60 (Sereus; optimystic 1.27.0, file storage, solo node).

## What happens

A commit's `BlockCommitProof` carries the commit `RepoMessage` verbatim, whose commit operation lists every block id and declared digest. `StorageRepo.persistProofIfContentMatches` saves that same proof under each committed block's `(blockId, rev)` key (`IBlockStorage.saveBlockProof` → `KvRawStorage.saveBlockProof` → `RawStoreDriver.putProof`; `proofs/<rev>.json` per block on `FileRawStorage`). Bytes retained per commit therefore grow as blocks-touched squared. This is the revisit condition of the existing `NOTE:` on `persistProofIfContentMatches` ("if per-coordinator batches ever grow large, store the proof once under its `messageHash` and key each revision to a pointer"), and it has tripped.

Reporter's measurements (5 commits × 500 rows, one table): with 1, 4 and 8 secondary indexes, proofs were 1.4×, 5.7× and 11.7× the block data (816 proof files for 7 distinct proofs at 4 indexes). On a real load — 18k transactions and 38k entries over tables with 16 secondary indexes, committed in ~1 MiB batches — the store reached 7.0 GB after 10 of 15 commits, 94% proofs, one 528 KB proof stored 3,383 times. The same data in another Quereus store is about 25 MB. Not re-measured here; the layout follows from the code.

## Requirement

- A commit proof is persisted once per node, keyed by something that identifies the consensus record (its `messageHash`), and each block revision that has one records a reference to it. Reading a block's proof (`servableProof`, repair, push, certified-claim selection) returns the same artifact it does today.
- The rules that decide whether a revision gets a proof are unchanged: a member persists one only when its own materialization matches the declared digest, back-fill onto an already-held revision keeps its checks, and an unverified proof from the restore wire is never stored.
- A proof stays as long as any revision referencing it does; there is no revision-delete site today, so no reference counting is needed until there is one (say so at the site).
- Stores written by earlier releases still read: `packages/upgrade-check` fixtures carry per-block proofs, so either read both layouts or document an upgrade step there.
- Every `RawStoreDriver` backend (memory, file, IndexedDB, React Native, NativeScript) and the conformance suite follow the new shape.

## Questions the issue also asks, to answer in the plan

- **Wire.** A replication push carries `blockProofs` keyed by block, so pushing N blocks of one commit sends N copies; a repair archive carries one per block fetched. Decide whether the push deduplicates by `messageHash`, and whether the proof can be cut to what a single block's claim needs without breaking signature verification (the signatures cover the whole message, so probably not).
- **Retention.** Whether `revs/` and `proofs/` are kept indefinitely or compacted is a separate question; answer it in the docs rather than here, and file it if it needs work.
