# The crypto backend takes native ECDSA verify

Requested in GitHub #59 (VoteTorrent; `@optimystic/quereus-plugin-crypto` 1.26.0 and 1.27.0).

## Current state

`CryptoBackend` has optional `sha256`, `sha512`, `ed25519Sign` and `ed25519Verify`; `setCryptoBackend` self-checks each supplied member and installs it. `verify(..., 'p256')` and `verify(..., 'secp256k1')` always call `p256.verify` / `secp256k1.verify` from `@noble/curves` with its defaults (verified by reading `verify` in `crypto.ts`). `sign` uses `{ lowS: true }` on both curves.

Measured by the reporter on a Pixel 8 emulator under Hermes: `p256.verify` 47 ms (noble) against 0.13 ms (OpenSSL via react-native-quick-crypto); `secp256k1.verify` 29 ms against 0.24 ms. Their schema `CHECK` constraints call `verify` on every replicated signed row, about 10 s of JS-thread time per authority device per election; an app cannot route around it because the call is inside SQL.

## Requirement

Two optional members, `p256Verify(signature, message, publicKey): boolean` and `secp256k1Verify(...)`, with exactly noble's default verify semantics: 64-byte compact `r || s` signature (not DER), the message hashed with SHA-256 by the member, a 33-byte compressed or 65-byte uncompressed SEC 1 public key, high-S signatures rejected, `r` or `s` of 0 or at least the curve order rejected; false or a throw for an invalid input. `verify` dispatches to the member when installed, as it does for `ed25519Verify`. No native signing members: OpenSSL's ECDSA uses a random nonce unless asked for RFC 6979, so a native sign would fail a byte-identical self-check, and the reporter does not need it.

## The self-check is the important part

`verify` runs inside `CHECK` constraints on replicated rows, so every machine must reach the same answer, and most machines run noble. OpenSSL accepts high-S signatures where noble rejects them, so a naive native member would accept a signature with `s` flipped to `n − s` on phones only, and replicas would diverge. Beyond what `checkEd25519Verify` checks (accept a valid signature, reject one over a different message, offset views), each new member's self-check must reject a high-S copy of a valid signature, reject a signature with `r = 0`, and accept the valid case with both compressed and uncompressed keys. The issue carries a reference member over Node's `crypto` that agrees with noble on valid, tampered, high-S, `r = 0` and `r = n` signatures with both key forms; it is a good basis for the test that pins the self-check, run against Node's OpenSSL.
