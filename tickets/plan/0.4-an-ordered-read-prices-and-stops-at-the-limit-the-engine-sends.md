## What changed upstream

Quereus 5.3.0 (`sort-absorb-sees-constant-limit`) and 5.4.0 (`sort-absorb-runtime-limit-choice`) send `request.limit` / `request.offset` beside `requiredOrdering` for a LIMIT the user wrote above an ORDER BY:

- A constant `limit 20 offset 40` arrives as `limit: 20, offset: 40`.
- A placeholder `limit ?` arrives as the largest bound the engine will ever run that plan under. The engine keeps the ordered plan the module returned and runs it only on executions whose actual `limit + offset` is at most that bound, falling back to scan-then-sort above it.
- The field is a licence, not a hint: when present, nothing between the scan and the LIMIT can discard a row, so a module may both price against it and stop after `limit + offset` rows — but only on a candidate that provides the requested ordering and claimed every filter (Quereus `docs/module-authoring.md`).

## What this repository assumes today

Read the citations of Quereus backlog `feat-sort-absorb-blind-to-limit-general` (now complete upstream): the comment on `orderedWalkCandidate`, the comment above `WALK_ROWS_BEFORE_SCAN`, and *Pricing* / *Finishing by scanning* in `docs/internals.md`.

- `orderedWalkCandidate` already reads `request.limit` when present (`wanted = min(rows, limit + offset)`), so a limited walk is now priced as a page. An unlimited one is priced at `seekCost + tableRowCount`, which was chosen to beat a scan and sort because the limit could never be seen. Now an unlimited request really is unlimited: the walk fetches each row with its own descent of the main tree (about five times a scan's cost per row), so a scan and sort should win it on cost rather than the walk winning and switching to a scan after 256 entries.
- `verifiedIndexRows` / `restOfWalk` switch to a table scan after `WALK_ROWS_BEFORE_SCAN` entries because the walk could not know how many rows were wanted. With a limit present the walk can stop at `limit + offset` instead, when the candidate claimed every filter. A walk claims none, so the stop applies only to a walk with no filters, or to a range seek whose filters it fully claimed.

## Questions the plan must settle

1. Price an unlimited ordered walk honestly (per-row descent cost) so scan-and-sort wins it, or keep today's pricing plus the scan switch? Measure both on the 2,000 and 5,000-row shapes `docs/internals.md` already quotes, at `transactor='test'`.
2. Keep `WALK_ROWS_BEFORE_SCAN` at all? It still guards a walk under a residual filter (unknown selectivity) and a range of assumed selectivity. Decide whether it stays only for those, and rewrite its `NOTE:` revisit condition.
3. For `limit ?`, the bound is a maximum: price against it, and confirm the engine's per-execution fallback means truncation at the bound never underproduces.
4. Update every `feat-sort-absorb-blind-to-limit-general` citation and the two `docs/internals.md` paragraphs to the new reality.

Tests: the existing differential specs (`index-ordered-walk.spec.ts`, `index-range-seek.spec.ts`, `ordering-claim-guard.spec.ts`) already compare against a memory table; add only a plan-shape case per pricing rule that changes (limited walk chosen; unlimited ordered read sorted by the engine, if that is the decision).
