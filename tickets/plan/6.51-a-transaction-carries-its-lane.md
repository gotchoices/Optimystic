# A transaction carries its lane

The second foundation of the partition-healing program (see the Stage 1 implement tickets (`the-hlc-clock-and-its-persistence-port`, `every-log-entry-and-transaction-carries-its-hlc`, `a-node-observes-the-hlcs-it-reads-and-stores`) for the first and backlog `feat-replay-mode-collections-merge-divergent-histories` for the stage that consumes both). This pass designs the vocabulary and the classification; it changes no admission rule.

## The idea, and the two sources that shaped it

The general result (Bailis et al., I-confluence; Li et al., RedBlue consistency) is that an operation can be committed without coordination and still converge if and only if the invariants it is responsible for are preserved under merge. Append-only sets, counters without bounds and last-writer-wins fields are; uniqueness, foreign keys and non-negative balances are not. So "convergent" versus "serializable" is a property of an **operation**, never of a system, and Optimystic should state it rather than infer it from behaviour. The old `6.5-partition-healing` ticket's 2026-09-14 arm asked for a first-class declaration on the collection. The maintainer's arm of the same day on `feat-long-lived-pend-completes-as-members-appear` refined that: Quereus can see, per statement, whether a write touches a constrained column, whether its write depends on a read, and whether a merge is defined for the touched fields, so the lane can be classified per transaction by the engine and carried inside the signed transaction, where every validator applies the same rule and one that disagrees refuses the pend rather than reclassifying.

Both are right, at two levels:

- **A collection profile**, declared, part of the schema hash: `strong` (today's behaviour, and the default) or `replay-permitted`. The profile is the application's ceiling. A `strong` collection never merges whatever a statement looks like; it is the choice for data whose invariants nobody has classified.
- **A per-transaction classification**, computed by the engine within a `replay-permitted` collection: `serializable` (quorum lane) or `convergent` (may commit locally and merge). It travels in the signed transaction, and on the log entry for a bare sync, which has no transaction.

The names follow `docs/crdt-sync.md` §Stage 5 (`strong` / `replay`) for the profile; the arms used "serializable" and "convergent" for the per-transaction classification, which this ticket keeps. Define both on first use wherever they appear.

## The classification rule

From the maintainer's arm, to be made precise here: a transaction is `convergent` when every statement in it (a) touches no column under a uniqueness, foreign-key or multi-row check constraint, (b) has an empty read set (a blind write; a hash-keyed insert qualifies, a `set n = n + 1` does not, because the increment reads), and (c) writes only fields for which the collection defines a merge. Anything else is `serializable`. A transaction over several collections takes the stricter lane of any of them.

Idempotence is not the criterion. Setting a column to a value is idempotent and still needs a tie-break under concurrency; an increment is not idempotent and merges fine. Note this where the rule is defined, because it is the mistake a later reader will make.

The engine's existing write description (`write-description.ts`) already answers (a) and (b) for the offline-sync outlook (`judgeTransaction` asks whether a write's outcome depends on state other writers can change). Reuse it; do not build a second analysis.

## The merge seam

`Collection.filterConflict` is the hook `docs/partition-healing.md` §How Optimystic Surfaces This names as the surface for reconciliation. Today it is untyped as to intent, pairwise, runs at client retry time, and nothing installs one (`Tree` and `Diary` install none; the `NOTE:` at `Collection.unstage` records that a hook answering a replacement instance would need a per-call token). This pass gives it a declared role: the convergent lane's merge rule for a collection, the thing clause (c) of the classification asks about. The serializable lane's rule is the tree entry guards (`TreeEntryGuard`), which already re-make every conflict decision deterministically on replay. Decide the typed shape of a merge declaration (per collection, per field for a tree entry, or both), whether `Diary.append` is declared convergent out of the box (append-only is I-confluent; it is the first natural case), and whether a table tag such as `"optimystic.merge" = 'last-writer-wins'` on a column is how SQL declares one.

## What changes observably in this stage

Only reporting. The `commit:solo-cohort` line and `pend:solo-refused` / `commit:solo-refused` name the lane of the write, so an operator can tell a lone write the merge stage will handle from one it will not. The offline queue's `queued` status may carry it beside the outlook. No admission rule moves: the solo path and the offline queue keep today's behaviour, and the replay-mode stage owns admission per lane.

## Decisions taken in this pass, open for the human to edit

- **Default profile is `strong`.** Every existing collection and every table that declares nothing behaves exactly as today. Sereus opts tables in per table. The alternative, defaulting to `replay-permitted`, would silently change what every application gets.
- **The classification is the engine's, validated by peers, never inferred by a member from the transforms.** A member that disagrees refuses the pend (a reject with a reason, under the same marker rules as the validity votes).
- **The catalog collection (`tree://optimystic/schema`) is `strong`.** Its fork-safety today rests on every machine writing byte-identical content (the `NOTE:` near `SchemaManager`'s record construction); that invariant stays, and the catalog is never classified convergent.

## Edge cases & interactions

- A transaction spanning a `strong` collection and a `replay-permitted` one is `serializable`; by the stricter-lane rule, verified by the pure classification test.
- `alter table … set tags` changing a profile while entries for that table are queued in offline mode: treat as a storage-shape change and refuse while entries are queued (`OfflineMode.assertNoQueuedEntries`), since a queued entry's classification was computed under the old profile. By inspection.
- A statement the engine cannot describe (no write scope offered) is `serializable`. Fail safe.
- A bare `Collection.sync` on a `Tree` with no merge declared is `serializable`; on a `Diary` declared convergent it is `convergent`. The entry records it.
- A peer on an older build ignores the field; nothing consumes it for admission yet, so mixed versions are unaffected in this stage.
- The long-lived-pend ticket's late signer and the replay-mode stage both read the same field; it must be inside the signed bytes of the transaction and inside the log entry, never a side channel.

## Tests that pay for themselves

One table-driven test of the pure classification rule over write descriptions (constrained column; read-dependent write; blind hash-keyed insert with a merge; mixed collections). Nothing for the tag plumbing or the log line.
