# SQL columns hold blob references

Last of four parts of backlog `feat-sql-columns-hold-blob-references`; this slug means all of it has landed. After `feat-blob-pins-follow-sql-commits`, an online commit pins, announces and unpins the references it adds, and pins a queued transaction's references under labels that name the transaction and the scope (`transactionReferencePinLabel` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts`). This part covers what happens after the commit call returns: a queued transaction settling, a restart that lost a release (the process stopped between a commit landing and its pins being released, or a release was kept because announce failed), and `unstaged` pins nobody referenced (docs/blobs.md §SQL, "A put outside a transaction", "Pins follow the transaction").

The blob records are the durable record of every pin, and a transaction's pins name its id and each reference's scope, so nothing here reads the offline journal's segments or changes `JournalEntryRecord` (`packages/db-core/src/offline/journal.ts`). This departs from the backlog, which proposed reading a queued entry's references back off its reference-tree segments.

## Additions to `SqlBlobPins` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pins.ts`)

```ts
interface SqlBlobPinsDeps {
	// … from feat-blob-pins-follow-sql-commits, plus:
	/** Every backend whose transactor key the factory has seen this process (CollectionFactory.knownBlobBackends: resolves each). */
	knownBackends(): Promise<BlobBackend[]>;
	/** True for a transaction this process must not settle yet: the bridge's active transaction, or one the offline mode lists with a non-terminal status (queued, submitting, partially-committed, or journaled and not yet restored). */
	isLive(transactionId: string): boolean;
	/** False until it is safe to judge a transaction settled from its absence: a configured journal's restore has completed at least one pass this process. True with no journal. */
	reconcileReady(): boolean;
	/** References the open transaction's ledger adds (`addedReferences`), whose `unstaged` pins must not expire. */
	openReferences(): ReadonlySet<BlobRef>;
	unstagedHoldingMs: number;
	now?: () => number;
}

/** A queued transaction settled. 'all' for `committed`; a failed one's `committedCollections` (possibly empty). Never throws. */
settleQueued(transactionId: string, committed: 'all' | ReadonlySet<string>): Promise<void>;
/** Settle every transaction pin whose transaction is not live, from committed state. Never throws. No-op until reconcileReady(). */
reconcile(): Promise<void>;
/** Unpin every `unstaged` pin older than the holding period, except on a reference the open transaction adds. Never throws. */
sweepUnstaged(now?: number): Promise<void>;
/** Run the first sweep and reconcile for a backend just resolved, and start the sweep timer. */
backendResolved(backend: BlobBackend): void;
/** Stop the timer and wait for the work chain. */
dispose(): Promise<void>;
```

All four operations run on one promise chain per `SqlBlobPins`, the way `OfflineRestore` chains its passes (`chained` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-restore.ts`), so a settle and a reconcile never handle one transaction's pins at once. Each is idempotent: announcing twice and unpinning a missing pin are harmless.

**`settleQueued`.** For each known backend, `listPins(transactionPinPrefix(id))`:
- a reference pin whose scope is committed: confirm the scope is registered (below), `announce(ref, scope)`, `unpin`; on failure keep the pin and log `blob:pin-kept`, as an online commit does;
- a reference pin whose scope is not committed (the transaction failed, was discarded, or failed in a cascade): `unpin`, so the writer's sweep removes the bytes (docs/blobs.md §Committing a reference, "A transaction that rolls back");
- a `put` pin: `unpin`.

Hooked in `OfflineMode.onQueueStatus` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`): for a `committed` status `void pins.settleQueued(id, 'all')`; for a `failed` status `void pins.settleQueued(id, new Set(status.committedCollections ?? []))`. A deferred record the restore discards reaches the same method, since its settled status goes through `onQueueStatus` (`emitSettled`). New `OfflineMode.attachBlobPins(pins)`, set once by `register`.

**`reconcile`.** For each known backend, `listPins(TRANSACTION_PIN_PREFIX)`, grouped by transaction id; skip every id `isLive` answers true for. For the rest:
- `put` pins: `unpin`.
- reference pins, grouped by scope: read the scope's reference tree with the db-core reader (`listed(refs)`, refs sorted ascending, over `backend.transactor` with `Tree.open` semantics, from `feat-committed-rows-register-the-blobs-they-reference`). Certain and listed: confirm registration, announce, unpin. Certain and not listed: unpin (the transaction never committed that reference, or a later one removed it, and a removed reference is not the writer's to keep). Uncertain: keep, log `blob:reconcile-uncertain scope=… refs=…`, and try again on the next trigger.

**Registration before announce, without resurrecting a dropped table.** `settleQueued` and `reconcile` call `BlobScopeRegistration.ensure` only for a scope a table in this process still backs (`TransactionBridge.tablesOf(scope)` is non-empty); otherwise they call a new check-only `BlobScopeRegistration.isRegistered(network, scope): Promise<boolean | undefined>` (enumerate; `undefined` when uncertain): registered → announce; not registered → unpin (the table was dropped, so its references are unreferenced by design); uncertain → keep. Without this, a reconcile running after another machine dropped the table would register the dropped tree again and keep its blobs for ever.

**Triggers for `reconcile`.**
- After every `OfflineMode.restore()` (and so after `plugin.hydrate`, which calls it). `reconcileReady` turns true when the first restore pass completes (`OfflineRestore.run` resolved once); with no journal there is nothing to restore and it is true from the start. Before that, an entry still on disk would look settled, its reference not yet listed, and its pin would be dropped while the entry later commits.
- On every reachability wake (`OfflineMode.onGateChange`), after its own work, once no transaction is open (`bridge.whenTransactionIdle()`), as the restore retry there does.
- When a backend first resolves in this process (`backendResolved`, from `CollectionFactory.onBlobBackendResolved`). With `plugin.hydrate` resolving the default network's backend after its restore, a host that calls `hydrate` gets the start-of-process reconcile on its default network; a table on another network gets it when that table is first initialized.

Add a `NOTE:` at `reconcile`: "reads one reference tree per scope with a kept pin and lists every transaction pin on each trigger; if a machine ever keeps many pins across wakes, remember the uncertain scopes and retry only those".

## The `unstaged` holding period

- Plugin-level option `blob_unstaged_holding_ms` (a number of milliseconds; default `86_400_000`, 24 hours), parsed beside `link_round_trip_ms` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` and refused the same way when it is not a positive number.
- `sweepUnstaged(now)`: for each known backend, `listPins(UNSTAGED_PIN_PREFIX)`; unpin each pin whose `putAtMs` is more than the holding period before `now`, unless `openReferences()` holds its reference (a long-open transaction about to commit it). A label whose time does not parse is left alone and logged once.
- When: in `backendResolved` (so at start, per backend), and on one timer while any backend is resolved, every `min(holdingMs / 4, 3_600_000)` ms, created with `setInterval` and released with `unref` when the runtime offers it (a cross-platform guard, as elsewhere in the repo); cleared in `dispose`, which `plugin.dispose()` awaits before `offline.dispose()`.
- Log `blob:unstaged-expired ref=… putAt=…`.
- `register` exposes the pins as `blobPins` beside `collectionFactory` and `txnBridge` ("internal components for testing and advanced usage"), which is how a test passes its own `now`.

## Edge cases & interactions

- **Queued, then committed.** Reference pins until the `committed` status, then announced and released; the `unstaged` pin was already dropped when the entry was queued. Test.
- **Queued, then discarded or failed (including a cascade failure).** Every pin of the transaction released; the bytes go with the next sweep. Test (discard).
- **Partial commit of a queued entry, then a permanent failure.** References into the committed collections are announced; the rest released. Inspection of `settleQueued`'s arms.
- **A restart while the entry is queued.** The restore puts the entry back; `isLive` answers true; its pins stay until it settles in this process. Test.
- **A restart after the commit landed but before its release.** The scope's tree lists the reference, certainly: announced and released. Test.
- **A restart after a commit that never landed** (the process died after pinning, before sending). The tree certainly does not list it: released. Test.
- **Cohort unreachable at reconcile.** Uncertain read: kept, retried on the next wake. Test, with a delegating transactor in the spec that answers the scope tree's blocks `unavailable` while armed.
- **A table dropped on another machine between commit and reconcile.** Check-only registration: not registered → released; never re-registered. Inspection.
- **An `unstaged` put referenced by a transaction open past the holding period.** Not expired while that transaction is open; moved to a reference pin when its commit starts. Test.
- **A put whose transaction ended before the put resolved** (a stray `put` pin). Released by the next reconcile. Inspection.
- **A table on another network.** Pins, announce and reconciliation run on the backend of the table's own transactor key; `plugin.blobs` is only the default network's. A reference staged into a table whose network does not hold the bytes commits, announces (nobody holds it) and reads as not held. Inspection.
- **No journal.** Queued entries do not survive a restart; at the next start their pins are unlisted and released. Inspection.
- **Concurrency with a commit.** A commit's pins belong to the active transaction, which `isLive` excludes; settles and reconciles share one chain. Inspection.

## Tests

`packages/quereus-plugin-optimystic/test/blob-pins-offline.spec.ts`, on the `local` transactor over one `MemoryRawStorage` and one `blobStorageFactory` result (a `MemoryPieceStore` and `MemoryKVStore` shared by successive plugin instances, which is how the spec simulates a restart), with an offline journal on a shared key-value store as `packages/quereus-plugin-optimystic/test/offline-restore.spec.ts` sets one up. Read pins through the backend's `pinsOf` and `parsePinLabel`.

- Queued then committed: `offline.enter()`; put; insert; commit; the reference has one reference pin and no `unstaged` pin; `offline.exit()`; `whenDrained()`; no transaction pin remains and `stat` reports durability `local`.
- Queued then discarded: the drain held with `packages/quereus-plugin-optimystic/test/commit-gate.ts`; `discard(id)`; no pin remains.
- Restart while queued: the drain held, the process "restarted" (new `Database` and plugin over the same stores, `hydrate`); the entry is restored and its reference pin is still there; released, it commits and the pin goes.
- Restart reconciliation, three arms, each by writing a transaction reference pin directly on the backend for a transaction id that is neither open nor queued, then `hydrate` in a fresh plugin: the scope's tree lists the reference (a row committed normally beforehand) → announced and released; the tree does not list it → released; the tree is unreadable (the spec's delegating transactor answers its blocks `unavailable`) → kept, and released after the failure is disarmed and `offline.restore()` runs again.
- Holding period: a put outside any transaction is kept by `blobPins.sweepUnstaged(putTime + holding - 1)` and released by `sweepUnstaged(putTime + holding + 1)`; a second put whose reference an open transaction has inserted survives the later sweep and is committed normally.
