GitHub [#55](https://github.com/gotchoices/Optimystic/issues/55), a follow-up to #49, whose completed ticket is `0.12-cohort-gossip-is-verified-once-off-the-synchronous-path`.

## What the reporter measured

Two parties on a two-member group, Galaxy S21 and Galaxy S7, Hermes CPU profiles, db-p2p 1.24.0:

- S21, 60 s idle with the partner online: 823 ms of JavaScript busy, of which 306 ms (37%) is `handleRegisterFrame → onRenew → handleRenew → … → verifyPeerSig`.
- S21, a 4 s window while a screen loads: 2.7 s busy, of which 658 ms (24%) is `handleRegister → runGuards → verifyPeerSig`.

Node 24 bench over the same signatures: `verifyPeerSig` 2.712 ms per check, `verifyPeerSigAsync` 0.149 ms, 18.2 times. The bench script is in the issue. #49 measured noble's verify at about 40 ms per frame on the S7.

## The ask

Check register and renew signatures with `verifyPeerSigAsync`, as #49 did for gossip. The issue offers two shapes: verify in the host's inbound frame handler before the frame reaches the member engine, or make the engine's two ports async. The planner chooses and records why. The first is what #49 did and keeps db-core's engine synchronous; the question to settle is whether the engine's synchronous decisions stay correct when the frame has waited on an await first, since another frame can be handled during it.

## Things to weigh

- **What a phone actually gains.** `verifyPeerSigAsync`'s own doc says a phone verifies natively only if a WebCrypto Ed25519 is present when the module loads, and otherwise gets noble at the same cost. The Node bench does not show the Hermes result, and nothing in this repository runs Hermes. If the runtime has no native verifier, this change saves nothing there. Say so in the handoff and in the release note, and name what a host must provide. If moving off the synchronous path is not enough on its own, say what else would cut the count: for example whether a plain renewal ping needs a signature check at all (read the comment at `verifyParticipantSig` in `renewal.ts`, which says plain pings are not gated, against the reporter's profile, which shows a check on the renew path).
- **Acceptance difference.** The async verifier is strict RFC 8032 and noble is ZIP215. Every signer here produces RFC 8032, as the #49 ticket records, but a check here that refuses what a synchronous check elsewhere would accept must not disagree about a frame already accepted.
- **Every call site.** `runGuards`, `handleProbe`, the single renew path and the `renew-batch` path. A site left on the synchronous path keeps the cost; a frame checked twice pays it twice. Check each frame once.
- **Order of checks.** Anything cheap that can drop a frame before the signature should still run first.
- **The synchronous ports that stay.** Bootstrap evidence, parent references and `verifyCollectedMultisig` stay as they are unless the plan finds they are on an idle path. List any that are.

## Done means

Inbound register and renew frames do not call `verifyPeerSig` on a node with a key, shown by a test that fails if one does. A bad signature is still refused on every path, each with a test. The issue's bench is re-run or an equivalent measurement is recorded in the ticket, stating that it is Node and not Hermes. `docs/cohort-topic.md` and the module comment in `peer-sig.ts` are updated, and the reply owed to #55 is noted in the handoff.
