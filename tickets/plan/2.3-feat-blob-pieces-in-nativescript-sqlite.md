# Blob pieces in the NativeScript SQLite database

`feat-a-node-stores-blob-pieces` defines `IPieceStore` (in `packages/db-p2p/src/blob/`), the store for the immutable pieces a blob is cut into (docs/blobs.md §The local store), with an in-memory and a filesystem implementation and a conformance suite every implementation runs. This ticket adds `SqlitePieceStore` to `@optimystic/db-p2p-storage-ns`: one table in the database `openOptimysticNSDb` already opens, sharing the handle with `SqliteRawStorage`, `SqliteKVStore` and the identity helper. It is not a `RawStoreDriver` store and does not go through `SqliteBatchBackend`'s write group: a piece is raw bytes written by one autocommit statement, and needs no cross-key atomicity.

The interface, as the prerequisite defines it (`PieceId` comes from `@optimystic/db-core`, `IPieceStore` from `@optimystic/db-p2p`):

```ts
interface IPieceStore {
	has(id: PieceId): Promise<boolean>;
	get(id: PieceId): Promise<Uint8Array | undefined>;
	put(id: PieceId, bytes: Uint8Array): Promise<void>;   // caller has verified the bytes; a put of a present id writes nothing
	delete(id: PieceId): Promise<void>;
	list(): AsyncIterable<PieceId>;
	bytesUsed(): Promise<number>;
	flush(): Promise<void>;
	readonly durability: StoreDurability;
	close?(): Promise<void>;
}
```

## Schema

Append to `SCHEMA_SQL` in `packages/db-p2p-storage-ns/src/db.ts`, in the package's uppercase style (the `NOTE:` there explains why):

```sql
CREATE TABLE IF NOT EXISTS pieces (
	id    TEXT PRIMARY KEY,
	bytes BLOB NOT NULL
);
```

- `id` is the `PieceId` string as given (a canonical CIDv1 base32 string, ASCII).
- An ordinary rowid table, not `WITHOUT ROWID`: SQLite's own guidance is that `WITHOUT ROWID` suits small rows, and a piece row is up to 1 MiB.
- `DEFAULT_DB_VERSION` stays 1 and no migration step is added: `applySchema` runs on every open and `CREATE TABLE IF NOT EXISTS` gives a database created by an older build the empty table on its next open, touching nothing else. Nothing reads `user_version` today.
- Extend the schema doc comment's bullet list with `pieces`.

## `SqlitePieceStore`

New module `packages/db-p2p-storage-ns/src/sqlite-piece-store.ts`, exported from `src/index.ts` beside `SqliteKVStore`.

```ts
export class SqlitePieceStore implements IPieceStore {
	readonly durability: StoreDurability = 'power-loss';
	constructor(db: SqliteDb);
	/** The same identity `SqliteBatchBackend` reports over this handle: `identityForHandle('sqlite-handle', db)`. */
	storeIdentity(): StoreIdentity;
	has(id: PieceId): Promise<boolean>;
	get(id: PieceId): Promise<Uint8Array | undefined>;
	put(id: PieceId, bytes: Uint8Array): Promise<void>;
	delete(id: PieceId): Promise<void>;
	list(): AsyncIterable<PieceId>;
	bytesUsed(): Promise<number>;
	flush(): Promise<void>;
}
```

Statements, each prepared once in the constructor through `db.prepare` (writes then go through the connection mutex, reads do not, as for `SqliteKVStore`):

| Member | Statement |
|---|---|
| `has` | `SELECT 1 AS present FROM pieces WHERE id = ?` |
| `get` | `SELECT bytes FROM pieces WHERE id = ?`, returning the row's `bytes` as the `Uint8Array` the driver returns |
| `put` | `INSERT OR IGNORE INTO pieces (id, bytes) VALUES (?, ?)` — a present id writes nothing, which is the interface's rule, in one statement with no read first |
| `delete` | `DELETE FROM pieces WHERE id = ?` |
| `list` | `SELECT id FROM pieces WHERE id > ? ORDER BY id LIMIT ?`, starting from `''`, `PIECE_LIST_PAGE = 1000` ids a page, each page drained by `all` before yielding and the next page keyed after the last id yielded |
| `bytesUsed` | `SELECT coalesce(sum(length(bytes)), 0) AS used FROM pieces`; SQLite answers `length()` of a BLOB from the record header, without reading the content |

- **Paged listing.** `list` pages rather than draining the whole table as `SqliteBatchBackend.listBlockIds` does, because a node can hold hundreds of thousands of pieces and the `NOTE:` on `NSPluginStatement.all` in `ns-opener.ts` says a result over 512 KiB crosses NativeScript 8's JNI bridge through a buffer holding a scarce global reference. A page of 1000 ids of about 60 characters stays far below that. Keyset paging (`id > last`) rather than `OFFSET`, so a page costs one index seek whatever the position.
- **Exact bytes on put.** Bind `bytes` when it spans its whole `ArrayBuffer` (`byteOffset === 0` and `byteLength === buffer.byteLength`), otherwise a copy (`bytes.slice()`), through a private `wholeBufferBytes` function. The plugin's binding of a typed array is native code this suite never runs, and a binding that sends the view's whole buffer would store bytes that are not the piece. The builder normally hands whole buffers, so the copy is rare.
- **Durability and flush.** Writes are autocommit statements: each survives a crash of this process once it resolves, and the write-ahead log keeps them in order. `flush()` makes every write resolved before it survive a power cut by one synced commit (`syncSqliteDb`), and only when something was written since the last flush; otherwise it resolves at once. That is exactly `SqliteKVStore.flush`, so extract the bookkeeping both use into `sqlite-sync.ts`:

```ts
/** Tracks whether a store wrote since its last flush, and latches the store failed when a sync fails. */
export class PendingSqliteSync {
	constructor(db: SqliteDb);
	/** Throws `StoreFailedError` once a sync has failed. Writes call it first. */
	throwIfFailed(): void;
	/** A write resolved; the next flush must sync. */
	noteWrite(): void;
	/** One synced commit when a write resolved since the last flush, otherwise nothing; a failure latches and throws `StoreFailedError`. */
	flush(): Promise<void>;
}
```

`SqliteKVStore` is rewritten over it with no change in behaviour (its `dirty` and `fault` fields and `throwIfFailed` go; the existing "flush() syncs once when something was written" test keeps passing unchanged). `SqlitePieceStore` uses it the same way: `put` and `delete` call `throwIfFailed`, run, then `noteWrite`; reads never throw for a latched store.

- **Handle ownership.** No `close`: the handle is shared, and the host closes it after the node has stopped and the block store has closed, as the README already says for the other stores. The store holds nothing in memory to release.
- **`storeIdentity`.** `feat-a-node-stores-blob-pieces` decides whether to add a piece store's bytes to the node's storage figure ("counted once", docs/blobs.md §The local store). `SqliteBatchBackend.approximateBytesUsed` multiplies `page_count` by `page_size`, which already includes the `pieces` table, so this store must be recognised as inside it. The expected form of that rule is equality of store identities, so `storeIdentity()` returns the identity the block backend computes over the same handle. If the prerequisite states the rule through another member, implement that member with this meaning instead, and drop `storeIdentity`.
- **Logging.** `bytesUsed` catches a failed query, logs it under `createLogger('storage:pieces')` (namespace `optimystic:db-p2p-storage-ns:storage:pieces`) and answers 0, as `approximateBytesUsed` does; nothing else logs.

## The 512 KiB JNI note

Add one sentence to the `NOTE:` on `NSPluginStatement.all` in `packages/db-p2p-storage-ns/src/ns-opener.ts`: `SqlitePieceStore.get` reads one piece per call, a piece this design writes is 256 KiB, and only a piece from a blob another IPFS tool made can exceed 512 KiB (the reader admits up to 1 MiB), so a node reading thousands of such pieces between garbage collections is the case that note's remedy would have to cover.

## Edge cases & interactions

- **A database an older build created.** It lacks `pieces`; the next open adds it empty and every block, proof, key-value and identity row reads as before. Test (below).
- **An older build opening this database.** It ignores the extra table; `CREATE TABLE IF NOT EXISTS` never drops one. Inspection.
- **A 1 MiB piece.** Round-trips under the `node:sqlite` stand-in through the conformance suite's large case. The JNI path of a real NativeScript 8 device is not run by any suite; the README's "What has run on a device" section says the piece store has not.
- **Two puts of one id at once.** Both statements serialize on the connection mutex; the second is ignored. Inspection.
- **A put racing a flush.** `PendingSqliteSync` clears its flag before syncing, as `SqliteKVStore` does today, so a write resolving during the sync is covered by the next flush. Inherited; inspection.
- **A failed sync.** Latches: every later `put`, `delete` and `flush` throws `StoreFailedError`, reads keep working. Covered for the key-value store by the existing test; the piece store uses the same class.
- **Crash between a put and a flush.** Survives a process crash; a power cut may lose it, and `put` of the blob service had not resolved, so the record was never written; the sweep removes any orphan. Inherited from the conformance suite's reopen case.
- **Listing while pieces are put or deleted.** Keyset paging may include or miss an id added during the walk and never yields one twice; the sweep that consumes `list` protects in-progress pieces itself (`feat-a-node-stores-blob-pieces`). Inspection.
- **Block-store listing.** `listBlockIds` reads `metadata` only, so pieces never appear as blocks. Inspection.
- **Storage use counted once.** The page count includes the table; the node adds the piece store's own figure only when the prerequisite's rule says it is outside the block store's. Covered by that rule's own test.

## Tests

- `packages/db-p2p-storage-ns/test/sqlite-piece-store.spec.ts`:
  - The shared suite from `feat-a-node-stores-blob-pieces` (expected as `runPieceStoreConformance` from `@optimystic/db-p2p/testing/conformance`; use whatever name and harness shape it exports), registered persistent, with a harness built like the `'SQLite'` one in `test/sqlite-storage.spec.ts`: a file database in a fresh temp directory through `openTestFileDb`, `reopen` closing the handle and opening the same file, `cleanup` closing it and removing the directory. This is what pins put/get, the ignored second put, delete, listing, bytes used, the 256 KiB and 1 MiB pieces, and flush-then-reopen.
  - One case: a database written without the table gains it. Open a file database through `openTestFileDb`, `DROP TABLE pieces`, write and flush one block through `SqliteRawStorage`, close; reopen through `openTestFileDb`; the block reads back, and a piece put then get round-trips. It pins the upgrade path the backlog asked for, which no other suite covers for this backend (`packages/upgrade-check` covers `fs` and `leveldb` only).

No test for `PendingSqliteSync` of its own: the key-value store's existing flush test covers it.
