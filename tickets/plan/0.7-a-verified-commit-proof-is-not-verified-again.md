# A verified commit proof is not verified again

Reported as GitHub #68 (Sereus/cadre on React Native, `@optimystic/db-p2p` 1.27.0, first seen on 1.19.0).

## What happens

`certifyClaim` runs `verifyBlockCommitProofClaim` — one Ed25519 verify per cohort signer — on every call, before anchoring. On a quiet node the same inputs recur: the embedder reloads its membership views every 15 s, past the 10 s `readRepairWindowMs`, so each reload consults the cohort, and every answering peer re-sends the same unchanged proof. On Hermes, where Ed25519 is pure JavaScript, this was about a fifth of an idle voter node's JS time; on Node one 3-signer proof costs 0.77 ms per verify. Verified by reading `certifyClaim`: there is no memo.

## Requirement

The offline verdict of `verifyBlockCommitProofClaim` (and of `verifyBlockCommitProofContent`, if it shows the same pattern) is remembered in a small bounded cache and reused for identical inputs. Anchoring (`anchorAcceptedProof`) still runs on every call, since it depends on local state. Verdicts with and without the cache are identical, including for a forged signature and for a valid proof presented for another claim.

## The key is the design question

The verdict depends on the whole proof, the claim and the thresholds. The reporter's local patch keys on `sha256` of `JSON.stringify([proof, claim, thresholds])` with a strict replacer (inputs JSON cannot represent exactly skip the cache), 512 entries, dropping a repeat to 0.08 ms — but hashing ~2 KB of JSON per call then became the top single call site in their Hermes profiles. A cheaper key must still bind everything the verdict reads: the proof's self-reported `messageHash` alone is not enough, because verification recomputes the hash from the message, and a key that trusts it would let a tampered message reuse a cached pass. The plan should find the cheapest key that cannot alias two inputs with different verdicts (for example, caching only passes and keying on the recomputed hashes the verifier already produces, or on identity of the decoded proof object for the same peer answer), and state why it is sound. Peer ids and proof contents come off the wire, so the cache must be bounded (the bound in `PeerReputationService` is the precedent).
