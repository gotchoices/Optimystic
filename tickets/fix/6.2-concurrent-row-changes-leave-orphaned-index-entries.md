## What was observed

A plan-stage probe ran on 2026-09-15. Setup: a two-node in-process mock mesh (`test/mesh-node-harness.ts`); table `Probe (Id integer primary key, Token text)` with `create index probe_by_token on Probe(Token)`; A inserted `(100,'tok-a')` and B inserted `(200,'tok-b')`. The index tree was then read directly through a fresh `Tree` on each node's transactor. The probe file was deleted afterwards; the shapes are reproduced permanently by the racing group of `test/two-node-index-mutation-sweep.spec.ts` (prereq), which currently asserts these orphans as **predicted discrepancies**.

Entries are shown as `token‖id`. Every commit below fulfilled, with no error. Both nodes showed identical rows and identical index contents.

| shape | rows after | index after | stray entry |
|---|---|---|---|
| A: `begin; update … set Token='tok-x' where Id=100`; B: `begin; update … set Token='tok-y' where Id=100`; A commits, B commits | 100:tok-y, 200:tok-b | tok-b‖200, **tok-x‖100**, tok-y‖100 | `tok-x‖100` → row holds `tok-y` |
| A: `begin; delete … where Id=100`; B: `begin; update … set Token='tok-y' where Id=100`; B commits, A commits | 200:tok-b | tok-b‖200, **tok-y‖100** | `tok-y‖100` → no row |
| A: `begin; insert or ignore … (300,'tok-ignored')`; B: `insert … (300,'tok-winner')`; A commits | 100, 200, 300:tok-winner | …, **tok-ignored‖300**, tok-winner‖300 | `tok-ignored‖300` → row holds `tok-winner` |

Controls, run in the same probe and clean: B updating A's row to a new value, and B deleting A's row, with no concurrency.

## Root cause (one site, three arms)

A statement's index maintenance is staged as a **delta computed from the stager's snapshot of the row**: delete `oldIndexKey‖pk`, add `newIndexKey‖pk`. The main-table change is staged separately. On a conflict replay the two collections replay **independently**, and the main-table entry's replay semantics do not match what the index delta assumed.

The site is the `update` method of `OptimysticVirtualTable` in `src/optimystic-module.ts` (the `insert`, `update` and `delete` arms), together with `IndexManager.insertIndexEntries` / `updateIndexEntries` / `deleteIndexEntries` in `src/schema/index-manager.ts`.

- **UPDATE, same key**: the main-table entry is staged unguarded (`[[newKey, [newKey, encodedRow]]]`), so the later committer silently overwrites the earlier one. The earlier committer's added index entry is never removed, because the later committer's delete targets `tok-a‖100` from its own stale snapshot.
- **DELETE after a rival UPDATE**: the delete removes the row, but its index delta targets the pre-race value `tok-a‖100`. The rival's `tok-y‖100` survives with no row.
- **INSERT OR IGNORE**: the main-table entry carries `keepExisting`, so replay skips it, but the index add replays anyway. The `NOTE:` beside that guard already records this as deliberately out of scope for that ticket.

`docs/internals.md` (§ "Conflict replay re-makes the uniqueness decision") already states the principle for secondary UNIQUE, and chose the refusal answer there: "the rival's row lives in the main collection, which an index tree's replay can neither skip around nor evict, so an unguarded entry would silently commit two rows under one unique value". The same reasoning applies to these three shapes.

## Consequences

- **Today, for non-unique seeks: masked.** `executeIndexScan` fetches the row for each entry; a `no-row` entry is skipped, and Quereus re-applies the predicate to a `stale-value` row (the `NOTE:` above its `findByIndexIn` loop). Wrong rows are not returned today. That `NOTE:` names what flips it: the engine trusting `handledFilters`, or a covering-index read that never fetches the row.
- **UNIQUE-enforcing index trees: likely a user-visible false refusal** (`repro: static`; confirm). A stray entry occupies its value's prefix range, so a later legitimate insert of that value should be refused by `uniquePrefixGuard` (an `absentRange` guard) and by the pre-stage probe, permanently. Confirm with the same racing UPDATE shape on a `unique` column, followed by a sequential insert of the orphaned value from a third row.
- **Persistent and replicated**: nothing purges these entries. `backfillIndexTrees` only adds, and `reconcileMaintainedIndexes` scans nothing on open.
- **Adjacent main-table semantics this exposes** (not orphans): racing same-row UPDATEs silently lose one writer's update, and the prediction model in the mutation sweep expects a racing DELETE followed by an UPDATE to **resurrect** the row. Whether same-row last-writer-wins is intended for SQL UPDATE is not documented anywhere found (`docs/internals.md` documents guards for INSERT and UNIQUE only). If the fix direction depends on that, and it likely does, decide it or route that question to `blocked/`.

## Fix directions to evaluate (not yet chosen)

1. **Refuse the loser**, which is the precedent in `docs/internals.md`. UPDATE and DELETE main-table entries would carry a guard that the row at the primary key still equals the pre-write row the statement read; `requirePreWriteRow` already fetches it. The replay refusal surfaces like `TreeKeyTakenError` and fails the whole transaction, so the loser's index delta never commits. INSERT OR IGNORE would move from `keepExisting` to refusal under concurrency, just as the UPDATE path's IGNORE already resolves to `absent` (see the `moveGuard` comment in the same method). This changes the IGNORE disposition under a race. The precedent accepts that for UNIQUE: "an application-level retry then honours the disposition sequentially".
2. **Make index replay coherent**: derive the index delta at replay from the row actually being replaced, rather than at stage time. That is cross-collection coordination inside a single collection's replace handler, which the `keepExisting` `NOTE:` calls out of scope. It is probably only feasible in session (coordinator) mode, where trees commit atomically.

Direction 1 closes all three arms at one site and matches the existing precedent. Direction 2 preserves last-writer-wins and IGNORE semantics, at a much higher cost.

Also consider the legacy-mode multi-tree tear window. The main and index trees flush separately in `commitDirtyTreesLegacy`, so a refusal landing in the main tree must roll back the index tree too; the pre-flight described in `docs/internals.md` applies.

## Regression criterion

The racing group of `test/two-node-index-mutation-sweep.spec.ts` currently asserts these orphans through a prediction model headed by a `NOTE:` naming this ticket. The fix is done when that model is deleted, every racing case asserts `expectIndexAgreesWithScan` clean on both nodes (or, under direction 1, asserts the loser's refusal message plus a clean index), and the UNIQUE false-refusal shape above has its own deterministic test.
