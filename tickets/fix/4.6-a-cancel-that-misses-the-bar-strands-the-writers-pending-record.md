# A cancel that misses the approval bar strands the writer's pending record

Reported by sereus (sereus-sam, 2026-10-12), found while chasing a sereus integration failure on optimystic 1.13.0. Full timeline and proposals: `C:\projects\sereus\tickets\blocked\optimystic-failed-cancel-strands-the-writers-pend-record.md`. Debug log: `C:/Users/n8ers/AppData/Local/Temp/claude/c--projects-sereus/9aa555b6-1ec8-443c-9d85-78765cc02290/scratchpad/degraded-full1.log` (read it; it is the evidence).

## What happens

Three-member cohort; the promise bar is 3 (`ceil(3 × 0.75)`), so one silent member decides every cluster transaction. Member C answers a write's pend, then stops answering.

1. Pend succeeds: all three promise, A and B apply it, C's apply is left to the retry timer.
2. The commit fails `Failed to get super-majority: 2/3 approvals (needed 3, 0 rejections)`, both the one-round commit and `commitTailThenSweep`.
3. `dischargeCancel` runs three cancel rounds; each fails with the same shortfall (`coordinator-repo:cancel-error`), so no member applies the cancel.
4. C recovers. Nothing re-sends the cancel. The writer A keeps the pending record, and `ClusterMember.validatePendOperations` votes `held` on every later pend of the block (`validation-pending-conflict … rivals: [<action>]`). Every later write fails with `Pend blocks held: …` or `SyncRetryExhaustedError: … pending conflict: block(s) held by unresolved rival action(s) <action>`.

Observed: action `Spxt2Y33t2wfNe6vvDsH6g` on Revocation block `8Z0Jn6ZB0ASMCGcl7PZ5ybUjYLdBqOJiDEscbtRSU9g` still refusing writes 9 min 16 s after the last cancel round, when the run ended (38 `held` votes). Also in sereus's release-gate log (rival `iiYkuFEivz2rQKdYHo8ZvQ`, ~10 min), and twice for multi-collection transactions (`tx:YHjnoQKB…`, `tx:p2aweyJa…`), so it is not specific to one collection or write path. Whether 1.12.1 behaves the same was not run; the cancel path did not change in 1.13.0, so assume latent.

The general class (a client that never sends its cancel) is `backlog/debt-unpromotable-pending-records-need-a-sweep`, which is waiting on a design decision about when a record counts as abandoned. This instance does not need that decision: the writer is alive, knows exactly which action it failed to cancel, and is still connected.

## Candidate fixes (from sereus; evaluate, do not assume)

- **Writer side: a cancel that fails for want of approval stays owed.** The coordinator keeps the cancel in the owed-delivery records it already carries to members on their next request (`takeOwedRecords`, landed in 1.13.0 by `a-cluster-request-carries-owed-consensus-deliveries`), and/or keeps retrying it on the existing retry timer, so B and C, and A itself, drop the record when reachable. Sereus also proposes applying the cancel to the coordinator's own storage at once.
- **Member side:** the expiry-based sweep from the backlog ticket. Out of scope here unless research shows the writer-side fix cannot close this instance.

## The safety question to settle first

Before anything drops a pending record without a cancel reaching consensus, establish that the commit cannot have landed anywhere. A commit round that gathered 2 of 3 commit signatures is a strict majority of commit signatures, and members apply on a commit majority (see *A behind member actively reconciles* in docs/internals.md, and `presignLocalCommit`). If any member can have applied the commit, a local cancel on the coordinator turns into a divergence, not a cleanup. Read `commitTransaction` / `commitInOneRound` / `CoordinatorRepo.commit` and decide from the code which shortfalls prove "applied nowhere". Then:

- if a shortfall can coexist with an applied commit, the cancel must not be applied locally on its own; the owed-and-retried consensus cancel is the only safe form, and a write whose commit may have landed is a torn-action case (`Collection.completeOwnEntry`), not a cancel case;
- if it cannot, the local apply is safe and closes the writer's own wedge immediately.

If the code leaves this genuinely undecidable, route that question to `blocked/` with proposed text, and still land the owed/retried cancel, which is safe either way: a consensus cancel of an action that committed is refused by the members that hold the revision.

## Reproduction

At the db-p2p layer, on the mesh harness (it can make a member answer one phase and go silent the next): three members; C answers the pend's promise, then holds every later cluster request; the write fails at commit; the cancel fails; C recovers; a second write to the same block must commit. Today it fails with `held` naming the first action. Keep that as the regression test.
