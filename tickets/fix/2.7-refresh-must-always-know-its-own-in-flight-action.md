# A refresh should never have to be *told* which of its own writes is in flight

## Plain-language background

A write can half-land. The network layer commits a collection's header and log tail first, then
sweeps the remaining blocks; if one of those later blocks loses a race, the whole write is
reported as failed even though the header and tail are already permanently stored. The write's
own record is therefore already in the collection's log when the writer is told "you failed".

If the retry does not recognise that record as its own, it writes the same thing a second time
and the log ends up with the write recorded twice, under the same identifier, at two different
revisions.

Ticket `torn-action-own-entry-consumption` fixed this for the single-collection path
(`Collection.sync`). The multi-collection path (`TransactionCoordinator`) has the identical
defect and is untouched.

## Root cause — one site, one missing piece of knowledge

`Collection.updateInternal` can only recognise its own already-committed entry when a caller
hands it the action id, as an optional argument:

```ts
private async updateInternal(inFlightActionId?: ActionId)
```

Exactly one of the three callers passes it (`syncInternal`). `update()` and `updateAndSync()`
correctly pass nothing — they are refreshes on behalf of a reader, with no write in flight. But
`TransactionCoordinator.commit`'s retry loop refreshes **through `update()`**:

```ts
for (const collection of this.collections.values()) {
	await collection.update();
}
```

so it is indistinguishable from a reader refresh, even though the coordinator is mid-retry of a
write it knows the id of. That is the whole bug: the knowledge exists at the call site and the
type system does nothing to make the call site supply it.

The uninformed-refresh shape is what should stop being expressible, not just this one instance
of it. A third write path added later inherits the same defect for free.

## Why the coordinator arm is reachable (traced, not run)

1. `commitOnceLatched` appends the log entry with `actionId = transaction.id`
   (coordinator.ts:782, 791-793) — the same id on every retry attempt.
2. `commitCollection` sends the `CommitRequest`. A torn commit answers `{ success: false }`, and
   the code deliberately maps *every* returned commit failure to `stale: true`
   (coordinator.ts:1183-1192) — a documented choice, and correct for its own purpose.
3. With no hard failure and nothing in `committedCollections`, `commitPhase` reports
   `staleLoss: true`, so the caller raises `CoordinatorStaleLossError` — classified as a *clean*
   loss with nothing durable. For a torn action that classification is wrong: the header and tail
   ARE durable.
4. `commit` catches it, calls `restorePending` (which restores the pending actions but not the
   log entry it appended, since that came after the snapshot), then refreshes with
   `collection.update()` — no id, so the durable entry is run through the conflict filter, kept,
   and replayed.
5. The retry's `addActions` appends a second entry with the same `transaction.id` at the next
   revision.

Result: two log entries carrying one action id at two revisions. Beyond the duplicated action,
this makes the action-id→revision relationship ambiguous for everything that reads it —
`Log.getActionContext`'s `committed` list, `findInvalidation`, and any dispute/invalidation
cascade that identifies an action by id.

`repro: static` — this is traced through the code, not observed. What would confirm it: a
coordinator-level test using a `DelegatingTransactor` that commits durably on the inner
transactor and then returns `{ success: false, conflict: true }` for the first commit (the
wrapper in `collection-own-action-replay.spec.ts` is exactly this), driving
`TransactionCoordinator.commit`, then asserting the collection's log holds the action once.

## What to build

The fix should be the invariant, not the instance: a refresh should learn which of the
collection's own writes is in flight **from the collection**, so no call site can forget to say.

The shape that does this: the collection owns the fact for the duration of a commit attempt —
something like an `inFlightActionId` field set when a write is submitted on the collection's
behalf and cleared when that write is confirmed or abandoned — and `updateInternal` reads it
instead of taking it as a parameter. `syncInternal` sets it around its own attempt; the
coordinator sets it (for each participant) around `commitOnce`, where it already holds every
participant's latch and already knows `transaction.id`. `update()` and `updateAndSync()` then
need no change at all and become correct by construction rather than by having nothing to pass.

Two properties the design has to preserve:

- **A reader refresh on a collection with no write in flight must behave exactly as today.** The
  field is unset outside a commit attempt, so the consume branch cannot fire.
- **The field must be cleared on every exit path**, including a thrown/abandoned commit — a stale
  id left behind would make a *later, unrelated* refresh consume a foreign entry that happens to
  match. Clearing belongs in the same `finally` that releases the latch.

Whether the coordinator threads one id per participant or one id for the whole transaction is an
implementation call: it uses `transaction.id` for every participant today, and that id is stable
across retries (unlike `syncInternal`, which mints a fresh one per `sync()` call but reuses it
across that call's retries), so no new identifier has to be invented.

## Coverage this must add

- A coordinator-level regression: torn commit on a single-collection transaction, retry, assert
  the action appears in the log exactly once and `landedCommits === 1`.
- The same over a **multi-collection** transaction, where one participant tears and the other
  does not — the participant that never committed must still replay normally.
- A guard that an abandoned commit attempt does not leave the in-flight id set: after a commit
  that throws a non-retryable error, a subsequent plain `update()` over a foreign entry carrying
  that same id must still replay it rather than consume it.

## Out of scope

- Do not change the header→tail→sweep commit order, and do not soften the non-tail sweep's stale
  failure into a tolerance. Both are load-bearing and are re-stated in
  `tickets/implement/2.6-torn-action-cleanup-and-mesh-validation.md`.
- Do not reclassify the coordinator's torn commit as a partial landing
  (`CoordinatorPartialCommitError`). That would make it non-retryable and lose the retry the
  writer is owed; the fix is for the retry to recognise its own work, exactly as the
  single-collection path now does.
