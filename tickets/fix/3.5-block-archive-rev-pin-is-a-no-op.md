# `serveBlockArchive`'s `rev` argument pins nothing

## The defect

`serveBlockArchive(repo, blockId, rev)` (`packages/db-p2p/src/storage/block-archive.ts`) is the one
function every peer answers a block-repair fetch with. Its `rev` parameter is supposed to pin the
read to a specific revision. It does not.

It expresses the pin by building a synthetic action context:

```ts
const context = rev !== undefined ? { rev, committed: [], pending: [] } : undefined;
const result = await repo.get({ blockIds: [blockId], context }, { skipClusterFetch: true } as any);
const latest = result[blockId]?.state?.latest;
```

`StorageRepo.get` (`storage-repo.ts`, the `if (context)` branch) reads **only** `context.committed`
— it walks that list to promote landed-elsewhere pendings. It never reads `context.rev`. With an
empty `committed` list the whole branch is a no-op, and the read then falls through to the repo's
own latest exactly as a contextless read would.

So the served archive is always the repo's newest revision, labelled with the newest revision's
number, whatever revision was asked for.

## How it was found, and how to confirm it

A test written for `serve-block-commit-proof` asserted that a rev-1 request served rev 1; it served
rev 2 instead. The observation is now pinned (deliberately, as the current behaviour, with a pointer
to this ticket) in `packages/db-p2p/test/block-archive-proof.spec.ts` — "serves the proof for the
revision it ACTUALLY serves". Landing this fix means turning that back into a real pin assertion.

To reproduce directly: commit two revisions of a block into a `StorageRepo`, call
`serveBlockArchive(repo, blockId, 1)`, and observe `archive.range[0] === 2`.

## Who is affected

- **`RestorationCoordinator`** (`storage/restoration-coordinator.ts`) is the one caller that passes a
  real revision — `client.requestBlock({ blockId, rev })`. That request crosses the sync protocol,
  `SyncService.buildArchive` forwards the `rev` to `serveBlockArchive`, and the peer answers with its
  latest. The restoring node receives content for a revision it did not ask for, correctly labelled
  as that other revision (the archive is internally consistent — nothing is *mis*-labelled), so the
  visible effect is a restore that does not restore the requested point in history.
- **The repair paths are not affected today.** Both latest-revision consults in
  `libp2p-node-base.ts` pass `rev: undefined`, which is the un-pinned path and is correct as written.
- **Commit proofs are not mis-paired by this.** `serve-block-commit-proof` looks the proof up for
  the revision *actually served*, so a served proof always certifies the revision it is attached to.
  This ticket is about serving the wrong revision, not about certifying it wrongly.

## What "fixed" should mean

Two shapes are plausible and the choice is the real work here:

1. **Honour the pin in `serveBlockArchive`** — read the pinned revision's stored block and action
   directly from block storage (`getBlock(rev)` / the revision's action record) rather than going
   through `repo.get`'s latest-oriented path. This keeps the repair wire's one entry point.
2. **Make the un-honoured argument impossible** — if no caller genuinely needs historical revisions
   from a peer, remove `rev` from `serveBlockArchive` and from `SyncRequest`, and give
   `RestorationCoordinator` whatever it actually needs. An argument that cannot be honoured is worse
   than an argument that does not exist.

Whichever is chosen, the type/representation question is worth asking first (the architecture ladder
in the workflow rules): the synthetic `{ rev, committed: [], pending: [] }` context is a value that
*looks* like it carries a pin to every reader and does not. If `ActionContext` is being used for two
unrelated jobs here, splitting it is the higher-rung fix.

## Expected behaviour

- A peer asked for revision N serves revision N, or serves nothing if it does not hold N — never a
  different revision presented as the answer.
- A peer asked for no revision serves its latest, exactly as today.
- `SyncService`, the mesh harness, and the repair paths keep behaving identically for the
  `rev: undefined` case, which is every caller except `RestorationCoordinator`.
