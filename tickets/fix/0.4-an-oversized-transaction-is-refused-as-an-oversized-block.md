# An oversized transaction is refused as an oversized block

Reported as GitHub #61 (Sereus; optimystic 1.27.0, solo node, file storage).

## What happens

One SQL transaction of ~1 KiB rows on a solo node: 1 and 3.5 MiB of rows commit; 4, 5 and 6 MiB are refused with `TransactionTooLargeError` (pends of 8.9, 11.2 and 13.4 MB); from 7 MiB the refusal is `BlockTooLargeError`, naming the collection's log block (8.0 MB at 7 MiB of rows). One committed transaction is one log entry, and an entry above `BLOCK_TARGET_BYTES` sits alone in its block, so that block is about as large as the transaction — the premise `MAX_BLOCK_BYTES` documents ("no single transaction produces a block over it on its own") holds only if the transaction check runs first. Deterministic in the reporter's runs.

## Read from the code

The block measure runs at staging: `stageAttempt` (every single-collection write) and `TransactionCoordinator.declareTouchedBlocks` (the coordinator path) call `oversizedBlock` right after the log append. The transaction measure, `assertTransactionFits`, runs only inside `NetworkTransactor.pend`, after both. So whenever a transaction is large enough that its lone log block alone exceeds 7.5 MiB, the block error wins. Both limits are 7.5 MiB, and the log block is a little smaller than the pend (the pend also carries the data blocks), which is why the window between 4 and 7 MiB of rows reports correctly.

## Expected

- A transaction whose pend would exceed `MAX_TRANSACTION_BYTES` is refused with `TransactionTooLargeError`, whatever else is also over a limit. `BlockTooLargeError` is reserved for the case its documentation describes: a block grown past the limit by something other than one transaction. A test pins the ordering at the size where both fire.
- The refusal comes before the pend is sent, as now; whether it can come earlier still — during staging, as soon as the staged change passes the limit, rather than after a 56k-row transaction spent 4.4 minutes of CPU and 3.3 GB of memory staging (the reporter's real case) — is the issue's second ask. Settle whether a cheap running estimate is available at the vtab or collection layer; if it is not, say so in the docs rather than leave it implied.
- The ratio of encoded pend to row data (the reporter measured ~2.2× for 1 KiB rows) is documented where the limit is: docs/internals.md already says a log entry repeats each action's data beside the blocks it changes, so row data counts roughly twice; give writers the number to size their batches by. Carrying row data once is `a-large-write-costs-time-and-space-per-byte` (plan), not this ticket.
