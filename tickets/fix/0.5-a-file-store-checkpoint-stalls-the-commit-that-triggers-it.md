# A file-store checkpoint stalls the commit that triggers it

Reported as GitHub #62 (Sereus; optimystic 1.27.0, `FileRawStorage`, solo node, Node 24.11 on macOS 15, Intel). Follow-on to GitHub #37, which added the write log and its checkpoint.

## What happens

120 sequential transactions of 50 rows (~230 bytes each):

| setup | median commit | slow commits (wall s / CPU s) |
|---|---|---|
| `MemoryRawStorage` | 30 ms | none (max 51 ms) |
| file, default `checkpointBytes` (16 MiB) | 133 ms | #43 5.1 / 0.31, then #44–55 at 1.0–1.8 each; #82 6.7 / 0.35; #119 6.1 / 0.30 |
| file, `transactor: 'local'` | 90 ms | #44 2.1 / 0.23 |
| file, `checkpointBytes` 4 MiB | 96 ms | 13 commits of 0.9–2.1 s, about four times as often |
| file, `checkpointBytes` 64 MiB | 125 ms | no big stall, but every commit from #101 takes 1.0–1.7 s at under 0.11 s CPU |

The large stall recurs about every 16 MiB of log and the first was commit 43 in 3 of 3 runs; wall time far above CPU time means the commit is waiting, not computing. The 64 MiB row suggests a second cost that grows with the uncheckpointed log. Not reproduced here (macOS-specific timings; the reporter's script is in the issue).

## Read from the code

The checkpoint is designed not to block commits: `scheduleCheckpoint` starts it with `checkpointInBackground`, which no commit awaits. But its first step, `seal`, runs inside the commit queue: it runs the pending sync step (`syncUnsynced`), closes the log, renames it, and creates and syncs a fresh empty log, and every commit behind it waits. Its second step, `syncDirtyPaths`, then syncs every file and directory written since the last checkpoint (`CHECKPOINT_SYNC_CONCURRENCY` at a time) off the queue, but on the same disk the commits' own log syncs need. Which of these accounts for the multi-second stall, and what makes commits slow down as the log grows (the log's own sync, a lookup over the dirty set, or something else), is unmeasured; the fix stage should trace it before choosing.

## Expected

No commit's latency includes the checkpoint's bulk file syncs: a commit that crosses `checkpointBytes` takes about as long as its neighbours, and commit latency does not grow with the size of the uncheckpointed log. The crash-recovery guarantees in the README's Write-ahead log and Durability sections, and Invariant 6 of `packages/db-p2p/docs/storage.md`, stay as they are.
