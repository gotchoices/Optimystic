# A relay reservation the relay dropped is never renewed

Source: GitHub sereus#64. Reported against Sereus's own supervisor in `@serfab/cadre-core`, which was modelled on this one and makes the same judgement; db-p2p's supervisor has the same defect in its own code.

## Background

A node with no address another machine can dial (a phone, a browser tab) is reachable only through a circuit relay. It holds a slot on the relay, called a reservation, and advertises an address of the form `<relay address>/p2p/<relay id>/p2p-circuit`. db-p2p runs one supervisor per configured relay (`superviseRelayReservation` in `packages/db-p2p/src/network/relay-reservation.ts`) because libp2p asks for the slot once and does not ask again after the relay restarts or the connection drops.

## The defect

The supervisor decides whether the reservation is held from local state alone: `RelayReservationLoop.held` is true when `node.getMultiaddrs()` contains an address routing through the relay. While held, every tick (the `checkMs` liveness poll, every 5 s by default) only re-reads that list and reschedules; it never contacts the relay. The supervisor drives a new reservation only when the address disappears, which happens on `connection:close` to the relay or when libp2p's own reservation store renews near expiry (the default relay TTL is 2 h).

A relay can drop a reservation on its side while the connection stays open. Sereus observed it twice on 2026-11-05 against a public circuit-relay-v2 relay, on reservations under 35 minutes old, once with no change at all on the phone's side; the cause on the relay is not known. After that:

- libp2p's reservation store still holds a record with a future expiry, so nothing renews it soon;
- the node still advertises its `/p2p-circuit` address, so the supervisor reads it as held;
- the relay answers `NO_RESERVATION` to every dial through it.

The node is unreachable through that relay until the connection drops, which on a quiet phone can take a very long time. In Sereus this showed as a joiner stuck on "Joining" forever (the inviting node's control node was the stale one) and as strand readers timing out. Hanging up the relay connection made the supervisor book again and everything recovered within seconds.

Verified statically in this repository: `held` reads `this.node.getMultiaddrs()` only, and `tick` returns through `onHeld` without any request while it is true. Confirming it needs a relay that forgets a reservation without closing the connection; an in-process `circuitRelayServer` whose reservation map entry is deleted by the test would do.

## Expected behaviour

A reservation the relay no longer honours is noticed and replaced within a bounded time, without waiting for the connection to close or for the reservation's TTL. The reporter's suggestions, either of which would satisfy it:

- while a reservation is held, re-send the reservation request to the relay on a timer well inside the TTL (a reservation request to a relay that already holds one renews it; libp2p's in-place renewal path does this), or
- check the reservation against the relay rather than trusting the local address list.

The interval should be configurable through `RelayReservationSupervisorOptions` (phones will want to tune it), with a default that keeps the request rate low. Sereus's interim patch on its own supervisor re-sends every 5 minutes with ±10% jitter and fixed the stuck "Joining" case for them.

Whatever the mechanism, it must not withdraw the advertised address while a still-valid reservation is being renewed (a node is unreachable for that gap), and must keep the existing per-relay serialization of drives and the `HadEnoughRelaysError` handling. The supervisor reaches libp2p internals in exactly one place (`findCircuitRelayTransport`, pinned by `relay-reservation-seam.spec.ts`); a renewal that needs more of the reservation store's surface extends that seam rather than adding a second.
