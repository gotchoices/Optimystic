# Quereus 4.20.0 restores the catalog when `apply schema` fails

## What was observed

`yarn check` on 2026-09-25 against `../quereus` at `v4.20.0` (`14f16432b`, clean tree, fresh build): everything is
green (db-core 1842, db-p2p 3114, the storage and crypto packages, `check:rn` with Metro and hermesc) except
`quereus-plugin-optimystic`, which has 994 passing and 3 failing, all in `test/schema-batch.spec.ts` under "APPLY SCHEMA
coalesces catalog writes into one commit":

1. "a statement refused mid-loop leaves no catalog trace of its own; what landed before it commits": expected 1, got 0.
2. "a create refused AFTER its schema reached the overlay is rolled back by the checkpoint": expected 1, got 0.
3. "a CREATE INDEX that fails inside the batch withdraws only the index from the pending record": after reopening,
   expected `{ tables: 1, indexes: 0 }`, got `{ tables: 0, indexes: 0 }`.

All three assert 4.19's behaviour: the steps that ran before the failing statement stay committed. Quereus 4.20.0
(ticket `apply-schema-rollback-journal` in that repository) runs the migration under an undo journal and, when a step
fails, unwinds the steps that already ran and restores the pre-apply catalog. Each failure is our stored catalog
coming back empty, which is what full rollback should produce.

## What has to be established

The tests are out of date. What matters is whether, after every failure shape, **the catalog Optimystic stores equals
the catalog Quereus holds in memory**. Check it on both sides, in the same process and after a reopen:

- The three cases above. The stored side is now empty. Confirm the in-memory side is too (for case 3,
  `h.db.schemaManager.findTable('t0', 'main')` should be undefined before any reopen).
- **"drop then create over the same URI in one apply sees the PENDING gravestone".** This case passes, and asserts
  that the drop was committed to storage even though the apply failed (`hydrated.tables` 0, `old` not found after
  reopen). Under 4.20.0, Quereus either restores `old` in memory (then the two sides disagree, and a later read of
  `old` in the same process finds a table whose storage says it was dropped), or it reports the drop as a step it
  cannot undo (`describeIrreversible`) and keeps it dropped. Find out which. If they disagree, that is the real bug.
- The `endSchemaBatch` contract in `../quereus/packages/quereus/src/vtab/module.ts` changed with this release, and
  there is a review NOTE there about a case that cannot be restored. Read it against what our module does at the end
  of a batch, including a failure that happens after our pending record has been committed.

## Expected outcome

- The plugin's stored catalog and Quereus's in-memory catalog agree after every failure shape of `apply schema`.
  Where they cannot agree (a step Quereus cannot undo), the failure is reported loudly and nothing is silently left
  half-applied.
- `schema-batch.spec.ts` pins 4.20.0's behaviour. Every case asserts both sides, not only the stored one after a
  reopen, since checking only storage is what let this go unnoticed.
- The `@quereus/quereus` range moves to `^4.20.0` in all four packages, with the peer ranges and `engines.quereus`
  moved in the same pass as `yarn.config.cjs` requires, because the plugin is only built and tested against one
  Quereus and now depends on 4.20.0's behaviour. This changes only the declared ranges; publishing is the
  maintainer's release.
- Update the docs that describe the old partial-commit behaviour. Search `docs/` and the plugin's README for the
  schema-batch description (see `docs/internals.md` and the plugin docs around "APPLY SCHEMA").
- `yarn check` green from the root.
