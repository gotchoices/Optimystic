# Matchmaking cannot register on a small network

Reported as GitHub #67 (VoteTorrent, measured on 1.24, unchanged in 1.27.0).

## Reported

`MatchmakingProviderSession.register` on networks of 1, 2 and 3 hosts, with cohort-topic reactivity enabled, is refused with `CohortBackoffError` ("no willing primary right now") on every retry for two minutes. The reporter attributes it to the cohort threshold signature needing `DEFAULT_MIN_SIGS = 14` of `wantK = 16` signers, which a network of fewer than about 14 hosts can never collect. Their elections run on a handful of authority hosts plus phones, so matchmaking never works there; they now run their own rendezvous.

## Read from the code (not run) — the reported mechanism does not match

- A participant's register goes through `FretTopicRouter.routeAndAct`, which passes `min_sigs` to FRET's `routeAct`. FRET hands it to the host's activity handler (`fret.setActivityHandler` in `createCohortTopicHost`), which dispatches the `RegisterV1` and returns the encoded reply. Nothing on that path threshold-signs the reply, and the participant's walk does not verify a threshold signature on it. `minSigs` is used for promotion and demotion notices, membership certificates and child links.
- `CohortBackoffError` is thrown by `CohortTopicService` whenever the walk's outcome is not `accepted` — a `retry_later` (an `UnwillingCohort`, the anti-denial-of-service gate on a cold-start `bootstrap`, the probe rate gate) or a `no_state` with no further step. So the refusal comes from one of those, and which one is the first thing to establish.
- Matchmaking topics are not root-placed: reactivity places a topic's root at its log tail's storage group with the ratio threshold `ceil(members × quorumRatio)` (`createRootPlacement`, `rootPlacedMinSigs`), which is why reactivity works on small groups. Matchmaking cohorts are the `wantK` FRET peers nearest a coordinate.
- `docs/cohort-topic.md` §Promotion says "a network of a few machines never promotes" — the design expects a small network to serve a topic from its root cohort, not to be unable to start one.

## Expected

- Reproduce on a real-libp2p network of one, two and three nodes with `cohortTopic.enabled` (the substrate integration specs build such meshes), and name the refusal by its outcome kind and the site that produced it.
- A provider registers, and a seeker finds it, on a network of one to three serving nodes with default configuration. If the fix needs a threshold or quorum to follow the cohort that actually exists (as root placement already does), say so in the cohort-topic doc.
- If any part of the refusal turns out to be a deliberate security floor that small networks cannot meet, that is a maintainer decision: route it to `blocked/` with the proposed rule rather than lowering it silently.
