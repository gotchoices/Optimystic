## What was observed (implement stage of `refuse-concurrent-row-change-loser`, 2026-09-15)

Two `Database` handles over one `FileRawStorage` directory and the `local` transactor (the shape `test/concurrent-secondary-unique-refusal.spec.ts` uses), table `T (id integer primary key, v text)` with `create index T_by_v on T(v)` declared on both handles, then, with no concurrency at all:

1. Handle A inserts `(1, 'seed-1')` and `(2, 'seed-2')`.
2. Handle B runs `select id, v from T` (a full scan, which refreshes B's main collection only) and sees both rows.
3. Handle B runs `delete from T where id = 1`. It succeeds.
4. `plugin.verifyIndexes(db, 'T')` on **either** handle reports `T_by_v`: 1 row, 2 entries, orphaned `no-row` entry `seed-1 ‖ 1`.

The row is gone from the table on both handles; its index entry is still in storage on both. The same scratch probe showed that an UPDATE from B in the same position (`update T set v = 'moved-B' where id = 1`) leaves the index correct, and the two-node mutation sweep's sequential sibling-delete cases are also clean — there the sibling inserted its own row before deleting, so its index tree had synced once and held the entry. The defect needs a DELETE issued from a handle whose index tree has never fetched the entry being deleted.

Reachable in ordinary use: a node opens a table (hydrates), reads it by primary key or full scan, and deletes a row. Every later lookup of the deleted value on every node then finds the stray entry. Today that returns nothing (the row is gone), but under a UNIQUE index the stray entry makes the deleted value permanently un-insertable on every node with `UNIQUE constraint failed`, and `bug-stale-index-entry-causes-false-unique-refusal` in the backlog describes that symptom.

## Root cause

Two things combine, one in the plugin and one in db-core.

**The plugin's index delete is blind.** `deleteIndexEntries` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts` stages `[[treeKey, undefined]]` without first reading the entry. The main-table delete, by contrast, always reads the row first (`requirePreWriteRow` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`), which pulls the leaf into the collection's tracker, so its delete changes a block. On an index tree that has never fetched the entry, `find` misses, `deleteAt` on a not-found path returns `false`, and the action changes no block. The action is still appended to the collection's pending list (`actInternal` in `packages/db-core/src/collection/collection.ts`).

**db-core replays pending actions only on a block conflict.** `updateInternal` in `packages/db-core/src/collection/collection.ts` adopts the newest committed revision, then re-stages the pending actions against it only `if (anyConflicts)`, where a conflict means an incoming log entry names a block the tracker holds a transform for. A pending action that changed no block holds no transform, so nothing conflicts, so it is never replayed. The commit then writes a log entry that lists the delete action while the block transforms it carries do not remove the entry. Readers materialize blocks, not log entries, so on every node the entry survives. The debug trace of the probe shows exactly this: B's index tree pre-flights to the latest revision, then pends and commits one block at the next revision, and the entry is still present afterwards.

The invariant that is broken: **a pending action must have been applied against the revision it commits over.** Today that holds only when the action's initial staging happened to touch a block the adopted revisions also touched.

## What to build

Fix at the db-core seam so every collection user gets the invariant, then remove the plugin's blindness as belt-and-braces:

- In `updateInternal`, replay the pending actions whenever the committed context advanced past the one they were staged against and the pending list is non-empty, not only when a block conflict was detected. The replay already runs under the collection latch and resets the tracker, so this is a gating change, not a new mechanism. Measure the cost on the plugin's suite (every legacy commit pre-flights every staged tree, so this adds a replay per staged tree per refresh that adopted something) and record it in the handoff.
- Make `deleteIndexEntries` read the entry it deletes (a `get` on the tree before staging), so the delete always touches the leaf and shows up as a transform. State in a comment that this is defence in depth over the db-core rule, not the fix.
- A db-core unit test over a raw `Tree`: two `Tree` instances on one transactor; one inserts an entry and syncs; the other, never having read the tree, stages a delete of that key and syncs; a third fresh `Tree` must not find the key. This is the property test for the invariant, independent of the plugin.
- In `test/concurrent-row-change-refusal.spec.ts`, `twoHandles` seeds rows alternately through both handles specifically to sidestep this defect (its comment names this ticket). Once fixed, add one case there that seeds through A only and lets B delete, closing on `expectIndexAgreesWithScan` on both handles, and drop the sidestep comment.
- Sweep for other blind deletes: every `stage([[key, undefined]])` on a tree the writer may not have read. `applyUniqueEvictions` reads the row through the probe first and is fine; check `backfillIndexTrees`, the unique-tree populate, and any index-tree write reached from DDL.

## What would confirm the root cause

The debug trace (`DEBUG=optimystic:*`) of step 3 above: after the bridge's `commit:collections` line shows the index tree at the latest revision, the index tree pends one block and commits, and a subsequent `verifyIndexes` still lists the entry. Adding a temporary unconditional `replayActions()` call in `updateInternal` when `pending.length > 0` makes the probe clean on both handles.
