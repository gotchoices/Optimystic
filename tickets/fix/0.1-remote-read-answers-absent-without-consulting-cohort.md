# A repo-protocol read skips the cohort consult, so an empty coordinator reports an authoritative absence

Filed from the Sereus repo, where this is the single largest source of multi-machine test failure.
Measured 2026-08-03 against `9b86eb3` (`v0.19.0`).

## The mechanism

`RepoService.handleIncomingStream` sets `skipClusterFetch: true` on **every** block read arriving
over the repo protocol — that is, every read a *remote* peer makes, the normal case in any party
with more than one machine:

```ts
// packages/db-p2p/src/repo/service.ts:264
response = await this.repo.get(operation.get, { expiration: message.expiration, skipClusterFetch: true } as any)
```

`CoordinatorRepo.get` (`coordinator-repo.ts:337`) reads that flag and skips the cohort consult
entirely, so a coordinator with no local copy answers `{ state: {} }` — an *authoritative* absence,
with no `unavailable` flag. `NetworkTransactor.get` (`network-transactor.ts:134-168`) treats an
unflagged absence as final and does not retry it against another peer, deliberately. Its comment at
lines 141-145 says why:

> Cross-member reconciliation for a missing block has already happened one layer down:
> `CoordinatorRepo.get` detects `isMissing` and consults cluster peers before it responds.

For a remote read that is not true, and `service.ts:264` is the reason.

## The observed sequence

Two nodes, one party:

1. A is genesis owner and writes rows while alone. Its raw block store holds `default/CadrePeer`.
2. B joins. The DHT ring changes and A's own lookups for `default/CadrePeer` now route to **B**.
3. B has never held that block. The read arrived over the repo protocol, so B skips the consult,
   never asks A, and answers absent-and-authoritative.
4. A's `Collection.updateInternal` sees "I hold committed revision 3, the header reads absent",
   which is the contradiction it is written to refuse, and throws `CollectionHeaderVanishedError`
   (`db-core/src/collection/collection.ts:236`). Every subsequent write on A fails the same way. The
   state is permanent, because the routing does not change back.

Instrumented evidence, `answerer` being the node whose `CoordinatorRepo.get` produced the entry:

```
before connect:  COORD answerer=A get(default/CadrePeer) ctx=null -> block=yes rev=1
after connect:   COORD answerer=B get(default/CadrePeer) ctx=null -> block=no  rev=-  unavail=-
                 write FAILED: collection default/CadrePeer holds committed revision 3,
                 but its header block read as absent
A raw store:     default/CadrePeer@1  default/CadrePeer/index/_uniq_5@1   (the block IS here)
B raw store:     optimystic/schema@1                                      (B holds nothing)
```

No `findCluster` call is logged on B between the read and its answer.

## The fix, and the measurement behind it

Drop `skipClusterFetch: true` at `service.ts:264`. The consult reaches peers over the *sync* and
*block-transfer* protocols rather than the repo protocol, so the recursion the flag guards against
does not arise on this path.

Emulated exactly at runtime from the consuming repo — patching `CoordinatorRepo.prototype.get` to
clear the flag **only** when `options.expiration !== undefined`, which is what distinguishes the
repo-protocol call from the sync-protocol one — and ran a consumer's full integration suite on
identical builds:

| | at `9b86eb3` | with `service.ts:264` neutralized |
| --- | --- | --- |
| test files red | 8 of 41 | **5 of 41** |
| tests red | 14 of 241 | **6 of 241** |
| `header block read as absent` occurrences | 23 | 7 |
| `peers-unreachable` occurrences | 3 | 3 |

Cleared outright: two-node control convergence, strand-unpublish sibling convergence,
delete-while-alone re-replication (both tests), cold-start bootstrap retry, three-machine cohort
writes, two of three push-wake scenarios, three of four closed-strand membership scenarios.

## Important: do NOT also change `sync/service.ts:160`

There are two production sites setting this flag:

```
packages/db-p2p/src/repo/service.ts:264   { expiration, skipClusterFetch: true }   <- change this one
packages/db-p2p/src/sync/service.ts:160   { skipClusterFetch: true }               <- leave alone
```

An earlier, cruder version of the experiment cleared the flag at *both* and the result was much
worse — the suite stayed at 13 red, `peers-unreachable` rose from 3 to 21 occurrences, and several
scenarios that pass today began failing with 60-113 s timeouts rather than errors, which looks like
exactly the recursion the flag exists to prevent. The sync path appears load-bearing. The numbers in
the table above are from the precise, repo-protocol-only emulation.

## An alternative shape, if the direct fix causes trouble

Keep the skip, but make the skipped-consult absence report `unavailable` instead of a bare
`{ state: {} }`, so `NetworkTransactor.get` retries it against another peer. That never widens what
a repo-protocol read is allowed to do. It was not measured — the direct fix was, and it worked — so
treat it as a fallback rather than a recommendation.

## What remains after this fix (not this ticket's problem)

Six failures survive in the consuming suite, none of them replication-core: one push-wake scenario
still showing the header-absent fingerprint (so it has a genuine second cause), one
`peers-unreachable` scenario, one member-visibility timeout, and three tests in a provider scenario
that is unstable at HEAD as well (4 of 5 red without the patch, 3 of 5 with it).
