# The reserved `~proof:` action-id namespace is not actually reserved

## Background

`persist-block-commit-proof` stores a revision's `BlockCommitProof` inside the existing
**transactions store** rather than adding a sixth store to `RawStoreDriver`, using a synthetic
action id built by `blockProofActionKey(rev)` in `raw-store-codec.ts`:

```ts
export function blockProofActionKey(rev: number): ActionId {
	return `~proof:${rev}` as ActionId;
}
```

Its comment states that `~proof:` is a *reserved* action-id namespace, on the grounds that real
action ids are hashes or prefixed forms (`tx:<hash>`, `stamp:<hash>`, `inv:<…>`) and never begin
with `~`.

That is true of the ids the system's own client code generates. It is **not enforced anywhere.**

## The defect

An action id is chosen by whoever originates the write, and no member ever re-derives or
format-checks it:

- `createTransactionId` (`db-core/src/transaction/transaction.ts:213`) runs only on the **client**.
  No server-side site recomputes it from the transaction and compares.
- `StorageRepo.pend` passes `request.actionId` straight through to storage. Its optional
  `validatePend` hook checks the transaction body and operations hash — never the action id.
- `BlockStorage.saveRestored` (`block-storage.ts:459`) writes
  `saveTransaction(blockId, action.actionId, action.transform)` using an action id taken verbatim
  from a **peer-supplied `BlockArchive`**.

So both an untrusted client and an untrusted peer can put a value into the transactions store under
the exact key a proof uses. The two entries then collide, in whichever order they arrive:

**Order A — history corruption.** A client pends and commits an action whose id is literally
`~proof:5` (at any revision below 5). It promotes into `transactions[block]["~proof:5"]`, and the
revisions store records that revision as being that action. Later the block commits revision 5 with
a proof; `saveBlockProof` writes to the same key and **overwrites the committed transform**. From
then on, reading that earlier revision returns a proof object where a transform is expected, so
materialising the block's history fails or produces wrong content on every node that took this path.

**Order B — silent loss of proofs.** The proof is written first, then a client action (or a restored
archive entry) with the colliding id overwrites it. The proof is gone with no signal; repair falls
back to corroboration as if the node had never retained one.

Order A is the serious one: it damages committed history, which the proof mechanism itself is
supposed to help protect.

Note that a *forged* proof is not among the consequences — `verifyBlockCommitProofClaim` is total on
hostile input and returns `malformed-proof` for a transform-shaped value. The damage is corruption
and denial, not false certification.

## What must change

The invariant to establish is: **a value written under a reserved key can only ever have come from
the proof-retention path.** Today the reservation is a naming convention in a comment; it needs to
be something the code enforces.

Two shapes are worth weighing; pick one and state why in the handoff.

1. **Guard the namespace at the untrusted seams.** Reject any externally-supplied action id in the
   reserved namespace at the boundaries where untrusted ids enter — `StorageRepo.pend` and
   `BlockStorage.saveRestored` at minimum. Cheap and local, but the guard must be placed with care:
   a blanket check inside `KvRawStorage.saveTransaction` would break the proof's own write path,
   because `CachedRawStorage` routes `saveBlockProof` through `RawStorageDriverAdapter.putTransaction`
   → `inner.saveTransaction` with the reserved key. Whoever does this must enumerate every writer of
   the transactions store and classify each as trusted or untrusted; a missed writer leaves the hole
   open.
2. **Stop sharing the keyspace.** Give proofs their own store on `RawStoreDriver`, so no key can be
   reached by both paths and the question cannot recur. Touches every backend that implements the
   driver, plus the conformance suite — the reason the shared-store approach was chosen originally.

Shape 1 is the smaller change; shape 2 is the one that makes the bad state unrepresentable rather
than merely rejected. Either is acceptable, but the choice should be deliberate rather than
defaulted to the cheaper one.

## Expected behaviour once fixed

- A client that pends an action whose id is `~proof:<n>` (or anything else in the reserved
  namespace) is rejected, and nothing is written — rather than being accepted and later silently
  overwritten.
- A `BlockArchive` restored from a peer that carries such an action id does not overwrite a stored
  proof.
- A block that has both committed revisions and retained proofs materialises every one of its
  revisions correctly, with no key able to serve both roles.

## Confirming the defect

It is inferred from reading the code, not observed. The test that would confirm it: pend and commit
an action with `actionId = '~proof:5'` on a block, then commit revision 5 of that block with a proof,
then read back the earlier revision — today it should fail to materialise (or return proof-shaped
content), and after the fix the first commit should never have been accepted.
