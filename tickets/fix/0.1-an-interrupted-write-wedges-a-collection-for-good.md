GitHub #54 (kjeib), read it with `gh issue view 54`: it carries the full repro script. Versions: optimystic 1.23.0, sereus cadre-core 1.20.0, Node 24, file storage. The reporter ran it; this repository has not reproduced it yet.

## What happens

1. A process on a one-machine group starts a write to `optimystic/schema`. The write's pending record (the first of a write's two steps) is saved.
2. The process calls `node.stop()` and exits 500 ms later while `stop()` is still running, the common `Promise.race([stop(), timeout])` shutdown. With a write in flight, `stop()` took 0.4–5.6 s in the report.
3. A new process opens the same files and writes to the same collection.

Result: the new write fails after 13–20 s with `SyncRetryExhaustedError: sync for collection optimystic/schema exhausted 10 retries`, in 8 of 8 reported runs, and on every later start. If `stop()` finishes, or the stores are closed without `stop()`, every interruption point resumes.

State on disk, as reported: the collection's root and log blocks are at revision 1 with `pendingRevs: { <dead action>: 2 }`. The new write also asks for revision 2, so `StorageRepo.pend` reads the old record as a live reservation and answers with a conflict. The transactor cancels its own attempt and reports stale, ten times. Nothing removes the old record: the stuck-reservation lines only name it, and owed cancels are kept in memory, so a restart forgets them.

## Expected

An interrupted write never makes a collection permanently unwritable. The reporter offers either of these, and either would do for them:

- (a) on start, discharge pending records whose writer was this node's previous run, at least when this node is the whole cohort;
- (b) make `stop()` finish or cancel in-flight writes promptly, or document that exiting before it resolves can wedge a collection.

(b) alone cannot be the whole answer, since a killed app never runs `stop()` to its end. The reporter's point stands that on a one-machine group the record is provably abandoned, or close to it: nothing but this node's own previous run could be the writer, unless a remote client was writing through this node.

## Relation to the backlog

`debt-unpromotable-pending-records-need-a-sweep` owns the general case (a writer that exits, on any cohort size) and records why guessing wrong is worse than the leak: deleting a live record costs a whole-block repair. This ticket is the narrower shape where the deciding facts are local. Do not try to close the general case here; leave what stays open as an arm on that ticket.

## Things the fix has to weigh

- **Offline restore.** `OfflineQueue.restore` re-drives journaled attempts under their old action id. A journaled in-doubt entry's own pending record must not be treated as garbage in a way that breaks the re-send, and a record it would re-pend should not block it either.
- **A remote writer.** A one-machine cohort can still be written to through the repo protocol by another process that has not restarted. Removing that writer's record makes its commit fail with a missing pend. Decide whether that is acceptable, since its retry re-pends.
- **A multi-member cohort.** A member restarting while its own coordinated write was in flight has the same record on other members, whose cancel needs consensus. Name what happens there, even if the answer is "unchanged, belongs to the debt ticket".
- **Own-action retry.** A record whose action id matches the incoming write already does not refuse it (`isOwnRevision`); a fresh write has a fresh id, so this does not help here.

If the architecture turns out to be silent on a question of consequence, route to `blocked/` with proposed text rather than guessing.
