# Review: commit content-digest check on the member side

## What landed

The transaction author already declares, on a commit request, what each block it touches will
contain once the action commits (`CommitRequest.blockDigests`, shipped by the earlier
`commit-cert-digest-threading` work). Until now nobody on the receiving side looked at that
declaration — it rode along inside the signature preimage and was otherwise inert.

This ticket makes cohort members *check* it. Two pieces:

**`StorageRepo.previewCommitDigest(blockId, actionId, rev)`**
(`packages/db-p2p/src/storage/storage-repo.ts:892`, just above `internalCommit`) — returns
`CommitDigestPreview = { digest?, baseRev?, baseIndependent }`: the digest this node's own pended
transform would materialize, plus the base revision it was computed against. It mirrors
`internalCommit`'s read sequence (pending transform → `latest` → base → `applyTransform`) so
prediction and eventual commit cannot drift, and is strictly read-only: no durable writes, no
commit latch, both base and transform `structuredClone`d before `applyTransform` (which otherwise
assigns `transform.insert` by reference and mutates in place).

**`ClusterMember.validateCommitOperations(record)`**
(`packages/db-p2p/src/cluster/cluster-repo.ts:1260`, just above `handleCommitNeeded`) — runs on the
promise round, chained after `validatePendOperations` in `evaluatePromise` (line ~955). Iterates
`{ commit }` operations, and for each declared block id compares `previewCommitDigest` against the
declaration. Mismatch → the whole record votes reject with the new exported reason
`CONTENT_DIGEST_MISMATCH = 'content-digest-mismatch'` (line 149, beside `MEMBERSHIP_NOT_ADMITTED`).

## The rule the reviewer should attack

A member cannot always check, and voting reject when it merely *cannot tell* would break honest
commits. `StorageRepo.commit` accepts any request where `latest.rev < request.rev` (not only
`request.rev - 1`), so a lagging member legitimately materializes different bytes from an
update-only transform. The checkable/abstain rule is keyed on the **member's own pended transform**,
never on the declaration:

| Member's pended transform for the id | Behaviour |
|---|---|
| carries an `insert` (with or without updates) | base-independent — always check; declared `baseRev` ignored entirely |
| `updates` only | check iff local `latest.rev` equals the declared `baseRev`; else abstain |
| `delete` only / no base / unmaterializable base | materializes nothing → abstain |
| no pending transform for the action | never saw the pend → abstain |
| repo without a `previewCommitDigest` method | abstain everywhere (duck-typed probe) |
| declared id not in `commit.blockIds` | surplus/hostile entry — ignored, even when it mismatches |
| `previewCommitDigest` throws | logged, abstain — never escapes the vote path |

"Abstain" means: vote exactly as before this check existed. Because base-independence is decided by
the member's transform and not by the declaration, a hostile declarer can neither *force* a check
(claiming a base the member does not hold) nor *dodge* one (omitting `baseRev` on an insert).

**The promise-round placement is load-bearing, not incidental.** The commit-round vote is cast
deliberately blind — `getTransactionPhase` signs the commit as soon as promise approvals reach
super-majority, regardless of this member's own promise vote. Promise approvals are therefore the
only votes that can carry "I checked this content". Moving the check to the commit round would make
it decorative. Worth confirming that reading of `getTransactionPhase` independently.

## Tests

- `packages/db-p2p/test/cluster-commit-digest.spec.ts` (NEW, 14 tests) — the abstain matrix above,
  the checkable paths (update match + mismatch, base-independent ignoring the declared `baseRev` in
  both directions), and a pair seeded through a real `StorageRepo` via `pend` (match approves,
  tampered declaration rejects with the signed reason). Harness mirrors
  `cluster-membership-admission.spec.ts`: v1 record, two declared peers so consensus never executes,
  vote read out of `record.promises[self]`, `member.dispose()` in a `finally`.
- `packages/db-p2p/test/storage-repo.spec.ts` — trailing `describe('previewCommitDigest')`
  (8 tests). The load-bearing ones assert the preview equals what `commit` **actually stores**
  afterwards (insert and update), so the two paths cannot silently diverge. Also: no-pend →
  `undefined`; updates-with-no-base and delete → defined preview with `digest: undefined`; a wedged
  (unmaterializable) base yields `digest: undefined` **without** deleting the pending record (unlike
  the commit path's `refuseMissingBase`); an insert previews cleanly even on a wedged block.

Verbose runs of both files were confirmed green individually, and root
`yarn build && yarn typecheck && yarn test` is clean (2038 passing in db-p2p, no failures anywhere
in the workspace).

One assertion was corrected during validation and deserves a second look: the delete test originally
asserted `repo.get(...).state.latest.rev === 2` after the tombstone commit, which fails — `get`
returns an **empty** `state` for a tombstone (the `!blockRev` branch, `storage-repo.ts:356`), by
design, as an authoritative absent. The test now reads `latest` from `BlockStorage` directly and
additionally asserts the entry carries no `unavailable` flag. Confirm that is the intended contract
and not a latent gap in `get`.

## Gaps and things to push on

- **An approval does not say whether it was a checked approval.** A member that verified content and
  a member that abstained emit byte-identical approvals. Nothing downstream can count how many
  approvals were content-attesting, so the guarantee is "some honest caught-up member would have
  rejected", not "N members vouched for these bytes". Making that countable and durable is
  `persist-block-commit-proof` (`tickets/implement/2-persist-block-commit-proof.md`, which declares
  this ticket as its prereq) — **explicitly out of scope here**.
- **Residual attack surface.** A false declaration commits only if the declarer lies *and* enough of
  the cohort is simultaneously unable to check (lagging on update-only blocks, missed pends) that no
  honest checker remains. Any single caught-up honest member rejects. Reviewer should sanity-check
  that this is genuinely stronger than the prior state (commit signatures bound no content at all)
  and that no path was made *weaker*.
- **The capability probe is duck-typed** (`typeof repo.previewCommitDigest !== 'function'`). Today
  `ClusterMember.storageRepo` is typed `IRepo` and the only production construction passes the local
  `StorageRepo`, so the probe hits. But a decorating/caching repo inserted at that seam later would
  silently disable the check with no signal. Worth deciding whether that should log, or whether the
  seam should be typed instead of probed.
- **Preview runs latch-free**, so a concurrent commit can move `latest` mid-preview. The argument is
  that the checkable rule degrades a torn read to an abstain rather than a false reject — that
  reasoning is documented at the method but is **not** exercised by a concurrency test.
- **Single-peer fast path is unchecked by construction**: with no cohort there is no promise round,
  so `StorageRepo.commit` accepts `blockDigests` and simply ignores them. Covered only to the extent
  that one storage-repo test asserts the request shape is accepted. Flagging it as a real (and
  arguably acceptable) hole rather than an oversight.
- **Tests are unit-level.** The cluster spec deliberately parks the record in the Promising phase
  with two declared peers so consensus never executes; no test drives a real multi-peer cohort to a
  rejected commit end to end.
- **Deletes are never checkable.** Symmetric on both sides today — `computeBlockContentDigests`
  (`packages/db-core/src/transform/digest.ts:26`) skips a block whose `peekMaterialized` yields
  nothing, so honest producers emit no digest for a delete — but a hostile producer *could* declare
  one and no member would reject it. Since a committed delete materializes nothing there is no
  content to forge; worth confirming that reasoning holds.
