# Storage drivers can carry values as text — review handoff

GitHub #51, first of two tickets. The follow-on, `react-native-reads-decode-utf8-in-native-code` (in `plan/`), puts the React Native LevelDB backend on this.

## What was built

How a driver holds a stored value in memory is now a type parameter, bytes by default at every seam:

- `raw-store-codec.ts` gains `StoredValue` (`Uint8Array | string`), `ValueCodec<V>` (JSON and action-id encode/decode, plus `storedBytes`, `residentBytes`, `toBytes`), `bytesValueCodec` (today's free functions; sizes are the byte length; `toBytes` is the identity) and `textValueCodec` (`JSON.stringify` / `JSON.parse`, action id as-is, `storedBytes` = UTF-16 length, `residentBytes` = length × 2, `toBytes` = the module's `TextEncoder`; never builds a `TextDecoder`). Also `ValueCodecArgument<V>`, a conditional rest-parameter tuple that makes the codec optional only when `V` is bytes, and `resolveValueCodec`, which reads it (the one cast lives there). The free functions stay; the journal record codec and `RawStorageDriverAdapter` still use them. The module is now exported from `src/index.ts` and `src/rn.ts`.
- `RawStoreDriver<V>`: every value position is `V`.
- `KvRawStorage<V>(driver, ...codec)`: every encode/decode goes through the codec. `new KvRawStorage(bytesDriver)` is unchanged; a text driver without its codec fails to compile.
- `CachedStoreDriver<V>(inner, pool?, label?, ...codec)`: caches `V`, charges `residentBytes` at every site that charged `.length`, and `promote`'s `instanceof Uint8Array` test is now "a value is present" (not `undefined`, not `null`). The old test would have sent every text value down the invalidate branch.
- `WriteGroup<K, V>`: overlay, entries and sink are `V`. `WriteGroupOptions` stays the non-generic pacing options (so the three KV stores' option types did not change); the new `WriteGroupValueOptions<V>` adds `storedBytes`, which defaults to the byte length for bytes and is required (by `WriteGroupOptionsArgument<V>`) for any other `V`.
- `WriteGroupDriver<V>(backend, options?, ...codec)`: overlay holds `V`; the sink it hands its group (`toBytesSink`) maps every value through `codec.toBytes` before `backend.commit`. `promote` moves the read value unconverted.
- `BatchBackend<R>`, `JournalStore<R>`, `JournalBatchBackend<R>`: only the reads (`get`, `rangeRevisions`) return `R`; writes, `BatchEntry` and journal records stay bytes. The `NOTE:` at `JournalBatchBackend.held` now says the byte sharing holds for bytes compositions only.
- `MemoryStoreDriver`, `RawStorageDriverAdapter`, `CachedRawStorage`, `withReadCache`, and every backend package: unchanged.
- Docs: `packages/db-p2p/docs/storage.md` §5 (representation is a type parameter; the codec; text becomes bytes in one place; why strings are not handed to the engine) and §6 (the cache holds `V`, charged at `residentBytes`), the memory-management bullet in the same file, and the kernel paragraph of docs/internals.md *Storage Returns References*.

## Test added

- `test/journal-batch-backend.spec.ts`: one `runRawStorageConformance` registration, persistent, over `KvRawStorage<string>` → `CachedStoreDriver<string>` (own `SharedCachePool`) → `WriteGroupDriver<string>` → `JournalBatchBackend<string>` → `TextReadsJournalStore` → `MemoryJournalStore`. It runs the whole suite over a text composition, including clone-on-read, drain-before-yield, promote, and flush-then-reopen through the cache and the overlay. `TextReadsJournalStore` (new, `src/testing/text-reads-journal-store.ts`, not exported from the testing entry) is a test double whose reads decode the wrapped store's bytes with Node's `TextDecoder`.

## Where this differs from the ticket — check these

- **One registration, not two.** The ticket asked for the text conformance at both `'power-loss'` and a lower durability, so that both the journaled path and the apply-at-once path would run. Every flush the conformance suite makes is strict (and so is the write group's idle flush), so `JournalBatchBackend` applies at commit at any durability, and nothing in the suite or `StorageRepo` branches on durability. A second registration would run the same path again. The relaxed, journaled path is not exercised over text by any test. What would differ there, that a journal record holds bytes, is enforced by `BatchEntry`'s type. If you want the relaxed path run over text anyway, the cheap test is: a relaxed flush on a text composition at `'power-loss'`, then a fresh composition over the same store reads the value back.
- **The `promote` fix is not pinned by a test.** The conformance case "promotePendingTransaction moves pending → committed atomically" passes with or without the fix, because the old branch invalidates the committed entry (a correct read through the cache, just uncached). The fix only restores the cache hit. Verified by inspection.
- **"Omitting the codec for a text driver does not compile" was verified, not pinned.** A temporary `@ts-expect-error` probe (deleted) confirmed that each of these fails to compile: a text `WriteGroupDriver`, `KvRawStorage` or `CachedStoreDriver` with no codec; `bytesValueCodec` over a text driver; a bytes driver under a text cache; and a `WriteGroup<string, string>` with no `storedBytes`. The bytes forms still compile with no codec. The ticket said no test was needed. `test/key-tuple-types.spec.ts` is the precedent if you want this kept as a type test.
- **Bytes compositions now allocate per commit.** `toBytesSink` maps every sealed group to new entry objects even when `toBytes` is the identity (the `Uint8Array` values are shared). Behaviour is unchanged and all suites pass. It costs one array of small objects per commit.
- **Public surface.** Exporting `raw-store-codec.ts` also publishes the existing `encodeJson`, `decodeJson`, `encodeActionId`, `decodeActionId` and `cloneDecoded`, not only the new names.
- **Cache constructor shape.** The codec comes after `pool` and `label`, so a text cache reads `new CachedStoreDriver(driver, pool, label, textValueCodec)`. The follow-on ticket's composition sketch leaves out the cache's codec, which would not compile.
- **Duplicate constant.** `textValueCodec.residentBytes` uses its own `UTF16_UNIT_BYTES = 2`, which matches `CHAR_BYTES` in `cached-store-driver.ts`. Neither is exported.

## Use cases for the reviewer

- A text composition (`KvRawStorage<string>` over `CachedStoreDriver<string>` over `WriteGroupDriver<string>` over a backend whose reads return text) behaves like every bytes backend; the conformance registration above shows it.
- A cache or overlay hit on a text composition returns the held string, and the kernel's `decodeJson` (`JSON.parse`) is the only codec call. Check by reading `KvRawStorage`, `CachedStoreDriver.get*` and `WriteGroupDriver.read`.
- What a text composition persists is `TextEncoder` output, byte-identical to the bytes path, so data earlier releases wrote reads unchanged. `toBytesSink` is the only conversion site.
- Pool accounting: every value charge in `cached-store-driver.ts` goes through `codec.residentBytes` (`cachePoint` and `revisionCharge`). The remaining `.length` uses are keys, ids and coverage intervals.
