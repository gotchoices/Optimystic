# What landed

Two additions to the db-p2p blob services, both for the SQL plugin's blob work (`feat-blob-sql-type-and-blob-service`) and neither specific to it. No production code calls either one yet — that plugin is their first caller — so judge the shapes against the interfaces `tickets/implement/2.702-feat-blob-sql-type-and-blob-service.md` declares it will use.

## The pin index (`packages/db-p2p/src/blob/local-blob-service.ts`)

`BlobPinIndex` is declared beside `BlobFetchStore` and `BlobOwedRecords`, with `pinsOf(ref)` and `listPins(ownerPrefix)`. `LocalBlobService implements BlobService, BlobOwedRecords, BlobPinIndex`, so drift is a compile error, and both methods answer from its `BlobRecordStore`:

- `pinsOf` reads through the existing private `readableRecord`, so an absent or undecodable record answers `[]` — the rule `durabilityOf`, `holdsWhole` and `responsibleRefs` already apply.
- `listPins` walks `BlobRecordStore.listRefs`, reads each record through `readableRecord` (an unreadable one is logged `record:unreadable` and skipped, as in `responsibleRefs`) and yields each `pin` hold whose owner starts with the prefix. An empty prefix lists every pin.

Both share one new module-level helper, `pinOwnersOf`, written with `flatMap` rather than `filter` so the hold's kind narrows to the variant carrying an owner — the alternative is a type-predicate callback, which is more ceremony for the same thing.

`NodeBlobService implements BlobService, BlobPinIndex` and forwards both to `this.local`, the way `pin` and `unpin` already do, so `node.blobs` satisfies `BlobService & BlobPinIndex` too.

**Asked for in the ticket and confirmed by inspection:** `LocalBlobService.pin` does create a record for a reference this machine holds nothing of. `pin` calls `changeRecord(ref, current => recordAfterPin(current, ref, owner, at))`, and `recordAfterPin` with `current === undefined` returns a fresh record `{ v: 1, ref, whole: false, holds: [the pin] }`. That is what lets a transaction pin a reference it copied out of another row whose bytes are elsewhere. Nothing was changed for it.

## `SingleMachineBlobService` (`packages/db-p2p/src/blob/single-machine-blob-service.ts`)

A `BlobService & BlobPinIndex` whose cohort is this machine alone, **by composition** over a `LocalBlobService` it constructs from `{ pieces, kv, digest?, now? }` — so it rests only on that class's public surface, which already carries everything it needs. Every member but `announce` is a one-line delegation (`read` returns the local service's iterable), plus `start`/`stop` forwarding the sweep lifecycle. The `digest` default is not re-applied here: it is passed through and `LocalBlobService` applies `defaultBlobDigest()`, so there is one copy of the default.

`announce(ref, scope)` is the only behaviour of its own, in the order the ticket specifies:

- `blobScopeProblem` and a `RangeError` naming the problem — the same refusal `NodeBlobService.announce` makes, so a recorded scope is always one a networked node could send.
- `local.holdOwed(ref)` — creates the record when there is none and flushes, so the blob survives a restart with a hold no sweep removes.
- A stored `durabilityOf` means this is a re-announce: stop, emitting nothing.
- Otherwise the class `{ quorum: 'local', accepting: 1, unconfirmed: [], confirmed: holdsWhole ? 1 : 0 }`, then `setDurability` and `emitDurability` in that order, so a listener never sees a class the record does not yet hold. Then one `blob:announce-single-machine ref=… scope=…` line on the `blob:store` namespace.

Nothing here ever releases the `owed` hold — there is nobody to copy to — so it is released only by reclaiming (`feat-unreferenced-blobs-are-reclaimed`), exactly as that work releases a networked node's owed entry whose cohort never fully holds the blob.

### One deviation from the ticket's letter, deliberate

The ticket says to export the new module from `packages/db-p2p/src/index.ts`. It is exported from **`packages/db-p2p/src/rn.ts` as well**, because `packages/db-p2p/test/entry-parity.spec.ts` requires the two entries to re-export an identical module set (its `NODE_ONLY` map is empty by design) — index-only would have failed that spec. The module is safe on that entry by construction: its imports are a subset of what `local-blob-service.ts` already imports, and that module is on the RN entry today. `entry-parity.spec.ts` passes, including its "reaches no Node builtin from the React Native entry" source walk. `yarn check:rn` was **not** run here, per `tickets/rules/testing.md`.

## Tripwires parked in the code

- `listPins` in `packages/db-p2p/src/blob/local-blob-service.ts`: scans every blob record; if a machine ever holds enough blobs for a prefix query to show up, index pins by owner prefix — the same tripwire `responsibleRefs` carries.
- `announce` in `packages/db-p2p/src/blob/single-machine-blob-service.ts`: `confirmed` is computed once and never recomputed, so a reference announced before its bytes arrived stays `confirmed: 0`; nothing on a single machine can make an incompletely held blob whole.

**No spec for `pinsOf` / `listPins`** — the implement ticket's call, on the grounds that they are a projection of `BlobRecord.holds` whose only non-obvious branch, the unreadable-record skip, the existing readers already share, and that `feat-blob-sql-type-and-blob-service`'s pin-label spec reads its pins back through `pinsOf`. # Known gaps and things to look at

- **No production caller.** `SingleMachineBlobService` and `BlobPinIndex` are exported and used only by the new spec. The node still builds `NodeBlobService`; nothing was wired to choose between them. That wiring is `feat-blob-sql-type-and-blob-service`'s.
- **`LocalBlobService.announce` still rejects** with "not built yet (feat-blob-owed-copies-are-drained)" — untouched, as it should be: the single-machine service does not delegate `announce`.
- **`SingleMachineBlobServiceInit` has no `sweepDelayMs` or `setTimer`,** exactly as the ticket specifies, so a test of this class cannot disarm the sweep timer the way `local-blob-service.spec.ts` does. It did not matter here — nothing in either case schedules a sweep, and `armUnrefTimer` is unref'd, so a stray timer holds nothing open — but a future spec that deletes a record through this service will want them.
- **`read` and `fetch` on a machine with no cohort report `cohort-unreachable`** for a piece that is not here, inherited from `LocalBlobService`. That reads correctly for a host with no node, since there is no cohort, but it is a reason string chosen for a different caller; worth a reviewer's opinion on whether `not-here` would serve a single-machine host better. Unchanged here.
- **Differing durability between the piece store and the record store is still undetectable** — a persistent piece store over in-memory records loses every pin at restart, and the reverse reports blobs it cannot serve, which `stat` corrects. The implement ticket parks this on the caller's option in `feat-blob-sql-type-and-blob-service` rather than checking it here; nothing was added for it.
- **Docs.** `docs/blobs.md` §The node's blob service gained a paragraph for `SingleMachineBlobService` — what it is for, that its durability stays `local`, and that its `owed` hold is released only by reclaiming — and its status line now reads "on a node, `announce` rejects…"; §Holds gained a sentence on pins being readable back by owner. `docs/debugging.md`'s `blob:store` row names `SingleMachineBlobService` and the `blob:announce-single-machine` tag.
