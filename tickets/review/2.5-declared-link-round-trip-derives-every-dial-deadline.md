# One declared link round trip, every dial deadline derived from it — review handoff

## What was built

`NodeOptions.linkRoundTripMs?: number` — the slowest round trip, in milliseconds, between any two nodes that will talk to each other, relayed hops included. `createLibp2pNodeBase` resolves it once, as its very first statement (before storage is acquired, so an invalid value throws with nothing to release), with `resolveLinkDeadlines` in `rpc-deadline.ts`:

| field of `LinkDeadlines` | derivation (`r` = round trip) | undeclared |
| --- | --- | --- |
| `dialTimeoutMs` | `max(3000, 6r)` | 3000 |
| `responseTimeoutMs` | `max(10000, 3r)` | 10000 |
| `connectionTimeoutMs` (libp2p `dialTimeout` and `inboundUpgradeTimeout`) | `max(10000, 5r)` | 10000 |
| `cohortQueryTimeoutMs` (fills an undeclared `clusterPolicy.cohortQueryTimeoutMs`) | `max(1000, 3r)` | 1000 |
| `transferTimeoutMs` (`BlockTransferCoordinator`) | `max(30000, dialTimeoutMs)` | 30000 |

Undeclared resolves to exactly the constants in force before (the resolver sets `r = 0`, so every `max` lands on its floor). Explicit per-deadline settings still win: `connectionManager.*`, `spreadOnChurn.push*`, `underReplicationDrain.push*`, `clusterPolicy.cohortQueryTimeoutMs`, and a caller's own `dialTimeoutMs`.

Where the resolved values go:

- `ProtocolClient` now carries `rpcDeadlines` (defaulting to `UNDECLARED_RPC_DEADLINES`). `ClusterClient`, `SyncClient` and `DisputeClient` merge caller options against the instance's values, not module constants; `ClusterClient`'s redirect hop passes its own values on; `DisputeClient.sendChallenge`'s hard-coded dial deadline is now the instance's.
- Node base: `createClusterClient`, `createDisputeClient`, both `SyncClient`s it builds, `RestorationCoordinator` (new optional fifth constructor parameter), the drain's `pushBlockToPeers` defaults, `SpreadOnChurnMonitor`'s `push*` defaults (derived values spread first, `options.spreadOnChurn` over them), `BlockTransferCoordinator`'s `transferTimeoutMs`, the libp2p `connectionManager` block, and `withLinkDerivedCohortBudget` before `resolveClusterPolicy`.
- `OptimysticNodeAttachments.linkDeadlines` exposes the resolved object.
- Quereus plugin: `NetworkTransactor.dialTimeoutMs` is `node.linkDeadlines?.dialTimeoutMs ?? DEFAULT_DIAL_TIMEOUT_MS` (a host-injected node without the attachment keeps 3000), and the node it builds gets `linkRoundTripMs` from `libp2pOptions`. The `NOTE:` tripwire sits at `timeoutMs: 30_000`.

## Decisions the reviewer should check (deviations from the ticket text)

- **Ceiling is `MAX_COHORT_QUERY_TIMEOUT_MS / 3`, not "where 6r overflows".** The largest delay derived from `r` is the reconcile pass bound on the derived cohort budget: `5 × 3r = 15r`. Bounding by that makes every derived delay fit a 32-bit timer and makes the filled cohort budget pass `resolveCohortQueryTimeoutMs`'s own ceiling by construction. `MAX_LINK_ROUND_TRIP_MS` = 143165576 ms (about 1.66 days).
- **`RepoClient` is unchanged.** It has no client-level fallback: its dial deadline comes entirely from the caller's `MessageOptions.dialTimeoutMs`, and `NetworkTransactor` passes `undefined` to mean "no cap" (for a non-positive `dialTimeoutMs`). A fallback there would turn that "no cap" into a cap. The redirect hop re-sends the caller's options unchanged, so it already carries whatever the transactor supplies (now the derived value in the plugin and the reference peer). Nothing in it read a module constant.
- **`ClusterMember.propagateIfNeeded` was threaded too** (not listed in the ticket). It re-sends a member's reject on an expired transaction with `ClusterClient.create` and the fixed defaults; it now uses a `createClusterClient` component, which the node passes as the same factory the coordinator uses. Absent → the old `ClusterClient.create`.
- **libp2p `dialTimeout` is now always passed** (10_000 undeclared, equal to libp2p's `DIAL_TIMEOUT`), where before it was omitted when undeclared. Same effective value; matches how `inboundUpgradeTimeout` was already handled.
- **Plugin-level setting `link_round_trip_ms`** added (package.json `quereus.settings`, README table, `declaredLinkRoundTripMs` in `optimystic-module.ts`). Without it the ticket's "pass through from `libp2pOptions`" was unreachable: `resolveBinding` rebuilds `libp2pOptions` from table args and plugin config only. It is plugin-level, not a table argument, because it configures the node that every table on one network and port shares, so `SESSION_BINDING_VTAB_ARGS` is untouched. A non-number value throws; a bad number is refused by the node.
- **Reference peer** (`packages/reference-peer/src/cli.ts`) builds its `NetworkTransactor` the same way the plugin did; switched it to `node.linkDeadlines.dialTimeoutMs`. It exposes no CLI flag for the round trip — out of scope.

## Known gaps — not threaded, left for the reviewer to judge

- `DEFAULT_SIGN_COLLECT_TIMEOUT_MS` (5000) in `cohort-topic/threshold-crypto.ts`: collecting threshold signatures from cohort members over the network. On a 3 s link a fresh dial plus negotiation plus request does not fit. Cohort-topic is opt-in (default off). Worth either a ticket or a tripwire; I did neither, since the ticket named its sites and this one has its own config path.
- `DEFAULT_RELAY_DRIVE_TIMEOUT_MS` (10000) in `network/relay-reservation.ts`: a direct dial to the relay, not a relayed hop, so the declaration (which covers relayed round trips) does not obviously apply.
- libp2p's `PROTOCOL_NEGOTIATION_TIMEOUT` (10 s) is not configured; negotiation is one round trip, so it fits up to a 10 s round trip.
- `RepoClient`'s `options.expiration ?? now + 30_000` only applies when a caller passes no expiration; `NetworkTransactor` always passes one.
- The `mesh-harness.ts` test transactor keeps its own values.

## Tests

- `packages/db-p2p/test/link-deadlines.spec.ts` (new) — pins the resolver's specification: undeclared equals the pre-existing constants; a fast `r` (300) changes nothing; `r = 3000` gives 18000 / 10000 / 15000 / 9000 / 30000; the transfer deadline follows the dial once the dial passes 30 s (`r = 10000`); `0`, `-1`, `NaN`, `Infinity` and `MAX + 1` throw; the ceiling itself is accepted and every derived delay there (including `5 ×` the cohort budget) fits a 32-bit timer.
- No wiring tests, per the ticket. The existing `connection-timeouts-node-wiring.spec.ts` still covers `connectionManager` reaching libp2p, and `rpc-response-deadline.spec.ts` covers the clients' fallback behaviour on undeclared defaults.

## Use cases to exercise in review

- A node built with `linkRoundTripMs: 3000`: `node.linkDeadlines` reads 18000 / 10000 / 15000 / 9000 / 30000, and the node's resolved `cohortQueryTimeoutMs` (and so `reconcilePassTimeoutMs` = 45000) follows.
- The same node with `clusterPolicy.cohortQueryTimeoutMs: 2000`: the declared 2000 wins.
- The same node with `connectionManager: { dialTimeout: 20_000 }`: libp2p gets 20000 for `dialTimeout` and 15000 for `inboundUpgradeTimeout`.
- `linkRoundTripMs: 0` or a string passed through the plugin's `link_round_trip_ms`: node construction (or table binding) throws.
