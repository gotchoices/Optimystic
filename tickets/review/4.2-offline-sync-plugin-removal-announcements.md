Second of the five stage-4 tickets of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). Two things: a failed queued transaction now wakes `Database.watch` subscribers on the tables its removal changed, and the SQL-level rules for a rollback that runs while the drain changes the sealed segments are pinned on a two-node mesh. No db-core change: the rollback rules held as stage 2 built them.

## What landed

- **The announcement.** `OfflineMode` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`) now takes the `Database` (`register` passes it; the parameter was `_db`). In `onQueueStatus`, after a `failed` status has been delivered to every `onStatus` listener, `announceRemoval` calls `Database.notifyExternalChange(table, schema)` once per distinct table behind the status's `changedCollections`. `committed` and `partially-committed` announce nothing. A cascade announces once per failed entry, so a table two cascading entries wrote is announced twice (one extra re-query for a watcher; accepted by the ticket's design). A failure is logged `offline:announce-failed` and never thrown into the drain.
- **One error-isolating helper for both callers.** `announceExternalChange` in the new `optimystic-adapter/external-change.ts`: fire-and-forget, a synchronous throw and a rejection both go to the caller's `onError`. The vtab's `handleCollectionChange` now uses it too; its two WARN log lines ("failed" / "threw") collapsed into one "failed" line. `reactive-watch.spec.ts`'s throw-and-reject isolation case still passes over it.
- **Structured table names in the bridge.** `TransactionBridge.collectionTables` is now `Map<CollectionId, Map<string, QualifiedTableName>>`, keyed by the `schema.table` rendering with the pair beside it, so nothing splits a name on a dot. `registerCollection` and `forgetTable` take a `QualifiedTableName` (the vtab's `qualifiedName` getter became `qualifiedTable`); `tablesOf` returns the map; the commit report reads its keys. The rendering is `qualifiedTableName` in `schema/table-identity.ts`, beside the existing `QualifiedTableName` type.
- **Harness.** `MockMeshOptions` in `test/mesh-node-harness.ts` passes `wrapRepo` through to the mesh transactors; `openFreshTree` was extracted from `readTree` so the new spec can read a committed log.
- **Docs.** README §Offline mode: a paragraph "What a watcher sees when a transaction fails", the "not yet" bullet removed, "first two plugin stages". docs/offline-sync.md §Removing an entry step 4 cites the helper and the controller and states the ordering and the cascade double-announce; §Implementation stages marks this part of stage 4 done. docs/internals.md §Reactive Watch Bridge gets one bullet. docs/debugging.md lists `offline:announce-failed`.

## Tests added — `test/offline-mode-removal.spec.ts`

Two-node in-process mesh. Each node coordinates its own writes, so a gate on the pends node A's repo receives (`CommitGate` from `test/commit-gate.ts`, wrapped by `parkingPends`) holds the drain's submission mid-flight while node B writes and node A runs SQL; releasing it is the reconnect. `parkPends()` arms a fresh gate, so a second submission can be held after the first is released.

- **Rival primary key.** A queues an insert of key 1 (held in flight), then an update of it; B inserts key 1; a live read on A before the release already shows B's row (the read's replay refuses both queued entries); after release the insert fails `constraint` with a `ConstraintError` reading `UNIQUE constraint failed`, no `causedBy`; the update fails `concurrent-modification` with a `ConcurrentModificationError` and `causedBy` = the insert; both statuses carry `tables` / `changedTables` `['main.Notes']`; a `db.watch` registered after A's local commits wakes, and only after the `failed` status. Verified to fail (watcher wait times out) with the announcement line removed.
- **Concurrent modification.** A queues an update of a committed row, B changes the row, release: `failed` / `concurrent-modification` / `ConcurrentModificationError`, A reads B's value. No reader on A before release here, so the refusal is found by the submission's own refresh — the other path from the rival case.
- **Rollback while the drain commits.** Two entries queued, the first held; `begin` + insert on A (snapshot taken with both sealed); first released and committed, second held; `rollback`. A reads seed + both queued rows and not the rolled-back one; after the drain and a network-acknowledged insert, B holds exactly 4 rows and its log 4 action entries (seed, two queued, online), and each entry was reported `committed` once, in order. The second queued entry is what makes this case pin the replay arm: with only one entry, the pre-segment rule (boundary moved, empty snapshot → reset) gives the right answer too.
- **Savepoint rollback after a refused entry was removed.** A queues an insert of key 1 (held), opens a transaction, inserts row 7, `savepoint sp1`, inserts row 8 (the savepoint snapshot is taken with the insert still sealed); B inserts key 1; release; the entry fails `constraint`; `rollback to sp1` → A reads B's row 1 and row 7, row 8 gone; `commit` queues row 7, which lands on B.

**Mutation checks run during implement** (db-core source restored and rebuilt afterwards; `git diff packages/db-core` empty): removing `restorePending`'s replay arm fails both rollback cases; forcing the verbatim arm always fails the savepoint case only — in the transaction-level case the verbatim restore's base pins make A's read correct and the next head commit's replay rebuilds the tracker, so nothing stale reaches the network.

## Deviations, each deliberate

- **The queue is not exposed on the controller.** The ticket asked for an `offline.queue` test seam; the spec needed only the controller's own `submitting`/`queued` statuses and the pend gate, so an unused public accessor would have been dead API. Add it if a later spec needs raw collection-level statuses.
- **"A statement in progress" is modelled with an explicit user `savepoint`.** Holding a statement mid-execution is not practical from a spec; explicit and statement-level savepoints go through the same `TransactionBridge.rollbackToSavepoint` → `restorePending` path.
- **The "refusal found by a reader's refresh before the drain" edge case is exercised with the head in flight**, not with the drain idle between iterations. The refresh refuses the in-flight insert (thrown by its submission on release) and the queued update (failed from the queue's pending refusals at the drain's next step, which is the "next iteration" path). Holding the drain idle instead (cutting B off for write rounds) was not used: every unanswered attempt leaves a reservation in A's cluster member until its staleness sweep, so B's rival write contends with A's re-tries. The idle-drain path is pinned in db-core (`offline-queue.spec.ts`, "a refusal a reader's refresh found before the drain did").
