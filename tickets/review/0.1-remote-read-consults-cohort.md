# A repo-protocol read now reaches the cohort consult

## What changed

One line, `packages/db-p2p/src/repo/service.ts:264`:

```diff
-					response = await this.repo.get(operation.get, { expiration: message.expiration, skipClusterFetch: true } as any)
+					response = await this.repo.get(operation.get, { expiration: message.expiration } as any)
```

Before: every block read arriving over the repo protocol (i.e. every read from a *remote*
peer — the normal case once a party has more than one machine) told `CoordinatorRepo.get`
to skip consulting cohort peers. A coordinator holding nothing locally would answer a bare
`{ state: {} }` — an *authoritative* absence, not flagged `unavailable` — for a block that a
cohort peer actually held. `NetworkTransactor.get` treats an unflagged absence as final and
does not retry it elsewhere. Downstream, `Collection.updateInternal` sees "I hold committed
revision N, but the header block reads as absent" and throws `CollectionHeaderVanishedError`
— permanently, since nothing about the coordinator's local state ever changes.

After: the same read reaches `CoordinatorRepo.get`'s existing cohort-consult path. On a
local miss it asks cohort peers before answering. If the cohort corroborates a revision this
node can't yet acquire, or stays partially silent, the response now carries
`unavailable: 'peers-unreachable'` so the transactor retries against a different peer instead
of accepting a false absence.

**Confirmed this does not recurse.** The consult reaches cohort peers over the **sync**
protocol only (`clusterLatestCallback` → `SyncClient.requestBlock`, and
`acquireBlockFromCohort` → `fetchArchiveFromPeer` → `SyncClient.requestBlock`, both in
`libp2p-node-base.ts`). Both land on `SyncService`, whose handler
(`sync/service.ts:160`) still calls `repo.get(..., { skipClusterFetch: true })` — that flag,
**left untouched**, is what terminates the chain: `A --repo--> B.get (miss) --sync--> A.get
(skip) -> answer`. Verified by reading both hop sites, not just asserted, and pinned by the
third new spec test ("a cluster-internal sync read still skips the consult").

Checked the surrounding comment blocks (`service.ts:252-259`, `coordinator-repo.ts:317-336`)
for staleness — both still describe the code accurately (the skip is now solely
"is this a sync request", which is exactly what remains true), so neither was touched.

## Regression test — `packages/db-p2p/test/repo-service-remote-get-consult.spec.ts`

Three specs, all against a real `RepoService.handleIncomingStream` driven with an encoded
wire message (not a mocked handler) and a `CoordinatorRepo` wired to a 2-peer cluster where
the local node holds nothing and a cohort peer corroborates rev 2 but cannot be acquired
(no `acquireBlockFromCohort` wired — the consult is deliberately left inconclusive):

1. **`does not answer a bare authoritative absent for a block the cohort holds`** — asserts
   the response carries `unavailable: 'peers-unreachable'`, not a bare `{ state: {} }`. This
   is the test that catches the original bug directly.
2. **`a repo-protocol get reaches the cohort consult`** — asserts more than one call reached
   local storage (the consult does a local read, fetches, then re-reads), proving the
   consult path actually ran rather than being skipped.
3. **`a cluster-internal sync read still skips the consult (no recursion)`** — calls
   `CoordinatorRepo.get` directly with `skipClusterFetch: true` (what `sync/service.ts:160`
   still passes) and asserts exactly one storage call and no `unavailable` flag — pins that
   the recursion-guard leg is untouched.

Run in isolation (`node --import ./register.mjs node_modules/mocha/bin/mocha.js
"test/repo-service-remote-get-consult.spec.ts" --reporter spec`): all 3 pass.

## Known gap — stale comment, deliberately not touched

## Cost / risk profile, for the reviewer's context

A repo-protocol read for a block the answering coordinator doesn't hold now costs one cohort
consult, bounded by `LATEST_QUERY_TIMEOUT_MS` (1000 ms, `coordinator-repo.ts:31`) run in
parallel across peers, plus `acquireBlockFromCohort`'s own 1000 ms per-peer race
(`libp2p-node-base.ts:723-726`). A read that hits locally pays nothing — unchanged. There's a
standing NOTE at `coordinator-repo.ts:663` (pre-existing, not touched by this ticket) that
those two budgets are LAN-shaped; this ticket is what first puts them on the remote-read hot
path for real, so if a WAN deployment ever shows steady `cluster-fetch:peers-silent` against
healthy peers, that's where to look. No ticket needed now — genuinely conditional on a
deployment shape this repo doesn't exercise.

## Fallback (documented, not applied)

The ticket also specified a fallback approach — keep the skip but have the skipped-consult
path report `unavailable: 'peers-unreachable'` instead of a bare absent — for if the direct
fix caused trouble. It did not: both suites are green and the regression spec passes. The
fallback was not applied and needs no action.
