## What changed

Quereus 5.4.0 never sends a module a required ordering for a `nulls last` key (Quereus invariant OPT-063, `extractOrderingFromSortKeys` in `@quereus/quereus/src/planner/framework/physical-utils.ts`), so every required ordering a module sees means NULLs first, in both directions. The index tree frames NULL below every present value (`encodeKeyElement` in `src/schema/key-encoding.ts`), so a forward walk already emits NULLs first.

`walkDelivering` used to ask `nullSafeOrderingPrefixLength` about every key column as if it were descending, which refused a nullable matched column in both directions. It now passes the walk key as it is (ascending in its bytes, no `desc`) and the walk's `reverse`, so the helper gates only a backward walk. Net effect:

| statement over nullable `s`, index on `s` | before | now |
|---|---|---|
| `order by s` / `order by s nulls first` | engine Sort | index walk, forward |
| `order by s nulls last` | engine Sort | engine Sort (engine sends no ordering) |
| `order by s desc` / `order by s desc nulls first` | engine Sort | engine Sort (backward walk would put NULLs last) |
| `where s is not null order by s desc` | backward walk | backward walk |

A `NOTE:` tripwire on `walkDelivering` records that `OrderingSpec.nullsFirst` is not read (the memory module does not read it either; nothing in the engine sets it). If the engine ever sets it, a forward walk of a nullable column must decline `nullsFirst: false`.

Docs: the old blocked-ticket citation (`quereus-explicit-nulls-placement-is-lost-when-an-index-serves-order-by`) is gone from `index-walk.ts`, `ordering-claim-guard.spec.ts` and `docs/internals.md`. The internals bullet is renamed "No NULL backwards". The README's ORDER BY sentence now says that only a descending order needs a NULL-free column, and that a `nulls last` ordering is sorted by the engine.

## Tests (changed, none added)

- `ordering-claim-guard.spec.ts`, "walks a nullable column forwards, and backwards only under a NULL-excluding filter": planner level. `asc(S)` on a nullable column is now claimed as a forward walk, `desc(S)` is still refused, and `desc(S)` under `is not null` is a backward walk. The old ascending-under-filter assertion was dropped because the unfiltered ascending case now covers it.
- `index-ordered-walk.spec.ts`, "walks a nullable column forward, NULLs first, and backward only under a NULL-excluding filter": end to end, differential against a memory table with interleaved NULLs. `order by u, id` and `order by u nulls first, id` are served from the index. `order by u nulls last, id`, `order by u desc, id desc` and `order by u desc nulls first, id desc` keep the engine Sort. `where u is not null order by u desc, id desc` walks. Every statement must return the memory table's rows in the memory table's order. This is the ticket's "explicit `nulls first` on a descending key still cannot be claimed" check.

## Gaps and things for the reviewer to check

- `yarn test:integration` was not run. The change only affects which plan is chosen for a nullable ascending `order by`. The integration specs cover meshes and reactivity, not ordering, but a mesh test that orders by a nullable indexed column would now walk instead of sorting.
- The walk-then-scan finish (`restOfWalk`, after `WALK_ROWS_BEFORE_SCAN` = 256 entries) has no test with NULL index values. I judged it covered by construction: the whole-index range `[ '', KEY_PREFIX_END )` includes NULL-tagged entries, and `restOfWalk` orders the scanned rows by the same tree key (`indexEntryKey`, NULL framed lowest). The ordered-walk spec's table has 42 rows, under the threshold. A reviewer may want a nullable-column case past 256 rows.
- An equality seek on a leading column followed by a nullable ordered column (`where g = ? order by u` over an index on `(g, u)`) is now claimed too, through the same `walkDelivering`. Its range `[P, P + KEY_PREFIX_END)` includes the NULL-`u` entries under `P`, which come first. The planner tests do not exercise this shape directly.
- `rule-minmax-index-boundary` is unaffected: it adds `is not null` for a nullable column, so `min(u)` never takes a NULL from the first row of a walk.
