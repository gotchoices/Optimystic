# A blob reaches the cohort before the row that shows it

One new integration spec and one docs sentence. **No production code changed.**

docs/blobs.md §Committing a reference ends with the two-commit pattern: an application that must not expose a reference before the bytes have moved commits the attachment row (reference only) first, waits for `onDurability` to report `majority` or `full`, and only then commits the row people act on. `feat-blob-pins-follow-sql-commits` pinned every link of that chain on one machine, where the cohort is that machine alone and durability therefore never leaves `local`. This spec runs it across two real libp2p nodes, which is the only place the announcement over the wire, the receiver's read of committed state, the multi-piece pull and a durability class past `local` are real.

## What was built

`packages/quereus-plugin-optimystic/test/two-node-blob-reference.integration.spec.ts` — one `it`, gated on `OPTIMYSTIC_INTEGRATION=1`, `this.timeout(240_000)` on the `describe`. Two real nodes (`clusterSize: 16` against `clusterPolicy.assumedClusterSize: 2`, as `two-node-secondary-index-libp2p.integration.spec.ts` does), each driving its own `Quereus` `Database` through its own plugin, with `types` registered so `blobref` resolves. Two tables over the `network` transactor, exactly the ticket's SQL (`Attachment(Id, Content blobref null)`, `Message(Id, Body, AttachmentId)`).

The run, on node A: put a 2×256 KiB + 1 KiB blob (three data pieces under one list piece — `BLOB_PIECE_BYTES` from db-core, so the constant follows the builder); subscribe `onDurability`; insert the attachment row; assert a durability event for that reference had already arrived by the time `db.exec` resolved; wait, bounded, for `majority` or `full`; assert **before the second commit** that node B answers `stat(ref).locality === 'here'` and that its `size` is the whole blob; then insert the message row and assert B reads it.

`docs/blobs.md` §Committing a reference: one sentence at the end of the two-commit bullet citing the spec.

## One deliberate deviation from the ticket — worth a reviewer's eye

The ticket said to follow the precedent for "node and transactor wiring", which builds a `NetworkTransactor` per node and hands it to the plugin with `registerTransactor('network:libp2p', …)`. **That wiring would have made this spec meaningless.** `CollectionFactory.resolveBlobBackend` reads the blob service off a node registered through `registerLibp2pNode`; a `network` transactor registered *directly*, with no node behind it, falls through to a `SingleMachineBlobService` whose cohort is that machine alone — durability `local` for ever, no announcement on the wire. So each plugin here is handed its node instead (`registerLibp2pNode(NETWORK_NAME, node, node.coordinatedRepo)`, as `network-change-notification.integration.spec.ts` does) and the factory builds the transactor over it. The spec header says so, and the `machineOver` helper carries the reason at the call site. Two consequences a reviewer may want to weigh:

- `default_network_name: NETWORK_NAME` is now load-bearing. The factory looks a registered node up by `${networkName}:${port}`, so without it the default binding would look for `optimystic:0`, find nothing, and silently get a single-machine blob service. Nothing in the test would fail loudly on that — it would stall at `local` and the durability wait would say so, which is why that wait names the last class seen.
- `two-node-secondary-index-libp2p.integration.spec.ts` and `plugin-first-launch-libp2p.integration.spec.ts` wire plugins the other way, so neither of those could exercise blobs across machines. That is the documented behaviour (`resolveBlobBackend` logs `blob:backend-single-machine reason=transactor-has-no-node` and calls it "the configuration working as intended"), not a defect found here.

## Tests added

One, and it is the ticket's whole deliverable:

| Test | What it verifies |
| --- | --- |
| `a blob reaches the cohort before the row that shows it, over real libp2p` › `copies the blob to the other machine before the row people act on is committed` | The two-commit pattern end to end on two machines: the attachment commit announces the blob (first durability event present when `exec` resolves), the other machine pulls it unprompted and holds it whole (`locality: 'here'`, full `size`) **before** the second commit runs, durability reaches `majority`/`full` with both accepting members confirmed, and the row people act on then commits and reads on the other machine. |

No unit tests: the mechanism's own doubles already exist one layer down (`blob-copy-drain.spec.ts`, `blob-announce-receiver.spec.ts`, and the same round trip without SQL in `blob-copy.spec.ts`), and this ticket's whole point is the round trip at the plugin layer.

## Honest gaps and things to probe

- **Timing margin is comfortable but unmeasured on CI.** Three runs on this machine: 5.4 s, 5.5 s, 5.5 s against a 120 s durability bound and a 240 s suite timeout. The copy drain's own schedule (debounce 5 s, then 15–30 s passes) means a first pass answered `unreferenced` would cost one more interval; five such answers would hit the drain's `maxAttempts` give-up and the wait would then report "stalled at `local`". Not observed, but a slower machine is where it would show.
- **`majority` is unreachable in a two-member cohort**, so the spec in practice always sees `full` (a strict majority of two is two, which is also everyone). The wait accepts either class because the specification states both and the test should not encode which one a 2-member cohort happens to produce. A reviewer who disagrees could tighten it to `full` and assert the whole class sequence (`['local', 'full']`, as `blob-copy.spec.ts` does).
- **The gates before the run are load-bearing, and one of them papers over a known defect.** Three bounded waits precede the SQL: the mesh connects, both nodes assemble the same 2-peer cohort for a probe key, and **each node knows the other serves the blob protocol**. The last one exists because a member whose protocol list has not landed yet reads as *refusing* blobs and is left out of the denominator durability is counted over — backlog `debt-a-peer-read-as-refusing-may-only-be-unidentified`. Gating on it keeps that misread from being what a failure of this spec is about; it also means this spec will not catch that defect. The comment at the gate says so.
- **A's cohort view is asserted, B's is not.** The spec waits for A to see both machines in the blob's cohort (A is the announcer, so its view decides who is owed). B's own view decides whether it answers `not-responsible`, and that is left to the drain's retries rather than gated. If it ever flakes, that is the wait to add.
- **Nothing asserts the announced scope** (`two-node-blob/Attachment/blobrefs`) or the pin labels. Those are `blob-pins-online.spec.ts`'s, on one machine where they are cheap to read.
