# Review: blob protocol wire format, frames and the progress deadline

The pieces of the blob protocol (`${prefix}/db-p2p/blob/1.0.0`, docs/blobs.md §Moving pieces between machines) that have no node wiring. Nothing is registered or called yet; the server, client, node wiring, stall specs and docs are the next ticket, `feat-blob-protocol-frames-stat-and-get` (already in `implement/`, prereq on this slug).

## What was built

- **Limits** (`packages/db-p2p/src/protocol-limits.ts`): `MAX_BLOB_HEADER_BYTES` (16 KiB), `MAX_BLOB_PIECE_FRAME_BYTES` (= db-core's `MAX_BLOB_PIECE_BYTES`, 1 MiB), `MAX_BLOB_GET_PIECES` (16), `MAX_BLOB_STAT_REFS` (64), `MAX_BLOB_INBOUND_GETS_PER_PEER` (2), `MAX_BLOB_INBOUND_GETS` (16). Like every other constant in that module, they are not re-exported from the package entry.
- **Wire** (`blob/blob-protocol.ts`): `buildBlobProtocol`; types `BlobRequest`, `BlobAnswer`, `BlobLocalHolding`, `BlobAnnounceAnswer`, `BlobRefusalReason`; `encodeBlobHeader`, `decodeBlobRequest`, `decodeBlobAnswer` (field-by-field checks, one small function per field shape, references and piece ids through db-core's `parseBlobRef` / `parsePieceId`); `checkAnswerFits`; errors `BlobTransferStalledError` (`code = BLOB_TRANSFER_STALLED`), `BlobPeerRefusedError`, `BlobProtocolError` (extends `Error`, not `RangeError`, with the reason in its doc comment). The module doc carries the frame sequences the next ticket implements.
- **Progress deadline** (`blob/progress-deadline.ts`): one `unrefTimer`'d `setTimeout`; `touch()` is one `Date.now()` assignment; the timer re-arms for the remainder when touched since, else aborts `signal` with `BlobTransferStalledError(peer, ms)`; `stop()` idempotent.
- **Frames** (`blob/blob-frames.ts`): `readBlobFrames` (touch per raw chunk → `lp.decode` with `maxDataLength: MAX_BLOB_PIECE_FRAME_BYTES` and a per-position `onLength` cap → `subarray()` per frame; returns an `AsyncIterator`, not an iterable, so a caller cannot `for await … break` it by accident; the buffering `NOTE:` is on it), `sendBlobFrame` (the `encode.single` / `send` / `onDrain` under the deadline rule), `closeBlobStream`. Types `BlobFrameSource`, `BlobFrameSink`.
- **Dial helper** (`protocol-client.ts`): `openStreamWithin(peerNetwork, peerId, protocol, options?: OpenStreamOptions)`, the body of the former private `ProtocolClient.openRequestStream` moved verbatim (log lines byte for byte). The private method is gone; `processMessage`'s two call sites call `openStreamWithin` directly. `cidSuffix` now takes `{ correlationId?: string }`.
- **`Libp2pKeyPeerNetwork.peersServing(protocol, peerIds)`**: order kept, self dropped, a peer without a record dropped, read through `peerRecords`; no membership predicate; the `NOTE:` about stream-merged protocols is on it.
- **Exports**: `blob-protocol.js`, `blob-frames.js`, `progress-deadline.js` added to both `src/index.ts` and `src/rn.ts`, same position.

## Choices beyond the ticket text — check these

- **`readBlobFrames` rewraps the decoder's own framing faults as `BlobProtocolError`.** `it-length-prefixed` checks `maxDataLength` *before* calling `onLength`, so a piece frame over 1 MiB would otherwise surface as its `InvalidDataLengthError`, and a stream ending mid-frame as `UnexpectedEOFError`. The four error classes are not exported, so they are matched by their `code` (`ERR_UNEXPECTED_EOF`, `ERR_MSG_DATA_TOO_LONG`, `ERR_MSG_LENGTH_TOO_LONG`, `ERR_INVALID_MSG_LENGTH`) in `DECODER_FAULTS`, with the original as `cause`. Anything else (a reset, an abort reason, the `onLength` refusal) passes through unchanged. If `it-length-prefixed` renames a code, that fault simply passes through untranslated. The next ticket's client gets "truncated mid-frame" as `BlobProtocolError` for free; "ended between frames, before the last piece" it must still detect itself (the iterator reports `done`).
- **`announce.scope`** is only checked to be a string (empty allowed); the 16 KiB header cap bounds its length. Duplicate references in a `stat` are allowed (the ticket forbids duplicates only for `get` piece ids). Unknown extra header fields are ignored rather than refused, so a later field does not break older readers.
- **`decodeBlobAnswer`** checks list lengths against the caps and non-emptiness; the exact length against the request is `checkAnswerFits`'s job.
- `ProgressDeadline.signal` is a readonly field initialised from the controller, as the ticket's interface shows.
- The first `NOTE:` in `packages/db-p2p/src/cohort-topic/stream-util.ts` was left unchanged; `sendBlobFrame`'s doc comment points at it.

## Tests added

None, as the ticket specifies: the codec and frame helpers are exercised end to end by the next ticket's stall specs (`blob-protocol-stalls.spec.ts`) and the fetcher's specs on real nodes. If the reviewer judges the codec's branching (every refusal arm of `decodeBlobRequest` / `decodeBlobAnswer`) worth one spec of its own, that is the one candidate; nothing else here has branching a later spec will not reach.

## Known gaps

- Nothing in this ticket proves the libp2p 3 behaviour the frame helpers assume on a real stream: that `close` ends only the write side and reading continues, and that a deadline-driven `stream.abort` reaches the reader. The next ticket's stall specs are where that is first exercised.
- `openStreamWithin` keeps `ProtocolClient`'s existing dial-timer `setTimeout` without `unrefTimer`, unchanged from before the move.
