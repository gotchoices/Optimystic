Fourth of the five stage-4 tickets (see `4.1-offline-sync-plugin-mode-and-sealing`). Two protections: the schema-change gate ([§Schema changes](../../docs/offline-sync.md#schema-changes)) and the invented-collection adoption ([§Invented collections](../../docs/offline-sync.md#invented-collections)). The second needed no code: it was proven and pinned.

## What landed

**The gate.**
- `QueuedEntriesBlockSchemaChangeError` (in `offline-mode.ts`, exported from both entries with the `StorageShapeChange` type). It is a `QuereusError` with `StatusCode.BUSY` and carries `table` (`schema.table`), `operation` and `transactionIds` in queue order.
- `OfflineMode.assertNoQueuedEntries(table, operation)`. It reads the table's collections from a new `TransactionBridge.collectionsOf(table)`, which scans the existing collection-to-table record. It then collects (a) queued entries whose `collections` intersect those collections and (b) sealed segments still present in those collections (`getCollectionRegistry().get(id).sealedEntries()`). Part (b) covers the moment after a failed entry has left the queue but its removal is still dropping its segments. The union is thrown; the call logs `offline:schema-change-refused`.
- Call sites in `OptimysticModule`:
  - `createIndex` and `dropIndex`: after the not-found check, before the batch checkpoint.
  - `destroy`: right after `whenCatalogPersisted`, before any teardown. Quereus awaits `destroy` before touching its own catalog, so the refusal vetoes the drop atomically.
  - `addColumn` and `dropColumn` arms: after their own UNSUPPORTED and blocker checks, just before `alterCatalogOnly`. A permanently unsupported shape is therefore still reported as unsupported rather than as "wait".
- The `create` arm, `assertRedeclarationKeepsShape`. It takes the declaration's main collection id (`collectionFactory.getCollectionId`) and finds every live table the bridge records over it. If a live table's `storedRowShape` (column names and types in order, plus the primary key via `describePrimaryKey`) differs from the new declaration, it calls `assertNoQueuedEntries` for that live table. A live table the bridge records but this module holds no instance for is treated as differing; there is a `NOTE:` at the site about that.
- `table` on the error is the table the queued transactions wrote. For the `create table` arm that is the live table, not the one being declared.

**Invented collections.** Nothing in `Collection` changed. Both drivers' opening refresh (`updateInternal`) already adopts the founder's header, replays from the empty baseline (`replayBaseline` uses `inventedBaseline` only while `actionContext` is undefined, and the context never returns to undefined), and lands the row in the founder's log. The design doc's §Invented collections now names the opening refresh as the probe, replacing the `Collection.open` phrasing.

**Docs.**
- README § Offline mode: a new "Schema changes wait for the queued transactions" subsection with the refused/not-refused table and the note that Quereus wraps the error; a new "A table first written offline joins the copy another machine created" subsection; the "Not yet" bullet removed; the stage count updated.

The `OfflineQueue` entry reaches `queued`/`waitingFor: 'cohort'`, stays listed, never fails, and no header reaches storage. Once the header reads absent, the entry commits the invented header as the first write. This covers the "authoritatively absent" outcome too.
- `test/offline-mode-ddl-gate.spec.ts`: a two-node mesh where A's repo parks exactly one pend (the drain's), so the entry stays submitting/in doubt while the DDL's own catalog writes go through. About 0.5 s.

  - An `apply schema` that adds an index fails with the refusal in its `cause` chain, and no index is created.
  - A tag change is not gated.
  - The `create` arm: an identical declaration under another name over the same URI passes, and one with an extra column is refused (`operation: 'create table'`).
- `test/offline-mode-invented-collection.spec.ts`: the joiner on a mesh. B is cut off only for deliveries to B, so A's commits fall short while B's own commits still land on both.
  - The founder's row then the joiner's: both rows on both nodes, and one log of two entries.

## Known gaps and judgement calls for the reviewer

- **When the `create` arm can be reached.** Within one registration, Quereus refuses `create table` for a name it already holds, and module `create` refuses a cached name. So the arm is reachable today only by a second table name declared over a URI whose collection has queued entries. The same-name warm-restart re-declare the ticket describes needs queued entries that survive a restart (stage 5, `offline-sync-journal`). A table recorded with no live instance is then treated as differing and refused (`NOTE:` at `assertRedeclarationKeepsShape`); stage 5 should revisit that.
- **After settling, the wider `create table` may still be refused**, this time by the storage-adoption guard: the settled rows cannot supply the added column. The spec does not assert that the wider declaration succeeds after the drain. The "succeeds once they settle" promise holds for the other five operations.
- **Quereus wraps the refusal** out of `create index`, `create table` and `apply schema` (outer `QuereusError` codes 5, 5 and 1), keeping it as `cause`. `alter … add/drop column`, `drop index` and `drop table` were not checked for direct versus wrapped; the README says to look along the `cause` chain.
- **Checked by reading, not tested:**
  - A CHECK added or dropped by name and `rename column` are not gated (none of those arms calls the gate).
  - The sealed-segment arm that covers a removal still in progress; it needs a removal held mid-drop to test.
  - A `create table` of an unrelated table.
  - A bridge built bare (no controller), where the gate does nothing.
- **Granularity.** The gate is per table (all of the table's collections), not per index: `drop index` is refused while any queued entry wrote the table, even one that never wrote that index. This is conservative and matches the design's wording.
- **The removal window for the network-ack route** was already handled by 4.3; this ticket adds the same view to the DDL gate. Both read the bridge registry's single instance per collection id. Two instances over one id (two tables over one URI) are the known 4.1 shape, and the registry holds only the last one registered.
