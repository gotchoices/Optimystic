# A lineage divergence drops the read cache

## What changed

A refresh (`Collection.updateInternal`) compares the context it holds with the one it just read off the log. Two copies of one collection id can sit at the same revision under different actions (a "lineage divergence"). Before this change that was only logged (`collection:lineage-divergence`), and the handle kept serving the blocks it had cached under the old history indefinitely. Now:

- **The verdict is behaviour, unconditional.** `Collection.judgeAdoption(held, next)` returns `refuse` (read learned nothing, or is below the held revision), `adopt`, or `adopt-divergent` (adopted, and the two contexts name different actions at the HELD revision). One comparison: `actionIdAt(next, held.rev)` vs `actionIdAt(held, held.rev)`, divergent only when both are defined and differ. Not gated on `log.enabled`. The printed `lineage-divergence` line still comes from the gated `earliestFork` and is unchanged in format.
- **`forgetAndAdopt` acts on it first.** It judges before touching anything; on `adopt-divergent` it calls `sourceCache.clear()` (whole cache) and `floors.clear()` before the per-entry loop, so this walk's floors (the new lineage's) are the ones left standing. Then the loop, reverted-block clear, `advanceContext` (now taking the precomputed verdict), `keepLogEnds`. Still await-free. Returns the verdict.
- **`mustReplay` has a fourth reason**, checked before the moved-base reason: `adoption === 'adopt-divergent' && replayable > 0`. Placed first so a whole-cache clear does not log one `restage-moved-base` line per pin.
- **`advanceContext`** uses the verdict for its refuse/adopt decision (default parameter computes it, so the `attach` site is unchanged and only logs). The parked `NOTE:` in its doc is replaced by the decision.
- **`actionIdAt`** now searches from the end (the held side's entry is normally last); its `NOTE:` ties the remaining linear cost to backlog `debt-the-collection-log-never-writes-a-checkpoint`, as does the `NOTE:` on `judgeAdoption`.
- **`BlockFloors.clear()`** is new — the one exception to "a floor, once raised, stands" (class doc and docs/internals.md updated).
- **`CacheSource.clear()` with no ids** now forgets and bumps the generation of every id the cache describes, including an LRU-evicted id's lingering `revisions` entry (before, only cached and unkept ids were bumped, so an in-flight read of an evicted id could still be kept after a whole clear). Nothing called the whole-cache form before this ticket.

Unchanged by design: the not-lowered path (handle above the read on another lineage) refuses, drops nothing, and keeps re-reporting both lines every refresh — that is backlog `feat-replay-mode-collections-merge-divergent-histories`.

## Use cases to validate

- **Same-revision fork** (held 1 on A, read 1 on B): cache dropped, floors reset, staged actions re-staged over B's content; next refresh is silent. Pinned by the test below.
- **Fork below held, read above** (held 2 on A, read 3 on B): adopted; drop, then the walk re-raises B's floors; replay (the revision advance would replay anyway). By inspection of the ordering in `forgetAndAdopt`.
- **Read below held on another lineage** (sereus `held=4 read=3`): `refuse`, nothing dropped. By inspection: a refused read names no action at the held revision, so `adopt-divergent` cannot coincide with `refuse`.
- **Logging off**: the drop and replay still happen — the test runs the discovering refresh with `debug.disable()`.
- **Open (`site=attach`)**: unchanged, logs only.

## Tests

- Rewrote "reports once per discovery, not once per refresh" into **"an adopted divergence drops the read cache and re-stages, and is not reported again"** (`collection.spec.ts`). A handle opens through the armed fixture holding revision 1 under a foreign action id and reads a data block the fixture serves with forked content (`'forked'`); it stages a `derive` action that INSERTS a second block computed from that content. Disarm, refresh with the namespace off, then assert the shared block reads `'stored'` (the drop) and the derived block reads `'stored+local'` (the replay); a second, captured refresh prints no divergence line. Verified it discriminates: disabling the clear makes the first assertion fail (`forked`); disabling the fourth reason makes the second fail (`forked+local`).
- Deviation from the ticket's test plan, on purpose: it asked to assert the staged block's base pin names the adopted lineage's revision. In a same-revision fork that revision is 1 on both lineages, so a pin assertion cannot discriminate — and with an update-based staged action the whole-cache clear makes the pin read as moved, so the existing third reason replays anyway and the fourth reason goes untested (confirmed by experiment). An insert pins no base, so the derived block's content isolates the fourth reason.
- "Exactly one line on the discovering refresh" remains pinned by the existing "a refresh that finds a different action at its held revision logs both ids…" test; the new test pins zero on the next refresh.

## Known gaps / things for the reviewer to weigh

- **Pinned read views share the floors.** `BlockFloors` is shared with every read source the handle built, so the reset also removes floors from a pinned view created before the drop. Such a view reads from a cloned snapshot of the old cache at the old context; its misses go to storage, which holds the new lineage, where the old floors would be wrong anyway. I judged that acceptable and did not record a `NOTE:`; push back if you disagree.
- **The line can print without a drop.** `earliestFork` (diagnostic) scans every shared revision; `judgeAdoption` compares only at the held revision. When the held revision's slot names no action on one side (an invalidation entry took it, or a checkpoint), or the two sides happen to agree there (the artificial "EARLIEST revision" test, which rewrites one entry below an honest one), the line reports a fork the handle does not act on. Documented in `judgeAdoption`'s doc, docs/internals.md and docs/debugging.md; the ticket accepted this.
- **debugging.md worked example**: the second illustrative line had the same `tag=` as the first, which no handle could print once the first refresh adopts. I gave it a second tag and reworded the explanation. Illustrative only.
- No new log field says whether a given `lineage-divergence` line was followed by a drop; operators distinguish via a `context-not-lowered` line on the same `tag=` (documented). A `dropped=` field was considered and left out to keep the line format stable.
