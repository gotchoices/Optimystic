# Review: certified claims in read-repair + provable-only penalties

Second of three tickets from `accept-certified-claims-in-repair` (prereq
`certified-claim-selection` landed the selection rules and `cluster/certified-claims.ts`;
`certified-claims-reconcile-and-persist` follows).

## What changed

All in `packages/db-p2p/src/repo/coordinator-repo.ts` unless noted.

**Proof verification in `queryClusterForLatest`.** After the claim set is built, every claim
carrying a `proof` is run through `certifyClaim` in parallel (thresholds:
`{ superMajorityThreshold: this.superMajorityThreshold, simpleMajorityThreshold: 0.5 }` — the 0.5
is hardcoded per the `ProofThresholds` doc, because cluster members enforce `count > total/2`, not
the config's 0.51). A verifying proof sets `claim.certified = true`, which `selectQuorumRev`
already weighs (previous ticket). A failing proof leaves the claim UNCERTIFIED but still in the
set (it corroborates by peer count as before) and logs `cluster-fetch:proof-uncertified`.

**Verification-time penalties.** A proof failure that `isAttributableProofFailure` classifies as
attributable (replay/`claim-not-in-message`, self-contradicting artifact, digest mismatch, …) →
`reportPeer(peerId, InvalidRestoration, 'read-repair:<blockId>')`, via a new never-throw helper
`penalizeProofService`. Non-attributable failures (malformed proof/signature, unknown signer,
legacy record, oversized cohort, …) are never penalized — the identity behind the artifact was not
proven, same discipline as `VerifyOutcome.penalize` in `cluster-repo.ts`.

**Equivocation naming.** When `selectQuorumRev` declines, `certifiedEquivocation(claims)` is
consulted and a distinct `cluster-fetch:certified-equivocation` line is logged (two verified
proofs for different actions at the same revision) before the unchanged `no-quorum` /
`reportRepairDeadlock` path. Also added `cluster-fetch:certified-selected` when the certified rule
won a selection — that is what `QuorumRev.certified` exists for.

**Penalty rework (`penalizeContradictingRevClaims`).** The `rev > selected.rev` branch is GONE —
a peer can honestly be ahead of the sampled quorum (in-flight commit; honest holders dropped by
the 1s per-peer deadline), and weight 30 vs deprioritize threshold 20 meant one false hit
deprioritized an honest peer. The same-rev/different-actionId branch stays (provable without any
proof machinery). This folds and deletes `tickets/backlog/debt-read-repair-penalty-provable-only.md`.

**Wiring.** `CoordinatorRepoComponents` gains optional `proofAnchoring?: ProofAnchoring`, threaded
through the `coordinatorRepo` factory and constructor into `certifyClaim`. Production wiring
leaves it absent by design (the next ticket documents that at the composition root);
`certifyClaim` logs unanchored acceptance internally regardless.

**Docs refreshed:** the stale "selectQuorumRev ignores the proof" comment, the
`queryClusterForLatest` NOTE about bare-assertion claims, the `uncorroboratedRev` availability-
lever NOTE (revisit condition now names the in-tree machinery instead of a deleted backlog slug),
`soleHolderMessage` + `reportRepairDeadlock` (sole-holder now only reachable for an UNCERTIFIED
lone holder — a certified one converges before it), and `PenaltyReason.InvalidRestoration`'s doc
(`reputation/types.ts`).

- Headline: 10-cohort, ONE peer answers with a valid proof-carrying claim, rest answer "holds
  nothing" → restoration fires (storage `get` saw `context.committed = [claim]`).
- One holder, no proof → declines as before, no penalty.
- Certified rev 5 vs lone uncorroborated rev 9 → restores rev 5.
- Certified rev 5 vs 2-peer-corroborated rev 9 → restores rev 9 (higher-corroborated rule).
- Mixed cohort: certified rev 7 short-circuits a corroborated rev 3.
- Two certified claims, same rev, different actions → no restoration,
  `certified-equivocation` logged (asserted via `captureLog`), nobody penalized.
- Replayed proof (genuine rev-5 proof on a rev-9 claim) → uncertified, does not steer
  restoration, server penalized exactly once with `invalid-restoration`.
- Unparseable proof (garbage object) → uncertified, NOT penalized.
- Same-rev/different-actionId conflict → still penalized (the kept branch).
