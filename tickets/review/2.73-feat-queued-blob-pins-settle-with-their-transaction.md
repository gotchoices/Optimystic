# Queued blob pins settle with their transaction

A commit that reaches the offline queue instead of the network leaves its blob reference pins in place on purpose: nothing is on the network yet, so the writer holds the only copy of the bytes a committed row will point at. This part releases those pins when the queued transaction finally settles — announced into the table's reference tree for the collections that committed, released outright for the ones that did not, so the writer's piece sweep can take the bytes of a transaction that never landed.

Everything is reconciled from committed state and the pins' own owner labels. Nothing reads the offline journal's segments and no field was added to any journal record.

## What was built

**`SqlBlobPins.settleQueued(transactionId, committed)`** (`blob-pins.ts`), with `settled()` and `dispose()` beside it. It runs on a new per-object work chain: each step first waits for any open transaction to end (`TransactionBridge.whenTransactionIdle`) and then returns at once if disposed. The chain never rejects. The four online arms (`holdForCommit`, `committed`, `queued`, `abandoned`) stay off the chain — they run inside `commitTransaction`/`rollbackTransaction` under Quereus's exec mutex and must not wait on a chain that waits for the transaction they belong to.

Where a transaction's owed pins come from:

- **From memory** when this process sealed the entry: `queued()` now remembers the transaction's `HeldPins` in `queuedPins`, and `settleQueued` takes it. No pin listing at all.
- **From the labels** when it did not — a process that restored the entry from the journal after a restart: `listPins(transactionPinPrefix(id))` over every backend `CollectionFactory.knownBlobBackends()` resolves, each label read through `parsePinLabel`. A stray `put` pin met on that path is dropped there (the label is in hand).

Per reference, once its scope is known to have committed: the scope is confirmed in the network's registry, then `announce`, then `unpin`. A scope not among the committed ones is unpinned without announcing. A scope that cannot be confirmed, or an announcement that throws, **keeps** the pin and logs `blob:pin-kept` — nothing in this part retries it; `feat-blob-pins-reconcile-after-a-restart` is what does, and the keep arm's comment says so.

**`BlobScopeRegistration.isRegistered(network, scope)`** — a read-only registry check answering `true` / `false` / `undefined`, used for a scope no table in this process backs any more. Registering there would re-register a tree whose table was deliberately dropped and keep its blobs for ever; a certain "not listed" is what makes those pins releasable.

**`CollectionFactory.knownBlobBackends()`** — every blob backend of a transactor key the factory has seen *options* for (not only the ones already resolved: a previous process's pin can sit in a store this one has not opened). A key whose resolution throws is logged and left out.

**`OfflineMode.attachBlobPins`**, and the call from `onQueueStatus` — the one place every terminal queue outcome passes through (the queue's own `onStatus`, and the restore's `emitSettled` for a discarded deferred record). `committed` → `'all'`; `failed` → `new Set(committedCollections ?? [])`; `partially-committed` settles nothing, since the entry is still at the head owing its remaining collections. Never awaited: the status arrives synchronously inside the drain.

**`plugin.ts`** — the pins are now built after `new OfflineMode(...)`, attached to both the bridge and the controller, exposed as `plugin.blobPins`, and `blobPins.dispose()` is awaited in `plugin.dispose()` before `offline.dispose()`.

## Two deliberate departures from the implement ticket

Both are small, both are called out here because a reviewer should weigh them rather than discover them.

- **A fast-path guard the ticket did not ask for.** `queued()` also records the transaction id in a `sealedHere` set, and `settleQueued` skips the label listing for a transaction this process sealed that is absent from `queuedPins` — such a transaction provably took no reference pin. Without it, a host that uses **no blobs at all** would pay a listing on every queued transaction it settles, and, worse than the ticket's "the scan reads nothing" reasoning assumes, that listing *resolves and starts a blob store per network* (`CollectionFactory.getBlobBackend` calls `SingleMachineBlobService.start()`). Absence from the set means "cannot say", which falls through to the listing — the safe direction.
- **The status line in docs/blobs.md was amended, not left alone.** The ticket said to leave it for the third part to flip. Left untouched it would have read "Settling a QUEUED transaction's pins with the entry … still to be built" in the same paragraph as the new bullet describing it as built. The minimal edit was made: that item was removed from the still-to-be-built list, and the other two (the restart reconciliation, the `unstaged` expiry) stay. The "A put outside a transaction" bullet is untouched, as asked.

## Known gaps, for the reviewer

- **A queued transaction that commits leaves its `unstaged` pin.** The online `committed()` arm drops the `unstaged` pin of a reference that landed; `settleQueued` does not, which is what the ticket specified (its test expectation is "no `sql/` pin remains"). The bytes are kept either way — the announcement took the `owed` hold — but nothing in the codebase releases that pin today: the holding-period expiry that would is `feat-sql-columns-hold-blob-references`. If a reviewer judges the mirror-image release to belong here, it is six lines (`releaseUnstaged` already exists and takes exactly the settled references).
- **The specs use a reachability gate, not `commit-gate.ts`.** The ticket named `commit-gate.ts` for holding the drain. A closed `ICohortReachability` gate (`offline-restore.spec.ts`'s precedent) is what the cases actually need: it keeps the entry **unsent**, which is the only state in which it is still discardable (test 2) and the state a restart must find it in (test 3). Parking the transactor instead would have put the entry in doubt and made `discard` throw.
- **A double-delivered terminal status costs a listing.** The second settle finds `queuedPins` and `sealedHere` already empty, so it takes the fallback and scans. It is correct (idempotent, finds nothing) and rare; the `mayHoldStalePins` flag the next part adds is the natural place to cut it.
- **`plugin.hydrate` does not await `blobPins.settled()`.** The ticket mentions `settled()` existing "for `plugin.hydrate` and for the specs"; nothing in this part needs hydrate to wait, and making it wait would deadlock a host that called hydrate inside a transaction. The next part's `reconcileReady` is the natural hook if one is wanted.

## Tests

`packages/quereus-plugin-optimystic/test/blob-pins-harness.ts` (new) — the shared harness the next two parts' specs will build on, so it is the module to read first. One `MemoryRawStorage`, one `{ pieces, kv }` blob store and one journal, created once and handed to every plugin handle, so closing one handle and opening another over the same stores **is** a restarted process. Also the reachability `Gate`, `restart()`, `putBlob` (real bytes, never a fabricated reference), the pin renderers (`pinsOn`, `allPins`, parsed, so a stray owner fails a comparison rather than being counted as ours), and `referencesInTree`. The journal is a small map-backed `IKVStore` rather than a `MemoryKVStore`, which the registration config refuses by name.

`packages/quereus-plugin-optimystic/test/blob-pins-queued.spec.ts` (new) — three cases, one per arm of `settleQueued` with a distinct outcome:

| Test | What it verifies |
|---|---|
| announces and releases the reference pins of a queued transaction that commits | While queued: exactly one pin of the transaction, its reference under the table's `/blobrefs` scope, nothing announced. After the drain and `settled()`: no transaction pin anywhere, `stat` reports durability `local` (the announcement's `owed` hold), the reference tree lists the reference. |
| releases the reference pins of a queued transaction that is discarded, announcing nothing | After the withdrawal: no transaction pin, nothing announced (`durability` still absent), the reference tree empty, and the application's own `unstaged` hold on bytes it put outside the transaction still there. |
| settles a queued transaction restored after a restart from the pins' own labels | The entry is back in the queue under the same id after a restart over the same stores, its reference pin intact; after the drain the pin is gone, `stat` says `local`, and the reference tree lists the reference — the announce went into a scope the registry really lists. |

The third case is the one that exercises the label fallback, and it is load-bearing: with `listQueuedReferences` stubbed out to return `[]`, cases 1 and 2 still pass and case 3 fails on the leftover `sql/<id>/ref/<scope>` pin (verified, then reverted).

No test was added for the partial-commit or cascade arms: both are the same two branches driven by a different `committedCollections`, checked by inspection of the two call sites in `OfflineMode.settleBlobPins`.

## Checked by inspection, not by a test

Each of these is argued in a comment at its site: `partially-committed` settling nothing; a cascade failure (`committedCollections` absent → empty set → everything released); a partial commit then a permanent failure (the two arms, driven by the set); a scope whose table was dropped elsewhere (`tablesOf` empty here too → `isRegistered` says `false` → released, never re-registered); an unreachable network at settle time (pin kept and logged, retried by the next part); a transaction with no blob references (now short-circuited, see the departure above); a table on another network (every pin, announce and registry read goes through the backend of that table's own transactor key); double settle; and a `behind-queue` commit, whose own settle parks on `whenTransactionIdle` until `awaitQueuedCommit`'s `finally` ends the transaction — no deadlock, since the commit never awaits the chain.
