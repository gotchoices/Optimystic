# Divergence report fields — implemented, ready for review

Pure diagnostics. **No behaviour change**: nothing new throws, nothing new is adopted or dropped,
and every added computation sits behind the existing `log.enabled` gate. The parked question
(should a detected divergence drop the read cache or throw?) stays parked with
`backlog/more-design/6.5-partition-healing`.

## What the three lines look like now

```
collection:context-short-of-tail   id=… tag=… before=… after=… tail=…
collection:context-not-lowered     id=… tag=… site=… held=… read=… heldAction=… readAction=…
collection:lineage-divergence      id=… tag=… site=… forkRev=… held=… read=… heldRev=… readRev=…
```

Four changes, all in `Collection`:

- **`site=`** — a new `DivergenceSite = 'refresh' | 'attach'` parameter on `advanceContext`.
  `updateInternal` passes `'refresh'` (this handle's copy vs the stored log — indicts a forked
  replica); `attachToLog` passes `'attach'` (the tail block's claim vs a walk of its own chain —
  indicts storage). The type's doc comment is where the two meanings are written down; the log
  lines carry it.
- **`forkRev=` / `heldRev=` / `readRev=`** — the divergence check was a single lookup at the
  holder's current revision. It is now `Collection.earliestFork`, which scans both `committed`
  lists and reports the LOWEST revision they both name an action for and disagree at. `held=` and
  `read=` are now the ids AT `forkRev`, and `heldRev=`/`readRev=` carry the two contexts' own
  revisions. This genuinely widens detection: a fork below the current revision used to be silent.
- **`heldAction=` / `readAction=` on `context-not-lowered`** — `actionIdAt` on each side, `none`
  where that side names no action there. The same id on both sides means one lineage this handle
  merely sits ahead of; different ids mean a fork sealed underneath it. The lookups are inside a
  `log.enabled` guard; the early `return` that refuses to lower is deliberately outside it.
- **`tag=` on all three lines** — the `instanceTag` the prereq ticket added. The prereq already
  minted it in `open`/`createOrOpen` *before* `attachToLog`, so no hoisting was needed;
  `attachToLog` just gained the parameter. `reportShortfall` gained it too.

`docs/debugging.md` and `docs/internals.md` are updated for the new shapes, including a
**"Worked example: what these fields buy you"** subsection that takes the August 2026 two-machine
capture, states the three questions it could not answer, and shows the same three events with the
new fields answering them.

## Use cases to exercise in review

The claim under review is *"an operator reading these lines can now answer which handle, which call
path, and which revision."* Worth pushing on:

- **Does `site=` actually discriminate?** `attach` fires only when storage's tail metadata and its
  own log entries disagree; `refresh` only from `update()`. Both are pinned by tests, but check the
  wiring: `createOrOpen`'s *create* branch never calls `attachToLog`, so an invented collection
  emits nothing at all from either path — is that the right silence?
- **Is `earliestFork` right about "earliest"?** It skips revisions only one side names (legitimate
  `undefined` from `actionIdAt`), which means a fork whose split revision has fallen off the read
  side's list past a checkpoint gets reported at the lowest *surviving* disagreement instead — a
  later revision than the true split. The docs say silence is weak evidence; they do not currently
  say `forkRev=` can be an upper bound on the split point. Judge whether that needs saying.
- **The `log.enabled` gate.** `earliestFork` allocates a Map and walks both lists. Confirm the gate
  really covers it on the refresh path (it sits inside `if (current !== undefined && log.enabled)`)
  and that nothing else made those lists longer.
- **The refusal path.** `context-not-lowered`'s `return` must happen whether or not logging is on.
  There is a test for the fields; there is no test asserting the refusal still happens with the
  namespace *off*. That is a real gap — see below.

### Tests added or changed

- `a refusal to move backwards names the action on each side, and its call site` — **new**. Opens a
  handle against an inflated tail so it is pinned above what any walk can reach, asserts
  `site=attach` on the open's own refusal and then the full field set on the refresh's, with the
  same action id on both sides (pinned-high, not forked).
- `names the EARLIEST revision the two sides disagree at, not the current one` — **new**. Two
  commits, then a transactor that rewrites only revision 1's log entry, leaving the tail metadata
  and revision 2 honest. The old single-revision check was silent on this; the new one reports
  `forkRev=1 heldRev=2 readRev=2`. This is the test that pins the widened detection.
- The existing refresh- and open-divergence tests now assert `tag=`, `site=`, `forkRev=`,
  `heldRev=`, `readRev=`; the shortfall test asserts `tag=` against `lagging.instanceTag`.
- Test helper `rewrittenLineageTransactor` gained `state` and `entryRev` options; new helper
  `storedEntryActionIds` reads the honest per-revision ids out of the tail block.

## Known gaps — treat the tests as a floor

- **No test runs the refusal path with the namespace off.** `context-not-lowered`'s early `return`
  is what actually enforces monotonicity, and it now sits one `if (log.enabled)` block away from
  that `return`. Every test reaching this code has logging on, so a future edit that pulled the
  `return` inside the guard would pass the whole suite while silently letting revisions go
  backwards. The cheapest guard is a test that pins the collection high, refreshes with debug
  disabled, and asserts the held revision did not drop.
- **`forkRev=` as an upper bound is untested and undocumented.** No test constructs a fork whose
  split revision has been truncated past a checkpoint, so "reports the lowest *surviving*
  disagreement" is inferred from the code, not observed.
- **`site=attach` is only exercised through a lying transactor.** No test produces a genuinely
  self-inconsistent tail; the test double is what makes storage look wrong. Inherent to testing a
  storage-corruption diagnostic in-process, but it means the `attach` path has never seen real
  input.
- **Field ORDER is now load-bearing for the tests.** Each assertion parses one regex over the whole
  line, so reordering fields breaks tests rather than surfacing as a semantic change. Acceptable
  (the lines are a documented format) but worth knowing before editing one.
- **The `heldAction`/`readAction` `none` placeholder is untested.** `actionIdAt` legitimately
  resolves `undefined`, and no test drives that branch.

## Tripwires recorded (not tickets)

- `NOTE:` in `Collection.earliestFork` — a `committed` list carrying two entries at one revision
  would be a defect in its own right, and the Map build keeps the last one arbitrarily. Harmless
  while every caller is a diagnostic; if such a list is ever seen, report the duplicate rather than
  silently picking one.

The downstream fork's mechanism was **never reproduced in-repo** (six attempts —
`tickets/blocked/secondary-index-repro-exhausted-upstream`). The interleaving spec
(`2.2-coordinator-interleaving-spec`, now complete) did not reproduce it either: it proved the

So these fields are now the next evidence channel, and what settles it is **a downstream (`sereus`)
run carrying them**. Concretely: if such a run emits `lineage-divergence` with `site=refresh` and
two distinct `tag=` values on one collection id, the fork is a replica problem and the commit
interleaving is back in scope; if it emits `site=attach`, or one tag with `forkRev=` at or near the
collection's first revision, the finding belongs to the genesis-cohort family tracked by
`backlog/more-design/6.5-partition-healing` (an arm was already appended there). Until that run
happens, neither branch can be closed from inside this repo.
