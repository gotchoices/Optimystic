# Review: move the repair corroboration floor off the replication factor

## What changed

`corroboratorCapacity(cohortPeerCount, clusterSize)` in `packages/db-p2p/src/cluster/quorum-restore.ts`
answers "how many peers other than me could possibly answer for this block", and both block-restoration
paths (read-repair in `CoordinatorRepo.queryClusterForLatest`, commit-path reconcile in
`createReconcileBlock`) capped their corroboration-vote requirement with it. The second parameter was
`clusterSize` — the replication factor, defaulting to `10` — so an unconfigured two-node deployment
computed `corroboratorCapacity(1, 10) = 9`, needed two corroborators, had exactly one peer that could ever
supply one, and could never repair a damaged block. This is the second half of a two-ticket split (the
first, `split-admission-floor-from-replication-factor`, did the same for the membership admission gate);
`assumedClusterSize` — the operator's declaration of the smallest cohort this deployment can genuinely
field, already threaded through `libp2p-node-base` for the admission gate — now feeds this too.

### The rename

- `corroboratorCapacity`'s second parameter: `clusterSize` → `assumedClusterSize`. Arithmetic unchanged
  (`Math.max(cohortPeerCount, assumedClusterSize - 1)`).
- `ReconcileBlockDeps.clusterSize` → `assumedClusterSize` (required field, unchanged cardinality — the
  fallback lives one level up, at the config-resolution sites that construct this object).
- `CoordinatorRepo` resolves `this.assumedClusterSize = policy.assumedClusterSize ?? policy.clusterSize`
  in its constructor — a caller that has not adopted the new field keeps today's behavior exactly.
- `libp2p-node-base.ts` threads `consensusConfig.assumedClusterSize` (already resolved there, defaulting
  to `minAbsoluteClusterSize` = 2) into `createReconcileBlock`'s deps.

### The deliberate asymmetry with the admission gate

The membership admission gate (prior ticket) treats an absent `assumedClusterSize` as **unknown** and
admits — refusing writes outright is unacceptable. This corroboration floor does the opposite: an absent
value falls back to `clusterSize` and **stays strict**. Reasoning: the failure mode here is a block that
goes unrepaired (degraded, not dead), not a refused write, so there is no reason to relax the floor just
because a caller hasn't adopted the new field yet. This is called out in a comment at both fallback sites
(`reconcile-block.ts` doc comment on `ReconcileBlockDeps.assumedClusterSize`, `coordinator-repo.ts`
constructor) so it doesn't read as an oversight on a future pass.

### Docs

Updated every place that documented the old "configure `clusterSize: 2`" escape hatch, which this change
invalidates: `packages/db-p2p/docs/cluster.md` (the `clusterSize` vs `assumedClusterSize` comparison table
and prose), `docs/internals.md` (the reconcile-path corroboration description), `docs/transactions.md`
(the read-repair "worst-case staleness" section, §"What a repair pass will and will not accept" —
flagged as belonging to this ticket by the prior ticket's own review), the `NodeOptions.clusterSize` and
`clusterPolicy.assumedClusterSize` jsdoc in `libp2p-node-base.ts`, and — beyond the ticket's original file
list, but the same stale claim — the `--assumed-cluster-size` CLI help text and README entry in
`packages/reference-peer` (added by the prior ticket, described the flag as admission-gate-only).
