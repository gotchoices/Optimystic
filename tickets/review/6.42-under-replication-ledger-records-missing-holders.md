# What was built

A commit acknowledged below `full` used to forget who was missing it the moment the writer was answered. Now every success exit of `CoordinatorRepo.commit` goes through `acknowledgeCommit`, which writes the shortfall to a per-node ledger before the answer is returned.

**The ledger** (`IUnderReplicationLedger`, implemented by `KvUnderReplicationLedger` over `IKVStore`, key `under-replicated/<blockId>`, JSON value). One entry per block:

- `record` — higher revision replaces the entry (resets `attempts` and `recordedAt`); same revision replaces `quorum` and `missingPeerIds` but keeps `attempts` and `recordedAt`; lower revision is skipped and logged (`record:skip-lower-rev`).
- `settle(blockId, rev)` — **added beyond the ticket's sketch.** Deletes the entry unless it records a higher revision. Answers from an in-memory index when no entry exists, so a healthy `full` commit does not read the store.
- `satisfy` — removes peers, deletes when empty. **Deliberate choice:** on an entry whose missing set is unknown (empty), it returns the entry unchanged rather than deleting it, because "unknown" is not "nobody". The drain ticket was told how to handle that.
- `noteAttempt`, `delete`, `get`, `list` (oldest `recordedAt` first).
- Every operation on one block runs in call order (a per-block promise queue inside the instance), so the read-compare-write rules hold under concurrency. Scoped to one instance per store — documented on the interface.
- `maxEntries` backstop (default 100,000), oldest-recorded evicted first, logged as `evict:over-cap`. Eviction runs after the recording block's queue is released and takes the victim's queue, so no call holds two queues at once.
- Malformed stored bytes are read as absent and logged (`read:unparseable` / `read:malformed`), never deleted by a read.

**Recording rules in `CoordinatorRepo`** (`noteReplicationShortfall`):

| Exit | `localHolds` | Effect |
|---|---|---|
| solo (`local` / `unrouted`) | true | record, empty missing set |
| local-executed | the member's retained verdict | `majority` → record naming `unconfirmed`; `full` → settle |
| local fallback commit landed | true (even off-cohort: it holds bytes) | same |
| tolerated divergence | false | `full` → settle; otherwise nothing |
| any refusal | — | never reaches the ledger |

`torn` blocks are filtered out. Ledger failures are caught per block with `Promise.allSettled`, logged as `coordinator-repo:under-replication-record-failed`, and never change the answer.

**Node wiring.** `NodeOptions.kvStore` (instance or factory). Absent → `MemoryKVStore` plus a `node-wiring` `WARN:` line naming what is lost. The reference peer passes `FileKVStore` over the `--storage-path` it gives `FileRawStorage`, or `MemoryKVStore` for memory storage (so no warning where persistence was never on offer). `PersistentTransactionStateStore` is **not** wired; a NOTE at `resolveKvStore` says it is now constructible and that wiring it belongs to `feat-long-lived-pend-completes-as-members-appear`.

# Known gaps and things to push on

- **The torn filter is exercised only through the private method.** No answer built in `CoordinatorRepo` carries `torn` today (the writer's `NetworkTransactor` derives it after every coordinator answered), so the spec calls `noteReplicationShortfall` directly via a cast. The comment at the filter says it guards a future producer.
- **Recording is awaited on the commit path.** One store read and write per block per below-full commit; on a genuinely solo node that is every commit, and a solo node's ledger holds an entry for every block it writes until a drain exists (bounded by the cap). Chosen so an entry cannot be lost to a crash between answering and writing. Parked as a NOTE on `noteReplicationShortfall`; nothing measured.
- **The eviction index loads the whole ledger on the first mutation after start** (one read per entry, sequential). Fine at current sizes; at the cap under `FileKVStore` that is 100,000 file reads on the first below-full commit or `full` settle after a restart. Not measured. The cap's NOTE says to measure before raising it.
- **The memory-fallback warning is a `debug` line**, off unless `DEBUG` includes `optimystic:db-p2p:node-wiring`. That matches the package's convention (no `console.warn` anywhere in db-p2p src), but it is quieter than "loud" in the ticket suggests. A reviewer may want a different call.
- **Same-revision re-record keeps `attempts`.** The ticket only specified higher and lower. Reasoning: same revision means the same shortfall observed again (for example a writer re-driving the same action), so it should not refill the give-up budget.
- **Off-cohort fallback coordinator records.** When this node is outside the cohort but its fallback commit landed, it records the cohort's unconfirmed members with itself as the implied source. It does hold the bytes; whether a drain should push from a node the cohort does not consider responsible is the drain's call.
- **Size.** `coordinator-repo.ts` measured 3084 lines with `wc -l` (2994 before this ticket). Already covered by the measured arm on `backlog/debt-freshness-state-scattered-across-coordinator-repo`; not re-filed.

# Note for the reviewer (added by the garden tender, 2026-09-16 15:2x)

The implementer's unmeasured "commit latency" gap deserves a measurement rather than a shrug, for two
reasons specific to this repository's current priorities:

1. **It lands on the solo and small-cohort path.** A `local` or `unrouted` commit — a machine that is
   genuinely alone, the N = 1 case the maintainer is focused on — now awaits a ledger read and write
   per block before acknowledging. The cold-apply cost work behind GitHub #8 (144 s → 10 s) was about
   exactly this path's storage-operation count.
2. **A downstream repository binds to our storage-operation counts.** sereus pins cold control-database
   start at 45 storage operations in a budget spec, and uses that count as a latency lever in a
   bring-up scenario (see the garden report, "A downstream cost of making this system faster"). Whether
   ledger writes count depends on whether that spec measures the `kvStore` or only block storage — so
   establish which, rather than assuming.

Suggested check: run the existing cold-apply / storage-op cost gates in this repository before and after
this commit, and state the delta in the review. If ledger writes add operations on the solo path, say so
in the handoff so the dependent repository re-measures its budget instead of meeting it as a red run.
