# A coordinator told of a newer revision consults its cohort past its window

## What was built

`CoordinatorRepo.get` now has two triggers for consulting the cohort about a block it holds. The old one is the lazy read-repair window's time test (`shouldReadRepair`). The new one is the asker's floor: when the read carries `BlockGets.floors[blockId]`, the block's local revision is below it, and the floor is strictly above the floor this node last consulted under for the block, the read consults now, inside the window (`floorDemandsConsult`). The rest of the pass is untouched: `fetchBlockFromCluster` corroborates, promotes or acquires, the refreshed local answer replaces the entry, and `recordAheadClaim` and `flagUnconfirmedCurrency` run as before. The coordinator never refuses on a floor. A copy still below the floor after the pass is served exactly as today, so the asker's own check and second-chance retry are still what handle an unmet floor.

The stamp the window keeps per block was widened from a timestamp to `FreshnessStamp = { at, floorConsulted? }`, still on the one existing `lastSeenCommitMs` map. `markBlocksSeen(blockIds, floor?)` records the floor a pass consulted under; a stamp written without one (every commit-path call, and a read pass that carried no floor) clears it. The floor is threaded into `fetchBlockFromCluster` as a fourth parameter and recorded at exactly the four exits that already armed the window: solo-self, `cohort-too-small`, `local-current`, post-restore. The exits that deliberately leave the window unarmed record nothing, so a floored read after one of them consults again; the `NOTE:` at `floorDemandsConsult` names that bound and the remedy. `readRepairMode: 'off'` stays off, stated at the predicate. `'paranoid'` is unchanged.

`cluster-tx:read-repair-triggered` carries two new fields: `reason` (`'window'` or `'floor'`; `'floor'` whenever the floor demanded the consult, even when the window would have consulted anyway, as the ticket asked) and `floor` (present when the read carried one).

## Tests

All new tests are in db-p2p. Each was run with the predicate patched to always return false, and each failed then; the mesh case failed with exactly the `SyncRevisionStalledError` the ticket describes.

- `coordinator-repo-read-repair.spec.ts`, describe "a read carrying a floor above the local copy". Consults are counted as callback invocations for the remote peer, one per consult. Self answers from the storage double, as the real callback does.
  - "consults inside the window and answers with the revision it converged onto": local 6 stamped fresh, cohort at 7; an unfloored read serves 6 with no consult; a read with floor 7 consults once and serves 7, and the trigger line is `{ reason: 'floor', floor: 7, ageMs: 0 }`; a further floored read does not consult (floor met).
  - "remembers the floor it consulted under": local 6, cohort also at 6; floor 7 consults once and serves 6 unrefused; the same floor and an unfloored read do not consult; floor 8 consults once more; a lapsed window's unfloored consult re-stamps without a floor, after which floor 7 consults again (the clearing rule).
  - "on a cohort of one, consults once per window per block under an unmeetable floor": solo cohort, lazy mode, stamped fresh; three reads at floor 7 and one at 8 produce trigger lines for floors 7 and 8 only, no callback invocation, and the served entry carries neither `unavailable` nor `unconfirmedAheadRev`.
- `floored-read-consults-a-lagging-coordinator.spec.ts` (new): three-member mesh, `clusterSize: 3`. Member B checks the tree's blocks with its cohort while all agree (arming its window; its coordinator's clock is then frozen so the window cannot lapse), then B's storage refuses the next commit with the ahead-shaped answer a member tolerates without reconciling, so A's write is acknowledged with B one revision behind. A handle whose every read goes to B's coordinator and whose writes go through A's transactor writes: A refuses it with `staleAt` at A's revision, the retry's refresh carries the floor to B, B consults and repairs itself, and the retry lands. Asserts the write's durability is reported and `isFullyDurable`, that B's coordinator logged a `reason: 'floor'` trigger for the tail at A's revision, that B's revision index names A's action at A's revision of the tail (only the read-time repair could have put it there), and that an observer through A and the handle both read every row.

No test for the fourth parameter's plumbing or the stamp record; the compiler and the existing suite cover them. `coordinator-repo-small-cohort-arming.spec.ts` and `coordinator-repo-solo-read-repair-window.spec.ts` pass unchanged.

## An existing test was adjusted

`superseded-own-write-is-saved.spec.ts`, case 2 ("one member missed the write and took the rival's revision as a replica"). It built its state by letting the rival's floored read of the leaf go through node A's coordinator, which served its older copy from inside its window so the transactor's second-chance round answered from B, leaving A behind. With this change A consults on that floored read and repairs itself before answering, so A ends up vouching for the write (`contains`) and the case no longer produced the `unknown`-must-not-veto shape its name claims (the whole-suite run failed on exactly that precondition assertion, and nothing else). The rival now reads B's storage directly, the same device case 3 already uses for A, with a comment saying why. The mechanism the case pins, cohort lineage folding, is untouched. Reviewer: judge whether the original device (a coordinator-routed floored read leaving a member behind) needs to survive somewhere; I concluded it cannot, since that state can no longer arise from a coordinator-routed read by design.

## Where the reviewer should look hardest

- The mesh case routes all of the handle's reads to B's coordinator and so bypasses `NetworkTransactor.get`'s second-chance round. That is deliberate (the ticket's shape is "the other coordinator may also be inside its window", and the harness picks read coordinators by ring distance, so a transactor-routed version is not deterministic), but it means the interaction of the coordinator-side consult with the transactor's below-floor retry is exercised only by the quereus and db-p2p suites at large, not by a targeted case.
- In the mesh case B converges through the free path, promoting the pending record it still holds for A's action; the acquire-from-cohort path under a floor is not separately pinned. It is the same `restoreCorroborated` code as before, with no change.
- The post-restore exit records the floor even when convergence failed (`cluster-fetch:not-restored`). Per the ticket that is the intended "floor unmet after the pass" behaviour: the next read under the same floor inside the window does not consult, and the doubt memo keeps stamping `unconfirmedAheadRev`. Worth a second look that this is the tradeoff wanted, since it means an unmet floor and a failed acquisition wait out one window together.
- Two concurrent floored reads of one block can both consult before either stamps. Inspection only, as the ticket allows; not new.
