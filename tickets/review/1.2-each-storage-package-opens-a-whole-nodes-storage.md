# Each storage package opens a whole node's storage

## What landed

Four functions, one per storage package, each returning the `OpenNodeStorage` db-p2p declares and each named for its backend so a host importing two packages gets two distinct names:

| Package | Function | Location | Options type |
|---|---|---|---|
| `@optimystic/db-p2p-storage-fs` | `fileNodeStorage(basePath, options?)` | one base path | `FileNodeStorageOptions` |
| `@optimystic/db-p2p-storage-ns` | `sqliteNodeStorage(db, options?)` | one open SQLite database | `SqliteNodeStorageOptions` |
| `@optimystic/db-p2p-storage-web` | `indexedDbNodeStorage(db, options?)` | one open IndexedDB handle | `IndexedDBNodeStorageOptions` |
| `@optimystic/db-p2p-storage-rn` | `levelDbNodeStorage(db, options?)` | one open LevelDB handle | `LevelDBNodeStorageOptions` |

Each is in its own `src/node-storage.ts`, exported from its package index, synchronous (every store constructor is), and builds that package's three stores over the one location with their existing defaults — including each key-value store's default `optimystic:txn:` prefix, which is what keeps its rows clear of the identity helper's. Each options type is the intersection of what that package's three stores accept, and is passed to each store that accepts one; in all four cases the block store's own options type turns out to be the superset.

Each ends by asserting its own result: `blockStoreCountsPieces(blocks, pieces)` must be true, and the throw names both identities. That is the boundary check that keeps a future edit — a piece store moved to a sibling directory, a second handle opened inside a factory — from silently making the node double-count its blob pieces.

### Who closes what

`close()` releases what the factory opened and nothing else, in one order across all four: the piece store, then the key-value store, then the block store, each step in `try`/`finally` so a rejection still closes the stores under it.

- **fs** — the order is *required*: the last store over the directory is what checkpoints the shared write-ahead log and removes the lock, so the block store goes last. This is the order `openBackend` in `packages/upgrade-check/test/current-build.ts` still uses by hand.
- **ns** — the piece store and the key-value store have no `close` (both write by autocommit statement), so their `flush()` is called instead: a flush is the whole of what closing either would mean, and it is what this package's readme told hosts to do at shutdown. Then `SqliteRawStorage.close()`.
- **web, rn** — the key-value store's `close()`, then the block store's. Nothing is called on the piece store: each put is durable when it resolves, so it has neither a `close` nor a flush with work to do.
- **ns, web, rn all leave the handle alone.** The host opened it, may be sharing it with the identity helper or with Quereus, and closes it afterwards. Stated on each function and in each readme.

### The fs factory returns one storage per directory

`fileNodeStorage` keeps a process-wide map from resolved directory identity to the stores it opened and counts its holders: the stores close when the last holder closes, the entry is dropped then, and a later call over that path opens them afresh.

Not a convenience — for files the location is named by a path rather than held as an object, and a second `FilePieceStore` over one directory is *documented-unsupported* (its open deletes the first's in-flight temps and fails its next put), unlike the block and key-value stores, which already share one log and one lock per directory by design.

### reference-peer

`openStores` is now one line — `fileNodeStorage(options.storagePath!)` for `--storage file`, `memoryNodeStorage()` for memory — and its hand-written three-step close chain is gone. The comment keeps both of its points: the CLI closes the storage because the node closes no store it was handed (after `stop()`, and on a failed `createLibp2pNode`), and memory storage is passed explicitly because a peer that asked for memory means it.

### Docs

Each storage package's readme section on handing stores to a node is replaced by the one call, each saying what the location is, that the three stores share it and therefore report one store identity so pieces are counted once, and who closes what. `packages/db-p2p/docs/storage.md` §8 gained two paragraphs naming the four functions and the fs one-set-per-directory rule; `docs/blobs.md` §The local store names the four in its piece-store paragraph.

## Two deviations from the ticket, both deliberate

**1. Two `fileNodeStorage(dir)` calls return two handles over the same three stores, not one identical object.** The ticket asked for both "two calls return the same value" and "make the returned value's `close` idempotent per holder" — which cannot both hold of one shared object, since there is then no way to tell one holder closing twice from two holders each closing once. The returned value is therefore a fresh three-field handle per call whose `blocks`, `kv` and `pieces` are the *same store instances*, with a `close` that releases its own holder at most once. The invariant the ticket is really after — one directory means one set of stores — holds exactly, and the test asserts it by instance identity on all three fields. **Worth a second opinion**: if the literal shared object is preferred, the idempotence requirement has to be dropped or moved onto a caller-supplied token.

**2. The map keys on `fileStoreIdentity(basePath)`, not bare `path.resolve`.** That is the same key the directory's write-ahead log registry uses (`FileWriteLog.acquire`), so the factory's map and the log agree exactly rather than approximately — it resolves the path *and* folds case on win32, where two cases of one directory are one directory and would otherwise be two sets of stores over it. The ticket's "does not normalise case" is true off win32 only; the residual under-approximation is parked as a `NOTE:` beside the map.

## Tripwires parked

- **Path spelling** — `NOTE:` above `openDirectories` in `packages/db-p2p-storage-fs/src/node-storage.ts`: two spellings that resolve differently (a symlink and its target; two cases of one directory on a case-insensitive volume off win32) are two map entries and two sets of stores over one directory, which double-counts pieces and breaks the piece store. The same under-approximation `identityForHandle` and the log registry make deliberately. Fix if ever reported: key on `fs.realpath`, which makes the factory asynchronous.
- **Options divergence is silent** — `NOTE:` above `fileNodeStorage`: the options are the first caller's, and a later call over a directory already open has its own options ignored without a word. The directory's log at least logs differing checkpoint settings; nothing here can, because a second caller constructs nothing for the log to compare.

## Tests

Two cases added, both in `packages/db-p2p-storage-fs/test/file-store-identity.spec.ts`, which already existed for this contract. Each gets its own `fs.mkdtemp` directory and closes every storage it opens, since the last close is what releases the directory's lock.

- **`gives the block store and the piece store one identity, so pieces are counted once`** — verifies `blockStoreCountsPieces(storage.blocks, storage.pieces)` is true for a storage over one directory. This is the claim `docs/blobs.md` §The local store makes about a Node host, and the thing each factory's own assertion protects.
- **`opens one set of stores per directory, released by the last holder`** — verifies the reference counting, using `store.lock` as the observable (present exactly while some holder has the directory): two calls hand back the same three store instances; the lock survives one holder closing, and that holder's write is still readable through the other; the lock survives the *same* holder closing twice, so a double close does not release another holder's stores; the lock is gone after the last holder closes; and a call after that opens a fresh set which reads what the released set flushed.

**No test for the three handle-taking factories**, as the ticket specifies: each is three constructor calls over a handle the caller passed, with no branch, and the identity assertion inside is what would fail if that stopped being true. See the next section for why that is not quite free.

## Known gaps — read these first

- **The ns and web identity equality had no test before this change, and still has none.** `packages/db-p2p-storage-rn/test/leveldb-piece-store.spec.ts` already asserts `blockStoreCountsPieces` over one LevelDB handle, but nothing asserted it for SQLite or IndexedDB — so an assertion that was *wrong* would have been a crash on every call, shipped untested. Each was therefore verified once by hand, with a throwaway script per package (written into the package's `test/`, run, deleted — nothing committed, working tree confirmed clean): each factory constructed, passed its own assertion, round-tripped a key-value write and closed cleanly. The reviewer may reasonably decide ns and web deserve a committed one-line case each beside the rn one; the implementing judgment was that the factory's own assertion plus each package's existing store suites cover it, and that a test asserting what the factory already throws on is a duplicate.
- **`openStores` in reference-peer is covered by `tsc` and nothing else.** No spec in that package exercises `cli.ts`, so the `--storage file` path has not been run since the change. Worth a manual `yarn workspace @optimystic/reference-peer start --storage file --storage-path <dir>`, stop, and restart over the same directory: the restart should read what the first run committed, and `<dir>/store.lock` should be absent between runs.
- **The four storage packages' own suites and `packages/reference-peer`'s were not run** — per `tickets/rules/testing.md`, full package suites are review's, and only the one spec file this change touched was run here. The fs package's other specs construct their stores directly and are untouched by the new module; nothing in the other three packages' specs imports `node-storage.ts`.
- **Root `yarn typecheck` was not run**: neither `quereus-plugin-optimystic` nor `quereus-plugin-crypto` changed, which is the condition the project rules attach it to.
- **`yarn lint` was run on the changed files only**, not repo-wide.

## What was checked and needs no action

- **No spec depends on two independent fs store sets over one directory.** Every `new FileRawStorage` call site in the repository was listed: all of them construct directly, so none goes through the factory and none sees the shared write groups. `packages/quereus-plugin-optimystic/test/legacy-commit-atomicity.spec.ts`, the one that deliberately builds a bare `FileRawStorage` beside the one the plugin opens and reasons about a per-directory warm cache, is unaffected for the same reason.
- **`packages/upgrade-check` keeps building its three stores by hand** and was not touched; its job is to reproduce each release's directory layout, which for `fs` is two directories. Its suite is green (341 passing) and its `typecheck` passes.
- **Nothing is logged** by any factory, so no `docs/debugging.md` row is owed and `packages/db-p2p/test/logger.spec.ts` is unaffected.
- **No new dependency**: each factory imports only its own package's modules and `@optimystic/db-p2p`, which each package already declares.
