# Review: torn action, part 3 of 3 — cleanup, tripwire, mesh coverage, validation

Third and final part of `torn-action-must-recognize-its-own-durable-work`. Parts 1
(`torn-action-pend-tier-carve-out`) and 2 (`torn-action-own-entry-consumption`) already landed the
behavioral fixes; this part carried no behavior change of its own except the new test.

Background in one paragraph, for a reader with no context: a write commits its blocks in stages —
collection header, then the collection's log tail, then everything else. If one of those later
blocks loses a race, the whole write is reported as failed even though the log tail is already
permanently stored. That is a "torn action". It used to leave the writer either stuck forever
(its own committed revision looked like a rival's to its retry) or recording the same entry twice.

## What changed

**Dead filter clause removed** (`network-transactor.ts`). The non-tail sweep filtered on
`bid !== tailId && !(headerId && bid === headerId && !blockIds.includes(headerId))`. The second
clause is unsatisfiable: `bid` comes from `blockIds`, so `blockIds.includes(headerId)` is
necessarily true whenever `bid === headerId`. Reduced to `bid !== request.tailId`, with a comment
saying plainly why the header needs no exclusion and why the header -> tail -> sweep order must
not be reordered (`Collection.bootstrapContext` depends on tail-first; tail-last would let a
committed header point at a never-committed tail). No behavior change.

**Stale NOTE rewritten** (same file, the non-tail sweep's error branch). It used to defer the
whole problem to a ticket that is this work. It now describes the resolved state: the refusal
stays a refusal (acknowledging a torn action is worse), but its two former harms are handled
upstream — the re-pend's own-revision carve-out at all three pend-tier checks, and the retry's
consumption of its own committed log entry. It also names the one arm that is NOT covered: the
multi-collection path (`TransactionCoordinator`) still refreshes without telling the collection
which of its own actions is in flight, tracked as
`tickets/fix/refresh-must-always-know-its-own-in-flight-action`.

**Tripwire NOTE, not a ticket** (`coordinator-repo.ts`, the `ConflictRaceLostError` conversion in
`pend`'s catch). With three or more contenders, members' votes can split so every contender is
told it lost — an all-lose round where nobody wins. Since parts 1-2 that costs one retry cycle
instead of wedging, and convergence rests on the aged retry priority carried on the re-pend plus
jittered backoff separating contenders next round. Recorded with a `NOTE:` tag and a revisit
condition (syncs exhausting `maxAttempts` on repeated all-lose rounds -> make the winner
deterministic, don't raise `maxAttempts`).

**New mesh-tier regression test** — `concurrent-diary-append-acknowledgement.spec.ts`, third `it`.
A `tearFirstCommit` wrapper makes the first commit tear deterministically: it delegates the tail
(and header, when present) to the real transactor, drops every other block, and answers the caller
with the retryable-conflict shape a genuine later-block loss produces. The test seeds one entry,
appends a second through the tearing transactor, and asserts the entry appears exactly once in the
writer's own view and exactly once on a node that never saw the tear.

## Known gaps — please probe these

- **The new test pins part 2's arm only, not part 1's.** Mutation-disabling the pend-tier
  own-revision carve-out in `StorageRepo.pend` leaves the new test passing. Reason, measured: a
  Diary's `append` module touches no blocks (entries live in the log), so the action's commit
  carries exactly **one** block — the tail — and `tears[0].dropped` is 0. With the entry-consumption
  fix in place the writer's refresh drains its pending set and the sync loop exits without ever
  re-pending, so the pend tier is never re-entered. Pinning that arm needs a collection whose
  action writes blocks beyond the log tail. This is stated in a comment at the test site, and
  part 1 is covered directly at its own tier by `storage-repo.spec.ts` and
  `cluster-pend-staleness.spec.ts`. If you think a mesh-tier wedge test is worth having, that is a
  fair finding — it was not built here.

- **db-p2p tests consume db-core's built `dist`, not its `src`.** This bit me: an early mutation
  run appeared to prove the test was worthless when in fact the compiled fix was still being
  loaded. Any db-core change must be rebuilt (`yarn workspace @optimystic/db-core build`, or root
  `yarn build`) before db-p2p tests can see it. Worth knowing if you re-run any of this.

- **The DEBUG reference-peer run did not exercise the commit-level tear.** Grepping that run's
  output: 39 `race-lost`, 8 `pend-error`, 1 `stale-classified`, 2
  `cluster-member:validation-stale-revision` — so it genuinely contended — but zero
  `non-tail commit had errors`. Consistent with the point above: a diary append's commit has one
  block, so there is no non-tail sweep to fail. The reference-peer spec exercises the pend-tier
  race, not the commit-tier tear; the new mesh test is what covers the tear. The grep log was
  deleted after use.

- **`tearFirstCommit` returns a hand-written delegating object**, not a spread of the inner
  transactor (`NetworkTransactor` is a class; a spread copies no prototype methods). If
  `ITransactor` gains a method, this wrapper will not forward it and the omission is silent —
  a plausible thing to flag.
