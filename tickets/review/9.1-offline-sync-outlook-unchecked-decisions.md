## What was built

- **`write-description.ts`** — `UncheckedRead` (`table` as Quereus's lowercased `QualifiedName`, `kind`, `scope`, and `rows: PinnedRow[]` for a `row` read: each pinned row's unique key and bound values), `uncheckedOf(write)` (pure, the derivation table of the ticket), two new `WriteFact` kinds (`statement` with its decisions, `undescribed`), `TransactionWriteFacts.described` (the `WeakSet<TableWrite>` that keys "once per statement"), and `foldWriteFacts` now answering `EntryFacts.unchecked` (statements' lists concatenated in order, deduped by (table, kind, scope) with pinned rows merged) and `EntryFacts.complete` (no `undescribed` record).
- **`commit-outlook.ts`** — `OutlookSchema` (`describe` and `table(name)`), `MainTreeKeys` and `TableOutlookSource.mainTree()`, `EntryFacts.unchecked`/`complete`, `EarlierEntry.tables`, `WriteIndex` writers per table beside writers per collection (`writersOfTable`), `OwnJudgement.unchecked`, the `via: 'unchecked'` dependencies in `outlookFrom` with `'guard'` winning and `kind` ignoring them, and the rendering.
- **`txn-bridge.ts`** — `noteWriteDescription(write)`: the first call for a `TableWrite` object records `{ kind: 'statement', unchecked: uncheckedOf(write) }`; a call with no description records `undescribed`. Kept, truncated on savepoint rollback and folded exactly as the fresh-element facts are.
- **`optimystic-module.ts`** — the vtab calls `noteWriteDescription(args.writeScope)` once at the top of `update()`, ahead of every arm's staging (DELETE included); `outlookSource.mainTree()` answers the main collection id and a `rowKey(key, values)` that reorders the values into primary-key order (names compared lowercased, any order) and encodes through `asPrimaryKeyTuple` and `createPrimaryKey`, the path a point lookup's seek key takes; `undefined` when `key` is not the primary key or the codec throws (logged `outlook:row-key-unencodable`).
- **`offline-mode.ts`** — implements `OutlookSchema`: `describeCollection` as before, and `table(name)` through a lowercased index of the published table names (`tablesByLowerName`, kept by `setTablePolicy`/`withdrawTablePolicy`) and the table's `mainTree()`. `EarlierEntry.tables` is the tables of the collections the entry still holds (the same set `FollowedEntry.tables` uses).
- **Docs** — docs/offline-sync.md: the `unchecked` and `dependsOn` comments in §The outlook, §Unchecked decisions (the derivation table, the four-to-three binding-mode map, the three resolutions), §Dependencies between entries (key-or-table matching, `'guard'` winning, deferred records by table), stage 9's status, and the test-plan paragraph. README § Offline mode: the `dependsOn` and `unchecked` bullets, a paragraph on `unchecked`, the example JSON now `"unchecked":[]`. docs/internals.md: one clause in the plugin-offline paragraph.

## Where the build differs from the ticket's sketch

Each is a simplification with the same observable behaviour; a reviewer may prefer the sketch.

- **Decisions are resolved when judged, not at `outlookFrom`.** `OwnJudgement.unchecked` holds each decision already rendered (`{ table, kind, scope }` with the published `schema.table`, or Quereus's name for an unpublished table) beside its span — the encoded main-tree keys of a `row` read, or the table name. So `followOutlooks` needs no schema and the rendering and key encoding are frozen with the judgement, which is what "fixed when judged" was meant to say. `judgedReads` in commit-outlook.ts is the one site.
- **`uncheckedOf(write)` takes no separate `target`**: `write.table` is the written table by Quereus's contract (a write through a view is described as the base-table write it becomes).
- **`noteWriteDescription(write)` takes no `describe` callback**: the bridge calls `uncheckedOf` itself; the vtab passes `args.writeScope` and nothing else.
- **`mainTree()` has no `keyColumns`**: `rowKey` does the column matching, so the field had no consumer and was left off.
- **The target rule reads "no wider than the selection" literally**: a `rows` watch on the target under a `rows` selection is dropped only when it has the selection's key and every tuple is among the selection's (`withinSelection`), so a subquery over the target pinned to a *different* row (`set x = (select y from t where id = 'other') where id = 'me'`) is a `read` rather than being silently dropped. Not pinned by a test; the shape did not come up in the write-scope output I checked.
- **The foreign-key rule prefers the whole-table watch on the parent** (`parentWatch`), since that is how Quereus lists the probe today, so a statement that also pins a parent row in a subquery keeps that as its own `row` read (pinned by a unit case). When Quereus narrows the probe to `rows` the first unconsumed watch is taken, and the two labels may swap; the union of dependencies is the same.
- **`undescribed` is pushed once per cascade row**, not deduped; the fold reads it as a flag either way.

## How to exercise it

- `select CommitOutlook()` inside an open transaction after `insert into Messages (…) values (StampId(), 'c1', …)` where `Messages.conversation references Conversations(id)`: `"unchecked":[{"table":"main.Conversations","kind":"foreign-key","scope":"global"}]`, and `dependsOn` naming the queued entry that inserted `c1` with `via: 'unchecked'` while that entry is unsettled. The outlook stays `assured` when the message's own key is fresh.
- `update T set done = 1 where status = 'open'` → `unchecked: [{ table: 'main.T', kind: 'row-selection', scope: 'global' }]`; `update T set n = n + 1 where id = ?` → `unchecked: []`.
- `insert into Memos (id, body) select id || '-copy', body from Notes where id = 'n7'` queued behind inserts of `n7` and `n8`: `dependsOn` lists the `n7` entry only, `via: 'unchecked'`, with `unchecked: [{ table: 'main.Notes', kind: 'read', scope: 'row' }]`.
- A transaction that both updates a row an earlier entry wrote and reads it through a foreign key lists that entry once, as `'guard'`.
- An `on delete cascade` foreign key: the cascade's child deletes carry no description, so the deleting transaction's `unchecked` is `'not-computed'`. By inspection only (Quereus's `resolveWriteScope` returns `undefined` under the cascade re-entry flag).

## Known gaps, honestly

- **Paths without a test**: `assertion` decisions (no assertion in any spec); `foreign-key-parent` on an UPDATE of a referenced column (only DELETE is pinned); the unpublished-table rendering (a table on another module); the cascade → `'not-computed'` path; deferred journaled records matched by table through an unchecked span (`outlookFrom`'s second deferred loop) — the restore spec has no FK table, and the next ticket, which journals the facts, is the natural place to pin it. Each follows the same few lines as a pinned sibling.
- **A `row` read pinned by a UNIQUE column rather than the primary key** (`… from T where email = ?`) is matched by table, not by key: `rowKey` answers `undefined` for a key that is not the primary key. Correct and conservative; one extra dependency at most.
- **A statement that stages nothing** (an `insert or ignore` that swallowed) still has its decisions recorded, since the record is made ahead of staging. One decision too many, by design.
- **`StampId()` in an autocommit INSERT is still NULL** (backlog `bug-stampid-is-null-inside-an-autocommit-insert`); the new SQL cases use explicit transactions as the earlier ones do.
- **Not run**: `yarn check:rn`, `yarn test:integration`, the db-core suite (no db-core change).
