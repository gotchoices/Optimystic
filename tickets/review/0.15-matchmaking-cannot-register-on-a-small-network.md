# Matchmaking cannot register on a small network — review handoff

GitHub #67. `MatchmakingProviderSession.register` on networks of 1–3 hosts with `cohortTopic.enabled` threw `CohortBackoffError` ("no willing primary right now") on every retry. The admission quorum in `GossipWillingnessCheck.evaluate` was `defaultQuorum(16) = 9` for every FRET cohort, and such a network's cohort has at most three members, so the decline was immediate and permanent.

## What changed

- **Quorum follows the live cohort** (`packages/db-core/src/cohort-topic/willingness.ts`). The default quorum is `defaultQuorum(m)` where `m` is the size of `WillingnessDeps.cohortMembers()` with self counted once, read once per evaluation (`readCohort`, which also yields the unheard count for `awaitingMembers`, so both come from one read). `WillingnessConfig.cohortSize` is removed; `WillingnessConfig.quorum` stays as the override. `cohortMembers` is now **required** (it was optional): the quorum cannot be computed without it, and every production and test caller now supplies it.
- **Host** (`createCoordEngine` in `packages/db-p2p/src/cohort-topic/host.ts`) no longer passes `cohortSize`; the existing `cohortMembers: () => cohort().members…` is the one source for both placements (FRET cohort and root group). The "read once … merely permissive" comment is gone.
- **Docs** (`docs/cohort-topic.md`): §Admission quorum rewritten (`⌊m/2⌋ + 1`, read every check, both placements, the 1/2/3-machine outcomes, the accepted transient-view consequence), a sentence in the "It is not `minSigs`" paragraph saying a sub-`k` cohort admits and answers queries but cannot threshold-sign (certs, notices, child links), the root-placement implementation note, and the configuration table row. `yarn lint:docs` clean.

## Tests

- `packages/db-core/test/cohort-topic/willingness.spec.ts` — the former awaiting-members test is now the regression: default config (no quorum override), a three-member `cohortMembers` list: declines `awaitingMembers: true` with nobody heard, still `true` after one sibling answers unwilling, `false` once both answered unwilling, `accepted` once one sibling is willing (self + 1 = majority of 3), and declines `awaitingMembers: true` again after the list grows to five (pins the per-evaluation read). The other tests in the file keep their explicit `quorum: 2` and gained a `cohortMembers` built from the view's heard members (helper `membersHeardIn`).
- `packages/db-p2p/test/matchmaking-small-network.integration.spec.ts` (new, gated on `OPTIMYSTIC_INTEGRATION=1`) — real TCP meshes of 1, 2 and 3 nodes, `cohortTopic: { enabled: true }` with no `wantK`/`minSigs` override. A `MatchmakingProviderSession` registers (bounded retry, 30 s), then a `createLibp2pMatchmakingSeekerSession` on a node that is not the topic's routed member walks to it (2 and 3 machines; at 3 the provider also sits off the routed member, so both sides cross the network). **Negative control run:** with the host temporarily forced back to `quorum: 9`, all three cases fail with "cohort-topic: no willing primary right now" — the #67 error verbatim; reverted and rebuilt afterwards.
- Mechanical updates only: `member-engine.spec.ts` (dropped `cohortSize`), `service.spec.ts` (`cohortSize: 1` → `cohortMembers: [self]`).

Runs: db-core `yarn test` 2060 passing; db-p2p `yarn test` 3660 passing / 78 pending; db-p2p `yarn test:integration` 54 passing / 2 pending (the existing `it.skip`s). eslint clean on the changed files.

## Deviations from the ticket and known gaps

- **One machine queries instead of walking.** The ticket asked for the seeker walk "on the same node at N=1". That cannot pass today: the walk registers the seeker under the node's own peer id, the registration store keys by (topic, participant), so the seeker record replaces the provider's, and the walk's closing withdraw removes it. Verified on a real node (provider listed by a `QueryV1` before the walk; walk returned nothing; neither provider nor seeker listed after). Filed as `tickets/backlog/bug-a-walk-by-a-provider-replaces-its-own-registration.md` (needs a design call: may one peer hold both roles on a topic). The N=1 case asserts the seeker session's one-shot `query` finds the provider and that the entry's `registrationSig` verifies.
- **Self-serve bound by hand.** A seeker whose own node is the cohort member needs `MatchmakingSelfServe`, which the node does not offer (existing backlog `feat-node-offers-matchmaking-self-serve`; I appended a section there describing the binding this spec built). The spec's `selfServeOn` routes a self-addressed register through a `FretTopicRouter` over the node's own FRET (FRET's activity handler runs the same admission as any routed register), answers queries with `createMatchmakingQueryHandler` in process, and renews with `resolveRenew`. At N=1 every seeker message uses it.
- **Threshold signing on a small network** (the ticket's "adjacent risk"). Register and query (seeker register, `QueryV1` under a single member's signature) needed no threshold signature at 1–3 machines. I did not check what the gossip-cadence driver does with the membership-cert publish it cannot complete on such a network (`minSigs` 14 > members) — possibly a failed `/sign` round per engine per refresh; worth a look for log noise or wasted dials, not for correctness.
- **Tripwire:** `willingSiblings` counts every member the gossip view holds, including one that left `cohortMembers`, against a quorum now taken over `cohortMembers`. Parked as a `NOTE:` at that method.
- Accepted consequence (documented, as the ticket asked): a transiently shrunken cohort view lowers the quorum for that moment; it cannot admit anything an honest network of that size would not.
