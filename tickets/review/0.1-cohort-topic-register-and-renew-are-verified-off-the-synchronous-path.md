## What changed

**Signatures are checked in the host, and the engine stays synchronous.** `verifyRegisterSig` and `verifyParticipantSig` are gone from db-core. A live-signer host authenticates a frame before handing it over, a key-less host hands frames over unchecked as it did before, and that contract is written on `handleRegister`, `handleRenew` and `onRenew`.

**A frame's origin decides whether it is checked.** `handleRegisterFrame` takes `"self"` from the router's `handleLocally` (frames this process just built) and `"remote"` from the `/register` handler and the FRET activity handler. The activity handler is always `"remote"`, because FRET does not say who sent a frame.

**Register and probe** (`dispatchRegister`): a `rootKey` on a host serving no root groups is refused with no crypto, then the signature is checked (failure answers `no_state`), then `now` is taken, then the root-group read and engine creation. So a forged frame now reads no group and creates no engine, which it used to do. The rate limiter stays behind the signature; the reason is at `runGuards` and in docs §Anti-DoS.

**Withdraw and re-attach** (`resolveAuthenticatedRenew`): no holder or a frame the freshness gate refuses is answered without crypto. Otherwise it verifies, looks the holder up again, and runs with a clock taken after the wait. Plain pings and the renew batch check nothing.

**One shared check.** `peerSignatureVerifies` replaces `gossipSignatureVerifies` for gossip, register and renew: non-empty test, guarded and logged decode, `verifyPeerSigAsync`.

**A diagnostic for the open question.** Each withdraw or re-attach this node answers logs on the `optimystic:db-p2p:cohort-topic` namespace: `privileged-renew kind=<reattach|withdraw> origin=<self|remote> answer=<result>`. It is documented in `docs/debugging.md`.

## Tests

| Test | What it verifies |
| --- | --- |
| `inbound-signature-gate.spec.ts`, register over the stream / through the activity handler | Each forgery (noble-only signature, a different key's, none) gets `no_state`, holds no record and creates no engine; the same frame correctly signed on the same host is admitted |
| same, probe | Forged probes get `no_state` on a served topic and create no engine on a cold one; correctly signed they resolve and reach an engine |
| same, re-attach | Forged gets `primary_moved` and the stored primary stays; correctly signed, the backup promotes itself |
| same, withdraw | Forged gets `unknown_registration` and the record stays; correctly signed, it evicts |
| `peer-sig.spec.ts`, order-8 nonce control | noble accepts the crafted signature and the platform refuses it, while both accept an honest one, so the table cannot pass vacuously if the two verifiers converge |
| `registration.spec.ts`, `refusalBeforeSignature` | For withdraw, re-attach and both flags set: refuses stale, future and not-newer-than-`lastPing` frames with exactly the answer `onRenew` gives; no record answers `unknown_registration`; a fresh frame returns `undefined` |
| `peer-key-signing.spec.ts`, key-less host | An unsigned register is admitted and an unsigned withdraw acts, through the real `/register` handler |

## Decisions a reviewer should check

- **`cohort-topic-scale-antiflood.spec.ts` needed a change, and this ticket caused it.** Its "burst of registrations" test failed every run: a walker got `promoted` at about walker 17 and then backed off. Measured on 36 walks: with the platform verifier the burst runs 0.9 to 3 ms per walk and the slope lookahead promotes; with noble substituted it runs 5 to 9 ms per walk and all 36 attach; with the lookahead off all 36 attach under either verifier. The promotion is correct for that arrival rate, and the test's "sparse regime" premise only held because noble slowed the burst. I set `promotion: { tPromoteLookaheadMs: 0 }`, which the mesh harness documents for this and the reactivity harness already uses. No assertion changed. A consequence I did not measure: a real phone whose arrival rate was limited by slow verification can now reach the slope rule sooner.
- **The key-less test changed more than "stays" implies.** It called `ce.engine.handleRegister` directly, which now pins nothing because the engine checks no signature on any host. It now drives the real `/register` handler and also covers an unsigned withdraw. Its two round-trip neighbours now use `verifyPeerSigAsync`, the verifier the host actually runs.
- **Small departures from the design text.** The success path calls `holder.engine.handleRenew` rather than `resolveRenew`, with the same effect and no third registry walk. An async `resolveInboundRenew` means a plain ping still passes through one `await`, but its decision is made synchronously with no verification wait, which is how I read "no await added".
- **A polyfill detail the ticket did not have.** `@libp2p/crypto`'s probe calls `subtle.generateKey({ name: 'Ed25519' }, true, ['sign', 'verify'])`. A polyfill providing only `verify` fails the probe and silently stays on noble, and a passing probe also routes signing through WebCrypto. The readme row says so.

## Known gaps

- **Nothing here runs Hermes or a phone.** I did run libp2p's browser build under Node: its WebCrypto path accepted an honest signature with a key decoded from a peer id. That shows the route works on Node's WebCrypto, not on any polyfill.
- **The verifier change saves nothing per check on a runtime with no WebCrypto Ed25519**, and no on-device saving was measured. There, only the self-frame skip and the early refusals help.
- **We did not reproduce the reported idle cost**, and its cause is unknown (see the reply below).
- **"No crypto" on the early refusals is by inspection.** No test counts verifications, since noble's `ed25519` object is frozen and no test-only option was added. Registers refused for a root key and renews with no holder or a stale timestamp are in this group.
- **Other edge cases are by inspection, as the plan expected:** the second holder lookup, an engine or record evicted during the wait, and two frames finishing out of order.
- **`privileged-renew` only covers frames arriving through `handleRegisterFrame`.** `MatchmakingSelfServe.renew` binds `resolveRenew` directly for this node's own frames and would log nothing; only the integration spec binds it today.

## Tripwires parked

- Unrated verifications from forged fresh frames: `NOTE:` at `peerSignatureVerifies`.
- A plain ping overtaking a privileged frame during its verify: accepted, `NOTE:` at `resolveAuthenticatedRenew`.
- The `NOTE:` at `publishSink` is reworded: only a validly signed frame creates an engine now, or any frame on a key-less host.

## Wording for the release note

Inbound cohort-topic registers, probes, re-attaches and withdraws are now verified with the platform's Ed25519 verifier instead of pure JavaScript, and a node no longer verifies frames it sent to itself. **Host requirement:** to get native verification on React Native, install WebCrypto Ed25519 on `crypto.subtle` (`generateKey`, `importKey`, `sign`, `verify`) before `@libp2p/crypto` is first imported. Without it each check costs the same as before. See the "Global polyfills" table in `packages/db-p2p/readme.md`.

## The reply owed to #55 (not posted; for the human)

Register and privileged renew frames now use the platform verifier. A phone needs WebCrypto Ed25519 installed before `@libp2p/crypto` is first imported, including `generateKey`, which is what the library probes for, or each check costs the same as before. A node no longer checks its own frames.

Plain pings were never signature-checked, at HEAD or in your 1.24.0. On a healthy two-machine group idling for about 375 s (Node, not Hermes) we measured zero signature checks. So the reported 306 ms means your S21 was receiving re-attach or withdraw frames while idle, which we could not reproduce. The verifier change may therefore not be what removes it.

Could you turn on `optimystic:db-p2p:cohort-topic` and report the `privileged-renew` lines, which give each frame's kind, origin and answer? Please also tell us whether your two phones' clocks differ. Differing clocks could make a re-attach fail the freshness rule after its signature was paid for, and the registration would then fail over again later, so the answer may be a failover bug rather than a verifier cost.
