# A member checks the lane a transaction claims — review handoff

Third of four tickets from the plan `a-transaction-carries-its-lane`. A validating member now refuses a `convergent` claim that its own engine computes as `serializable`. The refusal carries the validity marker (`validityRefusal('Lane mismatch: transaction claims convergent, this node computes serializable')`). The member never reclassifies the transaction.

## What was built

- **`ITransactionEngine.laneCeiling?(transaction): Promise<Lane>`** is optional. `ActionsEngine` omits it, so a validator accepts an actions transaction's lane unchecked. The ticket said every actions transaction is `serializable`, but that is not true: a caller can pass `SyncOptions.lane: 'convergent'` with any engine. The doc comment says "unchecked" instead.
- **`TransactionValidator.validate` step 2.5** comes after the schema-hash step and before the read-dependency check, through `claimsLaneAboveCeiling`. It checks only a `convergent` claim. An absent lane (an older writer) counts as `serializable`. An engine without the method is not asked. A throw propagates, and `checkPendValidation` turns it into an unmarked `validator-fault`. I read `checkPendValidation` (passes `validity` through), `voteFor` / `signedValidity` in `cluster-repo.ts` (signs it) and `classifyCommitFailure` (`ValidityRejectedError` → `rejected`) and changed nothing there.
- **`QuereusEngine.laneCeiling`** runs `db.prepare(sql).getWriteScope(params)` for each statement and judges each write site with `replicatedCeilingOf` against `db.schemaManager.findTable`. It folds the results with `stricterLane`, then finalizes the prepared statement. It parses statements through `parseStatement`, which `execute` now shares, so the two readers cannot disagree on format. The cost tripwire is a `NOTE:` at the method.

## Deviation from the ticket: the member uses its own ceiling rule, not `laneCeilingOf`

The ticket assumed "a rebuilt per-row statement has the same table, operation, assigned columns and constraints as the original". **That is false for UPDATE.** I captured a real rebuild through `txnBridge.getStatements()`: Quereus's `buildUpdateStatement` assigns every column, the key included. So `update t2 set Title = 'b' where Id = 'k'` reaches the member as `update t2 set Id = 'k', Title = 'b' where Id = 'k'`.

`laneCeilingOf` answers `convergent` for the original and `serializable` for the rebuild. The rebuild carries a `primary-key` constraint from the assigned key column, and also any untagged column. Built as specified, the check would have refused every honest convergent UPDATE with a final validity verdict.

`replicatedCeilingOf` in `lane.ts` answers `serializable` only where every statement that could produce the rebuild has a `serializable` ceiling:

- **INSERT:** `laneCeilingOf` unchanged. I checked that original and rebuild list identical constraints when the original leaves out a UNIQUE, foreign-key or CHECK column, and under `or ignore` / `or replace`. Only the disposition is lost, and a `do update` already made the writer `serializable`.
- **DELETE:** `serializable`, the same as `laneCeilingOf`.
- **UPDATE:** checks the table's profile, that the selection is by the primary key, and that the table declares a merge on at least one non-key column. An UPDATE assigns at least one column, so with no such column every UPDATE is `serializable`.
- **A table the catalog cannot find:** `serializable`.

Consequence, stated in the code, in `transactions.md §What a member verifies` and in the validator's comment: a writer that claims `convergent` for an UPDATE of an untagged column, or for one that moves the row's key, is **not caught**. This joins provenance and read-dependence as something only the writer sees. I considered a key-move clause (written key literal ≠ selected key literal). I dropped it: it needs value comparison across `ScopeValue` / param placeholders / `compareSqlValues`, and it catches one lie among several of the same kind the member still can't see. The `NOTE:` at `replicatedCeilingOf` names the way out: if Quereus's rebuilt UPDATE ever assigns only the assigned columns, the UPDATE arm becomes `laneCeilingOf`.

**Reviewer: please challenge this rule.** It is a judgement call on a decision the plan marked open for a human. The alternatives were (a) block the ticket until Quereus changes its rebuild (a dependency outside this repo), or (b) compare old and new row values during re-execution. Option (b) depends on the member's state, which `laneCeiling` deliberately does not read.

## Tests added

- `packages/db-core/test/validator-refusal-class.spec.ts`, "refuses a convergent claim the engine computes as serializable, and never asks about a serializable one". This is the ticket's case: an engine double whose `laneCeiling` answers `serializable` and counts calls. A `serializable` transaction passes with zero calls. A `convergent` one is refused with `Lane mismatch` and `validity: {}`.
- `packages/quereus-plugin-optimystic/test/replicated-lane-ceiling.spec.ts` (new, 6 rows) reproduces the defect above. Each row runs the writer's statement in a rolled-back transaction, captures the bridge's real rebuilt statements, and asks `QuereusEngine.laneCeiling`. Each row asserts the expected ceiling and the property that a writer whose own `laneOf` is `convergent` is never answered `serializable`. Row 2, a same-key update of a merge-tagged column on a table that also has an untagged column, fails under plain `laneCeilingOf`. The rule was also run directly against the rebuild while investigating, but no mutation run was kept. It wraps the captured raw SQL with `createQuereusStatement` because of the format gap below.

## Known gaps

- **The statements the SQL layer records cannot be parsed by any member.** This predates the ticket. The bridge records raw SQL, while `QuereusEngine` reads `{ sql, params }` JSON. On a real SQL transaction, re-execution answers `Re-execution failed: … Unexpected token`, and a `convergent` claim now gets an unmarked `validator-fault` from step 2.5 first. Nothing runs this path today: no deployment validates, and every engine test builds statements with `createQuereusStatement`. I appended it as an arm of backlog `feat-no-deployment-validates-transactions-at-pend` (the open ticket that owns `quereus-validator.ts`), with `repro: static` and the two possible fixes.
- **No deployment validates at pend.** The check runs only where a validator is wired by hand. Noted at `claimsLaneAboveCeiling`.
- A member's assertion and cross-row CHECK constraints on a rebuilt UPDATE are not used to refuse, because I could not establish that the original would have listed them too. They err toward accepting.
