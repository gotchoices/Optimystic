# Review: the RPC dial deadline can be set per node

## What changed

`NodeOptions.rpcDeadlines?: Partial<RpcDeadlineDefaults>` — `{ dialTimeoutMs?, responseTimeoutMs? }` — sets this package's own RPC dial and response deadlines exactly, in place of the values `resolveLinkDeadlines` derives from `linkRoundTripMs`.

- Applied **inside** `resolveLinkDeadlines(linkRoundTripMs?, rpcDeadlines?)`, before `transferTimeoutMs = max(30000, dial)` and `transactionTimeoutMs = max(30000, 4 × dial)` are computed, so both follow an explicit dial. Hosts read `node.linkDeadlines` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`, `packages/reference-peer/src/cli.ts`), so an explicit dial reaches a host's `NetworkTransactor` `dialTimeoutMs` / `timeoutMs` with no host change.
- No floor: `{ dialTimeoutMs: 1000 }` gives a 1000 ms dial even though the derived floor is 3000.
- Precedence, highest first: a caller's per-request value → the `spreadOnChurn` / `underReplicationDrain` `push*` fields → `rpcDeadlines` → derived from `linkRoundTripMs`. The `push*` sites in `createLibp2pNodeBase` already fall back to `linkDeadlines.*`, so no code change was needed there.
- Validation throws at node construction (same reasoning as `linkRoundTripMs`): each present field must be finite and above 0 (so `0`, which means "no cap" on a single request, is refused as a node-wide policy); `dialTimeoutMs ≤ MAX_RPC_DIAL_TIMEOUT_MS` (= floor((2^31 − 1) / 5) = 429 496 729 ms, about 5 days, so `4 × dial + 5000` fits a 32-bit timer); `responseTimeoutMs ≤ 2^31 − 1`. The error names the field: `rpcDeadlines.dialTimeoutMs must be a finite number of milliseconds above 0 and no greater than …; got …`.
- `validLinkRoundTripMs` became `validDeclaredMs(field, value, ceiling)`, shared by all three checks; the `linkRoundTripMs` error message is unchanged.
- `MAX_RPC_DIAL_TIMEOUT_MS` is exported from the package entry (through `export * from "./rpc-deadline.js"` in `packages/db-p2p/src/index.ts`).
- Not enforced, documented instead: `rpcDeadlines.dialTimeoutMs` should not exceed `connectionManager.addressDialTimeout`, which libp2p applies to each address inside every RPC dial.

## Docs

- `NodeOptions.rpcDeadlines` doc comment: what each field bounds, no floor, precedence, what follows the dial, the `addressDialTimeout` relationship, what throws.
- `linkRoundTripMs` doc: `rpcDeadlines` added to the "explicit setting still wins" list. The `connectionManager` doc's closing `NOTE:` now points at `rpcDeadlines`. The `spreadOnChurn` / `underReplicationDrain` docs now say the `push*` fields default to the node's RPC deadlines (`rpcDeadlines`, else derived).
- `LinkDeadlines` type doc and `resolveLinkDeadlines` doc updated.
- readme "Slow relayed links": the admission-time sentence names the three overrides sereus uses (`connectionManager.addressDialTimeout`, `connectionManager.dialTimeout`, `rpcDeadlines.dialTimeoutMs`); the override list gains `rpcDeadlines` with its no-floor rule, what follows it, the `addressDialTimeout` relationship and its validation.
- cluster.md "Declaring the link instead" does not list overrides; one clause added where it says the cluster client carries the derived deadlines ("or `NodeOptions.rpcDeadlines`, when set").

## Tests added

All in `packages/db-p2p/test/link-deadlines.spec.ts`, `describe('resolveLinkDeadlines with explicit rpcDeadlines')`:

- explicit dial 1000 at r = 3000 → dial exactly 1000 (below the derived floor).
- explicit dial 40 000 at r = 3000 → transfer 40 000, transaction 160 000, every other field equal to `resolveLinkDeadlines(3000)`.
- explicit response 2500 at r = 3000 → response 2500, every other field unchanged.
- each field throws, with a message naming the field, on `0`, `-1`, `NaN`, `Infinity` and ceiling + 1.
- the dial ceiling is accepted, and `transactionTimeoutMs + 5000` there fits a 32-bit timer.

No node-construction test, per the ticket: the wiring is one argument at one call site.
