# Storage flushes once per write group — review handoff

Reported in GitHub #37. `raw-storage-can-be-flushed` gave every `IRawStorage` a `flush()` (a write is durable once a later flush resolves; what survives a crash is a prefix of the resolved writes, in order) and every backend a no-op one. This ticket makes the node call it. Nothing changes on disk yet: every backend's flush is still a no-op, so the observable behaviour is unchanged. Downstream tickets make the flush do real work (`file-storage-pays-one-fsync-per-write-group`, `mobile-and-browser-storage-keep-the-durability-window`) and decide the policy (`durability-window-scales-with-cohort-size`).

## What changed

**`StorageRepo` holds its store.** Constructor is now `new StorageRepo(storage: IRawStorage, options?)`. `options.createBlockStorage?: (blockId, storage) => IBlockStorage` builds each block's storage over that same store (default `new BlockStorage(blockId, storage)`), so the store blocks write to and the store the repo flushes cannot differ. All ~108 call sites were migrated by script (simple `(id) => new BlockStorage(id, raw)` became `new StorageRepo(raw)`; ones with extra `BlockStorage` arguments or a subclass moved into `createBlockStorage`); three block-body factories in `storage-repo.spec.ts` and the dispute specs' helpers were converted by hand. Now-unused `BlockStorage` imports were dropped.

**`createLibp2pNodeBase`**: the `(storageRepo as any).createBlockStorage = …` swap is gone. The factory closes over `let restoreCallback`, which is reassigned to the restoration coordinator after start; nothing else reads that binding.

**`StorageRepo.endGroup(work, wrote?)`** — one helper every write group ends through: awaits `work()` (which takes and releases its own latches), then one `storage.flush()`, then returns. A throwing `work` still flushes, then rethrows the original; a flush error behind it is logged (`group:flush-failed-after-fault`). A flush that rejects after `work` returned propagates, so the caller reports and emits nothing.

- `commit`: body moved to `commitUnderLatches`, which returns `{ result, collectionBlocks }` from both the stale early return and the normal end. `commit` = `endGroup` → `emitCollectionChanges` → return. Change events now fire only after the flush.
- `pend`: validation stays outside (it writes nothing and takes no latch); the latched body moved to `pendUnderLatches`, wrapped by `endGroup`. Every exit inside the latches flushes, refusals included.
- `cancel`, `recoverBlock`, `saveReplicatedBlock`: wrapped; `saveReplicatedBlock` emits after the flush.
- `get`: flushes only when some block's read entered a write latch — a per-call `ReadWrites` flag set inside the promotion's latch callback and inside `readBlockHealing`'s restore latch callback. Then `emitPromotions`, then `answerLineage`, as before. A get with no context or nothing ahead takes no latch and does not flush.

**`applyInvalidation`**: `InvalidationContext` gains required `flush: () => Promise<void>`, called after the latch release and before `ctx.log.addInvalidation`. `CollectionEnv` in `cascade.ts` gains the same field, threaded to its `applyInvalidation` call. Not wired in production (dispute has no composition root).

**`KvUnderReplicationLedger`**: `flushWrites()` (`await this.kv.flush?.()`) once per public call that wrote — `record` (when it wrote or eviction removed something; `evictBeyondCap` now returns whether it evicted), `settle` when it removed, `satisfy` when it changed or deleted, `name` when it named, `noteAttempt` when it wrote, `delete` always. After the block's queue is released, never inside it.

**Docs**: `packages/db-p2p/docs/storage.md` invariant 6 gains "Who calls `flush()`", "Visible before durable (accepted)", and the eight crash-recovery write orders (with the file-backend gap noted on 3 and 7); the StorageRepo component section and the usage example show the new constructor. `packages/db-p2p/docs/repo.md` example updated. `docs/internals.md` commit path: one line on the per-apply flush. `docs/correctness.md` Theorem 6 point 1 now says what each backend's flushed write survives and that `durability-window-scales-with-cohort-size` decides the policy; §1.2 says coordinator-state restore happens only with `NodeOptions.transactionStateStore`. `yarn lint:docs` clean.

None added, as the ticket specified: who calls flush is wiring, to be checked by review against the list above; the flush contract itself is the conformance case from `raw-storage-can-be-flushed`. A reviewer who thinks "events fire only after the flush" or "a throwing group still flushes" deserves a pin can add one with a `MemoryRawStorage` subclass whose `flush` records call order — but note no backend can make a flush do anything observable yet.

## Things to look at / known gaps

- **`get` with a throwing block.** `Promise.all` rejects on the first block that throws; `endGroup` then flushes (if any block took a latch) while sibling blocks may still be mid-promotion. Those writes are not covered by that flush and become durable with the next group's. Nobody reports them (the get failed, and their promotions are never emitted), so this matches the "a write outside a group" case, but it is a gap in "exactly one flush per call covers the call's writes".
- **`applyInvalidation` flushes only on the success path**, exactly as the ticket placed it. A throw mid-writes (a refused compensating write, `assertWriteLanded`) leaves revisions with no entry and no flush — the recoverable direction the existing crash-window `NOTE:` already accepts, and re-delivery re-applies. `StorageRepo.endGroup` by contrast flushes behind a fault; say so if the two should match.
- **Ledger flush rejection.** `record` rejecting is caught by `CoordinatorRepo`'s `allSettled` and logged; the answer then carries no `recordedBy`. `satisfy`/`noteAttempt`/`name`/`delete` rejecting fails the drain pass, which logs it (`pass error`), and no full-replication event fires for an entry whose removal may not be durable. `settle` rejecting is inside the same `allSettled`. Checked by reading, not exercised.
- **`createBlockStorage` doubles.** Tests that replace `BlockStorage` methods still go through `createBlockStorage`; the repo flushes the `MemoryRawStorage` they pass (a no-op).
- **Concurrent groups share visibility before durability** (latches released before the flush). Documented as accepted under invariant 6; relies on rule 3 (prefix) holding for every backend, which today's backends do not all establish past a process crash — that is the downstream tickets' work.
