# File store syncs by the earliest deadline — implemented, for review

Fourth of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). `FileWriteLog` now defers the sync of a batch whose commit allowed it, and `FileBatchBackend` and `FileKVStore` pass the window through and forward `sync()`. Nothing outside `packages/db-p2p-storage-fs` changed except `packages/db-p2p/docs/storage.md`.

## What landed

`FileWriteLog.commit(entries, { syncWithinMs })` returns a `CommittedBatch` (`packages/db-p2p-storage-fs/src/file-write-log.ts`):

- **Append** (`append`): encode, `writeAll`, add to `appendedBytes`, push an `UnsyncedBatch { entries, deadline, durable }` onto the in-order `unsynced` list and lower `earliestDeadline` if this one is sooner. The deadline is `Date.now() + syncWithinMs` taken when `commit` is *called*, before the task waits in the queue, so a commit that waited in line past its own window is already overdue when it runs. A strict batch (`syncWithinMs` 0) has no deadline of its own; its deadline is the commit.
- **Strict, or the earliest waiting deadline has passed** (`deadlinePassed`): the sync step runs inside the same queued task before the commit resolves. The second case is the backpressure rule.
- **Otherwise**: `armSyncTimer(deadline)` arms the log's `setTimer` for the deadline unless a timer is already armed for one no later. The commit resolves with a pending `durable`.
- **Sync step** (`syncUnsynced`), always called from inside a queued task (a commit, `sync()`, the timer's task, or a checkpoint's seal): `handle.sync()`, then `applyBatch` for each covered batch in order into `this.dirty`, then resolve each `durable` in order, clear the list, disarm the timer. A failure anywhere latches the log and rejects every covered `durable`, including those whose tree write succeeded.
- **Timer fires** (`syncInBackground`): enqueue the sync step; a failure is logged on the `write-log` channel, like a background checkpoint failure.
- **`sync()`**: enqueue the sync step; with nothing waiting it touches no disk. `throwIfFailed` first.
- **Latch** (`latch`): one place now sets `fault`, rejects every waiting `durable` with `StoreFailedError`, clears the list and disarms the timer; used by the append, the sync step, the open, and both checkpoint fault sites. A failed append therefore also rejects the earlier batches still waiting, since no sync will ever be made for them.
- **Seal** runs the sync step first, before the rename, so a sealed segment holds only synced records whose tree writes are in the taken dirty set. The `appendedBytes === 0` early return cannot skip a waiting record (a waiting record always has bytes; `appendedBytes` is reset only in the seal, after the sync step); the argument is in the `seal` doc comment.
- **`shutDown`** disarms the sync timer beside the idle checkpoint timer; the final checkpoint's seal syncs whatever waits.
- **`window-overrun`**: logged once per episode by `reportOverrun` with the lateness in ms and the batch count; an episode ends at the next on-time sync (a sync covering no deadline counts as on time).

`FileBatchBackend.commit` passes the options through and returns the log's `CommittedBatch`; its `sync()` forwards to the log when one has been acquired and resolves otherwise. `FileKVStore`'s group sink does the same. `SYNCED_BATCH` is gone (nothing returned it any more). `FileBatchBackend.durability` stays `'power-loss'`.

Docs: `packages/db-p2p-storage-fs/README.md` sections *Write-ahead log*, *What a crash loses* (a process crash loses nothing a flush resolved; a power cut loses at most the groups inside their window, always a suffix, by the CRC argument), *Durability* (one sync per strict group, one per window otherwise, the idle checkpoint as the bound, the `window-overrun` line) and the tests list. `packages/db-p2p/docs/storage.md`: the Invariant 6 table row for `FileBatchBackend`, the "none does yet" sentence above the table, the *file backend* paragraph (the deferral, backpressure, the overrun line, the failure rule, the prefix-by-CRC argument), and the performance bullet.

## Where the implementation deviates from the ticket, deliberately

- **Overrun is measured at the sync's start, not its finish.** The ticket says "if it finished after the earliest deadline it covered". A sync that starts at its deadline finishes after it by the fsync's own duration, so by that letter every timer-driven sync is late and a strict commit's own inline sync is late too (its deadline is the moment it was appended), so the "episode" would never end and the line would say nothing. `reportOverrun` instead reports when the sync *started* after the earliest deadline among the deferred batches it covered; the fsync's duration is the disk's and no scheduling could have hidden it, whereas a late start means the sync waited for the queue, which is the disk falling behind. For the timer's own task the lateness counts from the moment the timer fired, so the operating system's timer granularity is not read as the log running late. A sync covering only strict batches is never late. Ticket `storage-sync-deadlines-are-shared` says "extract what landed"; its description of `settle()` logging "if it finished late" should follow this.
- **`scheduleCheckpoint()` is called at the end of every commit, as before, not from the sync step.** The ticket lists it in the sync step, but also relies on the idle checkpoint firing "5 s after the last append" and bounding how long a record can stay unsynced if a timer were lost. Both hold only when the append arms it. A consequence to know: a `checkpointIdleMs` shorter than the window syncs a waiting record at the idle checkpoint, so a record waits at most the shorter of its window and that setting (README *Durability*). The default 5 s equals the longest window the node computes.
- **A local `settlement()` helper** rather than db-p2p's `deferred`, which that package does not export. Same shape (pre-observed rejection, needed because a strict commit whose inline sync fails rejects the `durable` nobody has been handed yet). `storage-sync-deadlines-are-shared` moves this bookkeeping into db-p2p, where `deferred` is at hand.
- **`docs/debugging.md` untouched.** It lists only `optimystic:db-p2p`, `db-core` and `quereus-plugin` namespaces; the fs package's `optimystic:db-p2p-storage-fs:write-log` channel is documented in the package README instead, where the `window-overrun` line now is.
- **`commit` rejects a non-finite or negative `syncWithinMs` with a `RangeError`**, mirroring `WriteGroup.flush`. `WriteGroup` never passes one; a direct caller that does latches its group on it, which is a programming error surfacing as one.

## Tests added (`packages/db-p2p-storage-fs/test/file-write-log.spec.ts`, `describe('FileWriteLog deferred sync')`)

Each uses the injected `setTimer` (the sync timer is told apart from the idle checkpoint's by its delay) and `interceptHandleSync` as a sync counter and failure injector. Every pre-existing `log.commit` call in the spec now passes `STRICT` (`{ syncWithinMs: 0 }`).

| Test | Verifies |
|---|---|
| relaxed commits share one sync, made when the deadline timer fires, and the tree is written only then | two relaxed commits resolve with no sync, no tree file, pending `durable`s, one timer (the later deadline did not re-arm it); firing it makes one sync, writes both files, resolves both in order and disarms the timer |
| a strict commit after relaxed ones syncs once and settles them all | the strict catch-up rule |
| a commit that finds an earlier deadline already passed syncs before it resolves, whatever its own window | the backpressure rule (a 1 ms window, a real 10 ms wait, then a 5 s window) |
| a relaxed commit survives a process crash | the log bytes read while the record is unsynced, copied to a fresh directory and opened there, replay the value. The registry hands back the live instance for the same directory, so the copy is how "abandon without closing" is staged |
| a checkpoint syncs and applies the waiting records before sealing | tree holds the value, log is header-only, `durable` resolved |
| a deferred sync that fails rejects every waiting durable and latches the log | both `durable`s reject with `StoreFailedError`, nothing reached the tree, later commits refused |

Nothing tests the `window-overrun` line (logging) or the `RangeError` (validation).

## For the reviewer

- **The ordering inside `syncUnsynced`**: the list is left in place during the step and emptied only on success, so a failure's `latch` rejects exactly the covered batches; nothing can push during the step because it runs inside the queue. Check that every caller really is inside a queued task (`commit`, `sync`, `syncInBackground`'s task, `seal`).
- **Rejecting earlier waiting batches when a later append fails.** Their records are intact in the operating system and a reopen replays them, but no sync will be made for them while latched, so their `durable` would otherwise hang a strict flush or `whenDurable()` for ever. Rejecting is the honest answer; confirm you agree it should not instead attempt one last sync.
- **Reads.** The tree gets a batch only after its sync; `WriteGroup` drops an overlay entry only when `durable` resolves, which is after the apply, so no read path falls through to the tree early. The listing merges in `WriteGroupDriver` and `FileKVStore.list` take the overlay snapshot before awaiting the tree, as before.
- **Two stores over one log**: a strict flush of either syncs the other's waiting batches too (the prefix rule of one log); the existing shared-log tests cover the strict case only. Write order 8 (ledger entry after the commit it describes) therefore holds for free when both stores share a base path, as the ticket argued.
- **Timer slop handling in `reportOverrun`** is a judgment call (see deviations). If the reviewer prefers the ticket's finish-time measure, note the consequence above before changing it.
- **Memory**: an unsynced batch's entry objects are held in the log beside the overlay's, but the value byte arrays are shared references, not copies.
