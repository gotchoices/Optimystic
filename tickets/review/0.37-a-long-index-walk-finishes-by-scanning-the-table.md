GitHub #52. Closes the cost `an-index-walk-serves-order-by` accepted.

## What changed

A whole-index walk (`plan=0`) or a range seek (`plan=3`, `plan=7`) counts the index entries it fetches, rejected ones included. On reaching `WALK_ROWS_BEFORE_SCAN` (256) it stops the entry iterator and gets the rest from `executeTableScan` over the same main view. `restOfWalk` keeps a scanned row when its tree key lies past the last key fetched, in walk order, and inside the range, when it passes any row test for a bound the tree could not apply, and when the walk did not already yield it. It sorts the kept rows by tree key in walk direction. They then continue through the same `inEngineOrder` generator, so a run held at the switch flushes in order with them.

An equality seek, a multi-seek and the legacy `idxNum >= 10` arm never switch.

The limit is checked on the entry past the 256th, so a read of exactly 256 entries does no scan, and `matched` tops out at 256 on a `scan=1` line.

`index:seek` gains `scan=0|1`. `matched` and `rejected` stay counts of index entries, so the scan's rows are in neither.

## Use cases to check

- `order by t limit 10` reads 10 entries with `scan=0`, however large the table.
- `order by t` on a large table reports `scan=1`, `matched=256`, and costs about a scan and sort.
- `where t >= ?` holding more than 256 entries does the same. A range holding fewer never scans.
- `where g = ?` over `(g, t)` reads through the index however many rows match.
- A `committed.<Table>` read crossing the threshold stays at its pinned moment.

In `test/committed-read-isolation.spec.ts`: both phases read the one pinned view when a commit lands during the walk, with a live read bringing that commit into the live tree. It is hand-driven through the module, because an open `db.eval` holds the exec lock and a nested read on the same database deadlocks.

`test/trace-helpers.ts` parses `scan=`.

**Mutation check.** I broke the implementation 13 ways, one at a time. 11 were caught, including reading the live tree and starting a second `inEngineOrder`. The 2 survivors cannot be observed on a healthy tree, and I consider them equivalent rather than gaps:

- Keeping the row at exactly `lastKey`: it was already yielded, so `yielded` drops it.
- Ignoring a bound's inclusivity: every bound is a prefix form such as `f(x)`, and a real entry always continues with a framed primary key, so no entry sits exactly on one. The check is therefore defensive only.

## Known gaps

- Verified by inspection only, as the ticket allowed: selective residual, stale entry before the switch, damaged tree, concurrent change during the walk phase, table below the threshold. The `yielded` branch is tested on the pure function, not through a real concurrent writer.
- No test reads a range of exactly 256 entries with no `limit`. `limit 256` and a 255-entry range sit either side of it.
- A short `limit` over a long held run still scans. `order by t desc limit 10` whose top 256 entries all hold text at or above U+D800 reports `scan=1`, because the run yields nothing until it ends. This is correct and bounded by a scan and sort, but it is a page paying for the whole table.
- A range of more than 256 entries in a much larger table now reads the whole table, where the walk would have read a few more entries. This is the tradeoff the ticket accepted, parked as a `NOTE:` at the constant.
- `schema/index-walk.ts` imports `compareTreeKeys` from `optimystic-adapter/collection-factory.ts`, the first runtime import from `schema/` into the adapter. There is no cycle. Moving the comparator to `schema/key-encoding.ts` would restore the direction, and I left it out as unrelated churn. Reviewer's call.

## Noticed, not touched

A table alias costs a statement its index ordering, and this is in the engine rather than this module: `select x.id from m x order by x.t` plans `SORT INDEXSCAN` on a Quereus memory table where the unaliased form plans `INDEXSCAN`, and on an Optimystic table the aliased form plans `SORT SEQSCAN`. So `select … from Message M order by M.Timestamp desc limit 100` gets none of this work. I did not find the cause or establish whether Quereus already tracks it, so I filed nothing.

## Tripwires

Both are `NOTE:`s in the code: pages over 256 rows on large tables (`WALK_ROWS_BEFORE_SCAN`), and the answer depending on a row's position on a damaged tree (at the switch in `verifiedIndexRows`).
