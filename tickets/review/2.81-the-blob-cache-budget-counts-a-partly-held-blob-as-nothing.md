# Review: the blob cache budget counts a partly held blob as nothing

A node keeps a byte budget over the blobs it holds only because it read them (`BlobCacheBudget`, `packages/db-p2p/src/blob/cache-budget.ts`) and takes each blob's contribution from the `size` written on its blob record. A blob the node holds only part of had no size on its record, so it contributed zero — and because the budget's whole decision is "is the total over the limit", a cache made of such blobs was never found to be over the limit and nothing was ever evicted, however much disk the pieces took. Reproduced before the change (budget 0, all pieces present, `size` removed from the record: `cachedBytes 0 evicted 0 piecesLeft 3`).

Both arms of the fix landed, at the one cause: an absent size was read as "zero bytes" when it means "this node cannot say what it is spending here".

## What changed

**Arm 1 — the fetch writes the size as soon as it learns it.** `BlobFetchStore` has a new door, `markPartial(ref, size)` (`local-blob-service.ts`), wired to the existing `correctRecord(ref, false, size)` beside `markWhole`. `FetchSession` calls it once per session from `noteSize`, which is hooked into `plan()` itself behind a `held` guard rather than at the two call sites in `run()` — `plan()` is also where `dropArrived` re-walks the tree when a list piece arrives, which is the *earliest* moment the root's size becomes known, so one guarded site covers strictly more than the enumerated ones and nothing else. The guard is `this.held`, set right after `holdCached` resolves, because `correctRecord` never creates a record and the pre-hold walk may have none.

**Arm 2 — the budget evicts a cache-only blob whose size it never learned.** `CachedBlob.bytes` is now `number | undefined`; `LocalBlobService.cachedBlobs` passes `record.size` through instead of `record.size ?? 0`. `chooseEvictions` evicts every unsized blob not in use first (least recently read among themselves, ties by reference, as before), then runs the unchanged least-recently-read walk over the sized ones until their total is within budget. `cachedBytes` is the sum of the sized blobs only; both its doc comments now say what it leaves out and why the under-count is safe (the omitted blobs are evicted in the same pass).

Two smaller consequences of arm 2 that were not in the ticket's TODO list and are worth a look:

- `cache:evicted` logs `bytes=%s` with `'unsized'` rather than `bytes=%d` with `?? 0`, since 0 and "no size" are now different things and the first is *why* the blob was evicted.
- the `cache:enforced` summary line is now also emitted when `evicted.length > 0`, not only when the total was over budget — otherwise a pass that dropped only unsized blobs (and possibly skipped some as in use) would summarize nothing at all.

**Docs.** `docs/blobs.md` §Lifetime's "at its record's `size`" clause is replaced with the rule and its reasons: a cache-only blob counts at the blob's full size whether or not every piece is here (an over-count, which evicts sooner and so uses less storage); an unsized one is evicted at the next enforcement rather than counted as nothing; the fetch sizes a partly held blob off the root list piece without walking its tree; a 0-byte blob is not unsized. §Holds's list of what a fetch writes through `BlobFetchStore` gained the size write, which used to be described as happening only "once the blob is all here".

## Tripwires parked

- **A partly held blob counts at its full size.** `NOTE:` at the counting site in `chooseEvictions`, immediately above the `cachedBytes` reduce. While nothing asks for byte ranges the over-count is at most the tail of one interrupted download per blob; a caller reading small ranges out of very large blobs would count far more than it holds and evict a cache never over its real limit. The named cheaper route is to count what the fetch stored rather than walk each tree.
- **A ranged fetch of a single-piece blob is still left unsized.** `NOTE:` in `FetchSession.noteSize`. A blob of one piece has no list root for `noteSize` to read a size off, and `finish` writes no size for a ranged request — so arm 2 evicts it at the next enforcement. This is a gap arm 1 does not close, and it is deliberate: harmless today (nothing in this repository asks for a range), bounded when something does (one wasted re-fetch of at most 256 KiB per ranged read, never unbounded storage), and closed by sizing such a blob from the root piece's own length — which `finish` already reads for the unranged case — if ranged reads become ordinary.

## What to test, validate and use

**The reproduction, at the layer that reproduced it.** `evicts a cache-only blob whose size it never learned, even when the cache is within budget`, in `packages/db-p2p/test/blob-cache-budget.spec.ts`. Three blobs held for reads alone over a real `LocalBlobService` on a `MemoryPieceStore`: one 300 KiB blob, one 0-byte blob whose record says `size: 0`, and one 300 KiB blob whose record's `size` has been taken off (new `unsizedBlob` helper — `encodeBlobRecord` is `JSON.stringify`, so writing `size: undefined` drops the key). The budget is ten times what the node can account for, so nothing is over it. Only the unsized blob is evicted, only its pieces go, and the sized and empty blobs still read back whole. Without the fix `evicted` is `[]`; a fix that read an absent size as zero would evict the empty blob too, which is the point of including it.

**Arm 1 is observed for free** in the existing `keeps what an interrupted fetch stored and asks only for the rest` (`packages/db-p2p/test/blob-fetcher.spec.ts`), which now asserts `b.blobs.local.cachedBlobs()` reports `[[ref, content.byteLength]]` after the first, interrupted fetch — `[ref, bytes]` pairs only, since the entry's `lastReadAt` is a real clock reading. Before the change this was `[[ref, 0]]`.

**No other new test.** The `markPartial` door, the `fetchDoor` wiring and the `CachedBlob.bytes` type change are glue the typechecker already enforces.

**Worth a reviewer's attention:**

- `plan()` now performs a record write (once per session, through `noteSize`). It is a walk that writes, which is a small altitude cost; the alternative is two call sites in `run()` that miss `dropArrived`'s re-plan, i.e. a later write. `markPartial` logs rather than throws, so awaiting it inside `plan()` cannot fail a fetch.
- Every whole fetch now does one extra unflushed record write (`markPartial`, then `markWhole` at `finish`). Deliberate per the ticket — the early write is what covers the interrupt and crash windows — but it is a real added write on the common path.
- `sizeNoted` is set *before* the await, so a failed write is not retried. Noted in a comment; the reasoning is that `markPartial` swallows its own failures anyway, and arm 2 covers the record that never got a size.
- The `choose` closure in `chooseEvictions` mutates `evict` and `skippedInUse` from two loops. The function's documented purity (reads nothing, writes nothing) is intact, but it is denser than the single loop it replaced.
