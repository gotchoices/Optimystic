# Review: refuse a concurrent insert whose UNIQUE column value a rival already committed

## What the bug was

A secondary UNIQUE constraint (`col … unique`, table-level `unique (a, b)`, `create unique index`) was enforced only by the vtab's pre-stage probe — a range scan of the constraint's index tree evaluated against the writer's own snapshot. Two concurrent writers both probe clear and both commit, leaving two rows a UNIQUE column says cannot coexist. The primary-key guard from the prerequisite ticket could not catch this: an index tree keys `frame(indexValue) ‖ frame(primaryKey)`, so two rows sharing a value under different PKs occupy *different* tree keys inside one framed-value prefix. Uniqueness there is a property of the prefix, not of one exact key.

## What landed

**The `absentRange` guard arm (db-core).** `TreeEntryGuard`'s `absentRange` variant — defined but refused-until-wired by the prerequisite — is now enforced by the tree `replace` handler (`buildInit` in `packages/db-core/src/collections/tree/tree.ts`). On every run (initial staging and every conflict replay) it range-scans the guarded entry's claimed range over the same `Atomic` store the upsert writes to; any entry whose key is not the staging entry's own key (self-exclusion via `compare`) throws the new `TreeRangeTakenError` (`struct.ts`). That error is a **subclass of `TreeKeyTakenError`**, so every consumer that already treats a key refusal as a non-retryable uniqueness failure — the sync/commit retry loops that let it escape, the bridge that maps it — handles it with no new arm. `collectionId` is the discriminator naming which constraint fired.

**Guarded staging (plugin).** `IndexManager.insert/updateIndexEntries` take an optional `uniqueIndexes` set naming which maintained index trees' entry for this row must carry `uniquePrefixGuard(indexKey)` (the same `indexValueRange` prefix `findByIndexIn` seeks — one shared definition, so a seek and the guard can never drift). The vtab computes that set in `OptimysticVirtualTable.guardedUniqueIndexes`: every UNIQUE constraint that BINDS the row (non-partial, all columns present/non-null) and resolves to a BLOCKING action (ABORT/FAIL/ROLLBACK). REPLACE stays unguarded (its eviction already ran); IGNORE stays unguarded (last-writer-wins at replay, the documented index anomaly owned by backlog `6-debt-index-sweep-misses-update-delete-and-orphans`). Non-unique index staging is untouched — no guard, no extra descent, no behaviour change.

**Error mapping (bridge).** The vtab registers a per-index `keyTakenMessage` (naming the constraint's *columns*, not the PK) for each UNIQUE-enforcing index tree, in `registerCollections` and after `addIndex` mirrors a `create unique index`. A `TreeRangeTakenError` out of an index collection's replay maps through the existing `mapCommitRefusal` to `UNIQUE constraint failed: <table>.<col>`, indistinguishable from a sequential duplicate.

**Legacy commit pre-flight (bridge) — a behaviour change worth a close look.** A UNIQUE-constrained table is backed by ≥2 collections (main table + index tree), and the refusal lives in the index tree, which flushes *after* the main table in the legacy sweep. Without more, a secondary-unique refusal would land mid-sweep: the loser's base row durably committed, the index entry refused, a torn `PartialCommitError`. `commitDirtyTreesLegacy` now **pre-flights `tree.update()` over every staged tree before flushing any**, so a refusal whose rival already committed surfaces before any tree reaches storage — clean rollback, nothing torn. This narrows but does not close the legacy tear window (a rival landing between the pre-flight and a tree's own flush still tears loudly); the full close is backlog `feat-optimystic-legacy-commit-two-phase`. Session (coordinator) mode was already atomic across trees.

## Use cases / how to exercise it

- **New suite `concurrent-secondary-unique-refusal.spec.ts`** (two `Database` handles, one `FileRawStorage` dir, `T(id pk, v unique)`): deterministic staged-then-rival replay refusal naming `T.v`; racing same-value/different-PK (exactly one fulfils, loser refused, value stays enforced-present); disjoint values never refuse; delete-then-reinsert of a unique value allowed; SESSION-mode two-table transaction fails atomically.
- **`tree-guard.spec.ts`** (db-core, raw trees): `absentRange` refuses a foreign key in the prefix, self-excludes its own key, ignores a different value, allows re-use of a deleted value, and enforces at initial staging.
- Verify a non-unique index still admits duplicates: any two-node non-unique case in `two-node-shared-index-key.spec.ts` (`both rows survive …`).

## Two existing tests changed behaviour — confirm these are intended

The reviewer should treat these as the highest-value things to re-derive, because each **inverts a previously-asserted outcome**:

1. **`two-node-shared-index-key.spec.ts` — `a UNIQUE index over-admits the same value across two nodes`** asserted the OPPOSITE of this fix (both rows survive; it documented the lost-uniqueness bug as an accepted downstream trade at `sereus/schemas/control.qsql` FormationUsage.UsageStampId). Rewritten to assert the cross-node duplicate is now REFUSED once the rival commit is visible to the loser, and only one row survives. **Downstream impact:** any consumer relying on cross-node over-admission of a UNIQUE value now gets a refusal wherever the rival's commit is visible at write time. This is the ticket's explicit intent (the control schema's single-use StampId/MemberPrivateKey anti-replay columns need enforcement), but it is a real semantic change — worth confirming against the downstream `FormationUsage` nonce use case.

2. **`concurrent-insert-refusal.spec.ts` — the legacy two-table `MID-SWEEP` PK test** asserted a `PartialCommitError` (`not atomic`) tear. The new pre-flight makes the *deterministic* rival-first case roll back cleanly (bare UNIQUE message, U never persists), so the test now asserts the clean exit. The genuine mid-sweep `PartialCommitError` (a flush failing after an earlier tree committed) is still covered by the injected-commit-failure test in `legacy-commit-atomicity.spec.ts`.

## Known gaps / tripwires (parked, not filed)

- **Legacy racing tear (residual, not closed).** In legacy mode a rival committing between the pre-flight and a tree's own flush still leaves a torn base row (duplicate unique value present in base, absent from index) surfaced loudly as `PartialCommitError` — never a silent double-commit. Recorded as a `NOTE:` at the pre-flight site in `txn-bridge.ts` and in `docs/internals.md`; owned by backlog `feat-optimystic-legacy-commit-two-phase`. The racing test asserts only the invariant that always holds (exactly one fulfils; the value stays enforced-present on both handles).
- **True-partition over-admission.** Two nodes that never observe each other before both commit can still each admit the value and converge with two entries — the same limit the PK guard has. Noted in the rewritten two-node test; owned by backlog `feat-phantom-read-protection`.
- **Cost.** Each guarded unique insert/update adds one short range descent at staging (only on UNIQUE-enforcing index trees). Not measured — no plausible profile where a per-row DML descent registers; the prerequisite review made the same call for the PK `find()`.

## Not verified deeply — where a reviewer should push

- **Probe vs. guard timing.** In the two-node harness the vtab probe admitted the loser (its refreshed view had not yet fetched the rival's block) while the staging-time guard, scanning the tracker moments later, caught it — the guard is the authoritative backstop the probe is not. Worth confirming the probe/guard split is understood and that no path stages a guarded unique entry the probe would have had to block first in a way that changes the SQL result shape.
- **UPDATE guard self-exclusion on a PK-move that preserves the unique value.** `updateIndexEntries` stages delete-old-then-insert-new as one action so the guard scans a range the outgoing entry has already left; covered indirectly by `update-pk-move-uniqueness.spec.ts` staying green, but no test drives a *concurrent* PK-move-preserving-value race at the SQL level (the db-core self-exclusion tests cover the mechanism).
- **Displacing-move (REPLACE) index staging** (`deleteIndexEntries` of the displaced row before `updateIndexEntries` of the mover): unguarded by construction, but only exercised by the existing single-node REPLACE specs.
