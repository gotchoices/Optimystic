## The invariant, restated

`packages/db-p2p/docs/storage.md` §2 was titled "Every out-of-band writer of a block's
`meta.latest` serializes on the per-block commit latch". It is now "Every write to a block holds
that block's single write latch", stated over the **whole metadata blob** (`{ latest, ranges }` is
read and written whole, so any read-modify-write rewrites `latest` whether it meant to or not)
plus revision records, transforms, pending records and stored proofs. It names the one key
(`Block.write:<blockId>`, `blockWriteLatchKey`), names `block-latch.ts` as the single acquirer,
gives the two enforcement mechanisms (a required `BlockWriteLatch` parameter on every writing
method, so an unlatched write does not type-check; plus the grep below), and records
`materializeBlock`'s re-cache as the one named exclusion.

The old "Known deliberate exception" paragraph — about hosts that supply no latch runner to
`InvalidationContext.withBlockCommitLatch` / `CollectionEnv.withBlockCommitLatch` — is **deleted**.
Those optional capabilities no longer exist; grepping the tree for `withBlockCommitLatch` or
`commitLatchKey` now returns nothing outside `tickets/`.

## The check the docs make, and a wrinkle worth knowing

The ticket asked the doc to record `grep -rn "Latches.acquire" packages/db-p2p/src/storage` →
exactly one hit. **That check does not hold as written**: any comment stating the check contains
the pattern and matches itself, so the naive form returns two hits (the call plus its own doc
comment). The check shipped instead is:

```bash
grep -rnE "Latches\.acquire\(" packages/db-p2p/src
```

The escaped-regex spelling in the prose does not contain the literal call text, so the prose is not
a hit. Verified: **exactly one line**, `block-latch.ts:71`. The same corrected check is now in
`block-latch.ts`'s own header comment, which previously asserted the naive form and was therefore
self-falsifying. **Reviewer: please re-run it.**

## `NOTE:`s at the two code sites

- `block-storage.ts`, `materializeBlock`'s `saveMaterializedBlock` after the retention check — the
  one write outside the latch. The NOTE says why it is safe (key is `(blockId, actionId)`, value is
  a deterministic replay of already-retained transforms, so a racing writer of the same key writes
  identical bytes; it touches neither the metadata blob nor any revision record), why taking the
  latch there is not an option (a lock acquisition on every cold historical read, and it would
  self-deadlock the commit path, which reaches `materializeBlock` via `getBlock` while holding the
  latch — `Latches` is non-reentrant), and that dropping the re-cache is out of scope until someone
  measures the cold historical-read cost without it. It replaces a forward-reference to "the
  follow-up ticket" left by the prior ticket.
- `storage-repo.ts`, `readCommitBase` — the commit path deliberately does not restore in line.
  States the reason as the calling context (`commit` holds every batch block's latch across this
  call), names the refusal (`MissingBaseRevisionError`), names the healing route (cohort reconcile
  → `saveReplicatedBlock` → retry, see `ClusterMember`), points at the test below, and says where a
  future fetch would have to go instead (before the latches, not underneath them).

## The test

`packages/db-p2p/test/storage-repo.spec.ts`, new describe **"commit reads its base locally (no peer
fetch inside the latched critical section)"** — 4 tests, all passing.

A `restoreCallback` that *can* answer for rev 3 is wired into the `BlockStorage` factory and counts
every call. Then:

- **control: the READ path DOES fetch this same base from the peer** — same metadata, same wiring,
  through `repo.get()`. Asserts 1 restore call at rev 3 and that the peer's content comes back.
  This exists so the three "0 restore calls" assertions below are not vacuous — without it they
  would pass equally against a callback that could never have answered.
- **refuses a commit whose base is not locally covered, without calling the restore callback** —
  metadata `{ latest: { rev: 3, actionId: 'ghost' }, ranges: [] }`. Asserts
  `MISSING_BASE_REVISION_REASON`, `restoreCalls` deep-equals `[]`, the pending record is gone
  (`refuseMissingBase`), and `latest` is untouched at rev 3.
- **refuses the same way … when history under a claimed range is truncated** — `ranges: [[3]]` with
  no revision records. Different throw inside `getBlock`, same refusal path, same zero fetches,
  same dropped pending.
- **a multi-block batch refuses without a fetch, with every block in the batch latched** — the
  shape that made the old in-line restore expensive (N latches held across a network round trip).

# Known gaps — treat these as the starting point, not the finish line

- **The seeded state is synthetic.** `{ latest: { rev: 3 }, ranges: [] }` is written straight to
  raw storage because no code path produces it today — every writer of `latest` merges coverage for
  it in the same `saveMetadata`, as the pre-existing NOTE in `readCommitBase` says. It stands in for
  the states that *do* reach that code (a block wedged by an older build, truncated history), which
  are the ones the old code answered by fetching mid-commit. A test docblock says so. If a reviewer
  thinks the substitution is unsound, the alternative is a `BlockStorage` double that throws from
  `getBlock`, which trades realism of the storage state for realism of the failure.
- **No test asserts the latch is actually *held* during the refusal.** The tests prove no fetch
  happens; they do not prove a concurrent writer on the same block is blocked at that moment. A
  stronger test would race a second writer against a slow refusal. That is a genuine coverage gap,
  not a claim I made and didn't check.
- **Scope crept slightly past the ticket's `files:` list.** `ensureRevision` and the old key name
  `StorageRepo.commit:<blockId>` survived in `docs/internals.md` (4 spots), `docs/repository.md`
  (1), and `packages/db-p2p-storage-ns/src/ns-opener.ts` (1 comment) — names for things that no
  longer exist. All six are one-phrase renames. Worth confirming the reviewer agrees the renames
  are correct rather than merely plausible, especially `internals.md:786`, which reasons about a
  deadlock using the key by name.
- **The stale-reference sweep was grep-driven, not exhaustive.** Patterns swept: `ensureRevision`,
  `commitLatchKey`, `withBlockCommitLatch`, `StorageRepo.commit:`, `per-block commit latch`,
  `commit latch`, `three different per-block`. Prose describing the old three-lock scheme without
  using any of those words would have been missed.
- **README code block was also corrected beyond the ticket's ask.** It listed
  `savePendingAction`/`promotePendingAction`; the real names are `savePendingTransaction` /
  `promotePendingTransaction`. Fixed while rewriting the block.
