# Cohort-topic: a root-placed topic's root can move — review handoff

First of three tickets delivering "tiers below the root do not rotate; only the root moves" (the maintainer's decision of 2026-10-02). In substrate terms: one topic id for a collection's whole life, and a root key that changes. Tiers `d ≥ 1` are addressed by `coord_d(P, topicId)`, so they stay put; the root, `H(rootKey)`, is a different coordinate after a move. The two dependents (`reactivity-per-root-state-is-keyed-by-the-tail`, `reactivity-topic-is-the-collection-anchor`) consume the API added here: `moveRoot`, `CohortHint.treeTier`, tier-1 engines that follow the root key, and `findHolder` choosing the newer record. No wire field changed.

## What changed

**Walk outcome and handle carry the tree tier** (`packages/db-core/src/cohort-topic/walk.ts`, `service.ts`). `AcceptedWalkOutcome.treeTier` is the `treeTier` of the register frame the cohort accepted. `CohortHint.treeTier` (so `RegistrationHandle` and `lookup`'s result) is required and set from it in `hintFromReply`, which now takes the whole accepted outcome.

**`CohortTopicService.moveRoot(handle, rootKey)`** (`service.ts`). Sends nothing. The service's live-renewal map now holds `{ renewal, root }` (`LiveRenewal`), where `root` is a mutable `RootKeySlot` the renewal transport's `relookup` reads when it runs. `moveRoot` updates that slot and `handle.rootKey`. Guards: `assertRootKey` first; then **throws** on a handle registered without a root key (a judgment call not spelled out in the ticket — moving the root of a default-addressed topic would silently turn it root-placed); then a stale handle (not the live renewal for its `(topicId, participant)`, the same identity guard `renew`/`withdraw` use, now factored as `liveRenewal`) is a no-op. A registration at the root (`treeTier === 0`) is left at the old root — the caller re-registers; doc comment says so.

**`startRenewal` NOTE replaced** with the decided behavior: a second `register` displaces the first and no tombstone is sent for the displaced record, by design (a tombstone resolves through `findHolder`, which picks the newer record on a machine holding both, so it would evict the live one).

**A tier-`d ≥ 1` engine follows the topic's root** (`reconcilePlacement` in `packages/db-p2p/src/cohort-topic/host.ts`). Rule mismatch (`rootPlaced` differs) is still refused. Same key or no key on the frame: no-op. Engine with no key: adopts. Different key at a non-root-placed engine: logged (`cohort-topic` namespace, served coord) and adopted — newest frame wins — with the accepted-tradeoff `NOTE:` the ticket specified. Different key at a root-placed engine: still `CoordPlacementMismatchError`. `EnginePlacement`, `CoordPlacementMismatchError`, `CoordEngine.rootKey`/`adoptRootKey`, `CoordRegistry.forCoord` doc comments rewritten; the `dispatchRegister` NOTE now names the re-pointing effect and points at the new NOTE. Checked by reading `createCoordEngine`: `parentRootPlaced`, the promotion lifecycle's `parentCoord`, and the cold-start `registerWithParent` closure all read the `let rootKey` at use; none captured it at creation.

**`findHolder` returns the newer registration** (`host.ts`). `CoordEngine.heldRecord(topicId, participantId)` exposes the record; `holds` is kept beside it (≈26 spec call sites use it; it is now documented as a derivation). `isNewerRegistration` orders by `attachedAt`, ties by `lastPing`; its doc carries the rationale and a `NOTE:` on cross-member clock skew. A tripwire `NOTE:` at `findHolder` records that every renew now scans all resident engines (bounded by `coordEnginesMax`) instead of stopping at the first holder.

**Docs.** `docs/cohort-topic.md`: § Root placement at a routing key gains a table note (tier-1 `rootKey` follows the newest frame) and a "The root can move" paragraph; the db-core implementation note mentions `moveRoot` and `treeTier`; the db-p2p implementation note now says the *rule* is decided once and the *key* of a tier-`d ≥ 1` engine follows the newest frame. § TTL and renewal gains the displaced-record / newer-record bullet (with the skew residual). § Application policies item 6 gains the second shape (keep the topic, move the root). `docs/internals.md` § Service composition: one clause on `findHolder`. `yarn lint:docs` passes.

**Test fakes.** Five `CohortTopicService` fakes in db-p2p tests got a throwing `moveRoot` stub so they still implement the interface (`reactivity-topic-is-the-collection-anchor` will replace the collection-watch one with a real recording stub).

## Tests added

- `packages/db-core/test/cohort-topic/walk.spec.ts` — two assertions on existing cases: the sparse-regime walk (steps inward 3→0) reports `treeTier` 0; the `Promoted` redirect walk (1→0→1) reports `treeTier` 1, not the root it stepped through.
- `packages/db-core/test/cohort-topic/service.spec.ts` — "a renewal re-walk after moveRoot names the new root key": register with an old key, `moveRoot` to a new one, three failed pings with no backups → every re-walk frame carries the new key.
- `packages/db-p2p/test/cohort-topic/service.spec.ts`, describe "a topic whose root moved":
  - "a renew resolves to the newer of two records…, whichever engine was created first" — two engines on one host each hold a record for the same participant (attached 1 s apart); loops over both creation orders; asserts `findHolder` and that `resolveRenew` touches the newer record's `lastPing` and leaves the older one alone.
  - "two records attached at the same instant: the later lastPing wins" — the newer `lastPing` is on the second-created engine, so first-match would fail.
  - "a tier-1 engine follows a frame naming a different root key; a root-placed engine still refuses one" — `registry.forCoord` at a tier-1 coord with old then new key returns the same engine holding the new key; a root-placed engine created through the real activity-handler dispatch (host given a one-member `rootGroup`) throws `CoordPlacementMismatchError` for a different key and keeps its own.

Each new case fails against the previous code (first-match `findHolder`, throwing `reconcilePlacement`, no `moveRoot`/`treeTier`).

## For the reviewer to weigh

- **`moveRoot` throwing on a non-root-placed handle** is an addition beyond the ticket text. Alternative: allow it (the tier-1 engine would adopt a key it never had, and the next re-walk would go root-placed). I judged a loud error better.
- **`holds` kept alongside `heldRecord`** to avoid churning ≈26 spec sites; collapse if preferred.
- **The tier-1 reconcile test drives `registry.forCoord` directly**, not a register through dispatch (dispatch would also need a `rootGroup` on the host); the root-placed half does go through dispatch to get a real root-placed engine.
- **Interleaved old/new keys** at one tier-1 engine during a move flip its key and log once per flip. Recorded in the reconcile NOTE; harmless until child cohorts are linked to the root (backlog `feat-reactivity-notifications-reach-child-cohorts`).
- **Matchmaking** registers without a root key, so `placementOf` returns the default placement and the adoption branch never runs; verified by inspection, and the matchmaking suites are green.
- **Known, not fixed here:** a renewal failover's re-walk discards its outcome, so `treeTier` (and primary/backups) on the handle can go stale after a relookup — already appended as an arm to backlog `bug-a-participant-told-its-registration-is-unknown-never-registers-again`.
