# NativeScript storage syncs by the window — review handoff

Second of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). The maintainer's decision (2026-10-15): phones relax by the cohort-size window like any other node. This backend now commits each write group atomically as one SQLite transaction, keeps write order across a power cut through SQLite's write-ahead log, syncs by the group's deadline through the shared `SyncDeadlines` helper, and syncs at once when the window is 0.

## What changed

**`SqliteDb.transaction(fn, { synced })`** (`packages/db-p2p-storage-ns/src/db.ts`). A new `SqliteTransactionOptions` with one flag. The protocol both implementations run inside their mutex slot moved into one shared function, `runTransaction`: with `synced`, `PRAGMA synchronous = FULL`; then `BEGIN IMMEDIATE`, the body, `COMMIT`, or `ROLLBACK` on a throw; then `PRAGMA synchronous = NORMAL` whichever way the transaction ended. A restore that fails after a failed body is logged so the body's error surfaces; after a committed body it throws. `NSPluginDbWrapper` (`src/ns-opener.ts`) and the Node test driver (`test/node-sqlite-driver.ts`) both call it, so neither can drift from the other. `SCHEMA_SQL` gained the `durability_mark` table (`CREATE TABLE IF NOT EXISTS`, additive to an existing database).

**`syncSqliteDb(db)` and `bumpDurabilityMark(tx)`** (`src/sqlite-sync.ts`, new). The helper is one synced transaction that bumps the single marker row, so there is always a frame to commit. The bump is exported separately so the backend's own sync step can write it inside its synced transaction without duplicating the SQL.

**`SqliteBatchBackend` replaces `SqliteStoreDriver`** (`src/sqlite-storage.ts`). A `BatchBackend`: reads are the former driver's statements, generated from one table-layout map (the table is named after the store, with its key columns and value column), so the on-disk format is unchanged. `commit` validates `syncWithinMs`, refuses after a latch, takes the batch's deadline with `deadlineFor` as it is called, and decides with `mustSyncNow(deadline)` before taking the connection mutex whether the transaction is synced, because the pragma is set as the transaction starts. A deferred commit applies every entry in one `NORMAL` transaction and calls `defer` inside the body; a synced commit runs the sync step with the entries as its write. The sync step (`syncHeld`) is one synced transaction whose body runs the write if any, then `take`s the cover under the mutex, and bumps the marker only when there is a cover to settle and nothing of its own was written; the cover settles after the commit resolves, and any failure latches the backend, rejects the covered `durable` promises and throws `StoreFailedError` carrying the first cause. `sync()`, the deadline timer and `close()` all run that step; `close()` never closes the shared handle. `durability` is `'power-loss'`; the rule-3 `NOTE:` is gone and the prefix argument is stated once in the class doc.

**`SqliteRawStorage`** is `KvRawStorage` over `WriteGroupDriver` over `SqliteBatchBackend`, takes `SqliteRawStorageOptions` (the write group's options, whose `setTimer` also arms the backend's deadline timer), and redeclares `close` as always present. `src/index.ts` exports `SqliteBatchBackend`, the two option types, `syncSqliteDb`, `SqliteTransaction` and `SqliteTransactionOptions` in place of `SqliteStoreDriver`.

**`SqliteKVStore.flush()`** (`src/sqlite-kv-store.ts`) runs `syncSqliteDb` when a write has resolved since the last flush and resolves at once otherwise. Beyond the ticket's text, a failed sync latches the store, after which `set`, `delete` and `flush` throw `StoreFailedError` while reads keep working: rule 5 of the flush contract on `RawStoreDriver.flush` asks for that, and the store had no latch before.

**`loadOrCreateNSPeerKey`** (`src/identity.ts`) syncs after writing a newly generated key; an existing key is read as before.

**Docs.** `packages/db-p2p/docs/storage.md`: the Invariant 6 driver-table row, the sentences naming which backends defer, the *Rule 3 past the crashes a store names* paragraph (SQLite now stated as the reason this backend needs no log of its own), the write-orders sentence, the per-backend survival row and its trailing paragraph, and the kernel section. `docs/correctness.md`: the §1.2 storage-durability sentence and Theorem 6's backend caveat, both of which named this ticket as the one to update them. The package README: what a crash loses, the close order (`await storage.close()` before `db.close()`), the synced transaction, the helper, and the `durability_mark` row. The backlog ticket `feat-nativescript-storage-moves-to-sqlite-4` had one line naming the removed class, now corrected.

Use cases the change serves, for a reviewer reading the code against them:

- A phone node applying a write its cohort agreed to: `StorageRepo.endGroup` flushes with the cohort's window, the group commits as one `NORMAL` transaction, the flush resolves at once, and one `FULL` commit by the deadline syncs it together with every group since the last sync.
- A solo write on a phone (window 0): the group's own transaction commits under `FULL`, and the flush resolves only once it is on disk.
- A strict flush arriving while relaxed groups are held: its own commit is the one sync, every held `durable` settles, and the deadline timer is disarmed.
- A power cut inside the window: the write-ahead log keeps a prefix of committed transactions, so the most recent groups are lost whole and nothing older is.
- First start: the generated peer key is synced before it is handed out, so a power cut right after cannot give the node a different identity next time.
- The node's ledger (`SqliteKVStore`) flushed after the block store's strict flush: one synced commit when it wrote, none otherwise.

## Tests added

In `test/sqlite-storage.spec.ts`, over `node:sqlite` with the test driver's new `onExec` hook counting `PRAGMA synchronous = FULL` and `COMMIT` statements, and an injected `setTimer` fired by hand:

- *relaxed groups commit unsynced and share one sync when the deadline is due*: two `withinMs: 5000` flushes make two transactions and no `FULL`, a second storage over the same handle reads both groups back from the tables, `whenDurable()` stays pending, exactly one timer is armed; firing it gives exactly one `FULL` commit, `whenDurable()` resolves, and no timer is left armed.
- *a strict flush after relaxed ones syncs once and settles all of them*: after the same two relaxed flushes, a strict flush with a write makes exactly one `FULL` in total and no transaction beyond the three groups, the earlier `whenDurable()` resolves, and the timer is disarmed.
- The raw-storage conformance suite, persistent, now runs over the composed storage; its harness closes the storage before the handle, since the storage's timers must not fire on a closed connection.

In `test/sqlite-kv-store.spec.ts`: *flush() syncs once when something was written since the last flush, and not otherwise*, pinning the dirty-flag branch (no sync with nothing written, one per flush after a set, none when nothing changed, one after a delete).

`test/sqlite-transaction-serialization.spec.ts` was retargeted, not added: it drove the mutex regression through `promotePendingTransaction`, which no longer opens a transaction (a promote is two overlay entries of one group), so unchanged it would have tested only the overlay. It now drives `SqliteDb.transaction` directly with the same two assertions: two concurrent transactions on disjoint rows both commit, and a plain write concurrent with a rolling-back transaction is neither lost nor rolled back with it.

No test for the identity helper's sync: it is one call after the insert, and a test would only pin wiring.

## Known gaps and judgment calls for the reviewer

- **No power-loss test exists.** That a committed transaction survives a power cut, and that what survives is a prefix, rests on SQLite's documented write-ahead-log behaviour (checksummed frames, recovery stopping at the first bad frame, the WAL synced before every checkpoint under `NORMAL`, and `FULL` syncing the WAL at commit). Stated in the class doc and the README; nothing here can observe it.
- **The sync step takes the cover inside the synced transaction**, not before it as the ticket's phrasing ("take the cover; if it is empty, resolve; otherwise `syncSqliteDb`") suggests. Taking it outside the mutex opens a window where a held batch's own `COMMIT` fails after the take: the latch's `failAll` no longer holds that batch, and the sync's cover would then resolve its `durable` over a rolled-back transaction. Inside the body, under the mutex, the cover is exactly the batches whose transactions committed earlier. The cost is that `sync()`, the timer and `close()` always open a transaction; with nothing held the body writes nothing and the commit changes nothing, so no frame is written and no sync happens (four statements, no disk wait).
- **`close()` therefore runs one empty synced transaction after `WriteGroupDriver.close` has already flushed strictly.** `SyncDeadlines` exposes no "is anything held" query, and duplicating that state in the backend seemed worse. If a reviewer would rather add a count accessor to `SyncDeadlines` in `packages/db-p2p`, the step could skip the transaction on an empty hold.
- **`mustSyncNow` is decided before the mutex slot.** A deadline that passes while the commit waits in line defers that batch and leaves its backpressure to the timer, which is due anyway; the ticket accepts this, and the class doc says so.
- **Unserialized reads during an open transaction.** The `NOTE:` on `NSPluginStatement.get` kept its mechanism but its justification was stale (it named same-block promote as the only transaction writer). It now says why it still holds: every row a batch transaction writes is served by the write group's overlay until the batch is durable, so no read of those rows reaches the connection mid-transaction; the key-value store and identity helper write other tables by autocommit statements. A reader of a batch's rows that bypasses the overlay would need reads serialized too.
- **SQL casing.** AGENTS.md asks for lowercase SQL reserved words; this package was uppercase throughout before this ticket and the ticket's own SQL is uppercase, so the new statements match the package rather than mix cases within one file. A package-wide conversion is mechanical if wanted.
- **`PRAGMA synchronous` on the NativeScript plugin** goes through the same `raw.execute` path as the existing pragmas (assignment-form pragmas return no rows, which the Android plugin's `execSQL` requires). No device run was possible here.
- **`runTransaction` and `TransactionConnection`** are exported from `db.ts` as the shared seam for the two wrappers, but not re-exported from the package index.
- `feat-nativescript-storage-moves-to-sqlite-4` (backlog) already names this design and the obligation to keep one transaction per group and the synced option; nothing further was done there beyond the one-line class-name correction. `debt-ns-sqlite-concurrency-stress-test` (backlog) would now also exercise synced transactions; nothing to do here.
