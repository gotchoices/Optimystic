# Cached blob copies stay within a budget

Every fetch takes the `cached` hold on the blob it is fetching, and until now nothing released it, so a machine that read many files grew its storage without bound. `docs/blobs.md` §Lifetime says what should happen: cached blobs are evicted under a budget, least recently read first, never while a read of them is in progress. That is what landed.

A byte budget covers the blobs held **only** for reads. It is enforced after a read or fetch that pulled anything, and once when the node has built its blob service, by removing the `cached` hold from the least recently read such blobs until the total is within the budget and then running the piece sweep once. A blob with a read or fetch in flight is never evicted, and the sweep leaves the pieces of a blob in use alone — both through the use count `feat-a-blob-being-read-is-not-swept` added, which until now had no caller.

## What changed

**`LocalBlobService` (`packages/db-p2p/src/blob/local-blob-service.ts`)**

- Two new exported types beside `BlobOwedRecords`, and for the same stated reason — a door rather than a second `BlobRecordStore` over the same key-value store, so every write still goes through the one per-ref queue, the sweep gate and `PieceSweeper.noteRecordChange`: `CachedBlob` (`ref`, `bytes`, `lastReadAt`) and `BlobCacheRecords` (`cachedBlobs`, `releaseCached`, plus the existing `inUse` and `sweep`). The class now declares `implements … BlobCacheRecords`.
- `cachedBlobs()` enumerates `BlobRecordStore.listRefs()` and reads each record through the existing `readableRecord`, so an undecodable record is logged `record:unreadable` and skipped exactly as in `responsibleRefs` — such a blob is never counted and never evicted. `bytes` is the record's `size` (0 when it has none), `lastReadAt` the record's (0 when never read here).
- `releaseCached(ref)` goes through `changeRecord` with `recordAfterCacheEviction`, a change function that is itself the condition: it sees the record at this reference's turn in the per-ref queue, so a blob that gained a pin, an `owed` or a `responsible` hold since the enumeration keeps **every** hold and the call reports `false`. Dropping the only hold leaves an empty `holds`, which `BlobRecordStore.update` deletes and `changeRecord` then schedules a sweep for (harmless beside the budget's own).
- Two module-level helpers: `cacheOnly(record)` (held for reads and nothing else) and `recordAfterCacheEviction`.

**`packages/db-p2p/src/blob/cache-budget.ts` (new, ~185 lines)**

- `DEFAULT_BLOB_CACHE_BUDGET_BYTES` = 256 MiB.
- `chooseEvictions(blobs, budgetBytes, inUse)` — pure. Sorts by `lastReadAt` ascending then reference ascending (so the choice is deterministic on equal read times) and walks that order while `cachedBytes - evictedBytes > budgetBytes`: an `inUse` blob is skipped and counted in `skippedInUse`, any other is evicted. A blob with no recorded size contributes 0 and is evicted like any other once the walk reaches it; there is deliberately no guard that stops at a zero-byte blob.
- `BlobCacheBudget` with `enforce()`, `request()` and `stop()`. `enforce` enumerates, chooses, re-checks `inUse` immediately before each write, calls `releaseCached` in the chosen order, reports only the refs whose removal returned `true`, and awaits one `sweep()` at the end when anything was evicted. Single-flight with **one queued follow-on** rather than joining the run in flight (a run in flight enumerated the records before the read that triggered this call, so joining would under-enforce); several calls during one run share the one follow-on. `request()` is `void enforce()` with a logged catch. `stop()` sets a flag that makes a start resolve with the empty enforcement and awaits whatever is in flight.
- Exported from `packages/db-p2p/src/index.ts` beside `local-blob-service.js`.

**`NodeBlobService` (`packages/db-p2p/src/blob/node-blob-service.ts`)**

- `NodeBlobServiceDeps.requestCacheEnforcement?: () => void`, optional so every existing construction (and every existing test of the class) keeps working unchanged, caching without bound as it does today. The callback rather than the budget itself, because the budget is built over the `LocalBlobService` this service is built over.
- Called in two places, because either alone leaves a gap: at the end of `readFetching`'s `finally` when the read started a session (the inner `readThrough`'s `finally` has already released the read's use by then), and in `startSession`'s `settled` after the session's own use is released. Single-flight collapses the pair into one run plus one follow-on. A read that fetched nothing starts no session and triggers nothing.

**`libp2p-node-base.ts`**

- `NodeOptions.blobs` gains `cacheBudgetBytes?: number`, documented on the existing `blobs` doc comment.
- `resolveBlobCacheBudgetBytes` (beside `resolvePieceStore`) throws `RangeError('blobs.cacheBudgetBytes must be an integer number of bytes at or above 0, got …')` for anything that is not a safe integer at or above 0. Called beside `const blobHold`, before `createLibp2p` and `node.start()`, so a misconfigured host gets the error rather than a started node to roll back.
- The budget is built immediately before `NodeBlobService`, over the same `LocalBlobService`, with `createLogger('blob:reclaim', node.peerId.toString())`. Its stop wrapper is installed **after** the blob service's (so it runs **before** it, and no enforcement writes a record or sweeps once the blob service has stopped), then `budget.request()` runs once so a budget lowered across a restart is applied to what the last run cached. `requestCacheEnforcement: () => blobCacheBudget.request()` goes into `NodeBlobService`, and the budget is exposed as `(node as any).blobCacheBudget` beside `blobCopyDrain` and `owedBlobLedger`.

**Docs** — `docs/blobs.md`: the status line notes the budget exists and that the reference pass does not; the §Holds `cached` row cites `BlobCacheBudget` and names the option and its default; the §Lifetime bullet is rewritten to state what counts, the order, when it is enforced (no timer), that a blob being read is never evicted, and that the sweep protects blobs in use. `docs/debugging.md`: a `blob:reclaim` row with the three `cache:` lines (`logger.spec.ts` fails without it).

## Tests

`packages/db-p2p/test/blob-cache-budget.spec.ts` (new), over a real `LocalBlobService` on a `MemoryPieceStore` and a `MemoryKVStore`, with `setTimer: () => () => undefined` so the only sweeps are the budget's. A cache-only blob is made the way the service's own paths make one: `put` (pinned `default`), then a `cached` hold and a `lastReadAt` through a `BlobRecordStore` over the same key-value store, then `unpin(ref, DEFAULT_BLOB_OWNER)`.

| Test | What it pins |
|---|---|
| `evicts the least recently read cache-only blobs until the cache is within budget` | Four cache-only 300 KiB blobs with `lastReadAt` 1–4, plus a fifth that holds both `cached` and a pin at `lastReadAt` 0; budget 700 KiB. `cachedBytes` is 4 × 307200 (the pinned blob is not counted), `evicted` is exactly the blobs read at 1 and 2 in that order, their records are gone and every one of their pieces is absent from the piece store after the sweep, and the other two plus the pinned one — the least recently read of all — still read back whole with `from: 'here'`. Three pieces of the specification that cannot be checked apart: the ordering, the cache-only rule, and the hand-off to the sweep. |
| `does not evict a blob being read, and evicts it once the read ends` | Two cache-only blobs, budget 0 (so ordering is not what is under test). With one chunk of a `read` of the first taken, `enforce()` evicts only the other, reports `skippedInUse: 1`, and leaves the first blob's record and root piece. Draining the rest of the read, then `enforce()` again, evicts it and empties the piece store. Pins the skip, the count, and that the skip is not permanent. |

No other test. Everything the plan declared "by inspection" stayed that way, and the wiring (the node option, the trigger call sites, the stop-wrapper order, the export) is glue the types already hold together — see the gaps below for what that leaves unguarded.

## Known gaps and what to look at

- **The node wiring is pinned by nothing but reading it.** The `RangeError` on a bad `cacheBudgetBytes`, the one-shot enforcement at start, the stop-wrapper ordering (budget before blob service), and the two `requestCacheEnforcement` call sites have no test. The two trigger sites in particular could be deleted and every test here would still pass — the budget would then only ever run at start. Worth a reviewer's eyes on whether one integration-level test ("a read that fetched brings the cache back within budget on its own") earns its keep; I judged it did not, since it would need a two-node fixture to make a fetch happen at all.
- **`chooseEvictions` is exported and pure but has no direct unit test** — it is exercised only through `enforce`. Its ties-by-reference branch is therefore untested: both tests use distinct `lastReadAt` values.
- **The re-check before the write is not atomic with it.** `enforce` asks `inUse(ref)` immediately before `releaseCached(ref)`, but `releaseCached` awaits a per-ref queue, so a read beginning in that window loses its blob's hold. What covers it is the sweep taking in-use refs as roots (`feat-a-blob-being-read-is-not-swept`), so that blob's present pieces are kept and the read finishes; the read's own `touchLastRead` cannot resurrect the deleted record, because `recordAfterRead` returns `undefined` unchanged. Both by inspection.
- **`releaseCached`'s `true` rests on `recordAfterCacheEviction` never leaving a record behind.** It reports a `before` with no `after`, which is an eviction only because the change function either deletes the record (`cached` was its only hold) or returns it untouched. If a future hold kind made a partial removal possible, that return value would start lying.
- **Single-flight-with-follow-on is by inspection.** No test drives two overlapping `enforce()` calls, and the `queued = undefined` / `start()` ordering inside `startAfter` is the subtle part: it relies on the follow-on's continuation running after the run-in-flight's `finally` has cleared `running`.
- **Nothing retries on a timer.** A budget the evictions cannot reach because every remaining cache-only blob is in use stays over budget until the next read that fetches, or the next restart. Deliberate, and stated in the docs — but it does mean a node whose reads have stopped can sit over budget indefinitely.
- **`cache:enforce-failed` is the only report of a failed enforcement.** A store fault during an enforcement triggered by a read is logged and dropped; the read itself is unaffected.

## Review findings

- Tripwire parked as a `NOTE:` at `BlobCacheBudget.enforce` in `packages/db-p2p/src/blob/cache-budget.ts`: each enforcement reads every blob record (`LocalBlobService.cachedBlobs`), which is the same scan `responsibleRefs` and `listPins` already carry a tripwire for, but this one runs after every read that fetches rather than once at start. If record counts reach the tens of thousands and enforcement shows up in a profile, keep a running total of cache-only bytes in the record store.
