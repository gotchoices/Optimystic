# Unreferenced blobs are reclaimed

The reference pass of docs/blobs.md §Lifetime is built. Periodically (five minutes after a node starts, then every six hours after the previous pass ended) and on demand, each node reads every registered blob reference tree for the blobs it holds under `responsible` or owes, and releases a hold only for a blob that two **counting** passes at least a grace period apart (7 days by default) found listed nowhere. Releasing the last hold deletes the record and leaves the pieces to the piece sweep. Cache eviction (`BlobCacheBudget`) is untouched.

This is the first and only code in the repository that deletes replicated data on a schedule, so the review should read it as such: a wrong release deletes a file a committed row still names, on each holder independently, with nothing left to repair from. Everything below errs toward keeping.

## What was built

**`ConfirmationRecordingTransactor` + `ReclaimReadOnlyError`** — `packages/db-p2p/src/blob/confirmation-recording-transactor.ts`. A read-only `ITransactor` built fresh per pass. `get` forwards with `awaitConsult: true` and records every block whose answer did not carry `cohortConfirmed`, a block the result OMITS included (the marker is positive, so absent means "not known to be confirmed"). `getStatus` delegates; `pend`, `cancel` and `commit` throw rather than delegate. `ITransactor`'s optional members are omitted deliberately.

**`whyPassDoesNotCount` + `ReclaimEvidence` + `ReclaimNotCountedReason`** — the pure predicate holding every disqualifying condition from §Lifetime, answering the reasons a pass does NOT count (empty when it counts), in the type's declaration order: `partition`, `registry-threw`, `registry-uncertain`, `registry-absent`, `tree-threw`, `tree-uncertain`, `unconfirmed-not-alone`, `stopped`. Separate from the pass so the rule is readable and testable with no network.

**`BlobReclaimPass`** — `packages/db-p2p/src/blob/reclaim-pass.ts`, with `DEFAULT_RECLAIM_INTERVAL_MS` (6 h), `DEFAULT_RECLAIM_FIRST_PASS_DELAY_MS` (5 min), `BlobReclaimOnDemand`, `ReclaimPassReport`. One pass, in the ticket's order: snapshot `responsibleMarks()` and `owed.list()` (return `skipped: 'nothing-held'` when both are empty) → `detectPartition()` → registry → each registered tree in ascending order, asked only about the responsible references no earlier tree listed plus the owed references naming that scope → `aloneFor` over exactly the unconfirmed blocks, only when there were any → `detectPartition()` again → predicate → apply → one `sweep()` if anything was released → log. `start()`/`runNow()` (joins the pass in flight)/`stop()`; each pass re-arms the timer `intervalMs` after it **ends**, and only when `start()` armed the schedule, so a `runNow` on an unstarted pass arms no timer.

**Node wiring** — `NodeOptions.blobs.reclaimGraceMs`, resolved by `resolveReclaimGraceMs` beside the `resolveBlobCacheBudgetBytes` call before `createLibp2p`, so a bad value throws before the node starts. One pass built after the owed-ledger and drain block, **on both roles**, with its stop wrapper installed immediately (so it runs before the blob service's) and then `start()`. `OptimysticNodeAttachmentsBase.blobReclaim` assigned in the `shared` literal, plus `(node as any).blobReclaimPass`.

**Docs** — docs/blobs.md status line (reclaiming built in both halves; what is left is §SQL's two further steps), §Lifetime bullets 2–4 rewritten, §Holds `responsible`/`owed` "Released when" rows, §Threats "Make a live blob expire" row. docs/internals.md: one paragraph after the POSITIVE-marker paragraph in §Consensus Execution, one row in §Client nodes' table. docs/debugging.md: the `reclaim:` lines in the `blob:reclaim` row, and a `reclaim:pass` entry under §Reading the fields.

## Use cases for testing, validation and usage

**Driving it by hand.** `node.blobReclaim.runNow()` runs a pass (or joins the one running) and resolves with the `ReclaimPassReport`; `(node as any).blobReclaimPass` is the whole `BlobReclaimPass` for diagnostics. Nothing else triggers a pass but the timer. A pass on a node holding nothing returns `{ skipped: 'nothing-held' }` and reads no committed state at all.

**Reading a pass in the field.** `DEBUG='optimystic:db-p2p:blob:reclaim*'`. `reclaim:pass` is one line per pass; `counted=false` with a `notCounted` list means nothing was marked and nothing released, and the lines above it (`reclaim:registry-unusable`, `reclaim:tree-uncertain`, `reclaim:tree-threw`, `reclaim:not-alone`) say which read caused it. `reclaim:released` is one line per hold actually released. The `reclaim:pass` entry in docs/debugging.md §Reading the fields spells out how to tell "did not count" from "had nothing to decide", and says that a node whose passes never count is usually not alone and not hearing from its cohort.

**Configuring it.** `blobs: { reclaimGraceMs: … }`. Below `MIN_RECLAIM_GRACE_MS` (1 h) or non-finite throws a `RangeError` naming the option before the node starts, deliberately rather than clamping. There is no option for the interval or the first-pass delay (the pass takes both, but the node does not expose them) — tests inject `now` instead and never call `start()`.

**The cases worth probing by hand or in review:** a node whose cohort it cannot see (holds everything for ever, `unconfirmed-not-alone`); a one-machine deployment (counts, and releases after two passes); a partition (reads nothing); an absent scope registry on a node holding blobs (does not count); a blob pinned as well as responsible (loses `responsible`, keeps record, pin and pieces); and a reference that moves between tables while a copy is still owed (see the tripwire below).

## Tests added

`packages/db-p2p/test/blob-reclaim-pass.spec.ts`, 14 cases. Committed state is a db-core `TestTransactor`, whose answers never carry `cohortConfirmed`; everything else is the real class (a real `LocalBlobService` over a `MemoryPieceStore`, a real `OwedBlobLedger`, a real `KeyNetworkCohortReachability` over a key-network double, a real `PartitionDetector` driven in with `recordFailure`). The clock is injected; `start()` is never called, so no timer is armed.

- `whyPassDoesNotCount` over a table of evidence objects — each reason on its own, `registry-absent` only when `holdsAny`, an existing empty registry counting with unconfirmed blocks this node is alone for, `aloneForUnconfirmed: undefined` disqualifying nothing, and six reasons at once coming back in declaration order.
- One machine releases after two passes a grace period apart — and the piece assertions: B's own piece and list piece gone, the piece A and B share kept, A's own pieces kept, A's hold kept.
- Two passes closer together than the grace period leave the mark unchanged.
- Unreferenced → referenced → unreferenced: the period runs from the third pass, not the first.
- One failing tree among several (a `BlockPossiblyStaleError` on that tree's header): the pass does not count for any blob, reports exactly `['tree-uncertain']`, and the clean tree's listed blob still has its stale mark cleared — the branch that keeps a later counting pass from reclaiming with no grace period at all.
- A node that cannot see its cohort: two passes a grace period apart mark nothing and report `unconfirmed-not-alone`.
- Confirmed answers count without being alone: a cohort of two with every answer marked confirmed releases, with `unconfirmedBlocks: 0`, so `aloneFor` — which would answer false — is never consulted.
- Partition: `['partition']`, `treesRead: 0`, nothing marked.
- Absent registry while holding: `['registry-absent']`, nothing marked.
- An owed blob whose row was deleted: entry marked, then entry and `owed` hold both gone, and the drain's `list()` no longer names it.
- A pinned blob keeps its record, its pin and its pieces when `responsible` goes.
- Restart: a second service, ledger and pass over the same key-value and piece stores releases on the pass a grace period later.
- A `responsible` hold released and re-taken is marked afresh instead of released on one pass.
- A node holding nothing reads nothing (`skipped: 'nothing-held'`, empty `notCounted`).

No test was added for `stop()` mid-pass, the `runNow` join, clock movement, or the shared-piece rule as a case of its own — the ticket assigns those to inspection, and the shared-piece assertion rides inside the one-machine case as it specifies.

## Known gaps and things to push on

- **`skipped: 'stopped'` has no live path today.** The report type and the ticket both specify it, and the guard is the first thing `runPass` does, but I could not construct a reachable sequence: `runNow` rejects once stopped, `stop()` cancels the timer, and the timer callback reaches the stopped check in the same synchronous tick as the firing. It is defensive code documenting the contract. Keep or cut — I did not invent reachability for it.
- **`holdsAny` is always `true` inside a pass that reads**, because the `'nothing-held'` early return precedes it. It is a real field of `ReclaimEvidence` (the predicate's own callers and the spec's table exercise `false`), but at the one production call site it is a constant with a comment saying why. A reviewer may prefer it computed, or the field dropped from the evidence and the rule stated as "absent registry never counts".
- **Tripwire, parked as a `NOTE:` at the owed arm of `apply`:** an owed entry is kept only by its OWN scope listing the blob, per §Lifetime, while a receiver accepts a pull on any listing scope. The two part company if a reference moves between tables by the hand of a *different* writer — this node's entry still names the old scope and drops after the grace period although a committed row still names the blob. Harmless while the cohort got its copies during that period, which is exactly what the drain spends it doing. The `NOTE:` says what to change if a blob is ever lost this way, and that §Lifetime would have to change with it; it is a documented-design question, not a bug I could fix inside this ticket.
- **Two cost tripwires as `NOTE:`s above the class**, both from the ticket: `awaitConsult` makes each expired-window block a blocking consult and the trees are read one after another; `aloneFor` makes one `findCluster` per distinct unconfirmed block, which on a node that *is* alone is every block of every tree it read.
- **The owed-release leak `NOTE:`** at the release site: entry deleted first, hold released second, so a crash between them leaks an `owed` hold with no entry — storage kept, nothing lost. Nothing reclaims such a hold (see the drain fix above).
- **`cleared` in the report counts responsible-mark and owed-mark clears in one number**, and double-counts a reference that is both. The ticket's report shape has one `cleared`; worth confirming that is what was meant.
- **Not wired, deliberately:** cache enforcement after a release. The `NOTE:` above `BlobCacheBudget` names the condition ("if a node is ever seen sitting over budget with its reads idle") and it has not tripped.
