The marker half of backlog `1.1-dispute-validity-reject-marker`, moved forward for the offline-sync classification (`offline-sync-typed-validity-rejection` is its first consumer). Nothing acts on the marker yet; this ticket only produces, signs, verifies and documents it.

## What was built

- **`ValidityRejection`** (`packages/db-core/src/transaction/transaction.ts`, exported from the db-core root): `{ computedHash?: string }`. Added as optional `validity` on both `ValidationResult` (what `ITransactionValidator.validate` returns) and `PendValidationResult` (what a `PendValidationHook` / `checkPendValidation` returns). Both stay flat objects rather than `valid: true | false` unions, because dozens of existing tests read `result.reason` without narrowing; the doc says the field is set only on a failure.
- **`TransactionValidator`** (`packages/db-core/src/transaction/validator.ts`) marks exactly five refusals through the module-level `validityRefusal`: `Tampered transaction stamp`, `Missing client signature`, `Invalid client signature`, `Re-execution failed` (marker `{}`), and `Operations hash mismatch` (marker `{ computedHash }`). Unmarked: `Transaction expired`, `Unknown engine`, `Schema mismatch`, `Stale read`, `Unsupported operations-hash format version`. The class doc lists the mapping.
- **`checkPendValidation`** (`packages/db-p2p/src/pend-validation.ts`) is unchanged in code: it already returned the checker's verdict verbatim. Its doc now says its own two refusals (`PEND_NOT_VALIDATABLE`, `VALIDATOR_FAULT`) are unmarked and a checker's `validity` passes through.
- **`Signature`** (`packages/db-core/src/cluster/structs.ts`): the reject variant is split into two arms — plain/expiry (`expiredAt?: number; validity?: never`) and validity (`validity: ValidityRejection; expiredAt?: never`) — so a vote carrying both does not typecheck. `clusterVoteSigningPayload` encodes a validity vote as `<hash>:reject-invalid:<json [computedHash ?? null, rejectReason ?? null]>`; a vote with neither field encodes byte-identically to before. Doc comment's unambiguity argument extended for the third tag.
- **`ClusterMember`** (`packages/db-p2p/src/cluster/cluster-repo.ts`): `PromiseVerdict`'s `invalid` arm carries optional `validity`; `invalidVerdict(reason, validity?)`; `voteFor` signs it via `signedValidity`, which copies only `computedHash` (an embedder's hook could return extra fields that would otherwise ride on the vote unsigned). Only the pend-validation branch of `validatePendOperations` passes a marker; every other `invalidVerdict`/`verdictOf` caller stays unmarked. Comments on `PromiseVerdict` and `verdictOf` that called every `invalid` verdict "a validity judgement" were corrected.
- **Equivocation**: `detectEquivocation` now compares `equivocationKey` (the vote type, or `reject-invalid:<json computedHash>` for a marked reject) instead of the bare type, so a re-delivered reject whose marker was added, removed or changed is penalized and the first-seen vote kept. The log fields `existingType`/`incomingType` and the penalty context now carry those keys. A plain reject versus an expiry reject is still not flagged (out of scope; unchanged).
- Counting is unchanged everywhere (`rejectionCount`, thresholds, `ValidatorRejectionError`, `disputeEvidence`).
- Docs: `docs/internals.md` has a new Key Invariants bullet ("A reject that judges the transaction itself wrong says so in its signature") after the "never skips the check silently" bullet, which now notes its two refusals are unmarked. `docs/correctness.md` Theorem 11 describes the marker arm of equivocation.

## Tests added

- `packages/db-core/test/cluster-vote-payload.spec.ts` — "binds a validity marker to its vote signature: added, removed or altered, it no longer verifies": real Ed25519 key; a marked and an unmarked reject each verify as signed; marker removed, marker (or empty marker) added, `computedHash` altered or dropped all fail. The existing byte-identity test now also covers "no validity → same bytes as before".
- `packages/db-core/test/validator-refusal-class.spec.ts` (new) — one table-driven test pinning the class of every `TransactionValidator` refusal (all ten reasons) plus "an approval is never marked".
- `packages/db-p2p/test/cluster-repo.spec.ts` (`validation` describe) — "signs the validity marker a validator returns onto its reject, and a peer refuses the vote with the marker stripped": exercises the threading validator → `checkPendValidation` → verdict → `voteFor`, and `ClusterMember.verifySignature` refusing the stripped vote (`Invalid promise signature from <id>`).
- `packages/db-p2p/test/dispute.spec.ts` — helper only: it built a `Signature` with `type: 'approve' | 'reject'` in one literal, which the split union no longer accepts; it now builds each arm explicitly. No behavior change.

## Known gaps / things for the reviewer to weigh

- **Mixed versions (accepted, per ticket).** A member on an older build verifying a marked vote builds the old preimage, fails the signature and reports `InvalidSignature` against an honest member — the same cost the expiry encoding accepted. Rare because no composition root configures a checker today (backlog `feat-no-deployment-validates-transactions-at-pend`). Recorded in `docs/internals.md`.
- **StorageRepo tier drops the marker.** `StorageRepo.pend` turns a failed `checkPendValidation` into `{ success: false, reason }` without the class; deliberately left for `offline-sync-typed-validity-rejection`.
- **A hostile `validity: null` on the wire** makes `clusterVoteSigningPayload` throw (`null.computedHash`). Every verifier call site (`ClusterMember.verifySignature`, `commit-proof.ts`, `dispute-service.ts`) wraps it in try/catch and treats a throw as an invalid signature without penalty, so it is refused, not crashed. Worth a glance if the reviewer prefers the payload function to be total itself.
- **Pre-existing observation, not changed:** `voteTagAndExtra`'s default arm returns an unknown `type` verbatim, so a relayer can re-label an honest reject as `type: 'reject-invalid:[…]'` (or `'reject:…'`, `'reject-expired:…'`) and the signature still verifies; the vote then counts as neither approve nor reject. That is equivalent to the relayer dropping the vote (which it can always do), so the marker still cannot be stripped while keeping a counted reject. Not filed.
- `PendValidationResult` / `ValidationResult` were kept flat rather than made discriminated unions (see above); a reviewer may want the union, at the cost of narrowing in the existing tests.
