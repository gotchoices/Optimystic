## What landed

**`test/two-node-index-mutation-sweep.spec.ts`**, a second generator beside the insert-only `two-node-index-interleaving-sweep.spec.ts`. It runs on the in-process mock mesh (`mesh-node-harness.ts`), with table `FormationUsage (Id integer primary key, Token text)` and `create index formation_usage_by_token on FormationUsage(Token)`.

Every case starts from the same state. The declarer creates the table and index, and the other node re-declares or hydrates. A inserts `(100, 'tok-a')`, then B inserts `(200, 'tok-b')`. Both nodes' scans are asserted to hold both rows before anything mutates. The target is always row 100.

- **Pure-data coverage guard** (no mesh):
  - Case counts are pinned at 64, 32 and 4.
  - No case name appears twice.
  - Every value of every dimension is present.
  - Each of the 8 racing op pairs appears 4 times; the insert-only pair appears 0 times.
- **Sequential, 64 cases**: `declare` (A | B) × `open` (redeclare | hydrate) × `mutator` (owner | sibling) × `mutation` (to-sibling-value | to-new-value | pk-move | delete) × `locate` (by-pk | by-index). After the mutation:
  - Both scans equal the expected rows. This runs first, with its own message, so a mutation that touched no row does not show up as an index discrepancy.
  - A pk-move additionally asserts `where Id = 100` is empty and `where Token = 'tok-a'` returns 101 on both nodes.
  - `expectIndexAgreesWithScan` runs on both nodes.
  - The mutation statement is wrapped in the new `countIndexScans` helper: by-index must make at least one secondary-index seek, by-pk must make none. That keeps the `locate` dimension from silently collapsing into one.
- **Racing, 32 cases**: `declare` × A's op × B's op (update | delete | insert-shared, excluding insert-shared against itself) × `commit` (a-first | b-first). The flow is `A: begin; op`, `B: begin; op`, then the two commits as sequential awaits. Each commit's outcome is captured (`settleInOrder`), so the second commit runs whatever happened to the first.
- **INSERT OR IGNORE race, 4 cases**: `declare` × `loser`. The loser runs `begin; insert or ignore … (300, 'tok-ignored')`, the winner commits `insert … (300, 'tok-winner')`, then the loser commits.

**The replay model** is a small, pure model of today's replay semantics (`staged.update`, `staged.delete`, `staged.insert`, `staged.insertOrIgnore`, then `predictReplay`), headed by a `NOTE:`.
- Every racing case asserts that both commits fulfil and both scans equal the predicted rows.
- A clean prediction asserts `expectIndexAgreesWithScan` on both nodes.
- A prediction with discrepancies asserts that `readIndexIntegrity`'s report equals it exactly on both nodes: index name, row count, entry count, and each orphan's reason, value, primary key and current row. Missing entries are compared the same way, but no case predicts any.
- The model's `insert` throws if its `absent` guard would ever trip. That would be a refusal the model does not predict, and no case reaches it.
- Titles of pinned cases end in `-> pins orphan …`.

**`countIndexScans(body)`** is a new export in `test/query-helpers.ts` that reuses the existing routing probe.

**Comment updates**:
- The insert sweep's `WRITE_ORDERS` doc comment is restated: `staged-both` always commits A first; B-first is covered for mutations here and uncovered for inserts, as a recorded gap with no ticket.
- Its `runPreReads` now calls the read-only-sibling shape a recorded, unfiled gap.
- Its header points at the mutation sweep.

## Results

- **Sequential**: all 64 clean. No single-writer orphan producer was found.
- **Racing: 8 cases pin a discrepancy**, the same 4 under each declarer:
  - `a=update b=update commit=a-first`: orphan `tok-x|100` (stale-value)
  - `a=update b=update commit=b-first`: orphan `tok-y|100` (stale-value)
  - `a=update b=delete commit=a-first`: orphan `tok-x|100` (no-row)
  - `a=delete b=update commit=b-first`: orphan `tok-y|100` (no-row)
- **Resurrection**: 4 more cases have a clean index but a resurrected row 100:
  - `a=update b=delete commit=b-first`: row back holding tok-x.
  - `a=delete b=update commit=a-first`: row back holding tok-y.
- **The rest are clean with no resurrection**: both commits of `delete/delete` fulfil, and every pair involving `insert-shared` is clean.
- **IGNORE race**: all 4 pin orphan `tok-ignored|300` (stale-value, row holds tok-winner).
- **Model disagreements: none.** Every prediction the ticket marked unverified matched observation, including the double delete (both fulfil) and the mirrored update-vs-delete orders.

## Known gaps and things for the reviewer to push on

- **Non-vacuity was argued, not demonstrated with a negative control.**
  - Pinned racing cases can only pass if `verifyIndexes` actually reports those exact orphans. They match the fix-stage probe's printed tree contents, so the discrepancy branch is shown to bite.
  - The clean branch rests on `expectIndexAgreesWithScan`, whose structural arm `query-helpers.spec.ts` already pins against a broken index.
  - I did not run a deliberately broken sequential case, for example with `withIndexStagingPatched` from `index-staging-patch.ts` on the mutator.
- **Pinned cases skip the lookup half of the oracle.** `expectIndexAgreesWithScan` fails on structure first, so for the 12 pinned cases nothing checks that index-routed seeks still match the scan while the orphan exists. The integrity docs claim an orphan never changes a result set, and nothing here tests that claim.
- **`hydrate` here happens before any row exists.** The ticket's setup order puts the other node's arrival before the inserts. The insert sweep hydrates after a committed row, but no mutation case hydrates onto a table that already has rows.
- **The by-pk zero-index-scan assertion depends on the planner's choice.** If the planner ever routes a primary-key equality through a secondary index, 32 sequential cases go red. That is intended, since it keeps `locate` meaningful, but the failure would look like an index problem.
- **The racing group is narrow by design**: `open=redeclare` and by-pk locate only, per the ticket.
- **Undisposed Databases.** This adds 208 undisposed Databases to the run (the accepted tradeoff on `startMockMesh`). No slowdown was seen, and a `NOTE:` on `meshPerCase` says to close nodes in an `afterEach` first if that changes.
- **Downstream.** `refuse-concurrent-row-change-loser` deletes the model and expects, after its fix:
  - the second committer of any pair touching row 100 is refused, including the double delete, because an absent row counts as changed;
  - pairs involving `insert-shared` both fulfil;
  - the IGNORE loser is refused.

  The reviewer should confirm the header and the NOTE give that implementer everything needed.

## Usage

From `packages/quereus-plugin-optimystic`:
- Run the file: `node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/two-node-index-mutation-sweep.spec.ts" --reporter spec --exit`
- Run one shape: add `--grep "a=update b=update"`.
- A red sequential case is a single-writer orphan producer. File a `fix/` ticket citing the case name.
- A pinned racing case failing with "holds none" means the concurrent defect was fixed. Delete the model per its `NOTE:`.
- Any other racing failure is a model disagreement. Record it on `refuse-concurrent-row-change-loser`, or on a new `fix/` ticket, before touching the model.
