# A coordinator no longer asks the reader what the reader already holds

## What changed

**Reader side.** A read sent to another machine now carries `BlockGets.askerHolds`: per requested block, the sender's committed latest `(rev, actionId)`, or `null` when it holds no committed revision. A block whose local metadata could not be read is left out; the field is left off when none could be read. It is filled by `stateHoldingsOnReads(remote, local)`, a decorator over the remote repo, from `StorageRepo.heldRevisions`, which reads block metadata `latest` only (no materialization, so no restore from a peer; no context, so no promotion). Both call sites use it: the plugin's `CollectionFactory` `getRepo` (remote `RepoClient`s only; a host-injected node with no `storageRepo` sends nothing) and the mesh harness. Reads a node coordinates itself are never wrapped.

**Identity.** `RepoService` passes the connection's authenticated `remotePeer` to the repo as `MessageOptions.asker` on the `get` arm. Nothing in the request names a peer. The mesh harness has no `RepoService`, so it binds the reader's id the same way (`arrivingFrom`), with the layers in production order: reader decorator, then `wrapRepo` (transport faults), then the identity binding, then the coordinator.

**Coordinator side.** `askerStatementFor(blockGets, blockId, asker, localLatest)` validates the untrusted JSON and decides `standsIn`: true for "nothing", or for a revision below the coordinator's own `state.latest`, or equal to it under the same action. In `queryClusterForLatest`, the peer equal to the asker (in the consulted cohort, not self) is answered from the statement instead of `clusterLatestCallback` when `standsIn`. A stated revision is a claim (copied field by field, so no proof rides in); "nothing" is the resolved-`undefined` answer. The asker therefore counts as answered for every downstream rule, including `recordAheadClaim`'s weakening rule. Anything else (ahead, same revision under a different action, any revision when the coordinator holds none) is consulted as before. `cluster-fetch:asker-stated { blockId, asker, held, standsIn }` is logged whenever a cohort member's statement was weighed, used or not.

## Use cases to validate

- Two-member cohort, reader B routes to coordinator A, A is current: B's read costs one exchange; A logs `asker-stated … standsIn: true`; B logs no inbound sync request for that block.
- New-collection probe (header absent everywhere) through a remote coordinator with the reader stating `null`: one exchange, unflagged authoritative absent.
- Reader ahead of the coordinator: the reader is consulted, and the coordinator acquires as before.
- A request carrying `askerHolds` with no connection identity (in-process call, or `connection` absent): ignored, consult as before.
- An old coordinator ignores the field; an old reader sends none.

## Tests added

- `coordinator-repo-read-repair.spec.ts` › "a read from a cohort member that says what it holds" › "is answered without asking that member when it holds nothing ahead, and asked otherwise": statements below and equal (same action) are not consulted and the answer stays unflagged; same revision under another action, a statement ahead, and a statement with no bound asker are each consulted.
- same describe › "keeps the new-collection probe authoritative when the reader holds nothing either": a `null` statement on a missing block is not consulted and yields an unflagged absent.

Both fail with the one substitution line in `queryClusterForLatest` disabled (checked), and pass with it.

## Known gaps and judgement calls for the reviewer

- **A diagnostic change in undeclared two-member cohorts.** A statement carries no commit proof. Where the reader, if consulted, would have answered with a retained proof at the coordinator's own revision, the coordinator used to log `cluster-fetch:certified-selected` + `local-current`; it now logs `cluster-fetch:no-quorum` every pass and, once per block, `cluster-fetch:repair-deadlock` with `reason: 'cohort-too-small'`. The served answer, its flags and the window arming are identical (`cohort-too-small` arms the window just as `local-current` does). A declared two-member cohort corroborates on the one uncertified voter, so it logs `local-current` with `voters: 1` and no `certified`. Attaching the coordinator's own proof to the stand-in was considered and not done: the ticket's rule is that a statement carries no proof, and the gain would be log lines only.
- **Metadata `latest` versus what a consult reports.** `heldRevisions` states a committed tombstone and an unmaterializable `latest` as revisions; the consult (which projects `StorageRepo.get`) reports both as "holds nothing". The stand-in is used only at or below the coordinator's revision, where a claim and an absence both leave nothing ahead, so reads are unaffected; `no-quorum`'s `holders`/`absent` split and the `sole-holder` classification could differ in those rare shapes. Documented at `StorageRepo.heldRevisions`.
- **Mesh harness divergence, pre-existing.** The harness's consult reads the target's storage with the read's `context`, which can promote a pending on the target; production's consult sends no context. With the stand-in, a reader in the mesh no longer receives that promotion from being consulted. The suite stayed green; the divergence itself is older than this ticket.
- **A throwing holdings reader fails the read.** `stateHoldingsOnReads` does not catch. `StorageRepo.heldRevisions` cannot throw (each block is caught and logged under `storage-repo` as `held-revisions:unreadable`), so this only matters for another `IHeldRevisionReader`. No new log namespace was added, so the decorator has nowhere to log a degrade.
- **Tripwire recorded:** `NOTE:` at `stateHoldingsOnReads` — every remote read pays one local metadata read per block, even when the coordinator will ignore the statement.
- The ticket's inferred cause of B routing to A (the 30 s self-coordination grace period) is stated in the new transactions.md paragraph as the usual reason a fresh node reads remotely; it was not re-traced here.
