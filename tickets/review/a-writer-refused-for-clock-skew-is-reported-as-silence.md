GitHub issue #24. Before this change a member whose clock was more than the transaction timeout (30 s by default) ahead of the writer's threw `Transaction expired` out of `validateRecord`; the coordinator turned the throw into "no vote", charged the member `PenaltyReason.ConsensusTimeout`, and ended in `Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)`, the text a downstream repository retries as a silent cohort.

# What changed

**Member.** Expiry is now a promise verdict. When this member has not yet voted on a record and `message.expiration <= Date.now()`, it signs a `reject` vote carrying `expiredAt` (its own clock reading) and a prose reason `transaction-expired: expiration <iso>, member clock <iso>`. The check runs first in `evaluatePromise`, and `getTransactionPhase` sends an expired unvoted record to `OurPromiseNeeded` *before* `findConflict` — otherwise an expired record could still win a race on the tie-breaks and clear a live rival's reservation (the old throw in `validateRecord` prevented that by running before the phase machine). The timer-driven `handleExpiration` signs the identical vote. A member that has already voted on the record still throws `Transaction expired` (voting again would be equivocation); this is checked in `processUpdate` after the merge, with a `NOTE:`.

**Signing payload.** `clusterVoteSigningPayload` now takes the unsigned vote object (`ClusterVote`), so signer and verifier encode the same fields. Every vote without `expiredAt` produces exactly the old bytes (`<hash>:<type>[:<extra>]`). An expiry vote encodes `<hash>:reject-expired:` + `JSON.stringify([expiredAt, rejectReason ?? null])`: the tag differs from every other vote's after `reject` (hashes are base64url, so the first `:` ends them), and the JSON array cannot be read as a different pair.

**Coordinator.** The vote is counted as a rejection like any other, so the two-member repro now lands in `rejected-by-validators` (which broadcasts the abandonment) instead of `supermajority-failed`, and nothing is penalized. When every reject in `promises` carries a finite numeric `expiredAt`, it throws `TransactionExpiredError` (subclass of `ValidatorRejectionError`, so `CoordinatorRepo`'s classifiers treat it unchanged) with `expiration`, `memberClocks`, `coordinatorClock`, `apparentSkewMs`. The message never contains "super-majority"; it states the lower bound `expiration − coordinatorClock` ("at least N s ahead") when positive, the apparent skew, and that the fix is whichever side's clock is wrong. A mix of expiry and other rejects stays a plain `ValidatorRejectionError`. The `cluster-tx:rejected-by-validators` log gains `expiredAt` and `expiration` on an expiry refusal.

- `packages/db-core/test/cluster-vote-payload.spec.ts` — field-less votes of every type encode byte-identically to the old preimage; an expiry vote never collides with a reject whose reason contains `:` (`"x:5"`, `"5:x"`), nor with a string smuggled into `expiredAt`.
- `packages/db-p2p/test/cluster-expired-vote.spec.ts` — the coordinator-level repro (two members; local member approves, remote answers an expiry vote): `TransactionExpiredError` and `instanceof ValidatorRejectionError`, message without "super-majority", `expiration`, `memberClocks`, `apparentSkewMs` ≈ 31 s, and no `ConsensusTimeout` on the reputation spy.
- `packages/db-p2p/test/cluster-repo.spec.ts` — the three old throw-asserting expiry cases are gone (the one under "update - expiration" was passing by accident: its message hash was invalid and the hash-mismatch error text happened to contain "expired"). # Known gaps for the reviewer

- **Minority expiry voter in a cohort of four or more.** It is sent the commit round, has voted, and so throws there — the coordinator charges it a commit-round `ConsensusTimeout` (and the commit-broadcast retry may charge it again). Recorded as the tripwire `NOTE:` in `processUpdate`; the ticket said not to widen the already-voted case.
- **Abandonment broadcast after expiry rejects.** A member that voted expiry and still holds the record (only where one reject is not terminal, i.e. four-plus members) receives the abandonment broadcast already voted and expired, so it throws rather than computing `Rejected` and clearing. The record is dropped by `findConflict`'s 2 s staleness sweep on the next conflicting arrival and by the 60 s expiry sweep. Not covered by a test.
- **`<=` versus `<`.** The member now treats `expiration == clock` as expired (the ticket's rule; the old check was `<`). No test pins the boundary — that needs a clock injection, and `expiryOf` reads the real `Date.now()` like the old check did (see the `NOTE:` on `ClusterMemberComponents.now`).
- **Mixed versions.** An older-build member verifying a record that carries a newer member's expiry vote computes the old preimage, fails the signature, throws `Invalid promise signature` and reports `InvalidSignature` against the newer member. Acceptable under the stated "cluster consensus code is a single deployable unit" rule at `validateRecord`, but it is a real hazard during a rolling upgrade. Commit-proof verification is unaffected: `countApprovals` verifies only `approve` votes.
- **API change.** `clusterVoteSigningPayload(hash, type, extra?)` became `clusterVoteSigningPayload(hash, vote)` in db-core's public exports; any out-of-repo caller breaks at compile time.
- **Coordinator trust.** The coordinator does not verify vote signatures, so `expiredAt` is as trusted as `conflictWith` / `heldBy` already are; `expiryRejectionClocks` only checks it is a finite number.
- **Writer side** is the follow-on ticket `a-writer-is-told-its-transaction-expired-by-name` (prereq on this one): today `CoordinatorRepo.pend` still throws the error, and a remote writer sees a stream reset.
