# A node deletes what it released

## What landed

The eligibility handoff that was an in-memory `Set<string>` with no consumer is now a durable ledger with a sweep that reads it, and the sweep is the only caller of the `deleteBlock` that ticket 3.2 built.

### The invariant, and where it is enforced

> **A block's bytes are deleted only after a release that confirmed at least the replication floor of other serving holders hold a current replica of it.**

Three structural facts carry it, and each is the answer to a way it could be lost:

- **Two writers, both inside the confirmed-release paths.** `recordReleased` in `libp2p-node-base.ts` is the one function that writes the ledger, called from `RingShiftCoordinator`'s `onRelease` (Phase C) and from the rebalance reaction's `result.released` arm. Nothing else may.
- **The sweep derives nothing.** `ReleasedBlockSweep` reads the ledger and never the node's ring, partition or owned-block set. Mid-shift the advertised partition is the *target* ring, so a block that merely looks outside this node's slice may be one whose handoff rolled back and is still being served.
- **The entry outlives the delete it records.** It is dropped after the delete, which is why 3.2 made `deleteBlock` ordered and idempotent. A crash in between leaves content with no metadata plus an entry, and the next run finishes it.

### `ReleasedBlockLedger` (`packages/db-p2p/src/storage/released-block-ledger.ts`, new)

One entry per released block under the new `optimystic-released/` namespace of the node's `IKVStore`, shaped after `OwedBlobLedger`: `record` (durable; refreshes an existing entry rather than leaving it), `list` (oldest release first, so a capped run makes progress), `get`, `remove` (durable), `noteFailure` (deliberately not flushed — the exception `OwedBlobLedger.markUnlisted` already makes, argued at the site). An entry carries `releasedAt`, `source` (`ring-shift` | `rebalance`), `releasedRev` and `attempts`. `RELEASED_BLOCK_KEY_PREFIX` is in `NODE_KV_NAMESPACES`, so a file-backed store sharing the block store's directory does not list these keys as blocks.

`releasedRev` is the one design decision worth reviewing closely. The ticket asked for the sweep to skip a block whose `latest` is "newer than the moment the entry recorded"; block metadata carries no wall clock for a committed revision, so the entry records the **revision this node held at release** (read through `StorageRepo.heldRevisions`, one call per release) and the sweep compares against that. A commit landing between that read and the write makes the recorded revision early, which makes the sweep *decline* the block — the safe direction.

### `ReleasedBlockSweep` (`packages/db-p2p/src/storage/released-block-sweep.ts`, new)

Per entry: `StorageRepo.deleteBlockIfNotAdvanced`, then drop the entry. Single-flight with one queued follow-on (`BlobCacheBudget`'s shape). Per-run cap of 256 entries. Three failed attempts per entry, after which it is passed over and left in the ledger for an operator to see. One `sweep:run` line per run — empty ones included, because `found=0` is the answer to "why is this node's disk not getting any emptier" — plus a line per block at the same level. One `LocalBlobService.sweep` request per run that deleted anything; nothing new was built for the blob half.

**One addition beyond the ticket's list, and it needs a reviewer's eye:** a run that left actionable entries behind asks for the next run itself. Without it the cap rations rather than chunks — a node that dropped below `shedAbove` by deleting these very blocks gets no further pressure request, and nothing else asks until the next release, so a large shed's remainder could sit indefinitely. The chain terminates (every entry a run acts on is deleted, dropped, or counted one attempt toward the bound), and `actionableRemaining` is the predicate. The cost is a stretch of back-to-back synced writes on a large shed, parked as a `NOTE:` tripwire at `runOnce`.

### `StorageRepo.deleteBlockIfNotAdvanced` (new capability `IReleasedBlockDeleter`)

The latch hold, the written-again check and the delete as **one** operation, because the check is only meaningful inside the same hold — a push or commit landing between a separate read and delete would be taken anyway. Answers `'deleted' | 'advanced'`. Wrapped in `endGroup` with a `wrote` predicate, so the delete is durable before it resolves (the sweep drops the entry only after that) and a block the check kept flushes nothing. Declared beside the file's other capability interfaces (`IHeldRevisionReader`, `IRevisionActionReader`) so the sweep is testable without a store.

### Wiring

- `prepareServingStore` builds the ledger over `kvStore` after the repo (it reads `heldRevisions` through it) and returns it on `ServingStore`.
- The arachnode block's `gcEligible` set and its `NOTE:` are gone; both release callbacks go through `recordReleased`, which logs `release:unrecorded` rather than throwing — the release itself already happened and is correct, and losing the record costs bytes this node keeps rather than a block the cohort loses.
- `RingShiftDeps.onRelease` is now `=> void | Promise<void>` and Phase C **awaits** it, so a shift is not reported as settled until its release is recorded. A rejection does not roll back (the range is already released); the production callback never rejects.
- The rebalance reaction's callback became `async`, with the ledger write placed **last**: every monitor effect above it (untracking, `recordGrowthOutcome`, the under-replication log) was synchronous before and stays so, because deferring the growth feedback past a store write would let the re-check timer fire first and re-push a block already confirmed.
- The sweep is built in `createLibp2pNodeBase` after the blob cache budget and before `storagePressure.start()`: it needs the blob service's piece sweep, and it must exist before the first sample. It runs once immediately (the start-up run that finishes interrupted deletes), binds `serving.late.requestReleasedBlockSweep`, and installs its stop wrapper between the cache budget's and the pressure reading's, so teardown order is pressure → sweep → cache budget → blob service.
- `StoragePressure` gained `requestReleasedBlockSweep`. The single `try`/`catch` around the one old trigger became `requestSheddingReactions` + `fireTrigger`, so one reaction's fault neither disarms the other nor takes the sampler down. The log message `pressure:enforcement-refused` is replaced by `pressure:trigger-refused trigger=<name>`; `docs/debugging.md` is updated.
- `node.releasedBlockLedger` and `node.releasedBlockSweep` are exposed on the untyped attachment surface, beside `node.blobCacheBudget` and the arachnode diagnostics.

## Deviation from the ticket — the sweep runs on the serving role only

The ticket asked for the sweep on **both roles**, "for the reason the blob reclaim pass runs on a client: one wiring, one rule". I did not do that, and this is the one place to check my reasoning.

The blob reclaim pass runs on a client because its dependency — the blob service — exists on both roles. The sweep's dependency is block storage, and a client has none the node reads through: `prepareServingStore` is called only when `servesBlocks`, so a client builds no `StorageRepo`, no read cache in front of `nodeStorage.blocks`, and no ledger. Wiring the sweep there would mean a second handle onto a store nothing else uses, deleting entries nothing can have written — both release paths are inside the serving role, so a client's ledger is not merely always empty, it does not exist.

What the ticket's "Arachnode disabled or no FRET" case actually required is honoured: the sweep sits **outside** the arachnode gate, so a serving node whose FRET service is absent this run still finishes what a previous run recorded.

The scenario the ticket's instinct covers — an operator flipping a serving node to `servesBlocks: false` over the same storage — is left alone deliberately. Such a node's *entire* block store is dead weight, not just its released blocks, so freeing a sliver of it is the wrong answer to that problem. If it ever matters it is its own ticket.

## Known gaps and judgement calls

- **A block the sweep keeps.** `'advanced'` drops the entry without deleting. That is self-healing rather than a leak: a push or commit that advanced `latest` emitted a collection change, which the owned-block feed turns back into a tracked block, so the next rebalance pass releases it again with the revision it now holds. A push of a revision this node already held advances nothing and emits nothing, so such a block *is* deleted — right, since nothing new was accepted. Verified by reading `StorageRepo.saveReplicatedBlock`'s `landed` emit and `ensureOwnedBlockFeed`; not covered by a test.
- **No test for the per-run cap, the attempt bound, the self-chaining or the pressure trigger** — arithmetic and wiring, per the ticket. The self-chaining predicate is the one of those with a loop in it; its termination argument is at the site and in the docs, and the two shipped specs both exercise runs that do *not* chain (`actionableRemaining` of 0).
- **The block-id-as-path class.** The ledger uses a block id raw as its key remainder, and `FileKVStore.keyToPath` joins key segments onto the base path, so an id with `..` segments would address a file outside the namespace. No guard was added: `FileBatchBackend.blockPath` (3.2's review fix) already refuses such an id at the storage boundary, so a block with one cannot be stored, owned or released. A `NOTE:` at the site points at `bug-a-block-id-is-used-as-a-file-path-without-validation`, which owns closing the class properly.
- **An unreadable block at release time** records an entry with no `releasedRev`, under which the sweep declines the block if it holds a revision at sweep time. Conservative (bytes kept) and documented on `ReleasedBlockEntry.releasedRev`; `StorageRepo.heldRevisions` already distinguishes "no revision" (`null`) from "could not read" (absent) and I collapse both.
- **`tickets/backlog/debt-node-attachment-reads-bypass-typed-surface.md` lists `gcEligibleBlocks`** among the untyped `node` attachments. That name no longer exists, and this change adds two more of the same shape (`releasedBlockLedger`, `releasedBlockSweep`). The ticket is about the pattern, not the names, so I left it for gardening rather than editing a backlog ticket from an implement stage.
- **`docs/arachnode-ring-handoff.md` § Local bytes vs. tracking did not exist** before this change, although `libp2p-node-base.ts` already cited it (a broken citation `lint:docs` does not see, since it is in a `.ts` file). It exists now and the citation resolves.

## Tripwires parked

- `runOnce` in `released-block-sweep.ts` — chained runs delete back to back with no pause, each one latch hold and one synced write; if a large shed's sweep is ever seen starving a node's own reads and commits, delay between *chained* runs.
- `runOnce` in `released-block-sweep.ts` — each run re-reads every ledger entry and acts on at most `limit` of them; the tripwire `OwedBlobLedger.list` and `BlobCacheBudget.runOnce` already carry. The fix if it profiles is a bounded `list(limit)`, not a cached scan.
- `released-block-ledger.ts` module header — the block-id-as-path `NOTE:` above.

## What to test, validate and use

**The invariant, over its branching** — `packages/db-p2p/test/ring-shift-coordinator.spec.ts`, "deletes only the blocks the confirm step counted". Drives a real `RingShiftCoordinator` through a move-out whose Phase B fails (Phase B is all-or-nothing, so both shed blocks roll back), runs the sweep over the real ledger: nothing deleted, nothing even recorded. Then the same move-out confirming: the two shed blocks are recorded with the revision held at release, both are deleted, the block the new partition still covers is never offered, and the ledger is left empty. Storage is stubbed — which ids reach the delete is what this decides.

**Resumability across the two pieces** — `packages/db-p2p/test/released-block-sweep.spec.ts`. A real `StorageRepo` over `MemoryRawStorage` is put into the state a crash mid-delete leaves (revision, transform and materialization written with no metadata, which is how `raw-storage-conformance.ts` reproduces it), a real ledger entry is recorded over it (and carries no revision, which must not make the sweep decline), one run finishes the delete and drops the entry, and a second run finds nothing.

**Placement note:** the first case lives in the ring-shift spec rather than the new file because the handoff harness that produces a rolled-back Phase B is already there — ~70 lines of mocks and a real-hash shed-range derivation. Copying it would have been the only alternative. Both behaviours the ticket named are pinned; a reviewer who disagrees with the split should move the case, not rewrite it.

**Worth a reviewer's own look:**
- Teardown order. `node.stop()` must run pressure → sweep → cache budget → blob service. Each wrapper calls its captured `previousStop` last, so last-installed runs first; the sweep's wrapper is installed between the budget's and the pressure reading's.
- The self-chaining `request()` from inside `runOnce`: `this.running` is still set there, so it becomes the single queued follow-on, and `stop()` awaits `queued ?? running` — awaiting the follow-on awaits the run it waits on. Check there is no orphan run after `stop()`.
- `deleteBlockIfNotAdvanced`'s `endGroup` + `wrote` pairing, and that the latch is held across both the `getLatest` and the `deleteBlock`.
- Whether `recordReleased` belongs at the ledger write or whether `ReleasedBlockLedger.record` should swallow its own failures. I put the catch at the call site so the ledger keeps the house rule that a write either lands durably or rejects.
