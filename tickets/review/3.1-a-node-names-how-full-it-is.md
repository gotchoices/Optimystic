# A node names how full it is

## What landed

### `StoragePressure` — the one reading (`packages/db-p2p/src/storage/storage-pressure.ts`, new)

`StorageAccount` measures the disk; this reads that measurement against the operator's thresholds and names an **ordered stage**: `unknown` < `slack` < `steady` < `shedding` < `refusing`. Exports:

- `pressureStageOf(capacity, thresholds)` — pure, the one place a threshold meets a measurement.
- `usedFractionOf(capacity)` — `undefined` exactly when the node cannot measure its storage; unclamped above 1.
- `atLeastPressure(stage, atLeast)` — the one comparison a consumer makes, so no site re-derives the order. `unknown` is first in `STORAGE_PRESSURE_STAGES`, so `atLeastPressure('unknown', 'shedding')` is `false`.
- `StoragePressureThresholds`, `DEFAULT_STORAGE_PRESSURE_THRESHOLDS` (0.40 / 0.85 / 0.95), `resolveStoragePressureThresholds` (defaults + validates, throws).
- class `StoragePressure` — `read()` (async, samples, never rejects), `stage()` (synchronous, no I/O, the last stage *measured*), `configuredThresholds()`, `start()`, `stop()`.

`read()` logs `pressure:stage` only when the stage **changed**, and `pressure:unmeasured` when a scan threw — in which case it keeps the last stage rather than demoting to `unknown`. Its own unref'd timer samples once a minute (first sample at 0 ms after `start()`, each later one an interval after the previous read *ends*), and `read()` single-flights so a consumer's call and a tick's sample share one scan and one stage-change line.

### Thresholds are the operator's

`NodeOptions.storageAllotment.thresholds` (`StorageAllotmentOptions.thresholds`, typed `Partial<StoragePressureThresholds>`). Resolved once in `createLibp2pNodeBase` beside `assertStorageAllotmentBytes`, before anything starts, throwing on a value outside `(0, 1)` or an order other than `reclaimBelow < shedAbove < refuseAbove`. `RingSelectorConfig.thresholds.moveOut` / `.moveIn` keep their names and are now **fed** from `shedAbove` / `reclaimBelow` (the two `0.85` / `0.40` literals in the `RingSelector` constructor call are gone), threaded into `wireServingRole` as `ServingRoleContext.pressureThresholds`.

`StorageAccount` itself does **not** read `thresholds` — it measures; the field rides along in the same options bag because that is where an operator expects it.

### Low space advertises less work, not more

`RingSelector.determineRing` answers the new exported `MAX_RING_DEPTH` (16) instead of `-1` when `availableBytes < minCapacity`. The sentinel is gone, and with it `createArachnodeInfo`'s `Math.max(0, ringDepth)` clamp and its `ringDepth >= 0` partition guard — so such a node advertises the narrowest slice **with a real partition**, where before it advertised ring 0 (the whole keyspace) with none. `16` is now `MAX_RING_DEPTH` at all four sites that had the literal. The unknown-capacity answer is unchanged (ring 0).

### The cache shrinks as the node fills

A sample at `shedding` or above calls `BlobCacheBudget.request()`, reached through a `let` the factory assigns once the budget exists (the budget needs the started node's blob service; the pressure reading is built before `createLibp2p`). `cacheBudgetBytes` itself is untouched — this supplies only the trigger the cache was missing. The `NOTE:` above `BlobCacheBudget` now names the pressure sample as its third caller.

### Wiring

`storagePressure` is built beside `storageAccount` on **both** roles, outside the arachnode gate; started right after `blobCacheBudget.request()`; its `stop` wrapper is installed *after* the budget's so it runs *before* it. It is on the typed attachment surface (`OptimysticNodeAttachmentsBase.storagePressure`), not `(node as any)`. The arachnode tick reads `storagePressure.stage()` for its transition log line.

## How to exercise it

**Thresholds throw at construction.** `createLibp2pNode({ storageAllotment: { thresholds: { shedAbove: 1.2 } } })` → `RangeError` naming `shedAbove`. `{ reclaimBelow: 0.9, shedAbove: 0.5 }` → `RangeError` naming the required order. `{ thresholds: {} }` and no `thresholds` at all → the 0.40/0.85/0.95 defaults, and the node behaves exactly as before this ticket.

**An unmeasurable node does nothing.** A node on `memoryNodeStorage()` with no `storageAllotment.bytes` has no `totalBytes`, so `node.storagePressure.stage()` stays `unknown` forever and `atLeastPressure(stage, 'shedding')` is false. This is the case every sibling ticket's gate must read as "do nothing" — reading it as full is the failure mode to look for in each.

**The stage moves.** Set `storageAllotment: { bytes: N, usedBytesCacheTtlMs: 0 }` on a file-backed node, write until past `0.85 * N`, and `await node.storagePressure.read()` answers `shedding` with the capacity it derived that from; past `0.95 * N` it answers `refusing`. With `DEBUG=optimystic:db-p2p:storage:pressure` each transition prints one `pressure:stage` line and the steady stretches print nothing.

**`stage()` costs nothing.** It is a field read. The sibling tickets' gates (push handler, announce handler, promise vote) must call `stage()`, never `read()` — `read()` can walk a directory.

**Low space advertises ring 16.** `ring-selector.spec.ts` covers both arms by unit test. In a real node the start-up `node-wiring` line for an allotment below 100 MiB now says ring 16 and "keeps serving what it already holds".

**Teardown.** `node.start()` then `node.stop()` with no writes: the pressure timer is unref'd (it cannot hold a process open) and `stop()` awaits the sample in flight. `test/node-read-cache-wiring.spec.ts` builds and stops real nodes and passes.

## Known gaps and judgement calls — read these first

**1. "Have the arachnode tick read `stage()` rather than scanning again" was interpreted narrowly, and the reviewer should decide whether that is enough.** The ticket's TODO asks for this, while its *Edge cases* bullet "Both timers on one memo" says of the same interaction "Nothing new is needed". Those pull in opposite directions: making `shouldTransition` act on `stage()` would delete `RingSelectorConfig.thresholds`' only reader, which the ticket also says to keep and feed. What landed: the thresholds are shared (one figure, two readers) and the tick's transition log line reads `stage()`; `shouldTransition` still forms its own `usedPercent` from the account's own (memoized, therefore free) `capacity()`. The two can disagree only by one sample interval, and the ring arm is EWMA/dead-band/dwell-damped anyway. Restructuring `shouldTransition` to take the stage would have meant rewriting a large part of `ring-selector.spec.ts` for no behavioural gain. **If the reviewer reads the TODO as binding, this is the one place to push back.**

**2. New I/O at start-up on a node with `node-wiring` logging off.** `firstSampleDelayMs` defaults to 0, so the first pressure sample is a block-store scan right after `node.start()`. It is off the critical path (unref'd timer, nothing awaits it) and `logStorageAllotment` already pays the same scan when logging is on — but with logging off this is a new directory walk at start on a file host, where there was none. The deliberate alternative (first sample an interval in) would leave a node that came back already over its allotment refusing nothing for a minute, which the ticket explicitly wants avoided. Flagging rather than hiding: if a host reports a slow start over a very large store, raise `firstSampleDelayMs`.

**3. `StoragePressure`'s class behaviour is unit-tested only through its pure parts.** The spec covers `pressureStageOf` and `atLeastPressure`. The timer, the single-flight `read()`, the stage-change log, the kept-stage-on-failure path and the cache-enforcement trigger are verified by **inspection**, not by a test — which is what the ticket's Tests section asks for ("the wiring is wiring", and the rejecting-`capacity()` case is "verified by inspection at the one call site"). A reviewer who disagrees about `read()`'s never-reject contract or the kept-stage path has a `setTimer` + `account` seam to test through; that would be a new test, not a changed one.

**4. Nothing consumes `refusing` yet.** By design — the gates are siblings 3.3–3.6. So `refuseAbove` has no reader in this diff beyond the stage it names, and the only *behavioural* changes a reviewer can observe today are: the ring decision's thresholds became configurable, the below-minimum ring answer changed from 0 to 16 (with a partition), and the read cache now gets enforced on a timer when the node is full.

**5. `reference-peer`'s `logRingInfo` was not extended** to print the stage beside `storageAccount.capacity()` (`packages/reference-peer/src/cli.ts:219`). Out of this ticket's scope; `feat-an-operator-can-see-what-fills-a-node` owns the operator-facing report.

## Tripwires parked

- **`stage()` staleness** — `NOTE:` at `StoragePressure.stage()` (the ticket's verbatim text): between samples a node can accept up to one sample interval's inbound data past its limit; the `refuseAbove`-to-allotment gap is the headroom; if a node is ever seen well past its allotment between samples, add the bytes accepted since the last sample to the reading rather than scanning on the gate.
- **Ring 16 is the floor of advertised responsibility** — `NOTE:` at `RingSelector.shouldTransition`'s move-out arm: `d` is clamped at 16, so `d >= 16 + 1 - h` is unreachable and a node there has only refusing left. Also records that a *running* node below `minCapacity` does not jump to 16 — the single-step rule moves one ring per dwell, and the below-minimum answer is taken at bootstrap and by one-shot callers.
- **Hold-release sites still trigger no cache enforcement** — the `NOTE:` above `BlobCacheBudget` was rewritten rather than removed: the pressure sample bounds the wait to a minute *on a node under pressure*, which is where it matters, but a node at `steady` whose `unpin` or reclaim left the cache over budget still waits for a read or a restart. Condition to act on: a node at `steady` seen over budget with its reads idle.
- **An unmeasurable node's stage flapping** was considered and deliberately left undamped; the reasoning is in storage.md §10, not a code `NOTE:`, because it is a property of the design rather than of one site.

## Where to look hardest

- `pressureStageOf`'s strictness and the `totalBytes === 0` → `refusing` choice (`usedFractionOf`): a 0 total can only come from a location reporting no free space with nothing stored, i.e. a genuinely full disk. `RingSelector.shouldTransition` reads the same case as `usedPercent = 0`. That divergence is intentional (the ring decision is about pricing coverage, the pressure reading about room) but it is the one place the two readers of one figure genuinely differ, and it is worth a second opinion.
- The stop-wrapper ordering at the `storagePressure.start()` site: pressure must stop before `BlobCacheBudget`, which must stop before `LocalBlobService`. Wrappers run newest-first, so the install order is blobs → budget → pressure.
- `arm()`'s cancel-then-replace (copied from `BlobReclaimPass.arm`): a `read()` that lands while the schedule's timer is pending re-arms from the same place, and an arm that only overwrote the canceller would leak a live, un-cancellable timer per call.
- Whether `MAX_RING_DEPTH` should live in `ring-selector.ts` or beside the partition code in `arachnode-partition.ts`, which is the other place a prefix width is reasoned about.
