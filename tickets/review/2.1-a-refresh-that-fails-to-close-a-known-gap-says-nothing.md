# Review: `Collection.update()` now reports a refresh that fell short of the tail

## What was built

`Collection.updateInternal()` refreshes in two steps that arrive at a revision by different
routes: it reads the log **tail block**, whose stored state names the newest revision committed
under this collection id, and then it walks the log chain and advances the collection to whatever
that walk reports. The tail's number was being used only to unblock the walk (it is set on a
throwaway local `TransactorSource` so pending non-tail blocks are visible) and then thrown away. If
the walk landed **below** it, `update()` returned as though nothing newer existed.

Three changes:

1. **`packages/db-core/src/collection/collection.ts`** — `updateInternal` captures
   `tailRev = source.actionContext?.rev` immediately after `bootstrapContext` (that local source is
   where the tail's revision already sits — no extra fetch), and after `advanceContext` has run
   compares it against `this.source.actionContext?.rev`. On a shortfall it emits one line on the
   existing `db-core:collection` logger:

   ```
   optimystic:db-core:collection collection:context-short-of-tail id=test-collection before=1 after=1 tail=6
   ```

   That is a real captured line from the new test, not a sketch. It logs and returns normally — it
   does **not** throw, and it does **not** adopt `tailRev`. Both of those are deliberate and the
   reasoning is in a comment at the site.

2. **`packages/db-core/test/collection.spec.ts`** — new describe block with four tests (three
   silence assertions, one shortfall assertion), plus a local `captureCollectionLog` helper that
   enables the namespace and swaps `debug.log`, restoring both afterwards.

3. **`docs/debugging.md`** — new subsection *"Did the refresh itself fail to close the gap?"*
   between the index decision table and *Comparing action ids*, documenting the line field by
   field, stating that silence is meaningful, and wiring it into the decision-table row *"a live
   refresh ran immediately before the read and `rev` did not move"* (which now points at it).

## Why the shape it has

The originating investigation (`index-trace-cannot-tell-a-forked-collection-from-a-lagging-one`)
hit a machine whose index collection sat one revision behind its sibling while a live scan called
`update()` on it ~100 times over 30 seconds, and the revision never moved. From outside the class,
"the refresh had nothing to adopt" and "the refresh failed to adopt something it had just read" are
indistinguishable — and `update()` had read the authoritative number on every one of those calls.
This line makes the two cases separable from the log alone. Its sibling
`collection:context-not-lowered` (same file, `advanceContext`) covers the opposite direction — a
collection declining to move *backwards*.

## Use cases to exercise

- **The healthy path is the one that matters.** An ordinary refresh of an already-current
  collection, and a refresh that genuinely catches up to a newer commit, must emit **nothing**. A
  false positive here would be noise in every log this line is meant to be read in. Both are
  covered by tests; worth re-checking by hand against other `update()` call sites (the transaction
  coordinator's blanket refresh between commit retries, `updateAndSync`, the Quereus plugin's live
  scan path) that none of them routinely trip it.
- **Nothing committed yet.** No header, no tail, or a tail with no `latest` → `tailRev` stays
  undefined → silence. This is the common brand-new-collection state and must never be reported as
  a shortfall.
- **Shortfall.** Tail claims a revision the chain walk cannot reach → exactly one line, `update()`
  still resolves.
- **Reading the line in the field:** enable `DEBUG='optimystic:db-core:collection'`, reproduce a
  stale index read, and confirm the presence/absence of the line splits the decision-table row as
  documented.

## Known gaps — treat these as starting points, not a finished floor

- **The shortfall test fabricates the disagreement rather than reproducing it.** It wraps
  `TestTransactor` and inflates `state.latest.rev` by 5 on the *unpinned* tail read only (the read
  `bootstrapContext` makes), leaving every pinned read of the walk untouched. That proves the
  comparison and the log line, but it does **not** prove that any real-world condition produces a
  shortfall — no such condition has been demonstrated. The line is a diagnostic aimed at a
  suspicion, and the ticket was explicit that establishing whether a shortfall is always a fault is
  a later, evidence-based decision. If a reviewer can construct a natural shortfall (partitioned
  cohort, invalidation entry taking a revision slot, a checkpoint the walk stops at), that is a
  strictly better test and worth having.
- **The double had to be armed after `open`.** The first attempt inflated from construction, and
  the test failed with `collection:context-not-lowered id=test-collection held=6 read=1` instead —
  because `Collection.open` bootstraps from the *same* unpinned tail read, so an inflated tail
  simply pins the opened collection at the inflated revision. Worth a reviewer's attention on its
  own merits: **an inflated or wrong tail revision at open time silently pins the collection at a
  revision its log never reaches, and every later refresh then reports `context-not-lowered`
  forever.** That behaviour predates this ticket and was not changed here; it is noted rather than
  filed because it was observed only through a deliberately lying test double.
- **`before=`/`after=` render `none` when no revision is held; `tail=` is always numeric.** The
  format string mixes `%s` and `%d` accordingly. Any parser written against this line should expect
  the word `none` in the first two positions.
- **No integration-level assertion.** Nothing in `db-p2p` or the Quereus plugin asserts on this
  line; only the db-core unit tests do.
- **One `%d`/`%s` caveat for future capture tests:** `debug` substitutes only its own formatters
  before calling the sink, so the raw args are not the text. The new helper runs them through
  `node:util`'s `format` — same trick as `packages/db-p2p/test/support/capture-log.ts`, which was
  not reused because it is hard-coded to the `db-p2p` namespace prefix. Two near-identical
  capture helpers now exist in the repo (plus an inline third in
  `packages/db-core/test/cohort-topic/coldstart.spec.ts`); consolidating them is a fair finding if
  a reviewer thinks it is worth a ticket.
