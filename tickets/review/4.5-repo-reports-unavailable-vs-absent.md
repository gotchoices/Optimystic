# A block read now distinguishes "never existed" from "I could not find out"

## What was built

The per-block wire answer (`GetBlockResult` in `packages/db-core/src/network/struct.ts`) gained an
optional `unavailable?: 'unmaterializable' | 'peers-unreachable'` field. Absent field = the answer
is authoritative — every existing producer (including `TestTransactor`) keeps its meaning with no
change. A new `BlockUnavailableError` (same file, exported from the package index) carries the
block id and reason.

Producers:

- **`StorageRepo.get`** (`db-p2p/src/storage/storage-repo.ts`) flags `'unmaterializable'` when
  the block reads as absent but this node holds records proving it exists:
  - the read-driven promotion's `MissingBaseRevisionError` catch fired (the reported trace: a
    pending for revision 2 with no revision 1 to apply it to), or
  - `blockStorage.getBlock()` **threw** (truncated history "Failed to find materialized block", or
    a failed restore). These throws used to escape `Promise.all` and fail the whole batch; they are
    now caught **per block**, so healthy siblings in a mixed batch are still served.
  - The `context.actionId` branch's `Pending action … not found` throw is untouched
    (caller-contract violation, per ticket). When that branch serves a pending applied to a
    missing base and materializes nothing, the entry carries the flag too.
- **`CoordinatorRepo.get`** (`db-p2p/src/repo/coordinator-repo.ts`) flags `'peers-unreachable'`
  in its cluster-consult `catch`, **only** when the block was locally missing (`isMissing`). A
  merely-stale block with a failed consult keeps its real local answer, unflagged. A sharper
  storage flag (`'unmaterializable'`) is never overwritten. `skipClusterFetch` sync reads are
  never flagged.

Consumers:

- **`NetworkTransactor.get`**: a flagged entry no longer counts as "answered", so it earns the
  second-chance retry against a different peer that an authoritative absent deliberately does not
  get. The merge is now a three-way ranking per block: has a block > authoritative absent >
  unavailable. The long comment justifying no-retry-on-absent was updated to match.
- **`TransactorSource.tryGet`**: a surviving blockless flagged entry **throws
  `BlockUnavailableError`** instead of returning `undefined`, recording no read dependency. The
  throw propagates through Chain/BTree/Log/Collection, so `Collection.open`/`createOrOpen`
  against an unretrievable header reject instead of inventing an empty collection.

One behavior consequence discovered mid-implementation: the read-repair promotion path
(`CoordinatorRepo.promoteCorroborated`) used to learn "no local promotion can reach this
revision" via a storage throw and logged `cluster-fetch:promote-unavailable`. With the per-block
catch, that throw became a flagged entry — so `promoteCorroborated` now checks the flag and emits
the same log before falling through to acquisition. The existing spec pinning that observability
(`coordinator-repo-read-repair-content.spec.ts`) caught the regression and passes again.

Docs: `docs/internals.md` documents the three-valued block answer next to the missing-base
material and updates the `Collection.open` caveat (this ticket was the "not yet landed" half);
`docs/transactions.md` gained an "Unavailable reads" subsection (not a StaleFailure, not retried
by `Collection.sync`). Stale docstrings in `collection.ts` referencing this ticket as unlanded
were rewritten.

## Use cases to poke at in review

- **The regression that matters most**: `Collection.createOrOpen` of a genuinely new collection
  must keep creating. Pinned at three layers: storage (`a block never written returns { state: {} }
  with NO unavailable field`), coordinator (`stays an authoritative absent when the consult runs
  but corroborates nothing`), collection (`createOrOpen against an authoritative absent still
  creates`). If the flag ever leaks onto that probe, collection creation deadlocks.
- **Tombstones**: deleted block reads back absent, unflagged (`a tombstoned block reads back
  absent with NO unavailable field`).
- **Mixed batches**: one wedged block + healthy sibling → sibling served, wedged flagged
  (`a mixed batch returns healthy siblings alongside the flagged block`).
- **Transactor retry cost**: flagged answers now pay a second round trip
  (`network-transactor.spec.ts` "retries an unavailable answer…", "carries the unavailable flag
  through…"). Absent answers still resolve in exactly one round (pre-existing spec).
- **End-to-end**: `collection.spec.ts` "unavailable header vs authoritatively absent header" is
  the direct assertion for the reported bug.

## Known gaps / honest notes for the reviewer

- **A consult that runs but corroborates nothing stays an authoritative absent, even when every
  peer merely timed out.** The `ClusterLatestCallback` contract cannot distinguish "peer answered:
  I hold nothing" from a per-peer timeout (both surface as `undefined`), so a wholly-silent cohort
  that does not *throw* produces the same no-quorum outcome as a healthy cohort probing a
  nonexistent block — and flagging no-quorum would break the new-collection probe. Deliberately
  scoped per ticket to the *thrown* consult; NOTE recorded at the catch site in
  `coordinator-repo.ts`. If lying-silent cohorts show up in practice, the callback contract needs
  a responders count.
- **No explicit spec for `Collection.update()` hitting an unavailable header mid-life.** The
  propagation argument is structural — `updateInternal`'s `tracker.tryGet` throw is not a
  `StaleFailure`, so `syncInternal`/`updateAndSync` cannot absorb it — and the open/createOrOpen
  paths are tested end-to-end, but no test drives `update()` specifically into the flag.
- **The wire round-trip is trusted, not tested.** The repo protocol serializes responses with
  `JSON.stringify` (`repo/service.ts`), so the optional field needs no codec change; no spec
  exercises the flag across a real libp2p stream.
- **Behavior change beyond the flag**: a context-driven `StorageRepo.get` naming a revision the
  node cannot restore used to *throw* out of the whole batch (spec comments called it a
  "storage-layer read fault"); it now returns a flagged entry. All existing specs still pass, but
  callers relying on that throw (none found in-tree) would see a shape change.
- Pre-existing lint-level diagnostics (unused `blockIds` param in `network-transactor.ts`
  `commitBlock`, async-hint suggestions in `coordinator-repo.ts`) predate this ticket and were
  left alone.
