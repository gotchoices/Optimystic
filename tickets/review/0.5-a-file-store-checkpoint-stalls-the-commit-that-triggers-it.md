# A file-store checkpoint no longer stalls the commit that triggers it

GitHub #62 (Sereus; optimystic 1.27.0, `FileRawStorage`, solo node, macOS 15 on Intel): every checkpoint of the write-ahead log made one commit take 5–7 s and the dozen after it 1–2 s. Cause, from the fix stage: a checkpoint synced its files and directories sixteen at a time; on macOS libuv implements `fsync` as `F_FULLFSYNC` (a whole-drive cache flush, serialized by the device), and every `fs` call shares libuv's four pool threads, so the checkpoint held every thread and queued the commits' own appends and log syncs behind it.

## What changed

- **One tree sync at a time, giving way to the log.** `FileWriteLog.syncSealed` syncs the sealed segment's files, then directories, one at a time. Before each, `giveWayToLog` waits while any task is queued or running in the log's queue (commit, sync step, seal), counted by `enqueue` (`queuedTasks`) and woken when the count reaches zero. A sync already in flight is never interrupted, so a commit's log sync waits for at most one tree sync.
- **Behind, and the per-commit share.** `isBehind`: the current log has reached `checkpointBytes` while the previous checkpoint is still running (from its seal to the end of its truncate). The seal now publishes a `CheckpointPace` (paths to sync, sealed bytes) inside its queued task, beside the reset of `appendedBytes`. While behind, tree syncs stop giving way, and a commit, after its append, is charged by `CheckpointPace.charge` and its `commit()` promise resolves only once that many more syncs have completed. The wait happens after the task leaves the queue (`commit` chains it with `.then`), so a waiting commit is not counted by the give-way rule and blocks no other append.
  - Charges accumulate in append order on one fractional cursor; only the target is rounded up. Two commits waiting at once wait for two shares, so writers together are held to the disk's rate; many tiny records can share one sync instead of each paying a whole one. (The ticket said "rounded up" per commit; rounding the cumulative target is the same rule without over-charging small records. Flag it if you read the ticket the other way.)
  - **Deviation from the ticket: the share has a second term.** The share is the larger of (a) the ticket's formula, `record bytes × sealed paths / sealed bytes`, and (b) `record bytes × syncs not yet charged / bytes left before the current log reaches 2 × checkpointBytes`. A record that would take the log past that point is charged every remaining sync. Why: in the macOS model below, (a) alone does not keep up. A writer of strict flushes keeps the queue busy most of the time (each sync step's log sync and tree writes run inside the queue), so the checkpoint makes almost no progress before it falls behind. Charging at rate (a) then lets the current log grow by about one sealed segment while the checkpoint finishes, so each sealed segment is about `checkpointBytes` bigger than the last, and the log grows without bound. Term (b) is what makes the ticket's own promise, "the log stays near twice `checkpointBytes`", hold. It binds only when the checkpoint was starved before it fell behind.
  - The first commit to wait in a checkpoint logs once: `checkpoint-behind: …` on `optimystic:db-p2p-storage-fs:write-log`, with the log's size and synced/total paths.
  - On checkpoint end, success or failure, `pace.end()` releases every waiting commit. A commit whose record was appended resolves normally; a latched log fails its `durable` as before.
- **Unchanged:** the seal (still in the queue), the truncate, crash cases and replay order, the failure latch, idle and size triggers. Replay keeps 16-wide syncs (`syncDirtyPaths`, constant renamed `UNCONTENDED_SYNC_CONCURRENCY`). A checkpoint started after `release()` has begun (`closed`), meaning the close's final one or a queued `checkpointAgain` run, syncs 16-wide with no pacing, as the ticket allowed. A paced checkpoint already in flight when close begins finishes one at a time. A commit never waits for a checkpoint it did not fall behind.
- **Bound:** the current log reaches about 2 × `checkpointBytes`, plus about one record from each store over the directory (each store's write group has one commit in flight, and a commit appends before it waits). The `replaySegment` NOTE says this now.
- **Docs:** README § Write-ahead log (the Checkpoint paragraph, plus the relaxed-flush "resolves as soon as appended" sentence, which now has the behind exception); `storage.md` §6 (the checkpoint paragraph, the relaxed-commit sentence and the `FileBatchBackend` row of the backends table).
- **Tripwire** `NOTE:` at `giveWayToLog`: a writer faster than the disk alternates a run of `checkpointBytes` at full speed with a run at about twice the disk's pace. If that ever hurts, stop giving way part-way to `checkpointBytes`.

## Tests added (`test/file-write-log.spec.ts`, `FileWriteLog checkpoint pacing`)

Helper: `parkHandleSyncs` in `test/support/fs-injection.ts` wraps `fs.promises.open`. It parks a handle's `sync` when a predicate on its path says so (asked at sync time, so the log's handle, `FileWriteLog.logPath`, can be parked on demand), records each sync's start and end (`started`, `mostInFlight`), and exposes `closed` per parked sync. `closed` resolves when the handle is closed, which is the point the checkpoint's loop moves on, so the negative assertions do not depend on timing.

- *syncs one tree path at a time, and starts none while a commit is in the log's queue*: 40 files, with tree syncs parked and a commit held in the queue by parking its log sync. Releasing the parked tree sync starts no further tree sync until the commit resolves, then the next one starts. Max tree syncs in flight over the whole checkpoint is 1. Fails on the old code (16).
- *a commit made while the checkpoint is behind waits for its share …, and no longer*: `checkpointBytes` 1000, a 20-file sealed segment (22 paths), 10 syncs made, then a filler commit and a 90-byte commit that crosses the threshold. That commit stays pending until exactly `ceil(90 × 22 / sealed bytes)` = 2 more syncs complete, then resolves while the checkpoint still has syncs left. Fails on the old code (resolves at once).
- *a commit that takes the log past twice checkpointBytes waits for the rest of the checkpoint*: the sealed segment is about 3× the threshold and no syncs are done yet. A record taking the log past 2 × `checkpointBytes` is still pending with 19 of 20 files synced, although term (a) alone would charge it about 9. Fails without term (b), and on the old code.
- `test/fsync-count.spec.ts` unchanged and passing: its groups never reach a checkpoint.

The three new tests were each checked to fail with the old behaviour put back, and the third to fail with only term (b) removed. They passed on 8 repeated runs. The `started` count excludes the store root, because on non-Windows platforms the open, seal and truncate also sync the root. They have run on Windows only; their non-Windows paths (directory syncs) were reasoned through but not executed.

## The macOS effect is confirmed only in a model

The ticket's model: every handle `sync` reserves the next slot of one simulated device and holds a pool thread until the slot ends (`crypto.pbkdf2` sized to the wait), then makes the real sync; `process.platform` is set to `darwin` so directories are synced. It drove `StorageRepo.pend` and `commit` over `FileRawStorage` with `checkpointBytes` 4 MiB and 20 new 8 KB blocks per transaction. Run on Windows against this build:

| device slot | transactions | per transaction | checkpoints | close |
|---|---|---|---|---|
| 10 ms | 40 | ~100 ms until the log is behind, then ~2.0 s (first episode) and ~3.7 s (second; term (b) binding) | the first truncated at 17.9 s, during the run | 59 s (the in-flight paced checkpoint, then a ~8 MiB one 16-wide) |
| 3 ms | 60 | steady state: 8 at ~80 ms, then 8 at 1.1–1.25 s, repeating; max 1.25 s | truncated every ~10 s, bounded | 12.5 s |

For comparison, the ticket's runs of the old code under the same model: 16-wide gave 3.7–30.8 s per transaction during a checkpoint; one-at-a-time with no pacing left the first checkpoint unfinished at the end of the run and took 105 s to close.

**The ticket's expectation, "every transaction within about twice its neighbours", is not met where a behind episode starts or ends.** In both runs the simulated disk is 7–20× slower than the writer, so any scheme that keeps the log bounded must slow writes to the disk's pace once the checkpoint is behind. Until then the ticket's rule lets writes run free. Within an episode, neighbours are within 2× of each other; there is no longer a single multi-second stall. The total time is set by the disk, as before.

**For the reporter (GitHub #62):** ask them to rerun `commit-latency.mjs` on a build with this fix, three times: default settings, `CHECKPOINT_MIB=4`, and `CHECKPOINT_MIB=64`. Watch for the `checkpoint-behind` log line. The 64 MiB row (commits slowing from about #101 with no checkpoint yet) decides whether the follow-on is needed. That follow-on, from the fix stage: start the paced tree syncs before the size threshold is reached, so unsynced tree data never piles up for the log's `F_FULLFSYNC` to flush. It would also smooth the fast/slow alternation recorded in the NOTE above.

## Points for the reviewer

- Term (b) of the share is my addition beyond the ticket's text (reasoning above). Keep it, replace it with a hard cap (wait for the whole checkpoint at 2 × `checkpointBytes`), or drop it and accept a log that grows; the third test pins it.
- A relaxed flush (`syncWithinMs > 0`) is now delayed by pacing while the checkpoint is behind. Its `durable` timing is unchanged; only `commit()`'s own resolution waits. A `WriteGroup` has one commit in flight, so while a commit waits, that store's later flushes are joined into its next seal: fewer, larger records.
- `giveWayToLog` uses a single wake slot (`wakeWaitingSync`), which is correct only because one checkpoint runs at a time (`runCheckpoints`).
