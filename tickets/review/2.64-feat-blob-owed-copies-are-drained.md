# A blob's owed copies are drained

`node.blobs.announce(ref, scope)` now makes a node owe the blob to its cohort, and `BlobCopyDrain` announces it to each owed member until every member that accepts blobs holds it, reporting durability as that changes and releasing the writer's `owed` hold at `full`. A committed reference therefore survives the writer going offline once the cohort holds it.

## What exists

`BlobCopyDrain` (`packages/db-p2p/src/blob/blob-copy-drain.ts`) holds one `DrainScheduler<OwedBlobEntry, BlobCopyTally>` and supplies two seams: the owed-blob ledger as the entry source, and one announcement round per entry. Its public surface is `owe`, `noteHeld`, `settle`, `checkNow`, `isDeclining`, `noteDeclined`, `getDiagnostics`, plus `start`/`stop`.

- **The cohort view.** `findCluster(routingKeyForBlob(ref))` plus `absentCohortMembers` (an offline member still owes a copy), then an acceptance lookup over the other members. Any of the three failing leaves the view **unresolved** rather than short of members — a view short of members could read `full` and release the writer's hold while a member that never got the blob is simply unnamed.
- **One entry's step.** Settle; stop at `unrouted`, at a vanished entry, or at `full`; `solo` when nobody else accepts; `waiting` when no owed member is reachable; otherwise announce to each reachable owed member **in turn** and act on the answer (`whole` → holder, `fetching` → wait for its `held`, `declined` → remember the peer, `not-responsible`/`unreferenced`/a rejection → count against the give-up rule).
- **`settleRef` is the one durability transition,** serialized per reference by the drain's own `KeyedSerialQueue`, so a pass and an arriving `held` cannot both decide the class changed and emit the same value twice. At `full` it writes the class on the record, deletes the entry, and only then releases the `owed` hold.
- **Wiring** (`createLibp2pNodeBase`): the drain is built on **both roles** — a client is often the machine a blob was put on — which is why `PartitionDetector` moved up out of `wireServingRole` and is threaded in through `ServingRoleContext`. `NodeOptions.blobs.copy` configures it; `enabled: false` builds none and then `announce` **rejects** rather than recording an entry nothing would send. `node.blobCopyDrain` and `node.owedBlobLedger` are exposed for tests and diagnostics, and the `onHeld` closure now feeds `noteHeld`.

## Use cases to exercise

- **A writer commits a reference and goes offline.** `announce` → first `onDurability` (`local`) before it resolves → the drain announces → `majority` → `full`, at which point the owed entry is gone and the writer no longer holds the blob on the cohort's behalf. Note the consequence worth checking: because releasing the `owed` hold can delete the record when it was the last hold, `stat` on such a blob afterwards reports `unknown` with **no** durability, not `full`. (In the specs below the blob is also pinned by its `put`, so the record survives and reports `full` — a reviewer should decide whether both of those are the intended, documented behaviours.)
- **A phone in the group.** A cohort of only `on-demand` peers: every other member answers `declined`, the class stays `local`, the entry and the hold stay, and passes tally `solo` forever. Nothing is counted against anyone.
- **Two machines disagreeing about the cohort.** `not-responsible` is retried under the give-up rule and the peer is dropped for that blob until it reconnects — it is *not* remembered as declining, because it said nothing about whether it takes blobs.
- **Announcing before the commit is visible.** `unreferenced`, then `fetching` on a later pass. A receiver whose committed-state read is merely slow answers the same way, and the drain treats both as "ask again".
- **A restart with copies outstanding.** The entry and the `owed` hold are on the node's durable store, so a restarted writer resumes announcing.
- **`blobs.copy.enabled: false`.** `announce` rejects; the node still serves, fetches and holds blobs. Verified by inspection only — see the gaps below.

## Where this deviates from the ticket — please weigh these

- **The restart spec restarts the *writer*, not the receiver.** The ticket's test list says "restart the receiver mid-pull … the receiver asks only for the pieces it lacked". Restarting the receiver exercises `BlobAnnounceReceiver.resume` and the fetcher's piece-level resumption — both built by earlier tickets, and the latter already pinned by `blob-fetcher.spec.ts` ("keeps what an interrupted fetch stored and asks only for the rest") — while leaving **this** ticket's durable state untested. Restarting the writer instead covers the claim the ticket's own edge-case note leads with ("the entry and the `owed` hold are on the node's store; the scheduler's start pass resumes announcing"), and still yields the piece-count assertion, because stopping the writer is itself what interrupts the receiver's pull. If the reviewer wants the receiver's `resume` pinned over real nodes too, that is a separate test and arguably a separate ticket against the receiver.
- **The restart spec drives the resumed pass with `checkNow()`,** not the start pass. A2's start pass runs before the re-dial, so with nobody connected it skips; the natural `connection:open` trigger would do the work ~5 s later. The substantive claim — the entry was read back off the store that outlived the process — is unchanged, but "the **start** pass resumes announcing" is not literally what is pinned.
- **`durability:listener-threw` is not a `blob:copy` line.** The ticket asks for it in the `blob:copy` row of `docs/debugging.md`; it is emitted by `LocalBlobService.emitDurability` and is already documented under `blob:store`, where it belongs. Nothing was added.
- **The `blob:copy` row of `docs/debugging.md` already existed** before this run (written ahead of the code by an earlier ticket). It was read against the implementation and matches, so it was left as it stands; only the `blob:protocol` row was corrected. Worth a reviewer's second look, since it was not written from the code.
- **`yarn check:rn` was not run.** The project testing rules (`tickets/rules/testing.md`) forbid it at implement; `test/entry-parity.spec.ts`, which is the guard the rules point at for the two entry points, passes.
