# Review: back-fill a verified commit proof onto an already-held revision

All three arms of the implement ticket landed. `yarn build`, `yarn typecheck`, and `yarn test` all
pass from the repo root (no failures anywhere in the workspace; db-p2p alone: 2211 passing,
44 pending).

## What changed

### Arm 1 — the back-fill (`storage-repo.ts`, `block-storage.ts`)

`StorageRepo.backFillProof` was generalized from `(blockId, storage, request, proof)` to
`(blockId, storage, rev, actionId, proof)`. Its two commit-path callers (the idempotent re-commit
partition and the Crash-D3 `recover()` partition) now pass `request.rev, request.actionId`; nothing
about their behaviour changed.

`StorageRepo.saveReplicatedBlock` gained a back-fill on its **non-advancing** branch. It fires only
when all four hold: the save did not advance `latest`, a `verifiedProof` was supplied, a `source`
was supplied, and `effective` matches `source` on **both** `rev` and `actionId`. It runs inside the
per-block commit latch the method already holds, and routes through the existing
`persistProofIfContentMatches` retention rule (persist only when the local materialization matches
the digest the commit op declared), which never throws.

The back-fill is deliberately **not** inside `BlockStorage.saveForwardRevision`'s monotonic guard.
The proof was verified against the *pushed* bytes; a back-fill attaches it to this node's *held*
materialization, and a diverged holder's bytes at the same `(rev, actionId)` may differ. Storing a
proof whose declared digest contradicts local content would make this node serve content that fails
its own proof — and `digest-mismatch` is **attributable** in `certified-claims.ts`, so every
receiver would penalize it. The digest check is what makes the back-fill safe, and it lives in
`StorageRepo`.

A held revision *newer* than the pushed one is never back-filled: `servableProof` only ever serves
the proof for `latest.rev`, so the proof would be keyed to a revision this node will never serve.

The stale `NOTE:` in `saveForwardRevision`'s monotonic guard was replaced with the corrected
explanation and a pointer at the `StorageRepo` site. `docs/internals.md` § "Persistence and
retention" was updated the same way (its "two landing paths that skip `internalCommit`" sentence is
now three, plus a new "Back-filling onto an already-held revision" paragraph).

### Arm 2 — the two flag-downgraded specs

- `cohort-growth-heals-single-holder.spec.ts`: `writeRevision` was upgraded to a **certified**
  commit (declares the block's `canonicalBlockHash` in `blockDigests`, builds a 4-peer
  `makeSignedProof`, passes it as `commit`'s third argument, and asserts the proof was retained).
  `requirePushCertificate: false` was **removed** from both receiving services — B and C now run the
  production default. This spec therefore drives the producer → wire → receiver certification chain
  end to end over real repos and the real length-prefixed frames.
- `block-transfer-roundtrip.spec.ts`: **decision — the migration flag stays**, and the reason is now
  written at `makeWiredNetwork`'s default rather than left implicit. That spec's subject is the
  stream path (handler registration, framing, response deadline); those tests must fail for a
  framing reason and nothing else, so they push a bare block with no certification to build. The
  strict posture is not skipped in that file — the two `certified push:` tests already pass `{}`
  explicitly and run the production default with a real signed proof over the real wire, plus an
  uncertified control that must be refused.

### Arm 3 — producer-side coverage

New file `packages/db-p2p/test/source-block-certification.spec.ts` calls `sourceBlockCertification`
directly and pins its four outcomes plus three fail-closed paths (8 tests).

## What the new tests actually claim

**`block-transfer-push-persist.spec.ts` → `describe('back-filling a proof onto an already-held
revision')`** — the positive path and the three cases that make the retention rule matter. Real
signed Ed25519 proofs throughout, driven through `handlePush`, not through `StorageRepo` directly:

- *back-fills the proof when a certified push names the revision already held* — land rev 4
  proof-lessly via the legacy service, assert `getBlockProof` is undefined, push the same
  `(rev, actionId)` certified, assert the proof is now retained and `latest` is unchanged. **This is
  the assertion that would have failed before this ticket.**
- *withholds the proof when the held bytes differ from the pushed bytes (diverged holder)* — the
  trap. Both sides claim rev 4 / a4; local content is `'held'`, pushed content is `'pushed'`. The
  push itself verifies and is accepted, but nothing is retained, and the held content is unchanged.
- *withholds the proof when the same revision is held under a different action* — agreement on `rev`
  alone is not enough.
- *does not back-fill for a revision older than the one held*.
- *leaves an existing proof alone (back-fill is strictly additive)* — two independently-signed proofs
  for the same commit; the first one retained wins.

**`source-block-certification.spec.ts`** — no `latest` (three shapes: no entry, unseen block,
`state` with no `latest`) → `{}`; a pinned read (`materializedRev !== latest.rev`) → `{}`; an
unpinned read sitting at `latest` → both halves; `latest` with no retained proof → meta only;
`latest` plus a matching proof → both halves; a **mis-paired** stored proof (written under rev 5 but
naming a different action) → meta only; a repo with no `getBlockProof` accessor → meta only; a
throwing `getBlockProof` → meta only, meta preserved.

**`block-storage.spec.ts`** — the old `'monotonic-skip: a certified re-heal of a held revision does
NOT backfill its proof'` test was retitled to `'monotonic-skip: a re-heal whose proof declares no
digest back-fills nothing'`. Its stand-in `{ v: 1 }` proof declares no digest, so it still passes —
but now for the *true* reason (`commit:proof-undeclared`), and its comment says so and points at
where the positive path lives. The suite's leading doc comment was corrected the same way.

## Known gaps and things worth an adversarial look

- **The back-fill is not covered on the `reconcile-block.ts` path.** The new coverage drives it
  through `BlockTransferService.handlePush`. The reconcile caller reaches the same
  `saveReplicatedBlock` seam with the same arguments, so it is the same code — but nobody asserted
  it there. Cheap to add if a reviewer wants belt-and-braces.
- **`source` undefined is treated as "do not back-fill".** The implement ticket specified comparing
  against the caller's `source`, and `saveReplica` fabricates `rev = 1` plus a content-hash
  `actionId` when `source` is absent — comparing against a fabricated identity would be meaningless.
  In practice a proof never arrives without meta (`handlePush` refuses that combination, and
  `sourceBlockCertification` never attaches a proof without meta), so the branch is unreachable from
  production today. It is untested; a reviewer may reasonably want that stated as an assertion
  rather than an argument.
- **`makeSignedProof` freshness assumption.** The "strictly additive" test depends on two calls to
  `certify` producing structurally different proofs. They do — `makeSignedProof` generates fresh
  Ed25519 key pairs per call — but the test does not assert `first` ≠ `second` up front, so if that
  fixture ever became deterministic the test would silently go vacuous.
- **The `cohort-growth` upgrade widens that spec's blast radius.** It now fails if *certification*
  breaks, not only if *growth/heal* breaks. That is the intended gain (it is the only test driving
  the whole producer → wire → receiver chain over real repos), but it means a certification
  regression will now light up a spec whose name says nothing about certification. Worth a
  reviewer's opinion on whether the tradeoff is stated clearly enough in that file's comments.
- **No test forces the "proof-persist fault must not fail the no-op" discipline** on the replica
  path. `persistProofIfContentMatches` swallows and logs, and that is pinned on the commit path, but
  nothing injects a `saveBlockProof` failure through `saveReplicatedBlock`'s non-advancing branch.

## Tripwires recorded

None. The one conditional concern in this area (proof bytes growing with N² for an N-block commit)
already has its `NOTE:` on `persistProofIfContentMatches` and was untouched.
