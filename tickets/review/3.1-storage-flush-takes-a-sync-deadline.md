# Storage flush takes a sync deadline — implemented, for review

Second of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). Storage now has a way to be told how long a flush's writes may stay unsynced (`FlushOptions.withinMs`) and a way to ask when deferred writes have reached the disk (`whenDurable()`). No production caller passes a window yet and no real backend defers yet, so every production path behaves exactly as before: every flush is strict, every commit syncs before it resolves.

## How this landed

The work arrived in two runs. The first agent run wrote the contract, the wrappers, the trivial implementations, the `BatchBackend` reshape, the `WriteGroup` rewrite, the `MemoryBatchBackend` power-loss double, and the file-store adaptation, then was killed on the runner's idle timeout; the runner committed that partial tree as `67ba29a0` ("tess: timed out … added resume note"), and the test doubles across packages were swept into the sibling review commit that followed. This run verified that tree compiles and passes, fixed one defect in the draft, added the tests, and wrote the docs. Review the whole feature, not just this run's diff: `git diff 67ba29a0~1 -- packages/` is the ticket's footprint (29 files).

## What changed

**Contract** (`store-durability.ts`, `i-raw-storage.ts`, `raw-store-driver.ts`). `FlushOptions { withinMs? }`; `flush(options?)` and a new required `whenDurable()` on both `IRawStorage` and `RawStoreDriver`. The five-rule flush contract on `RawStoreDriver.flush` now says: rule 2, a resolved flush means the write survives a process crash, and survives every crash `durability` names once `withinMs` has passed (at once for 0) or once a later `whenDurable()` resolves; rule 3 notes a deferred sync is exactly when a power cut takes a suffix; rule 4, a `withinMs` 0 flush hastens every earlier deferred write; rule 5, a failed deferred sync latches the store, is logged, and is reported by the next write, flush or `whenDurable()`.

**Trivial implementations and wrappers.** `MemoryStoreDriver`, `LevelDBStoreDriver`, `IndexedDBStoreDriver`, `SqliteStoreDriver` ignore `withinMs` and resolve `whenDurable()` at once. `KvRawStorage`, `CachedStoreDriver`, `CachedRawStorage`, `RawStorageDriverAdapter` forward both. Test doubles in `cache-test-helpers.ts`, `cached-raw-storage.spec.ts`, `mid-ddl-crash.spec.ts`, `storage-monitor.spec.ts` and the quereus lagging-replica spec gained `whenDurable`.

**Backend seam** (`batch-backend.ts`, `write-group.ts`). `WriteGroupSink<K>` is `{ commit(entries, { syncWithinMs }) → Promise<CommittedBatch>; sync() }`, with `CommittedBatch { durable: Promise<void> }`; `BatchBackend extends WriteGroupSink<StoreKey>`. Reads of a backend must reflect every batch whose `durable` resolved and may reflect a batch earlier.

**`WriteGroup`.** Takes a sink instead of a bare commit function. Each flush has a deadline and is strict (`withinMs` absent or 0) or relaxed. Flushes sharing one seal pool their deadlines; the batch commits with `syncWithinMs = max(0, earliest − now)`; relaxed waiters resolve on commit, strict ones on `durable`. A strict flush with nothing open and committed-but-not-durable batches calls `sink.sync()` once (shared by concurrent hasteners) and resolves on the latest batch's `durable`. Overlay entries drop when their batch's `durable` resolves (sequence rule unchanged). New `maxUnsyncedBytes` (default 64 MiB) forces `syncWithinMs` 0 when a seal would leave more than that not yet durable. A rejecting `durable` latches the group exactly as a rejected commit does, logs once on `optimystic:db-p2p:write-group:error`, and rejects every pending strict waiter and `whenDurable()`. `whenDurable()` is the latest committed batch's `durable`, resolved at once when none is pending, rejected after a fault. Idle flush and `close()` stay strict.

**`WriteGroupDriver`** forwards `flush(options)` and `whenDurable()`. **`FileKVStore`** exposes `whenDurable()` too (it is not an `IRawStorage`; added so the next ticket can order across stores).

**`FileBatchBackend` and `FileKVStore`** adapt to the new shapes without deferring: commit still syncs through `FileWriteLog.commit` and returns `SYNCED_BATCH` (`{ durable: Promise.resolve() }`, in `file-write-log.ts`); `sync()` resolves at once. Deferring is `file-store-syncs-by-the-earliest-deadline`.

**`MemoryBatchBackend`** (the `./testing` entry). New `deferSync` option (default false, existing tests unchanged): a commit with `syncWithinMs` above 0 stays not durable until `sync()` or a later `syncWithinMs` 0 commit; the deadline itself is ignored. New `beforeDurable` hook to fail the sync that would make a batch durable. New `powerLoss()` rebuilds the maps from the durable prefix of `committed` alone; the dropped batches' `durable` promises never settle. `committed[i].syncWithinMs` and `.durable` are readable by tests. `syncs` counts hastens. This is the power-loss double `nodes-apply-the-durability-window` reuses.

**Docs.** Invariant 6 of `packages/db-p2p/docs/storage.md`: intro paragraph (three required members, strict vs relaxed, `whenDurable`), the five rules, a `withinMs` column in the driver table (only `WriteGroupDriver` honours it, only as far as its backend defers, none yet), the wrappers paragraph, and the *Writes that wait in memory* paragraph (two settle points, deadline pooling, overlay held until durable, byte bound, durable-failure latch and log, the test double). The theorem, window table and policy prose are left to `durability-docs-match-the-window`.

## Fixed in this run

The committed draft's `sealAndCommit` left the commit promise's rejection unobserved whenever every flush sharing the seal was strict (strict waiters await `durable`, which the rejection also reaches, so nothing held `committed`). Node reports that as an unhandled rejection. Now `committed.catch(noop)` marks it observed; waiters still receive it through their own settle point. `MemoryBatchBackend.sync` was also made `async` so a latched backend rejects rather than throws synchronously into `WriteGroup.syncOnce`.

## Tests added

All in `packages/db-p2p/test/write-group-driver.spec.ts`, over `MemoryBatchBackend({ deferSync: true })`:

- **A relaxed flush resolves before its batch is durable while reads still serve it, a strict one does not, and a power cut takes back the suffix.** Pins rule 2's two levels and the overlay holding a write past its commit.
- **A strict flush with nothing open hastens the deferred batches with one sync and no commit, after which they survive a power cut.** Pins the hasten path: `sink.sync()` exactly once, no re-commit, `whenDurable()` resolved.
- **A durable promise that rejects latches the store.** `whenDurable()` rejects; the next write and flush throw `StoreFailedError` carrying the cause; the overlay keeps serving.
- **The byte bound forces a strict commit.** `maxUnsyncedBytes: 8`; a second relaxed flush commits with `syncWithinMs` 0 and syncs the earlier deferred batch too.
- **A strict and a relaxed flush sharing one seal** commit it with `syncWithinMs` 0 and both resolve. See the gap below on what this does not assert.
- **`close` syncs the batches whose flushes allowed a deferred sync before closing the backend.** Added because the conformance registration cannot prove it (below).
- **Conformance suite registered a second time** as `WriteGroupDriver over memory (deferred sync)`, persistent.

## Known gaps and things for the reviewer

- **The deferred-sync conformance registration proves less than the ticket says.** The conformance suite only ever calls `flush()` with no options, so every commit it makes has `syncWithinMs` 0 and is synced inline; its reopen case therefore does not exercise `close` syncing a *deferred* batch. The explicit `close syncs the batches…` test above is what pins that. The registration still runs the whole suite over the deferring double, which is worth keeping, but a reviewer should not read it as covering the relaxed path.
- **The shared-seal test asserts a weaker property than the ticket's wording.** The ticket says "the relaxed waiter may resolve before the strict one". Over this double a strict commit awaits its sync inside `commit`, so the two settle points coincide and the ordering is one microtask apart; the test asserts the commit count, the forced `syncWithinMs` 0, that both waiters resolve and that the earlier deferred batch was synced by the shared seal, not the order. The distinct settle points are pinned by the first test instead (relaxed resolved, `whenDurable()` pending).
- **A one-microtask window where a hasten syncs nothing.** `runCommit` pushes the `notYetDurable` record before the already-resolved `durable`'s continuation drops it, so a strict flush with nothing open arriving inside that single microtask calls `sink.sync()` on a backend with nothing to sync. Harmless and unreachable from any awaiting caller; noted, not fixed.
- **`flush()` throws synchronously** (a `RangeError`) on a non-finite or negative `withinMs`, matching how the constructor validates `idleFlushMs` and `maxUnsyncedBytes`; every other failure path rejects. `maxUnsyncedBytes` accepts `Infinity` (no bound), which the ticket's "validate like `idleFlushMs`" neither asks for nor forbids.
- **Checked by inspection, as the ticket asked:** every `WriteGroupDriver` listing merge deduplicates a record present in both overlay and backend (`rangeRevisions` keys a `Map` by rev, `listPendingActionIds` a `Set`, `mergedBlockIds` a `seen` set); `promote` reads overlay-first; `whenDurable()` with nothing committed resolves at once and rejects after a fault; a backend `durable` rejecting with its own `StoreFailedError` is unwrapped to its `cause` in `WriteGroup.latch`.
- **No production path exercises a relaxed flush.** Every caller passes no options; `FileBatchBackend` treats the window as 0. The next two tickets are where a real deadline first matters.
- The conformance suite's `NOTE:` about the planned power-loss double (`raw-storage-conformance.ts`, flush case) now points at the double that exists.
