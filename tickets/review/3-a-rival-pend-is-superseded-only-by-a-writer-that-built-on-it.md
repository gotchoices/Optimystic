# A rival pend is superseded only by a writer that built on it — review

Third of the three tickets split from `bug-a-pended-transform-does-not-carry-its-base` (the second, which put the base on the pend and in storage, is complete). This one reads that base in the rival rule and at the commit vote.

The lost update it closes was reproduced before the fix, on a four-machine in-process mesh (the negative control below): with the base comparison removed, a writer that read a block one change short was acknowledged over the stale copy, and the earlier writer's data-block commit was then refused as stale — its log entry stored, its change on no machine.

## What was built

**The rule** (`packages/db-p2p/src/storage/pending-claim.ts`). `isReservationAgainst(claim, request: ReservationRequest)`, where `ReservationRequest = { rev?, baseRev? }`:

- either side's revision unknown → reserves (unchanged);
- a usable base (`usableBase`: a number strictly below `rev`) → reserves iff `claim.rev > baseRev`;
- otherwise (no base, or a malformed one) → the old rule, reserves iff `claim.rev >= rev`.

`reservationRequestFor(pend, blockId, transform)` is the one reading of an incoming pend both scan sites use. It takes the base through `declaredBaseFor` (so an inserted or deleted block, or a non-number entry, gives no base, exactly as storage keeps it). It also returns `ignoredBase` for a base the rule does not read, so the caller can log it. `isBaseIndependent` and `declaredBaseFor` moved here from `storage-repo.ts` unchanged, because the rival rule now shares them with storage.

**Scan sites.** `StorageRepo.pend` (apply) and `ClusterMember.reservingRivals` (promise vote) both feed `reservationRequestFor(...)` to the rule, log `pend:base-ignored` / `cluster-member:pend-base-ignored` for a malformed base, and never refuse on one. The superseded log lines now carry the base.

**`corroborateHeldBlocks` takes the base.** It uses the same inputs as the member that refused, so it names the same rivals. With the revision rule alone, a `held` cast because of the base (a record past the declared base, below the requested revision) would never be corroborated. It stays diagnostic only; a comment at the method says so.

**Commit vote.** New `ClusterMember.validateCommitBaseDeclarations`, run in `evaluatePromise` just before the digest check (`validateCommitOperations`; the ticket called it `validateCommitDigests`). For each declared block with a numeric `blockDigests[id].baseRev`, it reads this member's record for the action. If the record's stored base differs, it votes reject with the new exported reason `BASE_DECLARATION_DISAGREES = 'base-declaration-disagrees'`, logged as `cluster-member:base-declaration-disagrees`. It abstains when there are no declarations, on a surplus entry, on a non-number `baseRev`, when there is no record or the record has no base, and on a read fault. It needs no preview: `IPendingClaimReader` gained `pendingClaimOf(blockId, actionId)` (implemented on `StorageRepo`), and each method is probed separately. It runs before the digest check so the reason names the cause rather than the digest mismatch it causes.

**Four-member mesh spec, built** (`packages/db-p2p/test/rival-superseded-only-by-a-writer-that-built-on-it.spec.ts`). The harness change is one option on `transactorDrivenBy`, `wrapRepo`, which wraps each coordinator repo on the writer's side. The spec uses it to hold R's data-block commit (the second `commit` call, the one without the tail). `mesh.failures.onClusterDelivery` throwing makes every delivery of R's pend to D fail. Phases: seed; R pends without D, its tail commits everywhere (D reconciles it) and its data commit is held; N, a fresh handle driven by D, writes and is **held** while R's records still stand on A, B and C; R is released and its row reads on every machine; N is retried by the application and both rows read on every machine.

**Docs.** `docs/correctness.md`: §2 "Pend refusal reporting"; Theorem 1 Case 2, where the four-member shape is closed at the rival's own pend, stated only under the condition that holds (the members still holding the record must be enough to deny the rival a super-majority, which they are in the shape as it arises); Theorem 9, which now puts the rule on the declared base, makes read-side promotion the second line, and adds a paragraph on the liveness cost. `docs/repository.md`: the section is renamed "A pending record claims a slot, and reserves the block until a writer builds on it" (its one cross-reference, in `packages/db-p2p/docs/storage.md`, is updated), the bullets are rewritten, and a paragraph on the commit vote is added. `docs/internals.md`: the held-vote bullet, plus a paragraph in "Commit content-digest check" on the base-declaration check. Doc comments were updated at `operationsConflict`, the `validatePendOperations` rival branch, `BlockMetadata.pendingRevs`, `StuckReservationTracker`, `IBlockStorage.listPendingClaims` and `IPendingClaimReader`. No code or doc still points at `bug-a-pended-transform-does-not-carry-its-base` or at this ticket as the owner of open work (grep `carry-its-base\|superseded-only-by` over `packages/*/src`, `packages/*/docs`, `docs` finds only the new spec's filename).

## Findings the reviewer should weigh (not fixed here)

1. **The newcomer is held, then refused rather than landing.** This was measured, and it contradicts the ticket's liveness argument. In the four-machine spec, N reads the data block once through D and never re-reads it. It is held while R's records stand. Once R commits, it re-pends on the same stale base; that pend is admitted (R's record was promoted), and the fork guard refuses its data-block commit on all four members. The trace shows nine pends, all with base 1: the first held, eight admitted and refused at commit. N's write ends in `TornActionError`, with its log entry stored and its change on no machine. That is safe (never acknowledged over R), but the write doesn't succeed on its own. The rule change turns a silent lost update into this. The root cause is on the client: after a held refusal the handle gets no signal that its copy is stale, and the coordinator's `pend-held-uncorroborated` answer drops `heldBy`. Filed as `backlog/bug-a-writer-held-by-a-change-it-never-saw-retries-on-its-stale-copy` (repro verified). Spec phase 4 pins the safety half: R's row is everywhere, and N is either saved with both rows or refused and absent. Phase 5 shows the application's retry landing.
2. **A record whose change no member will ever take now holds the block forever.** This is reasoned from the code, not measured. There are two cases: an abandoned action whose data-block pend landed, whose log-tail pend didn't, and whose cancel never arrived, on a block no later write touches; or a base-less record (from an older sender) whose data commit never ran anywhere. The old rule superseded both once the collection moved past the slot. Now every newcomer's base is below the claim. The member can't tell these apart from the lost-update shape, so the cure is a sweep, not a looser rule. This is recorded in the `NOTE:` at `isReservationAgainst` and as a new dated section in `backlog/debt-unpromotable-pending-records-need-a-sweep`.
3. **The vote-time reject can sink an honest retry's commit at three members.** This is reasoned, not measured. Suppose a member holds a stale record from an earlier attempt of a retried action because it missed the retry's pend. It rejects the retry's commit, and at three members one reject fails the commit record. The apply-time refusal alone would have let the other two commit and this member reconcile. When the member's latest equals the declared base, the existing digest check usually rejects the same shape already, so this widens it mainly to a member that is behind. It heals through the writer's cancel or torn-entry re-send. The ticket asked for this reject, and I implemented it as specified; the `NOTE:` at `validateCommitBaseDeclarations` names the condition and the fallback (abstain when the member's latest is not the declared base). The reviewer should decide whether to keep it as is.
4. **The Case 2 closure is conditional.** If a pend reaches the promise super-majority but is *applied* on too few members to deny a rival a super-majority, a rival built on the stale copy can still land on the members that have neither the record nor the change. I did not check whether pend execution can land that narrowly. `correctness.md` Case 2 states the condition, and the rule's doc comment says the same.

## Use cases pinned by tests

- The rule table with and without a base; a base-less rival record judged by the newcomer's base; six malformed bases (equal to rev, past rev, string, null, NaN, object) falling back; a rev-less request with a base; and a generated check that across every claim, rev and honest base the base arm never admits what the revision arm holds, and does hold more somewhere. `pending-claim.spec.ts`.
- `reservationRequestFor`: an update-only block carries its base; no base, or another block's base, gives none; a base on an insert or delete is dropped and reported; a string or not-below-rev base is reported. `pending-claim.spec.ts`.
- Storage, with the block at 4 and a rival record at 5: a pend at 6 with base 4 is refused as held and writes no record; base 5 is admitted; no base is admitted (old rule pinned); malformed bases are admitted and never refused; a pend for the record's own slot is still held whatever its base. `storage-repo.spec.ts` "a rival record is superseded only by a pend that built on it".
