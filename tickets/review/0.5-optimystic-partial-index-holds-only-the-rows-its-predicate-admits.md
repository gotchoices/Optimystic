# A partial index holds only the rows its predicate admits — review

Suggestion 3 of GitHub [#42](https://github.com/gotchoices/Optimystic/issues/42). Before this change every maintained index tree got an entry for every row, ignoring the persisted `where` clause of `create index … where …`.

## What changed

**One rule for "what a partial index admits".** `IndexPredicate` (new, `src/schema/index-predicate.ts`) wraps Quereus's own `compilePredicate`. `admits(row)` is true only for SQL TRUE; FALSE and NULL exclude. `repositioned(reposition)` remaps the compiled column positions after a catalog-only DROP COLUMN instead of recompiling (the manager's `schema.columns` keeps its old numbering there). `storedToColumnSchema` was lifted from a `SchemaManager` method to a module-level export in `schema-manager.ts` so the predicate can build `ColumnSchema`s without a manager; its two callers were updated.

**IndexManager** compiles a predicate per partial index in its constructor and in `setSchema` (against that schema's own column list), remaps them in `repositionColumns`, drops one in `unregisterIndex`, and exposes `admits(index, row)`. A predicate that does not compile throws a plain `Error` naming table and index, with the `QuereusError` as `cause` — this surfaces out of `doInitialize`.
- `insertIndexEntries` / `deleteIndexEntries` skip an index that does not admit the row (covers plain DELETE, REPLACE eviction, and the displaced row of a PK move).
- `updateIndexEntries` was restructured: the old entry's delete is staged when the old row is admitted, the new entry's guarded insert when the new row is admitted, in one action, delete first; nothing when the two tree keys are equal (including both absent). That one shape covers the ticket's four-case table.

**Vtab (`optimystic-module.ts`)**
- `addIndex` compiles the predicate right after the fresh catalog read, before the adoption guard, the unique-constraint mirror and any write. Quereus does not compile it for non-memory modules at CREATE INDEX (checked `SchemaManager.createIndex` in Quereus), so this is the plugin's own guard. Verified ad hoc: `create index Bad on T (C) where length(C) > 1` fails with `createIndex failed … Unsupported expression in partial-index predicate: function`, leaves no index in the engine catalog and none in `verifyIndexes`, and later inserts work.
- `backfillIndexTrees` skips rows a target does not admit; `stagedAny` became a per-target `Set` of names that received entries.
- `getBestAccessPlan` skips any index with a predicate. The private `enforcesUniqueness` helper became unreachable for its predicate arm and was inlined as `index.unique ?? false`.
- `resolveEnforcingIndex` and `buildUniqueEnforcementIndexes` filter declared indexes through a new `holdsEveryRow` helper, so a partial declared index never enforces a full UNIQUE and never suppresses a `_uniq_` tree. `reassignUniqueEnforcement` goes through `buildUniqueEnforcementIndexes`, so it is covered too.
- `verifyIndexes` passes `admits` to `compareIndexToRows`.

**Integrity check (`index-integrity.ts`)**: expected entries come only from admitted rows; an entry whose own row implies it but is not admitted is a new orphan reason, `outside-predicate` (exported via the existing `OrphanReason` type). The old "predicate ignored" NOTEs are gone here and in backfill.

**Outside the listed files — please judge.** The ticket asked to confirm by inspection that every commit route skips a dirty tree with nothing staged. Findings: the session coordinator (`stagedCollections`), the offline route (`queueableSet` over `isStaged` trees) and the batched legacy commit (`legacyBatch`) all skip it. The per-tree legacy sweep (`sweepDirtyTreesLegacy` in `txn-bridge.ts`) did not commit an empty entry but did call `tree.sync()`, which is `updateAndSync` — one refresh per unstaged tree. That matters here: an insert outside every partial predicate stages only the main tree, so it now takes the sweep instead of the batch, and would have paid a refresh for each untouched index tree. The sweep now skips a tree with `isStaged(tree) === false`. A skipped tree is treated as unsynced on a later failure, so it is restored to its pre-transaction snapshot (a no-op for a tree with nothing staged) and named among the unpersisted trees of a `PartialCommitError`, exactly like trees after the failure point already were. This also removes a refresh per untouched index for UPDATEs that change no indexed column, which already took the sweep before this ticket.

**Docs**: `docs/debugging.md` — `outside-predicate` added to the reason table, with the leftover-entries explanation; the old "checked as if it had no `where` clause" bullet removed; `rowCount`/`entryCount` and `missing` bullets mention partial indexes. README Limitations has a new bullet on partial indexes.

## Tests

- `test/partial-index-maintenance.spec.ts` (new, `local` transactor, reads trees via `readIndexIntegrity`):
  - *stages an entry only for the rows the predicate admits, through insert, update and delete* — table `T (Id, C text null, Flag integer null)`, index `ByFlagged on T (C) where Flag = 1`. Rows `(1,'a',1)`, `(2,'b',0)`, `(3,null,1)`, `(4,'d',null)` → `entryCount` 2, clean (covers FALSE and NULL predicate results, and a NULL indexed value inside the predicate). Then in→out (`Id 1`), out→in (`Id 2`), and an update of a row that stays outside (`Id 4`) → 2, clean. Delete row 2 → 1, clean. This is the reproduction: before, `entryCount` was 4 after the inserts.
  - *backfills only the rows the predicate admits* — rows first, then `create index` → `entryCount` 2, clean.
  - *answers an equality on the indexed column with rows outside the predicate too* — `select Id from T where C = 'b'` with `Flag = 0` returns row 2. Fails if the planner exclusion is missed.
- `test/index-integrity-check.spec.ts`: added *reports an entry for a row outside a partial index's predicate as an outside-predicate orphan* — plants the entry an older build would have written and asserts the new reason (not in the ticket's list; added because it is the only pin on the new classification branch).
- `test/access-plan-estimates.spec.ts`: the case that pinned the old behaviour (partial unique index planned but not as one row) now asserts a partial index is never planned (`indexName` undefined, no handled filters).
- `test/query-helpers.ts`: `describeOrphan` renders the row for `outside-predicate` in failure messages.

Validation run: `yarn build`; full `yarn workspace @optimystic/quereus-plugin-optimystic test` — 1179 passing, 14 pending, 0 failing (before the final integrity-check case was added; that spec was re-run alone afterwards: 24 passing); `yarn typecheck`, `yarn lint`, `yarn lint:docs` clean. The existing `secondary-unique-hydrate.spec.ts` case (partial unique index declared before a full one over the same column, duplicate with `Flag = 0` refused) passes unchanged, which covers the enforcement arm. The integration suite (`yarn test:integration`) was not run.

## Covered by inspection only — worth a reviewer's eye

- **PK-move updates** (old and new primary keys differ) take the same `updateIndexEntries` branch with different keys; no dedicated test.
- **Catalog-only DROP COLUMN of a column the predicate does not name**: `IndexPredicate.repositioned` and the `positions` map are untested. Quereus refuses dropping a column a partial predicate names (`predicateReferencesColumn` in `@quereus/quereus/src/runtime/emit/alter-table.ts`), so `reposition` should never throw for a referenced position. The plugin's own `columnDropBlockers` does not check predicates — a record holding a partial index another machine added, naming the column, would make `repositionColumns` throw mid-edit.
- **`setSchema` recompiles every predicate** against the passed schema's column list. Called by reconcile with a schema from the catalog record; index column positions come from that same list, so the two agree. A record column list that disagrees with this engine's (backlog `bug-optimystic-stale-hydrated-table-rewrites-the-shared-catalog-record`) mis-positions the predicate the same way it already mis-positions index columns.
- **Conflict replay**: the admit decision is a pure function of the row the statement saw, like the index key itself, so it adds no new staleness.
- **Two-node / mesh**: not exercised. A sibling on an older build keeps writing entries for excluded rows; `verifyIndexes` reports them as `outside-predicate`.

## Known consequences (accepted by the ticket)

- A query that used to seek a partial index now does a full scan (backlog `feat-optimystic-plan-through-a-partial-index-whose-predicate-the-query-implies`).
- Entries older builds wrote for excluded rows are not removed, and deleting such a row leaves its entry (the delete stages nothing for an excluded row). Documented at `deleteIndexEntries` and in docs/debugging.md.
- A table that enforced a full UNIQUE through a partial declared tree gets a `_uniq_` tree at its next initialization, filled by `ensureUniquePopulated` on first probe.
- Partial UNIQUE enforcement is still out of scope (backlog `bug-optimystic-unique-ignores-collation-and-partial-predicate`); `IndexManager.admits` is the evaluator that ticket needs.
