# An oversized transaction is refused as an oversized block — review handoff

GitHub #61. One SQL transaction of more than about 7 MiB of 1 KiB rows was refused with `BlockTooLargeError` naming its log block, because the per-block check runs at staging and the per-transaction check only in the pend. And nothing checked size until the whole transaction had been staged (the reporter's 56k-row transaction spent 4.4 minutes and 3.3 GB first).

## What changed

**The transaction is judged before the block.** `oversizedWriteRefusal` in `packages/db-core/src/network/block-size.ts` is the one rule both staging sites call (`stageAttempt`, which serves `syncAttempts`, `commitHead` and the coordinator's per-entry commit; and `TransactionCoordinator.declareTouchedBlocks`). When `oversizedBlock` finds a block over `MAX_BLOCK_BYTES`, it measures the collection's transforms (after the log append) and, if those are over `MAX_TRANSACTION_BYTES`, returns `TransactionTooLargeError` with the action id instead. The transforms are serialized only on that refusal path. `declareTouchedBlocks` now takes the action id as its first argument (from `context.actionId` in `coordinateTransaction`).

**Refusal while staging.** Each open-segment unit now carries `bytes` (`StagedUnit.bytes`, `jsonEncodedBytes(action)`, measured once). `SegmentList` keeps a running total (`openBytes()`): `setOpen` recomputes it by summing units, `pushOpen` adds; `seal` and `unseal` now go through `setOpen`. `Collection.actInternal` measures the incoming actions and calls `assertStagedActionsFit(openBytes + incoming)` before staging, so a refused `act` stages nothing (it throws before `actAndSync`'s try/unstage). The refusal is `TransactionTooLargeError` with `actionId: undefined`. Replays don't go through `actInternal`; `replayActions` and `filterAgainstEntry` keep each kept unit's `bytes` rather than re-serializing, and a filter replacement is measured via `unitOf`.

**`TransactionTooLargeError`.** `actionId` is now `ActionId | undefined`. `bytes` is documented as a lower bound ("at least") except when the pend itself was measured. The message now reads "… encodes to at least N bytes …", with "the transaction staged so far" as the subject when there's no action id.

**SQL surface, checked, unchanged.** A throwaway plugin spec (deleted) inserted 1 KiB rows into one transaction over the `test` transactor. The 6,895th insert failed with `Error: insert failed: the transaction staged so far encodes to at least 7865006 bytes, …`, with `cause` the `TransactionTooLargeError` (the vtab DML catch's `rewrapAsQueryError`). It is readable and reachable, so I left it alone.

**Docs.** In docs/internals.md §A transaction's size limit:
- the measured ratio and the 3.4 MiB figure;
- the BLOB note (GitHub #63);
- the three places the refusal fires, under "What the writer gets";
- a new "The transaction is judged first" bullet;
- updates to "Where", "When it fires" and the `MAX_BLOCK_BYTES` bullet.

The `MAX_BLOCK_BYTES` and `BlockTooLargeError` doc comments are updated too. `yarn lint:docs` is clean.

## Tests (all in `packages/db-core/test/writer-refuses-oversized-block.spec.ts`)

- *Collection.sync refuses a block grown past the limit by one write as a transaction too large to send*: an insert plus a `grow` of `MAX_BLOCK_BYTES + 1000` characters in one `actAndSync` gives `TransactionTooLargeError` with an action id, and no pend reaches the transactor. This is the reproduction. I confirmed it fails (`BlockTooLargeError`) with the rule short-circuited.
- *TransactionCoordinator.commit refuses …*: the same transaction through `TransactionCoordinator.commit`. Also a confirmed reproduction.
- *Collection.act refuses an action that takes the staged actions past the limit, staging nothing, and counts from what a rollback restored*: two `grow` actions carrying 0.6 × the limit of text each. The second `act` is refused with `actionId` undefined. The pending actions and the block are unchanged. After `restorePending` of a snapshot taken before the first grow, one grow fits again and a second is refused.
- The existing two-write growth cases still give `BlockTooLargeError`; together with the above they pin the ordering.
- Mechanical updates only: `collection-segments.spec.ts` (`pushOpen` takes sizes; `setOpen` uses `unitsOf`) and `coordinator.spec.ts` (`declareTouchedBlocks` takes the action id).

## Validation

- `yarn test` in db-core: 2063 passing.
- `yarn test` in quereus-plugin-optimystic (after rebuilding db-core): 1381 passing, 14 pending.
- `tsc --noEmit` clean for db-core and db-p2p; eslint clean on the changed files.
- Not run: db-p2p's full suite and the integration tier. db-p2p only calls `assertTransactionFits`, whose behaviour is unchanged apart from the message wording, and nothing there matches the old wording.

**Cost.** One extra `JSON.stringify` + UTF-8 encode per staged action. Micro-benchmark over `dist`: 5,000 small replace actions took 4–6 ms; 5,000 actions with 1 KiB rows took about 12 ms. Staging the same 5,000 small rows through SQL took about 1.4–1.5 s (medians 1,417 ms without the check and 1,500 ms with it, but run-to-run noise on this machine was larger than that gap). That is under 1% of staging, so no `NOTE:` was recorded.

## Known gaps / for the reviewer

- **The staging refusal fires late, by design.** It fires at about twice the row volume the commit admits: 1 KiB rows were refused at about 6.7 MiB staged, while the commit takes about 3.4 MiB. Transactions between the two still stage fully and are refused at the pend (or at `oversizedWriteRefusal` once their log block passes 7.5 MiB). The ticket asked for exactly this bound; the docs say so. Carrying row data once is plan ticket `a-large-write-costs-time-and-space-per-byte`.
- **Engine-driven path untested.** `TransactionCoordinator.applyActions` calls `collection.act` per action, so a staging refusal there throws out of `applyActions`. There is no test of that throw; the vtab/`Tree.stage` path was checked by hand (above).
- **Per collection only.** A multi-collection transaction (table + indexes) is judged one collection at a time while staging. The sum across collections is still judged at the pend.
- **The remaining edge.** Transforms can be under the limit while a block and the full pend are over it. That needs a pre-existing oversized base and is refused as `BlockTooLargeError`; it is recorded as a `NOTE:` on `oversizedWriteRefusal`.
- **Wording.** The `TransactionTooLargeError` message now says "at least" even when the pend was measured exactly (true, slightly less precise). Nothing in the tree matches the old text.
