# Review: blob pins reconcile after a restart

Second of three parts finishing the SQL side of blobs. `feat-queued-blob-pins-settle-with-their-transaction` landed before it; `feat-sql-columns-hold-blob-references` follows and consumes two things this part establishes (`isLive`, and the per-backend `listPins` walk).

## What was built

`SqlBlobPins.reconcile()` settles every transaction pin whose transaction is not live, from committed state: the reference tree the pin's own label names either lists the reference or it does not. Listed → confirm the scope in the network's registry, announce, unpin. Certainly not listed → unpin, no announcement. Uncertain → keep every pin of that scope, log `blob:reconcile-uncertain`, retry on the next trigger. `put` pins of settled transactions are released outright. Nothing is read from the offline journal.

Supporting pieces:

- `OfflineRestore.holds(id)` (deferred or discarding) and `OfflineRestore.hasCompletedPass()` (set at the end of `pass()`, so a pass that threw leaves it false).
- `OfflineMode.holdsTransaction(id)` and `OfflineMode.reconcileReady()`, so `SqlBlobPins` interprets no queue statuses.
- `SqlBlobPinsDeps.isLive` / `.reconcileReady`, wired in `register`; `isLive` is the bridge's ACTIVE transaction (`getCurrentTransaction()`, `isActive === true`) or `offline.holdsTransaction`.
- `SqlBlobPins.backendResolved`, subscribed through `CollectionFactory.onBlobBackendResolved` in `register`.
- `mayHoldStalePins`: one boolean that makes `reconcile()` free unless something is actually owed. `reconcile` coalesces like `OfflineRestore.run` (a request before a chained pass starts joins it; one during a running pass is chained behind it).
- Triggers: `OfflineMode.restore()` **awaits** it; `onGateChange` fires it (bare `void`); `backendResolved` fires it. `plugin.hydrate` resolves the default network's blob backend after `restore()` and then awaits `blobPins.settled()`.
- `settleQueuedReference`'s announce-and-release tail is now the shared `releaseLanded`, used by both the queued settle and the reconciliation — identical log lines, one code path.

## Use cases to exercise

- **Crash after the commit landed, before the release.** Pin left under a dead transaction id; the scope's tree lists the reference → announced and released on the next `hydrate`.
- **Crash after pinning, before the send.** The tree certainly does not list it → released, nothing announced.
- **Cohort unreachable at reconcile time.** The committed read answers uncertain → every pin of that scope kept, flag stays set, next `restore()` or reachability wake releases them.
- **A journaled entry the restore has not read yet.** `reconcileReady()` false → the pass is a no-op. This is the one ordering where getting it wrong loses an application's bytes.
- **A journaled entry the restore deferred** (table missing or unreadable). `OfflineRestore.holds` → `isLive` true → its pins are skipped even though `reconcileReady()` is now true.
- **A queued entry put back by the restore.** `queue.status(id) !== undefined` → skipped until it settles; the previous part's `settleQueued` handles it.
- **No journal configured.** `reconcileReady()` true from the start; a queued transaction did not survive the restart, so its pins are correctly unlisted and released on the first pass.
- **Steady state cost.** After one clean pass, every reachability wake costs nothing: no `listPins`, no committed read. Worth confirming by inspection of the flag's setters.

## Tests added

`packages/quereus-plugin-optimystic/test/blob-pins-reconcile.spec.ts` — three cases, one per arm of the committed read, each writing the pin directly on the blob store under a dead transaction id (which is exactly the state a crashed process leaves) and restarting into a fresh plugin:

| Test | What it pins down |
|---|---|
| `announces and releases a leftover pin whose reference the table's tree lists` | listed + certain → the pin goes and the reference stays announced |
| `releases a leftover pin whose reference the tree does not list, announcing nothing` | not listed + certain → the pin goes, `stat().durability` stays undefined (so a wrong announce cannot pass as a release), and the application's own `unstaged` pin is left alone |
| `keeps a leftover pin whose reference tree cannot be read with confidence, and releases it on the next trigger` | uncertain → the pin is STILL there after `hydrate`; disarm the isolation, `restore()` again, and it is announced and released. Also the end-to-end proof that keep-and-retry works |

No other tests added. The registered-scope arms (`ensure` vs the check-only `isRegistered`, and the certainly-dropped scope) and the stray-`put`-pin arm are branches of the same pass over the same mechanism, and `reconcileReady`/`isLive` are inspection — flagged under *Gaps* below.

## A bug this ticket had to fix to work at all — please weigh the fix level

The first run of the new spec failed in a way that was not the reconciliation's fault, and the root cause is a pre-existing latent defect this ticket makes reachable on **every** `hydrate`:

`CollectionFactory.getOrCreateTransactor` remembers the FIRST options it sees per transactor key (`transactorOptions`), and `knownBlobBackends()` builds that network's BLOB store from that record. `OptimysticModule.createSchemaManager`'s schema-catalog options were assembled field by field and dropped `blobStorageFactory`. In a restarted process the catalog read is the first thing to name the key, so the reconciliation's `knownBlobBackends()` then built the network's blob store over **fresh in-memory stores** — the process read none of its own pins, and `plugin.blobs` was handed that same wrong store for the rest of its life (so `stat`, `pinsOf` and `listPins` all answered as if the machine held nothing).

Before this ticket the hole was dodged by accident: `knownBlobBackends()` was only reached from `settleQueued`'s rare listing path, by which time `plugin.blobs` had usually already resolved the backend from complete options.

What was done: `schemaOptions` now spreads `tableOptions` and overrides what differs, which is the pattern `openIndexTree` already uses; a `NOTE:`-free but explicit paragraph was added to `CollectionFactory.transactorOptions` stating what callers owe these options and why a hand-assembled options object is how a field gets dropped silently. The test harness's own `bindingOptions` had the identical gap and was fixed the same way.

**For the reviewer to judge:** that is a point fix plus a doc contract. The class is "any hand-built `ParsedOptimysticOptions` recorded as the first options for a transactor key corrupts that network's blob store, silently and permanently". A merge-on-record upgrade in `getOrCreateTransactor` was considered and rejected — it does not fix this case, because the reduced options are recorded first *and* the blob store is resolved before any fuller options arrive. A representation change (hold a transactor key's storage configuration separately from any collection's options, so there is nothing to drop) would make the class unrepresentable and is a `debt-` candidate if the reviewer thinks the contract paragraph is not enough.

## Gaps and departures, honestly

- **`OfflineMode.restore()` now throws while a transaction is open in EVERY configuration**, journal or none. It previously returned silently with no journal. Deliberate: the reconciliation it awaits waits for the open transaction to end, so awaiting `restore()` from inside a transaction would deadlock. The documented `@throws` was already written as unconditional; the existing `restore refuses to run while a transaction is open` test still passes. A no-journal host that called `restore()` inside a transaction and relied on the no-op now gets an error.
- **`mayHoldStalePins` is cleared at the START of a pass**, not at the end on success as the implement ticket worded it. Reason in the field's doc: a backend that resolves while a pass runs — including one the pass's own `knownBackends()` resolved — then leaves the flag set, so the next trigger looks again instead of the pass having to reason about what appeared behind it. Cost: the first trigger in a process runs one extra, empty pass (`backendResolved` during the pass coalesces into exactly one). The alternative (clear at the end) has a real hole: a backend resolving from an unrelated path after `knownBackends()` returned but before the pass ends would be cleared away.
- **The `listed` test's `durability === 'local'` assertion is weak.** The row was committed normally first, so the original commit had already announced the reference; the assertion says the reconciliation did not undo that, not that it announced. The `not listed` test (asserting `durability` stays undefined) is what makes a wrong announce fail. There is a comment saying so at the site. If the reviewer wants a strong positive, it needs a way to have a listed reference with no recorded durability, which this harness has no handle for.
- **`backendResolved(_backend)` ignores its argument.** A pass walks every known backend, so the one that just resolved is in the walk by definition. Kept in the signature because it is the `onBlobBackendResolved` listener shape.
- **Not covered by a test**: the `ensure`-vs-`isRegistered` split inside `releaseLanded` when reached from the reconciliation (it is the same method the queued settle's tests already drive), the certainly-dropped-scope release, the stray `put` pin, `reconcileReady`'s no-op, `isLive` for a deferred or queued record, and the two-process-over-one-store case (out of scope — a blob store is single-writer per machine, now stated in `docs/blobs.md` §SQL).
- **`docs/blobs.md`'s status line was edited**, which the implement ticket said to leave alone for the third part. Left as written it would have claimed the restart reconciliation is still to be built, which is now false; the edit is minimal — reconciliation moved into the "built" clause, the `unstaged` expiry left as still to be built.

## Tripwires parked in the code

- `SqlBlobPins.reconcile`, first `NOTE:` — a pass lists every transaction pin per backend and reads one reference tree per scope; if a machine ever keeps many pins across many wakes, remember the uncertain scopes and retry only those.
- `SqlBlobPins.reconcile`, second `NOTE:` — a pass can overlap the tail of an online commit (between `endTransaction()` and the off-chain `committed()` the transaction is not live and its pins are still there). Not a bug: the commit is durable by then and both announce and unpin are idempotent. Spelt out because it reads like one.
- `plugin.hydrate`, at the default-backend resolution — a host that uses no blobs now pays one empty single-machine blob store and its piece sweeper per hydrate; resolve it lazily on the first trigger that finds a pin if that ever shows up on a cold start.
