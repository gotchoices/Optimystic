# A blob remembers when it was last found unreferenced — review handoff

docs/blobs.md §Lifetime says a blob listed nowhere **at two passes a grace period apart** loses its `responsible` hold, and the same for an owed entry whose scope stopped listing it. Two passes a week apart can only be compared if the first leaves something behind that survives a restart. This ticket added that something — a **mark**, the start time of the first counting pass that found a blob listed nowhere — on both the blob record and the owed entry, with the writes that set, clear and act on it, and the pure rule that turns a mark and a pass's start time into a decision.

**Nothing here reads committed state, schedules anything or deletes anything.** The marks are inert until `feat-unreferenced-blobs-are-reclaimed` (the ticket right behind this one, `tickets/implement/2.86-…`) lands the pass that writes them. Nothing in the tree calls `markUnreferenced`, `clearUnreferenced`, `releaseResponsibleIfMarked`, `markUnlisted`, `clearUnlisted`, `deleteIfUnlisted` or `judgeMark` yet except the new spec; `NodeOptions.blobs.reclaimGraceMs` does not exist yet either, which is why `resolveReclaimGraceMs` has no caller. All of that is 2.86's wiring, by design — see *What is deliberately absent* below.

## What landed

### The pure rule — `packages/db-p2p/src/blob/reclaim-marks.ts` (new)

`DEFAULT_RECLAIM_GRACE_MS` (7 days), `MIN_RECLAIM_GRACE_MS` (1 hour), `judgeMark(mark, startedAt, graceMs): 'mark' | 'keep' | 'release'`, and `resolveReclaimGraceMs(declared)`. No clock and no store, so the pass and the node factory will share one copy of the bounds.

`judgeMark` answers `'mark'` for no mark **and** for a mark that lies after `startedAt` (the wall clock having gone back — restarting the period is the direction that keeps the blob); `'release'` when `startedAt - mark >= graceMs`, so exactly a grace period releases; `'keep'` otherwise. `resolveReclaimGraceMs` throws `RangeError` naming `blobs.reclaimGraceMs` rather than clamping, in the shape of `resolveBlobCacheBudgetBytes` in `libp2p-node-base.ts`. The accepted-tradeoff `NOTE:` about measuring the period on the host's wall clock sits at `judgeMark`; docs/blobs.md §Lifetime already states it under *Accepted limits* and nothing at the site did. Exported from `src/index.ts`, **not** from `src/rn.ts` (which stops at `single-machine-blob-service.js` and carries neither the owed ledger nor the reference check).

### The record field — `blob-record.ts`, `local-blob-service.ts`

`BlobRecord.unreferencedSince?: number`, checked in `recordProblem` exactly as `lastReadAt` is: a value that is not a finite number refuses the record. Refusing stops that blob's sweep until it is fixed, which is the established price of a checked field and the honest one — a mark nothing can interpret would otherwise decide a deletion.

The safety rule — **every write that adds or removes a `responsible` hold clears the mark in the same record write** — is carried by two helpers beside the existing ones:

- `recordAfterResponsibleHold` now ends in `withoutUnreferencedSince(...)`.
- `recordAfterResponsibleRelease` is no longer the bare `recordAfterHoldRelease('responsible')`: it composes that (now named `recordAfterResponsibleHoldRelease`) and drops the mark when the release actually released something. `recordAfterHoldRelease` is still the generic used for `owed`.
- `recordWithUnreferencedMark(current, at)` and `recordWithoutUnreferencedMark(current)` each return the current record **by identity** when there is nothing to do, so `BlobRecordStore.apply` writes nothing. `recordWithUnreferencedMark` returns the record unchanged when it holds no `responsible` hold — the mark is only ever about that hold.
- `withoutUnreferencedSince` omits the property via rest destructuring rather than setting it to `undefined`, so the record encodes and deep-compares as one that never carried it. (This package has `exactOptionalPropertyTypes` off — backlog `debt-tsconfig-exact-optional-property-types` — so the two are not the same value.)

New door `BlobReclaimRecords` with `ResponsibleMark`, implemented by `LocalBlobService` (added to the `implements` clause), a door rather than a second `BlobRecordStore` for the reason `BlobOwedRecords` already gives. Its five members: `responsibleMarks`, `clearUnreferenced`, `markUnreferenced`, `releaseResponsibleIfMarked`, `sweep` (the existing method). `responsibleRefs` is now `(await this.responsibleMarks()).map(…)`, so one enumeration serves both and they cannot disagree; its contract never promised an order, and its `NOTE:` about reading every record stayed where it was.

Both conditional writes use the shape `releaseCached` already uses — **the change function is itself the condition**, applied at that reference's turn in the record store's per-ref queue, so nothing is re-read first and no lock is added. "Answers whether it wrote" is read off a `let wrote = false` the change function sets, not off `BlobRecordChange`'s before/after, because a release that leaves a pin behind keeps the record.

`markUnreferenced` deliberately has **no** expected-mark condition while `releaseResponsibleIfMarked` does; the reasoning is in the interface's doc comment (nothing but the pass writes a mark and passes never overlap, so such a condition could never fire — conditioning on the hold, which *can* have gone, is the condition that matters).

### The ledger field — `owed-blob-ledger.ts`

`OwedBlobEntry.unlistedSince?: number`, validated in `isEntryFor` beside `recordedAt`; a malformed mark makes the whole entry read as absent and logged, never deleted by a read — the existing rule, unchanged.

`record` now builds the stored entry field by field (`{ ref, scope, holders: existing.holders, recordedAt: existing.recordedAt }`) instead of spreading, which drops the mark by construction rather than leaning on `JSON.stringify` discarding an `undefined` property. `addHolders` still spreads, with a line saying why: a peer confirming it holds a copy is not evidence that any row references the blob, so it must not restart the grace period.

`clearUnlisted`, `markUnlisted` and `deleteIfUnlisted`, each inside `queue.run(ref, …)` like the existing writes, with `deleteIfUnlisted` going through the same private `remove` helper `delete` does so the in-memory index stays in step.

**Flush policy, the one thing worth reading carefully.** The two mark writes do **not** flush, against this class's standing rule that every public write does; `deleteIfUnlisted` does. Both decisions are stated at the site. A mark is advisory (one a crash loses costs a delay of one grace period, never a lost copy) and flushing per entry per pass would cost a node with thousands of them one store flush each; what the rule exists for is unchanged, because every call that creates or deletes an entry still flushes. `deleteIfUnlisted` must flush because the pass deletes the entry and *then* releases the `owed` hold — a crash between the two must leave a hold with no entry (storage kept, nothing lost) rather than an entry whose drain announces a blob this node no longer holds — and that ordering only holds if the delete is durable before `LocalBlobService.releaseOwed` writes.

## Use cases to validate

- **The grace-period boundary.** `judgeMark` must release at exactly `graceMs` and keep one millisecond short of it; a mark in the future must give `'mark'`, not `'release'` (a backwards clock must not reclaim).
- **A mark cannot outlive its hold.** This is the one failure mode these marks have: a mark left over from before a hold was re-taken would let a *single* pass release a hold taken minutes ago. Check every write that touches the `responsible` hold clears the mark, and that `responsibleMarks` does not list a record that no longer holds `responsible`.
- **`releaseResponsibleIfMarked` with a stale mark.** Must write nothing and leave the hold standing — the branch that would otherwise delete a live blob.
- **A pin outlives the released hold.** `releaseResponsibleIfMarked` on a blob that is also pinned takes the hold and the mark and leaves the pin and the record; the mark going must not be read as the record going.
- **`markUnreferenced` with no `responsible` hold** (none at all, or only a pin): writes nothing, answers `false`.
- **An owed re-record clears, a holder confirmation does not.** `record` with the *same* scope still clears the mark (deliberate: an `announce` for a reference already owed is the writer saying the reference is live); `addHolders` keeps it.
- **`deleteIfUnlisted` on an entry the drain already deleted** reads as absent and answers `false`, so the pass will leave the `owed` hold to the drain, which released it with the entry. Inspection of `read` — not tested.
- **No behaviour change for existing callers.** `responsibleRefs` is now sorted where it was unordered; `BlobCohortReaction`, the announce receiver and the copy drain are its callers. Their specs pass unchanged.

## Tests

`packages/db-p2p/test/blob-reclaim-marks.spec.ts` (new), three tests, over a real `LocalBlobService` on `MemoryKVStore` + `MemoryPieceStore` and a real `OwedBlobLedger` on a `MemoryKVStore` — no mocks of anything this package owns:

- **`judges a mark against the pass start time, and refuses a grace period below the minimum`** — `judgeMark` over the table above (no mark, future mark, exactly `graceMs`, one millisecond short, mark equal to `startedAt`), and `resolveReclaimGraceMs` for `undefined`, exactly `MIN_RECLAIM_GRACE_MS`, one below (throws) and `NaN` (throws).
- **`a record mark lives and dies with the responsible hold it is about`** — `markUnreferenced` answering `false` with no hold and with only a pin; the mark set and read back through `responsibleMarks`; a second `holdResponsible` clearing it (and the property *omitted*, not `undefined`); `releaseResponsibleIfMarked` with a different mark answering `false` while `responsibleScope` still answers, and with the carried mark answering `true` and deleting the record; the pinned case leaving the pin and the record; and `clearUnreferenced` dropping the mark while the hold stands.
- **`an owed entry mark lives and dies with the entry it is about`** — `markUnlisted` answering `false` with no entry and never creating one; the mark set and visible through `list`; `addHolders` keeping it; `record` with the same scope clearing it; `deleteIfUnlisted` with a different mark answering `false` and the entry standing, with its own mark answering `true`, the entry gone and `size` back to 0; and `clearUnlisted` dropping the mark while the entry stands.

**No test for:** the two fields' decoding (one check each in validators the record and entry specs already cover), the flush policy (not observable without mocking a store this package owns), or the export from `src/index.ts` (wiring).

Splitting that rewrite across two tickets would have both editing the same paragraphs. **Do not read the absence as a gap.**
- **No `NodeOptions.blobs.reclaimGraceMs`.** 2.86 adds the field and the `resolveReclaimGraceMs` call beside the `resolveBlobCacheBudgetBytes` call in `createLibp2pNodeBase`. Until then `resolveReclaimGraceMs` is exported and unused outside its spec.

## Known gaps and judgement calls, for the reviewer to weigh

- **`responsibleHoldOf` in `releaseResponsibleIfMarked`'s condition is belt-and-braces.** A mark can only be written while the hold is held, and every hold-removing write clears the mark, so "mark matches" should already imply "hold present". It is kept because a record written by a build that had the field without the rule must not be read as a release that happened — and because without it a matching mark on a holdless record would set `wrote = true` for a change function that returns the record unchanged, making the flag lie. Stated in a comment at the site. A reviewer may judge it dead code; the argument for keeping it is the flag's honesty, not the hold's.
- **`clearUnreferenced` is a no-op on a record with no `responsible` hold**, per the planned contract, so a stray mark left by a crash between a release and its clear is not swept by it. That mark is inert (`responsibleMarks` does not list it) and the next `holdResponsible` removes it. The alternative — clearing unconditionally — is also defensible; the contract was written the first way and the code follows it.
- **`recordAfterHoldRelease` now has one caller** (`owed`), since `responsible` needed the mark step. Left as the shared generic rather than inlined, to keep the diff to the behaviour that changed.
- **`markUnreferenced`/`markUnlisted` answer `false` when the mark is already exactly `at`.** Honest ("it did not write") and unreachable from the pass, which only marks when `judgeMark` says `'mark'`.
- **`responsibleMarks` sorts by reference string** (`a.ref < b.ref`), which is a plain code-unit comparison; references are lowercase base32, so this is also their lexicographic order. No caller depends on the order yet — 2.86's pass will, for a deterministic enumeration.
- **Two `LocalBlobService` instances over one key-value store** each keep their own serial queue, so these conditional writes are serialized only per instance. Not a new exposure (`OwedBlobLedger`'s doc comment already says one instance per store, and a node builds one of each), but 2.86's restart test builds two, so it is worth knowing.
