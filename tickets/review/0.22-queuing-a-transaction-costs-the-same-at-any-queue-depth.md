GitHub #53. Both `NOTE:`s that were waiting for this report, at `judgeTransaction` and at `OfflineMode.followQueue`, are gone.

## What was built

**Segment lookups.** `SegmentList` keeps a `Map` beside its array, so `find` is a map read. `Collection.holdsSealed(entryId)` and `Collection.hasSealed()` replace the `.sealedEntries().includes(id)` and `.sealedEntries().length` call sites.

**One kept index.** `OfflineMode.queueWrites` is one `WriteIndex` of the queue. An entry joins it when it is judged and leaves when it commits, and `judgeTransaction` takes an index instead of building one. So `WriteIndex.remove` costs the entry's own keys, its member lists are maps keyed by transaction id, and `insertedAbsent` holds each inserter's freshness per key, read as "any is fresh". An indexed entry's `assured` is a getter that reads `OfflineMode.judgements`.

**A narrow follow on a commit.** `followCommit` is a pure function beside `followOutlooks`. Dependents lose the committed transaction in queue order, each one's kind is derived again by the shared rule (`outlookKind`), and a change of kind passes on through a reverse map, `OfflineMode.dependents`. `OfflineMode.followStatus` picks the route: a `committed` status takes the narrow follow when `judgements.size` equals the queue depth, meaning every queued entry is judged and none is leaving. Everything else takes the full walk, which rebuilds the index and the reverse map.

**Constant-time queue read.** `OfflineQueue.queuedEntry` gives one entry and its position. It is constant time for the newest entry and scans only for one a restore inserted ahead of others.

## Tests

In `packages/quereus-plugin-optimystic/test/commit-outlook.spec.ts`:

- `answers what the walk answers, after each commit of a head, and the kept index what a fresh one does`: 400 seeded queues with overlapping keys, a mix of kinds, unreadable segments, unchecked reads and refused entries. After each committed head the narrow follow's outlooks deep-equal `followOutlooks` (a refused entry keeps the outlook it had), and the index with removals deep-equals one built fresh. - `works a transaction out after every dependency it has, though a kind change reaches it late, and answers in queue order`: one hand-built shape, added beyond the ticket's one test because random queues did not produce it. It is the only test that catches a follow processing out of queue order.

Each behaviour was checked by breaking it on purpose. Removing `insertedAbsent` or `byKey` on `remove`, keeping empty groups, not passing a kind change on, recomputing a refused entry, reading a kind from before the follow, processing out of queue order, and counting `unchecked` towards the kind each make a test fail.

## Where this departs from the ticket

- **No entry count.** The ticket asked for one on `SegmentList`, but the only caller needs a yes or no, and `SegmentList.hasSealed` already answers that, so `Collection.hasSealed` exposes it.
- **`heldCollections` needed no change.** The ticket lists it as a `.sealedEntries().includes` site, but it only filters `committedCollections`. The scan the profile showed was `sealedWrites` reaching `SegmentList.find`.
- **`stillSealed` keeps `sealedEntries()`** in `OfflineMode.queuedTransactionsOf`. It needs the whole list and runs on a schema change.
- **Two extra replacements.** `OfflineRestore.positionOf` now uses `holdsSealed`. `OfflineMode.followedEntry` now reads refusal through `OfflineQueue.segmentRefused`, the queue's own collection instances, instead of the bridge's registry, so both follows ask one question. The two differ only with two tables declared over one URI, the caveat already recorded at `OfflineMode.sealedWrites`.

## Please look hard at

- **An entry that has left the queue but has no terminal status yet.** `OfflineQueue.committed` awaits the journal between taking an entry out and emitting its status, and a failed entry's drops take longer. That entry is still in `queueWrites`, so a transaction judged in that interval lists it as a dependency until the status arrives, where before it did not. I chose this over a strict membership check, because that check would put a whole-queue pass back on every commit landing in the journal write, the cost the ticket rejects. It also means such a transaction can be judged with `insertedFresh` true for a row that entry inserted. The same result already happens to a transaction judged just before the entry leaves, and docs/offline-sync.md §Judging each guard states that residual. **No test drives this interval.** It is described in docs/offline-sync.md §The outlook.
- **The coverage check is a count.** `queueWrites.size >= ahead` catches a restore that has registered an entry not yet indexed. A restoring entry (listed, not indexed) and a leaving one (indexed, not listed) can cancel out, which needs a discard running during a restore's staging plus an enqueue at that moment. The restored entry's own `queued` status then corrects it through the walk. The comment in `judgeQueued` says this. No test drives it.
- **The route's precondition is also a count.** `judgements.size === depth` can hold with one unjudged entry and one leaving entry together. The narrow follow then runs with the leaving entry's kind still held, so a dependent can flip to `assured` just before that entry's failure refuses it. `weighFailure` marks it `dependencyFailed`, so `assuredFailures` is not counted, but the application does see that `outlook-changed`.
- **A restored-already-committed entry now takes the narrow follow.** A transaction listing it as deferred loses it at once. The old walk still read it from the restorer's records until the pass ended, so the dependency stayed until the next walk. I believe the new behaviour is the correct one, but it is a change, and no spec pins either.

## Known gaps

- A UNIQUE index still scans. `WriteIndex.writersWithin` walks every indexed key of the collection for an `absentRange`, and the existing `NOTE:` there parks it. Measured with a scratch loop over `judgeTransaction`: 1.7, 11.8 and 108 microseconds per judgement behind 100, 1,000 and 10,000 indexed keys. The bench has no UNIQUE index, so its flat curve does not cover this.
- Many transactions writing one row still cost more with depth, because each lists every earlier writer in `dependsOn`, and that list is what the outlook reports. Not measured.
- The full walk makes two passes on its rare paths, one for the index and one for the walk. That was simpler than sharing, because the walk's index holds kinds as of the walk and the kept one reads them live.
- `queueWrites` holds a small map per queued key. A `NOTE:` on the field names the remedy if bulk offline writes make it heavy. Not measured.
- The property test does not exercise partial commits, deferred records or never-judged entries. Those take the walk, and the existing SQL-level specs cover them.
