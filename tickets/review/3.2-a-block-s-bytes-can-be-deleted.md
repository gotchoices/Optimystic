# A block's bytes can be deleted

## What changed

One operation, named `deleteBlock`, at every layer of the block store, removing everything a node holds for one block id. Before it, nothing in the system could take a byte off a node: the only delete in the whole surface was of one pending record, and invalidations write compensating *forward* revisions rather than removing anything.

**The layers, top to bottom.**

- `IBlockStorage.deleteBlock(latch)` / `BlockStorage.deleteBlock` — asserts the block's write latch (`assertLatch`, exactly as `restoreRevision` and `savePendingTransaction` do) and makes one storage call. No metadata read first: there is nothing to decide, and a block whose metadata is already gone still has content a resumed delete must take.
- `IRawStorage.deleteBlock(blockId)` / `KvRawStorage.deleteBlock` — a delegation to the driver, **not** a composition. See *Deviation from the ticket* below.
- `RawStoreDriver.deleteBlock(blockId)` — **required**, not optional, so a wrapper that forgets to forward it does not type-check (the reasoning `flush` and `durability` already carry). Three wrappers, three jobs: `WriteGroupDriver` flushes its group strictly and then delegates, so no overlay put can be applied after the delete and resurrect the block; `CachedStoreDriver` drops everything it caches for the block; `RawStorageDriverAdapter` delegates to the `IRawStorage` it fronts.
- `BatchBackend.deleteBlock(blockId)` — where the whole contract is written down once. The six block-scoped stores and only those; metadata first and durably before any content store; idempotent; the caller holds the latch. `JournalStore` inherits it, and `JournalBatchBackend.deleteBlock` applies everything held before delegating, so no journal record can be applied over the emptied block afterwards.

**The five backends.** Each in its own idiom, each scoped so that nothing sharing its database or directory is reached — not the commit proofs store, not the key-value namespaces, not the piece store, not the journal:

| Backend | How |
|---|---|
| memory driver | drops the block's entries from six maps, synchronously |
| filesystem | unlinks `meta.json` through the write-ahead log as a synced commit, **checkpoints** (which makes the tree durable and discards the log), then `fs.rm(blockDir, { recursive: true, force: true })` |
| SQLite | six `DELETE … WHERE block_id = ?` in one `synchronous = FULL` transaction |
| LevelDB | one batch deleting every key in the block's envelope range under each of six tag bytes, synced where the handle can sync |
| IndexedDB | one `readwrite` transaction (strict where supported) over six object stores: the metadata key, and each compound-keyed store's `[blockId] … [blockId, []]` range |

Three of the four shipping backends therefore do the whole thing in **one atomic transaction or batch**, which is strictly stronger than the ordering the contract asks for. The filesystem backend is the one that really is two steps, and the checkpoint is what makes its second step safe: a tree file only ever holds content whose log record is durable, so an unlink the log does not know about would be undone by the next open's replay.

**The commit proofs store is deliberately untouched.** It is keyed by a consensus message's hash alone, one entry per message however many blocks it covered, so an entry may still certify revisions of blocks this node keeps and the key shape admits no per-block delete. `deleteBlock` removes the deleted block's *entries* in the proofs store and leaves the proof *bodies* behind, orphaned when no kept revision names them. The two contract notes on `IRawStorage.getBlockProof` and `saveBlockProof` that said "no revision-delete site exists" are rewritten to say one now does, and to name `debt-unreferenced-commit-proofs-are-never-swept` as the residual's owner. That backlog ticket was already written in anticipation ("That site now exists, so the bytes now accumulate") and needed no change.

**Nothing calls it yet.** `gcEligibleBlocks` (`packages/db-p2p/src/libp2p-node-base.ts:3358`) still has no consumer; the sweep, and the rule about which blocks may be given to this operation, is the next ticket.

## Deviation from the ticket

The ticket asked for `IRawStorage.deleteBlock` to be "composed in `KvRawStorage` with the metadata-first, flush, content, flush ordering". It is a delegation instead, and the ordering is the backend's, stated as a contract on `BatchBackend.deleteBlock` and `RawStoreDriver.deleteBlock`. Why:

- The kernel has no metadata **delete** to call, and the ticket also requires exactly one new operation per layer. Composing a two-phase order above the driver would have meant a phase parameter on `deleteBlock` (`'metadata'` then `'content'`), which forces SQLite, IndexedDB and LevelDB into two transactions each where one suffices — trading away atomicity, which is *stronger* than the ordering it would buy, for nothing.
- The kernel also cannot enumerate a block's revisions: `rangeRevisions` is a bounded `[lo, hi]` scan, and the top revision is only knowable from the very metadata the operation removes — the same argument the ticket itself makes for putting the operation in the backend.

The reasoning is recorded at `KvRawStorage.deleteBlock`'s site and in `packages/db-p2p/docs/storage.md`. If the reviewer disagrees, the phase parameter is the alternative and it is a contained change.

## Also changed, beyond the ticket's list

- `CachedStoreDriver.deleteBlock` drops the block's cached state **twice** — before delegating (what the ticket asked for) and again after, in a `finally`. The second drop closes the window the first cannot: a read already in flight at the inner driver that fills its entry while the delete runs. One extra call, and the reasoning is at the site. A read that *starts* after the second drop reads the emptied store and caches a proven absence, which is correct.
- `CachedStoreDriver.clear()` now reuses the new private `dropBlock(blockId)` instead of repeating the same six drops inline. Behaviour-identical (same set of `pool.drop` calls, same `purgeGhosts` afterwards); it exists so the two per-block invalidations cannot drift.
- `MemoryStoreRows.deleteBlock` (shared by the two in-memory test doubles) compares each row's own `StoreKey.blockId` rather than prefix-matching the canonical string.
- Test doubles wired for the new required member: `GatedStoreDriver` and `FaultyStoreDriver` (`test/cached-raw-storage.spec.ts`), `CountingStoreDriver` (`test/support/cache-test-helpers.ts`), `CrashingRawStorage` (`test/mid-ddl-crash.spec.ts`), the `IRawStorage` stub in `test/storage-account.spec.ts`, the bare `BatchBackend` literal in `test/write-group-driver.spec.ts`, and `LaggingRawStorage` (`packages/quereus-plugin-optimystic/test/two-node-lagging-replica-multi-collection-commit.spec.ts`).

## Tests

Two, both added to the shared conformance suite (`packages/db-p2p/src/testing/raw-storage-conformance.ts`), so every registered composition runs them — the memory driver, both documented cache constructions (`KvRawStorage` over `CachedStoreDriver`, and `CachedRawStorage`), `WriteGroupDriver` over `MemoryBatchBackend`, the journal doubles, and all four shipping backends.

| Test | What it verifies |
|---|---|
| `deleteBlock removes every block-scoped store's records for its block and leaves another block's untouched` | The operation's whole inventory across the six stores (metadata, both revisions, their proof entries, a pending transform, a committed transform, a materialization) for a deleted block, every corresponding read for a second block unchanged, and `listBlockIds` no longer reporting the deleted one. **Both blocks' revisions reference one shared proof body**, so the kept block's `getBlockProof` still resolving is what proves the commit proofs store survived — the exact thing a backend whose key range is one off would break. |
| `deleteBlock is idempotent and finishes a half-done delete` | Called twice over a populated block (second call removes nothing, throws nothing); called over a block whose content was written with **no metadata**, which is the state a crash between the two halves leaves, and which must be removed — the resumability the next ticket's ledger depends on; and called over a block the store has never held (quiet success, not a throw). |

No other tests. Per-wrapper forwarding is forwarding and the type checker enforces it; the latch assertion is the one shared private method `BlockStorage` already relies on everywhere.

## For the reviewer

Things I would look at, in rough order of how much they would matter if I got them wrong:

- **The filesystem backend's three steps.** The checkpoint between the metadata unlink and the `fs.rm` is the whole safety argument, and it rests on `FileWriteLog.seal()` calling `syncUnsynced()` first (so no appended-but-unapplied record is discarded) and on the checkpoint unlinking the sealed log. I read both and believe it; it is the one place where being wrong means a replay resurrects a deleted block. Worth a second read of `checkpointOnce` / `seal` against this use.
- **No crash test.** The ordering and resumability are asserted only by the conformance case that *simulates* the post-crash state (content written without metadata) rather than by crashing. A real mid-delete crash test needs a fault-injection seam per backend, and for the filesystem the steps are the log's own operations. I judged the simulation the honest limit of what this layer can test; the reviewer may disagree.
- **`MemoryBatchBackend.powerLoss()` un-deletes a deleted block.** It rebuilds its maps from the recorded durable batches, and `deleteBlock` is not a batch, so the double cannot model a delete surviving a crash. Documented at the site. Anyone writing a power-loss test over that double must not expect otherwise.
- **Failure semantics are not uniform, deliberately.** A failed `deleteBlock` latches nothing on SQLite, LevelDB or IndexedDB — a garbage-collection write that failed must not leave the store refusing every later ordinary write. I moved the SQLite implementation off the `syncHeld` path for exactly this reason (its first draft latched, like a failed commit); the cost is that held batches' `durable`s are not settled by the delete's `FULL` commit even though it syncs their frames, which is conservative, never early. On the filesystem the first two steps are the log's own append and checkpoint and they latch the log if they fail (flush-contract rule 5, not this operation's choice); only the `fs.rm` rejects without latching. Someone may want that made uniform.
- **Nested block ids.** The filesystem backend and the memory driver lose a block nested inside a deleted one (`default/app/Ledger/index/LedgerLatest` under `default/app/Ledger`); SQLite, LevelDB and IndexedDB do not, because their keys are length-prefixed or relational. That is the filesystem layout's already-documented raw-id limit (`BLOCK_STORE_DIRS`), and a sweep working from responsibility ranges cannot produce the case — a nested id shares its parent's key prefix, so both fall in the same released range. `NOTE:`s at both sites. The conformance suite deliberately pins **neither** behaviour, since the backends genuinely differ.
- **Pre-existing, and not touched by this change:** `MemoryStoreDriver.listPendingActionIds` has a stronger form of that same prefix ambiguity — its keys are `${blockId}:${actionId}` with no length prefix, so listing pendings for `default/app/Ledger` would report phantom action ids like `index/LedgerLatest:<actionId>` for a nested block's records, which `StorageRepo.pend` would read as conflicting in-flight actions. The filesystem backend does not have this (it lists a directory). The memory driver is the local transactor's driver, and Quereus does create nested ids, so it looks reachable. Static, not reproduced. I left it alone as out of scope; filing it is the reviewer's call.
- **Three consecutive `NOTE:` blocks** on `FileBatchBackend.deleteBlock` (checkpoint cost, nested ids, empty prefix directories left behind). Each is a distinct tripwire, but it is a lot of comment for one method; trim if you think it reads as noise.
