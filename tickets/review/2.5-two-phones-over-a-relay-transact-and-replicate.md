# What landed

`packages/db-p2p/test/two-phones-over-relay.integration.spec.ts` uses one relay and two storage nodes, A and B.

- **The relay** is a plain libp2p relay speaking only identify and circuit relay, never an Optimystic cohort candidate.
- **A and B are phone-shaped:** WebSockets and circuit-relay transports only, each listening only on `<relay>/p2p-circuit`, each with a stable key and its own `MemoryRawStorage`.
- **Configuration** is the documented two-machine one: default `clusterSize`, `clusterPolicy: { repairCorroborationClusterSize: 2 }`.
- **Gating:** `OPTIMYSTIC_INTEGRATION=1`, so it runs in `yarn test:integration` and `yarn check`.

The phases are separate `it`s over shared state. A phase whose predecessor failed throws at once, naming that predecessor.

1. **Both up through the relay.** B starts knowing A's circuit address. The spec waits for a two-member cohort on both sides, then asserts:
   - every A↔B connection is relayed on both sides (production's `isLimitedConnection`);
   - the relay's identify reached each phone, and it serves neither Optimystic protocol.

   Then A writes and B reads it; B writes and A reads it.
2. **Replication, not read-through.** Waits until each node's own storage holds every committed block the other holds. Then it stops A and B reads every row, restarts A, stops B and A reads every row, and restarts B.
3. **One drops.** B stops and A writes. The admission outcome is recorded, not asserted, as in the direct-TCP spec. **B returns knowing only the relay**, with no partner address, so the pair reconnects only if A finds B again on its own. Every acknowledged row must then read on both.
4. **Both restart.** Both stop and come back over their storage: A knows only the relay, and B knows A's circuit address. Every acknowledged row reads on each, and a new write from each reads on the other.
5. **The relay restarts.** The relay stops, and the spec confirms both phones lost their reservation and their link. The relay then starts again as the same peer on the same address. The spec waits up to 30 s for both phones to re-reserve, then for the pair, then a write from each must read on the other.

"Relayed only" is asserted after connecting and after writing in every phase that opens streams, so a transport change that upgraded the link mid-spec would fail the spec rather than turn it into a direct test.

Supporting changes:

- **`test/util/two-machine-lifecycle.ts`** holds the helpers both lifecycle specs now share:
  - `Machine`, `createMachine`, `running`, `startMachine` and `stopMachine`. `startMachine` fixes the documented cluster configuration; a spec supplies only the network shape.
  - `transactorFor`, `waitForPair`, `writeRows`, `readRows` and `expectReadable`.
  - `committedBlocks` and `waitUntilHeldLocally`, which names the blocks still missing when it times out.
  - `attemptWrite` and `describeWriteAttempt`, for observed-not-asserted writes.
  - `sequentialPhases`, the phase-gating hooks.
- **`spawnRestartablePlainRelay`**, in `test/util/relay-topology.ts`, stops and restarts a plain relay under the same key on the same port. It verifies the re-bind, because a relay that silently came back elsewhere would look exactly like phones that never re-reserve. It is modelled on Sereus's `startDedicatedRelay` test harness.

# Results

Seven runs: one first run and six consecutive repeats, logged in `tickets/.logs/two-phones-over-relay.repeat.log`.

- **Phases 1–4 passed 7/7.** Each phase takes 1.2–5.6 s.
- **Phase 5 failed 7/7**, the same way every time: `waitFor timed out after 30000ms: A and B re-reserve on the restarted relay — A: 1 connection(s) to the relay, circuit address absent; B: 1 connection(s) to the relay, circuit address absent`. The first run failed at the same point, with an earlier, less detailed message.
- **Runtime:** 37–41 s in mocha, 43–56 s wall-clock, of which about 30 s is phase 5 spending its budget. The experiment's recovered path took about 9 s end to end, so a passing run should come in well under a minute. That is an estimate, not a measurement.

**Phase 3, admission observed.** A's write with B away was **refused in 7/7 runs, after 955–1144 ms**, with `Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)`. The refused row read as absent on both machines afterwards. Over direct TCP the same write is usually acknowledged after about 11–31 s, and refused only sometimes. The likely reason is inferred, not measured: a circuit dial to an absent phone fails at once, so the write's retries run out before the survivor's routing view drops the peer. This was recorded as an arm on `backlog/more-design/6.5-partition-healing`.

**Phase 3, reconnection.** A found B again on its own in every run. A throwaway experiment timed it: A reconnected 252 ms after B was back, with A's connection outbound. So the ticket's "if A never reconnects on its own" edge case did not trip.

**Phase 5, relay restart.** This is a real finding, filed as `fix/2-phones-never-re-reserve-after-their-relay-restarts` with log evidence. Here is the behaviour, from the throwaway experiment with libp2p's relay debug logs on:

- Both phones reconnect to the restarted relay within about 0.5 s.
- Neither ever asks for a new reservation. The installed `@libp2p/circuit-relay-v2` 4.1.3 re-queues only reservations found by searching; a reservation on a specifically configured relay is dropped for good.
- After a manual transport-manager re-listen, both re-reserve immediately, reconnect to each other within about 2 s, and a write crosses. So re-reservation is the only missing piece.

Sereus's `superviseRelayReservation` already compensates in the app layer, but a plain `db-p2p` host does not recover. The spec keeps asserting the correct behaviour, and it will be red in `yarn test:integration` and `yarn check` until the fix lands. The entry in `tickets/.pre-existing-known.md` keeps other agents from re-reporting it.

**Relay reservation limits.** None were tripped. The spec's relay lifts libp2p's default per-circuit cap (128 KiB / 2 min), as `spawnPlainRelayNode` already did before this ticket and as Sereus's deployed relay (`ops/docker/libp2p-infra`) does by default. A run is far shorter than the default reservation lifetime, so reservation expiry is not exercised.

**Hole punching.** The relayed-only assertion never failed.

# Known gaps and things to look at

- **Phase 5 is red by design.** If the reviewer prefers a different handling of `.pre-existing-known.md`, that entry is the only place the decision is recorded.
- **Phase 2's locality wait passes almost at once.** Both machines are in every cohort, so commits land on both. The wait proves the data is local, not how it got there; phase 1's cross-reads could also have pulled blocks in. The stop-the-writer reads prove the property that matters either way.
- **Phase 3 checks reachability after B returns, not whether B holds the missed write locally.** Every run refused that write, so there was nothing to replicate. If the admission rule changes so the survivor accepts, this is the same gap the direct-TCP spec's review recorded.
- **The spec has no "founder writes alone, then a joiner arrives" step over the relay**, because the ticket's phases start both phones together. The tripwire in `rebalance-monitor.ts`, which names a phone pair over a relay as the slow link to watch, is therefore neither tripped nor exercised here.
- **Phase 4 cannot use the "knows only the relay" start for both phones**: both peer stores are empty, so one of them must be given the other's address.
- **`sequentialPhases` calls mocha's global `beforeEach` and `afterEach`** from a util module. That is fine for specs, but calling it outside a mocha run would throw.
- **Observation in the sibling FRET repository, not filed.** In `p2p-fret`, `seedFromBootstraps` takes the *first* `/p2p/` component of a bootstrap multiaddr. For a circuit address `<relay>/p2p/<relay>/p2p-circuit/p2p/<partner>`, that is the relay's id, not the partner's, so a phone given its partner's circuit address as a bootstrap seeds FRET with the relay instead. I found this by reading the code only. It had no visible effect: the partner is learned once the connection opens, and the relay is classified foreign. The reviewer can decide whether it deserves a note or a ticket in that repository.

# Usage

- **Run it:** from `packages/db-p2p`, `OPTIMYSTIC_INTEGRATION=1 node --import ./register.mjs node_modules/mocha/bin/mocha.js test/two-phones-over-relay.integration.spec.ts --reporter spec`.
- **Read the phase 3 log line:** `phase 3 observed: A's write with B away was REFUSED|ACKNOWLEDGED …`. A change there means the admission behaviour moved.
- **New lifecycle specs** should build on `startMachine(machine, shape)` rather than calling `createLibp2pNode` directly, so the documented two-machine configuration stays in one place.
- **Relay-restart tests** should use `spawnRestartablePlainRelay(network)` and its `stop()` and `start()`.
