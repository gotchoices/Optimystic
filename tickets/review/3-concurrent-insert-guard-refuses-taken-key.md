# Review: concurrent insert guard refuses a taken key

## What was built

The implement ticket's design landed essentially as specified — guard-carrying tree actions — plus one db-core fix the tests forced (rollback across a moved committed boundary, below).

**db-core** (`packages/db-core/src/collections/tree/struct.ts`, `tree.ts`):

- `TreeEntryGuard<TKey>` — a serializable third slot on each `TreeReplaceAction` entry: `absent` (INSERT: key must not exist), `keepExisting` (INSERT OR IGNORE: skip silently if it does), `absentRange` (reserved for the secondary-unique follow-up; the handler currently REFUSES it loudly with "not enforced yet" rather than silently upserting — the follow-up ticket `concurrent-secondary-unique-guard` replaces that arm). A missing guard keeps plain upsert semantics, so existing callers and previously committed log entries replay unchanged.
- The `replace` handler enforces the guard on EVERY run — initial staging and every conflict replay — via `find(key)` + `path.on`. Violation of `absent` throws the new `TreeKeyTakenError` (carries `collectionId` + `key`); the handler runs inside the Atomic wrapper, so the throw discards the whole action's staged writes. The throw is not a `StaleFailure`, so neither `Collection.sync`'s retry loop nor `TransactionCoordinator.commit`'s stale-loss re-drive absorbs it.

**db-core rollback fix** (`Collection.restorePending` in `packages/db-core/src/collection/collection.ts`) — NOT in the implement ticket's plan; the new tests exposed it. The refusal fires after the loser's refresh has ADOPTED the rival's committed revision, so the pre-transaction snapshot its rollback then restores was captured on an older committed boundary. Restoring it verbatim reinstalled an invented collection's pre-commit header/root transforms over the rival's now-committed collection, and every later read on the loser's handle descended an empty tree (observed: `count(*)` = 0 on a table durably holding the winner's row). `restorePending` now detects the moved boundary and, when the snapshot's pending queue is empty (the transaction-rollback shape), resets the tracker empty so reads flow through to the adopted committed state. Snapshots restored on an unmoved boundary behave exactly as before.

**quereus-plugin-optimystic**:

- The vtab's insert arm resolves the conflict action even when the probe finds the key clear and stages the guard accordingly: ABORT/FAIL/ROLLBACK → `absent`; IGNORE → `keepExisting`; REPLACE → unguarded. ON CONFLICT (pk) DO UPDATE whose probe missed stages as a guarded insert — under concurrency it REFUSES rather than upserting (documented at the site; an application retry re-runs the statement and takes the update arm).
- An UPDATE that moves the PK guards the insert-half entry at `newKey` with `absent`, except a REPLACE-resolved move (unguarded — displacement is declared). An IGNORE-resolved move also guards `absent`, deliberately NOT `keepExisting`: skipping only the insert half at replay would still apply the oldKey delete half and lose the row entirely; refusing is safe and never silent (documented at the site).
- Error mapping: the vtab registers `uniqueConstraintMessage()` per main collection with the bridge (`registerKeyTakenMessage`); `mapCommitRefusal` in `txn-bridge.ts` walks the cause chain at both commit modes' failure exits and rewraps a `TreeKeyTakenError` as an error whose message is exactly `UNIQUE constraint failed: <table>.<col>[, …]`, with the structured error as `cause`. Idempotent (the legacy sweep maps before rethrowing; the shared catch maps again and detects the already-mapped shape by message equality). Downstream classifiers that already match `UNIQUE constraint failed:` need no new arm, and the refusal is automatically distinct from transport failures.

**Docs**: new subsection in `docs/internals.md` ("Conflict replay re-makes the uniqueness decision (entry guards)") covering the guard, the error mapping, and the restore-boundary rule. `yarn lint:docs` passes.

**Board**: appended the IGNORE index-anomaly arm to `6-debt-index-sweep-misses-update-delete-and-orphans` (backlog) with a `NOTE:` at the vtab's IGNORE staging site. The follow-up `concurrent-secondary-unique-guard` (implement, prereq on this slug) expects exactly the `absentRange` shape defined here.

## Known gaps and judgement calls for the reviewer

- **Legacy mid-sweep refusal → `PartialCommitError` is untested.** Reachable only in a multi-TABLE legacy transaction where an earlier table's tree synced before a later table's main tree refuses (a single table cannot hit it: guards live on the MAIN tree, which `markDirtyTrees` puts first in the sweep). The mapping code path is shared with the tested first-tree case, and the mapped message rides `PartialCommitError.reason` into its message text — but no test drives it end to end.
- **`restorePending`'s moved-boundary rebase only covers empty-pending snapshots.** A snapshot carrying pending actions across a moved boundary (a mid-transaction savepoint captured before a mid-transaction live-read refresh adopted a rival's commit) still restores verbatim — the old, potentially stale-shadowing behaviour, kept because rebasing needs an async replay a sync method cannot run. Recorded as a NOTE in the method's doc comment; pre-existing shape, not a regression.
- **"Writer several revisions behind" is argued, not tested.** `TestTransactor` refreshes fully in one round, so the lag-one-round-then-refuse loop shape (replay passes, re-transact stale-fails, later refresh refuses) has no deterministic harness. Bounded by the existing retry/stall budgets per the design; a refusal can therefore surface as `SyncRetryExhaustedError`-shaped only if refreshes never catch up, which is the pre-existing stall behaviour.
- **A live SELECT inside a doomed transaction can now surface the refusal early**: the vtab's live read path calls `tree.update()`, whose replay can throw `TreeKeyTakenError` mid-scan; it reaches the client wrapped as `Query failed: …` (via the vtab's rewrap), NOT the mapped UNIQUE message — bridge mapping sits only at the commit boundaries. Not silent, arguably useful, but the message shape differs from the commit-time refusal. Flagging rather than fixing: mapping inside the read path would need the vtab (not the bridge) to catch and rename.
- **SQL-level concurrent delete+reinsert is not raced** (which side's probe runs first is uncontrollable at SQL level, making assertions flappy); the spec covers the sequential cross-handle shape, and the stale-view replay variant is pinned deterministically at the db-core level.
- **The session-mode SQL test races one session-mode handle against a legacy rival** — the rival's commit mode is irrelevant to the loser's refusal. Two session-mode handles (two coordinators) over one directory are untested at the SQL level; the coordinator-vs-real-rival shape is covered at the db-core level.
- **Mixed versions**: an old-build peer replaying a guarded action ignores the guard and reverts to silent overwrite. Doc comment on `TreeEntryGuard` references `debt-mixed-version-identify-incompatibility`; no gating exists yet (as the implement ticket accepted).
- **Sereus follow-up (outside this repo)**: `../sereus/tickets/blocked/optimystic-concurrent-same-pk-insert-silent-lww.md` unblocks on this landing — rebuild `../optimystic` there and re-run its measurement. The refusal reuses the existing `UNIQUE constraint failed:` message shape, so no new `cadre-core` classification arm should be needed — verify rather than assume (`control-write-retry.ts` treats that message as a permanent refusal with zero retries).

## Use cases to exercise in review

- Two writers, one PK, same tick → one succeeds, one gets `UNIQUE constraint failed: <table>.<pk>`; the WINNER's row survives on every handle (pre-fix the loser's row survived and both reported success).
- INSERT OR IGNORE racing a rival on the same key → succeeds silently, rival's row kept (and on an INDEXED table, the known stale-index-entry anomaly parked on ticket 6).
- A multi-table transaction whose one insert collides → the whole transaction fails; nothing from it lands (both commit modes).
- Delete then re-insert of the same key across writers → allowed, never spuriously refused.
