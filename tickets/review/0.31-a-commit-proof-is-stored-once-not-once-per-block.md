# A commit proof is stored once, not once per block

Second half of GitHub #60 (Sereus; optimystic 1.27.0, file storage, solo node). The prereq added a commit proofs store keyed by `messageHash` to every backend; this change makes the kernel use it.

## What was built

The proofs store keeps its `(blockId, rev)` key and its meaning ("this revision has a proof"); its value is now a reference, `{ proofRef: messageHash }`, and the proof lives once per node in the commit proofs store.

- **Types** (`i-raw-storage.ts`): `ProofRef`, `StoredProofEntry = ProofRef | BlockCommitProof`; `IRawStorage.getProofEntry` / `saveProofEntry` (raw slot access, no logic).
- **`KvRawStorage.saveBlockProof`** (composed): ensure the commit proofs store holds a proof under `proof.messageHash`, then write the reference. Shared record first, so the prefix rule keeps no reference without its target. First writer wins (an existing record is kept), with the accepted-tradeoff `NOTE:` at `storeCommitProofIfAbsent`.
- **Memo**: `storedCommitProofs`, an `LruMap<string, Promise<void>>(1024)` per kernel, hash → in-flight-or-settled save. A commit of N blocks reads and writes the shared record once; concurrent saves of one message join; a rejected save is removed (identity-checked) and rethrown to its callers. The encode happens synchronously on a memo miss, so the stored proof is a snapshot at call time like every other save.
- **`KvRawStorage.getBlockProof`** (composed): a `ProofRef` resolves through `getCommitProof`; a missing target logs `proof-ref-dangling` on the new `storage` namespace (documented in `docs/debugging.md`, which the log-namespace guard requires) and answers `undefined`; any other entry is a legacy whole proof, returned as is, with a `NOTE:` that legacy entries are never rewritten.
- **`RawStorageDriverAdapter`** maps `getProof`/`putProof` onto `getProofEntry`/`saveProofEntry`, so `CachedRawStorage` (outer kernel composes) passes references through instead of resolving and re-expanding them.
- **`IBlockStorage.hasBlockProof(rev)`** (`getProofEntry(...) !== undefined`); `StorageRepo.backFillProof` uses it, keeping the duplicate-certified-push cost at one key lookup.
- The tripped `NOTE:` on `persistProofIfContentMatches` is replaced by a sentence saying the proof is stored once and referenced per revision.
- Docs: internals.md §Durable commit proof *Persistence and retention* (layout, retention, wire decision with both backlog tickets, the measurement); storage.md (choke-point quote, Invariant 2's note on who writes the commit proofs store and under which latch, §5 composition paragraph, fs layout); the four backend READMEs' layout tables now say the proofs store holds a `StoredProofEntry`.

Unchanged by construction: which revisions get a proof, what `servableProof`, repair, push and claim selection read (same artifact out of `getBlockProof`), the restore wire's stripping of unverified proofs.

## Measurement (not committed as a test)

One solo node, `FileRawStorage` (read cache kept out so the "before" override is not bypassed), 5 single-statement inserts of 500 rows into one table (integer key plus eight text columns), bytes and files counted on disk under the block store after close. "Before" is the same build with `saveBlockProof` overridden to write the whole proof into the revision's entry, which is byte for byte what the previous kernel wrote; it was not run on the 1.27.0 release itself.

| indexes | layout | proof files | proof bytes | rest of block store | proofs ÷ rest |
|---|---|---|---|---|---|
| 4 | per block (before) | 834 | 26,326,599 | 12,131,272 in 2,562 files | 2.17 |
| 4 | once (after) | 834 refs (50,040 B) + 14 proofs (145,932 B) | 195,972 | same | 0.02 |
| 8 | per block (before) | 1,566 | 93,585,343 | 19,859,636 in 4,738 files | 4.71 |
| 8 | once (after) | 1,566 refs (93,958 B) + 22 proofs (271,167 B) | 365,125 | same | 0.02 |

The distinct-proof counts include the DDL commits. Wall time was the same in both layouts (one run each, about 11.6 to 11.9 s at 4 indexes, 22.2 to 22.6 s at 8); no claim about speed is made from that.

## Tests

- Conformance (`raw-storage-conformance.ts`), every backend and composition: "a proof saved for several blocks is stored once, and each revision refers to it" — one proof saved for three blocks reads back equal for each, `getCommitProof(hash)` holds it, each `getProofEntry` is `{ proofRef: hash }`. Through `CachedRawStorage` this also pins the adapter's mapping.
- Conformance: "an entry holding a whole proof, as an earlier build wrote it, reads back as that proof" — the legacy arm.
- Upgrade check: "reads the commit proof the older build stored for the diary log tail it last committed" — reads, through the raw storage now exposed as `CurrentBuild.storage`, the proof at the diary tail's latest revision before any write, and checks `proofClaimsCommit` for that `(blockId, rev, actionId)`. Gated by `holdsRevisionProofs` in `fixture.ts` (fs: a `proofs/` path; LevelDB: a key with tag byte `0x06`, kept as a literal since it describes data already written). Every one of the 38 fixtures (1.0.0-beta.3 through 1.27.0, fs and LevelDB) holds proofs and passes.
- No test for the memo, the in-flight join, the rejection drop or the dangling arm, as the plan said.
- Changed fixtures, not new tests: `block-storage.spec.ts`'s cast-literal proof gained a `messageHash` (storage now files a proof under it; without one the reference was written as `{}` and read back as a legacy entry). `IRawStorage` wrappers gained the two methods: `CrashingRawStorage` (`mid-ddl-crash.spec.ts`), the storage-monitor stub, the plugin's `LaggingRawStorage`.

## For the reviewer

- The precondition on `saveBlockProof` (`proof.messageHash` is the hash of `proof.message`) is documented, not checked. Callers to confirm: `persistProofIfContentMatches` (from `internalCommit`, whose proof comes from `buildBlockCommitProof` in `applyConsensusCommits` or `CoordinatorRepo`'s `mintSoloCommitProof`, and from `backFillProof`), and `BlockStorage.saveRestored` (only the `saveReplica` caller-verified proof). A proof without a `messageHash` — reachable only by a cast — would be filed under the key `undefined`.
- First writer wins can degrade to last writer only when an in-flight memo entry is evicted (1024 other messages saved while it is in flight); both writes are of the same message, so references stay valid. Stated at the memo's doc.
- Noticed, not touched: docs/internals.md's bullet "Proof retention is per revision, and not retroactive" says a revision that landed proof-less keeps no proof even if a later certified heal carries one, which reads as contradicting the back-fill paragraph under *Persistence and retention* (a certified push or reconcile of a held revision back-fills). Worth a check.
