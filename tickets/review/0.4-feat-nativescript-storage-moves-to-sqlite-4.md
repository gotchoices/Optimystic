# NativeScript storage moves to `@nativescript-community/sqlite` 4.x

GitHub #38 (kjeib), also gotchoices/sereus#45 point 3. `@optimystic/db-p2p-storage-ns` now declares the plugin at `^4.1.0`, not `^3.5.0`.

## Nothing beyond the reporter's run was verified on a device

Nothing in this repository runs NativeScript. The only device evidence is the reporter's run of this package at 1.20.1, unmodified, on plugin 4.1.0 (Galaxy S7, Android 8.0, NativeScript 8.9). **Not run by anyone:** a long session with real network traffic, iOS, the Node-API binding NativeScript 9.1+ selects, and a power cut. The README and the release note both say so.

**What changed beyond that run:**

- Production behaviour: one line, `await raw.ready` in `openOverPlugin`, so a failed open states its own failure instead of through the first statement's rejection.
- Types and comments in `src/`: `NSPluginDb` and `NSPluginModule` tightened to the 4.x shape and exported for the test driver (not from `src/index.ts`); `TransactionConnection.execute` now returns only a promise; comments restated, including two tripwires.
- Everything else is tests, documentation, the peer range and its `yarn.lock` line.

**Owed at release, by a human:** ask the reporter to re-run their probe (`src/sqlite4-check.ts` in their app) on the release, and answer GitHub #38 and gotchoices/sereus#45 point 3.

## What the reviewer should look at

- **The test driver now runs production code.** `test/node-sqlite-driver.ts` no longer carries its own copy of the wrapper. It is a stand-in for the plugin over `node:sqlite` whose every call runs later, in the order made (`setImmediate` is first-in, first-out), handed to the real `openOverPlugin`. So the existing specs exercise the production wrapper, mutex and transaction protocol with other callers running between a body's statements.
- **The stand-in's limits.** It does not model the plugin's value encoding (rows and blobs are `node:sqlite`'s) or a real second thread (work runs on the JavaScript thread between turns). After `close()`, a later call rejects when its turn comes, where the plugin refuses at once. The plugin itself is still never loaded, so whether its rows really are copied `Uint8Array`s rests on reading its source and on the reporter's run.
- **The mutex stays**, with the reasons restated on `NSPluginDbWrapper`. Its comment also says why the plugin's own `db.transaction` is not used.
- **Tripwires:** a failed schema leaves the connection open (`openOverPlugin`); results over 512 KiB on the JNI bridge (`NSPluginStatement.all`, which also names `get`, since a single block read goes through it).
- **iOS bare database names move** from the working directory to the documents folder, which would mean an empty store and a new peer identity for an app that opened by bare name under 3.x. This is read from the plugin's source, not run; the release note states it.

## Small departures from the ticket's letter

- Removed the claim on `SqliteStatement` that both drivers cache parsed SQL. The wrapper's `prepare` only holds the SQL text, and nothing I could find in the plugin's documentation or JavaScript supports the claim; its compiled native core was not inspected.
- The stand-in's `get` answers `null` for no row, as the plugin does, so the wrapper's null arm is exercised.

## Tests

- Added `test/ns-opener.spec.ts`, "a failed open rejects with the plugin's error and runs no statement": the plugin's `ready` rejects while its statements would succeed and record calls; `openOverPlugin` must reject with that error and record none. Removing `await raw.ready` fails it, which I checked by doing so.
- No other new test. The suite moving onto the production wrapper is the rest of the coverage. Making `ConnectionMutex.serialize` not serialize fails both tests of the "SQLite transaction serialization" group, checked the same way and then restored.
- `settles` in `sqlite-storage.spec.ts` was not widened and no spec needed changing to pass; it did not flake in five whole-suite runs.
