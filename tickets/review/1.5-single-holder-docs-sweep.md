# Docs now match the shipped `sole-holder` diagnosis

Doc-only sweep, split from `implement/1-name-the-single-holder-deadlock` (see
`review/1-name-the-single-holder-deadlock` for the code half, which shipped separately and is
unaffected here). No behavior changed; this pass is prose plus one spec addition.

## What changed

The code (`CoordinatorRepo.reportRepairDeadlock`, already shipped, untouched by this ticket) emits
`cluster-fetch:repair-deadlock` with a `reason` of either:
- `cohort-too-small` — the cohort has fewer peers than the quorum needs even if all of them
  answered. Remedy: more machines, or an honest declared cohort size.
- `sole-holder` — the cohort is big enough, but exactly one of its peers holds the block and every
  other peer answered that it holds nothing. Remedy: another cohort peer holding the block
  (committing a new revision). No machine count or config setting helps.

Five docs previously described only the `cohort-too-small` shape and, in doing so, implied a
machine-count model ("four or more is the first size with any margin") that is only true for a
block at least two cohort peers already hold. An operator running four-plus machines could read the
old wording and believe every block was covered, when a block written while the deployment was
smaller can stay stranded at one copy forever regardless of how many machines are added later.

## What each file got

- **`docs/internals.md`** (~line 483 table, ~line 510 bullet): table now states its
  "assumes ≥2 holders" scope up front and the `4+` row's "survives one unreachable peer" is
  explicitly conditioned on that; the `cluster-fetch:repair-deadlock` bullet now documents both
  `reason` values side by side (was `cohort-too-small` only).
- **`docs/transactions.md`** (~line 634): the paragraph naming both log lines now also names both
  `reason` values and points at `internals.md` for the full picture.
- **`packages/db-p2p/docs/cluster.md`** (~line 862, new paragraph after the two-defaults
  discussion): added a "every number above counts PEERS, not COPIES" paragraph naming `sole-holder`
  explicitly, with a relative link to `docs/internals.md` (verified: `packages/db-p2p/docs/` is
  three `..` up from repo root).
- **`packages/reference-peer/README.md`** (`--assumed-cluster-size` help text, ~line 200): scoped
  "four or more is the first size that survives one unreachable peer" to blocks with ≥2 holders and
  named the `sole-holder` reason alongside the `cohort-too-small` one it already named.
- **`tickets/complete/1-repair-deadlock-is-never-named.md`**: corrected its summary table's `4+` row
  the same way. (Editing a `complete/` ticket — done deliberately per the source ticket's
  instruction, since it documents shipped operator-facing text.)
- **`packages/db-p2p/test/quorum-restore.spec.ts`**, `describe('how many answering peers a repair
  needs, by deployment size')`: docstring now states the `answeringPeersNeeded` helper's
  "every answering peer is a holder" assumption; added a new case,
  `'a block only ONE cohort peer holds needs a number of answering peers no deployment size
  supplies'`, which drives `selectQuorumRev` directly (not through `answeringPeersNeeded`, whose
  premise the singly-held case violates) across `nodes = [3, 4, 10]` and asserts `undefined` every
  time — pinning that no deployment size fixes a sole-holder block. This is what stops the
  four-plus-machines claim drifting back to unconditional if someone edits the table later.
