# Background consults started by consecutive reads share one request per peer

Source: GitHub sereus#60. A restarted member reads each table once, serially; no held block has a read-repair window stamp after a restart, so each read starts one background consult, and each consult used to go in its own read's `ConsultRound` — one `/db-p2p/sync` request per peer per read (measured 45 / 81 / 129 / 227 requests for 4 / 16 / 32 / 64 tables).

## What was built

- **`BackgroundConsultRounds`** (`packages/db-p2p/src/repo/background-consult-rounds.ts`): holds at most one open `ConsultRound` shared by the consults that run behind reads. `current()` returns (opening if needed) the open round and arms nothing; `join(round, context)` must name that round, arms an unref'd close timer on the first seat (`armUnrefTimer`), and closes at once on the 32nd seat (`MAX_CONSULT_BATCH_BLOCKS`). Each close logs `cluster-fetch:background-round` `{ blocks, reason: 'timer' | 'full' }`. A closed round still sends only when every joined seat is ready (the round's barrier).
- **Knob `readRepairCoalesceMs`**, default 250 (`DEFAULT_READ_REPAIR_COALESCE_MS`), on `ClusterConsensusConfig` and `clusterPolicy`, resolved by `resolveReadRepairCoalesceMs` (undefined → 250; finite in `[0, MAX_READ_REPAIR_WINDOW_MS]` → itself; else throws naming `clusterPolicy.readRepairCoalesceMs`), passed through `resolveClusterPolicy`, and re-resolved in the `CoordinatorRepo` constructor. `0` builds no `BackgroundConsultRounds`, and background passes join their read's round exactly as before.
- **`CoordinatorRepo`**: `backgroundRounds` is built when both consult callbacks exist and the delay is above 0. `startHeldBlockConsult` picks its round through `backgroundSeating`: the shared round when coalescing, else the read's round with the reserved seat as before. With coalescing it always readies the read's `reserved` seat (the quiet-span reservation), since the pass no longer uses it. `openConsultRound()` no longer takes a context. Accepted-tradeoff `NOTE:` at `startHeldBlockConsult` for a read with one blocking and one background consult.
- **Per-question context**: `ConsultRound.join(context?)`; `ConsultRoundDeps.context` removed; `PendingAsk` keeps its first registrant's context; `ConsultAsk.context` added; `ClusterLatestBatchCallback` lost its third parameter. The single-block callback (self, older peers) gets each question's own context. Production's batch callback in `libp2p-node-base.ts` already ignored context (it sends `rev: undefined`) and is unchanged; the mesh harness passes `ask.context` to `consultAnswerOf`.
- `HeldBlockConsults` logic is unchanged (it counts slots per round object; a shared round of ≤ 32 passes is one slot). Its doc comments and the `MAX_HELD_BLOCK_CONSULT_SLOTS` NOTEs now describe the shared rounds, including that coalescing concentrates the older-peer fallback without raising its ceiling.

## How to see it

- Three single-block reads of held, unstamped blocks issued back to back on a node with a batch callback → one batch request per remote peer naming all three, `readRepairCoalesceMs` after the first read. With `readRepairCoalesceMs: 0` → three requests per peer (verified by temporarily flipping the spec: it fails with 3 calls).
- 33 such reads with a long delay → the first 32 go out as soon as the 32nd joins (`reason: 'full'`), the 33rd in a later round (`reason: 'timer'`).
- A read of a block missing locally, a floored read, `'paranoid'` and `awaitWindowConsults` still use the read's own round and are not delayed.
- Operators: `cluster-fetch:background-round` lines; many `blocks: 1` lines mean reads arrive slower than the delay (docs/debugging.md entry).

## Tests added or changed (each beside what it verifies)

## Known gaps and things worth a second look

- Not measured end to end: the sereus#60 Node repro lives in another repo and was not re-run, so the "~105 → 4–8 requests" figure in docs/transactions.md is the ticket's arithmetic (`max(blocks / 32, burst duration / delay)`), not a measurement.
- The quiet-span path still reserves a seat in the read's own round before its `quietCohortStillVouches` await even when coalescing is on and the consult will go background; the reserved seat is then readied unused. Harmless (it can hold back the read's own blocking consults only for that one local await, as before), but it could be skipped when `backgroundRounds` exists and `awaitWindowConsults` is off.
- `settleHeldBlockConsults` now waits up to the delay: mesh specs that settle after reads with the default config (e.g. the quiet-cohort specs in `coordinator-repo-read-repair.spec.ts`) each take ~250 ms longer per settle. The db-p2p suite still ran in ~3 minutes.
- The two timing specs each cost ~1 s (they wait out a 1 000 ms delay so they can settle cleanly instead of leaving a timer to fire during a later spec).
- Mesh-based specs elsewhere that read and then immediately re-read expecting a background repair, without settling, would now be racy; none failed across the db-p2p, quereus-plugin and upgrade-check suites.
