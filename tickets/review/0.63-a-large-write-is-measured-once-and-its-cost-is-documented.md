# A large write is measured once, and its cost is documented

Last of the four GitHub #63 tickets. Code changes are small; most of the work is the measurement and the docs.

## What changed

**1. The coordinator skips its size backstop for its own node's writer.** `CoordinatorRepo.pendMany` now calls `assertTransactionFits(requests)` only when `options?.localWriter !== true`. Confirmed before changing:

- `MessageOptions.localWriter` reaches `CoordinatorRepo` only from `NetworkTransactor` (`localWriterMark`, keyed on the peer each request actually goes to). The Quereus plugin's `local` transactor also sets it, but hands it to `StorageRepo.pend` directly, never to `CoordinatorRepo`. `RepoService` builds options from the message (`{ expiration }` only), so a remote writer cannot claim it.
- Both writer paths measure before sending: `NetworkTransactor.pend` calls `assertTransactionFits([blockAction])` on the whole pend, and each per-coordinator batch (`pendRequestForBatch`) is a subset of it (subset transforms and `baseRevs`, same other fields), including batches re-homed by `processBatches` retries. `NetworkTransactor.pendMany` checks the sum and answers `undefined` when over, and the coordinator then falls back to per-collection `pend`s, each measured.
- The `NOTE:` on `transactionBytes` is rewritten: each machine now measures a pend once (writer; a coordinator that received it from another machine, which cannot trust a remote measure), with the remaining revisit condition (take the writer's measure from the encoding it is sent in).

**2. `Chain.takenBy` skips measures that cannot change the decision.** Early `return 1` for an empty block with exactly one entry to place (`block.entries.length === 0 && room === 1`), before measuring the block or the entry; and inside the loop, `break` before measuring the next entry when the block holds an entry and `bytes >= target` (any further entry adds at least its comma, so `grown > target` would have broken anyway). Every decision is unchanged; for a large write, an append now measures the tail once instead of tail + entry + entry again. The tail-measure `NOTE:` is kept, reworded.

**3. Docs.** docs/internals.md §A transaction's size limit:
- *Backstops* bullet says the coordinator skips the check for `localWriter`.
- New **What a large value costs** paragraph: the bench, a before/after table (ms per MiB staging/commit, expansion) for legacy 1/4/8 and session 1/4 values, the summary (about 0.2–0.3 s per MiB now vs 0.4–0.85 s before on the same machine; the plan's ~0.5 s; #63's 1.7 s on file storage), the run-to-run caveat, what was seen about outliers, and four bullets: what the expansion is made of, what fits, where the CPU goes, and that carrying a value once is native blobs (`docs/blobs.md`, `tickets/backlog/blobs/`), with no change to what is stored or sent.
- The *What counts* bullet's #63 sentences and the dead reference to plan ticket `a-large-write-costs-time-and-space-per-byte` are replaced with a pointer to the new paragraph.
- The log roll-over paragraph states the two skipped measures.
- docs/blobs.md §Why *Time* bullet gained one sentence pointing at the new figures, since it otherwise read as the current cost.
- `yarn lint:docs`: all resolve.

**4. Backlog ticket filed:** `debt-a-log-append-carries-its-entry-once`. Found while explaining the 4.01× expansion of one value per transaction: `Log.addActions` adds the entry, then `Chain.updateAt` rewrites it with `blockIds`; when the entry is appended to a tail that already holds entries, the tracker records both operations, so the pend carries the whole entry twice (seen in a dump of the writer's pend: `[entries,1,0,349946] [entries,1,1,350037]`). Not fixed here (out of scope, and it changes recorded operations, which retries must reproduce byte for byte).

## Tests

None added. The `takenBy` change keeps every decision, and the existing chain and log specs pass unchanged (`chain.spec.ts` "packs several entries added at once by size as well as by count" exercises both short-circuits: a block at the target after the 5,000-character entry, and a lone entry for a new empty block at the end). The coordinator change is a one-line condition on a backstop that had no test before either; I judged a test that the remote path still refuses an oversized pend not worth its cost (the 8 MiB frame cap also bounds a remote pend). Reviewer may disagree.

## Measurements (how the docs' numbers were produced)

- **Before/after, same session.** A temporary `git worktree` at `3f0e3d22` (the plan commit, before the first #63 implement commit) with its own `yarn install` (17 s) and `yarn build`, the bench copied in, then each configuration run old-then-new and, in a second pass, new-then-old, `REPS=20`. The worktree and its directory were removed afterwards. The table in the docs gives ranges over the two passes; session 1-value had one pass only.
- **Earlier runs today** (new code only, before the paired runs) were slower — legacy 8 at 374 ms per MiB total vs 207–213 in the paired runs — which is the 1.5–2× session-to-session variance the docs mention.
- **Refusals.** Legacy 8 values: 0–3 of 20 refused at 7.67–8.01 MiB; session 8 values: all refused at 9.34 MiB; 16 values: all refused (legacy 10.68, session 18.68 MiB). The bench prints MiB though it labels them MB; the docs say MiB.
- **Expansion breakdown.** Verified with two throwaway scripts (deleted) that wrapped node 0's `transactor.pend` and printed each pend's inserted blocks (by header type) and update operations with their sizes, and counted occurrences of each value's base64/hex fragment. Legacy multi-value pends: inserts of new leaves (`TL`) and the log block (`LGD`), leaf divisions carrying 1–4 already-stored rows per transaction, and own rows staged into a leaf before it divided appearing twice; session adds exactly 2.00× of validation payload (one hex copy per value). The fragment counter double-counted fragments with no `+`/`/`, so only the byte ratios were used for the docs.
- **Profile.** `node --cpu-prof`, legacy, 8 values, `REPS=20` (profile deleted). Busy 15.7 s including start-up and the bench's own pend measure (0.41 s). No `CoordinatorRepo` frame under `jsonEncodedBytes` (the backstop is gone); `takenBy` 0.14 s over 21 appends (tail measure only). Hashing ~30% (`canonicalBlockHashAndBytes` 2.35 s: preview 1.53, writer's `describeTouchedBlocks` 0.78; `hashParts` 2.09 s; `canonicalMessageBytes` 0.37 s), storage JSON ~27% (`decodeJson` 2.36 s, `encodeJson` 1.88 s), GC 1.14 s, writer size measures 1.04 s, `structuredClone` ~1.06 s, base64 of values ~0.6 s.
- **Outliers.** Over 400 commits, none above 2.6× its run's median, longest 0.89 s. The issue's 11–13 s commits and the earlier 403 s one did not appear, so no `fix/` ticket. The 403 s observation from the first ticket is recorded in the docs as seen once, cause unknown.

## Known gaps for the reviewer

- **Commit time rises during each run** (first few transactions about half as long as later ones, e.g. legacy 8: ~330 ms then ~650–750 ms). Not isolated: a 4 s pause between transactions put all of them at ~300–500 ms rather than keeping late ones fast, so CPU boost/idle state confounds it. The docs say the cause was not isolated. If someone wants it resolved, a run with a pre-filled table vs an empty one would separate table size from machine state.
- **Docs table precision.** Wall-clock on this machine is noisy (legacy 4 before: 476 vs 853 ms per MiB total across the two passes). The headline claim ("0.2–0.3 s per MiB now vs 0.4–0.85 before") holds in both passes for every configuration, but individual cells are two-sample ranges.
- **"About 0.5 s per MB when planned"** is the ticket's figure from the plan ticket's machine, not re-measured.
- **docs/blobs.md** *Space* bullet still quotes #63's 2.75–3.4× (labelled as #63's measurement); the bench now measures 3.34–4.01× legacy. Left as the issue's own number.
