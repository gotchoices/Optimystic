# A node observes the HLCs it reads and stores

Third of the three Stage 1 tickets of docs/crdt-sync.md §Migration Path (after `the-hlc-clock-and-its-persistence-port` and `every-log-entry-and-transaction-carries-its-hlc`, both complete). No ordering, admission or visibility changed: the clock only rises, and the skew measurement refuses nothing.

## What landed

**The three feed points.** Each calls `clock.observe` once, with the single highest HLC the site saw:

- **A refresh that walks the log.** `Log.getFrom` now returns `hlcHighWater`, the highest `hlcOf` over every entry it read (actions, checkpoints and invalidations; legacy entries count at their timestamp with node id `''`). `Collection.forgetAndAdopt` has `clockOf(this.transactor)` observe it, synchronously, whatever the adoption verdict (the entries were read either way, and a clock only rises).
- **An open.** `Collection.attachToLog` takes the clock (`clockOf(transactor)` from `open` and `createOrOpen`) and calls the new `observeTailEntries`, beside `floorTailEntries`: the highest HLC in the log tail block it read.
- **A pend this node stores.** `StorageRepo.pend` hands the request to `PendHlcIntake` (new module) on receipt, and has the clock observe the HLC only when the storage apply succeeded. A repo built without `StorageRepoOptions.clock` creates no intake and does nothing.

**Skew measurement.** `SkewLedger` (db-core, pure, an `LruMap` of 256 node ids) keeps per node the sample count and largest gap ahead and behind. `PendHlcIntake.receive` computes `gapMs = hlc.wallMs - clock.localTime()` for every pend carrying a well-formed HLC (`isHlc`), records it, and logs `hlc:skew` (actionId, nodeId's first 12 characters, gapMs, maxAheadMs, maxBehindMs, samples) when `|gapMs| > skewLogThresholdMs` (default 1000). A malformed field is logged once per action as `hlc:malformed` (an `LruMap` of 256 action ids) and otherwise ignored; a pend without the field is ignored silently. Exposed as `storageRepo.hlcSkew` (`undefined` without a clock).

**Node wiring.** `createLibp2pNodeBase` builds one clock with `HlcClock.start({ nodeId, store: new KvHlcClockStore(kvStore) })` before constructing `StorageRepo`, hands it to the repo, and exposes it as `node.hlcClock` on `OptimysticNodeAttachments`. The node id is `peerIdFromPrivateKey(nodePrivateKey)`, so the private-key line moved up above the storage repo. `KvHlcClockStore` stores the JSON of one `Hlc` under `hlc/high-water` and never flushes (the store's doc says why). The in-memory-store warning now mentions the clock's mark. The Quereus plugin's `network` transactor and the reference peer's `NetworkTransactor` pass `clock: node.hlcClock`.

**Docs.** crdt-sync.md §Stage 1 rewritten as what landed (clock, three carriers, transaction-not-stamp and why, stamp ids unchanged, restart rule, three feed points and the deliberate exclusions, `hlc:skew`) and the clock-skew open question points at the measurement; correctness.md §7.4 gains the HLC-issuance bullet; debugging.md gains the db-core `hlc` row and the two `hlc:` lines in the `storage-repo` row; internals.md §Key Invariants gains *Every Write Carries an HLC*; packages/db-core/docs/logs.md shows `hlcHighWater`.

## Decisions a reviewer should weigh

- **Measure on receipt, observe after a successful apply.** The ticket allowed either side of the apply for observing; observing only on success follows its own rule that the node does not build on a write it refused (a stale or validation refusal at storage included). Measurement happens before validation because it describes the sender's clock, not the write.
- **The gap is measured against the wall clock, through a new `HlcClock.localTime()`,** not against the clock's mark (which has already risen to any far-ahead HLC it observed) and not against `Date.now` directly (so a test with an injected `localClock` measures coherently).
- **A behind gap includes the write's age.** An offline-queue entry keeps the HLC minted at enqueue and a retry keeps its first attempt's, so `maxBehindMs` can be hours on a healthy cohort. Documented in `PendHlcIntake`'s doc and the debugging.md row; only `maxAheadMs` is clean clock evidence. The ticket's spec (log when `|gapMs|` exceeds the threshold) was kept as written.
- **A node's own pends are measured too,** so its own id appears in its ledger; after a jump it shows itself ahead, consistent with how others see it.
- **The two `hlc:` lines log under the existing `storage-repo` namespace,** from the new `pend-hlc-intake.ts` module (shared namespaces are normal in db-p2p), so the 58-namespace table in debugging.md and `packages/db-p2p/test/logger.spec.ts` needed no new row. The intake was split out of `StorageRepo` (already over 2,200 lines) rather than inlined.
- **`hlc` was added to `NODE_KV_NAMESPACES`.** Not in the ticket, but `FileKVStore.keyToPath`'s NOTE requires every node KV namespace there so `FileRawStorage.listBlockIds` skips it when the stores share a base path. The fs README and that NOTE list it.
- **Wired beyond the ticket:** the reference peer's `NetworkTransactor` (one line). **Not wired:** the reference peer's offline `LocalTransactor`, the db-p2p test mesh harness, and a node a host injects into the plugin without `createLibp2pNode` — all fall back to the process-wide `'local'` clock through `clockOf`, which observes nothing the node stores.
- **Startup failure surface.** `HlcClock.start` is awaited after the raw-storage lease is taken and before its release wrapper is installed. It cannot reject in practice: `loadMark` catches every load failure and the options are defaults. `generateKeyPair` already sat in the same window.
- **`getFrom`'s high water includes the entry the second loop stops at (at or below `startRev`) and reads the checkpoint twice.** Both harmless for a maximum; the field's doc says it covers every entry read.

## Use cases to validate

- A node whose wall clock is behind a peer's: after a refresh walks the peer's entry (or an open reads its tail), the next write through that handle mints an HLC above the peer's (`forgetAndAdopt` → `observe`).
- A cohort member storing a pend from a peer whose clock is 5 s ahead: its clock rises to that HLC, `storageRepo.hlcSkew.snapshot()` shows the peer with `maxAheadMs ≈ 5000`, and with `DEBUG=optimystic:db-p2p:storage-repo` one `hlc:skew` line per pend appears.
- A pend refused by storage (stale revision): measured, not observed.
- A pend whose `hlc` is `{ wallMs: 'x' }` or has a negative `logical`: one `hlc:malformed` line per action, pend handled normally.
- A node restarted over a `FileKVStore`: `hlc/high-water.json` exists beside `under-replicated/`, and the clock resumes 10 s above it; without a `kvStore` the `node-wiring` warning names the clock mark.
- Upgrade-check fixtures carry no stored mark; the clock starts from the local clock and the suite passes unchanged (it did).
