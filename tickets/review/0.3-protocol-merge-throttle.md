GitHub [#40](https://github.com/gotchoices/Optimystic/issues/40), second source. Stream reuse was declined; the cause is fixed upstream in [libp2p/js-libp2p#3692](https://github.com/libp2p/js-libp2p/pull/3692), and this change carries phones until a libp2p release includes it.

## What was built

`throttleProtocolMerges` in `packages/db-p2p/src/network/protocol-merge-throttle.ts` wraps `node.peerStore.merge` (and `delete`) at runtime. It is installed in `createLibp2pNodeBase` right after `identifyOnConnectionOpen`, before `node.start()`. Imports are type-only or pure (`LruMap` from db-core, the logger), so the React Native entry stays clean; `yarn check:rn` passes.

- **What it intercepts:** a merge whose data has exactly one key, `protocols`, naming exactly one protocol (`isProtocolOnlyMerge`, a type guard). That is the shape libp2p 3.3.11's `Connection.newStream` and `onIncomingStream` use. Every other merge passes straight through, the address merges from `peer-address-book.ts` included.
- **The rule:** per (peer, protocol), at most one such merge reaches the store per `PROTOCOL_MERGE_INTERVAL_MS` (60 s). The first merge for a pair always goes through. Inside the interval the call resolves without touching the store. If the caller's abort signal has already fired it throws, as the real merge would have done at its lock.
- **A rejected merge** records nothing, so the next stream retries.
- **Memory:** an `LruMap` of 256 peers (`PROTOCOL_MERGE_TRACKED_PEERS`). Each entry holds a per-protocol map of times and one `Peer`. Protocols per peer are bounded by the protocols this node registers or dials, because libp2p merges only protocols it actually negotiated.
- **No timer**, so `node.stop()` has nothing to tear down.

## Where this deviates from the ticket (reviewer: please judge)

- **There is no `peer:delete` event in libp2p 3.** The ticket said to drop a peer's entries on `peer:delete`. libp2p 3.3.11 dispatches no event when a record is deleted. FRET does call `peerStore.delete` (its own comment says only a host does). So the throttle also wraps `peerStore.delete` and forgets the peer once the original delete resolves (in `finally`). The store also deletes a record silently when it expires on read. That needs no handling: expiry requires `updated` to be over 6 h old, and the last real merge stamped it, so the 60 s interval ran out long before.
- **What a skipped merge returns:** the `Peer` the peer's most recent real throttled merge returned, for any protocol, not that specific pair's. This keeps one `Peer` per peer instead of one per pair. libp2p's callers ignore the value; the doc comment says so.
- **Concurrent first merges are not shared.** A burst of streams to a pair whose interval has run out each reach the store until the first resolves. Sharing the in-flight promise would tie one stream's negotiation to another stream's abort signal, since the inbound merge passes the stream's negotiation-timeout signal.

## Tests added

- `packages/db-p2p/test/protocol-merge-throttle.spec.ts`
  - "lets one per-stream merge per peer and protocol reach the store per interval": the first stream reaches the store; a second inside the interval does not and returns the first's `Peer`; a second protocol has its own interval; a stream after the interval reaches the store. Fake clock. The fake store's `merge` reads `this`, so a wrapper that dropped the store as `this` would fail here.
  - "forgets a deleted peer, so its next stream re-creates the record": covers the `delete` wrapper described above.
- `packages/db-p2p/test/libp2p-merges-protocol-per-stream.spec.ts`: the pinning spec. It uses two plain libp2p nodes over loopback TCP, no throttle installed, and opens two streams of one protocol. It asserts that each end's `peerStore.merge` is reached once per stream, and that every such call matches `isProtocolOnlyMerge`. It fails on the libp2p release carrying #3692 (fewer merges, so delete the throttle). It also fails if libp2p moves the call or changes its shape, which would otherwise make the throttle a silent no-op. Runs in about 120 ms.

As a one-off check, not committed, the throttle was installed on the real nodes in the pinning spec: two streams reached the real store once per end, and both streams still completed. So the wrapper works against `@libp2p/peer-store`'s private-field `this` and the third `options` argument.

## Known gaps / things to look at

- **A rejected merge being retried** is not tested (the ticket said to check it by inspection). The code records only after the `await`, so a rejection skips the record.
- **Behaviour change:** a protocol identify removes from a record is put back by a later stream up to 60 s later instead of at once. The ticket accepted this.
- **Upgrade bypass:** if libp2p starts calling a different method or object, the throttle is silently bypassed and behaviour reverts to today's. Only the pinning spec catches that, so keep it out of any env gate.
- The interval and peer cap are constants, not `NodeOptions`, on purpose: this code is temporary.
