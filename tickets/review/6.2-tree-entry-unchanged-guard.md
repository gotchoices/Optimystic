description: A staged tree write or delete can now say "the entry I am replacing must still be exactly the one I read", so a commit that would silently overwrite or resurrect a row another machine changed in the meantime is refused instead.

## What landed

A fourth `TreeEntryGuard` kind, `unchanged`, in `packages/db-core/src/collections/tree/struct.ts`. The three existing kinds all say "nothing may be here"; this one says "what is here must still be what I read". The tree's `replace` handler enforces it on every run — initial staging and every conflict replay — so a losing concurrent writer is refused rather than re-applying a staged effect that was computed from an entry image a rival has since changed or removed.

Nothing in the SQL layer stages one yet. That is the sibling ticket `refuse-concurrent-row-change-loser`; this ticket is the db-core mechanism only, exercised through raw `Tree`s.

**The guard.** `TreeUnchangedGuard<TEntry> = { kind: 'unchanged', expected: TEntry }`. `expected` is the entry as stored, not a digest, so it round-trips through the log under the same encoding entries already use. An **absent** entry counts as changed, on upserts and on deletes alike — refusing an upsert is what stops a rival's delete being undone, and refusing the second of two racing deletes is the ordinary optimistic answer (the writer read a row that is now gone; a sequential retry then affects zero rows).

**Guards on deletes.** The handler previously ignored the guard slot on a delete entirely. `TreeReplaceAction` is now a union of `TreeUpsertElement` (any guard kind) and `TreeDeleteElement` (an `unchanged` guard or none), so a well-typed caller cannot attach a meaningless kind to a delete; the handler re-checks at runtime too, because a replayed log entry is deserialized data no type policed. It stays a positional tuple, so previously committed log entries and existing callers deserialize and replay unchanged.

**The error hierarchy.** New base `TreeGuardRefusedError` carries the contract shared by every guard refusal (discards the whole action's staged writes, is not a `StaleFailure`, is never downgraded to retryable). `TreeKeyTakenError` now extends it; new `TreeEntryChangedError` (carrying `collectionId`, `key`, `expected`, `actual`) extends it as a **sibling**, deliberately not a subclass of `TreeKeyTakenError` — the Quereus bridge's `mapCommitRefusal` renders every `TreeKeyTakenError` as that collection's registered `UNIQUE constraint failed` message, and a lost update is not a uniqueness failure. All three are exported from `packages/db-core/src/index.ts` through the collections barrel.

**Structural equality.** New `structuralEquals` in `packages/db-core/src/utility/structural-equals.ts` (exported from the package index). JSON-shaped values plus `Uint8Array` compared by bytes. Three deliberate rules, each because one side of a guard comparison has usually crossed an encoding boundary and the other has not: object key order is ignored, an `undefined`-valued property counts as absent (what JSON does to it), and `NaN` equals `NaN`. No `entryEquals` constructor parameter was added to `Tree.createOrOpen` — no caller needs one.

**Plugin fallout.** `uniquePrefixGuard` and `IndexManager.guardFor` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts` now return `TreeEntryGuard<IndexKey, IndexEntry>` rather than `TreeEntryGuard<IndexKey>` — the second type parameter defaults to `unknown`, which is not assignable to a typed tree's entry. Two annotation changes, no behaviour change. The `TreeEntryGuard<string>` annotations in `optimystic-module.ts` needed nothing because that tree is typed `Tree<string, any>`.

New coverage:

- `packages/db-core/test/tree-guard.spec.ts` — a new `unchanged guard (lost-update refusal)` describe plus one coordinator-path case. Guarded upsert commits when uncontested; refused when a rival changed the entry (asserting `expected`/`actual`/`collectionId`/`key`, that it IS a `TreeGuardRefusedError` and is NOT a `TreeKeyTakenError`); refused when a rival deleted it (`actual` undefined, and the row stays deleted); guarded delete commits when unchanged and is refused when the rival changed the entry; a two-entry action where only the first is refused lands neither entry; a JSON round-tripped guard still compares equal and still refuses a genuine difference; a `Uint8Array`-bearing entry compares by bytes across a different instance; a delete carrying a non-`unchanged` guard is rejected at the type level (`@ts-expect-error`, which the package's `tsc` build verifies since its tsconfig includes `test`) and at runtime; the sync loop does not retry the refusal (`pendCalls` stays 1 against a real `CompetingWriterTransactor`); and the coordinator's inter-attempt refresh surfaces it with the sibling collection landing nothing.

## Handoff notes — where to look hard

**The ordering the ticket asked about was easy to preserve, but one nearby thing was not what it looked like.** Guard-before-write and first-refusal-discards-the-whole-action both fell out of the existing structure: the handler already ran inside the Atomic wrapper, and the upsert guard already ran before `upsert`. Moving the three kinds into a `enforceUpsertGuard` / `assertEntryUnchanged` / `deleteGuardExpected` trio changed no order. The delete branch now finds its path once and reuses it for both the guard read and `deleteAt` (no mutation in between, so the path stays valid) — worth a second pair of eyes on that reuse.

**I tightened a pre-existing hazard in passing, and it deserves scrutiny.** Both guard-presence checks were `guard !== undefined`. JSON renders an explicitly-passed `undefined` guard as `null` — and `IndexManager.insertIndexEntries` stages exactly that shape for every non-unique index (`this.guardFor(...)` returns `undefined`). A replay reading `guard = null` would have thrown a `TypeError` off `.kind`. They are now truthiness checks, with a test (`reads a JSON round-tripped empty slot as "no entry" / "no guard", never as a value`) pinning both slots. I did **not** chase whether the real log encoding actually produces that `null` on any live path — `TestTransactor` uses `structuredClone`, which preserves `undefined`, so no existing test could have caught it. If a reviewer can confirm or rule out the live encoding path, that is worth knowing either way; if it is reachable, this was a latent crash rather than a hardening.

**Tripwires parked in code, not filed as tickets:**

- The falsy-entry discrimination, `NOTE:` in the handler loop in `packages/db-core/src/collections/tree/tree.ts`. An element is a delete when its entry slot is *falsy*, not when it is strictly `undefined` — deliberate, because a JSON round trip turns a delete's empty slot into `null`. The cost is that a falsy-but-real entry (`''`, `0`, `false`) would read as a delete. No entry type in this repo is falsy today, so it is conditional, not broken. I left the existing check as-is rather than "fixing" it to `!== undefined`, which would have been an actual regression.
- The `expected`-is-a-full-copy cost, `NOTE:` on `TreeUnchangedGuard` in `packages/db-core/src/collections/tree/struct.ts`. A guarded log entry roughly doubles its row bytes; the digest alternative is named there if log volume ever becomes the binding constraint. I did not measure log volume — the "roughly doubles" claim is arithmetic on the guard carrying a second copy of the entry, not a measurement.
- Non-JSON-shaped values in `structuralEquals`, `NOTE:` at the top of `packages/db-core/src/utility/structural-equals.ts`. A `Date`, `Map` or `Set` falls through to the plain-object arm and compares by own enumerable properties, so two distinct `Date`s report EQUAL. Unreachable today (entries are JSON-shaped by contract — they are serialized into the log), but it is a silently-wrong answer rather than a loud one if that ever changes.

**Gaps I know about:**

- Everything is exercised through raw `Tree`s over `TestTransactor` and `CompetingWriterTransactor`. There is no end-to-end SQL coverage because no SQL path stages an `unchanged` guard yet — that arrives with `refuse-concurrent-row-change-loser`, and the cross-layer behaviour (which statements carry it, what a client sees) is unverified until then.
- The `Uint8Array` case is pinned through `structuredClone` transport (what `TestTransactor` does) and through `structuralEquals` directly. It is **not** pinned through the real log encoding — I did not verify that a `Uint8Array` inside a guard's `expected` survives the production encode/decode as a `Uint8Array` rather than as a base64 string or an index-keyed object. If it degrades, the guard would refuse an honest write. The plugin encodes BLOBs to base64 before they reach a tree entry (`row-codec.ts`), so this may be moot for the SQL layer, but it is untested either way.
- The delete-guard runtime rejection throws a plain `Error`, not a typed one. It is a programming error rather than a concurrency refusal, so nothing should be catching it by type — but a reviewer may prefer a named class.
- `mapCommitRefusal` was read but not modified, and there is no test in the plugin package pinning that a `TreeEntryChangedError` passes through it unmapped. The db-core spec asserts the error is not a `TreeKeyTakenError`, which is the property the bridge keys on, but the bridge itself is untested against this error.
