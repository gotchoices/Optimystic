# Push-state gossip sends only when the state changed — review handoff

GitHub [#49](https://github.com/gotchoices/Optimystic/issues/49). Second of three tickets from the plan `feat-idle-cohort-gossip-costs-a-phone-little`. The first, `cohort-gossip-sends-a-frame-only-when-something-changed`, applied the same rule to the signed cohort gossip.

## What changed

`ReactivityPushStateGossipDriver` (`packages/db-p2p/src/reactivity/push-state-gossip.ts`) still ticks every 5 s and still builds every live push state's bounded (clipped) frame each round. It now sends that frame only when:

- the frame differs from the last frame this driver sent for that push state, or
- `reAdvertiseMs` has passed since that send. This is a new dep, defaulting to `DEFAULT_WILLINGNESS_HEARTBEAT_MS` (30 s), the cohort gossip's slow refresh.

Otherwise the push state is skipped for the round.

- The decision reuses `isGossipRoundDue` from `packages/db-p2p/src/cohort-topic/cohort-gossip-driver.ts` (with `hasDeltas: false`), so the two gossips follow one rule. The key it compares is the hex SHA-256 (`@noble/hashes`) of the bounded frame, so a clipped frame is compared as clipped.
- Memory is a `WeakMap<PushState, SentGossip>` holding `{ key, at }`, a 64-character digest and a timestamp. The frame bytes are never kept.
- The `clock` dep is now used (default `Date.now`).
- A `broadcastOver` that **throws** is not recorded, so the next round retries. One that returns counts as sent: per-peer failures are swallowed inside it, and the refresh covers them.
- The truncation log and `onTruncate` now fire only on rounds that send. They were split into `reportClip`; the `boundedFrame` return type became the named `BoundedFrame`.
- A `NOTE:` at the comparison names the remedy if the sender-side serialize and hash ever shows in profiles: a change counter on `PushState`.
- `libp2p-node-base.ts` needed no wiring change, since the default applies. Only its `NOTE:` on the inbound membership gate's per-frame cost was updated, because that cost is now per change or refresh, not per round.

## Convergence after a merge (inspection, plus one assertion)

I read `PushState.mergeGossip`, `ReplayBuffer.merge` and `DedupeWindow.merge` in db-core. Every field only grows, so a merge that adds nothing leaves the serialized bytes identical and two members cannot keep sending to each other:

- **Ring entries** are replaced only on a strictly newer `receivedAt` (`>`). An equal-time copy with a different payload keeps the local one on both sides, so it does not ping-pong.
- **Dedupe** is a union; a key it already holds is not re-inserted, so insertion order is unchanged.
- **`lastRevision`** takes the max.
- **`childCohorts`** is replaced only when the incoming list is strictly longer.
- **`parentCohort`** is set only when unset.

The replay serialization sorts by revision. Dedupe serializes in Map insertion order, so two members may encode the same set in different orders. That only matters to each member's comparison with its own last frame, and that order does not move unless the content does.

## Tests

- **New:** `sends a push state only when its frame changed or reAdvertiseMs has passed since its last send`. Uses an injected clock and a fake transport. The first round sends. An unchanged state 5 s later sends nothing. After a replay entry is appended, the next round sends. Nothing is sent at 29 999 ms after that send; the refresh resends at 30 000 ms, with frame bytes identical to the previous send.
- **Extended:** `replicates an origin entry …` now also checks the convergence claim. B sends once what it merged. A merges B's frame, which adds nothing, and A's next round sends nothing.
- **Adjusted:** `start() begins ticking and stop() halts further rounds` passes `reAdvertiseMs: 0`, so every round sends. Without it, the "no rounds after stop()" check would pass even with a broken `stop()`, because an unchanged state sends nothing anyway.
- All other tests are unchanged. Each live push state still sends on its first round, so their broadcast counts did not move.

## Known gaps / things for the reviewer to weigh

- **Late joiner's wait.** A member that joins the root group after a change, or misses that one frame, now waits up to `reAdvertiseMs` (30 s) to catch up, where it used to wait 5 s. The ticket accepts this. Until it catches up, a backfill that reaches that member declines and the recover transport tries the next member.
- **Two tunables not bound to the host.** `reAdvertiseMs` is not tied to the host's `cohortTopic.host.willingnessHeartbeatMs`, and the driver's `intervalMs` was never tied to the host's `gossipIntervalMs` either. An operator who tunes the cohort gossip cadence does not move the push-state cadence. I left this alone because the ticket did not ask for it; binding both in `libp2p-node-base.ts` takes one line each.
- **One push state, two coords.** The comparison memory is keyed by push state only, not by (push state, coord). In production the coord is derived from `tailIdAtJoin`, which is in the frame, so a change of coord always changes the frame. If a caller ever lists the same push state under two coords in one round, only the first successful send that round counts and the second is skipped. The existing per-collection-failure test lists one push state twice, but its first entry throws, so the second still sends.
