# Reactivity: the topic is the collection anchor; only the root moves

Third of three tickets for the maintainer's decision of 2026-10-02 (the first two, `cohort-topic-a-topics-root-can-move` and `reactivity-per-root-state-is-keyed-by-the-tail`, are complete). After this ticket a collection's reactivity topic is `H(utf8(collectionId) ‖ "reactivity")` for its whole life; its root is the current tail block's storage group at `H(tailId)` and moves when the log starts a new block; the tiers below the root are addressed by the topic and never move. `H(tailId ‖ "reactivity")` is retired. A rotation is "same topic, the root moved".

## What changed

**db-core.**

- `reactivityCollectionTopicId(collectionId)` in `packages/db-core/src/reactivity/topic-anchor.ts` replaces `reactivityTopicId`; `ReactivityTopicAnchor` and `createReactivityTopicAnchor` are deleted. `reactivityRootCoord` is unchanged.
- `packages/db-core/src/reactivity/rotation.ts`: `ReRegistrationPlan` has no `newTopicId`; `planReRegistration` / `planReRegistrationWave` no longer hash. `TailDrainGateInit` takes the collection's `topicId` (base64url) instead of a hash; `RotationRedirectV1.newTopicId` stays on the wire carrying that unchanged topic (no wire change). `detectRotation` compares against the tail the subscriber last followed (parameter renamed).
- `BLOCK_FILL_SIZE_DEFAULT` is `EntriesPerBlock` (32), imported from `chain/chain.js` directly. The `NOTE:` about the 64/32 mismatch is gone.
- `ActiveSubscription.tailIdAtAttach` → `tail` (the latest followed tail). The wire payload field `tailIdAtAttach` is unchanged: it is the tail at that registration.

**db-p2p.**

- `reactivityNotificationTopicId(n)` in `forwarder-host.ts` is now `reactivityCollectionTopicId(b64urlToBytes(n.collectionId))`, so forwarder ingest, inbound routing and local delivery all route by the collection. `markRotated` takes a `RootRotation` (`newTailId`, `effectiveAtRevision`, `topicId`); the origination manager derives the topic from the event's collection id and passes it, because a root this node never built state for has no push state to read it from.
- `ReactivitySubscriptionManager`: one per collection subscription for its life. Option `tailIdAtAttach` → `tail`; the manager holds the **latest tail it has followed** (`get tail()`), which is what `resume` sends as `latestKnownTailId`, what rotation detection compares against, and what the recover transports read per request. New `followTail(tail): Promise<boolean>` (true iff a registration landed): no registration → `register`; a handle already naming `tail` as its root key → nothing; a handle at the root (`treeTier` 0) → `register` again (the service displaces the old registration, which expires by TTL at the old root); a handle below the root → `service.moveRoot`, nothing sent. A failed re-registration throws and leaves the old registration renewing; the same condition re-fires on the next call. The stale-tree-tier concern from the ticket is recorded as a `NOTE:` on `followTail`.
- `Libp2pReactivityRecoverTransport.backfillTransport` / `resumeTransport` take a tail getter (`() => Uint8Array`), resolved per request, so a recover after a rotation targets the current root's group.
- `ReactivityCollectionWatch`: a subscription owns one manager and one registry handler, both created at the first attach (the handler is registered under the collection topic before the first `register`) and released at close. `Attachment`, `attached` / `arriving` and the handler hand-over are gone; `moveTo` builds the manager if absent, moves its contiguity head to the read revision, awaits `followTail`, and returns whether a registration landed (the re-check after a landed registration stays). `isAttached` means the manager holds a registration. Close withdraws the registration the manager holds; one that lands after close is withdrawn on landing.
- `ReactivitySubscriberRegistry`: code unchanged, keyed by the collection topic; module doc rewritten.
- `libp2p-node-base.ts`: comments only (the encoding loop, the scheduler's de-dupe key, the watch service's follow).
- Harnesses: the reactivity mesh harness derives one topic per collection; `rotateTail` moves the root key and has every live subscriber's real manager follow the new tail (`followTail`), so root-direct subscribers re-register over the real walk and a tier-1 subscriber is moved with the real `moveRoot`; the wave plans count root-direct subscribers only; an asleep subscriber follows nothing and learns of the move when it resumes. New `seedTierOneCohort(nodeIndex, collection)` seeds a willing cohort at `coord_1(P, topicId)`, and `SubscriptionHandle.registration` is now the manager's live handle (a getter). The cohort-topic mesh harness gains `setupCohortAt(mesh, coord, treeTier, participantCoord)`, which `setupTopic` now wraps.

## Known gaps and things to look at

- **Order of rebaseline and follow in `moveTo`.** The ticket listed follow then rebaseline; the code moves the manager's contiguity head to the read revision *before* the follow, so a notification arriving for the next revision during a registration is delivered rather than read as a gap. `rebaseline` only advances, so the difference is only which of the two reads a mid-registration notification as contiguous. Judge whether that is the right call.
- **The `rootKey` equality guard in `followTail` applies at every tier**, not only at the root: the watch service calls `followTail` on every tick's tail read, and without it a registration below the root would call `moveRoot` every 30 s. The real `moveRoot` is idempotent, so this is a cost saving, not a correctness point.
- **The tier-1 mesh case depends on a seeded tier-1 cohort.** `setupCohortAt` creates the engines at tree tier 1 and feeds willingness with the harness's `signedWillingness` frames, which carry `treeTier: 0`; the merge did not object. In the mock mesh the tier-1 forwarder's child link to the root probably stays `awaiting_parent` (the known mock-mesh limit noted in `cohort-topic-scale-lifecycle.spec.ts`); the case does not depend on it. The harness still models fan-out to every tracked subscriber, the tier-1 one included, so "delivery continues for all three" is the model's statement, not a live node's (backlog `feat-reactivity-notifications-reach-child-cohorts`).
- **The old root's records after a rotation** are not asserted anywhere: they are displaced at the service (no tombstone) and expire by TTL at the old root, as the prerequisite ticket documented at `startRenewal`.
- **Close during an in-flight re-registration** (as opposed to the first registration) has no unit case; the code path is the same `sub.closed` check after `followTail`, and the registration that lands is withdrawn.
- **`substrate-simulator`** still models the previous design (`blockFillSize: 64`, a whole-tree wave); the docs preface its measured block accordingly. Not changed.
- **Mixed versions** are not tested; the protocol break was accepted with the decision.
- **The drain redirect's `newTopicId`** is now informational: a receiver acts on `newTailId`. Retiring the field would be a wire change and was left alone.
