description: A lookup that goes through a secondary index now checks each row it fetched before returning it, so it can no longer hand back a row that does not actually match what was asked for. Documentation that said such a leak was harmless said so wrongly and has been rewritten.

## What changed

`executeIndexScan` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` used to fetch each index entry's row by primary key and yield it without ever asking whether that row still implied the entry it came from. The engine is entitled to trust the seek — `getBestAccessPlan` claims the matched equality filters as `handledFilters=true`, and quereus reattaches a residual predicate only for a *claimed but unconsumed* constraint — so whatever the scan yields is the answer. Four wrong answers followed from that one missing step. All four are closed.

**The verification.** Every entry is now checked against the row it resolves to, and the check is the full one: an entry is `[treeKey, primaryKey]`, the row it resolves to implies exactly one tree key (`indexEntryKey(createIndexKey(schema, row), primaryKey)`), and the two must be equal. That is `rowImpliesEntry` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts`, sitting beside `indexEntryKey`, and the integrity check's `classifyEntry` now answers its own question with the same function — so a seek and the check can no longer disagree about what an entry means. A full-entry check rather than a prefix match is what also closes the duplicate: on a seek narrower than the index, a moved row's two entries *both* prefix-match, and only one can equal its full implied key.

**The NULL guard.** A `null`/`undefined` seek arg now produces no rows, above the key framing. It has to sit above it: `indexKeyFromValues([null])` frames a perfectly valid NULL-tag key that really does find the NULL-keyed row, and the verification would not reject that row either — the entry genuinely belongs to it. Only refusing to seek is correct. Same guard, same reasoning as `executePointLookup` already carried.

**Entry-yielding scan.** `IndexManager.findEntriesIn` yields whole `IndexEntry` values over `indexValueRange(indexKey)`; `findByIndexIn` is now a projection of it, so there is still one range definition.

**Observability.** `IndexSeekProbe` gained `rejected`, printed as `rejected=` on the `index:seek` trace line between `matched=` and `node=`. It counts entries the scan produced and did not yield — row gone, or row present but not implying the entry. A healthy index rejects nothing, so nonzero means this node's tree disagrees with its table and the seek silently corrected for it. `test/trace-helpers.ts` parses the new field (`IndexSeekTrace.rejected`); every existing spec that asserts on `matched` still reads through that parser and is unaffected.

**Shared row fetch.** `readRowAt` (module scope, next to `walkDecodedRows`) is now the one "fetch the decoded row this primary key names" for both the point lookup and the index scan.

### The new spec is the thing to read first

`packages/quereus-plugin-optimystic/test/index-seek-correctness.spec.ts` pins the PROPERTY, not the four instances: for a matrix of index shapes (single-column text, single-column integer, composite `(text, integer null)`) and seek forms (literal, bound parameter, full width, partial prefix, NULL-valued), every index-routed seek must return only rows satisfying its equality predicate, must not return a primary key twice, and must return exactly the rows a full scan says match. Each shape runs twice — over a healthy index and over one deliberately left holding an entry its row moved off — and the damaged run asserts the leftover is actually there before seeking, so a patch that stopped working could not make it pass vacuously. A final case pins `rejected=0` on a healthy seek and `rejected=1` once the leftover exists.

### Negative control — this was run, not assumed

The two guards were temporarily made conditional on an env var, the package rebuilt, and the specs re-run with them off. Seven failures, one per arm, naming the exact wrong row:

- `parameter seek Token = "tok-b": returned a row that does not satisfy it — Token is "tok-z"` (moved row leaks)
- `parameter seek Token = null: returned a row that does not satisfy it — Token is null in row [Id 4]` (and the same for `Num = null` and `C = "x" and D = null`) — a wrong answer on a perfectly healthy index
- `parameter seek C = "x": returned a primary key more than once (Ids 4, 1, 2, 2)` (partial-prefix duplicate)
- `query-helpers.spec.ts`: `expected [ 3 ] to deeply equal []`

The source was then restored from a scratchpad copy and rebuilt; `grep SEEK_GUARD_OFF` over the source returns nothing, and the working tree carries only the intended changes.

### Flipped pin

`test/query-helpers.spec.ts`, "fails on an entry left behind for a value no row holds any more": the `tok-b` seek was pinned to `[3]` and is now pinned to `[]`. The sweep's `expectOrphanSeeks` was already gone — `refuse-concurrent-row-change-loser` (6.3) deleted that whole racing branch, as the ticket predicted — so there was nothing to flip there.

## Known gaps, honestly

- **The false-UNIQUE consequence is NOT fixed, deliberately.** `probeUniqueConstraint` still calls `findByIndexIn` and treats every entry in the value's range as a live collision, so a leftover entry can still make a value look taken when no row holds it. That is `bug-stale-index-entry-causes-false-unique-refusal` in `backlog/`, filed separately and out of scope here. The read path and the write-side probe now differ on purpose: the read path verifies, the probe does not. Three prose sites (the integrity-check header, the backfill NOTE, `docs/debugging.md`) name that ticket so the difference is not read as an oversight.
- **The `width === 0` branch remains unreachable and untested.** Its comment now says why — the secondary-index arm of `getBestAccessPlan` names an index only once an equality filter matched, `runQuery` sets `scanIndexName` on that path only for `args.length > 0`, and the legacy `idxNum >= 10` arm is dead because `idxNum` is hard-coded to `0` at every construction site in `@quereus/quereus/src/vtab/filter-info.ts`. Confirmed by reading, not by a test; a test would have to call `executeIndexScan` directly, past the planner.
- **The NULL guard tests `args`, not `args.slice(0, width)`.** If the planner ever handed over more constraint values than the index covers and one of the excess was NULL, the seek returns nothing. That is still the right answer under either reading (a claimed equality on NULL is UNKNOWN; an unclaimed one gets a residual filter that would reject everything anyway), but it is reasoned, not covered by a case — the modern path cannot produce that shape today, since `matchedFilterIndices` is built by iterating index columns.
- **`rejected` is only populated when the `optimystic:quereus-plugin:module` namespace is enabled**, exactly like `matched`. A production node with tracing off keeps no counter, so index damage is still invisible there until someone runs `plugin.verifyIndexes`. That is today's design for this probe, not a new hole, but it is worth knowing before treating `rejected=` as monitoring.
- **One tripwire recorded at the site** (`NOTE:` above `indexKeyOf` in `executeIndexScan`): the verification derives the row's full index key once per entry the seek produces, over a row the fetch already decoded. Small beside the tree descent, and paid only on index-routed reads; if a hot seek path shows up in a profile, the derivation is the part to narrow — a healthy entry's own tree key already carries the answer.
- **`classifyEntry`'s fast path changed shape.** It was a map lookup keyed on the tree key; it is now a row lookup by primary key plus the shared predicate. The two are equivalent because a tree key's primary-key half is recoverable (both halves are self-delimiting tuples), so only one row can imply a given key — that argument is written at the site and is worth a reviewer's eye, since it is the one place where a behaviour-preserving refactor was justified by reasoning rather than by a new test. `index-integrity-check.spec.ts`, which pins the report itself, passes unchanged.

## Documentation rewritten

Six sites said, as settled fact, that a leftover entry could never change a result set, because "Quereus re-applies the predicate". That was never true for a consumed constraint. Each now describes the check that makes the claim true, rather than being softened:

- `executeIndexScan`'s stale-entry NOTE (now the description of the verification, and it no longer credits the engine);
- the residual-filter aside inside `executePointLookup` (the "a secondary index seek keeps one" clause was false and is gone);
- the `backfillIndexTrees` NOTE that pointed at it;
- the ORPHANED bullet in `packages/quereus-plugin-optimystic/src/schema/index-integrity.ts`;
- the `verifyIndexes` doc comment in `packages/quereus-plugin-optimystic/src/plugin.ts`;
- `docs/debugging.md`, "Does an index agree with its table?" — the false-UNIQUE sentence there is real, survives this ticket, and now links its ticket rather than being deleted. The `index:seek` field list and example line gained `rejected=`.

`test/query-helpers.ts`'s two claims (the `expectIndexesIntact` parenthetical and the structural-arm bullet on `expectIndexAgreesWithScan`) were rewritten for the new reason: the structural arm is still the only arm that sees an orphan, but because the seek now skips the entry and returns nothing, so no row set can distinguish a leftover entry from no entry.

## What a reviewer should push on

- Is full-entry equality the right predicate, or does some legitimate write path produce an entry a row does not imply? The claim rests on `createIndexKey` being the one formula every staging path uses, and on `serializeIndexValue` unifying `bigint` onto the `number` branch so `5n` and `5` frame identically. `verifyIndexes` re-derives expected keys the same way and is run by every index spec, which is the continuous evidence — but it is evidence, not proof.
- A NULL in a *trailing, unconstrained* index column must still compare equal, and the composite shape's row 4 (`'x', null`) covers exactly that. Check that case reads the way it should.
- The `rejected` field's placement in the trace line is between `matched=` and `node=`; `indexSeekTraces`' regex is order-sensitive and was updated to match. Worth confirming no other consumer parses that line positionally.
