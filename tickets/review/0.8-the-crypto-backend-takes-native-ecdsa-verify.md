# The crypto backend takes native ECDSA verify — review

Requested in GitHub #59 (VoteTorrent): on a Pixel 8 emulator under Hermes, `p256.verify` took 47 ms in `@noble/curves` against 0.13 ms in OpenSSL, and `secp256k1.verify` 29 ms against 0.24 ms, paid for every signed row a schema `CHECK` constraint verifies.

## What was built

- **Two optional members on `CryptoBackend`**, `p256Verify` and `secp256k1Verify` (signature: 64-byte compact r‖s, message, 33- or 65-byte SEC 1 key → boolean). The doc comment states the contract: the member hashes the message with SHA-256 itself, and must reject high-S, r or s outside [1, n−1], and any key prefix other than 0x02/0x03 (33 bytes) or 0x04 (65 bytes). The interface doc also says why there is no ECDSA signing member (random nonce, no byte-identical check possible).
- **`snapshotBackend`** copies and binds both.
- **Dispatch**: `ecdsaVerify(member, curve, …)` reads `currentBackend()` per call and falls back to `curve.verify(…, ECDSA_VERIFY_OPTS)`; `verify`'s `'p256'` and `'secp256k1'` cases go through it. `verify`'s existing `try/catch` still turns a member's throw into `false`.
- **Noble options pinned**: `ECDSA_VERIFY_OPTS = { prehash: true, lowS: true, format: 'compact' }` (frozen), equal to noble 2.0.1's defaults — no result changes.
- **Self-check** `checkEcdsaVerify(member, curve, native)`, one function for both curves, every input an `offsetView`, vectors computed inside the function (nothing at module load): accept the valid signature under the compressed key and under the uncompressed key (exactly `true`, through `runCheck`); then reject-or-throw each of the five in `ecdsaRejections`: tampered message, high-S copy (`s → n − s`), `r = 0`, `r = n`, uncompressed key re-prefixed hybrid (`0x06 | (y & 1)`). Refusal text names member and vector, e.g. `setCryptoBackend: p256Verify accepted a high-S signature, which @noble/curves rejects; the backend was not installed`.
- The Ed25519 check's tampered-message construction was pulled into `tamperedCheckMessage()`, shared with the ECDSA vectors.

## Deviations from the plan, and why

- **The self-check does not call noble's verify for reference answers.** The plan said "use the same options object in the self-check's reference calls". The vectors' expected answers are written down (accept / reject) rather than asked of noble, because noble's verify costs ~30–47 ms a call under Hermes and the self-check runs at app start: seven reference verifies per curve would add about half a second. The only noble calls in the check are `sign` (with `{ lowS: true }`, as SQL `sign` passes) and `getPublicKey`, both cheap. The comment on `checkEcdsaVerify` records this; the comment on `ECDSA_VERIFY_OPTS` says the vectors encode those options. I confirmed by a scratch run (Node 24.2.0, OpenSSL 3) that noble under `ECDSA_VERIFY_OPTS` gives exactly the written-down answer on all seven vectors for both curves, and that a bare OpenSSL member diverges on exactly the high-S and hybrid vectors — the planning table reproduced.
- **`import type { ECDSA, ECDSAVerifyOpts } from '@noble/curves/abstract/weierstrass.js'`** was added. It is type-only, erased under `verbatimModuleSyntax`; `dist/plugin.js`'s import list is unchanged and contains none of the self-check (`checkEcdsaVerify` appears 0 times in `dist/plugin.js`). No runtime import was added for the self-check.

## Tests (in `test/crypto-backend.spec.ts`; no new spec file)

- `nodeBackend()` now includes `p256Verify` and `secp256k1Verify`, built as `guardedEcdsaVerify(curve)` = key-prefix guard ∧ scalar-range guard ∧ `openSslEcdsaVerify(curve)` (SPKI-wrapped `node:crypto` verify with `dsaEncoding: 'ieee-p1363'`), counting calls like the other members.
- `evaluate()` now signs through SQL `sign` with each of ed25519, p256 and secp256k1 and verifies through SQL `verify` the valid signature, a tampered message and, for the ECDSA curves, the high-S copy. **First test** ("byte-identical … and is actually used") asserts valid/tampered/high-S answers without a backend, then deep-equal results with the backend, then that every member was called (now via `expectEveryMemberCalled`). The plugin is still registered from `dist/plugin.js` before the backend is set through `dist/index.js`, so the per-call dispatch of the new members across the two bundles is covered.
- **Refusal test** gains two adapter mistakes, each caught by a different vector: bare OpenSSL `p256Verify` must throw `/p256Verify accepted a high-S/`; `secp256k1Verify` with the scalar guard but no prefix guard must throw `/secp256k1Verify accepted a hybrid-encoded/`. Afterwards the previously installed backend must still be the one used — now asserted for every member, not only sha256 and ed25519Sign.
- No per-vector tests and no test of the option pinning, per the plan.

## Validation run

- Package: `yarn build`, `yarn typecheck`, `yarn test` — 128 passing.
- Root: `yarn lint:docs` (all citations resolve), `npx eslint packages/quereus-plugin-crypto` (clean), `yarn check:rn` (Metro bundle + hermesc compile passed).
- The README's Node adapter block was extracted and run against the built package: `setCryptoBackend` accepted it, and p256 / secp256k1 / ed25519 each verified the valid signature and rejected a changed message.

## Things for the reviewer to look at

- **`react-native-quick-crypto` is unconfirmed.** Neither the SPKI key wrapping nor `dsaEncoding: 'ieee-p1363'` was exercised on a device or under its implementation; the README says so and relies on the self-check to fail loudly at startup if it differs. The issue's reporter measured RNQC p256 at 0.13 ms, so the call exists, but its accepted options are not verified here.
- **Inputs the self-check does not cover** (contract only, as the plan decided): DER signatures, wrong-length signatures, a point not on the curve, the point at infinity. noble and OpenSSL both reject all of these; another native library might not.
- **Doc wording**: README §Native crypto backend has a new "ECDSA verify must match `@noble`'s rules" bullet, an extended "Checked when set" bullet, the Pixel 8 numbers in the intro, and the extended Node adapter (`ecdsaVerify(curve)`). `docs/crypto.md` names `checkEcdsaVerify` and `ECDSA_VERIFY_OPTS`. CHANGELOG entry is headed **Unreleased** for the releaser to rename.
- The test's `highS` field is `undefined` for ed25519 in `evaluate()`; `deep.equal` treats both runs the same, but the shape is slightly irregular.
