## What changed

One behavioural edit, in `updateInternal` (`packages/db-core/src/collection/collection.ts`). It used to re-stage its pending actions against the freshly adopted revision only when a **block conflict** was detected — a conflict meaning an incoming log entry names a block this instance's tracker already holds a transform for. An action that changed no block holds no transform, so it never conflicts, so it was never replayed; the commit then wrote a log entry listing that action while the transforms it carried did nothing. Readers materialize blocks, not log entries, so the action vanished on every node.

The gate is now "a conflict was found, **or** the refresh adopted a newer revision and something is still pending":

```ts
const adoptedRev = this.source.actionContext?.rev;
const contextAdvanced = adoptedRev !== undefined && adoptedRev !== actionContext?.rev;
if (anyConflicts || (contextAdvanced && this.pending.length > 0)) {
	await this.replayActions();
}
```

`replayActions` already resets the tracker and re-stages under the collection latch, so nothing new was built — only the condition widened. The invariant it now enforces, stated in the comment at the site and in the docs: **a pending action was applied against the revision it commits over.**

Everything else is tests, comments and documentation:

- `packages/db-core/test/two-handle-collection-fork.spec.ts` — new `describe('a pending action that changed no block')` with one case, the white-box regression test.
- `packages/quereus-plugin-optimystic/test/concurrent-row-change-refusal.spec.ts` — `twoHandles` gained a `seedThrough: 'alternate' | 'a'` parameter (default `alternate`, so every existing case is unchanged), and one new case uses `'a'`. The paragraph in the `twoHandles` doc comment that named this ticket as a defect to sidestep is gone, replaced by a description of what the parameter does and why the alternating default exists.
- `packages/quereus-plugin-optimystic/src/schema/index-manager.ts` — two `NOTE:` comments, at `deleteIndexEntries` and at the `[oldTreeKey, undefined]` element in `updateIndexEntries`, saying the blind delete is deliberate and naming the db-core site its correctness rests on. No code change; see "The refresh that was not added" below.
- `docs/internals.md` — a paragraph in [§Conflict replay must read at the revision it is adopting, not the one it is leaving](docs/internals.md#conflict-replay-must-read-at-the-revision-it-is-adopting-not-the-one-it-is-leaving) covering **when** the replay fires, which that section previously did not say.

## The refresh that was not added — a deliberate decline

The originating fix ticket asked for a `get` on the index tree before staging in `deleteIndexEntries`, to pull the leaf in. The implement ticket had already measured that reasoning to be wrong (a read creates no transform, and it reads at the same stale context the staging does) and recommended against the working alternative, `await tree.update()`. **That recommendation was followed: no refresh was added.** It costs a refresh per maintained index per deleted row, and it only narrows the window rather than closing it — an entry a rival commits between that `update()` and the sync is blind again. The db-core rule closes the whole class, so the refresh would buy nothing. The two `NOTE:` comments are what records that decision at the code sites.

## What to hit hardest in review

**The gate's condition, not the replay itself.** `contextAdvanced` compares `this.source.actionContext?.rev` *after* `advanceContext` against the `actionContext` captured before the refresh. `advanceContext` is monotonic (it refuses to lower), so "different" does mean "advanced" — but that is an inference from another method's contract, and it is the load-bearing one. Worth checking whether any path can leave `source.actionContext` changed in identity but equal in `rev` in a way that matters, or the reverse.

**The guards are the one behavioural surface that genuinely moved.** A replay that did not previously happen now re-runs `enforceUpsertGuard` and `assertEntryUnchanged` against the newly adopted state. [docs/internals.md §Conflict replay re-makes the uniqueness decision (entry guards)](docs/internals.md#conflict-replay-re-makes-the-uniqueness-decision-entry-guards) says that is what *should* happen on every replay, and `packages/db-core/test/tree-guard.spec.ts` plus the whole refusal spec pass — so the reading is that the gate caught up with documented intent rather than changing it. That reading is the thing to attack. A guarded action that was previously carried to commit un-replayed and is now refused earlier would be a behaviour change no test in either suite happens to cover.

**Whether `pending.length > 0` is the right second conjunct.** It skips the replay for a pure reader, which is the intent (a reader has nothing to re-stage and the tracker reset would be wasted work). Check it cannot skip a case where the tracker holds transforms but `pending` is empty — `consumeOwnEntry` is the path that drains `pending` while the tracker still holds the consumed action's transforms, and it sets `mutated` unconditionally precisely so the replay still fires via `anyConflicts`. That coupling is worth re-reading.

## Known gaps — where the tests are a floor, not a ceiling

- **`updateIndexEntries`' old-entry delete is not reproduced.** The implement ticket identified it as the same class, masked in small trees because the sibling upsert writes a block that forces a replay when old and new entries share a leaf. Demonstrating it needs a multi-level index tree with the two keys in different leaves. It is closed by the same db-core change and it now carries a `NOTE:`, but **nothing tests it**. If a reviewer wants one more test, that is the highest-value one to add.
- **The db-core test is one shape, not a property test over shapes.** The implement ticket called it "the property test for the invariant"; what landed is a single deterministic case (create, open, commit, blind delete, read through a third handle). It pins the exact regression and the control proved it discriminates, but it does not sweep the space of actions-that-change-no-block. Whether there are other such actions beyond a missed delete was not enumerated.
- **The `catch` fallback in `deleteSchema` (`packages/quereus-plugin-optimystic/src/schema/schema-manager.ts`)** stages a bare `[tableName, undefined]` after a failed read, which is blind in the same way. The implement ticket identified it; it is closed by the db-core change but got no `NOTE:` and no test, because it is a failure-path fallback and reaching it deliberately was out of scope.
- **`Tree.open` for the second handle is load-bearing in the db-core test and fragile to future edits.** Building both handles with `createOrOpen` does not reproduce — the second call stages its own header/root, which conflicts and masks the defect. That is stated in the test's doc comment, but nothing enforces it: someone "tidying" the test to use the shared `openHandle` helper would turn it into a test that passes for the wrong reason. The control run is the only thing that would catch that, and it is not automated.
- **The intermittent 3-failure plugin run the implement ticket warned about did not appear** across four full plugin suite runs here (three patched, one control). No `tickets/.pre-existing-error.md` was written; nothing unrelated failed. That is absence of evidence, not evidence of absence — it was intermittent before and may still be.
