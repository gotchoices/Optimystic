## What was built

**The gates** (`insertAcceptsEqualRow` and `rewriteAcceptsEqualRow` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/write-description.ts`): pure over Quereus's `TableWrite` and the arm. An INSERT at a clear key admits `absentOrEqual` when the disposition is `ignore`, `replace`, or an upsert with a `do nothing` clause whose target is `'primary-key'` or the primary-key columns as a lowercased set. A rewrite (same-key UPDATE on the `update` arm, INSERT OR REPLACE over an occupied key on the `insert` arm) admits `unchangedOrEqual` when the description is of that arm and `selfIndependent`. No description, or a description of another operation (the upsert `DO UPDATE` arm receives the INSERT's), answers false.

**The staging sites** (`update()` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`): `insertGuard` chooses `absentOrEqual` when the gate holds OR the table is tagged `"optimystic.content_key" = true` (new tag, `CONTENT_KEY_TAG`, read `=== true` at staging beside `optimystic.single_writer`); `rewriteGuard` chooses `unchangedOrEqual` or `unchanged` for the same-key UPDATE and the INSERT OR REPLACE over an occupied key; the DELETE and each secondary-UNIQUE eviction's delete (`applyUniqueEvictions`) always carry `unchangedOrAbsent`; both halves of a primary-key move keep their base kinds. Two helpers beside `unchanged` build the variants. The "guard refusal at INITIAL staging" note beside the DML catch now also records that the acceptance can be met there. `recordWriteFacts` shares the primary-key column names with the gate through `primaryKeyColumnNames`.

**The effect**: `QueuedTransactionStatus`'s `committed` arm is `{ kind: 'committed'; effect: CommittedEffect } & SqlCommitDurability` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-status.ts`); `OfflineMode.committed` passes the queue's `effect` through; the journal's `PersistedOutcome` carries `effect?` and `decodeOutcome` answers `'applied'` for a record without it. The `onCommitDurability` report is unchanged.

**The outlook** (`packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-outlook.ts`): `CollectionJudge` judges `absentOrEqual` as `absent` and the two `unchanged` variants as `unchanged`; the cover rule counts all five exact-key kinds; `writtenKeysIn` counts an `absentOrEqual` insert among `insertedAbsent`; `Exposure` gains `tolerates?: 'same-change'`, set on every exposure a variant produces, and `renderCommitOutlook` includes it when present.

## Behaviour change outside offline mode, deliberately

The variants are a property of the statement, not of the mode, and session mode stages through the same `update()`. So an ONLINE racing identical write now commits where it refused: two transactions deleting one row both commit, the second's delete skipped as already applied. Two existing tests pinned the old behaviour and were changed to pin the new one, which the ticket's "keep green" instruction could not be met without: the DELETE-vs-DELETE case of `packages/quereus-plugin-optimystic/test/concurrent-row-change-refusal.spec.ts` (now asserts both commit and the index is clean), and the racing oracle of `packages/quereus-plugin-optimystic/test/two-node-index-mutation-sweep.spec.ts` (`refusesSecond`: a delete-vs-delete race no longer refuses the second committer; the two updates write different tokens and still refuse). Every other same-row race still refuses, since the rivals' changes differ. Two outlook expectations in `packages/quereus-plugin-optimystic/test/offline-outlook.spec.ts` gained `tolerates: 'same-change'` for literal updates, which are self-independent.

## Known gaps for the reviewer

- **By inspection only**: the INSERT OR REPLACE over an occupied key under `unchangedOrEqual` (its displaced-image index deletes finding nothing when the rival made the same replace), and an eviction's delete accepted when the evicted row is already gone. Both are stated at their sites; neither has an end-to-end case.
- **The gate's `do nothing` target for a composite key** is compared as a set of column names; a clause naming a UNIQUE constraint whose columns happen to equal the primary key's would also pass, which is correct, since the conflict is then at the key.
- **`absentOrEqual` under `or replace`** accepts only an equal row; a rival's different row refuses with the constraint error as before, and the sequential retry replaces. The ticket's table asked for exactly this, but it means `insert or replace` of a changed row over a rival's write still fails offline rather than winning, which an application may not expect from "replace".
- **The two tag-table README rows and the design doc's test-plan sentence** say stage 10 is fully pinned; the two inspection-only cases above are the residue.
- **No tripwire NOTE was added**; the outlook's existing linear-scan note still covers the only cost that grew (one more set membership test per element).
