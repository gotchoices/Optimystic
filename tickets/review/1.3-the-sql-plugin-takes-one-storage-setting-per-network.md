# The SQL plugin takes one storage setting per network

## What landed

`OptimysticOptions.rawStorageFactory` (`() => IRawStorage`) and `OptimysticOptions.blobStorageFactory` (`() => { pieces, kv }`) are gone. In their place is one field, on `OptimysticOptions` and on `ParsedOptimysticOptions`:

```ts
storageFactory?: () => NodeStorage;   // NodeStorage from @optimystic/db-p2p: { blocks, kv, pieces }
```

It is read by the aux-option reader (`resolveBinding` in `optimystic-module.ts`) under the same `typeof === 'function'` guard, so it is still `register()`-only and cannot be carried by a `USING` clause. The schema-manager fingerprint folds `tableOptions.storageFactory ? '1' : '0'` where it folded the raw one.

`CollectionFactory` resolves it **once per transactor key** into a new private map, `storages`, and all three consumers read from there:

- `createLocalTransactor` wraps `storageFor(options)?.blocks` in `withReadCache`, with the same lease-ownership rule as before.
- `resolveBlobBackend`'s single-machine arm passes the resolved value straight to `SingleMachineBlobService`, which reads `pieces` and `kv` off it.
- `createNetworkTransactor` passes it as `NodeOptions.storage` to its `createLibp2pNode` call. **This is the new capability**: the plugin's own node now keeps its blocks, blob pieces and blob records where the host says, so a pin survives a restart without the host building and registering a node by hand. The superseded `NOTE:` saying it could not is gone.

`storageFor` returns `NodeStorage | undefined` rather than manufacturing a memory default. That is deliberate and is the one subtlety worth checking: the node's missing-storage `node-wiring` `WARN:` tests the *presence of the option*, so a default built inside the plugin would have silenced it and made the memory case look intended.

## How to validate it

**The capability that is new** — a `network` transactor's own node writing to host storage. Register with `default_transactor: 'network'` and a `storageFactory` returning a `NodeStorage` whose `pieces` store counts its `put`s, then `await plugin.blobs.put(bytes)`. The host's piece store must see the put, and the backend's service must be a `NodeBlobService` — not a `SingleMachineBlobService`, which would mean the node carried no blob service and the single-machine arm served it. That arm now reads the same `pieces`, so a check that only counted puts would not tell the two apart. Done by hand during implementation and it passed: one piece put, `service = NodeBlobService`. **No shipped test covers it** — see Gaps.

**Called once per network.** `test/local-transactor-storage.spec.ts` has a new case: one plugin, two tables and two blob services on one transactor key, and the factory must be called exactly once. Without the memo it is called twice — once by `createLocalTransactor`, once by `resolveBlobBackend` — so the case discriminates.

**The restart path.** `test/blob-pins-*.spec.ts` are the suite that matters most here: they open a plugin over shared stores, close it, open another, and read back the pins the first wrote. `blob-pins-harness.ts`'s `BlobPinStores` now holds one `NodeStorage` instead of a `MemoryRawStorage` plus a separate pieces-and-records pair, and every handle's `storageFactory` returns that same value — which is what still makes a second handle a restart rather than a fresh machine.

**Host usage, for a reader checking that the docs match the code.**

```ts
const storage = fileNodeStorage(dir);   // one set of stores per directory; you opened it, you close it
const plugin = register(db, { default_transactor: 'local', storageFactory: () => storage });
// ...
db.close();
await plugin.dispose();      // releases only the read-cache lease; closes no store
await storage.close();
```

A host that wants durable blobs over a throwaway block store — what `blobStorageFactory` alone used to express — builds `{ blocks: new MemoryRawStorage(), kv: durableKv, pieces: durablePieces }`. Nothing refuses any combination; the README names the mixtures that bite.

## Gaps and judgement calls to review

**The node arm has no shipped test.** It was verified by hand only, as described above. If the reviewer wants coverage, the cheapest honest shape is a `network`-transactor spec that puts a blob through `plugin.blobs` and asserts both that the host's piece store received it and that the resolved backend's service is a `NodeBlobService`. It builds a real in-process libp2p node and ran in about 120 ms when done by hand. The ticket argued against a test here as wiring; the hand check showed that framing is slightly off, because the single-machine arm now reads the same `pieces` and a naive assertion cannot distinguish the two arms.

**The roughly twenty `FileRawStorage(dir)` specs keep memory blob stores; they were not moved to `fileNodeStorage(dir)`.** A new test helper, `test/storage-helpers.ts`, exports `blocksOnly(blocks)`, which returns `{ blocks, kv: new MemoryKVStore(), pieces: new MemoryPieceStore() }`, and every such site became `storageFactory: () => blocksOnly(new FileRawStorage(dir))`. That is behaviour-identical to what those specs ran on before: block store on disk, blob stores in memory and unused. The ticket's edge-case note anticipated `fileNodeStorage(dir)` instead. It was rejected because `fileNodeStorage` hands a *second* caller over one directory the same `FileRawStorage` instance, and several of these specs register two plugins over one directory precisely to get two independent write groups, or a reopen that reads what the first flushed — `legacy-commit-atomicity`'s `createDbPlain`, `committed-read-isolation`, `concurrent-insert-refusal`. Converting them would have made those assertions pass more easily while testing something else. If the reviewer disagrees, the change is mechanical but should be made one spec at a time with each one's premise re-read.

**`storages` outlives `dispose()`, by design, and that is a visible change.** Before, a transactor rebuilt after `dispose()` called the host's factory again; now it reuses the storage. So a stray statement after a host has both disposed the plugin and closed its stores reaches a *closed* store, where it used to silently reopen one behind the host's back. Both are host-lifecycle errors and the closed store is the louder of the two. Parked as a `NOTE:` at the `storages` declaration in `collection-factory.ts`. `dispose()`'s own doc comment was corrected — it claimed the factory is invoked again.

**Transactor key versus node key is unchanged, and still wrong in the same way.** Storage is keyed by `<transactor>:<keyNetwork>`; the node by `<networkName>:<port>`. Two transactor keys that resolve to one node key build the node once and it keeps whichever key's storage built it — exactly as it already keeps whichever key's `libp2pOptions` built it. Stated in a `NOTE:` where the map is declared; it is an arm on backlog `debt-a-networks-storage-is-taken-from-one-collections-options`, not this ticket's to fix.

**The backlog ticket was refreshed, not just armed.** `tickets/backlog/debt-a-networks-storage-is-taken-from-one-collections-options.md` had its arm written at plan time, but its `NetworkOptions` sketch and surrounding prose still named the two old fields, which would have had the next agent copy a dead API. Those mentions now read `storageFactory`, and the arm says the narrowing landed.

**Out of scope and deliberately untouched.** `MeshOptions.rawStorageFactory` (`packages/db-p2p/src/testing/mesh-harness.ts`) is a different option that takes a node index, and it stays — `test/mesh-node-harness.ts`, `test/offline-restore.spec.ts`, `test/two-node-lagging-replica-multi-collection-commit.spec.ts` and `test/cold-apply-cost.spec.ts` all use *that* one. The ticket listed `cold-apply-cost.spec.ts` among the plugin's callers; reading it showed it calls `createMesh`, so it was left alone. `.release-notes.pending.md` mentions `rawStorageFactory` inside the already-written v1.27.0 section; that is a historical record and was left as published.
