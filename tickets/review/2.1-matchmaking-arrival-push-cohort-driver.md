# Matchmaking arrival push — the cohort member that sends pushes (review)

Second of five tickets (chain in `matchmaking-arrival-push-wire-and-selection`). This is the sending side only. Nothing constructs the driver or subscribes it yet: node wiring, the libp2p `send` binding, the mesh end-to-end test and the design-doc updates are `matchmaking-arrival-push-wiring-and-e2e`.

## What landed

**The trigger (db-core).** `observeRecordAdditions(store, onAdded)` in `packages/db-core/src/cohort-topic/registration/store.ts` wraps a `RegistrationStore`. Its `put` checks `getByParticipant` first and calls `onAdded(rec)` after the write only when the record was absent. Every other method delegates. A listener throw is caught and logged under `cohort-topic:registration`, never propagated into `put`. It has no matchmaking knowledge.

**The host seam (db-p2p).** `createCoordEngine` builds its store as `observeRecordAdditions(createRegistrationStore(), rec => ctx.recordAdded(coordEngine, rec))`, so admission (`CohortMemberEngine.accept`), gossip merge (`mergeRecords`) and the handoff pull all reach it. `coordEngine` is the object the function now returns by name; the closure refers to it before its declaration, which is safe because no record is written during construction. `CohortTopicHost.onRecordAdded(listener)` adds to a node-level `Set`, returns an idempotent unsubscribe (the `StorageRepo.onAnyCollectionChange` shape), isolates and logs each listener's throw, and `host.stop()` clears the set.

**The driver.** `ArrivalPushDriver` in `packages/db-p2p/src/matchmaking/arrival-push-driver.ts`, independent of libp2p. On a record added:

1. Decode it. Not a matchmaking provider → return.
2. Decode the topic's push-opted seekers from `engine.records(topicId)`.
3. Drop this `(servedCoord, topic)` scope's bindings whose seeker record is gone or carries another correlation id.
4. `selectArrivalPushTargets`, then keep the seekers whose `slots.assignSlots(...).primary` (current cohort view) is this node.
5. Queue `providerEntryOf(provider)` into each kept seeker's binding unless the binding is dead, satisfied, or already holds that provider.

Flush happens when the `coalesceMs` timer fires, at once when the queued entries cover `wantCount`, or when the batch reaches `QUERY_LIMIT_MAX`. A flush re-checks `engine.heldRecord` for the seeker with the same correlation id and skips the send if the record is gone. The push is signed over `arrivalPushSigningPayload` with the epoch and traffic read at flush, and sent without being awaited. An `unknown_seeker` ack marks the binding dead. No reply, an undecodable ack, or a throw from signing or sending drops the batch, logged under `matchmaking:arrival-push`. The driver never calls `recordQuery`. Bindings are capped at `maxBindings` (default 4096), with least-recently-touched eviction; the `NOTE:` tripwire sits at the cap. `stop()` cancels every timer and drops all state.

**Protocol id.** `arrivalPush` (`/optimystic/matchmaking/1.0.0/arrival-push`, namespaced form in `makeMatchmakingProtocols`) is in `matchmakingProtocolList`. Node teardown already unhandles that list, which is a no-op for this id until the wiring ticket registers a handler.

## Decisions that differ from, or go past, the ticket — check these

- **A lost push leaves `pushed`.** When a batch is dropped, its providers are removed from the binding's `pushed` set. The ticket says "the binding stays live: the next arrival tries again". If `pushed` kept them, a lost push covering the whole `wantCount` would leave the binding satisfied, and no later arrival would ever be pushed to that seeker. Failed providers are still not replayed.
- **No `clock` dependency.** The ticket's sketch listed `clock?`. Nothing needs time: least-recently-touched order is `Map` insertion order. It was left out rather than kept unused.
- **`heldRecord` is part of the narrow engine type.** `ArrivalPushEngine = Pick<CoordEngine, "servedCoord" | "cohort" | "records" | "heldRecord" | "topicTraffic">`. The flush check looks up one seeker in constant time instead of listing the topic.
- **Arrival decode is silent; topic reads log.** Every cohort-topic application's records go through `onRecordAdded`, reactivity's included. Logging each non-matchmaking arrival as "undecodable" would be wrong and noisy, so the arriving record is decoded without a logger. The seeker pass and the flush check do log. A malformed provider record is therefore not logged by the driver on arrival; the query handler logs it whenever its topic is queried.
- **Decoded-registration cache.** A `WeakMap` keyed by record object holds successful decodes only. A member catching up on a topic receives its records one at a time, and without the cache each arrival would re-parse every record in the topic. It is never stale because every store write puts a new record object (checked: `accept`, `mergeRecords`, renewal touch and restamp, handoff).
- **`onRecordAdded` is an arrow-function property**, so the wiring ticket can pass `driver.onRecordAdded` unbound, as its text does.
- **`maxBindings < 1` throws `RangeError`.** A cap of 0 would orphan the binding just created, leaving its timer outside `stop()`'s reach.
- **The record decoding is now a shared helper**, `decodeLocalRegistration` in the new `local-registration.ts`, returning `{ role: "provider" | "seeker", registration }`. The query handler's behaviour is unchanged: same skip, still one log line per undecodable record. The log text changed from "matchmaking query handler: skipping…" to "matchmaking: skipping…".

## Tests added (`packages/db-p2p/test/matchmaking/arrival-push-driver.spec.ts`)

The fake engine is a real `createRegistrationStore` behind `observeRecordAdditions`, with a fixed cohort view, constant traffic, manual timers and a recording `send` that decodes the push and answers an ack.

- *A renewal of a held provider is not an arrival.* Exactly one push in total, no timer armed by the renewal, and the observer reported only the seeker and the provider's first put. The `added` assertion is what pins the decorator: the binding's `pushed` set alone would also block a second push.
- *Coalescing.* Three providers inside the window produce one push carrying all three, with the correlation id and traffic. A `wantCount = 1` seeker is pushed with no timer fired.
- *Only the slot primary pushes.* Two members, six seekers. Each seeker is pushed exactly once across both drivers, and each push came from that seeker's computed primary.
- *`unknown_seeker`.* After the stale ack, the next arrival arms nothing. Once the seeker's record carries a new correlation id, the next arrival is pushed under it.

Mutation check: forcing every member to count as primary, ignoring `unknown_seeker`, and removing the cover-the-need flush each fail exactly one of these tests. No test for the listener-throw catch (the ticket marked it inspection-only).

## Known gaps and things for the reviewer

- **Docs are deferred to `matchmaking-arrival-push-wiring-and-e2e`.** That ticket explicitly owns the `docs/matchmaking.md` *Implemented* callout, `docs/internals.md` §Matchmaking subsystem, and `docs/cohort-topic.md` §Application policies (naming `CohortTopicHost.onRecordAdded`). Only `docs/debugging.md` changed here, because its guard test requires it. Its claim "`db-p2p` emits 46 sub-namespaces" was already stale (51 rows); it now says 52.
- **Per-arrival cost.** Each provider arrival lists the topic's records and calls `engine.cohort()` once (a FRET assembly on a default engine), plus once more per flush. Unmeasured. The decode cache removes the parsing; the listing is the same cost the query handler pays per query.
- **Binding scope uses `servedCoord`.** Engines holding records are never evicted, so a binding's engine stays the same object while it matters. `binding.engine` is still refreshed on every queue, in case a coord's engine is recreated.
