# What changed

Hermes, React Native's JavaScript engine, has no `TextDecoder` and no `structuredClone`. A `new TextDecoder()` at module scope runs while the module is being *imported*. So on a runtime whose polyfill is not installed yet, `import '@optimystic/db-p2p/rn'` threw before the importing app could run anything.

## Scope grew beyond the ticket's file list, deliberately

The ticket named only `raw-store-codec.ts`. I ran a probe (described under Tests) that loads the RN entry and records every first-party `TextDecoder` built during the load. It found six sites on that load path, not one:

- db-p2p: `storage/raw-store-codec.ts` and `cohort-topic/peer-codec.ts`.
- db-core: `cohort-topic/wire/codec.ts`, `cohort-topic/antidos/bootstrap-evidence-envelope.ts`, `matchmaking/wire.ts`, `reactivity/wire.ts`.

db-core loads as part of the RN entry, so fixing only db-p2p would have left the import still throwing because of first-party code. I fixed all six.

I also fixed the same pattern in `db-p2p-storage-rn` (`keys.ts`, `leveldb-kv-store.ts`), the phone storage backend. It is not on db-p2p's load path, but phones import it directly.

`db-p2p-storage-fs/file-storage.ts` runs only on Node, so it never had the problem. I changed it anyway so the new lint rule needs no per-package exemption. That is the only reason for that change.

## The pattern

Every site now looks the same:

```ts
let utf8DecoderInstance: TextDecoder | undefined;
const utf8Decoder = (): TextDecoder => utf8DecoderInstance ??= new TextDecoder("utf-8", { fatal: true });
```

It is memoized, so each module still shares one decoder, as the old module-scope singleton did. The decode options are unchanged: the fatal decoders stay fatal and the plain ones stay plain.

In the four db-core parsers, the old code decoded inside a `try` whose `catch` turned any error into "not valid UTF-8" or "not offered". I moved the `utf8Decoder()` call **above** the `try`, so a missing polyfill throws as itself instead of looking like bad input. `parseBootstrapEvidenceEnvelope`'s doc said it "never throws"; I reworded it to "never throws on its input" and noted the polyfill exception.

## Deliberately not done

- **`TextEncoder` stays at module scope everywhere**, including in `raw-store-codec.ts`, even though the ticket asked for "encoder/decoder lazily". The readme already lists `TextEncoder` as built into Hermes, and db-core builds it at module scope in about a dozen modules. Making it lazy would be churn for no gain. The comment at the codec site says so.
- **`peer-codec.ts` callers are not restructured.** `verifyPeerSig` (`cohort-topic/peer-sig.ts:72`) calls `bytesToPeerIdString` inside a catch-all `try` that returns `false`. With no polyfill it now reports "bad signature" rather than the import failing. I could not hoist that call without changing how invalid UTF-8 is handled. It is effectively unreachable, because a host with no `TextDecoder` already fails at startup inside multiformats. The reviewer may disagree.

## `structuredClone` in `storage-repo.ts` (`previewCommitDigest`)

I replaced it with `cloneDecoded`, a new function in `raw-store-codec.ts`: a JSON round-trip that passes `undefined` through. That pass-through matters because the base block is `undefined` for a block with no content yet, and `JSON.parse(JSON.stringify(undefined))` throws.

**Why the JSON round-trip loses nothing here:** both values were just decoded from JSON by the store. Every `IRawStorage` in this repo is `KvRawStorage` over `raw-store-codec`, and the read caches hold bytes, not decoded objects. The values therefore contain nothing a JSON round-trip drops or rewrites. `internalCommit` applies the transform to the same freshly decoded objects without cloning, so preview and commit still agree.

**Tripwire (NOTE at the call site):** suppose someone wires in an `IRawStorage` that hands out live objects that were never serialized. The preview could then drift from the commit. The concrete case: an update that sets a field to `undefined` clones to `null`, and canonical JSON hashes `null` differently from an omitted field.

**Limit:** the preview of an *update* still reaches db-core's `applyOperation`, which calls `structuredClone` itself. This change removes db-p2p's own call only. The polyfill is still required, and the readme now says so.

## Lint rule: `NO_MODULE_SCOPE_TEXT_DECODER`

Selector: `NewExpression[callee.name='TextDecoder']:not(:function NewExpression, PropertyDefinition[static=false] > NewExpression)`.

- **Flags:** module-scope construction, construction nested in a module-scope object literal, and `static` class fields.
- **Allows:** construction inside any function or arrow, and per-instance class fields.

I checked it on a scratch file with all of those shapes: exactly the three expected lines were flagged. I also linted the pre-fix versions of `raw-store-codec.ts`, `reactivity/wire.ts` and `storage-rn/keys.ts` via `git show HEAD:… | eslint --stdin`: each fails. `yarn lint` is clean on the current tree.

**Known holes:** `new globalThis.TextDecoder()`, an aliased constructor, and an immediately-invoked function at module scope all pass the rule. The runtime test below still catches all three, but only for modules on the RN entry's load path.

The existing NOTE in `eslint.config.js` listing unbanned globals was reworded to match.

# Tests

**`test/module-load-globals.spec.ts`** is the regression test the ticket asked for.

- **Why a child process:** it spawns `node --import ./register.mjs test/support/module-load-globals-probe.ts`. It has to be a fresh process, because inside mocha every module was already loaded by another spec.
- **Wrap, don't delete:** the probe wraps `TextDecoder` and `structuredClone` so each use is recorded with its calling file, then delegates to Node's real implementation. The ticket suggested deleting the globals, but then multiformats and cborg throw first, at their own module load, and the run says nothing about our code.
- **Sequence:** the probe loads `src/rn.ts`, then makes one direct use of each global from the probe file itself (a calibration step), then exercises the codec.

Assertions:

- **The probe is not vacuous:** the calibration step shows exactly one use of each global, attributed to the probe file.
- **Nothing first-party during the load:** no first-party `TextDecoder` construction and no first-party `structuredClone` call. "First-party" means under this repo and outside `node_modules`, which covers db-p2p `src` and db-core `dist`.
- **Lazy and memoized:** three `decodeJson` calls plus one `decodeActionId` produce exactly one construction, from `raw-store-codec.ts`, and the values round-trip.
- **`cloneDecoded` unit cases:** an independent deep copy, `undefined` passes through, and it never calls `structuredClone`.

**Mutation-checked:**

- I put `new TextDecoder()` back at module scope in `peer-codec.ts` and `raw-store-codec.ts`. The "no first-party construction during load" case failed and named both files, and the "exactly one construction" case also failed. Restored afterwards.
- Before any fix, the same probe listed all six sites.

**`storage-repo.spec.ts`:** new case `previews without calling structuredClone (Hermes lacks it)`. It pends an insert, swaps `globalThis.structuredClone` for a function that throws, runs the preview, and checks the digest matches what the commit stores. With the old `structuredClone` line restored it fails with "structuredClone called on the preview path".

**Cost:** the probe adds about 5–10 seconds to the db-p2p suite, for one ts-node load of the whole entry graph. The timeout is set to 180 seconds.

# Known gaps for the reviewer

- **Not verified on a device.** Nothing here was run on Hermes. The probe runs under Node's package conditions, which changes which *third-party* builds load but not which first-party modules do.
- **This does not make the package self-sufficient on a bare phone.** multiformats and cborg still build `TextDecoder` at their own module load, and db-core still calls `structuredClone` on ordinary paths. The readme row and the new paragraph say both polyfills remain required and should still be installed before any other import. Check that wording reads that way to someone skimming.
- **The runtime test covers only db-p2p's RN entry graph, which includes db-core.** `db-p2p-storage-rn` is guarded only by the lint rule; nothing loads it in a probe.
- **"Hermes provides `TextEncoder` natively (React Native 0.74+)"** in the eslint NOTE and the codec comment rests on the readme's existing "built-in to Hermes" line. I did not verify it independently.
- The `??=` getter is repeated in eight files instead of shared through a helper. That was deliberate, to avoid adding a public db-core export for a two-line pattern; the lint message points at the canonical example. The reviewer may prefer a helper.
