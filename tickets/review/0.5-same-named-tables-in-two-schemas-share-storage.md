# What was wrong

A table declared without `using optimystic('<uri>')` defaulted to `tree://default/<table>`, and its schema-catalog record was filed under the bare table name. So `strand.Member` and `app.Member` opened one collection and shared one catalog record. Only the plugin's in-memory table map (`schema.table`, lowercased) told them apart.

Observed at HEAD with the new spec, before the fix:

- Index-free tables with overlapping columns (`strand.Member(id integer pk, name)`, `app.Member(member_id text pk, name)`): `select id, name from strand.Member` returned `[{id: 1, name: 'alice'}, {id: null, name: 'bob'}]`. The second row is the app's insert, read back through the strand table with a null id. That is the symptom sereus reported.
- With a same-named index on both (`member_by_name`), declaring `app.Member` failed outright: `Cannot re-declare table 'Member' without column 'name': persisted index 'member_by_name' covers it`. The app declaration had picked up the strand table's catalog record.
- `getDroppedSchemaRecord` and `getSchema` had no way to ask about one schema's table.

# What changed

**One rule for where a table lives and what the catalog calls it** (`src/schema/table-identity.ts`):

- `defaultCollectionUri(schemaName, tableName)` gives `tree://default/<schema>/<table>`. `main` is qualified like any other schema. `parseTableSchema` and `recordUriOf` (used by both the batched and unbatched URI lookups) call it, so the three old copies of the rule are now one. Indexes are unchanged at `<uri>/index/<name>`.
- `catalogKey(schemaName, tableName)` builds the key with `encodeKeyTuple([schema, table])`, the same injective framing the data trees use. A plain `schema.table` join would let `a.b`.`c` and `a`.`b.c` share one record. `namesOfCatalogKey` decodes a key, and returns undefined for anything that isn't exactly a two-element framed key (for example a legacy bare `Member` key).
- Names are used as Quereus's `TableSchema` carries them: the schema name is already canonical (lowercase), and the table name keeps its declared casing.

**Catalog re-keyed** (`schema-manager.ts`, `catalog-batch.ts`): `getSchema`, `getSchemaFresh`, `deleteSchema` and `getDroppedSchemaRecord` now take `(schemaName, tableName, transactor?)`. `storeStoredSchema` keys by `stored.schemaName` + `stored.name`. The per-instance cache is keyed by catalog key; `resolveAndCache` caches under `entry[0]`. `CatalogBatch` treats every key as opaque, and the `SchemaManager` computes it. `listTables()` returns `{ schemaName, tableName }[]` decoded from the keys. Entries whose key doesn't decode (legacy records) are skipped.

**Hydrate** (`hydrateCatalog`): each table is restored into the engine schema it was persisted in, and that schema is created with `db.schemaManager.addSchema(name)` if it doesn't exist yet. Previously every table was re-stamped into the host's *current* schema. That would now point it at a different, empty storage location.

**Refusal not added:** two same-named tables that name the *same explicit* URI still share storage, as the ticket asked. The existing storage-adoption guard judges the second against the first's record through `findRecordForUri`.

# Tests and validation

New `test/same-named-tables-across-schemas.spec.ts` (7 cases, all pass). Five of the six original cases failed at HEAD. The catalog-key case was added after the fix.

- The default location includes the schema. The catalog key is injective and decodes; a legacy bare key decodes to undefined.
- One database, `declare schema strand {…}` and `declare schema app {…}`, each with a `Member` table (different columns) and a same-named index `member_by_name`. Each table reads back only its own rows, including through its index. The two collection URIs differ and equal `defaultCollectionUri`. Each catalog record has its own columns.
- Index-free, overlapping columns: no row crosses (this is the device symptom).
- A fresh `Database` plus `hydrate` over the same storage returns `{ tables: 2, indexes: 2 }`. Each table lands in its own schema with its own columns, nothing lands in `main`, rows and index seeks are correct, and re-applying both declarations afterwards changes nothing.
- `drop table app.Member`: the strand table's record, rows and lack of a gravestone are untouched. A contradicting re-declare of `app.Member` is refused by *its own* gravestone (message names `tree://default/app/Member` and `a dropped table declared as (member_id, nick, joined)`). Re-declaring the original shape adopts its own rows.
- A gravestone for `strand.Member` does not judge a first-ever `app.Member` of a different shape.

# Known gaps and things to look at hard

- **Format break for existing data.** Defaulted tables written by earlier builds live at `tree://default/<table>`, and their catalog records are under bare-name keys. This build doesn't read either: `hydrate` skips those records, and a re-declared table starts empty at its new location. AGENTS.md says no backwards compatibility is owed yet, so there is no migration. The README caveat suggests declaring the old location as an explicit URI to keep the rows. That workaround is **untested**; it rests on reading `guardStorageAdoption`/`findRecordForUri`, where a legacy record's recomputed URI no longer matches. Sereus devices with existing data will hit this, so coordinate downstream (`implement/3-strand-app-table-names-collide-with-strand-tables` on the sereus side can revisit its rename and refusal stopgap).
- **Hydrate behaviour change for explicit-URI tables too.** A table persisted in `main` now always hydrates into `main`, even when the host's current schema is something else. No existing test relied on the old re-stamp. Tables are added to an existing schema whatever its kind, and a missing schema is created as `physical`.
- **URI segments aren't escaped.** A `/` inside a schema or table name can spell another table's location. This is parked as a `NOTE:` on `defaultCollectionUri`. The catalog key has no such hole.
- **`this.schemaName` vs `tableSchema.schemaName`.** Vtab catalog reads and deletes use `this.schemaName`, which `instantiateTable` sets to `tableSchema.schemaName || 'main'`. Writes key by `stored.schemaName`, which is `tableSchema.schemaName`. The two diverge only for an empty schema name, which Quereus never produces.
- **Not reproduced in this repo:** the two-node, two-party sereus scenario. Coverage here is single-process over shared storage. There is also no case with two same-named tables inside *one* `apply schema` batch; that can't happen, because one apply targets one schema. The cross-schema overlay path (app applied while the strand record is committed) is covered.
- **Left unchanged on purpose:** `packages/db-core/test/two-handle-collection-fork.spec.ts` uses `tree://default/Table/index/ByToken` only as an opaque string and doesn't depend on the plugin's rule. `docs/debugging.md` log lines quoted from real runs ("As captured then", issue #8's `default/Revocation`/`default/Strand`) and the reported signature quoted in `two-node-multi-collection-commit.spec.ts`'s header stay as reported. The illustrative `Usage` samples were updated to `default/main/Usage`.
- Raw catalog keys now contain framing control characters (`\x02main\x00\x02Member\x00`), which is less readable in a storage dump.

# Notes for the reviewer (garden tender, 2026-09-16 evening)

1. **Catalog determinism is load-bearing, and nobody had written it down.** A downstream application
   (sereus) writes the schema catalog alone at every strand launch, on every machine, before any peer
   contact. That is fork-safe only because both machines produce **byte-identical** catalog content.
   This ticket changed catalog keying (`catalogKey(schema, table)`) and restore behaviour. Confirm the
   new keys and any hash-named blocks derive from the schema definition alone — no per-machine input, no
   dependence on declaration or restore order. The warm-restart change ("each table is restored into
   the schema it was declared in, creating that schema if needed") is the place to look hardest.
2. **The no-migration decision lands on real devices.** The implementer followed AGENTS.md (no
   backwards compatibility owed yet): stores written by earlier builds are no longer read, and a
   re-declared table starts empty at its new location. Sereus devices with existing data will hit this.
   The README's suggested workaround (declare the old location as an explicit URI) is **untested** —
   either test it or say plainly in the README that it is untested.
3. Sereus has one integration assertion reading block ids under the `default/` prefix; it will need
   updating against this build. Expected, not a regression.
