# A durability answer says whose ledger owes it — review handoff

Part of GitHub issue #26. Consumer: `a-sql-commit-learns-when-it-becomes-fully-held` (implement/5.53), which follows a commit only when every below-`full` cohort answer has `recordedBy === selfPeerId`.

## What landed

**`recordedBy` on each cohort answer.** `WriteDurability.recordedBy?: string` — the peer id of the node whose under-replication ledger recorded the write's missing copies, i.e. the only node that will fire `BlockDurabilityReachedEvent` for those blocks. `CoordinatorRepo.acknowledgeCommit` (the single exit every commit success goes through: solo, local-executed, local fallback, tolerated divergence) sets it from `localPeerId` when `noteReplicationShortfall` returns `true`. That is true only when a ledger exists, the answer is below `full`, this node holds the bytes (`localHolds`), there is at least one non-torn block, and every non-torn block's `record` succeeded. No `localPeerId` → never set. `mergeDurability`'s dedup key (`distinctReports`) now includes `recordedBy`, so two otherwise identical answers recorded by different coordinators both survive the merge.

**A settle that removed an entry announces it.** `IUnderReplicationLedger.settle` returns the entry it removed (or `undefined`). `CoordinatorRepo` takes an optional `onBlockDurabilityReached` component, typed as the drain's `BlockDurabilitySink`; `libp2p-node-base.ts` wires it to `storageRepo.emitBlockDurabilityReached`, the same callable the drain gets. On a `full` commit, each block whose `settle` removed an entry fires `{ blockIds: [blockId], rev: request.rev, actionId: request.actionId }` after the removal. No `collectionId` (the coordinator does not read the block; the field is best-effort and documented as always absent from this producer). A throwing sink is logged as `coordinator-repo:block-durability-sink-error` and never fails the commit.

**Deviation from the ticket — `satisfy` changed too.** The ticket said "a `full` settle racing the drain fires exactly one event, verified by inspection of the per-block serialization". Inspection said otherwise: the drain treated `satisfy` returning `undefined` as "cleared" whether it emptied the entry or found it already gone, so with settle now announcing, a settle landing mid-push would fire twice (the drain's own NOTE named the fix). `satisfy` now returns `SatisfyOutcome` — `{status:'owed', entry}` / `{status:'cleared'}` / `{status:'absent'}` — and the drain emits only on `cleared`; on `absent` it forgets the block's failure counters and returns (logged `entry:settled-elsewhere`). Side effect worth knowing: an entry evicted by the ledger's size cap mid-push used to produce a false full-replication event from the drain; it now produces none.

## Things a reviewer should push on

- **`recordedBy` vs. a lower-rev `record` skip.** If the ledger already holds a higher revision for a block, `record` skips silently and `noteBlockShortfall` still returns `true`. I treated that as "tracked" — the event will fire at the higher revision, which covers this write under the event's "`rev` or later" rule. Confirm that reading.
- **Size-cap eviction strands a `recordedBy` promise.** An entry evicted at the cap (default 100 000) never fires its event, but its write was answered naming this node. Recorded as a tripwire `NOTE:` on `KvUnderReplicationLedger.evictBeyondCap` (remedy: a distinct "no longer tracked" signal), not fixed.
- **Event fires before the writer's answer leaves.** The settle event is emitted inside `acknowledgeCommit`, i.e. before the answer returns — the same ordering the drain can produce relative to a writer's answer. The consumer ticket already plans a recent-events record for this race.
- **Constructor positional parameter count.** `CoordinatorRepo`'s constructor gained a 15th positional parameter; the factory hides it, but direct constructors in tests/readme would need it positionally. Matches the existing pattern; not refactored.
- **Mixed versions.** An older coordinator never sets `recordedBy` (consumer treats the write as unfollowable — safe). An older drain on a node with a newer coordinator is not a real configuration (same package).
