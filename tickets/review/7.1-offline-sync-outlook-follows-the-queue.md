## What was built

- **`commit-outlook.ts`** — the per-earlier-entry key index is replaced by `WriteIndex`, one index of what the entries ahead write, per collection (`byKey` → writers, `writers`, `unreadable`, `insertedAbsent`), added to one entry at a time; a check is matched by lookup (a range by scanning the collection's written keys — `NOTE:` at `writersWithin`). `judgeTransaction` now returns `QueuedJudgement = { own, outlook }` (`OwnJudgement` exported). New pure `followOutlooks(queue: FollowedEntry[], deferred)`: walks the queue in order, for each judged, non-refused entry drops own exposures/spans in `committedCollections`, recomputes `dependsOn` against the index built so far plus deferred records below its seq, derives `kind`; then adds the entry to the index with the kind just computed. New `outlookContradicted(outlook, { reason, causedBy, dependencyFailed })`, `refusedCheck(refusal, description)` (table + decoded key; a unique index's value from the `TreeRangeTakenError` range's lower bound), `renderKey`; the JSON replacer is shared with `renderCommitOutlook`.
- **`OfflineMode`** — holds `judgements: Map<id, QueuedJudgement & { dependencyFailed }>` instead of `outlooks`. `onQueueStatus`: on `failed`, `weighFailure` reads the held outlook before it is dropped, reports a contradicted prediction (`reportAssuredFailure`: increments `assuredFailures`, logs `offline:assured-entry-failed transaction=… reason=… refusal=<class> table=… key=… causedBy=…`, publishes state), then marks `dependencyFailed` on every held judgement listing the failed id. After delivering the triggering status (and the failure announcement), `followQueue` runs when `changesTheQueue` says so: `committed`, `failed`, `partially-committed`, or a first `queued` with entries behind it (a restore putting an entry back). `followQueue` builds `FollowedEntry`s (held segments, tables, `committedCollections`, held judgement, `refused` = any held collection's `sealedRefusal(id)`), holds the results (resetting `dependencyFailed`), logs `offline:outlook-regressed` on assured→exposed, and only then delivers one `outlook-changed` per kind change. Isolated with try/catch (`offline:outlook-unfollowed`), like `tryJudgeQueued`. `NOTE:` tripwire on the quadratic drain cost.
- **`offline-status.ts`** — `{ kind: 'outlook-changed'; transactionId; outlook }` in `QueuedTransactionStatus`; `assuredFailures: number` on `OfflineModeState`.

## Tests added (all in `test/offline-outlook.spec.ts`)

- *a transaction exposed only through an earlier one it depends on is told it is assured once that one commits, before it is sent* — two-node mesh, `single_writer` `Prefs` table: natural-key insert (exposed) then an update (exposed only via `dependsOn`); after opening the gate, exactly one `outlook-changed` (the update's, `assured`, empty `dependsOn`), after the insert's `committed` and before the update's `submitting`.
- *a false fresh tag …* — two-node mesh, node B commits the same fresh-tagged key: the entry's `queued` outlook is assured, it fails `constraint`, `expectAssuredFailures(a.plugin, 1)`, and exactly one `offline:assured-entry-failed` line naming `refusal=TreeKeyTakenError table=main.Notes key=["n9"] causedBy=none` (captured with `captureTrace`).
- *an assured transaction that fails because the one it depends on was discarded is neither re-judged on the way nor counted* — one node: fresh insert + update (assured, depends on the insert); discard the insert → update fails `concurrent-modification` with `causedBy` = insert, no `outlook-changed`, count 0. Mutation-checked: making `followedEntry` report `refused: false` fails this case and the root hook (the pass recomputes the refused update without the discarded insert, and its failure is then counted).

## Judgement calls the reviewer should weigh

- **A refused entry is not recomputed** (not in the ticket). When E1 fails, E2 refused by E1's removal is still listed by the queue until the drain fails it; recomputing it then would drop E1 from its `dependsOn`, possibly flip it to assured (a misleading `outlook-changed`), and turn its cascade failure into a false `assured-entry-failed`. Detected through `Collection.sealedRefusal`, which every refusal path (replay, restore) records.
- **The pass is deferred while an entry has left the queue without its terminal status** (its judgement is still held). The queue claims an entry before its removal's drops run; a `discard` removal runs off the loop, so a head `committed` can arrive mid-removal, before the discarded entry's dependents are refused. The terminal status that ends the removal always runs the pass. If some future path removed an entry with no terminal status, outlooks would silently stop following — all current paths (`committed`, `remove`, `unregisterRestored` on never-judged entries) were checked.
- **`assured-entry-failed` rule widened beyond the ticket's**: logged when assured ∧ reason ∈ {constraint, concurrent-modification} ∧ (`causedBy` absent ∨ (`causedBy` ∉ `dependsOn` ∧ no dependency has failed)). The `dependencyFailed` arm exists because `OfflineQueue.causeOf` names the *nearest* failing earlier entry, so in E1 ← E2 ← E3 with E3 depending only on E1, `causedBy` is E2 — the ticket's literal rule would count a discard of E1 as an assured failure of E3. Not covered by a test (needs three entries in a chain); by inspection.
- **No guard refusal in the chain** (should not happen for the two predicted reasons) logs `refusal=none table=unknown key=null`; a description that throws logs `offline:refusal-undescribed` and falls back to the collection id.

## Known gaps / not covered by tests (by inspection)

- Partial commit narrowing to assured; restore putting an older transaction back ahead (narrowing, and the regression + `offline:outlook-regressed` log); listener throwing during `outlook-changed` (uses `notifyListeners`).
- A deferred record that appears in `OfflineRestore.records()` with no queue status (hydrate's first read after a commit made before it — the host-contract violation) triggers no pass by itself; the next settle catches it.
- Each `sealedActions(id)` lookup scans the collection's sealed list, so one pass is quadratic when one collection holds the whole queue (in the `NOTE:` at `followQueue`). A db-core accessor listing a collection's segments once would make it linear; not added (plugin-only ticket).
- `assuredFailures` is in memory, reset by a restart (as `unclassifiedFailures` is).
- A failing root `afterEach` hook makes mocha skip the remaining tests of the run — that is the design the ticket chose; worth knowing when it fires.
