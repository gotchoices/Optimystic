# A transaction larger than the control frame can commit — review handoff

GitHub [#35](https://github.com/gotchoices/Optimystic/issues/35).

## What was wrong

A pend's payload travels twice: writer → coordinator on the repo protocol (decoded under 8 MiB), then coordinator → each other cohort member inside the cluster record, which the member echoes back with its vote. The cluster protocol was classed as control-plane and decoded/read under 1 MiB, so a 1–8 MiB transaction passed hop 1 and was reset at hop 2 by every remote member: `Failed to get super-majority`. A cohort of one never takes hop 2, which is why it only failed once a second machine joined.

## What changed

- **One per-transaction limit, in db-core** (`packages/db-core/src/network/transaction-size.ts`, exported from the package root): `MAX_TRANSACTION_BYTES` = 7.5 MiB, measured by `jsonEncodedBytes` (UTF-8 length of `JSON.stringify`) over the `PendRequest`(s); `TransactionTooLargeError` (`actionId`, `bytes`, `limit`, message names `MAX_TRANSACTION_BYTES` and says to split); `assertTransactionFits(requests)` sums and throws.
- **Frame cap derived from it** (`protocol-limits.ts`): `TRANSACTION_ENVELOPE_RESERVE_BYTES` = 512 KiB; `MAX_BLOCK_MESSAGE_BYTES = MAX_TRANSACTION_BYTES + reserve` (still exactly 8 MiB). Comments rewritten: cluster and dispute-challenge are block-carrying; control stays 1 MiB for sync requests and dispute responses.
- **Cluster protocol on the block cap, both directions**: `ClusterService` decode, `ClusterClient.send` response read and request cap, and `updateCarrying`'s carried-records fallback (now `jsonEncodedBytes` against the same cap the request is sent under, so a too-big carried request falls back instead of throwing). The private `encodedBytes` is gone.
- **Dispute**: `DisputeProtocolService` decodes under the block cap (a challenge carries the disputed record); `DisputeClient` sends both message kinds under the block cap and still reads responses under control.
- **Writer check** — `NetworkTransactor.pend`, first statement, `assertTransactionFits([blockAction])`, ahead of owed cancels and coordinator lookup.
- **Coordinator check** — `CoordinatorRepo.pendMany`, before `verifyResponsibility`, on every cohort size including solo.
- **Sender backstop** — `ProtocolClient.processMessage` encodes once before dialing; `ProcessMessageOptions.maxRequestBytes` makes an oversized request throw `MessageTooLargeError` (`code = 'MESSAGE_TOO_LARGE'`, `protocol`, `bytes`, `limit`; log `request:too-large`) without opening a stream. `exchange` and the prepared-stream re-send take the encoded bytes. Caps passed: repo, cluster, block-transfer, dispute → block; sync → control.
- **One change the plan said would not be needed** (`TransactionCoordinator`, `packages/db-core/src/transaction/coordinator.ts`): its pend phase runs each collection's pend under `Promise.allSettled` and kept only the *message* of a thrown error, so `commit()` would have thrown `Error('Transaction commit failed: …')`. It now carries a `TransactionTooLargeError` whole (a `tooLarge` field beside the existing `expired` one) and `commitOnceLatched` rethrows it by name. `Collection.sync` needed nothing: the pend in `TransactorSource.transact` is outside its try, and `syncAttempts` has no catch around `transact`.
- **Docs**: new `docs/internals.md` § *A transaction's size limit*; `packages/db-p2p/docs/cluster.md` *Size* bullet; `docs/debugging.md` (`carried:too-large` wording, new `request:too-large` line); stale "1 MiB" comments in `peer-address-book.ts` and `commit-proof.ts` corrected.

## Things to check / known gaps

- **What the limit binds in multi-collection transactions.** `TransactionCoordinator` sends one pend per collection (no writer sends `pendMany` batches yet), so `NetworkTransactor.pend` judges each collection's pend separately — the limit binds each collection's share (plus its copy of the validation payload), not the transaction's sum. This matches the frames (each pend is its own record). `CoordinatorRepo.pendMany` does sum a batch. Documented in internals.md; a reviewer may prefer the coordinator to sum across collections before pending.
- **Envelope reserve is reasoned, not measured.** 512 KiB is assumed to cover the cluster record's peer map, signatures, apply outcomes, `coordinatingBlockIds`, and a commit record carried with a deferred pend. No test measures a near-limit record. If it is ever too small: a pend record still has room (the fallback sends the commit alone and the member reconciles), but a `ClusterClient.update` of a near-limit pend record whose envelope exceeds 512 KiB would throw `MessageTooLargeError` and read as a missing vote.
- **Up to four carried records** (`MaxCarriedRecords`): several owed near-limit pend records to one peer exceed the frame, so carrying falls back to the timer path. Correct, slower; noted in cluster.md.
- **`MessageTooLargeError` from `RepoClient` inside `processBatches` would be retried** onto other coordinators with backoff. Unreachable for pends (the writer check sits below the frame cap by the reserve); confirmed by reading, no test.
- **Remote writer that bypasses `NetworkTransactor`** gets a reset stream from `RepoService` when `CoordinatorRepo.pendMany` refuses; only the coordinator's log names the cause. As planned.
- **Solo cohorts are now refused above 7.5 MiB** where they were unlimited before. Intended; noted in internals.md. There is no `CHANGELOG.md` entry; whoever cuts the release should mention it.
- **Mixed versions**: an un-upgraded member still decodes cluster frames at 1 MiB, so 1–7.5 MiB writes fail against it until it upgrades.
- **Extra encoding cost**: `assertTransactionFits` re-serializes the pend on the writer and on the coordinator. Tripwire `NOTE:` at `assertTransactionFits`.
- **The reporter's follow-on `TornActionError`** did not reproduce: the 1.1 MB two-node spec commits and reads back clean.

## Reply-ready note for issue #35

> Fixed. The cluster protocol now frames records under the same 8 MiB cap the writer's request uses, so a write up to the per-transaction limit commits whether the group has one machine or several. The limit is `MAX_TRANSACTION_BYTES` (7.5 MiB of JSON-encoded pend, exported from `@optimystic/db-core`), the same at every group size. A transaction above it is refused on the writer before anything is sent, with `TransactionTooLargeError` (carrying `bytes` and `limit`); split the batch into smaller transactions. For SQL writes the log entry repeats the row data beside the tree's blocks, so usable row volume is about half the limit. Two related limits are tracked separately: a single block that outgrows a frame by accumulation (backlog `bug-a-block-larger-than-a-frame-cannot-be-copied`) and transactions larger than one frame via chunking (backlog `feat-a-transaction-larger-than-one-frame-can-commit`). The follow-on `TornActionError` you saw after raising the cap locally did not reproduce on our two-node test with a 1.1 MB append.
