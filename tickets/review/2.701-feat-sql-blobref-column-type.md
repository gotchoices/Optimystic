# The `blobref` column type — review

First part of [docs/blobs.md §SQL](../../docs/blobs.md#sql): the column type and nothing else. No blob service, no reference trees, no pins, no SQL functions — those are `feat-blob-sql-type-and-blob-service` and its successors.

A **blob reference** is the short string that names a large stored file: a content identifier, 59 characters of lowercase base32, with exactly one accepted spelling. `isBlobRef` in `packages/db-core/src/blob/blob-ref.ts` is the one rule for what is and is not one, and the type adds no grammar of its own.

## What landed

**The type.** `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts` holds `BLOBREF_TYPE_NAME` (`'BLOBREF'`), `BLOBREF_TYPE` (physical TEXT, `isTextual`, `supportedCollations: []`, `validate` delegating to `isBlobRef`, a BINARY `compare`, no `parse`, no `collationAware`, no `semanticOrdering`), `isBlobRefColumn`, and guard 2's assertion `assertBlobRefTypeRegistered`. The reasoning behind each flag is in the module's doc comments.

**Registration.** `register` in `src/plugin.ts` returns `types: [{ name: 'blobref', definition: BLOBREF_TYPE }]` beside `vtables`, `functions` and `collations`; `registerPlugin` (`@quereus/quereus/src/util/plugin-helper.ts`) registers it. `src/index.ts` exports `BLOBREF_TYPE`, `BLOBREF_TYPE_NAME` and `isBlobRefColumn`. `package.json`'s `quereus.provides` block gained `"types": ["blobref"]` (host UI metadata — one line, not in the plan).

**Guard 1 — a stored record whose declared spelling no longer resolves to the type its rows were written under.** `hydratedColumnType` in `src/schema/schema-manager.ts` now holds both arms of the hydrated-column type decision: the `declaredType` arm re-infers with `inferType` and then refuses when the result's `name` differs from the record's `affinity`; the no-declared-type arm is the existing `registeredStoredType`. One site, so it covers `hydrateCatalog`, the stale-record rebuild, the vtab's hydrate and load arms, and the index manager's partial-index predicates.

**Guard 2 — a declaration naming `blobref` while the type is not registered.** `assertBlobRefTypeRegistered` refuses a column whose declared spelling's base name is `blobref` (case-insensitively, parameter list stripped) while its `affinity` is not `BLOBREF` — the shape a process with `pragma strict_type_names = false` and no registered type produces, where the column becomes a **BLOB** column whose row codec base64-*decodes* every stored string.

**Docs.** `docs/blobs.md`'s status paragraph names the type as built and narrows what remains of SQL; §SQL's opening moved from intent to what exists and gained the refusal. The plugin README gained "Large values — the `blobref` column type" under *Data Model*.

## Deliberate deviations from the plan — read these first

1. **`compareNulls` is not exported from `@quereus/quereus`'s root entry.** The plan said it was. The three-line null preamble is inlined in `BLOBREF_TYPE.compare` with a comment saying why. Nothing else changed.

2. **Guard 2 is called TWICE from `OptimysticVirtualTable.doInitialize`, not once.** The plan's single placement (after `storedSchema` is settled, before the `RowCodec`) runs *after* the DDL arm's `storeStoredSchema`. So a type-less process re-declaring `create table … (Content blobref)` over an existing record whose rows were written as `BLOBREF` would have persisted `affinity: 'BLOB'` over that record and only *then* been refused — leaving the table unopenable even by a process that does have the type (guard 1 would then fire for everyone). The second call sits on `candidateStored.columns`, before the write. Both calls are commented with what each covers. **This is the main judgment call in the change; if review disagrees, the one-call version is a two-line revert.**

3. **Guard 1's message is direction-neutral.** `Type mismatch for column 'x' in a stored table description: its rows were written as 'A', but its declared spelling 'a' resolves to 'B' in this process. Usually the type is not registered here — to fix: …`. The plan assumed only the missing-type direction; the disagreement runs both ways (a record written before a type was registered, read by a process that has it). The remedy sentence is one shared constant, `REGISTER_TYPES_REMEDY` in `blobref-type.ts`, and `registeredStoredType`'s own message was rewritten to use it too — its old wording ("register the type (Database.registerType) before opening the table") was pinned by no test or doc.

4. **The plan's "hydrate without `types` registered is refused" test case cannot be written as stated.** Quereus's type registry is process-wide with no un-register (`TypeRegistry` in `@quereus/quereus/src/types/registry.ts`), so no test in a shared mocha process can rely on `BLOBREF` being absent — it would pass or fail on file ordering. The equivalent is written from the other direction instead: the record is tampered to `affinity: 'BLOB'` (what a build predating the type writes) and hydrate is refused naming the column, `BLOBREF` and `BLOB`. Same disagreement, same code path, same throw.

5. **Guard 2's rule is pinned by a direct call, not through SQL.** For the same registry reason: in a process that *has* the type, no SQL path reaches that rule (a declaration here resolves to `BLOBREF`, and a stored record that disagrees is refused by guard 1 first). The spec imports `assertBlobRefTypeRegistered` from `../src/schema/blobref-type.js`, which a dozen existing specs already do for internals. It is **not** exported from `src/index.ts` — review may want to decide whether it should be, rather than leaving a public entry point to satisfy a test.

6. **NULL rides in the round-trip test** rather than having its own `it` — one behaviour ("what the column stores"), two rows.

## Tests added

`packages/quereus-plugin-optimystic/test/blobref-column.spec.ts`, over `create table Attachment (Id text primary key, Content blobref null)` on a shared `local` transactor, with the plugin's `types` registered as `registerPlugin` would:

| Test | What it verifies |
|---|---|
| stores a well-formed reference verbatim, and NULL as nothing referenced | A canonical reference round-trips byte-identical, and a nullable `blobref` column accepts and returns NULL. |
| refuses every spelling that is not a canonical reference | Six shapes — upper-cased, a version-0 CID, a dag-cbor CID, a leading space, `=` padding, an integer — each refused with `Type mismatch for column 'Content': expected BLOBREF` at `StatusCode.MISMATCH`, and no row written. |
| refuses to hydrate a stored column whose rows were not written under the type | Guard 1: a record whose `affinity` and `declaredType` disagree stops `plugin.hydrate(db)`, naming the column and both type names, and nothing enters the catalog. |
| refuses a column declared blobref whose rows resolved to another type | Guard 2's rule: fires for `blobref` / `BlobRef` / `blobref(2)` against a non-`BLOBREF` affinity; quiet when the affinity *is* `BLOBREF`, when the column is a plain `blob`, and when the record names no declared spelling. |

The reference vector is the 1,000-byte file's reference from `packages/db-core/test/blob-builder.spec.ts`, so it is one real IPFS tools produce.

Nothing tests the registration wiring, the type's metadata flags, or that an index on the column still walks — a type, the existing index-walk specs and `yarn check` cover those. The plan's inspection-only cases (a value copied between two `blobref` columns, `collate nocase`, a non-BINARY session `default_collation`, an index on the column, `strict_type_names` off, two `Database`s in one process) were read in the Quereus source and left untested, as it said.

## Known gaps for review

- **Guard 1 now refuses *any* record whose `affinity` and `declaredType` disagree, for every type, not just this one.** The argument that it is quiet for records that exist today is structural: `columnSchemaToStored` stores `col.logicalType.name` as `affinity`, and a DDL-created column's `logicalType` is `inferType(declaredType)`, so the two agree for every spelling a process can resolve. The evidence run for it is the `@optimystic/upgrade-check` suite, which hydrates and queries a persisted table on every past release's data — but its fixture table is only `integer`/`text` columns. Worth confirming in the full plugin run which *other* declared spellings are actually created-then-hydrated anywhere (`timestamp`, `json`, `decimal(10,2)`, `interval`, `boolean`, `varchar(20)`); if none are, that is a coverage observation, not necessarily a ticket.
- **Whether `assertBlobRefTypeRegistered` belongs in the public entry.** See deviation 5.
- **The second guard-2 call.** See deviation 2 — the hazard is real, the fix is mine rather than the plan's.
- A parked tripwire: `declaresBlobRef` in `blobref-type.ts` reimplements Quereus's unexported `declaredTypeBase`; a `NOTE:` at the site says the two agree today and that this must follow if Quereus changes how it splits a declared name from its parameter list.
