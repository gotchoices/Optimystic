## What changed

Quereus 5.4.0 puts the collation a comparison runs under on `PredicateConstraint.collation` (absent means BINARY). The module never read it, so it treated `b = 'x' collate nocase` and `b > 'w' collate nocase` as plain byte comparisons at three sites. The engine already refused the resulting seek (its `classifyCollationCover` backstop), so no wrong rows came out, but the module had chosen that doomed seek over a valid walk of another index, and the engine fell back to a scan plus a Sort.

All three sites now gate on the filter's collation, using the predicates Quereus exports for exactly this contract rather than a local copy:

- **Pinning** — `pinnedColumns` in `src/schema/index-walk.ts` pins a column only when the filter's comparison refines the column's collation (`equalityServesKeyColumn`, against the table column). The `NOTE:` that waited for this field is gone.
- **Equality seek** — `firstEqualityRoleFilter` in `src/optimystic-module.ts` now takes the key column (index and collation) and returns `-1` when the first equality-role filter does not refine the key column's collation. It deliberately does not fall through to a later filter that would serve, because the engine seeks on the first (the memory module's `findEqualityMatches` does the same). This is the one picker under `matchEqualitySeek` for both the primary key (table column's collation) and every secondary index (index column's collation). `matchEqualitySeek`'s parameter type is now the shared `KeyColumn`.
- **Range seek** — `claimableBound` takes the range column and requires `rangeServesKeyColumn` (collation names equal). A failing first bound declines the whole range, as a non-string literal already did.

**Deviation from the plan:** the ticket asked for one new exported predicate in `index-walk.ts` wrapping `collationRefines`. Quereus 5.4.0 already exports `equalityServesKeyColumn` and `rangeServesKeyColumn` (`@quereus/quereus/src/vtab/best-access-plan.ts`), which are that contract, and its memory module uses them. I called those directly instead of writing a third copy. The plugin's peer range is already `^5.4.0`, so no dependency change.

**Not changed:** the `Partial primary key scan` candidate in `getBestAccessPlan` (the `isPkColumn && filter.op === '='` branch). It claims no filter and only adjusts cost, so the ticket called gating it optional and cosmetic.

A comment on `rangeSeekCandidate` now says why a range seek's prefix equalities need no extra check. The engine holds them to the bounds' rule (equal collation names). `matchEqualitySeek` trusts only BINARY key columns, and the only collation that refines BINARY is BINARY itself, so a prefix that passes the equality gate also passes the equal-names rule.

## Tests

- `ordering-claim-guard.spec.ts`, "neither seeks nor pins a BINARY column on an equality compared under NOCASE" (equality describe): with `idx_cat(category)` and `idx_name(name)`, `category = 'x'` under NOCASE plus `order by name` returns the walk of `idx_name` with the filter left unclaimed. Over `idx_cat_name(category, name)` it seeks nothing and claims no ordering. This covers the pinning and equality-seek sites.
- `ordering-claim-guard.spec.ts`, "does NOT claim a bound compared under another collation than the index column's" (range describe): a NOCASE `>` bound on `idx_name` gets a scan with nothing claimed, and a BINARY lower bound beside a NOCASE first upper bound declines the whole range. This covers the range site.
- `index-ordered-walk.spec.ts`, new describe "A filter compared under a coarser collation than its column leaves the order to another index": a table with `idx_b(b)` and `idx_c(c)` and rows `('1','X','b'), ('2','x','a'), ('3','y','c'), ('4','x','d')`. For `where b = 'x' collate nocase order by c` and `where b > 'w' collate nocase order by c`, the plan has no SORT and goes through an index (`expectOrderFromIndex`), and the rows match a memory table. This is the end-to-end check.

All three tests failed before the change: the planner tests found the claimed seek of `idx_cat` / `idx_name`, and the SQL test saw SORT / FILTER / SEQSCAN. They pass after it. Full package `yarn test`: 1380 passing, 14 pending, 0 failing, plus the smoke check. `yarn typecheck`, `eslint` on the changed files and `yarn lint:docs` are clean.

## Docs

- `docs/internals.md` §An ordered read walks a secondary index, **Which columns**: a column is pinned only when the filter's collation refines the column's, and the same rule keeps such an equality from being claimed as a seek.
- `docs/internals.md` §A range predicate seeks a secondary index: the module now declines a bound under another collation itself (`claimableBound`), and the engine's `classifyCollationCover` is named as the backstop.
- `packages/quereus-plugin-optimystic/README.md`: three phrases in the access-path paragraph changed: a collated `=`/`in` is not sought, a collated range is applied "above whatever else serves the statement" rather than "over a scan", and only an `=` compared under BINARY counts as pinning.

## For the reviewer

- An adjacent shape I checked by hand, not covered by a test: `where b = 'x' collate nocase order by b, c` over `idx_bc(b, c)`. The module now offers a walk of `idx_bc` claiming `(b, c)`; the claim is correct, because the walk orders `b` by BINARY bytes and the filter is only a residual. The engine's `orderingClaimSurvivesCollation` still refuses any ordering claim on an index that has a mismatched equality on one of its key columns, so the plan is SORT / FILTER / SEQSCAN, the same as before this change. Rows are correct (1, 2, 4). That conservatism lives in the engine, not here; I filed nothing.
