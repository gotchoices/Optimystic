Part of stage 1 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages): the "Validity rejection" row of the classification table now has a typed error at the writer.

## What landed

**A fourth returned refusal (db-core).** Beside `StaleFailure`, `ExpiredFailure` and `ShortfallFailure` in `WriteFailure` (`packages/db-core/src/network/struct.ts`):

```ts
type ValidityRefusal = ValidityRejection & { peerId?: string; reason?: string };   // one refuser
type TransactionInvalidity = { refusals: ValidityRefusal[] };                      // never empty
type RejectedFailure = { success: false; reason?: string; conflict: false; rejected: TransactionInvalidity; /* siblings' fields never */ };
isRejectedFailure(failure): failure is RejectedFailure                            // stale-failure.ts
class ValidityRejectedError extends Error { refusals; toFailure(): RejectedFailure } // validity-rejected-error.ts
```

Every sibling got `rejected?: never`; `isConflictFailure` is false for the new shape.

**Naming deviation from the plan:** the plan called the aggregate `ValidityRejection`, but the marker ticket already uses that name for the per-vote class (`{ computedHash? }` in `packages/db-core/src/transaction/transaction.ts`, signed into `Signature.validity`). So the aggregate is `TransactionInvalidity` (mirroring `TransactionExpiry`) and each entry is `ValidityRefusal` = the per-vote class plus `peerId` and `reason`.

**The coordinator's rule (db-p2p).** `validityRejectionOf(promises)` in `packages/db-p2p/src/repo/cluster-coordinator.ts` (exported, pure) returns a `TransactionInvalidity` only when every reject vote in the record is validity-marked or an expiry vote, and at least one is validity-marked. The refusals are the marked votes only. Votes are read defensively, as `expiryRejectionClocks` already did: a `validity` that is not an object counts as no marker. `ClusterCoordinator` attaches the result to `ValidatorRejectionError.validity` (a new optional third constructor argument). The all-expiry case still throws `TransactionExpiredError` first, unchanged. `expiryRejectionClocks` now shares an `expiryClockOf` helper with the new rule.

**Where it is returned.**
- `CoordinatorRepo.pendThroughCluster`'s catch, in order: expiry → shortfall → conflict → held → stale classifier → `ValidatorRejectionError` carrying `validity` → `ValidityRejectedError(...).toFailure()` → rethrow. The confirmed-stale arm stays first.
- `StorageRepo.pend` (a cohort of one, reached through `CoordinatorRepo.pendSolo`): a check verdict carrying `validity` returns `RejectedFailure` with one refusal and no `peerId` (`validationRefusal`, a module function). Unmarked refusals (`PEND_NOT_VALIDATABLE`, `VALIDATOR_FAULT`) still return a bare reason.
- The commit side is unchanged: commit records never run the transaction checker.

**Writer consumers (db-core).**
- `refusalFrom` precedence is now rejected > expiry > shortfall > stale.
- `Collection.syncAttempts` stops on it by name with `ValidityRejectedError`.
- `TransactionCoordinator`: `pendRefusalError` maps it, `pendFailure` carries it as `rejected`, `CoordinationResult.rejected` carries it up, and `commit()` throws it by name (before the expiry arm). `execute()` already reports a pend-phase failure as failed with the error's message, and now that message is the `ValidityRejectedError` text.

**Docs.** `docs/internals.md`: the stale-classification bullet is renamed "A pend rejection is returned only when it is classified…" and gives the rule and its ordering. The retryability bullet now lists three never-retryable refusals and describes `RejectedFailure`. The marker bullet no longer says nothing consumes the marker. `docs/offline-sync.md`: the table row names `ValidityRejectedError`, and the "no stable class yet" sentence is replaced. `yarn lint:docs` is clean.

**Dispute ticket arm.** `tickets/backlog/1.5-dispute-writer-sees-disputed-pend.md` gains a section that ticket must handle: `DisputedFailure` needs `rejected?: never`, and the siblings need `dispute?: never`. Its "expiry outranks a dispute" ordering predates the new rejected > expiry rank in `refusalFrom`. It must also choose between `TransactionRuledInvalidError` and `ValidityRejectedError` for `rejecters-won`.

## Use cases for review / validation

- **Remote writer, all members judge invalid** (multi-collection pend with a `validation` pair, members armed with an enforcing validator): `coordinatorRepo.pend` returns `{ success: false, conflict: false, rejected: { refusals: [...] } }`, and `TransactionCoordinator.commit` throws `ValidityRejectedError` with no re-drive. The mesh spec shows the first half.
- **Marked plus unmarked reject** (one member stale, one invalid): still a thrown `ValidatorRejectionError`, which a remote writer sees as a reset stream. This is deliberate: an unmarked reject may be a stale revision that only members ahead of the coordinator can see.
- **Marked reject while the coordinator's own storage holds a newer revision**: returned as a `StaleFailure` with `conflict: true`, and the writer rebases. The stale classifier runs first.
- **Cohort of one with a `validatePend` hook giving a `validity` verdict**: `RejectedFailure` with one refusal and no `peerId`. The message names it as "coordinating node: <reason>".

## Known gaps and things worth a second look

- **Mixed versions.** An older member never marks, so its rejects never produce this failure. An older writer receiving `RejectedFailure` treats it as a reason-only refusal and retries until its budget ends (`Collection.syncAttempts`), or treats it as a non-conflict hard failure (`TransactionCoordinator`'s `PendRejectedError` with `conflict: false`).
- **Quereus bridge.** `mapCommitRefusal` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts` passes `ValidityRejectedError` through untouched, since it is not a `TreeGuardRefusedError`. Session mode does not catch `coordinator.commit`'s throw (`TransactionSession.commit`), so the class reaches the bridge whole. In the legacy per-tree sweep, `Collection.sync` throws it; if an earlier tree already landed, it ends up as the `PartialCommitError` reason. I did **not** check whether the Quereus engine wraps an error thrown from the vtab commit hook. If it does, the class is reachable only through `cause`. No mapping was added; stage 4 decides how offline mode shows `rejected`.
- **`execute()` returns a string.** `ExecutionResult.error` carries only the message, so a host using `execute()` cannot test the class. That is the existing contract for every failure there.
- **Storage refuses what the cohort approved.** On the consensus path, if this node's own storage returns `RejectedFailure` after the cohort approved the pend, `pendThroughCluster` still treats it as tolerated local divergence (the `localPendResult` arm). Only its comment changed. This needs the member's validator and the storage hook to disagree, which happens only when they are configured differently.
- **A vote with both markers.** A malformed vote carrying both `validity` and `expiredAt` (the type forbids it, and `voteFor` never produces it) is counted as an expiry vote by `expiryRejectionClocks`. So a record made only of such votes throws `TransactionExpiredError`, even though the signing payload reads them as validity votes. I judged this contrived and did not guard it.
- **Re-sent attempts never see it.** `completeOwnEntry`'s re-send carries no `validation` pair, so it can never meet a validity rejection. A comment line now says so.
- `tickets/.garden-report.md` shows as modified in the working tree. That was not this ticket.
