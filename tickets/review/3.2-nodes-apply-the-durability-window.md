# Nodes apply the durability window — review handoff

Third of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). The node now connects the window function (`durabilityWindowMs`) to the flush deadline (`flush({ withinMs })`): every storage apply that runs on a consensus record flushes with the window for that record's cohort, every other write group stays strict, and the two cross-store writes that describe a block-store write are ordered after it survives a power cut. Until `file-store-syncs-by-the-earliest-deadline` lands no production backend defers a sync, so on a real node nothing observable changes; the tests use the deferring memory backend.

## What changed

**`StorageRepo`** (`packages/db-p2p/src/storage/storage-repo.ts`)

- `StorageApplyOptions { proof?, syncWithinMs? }` is the third parameter of both `pend` and `commit`. The commit's bare `proof?` parameter is gone; the proof rides in the options. `ICommitProofPersister` is renamed `ILocalApply` and declares both methods. `IDurableStorage { whenDurable() }` is the named capability `ClusterMember` probes for, and `StorageRepo.whenDurable()` forwards to the store.
- `endGroup(work, wrote, flush?)` hands `flush` to `storage.flush`. `pend` and `commit` pass `{ withinMs: apply?.syncWithinMs ?? 0 }` (`groupFlush`); `cancel`, `recoverBlock`, `saveReplicatedBlock` and a `get` that took a latch pass nothing, so they stay strict. `flushBehindFault` stays strict whatever the group asked.
- The `endGroup` doc comment now says what a relaxed group means: change events fire when the flush resolves, which is after a process crash is survived but before a power cut is, and that within the window a power cut can take back a write this node announced and reported held.

**Window helper** (`packages/db-p2p/src/storage/durability-window.ts`): `DurabilityWindowFor = (cohortSize) => number` and `recordDurabilityWindowMs(windowFor, record)`, which reads the cohort size as `Object.keys(record.peers).length` and answers 0 when no window function was given. Both classes below use it, so the cohort-size rule lives in one place.

**`ClusterMember`** (`packages/db-p2p/src/cluster/cluster-repo.ts`): takes `durabilityWindowFor?` as a component and trailing constructor parameter. `applyConsensusOperation` applies a record's pend and commit through `localApply()` with `{ syncWithinMs: syncWindowFor(record) }`; a consensus `get` or `cancel` operation stays strict. `handleConsensus` now writes the executed marker through `markExecutedOnceDurable`: it awaits the store's `whenDurable()` (when the repo has one) and only then calls `stateStore.markExecuted`; a rejection logs `cluster-member:persist-executed-error` and writes no marker. A repo without `whenDurable` (a plain `IRepo` double) has the marker written at once, as before.

**`CoordinatorRepo`** (`packages/db-p2p/src/repo/coordinator-repo.ts`): same component and trailing constructor parameter, through the `coordinatorRepo` factory. The fallback pend after consensus (`!localExecuted`) and the fallback commit that carries `consensusProof` flush with the record's window. `pendSolo` and `commitSolo` stay strict, with a comment saying why.

**`KvUnderReplicationLedger`** (`packages/db-p2p/src/repo/kv-under-replication-ledger.ts`): `KvUnderReplicationLedgerOptions.beforeRecord?: () => Promise<void>`, awaited at the start of `record` before any key-value write, ahead of the per-block queue so the hook's flush never holds the block's other ledger operations behind the disk. A rejection makes `record` reject, which `noteReplicationShortfall` already logs per block and answers without `recordedBy`.

**`createLibp2pNodeBase`** (`packages/db-p2p/src/libp2p-node-base.ts`): builds one `durabilityWindowFor` from the resolved policy and passes it to both `clusterMember(...)` and the coordinator factory; wires the ledger's `beforeRecord` to a strict `rawStorage.flush()`.

**`served-repo-proxy.ts`**: comment updated; it still forwards only the plain `IRepo` surface, which is correct because neither the proof nor the window ever goes on the wire.

**Docs**: `packages/db-p2p/docs/storage.md` Invariant 6 — the sentence claiming every caller flushes strictly, *Who calls `flush()`* (a new paragraph listing which groups carry a window and which never do), *Visible before durable* (the window's accepted risk), and write order 8 (now kept by `markExecutedOnceDurable` over `whenDurable()` and by the ledger's `beforeRecord`). `packages/db-p2p/docs/repo.md`: one sentence at the ledger. Theorem 6 in `docs/correctness.md` is left to `durability-docs-match-the-window`.

## Things worth a reviewer's eye

- **The fallback pend gets the window even when this node is outside the cohort.** `!localExecuted` also covers a coordinator that is not in `record.peers`. Its copy is one nobody reconciles from, so relaxing it cannot weaken what the cohort holds, and the ticket asked for the record's window on that branch; but if the reviewer prefers an off-cohort coordinator to stay strict, the gate is `selfInCohort` on the commit side and would need a mirror on the pend side.
- **`markExecutedOnceDurable` waits on the store's latest committed batch**, not on the apply's own batch: `WriteGroup.whenDurable()` answers with the newest batch's `durable`, so an unrelated relaxed group committed between the apply and this call extends the wait by at most one window. Bounded and harmless; noted here rather than in code.
- **The "still pending" assertion in the storage-repo test is a 20 ms race** against `whenDurable()`. The deferring backend never syncs unless asked, so the race cannot flake toward a false pass of the strict arm, but it is timing-shaped.
- **`beforeRecord` runs before the per-block queue.** Two concurrent `record` calls each flush the block store; a strict flush with nothing to seal is a no-op on `WriteGroup`, so the second costs nothing, but a backend that syncs unconditionally on every flush would pay twice. No such backend exists.
- **A refused pend or commit with a window flushes relaxed.** What a refusal writes is at most a dropped pending record, and the writer is told to retry, so nothing is announced on it; still, the ticket's table says "every other storage write group stays strict" and a refusal is the one exit of `pend`/`commit` that is not an apply.
- The start-up line (`logStorageDurability`) and the window table in storage.md still say no backend defers, which is accurate until `file-store-syncs-by-the-earliest-deadline` lands.
