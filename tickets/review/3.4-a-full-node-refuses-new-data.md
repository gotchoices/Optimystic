# A full node refuses new data

## What landed

Three doors a node used to leave open now refuse at the `refusing` stage of the storage pressure reading that ticket `a-node-names-how-full-it-is` built, and a fourth limit — the host's own writes — refuses only once the measured use has reached the whole allotment.

### The reading answers two questions now

`packages/db-p2p/src/storage/storage-pressure.ts` gained three things:

- `refusingNewData(): boolean` — "does this node take data from other machines", `atLeastPressure(lastStage, 'refusing')`. The one predicate all the inbound doors read, so none of them re-derives a threshold comparison. `false` at `unknown` and `false` before the first successful sample.
- `ownWriteRoom(): OwnWriteRoom` — the host's own limit, a discriminated result: `{ hasRoom: true }` or `{ hasRoom: false, usedBytes, totalBytes }`. Derived from a new `lastCapacity` field holding the last SUCCESSFUL scan's capacity (kept across a failed scan, exactly as `lastStage` is), via the pure `ownWriteRoomOf(capacity)`. Room when `totalBytes` is absent, and room before the first sample.
- `NodeOutOfSpaceError`, carrying `usedBytes` and `totalBytes`, exported from `@optimystic/db-p2p` (it reaches the package index through the existing `export * from "./storage/storage-pressure.js"`).

### Door 1 — a pushed replica

`BlockTransferResponse` gained `outOfSpace?: true`, a property of the receiver, riding once per response. `BlockTransferService.handlePush` refuses as its FIRST statement — ahead of the structural check and ahead of every `certifyContent` call — answering every requested block id `missing` plus `outOfSpace: true`, and logging `push:out-of-space`. `BlockTransferServiceComponents.storagePressure` is the optional dep; absent, nothing refuses.

The sender side runs through `pushBlockToPeers`:

- `PushRefusal.reason` gained `'out-of-space'`.
- `PushBlockOptions.fullPeers?: Set<string>` is a caller-owned, pass-scoped memory: a peer in it is reported `skipped` and never pushed to again; a peer that answers `outOfSpace` is added.
- The named-proof path returns an `outOfSpace` answer as it is rather than re-pushing the proof inline and rather than calling `recordUnresolved` — the receiver never looked at the reference, so its answer says nothing about it.
- `logRefusals` in `block-transfer.ts` gained a `%s:peer-full` line, which is the whole of what `confirmReplicated` gains (a full new owner was already not counted as a holder, so a shed range was already retained).
- `replicateGrown` keeps one `fullPeers` set per reaction and checks it **ahead of** the floor-met branch: a block with any full reported peer is reported `complete: false` with only the peers that actually confirmed, so a full peer never enters `RebalanceMonitor`'s seen set.
- `executeConfirm` takes the set optionally (`confirmReplicated` passes none, deliberately) and short-circuits its retry loop when every candidate owner is in it, so a pass does not sleep out two backoffs pushing to nobody.

### Door 2 — an announced blob

`BlobAnnounceAnswer` gained `'out-of-space'`, added to `ANNOUNCE_ANSWERS` (the decoder's validation list). `BlobAnnounceReceiver.decided` answers it after the on-demand, membership, cohort and allowance checks and **before** the reference read. `BlobAnnounceReceiverDeps.storagePressure` is the optional dep.

It is deliberately **not** in `SATISFYING_ANSWERS` (`cohort-reaction.ts`) — the reasoning is written out at that constant. The release arm of `BlobCohortReaction` is untouched, on purpose.

### Door 3 — the program on the same machine

`LocalBlobServiceInit.ownWriteRoom?: () => OwnWriteRoom` (a thunk; default "always room"). `put` and `pin` call one private `requireRoomForOwnWrite`, which throws `NodeOutOfSpaceError`. In `put` the call sits before `buildBlob`, so no piece is ever staged. `node.blobs.put` / `.pin` delegate straight here, so the gate covers the host's entry points. `SingleMachineBlobService` passes no thunk and so refuses nothing.

### Wiring

`libp2p-node-base.ts`: `storagePressure` is now a sixth argument to `storageProtocolServices` and reaches the `blockTransfer` service entry; it is passed to `BlobAnnounceReceiver`; and `LocalBlobService` gets `ownWriteRoom: (): OwnWriteRoom => storagePressure.ownWriteRoom()`. **The return-type annotation on that thunk is load-bearing** — `blobs` → thunk → `storagePressure` → `storageAccount` → its own `blobRecords` thunk → `blobs` is a type cycle TypeScript reports as five `TS7022`/`TS7023` errors without it.

### Beyond the ticket's `files:` list

`packages/db-p2p/src/blob/blob-copy-drain.ts`: adding a value to `BlobAnnounceAnswer` changes what `announceTo`'s final `if/else` does with it. Left alone, `out-of-space` would have fallen into `context.noteSuccess` — the peer asked again every pass for ever, with no give-up bound. It is now grouped with `not-responsible` / `unreferenced` under `noteFailure`, which is the ticket's "treated exactly as an unreachable one". **Worth a reviewer's second look**: the ticket also says "asked again on the next pass", and `noteFailure` means asked again for `maxAttempts` passes and then abandoned until the peer reconnects. I read the two sentences as agreeing (an unreachable peer gets exactly that treatment) but they could be read as disagreeing.

## Use cases to check

- **A node on a memory / SQLite / LevelDB store with no configured allotment is unchanged.** This is the arm most worth probing: `capacity().totalBytes` is absent → `stage()` is `unknown` → `refusingNewData()` is `false`, and `ownWriteRoom()` answers room. Every door is open. Likewise a node whose free-space read threw on one scan: `lastStage` and `lastCapacity` are both kept, so one fault does not flip a gate either way.
- **A node that has not sampled yet.** Before the first successful `read()`, `lastCapacity` is `undefined` and `lastStage` is `unknown`; a `put` that lands in that window succeeds.
- **A full receiver answering a push.** Expect `accepted: []`, `missing` = every requested id, `outOfSpace: true`, no `unresolvedProofs` even when the request carried `proofRefs`, nothing persisted, and no `certifyContent` call made.
- **An older sender against a full receiver.** It reads every block `missing` and behaves exactly as today; `confirmReplicated` already does not count such a peer.
- **A full receiver answering an announcement.** Expect `out-of-space` with no reference read and no `holdResponsible`; the announcer's drain counts it as a failure and asks again on a later pass; the growth arm reports the reference incomplete; the release arm still requires `stat`-confirmed `whole` holders.
- **A `put` or `pin` on a node at its allotment.** `NodeOutOfSpaceError` with the measured figures, no piece written, no record written. A `pin` on a blob already whole here is refused too — the accepted sharp edge, stated in `docs/blobs.md` §Holds.
- **A full node still serves.** `get`, `stat`, piece serving and fetches already in flight are ungated.
- **A commit whose pend was approved still applies.** Nothing here refuses inside an apply; that refusal is sibling ticket `a-full-cohort-member-refuses-a-pend`'s.

## Tests

One spec added, in `packages/db-p2p/test/local-blob-service.spec.ts`:

- **"a put on a node with no room writes no piece and no record, and never reads the source"** — pins the part that is easy to implement wrongly and invisible when it is: a refusal after three pieces leaves three pieces. It asserts the typed error and its two figures, that the piece store is empty, that `kv.list(BLOB_RECORD_KEY_PREFIX)` is empty, that the source generator was never pulled, and that `stat` still answers on the same service.

Nothing else was added, per the ticket: the push and announce refusals are one guard reading one predicate and returning a value, `SATISFYING_ANSWERS` is a constant, and the senders' handling is reporting. **Honest gap for the reviewer to weigh**: `replicateGrown`'s out-of-space branch is the one piece of this change with real branching that no test covers — it reorders the per-block outcome rules and changes what the monitor is told, and its interaction with the concurrent-block `fullPeers` set is the subtle part. If any arm of this change earns a test, it is that one.

## Tripwires parked

None new. The existing `NOTE:` on `StoragePressure.stage()` — that a gate reads the last sample, so a node can accept up to one sample interval's data past its limit — now covers `refusingNewData()` and `ownWriteRoom()` too, since all three read the same sample; the tripwire text and its remedy ("add the bytes accepted since the last sample to the reading rather than scanning on the gate") are unchanged and still apply.

## Review focus

- The `blob-copy-drain.ts` `noteFailure` reading, above.
- `replicateGrown`'s ordering: out-of-space is checked **before** `result.confirmed`, so a block whose floor WAS met is still reported incomplete when any reported peer was full. That makes it appear in `RebalanceReactionResult.underReplicated` — reporting only, nothing is released off that list — but it does mean the monitor re-detects such a block on its next check.
- The pass-scoped `fullPeers` set is read after a block's confirm returns, so it includes peers a *concurrent* block's push found full. I believe that is right (one pass, one verdict per peer) but it is a deliberate choice, not an accident.
- `handlePush` omits `unresolvedProofs` on an out-of-space answer. The sender's `pushToPeer` short-circuits on `outOfSpace` before it would read that field, so the "an answer with no `unresolvedProofs` counts as unresolved" rule is never reached — worth checking that both halves stay in step.
- Whether `requireRoomForOwnWrite` belongs after `assertOwner` in `put`/`pin` (argument validation first) or before it. I chose after, so a bad owner keeps the error it gets today.
