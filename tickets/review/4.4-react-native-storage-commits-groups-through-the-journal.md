# React Native storage commits groups through the journal

Implement handoff. Fifth of five tickets from the retired plan `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). The blocked `react-native-storage-syncs-once-rn-leveldb-can` is the one step left: a release of `rn-leveldb` whose batch write takes a sync flag.

## What landed

**The driver surface says whether it can sync, and only writes batches.** `LevelDBLike` (`packages/db-p2p-storage-rn/src/leveldb-like.ts`) gained `readonly canSync: boolean`, and `LevelDBWriteBatchLike.write` takes `{ sync?: boolean }`. `put` and `delete` are gone from the interface: every write this package makes is a `batch().write(...)`, so no unsynced direct write can sit in an old LevelDB log file outside the journal's reach. The `rn-leveldb` adapter (`src/rn-opener.ts`) reports `canSync: false` and throws when asked to sync (a caller bug). The native module's declared shape (`RNLevelDBNative`) is unchanged, so the Quereus plugin sharing it is unaffected. The `classic-level` test adapter and the upgrade-check writer's adapter report `canSync: true` and pass the flag through; the writer's adapter keeps its `put` and `delete` because published older builds call them.

**`LevelDBJournalStore` replaces `LevelDBStoreDriver`** (`src/leveldb-storage.ts`). Reads are the old driver's, same tags and encodings, so data an earlier build wrote reads unchanged and an old database has no journal, so the first open applies nothing. The journal is tag byte `0x07` (`TAG_JOURNAL` in `src/keys.ts`): a record under its sequence as 8 bytes big-endian, the applied-through mark under the bare tag, which sorts first. `appendJournal` is one unsynced batch; `applyJournal` is one batch over the data tags and the journal written `{ sync: db.canSync }`; `readJournal` is one drained scan that leaves out a record that does not decode or whose decoded number differs from its key's, and reads a mark that is not 8 bytes as 0. `durability` is `'power-loss'` when the handle can sync, else `'process-crash'`; the `NOTE:` there names the blocked ticket. `LevelDBRawStorage(db, options?)` is now `KvRawStorage` over `WriteGroupDriver` over `JournalBatchBackend` over the store, with `close` declared always present. `index.ts` exports `LevelDBJournalStore` in place of the driver, plus the two option types.

**`LevelDBKVStore` sits on a `WriteGroup<string>`** as the browser store does: `set` and `delete` resolve into memory, `get` and `list` read the overlay over the `TAG_KV` range, and a flush commits one batch written `{ sync: db.canSync }`. `loadOrCreateRNPeerKey` writes a new key as one such batch.

**Upgrade-check** keeps one `LevelDBRawStorage` and one `LevelDBKVStore` per open in both the reader (`test/current-build.ts`) and the writer (`writer/write-scenario.mjs`), returns the same storage from `storage()`, and closes both before the handle, as the `fs` case does.

**Docs.** `packages/db-p2p/docs/storage.md`: the Invariant 6 driver table row, the journal-backend paragraph, the *Rule 3 past the crashes a store names* paragraph, the per-backend survival table row, and the kernel composition paragraph. `docs/correctness.md` §1.2 and the Theorem 6 backend caveat. `docs/debugging.md` gained a `db-p2p-storage-rn` namespace row for the `read-journal` line. The package README has new persistence, durability, identity and tests sections. The retired plan slug no longer appears outside `tickets/`.

## Behaviour the reviewer should hold it to

- On a handle that cannot sync (every phone today): a flushed group is one unsynced batch carrying the group's entries and the mark, nothing is appended, `whenDurable` settles at once, no deadline timer is armed, `durability` is `'process-crash'`.
- On a handle that can sync: a relaxed flush appends one unsynced batch on the journal tag alone; the overlay serves the group; the data tags do not hold it; one synced batch over data tags and journal applies it when the deadline timer fires, sets the mark and deletes the record. A strict flush applies at once.
- A second storage over the same handle, the first never closed, applies the appended records at its open and reads them back: what the process going away leaves behind is recovered.
- A batch that fails leaves the database untouched on disk and latches the storage (rule 5): the next flush rejects with `StoreFailedError` whose `cause` is the batch's error.
- Process crash now loses an unflushed group whole, where the old driver kept each write individually. By design; the README and the survival table say so.

## Tests added, each beside what it pins

In `packages/db-p2p-storage-rn/test/leveldb-storage.spec.ts`, over `classic-level` with an injected `setTimer` and a batch-write spy (`test/support/spy-batch-writes.ts`, which records each write's `sync` flag and the tag bytes it touched, and can present the handle as unable to sync):

- the conformance suite over the composed storage, persistent, with cleanup closing the storage before the handle (re-pointed, not new);
- *a batch write that fails leaves the database untouched and latches the storage*: rule 5 at this layer, with the on-disk state read by a fresh storage (rewritten from the old promote-failure case);
- *readJournal leaves out a record it cannot trust and reads a malformed mark as 0*: the `JournalStore.readJournal` contract over LevelDB's byte encoding, three shapes;
- *a relaxed group is appended unsynced and applied synced when its deadline is due*;
- *journaled groups survive the process going away: the next open applies them*;
- *on a handle that cannot sync, a flushed group is one unsynced batch and nothing is journaled*;
- *the mark survives its encoding above 32 bits*: the 8-byte mark round trip through `BigInt`.

In `test/leveldb-kv-store.spec.ts`: *flush() commits the writes since the last flush as one synced batch on the kv tag*. The identity spec's collision case now flushes and closes the key-value store it opens.

## Known gaps and judgement calls

- **Nothing cuts the power.** The tests check which batches were written and whether each asked to sync. That `classic-level` honours the flag with an `fsync` is its own documentation; the phone's survival of a hard reset waits on the binding and the device check the blocked ticket lists.
- **The `rn-leveldb` adapter is not unit-tested** (it needs the native module), so its new throw on `write({ sync: true })` is covered only by inspection and by the spy mirroring it. This was the adapter's state before too.
- **The fixture writer's LevelDB close was changed without being run.** `writer/write-scenario.mjs` runs inside a published build's scratch install during a release step; it now closes the two stores (with `?.()`, since older builds have no `close`) before the handle. The reader side of the same change is exercised by the upgrade-check suite.
- **`readJournal` logs on the package's plain channel**, not an `:error` sub-channel: the storage packages' loggers have none, unlike db-p2p's. Same as the browser store.
- **Tests open a second `LevelDBRawStorage` over one handle** as a reader with an empty overlay, which Invariant 5 forbids for production; each such reader holds nothing and is closed.
- **`applyJournal` on a cannot-sync handle writes the mark on every group**: one extra small put per flush, inherent to applying through the journal store rather than beside it. Not measured; negligible next to the group's own entries.
- The `JournalRecord` seq-versus-key check in `readRecord` is this store's own strictness beyond the browser store's; a record is left out when the two disagree, which recovery treats as a gap.
