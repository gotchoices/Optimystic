# Blob `announce` and `held` can be sent — review handoff

Second of three parts of `feat-blob-announcements-are-answered`. The receiver (answering `announce` / `held` for real) is the third part, `feat-blob-announcements-are-answered`, already in `implement/`. This part adds the sending side and the `responsible` hold's scope. Nothing in production calls the new methods yet.

## What was built

- **Scope bound.** `MAX_BLOB_SCOPE_CHARS = 1024` (UTF-16 code units, `scope.length`). `blobScopeProblem(scope)` in `blob-protocol.ts` is the one rule both ends apply: `scopeField` throws `BlobProtocolError` for an empty or over-cap scope, so the service answers `refused: malformed` before `onAnnounce` runs; the client throws `RangeError` for the same before opening a stream. `BlobRequest`'s `announce.scope` is now typed `BlobScope` (an alias of `string`).
- **Client.** `BlobProtocolClient.announce(peer, ref, scope, options)` → `BlobAnnounceAnswer`, and `held(peer, ref, options)` → `void`. Each parses the ref locally (`BlobRefError`), then asks the optional `acceptance` init hook and throws `BlobPeerRefusesError` on `refuses` before dialing (`openAccepted`), then follows `stat`'s exchange shape under the same `ProgressDeadline`. Log lines `client:announce peer=… ref=… answer=… ms=…`, `client:held peer=… ref=… ms=…`, and `client:peer-refuses-blobs peer=… kind=…` on the pre-dial refusal. `stat`, `announce` and `held` now share `ClientExchange.readSoleAnswer` (read the header, require end of stream, fail/finish) instead of three copies of the try/catch/finally; `readAnswer` is generic over every request kind.
- **Acceptance.** `packages/db-p2p/src/blob/accepts-blobs.ts`: `BlobAcceptance`, `BlobPeerRefusesError`, `blobAcceptanceOf(keyNetwork, blobProtocol, peerIds)`. Over the new `Libp2pKeyPeerNetwork.protocolSupport(protocol, peerIds)` → `listed | unlisted | unknown` (exported type `ProtocolSupport`), which reads the same `PeerRecordCache` as `peersServing`; `peersServing` is now expressed over it (`listed` only). This node is left out of `protocolSupport`'s answer, as it was from `peersServing`'s. `wireBlobFetcher` passes `acceptance` to the node's client. Exported from both `index.ts` and `rn.ts` (the client, which imports it, is on the react-native entry; the module's only import is type-only).
- **`responsible` hold scope.** `BlobHold`'s `responsible` variant carries `scope: BlobScope`; `holdProblem` refuses a `responsible` hold without a non-empty string scope. No stored record carries one yet, so not a format change.
- **`LocalBlobService`.** `holdResponsible(ref, scope)` (empty scope → `RangeError`; adds the hold or replaces an existing one's scope and `at`, keeps every other hold, creates a `whole: false` record when none; through `changeRecord`; flushed). `responsibleScope(ref)` (a malformed record throws `BlobRecordFormatError`). `responsibleRefs()` (reads every record; a `BlobRecordFormatError` is logged `record:unreadable` and skipped, any other error — a key-value store failure — propagates; `NOTE:` on the per-record read cost).

## Things to look at

- **A peer mid-identify can read `refuses`.** `protocolSupport` takes any non-empty protocol list as the peer's statement (the ticket's chosen reading, matching `membershipOf`). A peer of this network whose identify has not landed can hold a partial list — the protocol of one stream it opened, merged by libp2p — and so reads `unlisted` → `refuses` for that moment. Parked as a `NOTE:` at `blobAcceptanceOf`: harmless while a refusal skips one attempt; the owed-copies drain (`feat-blob-owed-copies-are-drained`, which counts `BlobPeerRefusesError` as a failed attempt toward its give-up rule) should not remember it past `peer:identify`.
- `holdResponsible` always writes (it refreshes `at` even when the scope is unchanged), so each call costs a key-value write and a flush. Intended: `at` is "last verified".
- `BlobProtocolServiceInit.onAnnounce` still types its scope parameter as `string`; identical to `BlobScope`, left for the third part, which sets that hook.
- docs/blobs.md: the `announce` table row carries the bound; a paragraph says a sender does not dial a peer whose list lacks the protocol; §Holds says the `responsible` hold records its scope and names the three store methods; the "To be built" sentence now says only the answering side remains.
