GitHub #52, first of three chained tickets. `a-secondary-index-serves-range-predicates` (0.36) adds range bounds on the same walk and `a-long-index-walk-finishes-by-scanning-the-table` (0.37) bounds what an unbounded walk costs. Both build on what landed here: `walkDelivering` for the column rule, `inEngineOrder` for the read-time order, `indexValueRange(key, ascending)` plus `IndexManager.walkEntriesIn` for the entry loop, and `executeIndexScan` taking a list of `KeyRange`s.

## What was built

**Plan time** (`getBestAccessPlan` in `optimystic-module.ts`). The planner now keeps a list of candidates and picks by `pricedWithSort`: a candidate's own cost, plus `rows · log2(rows) · 0.1` when the request wants an ordering the candidate does not deliver (the constant mirrors the memory module's unexported `SORT_COST_PER_COMPARISON`). The reported `cost` stays the plan's own. Three sources of candidates:

- The existing scan, partial-key and primary-key candidates, unchanged in cost.
- The equality seek on each non-partial index (`equalitySeekCandidate`), now asking `walkDelivering` whether the seek's prefix walk delivers the ordering; a multi-seek never does. A seek that delivers one returns `orderingIndexName` and an `indexDescriptor` with `reverse`.
- New: an ordered walk of each non-partial index (`orderedWalkCandidate`), when `walkDelivering` accepts it and at least one required column is one the walk itself orders. It claims no filter, costs one descent plus the rows wanted (`min(rows, limit + offset)` when the request carries a limit, which only `rule-minmax-index-boundary` does), reports the table's row count, and names no `indexName`, which sends it down the engine's ordering-only arm (`plan=0`, no arguments). An index the instance does not maintain is skipped as a walk candidate rather than chosen and refused.

**The rule** (`walkDelivering` in `schema/index-walk.ts`). The walk key is the index columns then the primary-key columns not among them. A column pinned by a usable `=` or single-element `in` (and whose own collation is BINARY, type not boolean/any/semantic) is dropped from the required list and skipped in the key. The remaining required columns must match the key positionally, each TEXT, BINARY on both the table column and the key column, not `hasSemanticOrdering`; all one direction, which sets `reverse`. `nullSafeOrderingPrefixLength` is asked about every consumed key column as if descending, so a nullable ordered column is claimed only under a NULL-excluding filter, in either direction. The result also says how many required columns the walk itself orders (`WalkDelivery.orders`), so a walk is never proposed for an ordering made entirely of pinned columns.

**Read time** (`runQuery`, `executeIndexScan` in `optimystic-module.ts`). `scanIndexName` is also set for a secondary index with `plan=0` and no arguments, inside the synchronous view-building block. Direction is `filterInfo.accessPath.index.reverse`. `indexScanRanges` turns the sought keys into `indexValueRange(key, !reverse)` ranges (the empty prefix brackets the whole index); `verifiedIndexRows` is the old entry loop over `IndexManager.walkEntriesIn`; `executeIndexScan` passes a single range's rows through `inEngineOrder` and a multi-seek's rows through untouched. `inEngineOrder` holds rows whose key columns contain a UTF-16 unit at or above U+D800 in runs, sorted by `compareSqlValues` at the next pivot row or the end, so the engine's code-point order comes out of the tree's code-unit order. The `index:seek` trace gains `dir=asc|desc`.

**Docs.** README's ordering paragraph; a new section "An ordered read walks a secondary index" in `docs/internals.md`; the `dir=` field and the surrogate-run note in `docs/debugging.md`. `yarn lint:docs` passes.

## Measured end to end

`transactor='test'`, Node 24, median of 7, `select Id from M order by Timestamp desc, Id desc limit 100` with an index on `(Timestamp)` and a TEXT `Id`, against the same table with no index (so the engine scans and sorts). The plan is `LIMITOFFSET INDEXSCAN`; the two tables return the same page.

| rows | page of 100, walk | page of 100, scan and sort | whole table, walk | whole table, scan and sort |
|---|---|---|---|---|
| 2,000 | 7.4 ms | 12.2 ms | 66.7 ms | 13.1 ms |
| 5,000 | 11.8 ms | 42.2 ms | 139.8 ms | 45.7 ms |

The page is 1.7 to 3.6 times faster end to end, well below the 35 to 100 times the planning ticket's bare-loop figures suggested: a page pays one tree descent per row (`readRowAt`) plus the refresh of two trees, which is most of its 7 ms at 2,000 rows. The unbounded `order by` is 3 to 5 times slower than today, as the planning ticket accepted; 0.37 is what closes that. The scratch script is not in the tree; the figures above are what it printed.

## Known gaps and things to look at

- **Committed read with an interleaved commit is not tested.** The committed arm is covered by the `max(t)` CHECK over `committed.<Table>` with a staged row; the two-database interleave of `committed-read-interleave.spec.ts` was not extended to an index walk. The route is the same synchronous block as before, so the pinning argument is unchanged, but nothing new pins it under an interleaved commit.
- **Unmaintained index skipped at plan time is by inspection only.** Manufacturing an index the catalog lists but the instance does not maintain needs the two-handle withheld-index setup; no test was added for `orderedWalkCandidate`'s skip.
- **Pinning trusts the column's own collation, not the index column's.** `pinnedColumns` judges `indexSeekCanBeTrusted(column, column.collation)`, since an unclaimed residual compares under the column's collation and the engine extracts an equality on a BINARY column only when its effective collation is at least as fine as BINARY. The planning ticket's text said "passes `indexSeekCanBeTrusted`" without naming the collation; a reviewer should confirm the engine never hands a module a `usable` equality on a BINARY column whose comparison is coarser (a `collate nocase` literal).
- **`inEngineOrder` runs on every single-range index scan**, claimed ordering or not, so a plain equality seek now pays one regex test per key column per row. Negligible beside the row fetch, and it keeps the module from having to know what the engine trusted.
- **Tie-break generalised.** The "longer seek wins a cost tie" rule now applies across all candidates, where it used to apply only within the index loop. A tie between a primary-key multi-seek and a partial-key scan would now prefer the multi-seek; no test observed a change.
- **The `IndexSchema`-less `ColumnSchema` alias** (`type ColumnSchema = TableSchema['columns'][number]` in `optimystic-module.ts`) is still used by `matchEqualitySeek`; `index-walk.ts` imports the engine's `ColumnSchema` type directly. Same type, two spellings.
- **The whole-index range is the empty prefix's `indexValueRange`**, not an unbounded `KeyRange`, so `probe.keys` prints the documented empty `seek=`. An entry whose key is not well framed (a tag at or above `\x03`) would be outside it; the integrity check's `allEntriesIn` keeps its unbounded range for exactly those.
- **No tripwire filed** beyond the one the ticket asked for, at `IndexManager.walkEntriesIn`: a live walk that has yielded throws on a concurrent change where the table scan resumes.
- Not in scope and not done: a walk of the primary-key tree itself for `order by Id` on a TEXT primary key (the main tree is in that order already); the next two tickets.
