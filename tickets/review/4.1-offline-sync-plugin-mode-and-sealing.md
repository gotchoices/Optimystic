First of the five stage-4 tickets of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). The db-core queue now sits behind the plugin: a database enters and leaves offline mode, a commit begun in the mode is sealed into one queue entry under its `StampId()` instead of reaching storage, the queue's collection-level events are reported as table-level statuses, and a drained entry produces the same durability report an online commit does. Everything is in memory.

## What landed

- **`OfflineMode`** (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`), one per registered plugin, exposed as `plugin.offline`: `enter` / `exit` / `isEntered`, `whenDrained`, `dispose`, `onStatus`, `onQueueState`, `queueState`, `entries`, `status`, `discard`, `outcomes`, `acknowledge`. It owns one `OfflineQueue` per `Database` (built at registration, drain idle until the first entry) and translates every queue status: entry id to `transactionId`, collection ids to deduplicated qualified table names through the bridge's new `tablesOf`, `committed` to the bridge's `SqlCommitDurability` plus `kind`, `failed`'s `error` through `mapCommitRefusal`. Terminal outcomes are retained for `outcomeRetentionMs` (default seven days), pruned lazily on access and on each new outcome, no timer. The status types are in `offline-status.ts` (`QueuedTransactionStatus`, `QueuedTransaction`, `TransactionOutcome`, `OfflineModeState`).
- **Registration config** `offline: { expireAfterMs?, outcomeRetentionMs?, recheck?: { baseMs?, maxMs? } }`, parsed by `parseOfflineConfig`; any other key under `offline` (or `offline.recheck`), or a non-positive number, is refused at `register` with a message naming the key. `offline` is a JSON object, so it fits the existing `Record<string, SqlValue>` config type with no widening.
- **The bridge** (`txn-bridge.ts`): `TransactionState.acknowledgement` fixed at `beginTransaction` from the controller's flag; `commitTransaction` seals a `'local'` transaction's staged dirty trees through `OfflineMode.enqueue` (`sealForLocalAcknowledgement`), tearing the transaction down as a successful commit does but leaving the degraded latch as it was; `localAcknowledgementSet` falls back to the network route, logging `offline:local-ack-unavailable`, for a tree without a collection, collections on different transactors, or two instances over one collection id; `reportCommitDurability` is package-visible, takes a `demanded` flag and returns the report it built; `configureTransactionMode` throws `SessionModeRefusedError` while the mode is entered or entries are queued; `attachOfflineMode` setter; `tablesOf` read accessor. The `commit:collections` trace gains `mode=offline`.
- **The factory** (`collection-factory.ts`): `setSealedRefusedListener`, set once by `register`, passed as `{ onSealedRefused }` to both `Tree.createOrOpen` and `Tree.open`, so every data, index and catalog tree reports refusals to this database's queue.
- **db-core**: `OfflineQueue`'s constructor no longer takes a transactor; `send` builds the per-entry coordinator over the remaining collections' shared `transactor` (`sharedTransactor`), throwing a drain-stopping defect if they differ. Both existing specs updated.
- **Shared listener helpers** moved out of the bridge into `listeners.ts` (`addListener`, `notifyListeners`), used by the bridge and the controller; the bridge's throw-log lines keep their names.
- **Exports** from both entries: `OfflineMode`, `OfflineModeRefusedError`, `SessionModeRefusedError`, db-core's `EntryNotDiscardableError`, `UnknownEntryError`, `QueueDisposedError`, and the status types.
- **Docs**: README section "Offline mode" (registration, enter/exit/whenDrained, the status shapes with a listener example, the queue state, queries, the session-mode refusal, the promise-to-try rule, and a "Not yet in this stage" list). docs/offline-sync.md §Application interface now names what exists and corrects the shapes (`changedTables`, the extra `queued` fields, `OfflineModeState`).

## Deviations from the ticket, each deliberate

- **The controller always demands the durability report** for a drained commit, listeners or not, rather than only when a durability, fully-held or status listener is registered: `outcomes()` and `status()` retain the `committed` status, which IS the report. Cost: every drained commit is followed by the `DurabilityFollower` (bounded by its 10 000 cap).
- **The controller does not take the `Database`.** Nothing in this ticket needs it; ticket 4.2 adds it with `notifyExternalChange`.
- **Two refusal classes**, not one: `OfflineModeRefusedError` (reason `'session-mode'`) for `enter()`, and `SessionModeRefusedError` (reason `'offline-mode'` or `'queued-entries'`) for `configureTransactionMode`.
- **Status names**: `QueuedTransactionStatus` as the design doc; the queue-wide state is `OfflineModeState` (the doc said `OfflineQueueState`, which is db-core's name), and `queueState()` exists beside `onQueueState`.
- **The expiry scenario is not tested at the plugin level.** Stage 4 wires no reachability gate, so the drain sends the head at once; the first attempt runs the write-ahead wrapper and puts the entry in doubt, and a promise shortfall does not clear doubt (pinned in `packages/db-core/test/offline-queue.spec.ts`: "an attempt was about to be sent, so the entry is in doubt"). An entry queued against an unreachable cohort can therefore neither be expired nor discarded once the drain has tried it. The expiry rule itself is pinned in db-core. The discard-before-send case withdraws the entry from the synchronous `queued` delivery, ahead of the drain's first iteration, which is deterministic. **This also affects ticket 4.3's "timeout, never sent" case**; a note was appended to that ticket.
- **The README gap for a network-acknowledged commit behind a non-empty queue** is stated as it actually behaves, by inspection of `Collection.sync` / `updateAndSync` / `getPendingActions` (each throws `SealedSegmentsError` over sealed segments): a commit that writes a table with queued entries fails with `SealedSegmentsError` and is rolled back cleanly; one that writes other tables commits ahead of the queue. Ticket 4.3 closes both.

## Use cases to validate

- Register with `offline: { recheck: { baseMs: 20, maxMs: 100 } }` on a two-node mesh (`createMeshDbNode(transactor, config)` now takes extra config); `enter()`; insert; the `queued` status arrives inside `db.exec`; `whenDrained()`; the row is on the other node and `onCommitDurability` saw the same report the `committed` status carries.
- Make node B unreachable with `mesh.failures.failingPeers`: the entry reports `queued` with `waitingFor: 'cohort'` (a promise shortfall sorts as `cohort-unreachable`, as the ticket predicted; no wrapped transactor was needed), A reads its own row, B holds nothing, `entries()` lists it; clear `failingPeers` and the re-check timer drains it.
- `enter()` or `exit()` between `begin` and `commit` changes nothing about that transaction.
- `exit()` with entries queued publishes `mode: 'online'` with the depth unchanged and the drain continues.
- Session mode and offline mode refuse each other in either order, including with entries queued after `exit()`.
- Two tree instances over one collection id in one transaction fall back to the network route with no status.

## Tests added

`packages/quereus-plugin-optimystic/test/offline-mode.spec.ts`, eleven cases on the two-node mesh (plus the `test` transactor for the session-mode and shared-id cases):

- an offline commit with the cohort reachable: `queued`, `submitting`, `committed` once each under the `StampId()`, `tables` is `['main.Notes']`, the `committed` status's `durability` is the very object `onCommitDurability` received, the row is on B, and `status` / `outcomes` / `acknowledge` retain and forget the outcome.
- an offline commit while B is unreachable: read back on A, listed by `entries()`, absent from B, `waitingFor: 'cohort'` reported, queue state `{ mode: 'offline', depth: 1, waitingFor: 'cohort' }`, drained to B on reconnect with `committed` exactly once.
- three entries across a table and its secondary index drain in queue order; after each `committed`, an index-driven read and a full scan on B agree and B holds at least that many rows; both trees hold three entries.
- the acknowledgement is fixed at begin: `enter()` after `begin` leaves the commit network-acknowledged (no status, row on B); `exit()` after `begin` leaves it queued.
- `exit()` with entries queued: the mode change is published, both entries land in order on reconnect.
- a `select` and an update matching no row in offline mode queue nothing.
- an autocommit statement's `queued` status is delivered during the `db.exec` that committed it.
- discard before send (from the `queued` delivery) fails the entry with `discarded`, `changedTables` names the table, the row disappears while the seed row stays, the outcome is retained; discard during `submitting` throws `EntryNotDiscardableError` with `because: 'submitting'`.
- session mode first refuses `enter()` (`OfflineModeRefusedError`, `'session-mode'`); offline mode first refuses `configureTransactionMode` (`'offline-mode'`); entries queued after `exit()` refuse it (`'queued-entries'`).
- two tree instances over one collection id (bridge driven directly, model `legacy-batch-shared-collection-id.spec.ts`): `acknowledgement` is `'local'`, nothing is queued, both rows are durable, the bridge is not degraded.
- `register` refuses `offline.journal`, a negative `expireAfterMs`, and `offline.recheck.base`.

No new db-core or db-p2p tests: the two existing queue specs only changed their constructions. `test/adapter-integration.spec.ts` gained the required `acknowledgement` field on its two state literals.

## Known gaps and what the reviewer should look at

- **By inspection only** (as the ticket allowed): `plugin.dispose()` while entries are queued (queue disposed after the bridge; `whenDrained` rejects); a refusal for an entry another queue holds is ignored by the queue; the degraded latch is neither set nor cleared by a local acknowledgement (the `reconciled` flag in `commitTransaction`); the controller reads none of the bridge's single-writer state (check the diff: it touches only `isTransactionModeEnabled`, `tablesOf`, `mapCommitRefusal`, `reportCommitDurability`).
- **A tree holding only sealed segments** answers `hasUnsyncedChanges()` true, so it enters `localAcknowledgementSet` and is then simply not part of the entry (`sealPending` answers false). Harmless, but it means such a tree counts toward the "two instances over one id" and "different transactors" checks.
- **The in-doubt consequence above** is a user-visible limitation of this stage, documented in the README; it ends when stage 6's reachability port keeps an entry unsent while the cohort is unreachable.
- **Tripwire**: `NOTE:` at `pruneOutcomes` in `offline-mode.ts`, the O(n) walk of retained outcomes per access.
- Later tickets consume: `changedTables` on `failed` (4.2), `OfflineMode.enqueue` returning the listed entry and `hasQueuedEntries` (4.3), `tablesOf` on the bridge (4.2, 4.4), `OfflineModeState.readsServedLocally` placeholder (4.5).
