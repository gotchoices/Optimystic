# Review: a narrowed ring sheds its large files

## What landed

A move-out previously handed over only blocks, so a node whose disk was mostly blobs could shed from ring 3 to ring 6 and free nothing. The ring now bounds blobs the same way, in two halves that have to be read together.

**The shed pass.** `RingShiftCoordinator` gained one callback beside `onRelease` — `onNarrowed({ from, to })`, fired from Phase C of a move-out only, immediately after the narrower slice is advertised and *before* the awaited `onRelease` (so a block-ledger fault, which `onRelease` is deliberately allowed to surface, cannot swallow the blob pass). The coordinator still knows nothing about blobs. The node factory binds the pass through `LateServingBindings.ringNarrowed`, the same late-binding seam `requestReleasedBlockSweep` uses, because Phase C is wired inside the Arachnode gate while the blob monitor and reaction are built later. The pass itself is `shedNarrowedBlobs` in the new `packages/db-p2p/src/blob/ring-shed-pass.ts`: select over `heldBlobRefs`, build each shed reference's owners from its own `findCluster` cohort, hand them to the reaction's release arm, then `releaseResponsible` what confirmed and `retainLost` what did not. It is hopped off the callback and its rejection logged.

**The gate.** `BlobAnnounceReceiver` now tests responsibility as "the slice I serve covers this key **and** my own view of the cohort includes me" (`responsibleFor`), through `isServingHolder`, so a node mid-shift still accepts for the range it is still serving. Reader repair goes through the same predicate, so a read cannot re-adopt what an announcement would be refused. The slice is read live off `ArachnodeFretAdapter.getMyArachnodeInfo`; absent (client, Arachnode disabled, no FRET) means the whole keyspace, as ring 0 does.

**One release implementation.** `BlobCohortReaction.releaseLost` is now public and takes `(refs, owners, floor, acceptance?)`. Both paths call it. It carries the partition guard itself now (retain everything on a detected partition), so every caller gets it without making the check; `handleRebalanceEvent` keeps its own early return because it also has growth outcomes to report. `acceptanceOf(event)` split into `namedPeers(...maps)` + `acceptanceOfPeers(peers)` so the event path still classifies both arms' peers in one call while the ring path classifies its own.

**One coverage predicate.** `narrowingSheds(narrowing, coord)` in `arachnode-partition.ts`, read by both `RingShiftCoordinator.computeShedBlocks` and `selectShedBlobRefs`.

## What to poke at

- **The predicate's direction is the one failure that loses data.** `selectShedBlobRefs` must return the half the node *gave up*. Inverted, a narrowing releases the half it keeps. That is what the new spec pins; read it against `narrowingSheds` and `partitionCovers`.
- **The coordinate.** A blob's ring coordinate is `hashKey(routingKeyForBlob(ref))` — the routing key hashed once, because `routingKeyForBlob` is the 32-byte digest and the key network hashes it. Comparing a partition prefix against the un-hashed digest would be a prefix of the wrong space and would select an arbitrary half. Worth confirming independently (`coordOf` in `ring-shed-pass.ts` against `buildOwnersMap` in `ring-shift-coordinator.ts`, which does the same for blocks).
- **Partitions come from the callback, never re-read.** A later shift could have moved the node's advertisement by the time the pass runs.
- **`onNarrowed` fires from nowhere else.** A rolled-back shift must shed no blobs; a move-in must shed none either.
- **The late binding's lifetime.** Set after `monitor.start()`, cleared in the blob block's stop wrapper beside `offHoldsFeed`, and cleared in its catch. Before it is bound, and on a node with no blob monitor, a narrowing sheds blocks only — which is the documented degradation, not a silent one.
- **The gate's order.** Slice before cohort, because the slice is local arithmetic (one SHA-256) and the cohort is a peer-store sweep. Both answer `'not-responsible'`, so the order is only about cost — confirm it does not disturb the "nothing is read before it must be" ordering `docs/blobs.md` §Who may fetch and who may store sets out.
- **Ring 0 really is the whole keyspace.** `RingSelector.calculatePartition(0, …)` answers `undefined` and `partitionCovers(undefined, …)` answers true, so a node with Arachnode disabled behaves exactly as before. Verified by reading both; the end-to-end blob specs (which run on real meshes) passing is the other half of that evidence.

## Honest gaps

- **The pass itself has no test** — only its selection half does. `shedNarrowedBlobs`'s owners-building, its call into the release arm, and its application of the answer (`releaseResponsible` / `retainLost`) are covered by types and by the specs of the pieces they call, not by a test of the pass. The ticket set that bar deliberately ("no test for the release itself, for the `decided` gate, or for the callback wiring"); if you disagree, the cheapest useful addition is a doubles-based test that the answer is *applied* (a released reference loses its hold, a retained one does not), since that is the part which could silently do nothing.
- **An unconfirmed shed blob is not retried soon.** `RebalanceMonitor.retainLost` ignores an id this node is still responsible for, and a ring narrowing does not change a cohort — so for the usual case (still in the cohort, outside the slice) the `retainLost` call is a no-op and the blob is re-offered only by the next narrowing or a cohort departure. The node keeps the bytes meanwhile, which is the safe direction but frees less than the narrowing asked for. Parked as a `NOTE:` tripwire at the `retainLost` loop in `ring-shed-pass.ts` with what to do if it bites.
- **A narrowed holder understates what it holds.** It answers `not-responsible` for a blob it still holds whole and still serves, so an announcer stops counting it as a holder before it has actually released — conservative for the length of the handover, and permanent where every member has narrowed past the key (the cohort-wide decline the docs now state). Parked as a `NOTE:` at the `responsibleFor` call in `announce-receiver.ts`.
- **One `findCluster` per shed reference, in turn.** A node narrowing out of a deep ring sheds most of what it holds, so that is the pass's cost. `NOTE:`d at `ownersOf`; the lookups are independent and could go in a bounded parallel run like the reaction's arms.
- **A node that *starts* at a deep ring sheds nothing.** `RingSelector.determineRing` answers `MAX_RING_DEPTH` for a node below `minCapacity`, and that is not a narrowing, so the pass never fires for it: it stops accepting blobs outside its slice but keeps what it already holds until a cohort change. Stated in `docs/blobs.md`; flagging it because it is the one shape where "narrowing frees the disk" does not apply.
- **The partition guard inside `releaseLost` is unreachable from the event path** (`handleRebalanceEvent` returns earlier). Deliberate redundancy so the rule lives with the decision rather than in each caller, but it is dead code on the path that has the most traffic.
- `RingShedOutcome.unresolved` is returned and only logged — no caller reads it.
