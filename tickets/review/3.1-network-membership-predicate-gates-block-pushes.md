# The membership predicate gates the raw-ring replication paths

The prereq added `NodeOptions.isNetworkMember` and made the key network's cohort and coordinator choices obey it. Four senders bypass the key network and take candidates from FRET (the peer-discovery ring) directly, and FRET's ring membership is something any connected peer can join. Each of them now takes an optional `membership?: NetworkMembershipGate` — the same instance `createLibp2pNodeBase` builds once beside the key network — and drops every candidate it refuses before dialing. Absent gate → each filter is skipped, behaviour unchanged.

| Path | What is filtered | Consequence of a refusal |
| --- | --- | --- |
| `SpreadOnChurnMonitor.performSpread` | `targets` (expansion targets outside the FRET cohort) | not pushed; not in the spread event's `targets` |
| `RingShiftCoordinator.buildOwnersMap` | `qualifying` holders per shed block | neither pushed a shed block (the confirmer only pushes to the owners map) nor counted toward the floor; an unmet floor rolls the shift back |
| `RestorationCoordinator.restore` | my-ring candidates (`getMyRingPeers`) and each inner ring's partition-filtered list | never asked for an archive |
| `UnderReplicationDrain.pushablePeers` | connected peers | not pushable, so an entry owing only refused peers counts as `waiting` |

`RebalanceMonitor` and `BlockTransferCoordinator` take owners from `findCluster` and were covered by the prereq.

## Use cases to validate

- **Spread with a refused expansion target** (tested): FRET expands to `[self, p2, p4, p5]`, cohort `[self, p2]`, gate refuses `p5` → the pass targets and pushes only `p4`. Verified that the case fails with the filter removed.
- **Ring shift with refused peers in the band** (inspection): a refused peer is filtered before the Arachnode-info check, so with too few admitted qualifying holders `confirmReplicated` reports the block unconfirmed and `moveOut` rolls back to the old ring.
- **Restoration, every candidate refused** (inspection): at ring depth ≤ 0 this lands on the existing early return, which logs `restore:solo-node-skip` — the line reads "solo" even though peers exist and were refused. At deeper rings it walks to the existing `restore failed` line. A reviewer may want a distinct log line for the refused case; I left the existing one.
- **Drain, entry naming a peer refused after it was written** (inspection): the peer is never pushable, so the entry waits and its full-replication event does not fire while the refusal holds. A `NOTE:` at `pushablePeers` records this and the revisit condition. Side effect worth knowing: `forgetDisconnected(pushable)` now also forgets a refused peer's give-up count, so a peer the application re-admits is retried from scratch — the same treatment a reconnecting peer gets.
- **Self**: the gate admits self by construction; spread, ring shift and restoration already exclude self separately.

## Docs

`docs/internals.md` § Network Membership Predicate: the "background replication paths" bullet moved from *What it does not gate* to *What it gates*, naming each path and its consequence. A paragraph after that list states the property: apart from redirect targets and the opt-in dispute path, no peer this node chooses to send block contents to, or to ask for an archive, is one the predicate refuses. Content a refused peer pushes to this node is `authorizeInboundStream`'s business.

## Known gap the reviewer should weigh

While checking the docs claim I found a fifth FRET-direct sender outside this ticket's scope: the dispute service's `selectArbitrators` hook in `createLibp2pNodeBase` draws arbitrators with `fret.assembleCohort`, and a challenge carries the disputed `ClusterRecord`, transforms included. It is behind `dispute.disputeEnabled` (default `false`). I added it to *What it does not gate* rather than gating it, because the draw must stay deterministic across nodes (see the `NOTE:` there about `exclude`), and filtering by a node-local predicate breaks that unless every honest node's predicate agrees. Whether to file a ticket is the reviewer's call. No other FRET-direct path in `src` sends block contents (cohort-topic, matchmaking and the trust anchor send no block bytes; `NetworkManagerService.getCluster` / `getCoordinator` have no production caller).
