# Blob fetch building blocks — review handoff

The first half of the plan for `feat-blob-fetcher-verifies-and-resumes` (implement/2.42, which depends on this). Nothing here dials a peer or is wired into the node yet; the fetcher ticket wires and exports all of it (`index.ts`, `rn.ts`).

## What was built

**Scheduling constants** in `packages/db-p2p/src/protocol-limits.ts`: `MAX_BLOB_BACKGROUND_GET_STREAMS = 4`, `MAX_BLOB_FOREGROUND_GET_STREAMS = 8`, `BLOB_WAIT_RETRY_INITIAL_MS = 500`, `BLOB_WAIT_RETRY_MAX_MS = 8_000`.

**`blob-holders.ts`** (logger `blob:fetch`):

- `blobHolderCandidates(deps, ref, knownHolders?)`: hints first (deduplicated, in their order), then `findCluster(routingKeyForBlob(ref))` members not hinted, connected before not connected (stable). Then drops malformed ids (`peerIdFromString` refuses; logged together once per call as `holders:bad-peer-id`), self, peers `admittedBy(membership, …)` refuses, banned peers, and peers `keyNetwork.peersServing(blobProtocol, …)` does not list. Deprioritized peers move to the end in their order. A throwing `findCluster` logs `holders:cohort-lookup-failed` and counts as an empty cohort. The membership-predicate comment the plan asked for is at `isEligible`. Malformed ids are dropped before the predicate runs, so an embedder's predicate never sees junk.
- `unavailableOutcome(attempts)`: pure, the five-row table, with `PieceAnswer`, `PieceOutcome` and the result type exported as `UnavailableOutcome` (reason typed `Exclude<BlobUnavailableReason, 'not-here'>`).

**`blob-get-slots.ts`**: `FetchPriority`, `BlobGetSlotLimits`, `BlobGetSlots`. Two independent pools; per pool a FIFO queue where a free slot goes to the first waiter whose peer has no open stream of that priority (busy-peer waiters are skipped, not blocking). A new waiter joins the back and the pool re-grants, which is equivalent to "grant at once if possible" because after every change no queued waiter is grantable. Release is idempotent; an aborted waiter leaves the queue and rejects with `signal.reason` (at once when already aborted).

**`LocalBlobService.fetchStore()`** returns one `BlobFetchStore` object built in the constructor:

- `source`: the service's `localPieceSource`.
- `holdCached(ref)`: through `changeRecord`; adds a `cached` hold or creates a `whole: false` record with one; a record already holding `cached` is unchanged; `whole` is never touched. Not flushed. The `NOTE:` about eviction skipping blobs with a fetch in flight is on `holdCached`.
- `storePiece(ref, id, bytes)`: `parseBlobRef(ref)`, then `gate.shared(() => { sweeper.noteRecordChange(ref); pieces.put(id, bytes) })`. Not flushed.
- `markWhole(ref, size)`: `correctRecord(ref, true, size)` (never creates a record; failures logged).

`PieceSweeper`'s class comment now lists four writers, the fourth being a fetch storing a list piece over an orphan child, and why noting the ref closes it; `noteRecordChange`'s comment says fetched piece stores call it too; the older `walkRecord` `NOTE:` that described how fetches would stay safe now names `BlobFetchStore.storePiece`.

## Tests added

- `packages/db-p2p/test/blob-holders.spec.ts`: one case per row of `unavailableOutcome`'s table (none; all silent; corrupt beside not-held; silent beside not-held and corrupt; all not-held). This branching decides which error an application sees.
- `packages/db-p2p/test/local-blob-service.spec.ts`, *a piece present when a sweep first walked its held blob survives once its parent arrives*: a three-data-piece blob with its list piece absent and one data piece stored as an orphan; `holdCached`; a second held blob put after it so the records pass walks it second; the sweep paused on a `get` of the second blob's list root (`HeldGetPieceStore`); `storePiece` of the list piece during the pause; the sweep then reports `deleted: 0` and the orphan is still there. The test also asserts the paused sweep had already asked for the fetched blob's list piece, so it cannot silently stop exercising the race if the records order ever changes. **Verified as a reproduction**: with the `noteRecordChange` call removed from `storeFetchedPiece` it fails with `deleted: 1`. Pausing was arranged with the real store and sweeper; nothing is mocked beyond the paused `get`.

No test for `blobHolderCandidates`' filter order or `BlobGetSlots`, as planned (inspection; the fetcher's mesh tests exercise both). A reviewer may reasonably want a small unit test of `BlobGetSlots`' skip-the-busy-peer rule, which has real branching; it was left out per the plan.
