## What changed

A table instance now writes its description on initialization only when it **owes** the catalog one: it was built by `create table`, or a failed `apply schema` left its table without what the engine holds. That is the new `owesCatalogRecord` on `OptimysticVirtualTable`. `declaredColumns` is unchanged and still answers its own question.

An instance that owes nothing and finds a live record or a gravestone works from a **view** (`SchemaManager.viewOverRecord`) and writes nothing. The view has the engine's columns, because Quereus plans positions from its own catalog entry, plus the record's indexes over those columns. With neither a record nor a gravestone, the old arm still runs, with its storage-adoption guard and its write.

`addIndex` no longer writes a stale description. It refuses over a gravestone, translates its column positions to the record's by name, and refuses a column the record lost. `alterCatalogOnly` marks a table `written` for an initialization only if that initialization writes.

## Where this departs from the implement ticket

Please check these first; each was a judgement call.

- **Step 5 could not work as written.** The ticket proposed clearing marks when the undo batch commits. The reproduction showed the record had already lost the other machine's CHECK by the time the apply returned, before any later touch. The undo DDL's own first touch of the marked table writes the old description into the overlay that batch commits, so clearing at commit is too late. `beginSchemaBatch` now forgives what the refused batch owed, for the length of the next batch.
- **Step 5 judges by the engine's catalog, not by which tables the undo reached.** `settleOwedRecords` compares each table's engine entry with its entry when the apply began (`describesSameTable`). Same description: the apply was taken back, nothing is owed. Different: the engine kept something the record lacks. This needs no tracking in the hooks and removes both limitations the ticket proposed to accept, the mark clearing early and a second refusal leaving marks standing. A wrong "different" only keeps the mark, which is the old behaviour.
- **One more failure shape is covered by that rule.** A failed step unwound inside a batch whose commit is then refused had the same defect. The ticket did not list it.
- **The gravestone fix is in `getSchemaFresh`, not `addIndex`.** `saveCatalogOnly` had the same cached-copy fallback, so a catalog-only `alter table` could also bring a dropped table back. Both now refuse.
- **The view also leaves out an index whose `where` clause reads an unknown column.** The ticket's prototype filtered on key columns only, and such an index makes the table unreadable, because the index manager cannot compile the clause. `predicateColumnNames` uses Quereus's own compiler.
- **`addIndex`'s maintenance uses the view too.** It used to fold the record's layout into the `IndexManager`, so on a machine with a different column list its index entries were computed from the wrong column even with a correct record. The ticket did not mention this, and a test failed without the change.
- **Small moves.** `mirrorDerivedUniqueConstraint` now runs inside each arm of `addIndex`, so a refusal leaves no trace. The unused `initialized` getter is gone.

The step 5 test has B apply its own `tiny` CHECK rather than "the same" change as A. If B applies the same change, its description matches A's and nothing visibly goes wrong, so the reproduction needs B's description to be older than the record.

## Known gaps

- **Stale machine after a data-destroying apply.** A data-destroying step plus a refused commit on a machine holding an older description still writes that older description on the next touch. `NOTE:` at `settleOwedRecords`; also stated in the README.
- **A later refused apply can forgive an owed table.** A table still owing from a data-destroying apply is forgiven if a later apply touches it and is refused and unwound. The record then lacks the first change until a restart's `apply schema` re-emits it. `NOTE:` at `settleOwedRecords`.
- **Behaviour change to weigh, tables over several transactors.** One manager commits the migration, another refuses, and the first manager's undo commit is then refused too. Previously the next touch rewrote the restored description over that record. Now nothing does, so the record keeps the migration under a restored engine catalog, which is what the existing `NOTE:` on `endSchemaBatch` already describes. Quereus reports this case as not restored. No test covers it.
- **Tag undo is still open.** Undoing a tag change in the unwind still overlays this machine's tags onto the record. That is `bug-optimystic-failed-apply-on-a-second-machine-reverts-saved-tags`, in `fix/`. `adoptedByRefusedBatch` keeps its meaning for that ticket.
- **A stale machine still acts on its old columns.** Its writes can erase a value in a column it does not know, and an index over such a column goes unmaintained there. That is `bug-optimystic-a-machine-keeps-acting-on-a-table-description-another-machine-replaced`; this ticket makes that case reachable on first touch, as that ticket anticipated.
- **Gone on purpose.** A first touch no longer repairs a record that differs only in form, or a failed tag save outside a batch. Both wait for the next re-declaration or DDL.
