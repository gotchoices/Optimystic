# A pend refused late still stops its commit

## Why this is not the ticket that was planned

The implement ticket `a-two-member-pend-defers-its-final-delivery-to-the-commit` was built in full: the kept promise-round commit signature, no commit round when the pre-sign completes the majority, the deferred pend delivery, and `pendDeliveryDeferralMs`. The db-p2p suites passed. The Quereus plugin's `test/two-node-unique-value-race.spec.ts` then failed, twice out of two runs: a same-instant UNIQUE race on a table with a plain index ended in `CoordinatorPartialCommitError` (main table and `T_g` committed, `_uniq_1.v` refused) instead of the clean `UNIQUE constraint failed` refusal that spec pins. The cause is in the design, not the code: on a two-member cohort the other machine's refusal of one tree's pend surfaced only in the commit phase, after sibling trees had committed. That breaks the legacy multi-tree commit's "pend everything before committing anything" guarantee (`docs/internals.md`, *Conflict replay re-makes the uniqueness decision*). The decision ticket said to route such a case back to `blocked/` instead of shipping it. The deferral, the kept signature and the setting were reverted, and the question is in the blocked ticket `decide-which-writes-may-defer-a-two-member-pends-delivery`.

Building it turned up three gaps in the code the prereq `a-cluster-request-carries-owed-consensus-deliveries` landed. They exist without the deferral, and they are what this ticket ships. Each one stops a commit from going ahead while a member has refused its pend.

## What was built

- **The refused-pend guard sees rivals on new blocks.** `ClusterMember.validateCommitAgainstRefusedPend` refuses to co-sign the commit of an action whose pend this member refused, while local storage still corroborates the refusal. Its corroboration (`refusedPendConflictsWithLocalState` in `packages/db-p2p/src/cluster/cluster-repo.ts`) read `get`'s `state.pendings`. `get` lists pending records only beside a block it materialized, so a rival on a block with no committed revision went unseen and the member co-signed. A new collection's header is such a block. Two writers racing for one such block, each refused by the member that held the other's pend, could then both commit it at one revision, a fork. The corroboration now reads metadata through the same helpers the pend vote uses (`heldLatestOf`, `rivalClaimsOn`), and a read fault is still an abstain.
- **A commit carries its own action's owed pend, first.** `takeOwedRecords` in `packages/db-p2p/src/repo/cluster-coordinator.ts` now takes the request's record rather than its hash. A request that commits or cancels an action carries that action's owed pend records first. It does so even while another request is already carrying them, and ahead of the `MaxCarriedRecords` limit for the rest. The member has then applied the pend, or refused it, before it votes on the commit. Before this, a pend riding on a concurrent request could arrive after the commit vote, and the member abstained. A cancel can no longer overtake its own pend and leave a record nothing removes. The `NOTE:` there records the one cost: an escorted copy clears the in-flight mark early, so the retry timer may send a duplicate, which the member dedups.
- **A late refusal answers the commit instead of a throw.** A conflict-shaped pend refusal reported on a carried or retried delivery is kept, keyed by action id, in `ClusterCoordinator.latePendRefusals`. It holds 1024 actions, ends at the pend record's expiration, and is dropped when a new pend of the same action starts. The hooks are `retainLatePendRefusals`, called from `noteDelivered` and after `runRetry`'s broadcast, and the public `takeLatePendRefusals(actionId)`. `CoordinatorRepo.commit` now runs the cluster path in `commitThroughCluster` and reads the refusal once after it settles (`latePendRefusalFor`). When the commit threw, it returns the first refusal in peer-id order as the retryable conflict, logged as `coordinator-repo:commit-late-pend-refusal`. The throw is typically the guard above surfacing as a `ValidatorRejectionError` that no local re-read confirms. Without this, db-core retried it verbatim and then failed hard. It does not convert:
  - a commit that returned an answer: acknowledged, or its own conflict or expiry, which may carry a confirmed `staleAt`;
  - a throw over a revision this node already holds under the same action (`confirmCommitRivalAgainstLocal` returns `'own-durable'`). That honours `classifyCommitStaleRejection`'s rule that such a commit is never answered as a conflict.
- `ICoordinatorClusterSeam` gained `takeLatePendRefusals`, so the five spec doubles of that seam gained a one-line stub. The comment on `CoordinatorRepo.pend` and the `cohortPendRefusals` doc in `executeClusterTransaction` now say where a late refusal goes. `conflictPendRefusalOf`, `pendActionIdsOf` and `settledActionIdsOf` are small module helpers in `cluster-coordinator.ts`, and `firstPendRefusal` in `coordinator-repo.ts` is now shared by `pend` and `commit`.
- Docs: `docs/correctness.md` §2 (the residual sentence of *A pend that reaches pend-consensus is not thereby stored*, now including the multi-collection residual), `packages/db-p2p/docs/cluster.md` (two bullets under *Owed deliveries ride on the next request*), `docs/debugging.md` (the `cluster` row and a paragraph after the pend-verdict table, describing the two new log lines).

## Tests added, each beside what it pins

Each was run against the code without its change and failed there.

- `test/cohort-pend-refusal-channel.spec.ts`, "votes reject when the rival holds a block with no committed revision": the guard's corroboration on a new block. Against HEAD's guard it voted approve.
- `test/cluster-coordinator.spec.ts`, "a commit carries its own action's owed pend even while another request is carrying it": the escort rule. With the rule disabled, the commit's request carried nothing.
- `test/carried-consensus-delivery.spec.ts`, "a member that refuses a pend carried on its commit makes the commit answer the retryable conflict". It runs a three-member mesh where one member misses the pend's decision and a rival then takes the block there. The commit returns `isConflictFailure`, and no member holds the revision. Without the late-refusal read, the commit threw `ValidatorRejectionError`. This also runs the guard fix end to end, since the block is new.

## For the reviewer

- **Late refusals are keyed by action id, and a multi-collection transaction shares one** (`tx:…` from `TransactionCoordinator`). A refusal of collection U's pend can be read, and consumed, by the first of that action's commits to throw, which may be collection M's. Every such answer is a retryable conflict for the same transaction, so this looked right. Check that the consumption by one commit cannot leave another commit of the action answering a throw it should not.
- The escort ignores `carrying` for the action's own pends but still respects the four-record limit. More than four owed pends of one action to one member are not all escorted. Without the deferral, owed pends come only from failed deliveries, so this was left alone.
- `latePendRefusalFor` does one extra local read (`confirmCommitRivalAgainstLocal`), only when a late refusal exists and the commit threw.
- The guard now reads `heldRevisions`, so a member whose `latest` will not materialize can corroborate with "already committed by a different action" where it used to abstain. This is stricter in the right direction, and the same reading the pend vote already uses.
- Untested by design: the cancel arm of the escort (a cancel carrying its own pend). It is the same code path as the commit arm, which is tested.
