# A single-collection write defers a two-member pend's delivery

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29). A write is two agreement rounds, **pend** (reserve) and **commit**, and each round is a promise request plus a decision to the other member. The maintainer accepted the narrowed design on 2026-10-12: hold the pend's decision back and send it inside the commit's first request, but only for a write that reserves everything it will commit in one pend through one coordinator. The full design and its correctness argument are in `tickets/complete/decide-whether-a-two-machine-write-drops-to-three-calls.md`; why it was narrowed is in the old blocked text (git history of this ticket): deferring every pend tore multi-tree SQL writes.

## What was built

**The writer's mark — `PendRequest.soleReservation?: true`** (`packages/db-core/src/network/struct.ts`). It means "this pend is the action's only one, and its commit goes to the coordinator this pend goes to". It is omitted rather than `false`, because the pend request is hashed into every signature preimage.
- `TransactorSource.transact` sets it. That is every `Collection.sync` write, and so every legacy-mode SQL insert into a table with no index (one tree, `tree.sync()`).
- `TransactionCoordinator.pendPhase` sets it only when the transaction has exactly one participant collection (`sole = collectionTransforms.size === 1`). That is the widening: session-mode SQL writes to one table. I confirmed by reading `commitOnce`/`commitOnceLatched`/`pendPhase`/`commitPhase` that a one-collection transaction pends once (one `NetworkTransactor.pend`) and commits once (`commitCollection` → `NetworkTransactor.commit`), and the commit resolves its coordinator from the pend's per-action cache (`resolveCoordinator`), so it goes to the same coordinator. `commitBatchLegacy` (the legacy multi-tree batch) always has two or more collections, so it never sets it.
- `NetworkTransactor.pend` keeps the mark only on a request carrying every block of the action (`pendRequestForBatch`). This is decided per send, so a pend that `consolidateCoordinators` splits, or that `processBatches` re-splits on retry, carries no mark.
- `Collection.completeOwnEntry` re-sends one participant of a half-landed multi-collection action through `transact`, so it carries the mark too. I judged that safe, and the field's doc comment says why: that re-send pends and commits its one collection on its own, so a late refusal stops only its own commit.

**The coordinator** (`packages/db-p2p/src/repo/cluster-coordinator.ts`):
- `keepCommitsSignedOverMergedPromises`. After every promise answer is merged, it keeps a remote member's own commit signature when that answer's promise map equals the merged map (`canonicalJson`). It runs only when this node's member's promise is already in the map (or there is no local member). Comments in `collectPromises` and `prevoteLocalPromise`, and the `docs/internals.md` rule, were rewritten for the narrowed "merges only promises" rule.
- `commitTransaction`. When the pre-sign completes the majority, no commit round runs (`deliverDecidedWithoutCommitRound`), and the decision goes to every remote member (`deliverConsensus`) or is deferred.
- `mayDeferPendDelivery` / `deferPendDelivery`. The deferral needs all of these:
  - every operation is a pend carrying the mark;
  - **the cohort is exactly two members**. I added this condition beyond the ticket's list. A lowered `superMajorityThreshold` (nothing validates its range) can keep a promise-round signature in a three-member cohort, and there the "one `held` vote stops a rival" argument does not hold;
  - this node's member applied the pend and its storage accepted it;
  - every awaiting member is carry-capable;
  - `pendDeliveryDeferralMs > 0`;
  - the expiration is more than twice the deferral away.

  The deferral arms the retry with `deferred: true`. `scheduleCommitRetry` does not count it as an attempt, and the new `armRetry` helper is shared by both. The three NOTEs are at `deferPendDelivery`: the rival during the window, a crash losing the owed message, and failover. I checked the failover NOTE's claim against `StorageRepo.pend`: an own-revision late pend is "satisfied" and stores nothing, and a later revision there refuses it as stale.
- Carry capability now also needs this node's client to have `updateCarrying` (`forgetCarryCapability` in `requestMember`).

**Config.** `ClusterConsensusConfig.pendDeliveryDeferralMs`, defaulting to 2000 through the exported `DEFAULT_PEND_DELIVERY_DEFERRAL_MS`, is resolved in the `CoordinatorRepo` constructor beside the retry settings. It is not exposed on `NodeOptions`, matching the other retry knobs.

**Harness.** `MeshFailureConfig.carryUnawarePeers` makes a member answer as an older build: no `acceptsCarried` stamp, and carried records are ignored.

## Tests

- `packages/db-p2p/test/commit-round-carries-coordinator-commit-vote.spec.ts`, rewritten as mesh tests on two members:
  - **Three deliveries.** The second delivery carries the pend, and both members hold the commit.
  - **An unmarked pend gets four, nothing carried.** This pins the gate that keeps multi-collection writes un-deferred.
  - **An older-build member (`carryUnawarePeers`) gets four, nothing carried.**
  - **A pend with no commit after it** reaches the other member when a 50 ms deferral runs out, as a standalone delivery.
  - **The other member's refusal of the carried pend** (a rival pending record planted after the pend) answers the commit as a retryable conflict, and no member holds the revision.
  - **The other member misses the commit's decision** (both in-line attempts). The gate refuses (1 of 2 holders), the coordinating member already holds the commit, and the scheduled retry lands it on the other member.
- `packages/db-p2p/test/cluster-coordinator.spec.ts`, two unit cases with a `SigningMember` fake:
  - **Kept** in a two-member cohort, and no commit round runs.
  - **Dropped** in a three-member cohort at threshold 0.5, where each member signs over two promises. No record any member is sent carries a commit signed over a different promise map.
- `packages/db-p2p/test/commit-durability-quorum.spec.ts`: comments updated for the new apply order. In the mirror case the coordinating member's fetch count is now 2 (first reconcile finds no holder, second finds the remote copy), as the ticket predicted.
- `packages/db-core/test/commit-digest-threading.spec.ts`, one case: a pend split across coordinators, and re-split on retry, carries the mark on no request. No mesh fixture forces two coordinator batches (backlog `debt-no-mesh-fixture-forces-two-coordinator-batches`), so this is the only layer that can see it.
- `packages/quereus-plugin-optimystic/test/two-node-write-request-count.spec.ts` (new), counting `/cluster` requests to the other node for one SQL insert after a warm-up insert:
  - legacy mode, table without an index: **3**;
  - session mode (`TransactionCoordinator`), table without an index: **3**. This is the widening. With the coordinator's mark disabled the count is 4, which I checked by mutation;
  - session mode, table with an index: **8, four per collection** (main tree and index tree). The ticket said "costs four"; each collection pays four, so I asserted 4 × 2. A reviewer should confirm that reading.
- `packages/quereus-plugin-optimystic/test/two-node-unique-value-race.spec.ts` passes unchanged (the acceptance test).

## Known gaps and things to look at

- **The two-member cohort condition is untested.** Pinning it needs a three-member mesh at a lowered threshold with one promise answer missing. I judged that not worth a test, given the condition is a one-line guard on a non-default configuration. Look at it by reading `mayDeferPendDelivery`.
- **File size.** `packages/db-p2p/src/repo/cluster-coordinator.ts` is 1953 lines (`wc -l`), up from 1786. Its own NOTE (at `carryCapablePeers`) says to move owed-delivery bookkeeping into its own module if it grows. The deferral is mostly doc comment, but the reviewer may want to file or do the split.
- **Theorem 9 in `docs/correctness.md` was not edited.** The longer sign-to-apply window on two members is argued in the first NOTE at `deferPendDelivery` and in the §2 text I added. The "Commit revision staleness" remark names the longer window.
- **The pend's answer on two members now rests on the coordinating member's verdict alone.** That is the documented residual, moved into the ordinary path for single-collection writes (§2). The other member's refusal reaches the writer as the commit's retryable conflict.
- **Re-measure.** Please ask the #29 reporter to re-run `message-latency.mjs` on a relayed two-machine pair, and on phones if possible, to confirm three relay round trips per single-table write.
