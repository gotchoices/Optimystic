# Browser storage syncs by the window — review

Fourth of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). Implemented as designed in the implement ticket; the design is restated only where the code departs from it or where a reviewer needs it to judge the code.

## What landed

- **Strict detection** (`packages/db-p2p-storage-web/src/durability.ts`): `supportsStrictDurability()` is `typeof IDBTransaction !== 'undefined' && 'durability' in IDBTransaction.prototype`, asked once per store at construction and overridable with `strictDurability?: boolean` on every store's options. `transactionDurability(strict)` is `'strict'` or `'relaxed'`.
- **Schema version 3** (`src/db.ts`): a `journal` object store, number keys holding a `JournalRecord` by structured clone and the string key `JOURNAL_MARK_KEY` (`'applied-through'`) holding the mark. Additive under the existing `objectStoreNames.contains` guards. The upgrade itself is untested, which backlog `debt-indexeddb-version-upgrade-is-untested-and-unhandled` already carries as its third arm.
- **`IndexedDBJournalStore implements JournalStore`** replaces `IndexedDBStoreDriver` (`src/indexeddb-storage.ts`). Reads are the old driver's cursors and keys unchanged, returned as `BatchBackend` asks (arrays, ascending). `durability` is `'power-loss'` when strict, else `'process-crash'`. `appendJournal` is one relaxed `readwrite` transaction on `journal`; `applyJournal` is one transaction over the six data stores and `journal`, strict when supported, with every request queued synchronously and awaited together with `tx.done`; `readJournal` is one readonly transaction over the number range `[1, MAX_SAFE_INTEGER]` plus the mark. No `close`: the handle is shared. Both `NOTE:`s reworded as the ticket asked (rule 3 holds only for the non-strict case; two tabs over one database).
- **`IndexedDBRawStorage(db, options?)`** is `KvRawStorage` over `WriteGroupDriver` over `JournalBatchBackend` over `IndexedDBJournalStore`; `IndexedDBRawStorageOptions` is the write group's, the journal backend's and the strict override together. `close` is declared always present.
- **`IndexedDBKVStore(db, prefix?, options?)`** writes through a `WriteGroup<string>` as `FileKVStore` does: `set`/`delete` into the group, `get` and `list` read the overlay over the `kv` store, and the sink commits a batch as one `readwrite` transaction on `kv`, strict when supported, with an already-resolved `durable`. Values are UTF-8 bytes in the group and strings in the store, so stored data keeps its type and the identity helper's `instanceof Uint8Array` test stays meaningful. `flush`, `whenDurable`, `close` are the group's. The sink ignores `syncWithinMs` on purpose: every flush of this store is strict, so there is no relaxed path to journal.
- **`loadOrCreateBrowserPeerKey(db, keyName?, options?)`** writes a newly generated key in one `kv` transaction that is strict when supported.
- **Docs**: `packages/db-p2p/docs/storage.md` (the deferring-backend sentence and the Invariant 6 driver table row, the journal-backend paragraph, the *Rule 3 past the crashes a store names* paragraph, the survival table row and the sentence under it, the kernel section's backend list, and the overview's "each supplying only a driver" sentence); `docs/correctness.md` (§1.2 storage durability and Theorem 6's backend caveat, both of which named this ticket as the one to update them); `docs/debugging.md` (a namespace row for this package); the package README (the eighth object store, the journal, what a crash loses with and without strict transactions, the close order, eviction and persistent storage, and what the tests can and cannot check).

## Departures from the ticket, and judgment calls

- **A malformed journal record is dropped by a structural check, not a codec.** The ticket said no codec is needed because structured clone stores the record whole. `readJournal` still checks each value's shape (`seq` a positive safe integer, each entry a `StoreKey` with an optional `Uint8Array`) and leaves out one that fails, logging `read-journal` on `optimystic:db-p2p-storage-web:storage:indexeddb`, so that a value some other build wrote under a number becomes a recovery gap rather than an `objectStore()` throw inside the apply, which would latch the backend for the life of the page. A mark that is not a non-negative safe integer reads as 0.
- **The reader-storage trap in the window test.** A second `IndexedDBRawStorage` over the same handle runs recovery on its first read, which applies whatever is journaled. So the test that checks "the data stores do not hold the group before the deadline" reads the raw object stores through the handle, not through a second storage; a second storage is used only where applying is the point (the page-going-away case) or after the apply.
- **Transactions are observed through a `Proxy` over the handle** (`test/support/spy-transactions.ts`), recording each explicit `transaction()` call's stores, mode and durability. Every other property is bound to the real handle, so idb's one-request shortcuts (`db.get`, `db.getAllKeys`) open their readonly transactions unseen; every write this package makes is an explicit `transaction()`, so the recorded `readwrite` calls are exactly the stores' own writes.
- **`IndexedDBKVStore`'s existing tests now close the store before the handle**, since a write left in the group would otherwise be flushed by the idle timer onto a closed handle. The prefix-isolation test flushes both stores before listing, so it checks the stored keys and not only the overlays.

## Tests added, each beside what it verifies

`test/indexeddb-storage.spec.ts`, over `fake-indexeddb` with `strictDurability: true` and an injected `setTimer`:

- *a relaxed group is appended relaxed and applied strictly when its deadline is due* — one `readwrite` transaction on `journal` alone with `durability: 'relaxed'`; the data stores empty and the journal holding record 1 with no mark; `whenDurable()` not settled before the timer; the timer firing opens one `readwrite` transaction over the six data stores and `journal` with `durability: 'strict'`; `whenDurable()` resolves; a reader sees the data; the journal holds only the mark, at 1.
- *a strict flush applies the groups held and its own in one strict transaction* — a relaxed group then a strict one: exactly one strict apply, no second append, the held group's `durable` settled, both groups readable, the deadline timer disarmed.
- *journaled groups survive the page going away: the next open applies them* — two relaxed flushes, then a second storage over the same handle with the first never closed reads both back, and the journal holds only the mark, at 2.
- The raw-storage conformance suite (`persistent`), over the composed storage; its `reopen` closes the handle and reopens the same database name.
- The two store-level specifics (byte fidelity, the pending key range) rewritten against `IndexedDBJournalStore.applyJournal` and its reads.

`test/indexeddb-kv-store.spec.ts`:

- *flush() commits the writes since the last flush as one strict transaction on kv* — three writes open no transaction; the overlay serves them; one flush is one `readwrite` transaction on `kv` with `durability: 'strict'`; a store with an empty overlay reads the put and the delete back; a second flush with nothing written commits nothing.

`test/identity.spec.ts`: none new, as the ticket said.

## Known gaps, honestly

- **No browser has run this.** `fake-indexeddb` keeps the durability a transaction asked for and has no disk, so every test checks what was asked, not what the disk did. The detection predicate (`'durability' in IDBTransaction.prototype`) rests on WebIDL attributes being prototype accessors and on the ticket's browser list; a reviewer with a browser to hand could confirm it reads true in Chrome and false under `fake-indexeddb` (the latter is what makes the `strictDurability: true` override necessary, and the tests would still pass if detection flipped — they always override).
- **A browser without strict transactions is covered by inspection only**: detection false → `'process-crash'` → `JournalBatchBackend` applies each group at once with `{ durability: 'relaxed' }`, and the node's start-up line says such a store cannot keep the window (`durabilityWindowClause` in `packages/db-p2p/src/libp2p-node-base.ts` is keyed on the durability value). No test runs that path; it is one branch of a string.
- **Hosts must now `close()` the storage and the key-value store before closing the handle**, where before a write reached IndexedDB as it resolved. The README says so; nothing in this repository consumes `IndexedDBRawStorage` outside the package, so no caller was updated.
- **Not run**: `yarn check:rn` (this package is not in the React Native bundle and `db-p2p` is unchanged), `yarn test:integration`, and the root `yarn test` fan-out beyond this package (no other package imports it; `packages/upgrade-check` has fixtures for the file and LevelDB backends only).

## For the reviewer
