# A decided promise map is never extended — review handoff

First half of the GitHub #64 work; `a-consensus-round-stops-waiting-once-its-outcome-is-decided` (in `implement/`) builds on it. Absorbed backlog `bug-a-late-promise-invalidates-the-commit-signatures-already-collected` (its file was already deleted by planning; the two doc references to it are gone).

## The rule as implemented

A record is **decided** when its approved promises reach `ceil(peerCount × superMajorityThreshold)`. A decided record's promise map is never extended, and a commit signature is placed only in a record whose promise map is exactly the one it was signed over. The signed-hash layout (`computeClusterCommitHash`) is unchanged.

### Member (`ClusterMember`, `cluster-repo.ts`)

- `isDecided` / `superMajorityOf` are new helpers; `getTransactionPhase` uses them.
- `getTransactionPhase`: after the `Rejected` / `ConflictSuperseded` checks, a decided record without this member's commit → `OurCommitNeeded`, whether or not the member has a promise on it. The own-promise branch (`OurPromiseNeeded` / conflict vote / expiry vote) now runs **only on an undecided record**. That second guard matters: without it, a late member that had just signed the commit was routed to `OurPromiseNeeded` on the next phase-loop step and added its promise after signing — the reproduction caught exactly that.
- `mergeRecords` delegates the signature merge to a new `mergeSignatures`: held decided → keep held map; else incoming decided → adopt incoming map verbatim; else union (first-seen). Each side's commits are kept only if that side's map equals the chosen map; dropped ones are logged `cluster-member:commit-over-other-promise-map`. Promise equivocation is still detected over shared peers (promise hash does not depend on the map); commit equivocation only between commits both kept. I applied the "kept only when its map is the chosen one" test uniformly, including the neither-decided branch, rather than an unconditional union there — in honest flows the two are identical (an undecided record carries no valid commits). The two-coordinators case is recorded as a `NOTE:` on `mergeSignatures`.
- The private `ClusterMember.canonicalJson` copy is gone; the member now imports db-core's `canonicalJson` (its own NOTE asked for that once a third caller appeared — this merge is the third).

### Coordinator (`ClusterCoordinator`, `cluster-coordinator.ts`)

- `mergeCommits` and the method `keepCommitsSignedOverMergedPromises` are replaced by one module function, `keepCommitsSignedOverRecordPromises(record, answers, round)`: own entry only, keyed by the peer asked, only when `canonicalJson(answer.promises) === canonicalJson(record.promises)`. Used by the promise round (now unconditionally), the pre-sign, the commit round, and the retry. Drops are logged `cluster-tx:commit-over-other-promise-map` with `round` and `dropped`. The old per-answer `cluster-tx:promise-round-commit` line is gone; `docs/debugging.md` updated.
- `presignLocalCommit` no longer merges the local member's promises.
- **"Stays owed"** needed two small changes beyond the merge, otherwise a member whose commit was dropped was silently forgotten:
  - `commitTransaction`, no-majority branch: the retry now owes every round member whose commit the record does not hold (failed delivery *or* dropped commit), not only failed deliveries.
  - `runRetry`: short of a majority, a member that answered but whose commit was not kept stays in `pendingPeers`; once there is a majority, the broadcast covers it as before.

  Side effect worth a look: a member that answers the commit round with no commit at all for some other reason, in a round that falls short of a majority, is now retried too (before, it was dropped from the retry). I believe that is the right behaviour and it is bounded by the retry budget.

## Known gaps / things to scrutinise

- **Held-decided branch is dormant.** A member never persists a decided record today — it clears its record as soon as it signs (`shouldPersist = false`), and `Promising` is the only persisting phase, which is undecided by definition. So the "keep the held decided map" arm only runs for a record restored from an older build's participant state. It is untested beyond inspection.
- **Expired record, unmerged own promise.** Previously a member that had voted, whose own promise the coordinator never merged, and whose clock had passed expiry threw `Transaction expired` on the decided commit-round record (its promise survived the union). Now its promise is dropped by the adopt-incoming branch, so it signs the commit instead. This matches the blind-commit rule and the direction of the existing NOTE above that throw in `processUpdate`, but it is a behaviour change in a narrow case.
- **Late member skips pend validation entirely**, so a slot hold it holds for this action is not consumed and lapses on its own window; it also no longer runs `findConflict`, so a rival it would have beaten and cleared stays held until the staleness sweep. Both covered by the quorum-intersection argument in the `getTransactionPhase` comment.
- **At HEAD the reproduction's `pend` still answered success**: with every member refusing the broadcast, `CoordinatorRepo.pendMany` fell back to applying the pend to its own storage alone (the documented "pend-consensus confers no durability" fallback). Not a new defect, but it is why the old failure was invisible to a writer.
