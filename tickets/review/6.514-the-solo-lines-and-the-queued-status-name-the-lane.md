# The solo lines and the queued status name the lane

Last of four implement tickets from the plan `a-transaction-carries-its-lane` (the other three are in `tickets/complete/`). This one only reports the lane; no admission rule moved. The solo path and the offline queue behave exactly as before.

## What changed

**The three solo log lines.** `commit:solo-cohort`, `pend:solo-refused` and `commit:solo-refused` now carry `lane`. `soloLogFields` takes the batch as its first argument and adds `...laneField(statedLane(batch))`, so all three lines get the field from one place. `statedLane` (in `request-batch.ts`) returns `undefined` when no request in the batch states a lane, as with an older writer, and the field is then left off. Otherwise it returns the stricter of the lanes the requests state. A batch built by one writer has one lane on every request, so the fold only matters for a malformed or mixed batch. Note that a request with no lane is skipped, not counted as `serializable`: the field reports what was stated.

**The queued status.** The plugin's `QueuedTransactionStatus` `queued` variant now has a required `lane: Lane`, next to `outlook`. `translateListed` passes through the db-core `EntryStatus.queued.lane`. `deferredStatus`, for a journaled transaction that has not yet been put back in the queue after a restart, reads `DeferredRecord.lane`. The new `journaledLane(entry)` in `offline-restore.ts` fills that field. `restoreOne` now uses the same helper, so the `'serializable'` default for a pre-field record is defined once. `entries()` gets the field through `translateListed` and `listedDeferred`, with no separate change. No `lane-changed` status exists, because the lane is fixed for an entry's life.
