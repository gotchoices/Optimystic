# Blob references and the piece-tree builder — review handoff

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). This ticket built the pure-logic foundation in `packages/db-core/src/blob/`. It has no network or disk access. The reader that checks pieces received from elsewhere is the next ticket (`feat-blob-references-and-verified-piece-trees`, in `tickets/plan/`).

## What exists now

- **References and piece ids** (`blob-ref.ts`). `BlobRef` and `PieceId` are branded strings: a CIDv1, SHA-256 with a 32-byte digest, codec raw (0x55) or dag-pb (0x70), lowercase base32. `parseBlobRef` and `parsePieceId` apply the parse rule in order: string, at most 128 characters, first character `b`, `CID.parse(text, base32)` succeeds, version 1, `isPieceCid`, then re-encodes to the same string. Anything else throws `BlobRefError`, with the decoder's message as `detail` when the decoder threw. `isBlobRef` uses the same rule without throwing. It is built on a verdict value, so there is no try/catch control flow except around `CID.parse` itself. `pieceIdOfCid` re-spells a CIDv0 link as v1. `cidOfPiece` decodes a branded id. `rootPieceId` is the identity cast.
- **Errors** (`errors.ts`): `BlobRefError`, `BlobUnavailableError` (reason plus an optional piece id), `BlobCorruptError` (reason, piece id, optional ref, optional detail in the message), and `BlobDigestError`. Each sets `name`.
- **Limits** (`limits.ts`): the five constants, exactly as the ticket specified.
- **Hashing port** (`digest.ts`). `defaultBlobDigest` is memoized. It uses `crypto.subtle` when present, and otherwise `@noble/hashes` with one `blob:digest-fallback` line on `optimystic:db-core:blob`. `checkBlobDigest` runs three FIPS 180-2 known answers and rejects a result that is not a `Uint8Array`, is the wrong length, or is wrong, plus any digest that throws (the error is wrapped, with `cause`). `selectBlobDigest` is exported from the module only, not from `blob/index.ts`.
- **Piece ports** (`pieces.ts`): `PieceSink` and `PieceSource` (with optional `has` and `verified`).
- **List-piece encoder** (`list-piece.ts`): `encodeListPiece` encodes the way kubo does. Links carry an empty `Name` and a cumulative `Tsize`, and the `blockSizes` are the children's content sizes.
- **Builder** (`builder.ts`). `buildBlob(source, sink, { digest?, signal? })` cuts 256 KiB leaves, each into a fresh buffer, and emits one empty leaf for an empty source. `BlobTreeAssembler` (`add` / `finish`) holds the level logic. `buildBlob` is only the chunker feeding it. Pieces are put one at a time, each after the pieces it names. The signal is checked before each source chunk is consumed and before each put.
- **Service types** (`service.ts`): `BlobService` and its option and result types, copied from docs/blobs.md, plus `BlobFetchOptions`, `BlobDurability`, `BlobDurabilityEvent` and `BlobProgressEvent`.
- **Routing key**: `routingKeyForBlob(ref)` in `network/routing-key.ts` is the reference's 32 raw digest bytes. The `RoutingKey` comment now names both constructors.
- **Dependencies**: `@ipld/dag-pb@^4.2.0` and `ipfs-unixfs@^13.1.2` (this brings in `protons-runtime@8.0.2`). `yarn lint:deps` and `yarn check:rn` both pass with no alias or shim, so `packages/rn-bundle-check/readme.md` is untouched. The `sha2-browser` exports warnings in the `check:rn` output come from the existing `multiformats/hashes/sha2` imports elsewhere, not from this code.

## Where this differs from the ticket text (please check)

- **The ticket's 56-byte known-answer input was wrong.** Its string, `abcdbc…mnopnopq`, was 50 bytes long and missing `klm`/`lmn`. The hex it gave (`248d6a61…`) is the digest of the real FIPS 180-2 message, `abcdbcdecdefdefgefghfghighijhijkijkljklmklmnlmnomnopnopq` (56 bytes), and that is what `digest.ts` uses. I checked it against Node's `crypto`.
- `SubtleDigest` is exported, from the module and from `blob/index.ts`. Declaration emit needs it, because the exported `selectBlobDigest` takes it as a parameter.
- `BlobDigestError` takes an optional second `ErrorOptions` argument, so it can carry the thrown cause.
- `BlobTreeAssembler`'s constructor is `(sink, options: BuildBlobOptions)`, which takes the digest and the signal together and so shares one options type with `buildBlob`. It is not a positional digest. `finish()` throws if no leaf was added, and both methods throw once it has finished.
- **`crypto.subtle` polyfills.** db-p2p's readme already asks React Native hosts to install a `crypto.subtle.digest` polyfill (for `multiformats`). That polyfill is usually JavaScript, so on such a phone `defaultBlobDigest` takes it as native: hashing runs at JavaScript speed and no fallback line is logged. I wrote this down in docs/blobs.md and debugging.md, in a `NOTE:` at `defaultBlobDigest`, and in the db-p2p readme's polyfill row.

## Tests added

- `test/blob-builder.spec.ts`:
  - Six kubo 0.43.1 vectors (0; 1,000; 262,144; 262,145; 174 × 262,144; 175 × 262,144 + 1 bytes), each fed in 100,003-byte chunks. Each one asserts `ref` and `size`, and that no list piece was put before a piece it names. The ordering check runs on every vector, not only the last.
  - Chunking independence: `[1, 0, 262,143, 1]`-byte chunks and one whole chunk give the same reference.
  - `BlobTreeAssembler`, fed the 176 leaf links of the largest vector directly, gives its reference and its size.
  - `checkBlobDigest` accepts `selectBlobDigest(undefined)` and the native one, and rejects a digest that returns 32 zero bytes, one that returns 31 bytes, and one that throws.
- `test/blob-ref.spec.ts`: one table-driven test. It accepts the raw and dag-pb vector references and rejects uppercase base32, base58btc, CIDv0, sha2-512, the identity hash, dag-cbor, a truncated reference, a trailing space, a 200-character string, and non-strings passed to `isBlobRef`. The alternative spellings are built with `multiformats`.
- `test/routing-key.spec.ts`: a `routingKeyForBlob` case. The key is 32 bytes and equals the reference's multihash digest.

## Known gaps, by inspection only

- Three-level trees (more than 174 × 174 leaves, about 7.4 GiB) are not vector-tested. The level code is the same at every level.
- Nothing tests that a source that throws, a `put` that rejects, or an aborted signal propagates and returns no reference.
- Nothing tests that each leaf gets a fresh buffer. A builder that reused one would still produce correct references while corrupting a sink that keeps arrays.
- `isBlobRef` returns true for any raw or dag-pb piece id. That is intended, since any piece can be a root.
