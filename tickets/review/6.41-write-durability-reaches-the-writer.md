# What landed

The transactor already answered a commit with a `WriteDurability` (prereq ticket `commit-result-carries-durability-class`). Nothing above it passed that on. Now it reaches the writer:

- `TransactorSource.transact` returns the `CommitResult` it already had instead of collapsing success to `undefined`. Its one production caller (`Collection.syncAttempts`) switched from `if (staleFailure)` to `if (!attempt.success)`; test call sites switched from `expect(result).to.be.undefined` to `expect(result.success)`.
- `Collection.sync`, `syncInternal`, `syncAttempts` and `updateAndSync` return `WriteDurability | undefined`. `undefined` means **nothing was written** — no staged changes, so no pend and no commit and no class to fabricate. A write that never lands still throws `SyncRetryExhaustedError`; it never returns a class.
- `ICollection.sync` and `ICollection.updateAndSync` widened to match. `Collection` is the only implementer (grepped).
- `Tree.replace`, `Tree.sync` and `Diary.append` forward the value without interpreting it, `torn` list included.
- `TransactionCoordinator.commit` still returns `void` and now carries a `NOTE:` saying so and naming `tickets/backlog/feat-multi-collection-commit-reports-durability.md`.

No behaviour changed: the same writes succeed, the same are refused, the same retries happen. Only return values widened.

# What to poke at first

**The multi-commit fold is the one place I went past the ticket's letter.** `syncAttempts` loops on `hasUnsyncedChanges()` and *can* run more than one successful commit in a single sync (its own `maxAttempts` doc calls this "a legitimate large multi-batch sync"). The ticket only specified the single-commit answer. I accumulate as:

```ts
durability = durability === undefined ? attempt.durability : mergeDurability([durability, attempt.durability]);
```

so a sync that commits **once** — every sync with a caller today — returns exactly that attempt's report, with `mergeDurability` never called. A sync that commits twice folds weakest-wins, because reporting the last batch's class would show a write as saved when an earlier batch only reached the writer. Refused attempts contribute nothing either way. Worth a second opinion: the alternative reading is plain last-success-wins, which is simpler and over-optimistic in a case that may be unreachable (the loop's own comment argues the post-commit replay is a no-op today, so the second iteration may never happen). **Not covered by a test** — I could not construct a two-commit sync without faking the loop.

**`DirtyTree.sync()` had to change, which the ticket predicted it would not.** The ticket said the quereus plugin's `tree.sync()` call sites are unaffected because ignoring a return value is not a type error. True for the calls — but `DirtyTree` is a *structural interface* declaring `sync(): Promise<void>`, and a `Tree` returning `Promise<WriteDurability | undefined>` stops satisfying it. Widened to `Promise<unknown>` with a comment saying the bridge consumes neither the class nor the void. The three call sites (`txn-bridge.ts`, `optimystic-module.ts`, `catalog-batch.ts`) are otherwise untouched, as instructed.

**`ICollection.sync` widened too**, not just `updateAndSync` as the ticket listed — unavoidable once `Collection.sync` widened.

# Use cases to validate

**The writer can tell a solo write from a group write.** `await tree.replace(...)` resolves to a class; `isFullyDurable(d)` is the only "really saved" test. Confirmed end-to-end on the two-machine lifecycle: with one machine stopped, the survivor's accepted write reports `local` and `isFullyDurable` says no.

**An empty flush is not a failure.** `await tree.sync()` on a tree with nothing staged resolves to `undefined` and runs no commit at all. This is the one case a caller must handle, and it is the case `optimystic-module.ts`'s `flushDirtyTrees` already guards with `hasUnsyncedChanges()` before calling — so it never reaches `undefined` there. Checked: no quereus site reads the value, and none treats `undefined` as failure.

**A torn commit's abandoned blocks survive the trip.** A transactor reporting `quorum: 'full'` with a non-empty `torn` arrives at `Tree.replace` with `torn` verbatim and `isFullyDurable` false. That is the single signal distinguishing a torn write from a clean one, and it is exactly where an app looks.

**A refused write reports nothing.** Retry exhaustion throws; no class is invented for a write that never landed.

# Known gaps — treat these as the floor, not the finish line

- **No test pins a REAL multi-machine class arriving at the collection API.** Every unit test stamps the class with a double. The only end-to-end class is phase 5's `local`. A real `majority` or `full` reaching `Tree.replace` unmangled is unproven above the transactor — the prereq ticket covers the transactor level. `backlog/debt-no-mesh-fixture-forces-two-coordinator-batches` is the reason a multi-cohort shape is hard to reach in-process.
- **`unrouted` is never exercised through the collection API**, at any level of this change.
- **The multi-batch fold is untested** (see above) and may be unreachable today.
- **`writeRows`'s merge across rows is exercised with one row only.** Phase 5 writes a single row; the weakest-wins fold over several rows in a batch is unproven.
- **The `const staleFailure = attempt;` alias** inside the refusal branch exists only to keep the existing branch body unchanged under the narrowing. Reviewer's call whether to inline it.
- **`docs/` additions are new prose**, not a transcription of something reviewed elsewhere: a "Was it really saved?" subsection in `docs/optimystic.md` and one paragraph after the Commit Path diagram in `docs/internals.md`. Worth reading for accuracy, not just for citation lint.
