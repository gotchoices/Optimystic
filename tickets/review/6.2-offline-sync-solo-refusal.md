Part 2 of stage 6 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages): the hard form of the reachability gate, under the maintainer decision of 2026-10-25 recorded in [§When to submit: the reachability gate](../../docs/offline-sync.md#when-to-submit-the-reachability-gate). Implemented as the implement ticket designed it; the deviations are listed below.

## What was built

**The option and its wire fields.**
- `SyncOptions.refuseSoloCommit?: boolean` (`packages/db-core/src/collection/struct.ts`). Default off.
- `PendRequest.refuseSolo?: true`, `CommitRequest.refuseSolo?: true` (`packages/db-core/src/network/struct.ts`), `RepoCommitRequest.refuseSolo?: true` (`i-repo.ts`). Always omitted rather than `false`, through one helper, `refuseSoloField` in the new `packages/db-core/src/network/refuse-solo.ts`, so an unset write serializes byte-identically (signature preimages unchanged).
- `PromiseShortfall.soloRefused?: SoloRefusalReason` (`'absent-members' | 'awaiting-bootstrap' | 'unrouted'`), carried through `PromiseShortfallError` (new `soloRefused` field, copied back by `toFailure`). The error message is unchanged.

**Carrying it through every send of a cycle.**
- `Collection` records the cycle's terms beside the in-flight mark: `beginInFlightAction(actionId, cycle?: InFlightCycle)` stores `inFlightCycle`, cleared by the same disposer. `Collection.send` (sync attempts and the head commit's `send`) and `completeOwnEntry`'s re-send of a torn attempt both read it. `syncInternal` marks with `options.refuseSoloCommit`; `commitHead` passes it to `openHeadCommit`.
- `openHeadCommit(entryId, identity, resume?)` became `openHeadCommit(entryId, identity, options: OpenHeadCommitOptions = {})` with `{ resume?, refuseSolo? }` (type in `collection/struct.ts`). Two callers: `commitHead` and `EntryParticipants.open`.
- `TransactorSource.transact` trailing optionals (`priority`, `blockDigests`, `baseRevs`) plus the new flag are now one `TransactOptions` bag (exported from `transactor-source.ts`). The two `src` callers were updated; no test passed more than five arguments, so no test changed.
- `TransactionCoordinator`: `CommitCycle` gained `inFlight: InFlightCycle` (from the commit's `SyncOptions`, via `inFlightCycleOf`), used for the participants' in-flight marks (so a coordinator refresh that finishes a torn participant re-sends with the flag) and for `writeContextOf(transaction, cycle.inFlight)`. `WriteContext.refuseSolo?: true`. `commitEntry` passes it to `EntryParticipants.open` and its per-attempt context. `pendRequestFor` and `commitRequestFor` spread it; the commit phase now takes the `WriteContext` (`commitPhase`, `commitTogether`, `commitEach`, `commitCollection`, `commitRequestFor`) instead of a bare action id.
- `NetworkTransactor`: `pend`'s per-batch rebuild (`pendRequestForBatch`) already kept every field but `baseRevs`/`soleReservation` (comment added); `pendMany` sends requests whole; `repoCommitRequest` (every commit send: one-round, batched, tail-then-sweep) now copies the flag; `commitBlock` takes a `RepoCommitRequest` instead of five positional values, built by the new `commitOf(request, blockIds)`.

**The refusal (`packages/db-p2p/src/repo/coordinator-repo.ts`).**
- The solo cohort is read once per solo write (`soloCohortOf` → `SoloCohort`: `unrouted`, or `self` with the absent members). `soloCohortDurability` is now a module function over it (name kept: docs cite it). `soloRefusalFor(solo, awaitingBootstrap)` is the one rule: `unrouted` → `'unrouted'`; absent members → `'absent-members'`; else awaiting bootstrap → `'awaiting-bootstrap'`; else `undefined` (genuinely alone, commits `local`). The identify-in-flight NOTE sits on it.
- `pendSolo`: when any request carries `refuseSolo` (`refusesSolo` in `request-batch.ts`) and the rule refuses, it answers before `applyPendsInOrder` with `PromiseShortfallError({ approvals: 1, rejections: 0, peerCount: 1 + absent, needed: max(2, ceil(superMajorityThreshold × peerCount)), silentPeers: absent, soloRefused }).toFailure()`, logged `pend:solo-refused`.
- `commitSolo`: same rule, before the proof is minted or anything applied; answers `{ success: false, conflict: true, reason: 'solo-commit-refused: …' }`, logged `commit:solo-refused`. `SOLO_COMMIT_REFUSED_REASON` is exported from `packages/db-p2p/src/storage/storage-repo.ts` beside `COMMIT_NOT_DURABLE_REASON`.
- All three solo log lines share `soloLogFields` (`knownAbsent`, `absentPeers`, `awaitingBootstrap`).

**The queue.** `OfflineQueueOptions.allowSoloCommit?: boolean`; unless `true`, `OfflineQueue.send` adds `refuseSoloCommit: true` to the `SyncOptions` it hands `commitHead` and `commitEntry`. Nothing else sets the option.

**Docs.** offline-sync.md §When to submit (field names, both refusal shapes, the three reasons, the log lines, in-doubt stays sticky) and the classification table row; internals.md *The offline queue* (one sentence) and the "still commits alone, at `local`" passage; correctness.md and transactions.md, where they said a cohort of one "always commits alone"; debugging.md's `coordinator-repo` namespace row names the two new lines.

## Deviations from the implement ticket

- `TransactionCoordinator.execute` takes no `SyncOptions`, so it builds its `WriteContext` without the flag (the ticket said "commit/execute for uniformity"). `TransactionSession.commit` goes through `commit`, which carries it. Nothing in offline mode uses `execute`.
- The mesh spec's "neither node holds a committed revision of the collection's header" assertion is made on a collection node A creates itself (`NOTES`, invented before the cut, never committed), read straight from each node's `storageRepo`. The seeded table/index collections of the existing cases could not support that assertion.

## Known gaps — verified by reading the code only

- `'awaiting-bootstrap'` and `'unrouted'` are reached only through `soloRefusalFor`'s branches; the mesh exercises `'absent-members'` end to end.
- The commit-side refusal is unit-tested at `CoordinatorRepo`; the end-to-end sequence (pend on a real cohort, partner drops, commit refused, writer cancels, retry's pend refused as a shortfall) has no mesh test. Worth a look: after the commit-side refusal the writer's cancel reaches only this node (cohort of one), so the partner keeps the pend's reservation until its own cleanup; that is the existing partition behaviour, not new.
- Multi-collection entries (`pendMany` / `commitMany` solo branch) refuse when any request carries the flag; the mesh cases use one collection.
- A remote coordinator: the field crosses `RepoClient` / `RepoService` as plain JSON inside the operation, which both forward verbatim; the mesh calls coordinators in process, so the wire is not exercised.
- Mixed versions: an older coordinator ignores the field and commits `local`; stated in the field comment and the doc, not tested.
- Preimage stability: checked that every producer goes through `refuseSoloField` or spreads an existing request; an unset write is unchanged byte for byte.

## Behaviour change to be aware of

The Quereus plugin's offline mode builds its `OfflineQueue` without `allowSoloCommit` (the plugin's `offline.allowSoloCommit` key is ticket `offline-sync-cohort-reachability`, and `parseOfflineConfig` still refuses it), so every plugin offline drain on a networked transactor now refuses lone commits while the node knows a partner is missing. A node that FRET still remembers a departed partner for keeps its entries queued until FRET marks the partner dead; a genuinely alone node (never had a partner) commits as before. Writes outside offline mode are unchanged.
