# Interleaving spec for the commit latch and revision threading

The only change is one new test file. No source was modified.

`packages/db-core/test/coordinator-latch-interleaving.spec.ts` adds two cases that park a
coordinator commit mid-flight and release a `Collection.update()` into the parked instant, then
assert the collection cannot be corrupted by it. Both cases were designed against the actual code
paths and both were confirmed to FAIL against the pre-fix mechanism (see *Honesty* below).

## What each case does

**Case 1 — refresh between the durable commit and `recordCommitted`.**
`GatedCommitTransactor` (extends `DelegatingTransactor`) records the `rev` on every pend and
commit request, delegates the commit so it lands durably FIRST, then parks before returning the
result to the coordinator. The test awaits that park, releases `collection.update()`, drains ten
macrotask turns, asserts the refresh is still pending, opens the gate, and awaits both. It then
asserts the collection recorded exactly the revision it pended at, under this transaction's own
action id, and that a freshly-opened `Collection` over the inner transactor reports the same
`(revision, action id)` pair — local record and storage agree.

**Case 2 — refresh replaying the tracker under a parked pend.**
`GatedPendTransactor` parks the first pend BEFORE it reaches the inner transactor and, on every
delegated pend, snapshots the pair `(transforms handed to the network, transforms the collection's
tracker holds)` at delegation time. While parked, a rival — a second `Collection` over the same id
driven through `updateAndSync` against the unwrapped transactor — durably takes the revision. The
test then releases a refresh on the loser's instance, asserts it is blocked, opens the gate. The
pend fails stale, the coordinator retries, and attempt 2 wins. Assertions: every snapshot pair is
deep-equal; the log holds `['rival', 'local']` — both writers durable, exactly one entry each, so
the retry did not re-append; storage read through a fresh handle agrees.

Both cases also `await` the released refresh's promise after the gate opens. That is the latch
non-reentrancy assertion — if the coordinator re-entered a latched `Collection` method inside its
own held span, or the retry loop called `update()` without first releasing, the test hangs and the
5s mocha timeout catches it.

## Honesty: does this reproduce the pre-fix bug?

Yes, both cases, verified empirically — not reasoned about. Method: `packages/db-core/src/collection/collection.ts`
and `packages/db-core/src/transaction/coordinator.ts` were temporarily overwritten with their
`210ebffd^` (pre-fix) contents, the new spec run, then both files restored byte-for-byte from
backups. Nothing was committed and the working tree ends with only the new test file added.

Pre-fix results:

- **Case 1** failed at `records exactly the revision it pended at`: actual `2`, expected `1`. That
  is exactly the predicted `pendRevs[0] + 1` — the refresh adopted rev 1 out of the log, and the
  old `recordCommitted(actionId)` (no `rev` parameter) recomputed `getNextRev()` and appended the
  same action again at rev 2.
- **Case 2** failed at `pend #1 sent exactly what the collection believed it had staged`: the
  pended object still carried the loser's header block, log-tail block and the entry appended for
  this transaction, while the staged object — after `replayActions()` → `tracker.reset()` replaced
  it — held only the freshly-replayed action block.
- The `blocked()` assertions also failed in both cases pre-fix, and a probe run measured that an
  unlatched refresh completes on **macrotask turn 1** against `TestTransactor` — so the ten-turn
  drain is a ~10x margin, not a coin flip.

**What this does and does not settle about the downstream two-machine fork.** It settles that the
mechanism is real and reachable: pre-fix, a single process can leave a collection's revision
counter permanently one ahead of storage while carrying its own action id, which is the
`collection:context-not-lowered`-forever state. It does NOT prove the field incident had this
cause, and the shapes are not identical — in this in-process reduction storage attributes the
forked revision to *nothing at all* (no such revision exists yet), whereas the field diagnostics
described the collection's own action id sitting at a revision *storage attributes to a different
action*. That remaining gap still needs evidence from a downstream run carrying the new
diagnostic fields (`2.4-collection-divergence-report-fields`).

## Known gaps — treat these as the floor, not the finish line

- **Only the `coordinator.commit()` path is exercised.** `TransactionCoordinator.execute()`
  (coordinator.ts ~635-732) is the OTHER site that acquires participant latches across a commit
  span, with its own subtlety (latches acquired only *after* `applyActions`, because
  `collection.act` takes the same non-reentrant latch, plus a dedupe before acquiring). No case
  here parks a commit on that path. A reviewer looking for the next test to write should start
  there.
- **Single collection only.** The sorted-by-collection-id acquisition order that makes two
  concurrent overlapping commits deadlock-free is not exercised — one collection has no order to
  get wrong. A multi-collection parked commit (two coordinators, overlapping participant sets) is
  untested.
- **One interleaving point per case.** The refresh is released at exactly one instant in each
  case. Nothing sweeps the release point across the span, so a window that opens somewhere else in
  the commit path would not be caught.
- **In-process reduction.** `TestTransactor` only: no network, no cluster consensus, no partial
  failure. Case 2's stale loss is genuine (a real rival really commits) but the pend/commit round
  trips are local.
- **Case 1 asserts final state plus "the refresh was blocked".** The `blocked()` check is what
  keeps it from passing vacuously, and it was confirmed to fail pre-fix — but that is a
  point-in-time result against one reverted revision, not a standing structural guard.

## Tripwire recorded

- The ten-macrotask-turn drain is what gives the `blocked()` assertions their discriminating
  power; if `Collection.update()` ever grows a deeper await chain, or these cases move onto a
  transactor with real I/O, "still pending" degenerates into a tautology. Parked as a `NOTE:` on
  `drainMacrotasks` in the spec, carrying the measured turn-1 baseline.

## Review checklist

- Do the two gated wrappers park at the instants their doc comments claim, given the current
  `commitOnceLatched` ordering? (They park inside `transactor.commit`/`transactor.pend`, so they
  are sensitive to the coordinator continuing to call those once per collection.)
- Case 2 asserts `snapshots.length > 1` rather than `=== 2`. Deliberate — the retry budget is
  bounded (`maxAttempts: 4`) and an extra attempt would still be correct — but confirm that a
  silently *degenerate* run (e.g. the parked pend somehow succeeding) could not satisfy it.
- Is asserting `['rival', 'local']` on log order over-tight? It encodes both "one entry per
  writer" and commit ordering; the latter is a `TestTransactor` property.
- `structuredClone` on `Transforms` in `GatedPendTransactor` assumes blocks stay structurally
  cloneable. True today (`TestTransactor` already relies on it); worth a glance.
