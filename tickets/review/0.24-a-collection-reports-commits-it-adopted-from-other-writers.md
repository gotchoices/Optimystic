# A collection reports commits it adopted from other writers

Part of GitHub #58. The dependent ticket `a-materialized-view-follows-rows-other-members-commit` consumes this in the Quereus plugin.

## What was built

`CollectionInitOptions.onExternalCommits?: (rev: number) => void`. A refresh (`Collection.updateInternal`) calls it once, synchronously, when the revision it adopts includes changes this handle did not write. `rev` is the adopted revision.

- **The rule** is `Collection.walkedOthersWrites`: the walk found an action entry other than `ownEntry` (the in-flight write's own torn entry, which the refresh finishes and consumes), or any durable invalidation. On top of that, `forgetAndAdopt` reports when the adoption verdict is `adopt-divergent` (another lineage), or `adopt` with `othersWrote`. A `refuse` verdict never reports. Checkpoints cannot be counted: `Log.getFrom` returns action entries only.
- **Where it fires.** At the end of `forgetAndAdopt`, after `advanceContext` and `keepLogEnds`, in the same await-free step. It sits inside that method, not after it in `updateInternal`, so a later edit to `updateInternal` cannot put an `await` between the adoption and the call. It runs before the replay, so a replay that throws still leaves the call made, which is correct because the adoption stands.
- **Guarded** like `viewChanged`: `externalCommitsAdopted` catches a throw and logs `collection:external-commits-callback-threw` with the revision.
- **Threading.** It is passed through the `Collection` constructor at both open sites. `Tree` takes it by adding `'onExternalCommits'` to `TreeCollectionOptions`' `Pick`. `Tree.buildInit` already spreads `options`, so it needed no other change.
- `RefreshReport` and `update()`'s return type are unchanged, as the ticket required.
- Two doc wordings changed because `keepLogEnds` is no longer the last statement of `forgetAndAdopt`: its comment and docs/internals.md now say "last cache move".

## Test

`packages/db-core/test/collection-external-commits.spec.ts`, one case:

- Handle A creates the collection and commits.
- Handle B opens after that and commits through `TailLandsButReportsStale`. Only the log tail lands and the commit is reported refused, so B's refresh between attempts walks B's own entry, finishes it and consumes it. B then refreshes again with `update()`.
- A refreshes.
- Expected: A's callback ran once, with A's adopted revision, which equals B's committed revision. B's never ran.

This test covers the own-versus-other branch in `walkedOthersWrites`. As a mutation check, I made every walked entry count. B's assertion then failed, and it passed again once the code was restored.

## Covered by inspection only (no test)

- An own entry and a rival's entry in one walk give one call, since only `ownEntry` is excluded.
- A refresh deferred to an in-flight head commit (`headInFlight`) returns before `forgetAndAdopt`, so there is no call.
- The idle path (`tailShowsNothingNewer`) returns before the walk, so there is no call.
- An invalidation-only refresh calls, because `invalidations.length > 0`.
- An open (`attachToLog`) does not go through `forgetAndAdopt`, so there is no call.
- A callback that throws is logged, and the refresh continues.
- A `refuse` adoption has no walked entries anyway, because `getFrom` returns only entries above the held revision. The verdict gate makes that explicit rather than relying on the arithmetic.

## Things worth a reviewer's look

- **Over-reporting across handles of one `Database`.** Each handle reports what it adopted, so handle B of the same `Database` reports a commit made through handle A. This is accepted in the ticket as costing a redundant view refresh, never a missed one. Whether the plugin holds one handle or several per table is the dependent ticket's concern.
- **`adopt-divergent` reports even when the walk found nothing new.** That is deliberate: another lineage means everything read so far may differ.
- **The constructor now takes 12 positional parameters**, three of them optional callbacks. Their types differ, so a mix-up fails to compile. I left it positional to match the existing style. Grouping the callbacks into one object would be a small refactor if the list grows again.
