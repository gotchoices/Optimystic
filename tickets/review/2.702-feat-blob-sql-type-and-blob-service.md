# Review: `plugin.blobs`, `plugin.blobsFor(table)` and the blob SQL functions

Second part of [docs/blobs.md §SQL](../../docs/blobs.md#sql). The `blobref` column type already existed; this added the service an application puts files through, the owner labels pins are held under, and the two SQL functions that read a reference's local state. Nothing here maintains a reference tree, pins on behalf of a commit, or announces — that is `feat-blob-reference-trees-follow-sql-rows`, `feat-blob-pins-follow-sql-commits` and `feat-sql-columns-hold-blob-references`.

## What was built

**`blob-pin-labels.ts`** (new) — the one place in the plugin a pin's owner label is built or read. Three builders (`transactionReferencePinLabel`, `transactionPutPinLabel`, `unstagedPinLabel`), the two string prefixes plus `transactionPinPrefix(stampId)`, and `parsePinLabel`. Only two of the three labels are built by this part; the parser has to know all three to be right about which labels are *not* this plugin's, and the prefixes are what the later parts enumerate pins by.

**`CollectionFactory`** — `SqlBlobBackendService` (`BlobService & BlobPinIndex`), `BlobBackend` (`key`, `service`, `transactor`), `getBlobBackend(options)` keyed and de-duplicated in flight exactly as `getOrCreateTransactor` is, and `onBlobBackendResolved(listener)`. A `network` transactor whose node carries `blobs` gets `node.blobs`; everything else (and a node without `blobs`) gets a `SingleMachineBlobService` over `options.blobStorageFactory?.()` or memory, `start()`ed, logged once under the new `optimystic:quereus-plugin:blob` namespace. `dispose()` stops the single-machine services it built and forgets its backends; a `network` backend's service belongs to the node.

**`SqlBlobService`** (new) — a thin wrapper over one network's backend, resolved on first use, which defaults `put`'s owner label from the bridge's open transaction (decided when the put *starts*). `onProgress` / `onDurability` keep listeners in their own sets and attach one forwarder each once the backend resolves, on the `LateBoundCohortReachability` pattern.

**`OptimysticModule.defaultBindingOptions` / `bindingOptionsOfTable`**, and `OptimysticVirtualTable.bindingOptions` — the lazy binding resolution behind `plugin.blobs` and `plugin.blobsFor(table)`.

**`BlobLocality(ref)` and `BlobSize(ref)`** in `functions/blob-functions.ts`, registered in `register`'s `functions`. Local `stat` with no probe, not `DETERMINISTIC`, NULL in gives NULL, a `BlobRefError` rethrown as `QuereusError(…, MISMATCH, error)`.

**`blobStorageFactory`** on `OptimysticOptions` / `ParsedOptimysticOptions`, read in `resolveBinding` out of the registration config only, as `rawStorageFactory` is.

## Use cases to exercise

- **Put, insert, read back.** `const { ref, size } = await plugin.blobs.put(stream)`; insert `ref` into a `blobref` column; `for await (const bytes of plugin.blobs.read(ref))`. On any non-`network` transactor this is wholly in memory and needs no node.
- **`select BlobLocality(Content), BlobSize(Content) from Attachment`** over a mix of rows: a blob put here (`here`, its size), a reference nobody put (`unknown`, NULL), and NULL (NULL, NULL).
- **A malformed reference** in either function: `QuereusError` with `StatusCode.MISMATCH` whose `cause` is a `BlobRefError`. Both a bad string and a non-string.
- **Pin labels.** `plugin.blobs.pinsOf(ref)` after a put outside a transaction, and after one made between `begin` and `commit`; `parsePinLabel` on each. `listPins('sql/')` / `listPins('sql-unstaged/')`.
- **Two tables on one transactor key**, and `plugin.blobs` beside `plugin.blobsFor(t)`: one store, different wrapper objects.
- **`plugin.dispose()`** after `db.close()`: the single-machine services stop.

## What is tested, and what is not

`packages/quereus-plugin-optimystic/test/blob-functions.spec.ts`, five cases on the `test` transactor:

| Case | What it pins |
|---|---|
| a blob put through `plugin.blobs` | `BlobLocality` → `here` and `BlobSize` → the put's size, over a two-piece blob (so the size comes off a list root) |
| a well-formed reference nobody put | `unknown` and NULL — not an error, not a missing-block fault |
| NULL, and two refused values | NULL from both; and `MISMATCH` with a `BlobRefError` cause, one case per arm of the parse rule, over both functions |
| a put outside any transaction | exactly one pin, which `parsePinLabel` reads as `unstaged` with a plausible time |
| a put between `begin` and `commit` | exactly one pin, read as `put` for that transaction's `StampId()` — and still there after the commit |

**Deliberately untested** (the ticket called these inspection, and that is how they were checked): the registration of the functions, the `blobStorageFactory` option plumbing, the label builders against the parser (that would test the module against itself), `getBlobBackend`'s keying and in-flight de-duplication, `onBlobBackendResolved`, `dispose` stopping the services, and the listener-before-resolution path.

**Untested and worth a reviewer's eye** — `plugin.blobsFor` has no spec. It was verified by a throwaway probe (since deleted), which showed: it resolves the right network's store, it is **not** reference-equal to `plugin.blobs`, and it rejects with `QuereusError` naming a table the catalog does not know. A reviewer who thinks that deserves a permanent spec should say so; it is one behaviour with real branching (the catalog lookup, the ownership guard, the per-call wrapper), so it may well pay for itself.

## Where the implementation went past the ticket, and why

Three places. Each is a judgement call a reviewer may reverse.

- **`onBlobBackendResolved` replays already-resolved backends** to a listener as it subscribes, rather than only reporting resolutions after it. The ticket's wording ("called once per backend, the first time it resolves") would let a listener registered after a network's first table silently miss that network — and the listener this exists for reconciles each network's pins after a restart, where missing a network means leaving pins stranded. Each listener still hears each backend exactly once. If the reviewer prefers the literal contract, the replay loop in `onBlobBackendResolved` is the only thing to delete.
- **`SqlBlobService.adoptBackend` moves its event forwarders when the backend object changes.** The ticket says a service used after `dispose()` resolves a fresh backend; without this the forwarders would stay attached to the stopped service and the host's listeners would go silent for ever.
- **The single-machine `reason=` is chosen from whether a node exists, not from the transactor name.** A `network` transactor a host registered directly (`registerTransactor('network:libp2p', …)`, no node) now logs `transactor-has-no-node` rather than `node-without-blobs`, which is what actually happened.

Also: `parsePinLabel`'s `unstaged` arm requires digits (`/^\d+$/`), not just `Number.isInteger` — otherwise `sql-unstaged/` alone would read as a pin taken at time 0.

## Tripwires parked

- **Neither function's value is refused in a written row.** Probed: `insert into T (Loc) values (BlobLocality(?))` goes in today. It is harmless only because no deployment wires a transaction validator (`feat-no-deployment-validates-transactions-at-pend` in `tickets/backlog/`), so nothing re-executes a statement; once one does, a validating member computes its own machine's answer and disagrees with the writer. `CommitOutlook()` has had the same shape since it shipped, so this is a class, not a point. Parked as a `NOTE:` at the head of `packages/quereus-plugin-optimystic/src/functions/blob-functions.ts`, naming the ticket that trips it and saying to refuse it at the write-provenance seam for all three functions at once. Not filed: conditional on a ticket that is itself still in backlog.
- **A blob-backend resolution in flight across `dispose()`** lands in `blobBackends` afterwards and its service escapes the set `dispose` stopped. `NOTE:` on `blobBackendsInFlight`, beside the identical one already on `transactorsInFlight` — the same remedy covers both if hosts ever dispose mid-initialization.
- **The plugin's own node still keeps blob pieces and records in memory.** `createNetworkTransactor` calls `createLibp2pNode` with no `pieceStorage` and no `kvStore`, so a restart loses every pin and the next sweep deletes the pieces (the node logs its own `node-wiring` warning). `NOTE:` at that call site saying to thread `blobStorageFactory` through when a host needs it; a host that builds its own node and registers it already can. Said plainly in the README's `blobStorageFactory` row too.

## Known gaps, honestly

- **Nothing releases a pin.** Every blob put through `plugin.blobs` is held through its transaction's commit *and* its rollback, so an application on this release accumulates every blob it puts until it unpins by hand. That is the design (`feat-blob-pins-follow-sql-commits` closes it) and is stated in the `put` doc comment, in the README and in docs/blobs.md — but it is the sharpest edge in this release and worth checking the wording lands.
- **`BlobBackend.transactor` has no reader here.** `feat-blob-reference-trees-follow-sql-rows` reads reference trees and the scope registry through it. Not dead code to cut.
- **`blobStorageFactory` is not validated and cannot be.** Persistent pieces over in-memory records, or the reverse, are both accepted; the consequence of each is documented on the option and in the README.
- **A reference written into a table on another network is not refused.** Belongs to `feat-sql-columns-hold-blob-references`.
