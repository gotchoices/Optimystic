# Commit content digest — part 2 of 3: threading to the wire (review)

Part 1 (`commit-cert-digest-core-primitives`, landed) supplied `computeBlockContentDigests`,
`Tracker.peekMaterialized`, and the optional `blockDigests` field on `CommitRequest` /
`RepoCommitRequest` with **no producer and no consumer**. This slice adds the producers and the
per-batch subsetting on the wire. Part 3 (`commit-cert-digest-member-check`, sequence 1.4, already in
`implement/`) adds the member-side check that actually uses the field.

Nothing in this slice changes what a member does with a commit. The observable change is that commit
requests now carry an extra field, and that the field is narrowed per peer.

## What shipped

**`TransactorSource.transact`** gained a trailing `blockDigests?: BlockContentDigests` parameter after
`priority`, spread onto the `CommitRequest` it builds. The key is omitted when the map is absent **or
empty**, so a commit that declares nothing serializes byte-identically to before — this matters
because the request is the consensus message and is hashed verbatim into every cohort signature.

**`Collection.syncInternal`** computes `computeBlockContentDigests(tracker, tracker.transformedBlockIds())`
from the per-attempt snapshot tracker and passes it to `transact`. It is computed **after** the log
append, so the log tail (and, on collection creation, the header) are digested like any other block.
Recomputed on every retry attempt, because the snapshot tracker is rebuilt each iteration.

**`TransactionCoordinator.commitCollection`** computes digests from `collection.tracker` (public,
still holding the staged transforms — resets happen after commit) over the `blockIds` it was handed,
once, before the 3-attempt transient-retry loop. Verified that `applyActionsToCollection` takes its
transforms from that same `collection.tracker` and appends the log to it, so the digests describe
exactly what was pended.

**`NetworkTransactor` per-batch subsetting.** `commit` threads the full map into both `commitBlock`
calls (header, tail) and into `commitBlocks` for the remainder. A new module-level helper
`digestsFor(all, batchBlockIds)` narrows the map inside the `processBatches` send callback — at send
time, not up front, because `processBatches` re-splits a failed batch across different coordinators on
retry. It returns `{}` (spreads to nothing) when the batch declares nothing, so the key is absent
rather than `{}`.

**`computeBlockContentDigests` hardened (part-1 file, deliberate change).** Materializing replays the
staged ops against the *locally cached* base, which can throw on its own — an op naming an entity the
cached base does not have is reachable when another action's commit folds a different shape into the
cache between staging and digesting. Unguarded, that turned a retryable stale failure into a
`TypeError` thrown out of `Collection.sync()` **before the pend**. The per-id loop now catches and
skips, degrading to "undeclared" exactly like an uncached base. This was found by a test, not by
reading. See "Things to attack" — this is the change most worth a second opinion.

**Docs.** `docs/repository.md` §`commit(request)` gained the `blockDigests` input line and a new
"Declared block content" subsection covering the three load-bearing properties (optional per block,
rides inside the request so mixed-version peers hash identically, each cohort sees only its own
blocks) and the never-break-the-commit rule.

## What to validate / use cases

Ordered roughly by how much a reviewer should distrust them.

**Per-batch subsetting is the security-relevant behavior.** If the whole map shipped to every batch,
a cohort would sign a record declaring content for blocks it is not responsible for — which is
exactly what part 3 will check against. Covered by `commit-digest-threading.spec.ts`:
- three peers, five routable blocks, an explicit block→peer preference map; every recorded per-peer
  request carries exactly the digests for its own payload, and peer-B never sees peer-C's block.
- header and tail arrive as **separate single-block batches** on the same peer, each carrying only its
  own digest (this is asserted, not assumed — the ticket called it out).
- a batch whose blocks are all undeclared omits the key entirely (`hasOwnProperty` is false, not an
  empty object), and a commit that declares nothing omits it on every batch.
- **retry split**: peer-B throws once; b1 re-resolves to peer-C and b3 to peer-A, splitting the failed
  batch, and each retry request carries only its own subset. This is the test that fails if anyone
  "optimizes" the subsetting to happen once up front.

**`Collection.sync` end-to-end** (same spec, `TestTransactor` behind a capturing delegator): round one
inserts two blocks (digests present, `baseRev` absent — inserts are base-independent); round two
updates one (digest with a numeric `baseRev`), deletes another (**no entry** — a delete materializes
to nothing), and inserts a third. The deleted id is still in `blockIds`, pinning that a partial map is
legal. A second test asserts the log tail id is among the declared ids.

**Mixed-version hash guarantee** (same spec): a `RepoMessage` whose commit op carries `blockDigests`,
JSON-round-tripped to simulate a peer that parses the message with no knowledge of the field, hashes
byte-identically under `computeClusterMessageHash` / `computeClusterPromiseHash` /
`computeClusterCommitHash`, at both membership versions (`undefined` and a digest). This pins that
nobody later turns the canonicalising helpers into a field allowlist.

**Unreplayable op** (`digest.spec.ts`): an op that cannot replay against the cached base is skipped
while its sibling still declares.

**`coordinator.spec.ts` fake collections** now carry a real (empty) `Tracker`, because `commitPhase`
reads `collection.tracker` in addition to `getNextRev()`. The comment on `fakeCollections` was updated
to say so. Three coordinator tests failed on the old two-method fake; that was my change, not a
pre-existing failure.

## Things to attack

- **The new `try { peekMaterialized } catch { continue }` in `computeBlockContentDigests`.** It is a
  bare catch that swallows every error class, not just replay failures. The argument for it is that
  the declaration path is advisory and must never be able to fail a commit that would otherwise
  succeed — but the counter-argument (it can now hide a genuine bug in `applyTransform` behind a
  silently-undeclared block) is real and unaddressed. There is no logging on the swallow. Decide
  whether that should narrow, or at least log.
- **Digest cost on the `Collection.sync` retry path.** Digests are recomputed from scratch on every
  retry attempt, each one hashing every touched block. Not measured. A high-contention sync that
  retries ten times now does ten full hashing passes it did not do before. I did not benchmark this
  and make no claim about magnitude.
- **`TransactionCoordinator.commitCollection` computes digests before the transient-retry loop but the
  request object is reused across all three attempts.** Correct today (the request is not mutated),
  but the reuse is implicit.
- **I did not test the coordinator's multi-collection commit path end-to-end for digest content** —
  only that the phases still work with a tracker-bearing collection. `commitCollection`'s digest
  computation is exercised by the existing coordinator tests only to the extent that it returns `{}`
  for an empty tracker. A reviewer wanting real coverage there should add a coordinator test with
  staged transforms.
- **No cross-package test.** Nothing verifies that a digest computed by a db-core client equals what
  `StorageRepo.internalCommit` in db-p2p materializes. That is part 3's surface by design, but it
  means this slice's digests are unvalidated against the thing that will consume them.
- **The part-1 tripwire still applies**: digest coverage is bounded by the `CacheSource` capacity
  (default 128), so a commit touching more update-carrying blocks than that silently digests only the
  resident ones. Parked as a `NOTE:` at the top of `packages/db-core/src/transform/digest.ts`; not
  re-recorded here.
