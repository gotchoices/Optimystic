# Refresh always knows its own in-flight action

## What changed, in plain terms

`NetworkTransactor.commit` stores a collection's header and log tail first, then sweeps the rest of
the blocks. If a later sweep block loses a race the whole write is reported as failed — but the
header and tail are already permanently stored, so the write's own record is already in the log
when the writer is told "you failed". This is a **torn commit**.

The retry must recognise that record as its own and drop the matching queued work instead of
writing it again. `Collection.sync` already did. `TransactionCoordinator.commit` did not: its
between-attempt refresh calls the same `Collection.update()` a plain reader calls, so it was
indistinguishable from a reader refresh — even though the coordinator was holding the very
identifier it was retrying. Result on HEAD: two log entries, same action, same transaction id, at
two revisions, plus a second commit that actually landed on storage.

The fix makes the knowledge live on the collection instead of travelling as an argument:

- `Collection` gained a private `inFlightActionId` and a public
  `beginInFlightAction(actionId): () => void` that sets it and returns an id-guarded disposer.
- `updateInternal()` takes **no** parameter now — it reads the field. `update()` and
  `updateAndSync()` are therefore correct by construction, not by having nothing to pass, and a
  fourth write path added later cannot inherit the old defect by omission.
- `syncInternal` is now a thin bracket (mint id → `beginInFlightAction` → `finally` disposer) around
  a new private `syncAttempts` holding the unchanged retry loop. Split this way rather than
  re-indenting ~90 lines, so the diff shows the change and not a whitespace shift.
- `TransactionCoordinator.commitOnce` marks each participant with `transaction.id` right after
  acquiring its latch, pushing the disposer into an array `commit` owns; `commit` wraps its **whole**
  `for(;;)` retry loop in `try/finally` and runs every disposer on exit.

### The lifetime correction the fix ticket got wrong

The originating `fix/` ticket said the clear belongs in the same `finally` that releases the latch.
That is wrong, and this implementation does not do it. The coordinator's between-attempt refresh
runs *outside* the latched span by design (`Latches` is non-reentrant), so a latch-scoped clear
would already have run by the time the only reader of the mark executes. The correct lifetime is
the **attempt cycle**, which is what shipped. The clear therefore runs without the latch held; that
is documented at the field, and is safe because it is a single id-guarded field write whose only
reader runs under the latch.

## Use cases the new suite covers

`packages/db-core/test/coordinator-own-action-replay.spec.ts`:

- **Single-collection torn commit through the coordinator.** One staged action; the first commit is
  made durable on the inner transactor and then masked as `{ success:false, conflict:true }`. The
  commit must *resolve* (the action is durable, so the writer is owed a success), the log must hold
  the action once, exactly one commit must have landed on storage, and a second reader opened over
  the **unwrapped** transactor must agree. Also asserts the refresh — not `recordCommitted`, which
  never runs on this path — advanced the context onto revision 1 under the transaction's own id.
- **Multi-collection: one participant tears, the other cleanly loses.** The wrapper distinguishes
  the two by block id: the torn collection's commit is delegated (durable) then masked; the other's
  is refused *without ever reaching storage*. That asymmetry is what makes the case exercise the
  bug at all — if both had landed, the coordinator would classify a partial landing
  (`CoordinatorPartialCommitError`, deliberately not retryable) and the retry path would never run.
  Both logs must end up holding their own action exactly once, and exactly two commits total land.
- **An abandoned commit leaves no mark behind.** A hard (non-conflict) pend rejection makes the
  commit non-retryable, so it escapes as a plain `Error` with nothing durable. A *different* writer
  then lands an entry carrying the same action id, and a plain `update()` must **replay** the still
  pending action, not consume it. A leaked mark turns this into silent loss of work that was never
  stored.

## Known gaps and things worth an adversarial look

Flagging these rather than claiming full coverage — the tests below are a floor.

- **Participant identification in the multi-collection case is by header block id.** The wrapper
  keys off `request.blockIds.includes(collectionId)`, which works because `createOrOpen` uses the
  collection id as the header block id and a *first* commit carries that header among its blocks. A
  future case that tears a **second** commit on an already-committed collection will not be
  identified this way. Call-order keying was rejected deliberately: `commitPhase` fans out
  concurrently and its call order is not contractual.
- **Case 3's premise is synthetic.** Two real transactions colliding on one action id does not
  happen in production; the case forces it by overriding `Transaction.id`. It guards the invariant
  ("cleared on every exit"), not a realistic scenario. Its value is that it fails the moment the
  clear is removed.
- **Only two of the exit paths are actually driven.** The `finally` covers return, stale-loss
  exhaustion, partial commit, hard error, and abort — but only *return* and *hard error* are
  exercised by a test. Abort/deadline and `CoordinatorPartialCommitError` exits rely on the
  `finally` being a `finally`.
- **`commitOnce`'s `inFlightDisposers` parameter is optional.** Nothing forces a future caller to
  pass it. Today `commit` is the only caller, and a caller that never refreshes between attempts
  genuinely needs no mark — but the optionality is a place a later path could quietly regress. Worth
  a reviewer's opinion on whether it should be required.
- **The latch-free clear is documented, not tested.** No test drives a concurrent foreign refresh
  against a clearing commit. The argument for safety is in the code (single id-guarded field write;
  the only reader holds the latch), not in an assertion.
- **`TransactionCoordinator.execute` is untouched, deliberately.** It has no retry loop and never
  refreshes between attempts, so it has no in-flight cycle to mark. Confirm that reading holds.
- **`debt-coordinator-execute-and-multi-collection-latch-span-untested` is not closed here** and was
  not attempted — the multi-collection case incidentally drives that path but proves nothing about
  the latch span, which needs its own gated-transactor harness.

## Tripwires recorded (not tickets)

- `packages/db-core/src/collection/collection.ts`, at `beginInFlightAction` — the mark deliberately
  outlives the latch, so **two writes overlapping on one collection instance can trample each
  other's mark**: a second write that takes the latch between the first's failed attempt and its
  retry-refresh replaces the id, and the first's refresh would then read the *second* write's id and
  consume that write's durable entry, dropping pending actions of its own that never landed. Not
  reachable today — a coordinator commit and a `sync()` run on one session call path, the same
  assumption `commitOnce`'s participant selection and `rollback` already rest on. `NOTE:` at the
  site says what to change (a per-attempt token compared by identity, refusing to replace a live
  mark) if a second writer is ever allowed to drive the same instance concurrently.
- `packages/db-core/src/transaction/coordinator.ts`, at the `applyActionsToCollection` log append —
  after a torn commit the torn participant drops out of the retry's participant set, so the retry's
  log entries carry an `allCollectionIds` list naming only the *remaining* participants while the
  torn participant's already-durable entry names all of them: one transaction id, two different
  lists. Nothing keys off that list for correctness today. `NOTE:` says a cross-collection
  invalidation cascade must union the list across the transaction's entries rather than trust any
  single one.
