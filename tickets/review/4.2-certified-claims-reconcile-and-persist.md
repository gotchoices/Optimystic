## Already applied (in the working tree, validated, not yet committed)

- **`BlockStorage.saveRestored` no longer reads a proof out of the archive body.** It previously
  persisted `archive.revisions[rev].proof` and relied on every caller to strip proofs it had not
  verified; `restoreBlock` did that stripping by mutating the archive the remote-fetch callback
  returned. That made "an unverified proof reaches `saveBlockProof`" a comment-enforced caller
  obligation that the next caller of `saveRestored` would silently break. Now `saveRestored` takes
  the verified proof as a separate `verified?: { rev, proof }` parameter and ignores the archive's
  own `proof` field entirely, so only the one chain that verified a proof against the exact bytes
  (`reconcile-block.ts` → `StorageRepo.saveReplicatedBlock` → `saveReplica` →
  `saveForwardRevision`) can persist one. `restoreBlock` is back to a plain pass-through and no
  longer mutates its callee's return value.
- **The proof-verification thresholds are shared instead of duplicated.** Both repair paths built
  `{ superMajorityThreshold, simpleMajorityThreshold: 0.5 }` inline with the same four-line
  rationale comment. That hardcoded `0.5` is the one number that must mirror what cohort members
  actually enforce (`ClusterMember.hasMajority`), and two copies could drift silently. Extracted as
  `proofThresholds(superMajorityThreshold)` in `cluster/certified-claims.ts`; both
  `CoordinatorRepo.queryClusterForLatest` and `reconcile-block.ts` now call it.
- **`reconcile-block.ts`'s header comment corrected.** It still pointed at a closed ticket
  (`debt-read-repair-commit-cert-verification`) and still claimed the sole-peer content exposure was
  entirely open; it is now closed for a candidate carrying a verified proof, and the comment says so
  and names the remaining unanchored-cohort residual instead.

## Remaining

### Documentation that is now wrong, not merely incomplete

`docs/transactions.md` was updated for certified claims. `docs/internals.md` was not, in two places
that an operator reads when a block will not repair. Both now state the opposite of what the code
does.

- **The repair-size table and the paragraph under it** (`docs/internals.md`, the *How many machines
  repair actually needs* table). The two-machine undeclared row says repair is possible **never**,
  and the prose below says a block that only one cohort peer holds "cannot be repaired at *any*
  machine count, four-or-more included". Both are now false for a holder that serves a verified
  cohort commit proof: that claim needs no corroborating peer at any cohort size. The table and
  prose describe the uncertified case only, and must say so.
- **The `sole-holder` repair-deadlock entry** (same file, the `cluster-fetch:repair-deadlock`
  reason list). It tells operators the only remedy is another cohort peer holding the block and that
  "no machine count or configuration setting helps". There is now a second way out: the lone holder
  retaining the commit proof for the revision. Worth stating, because a repaired replica now carries
  the proof onward, so this case should get rarer over time rather than staying permanent.

Verify before writing: a certified lone holder converges inside `selectQuorumRev`, so the decline
branch that calls `reportRepairDeadlock` is never reached and `sole-holder` genuinely cannot fire
for it. That was confirmed by reading `CoordinatorRepo.queryClusterForLatest`; re-confirm rather
than trusting this note.

### Operator-facing log lines that no document names

The chain added four log lines and the docs mention none of them. Two are *incident* lines that an
operator must be able to tell apart from an ordinary shortage, which is exactly what the
implement-stage handoff asked a reviewer to check:

- `reconcile:certified-equivocation` and `cluster-fetch:certified-equivocation` — two verified
  proofs certify different actions into one revision.
- `reconcile:certified-content-equivocation` — one revision, two certified content digests.
- `reconcile:certified-selected` / `cluster-fetch:certified-selected` — which rule won a selection.

Both equivocation cases mean whoever holds the cohort's signing keys signed both sides, and both
leave the block unrepaired permanently and by design. Today each is accompanied by a
`reconcile:no-rev-quorum` / `no-content-quorum` line that reads as a routine shortage. The decline
lines are already documented in `docs/internals.md` next to the reconcile description; the
incident lines belong beside them, with what an operator should actually do (this is a key
compromise, not a capacity problem — the remedy is investigating the cohort, not adding machines).

### Test gaps — behaviours nothing currently pins

All three are in `packages/db-p2p/test/reconcile-block.spec.ts`, in the existing
*certified claims (cohort commit proofs)* describe. Real signed proofs are available from
`test/support/commit-proof-fixtures.ts` (`makeSignedProof`); the existing tests there show the
recipe.

- **The certified-win penalty skip is unpinned.** When a certified carrier wins the content quorum,
  peers that served different bytes are deliberately *not* penalized — an unanchored proof must not
  become a reputation lever against honest dissenters. This is the most security-sensitive
  deliberate choice in the change and no test asserts it, so a refactor could silently re-enable
  the penalties. Add: a certified carrier plus a proof-less peer serving different bytes for the
  same revision; assert the heal lands on the certified bytes and no penalty is reported.
- **A proof that declares no digest for this block is untested.** That is the pre-digest-upgrade
  shape and it takes its own branch: the revision certifies, the content does not, and nobody is
  penalized. Assert that the revision selection goes certified while the content gate still demands
  ordinary corroboration, and that no proof is persisted.
- **The block-less certification arm is untested.** A cohort answer can carry a revision and a
  proof but no materialized block, which routes through `certifyClaim` instead of `certifyContent`
  — an entire arm of `certifyCandidates` that no reconcile test reaches. Cover it, including that
  an attributable failure on that arm (a genuine proof presented for a revision it does not cover)
  penalizes the serving peer.

## Findings deliberately NOT actioned, with reasons

Record these in the eventual `## Review findings` section rather than re-investigating them.

- **Anchoring is unwired** — layer 1 proves the listed signers signed, not that they are the
  block's legitimate cohort. Already tracked as `feat-cluster-membership-threshold-cert-anchoring`
  in `backlog/`, and honestly stated in all three docs. Evidence for that ticket, not a new one.
- **The certified-win penalty skip is sound.** Probed as the handoff invited. An attacker cannot
  force a certified win without cohort keys or a wholly fabricated cohort; if they have either,
  reputation is not the binding constraint. The alternative — letting a forged proof convict the
  honest cohort — is the worse failure mode. Keep the behaviour; just pin it with the test above.
- **The monotonic-skip proof gap** (a revision that first landed proof-less keeps no proof even
  when a later certified heal of the same revision carries one) is decided at the site with a
  stated rationale and pinned by a test that names itself as the assertion to flip. Left alone.
- **Verification cost** — one proof verification per proof-carrying answer per reconcile, bounded
  by the 256-signer cap times cohort width. Already carries a `NOTE:` at `certifyCandidates` saying
  it is fine at deployment cohort sizes of about ten. Tripwire, already parked.
- **Content certification is not vacuous in production** — checked that the real commit path
  populates the per-block content digests (`computeBlockContentDigests`, reached from both
  `collection.ts` and `transaction/coordinator.ts`), so the digest-bound content path fires outside
  tests.
