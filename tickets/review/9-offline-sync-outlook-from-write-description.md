First of three tickets for stage 9 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages), implemented as the implement ticket designed it: the vtab opts into Quereus 4.21.0's write description, records which staged elements carry a fresh value, the bridge keeps those records with the transaction (savepoint-aware) and folds them into the queue entry's facts, and the judgement reads the facts beside the `optimystic.fresh` tag. The two follow-ups, `offline-sync-outlook-unchecked-decisions` and `offline-sync-outlook-facts-survive-a-restart`, build on the plumbing described here.

## What was built

- **`StampId` is registered fresh** (`plugin.ts`): flags `FunctionFlags.UTF8 | FunctionFlags.FRESH`, the value imported from `@quereus/quereus` in place of the `1 as FunctionFlags` literal; `CommitOutlook` keeps `FunctionFlags.UTF8`. A comment at the registration states the same-transaction caveat (every call in one transaction answers the same value; two rows inserted under it collide sequentially and the pre-stage probe refuses the second).
- **`write-description.ts` (new, pure)** — `WriteFact` (`{ kind: 'fresh', collectionId, key }`), `freshElementsOf(write, arm, row)` and `foldWriteFacts(records)`. One deviation from the ticket's sketched signature: `freshElementsOf` takes the staging **arm** (`'insert' | 'update'`) as its second argument, because the rule "a description of another operation than the arm staging the row describes none of its values" (the upsert `DO UPDATE` arm receives the INSERT's object) needs to know the arm; the ticket's sketch had no way to express it. Column names are compared lowercased.
- **`commit-outlook.ts`** — `EntryFacts` (`fresh: ReadonlyMap<CollectionId, ReadonlySet<string>>`); `facts` on `JudgedTransaction`, `EarlierEntry` and `FollowedEntry`. `CollectionJudge` takes the collection's fresh keys: `absent` is not exposed when the tag or the facts say the key is fresh, `absentRange` likewise with the index entry's tree key. `WriteIndex.insertedFresh(collectionId, key, description)` replaces `insertedAbsent`: `insertedAbsent` is now a `Map<key, byFacts>` merged with OR across the entries that inserted the key, and the `unchanged` rule asks it. `unchecked` stays `'not-computed'`.
- **`TransactionBridge`** — `TransactionState.writeFacts: { records, marks }` (`types.ts`), fresh per transaction; `noteWriteFacts`, `openWriteFacts`; `createSavepoint` marks the record count ahead of the session-mode return, `rollbackToSavepoint` truncates to the mark and drops marks above the depth ahead of the snapshot check, `releaseSavepoint` drops marks at and above the depth. `sealIntoQueue` passes `openWriteFacts()` to `OfflineMode.enqueue`.
- **`OfflineMode`** — `entryFacts: Map<transactionId, EntryFacts>`, set by `enqueue(collections, id, facts)` before `queue.enqueue` (the `queued` status, and so the judgement, fires inside it) and deleted in a `finally` when nothing was queued (nothing staged, or the journal refused); read by `judgeQueued`, `queueAhead`, `followedEntry`; `openTransactionOutlook` reads `bridge.openWriteFacts()`; deleted with the judgement on a terminal status. A restored transaction has none.
- **vtab** — `wantWriteScope = true` in the constructor with the tripwire `NOTE:`; `guardedUniqueConstraints(values)` is the one walk `guardedUniqueIndexes` and `recordWriteFacts` both read; `recordWriteFacts(write, arm, rowKey, values)` is called after the last stage of the fresh INSERT path, the INSERT OR REPLACE-in-place path and the UPDATE arm (never DELETE), keying each unique entry as `indexEntryKey(createIndexKey(descriptor, values), rowKey)`, the formula `IndexManager` stages under. Two hand-built `TransactionState` literals in the module (an index tree opened on a given transactor, the schema catalog) now go through `transactorOnlyState`, which carries empty facts.

## Two things the ticket asked for that the facts did not allow

- **`randomblob(16)` written bare to a `text` key cannot be pinned as exposed.** The ticket said Quereus labels it `other` (lossy blob→text) and asked the unit spec to pin "must be exposed". Quereus 4.21.0 labels it **`fresh`** on a table with no blob column: the lossy-conversion rule runs only on a cell the insert builder wrapped in a `WriteCoercionNode`, and that wrap is skipped for `text` columns (`coerceToDeclared`: `TEXT_TYPE` has neither `parse` nor `validate`), while the executor still converts the cell — the stored key is a string with U+FFFD characters (`typeof(id)` answers `text`, verified on a memory table and an Optimystic table). With a `b blob` column in the table the same insert's `id` classifies `other`. The plugin trusts the label by design, so such an insert is judged assured today. Filed as `tickets/blocked/quereus-labels-a-fresh-blob-written-to-text-as-fresh.md` (a dependency outside this repo, with the proposed upstream fix and the work here once it lands); the unit spec pins the lossy-wrapper shape Quereus's doc and behaviour agree on instead (`cast(randomblob(16) as text)` → not fresh) with a comment naming the ticket; the caveat is stated in docs/offline-sync.md §What the analysis needs from Quereus and the README.
- **`StampId()` in an autocommit INSERT is NULL.** `insert into Memos … values (StampId(), 'a')` outside `begin … commit` fails with `NOT NULL constraint failed: Memos.id`: the VALUES row is evaluated before the write begins the bridge's transaction. Pre-existing (the function answers `null` without an active transaction, and every existing `StampId()` test uses an explicit `begin`), not caused here; the new SQL-level tests use explicit transactions and say why. Worth a README sentence under `StampId()` if a reviewer agrees it is surprising; not changed here.

## Judgement calls a reviewer should look at

- **Facts are recorded on the INSERT OR REPLACE-in-place path too.** The ticket's "REPLACE over an occupied key … no fact applies" is about the main-tree `unchanged`; that path also stages the new row's unique entries under `absentRange` (through `updateIndexEntries` with the guarded set), and a fresh unique value there is a true fact. The main-tree fact it may record (a fresh PK column on a key that already exists, which happens only when the key was minted earlier in the same transaction) is true as well.
- **The OR fold across entries in `insertedAbsent`.** Two queued entries inserting one key under `absent` (insert, delete, literal re-insert) credit the key as fresh while the fresh inserter is queued. The literal re-inserter is itself exposed on its `absent`, and anything behind it depends on it, so the credit changes no verdict; noted at `WriteIndex.add`.
- **A same-key UPDATE whose assigned PK column is fresh records a main-tree fact.** The ticket argued it "cannot happen"; it can (`update T set id = StampId() where id = <the id StampId() minted earlier in this transaction>`), and the fact is then true. The code comment at the UPDATE arm's call says so.
- **`enqueue` deletes the facts in a `finally` when `entry === undefined`**, covering both the refused journal write and the nothing-staged case the ticket did not mention (an enqueue that seals nothing emits no `queued` status, so nothing would ever drop the facts).
- **Savepoint marks dedupe per depth like the snapshots** (first capture kept), inheriting the `NOTE:` at `createSavepoint` about Quereus reusing a depth.
- **`transactorOnlyState`** replaces two inline `TransactionState` literals in the module so the new required field has one home; a reviewer may prefer making `writeFacts` optional instead — I kept it required so no code path can forget it.
