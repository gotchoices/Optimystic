# Review: matchmaking arrival push — the seeker's push-path hang-out loop

Third of five tickets in the arrival-push chain. Only `SeekerWalkClient` and its transport seam changed; no production transport supplies a push channel yet (that is `matchmaking-arrival-push-seeker-transport`), so on real nodes every walk still takes the poll path. `module.ts` needed no change.

## What was built

**Transport seam** (`seeker-walk-client.ts`): `SeekerWalkTransport` gained an optional `readonly pushes?: SeekerPushChannel` and optional `close?()`. `SeekerPushChannel` is `{ take(): ArrivalPushV1[]; wait(ms): Promise<void> }`; `wait` is documented to resolve at once for `ms <= 0` and never reject. The walk takes the push path exactly when `transport.pushes` is present — no client option.

**`run()`** now wraps the walk (moved to a private `walk()`) in `try/finally` that awaits `transport.close?.()`; a close failure is logged on `matchmaking:seeker-walk:error`, never rethrown, so it cannot replace the walk's result or its error.

**Shared admission.** `collect(reply)` (query replies) and `absorbPush(push)` both go through `admit(entries)` — filter → `verifyProviderEntry` → dedupe by `participantId` — and `noteTraffic(traffic)`. Only `collect` feeds `observeYield` (the `filterAcceptRatio` refinement); pushes don't, since they're filtered cohort-side. `absorbPush` drops a push whose `topicId` (base64url) is not the walk's, with a log line. The pushing member's own signature is left to the transport.

**Push-path hang-out** (`pushHangOut`), as the ticket's pseudo-code: wait until the next safety poll or the deadline, absorb everything `take()` returns, stop if `wantCount` is met or a promotion was seen, else `renew()` (every wake; the transport throttles it), then a safety `QueryV1` if one is due and patience remains. After the loop, one final `QueryV1` unless the tier already exited (met or promotion). A wake exactly at the deadline skips the safety poll so the final poll isn't doubled. With no pushes at 10 s patience and a 5 s safety poll, the hang-out issues 2 queries (the 5 s safety poll and the final one), 3 counting the immediate query; the poll path issues 11.

**Promotion seen mid-tier (both paths).** `enterTier(d, acceptedTraffic)` arms a watch when the `Accepted` reported `childCohortCount` 0 (or no traffic) and the walk hasn't re-registered at `d` yet. `noteTraffic` sets `promotionObserved` when an armed tier hears `childCohortCount > 0` from a query reply or push. `tierExit()` returns `done` / `reregister` / `undefined` and is the single exit test used after the immediate query, in both hang-out loops, and after them. `run()` on `reregister` adds `d` to `reregisteredTiers` and registers at the same tier with no withdraw; the existing `promoted` case descends. The bound is once per tier **per walk**, not per visit, which is stricter than "per tier visit" and rules out any loop.

## Judgment calls the reviewer should weigh

- **The immediate query also feeds the promotion check.** The ticket frames the trigger as "during hang-out". Putting the check in the shared path means the immediate `QueryV1` right after `Accepted` can also trigger `reregister` (checked after the `done` short-circuit, before edge case 1 and `decide`). Effect: an `Accepted` with no traffic whose immediate query shows child cohorts re-registers instead of escalating. Handed to the docs ticket.
- **Query-reply and push traffic now feed `maxChildCohortCount`**, not only `Accepted` replies (doc comment on `SeekerWalkResult.maxChildCohortCount` updated). It can only rise, so it can only push the public session / voting binding toward the sweep. The mesh `hot regime` test (expects 4) still passes because its query replies use the same modelled traffic. Handed to the docs ticket.
- **Re-register is not gated on remaining patience.** A promotion seen on the final poll (patience 0) still re-registers and descends. I considered gating it but didn't: the walk already keeps escalating past the deadline on the poll path, and the per-walk bound limits it to one extra register per tier.
- **Push path at zero patience still runs the final poll**, as the ticket says, which repeats the immediate query when a walk reaches the root with no patience left. The poll path issues none.

## Known gaps / inspection-only

- **Stale pushes across a tier change.** After escalating, pushes queued from the old tier's primary are taken at the next push-path hang-out, and their entries are admitted (still valid providers for the topic). Their traffic is the *old* cohort's, so a promoted old tier could set off one extra re-register at the new tier. In a consistent tree the new (parent) tier's `Accepted` already reports child cohorts, so its watch isn't armed. Not tested.
- Pushes still queued when a tier exits without a push hang-out (done on the immediate query, plain escalation) are never taken. `close()` releases them. The safety and final polls cover what they carried.
- Spurious early wakes, `pushSafetyPollMs <= 0` (re-queries on every wake, same as `requeryIntervalMs: 0` on the poll path), and push-for-another-topic are covered by reading the code, not by tests.
- `close()` being called is wiring and has no test.

## Tests added (`seeker-walk-client.spec.ts`, `push path` block)

The harness got an optional push schedule (any schedule, even empty, gives the transport a `pushes` channel whose `wait` advances the virtual clock to the next scheduled push or the timeout) and per-tier register scripts (`probe` may be a function of the register ordinal). Existing tests construct it unchanged and still take the poll path.

- *sparse safety-poll cadence* — no pushes, 10 s patience: exact call sequence `register, query, renew, query, renew, query`, waits `[5000, 5000]`, no `sleep` (doc *Sparse safety-poll cadence*).
- *missed push, final poll recovers* — a provider only the final query returns ends up in the result (doc *Missed push, final poll recovers*).
- *push/poll overlap deduped* — pushed B then polled B: `wantCount` 3 stays unmet with `[A, B]` (doc *Push/poll overlap deduped*).
- *push forgery rejected* — a tampered entry in a push is dropped and its valid neighbour admitted (doc *Push forgery rejected*).
- *promotion observed via a push* — `register:1, query:1, register:1, register:2, query:2`: no withdraw, follows `promoted`, `maxChildCohortCount` 2 (doc *Promotion observed via folded topicTraffic*).
- *a push that meets wantCount* — the walk ends at the push's time with only the immediate query issued.
