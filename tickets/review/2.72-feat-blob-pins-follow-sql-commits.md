# Blob pins follow SQL commits — review

Third of four parts of backlog `feat-sql-columns-hold-blob-references`. Connects the reference trees (`feat-blob-reference-trees-follow-sql-rows`) to the cohort announcement (`feat-a-held-blob-follows-its-cohort`) for every commit that reaches storage or the offline queue: the references a transaction adds are pinned on the writer when its commit starts, announced with the table's reference tree as their scope and unpinned once the commit lands, and unpinned if the transaction is abandoned.

## What was built

**The replay guard** (`src/transaction/replay-scope.ts`). `duringReplay(db, run)` / `isReplaying(db)` over a module-level `WeakMap<Database, number>` counter. `QuereusEngine.execute` holds it raised around its whole statement loop, inside the existing `try` so a throwing re-execution still decrements. Every execution through that engine is a replay — the writer's own session records statements rather than running them there — so the whole loop is marked rather than any narrower scope. `laneCeiling` is unguarded: it prepares without executing.

**The ledger** (`src/optimystic-adapter/blob-reference-ledger.ts`). `TransactionState.blobReferences`, initialized in `TransactionBridge.beginTransaction` and in `transactorOnlyState`, holding one record per staged reference change (in staging order, each with its network's transactor key) and one per blob put while the transaction was open. `addedReferences` folds the records by **referrer** — `(backendKey, scope, referrer)`, last change wins — and then deduplicates the surviving adds by `(backendKey, ref, scope)`. `putReferences` deduplicates puts by `(backendKey, ref)`.

**Recording.** `OptimysticVirtualTable.buildBlobReferences` now passes the maintainer an `onStaged` that calls `TransactionBridge.noteBlobReferences(backendKey, changes)` unless `isReplaying(this.db)`. The backend key comes from the new public `CollectionFactory.transactorKeyOf(options)`, read once synchronously at construction. `SqlBlobService.put` records its put through `noteBlobPut` only when this service defaulted the owner label to a transaction **and** that transaction is still the open one when the put resolves.

**Savepoints.** Legacy mode only: `createSavepoint` marks `records.length` after the session-mode and dedup returns, `rollbackToSavepoint` truncates after the absent-snapshots return, `releaseSavepoint` drops the marks at and above the depth. Deliberately *not* `writeFacts`' placement, because in session mode a statement savepoint rollback does not restore the trees, so truncating there would leave a reference that *will* commit unpinned. A comment at the mark says exactly that. Puts are never truncated.

**The pins** (`src/optimystic-adapter/blob-pins.ts`). `SqlBlobPins` with `holdForCommit` (all or nothing; unpins what it took and rethrows, so a failed pin fails the commit before anything is sent) and three settling arms — `committed`, `queued`, `abandoned` — none of which throws, each handling one reference in its own `try`. Every arm takes the transaction and reads its puts off the ledger rather than off `HeldPins`, so an arm runs correctly for a commit whose `holdForCommit` never completed. Announce before unpin, always. Built and attached in `register`; a bridge built bare (every spec that constructs `new TransactionBridge(factory)`) has none and neither pins nor announces.

**The factory.** `transactorKeyOf`, a private `Map<string, ParsedOptimysticOptions>` written at the top of `getOrCreateTransactor` (ahead of the cache check, first options per key winning), and `blobBackendForKey` which looks the options up and delegates to `getBlobBackend` so it shares the per-key de-duplication. `clearCache()` and `dispose()` deliberately do not forget the options.

**The routes.** One private `TransactionBridge.settleBlobPins(transaction, settlement)` with a once-guard (a flag beside `heldBlobPins`, both reset in `beginTransaction`), called from every exit; `holdForCommit` runs inside `commitTransaction`'s `try`, after the stale-description check and before the route branch. `afterFailedCommit` now takes the transaction, because its two partial-commit arms settle by what they left durable. The route table is in docs/internals.md §A table's blob references.

## How to exercise it by hand

```ts
const { ref } = await plugin.blobs.put(fileStream);          // pinned sql-unstaged/<ms>
await plugin.blobs.pinsOf(ref);                              // ['sql-unstaged/…']
const off = plugin.blobs.onDurability(e => console.log(e));  // subscribe BEFORE the insert
await db.exec('insert into Attachment (Id, Content) values (?, ?)', [id, ref]);
await plugin.blobs.pinsOf(ref);                              // [] — announced, then released
(await plugin.blobs.stat(ref)).durability;                   // { quorum: 'local', … }
```

`DEBUG=optimystic:quereus-plugin:blob` shows the lifecycle: `blob:pin-held` once per commit that pinned something, `blob:announced` per reference, `blob:pin-kept` with a `reason=` for a pin deliberately retained, `blob:pin-release-failed` for an `unpin` that threw, `blob:pin-settle-failed` for a whole arm that faulted.

## Tests, and what each verifies

`packages/quereus-plugin-optimystic/test/blob-pins-online.spec.ts` (new), on a `local` transactor over one `MemoryRawStorage`, real blobs throughout:

- **announces and releases a blob a committed row came to reference** — docs/blobs.md §SQL's own example (put outside a transaction, insert later): the `unstaged` pin before the insert, no pin of any kind after it, `locality: 'here'` with durability `local`, exactly one durability event naming the reference, and the announced scope present in the network's registry.
- **releases a put made inside a rolled-back transaction, and keeps one made before it** — the `put`-pin arm of `abandoned`, and the deliberate asymmetry that keeps an `unstaged` pin so a retry need not re-put the bytes.
- **leaves a reference only a rolled-back savepoint staged unpinned and unannounced** — the legacy-mode ledger truncation: the committed row's reference is announced and released, the discarded statement's blob keeps the hold it had and was never announced. Also the mechanism that keeps an aborted statement's references out, since Quereus wraps every non-FAIL DML statement in its own savepoint.
- **leaves a refused writer's blob pinned as it was, with nothing of the transaction left on it** — two handles over one block store racing one primary key; the loser's reference pin goes, its `unstaged` pin stays, nothing was announced.
- **neither pins nor announces anything while re-executing a replicated transaction** — the replay guard, driving `QuereusEngine.execute` directly. **Verified load-bearing**: with the guard forced off, this fails on `stat(ref).durability` (the member had created a record with durability `local` and an `owed` hold for bytes it never had).
- **`what a commit pins`** — eight table-driven cases over `addedReferences` plus one over `putReferences`: insert-then-delete pins nothing, an update pins only the new reference, a bare remove pins nothing, a primary-key move keeps the pin, a displacing move at one referrer keeps one pin, two rows and two columns of one table each dedupe to one pin, two tables stay two pins.

`blob-functions.spec.ts` — "pins a put made while a transaction is open under that transaction" **changed**: it asserted the pin survives the commit (which this ticket is what changes). It now asserts the `sql/<stampId>/put` label while the transaction is open and no pin after the commit, which is the documented footgun.

`adapter-integration.spec.ts` — two hand-built `TransactionState` literals gained `blobReferences`. No behaviour change.

## Known gaps — read these first

- **The partial-commit arms are inspection only.** Neither `PartialCommitError` (the legacy per-tree sweep's split) nor `CoordinatorPartialCommitError` is driven with a `blobref` table anywhere. `legacy-commit-atomicity.spec.ts` drives both errors but over tables with no `blobref` column, so the new `settleBlobPins` calls in those two arms never execute under test. The claim they rest on — that `PartialCommitError.persisted` holds collection ids, because `treeLabel` answers `Tree.describe()` which renders `collection.id`, and a reference tree's scope *is* that id — is read from the code, not observed. Worth a reviewer's eye, and a candidate for a test if one is cheap on the existing fixture.
- **The `queued` route is wired but untested here.** `feat-queued-blob-pins-settle-with-their-transaction` owns the queued lifecycle and its harness; what this part added is the two call sites (`local` route after `endTransaction`, `behind-queue` route *before* `awaitQueuedCommit`, since the entry is the queue's by then) and the arm that drops the transaction's `put` pins while keeping its reference pins.
- **Session-mode pinning is wired but not asserted.** `holdForCommit` sits before the route branch, so session mode pins, announces and releases exactly as legacy does, and `blob-reference-tree.spec.ts`' session-mode case now runs that path — but it asserts nothing about pins or durability. A pin assertion there would be cheap.
- **The `announce`-throws and `scope-unregistered` arms are inspection only.** Both keep the pin and log `blob:pin-kept`; neither is reached by a test. The first is the whole behaviour of a node built without a blob copy drain (`NodeBlobService.announce` throws for every reference), and it is also the reason the arm must not escape into the commit — the rows are durable by then.
- **A judgement call worth confirming.** `committed` drops the `unstaged` pins of every reference whose scope committed, *including* ones whose announcement failed and whose reference pin is therefore kept. That follows the ticket's wording ("for each reference with at least one committed scope") and is safe — the kept reference pin holds the bytes just as the `unstaged` pin did — but it is a choice, commented at the site.
- **A deliberate deviation from the ticket.** The ticket marked the `addedReferences` fold "Inspection of `addedReferences`"; it is tested instead (the `what a commit pins` block). It is a pure function with eight specified behaviours, five of which no end-to-end case can distinguish from a pin that was taken and released, and the test needs no fixture. The reviewer is free to cut it; the reasoning is here rather than hidden.
- **One log line beyond the four the ticket named.** `blob:pin-settle-failed` (a whole settling arm faulting, which should be unreachable since each reference is isolated) is emitted and documented in docs/debugging.md alongside the other four.
- **`plugin.blobPins` is not exposed.** `feat-sql-columns-hold-blob-references` expects to drive `plugin.blobPins.sweepUnstaged(now)`; the instance is attached to the bridge and nothing else holds it. Adding the handle is the work of whichever earlier part needs it first, not this one.
- **Tripwire, parked in code.** `SqlBlobPins`' constructor carries a `NOTE:` saying every pin, announcement and release is awaited in sequence — N local record writes at `holdForCommit` and up to 2N at the release, inside the commit the host is awaiting — with what to do if a transaction referencing hundreds of blobs ever shows the commit slowing.

## Behaviour changes a reviewer should weigh

- **A commit of a `blobref` table now resolves that network's blob backend**, where before nothing on the commit path touched it. For `local`/`test`/`mesh-test` that builds a `SingleMachineBlobService` over a memory piece store on the first such commit, so `blob-reference-tree.spec.ts` and `blobref-column.spec.ts` now create blob records for the fabricated references they commit (announcing a reference whose bytes are absent succeeds there: `owed` hold, durability `local`, `confirmed: 0`). Both specs pass; neither asserted the records' absence. A commit that added no reference resolves nothing — `holdForCommit` returns before touching the factory.
- **`plugin.blobs` no longer holds every blob it ever put.** A put inside a transaction that never references the blob loses its pin when the transaction ends. Stated in `SqlBlobService.put`'s doc comment, in the plugin README and in docs/blobs.md §SQL, with the two ways to keep such a blob (put outside any transaction, or pass an explicit `owner`).
- **A departure from docs/blobs.md §SQL as written**, now documented there: the pin moves to the transaction when the **commit starts**, not when the first statement stages the reference. Nothing reached from `update()` may call the blob service, because a validating member runs the same statements with no bytes. The bounded cost — a transaction open longer than the 24-hour `unstaged` holding period — is what the last part closes.

## Handoff to the last part (carry forward unchanged)

`feat-sql-columns-hold-blob-references` must not expire an `unstaged` pin whose reference carries a reference pin (`sql/<stampId>/ref/<scope>`) of a live transaction — open or queued — because `queued` and `abandoned` now leave those `unstaged` pins in place deliberately. Its `openReferences` dependency therefore widens from "the open transaction's ledger" to "any live transaction's references", which it can read straight off the pin labels. That ticket already carries this requirement in full; nothing needs adding to it.
