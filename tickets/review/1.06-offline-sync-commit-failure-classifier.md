The last ticket of stage 1 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). The offline queue's sender (stage 3) will call this to decide, per failed attempt, whether an entry waits, settles as failed, or is treated as possibly landed.

## What landed

`classifyCommitFailure(error: unknown): CommitFailureClass` in `packages/db-core/src/transaction/commit-failure-class.ts`, exported (with the `CommitFailureClass` type) through `packages/db-core/src/transaction/index.ts`, which the root barrel re-exports — so `import { classifyCommitFailure } from '@optimystic/db-core'` works. Every class is imported from its defining module, not a barrel.

Arms, in the order the function tests them:

| Error | `kind` |
|---|---|
| `PromiseShortfallError` | `cohort-unreachable` |
| `BlockUnavailableError`, `reason` `cohort-unreachable` / `peers-unreachable` | `cohort-unreachable` |
| `BlockUnavailableError`, any other reason | `unknown` |
| `SyncRetryExhaustedError` (covers `SyncRevisionStalledError`), `CoordinatorStaleLossError` | `contention` |
| `TreeEntryChangedError` | `guard-refused`, `refusal: 'concurrent-modification'` |
| any other `TreeGuardRefusedError` (`TreeKeyTakenError`, `TreeRangeTakenError`, future subclasses) | `guard-refused`, `refusal: 'constraint'` |
| `ValidityRejectedError` | `rejected` |
| `TransactionTooLargeError`, `BlockTooLargeError` | `too-large` |
| `TransactionExpiredError` | `expired` |
| `TornActionError`, `final: true` / `false` | `torn-not-saved` / `in-doubt` |
| `CoordinatorPartialCommitError` | `partial` |
| everything else | `unknown` |

Rules held by construction: only `instanceof` and the structured fields `reason` / `final` are read (never `message`); `cause` is never walked. Each arm's `error` is the input, narrowed to its classes. The doc comment notes that a duplicated package copy would defeat `instanceof` and that `yarn lint:deps` keeps that out.

Docs:
- `docs/offline-sync.md`: status line now says stage 1 is implemented and the rest is a proposal; the classification table names `PromiseShortfallError` in the unreachable row, adds `CoordinatorStaleLossError` to the contention row, and has a new "Too large to commit" row (entry becomes `failed`: `too-large`); the "Two of these rows needed typed errors" paragraph is replaced by one naming `classifyCommitFailure` and its two rules (keeping the validity-classification caveat and the `unknown`-is-transient rule); `'too-large'` added to `QueuedFailureReason`; stage 1 marked implemented.
- `docs/internals.md`: one sentence at the end of the "Pend retryability is an explicit field" bullet naming `classifyCommitFailure` as the one place commit failures are sorted.

## Test

`packages/db-core/test/commit-failure-class.spec.ts` — one table-driven `describe`, 12 cases, each asserting the kind (plus `refusal` for guard refusals) and that `error` is the input:
- `BlockUnavailableError` `'cohort-unreachable'` → `cohort-unreachable`; `'named-by-log'` → `unknown` (the reason branch).
- `TreeEntryChangedError` → `concurrent-modification`; `TreeKeyTakenError`, `TreeRangeTakenError` → `constraint` (the subclass branch).
- `SyncRevisionStalledError` → `contention` (subclass not mis-sorted).
- `TornActionError` `final: true` / `false` → `torn-not-saved` / `in-doubt`.
- A plain `Error` whose message is exactly the shortfall sentence → `unknown` (no text read); a plain `Error` whose `cause` is a `PromiseShortfallError` → `unknown` (cause not walked).
- `PromiseShortfallError`, `ValidityRejectedError` → their rows.

A `summarize` helper in the spec switches over `kind` with a `never` default, so adding an arm without handling it fails `yarn build` (db-core's `tsconfig.json` includes `test/`). That is the exhaustiveness check the ticket asked for; there is no `assertNever` helper in the codebase to use instead.

Validation run: `yarn build` and `yarn test` in db-core (1933 passing), `yarn lint:docs` clean, eslint clean on the touched files.

## Things for the reviewer to weigh

- **Errors that fall to `unknown` without a case:** `TreeDeleteGuardKindError` (outside the guard hierarchy by design), `CoordinatorConcurrentStampError`, `BlockPossiblyStaleError` (a sibling of `BlockUnavailableError`, not a subclass) and `CollectionHeaderVanishedError`. All are `unknown` by fall-through; none has its own test case. If any of these should get a row of its own, the doc table is the place to decide it first.
- **`TornActionError.reason` is ignored** — only `final` decides. That matches the doc table, which keys the two torn rows on `final` alone.
- **The export goes through the transaction barrel**, not a direct line in `src/index.ts`; the ticket named `src/index.ts`, and the root re-exports `transaction/index.js`, so the public surface is the same.
- **`QueuedFailureReason` `'too-large'`** exists only in the design doc; no code has that type yet (it arrives with stage 3/4).
- The `cohort-unreachable` row in the doc still lists "a refused solo write" and "the gate saying no", which are stage-6 conditions the classifier does not see; left as is because they describe drain outcomes, not error classes.
