# quereus-plugin-crypto: a native crypto backend (review)

GitHub: [#30](https://github.com/gotchoices/Optimystic/issues/30). The reporter measured one tally invitation at 29 s on a Galaxy S7, with SQL `verify` at 408 ms inclusive, 366 ms of it in noble's JavaScript Ed25519.

## What was built

`setCryptoBackend(backend | undefined)` and the `CryptoBackend` interface, in `packages/quereus-plugin-crypto/src/crypto.ts`, exported from the package root (`src/index.ts`). Members, all optional: `sha256`, `sha512`, `ed25519Sign(message, rawSeed)`, `ed25519Verify(signature, message, rawPublicKey)`. An omitted member stays on `@noble`.

- **State on `globalThis`** under `Symbol.for('@optimystic/quereus-plugin-crypto/backend')`, because `dist/index.js` and `dist/plugin.js` are separate tsup entries with `splitting: false`, each carrying its own copy of `crypto.ts`.
- **Call-time dispatch.** `HASHERS.sha256` / `.sha512` are now dispatchers (`dispatchHash`) that read the slot on every call and fall back to noble; `blake3` is still noble directly. So everything that gets a hasher from `resolveHasher` — the plugin's registration-time `digestHasher`, `cid`, `hashMod`, `set_commit` / `set_verify` in `sd.ts` — honours a backend set after registration. The Ed25519 branches of `sign` / `verify` go through `ed25519Sign` / `ed25519Verify` helpers that do the same. `verify`'s existing catch-all turns a backend throw into `false`; a `sign`, `digest` or `cid` throw propagates.
- **Self-check at set time** (`selfCheckBackend`): each supplied member against noble on fixed inputs — hashes equal; `ed25519Sign` equals noble's signature for a fixed 32-byte seed; `ed25519Verify` accepts noble's signature and rejects (false or throw) once one message byte is flipped. Failure throws an `Error` naming the member (a member that throws is wrapped with `cause`) and the slot is untouched.
- **ZIP-215 tripwire**: `NOTE:` at `ed25519Verify` in `crypto.ts`, and the same caveat in the README section.

Two things beyond the ticket's text, both small and worth a reviewer's opinion:

- **Inputs to the self-check are offset views** (`offsetView`): each input is a `subarray` at offset 1 inside a larger buffer. An adapter that hands the native side `data.buffer` (a common mistake, and the plugin does pass views) hashes the wrong bytes; without this, the fixed inputs are exactly-sized fresh arrays and that adapter would pass the check. The refused-backend test uses exactly that adapter.
- **The installed backend is a frozen, bound snapshot** (`snapshotBackend`): only the four known members are copied, each `bind`-ed to the caller's object. So a member added to or replaced on the caller's object after the call never runs unchecked, and an older copy of the package sharing the `Symbol.for` slot never installs a member it cannot check. Untested; by inspection.

Also: comments that said "no per-call branching" in `crypto.ts` (`HASHERS`, `resolveHasher`, `digestFields`) and `plugin.ts` (`register`) now say the algorithm/encoding *selection* is done once and the hasher reads the backend per call; `cid.ts`'s header notes the sha2 routing. Byte comparison in the self-check goes through `bytesToHex` (already imported) rather than a new `uint8arrays` `equals` import, because the `/plugin` bundle tree-shakes the setter out and the import left unused there produced a tsup build warning.

Docs: README gains a "Native crypto backend" section (what it speeds up, set once / process-wide / call-time effect, why not a plugin option, the self-check, byte-identity requirement, error behaviour, ZIP-215 caveat, the `node:crypto` adapter as a worked example, and that react-native-quick-crypto's acceptance of the DER-wrapped raw keys is unconfirmed); the "React Native Compatibility" and "Security Notes" wording no longer implies there is no native path. `docs/crypto.md` §Architecture gets one paragraph. `CHANGELOG.md` gets an entry headed **"Unreleased"** — the version number is chosen at release (`yarn bump`), so whoever releases should rename that heading.

## Tests

`packages/quereus-plugin-crypto/test/crypto-backend.spec.ts`, with a real node backend on `node:crypto` (DER-wrapped raw Ed25519 keys, counting calls per member); `afterEach` restores noble since the slot is process-global.

- **"gives byte-identical results through the SQL functions, and is actually used"** — plugin registered from `dist/plugin.js` before the backend is set through `dist/index.js` (covers both the two-bundle case and the set-after-registration case); `digest('a', 1)`, `cid` with sha2-256 and with sha2-512, `sign(..., 'ed25519')`, and `verify` on a valid and a tampered message equal the no-backend values; counters are reset after `setCryptoBackend` (the self-check itself calls every member) and each is then above zero.
- **"refuses a backend that disagrees with @noble and keeps the one installed"** — a `sha256` adapter that hashes `data.buffer` and an `ed25519Sign` that returns a different signature each make `setCryptoBackend` throw naming the member; the previously installed node backend's counters still advance afterwards.

## Validation run

From `packages/quereus-plugin-crypto`: `yarn build`, `yarn test` (127 passing), `yarn typecheck`. From root: `yarn lint`, `yarn lint:docs`, `yarn check:rn` (Metro + hermesc passed), `node scripts/check-undeclared-deps.mjs`.

## Known gaps — not covered by a test

- A backend that throws at call time (`verify` → false; `sign` / `digest` / `cid` propagate) — by inspection only, as the ticket allowed.
- A partial backend (e.g. only `ed25519Verify`) leaving hashes on noble — by inspection.
- Two separately installed copies of the package sharing the slot — only the two-bundle case is tested.
- `setCryptoBackend(undefined)` is exercised only as the `afterEach` reset, not asserted directly.
- Nothing has run on a device or with react-native-quick-crypto; the README says so. The self-check runs one known answer per member, so it catches a mis-built adapter, not a native library that is wrong on other inputs.
- A backend returning a node `Buffer` (a `Uint8Array` subclass) is passed through to the encoders, `cid` framing and `hashMod`'s `DataView` (which uses `byteOffset`); the first test covers digest/cid/sign with Buffers, not `hash_mod`.
