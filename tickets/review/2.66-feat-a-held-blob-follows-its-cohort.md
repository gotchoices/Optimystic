# A held blob follows its cohort

[docs/blobs.md §Placement, copying and durability](../../docs/blobs.md#placement-copying-and-durability), *When the cohort changes*: "A node's held blobs are enumerable from its records, so the cohort comparison `RebalanceMonitor` makes for blocks is made for blobs too, by giving it the routing key rule rather than a second copy of its logic."

The prereq (`feat-the-blob-cohort-reaction`) built the decision with no wiring. This ticket runs a second `RebalanceMonitor` over the blob references this node keeps for the network and acts on what `BlobCohortReaction.handle` returns. With it, every part of that section of docs/blobs.md exists.

No new tests. Everything here is a feed, a restart seed and registration; the reaction's two arms are pinned by `test/blob-cohort-reaction.spec.ts`, the monitor's check-and-report behaviour by the five rebalance suites with the routing rule a pass-through, and the copying this triggers end to end by `test/blob-copy.spec.ts`. The gaps that leaves are listed under *What is not covered* below — read that before deciding the ticket owes nothing.

## What landed

**The feed.** `LocalBlobService.onHoldsChanged(listener)` (declared on `BlobResponsibleRecords`) is a second listener set beside `durabilityListeners`, emitted from `changeRecord` — the one path every record change takes — through `emitHoldsChanged`, and only when the set of hold *kinds* in `result.before` differs from the set in `result.after` (a missing record counting as no holds, `sameHoldKinds`). So a `lastReadAt` touch, a `whole` correction, a second owner's pin, and a `responsible` hold whose scope was replaced do not fire; every hold that appears or goes does. A listener that throws is logged (`holds:listener-threw`, under `blob:store`) and does not stop the others, as `emitDurability` does. It emits before the caller's `flush`, which is deliberate: a listener only mutates an in-memory set that is re-derived at every start.

`subscribe` is now generic in the listener type rather than in an event type, so a feed can hand its listeners more than one argument. The two existing feeds are unchanged.

**The restart seed.** `seedHeldBlobs` in `packages/db-p2p/src/blob/held-blob-seed.ts`, modelled on `seedOwnedBlocksFromStorage` in `packages/db-p2p/src/owned-block-seed.ts`: every `responsibleRefs()` reference is tracked, then every `owed.list()` entry is tracked **and then** its holders reported through `monitor.recordBlockHolders`, so the first check after a restart does not re-announce to members the writer already knows hold the blob. Tracked before reported, because evidence for an untracked id is dropped at the next check. `isStopping()` is checked each reference and a cooperative yield lands every `yieldEvery` (default 1000) references.

**The monitor instance.** Built in `createLibp2pNodeBase` after the owed-copies drain, from `served.arachnode` — a new additive field on the internal `ServingRole` carrying the FRET service and its `ArachnodeFretAdapter`, assigned inside the arachnode `if (fret)` gate that is the only place they exist. Its tracked set is its own `Set`, never the shared owned-block set; it takes `routingKeyOf: id => routingKeyForBlob(id as BlobRef)` and `logName: 'blob:copy'`, shares `options.rebalance` with the block instance, and is constructed directly rather than through `NetworkManagerService.initRebalanceMonitor`, which holds the block instance. A wiring failure is logged (`node-wiring`) and non-fatal. Exposed as `(node as any).blobRebalanceMonitor`, beside `blobCopyDrain` and `rebalanceMonitor`.

Order inside the block: construct, subscribe the feed, build the reaction, attach the handler, `await monitor.start()`, assign `blobRebalanceMonitor`, install the stop wrapper, fire the seed off the start path.

**What is tracked** is a reference whose record carries an `owed` or a `responsible` hold. A pin and a `cached` hold are not tracked: a node does not announce a blob it merely read.

**The handler** hops the reaction off the monitor's synchronous emit loop, then releases each confirmed reference in turn (`blobs.releaseResponsible`, which fires the feed and untracks the reference when no `owed` hold remains), calls `retainLost` for each unconfirmed one and `recordGrowthOutcome` for each growth outcome. A rejection logs `reaction:failed` under the new module-level `blobCopyLog` and records nothing, so the next check retries.

**Holder evidence while running.** `BlobCopyDrainDeps.onHolderConfirmed`, unset until now, is wired to `blobRebalanceMonitor?.recordBlockHolders(...)`, so a `whole` answer or an arriving `held` also counts for growth.

**A client** (`NodeOptions.servesBlocks: false`) runs no serving role, so `served` is undefined and it gets no blob monitor: it is in no cohort, never takes a `responsible` hold, and its owed blobs are followed by the drain on its own passes.

## Decisions taken here that the ticket left open

- **The handler is guardless**, with a `NOTE:` at the site saying so. `onRebalance` handlers are synchronous and `void`, so a check landing before the previous reaction settles runs a second one over the same references. Judged benign and unlikely (a 60-second minimum interval against a reaction of a few round trips): `releaseResponsible` is idempotent, duplicate announcements are what `AnnounceLimiter` is for, and two reactions over one snapshot agree on their outcomes. The note names the fix (one in-flight promise per monitor, as `BlockTransferCoordinator` does with its `inFlight` keys) if overlap is ever observed. **This is the one judgment call in the ticket worth a second opinion.**
- **An owed entry with no holders is not reported.** The ticket's text reports every entry through `recordBlockHolders`; an entry with an empty `holders` array has nothing to say and would only leave an empty evidence entry for the next check to discard, so it is skipped.
- **`heldBlobRefs` is declared inside the wiring block** rather than above the `if`, since nothing outside it reads the set.

## What is not covered

- **No test asserts the blob monitor is wired at all.** `test/rebalance-monitor-node-wiring.spec.ts` builds a real solo node with arachnode and FRET, so that spec now constructs this monitor too and proves the wiring does not throw or break the node's teardown — but it asserts nothing about `node.blobRebalanceMonitor`, the feed, or the seed. There is precedent for such a spec on both sides (`test/owned-block-seed-node-wiring.spec.ts`, `test/rebalance-monitor-node-wiring.spec.ts`). Whether one is worth adding here — the obvious shape being "a node with a `responsible` hold on disk comes up tracking that reference, and `rebalance: { enabled: false }` or arachnode disabled leaves `node.blobRebalanceMonitor` undefined" — is a judgment the review should make rather than inherit.
- **No test pins the feed's kind-change rule.** `emitHoldsChanged` has real branching (a hold appearing, a hold going, a record deleted, a scope replaced, a second pin), and nothing exercises it. `test/local-blob-service.spec.ts` covers the hold paths underneath it and passes unchanged, which only means the emit broke nothing.
- **A holder confirmed in the window before `blobRebalanceMonitor` is assigned is dropped.** The drain's start pass runs off its start path (`DrainScheduler.start` fires it with `void`), so it can confirm a holder while the monitor block is still wiring, and `blobRebalanceMonitor?.` no-ops. Mostly closed by the seed, which reports every holder the owed ledger records before `owed.list()` runs; a confirmation landing after that read self-heals at one announcement's cost — the next check reports the peer grown, it answers `whole`, and `onHolderConfirmed` records it then.
- **A `responsible` holder re-announces to its whole cohort after every restart.** There is nowhere to seed its holder memory from (the holders of a blob it did not write are recorded nowhere), so this is by design, bounded by `growthBlockBudget` (64) references per check and `minRebalanceIntervalMs` (60 s) between checks — well inside `BLOB_ANNOUNCES_PER_PEER_PER_MINUTE`. Each receiver answers `whole` without reading committed state. Stated in docs/blobs.md.
- **The release arm's announcements remain the one unbudgeted announcement path**, which the prereq's review already parked as a tripwire at `BLOB_ANNOUNCES_PER_PEER_PER_MINUTE` in `packages/db-p2p/src/protocol-limits.ts`. This ticket is what makes that path reachable on a running node; nothing about the tripwire's analysis changed, so it was not re-filed.

## Use cases to check

- **A member joins a held blob's cohort.** A node holding a blob `responsible` sees a peer join; the check reports the reference `grown`; the reaction announces to that peer under the hold's scope; `whole`, `fetching` or `declined` satisfies it and the peer stops being re-announced to. A `fetching` peer's later `held` reaches the monitor through the drain's `onHolderConfirmed`.
- **A node leaves a blob's cohort with enough holders.** The reference is reported `lost`; the reaction `stat`s the new owners that accept blobs; once the floor answers `whole` the handler calls `releaseResponsible`, the feed untracks the reference, and the record's deletion (when no other hold remains) schedules the piece sweep that reclaims the bytes.
- **A node leaves a cohort with too few holders.** Nothing is released: the handler calls `retainLost`, the re-check timer is armed, and the reference is re-reported `lost` on later checks until enough current members answer `whole`.
- **A restart.** A node with `responsible` holds and owed entries on disk comes up tracking both, and the first check does not re-announce to the holders its owed entries already name.
- **A blob read but not kept for the network.** A `cached` hold or a pin is never tracked, so such a blob is never announced to anyone.
- **Switches.** `rebalance: { enabled: false }`, `arachnode: { enableRingZulu: false }`, a node with no FRET, and `servesBlocks: false` each leave `node.blobRebalanceMonitor` undefined, and the drain keeps working. `blobs: { copy: { enabled: false } }` leaves the monitor wired with the reaction's `declining` dep absent.
- **Partition.** The monitor suppresses its checks and the reaction re-checks before acting, so no release and no announcement.
- **Block replication unchanged.** The block monitor, its reaction and the owned-block set are untouched; the one `ServingRole` field is additive.
