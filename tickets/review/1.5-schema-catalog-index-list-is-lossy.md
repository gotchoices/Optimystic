# Review: persisted schema `indexes` list made durable across nodes

Implements `implement/schema-catalog-index-list-is-lossy`. Both loss sites closed; build,
typecheck and the full package suite (454 passing, 11 pending — pre-existing pendings) are green.

## What was built

**The choke point — every schema write is now non-destructive for `indexes`.**
`SchemaManager.storeStoredSchema` (schema-manager.ts) re-reads the table's catalog entry through
the write tree immediately before writing and unions the incoming index list with what is
persisted right now (`mergeIndexLists`, exported from the package index for direct testing).
Union rules: an index on either side survives (incoming order first, persisted-only appended);
uniqueness never silently downgrades (a persisted `unique` flag and its predicate are kept when
the incoming copy lacks them; an incoming unique upgrade wins). The method now returns the schema
**actually written** and refreshes the per-instance cache with it only after the write succeeds;
both callers were updated to honour the returned value. There is no index-removal path in the
plugin today (DROP TABLE tombstones the whole record via `deleteSchema`), so union and correct
coincide — a future DROP INDEX needs a dedicated removal API, stated in the `mergeIndexLists` doc.

**Site A (clobber-on-unreadable-read).** `doInitialize`'s mismatch branch no longer trusts
"persisted read came back empty" as proof of absence: the contract is stated at the call site, a
debug log fires when it writes with no persisted side visible, and the write-time union preserves
any index list the read could not see. The write-then-read-back detour (`getSchema` after store,
with a 'Failed to store and retrieve schema' error) was replaced by using the store's return value.

**Site B (stale cache / lost update).** New `SchemaManager.getSchemaFresh` reads the catalog
first, bypassing the never-invalidated per-instance cache, falling back to the cache only when
the catalog read yields nothing (a cached entry proves a schema existed; "nothing" can still mean
unreadable). `addIndex` — the mutating path — now uses it; `getSchema` keeps its cached behavior
for read paths (hydrate seeding perf) and both contracts are documented on the methods.
`addIndex`'s write-back is a name-keyed union via the choke point, so two nodes adding different
indexes from independent caches both survive.

**Ordering fix the union forced.** A union-widened written schema can list a sibling's index this
vtab has no tree for, and `IndexManager.insertIndexEntries` throws `Index tree not found` for a
listed index without a registered tree. Both `addIndex` paths therefore route through
`reconcileMaintainedIndexes` (which opens/registers trees for every declared index and registers
collections with the transaction bridge) before/instead of a bare `setSchema`: the new-index path
registers its own tree then reconciles against the written schema; the unique-upgrade path
reconciles first, then folds the upgraded descriptors in.

**Discovery — the storage-layer prerequisite already landed.** The ticket assumed
`repo-reports-unavailable-vs-absent` had not landed; it is in `tickets/complete/4.5-…`. A
*provably* indeterminate block read now throws `BlockUnavailableError` out of
`Tree.open`/`update`, which propagates out of `getSchema` — so the "unreachable catalog" arm of
Site A already fails loudly (the ticket's preferred option 1, for free). The residual undetectable
case is a cohort that *silently* answers "nothing" (per-peer timeout indistinguishable from an
empty peer — the coordinator-repo tripwire recorded in complete/4.5). Several stale comments
claiming the layers "cannot yet distinguish" were corrected to this narrower reality
(schema-manager read/write docs, doInitialize contract).

`npx tsc --noEmit` clean; repo-root `yarn typecheck` clean.

New spec `test/schema-catalog-index-durability.spec.ts`:
- **Clobber pin**: session 1 persists table+index; session 2's `getCollection` is intercepted to
  report the schema catalog absent (simulating the silent-absent case) while the write path still
  reaches storage; re-running the bare CREATE TABLE must not shrink the persisted list. Fails
  pre-fix (wrote `indexes: []`).
- **Lost-update pin**: two plugins over shared storage; both CREATE TABLE (cold caches), A adds
  idx_vendor, an assertion pins B's cached copy as stale, B adds idx_sku; both indexes must be
  persisted. Fails pre-fix (B wrote `[idx_sku]` from its stale cache).
- **mergeIndexLists unit pins**: order/append, never-shrinks, no unique downgrade (predicate
  travels), incoming upgrade wins.

## Known gaps and residuals (honest list)

- **Residual clobber window, documented not closed**: if the *write* path's pre-union read is also
  served a silent "absent" for a catalog that exists, the union has nothing to merge and the write
  can still clobber. Closing it needs a responders count in the cluster-consult contract — the
  coordinator-repo tripwire in complete/4.5. Documented at `storeStoredSchema`.
- **No CAS**: pre-write read → `tree.replace` (which internally re-syncs) is not atomic; two truly
  concurrent writers interleaving inside that window can still lose an index. The union shrinks
  the window from "since first cached read" to milliseconds; the real fix is the schema-versioning
  design parked in `backlog/more-design/6.5-schema-versioning` (which already cites this ticket).
- **`getSchemaFresh` fallback**: serves the cached copy when the catalog read is empty — so a
  table dropped by another node could still be acted on by a concurrent CREATE INDEX here.
  Pre-existing hazard class (cross-node DDL has no coordination), documented on the method.
- **doInitialize's read path is still cached** (deliberate): the equal-compare short-circuit reads
  through `getSchema` to keep hydrate's N-cache-hits perf win. Staleness there is bounded by the
  write-time union and by `reconcileMaintainedIndexes` on the addIndex side.
- **addIndex's populate loop now iterates union-added sibling indexes too**, staging entries for
  existing rows into the sibling's tree. Idempotent (keyed replace) and arguably helpful, but it
  is extra work the reviewer may want to scope to the new index only.
- **Reproduction remains synthetic**: the clobber is driven via factory interception and the lost
  update via two plugin instances' independent caches — faithful to both mechanisms, but no
  two-real-node mesh test drives either end-to-end (the original fix ticket's eight mesh shapes
  all converged even pre-fix).

## Findings for the reviewer to weigh

- **`deleteSchema`'s revisit condition has tripped.** Its NOTE (schema-manager.ts) says: if
  `repo-reports-unavailable-vs-absent` lands and the delete is still create-on-missing, make it a
  no-op on an absent catalog. That ticket landed; the delete still invents the catalog. Small,
  self-contained change — fix inline during review or file it; I left it untouched as
  out-of-scope for the indexes list.
- `reconcileMaintainedIndexes` still REPLACES the manager's list when reconciling (its NOTE
  updated to reflect the supply side now being closed); the name-keyed-union suggestion there
  stands as a belt-and-braces hardening if a narrower schema ever reaches it.
