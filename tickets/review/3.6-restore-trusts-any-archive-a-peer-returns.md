# Review: `ensureRevision` vets the archive before writing it

## What changed

`BlockStorage.ensureRevision` used to check exactly one thing about the archive a peer handed back
— that it was not `undefined` — and then write it. It now vets it first. A refused archive is
indistinguishable to the caller from an absent one: the same
`Block <id> revision <n> not found during restore attempt.` throw, so
`StorageRepo.readCommitBase`'s deliberately-unnarrowed catch keeps behaving exactly as before. The
specific refusal reason is **logged**, not thrown.

Three files:

- **`packages/db-p2p/src/storage/block-storage.ts`** — new `vetRestoredArchive` (the trust
  boundary) and `noDivergentRewrite` (the overwrite guard), a new module-level `RestoredRevision`
  type, `ensureRevision` rewired to use them, and a new block on `saveRestored`'s doc recording
  which caller earns what.
- **`packages/db-p2p/test/block-storage.spec.ts`** — a new `describe('BlockStorage restore archive
  vetting')` block, 8 tests.
- **`packages/db-core/src/index.ts`** — one added line exporting `canonicalJson`. The overwrite
  guard compares held content against incoming content, and `utility/canonical-json.ts`'s own doc
  says a second copy of that encoding is "a correctness hazard, not a style nit — import this
  rather than re-deriving it". It was simply never on the public barrel. Nothing else changed in
  db-core.

## The rules, and where each one lives

All checks run in `ensureRevision`, not `saveRestored`. **That resolves the ticket's open question**
— see *Placement* below.

| Rule | Refuses |
|---|---|
| `archive.blockId === this.blockId` | an answer about a different block (`saveRestored` writes under `this.blockId` and ignored `archive.blockId` entirely) |
| every revision key is an integer ≥ 1 | a JSON key that coerces to `NaN` and lands as a garbage revision number |
| entry's own `action.rev`, when present, equals the key it is filed under | the mislabel, in miniature |
| entry carries an `action.actionId` | a hollow entry |
| **lowest** revision ≤ the pin | the mislabel class: an archive entirely above the requested revision |
| `range[0] === lowest`, `range[1]` a finite integer `> highest` | a declared range that contradicts the revisions carried; open-ended is refused outright |
| nothing already held is overwritten with different content | see *Overwrite policy* |

Min/max are folded in the parse loop rather than taken with `Math.min(...keys)` — the same
`RangeError`-past-~125k-arguments hazard `maxArchiveRevision` documents, reachable inside the 8 MiB
sync-response cap.

## The two decisions the ticket left open — and the third it did not

### 1. "Covers the requested revision" means **lowest ≤ pin**, not "carries the pin"

This is the arm the `serve-pinned-revision-honestly` review added, and it is load-bearing.
`ActionContext.rev` is a **collection-wide** revision, so it routinely sits above the revision at
which this particular block last changed. A peer answering a pin at 9 for a block whose last commit
was rev 2 correctly serves rev 2 labelled as rev 2, in a range of `[2, 3)`. The ticket's literal
first bullet would have rejected that and turned working historical reads into hard failures.

`materializeBlock` descends from the pin, so what actually matters is that the archive's floor sits
at or below it.

### 2. Recorded coverage is `[lowest, max(highest + 1, pin + 1))` — the arm's second concern

The ticket's rationale said "the range is what gets merged into `meta.ranges` and is therefore the
claim that matters most." **The implementation deliberately does not merge the declared range.** It
validates it for internal consistency and then records a coverage derived from the pin.

Without this, an honest peer's `[2, 3)` answer to a pin at 9 leaves `inRanges(9, …)` false, and
**every later read at rev 9 re-runs the entire restore** — network round trip plus a full
`saveRestored` write — forever, never converging.

The extension is an **inference**, and the only one in the whole guard: a peer answering a pinned
fetch with revision M ≤ N is asserting "M is my highest committed revision of this block at or below
N", i.e. nothing changed in (M, N]. This node cannot verify that locally.

**Why not the ticket's other option — have the wire state the claim explicitly?** It would make the
claim explicit without making it verifiable (a hostile peer echoes whatever it likes), and it would
break repair against every peer running an older build, whose `[M, M+1)` would no longer be
accepted. Rejected on those grounds; the tradeoff is recorded at the code site.

**The residual, recorded as an accepted-tradeoff `NOTE:` on `vetRestoredArchive`:** a lying peer's
answer is now *sticky* across the whole span it was asked about. Reads between M and N are served
locally from M's content and never re-ask, so a later honest peer is never consulted for them.
That is the same position `setLatest` and `saveForwardRevision` already take ("`ranges` records what
this node can locally reconstruct; freshness is a separate concern"). Revisit condition stated: if a
restore ever gains a way to verify an archive, record only what verifies.

### 3. Overwrite policy: **refuse the whole archive**

Of the ticket's two offered options, this is the "safest, and consistent with the bullets above"
one. One divergent entry rejects the entire archive rather than landing the entries this node
happens to lack — because an archive that contradicts locally held content is evidence the peer is
wrong or hostile about this block (which makes the rest of it no more trustworthy), and because a
partial apply would leave the coverage claim above spanning revisions the applied subset may not
support.

The three conflict keys mirror `saveRestored`'s three writes exactly:

- `getRevision(rev)` held under a **different** action id;
- `getTransaction(actionId)` held with a **different** transform;
- `getMaterializedBlock(actionId)` held with **different** bytes (only checked when the entry
  carries a `block`, since otherwise no materialization is written).

**Identical content is not a conflict** — a re-restore must stay idempotent, which the pin-extended
coverage above relies on across overlapping restores. Comparison is by `canonicalJson`, so key
order across a JSON round trip never reads as divergence.

### Placement: `ensureRevision`, not `saveRestored`

The ticket asked which. Answer: **all of it in `ensureRevision`; `saveRestored` pays nothing.**

The shape checks are inherently *about the pinned request* — "does this archive answer the revision
I asked for?" — and `saveRestored` has no pin to check against, so they could not live there
cleanly. Given that, putting the overwrite guard there too keeps the whole boundary in one place.
The verified path (`saveReplica`/`saveDeletion` → `saveForwardRevision` →
`StorageRepo.saveReplicatedBlock`, where `cluster/reconcile-block.ts` bound the bytes to a verified
proof) is exempt, and it does not need the guard on its own terms: its monotonic guard returns
before writing unless the revision is strictly above its own `latest`, so it cannot rewrite held
history.

`saveRestored`'s doc now spells out that it is a **writer, not a gate**, what each of its two
callers earns, and that a third caller taking an archive off a network must route through
`vetRestoredArchive` first. **That is documentation, not enforcement** — see *Known gaps*.

## Testing and validation

`packages/db-p2p/test/block-storage.spec.ts`, `describe('BlockStorage restore archive vetting')`,
8 tests. `seedAtRev` commits a block's first revision at a high global rev so coverage opens at
E = that rev and every read below it is a genuine gap that fires restore.

- **`refuses an archive whose revisions all sit ABOVE the pin`** — the ticket's reproduction. Node
  holds rev 2 = `["TWO"]` under action `a2`; asks for rev 1; peer answers rev 1's bytes filed under
  `2`/`a2`. Asserts the throw, that the fetch *was* made (the refusal is on the answer, not on
  asking), that metadata is byte-identical, and that rev 2 still reads `["TWO"]` under `a2`.
- **`accepts a LOWER revision for a collection-wide pin, and records coverage that stops the
  re-fetch`** — the arm's case, both halves. Pin 9, peer serves rev 2 in `[2, 3)`. Asserts the read
  succeeds and is labelled `{rev: 2, actionId: 'low2'}`, that ranges become `[[2, 10], [20]]`, and
  that a second read at rev 9 makes **no** second fetch.
- **`a correct restore at the pin itself still succeeds and still merges its range`** — the
  no-regression case (ticket TODO's last test). Also covered incidentally by four pre-existing
  restore tests whose exact range assertions (`[[1, 2]]`, `[[2, 3], [10]]`) are unchanged.
- **`refuses an archive whose declared range disagrees with the revisions it carries`** — three
  sub-cases (floor below the revisions carried, end at/below the highest, open-ended), then asserts
  no revision record and no transform landed.
- **`refuses a malformed archive`** — five sub-cases: another block's id, a non-numeric revision
  key, an entry with no action, an entry whose `action.rev` contradicts its key, and an empty
  archive.
- **`never overwrites content this node already holds`** (3 tests) — node restores rev 5 into a
  lower range first, then a rev-3 archive also restates rev 5: under a different action id
  (refused), with different bytes under the same action id (refused), byte-identical (accepted,
  ranges merge to `[[3, 6], [10]]`). Both refusals additionally assert that rev 3 — the entry this
  node genuinely lacked — did **not** land, which is what pins "all-or-nothing" rather than
  "skip the conflicting entry".

## Known gaps — treat these as the starting point

- **`saveRestored`'s trust contract is documented, not enforced.** A third caller that hands it a
  network-sourced archive without vetting would reintroduce exactly this bug. Making it structural
  (a required discriminator parameter, or splitting the writer behind two named entry points) was
  considered and skipped as churn for two call sites; a reviewer may reasonably disagree, and this
  is the single highest-value place to push back.
- **The stickiness tradeoff in decision 2 is a judgement call, not a proof.** It is written up at
  the code site with a revisit condition, but a reviewer who thinks a bounded re-verification (say,
  re-fetching a restored span once on a later pin) is worth the round trips should say so — the
  guard is the right place for it and nothing in the current shape blocks it.
- **`RestorationCoordinator` still verifies nothing** (`restoration-coordinator.ts:144-159` returns
  `response.archive` straight through), and this ticket did not change that. The check now lives one
  layer down, at the consumer. That is deliberate — `BlockStorage` is the layer that knows what it
  holds and what it asked for — but it means a peer's lie is caught at write time, never at fetch
  time, so the round trip is still spent.
- **No test drives a refusal through a real `RestorationCoordinator` or the sync protocol.** All 8
  new tests inject a `restoreCallback` directly. That is how every existing restore test in the file
  works, and the wire shape is pinned separately in `block-archive-proof.spec.ts`, but nothing
  end-to-end proves the two agree about `range`.
- **The conflict guard costs up to three raw-storage reads per revision entry.** Restore-path only,
  which has already paid for a network round trip. Recorded as a `NOTE:` on `noDivergentRewrite`
  with the cheap optimisation (check `getRevision` first, skip the other two for a revision this
  node does not hold) if it ever matters.
- **`canonicalJson` now has two implementations in the tree.** `ClusterMember` in
  `packages/db-p2p/src/cluster/cluster-repo.ts:735` still carries a private static copy, which
  contradicts `canonical-json.ts`'s own "import this rather than re-deriving it". Deduplicating it
  is now a one-line change but is **out of scope here and was not done** — it touches cluster
  agreement hashes, which is not this ticket's blast radius.

## Review focus

1. Is `lowest ≤ pin` the right admission rule, or should it be `highest ≤ pin` as well? An archive
   carrying revisions *above* the pin is currently accepted (the pre-existing `ck-staleread` test
   restores `{2, 3, 4}` at a pin of 3 and depends on it), and those upper entries are written. They
   are covered by the conflict guard but not by the pin rule.
2. Decision 2 — the pin-extended coverage. It is the one place this code believes something it
   cannot check.
3. Whether refusing the whole archive on a single conflicting entry is right, or whether landing the
   non-conflicting entries would be better in practice for a partially-diverged peer.
