# A refresh after a refused write asks for a tail no older than the revision it was told about

## What changed

A write refused with `StaleFailure.staleAt = { blockId, rev }` used to refresh by reading the collection header and log tail unpinned from whichever coordinator answered first. A coordinator behind the rival answered the tail at the revision the writer already held, the refresh moved nowhere, and after two rounds `Collection.syncAttempts` threw `SyncRevisionStalledError` — even when a machine one hop away held the revision. Every commit touches the log tail block, so the refused revision is a lower bound (a floor) for the tail read.

- **Collection.** `syncAttempts` passes `lastStaleAt?.rev` into the refresh between attempts (`updateInternal(report, lastChance, tailFloor)`). `refreshInFlight` takes the same optional third argument; `TransactionCoordinator.commit` passes none (its loop loses the number — backlog `debt-multi-collection-retry-cannot-see-the-taken-revision`). `readLogEnds` puts the floor on whichever request reads the tail (the batched header-and-tail read, or `readLogTail` when the header names a different tail) via `tailFloorField`; the header never carries one. The floor lasts one refresh and is never raised into the handle's `BlockFloors` (roll-over argument in the `readLogEnds` doc). When the tail still comes back below the floor, `reportTailBelowFloor` logs `collection:tail-below-floor id=… tag=… floorRev=… servedRev=…`, judged by `servedRevision` and only for a block-carrying answer (the same rule `NetworkTransactor.get` uses). Behaviour after that is unchanged: the stall check still decides.
- **NetworkTransactor.** Both `processBatches` calls in `get` now go through one `askRepo`, which sends `downstreamGets(batch.payload, blockGets)`: `{ blockIds, context }` plus `floors` narrowed to the batch's ids, with the key omitted when the batch has none. The reader-side below-floor check and the retry against a different coordinator are untouched. db-p2p does not read the field yet — that is the companion ticket `a-coordinator-told-of-a-newer-revision-consults-past-its-window` (implement/, sequence 5.5).
- **Docs.** `BlockGets.floors` doc rewritten (on the wire, per batch; old peers ignore it). `docs/internals.md`: the "floor also rides out on the read" paragraph and the Key Invariants "asker's floor" bullet no longer say the floor stays in the process; a new paragraph, "A refresh that follows a refused write puts a floor on its read of the log tail", covers where the floor comes from, why it lasts one refresh, why the header carries none, and where partition healing takes over. `docs/transactions.md` § Below-floor answers: "Nothing new goes on the wire" became "One optional field goes on the wire", and the window paragraph and the cost bullet were updated to match. `docs/debugging.md`: the new line is in the collection namespace row, and the sync-stalled section explains how to read it next to a strike.

## Tests

- `network-transactor.spec.ts` › `a below-floor answer` › `on the wire` replaces the old "never reaches a repo" case with two cases:
  - "forwards each batch the floors of its own blocks, in both rounds": the first round and the retry each carry `floors` narrowed to the batch. A floor for a block outside the batch is dropped.
  - "leaves the field off entirely when no block in the batch has a floor": the request has exactly the keys `blockIds` and `context`.
- `refresh-below-floor.spec.ts` › `a refresh after a write refused for a newer revision`. The double's first replica is now behind on the log too (`lagsLog`):
  - "asks the machine that holds the confirmed revision, and the write lands on the next attempt": the first thing re-asked is the current log tail, the write commits at the rival's revision + 1, no tail-below-floor line is logged, and both rows are in storage. **Verified as the reproduction:** with `lastStaleAt?.rev` removed from the `syncAttempts` call, this case fails with `SyncRevisionStalledError`.
  - "still stalls when no machine holds it, and says every stalled refresh asked for it": with `secondLagAt` set, both replicas are behind. The sync throws `SyncRevisionStalledError`, and the log has one `collection:tail-below-floor` line (floorRev = rival's revision, servedRev = one below) per `collection:sync-stalled` strike (2), with the second replica asked each time.
- Test doubles widened, with the defaults unchanged: `LaggingDataTransactor.lagsLog` (and `laggedReads`' asked revision may now be `undefined` for an unpinned read), and `TwoReplicaTransactor.secondLagAt`.

## Known gaps / things to check

- **Only checked by reading the code, not by a test:**
  - The tail rolls over between the held and the refused revision. A current machine answers the old tail below the floor, which costs one wasted retry round. The header then names the new tail, which is read with the same floor. This is recorded as a `NOTE:` in `readLogEnds`.
  - An older-build coordinator ignores the field.
  - Concurrent unpinned reads through the handle's own source are unaffected.
- **Not tested end to end over the real `NetworkTransactor`.** The collection-level cases run through the `TwoReplicaTransactor` double. The transactor side is pinned only by its wire-shape cases, and no mesh test drives a refused write past a lagging coordinator. A real-network version would sensibly come with the companion ticket, once coordinators act on the floor.
- **An absent tail answer under a floor is not reported.** `reportTailBelowFloor` judges only block-carrying answers, to stay consistent with the transactor. Decide whether an authoritatively-absent tail (named by the header) deserves the line too.
- **The floor is the highest confirmed revision seen so far in this sync.** It is `lastStaleAt`, which persists across refreshes until a success resets it. That is correct because a confirmed revision never becomes free, but it means the floor can come from an earlier round than the current one.
- **Existing stall tests now log the new line.** The `collection.spec.ts` "stalled revision view" cases use a made-up `staleAt` rev 42 that the tail never reaches, so on runs with the namespace enabled they now also emit `collection:tail-below-floor`. That is harmless because they count only `sync-stalled` lines.
- **Check one claim in `docs/debugging.md`.** It says a strike *without* the new line means the tail met the floor and the walk fell short, pointing at `collection:context-short-of-tail`. That reasoning comes from reading the code; confirm it holds.
