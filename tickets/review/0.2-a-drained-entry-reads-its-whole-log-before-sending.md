GitHub #53 reported the cost of offline commits; this is the one term that grew with the collection's total history.

## What changed

`Collection.updateInternal` now takes the early exit (`Collection.tailShowsNothingNewer`) when a write is in flight but **no attempt is retained**: `(inFlightActionId === undefined || inFlightAttempt === undefined) && tailShowsNothingNewer(...)`. The opening refresh of `Collection.commitHead` and `TransactionCoordinator.commitEntry` therefore costs one read request instead of a walk back to the first log block. A refresh with a retained attempt (a failed attempt, or `resume` on a re-drive) still walks.

Also corrected: the comment above that condition, the coordinator comment that said the mark disables the shortcut for committed siblings (it now does so only if an earlier attempt of the cycle was retained), and `docs/internals.md`.

## For the reviewer to check

- The safety rests on the contract on `Collection.retainInFlightAttempt`: a path that could have landed an entry retains before the next refresh. Retention sites: `Collection.syncAttempts`, the handle's `refused` step, `commitOnceLatched`'s failure branch, `openHeadCommit`'s `resume`. Existing specs covering them: `coordinator-own-action-replay.spec.ts`, `own-entry-completes-the-action.spec.ts`, `offline-restore.spec.ts`, `collection-segments.spec.ts`.
- By inspection only, not by a new test: a send that THROWS retains nothing in the cycle. The throw leaves the cycle, and the queue re-drives with `resume` from `OfflineQueue.recordAttempts`. In `commitOnceLatched`, a throw from `coordinateTransaction` also retains nothing (its catch restores the snapshots and rethrows); its comment says nothing landed. If an entry had landed, the tail test still refuses the shortcut unless the tail read is behind, in which case the old walk, seeded with that same tail, would not have found it either. Worth a second look.
- A reader's refresh while a head commit has the latch released and no attempt is retained can now take the shortcut. If the commit has landed, the tail shows it and the refresh walks into the `headInFlight` deferral as before.
- The early exit does not call `keepLogEnds`, so an opening refresh no longer seeds the handle's cache with the header and tail. Its reasoning (the comment on `keepLogEnds`) is that the cache is already warm when the log has not moved; reads/txn stayed flat in the bench, but an LRU eviction would cost a fetch here.
