## What was built

**Plan time** (`rangeSeekCandidate` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`). For each non-partial index, after `matchEqualitySeek` has found the one-key equality run on the leading columns (possibly none), the key column after that run is the range column. It qualifies when it passes the walk's column rule (`bytesOrderAsValues` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts`: TEXT, not compared by meaning, BINARY on both the table and index column), carries no `=` or `in` filter, and carries a bound. The candidate claims the first lower-role filter and the first upper-role filter on the column and nothing else, because those are the two the engine consumes as seek bounds for a handled column whether or not they were claimed (`findLower` and `findUpper` in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`); a further bound on the same side stays a residual. If either first bound is not claimable (unusable, a runtime set, or a plan-time literal of another type than a string) the whole range on that column is declined. It reports `indexName`, `seekColumnIndexes` of the prefix columns followed by the range column, `rows = max(1, floor(tableRowCount × prefixSelectivity × 0.25^bounds))` and `cost = seekCost + rows`, and delivers an ordering under `walkDelivering`'s rules with `reverse` on its descriptor. An index this instance does not maintain is skipped, as for a walk. The primary-key range branch now reads the same `RANGE_BOUND_SELECTIVITY` constant.

**Read time** (`rangeSeekOf`, `indexRangeScanOf`, `indexRangeScan`). `runQuery`'s secondary-index arm routes `plan=3` and `plan=7` to `indexRangeScanOf` instead of treating the args as a key to seek. `rangeSeekOf` reads the prefix values, the range column and the bounds off `FilterInfo.constraints` and `args`, with `prefixLen` through `decodeIdxStr`, and refuses any other shape as malformed (`StatusCode.INTERNAL`). The prefix is framed through `indexSeekKey` under the same NULL rule as an equality seek. `indexRangeScan` builds one `KeyRange` from the bound table in the ticket (lower keys inclusive, upper exclusive, `> x` as `f(x) + KEY_PREFIX_END`, no lower as `P + KEY_PRESENT_START`), swapped for a backward walk, and a row test for any bound the tree cannot apply. A NULL bound yields no range: nothing is sought, `seek=unset`. The row test runs in `verifiedIndexRows` after `rowImpliesEntry`; a failing row counts in `rejected`. The range's rows go through `inEngineOrder` as a walk's do.

**Trace.** `index:seek` prints a range as `low:high`, each key through `printableSeekKey`; an equality seek and a walk print as before, so no other spec's `seek=` assertion changed. The probe's `keys` field became `sought`, a list of either a prefix or a key pair, rendered by `printableSeekTrace`.

**Docs.** README (what ranges seek, what still scans), `docs/internals.md` (new section "A range predicate seeks a secondary index": the claim rule, the bound table, the three kinds of bound), `docs/debugging.md` (the `low:high` form, the third cause of `rejected=`). `yarn lint:docs` resolves.

## Use cases to exercise

- `where T > ? order by T desc limit 100` over an index on `(T)`: one backward range seek, `INDEXSEEK … DESC`, no `SORT`; the `index:seek` line shows `dir=desc seek=%02<bound>%00%03:%03`.
- `where a = ? and t > ? order by t desc limit 10` over `(a, t)`: `plan=7`, both keys carry the framed prefix.
- `t between 'a' and 'b'`: both halves claimed, no `FILTER` above the seek.
- `t > ? and t > ?`: the first is the seek bound, the second a `FILTER`.
- `t collate nocase > ?` over a BINARY index: the engine declines to `SEQSCAN` plus `FILTER`; rows are right.
- `u < ?` on a nullable column: no NULL-keyed row comes back.
- A bound holding an emoji or a character at or above U+E000: the tree end on that side is open (`%02` or `%03`) and the rows are tested one by one; the order and the set match a memory table.

## Known gaps and judgement calls

- **The non-string bound branch is unreachable through SQL.** Quereus types a parameter from the value first bound to it and plans a mixed-type comparison as `cast(t as numeric) > 5`, which is not a constraint, so a number never reaches this module as a bound; re-binding a prepared statement to another type is refused by `validateParameterTypes`. The branch is kept as the ticket designed it, documented as dormant in `docs/internals.md`, and pinned only at the function level. A reviewer may judge it dead weight; the cost is one `typeof` per bound at scan start.
- **`rejected=` now counts a row-test failure**, as the ticket asked, so the field no longer means "the index and the table disagreed" on its own. The doc and the probe comment carry the third cause; the alternative of a separate counter was not taken.
- **The equality check on the range column is by operator** (`=` or `IN` on the column, whatever its usability or shape) rather than the ticket's `firstEqualityRoleFilter`, because the engine's own equality-arm test (`eqBySeekCol` and `findPrefixEq`) is by operator, and that arm seeking on an unclaimed filter is the hazard. It only ever declines more.
- **"0.25 per bound" was read multiplicatively**: two bounds estimate a sixteenth of the prefix's rows. The memory module publishes no range selectivity to mirror. If the reviewer prefers a flat quarter, `rangeSeekCandidate` and one planner assertion change.
- **Not measured.** No timing was taken; the walk ticket's figures and method apply, and `a-long-index-walk-finishes-by-scanning-the-table` is the ticket that measures.
- **Verified by inspection only**: the committed arm (the range runs in the same synchronous view-building block as a walk), a stale entry (same loop, `rowImpliesEntry` before the row test), and `a in (x, y) and t > z` at the SQL level (the planner-level case is pinned).
- **Not in scope**: a range on the primary key, a range on a numeric column, a range under a non-BINARY collation served by this module (`honorsCollatedRangeBounds` stays unset), and an `or`-range (`plan=6`).
