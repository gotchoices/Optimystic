# A store keeps commit proofs by message hash — review

First half of GitHub #60 (a commit proof is stored once per block it covers; a bulk import grew a file store to 7 GB, 94% duplicate proofs). This change adds a seventh logical block-storage store, **commit proofs**, to every backend and every driver layer. `a-commit-proof-is-stored-once-not-once-per-block` (in `implement/`) makes the kernel use it.

## What was built

The store holds one encoded `BlockCommitProof` per consensus message, keyed by the proof's `messageHash` (base58btc, from `computeClusterMessageHash`). Plain get and put, no delete, for the reason the per-revision proofs store has none.

- **Driver surface:** `RawStoreDriver.getCommitProof(messageHash)` / `putCommitProof(messageHash, value)`.
- **Batch key:** `StoreKey` gains `{ store: 'commitProofs'; messageHash: string }`. This is the only variant with no `blockId`.
- **`canonicalStoreKey`:** returns `commitProofs/<hash>`. Every canonical string starts with its store's name and a `/`, and store names contain no `/`, so no other key can produce this string.
- **`decodeStoreKey`** (journal record codec): restructured to switch on `store` first, then check the fields that store has. It used to require `blockId` before reading `store`. A key that matches no shape is still refused.
- **`IRawStorage.getCommitProof` / `saveCommitProof`:** raw access with no logic. `KvRawStorage` implements them by decoding and encoding over the driver. `RawStorageDriverAdapter` re-encodes across the byte boundary.
- **Pass-throughs:** `CachedStoreDriver` passes both methods through uncached, under the proofs store's `NOTE:`. `WriteGroupDriver` routes them through the overlay and batch like every other store.

### Per backend

- **Memory:** `MemoryStoreDriver` has one more map. `MemoryBatchBackend`, `MemoryJournalStore` and `TextReadsJournalStore` needed no change, because they key on `canonicalStoreKey`.
- **File (`FileBatchBackend`):**
  - Proofs go in a root directory, `commit-proofs/<messageHash>.json`, and are read with the corrupt-content-as-missing guard.
  - `listBlockIds` skips the directory at the root, beside the KV namespaces (`ROOT_NON_BLOCK_DIRS`). The `NOTE:` at `COMMIT_PROOFS_DIR` records the accepted limit: a block whose id is `commit-proofs` or starts with `commit-proofs/` is hidden from the listing.
  - **Deviation from the ticket:** the file name percent-encodes every character outside `[A-Za-z0-9_-]` (`commitProofRelativePath`). A base58 hash passes through unchanged, so real files are named by the bare hash. See *Decisions* below.
  - A comment on the path function covers case-insensitive filesystems.
- **SQLite:** new table `commit_proofs (message_hash TEXT PRIMARY KEY, value BLOB NOT NULL)` in `SCHEMA_SQL`. `TableLayout` gained a `table` field, because table names used to be the store names and this one is snake_case. Get, put and the batch apply all come from `LAYOUTS`. An existing database file gains the table on its next open (`CREATE TABLE IF NOT EXISTS`).
- **IndexedDB:**
  - New `commitProofs` object store, created in `upgrade` when it is missing.
  - `DEFAULT_DB_VERSION` is now 4, with the comment extended.
  - Added to `APPLY_STORES`. `idbKeyOf` returns the hash string.
  - `isStoreKey` was restructured to switch on `store` first.
  - The untested-upgrade debt (backlog `debt-indexeddb-version-upgrade-is-untested-and-unhandled`, which already has a version-4 section) applies unchanged.
- **LevelDB:**
  - `TAG_COMMIT_PROOFS = 0x08`; the key is the tag byte followed by the hash's UTF-8, with no block envelope. Documented in the `keys.ts` header.
  - Confirmed that no listing reaches tag `0x08`. The journal's range is `[0x07, 0x08)`, metadata's is `[0x01, 0x02)`, the per-block scans stay inside their own envelope, and the KV store starts at `0x10`. Only `approximateBytesUsed`, which sums the whole database, counts these keys.

### Test doubles updated for the wider interfaces

`CrashingRawStorage` (`mid-ddl-crash.spec.ts`), the `StorageMonitor` stub, `GatedStoreDriver`, `FaultyStoreDriver`, `CountingStoreDriver`, and `LaggingRawStorage` in the plugin's lagging-replica spec. In that spec, commit proofs pass through the veil, since they are not scoped to a block. The read and write method lists in `cold-apply-cost.spec.ts` now include the two new methods; they count zero today.

## Decisions to check

- **The file backend encodes the hash rather than trusting it.** The ticket says a base58 hash is filename-safe and stops there. The store is keyed by any string, though, and a key like `../x` would otherwise name a path outside `commit-proofs/`.
  - I first tried a base58 check in `KvRawStorage`. I dropped it for two reasons. First, the follow-on ticket's fixtures (`makeProof` gives `hash-<marker>`) are not base58, so once it routes `saveBlockProof` through this store, every existing proof test would have thrown. Second, a check inside the file backend only fires at flush time, and a failed flush latches the whole store.
  - The encoding follows the existing colon-encoding of action ids. It is injective because `%` is itself encoded.
  - A one-off probe (not committed) confirmed that `../escape` lands at `commit-proofs/%2E%2E%2Fescape.json` and that `%2E%2E%2Fescape` gets a separate file.
- **The latch.** Invariant 2 in `packages/db-p2p/docs/storage.md` says a block's records are written under that block's write latch. The commit proofs store is not filed under any block. I added a sentence saying it has no writer yet and that the change giving it one must state which latch that writer holds. The follow-on ticket expects to call it from under different blocks' latches, joined through a memo.
- **Downgrade.** An older build that finds a journal record holding the new key discards the record as undecodable (a gap). An older build asking for IndexedDB version 3 is refused by a version-4 database. Both are downgrades, which are not supported.

## Tests (what each verifies)

All in the shared conformance suite (`packages/db-p2p/src/testing/raw-storage-conformance.ts`), which runs against every backend (memory, file, SQLite, LevelDB, IndexedDB) and every cached, write-group, journal and text composition:

- `getCommitProof returns undefined on a miss`.
- `commit proof round-trips under its message hash, and distinct keys stay distinct`. Covers a base58 key, a key with path characters, and that key's own percent-encoded spelling. On the file backend this pins the encoding: without `%` in the encoded set, the last two keys would share a file.
- `a commit proof under hash X and the proof for a revision of block X do not see each other`. Keyspace isolation, following the `~proof:<N>` precedent.
- The persistent-backend flush/reopen case gained one write and one read of a commit proof. This is how the file, SQLite, LevelDB and IndexedDB stores are shown to persist across a reopen.
- `journal record codec` round-trip (`packages/db-p2p/test/journal-batch-backend.spec.ts`) gained a `commitProofs` entry. This is the only place `decodeStoreKey` runs on the new key: every conformance flush is strict, and the memory journal store never byte-encodes a record. So the ticket's claim that "the conformance suite running through a write group over the journal backends" covers decoding did not hold.
- `IndexedDB sync by the window` expected store list (`DATA_AND_JOURNAL`) gained `commitProofs`, because the strict apply now spans it.
