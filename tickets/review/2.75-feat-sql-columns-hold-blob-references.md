# SQL columns hold blob references — the holding period, built

Last of the four parts that build the SQL side of blobs. What landed closes the one pin no transaction ever answered for: a `put` made outside any transaction is pinned `sql-unstaged/<putAtMs>`, and only an online commit that stages the reference ever dropped one — so a cancelled upload, a failed insert or a stopped process kept those bytes for ever. docs/blobs.md §SQL promised a holding period; this builds it, and flips the status lines now that all four parts are in.

## What was built

**`parseUnstagedHoldingMs` and `DEFAULT_UNSTAGED_HOLDING_MS`** in `blob-pins.ts`. Read in `register` beside `moduleCostProfile`, so a bad value throws before anything is built. Default `86_400_000`.

**`SqlBlobPins.sweepUnstaged(now?)`**, chained like `settleQueued` and `reconcile` — so it waits for any open transaction to end and never runs beside the other two. Per known backend: collect every `unstaged` pin past `putAtMs + holdingMs`, then release each one whose reference no unfinished transaction is relying on, logging `blob:unstaged-expired ref=… putAt=…`.

**The protected set**, in two halves:

- every reference carrying a reference pin whose transaction `isLive` answers for — the open transaction once its commit has started, and every QUEUED transaction, whose pins stay until the queue finishes with it;
- `TransactionBridge.openBlobReferences()` — the fold `addedReferences` takes over the OPEN transaction's ledger, which is the only record of a reference a statement has staged and whose commit has not yet pinned.

**The timer**: one `unrefTimer(setInterval(...))` per `SqlBlobPins`, armed by the first blob backend to resolve (and a sweep run at each resolution), period `max(60s, min(holdingMs/4, 1h))`, cleared by `dispose()` before it awaits the chain.

**Docs**: the status line in docs/blobs.md (SQL built in all four parts; what remains in the blob work is reclaiming), both §SQL bullets, the holding-period and protected-set prose finishing `docs/internals.md` §A table's blob references, the two new log lines in docs/debugging.md, and the README's config row plus its blob bullets.

## Where I departed from the ticket — read these first

**The second test is the QUEUED case, not the open-transaction case the ticket specified.** The ticket asked for: `begin`; insert the second reference; `sweepUnstaged(expired)`; `commit`; assert the second survived. That test cannot observe what it claims to. `sweepUnstaged` is chained, and a chained step first awaits `whenTransactionIdle()`, so the sweep does not run while the explicit transaction is open — it runs after the `commit`, by which time the commit's own `committed()` arm has dropped that `unstaged` pin for its own reasons. The assertion would pass with the protection deleted. So the protection is driven instead through a **queued** transaction, which is `isLive` for as long as it sits in the queue with no SQL transaction open: a deterministic case that exercises the reference-pin half of the protected set and the handoff from the `unstaged` pin to the announcement's `owed` hold. The ledger half (`openBlobReferences`) is inspection, for the same reason no spec can see a sweep inside an open transaction. **If the reviewer can see a way to drive the ledger half deterministically, that is the gap worth closing.**

**The ledger half is read per expiring pin, not folded into one up-front set.** The ticket's step 1 builds both halves before the listing. Doing that leaves a real byte-loss window: the chain's idle wait covers the transaction open when the step STARTS and says nothing about the next one, so a statement can begin behind a running pass, stage a reference, and have its `unstaged` pin expired before its commit writes a reference pin — the bytes then go with the piece sweep and the committed row references a blob this machine no longer holds. `openReferences()` is synchronous and in-memory, so asking it immediately before each `unpin` closes almost all of that at no measurable cost, and only a pin that is otherwise expiring pays the call. The residual instant between that read and the `unpin` is parked as a `NOTE:` at `sweepUnstaged`.

**The sweep collects before it releases.** `listExpiringUnstaged` walks the listing into an array and the releases happen after it, following `listStalePins` rather than unpinning inside an open iteration of the same store. This also makes the live-pin listing lazy: a sweep that finds nothing expiring — the steady state — pays one listing of the machine's blob records instead of two.

**`parseUnstagedHoldingMs` treats `''` and `null` as unset** rather than throwing, following `cost_profile`'s `isUnset` (a plugin loader's settings form sends an empty field as `''`). Everything else that is not a finite positive number throws, which is what the ticket and the README promise.

**The holding period and the clock ride on `SqlBlobPinsDeps`** (`unstagedHoldingMs`, `now()`, `openReferences()`) — the ticket said to pass the period to `SqlBlobPins` without saying how, and the deps object already mixes a non-function member (`registration`).

**A second log line, `blob:unstaged-unreadable ref=… owner=…`**, for an `unstaged` label whose time this build cannot read. The ticket specified the log-once behaviour but named no line; this one is documented in docs/debugging.md beside `blob:unstaged-expired`.

**The status line's "still to be built" list is shorter than the ticket's.** The ticket said to keep the cached-copy budget and `feat-blob-reads-say-whether-a-cohort-confirmed-them` on that list; both landed since the ticket was written (`2.81` and `2.82`, per `tickets/.garden-report.md`). The line now names only reclaiming (`2.85`, `2.86`, both in `implement/`). Worth a second pair of eyes — a status line that over-claims is the worst kind of doc bug.

## Tests

`packages/quereus-plugin-optimystic/test/blob-pins-unstaged.spec.ts`, over `blob-pins-harness.ts`. Every sweep is driven by hand with an explicit `now`, so nothing waits on the plugin's own hour-long interval.

- *keeps the pin up to the holding period and releases it past it* — the boundary rule. A put outside any transaction, its `putAtMs` read back through `parsePinLabel`; `sweepUnstaged(putAt + holding - 1)` leaves the pin, `sweepUnstaged(putAt + holding + 1)` releases it and leaves no `unstaged` pin on the machine.
- *never expires the pin of a reference a queued transaction is still relying on* — the protection. Two puts outside any transaction, one of them referenced by an insert that is sealed into the queue behind a closed gate; one sweep past the period releases the abandoned put's pin and keeps the referenced one. Then the queue drains, the reference is announced and its reference pin goes; the next sweep releases the now-unprotected `unstaged` pin, and `stat` still reports durability `local` — the bytes the protection kept are the ones the commit announced.
- *parseUnstagedHoldingMs: …* — three cases, one per branch (default for the unset trio, a declared number, the refusal), following `cost-profile.spec.ts`'s precedent for a config parse whose refusal is load-bearing.

By inspection, as the ticket directs: the queued-transaction reference-pin arm beyond the above (same code the open case falls through to), a put inside a transaction the transaction never references (labelled `sql/<stampId>/put`, so this sweep never sees it), an unreadable `unstaged` label, a clock moved backwards, a host that never resolves a blob backend, `dispose()` mid-sweep, and two backends under one timer.

## What a reviewer should check

- **The chain.** `sweepUnstaged` on the same chain as `settleQueued` and `reconcile` is what keeps three passes from fighting over one blob's pins. Satisfy yourself that nothing in the sweep awaits the chain (it would deadlock) and that `dispose()` cannot leave the interval running.
- **`openBlobReferences`'s `isActive` guard.** `currentTransaction` outlives its transaction on the bridge (only `cleanup()` nulls it), so without that guard the last transaction's references would be protected for ever. Check the guard matches what `plugin.ts`'s `isLive` asks.
- **The two `NOTE:` tripwires** in `blob-pins.ts`: the per-pass listing of every blob record with no `mayHoldStalePins`-style gate (at `listExpiringUnstaged`), and the residual window between the `openReferences()` read and the `unpin` (at `sweepUnstaged`). Both are "fine now, here is the condition and the remedy"; neither is filed as a ticket.
- **The doc pass is wider than the code pass**, and it declares a four-part feature built. The §SQL "A put outside a transaction" and "Pins follow the transaction" bullets, the internals prose, the README config row and the README blob bullets all now claim things; read them against the code, not against each other.
- The `README` blob bullet now says plainly that `plugin.blobs` does not hold every blob it ever put, and that a queued commit is not a backup of a file. Both are the kind of claim a host will act on.
