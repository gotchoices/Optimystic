# Review: the hybrid logical clock and its persistence port

First of the three Stage 1 tickets of docs/crdt-sync.md §Migration Path. The other two, `every-log-entry-and-transaction-carries-its-hlc` and `a-node-observes-the-hlcs-it-reads-and-stores`, are in `implement/` and build on exactly what landed here. Nothing in this ticket stamps, orders, admits or refuses anything.

## What landed

- **`packages/db-core/src/hlc/hlc.ts`** — `Hlc` (`wallMs`, `logical`, `nodeId`, plain JSON), `compareHlc` (wallMs, then logical, then nodeId by plain code-unit comparison), `legacyHlc(timestamp)` = `{ wallMs: timestamp, logical: 0, nodeId: '' }`, and `isHlc` (two finite numbers and a string node id; nothing more).
- **`packages/db-core/src/hlc/clock-store.ts`** — the port `HlcClockStore { load(); save(hlc) }`, `DEFAULT_HLC_PERSIST_INTERVAL_MS` (1000), `DEFAULT_HLC_RESTART_SLACK_MS` (10 000) with its derivation, and `restartFloor(stored, slackMs, nodeId)`.
- **`packages/db-core/src/hlc/clock.ts`** — `HlcClock` and `clockOf`.
  - `new HlcClock({ nodeId, localClock? })` is purely in memory. A store-backed clock exists only through the async factory `HlcClock.start({ nodeId, localClock?, store, persistIntervalMs?, restartSlackMs? })`, which loads the mark before returning, so "a store-backed clock that issued before loading its mark" cannot be constructed. That is why the constructor takes no store, a deliberate narrowing of the ticket's `{ nodeId, localClock?, store? }`.
  - `now()`: `wallMs = max(local, last.wallMs)`, `logical = last.logical + 1` when wallMs did not move, else 0, own nodeId.
  - `observe(hlc)`: raises `last` (a copy) when `compareHlc` says it is above; ignores a value failing `isHlc`, silently (the wire-side caller in the third ticket reports it).
  - Restart: `start` treats `restartFloor(stored)` as an observed HLC, so a local clock already past it simply wins. Consequence: the first HLC after a floored restart is `{ floor, 1 }`, not `{ floor, 0 }`.
  - Saves (`MarkPersistence`, private): after any `now`/`observe` that moved `wallMs`, save when the new `wallMs` is ≥ `persistIntervalMs` above the last mark handed to the store (before the first save, the loaded mark; with nothing loaded, the first advance saves). Fire-and-forget, one in flight, a newer mark replaces a queued one, a rejection (or a synchronous throw from the binding) is logged as `hlc:save-failed` on `optimystic:db-core:hlc` and never reaches the caller. A `load` that rejects or returns a malformed value logs `hlc:load-failed` / `hlc:load-malformed` and the clock starts from the local clock alone, still attached to the store.
  - `clockOf(transactor)` returns `transactor.clock` or one lazily built process-wide fallback clock, node id `'local'`, no store. That module-level variable is commented as the one place a second clock instance can exist.
- **`ITransactor.clock?: HlcClock`** (`packages/db-core/src/transactor/transactor.ts`); `NetworkTransactorInit.clock` carried to `NetworkTransactor.clock`; `TestTransactor` takes `TestTransactorOptions { clock? }` and defaults to `new HlcClock({ nodeId: 'test' })`; `DelegatingTransactor` forwards it with a getter. The reference peer's `LocalTransactor` and the plugin's `local`/`test` transactors are untouched and fall back through `clockOf`.
- Exported from the db-core root through a new `hlc/index.ts` barrel; the modules import siblings directly (barrel-cycle guard passes).
- `docs/crdt-sync.md` §HLC Generation and Causal Tracking names `HlcClock`, `clockOf`, `HlcClockStore` and `restartFloor`. §Stage 1 is left for the third ticket.

## The restart slack, as asked

Confirmed against packages/db-p2p/docs/storage.md §6: the longest a db-p2p store may leave a write undurable is the relaxed flush window's cap, `maxWindowMs` (5000 ms default, `DEFAULT_DURABILITY_MAX_WINDOW_MS`); unflushed writes are synced by the write group's idle timer after 1 s. So the durable mark trails what was issued by at most 1000 + 5000 = 6000 ms at the defaults; 10 s was kept, with 4 s margin. The derivation is at the constant, with the remark that a deployment raising `maxWindowMs` past 9 s should raise the slack (`restartSlackMs`). Ticket 3 builds the node's clock with the defaults; deriving the slack from the node's resolved durability policy there is a reasonable alternative if the reviewer prefers.

## Known gaps, flagged honestly

- **A lost jump.** Recorded as a `NOTE:` tripwire at `DEFAULT_HLC_RESTART_SLACK_MS`: the slack covers an unsaved stretch only while the mark tracked wall time. A jump (an observed far-ahead HLC, or the restart floor itself) is saved at once but never flushed by the clock, so a crash inside the store's durability window loses it, and the next start can issue HLCs at or below ones the lost run issued. In particular a crash loop faster than that window repeats one floor, giving two HLCs from one node with equal `(wallMs, logical)`. Harmless while HLCs are observational; the remedy (a durable save after a jump before issuing past it) is named for when Stage 2 orders by HLC. The ticket's "the clock never flushes" design is otherwise followed. A reviewer may judge this should be fixed now rather than parked; the cheap partial fix would be `start` awaiting the floor save, which still does not make it durable.
- **Debounce keys on the mark handed to the store, not on a confirmed save.** After a rejection the next attempt waits for `wallMs` to move another interval, rather than retrying on every issue against a failing store. Chosen deliberately; the ticket's "the next qualifying advance tries again" reads either way.
- **No shutdown save and no read of `last`.** The clock exposes only `now`, `observe` and `nodeId`. Nothing awaits an in-flight save on stop; the slack covers it.
- **`isHlc` checks shape only**: a finite but absurd `wallMs` (far future, negative) is accepted by `observe`. Bounding it is the skew question the third ticket measures and Stage 2 decides.

## Tests
