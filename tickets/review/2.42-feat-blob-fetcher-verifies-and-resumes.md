# Blob fetcher: verify, resume, schedule — review handoff

`BlobFetcher` is the one code path that receives blob pieces. `feat-blob-pieces-move-between-machines` (plan/2.45) builds `node.blobs.read`, `fetch` and `stat` with `probe` on it; `feat-a-referenced-blob-is-copied-to-its-cohort` uses it at background priority. Nothing in the node calls it yet.

## What was built

- **`BlobFetcher`** (`blob-fetcher.ts`): the public types (`BlobFetchRequest`, `BlobFetchSession`, `PieceStoredEvent`, `BlobFetcherDeps`, re-exported `FetchPriority`), `start`, `onPieceStored` (a throwing listener is logged as `fetch:listener-threw`), `stop` (aborts with `Error('blob fetcher stopped')`, which rejects running sessions and every later start, aborts streams in flight, cancels wait timers, and resolves once each session's work has unwound).
- **`FetchSession`** (`blob-fetch-session.ts`), one per `start`, following the ticket's seven steps: an unheld walk (nothing missing → resolve with no hold, no `findCluster`, no peer, no log); `holdCached` then a second walk whose absent entries are the frontier; rounds whose candidates are recomputed each time (`blobHolderCandidates` minus peers this session caught serving wrong bytes); one batch at a time, the slot acquired before the pieces are chosen; each piece `checkPiece`d with the store's digest, then `storePiece`d; a `BlobCorruptError` penalizes the peer once (`PenaltyReason.InvalidRestoration`, context `blob-piece <id>`), excludes it for the session and abandons the rest of its answer; any other failure of the request marks the peer failed for the round; a walk again only after a batch stored a list piece; a confirming walk before a round ends; classification of the first missing piece with `unavailableOutcome`; `waitMs` backoff (500 ms doubling to 8 s, capped by the time left, reset by any piece arriving); `markWhole` for a session with no range, with the `NOTE:` that nothing is flushed.
- **`PieceTraffic`** (`blob-piece-traffic.ts`): the in-flight map shared by a fetcher's sessions (with the assertion at `claim` and the `NOTE:` about a read waiting on a background batch), and the `stored(id)` waiters.
- **Wiring** (`wireBlobFetcher` in `libp2p-node-base.ts`): one `BlobProtocolClient` and one `BlobFetcher` on both roles, built right after the blob service's stop wrapper, with their own stop wrapper installed at once (so it runs before the blob service stops, and a startup rollback stops it). Kept in the local `_blobTransfer` for the next ticket; not a node attachment.
- **Exports**: `blob-get-slots.js`, `blob-holders.js`, `blob-fetcher.js` from both `index.ts` and `rn.ts` (the session and traffic modules stay internal).
- **Docs**: `docs/blobs.md` (status line; §Holds: the `cached` hold a fetch takes, `BlobFetchStore` as its only way to write, and the fourth sweep race with why a fetched piece notes its blob; §Moving pieces between machines: fetching built, the six steps, the wrong-piece rule, the classification table, resumption, one request per piece, "Other traffic is not held up" as built; §Threats names `PenaltyReason.InvalidRestoration`), `docs/internals.md` (§Network Membership Predicate bullet for the fetcher), `docs/debugging.md` (`blob:fetch` row: every `fetch:` line; the namespace count is unchanged at 66).

## Where it departs from the plan (review these)

- **`digest` lives on `BlobFetchStore`, not on `BlobFetcherDeps`.** The plan suggested having `LocalBlobService` expose the digest "so the two cannot differ"; putting it on the store door the fetcher already takes makes a mismatch unrepresentable rather than merely unlikely. `BlobFetcherDeps.client` is `Pick<BlobProtocolClient, 'get'>`.
- **A presence check after the slot is granted** (`FetchSession.batchFor`). Without it, a session that noted which pieces were in flight, then waited for a slot while another session claimed, stored and released pieces, would request those pieces again (the claim and the settle both happen between its note and its slot). It costs up to 16 local `has` calls per batch; found pieces leave the frontier and count as progress.
- **The in-flight map and the waiters are keyed by piece id alone**, not `(ref, id)`: a piece is named by its content, so one request serves every blob whose tree names it. Sweep safety still holds: each blob's own hold and its present parent protect a child stored under another blob's `storePiece` call.
- **`done` is marked handled internally** (`this.done.catch(...)`), because a reader that follows pieces through `stored` may never await `done`; every failure is still logged and still reaches every waiter. Without it, an unawaited failing session is an unhandled rejection.
- **Extra log lines**: `fetch:failed ref err` for a session ending by anything other than unavailability or corruption (caller's abort, the node stopping, a range past the end, a store fault), and `fetch:corrupt` also carries `reason` (a malformed list piece from the walk reports the same way). Both are in the debugging row.
- **A session's own abort** rejects `done` and its waiters at once, but `run()` unwinds only after a batch already sent finishes (that batch uses the fetcher's stop signal, as the plan specifies). `stop()` waits for that unwinding, so no fetched piece is stored after the node's blob service stops.

## Known gaps and judgment calls

- A peer penalized for one piece is recorded `no-answer` for the rest of its batch in that round, so the classification of a *different* missing piece can come out `peers-unreachable` where it would otherwise be `not-held`. The plan calls this moot; it is visible only when the corrupt peer was the round's last hope for that other piece.
- Classification looks only at the first missing piece in tree order, as specified.
- The frontier is scanned linearly per batch (peer choice, batch choice, dropping what arrived). Recorded as a tripwire `NOTE:` on `Round` (quadratic in the frontier, negligible at tens of megabytes, seconds at tens of gigabytes).
- `blob-fetch-session.ts` is about 600 lines: `FetchSession`, `Round`, `CorruptServers` and four small helpers. Each method is single-purpose; splitting `Round` out was not done.
- Not exercised by a test, by design or for the next ticket: concurrent sessions sharing an in-flight piece (inspection plus the `claim` assertion), `waitMs` (tested end to end by plan/2.45), `stop()` mid-fetch, the "every holder served wrong bytes" row (the classification itself is pinned by `blob-holders.spec.ts`), and the node-wired fetcher (inspection; nothing calls it yet).

## Tests added

`packages/db-p2p/test/blob-fetcher.spec.ts` — three real nodes over loopback TCP, `clusterSize` 3, each with its own piece store; the fetcher under test is built over node B's parts (`node.blobs` narrowed with `instanceof LocalBlobService`).

- *Takes a piece from another holder when one serves wrong bytes, and penalizes it once*: A's piece store flips a byte of the second of three data pieces; B fetches with `knownHolders: [A, C]`. Pins: B's store reads back the exact content through a hashing source, and reputation saw exactly one `InvalidRestoration`, against A. Mutation-checked: with the `checkPiece` call removed the test fails with `BlobCorruptError`.
- *Keeps what an interrupted fetch stored and asks only for the rest*: 500 ms response deadline; A holds an 8-piece blob and holds its `get` of the fifth data piece. The first session stores the list piece and four data pieces, then fails with `BlobUnavailableError` (reason not pinned); the second session's stored pieces are exactly the last four; A served each data piece once and the held one twice; the result reads back exactly. The list piece's `get` count is not asserted because A's own start-up sweep reads list pieces.
