# Review: reactivity per-root state is keyed by the tail; the outgoing root sees the move

Second of three tickets for the stable-tier decision (`cohort-topic-a-topics-root-can-move` → this → `reactivity-topic-is-the-collection-anchor`). The reactivity topic id is still `H(tailId ‖ "reactivity")` after this ticket, so the re-keying changes no behaviour by itself; the one behaviour change is the outgoing-root fix below.

Terms: a collection's **root** is the group of machines that stores its current log tail block and announces its commits. Today one topic has one root; after the next ticket one topic will have a root per tail block, so everything kept per root must be keyed by the tail, not the topic.

## What changed

**Per-root state keyed by the root's tail** (`ReactivityForwarderHost`, `packages/db-p2p/src/reactivity/forwarder-host.ts`). The `served`, `ingestTails` and `rotationGates` maps are keyed by the base64url of the root's tail bytes (= `NotificationV1.tailId`). API changes:

- `ingest(n)` takes the notification only; it derives the root (`n.tailId`) and the topic (`reactivityNotificationTopicId(n)`, the one helper the next ticket switches). An undecodable `tailId` is logged and dropped inside `ingest` (it never rejects).
- `pushStateFor(topicId)` → `pushStateForRoot(tail)`; `markRotated(oldTail, …)`; `rotationRedirectFor(oldTail, …)`.
- `directSubscribers` dependency is `(topicId, rootTail) => string[]`.
- Internal renames: `ServedTopic` → `ServedRoot`, `releaseDrainedTopics` → `releaseDrainedRoots`.
- The `NOTE:` at `served` is extended with the one-round-commit tripwire (a root this node never sees a later tail for is never released; remedy: release a root with no ingest for longer than `T_drain`).

**Node wiring** (`createLibp2pNodeBase`, `packages/db-p2p/src/libp2p-node-base.ts`):

- `directSubscribers` now reads the engine at the root coordinate — `host.registry.findByCoord(reactivityRootCoord(rootTail))`, requiring `engine.rootPlaced` — instead of `findServing(topicId, 0)`. `REACTIVITY_FORWARDER_TREE_TIER` is gone.
- Push-state gossip resolves a frame by `g.tailIdAtJoin` and drops it when the served state's `topicId` differs from the frame's (`servedPushStateForGossip`, shared by the resolve step and the membership gate).
- Recover serve: `pushStateForRoot`; `rotationFor` takes `{ tailId?, collectionId }`; `resolveCurrentServedTopic` → `resolveCurrentServedRoot` (returns the current served `PushState`'s `tailIdAtJoin` bytes).
- `attachCohortChangeBridge` moved below the origination manager it now feeds (`observeTailCommit: (event) => origination.observeTailCommit(event)`). Nothing between the old and new positions read `node.blockChangeNotifier`; the stop wrapper's `unsubscribeCohortBridge` is still undefined-guarded.

**Recover serve deps** (`packages/db-p2p/src/reactivity/recover-transport.ts`): `RecoverServeDeps.pushStateFor` → `pushStateForRoot(tail)`; `rotationFor` takes `tailId`. `serveResumeReply` looks up `latestKnownTailId`'s bytes directly instead of hashing them into a topic.

**Scheduler and watch** (`rotation-rereg-scheduler.ts`, `collection-watch.ts`): the scheduler de-duplicates and cancels by successor tail (`plan.newTailId`, base64url); `cancel(newTailId?)`. The watch's `rotationTargets` map is keyed the same way.

**The outgoing root sees the move** (`ReactivityOriginationManager.observeTailCommit` in `origination-manager.ts`; `CohortTopicChangeNotifierDeps.observeTailCommit` in `change-bridge.ts`):

- The bridge calls the observer for every event that names a tail, ahead of and independently of the `selfAppliedTail` gate, in its own try/catch so a throw never blocks origination.
- The manager keeps, per collection, the tail this node last applied a commit for (`lastAnnouncedTail`). An event naming a different tail fires `markRotated(oldTail → newTail, effectiveAtRevision = event.rev)` and forgets the baseline; an event whose tail this node applied becomes the baseline; a same-tail event this node did not apply leaves the baseline alone. Tail-less events are ignored.
- `detectTailRotation` is removed from the originate path; block-fill tracking stays there (now isolated in `trackBlockFill` itself).
- Why it matters: a machine only in the old tail's group never applies a commit naming the new tail, so it never marked the rotation, never redirected recover requests, and never released the old root's `PushState`. It does apply the rollover's rewrite of the old tail's `nextId`, whose event names the new tail. This is read from the code, not reproduced on a real wide network (see gaps).

**Decided, not built** — the outgoing root telling its direct subscribers of the move — is recorded as a bullet in `docs/reactivity.md` § Tail rotation with its revisit condition.

## Tests

Added (each pins branching the outgoing-root fix rests on):

- `managers.spec.ts` › tail observation › "a machine only in the old tail's group marks the rotation from the rollover rewriting the old tail" — announced at A, then an event naming B whose blocks include A but not B → `markRotated(A → B)`; afterwards no baseline, so a later commit marks nothing.
- `managers.spec.ts` › "keeps its baseline through a commit that names its tail without applying it (a data-block sweep)" — same-tail, not-applied event keeps A, so a later rollover still marks.
- `change-bridge.spec.ts` › "hands the tail observer every event naming a tail, the ones the gate drops included, and no tail-less one" — uses a stub `ChangeBridgeSource` because `StorageRepo.commit` cannot produce a tail-less event.

Adapted (no new cases): `forwarder-host.spec.ts` (root-keyed API), `recover-transport.spec.ts` and `recover-signers.spec.ts` (`pushStateForRoot`, `rotationFor.tailId`), `rotation-rereg-scheduler.spec.ts` (every successor now shares one topic and is distinguished by tail — this pins that dedupe is by tail), `managers.spec.ts` existing observe-rotation cases moved from `onLocalCommit` to `observeTailCommit` and now assert the old **tail** bytes. The old "with markRotated absent, origination is unchanged" case was dropped: rotation detection no longer runs on the originate path, so it tested nothing.

**Integration fixture change — reviewer please check.** Two real-socket cases in `substrate-real-libp2p.integration.spec.ts` ("a commit on a real cohort member delivers a NotificationV1…" and "a remote subscriber resumes past the tail over a real recover socket…") hand-built a FRET-placed tier-0 engine at the reactivity root coordinate and called `handleRegister` on it directly. With the ticket's `engine.rootPlaced` requirement they failed (verified: no notification delivered). Production never builds a FRET-placed reactivity root, so I changed the fixtures, not the requirement: new helpers `rootMemberFor` (the root group member at clusterSize 1) and `registerAtRoot` (a T3 self-vouched `RegisterV1` carrying `rootKey`, dialed to the root member over the real register protocol, which creates a root-placed engine). Those two cases no longer seed FRET willingness (`engines` / `quorumOn`); willingness convergence is still covered by the cohort and matchmaking cases in the same suite. `signedRegister` gained a `rootKey` option. The direct-dial path goes through wire validation, which needs 16-byte correlation ids (`'rx-socket-subscr'`, `'rx-resume-subscr'`).

## Known gaps / things to look at

- **The outgoing-root fix has no real-network test.** It is pinned at the manager and bridge seams only. A real two-tail rotation on a mesh wider than one group stays `it.skip` in the integration spec (pre-existing, for runtime budget).
- **"Last announced" is approximate.** The baseline is set when this node *applied* the tail, even if it announced nothing (e.g. a member that applied with too few signatures to retain a commit certificate). Such a node then marks a rotation and arms a drain gate for a root it may not serve; the gate is swept after `T_drain` and a recover request reaching it during drain gets the correct redirect, so I judged it harmless.
- **One-round commits** can leave an old-group machine outside the new tail's cohort never seeing the rollover; recorded as the tripwire `NOTE:` at `served`, not fixed.
- `ReactivityCollectionWatch.buildManager` has a pre-existing unused `topicId` parameter; left alone because `reactivity-topic-is-the-collection-anchor` rewrites that method.
- The "two roots of one topic on one machine" case is unrepresentable while the topic is tail-derived; the next ticket adds it.
