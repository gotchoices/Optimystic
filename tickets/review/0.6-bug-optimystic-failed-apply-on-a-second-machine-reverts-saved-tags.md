## What changed

Quereus applies a tag change to its own catalog and announces it as `table_modified`. The listener used to overlay every tag of the engine's new schema onto the catalog record, on every such event, so this machine's whole view of the tags overwrote a record that could be newer.

It now saves what the event changed, one tag location (a *slot*) at a time, judged against the record. A slot is the table, or one column, named CHECK, foreign key, non-derived UNIQUE constraint or index.

- `tagChangesBetween` in `tag-overlay.ts` compares the event's old and new schemas. Only a slot both have counts, so an object that merely appeared (such as a CHECK re-added by an unwind) is not a tag change.
- `tagsToSave` in `catalog-only-change.ts` judges each change against the record the save read:
  - the undo of an adopted change is not saved;
  - a slot the record lacks is not saved;
  - a change the record already holds is adopted and not saved;
  - anything else is saved.
- `persistTags` takes a `record => slots` callback, so the decision and the write concern one record, and it writes nothing for an empty result.
- `followTableTags` returns before touching the catalog when the event changed no tags, so `analyze` no longer costs a catalog read.
- `saveTableTags` marks the table `written` in the batch only on outcome `'saved'`. An adopted change therefore cannot lead a failed commit to re-persist this machine's older description.

## Behaviour to validate

Sessions share one `MemoryRawStorage`. A declares `t` with `version = 1`, B hydrates, and A applies `version = 2`.

| Case | B does | Record afterwards |
| --- | --- | --- |
| R1 | applies v2 plus a step the module refuses | `version = 2`; B's own catalog goes back to 1 |
| R2 | `alter table main.t add constraint small check (a < 100)` | `version = 2`, plus `small` |
| R3 | `analyze main.t` | `version = 2` |
| R4 | column tag `k = 2` was set by A; B applies it plus the refused step | `k = 2` |
| R5 | applies v2 plus a new column, commit refused once, then retries | `version = 2` after the refusal and after the retry |
| R6 | B alone applies v2 plus the refused step | `version = 1`, since B's own change is taken back |
| R8 | A re-bodied a CHECK with tags `v = 2`; B applies that plus the refused step | the CHECK keeps `v = 2` |

## Known gaps

- **Verified defect, filed separately:** if an apply's commit and its undo batch's commit are both refused, the retry reports success but leaves the change out of the record. This needs a second batch that stages a write, such as an apply that also creates a table. Tags inherit this by following the adoption rule, and the CHECK arm does the same independently of this fix. A column is expected to as well, but that was only read from the code. Filed as backlog `bug-optimystic-a-retry-after-two-refused-commits-leaves-the-change-out-of-the-record`, and cited from the `NOTE:` on `adoptedByRefusedBatch`.
- **Accepted by the ticket:** a failed tag save is no longer repaired by the next DDL. It stays out of the record until the next change to that slot, or until `apply schema` after a restart re-emits a declared tag, so an imperative tag edit whose save failed is lost at restart. The `NOTE:` is in `saveTableTags`.
- **Conditional, recorded as `NOTE:`s:**
  - at `tagChangesBetween`: an adopted added CHECK or column keeps the record's tags even when this machine's declaration differs;
  - at `tagsToSave`: a machine applying an older declaration overwrites a newer tag.

## For the reviewer

- `tagsToSave` is not pure, because it updates `adopted`. It is called once per change event through the `persistTags` callback, and the batched read that precedes it can throw before it runs. A forward save whose read failed records no adoption, so its undo would be judged as an ordinary change and could write. That takes a failed read followed by a successful one inside one batch. I did not test it and did not add a `NOTE:` for it.
- The slot keys (`columns:a`, `indexes:ia`, `table`) appear only inside `tag-overlay.ts` and the adopted-change key, and are never persisted.
