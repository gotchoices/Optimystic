# A peer is judged serving only by its own identify — review

## What was wrong

`Libp2pKeyPeerNetwork.membershipOf` counts a remote peer as serving this network when its libp2p peerStore protocol list names `<prefix>/repo/1.0.0` or `<prefix>/cluster/1.0.0`. libp2p 3.3.11 writes that list from two places: identify's `patch` (the peer's own list), and a `peerStore.merge(remotePeer, { protocols: [protocol] })` on every negotiated stream, on both ends (`Connection.newStream` and `onIncomingStream` in `libp2p/dist/src/connection.js`). On the receiving end the second write is false: a machine that sends this node a `repo` request gets `repo` added to its own record here, is classified serving, remembered (`rememberedServing`), persisted, and placed in cohorts whose writes then wait on it (GitHub sereus#63, 84–105 s per write). The same merge was the "by opening a stream" route a stranger used to get counted as a member.

## What was built

- **`storageServingProtocols(protocolPrefix)`** in `packages/db-p2p/src/network/storage-protocols.ts`: the one place the two ids are named. Used by `Libp2pKeyPeerNetwork.servesThisNetwork` (cached once in the constructor as `storageProtocols`, empty on the unscoped path, which never asks), by the filter, and by `preparedStreamProtocols` in `libp2p-node-base.ts`.
- **`filterStorageClaimMerges(peerStore, self, protocolPrefix)`** in `packages/db-p2p/src/network/storage-claim-filter.ts`: wraps `peerStore.merge`. A merge into a peer other than self that is exactly `{ protocols: [<repo or cluster id>] }` (`isProtocolOnlyMerge`) resolves to `peerStore.get(id)` without recording anything; when the peer has no record yet (`NotFoundError`, tested by name), it falls through to the inner merge with `{ protocols: [] }`. Every other merge, and every merge into self, passes through. Logs `installed` once (`storage-claim-filter` namespace, row added in `docs/debugging.md`).
- **Installed in `createLibp2pNodeBase`** right after `throttleProtocolMerges`, before `node.start()`, so it is the outer wrapper and a dropped merge never touches the throttle's bookkeeping. `protocolPrefix` is now computed before start (moved up, with its comment) since the filter needs it there.
- **`isProtocolOnlyMerge` / `ProtocolOnlyMerge` moved** from `protocol-merge-throttle.ts` into `storage-claim-filter.ts`; the throttle imports it. Reason: the filter outlives the throttle (libp2p/js-libp2p#3692 still records a stream's protocol once per connection on the receiving end). The blocked ticket `libp2p-carries-the-per-stream-merge-fix` arm was rewritten with the real names, and its "delete the pin spec" step changed to "keep its shape assertion for the filter".
- **Comment/doc updates**: `membershipOf` NOTEs (partial lists never gain storage protocols from streams; identify-failure NOTE gains one sentence that storage streams do not rescue such a peer); the `heardFromBootstrapPeer` NOTE about a refused bootstrap peer filling its list by opening a `cluster` stream was removed and folded as one sentence into that method's accepted-cost NOTE (only advertising remains, which IS the accepted-cost case); `NodeOptions.isNetworkMember` doc, `network-membership-gate.ts` header, `prepared-streams.ts` NOTE, and the throttle header. `docs/internals.md` §Network Membership Predicate: the stream route is marked closed with the filter cited, a "what closing it costs" paragraph (identify failure, a machine that switched from serving under one peer id), and a **Mixed versions** paragraph; §Third-Party Address Learning: one paragraph naming the filter and saying it is not part of the throttle's removal.

## Tests

- **Added `packages/db-p2p/test/storage-claim-filter.spec.ts`** — the reproduction. Two real libp2p nodes over loopback TCP with identify and the filter. Listener serves `repo` and a non-storage `sync` id; dialer registers no storage protocol, waits for identify to settle on both ends (so a later identify `patch` cannot erase the merge and mask the bug), then opens two streams on each. Asserts: listener's record of the dialer does not name `repo` but does name `sync` (filter is selective); listener's own record names `repo` (a merge into self — the registrar's — passes through); dialer's record of the listener names `repo` (identify's write survives). **Verified it fails without the filter** on the first assertion ("the requester is not recorded as serving storage").
- **`libp2p-merges-protocol-per-stream.spec.ts`**: header now says both wrappers depend on the `isProtocolOnlyMerge` shape and what to re-aim if it changes; import moved to the filter module; test title updated.
- No key-network spec changes (its doubles write peerStore lists directly), as the plan expected.

## Known gaps / things to look at

- **Cost of a dropped merge.** Each dropped merge does a `peerStore.get` (read lock, datastore read, decode), where the throttle answered repeat merges from memory. Cheaper than the merge it replaces (no rebuild/sort/encode/write), but every repo/cluster stream on both ends now pays one read. Unmeasured on a phone; parked as a `NOTE:` tripwire in `filterStorageClaimMerges` (remedy: answer with the last `Peer` read for the peer, as the throttle does).
- **Missing-record fallback creates an empty record** (`merge(id, { protocols: [] })`), which dispatches `peer:update` for a new record. Only reachable when a stream arrives before any record exists for the peer; the spec cannot reach it (identify always runs first), so this branch is verified by inspection only. I judged a unit test for it to be glue; the reviewer may disagree.
- **Only nodes built by `createLibp2pNodeBase` get the filter.** A `Libp2pKeyPeerNetwork` built over a node from elsewhere (the foreign-node fallback in the Quereus plugin's collection-factory) still reads a peerStore that stream merges write. The `membershipOf` NOTE's "only identify writes the storage protocols" is true for this repo's own nodes only.
- **Mixed versions** are documented, not solved: servers on an older build keep classifying clients by their streams; an embedder keeps `isNetworkMember` refusing clients until every serving machine upgrades.
- The dialer-side merge is dropped too (the wrapper cannot tell `newStream` from `onIncomingStream`); it was true but redundant with identify. A serving peer whose identify failed is no longer rescued into `serves` by storage streams — accepted per the plan, noted at `membershipOf`.
