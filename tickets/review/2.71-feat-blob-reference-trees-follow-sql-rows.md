# Blob reference trees follow SQL rows — review

Third of four parts of backlog `feat-sql-columns-hold-blob-references`. Built as the implement ticket specified, with three deliberate deviations (below). Nothing touches the blob service: pinning and announcing are `feat-blob-pins-follow-sql-commits`.

## What now exists

**A maintainer per table.** `BlobReferenceMaintainer` in `packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts` is `IndexManager`'s counterpart for blob references: `columnsOf`, the three staging methods (`stageInsert`, `stageDelete`, `stageUpdate`), `withColumns`, and the free function `blobReferrer` (framed primary key, then the column NAME framed as one more element). What it stages is a pure function of `(rows, keys, columns)` — it holds no transactor and no blob service, which is the structural form of the purity a validating member's re-execution depends on. `onStaged` exists in the constructor and is left unset; `feat-blob-pins-follow-sql-commits` wires it.

**Wiring in `OptimysticVirtualTable`** (`packages/quereus-plugin-optimystic/src/optimystic-module.ts`): `openBlobReferenceTree` (through the ordinary collection factory, with the declared-at-another-table's-`/blobrefs` `NOTE:`), the tree opened and the maintainer published in `doInitialize`'s one synchronous step, kept across a re-initialization (`KeptHandles`, `adoptCatalogEntry`, `forgetUnmaintainedTrees`), registered with the bridge, marked dirty, counted in `hasStagedWrites`, named by its table in `describeCollection`, rebuilt in `republishColumnLayout`, and `attachBlobReferences` for the ADD COLUMN that gives a table its first such column. Six staging call sites in `update()` / `applyUniqueEvictions`, each beside the index call it mirrors.

**The scope registry.** `BlobScopeRegistration` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-scope-registration.ts` (read-then-register, memoized per (network key, scope) once confirmed), plus `blobReferenceOptions` as the one place the `/blobrefs` URI is formed. `CollectionFactory` gained `networkBinding` and `blobScopes`, `BlobBackend` now extends `NetworkBinding`, and `clearCache`/`dispose` clear the memos. Written by `create` (a table that has a `blobref` column) and `addColumn` (the first such column), unregistered by `destroy`, never on hydrate.

**The two refusals.** `ColumnKeyedParts.columns` widened with `BlobRefColumnShape` and the `it holds blob references` blocker added to `columnDropBlockers`; `SchemaManager.mergeForWrite` added with the two re-declare refusals, and `storeStoredSchema`, `storeInBatch` and `mergeWithPersisted` routed through it, `viewOverRecord` left on `mergePersistedSchemas`.

## Deviations from the implement ticket — each deliberate, each documented at its site

- **`BlobReferenceMaintainer`'s constructor takes the qualified table name first**: `(table, columns, tree, scope, onStaged?)`, not the declared `(columns, tree, scope, onStaged?)`. The ticket required the malformed-value refusal to name "the table and column"; the declared shape carried no table name, and the scope (`<path>/blobrefs`) is not a table name a human can match back to their SQL.
- **`BlobScopeRegistration.ensure` answers `BlobScopeOutcome`** — `{ registered: true } | { registered: false; cause }` — not `Promise<boolean>`. The ticket also required `create` and `addColumn` to throw with "the failure attached as `cause`", which a boolean cannot carry. `ensure` still never throws, and still only memoizes a confirmed registration.
- **`mergeForWrite` calls `assertBlobRefTypeRegistered` ahead of the new kept-columns rule.** Without that ordering, a process that cannot resolve the `BLOBREF` type sees the new "Cannot re-declare column … to or from blobref … Drop and re-create the table" refusal — actively wrong advice, since what that process needs is to register the type. The guard is the same one `storeStoredSchema` already holds at its own entry, so this is a cheap re-ordering, not a new rule. **Worth a reviewer's eye**: it means `mergeWithPersisted`'s dry run now throws for that combination where it previously did not (the refusal came a few lines later, from `doInitialize`'s own `assertBlobRefTypeRegistered`). The net outcome is the same refusal with a better message, but it is a changed throw site.

## Known gaps — read these before reviewing the tests

**The validator re-execution round-trip is NOT tested, and I did not attempt it.** The implement ticket asked for "one session-mode transaction with an insert, an update and a delete, validated by `createQuereusValidator`". Three things make that test pin something other than this change:

1. The operations hash covers each operation's `blockId`, and a new block's id is a random 256-bit value (`BlockId` in `packages/db-core/src/blocks/structs.ts`). A re-execution can only reproduce the hash for a transaction that creates no block — so whether such a test passes turns on whether the chosen fixture happened to touch only already-committed leaves, not on whether the maintainer is pure.
2. `QuereusEngine.execute` applies while translating, through whatever coordinator the database it holds is bound to (the contract is spelled out in `TransactionValidator.validate`, step 5, in `packages/db-core/src/transaction/validator.ts`). Isolating a validation run is the caller's job, and nothing in the repo does it, so a re-execution against the writer's own store would commit the transaction a second time.
3. `createQuereusValidator` has no production caller at all — backlog `feat-no-deployment-validates-transactions-at-pend`, recorded as an accepted tradeoff in `packages/quereus-plugin-optimystic/src/transaction/quereus-validator.ts`.

What I substituted is the half of the claim this change owns: a session-mode case that commits through a real `TransactionCoordinator` and asserts both that the reference tree's entries landed (read back through a fresh handle, so it is the coordinator's commit and not a legacy flush) and that **every** pend of that commit carried the transaction and its operations hash. If the tree were not a registered collection, its entries would be absent from both. The reviewer may reasonably want more; the missing piece is a harness that isolates a validation re-execution, which is new infrastructure rather than a change to this spec.

**Covered by inspection only** (the implement ticket's own call, restated so nothing is assumed tested): rollback and savepoint rollback; the offline queue and its restore after a restart; two tables declared over one URI sharing a reference tree; an index on a `blobref` column; a registry write that fails at `create`; an unregister that fails at `drop`; a dropped-then-re-created table counting its old entries.

**`forgetUnmaintainedTrees`'s reference-tree arm is unreachable today** — the refusals keep a table from losing a `blobref` column. It is there as insurance for a future arm that can, and a reviewer who wants it deleted rather than kept has a fair case.

## Use cases to exercise

A table declares a `blobref` column; every write to it keeps `<table>/blobrefs` saying exactly what the rows say, and the table's id is in its network's scope registry so a storage node can find it:

```sql
create table Attachment (
	Id text primary key,
	Name text,
	Content blobref null
) using optimystic('tree://app/attachment');

insert into Attachment (Id, Name, Content) values ('a', 'photo.jpg', 'bafkrei…');
update Attachment set Content = 'bafkrei…other' where Id = 'a';   -- old entry out, new entry in
update Attachment set Content = null where Id = 'a';              -- entry out, nothing in
delete from Attachment where Id = 'a';                            -- entry out
alter table Attachment drop column Content;                       -- REFUSED: it holds blob references
alter table Attachment add column Thumb blobref null;             -- scope registered, maintained from the next statement
drop table Attachment;                                            -- scope unregistered
```

Reading the list back, as a host or a later part does: walk the tree at `<table uri without scheme>/blobrefs`, decode each key with `decodeBlobReferenceKey` (db-core), and split the referrer with `splitKeyTuple` — the last element is the column name, the ones before it the row's primary key.

## Tests added

`packages/quereus-plugin-optimystic/test/blob-reference-tree.spec.ts` — 21 cases, ~0.9 s:

| Case(s) | What it verifies |
|---|---|
| 13 table-driven shape cases | The tree's triples `(reference, row key, column)` equal the ones a full scan of the rows implies, through ONE oracle built from the production `blobReferrer` and the table's own `RowCodec`. Each case also pins an exact entry count, so a case cannot pass because both sides came out empty. The shapes: insert (and NULL registering nothing); delete; cascade delete; secondary-UNIQUE REPLACE eviction; INSERT OR REPLACE over an occupied key; same-key update changing / keeping / clearing / setting a reference; primary-key move; displacing move; displacing move where both rows hold one reference in one column (the case the remove-before-add order exists for); one reference held in both columns of one row; and a catalog-only DROP COLUMN of an unrelated column followed by further writes (the `republishColumnLayout` renumbering). The table has a composite primary key whose columns are not the leading ones, two `blobref` columns, a REPLACE-resolving secondary UNIQUE, a REPLACE-resolving primary key and a cascading foreign key. |
| session-mode commit | The reference tree is one of the registered collections a real `TransactionCoordinator` commits, and every pend of that commit carried the transaction and its operations hash. |
| ADD COLUMN of a first `blobref` column | The scope was not registered before and is after; the instance maintains the tree from the very next statement with no re-initialization (`attachBlobReferences`); a second such column extends the column list. |
| the registry | A created table's scope is listed; a table with no `blobref` column registers nothing; a dropped table's scope leaves. |
| racing writers (two handles, one store) | A loser refused on the row it changed leaves no reference entry behind (asserted on BOTH handles, against the oracle); two writers referencing one blob from different rows both land, one entry each, so neither unguarded upsert overwrote the other. |
| the three refusals | A re-declare that turns a persisted `text` column into `blobref`; one that omits a persisted `blobref` column; a DROP COLUMN of a `blobref` column — and an ordinary column of the same table still dropping, so the refusal is the rule and not a table-wide block. |

`packages/quereus-plugin-optimystic/test/catalog-only-change.spec.ts` — one added case: `columnDropBlockers` names a `blobref` column in **both** shapes a column arrives in (the engine's `logicalType` and a record's `affinity`), and nothing for an ordinary text column. Pure; the record shape is the only one a SQL-level test would reach.

No other test was added. The commit routes, the offline restore and the savepoint machinery are held for every tree a table opens by the existing specs, and a test of this tree's place in them would pin the wiring rather than the behaviour.
