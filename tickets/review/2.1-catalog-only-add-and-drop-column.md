# Catalog-only ADD COLUMN and DROP COLUMN — review handoff

The code and tests were written by an earlier run and are already in commit 38fc7d3c (that commit's message says "timed out", but the work in it is complete). This run updated the release note, checked the README claims against Quereus's source, and ran the checks. Review the diff of 38fc7d3c for the source and specs, plus this run's change to `.release-notes.pending.md`.

## What it does

The `alterTable` hook of `OptimysticModule` used to refuse `addColumn` and `dropColumn`. Both now go through the shared catalog-only helper `alterCatalogOnly`, which the prereq added. The helper reads the record fresh, classifies the change (owned, adopted or refused), writes under the batch checkpoint, updates the engine result and the table instance, and keeps the undo of an adopted change off the record.

- **ADD COLUMN** is accepted when the column, resolved with `columnDefToSchema` under the session's `default_column_nullability` / `default_collation`, is nullable, has no DEFAULT, is not generated, is not in the primary key, and its constraints are only `null`, `notNull` or `collate` (`CATALOG_ONLY_COLUMN_CONSTRAINTS`). It must also be an append. Anything else keeps the old refusal text, `Module for table '<t>' does not support ALTER TABLE ADD COLUMN`, with `UNSUPPORTED`. A `backfillEvaluator` on an accepted column raises `INTERNAL`. The record edit `withColumn` appends `columnSchemaToStored(column)`.
- **DROP COLUMN** is refused when `columnDropBlockers` finds the column in any of: the primary key, an index, a UNIQUE constraint, this table's foreign key, a generated column (the column itself), or the inputs of another generated column. The check runs three times: against the engine's `tableSchema`, against the instance's own schema and maintained index trees (`OptimysticVirtualTable.columnDropBlockers`), and against the fresh record (inside `classifyColumnChange`). The message keeps the prefix `Module for table '<t>' does not support ALTER TABLE DROP COLUMN` and then names what uses the column. When the blocker is only in the record it adds "(in the table's stored description, saved by another machine)". The record edit `withoutColumn` renumbers every positional field: primary key, index columns, UNIQUE constraints, foreign keys, generated-column dependencies (keys and values), and generated-column topological order. The engine side uses Quereus's `shiftSchemaIndicesForDrop` plus the same generated-column renumbering (`withoutColumnAt`).
- **Classification** (`classifyColumnChange`): an add over a record with no column of that name is owned; over the same column (tags and name case ignored) it is adopted; over a different column of that name it is refused with `ERROR` and a message saying retrying will not help. A drop over a record holding the column is owned whatever the column's definition, unless the record keys on it, which refuses with `UNSUPPORTED`; a drop over a record without the column is adopted.
- **Table instance.** `applyCatalogOnlyEdit` takes an optional `ColumnLayoutChange` and calls `republishColumnLayout` in one synchronous step. That builds a new `RowCodec`, and after a drop it renumbers the maintained index descriptors (declared and unique-enforcement) through `IndexManager.repositionColumns`. No tree is opened, closed or re-registered.
- **Scans** now take `rowCodec` and `indexManager` once, at the start of `runQuery`, and pass them to `executeTableScan`, `executePointLookup`, `executeRangeQuery`, `executeIndexScan` and `resolveIndexTarget`. The comment in `doInitialize` was updated to say this is done.
- The accepted-tradeoff `NOTE:` about re-adding a dropped name is on `OptimysticModule.dropColumn`.

## Where it departs from the ticket text (please judge)

- `withColumn` and `withoutColumn` are free functions in `schema-manager.ts`, next to `withoutCheckConstraint`, not `SchemaManager` methods.
- The instance's row codec is built from the instance's own `tableSchema` (after the edit), not from the record. Index descriptors are renumbered in place (`IndexManager.repositionColumns`) rather than replaced through `setSchema(record)` and `buildUniqueEnforcementIndexes(record)`. The reasons are in the `NOTE:` on `repositionColumns` and in `republishColumnLayout`'s doc. Rows reach the instance positioned by this machine's engine, and the instance mirrors that engine. The record can list an index this manager has no tree for, and a listed index with no tree makes every staging path throw. The record can also be behind this engine (`bug-optimystic-stale-hydrated-table-rewrites-the-shared-catalog-record`). After an adopted change the engine's column list is the record's for the changed column, so the codec still follows the change.
- On an adopted ADD COLUMN whose tags differ from the record's, classification ignores tags, so no structural write happens. The `table_modified` tag listener then overlays this machine's column tags onto the record (`SchemaManager.persistTags` returns `saved`). Last tagger wins, as for any tag change. This was checked by reading the code and has no spec.

## Tests added (all in 38fc7d3c)

`test/catalog-only-change.spec.ts`, describe "catalog-only column changes":
- "judged against the record" — six cases of `classifyColumnChange`, one per row of its table, including the refusal codes and a drop refused for an index only the record holds.
- "removing a column renumbers every positional field after it" — `withoutColumn` over a record with a primary key, a foreign key, an index, a UNIQUE and a generated column after the dropped one, plus `toPersistedSchema` persisting the index under the right column name.

`test/alter-table-arms.spec.ts`:
- `REFUSED` table: the old ADD COLUMN and DROP COLUMN rows, which used statements that now succeed, were replaced. New ADD rows: DEFAULT, generated, inline CHECK, inline UNIQUE, inline REFERENCES. New DROP rows: primary-key column (Quereus refuses first, `CONSTRAINT`), indexed column, UNIQUE column, foreign-key column, generated column. Each row checks the message and code, that the engine catalog object is identical, and that the rows are unchanged.
- "rows written under either column list read under the other, before and after a restart" — add `b`, read old rows with `b` null, write one with `b`, restart by hydrating only, drop `b`, restart again.
- "a drop renumbers the index, UNIQUE constraint and generated column after the dropped column" — index seek, duplicate refused, generated value, and `verifyIndexes` with no missing or orphaned entries, before and after a hydrate-only restart.
- "inside apply schema, on one machine and on two":
  - a failed apply undoes its ADD COLUMN in the session, the instance and the record, and the restore is reported as verified;
  - a second machine adopts an upgrade (add `b`, drop `c`) with zero pends and commits, then reads rows with `b` and without `c`;
  - a second machine whose apply fails after adopting the ADD leaves `b` in the record and restores its own catalog;
  - two machines applying the same upgrade at once both succeed, and the record holds `b` once and no `c`.

The pre-existing test "refuses ADD COLUMN of a NOT NULL column with no default over rows, reporting the missing default first" covers the NOT NULL shape.

## Checked by reading the code only, no test

- DROP COLUMN refused because of an index another machine added (in the record, not hydrated here). Only the unit test covers it; reading `alterCatalogOnly` shows the refusal is thrown with `verdict.code` before any write and before `mergePersistedSchemas` runs.
- Concurrent scans: a committed read that overlaps an ADD or DROP COLUMN keeps its codec. No spec forces that interleaving.
- Batched data events: Quereus remaps them itself (`remapBatchedDataEvents`), and the plugin emits none of its own.
- An `insertAtIndex` other than an append is refused. No spec; ordinary Quereus syntax may not produce one.
- ADD COLUMN NOT NULL on an *empty* table reaches the module's own refusal. No spec.

## Quereus issue to raise for Sereus #46 (not worked around here)

`generateMigrationPlan` in `../quereus/packages/quereus/src/schema/schema-differ.ts` emits index creates (`pushCreates(diff.indexesToCreate, 'index')`) before the per-table alter block, where ADD COLUMN runs. A schema version that adds a column and an index on that column therefore fails with `Column '…' not found`, on every module, the memory module included. Quereus already moved assertion creates to the end for exactly this reason (the "Assertion creates LAST" comment), but not index creates. Drops are fine: `DROP INDEX` runs before the alter block, so dropping an index together with its column works. The README Limitations entry documents the workaround (add the column in one version, its index in the next). Someone with access to the Quereus repository should file this there.
