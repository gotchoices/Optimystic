# A writer refuses a block too large to copy — review handoff

## What was built

Before a write is sent, every block it touches that the writer can materialize locally is measured as it will be after the write. A block over `MAX_BLOCK_BYTES` (7.5 MiB of JSON) throws `BlockTooLargeError` (`blockId`, `bytes`, `limit`, message naming `MAX_BLOCK_BYTES`). It has the same terms as `TransactionTooLargeError`: nothing sent, nothing to cancel, not a `StaleFailure`, never retried.

- **One pass, two outputs.** `describeTouchedBlocks` (digest.ts) is the old digest loop, now returning `{ digests, bytes }`. The byte count is the length of the canonical-JSON serialization the digest already hashes (`canonicalBlockHashAndBytes`). Canonical JSON is `JSON.stringify` with keys reordered, so the length equals `jsonEncodedBytes`. `computeBlockContentDigests` is now a thin wrapper returning `.digests`; production calls `describeTouchedBlocks`, while tests and db-p2p tests still call the wrapper.
- **Judging is a separate step.** `oversizedBlock(bytes)` returns the error or `undefined`, and never throws. The digest pass keeps its rule that declaring content never breaks committing it. `Collection.syncAttempts` throws what `oversizedBlock` returns. The coordinator turns it into a pend-phase failure.
- **Collection path.** `Collection.syncAttempts` measures on every attempt, after the log append, so the log tail and header blocks are measured too, right before `source.transact`. The throw escapes `sync` unchanged. `actAndSync` (used by `Tree.replace` and `Diary.append`) unstages, as it does for any failure.
- **Coordinator path: a design change to check.** The coordinator used to compute its commit's `blockDigests` in `commitRequestFor`, *after* the pend round trip. The ticket assumed it did this in the pend phase; it did not. To measure before anything is sent without materializing twice, `coordinateTransaction` now calls `declareTouchedBlocks` first, ahead of gather and pend. That call measures each collection's blocks and keeps the digests as `DeclaredDigests`, which are threaded through `commitPhase` → `commitTogether` / `commitEach` → `commitCollection` → `commitRequestFor`. `commitRequestFor` is now synchronous.
  - The refusal is a `PendPhaseFailure` with `tooLarge` (now `TransactionTooLargeError | BlockTooLargeError`). So `commit()` throws it by name after restoring snapshots, through the existing `tooLarge` branch, and `execute()` returns it as `{ success: false, error }`.
  - The declaration is now taken from the same tracker state and pins the pend's `baseRevs` come from, before the pend instead of after. The tracker is latched for the whole span and isn't reset until commit succeeds. All digest/base tests pass unchanged, but a reviewer should confirm nothing relied on the post-pend timing. For example, a pin judged "moved" by a concurrent unlatched read between pend and commit used to make that block undeclared at commit. Now it is declared from the pin, which matches what the pend named.
  - The coordinator still retains no digests for a torn-attempt re-send (`retainInFlightAttempt`); the comment there was updated. Retaining them would now be a one-line change if wanted: the `Collection.sync` path does retain them.

## Known gaps and consequences (please weigh)

- **Unmeasured blocks.** A block the writer can't materialize is neither declared nor measured: a delete, a blind update to a never-read block, an update whose base was evicted before staging, a moved base, or a base the ops won't apply to. This is recorded in the doc comment on `describeTouchedBlocks`, with a `NOTE:` tripwire, and in internals.md.
- **Data from before the size rules can now wedge writes.** Say a log tail block was grown past 7.5 MiB by a build without `a-log-block-rolls-over-by-size`. The next append rolls over from it, rewriting its `nextId`; that touches the oversized block, so it is refused, and so is every later write to that collection. A tree leaf over the limit is divided by its next insert or growing update, so that passes. A delete or shrinking update that leaves it over is refused. Before this change those writes succeeded, though the block was already uncopyable. AGENTS.md says not to worry about backwards compatibility yet, so this is documented in internals.md ("When it fires") and not mitigated. One possible mitigation: refuse only a write that makes an already-oversized block bigger by more than a small amount. I judged that too fiddly to do without a decision. It is a reviewer/human call whether this needs a backlog ticket.
- **Error is per first block.** `oversizedBlock` reports only the first oversized block found; the order is the order the tracker lists its transformed blocks.

## Tests

- `packages/db-core/test/writer-refuses-oversized-block.spec.ts` (new):
  - "Collection.sync refuses it before the pend, and actAndSync unstages the write". A test-only `grow` handler grows one block by half of `MAX_BLOCK_BYTES` per write. Each write's transaction is about half the limit, so the transaction limit could never catch this. The second write gets `BlockTooLargeError` with the right fields. The transactor gets no pend, `hasUnsyncedChanges()` is false, and the block reads back as committed (one item). This is the test the ticket asked for.
  - "TransactionCoordinator.commit refuses it by name before the pend". Same shape, through `applyActions` + `commit`. It pins the second write path, which has its own wiring (pend-phase failure → `tooLarge` → throw). The ticket asked for one test, so this second test is beyond it; cut it if you judge it wiring.
- `packages/db-core/test/coordinator.spec.ts`: the five private-`commitPhase` tests now pass the new `declared` argument. The two digest tests ("declares the digests of the blocks its collection actually staged", "omits the field entirely…") get it from the private `declareTouchedBlocks` through a small `declaredFor` helper, so they still check that the commit declares what was described off each collection's own tracker. The other three pass `new Map()`.
