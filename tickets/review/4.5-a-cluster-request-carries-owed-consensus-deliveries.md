# Review: a cluster request carries the consensus deliveries its target is still owed

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29), question 2, first half. The second half, `a-two-member-pend-defers-its-final-delivery-to-the-commit` (already in `implement/`), builds on this to cut a two-machine write from four requests to three. The design and its correctness argument are in the completed decision ticket `decide-whether-a-two-machine-write-drops-to-three-calls`.

## What was built

A record is **owed** to remote member P when its `ClusterCoordinator.transactions` entry has an armed retry whose `pendingPeers` lists P and the record carries a commit majority. Any other request the coordinator sends P now carries P's owed records ahead of its own record, and P applies them first.

- **db-core.** `MemberApplyOutcome.acceptsCarried?: true`; `CarriedOutcome` `{ messageHash, delivered, outcome?, error? }`; `MaxCarriedRecords = 4` (all in `structs.ts`); optional `ICluster.updateCarrying(record, carried)` returning `{ answer, carried }`.
- **Member.** `ClusterMember.withOwnApplyOutcome` stamps `acceptsCarried: true` on every answer, so the member's own `applyOutcomes` entry is never omitted. Every reader of `applyOutcomes` was checked and treats an entry carrying only the stamp as "nothing reported": `membersAwaitingConsensus` (`executed !== true` → still awaiting), `remoteMemberHolds` (reads `commit.success`), the cohort loop in `executeClusterTransaction` (reads `pend` / `commit`), and `pendCohortDurability` (reads promises only).
- **Shared member-side loop.** `applyCarriedRecords` in the new `packages/db-p2p/src/cluster/carried-records.ts`: for each carried record in order, address learning, then the redirect check (a redirect is not delivered), then `cluster.update` in its own `try`. A `carried` that is not an array of at most 4 entries is ignored (logged), not refused. `readCarriedOutcomes` in the same file is the client side: exactly one outcome per record sent, in order, matched by `messageHash`, defaulting to not delivered.
- **Wire.** `ClusterService.processOperation` applies `carried` first, then the main record, and puts `carried: CarriedOutcome[]` on whatever it answers with (the record, a redirect, or the error envelope). To make that possible the error-envelope `try/catch` moved from `handleIncomingStream` into `processOperation`, which now never throws for an application error. The wire behaviour is unchanged; no spec relied on the throw. `ClusterClient.update` was split into `send` + `answerFor`, and `updateCarrying` strips the `carried` field off the raw answer (`takeCarriedField`) before the existing error and redirect handling. It falls back to sending the record alone (all carried reported not delivered) when the encoded request would exceed `MAX_CONTROL_MESSAGE_BYTES`. A redirect is followed for the main record only.
- **Coordinator.** `updateMember` → `requestMember` → `takeOwedRecords` (synchronous; marks each taken record in flight in the new `ClusterTransactionState.carrying` set) → `updateCarrying` → `returnCarried`. A delivered record goes through `settleCarriedDelivery`: merge the outcome, drop P from `pendingPeers` (via `noteDelivered`, which `retryCommits` now also uses), finish the retry when nobody is left (`finishRetry`, also used by `retryCommits`), and give this node's member its second reconcile (`reconcileLocalMemberAgain`, fire-and-forget) when P reports holding the revision. A record that was not delivered, or whose carrying request threw, just has its in-flight mark cleared and stays owed. `retryCommits` skips in-flight peers, which stay in `pendingPeers`, so the retry never finishes on their account. Capability is per peer in `carryCapablePeers`, an LRU of 1024 entries set from the peer's own `applyOutcomes` entry and cleared when an answer lacks the stamp. `owedSince` (set when a retry is first armed on a majority record) orders the owed records, oldest first.
- **Harness.** The mesh client implements `updateCarrying` through the same `applyCarriedRecords`. `onClusterDelivery` gains a third `carried` argument (existing two-argument hooks still compile). New `MeshOptions.coordinatorConfig` is spread over the resolved policy for the coordinator only, for retry timings. New `MeshFailureConfig.dropCarried` loses one carried record on its way to a member while the rest of the request arrives.

### Deviations from the ticket, on purpose

- **A record is carried only once this node's own member has applied it**, meaning self is not in `pendingPeers`. The ticket's definition of "owed" did not say this. It keeps the "coordinating member applies first" order that `broadcastMergedRecord` documents as load-bearing for behind-member reconciles.
- **`dropCarried` harness option and the rival spec.** `rival-superseded-only-by-a-writer-that-built-on-it.spec.ts` makes member D miss R's pend "including the coordinator's scheduled retries". With carrying, the pend rode on the next request to D, and phase 2 failed. The scenario is still a real one: a commit coordinated elsewhere, a retry budget run out, or a request too big to carry. So the spec now also drops carried copies of R's pend to D, instead of being rewritten.
- **Harness logger.** It logs under `cluster-service`, the namespace of the member side of the wire it stands in for. A new `mesh-harness` namespace failed the log-namespace doc guard in `logger.spec.ts`.

## Tests added (each beside what it pins)

- `cluster-coordinator.spec.ts`, "carries a record owed to a member only when that member's last answer stamped acceptsCarried". Five fake members, two of which miss transaction 1's commit. On transaction 2 the stamping member gets `updateCarrying` with transaction 1's record, exactly once. The unstamped member gets plain `update` only. The retry timer then sends transaction 1 to the unstamped member alone, and nothing to the stamping one.
- `carried-consensus-delivery.spec.ts`, mesh case: three members, `commitBroadcastRetryInitialMs: 60_000`. One member misses write 1's commit round and its consensus delivery. Write 2's first request to it carries write 1's commit. The member's `update` sees write 1's commit immediately before write 2's record, so the carried record is applied ahead of the main one. The member then holds write 1, and write 1's retry is cleared. The test reads the retry through a typed peek at private coordinator state; no public seam reports it.
- `carried-consensus-delivery.spec.ts`, wire case: the real `ClusterClient.updateCarrying` against the real `ClusterService`, over the length-prefixed JSON codec. It checks that carried records are applied in order before the main record, that one throwing carried record becomes that record's `error` without failing the request, that the client reads one outcome per record, and that the answer record carries no `carried` field. This third test goes beyond the ticket's two; it is the only coverage of the production client/service path. Cut it if you judge it below the bar.
- Updated `rival-superseded-only-by-a-writer-that-built-on-it.spec.ts` (`dropCarried`, see above).

## Known gaps and things to look at

- **A refused commit reported on a carried delivery gets no second send.** In `retryCommits`, a pending member that answers but still reports not-executed or a refused commit is sent the record a second time in the same retry (via `broadcastMergedRecord`). A carried delivery books the member as done on the first delivered answer, matching how a successful broadcast delivery is booked. The coordinating member has already applied when a record is carried, so the member's own reconcile had a holder. Decide whether a delivered-but-refused outcome should instead stay owed.
- **Outcomes are lost with an error answer.** When the main record's answer is an error envelope, the client throws and the carried outcomes on that envelope go with it. The records stay owed and are re-sent, and the member dedups them. This is commented in `ClusterClient.updateCarrying`.
- **Downgrade detection lags.** An older member echoes the coordinator's copy of its `applyOutcomes` entry, so a member moved back to an older build still reads as capable until the next promise round, whose record carries no entries. Until then its carried records come back not delivered: wasted bytes only. `NOTE:` at `noteCarryCapability`.
- **A retry attempt can be spent with nothing sent.** If the timer fires while every pending member's delivery is riding on another request, the attempt counts. `NOTE:` in `retryCommits`. Attempt counting was deliberately left unchanged (backlog `debt-a-recovered-commit-retry-restarts-its-budget`).
- **Untested by inspection only:** the client's size fallback (`carried:too-large`), the service's handling of a malformed `carried`, and the late answer arriving after the transaction was released (dropped because `state.retry` is gone). No real-socket integration spec exercises carrying.
- `takeOwedRecords` scans every held transaction on each remote request (`NOTE:` there).
- `ClusterService.processOperation` now takes an optional `remotePeer` for its error log line and returns the envelope instead of throwing. External embedders calling it directly would see that change.

Those last ones had said the retry timer was the only late-delivery path; they now name carried delivery too.
