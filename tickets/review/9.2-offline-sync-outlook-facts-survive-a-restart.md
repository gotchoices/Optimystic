Third of three tickets for stage 9 of docs/offline-sync.md §Implementation stages; stage 9 is now marked implemented. Before this, the facts a queued transaction's outlook rests on (`EntryFacts`: which staged elements carry a fresh value, and which decisions each statement made against other rows) lived only in memory, so a restored transaction came back judged from tags alone: an insert under `StampId()` came back `exposed` and `unchecked` came back `'not-computed'`.

## What changed

- **`JournaledFacts`, `encodeFacts`, `decodeFacts`** in `write-description.ts`, beside `foldWriteFacts`. `fresh` is written as `[collectionId, keys[]]` pairs; each `unchecked` read keeps `table` / `kind` / `scope` and drops its pinned `rows` (bound values can be bigint or bytes, which the journal's `JSON.stringify` cannot carry). The tripwire `NOTE:` at `encodeFacts` names the remedy (journal the encoded main-tree keys) if the resulting widening ever bites.
- **`EntryRecordV1.outlook?: JournaledFacts`** in `offline-journal.ts`, record version still 1. The journal asks its owner through a new `OfflineJournalHooks.factsOf(transactionId)` as it builds the entry record; `OfflineMode` answers from `entryFacts`, which `enqueue` sets before `queue.enqueue` (the only enqueue path, via `TransactionBridge.sealIntoQueue`).
- **Restore** (`OfflineRestore.restoreOne`): decodes `entry.outlook` and calls `RestoreHost.factsRestored` before `queue.restore`, whose `queued` status judges the entry. If `queue.restore` throws (deferral on `BlockUnavailableError`, or any other error), it calls `RestoreHost.restoreRolledBack`, and the controller drops the facts unless the queue lists the transaction (`OfflineMode.forgetUnqueuedFacts`). The settled-at-restore path (every collection already committed) drops them through the existing terminal-status cleanup in `onQueueStatus`.
- **Judgement** (`commit-outlook.ts`): `encodedKeys` now answers `undefined` for a `row` read with no rows, so a restored row-scoped read is matched by its table. Without this, the empty key list matched *no* earlier writer: narrower than the original, the wrong direction. A live `row` read always has at least one row (`pinnedRows` already widens an empty one to `global`), so this changes nothing outside restore.
- A record with no `outlook` (written by an earlier build) restores exactly as before: no facts, judged from checks and tags, `unchecked: 'not-computed'`.

## Test added

One case in `test/offline-restore.spec.ts`, "the outlooks queued transactions had survive a crash after the local acknowledgement…", on a one-node mesh with the gate closed. Queued: conversation `c1` (natural key), conversation `c2`, a message under `StampId()` referencing `c1`, and conversation `c3` copied from `c1` by key (`insert … select … where id = 'c1'`, a `row`-scoped read). It checks:
- On disk: the message's entry record carries one fresh key in the Messages collection, the foreign-key decision on `{ schema: 'main', table: 'conversations' }`, and `complete: true`. (The ticket put this check in `offline-journal.spec.ts`. I folded it in here to avoid a second mesh setup for the same record. Move it if you prefer.)
- After crash + `hydrate`: every restored outlook deep-equals the pre-crash one, except the copy's `dependsOn`, which widens from `[c1]` to `[c1, c2]` (its read is matched by table now). This pins the widening.
- The same records with `outlook` stripped (copied into a fresh `PowerLossKVStore`; the plugin refuses a `MemoryKVStore` journal) restore the message `exposed` on its own key with `dependsOn: []` and `unchecked: 'not-computed'`.

I mutation-checked the `encodedKeys` empty-rows guard: with it disabled the copy restores with `dependsOn: []` and the test fails.

## For the reviewer

- **Edge cases checked by reading the code, not by tests:** a record in doubt with facts (the facts apply the same; they describe the entry, not its attempt); `offline:outlook-regressed` (unchanged); a journal that refuses the entry record (`enqueue`'s existing `finally` drops the facts); two labels over one store (the facts live inside the entry record, so they follow the label).
- **`forgetUnqueuedFacts` guards on `queue.status(id) === undefined`.** Every throw out of `OfflineQueue.restore` leaves the entry unregistered (`stageRestored` → `unregisterRestored`, or it was never registered), so the guard should never hold facts back. It is there so the rule "facts are held while the queue lists the transaction" holds even if that changes.
- **`decodeFacts` trusts the record's shape.** It does not validate, matching `versioned` in offline-journal.ts ("this build wrote it").
