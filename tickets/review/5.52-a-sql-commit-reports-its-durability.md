# A SQL commit reports its durability — review handoff

GitHub issue #26 (gap: the SQL layer dropped db-core's durability answer). The follow-up `a-sql-commit-learns-when-it-becomes-fully-held` (implement/, prereq on this slug) builds on the surface below.

## What was built

`register(...)` returns `onCommitDurability(listener): () => void`. After a SQL commit that wrote something, once the bridge has torn its transaction down and before `commitTransaction` returns, every listener is called synchronously, in registration order, with a frozen `SqlCommitDurability`:

- `transactionId` — `TransactionState.stampId`, i.e. what `StampId()` returned inside the transaction.
- `durability` — a `TransactionDurability` (fresh copy of the map, via `transactionDurability`).
- `tables` — per `schema.table`, the table's collections folded with `transactionDurability(...).overall` (so `undefined` when any of its collections is unknown — the same rule as `overall`).

Per route:

- **Session** — `commitSession` (extracted verbatim from `commitTransaction`) returns `ExecutionResult.durability`.
- **Batch** (two or more staged trees on one transactor) — `commitBatchLegacy` returns `coordinator.commit(...)`'s answer.
- **Sweep** (the single-table write, and the fallback) — each `tree.sync()` result folded with db-core's `recordCollectionDurability`, keyed `getCollection()?.id ?? treeLabel(tree, i)`; an `undefined` result adds no key. `PartialCommitError` gains a 4th constructor argument `durability` built the same way from the trees persisted before the failure.
- Any route answering `undefined` (nothing written) → no report, no listener call. Zero listeners → the report is not built.

Table names: `registerCollection(collection, table?)` records `collection.id → Set<"schema.table">` (`collectionTables`). A set, not a single name, because two tables declared over one URI share collections (the `legacy-batch-shared-collection-id` configuration); a write to either lists both, which is true at the storage level. `forgetTree` drops the entry together with the registry entry. The vtab's four registration sites go through a new private `registerTree(tree)` that passes `${schemaName}.${tableName}`.

Listener discipline: snapshot of the set per delivery; a throwing listener is logged on the `txn-bridge` debug namespace (`commit:durability-listener-threw`) and the next still runs; unsubscribe is idempotent (same pattern as `StorageRepo.onAnyCollectionChange`).

## Decisions a reviewer should weigh

- **db-core barrel change.** The ticket listed `durability.ts` as consumed-not-changed; `recordCollectionDurability` was not exported, so `packages/db-core/src/transaction/index.ts` now exports it (the function itself is untouched). The alternative was re-implementing the merge in the plugin.
- **`DirtyTree.sync` is now `Promise<WriteDurability | undefined>`.** The ticket expected test doubles resolving nothing to still satisfy it; they do not — `async () => {}` infers `Promise<void>`, which `tsc` rejects. The four doubles in `adapter-integration.spec.ts` were changed to `async () => undefined` rather than widening the type to include `void`.
- **Delivery sits after the try/catch** in `commitTransaction`, so nothing a listener does can reach the rollback/degraded-latch catch. If `sqlCommitDurability` itself threw (only possible if db-core broke its "collections never empty" contract) it would escape an acknowledged commit; not guarded.
- **Listener-throw logging uses the debug logger**, which is silent unless the namespace is enabled — consistent with `StorageRepo`'s listener isolation, but a host that never enables logging will not see it.
- **Not re-exported:** `isFullyDurable` — the README example imports it from `@optimystic/db-core`. The error classes are re-exported from both entries so hosts need no db-core import to catch them; the reviewer may want the same for this predicate.
- **For the follow-up ticket:** `reportCommitDurability` returns early when no listener is registered, so an internal consumer (the planned durability follower) must register through `onCommitDurability` or that early-return must account for it.

## Tests (one new spec, `test/sql-commit-durability.spec.ts`, in-memory `test` transactor)

- single-table insert in an explicit transaction (sweep route) → one report; collections exactly `['sqldur/single']`; `overall` present; `tables` exactly `main.Single`, equal to `overall`; `transactionId` equals `select StampId()` taken inside the transaction.
- table with a secondary index, autocommit insert (batch route) → one report with both the main and `…/index/idx_indexed_cat` collections, one table `main.Indexed`.
- session-mode insert (setup copied from `session-mode-commit.spec.ts`'s `enableSessionMode`) → one report with the coordinator's collection under `main.Sess`.
- `select` in its own autocommit → no report.
- a throwing listener registered first → the insert succeeds, the second listener still gets the report, the row is readable.

Asserts presence and shape, not a quorum class (the `test` transactor decides it).

Not covered by a test (by inspection only): the `PartialCommitError.durability` arm, two tables over one collection id appearing together in `tables`, a collection with an unknown class making its table's entry `undefined`, unsubscribe.
