# A SQL commit learns when it becomes fully held

GitHub issue #26, gap 3 (and sereus GH #44's "not yet delivered" mark). Builds on `a-sql-commit-reports-its-durability`.

## What landed

- `register(...)` returns `onCommitFullyHeld(listener): () => void`. The listener gets `{ transactionId }` once per followed commit when every block it wrote below full replication is held by its whole cohort. Same discipline as `onCommitDurability`: synchronous, registration order, a throwing listener is logged and the rest run, idempotent unsubscribe. Both now share two module-level helpers in `txn-bridge.ts` (`addListener`, `notifyListeners`).
- `SqlCommitDurability.followed: boolean` — `true` when `onCommitFullyHeld` will fire, or when the commit is already fully held (that case is "saved now" and is never reported again).
- `DurabilityFollower` (no SQL or libp2p in it). `follow(transactionId, durability, { selfPeerId, notifier })` returns one of four verdicts:
  - `held`: `overall` is fully durable. Not registered.
  - `unfollowed`: `overall` is absent, something is `torn`, there is no notifier or peer id, a below-`full` collection has no `blockRevs`, a collection mixes `full` and below-`full` cohort answers, or a below-`full` answer's `recordedBy` is not this node. The reason goes to a debug line, `follow:unfollowed reason=…`.
  - `covered`: every owed block was already reported by an event that arrived before the commit's answer did.
  - `pending`: registered.

  A commit owes the `blockRevs` of its below-`full` collections. An event `{ blockIds, rev }` covers an owed `(block, r)` when `rev >= r`. `coverHeld(durability, notifier)` treats every collection a later commit wrote at `full` as an event for its blocks.
- `CollectionFactory.getBlockDurabilityNotifier(options)` returns `node.storageRepo` when it passes the `isBlockDurabilityNotifier` check, for the `network` transactor only. Every other transactor gets `undefined`.
- Bridge flow in `reportCommitDurability`:
  - It runs when either listener set is non-empty. This answers the prereq review's note: a host with only `onCommitFullyHeld` is still followed.
  - Order: follow, build the report with `followed`, deliver it, then call `onCommitFullyHeld` if the verdict was `covered`. The report always reaches the host before the fully-held call.
  - Then `coverHeld` runs whatever the listeners.
- Caps, each with a `NOTE:` tripwire at the site: 10 000 pending commits (the oldest is dropped, and a `follow:evicted` line names the transaction), and 4 096 remembered events per notifier.

## Where this departs from the ticket (reviewer: check these)

- **When the subscription starts.** It starts in `beginTransaction`, before the commit is sent, not on the first followed commit. Subscribing lazily on the first followed commit would miss an event that fires before that subscription exists. The first followed commit per node would then hit exactly the race the remembered-events record is meant to close. Cost: one listener on the node's `StorageRepo` for the plugin's life, on `network` transactors only.
- **Who releases the subscription.** `TransactionBridge.dispose()` releases it, and `plugin.dispose()` now calls that before `CollectionFactory.dispose()`. The follower owns the subscription; the factory only resolves the notifier. If the factory owned it, a factory dispose would leave the follower believing it was still subscribed. Consequence: `collectionFactory.shutdown()` on its own does not stop following. The README "Closing down" section now tells hosts to call `plugin.dispose()` as well (both are safe to call twice).
- **State is kept per notifier.** The remembered events and the block → waiting-commits index are separate for each node. A header block's id is its collection id, so two nodes in one plugin can share a block id, and one node's event must not cover another node's commit.
- **`covered` is reported by the bridge, not the follower**, so the fully-held call can come after the commit's report (see above). The ticket allowed either.

## Tests added (`test/durability-follower.spec.ts`)

- "decides which commits it can follow": a table of the `pending`, `held` and every `unfollowed` case. The unfollowed cases are another node's ledger, no ledger, torn, unknown holders, no `blockRevs`, mixed cohort answers, and no notifier.
- "clears a superseded write with the event for the write that superseded it": commits at X@5 and X@7, then one event at X@7 clears both. This also covers two commits waiting on one block.
- "remembers an event that arrives before the commit it covers, at that revision only": event X@5, then a commit at X@5 is `covered` and a commit at X@7 is `pending`. An event at X@6 covers nothing; X@7 clears it.
- "waits for every collection of a commit (a table and its index)".
- "clears a pending block when a later commit writes it at full replication, without an event" (`coverHeld`).

Checked by reading only:
- The pending cap's eviction (I wrote a test for it, then removed it because the ticket did not ask for one).
- `dispose`.
- A listener that throws (shared helper).
- That a failed commit is never followed: both partial-commit errors throw before `reportCommitDurability`, as before.

## Known gaps

- **No end-to-end run over real nodes.** Nothing here shows `followed: true` from a real `network` transactor followed by `onCommitFullyHeld` firing. The plugin's own `createLibp2pNode` uses `clusterSize: 1`, and I did not confirm what a reporter-shaped setup (a node injected through `registerLibp2pNode`) answers. If a reviewer wants that run, build it on `packages/db-p2p/test/util/two-machine-lifecycle.ts`.
- **`followed: true` is not a promise.** A commit dropped by the pending cap, by `dispose()`, or by a restart is never reported. The README and the docs say so; restart is backlog `feat-a-host-can-ask-whether-an-earlier-commit-is-fully-held`.
- **Hosts that register listeners late.** With no listener of either kind, commits are not followed. A host that registers `onCommitFullyHeld` later hears nothing about commits made before it registered.
- **Mixed cohort answers.** A collection whose blocks got `full` from one cohort and below `full` from another is refused. Only a group wider than one cohort can produce that; lifting it would need `blockRevs` to say which cohort answered for each block.
