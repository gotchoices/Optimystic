# Review: blob transfer is measured

## What was done

- **New bench** `packages/db-p2p/test/bench-blob-transfer.mjs`, in the style of `test/bench-findcluster.mjs` (imports `../dist/src/index.js`; header comment with what it measures, how to run it, and the result). Not a mocha spec; runs in no script. Run as `yarn build && node test/bench-blob-transfer.mjs` from `packages/db-p2p` (`N` env var, default 5).
  - Two nodes over loopback TCP with the options the ticket named, memory piece stores (the default). B dials A; it waits until each lists the other in `keyNetwork.peersServing(buildBlobProtocol('/optimystic/bench-blob-transfer'), …)`, and before each read until B's `findCluster(routingKeyForBlob(ref))` includes A.
  - Sizes 1, 3 and 16 MiB of fresh `randomBytes` per repetition. A puts; B reads with `for await (… of b.blobs.read(ref))`, timed from the first call to the last chunk; wire = delta of `b.blobs.wireBytes()` sent + received across the read. Reports medians.
  - Beyond the ticket: it also times A's `put` (reported apart from the transfer, so the doc's comparison with the row path is fair), and splits the overhead into list-piece bytes (computed by running `buildBlob` over the same content apart from both nodes) and the rest (frame headers and length prefixes). It prints each read sample so warm-up can be judged.
  - Nodes are stopped in a `finally`; the process exits 1 on failure.
- **docs/blobs.md §What this answers in GitHub #63**: the "expected cost" paragraph was replaced by a measured-results paragraph with a per-size table (put ms/MiB, transfer ms/MiB, wire bytes per MiB, overhead, list pieces, frames), the machine (AMD Ryzen AI 9 HX 370, Windows 11, Node 24.2.0), the date and the command, and three bullets: time against the 0.2 to 0.3 s/MiB row path and #63's 1.7 s/MB (with what each figure does and does not include), space against the 2.75 to 4 times (legacy) and 5.3 to 6 times (session) expansion, and the overhead.

## Results (5 runs, one of N=9)

| Blob | put ms/MiB | read ms/MiB | wire B/MiB | overhead B/MiB |
|---|---|---|---|---|
| 1 MiB | 1.2–1.6 | 9.0–10.5 | 1,049,234 | 658 |
| 3 MiB | 1.0–3.6 | 5.5–7.1 | 1,049,116 | 540 |
| 16 MiB | 1.4–1.6 | 5.5–6.6 | 1,049,077 | 501 |

- The wire overhead is **more than the "few kilobytes per 45 MiB" the doc expected**: about 22 KB per 45 MiB (about 125 bytes per 256 KiB piece). The doc says so and names the bytes: about 50 per piece for its link in a list piece, about 75 for the `get` header naming it by its 59-character id in JSON, its answer flag and its 3-byte length prefix, plus 52 bytes of fixed header per `get`. I checked this by modelling the frames from `encodeBlobHeader` (one `get` for the root, then one per 16 data pieces). The model matched the measured counts to the byte at all three sizes. The modelling script was a throwaway and is not in the tree.
- Warm-up: the first read of each run took about twice the others (16 to 18 ms for 1 MiB against about 9). The median of 5 absorbed it: dropping the first sample did not change the median by more than about 1 ms. So no warm-up read is discarded, and the bench header says so.

## For the reviewer

- **Comparison framing.** The doc says the transfer is 19 to 55 times cheaper than committing a value in a row. That ratio compares different work: the row figure includes consensus and both machines storing the value, while the transfer leaves out the small reference-row commit, copying to the blob's cohort (not built yet) and disk. The doc states both sides of that. Check that the wording does not overclaim.
- **Range breadth.** The ranges come from five runs on one machine that was running other work; the 3 MiB put has two high values (3.1 and 3.6). These are reported, not smoothed away.
- **Possible reviewer cut.** The extra columns (put time, list/frames split, samples) go beyond the ticket's spec. Trim them if they are judged noise.
- **Line not touched.** The "a list piece is a few kilobytes" line in §References and pieces still stands. A full list piece of 174 links measures about 9 KB at about 52 bytes per link, extrapolated rather than measured. I left that line alone.
