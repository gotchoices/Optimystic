# Review: commit proofs moved out of the transactions keyspace into their own store

## What changed and why

A node stores two different kinds of record per block: the **transforms** that make up its
history, and the **commit proofs** that certify particular revisions. Both used to live in the
transactions store, separated only by a naming convention — a proof for revision *N* was filed
under a made-up action id `~proof:<N>`, on the assumption that no real action id starts with `~`.

Nothing enforced that assumption. An action id is chosen by whoever originates a write and is
never re-derived or format-checked by the node that stores it, so a client's `pend` or a peer's
restore archive could name that exact id. Whichever write landed second won, silently.

**Proofs now have their own logical store**, keyed by `(blockId, rev)` — the same key shape the
revisions store already uses. There is no key a transform and a proof can both name, so the
collision is unrepresentable rather than guarded against. `blockProofActionKey` and its
reserved-namespace doc block are deleted.

## The shape of the change

`RawStoreDriver` gained two methods — `getProof(blockId, rev)` / `putProof(blockId, rev, value)`
— and `KvRawStorage.getBlockProof` / `saveBlockProof` delegate to them instead of building an
action-id key. Nothing in `IRawStorage` changed; the public storage surface was already
`getBlockProof(blockId, rev)` / `saveBlockProof(blockId, rev, proof)`.

Per-backend layout, each following that backend's existing convention:

| backend | proofs store |
| --- | --- |
| memory | a sixth `Map`, keyed by `revisionKey` (blockId, rev) |
| filesystem | `basePath/<blockId>/proofs/<rev>.json`, JSON-valued (takes the corrupt-content-as-missing read guard), atomic write |
| SQLite | a `proofs (block_id, rev, value)` table, same primary-key shape as `revisions`, with its own prepared get/save |
| LevelDB | `TAG_PROOFS = 0x06` and `proofKey(blockId, rev)` using the same 8-byte big-endian rev suffix as `revisionKey` |
| IndexedDB | a `proofs` object store with a `[blockId, rev]` compound key, created in the guarded `upgrade` hook; `DEFAULT_DB_VERSION` bumped 1 → 2 |

`RawStorageDriverAdapter` delegates to the inner storage's `getBlockProof`/`saveBlockProof`,
re-encoding across the byte boundary the way its sibling methods do.

**No `deleteProof`** — matching the pre-existing contract: `RawStoreDriver` has no revision delete
either (invalidations write compensating forward revisions), and a proof lives and dies with its
revision record. The contract note was carried across from `i-raw-storage.ts` onto the new store's
doc comment.

**No data migration.** `AGENTS.md` states backwards compatibility is not yet a concern; proofs are
advisory retention, so losing ones already written under the old key degrades to corroboration,
which is an already-supported state.

## Deliberate behaviour change to check

`CachedStoreDriver` passes proofs **straight through** to the inner driver — no sixth cache
namespace. Proof reads happen on repair and archive-serving paths, not the hot read path, and a
namespace that is never populated cannot go stale. Previously proofs were *incidentally* cached
(they rode the transactions cache), so this is a real, small change: a proof read now always
reaches the backend. Parked as a `NOTE:` tripwire at the passthrough
(`cached-store-driver.ts`) — *if proof reads ever show up hot, give proofs their own cache
namespace alongside `transactions`.*

Consequence worth a reviewer's eye: `READ_METHODS`/`WRITE_METHODS` in
`test/support/cache-test-helpers.ts` deliberately **exclude** `getProof`/`putProof`, so the
cache-hit-ratio assertions do not count a store the cache does not claim to serve. The counting
driver still records them, so a future test can assert on the counts directly.

### New parity coverage — `src/testing/raw-storage-conformance.ts`

Proofs had **no** conformance coverage at all before, so this is new parity ground every backend
now has to satisfy. Six cases: a miss reads `undefined`; a proof round-trips; proofs are per-block
and per-revision; a later save replaces only that revision's proof; **a transaction named
`~proof:<N>` and the proof for revision N do not collide, in either arrival order**; and
`saveBlockProof` snapshots (a caller mutating the proof object afterwards cannot corrupt stored
state).

### New regression spec — `test/proof-keyspace-isolation.spec.ts`

Drives the reproduced arrival orders through the real `StorageRepo` / `BlockStorage` surface:

- **Order A** — commit an action literally named `~proof:5`, then retain a proof for revision 5;
  the committed transform survives. A second case asserts the user-visible fallout is gone: a
  later client pending against the stale revision gets a catch-up response whose rev-1 entry
  carries the **real** insert, not the empty transform the bug produced.
- **Order B** — retain the proof first, then commit the colliding action; the proof survives.
- **Order C** — a peer-supplied revision (`saveReplica` → `saveRestored`) naming `~proof:5`
  leaves a retained proof intact.
- **Fourth route** — the one the original bug report missed, which needs no transactions write at
  all: `materializeBlock` feeds a revision's action id back to `getTransaction` when replaying a
  revision whose materialization was pruned. Two revisions are written (rev 2 named `~proof:5`),
  rev 2's materialization is dropped, and the read must replay rev 2's own transform onto rev 1's
  materialization rather than consuming the proof.

## Known gaps — treat these as the starting points, not settled ground

- **The regression spec runs only against `MemoryRawStorage`.** The cross-backend claim rests
  entirely on the conformance suite's collision case, which asserts at the `IRawStorage` level
  (`saveTransaction` + `saveBlockProof`), not through `StorageRepo`/`BlockStorage`. A reviewer may
  reasonably want at least one backend-level end-to-end pass.
- **No test asserts the cache passthrough.** The `CachedStoreDriver` proof methods are exercised
  only incidentally, by the conformance suite running over the cached compositions
  (`cached-raw-storage.spec.ts`, `shared-cache-pool.spec.ts`). Nothing pins "a proof read reaches
  the inner driver every time" — if someone later adds a proofs cache namespace without coherence
  rules, no test fails.
- **The IndexedDB version bump is untested against a pre-existing v1 database.** The `upgrade`
  hook is guarded by `objectStoreNames.contains`, and the spec's harness opens a fresh
  uniquely-named database per case, so the v1 → v2 upgrade path itself is never executed. The
  guard makes it safe by construction, but that is an argument, not a test.
- **`blockEnvelopeRange` and per-block sweeps were checked, not re-tested.** In the LevelDB
  backend `blockEnvelopeRange` is used only for `TAG_PENDING`, so `TAG_PROOFS = 0x06` needs no
  change there — but that is a read of the current call sites, and a future per-block sweep would
  have to include the new tag.
- **The SQLite `proofs` table is `CREATE TABLE IF NOT EXISTS` with no `user_version` bump.** That
  matches the surrounding tables exactly (the existing NOTE in `db.ts` already documents the
  no-migration stance), so an existing database gains the table on next open — but the
  `DEFAULT_DB_VERSION` there is still 1 while the web package's went to 2. That asymmetry is
  deliberate (SQLite DDL is idempotent; IndexedDB needs a version bump to run `upgrade` at all),
  and worth a second opinion.
- **`storage-repo.ts`'s N² proof-size NOTE was only re-worded**, not re-measured. The measured
  figure it cites (~4.6 KB for a 10-peer 2-block commit) is unchanged by this work.
