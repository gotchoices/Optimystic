GitHub #54. The reproduction spec `packages/db-p2p/test/an-interrupted-write-does-not-wedge-the-collection.spec.ts` was red at HEAD (phase 3 refused `conflict=true` naming run 1's dead action) and now passes whole, all five phases. Its entry was removed from `tickets/.pre-existing-known.md`.

## What was built

The rule is the one the implement ticket specified, with no departures from its design: a pending record is **abandoned** when three facts hold, all recorded by the node at the moment it saved the record.

- **The writer ran in this node's process.** `NetworkTransactor.pend` and `pendMany` set a new non-wire field, `MessageOptions.localWriter: true`, on a pend sent to the repo of the transactor's own `localPeerId` (`localWriterMark`, keyed on the peer each batch actually goes to, so a batch re-homed by a retry carries no mark). `RepoClient` copies only `expiration` onto the wire and `RepoService` builds options from the message, both confirmed by reading them, so a remote writer cannot set it.
- **The node applied the pend alone.** `CoordinatorRepo.pendSolo` hands the writer's options through to `StorageRepo.pend` unchanged. The one other site that threads options into storage, the coordinated path's fallback apply (`!localExecuted` in `pendThroughCluster`), now strips the mark through `withoutLocalWriter`, so a record a cohort decided is never stamped. The fix ticket named `pendSolo` as the only threading caller; that fallback was the second, and is now explicitly excluded.
- **The run that saved it is over.** `StorageRepo` mints `runId` at construction (12 random bytes, base64url; `StorageRepoOptions.runId` overrides it for tests) and `pendUnderLatches` pass 2 stamps it into a third sibling metadata map, `BlockMetadata.pendingRuns`, written, dropped and swept by the same `recordClaim` writes as `pendingRevs` and `pendingBases`, and read back as `PendingClaim.localRun` by `claimOf`. A record with no entry is simply unstamped; metadata from the release before the field reads unchanged.

`isAbandonedClaim(claim, currentRun)` in `pending-claim.ts` is the predicate: stamped, and stamped with a run other than the current one. `isReservationAgainst` is untouched. Both rival scans ask abandonment first: `StorageRepo.pendUnderLatches` pass 1 sets abandoned records aside (logged `pend:abandoned-claim`) instead of counting them as reservations, and pass 2 deletes each one under the same latch hold, before saving the newcomer's record for that block (deleted on a satisfied block too). `ClusterMember.reservingRivals` skips them at the vote (logged `cluster-member:validation-pending-abandoned`), reading the current run off `IPendingClaimReader.runId`, which `StorageRepo` now exposes; a claims reader without a run id judges nothing abandoned.

`IBlockStorage.savePendingTransaction` changed shape: the three claim values now travel as one `PendingClaimFields` object (`{ rev?, baseRev?, localRun? }`) ahead of the latch, instead of two positional values. Every call site reads `savePendingTransaction(id, transform, { rev: 2, baseRev: 1 }, latch)` now; the compiler named only the two `IPendingClaimReader` test doubles beyond the spec call sites.

## Each case the ticket asked about

- **Offline restore.** Unchanged by construction: a re-pend of the same action by the new run overwrites the record, its claim and its stamp (pinned at the storage layer by the redelivery case in `block-storage.spec.ts`), so a restored in-doubt entry's record is live again. Nothing was added to `docs/offline-sync.md`; the restore reads the log, never a pending record.
- **A remote writer through this node.** Never stamped; pinned by the first new `storage-repo.spec.ts` case (a record pended without the mark still refuses a newcomer from a repo with a different run id, and is left standing).
- **A multi-member cohort.** A coordinated write's records carry no stamp (consensus apply passes no options; the coordinator's fallback strips the mark). The one multi-member shape the rule reaches, a record stamped while the node was alone and met after a second member joined, is handled as the ticket described: this node's member votes approve, and the approved pend's apply here deletes the record.
- **Own-action retry and a same-run rival.** Overwrite on re-pend; a same-run stamp is judged by the slot rule like any other record. Phase 4 of the mesh spec and the "still holds for a record stamped with the current run" vote case pin the comparison.
- **A host that rebuilds its node in one process while keeping the old transactor.** Recorded as a `NOTE:` at `StorageRepo.runId` and at `isAbandonedClaim`, not guarded against: no host in this repository does it.
- **`stop()`.** Nothing changed about how long it takes or what it cancels. `docs/repository.md` now says a process exit before `stop()` resolves no longer wedges a one-machine group, and still strands the record on the other members of a larger cohort.

## Tests, each beside what it verifies

- `an-interrupted-write-does-not-wedge-the-collection.spec.ts` (existing, was red): the whole fix end to end on the mesh, including phase 4's same-run rival still refused.
- `storage-repo.spec.ts`, new describe "a record an earlier run of this node left for its own writer is abandoned": (1) a record pended without the mark is not stamped and still reserves against a later run; (2) a stamped record from an earlier run is deleted, its claim and stamp dropped from the metadata, and the newcomer's pend lands reporting no rival.
- `block-storage.spec.ts`, existing base-claim cases extended rather than new cases: the run lands in the same metadata write as slot and base, both readers join it, delete drops it, a redelivery without a run drops the earlier stamp, and a promotion's sweep leaves only the live record's run.

## Known gaps and things worth a reviewer's eye

- **The consensus fallback strip is a negative action** (`withoutLocalWriter` at the `!localExecuted` apply in `CoordinatorRepo.pendThroughCluster`). Forgetting it on a future apply path would stamp a coordinated record; the consequence is bounded (the writer is still provably dead, so the deletion is still correct), but it would cut the other members' copies off from this node's agreement on the record. No test pins the strip, since no existing harness reaches the fallback arm; a reviewer may want one or may judge the comment enough.
- **`IPendingClaimReader.runId` is required**, which makes every `implements IPendingClaimReader` double declare one. Two test doubles did. A decorator wrapping `StorageRepo` for the member's seam would need to forward it, as it already must forward `listPendingClaims`; none exists today.
- **The deletion runs on every block of the pend, satisfied blocks included.** Reasoned as harmless (the judgement does not depend on what the pend writes); flagged because the ticket's text said "before saving the newcomer's record for that block" and a satisfied block gets no save.
- **`pendingRuns` is not swept by `sweepDeadClaims` on its own key**, like `pendingBases`: a rev-less pend that was stamped would leave an entry the slot-driven sweep cannot see. No production caller sends a rev-less pend; the `NOTE:` on `pendingBases` in `struct.ts` was widened to cover both sibling maps.
- **No GitHub #54 comment was posted.** The runner's commit is the trigger; a human should post the one-line note naming the rule (abandoned-reservation judgement on a one-machine group) and the release it lands in.
- The backlog ticket `debt-unpromotable-pending-records-need-a-sweep` already carried an arm describing exactly this design, written by the fix stage; the implementation matches it, so it was left as is.
