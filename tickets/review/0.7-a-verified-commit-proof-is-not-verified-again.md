# A verified commit proof is not verified again — review handoff

Reported as GitHub #68 (Sereus/cadre on React Native). Built as the plan ticket specified; no design deviations.

## What changed

- **`verifyBlockCommitProofClaim` is split in two** (`packages/db-p2p/src/cluster/commit-proof.ts`). The private `verifyProofVotes(proof, thresholds)` holds every check that does not depend on the claim — version, structure, duplicate signers, membership digest, message hash, both rounds' signatures, both thresholds — in the original order with its own `try → malformed-proof`. `verifyBlockCommitProofClaim` takes the votes verdict through `judgeProofVotes`, returns it on failure, and then always runs the claim step (`findClaimedCommitOp`) on the **live** proof, inside one outer `try → malformed-proof`. Votes still come first, so a forged proof for the wrong claim still reports the non-attributable `malformed-signature`.
- **The memo key is the proof's own JSON text**: `` `${superMajorityThreshold}|${simpleMajorityThreshold}|${JSON.stringify(proof)}` `` — native serializer, no replacer, no hash. A miss verifies `JSON.parse(body)`, never the live object, so the remembered verdict is a function of the key alone. When `JSON.stringify` throws or returns a non-string (`proofText`), the live proof is verified with no memo, as before.
- **`VerdictMemo<V>`** (`packages/db-p2p/src/cluster/proof-votes-memo.ts`, no crypto): concurrent calls with one key share one in-flight promise (removed in a `finally`; `compute` is started on a microtask so the removal can never precede the insertion even if `compute` throws synchronously); only verdicts `retain` accepts are kept (for proofs, `ok: true`); retained keys are bounded by summed length (1 MiB) with a 64 KiB per-entry cap, least recently used evicted first, a hit refreshing recency. One instance per process, module-level in `commit-proof.ts`. The `NOTE:` tripwire on the class covers churn by a peer minting valid self-certified proofs.
- **Never memoized**: the claim step; the content digest in `verifyBlockCommitProofContent`; failing verdicts; `certifyClaim` / `certifyContent`'s `exceedsSignerCap` (still first) and `anchorAcceptedProof` / `onUnanchored` (still on every accepted call). `certified-claims.ts` is untouched; `MAX_PROOF_SIGNERS`' doc still reads true, so it was left alone.
- **Docs**: the doc comments of `verifyBlockCommitProofClaim` (snapshot semantics, memo, caller obligation #2 restated for hit and miss) and `verifyBlockCommitProofContent` (digest step not memoized); the cost `NOTE:` above `certifyClaim` in `CoordinatorRepo.queryClusterForLatest` (it used to propose this cache); three paragraphs in `docs/internals.md` §Durable commit proof after the verification bullets.

## Measured (Node only)

Node 24.2.0 on Windows, a 3-signer proof of 1.7 KB decoded from JSON before each call, medians of 400 calls after 100 warm-up, three runs (a throwaway script against `src` through the package's ts-node loader, deleted afterwards): miss 1.44–1.53 ms, of which the added stringify + parse is 0.011 ms; hit 0.008 ms. The reporter measured 0.77 ms per verify on their machine, so this machine is roughly twice as slow; compare within the row. Hermes was **not** measured — the hit path deliberately contains no JS replacer and no JS hash, which is what the reporter's Hermes profile flagged; confirmation is left to the reporter on GitHub #68.

## Tests added

- `packages/db-p2p/test/commit-proof.spec.ts` — "a remembered pass is never reused for a changed proof or another claim": verifies a genuine proof (pass, remembered), then JSON round-tripped copies with (a) a changed message under the untouched `messageHash` → `message-hash-mismatch`, (b) one changed promise signature (first character flipped, since base64url's last character can be padding-only) → `malformed-signature`, (c) the untouched proof for another revision → `claim-not-in-message`, (d) the untouched proof for its own claim → passes with the same `declaredDigest`. Pins that a hit cannot alias a different proof or claim.
- `packages/db-p2p/test/proof-votes-memo.spec.ts`, counting fake `compute`: (1) concurrent and repeated calls with one key compute once while retained; concurrent calls share one computation even when not retained; a non-retained verdict is computed again; (2) the character budget evicts the least recently used key, a hit refreshes recency, a key over the entry cap is never retained and evicts nothing.

## Things for the reviewer to push on

- **Soundness argument** (the heart of it): the votes verdict reads only things inside the key's text, and a miss verifies exactly that text. Check `verifyProofVotes` reads nothing outside `proof` and `thresholds` (it calls db-core hashing and `@libp2p` key parsing only), and that the claim step's use of the live proof cannot be fooled by a live object whose JSON differs from what `findClaimedCommitOp` reads (only possible for non-JSON-faithful in-process objects — accepted and documented).
- **Shared module-level memo across all nodes and tests in a process.** Sound because the verdict is pure in its key; no existing spec failed, but a future spec that counts signature verifications (e.g. stubbing `publicKeyFromRaw`) would see hits from earlier specs. There is no reset hook; add one only if such a test appears.
- **Per-call cost that remains**: every call still does one native `JSON.stringify` of the proof, linear in its size — up to the 8 MiB frame for a padded proof under the signer cap, which is also never retained (over 64 KiB). Same order as before for such proofs; the existing `MAX_PROOF_SIGNERS` `NOTE:` already names a serialized-size bound as the remedy if that path ever matters.
- **`canonicalMessageBytes`' `WeakMap` memo in db-core** is now filled for a parsed copy that dies after the miss; harmless, noted in the plan.
- Pre-existing, outside this ticket: `docs/internals.md` §Durable commit proof says proof failures "are never a reputation signal", while `isAttributableProofFailure` in `certified-claims.ts` does penalize the attributable ones. Not touched here.
