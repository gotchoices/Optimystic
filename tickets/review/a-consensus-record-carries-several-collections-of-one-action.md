# A consensus record carries several collections of one action — review handoff

First of three tickets for GitHub #42 (siblings: `a-coordinator-runs-an-actions-collections-as-one-record`, `a-transaction-pends-and-commits-its-collections-together`). This one is the cohort-member side only: what a member does when a record's message carries more than one operation. No sender builds such a record yet, so production behaviour for one-operation records must be unchanged.

## What was built

- **The shape.** `RepoMessage.operations` is now `[RepoOperation, ...RepoOperation[]]` (`RepoOperation` is the named element union). The doc on the field states the **batch** rule: all `pend` or all `commit`, one action id, no block id in two operations. `batchShapeFault(operations)` in `record-operations.ts` is the one implementation; it returns prose or `undefined`. A single operation passes; an empty list also passes *this* check on purpose, because the membership admission gate already refuses an operation-less record with a signed vote (`cluster-membership-admission.spec.ts` "refuses with affected=0…" pins that, and a throw here would have replaced the vote).
- **Refusal.** `ClusterMember.validateRecord` throws `Malformed batch: …` right after the message-hash check and before signature validation — a fault of the record, like the digest/hash/signature faults, not a vote.
- **Pend fold.** `applyConsensusPends` applies each pend operation (`applyConsensusPend`, which still retains/retires per-block refusals exactly as before) and retains `foldPendResults(results)`: success only if every operation succeeded (blockIds union, pending concatenated, durability via `mergeDurability`); otherwise the first conflict-shaped refusal, else the first refusal. A single result is returned unchanged.
- **Commit fold.** `executedCommitResults` now maps messageHash → `{ operations: CommitOperationVerdict[], folded }`; the old `behindCommitRefusals` set is gone — "behind" is now per operation (`isBehindRefusal`). `getExecutedCommitResult` and `withOwnApplyOutcome` read `.folded`. Prune, rollback and `dispose` lost the extra set.
- **Cert and proof once per record.** `applyConsensusCommits` calls `captureConsensusCommitCert` (one `computeCommitHash`, one capture, keyed by the shared action id) and `consensusCommitProof` (one `buildBlockCommitProof`) before the first operation's storage commit, then applies each operation with the same proof. `CommitCertStore.get` does not consume, so the one cert resolves for every collection's change event.
- **Reconcile.** `reconcileRefusedCommit` reconciles only the operations whose own verdict is a behind refusal (in parallel, via `reconcileCommitOperation`), keeps the "never resurrect a pruned/rolled-back retention" identity guard, and re-retains the fold. `retainCommitVerdicts(record, operations, previous?)` reports block holders only for operations that newly succeeded.
- **Other readers.** `ClusterClient.recordCoordinatorForRecordIfSupported` records a hint for every operation's first block. `LatePendRefusals` (`pendsOf`) now groups a record's pends by action and unions their blocks — before, the per-operation loop filtered out the previous operation's entry (same peer + messageHash) and kept only the last collection's blocks. `mayDeferPendDelivery`'s first doc bullet now explains why a batch pend record is still safe to defer. `findClaimedCommitOp` (commit proofs), `validateCommitAgainstRefusedPend`, `validateCommitRevisions`, `validateCommitBaseDeclarations`, `validateCommitOperations`, `operationsConflict` and `recordPriority` already loop or union correctly — checked by reading, unchanged.
- **Renames.** The old `applyConsensusOperation` is gone (split as above); every doc and comment that named it now names the function that does the thing it described.

## Deviation from the ticket's test plan (please weigh)

The plan put the rival on the **second** collection's tail. With the old last-operation-wins retention that test would have passed anyway (the last operation is the refused one). I put the rival on the **first** collection — the "first refused, second accepted" edge case the plan says the test covers. Confirmed: with `foldPendResults` sabotaged to return the last result, the case fails; with the real fold it passes.

## Tests

- `packages/db-p2p/test/cluster-member-batch-record.spec.ts` (new), real `ClusterMember` over real `StorageRepo`, hand-signed v2 two-member records (hash recipe taken from db-core's `computeCluster*Hash`, not re-implemented):
  - *refuses the whole pend record when one collection is refused, and then the whole commit record* — rival placed after this member's promise vote and before it applies; `getExecutedPendResult` is a conflict naming the rival; the two-collection commit record then gets a `reject` promise vote with the `refused pend` reason. Pins the pend fold and the deferral-safety property.
  - *commits every collection of a commit record and answers success* — both tails hold the action at their own revisions (2 and 5); `getExecutedCommitResult` is a success. Pins the batch commit path (cert/proof once, per-operation apply). It does not discriminate the commit fold's refusal arm — see gaps.

## Known gaps, for the reviewer to judge

- **Commit fold refusal arm, behind-only reconcile, mid-loop throw rollback, redelivery reconcile**: inspection only, no test. A cheap discriminating test would be a two-operation commit where this member never saw one collection's pend (behind, no reconcile callback): the fold must be a refusal; old code would have answered success.
- **Slot holds for a batch** grant on the first stale operation's blocks only — parked as a `NOTE:` at `noteStaleLoss` (conditional: only matters if aged multi-collection writers starve).
- **Dispute over a batch** reverses only the first collection: `DisputeService.extractInvalidationTarget` returns the first commit operation, and the certificate binds one target. Real latent defect on a dormant path (disputes are off, nothing sends batches); appended as an arm to backlog `feat-dispute-subsystem-live-activation` (§ "A dispute over a batch reverses only its first collection") with a pointer `NOTE:` at the site.
- **Proof size** grows per collection: `NOTE:` at `buildBlockCommitProof`. The per-block byte figure there is an estimate from field sizes, not measured. The ticket's suggestion "trim the proof to the claimed operation" is not a drop-in: verification recomputes the message hash from the carried message, so trimming needs a per-operation hash structure — the NOTE says so.
- **A batch pend whose first operation is refused still pends the later collections** in storage (the apply loop does not stop). Same as today's separate records: the writer's cancel removes them. Not changed.
- **Ingress**: `RepoService` still serves `operations[0]` only; the next ticket adds `batchShapeFault` there.
- **Mixed builds** in one group are out of scope (an older member folds nothing); nothing sends a batch until the third ticket.
