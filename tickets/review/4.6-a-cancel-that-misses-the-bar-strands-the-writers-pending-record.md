# A cancel that misses the approval bar strands the writer's pending record — implemented

Reported by sereus (sereus-sam, 2026-10-12) on 1.13.0; their write-up is `C:\projects\sereus\tickets\blocked\optimystic-failed-cancel-strands-the-writers-pend-record.md`.

## The defect, briefly

At three members the promise bar is all three, so one silent member sinks every cluster transaction — the write's commit and then every round of the cancel that should discharge its pend (a cancel is itself a cluster transaction). `NetworkTransactor.dischargeCancel` threw, the caller let the commit's error win, and the cancel was forgotten. When the member returned, nothing re-sent it, and every member holding the record voted `held` on every later write to the block, from any machine.

Why re-sending is safe (settled in the implement ticket, restated in docs/repository.md): a promise-round shortfall proves the commit applied nowhere, and in any case a cancel deletes only its own action's pending records and never moves a revision, so it commutes with every other action. The one unsafe late cancel is one sent after the writer has re-pended the **same action id** — which only the writer can see, hence the fix sits in the writer's transactor.

## What was built

`OwedCancels` (`packages/db-core/src/transactor/owed-cancels.ts`), one per `NetworkTransactor`:

- **Recording.** `dischargeCancel`, when it runs out of rounds/deadline, records the blocks still outstanding (`cancel:owed`, with the root cause as `why`) right before it throws. When any cancel for an action is answered — the full loop or a re-send — those blocks leave the owed set (`cancel:owed-discharged`, with re-send count and how long it stood). `dischargeCancel` still throws as before, so callers' verdict-ordering is unchanged.
- **Before every pend** (`NetworkTransactor.pend` → `beforePend`): first, a pend of an owed action **supersedes** the owed cancel for every block it names — those blocks are removed synchronously (`cancel:owed-superseded`) and any re-send of that action already in flight is awaited, so it lands before the pend. Blocks of the old attempt the new pend does not name stay owed. Then every OTHER owed action naming any of the pend's blocks gets **one** re-send (a single `cancelRound`, bounded by `abortOrCancelTimeoutMs`, not the six-round loop); concurrent callers join one in-flight re-send per action. A re-send that falls short is logged (`cancel:owed-retry-short`) and the pend proceeds as it does today.
- **Timer.** One timer per transactor, armed only while something is owed and not already being re-sent, at the earliest due entry. Per-entry backoff: `jitteredBackoffMs` with base 1 s, cap 30 s, exponent = re-sends so far. Retries for the transactor's life. Unref'd via `armUnrefTimer` (guarded `unref`, so browsers/React Native are fine); injectable through `NetworkTransactorInit.owedCancelClock` (`{ now?, setTimer? }`, the `ClusterCoordinatorClock` shape).
- **Bounded.** 256 actions; the oldest is evicted with `cancel:owed-evicted` (blocks and age), since eviction re-opens the wedge.
- **Diagnostics.** `NetworkTransactor.owedCancelBlocks()` returns a snapshot (action → blocks still owed), so an embedder about to drop a transactor can see what it would leave standing. Not on `ITransactor`.

`unrefTimer` moved from db-p2p to db-core (`packages/db-core/src/utility/unref-timer.ts`, exported from the db-core root); db-p2p's `src/unref-timer.ts` re-exports it so its fourteen import sites are untouched. This is what the NOTE beside `NO_TIMER_UNREF` in `eslint.config.js` prescribed for the first db-core timer needing `unref`.

## Known gaps and things for the reviewer to weigh

- **The pre-pend re-send costs one cancel round on every pend that overlaps an owed cancel while the cohort is still short.** That is up to `abortOrCancelTimeoutMs` (5 s default) per pend in the worst case of a coordinator that hangs rather than refuses; in the reproduction the refusal is fast. The ticket chose this trade (a cohort that cannot approve the cancel cannot approve the pend either); worth a look.
- **A late cancel can still delete a same-action re-pend through a path the writer does not see:** the coordinator's commit-retry timer / `takeOwedRecords` can deliver a cancel's consensus record to a member that missed it, after the writer has re-pended the same action id. That hazard predates this ticket (any self-cancel followed by `Collection.syncAttempts`' same-id retry has it) and is not widened here, but supersession only orders the writer's own sends.
- **No dispose.** The owed set and timer live as long as the transactor; there is no `stop()`. In tests, a transactor left owing cancels keeps re-sending (unref'd, so the process still exits) until the cancel lands or the process ends. No suite showed interference. If an embedder wants a clean shutdown, `owedCancelBlocks()` reports what would be left; a `dispose` was not added because nothing calls one today.
- **In memory only.** A restarted writer forgets what it owed — the remainder recorded on backlog `debt-unpromotable-pending-records-need-a-sweep` (arm appended).
- **Cross-transactor:** two `NetworkTransactor` instances in one process do not share owed sets. Harmless while action ids are minted per writer per sync; noted only because supersession relies on the same transactor seeing the re-pend.
- `owed-cancels.ts` logs on db-core's existing `network-transactor` namespace (deliberately — one `DEBUG` pattern covers the whole cancel story); documented in docs/debugging.md.
