# A block id is used as a file path without validation

## What changed

A block id is the name of one stored item, and the filesystem backend uses it raw as a relative path. Nothing validated one anywhere, so a peer naming a block `../escaped` made this node write a file outside its own store. Both arms of the ticket's repro were re-run against the new code and both are closed; see *Validation* below for the before/after I measured.

**The rule lives in db-core, alone.** `packages/db-core/src/blocks/block-id.ts` is new: `isValidBlockId(id): boolean`, `assertValidBlockId(id): void` throwing `InvalidBlockIdError`, and the rule stated once in the doc comment with the reason for each clause. A block id is valid when it is a non-empty string; holds no C0 control character and no `\u007f`; holds no backslash (on win32 `\` is a path separator, so a `/`-split check alone misses `a\..\..\b`, which resolves to `C:\b`); does not start with a Windows drive prefix; and every `/`-separated segment is non-empty and is neither `.` nor `..`. The leading-`/` case the ticket lists separately falls out of the empty-segment clause, which the comment says so a reader does not think it is missing. Both exports are re-exported from `packages/db-core/src/blocks/index.ts`, which the package barrel already picks up.

`BlockId`'s stale `// base64url encoded (256-bit random)` comment in `structs.ts` is now a doc comment saying what a block id actually is — a random base64url id **or** a human-named `/`-separated collection path — and pointing at the validator.

**`KvRawStorage` enforces it, in one place.** A new private `checkedId(blockId)` asserts and returns, and all 18 `this.driver.<op>(blockId, …)` forwards now name `this.checkedId(blockId)` — reads included. The class doc comment gained a paragraph stating both inspection greps, in the shape `block-latch.ts` uses, with the escapes that keep the comment from matching its own pattern. I ran both and they hold: `grep -rnE "this\.driver\.[a-zA-Z]+\(blockId" packages/db-p2p/src` returns nothing, and `grep -rnE "implements\s+IRawStorage" --include=*.ts --exclude-dir=dist --exclude-dir=test packages` returns exactly the one line for `KvRawStorage`. The second grep is a change from what the ticket sketched: it is a stronger and much less fragile check than enumerating driver constructor names, because every shipping backend and the read cache `extends` this kernel rather than implementing `IRawStorage` itself.

**The write-ahead log guards a recorded path, not a block id.** `FileWriteLog.applyBatch` now resolves every entry's path through a new `containedTarget` before applying any of the batch, so a record naming a path outside the store applies none of itself — exactly as a torn or CRC-bad record does. It throws a module-local `WriteLogEscapedPathError`; `replaySegment` catches that one type, logs, and returns `'stopped-short'`, which is the existing stop semantics: what precedes the record applied, the rest is discarded, the open succeeds and the store serves normally. The comment states both reasons this guard is not a second owner of the rule — a store written by a pre-fix build can hold such a record and replays it on every open until a checkpoint truncates it, and a log damaged or forged on disk can name anything. `path.join` became `path.resolve`, which is the primitive that actually handles an absolute or drive-relative entry path (`join` would have produced a nonsense `<store>\C:\…`).

**Two comments updated, no behaviour.** `FileBatchBackend.blockPath`'s doc comment no longer claims to own the rule or point at this ticket; it names `KvRawStorage` as the owner and says the guard stays as a backstop because `deleteBlock` removes that directory recursively. `released-block-ledger.ts`'s NOTE now cites the kernel assert instead of `blockPath` (the old reasoning was false — a pend write did escape) and is tagged `accepted tradeoff` with a revisit condition, since the declined guard is a deliberate call.

**Docs.** `packages/db-p2p/docs/storage.md` gained `### 7. A block id reaching a backend names a location inside the store`, in the shape the other six use (rule, where enforced, what breaks), plus what it does **not** address — ids that alias another block's *store* directory, which stay the separate limits noted at `BLOCK_STORE_DIRS`. The "These six properties" line is now "seven".

## Tests

Four, as the ticket specified, each a different behaviour. The boundary table is in db-core only; no backend restates it.

- **`packages/db-core/test/block-id.spec.ts`** — the rule's edges, in three table-driven cases plus one for the error type. Accepts `default/app/Ledger`, `a`, a base64url-shaped id, `a..b`. Rejects `''`, `'..'`, `'../escaped'`, `'a/../..'`, `'/abs'`, `'C:/elsewhere'`, `'C:elsewhere'`, `'a\\..\\..\\b'`, `'a//b'`, `'./a'`, `'a/./b'`, `'a/'`, and a NUL-bearing id — and a non-string, which the declared type does not rule out at a network boundary. This is the one place the rule is pinned.
- **`packages/db-p2p/src/testing/raw-storage-conformance.ts`** — one case, one id: a pend under `../escaped` rejects with `InvalidBlockIdError`, a *read* of the id rejects too, and a later `saveMetadata` + `flush` + read still works. That last assertion is the point of refusing above the write group: a throw from inside a `commit` would have latched the store failed. One case covers all five backends and every wrapper composition, which is why it is here. Needed a small local `rejection()` helper — this file has no chai-as-promised, and the existing precedent is hand-rolled try/catch.
- **`packages/db-p2p-storage-fs/test/file-storage.spec.ts`** — a new `describe` over a store nested in its own root: after a refused pend, `readdir` of the store's parent holds only `store`, and the log holds only the legitimate record. The conformance case asserts the rejection; this asserts what is (not) on disk, which only this backend can.
- **`packages/db-p2p-storage-fs/test/file-write-log.spec.ts`** — a log hand-built from `WRITE_LOG_HEADER` + `encodeWriteLogRecord` with a legitimate record, then one naming `../escaped/pend/tx-abc.json`, then another legitimate one. On open: nothing outside the store, the first record applied, the third discarded, and a `commit` after it lands — the store opens and serves normally.

The existing `deleteBlock` rejection loop in `file-storage.spec.ts` now asserts `/does not name a location inside the store/`. **This was a deliberate choice, not a message tweak to get green:** the kernel guard fires first for all five of its ids, so asserting the kernel's wording is what keeps the test honest about which guard actually runs on the node path. Its `describe` comment says so, and says the backend guard survives underneath as a backstop. All five ids are rejected by the rule on both platforms (`''`, `'..'`, `'../sibling'`, `'held/../..'`, and an absolute `path.resolve(os.tmpdir(), …)` — which is caught by the drive prefix on win32 and the empty leading segment on POSIX).

## For the reviewer

Honest gaps and judgment calls, in the order I would check them.

- **A refused id now throws where some backends used to answer `undefined`.** Before this change, a read of an escaping id returned `undefined` on the memory/sqlite/leveldb/indexeddb backends (the fs backend already threw from `blockPath` for metadata reads). It now rejects on all five. I did not trace what `StorageRepo.get` / the request handlers make of an `InvalidBlockIdError` reaching them from a peer request — whether it is classified as a hard failure a caller stops retrying, or falls into a generic bucket. Refusing the request is the correct semantics and the ticket chose it deliberately, but the *shape* of that refusal on the wire is unverified. Worth a look at `packages/db-p2p/src/storage/storage-repo.ts` `get`/`pend` error classification.
- **The two win32 tripwires are recorded as `NOTE:`s at the validator, but one of them is NOT what the ticket said.** The ticket asserted `path.resolve` trims a trailing space from a segment on win32, so `a ` and `a` would alias. I measured it on this machine (Windows 10, Node 25) and it does not: `path.resolve` preserves the trailing space, and writing a file `a ` leaves `a` at ENOENT, because libuv opens paths in the `\\?\` long-path form, which bypasses Win32 path normalization. So it is neither an escape nor an aliasing bug in the store — it is a name ordinary Windows tooling (Explorer, non-long-path-aware tools) cannot address. The NOTE now says that, with the measurement. The colon tripwire *does* hold, and I measured its mechanism too: `mkdir` of a colon-bearing directory fails ENOENT, which is why a block id with a colon fails noisily (the layout mkdirs a block's directory before writing into it); a bare `writeFile` to such a path would instead succeed as an NTFS stream on the prefix file.
- **`commitProofRelativePath` was the other peer-supplied path input I checked.** It is already safe and I changed nothing: it percent-encodes every character outside `[A-Za-z0-9_-]`, and `saveBlockProof` demands a verified proof whose `messageHash` is re-derived (`computeClusterMessageHash`), so the hash is not attacker-chosen. Mentioned so a reviewer does not have to re-derive that it is out of scope.
- **The sealed-segment cost of a refused record.** When the *sealed* segment stops short, `replay()` already discards the current log with it, so a pre-fix store whose sealed segment holds an escaped record loses the current log's legitimate records too. That is the existing bargain the `NOTE:` in `replay` states for a damaged sealed segment, and the new doc comment on `replaySegment` says it applies here as well. I judged consistency with the existing stop semantics worth more than a special case; say if you disagree.
- **Not addressed, by design:** ids that alias another block's store directory (`x/revs`, `x/blocks/y`). The `NOTE:`s at `BLOCK_STORE_DIRS` and on `deleteBlock` are untouched, and §7 of the storage doc says the validator does not reach them.
- **`FileBatchBackend` driven without the kernel** (a spec, or a future caller) is outside the enforcement point; the kernel's class comment says so explicitly. The log's containment check happens to cover the write path there too, as the repro re-run above shows, but it latches the store rather than refusing one call.
