# A below-floor block answer earns a retry against a different coordinator — review

## What landed

The prerequisite (`refreshed-collection-caches-a-block-older-than-its-log-entry`, now in `complete/`) gave a collection a per-block **floor**: after a refresh walks a log entry saying "revision *r* changed block X", a read of X at a context at or above *r* must come back materialized at *r* or later, and an answer under that floor is never kept in memory. It could not, however, ask anybody else — one `ITransactor.get` was all a `TransactorSource` could make, so against a lagging coordinator the old row was still *returned* until the read-repair window expired.

This ticket lets the asker's floor reach the transactor and turns a below-floor answer into one more reason to consult a second coordinator. Four changes:

- **`BlockGets.floors?: Record<BlockId, number>`** (`packages/db-core/src/network/struct.ts`) — per block, the lowest revision the asker will accept. A **client-side hint that never goes on the wire**: `NetworkTransactor.get` builds its own `{ blockIds, context }` for every downstream `IRepo.get`, so no peer and no coordinator freshness decision sees it, and an `ITransactor` that ignores it (`TestTransactor`, the reference peer's) stays correct because `TransactorSource` still judges the merged answer.
- **`TransactorSource.tryGet` fills it** from `BlockFloorCheck.applicableTo(id, context)` — the side-effect-free lookup the prerequisite already exposed — and omits the field entirely when the block has no applicable floor, so an ordinary read's request shape is byte-for-byte what it was.
- **`NetworkTransactor.get`'s `isAuthoritative` fails a below-floor entry**, so it earns the same single second-chance round (coordinator excluded) that `unavailable` and `unconfirmedAheadRev` earn. Only a **block-carrying** entry can be below a floor; an absent answer is judged by the existing rules, which keeps the single-round `createOrOpen` probe off the retry path.
- **The merge breaks ties on the newer content.** A confirmed block ranks 6 whatever revision it is and only a strictly greater rank replaces, so the stale first answer would have beaten the fresh one its own retry fetched. `beats(candidate, held)` now orders by rank first and, at equal rank with both entries carrying a block, by `servedRevision`. The `NOTE:` above `rankOf` that predicted this ("If peers are ever seen to disagree here, break the tie on the HIGHEST `materialized.rev`") has been rewritten to describe what was done and why the tie-break stays *inside* a rank.

When every reachable coordinator is below the floor, the highest revision anyone served comes back **unflagged** — no throw, no `unconfirmedAheadRev`. That is deliberate and falls out of the merge: a refused write can leave its log entry behind while its blocks never take that revision anywhere, and then the below-floor content is the correct content.

## Use cases to check

**The motivating failure.** Reader B refreshes past a write, picks *itself* as coordinator for the changed data block, and serves its own revision-6 copy from inside the read-repair window while machine A one hop away holds revision 7. Before: B returns the old row (uncached, so the next read re-asks — which is all the prerequisite could promise). Now: the floor rides out on the read, B's own answer fails `isAuthoritative`, the second-chance round re-resolves the coordinator with B excluded, A answers at 7, and the merge keeps 7. The reader sees the new row on the **first** read after the refresh.

**An ordinary read must cost exactly what it did.** No floor on the request ⇒ one coordinator round, first answer stands, no second peer consulted. `network-transactor.spec.ts` › "costs an ordinary read nothing" is the same two peers and the same two answers as the retry case, with only the floor removed.

**An abandoned log entry must stay readable and writable.** A floor no machine can meet (`refresh-below-floor.spec.ts` › "an entry whose blocks never landed…") must not start throwing now that a retry exists. It costs one extra round per read and then returns the content.

**Multi-block batching.** A floor on one block must not drag an already-answered batch into a retry. Note the honest limit below: `TransactorSource.tryGet` asks for **one** block at a time, so nothing in-tree produces a multi-block `floors` map — only the spec does.

## Known gaps — please probe these

- **The collection-level case runs against a hand-written double, not the real `NetworkTransactor`.** `TwoReplicaTransactor` re-implements the rule it is testing (read `gets.floors`, re-ask, prefer the newer answer). It pins that *a collection driving a floors-aware transactor gets the new row on the first read*, which is the property the ticket asked for, but the double and `NetworkTransactor.get` can drift apart with nothing catching it. `network-transactor.spec.ts` covers the real merge and retry separately; nothing covers the two joined. Standing up `Collection` over a real `NetworkTransactor` over two `NetworkSimulation` repos was judged out of scope here — worth a reviewer's call on whether that is a `debt-` ticket.
- **The tie-break now applies to *every* `get`, not just floored reads.** Two peers answering one read with content at different revisions previously resolved to first-arrival; they now resolve to the newer content. That is what the old `NOTE:` prescribed and the failure direction is safe, but it is a behaviour change on the ordinary read path and deserves an adversarial look.
- **Tripwire recorded, not fixed:** `servedRevision` falls back to `state.latest` when a producer omits `materialized`, and on a pinned read that number overstates. Every in-tree producer populates `materialized`, and `belowFloor` reads the same number so the two stay consistent — but a third-party `IRepo` that omits it could win a tie with a revision describing content it did not serve. Parked as a `NOTE:` above `beats` in `network-transactor.ts`, with the remedy (cap both comparisons at `blockGets.context.rev`) and the condition that would trip it. A capped comparison was deliberately *not* added: it is extra machinery in a distributed read path for a currently-dormant producer shape, and that is a call worth a reviewer weighing rather than me making quietly.
- **Nothing tests that the field stays off the wire.** It is structural — `NetworkTransactor.get` constructs a fresh `{ blockIds, context }` per downstream call — but it is read off the code, not asserted. A one-line assertion in a db-p2p repo-client spec would make it a property rather than a reading.
- **The multi-block `floors` path has no in-tree producer.** `TransactorSource.tryGet` asks for one block per request, so the map never has more than one entry in practice. The spec exercises it; a future batching read source would be its first real user.
- **Costs are unmeasured**, as the ticket said they would be. A reader whose own replica lags pays one extra request per changed block per refresh while it lags. A log entry whose blocks never landed pays the first request *and* the retry round on every read of that block until it is next written. The prerequisite's tripwire `NOTE:` at `TransactorSource.mayRetain` was extended to name the retry round rather than a second note being added. On an isolated node the retry re-picks the same node (`findCoordinator:all-excluded`), the same bounded extra consult today's flagged-entry case already pays.
- **No log line is emitted when a retry succeeds.** `collection:block-below-floor` is reported from `mayRetain`, which runs on the *merged* answer, so a read that was repaired by the retry leaves no trace at all. Correct — the answer met the floor — but it means the retry is invisible in the field. Consider whether the reviewer wants a line for it.
