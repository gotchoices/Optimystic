# Verified reading of blob piece trees — review handoff

The reader side of blobs, network-free, in `packages/db-core/src/blob/`. Everything reaches pieces through an injected `PieceSource` (`blob/pieces.ts`). A list piece is written by whoever made the blob, so this is the code that faces hostile input.

## What was built

- **`verify.ts`** — `checkPiece(id, bytes, digest, ref?)`: size test first (`> MAX_BLOB_PIECE_BYTES` → `piece-too-large`, no hashing), then the digest against `cidOfPiece(id).multihash.digest` (`digest-mismatch`). `checkPieceSize` is the size test alone, for a `verified` source. This is what the fetcher (`feat-blob-pieces-move-between-machines`) calls per received piece.
- **`list-piece.ts`, decode half** — `decodeListPiece(id, bytes, ref?)` → `{ children: [{ id, kind, fileBytes }], totalBytes }`, the only function that interprets dag-pb bytes. Checks in the ticket's order: dag-pb decode → `malformed-encoding`; no `Data` / non-file type → `not-a-file-node`; UnixFS unmarshal throws → `malformed-encoding`; inline data → `list-carries-data`; 0 links → `no-links`; > 1024 → `too-many-links`; block-size count ≠ link count → `size-mismatch`; per link: codec → `unsupported-codec`, hash → `unsupported-hash`, size 0 → `empty-child`, raw child declared > 1 MiB → `piece-too-large`; bigint total > `MAX_SAFE_INTEGER` → `size-too-large`. The two `NOTE:`s (filesize not read; absent UnixFS type read as file) are on it, plus a why-comment at `empty-child`. Also exports `PieceKind` (`'data' | 'list'`) and `pieceKind(id)` (kind off the codec), used by the reader and useful to the fetcher.
- **`reader.ts`** — `planBlobRange`, `readBlob`, `readBlobSize`, `walkBlobPieces`, with `BlobRangePiece`, `BlobWalkEntry`, `BlobReaderOptions`, `BlobRangeOptions`. All share one private `PieceLoader` class (get → `not-here` when absent → `checkPiece`, or `checkPieceSize` when `source.verified` → for a list piece `decodeListPiece`, declared-size check, then `too-deep` at depth ≥ 8 with any list child, before any child is requested; for a data piece the declared-size check). `planBlobRange` and `readBlob` share one private generator (`planPieces`) that carries the raw root's already-loaded bytes, so a raw root is fetched once. Range arguments are validated before any request (`RangeError` on first `next()`); `offset > size` → `RangeError`; empty ranges yield nothing; past-the-end is clamped (compared, not summed, so `offset + length` never overflows). Descent is lazy and depth first, so a fault part way stops the read with nothing past it yielded.
- **Exports**: `blob/index.ts` re-exports `verify.js` and `reader.js`.
- **Docs**: `docs/blobs.md` status line updated; §References and pieces now has a rewritten **Verification** paragraph (what exists, the bounds with their constants, the two decisions — inline data and zero-size children are malformed, and why the second matters — that `filesize` is not read, and what a fault and a range read do), and the builder's sentences moved to a **Building.** paragraph. §Extending toward a file system cites `walkBlobPieces` and `decodeListPiece`. `yarn lint:docs` passes.

## Deviations from the ticket — please judge

- **The walk's repeat key includes depth.** The ticket keyed on id (plus the covered slice at range edges). The depth bound judges a list piece by where it sits, so with an id-only key a list piece met first shallow and later deep would not be re-walked at the deeper position, and the walk could accept a tree `readBlob` refuses as `too-deep`. Keying on `(id, depth, slice)` makes the two agree, at most ×8 set size. The `NOTE:` at `TreeWalk.met` says so.
- **Absent list pieces are deduped too.** The set records list pieces *met* (yielded), present or absent, not only those expanded, so a repeated absent piece is reported once per key rather than once per position.
- **One loader class, not one `loadPiece(id, kind, declaredSize, depth)` function.** `PieceLoader` has `root`/`tryRoot`/`list`/`tryList`/`data` over one private `fetch`; every rule lives in it once.
- **Two extra malformed rows** beyond the ticket's list: "UnixFS data that does not decode" (`malformed-encoding`) and "a dag-pb piece with no UnixFS data" (`not-a-file-node`) — both are spec'd branches.
- **A raw root's walk does not judge `offset > size`**: the walk never hashes or sizes a data piece, so it does not know a raw root's size (the entry's `fileBytes` is absent, as the ticket's `BlobWalkEntry` doc says). Stated on `walkBlobPieces`.

## Tests (`packages/db-core/test/blob-reader.spec.ts`)

One 175 × 262,144 + 1-byte blob is built once in a `before` (root over a 174-leaf and a 2-leaf list piece). Sources are `Map`-backed `MapSource`s recording every `get`; digest calls are counted with a wrapper passed only to the reader.

- *reads a built blob back whole, hashing each piece once* — whole read equals the content; digest called 179 times.
- *hashes nothing through a verified source* — same read, `verified: true`, digest never called.
- *plans and reads …* (7 rows) — empty range, range at the end, past-the-end clamped to 10 bytes, inside one piece, across a data-piece boundary, across a list-piece boundary, everything after an offset: planner piece count, and `readBlob` yields exactly the content slice.
- *refuses … with RangeError* (3 rows) — offset past the end (root requested), negative offset and fractional length (nothing requested).
- *requests only the path of a range across a list-piece boundary* — planner gets exactly root, both list pieces; reader gets root, first list, its last leaf, second list, its first leaf, in that order.
- *names the piece a source lacks* — `BlobUnavailableError`, `not-here`, the missing leaf's id.
- *walks around an absent list piece without reading data pieces* — the absent list piece is `present: false` with its declared size, its children are not yielded, `get` never called for a raw piece (source has `has`).
- *a malformed tree is refused as …* (18 rows) — each malformed shape of the ticket's list plus the two above; asserts the reason and that a piece below (or after) the fault is never requested; the oversized-piece row also asserts the digest was called only for the root.
- *walkBlobPieces expands a repeated list piece once* — root linking one list piece 1,024 times: walk yields root, list piece, leaf, and the list piece is requested once.

`test/blob-content.ts` (new) holds the `i % 251` content helpers that `blob-builder.spec.ts` used to define privately; the builder spec now imports them.

## Known gaps (by inspection only, per the ticket)

- `readBlobSize` has no test.
- The walk with a range (pruning, and the two edge-cut repeat keys) is untested.
- "A verified source still bounds list pieces" is shown only by code reading: the verified round trip asserts no hashing, not that a malformed list piece is still refused.
- A source whose `get` throws or aborts propagates unchanged — inspection.
- CIDv0 links inside a list piece re-spelt as v1 — inspection (`pieceIdOfCid`).
- `readBlob` over a tree that repeats one list piece fetches and checks it at every occurrence (cost bounded by declared size × depth, as the ticket accepts); there is no memo.
