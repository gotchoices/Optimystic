## What changed

`NetworkTransactor.get` (`packages/db-core/src/transactor/network-transactor.ts`), after the merge and the second-chance round, now splits the blocks that have no entry:

- **Unanswered** — no batch in the tree whose payload carries the block got any response (every one threw, timed out, or was still in flight at the deadline). The block is returned as `{ state: {}, unavailable: 'peers-unreachable' }`, the shape `CoordinatorRepo` uses for its own flagged absents, and logged `get:unanswered blockIds=… root=…` (root = first batch error, else the round's error). The read's other blocks are returned as answered.
- **Omitted** — some coordinator responded (any `isResponse`, including a null/empty response) and left the block out. Protocol fault; the `Some peers did not complete` aggregate is thrown exactly as before (still logged `get:missing`).

"Responded" is decided by `respondedBlocks`, which is the cancel path's former `dischargedBlocks` made generic over the response type (same body, renamed; `cancelRound` uses it unchanged). Flagged entries are added after the merge, so they never compete with a real answer in the ranking.

The `NOTE:` in `refreshLive` (`packages/quereus-plugin-optimystic/src/optimystic-module.ts`) is replaced by one line saying the transactor types this failure, so `isCohortUnreachableRead` now absorbs it.

## Consumer audit (direct readers of a transactor `get`)

All already check `unavailable` before concluding anything from an empty entry; no code fix was needed:

- `TransactorSource.tryGet` → `answeredBlock` throws `BlockUnavailableError(id, 'peers-unreachable')`.
- `Collection.readLogEnds` → `answeredHeader` / `checkedLogTail` → `answeredBlock`. An unreachable *out-of-date* known tail (header names a different tail) is now just dropped instead of failing the refresh; the old `NOTE:` about that cost was removed.
- `Collection.readCommittedTails` / `readAttributed` / `readAlone` → `judgedTail` → `checkedLogTail`; a flagged block now fails only its own collection without the split fallback. Doc comment updated.
- `Collection.readLogTail` → `checkedLogTail`.
- `NetworkTransactor.getStatus` throws `BlockUnavailableError` on a blockless flagged entry before judging; `refineInvalidatedStatuses` runs only after that check, and its log reads go through `TransactorSource`.
- `getLineage` does not go through `get` (asks each cohort member's repo directly); its caller `settleUnfinished` is unaffected.
- Everything else in db-p2p / the plugin / reference-peer that calls `.get(` calls a repo (`StorageRepo`), not a transactor.

## Consequences (stated, not changed)

- **Classification.** A write whose refresh meets an unanswered block now sorts `cohort-unreachable` (wait) where the aggregate sorted `unknown`. Both keep a queued entry queued; in-doubt stays sticky via the drive record. `classifyCommitFailure`'s "never its `cause`" rule concerns the commit-phase aggregate, untouched.
- **Error text.** Such a read now throws `Block <id> is unavailable (peers-unreachable): …` from `TransactorSource` instead of `Some peers did not complete: …`. No spec matched the old text for a `get` (the only match, in `commit-failure-class.spec.ts`, is a commit-phase aggregate and is unchanged).
- **`createOrOpen` / `open` probe**: an unanswered header probe now throws `BlockUnavailableError` (already the documented behaviour for a flagged probe).
- **`completeOwnEntry`'s `getStatus`** now throws `BlockUnavailableError` rather than the aggregate when a block went unanswered; it propagates either way.
- **Mixed read**: if one block is omitted and another unanswered, the whole read still throws the aggregate (the omitted arm wins). Deliberate — a protocol fault fails the read.
