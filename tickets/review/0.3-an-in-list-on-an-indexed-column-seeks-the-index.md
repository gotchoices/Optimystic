GitHub #44 (kjeib), comment of 2026-11-03. A page of log entries filtered with `where lei.entry_id in (…31 ids…)` read all of `log_entry_items` and then did one lookup per row in each joined table. That took 7 seconds on the reporter's phone.

## What changed

**Which columns may be sought.** The index and primary-key trees compare raw bytes, and the engine does not re-check a filter a module claims. So a seek on a column where equal values can have different bytes loses rows. `seekCanBeTrusted` now declines any key column that has a non-BINARY key collation or a type with semantic ordering (`timespan`, `json`), for both `=` and `in`. A declined column stays a residual filter over a scan. This fixes three wrong results that plain `=` gave at HEAD:

| statement | stored | before | now |
|---|---|---|---|
| `city = 'abc'`, indexed `nocase` column | `ABC`, `abc` | `abc` | both |
| `id = 'abc'`, `nocase` primary key | `ABC` | none | `ABC` |
| `d = 'PT60M'`, indexed `timespan` column | `PT1H` | none | `PT1H` |

**Which filters are claimed.** `matchEqualitySeek` walks a key's columns and claims the first equality-role filter on each, which is the one the engine seeks on. `runtimeSet` filters are never claimed. A multi-value `in` is only ever the sole seek column. On a later column it ends the match and stays a residual, because of the engine defect in the `blocked/` ticket `quereus-composite-in-seek-drops-a-bound-equality`. So a primary-key list needs a single-column key.

**Cost and rows.** With `seek = log2(max(2, N)) * 2`:

- `rows = max(1, floor(min(N, K * perKey)))`.
- `cost = K * seek + rowTerm`, where `rowTerm` is `min(N, K * perKey)` for measured or unique seeks and `perKey` for the no-statistics constant.
- A primary-key list costs `K * seek`.

At `K = 1` this equals the old `=` cost. Multi-seeks report `isSet: false` and no `providesOrdering`. A primary-key list now competes on cost rather than exiting early.

**Running it.** A `plan=5` plan means one seek per argument, and `seekTuplesOf` throws on a `seekWidth` other than 1. `seekKeysInTreeOrder` drops NULL-bearing seeks, drops repeats and sorts. Both `executeIndexScan` and `executePointLookup` use it. Views are built once per scan, never once per value. The trace stays one `index:seek` line per scan, with `seek=` listing every key.

## Known gaps

- **No test exercises the primary-key repeat tracking in `executeIndexScan`.** Removing `yielded` leaves all tests passing. The ticket lists the update test against this, but the trace of that update shows `matched=3 rejected=0`: the engine finishes reading before its staged entries are visible, so no repeat arises. A live repeat needs a row to move in the gap between two seeks, because a scan that has yielded throws for a change between its steps. `db.exec` during an open `db.eval` on one `Database` blocks, so I could not drive that gap from SQL without mocking repository code. The guard stays as the ticket designed it, and the comment at the site says all this. Please judge whether it should stay.
- Multi-seek order is the tree's byte order, not the declared order for numeric or DESC keys. This is safe only because this module is not wrapped by Quereus's isolation layer. The `NOTE:` is at `seekKeysInTreeOrder`.
- I did not look at whether a `nocase` primary key enforces uniqueness across case. The trees key on raw bytes, so it may not. No claim either way.

## Differences from the ticket

- `equalityTupleSelectivity` is gone rather than kept as a wrapper, because nothing would call it. `measuredEqualityTupleSelectivity` replaces it as a module-level function.
- The partial-primary-key arm also skips declined columns, so a `nocase` key reads as a plain scan rather than a "partial" one priced at 0.3 N. The ticket did not ask for this.
- A point seek now claims only the first `=` per key column. It used to claim all of them and rely on the engine to reattach the rest.
- The `plan=5` arm has no `args.length > 0` check, so an empty multi-seek returns nothing rather than falling through to a scan.
- A repeat skipped by the tracking counts toward `rejected`, so `matched - rejected` stays what the scan returned. `docs/debugging.md` says so.
- `compareTreeKeys` is extracted so the sort and the tree share one comparator.
- With a measured `N = 0`, a unique seek costs `seek` rather than `seek + 1`, by the formula.
- The composite-`in` `NOTE:` is at `matchEqualitySeek`. The blocked ticket says `getBestAccessPlan`, its caller. Searching for the slug finds it.
