# SQL statements are built only when something reads them

Part of GitHub #63; the measurements and the split are in the completed ticket `a-consensus-record-is-serialized-once-per-delivery`.

## What changed

Quereus builds a SQL statement for each row a write touches (blobs as `x'…'` hex) whenever the vtab's `wantStatements` is true. Only a session-mode transaction reads those statements: they become its replicated record, which validating members re-execute. Legacy mode, the default, pends bare transforms and never read them. Building them was 12% of the CPU of an 8 × 256 KiB blob commit.

- `TransactionBridge.recordsStatements()`: while a transaction is open, `this.session !== null`. While none is open, `isTransactionModeEnabled()`, meaning the mode the next transaction will begin in.
- `OptimysticVirtualTable`'s constructor replaces `this.wantStatements = true` with a getter reading `recordsStatements()`, defined on the instance with `Object.defineProperty`. Quereus's `VirtualTable` declares `wantStatements` as a class field and builds for ES2022. Its built `dist/src/vtab/table.js` has the `wantStatements;` field, so a getter on our prototype would be shadowed. The comment at the site explains this.
- Quereus reads `vtab.wantStatements` per row at all four sites in `@quereus/quereus/src/runtime/emit/dml-executor.ts`: insert, update, upsert-update and delete. Nothing caches it per plan, so a host that configures session mode after a table opened gets statements from its next transaction.
- `addStatement`, `getStatements` and `getStatementCount` are unchanged. In legacy mode they now receive nothing.
- docs/transactions.md §Secrets and the replicated statement record now says when the statement is built and why.

## Deviation from the ticket's design: the no-transaction-open arm

The ticket specified `recordsStatements() = this.session !== null`. That rule drops a statement in session mode. Quereus asks for a row's statement before calling the vtab's `update()`. If the table's connection is not registered yet, it is `update()` → `ensureConnectionRegistered` → `joinConnection` → `begin()` that begins the bridge's transaction and creates the session. Under the literal rule, the first row is read with no session and gets no statement.

This happens when a table's first touch in a `Database` was a committed read. `initializeForCommittedRead` registers no connection, and a later live `connect` of the cached, non-fresh instance does not register one either. Verified, not inferred: under the literal rule the new test fails with 1 of 2 statements recorded. Because the record is what members re-execute, a missing statement makes their operation set diverge. It also moves the coordinator's pre-stage snapshot past the first row, which breaks session-mode rollback.

So while no transaction is open the answer is "session mode is configured". The worst case is a statement built for a row whose `update()` does not then begin a transaction, and `addStatement` drops it as before. A transaction already open keeps the mode it began in, so one open when session mode is configured records nothing, as the ticket asked.

## Tests

- **New:** `session-mode-commit.spec.ts` › "Session-mode statement record" › "records the row on which the table joins the transaction". A second `Database` hydrates, configures session mode, reads `committed.Notes` first, then inserts two rows. The test asserts the session's own record holds both statements in order. It fails under the literal `session !== null` rule (checked by patching the built output) and passes under the implemented rule.
- **Replaced:** `adapter-integration.spec.ts` › "statement accumulation". The case that said statements accumulate during an active transaction is replaced by "records no statement for a legacy-mode transaction's writes". It runs real insert and update statements through the engine and asserts `recordsStatements()` is false and the count is 0; the old code would have counted 3. The other cases in that describe call `addStatement` directly and test its clear-on-commit/rollback/begin lifecycle, which does not depend on mode, so they are unchanged.
- **Moved to session mode:**
  - `statement-secret-arg-redaction.spec.ts`: both cases read the session's own record through a local `enableSessionMode` helper.
  - `replicated-lane-ceiling.spec.ts`: one `QuereusEngine` over a real `TransactionCoordinator` serves as the session's engine and as the member's `laneCeiling`, and `replicated()` reads `getSession()!.getStatements()`.
- **Results:** `yarn build`, `yarn typecheck`, eslint on the touched files and `yarn lint:docs` are clean. The full plugin `yarn test` has 1385 passing, 0 failing and 14 pending (log: `tickets/.logs/sql-statements-built-only-when-read.test.log`). db-core is untouched, so its session tests were not re-run. No integration spec configures session mode.

## Bench (`test/large-value-commit-cost.bench.mjs`, in-process two-node mock mesh, memory storage, REPS=20)

| run | staging median (ms per MB) | commit median (ms per MB) | expansion |
|---|---|---|---|
| legacy, 8 × 256 KiB, before | 337 ms (169) | 1143 ms (572) | 3.50× |
| legacy, 8 × 256 KiB, after | 135 ms (67); rerun 119 ms (59) | 1180 ms (590); rerun 1102 ms (551) | 3.42×; 3.50× |
| legacy, 4 × 256 KiB, before | 168 ms (168) | 589 ms (589) | 3.34× |
| legacy, 4 × 256 KiB, after | 60 ms (60) | 546 ms (546) | 3.67× |
| session, 4 × 256 KiB, before | 162 ms (162) | 692 ms (692) | 5.67× |
| session, 4 × 256 KiB, after | 180 ms (180) | 722 ms (722) | 5.67× |

- Legacy staging falls by about 60%. Commit time and session mode are unchanged within run-to-run noise. Session mode still builds every statement, which is expected.
- Session mode at 8 × 256 KiB refuses every transaction as too large (9.34 MB), before and after, because of the hex statement in each collection's validation payload. That is why session mode was measured at 4 values.
- Legacy at 8 values sits near the 7.5 MiB limit. Some transactions were refused at 7.67 to 7.68 MB: 4 of 20 before, 0 and then 1 of 20 after. This is run-to-run variance from the random content, not this change, since statements never entered a legacy pend.

## For the reviewer

- The getter has no setter, so an assignment to `wantStatements` would throw in strict mode. Nothing assigns it today, in Quereus or the plugin. An assignment would be a bug worth hearing about.
- `debt-session-mode-bridge-coverage` (backlog) got a note: these specs now read the session's own record, which covers part of its Arm B first bullet. The slow-first-`applyActions` race and the rollback-ordering assertion are still open.
- Not changed, by design: session mode still carries each blob again as hex in every collection's validation payload. Ticket `a-large-write-is-measured-once-and-its-cost-is-documented` documents that.
