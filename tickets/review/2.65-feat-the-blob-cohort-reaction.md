# Review: the blob cohort reaction

The decision half of docs/blobs.md §Placement, copying and durability, *When the cohort changes*, landed as one class plus one record-door method. **No wiring** — nothing constructs `BlobCohortReaction` yet; `feat-a-held-blob-follows-its-cohort` (next ticket, sequence 2.66) runs the second `RebalanceMonitor` that feeds it, and carries the documentation for both halves. So the class is exported and tested but unreferenced in `src`, by design.

## What was built

**`packages/db-p2p/src/blob/cohort-reaction.ts`** (new). `BlobCohortReaction.handle(event: RebalanceEvent): Promise<BlobReactionResult>`, the blob counterpart of `BlockTransferCoordinator.handleRebalanceEvent`: same event in, same shape of feedback out, announcement instead of push and `stat` instead of push response. Module-level `createLogger('blob:copy')`, every import type-only or pure (`createLogger`, `admittedBy`, `MAX_BLOB_STAT_REFS`), exported from both entries.

Shared preamble, resolved once per event:

- **Partition** (`detectPartition()` true) → every non-empty `grown` entry gets `{ satisfiedPeers: [], complete: false }`, every `lost` reference is retained, `released` empty; `reaction:partition lost=%d grown=%d`, return.
- **Acceptance** in ONE `deps.acceptance(...)` call over the union of `event.grown`'s and `event.newOwners`'s peers with `selfId` removed. A rejection logs `acceptance:failed err=%s` and yields an empty record, so every peer reads `unknown` → accepting (errs toward keeping this node's copy).
- **Satisfiable without a request** = membership refuses it, acceptance is `refuses`, or the drain's `isDeclining` says so. Such a peer is owed nothing.

The two arms then run under `Promise.all`, each over at most `REACTION_CONCURRENCY` (4) references at a time; announcements within one reference go in turn.

- **`grown`**: scope is `records.responsibleScope(ref)` else `owed.get(ref)?.scope`; with neither, the reference is reported `{ satisfiedPeers: [...reported], complete: true }` and `grow:no-scope` logged. Otherwise each unsatisfiable-without-request peer is announced to; `whole`/`fetching`/`declined` satisfy, `not-responsible`/`unreferenced`/a rejection do not, and `declined` also calls `noteDeclined`. `complete` iff every reported peer is satisfied.
- **`lost`**: `responsibleScope` undefined → **no** entry in `released` or `retained` and no outcome (`release:not-responsible`), so the monitor's state is untouched. Candidates are `newOwners.get(ref)` deduped minus the satisfiable-without-request peers; `required = min(max(1, event.floor), candidates.length)`; `required === 0` retains (`release:no-accepting-owner`). Then the inverted **stat** step — peer → the references it is a candidate for, 4 peers at a time, chunked at `MAX_BLOB_STAT_REFS` (64) per request, a rejection or wrong-length answer array counting the whole chunk as not `whole` — then, per reference, an announcement to each candidate that did not answer `whole`. Released iff the `whole` count from the **stat** alone reaches `required`.

**`packages/db-p2p/src/blob/local-blob-service.ts`**. New `BlobResponsibleRecords` door beside `BlobOwedRecords` (`responsibleScope`, `responsibleRefs` — both pre-existing and unchanged — plus new `releaseResponsible`), implemented by `LocalBlobService`. `releaseResponsible` is `releaseOwed`'s mirror: `changeRecord` with a new `recordAfterResponsibleRelease` helper that returns the current record unchanged when there is nothing to release, then `records.flush()`.

- *releases a lost blob only once the floor of new owners answers `whole`* — floor 2, two accepting new owners. Verifies: the first pass (one `whole`, one `none`) retains rather than releases, announces to the non-`whole` owner only, and leaves the `responsible` scope on the record; the second pass (both `whole`) releases; and `releaseResponsible` — standing in for the caller's handler — then leaves `responsibleScope` undefined. This is the release count, the retain-on-short-count path, the announce-after-stat step and the new record door in one.
- *reports a grown blob complete only when every new peer is satisfied* — four new peers answering `whole`, `fetching`, `declined`, `unreferenced`. Verifies the answer-to-`GrowthOutcome` mapping: `satisfiedPeers` is the first three, `complete` is false, and `noteDeclined` recorded the third peer.

## Known gaps — treat these as the review's starting points

- **`release:unreachable` is a log line the next ticket's doc list does not name.** The release arm's announcement can reject, and the ticket named no log for it; swallowing it silently would have left a failed announcement invisible, so it is logged as `release:unreachable ref=%s peer=%s err=%s`, symmetric with `grow:unreachable`. `feat-a-held-blob-follows-its-cohort`'s `docs/debugging.md` edit lists eleven reaction lines and should list twelve. Flagging rather than editing docs here, since that ticket owns the `blob:copy` row.
- **An undecodable blob record fails the whole reaction rather than skipping one reference.** `responsibleScope` throws `BlobRecordFormatError` (unlike `durabilityOf`/`holdsWhole`, which read through `readableRecord` and tolerate it), and both arms call it per reference. Parked as a `NOTE:` tripwire on `BlobCohortReaction.scopeOf` — conditional, because no path in `src` writes a record this class could not decode, but if one is ever observed it would fail every check for as long as it is there. Reviewer's call whether that is a tripwire or a defect.
- **`BlobReactionResult.growth` is keyed by `string`, while `released`/`retained` are `BlobRef[]`.** As the ticket specified — the key feeds `RebalanceMonitor.recordGrowthOutcome(blockId: string, …)`, whose parameter is a plain id — but the asymmetry inside one result type is worth a second look.
- **`event.lost` and `event.grown`'s keys are cast to `BlobRef`** (`event.lost as BlobRef[]`, `ref as BlobRef`) with a comment, not validated. In the wired instance every tracked id came from a blob record, so it is canonical; a non-reference would throw `BlobRefError` out of the record read rather than being mis-handled. Nothing in this class enforces it.
- **Coverage by inspection only** (as the ticket scoped it): the partition branch, the `required === 0` retain, the `stat` chunking and wrong-length-answer path, the membership and `refuses` filters, the `grow:no-scope` path, and the both-`owed`-and-`responsible` case. Each is a few lines of branching; a reviewer who wants one pinned can add it against the doubles already in the spec.
- **`inParallel` and `chunksOf` are new local helpers.** No pool or chunk utility existed in `db-p2p/src` to reuse (searched); if the reviewer knows of one, these should fold into it.
- **No magnitude was measured.** The claims about request counts ("one acceptance call per event rather than one per reference", "at most one round trip per owed member") are read off the code, not profiled.
- **Nothing constructs the class yet,** so no end-to-end behaviour changed in this ticket: a reviewer cannot observe the reaction on a running node until `feat-a-held-blob-follows-its-cohort` lands.
