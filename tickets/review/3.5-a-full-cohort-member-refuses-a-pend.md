# A full cohort member refuses a pend

A cohort member whose storage has filled the space its operator gave it now answers a pend with a signed `out-of-space` vote, instead of approving and discovering the problem at apply (where its refusal is an unsigned report, after consensus) or filling its disk. The writer gets a typed terminal answer naming the full members rather than a retry loop it cannot win.

## What to review, in order

Read `docs/correctness.md` Theorem 1 Case 2 first — the refusal table there now has three rows, and the two paragraphs after it are the whole design argument. Then the gate at the end of `ClusterMember.validatePendOperations`, then the coordinator branch, then the writer-side plumbing.

## What was built

**The vote.** `Signature` gains `{ type: 'out-of-space'; signature: string }` — no payload, deliberately: a byte figure would be unverifiable, a publication of an operator's disk to every writer that pends, and unread. So it signs the bare tag `<hash>:out-of-space`, the form it shares with `approve`; `clusterVoteSigningPayload`'s doc now names that shape rather than leaving the new tag to fall through a `default` documented as "any type off the wire this code does not know". The ambiguity argument holds: a hash is base64url so the first `:` ends it, and `out-of-space` differs from `approve`, `conflict`, `held` and `reject` at its first character.

**The member.** `PromiseVerdict` has a fourth kind, `voteFor` maps it, `refusalLogTag` gains `cluster-member:validation-out-of-space`. The gate sits at the very end of `validatePendOperations`, behind a `sawPend` flag so only a record that actually asked this member to store something can draw it. It reads `StoragePressure.refusingNewData()` — never a scan.

**Ordering is the one real correctness requirement, and it holds all the way up.** The gate is after every other refusal in `validatePendOperations`, and a record can never carry both a pend and a commit (`batchShapeFault`: a multi-operation message is all pends or all commits; a single-operation one is one or the other), so the four commit-side checks `evaluatePromise` runs after it always have nothing to inspect on a record that can reach this gate. `out-of-space` is therefore only ever the answer for a record the member would otherwise have approved. Worth re-deriving rather than taking on trust — it is the claim the spec's two "still rejects" / "still holds" cases pin.

**Member-side counting.** `'out-of-space'` joined `getTransactionPhase`'s `retryableRefusals` beside `conflict` and `held`, and is absent from `rejectedPromises`. The `ConflictSuperseded` enum comment now says the phase means "terminal for this record, retryable as a fresh one"; the name is unchanged.

**The coordinator.** A new branch in `ClusterCoordinator.executeTransaction`, after conflict and held and before the generic shortfall, throwing `CohortOutOfSpaceError`. It gates its abandonment broadcast on `refusalsProveUnreachable`, whose sum now includes the out-of-space votes — necessary, not incidental: that sum has to match what a member re-derives from the same signed votes, and the member now counts them.

**The writer's answer.** `OutOfSpaceFailure` in `WriteFailure`, modelled field for field on `ShortfallFailure`; `isOutOfSpaceFailure` in `stale-failure.ts` (and added to `isConflictFailure`'s guard list, like its three siblings); `CoordinatorRepo.pend` **returns** it rather than letting it escape. A cohort of one casts no vote, so `refuseSoloPendForSpace` builds the same answer directly.

## Three decisions a reviewer should weigh

**1. ONE `CohortOutOfSpaceError`, in db-core.** The ticket's TODO reads as if there were two (one "added to `cluster-coordinator.ts`", one in db-core). Two classes of one name across two packages would be a trap, and the precedent the ticket itself cites settles it: `PromiseShortfallError` and `TransactionExpiredError` each live in db-core, are thrown by the db-p2p coordinator, and are converted to a failure by the coordinating repo. The ticket's `files:` line also names `packages/db-core/src/network/cohort-out-of-space-error.ts (new)` and no db-p2p equivalent. So: one class in db-core, thrown in `cluster-coordinator.ts`, converted in `coordinator-repo.ts`.

**2. Three db-core write-path sites the ticket's `files:` line did not name.** Each is required by the ticket's stated goal ("told its group is full rather than being sent round a retry loop that cannot succeed") and would otherwise defeat it:

- `WriteAttempts.recordRefusal` (`collection/write-attempts.ts`) is `Collection.sync`'s refusal classifier — the single-collection write path, the common one. Without an arm there the refusal falls through to `consecutiveFailures++` and the write burns its whole retry budget before reporting `SyncRetryExhaustedError`, a contention story, for a cohort that is simply full. **This is the exact loop the ticket exists to remove**, so leaving it out would have shipped the ticket's symptom.
- `refusalFrom` (`transactor/network-transactor.ts`) rebuilds one action-level answer from several per-batch ones, and anything not in its `unretryable` chain is flattened into a reason-only `StaleFailure` — non-retryable, but with the typed `outOfSpace` payload thrown away, so the writer gets "Pend failed … rejected". Placed last of the four, below the shortfall, by the ordering rule already written there (least permanent last from the top): a full member sheds to peers with room on its own, with no operator and no absent machine to wait for. **That placement is a judgement call** — it only matters for a write whose batches mix a shortfall with a full cohort, and the opposite order is arguable.
- `transaction/coordinator.ts` — the site the ticket did name: `pendRefusalError`, `PendPhaseFailure`, `pendFailure`, `CoordinationResult` and `cleanFailureError`, each beside `shortfall`.

**3. The solo gate exempts the program on this machine.** `refuseSoloPendForSpace` returns `undefined` when `options.localWriter === true`. The ticket's text does not mention the exemption; its stated purpose does ("a full single-member deployment accepts writes from client nodes until its disk fails"). Two reasons, argued at the site:

- The repository's documented rule is that the host's own writes are refused *later* than everybody else's — not at `refuseAbove` where the inbound doors refuse, but at the allotment (`OwnWriteRoom`, and `complete/a-full-node-refuses-new-data`'s "this limit is a *different*, later one").
- On a cohort of one it is load-bearing, not cosmetic. The ticket's own resolution path for a full cohort is "the full member sheds, and the cohort reforms around peers with room" — and a cohort of one has no peer to shed to. Without the exemption a single-machine deployment stops accepting its own application's writes at 95 % of its allotment with no path back but the operator raising the number.

`localWriter` is set only by a transactor in this process and is never carried on the wire, so a remote writer cannot claim it. **If the reviewer disagrees, the change is deleting one clause** — but note the consequence above before doing so. Consequence of keeping it, stated plainly: a solo node's own *block* writes are now gated by nothing until the disk itself fails. That is the status quo (the sibling ticket gated blobs only, through `LocalBlobService`), not a regression, and it is the host-gate story's gap rather than this ticket's.

## Verified by reading, no change needed

- **Equivocation.** `equivocationKey` keys on `sig.type` (plus a reject's validity marker), so a member that voted out-of-space and later approves is caught as a type flip exactly like any other, and the first-seen vote is kept.
- **Penalties.** The coordinator's promise-round penalty is `ConsensusTimeout` on a failed *delivery* (`!success`), never on a vote type, so an honest out-of-space vote is penalized nowhere a `conflict` or `held` vote is not.
- **Round decision.** `promiseRoundDecided` counts approvals only, so an out-of-space vote makes a round decided *out of reach* without any change.
- **No vote-type whitelist.** `validateRecord` checks the membership version and digest, nothing about vote types, and nothing else in either package reads vote types except the approval counts (all positive tests) and the branches changed here.

## Known gaps — read these before reviewing the test set

- **An older member meeting the new vote counts it toward nothing.** Its signature verifies (the preimage is the bare tag, which its `voteTagAndExtra` default already produces) but the vote is neither an approval, a rejection, nor a retryable refusal, so the record neither decides nor dies on that member until its promise timeout. Acceptable under the repository's current rule that backwards compatibility is not yet a constraint, and the ticket says explicitly not to add a shim — recorded here so it is not discovered rather than read.
- **A cohort of three at the default threshold still cannot complete the write.** `superMajority` is 3 and `maxAllowedRejections` is 0, so one full member blocks every write to that slice. What this ticket changes is the *answer* (typed, terminal, non-looping, naming the refuser) rather than the outcome; the shedding and ring-narrowing siblings are what make the write succeed. Written down in `docs/correctness.md` rather than left to inference.
- **`classifyCommitFailure` has no arm for `CohortOutOfSpaceError`,** so an offline drain sorts it as `unknown` and treats the write as in doubt. Conservative and safe (nothing was stored; a retry under the write's own identity stores it once) but less specific than the facts allow. Parked as a `NOTE:` in the error class's doc with the remedy and the reason not to fold it into `cohort-unreachable`, whose documented meaning is "too few members answered". **Not a ticket:** that mapping is a decision about drain behaviour, which the classifier's own doc says to make deliberately.
- **Two branches ship with no test,** and the reviewer should decide whether either is worth one. The solo gate (`refuseSoloPendForSpace`) and its `localWriter` exemption are a guard plus a predicate, but the exemption is a second behaviour and it is mine rather than the ticket's. The ticket says "One spec … Nothing else", which is why they are uncovered.

## Tests

One new spec, `packages/db-p2p/test/cluster-pend-out-of-space.spec.ts`, 6 cases over the two tiers where the ticket's three claims are observable. It is the test the ticket asked for; the file-level comment states the defect class.

| Case | What it pins |
| --- | --- |
| signs an `out-of-space` vote, verifiable and carrying no payload | the vote exists, carries nothing, and the bare-tag preimage verifies under the voter's own key |
| leaves the record in the terminal-but-retryable phase, never `Rejected` | **the headline.** A cohort of three at 0.75 has `maxAllowedRejections` 0, so one refusal decides the record — the shape in which a `reject` becomes a permanent `ValidatorRejectionError`. Asserted off the member's own phase log: `action-conflict-superseded` present, `action-rejected` absent |
| approves the same pend when the member has room | the control, so the case above cannot pass by the gate firing unconditionally |
| still rejects — permanently — a pend whose requested revision is already taken | the ordering rule: a full member still judges content, and a stale verdict wins |
| still holds for a rival reservation | the other half of the ordering rule: `held` names an actionable rival, this names only a condition |
| returns the typed out-of-space refusal when one of three members has no room | the writer's answer, end to end through the real `ClusterCoordinator`: `isOutOfSpaceFailure` true, `isConflictFailure` false, **returned not thrown**, naming the refusing peer with its approvals and bar, and the refused pend never reaching local storage |

One case added to the existing `packages/db-core/test/cluster-vote-payload.spec.ts` — `out-of-space` encodes as `aGFzaA:out-of-space` — in the existing "every vote without expiredAt or validity" test rather than a new spec, as the ticket specified.

Nothing else added. The failure shape, the classifier and the error class are types plus one field; `voteFor` and `refusalLogTag` are mappings the compiler checks exhaustively; the coordinator branch is covered by the sixth case above (without it the generic shortfall branch would throw `PromiseShortfallError` and the answer would be a `ShortfallFailure`).
