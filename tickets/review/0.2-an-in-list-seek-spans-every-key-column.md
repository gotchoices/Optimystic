## What changed

Quereus 5.4.0 fixed the composite multi-seek arm of `selectPhysicalNodeFromPlan`: a column with a single bound `=` beside an `in` now seeks on `equalitySeekKey`, not `Literal(undefined)`. Before building anything I re-ran the ticket's table on a plain Quereus memory table, with both a composite secondary index and a composite primary key. Every parameterised form now returns the right rows (`1,2`, `1,2`, `1,3`, and `xp,xq`, `xp,xq`, `xp,yp`).

In this repository:

- **`matchEqualitySeek`** no longer stops at a multi-value `in`. The match runs through every leading key column that has an equality-role filter, and its `keyCount` is the product of the columns' key counts. So `a = ? and b in (…)` over `(a, b)` seeks both columns, and an `in` on a composite primary key now plans a `_primary_` multi-seek instead of a scan.
- **`MAX_MULTI_SEEK_KEYS` = 1000** is the same value as the store module's constant of that name. After the first column, a column whose count would take the product past it ends the match, and that column stays a residual over the seek of the columns before it. Two rules here are deliberate:
  - The first column's own list is never capped. It is the list the statement's author wrote, and it competes on cost exactly as before.
  - A column with a single value (`=`, or `in (?)`) never ends the match, because it does not raise the product. So `a in (<1500 values>) and b = ?` still seeks both columns.
- **`seekTuplesOf`** reads `seekWidth` from `idxStr` and splits `args` into tuples of that width, with width 1 when the parameter is absent. It throws `INTERNAL` when the width is not a positive integer or does not divide the argument count. The old check, which refused any width other than 1, is gone. Both readers (`executePointLookup` and `indexScanRanges`) already took tuples. NULL-bearing tuples are still dropped, and duplicate tuples still collapse, in `seekKeysInTreeOrder`.
- The `isMultiValueEquality` import is gone (it is no longer used in this file). The comment on `executePointLookup` is updated, and so is the README's sentence on which predicates seek. One `seek=` line in docs/debugging.md now says a list beside other sought key columns prints one key per distinct combination.

## Tests (all in `test/in-list-index-seek.spec.ts`)

- The differential suite gained `claimsAll`, which asserts the plan keeps no `FILTER` above the seek, i.e. every filter was claimed. The three existing composite cases on `idx_bc` now carry it, and they would fail on the old planner, which left the trailing column residual. Two cases are new: a bound NULL `=` beside an `in` (expects no rows), and a list on each column.
- A new block, "in-list seeks of a composite primary key agree with a scan of the same rows", runs six cases against a `primary key (b, c)` table and an unindexed copy of it. Each must plan an INDEXSEEK through `primary` with no FILTER. The rows include a value that prefixes another (`x` and `xa`), and a bound NULL. This block is the only end-to-end test of `seekTuplesOf` at width 2 over the primary key. The index arm gets the same coverage from the `idx_bc` cases.
- In the planner unit tests:
  - The old "seeks a multi-value in only as the sole column" test is now "seeks every column of a composite index through a multi-value in, up to the cap on the product". It covers leading and trailing lists, the product in `explains`, the cap ending the match at 40 × 40 on a million-row estimate, and a single value extending a 1500-key list.
  - The composite-primary-key test now expects a `_primary_` multi-seek of 2 keys.
  - The `plan` helper takes an optional `estimatedRows`, because the cap only matters on a table large enough for a long list to beat a scan.

`yarn build`, then the plugin's full `yarn test`: 1376 passing, 14 pending. `yarn typecheck`, `yarn lint:docs` and eslint on both changed files are clean. **Not run:** `yarn test:integration`, which needs real TCP meshes. Nothing in the diff touches the mesh path, but no integration spec has been run against it.

## For the reviewer

- **Cap semantics.** The ticket said only "add a cap on the product". The choice to stop before the column that crosses the cap, rather than decline the whole candidate as the store module's cost-only branch does, is mine. So is leaving the first column uncapped. Check that you agree.
- **Pricing.** Without statistics, `equalitySeekCandidate` charges the 0.1 equality constant once rather than per key (see the existing `NOTE:` there). A product such as 2 × 3 is therefore priced as 6 descents plus 100 rows, the same as a single-column list of 6. I did not revisit that.
- **Key order of a composite multi-seek.** Keys are visited in tree byte order (`seekKeysInTreeOrder`). The existing `NOTE:` there about the isolation layer applies unchanged to composite keys, and nothing here relies on more than that.
- **Use cases to try by hand.** `select … where a = ? and b in (?, ?)` over an index on `(a, b)`; `where a in (?, ?) and b = ?` on `primary key (a, b)`. In `query_plan`, expect one INDEXSEEK with no FILTER above it, and in the `index:seek` trace, one `seek=` key per combination.
