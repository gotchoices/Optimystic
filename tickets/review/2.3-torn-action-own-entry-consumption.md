# Review: torn action, part 2 of 3 — consume your own committed log entry (db-core)

Implements `2.3-torn-action-own-entry-consumption` as specified; the design in that ticket was
followed without deviation. Part 1 (`torn-action-pend-tier-carve-out`, db-p2p) already landed;
part 3 (`torn-action-cleanup-and-mesh-validation`) still owns end-to-end mesh validation and the
`network-transactor` dead-clause cleanup, neither of which this change touches.

## What was wrong

`NetworkTransactor.commit` commits the collection header and log tail BEFORE sweeping the
remaining blocks. If a later sweep block comes back as a confirmed conflict, commit returns a
stale failure — correct, because acknowledging a torn action would be worse — but the header and
tail are already durable, so the collection's log already carries this action's entry.

The writer's retry then called `Collection.updateInternal`, whose entry loop only ran pending
actions through `doFilterConflict` (default: keep everything) and replayed the lot, re-appending
content the committed tail already held. Result: **the same action recorded twice in the log.**

## What changed

- `updateInternal` takes an optional `inFlightActionId`. `syncInternal`'s retry path
  (collection.ts:885) passes the actionId minted for the attempt; `update()` and
  `updateAndSync()` still call it with no argument, so their behavior is byte-for-byte
  unchanged.
- In the entry loop, a new branch runs BEFORE the conflict filter: when the entry's `actionId`
  equals the in-flight id, the entry is **consumed** — `this.pending = before.slice(entry.actions.length)`
  — and `mutated` is set unconditionally, including for a zero-action entry.
- `mutated` matters because it drives `replayActions()`, which resets the tracker and re-stages
  only what remains. That reset is what drops the consumed action's staged transforms, so
  `hasUnsyncedChanges()` turns false and the sync loop exits reporting success — which is the
  honest answer, because the action IS durable.
- Everything else in the loop is untouched: `sourceCache.clear(entry.blockIds)` still runs for
  the consumed entry, the invalidation handling is unchanged, and `advanceContext` still runs
  before the replay.

## How to exercise it

New spec: `packages/db-core/test/collection-own-action-replay.spec.ts`. It uses a
`CommitLandsButReportsStale` wrapper (extends the existing `DelegatingTransactor`) that commits
durably on the inner `TestTransactor` and then masks the first success as a stale conflict —
the observable shape of tail-committed-then-later-block-conflict. Safe because
`TransactorSource.transact` cancels the pend on the reported failure and `TestTransactor.cancel`
only deletes pending records, which the real commit already promoted.

Three cases:

- **consumes its own durably committed entry** — one action, `sync({ maxAttempts: 5, baseBackoffMs: 1, maxBackoffMs: 5 })`
  must RESOLVE (not exhaust); `selectLog()` yields the action exactly once; only one commit ever
  landed on the inner transactor; `hasUnsyncedChanges()` is false; and a second collection opened
  on the *unwrapped* transactor also sees exactly one entry (proves the durable log, not just this
  instance's view).
- **still replays when the entry belongs to someone else** — a rival writer's committed action
  must not be mistaken for this sync's own work; log ends `['rival', 'local']`.
- **`update()` with no in-flight action is unaffected** — the no-argument path keeps its pending
  action across an `update()` over a foreign entry and still syncs it.

Confirmed the first case FAILS pre-fix (`expected [ …(2) ] to have a length of 1 but got 2`) and
passes after.

## Known gaps — please push on these

- **The multi-collection / coordinator path is NOT covered.** `TransactionCoordinator.commit`'s
  retry loop refreshes participants with a plain `collection.update()` (coordinator.ts:201), with
  no in-flight actionId, so a torn action committed through the coordinator can still replay into
  a duplicate entry. That is outside the scope this ticket specified (which named only
  `syncInternal`'s retry), but it is the same defect on a different path — worth a judgement call
  on whether it becomes a fix ticket now or rides with part 3. The coordinator names its
  transaction id, not a per-attempt actionId, so the fix is not a one-line thread-through.
- **The spec injects the failure rather than reproducing the real ordering.** It asserts the
  observable contract (commit landed, failure reported) but does not drive a real
  `NetworkTransactor` sweep where a late block conflicts. Real-ordering coverage is explicitly
  part 3's.
- **The slice relies on a latch invariant and fails silently if it breaks.** `entry.actions.length`
  equals the leading pending prefix only because `act()` and `syncInternal` share the collection
  latch. An entry longer than `pending` would silently drop uncommitted actions rather than throw.
  Left as a tagged tripwire, not an assertion, per the ticket's "defensive `slice` is the right
  shape" call — see below.
- No test covers the zero-action-entry case (an entry whose `actions` array is empty) reaching the
  consume branch. The `mutated = true` line is written to handle it, but nothing exercises it.

## Tripwires parked

- `packages/db-core/src/collection/collection.ts` (~line 506): `NOTE:` at the consume branch —
