# A redirect can send a reader to itself — implemented

GitHub #65. A read-only browser node sent a repo `get` to a host; the host's view of the block's cohort included the browser, so its redirect listed the browser's own peer id; the browser picked itself, libp2p refused the self-dial, and the read failed as peers-unreachable.

## What changed

**Client (asker side).** `IPeerNetwork` gained an optional `readonly localPeerId?: PeerId` ("this node's own peer id, so a protocol client never dials or follows a redirect to itself"). `Libp2pKeyPeerNetwork` implements it as a getter over `libp2p.peerId`. Every production `RepoClient`/`ClusterClient` is built over a `Libp2pKeyPeerNetwork` directly (checked: `createLibp2pNodeBase`, the Quereus `CollectionFactory`, the reference peer), so no wrapper drops the field. Test doubles that omit it keep the old behaviour.

Both redirect branches now call one shared function, `pickRedirectTarget(peers, askedId, localId)` in `packages/db-p2p/src/repo/redirect.ts`: the first listed peer that is neither the peer just asked nor this node. When none remains it throws `Redirect from <asked> named no peer other than the one asked and this node` (replacing the two "same peer" throws; nothing matched on their text). The pick happens before `recordPeerAddresses` and the coordinator hint, so neither is ever recorded for a filtered-out peer. The two-hop limit is unchanged.

**Host (redirecting side).** `RepoService.checkRedirect(blockKey, opName, message, requester?)` gets `connection.remotePeer` from `handleIncomingStream`; `ClusterService.checkRedirect(record, requester?)` gets `remotePeer` from `processOperation`, through `processRecord`, and through the `applyCarriedRecords` hook. Each leaves the requester out of the redirect list. If nothing remains, it does not redirect (`null`) and logs `redirect:only-requester`: the request is processed locally. `RepoService` still stamps `message.cluster` with the full cohort; only the redirect payload is filtered.

**Why local processing is safe on each side:**
- Repo: `CoordinatorRepo` serves a `get` fail-open and refuses `pend`/`cancel`/`commit` (and the batch forms, which share that path) with `ResponsibilityRefusalError` for a block this node is not responsible for (docs/internals.md §Proximity Verification).
- Cluster: the ticket asked to verify that `ClusterMember.update` refuses a record whose `peers` does not name this node. **It does, but by signing a reject vote, not by throwing.** The membership admission gate (`admitMembership` in `packages/db-p2p/src/cluster/cluster-repo.ts`, predicate 1, "self-membership", always enforced, including under `allowUnvalidatedSmallCluster`) answers with `membership-not-admitted:self-not-member`. In the only shape that reaches the new path (`record.peers` = {requester}), one reject already exceeds `maxAllowedRejections` (0), so the record goes straight to `Rejected` on this node and nothing is applied. That reject is signed under an id that is not in `record.peers`, so a third member verifying the record would refuse it as an invalid signature. That cannot happen here: a cohort of one never dials anyone, so this path is reached only by a dialer that is not the record's own coordinator, or by a carried record. No change was made there.

## Tests added

All are in db-p2p unit specs (millisecond scale):
- `coordinator-cache-hint.spec.ts`, "RepoClient redirect target":
  - **skips this node in a redirect and follows it to the next peer named.** This is the reproduction of #65: a fake network with `localPeerId` gets a redirect listing `[self, other]`. The test asserts the dials are exactly `[asked, other]` and that addresses and the coordinator hint are recorded only for `other`.
  - **fails without a second dial when the redirect names only this node and the peer asked.** A redirect listing `[self, asked]` throws after one dial and records nothing.
  - Verified both fail with the local-peer exclusion removed. A `ClusterClient` case was not added, because its branch is now just a call to the same function.
- `redirect.spec.ts`, "RepoService redirect logic → checkRedirect":
  - **leaves the requesting peer out of the redirect, and keeps it in the responsible ids.** Cohort `[requester, other]` with K=2 and self absent: the payload is `[other]`, and `message.cluster` is still both.
  - **handles the request locally when the requesting peer is the only one to redirect to.** Cohort `[requester]`: the result is `null`.
- `cluster-service-redirect.spec.ts`, "ClusterService redirect logic → checkRedirect":
  - **leaves the requesting peer out of the redirect.** The payload is `[other]`.
  - **processes the update locally when the requesting peer is the only one to redirect to.** This goes through `processOperation`, so it also covers the `remotePeer` threading: `cluster.update` is called once.

## Known gaps / things for the reviewer

- **The `RepoService` requester wiring is untested end to end.** `handleIncomingStream` passing `connection?.remotePeer` into `checkRedirect` is one argument; the unit tests call `checkRedirect` directly. The cluster side's equivalent is covered through `processOperation`.
- **A second hop can still name the original asker.** On the hop to `other`, the new `RepoClient` asks `other`. If `other` redirects again, the list is filtered against `other` and this node, but not against the first peer asked. The two-hop limit still bounds it.
- **The redirect is still followed without the network-membership predicate** (the existing `NOTE:` in `RepoClient`). That is unchanged and out of scope.
- **Root cause of an edge reader being in other machines' cohorts.** Every node built by `createLibp2pNode` registers the `repo`/`cluster` services, so an `edge` browser is classified as serving. Plan ticket `client-only-node` (`NodeOptions.servesBlocks: false`) addresses that. This fix stands on its own, because two serving nodes whose cohort views differ can still produce the same redirect.
- **Docs.** The "Redirect check (same rule)" bullet in docs/internals.md §Proximity Verification now states both rules and cites `pickRedirectTarget` and `IPeerNetwork.localPeerId`.
