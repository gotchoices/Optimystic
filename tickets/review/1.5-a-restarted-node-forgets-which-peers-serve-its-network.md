# A restart no longer turns "I cannot reach my cohort" into "this block does not exist"

## The defect

A scoped key network (`protocolPrefix` set, as every production node is) admits a remote peer to a cohort only when `membershipOf` classifies it `'serves'`, from the protocol list in the libp2p peerStore. The peerStore is in memory. After a restart with `createLibp2pNode({ persistence })`, FRET's table is restored and FRET still returns the remembered peers for a key, but every one of them has an empty protocol list until it reconnects and identify re-runs, so it read `'unknown'` and was never admitted. The cohort came back self-only, `CoordinatorRepo.fetchBlockFromCluster` took its solo-self exit, and every read of a block this node lacked was served as an authoritative absent. That is the "why is absent served" half of the sereus re-attach report (optimystic #22).

Confirmed before the fix at the key-network tier: with the new spec's shape and an explicit `persistState()` standing in for the save, the restarted network's `findCluster` returned `[self]` where the pre-restart one returned `[remote, self]`.

## The fix

- `Libp2pKeyPeerNetwork.rememberedServing`: a set of remote peer ids last classified `'serves'` from a non-empty protocol list. Only positive verdicts are kept.
- `membershipOf`: a non-empty protocol list is classified as before and updates the set (`'serves'` adds, `'foreign'` removes, so the live peerStore always wins). An empty or missing list returns `'serves'` for a remembered id, `'unknown'` otherwise. Self and the unscoped path are unchanged.
- `PersistedNetworkState.servingPeers?: string[]`: optional, no `PERSISTED_STATE_VERSION` bump; an older snapshot restores an empty memory. `persistState` writes only the remembered ids that are in the FRET table it is exporting beside them. `initFromPersistedState` loads it after the table import.
- The accepted-tradeoff `NOTE:` (a remembered peer that never returns keeps doubt alive until FRET declares it dead; revisit condition names `feat-declared-membership-feeds-cohort-assembly` or a "forget peer" operation) sits at the empty-protocols branch of `membershipOf`.
- Nothing in `CoordinatorRepo` changed. Its existing handling turns the now non-self, silent cohort into `'cohort-unreachable'`.

### Deliberate deviation from the plan: the verdict is saved when it changes

The plan said the memory would be saved "by the next `persistState` (driven by connection events)". That does not work for the case this ticket exists for. `persistState` runs on `connection:open`, which fires *before* identify has filled in the peer's protocols, so the first classification of a peer as serving happens after the save that followed its connection. In a two-machine deployment there may be no later `connection:open` before the process stops, and the verdict would never reach disk. So `rememberVerdict` calls `schedulePersist`, which coalesces every change made in one synchronous classification loop into one `persistState` on the next microtask (`queueMicrotask`). Changes are rare (a peer's verdict flips about once per lifetime), and at that moment the peer is in FRET's band, so it is in the exported table and survives the bound. The crash window left is the duration of one async save. The regression test pins this: it waits for `persistence.saved.servingPeers` to name the remote with no connection event fired.

## Test added

- `libp2p-key-network.spec.ts`, "findCluster still admits a peer it saw serving this network after a restart, before identify re-runs": a scoped network with `MemoryPersistence` and a mock FRET whose `assembleCohort` returns `[remote, self]` sees `remote` serving and saves the verdict; a second network over the same persistence with an empty peerStore (the restart) runs `initFromPersistedState` and must assemble `[remote, self]`. This is the one regression test, at the lowest layer that shows the defect. No CoordinatorRepo test was added, per the plan: a silent non-self cohort becoming `'cohort-unreachable'` is already covered by that class's own specs.

## Known gaps and things for the reviewer to weigh

- **Nothing end to end.** FRET's side of the chain — `importEntries` keeps restored peers as `membership: 'member'`, `state: 'disconnected'`, and `assembleCohort` returns them — is read from `../Fret/packages/fret/src/store/digitree-store.ts`, not exercised. The spec mocks `assembleCohort`. A real two-node restart with `persistence` (stop one node, restart it over the same persistence while the other stays down, read a block only the other holds, expect `BlockUnavailableError` with reason `'cohort-unreachable'`) would prove it; no existing harness restarts a node over persisted network state, so none was built here.
- **Writes after a restart change too, not only reads.** A restarted node whose remembered partner is still offline now has a two-member cohort instead of a self-only one. `findCoordinator` still picks only connected members, so this node self-coordinates, but the commit then runs consensus against a cohort whose other member is unreachable, where before the fix it committed solo and minted a one-peer proof the partner never saw. This matches what the same process did before any restart when its partner went offline, which is the rule the ticket set, but it is an availability change for restarted nodes worth a conscious look.
- **How long doubt lasts is FRET's liveness, unmeasured.** Until FRET marks a never-returning peer dead, reads of blocks this node lacks fail loudly and creating a new collection through this node fails. How long FRET takes to mark a restored, never-reachable entry dead was not measured.
- **In-memory growth.** Only the saved copy is cut to FRET's table; in process the set gains one entry per distinct peer ever seen serving. Recorded as a tripwire `NOTE:` at `rememberedServing`.
- **Loaded ids are not validated.** `servingPeers` is trusted like the snapshot's other fields; a corrupted snapshot could only admit ids FRET also returns for a key.
- **Staleness.** A remembered peer that has since moved to another network is admitted until it reconnects and identify replaces its protocol list; its dials fail at protocol negotiation and the existing exclude-and-retry absorbs them, the same cost a stale FRET entry already carries.
