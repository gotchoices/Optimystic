## The decision the reviewer must confirm

**Refuse the loser.** A concurrent same-row UPDATE or DELETE whose pre-write row image a rival changed or removed is refused at commit, never resolved last-writer-wins, and under concurrency every conflict disposition (`or ignore`, `or replace`, `on conflict … do nothing`) resolves to refusal, with the sequential retry honouring the disposition. Grounds, restated from the implement ticket: last-writer-wins cannot be made index-coherent because the loser's index delta was computed against a row the collection no longer holds and no commit mode replays across collections; the UNIQUE guard already made the same call for the same reason; and the transactions doc calls two users editing the same row a semantic conflict the application resolves. If a human wants last-writer-wins for UPDATE instead, that is a `blocked/` decision and the fix becomes "derive the index delta at replay from the row actually replaced", a much larger change.

## What landed

**The guard, in the vtab** (`optimystic-module.ts`). A module-level `unchanged(entry)` builds `{ kind: 'unchanged', expected: entry }` over the stored entry as read (`StoredRowEntry = [framedPk, encodedRow]`), never a re-encoding. `requirePreWriteRow` returns `{ row, entry }` (`PreWriteImage`); `UniqueCollision` and `PkMoveDecision`'s `displace` arm carry the entry the probes already held. Every main-table entry whose index delta was derived from a pre-write image is guarded:

- same-key UPDATE: `[[key, [key, encoded], unchanged(oldEntry)]]`;
- primary-key move: the delete half `unchanged(oldEntry)`; the insert half `unchanged(displacedEntry)` for a REPLACE onto an occupied key, else `absent` under every resolved action (the "clear + resolved REPLACE, a late rival is displaced too" arm is gone);
- DELETE: `[[key, undefined, unchanged(oldEntry)]]`;
- INSERT at a key the probe found clear: `absent` under every disposition (IGNORE was `keepExisting`, REPLACE was unguarded); the `keepExisting` NOTE beside the guard is deleted and the guard-selection comment rewritten;
- INSERT OR REPLACE at an occupied key: `unchanged(existingEntry)`;
- each secondary-UNIQUE eviction in `applyUniqueEvictions`: `unchanged(collisionEntry)`.

`IndexManager` is untouched: index entries are keyed `indexKey ‖ pk`, so a stale delta can only be prevented at the main-table action. `keepExisting` has no SQL producer any more; it stays in db-core as a documented, serialized log form.

**The message, in the bridge** (`txn-bridge.ts`). `registerEntryChangedRenderer(collectionId, render)` beside `registerKeyTakenMessage`; `mapCommitRefusal` now walks the cause chain for `TreeGuardRefusedError` and dispatches by class through a private `renderRefusal`: `TreeKeyTakenError` (and its range subclass) to the registered UNIQUE message as before, `TreeEntryChangedError` to the renderer. The vtab registers the renderer for its main collection only, in `registerCollections`, and renders `concurrent modification: another writer changed or removed the row in <table> at primary key (100)` via a new `concurrentModificationMessage`. The double-mapping guard (`error.message === message`) is unchanged and covers the rendered form. Still a plain `Error` with `cause`; the type question is appended to backlog `bug-concurrent-unique-refusal-is-not-a-constraint-error`, which now names both classes.

**Key decoding, in the codec** (`row-codec.ts`). New public `decodePrimaryKey(key)` — the rendering-only inverse of `createPrimaryKey`, decoding each framed part under its primary-key column's affinity with the private helpers the comparator already uses — so the message names `(100)`, not a framed tree key.

**Docs.** `docs/internals.md` entry-guards section: the `keepExisting` entry in the kinds list says no statement stages it any more; a new paragraph "Which statements carry `unchanged`" states the principle, the refuse-the-loser decision and why, the disposition rule, the message and its plumbing, why index trees carry no guard, why within-transaction chains never refuse themselves, and the read-time shape below; the regression-suite list gains the two specs.

## Client-visible behaviour changes

1. A racing same-row UPDATE, DELETE, REPLACE-over-occupied-key, displacing move, or UNIQUE eviction fails the loser's commit with the concurrent-modification message. Both commit modes: the legacy sweep refuses at the first-tree flush or, for an indexed table, at the pre-flight, with a clean rollback; session mode fails the whole transaction (the new spec has one arm for each).
2. INSERT OR IGNORE and INSERT OR REPLACE at a key a rival takes first are now refused with the ordinary `UNIQUE constraint failed: <table>.<pk>` message instead of being admitted (the IGNORE one silently, the REPLACE one by overwriting). A sequential retry swallows or replaces as before.
3. **A live read inside a doomed transaction can now throw** where it used to return the reader's own staged value. Every vtab read refreshes the tree, which replays the staged action, and an `unchanged` guard a rival has contradicted refuses mid-scan, wrapped as `Query failed: … changed by another writer …`. This is the exact shape the read path's `NOTE: a live read inside a doomed transaction` already accepted for the insert guard; the note now names the new class. One existing test, `external-commit-visibility-after-rollback.spec.ts`, asserted the masked staged value on that read and was changed to assert the early refusal — its comment already called the masked value incidental, and its real assertions (B's commit visible after rollback, twice) are unchanged. **Reviewer:** confirm you are comfortable with a SELECT surfacing a concurrency refusal early; the alternative is to catch guard refusals in the read path and keep serving the staged view, which hides a doomed transaction until commit. Mapping the read-time message through the bridge (so it reads like the commit's) was deliberately not done, per the note's existing scoping.

## Tests

**New `test/concurrent-row-change-refusal.spec.ts`** (16 tests, two handles over one `FileRawStorage` dir, `T (id integer primary key, v text)` plus `create index T_by_v on T(v)` unless stated). Every refused case asserts on both handles that the rows equal the winner's outcome and that `expectIndexAgreesWithScan` is clean (the failure names the handle), then re-runs the loser's statement sequentially and asserts the documented outcome:

- UPDATE vs rival UPDATE; DELETE vs rival UPDATE; UPDATE vs rival DELETE (no resurrection); DELETE vs rival DELETE (absent counts as changed, retry affects zero rows).
- Control: UPDATE vs rival INSERT of a different key sharing the indexed value — both commit, the lookup arm finds both entries.
- INSERT OR IGNORE and INSERT OR REPLACE at a clear key vs rival INSERT of that key: refused with the UNIQUE message, retry honours the disposition.
- INSERT OR REPLACE at an occupied key vs rival UPDATE; primary-key move vs rival UPDATE of the moving row; REPLACE move (`primary key on conflict replace`) onto an occupied key vs rival UPDATE of the occupant.
- Secondary-UNIQUE eviction (`v text unique on conflict replace`, no declared index, structural check only) vs rival UPDATE of the evicted row.
- The false-UNIQUE-refusal shape under `create unique index`: after the refused race the loser's value is inserted on the loser's handle, then on the winner's.
- Three within-transaction chains with no rival: `update; update`, `insert; update; delete`, `update (pk move); update`.
- Session mode, two-table transaction: UPDATE vs rival UPDATE fails the whole transaction with the concurrent-modification message; both tables roll back.

**`test/concurrent-insert-refusal.spec.ts`**: the IGNORE and REPLACE clear-key tests flipped to a refusal plus a sequential retry honouring the disposition, mirroring the UNIQUE spec's loop; header extended.

**`test/two-node-index-mutation-sweep.spec.ts`**: the replay model, `pinReport`, `describePrediction`, `expectPrediction` and `expectOrphanSeeks` are deleted (`grep -rn "replay model" packages/quereus-plugin-optimystic/test/` returns nothing); `RaceStatement` collapsed to SQL strings; new `expectRaceOutcome` and `expectedRaceRows`; header's "What green means" rewritten. Of the 32 racing cases, the 16 where both sides are `update` or `delete` now assert the first committer fulfils and the second is refused with the concurrent-modification message; the 16 with one `insert-shared` side assert both fulfil; the 4 INSERT OR IGNORE races assert the loser is refused with the UNIQUE message. All 104 tests in the file pass and every racing case closes on `expectIndexAgreesWithScan` on both nodes. The sequential group is untouched.

## Two pre-existing defects the new spec exposed, filed rather than fixed

Both reproduce with **no race at all** (scratch probes, deleted); neither touches code this ticket changed.

- **`fix/6.35-blind-index-delete-is-logged-but-never-applied`** — a DELETE issued from a handle whose index tree has never fetched the row's entry leaves the entry in storage forever: the index delete changes no block at staging, and `Collection.updateInternal` replays pending actions only on a block conflict, so the commit logs the delete without applying it. Corruption-class and reachable in normal use (hydrate, read by pk, delete), so it went to `fix/`. The new spec seeds rows alternately through both handles to keep this out of the guard's cases; its comment names the ticket and the ticket says which case to add once fixed.
- **`backlog/bug-unique-enforcement-tree-set-differs-across-handles`** — a handle that opens a table after a plain `create index` covers a `unique` column synthesizes no enforcement tree, while a handle that opened before keeps maintaining its own, which then goes stale. Harmless today (the declared index is preferred for enforcement) but latent, and the existing note on `resolveEnforcingIndex` names the wrong producer. The eviction case avoids the shape by declaring no index.

While chasing the second one I also learned that passing `undefined` to a parameter with a default selects the default; the spec's "no index" sentinel is `null` and says why.

## Known gaps for the reviewer

- `decodePrimaryKey` is exercised only through message assertions on single-column INTEGER keys. TEXT and composite keys (and a BLOB key, which `formatKeyValues` renders as `<blob n bytes>`) have no test; a one-column TEXT key and a two-column key would close that cheaply.
- `expected` holds a reference to the entry object `collection.get` returned, not a copy. Safe because tree entries are never mutated in place and the action is serialized at pend, but a reviewer should confirm nothing between staging and pend can touch that object.
- Refusals are matched on message only, like the two existing concurrent specs; the error type is backlog `bug-concurrent-unique-refusal-is-not-a-constraint-error`, now covering both classes.
- The mesh sweep exercises legacy mode only; session mode is covered by the new spec's two-handle arm, not on a mesh.
- The legacy residual window (a rival landing between the pre-flight and a tree's own flush) is unchanged and stays with `feat-optimystic-legacy-commit-two-phase`.
- `insertGuard` in the INSERT arm is now a constant `{ kind: 'absent' }` kept as a named binding for the comment above it; inline it if that reads as clutter.
- The db-core `unchanged` guard doubles the row bytes of every guarded log entry (its own NOTE). Every UPDATE and DELETE now carries one; nothing was measured.
