# Journal batch backend — review handoff

Third of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). The implement ticket's design is in the body below the handoff; the two tickets that consume this one are `implement/4.3-browser-storage-syncs-by-the-window` and `implement/4.4-react-native-storage-commits-groups-through-the-journal`, both still on the board, and they are the first real `JournalStore` implementations. Nothing in production composes the backend yet; the only store over it is the test double.

## What landed

- **The port and the backend**, `packages/db-p2p/src/storage/journal-batch-backend.ts`: `JournalRecord`, `JournalContents` (what `readJournal` answers), `JournalStore` (`Omit<BatchBackend, 'commit' | 'sync'>` plus `appendJournal`, `applyJournal`, `readJournal`), `JournalBatchBackendOptions` (`setTimer`, `now`), and `JournalBatchBackend implements BatchBackend`. Open is lazy and memoized, awaited by every read and queued step; recovery is a pure `planRecovery` (stale records at or below the mark deleted, the consecutive run after it applied, everything after the first gap discarded) followed by at most one `applyJournal`. Commits, syncs, the timer's apply and close run on one serial queue. A commit whose store is below `'power-loss'`, or whose deadline (taken at the call, per `SyncDeadlines.deadlineFor`) `mustSyncNow`, takes the cover and applies cover plus its own record in one `applyJournal`, returning an already-settled `durable`; otherwise it appends and defers. Any store write rejecting latches the backend (`failAll`, `StoreFailedError` with the first cause). Optional members are forwarded only when the store has them. The class doc carries the prefix argument once.
- **The byte codec**, `packages/db-p2p/src/storage/journal-record-codec.ts`: `encodeJournalRecord`, `decodeJournalRecord`, `JournalRecordDecodeError`, `JOURNAL_RECORD_FORMAT_VERSION`. Big-endian: version byte, 8-byte seq (two u32 halves, no BigInt, so Hermes is fine), u32 entry count, per entry a length-prefixed UTF-8 JSON `StoreKey`, a flag byte, and for a put a length-prefixed value. Decode is strict: unknown version, bad flag, a key that is not a `StoreKey`, a length past the end, or trailing bytes all throw the named error, so a store can tell a damaged record from an I/O failure and leave it out of `readJournal`.
- **The test double**, `packages/db-p2p/src/testing/memory-journal-store.ts` (`MemoryJournalStore`, exported from `./testing`): `durability` chosen at construction (default `'power-loss'`), `appended` and `applied` as call recorders (never rewound), `journalSeqs` and `mark` for assertions, `beforeAppend`/`beforeApply` hooks to fail or park a write, and `powerLoss({ lose? })`, which drops every unapplied journal record or only the numbered ones and keeps the applied stores.
- **A small refactor of the existing double**: the applied-rows map and its five reads that `MemoryBatchBackend` and `MemoryJournalStore` would otherwise duplicate moved into `MemoryStoreRows` (`packages/db-p2p/src/testing/memory-store-rows.ts`, not exported from the barrel); `MemoryBatchBackend`'s behaviour is unchanged and its spec still passes.
- **Exports** from `src/index.ts` and `src/rn.ts` (both new modules, same position in each; entry parity passes).
- **Docs**: a `journal` row in the db-p2p namespace table of `docs/debugging.md` (the count line went from 53 to 58, which is the row count the table now has; the logger spec checks rows against `createLogger` calls, not that number), and in `packages/db-p2p/docs/storage.md` Invariant 6: a `JournalBatchBackend` row in the driver table, a *The journal backend* paragraph between the file backend and *Rule 3 past the crashes a store names*, a clause in the "who honours `withinMs`" sentence, and a clause in the rule-3 paragraph pointing both sibling tickets at it.

## Decisions a reviewer should weigh

- **One branch for "apply at once".** A cannot-sync store and a `mustSyncNow` commit share one path: take the cover (empty for a cannot-sync store, which never defers) and apply cover plus record. Simpler than the ticket's two bullets, same behaviour.
- **A strict group's record is never appended, yet its number is in `apply`.** `applyJournal` therefore deletes a journal number that has no record. The interface says a number with no record present is nothing to delete; the two sibling tickets must honour that (a LevelDB batch delete and an IndexedDB delete of an absent key both do).
- **`nextSeq` advances before the write.** A failed append or apply latches the backend, so a number taken by a failed write is never reused in this process, and the next open's recovery decides from the journal. Consistent with "a failed append leaves at most a record the next open applies or discards".
- **`close()` does not open the store merely to close it.** Before the first open nothing is held; after a latch `failAll` has emptied the held list; so it applies held records only on an opened, healthy backend, then calls the store's `close` if any. A second `close` is harmless.
- **Reads await open and go straight to the store, outside the queue.** A read can run beside an apply in flight; the store's apply is atomic, so a read sees before or after, and `BatchBackend`'s read contract allows either (the overlay serves the rest).
- **The memory note** went at `held` in the backend rather than beside the overlay `NOTE:` in `write-group.ts`: that note counts the overlay's value bytes, and a held record's `entries` reference those same `Uint8Array`s (`WriteGroup.runCommit` maps the open entries to a new array of the same entry objects), so the journal holds the arrays, not a second copy of the bytes. `write-group.ts` is untouched.
- **Stale records log on `journal:error`**, since they can only exist if a store lost part of an atomic apply; the gap log is a plain line, since a gap is the ordinary shape of a power cut.

## Tests added (`packages/db-p2p/test/journal-batch-backend.spec.ts`)

Over `WriteGroupDriver(new JournalBatchBackend(new MemoryJournalStore(), { setTimer, now: () => 0 }))`, with the driver's idle timer never firing:

- **Relaxed groups are journaled, not applied, and applied together in order when the deadline is due** — two relaxed flushes append seqs 1 and 2 and apply nothing; the store's own reads do not see them while the driver's do; exactly one timer is armed; firing it yields one apply `[1, 2]` through 2, the journal is empty, and `whenDurable()` resolves.
- **A strict flush applies every held record and its own group in one apply** — one relaxed then one strict: appended `[1]`, applied `[[1, 2], 2, []]`.
- **A power cut that loses a middle record keeps the groups before it and none after; the sequence continues after the prefix** — three relaxed groups, `powerLoss({ lose: [2] })`, fresh backend: group 1 reads back, 2 and 3 do not, the open's apply is `[[1], 1, [3]]`, the next group is appended as seq 2 and a strict flush then applies it.
- **A process crash loses nothing that was flushed** — two relaxed groups, a fresh backend over the same store: both read back from one recovery apply, mark 2.
- **On a store that cannot sync, every group is applied at once and nothing is journaled** — `durability: 'process-crash'`: no appends, one apply per group, `whenDurable()` resolved.
- **A deferred apply that rejects fails the held durables and latches the backend** — `beforeApply` throws on the timer's apply: `whenDurable()` rejects with `StoreFailedError` carrying the cause, the next flush is refused, the overlay still serves the group.
- **The codec round-trips puts and a delete with a seq above 32 bits**, and **refuses an unknown version and a length past the end**.
- **The raw-storage conformance suite** over the composition, persistent, reopen a fresh backend and driver over the same store (40 cases, one pending as for every identity-less backend).

- **Backpressure and `window-overrun` are not re-tested here.** They are `SyncDeadlines`'s rules, covered by `packages/db-p2p/test/sync-deadlines.spec.ts`; the backend only passes `deadlineFor`, `mustSyncNow`, `take(owedSince)` and `failAll` through as the file log does. # Journal batch backend (design, as implemented)

## Why a journal

The maintainer's decision (2026-10-15) asks the browser and React Native backends to commit each write group atomically, keep write order across a power cut (what survives is a prefix of the groups, in order), sync by each group's window deadline, and sync at once when the window is 0. Neither engine can do the last three by committing groups directly:

- **IndexedDB** can make one transaction durable (`durability: 'strict'`), but cannot sync earlier relaxed transactions later. A strict transaction after relaxed ones would need the browser to persist transactions in order, which the IndexedDB specification does not promise.
- **LevelDB** (behind React Native, and behind IndexedDB in some browsers) syncs only its current log file on a synced write. When it switches to a new log file it closes the old one without syncing it (`DBImpl::MakeRoomForWrite`), so a later synced write does not cover unsynced writes left in the old file. Its recovery under default options also skips a damaged log record and keeps the records after it (`DBImpl::RecoverLogFile`). Either way a power cut can keep a later write and lose an earlier one.

A journal removes the dependence on the engine's ordering:

- A **relaxed** group (window greater than 0) is written as **one journal record**, numbered by a sequence, in one atomic unsynced write. It is not applied to the stores reads come from. It survives a crash of the process, so a restart can replay it. The `WriteGroup` overlay above keeps serving its writes until the group is durable.
- An **apply** is one atomic **synced** write that applies, in order, every journal record not yet applied (plus, for a strict group, the group itself), records the sequence it applied through, and deletes those records. The apply carries all the data it applies, so its durability depends on nothing written before it.
- **Recovery** at open reads the journal, drops records at or below the applied-through mark, applies the run of consecutive records after it, and discards everything after the first missing number. A lost record (a damaged LevelDB log record, an IndexedDB transaction the browser did not keep, an unsynced old log file) is a missing number, and nothing after it is applied. What survives is a prefix.

Every apply is synced before the next one starts, so a later apply can never survive without an earlier one.

## The port

`packages/db-p2p/src/storage/journal-batch-backend.ts`:

```ts
/** One write group recorded ahead of being applied. `seq` counts up from 1 with no gaps. */
export interface JournalRecord {
	readonly seq: number;
	readonly entries: readonly BatchEntry[];
}

export interface JournalContents {
	readonly appliedThrough: number;
	readonly records: readonly JournalRecord[];
}

export interface JournalStore extends Omit<BatchBackend, 'commit' | 'sync'> {
	appendJournal(record: JournalRecord): Promise<void>;
	applyJournal(apply: readonly JournalRecord[], appliedThrough: number, discard: readonly number[]): Promise<void>;
	readJournal(): Promise<JournalContents>;
}
```

The journal records and the mark live in the engine's own keyspace (an IndexedDB object store, a LevelDB tag byte), defined by each store. `applyJournal` deletes the numbers in `apply` and `discard`; a number with no record present (a strict group's) is nothing to delete.

## `JournalBatchBackend implements BatchBackend`

Constructor `(store: JournalStore, options?: { setTimer?: SetTimer; now?: () => number })`.

- **Open (lazy, memoized, awaited by every operation):** `readJournal()`, then `planRecovery`: records with `seq <= appliedThrough` are stale (deleted); the run `appliedThrough + 1, + 2, …` with no gap is applied; every record after the first gap is discarded. If anything is to be applied or discarded, one `applyJournal(run, lastOfRun ?? appliedThrough, stale + discarded)`. The next sequence is one past the last applied. A gap is logged on `journal` (the missing number, how many were discarded, how many applied); stale deletes on `journal:error`.
- **A serial queue** orders open, commits, sync steps, the timer's apply and close.
- **`commit(entries, { syncWithinMs })`**: the deadline is `deadlineFor(syncWithinMs)` at the call. In the queue: open, refuse if closed or failed, take the next seq; if the store's `durability` is not `'power-loss'` or `mustSyncNow(deadline)`, take the cover and `applyJournal([...cover, record], seq, [])`, settle the cover, return a settled `durable`; otherwise `appendJournal(record)` and return `defer(record, deadline)`.
- **`sync()` and the timer**: in the queue, take the cover (the timer passes the moment it fired); empty is a no-op; else `applyJournal(cover, last seq, [])` and settle.
- **Reads** are the store's, after open.
- **Failure**: any store write rejecting latches the backend; held durables reject; later commits and syncs throw `StoreFailedError` with the first cause. A failed open latches for the life of the instance.
- **`close()`**: in the queue, apply whatever is held (only on an opened, healthy backend), then the store's `close` if it has one.
- **Optional members** forwarded only when the store has them; `durability` is the store's.

## Record codec

`packages/db-p2p/src/storage/journal-record-codec.ts`: `encodeJournalRecord(record): Uint8Array` and `decodeJournalRecord(bytes): JournalRecord`; a version byte, the `seq` (8 bytes big-endian), an entry count (4 bytes), then per entry the UTF-8 JSON of its `StoreKey` length-prefixed (4 bytes), a flag byte (1 put, 0 delete), and for a put the value length-prefixed (4 bytes). Decode throws `JournalRecordDecodeError` for an unknown version, a bad flag, a malformed key, a length past the end, or trailing bytes; a store treats such a record as missing, which recovery handles as a gap.

## `SyncDeadlines` as it landed

The backend follows the five rules the implement ticket recorded: the deadline is taken when `commit` is called; `mustSyncNow(deadline)` is checked before `defer`, so a commit that applies at once is never deferred; the timer's step passes the time the timer fired to `take`; `subject` is the store's identity; and `defer` is called with no await between the append resolving and it (the append's own failure throws first, and nothing else on the queue can latch in between).
