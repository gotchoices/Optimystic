# Every log entry and transaction carries its HLC

Second of the three Stage 1 tickets of docs/crdt-sync.md §Migration Path (`the-hlc-clock-and-its-persistence-port` landed the clock; `a-node-observes-the-hlcs-it-reads-and-stores`, in `implement/`, feeds it). This one puts the hybrid logical clock value on the wire and in the log. It changes no ordering: the revision is still the order within a collection, the log-tail cohort still sequences, and nothing compares two HLCs except the clock's own `observe`.

## What landed

**Three places carry one value per write.** `LogEntry.hlc` beside `timestamp` (two facts: the wall time the writer read, and the HLC whose `wallMs` may sit above it after an observed jump). `Transaction.hlc`, minted at commit after the read set is final, so it sits above every HLC a read observed, and therefore on the transaction rather than the stamp (stamp ids are unchanged). `PendRequest.hlc`, optional on the wire because an older writer sends none, set by every writer this build has, so a storage node observes the HLC of every write it stores without parsing log blocks out of transforms. The transaction and the entry agree for one write because `writeContextOf` copies `transaction.hlc` into `WriteContext.hlc` and `applyActionsToCollection` stamps that on every participant's entry, exactly as `timestamp` travels. `pendRequestForBatch` in `NetworkTransactor` spreads the request's other fields onto each per-coordinator batch, so the pend-level value survives a split (by inspection; no code change was needed there).

**Four sites mint, all from the writer's clock** (`clockOf(transactor).now()`, or the node's clock where there is no transactor): `Collection.syncInternal` beside the action id and timestamp; `TransactionSession.commit` after `getReadDependencies()`, through a new `TransactionCoordinator.clock` getter (chosen over exposing the whole transactor); the Quereus bridge's `legacyTransaction`, now given the batch's transactor; `OfflineQueue.enqueue`, which mints `Entry.hlc` beside `queuedAt` from the first sealed collection's transactor, journals it (`JournalEntryRecord.hlc`, the plugin's `EntryRecordV1.hlc`), and re-supplies it on every drive as `HeadCommitOptions.hlc` or `EntryCommit.hlc`; and `applyInvalidation`, which mints the compensating entry's HLC from `InvalidationContext.clock`. Everything else stamps what it is handed: `stageAttempt` and `applyActionsToCollection` stamp the identity's or context's value, a resumed head commit re-sends the recorded attempt whole, a validator's re-execution stamps the transaction's own, and a refresh's `completeOwnEntry` re-sends the retained transforms.

**Identity.** `createTransactionId(stampId, statements, reads, hlc)` folds the HLC in, so two transactions that differ only in when they committed differ in id, which is the action id the log records. `clientSignaturePayload` folds it in too and `CLIENT_SIG_VERSION` is `txsig:v2`; the HLC's three fields are written in one fixed key order in both preimages (`canonicalHlc`), so a value rebuilt by hand hashes like a round-tripped one. The mixed-version cost (a `v1` signer refused by a `v2` verifier) is accepted on the validity marker's precedent and recorded at the constant; no deployment wires a verifier today. `TransactionValidator.validate` is the one wire ingress that tolerates a transaction without an HLC: it derives the payload's value from the stamp's time so the check is well-typed, and hands the transaction object on unchanged, so a re-execution stamps exactly what the writer stamped.

**Legacy entries and records.** `LogEntry.hlc` is required on the type, so every writer this build has must set it; a stored entry from before the field lacks it and is read through `hlcOf` in `packages/db-core/src/log/struct.ts` as `legacyHlc(entry.timestamp)`, the only reader rule. A journal record from before the field restores with `legacyHlc(queuedAt)` (`OfflineRestore.restoreOne`). The upgrade-check fixtures pass unchanged with no documented step and nothing retired: an entry without the field reads as before, the fixtures' in-flight pend carries no `hlc` and is applied as before, and the diary appended on top gets entries the older code never reads.

**Every entry kind carries one.** `Log.addCheckpoint(pendings, rev, times)` and `Log.addInvalidation(..., rev, options)` now take the HLC through an `EntryTimes` options object (`hlc` required, `timestamp` defaulting to now) rather than positional defaults; `AddActionsOptions` is `EntryTimes` plus `collectionIds` and `reads`, and is no longer optional. `addInvalidation`'s `cascadeRoot` and `timestamp` moved into `AddInvalidationOptions`. No caller writes a checkpoint today (backlog `debt-the-collection-log-never-writes-a-checkpoint`).

## Decisions a reviewer should weigh

- **`InvalidationContext.clock` is a required `HlcClock`, not a transactor.** The ticket said to mint through `clockOf(transactor)`, but the dispute layer's apply primitive has no transactor: its context is a log, a block-storage factory and a flush. The node's own clock is what the entry should carry, so the context takes it directly, and `CollectionEnv` (the cascade's per-collection environment) carries it on to each child invalidation. No production code builds either today (`onInvalidate` is deliberately unset on live nodes); the third ticket's node wiring will supply `node.hlcClock` when a composition root does. Tests build a `new HlcClock({ nodeId: 'test' })`.
- **The re-send of a retained attempt carries no pend-level `hlc`.** `completeOwnEntry` is handed an `ActionEntry`, not the `LogEntry`, and `InFlightAttempt` does not carry the HLC separately; the write's HLC is inside the log entry in the retained transforms. A member that missed the first pend and stores the re-send observes the HLC when it next reads the entry, not at the pend. Recorded as a `NOTE:` at the re-send, with the remedy (retain the HLC on `InFlightAttempt`) if a feed point at the pend ever becomes load-bearing. `TransactOptions.hlc` is optional for this one caller.
- **The queue mints from `sealed[0].transactor`, not through `sharedTransactor`.** The stranger check in `sharedTransactor` throws, and an enqueue that has already sealed must not fail on it; it still runs, and throws, at the send, exactly as before. `enqueue` also accepts `init.hlc` beside `init.timestamp`, for tests.
- **`TransactionSession.execute`'s temporary translation transaction mints an HLC too**, since the field is required and the value is never read (the engine translates and commits nothing). It advances the clock by one logical count per statement, which is harmless; a `legacyHlc` placeholder would have been a lie about provenance.
- **The validator's legacy fallback applies to the signature payload only.** Passing the transaction through unchanged means an older writer's re-execution stamps `undefined`, which JSON drops, so the operations hash matches the writer's entry; wrapping it in `legacyHlc` would have made the hashes disagree. Reachable only with a `ClientSignatureVerifier` or validator wired against an older writer, which no deployment has.
- **The `NOTE:` at `WriteIdentity.hlc`** records the accepted imprecision: a write refused as stale is retried over a refresh that may have observed newer HLCs, and keeps the HLC it was first minted with, so its entry can carry an HLC below a rival it was re-staged over. Observational today; the replay stage commits locally without a log-tail retry.

## Tests

- `packages/db-core/test/retry-resends-identical-transforms.spec.ts`, extended: each of the four cases now also asserts that the committing attempt's log entry carries an HLC whose `nodeId` is `'test'` (the `TestTransactor`'s), the one fact the whole-transform-set comparison cannot pin, since two attempts could agree on a missing field.
