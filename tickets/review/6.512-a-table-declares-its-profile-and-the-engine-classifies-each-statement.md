# A table declares its profile, and the engine classifies each statement

Second of four implement tickets from the plan `a-transaction-carries-its-lane`. Implemented as the ticket describes, with three deliberate deviations recorded below for the reviewer. No admission rule changed: the lane is computed, recorded and carried, and nothing admits, refuses or merges by it.

## What landed

- **Two tags** (`declared-tags.ts`): `"optimystic.profile"`, read `=== 'replay-permitted'`, every other value `strong` (the default); `"optimystic.merge"`, read `=== 'last-writer-wins'`, every other value no merge. An unrecognised value is logged once per table (`optimystic:profile-tag-ignored`) and once per column (`optimystic:merge-tag-ignored`) by the vtab, at construction and on every `table_modified`, and never refused. Both tags were already in the schema hash: verified by reading `generateTableDDL` in `@quereus/quereus/src/schema/ddl-generator.ts`, which renders the table-level `with tags (…)` clause and each column's, and `computeSchemaHash` digests that text through `schema()`. Said so in the module doc of `declared-tags.ts`.
- **The rule** (`lane.ts`), in two exported layers as the next ticket needs them. `laneCeilingOf(write, table)`: `serializable` when the profile is not `replay-permitted`; when a `unique`, `foreign-key-child`, `foreign-key-parent` or `assertion` constraint, a cross-row `check`, or a `primary-key` constraint on a non-INSERT is listed; for an UPDATE with a `global` selection; for every DELETE; for an UPDATE assigning a column with no merge tag; for an upsert with a `do update` clause. `laneOf(write, table)`: the ceiling, then `serializable` when `reads` is non-empty or `selfIndependent` is false, or when an INSERT's key can collide (table not content-keyed and no key column fresh, by label or by `optimystic.fresh` tag); `undefined` (a cascade child write) is `serializable`. `transactionLaneOf(records)` folds the `lane` facts with `stricterLane` and answers `serializable` on any `undescribed` record or none at all. The idempotence note and the three `NOTE:`s (tombstone merge for deletes, `'counter'` merge kind, index trees) are at the rule.
- **Recording and the four routes.** `noteWriteDescription(write, table)` records `{ kind: 'lane', lane }` beside the statement's `statement` record, once per described `TableWrite` object (the existing weak set), so a savepoint rollback truncates both. `TransactionBridge.openLane()` folds; `commitTransaction` reads it once and hands the one value to `session.commit({ lane })`, `legacyTransaction(transactor, lane)` (now a required parameter), `tree.sync({ lane })` per tree of the sweep, and `OfflineMode.enqueue(collections, transactionId, facts, lane)` → `OfflineQueue.enqueue(…, { lane })`. `Tree.sync` in db-core gained an optional `SyncOptions` parameter, forwarded to `updateAndSync`.
- **A tag change under queued entries.** `followSchemaTags` compares the profile and each column's merge before and after the overlay (`laneDeclarationChanged`) and, when something moved and `OfflineMode.queuedTransactionsOf(table)` lists anything, logs `offline:profile-changed-with-entries-queued` naming the transactions. Nothing else: each entry keeps the lane fixed at enqueue.

## Deviations from the ticket, for the reviewer

- **Where the tag constants live.** The ticket put the two new constants beside `CONTENT_KEY_TAG` in `optimystic-module.ts`. The rule in `lane.ts` has to read `optimystic.content_key` and `optimystic.fresh` too, and the vtab imports `lane.ts`, so constants in the vtab module would make a runtime import cycle. All five declared-hint tags (`fresh`, `single_writer`, `content_key`, `profile`, `merge`) and their `=== true` readers moved to the new `schema/declared-tags.ts`, imported by both. `NETWORK_WATCH_TAG` and `OFFLINE_POLICY_TAG` stayed where they were, since only the vtab reads them.
- **The content-key exemption sits in the writer-only clause, not the ceiling.** The ticket's ceiling text said a `primary-key` constraint is `serializable` when "the table is not tagged `content_key` and the operation is not an INSERT". Read literally, a key-moving UPDATE on a content-keyed table would then be `convergent` at the ceiling, contradicting the ticket's own "an UPDATE that assigns a key column is `serializable`". The ceiling therefore says `primary-key` on anything but an INSERT is `serializable`, and the content-key tag is consulted only where the ticket's writer-only clause judges an INSERT's key. For an INSERT the two readings agree.
- **A composite key is fresh when ANY key column is**, not every column. The ticket's writer-only clause said every primary-key column must be fresh. One column unique per call with 128 bits of entropy makes the whole composite key unique, which is the rule `freshElementsOf` already applies for the outlook (docs/offline-sync.md §Judging each guard), so the lane uses `anyFresh` over the description's fresh labels plus the `optimystic.fresh`-tagged key columns. A stricter "every" rule would make a `(tenant, StampId())` key `serializable` for no safety gain.

## Use cases for testing and validation

- `create table t (Id text primary key, Title text with tags ("optimystic.merge" = 'last-writer-wins')) using optimystic(…) with tags ("optimystic.profile" = 'replay-permitted')`, then `insert into t values (StampId(), 'a')`: the commit's log entries (main tree and any index tree) carry `lane: 'convergent'`; in offline mode the `queued` status reports `lane: 'convergent'` and the journal record stores it.
- The same insert with `:id` bound from the application: `serializable`, unless `Id` is tagged `optimystic.fresh`.
- `update t set Title = :v where Id = :id`: `convergent`; `update t set Title = :v where Title = :old`, `update t set n = n + 1 where Id = :id`, any `delete`: `serializable`.
- A transaction writing `t` and an untagged table: `serializable` on every participant.
- `alter table t set tags ("optimystic.profile" = 'maybe')`: logged once as `optimystic:profile-tag-ignored`, the table stays `strong`, no error. Changing the profile with entries queued for the table: logged as `offline:profile-changed-with-entries-queued` with the transaction ids; the queued entries' lanes are unchanged.

## Known gaps and things to look at

- **No end-to-end check that a SQL commit's log entry carries the classified lane.** The four routes were changed by hand and read; no spec commits through the plugin and reads `laneOf` off the entry. The previous ticket's db-core test covers `SyncOptions.lane` → entry, and `session.commit({ lane })` → `Transaction.lane` is read in `session.ts`; the plugin side rests on inspection. A reviewer who wants one could extend an existing two-handle legacy spec with a `replay-permitted` table and read the main collection's `committedActionId` entry.
- **`insertKeyIsFresh` reads `table.primaryKeyDefinition` of the vtab's own `tableSchema`.** Same object the vtab reads the key from, so it agrees with staging; in the spec it is Quereus's memory-table schema, which has the same shape.
- **The merge rule requires every ASSIGNED column to carry the tag**, and says nothing about unassigned ones. Two machines each setting a different merge-tagged column of one row are both `convergent`; the replay stage will have to merge per column, which is what `last-writer-wins` on a column implies. Recorded in the rule's doc, not as a `NOTE:`, since it is the design rather than a tripwire.
- **`queuedTransactionsOf` is public on `OfflineMode`** (previously internal to `assertNoQueuedEntries`), so the vtab can ask without throwing. It carries the same two-tables-over-one-URI caveat the assert had.
- The `tickets/.garden-report.md` change in the working tree is not this ticket's; left as found.
