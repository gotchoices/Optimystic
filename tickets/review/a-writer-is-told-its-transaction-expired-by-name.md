GitHub issue #24, writer side. The prereq made skewed members cast signed expiry votes and made the cluster coordinator raise `TransactionExpiredError`; this ticket gets that verdict to the application that wrote.

# What changed

**Returned refusal, sibling variant.** An expiry crosses the repo protocol as `ExpiredFailure` — `{ success: false, conflict: false, reason, expired: TransactionExpiry }`, where `TransactionExpiry = { expiration, memberClocks, coordinatorClock }` — a sibling of `StaleFailure` in `PendResult` / `CommitResult` (`WriteFailure = StaleFailure | ExpiredFailure`). The fields it can never carry (`missing`, `pending`, `staleAt`) are typed `never`, and `StaleFailure.expired` is `never`, so consumers still read `reason`/`staleAt`/`missing` off any failure unnarrowed, while a producer cannot build "expired and conflict" as a fresh literal and an `ExpiredFailure` is not assignable to `StaleFailure` (so a site typed `StaleFailure` that receives a failure fails to compile). `isExpiryFailure` in `stale-failure.ts` is the one predicate; `isConflictFailure` returns false for an expiry.

**One error class.** db-core's `TransactionExpiredError` is now the only class: the cluster coordinator constructs it, `CoordinatorRepo` returns `error.toFailure()`, and both write paths construct it again from the returned facts. It is deliberately no longer a `ValidatorRejectionError` (the prereq's design); the class comment says why — `CoordinatorRepo` converts it before its validator-rejection classifiers run. Fields: `expiration`, `memberClocks`, `coordinatorClock`, `localClock` (the clock of the node raising it), `apparentSkewMs = max(memberClocks) − localClock`. At the writer that is how far the refusing members' clocks appear to be from the writer's own, which is the useful number when the writer is the one behind and the coordinator is remote (the coordinator's own skew is ≈ 0 then). The message is written for a person: "The transaction expired before the cohort could accept it: by their own clocks, N cohort member(s) found its expiration (ISO) already past. Their clocks appear to be about X s ahead of this device's. This is a clock disagreement … correct the clock of whichever device is wrong — this one, or the refusing members." It never contains "super-majority".

**Coordinating repo.** `pendThroughCluster` and `commit` return the expiry first in their catch, ahead of `ConflictRaceLostError` and ahead of the stale classifiers — even where local storage shows a rival at the requested revision, because every reject was a clock verdict.

**Transactor.** `NetworkTransactor.pend`'s hand-built aggregate is replaced by `refusalFrom`, the same rebuild commit already used (behaviour otherwise identical: first `reason`, `some` conflict, highest `staleAt`, distinct `missing`). An expiry in any batch is returned verbatim as the aggregate (first one wins) — a conflict beside it must not make the write look retryable.

**Write paths.** `Collection.syncAttempts` throws `TransactionExpiredError` on the first expiry refusal, before touching the failure counters or retaining the attempt; staged actions stay staged. `TransactionCoordinator`: `pendCollection` throws it, `pendPhase` carries it (it counts as hard, so no stale-loss retry), `commitCollection` returns it as not-stale (it used to map every returned commit failure to `stale: true`, which would have re-driven an expiry up to `maxAttempts`), and `commitOnceLatched` throws it — or puts it as the `reason` of `CoordinatorPartialCommitError` when a sibling already committed; `reportSaved` wraps it the same way after a refresh-saved participant. `execute()` was not changed (it returns a string `error` and has no retry loop).

# Known gaps for the reviewer

- **Expiry on a commit sweep leaves the log entry behind.** When `NetworkTransactor.commitTailThenSweep`'s tail round succeeds and a sweep cohort refuses as expired, the tail is stored, and both write paths throw at once with no refresh, so the attempt's log entry stays with none of its data — the same state the budget-exhausted exit leaves. Needs a sweep cohort whose clocks disagree while the tail's agree (multi-coordinator layouts only). NOTE at the throw in `syncAttempts`; arm appended to `tickets/backlog/bug-a-refused-write-can-leave-its-log-entry-behind.md`. Not tested (no mesh fixture forces two commit batches; see `debt-no-mesh-fixture-forces-two-coordinator-batches`).
- **`completeOwnEntry` re-send refused as expired** is retried as `completion-refused` each round until the budget ends. Reachable only if clocks start disagreeing between a write's attempts. Recorded as a NOTE tripwire there, not changed.
- **Mixed hard failures in the coordinator.** If one collection's pend is refused as expired and another fails hard for a different reason, the commit surfaces the expiry (first expiry wins), hiding the other failure until the clock is fixed. Same rule in `refusalFrom` across batches. Deliberate; say so if you disagree.
- **Coordinator-side message wording.** When the cluster raises the error at a remote coordinator, its message says "this device" for the coordinator, though the writer set the expiration. That text only reaches coordinator logs and the refusal's `reason`; the writer builds its own message from the facts.
- **Mixed versions.** A writer on an older build talking to an upgraded coordinator receives an `ExpiredFailure` it does not know: it reads it as a reason-only, `conflict: false` refusal (hard failure in the coordinator; `Collection.sync` retries it to exhaustion as before). An older coordinator still throws. No version gate added.
- **Public API changes** (no compatibility kept, per AGENTS.md): `PendResult`/`CommitResult` widened; `isConflictFailure` takes `WriteFailure`; db-p2p no longer exports `TransactionExpiredError` or `formatInstant` (db-core does); `TransactionExpiredError` is no longer a `ValidatorRejectionError` and lost `rejectReasons`.
- `memberClocks` off the wire is trusted as numbers (as the coordinator already trusts `expiredAt` after `expiryRejectionClocks`' finite check); a malformed coordinator answer would give `apparentSkewMs` NaN, not a throw.
