# A write names the blocks it committed

Part of GitHub issue #26 (a SQL app learns its commit's durability, and when it becomes full). The db-core half of "map the full-replication event back to the commit the app knows". The consumer is ticket `a-sql-commit-learns-when-it-becomes-fully-held`.

## What changed

`WriteDurability` has a new optional, action-level field:

```ts
readonly blockRevs?: Readonly<Record<BlockId, number>>;
```

Every block the write committed, with the revision it committed at. It is set client-side only, never by a coordinator, and is never on the wire. The `BlockDurabilityReachedEvent` (keyed by block + revision, never by action) is matched against it: a block is covered by an event naming it at its revision or later.

- **One helper sets it**: `withBlockRevs(d, blockIds, rev)` in `packages/db-core/src/network/durability.ts`. It max-merges with any `blockRevs` already on `d` and leaves out every id in `d.torn`.
- **Three set-sites**, one call each:
  - `TransactorSource.transact`, on a successful commit: `pendResult.blockIds` at `rev`. This covers every `Collection.sync` attempt and the own-entry re-send in `Collection.completeOwnEntry`.
  - `TransactionCoordinator.commitCollection`, on success: its `blockIds` at the pended `rev`.
  - `Collection.settleUnfinished`, "superseded but saved" return: `entry.blockIds` at the write's own `rev`, and only when `getLineage` returned a durability. When it returned none, the answer stays `undefined`.
- **Merging**: `mergeDurability` treats it like `torn`. It is taken over the ORIGINAL reports (union, max revision per block, then minus every torn id), and `stripMergedFields` strips it, so it never appears inside `otherCohorts` and never enters `distinctReports`' key. `withTornBlocks` removes newly torn ids from it. An empty map is left off, as an empty `torn` is.
- `recordCollectionDurability` / `transactionDurability` are unchanged and carry it through `mergeDurability`. So `TransactionDurability.overall.blockRevs` names every block of every collection, and `CoordinatorPartialCommitError.durability` names exactly the committed half.
- `settleUnfinished` gained a `rev !== undefined` term in its saved condition. This changes no behaviour: `lineage` is only asked for when `rev` is defined. TypeScript cannot see that.

## Tests

- **Added** — `packages/db-core/test/durability.spec.ts`, "names every committed block at its highest revision, never a torn one, and a merge of a merge equals the flat merge". It pins:
  - max-revision-wins for a block named at two revisions;
  - a torn block left out, both by `withBlockRevs` and by the merge, even when another input names it committed;
  - `blockRevs` absent from every `otherCohorts` entry;
  - nested merge deep-equals the flat merge.
- **Adjusted, not added**: `write-durability-reaches-the-writer.spec.ts` and `multi-collection-commit-durability.spec.ts` deep-equalled the writer's answer to the transactor's stamped report. That answer now also carries `blockRevs`, under random block ids. Each spec gained a local `answered()` helper that strips `blockRevs` before comparing, so they still pin "the transactor's class reaches the writer unchanged".
- **No test for the three set-sites**, per the plan: each is one helper call, and the consumer ticket's end-to-end test covers them. The failing runs before the adjustment did show `blockRevs` arriving through `Collection.sync`, `Tree.sync`, `Diary.append`, `updateAndSync` and the coordinator. Now nothing asserts it. A reviewer who wants a pin can add one assertion to an existing case rather than a new test.

## Things for the reviewer to weigh

- **Torn wins over committed in a merge.** If one input of a write tore block X and another named X committed, the merge leaves X out. That is the plan's rule ("torn ids absent from the result"), and it is safe: a write with any `torn` block is never `isFullyDurable`, and torn blocks never heal by replication. So a host should treat a torn write as never becoming full, whatever events arrive. The consumer ticket should state that.
- **Deleted blocks are named.** `pendResult.blockIds` / the commit's `blockIds` include deleted blocks. I checked by reading the code: `CoordinatorRepo.noteReplicationShortfall` records a ledger entry for every `request.blockIds` entry except torn ones, so deletes are tracked and can produce events. Not verified by a run.
- **A write answered `full` may get no event at all.** A `full` commit settles the ledger instead of recording an entry. The consumer must check `isFullyDurable` on the answer first and only wait on events for a write answered below `full`. That is consumer-ticket territory; flagged so it is not missed.
- **No `blockRevs` where durability is `undefined`.** This covers the status-read branch of `completeOwnEntry`, `settleUnfinished` when `getLineage` had no durability, and a `recordCollectionDurability` merge where either side is `undefined` (this drops the known side's `blockRevs` along with its class). All are documented as "saved, holder unknown". The consumer treats such a write as one it cannot follow.
- **A sync whose loop commits more than one batch** (the `hasUnsyncedChanges` re-entry) unions the blocks of several actions into one answer. That matches "every block this write committed".
- A remote coordinator never sets the field, and nothing is added to any request or response, so mixed-version peers are unaffected. I checked this by reading the code: no db-p2p source references `blockRevs`.
