# A coordinator runs an action's collections as one record

Second of three tickets for GitHub #42 (first: `a-consensus-record-carries-several-collections-of-one-action`, landed; third: `a-transaction-pends-and-commits-its-collections-together`, which makes the writer use this). A **batch** is one action's pends, or one action's commits, of several collections, with no block in two requests (`batchShapeFault` in `packages/db-p2p/src/cluster/record-operations.ts`).

## What landed

- **Interface.** `IRepo.pendMany?` / `IRepo.commitMany?` (`packages/db-core/src/network/i-repo.ts`): one record, one answer, success only if every request was accepted; a malformed list throws. Optional: `CoordinatorRepo`, `RepoClient` and the proxies implement them; `StorageRepo` does not.
- **Batch shape.** New `packages/db-p2p/src/repo/request-batch.ts`: `pendBatchOf` / `commitBatchOf` validate (empty list → throw; `batchShapeFault` → throw `Malformed batch: …`) and give the record's `operations`, the action id and the union of blocks in request order. `forwardedBatchMethods(repo)` lets a wrapper forward the two methods exactly when the wrapped repo has them.
- **`CoordinatorRepo`.** `pend` = `pendMany([request])`, `commit` = `commitMany([request])`; one code path. Site by site, as the ticket specified:
  - responsibility, `clearStuckReservations`, `answerBlocksHeld` / `corroborateHeldBlocks`, `takeLatePendRefusals`, `markBlocksSeen`, the holder report: over the union (each block judged against the request that writes it where a request field matters);
  - `classifyStaleRejection`: each block against its own request's `rev`; a confirmation on any request answers the batch; `staleAt` is the highest across requests, and the reason prose names that block's own requested revision;
  - `confirmCommitRivalAgainstLocal`: per request (new `commitRevisionHolder`, the old single-request logic unchanged), then a rival on any request → stale loss with highest `staleAt`; `'own-durable'` only when every request is;
  - solo and fallback paths apply each request in order, stopping at the first refusal (`applyPendsInOrder`, `applyCommitsInOrder`, folded with `foldPendResults` / the now-exported `foldCommitResults`); the solo commit mints one proof over the whole batch message;
  - the post-consensus local commit fallback (`applyCommitsAfterConsensus`) judges divergence per request: a tolerated divergence (missing pend throw, or `missing-base-revision` with consensus reached) is noted and the loop **continues** applying the remaining requests, then the batch goes to `tolerateLocalCommitDivergence` since this node does not hold all of it; any other refusal stops the loop and is the answer;
  - the under-replication ledger records per block at that block's own request's `rev` / `actionId`;
  - the accepted-tradeoff `NOTE:` (one answer for the whole batch) sits on `commitThroughCluster`.
- **Wire.** `RepoService` refuses (throw → logged → stream abort) a multi-operation message that fails `batchShapeFault`, and hands a batch to `runBatch` → `repo.pendMany` / `commitMany` (throwing if the repo lacks them). The redirect key is `deriveMessageKey`: a one-operation message as before, a batch keyed on its first block (`getAffectedBlockIds(...)[0]`). `RepoClient.pendMany` / `commitMany` send every operation in one message, with the two `NOTE:`s (frame limit; an older coordinator reads only the first operation).
- **Proxies.** `createServedRepoProxy` forwards both to the coordinated repo and throws before assembly (no local-storage fallback — a batch is a coordinator's job). `stateHoldingsOnReads` (the production wrapper the plugin and reference peer put in front of every `RepoClient`) and the mesh harness's `arrivingFrom` spread `forwardedBatchMethods`.
- **Docs.** `docs/internals.md` (§One commit round…: the coordinator side of a batch; §Inbound Stream Authorization parenthesis), `packages/db-p2p/docs/repo.md` (RepoService refuses / dispatches batches), `packages/db-core/docs/network.md` (IRepo sketch). The `NOTE:` on `highestStaleAt` (`packages/db-core/src/network/stale-failure.ts`) no longer claims a pend never spans collections; an arm was appended to backlog `debt-multi-collection-retry-cannot-see-the-taken-revision` saying a batched `staleAt` names one collection among several counters.

## Deviations from the ticket text — check these

- **Redirect key ignores `message.coordinatingBlockIds`.** The ticket said "`coordinatingBlockIds[0]` when present". `RepoClient` never puts `coordinatingBlockIds` on the wire and `RepoService` never passes one to the repo, so `CoordinatorRepo` resolves the batch's cohort for the union's first block. Keying the redirect on a field the coordinator never sees could only make the two disagree, and honouring an off-the-wire coordinating list would be new trust surface (backlog `debt-sender-side-coordinating-block-binding-is-unchecked`). So the key is the batch's first block — "the block CoordinatorRepo resolves the cohort for", which was the stated intent.
- **`stateHoldingsOnReads` forwards the batch methods.** Not listed in the ticket, but it is the production wrapper in front of `RepoClient`; without it the plugin's transactor would never see `pendMany` and the next ticket's writer would fall back silently.
- **Commit fallback keeps going after a tolerated divergence** (see above) rather than stopping. Reasoning: those requests reached consensus, so landing them makes this node hold more of the record; the answer is the same either way.
- **Log field.** `coordinator-repo:commit-not-durable` now carries `revs` (array) instead of `rev`; its reason prose says `rev N` for one request (unchanged text) and `revs N, M` for several. No doc listed that field.

## Known gaps for the reviewer

- **No direct test** of `RepoService.runBatch` / the malformed-batch refusal, `RepoClient.pendMany` over a real stream, the served proxy's batch members, or any `commitMany` arm with more than one request (fallback divergence, rival confirmation across requests, solo batch commit). The happy path is pinned end to end by the SQL request-count spec the next ticket re-pins; the rest is by inspection. A reviewer may judge the `confirmCommitRivalAgainstLocal` combination rule (rival beats own-durable on another request) worth one spec.
- **Spec-supplied `wrapRepo` wrappers do not forward the batch methods** — `aged-writer-slot-hold`, `reset-does-not-strand-its-own-pend`, `rival-superseded-only-by-a-writer-that-built-on-it`, `routing-key-convention-divergence`, `torn-commit-cancels-abandoned-blocks`, `test/util/node-count-mesh.ts` (db-p2p) and `two-node-lagging-replica-multi-collection-commit` (quereus plugin). Harmless now; once the writer batches, those specs will exercise the per-collection fallback instead. Whether each should forward (`forwardedBatchMethods`) is the next ticket's call per spec — some inject faults into `pend`/`commit` deliberately.
- **Pend refused part-way leaves earlier requests' pending records** (solo and fallback paths): by design, the writer's refused-pend path cancels the whole action (`NetworkTransactor.pend`); the doc comment on `applyPendsInOrder` says so.
- **Mixed builds**: an older coordinator answering a batch after reading only its first operation is a silent partial commit; only the `NOTE:` at `RepoClient.pendMany` records it (mixed versions are out of scope per AGENTS.md).
