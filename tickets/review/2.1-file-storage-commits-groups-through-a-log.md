# File storage commits groups through a log

Second of three tickets from `file-storage-pays-one-fsync-per-write-group` (GitHub #37). `write-group-overlay-driver` (in `review/`) holds a group's writes in memory and hands them to a `BatchBackend.commit`; this ticket is the file backend's `commit`, built as a write-ahead log. Checkpointing, the shared log for `FileKVStore` and the README rewrite follow in `file-store-checkpoint-and-shared-log`.

## What landed

- **`FileRawStorage`** (`packages/db-p2p-storage-fs/src/file-storage.ts`) is now `KvRawStorage` over `WriteGroupDriver` over `FileBatchBackend`. The constructor `new FileRawStorage(basePath, options?)` stays synchronous; `options` is the driver's `WriteGroupOptions` (`idleFlushMs`, test-only `setTimer`). `close` is declared always-present beside `listBlockIds`, `getApproximateBytesUsed` and `getStoreIdentity`. `FileStoreDriver` is gone: its reads, listings, path helpers, colon encoding, legacy raw-colon fallback and the corrupt-JSON-reads-as-missing guard moved to the backend unchanged; its writes went.
- **`FileBatchBackend`** (`packages/db-p2p-storage-fs/src/file-batch-backend.ts`): maps each `StoreKey` to its tree path (relative, forward slashes, for the log; absolute for reads), awaits the shared log's open before every operation, and turns a batch into log entries — a delete of a pending or materialized record off win32 with a colon in the id adds a second delete entry for the raw-colon sibling, so a replay removes it too. The log is acquired on the first operation, not in the constructor, so an instance `withReadCache` discards unused holds no handle and no lock; `close` releases the reference.
- **`FileWriteLog`** (`packages/db-p2p-storage-fs/src/file-write-log.ts`): `<basePath>/write-ahead.log`, header `OPTIMYSTIC-WAL` plus a version byte, records `[u32 length][u32 CRC-32][payload]` with entries `[u8 kind][u16 path length][path][u32 value length][value]`, CRC from `zlib.crc32`. `commit` runs on a per-log queue: one `write`, one `sync`, then the apply (`mkdir -p`, `writeFile` straight to the canonical path, or `unlink`), resolving after the apply. `open` is memoized: wait for a previous log over the directory still closing, `mkdir` the base, take the lock, replay strictly (torn record, length past the end, CRC mismatch, bad entry, wrong header: stop before it, apply what precedes, log one `write-log` line), fsync every file and directory the replay touched, then open the handle with `'w'`, write the header, sync it and the directory. A `dirty` set (`{ files, directories }`, absolute paths) collects what the tree was given since the last truncation, for the checkpoint ticket. Registry keyed by `fileStoreIdentity` with a reference count; the last `release` waits for the commit in flight, closes the handle and removes the lock, and a log acquired meanwhile opens after that. An I/O failure in open, append or apply latches the log; a `StoreLockedError` is rethrown as-is from every operation. `fsyncDir` moved here from `atomic-write.ts` (which now imports it), and `readFileIfExists` is shared with the backend. The codec is exported (`encodeWriteLogRecord`, `decodeWriteLog`, `WRITE_LOG_HEADER`) so tests can hand-build damaged logs.
- **`acquireStoreLock`** (`packages/db-p2p-storage-fs/src/store-lock.ts`): `<basePath>/store.lock` created `wx` holding `{ pid, hostname }`; same host and `process.kill(pid, 0)` alive refuses with `StoreLockedError`; otherwise stale, replaced, three attempts. Closes the `proper-lockfile` TODO with no dependency.
- **`WriteGroup`** (`packages/db-p2p/src/storage/write-group.ts`): one line — a backend that throws its own `StoreFailedError` has its cause unwrapped into the group's, so a latched log does not produce a `StoreFailedError` wrapping a `StoreFailedError`.
- **`upgrade-check`** reader (`packages/upgrade-check/test/current-build.ts`): keeps the fs `FileRawStorage` instance and closes it in `stop`, so the suite's restart is a real reopen through replay and the lock is released.
- **Docs**: `storage.md` §4 describes the composition; §5 names the backend; the layout block gains `write-ahead.log`, `store.lock` and the `proofs/` directory; Invariant 6's table row for the file backend, the former *file backend's gap* paragraph (now *The file backend*: record shape, write-ahead rule, strict replay, dirty set, lock, registry), write-order items 3 and 7, and the cross-process bullet under the cache are rewritten. `docs/repository.md` Invariant P says "two entries of one write-ahead-log record". The fs README's *Atomic writes* and *Durability* sections are replaced with *Write-ahead log* and a rewritten *Durability* (plus the lock), the layout and tests sections updated, and the "No cross-process lock" limitation replaced by "The lock protects one machine"; the full README rewrite is still the next ticket's. `packages/db-p2p/readme.md` no longer says "atomic writes". The `NOTE:` in `with-read-cache.ts` says why the discarded instance holds nothing.

## How to exercise it

- Any `StorageRepo` over `new FileRawStorage(dir)`: one record per group in `<dir>/write-ahead.log`, `store.lock` beside it, the tree written after the sync. Kill the process after a commit resolved and reopen: the group is back.
- `DEBUG=optimystic:db-p2p-storage-fs:*` shows a replay that stopped short (`write-log`) and a stale lock replaced (`store-lock`).
- `FileWriteLog.acquire(dir)` directly, with `WriteLogEntry` paths, is the log without the kernel; `encodeWriteLogRecord` builds records to damage.

## Tests added

`test/file-write-log.spec.ts`:
- codec round-trip of puts and deletes through one record (UTF-8 path included).
- replay applies every intact record in order and truncates the log to its header.
- a torn final record: records before it applied, log back to its header.
- a CRC mismatch in the middle: the record before applied, the intact record after it discarded.
- a record whose length runs past the end of the file is torn.
- a file that is not a log replays nothing and is replaced by a fresh header.
- a store from a build before the log (tree, no log file) opens over its tree unchanged.
- crash after the sync, before the apply (`fs.writeFile` throws): commit rejects `StoreFailedError`, the tree keeps the prior content, the log is latched and refuses later commits, and the next open rebuilds the tree from the durable record.
- a batch whose record never reached the log (the handle's `sync` throws): nothing in the tree, latched, a retried sync never trusted.
- lock: a live pid on this host refuses from `open`, from a store's read (`StoreLockedError`) and from its flush (`StoreFailedError` with that cause), and keeps the holder's lock; another machine's lock and an exited process's lock (a spawned child's pid) are replaced; two stores over one directory share one log and one lock, the second reads what the first flushed, and the last close removes the lock; a store opened while the previous one is still closing opens after it.

`test/fsync-count.spec.ts`: wraps `fs.promises.open` so every handle counts its `sync`; over a `StorageRepo`, a pend and a commit touching 1 and 8 blocks each issue at most one sync, and a refused pend issues none. The store is opened (one read) before counting, since the open's header sync and directory sync are not a group's.

`test/file-storage.spec.ts`: the conformance registration now closes every store it opened in `cleanup`; the three `.tmp`/`withFailingRename` cases are replaced by: a flushed metadata write sits at its canonical path with nothing beside it (and only the log and lock at the root); a second write replaces the prior value in the tree; a group whose tree write fails after its record is durable is still served from memory, latches the store (later writes and `close` reject), and is replayed into the tree on reopen. The non-ASCII case also checks the bytes on disk; the pending listing case covers a flushed id from the tree beside an unflushed one from memory; the legacy raw-colon delete case (POSIX) asserts the hide-before-flush and the sibling's removal after it. `FileKVStore` cases are unchanged (it still uses `atomicWriteFile`).

Test support: `test/support/tracked-stores.ts` (open stores that an `afterEach` closes before the temp dir is removed) and `test/support/fs-injection.ts` (the `open`/`sync` wrapper and the failing `writeFile`).

## Known gaps and judgment calls for the reviewer

- **A wrong header is replaced, not refused.** Per the ticket, a log whose magic or version is not this build's stops the read before anything and is then truncated to a fresh header, with one `write-log` line. A log from a newer format would be discarded silently apart from that line. Refusing to open would be the safer direction; the ticket chose the other, and I followed it.
- **A sync that throws may still leave its record in the file.** The failed commit latches the log and the writer is told it failed, but the bytes were written before the sync rejected, so the next open can replay a group its writer was told was lost. That is the ordinary "unconfirmed write may or may not survive" case, and the test asserts only the pre-reopen state. Rule 5 is why nothing tries to truncate it back out.
- **The log grows for the store's life.** No checkpoint until `file-store-checkpoint-and-shared-log`; only a reopen truncates it. The `dirty` set grows with it. Both are `NOTE:`d at the class. Replay reads the whole file into memory (`NOTE:` at `replay`).
- **`dirty` is two sets** (`files`, `directories`), not one, since the checkpoint syncs files then directories. Directories are marked as a superset: when `mkdir -p` created anything, every directory from the file's up to the base is marked, because the created path it returns comes back in `\\?\` form on win32 and comparing it was not worth the risk.
- **Replaying a put under a path with `..` is not refused.** Block ids come from the kernel and are random or collection names; a check at replay alone would make a log the store itself wrote unreplayable, so neither side checks. The CRC covers corruption.
- **The lock's create and content write are two steps**, so two processes starting over one directory in the same microseconds could each judge the other's empty lock stale (`NOTE:` at `acquireStoreLock`).
- **A commit on a backend after its `close()` reacquires the log** instead of throwing; `WriteGroupDriver.close` flushes first and disarms the idle timer, so nothing in the tree does this.
- **`StoreLockedError` on a read is raw; on a flush it arrives wrapped** in `StoreFailedError` (the group latches on the rejected commit). The test pins both shapes.
- **Open creates `basePath`** (the lock and log live there), so `listBlockIds` over a directory that did not exist now creates it; the case's title says so.
- **`approximateBytesUsed` now counts the log and the lock.** Noted in its doc comment.
- **`FileStoreDriver` is removed from the public exports**, replaced by `FileBatchBackend`; the identity spec's driver-level cache composition is `CachedStoreDriver(WriteGroupDriver(FileBatchBackend))`. No consumer in the tree used `FileStoreDriver` directly.
- **The reference peer and the upgrade-check writer still never close their stores**, so a clean stop leaves `store.lock` behind, replaced as stale on the next start since the pid is dead. The next ticket wires both closes. The upgrade-check reader closes now (above).
- **`fsyncDir` moved** from `atomic-write.ts` into `file-write-log.ts` one ticket early, since the log needs it and the next ticket planned the move.
- **No `docs/debugging.md` rows** for this package's `write-log` and `store-lock` namespaces: the namespace guard covers db-p2p only and the file has no section for this package.
- **Test cuts the reviewer may make**: the codec round-trip is pure and could be read as covered by the replay cases; the "store from a build before the log" case is close to what every fresh-directory test proves.
