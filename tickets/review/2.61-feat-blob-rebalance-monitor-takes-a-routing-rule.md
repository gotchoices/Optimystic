# The rebalance monitor takes a routing rule — review handoff

`RebalanceMonitor` (`packages/db-p2p/src/cluster/rebalance-monitor.ts`) compares, for each tracked id, the cohort `findCluster` assembles now with the one it remembered, and reports `gained` / `lost` / `grown`. It was tied to blocks by one call (`routingKeyForBlock` in `cohortFor`) and its module-level logger. Both are now injectable so `feat-a-referenced-blob-is-copied-to-its-cohort` can build a second instance over held blob references. It also gains one opt-in capability the blob reaction needs: re-reporting a `lost` id whose release could not be confirmed.

## What changed

- `RebalanceMonitorDeps.routingKeyOf?: (id: string) => RoutingKey` — default `routingKeyForBlock`. `cohortFor` uses it for both the `findCluster` path and the FRET `assembleCohort(hashKey(key), …)` fallback.
- `RebalanceMonitorDeps.logName?: string` — default `'rebalance-monitor'`. The module-level `log` is now an instance field `private readonly log: Logger` built in the constructor; every `log(...)` became `this.log(...)` (all inside arrow callbacks or methods, so `this` is the instance). The literal `'rebalance-monitor'` stays in the `createLogger(deps.logName ?? 'rebalance-monitor')` call, so `test/logger.spec.ts`'s namespace scan still sees it. A blob instance's `'blob:copy'` namespace is NOT in `docs/debugging.md` yet — the blob ticket that introduces the instance owns that row (the logger spec only scans string literals, so it will not catch it).
- `trackedBlocks` doc gained one sentence: the ids are whatever `routingKeyOf` places. No method renamed.
- `BlockGrowthState.releasePending: boolean` — false from `emptyGrowthState` and `carryGrowthState`.
- `RebalanceMonitor.retainLost(id)` — sets `releasePending` on the id's state when the state exists and `responsible` is false, then calls `updateRecheckTimer()` (the reaction is async and runs after the reporting check already evaluated the timer).
- `lost` branch: `!isResponsible && (wasResponsible || prior?.releasePending === true)`, still the `else if` after `gained`. The non-responsible state is rebuilt as `emptyGrowthState(false)` every check, so the flag is consumed by the re-report; a regain goes through `carryGrowthState`, which clears it.
- `hasOutstandingGrowthWork` → `hasOutstandingWork` (private); also true for a tracked id with `!responsible && releasePending`. The loop now skips untracked ids first, then checks `pendingPeers` for responsible ids or `releasePending` otherwise — equivalent for the growth arm.
- Block wiring (`libp2p-node-base.ts`) untouched; `retainLost` is never called for blocks. Whether it should be is backlog `bug-a-block-kept-after-a-failed-handoff-is-never-offered-again`.

## Tests

- Added `RebalanceMonitor › checkNow › re-reports a lost id once per retainLost call` (`packages/db-p2p/test/rebalance-monitor.spec.ts`): responsible → lost (reported) → `retainLost` + cohort moves again → reported lost again with the *current* `newOwners` → next check without `retainLost` returns `null`. Pins the one new branch and that `newOwners` is recomputed, not remembered.
- No test for `routingKeyOf` / `logName` (pass-throughs; the blob ticket's reaction tests build an instance with them) or for the timer arming in `retainLost` (reuses `updateRecheckTimer`, pinned by the "growth re-check timer" cases).

## Things a reviewer might check

- **Lost-but-untracked interaction with the shared set.** `retainLost` is ignored for an id whose state was deleted by `untrackBlock`, but a `trackedBlocks` set mutated externally (`delete` on the shared set, not via `untrackBlock`) leaves the snapshot entry in place. `retainLost` would then set the flag; `hasOutstandingWork` skips it (untracked), and `performRebalanceCheck` only iterates tracked ids, so it is inert — and if the id is re-tracked later while still outside the cohort, the next check reports it `lost` once. That matches the "lingering entry is inert, re-derived on re-feed" comment on `responsibilitySnapshot`, except for this one extra `lost` report on re-feed. Judged harmless (a lost report on an id this node is not responsible for, which the reaction re-confirms); flagging in case the reviewer disagrees.
- **Partition suppression / failed lookup** leave the state untouched, so `releasePending` survives to the next unsuppressed / successful check (inspection, as the plan said).
- `getGrowthDiagnostics()` does not count retained releases; `recheckArmed` will read `true` while one is outstanding. Left as is — the blob ticket can add a counter if its log line wants one.
