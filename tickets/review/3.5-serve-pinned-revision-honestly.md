# Review: `serveBlockArchive` no longer labels pinned content with the wrong revision

## What was wrong

`StorageRepo.get` honours `context.rev` — it serves the highest committed revision at or below the
pin. But `GetBlockResult` carried no field saying *which* revision the bytes in hand actually were
(only `materializedRev`, a bare number, with no matching action id). So `serveBlockArchive`, which
needs both halves to build an archive, reached for `entry.state.latest` — the serving node's
**newest** revision. A rev-1 request came back as rev 1's bytes under rev 2's number and action id.

The asker's `BlockStorage.saveRestored` stores by action id, so it wrote rev 1's content under rev
2's action id, clobbering its own good rev 2. `meta.ranges` stayed `[[2,3]]`, so rev 1 was still
recorded as missing and every later rev-1 read repeated the fetch and the overwrite.

## What changed (two arms)

**Arm 1 — fail closed.** `serveBlockArchive` refuses (returns `undefined`, logs
`serve:skip … (pinned read — refusing to mislabel content)`) when a revision was requested and the
revision it would serve is newer than the pin. After Arm 2 this only fires for a plain `IRepo` that
reports no materialized revision and whose latest is newer than the pin.

**Arm 2 — make the mislabel unrepresentable.** `GetBlockResult.materializedRev?: number` became
`materialized?: ActionRev` — the `(rev, actionId)` pair as one field, so a caller cannot hold one
half without the other. `serveBlockArchive` now labels from `served = entry.materialized ?? latest`
and looks the proof up for that same revision.

Producers updated: `StorageRepo` (both sites pass `blockRev.actionRev` whole), `TestTransactor`
(keeps a local `materializedRev` number internally, emits `materialized` only when both halves are
known). Consumers updated: `TransactorSource`, `BlockTransferService`.

## Use cases to exercise

Fastest single command: `cd packages/db-p2p && node --import ./register.mjs
node_modules/mocha/bin/mocha.js "test/block-archive-proof.spec.ts" --reporter spec`

- **The original corruption.** Two repos both hold rev 1 (`one`) and rev 2 (`two`); the asker
  forgets rev 1 and asks a peer for it. The asker's stored rev 2 bytes must still be `two`
  afterwards, and a later unpinned read must still return rev 2.
- **A pinned request that succeeds.** Asking for rev 1 lands rev 1 *labelled rev 1*: archive
  `range` is `[1, 2]`, action id is rev 1's, `meta.ranges` merges to `[[1, 3]]`, bytes are stored
  under rev 1's own action id, and the result's `materialized` is `{ rev: 1, actionId: ACTION }`.
- **A repo that cannot say what it materialized.** A plain `IRepo` pinned below its latest gets
  `undefined`; pinned at or above its latest it serves normally.
- **No revision requested.** Serves latest, byte-identical to before — `SyncService`, the mesh
  harness, and both `libp2p-node-base.ts` latest-revision consults all pass `rev: undefined` and
  must be unaffected.
- **Proofs follow the served revision.** The proof shipped is the one stored for the revision
  actually served, never for a revision chosen elsewhere.

## Known gaps — please push on these

- **The corruption regression test is an outcome assertion, not a tight single-mutation
  regression.** "never overwrites a revision the asker already holds" passes under *either* mutation
  alone, because Arm 1 and Arm 2 each independently prevent the corruption; it only fails if both
  are broken. That is honest defence-in-depth and each mechanism is individually covered by one of
  the other two tests — but if you want a test that pins the corruption to one mechanism, it does
  not exist today.
- **Pin semantics are still "highest committed at or below N".** A peer that is merely *behind*
  answers with an older revision, now labelled honestly, and `ensureRevision` records that older
  range as held. Whether an older revision legitimately "covers the requested revision" is
  `restore-trusts-any-archive-a-peer-returns`'s call, not this ticket's. This ticket only guarantees
  the label matches the bytes.
- **`sourceBlockMeta` / `sourceBlockCertification` still drop the meta on a pinned read, by
  design.** A push is "here is my latest replica"; no push path reads pinned, so a mismatch there is
  a caller bug. The reasoning is recorded in a doc comment at the site — worth a second opinion on
  whether that should assert rather than drop silently.
- **The mesh harness's `clusterLatestCallback` still returns `state.latest` from a possibly-pinned
  read.** Correct for a *latest* consult and deliberately untouched, but it is the one remaining
  place that reads `state.latest` near a pinnable path.
- **Only the two packages above were tested.** No other workspace was built or run; if another
  package consumes `GetBlockResult`, the rename would surface there and was not checked.

## Suggested review focus

1. Is `served = entry.materialized ?? latest` the right fallback, or should a repo that cannot
   report `materialized` be refused outright even for an unpinned read?
2. Does any remaining site read `state.latest` where it means "the revision I am holding"? That is
   the exact bug class this ticket closed; a sweep is cheap insurance.
3. The `ActionRev` pairing is the structural fix — confirm no producer can still construct a
   `GetBlockResult` with a rev from one revision and an action id from another.
