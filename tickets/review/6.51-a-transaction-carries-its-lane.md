# A transaction carries its lane

First of four implement tickets from the plan of the same name; db-core's half of the lane vocabulary. Every write now carries a **lane**, `serializable` or `convergent`, saying whether its conflicts with other machines' concurrent writes are the quorum's to decide under the revision order, or may be merged later under the collection's declaration. The field rides exactly where the HLC rides, is minted once per write and re-sent by every retry, and a collection declares which of its actions merge through `CollectionInitOptions.merge`, which replaces the bare `filterConflict` hook. **No admission rule changed**: the solo path, the offline queue and the conflict replay behave as before. The next three tickets are the SQL classification, the member-side check and the operator-visible reporting.

## What landed

**The vocabulary.** `packages/db-core/src/lane/lane.ts`, exported from the package index: the `Lane` type with the doc comment the plan asked for (convergence is a property of the operation; idempotence is not the criterion), `stricterLane(lanes)` (serializable if any part is), and `laneField(lane)`, the request-field wrapper that mirrors `refuseSoloField` so an unset lane is omitted from a request rather than sent as `undefined`.

**The declaration.** `ConvergentMerge<TAction>` in `packages/db-core/src/collection/collection.ts`: `laneOf(action)` and an optional `filterConflict(action, committed)` with the old hook's contract verbatim. `CollectionInitOptions.filterConflict` is gone; `merge?: ConvergentMerge` is in its place. `Collection.doFilterConflict` offers the hook only an action whose `merge.laneOf` is `convergent`; everything else is kept as-is, which is what every collection got before. `Collection.laneOf(actions)` is public and pure: `stricterLane` over the declaration, `serializable` without one or for an empty list. `Diary` declares `merge: { laneOf: () => 'convergent' }`; `Tree` declares nothing, and `TreeCollectionOptions` is now generic (`<TKey = unknown, TEntry = unknown>`) and carries `merge` beside `onSealedRefused` so a raw tree user can declare one.

**The carriers.** Each row of the plan's table is in place: `ActionEntry.lane` (required, stamped by `Log.addActions` from `AddActionsOptions.lane`, read through `laneOf` in `packages/db-core/src/log/struct.ts`), `WriteIdentity.lane`, `SyncOptions.lane`, `InFlightCycle.lane`, `TransactOptions.lane` → `PendRequest.lane` and `CommitRequest.lane` (and `RepoCommitRequest.lane`, since `repoCommitRequest` and `commitOf` in `packages/db-core/src/transactor/network-transactor.ts` rebuild every per-coordinator commit through it), `Transaction.lane` (folded into `createTransactionId` and `clientSignaturePayload`, whose version is `txsig:v3`), `WriteContext.lane`, `EntryCommit.lane`, `HeadCommitOptions.lane`, and the offline queue's `Entry.lane`, `JournalEntryRecord.lane`, `RestoreInit.lane`, `EntryStatus.queued.lane` and `QueuedEntry.lane`. The plugin's `EntryRecordV1.lane?` is optional on the record with `v: 1` unchanged, restored as `serializable` when absent; `legacyTransaction` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts` takes a `lane` parameter defaulting to `serializable`.

**The sources.** `Collection.syncInternal` mints `options?.lane ?? this.laneOf(this.segments.open)`. `TransactionSession.commit(options)` mints `options?.lane ?? 'serializable'` and folds it into the id and signature. `OfflineQueue.enqueue` takes `init.lane`, defaulting to `stricterLane` over each sealed collection's `laneOf` of the segment it sealed (`sealedLaneOf`), journals it, and re-supplies it on every drive. `TransactionCoordinator.commit` and `commitEntry` take the lane off the transaction and the entry and never read `SyncOptions.lane` (documented on the field).

## Decisions the reviewer should weigh

- **The re-send of a torn attempt carries the lane, unlike the HLC.** The plan's wire table said the re-send "has none at hand". It does: `InFlightCycle.lane` is set by every write path from the identity it minted (`beginInFlightAction`), and `Collection.completeOwnEntry` reads it beside `refuseSolo`. So `PendRequest.lane` and `CommitRequest.lane` are optional on the wire for an older writer only; the `NOTE:` at the re-send says so. `InFlightCycle.lane` is therefore **required**, and `beginInFlightAction` lost its `= {}` default: a caller must say what lane the cycle is in. Four test call sites now pass `{ lane: 'serializable' }`.
- **`OpenHeadCommitOptions` is `Omit<InFlightCycle, 'lane'>` plus the two hooks.** The identity passed to `openHeadCommit` is the one source of the cycle's lane; `EntryParticipants.open` and `commitHead` pass the lane on the identity, and the coordinator's `inFlightCycleOf(options, lane)` builds the cycle from the transaction's or the entry's lane. `writeContextOf(transaction, cycle)` likewise takes the cycle without its lane.
- **`inFlightCycle` is `undefined` outside a cycle** rather than `{}` (it can no longer be an empty object), read with `?.` at the two sites that use it. Both run only inside a marked cycle, so the optional reads never see `undefined` in practice; the type cannot say that.
- **`stricterLane([])` answers `serializable`.** A write of no parts claims nothing, and that is what makes `Collection.laneOf([])` and an invented collection's header-only sync come out serializable without a special case. Documented at the function.
- **`TreeCollectionOptions` generic with defaults.** `Pick<CollectionInitOptions<TreeReplaceAction<TKey, TEntry>>, 'onSealedRefused' | 'merge'>`. The plugin's `treeOptions()` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts` now returns `Pick<TreeCollectionOptions, 'onSealedRefused'>`: it never declares a merge, and `ConvergentMerge<unknown-keyed tree>` is not assignable to the string-keyed one the table opens (the hook's return type is covariant), so the narrower return type is what keeps the plugin compiling without a cast.
- **Signature and id preimages changed.** Every transaction id this build computes differs from what the previous build would compute for the same inputs, and a `v2` signature fails a `v3` verifier. Accepted on the `v2` precedent, recorded at `CLIENT_SIG_VERSION`; no deployment wires a verifier. The validator derives `transaction.lane ?? 'serializable'` for the payload check alone and never rewrites the transaction, as it does for the HLC.
- **`docs/optimystic.md` claimed that by default conflicting local actions are dropped.** That was already false (a collection with no hook keeps and replays every action); the sentence now says what happens, and the example declares the counter's increment convergent.
- **The plugin's `OfflineMode.enqueue` passes no `lane`** yet, so an offline SQL transaction's entry takes the stricter of its trees' declarations, which is `serializable` for every table. The SQL classification ticket passes the fold through `init.lane`; until then this is exactly today's behaviour, by design.

## Use cases for validation

- **A diary append is convergent by declaration; a tree write is serializable; the sync option wins.** `packages/db-core/test/collection.spec.ts`, "the lane a write carries": three assertions, one behaviour (which source decides), read back through `laneOf` on a fresh handle over the collection's log.
- **A retry re-sends the lane it was minted with.** `packages/db-core/test/retry-resends-identical-transforms.spec.ts` compares whole transform sets across attempts on the collection, coordinator and head-commit paths, so any per-attempt lane would fail it. It passes unchanged.
- **A stored entry from before the field reads as serializable.** `packages/upgrade-check` restarts the working tree over data every published release wrote; its 199 cases pass with no fixture change, which is the evidence `laneOf`'s fallback is right.
- **The convergent lane's hook is the old hook.** The four `filterConflict` cases in `collection.spec.ts` and the three in `transaction.spec.ts` ("merge.filterConflict during a coordinator retry") now declare every action convergent through `merge` and assert exactly what they asserted before: keep, replace and discard each decide what commits.
- **A queued entry's lane is fixed and journaled.** By inspection of `OfflineQueue.enqueue`, `entryRecord`, `registerRestored` and `send`; the plugin's restore re-supplies `entry.lane ?? 'serializable'`. The existing offline-queue and offline-restore suites pass.
- **A multi-collection write has one lane on every participant.** By construction: `WriteContext` is built once per attempt from the transaction (`writeContextOf`) or the entry (`commitEntryOnce`), and `EntryParticipants.open` hands every handle the same identity.

## Tests added
