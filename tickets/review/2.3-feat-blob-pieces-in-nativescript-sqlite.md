# Review: blob pieces in the NativeScript SQLite database

## What was built

- `SqlitePieceStore` (`packages/db-p2p-storage-ns/src/sqlite-piece-store.ts`), exported with `PIECE_LIST_PAGE` from the package index. One `pieces (id TEXT PRIMARY KEY, bytes BLOB NOT NULL)` table appended to `SCHEMA_SQL` (no version bump; `CREATE TABLE IF NOT EXISTS` adds it on the next open). Statements prepared once: `has`, `get`, `put`, a separate zero-length put, `delete`, keyset-paged `list` (1000 ids a page, each page drained before yielding), `bytesUsed` via `sum(length(bytes))` (logs and answers 0 on failure). `durability = 'power-loss'`, no `close`, `storeIdentity()` = `identityForHandle(SQLITE_HANDLE_SCHEME, db)`.
- `SQLITE_HANDLE_SCHEME` constant in `sqlite-storage.ts`, used by `SqliteBatchBackend` and the piece store, so the identities are equal over one handle by construction.
- `PendingSqliteSync` in `sqlite-sync.ts` (internal, not exported from index): dirty flag + failure latch + `flush` via `syncSqliteDb`. `SqliteKVStore` rewritten over it, no behaviour change.
- `wholeBufferBytes` copies a sub-view before binding (device-side precaution; documented as such).
- JNI 512 KiB `NOTE:` in `ns-opener.ts` gained the piece-store sentence; "512 KiB" fragment kept.

## Deviation from the plan — read this

The plan said `node:sqlite` binds an empty `Uint8Array` as an empty BLOB and asked for `INSERT OR IGNORE` plus only a tripwire for zero-length. Both were wrong in practice, and the conformance zero-length case failed:

- `node:sqlite` binds a **zero-length typed array whose `.buffer` has been read** as NULL (reproduced with plain `node -e`: a fresh `new Uint8Array(0)` binds as blob, the same array after touching `.buffer` binds as null). `wholeBufferBytes` reads `.buffer`, and so would plenty of other callers.
- `INSERT OR IGNORE` also ignores NOT NULL violations, so the piece was silently not stored and `put` resolved.

Fix: a zero-length piece is written by its own statement with `zeroblob(0)` (never bound), and both puts use `INSERT … ON CONFLICT(id) DO NOTHING`, which ignores only the id conflict, so any future NULL bind fails loudly instead of losing a piece. The zero-length tripwire on `put` is therefore resolved rather than parked; the remaining device unknown is the read side (a `NOTE:` in `get`: if the plugin returns NULL for an empty BLOB, read it as the empty piece). `get` throws a `TypeError` if a row's bytes are not a `Uint8Array` — reviewer may prefer the NULL→empty mapping now instead.

## Tests

- `test/sqlite-piece-store.spec.ts`:
  - `runPieceStoreConformance('SQLite pieces', …, { persistent: true })` over a temp-file database (`openTestFileDb`), reopen closes and reopens the file. Pins the whole `IPieceStore` contract incl. zero-length, 256 KiB/1 MiB pieces, flush-then-reopen.
  - "a database written without the pieces table gains it on its next open": drops `pieces`, writes+flushes block metadata via `SqliteRawStorage`, reopens; the block reads back and a piece round-trips. The only upgrade coverage for this backend.
- No test for `PendingSqliteSync` itself (the existing kv-store flush test covers it, still passing). No dedicated page-boundary test for `list` (conformance listing cases hold fewer than 1000 pieces, so the multi-page path is covered by inspection only).

## Known gaps

- Nothing has run on a device: 1 MiB piece over the JNI bridge, empty-BLOB read-back, sub-view binding (README §What has run on a device says so).
- `list` multi-page loop untested (see above).
- README usage example now passes `kvStore` and `pieceStorage` to `createLibp2pNode`; it still does not pass the raw storage (pre-existing omission in the example, left alone).
