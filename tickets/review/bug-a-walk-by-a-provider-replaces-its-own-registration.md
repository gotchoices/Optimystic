# A seeker walk by a provider no longer replaces the provider's own registration

## What was wrong

A topic's cohort keeps one registration record per (topic, machine), keyed by the machine's peer id; renew and withdraw frames are matched by that pair. A provider registers through the node's `CohortTopicService`. A matchmaking seeker walk from the same machine registered through `createLibp2pMatchmakingTransport` with its own `RegisterV1` under the same id, bypassing the service, so the walk's record replaced the provider's (the machine was listed as a seeker), and the walk's closing withdraw then removed the record outright. The provider reappeared only when its own renewal loop gave up and re-walked, roughly one provider TTL later.

## What changed (the rule: one registration per machine per topic)

- **`CohortTopicService.holds(topicId)`** — this machine holds a live registration for the topic (registered through the service, not withdrawn). **`CohortTopicService.isLive(handle)`** — the handle is still the live one (not displaced, not withdrawn). Both are on the interface and the implementation; `holds` is one map lookup on the existing `renewals` map.
- **Transport** — `Libp2pMatchmakingTransportDeps.localRegistrations: Pick<CohortTopicService, "holds">` is **required** (an optional default of "holds nothing" would reproduce the defect for any caller that forgets it). `createLibp2pMatchmakingSeekerSession` fills it from `deps.service` (its deps type now `Omit`s the field). In `walkTransport`:
  - `holds(topicId)` is read on every tier's `register`. While true, the frame is a read-only probe (`probe: true`, no `bootstrap`, no evidence, no `appPayload`, signed over `registerSigningPayload`), sent through the same `dialRegister` (a self-routed one goes through `selfServe.register`), and `keepAlive.accepted` is not called. The walk logs once per walk that it is looking without registering and why.
  - When `holds` is already true at `walkTransport()` construction, the walk is built without a push receiver (poll path). A misconfigured `pushOnArrival: true` with no receiver still throws as before.
- **Keep-alive** — `SeekerKeepAliveDeps.stillOurs` (required), bound to `() => !holds(topicId)`, is checked before every renew and every withdraw; when false the live registration is forgotten without sending anything, and a line is logged.
- **Seeker manager** — `MatchmakingSeekerManager.register` throws `TopicRegistrationHeldError` when the service holds a live registration for the topic that is not this manager's own handle. Re-registering over its own handle is allowed. A provider registering over a brief seeker registration is allowed (the offer wins); the manager's handle then goes stale and its withdraw is a no-op through the service's identity guard.
- **Docs** — `docs/matchmaking.md` §Overview states the rule, what a provider's walk gives up (arrival pushes, being visible as a seeker), the voting coordinator that is also a voter, and that the mock mesh harness does not follow the rule. `docs/internals.md` §Matchmaking subsystem → *Public module* got one sentence. `yarn lint:docs` passes.

## Tests added / changed

- `query-transport-client.spec.ts` — "a walk probes instead of registering while its machine holds a registration for the topic, and never withdraws that record": table of three cases over the self-routed `selfServe` pattern — holds nothing (normal register with payload, `close()` sends one withdraw); holds a registration (probe, no payload, `close()` sends no withdraw); holds turns true after an accepted register (the reverse order: no withdraw sent). Each frame is also checked wire-valid (`validateRegisterV1`) and correctly signed, since a remote cohort silently answers `no_state` to a frame whose signature does not verify. This is the reproduction at the transport.
- `managers.spec.ts` — "refuses to register over another live registration of the machine for the topic, not over its own". The existing `RecordingService` double now tracks the live handle per topic (displace on register, drop on withdraw of the live one), which is how it can answer `holds`/`isLive`.
- `matchmaking-small-network.integration.spec.ts` — the one-machine `query` branch is gone; every size walks, then a one-shot query asserts the provider is still listed with its own signature. **Ran** with `yarn workspace @optimystic/db-p2p test:integration --grep "smaller than one cohort"`: 1, 2 and 3 machines pass (126 ms / 390 ms / 5.4 s); with debug logging the one-machine walk logged "looks without registering from tier 0". The comment pointing at this ticket is removed.
- Mechanical: every other `CohortTopicService` test double gained `holds`/`isLive` (throwing stubs where unused; `module.spec.ts` answers `holds` false), `seeker-keep-alive.spec.ts` passes `stillOurs: () => true`, and the two `createLibp2pMatchmakingTransport` calls in `substrate-real-libp2p.integration.spec.ts` pass `localRegistrations: seeker.host.service`.

## Known gaps / things for the reviewer to look at

- **`substrate-real-libp2p.integration.spec.ts` was not run.** The change there is only the new required field; those seekers hold no service registration for the walked topic (providers there are hand-registered with fresh keys through `engine.handleRegister`), so behaviour should be unchanged.
- **A register still in flight is not "held".** The service adds a registration to `renewals` only once its walk is accepted, so a seeker walk started while the same machine's provider `register` is still walking sees `holds` false, registers, and replaces the record being admitted. Narrow (needs concurrent calls from one machine); parked as a `NOTE:` at `holds` in `packages/db-core/src/cohort-topic/service.ts`.
- **Mid-walk registration keeps its push subscription.** A walk whose machine registers as a provider after the walk started keeps subscribed to pushes that can no longer come; its safety poll covers them (comment in `walkTransport`). By design per the ticket.
- **Mock mesh harness unchanged.** `buildWalkTransport` in `packages/db-p2p/src/testing/matchmaking-mesh-harness.ts` still has its own register path without the rule (its `seek` doc already tells callers to use a non-provider node); no mesh test was added for it, as the ticket asked.
- **The probe is subject to the cohort's probe rate limiter** (over-rate → `unwilling_cohort`, which ends the walk). A walk probes once per tier, so this should not trip in practice.
- `holds` is "any registration this service holds for the topic", so a brief seeker registration made through `MatchmakingSeekerSession.register` also makes the same session's walks probe. That matches the rule (that brief registration is the machine's registration there), but the reviewer may want to confirm it is the intended reading.
