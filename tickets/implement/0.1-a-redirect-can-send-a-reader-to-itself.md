# A redirect can send a reader to itself

Reported as GitHub #65 (VoteTorrent, `@optimystic/db-p2p` 1.27.0): a read-only browser node sends a repo `get` for the `optimystic/schema` header to a host; the host answers with a redirect whose peer list contains the browser's own peer id; the browser picks itself, dials itself (`Can not dial self`), and the read fails as peers-unreachable. Seed-dependent: whether the browser sorts ahead of the other cohort members in the host's list decides it.

## Cause (read from the code)

Two defects, one on each side of the redirect.

**Client.** Both redirect branches pick `peers.find((p) => p.id !== currentIdStr) ?? peers[0]`, where `currentIdStr` is the peer just asked (the host). Nothing excludes the local peer, because neither client knows its own peer id: `RepoClient.create` and `ClusterClient.create` take the target, the `IPeerNetwork` and the prefix. When the asker comes first in the list it picks itself. The "same peer" loop check compares only against the host.

- `RepoClient.processRepoMessage` in `packages/db-p2p/src/repo/client.ts`
- `ClusterClient.answerFor` in `packages/db-p2p/src/cluster/client.ts` (the ticket's original note said `update`; the branch now lives in `answerFor`, shared by `update` and `updateCarrying`)

**Host.** `RepoService.checkRedirect` redirects to every id in `responsiblePeerIds(keyNetwork, blockKey)` (the host's `findCluster` view) whenever that cohort is full-size and excludes the host, without removing the requesting peer — whose id `handleIncomingStream` already has (`connection.remotePeer`). `ClusterService.checkRedirect` has the same shape: it removes self from `record.peers` but not the dialer, whose id `processOperation` receives as `remotePeer`.

**Why an edge reader is in the host's cohort at all.** Not a misclassification. Every node `createLibp2pNode` builds registers the `repo`, `cluster`, `sync` and `block-transfer` services, whatever its FRET profile, so an `edge` browser advertises `repo`/`cluster` and `membershipOf` correctly classifies it serving. It therefore lands in other machines' cohorts. It went to the host rather than serving itself because its own view (its routing view, its self-coordination guard on a fresh node with no data) sent the read remote. Keeping such a node out of every cohort is exactly what plan ticket `client-only-node` (`NodeOptions.servesBlocks: false`) delivers; this ticket does not depend on it and does not duplicate it. Even with that ticket, two serving nodes whose cohort views differ can still produce this redirect, so the fix here stands on its own.

## Design

**The client learns its own id from the peer network.** Add an optional read-only `localPeerId?: PeerId` to `IPeerNetwork` (`packages/db-core/src/network/i-peer-network.ts`), documented as "this node's own peer id, so a protocol client never dials or follows a redirect to itself; implementations without an identity omit it". `Libp2pKeyPeerNetwork` implements it as a getter over `this.libp2p.peerId`. Every client already holds the network it dials through, so no `create` signature and none of the ~40 call sites change, and test doubles that omit it keep today's behaviour. (Rejected: a new `create` parameter — many call sites across four packages, and a call site that forgets it reintroduces the bug.)

**Client rule, shared by both clients.** From the redirect list, drop the peer just asked and the local peer (when `localPeerId` is known). Pick the first remaining. If none remains, throw (as today's "same peer" throw does) with a message saying the redirect named no peer other than the one asked and this node. A throw is already what makes `NetworkTransactor` exclude that coordinator and re-pick, which is the required outcome; no new error type is needed. Factor the pick into one small exported function (e.g. `pickRedirectTarget(peers, askedId, localId)` in `packages/db-p2p/src/repo/redirect.ts`, beside `RedirectPayload`) so the two branches cannot drift. Never call `recordPeerAddresses` or `recordCoordinatorHint` for a peer that was filtered out.

**Host rule.** `RepoService.checkRedirect` and `ClusterService.checkRedirect` take the requester's peer id (optional — absent when the connection has none) and leave it out of the redirect peer list. If removing the requester (and, for the cluster service, self) leaves the list empty, do NOT send a redirect: an empty `peers` array fails the client's `redirect?.peers?.length` test and would be returned to the caller as if it were the operation's answer. Process locally instead (`return null`). That is correct because the downstream checks already decide: `CoordinatorRepo` serves a `get` fail-open and refuses `pend`/`cancel`/`commit` with `ResponsibilityRefusalError` when the cohort excludes it (`docs/internals.md` §Proximity Verification), which the writer treats as a failed coordinator. For the cluster service, verify that `ClusterMember.update` refuses a record whose `peers` does not name this node; if it does not, say so in the handoff rather than widening scope.

Note the order in `RepoService.checkRedirect`: it stamps `message.cluster` with the full cohort before deciding; leave that stamp as the full cohort (it is the responsible set, used downstream), and filter only the redirect payload.

## Tests

- **Client reproduction (required).** In `packages/db-p2p/test/coordinator-cache-hint.spec.ts`'s style (or a new small spec beside it): a fake `IPeerNetwork` with `localPeerId` set, whose first dial answers a redirect listing `[self, other]` and whose second answers a terminal value. Assert the second dial goes to `other` and no dial targets self. One case for `RepoClient` covers the shared pick function; add the `ClusterClient` case only if the branch is not reduced to a call of the shared function. A second case in the same test: redirect listing only `[self, asked]` throws without a second dial.
- **Host reproduction.** One case in `packages/db-p2p/test/redirect.spec.ts` (repo service) and one in `packages/db-p2p/test/cluster-service-redirect.spec.ts`: a full-size cohort excluding self and including the requester → the redirect payload omits the requester; a cohort whose only non-self member is the requester → no redirect (`null`).

## Docs

`docs/internals.md` §Proximity Verification, the "Redirect check (same rule)" bullet: add that the redirect never names the requesting peer, and that a client never follows a redirect to itself, treating a list with no other peer as a failed coordinator. Run `yarn lint:docs`.
