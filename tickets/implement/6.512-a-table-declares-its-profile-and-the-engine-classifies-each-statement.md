# A table declares its profile, and the engine classifies each statement

Second of four implement tickets from the plan `a-transaction-carries-its-lane`. The previous ticket gave every write a **lane** (`serializable`: needs the cohort's quorum, revision order decides conflicts; `convergent`: may be committed by one machine and merged later) and a `SyncOptions.lane` / `Transaction.lane` for a caller to state it. This ticket is the caller: the Quereus plugin, which can see for each statement what the plan ticket's rule asks about. No admission rule changes.

## Two levels, two tags

- **The profile, per table.** `with tags ("optimystic.profile" = 'replay-permitted')` opts a table in. The only other value is `'strong'`, which is also what an absent tag means, so every existing table and every table that declares nothing behaves exactly as today. The profile is the application's **ceiling**: a `strong` table's writes are `serializable` whatever a statement looks like. The decision taken in the plan and open for a human to edit: the default is `strong`, because defaulting to `replay-permitted` would silently change what every application gets. Any other value is read as `strong` and logged once per table (`optimystic:profile-tag-ignored`), fail safe.
- **The merge, per column.** `"optimystic.merge" = 'last-writer-wins'` on a column says two concurrent assignments of the column merge by the later HLC winning. It is the plan's clause (c), "the collection defines a merge for the touched fields". It is the only merge kind this pass defines; any other value means no merge, logged once per column. The merge itself is evaluated by the replay stage; here it only decides the lane.

Both tags are read `=== 'replay-permitted'` and `=== 'last-writer-wins'`, from the vtab's `tableSchema` as `optimystic.single_writer` and `optimystic.content_key` are read. They are **already part of the schema hash**: `QuereusEngine.computeSchemaHash` digests the `sql` column of Quereus's `schema()` function, which `generateTableDDL` in `@quereus/quereus/src/schema/ddl-generator.ts` renders with every table and column `with tags (…)` clause, so two machines whose tags differ already fail the validator's schema check. Nothing to build; say so in the rule's doc comment and verify by inspection of that generator. The tags are persisted to the catalog record by the existing `SchemaManager.persistTags` path, so `hydrate` restores them.

## The classification rule

A new module `packages/quereus-plugin-optimystic/src/optimystic-adapter/lane.ts`, pure over Quereus's `TableWrite` (the write description, `@quereus/quereus` docs/write-scope.md in the sibling checkout) and the table's `TableSchema`, reusing `write-description.ts`'s helpers rather than building a second analysis. It has **two layers**, because the two parties that compute it see different inputs (next ticket): a member re-executes statements that were rebuilt from evaluated row values (`TransactionBridge.addStatement`'s `NOTE:`), so a value the writer saw as `fresh` reaches the member as a literal.

**The ceiling** (`laneCeilingOf(write, table): Lane`) is what the catalog and the statement's shape alone decide, the same on every machine with the same schema hash. It is `serializable` when any of these holds, else `convergent`:

- the table's profile is not `replay-permitted`;
- `write.constraints` lists a `unique`, `foreign-key-child`, `foreign-key-parent` or `assertion` constraint, or a `check` whose locality is `cross-row` — clause (a). A `foreign-key-parent` entry is also how a cascade reaches the rule: the cascade's child writes carry no description of their own (an `undescribed` fact), but the parent statement lists the constraint;
- `write.constraints` lists `primary-key` and the table is not tagged `optimystic.content_key` and the operation is not an INSERT. An INSERT's primary key is judged by the writer-only clause below: a fresh key cannot collide, and a content key (`absentOrEqual`, the same row from the same content) merges as the same write made twice. An UPDATE that assigns a key column is `serializable`;
- the operation is `update` or `delete` with `selection.kind === 'global'`: which rows the statement touches is itself a read of other writers' state;
- the operation is `delete`: no tombstone merge is declared in this pass (the `NOTE:` at the rule records this as the first arm to add once a replay-mode application needs deletes to merge);
- the operation is `update` and any assigned column (`write.columns`) is not tagged `optimystic.merge = 'last-writer-wins'` — clause (c);
- the disposition is an `upsert` with a `do update` clause (the arm's assignments are a second write the rule would have to judge; conservative).

**The lane** (`laneOf(write, table): Lane`) is the ceiling plus what only the writer sees — clause (b), the write must not depend on a read:

- `write.reads` is non-empty, or `write.selfIndependent` is false (`set n = n + 1` reads `n`; a volatile `now()` is fine, it is a last-writer-wins value like any other);
- for an INSERT with a `primary-key` constraint on a table not tagged `content_key`: every primary-key column's provenance must be `fresh` (`freshColumnsOf`), or the column tagged `optimystic.fresh = true` (the same declared hint the outlook honours, docs/offline-sync.md §Declared hints). An `input` or `literal` key may collide with another machine's and is `serializable`.

A write with no description (the vtab's `update()` called with no `writeScope`: a cascade child write) is `serializable`, fail safe. A transaction's lane is `stricterLane` over the lanes of its statements, so a transaction spanning a `strong` table and a `replay-permitted` one is `serializable`.

Write the idempotence note at the rule, as the plan asks: setting a column is idempotent and still needs the tie-break the merge tag declares; an increment is not idempotent and would merge fine, and is `serializable` here only because clause (b) cannot see that the read is one a counter merge absorbs (a `'counter'` merge kind is the natural second arm; record it as a `NOTE:`).

## Where the vtab and bridge record it

- In `update()`, beside the existing `noteWriteDescription(args.writeScope)` call, the vtab hands the bridge the statement's lane: `noteWriteLane(laneOf(args.writeScope, this.tableSchema))` — or fold it into `noteWriteDescription` by giving the bridge the `TableSchema` too; pick whichever keeps the bridge free of catalog lookups. Recorded once per described statement (the `described` weak set already keys on the `TableWrite` object), kept with `TransactionState.writeFacts` as a new `WriteFact` kind `{ kind: 'lane', lane }`, so a savepoint rollback discards it with the statement's other facts, and an `undescribed` record is read as `serializable`.
- `TransactionBridge.openLane(): Lane` folds the open transaction's records with `stricterLane`, `serializable` for a transaction with no described write.
- Every commit route passes it: `tree.sync({ lane })` in `sweepDirtyTreesLegacy`; `legacyTransaction(transactor, lane)` for `commitBatchLegacy`; `session.commit({ lane })` in session mode; `OfflineMode.enqueue(collections, transactionId, facts, lane)` → `OfflineQueue.enqueue(…, { lane })` in `sealIntoQueue`. One fold, read at commit, so the four routes cannot disagree.

## `alter table … set tags` while entries are queued

The plan proposed refusing a profile change while entries for the table are queued, as `OfflineMode.assertNoQueuedEntries` refuses a storage-shape change. That is not available: Quereus applies a tag change to its own catalog and tells the module afterwards through `table_modified` (`followSchemaTags`), so the module cannot refuse it. The resolution, consistent with the previous ticket's rule that a sealed segment's lane is fixed at enqueue: a queued entry keeps the lane it was classified with, which was true of its statements when the application made them and is journaled. When `followSchemaTags` sees the profile or a merge tag change while `assertNoQueuedEntries`'s listing for the table is non-empty, log `offline:profile-changed-with-entries-queued` naming the transactions, and nothing else. No hazard follows in this stage, since nothing admits by lane; the replay stage reads the entry's lane under the table's profile at merge time, and a `strong` table never merges whatever an entry says.

## Edge cases & interactions

- **Strong and replay-permitted tables in one transaction** → `serializable`. Pinned by the table-driven test's mixed case through `stricterLane`.
- **A read-only transaction, or one whose only writes staged no row** (an UPDATE matching nothing): no described write is recorded, the fold answers `serializable`, and nothing is pended anyway. By inspection.
- **The upsert `DO UPDATE` arm receives the INSERT's description**, as `write-description.ts` already notes: the rule sees an `upsert` disposition with a `do update` clause and answers `serializable` for the whole statement. By inspection.
- **Index trees.** A transaction's lane is stamped on the main tree's entry and on each index tree's entry alike (one `WriteContext` per transaction, previous ticket). A non-unique index entry is keyed `indexValue ‖ pk`, so a fresh-keyed insert's index entry is new too; how an index tree's entries merge under last-writer-wins is the replay stage's question, not this one's. Record that at the rule.
- **`optimystic.fresh` on a key column** counts as fresh provenance here as it does for the outlook; a false tag produces a `convergent` lane for a write that can collide, which the replay stage would resolve by its guards. Same contract the README already states for the tag: a tag changes only the prediction, every guard is still enforced.
- **A cascade child write.** Carries no description → `undescribed` → `serializable`; and the parent statement lists `foreign-key-parent`, so the ceiling says `serializable` too. Both arms by inspection; the test covers the constraint arm.
- **A tag with an unexpected value** is read as absent and logged once; never a throw at staging time. By inspection.
- **A profile change on a running table** reclassifies the next transaction only. By inspection of `followSchemaTags`, which replaces the vtab's `tableSchema`.
- **Session mode and the validator.** `session.commit({ lane })` is the writer's; the member's check is the next ticket, which uses `laneCeilingOf` from this module. Keep the two layers as separate exported functions for that reason.

## Tests that pay for themselves

One table-driven spec, `packages/quereus-plugin-optimystic/test/lane.spec.ts`, in the shape of `write-description.spec.ts` (a plain `Database`, memory tables, the plugin's `StampId()` registered as fresh, each case handing `Statement.getWriteScope()`'s write site and the table's schema to the rule). Cases, each one row: a `StampId()`-keyed insert into a `replay-permitted` table → `convergent`; the same table with a UNIQUE column → `serializable`; with a foreign key → `serializable`; an insert whose key is a parameter → `serializable`, and `convergent` once the key column is tagged `optimystic.fresh`; a `content_key` table's literal-keyed insert → `convergent`; `update set title = ? where id = ?` on a merge-tagged column → `convergent`, untagged → `serializable`; `set n = n + 1 where id = ?` tagged → `serializable` (read-dependent), and its ceiling `convergent` (what a member can see); `update … where name = ?` → `serializable`; `delete` → `serializable`; the same `StampId()` insert into a table with no profile tag → `serializable`; and the fold over two statements of different lanes → `serializable`. Nothing for the tag plumbing, the bridge fold or the four routes.
