Third of the five stage-4 tickets (see `4.1-offline-sync-plugin-mode-and-sealing`). Two coupled pieces: the `optimystic.offline` table tag ([§Per-table policy](../../docs/offline-sync.md#per-table-policy)), and the rule that a network-acknowledged commit made while entries are queued waits behind them ([§Network acknowledgement behind a non-empty queue](../../docs/offline-sync.md#network-acknowledgement-behind-a-non-empty-queue)). They are coupled because a `'network'` table in offline mode is the main way a network-acknowledged commit meets a non-empty queue.

## Design

### The tag

`optimystic.offline` on a table takes `'queue'` (the default) or `'network'`. It is read like `optimystic.network_watch` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`: from the declaration at construction (`wantsNetworkWatch` is the model), then from every `table_modified` through `OptimysticVirtualTable.followSchemaTags`, so `alter table … set tags` changes the policy on a running table. Saving the tag to the catalog record and restoring it on `hydrate` is what the existing tag persistence already does for every tag (`SchemaManager.persistTags`); nothing to add there beyond a test that the tag survives.

A value other than those two strings reads as `'queue'` and logs one warning per table (`offline:unknown-policy-tag`). The tag cannot be refused: Quereus applies a tag change to its own catalog before the module hears of it.

The vtab publishes its policy to the controller (`OfflineMode.setTablePolicy(schema, table, policy)`) at initialization and on each tag change, and withdraws it on drop (`forgetInCommitReports` is the sibling call). The controller keeps the map; the bridge asks it at commit.

### Which acknowledgement a commit gets

At `commitTransaction`, a transaction fixed `'local'` at begin (ticket 4.1) is sealed only when **every** dirty tree's table has policy `'queue'`. A dirty set that writes any `'network'` table gets network acknowledgement for the whole transaction, since it commits atomically. The policy can only demote local to network; it never promotes.

### Network acknowledgement behind a non-empty queue

A network-acknowledged commit, whatever made it one (mode off, a `'network'` table, the fall-back of ticket 4.1), takes today's route **only while the queue is empty**. With entries queued it was decided on a view that includes them, so it is sealed and enqueued like any entry, and `commitTransaction` awaits that entry's terminal status:

- `committed`: the commit resolves; `onCommitDurability` listeners were already called by the drain's report (ticket 4.1), and `queued` / `committed` statuses were delivered for it like any entry. Do not report twice.
- `failed`: `commitTransaction` throws the status's mapped `error`. The queue has already dropped the entry's segments and replayed, so the bridge tears the transaction down **without** running its snapshot restore (the shape the partial-commit catch uses), and sets the degraded latch only when the status carries `committedTables`.

The wait is bounded by `offline.networkCommitTimeoutMs` (registration option; default the legacy commit's own bound, `LegacyCommitTtlMs` in the bridge, five minutes — move the constant where both can read it). On expiry:

- entry never sent (`discard` succeeds): the entry is withdrawn (its `failed` status says `discarded`, which the README must say) and `commitTransaction` throws `OfflineCommitTimeoutError` with `transactionId` and `sent: false`;
- entry sent (`discard` throws `EntryNotDiscardableError`): it stays queued as a locally acknowledged entry, and the error carries `sent: true` so the caller follows it through `onStatus` / `status(transactionId)`.

`OfflineCommitTimeoutError` extends `QuereusError` with `StatusCode.BUSY`, like `ConcurrentModificationError`, and is exported from both entries.

The awaiting is a promise the controller resolves from its own `onStatus` translation (`whenSettled(transactionId)`), so there is one status path. `plugin.dispose()` during the wait rejects it with `QueueDisposedError`, which `commitTransaction` throws as is.

## Edge cases & interactions

- **A `'network'` table written in offline mode with an empty queue** commits on today's path and gets no `queued` status. Test.
- **A `'network'` table written in offline mode behind queued entries** waits; `commit` resolves when its entry commits, after the earlier entries. Test: node B unreachable, queue one `'queue'` entry, write the `'network'` table (the `exec` stays pending), reconnect, both land in order, the second `exec` resolves after the first entry's `committed`.
- **`exit()` with entries queued, then a commit** (the gap ticket 4.1 noted in the README): the commit waits behind the queue. Test, and remove the README note.
- **A mixed transaction** (`'queue'` and `'network'` tables in one transaction) is network-acknowledged whole. Test as part of the first case.
- **The tag changed while entries of the table are queued** (`'queue'` → `'network'`): the queued entries keep draining as they are; only new transactions see the policy. By inspection; say so in the README.
- **Timeout, never sent**: `failingPeers` holds node B unreachable past a short `networkCommitTimeoutMs`; `exec` rejects with `OfflineCommitTimeoutError { sent: false }`, `status(id)` is the retained `failed` outcome with reason `discarded`, and the row is gone. Test.
- **Timeout, sent**: the pend is parked by a `wrapRepo` gate (`test/commit-gate.ts` pattern) past the timeout; `exec` rejects with `sent: true`, the entry is still listed by `entries()`, and after the gate releases it commits and `status(id)` reports `committed`. Test.
- **A network-acknowledged commit's failure must not restore snapshots.** The entry's segments are already dropped and the remaining ones replayed; a snapshot restore would run the replay arm (harmless) but a verbatim one would be wrong. Tear down without restoring; by inspection, and the `concurrent-modification` arm of the test above asserts the row is gone and the next transaction works.
- **Session mode** never reaches this path (refused in ticket 4.1). By inspection.
- **An autocommit statement** behind a non-empty queue waits inside its own `exec`. Covered by the first wait test (use an autocommit insert).
- **Unknown tag value** reads `'queue'` and logs once. Test with a `with tags ("optimystic.offline" = 'later')` declaration asserting the write is locally acknowledged.
- **Tag survives hydrate.** Declare `'network'`, `plugin.hydrate` on a fresh `Database` over the same transactor, assert the policy (through the behaviour: a write in offline mode gets no `queued` status). One test; model `test/catalog-hydration.spec.ts`.

**Note from ticket 4.1 (landed).** Stage 4 wires no reachability gate, so the drain sends the head at once; its first attempt runs the queue's write-ahead wrapper and puts the entry in doubt, and a promise shortfall does not clear doubt (`OfflineQueue.recordAttempts`; pinned in `packages/db-core/test/offline-queue.spec.ts`). So with `failingPeers` alone an entry is sent and refused before any timeout, and `discard` then throws `EntryNotDiscardableError` with `because: 'in-doubt'`: the "timeout, never sent" arm cannot be produced that way. Keep the entry genuinely unsent with a parked pend (`test/commit-gate.ts` pattern) that is never released, or a registered reachability port answering false (ticket 4.5 plans the registry), and treat a never-sent timeout as the `sent: false` arm only when `discard` succeeds.

## Tests

`test/offline-mode-network-ack.spec.ts` with the cases above, on the two-node mesh. Each case asserts an observable (which node holds the row, the order of `committed` statuses, the error class), not internal state.
