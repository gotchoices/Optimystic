# Reactivity: per-root state is keyed by the tail, and the outgoing root sees the move

Second of three tickets for the stable-tier decision (see `cohort-topic-a-topics-root-can-move` for the decision text and the reading of it). The third, `reactivity-topic-is-the-collection-anchor`, changes the reactivity topic id from `H(tailId ‖ "reactivity")` to a per-collection `H(collectionId ‖ "reactivity")`. After that, one topic has a different root for every log tail block, and everything a root group keeps for its root has to be keyed by the root, not the topic. This ticket does that re-keying while the topic is still derived from the tail — so it changes no behaviour except the one fix below — and leaves the identity switch to the next ticket.

## Re-key per-root state by the root's tail

Today these are keyed by the topic id, which is one-to-one with the tail. Key them by the tail block id the state was built for (`NotificationV1.tailId` / `PushState.tailIdAtJoin`, base64url of `reactivityTailBytes(tail)`):

- **`ReactivityForwarderHost`** (`packages/db-p2p/src/reactivity/forwarder-host.ts`): the `served`, `ingestTails` and `rotationGates` maps. `ingest(n)` takes the notification alone and derives both the root key (`n.tailId`) and the topic (`reactivityNotificationTopicId(n)`, the one helper `reactivity-topic-is-the-collection-anchor` will switch). `pushStateFor(topicId)` becomes `pushStateForRoot(tail: Uint8Array)`. `markRotated(oldTail: Uint8Array, redirect, now)` and `rotationRedirectFor(oldTail: Uint8Array, now)`. The `directSubscribers` dependency becomes `(topicId, rootTail) => string[]`. `pushStateForCollection` is unchanged.
- **Node wiring** (`createLibp2pNodeBase` in `packages/db-p2p/src/libp2p-node-base.ts`):
  - `directSubscribers` resolves the engine **at the root coordinate** — `host.registry.findByCoord(reactivityRootCoord(rootTail))`, requiring `engine.rootPlaced` — instead of `findServing(topicId, REACTIVITY_FORWARDER_TREE_TIER)`, which with one topic per collection would return any tier-0 engine of that topic (an old root's included). Remove the constant if nothing else uses it.
  - Push-state gossip: `pushStateForGossip` and the `isCohortMember` gate resolve by `g.tailIdAtJoin`, and drop a frame whose `topicId` differs from the resolved state's.
  - Recover serve: `rotationFor` resolves by tail; `resolveCurrentServedTopic` becomes a resolver of the collection's current served root (`tailIdAtJoin` of `pushStateForCollection`).
- **Recover serve** (`packages/db-p2p/src/reactivity/recover-transport.ts`): `RecoverServeDeps.pushStateFor` → `pushStateForRoot(tail)`; `rotationFor` takes `{ tailId?: Uint8Array; collectionId }`. `serveResumeReply` looks up `latestKnownTailId` directly instead of hashing it into `staleTopic`.
- **Rotation scheduler and watch** (`packages/db-p2p/src/reactivity/rotation-rereg-scheduler.ts`, `packages/db-p2p/src/reactivity/collection-watch.ts`): the scheduler de-duplicates and cancels by the successor **tail** (`plan.newTailId`, base64url), and the watch's `rotationTargets` map is keyed the same way. With one topic per collection every successor would share a topic.

`PushState.topicId`, `PushStateGossipV1`, `RotationRedirectV1` and `ReRegistrationPlan` keep their fields here; the next ticket changes what `newTopicId` holds.

## The outgoing root must see the move

`ReactivityOriginationManager.detectTailRotation` (`packages/db-p2p/src/reactivity/origination-manager.ts`) runs only on commits this node **originates**, i.e. commits whose tail it applied (`selfAppliedTail` in `packages/db-p2p/src/cohort-topic/change-bridge.ts`). Since `reactivity-notifications-need-the-tail-cohort-to-be-the-topic-cohort`, a root group is the tail block's storage group, and once the network is wider than one group the old tail's group and the new tail's group are mostly different machines. A machine only in the old group never applies a commit naming the new tail, so it never calls `markRotated`: it never redirects a recover request reaching it, and it never releases the old root's `PushState` (the release is driven from `markRotated`'s sweep and from `rotationRedirectFor`). Read from the code, not reproduced; the same-machine case is what the existing specs cover.

The old group does see the rollover. The commit that starts a new log block rewrites the old tail block's `nextId`, so the old tail's group applies that block in a commit whose `tailId` names the new tail (the sweep half of `commitTailThenSweep`; `docs/internals.md` § Cohort-Topic Origination Bridge already says that group "holds a certificate for the same action but did not apply the tail").

**Design.** Rotation is observed from every commit event that names a tail, not only from originated ones:

- `ReactivityOriginationManager` gets `observeTailCommit(event: CollectionChangeEvent): void`, isolated (logs, never throws). With `last` = the tail this node last announced for the collection and `now` = the event's tail (in the reactivity tail encoding):
  ```
  if event.tailId is undefined → return
  if last is defined and last ≠ now → markRotated(last, { newTailId: now, effectiveAtRevision: event.rev }); forget last
  if selfAppliedTail(event) → last := now
  ```
  An event naming the **same** tail that this node did not apply (a data-block sweep landing on a node that is also in the tail's group) must leave `last` in place; forgetting it there would lose the baseline the rollover needs. The originate path no longer runs its own detection; block-fill tracking stays on the originate path.
- The change bridge calls it: `CohortTopicChangeNotifierDeps` gains an optional `observeTailCommit?: (event) => void`, invoked for every event with a `tailId`, **before** the `selfAppliedTail` gate and independently of it, inside the bridge's existing isolation. One catch-all subscription per node, one teardown. The node wiring passes the origination manager's method.
- `markRotated`'s first argument is now the old tail's bytes (see the re-keying above).

**Decided: the outgoing root does not tell its direct subscribers.** Folded in from the retired `feat-reactivity-rotation-reaches-current-subscribers`: a machine in the old group could, at the rollover commit, send its direct subscribers a notification under the old tail carrying `rotationHint{ newTailId }`, so they learn of the move at once instead of at their next tail check. Not built. The move it would trigger still waits on the subscriber's re-registration jitter (`T_rejoin_jitter`, 30 s uniform) and on the new root's cold-start deferral of a first registration (backlog `feat-a-new-topic-admits-its-first-registration-without-a-second-ask`, about 30 s measured) — the same order as the tail check it would replace — so its saving is the latency of one notification per log block, against a second notification path that runs only on old-group machines that hold a certificate for the rollover commit (a group of three or fewer: only the coordinator does). Record this as a bullet in `docs/reactivity.md` § Tail rotation with the revisit condition: if the cold-start deferral is removed and the root's direct subscribers on busy collections show the tail check as their dominant wake latency.

## Tests

- `observeTailCommit` (unit, `packages/db-p2p/test/reactivity/managers.spec.ts`): (1) a node that announced for tail A, then receives an event naming tail B that lists A among its blocks but not B, calls `markRotated(A → B)`; (2) a node that announced for A and receives a non-tail event naming A (it did not apply A) keeps A as its baseline, so a later event naming B still marks. Both are the branching contract the outgoing-root fix rests on; nothing else needs a new test.
- Change bridge: the observer is called for an event the gate drops (tail not applied) and is not called for a tail-less event. One case in `packages/db-p2p/test/cohort-topic/change-bridge.spec.ts`.
- Re-keying: adapt `forwarder-host.spec.ts`, `recover-transport.spec.ts`, `rotation-rereg-scheduler.spec.ts` and `collection-watch.spec.ts` to the new signatures; no new cases. While the topic is still tail-derived, keying by tail partitions state exactly as keying by topic did; `reactivity-topic-is-the-collection-anchor` adds the "two roots of one topic on one machine" case once that can happen.

## Edge cases & interactions

- **One-round commits.** When one coordinator covers every block, the other blocks commit on the tail's cohort (`docs/internals.md` § One commit round), so an old-group machine outside the new tail's cohort may never see the rollover and keeps its served `PushState` for that root. Add a `NOTE:` at the `served` map in `forwarder-host.ts` (extending the existing one): a root this node never sees a later tail for is never released; if that shows in memory, release a served root that has had no ingest for longer than `T_drain`. Tripwire, not work.
- **Nodes in both groups** see the tail commit (marks and re-baselines) and then the sweep (same tail, no-op). By inspection.
- **Tail-less events** (replica push, read-driven promotion, a group-of-one node) are ignored by the observer. By the guard.
- **Event order.** Events fire in commit order on one node, and a commit appending to a superseded tail is refused as stale before it lands, so an older tail cannot follow a newer one. By inspection; no test.
- **A gossip frame naming a tail this node serves under a different topic** is dropped by the new topic check, not merged into the wrong state.
- **Recover resume naming a tail this node never served** falls through to the collection's current served root, as the stale-topic lookup did.
- **Throws in the observer** must not block origination: the bridge already isolates per event; keep the observer before the gate inside that try.
