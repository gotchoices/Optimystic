# Queued blob pins settle with their transaction

First of three parts that finish the SQL side of blobs (the other two are `feat-blob-pins-reconcile-after-a-restart` and `feat-sql-columns-hold-blob-references`, which carry the same anchor and chain behind this one).

After `feat-blob-pins-follow-sql-commits`, a commit that reaches the network pins the references it adds, announces them, and releases the pins before the commit returns. A commit that is **queued** instead — offline mode, or a commit routed behind the queue — leaves its reference pins in place deliberately: nothing is on the network yet, so the writer is the only machine holding the bytes. This part releases those pins when the queued transaction finally settles: announced and released for the collections that committed, released outright for the ones that did not.

Nothing here reads the offline journal's segments or changes `JournalEntryRecord` (`packages/db-core/src/offline/journal.ts`). A reference pin's own label carries the transaction's `stampId` and the reference tree's collection id (`transactionReferencePinLabel` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts`), so the blob records are the durable, per-machine record of which transaction owes which pin under which scope. This departs from the backlog ticket `feat-sql-columns-hold-blob-references`, which proposed reading a queued entry's references back off its journaled reference-tree segments.

## What `SqlBlobPins` gains

One new public method, one work chain, and one piece of remembered state.

```ts
interface SqlBlobPinsDeps {
	// … from feat-blob-pins-follow-sql-commits (backendByKey, registration), plus:
	/** Every blob backend of a transactor key this factory has seen options for, each resolved. */
	knownBackends(): Promise<BlobBackend[]>;
	/** The tables a scope (a reference tree's collection id) still backs in this process. */
	tablesOf(scope: BlobScope): ReadonlyMap<string, unknown> | undefined;
	/** Resolves once no transaction is open on the bridge (`TransactionBridge.whenTransactionIdle`). */
	whenTransactionIdle(): Promise<void>;
}

export class SqlBlobPins {
	/** A queued transaction settled. `'all'` for a `committed` outcome; for a failed one the
	 * collection ids it had committed (possibly none). Never throws. */
	settleQueued(transactionId: string, committed: 'all' | ReadonlySet<string>): Promise<void>;
	/** Resolves once everything chained so far has run. Never await this inside a transaction. */
	settled(): Promise<void>;
	/** Stop chaining further work and wait for what is chained. Idempotent. */
	dispose(): Promise<void>;
}
```

**The chain.** `settleQueued` does not run inline; it is appended to one promise chain per `SqlBlobPins`, exactly as `OfflineRestore` chains its passes (`chained` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-restore.ts`): the chain never rejects, and each step's failure is logged. Every chained step **first** awaits `whenTransactionIdle()` and then returns at once if `disposed`. The chain is what the next two parts' reconcile and sweep join, so no two of them ever handle one transaction's pins at the same time.

The online arms of `feat-blob-pins-follow-sql-commits` (`holdForCommit`, `committed`, `queued`, `abandoned`) stay **off** the chain: they run inside `commitTransaction` / `rollbackTransaction` under Quereus's exec mutex and must not wait on a chain that waits on the transaction they belong to.

`settled()` exists for `plugin.hydrate` and for the specs; the warning in its doc comment is not decoration — a chained step awaits transaction idleness, so awaiting `settled()` from inside a transaction deadlocks.

**Settling from memory, falling back to the labels.** `queued()` already builds the `HeldPins` of the transaction it seals into the queue. Remember it: `private readonly queuedPins = new Map<string, HeldPins>()`, written by `queued()` and deleted by `settleQueued`. Then `settleQueued`:

- **Fast path** — the map holds the transaction: settle exactly those held references, with their backends and labels. No pin listing at all.
- **Fallback** — it does not (this process did not seal the entry: the queue was restored from the journal after a restart): for each `knownBackends()`, `listPins(transactionPinPrefix(transactionId))` and parse each label through `parsePinLabel`.

The fallback is the correct general answer and the fast path is the one almost every settle takes, because `listPins` **scans every blob record on the machine and reads each one** (the `NOTE:` already at `LocalBlobService.listPins` in `packages/db-p2p/src/blob/local-blob-service.ts`). Without the fast path a phone holding ten thousand photos would pay ten thousand key-value reads per offline commit. Say that at the fast path, so nobody simplifies it away.

The `put` pins (`transactionPutPinLabel`) need no arm here: `queued()` already dropped them. A stray one — a put that outlived its transaction — is `feat-blob-pins-reconcile-after-a-restart`'s to remove; `settleQueued` unpins any it meets on the fallback path, since it is already holding the label.

**What each reference pin gets.** For each (backend, ref, scope, label):

- **scope committed** (`committed === 'all'`, or the set holds the scope): confirm the scope is registered (below); `service.announce(ref, scope)`; `service.unpin(ref, label)`. On any failure keep the pin and log `blob:pin-kept transaction=… ref=… scope=… reason=…`, exactly as an online `committed()` does — the bytes stay here and the next part's reconciliation retries.
- **scope not committed** (the transaction failed, was discarded, or failed in a cascade; or a partial commit's other half): `service.unpin(ref, label)`, so the writer's piece sweep removes the bytes (docs/blobs.md §Committing a reference, "A transaction that rolls back").

Each reference in its own `try`; a failure is logged (`blob:pin-release-failed` for an unpin that threw) and the next reference still runs. Nothing here throws — the transaction has already settled, and a pin that cannot be released must not be reported as anything worse than a line in the log.

**Registration before announce, without resurrecting a dropped table.** Announcing into a reference tree the network's scope registry does not list tells the cohort to hold bytes no storage node will ever find referenced. So before announcing:

- the scope is still backed by a table in this process (`tablesOf(scope)` is non-empty) → `BlobScopeRegistration.ensure(backend, scope)` as an online commit does; `registered: false` keeps the pin;
- otherwise → a new **check-only** `BlobScopeRegistration.isRegistered(network, scope): Promise<boolean | undefined>`: `true` → announce; `false` → unpin (the table was dropped, so its references are unreferenced by design); `undefined` → keep the pin and retry later.

Without the check-only arm, a settle running after another machine dropped the table would *register the dropped tree again* and keep its blobs for ever.

```ts
/** Whether `scope` is in `network`'s registry, without writing: `undefined` when the answer cannot
 * be trusted. Not memoized — `ensure`'s memo records a registration this process made, and this
 * answers a question about another machine's state, which can change under us. */
async isRegistered(network: NetworkBinding, scope: BlobScope): Promise<boolean | undefined>
```

Read `BlobScopeRegistry.enumerate(network.transactor)` (`packages/db-core/src/blob/scope-registry.ts`) and answer:

- the listing holds `scope` → `true`, certain or not: every scope a listing names is listed.
- `certain` and `exists` and the listing does not hold it → `false`.
- anything else — an uncertain read, a registry that has never been written (`exists: false`), or a throw (logged `blob:scope-register-failed`, the existing line) → `undefined`. A registry reading as absent on a machine that holds pins is self-contradictory, and docs/blobs.md §Lifetime already fixes the bias: an uncertain read counts as "still referenced".

## Where `settleQueued` is called from

`OfflineMode.onQueueStatus` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`), which is the one place every terminal queue outcome passes through — the queue's own `onStatus`, and the restore's `emitSettled` for a deferred record it discarded. Add a new field and setter beside `attachOfflineMode`'s precedent:

```ts
/** The blob pins of this Database's plugin registration; set once by `register`. Absent on a
 * controller built bare, which every spec that constructs `new OfflineMode(bridge, db)` relies on. */
attachBlobPins(pins: SqlBlobPins): void;
```

In `onQueueStatus`, after the status has been translated and delivered (so a host's listener is never behind a pin release):

- `status.kind === 'committed'` → `void this.blobPins?.settleQueued(status.entryId, 'all')`
- `status.kind === 'failed'` → `void this.blobPins?.settleQueued(status.entryId, new Set(status.committedCollections ?? []))`

`'all'` is right for `committed` because `EntryStatus`'s `committed` arm names no collections — it carries the whole transaction's `durability` (`packages/db-core/src/offline/status.ts`). `partially-committed` is **not** terminal (the entry stays at the head, in doubt), so it gets nothing: its pins stay until the entry finally commits or fails.

`void` rather than `await`: `onQueueStatus` is called synchronously from the queue's drain and from the restore, and the release is chained work that must not hold either up.

## Construction order in `register` (`packages/quereus-plugin-optimystic/src/plugin.ts`)

`SqlBlobPins` is built **after** `new OfflineMode(...)`, because this part's `isLive` dependency (added in `feat-blob-pins-reconcile-after-a-restart`) reads the controller. Then both attachments: `txnBridge.attachBlobPins(pins)` (from `feat-blob-pins-follow-sql-commits`) and `offline.attachBlobPins(pins)`.

Expose it on the registration object beside `collectionFactory` and `txnBridge`, under the existing "internal components for testing and advanced usage" heading, as `blobPins` — that is how a spec reaches `settled()`, and how the third part's spec passes its own clock to the sweep.

`plugin.dispose()` awaits `blobPins.dispose()` **before** `offline.dispose()`: a chained step may still read the controller. A step parked on `whenTransactionIdle()` resolves as soon as the open transaction ends, which `db.close()` — called before `plugin.dispose()` — has already done.

## The factory's part

```ts
/** Every blob backend of a transactor key this factory has seen options for, each resolved
 * ({@link getBlobBackend}), in no promised order. A key whose resolution throws is logged
 * (`blob:backend-resolution-failed`) and left out, so one bad network does not hide the rest.
 *
 * Over the options map {@link getOrCreateTransactor} fills, NOT over the backends already
 * resolved: a pin written by a PREVIOUS process sits in a store this one may not have opened yet,
 * and a settle that only looked at opened stores would never find it. Resolving a store that
 * holds nothing costs one empty store.
 */
async knownBlobBackends(): Promise<BlobBackend[]>
```

The `Map<string, ParsedOptimysticOptions>` it reads is the one `feat-blob-pins-follow-sql-commits` adds to `getOrCreateTransactor` (first options per key winning). Nothing else is added here.

## Edge cases & interactions

- **Queued, then committed.** Reference pins held from the commit until the `committed` status, then announced and released; the `unstaged` pin went when the commit started. Test.
- **Queued, then discarded.** Every reference pin of the transaction released, nothing announced; the bytes go with the writer's next piece sweep. Test.
- **Queued, then failed in a cascade** (an earlier entry's removal failed this one). Same arm as discarded: `committedCollections` absent → empty set → everything released. Inspection of the `failed` call site.
- **Partial commit of a queued entry, then a permanent failure.** References into the committed collections are announced; the rest released. Inspection of the two arms, driven by `status.committedCollections`.
- **`partially-committed` while the entry is still queued.** No settle: the status is not terminal and the entry's remaining collections are still owed. Inspection.
- **A restart while the entry is queued.** The journal's restore puts the entry back; its reference pins are untouched by anything in this part, because no terminal status has arrived. When it later commits in this process, `settleQueued` takes the fallback path (this process never sealed it, so `queuedPins` has no entry) and releases from the labels. Test, over a "restarted" plugin on the same stores.
- **A transaction with no blob references at all.** The fast path's map has no entry and the fallback's `listPins` yields nothing: a scan per settle for a host that uses no blobs on that network. That is the cost the fast path exists to avoid for hosts that *do*; a host with no blobs has no blob records, so the scan reads nothing. Inspection.
- **A scope whose table was dropped on another machine between the queued commit and the settle.** `tablesOf` is empty in this process too once the drop reached it; `isRegistered` answers `false`; released, never re-registered. Inspection.
- **A scope whose network cannot be reached at settle time.** `isRegistered` or `announce` fails; pin kept and logged `blob:pin-kept`. Nothing retries it in this part — that is `feat-blob-pins-reconcile-after-a-restart`. Say so in the log line's doc and in the handoff below. Inspection.
- **A table on another network.** The pins, the announce and the registry read all go through the backend of the table's own transactor key, which the pin's own `HeldPins` entry (fast path) or `knownBackends` (fallback) supplies. `plugin.blobs` is only the default network's. Inspection.
- **No journal configured.** Queued entries do not survive a restart, so no settle ever takes the fallback path in a fresh process; the pins those entries left are stale and are `feat-blob-pins-reconcile-after-a-restart`'s to release. Inspection.
- **Concurrency with an online commit.** A commit's own pins belong to the active transaction and are settled by the bridge's off-chain arms; `settleQueued` only ever names a transaction the queue has finished with. Inspection.
- **Double settle.** A status delivered twice, or a settle racing the next part's reconcile, re-announces and unpins a label that is already gone. Both are idempotent; `settleQueued` is written so neither throws. Inspection.

Registers `vtables`, `functions` **and** `types`, which is what makes a `blobref` column resolve.
- `restart(node)`: dispose and close the old handle, open a new one over the same stores, `await plugin.hydrate(db)`.
- `pinsOn(plugin, ref)` and `allPins(plugin, prefix)`: `plugin.blobs.pinsOf` / `listPins` read back through `parsePinLabel`, so a test asserts on parsed kinds rather than on label text.
- A real blob: `plugin.blobs.put` of a few bytes, so `stat` and the `owed` hold mean something. Not a fabricated reference.

`packages/quereus-plugin-optimystic/test/blob-pins-queued.spec.ts`:

- **Queued, then committed.** `offline.enter()`; `put`; `insert` into a `blobref` table; commit. The reference then holds exactly one reference pin naming that transaction and that table's `/blobrefs` scope, and no `unstaged` pin. `offline.exit()`; `await offline.whenDrained()`; `await plugin.blobPins.settled()`. No `sql/` pin remains on the reference and `plugin.blobs.stat(ref)` reports durability `local`.
- **Queued, then discarded.** The drain held with `packages/quereus-plugin-optimystic/test/commit-gate.ts` so the entry cannot leave the queue; `offline.discard(id)`; after `settled()` no pin of any kind remains on the reference, and the table's reference tree is empty.
- **Restart while queued, then committed.** The drain held; `restart()` over the same stores; the entry is back (`offline.entries()` names it) and its reference pin is still there; release the gate, `whenDrained()`, `settled()`; the pin is gone and `stat` reports durability `local`. This is the arm that exercises the label fallback, so assert the reference tree lists the reference as well — an announce into an unregistered scope would be the silent failure here.

Three tests, one per arm of `settleQueued` that has a distinct outcome. The partial-commit and cascade arms are the same two branches driven by a different `committedCollections`, and are checked by inspection rather than by a fourth harness.
