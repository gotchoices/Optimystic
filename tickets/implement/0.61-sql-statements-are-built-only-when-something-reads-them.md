# SQL statements are built only when something reads them

Part of GitHub #63; measurements and the split are in `a-consensus-record-is-serialized-once-per-delivery`.

## What happens

`OptimysticVirtualTable` sets `wantStatements = true` in its constructor. Quereus then builds, for every row an INSERT, UPDATE or DELETE touches, a SQL text reproducing the row (`buildInsertStatement` and its siblings in `@quereus/quereus/src/util/mutation-statement.ts`, called from `@quereus/quereus/src/runtime/emit/dml-executor.ts`), writing a blob as `x'…'` hex — two characters per byte. The vtab's `update()` hands it to `TransactionBridge.addStatement`, which appends it to `accumulatedStatements` and, only when the transaction has a `TransactionSession` (session mode, configured through `configureTransactionMode`), records it in the session, from which it becomes the pend's validation payload.

In legacy mode — the default, and what every commit route but session mode takes — the statements are never read: the legacy commit pends bare transforms (`statements: []` in the bridge's legacy transaction), and `getStatements()` has no production caller, only tests. Profiled on the bench of the prereq ticket, building them was 12% of the CPU of an 8 × 256 KiB blob commit (0.84 s of 7.0 s), almost all in Quereus's `uint8ArrayToHex`.

## The change

`wantStatements` is true exactly when the bridge's current transaction has a session, read live on every access, so a host that configures session mode after tables were opened gets statements from its next transaction:

- Add `TransactionBridge.recordsStatements(): boolean` — `this.session !== null` (the session exists only while a session-mode transaction is open, and `addStatement` already ignores a statement outside an active transaction).
- In the vtab, replace the constant with a getter reading it. **Quereus declares `public wantStatements?: boolean` as a class field and is compiled for ES2022**, so its constructor defines an own property `wantStatements` on the instance, which shadows any getter on the subclass's prototype. Define the getter on the instance after `super(...)` (`Object.defineProperty(this, 'wantStatements', { get: …, configurable: true, enumerable: true })`), with a comment saying why. Confirm in `dml-executor.ts` that Quereus reads `vtab.wantStatements` per row (it does at the insert, update, upsert-update and delete sites as of this writing) rather than caching it per plan; if any site caches it per plan, note it — a plan prepared before session mode was configured would then send no statements, which is a session-mode defect to raise.
- Keep `addStatement` and `getStatements` as they are: in legacy mode they now simply see no statements.

The engine's work is then: no statement in legacy mode; in session mode the same statements as today.

## Edge cases & interactions

- **Session mode keeps every statement.** A session-mode transaction must record exactly the statements it records today, in order; `replicated-lane-ceiling.spec.ts` and the db-core session tests depend on that. Verify by running them.
- **Tests that read `getStatements()` in legacy mode** (`adapter-integration.spec.ts`, the statement-tracking cases around `getStatements`/`getStatementCount`; `statement-secret-arg-redaction.spec.ts`; `replicated-lane-ceiling.spec.ts`) were relying on the unused legacy recording. Move each to session mode (the `enableSessionMode` helper in `two-node-write-request-count.spec.ts`, or `session-mode-commit.spec.ts`'s) where what it checks is the statement text — the redaction spec's purpose is that a built statement carries no secret argument, which still matters in session mode. Where a legacy-mode case only counted statements, change it to assert legacy mode records none (that is the new contract, and replaces the old assertion rather than adding a test).
- **A transaction open when session mode is configured** has no session (it is created in `beginTransaction`), records nothing, and commits on the legacy route, as today.
- **Offline mode** seals and journals segments, not statements; confirm nothing in `offline-mode.ts`, `offline-journal.ts` or the outlook reads `accumulatedStatements` (a grep found only the bridge).
- **Session mode still carries each blob a further time**, as hex inside the validation payload of every collection's pend. That is a property of re-execution validation, not redundancy; the docs ticket `a-large-write-is-measured-once-and-its-cost-is-documented` states it. Do not change it here.
- Backlog `debt-session-mode-bridge-coverage` wants a session-mode harness for `addStatement`; if this ticket builds one for the moved tests, say so in that ticket.
