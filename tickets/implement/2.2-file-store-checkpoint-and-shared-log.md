# File store checkpoint and shared log

Last of three tickets from `file-storage-pays-one-fsync-per-write-group` (GitHub #37). `file-storage-commits-groups-through-a-log` left `FileWriteLog` appending for ever and keeping a `dirty` set of every path and directory written since the log was last truncated. This ticket spends that set.

## Checkpoint

A checkpoint makes the tree as durable as the log and then discards the log. In `FileWriteLog`:

1. **Seal.** Take a turn in the commit queue (so no apply is in flight), rename `write-ahead.log` to `write-ahead.log.sealed`, open a fresh `write-ahead.log` with its header, fsync it and `basePath`, and swap in an empty `dirty` set. Commits resume on the new log at once; only this step waits in the queue.
2. **Sync**, off the commit path and concurrently (a bounded fan-out, say 16 at a time): every file in the old `dirty` set, then every directory in it. A file deleted since is skipped (ENOENT), a file rewritten since is synced with its newer content, which the new log also covers.
3. **Truncate.** Unlink the sealed segment and fsync `basePath`.

A checkpoint runs when the log passes a size threshold (`checkpointBytes`, default 16 MiB, checked after each append), on an unref'd idle timer (`checkpointIdleMs`, default 5 s after the last append; re-armed by appends; `armUnrefTimer`), and on `close`. One at a time: a trigger during a checkpoint marks one more to run after it. A failure latches the store failed, like a rejected commit, since a half-synced tree under a discarded log is not recoverable.

**Replay** on open now reads `write-ahead.log.sealed` first, if present, then `write-ahead.log`: a crash between sync and truncate, or after the unlink but before the directory sync, leaves the sealed segment behind, and re-applying it before the current log is harmless because the current log holds every later write of the same paths in order. After replay both are gone and the current log is empty.

## `FileKVStore` on the shared log

`FileKVStore` keeps its interface and its on-disk shape (`<basePath>/<key>.json`, `/` to subdirectories) and writes through `WriteGroup` (`packages/db-p2p/src/storage/write-group.ts`, string keys) over the same `FileWriteLog` registry entry a `FileRawStorage` on the same directory holds, so the reference peer's blocks and under-replication ledger share one log, one lock and one checkpoint, and two stores' commits never interleave in one file. `get` consults the overlay first; `list` merges overlay puts and deletions with the directory walk; `flush` is the group commit; `IKVStore.flush` stays optional in the interface and `FileKVStore` implements it. Add `close()` and release the registry reference. `atomicWriteFile` then has no caller: delete it with its tests, and move `fsyncDir` into `file-write-log.ts`.

The ledger already flushes after every call that wrote, so a solo node's commit still costs one more sync for its shortfall entry: three per write, against the seventy-plus measured in #37. Say so in the README.

## Edge cases & interactions

- Crash after seal, before truncate: both segments present; replay applies sealed then current. Test by killing the checkpoint between steps (inject a throwing `unlink`) and reopening.
- A commit landing during the sync step goes to the new log and the new dirty set; its file may also be in the old set and is synced twice. By inspection; one test that writes during a parked checkpoint and reads it back after reopen.
- Checkpoint while the store is failed: skipped.
- `close()` with a checkpoint in flight waits for it, then runs the final one.
- A `FileKVStore` opened alone on a directory (the upgrade-check layout uses separate `blocks` and `kv` directories) owns the log entry itself; the registry refcount makes both orders of open and close work. Test both orders.
- The ledger's `list` after a delete not yet applied must omit the key: `under-replication-ledger.spec.ts` already round-trips record, satisfy and list; add the unflushed-delete case.
- The idle checkpoint timer and the overlay's idle flush timer are both unref'd; a process with nothing else to do exits. Assert by inspection, not a test.
- Size threshold with a batch larger than the threshold: one checkpoint after that append, not a loop.
