# Nodes apply the durability window

Third of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). `durability-window-from-cohort-size` added `NodeOptions.storageDurability` and `durabilityWindowMs(cohortSize, policy)`. `storage-flush-takes-a-sync-deadline` added `flush({ withinMs })` and `whenDurable()` to every store. This ticket connects them. Each storage apply that runs on a consensus record flushes with the window for that record's cohort. Every other storage write group stays strict (`withinMs` 0). Two writes to other stores that describe a block-store write are ordered after it.

Until `file-store-syncs-by-the-earliest-deadline` lands, no production backend defers, so on a real node this ticket changes nothing observable. The tests use `MemoryBatchBackend({ deferSync: true })`.

## Which groups get a window

| Storage write group | Caller | `withinMs` |
|---|---|---|
| pend apply on a consensus record | `ClusterMember.applyConsensusOperation` (`packages/db-p2p/src/cluster/cluster-repo.ts`) | `durabilityWindowFor(cohort size of record)` |
| commit apply on a consensus record | same | same |
| coordinator's own fallback pend / commit after consensus ran (`!localExecuted` branch of `pend`; the `consensusProof` fallback commit in `CoordinatorRepo.commit`) | `CoordinatorRepo` (`packages/db-p2p/src/repo/coordinator-repo.ts`) | same, from the record it ran on |
| `pendSolo`, `commitSolo` | `CoordinatorRepo` | 0. No consensus ran and only this machine holds the write (decision rule 5). |
| `cancel`, `recoverBlock`, `saveReplicatedBlock`, a `get` that took a write latch, a consensus `get`/`cancel` op | `StorageRepo` and its callers | 0. No cohort context. These are repair or bookkeeping writes, off the per-write hot path, and a replica a pusher counts as held (and may then release its own copy of) should not sit in a window. |

The cohort size is `Object.keys(record.peers).length`. The record lists every member, this node included. The policy caps it at the declared `clusterSize`.

## Mechanism

**`StorageRepo`** (`packages/db-p2p/src/storage/storage-repo.ts`):

- New `StorageApplyOptions { readonly proof?: BlockCommitProof; readonly syncWithinMs?: number }`.
- `pend(request, options?, apply?: StorageApplyOptions)` and `commit(request, options?, apply?: StorageApplyOptions)`. The commit's third parameter, today a bare `proof?`, becomes `apply`. Rename `ICommitProofPersister` to `ILocalApply`. It declares both methods with the extra parameter, and every cast site (`cluster-repo.ts`, `coordinator-repo.ts`) and the comment in `served-repo-proxy.ts` follow. A plain `IRepo` double still ignores the extra argument.
- `endGroup(work, wrote?, flush?: FlushOptions)` passes the options to `this.storage.flush`. `pend` and `commit` pass `{ withinMs: apply?.syncWithinMs ?? 0 }`. Every other caller passes nothing. `flushBehindFault` keeps flushing strict: a group that threw is reported as a failure, and what landed before the throw is synced before anyone acts on it.
- New `whenDurable(): Promise<void>` forwarding to the store, exposed as a named capability `IDurableStorage { whenDurable(): Promise<void> }`, so `ClusterMember` can probe it the way it probes the other capabilities.
- Change events still fire after `endGroup`. For a relaxed group that means after the write survives a process crash, not a power cut. Update the `endGroup` doc comment ("nothing announces a commit this node could still lose" now holds only for strict groups) and the *Visible before durable* paragraph in `packages/db-p2p/docs/storage.md` Invariant 6. Say that within `w` a power cut can take back a write this node announced and reported held, which is the accepted risk the window's loss target prices.

**`ClusterMember`** and **`CoordinatorRepo`** each take an optional component `durabilityWindowFor?: (cohortSize: number) => number`. Absent means 0, so every existing test and direct constructor stays strict. `createLibp2pNodeBase` builds it once from the resolved policy (`cohortSize => durabilityWindowMs(cohortSize, policy)`) and passes the same function to both.

**Executed marker after its apply** (write order 8, first half). `handleConsensus` today calls `this.stateStore?.markExecuted(...)` fire-and-forget right after the apply loop. It now writes the marker only once the apply is power-loss durable: `void durable.whenDurable().then(() => this.stateStore?.markExecuted(...))`, with the existing `.catch` logging. A rejection logs and writes no marker. `durable` is the `storageRepo` probed for `IDurableStorage`; without it, write at once as today. A process crash before the marker is written loses only the marker, and redelivery re-applies idempotently, which the comment already above that call argues. Extend that comment.

**Ledger entry after the commit it describes** (write order 8, second half). `KvUnderReplicationLedger` gains `KvUnderReplicationLedgerOptions.beforeRecord?: () => Promise<void>`, awaited at the start of `record` before any key-value write. `createLibp2pNodeBase` wires it to `() => rawStorage.flush()`, a strict flush of the block store. A shortfall entry is bookkeeping only this machine holds, so it is strict itself (its key-value store flushes strictly, as today). The block-store flush is what puts the commit it names on disk first. For a solo commit the block store is already synced, so this flush finds nothing to do and costs nothing. For a `majority` commit with a shortfall it forces the window's sync early, which costs one sync in a degraded case only. `settle` and `satisfy` need no ordering. A lost settle leaves an entry the drain re-satisfies, and that is harmless.

## Edge cases & interactions

- `record.peers` is the signed cohort for the record, and the cap at `clusterSize` lives in the policy function (by inspection; the function is tested in its own ticket).
- A cohort member that applies a commit with a window and then reports holding it is counted by the durability gate like any other (`withOwnApplyOutcome`). Nothing changes there, and `WriteDurability` is unchanged (decision rule 6, by inspection).
- Mixed cohorts, some members on backends that defer and some not, need nothing special (by inspection).
- A deferred sync that later fails latches the store. The next group on this node then fails, and the node logs it, but the writer was already answered. This is the window's accepted risk. Note it in the `endGroup` comment (by inspection).
- `beforeRecord` rejecting makes `record` reject. `noteReplicationShortfall` already logs per block and leaves `recordedBy` off (by inspection).
- The handleConsensus rollback path (apply threw) never reaches the marker write, so a deferred marker cannot be written for a rolled-back apply (by inspection).
- The coordinating member's apply happens inside `ClusterMember` (its own member). `CoordinatorRepo`'s own `storageRepo` calls happen only on the fallback and solo branches. Make sure the fallback pend after consensus (`if (!localExecuted)` in `pend`) uses the record's window and `pendSolo` stays strict (by inspection).
- `served-repo-proxy.ts` forwards only the plain `IRepo` surface. No apply options cross it, which is correct, because they are a local concern and never go on the wire (by inspection; keep its comment accurate).
- Read the `NOTE:` on `noteReplicationShortfall` about latency. `beforeRecord` adds a sync there only when a relaxed group is still pending.

## Tests

Over `new StorageRepo(new KvRawStorage(new WriteGroupDriver(new MemoryBatchBackend({ deferSync: true }))))`, in `packages/db-p2p/test/storage-repo.spec.ts`:

- **A commit applied with a window is reported and announced before it is power-loss durable, and a power cut takes it back; the same commit with no window survives.** Pend and commit a block with `syncWithinMs: 5000`. The commit resolves `success` and the change event fires, while `backend.committed` shows the last batch not durable and `whenDurable()` still pending. Then `powerLoss()`, and a fresh `StorageRepo` over the backend no longer holds the revision but does hold everything synced before. Repeat with no window: the revision survives `powerLoss()`.

In `packages/db-p2p/test/coordinator-repo.spec.ts`, or the spec that already drives `commitSolo`:

- **A solo commit is synced before it is acknowledged, even on a node whose window is non-zero.** Give the coordinator `durabilityWindowFor: () => 5000` over the deferred backend, commit through the solo path, then `powerLoss()`. The revision is still there.

No test for the marker or ledger ordering (two `await`s at a seam; by inspection). No test for the option plumbing (wiring).
