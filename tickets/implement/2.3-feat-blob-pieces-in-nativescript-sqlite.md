# Blob pieces in the NativeScript SQLite database

`feat-a-node-stores-blob-pieces` has landed: `IPieceStore` in `packages/db-p2p/src/blob/piece-store.ts`, `MemoryPieceStore`, `FilePieceStore` in `packages/db-p2p-storage-fs/src/file-piece-store.ts`, and the conformance suite `runPieceStoreConformance` in `packages/db-p2p/src/testing/piece-store-conformance.ts` (published as `@optimystic/db-p2p/testing/conformance`, which this package's tests already import for the raw-storage suite). This ticket adds `SqlitePieceStore` to `@optimystic/db-p2p-storage-ns`: one table in the database `openOptimysticNSDb` already opens, sharing the handle with `SqliteRawStorage`, `SqliteKVStore` and the identity helper. It is not a `RawStoreDriver` store and does not go through `SqliteBatchBackend`'s write group: a piece is raw bytes written by one autocommit statement, and needs no cross-key atomicity.

Read the contract on `IPieceStore` before writing: every method's doc comment is a requirement (fresh bytes per `get`, the store keeps its own copy on `put`, a present id writes nothing, zero-length is a piece, the drain-before-yield and concurrency rules on `list`, flush rules 1, 2 and 4 of `RawStoreDriver.flush`, `storeIdentity` only when a block store measures this store's bytes).

## Schema

Append to `SCHEMA_SQL` in `packages/db-p2p-storage-ns/src/db.ts`, in the package's uppercase style (the `NOTE:` there explains why):

```sql
CREATE TABLE IF NOT EXISTS pieces (
	id    TEXT PRIMARY KEY,
	bytes BLOB NOT NULL
);
```

- `id` is the `PieceId` string as given (a canonical CIDv1 base32 string, ASCII).
- An ordinary rowid table, not `WITHOUT ROWID`: SQLite's own guidance is that `WITHOUT ROWID` suits small rows, and a piece row is up to 1 MiB.
- `DEFAULT_DB_VERSION` stays 1 and no migration step is added: `applySchema` runs on every open and `CREATE TABLE IF NOT EXISTS` gives a database created by an older build the empty table on its next open, touching nothing else. Nothing reads `user_version` today.
- Extend the schema doc comment's bullet list with `pieces` (one line: blob piece bytes keyed by the piece id, written by `SqlitePieceStore`, outside the write group; a file created before the table existed gains it on its next open).

## `SqlitePieceStore`

New module `packages/db-p2p-storage-ns/src/sqlite-piece-store.ts`, exported from `src/index.ts` beside `SqliteKVStore`.

```ts
export class SqlitePieceStore implements IPieceStore {
	readonly durability: StoreDurability = 'power-loss';
	constructor(db: SqliteDb);
	/** The identity `SqliteBatchBackend` reports over this handle, so `blockStoreCountsPieces` counts the pieces once. */
	storeIdentity(): StoreIdentity;   // identityForHandle('sqlite-handle', db)
	has(id: PieceId): Promise<boolean>;
	get(id: PieceId): Promise<Uint8Array | undefined>;
	put(id: PieceId, bytes: Uint8Array): Promise<void>;
	delete(id: PieceId): Promise<void>;
	list(): AsyncIterable<PieceId>;
	bytesUsed(): Promise<number>;
	flush(): Promise<void>;
}
```

`IPieceStore`, `StoreDurability`, `StoreIdentity`, `identityForHandle` and `StoreFailedError` come from `@optimystic/db-p2p`; `PieceId` from `@optimystic/db-core` (both already dependencies). `SqliteBatchBackend` builds its identity as `identityForHandle('sqlite-handle', db)` in `packages/db-p2p-storage-ns/src/sqlite-storage.ts`; that function returns the same string for the same handle object, and `KvRawStorage`, `WriteGroupDriver` and the read-cache wrapper all pass it through, so `SqliteRawStorage.getStoreIdentity()` equals this store's `storeIdentity()` over one handle. Export the scheme string as a module constant shared by both classes rather than spelling `'sqlite-handle'` twice.

Statements, each prepared once in the constructor through `db.prepare` (writes then go through the connection mutex, reads do not, as for `SqliteKVStore`):

| Member | Statement |
|---|---|
| `has` | `SELECT 1 AS present FROM pieces WHERE id = ?` |
| `get` | `SELECT bytes FROM pieces WHERE id = ?`, returning the row's `bytes` as the `Uint8Array` the driver returns (a fresh one per row, which satisfies "bytes no one else holds") |
| `put` | `INSERT OR IGNORE INTO pieces (id, bytes) VALUES (?, ?)` — a present id writes nothing, which is the interface's rule, in one statement with no read first |
| `delete` | `DELETE FROM pieces WHERE id = ?` |
| `list` | `SELECT id FROM pieces WHERE id > ? ORDER BY id LIMIT ?`, starting from `''`, `PIECE_LIST_PAGE = 1000` ids a page, each page drained by `all` before yielding, the next page keyed after the last id of the previous page, stopping at a page shorter than the limit |
| `bytesUsed` | `SELECT coalesce(sum(length(bytes)), 0) AS used FROM pieces`; SQLite answers `length()` of a BLOB from the record header, without reading the content |

- **Paged listing.** `list` pages rather than draining the whole table as `SqliteBatchBackend.listBlockIds` does, because a node can hold hundreds of thousands of pieces and the `NOTE:` on `NSPluginStatement.all` in `ns-opener.ts` says a result over 512 KiB crosses NativeScript 8's JNI bridge through a buffer holding a scarce global reference. A page of 1000 ids of about 60 characters stays far below that. Keyset paging (`id > last`) rather than `OFFSET`, so a page costs one index seek whatever the position. It yields each id once and every id present for the whole walk, which is exactly the `list` contract.
- **Exact bytes on put.** Bind `bytes` when it spans its whole `ArrayBuffer` (`byteOffset === 0` and `byteLength === buffer.byteLength`), otherwise a copy (`bytes.slice()`), through a private module function `wholeBufferBytes`. The plugin's binding of a typed array is native code this suite never runs, and a binding that sends the view's whole buffer would store bytes that are not the piece. The builder normally hands whole buffers, so the copy is rare. (Verified: `node:sqlite` itself binds a sub-view correctly, so the stand-in cannot catch this; it is a device-side precaution, say so in the function's comment.)
- **Zero-length piece.** Under `node:sqlite` an empty `Uint8Array` binds as an empty BLOB (verified), so the conformance case passes. Whether the plugin on a device binds it as an empty BLOB or as NULL (which `NOT NULL` would refuse) is unverified: leave a `NOTE:` tripwire at `put` — if a device refuses a zero-length piece, bind it as `zeroblob(0)` — and list it in the README's device section. No defensive code now.
- **Durability and flush.** Writes are autocommit statements: each survives a crash of this process once it resolves, and the write-ahead log keeps them in order. `flush()` makes every write resolved before it survive a power cut by one synced commit (`syncSqliteDb`), and only when something was written since the last flush; otherwise it resolves at once. That is exactly `SqliteKVStore.flush`, so extract the bookkeeping both use into `sqlite-sync.ts`:

```ts
/** Tracks whether a store wrote since its last flush, and latches the store failed when a sync fails. */
export class PendingSqliteSync {
	constructor(db: SqliteDb);
	/** Throws `StoreFailedError` once a sync has failed. Writes call it first. */
	throwIfFailed(): void;
	/** A write resolved; the next flush must sync. */
	noteWrite(): void;
	/** One synced commit when a write resolved since the last flush, otherwise nothing; a failure latches and throws `StoreFailedError`. */
	flush(): Promise<void>;
}
```

Move the existing comment about clearing the flag before the sync with it. `SqliteKVStore` is rewritten over it with no change in behaviour (its `dirty` and `fault` fields and `throwIfFailed` go; its class comment keeps describing the behaviour; the existing "flush() syncs once when something was written" test in `test/sqlite-kv-store.spec.ts` keeps passing unchanged). `SqlitePieceStore` uses it the same way: `put` and `delete` call `throwIfFailed`, run, then `noteWrite`; reads never throw for a latched store. Keep `PendingSqliteSync` internal to the package (not exported from `index.ts`).

- **Handle ownership.** No `close`: the handle is shared, and the host closes it after the node has stopped and the block store has closed, as the README already says for the other stores. The store holds nothing in memory to release. The interface makes `close` optional.
- **Logging.** `bytesUsed` catches a failed query, logs it under `createLogger('storage:pieces')` (namespace `optimystic:db-p2p-storage-ns:storage:pieces`) and answers 0, as `approximateBytesUsed` does; nothing else logs.

## The 512 KiB JNI note

Add one sentence to the `NOTE:` on `NSPluginStatement.all` in `packages/db-p2p-storage-ns/src/ns-opener.ts`: `SqlitePieceStore.get` reads one piece per call, a piece this design writes is 256 KiB, and only a piece from a blob another IPFS tool made can exceed 512 KiB (the reader admits up to 1 MiB), so a node reading thousands of such pieces between garbage collections is the case that note's remedy would have to cover. Keep the note's fragment "512 KiB" intact; docs cite it.

## Edge cases & interactions

- **A database an older build created.** It lacks `pieces`; the next open adds it empty and every block, proof, key-value and identity row reads as before. Test (below).
- **An older build opening this database.** It ignores the extra table; `CREATE TABLE IF NOT EXISTS` never drops one. Inspection.
- **A 1 MiB piece.** Round-trips under the `node:sqlite` stand-in through the conformance suite's large case. The JNI path of a real NativeScript 8 device is not run by any suite; the README's "What has run on a device" section says the piece store has not.
- **A zero-length piece.** Conformance case on the stand-in; device binding unverified, tripwire `NOTE:` at `put`.
- **A view over a larger buffer.** Copied by `wholeBufferBytes` before binding. Inspection (the stand-in binds views correctly either way).
- **Two puts of one id at once.** Both statements serialize on the connection mutex; the second is ignored. Conformance case.
- **A put racing a flush.** `PendingSqliteSync` clears its flag before syncing, as `SqliteKVStore` does today, so a write resolving during the sync is covered by the next flush. Inherited; inspection.
- **A failed sync.** Latches: every later `put`, `delete` and `flush` throws `StoreFailedError`, reads keep working. Covered for the key-value store by the existing test; the piece store uses the same class.
- **A put racing a block-store write group.** A piece put is a mutex-guarded autocommit statement; `SqliteBatchBackend.commit` holds the mutex for its whole transaction, so a put waits for it and never lands inside the group's transaction. Inspection.
- **Crash between a put and a flush.** Survives a process crash; a power cut may lose it, and the blob service had not yet written the record naming it (it flushes pieces before writing the record); the sweep removes any orphan. Inherited from the conformance suite's reopen case.
- **Listing while pieces are put or deleted.** Keyset paging may include or miss an id added during the walk and never yields one twice; the sweep that consumes `list` protects in-progress pieces itself (`InProgressPieces`, `SweepGate`). Inspection.
- **Block-store listing.** `listBlockIds` reads `metadata` only, so pieces never appear as blocks. Inspection.
- **Storage use counted once.** `SqliteBatchBackend.approximateBytesUsed` multiplies `page_count` by `page_size`, which already includes the `pieces` table; equal identities make `blockStoreCountsPieces` leave the piece figure out. Covered by that rule's own test in db-p2p; the identity equality here is by construction (one shared constant, one handle).

## Tests

- `packages/db-p2p-storage-ns/test/sqlite-piece-store.spec.ts`:
  - `runPieceStoreConformance('SQLite pieces', makeStore, { persistent: true })`, returning a `PieceStoreHarness`, built like the `'SQLite'` harness in `test/sqlite-storage.spec.ts`: a file database in a fresh temp directory (`mkdtemp`) through `openTestFileDb`; `reopen` closes the handle and opens the same file, returning a new `SqlitePieceStore` over it; `cleanup` closes the current handle and removes the directory. This pins put/get, the ignored second put, the zero-length piece, delete, listing, bytes used, the 256 KiB and 1 MiB pieces, and flush-then-reopen.
  - One case: a database written without the table gains it. Open a file database through `openTestFileDb`, `DROP TABLE pieces`, write and flush one block through `SqliteRawStorage` (close the storage), close the handle; reopen through `openTestFileDb`; the block reads back, and a piece put then get round-trips. It pins the upgrade path for this backend, which no other suite covers (`packages/upgrade-check` covers `fs` and `leveldb` only).

No test for `PendingSqliteSync` of its own: the key-value store's existing flush test covers it. No test of paging beyond the conformance listing cases unless a page boundary bug is suspected; if the implementer wants confidence in the page loop, make `PIECE_LIST_PAGE` a constructor option only if that costs nothing else — otherwise rely on inspection.
