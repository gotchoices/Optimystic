# Commit content digest — part 2 of 3: threading to the wire

Split from `commit-cert-bind-block-content-digest`. Part 1 (`commit-cert-digest-core-primitives`)
provides `computeBlockContentDigests`, `Tracker.peekMaterialized`, and the `blockDigests?` field on
`CommitRequest` / `RepoCommitRequest`. This part makes the two commit call sites compute the digests
and makes `NetworkTransactor` put the right subset on each per-peer request. Part 3
(`commit-cert-digest-member-check`) adds the member-side check.

Who declares the digest is SETTLED (do not re-open): the client, via its `Tracker` — the coordinator
cannot (`CoordinatorRepo.commit` forwards without materializing and explicitly handles a coordinator
that missed the pend), and both client commit sites still hold the staged tracker.

## Tasks

**`TransactorSource.transact`** (`transactor-source.ts:140`) gains a trailing
`blockDigests?: BlockContentDigests` parameter (after `priority`) and spreads it onto the
`CommitRequest` it builds (`:150-153`) — omit the key when undefined, so the common no-digest request
serializes exactly as before (the field is inside every signed hash preimage; a spurious
`blockDigests: undefined` key would be dropped by JSON.stringify anyway, but keep the request shape
clean).

**`Collection.sync`** — in `syncInternal` (`collection.ts:590-680`): the snapshot tracker is built at
`:624` (`new Tracker(this.sourceCache, snapshot)`); before the `this.source.transact(...)` call at
`:638`, compute `await computeBlockContentDigests(tracker, tracker.transformedBlockIds())` and pass it
as the new argument. The tracker layers over `this.sourceCache` (a `CacheSource`), so the part-1 duck
probes are live here.

**`TransactionCoordinator.commitCollection`** (`transaction/coordinator.ts:1025-1083`): it reaches
`this.collections.get(collectionId)` whose `.tracker` is public and still holds the staged transforms
(resets happen at `:385`/`:636`, after commit). Compute
`await computeBlockContentDigests(collection.tracker, blockIds)` and put it on the `CommitRequest`
built at `:1046-1051`. That tracker also layers over the collection's `CacheSource`.

**`NetworkTransactor` per-batch subsetting** (`network-transactor.ts`): `commit` (`:681-719`) commits
the header (when present and not in `blockIds`) and the tail as their own single-block batches via
`commitBlock` (`:721`), then the rest via `commitBlocks` (`:750`). Thread `blockDigests` from the
incoming `CommitRequest` through `commitBlock` into `commitBlocks`, and inside `commitBlocks` subset
AT SEND TIME in the `processBatches` callback: the per-peer request carries only the entries whose ids
are in that batch's `batch.payload` (the batch's block ids). Send-time subsetting from the full map is
what keeps retries correct — `processBatches` re-batches failed blocks onto different coordinators.
Omit the field entirely when the subset is empty. Each batch's message becomes its own cluster
record, so shipping the whole map would make one cohort sign for blocks it is not responsible for.

Header and tail are ordinary tracker blocks, so both end up carrying their own digest through the same
subsetting — assert that in tests rather than assuming it.

## Tests (db-core; see `test/network-transactor.spec.ts` for the existing transactor harness)

- Per-batch subsetting: a multi-peer commit where blocks map to different coordinators — each repo's
  received `RepoCommitRequest.blockDigests` contains exactly its own blocks' entries, none of the
  others'; a batch with no digested blocks receives NO `blockDigests` key.
- Header and tail single-block batches carry their own digest.
- A partial map is legal: ids without digests still commit (undeclared ids simply have no entry).
- `Collection.sync` end-to-end (TestTransactor or the network harness): the commit request(s) carry
  digests for insert and update blocks; delete-only blocks have no entry.
- Mixed-version hash guarantee: build a `RepoMessage` whose commit op carries `blockDigests`,
  JSON-round-trip it (simulating an un-upgraded peer that parses the message with no knowledge of the
  field), and assert `computeClusterMessageHash` / `computeClusterPromiseHash` /
  `computeClusterCommitHash` over original and round-tripped message are byte-identical (the helpers
  in `db-core/src/cluster/membership.ts` canonicalise generically — this pins that no one "optimizes"
  them into a field allowlist later).
