# Blob reference trees follow SQL rows

Second of four parts of backlog `feat-sql-columns-hold-blob-references` (docs/blobs.md §SQL, §Registering references). After `feat-blob-sql-type-and-blob-service` a table can declare a `blobref` column. After `feat-committed-rows-register-the-blobs-they-reference` `packages/db-core/src/blob/` holds the reference tree (`BlobReferenceTree` in `packages/db-core/src/blob/reference-tree.ts`, with `stage`, `stageAdd` and `stageRemove` into the caller's transaction, the reader `listed`, and `readonly tree`), the key codec (`blobReferenceKey` and `decodeBlobReferenceKey` in `packages/db-core/src/blob/reference-key.ts`) and the scope registry (`BlobScopeRegistry` in `packages/db-core/src/blob/scope-registry.ts`, with staging methods, the stage-and-sync statics `register` and `unregister`, and the reader `enumerate`).

This part makes every table with a `blobref` column keep its reference tree in step with its rows — exactly as it keeps its index trees, through every write path and every commit route — registers the tree in the network's scope registry, and refuses the two schema changes that would leave the tree describing rows that no longer hold what it says. It touches no blob service: pinning and announcing are `feat-blob-pins-follow-sql-commits`.

## The table's reference tree

**Location.** For a table with at least one `blobref` column the reference tree lives at `${this.options.collectionUri}/blobrefs`, the index precedent being `${collectionUri}/index/${indexName}` (`openIndexTree` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`). Its collection id — `<path>/blobrefs`, the URI with any `tree://` prefix stripped — is the table's **scope**, the `BlobScope` the registry lists and a later announcement names. An index tree can never collide with it: index trees sit one segment deeper, under `/index/`.

**Opened through the ordinary collection path, not through db-core's.** Add a private `openBlobReferenceTree(transactor?: ITransactor): Promise<BlobReferenceTree>` to `OptimysticVirtualTable`, a copy of `openIndexTree` with the `/blobrefs` URI, which calls `CollectionFactory.createOrGetCollection` and wraps the result: `new BlobReferenceTree(tree as unknown as Tree<string, BlobReferenceEntry>)`. No new factory method for the tree, and no call to `BlobReferenceTree.createOrOpen` from the plugin.

Why this is the same tree `BlobReferenceTree.createOrOpen` would have opened, and why it is the better path here:

- db-core opens it with `pairEntryKey` (the entry's first element) and the `Tree` default comparator, `(a, b) => a < b ? -1 : a > b ? 1 : 0`. The factory opens it with `extractKeyFromEntry` (also the entry's first element) and `compareTreeKeys` in `packages/quereus-plugin-optimystic/src/schema/key-encoding.ts`, which is that same expression. The two constructions are identical.
- Going through the factory is what applies the factory's `treeOptions` — the offline queue's sealed-segment refusal callback and the materialized-view follower's adopted-commits callback — and the per-transaction collection cache, to this tree exactly as to every other tree the table opens. A db-core-routing factory method would have to re-derive both.

Create-or-open, as for index trees and for the same reason: a table whose rows have never referenced a blob has never committed the tree's header, so "absent header" and "empty tree" are indistinguishable at the block layer, and inventing the empty tree in the local tracker is the correct representation.

Add a `NOTE:` at `openBlobReferenceTree`: a table deliberately declared at another table's `<uri>/blobrefs` would adopt that table's reference tree as its main tree. The storage-adoption guard matches whole table URIs (`findRecordForUri` in `packages/quereus-plugin-optimystic/src/schema/schema-manager.ts`), so it does not see this, exactly as it does not see a table declared at another's `<uri>/index/<name>`; revisit with that case, not before.

**Wiring in `OptimysticVirtualTable`** (all in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`). A new private field `blobReferences?: BlobReferenceMaintainer`.

- `doInitialize`: when the resolved `storedSchema` has a `blobref` column (`isBlobRefColumn` in `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts`, which reads either the engine's `logicalType` or a record's `affinity`), open the reference tree alongside the index trees — reusing a kept handle when there is one — and publish the maintainer with the row codec and index manager in the one synchronous step after the last await (the "Publish the rebuilt state in ONE synchronous step" rule there). A table with no `blobref` column opens nothing: every registered collection costs a snapshot per savepoint and a slot in the session coordinator's map. The read-only (provisional) pass opens it too and returns before `registerCollections`, as it does for index trees.
- `KeptHandles` and `adoptCatalogEntry`: keep the reference tree with the main collection and the index trees. A transaction the offline queue holds is sealed into that handle, so a re-initialization that opened a fresh one would leave the queued entry staged into a tree nothing commits. `forgetUnmaintainedTrees` takes a kept reference tree out of the bridge if the adopted description has no `blobref` column — unreachable today, since the refusals below keep a table from losing such a column, and cheap insurance against a future arm that can.
- `registerCollections`: `registerTree` the reference tree, so it is in the session coordinator's live registry, in legacy savepoints, and in `TransactionBridge.collectionsOf(table)` — which is how the offline restore finds its journaled segment (`collectionsOfTable` in `optimystic-module.ts`, `resolveCollections` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-restore.ts`) and how the DDL gate `assertNoQueuedEntries` sees it. No key-taken or entry-changed renderer: its elements carry no guard.
- `markDirtyTrees`: mark it dirty with the main and index trees. That is what carries it on every commit route with no commit-route code change — a session-mode participant (the coordinator commits every registered collection with staged changes), a member of the legacy batch (`commitBatchLegacy`, through `legacyBatch`), a tree of the per-tree sweep, and a collection of the offline entry (`queueableSet`, `sealIntoQueue`).
- `hasStagedWrites`: include it. A statement that stages a reference entry always stages into the main tree too, so this changes no answer today; it is included so the question stays "any of this table's trees".
- `describeCollection`: answer `{ kind: 'index', table }` for the reference tree's collection id, so the collection is named by its table rather than reading `{ kind: 'unknown' }`. Be honest about what that buys: the outlook never reads the description for these elements, because `CollectionJudge.element` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-outlook.ts` returns before judging any element with no guard. It is for a restored entry's reported description, nothing more.
- `republishColumnLayout`: rebuild the maintainer's column list from the `tableSchema` it is handed — not from `this.tableSchema`, which `applyCatalogOnlyEdit` has not yet replaced — through `withColumns`, for both layout kinds. A catalog-only DROP COLUMN of another column moves the `blobref` columns' positions; an ADD COLUMN of a second `blobref` column extends the list.
- `attachBlobReferences(): Promise<void>`: open the tree, build the maintainer from `this.tableSchema`, register the tree with the bridge. Idempotent — a no-op when the instance is not initialized, when its schema has no `blobref` column, or when it already has a maintainer. Awaited in `OptimysticModule.alterCatalogOnly` immediately after `table?.applyCatalogOnlyEdit(...)`, which is where every catalog-only arm converges, so the ADD COLUMN that gives a table its first `blobref` column leaves the instance maintaining the tree from the next statement.
- `pullEveryTree`, `queryCommitted`, `verifyIndexes` and every read path: untouched. Nothing in the plugin reads the reference tree, so refreshing it on an external change would be work for nobody.

## The maintainer

New module `packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts`, the counterpart of `IndexManager` for references:

```ts
/** A staged change to the reference tree, as the pin lifecycle consumes it (feat-blob-pins-follow-sql-commits). */
export interface ReferenceChange {
	readonly op: 'add' | 'remove';
	readonly ref: BlobRef;
	readonly referrer: string;
	readonly scope: BlobScope;
}

/** One `blobref` column of a table: where the engine positions it, and the name it is stored under. */
export interface BlobRefColumn {
	readonly position: number;
	readonly name: string;
}

export class BlobReferenceMaintainer {
	constructor(
		columns: readonly BlobRefColumn[],
		tree: BlobReferenceTree,
		scope: BlobScope,
		onStaged?: (changes: readonly ReferenceChange[]) => void,
	);
	/** The table's `blobref` columns, in declaration order. Takes either column shape (`isBlobRefColumn`). */
	static columnsOf(columns: readonly BlobRefColumnShape[]): BlobRefColumn[];
	/** The underlying db-core tree, for the vtab to mark dirty and register. */
	get tree(): BlobReferenceTree;
	stageInsert(row: Row, primaryKey: PrimaryKey): Promise<void>;
	stageDelete(row: Row, primaryKey: PrimaryKey): Promise<void>;
	stageUpdate(oldRow: Row, newRow: Row, oldPrimaryKey: PrimaryKey, newPrimaryKey: PrimaryKey): Promise<void>;
	/** This maintainer over a new column list, everything else kept ({@link republishColumnLayout}). */
	withColumns(columns: readonly BlobRefColumn[]): BlobReferenceMaintainer;
}

/** The referrer of one row's one column: the table's framed primary key, then the column name framed
 *  as one more element. */
export function blobReferrer(primaryKey: PrimaryKey, column: string): string;
```

- **Referrer key.** `primaryKey` is already the self-delimiting framed tuple the main tree is keyed by (`RowCodec.createPrimaryKey` and `RowCodec.extractPrimaryKey`, over `encodeKeyTuple`), so `blobReferrer` is `primaryKey + encodeKeyElement(column)`: each element self-delimits, so the concatenation is injective and `splitKeyTuple(referrer)` gives the key's elements followed by the column name. A referrer contains U+0000 framing characters, which is fine — `blobReferenceKey` splits at the **first** one, and a reference, being lowercase base32, contains none.
- **The column name** is the stored spelling, exactly as `tableSchema.columns[i].name` holds it. It is stable: RENAME COLUMN is refused on every table of this module (`alterTable`, arm `renameColumn`), and the two refusals below keep a `blobref` column from being dropped or re-declared away.
- **Values.** For each `blobref` column, a NULL cell stages nothing. A non-NULL cell goes through `parseBlobRef`; a `BlobRefError` is rethrown as `QuereusError(…, StatusCode.MISMATCH, cause)` naming the table and column. The engine already validates through the type, so this is unreachable through SQL; it is what keeps a malformed value out of the tree whatever path delivered the row.
- **Per row and per `blobref` column.** Insert adds `(new value, new key, column)`. Delete removes `(old value, old key, column)`. An update at the **same** key removes the old value and adds the new one only for a column whose value changed — equal values, both NULL included, stage nothing. An update at a **changed** key removes every old non-NULL value under the old key and adds every new non-NULL value under the new key, whether or not the value changed. Each call stages removes before adds, in one `BlobReferenceTree.stage` action, so a remove and an add of one key within a call cannot invert. Then `onStaged(changes)` is called with exactly what was staged, in that order; nothing is called when nothing was staged.
- **Pure.** The staged operations are a function of `(rows, keys, columns)` alone: no read of the tree, no clock, no blob service. That is what lets a validating member's re-execution through `QuereusEngine` (`packages/quereus-plugin-optimystic/src/transaction/quereus-engine.ts`) derive the same operations (docs/blobs.md §Registering references, *Under transaction validation*). A remove is blind, as an index delete is — `IndexManager.deleteIndexEntries` explains why that is sound — and an add is an upsert of a key fixed by the reference and the referrer whose value is fixed by the key. Neither carries a guard, so neither is counted in the offline queue's already-applied tally and neither can refuse: a racing change to one row is refused by the main tree's `unchanged` guard, which rolls that transaction's reference entries back with it.
- **`onStaged` is left unset in this part.** It is in the constructor because the maintainer is the one place that knows what was staged and in what order, and `feat-blob-pins-follow-sql-commits` wires it there; do not add any other reporting path.

**Call sites in `update()`**, each immediately beside the index call it mirrors and in the same order, one `if (this.blobReferences)` per site:

| Site | Index call | Reference call |
|---|---|---|
| `applyUniqueEvictions`, per evicted row | `deleteIndexEntries(row, pk)` | `stageDelete(row, pk)` |
| INSERT OR REPLACE over an occupied key | `updateIndexEntries(existingRow, values, insertKey, insertKey)` | `stageUpdate(existingRow, values, insertKey, insertKey)` |
| INSERT at a clear key | `insertIndexEntries(values, insertKey)` | `stageInsert(values, insertKey)` |
| UPDATE, displacing move | `deleteIndexEntries(pkMove.row, newKey)` | `stageDelete(pkMove.row, newKey)` |
| UPDATE | `updateIndexEntries(oldRow, values, oldKey, newKey)` | `stageUpdate(oldRow, values, oldKey, newKey)` |
| DELETE (cascade child deletes included: they reach this arm) | `deleteIndexEntries(oldRow, deleteKey)` | `stageDelete(oldRow, deleteKey)` |

The displacing move's order matters for the reason it matters for indexes: when the displaced row and the moving row hold the same reference in the same column they stage the identical key, and remove-then-add leaves it present. Arms that return without staging — IGNORE, a blocked or swallowed decision, a `constraint` result, `removedEarlierInTransaction` — stage nothing here either.

## Registering the tree in the scope registry

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-scope-registration.ts`:

```ts
/** One network as the registry needs it: the transactor key and its transactor. */
export interface NetworkBinding {
	/** The transactor key, `${transactor}:${keyNetwork}`. */
	readonly key: string;
	readonly transactor: ITransactor;
}

export class BlobScopeRegistration {
	/**
	 * True once `scope` is confirmed in `network`'s registry in this process: read first
	 * (`BlobScopeRegistry.enumerate`, certain and listing it), otherwise registered
	 * (`BlobScopeRegistry.register`, which opens, stages and syncs in one step). False, logged
	 * `blob:scope-register-failed`, when that register throws. Memoized per (network key, scope)
	 * once true, so the steady state costs nothing, and concurrent calls for one pair share one promise.
	 */
	ensure(network: NetworkBinding, scope: BlobScope): Promise<boolean>;
	/** `BlobScopeRegistry.unregister`; idempotent. Clears the memo for the pair. */
	unregister(network: NetworkBinding, scope: BlobScope): Promise<void>;
	/** Forget every memo, for a factory clearing its transactors. */
	clear(): void;
}
```

No registry handle is held and no new tree-opening method is needed: db-core's three entry points — `enumerate`, `register` and `unregister` — each open their own handle. They therefore open it without the factory's `treeOptions`, which is correct rather than merely tolerable, and the module's doc comment must say so, so nobody "fixes" it later: the sealed-segment refusal callback matters only for a tree that joins an offline queue entry, and the registry is always synced on its own at DDL time, which `assertNoQueuedEntries` has already gated; the adopted-commits callback matters only for a materialized view's source collections, which the registry is never one of.

On `CollectionFactory`, two additions and one widening:

```ts
/** The transactor and key of `options`'s network, with no blob service resolved. */
async networkBinding(options: ParsedOptimysticOptions): Promise<NetworkBinding>;
/** This factory's blob-scope registrations, keyed by (transactor key, scope). */
readonly blobScopes: BlobScopeRegistration;
```

`networkBinding` is `{ key: this.getTransactorKey(options), transactor: await this.getOrCreateTransactor(options) }`. Change `BlobBackend` to `extends NetworkBinding` so one shape serves both, and let `resolveBlobBackend` keep building it as it does. `clearCache` and `dispose` call `this.blobScopes.clear()` beside the existing `blobBackends.clear()`: a memo for a key whose transactor has been replaced would otherwise skip a registration that is genuinely needed. Deliberately **not** `getBlobBackend`: the DDL paths need no blob service, and for a `network` transactor resolving one would build or reuse a libp2p node for a statement that only has to write one registry entry.

**When the registry is written.**

- `OptimysticModule.create`, for a table whose `tableSchema` has a `blobref` column: `ensure` before the batch checkpoint that initializes the table, and throw `QuereusError(…, StatusCode.ERROR)` with the failure attached as `cause` when it answers false. Registering first is harmless if the create then fails: an id whose tree was never written reads as an empty tree, certainly. A re-declare of an existing table pays one registry read the first time in a process and nothing after.
- `OptimysticModule.addColumn`, when the added column is `blobref` and the table had none: `ensure` before `alterCatalogOnly`, same refusal. ADD COLUMN already refuses a DEFAULT, so no stored row gains a reference and nothing is backfilled. `attachBlobReferences` then gives the instance its maintainer.
- `apply schema` reaches those two arms unchanged. The registration syncs immediately rather than joining the batch; a failed batch leaves an idempotent, harmless registry entry.
- **Hydrate does not register.** docs/internals.md §A first touch writes only what the table owes forbids a first touch writing what the table does not owe, and a hydrated table's tree was registered by whichever machine created it. The remaining gap — a tree missing from the registry, because it was created by a build that registered nothing, or dropped on another machine while this one kept writing — is closed where it matters: `feat-blob-pins-follow-sql-commits` calls `ensure` before any announcement names the tree as its scope, and does not announce until it answers true. A receiver only ever reads a scope it was told about, so a reference committed before its tree is registered is harmless until the announcement, and nothing is announced into an unregistered tree. This departs on purpose from the backlog ticket's "hydration checks the registry and registers a missing tree", which would cost a registry read per table at every start.
- `OptimysticModule.destroy`, for a table whose engine catalog entry (`db.schemaManager.findTable`) has a `blobref` column: after the gravestone write, `unregister`. A failure is logged and does not stop the drop, like the gravestone failure beside it — the blobs that tree lists then stay referenced, which keeps bytes rather than losing them. The reference tree itself stays in storage, as a dropped table's index trees do. Add a `NOTE:` (accepted tradeoff) at that site: a table re-created over the same URI re-registers the old tree, whose leftover entries then keep their blobs alive; it never loses one; revisit if reclaiming those matters. docs/blobs.md §Lifetime already records this under *Accepted limits*.

## The two refusals that keep the tree describing real rows

Both are the maintainer's preconditions, so they land with it.

- **DROP COLUMN of a `blobref` column.** `columnDropBlockers` in `packages/quereus-plugin-optimystic/src/schema/catalog-only-change.ts` gains the blocker `it holds blob references`, judged by `isBlobRefColumn`. Widen `ColumnKeyedParts.columns` so each column also carries the two optional fields that rule reads — they are exactly `BlobRefColumnShape`, so reuse that type rather than restating it. Widening the one shared rule is what makes the refusal reach all of its callers with no further edits: `OptimysticVirtualTable.columnDropBlockers` and `OptimysticModule.dropColumn` over the engine's entry (`logicalType`), `classifyColumnChange` over a freshly read record (`affinity`), and `withoutColumn` in `packages/quereus-plugin-optimystic/src/schema/schema-manager.ts`. Why: dropping the column would leave entries no row implies, keeping their blobs alive for ever.
- **A re-declare that changes a column to or from `blobref`, or omits a persisted `blobref` column.** Refused where the existing "cannot re-declare without an indexed column" rule is enforced, but on the **write and dry-run** paths only. Add a private `SchemaManager.mergeForWrite(candidate, persisted)` that applies the new rule and then calls `mergePersistedSchemas`, and route `storeStoredSchema`, `storeInBatch` and `mergeWithPersisted` through it. `viewOverRecord` keeps calling `mergePersistedSchemas` directly, and that distinction is the point: a machine that hydrated before another machine's `add column … blobref` legitimately works from its own narrower column list and writes nothing, so refusing there would make the table unopenable on exactly the machine that is behaving correctly. Two messages, in the shape of the index one beside them:
  - `Cannot re-declare column '<c>' of table '<table>' to or from blobref: its rows' blob references would need rewriting. Drop and re-create the table.`
  - `Cannot re-declare table '<table>' without column '<c>': it holds blob references. Drop and re-create the table.`

  Thrown as a plain `Error`, as the index refusal is, and surfaced by `doInitialize`'s wrap with its other re-declare refusals. Why: turning a `text` column that holds references into `blobref` over existing rows would give committed references with no entries, and turning one the other way would leave entries for a column nothing maintains.

## Edge cases & interactions

How each is covered is named; most are inspection, for the reason the *Tests* section gives.

- **Every row-change shape** — insert; delete; cascade delete; secondary-UNIQUE REPLACE eviction; insert or replace over an occupied key; same-key update changing the value, keeping it, setting NULL, setting from NULL; primary-key move; displacing move onto an occupied key — on a table with a composite primary key whose columns are not the leading ones and two `blobref` columns, with one row holding the same reference in both. *Test, table-driven, against an oracle over the rows.*
- **Racing writers.** Two handles change one row's reference: the main tree's `unchanged` guard refuses the loser at commit and its reference entries leave with the rest of its transaction. Two handles insert different rows referencing one blob: both land, with one entry each, since the two referrers differ. *Test.*
- **Validation.** A session-mode transaction that inserts, updates and deletes `blobref` rows passes `createQuereusValidator`'s re-execution: the operations hash covers the reference tree's operations, so a mismatch would reject. *Test.* (That no blob service is touched there belongs to `feat-blob-pins-follow-sql-commits`.)
- **Rollback and savepoint rollback.** The reference tree is a dirty tree and a registered collection, so a rollback restores it from the snapshot `markDirty` captured and a legacy savepoint rollback restores it with the others. Session mode has the existing statement-savepoint gap — the `savepoints` note in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts`, backlog `debt-optimystic-session-mode-statement-savepoint-gap` — for it exactly as for index trees. *Inspection.*
- **Offline.** A queued entry carries the reference tree's segment; a restart restores it through `collectionsOfTable`, which lists it. A `blobref` table's DDL is gated by queued entries that wrote its reference tree, through that same registry. *Inspection — the existing restore and gate specs cover the mechanism and the tree is one more collection.*
- **Two tables over one URI** share one reference tree and one scope, as they share index trees. The referrer carries the primary key and column, not the table name, so two tables sharing a collection must also share the row shape — which `assertRedeclarationKeepsShape` already requires. *Inspection.*
- **A table declared at another table's `<uri>/blobrefs`** adopts that tree as its main tree, uncaught, as `<uri>/index/<name>` already is. *Inspection; recorded as the `NOTE:` at `openBlobReferenceTree`.*
- **An index on a `blobref` column** works as a text index; nothing here interacts. *Inspection.*
- **Column positions after a drop of another column** are rebuilt in `republishColumnLayout`. *Inspection, plus one case of the shapes test that drops an unrelated column mid-way and writes again.*
- **A second `blobref` column added by ADD COLUMN** extends the maintainer's column list through `republishColumnLayout`, and `attachBlobReferences` no-ops because the maintainer already exists. *Inspection.*
- **A registry write that fails at create** throws out of `create`; nothing else is written, and the instance is dropped from the module's cache by the existing `catch`. *Inspection.*
- **An unregister that fails at drop** is logged; the drop proceeds. *Inspection.*
- **A dropped then re-created table** counts its old entries again — the accepted-tradeoff `NOTE:` at `destroy`. *Inspection.*
- **A table with no `blobref` column** opens, registers and marks nothing, and pays one `isBlobRefColumn` pass over its columns per initialization. *Inspection.*
