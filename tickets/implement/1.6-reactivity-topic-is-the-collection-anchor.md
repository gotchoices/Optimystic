# Reactivity: the topic is the collection anchor; only the root moves

Third of three tickets for the maintainer's decision of 2026-10-02 (third paragraph; the text and its reading are in `cohort-topic-a-topics-root-can-move`). After this ticket a collection's reactivity topic is

```
topicId(C)        = H(utf8(C.collectionId) ‖ "reactivity")       (stable for the collection's life)
coord_0           = H(tailId)                                      (root: the tail block's storage group; moves on rotation)
coord_d(P)        = H(d ‖ prefix(H(P), d·log₂F) ‖ topicId)         (d ≥ 1; never moves)
```

and `H(tailId ‖ "reactivity")` is retired. A rotation is "same topic, the root moved". The prerequisites made the substrate accept a moving root (`moveRoot`, the tree tier on a registration handle, tier-1 engines that follow the root key, `findHolder` that picks the newer record) and re-keyed every per-root structure in reactivity by the root's tail; this ticket switches the identity and reworks the subscriber side around it.

## Why

Every tier's address includes the topic id, and the topic id changes every 32 log entries (`EntriesPerBlock` in `packages/db-core/src/chain/chain.ts`), so each rotation moves the whole tree and every subscriber re-registers. Derived, not measured: at 10 commits/s and 10,000 subscribers that is about 3,000 registrations per second against a new root that admits `cap_promote_fast` = 32 per window, and a live node learns of a rotation only from the watch service's 30 s tail check, so on a busy collection network watch degrades to 30 s polling.

## db-core

- `packages/db-core/src/reactivity/topic-anchor.ts`: add `reactivityCollectionTopicId(collectionId: Uint8Array, hash?: IRingHash): Uint8Array` = `H(collectionId ‖ "reactivity")`, where `collectionId` is the same bytes a notification's `collectionId` encodes (`reactivityCollectionIdBytes` in `packages/db-p2p/src/reactivity/topic-bytes.ts`, the UTF-8 of the id). Delete `reactivityTopicId`, `ReactivityTopicAnchor` and `createReactivityTopicAnchor` (only the spec uses the latter two). Rewrite the module doc: topic stable per collection; root at the tail (`reactivityRootCoord`, unchanged).
- `packages/db-core/src/reactivity/rotation.ts`: a rotation moves the root, not the topic. `ReRegistrationPlan` drops `newTopicId` (`newTailId` is the new root key); `planReRegistration` / `planReRegistrationWave` no longer hash. `TailDrainGateInit` takes the collection's `topicId` (base64url) for the redirect instead of deriving one from the new tail; `RotationRedirectV1.newTopicId` stays on the wire and now carries that unchanged topic (no wire change; a receiver acts on `newTailId`). Rewrite the module doc.
- `packages/db-core/src/reactivity/config.ts`: `BLOCK_FILL_SIZE_DEFAULT` is 64 but a log block holds `EntriesPerBlock` = 32 entries; set it from `EntriesPerBlock` (import the module directly, not a barrel — `docs/internals.md` § Common Pitfalls 6). The tracker is signal-only on a live node; update any spec that pinned 64 through the default.

## db-p2p

**Topic derivation.** `reactivityNotificationTopicId(n)` in `packages/db-p2p/src/reactivity/forwarder-host.ts` becomes `reactivityCollectionTopicId(b64urlToBytes(n.collectionId))`. It is the one place both roles compute a notification's topic (forwarder ingest after the previous ticket, inbound routing, `deliverLocal`). Origination passes the collection's topic to `markRotated` for the drain gate's redirect. `pushStateInit`'s `topicId` follows from the helper.

**Subscriber registry** (`packages/db-p2p/src/reactivity/subscriber-registry.ts`): keyed by the collection topic. One handler per collection subscription for its whole life; rewrite the module doc ("registering and unregistering them here as a collection's tail moves" no longer happens).

**Subscription manager** (`packages/db-p2p/src/reactivity/subscription-manager.ts`): one manager per collection subscription for its life, following the tail.

- `topicId = reactivityCollectionTopicId(collectionId)`, fixed. The option `tailIdAtAttach` becomes `tail` (the tail at construction); the manager holds the **latest tail it has followed** (`get tail()`), which is what `resume` sends as `latestKnownTailId`, what `detectRotation` compares against, and what the recover transports target. The register's `appPayload.tailIdAtAttach` is the tail at that registration.
- `register()` registers under `rootKey = this.tail`.
- New `followTail(tail: Uint8Array): Promise<boolean>`, true iff a registration landed:
  - record `tail` as the latest tail;
  - no registration yet → `register()`;
  - registration at the root (`handle.treeTier === 0`) whose `rootKey` is not `tail` → `register()` again (the service displaces the old registration, which expires by TTL at the old root; see the `startRenewal` NOTE) and adopt the new handle; a failure throws and leaves the old registration renewing, and the same condition re-fires on the next call;
  - registration below the root (`treeTier ≥ 1`) → `service.moveRoot(handle, tail)`; nothing is sent, nothing re-registers.
- The rotation notice path (`surfaceRotation`) is unchanged in shape: it hands the host a plan whose `newTailId` the watch then follows. For a registration below the root following is free, so the jitter delays only a recover-target update; acceptable, no special case.
- Recover transports target the root group of the **current** tail: `Libp2pReactivityRecoverTransport.backfillTransport` / `resumeTransport` (`packages/db-p2p/src/reactivity/recover-transport.ts`) take a tail getter (`() => Uint8Array`) instead of fixed bytes, resolved per request.

**Collection watch** (`packages/db-p2p/src/reactivity/collection-watch.ts`): a subscription owns one manager and one registry handler, both created at its first attach (handler registered under the collection topic before the first `register`) and released at close. `Attachment`, `attached`/`arriving` and the handler hand-over in `moveTo` go away; `moveTo` becomes a follow: build the manager if absent, `await manager.followTail(tailBytes)`, `rebaseline(lastRevision)`, return whether a registration landed (the caller's re-check after a landed registration stays). `isAttached` = the manager holds a registration. `closeSubscription` unregisters the handler and withdraws the manager's registration; a registration that lands after close is withdrawn when it lands, as today. `reRegister(plan)` follows `plan.newTailId`. Keep the `NOTE:` on `reRegister` (a timer for a successor the log already left moves the registration back for one round), reworded for roots.

**Node wiring** (`packages/db-p2p/src/libp2p-node-base.ts`): follow the signature changes; update the comments that explain the encoding loop (`reactivityNotificationTopicId(n) = reactivityTopicId(...)`, "`oldTopicId` is byte-identical…").

**Harnesses.** `packages/db-p2p/src/testing/reactivity-mesh-harness.ts` derives one topic per collection; its rotation step moves the root key and leaves the topic (`c.topicId = reactivityTopicId(newTailId)` goes). `setupRootPlacedTopic` in `packages/db-p2p/src/testing/cohort-topic-mesh-harness.ts` keeps working for a topic whose root key changes between calls.

## Tests

The specs listed in `files:` reference the retired derivation and adapt. New cases, each pinning the ticket's headline behaviour or a branch that was not reachable before:

- **A rotation re-registers only a registration at the root** (`packages/db-p2p/test/reactivity/collection-watch.spec.ts`, fake service): after a tail move, a subscription whose handle says `treeTier: 0` calls `register` with the new root key; one whose handle says `treeTier: 1` calls `moveRoot` and not `register`. One case per branch.
- **Two roots of one topic on one machine** (`packages/db-p2p/test/reactivity/forwarder-host.spec.ts`): ingests under tails A and B of one collection keep separate push states, `directSubscribers` is asked with each root's tail, and `markRotated(A)` followed by the drain releases only A's state. This was unrepresentable while the topic was tail-derived.
- **Tier-1 registrations survive a rotation, mock tier** (`packages/db-p2p/test/reactivity/mesh-tail-rotation.spec.ts`): with a promotion cap low enough that some subscribers land at tier 1 (the live-tier specs lower `capPromote` the same way), a rotation moves the root-direct subscribers to the new root and sends no register frame for the tier-1 subscribers. Rework the spec's existing cases from "new topic per tail" to "same topic, new root"; this is the end-to-end evidence for the decision.
- `topic-anchor.spec.ts`: the collection topic is a function of the collection id alone (two tails of one collection, same topic; two collections, different topics) and is domain-separated from `reactivityRootCoord`. Replace the retired-function cases; do not keep cases for deleted code.

The integration specs (`substrate-real-libp2p.integration.spec.ts` reactivity and watch cases, `network-change-notification.integration.spec.ts` in quereus-plugin-optimystic) derive their topic from the collection and must pass unchanged in what they assert.

## Edge cases & interactions

- **Root-direct subscriber whose re-registration at the new root is deferred** (the new root is a cold engine; backlog `feat-a-new-topic-admits-its-first-registration-without-a-second-ask`): the old registration keeps renewing at the old root, which receives no commits; the next tick retries. Verified by the follow rule (handle root key ≠ tail re-fires).
- **Stale tree tier on the handle** after a renewal failover re-walk (the service does not track a relookup's landing; arm appended to `bug-a-participant-told-its-registration-is-unknown-never-registers-again`): a handle that says 0 but is at tier 1 re-registers needlessly; one that says ≥ 1 but re-walked to the root stays at that root until the next relookup. `moveRoot` keeps any later re-walk pointed at the current root. Record as a `NOTE:` in `followTail`.
- **A tier-1 registration and the old root.** A subscriber at tier 1 whose registration predates several rotations re-walks (on failover) with the current root key because the watch calls `moveRoot` on each follow. By inspection.
- **Close during a follow's in-flight re-registration**: the service displaced nothing yet (it replaces only on success); close withdraws the live (old) registration, the landing one is withdrawn on landing. A tombstone resolving to the newer record on a machine holding both is harmless while closing.
- **Two notifications for one revision** cannot come from two roots: a revision is announced by the group that applied its tail, once. The subscriber's `(collectionId, revision)` dedupe covers retransmits as before.
- **Self as subscriber and root member.** `deliverLocal` now routes by collection topic; a node that is a root member and a subscriber of the same collection still delivers once (subscriber dedupe), and a node serving two roots of one collection routes both to the same manager. Covered by the two-roots forwarder case.
- **Mixed versions.** A subscriber on an older build registers under the tail-derived topic and is never matched; the protocol break was accepted with the decision (§ Origination point already says any anchor change is one). Not tested.
- **Matchmaking topics** share engines' stores with reactivity on a node; `reactivityDirectSubscribers` still filters by `appState` kind. By inspection.
