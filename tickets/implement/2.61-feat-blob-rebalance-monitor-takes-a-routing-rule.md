# The rebalance monitor takes a routing rule

`RebalanceMonitor` in `packages/db-p2p/src/cluster/rebalance-monitor.ts` compares, for every id in its tracked set, the cohort `findCluster` assembles now with the cohort it remembered, and reports `gained`, `lost` and `grown`. docs/blobs.md §Placement, copying and durability requires the same comparison for blobs this node holds, "by giving it the routing key rule rather than a second copy of its logic". The monitor already works on plain string ids and takes its tracked set by injection (`RebalanceMonitorDeps.trackedBlocks`); what ties it to blocks is one call, `routingKeyForBlock(blockId)` in `cohortFor`, and its module-level logger. This ticket makes both injectable, so `feat-a-referenced-blob-is-copied-to-its-cohort` can build a second instance over held blob references.

It also adds one opt-in capability the blob reaction needs and blocks do not use: re-reporting a `lost` id whose release the reaction could not confirm (*Retained lost ids*, below).

## Design

Add two optional fields to `RebalanceMonitorDeps`; every default is today's behaviour.

```ts
import type { RoutingKey } from '@optimystic/db-core'

export interface RebalanceMonitorDeps {
	// ...existing fields unchanged. `trackedBlocks` keeps its name (the existing spec and node wiring use
	// it); its doc gains one sentence: the ids are whatever `routingKeyOf` places — block ids by default.
	/**
	 * The routing key an id is placed by. Default `routingKeyForBlock`. A blob instance passes
	 * `id => routingKeyForBlob(id as BlobRef)` (`packages/db-core/src/network/routing-key.ts`); the ids it
	 * tracks are blob reference strings, which `routingKeyForBlob` takes as a branded `BlobRef`.
	 */
	routingKeyOf?: (id: string) => RoutingKey
	/** Logger sub-namespace. Default `'rebalance-monitor'`. The blob instance passes `'blob:copy'`. */
	logName?: string
}
```

- `cohortFor(id)` computes `const key = (this.deps.routingKeyOf ?? routingKeyForBlock)(id)` and is otherwise unchanged (both the `findCluster` path and the FRET `assembleCohort(await hashKey(key), …)` fallback use `key`).
- The module-level `const log = createLogger('rebalance-monitor')` becomes an instance field `private readonly log: ReturnType<typeof createLogger>`, assigned in the constructor from `deps.logName ?? 'rebalance-monitor'`; every `log(...)` in the class becomes `this.log(...)` (including the ones inside timer callbacks and `.catch` arrows — they are arrow functions, so `this` is the instance). Nothing at module level logs, so nothing else moves.
- No method is renamed. `trackBlock`, `untrackBlock`, `recordBlockHolders`, `getTrackedBlockCount` keep their names and take whatever ids the instance tracks; renaming them would churn the node wiring and every rebalance spec for no behaviour.

### Retained lost ids

Today an id is reported `lost` once, on the check where `isResponsible` is false and `wasResponsible` is true; that check stores `emptyGrowthState(false)`, so the next check does not report it again. The blob reaction must keep its `responsible` hold until it confirms enough current members hold the blob, and must retry that confirmation on later checks. Add:

```ts
/**
 * The reaction could not confirm a `lost` id's release: report it in `lost` again (with its current
 * `newOwners`) on the next check while it stays tracked and this node stays outside its cohort. One call
 * buys one re-report; a reaction that still cannot confirm calls it again. Arms the re-check timer, as
 * outstanding growth does, so the re-report happens on a quiet network. Ignored for an id with no state
 * (never checked, or untracked since) or one this node is responsible for again.
 */
retainLost(id: string): void
```

- `BlockGrowthState` gains `releasePending: boolean` — false from `emptyGrowthState` and from `carryGrowthState`.
- `retainLost` sets it on the id's `responsibilitySnapshot` state when the state exists and `responsible` is false, then calls `updateRecheckTimer()`. The call is needed: the reaction is asynchronous and calls `retainLost` after the check that reported the id has already evaluated the timer and found nothing outstanding.
- In `performRebalanceCheck`, the `lost` branch condition becomes `!isResponsible && (wasResponsible || prior?.releasePending === true)` (still the `else if` after the `gained` branch). The new non-responsible state is still `emptyGrowthState(false)`, so `releasePending` is cleared by every check that re-reports; the id is reported again only if the reaction calls `retainLost` again for this report. A regain (`isResponsible`) builds the state through `carryGrowthState`, which clears it.
- `hasOutstandingGrowthWork` also returns true while any tracked id's state is `!responsible && releasePending`. Rename it `hasOutstandingWork` (private; its doc comment says growth or a retained release) so the name stays honest.
- A cohort lookup that fails leaves the state untouched (existing behaviour), so `releasePending` survives to the next check, which the lookup-failure count already re-arms the timer for.
- The block wiring in `libp2p-node-base.ts` does not call `retainLost`; block behaviour is unchanged. Whether blocks should is backlog `bug-a-block-kept-after-a-failed-handoff-is-never-offered-again`, which already names this mechanism as its likely fix — do not wire it here.

## Edge cases & interactions

- **Block behaviour unchanged.** Defaults reproduce today's key rule and log namespace; `retainLost` is never called for blocks, so `releasePending` is always false on a block monitor and the widened condition reduces to today's. Verified by the existing rebalance suites passing unedited: `rebalance-monitor.spec.ts`, `rebalance-reaction.spec.ts`, `rebalance-committed-holders.spec.ts`, `rebalance-push-holders.spec.ts`, `rebalance-monitor-node-wiring.spec.ts`, `cohort-growth-heals-single-holder.spec.ts`, `unify-tracked-block-set.spec.ts`.
- **A retained id regained before the next check.** `isResponsible` true: `wasResponsible` is false (state `responsible: false`), so it is reported `gained` as any regain is, its state is built through `carryGrowthState` (`releasePending` false, whole cohort grown), not reported lost. Inspection.
- **A retained id untracked.** `untrackBlock` deletes the snapshot state; `retainLost` afterwards finds no state and is ignored; `hasOutstandingWork` skips untracked ids. Inspection.
- **`retainLost` on an id never reported lost** (state responsible, or no state): ignored. Inspection.
- **`retainLost` called twice before the next check:** idempotent flag. Inspection.
- **`retainLost` while stopped:** `updateRecheckTimer` already returns without arming when `!running`; the flag is kept and the next check after a restart honours it. Inspection.
- **Throttle.** A re-reported lost id costs one cohort lookup per check, which every tracked id already costs; `minRebalanceIntervalMs` bounds how often the re-check timer's `maybeRebalance` runs. Inspection.
- **Partition.** A suppressed check returns before the loop, so `releasePending` stays set and the id is re-reported on the first unsuppressed check. Inspection.
- **`lost` ∩ `grown` stays impossible**: the growth arm is still gated on `isResponsible`. Inspection.

## Tests

One new case in `packages/db-p2p/test/rebalance-monitor.spec.ts`, built like the existing "detects lost responsibility" case (`describe('checkNow')`): track an id with self in its cohort, `checkNow`; move self out of the cohort, `checkNow` → `lost` contains the id; call `monitor.retainLost(id)`; `checkNow` → `lost` contains the id again with the current `newOwners`; `checkNow` again without calling `retainLost` → the result is `null` (nothing reported). `checkNow` returns the event without running handlers, so the test calls `retainLost` directly rather than from an `onRebalance` handler. This pins the one new branch.

No test for `routingKeyOf` or `logName`: they are pass-throughs, and the blob ticket's reaction tests exercise an instance built with them. No test for the timer arming: it reuses `updateRecheckTimer`, which the "growth re-check timer" cases already pin.
