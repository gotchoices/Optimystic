# Why

Release goal (2026-09-14): every core low-node-count scenario works, React Native included. On a phone, the two-machine case always runs over a circuit relay. The inventory of relay coverage found: address-propagation and inbound-stream specs, long-lived relay and hole-punching specs that only run under `RUN_LONG_TESTS=1` (no script sets it), and `multi-coordinator-write-relay.integration.spec.ts`, which proves one 2-of-2 write whose second promise crosses the relay. Nothing reads data back across the relay, writes from both sides, replicates, or survives a drop or restart. Relay-limited connections have produced defects here before (inbound streams refused on limited connections; a relay unable to dial its own reservation holders), each found downstream rather than by this suite.

# The scenario

Topology, reused from `multi-coordinator-write-relay.integration.spec.ts`: one plain libp2p relay node (identify plus circuit-relay-v2, no Optimystic protocols, via `spawnPlainRelayNode`), and two storage nodes A and B that are phone-shaped: WebSockets and circuit-relay transports only, listening only on `<relay>/p2p-circuit`, so every A↔B stream rides the relay. Each has a stable key and its own `MemoryRawStorage`. Default `clusterSize` with `clusterPolicy: { repairCorroborationClusterSize: 2 }`, the documented two-machine configuration, as in the prereq spec.

Assert up front that the A↔B connection is limited (`isLimitedConnection`), so a regression that sneaks a direct transport in cannot turn this into a TCP test that still passes.

Phases, mirroring the direct-TCP lifecycle spec where the relay makes a difference:

1. **Both up through the relay.** A writes rows; B reads them. B writes rows; A reads them.
2. **Replication, not read-through.** Wait (bounded) until each holds the other's blocks locally; prove it by stopping the writer and reading on the other.
3. **One drops.** Stop B. Write on A; record acknowledged or refused. Restart B (it must re-reserve on the relay and re-listen on its circuit address; `waitForCircuitListen`). Invariant: every acknowledged write is readable on both once both are back.
4. **Both restart.** Stop A and B; start both over their storage, through the relay. Every acknowledged row readable on each; one more write from each crosses the relay and is readable on the other.
5. **The relay restarts.** Stop and restart the relay (same key and address if the utility allows; otherwise document why not). A and B re-reserve; a write from each is readable on the other. A phone pair whose relay pod restarts must recover without the app restarting.

Gate on `OPTIMYSTIC_INTEGRATION=1`. Target runtime near two minutes; state the measured time.

# Edge cases & interactions

- **A failure here is a finding, not a flaky test.** Same rule as the prereq: never loosen, over-retry or skip; reduce to the smallest failing phase, keep asserting the correct behaviour, file a `fix/` ticket with log evidence, and say so prominently in the handoff.
- **No layout-dependent self-skips.** The relay is not an Optimystic node, so it never competes for a cohort slot (the header of the existing relay spec explains the failure that caused). Do not add a precondition that can `this.skip()`.
- **Hole punching must stay off.** Loopback blocks DCUtR's direct upgrade today, which is what keeps streams on the relay. Assert limitedness at each phase that opens new streams, not only once, so a future transport change cannot silently upgrade the connection mid-spec.
- **Relay reservation limits.** Default circuit-relay-v2 reservations have duration and data limits. If a phase trips one, that is a real phone-pair finding: record which limit, and whether production relay configuration in docs or in `../sereus` sets it differently. Do not raise the limit in the test to make it pass without saying so.
- **Reconnection after a peer restart.** B restarting gets a new circuit address only if its reservation changes; A must find B again through the peer store and the relay. If A never reconnects on its own, that is a finding, not a helper to add in the test.
- **Teardown** of all three nodes in `after`, including on mid-phase failure.
- **Repeat before handing off.** Five or more consecutive runs, pass count reported.
