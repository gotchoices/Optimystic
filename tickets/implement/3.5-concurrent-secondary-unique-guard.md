# Refuse a concurrent insert whose UNIQUE column value a rival writer already committed

## Why the primary-key guard does not cover this

Secondary unique constraints are enforced only by the vtab's pre-stage probe (`resolveSecondaryUniqueDecision` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`), a range scan over the unique column's index tree — evaluated against the writer's own snapshot, so two concurrent writers both pass, same as the PK probe.

The exact-key `absent` guard from the prerequisite ticket cannot catch this at replay: index tree keys are framed composites `indexKey ‖ primaryKey` (see `findByIndex` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts`), so two rows sharing a unique value but differing in PK occupy *different* tree keys. Uniqueness on the index tree is a property of the framed **prefix**, not of one key.

## Design

Wire up the `absentRange` guard the prerequisite ticket defined on `TreeReplaceAction` entries:

- Handler semantics (in `Tree`'s `replace` handler): the range `[indexKey, indexKey + KEY_PREFIX_END)` — the same framed-prefix range `findByIndexIn` scans — must contain **no entry other than this action's own key**. Self-exclusion matters: the entry being staged lands inside its own range. On violation throw the structured error from the prerequisite ticket (or a sibling carrying the colliding range), never a silent skip.
- The range scan runs over the `Atomic` store the handler is handed, via a throwaway `BTree` exactly as the handler already builds one — `range(...)` and early-exit on first foreign hit. Cost is one short descent per guarded entry, only on unique indexes.
- Vtab wiring (`insertIndexEntries` / `updateIndexEntries` paths in `index-manager.ts`, driven from `optimystic-module.ts`): attach `absentRange` to entries staged into trees of UNIQUE indexes, keyed off the same resolved conflict action as the PK guard — ABORT/FAIL/ROLLBACK guard, REPLACE unguarded (the eviction already ran), IGNORE per the prerequisite ticket's `keepExisting` disposition and its documented index anomaly.
- Error mapping: the bridge's commit-boundary catch must render `uniqueConstraintMessage(uc.columns)` — naming the violated UNIQUE constraint's columns, not the PK — so the structured error needs to carry which index tree (collection id) it fired in; the bridge resolves collection id → index → column indices.

## Edge cases

- **Excluded keys on UPDATE**: the sequential probe excludes the row being updated (and a displaced row on a REPLACE move) — the replay guard's self-exclusion covers the first; verify the displacing-move shape has no guarded index entry that would spuriously refuse.
- **Delete-then-reinsert of a unique value**: winner deletes its row (and index entry) — the loser's replay sees the prefix empty and proceeds. Must not be refused; test it.
- **Both writers same PK and same unique value**: PK guard fires first (main tree replays first only by ordering accident — do not depend on order; either refusal is correct, both render as UNIQUE messages).
- **Multi-collection**: an index-tree refusal must fail the whole transaction exactly as a main-tree one does — same propagation paths, but the throw now originates in an index collection's replay; test in both legacy and session modes.
