# A node deletes what it released

## Why

The ring handoff already does the hard, careful half of this. A node that narrows its range advertises the new ring, confirms every block of the shed range is replicated to at least the replication floor of post-move holders, and only then releases it (`docs/arachnode-ring-handoff.md` § Part 2). The confirmed-rebalance release does the same for a block whose cohort it has left.

Then nothing happens. Both release paths add the block id to a plain `Set<string>` in the node factory called `gcEligible`, under a comment that says what it is for and admits what it is not:

> NOTE: no sweep consumes this set yet; it is the coordinated eligibility handoff the sweep ticket will read. Until then it grows unbounded — bound it when the sweep lands.

The comment names a ticket, `st-storage-sweep-archival-and-capacity-estimate`, which does not exist. So a node that sheds its way from ring 3 to ring 6 has given seven eighths of its data to other machines and still holds all of it, and the set remembering which seven eighths is in memory, so a restart loses even the knowledge. That is the one reason shedding frees nothing today, and it is what makes an allotment unenforceable: a node can narrow its responsibility as far as the ring model goes and its disk never gets emptier.

## What to build

### The eligibility is written down

`gcEligible` becomes a durable ledger, `ReleasedBlockLedger`, over the node's key-value store under a new `NODE_KV_NAMESPACES` prefix (`optimystic-released/`), one entry per released block id carrying the moment of release and which path released it (a ring shift's Phase C, or a confirmed rebalance release). Durable for two reasons, and both matter: a restart must not lose the knowledge that bytes are free to go, and an entry is what makes a half-finished delete resumable — the previous ticket's `deleteBlock` is ordered and idempotent precisely so that this entry can be removed *after* the delete rather than before.

The ledger is the only way a block becomes sweepable. Nothing else may add to it, and in particular the sweep never derives eligibility for itself from the node's own ring or partition: a block that merely *looks* outside this node's current slice may be one whose handoff rolled back, and is still being served. **Only the release that followed a confirmation may write an entry.**

### The sweep

`ReleasedBlockSweep` reads the ledger and, for each entry, acquires the block's write latch and calls `BlockStorage.deleteBlock`, then removes the entry. It runs:

- when a release has just written entries (so an ordinary shed frees its bytes promptly),
- when the storage pressure reading is at `shedding` or above (from the previous ticket's `read()`), so a node under pressure sweeps whatever a previous run left behind,
- once shortly after start-up, which is what finishes the deletes a crash interrupted.

Single-flight with the shape the repository already uses for passes of this kind (`BlobCacheBudget`'s one-run-plus-one-queued-follow-on, or `BlobReclaimPass`'s "joins the pass in flight"): a sweep must never overlap itself, and a request arriving during a run must not be dropped. Bounded per run — a cap on the blocks one run deletes, so a node that released tens of thousands does not hold the event loop for one pass; the remainder is taken by the next run, and the ledger is what makes that safe. One log line per run naming how many entries it found, deleted and left, and one per block at debug.

It also requests the **existing** blob piece sweep once per run that deleted anything (`LocalBlobService.sweep`, already the mechanism that removes pieces no remaining hold needs). Nothing new is built for the blob half of deleting: the holds are released by the blob reclaim pass and by the cohort reaction, and the piece sweep already follows.

### The invariant, stated and pinned

> **A block's bytes are deleted only after a release that confirmed at least the replication floor of other serving holders hold a current replica of it.**

Everything above is in service of that sentence. It is the reason the ledger is written only by the two confirmed-release callbacks, the reason the sweep derives nothing itself, and the reason the entry survives a restart rather than being re-derived from the node's partition. The parent ticket asks for it to be pinned with a test that a sweep never deletes a block the confirm step did not count, and that is the one test here that earns its keep (below).

### Bounding the ledger

An entry whose delete keeps failing — a storage fault on one block — must not make every later sweep retry it for ever at the head of the queue. Keep a per-entry attempt count, log each failure, and after a small bound (three, matching `SlotHoldAfterLosses`' style of small explicit constant) stop retrying that entry while leaving it in the ledger, so an operator can still see the block was released and not deleted. Nothing silently drops an entry: that would leak the bytes *and* the record of them.

## Edge cases & interactions

- **A rolled-back shift.** A Phase-B failure rolls back to the old ring and releases nothing, so no entry is written and nothing is swept. The one thing that must not creep in is a sweep that reads the node's current partition — which, mid-shift, is the *target* ring — and deletes from it. Verified by the invariant test.
- **A block retained after a failed handoff.** `bug-a-block-kept-after-a-failed-handoff-is-never-offered-again` (backlog) says a lost block whose confirmation failed is never offered again, so it is never released and so never swept: it stays on disk, served, for ever. That is the safe direction and this ticket does not change it — but it does mean the sweep cannot be relied on to free a node whose handoffs are failing. Say so in the docs; do not work around it here.
- **A released block that is pushed back.** A peer may push the same block to this node again (the receiver is idempotent and three producers may push the same block). If the push lands between the release and the sweep, the sweep deletes a replica the node has just accepted. Harmless — the node is not responsible for it and the cohort holds it to the floor — but the ledger entry must be **removed when a block is written again**, or the node will keep deleting a block it keeps re-accepting in a loop. The cheapest correct point is the delete itself: under the block's latch, re-read the metadata and skip (and drop the entry) if the block's `latest` is newer than the moment the entry recorded. Verified by inspection; this is the one ordering subtlety in the sweep.
- **A block released twice.** The second release finds an entry already there and leaves it (or refreshes its release moment, which the point above needs anyway). Idempotent by construction.
- **A restart mid-delete.** Covered by the previous ticket's ordering: metadata is gone, content may remain, the entry is still there, and the next sweep's `deleteBlock` finishes it. This is the whole reason the entry outlives the delete.
- **A client node.** A client stores no blocks for anyone and never sheds a range, so its ledger is always empty and the sweep is inert. Build it anyway on both roles rather than gating it, for the reason the blob reclaim pass runs on a client: one wiring, one rule.
- **Arachnode disabled or no FRET.** Both release callbacks live inside the arachnode block, so no entries are written — but the sweep must still run, to finish entries a *previous* run of that node (with FRET up) left in the ledger. Wire the sweep outside the arachnode gate; wire the writers inside it.
- **The key-value store shared with a host's journal.** The new prefix must be added to `NODE_KV_NAMESPACES`, or a file-backed store sharing a base path with block storage will have `FileBatchBackend.listBlockIds` walk the ledger's keys as if they were block directories.
- **Concurrency with a commit.** The latch is what serializes it; a commit holding the latch simply makes the sweep wait, and a commit that lands first is caught by the newer-`latest` check above.

## Tests

Two specs, both over the sweep with stubbed storage:

- **A sweep never deletes a block the confirm step did not count.** Drive a move-out whose Phase B fails for one of two shed blocks, let the handoff roll back, then run the sweep: nothing is deleted. Then drive one that confirms both, and only those two are deleted. This is the invariant the parent ticket names, over the branching that decides it, and it is the test that would catch the whole class of "the sweep derived eligibility itself".
- **A sweep finishes a delete a restart interrupted.** An entry in the ledger for a block whose metadata is already gone but whose revisions remain is deleted and its entry removed. This pins the resumability contract across the ledger and `deleteBlock` together, which neither ticket's own tests cover alone.

No test for the per-run cap, the attempt bound, or the pressure trigger: a cap and a counter are arithmetic, and the trigger is wiring.
