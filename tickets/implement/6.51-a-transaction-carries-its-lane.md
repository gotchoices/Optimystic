# A transaction carries its lane

First of four implement tickets from the plan of the same name, the second foundation of the partition-healing program after the three Stage 1 HLC tickets (`the-hlc-clock-and-its-persistence-port`, `every-log-entry-and-transaction-carries-its-hlc`, `a-node-observes-the-hlcs-it-reads-and-stores`). This ticket is db-core's half: the vocabulary, the collection-level declaration, and the field on every carrier a write travels in. The SQL layer's classification is `a-table-declares-its-profile-and-the-engine-classifies-each-statement`, the member-side check is `a-member-checks-the-lane-a-transaction-claims`, and the operator-visible reporting is `the-solo-lines-and-the-queued-status-name-the-lane`. **No admission rule changes in any of the four.** The solo path, the offline queue and the conflict replay all behave exactly as today; the replay-mode stage (backlog `feat-replay-mode-collections-merge-divergent-histories`) is what consumes the field.

## The vocabulary

A write's **lane** says how its conflicts with other machines' concurrent writes are decided:

- `serializable` — the quorum lane. The write needs the collection's cohort to agree, and the revision order decides every conflict (today's behaviour for every write). The tree entry guards (`TreeEntryGuard` in `packages/db-core/src/collections/tree/struct.ts`) are this lane's conflict rule: they re-make every uniqueness and lost-update decision deterministically on replay.
- `convergent` — the merge lane. The write may be committed by one machine without first agreeing with the others, and merged into their concurrent writes later, because the invariants it is responsible for survive a merge (an append to an append-only set, an increment of an unbounded counter, a last-writer-wins field). The collection's merge declaration (below) is this lane's conflict rule.

This is the result of the invariant-confluence literature (Bailis et al.; Li et al.'s RedBlue consistency): convergence is a property of an **operation**, never of a system. **Idempotence is not the criterion**, and the type's doc comment must say so because it is the mistake a later reader makes: setting a column to a value is idempotent and still needs a tie-break under concurrency, while an increment is not idempotent and merges fine.

The type lives in a new module, `packages/db-core/src/lane/lane.ts`, beside `hlc/`, exported from the package index:

```ts
export type Lane = 'serializable' | 'convergent';
/** The lane of a write made of several parts: `serializable` if any part is. */
export function stricterLane(lanes: Iterable<Lane>): Lane;
```

The SQL-level **profile** of a table (`strong` / `replay-permitted`, the ceiling an application sets per table) is the next ticket's concern. db-core has no profile concept: at this layer a collection with no merge declaration is `strong`, and a declaration is the opt-in.

## The merge declaration replaces `filterConflict`

`CollectionInitOptions.filterConflict` is today untyped as to intent, offered every open-segment action against every stranger's entry, and installed by nobody (`Tree` and `Diary` install none; the `NOTE:` at `Collection.unstage` records what a replacement-answering hook would need). Give it a declared role by grouping it under a typed declaration:

```ts
/** The convergent lane's conflict rule for a collection. A collection with no declaration is
 *  strong: every action is serializable and nothing merges. */
export type ConvergentMerge<TAction> = {
	/** The lane of one of this collection's actions when no engine has classified it (a bare
	 *  `Collection.sync`, an offline-queue entry sealed without a classification). */
	laneOf(action: Action<TAction>): Lane;
	/** Today's `filterConflict` contract, verbatim (keep the same instance, answer a replacement,
	 *  or `undefined` to drop), now offered only convergent actions: rebase one over a stranger's
	 *  committed actions. Optional, since a convergent action that touches no shared block (a diary
	 *  append) has nothing to rebase. */
	filterConflict?(action: Action<TAction>, committed: Action<TAction>[]): Action<TAction> | undefined;
};
CollectionInitOptions.merge?: ConvergentMerge<TAction>;
```

- `doFilterConflict` consults `merge.filterConflict` only for an action whose `merge.laneOf` is `convergent`; a serializable action is kept as-is, since its guards decide on replay. With no declaration every action is kept, which is today's default. Nothing installs a hook, so nothing observable changes; the `NOTE:` at `unstage` stays as it is.
- `Diary` declares `merge: { laneOf: () => 'convergent' }`: append-only is the first natural convergent case (the I-confluence table in `docs/partition-healing.md` §I-Confluence Classification: append-only merges as union). Its handler touches no block, so no `filterConflict`.
- `Tree` declares none. `TreeCollectionOptions` (today `Pick<CollectionInitOptions, 'onSealedRefused'>`) widens to carry `merge` too, passed through `buildInit`, so a raw tree user can declare one; the SQL vtab never will, because it classifies per statement and passes the lane on each write (next ticket). The per-field last-writer-wins merge for a tree entry is a SQL-layer declaration evaluated by the replay stage, not a db-core hook.
- Add `Collection.laneOf(actions: readonly Action<TAction>[]): Lane` (public, pure): `stricterLane` over `merge.laneOf` of each action, `serializable` without a declaration or for an empty list. Used by `syncInternal`, by `OfflineQueue.enqueue`'s default, and by the next ticket's tests.

## Where the lane rides

Mirror the HLC's carriers one for one (the completed ticket `every-log-entry-and-transaction-carries-its-hlc` is the template; read its review findings first). The rule it followed holds here: the lane is minted **once per write**, beside the action id, timestamp and HLC, and re-sent unchanged by every retry, so two attempts at one `(action id, revision)` append byte-identical entries (`docs/internals.md` §*A write's log append is a fixed function of the write and the revision it is requesting*).

## Edge cases & interactions

- **A retry re-sends the lane it was minted with.** By inspection of the three minting sites (`syncInternal`, `TransactionSession.commit`, `OfflineQueue.enqueue`) and the whole-transform-set assertion in `retry-resends-identical-transforms.spec.ts`, which fails for any per-attempt value.
- **A multi-collection write has one lane on every participant's entry.** By construction: `WriteContext` is built once per attempt from the transaction, and `EntryCommit` once per entry from the queue.
- **The sync option wins over the declaration; the declaration wins over nothing.** A test (below).
- **A sealed segment's lane is fixed at enqueue.** A later change to the collection's declaration, or to the SQL table's tags, does not reclassify a queued entry: its lane is what was true of the statements when the application made them, and it is journaled. By inspection; the SQL consequence is in the next ticket.
- **A stored entry from before the field.** `laneOf` answers `serializable`; the `packages/upgrade-check` fixtures must pass unchanged, which is the evidence. A direct read of `ActionEntry.lane` on a legacy entry meets `undefined`, the same tripwire the HLC review recorded at `hlcOf`; record it at `laneOf` the same way.
- **An older writer's pend or commit carries no lane field.** Every reader of `PendRequest.lane` and `CommitRequest.lane` treats absence as "not stated", never as a lane. Nothing reads them in this ticket.
- **The signature version bump.** A `v2` writer's signature fails verification on a `v3` verifier; accepted on the `v2` precedent, since no deployment wires a `ClientSignatureVerifier` (backlog `feat-no-deployment-validates-transactions-at-pend`). Update the precedent note at `CLIENT_SIG_VERSION`.
- **Gating `filterConflict` on the lane changes no behaviour.** No collection installs a hook. By inspection; say so in `collections.md`.
- **An invalidation or checkpoint entry.** Carries no lane; `laneOf` is for action entries only. A dispute's compensating entry (`applyInvalidation` in db-p2p) needs no change.
- **A partial commit, a torn action, a resumed head attempt.** None of these mint anything: the lane travels inside the retained attempt's log entry and on `WriteContext` and `EntryCommit`, so every re-drive and re-send carries the same value. By inspection of `completeOwnEntry`, `resumedAttempt` and `commitEntry`.

## Tests that pay for themselves

One case, in `packages/db-core/test/retry-resends-identical-transforms.spec.ts` or the collection spec beside the HLC's cases, pinning the branching of the lane's source over `TestTransactor`: a `Diary.append` entry reads `convergent` through `laneOf`; a `Tree.replace` entry reads `serializable`; a `Collection.sync({ lane: 'convergent' })` on a tree reads `convergent`. Three assertions, one behaviour (which source decides). Extend the existing fixed-value fixtures in the log, transaction and signature specs with the field; add no test for the wire plumbing, the journal field or the status field.
