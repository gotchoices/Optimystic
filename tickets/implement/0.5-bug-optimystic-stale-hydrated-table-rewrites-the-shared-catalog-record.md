description: When one machine changes a shared table's stored description, another machine that loaded the old description earlier can write that old copy back over the change, or bring back a table that was dropped, the first time it touches the table; the change is silently undone until someone re-applies it.

## The defect

`hydrate` copies every catalog record into the engine's in-memory catalog. The first statement that touches a hydrated table builds a table instance from that engine entry, so `declaredColumns` is true and `doInitialize` takes the "local declaration wins" arm: it compares the engine's copy with the record and, on any difference, writes the engine's copy. That arm exists for `create table`, whose declaration is meant to win. A copy of a record is not a declaration. On a machine that hydrated before another machine's change, it puts the older description back.

**When it fires.** The plain sequence (A changes `t`; B, already hydrated, runs `select * from t`) does NOT lose the change on today's code, because hydrate fills the `schemaCache` that `doInitialize` then reads, so B compares its copy with the same copy. It fires once something has refreshed B's cache with the newer record. Every mutating path does (`getSchemaFresh`, `persistTags`, a catalog batch's overlay).

Each of these was run at HEAD with two sessions over one `MemoryRawStorage` (harness: `openSession` in `test/alter-table-arms.spec.ts`). A created `t` with `constraint pos check (a > 0)`, B hydrated, and A then ran `alter table main.t add constraint small check (a < 100)`. A third session then hydrated to read the record:

| B's steps | The record afterwards |
|---|---|
| `alter table main.t set tags (x = 1)`, then `select * from main.t` | `small` is gone |
| `alter table main.t drop constraint pos`, then `select * from main.t` | `small` is gone |
| `apply schema` of its old shape plus `index t_c on t (c)` | `small` is gone |

Two more outcomes at HEAD, from scenarios of their own:

- **The `apply schema` arm:** A declares `pos check (a > 0)`; B hydrates; A applies `pos check (a >= 0)`; B applies that plus `constraint one_c unique (c)`, which the module refuses. The record ends with no `pos` at all. Quereus's check of stored rows against the re-added CHECK builds B's instance inside the batch.
- **An unreadable table:** A adds column `y` and `create index t_y on main.t (y)`; B, whose cache holds that record, first-touches `t` and every statement fails with `Cannot re-declare table 't' without column 'y'`, because the union with the record cannot resolve `t_y` against B's columns.

## The fix

**1. A table built from a catalog entry never writes on its first initialize.** Add one instance field saying the instance owes the catalog its description, and branch on it in `doInitialize`. Keep `declaredColumns` as it is. It answers a different question (does the engine's entry carry columns), and the provisional-to-full rerun relies on it.

The field is true for an instance built by `create()`, after `markSchemaUnpersisted`, and for an instance built for a table a failed batch owes but which had no instance then. The last case is the one the `endSchemaBatch` doc comment describes: a tag change on a hydrated table no statement has touched. Without it that change is lost, so `endSchemaBatch` needs a set of table keys it consults in `instantiateTable`.

When the instance owes nothing and a live record or a gravestone exists, the instance adopts a view and writes nothing. When neither exists, the existing arm still runs, with its storage-adoption guard and its write. Read the gravestone only when `persistedSchema` is undefined, so the common path pays no extra catalog read.

**2. The view is the engine's columns plus the record's indexes, not the record.** The original ticket's first idea was the load arm: adopt the record and rebuild the instance's schema from it. That does not work. Quereus plans column positions from its own catalog entry, and the statement that triggers the first touch is already planned, so an instance whose columns differ from that entry hands back rows the plan misreads. Refreshing the engine's entry cannot help the statement in progress either. So the instance keeps the engine's columns, which is what it did before this fix on every path, and only stops writing.

```ts
viewOverRecord(candidate: StoredTableSchema, persisted: StoredTableSchema | undefined): StoredTableSchema {
	if (!persisted) return candidate;
	const names = new Set(candidate.columns.map(col => col.name.toLowerCase()));
	const record = toPersistedSchema(persisted);
	const indexes = record.indexes.filter(idx => idx.columns.every(col => names.has(col.name.toLowerCase())));
	return toStoredSchema(mergePersistedSchemas(toPersistedSchema(candidate), { ...record, indexes }));
}
```

Leaving out indexes over columns this machine does not know is what cures the unreadable table. Such an index goes unmaintained on this machine, which belongs to `bug-optimystic-a-machine-keeps-acting-on-a-table-description-another-machine-replaced`. Say so in a `NOTE:` there.

Steps 1 and 2 were prototyped, and the plugin's `yarn test` passed with them (1216 passing, 14 pending). All the scenarios above then kept A's change, as did the same first touch after A's drop check, set tags, add column, drop column or create index, and after A's drop of the table. The prototype's parameter threading was throwaway and has been removed, so write the field properly. The steps below were not prototyped.

**3. Stop marking a table `written` for a first-touch initialize.** `alterCatalogOnly` passes `outcome === 'owned' || initializesHere` to `underBatchCheckpoint`. After step 1 an initialize stages a write only when the instance owes one, so test that instead. Otherwise a failed commit marks a table that wrote nothing.

**4. `addIndex` must not write a stale description (first-touch `create index`).** Both of these are at this one site, and both ran on HEAD.

- **It brings back a dropped table.** A drops `t`; B runs `create index t_a on main.t (a)`. `getSchemaFresh` falls back to the cached copy when the live record is gone, and `storeStoredSchema` then writes a live record over the gravestone. A third session finds `t` again. Refuse instead, the way `saveCatalogOnly` refuses a missing record, when `getDroppedSchemaRecord` finds a gravestone. Check that this does not break the undo of a `DROP TABLE`, which goes through `create` first and so finds a live record.
- **It can index the wrong column.** A runs `drop column a` on `(id, a, c, d)`; B runs `create index t_c on main.t (c)`. `indexSchemaToStored` gives positions in B's column list and `addIndex` appends them to the record's column list, so a third session reads `t_c` as an index on `d`. This fix makes that path easier to reach, since a first touch no longer puts B's columns back first. Translate B's positions to names through `this.tableSchema`, then resolve the names against the record, and refuse when a name is not there. `IndexPredicate.compile` in the same method compiles the predicate against the record's columns, so check it against the same rule.

**5. A failed apply's unwind must clear the marks it made unnecessary.** When a catalog commit is refused, `endSchemaBatch` marks every `written` table unpersisted. Quereus then unwinds the apply in a second batch, so B's engine is back on its old description while the mark still rewrites it over the record on the next touch. Marks exist for the data-destroying case, where nothing is unwound (see the `endSchemaBatch` doc comment). Steps 1 to 4 leave this path open.

The recommended shape: carry the refused batch's marked tables beside `adoptedByRefusedBatch` into the next `beginSchemaBatch`, and when that batch commits, clear the mark on the tables its undo DDL reached. It inherits the limitation in the `NOTE:` on `adoptedByRefusedBatch`, that a hook cannot tell an unwind from the next apply, so extend that note. If a data-destroying apply is followed by another that touches the same table, that table's mark clears early: the record stays without the first apply's change until the next `apply schema` re-emits it. A second refusal leaves the marks standing, and the older description can still be written back. Record both as accepted.

This step comes from reading the code and has not been run. Reproduce it first with the failing-commit harness in `test/schema-batch.spec.ts`: A applies; B applies the same with a tag or CHECK change and a refused catalog commit; B then touches `t`; a third session must find A's record. `bug-optimystic-failed-apply-on-a-second-machine-reverts-saved-tags` works beside this in `followTableTags` and reads `adoptedByRefusedBatch`, so keep that field's meaning intact or update that ticket.

**One behaviour goes away on purpose.** A hydrated table's first touch no longer rewrites a record that differs only in form (out of canonical order, or written before uniqueness metadata existed). Those upgrade rewrites still happen on a re-declaration. A failed tag save outside a batch is also no longer repaired by a later first touch, only by the next DDL, as the note on `followTableTags` already describes.

## Tests

Add one spec, `test/stale-hydrated-table.spec.ts`, using the two-session harness, with one test per behaviour:

- B's cache was refreshed by its own `set tags`, then B selects: A's CHECK stays in the record.
- B first-touches a table with an index on a column it does not know: the read works and the record is unchanged.
- A dropped the table, B runs `create index`: refused, and a third session does not find the table.
- A dropped a column, B runs `create index` on a later column: the record names the column B asked for, or the statement is refused.
- A hydrated table with an owed record and no instance: the first touch still writes it.
