# Cached blob copies stay within a budget

`docs/blobs.md` §Holds lists four reasons a machine keeps a blob. One of them, `cached`, is taken by every fetch — a read that had to pull pieces from another machine takes it before it decides which pieces are missing (`LocalBlobService.holdCached`) — and nothing releases it, so a machine that reads many files grows its storage without bound. §Lifetime says what should happen: "Cached blobs are evicted under a budget, least recently read first. This is local and needs no agreement."

This ticket builds that. A byte budget covers the blobs held *only* for reads. It is enforced after a read or fetch that pulled anything, and once when the node has built its blob service, by removing the `cached` hold from the least recently read such blobs until the total is within the budget, and then running the piece sweep once. A blob with a read or fetch in flight is never evicted, and the sweep leaves the pieces of a blob in use alone — both through the use count `feat-a-blob-being-read-is-not-swept` added.

It is independent of the reference pass (`feat-unreferenced-blobs-are-reclaimed`), which releases `responsible` and `owed` holds. That ticket reuses the `blob:reclaim` log namespace this one creates.

## Design

### What counts against the budget

A **cache-only blob** is one whose record holds `cached` and nothing else — no pin, no `owed`, no `responsible`. Only cache-only blobs are counted, and only they are evicted. A blob that carries another hold stays whatever its cache status, so counting it would make the budget evict blobs it *can* remove to pay for one it cannot.

A blob's bytes are its record's `size`, which is known once the root piece is here; a record with no size counts 0. Pieces shared between blobs are counted once per blob, which over-counts and so evicts sooner — the direction that uses less storage, which is the point of a budget.

Rejected: measuring with the piece store's `bytesUsed`, which counts every blob's pieces whether held for reads or not; and walking each blob's tree for the pieces actually present, which costs one piece-store read per piece per enforcement. The record's `size` is already there.

### The door into the records (`LocalBlobService`)

The budget must not reach the records through a second `BlobRecordStore` over the same `IKVStore`: two instances keep separate per-ref queues, and a write that bypassed `LocalBlobService.changeRecord` would also bypass the sweep gate and `PieceSweeper.noteRecordChange`, which is what keeps a running sweep from deleting a concurrent write's pieces. So the budget gets a door, declared beside `BlobOwedRecords` in `local-blob-service.ts` and for the same stated reason:

```ts
/** One cache-only blob as the budget sees it. */
export interface CachedBlob {
	readonly ref: BlobRef;
	/** The record's `size`; 0 when it has none yet. */
	readonly bytes: number;
	/** The record's `lastReadAt`; 0 when it has never been read here. */
	readonly lastReadAt: number;
}

/** What the cache budget needs of this node's blob records and pieces; `LocalBlobService` is it. */
export interface BlobCacheRecords {
	/** Every blob whose record holds `cached` and no other hold. A record that does not decode is
	 *  logged (`record:unreadable`) and skipped, as `responsibleRefs` does, so one unreadable record
	 *  cannot fail an enforcement — and a blob whose record cannot be read is never evicted. */
	cachedBlobs(): Promise<CachedBlob[]>;
	/** Remove `ref`'s `cached` hold, but only while that is still its only hold; `true` when it did.
	 *  A record left with no hold is deleted and its pieces left for the sweep. Not flushed: a hold
	 *  removal a crash undoes is made again by the next enforcement. */
	releaseCached(ref: BlobRef): Promise<boolean>;
	/** `LocalBlobService.inUse`, from `feat-a-blob-being-read-is-not-swept`. */
	inUse(ref: BlobRef): boolean;
	/** `LocalBlobService.sweep`. */
	sweep(): Promise<BlobSweepResult>;
}
```

`cachedBlobs` enumerates `BlobRecordStore.listRefs()` and reads each record, as `responsibleRefs` and `listPins` already do. `releaseCached` goes through `changeRecord` with a change function that is itself the condition — it sees the record as it is at its turn in the per-ref queue, so a blob that gained a pin, `owed` or `responsible` hold between the enumeration and the write keeps **every** hold and is reported `false`:

```ts
function recordAfterCacheEviction(current: BlobRecord | undefined): BlobRecord | undefined {
	if (current === undefined || !cacheOnly(current)) return current;	// unchanged: nothing is written
	return { ...current, holds: current.holds.filter(hold => hold.kind !== 'cached') };	// no holds left → deleted
}
```

Dropping the only hold leaves an empty `holds`, which `BlobRecordStore.update` deletes, and `changeRecord` then schedules a sweep of its own — harmless beside the one the budget runs.

### Module `packages/db-p2p/src/blob/cache-budget.ts`

```ts
/** 256 MiB: a phone's worth. A host with room sets more through `NodeOptions.blobs.cacheBudgetBytes`. */
export const DEFAULT_BLOB_CACHE_BUDGET_BYTES = 256 * 1024 * 1024;

/** Which of `blobs` to evict to bring their total within `budgetBytes`, least recently read first
 *  (ties by `ref` ascending, so the choice is deterministic), skipping any `inUse` reports true for.
 *  Pure: it reads nothing and writes nothing. */
export function chooseEvictions(blobs: readonly CachedBlob[], budgetBytes: number, inUse: (ref: BlobRef) => boolean): {
	readonly evict: readonly BlobRef[];
	/** The total of every blob given, before eviction. */
	readonly cachedBytes: number;
	readonly skippedInUse: number;
};

export interface BlobCacheBudgetDeps {
	readonly records: BlobCacheRecords;
	readonly budgetBytes: number;
	readonly log: Logger;
}

export interface CacheEnforcement {
	readonly cachedBytes: number;
	readonly evicted: readonly BlobRef[];
	readonly skippedInUse: number;
}

export class BlobCacheBudget {
	constructor(deps: BlobCacheBudgetDeps);
	/** Enumerate the cache-only records, choose, remove each chosen blob's `cached` hold, then sweep
	 *  once if anything was evicted. Single-flight. */
	enforce(): Promise<CacheEnforcement>;
	/** `void enforce()` with a logged catch, for the call sites that must not wait. */
	request(): void;
	/** Refuse further runs and wait for the one in flight. */
	stop(): Promise<void>;
}
```

`chooseEvictions` sorts by `lastReadAt` ascending then `ref` ascending, and walks that order while `cachedBytes - evictedBytes > budgetBytes`: a blob `inUse` reports true for is skipped and counted in `skippedInUse`; any other is added to `evict` and its bytes to `evictedBytes`. A budget it cannot reach because the rest are in use is left over budget until the next enforcement — nothing retries on a timer. A cache-only record with no size contributes 0 bytes and is evicted like any other once the walk reaches it; do **not** add a guard that stops at a zero-byte blob, since dropping a blob nobody has read that this node knows nothing about is free and correct.

`enforce` then, for each chosen ref **in the chosen order**, checks `records.inUse(ref)` again immediately before the write — so a read that started after `chooseEvictions` ran keeps its blob — and calls `records.releaseCached(ref)`. `evicted` carries only the refs whose removal returned `true`. If `evicted` is non-empty it awaits `records.sweep()` once at the end, and reports. A `releaseCached` or `sweep` that throws rejects `enforce`; `request`'s catch logs it.

**Single-flight**, in the shape `PieceSweeper.run` and the drains already use, but with one queued follow-on rather than joining the run in flight: the enumeration a run in flight already did cannot see the read that triggered this call, so joining it would under-enforce. A call while a run is in flight returns a promise for one more run **after** it, and several such calls share that one follow-on run. `stop` sets a flag that makes `enforce` resolve with the empty enforcement rather than starting, and awaits the run in flight; it is what the node's stop wrapper calls.

### Triggers

- **A read or fetch that pulled something.** In `NodeBlobService`: at the end of `readFetching` (in the `finally`, after the read's use is released) when it started a session, and when a session `startSession` started settles and its use is released. Both, because either one alone leaves a gap: at the end of the read the session's tail may still hold a use, so the blob just read is skipped as in use; and at the session's settle the read may still be consuming. Single-flight collapses the pair into one run plus one follow-on. A read that fetched nothing starts no session, adds nothing to the cache, and triggers nothing.
- **Node start.** Once, right after the budget is built, so a budget lowered across a restart is applied to what the last run cached.

No timer: the cache grows only through reads that fetch, and each of those triggers an enforcement.

`NodeBlobService` takes the trigger as an optional callback (`requestCacheEnforcement?: () => void`), not the budget itself — the budget needs the local service, which `NodeBlobService` is built over, and a service built without one (every existing test of it) must keep working unchanged.

### Node option and wiring

`NodeOptions.blobs.cacheBudgetBytes?: number`, added to the existing `blobs` option object in `packages/db-p2p/src/libp2p-node-base.ts`; default `DEFAULT_BLOB_CACHE_BUDGET_BYTES`. `0` keeps no cache-only blob beyond those being read.

A value that is not a finite integer of at least 0 throws a `RangeError` naming the option (`blobs.cacheBudgetBytes must be an integer number of bytes at or above 0, got …`, the shape `durability-window.ts` and `cohort-topic/host.ts` already use). Validate it **where the option is read, beside `const blobHold` at `libp2p-node-base.ts:1251`** — that is before `createLibp2p` and `node.start()`, so a misconfigured host gets the error instead of a started node that has to roll back.

Build the `BlobCacheBudget` beside `NodeBlobService` (`libp2p-node-base.ts:~1746`), over the `LocalBlobService` built at line 1248, with `createLogger('blob:reclaim', node.peerId.toString())`. Pass its `request` to `NodeBlobService` as `requestCacheEnforcement`, call `budget.request()` once after it is built, install a `node.stop` wrapper calling `budget.stop()` — installed **after** the blob service's wrapper at line 1733, so it runs **before** it, and no enforcement writes records or sweeps after the blob service has stopped — and expose it as `(node as any).blobCacheBudget` for diagnostics, as `blobCopyDrain` and `owedBlobLedger` already are.

Export `cache-budget.js` from `packages/db-p2p/src/index.ts`, in blob order beside the others.

### Logging

`createLogger('blob:reclaim', node.peerId.toString())` — namespace `optimystic:db-p2p:blob:reclaim`, which `feat-unreferenced-blobs-are-reclaimed` will share:

- `cache:enforced cachedBytes=%d budget=%d evicted=%d skippedInUse=%d` — once per enforcement that found the cache over budget. Nothing is logged by an enforcement with nothing to do, which is most of them.
- `cache:evicted ref=%s bytes=%d lastReadAt=%d` — once per hold actually removed.
- `cache:enforce-failed - %e` — `request`'s catch (`%e` is this package's error formatter, `packages/db-p2p/src/logger.ts`).

## Edge cases & interactions

- **A read in progress.** Never chosen by `chooseEvictions`, and `inUse` is checked again immediately before the write. **Test.**
- **A read starting after the hold was removed.** The sweep takes in-use refs as roots (`feat-a-blob-being-read-is-not-swept`) and deletes none of that blob's present pieces, so the read finishes. By inspection of the sweep's roots.
- **A blob with another hold.** Neither counted nor evicted; its `cached` hold stays, and it counts again once the other hold goes. **Test** (inside the eviction test, as the fifth blob).
- **A hold gained between the enumeration and the write.** The conditional change function keeps every hold and reports `false`, so the blob is not in `evicted`. By inspection of `recordAfterCacheEviction`.
- **A read's `lastReadAt` write racing an eviction.** Both go through the same per-ref queue in the one `BlobRecordStore`; `recordAfterRead` returns `undefined` unchanged for a record that is already gone, so a read cannot resurrect an evicted record. By inspection.
- **A partially fetched cache-only blob.** Counted at its record `size` — more than it stores — and evictable like any other; a later read fetches again. By inspection.
- **A cache-only record with no `size`.** Counts 0 and is still evicted when the walk reaches it. By inspection.
- **Equal last-read times.** Ordered by reference ascending, so the choice is deterministic. By inspection of `chooseEvictions`.
- **Budget 0.** Every cache-only blob not in use is evicted after each fetching read. By inspection; it is also what the in-use test uses.
- **A budget the evictions cannot reach.** Every remaining cache-only blob is in use; the cache stays over budget until the next enforcement. By inspection.
- **Concurrent enforcements.** Single-flight with one queued follow-on, so a trigger during a run gets a run that can see what it cached. By inspection.
- **An unreadable record.** Skipped by `cachedBlobs`, so that blob is never evicted and its bytes are not counted. By inspection.
- **Node stopping mid-enforcement.** `budget.stop()` runs before the blob service's stop, so no record write or sweep is started after it; a run already in flight is awaited. By inspection of the wrapper order.
- **A crash during enforcement.** A hold removal whose write did not reach disk is made again by the next enforcement; a deleted record whose pieces were not swept leaves orphans the next sweep removes. Nothing a remaining hold names is lost. By inspection.
- **Large record counts.** Each enforcement reads every blob record. `NOTE:` at `enforce`: if record counts reach the tens of thousands and enforcement shows up in a profile, keep a running total of cache-only bytes in the record store — the same tripwire `responsibleRefs` and `listPins` already carry.

## Tests

`packages/db-p2p/test/blob-cache-budget.spec.ts` (new), over a real `LocalBlobService` on a `MemoryPieceStore` and a `MemoryKVStore`, with `setTimer: () => () => undefined` so the only sweeps are the budget's. A cache-only blob is made the way the service's own paths make one — `put` (pinned `default`), then add a `cached` hold and a `lastReadAt` through a `BlobRecordStore` over the same `MemoryKVStore` (as `local-blob-service.spec.ts` already does), then `unpin(ref, DEFAULT_BLOB_OWNER)`.

- **The least recently read cache-only blobs are evicted until the cache is within budget.** Four cache-only blobs of 300 KiB with `lastReadAt` 1, 2, 3 and 4, plus one blob holding both `cached` and a pin with `lastReadAt` 0; budget 700 KiB. `enforce()` reports `cachedBytes` of 4 × 307200 and evicts exactly the blobs read at 1 and 2: their records are gone and their pieces are not in the piece store after the sweep, while the other two cache-only blobs and the pinned one still read back whole with `from: 'here'`. One test for three pieces of the specification that cannot be checked apart — the ordering, the cache-only rule (the pinned blob is neither counted nor evicted, though it is the least recently read of all), and the hand-off to the sweep.
- **A blob being read is not evicted, and is evicted once the read ends.** Two cache-only blobs, budget 0 (so the ordering is not what is under test here). Open a `read` of the least recently read one and take its first chunk; `enforce()` evicts the other, reports `skippedInUse: 1`, and leaves the first blob's record and pieces. Finish the read; `enforce()` then evicts it too. Pins the skip, the `skippedInUse` count and that the skip is not permanent.
