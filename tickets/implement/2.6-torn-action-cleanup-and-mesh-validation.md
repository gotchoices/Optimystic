# Torn action, part 3 of 3: cleanup, tripwire, mesh coverage, end-to-end validation

Split from `torn-action-must-recognize-its-own-durable-work` after a budget stop. Parts 1
(`torn-action-pend-tier-carve-out`) and 2 (`torn-action-own-entry-consumption`) carry the
behavioral fixes; this part finishes the ticket. Context: a write that commits some blocks and
loses the race on the rest (a "torn action") used to wedge its own retries forever (part 1) or
duplicate its entry (part 2).

## Rejected direction (carried over — do not reorder the commit)

`NetworkTransactor.commit` commits header (when not in `blockIds`) → tail → sweep. Tail-first is
a load-bearing protocol guarantee: `Collection.bootstrapContext` documents "The tail is always
committed first (commit protocol guarantee), so it's readable with context=undefined" — context
bootstrap is what makes pending non-tail blocks visible to a chain walk. Tail-last would let a
committed header point at a never-committed tail (a dangling pointer, strictly worse than an
orphan block). Do not change the order.

## Tasks

**Dead clause** — in `NetworkTransactor.commit` (network-transactor.ts:708-711):

```ts
const remainingBlocks = request.blockIds.filter(bid =>
	bid !== request.tailId &&
	!(request.headerId && bid === request.headerId && !request.blockIds.includes(request.headerId))
);
```

The second clause is dead: `bid` is drawn from `request.blockIds`, so
`blockIds.includes(headerId)` is necessarily true whenever `bid === headerId`. Reduce to
`bid !== request.tailId` and comment plainly: the header commits FIRST (line 694) only when it
is NOT in `blockIds`; when it is, it commits here as part of the non-tail sweep. Also state that
the header→tail→sweep order is deliberate and why contested-first was rejected (see above). No
behavioral change.

**Rewrite the stale NOTE** at network-transactor.ts:726-733: it currently defers the
durable-orphan class to `tickets/fix/2-all-lose-conflict-race-wedges-concurrent-first-appends`,
which is this work. Once parts 1 and 2 are on the branch, rewrite it to describe the resolved
state: the writer's re-pend recognizes its own durable revision (StorageRepo.pend /
validatePendOperations own-action carve-out) and its retry consumes its own committed log entry
(Collection.updateInternal), so the refusal here no longer wedges or duplicates — it still must
NOT be softened into a tolerance.

**Tripwire NOTE (not a ticket)** — at the `ConflictRaceLostError` → StaleFailure conversion in
`CoordinatorRepo.pend`'s catch (coordinator-repo.ts:1428): with three or more contenders the
members' votes can split so EVERY contender is told it lost the race (an all-lose round);
nobody wins and each writer retries. After parts 1–2 that costs one retry cycle instead of
wedging, and convergence rests on the aged retry priority (`clampPriority(consecutiveFailures)`
carried on the re-pend) plus jittered backoff separating contenders next round. Record exactly
that, greppable `NOTE:` tag.

**Mesh spec extension** — add to `concurrent-diary-append-acknowledgement.spec.ts` the
tail-committed-then-later-block-conflict shape, asserting no duplicate entry. Deterministic
recipe (verified against the harness types): wrap node 0's transactor from
`buildNetworkTransactors(mesh)`; on the FIRST commit call, delegate to the inner transactor with
`blockIds` reduced to `[tailId, headerId].filter(id => request.blockIds.includes(id))` plus the
header-first behavior the inner transactor already applies, then return
`{ success: false, conflict: true, reason: 'stale commit: injected later-block conflict after tail commit' }`;
subsequent calls delegate untouched. Append one entry through a Diary over the wrapper; assert
the entry appears exactly once in that diary AND exactly once in a Diary opened over another
node's unwrapped transactor (convergence). The writer's cancel after the injected failure is
safe: committed blocks' pending records were already promoted, and cancel on an absent record is
a no-op.
