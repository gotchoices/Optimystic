# A file-store checkpoint stalls the commit that triggers it

Reported as GitHub #62 (Sereus; optimystic 1.27.0, `FileRawStorage`, solo node, Node 24.11, macOS 15 on Intel). Follow-on to GitHub #37, which added the write-ahead log and its checkpoint. The reporter's table, 120 sequential transactions of 50 rows:

| setup | median commit | slow commits (wall s / CPU s) |
|---|---|---|
| `MemoryRawStorage` | 30 ms | none |
| file, default `checkpointBytes` (16 MiB) | 133 ms | #43 5.1 / 0.31, then #44–55 at 1.0–1.8 each; #82 6.7 / 0.35; #119 6.1 / 0.30 |
| file, `checkpointBytes` 4 MiB | 96 ms | 13 commits of 0.9–2.1 s |
| file, `checkpointBytes` 64 MiB | 125 ms | no big stall, but every commit from #101 takes 1.0–1.7 s at under 0.11 s CPU |

## What the fix stage found

**On Windows there is no stall.** A script driving `StorageRepo.pend` + `commit` over `FileRawStorage` (20 new 8 KB blocks per transaction, `checkpointBytes` 4 MiB) checkpointed every 9 transactions; each checkpoint synced 720 files (directories are skipped on win32) in 53–95 ms, and the transaction that triggered it took 110–250 ms against neighbours of 80–170 ms. With `checkpointBytes` at 1000 MiB, 150 transactions showed no latency growth with the log (median 178 ms, flat from transaction 30 to 150). Nothing in the commit path does work that grows with the uncheckpointed log: the dirty sets are `Set` adds, the write group's overlay holds only the batches still waiting for their sync, and an append writes one record.

**The cost is the number of syncs a checkpoint makes, and how they share the machine with commits.** Two facts about Node make it expensive on macOS:

- libuv implements `fsync` (and `fdatasync`) on Apple platforms as `fcntl(F_FULLFSYNC)`, which flushes the whole drive's write cache. Each one costs a device-wide flush, and the device runs them one after another. There is no cheaper sync reachable from Node there.
- Every `fs` call in the process runs on libuv's thread pool, four threads by default (`UV_THREADPOOL_SIZE`). A sync holds a thread for its whole duration.

A checkpoint syncs every file written and every directory whose entries changed since the last one. In the Windows run that was 720 files and 902 directories per 4 MiB of log — about 400 syncs per MiB, since the layout writes four files and touches five directories per new block. `syncDirtyPaths` runs them sixteen at a time (`CHECKPOINT_SYNC_CONCURRENCY`), so for the whole checkpoint all four pool threads are blocked in device flushes, about twelve more syncs are queued behind them, and every other file operation of the process — the commits' log append and log sync, their tree writes, and every block read — waits in that queue. That matches the report: wall time far above CPU time, the triggering commit and the dozen after it slow, then normal again.

**Simulated, it reproduces.** Replacing every handle's `sync` with a model of `F_FULLFSYNC` — each sync reserves the next 10 ms slot of a single device and holds a pool thread until its slot ends (a `crypto.pbkdf2` call sized to the wait, since that runs on the same pool), with `process.platform` set to `darwin` so directories are synced too — gave, at `checkpointBytes` 4 MiB:

| `CHECKPOINT_SYNC_CONCURRENCY` | transactions during a checkpoint | checkpoint duration | log truncated during the run |
|---|---|---|---|
| 16 (today) | 3.7–30.8 s each, neighbours ~200 ms | 8–45 s | yes |
| 1 | 170–230 ms, neighbours 90–140 ms | first one 31.7 s, still running when the 40 transactions ended | no: the close's final checkpoint took 105 s over 2,480 files and 3,102 directories |

The model's CPU figures are not meaningful (the model burns CPU to hold a thread). It shows the two halves of the fix: fewer syncs in flight is what keeps commits fast, and on its own it lets the checkpoint fall behind the writes without limit, which grows the log (an open reads a log whole into memory, see the `NOTE:` in `replaySegment`) and the time a close takes.

**The seal is not the problem.** It ran in 2–95 ms in every run; on macOS it costs two device flushes (the new empty log and the store directory). It stays in the commit queue.

**The 64 MiB row is not explained.** Commits slowing from about #101 with no checkpoint yet run was not reproduced on Windows, and no code path grows with the log. The likeliest cause is the operating system writing back the unsynced tree files on its own, so each of the log's `F_FULLFSYNC`s flushes a drive cache full of that writeback; that is a hypothesis only, and confirming it needs the reporter's script on macOS (`CHECKPOINT_MIB=64`). If it holds after this fix, the remedy is to start the paced tree syncs below before the size threshold is reached, so unsynced tree data never accumulates — a follow-on, not this ticket.

## What to build

A checkpoint whose tree syncs run at a pace commits do not feel, and that still keeps up with the writes.

- **One tree sync at a time.** The checkpoint syncs its files and directories one at a time, not sixteen, leaving three of the default four pool threads to commits and reads. `replay` at open keeps its own wider limit: nothing competes with it. (If measurement shows two is materially faster on Linux with no cost to commits, two is acceptable; more than half the default pool is not.)
- **Give way to the log.** A tree sync does not start while a task is queued or running in the log's queue (a commit, a sync step, a seal). Count the queue's outstanding tasks in `enqueue` and let the checkpoint wait for that count to reach zero before starting each sync. A sync already in flight is not interrupted, so a commit's own log sync waits for at most one tree sync.
- **Keep up, by charging each commit its own share when behind.** The checkpoint is *behind* when the current log reaches `checkpointBytes` while the previous checkpoint is still syncing. While it is behind, the tree syncs stop giving way, and a commit, after its append, waits until the running checkpoint has completed its share of syncs: the record's bytes times the sealed segment's path count divided by its bytes, rounded up. Writers are then held to the rate the disk can make the tree durable, each paying for roughly the syncs its own bytes will cost, rather than one commit paying for a window's worth; and the log stays near twice `checkpointBytes` at most. The first commit to wait in an episode logs it once (like `window-overrun` in `SyncDeadlines`), with how far behind the checkpoint is, so an operator can see a disk that cannot keep up. A commit that is waiting does not count as a queued task for the give-way rule (it has already appended), or the two rules would deadlock — design the wait outside the queue, or release the queue slot before it.
- **Unchanged**: the seal, the truncate, the crash cases and their replay order, the failure latch, the idle and close checkpoints (the close's final checkpoint may sync at full width, since nothing competes), and every promise in the README's Write-ahead log and Durability sections and Invariant 6 of `packages/db-p2p/docs/storage.md`. A commit still never waits for a checkpoint it did not fall behind.

## Tests

The rule is a scheduling rule, so test it by counting syncs in flight rather than by timing. `interceptHandleSync` in `test/support/fs-injection.ts` wraps every handle's `sync`; extend it (or add a sibling) that can park a sync and tell the log's own handle from a tree file's — the log's path is `FileWriteLog.logPath`.

- One test that fails today: with tree syncs parked, a checkpoint in its sync phase never has more than one tree sync in flight, and a commit queued while one is parked starts no further tree sync until it has resolved. Today sixteen are in flight at once.
- One test for the share: with a small `checkpointBytes` and tree syncs parked, commit until the checkpoint is behind; a commit made then does not resolve until enough parked syncs are released, and resolves once they are.
- `test/fsync-count.spec.ts` counts every sync made between the start and end of a group, through every handle; a background checkpoint whose tree syncs land inside a measured window would break it. Its groups are far below the 16 MiB default and finish well inside the 5 s idle checkpoint, so it should be unaffected — confirm it still passes as it is.

No test of the macOS timings: the model above is for the implementer to check the effect, not a spec. To reproduce it, wrap `fs.promises.open` before the store opens so each returned handle's `sync` first reserves a slot on a shared `deviceFreeAt` clock (`start = max(now, deviceFreeAt)`, `deviceFreeAt = start + 10`), then runs a `crypto.pbkdf2` sized to `deviceFreeAt - now` ms, then calls the real `sync`; set `process.platform` to `darwin` with `Object.defineProperty` so `fsyncDir` runs; drive `StorageRepo.pend` and `commit` over `FileRawStorage` with `checkpointBytes` 4 MiB and 20 new 8 KB blocks per transaction, 40 transactions. Expect every transaction within about twice its neighbours and the log truncated during the run.
