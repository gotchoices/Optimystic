# A refresh should never have to be *told* which of its own writes is in flight

## Plain-language background

A write can half-land. The network layer commits a collection's header and log tail first, then
sweeps the remaining blocks; if one of those later blocks loses a race, the whole write is
reported as failed even though the header and tail are already permanently stored. The write's
own record is therefore already in the collection's log when the writer is told "you failed".

If the retry does not recognise that record as its own, it writes the same thing a second time
and the log ends up with the write recorded twice, under the same identifier, at two different
revisions.

Ticket `torn-action-own-entry-consumption` fixed this for the single-collection path
(`Collection.sync`). The multi-collection path (`TransactionCoordinator`) has the identical
defect and is untouched.

## Reproduced (this is `repro: verified`, not inferred)

A throwaway spec was driven against HEAD and then against a working prototype of the fix below.
Against HEAD, both cases fail; with the prototype, both pass and the whole `@optimystic/db-core`
suite stays green (1456 passing).

Observed on HEAD, single collection, one action, one injected torn commit:

```
landedCommits= 2
logged= [ {set,"torn",transaction:"stamp:VKQ…"}, {set,"torn",transaction:"stamp:VKQ…"} ]
```

Two log entries, same action, same transaction id, two revisions — and a second commit that
actually landed on storage. A second reader opened over the raw transactor sees the same two
entries, so this is durable duplication, not a local-view artifact.

## Root cause — one site, one missing piece of knowledge

`Collection.updateInternal` can only recognise its own already-committed entry when a caller
hands it the action id, as an optional argument:

```ts
private async updateInternal(inFlightActionId?: ActionId)
```

Exactly one of the three callers passes it (`syncInternal`). `update()` and `updateAndSync()`
correctly pass nothing — they are refreshes on behalf of a reader, with no write in flight. But
`TransactionCoordinator.commit`'s retry loop refreshes **through `update()`**
(coordinator.ts:199-202):

```ts
for (const collection of this.collections.values()) {
	await collection.update();
}
```

so it is indistinguishable from a reader refresh, even though the coordinator is mid-retry of a
write whose id it holds. The knowledge exists at the call site and nothing forces the call site
to supply it. The uninformed-refresh *shape* is what should stop being expressible — a fourth
write path added later would inherit the same defect for free.

## The path, end to end

1. `applyActionsToCollection` appends the log entry with `actionId = transaction.id`
   (coordinator.ts:~790) — the same id on every retry attempt.
2. `commitCollection` sends the `CommitRequest`. A torn commit answers `{ success: false }`, and
   the code deliberately maps *every* returned commit failure to `stale: true`
   (coordinator.ts:~1183-1192) — a documented choice, correct for its own purpose.
3. Nothing lands in `committedCollections`, so `commitPhase` reports `staleLoss: true` and
   `commitOnceLatched` raises `CoordinatorStaleLossError` — a *clean* loss, nothing durable. For
   a torn action that classification is wrong: the header and tail ARE durable.
4. `commit` catches it, `restorePending` puts back the pre-append pending actions (the log entry
   it appended came after the snapshot, so nothing undoes that), then refreshes with
   `collection.update()` — no id, so the durable entry runs through the conflict filter, is kept,
   and is replayed.
5. The retry appends a second entry under the same `transaction.id` at the next revision.

Beyond the duplicated action, this makes the action-id→revision relationship ambiguous for
everything that reads it — `Log.getActionContext`'s `committed` list, `findInvalidation`, and any
dispute/invalidation cascade that identifies an action by id.

## What to build — the invariant, not the instance

The collection owns the fact for the duration of a write attempt. `updateInternal` reads it from
`this` instead of taking it as a parameter, so `update()` and `updateAndSync()` become correct by
construction rather than by having nothing to pass.

```ts
class Collection<TAction> {
	/** The action id of a write currently in flight ON THIS INSTANCE'S BEHALF. Set for the whole
	 *  attempt CYCLE — including the refresh BETWEEN a failed attempt and its retry, which is the
	 *  only moment it is read. Unset outside a write, so a reader refresh cannot consume. */
	private inFlightActionId?: ActionId;

	/** Bracket a write attempt cycle; the returned disposer clears the id (id-guarded, so a
	 *  nested/overlapping clear cannot wipe someone else's mark). Call in a `finally`. */
	beginInFlightAction(actionId: ActionId): () => void;
}
```

A disposer-returning `begin…` (mirroring `acquireLatch`) is preferred over a separate
`endInFlightAction` — the prototype used a pair and it works, but the disposer shape is the one
that makes the clear hard to forget.

### Correction to the fix ticket's sketch — read this before wiring the clear

The `fix/` ticket said *"Clearing belongs in the same `finally` that releases the latch."* **That
is wrong and the fix does not work that way.** The coordinator's inter-attempt refresh
(`collection.update()`) runs *outside* the latch span, after `commitOnce` has released — by
design, since `Latches` is non-reentrant. If the id were cleared when the latch is released, it
would already be gone by the time the refresh that needs it runs.

The correct lifetime is the **attempt cycle**, not the latched span:

- `syncInternal` — set at the top (it mints one `actionId` per `sync()` call and reuses it across
  that call's retries), clear in a `finally` around the whole retry `while` loop. `sync()` holds
  the collection latch across all of it, so the field's lifetime is contained.
- `TransactionCoordinator.commit` — mark each participant inside `commitOnce`, right after
  acquiring its latch (`transaction.id` is stable across retries, so no new identifier is needed);
  clear in a `finally` wrapping the **entire retry `for (;;)` loop**, so the mark survives every
  inter-attempt `update()` and is gone on every exit — return, stale-loss exhaustion, partial
  commit, hard error, abort.

The clear therefore runs *without* the latch held. That is safe and must be documented at the
site: it is a single field write, id-guarded, and the only reader (`updateInternal`) runs under
the latch, so the worst case for a foreign concurrent refresh is that it stops consuming — never
that it consumes something it should not.

Two properties to preserve, both verified in the prototype:

- A reader refresh on a collection with no write in flight behaves exactly as today (the field is
  unset, so the consume branch cannot fire).
- The field is cleared on every exit path, including an abandoned/throwing commit — a stale id
  left behind would let a *later, unrelated* refresh consume a foreign entry that happens to
  match.

### Prototype notes worth keeping

- `commitOnce` marks only the collections it actually participates with; the clear loop iterates
  all registered collections and is id-guarded, so a non-participant is untouched.
- After a torn participant consumes its own entry, its pending queue empties, its tracker resets,
  and it therefore **drops out of the next attempt's participant set** (`commitOnce` filters on
  non-empty tracker transforms). The retry commits only the remaining participants, under the same
  `transaction.id`. That is the intended behaviour, but it means the retry's log entries carry an
  `allCollectionIds` list naming only the *remaining* participants, while the torn participant's
  already-durable entry names all of them. Record that asymmetry as a `NOTE:` at the
  `applyActionsToCollection` append site — it is what a future reader of the cross-collection
  invalidation cascade will need.
- If every participant consumes its own entry, `commitOnce` finds nothing to commit and returns
  successfully — `recordCommitted` never runs for the torn collection, but the refresh already
  advanced its context past the durable entry, so local state stays consistent. Confirmed in the
  single-collection prototype run (`landedCommits = 1`, log length 1, second reader agrees).

## Coverage this must add

Reuse `CommitLandsButReportsStale` from `collection-own-action-replay.spec.ts` (commits durably on
the inner `TestTransactor`, then answers `{ success:false, conflict:true }`) and the coordinator
staging/`logActions` helpers from `coordinator-latch-interleaving.spec.ts`. All three cases below
were exercised in the prototype except the third, which was reasoned through, not run.

- **Single-collection torn commit through the coordinator.** Stage one action, commit with fast
  retry options (`{ maxAttempts: 5, baseBackoffMs: 1, maxBackoffMs: 5 }`), assert the collection's
  log holds the action exactly once, that exactly one commit landed on the inner transactor, and
  that a second `Collection` opened over the *unwrapped* transactor sees one entry too.
- **Multi-collection, one participant tears and the other cleanly loses.** The wrapper must
  distinguish the two: the first `commit` call delegates durably and is then masked as
  `{ success:false, conflict:true }` (the torn one); the second returns a stale failure *without*
  delegating (a clean loss, nothing durable); later calls pass through. Both collections' logs
  must end up holding their own action exactly once. If the non-torn participant had committed
  durably instead, the coordinator would classify the attempt as a partial landing
  (`CoordinatorPartialCommitError`, not retryable) and the retry path would never run — so the
  "clean loss, never durable" half is what makes this case exercise the bug at all.
- **An abandoned commit leaves no id behind.** Drive a commit that fails non-retryably (a hard
  error, not a stale loss), then run a plain `update()` over a foreign log entry that happens to
  carry that same action id, and assert it is *replayed*, not consumed.

## Out of scope

- Do not change the header→tail→sweep commit order, and do not soften the non-tail sweep's stale
  failure into a tolerance. Both are load-bearing and are re-stated in the completed
  `torn-action-cleanup-and-mesh-validation` work.
- Do not reclassify the coordinator's torn commit as a partial landing
  (`CoordinatorPartialCommitError`). That would make it non-retryable and lose the retry the
  writer is owed; the fix is for the retry to recognise its own work, exactly as the
  single-collection path now does.
- Do not try to close `debt-coordinator-execute-and-multi-collection-latch-span-untested` here.
  The multi-collection case above happens to drive that path, but proving the latch span is a
  separate ticket with its own gated-transactor harness.
