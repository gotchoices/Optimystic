Second of the five stage-4 tickets (see `4.1-offline-sync-plugin-mode-and-sealing` for the controller this builds on). Two things: the reactive announcement a removal owes, and the SQL-level pins of the rules stage 2 built into `Collection.restorePending` for a rollback that runs while the drain changes the sealed segments.

## Design

### Removal announces the tables whose rows changed

A `failed` status from the db-core queue carries `changedCollections`: the collections the entry still had a segment in when it was removed (`OfflineQueue.remove`). The controller maps them to tables through the bridge's collection-to-table record (ticket 4.1 exposed it) and calls `Database.notifyExternalChange(table, schema)` once per distinct table, after the status has been delivered to the application's listeners. That is the same call the reactive watch bridge makes for a remote commit (`OptimysticVirtualTable.handleCollectionChange`), so `Database.watch` subscribers re-query and see the row gone ([§Removing an entry](../../docs/offline-sync.md#removing-an-entry), step 4; [§Reactive watching](../../docs/offline-sync.md#reactive-watching)).

The bridge records qualified names as `schema.table` strings. Keep the structured pair beside the string (or store the pair and render the string where the durability report needs it) rather than splitting on a dot, since a schema or table name may contain one.

A `committed` status announces nothing: the drain committed the entry with the effect it already had locally, so no row this machine sees changed. A cascade announces each failed entry's tables as each `failed` status arrives; a table named by two cascading entries is announced twice, which only costs a re-query.

The call is fire-and-forget with the error isolation `handleCollectionChange` already has (a rejected promise is logged, never thrown into the drain).

### Rollback during a drain

Nothing new to build: stage 2 made snapshots open-segment-only and `restorePending` version-aware, and the bridge awaits every restore (`rollbackTransaction`, `rollbackToSavepoint`). This ticket pins the two SQL-level shapes the design names and fixes whatever they find:

- An entry is queued, then a SQL transaction is opened on the same table and rolled back while the drain commits the entry. The entry commits exactly once (one log entry under its action id on the other node) and the rolled-back transaction's rows are gone.
- A savepoint is open (a statement in progress) while the drain removes a refused entry. The savepoint rollback replays the sealed segments as they are now, so the removed entry's rows stay gone and the statement's own rows are discarded.

Both need the drain held at a chosen moment. Use a write-ahead observation: `OfflineQueueOptions.recordAttempt` is the queue's hook, and the controller should pass through a test-only seam for it (a `recordAttempt` option under `config.offline` is not wanted; instead expose the queue on the controller for tests, the way `plugin.txnBridge` and `plugin.collectionFactory` are exposed, and have the spec subscribe to `onStatus` for `submitting` plus a `wrapRepo` on the mesh transactor that parks the pend until released, as `test/commit-gate.ts` does for other specs).

## Edge cases & interactions

- **An entry over a table and its index refused in the index collection.** `changedCollections` lists both collections; the table is announced once. Test: part of the rival scenario below.
- **A partly committed entry that then fails** announces only the tables of the collections it still held a segment in (the committed half's rows stay). By inspection of `remove`; no plugin test.
- **A watcher registered on a `Database` that has been closed** sees nothing; the controller's call lands in the same logged no-op the watch bridge documents. By inspection.
- **A refusal found by a reader's refresh before the drain** (a live `select` pulled the rival's commit) fails the entry from the drain's next iteration; the announcement fires then, after the read that found it. Test: the rival scenario reads node A before the drain runs.
- **Rollback of an open transaction after its own `markDirty` snapshots were captured over sealed segments that the drain has since removed** takes the replay arm; a verbatim restore would put the drained segment back and the next head commit would commit it twice. This is the first scenario above; assert on the other node's log length.
- **A savepoint rollback whose replay refuses the open segment** surfaces through the statement as a rival's commit would. By inspection (`restorePending`'s documented contract); no new test.

## Tests

`test/offline-mode-removal.spec.ts`, on the two-node mesh from ticket 4.1's harness usage:

- **Rival primary key.** Node A offline queues an insert of key `k`; node B commits `k` meanwhile; node A reconnects. The entry fails with `constraint` (`error` is a `ConstraintError` whose message reads `UNIQUE constraint failed: …`), the row disappears from a live read on A, a `db.watch` on the table fired after the `failed` status, and a later queued entry that updated `k` fails with `concurrent-modification` and `causedBy` naming the first entry. Check the `tables` on both statuses.
- **Concurrent modification.** Node A queues an update of a row node B then changes: `failed` with `concurrent-modification`, `error` a `ConcurrentModificationError`.
- The two rollback-during-drain scenarios above.
