# A verified commit proof is not verified again

Reported as GitHub #68 (Sereus/cadre on React Native, `@optimystic/db-p2p` 1.27.0, first seen on 1.19.0).

## What happens now

`certifyClaim` and `certifyContent` (`packages/db-p2p/src/cluster/certified-claims.ts`) call `verifyBlockCommitProofClaim` (`packages/db-p2p/src/cluster/commit-proof.ts`) on every call. That verifier, for a proof freshly decoded off the wire, does: `canonicalJson` + SHA-256 of the peer list (membership digest), `canonicalJson` of the message (a JS replacer) + three SHA-256 passes over it (message, promise and commit hashes), `canonicalJson` + SHA-256 of the promise map, and one Ed25519 verify per approve vote in both rounds (up to 6 for a 3-signer proof). Then the cheap claim step (`findClaimedCommitOp`). Nothing is remembered.

On a quiet node the same inputs recur: the embedder reloads its membership views every 15 s, past the 10 s `readRepairWindowMs`, so each reload consults the cohort, and every answering peer re-sends the same unchanged proof. `queryClusterForLatest` in `packages/db-p2p/src/repo/coordinator-repo.ts` verifies all answers in one `Promise.all`, so the k identical proofs of one consult are also verified k times in parallel. On Hermes, where Ed25519 and SHA-256 are pure JavaScript, this was about a fifth of an idle voter node's JS time; on Node one 3-signer proof costs 0.77 ms per verify.

The reporter's local patch keyed a 512-entry cache on `sha256(JSON.stringify([proof, claim, thresholds], strictReplacer))`, which dropped a repeat to 0.08 ms on Node, but the JS replacer plus a JS SHA-256 over ~2 KB became the top single call site in their Hermes profiles.

## Design

### Split the verdict: the votes part is memoized, the claim part never is

Everything `verifyBlockCommitProofClaim` checks except the final claim step depends on the proof and the thresholds alone, not on the claim: version, structure, duplicate signers, membership digest, message hash, both rounds' signatures and both thresholds. Move all of that into a private `verifyProofVotes(proof, thresholds): Promise<VotesVerdict>` (`{ ok: true } | { ok: false; reason: ProofFailure }`), keeping its checks in today's order and its outer `try/catch → malformed-proof`. `verifyBlockCommitProofClaim` becomes: votes verdict (memoized, below); on failure return it; then the claim step (`findClaimedCommitOp` on the **live** proof's message, inside the same total-on-hostile-input `try`), returning `claim-not-in-message` or `{ ok: true, declaredDigest }` exactly as now.

Consequences, all of which keep verdicts identical to today:

- The claim step runs on every call, so a valid proof presented for another claim — the replay case — still fails `claim-not-in-message` on a memo hit.
- The order of checks is unchanged (votes first, then claim), so a proof that fails both still reports the votes reason. Do not move the cheap claim step first: a forged proof for the wrong claim would then report the attributable `claim-not-in-message` instead of the non-attributable `malformed-signature`, which `isAttributableProofFailure` turns into a penalty.
- `verifyBlockCommitProofContent` calls `verifyBlockCommitProofClaim`, so it shares the memo for its votes half. Its `canonicalBlockHash(block)` step is not memoized: a key that binds the block bytes costs about what hashing them does, and the content path (`reconcile-block.ts`, `BlockTransferService.handlePush`) is not the recurring idle path.
- `certifyClaim` / `certifyContent` are unchanged: `exceedsSignerCap` still runs first, and `anchorAcceptedProof` still runs on every accepted call (it depends on local state, and `onUnanchored` keeps firing once per certification, so callers counting unanchored acceptances see the same counts).

### The key is the proof's own JSON text, and a miss verifies that text

Key: `` `${thresholds.superMajorityThreshold}|${thresholds.simpleMajorityThreshold}|${body}` `` where `body = JSON.stringify(proof)` — the engine's native serializer, **no replacer and no hash**. The string itself is the `Map` key; the engine hashes and compares it natively. If `JSON.stringify` throws (a throwing getter, a cycle, a BigInt) or does not return a string (an `undefined` proof), there is no key: verify the live proof with no memo, as today.

On a miss, verify **`JSON.parse(body)`**, not the live object. That makes the memoized verdict a pure function of the key string, which is the whole soundness argument:

- **No aliasing, by construction.** Two calls with the same key verify the same text, so a memo hit can only return what a fresh verification of that key would return. The key binds everything the votes verdict reads — the message (so a tampered message with an untouched self-reported `messageHash` is a different key, and its verification recomputes the hash and fails `message-hash-mismatch`), the promise and commit maps with every signature string, the peer list, the declared digests and hashes — because it *is* all of them. It never trusts the self-reported `messageHash`.
- **Hit and miss agree.** With or without a hit, the votes verdict is `verifyProofVotes(JSON.parse(body))`.
- **The snapshot judges what today's code judged, for every proof that came off a wire or out of storage.** Such a proof was produced by `JSON.parse`, and for a parsed object graph `JSON.parse(JSON.stringify(x))` differs from `x` only by `Infinity`/`-Infinity` becoming `null` and `-0` becoming `0`. The votes verdict reads none of those distinctions: every numeric read is a strict comparison with the literals `1` and `2` (`proof.v`, `proof.membershipVersion`), which none of `null`, `±Infinity`, `0`, `-0` satisfy; every other read is a `typeof`/`Array.isArray`/`=== null` test that classifies `null` and `Infinity` the same way as far as the verdict goes (both fail `typeof … === 'string'` and `typeof … === 'object' && !== null`, both are skipped as votes), a string comparison, or a serialization through `canonicalJson`/`JSON.stringify`, which collapse the same values the same way. Only approve votes are verified, and `clusterVoteVerificationPayload` reads only `type` for them.
- **What changes, deliberately.** An in-process proof holding values JSON cannot represent faithfully (a `Number` or `String` wrapper object, a `toJSON`, a getter that answers differently on each read) is now judged as it would be once sent. No production path builds such a proof — `buildBlockCommitProof` and `mintSoloCommitProof` produce plain data — and certification is a judgement on the artifact a peer sends, so this is the right semantics. Say so in the verifier's doc comment.
- **A proof mutated while it is being verified** cannot poison the memo, since the verification reads a private copy. A proof mutated *after* it was memoized produces a different key on its next call.

The cost of a hit is one native `JSON.stringify` of the proof (a few KB), one string concatenation, one `Map` lookup and the claim step's loop — no JavaScript replacer and no JavaScript hash, which is what made the reporter's key expensive on Hermes. A miss adds one native `JSON.parse` to a verification whose Ed25519 work dwarfs it.

Rejected keys:

- **The recomputed hashes** the verifier produces (commit hash plus the commit map's signatures): computing them is three SHA-256 passes over the message plus `canonicalJson` with a JS replacer — more per call than the reporter's key.
- **Identity of the decoded proof object** (a `WeakMap`, like `canonicalMessageBytes`' memo in `packages/db-core/src/cluster/membership.ts`): every answer, and every consult, decodes a fresh object, so it never hits in the reported case.
- **`messageHash` plus the signature strings**: trusts the self-reported hash, so a tampered message under an untouched hash would reuse a cached pass — the hazard the ticket names.

### Only passes are remembered; identical proofs in flight share one verification

New module `packages/db-p2p/src/cluster/proof-votes-memo.ts`, a small generic class (named e.g. `VerdictMemo<V>`) with no crypto in it so it is testable with a fake computation:

- `judge(key: string, compute: () => Promise<V>, retain: (verdict: V) => boolean): Promise<V>`.
- **In flight:** while a computation for `key` is pending, a second call with the same key awaits the same promise (removed from the in-flight map in a `finally`, whether it resolves or rejects; a rejection propagates to every waiter — `verifyProofVotes` is total, so this is defensive). This is what collapses the k identical answers of one consult's `Promise.all` into one verification.
- **Retained:** after it settles, the verdict is remembered only when `retain(verdict)` is true — for proofs, only `ok: true`. Failures are not remembered: honest recurring input is passing proofs, and keeping junk out means a peer spraying invalid proofs can never evict a good entry. (A failing proof costs exactly what it costs today.)
- **Bounded by characters, not entries,** because proof size is chosen by whoever sends it (a padded message can approach the 8 MiB frame, `MAX_BLOCK_MESSAGE_BYTES`): a total budget of the summed key lengths (1 MiB of characters, `PROOF_VOTES_MEMO_CHARS`), and a per-entry cap (64 KiB, `PROOF_VOTES_MEMO_ENTRY_CHARS`) above which a verdict is not retained, so one large proof cannot flush the rest. Least recently used goes first (`Map` insertion order, a hit re-inserts), evicting until the total fits. The precedent for bounding a table whose keys come off the wire is `PeerReputationService`'s `maxPeers` (`packages/db-p2p/src/reputation/peer-reputation.ts`); `LruMap` (`packages/db-core/src/utility/lru-map.ts`) is count-only, which is why this is its own small class. Measured proofs are ~1 KB (solo) to ~4.6 KB (10-peer, two blocks), so the budget holds a few hundred — far more than the handful of distinct proofs a node's idle consults recur on.
- **One instance per process** (module level in `commit-proof.ts`), shared by every node in the process: it memoizes a pure function of its key, so sharing is sound, and in-process test meshes get the same behaviour as production.

Put a `NOTE:` tripwire at the memo: a peer holding enough keys to mint valid self-certified proofs can churn the memo, which costs honest proofs their re-verification (today's cost) and nothing else; if that ever shows up, bound retention per serving peer.

## Edge cases & interactions

- **Forged signature** (one signature string changed on an otherwise memoized proof): different key → miss → `malformed-signature`. Test.
- **Tampered message, untouched `messageHash`**, after the genuine proof is memoized: different key → miss → `message-hash-mismatch`. Test.
- **Valid memoized proof presented for another claim** (another block, rev or action): hit on the votes, claim step → `claim-not-in-message`. Test.
- **Same proof, different thresholds**: different key prefix → miss. Inspection.
- **Concurrent identical proofs** (`Promise.all` in `queryClusterForLatest`): one computation shared. Test at the memo.
- **Un-keyable proof** (`JSON.stringify` throws or returns `undefined`): bypass, verify live — the existing hostile-shape tests in `test/commit-proof.spec.ts` ("rejects structurally-invalid input as malformed-proof, never throwing") and `test/certified-claims.spec.ts` must pass unchanged. The hostile literals there (`null`, `'garbage'`, `promises: null`, …) all stringify, round-trip and still fail `malformed-proof`.
- **Verifier totality**: building the key and parsing the body sit inside the verifier's no-throw contract (`try`, fall back to the live path). Inspection.
- **Oversized proof**: `exceedsSignerCap` in `certified-claims.ts` still declines before any key is built; a large proof under the signer cap is verified and, above the per-entry cap, not retained. Test at the memo (with eviction, below).
- **Byte budget eviction** — least recently used first, a hit refreshes, an entry over the per-entry cap is never retained. Test at the memo.
- **Anchoring and `onUnanchored`** still run on every accepted call. Inspection (the existing certified-claims tests cover the callback).
- **`canonicalMessageBytes`' `WeakMap` memo** in db-core: verification now hashes a fresh parsed copy, so that memo is filled for an object that dies after the verification. Harmless; it never saw the wire-decoded proof's reuse anyway. Inspection.
- **Mixed versions**: nothing on the wire changes. Inspection.

## Tests (only these)

- `packages/db-p2p/test/commit-proof.spec.ts`, one contract test: verify a genuine proof (pass, memoized), then verify JSON round-tripped copies with (a) a changed message under the untouched `messageHash` → `message-hash-mismatch`, (b) one changed signature → `malformed-signature`, (c) the untouched proof for another claim → `claim-not-in-message`, and (d) the untouched proof for its own claim → passes with the same `declaredDigest`.
- `packages/db-p2p/test/proof-votes-memo.spec.ts`, with a counting fake `compute`: (1) concurrent and repeated calls with one key compute once while the verdict is retained; a non-retained verdict is computed again on the next call; (2) the character budget evicts the least recently used entry, a hit refreshes recency, and an entry above the per-entry cap is never retained.
