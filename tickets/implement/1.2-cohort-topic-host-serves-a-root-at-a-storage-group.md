# Cohort-topic host: serve a root at a storage group

Second of three tickets for the accepted decision in `docs/reactivity.md` § Origination point. The prereq added root placement to db-core (`RegisterV1.rootKey`, `ChildLinkV1.rootKey`, `rootPlaced` flags, `RootPlacement` on the verifier, the optional `ITopicRouter.routeToRoot`). This ticket makes the db-p2p host honor it. Reactivity does not produce root-placed frames until `reactivity-notifications-need-the-tail-cohort-to-be-the-topic-cohort`, so the node's behavior is unchanged when this lands; the host is exercised by its own specs.

## The root group, as the host sees it

A new host option supplies the one rule the whole design rests on — "the root group at a coordinate is the key network's serving cohort there":

```ts
interface RootGroupOptions {
	/** Members (peer-id strings, proximity order) of the root group at `coord` — the key network's
	 *  network-scoped serving cohort, clusterSize wide. Async: it reads the peerStore. */
	membersAt(coord: RingCoord): Promise<string[]>;
	/** Threshold ratio for a root-placed cohort: minSigs = ceil(members × quorumRatio). */
	readonly quorumRatio: number;
}
// CohortTopicHostOptions.rootGroup?: RootGroupOptions
```

The node wiring binds it in the third ticket (to the key network and `consensusConfig.superMajorityThreshold`); this ticket's specs use a fake. A host with no `rootGroup` refuses every root-placed frame (`unwilling_cohort`, reason "root placement not served"), so a node that has not opted in never pretends to be a storage group.

**Root-group snapshots.** Every host site that today calls `cohortAround(coord)` / `fret.assembleCohort(coord, wantK)` reads synchronously. For a root-placed coord those sites must read a per-coord **root-group snapshot** instead: `{ members, epoch = H(sorted members) }`, filled from `rootGroup.membersAt(coord)` when the engine is created (before it handles the frame that created it — register dispatch is already async), refreshed on each gossip-cadence tick, and filled on demand before answering a `/sign` or membership request for a root-placed coord that has no snapshot yet. Keep the snapshot store bounded the same way the coord-engine registry is.

## What changes, site by site

- **Register dispatch** (`dispatchRegister`): with `reg.rootKey`, `servedCoord = addressing.coord(reg.treeTier, participantCoord, topicId, rootKey)`. At `treeTier 0` the engine is created root-placed. Before admitting, check self is in the root group; if not, reply `unwilling_member` with `candidateMembers` = the root group, so the walk's existing member retry dials a real member. At `treeTier 1` the engine's `parentCoord` is `rootCoord(rootKey)` (store the root key on the engine; the tier-1 engine also puts it on its `ChildLinkV1`).
- **Child-link dispatch** (`dispatchChildLink` and `childLinkDeps`): with `link.rootKey` and `childTier === 1`, the parent's served coord is `rootCoord(link.rootKey)`; resolve the parent engine as root-placed.
- **Engine cohort view, signers, publisher.** A root-placed `CoordEngine`'s `cohort()` reads the snapshot; its threshold signers (`makeCoordSigner`, the rotation attestation in `produceRotation`) and its `MembershipCertPublisher` use `ceil(|snapshot| × quorumRatio)` instead of `ctx.minSigs`; its `/sign` requests carry `rootPlaced: true`.
- **`/sign` endorsement** (`signEndorse` → `handleSignRequest`'s `cohortMembersAround`, `currentEpoch`, `expectedMembershipFields`): for a coord this node serves root-placed, or a request carrying `rootPlaced: true`, derive members and epoch from the snapshot.
- **Gossip.** A root-placed engine's `CohortGossipV1` carries `rootPlaced: true`; the co-member gate (`verifyGossip`) and cold-sibling instantiation (`maybeInstantiateColdSibling`) use the root group for such frames and create the sibling engine root-placed; `FretCohortGossipTransport.broadcast` targets the root group for a root-placed coord (give it the snapshot reader).
- **Membership fetch.** `FretMembershipSource.current/fetch(coord, { rootPlaced: true })` fetches from root-group members (via `rootGroup.membersAt`) rather than the FRET cohort around the coord.
- **Trust anchor.** `FretTrustAnchor.directAnchor(cert, tier, placement)` compares a root-placed cert's signers against the root group (`membersAt`; slack still applies) rather than `assembleCohort(coord, k)`. The anchor is synchronous today; either read the snapshot store (and return `"unknown"` when there is none) or make the comparison against an injected synchronous view. Never `"rejected"` from a missing snapshot.
- **Participant verifications of root-signed notices.** Where the host verifies a promotion/demotion notice for a registration it holds (`verifyAndApplyNotice`), pass `RootPlacement { quorumRatio }` when that registration's root key is set and the notice's coord is the root.
- **Router.** `FretTopicRouter` gains `routeToRoot(rootKey, activity)`: resolve `rootGroup.membersAt(rootCoord(rootKey))` and dial each member's `/register` in order (`dialMember`) until one replies; a member's `unwilling_member` reply is returned to the walk as-is. Wire it only when the host has `rootGroup` (the router is constructed inside `createCohortTopicHost`).
- `crossCheckCohort` is a diagnostic over the FRET cohort; skip it for root-placed coords rather than logging a false mismatch.

## Edge cases & interactions

- **Self outside the root group** (a FRET-routed frame landing on the nearest ring peer, which on a ring shared with another network may serve that other network): `unwilling_member` naming the group. Test in `live-tier.spec.ts` with a fake `membersAt` that excludes the landing node.
- **Root group of one** (`clusterSize: 1`): threshold `ceil(1 × ratio) = 1`; the engine signs its own cert. Inspection plus the same live-tier fixture with a one-member group.
- **Snapshot churn.** A refresh that changes members changes the epoch, which is exactly what drives the existing rotation-attestation and republish paths; nothing new is needed beyond feeding them the snapshot. Inspection.
- **Endorser with no snapshot** receives a `/sign` with `rootPlaced: true`: fills the snapshot first, then applies the usual member/epoch/payload checks. Its derived view may differ from the requester's under churn — the existing epoch-mismatch refusal covers that.
- **No `rootGroup` configured**: every root-placed register is refused, every non-placed frame behaves exactly as before. The existing host suites staying green is the verification.
- **Mixed signer thresholds on one node.** A node serves default-rule coords and root-placed coords at once; each engine uses its own rule. The live-tier test should assert a root-placed engine's published cert has `|members|` = the fake group size and verifies under `RootPlacement`, and is untrusted under the default rule.
- **Engine registry pressure.** A root-placed engine counts against the same registry cap; eviction drops its snapshot too (bounded maps only).
- **Unbound root key (accepted, document it at the dispatch site as a `NOTE:`).** Nothing ties a frame's `rootKey` to its `topicId` here. A participant that names a wrong root key places its own registration at a root group that never announces to it; the only other effect is choosing which storage group serves a registration, which grinding a topic id already allowed. The host does check it is in the named group.

- **A root key can be chosen to land on a default-addressed coordinate (added by the prereq's implementer).** `rootCoord(rootKey)` is `H(rootKey)` with no tier byte or topic id in front — by design, so it equals the storage position — which means the 33 bytes `0x00 ‖ topicId` are a valid root key whose root coordinate is exactly `coord_0(topicId)` of a default-addressed topic (and `d ‖ prefix ‖ topicId` lands on a `coord_d`). The coord-engine registry is keyed by served coord, so a root-placed register naming such a key arrives at a coordinate that may already have, or later get, a default-rule engine. Decide the rule once per engine and refuse a frame that claims the other one for that coord (a root-placed register, child link, `/sign` or gossip frame at a coord served under the default rule, and the reverse), rather than letting whichever frame arrives first pick the cohort view and threshold for a coordinate another topic depends on. `docs/cohort-topic.md` § Root placement at a routing key states this as a requirement on the serving node.
- **`routeToRoot` must not be built on `routeAndAct` (added by the prereq's reviewer).** `FretTopicRouter.routeAndAct` hands the db-core coordinate to FRET's `routeAct`, which hashes whatever key it is given, so it lands at `H(coord)`, one hash past where the host assembles the cohort — a pre-existing mismatch for every tier, filed as `tickets/backlog/bug-cohort-topic-router-hashes-a-coordinate-as-a-key`. For the root group it means `routeAndAct(H(rootKey))` reaches `H(H(rootKey))`, never the storage group. Bind `routeToRoot` to the key network's cohort for the raw key (`findCluster(rootKey)` and a direct dial), and have `rootGroup.membersAt(coord)` take the coordinate `H(rootKey)` directly, as the third ticket's `servingCohortAt` plans.
- **Tell the verifier which rule a self-published cert was published under.** `MembershipVerifier.cache(cert, placement?)` now takes the placement. A root-placed engine's `onCertPublished` must pass it; without it the cert is cached under the default rule, every verification under the placement misses the cache and re-validates from the source, and the self-published trust lock is never used for that coord.

## Tests (only these)

- `live-tier.spec.ts`: a root-placed register lands on a group member and is accepted; one landing outside gets `unwilling_member` naming the group; the root engine's cert has the group's members and verifies only under the placement rule.
- `fret-trust-anchor.spec.ts`: a root-placed cert whose signers are the root group is `"anchored"` even when the FRET `wantK` cohort around the coord differs; no snapshot → `"unknown"`.
