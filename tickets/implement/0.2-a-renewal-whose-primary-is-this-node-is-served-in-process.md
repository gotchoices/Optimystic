# A renewal whose primary is this node is served in process

Found while planning `subscription-renewals-to-one-cohort-member-share-a-request`.

## What happens

A participant's registration names a primary chosen by `assignSlots` (`packages/db-core/src/cohort-topic/registration/sharding.ts`) over the cohort's members: `slot = H(participantId ‖ cohortEpoch) mod k`. When the participant is itself a member of that cohort — every node of a group no larger than a cohort, so both machines of a two-member group — the slot can name the participant's own node.

The participant-facing service renews through `ITopicRouter.dialMember` (`CohortTopicService.renewalTransport` in `packages/db-core/src/cohort-topic/service.ts`). The host builds that router (`new FretTopicRouter` in `packages/db-p2p/src/cohort-topic/host.ts`), and `FretTopicRouter.dialMember` always dials over libp2p, which refuses a dial to its own peer. So every plain ping of a self-primary registration is a failed ping. After `MAX_PING_FAILURES` (3) the participant re-attaches to `backups[0]`, the other machine, which accepts and serves it from then on under an epoch-scoped failover override. Net effect today: each such registration loses three pings and one failover round per cohort epoch, and ends up renewed across the network although its own node holds the record.

The router already knows how to serve a frame addressed to this node in process — `dialRootGroup` uses `selfPeerId` and `handleLocally` — but the host passes those two options only when root placement is configured, and `dialMember` never consults them. The matchmaking transport hit the same problem and serves self-routed renews in process (`sendRenew` in `packages/db-p2p/src/matchmaking/query-transport.ts`); the reactivity side never got the same treatment.

Because the slot depends only on the participant and the epoch, every registration a node holds at cohorts with one member list (every cohort on a two-member group) shares one primary: either all of them are self-primary or none are. Fixing this makes the self-primary case cost no network request at all, and is a prerequisite for the batched renewal in `subscription-renewals-to-one-cohort-member-share-a-request`, whose self-addressed batches need the same in-process route.

Repro is static. To confirm: on a two-node in-process mesh with cohort-topic enabled, register from a node whose `assignSlots` names itself, call `renew` once, and observe the self-dial rejection (the renewal counts a failure; after three, `reattach` goes to the other node).

## Expected behaviour

- `FretTopicRouter.dialMember(member, activity)` serves `activity` through `handleLocally` when `member.id` is this node, exactly as `dialRootGroup` does for a root-group member. A throw from the local handler propagates (it is a fault of the frame, not of a link; the renewal counts it as a failed ping as it counts any rejection).
- The host always gives the router `selfPeerId` and `handleLocally` (`handleRegisterFrame`), not only under the root-group branch. Root-group dialing keeps its behaviour.
- The in-process answer is the same one an inbound `/register` frame gets (`handleRegisterFrame` → `resolveRenew` for a `RenewV1`, the register dispatch for a `RegisterV1`), so a self-served renew touches and gossips exactly as a remote one.
- The walk's direct member dial (`dialMember` in `packages/db-core/src/cohort-topic/walk.ts`, used for an `unwilling_member` retry or a direct re-attach) gets the same route for free; that is intended. The walk's missing failure handling is a separate backlog ticket (`bug-walk-direct-dial-failure-aborts-register`) and is not part of this one.

## Edge cases & interactions

- **Self id comparison.** Compare by the peer-id string the router already holds (`selfPeerId`), after encoding `member.id` the way `dialMember` does (`bytesToPeerId(member.id).toString()`). Verified by the test below.
- **Router built without the two options** (tests, other embedders). `dialMember` keeps dialing, as today. Verified by inspection; no test.
- **Reentrancy.** `handleRegisterFrame` is declared after the router in `createCohortTopicHost`; the router only calls it at dial time, as the root-group branch already relies on. Verified by inspection.
- **Withdraw tombstone to self.** `RenewalParticipant.withdraw` sends through the same `send`, so a self-primary registration's tombstone now reaches its own engine and evicts locally (gossiped), where today it silently failed and the record waited out its TTL. Intended. By inspection.
- **Failover override churn.** After the fix, a self-primary registration stays served by its own node; it no longer migrates to the backup. No other code reads which member serves. By inspection.

## Tests

One test in `packages/db-p2p/test/cohort-topic/topic-router.spec.ts`: a router given `selfPeerId` and a recording `handleLocally`, asked to `dialMember` its own id, returns `handleLocally`'s bytes and opens no stream (the `MockNode` sees no dial). No test for the unchanged remote path; the existing dial tests cover it.
