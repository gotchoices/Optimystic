# Matchmaking arrival push — the seeker's push-path hang-out loop (db-p2p)

Third of five tickets (chain in `matchmaking-arrival-push-wire-and-selection`). This changes only `SeekerWalkClient` and the `SeekerWalkTransport` seam. The libp2p receiver and real renew/withdraw come next, in `matchmaking-arrival-push-seeker-transport`; here the push source is an abstract channel driven by scripted tests.

## Transport seam

```ts
/** Arrival pushes delivered to one walk. Present only when the transport registered the seeker with pushOnArrival. */
interface SeekerPushChannel {
	/** Remove and return every push received since the last call (already decoded; not yet re-validated). */
	take(): ArrivalPushV1[];
	/** Resolve after `ms`, or earlier as soon as a push is waiting. Never rejects. */
	wait(ms: number): Promise<void>;
}
interface SeekerWalkTransport {
	// …existing register / query / renew / withdraw…
	/** Present iff this walk's registration opted into arrival pushes and the transport can receive them. */
	readonly pushes?: SeekerPushChannel;
	/** Release transport resources when the walk ends (the libp2p transport withdraws + unsubscribes). Optional. */
	close?(): Promise<void>;
}
```

The client takes the push path exactly when `transport.pushes !== undefined`. Opting in is the transport's business: it is what put `pushOnArrival` in the registration, and it knows whether it can receive pushes. No new client option is needed. `wait` gives the tests control over time: the scripted channel resolves it on the virtual clock.

`run()` calls `transport.close?.()` in a `finally` around the walk, on both paths, and logs (does not rethrow) a close failure.

## Push-path hang-out

`hangOut` keeps its poll loop unchanged when there is no channel. With a channel, it runs this loop instead (`cfg = this.config`):

```
lastPoll = now
while remaining() > 0 and matched < want:
    nextSafety = lastPoll + cfg.pushSafetyPollMs
    await pushes.wait(min(nextSafety, deadline) − now)
    for push of pushes.take(): absorbPush(push)
    if matched >= want: break
    await transport.renew()
    if now >= nextSafety and remaining() > 0: collect(await query(d)); lastPoll = now
if matched < want: collect(await query(d))            // the mandatory final poll
```

- **Final poll**: one `QueryV1` when the loop ends with `wantCount` unmet, which is when patience has run out. The poll path already queries at the deadline the same way, so both paths overrun patience by one RPC; doc wording "immediately before `patienceMs` drains" is read as this. It fires even if a push is in flight (doc *Final-poll boundary*).
- **Renewal**: the loop calls `transport.renew()` on every wake, as the poll loop does on every poll. The transport throttles it to the TTL cadence (next ticket); the client stays cadence-agnostic.
- Query count with no pushes: about `patienceMs / pushSafetyPollMs` safety polls plus the final poll (≈ 3 at defaults: polls at 5 s and 10 s, then the final one).

`absorbPush(push)`:

- Drop the whole push if `push.topicId` is not this walk's topic (log). The pushing member's signature is checked by the transport, which knows the sender; the client does not re-check it.
- Run each entry through the same path as a query reply: `matchesFilter`, then `verifyProviderEntry` (a forged entry is dropped, doc *Push forgery rejected*), then dedup into `matched` by `participantId` (doc *Push/poll overlap deduped*). Factor the shared part out of `collect` so query replies and pushes take one code path.
- Do **not** fold push entries into the `filterAcceptRatio` yield. A push is already filtered cohort-side, so it would bias the ratio upward. Only query replies feed it.
- Fold `push.topicTraffic.childCohortCount` into `maxChildCohortCount` (the sweep-escalation signal), and run the promotion check below.

## Promotion observed during hang-out (both paths)

Doc *Promotion while hanging out*: after the cohort promotes, the seeker sees `childCohortCount > 0` on a push or a poll reply and "enters the descend branch". Today the client reads `childCohortCount` only from the `Accepted` reply, so this is new for both paths. Decision: implement it once in the shared absorb/collect path, for both.

- Trigger: a push's or a query reply's `topicTraffic.childCohortCount > 0` while the `Accepted` reply that started this tier's hang-out reported `0` (or no traffic). Only that transition triggers, so a tier that was already promoted when accepted cannot loop.
- Effect: end the hang-out and return a new `AcceptedOutcome` `"reregister"`. `run()` re-registers at the **same** tier without withdrawing. The cohort answers `promoted(targetTier)` and the existing `promoted` case descends. If it answers `accepted` again, the walk proceeds as usual. At most one re-register per tier visit (track it per tier).
- The query reply's `topicTraffic` is the cohort's, so feeding it is safe. The libp2p transport's synthesized empty reply (no cohort answered) carries all-zero traffic and can never trigger.

Decision recorded for the doc ticket: a push does **not** re-run the hang-out-vs-escalate decision mid-hang-out. The poll path does not either, and `patience_per_tier_fraction = 1.0` already commits the remaining patience to the tier when `decide` says hang out. Promotion is the only structural signal acted on. The doc's sentence "lets a hanging-out seeker re-run its hang-out-vs-continue math" is narrowed to that by `matchmaking-arrival-push-wiring-and-e2e`.

## Edge cases & interactions

- Push arrives for another topic → dropped and logged (inspection).
- A push whose entries all fail re-validation → nothing matched, the loop continues (covered by the forgery test).
- A push arriving after `wantCount` is met → the loop has exited; nothing reads the channel; `close()` releases it (inspection).
- A push and a safety poll returning the same provider → counted once (test).
- `pushes.wait` resolving early with nothing waiting (spurious wake) → harmless: `take()` is empty, renew is throttled by the transport, and the safety poll is gated on time (inspection).
- Patience already 0 when hang-out starts → loop skipped, final poll runs (inspection).
- Escalation from a push-path tier: `withdraw()` then re-register at `d − 1`, exactly as today. The new tier's hang-out uses the same channel; the transport binds the same correlation id at every tier, so pushes from the old tier's primary are answered `unknown_seeker` only once the walk closes (see the transport ticket).
- Existing poll-path behaviour and tests are unchanged, apart from the new promotion re-register, which no existing script triggers (verify by running the existing suite).

## Tests (`seeker-walk-client.spec.ts`, scripted transport + virtual clock)

Each pins a doc bullet under "Arrival-push behavior":

- *Sparse safety-poll cadence*: a push-path seeker that receives no pushes issues about `patienceMs / pushSafetyPollMs` queries plus the final one (3 at a 10 s patience and a 5 s poll), not about 10.
- *Missed push, final poll recovers*: no pushes are ever delivered; the provider appears only in the cohort's answer to the final query and is returned.
- *Push/poll overlap deduped*: the same provider arrives by push and by a later safety poll → one entry, counted once toward `wantCount`.
- *Push forgery rejected*: a push whose entry has a bad `registrationSig` is not returned.
- *Promotion observed via folded topicTraffic*: a push with `childCohortCount > 0` after an `Accepted` with 0 → the client re-registers at the same tier and follows the `promoted` reply.
- A push that meets `wantCount` ends the walk before the first safety poll (the point of the feature: zero queries after the immediate one).
