# Multi-round escalation in the dispute service

## Why

`DisputeService.initiateDispute` runs exactly one round (`const round = 0`), and its only caller is a test. The design of record (`docs/right-is-right.md` §Escalation, `docs/correctness.md` Theorem 8) needs a loop that widens until a round decides, with hard bounds, and that two independent drivers can run for the same dispute without disagreeing. This ticket builds that loop as a service capability. Nothing on a live node calls it yet; `dispute-commit-path-block` (pre-commit) and `dispute-post-commit-challenge` (post-commit) are its callers.

## Specification

- **Entry point**: `driveDispute(record, side)` — `side` is the driver's own side (`'approvers' | 'rejecters'`), used only for the driver's signature and logs. Returns the ruling or `unresolved`. Idempotent per dispute id (from `dispute-ruling-certificate`): a second call while one is running joins it; a call after a ruling is known returns it.
- **Rounds.** For `r = 0 .. maxEscalationRounds - 1`: draw `n_r = K × 2^r` arbitrators with `selectArbitrators(blockId, exclude, n_r, r, epoch)`, where `K = arbitratorCount ?? cohort size`, `exclude` = the record's peers ∪ every arbitrator drawn in an earlier round, and `epoch` is fixed for the whole dispute. Send each the challenge (now carrying `round` and that round's set, signed by the driver). Collect votes until the round deadline. The round **decides** when one side's valid votes reach `ceil(2/3 × n_r)` — the same function the verifier uses. Otherwise continue.
- **Termination → `unresolved`** when the first of these holds: the cap is reached; a draw returns fewer than `n_r` peers and that round does not decide (population exhausted); the dispute deadline passes. Log `dispute:unresolved` with dispute id, rounds run, and per-round vote counts — it is a health signal, not an error.
- **Config** (`DisputeConfig`): `disputeRoundTimeoutMs` (default 10 000), `maxEscalationRounds` (default 4), `disputeDeadlineMs` (default `maxEscalationRounds × disputeRoundTimeoutMs`). Remove `disputeArbitrationTimeoutMs`; the challenge's `expiration` becomes the dispute deadline.
- **Two drivers.** A ruling pushed to this node for a dispute it is driving stops its loop and is adopted (after verification). If it already holds a ruling from another round, keep `preferRuling`'s choice. An arbitrator answers a given dispute id and round once: `handleChallenge` caches its signed vote and returns it to any later asker (the same arbitrator cannot be drawn in two rounds of one dispute, by the exclusion rule).
- **Ruling delivery.** On a ruling: verify it with the ruling verifier (never trust a local computation path that skips it), store it, resolve waiters, apply reputation penalties, and push it to the record's peers and every arbitrator drawn in any round (extend `broadcastResolution`). Add a protocol message to fetch a ruling by dispute id (`get-ruling`), answered from the store.
- **Waiting.** `awaitRuling(disputeId, deadline): Promise<ruling | undefined>` for local callers (the coordinator waits through this).
- **Ejection hand-off.** An optional `onRuling(ruling, record)` sink, called once per verified ruling after it is stored. `dispute-ejection-registry` consumes it. Reputation penalties apply to every participant whose signed vote opposed the ruling: the record's promise votes (approve vs marked validity reject) and every arbitrator's vote in every round of this dispute that this node collected; inconclusive votes are not penalized.
- **Arbitrator re-execution.** `handleChallenge` keeps using the injected `revalidate` (unwired on live nodes until `feat-dispute-subsystem-live-activation`). With no `revalidate`, it votes `inconclusive` as today. The vote is about the record's transaction against the state it read, pinned at the record's revision; state that in the `RevalidateTransaction` doc comment so the eventual wiring reads through the ordinary read path at that revision.
- **Engine health**: a driver whose engine is unhealthy does not drive (existing skip); it still answers as an arbitrator.

## Edge cases & interactions

- **Exclusion grows**: round r's draw must exclude all earlier rounds' sets, so the verifier's layer-2 recompute must be able to reconstruct `exclude` from the record's peers and the earlier rounds' *draws* (deterministic from `(blockId, round, epoch)`), not from votes. Make the recompute derive earlier draws itself rather than read them from the proof.
- **Sampling collisions**: `sampleArbitrators` may return the same peer for two coordinates; the round size is the number of distinct peers returned, and a shortfall is judged against `n_r`.
- **Partial failure**: an arbitrator dial failure or timeout is silence (counts against resolution); never throws out of the loop. A selection throw ends the dispute `unresolved` with the error logged.
- **Concurrency**: two `driveDispute` calls for one id, or a pushed ruling arriving mid-round, must not double-apply penalties or double-broadcast (one ruling per id in the store, first-stored wins subject to `preferRuling`).
- **Restart**: in-memory dispute state is lost on restart; a driver that restarts mid-dispute simply stops (the other driver, or the writer's re-drive, carries on). Rulings already stored are not persisted by this ticket — `dispute-ejection-registry` persists what outlives a restart (the ejections). Note this at the store.
- **Bound**: worst-case arbitrator count is `K × (2^maxEscalationRounds − 1)`; at the defaults 15 × K. The loop must not draw past the cap even if the deadline allows.

## Tests

With an injected `DisputeClient` factory standing in for remote arbitrators (they are network peers, not modules this repo owns):
- A round where approvers hold 2/3 of the drawn set returns `approvers-win` at round 0.
- A split round 0 draws `2K` fresh arbitrators for round 1, excluding round 0's.
- A dispute split in every round ends `unresolved` after exactly `maxEscalationRounds` rounds.
- A pushed ruling stops a running loop and is returned.
