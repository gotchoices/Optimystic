# Matchmaking arrival push — the seeker's receiving end and real renew/withdraw (db-p2p)

Fourth of five tickets (chain in `matchmaking-arrival-push-wire-and-selection`). After this, a seeker built with `createLibp2pMatchmakingTransport` can opt into pushes and receive them. Wiring the receiver into the node factory, and the cohort side's libp2p `send`, are in `matchmaking-arrival-push-wiring-and-e2e`.

## `ArrivalPushReceiver` (`arrival-push-receiver.ts`)

One per node. It holds the walks currently listening, keyed by the seeker registration's correlation id (base64url).

```ts
class ArrivalPushReceiver {
	/** Listen for pushes bound to `correlationId` on `topicId`; the returned channel feeds SeekerWalkClient. */
	subscribe(topicId: Uint8Array, correlationId: string): { readonly channel: SeekerPushChannel; unsubscribe(): void };
	/** Inbound handler body: one encoded ArrivalPushV1 from `from` → an encoded ack, or undefined for no reply. */
	handle(frame: Uint8Array, from: string): Promise<Uint8Array | undefined>;
}
function registerArrivalPushHandler(node: Libp2p, protocol: string, receiver: ArrivalPushReceiver, maxBytes?: number): void;
```

`handle`:

1. Decode with `decodeArrivalPushV1` (bounded by `maxBytes`). A malformed frame → no reply (log). Never throw out of the stream handler, the same discipline as `createMatchmakingQueryHandler`.
2. Verify `signature` over `arrivalPushSigningPayload` against `from`, the peer id the connection authenticated (`verifyPeerSig`). A bad signature → no reply (log). Do not answer `unknown_seeker` to a frame that is not provably from its sender.
3. No subscription for `correlationId`, or a subscription whose topic differs → ack `unknown_seeker`. The pushing member then drops its binding.
4. Otherwise queue the push on that subscription's channel, wake any pending `wait`, and ack `ok`.

The channel: an array queue plus at most one pending waiter. `wait(ms)` resolves on whichever comes first, a queued push or the timer (unref'd, cleared when the push wins). `take()` drains the queue. Cap the queue (e.g. 64 pushes; drop the oldest and log): pushes are advisory and the walk drains the queue on every wake, so only a misbehaving sender fills it. `unsubscribe` resolves any pending waiter and drops the queue.

In-process delivery for a seeker whose slot primary is its own node is just `receiver.handle(frame, selfPeerId)`. The wiring ticket's `send` calls it, with no dial.

## `createLibp2pMatchmakingTransport` changes (`query-transport.ts`)

### Opting in

- New deps: `arrivalPush?: ArrivalPushReceiver` and `pushOnArrival?: boolean`. `pushOnArrival` defaults to `arrivalPush !== undefined`. `pushOnArrival: true` with no receiver throws at construction: a seeker that asks for pushes it cannot receive is a configuration error, and failing loudly beats silently waiting on the safety poll.
- `walkTransport(topicId, options?: { pushOnArrival?: boolean })`: the per-walk override wins over the transport default. `MatchmakingSeekerSession.walk` passes `SeekerWalkRequest.pushOnArrival` through (add the field; `MatchmakingSeekerSessionDeps.walkTransport` gains the same optional second parameter). The voting `QuorumDiscovery` binding keeps the transport default.
- With push on: the walk's `MatchmakingSeeker` is built with `pushOnArrival: true`, so its payload carries its `correlationId`. The transport subscribes to the receiver under `bytesToB64url(seekerState.correlationId)` when the walk transport is built, and exposes `pushes` (the channel). With push off, `pushes` is absent and the walk takes the poll path.
- One correlation id per walk, shared by every tier the walk visits: the binding follows the seeker from tier to tier, and the old tier's binding is dropped once the walk withdraws from it.

### Real renew and withdraw (both paths)

Today `renew` and `withdraw` are documented no-ops. That is fine for polling, because a seeker's own query does not depend on its record. Pushing does: the cohort pushes only to seekers whose record it still holds, and the seeker TTL is 10 s while patience runs from 1 s to minutes. So both become real, on both paths. Polling gains a seeker record that stays alive for collective assembly, and a polite withdraw on escalation, as the doc describes.

- On each `accepted` register reply, remember the live registration: the tier, the topic, the `RegisterV1.correlationId` that was accepted, and the slot primary from the reply's `primary` field. Check its encoding (`bytesKey` in the member engine) and convert it to a peer-id string with `bytesToPeerIdString`. A later register at another tier replaces it.
- `renew()`: return at once if there is no live registration, or if the last renew attempt was less than `seekerTtlMs / 3` ago. The walk calls `renew` on every hang-out wake (every 1 s on the poll path), so the throttle lives here and the walk client stays cadence-agnostic. Otherwise send a signed plain-ping `RenewV1` (`renewSigningPayload`, same correlation id as the accepted register) over the cohort-topic `register` protocol to the slot primary. Outcomes:
  - `ok` → done.
  - `primary_moved` → adopt `newPrimary` for the next renew.
  - `unknown_registration` → log at debug. This is expected while the admission has not yet reached the slot primary by gossip (the walk registers through the FRET-routed member, which can differ from the slot primary, and a gossip round is up to 5 s), and the next renew lands. Do not re-register: the record still exists on the admitting member.
  - A dial or decode failure → log.
  `renew` never throws: a failed keep-alive must not abort the walk.
- `withdraw()`: if there is a live registration, send a signed `RenewV1` with `withdraw: true` to the slot primary (any holder honours a withdraw) and clear the live registration. Best effort: log failures, never throw. The record otherwise ages out by TTL.
- `close()`: `withdraw()`, then unsubscribe from the receiver. Idempotent.
- Self-primary: if the slot primary is this node, route renew and withdraw through a new `MatchmakingSelfServe.renew?(r: RenewV1): Promise<RenewReplyV1>` (the composition root can bind it to the host's `resolveRenew`). If that hook is absent, log and skip, rather than throw as `register` does: a missing keep-alive costs only the push optimisation.

## Edge cases & interactions

- Push for an unknown or finished walk → `unknown_seeker` (test).
- Push signed by a key other than the connection's peer → no reply, nothing queued (test).
- Push for the right correlation id but another topic → `unknown_seeker` (inspection; same branch as unknown).
- A flood of pushes on one subscription → queue capped, oldest dropped, logged (inspection).
- `wait` called with `ms <= 0` → resolves at once (inspection).
- A walk that ends while a `wait` is pending → `unsubscribe` resolves it (inspection).
- A renew racing the first gossip round → `unknown_registration` tolerated (inspection; covered end-to-end by the wiring ticket's mesh test, where the seeker's record must survive past one TTL).
- Escalation: `withdraw` (real now) to the tier being left, then register at `d − 1`. The live registration and slot primary are replaced by the new tier's (inspection).
- Withdraw on a walk that never got `accepted` → nothing sent (inspection).
- The real-socket transport's existing single-tier-0 behaviour (queries go to the tier-0 cohort whatever the walk tier) is unchanged.

## Tests (`arrival-push-receiver.spec.ts`)

Unit-level, against the receiver directly with real Ed25519 keys (no libp2p):

- A valid push for a subscribed correlation id is acked `ok` and returned by the channel's `take()`, and a pending `wait` resolves early.
- An unknown correlation id is acked `unknown_seeker` (doc *Stale push acked `unknown_seeker`*, seeker half).
- A push whose signature does not verify against the sending peer gets no reply and is not queued.

Renew and withdraw over real sockets are exercised by the wiring ticket's integration case; do not mock libp2p here.
