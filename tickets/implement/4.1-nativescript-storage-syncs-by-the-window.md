# NativeScript storage syncs by the window

Second of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). The maintainer's decision (2026-10-15): phones relax by the cohort-size window like any other node, so this backend does **not** sync every write group. It must commit each group atomically, keep write order across a power cut, sync by the group's deadline, and sync at once when the window is 0.

## Today

`SqliteStoreDriver` (`packages/db-p2p-storage-ns/src/sqlite-storage.ts`) is a `RawStoreDriver`: every write is its own autocommit statement, `promote` is the only transaction, `flush()` is a no-op, and `durability` is `'process-crash'`. `applySchema` (`src/db.ts`) opens SQLite in write-ahead-log (WAL) mode with `PRAGMA synchronous = NORMAL`.

## What SQLite already gives, and what it needs

- **Prefix: already kept.** In WAL mode every commit appends frames to one file, each frame checksummed over the frames before it, and recovery stops at the first bad frame. Under `NORMAL`, SQLite syncs the WAL before every checkpoint, so a checkpoint never puts later content in the database file ahead of earlier content. What survives a power cut is a prefix of the committed transactions (SQLite's *PRAGMA synchronous* documentation: WAL under NORMAL "is always consistent", "might roll back following a power loss"). No journal is needed here, unlike the browser and React Native backends.
- **A sync: one commit under `synchronous = FULL`.** In WAL mode, `FULL` syncs the WAL file at that commit. The WAL is one append-only file, so that sync covers every frame before it: every earlier `NORMAL` commit on this database, the key-value store's and the identity helper's included, since all three share one connection. The setting is per connection and can be changed between transactions.

Rejected: `PRAGMA wal_checkpoint(PASSIVE)` as the sync. It also syncs the WAL first, but only when it has frames it may copy, which a read in progress on the same connection can prevent, and it copies pages and syncs the database file too. A `FULL` commit is one documented sync with no conditions.

## Design

### `SqliteDb` gains a synced transaction (`src/db.ts`)

`transaction<T>(fn, options?: { readonly synced?: boolean }): Promise<T>`. With `synced`, inside the mutex slot the transaction already holds: `PRAGMA synchronous = FULL`, `BEGIN IMMEDIATE`, the body, `COMMIT`, and `PRAGMA synchronous = NORMAL` in a `finally` that also runs after a rollback. Both implementations change: `NSPluginDbWrapper` in `src/ns-opener.ts` and the Node test driver in `test/node-sqlite-driver.ts`. Update the `SqliteDb.transaction` doc comment.

### One sync helper (`src/sqlite-sync.ts`)

`syncSqliteDb(db: SqliteDb): Promise<void>`: a synced transaction that bumps one marker row, so there is always a frame to commit. Schema: `CREATE TABLE IF NOT EXISTS durability_mark (id INTEGER PRIMARY KEY CHECK (id = 1), n INTEGER NOT NULL)`, added to `SCHEMA_SQL`; the helper runs `INSERT INTO durability_mark (id, n) VALUES (1, 1) ON CONFLICT(id) DO UPDATE SET n = n + 1`. `CREATE TABLE IF NOT EXISTS` makes it additive to an existing database. Every other sync in the package goes through this helper or a synced transaction that writes real rows.

### `SqliteBatchBackend` replaces `SqliteStoreDriver`

A `BatchBackend` (`packages/db-p2p/src/storage/batch-backend.ts`). Reads (`get`, `rangeRevisions`, `listPendingActionIds`, `listBlockIds`, `approximateBytesUsed`, `storeIdentity`) are the current driver's SQL, unchanged, so the on-disk format does not change. Writes:

- **`commit(entries, { syncWithinMs })`**: one `db.transaction` applying every entry in order, a put as the store's existing `INSERT OR REPLACE`, a delete as its existing `DELETE`, each through `tx.prepare` (never a class-level statement, which would deadlock on the mutex). `deadlines.mustSyncNow(syncWithinMs)` chooses `synced` when the transaction is started; the bookkeeping itself happens inside the transaction body, so the mutex orders it against every other commit and sync:
  - synced: `take()` the cover inside the body, settle it after the commit resolves, and return an already-resolved `durable`;
  - unsynced: `deadlines.defer(undefined, syncWithinMs)` inside the body, and return that `durable`.

  A deadline that passes between choosing and acquiring the mutex only delays that commit's backpressure to the timer, which is due anyway (by inspection).
- **`sync()` and the deadline timer**: take the cover; if it is empty, resolve; otherwise `syncSqliteDb(db)` and settle it.
- **Failure**: any transaction or sync rejecting latches the backend: `failAll`, and every later `commit` or `sync` rejects with `StoreFailedError` carrying the first cause. `WriteGroup` latches above it the same way.
- **`close()`**: disarm the timer only. The handle is shared with the key-value store and the identity helper, so the backend never closes it (keep the existing `NOTE:`). `WriteGroupDriver.close` flushes strictly before calling it, so nothing is left held.
- **`durability`: `'power-loss'`.** Remove the rule-3 `NOTE:` at `durability`; the prefix argument above replaces it, stated once in the class doc.

The reads see a batch as soon as its transaction commits, before it is synced. `BatchBackend` allows that ("MAY reflect a batch earlier"), and `WriteGroupDriver`'s listing merges already deduplicate (by inspection).

`SqliteRawStorage` becomes `new KvRawStorage(new WriteGroupDriver(new SqliteBatchBackend(db, options), options))` with `options: WriteGroupOptions & { setTimer? }`, and redeclares `close` as always present, as `FileRawStorage` does. Export `SqliteBatchBackend` in place of `SqliteStoreDriver` from `src/index.ts`.

### Key-value store and identity

- **`SqliteKVStore`**: writes stay direct autocommit statements (each already survives a process crash and is ordered in the WAL). New `flush()`: when the store has written since its last flush, `syncSqliteDb(db)`; otherwise resolve. `IKVStore.flush` asks only for this store's own writes, and the node orders the block store's flush ahead of the ledger's (`beforeRecord`, from `nodes-apply-the-durability-window`).
- **`loadOrCreateNSPeerKey`**: after inserting a newly generated key, `syncSqliteDb(db)`, so a power cut right after first start cannot give the node a different peer id next time. An existing key is read as today.

## Edge cases & interactions

- **Process crash loses an unflushed group now**, where today each write survives one. Nothing in an unflushed group was reported yet (rule 2), and a group is all or nothing. Say so in the README (by inspection).
- **`PRAGMA synchronous` inside the mutex slot**: an outside-transaction write queued behind a synced transaction runs after `NORMAL` is restored, so no other write pays `FULL` by accident (by inspection). The restore runs after a failed `COMMIT` too (by inspection).
- **Unserialized reads during a synced transaction** read on the same connection, as today; the `NOTE:` on `NSPluginStatement.get` about uncommitted rows is unchanged (by inspection).
- **A strict commit after relaxed ones** takes them into its cover, so one `FULL` commit settles all of them in order (test).
- **The deadline timer firing with nothing held** does nothing (by inspection).
- **Backpressure**: an overdue deadline makes the next commit synced (the helper's rule; covered by its test).
- **`feat-nativescript-storage-moves-to-sqlite-4`** (backlog, GitHub #38) changes the plugin's open, transaction and threading model. That ticket now names this design; whichever lands second keeps the synced transaction and one transaction per group (by inspection there).
- **`debt-ns-sqlite-concurrency-stress-test`** (backlog) would now also exercise synced transactions; nothing to do here.
- **`packages/upgrade-check`** has no NativeScript fixture; nothing to keep green there.

## Tests

In `packages/db-p2p-storage-ns/test/sqlite-storage.spec.ts`, over `node:sqlite` with a `SqliteDb` wrapper that counts `PRAGMA synchronous = FULL` statements, and an injected `setTimer`:

- **Relaxed groups commit unsynced and share one sync when the deadline is due.** Two flushes with `withinMs: 5000` each commit a transaction, issue no `FULL`, and their writes read back from the store; `whenDurable()` is pending. Fire the timer: exactly one `FULL`, then `whenDurable()` resolves.
- **A strict flush after relaxed ones syncs once and settles all of them.** Two relaxed flushes, then a strict `flush()` with writes: exactly one `FULL` in total, and `whenDurable()` has resolved.
- Run the raw-storage conformance suite over the composed `SqliteRawStorage`, persistent (reopen over the same file), as the current spec does for the driver.

No real power-loss test is possible over a live file system; the prefix argument is by inspection.

## `SyncDeadlines` as it landed

`storage-sync-deadlines-are-shared` built `SyncDeadlines` (`packages/db-p2p/src/storage/sync-deadlines.ts`) from the file log's own bookkeeping, and its interface differs from the calls this ticket writes above in these ways:

- **A deadline is taken when the commit is called, not when it runs.** Call `deadlines.deadlineFor(syncWithinMs)` as `commit` is called (`undefined` means strict), and pass that deadline, not `syncWithinMs`, to `defer(item, deadline)` and `mustSyncNow(deadline)`. A commit that waited in the owner's queue past its own deadline then counts as overdue.
- **`mustSyncNow(deadline)` checks the batch's own deadline as well as the held ones**, so it can be called before `defer`. A commit that syncs at once does not have to be deferred: take the cover, sync it together with the new batch, settle the cover, and return an already-resolved `durable`.
- **The timer's sync step passes the time the timer fired.** `onDue` is `(firedAt: number) => void`; the step it enqueues calls `take(firedAt)`, so the timer's own lateness is not reported as the disk running late. Every other `take()` passes nothing.
- **`subject`** (required) is what the `window-overrun` line names as being synced, such as the database path; `log` is the owner's channel.
- **`defer` throws after `failAll`.** An owner that awaits anything between its own failure check and `defer` must check again after the last await, with no await between that check and `defer` (the file log's `commit` does, right after its append).
