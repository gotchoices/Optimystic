# Matchmaking arrival push — the cohort member that sends pushes (db-p2p)

Second of five tickets (see `matchmaking-arrival-push-wire-and-selection` for the chain). This builds the sending side; node wiring and the mesh end-to-end test are in `matchmaking-arrival-push-wiring-and-e2e`.

## The trigger: a record goes from absent to present on this member

The doc's trigger is "a provider `RegistrationRecord` for the topic going absent→present at this cohort" — not renewals, not the arrivals counter. A record reaches a member's store by three paths: local admission (`CohortMemberEngine.accept` → `store.put`), gossip merge (`TransportCohortGossipBus.mergeRecords` → `store.put`), and the rotation handoff pull (`handoff.ts` → `store.put`). All three go through `RegistrationStore.put`, so the hook goes there and nowhere else.

- **db-core**: add a store decorator in `packages/db-core/src/cohort-topic/registration/store.ts`, e.g. `observeRecordAdditions(store, onAdded: (rec) => void): RegistrationStore`. Its `put` checks `getByParticipant(rec.topicId, rec.participantId) === undefined` before delegating, and calls `onAdded(rec)` after the put when it was absent. Every other method delegates. It is substrate-generic: no matchmaking knowledge enters db-core's cohort-topic layer. A listener throw is caught and logged, never propagated into `put` (it would abort a gossip merge or an admission otherwise).
- **db-p2p host**: `createCoordEngine` wraps its `createRegistrationStore()` with the decorator. `CohortTopicHost` gains `onRecordAdded(listener: (engine: CoordEngine, rec: RegistrationRecord) => void): () => void` (idempotent unsubscribe), fanned out from a node-level listener set in `CoordEngineContext`. This is the same subscription shape `StorageRepo.onAnyCollectionChange` uses. A subscription avoids construction-order problems, because the matchmaking wiring is built after the host.

What a renewal touch, a reattach restamp, or a re-merge of a record the member already holds does: nothing, because the record was present. That is how *renewal does not push* holds.

## The driver: `ArrivalPushDriver` (`packages/db-p2p/src/matchmaking/arrival-push-driver.ts`)

A node-level object, independent of libp2p so the mesh harness and unit tests can drive it. Dependencies, all injected:

```ts
interface ArrivalPushDriverDeps {
	readonly selfPeerId: string;                     // compared with the computed slot primary
	readonly slots: SlotAssigner;                    // createSlotAssigner(new RingHash()) — the same rule renewal uses
	readonly sign: (payload: Uint8Array) => Promise<string>;   // node peer key, base64url
	/** Deliver one encoded ArrivalPushV1 to the seeker named by contactHint; resolves the ack frame, or undefined on no reply / failure. */
	readonly send: (contactHint: string, frame: Uint8Array) => Promise<Uint8Array | undefined>;
	readonly config?: ArrivalPushConfig;             // coalesceMs, default DEFAULT_ARRIVAL_PUSH_CONFIG
	readonly clock?: () => number;
	readonly setTimer?: (fn: () => void, ms: number) => () => void;   // default: setTimeout + unrefTimer; returns cancel
	readonly maxBindings?: number;                   // default 4096
}
class ArrivalPushDriver {
	onRecordAdded(engine: CoordEngine, rec: RegistrationRecord): void;   // the host listener
	stop(): void;                                                         // cancel every timer, drop all state
}
```

Take only the parts of `CoordEngine` the driver uses (`servedCoord`, `cohort()`, `records(topicId)`, `topicTraffic(topicId)`) as a narrow interface type, so the unit test can pass a small fake rather than mock the whole host.

### On a record added

1. Decode `rec.appState` with `decodeMatchAppPayload`. Not a matchmaking payload, or a seeker payload → return. (A seeker record arriving changes no push decision; a seeker's binding is read from the store when a provider arrives.) Decode failure → log and return, the same way `handleMatchmakingQuery` skips undecodable records. Factor the record → `LocalProviderRegistration` / `ArrivalPushCandidate` decoding into one helper shared with `query-handler.ts`.
2. Read `engine.records(rec.topicId)`, decode the seeker records into `ArrivalPushCandidate`s, and call `selectArrivalPushTargets(provider, candidates)`.
3. For each selected seeker, compute `slots.assignSlots(seekerParticipantBytes, cohort.cohortEpoch, cohort.members).primary`. Skip it unless that is this node. This is the doc's `primary(participantId, members)` slot hash, computed fresh from the current cohort view. That way a rotation moves push duty with no handoff of push state.
4. For each remaining seeker, look up or create its **binding** under the key `(servedCoord, topicId, seeker participantId, correlationId)`, and enqueue the provider entry (`providerEntryOf`) unless the binding is dead, satisfied, or already holds that provider.
5. Lazy cleanup for this `(engine, topic)`: drop bindings whose seeker record is no longer in `engine.records(topicId)`, or whose record now carries a different `correlationId` (the seeker re-registered). Cancel their timers.

### Binding state (soft, local, never gossiped)

```ts
interface Binding {
	readonly contactHint: string;
	readonly wantCount: number;
	readonly pushed: Set<string>;        // provider participantIds delivered or queued under this binding
	batch: ProviderEntryV1[];
	cancelTimer?: () => void;
	dead: boolean;                        // the seeker answered unknown_seeker
}
```

- *Outstanding need* = `wantCount − pushed.size`. A binding with need 0 is satisfied: further arrivals are not queued to it.
- Bindings are lost when the member restarts or the engine is evicted. Re-created bindings start with an empty `pushed` set, so a new primary may re-push providers the seeker already has. The seeker dedups by `participantId` (doc §Failure mode), so this is harmless.
- Cap: `maxBindings` total across the node. On overflow evict the least recently touched binding (cancel its timer). Add a `NOTE:` tripwire at the cap: if pushes are ever measured missing under load, size the cap from `cap_promote × coord engine budget` instead.

### Coalescing and flush

- The first entry queued into an empty batch arms a timer for `coalesceMs`.
- The batch flushes when the timer fires, **or** at once when the entry just queued brings `pushed.size` up to `wantCount` (the batch now covers the seeker's whole remaining need — `pushed` counts queued entries too), or when the batch reaches `QUERY_LIMIT_MAX`.
- Flush: build the unsigned `ArrivalPushV1` (`topicId`, the engine's current `cohortEpoch`, `correlationId`, the batch, `engine.topicTraffic(topicId)`), sign `arrivalPushSigningPayload`, encode, and call `send(contactHint, frame)` without awaiting it in the arrival path (`void` with a `.catch` that logs). Clear the batch before sending; a concurrent flush for the same binding is allowed.
- Do **not** call `engine.recordQuery`. Pushes are not `QueryV1`s and must not inflate `queriesPerMin` (doc *Contention-signal interaction*).

### Ack handling

- `{ result: "ok" }` → nothing.
- `{ result: "unknown_seeker" }` → mark the binding dead and cancel its timer. A later record for that seeker with a different `correlationId` produces a new binding (the key differs), so a seeker that re-registers is pushed again.
- No reply, a decode failure, or a thrown `send` → log at debug and drop that batch. The binding stays live: the next arrival tries again. No retry and no replay buffer (doc: the push is advisory; the seeker's safety poll recovers). A seeker that has gone away stops renewing, so its record and its binding leave within one seeker TTL; that bounds the wasted sends.

## Edge cases & interactions

- **Renewal vs fresh arrival**: a touch of a held provider never reaches `onAdded` (decorator semantics). Test.
- **Provider evicted on this member and then re-merged from a sibling's touch**: it reaches `onAdded` again. The `attachedAt` rule and the per-binding `pushed` set stop a repeat push to the same binding. Inspection.
- **Bulk catch-up** (a new member receiving the whole record set, or a handoff pull): providers older than each seeker are filtered by the selection rule from the prereq. Inspection.
- **Seeker re-registered** (new `correlationId`): the old binding is dropped by the lazy cleanup and a new one is created. Test, as part of the `unknown_seeker` test.
- **Cohort rotation mid-batch**: the queued batch flushes from the old primary with the epoch read at flush. The new primary starts fresh. Duplicates are deduped by the seeker. Inspection.
- **The seeker is this node** (its slot primary is itself): `send` is the binding's job (the wiring ticket delivers in-process). The driver does not special-case it.
- **Listener throws inside the store decorator**: caught and logged; the gossip merge or admission completes. Assertion at the seam (try/catch), no test.
- **`stop()`** cancels every timer, so a stopped node leaves no timer behind (timers are also unref'd so they never hold a process open).
- **Engine evicted from the registry**: its bindings go stale. They are cleaned up lazily, by the cap, or when a flush finds the seeker record gone (check `engine.records` again at flush; skip the send if the seeker is no longer held).

## Tests (`packages/db-p2p/test/matchmaking/arrival-push-driver.spec.ts`)

Drive the driver with a fake engine (a real `createRegistrationStore` wrapped by the new decorator, a fixed cohort view, a constant traffic snapshot), a fake clock and timer, and a recording `send`:

- *Renewal does not push*: put a provider record, flush, then put the same participant again with a newer `lastPing` → exactly one push total.
- *Coalescing*: three providers arriving within `coalesceMs` → one `ArrivalPushV1` with 3 providers per selected seeker, not three pushes. A second case: a seeker with `wantCount = 1` gets its push without waiting for the timer.
- *Only the slot primary pushes*: with two drivers for two members over the same records, each selected seeker is pushed by exactly one of them.
- *Stale push acked `unknown_seeker`*: the ack marks the binding dead (no further pushes to that correlation id); after the seeker's record is replaced with a new `correlationId`, the next arrival pushes again.
