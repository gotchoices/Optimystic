# Why

A coverage map of this repository (2026-09-15) found that a member leaving *mid-session* and returning is tested at two machines only, in the real-socket lifecycle and relay specs. Three, four and five machines cover only boot-time absence: the member was never there, so nothing was missed while it was gone, and nothing has to heal when it returns. Restarting more than one machine is likewise tested only at two.

That is the gap where a phone-shaped deployment lives. A member goes to sleep, work continues without it, and it comes back needing everything it missed. The maintainer's current focus is transactions working at every node count, especially the low ones.

# What to build

`member-leaves-and-returns.spec.ts`, on the in-process mesh harness so it runs in plain `yarn test`, at **three machines**, using the same production-shaped configuration the prereq sweep establishes (default replication factor plus a declared `repairCorroborationClusterSize`, not the `clusterSize: N` shortcut). Phases over shared state, each failing fast and naming its predecessor if that failed:

1. **Whole group.** All three commit rows; every node reads every row.
2. **One leaves.** C becomes unreachable mid-session. A writes. Assert the documented outcome for three machines with one member down, consistent with the prereq sweep: the promise bar is all three, so the write is refused, with the refusal's typed shape asserted. Record, without asserting, how long the refusal took.
3. **The group works while C is away**, if anything is permitted to: whatever the previous phase established as allowed, do it and assert it, so the rest of the scenario starts from a real state rather than an empty one.
4. **C returns.** After reconnection, C reads every row committed while it was gone, without a manual repair step. This is the phase that has never been tested above two machines: assert that C's *own storage* holds those blocks, not merely that it can fetch them, since a fetched copy is not a healed replica.
5. **Restart two of the three** over their storage, C included. Every acknowledged row is readable on each; a fresh write from each of the three is readable on the other two.

Add a two-arm variant of the leave step if it costs little: the member that leaves is (a) one that has written, and (b) one that has only read. A member holding blocks nobody else wrote is the interesting case for healing.

# Edge cases & interactions

- **Healing has a trigger and a bound.** The returning member is brought current by the cohort-growth reaction, by read repair, or by both. Wait on the property (C's storage holds the block) with a bounded, named wait, and if a documented throttle makes the wait long, say which and how long in the handoff rather than extending the timeout silently.
- **Do not assert the two-machine lone-survivor rule anywhere.** It is under design — `backlog/more-design/6.5-partition-healing.md`, with the maintainer's decision recorded there that the CRDT sync layer is the intended fix. This spec is three machines precisely so it can assert a documented rule instead.
- **Restart means over the same storage and identity.** A restarted node that comes back with a fresh identity is a different scenario, and not this one.
- **A failure is a finding.** If a returning member never heals, keep the assertion and file a `fix/` ticket with the log evidence; do not add retries until it passes.
- **Runtime** stays in the fast lane: measure it, report it, and prefer fewer rows to a longer timeout.
