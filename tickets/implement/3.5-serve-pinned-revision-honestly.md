# `serveBlockArchive` labels pinned content with the wrong revision

Supersedes `fix/block-archive-rev-pin-is-a-no-op`, whose diagnosis was written before
`GetBlockResult.materializedRev` landed and is now wrong in the direction that matters. Read the
corrected account below rather than that ticket's.

## What the old ticket got wrong

It claimed `StorageRepo.get` ignores `context.rev` entirely, so a pinned request is answered with
the newest revision, "correctly labelled ... nothing is *mis*-labelled". Both halves are false at
HEAD:

- `StorageRepo.get` **does** honour the pin. `storage-repo.ts:308` calls
  `blockStorage.getBlock(context?.rev)`, which materializes the highest committed revision at or
  below the pin and reports it as `GetBlockResult.materializedRev`.
- So the content **is** pinned, and only the label is not. `serveBlockArchive` builds the archive
  from `entry.state.latest` — the serving node's *newest* revision — while `entry.block` holds the
  *pinned* content. The archive therefore pairs old bytes with a new revision number and a new
  action id.

That is a mislabel, not a benign substitution, and it is the difference between "the restore was
useless" and "the restore corrupted local storage".

## Reproduction (verified)

Two revisions of one block through the real `StorageRepo` commit path — rev 1 content `ONE` under
action `a1`, rev 2 content `TWO` under action `a2` — then `serveBlockArchive(repo, BLOCK, 1)`
returns:

```
{"blockId":"block-1",
 "revisions":{"2":{"action":{"actionId":"a2","transform":{"insert":{... "items":["one"]}}},
                   "block":{... "items":["one"]}}},
 "range":[2,3]}
```

Revision key `2`, action id `a2`, **rev 1's bytes**. The underlying read is correct — `repo.get`
with `context.rev = 1` returns `{block: ONE, materializedRev: 1, state.latest: {rev: 2, actionId:
'a2'}}` — `serveBlockArchive` just reads the wrong one of those two numbers.

### The corruption this causes (also verified)

`BlockStorage.getBlock(rev)` reaches `ensureRevision`, which calls `restoreCallback`, which reaches
a peer's `serveBlockArchive`, and whose answer is written by `saveRestored`. `saveRestored` writes
`saveMaterializedBlock(blockId, action.actionId, block)`, keyed by action id. So an asker that
already holds a perfectly good rev 2 and merely wants rev 1:

```
ASKER rev2 BEFORE:            {block: items:["TWO"], actionRev:{rev:2, actionId:"a2"}}
ASKER asks peer for rev 1  →  archive keyed 2/a2 carrying ONE  →  saveRestored
ASKER meta AFTER:             {"ranges":[[2,3]], "latest":{"actionId":"a2","rev":2}}
ASKER rev2 AFTER:             {block: items:["ONE"], actionRev:{rev:2, actionId:"a2"}}
```

Its own rev 2 now reads back as rev 1's content, silently and permanently. No error is raised, and
`meta.ranges` is unchanged — the requested rev 1 was never recorded as held, so every later read of
rev 1 re-fetches and re-corrupts.

To recreate as a regression test: `MemoryRawStorage` plus `StorageRepo` for both sides, wire the
asker's `BlockStorage` with `restoreCallback = (id, rev) => serveBlockArchive(srcRepo, id, rev)`,
land rev 1 and rev 2 on both, then set the asker's `meta.ranges = [[2, 3]]` to forget rev 1 and call
`getBlock(1)`. `packages/db-p2p/test/block-archive-proof.spec.ts`'s `landRevision` helper already
does the commit-path setup.

## Root cause, and why it is a representation problem

`GetBlockResult` describes the newest revision as an `ActionRev` (`state.latest`) but the revision
the content was actually materialized at as a bare `number` (`materializedRev`). A site that needs
the `(rev, actionId)` **of the content it is holding** — which is exactly what a block archive entry
is — has no field to read, so it reaches for `state.latest`. `serveBlockArchive` is the site where
that costs correctness; `sourceBlockMeta` (`cluster/block-transfer-service.ts:65-82`) is a site that
already noticed the hazard and defends against it by *dropping* the metadata when `materializedRev
!== latest.rev`, logging "pinned read — refusing to mislabel content".

Making the materialized revision a first-class `ActionRev` makes the bad pairing unrepresentable at
every such site rather than patched at one. The action id is already in hand and thrown away:
`BlockStorage.getBlock` returns `{block, actionRev}`, and `storage-repo.ts:392` keeps only
`blockRev.actionRev.rev`.

## Two arms, in this order

The guard is unconditional and lands first; the representation change is what stops the guard from
firing on every legitimate historical restore. Landing only the guard is an acceptable partial
outcome (corruption is dead, historical restore is disabled); landing only the representation change
is not.

### Arm 1 — fail closed at `serveBlockArchive`

Refuse to serve rather than serve a mislabel. When the read reports a `materializedRev` that
disagrees with the `state.latest` the archive would be labelled with, return `undefined` — the
"holds nothing" answer every caller already handles (`ReconcileBlockDeps.fetchArchive` folds
unreachable into it, and `ensureRevision` turns it into a clean `revision N not found during restore
attempt` throw instead of a silent overwrite). Mirror `sourceBlockMeta`'s log line so the two
refusals read alike.

This arm alone must make the reproduction above stop corrupting the asker.

### Arm 2 — carry the materialized revision as an `ActionRev`

Replace `GetBlockResult.materializedRev?: number` with the revision *and* its action id, so
`serveBlockArchive` can label the pinned content with its own revision and the guard above stops
firing for a peer that genuinely holds the requested revision.

Prefer replacing the field over adding a sibling `materializedActionId?: ActionId`: two
independently-optional fields that can disagree is the same class of defect one rung down.

Measured scope: 32 non-comment references across 9 files, counted with

```bash
grep -rn "materializedRev" packages/*/src packages/*/test --include=*.ts | grep -vE ":\s*(//|\*|/\*)" | wc -l
```

Most are mechanical `.rev` additions:

- `packages/db-core/src/network/struct.ts` — the definition and its doc comment.
- Producers: `packages/db-p2p/src/storage/storage-repo.ts` (2 sites, lines 359 and 392 — the action
  id is already on `blockRev.actionRev`), `packages/db-core/src/testing/test-transactor.ts` (8
  sites).
- Consumers: `packages/db-core/src/transactor/transactor-source.ts:93` (uses the number only),
  `packages/db-p2p/src/cluster/block-transfer-service.ts` (comparison only — and once
  `serveBlockArchive` can serve a pinned revision honestly, re-read whether `sourceBlockMeta` should
  still drop the meta or now label it correctly; a push is a different wire from a repair fetch, so
  keep dropping unless there is a reason not to).
- Comment-only mentions that must stay accurate: `network-transactor.ts:241-247`,
  `repo/coordinator-repo.ts:671`.

Note also that `serveBlockArchive`'s proof lookup (`servableProof(repo, blockId, latest)`) must
follow the served revision, not `state.latest` — it is already structured to take whatever
`ActionRev` it is handed, so passing the corrected value is the whole change. Without it, a pinned
serve would attach the newest revision's proof to older bytes, which passes
`verifyBlockCommitProofClaim` and fails `verifyBlockCommitProofContent` — a strictly worse artifact
than no proof at all.

## Expected behaviour

- A peer asked for revision N serves revision N labelled N, or serves nothing. It never serves
  content from one revision under another revision's number or action id.
- A peer asked for no revision serves its latest, byte-identical to today.
- `SyncService`, the mesh harness, and both `libp2p-node-base.ts` latest-revision consults (which
  pass `rev: undefined`) behave identically.
- A restore that cannot be satisfied fails loudly at `ensureRevision` rather than writing a wrong
  answer into local storage.
