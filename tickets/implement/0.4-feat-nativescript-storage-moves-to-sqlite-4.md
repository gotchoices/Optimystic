# NativeScript storage moves to `@nativescript-community/sqlite` 4.x

GitHub #38 (kjeib), also gotchoices/sereus#45 point 3. `@optimystic/db-p2p-storage-ns` requires the plugin at `^3.5.0`. This ticket requires it at `^4.1.0`.

## Why

Measured by the reporter on 3.x (NativeScript 8.9, V8, a Galaxy S7 and an Android emulator):

- A bound or returned blob crosses between JavaScript and Java one element at a time, about 10 µs each on the S7, so a 16 KB blob costs 109–170 ms each way against about 1 ms copied in bulk. Every block, revision, action and proof this storage writes is a blob.
- Every statement runs on the JavaScript thread, which also runs libp2p, Noise and yamux: 2.9 ms per 1 KB autocommit write and 4.1 ms per 1 KB read on the S7.
- A bare database name opens through the foreground activity, which may not exist yet at launch, and intermittently fails with "Cannot read properties of undefined (reading 'openOrCreateDatabase')".
- `ON CONFLICT … DO UPDATE`, which the key-value store and the sync's `durability_mark` bump use, fails on Android 8, whose platform SQLite is 3.18.

## What was run on a device

The reporter ran `db-p2p-storage-ns` 1.20.1, unmodified, with the plugin forced to 4.1.0 (GitHub #38 comments; `gh issue view 38 --comments`). Galaxy S7, Android 8.0, NativeScript 8.9, so the plugin's JNI bridge:

| Check | Result |
|---|---|
| Opens through `openOptimysticNSDb` | works, `journal_mode` = `wal`, SQLite 3.50.1 (bundled by the plugin) |
| `ON CONFLICT … DO UPDATE` | works |
| `SqliteRawStorage` save, `flush()`, read back | works |
| Write, then `am force-stop` within milliseconds of the commit resolving | 10 of 10 marker rows survived 5 kills: one autocommit row and one `synced: true` row per cycle |
| 2,003 point reads interleaved with a 2,000-row transaction | no errors; the reads see the transaction's uncommitted rows |
| App boot on databases written by 3.5.9 | opened and ran |

Nothing in this repository runs NativeScript on a device. **Not run by anyone yet:** a long session with real network traffic; iOS; the Node-API binding NativeScript 9.1+ selects; a power cut (a force-stop kills the process only). The handoff and the release notes must say so.

## Design

The reporter's test ran the current code unchanged, and that is the design: **change as little as the plugin's new contract requires, so what ships is what was tested.** Each migration point, checked against the plugin's source (4.1.1: `sqlite-core/database.js`, `core/db.c` in the plugin's repository):

| Point | Finding | Action |
|---|---|---|
| The open is asynchronous | `openOrCreate` returns at once. A failed open rejects `db.ready` and also fails the first request with the same error, so today `applySchema`'s first read already rejects `openOptimysticNSDb`. Nothing goes unnoticed, but only by that accident. | `await raw.ready` before the wrapper is built, so the open states its own failure. Still `openOrCreate`, the call the reporter ran, rather than `openOrCreateAsync`, which does the same. |
| `threading` ignored, `getVersion` / `setVersion` async, plugin's `wrapDb` gone | This package uses none of them. `user_version` goes through a pragma; `wrapNSPluginDb` is our own function. | Nothing. |
| Calls on one `db` during a `transaction` join it | That applies only to the plugin's own `db.transaction`, which sets `activeTx`. The wrapper never calls it: it issues `BEGIN IMMEDIATE` and `COMMIT` as ordinary `execute` calls, so `activeTx` stays 0 and the native scheduler runs every request in arrival order on the database's one thread (`eligible` in `core/db.c`). | Keep the wrapper's raw transaction. See below. |
| `SqliteBatchBackend.commit` could use `batch()` | Not run by the reporter, and a trap in it: see the backlog ticket. | Not in this ticket; parked as backlog `feat-nativescript-storage-commits-a-write-group-in-one-native-call`. |
| Parameters bound with their real types | `SqliteParam` allows only string, number, `Uint8Array` and null. Every number this package binds is `rev`, against an INTEGER column, and no string is compared with a numeric column. | Nothing. |
| Blobs returned natively | Rows hold a copied `Uint8Array` (`u8.slice`), so `instanceof Uint8Array` in `identity.ts` and the casts in `sqlite-storage.ts` hold, and a row may be kept after the call. | Nothing. |

**The connection mutex and `transaction(fn)`, re-derived.** The native queue orders single calls; it does not keep a *sequence* of calls together. Two `transaction` bodies on one connection would still each send `BEGIN`, the second would fail, and its `ROLLBACK` would discard the first's open writes, exactly the cross-rollback the mutex closes. A plain write between another body's `BEGIN` and `COMMIT` would land inside that transaction and share its fate. So the mutex stays, for the same reason it has now, and matters more: on 3.x the JavaScript thread was blocked during each statement, while on 4.x every statement is a real yield, so other callers run between a body's statements every time. Statements bound to the open transaction still bypass the mutex (their body holds the slot), so the deadlock reasoning on `SqliteDb.transaction` is unchanged. Reads stay off the mutex, so a read does not wait for a whole transaction body; it waits for the statements queued ahead of it, and lands between the body's statements on the same connection, seeing its uncommitted rows. That is what the reporter measured, and what the `NOTE` on `NSPluginStatement.get` already accepts.

**Why not the plugin's `db.transaction`.** It would not remove the mutex: the plugin's transaction joins a second concurrent `transaction` call into the first, so one body's failure would roll the other back. It would have to take the place of `runTransaction`, whose `PRAGMA synchronous = FULL` must run outside the transaction (SQLite refuses to change it inside one) and be restored after the rollback, the behaviour `nativescript-storage-syncs-by-the-window` built. It buys nothing here, and it was not what the reporter ran.

**The synced transaction survives unchanged**, since `runTransaction` is untouched. The reporter's kill test exercised it, though a process kill does not test the sync itself. That a `FULL` commit survives a power cut still rests on SQLite's write-ahead log, as the README states.

**`journal_mode = WAL` stays in `applySchema`.** The plugin turns WAL on by default on Android only; iOS relies on this pragma.

**Peer range: `^4.1.0`, not `^3.5.0 || ^4.1.0`.** Tradeoff: a host on 3.x has to move in the same upgrade, and npm 7+ reports a peer conflict until it does. Keeping 3.x in the range would advertise a store whose key-value writes fail on Android 8, the blob and thread costs this ticket exists to remove, and a code path nobody here can test. NativeScript 8 stays supported: the umbrella package brings `sqlite-bridge`, so a host needs nothing extra. 4.0.x is left out because nobody ran it. Widening later is a one-line change. There is deliberately no `devDependencies` entry: the plugin needs `@nativescript/core` and native libraries, and the package's types re-declare the surface it uses.

**The test driver runs the production wrapper.** `test/node-sqlite-driver.ts` today carries `NodeSqliteWrapper`, a hand-kept copy of `NSPluginDbWrapper`, so no test has ever run `ns-opener.ts`, and its statements execute synchronously, which is the 3.x shape. Replace the copy with a stand-in for the plugin itself: an object implementing `NSPluginDb` over `node:sqlite` whose every call resolves later (`setImmediate`), strictly in the order made, as 4.x's one native thread does. Hand it to the production opener. The existing suite then exercises the real wrapper, mutex and transaction protocol under real yields between statements, with no new specs, and one duplicate class goes away. `node:sqlite` stays the engine, and the plugin itself is still never loaded.

```ts
// ns-opener.ts; exported for the test driver, not from index.ts
export interface NSPluginDb {
	readonly ready: Promise<void>;
	execute(sql: string, params?: ReadonlyArray<unknown>): Promise<unknown>;
	get(sql: string, params?: ReadonlyArray<unknown>): Promise<Record<string, unknown> | null | undefined>;
	select(sql: string, params?: ReadonlyArray<unknown>): Promise<Array<Record<string, unknown>>>;
	close(): Promise<void>;
}
export interface NSPluginModule {
	openOrCreate(path: string): NSPluginDb;
}

/** `openOptimysticNSDb` once the plugin is loaded. */
export async function openOverPlugin(plugin: NSPluginModule, name: string, version: number): Promise<OptimysticNSDBHandle> {
	const raw = plugin.openOrCreate(name);
	await raw.ready;
	const wrapped = wrapNSPluginDb(raw);
	await applySchema(wrapped, version);
	return wrapped;
}
```

The stand-in keeps the two things specs use. `onExec` fires for each `execute` called without params: the wrapper's `exec` statements, and each transaction's pragmas, `BEGIN IMMEDIATE`, `COMMIT` and `ROLLBACK`. Statement `run` always passes an array, which is how the two are told apart. A throw from `onExec` rejects that call, which is how `failSyncs` in `sqlite-storage.spec.ts` works. `exec` bodies now arrive split into statements; the specs only filter for single statements, so that is safe.

## Tests

- `test/ns-opener.spec.ts`, one test: **a failed open rejects with the plugin's error and runs no statement.** The stand-in plugin's `ready` rejects with a known error while its `get` and `execute` would succeed and record calls. Expect `openOverPlugin` to reject with that error and the recorded calls to be empty. This pins the case the ticket singles out, the one case the reporter's run did not reach.
- No other new test: the suite moving onto the production wrapper is the rest of the coverage. If a spec turns out to rely on a statement finishing within a microtask, have it await the promise it means rather than making the stand-in synchronous. `settles` in `sqlite-storage.spec.ts` uses a 10 ms race; widen it only if it actually flakes, and say so in the handoff.

## Edge cases & interactions

- **Failed open:** the test above. The handle of a failed open is dropped unclosed, as the plugin's own `openOrCreateAsync` drops it.
- **A failed `applySchema` after a good open** leaves the connection open, as it does on 3.x, and on 4.x that also keeps its native thread. Add a tripwire at the site: `// NOTE: a failed schema leaves this connection open; if a host ever retries the open in a loop, close it here.`
- **Two concurrent transaction bodies, and a plain write racing a rolling-back body:** `sqlite-transaction-serialization.spec.ts`, now through the production wrapper with real yields.
- **A statement inside a body does not re-take the mutex:** inspection; a deadlock would hang the suite.
- **A read during a body:** the `NOTE` on `NSPluginStatement.get`, extended to say that on 4.x the read lands between the body's statements in queue order. The overlay reasoning in that note is unchanged; the reporter measured the behaviour.
- **Synced commit, pragma restored after a failure, latch on a failed sync:** the existing `sqlite-storage.spec.ts` and `sqlite-kv-store.spec.ts` cases.
- **A commit's deadline decision is made before the mutex** (`SqliteBatchBackend`'s class comment). Waiting for the mutex now takes real time on a busy phone, so a late `FULL` is likelier, but the comment's reasoning holds: it only delays that commit's backpressure to the timer. Inspection.
- **`close()`:** 4.x refuses new calls at once and runs what is queued. A body still running when the handle closes fails on its next statement, and the README already requires closing the storage first. Inspection.
- **Existing databases on Android:** 3.x's `activity.openOrCreateDatabase(name)` and 4.x's `getApplicationContext().getDatabasePath(name)` name the same file, and a full path is used as given. The reporter booted on 3.5.9 data, through whichever form their app uses.
- **Existing databases on iOS, by bare name:** a real change. 3.x left a bare name relative to the process's working directory (`getRealPath` returns it unchanged), while 4.x puts it in the documents folder. An app that opened by bare name under 3.x would find no database after the move, which means a new, empty store and a new peer identity. Read from the plugin's source, not run; the release note states it. A full path is unaffected.
- **A result larger than 512 KiB on the JNI bridge:** the bridge reuses one arena for smaller results, but a larger one arrives through a fresh direct `ByteBuffer` handed to `ArrayBuffer.from` (`RESULT_ARENA_SIZE` in the plugin's `NativeSqlite.java`, and the `dataLen === -2` arm in `sqlite-core/platform.android.js`). The reporter's own 3.x patch overflowed Android's 51,200 JNI global references that way on a fast phone, by doing it per blob. Here it takes a single block near or over 512 KiB per read (`BLOCK_TARGET_BYTES` is 1 MiB), or `listBlockIds` over a large table. Fine now; add a tripwire at `NSPluginStatement.all`, naming the condition: a node on NativeScript 8 reading thousands of such results between garbage collections.
- **`nativescript-storage-syncs-by-the-window`:** its behaviour holds by keeping `runTransaction`, one transaction per write group, and `syncSqliteDb`.
