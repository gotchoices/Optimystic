# A cancel that misses the approval bar strands the writer's pending record

Reported by sereus (sereus-sam, 2026-10-12) on 1.13.0; their write-up is `C:\projects\sereus\tickets\blocked\optimystic-failed-cancel-strands-the-writers-pend-record.md`.

## What happens

A three-member group's promise bar is all three (`ceil(3 × 0.75)`), so one silent member sinks every cluster transaction. Member C answers a write's pend (and applies it), then goes silent:

1. The write's commit fails at its promise round: `Failed to get super-majority: 2/3 approvals (needed 3, 0 rejections)` — both the one-round commit and the tail-then-sweep fallback.
2. `NetworkTransactor.dischargeCancel` runs its rounds; every cancel is itself a cluster transaction and fails the same way, so no member drops its pending record. `dischargeCancel` throws, the caller (`TransactorSource.transact`) lets the commit's error win, and the failed cancel is forgotten.
3. C returns. Nothing sends the cancel again. Every member that holds the record (A, B and C in the reproduction) votes `held` on every later pend of the block; every later write fails with `pending conflict: block(s) held by unresolved rival action(s) <the stranded action>`.

## Reproduction (verified)

`packages/db-p2p/test/failed-cancel-does-not-strand-the-writers-pend.spec.ts`, on the production-shaped three-machine mesh (`test/util/node-count-mesh.ts`), one transactor per writer for the whole spec (the shape the Quereus plugin's `CollectionFactory` gives a host — it caches one transactor per key). C is made unreachable on the first delivery of the write's commit (`MeshFailureConfig.onClusterDelivery`), after it applied the pend. Phase 2 shows the stranded records on A, B and C; phase 3 (C back, A writes the same row) fails today with `SyncRetryExhaustedError … held by unresolved rival action(s)` after ~16 s.

Hypothesis tested: with C back, one `transactor.cancel` for the stranded action, sent before phase 3's write, cleared the record on all three members and the write landed (run as a throwaway variant of the spec). So re-sending the cancel once the group can approve it is the whole repair.

Run: `node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/failed-cancel-does-not-strand-the-writers-pend.spec.ts"` from `packages/db-p2p` (build db-core first; the freshness guard enforces it).

## The safety question — settled from the code

*Can a cancel sent after this failure, or applied by any member at any time, turn into a divergence?* No, in every shape:

- **A promise-round shortfall proves the commit applied nowhere.** `ClusterCoordinator.executeTransaction` throws `Failed to get super-majority` (and the held / conflict / validator-rejection / expiry refusals) after the promise round and before `commitTransaction`. A member signs a commit only on seeing a super-majority of approved promises, and applies only on a commit majority; the record never carried either, and the commit-retry timer is armed only for records that reached a commit majority. So the reported failure left nothing of the commit anywhere.
- **Even where a commit may have landed, a cancel cannot diverge anything.** A cancel deletes only the cancelled action's pending records and never moves a revision (`operationsConflict` in `packages/db-p2p/src/cluster/race-resolution.ts` — a cancel-only message commutes with every other action). The three timings at `NetworkTransactor.cancelAbandonedSweepBlocks` cover a cancel racing a decided commit: a member that applied has no record left; a member that receives the decided commit after the cancel meets a missing pend and reconciles from the holders. A write that may have landed is the torn-action case `Collection.completeOwnEntry` owns, not this one.

So no `blocked/` question: re-sending a cancel later is safe whenever it arrives. The one thing that is NOT safe is re-sending it after the writer has pended the **same action id** again (`Collection.syncAttempts` retries, and `Collection.completeOwnEntry` re-sends, under one action id): the new pend overwrites the record on the blocks it names, and a late cancel would delete that live pend. The writer is the only party that knows when that happens, which is one reason the fix sits on the writer (below).

## Design

**The writer keeps a cancel it could not discharge, and re-sends it.** `NetworkTransactor` (the single funnel every cancel goes through: `TransactorSource.transact`, `Collection`'s own cancel, `TransactionCoordinator`'s cancel phase, `cancelAbandonedSweepBlocks`, and `pend`'s self-cancel) remembers, per action id, the blocks `dischargeCancel` left outstanding when it gave up, and:

- **Before every pend, discharges the owed cancels that overlap it.** For each owed action (other than the one being pended) that names any of the pend's blocks, run one bounded cancel attempt for that action's owed blocks first (one round, within `abortOrCancelTimeoutMs` — not the six-round loop, since a cohort still unable to approve the cancel cannot approve the pend either). Discharged blocks leave the owed set; a failure is logged and the pend proceeds as it does today. This is what makes the writer's own next write to the block (the reported case, and the reproduction's phase 3) clear its leftover first.
- **Re-sends on a backoff timer while anything is owed**, so writes from *other* machines, which the writer's records also refuse, are freed without waiting for this writer to write the block again. One timer per transactor, armed only while the owed set is non-empty; suggested 1 s doubling to a 30–60 s cap, retrying for the transactor's life. The timer is `unref`'d where the platform has it (`timer.unref?.()` — browsers and React Native have no `unref`; stay cross-platform) and injectable (the `ClusterCoordinatorClock` seam in `packages/db-p2p/src/repo/cluster-coordinator.ts` is the precedent) so a unit test needs no wall-clock wait.
- **A pend of the same action id supersedes the owed cancel for the blocks it names** — drop those blocks from the owed entry before sending the pend, and do not let an owed-cancel attempt for that action be in flight while its pend goes out (await or skip it). Blocks of the old attempt the new pend does not name stay owed.
- **Bounded.** Keyed by action id with a size cap (e.g. 256); evicting an entry logs the action and its blocks, since eviction re-opens exactly this wedge.
- `dischargeCancel` still throws as today — callers' verdict-ordering rules (docs/repository.md: the cancel failure rides beside the original error) are unchanged. Recording the owed entry happens inside `dischargeCancel` before the throw, from its own `outstanding` list, so no caller has to remember to.

Put the bookkeeping and timer in their own small module (`packages/db-core/src/transactor/owed-cancels.ts` or similar): `network-transactor.ts` is 1556 lines (`wc -l`), and this is a single-purpose concern.

Log lines worth having: `cancel:owed` (action, blocks, why), `cancel:owed-discharged` (action, attempts, how long it stood), `cancel:owed-evicted`.

### Alternatives considered and rejected

- **Apply the cancel to the coordinator's own storage at once (sereus's first proposal).** Safe by the argument above, but does not close the instance: B (and C, when it applied the pend) still hold the record and vote `held`, and at three members one such vote denies the bar. It would also add a fifth remover to the four docs/repository.md enumerates, and leave a cancel that is half applied across the group. Not needed once the re-send exists.
- **Have the coordinating node own the retry (`ClusterCoordinator`, re-running the cancel transaction on its retry timer).** It has the right lifecycle and survives the writer dying, but it cannot see the writer re-pend the same action id through itself or another coordinator, so its late cancel can delete a live retry's pend. The dead-writer case stays with backlog `debt-unpromotable-pending-records-need-a-sweep`. Note also that `takeOwedRecords` cannot carry this cancel: it carries only records that already reached a commit majority, and this one never did.
- **Members apply a cancel on first sight, at the promise vote.** Would drop the records of every member the failed cancel reached, but not of the silent member that applied the pend before going silent, so the re-send is needed anyway — and it changes consensus semantics for every cancel.

## Docs

- `docs/repository.md` *A pending record's lifetime is bounded by its writer*: the sentence "Budgets are finite, so a fault outlasting one still strands the record" becomes: a cancel that runs out of budget is kept by the writer's transactor and re-sent before its next pend of those blocks and on a backoff timer, for the transactor's life; only a writer that exits first strands it (the backlog ticket). Add the safety argument in one or two sentences (a cancel commutes with every other action; a late one is safe except over a re-pend of the same action id, which the transactor supersedes).
