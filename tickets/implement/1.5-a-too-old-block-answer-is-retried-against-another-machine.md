# A below-floor block answer earns a retry against a different coordinator

## Background

The prerequisite ticket gives a collection a per-block **floor**: after a refresh walks a log entry saying "revision *r* changed block X", a read of X at a context at or above *r* must come back materialized at *r* or later. An answer below that is a **below-floor answer**. The prerequisite makes sure such an answer is never kept in memory, and — when nobody better can be asked — returns it uncached.

In the downstream failure that motivated both tickets, somebody better *could* be asked. Reader B picked **itself** as coordinator for the data block, served its own revision-6 copy inside its read-repair window, and machine A — one hop away, holding revision 7 — was never asked. `NetworkTransactor.get` already has the machinery to ask someone else: a second-chance round that re-resolves the coordinator with the first one excluded (the passing downstream trace shows it as `findCoordinator:start … excluded=[self]`). It runs for answers flagged `unavailable` or `unconfirmedAheadRev`. A below-floor answer is not flagged — only the asker knows the floor — so it counts as authoritative and the round never runs.

`repro: static`: the missing retry is read off `NetworkTransactor.get`'s `isAuthoritative`; confirm with the spec described below before changing anything (it should fail at HEAD by returning the first peer's revision-1 block).

## Change

- **Let the floor reach the transactor.** Add an optional per-block minimum revision to `BlockGets` (for example `floors?: Record<BlockId, number>`), filled by `TransactorSource.tryGet` for a block with an applicable floor. It is a client-side hint: `NetworkTransactor.get` builds its own `{ blockIds, context }` message for `getRepo(...).get`, so **nothing new goes on the wire in this ticket**, and an `ITransactor` that ignores the field (`TestTransactor`, the reference peer's) stays correct because `TransactorSource` still does the final check.
- **A below-floor entry is not an answered batch.** In `isAuthoritative`, an entry carrying a block whose served revision (`materialized?.rev ?? state.latest?.rev` — reuse `servedRevision`) is below the block's floor fails the test, exactly like `unconfirmedAheadRev`, and so earns the existing retry round with the answering coordinator excluded. One extra round at most — the round is already bounded.
- **The merge must prefer the newer content.** `rankOf` ranks a confirmed block at 6 whatever revision it is, and only a strictly greater rank replaces — so the stale first answer would beat the fresh retry answer in the very merge the retry exists to fix. The `NOTE:` above `rankOf` already names this case and its remedy ("If peers are ever seen to disagree here, break the tie on the HIGHEST `materialized.rev` among top-rank entries") — that condition has now tripped (downstream trace, 2026-09-17: two cohort members answered one pinned read at revisions 6 and 7). Implement the tie-break and rewrite the NOTE.
- **If every reachable coordinator is below the floor,** return the best (highest-revision) entry unflagged. The prerequisite's reader then returns it uncached and logs `collection:block-below-floor`. Do not throw and do not stamp `unconfirmedAheadRev`: a log entry's blocks may legitimately never have landed (see the prerequisite, and `backlog/bug-a-refused-write-can-leave-its-log-entry-behind`), in which case the below-floor content is correct and every machine will agree on it.

## Costs to state in the handoff

- A reader whose own replica lags pays one extra request per changed block per refresh while it lags. Not measured.
- For a log entry whose blocks never landed, every read of that block through a refreshed handle pays the first request *and* the retry round until the block is next written. The prerequisite's tripwire `NOTE:` (retire a floor after repeated below-floor answers from a coordinator other than this node) covers both; extend its wording to mention the retry round rather than adding a second note.
- On an isolated node the retry re-picks the same node (the existing `findCoordinator:all-excluded` path, already noted in `get`). Same bounded extra consult as today's flagged-entry case.
