# Catalog-only ALTER, part 2: ADD COLUMN (nullable) and DROP COLUMN

Builds on `catalog-only-drop-check-constraint`, which adds the shared catalog-only helper (manager resolution without instantiating a table, fresh record read, pure owned/adopted/refused classification, write under the batch checkpoint, instance update, and the *adopted* rule: a change already in the record is not rewritten, and a reversal of an adopted change inside the same batch touches only this machine's engine catalog and instance). Read that ticket first; both arms here go through that helper.

## Why no row is rewritten

`RowCodec.encodeRow` stores a row as a JSON object keyed by column name; `decodeRow` reads each catalog column by name, a missing field reads as null (`denormalizeValue`), and a field with no column is ignored. A row written under either catalog reads under the other. Keys are unaffected: the arms below refuse any column in the primary key.

## ADD COLUMN

Accepted only when the column, resolved with `columnDefToSchema(columnDef, default_column_nullability === 'not_null', default_collation, isCollationRegistered)` exactly as Quereus's memory module resolves it, is **nullable**, has **no DEFAULT**, is **not GENERATED**, is **not a primary-key column**, and `columnDef.constraints` carries no `check`, `unique` or `foreignKey`. An explicit `collate` and column tags are allowed (the differ emits a resolved `collate`). `insertAtIndex` other than an append is refused. Anything else keeps today's refusal text, `Module for table '<t>' does not support ALTER TABLE ADD COLUMN`, `UNSUPPORTED` — refusing an inline CHECK here matters: otherwise Quereus would install it afterwards through the CHECK arm and a later failure would leave the column half-installed.

`backfillEvaluator` is absent for an accepted column (no default, not generated); assert that rather than ignore it.

Record edit: new `SchemaManager.withColumn(stored, column)` appends `columnSchemaToStored(column)`. Appending moves no position, so no positional field changes. Engine result and instance `tableSchema`: append the `ColumnSchema`, rebuild `columnIndexMap` with `buildColumnIndexMap`.

Classification against the record (compare with `columnSchemaToStored` on both sides, every field except `tags`, names case-insensitive):

| record holds | outcome |
| --- | --- |
| no column of that name | owned: append |
| that column, equal | adopted: no write |
| that column, different | refused: `ERROR`, naming the table, the column, and that the stored description already has a different column of that name (another machine's upgrade disagrees; not retryable) |

## DROP COLUMN

Accepted only when the column is in **no** primary key, index (declared or the synthesized unique-enforcement trees), UNIQUE constraint, or this table's own FOREIGN KEY, and is **not GENERATED**. Judge this against both the engine's `tableSchema` (Quereus has already refused PK columns, columns a generated expression / CHECK / DEFAULT / partial-index predicate / another table's FK / an assertion names) and the fresh record, whose `indexes` may hold an index another machine added that this engine has not seen. Refuse with `UNSUPPORTED` and a message naming what uses the column; keep the `ALTER TABLE DROP COLUMN` wording so a caller matching today's text still matches.

Record edit: new `SchemaManager.withoutColumn(stored, name)` removes the column and renumbers every POSITIONAL field over the removed slot: `primaryKeyDefinition`, resolved `indexes` (the in-memory `StoredTableSchema` holds index columns by position; `toPersistedSchema` turns them into names, so a stale position would persist the wrong column name), `uniqueConstraints`, `foreignKeys`, `generatedColumnDependencies` (keys and values), `generatedColumnTopoOrder`. `assertPositionsInRange` already runs on every write; it does not catch a position that is in range but wrong, so the spec below must cover a table with an index and a UNIQUE over columns *after* the dropped one.

Engine result: `shiftSchemaIndicesForDrop(tableSchema, colIndex)` (exported by `@quereus/quereus`; nothing it would remove can be present, since those columns are refused), spread over the engine's schema with `columnIndexMap` rebuilt. Quereus recomputes the generated-column graph itself after the module returns. Instance `tableSchema`: the same function over the instance's own schema (it carries UNIQUE constraints folded in from the record), plus the generated-column fields shifted like the record's.

Classification against the record:

| record holds | outcome |
| --- | --- |
| the column | owned: remove (whatever its definition — Sereus never reuses a dropped name, and a column the record has but this engine thinks differs is still the column being dropped) |
| no such column | adopted: no write |

Undo: Quereus marks DROP COLUMN **irreversible** (`droppedColumn` in `schema-differ.ts`) — it never re-adds the column, it reports the apply as partially migrated if a later step fails, and `endSchemaBatch` commits the overlay so record and engine still agree. The ticket text this was planned from assumed the undo re-adds the column; it does not. DROP COLUMN does run *as an undo* — of ADD COLUMN (`dropAddedColumn`) — and that is the case the adopted rule protects: an ADD this machine found already in the record must not be reversed in the record by its undo.

## Rebuilding the instance's derived state

An initialized `OptimysticVirtualTable` derives `rowCodec`, `indexManager`'s schema, and `uniqueEnforcementIndexes` from its `StoredTableSchema`. After an owned **or adopted** column change (an adopted one changes this machine's view too), publish all of them from the record the arm wrote (or, when adopted, read) in one synchronous step, as `doInitialize`'s publish does: `new RowCodec(record, encoding)`, `indexManager.setSchema(record)`, unique-enforcement descriptors rebuilt with `buildUniqueEnforcementIndexes(record)` and handed to the index manager **without re-opening any tree or re-registering collections with the transaction bridge** — the descriptor tree names come from column names (`uniqueEnforcementTreeName`), so they are unchanged; add an index-manager method that swaps descriptors only, if `setUniqueEnforcementIndexes` opens trees. A table with no instance needs nothing: its first statement builds it from the engine's catalog entry, which now matches the record.

Scans: the `doInitialize` NOTE says scans re-read `rowCodec` / `indexManager` per row and that "if concurrent DDL ever becomes real here, a scan must capture its codec and index manager as locals". A column change makes it real: a committed read (`readCommittedSnapshot`, runs outside the engine's exec lock) planned against the old column list must not decode with the new codec mid-scan. Capture both at the start of each scan generator and use the locals; update that NOTE to say it is done. If a scan site cannot capture them without restructuring, stop and record why in the review handoff rather than half-doing it.

## Re-adding a dropped name — decided: document, do not refuse

Rows keep a dropped column's field until rewritten, so a later ADD COLUMN of the same name reads those old values (possibly of another type — `denormalizeValue` converts by the new column's affinity). Refusing would need a permanent list of dropped names in the record (a new field with the byte-equality and merge discipline every record field carries, and a name the table can never use again); rewriting every row on drop defeats catalog-only. The same stale-field read already exists for a table re-declared with a different column list. Record an accepted-tradeoff `NOTE:` at the DROP COLUMN arm (revisit if a host needs to reuse a dropped name) and state it in the README.

## Edge cases & interactions

- **Rows under both catalogs.** Insert rows, add `b text null`: existing rows read `b` null; write a row with `b`; restart with hydrate only: both rows read back. Drop `b`: rows read without it; restart: same. Test (one spec, restart in the middle).
- **Positions after a drop.** Table `(id pk, a, b, c, d)` with an index on `c`, a table-level `unique (d)` and a generated column after the dropped one; drop `a`; then index seek on `c`, a duplicate `d` refused, the generated column correct, and the same after a hydrate-only restart. Test — this is the case `assertPositionsInRange` cannot see.
- **Refusals.** Drop a PK column (Quereus refuses first), an indexed column, a column in a UNIQUE, a column in this table's FK, a generated column; add a NOT NULL column, one with a DEFAULT, a GENERATED one, one with an inline CHECK/UNIQUE/FK. Each refused and nothing changed (engine catalog object identical, rows unchanged). Fold into the existing `REFUSED` table in `alter-table-arms.spec.ts`, replacing its ADD COLUMN / DROP COLUMN rows (which use statements that now succeed) with refused shapes.
- **Index another machine added.** The record lists an index on `c` that this engine has not hydrated; this engine's DROP COLUMN `c` is refused (by the fresh-record check, with a clear message — not the generic `mergePersistedSchemas` "Cannot re-declare" text). Verify by inspection or fold into the two-session spec.
- **Undo of ADD COLUMN through a failed apply.** Apply adds `b text null`, then a step fails: verified restore (message does not match `/partially migrated|could not be restored/`), `b` gone from the engine, the instance and the record. Test.
- **Second machine.** Two sessions over shared storage (`shared-local-transactor.ts`) hydrate; A applies a schema adding `b` and dropping `c`; B applies the same: succeeds, no record write (adopted), B's instance decodes rows with `b` and without `c`. Then B applies the same plus a failing step: B's engine restores its pre-apply state, the record keeps A's `b` (the undo DROP of an adopted `b` is engine-only) and still lacks `c` (DROP COLUMN is irreversible anyway). Test, sharing setup with the concurrent case.
- **Concurrent apply.** A and B apply at once; both succeed; the record has `b` once and no `c`. Test.
- **Different definitions on two machines.** Record has `b integer null`, this engine adds `b text null`: refused `ERROR`, nothing changed. Covered by the classification unit test; no spec.
- **Batched data events.** Quereus remaps events already batched in the transaction for the new arity itself (`remapBatchedDataEvents`); the plugin emits none of its own. Verify by inspection.
- **Tag listener.** `table_modified` fires after the arm; `followSchemaTags` overlays by column name, so the new column's tags (if declared inline) are already in the record and the save is `unchanged`. Verify by inspection.
- **Watch and committed reads** during the ALTER: covered by the scan capture above; verify by inspection.
- **Old builds** (same as the prereq): an older release's `apply schema` over a catalog a newer machine extended emits DROP COLUMN for the newer column and now succeeds. Extend the README caller obligation written in the prereq to columns.
- **RENAME COLUMN** is still schema-only and unsaved (`bug-optimystic-rename-column-lost-on-restart`); since rows are name-keyed, a session that renamed then added/dropped columns writes a record with the renamed column absent. Out of scope; do not touch.
