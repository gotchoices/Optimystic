Stage 5 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages), part two of three: the key-value journal, written through the port part one (`offline-sync-journal-port`) added to the db-core queue. Restoring from it after a restart is part three (`offline-sync-journal-restore`); this ticket only writes, so a crash test here checks what is on disk, not what comes back.

## Registration

Two keys are added to the `offline` block (`parseOfflineConfig` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-config.ts`, which today refuses them by name; update its message):

```typescript
offline: {
  journal: () => new FileKVStore(path.join(dataDir, 'offline')),   // an IKVStore, or a factory for one
  journalLabel: 'main',                                              // optional; see "Two databases, one store"
}
```

- `journal` is an `IKVStore` or a zero-argument function returning one; a function is called once, inside `register`. The value is checked structurally (`get`, `set`, `delete`, `list` are functions; `flush`, when present, is one) with a plain error naming what is missing. A `MemoryKVStore` (`instanceof`, imported from `@optimystic/db-p2p`) is refused with an error saying that a journal that does not survive a restart is the no-journal configuration and should be spelled by leaving `journal` off ([§Registration](../../docs/offline-sync.md#registration)). A store without `flush` is accepted, since `IKVStore` defines its absence as "every write is already durable".
- `journalLabel` is a string matching `/^[A-Za-z0-9_-]+$/`, default `'default'`; refused otherwise, and refused when given without `journal`.

Where `IKVStore` comes from: `@optimystic/db-p2p` already exports `IKVStore` and `MemoryKVStore` from its root (`packages/db-p2p/src/index.ts`), the plugin already depends on and value-imports from that package (`createPeerClientSignatureVerifier`, `MemoryRawStorage`), and `@optimystic/db-p2p` is `external` in the plugin's `tsup.config.ts`, so the plugin bundles nothing of it. No new dependency, no concrete storage package.

## Records

`OfflineJournal` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-journal.ts` implements db-core's `IOfflineJournal` over the store, under the prefix `optimystic-offline/<label>/`. Three sub-namespaces, so a listing of one never walks another, and keys that every `IKVStore` implementation can hold (`FileKVStore` turns `/` into directories and appends `.json`; a prefix it lists must end in `/`):

| Key | Written | Value |
|---|---|---|
| `…/entries/<seq>` | once, at enqueue (`queued`) | `{ v: 1, transactionId, seq, queuedAt, expiresAt?, segments: [{ collectionId, table, actions }] }` |
| `…/drives/<seq>` | before each send, after a partial commit, after an identity renewal (`driving`) | `{ v: 1, transactionId, actionId, attempts: [[collectionId, InFlightAttempt]…], committed: [[collectionId, WriteDurability \| null]…] }` |
| `…/outcomes/<transactionId>` | at a terminal outcome (`settled`), before the entry and drive records are deleted | `{ v: 1, at, status }` with `status` a `PersistedOutcome` (below) |

`<seq>` is the entry's `seq` zero-padded to 12 digits, so a prefix listing sorted as strings is queue order. `table` is each segment's table as the bridge records it (`TransactionBridge.tablesOf` on the collection id, the first name — a collection backing two tables is logged `offline:journal-ambiguous-table` and the first is recorded; part three's restore needs any one table that opens the collection). Actions are written as the queue hands them, `JSON.stringify`, which is the encoding the log transport already imposes on them ([§What is journaled](../../docs/offline-sync.md#what-is-journaled)); a `Uint8Array` inside an action would not round-trip, and none exists today (the JSON note under the `unchanged` guard in `docs/internals.md`). `WriteDurability` is plain data; `undefined` inside a pair becomes `null` on the wire and back.

`PersistedOutcome` is the terminal `QueuedTransactionStatus` reduced to what JSON carries: for `committed`, `transactionId`, `durability` with `collections` as pairs and `overall`, `tables` as pairs, and `followed` dropped (a restart follows nothing); for `failed`, `transactionId`, `reason`, `causedBy`, `changedTables`, `committedTables`, and `error` as `{ name, message }`. The codec that writes it and the one that reads it back (`decodeOutcome`, used by part three) live beside each other in `offline-journal.ts`; a decoded `failed` carries a plain `Error` with that name and message and no `cause`, and a decoded `committed` has `followed: false` — say so on `TransactionOutcome` in `offline-status.ts`.

Every `set` that the write ordering depends on is followed by `await store.flush?.()` before the port method resolves: the entry record, the drive record, the outcome record. Deletes are not flushed — a lost delete leaves a settled entry's records behind, which part three resolves by the rule "an entry record whose transaction has an outcome record is settled" (write that rule into §Restore after a restart now, so part three implements against it).

A store that throws: `queued`'s throw fails the commit (part one's queue unseals; the bridge rolls the transaction back — `sealIntoQueue` now awaits `OfflineMode.enqueue`, and a rejection takes `afterFailedCommit`'s ordinary path, which must treat it as a clean rollback: nothing reached storage). `driving`'s throw before a send keeps the entry queued (part one). `settled`'s is logged by the queue.

## Wiring

- `OfflineMode` builds the journal from the parsed config and passes it as `OfflineQueueOptions.journal`; `enqueue` becomes async and `TransactionBridge.sealIntoQueue` awaits it.
- `persisted: boolean` is added to the plugin's `queued` status (`translateListed`) and to `QueuedTransaction`, `true` when a journal is configured. db-core's `EntryStatus` is unchanged.
- Retained outcomes: `OfflineMode.retain` keeps the in-memory map as today; the journal's `settled` wrote the record first. `acknowledge(transactionId)` also deletes the outcome record; `pruneOutcomes` deletes the records it prunes (fire-and-forget, logged on failure — pruning is a read-path side effect and must not throw into `status()` or `outcomes()`). The outcome record is written by `settled`, which the queue calls with the db-core status; the journal translates it to the SQL-level outcome through the controller's existing `translate`, so wire `settled` to call back into `OfflineMode` for the translation rather than duplicating it. Mind the order the controller already relies on: `translate`'s `committed` arm calls `TransactionBridge.reportCommitDurability`, which notifies `onCommitDurability` listeners; with the journal in front, that report now happens inside `settled`, before the `committed` status is delivered — the same order as today, one call earlier. Keep `reportCommitDurability` called exactly once per drained commit: `onQueueStatus` must reuse the translation `settled` produced (cache it on the controller by transaction id for the moment between the two calls) rather than translating again.
- `OFFLINE_JOURNAL_KEY_PREFIX = 'optimystic-offline/'` is defined in `packages/db-p2p/src/storage/node-kv-namespaces.ts` beside the other prefixes and added to `NODE_KV_NAMESPACES`, with a comment that the Quereus plugin owns the keys under it; the plugin imports the constant from `@optimystic/db-p2p`. Grep `NODE_KV_NAMESPACES` across `docs/` and `packages/*/README.md` and extend any list of the node's namespaces you find.

## Two databases, one store

Two `Database`s registered over one store with different labels never see each other's records: every listing is under `optimystic-offline/<label>/…`. Two with the SAME label over one store corrupt each other's queue order and cannot be detected from inside either (no `IKVStore` lock); document that as the application's responsibility in the README and in §Which store, and put a `NOTE:` at the prefix builder.

## Test double

`PowerLossKVStore` in `packages/db-p2p/src/testing/power-loss-kv-store.ts`, exported from `@optimystic/db-p2p/testing`: an `IKVStore` with `flush` over a `WriteGroup<string>` (`packages/db-p2p/src/storage/write-group.ts`) whose sink is an in-memory map with the `deferSync` / `sync` / `powerLoss` behaviour `MemoryBatchBackend` has (`packages/db-p2p/src/testing/memory-batch-backend.ts`): a write resolves at once, `flush` commits the group, with `deferSync` a committed batch stays not durable until `sync`, and `powerLoss` rebuilds the map from the durable batches alone. It is deliberately not a `MemoryKVStore` subclass, so the registration check does not refuse it. `reopen()` returns a fresh store over the same maps, the way the conformance reopen case opens a fresh driver after a power loss (the write group's overlay must not survive the crash).

## Edge cases & interactions

- **Store throws at enqueue** → `commit` rejects with that error, the transaction is rolled back, no `queued` status, no record. Test: a `PowerLossKVStore` whose `set` is made to throw once; assert the rejection, no status, the row absent from a later read, and the collection's `sealedEntries()` empty.
- **Crash between the entry record and `commit` resolving** is not a crash the application can see (it never got the acknowledgement); the record is on disk and part three restores it, which drains a transaction the application never heard committed. State this in §Write ordering as the cost of flushing before resolving; the alternative (resolve, then write) breaks the acknowledgement promise.
- **Flush with a window.** `IKVStore.flush` takes no options; the journal's call is the strict form. By inspection.
- **Behind-queue network-acknowledged commit** goes through the same `enqueue` and is journaled like any entry; after a restart it is an ordinary queued entry (its waiter was in memory). By inspection; mention in the README.
- **Large attempts.** A drive record carries every transform of the attempt, up to the transaction size limit (7.5 MiB) per collection, rewritten per send. Accepted; `NOTE:` at the write site naming the remedy (write transforms under a content-addressed key, rewrite only the small part) if journal writes ever show up in profiles.
- **Outcome record written, entry record delete lost.** Covered by the rule above; verified in part three.
- **`acknowledge` of an outcome that was never journaled** (no journal configured, or the record's write failed): the delete is a no-op. By inspection.
- **Two tables over one collection URI** → `offline:journal-ambiguous-table`, first name recorded. By inspection.
- **No journal configured** → `persisted: false`, nothing else changes; the existing offline specs must pass unchanged.
- **`journal` given as a factory that throws** → `register` throws that error. By inspection.
- **Crash scenario, write side** (the restore side is part three): on a two-node mesh with node A's journal a `PowerLossKVStore({ deferSync: true })`, commit offline, let it drain, `powerLoss()` before the queue's delete flushes… the delete is not flushed, so after `powerLoss` the entry record, the drive record and the outcome record are all present — assert exactly that, and that the drive record's attempt names the action id the log on node B holds (`entriesUnder` / the helpers `packages/db-core/test/offline-queue.spec.ts` uses). Second case: `powerLoss()` while node B is severed and the entry has been sent once — the entry and drive records present, no outcome.
