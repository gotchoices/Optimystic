# A narrowed ring sheds its large files

## Why

Blobs are where the bytes are — that is the sentence `docs/blobs.md` §Lifetime opens with, and the reason reclaiming was built for blobs first. But the one mechanism by which a node reduces what it is responsible for, narrowing its arachnode ring, reaches only blocks. `RingShiftCoordinator.computeShedBlocks` walks `ownedBlocks`, hashes each block's routing key, and sheds the ones the old partition covered and the new one does not. Nothing walks the blobs.

A blob's `responsible` hold follows its **cohort** instead: the blob rebalance monitor derives each held reference's cohort from `findCluster(routingKeyForBlob(ref))` — FRET proximity plus network membership — and `BlobCohortReaction` releases a hold only when this node leaves that cohort, and only after confirming enough current members hold the blob whole. The arachnode ring plays no part, as `docs/arachnode-ring-handoff.md` § Part 2 already records for the block side's gained half.

So a node can shed its way from ring 3 to ring 6, hand over seven eighths of its blocks, and keep every blob. If its disk is mostly blobs — the case the blob design was written for — narrowing frees nothing and the node sits at its limit refusing new data for ever. Shedding has to reach blobs for the parent ticket's promise to hold.

## What to build

### The decision: the ring narrows what a node keeps, and only ever narrows

A node's advertised partition starts to mean, for blobs as for blocks, "this is the slice of the keyspace I keep". Three asymmetries make that safe, and all three are deliberate:

- **Narrowing may release; it never acquires.** Moving *in* (gaining keyspace) fetches no blobs, exactly as it fetches no blocks. What delivers a gained range is the cohort's own announcements and read repair.
- **The cohort still decides what a node takes; the ring only decides what it keeps.** A blob reaches a node because its cohort assigned it, and that is unchanged.
- **Every release is still individually confirmed.** A shed blob's hold is dropped only through the existing release arm of `BlobCohortReaction` — announce to the current members that do not have it, `stat` them, and drop the hold only once at least the floor of them answer `whole`. No new release rule is invented, and nothing drops below its floor.

### The shed pass

`RingShiftCoordinator` gains one callback beside `onRelease`: `onNarrowed({ from, to })`, carrying the old and new partitions, fired at Phase C when a move-out completes. The coordinator itself learns nothing about blobs — it stays a block-and-ring state machine — and the node factory, where the blob monitor and the reaction already live, wires the callback to a pass over `heldBlobRefs`:

1. hash each held reference's routing key (`routingKeyForBlob`, the same key the blob monitor already derives cohorts from),
2. keep the ones the old partition covered and the new one does not — the identical predicate `computeShedBlocks` uses, from `packages/db-p2p/src/storage/arachnode-partition.ts`,
3. hand those to the reaction's release arm with the current owners and the floor, and apply its answer exactly as the monitor's own `lost` arm does: `releaseResponsible` for each released reference, `retainLost` for each retained one.

That means lifting `BlobCohortReaction`'s `releaseLost` into a method that takes references, an owners map and a floor, so the event path and the ring path share one implementation rather than two that drift. The owners map is built the way the reaction's own arm gets it — from each reference's current cohort — not from the shift's block-owners map.

**Blobs do not gate the shift.** Phase B keeps its all-or-nothing rule for blocks, and the blob pass runs after Phase C, per reference: what confirms is released, what does not is retained and re-offered by the blob monitor's next check. Coupling the two would mean one unconfirmable blob rolling back a block handoff that had already confirmed, which trades a real guarantee for a storage saving.

### The gate that stops the loop

This is the part that cannot be left out. Shedding a blob while still accepting announcements for it is a loop: the node drops the hold, a current member or the writer's copy drain announces the reference again, `BlobAnnounceReceiver.decided` finds this node in the cohort and committed state listing the reference, takes a fresh `responsible` hold and pulls the whole blob back. Bandwidth spent, nothing freed, for ever.

So `decided`'s responsibility test becomes "my own view of the cohort includes me **and** the slice I serve covers this blob's routing key", through `isServingHolder` in `arachnode-partition.ts` — the shared predicate that already encodes fail-toward-the-old-holder, so a node mid-shift (`status: 'moving'`, with `moveFrom` set) still accepts for the range it is still serving and does not refuse what it has not yet handed over. The answer for a blob outside the slice is the existing `'not-responsible'`, which is exactly what it means.

Two consequences, both to be written down rather than discovered:

- **A blob can be declined by every member of its cohort**, if each has narrowed past its key. The writer then keeps its `owed` hold and its drain keeps retrying — the blob-level expression of "the network has no room for this where it routes". It is the honest outcome, and the thing that would improve it is placement that takes a holder's slice into account, which is backlog `feat-cohort-selection-owner-aware-placement`.
- **Reader repair narrows too.** `keepAfterRead` takes a `responsible` hold for a blob a read brought here, through the same `inCohort` test, so it picks up the same gate and stops re-adopting blobs outside the slice.

## Edge cases & interactions

- **A rolled-back shift.** `onNarrowed` fires only from Phase C, so a shift that rolled back sheds no blobs and the node's partition is unchanged. The pass must take its partitions from the callback's arguments, never re-read them from the adapter, where a later shift could have moved them.
- **A reference held only as `owed`.** The release arm already skips it (`release:not-responsible`), and the owed drain follows its own cohort. So a writer's owed blob is never shed by the ring — right, because nobody else has it yet and the writer owes it.
- **A pinned blob.** A pin is the application's own hold and the reclaim pass never reads or changes one; shedding must not either. Releasing `responsible` on a pinned blob leaves the pin, the record and the pieces, which is the existing behaviour of every release — verify by reading `releaseResponsible`, and do not special-case it.
- **A blob partly held.** The release arm counts a member's `whole` answers only, so a node sheds a blob it holds partly once the members hold it whole. Its pieces then go to the existing piece sweep with everything else no hold needs.
- **A node at the deepest ring.** Ring 16 covers one 65536th of the keyspace, so almost every blob a node at that depth holds is outside its slice and will be shed as fast as its cohort confirms. That is the intent — a node with no room keeps almost nothing — but it also means a cohort of deep-ring nodes holds very little, which the first consequence above already states.
- **The monitor's tracked set.** `releaseResponsible` fires the holds feed, which untracks the reference when no `owed` hold remains; the shed pass needs no separate untracking. Verify against the feed in the blob rebalance block.
- **A shed pass overlapping a monitor check.** Both call the same release arm over overlapping reference sets. The reaction's wiring already accepts overlapping reactions (`releaseResponsible` is idempotent, duplicate announcements are what `AnnounceLimiter` is for), so no new guard — but the pass must be hopped off the Phase-C callback rather than awaited inside it, as the monitor's own handler is hopped off its emit loop.
- **Arachnode disabled.** No shifts, so no shed pass, and the `decided` gate reads an absent partition as covering everything (`partitionCovers`'s existing contract for ring 0) — so a node with no arachnode behaves exactly as it does today. Confirm that contract rather than assuming it.

## Tests

One spec, over the shed selection: **a move-out sheds exactly the held references the old slice covered and the new one does not, and nothing held outside the old slice or inside the new one.** The predicate is shared with the block side, but the *selection over blob routing keys* is new, and getting it inverted would have a node releasing the half it keeps — the one failure here that loses data rather than wasting space.

No test for the release itself (it is the reaction's existing arm, specced where it lives), for the `decided` gate (one predicate call added to an ordered sequence of checks), or for the callback wiring.
