# Blob `announce` and `held` can be sent

Second of three parts of `feat-blob-announcements-are-answered`. The wire already decodes and answers both requests (`BlobRequest`, `BlobAnswer`, `BlobAnnounceAnswer` in `packages/db-p2p/src/blob/blob-protocol.ts`; `BlobProtocolService.answerAnnounce` and `answerHeld` answer with placeholders through the optional `onAnnounce` / `onHeld` init hooks). This part adds what a sender needs and the `responsible` hold's scope. The receiver is the third part.

## The scope's bounds

`MAX_BLOB_SCOPE_CHARS = 1024` in `packages/db-p2p/src/protocol-limits.ts`, with a one-line comment (a scope is a collection id; 1024 keeps the header far under `MAX_BLOB_HEADER_BYTES`). `scopeField` in `blob-protocol.ts` refuses an empty scope and one longer than the cap, as `BlobProtocolError` — so the service answers `refused: malformed`, the existing handling of every malformed header (not a reset). Length is `scope.length` (UTF-16 code units), stated in the constant's comment.

## Client: `announce` and `held`

```ts
// BlobProtocolClient
/** Throws RangeError, locally, for an empty scope or one over MAX_BLOB_SCOPE_CHARS; BlobPeerRefusesError for a peer known not to run the blob protocol; BlobPeerRefusedError when the peer answers `refused`. */
announce(peer: PeerId, ref: BlobRef, scope: BlobScope, options?: BlobRequestOptions): Promise<BlobAnnounceAnswer>;
/** Resolves once the peer's empty acknowledgement is read. Same errors, less the scope check. */
held(peer: PeerId, ref: BlobRef, options?: BlobRequestOptions): Promise<void>;
```

Both follow `stat`'s shape (`open`, `readAnswer`, `requireEnd`, `fail`, `finish`) and are bounded the way every blob exchange is, by the exchange's `ProgressDeadline` of one `responseTimeoutMs` with no bytes moving. A ref that is not canonical throws `BlobRefError` locally (`parseBlobRef`), as `stat` would through the codec rule. Log lines `client:announce peer=%s ref=%s answer=%s ms=%d` and `client:held peer=%s ref=%s ms=%d`.

## Which peers accept blobs

`packages/db-p2p/src/blob/accepts-blobs.ts`:

```ts
/** What this node knows about whether a peer runs the blob protocol, from its protocol list. */
export type BlobAcceptance = 'accepts' | 'refuses' | 'unknown';

/** Thrown, before dialing, for a peer whose protocol list says it does not run the blob protocol (an older build: docs/blobs.md §Compatibility). */
export class BlobPeerRefusesError extends Error { constructor(readonly peer: string) }

export function blobAcceptanceOf(keyNetwork: Pick<Libp2pKeyPeerNetwork, 'protocolSupport'>, blobProtocol: string, peerIds: readonly string[]): Promise<Record<string, BlobAcceptance>>;
```

Add `Libp2pKeyPeerNetwork.protocolSupport(protocol, peerIds): Promise<Record<string, 'listed' | 'unlisted' | 'unknown'>>` beside `peersServing`, over the same `peerRecords` cache (so a peerStore read is paid only when a record changed): `listed` when the record's protocols include it; `unlisted` when the peer has a record with a **non-empty** protocol list that lacks it; `unknown` when there is no record or an empty list (not yet identified). This is the same reading `membershipOf` gives a protocol list — a non-empty list is taken as the peer's statement — so the two cannot disagree about when a list counts. `peersServing` may be re-expressed over it; not required. `blobAcceptanceOf` maps `listed → accepts`, `unlisted → refuses`, `unknown → unknown`.

`BlobProtocolClientInit` gains optional `acceptance?: (peerId: string) => Promise<BlobAcceptance>`; `announce` and `held` call it before dialing and throw `BlobPeerRefusesError` on `refuses` (dialing would fail protocol negotiation anyway; this makes the reason typed for the drain, `feat-blob-owed-copies-are-drained`). `stat` and `get` do not consult it (the fetcher already filters its candidates through `peersServing`). `wireBlobFetcher` in `libp2p-node-base.ts` passes `acceptance: id => blobAcceptanceOf(keyNetwork, buildBlobProtocol(protocolPrefix), [id]).then(r => r[id] ?? 'unknown')`. Export the module from `packages/db-p2p/src/index.ts`.

## The `responsible` hold carries its scope

In `blob-record.ts`, the `responsible` variant becomes `{ readonly kind: 'responsible'; readonly at: number; readonly scope: BlobScope }`: the scope the reference was last verified under, which the cohort reaction re-announces with (`feat-a-referenced-blob-is-copied-to-its-cohort`). `holdProblem` refuses a `responsible` hold whose `scope` is not a non-empty string. No stored record carries a `responsible` hold yet, so this is not a format change.

`LocalBlobService` gains, each through `changeRecord` (the one path every record change takes, which the piece sweep depends on):

```ts
/** Adds the `responsible` hold under `scope`, or replaces an existing one's scope and `at`; creates the record (`whole: false`) when there is none. Flushed before it resolves: a lost hold would let a restart sweep a blob this node told an announcer it is pulling. */
holdResponsible(ref: BlobRef, scope: BlobScope): Promise<void>;
/** The scope of `ref`'s `responsible` hold, or undefined. */
responsibleScope(ref: BlobRef): Promise<BlobScope | undefined>;
/** Every ref whose record holds `responsible`. A record that fails to decode is logged and skipped. */
responsibleRefs(): Promise<BlobRef[]>;
```

`responsibleRefs` reads `records.listRefs()` then each record; it is a start-up enumeration, so reading every record is acceptable (leave a `NOTE:` saying so, and what to do if the record count ever makes start-up slow: keep an index of held kinds). No hold-removal method is added here; `feat-a-referenced-blob-is-copied-to-its-cohort` adds the one it needs.

## Edge cases & interactions

- **Malformed scope over the wire**: empty or over the cap is refused `malformed` before `onAnnounce` runs (test: codec).
- **Client-side refusal before dialing**: an oversized or empty scope throws `RangeError` without opening a stream (inspection: checked before `open`).
- **Not yet identified peer**: `unknown`, so the client dials; a refusal arrives as a failed protocol negotiation (inspection).
- **A peer that opened a blob stream to us** gets the blob protocol merged into its record by libp2p, which reads `accepts` — correct, since it runs the protocol. Inspection.
- **A hold on a record also holding `cached` or a pin**: both kept; `holdResponsible` touches only the `responsible` entry. Inspection.
- **Concurrent hold writes**: serialized per ref by `BlobRecordStore.update`. Inspection.
