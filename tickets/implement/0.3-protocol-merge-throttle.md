GitHub [#40](https://github.com/gotchoices/Optimystic/issues/40), second source. Decision recorded in the retired blocked ticket `0.3-feat-a-stream-carries-more-than-one-request`: stream reuse declined; the cause is fixed upstream; this interim carries phones until it ships.

**Upstream:** [libp2p/js-libp2p#3692](https://github.com/libp2p/js-libp2p/pull/3692) — `Connection` merges each protocol once per connection, and the peer store treats an open connection as proof the peer is live (so it no longer depends on stream traffic to keep `updated` fresh) and stamps `updated` once at disconnect. When a libp2p release carries it, delete this throttle (the pinning spec below says when).

## The cost

libp2p 3.3.11 calls `peerStore.merge(remotePeer, { protocols: [protocol] })` for every stream, on both ends (`Connection.newStream` and `onIncomingStream` in `libp2p/dist/src/connection.js`). `@libp2p/peer-store`'s merge always decodes the record, rebuilds a `Peer` (a multiaddr per address) twice, re-sorts the addresses and writes, even when the protocol is already recorded. Measured 59 µs per merge with 2 addresses, 246 µs with 8 (desktop, in-memory datastore); #40 profiled about 7% of the JavaScript thread on a Galaxy S7.

## Where the record's freshness comes from today (corrected)

The record is evicted on read once `updated` is over 6 h old (`maxPeerAge`) and no address was observed within 1 h (`maxAddressAge`); an existing address keeps its first `observed` time. Within one long-lived connection, the per-stream merges are what refresh `updated`. The earlier ticket attributed that to our own request streams; in fact the main source is **libp2p's connection monitor**, which opens a `/ipfs/ping/1.0.0` stream every 10 s (`DEFAULT_PING_INTERVAL_MS`) — six merges a minute per connection on each end before any request of ours.

Under the throttle that ping pair still reaches the store once per interval, so `updated` is never more than one interval stale on a connection the monitor pings — the 6 h expiry stays far off. With the monitor disabled, a connected peer can already be evicted on `main` today (the upstream PR's integration test reproduces it); the throttle neither causes nor fixes that.

## The change

After `createLibp2p` in `createLibp2pNodeBase` (`packages/db-p2p/src/libp2p-node-base.ts`), next to `identifyOnConnectionOpen` (`packages/db-p2p/src/network/identify-on-open.ts`), install a wrapper around `node.peerStore.merge`. `node.peerStore` is the object libp2p's connections call through (`configureComponent` assigns `components.peerStore` and returns it). Put it in its own module, `packages/db-p2p/src/network/protocol-merge-throttle.ts`, with type-only libp2p imports, since `libp2p-node-base.ts` must stay reachable from the React Native entry.

- **What it intercepts:** only a merge whose data has exactly one key, `protocols`, holding exactly one protocol — the shape `connection.js` uses. Every other merge (identify, the dial queue, circuit relay, `peer-address-book.ts`) passes straight through.
- **The rule:** per (peer, protocol), at most one such merge reaches the store per interval (`PROTOCOL_MERGE_INTERVAL_MS = 60_000`). Others inside the interval resolve without touching the store. The first merge for a pair always goes through, so a protocol is recorded at its first stream exactly as today.
- **What it returns when it skips:** the `Peer` the last real merge for that pair returned. `connection.js` ignores the value; say so in the doc comment.
- **A merge that rejects** does not start the interval, so the next stream retries.
- **Memory:** a bounded `LruMap` keyed by peer and protocol. Drop a peer's entries on `peer:delete`, so a deleted record is re-created by the next stream.
- **Behaviour change:** a protocol identify removes from a record within the interval is re-added by a stream up to one interval later instead of at once. That re-add is the path by which a stranger can put this network's protocols into its own record ([docs/internals.md §Network Membership Predicate](../../docs/internals.md#network-membership-predicate)), so delaying it loses nothing.

## Edge cases & interactions

- First stream on a new protocol is recorded at once — test.
- A second stream inside the interval does not reach the store — same test, counting calls to the original method.
- A stream after the interval does reach it — fake clock in the same test.
- A rejected merge is retried by the next stream — inspection.
- Only the exact single-protocol shape is throttled — a type on the predicate, plus inspection.
- The original is called with the store as `this` — inspection.
- `node.stop()` needs no teardown (no timer) — inspection.
- **libp2p upgrade:** a pinning spec opens two streams of one protocol over a loopback pair and asserts the original `merge` is reached once per stream. It fails on the libp2p release that carries #3692, which says to delete the wrapper — as `packages/db-p2p/test/relay-third-party-address-gap.spec.ts` does for address learning. If libp2p moves the call off `components.peerStore.merge`, the wrapper is bypassed silently and behaviour reverts to today's; the spec is what catches that.
