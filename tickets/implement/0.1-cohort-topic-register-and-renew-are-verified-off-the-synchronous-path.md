GitHub [#55](https://github.com/gotchoices/Optimystic/issues/55), a follow-up to #49. The precedent is the completed ticket `cohort-gossip-is-verified-once-off-the-synchronous-path`, and `handleGossipFrame` in `host.ts` is the shape to copy.

## What was measured while planning

All of this is **Node 24 on a desktop, not Hermes**. Nothing in this repository runs Hermes, so none of it says what a phone gains.

**Cost of one check** (the issue's bench, same shape, against the current build): `verifyPeerSig` 0.993 ms, `verifyPeerSigAsync` 0.067 ms, 14.8 times, on Node v24.2.0. The reporter's machine gave 2.712 ms, 0.149 ms and 18.2 times. This satisfies the ticket's measurement requirement; re-run it only if the primitives change.

**Which checks run on a two-machine group.** Two real libp2p nodes, each with a node key, both watching the same 6 collections (12 registrations), counting every call into noble by call site:

| Phase | Plain pings | Re-attach / withdraw frames | noble verifications |
|---|---|---|---|
| Opening the 6 watches | 0 | 0 | 18 register signatures, 6 bootstrap-evidence signatures |
| About 375 s idle, longer than the 5-minute membership refresh interval | 156 since the watches opened, all answered `ok` | 0 | **0 of any kind** |

Of the 18 register signatures in one run, 12 were a node checking its **own** frame, arriving in process through `handleLocally`, and 6 came from the other machine. All 6 evidence checks were the node's own frames too. The split depends on which member the walk reaches first, so it varies by topic and run.

## What that means for the report

**The reported renew cost is not a healthy idle group, and this ticket's verifier change may not be what removes it.** Plain pings are never signature-checked (`onRenew` returns on them before any gate, at both HEAD and the reporter's 1.24.0, whose gate code is the same). The check on the renew path only runs for a `reattach` or `withdraw` frame. The real stack is `handleRegisterFrame → resolveRenew → handleRenew → onRenew → verifyParticipantSig → verifyPeerSig`, so the reporter's S21 was receiving privileged frames while idle. The healthy run above sends none.

We did not reproduce what the reporter saw, and the cause is unknown. Two candidates, both inferred from reading code and neither observed:

- Failing pings. Three failed pings send a `reattach` to each backup. On a two-machine group the backup is often the node itself, and that frame arrives in process through `handleRegisterFrame`, which is the shape of the reported stack. If the clocks of the two phones differ, the freshness rule (`timestamp <= lastPing`) refuses it after the signature was already paid for, and the registration re-walks and fails over again later.
- Watches opening and closing in the application, each close sending a `withdraw`.

So this ticket also adds the two things that help regardless of cause (the self-frame skip and the check-freshness-first order) and a log line that lets the reporter tell us which frames they are getting.

**What a phone gains.** `verifyPeerSigAsync` is native only where the runtime provides WebCrypto Ed25519, and that must be installed before `@libp2p/crypto` is first imported. Without it, `@libp2p/crypto` uses noble at the same cost, inside an `async` function that still blocks the thread. On such a phone the verifier change saves **nothing per check**. What still helps there is not checking at all: the self-frame skip and the early refusals. No on-device saving has been measured.

## Design

**Authenticate in the host, before the engine; the engine stays synchronous.** This is the first shape the issue offers and the one #49 took: there, "the signature is the transport's job" and the bus keeps only its membership gate. The alternative, async engine ports, was rejected: `onRenew` reads the record and then decides, so an await between would have it act on a record read before the wait, and every engine decision after the gate would need re-reading state. With the check in front, every synchronous decision reads current state after the wait, and db-core's engine and its many direct-call tests stay synchronous.

So `verifyRegisterSig` and `verifyParticipantSig` are **removed** from db-core, not left unbound. A live-signer host authenticates a frame before handing it over, and a key-less host hands frames over unchecked, as it does today. Write that contract on `handleRegister`, `handleRenew` and `onRenew`. `resolveRenew`, on a privileged frame, must only ever be reached by the path below.

**A frame this node sent to itself is not checked.** `handleLocally` and `handleRenewBatchLocally` are called only for frames this process just built and signed: the renewal service (`CohortTopicService.sendRenew`), the walk (`walk.ts`) and the forwarder's parent link (`registerForwarderWithParent`). `handleRegisterFrame` gains an origin argument, `"self"` from `handleLocally` and `"remote"` from the `/register` stream handler and the FRET activity handler. The FRET activity handler is always `"remote"`: FRET does not say who sent a frame, and `participantCoord` matching this node proves nothing, since that claim is what the signature exists to check.

**Inbound register** (`dispatchRegister`), in order:
1. Decode and validate once (already done by the callers).
2. A `rootKey` on a host that serves no root groups gets its existing refusal. No crypto.
3. Live-signer and `"remote"`: check the signature. Failure answers `no_state`, as the engine's gate does today.
4. Take `now` here, after the wait. Remove the `now` parameter both callers pass.
5. Everything else as today: `prepareRootPlacedCoord`, `registry.forCoord`, `engine.handleRegister`.

Step 3 ahead of step 5 is a gain as well as a move: a forged frame no longer reads a root group or creates a coord engine, which the `NOTE:` at `publishSink` in `host.ts` records as a current weakness. Reword that note, since a validly signed frame can still create one before the anti-DoS gate judges it. Probes take the same path, so they get the signature check at this same point, and their `no_state` answer is unchanged.

**The rate limiter stays after the signature.** Moving it ahead would look like "cheap checks first" but would let a forged frame spend a victim's per-(peer, topic) budget and let a stranger grow the limiter's memory. Keep `runGuards`' order and its reasoning, minus the signature step.

**Inbound renew** (a new `resolveInboundRenew`, called from `handleRegisterFrame`):
1. Key-less, `"self"`, or a plain ping: `resolveRenew` as today, with no await added.
2. `findHolder` finds nothing: `unknown_registration`. No crypto.
3. Ask the engine whether the frame is already refused without its signature (below). If so, answer that.
4. Check the signature.
5. Look the holder up **again**, since the wait can outlast the engine or the record. Failure: the engine's opaque refusal, or `unknown_registration` if no holder remains. Success: `resolveRenew` with a `now` taken after the wait, so `onRenew` re-runs the freshness check against current state.

`handleRenewBatchFrame` needs no signature path: `decodeRenewBatchV1` already refuses a batch with a `reattach` or `withdraw` entry, so it stays synchronous and checks nothing.

**New db-core surface.** In `renewal.ts`, on `RenewalCohortSide`, with pass-throughs on `CohortMemberEngine`:

```ts
/** A withdraw or re-attach, the two renews whose signature matters. */
export function isPrivilegedRenew(msg: RenewV1): boolean;

/** The answer `msg` gets whatever its signature says: no record, or it fails the freshness gate. Undefined: the signature decides. */
refusalBeforeSignature(msg: RenewV1, now: number): RenewReplyV1 | undefined;

/** The opaque answer to a privileged renew whose signature failed. */
refuseUnauthenticated(msg: RenewV1): RenewReplyV1;
```

Both refusals return what `onRenew` returns today, and `onRenew` should build its own refusals from the same code: no record or a withdraw gives `unknown_registration`, a re-attach gives `primaryMoved` for the current assignment. `withdraw` is judged before `reattach` when both are set, as now. A stale frame and a forged one get the same answer, so the early check tells a sender nothing it could not already learn.

**One shared check.** Generalise `gossipSignatureVerifies` so register, renew and gossip share the non-empty test, the guarded and logged base64url decode, and the `verifyPeerSigAsync` call. An undecodable signature must log and refuse. Today's `verifyRegisterSig` decodes outside any guard, so a bad one aborts the stream.

**A diagnostic for the open question.** Log each privileged frame on `createLogger("cohort-topic")`: kind, origin, and answer. Key it so the reply to #55 can name the line. Add it to `docs/debugging.md` under the db-p2p namespaces, since the "cohort-topic sub-namespaces" table there is known to be wrong (backlog `bug-cohort-topic-debug-namespaces-are-documented-but-not-emitted`).

**The synchronous verifier stays for:** bootstrap evidence, parent references and `verifyCollectedMultisig` (none ran while idle above; evidence is filed as backlog `debt-cold-start-evidence-is-checked-with-the-synchronous-verifier`), plus the other `verifyPeerSig` callers outside this path: the client signature verifier, the arrival push receiver, the matchmaking entry verifier and the recover transport. Their cost is out of scope, and none ran in the measurement above.

**Acceptance difference (strict RFC 8032 against noble's ZIP215).** Nothing re-checks a frame once accepted, so the two verifiers can never disagree about one: `RegistrationRecord` carries no participant signature, gossip replicates records without re-verifying, and a re-attach is judged once by the member it reaches. Matchmaking's `registrationSig` is a separate signature with its own verifier. Across runtimes or builds, one member could accept what another refuses only for a signature crafted by the key's own holder, and all that does is affect that holder's own soft-state registration. Self-frames skip the check, and every signer here produces RFC 8032. Say this in the `verifyPeerSigAsync` doc.

## Edge cases & interactions

- **A record evicted or moved during the wait.** Step 5 of the renew path looks up again; `onRenew` reads the store after the wait. By inspection.
- **An engine evicted during a register's wait.** `registry.forCoord` runs after the wait, so it finds or creates one then. By inspection.
- **A plain ping overtaking a withdraw or re-attach still verifying.** The ping sets `lastPing` to the member's clock, so the privileged frame can then fail `timestamp <= lastPing`. A withdraw then answers `unknown_registration` and the record expires by TTL; a re-attach answers `primary_moved` and the participant carries on. This already happens on network reordering; the wait only widens the window by one verify. Accepted: record it as a `NOTE:` at the re-check. By inspection.
- **Two copies of one register verifying together.** The replay guard runs after the wait with no await inside `runGuards`, so the first is admitted and the second refused. By inspection.
- **A withdraw finishing after a later re-register.** The monotonic freshness check refuses the withdraw, because `lastPing` is now newer. By inspection; `registration.spec.ts` pins the rule.
- **Two frames finishing out of order.** Frames for one participant and topic are last-writer-wins already, as on any reordering network. No new class of outcome. By inspection.
- **Frames held during verification.** With a native verifier a flood no longer blocks the thread, so more frames can be in flight at once. Each holds one inbound stream, under libp2p's per-protocol stream limit, as the gossip handler's do. Forged frames carrying fresh timestamps still cost one verification each, unrated, as today. Leave a `NOTE:` at the check, tripwire: if it shows up in profiles, add a limiter here keyed by the connection's peer, not by the frame's claim, so a stranger cannot spend someone else's budget.
- **Key-less hosts.** No check on either path, the same behaviour as today. Pinned by the existing "without a node key" test in `peer-key-signing.spec.ts`.
- **An unsigned frame on a live-signer host (mixed configuration).** Refused, by the empty-signature check. Test.
- **A re-attach with `reattach: false` or a withdraw with `withdraw: false`.** A plain ping: `isPrivilegedRenew` tests `=== true`, matching `onRenew`. Inspection.
- **Tests that call `engine.handleRenew` directly with signed re-attaches** (`gossip-cadence`, `live-tier`, `cohort-topic-scale-lifecycle`, the integration spec). These frames are correctly signed and keep working unchanged.
- **Check each frame once.** After this ticket no port remains that could check a second time. By type: the ports are gone.
- **FRET-routed frames to self.** A register FRET routes to this node through the activity handler is checked even when this node sent it, since FRET does not say. It costs one check, and is safe. Inspection.

## Tests

The default is no new test. These earn their place:

- **A signature only noble accepts is refused on every inbound path.** This is the "fails if a path uses `verifyPeerSig`" test the ticket requires. noble's `ed25519` object is frozen, so it cannot be spied on, and no test-only option should be added. Instead build a signature that separates the two verifiers: with `R = rB` and a point `T` of order 8, publish `R' = R + T` and `S = r + H(R' ‖ A ‖ M)·a mod L`. The cofactored ZIP215 equation accepts it and the cofactorless one Node uses refuses it. `T` encodes as `26e8958fc2b227b045c3f489f2ef98f0d5dfac05d3c63339b13802886d53fc05`; read it with `ed25519.Point.fromBytes(bytes, false)`, and get `scalar` and `pointBytes` from `ed25519.utils.getExtendedPublicKey(seed)`. **Measured during planning: noble `true`, platform `false`, honest signature `true` on both** on Node v24.2.0. Pin that control in `peer-sig.spec.ts`, so the test below cannot pass vacuously if the two verifiers ever converge.
- **Refusal on each path**, table-driven in one new spec under `packages/db-p2p/test/cohort-topic/`, driving the real handlers on a keyed host (`MockNode.handlers` in `cohort-topic-mesh-harness.ts` for `/register`, and a captured `setActivityHandler` callback as `service.spec.ts` does). Paths: register over the stream, register through the activity handler, probe, re-attach, withdraw. Signatures: the noble-only one above, a different key's, and empty. Expected: register and probe answer `no_state`, hold no record, and create no coord engine; re-attach answers `primary_moved` and leaves `primary` unchanged; withdraw answers `unknown_registration` and keeps the record. A correctly signed frame is admitted or acted on, so the refusals mean something.
- **`refusalBeforeSignature`**, in `registration.spec.ts`: no record, stale and future and not-newer-than-`lastPing` for each of withdraw and re-attach, and `undefined` for a fresh one.

Move or cut existing tests rather than keep both. `peer-key-signing.spec.ts`'s register, reattach and withdraw forgery tests call the removed ports or a host engine directly, so they are replaced by the table above. Its key-less test stays. In `registration.spec.ts`, `sideWithGate` loses the signature cases and keeps the freshness and replay cases. In `member-engine.spec.ts`, remove `verifyRegisterSig` and the forged-probe case. `cohort-topic-mesh-harness.ts` and its users need no change.

The self-frame skip gets no test of its own: it is wiring, and the table above already fails if the stream or activity paths are marked `"self"`.
