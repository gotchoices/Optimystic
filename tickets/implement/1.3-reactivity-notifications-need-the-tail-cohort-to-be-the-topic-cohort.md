# Reactivity: root the announcement tree at the tail block's storage group

Third of three tickets for the decision below. The first two added root placement to the cohort-topic substrate (`cohort-topic-a-topic-can-place-its-root-at-a-routing-key`) and taught the db-p2p host to serve a root whose group is a block's storage group (`cohort-topic-host-serves-a-root-at-a-storage-group`). This ticket switches reactivity onto it and binds the host's root group to the key network.

## The decision (accepted by the maintainer, 2026-10-02)

`docs/reactivity.md` § Origination point claimed the machines that store a collection's log tail block and the machines that announce its changes are one group "since they share the same coordinate". They were not: the storage group is the `clusterSize` serving peers nearest `hashKey(routingKeyForBlock(tailId))` (`findCluster` in `packages/db-p2p/src/libp2p-key-network.ts`), while the announcing group was FRET's raw `wantK` (16) cohort around `coord_0 = H(0x00 ‖ H(tailId ‖ "reactivity"))` (`createReactivitySelfMembershipGate` in `packages/db-p2p/src/cohort-topic/reactivity-membership-gate.ts`). Once a network is wider than a cohort the two are disjoint, so (1) almost no commit is announced — a node announces only if it applied the commit *and* sits in the announcing group — and (2) an announcement would not verify anyway: its signature is the commit certificate, signed by storage-group members, checked against announcing-group membership with `minSigs` 14 (`DEFAULT_MIN_SIGS` in `packages/db-core/src/cohort-topic/sig/threshold.ts`), which a `clusterSize` group below 14 can never meet. Today it works only with `wantK` ≥ machine count and `minSigs` ≤ `clusterSize`, which every real-network test uses.

The accepted text, to land in the docs (see *Docs*):

> **Root at the tail's storage group.** A collection's reactivity tree is rooted at its log tail block's own ring position: `coord_0` for a reactivity topic is the routing coordinate the key network assigns `routingKeyForBlock(tailId)`, not `H(0x00 ‖ topicId)`. The root (announcing) group is the tail block's storage group, chosen by the same rule the key network uses for storage — `findCluster`'s network-scoped selection, with reactivity's root `wantK` equal to `clusterSize` — so the machines that apply a commit are exactly the machines that announce it. Every party that derives the root group — the origination gate, the notification verifier, the subscriber's registration walk and the forwarder — uses that one rule.
>
> **Threshold from the verifier's side.** A notification carries the commit certificate as its signature. A verifier accepts it when its signers are members of the root group it derived itself and number at least `ceil(|root group| × superMajorityThreshold)` — the same threshold the commit certificate is captured under (`captureCommitCert`). The threshold is never read from the notification. The cohort-topic default `minSigs` (14) does not apply to the reactivity root.

The third paragraph of the accepted text — tiers `d ≥ 1` addressed by a stable `collectionTopicId` so only the root moves on rotation — is **not** this ticket; it is planned in `reactivity-tiers-below-the-root-use-the-collection-anchor`. Here the topic id stays `H(tailId ‖ "reactivity")` and tiers `d ≥ 1` keep `coord_d(P, topicId)`; do not write that third paragraph into the docs yet.

## Changes

**One root key, one rule.** The reactivity root key is the tail's routing key bytes — `reactivityTailBytes(tailId)` in `packages/db-p2p/src/reactivity/topic-bytes.ts` is already `utf8(tailId)`, the `routingKeyForBlock` encoding. So `rootCoord = H(reactivityTailBytes(tailId))`, byte-identical to `hashKey(routingKeyForBlock(tailId))`. Pin that equality in `topic-bytes-encoding.spec.ts` (db-p2p can import FRET's `hashKey`; db-core cannot) — this is the cross-implementation contract every party leans on, so it is worth its one test.

**Key network.** Expose the coordinate form of the storage rule on `Libp2pKeyPeerNetwork`: split `assembleServingCohort(key)` into `hashKey(key)` plus a coordinate-taking assembly, and add a public method (e.g. `servingCohortAt(coord): Promise<string[]>`) returning the cohort ids. `findCluster(key)` must keep calling the same assembly, so storage placement and root placement cannot drift. Bind the host option `rootGroup = { membersAt: (c) => keyNetwork.servingCohortAt(c), quorumRatio: consensusConfig.superMajorityThreshold }` in the cohort-topic block of `createLibp2pNodeBase`.

**Origination gate.** Replace `createReactivitySelfMembershipGate` (delete the module and its FRET read) with: a change event originates iff it carries a `tailId` **and its `blockIds` include that tail** — this node applied the tail block's commit, i.e. it is in the tail's storage group as the commit's coordinator chose it. The bridge's existing "no retained commit cert → skip" stays. Rename `selfIsCohortMember` in `packages/db-p2p/src/cohort-topic/change-bridge.ts` to say what it now tests. This excludes the sweep commit that lands a collection's *data* blocks (or the old tail's `nextId` rewrite on a rollover) on another group: that group holds a certificate for the same action but did not apply the tail.

**Notification verifier** (`packages/db-core/src/reactivity/verify.ts`): `expectedCoord = rootCoord(b64urlToBytes(n.tailId))` (`n.tailId` is the base64url of the tail bytes) and pass `RootPlacement { quorumRatio }`; `quorumRatio` becomes a required dep. db-core may add a small `reactivityRootCoord(tailBytes, hash)` helper beside `reactivityTopicId` in `topic-anchor.ts` so origination, verification and the harness share one derivation. The node's `verifierFor` passes `consensusConfig.superMajorityThreshold`.

**Subscriber walk.** `ReactivitySubscriptionManager.register` passes `rootKey: tailIdAtAttach` (already the tail bytes) on `service.register`; the walk's root step then goes through the host router's `routeToRoot`.

**Forwarder-side root-group reads.** Each site in the reactivity block of `createLibp2pNodeBase` that derives "the cohort for this topic" from `fret.assembleCohort(reactivityAddressing.coord0(topicId), cohortWantK)` switches to the root group of the topic's **tail** — a topic id cannot be inverted, so each site keys on a tail it already holds:
- push-state gossip `cohortCoord` and the `isCohortMember` gate: the push state's `tailIdAtJoin`;
- the recover transport's `resolveCohort`: the request's tail (`latestKnownTailId`) — change `resolveCohort` to take the tail bytes and return a promise;
- `resolveChildPrimary` is for child cohorts (tier `d ≥ 1`) and stays on FRET.
Delete `reactivityAddressing`'s `coord0` use from those sites; the matchmaking query handler keeps its own `coord0`.

**Harness.** `packages/db-p2p/src/testing/reactivity-mesh-harness.ts` derives `coord0(reactivityTopicId(tailId))`; move it to the root coord so the mock-tier `mesh-*.spec.ts` suites keep exercising what production does.

**Option comment.** `cohortTopic.wantK`'s comment says it must match the host so "the membership gate checks the same cohort"; the gate is gone — say what `wantK` still governs (non-root cohorts).

## Edge cases & interactions

- **Ring wider than a storage group** — the reason for this ticket. Integration test (below).
- **Small groups keep working**: every existing real-network spec (all machines in every group) must stay green — the root group is then the whole mesh, threshold `ceil(n × 0.75)`.
- **Three-member group**: only the coordinating member retains a certificate (the `NOTE:` on `captureCommitCert` in `packages/db-p2p/src/cluster/cluster-repo.ts`), so one member originates. Unchanged and acceptable; inspection.
- **Solo group (`clusterSize: 1`)** never produces a certificate, so never announces — out of scope (a separate rough edge noted in the decision; the Quereus plugin's node runs `clusterSize: 1`). Do not paper over it.
- **Read-driven promotion events** have no `tailId` and never originate (unchanged).
- **Coordinator view vs root-node view disagree under churn**: the certificate's signers come from the coordinator's `findCluster`, the published membership from the root node's; a signer outside the published group makes the notification untrusted, and the watch service's tail check (about 30 s) still wakes the watcher. Inspection; mention in the docs' failure-mode text.
- **`superMajorityThreshold` differs between machines**: a verifier uses its own value. Consensus already requires one value per deployment; say so in the docs rather than adding a check.
- **Rotation** keeps its current shape (whole-tree move per tail), now with a root that moves to each new tail's storage group. `ReactivityOriginationManager`'s rotation detection reads `event.tailId` changes and is unaffected by the gate change, because the rollover commit lands on the new tail's group with that group's tail in `blockIds`.
- **Mixed versions**: an old-build subscriber registers and verifies at the old coordinate and will not interoperate with a new-build root. A protocol break, accepted ("no backwards compatibility yet"); note it in the docs' reversibility line.
- **Distant subscribers trust the root's membership on first use** — tracked by `feat-reactivity-root-membership-anchored-by-the-commit-log` (plan), which depends on this ticket. Do not expand scope.

## Tests

- `topic-bytes-encoding.spec.ts`: the root coordinate db-core derives for a tail equals `hashKey(routingKeyForBlock(tail))`.
- `change-bridge.spec.ts`: replace the membership-gate cases with the tail-applied rule — originates when `blockIds` includes `tailId`, not when only data blocks landed. Drop tests that only exercised the deleted FRET gate.
- `substrate-real-libp2p.integration.spec.ts` (env-gated, `OPTIMYSTIC_INTEGRATION=1`): a mesh wider than one storage group (e.g. six nodes, `clusterSize: 3`, `cohortTopic.enabled`), a watch through `node.reactivityWatch` on a node **outside** the tail's storage group, a commit from another node; assert the watcher is woken by a delivered notification — count deliveries through `node.reactivitySubscribers` or make the bound tighter than the watch tick — not by the 30 s tail check. This is the reproduction of the defect; it fails before this change.
