No plugin change. Every existing path must behave exactly as today while no segment is sealed; the existing db-core suites are the safety net for that.

## The shape

A `Collection` today holds one list, `pending`, of staged actions. It becomes two things, kept in a small new module `packages/db-core/src/collection/segments.ts` so the collection file does not grow by another few hundred lines (see backlog `debt-collection-write-retry-logic-outgrew-its-file`):

```ts
/** A queue entry's id, opaque to the collection. */
export type EntryId = string;

export type SealedSegment<TAction> = {
	readonly entryId: EntryId;
	/** Exactly the actions the entry staged into this collection, in staging order (invariant 3 of the doc). */
	readonly actions: readonly Action<TAction>[];
	/** The refusal recorded for this segment, once a replay refused it. A refused segment is excluded from every later replay until it is dropped. */
	refused?: ActionRefusedError;
};

export class SegmentList<TAction> {
	/** Sealed segments in queue order, oldest first (invariant 1). */
	sealed: SealedSegment<TAction>[];
	/** The open segment: what the current transaction has staged. */
	open: Action<TAction>[];
	/** Bumped on every change to the sealed list: a seal, a drop, a head removal, a refusal recorded. Captured by a snapshot so a restore can tell whether the sealed segments it was taken over are still the ones in place (see the next ticket). */
	version: number;
}
```

Keep the pure list operations (seal, drop by id, head, lookup, the counts) on `SegmentList`, and keep everything that touches the tracker or the latch on `Collection`. The collection replaces its `pending` field with a `SegmentList`; the 23 sites that read `this.pending` today each become one of: the open segment (`act`, `getPendingActions`, `clearPendingActions`, `unstage`, `filterAgainstEntry`, `consumeOwnEntry`, `syncAttempts`), or every replayable action (`replayActions`, and the counts in `mustReplay`, `restageIfBasesMoved`, `hasUnsyncedChanges`). The split is the point of the ticket, so decide each site deliberately and say which in a one-line comment where it is not obvious.

## The refusal class

Replay has to recognise "this action can no longer be applied over the committed state" without the collection importing the tree module (the tree already imports the collection). Add to `packages/db-core/src/collection/struct.ts`:

```ts
/** A handler's statement that an action cannot be applied over the committed state it is being
 * replayed against — a uniqueness or lost-update check failed. Not a transport failure and never
 * retryable: the action's staged writes are discarded (the handler runs inside an Atomic), and
 * nothing downgrades it to a stale failure. TreeGuardRefusedError is the tree's subclass.
 * Segment-aware replay (Collection.replayActions) treats a throw of this class from a SEALED
 * segment as that segment's refusal and keeps going; from the open segment it propagates as today. */
export class ActionRefusedError extends Error {
	constructor(readonly collectionId: CollectionId, message: string) { /* … */ }
}
```

`TreeGuardRefusedError` extends it (keep its own `key` field and name). `classifyCommitFailure` and the Quereus bridge keep matching `TreeGuardRefusedError`, which still works through the subclass; nothing else needs to change for them.

## The collection's new members

- `sealPending(entryId): boolean` — closes the open segment into a sealed one owned by `entryId`. Returns false and changes nothing when the open segment is empty (an invented collection's header transforms are not an action and are not sealed; see below). Throws if `entryId` is already sealed here. Synchronous and latch-free by contract, like `snapshotPending`: the caller brackets it.
- `sealedEntries(): EntryId[]` — in order.
- `sealedRefusal(entryId): ActionRefusedError | undefined` — the recorded refusal, if the segment was excluded from replay.
- `dropSealed(entryId): Promise<void>` — under the collection latch: remove the segment wherever it sits, bump the version, then `replayActions()`. A later segment whose guard now refuses is recorded and reported during that replay (the cascade of [§Removing an entry](../../docs/offline-sync.md#removing-an-entry) is the queue's job in stage 3; this ticket only makes the second refusal observable). Throws for an unknown id.
- A constructor-time callback in `CollectionInitOptions`: `onSealedRefused?: (entryId: EntryId, error: ActionRefusedError) => void`. Called once per refusal discovery, synchronously from inside the replay, under the latch. A throwing callback is caught and logged (`collection:refusal-callback-threw`), never allowed to abort the replay. Document that the callback must not call a latched method of this collection synchronously (it would deadlock on the non-reentrant latch); the stage-3 queue schedules its reaction.

## Segment-aware replay

`replayActions()` becomes:

1. Reset the tracker to the collection's **invented baseline** when it holds no committed revision (`source.actionContext === undefined`), and to empty otherwise. The baseline is the tracker's transforms right after `createOrOpen`'s create branch has staged the header, the empty log and (for a tree) the empty root — captured there with `copyTransforms` into a new private field, never cleared (it is read only while no context has been adopted, which is the exact state in which those blocks are not in storage). Today a replay on an invented collection would drop its header, the hazard `mustReplay` and `snapshotPending` describe; `dropSealed` on an invented collection with sealed segments is the first path that reaches it. Capture the baseline from the same tracker `Log.open` wrote into, after that call.
2. For each sealed segment, in order, skipping those already refused: stage the whole segment through ONE `internalTransact(...segment.actions)` call, so a throw discards the entire segment's writes (the Atomic inside it already gives that). Catch `ActionRefusedError` only: record it on the segment, bump the version, log `collection:sealed-segment-refused id=… tag=… entry=… error=…`, call `onSealedRefused`, continue. Any other error propagates as today.
3. Then the open segment, one `internalTransact` per action, exactly as today — a refusal there propagates, which is the live transaction's own refusal ([§Replay with a per-segment refusal](../../docs/offline-sync.md#replay-with-a-per-segment-refusal) keeps today's behaviour for it). The existing NOTE at `updateInternal`'s replay call about a half-replayed tracker still describes the open segment; sealed segments are now atomic per segment, so say so in that NOTE rather than leaving it to imply the whole replay.

`mustReplay` and `restageIfBasesMoved` count replayable actions (non-refused sealed plus open), not the open segment alone: a refresh that adopts a newer revision must re-stage every sealed segment too.

## The success-branch reorder in `syncAttempts`

The baseline rule makes the dormant defect in `syncAttempts`' success branch live: today it resets the tracker, replays, and only then folds the committed transforms into the cache and adopts the revision. With the baseline, a replay run before the adoption on an invented collection's first commit would reinstate the header insert over the now-committed header, and `hasUnsyncedChanges()` would never turn false. Move the fold (`sourceCache.transformCache`) and the context adoption above the replay, which is the order `updateInternal` and `TransactionCoordinator.commitOnceLatched` already require, and delete the NOTE that described it as dormant. This also makes the order right for the head commit (third ticket), where staging genuinely happens while the transact is in flight.

## Whole-collection commits refuse over sealed segments

`sync`, `updateAndSync` and `actAndSync` commit everything staged as one log entry; over sealed segments that would merge several queue entries into one entry and one action id, which the queue's identity rules forbid. Add `SealedSegmentsError` to `collection/struct.ts` (collection id, the sealed entry ids) and throw it from `syncInternal` before minting an action id, and from `getPendingActions()` — the coordinator's only use of it is the same whole-collection append (`commitOnceLatched`), and that throw lands in its existing catch, which restores every participant. `actAndSync` checks before staging, so there is nothing to unstage. `clearPendingActions()` clears the open segment only (the coordinator calls it after committing exactly what `getPendingActions()` returned, which cannot have included a sealed segment). The stage-3 queue commits sealed segments through `commitHead` and a coordinator slice; until then no caller seals, so no caller meets the error.

`hasUnsyncedChanges()` keeps its formula (open segment non-empty, or tracker transforms non-empty — which now includes sealed effects). Its doc comment must say that `sync` refuses while segments are sealed, so a caller that loops on it over a sealed collection gets the typed error rather than a silent no-op.

`filterAgainstEntry` (the `filterConflict` hook) applies to the open segment only. A sealed segment's action list is the entry's own and is never rewritten (invariant 3); `Tree` and `Diary` install no hook, so nothing observable changes.

`consumeOwnEntry` for a `sync` write still drops the leading actions of the open segment (no sealed segment can exist in a `sync`, see above). Leave its head-segment form to the third ticket, but shape the slice so that ticket can add the sealed arm without touching the open one.

## Edge cases & interactions

- **No sealed segment, every existing path.** By inspection of each `pending` site, and by the whole db-core suite unchanged. In particular `retry-resends-identical-transforms.spec.ts`, `own-entry-completes-the-action.spec.ts`, `collection-own-action-replay.spec.ts`, `two-handle-collection-fork.spec.ts` and `tree-guard.spec.ts` exercise every path this ticket touches.
- **Seal with an empty open segment.** Returns false; the version is not bumped; an invented collection's header is not an action and stays in the tracker, owned by no segment. Test.
- **Refusal in a sealed segment found by a refresh a live read triggered.** `update()` adopts the rival, the replay records the refusal, calls the callback and completes; the read proceeds and sees the collection without that segment's effect. Test over `Tree` with `commitRivalTreeWrite` taking a key the sealed segment inserted under an `absent` guard; assert the callback's `(entryId, error)`, `sealedRefusal(entryId)`, that the segment is still listed by `sealedEntries()`, and that the read returns the rival's entry.
- **Refusal in the open segment.** Propagates out of `update()` exactly as today; no callback, nothing recorded. By the existing collection.spec "external commit visibility after conflict replay" cases plus one assertion in the new spec that the callback was not called.
- **A refused segment stays excluded.** A second refresh does not replay it and does not call the callback again. Test with two refreshes.
- **`dropSealed` of a non-head segment** with a later segment that depended on it (the later segment updates a row the dropped one inserted, under an `unchanged` guard): the replay after the drop refuses the later segment and reports it. Test. Also `dropSealed` of a refused segment clears it; the remaining segments replay cleanly.
- **Invented collection with sealed segments.** `createOrOpen` on a fresh id, seal two segments, `dropSealed` the first: the header, log and root survive the replay (the tree is still readable, and `hasUnsyncedChanges()` is true), and the second segment's entries are visible. Test. `commitHead` of such a collection is the third ticket; here, assert only the staged state.
- **An invented collection whose refresh finds the collection exists elsewhere** (collection.spec "concurrent creation" cases): context becomes defined, the replay resets to empty, the baseline is not used. Existing tests.
- **Atomicity of a sealed segment's replay** versus the open segment's: a sealed segment of three actions whose third refuses leaves none of the three staged; the open segment keeps today's half-replayed shape (backlog `debt-a-failed-refresh-can-leave-a-collection-half-restaged` is about that shape and is unchanged by this ticket). Test the sealed half.
- **`sync` over sealed segments** throws `SealedSegmentsError` and leaves everything staged. Test. The coordinator's commit over such a collection throws it out of `commit()` with every participant restored (its existing catch); by inspection, one assertion in the test.
- **The callback throwing.** Logged, replay completes, refusal recorded. Test.
- **Concurrent access.** `sealPending` is synchronous and latch-free like `snapshotPending`; `dropSealed` takes the latch like `update`. The version counter is read and written only under the latch or from synchronous callers; by inspection.
- **Base pins.** A per-segment atomic replay pins bases through `Atomic.commit` → `Tracker.absorb`, the same path `act` uses; nothing new. By inspection.
