First of five tickets for stage 4 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). This one puts the db-core queue (`OfflineQueue` in `packages/db-core/src/offline/queue.ts`, stage 3) behind the plugin: entering and leaving the mode, sealing a transaction's staged trees into an entry at commit, the SQL-level statuses, and the durability reports for drained entries. The four tickets after it add removal announcements (`4.2-offline-sync-plugin-removal-announcements`), the per-table policy and network acknowledgement behind a queue (`4.3-offline-sync-plugin-table-policy-and-network-ack`), the schema-change gate and the invented-collection probe (`4.4-offline-sync-plugin-ddl-gate-and-invented-collections`), and the read degrade plus the stage's close-out (`offline-sync-plugin-offline-mode`). Everything here is in memory; persistence is stage 5 (`5-offline-sync-journal`) and the real reachability port is stage 6 (`6-offline-sync-cohort-reachability`).

## Design

### One controller per registered plugin

A new class, `OfflineMode` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`, owns everything the application sees under `plugin.offline`. `register(db, config)` in `packages/quereus-plugin-optimystic/src/plugin.ts` builds one per `Database`, hands it the `Database`, the `TransactionBridge` and the `CollectionFactory`, and exposes it as `plugin.offline`. The bridge gets a reference through a setter (`TransactionBridge.attachOfflineMode`), since the two refer to each other and the bridge's constructor is used bare in tests.

The controller holds **one `OfflineQueue` per `Database`**, built at registration. The queue's drain loop starts on the first `enqueue`, so an idle queue costs nothing. Its options come from the registration config, read in `plugin.ts` from `config.offline` (function-typed and object-typed config can only arrive through `register()`, like `rawStorageFactory`):

```typescript
offline?: {
  expireAfterMs?: number;        // OfflineQueueOptions.expireAfterMs
  outcomeRetentionMs?: number;   // how long a terminal outcome stays in outcomes() / status(); default 7 days
  recheck?: { baseMs?: number; maxMs?: number };  // OfflineQueueOptions.recheck; documented as advanced, tests shorten it
}
```

`journal` arrives with stage 5 and `allowSoloCommit` with stage 6; refuse unknown keys under `offline` with a clear error rather than ignoring them, so a misspelt `journal` is not silently a no-journal configuration later.

**The queue no longer takes a transactor.** `OfflineQueue`'s constructor becomes `new OfflineQueue(options)`, and `send` builds its per-entry `TransactionCoordinator` over the remaining collections' own `transactor` (`Collection.transactor` is public), throwing a defect when they differ. The plugin cannot name one transactor at registration (a `Database` can mix them per table, see `legacyBatch` in the bridge), and the queue only ever used it for that coordinator. Update the two existing constructions in `packages/db-core/test/offline-queue.spec.ts` and `packages/db-p2p/test/offline-queue-mesh.spec.ts`.

**The refusal callback reaches every collection.** `Collection.onSealedRefused` is fixed at construction, and the plugin's collections are built before any `enter()`. `CollectionFactory` therefore takes a stable listener (`CollectionFactory.setSealedRefusedListener`, set once by `register`) and passes `{ onSealedRefused }` as the `options` argument of every `Tree.createOrOpen` and `Tree.open` it makes (`createOrGetCollection` and `getCollection`). The listener forwards to the controller's queue (`OfflineQueue.onSealedRefused`). Index trees and the schema catalog tree go through the same two factory methods, so nothing else needs wiring.

### Entering and leaving

- `plugin.offline.enter()` throws a typed `OfflineModeRefusedError` (reason `'session-mode'`) while `TransactionBridge.isTransactionModeEnabled()` is true ([§Session mode](../../docs/offline-sync.md#session-mode)). Conversely `TransactionBridge.configureTransactionMode` throws while the mode is entered or the queue is non-empty, so the two cannot be combined in either order.
- `enter()` and `exit()` only flip a flag and publish the queue state (`mode` changes). Neither touches the open transaction or the drain.
- `plugin.offline.whenDrained()` is `OfflineQueue.whenDrained`. `plugin.dispose()` disposes the queue (after the bridge) so a pending `whenDrained` rejects with `QueueDisposedError`; entries stay sealed in their collections, as the queue documents.

### The acknowledgement is fixed when the transaction begins

`TransactionState` in `packages/quereus-plugin-optimystic/src/types.ts` gains `acknowledgement: 'local' | 'network'`, set in `TransactionBridge.beginTransaction` from the controller's flag (`'network'` when no controller is attached). A mode change during an open transaction changes nothing about it ([§Entering and leaving the mode](../../docs/offline-sync.md#entering-and-leaving-the-mode)). Session mode is never `'local'`, by the two refusals above.

### Sealing instead of committing

In `TransactionBridge.commitTransaction`, the legacy route (`commitDirtyTreesLegacy`) is replaced for a `'local'` transaction by one call: `offline.enqueue(dirtyTrees, stampId)`. The controller seals each dirty tree's collection (`OfflineQueue.enqueue(collections, { id: stampId, timestamp: Date.now() })`), so the entry id **is** the transaction's `StampId()`. A transaction that staged nothing enqueues nothing (`enqueue` answers `undefined`), exactly as a commit that wrote nothing reports nothing today.

Local acknowledgement needs the shape `legacyBatch` accepts, with the single-tree case allowed too: every dirty tree has a collection (`getCollection` defined), the collections share one transactor, and no two dirty trees are separate instances over one collection id. A dirty set that fails those checks takes today's network-acknowledged route for that transaction and logs `offline:local-ack-unavailable` with the reason. Two instances over one id would seal two segments under one entry id that the coordinator's id-keyed map collapses; the sweep already refuses to batch them for the same reason.

After sealing, the transaction is torn down the way a successful commit is (`isActive = false`, statements, dirty set and savepoints cleared), **without** clearing the degraded latch: nothing reached storage, so nothing was reconciled.

Session mode's route and the network-acknowledged legacy route are unchanged. With the mode off and nothing queued, every commit takes exactly today's path.

### Statuses

The controller subscribes to `OfflineQueue.onStatus` and `onQueueState` once and translates ([§Following transactions](../../docs/offline-sync.md#following-transactions)):

- `entryId` → `transactionId`; `collections` → `tables`, the deduplicated qualified names the bridge recorded for those collection ids (`TransactionBridge.collectionTables`, exposed read-only to the controller; an index collection maps to its table). A collection the bridge knows no table for is dropped from `tables`, as `sqlCommitDurability` drops it.
- `queued` carries `seq`, `tables`, `waitingFor`, plus the db-core extras (`attempts`, `inDoubt`, `lastError`, `committedCollections` as `committedTables`). `persisted` and `outlook` are later stages; leave them off.
- `committed` is the entry's `SqlCommitDurability` plus `kind` and `transactionId`: the controller calls `TransactionBridge.reportCommitDurability(entryId, durability)`, which becomes package-visible and **returns** the report it built (`SqlCommitDurability | undefined`), so `onCommitDurability` listeners, the `DurabilityFollower` and `onCommitFullyHeld` behave exactly as for an online commit ([§Durability reports](../../docs/offline-sync.md#durability-reports-and-the-full-replication-event)). The report is built, and the commit followed, whenever a durability listener, a fully-held listener **or** an offline status listener is registered; the status carries its `followed`.
- `partially-committed` maps `committedCollections` / `pendingCollections` to tables and keeps `cause`.
- `failed` carries `reason`, `causedBy`, `committedTables`, and `error` mapped through `TransactionBridge.mapCommitRefusal`, so a guard refusal arrives as the engine's `ConstraintError` or the plugin's `ConcurrentModificationError` with the db-core refusal on `cause`. The removal's `changedCollections` is kept on the SQL status as `changedTables`; ticket 4.2 consumes it.
- `queued` is delivered synchronously inside `commit`, before it resolves: `enqueue` emits synchronously and the translation is synchronous, so a host wrapping `db.exec` can attribute it (the same rule `onCommitDurability` relies on).
- A listener that throws is logged and the next still runs (`notifyListeners` in the bridge is the model).

Queue state is db-core's `OfflineQueueState` plus `mode: 'offline' | 'online'` and `readsServedLocally` (always `false` until ticket `offline-sync-plugin-offline-mode`). Published when either changes.

### Queries and actions

`entries()` translates `OfflineQueue.entries()`. `status(transactionId)` answers the queued status, else a retained outcome, else `undefined`. `discard(transactionId)` forwards and lets `EntryNotDiscardableError` / `UnknownEntryError` propagate. `outcomes()` lists terminal statuses (`committed`, `failed`) retained since they were emitted, pruned lazily on every access and every new outcome once older than `outcomeRetentionMs`; `acknowledge(transactionId)` forgets one. No timer.

## Edge cases & interactions

- **Mode switch during an open transaction.** `enter()` or `exit()` between `begin` and `commit` leaves the acknowledgement as fixed at begin. Test: begin, insert, `enter()`, commit → network acknowledged (no `queued` status, row committed); and the mirror with `exit()`.
- **`exit()` with entries queued.** The drain continues; the next transaction is network-acknowledged. Until ticket 4.3 lands, such a commit goes straight to the network ahead of the queue; note that gap in the README and close it there. Test: queue two entries while the cohort is unreachable, `exit()`, reconnect, `whenDrained` → both committed.
- **Local acknowledgement with a dirty set that cannot batch** (two tables over one URI; trees without a collection). Falls back to network acknowledgement and logs. Verified by inspection plus one test for the shared-URI case (model: `test/legacy-batch-shared-collection-id.spec.ts`).
- **A transaction that staged nothing** in offline mode: no entry, no status, commit resolves. Test: a `select` in offline mode.
- **The queue's `whenDrained` and `dispose`.** `plugin.dispose()` while entries are queued disposes the queue; entries stay sealed; `whenDrained` rejects. By inspection.
- **Session mode in either order.** `enter()` after `configureTransactionMode` throws; `configureTransactionMode` after `enter()`, or with a non-empty queue, throws. Test both arms with the `enableSessionMode` helper from `test/sql-commit-durability.spec.ts`.
- **A `queued` status for an autocommit statement** is delivered during the `db.exec` that committed it. Test: a listener records the status while an `await db.exec('insert …')` is in flight.
- **The degraded latch** is neither set nor cleared by a local acknowledgement. By inspection.
- **Discard before and after send.** `discard` of a never-sent entry fails it with `discarded` and its row disappears; `discard` of a sent entry throws `EntryNotDiscardableError`. Test on the mesh with `failures.failingPeers` holding the other node unreachable for the first and a write-ahead observation (or the `submitting` status) for the second.
- **Expiry.** `expireAfterMs` reached while unreachable fails the entry with `expired`. Test with a short `expireAfterMs` and `recheck.baseMs`.
- **Two queue consumers of one collection.** The factory's listener forwards every collection's refusals to this `Database`'s queue; a refusal for an entry it does not hold is ignored by the queue (`offline:refusal-for-unknown-entry`). By inspection.
- **The single-writer bridge state** (`currentTransaction`, `dirtyTrees`, `savepoints`) is never read or written by the controller or the drain ([§The single-writer bridge](../../docs/offline-sync.md#the-single-writer-bridge)). By inspection; the reviewer checks the diff.
