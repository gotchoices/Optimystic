# A block's bytes can be deleted

## Why

There is no way to remove a block from a node. `IRawStorage` has a delete for exactly one thing — a pending transform — and its own documentation says so twice: "`RawStoreDriver` has no revision delete at all", and "a stored proof is kept as long as any revision refers to it — forever, since no revision-delete site exists". Invalidations are handled by writing compensating *forward* revisions rather than removing anything.

So a node that stops being responsible for a range keeps every byte of it. The ring handoff already releases responsibility safely (`docs/arachnode-ring-handoff.md` § Part 2, Phase C) and collects the released block ids in a set the node factory calls `gcEligibleBlocks`, under a comment saying a future sweep must consult it — and there is nothing for that sweep to call. This ticket builds the one operation it needs. The sweep itself, and the rule about *which* blocks may be given to it, is the next ticket.

## What to build

One operation at each layer, named the same thing, doing exactly one thing: remove everything this node holds for one block id.

### At the backend

`BatchBackend.deleteBlock(blockId)` — remove the block's records from the six **block-scoped** stores (metadata, revisions, pending, transactions, materialized, proofs), each backend in its own idiom, which is where this belongs: the filesystem backend removes the block's directory, the LevelDB backend deletes each tag's block-envelope key range, the SQLite backend deletes by `blockId` across its six tables in one transaction, the IndexedDB backend deletes each object store's block key range, and the memory driver drops the block's entries from its maps.

The seventh store, **commit proofs, is explicitly not touched**: it is keyed by a consensus message's hash alone, one entry per message however many blocks that message covered, so an entry may still certify revisions of blocks this node keeps. Deleting it by block is not a thing the key shape allows. The bytes it leaves behind are the subject of the backlog ticket `debt-unreferenced-commit-proofs-are-never-swept`, and the contract notes on `IRawStorage.getBlockProof` and `saveBlockProof` — which today say no delete site exists — must be rewritten to say that one does, that it removes the revisions' *entries* in the proofs store, and that the proof bodies it orphans are not yet swept.

Why a backend operation rather than a composition in the kernel over per-store deletes: the kernel cannot enumerate a block's revisions without knowing where they end. `rangeRevisions` is a bounded `[lo, hi]` scan, and the filesystem backend walks it rev-by-rev — so there is no "every revision of this block" range to ask for, and the top revision is only knowable from the metadata this operation is itself removing. Every backend already has a cheap native answer for "everything under this block"; asking each for it is both simpler and faster than any composition.

### At the driver

`RawStoreDriver.deleteBlock(blockId)`. **Required, not optional** — the same reasoning `flush` and `whenDurable` carry: a wrapper that forgets to forward it must not type-check. Three wrappers, three different jobs:

- `WriteGroupDriver` holds writes in an in-memory overlay until the group is flushed, so it must **flush the group first** and only then delegate to the backend. Otherwise an overlay put for the block would be applied after the backend delete and resurrect it. A full flush is wider than the one block, which costs nothing here: deleting is not a hot path.
- `CachedStoreDriver` must invalidate everything it caches for the block before delegating, or a later read is served content the backend no longer has.
- `RawStorageDriverAdapter` delegates to the `IRawStorage` it fronts.

### At the storage and the block

`IRawStorage.deleteBlock(blockId)`, composed in `KvRawStorage` over the driver, and `IBlockStorage`/`BlockStorage.deleteBlock(latch)` above it.

The latch is not optional. Invariant 2 of `packages/db-p2p/docs/storage.md` is that every write to a block holds that block's single write latch, and a delete is the widest write there is: a concurrent pend or commit that interleaves with it would write records back under a block whose metadata has just gone, leaving content no listing reports. `BlockStorage.deleteBlock` therefore takes a `BlockWriteLatch` and `assertLatch`es it exactly as `restoreRevision` and `savePendingTransaction` do, and the sweep in the next ticket acquires the latch the ordinary way.

### Order, idempotence and a crash in the middle

The operation is **not** atomic across stores, and does not need to be, provided it is ordered and resumable:

1. **Metadata first**, then a flush. Metadata is what makes a block present: once it is gone, `getMetadata` answers `undefined`, `listBlockIds` (which enumerates metadata keys only) stops reporting the block, and a restart's owned-block seeding does not re-adopt it. The block reads as one this node does not hold, which is the state the delete is driving toward.
2. **Everything else after**, then a flush.

A crash between the two leaves content with no metadata: bytes nothing serves and nothing reports. That is the orphan the next ticket's durable eligibility ledger exists to finish — its entry is written before the delete begins and removed only after it completes, so the sweep re-runs `deleteBlock` for the same id after a restart. Which makes **idempotence a requirement, not a nicety**: `deleteBlock` on a block with no metadata must still remove whatever content is there, and on a block with nothing at all must resolve quietly. Each backend's native "delete everything under this prefix" already behaves that way; the filesystem one must treat a missing directory as success (`ENOENT` only — every other error surfaces, the discrimination `directoryByteSize` and `listPendingActionIds` already make).

The reverse order was considered and rejected: deleting content first leaves metadata naming a `latest` whose revision record is gone, so the block still reads as held and every read of it fails inside materialization. A block that reads as absent is a state the whole system already handles; a block that reads as present and then throws is not.

## Edge cases & interactions

- **A read in flight.** A `get` that read metadata before the delete and materializes after it sees a revision record that is gone. It fails rather than returning wrong content, which is the right direction — but the sweep must only ever be given blocks the node has already stopped serving (the next ticket's invariant), so this is the window between release and delete, not an ordinary read. Verified by inspection; nothing here needs to serialize against readers beyond the latch.
- **The read cache.** `CachedStoreDriver` can sit either above or below the kernel (both constructions are documented on `IRawStorage.readCached`). Both compositions must end up invalidating: the wrapper's own `deleteBlock` covers the `new CachedRawStorage(inner)` shape through `RawStorageDriverAdapter`, and the `new KvRawStorage(new CachedStoreDriver(driver))` shape through the driver method. Check both by reading the two constructions, not one.
- **`promotePendingTransaction` and the delete.** Promote is the kernel's one cross-store atomic move. Under the block's latch the two cannot interleave, so nothing more is needed — but do not relax the latch requirement to make the sweep cheaper.
- **The owned-block set and the monitors.** A released block is already untracked from `ownedBlocks` at Phase C, before it is ever eligible, so the delete does not need to touch either monitor. If a block somehow reaches the delete while still tracked, the next tick's listing simply no longer finds it. Verified by inspection of the release callbacks in `libp2p-node-base.ts`.
- **Collection change notifications.** Every other write path emits a change so trackers and the reactivity layer see it. A delete emits **nothing**: the block's content has not changed, the node has stopped holding it, and a change event would make readers re-read a block this node is deliberately no longer the place to ask. State this in the doc rather than leaving it to be rediscovered.
- **Block archives and restoration.** Deleting a block does not invalidate any archive already served, and a later read repairs from the cohort through `RestorationCoordinator` as it does for any block this node does not hold.
- **A backend handed a shared handle.** The SQLite, IndexedDB and LevelDB backends share one database with the node's key-value and piece stores. The delete must be scoped to the block-scoped stores' own key ranges or tables and must not touch the key-value store's namespaces (`NODE_KV_NAMESPACES`). Verified per backend by reading its key construction.

## Tests

Two, both in the existing conformance spec `packages/db-p2p/test/kv-raw-storage.spec.ts`, so every backend composition the suite runs gets them:

- **`deleteBlock` removes every block-scoped store's records for its block and leaves another block's untouched** — write metadata, two revisions with their proofs, a pending transform, a transaction and a materialization for two blocks, delete one, assert every read for it answers `undefined` and every read for the other is unchanged. This is the operation's whole contract on branching logic across seven stores, and it is the one thing a backend can implement subtly wrongly (one key range off).
- **`deleteBlock` is idempotent and finishes a half-done delete** — call it twice, and call it on a block whose metadata has already been removed but whose revisions remain; both must resolve and leave nothing behind. This pins the resumability the next ticket's ledger depends on.

Nothing else: the per-wrapper forwarding is forwarding, and the latch assertion is the shape `BlockStorage` already tests nowhere and enforces by one shared private method.
