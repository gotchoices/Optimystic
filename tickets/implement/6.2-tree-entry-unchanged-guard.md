description: Let a staged tree write or delete declare "the entry I am replacing must still be exactly the one I read", so that when another machine changed or removed that entry in the meantime the commit is refused instead of silently overwriting or resurrecting it.
files: packages/db-core/src/collections/tree/struct.ts, packages/db-core/src/collections/tree/tree.ts, packages/db-core/src/index.ts, packages/db-core/test/tree-guard.spec.ts, docs/internals.md
difficulty: medium
----

## Why

`fix/concurrent-row-changes-leave-orphaned-index-entries` (now split into this ticket and `refuse-concurrent-row-change-loser`) reproduced five ways two machines can leave a secondary index pointing at a value no row holds, or at a row that no longer exists. Every one has the same root cause: the SQL layer stages a main-table upsert or delete as a **bare** action, while the index delta it stages beside it was computed from the row image the statement read. When a rival's commit changes that image first, the loser's conflict replay re-applies the bare main-table action over the rival's row (a same-row UPDATE silently wins, a DELETE removes a row the rival just changed, an UPDATE resurrects a row the rival deleted) and its stale index delta lands beside it.

The tree already has the mechanism to refuse a loser at replay: `TreeEntryGuard` in `packages/db-core/src/collections/tree/struct.ts`, enforced by the `replace` handler in `buildInit` (`packages/db-core/src/collections/tree/tree.ts`) on initial staging and on every conflict replay. Its three kinds (`absent`, `keepExisting`, `absentRange`) all express "nothing may be here". None can express "what is here must still be what I read", and the handler never evaluates a guard on a delete entry at all (the `if (entry)` branch). This ticket adds that guard kind; the sibling plugin ticket stages it from every write path.

## Design

### A fourth guard kind

```ts
export type TreeEntryGuard<TKey, TEntry = unknown> =
	| { kind: 'absent' }
	| { kind: 'keepExisting' }
	| { kind: 'absentRange', range: KeyRange<TKey> }
	| { kind: 'unchanged', expected: TEntry };
```

Semantics, enforced on **every** handler run exactly like the other kinds: the entry currently at `key` must exist and be structurally equal to `expected`. Otherwise the handler throws `TreeEntryChangedError`, discarding the whole action's staged writes (the Atomic wrapper), and the error propagates out of both commit paths.

**An absent entry counts as changed.** The staged effect was computed from an image that no longer exists. For an upsert, tolerating absence would resurrect a row a rival deleted (the fix ticket observed exactly that: delete committed first, update committed second, row back with the update's value). For a delete, tolerating absence would be harmless, but the guard's contract stays uniform and a racing double-DELETE therefore refuses the second deleter. That is the optimistic-concurrency answer (the transaction read a row that is now gone) and the application's retry then affects zero rows sequentially. If that ever proves too strict in practice, add a separate `unchangedOrAbsent` kind for deletes rather than weakening this one.

`expected` is the entry **as stored**, not a hash: the guard is serialized into the log beside its action with the same encoding entries already use, so a full copy of an entry round-trips by construction, and no digest scheme has to be invented or versioned. Add a `NOTE:` at the guard's definition: an `unchanged` guard roughly doubles the row bytes of every guarded log entry; if log volume ever matters, replace `expected` with a content digest (the block-digest utilities in `packages/db-core/src/transaction/` are the starting point).

### Guards on delete entries

A `TreeReplaceAction` element `[key, undefined, guard]` currently carries its guard into the log and ignores it. The handler must evaluate `unchanged` before `deleteAt`. The other three kinds are meaningless on a delete. Prefer making that unrepresentable: split the action element type into an upsert form (any guard kind) and a delete form whose guard, if present, is `unchanged` only. If the tuple typing fights back, fall back to a runtime throw at handler time with a message naming the key and kind, and pin it with a test. Either way `TreeReplaceAction` stays a positional tuple so existing callers and previously committed log entries deserialize and replay unchanged.

### Structural equality

Entries in this codebase are JSON-shaped values: arrays, plain objects, strings, numbers, booleans, null, and `Uint8Array` (compare by bytes). Check `packages/db-core/src/utility/` for an existing deep-equal before writing one; if none, add a small `structuralEquals` there, with object key order irrelevant, and unit-test it. Do not add an `entryEquals` constructor parameter to `Tree.createOrOpen` unless a caller actually needs a custom notion of equality; none does today.

### The error class

`TreeEntryChangedError<TKey, TEntry>` carries `collectionId`, `key`, `expected`, and `actual` (`undefined` when the entry is absent). It must **not** extend `TreeKeyTakenError`: the Quereus bridge maps every `TreeKeyTakenError` to a registered `UNIQUE constraint failed` message by collection id (`mapCommitRefusal` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts`), and a lost-update refusal is not a uniqueness failure. Introduce a shared base, `TreeGuardRefusedError`, that both `TreeKeyTakenError` and the new class extend, and move the "not a StaleFailure, never downgraded to retryable, discards the whole action" contract onto the base's doc comment so it is stated once. Export the new classes from `packages/db-core/src/index.ts` alongside the existing ones.

No retry loop needs changing. `Collection.sync` absorbs only *returned* stale failures (`packages/db-core/src/collection/collection.ts`, the `staleFailure` branch), and `TransactionCoordinator.commit` retries only `CoordinatorStaleLossError` (`packages/db-core/src/transaction/coordinator.ts`); every thrown error already escapes both. Pin that with tests rather than assuming it.

### Documentation

Extend the "Conflict replay re-makes the uniqueness decision (entry guards)" section of `docs/internals.md` with the new kind and the absent-counts-as-changed rule. Keep the section heading (other docs may link its anchor; `yarn lint:docs` checks). The plugin-side principle (which SQL statements carry it, and the decision that a racing same-row UPDATE or DELETE is refused rather than last-writer-wins) is written by the sibling ticket.

## Tests — `packages/db-core/test/tree-guard.spec.ts`

Follow the file's existing shape: raw `Tree`s over `TestTransactor`, a rival landing through `commitRivalTreeWrite`, both the sync path and the coordinator path (`CompetingWriterTransactor`).

- Upsert guarded `unchanged` with the committed entry equal to `expected`: commits.
- Rival committed a different entry at the key before the loser's sync: refused with `TreeEntryChangedError` carrying `expected` and `actual`; the loser's whole action is discarded; the rival's entry survives.
- Rival deleted the key: refused (`actual` undefined).
- Delete guarded `unchanged`: refused when the rival changed the entry, commits when the entry is unchanged.
- A two-entry action `[[k1, undefined, unchanged], [k2, e2, absent]]` where only the first is refused: neither lands.
- Coordinator path: the refusal escapes the inter-attempt refresh after a clean stale loss, as the existing `absent` test pins.
- A guard that has round-tripped through JSON (mirror the existing `absentRange` round-trip test) still compares equal, including an entry containing a `Uint8Array` if the encoding supports one.
- A delete carrying a non-`unchanged` guard is rejected, at the type level or at runtime per the choice above.
- The retry-loop pin: the sync path does not retry the refusal (attempt count stays 1), and the coordinator does not treat it as a stale loss.
