# SQL columns hold blob references

Last of three parts (after `feat-queued-blob-pins-settle-with-their-transaction` and `feat-blob-pins-reconcile-after-a-restart`), and the last of the four that build the SQL side of blobs. This slug landing means all of it has landed, so this is also the ticket that flips the status line in docs/blobs.md and finishes the README and `docs/internals.md`.

One thing is left unfinished by everything before it. `SqlBlobService.put` made outside any transaction pins the blob as `sql-unstaged/<putAtMs>` (`unstagedPinLabel` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts`). An insert that references the blob replaces that pin with a reference pin and the `unstaged` pin goes. But an application that puts a file and then never inserts anything — the user cancelled the upload, the statement failed, the process stopped — leaves the `unstaged` pin, and nothing has ever released one. docs/blobs.md §SQL promises a holding period: "a blob no statement has staged after a holding period (24 hours by default) is unpinned". This builds it.

## The option

`blob_unstaged_holding_ms`, a plugin-level registration option (README § Plugin-Level Configuration), default `86_400_000` (24 hours). Parsed in `blob-pins.ts` and called from `register`, the way `cost_profile` is parsed in `cost-profile.ts` and called from `register` — **not** in `optimystic-module.ts` beside `link_round_trip_ms`, which is a per-binding node option and the wrong shape for one timer per plugin registration:

```ts
export const DEFAULT_UNSTAGED_HOLDING_MS = 86_400_000;
/** The registration's `blob_unstaged_holding_ms`, or the default when unset.
 * @throws Error for anything that is not a finite positive number — ignoring it would silently keep
 * every unreferenced put for a day when the host asked for a minute, or expire bytes it meant to hold. */
export function parseUnstagedHoldingMs(config: Readonly<Record<string, unknown>>): number;
```

## `SqlBlobPins.sweepUnstaged`

```ts
/** Unpin every `unstaged` pin older than the holding period, except on a reference some live
 * transaction is relying on. Never throws. */
sweepUnstaged(now?: number): Promise<void>;
```

Chained like `reconcile` and `settleQueued` (awaiting `whenTransactionIdle()` first, bailing when `disposed`), so it never runs beside them. `now` defaults to the deps' clock; a spec passes its own through `plugin.blobPins`.

For each `knownBackends()`:

1. Build the **protected** set of references, which must not expire however old their pins are:
   - every reference carrying a reference pin (`parsePinLabel`'s `kind: 'reference'`) whose transaction `isLive` answers true for — read off `listPins(TRANSACTION_PIN_PREFIX)`, the same listing `reconcile` makes;
   - plus `openReferences()`, the references the **open** transaction's ledger has added. Those have no reference pin yet: `holdForCommit` writes the pins when the commit starts, so between a statement staging a reference and that commit there is a window where only the ledger knows.
2. `listPins(UNSTAGED_PIN_PREFIX)`; for each pin, parse the label. A label whose time does not parse (`parsePinLabel` answers `undefined` for a non-numeric tail) is **left alone** and logged once per label, kept in a `Set<string>` so a stuck label does not log on every sweep.
3. Unpin each pin whose `putAtMs + holdingMs` is at or before `now`, unless the protected set holds its reference. Log `blob:unstaged-expired ref=… putAt=…`.

Each pin in its own `try`; a failure is logged (`blob:pin-release-failed`) and the next pin still runs.

**Why `queued` and `abandoned` leave `unstaged` pins in place, and why that forces step 1.** Only the online `committed()` arm drops an `unstaged` pin, because only a commit that landed makes the reference pin the blob's new hold. A rollback or a refused commit keeps it, so the application's retry does not have to put the bytes again; a queued transaction keeps it because a queued entry can still fail with nothing committed, and dropping it would lose bytes an immediate rollback would have kept. This fails toward keeping bytes, which is the bias docs/blobs.md takes throughout. The cost is exactly the case step 1 handles: an `unstaged` pin can outlive its holding period while its transaction waits in the queue, and expiring it then would delete bytes a transaction that is about to commit references.

**`openReferences`.** New on the bridge:

```ts
/** The references the OPEN transaction's ledger leaves added (`addedReferences`), as a set; empty
 * with no active transaction. What keeps a sweep from expiring an `unstaged` pin whose reference a
 * long-open transaction has already staged. */
openBlobReferences(): ReadonlySet<BlobRef>;
```

Deliberately **not** keyed by backend: a reference protected on the wrong network only delays the expiry of an identically-addressed blob on another network, which fails toward keeping bytes and costs one extra holding period. Say so at the method.

## The timer

- Started by `backendResolved` — so the first sweep of each backend happens as that backend resolves, and the interval starts with the first one.
- Period `Math.max(60_000, Math.min(holdingMs / 4, 3_600_000))`: a quarter of the holding period, never more than an hour and never less than a minute. The floor is what keeps a host that configures a one-second holding period (a test, a tool) from arming a 250 ms interval.
- `unrefTimer(setInterval(...))` from `@optimystic/db-core` (`packages/db-core/src/utility/unref-timer.ts`) — the `NO_TIMER_UNREF` lint rule in `eslint.config.js` requires every `unref` to go through it — and `clearInterval` in `dispose`.
- One timer per `SqlBlobPins`, started once however many backends resolve.

`dispose()` clears the timer before awaiting the chain, which it already does from `feat-queued-blob-pins-settle-with-their-transaction`.

## Edge cases & interactions

- **A put outside any transaction, never referenced.** Kept until the holding period has passed, then released; the writer's piece sweep then removes the bytes. Test, both sides of the boundary.
- **A put whose reference an open transaction has inserted, past the holding period.** Protected by `openBlobReferences`, and then by its reference pin from the moment its commit starts. Test.
- **A put whose reference a *queued* transaction references, past the holding period.** Protected by its reference pin and `isLive`. Inspection — the reference-pin arm of step 1 is the same code the open-transaction case falls through to once the commit has started, and `feat-queued-blob-pins-settle-with-their-transaction` already tests the queued lifecycle.
- **A put inside a transaction the transaction never references.** Its pin is `sql/<stampId>/put`, not `unstaged`, so this sweep never sees it: it is released when the transaction ends, which is the documented footgun (`SqlBlobService.put`'s doc comment, and the README). Inspection.
- **An `unstaged` label with a time this build cannot read** — written by a future build, or corrupted. Left pinned for ever and logged once. Deliberate: releasing a pin whose meaning is unknown drops somebody's bytes. Inspection.
- **A clock moved backwards.** `putAtMs` is in the future relative to `now`, so nothing expires until the clock catches up. No guard: the holding period is measured on this machine's own clock, the limit docs/blobs.md §Lifetime already states for the reclaim pass. Inspection.
- **A host that never resolves a blob backend.** No timer is ever armed, and nothing needs sweeping — a process with no blob store holds no `unstaged` pins. Inspection.
- **`dispose()` during a sweep.** The timer is cleared, the chained step bails at its `disposed` check, and the pins it had not reached stay — the next process's first sweep takes them. Inspection.
- **Two backends, one timer.** Each tick sweeps every known backend, so a network whose backend resolved second is not swept on a timer of its own. Inspection.

## Tests

`packages/quereus-plugin-optimystic/test/blob-pins-unstaged.spec.ts`, over the harness `blob-pins-harness.ts`. Drive `plugin.blobPins.sweepUnstaged(now)` by hand with explicit times; the plugin keeps the default holding period so the interval timer never fires inside a test.

- **The boundary.** `plugin.blobs.put` outside any transaction; read the pin's `putAtMs` back through `parsePinLabel`; `sweepUnstaged(putAt + holding - 1)` leaves the pin; `sweepUnstaged(putAt + holding + 1)` releases it and nothing is pinned on the reference.
- **A reference an open transaction has staged.** Two puts; `begin`; `insert` the second reference; `sweepUnstaged(putAt + holding + 1)` — the first is released, the second still pinned; `commit`; the second now has no `unstaged` pin, its reference is in the table's reference tree and `stat` reports durability `local`.

Two tests: one for the expiry rule and one for the protection that is the whole reason the rule is not just "older than the period". The reference-pin half of the protected set is checked by inspection, as above.
