## The engine's contract

Read from `selectPhysicalNodeFromPlan` in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`:

- A plan with `indexName`, `seekColumnIndexes` starting at the range column, and the bound filters handled becomes `plan=3`. `filterInfo.constraints` lists the lower bound and then the upper, each with an `IndexConstraintOp` and an `argvIndex` into `filterInfo.args`.
- `seekColumnIndexes` of prefix equality columns followed by the range column becomes `plan=7` with `prefixLen`: equalities first, then bounds.
- A claimed filter gets **no residual**, so what this module returns is the answer. The engine seeks on the first lower and first upper filter of the column. Claim exactly those; any further bound stays unclaimed and the engine keeps it as a residual.
- A range under a collation other than the index's is declined by `classifyCollationCover` into a scan plus residual, and `honorsCollatedRangeBounds` stays unset. So `T collate nocase > x` over a BINARY index stays correct without this module seeing the predicate's collation.

## Design

### Plan

In the secondary-index loop, for each non-partial index, take `matchEqualitySeek(...)`. When `keyCount === 1`, the next key column is the candidate range column, and it qualifies when:

- it passes the same column rule as an ordered column (TEXT, not semantic, BINARY on both the column and the index column);
- it has **no** equality-role filter (`firstEqualityRoleFilter`). Otherwise the engine's equality arm would seek on a filter this module did not claim;
- it has a usable `>`, `>=`, `<` or `<=` filter with no `runtimeSet`, whose plan-time `value` is `undefined` (bound at runtime), a string, or null. A literal of another type, such as `T > 5`, is not claimed and stays a residual over a scan.

Cost: `rows = max(1, floor(tableRowCount × prefixSelectivity × 0.25 per bound))`, `cost = seekCost + rows`. `prefixSelectivity` is the equality estimate the seek branch already computes, 1 with no prefix. 0.25 matches the primary-key range branch's assumed selectivity. It is an assumption, not a measurement, and `a-long-index-walk-finishes-by-scanning-the-table` bounds what a bad guess costs. The candidate competes with the others under the rules of `an-index-walk-serves-order-by`. It delivers an ordering when `walkDelivering` accepts its index for `request.requiredOrdering`, with `reverse` on its descriptor. A range filter on the column satisfies that function's NULL rule.

Unmaintained indexes are skipped, as for a walk.

### Bounds

Bounds are computed at runtime from `filterInfo`, in `schema/index-walk.ts`. Export the present tag from `key-encoding.ts` as `KEY_PRESENT_START` (`'\x02'`), beside `KEY_PREFIX_END`. With `P` the framed prefix values (empty when there are none) and `f(x)` = `P ‖ frame(x)`:

| bound | tree key |
|---|---|
| `>= x` | lower `f(x)` inclusive |
| `> x` | lower `f(x) + KEY_PREFIX_END` inclusive |
| `< x` | upper `f(x)` exclusive |
| `<= x` | upper `f(x) + KEY_PREFIX_END` exclusive |
| no lower | lower `P + KEY_PRESENT_START` inclusive |
| no upper | upper `P + KEY_PREFIX_END` exclusive |

"No lower" must not be left open: NULL-keyed entries sort first and `t < x` would return them. `KEY_PREFIX_END` is what makes `> x` skip every entry of `x` without skipping a longer value such as `x + '\x00'` (the reasoning at `KEY_PREFIX_END` in `key-encoding.ts`). Reverse swaps the two ends into `new KeyRange(upper, lower, false)`.

### Bounds the tree cannot apply

Each bound value is one of three things at runtime:

- **NULL or undefined:** the comparison is UNKNOWN, so the scan yields no rows and seeks nothing, as `seekKeysInTreeOrder` does for equality. The engine folds only a literal NULL.
- **A string with no code unit at or above U+D800:** both orders agree on comparing any stored value with it (the pivot argument in `an-index-walk-serves-order-by`), so it goes in the tree range.
- **Anything else** (a string with such units, or a bound parameter of another type, such as a number against a text column): it is left out of the tree range, and every row is tested with `compareSqlValues(row[column], bound)` under the constraint's op. This is the comparison the engine's own filter makes for a BINARY, non-semantic column (`compareSqlValuesFast` under BINARY in `@quereus/quereus/src/runtime/emit/binary.ts`), including its ranking of numbers below text. A NULL column value fails the test.

The row test runs after `rowImpliesEntry` and before `inEngineOrder`, and a failing row counts in `rejected`. For the first two kinds no such test is needed: a verified row's tree key equals the entry's, which lies in the range.

A prefix value is an exact-byte equality, so it goes in the key as it does for a seek (`indexSeekKey`, including its NULL rule). Non-string prefix values already carry the `NOTE:` at `seekKeysInTreeOrder`.

### Reading

- `runQuery`: the existing `isSecondaryIndex && args.length > 0` arm now also carries `plan=3` and `plan=7`, and hands `executeIndexScan` the range this ticket computes rather than `seeks`. A `plan=3` over `_primary_` stays where it is.
- Read `prefixLen` with `decodeIdxStr`. Do not parse by hand.
- A range walk uses `yielded` tracking only as a walk does, and `inEngineOrder` on its rows.
- The `index:seek` line prints a range's two keys as `low:high`, each through `printableSeekKey`, which escapes `:` so the form is unambiguous.
- `IndexManager.scanIndexRange` has no caller and brackets differently: delete it rather than leave two definitions of a range.
