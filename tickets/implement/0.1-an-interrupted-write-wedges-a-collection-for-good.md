## What happens, in the code

A write has two steps. `StorageRepo.pend` saves a pending record for each block and records the slot it claims in the block's metadata (`BlockMetadata.pendingRevs`, written by `BlockStorage.savePendingTransaction` through `recordClaim`), then flushes. The commit promotes the record; a cancel deletes it. Only four things ever remove a record (docs/repository.md, "A pending record's lifetime is bounded by its writer"): the writer's cancel, a divergence-shaped commit refusal, a forward write under the same action id, and the dead-claim sweep that runs when the block's `latest` reaches the record's slot (`BlockStorage.sweepDeadClaims`). A process that exits between pend and commit does none of these: the writer's owed cancels live in memory (`OwedCancels`), the slot is never reached, and `stuckReservationMessage` says so in words.

The next process's first write to the collection asks for the same slot. `StorageRepo.pendUnderLatches` lists the block's claims (`listPendingClaims`) and asks `isReservationAgainst(claim, { rev })`, which answers true because the dead record claims exactly the requested revision. Under the writer's `policy: 'r'` the pend is answered as a conflict, the transactor cancels its own attempt and reports stale, the collection refreshes and moves nowhere, and after ten attempts `SyncRetryExhaustedError` escapes. Every later write to the collection takes the same path.

## The fix: a reservation the node itself made, for a writer in its own process, in an earlier run, is abandoned

The deciding facts are local when all three hold, and the node can record all three at the moment it saves the record:

1. **The pend was applied by this node alone**, with no consensus. That is `CoordinatorRepo.pendSolo`, the only caller that threads the writer's `MessageOptions` into `StorageRepo.pend` (`applyPendsInOrder(batch, options)`). A record applied by `ClusterMember.applyConsensusPend` arrives with `undefined` options and gets no stamp, so a record of a coordinated write on a multi-member cohort is never judged by this rule.
2. **The writer runs in this node's process.** `NetworkTransactor` knows it: its `localPeerId` is documented as "the peer id of the node this transactor runs on, when `getRepo` hands that id the node's own repo". When it sends a pend (or a batched `pendMany`) to the repo of `localPeerId`, it marks the call with a new non-wire field on `MessageOptions`, say `localWriter: true`. `RepoClient.processRepoMessage` copies only `expiration` onto the wire, and `RepoService` builds its options from the message, so a remote writer cannot set the mark; `coordinatingBlockIds` and `asker` on the same type are the precedent for options that never travel. The mark is positive on purpose: a path that forgets it keeps today's behaviour (the leak), whereas a negative mark forgotten would have a remote writer's live record judged dead, and deleting a live record costs that writer a failed commit and a whole-block repair, which the sibling backlog ticket names as worse than the leak.
3. **The run that saved it is over.** `StorageRepo` mints a run identity at construction (a random id, `StorageRepoOptions.runId` to override) and stamps it beside the slot, in a third sibling map on `BlockMetadata`, say `pendingRuns?: Record<ActionId, string>`, present only for records that meet facts 1 and 2. Written, dropped and swept in the same `recordClaim` writes as `pendingRevs` and `pendingBases`, so the three maps can never describe different records, and joined against the pending namespace like the other two, so an entry whose record is gone is inert. A production node builds its `StorageRepo` once per process (`createLibp2pNodeBase`), so a run is a process run there; the mesh harness builds a new one on `Mesh.restart`, which is what makes the spec's restart a new run with no harness change. Metadata written by the release before the field stays readable: a record with no entry is simply not stamped.

A claim whose stamp names a run other than the current one is **abandoned**: its writer was a transactor in a process of this node that no longer exists, and nothing else could ever commit or cancel it. Put the predicate in `pending-claim.ts` beside `isReservationAgainst`, as a pure function of the claim and the current run id (`PendingClaim` grows an optional `localRun` field; `BlockStorage.claimOf` fills it), and apply it at both rival scans ahead of the reservation rule:

- **`StorageRepo.pendUnderLatches`, pass 1:** an abandoned claim is not a reservation; log it (`pend:abandoned-claim actionId blockId rival claimedRev run`) the way `pend:superseded-claim` is logged. **Pass 2** deletes each abandoned record and its claim (`BlockStorage.deletePendingTransaction`, which already clears the claim) under the same latch hold, before saving the newcomer's record for that block. Deleting under the hold is what makes the judgement safe against a concurrent re-pend of the same action: a re-pend overwrites the stamp with the current run, and pass 1 read the stamp under the same hold.
- **`ClusterMember.reservingRivals`:** skip abandoned claims the same way, so this member's vote does not hold a rival on a record its own earlier run left. The vote is read-only; the record is deleted when the approved pend applies here. The member needs the current run id, which `StorageRepo` exposes (`IPendingClaimReader` is the seam the member reads claims through).

`isReservationAgainst` itself is unchanged: abandonment is a fact about the writer, independent of the slot rule, and the two must stay separate functions.

Expected effect on the spec: phase 3's pend finds run 1's record stamped with run 1's id, judges it abandoned, deletes it, and succeeds; phase 3b's tree write commits at `local`; phase 4's rival in the same run meets a record stamped with the current run and is refused as before.

## What the fix does to each case the fix ticket asked about

- **Offline restore.** `OfflineQueue.restore` re-drives a journaled in-doubt entry under its old action id, re-sending the retained attempt verbatim. If its own record from the previous run is still on disk, the re-pend of the same action overwrites the record and its claim (`savePendingTransaction` is documented to overwrite all of them for a redelivered pend), including the stamp, so it is live again. If a rival's pend got there first and deleted it, the re-send pends fresh and either lands or meets the rival's committed revision as an ordinary stale loss, which the queue already handles (`torn-not-saved`, a fresh id). The restore itself reads the log, never a pending record (`Collection.holdsCommitted`), so nothing it depends on is removed. Nothing breaks either way; say so in a sentence in docs/offline-sync.md only if a reader would otherwise wonder.
- **A remote writer through this node.** Its pend arrives through `RepoService` with no mark, so its record carries no stamp and is never judged abandoned. Unchanged, and left to the backlog ticket.
- **A multi-member cohort.** A record of a coordinated write carries no stamp (fact 1), so this rule never fires on it. Unchanged, and the backlog ticket's. The one multi-member shape the rule does reach is a record stamped while the node was alone and met after a second member joined: this node's member votes approve on it, the new member holds nothing, and the approved pend's apply here deletes it. Correct, because the stamped record's writer is still provably dead.
- **Own-action retry and a same-run rival.** A retry of the same action re-pends over its own record (overwrite). A rival in the same run meets a stamp equal to the current run and is refused as a live reservation. Both are what the spec's phase 4 pins, and `isOwnRevision` is untouched.
- **A host that rebuilds its node in one process while keeping a transactor from the old one.** Its records are stamped with the old `StorageRepo`'s run, so a later rival judges them abandoned while that transactor may still commit; the commit then meets a missing record. No host in this repository does this (the Quereus plugin's `CollectionFactory.shutdown` stops the transactor before the node), so record it as a `NOTE:` at the run id's mint site rather than guarding against it.
- **`stop()`.** Nothing here changes how long `node.stop()` takes with a write in flight, and nothing cancels in-flight writes on stop. The reporter's option (b) is answered by making an interrupted stop harmless on a one-machine group, which is the case the ticket owns. Document in docs/repository.md that exiting before `stop()` resolves no longer wedges a collection on a one-machine group, and still strands the record on other members of a larger cohort until the backlog ticket's sweep exists.

## Alternatives considered and rejected

- **A start-up pass that discharges previous-run records (the reporter's option (a) as written).** It needs an enumeration of every block's pending records, which `IRawStorage` does not offer (reads are per block), and on a one-machine group the next write to the block already reads the block's claims under the latch, so the opportunistic check is free and needs no enumeration, no timer and no start ordering against the offline queue's restore. The backlog ticket named this choice as an open question; this is the answer for the locally decidable case.
- **An age bound.** A slow writer is not a dead one; the backlog ticket records why guessing is worse than the leak, and this ticket's whole point is to need no guess.
- **Marking origin negatively (stamp everything, exempt remote writers).** Rejected above: forgetting the exemption on a new ingress deletes live records.
