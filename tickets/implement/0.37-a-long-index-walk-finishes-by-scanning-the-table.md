GitHub #52. Closes the cost `an-index-walk-serves-order-by` accepts.

## Why

Measured in Node, `transactor='test'`, median of 7:

| rows | walk everything | `order by T` as a table scan and engine sort | walk 10 |
|---|---|---|---|
| 2,000 | 63 ms | 13.7 ms | 0.37 ms |
| 5,000 | 188 ms | 37.7 ms | 0.38 ms |

The walk columns are a bare loop over the trees, with no SQL layer and no refresh, and the middle column is a full SQL statement, so treat the comparison as approximate until the acceptance run below replaces it. The walk's cost is one tree descent per row (`readRowAt`), about 31 to 38 µs here. A user's LIMIT sits above the Sort, so `getBestAccessPlan` cannot see it (Quereus backlog `feat-sort-absorb-blind-to-limit-general`), and a `limit ?` would not be known at plan time anyway. Range selectivity is an assumption too. Only the walk itself finds out how many rows are wanted, because the consumer stops pulling.

Alternatives rejected:

- **Decline the walk without a known limit.** That loses the motivating query, whose LIMIT never reaches the module.
- **Wait for the Quereus change.** It would not cover a bound `limit ?` or a read the consumer abandons.
- **Accept the slowdown.** A full read on a phone would pay about 5 times today's cost for no benefit.

## Design

`WALK_ROWS_BEFORE_SCAN = 256`, a named constant in `schema/index-walk.ts`, with this reasoning in its comment: above the 100-row page the issue measures, and costing about 8 ms in this measurement. It applies to a walk or a range, never to an equality seek or multi-seek, whose row counts are the statement's own.

In `executeIndexScan`, count entries fetched, rejected ones included, so a walk under a selective residual also moves on. On reaching the constant:

1. Stop the entry iterator, and remember `lastKey`, the tree key of the last entry fetched.
2. Read the remaining rows through `executeTableScan(mainRead, rowCodec)`, which keeps its resume-on-change behaviour and reads the same refreshed or pinned main view the walk used, so a committed read stays at its one moment.
3. For each row, compute `treeKey = indexEntryKey(indexManager.createIndexKey(schema, row), rowCodec.extractPrimaryKey(row))`. Keep the row when `treeKey` lies inside the walk's range (`compareTreeKeys`, honouring each bound's inclusivity), lies strictly beyond `lastKey` in walk order, and passes the row test for any bound the tree could not apply.
4. Skip a row whose primary key is already in `yielded`. On a live read a row can move past `lastKey` after it was yielded. Track `yielded` for walks, which holds at most 256 keys before the switch.
5. Sort the kept rows by `treeKey` in walk direction, then pass them through `inEngineOrder` exactly as walked rows pass.

The first post-switch row therefore waits for the whole table scan, and the remainder is held in memory, as the engine's Sort holds it today.

Result: a read within 256 rows costs what the walk costs. Any longer read costs at most today's scan and sort plus about 8 ms of walking, with no regression at any table size. A page larger than 256 rows on a very large table gets today's cost rather than the walk's: record that as a `NOTE:` at the constant, with the revisit condition "if pages over 256 rows on large tables show up slow, scale this by `analyze`'s row count".

`index:seek` gains `scan=0|1`, saying whether the walk finished by scanning. `matched` and `rejected` stay counts of index entries.

## Edge cases & interactions

| Case | Expected | Verified by |
|---|---|---|
| Read crossing the threshold, forward and reverse, ordered and unordered range | same rows and order as a memory table; no duplicate or gap at the switch | test with about 300 rows |
| Astral and U+E000+ values straddling the switch | engine's order. A run held by `inEngineOrder` at the switch must flush in order with the scan's rows: continue the same generator rather than start a second one | test |
| `limit` satisfied within the threshold | no table scan | test counting scanned rows |
| Selective residual: `where x = ? order by t limit 10`, matching rarely | walk gives up after 256 entries; correct rows | inspection: same path |
| Stale entry before the switch | rejected as before | inspection |
| Row the index is missing (damaged tree) | appears after the switch and not before; the answer depends on position only on a damaged tree, which `plugin.verifyIndexes` reports. Note this at the switch | inspection |
| Row changed by a concurrent writer on a live read | `yielded` prevents a second return; new rows beyond `lastKey` may appear, as in a walk | inspection |
| Committed read | both phases read the one pinned main view | test with an interleaved commit |
| Concurrent change during the walk phase | still throws per the live-scan contract; the scan phase resumes as `executeTableScan` does | inspection |
| Table with fewer rows than the threshold | never switches | inspection |

## Acceptance

Rerun the issue's `index-ordering-plans.mjs` at `ROWS=2000` and `ROWS=5000`. Expected plans: `INDEXSCAN` for both `order by T` rows (asc and desc), `INDEXSEEK` for the range and equality rows. Record the times in the handoff, along with an unbounded `select Id from M order by T` at both sizes, which should be within about 8 ms of 13.7 ms and 37.7 ms on comparable hardware.
