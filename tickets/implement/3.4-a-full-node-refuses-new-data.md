# A full node refuses new data

## Why

Nothing in the node ever declines data on storage grounds. Three doors stand open whatever the node's allotment says:

- **A pushed replica.** `handlePush` in `packages/db-p2p/src/cluster/block-transfer-service.ts` validates a block's structure and its commit proof and then persists it. The only outcome that is not "accepted" is a block that was malformed, uncertified, or whose write threw — so a full node accepts replicas until its disk refuses one, and reports that refusal as `missing`, indistinguishable from "I could not verify this".
- **An announced blob.** `BlobAnnounceReceiver.decided` takes a `responsible` hold and starts pulling whenever committed state lists the reference and this node is in the blob's cohort. Its only "no" on policy grounds is `on-demand` holding, which is a configuration, not a condition.
- **The program on the same machine.** `LocalBlobService.put` writes every piece and then the record. A host writing a large file fills the node's own allotment with no error until the store itself fails, part-way through, leaving pieces for the sweep.

With the previous ticket's storage pressure reading there is now one answer to "is this node full", and these three doors can read it.

## What to build

Each door refuses at the `refusing` stage, reading `StoragePressure.stage()` — the synchronous last sample, never a scan: all three are inbound or latency-sensitive paths. A node whose stage is `unknown` refuses nothing, which is the whole of what an unmeasurable node does.

### A pushed replica

`BlockTransferResponse` gains `outOfSpace?: true`. It is a property of the **receiver**, not of a block, so it rides once per response rather than per block id: when it is present every block of the request is reported `missing` and nothing was certified or persisted. The refusal happens before any proof verification, which also means a full node stops spending CPU on signatures it is going to refuse anyway (the `NOTE:` on `handlePush` about unbounded per-request verification cost).

Two senders read it:

- `confirmReplicated` already counts a holder only when the response does **not** list the block as `missing`, so a full peer is already not counted and a shed range is already retained. What it gains is the ability to say why: log the peer as out of space rather than as a holder that did not have the block, so an operator reading a handoff that will not confirm can see that the new owners are full rather than unreachable.
- `replicateGrown` should stop re-pushing to a peer that answered out of space for the rest of that pass, and report the outcome incomplete so the monitor retries on a later check (which `growthMaxAttempts` already bounds). It must **not** record the peer as satisfied: a peer that is full holds nothing.

### An announced blob

`BlobAnnounceAnswer` gains `'out-of-space'` (added to `ANNOUNCE_ANSWERS`, the decoder's validation list). `decided` answers it after the membership, cohort and allowance checks and **before** the reference read: the reference read is the expensive part of answering an announcement, and a node that is not going to take the blob either way should not spend a read slot establishing that it is referenced.

The answer is deliberately **not** added to `SATISFYING_ANSWERS` in `packages/db-p2p/src/blob/cohort-reaction.ts`. That list means "this peer is owed nothing more", and `'declined'` is in it because a node configured `on-demand` will never hold the blob — a permanent fact about a configuration. Out of space is a condition that clears, so counting it as satisfying would enter the peer in `RebalanceMonitor`'s seen set, which only a departure from the cohort clears, and the announcer would never offer that blob to that peer again.

Nothing remembers the answer per peer, unlike `'declined'`, which `BlobCopyDrain` remembers until the peer's next connection. A full peer is treated exactly as an unreachable one: not satisfied, asked again on the next pass. That is deliberate — a memory of "full" would need a clock to expire it, and the drain's passes are already the retry.

The release arm of `BlobCohortReaction` needs no change and must not get one: an out-of-space candidate stays in both the numerator and the denominator of the release count, its `stat` does not answer `whole`, so the reference is retained. Dropping it from the count (the `satisfiedWithoutRequest` treatment) would *lower* the number of holders a release needs and let a node drop a hold because its neighbours are full — the exact inversion to avoid.

### The program on the same machine

The host's own writes are refused later than everybody else's: not at `refuseAbove`, but only once the measured use has reached the effective total. A node's own writes are the work it exists to do and the last thing it should give up; the replicas and blobs it holds on the network's behalf are the giveable part. The gap between `refuseAbove` and the allotment is the headroom this uses — the same headroom that covers pends already approved and the sampling window.

So `StoragePressure` answers a second question beside the stage: whether the node has room for the host's own writes at all (`usedBytes < totalBytes`, and always true while the total is unknown). `LocalBlobService.put` and `pin` throw a typed `NodeOutOfSpaceError` carrying the measured use and the effective total, **before** the first piece is written — "before anything is staged or sent" — so a refused put leaves no pieces behind and no sweep to run. One error class, exported from `packages/db-p2p`, so a host can catch it rather than matching on a message.

## Edge cases & interactions

- **An unmeasurable node.** `stage()` answers `unknown` and the room question answers yes: nothing refuses. This is the single most important arm to get right — a node on a memory, SQLite or LevelDB store with no configured allotment must behave exactly as it does today, and a node whose free-space read failed for one scan must not start refusing.
- **The sample is up to a minute old.** All three gates read the last sample, so a node can accept one sample-interval's worth of data past its limit. Bounded, deliberate, and the reason the limit is below the allotment; the tripwire is recorded on `StoragePressure.stage()` by the previous ticket.
- **A commit whose pend was approved.** This ticket refuses only at the three doors above. A member that approved a pend must still apply the commit, and the sibling ticket that adds the consensus refusal says why; nothing here may refuse inside an apply.
- **The node's own blob fetches.** A fetch pulling pieces for a `responsible` hold this node already took is not "new data from others" — the hold was taken, the blob is owed to the network, and abandoning the pull mid-way leaves a partial blob that is worse than a whole one. Fetches are not gated. The announcement that *would have* taken a new hold is where the refusal belongs, which is what `decided` does.
- **A full node still serves.** Nothing on a read path is gated: answering `get`, serving pieces and answering `stat` cost no storage. A full node is still a useful member for everything it already holds.
- **The piece sweep after a refused put.** Because the refusal is before the first piece, `put`'s existing `scheduleSweep()` on failure has nothing to clean — but leave it: it still covers the fetch and build failures it was written for.
- **`pin` on a blob already held.** A pin takes no new bytes if the blob is already whole here, so refusing it costs an application a hold it could have had for free. Refuse anyway: a pin is a promise to keep bytes a node has no room to keep, and the alternative is a stat on the hot path of a gate. State it in the doc as the accepted sharp edge.
- **Older peers.** A sender on a build that does not know `outOfSpace` reads the response exactly as it does today (every block `missing`), and one that does not know `'out-of-space'` as an announce answer must not crash on it — the decoder's validation list is what decides that, so adding the value there is not optional.

## Tests

One spec: **a `put` refused for space writes no piece and no record.** Build a service over a store whose account reports the node at its total, call `put`, assert the typed error and that the piece store and record store are untouched. "Before anything is staged" is the part of this that is easy to implement wrongly and invisible when it is — a refusal after three pieces leaves three pieces.

Nothing else: the push and announce refusals are one guard reading one stage and returning a value, the `SATISFYING_ANSWERS` membership is a constant, and the senders' handling is reporting.
