# A durability answer says whose ledger owes it

Part of GitHub issue #26. The plugin-side consumer is `a-sql-commit-learns-when-it-becomes-fully-held`.

## Background

`CoordinatorRepo.commit` answers every below-`full` commit after writing the shortfall into **its own node's** under-replication ledger (`noteReplicationShortfall`), and that node's `UnderReplicationDrain` later pushes the missing copies and fires `BlockDurabilityReachedEvent` through **that node's** `StorageRepo`. So the "now fully held" event for a write reaches only the machine that coordinated it.

Two gaps follow for a host that wants to turn a write's "pending" mark into "saved":

1. **The writer cannot tell whether the event will ever reach it.** In a group no bigger than one cohort the writer normally coordinates its own write (the reporter's case — a phone writing while its partner is offline), so the event arrives locally. But when another cohort member coordinated, or when the coordinator answered success without holding the bytes (a tolerated divergence — "Only when this node holds the bytes" in repo.md), no event will ever come here, and a host waiting on one waits forever. Nothing in the answer distinguishes the cases.
2. **A `full` commit clears an entry silently.** `noteBlockShortfall` on a `full` commit calls `ledger.settle(blockId, rev)`, which deletes any entry at the same or a lower revision and emits nothing. The block did reach full replication — at a revision that supersedes the entry's — but a host waiting on the earlier write's block never hears it unless it happened to see the later write itself (another `Database` on the same node, or another machine's write this node coordinated, are invisible to it).

## Design

### `recordedBy` — who will announce

Add one optional **per-cohort** field to `WriteDurability` (`packages/db-core/src/network/struct.ts`):

```ts
/** Peer-id string of the node whose under-replication ledger recorded this write's missing copies —
 *  the one node that will fire `BlockDurabilityReachedEvent` for these blocks when they reach full
 *  replication. Set only below `full`, and only when every non-torn block's shortfall was recorded.
 *  Absent: no node is tracking the shortfall (nothing to push from the coordinator, a ledger fault,
 *  no ledger, a producer that predates the field), so no full-replication event should be expected. */
readonly recordedBy?: string;
```

- Set by `CoordinatorRepo` on the answer it returns, from `this.localPeerId`, when `noteReplicationShortfall` reports that it recorded an entry for every block it was asked to (not settling, not skipped for `!localHolds`, no per-block failure). Have `noteReplicationShortfall` return that boolean; it still never throws.
- No `localPeerId` (some test wiring) → never set.
- It crosses the wire as plain JSON; an older writer ignores it, an older coordinator never sets it (the consumer then treats the write as one it cannot follow — the safe direction).
- **`distinctReports`** in `durability.ts` must include `recordedBy` in its dedup key: two otherwise identical cohort answers recorded by different coordinators are two different facts, and a consumer needs to see both. It is a per-cohort field, so `stripMergedFields` keeps it (it strips only action-level fields).

### A settle that removed an entry announces it

- `IUnderReplicationLedger.settle` returns the entry it removed, or `undefined` when it removed nothing (no entry, or the entry is at a higher revision). Update `KvUnderReplicationLedger` and any test doubles implementing the interface (grep `settle(` under `packages/db-p2p/test`).
- `CoordinatorRepo` takes an optional sink in its components, typed as the drain's existing `BlockDurabilitySink` (`packages/db-p2p/src/repo/under-replication-drain.ts`) — reuse it, do not declare a second. `libp2p-node-base.ts` passes `(event) => storageRepo.emitBlockDurabilityReached(event)`, the same callable it hands the drain.
- When `settle` removed an entry, emit `{ blockIds: [blockId], rev: request.rev, actionId: request.actionId }` (plus `collectionId` when the coordinator knows it cheaply; it is best-effort) — after the removal, never before, the same order the drain keeps. `rev` is the full commit's revision, which is what every cohort member now holds, matching the event's documented meaning. A sink that throws is logged, never fails the commit (same discipline as `onBlockHolders`).
- Update the event docs (`change-notifier.ts`, repo.md § drain/event) to say the event has two producers: the drain emptying an entry, and a `full` commit settling one.

## Edge cases & interactions

- **Partial ledger failure** (one block's `record` rejects): `recordedBy` absent for the whole answer — a host must not wait on an event the ledger cannot produce. Verified in the write-durability spec.
- **Torn blocks** are already skipped by `noteReplicationShortfall`; "every block it was asked to" means every non-torn block.
- **`local` with an empty missing set** (a node genuinely alone) is still recorded, so `recordedBy` is set: the event will fire when a peer appears and confirms. Correct — the drain leaves such an entry untouched while alone and counts no attempt.
- **A `full` settle racing the drain** emptying the same entry: the ledger is serialized per block (`serialized` in `KvUnderReplicationLedger`), so exactly one of them removes it and exactly one event fires. Verified by inspection of the per-block serialization.
- **A settle at a lower revision than the entry** removes nothing → no event (the ledger already logs `settle:keep-higher-rev`).
- **Solo short-circuit and the local-executed / fallback / tolerated-divergence exits** all go through `noteReplicationShortfall`; check every call site gets `recordedBy` applied to the answer it returns, not to a copy.
- **Mixed versions**: covered above — absence is always the safe reading.

## Tests

- In `coordinator-repo-write-durability.spec.ts`: a below-full commit on a node with a ledger answers with `recordedBy` = the node's peer id; the same commit with a ledger whose `record` rejects for one block answers without it.
- In the same spec (or `kv-under-replication-ledger.spec.ts` for the return value): a `full` commit over a block with an outstanding entry fires exactly one `BlockDurabilityReachedEvent` naming that block at the full commit's revision; a `full` commit over a block with no entry fires none.
