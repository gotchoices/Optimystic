# Cohort-topic: a topic can place its root at a routing key

First of three tickets implementing the accepted decision in `docs/reactivity.md` § Origination point (decision record: the plan ticket `reactivity-notifications-need-the-tail-cohort-to-be-the-topic-cohort`, accepted 2026-10-02). This ticket adds the **generic, transport-free** half to db-core. The db-p2p host honors it in `cohort-topic-host-serves-a-root-at-a-storage-group`; reactivity starts using it in `reactivity-notifications-need-the-tail-cohort-to-be-the-topic-cohort`. Nothing produces the new fields until that last ticket, so this one changes no observable behavior and must leave every existing test green.

## Why

Today every cohort-topic tree's root sits at `coord_0 = H(0x00 ‖ topicId)` and is the FRET cohort of `wantK` (16) peers there, signing with `minSigs` (14). Reactivity needs its root to be **the storage group of the collection's log tail block** — the `clusterSize` peers the key network chooses for that block (`findCluster` in `packages/db-p2p/src/libp2p-key-network.ts`), which hashes the block's routing key exactly once (`hashKey(key)` = SHA-256 of the key bytes — byte-identical to db-core's `RingHash.H` at the default 256 bits). That group signs commit certificates under `ceil(|group| × superMajorityThreshold)` (`captureCommitCert` in `packages/db-p2p/src/cluster/cluster-repo.ts`), not under 14.

So the substrate needs two per-topic overrides, carried as data so every party derives the same answer:

- **Root placement.** A topic may name a **root key** (raw bytes — for reactivity, the tail block's routing key). Then `coord_0 = H(rootKey)` instead of `H(0x00 ‖ topicId)`. Tiers `d ≥ 1` are unchanged (`coord_d(P, topicId)`), and the root key is carried at every tier because a tier-1 cohort needs it to find its parent.
- **Root quorum.** A root-placed cohort's threshold is `ceil(memberCount × quorumRatio)` (the verifier's own ratio, never read off a message or cert), not the node-wide `minSigs`.

Matchmaking and every other application keep today's addressing and `minSigs`; the new fields are optional and absent for them.

## Design

### Addressing

`TierAddressing` gains the root-key form (names are a suggestion; keep them consistent across db-core):

```ts
/** H(rootKey) — the root coordinate of a root-placed topic. Byte-identical to FRET's hashKey(rootKey). */
rootCoord(rootKey: Uint8Array): RingCoord;
/** coord(d, P, topicId), except d === 0 with a rootKey yields rootCoord(rootKey). */
coord(d: number, peerId: Uint8Array, topicId: Uint8Array, rootKey?: Uint8Array): RingCoord;
```

### Wire (all optional, base64url, length-bounded like the other byte fields)

- `RegisterV1.rootKey?` — set on every tier's frame of a root-placed topic. Appended to `registerSigningPayload` (`packages/db-core/src/cohort-topic/wire/payloads.ts`) **only when present**, following the `followOn` precedent, so a frame without it signs exactly as today and a man-in-the-middle cannot strip or swap it.
- `ChildLinkV1.rootKey?` — set by a tier-1 child of a root-placed topic so the parent (the root) can recompute its own served coord. Covered by `childLinkSigningPayload` (`packages/db-core/src/cohort-topic/sig/payloads.ts`) the same conditional way. Note the `NOTE:` in `handleSignRequest` (`packages/db-p2p/src/cohort-topic/host.ts`) that reads the epoch as the **last** element of the promotion/demotion images — the child-link image is a different image, but do not append after `cohortEpoch` in any image that endorser reads positionally.
- `SignRequestV1.rootPlaced?: true` and `CohortGossipV1.rootPlaced?: true` — a flag telling a member that has no engine for the coord yet that the coord is root-placed, so it derives the root group rather than the FRET cohort (the host ticket uses it). Gossip covers it in `cohortGossipSigningPayload` when present. A forged flag is harmless: the member then derives the root group around a coord whose real cohort it would otherwise use, its own member/epoch checks still apply, and a cert minted that way lists at most `clusterSize` members, which a default-rule verifier (14) can never accept.

Validators reject a `rootKey` that is empty, not base64url, or over the bound; `rootPlaced` must be literally `true` when present.

### Participant side (service + walk)

- `RegisterRequest.rootKey?: Uint8Array`; `CohortTopicService.lookup(topicId, tier, rootKey?)`. The walk puts the root key on every frame it builds and uses `addressing.coord(d, self, topicId, rootKey)`.
- `ITopicRouter` gains an **optional** `routeToRoot?(rootKey: Uint8Array, activity: Uint8Array): Promise<Uint8Array>` — "deliver this frame to the root group of `rootKey`". The walk uses it for the `d = 0` step of a root-placed topic when the router has it, and falls back to `routeAndAct(rootCoord(rootKey), …)` otherwise. db-p2p binds it to the key network so the subscriber reaches the root by the same rule storage placement uses (FRET's raw nearest peer can be a different network's peer on a shared ring).
- The registration handle remembers the root key, so renewal's "all backups failed → re-run the walk from `d_max`" re-registers at the same root.

### Verifier

`MembershipVerifier.verifyMessage(…, opts)` accepts a placement in its options (extend `RefetchBound` or add a sibling options type):

```ts
/** The coord is a root-placed cohort; its threshold is ceil(cert.members.length × quorumRatio). */
interface RootPlacement { readonly quorumRatio: number }
```

With a placement, the verifier uses `ceil(cert.members.length × quorumRatio)` for **all three** threshold checks it makes at that coord — the cert's self-consistency, the rotation-chain check, and the message — instead of its constructor `minSigs`. It passes the placement to the membership source (`IMembershipSource.current/fetch(coord, opts?)` gain an optional `{ rootPlaced: true }`, routed unchanged by `createMembershipSourceRouter`) and to the direct trust anchor (`IMembershipTrustAnchor.directAnchor(cert, tier, placement?)`), so db-p2p can fetch from and anchor against the root group.

A cached cert remembers the placement it was validated under. A call with a different placement (absent vs present, or a different ratio) treats the cache entry as a miss and re-validates, so a cert accepted under one rule is never used under another. `CohortSigner.verifyThreshold` already takes `minSigs` per call; reuse it.

Keep `DEFAULT_MIN_SIGS` and the constructor `minSigs` as the rule for every non-placed coord.

## Edge cases & interactions

- **No producer yet.** Every new field is optional; with none set, every code path computes exactly what it computes today. Verify by the existing suites staying green, not by new tests.
- **Signing-payload coverage.** A frame signed with `rootKey` must fail verification once `rootKey` is removed or changed, and a frame signed without it must keep its exact current image. One `wire.spec.ts` test per payload that gains the field (register and child link).
- **Placement mismatch in the verifier cache.** A cert cached as trusted under the default rule must be re-checked, not reused, when a call arrives with a placement, and vice versa. This is the one piece of new branching logic worth a test in `membership.spec.ts`: a 3-member cert threshold-signed by 3 verifies under `{ quorumRatio: 0.75 }` (needs `ceil(2.25) = 3`), the same cert is untrusted under the default `minSigs` 14, and a 3-member cert with only 2 signers is untrusted under the ratio.
- **Rounding.** `ceil(n × ratio)` with `n = 1` gives 1; with ratio `0.75` and `n = 4` gives 3. Same formula as `captureCommitCert`, so the commit certificate and the verifier agree by construction — say so in the doc comment.
- **Ratio validation.** A ratio outside `(0, 1]` is a programming error: throw at the call site that constructs the placement, not inside verification.
- **Router without `routeToRoot`.** The walk's fallback to `routeAndAct(rootCoord(rootKey))` keeps mock routers and older bindings working; test one `walk.spec.ts` case where a router with `routeToRoot` is used for `d = 0` and `routeAndAct` for `d ≥ 1`.
- **`rootKey` at `d ≥ 1`.** Carried but does not change the coord; it only matters to the host's parent-coord derivation for `d = 1`.
- **Renewal re-walk** keeps the root key (inspection; the handle stores the original request).
- **db-core stays FRET-free** — `packages/db-core/test/no-fret-import.spec.ts` must stay green.
