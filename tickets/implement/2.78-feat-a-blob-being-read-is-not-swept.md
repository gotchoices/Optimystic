# A blob being read is not swept

A node keeps a blob's pieces while some hold names it, and `PieceSweeper` (`packages/db-p2p/src/blob/piece-sweeper.ts`) deletes every stored piece that no held blob's tree reaches. Today the sweeper's roots are exactly the blobs with a record (`BlobRecordStore.listRefs`), so a blob whose last hold has gone has no root and its pieces are deleted — correctly, since nothing named it. What is missing is the case where a read of such a blob is running: the read is reading pieces the sweep is about to delete.

Nothing takes the last hold off a blob on its own today, so the case is not yet reachable in practice. `feat-blob-cached-copies-stay-within-a-budget` makes it reachable: it removes the `cached` hold from the least recently read blobs to stay inside a byte budget, and then sweeps. The existing `NOTE:` at `LocalBlobService.holdCached` in `packages/db-p2p/src/blob/local-blob-service.ts` already names the requirement — "eviction of cached blobs must skip a blob with a fetch session in flight" — and this ticket builds the mechanism it asks for, so the budget has something to ask.

The mechanism is a count of reads and fetches in flight per reference, kept by `LocalBlobService`. The sweeper takes those references as extra roots, so their present pieces are kept whether or not they have a record. The budget (next ticket) reads the same count to skip a blob it must not evict.

## Design

### Uses in flight (`LocalBlobService`)

```ts
/** Whether a read or a fetch of `ref` is running on this node. */
inUse(ref: BlobRef): boolean;
/** Every ref with a use in flight, in no promised order. */
inUseRefs(): BlobRef[];
/** Count a use of `ref` until the returned function is called. Calling it more than once is a no-op. */
beginUse(ref: BlobRef): () => void;
```

A private `Map<BlobRef, number>` of counts: `beginUse` raises the count and returns a release that lowers it and deletes the entry at zero. The release captures a `released` flag so a second call cannot lower another holder's count — a release is handed to a `finally`, and a `finally` reached twice (a generator that throws while returning) would otherwise unprotect a live read. `beginUse` is synchronous and takes no lock, so it can be the first statement of a generator body with no `await` before it.

**Where a use is held.** Every path that reads bytes or brings them here:

- `LocalBlobService.readThrough` — the use is taken as the **first statement of the generator body**, before `signal?.throwIfAborted()` and before any `await`, and released in a `finally` around the rest. An async generator's body does not start until its first `next()`, so a read that is created and never iterated takes no use; `finally` runs on completion, on a throw, and when a `for await` consumer `break`s (which calls the generator's `return`). This one site covers `LocalBlobService.read` and both branches of `NodeBlobService.read`, which all reach bytes through `readThrough`.
- `LocalBlobService.fetch` — around its body. It only stats today, but the contract is "every public read and fetch holds a use", and a path that is exempt by accident is the kind of hole this ticket exists to close.
- `NodeBlobService.fetch` — around its body, so a blob being brought here from another machine is in use from before its first piece rather than from the session's start.
- `NodeBlobService.startSession` — the one path for every fetch session this service starts. The use is taken when the session starts and released when `session.done` settles, either way. This is the window the `holdCached` `NOTE:` names: a read that consumed its whole range returns while its session is still finishing its confirming walk and marking the record whole, so the read's own use is already gone by then and the session's is what keeps the blob.

A pull the announce receiver starts on the fetcher directly (`BlobAnnounceReceiver` in `packages/db-p2p/src/blob/announce-receiver.ts`) needs no use: it takes the `responsible` hold and flushes it before it starts the pull, so the blob has a hold of its own for the whole pull.

### The sweeper's extra roots

```ts
export interface PieceSweeperDeps {
	// …existing…
	/** Refs a read or fetch is running on (`LocalBlobService.inUseRefs`); their present pieces are kept
	 *  whether or not they have a record. */
	readonly inUseRefs: () => Iterable<BlobRef>;
}
```

Required, not optional, so the one construction site (`LocalBlobService`'s constructor) is a compile error until it supplies it.

The sweep gains a walk that does not require a record — `walkRecord` returns at once for a ref with none, which is exactly the ref this protects — and calls it **inside the exclusive gate, in `decideAndDelete`**, beside the re-walk of `changed` and before `inProgress`'s ids are added. Inside the exclusive block because that is the latest point at which the sweep can read anything, so a use taken at any time before the deletes begin is seen. A ref that also has a record is walked twice, which is idempotent and costs one extra tree walk of a blob somebody is reading right now.

A ref in use whose tree cannot be read aborts the sweep (`tree-unreadable`) exactly as a held blob's does. An aborted sweep deletes nothing, which is the keep-everything direction this subsystem already chose (the accepted-tradeoff `NOTE:` above `walkRecord`).

**What this does not close.** `beginUse` takes no gate, so a read that begins after the sweep has read `inUseRefs()` inside its exclusive block, but before the deletes finish, is not protected. Such a read is a read of a blob with no hold at all, which is the exposure the `NOTE:` at `NodeBlobService.storedPiece` already records; leave that `NOTE:` as it is. Making `beginUse` take the gate shared would make it `async`, which would move it after an `await` and lose the "before any `await`" property the generator site depends on — the trade is deliberate, and the window is bounded by one delete phase.

### `NOTE:` to replace

The `NOTE:` above `LocalBlobService.holdCached` asks a future ticket to do what this one does. Replace it with one line saying where the protection now is: the uses `readThrough`, `fetch` and `startSession` hold, and the sweeper's `inUseRefs` roots.

## Edge cases & interactions

- **A read of a blob whose record is gone.** The sweep walks the ref from its reference through the pieces present and keeps them; the read finishes. **Test.**
- **An abandoned iterator.** A consumer that stops calling `next()` without calling `return` never runs the `finally`, so the use stays until the process ends, and the blob is never swept or evicted. `NOTE:` at `beginUse`: harmless while consumers use `for await` or call `return`; if a cache that never shrinks is seen, put a time limit on a use. By inspection.
- **A release called twice.** The `released` flag makes the second call a no-op, so a live read keeps its protection. By inspection of `beginUse`.
- **A session that outlives its read.** The session's own use covers the tail; the read's is already released. By inspection of `startSession`.
- **A use taken during the delete phase.** Not protected; the pre-existing exposure of reading an unheld blob, recorded at `NodeBlobService.storedPiece`. By inspection.
- **A ref in use that also has a record.** Walked by both passes; the second walk adds nothing and removes nothing. By inspection.
- **An in-use ref whose tree is malformed.** Aborts the sweep as a held blob's does, deleting nothing. By inspection.
- **`inUseRefs` while no sweep runs.** Nothing reads it; the map is the only cost. By inspection.
- **Concurrent reads of one blob.** The count is a count, so the last release unprotects the blob. By inspection.

## Tests

One test, added to `packages/db-p2p/test/local-blob-service.spec.ts` beside the existing sweep-race tests, over a `LocalBlobService` built by that file's `serviceOver` helper (whose `setTimer` never fires, so the only sweep is the one the test calls).

- **A sweep keeps the pieces of a blob being read after its last hold went.** `put` 300 KiB (two data pieces and a list root, so the read pauses between chunks), then `unpin(ref, DEFAULT_BLOB_OWNER)`, which deletes the record and leaves the pieces. Open `read(ref, { from: 'here' })` and take its first chunk. `sweep()` deletes nothing and its `kept` count covers the blob's pieces; the rest of the read yields the original bytes. Finish the read, `sweep()` again, and the pieces are gone. This is the one race the next ticket's eviction depends on, at the lowest layer that reproduces it.

## Docs

- `docs/blobs.md` §Holds: the sweep paragraph lists "Four things can make a piece live while it decides" — make it five, with the new one: **a read or fetch in flight on a blob with no record.** `LocalBlobService` counts the reads and fetches running per reference (`inUse`, `inUseRefs`, `beginUse`), every `readThrough`, `fetch` and fetch session holds one for its duration, and the sweep takes those references as roots inside its exclusive phase, keeping every piece of their trees that is present. Say plainly what it is for: the blob whose last hold has just gone while something is reading it. Mention the bounded window a read starting during the delete phase leaves.
