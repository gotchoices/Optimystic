## The one thing that is wrong

`updateInternal` in `packages/db-core/src/collection/collection.ts` adopts the newest committed revision and then re-stages its pending actions against it **only if a block conflict was detected** — where a conflict means an incoming log entry names a block the tracker already holds a transform for. An action that changed no block holds no transform, so nothing conflicts, so it is never replayed. The commit then writes a log entry listing that action while the block transforms it carries do nothing. Readers materialize blocks, not log entries, so the action is lost on every node, permanently and silently.

The invariant that ought to hold, and does not: **a pending action must have been applied against the revision it commits over.** Today it holds only when the action's initial staging happened to touch a block the adopted revisions also touched.

A staged delete of a key the staging instance cannot see is exactly the action that changes no block: the `replace` handler (`buildInit` in `packages/db-core/src/collections/tree/tree.ts`) calls `find`, misses, and `deleteAt` on a not-found path returns `false` without writing. That is why the secondary-index symptom in the ticket title is the one that surfaces — `deleteIndexEntries` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts` stages such a delete whenever the deleting handle's index tree has not synced since the entry was written.

## Reproduced, at both levels

**db-core, no plugin.** One `TestTransactor`, one tree id. Handle A creates the tree and commits an anchor entry; handle B then opens it with `Tree.open` (so B's tracker holds **no** transforms) and reads the anchor; A commits a second entry, key `1`; B — which has never read key `1` — stages `[[1, undefined]]` and syncs. A third, fresh `Tree.open` still finds entry `1`.

> The `Tree.open` for B is load-bearing and is the part that costs time to rediscover. Building **both** handles with `Tree.createOrOpen` does **not** reproduce: the second `createOrOpen` stages its own header/root blocks into B's tracker, A's log entry names the root, so `conflicts` on the tracker fires and the existing replay masks the defect. B must open an already-committed tree.

**Plugin, two `Database` handles over one `FileRawStorage` directory.** Exactly the fix ticket's steps — A inserts `(1,'seed-1')` and `(2,'seed-2')`, B scans, B deletes id 1 — and `expectIndexAgreesWithScan` (`packages/quereus-plugin-optimystic/test/query-helpers.ts`) fails on both handles with:

```
T: index entries must correspond one-to-one with rows
  T_by_v (declared): 1 rows, 2 entries
    orphaned (no-row): value ["seed-1"] pk ["1"]
```

## The fix, and the evidence it is the right one

Replay whenever the adopted context moved past the one the pending actions were staged against and there is anything pending — not only on a detected block conflict. `replayActions` already resets the tracker and re-stages under the collection latch, so this is a gating change, not new machinery. The exact edit that was validated, at the tail of `updateInternal`:

```ts
const adoptedRev = this.source.actionContext?.rev;
const contextAdvanced = adoptedRev !== undefined && adoptedRev !== actionContext?.rev;
if (anyConflicts || (contextAdvanced && this.pending.length > 0)) {
	await this.replayActions();
}
```

(`actionContext` is the pre-refresh context already captured earlier in the method; `advanceContext` is monotonic, so "different" means "advanced".) With it applied, both reproductions above go green.

Measured on that change, so the implement pass does not have to re-establish it:

- `packages/db-core` full suite: **1668 passing, 0 failing**.
- `packages/quereus-plugin-optimystic` full suite: **939 passing, 13 pending, 0 failing** — the same counts as the unpatched baseline.
- Wall clock for that suite: **2m51s patched vs 2m46s unpatched** (one run each, `yarn workspace @optimystic/quereus-plugin-optimystic test`). About 3%, inside run-to-run noise. The op-counting specs (`index-backfill-cost.spec.ts`, `cold-apply-cost.spec.ts`) pass unchanged, so the extra replays did not move the storage-op budgets either. Re-measure and record what you get, but do not expect to have to defend a regression.

The guards are the one behavioural surface worth thinking about: a replay that did not previously happen now re-runs `enforceUpsertGuard` and `assertEntryUnchanged` against the newly adopted state. That is what [docs/internals.md §Conflict replay re-makes the uniqueness decision (entry guards)](docs/internals.md#conflict-replay-re-makes-the-uniqueness-decision-entry-guards) already says *should* happen on every run, and the whole of `packages/db-core/test/tree-guard.spec.ts` passes, so this is the gate catching up with the documented intent rather than changing it.

## Correction to the fix ticket's plugin prescription

The fix ticket asked for a `get` on the tree before staging in `deleteIndexEntries`, reasoning that it would pull the leaf in so the delete shows up as a transform. **That reasoning is wrong, and it was measured to be wrong.** A read creates no transform, and — more to the point — the read happens at the same stale context the staging does, so it misses the entry too. The db-core reproduction above already performs a `get` on the missing key immediately before staging and still loses the delete.

What does work in that position is `await tree.update()` before staging: it advances the index tree's context, the subsequent `find` locates the entry, and the delete writes a real transform. That was confirmed working. But it costs a refresh per maintained index per deleted row, and it still only narrows the window — an entry a rival commits between that `update()` and the sync is blind again. With the db-core rule in place it buys nothing the rule does not already guarantee.

**Recommendation: do not add the `update()`.** Put a `NOTE:` at `deleteIndexEntries`, and at the `[oldTreeKey, undefined]` element inside `updateIndexEntries` which is the same shape, recording that these deletes are deliberately staged without first proving the entry is visible and that their correctness rests on `updateInternal` replaying pending actions against the revision it adopts. Name the db-core site so the next reader can follow it. If you disagree and add the refresh anyway, say in the handoff what it cost.

## Sweep for other blind deletes

Every site that stages a delete slot on a tree the writer may not have read:

- `deleteIndexEntries` (`packages/quereus-plugin-optimystic/src/schema/index-manager.ts`) — the reproduced site.
- `updateIndexEntries` (same file), the `[oldTreeKey, undefined]` element. Same class, currently masked in small trees: the sibling upsert of the new entry in the same action writes a block, and when old and new entries share a leaf the resulting transform makes the adopted entry conflict and forces a replay. Once old and new keys land in **different** leaves the overlap disappears and the old-entry delete is lost exactly as above. Not separately reproduced — it needs a multi-level index tree — and it is closed by the same db-core change.
- `CatalogBatch.commit` (`packages/quereus-plugin-optimystic/src/schema/catalog-batch.ts`) and the drop tombstone in `deleteSchema` (`packages/quereus-plugin-optimystic/src/schema/schema-manager.ts`) both call `update()` on the tree before staging, so they are narrowed today rather than blind — with the residual rival window described above. The tombstone path's `catch` fallback stages a bare `[tableName, undefined]` after a failed read, which *is* blind; also closed by the db-core change.
- `applyUniqueEvictions` and the DELETE arm of `xUpdate` (both `packages/quereus-plugin-optimystic/src/optimystic-module.ts`) stage main-table deletes guarded `unchanged` after `requirePreWriteRow` has read the row, so the row is visible and the delete always writes. Fine as they are.
- The two `tree.stage` backfill/populate sites in `optimystic-module.ts` are upserts, which always write. Not this defect. (Whether a transform computed against a stale base is still safe to apply over adopted content is a different, already-filed concern — `bug-a-pended-transform-does-not-carry-its-base` in the backlog. Worth noticing that this change also narrows that one, since a replay re-derives the transform against the adopted base. Do not widen this ticket to chase it.)

## Tests to add

Pick whichever package's existing helpers fit and say which in the handoff. - **Plugin, the end-to-end shape.** `twoHandles` in `packages/quereus-plugin-optimystic/test/concurrent-row-change-refusal.spec.ts` currently seeds rows **alternately** through A and B specifically to sidestep this defect, and its doc comment names this ticket. Once the fix lands, add a case that seeds through A only and lets B delete, closing on `expectIndexAgreesWithScan` on both handles, and delete the sidestep paragraph from that comment. Leave the alternating seed itself in place for the existing cases unless removing it is free — the point of those cases is the guard, not this.

## Docs

Add the gate: a replay runs whenever the refresh adopted a newer revision and anything is pending, because an action that changed no block leaves no conflict to detect and would otherwise be logged without ever being applied.
