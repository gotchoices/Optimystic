# A cluster request carries the consensus deliveries its target is still owed

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29), question 2. Waits on the decision ticket `decide-whether-a-two-machine-write-drops-to-three-calls`, which carries the full design and its correctness argument; this ticket is its first half. The second half, `a-two-member-pend-defers-its-final-delivery-to-the-commit`, is what actually removes a request from a two-machine write, using the mechanism built here.

## Background

A consensus operation ends with the **consensus delivery**: the coordinating node sends each member the record carrying a majority of commit signatures, and the member applies the operation to its storage on receipt (`broadcastMergedRecord` in `packages/db-p2p/src/repo/cluster-coordinator.ts`). A member whose delivery failed is retried by a timer (`scheduleCommitRetry` / `retryCommits`, starting at `commitBroadcastRetryInitialMs`, default 250 ms, backing off), and the transaction's entry in `ClusterCoordinator.transactions` lives until the retry finishes.

A delivery like that is "owed" to the member: the record is decided, nothing about it can change, and the member only has to receive it. This ticket lets any other request the coordinator sends that member carry the owed records along, ahead of its own record, so the member applies them first. Today the only case is a failed delivery; the follow-up ticket adds a deliberate one.

## Design

### Which records ride along

A record is **owed** to peer P when its `ClusterCoordinator.transactions` entry has an armed retry whose `pendingPeers` contains P **and** the record already carries a commit majority (`hasCommitMajority`). Records without a majority are excluded: re-sending one asks the member for a vote, and the compact answer below carries no signatures.

`updateMember` is the one place a request goes to a remote member, so it attaches P's owed records there, oldest first (by when they became owed), at most `MaxCarriedRecords` (4) per request, and only when P has advertised that it understands carried records (below). The record the request is *for* is never carried in its own request.

### Taking and returning an owed record

An owed record is **taken** synchronously when attached: P is marked in flight for that record so a second concurrent request to P does not carry it too. It is not removed from `pendingPeers` until the answer says it was delivered, and `retryCommits` neither re-sends to an in-flight peer nor treats the retry as finished because the in-flight peer is skipped. When the carrying request's answer comes back:

- **delivered** → the same bookkeeping `retryCommits` does for a successful delivery: merge the outcome into the record's `applyOutcomes`, drop P from `pendingPeers`, clear the retry when nobody is left, and give this node's own member its second reconcile when it applied and P now reports holding the revision (`reconcileLocalMemberAgain`, as `broadcastMergedRecord` decides). Factor this into one helper that `retryCommits` also calls, rather than duplicating it.
- **not delivered, or the carrying request failed** → clear the in-flight mark; the record stays owed and the timer (or the next request) delivers it.

Delivery is idempotent on the member (`handleConsensus` dedups by `messageHash` and runs `handleAlreadyExecuted`), so a carried record that P applied but whose answer was lost is harmless to send again.

### Interface

- `ICluster` (`packages/db-core/src/cluster/i-cluster.ts`) gains an optional method beside `update`:
  `updateCarrying?(record: ClusterRecord, carried: readonly ClusterRecord[]): Promise<{ answer: ClusterRecord; carried: CarriedOutcome[] }>`.
  `ClusterMember` does not implement it (this node's own member is never owed a carried record: `broadcastMergedRecord` delivers it in process, first). `ClusterClient` and the mesh harness's client do. `updateMember` uses it only when it has records to carry.
- `CarriedOutcome` (in `packages/db-core/src/cluster/structs.ts`): `{ messageHash: string; delivered: boolean; outcome?: MemberApplyOutcome; error?: string }`, one per carried record, in the order sent. `delivered` is true only when the member ran `update` on it without throwing and without redirecting. `outcome` is the member's own `applyOutcomes` entry from that answer. Compact on purpose: echoing whole records back would double the response size.
- `MemberApplyOutcome` gains `acceptsCarried?: true`. `ClusterMember.withOwnApplyOutcome` stamps it on every answer, so the entry is no longer omitted when there is nothing else to report. The coordinator remembers, per peer, the last value that peer's own answer stamped (taken from the peer's own response, keyed by the peer asked, exactly as `collectApplyOutcomes` does), in a bounded map (LRU, 1024 peers). A peer that answers without the stamp is forgotten, so a downgrade to an older build stops the carrying. Check every reader of `applyOutcomes` (`membersAwaitingConsensus`, `remoteMemberHolds`, `executeClusterTransaction`'s cohort loop, `pendCohortDurability` in `coordinator-repo.ts`) still treats an entry carrying only `acceptsCarried` as "nothing reported".

### Wire

The cluster request envelope `{ operation: 'update', record }` gains an optional `carried?: ClusterRecord[]`, and the answer to a request that carried any gets one extra field, `carried: CarriedOutcome[]`, on whatever object it already returns (the record, a redirect, or the error envelope). No new operation name and no protocol version: an older member parses the envelope, ignores the field and answers without `carried`, which the client reports as every carried record not delivered. An older coordinator never sends the field.

- `ClusterClient.updateCarrying` builds the envelope and encodes it; if the encoding exceeds `MAX_CONTROL_MESSAGE_BYTES` it sends the record alone and reports every carried record not delivered, so carrying can never make an otherwise-sendable request fail. It strips `carried` off the answer before the existing redirect/error handling sees it. A redirect of the main record does not undo carried records the member already applied; follow the redirect for the main record only.
- `ClusterService.processOperation` processes `carried` first, in order, each exactly the way a standalone record is processed — `learnPeerAddresses`, `checkRedirect` (a redirect means not delivered), then `cluster.update` inside its own `try`, so one carried record's throw is that record's `error` and never fails the request — then the main record as today. Reject a `carried` that is not an array of at most `MaxCarriedRecords` entries by ignoring it (log once), not by failing the request.
- Put that loop in one shared function (for example `applyCarriedRecords` in a new `packages/db-p2p/src/cluster/carried-records.ts`) that both `ClusterService` and the mesh harness's client call, so the in-process mesh exercises the same ordering the wire does. The harness's `onClusterDelivery` hook should report the carried records too (extend its signature; keep existing callers compiling).

## Edge cases & interactions

- **Ordering on the member** — carried records are applied strictly before the main record, in the order sent. Verified by the test below.
- **Two concurrent requests to one peer** — the in-flight mark stops both carrying the same record. By inspection.
- **The retry timer firing while a carry is in flight** — `retryCommits` must skip the in-flight peer without clearing or releasing the transaction (today it clears when `pendingPeers` is empty). By inspection plus the assertion that a transaction with an in-flight carry is never released.
- **The transaction released while a carry is in flight** (retry budget exhausted, `releaseTransaction`) — the late answer finds no entry and is dropped. By inspection.
- **Carried record expired by the member's clock** — the member throws `Transaction expired` for a record it already voted on; that is the record's `error`, it stays owed, and the retry budget ends it as today.
- **Request too large with carried records** — sent without them (client-side check above).
- **Older member** — never advertised `acceptsCarried`, so never sent `carried`; if the stamp is lost or forged, it ignores the field and everything stays owed. Mixed-version behaviour is by construction; the unit test below pins the gate.
- **Redirected main record** — carried records the member applied stay applied; the main record follows the redirect alone.
- **Address learning and inbound authorization** — carried records go through `learnPeerAddresses` and `checkRedirect` like any record; authorization is per stream and unchanged.
- **Recovery after restart** (`recoverTransactions`) — re-arms owed deliveries as before; carrying picks them up. No change to persisted state shape.
- **`debt-a-recovered-commit-retry-restarts-its-budget`** (backlog) touches the same retry fields; do not change the attempt counting here.

## Tests

Default is no new test; these two pin branching that nothing else covers.

- `cluster-coordinator.spec.ts` (fake clients): a record owed to a peer rides on the next request to that peer only when that peer's last answer stamped `acceptsCarried`; a peer whose answer drops the stamp is sent the record alone by the retry. Expected: the carrying client's `updateCarrying` is called with the owed record for the stamping peer, plain `update` for the other.
- Mesh (three members, `createMesh(3, { responsibilityK: 3, clusterSize: 3 })`): fail one member's consensus delivery for write 1 (so a retry is armed; make its first interval long — `commitBroadcastRetryInitialMs` through the mesh's consensus config, adding the pass-through to `MeshOptions` if it is not there), then run write 2. Expected: the member applies write 1 from write 2's first request, before the retry timer fires, and the retry for write 1 is cleared.
