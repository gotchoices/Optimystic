# A block read must distinguish "never existed" from "I could not find out"

## Background

A read for a block travels down four layers:

```
Collection / BTree / Log
  └─ TransactorSource.tryGet         (db-core)   → IBlock | undefined
      └─ NetworkTransactor.get       (db-core)   → GetBlockResults
          └─ CoordinatorRepo.get     (db-p2p)    → local storage, then the cohort
              └─ StorageRepo.get     (db-p2p)    → BlockStorage
```

The wire answer per block is:

```ts
export type GetBlockResult = {
    block?: IBlock;            // materialized content, if any
    state: BlockActionState;   // { latest?: ActionRev, pendings?: ActionId[] }
};
```

There is no way to express "I do not know." A block that has never been written and a block this
node cannot reconstruct both come back as `{ state: {} }`, and `TransactorSource.tryGet` turns both
into `undefined` — which every caller above reads as *absent*.

### The two sites that collapse the distinction

Both are places where the code already **knows** it is guessing, and says nothing:

1. **`StorageRepo.get`, the missing-base catch** (`storage-repo.ts:229-239`). Promoting a
   context-supplied revision throws `MissingBaseRevisionError` when this node holds the pending
   record for revision N but never received the revision it applies to. The catch logs
   `get:promote-skipped-missing-base` and falls through; `blockStorage.getBlock()` then finds no
   committed revision and the block is returned as `{ state: {} }` at `storage-repo.ts:271-273`.
   This node holds records proving the block exists and still answers "nothing here."

   This is exactly the reported trace: a node held revision 2 of a collection's blocks with no
   revision 1 to apply it to, so every read of the collection header came back absent — and the
   layer above invented an empty collection on every query, indefinitely, with no error.

2. **`CoordinatorRepo.get`, the cluster-consult catch** (`coordinator-repo.ts:341-357`). When the
   block is missing locally the coordinator asks the cohort. If that throws, it logs
   `cluster-fetch:error` and returns the local "absent" — an answer it has just failed to confirm.
   `NetworkTransactor` then treats that as an **authoritative** absent and deliberately does not
   retry it (`network-transactor.ts:133-162`, which cites this coordinator reconciliation as the
   reason retrying is unnecessary). The one thing that was supposed to make the absent trustworthy
   silently did not run.

Note what is **already correct** and must stay that way: a block for which no peer responded at all
throws out of `NetworkTransactor.get` (`network-transactor.ts:218-232`), so a total network failure
is not the gap. The gap is a peer that answered, confidently, with a guess.

## Design

Add an optional third field to the per-block result. It is opt-in: absent means "authoritative",
which is what every existing producer (including `TestTransactor`) keeps meaning with no change.

```ts
/** Why a repo could not establish whether a block exists. Present ONLY when the repo
 *  knows its own answer is a guess; an absent field is an authoritative answer. */
export type BlockUnavailableReason =
    /** Records for this block exist here but it cannot be reconstructed locally — a
     *  revision was received with no base to apply it to, or its history is truncated. */
    | 'unmaterializable'
    /** Nothing is held locally and the cohort could not be consulted to confirm it. */
    | 'peers-unreachable';

export type GetBlockResult = {
    block?: IBlock;
    state: BlockActionState;
    unavailable?: BlockUnavailableReason;
};
```

The repo protocol serializes the whole response with `JSON.stringify` (`repo/service.ts:250,274`),
so an added optional field needs no codec change.

```ts
/** Thrown by a block read when the responsible repo could not determine whether the
 *  block exists. Distinct from "the block is absent" (undefined) and from a transport
 *  failure — this node's data is genuinely indeterminate and the caller must not treat
 *  it as empty. */
export class BlockUnavailableError extends Error {
    constructor(readonly blockId: BlockId, readonly reason: BlockUnavailableReason) { … }
}
```

### Producers

- **`StorageRepo.get`** — track per block whether the missing-base catch fired. If it did *and*
  the block then reads as absent, return `{ state: {}, unavailable: 'unmaterializable' }`.
  Additionally, `blockStorage.getBlock()` can **throw** on a truncated history
  (`block-storage.ts:327-347` "Failed to find materialized block") or a failed restore
  (`block-storage.ts:312-314`). Today those escape `Promise.all` and fail the *entire* batch,
  taking healthy sibling blocks down with them. Catch them per block, log, and report
  `unavailable: 'unmaterializable'` — the read still fails at `TransactorSource`, so nothing is
  swallowed, but it fails for the one block that is actually broken.

  Leave the `context.actionId` branch's `Pending action ${id} not found` throw
  (`storage-repo.ts:256-259`) alone: that is a caller-contract violation, not an availability
  question.

- **`CoordinatorRepo.get`** — in the `catch` at `coordinator-repo.ts:355-357`, set
  `unavailable: 'peers-unreachable'` on the entry **only** when the block was `isMissing` (no local
  `state.latest`). A failed consult on a merely `isStale` block still has a real local answer and
  stays authoritative. Propagate any `unavailable` the refreshed local read carries.

  When `clusterLatestCallback` is unset there is no cohort to consult and the local answer *is* the
  whole truth — keep it authoritative, and say so in a comment (the existing note at
  `coordinator-repo.ts:317-323` already flags this configuration).

### Consumers

- **`NetworkTransactor.get`** — `isAuthoritative` (`network-transactor.ts:152-156`) must also
  require that no entry for the batch carries `unavailable`, so an indeterminate answer earns the
  second-chance retry against a different peer that an absent answer deliberately does not get.
  Extend the merge preference at `network-transactor.ts:204-216` to a three-way ranking:
  **has a block** > **authoritative absent** > **unavailable**. One peer that positively knows the
  block is absent outranks another that does not know.

- **`TransactorSource.tryGet`** (`transactor-source.ts:38-63`) — when the surviving entry carries
  `unavailable` and no block, throw `BlockUnavailableError` instead of returning `undefined`. Do
  not record a read dependency for it (the existing rule: dependencies are recorded only for blocks
  that actually exist).

The throw propagates through `Chain`, `BTree`, `Log`, and `Collection`, so a query against a
collection this node cannot read fails with a named error naming the block — instead of returning
zero rows.

## Edge cases & interactions

- **A genuinely new collection.** The first `createOrOpen` of every collection probes a header that
  has never existed. That must stay an authoritative `{ state: {} }` — if it ever came back
  `unavailable`, creating any collection would become impossible. This is the single most important
  regression to guard; make it an explicit spec.
- **Tombstones.** A deleted block reverse-applies to nothing and `materializeBlock` returns
  `undefined` by design (`block-storage.ts:359-365`) with `meta.latest` still set. That is an
  authoritative absent and must **not** be marked unavailable. It never enters the missing-base
  catch, so keying off the explicit flag (not off "no block") gets this right — but assert it.
- **Pending-only blocks.** Metadata seeded by `savePendingTransaction` with no committed revision
  reads as absent (`block-storage.ts:53-58`). "Pended but not committed" is genuinely absent for a
  contextless read; keep it authoritative.
- **Mixed batches.** A `get` for ten blocks where one is unmaterializable must return nine good
  entries plus one flagged entry — not fail wholesale. This is the behaviour change in the
  per-block catch; test it directly.
- **`skipClusterFetch`.** Cluster-internal sync reads bypass the cohort consult on purpose
  (`coordinator-repo.ts:316`). Do not mark those unavailable — that would feed the recursion it
  exists to prevent.
- **Read-repair.** `isStale` with a failed consult keeps a valid local answer; only `isMissing`
  produces `peers-unreachable`. The specs in `coordinator-repo-read-repair.spec.ts` must stay green.
- **Retry cost.** `unavailable` re-enables the second-chance retry for a class of answer that
  currently short-circuits. That is intentional, but it is the same round-trip cost the
  `txn-perf-authoritative-notfound` work removed for *absent* — so the flag must never be set on
  the common "block does not exist yet" probe. The new-collection spec above pins this.
- **`Collection.update()`** (`collection.ts:132`) re-probes the header and silently no-ops when it
  is absent. With this change it throws on an unavailable header, which is the point — confirm the
  throw reaches the caller rather than being absorbed by `updateAndSync`'s retry loop. If
  `syncInternal` would retry it as a stale failure, it must not: `BlockUnavailableError` is not a
  `StaleFailure` and should propagate.
- **`TestTransactor`** never sets the field, so every db-core spec keeps its current behaviour.
- **File-level overlap, not site overlap.** `backlog/bug-orphaned-pending-after-divergent-commit`
  also lists `storage-repo.ts`, but it concerns leftover pending records on the **commit** path.
  This ticket touches only `get`. Do not merge them; do keep the two `KNOWN GAP` specs in
  `storage-repo.spec.ts` green.

## Key tests

`packages/db-p2p/test/storage-repo.spec.ts`
- A block whose pending revision has no base: `get` with a context returns `unavailable:
  'unmaterializable'`, not `{ state: {} }`.
- A block never written returns `{ state: {} }` with **no** `unavailable` field.
- A tombstoned block returns absent with no `unavailable` field.
- A mixed batch returns healthy siblings alongside the flagged block.

`packages/db-p2p/test/coordinator-repo-*.spec.ts`
- Missing locally + cohort consult throws → `peers-unreachable`.
- Missing locally + cohort consult succeeds → the fetched block, no flag.
- Stale locally + consult throws → the local block, no flag.

`packages/db-core/test/transactor-source.spec.ts`
- An entry with `unavailable` and no block throws `BlockUnavailableError` carrying the block id and
  reason, and records no read dependency.
- An entry with no block and no flag still returns `undefined` (the sparse-result and
  populated-but-empty cases already covered there must not regress).

`packages/db-core` collection level
- `Collection.createOrOpen` against a transactor whose header read is `unavailable` **throws**
  rather than inventing an empty collection. This is the end-to-end assertion for the reported bug.
- `Collection.createOrOpen` against a transactor with an authoritative-absent header still creates.
