Part of stage 1 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages) (the "Validity rejection" row of the classification table). Builds on the two prereqs: the returned-refusal plumbing `offline-sync-typed-promise-shortfall` adds (a new `WriteFailure` sibling, `refusalFrom` precedence, writer stop-by-name) and the signed `validity` marker `signed-validity-marker-on-reject-votes` puts on reject votes.

## The defect

When enough members vote reject, `ClusterCoordinator` throws `ValidatorRejectionError` (db-p2p only). `CoordinatorRepo.pendThroughCluster` returns it as a retryable `StaleFailure` when its own storage confirms a revision loss (`classifyStaleRejection`) and otherwise **rethrows** — so a remote writer sees a reset stream and a local one a plain aggregate, neither of which says "a validator judged this invalid". It must keep rethrowing anything it cannot classify: an unconfirmed reject is often a stale-revision loss seen only by members ahead of this coordinator, and calling that permanent would make the offline drain drop a change the network would have accepted after a rebase.

## Design

### Data, shape, predicate, error (db-core) — mirror the shortfall and expiry siblings

```ts
/** A write refused because members judged it invalid (signed `validity` marker on their reject votes,
 *  or this node's own storage-tier check). Plain data. Reasons are free-form, for a log line. */
export type ValidityRejection = {
	/** Never empty. `peerId` absent for a refusal this node's storage made without a vote. */
	refusals: { peerId?: string; reason?: string; computedHash?: string }[];
};
export type RejectedFailure = { success: false; reason?: string; conflict: false; rejected: ValidityRejection; /* siblings' fields `never` */ };
export type WriteFailure = StaleFailure | ExpiredFailure | ShortfallFailure | RejectedFailure;
export function isRejectedFailure(failure: WriteFailure): failure is RejectedFailure;
export class ValidityRejectedError extends Error { readonly refusals; constructor(rejection: ValidityRejection); toFailure(): RejectedFailure; }
```

Never retryable: re-sending the same content to the same validators gets the same verdict.

### When the coordinator says "rejected" — and only then

A rejection is typed as validity only when **every** reject vote that sank the record is either validity-marked or an expiry vote, and **at least one** is validity-marked. Anything else — an unmarked reject (stale revision, admission, an older member) beside it, or no marked reject at all — stays exactly as today. This is the cross-vote analogue of `expiryRejectionClocks`'s rule ("a mix stays a plain validator rejection"), tilted toward "unclassified" because the cost of a false "rejected" is a lost change and the cost of a false "unclassified" is a retry.

- `ClusterCoordinator`: compute it from the merged record's promise votes beside `expiryRejectionClocks` and attach it to `ValidatorRejectionError` as an optional `validity?: ValidityRejection` (the all-expiry case still throws `TransactionExpiredError` first, unchanged).
- `CoordinatorRepo.pendThroughCluster`'s catch, order: expiry → shortfall → conflict → held → **stale classifier** → `ValidatorRejectionError` with `validity` → `ValidityRejectedError(...).toFailure()` → rethrow. The confirmed-stale arm stays ahead: a confirmed revision loss means the writer rebases and sends different content, so a verdict on the old content says nothing final.
- **Commit side: nothing.** Commit records never run the transaction checker, so no commit-round reject is validity-marked (content-digest and base-declaration refusals are unmarked incapacity, per the marker ticket's table); `CoordinatorRepo.commit` is unchanged.

### Storage tier (solo cohort)

`StorageRepo.pend` runs `checkPendValidation` too, and today returns a reason-only `{ success: false, reason }`, which a writer retries as a non-conflict refusal up to its budget. When the result carries `validity`, return `RejectedFailure` with one refusal (no `peerId`). Unmarked refusals (`PEND_NOT_VALIDATABLE`, `VALIDATOR_FAULT`) keep their current answer. This is the answer a solo cohort's writer gets through `CoordinatorRepo.pendSolo`, which returns storage's refusal untouched.

### Writer consumers (db-core)

- `refusalFrom`: precedence becomes **rejected > expiry > shortfall > stale**. Rejected outranks expiry for the reason `expiryRejectionClocks` gives inside one record: a member judged the content, and reporting it as a clock problem would invite a retry the judgement already refuses.
- `Collection.syncAttempts`: stop by name with `ValidityRejectedError`, beside the expiry and shortfall arms.
- `TransactionCoordinator`: `pendRefusalError` maps it to `ValidityRejectedError`; `pendFailure` carries it whole; `commit()` throws it by name and `execute()` reports it as failed.

## Edge cases & interactions

- **A validity reject beside an unconfirmed stale reject** stays a thrown `ValidatorRejectionError` (unclassified). Deliberate — see the rule above. By inspection.
- **Mixed versions.** An older member never marks, so its rejects never produce this failure. An older writer receiving `RejectedFailure` retries it as a reason-only refusal until its budget ends, then fails. Note in the handoff.
- **Cancel** still runs on the writer for a returned refusal (`NetworkTransactor.pend`). By inspection.
- **The Quereus bridge** (`mapCommitRefusal` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts`) sees `ValidityRejectedError` in its fallthrough; check that the class name survives in the message or `cause`, and note it in the handoff rather than adding a mapping (stage 4 decides how offline mode surfaces `rejected`).
- **The dispute tickets** (`1.4-dispute-commit-path-block`, `1.5-dispute-writer-sees-disputed-pend`) will later block a marked rejection before it ends the pend; when they land, a disputed pend answers with their `DisputedFailure` instead. Nothing to do here; mention it in the `ValidityRejectedError` doc comment so the two are not confused.

## Tests

- One db-p2p test of the coordinator's rule, the only real branching here: given merged promise records, (a) all rejects validity-marked → `RejectedFailure`; (b) marked + expiry → `RejectedFailure`; (c) marked + unmarked → rethrown `ValidatorRejectionError`; (d) all expiry → `ExpiredFailure` (existing behaviour, keep as the control). Drive it at the lowest layer that has the rule — the helper that computes `validity` from the promise map, if it is a pure function, else `CoordinatorRepo.pend` with a stubbed `ClusterCoordinator` the way `packages/db-p2p/test/coordinator-repo-commit-conflict.spec.ts` stubs it.
