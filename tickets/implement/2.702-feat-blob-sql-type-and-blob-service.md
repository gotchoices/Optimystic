# `plugin.blobs`, `plugin.blobsFor(table)` and the blob SQL functions

Second part of what [docs/blobs.md §SQL](../../docs/blobs.md#sql) describes. `feat-sql-blobref-column-type` gave SQL the column type; this gives the plugin the service an application puts files through, the owner labels the later parts pin under, and the two SQL functions that read a reference's local state. This slug is the one `feat-blob-reference-trees-follow-sql-rows` names as its prerequisite: when it lands, the type and the service of [docs/blobs.md §SQL](../../docs/blobs.md#sql) both exist, and what remains is the reference trees, the pins and the offline queue.

Nothing here maintains a reference tree, pins on behalf of a commit, or announces. A blob put through this service is pinned — under a label that names the open transaction, or as `unstaged` — and stays pinned until something unpins it, which is `feat-blob-pins-follow-sql-commits`' and `feat-sql-columns-hold-blob-references`' work.

## Pin owner labels

A pin is held under an **owner label**, an opaque string the blob record stores (`BlobHold` in `packages/db-p2p/src/blob/blob-record.ts`). The plugin's labels are printable on purpose: they turn up in records and in logs. New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pin-labels.ts` — the one place in the plugin a label is built or read:

```ts
/** A pin held for a transaction's reference committed into `scope` (a reference tree's collection id). */
export function transactionReferencePinLabel(stampId: string, scope: string): string; // `sql/${stampId}/ref/${encodeURIComponent(scope)}`
/** A pin held for a blob `put` made while the transaction `stampId` was open. */
export function transactionPutPinLabel(stampId: string): string;                       // `sql/${stampId}/put`
/** A pin held for a blob `put` made outside any transaction, at `putAtMs`. */
export function unstagedPinLabel(putAtMs: number): string;                             // `sql-unstaged/${putAtMs}`
export const TRANSACTION_PIN_PREFIX = 'sql/';
export const UNSTAGED_PIN_PREFIX = 'sql-unstaged/';
export function transactionPinPrefix(stampId: string): string;                         // `sql/${stampId}/`

export type ParsedPinLabel =
	| { kind: 'reference'; stampId: string; scope: string }
	| { kind: 'put'; stampId: string }
	| { kind: 'unstaged'; putAtMs: number };
/** `undefined` for a label this plugin did not write (an application's own owner, or `default`). */
export function parsePinLabel(label: string): ParsedPinLabel | undefined;
```

The whole vocabulary lands in one go even though this part builds only two of the labels: `parsePinLabel` has to recognise all three shapes to be correct about which labels are not the plugin's, and the three prefixes are what `feat-sql-columns-hold-blob-references` enumerates pins by (`listPins(TRANSACTION_PIN_PREFIX)`, `listPins(UNSTAGED_PIN_PREFIX)`, `listPins(transactionPinPrefix(id))`). Splitting it would mean editing the module three times.

Why the labels are shaped this way: a `StampId()` is base64url, so it contains no `/`, and a scope is URI-encoded, so it contains none either — which makes the label unambiguously splittable without a parser. And putting the **scope** in the label rather than in the offline journal means the blob records are already the durable, per-machine record of which transaction owes which pin under which scope: a later settle or a restart reconciliation needs nothing added to `JournalEntryRecord` (`packages/db-core/src/offline/journal.ts`) and never decodes a journaled segment. One reference committed into two tables in one transaction is two pins.

## Where blobs live for each kind of transactor

**A new plugin-level option.** Add to `OptimysticOptions` and `ParsedOptimysticOptions` in `packages/quereus-plugin-optimystic/src/types.ts`, read in `resolveBinding` (`packages/quereus-plugin-optimystic/src/optimystic-module.ts`) exactly as `rawStorageFactory` is — out of the registration config only, never a per-table `using` argument, because it is a function reference. The argument-name list `resolveBinding`'s doc comment pairs with `SESSION_BINDING_VTAB_ARGS` is unaffected, for the same reason it is unaffected by `rawStorageFactory`.

```ts
/**
 * For a transactor with no libp2p node (`local`, `test`, `mesh-test`, a custom transactor):
 * where blob pieces and blob records live. Defaults to both in memory.
 *
 * Both or neither should be persistent. A persistent piece store over in-memory records loses
 * every pin at restart and the next sweep then deletes every piece; persistent records over
 * in-memory pieces report blobs the machine cannot serve, which `stat` corrects. The plugin
 * cannot tell whether an `IKVStore` is persistent, so neither case is refused.
 */
blobStorageFactory?: () => { pieces: IPieceStore; kv: IKVStore };
```

Honoured on **every** single-machine arm, not just `local`: an option a `test` transactor silently ignored would be a trap, and `feat-sql-columns-hold-blob-references`' restart spec uses it to stand in for a restart.

**The backend, in `CollectionFactory`** (`packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`):

```ts
/** A blob service that also lets its pins be read back by owner (`BlobPinIndex`, feat-blob-single-machine-service-and-pin-index). */
export type SqlBlobBackendService = BlobService & BlobPinIndex;

/** One network's blob store, as the SQL layer needs it. */
export interface BlobBackend {
	/** The transactor key (`${transactor}:${keyNetwork}`) this backend belongs to. */
	readonly key: string;
	readonly service: SqlBlobBackendService;
	/** The transactor of the same key. Reference trees and the scope registry of this network are read and written through it (feat-blob-reference-trees-follow-sql-rows). */
	readonly transactor: ITransactor;
}

/** One backend per transactor key, created on first use and shared by every table on that key. */
async getBlobBackend(options: ParsedOptimysticOptions): Promise<BlobBackend>;
/** Called once per backend, the first time it resolves; returns an idempotent unsubscribe. */
onBlobBackendResolved(listener: (backend: BlobBackend) => void): () => void;
```

Keyed and de-duplicated in flight exactly as `getOrCreateTransactor` is — a `blobBackendsInFlight` map beside `transactorsInFlight`, a resolution that fails not remembered, so the next caller tries again.

Resolution always starts with `getOrCreateTransactor(options)` (the backend carries it, and for `network` it is also what builds or reuses the node), then:

- **`network`:** the node's own service, `node.blobs` of the node under `getNodeKey(options)`. A node a host injected through `registerLibp2pNode` without `blobs` — `FactoryNode` types the attachments as `Partial`, so this is representable — falls through to the single-machine arm, logged once.
- **everything else** (`local`, `test`, `mesh-test`, a custom transactor): `new SingleMachineBlobService(options.blobStorageFactory?.() ?? { pieces: new MemoryPieceStore(), kv: new MemoryKVStore() })`, `start()`ed once built.

Log one line per backend under a new `blob` logger (`optimystic:quereus-plugin:blob`): `blob:backend-single-machine key=… reason=…`, with `reason` `transactor-has-no-node` or `node-without-blobs`.

**Lifecycle.** `CollectionFactory.dispose` stops and forgets the `SingleMachineBlobService` instances it built, beside clearing the transactors — the sweep timer is unref'd so this is hygiene rather than a leak, but a service nobody stops can run a sweep against a store the host has closed. A `network` backend's service belongs to the node and is stopped by `node.stop()` in `shutdown`; do not stop it here.

**A `NOTE:` in `createNetworkTransactor`,** where `createLibp2pNode` is called without `pieceStorage`: *the plugin's own node keeps blob pieces and records in memory, so they are lost on restart (the node logs its own `node-wiring` warning). If a host needs them persistent through the plugin, thread `blobStorageFactory` into this call's `pieceStorage` and key-value store.*

## The service an application holds

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/sql-blob-service.ts`:

```ts
/**
 * The blob service `plugin.blobs` and `plugin.blobsFor` hand out: one network's backend, resolved
 * on first use, with `put`'s owner defaulted from the bridge's open transaction.
 */
export class SqlBlobService implements SqlBlobBackendService {
	constructor(resolve: () => Promise<BlobBackend>, bridge: TransactionBridge, now?: () => number);
}
```

- **`put(source, options)`** uses the caller's `owner` when it gave one. Otherwise, while `bridge.getCurrentTransaction()?.isActive`, `transactionPutPinLabel(stampId)`; else `unstagedPinLabel(now())`. This is what [docs/blobs.md §SQL](../../docs/blobs.md#sql) means by "pinned as `unstaged`" and by a pin that follows the transaction. The decision is taken when the put starts, not when it resolves: a put that outlives its transaction keeps the label it began under, and `feat-sql-columns-hold-blob-references`' reconciliation is what clears such a stray pin. Say so in the doc comment.
- **`stat`, `fetch`, `pin`, `unpin`, `announce`, `pinsOf`** await the backend and delegate. **`read`** and **`listPins`** are async generators that await the backend and then `yield*`.
- **`onProgress` and `onDurability`** keep their listeners in a set on the wrapper. The first subscription starts resolution (`void`, a failure logged) and, once it resolves, attaches one forwarding listener to the backend's service; the returned unsubscribe removes the listener from the set and is idempotent. The precedent is `LateBoundCohortReachability` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/late-bound-reachability.ts` — follow its shape, including that a listener subscribed before resolution still hears everything after it, and that an unsubscribe before resolution leaves nothing attached.
- `pinsOf` and `listPins` are on the public surface deliberately: they are how a host inspects what the plugin is holding, and how the plugin's own later parts find their pins after a restart. Document them as reading this machine's blob records, not the network's.

## `plugin.blobs` and `plugin.blobsFor(table)`

`register` returns:

```ts
/** The blob service of the plugin's default network: the one a table declared with no `using` clause binds to. */
blobs: SqlBlobService,
/** The blob service of the network `table` uses. Rejects for a table that is not a known Optimystic table. */
blobsFor: (table: string, schema?: string) => Promise<SqlBlobService>,
```

Both need binding options, which are **resolved lazily, on first use**, because a host may set the session's `default_vtab_args` after `register` returns. Two new public members on `OptimysticModule`, each a thin wrapper over machinery that is already there but private:

- `defaultBindingOptions(db, config)` — `deriveDefaultOptions(config, sessionDefaultVtabArgs(db))`. Its `collectionUri` is the plugin catalog's and is irrelevant to a blob backend, which reads only the transactor, the key network and the libp2p options; say so in the doc comment.
- `bindingOptionsOfTable(db, table, schema?)` — `lookupOrInstantiate` (no initialization: the binding is fixed at construction), then the table's own options. That needs a public `get bindingOptions()` on `OptimysticVirtualTable` returning its private `options`. A table the engine's catalog does not know rejects with a `QuereusError` naming it.

`plugin.blobs` is one `SqlBlobService` built at `register` over `() => factory.getBlobBackend(module.defaultBindingOptions(db, config))`. `blobsFor` builds a fresh `SqlBlobService` per call over `() => factory.getBlobBackend(await module.bindingOptionsOfTable(...))`. **Not cached, and not reference-equal to `plugin.blobs`:** the wrapper is thin and `getBlobBackend` is where the sharing happens, so two wrappers over one network read the same records, hold the same pins and (each through its own forwarder) receive the same events. Document that plainly rather than implying identity.

A reference means something only in the network whose machines hold the bytes ([docs/blobs.md §SQL](../../docs/blobs.md#sql)). Nothing here refuses a reference written into a table on another network; that belongs to `feat-sql-columns-hold-blob-references`.

## SQL functions

New module `packages/quereus-plugin-optimystic/src/functions/blob-functions.ts`: `createBlobLocalityFunction(blobs: SqlBlobService)` and `createBlobSizeFunction(blobs)`, registered in `register`'s `functions` beside `StampId` and `CommitOutlook` and following the shape in `packages/quereus-plugin-optimystic/src/functions/transaction-id.ts`.

- **`BlobLocality(ref)`** — `numArgs: 1`, `flags: FunctionFlags.UTF8`, `isAsync: true`, return type `TEXT_TYPE`, nullable. NULL in gives NULL. Otherwise `parseBlobRef(arg)` then `(await blobs.stat(ref)).locality`: `here`, `partial`, `elsewhere` or `unknown`. **No `probe`**, so it is answered from this machine's records alone and never waits on the network.
- **`BlobSize(ref)`** — same flags, return type `INTEGER_TYPE`, nullable; `(await blobs.stat(ref)).size ?? null`. NULL while the root piece is not here, and for a reference this machine knows nothing of.
- Not `FunctionFlags.DETERMINISTIC`: the answer changes as bytes move.
- A `BlobRefError` — a non-string argument and a malformed string both raise one — is rethrown as `QuereusError(error.message, StatusCode.MISMATCH, error)`, so the SQL error carries the reason and keeps the original as its `cause`. Any other error propagates.
- Both answer through `plugin.blobs`, the default network: a scalar function has no table context. A host with tables on several networks reads `stat` through `plugin.blobsFor(table)` instead; the README says so.
- Document both as **not for writes**: a validating member re-executing a statement whose written value came from `BlobLocality` would compute a different value. (Backlog note "BlobLocality written into a row".)

## Edge cases & interactions

- **Malformed and NULL arguments.** Both functions: a malformed string or a non-string raises `MISMATCH` with a `BlobRefError` cause; NULL answers NULL. Spec cases.
- **A well-formed reference nobody put.** `unknown` and NULL — never an error, and never a missing-block fault ([docs/blobs.md §Design principles](../../docs/blobs.md#design-principles), "Known but not here is an ordinary state"). Spec case.
- **`plugin.blobs` used before any table exists.** Resolves the default network's backend on first use; for `network` that builds the node, exactly as the first table would. Inspection.
- **A durability or progress listener subscribed before resolution.** It receives every event after resolution; an unsubscribe before resolution leaves nothing attached to the backend. Inspection against the `LateBoundCohortReachability` precedent.
- **A backend resolution that fails.** Not remembered (the in-flight entry is cleared in a `finally`), so the next call retries — and a listener subscribed meanwhile stays in the wrapper's set and attaches on the next successful resolution. Inspection.
- **A host-injected node with no `blobs`.** Single-machine service, logged once with `reason=node-without-blobs`. Inspection.
- **`put` while a transaction is open that then rolls back.** The `put` pin survives the rollback — this part releases nothing. Stated in the doc comment and in the README, and closed by `feat-blob-pins-follow-sql-commits`.
- **Two tables on one transactor key.** One backend, so one set of records and pins. That is what `getBlobBackend`'s keying buys; `plugin.blobs` and `plugin.blobsFor` over those tables are different wrappers over it.
- **`plugin.dispose()`.** Stops the single-machine services the factory built (through `CollectionFactory.dispose`, which `dispose` already awaits last). A `SqlBlobService` used after dispose resolves a fresh backend, as a transactor requested after dispose is rebuilt. Inspection.
- **`blobStorageFactory` with a persistent piece store over in-memory records, or the reverse.** Documented on the option; not refused, because the plugin cannot tell. Inspection.

## Tests

`packages/quereus-plugin-optimystic/test/blob-functions.spec.ts`, on the `test` transactor, with the plugin registered including its `types` and `functions` (the helper `feat-sql-blobref-column-type` widened). A blob of two pieces, so the size comes off a list root rather than a raw root: `BLOB_PIECE_BYTES` (`packages/db-core/src/blob/limits.ts`) plus a short tail of a repeating pattern is enough.

- **A blob put through `plugin.blobs`.** `select BlobLocality(?), BlobSize(?)` answers `here` and the blob's size.
- **A well-formed reference never put.** `unknown` and NULL.
- **A malformed string.** The statement rejects with `StatusCode.MISMATCH` and the error's `cause` is a `BlobRefError`.
- **NULL.** Both functions answer NULL.
- **`put`'s owner default**, the one piece of branching logic in `SqlBlobService`: a put made outside any transaction holds exactly one pin, which `parsePinLabel` reads as `unstaged`; a put made between `begin` and `commit` holds one that `parsePinLabel` reads as `put` for that transaction's `StampId()` (read it with `select StampId()` inside the `begin`, which answers once a table has been touched — see the `StampId()` contract in `packages/quereus-plugin-optimystic/src/functions/transaction-id.ts`). Read the pins back with `plugin.blobs.pinsOf(ref)`.

Nothing tests the registration of the functions, the option plumbing, or the label builders on their own: `parsePinLabel` is exercised by the case above, and a round-trip test of the three builders against the parser would test the module against itself.
