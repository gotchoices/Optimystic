# A write names the blocks it committed

Part of GitHub issue #26 (a SQL app learns its commit's durability, and when it becomes full). This is the db-core half of "map the full-replication event back to the commit the app knows".

## Why

The full-replication event (`BlockDurabilityReachedEvent` in `packages/db-core/src/transactor/change-notifier.ts`) is keyed by **block** and **revision**, deliberately: the under-replication ledger keeps one entry per block at its highest revision, so a later write's copies clear an earlier write's shortfall and the earlier write never gets an event of its own. The event's own doc tells a host to "hold the block ids the write's result names (`PendSuccess.blockIds`)" — but nothing above the transactor ever sees `PendSuccess`. `Collection.sync` returns a `WriteDurability`, `TransactionCoordinator.commit` a `TransactionDurability`, and neither names a block. So no host can do what the event's doc says.

A host also needs the **revision** each block committed at, not just the id: an event for block X at revision 5 covers a write of X at revision 5 but not a later write of X at revision 7, and an event can fire before the write's answer has climbed back up to the host (see ticket `a-sql-commit-learns-when-it-becomes-fully-held`, which consumes this).

Capturing block ids from the tracker before commit is not a substitute: a retried attempt re-stages, and a re-stage mints fresh ids for inserted blocks.

## Design

Add one optional, action-level field to `WriteDurability`, beside `torn` and with the same lifecycle:

```ts
/** Action-level: every block this write committed, with the revision it committed at. Set by the
 *  db-core layer that issued the commit, never by a coordinator and never on the wire. Excludes
 *  `torn` blocks (they hold nothing). Merging two reports keeps, per block, the HIGHER revision —
 *  a block written at r and again at r+1 by one write is covered by an event at r+1 or later. */
readonly blockRevs?: Readonly<Record<BlockId, number>>;
```

A `Record` rather than a `Map` so it stays plain JSON like the rest of the type.

Rules:

- **Where it is set** — client side, at the three places a write's commit is confirmed, through one helper in `durability.ts` (e.g. `withBlockRevs(d, blockIds, rev)`), which drops any id in `d.torn`:
  - `TransactorSource.transact`, on a successful commit: `pendResult.blockIds` at `rev`. This covers every `Collection.sync` attempt and the own-entry re-send in `Collection.completeOwnEntry`, which both go through it.
  - `TransactionCoordinator.commitCollection`, on `commitResult.success`: its `blockIds` at the collection's pended revision.
  - `Collection.settleUnfinished`, on the "saved" return: `entry.blockIds` at `rev` (the write's own revision; a later revision built from it is ≥, so any event that covers the later one covers this).
  - The status-read branch of `completeOwnEntry` returns `undefined` and stays that way (no durability, so nowhere to put block ids — the existing NOTE there already describes this).
- **Merging** — `mergeDurability` treats `blockRevs` like `torn`: computed over the ORIGINAL reports (union, max revision per block) and re-attached to the merged answer; `stripMergedFields` strips it from per-cohort reports, so it never appears inside `otherCohorts` and never enters `distinctReports`' key. `withTornBlocks` removes newly torn ids from `blockRevs`.
- `recordCollectionDurability` / `transactionDurability` need no change: they go through `mergeDurability`.
- Update the `BlockDurabilityReachedEvent` doc to name `WriteDurability.blockRevs` as what a host holds, and the internals Commit Path paragraph to mention the field.

## Edge cases & interactions

- **Torn write**: blocks in `torn` must not appear in `blockRevs` — verified by the merge test below and by inspection of `withBlockRevs`.
- **Same block at two revisions in one write** (an own-entry finish at r, then a further attempt at r+1 under the same action id, merged in `syncAttempts`): max wins. Covered by the merge test.
- **Merging a merge** must equal merging its inputs (the existing `mergeDurability` property) — `blockRevs` included.
- **A remote coordinator's answer** never carries the field (set client-side only); a peer on an older build is unaffected since nothing is added to the wire. Verified by inspection: no db-p2p producer sets it.
- **A `CoordinatorPartialCommitError`'s `durability`** describes the committed half through the same `recordCollectionDurability` path, so it carries `blockRevs` for exactly the committed collections — no extra work, check by inspection.
- **`undefined` durability** (saved, holder unknown) carries no blocks; the consumer ticket treats such a write as one it cannot follow.

## Tests

One test pays: extend the existing `mergeDurability` spec with a case merging two reports whose `blockRevs` overlap (max wins), one carrying `torn` (torn ids absent from the result), and a merge-of-a-merge equal to the flat merge. No test for the three set-sites — they are one helper call each, checked by inspection and by the consumer ticket's end-to-end test.
