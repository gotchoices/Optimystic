# A blob remembers when it was last found unreferenced

docs/blobs.md §Lifetime: "A blob listed nowhere at two passes a grace period apart (7 days by default) loses its `responsible` hold", and the same for an owed entry whose scope stopped listing it. Two passes a week apart can only be compared if the first one leaves something behind that survives a restart. This ticket adds that something — a **mark**, the start time of the first counting pass that found a blob listed nowhere — on both the blob record and the owed entry, with the writes that set, clear and act on it, and the pure rule that turns a mark and a pass's start time into a decision.

Nothing here reads committed state, schedules anything or deletes anything. The marks are inert until `feat-unreferenced-blobs-are-reclaimed` lands the pass that writes them; this ticket exists separately because the record and ledger surface is a self-contained change with its own failure mode — a mark that outlives the hold it was about would release a live blob on a single pass — and because the pass is large enough on its own.

## The mark

Two fields, one on each of the two things that mean "kept for the network":

- `BlobRecord.unreferencedSince?: number` — milliseconds since the epoch, meaningful only while the record holds `responsible`.
- `OwedBlobEntry.unlistedSince?: number` — the same, for the owed entry's own scope.

Only the reclaim pass sets either. **Every write that adds or removes a `responsible` hold clears `unreferencedSince` in the same record write**, and **every write that creates or re-records an owed entry clears `unlistedSince`**. That rule is the whole safety argument: each of those writes is either fresh evidence that the blob is referenced, or the end of the hold the mark was about, so a mark left over from before could otherwise make one pass release a hold taken minutes ago.

### The record field

`packages/db-p2p/src/blob/blob-record.ts`: the field on `BlobRecord`, and a check in `recordProblem` mirroring `lastReadAt`'s — a value that is not a finite number refuses the record. Refusing is the established choice for a checked field (`lastReadAt`, `durability`) and it is the honest one, even though a refused record stops that blob's sweep until it is fixed: the alternative is a mark nothing can interpret deciding a deletion.

`packages/db-p2p/src/blob/local-blob-service.ts`:

- `recordAfterResponsibleHold` drops `unreferencedSince` from the record it returns.
- `recordAfterResponsibleRelease` (the prereq's helper) drops it too.
- Two new module helpers beside them, `recordWithUnreferencedMark(current, at)` and `recordWithoutUnreferencedMark(current)`, each returning the current record unchanged when there is nothing to do, so `changeRecord` writes nothing. `recordWithUnreferencedMark` returns the record unchanged when it holds no `responsible` hold: the mark is only ever about that hold.

### The ledger field

`packages/db-p2p/src/blob/owed-blob-ledger.ts`:

- The field on `OwedBlobEntry`, validated in `isEntryFor` beside `recordedAt` — an entry whose mark is not a finite number is malformed, which the ledger already logs and reads as absent rather than deleting, the existing rule, unchanged.
- `record` builds the stored entry from the fields a re-record keeps, explicitly, rather than spreading the existing entry: `{ ref, scope, holders: existing.holders, recordedAt: existing.recordedAt }`. That drops the mark, which is the point, and it does so without relying on `JSON.stringify` discarding an `undefined` property — this repository has `exactOptionalPropertyTypes` off (backlog `debt-tsconfig-exact-optional-property-types`), so an explicit construction is what says "these four fields and no others".
- `addHolders` keeps the mark: it spreads the existing entry today and should go on doing so. A peer confirming it holds a copy is not evidence that any row references the blob, so it must not restart the grace period. Say so in one line at the spread.

## The operations

Mirrored between the two stores, so the pass's apply step reads the same on both sides. Every one of them is a conditional write in the shape `LocalBlobService.releaseCached` already uses: **the change function is itself the condition**, applied at that reference's turn in the per-reference serial queue the store already holds, so nothing has to be re-read first and no lock is added.

### On the records

A new door beside `BlobCacheRecords`, declared in `local-blob-service.ts` and implemented by `LocalBlobService` for the same reason that one is a door rather than a second `BlobRecordStore`: every record change has to go through `changeRecord`, which the piece sweep relies on.

```ts
/** What the reclaim pass knows about one blob this node holds because it is responsible for it. */
export interface ResponsibleMark {
	readonly ref: BlobRef;
	/** When the first counting pass that found this blob listed nowhere started, if one has. */
	readonly unreferencedSince?: number;
}

/** What the reclaim pass needs of this node's blob records; `LocalBlobService` is it. */
export interface BlobReclaimRecords {
	/** Every record holding `responsible` with its mark, ascending by reference. A record that does
	 *  not decode is logged (`record:unreadable`) and skipped, as `responsibleRefs` does. */
	responsibleMarks(): Promise<ResponsibleMark[]>;
	/** Drop the mark. A record that is gone, holds no `responsible` hold, or carries no mark is a
	 *  no-op. Not flushed. */
	clearUnreferenced(ref: BlobRef): Promise<void>;
	/** Set the mark to `at` while the record still holds `responsible`; answers whether it wrote.
	 *  Not flushed. */
	markUnreferenced(ref: BlobRef, at: number): Promise<boolean>;
	/** Remove the `responsible` hold and its mark, but only while the record still holds
	 *  `responsible` AND its mark is still exactly `mark`; answers whether it wrote. A record left
	 *  with no hold is deleted and its pieces are left for the sweep. Flushed, as
	 *  `releaseResponsible` is. */
	releaseResponsibleIfMarked(ref: BlobRef, mark: number): Promise<boolean>;
	/** {@link LocalBlobService.sweep}, so the pass can sweep once after releasing holds — the same
	 *  door `BlobCacheRecords` opens for the cache budget. */
	sweep(): Promise<BlobSweepResult>;
}
```

- `responsibleRefs` is re-expressed over `responsibleMarks`, so one enumeration serves both and they cannot disagree about which records hold `responsible`. Its contract never specified an order, so sorting is not a change any caller can see; keep its `NOTE:` about reading every record where it is.
- **Why `markUnreferenced` has no expected-mark condition while the release does.** Nothing but the pass writes a mark, and passes never overlap, so the only thing that can change a mark under a running pass is a *clear* — from a hold being taken or released. For the release that is decisive, and the condition is the whole safety argument. For a mark it is not: a hold released and re-taken mid-pass leaves no mark, which is exactly what the snapshot said, so the condition could never fire. Conditioning on the hold, which *can* have gone, is the condition that matters. State this in the doc comment rather than carrying a parameter that cannot do anything.
- "Answers whether it wrote" is read off a `let wrote = false` the change function sets, not off `BlobRecordChange`'s before/after: a release that leaves a pin behind keeps the record, so presence cannot tell a write from a no-op. `BlobRecordStore.apply` calls the change function exactly once per update, which is what makes the flag sound.

### On the ledger

```ts
/** Drop the mark; no entry, or no mark, is a no-op. Not flushed. */
clearUnlisted(ref: BlobRef): Promise<void>;
/** Set the mark to `at` while the entry exists; answers whether it wrote. Never creates an entry. Not flushed. */
markUnlisted(ref: BlobRef, at: number): Promise<boolean>;
/** Delete the entry, but only while its mark is still exactly `mark`; answers whether it wrote. Flushed, as `delete` is. */
deleteIfUnlisted(ref: BlobRef, mark: number): Promise<boolean>;
```

Each runs inside `queue.run(ref, …)` like the ledger's existing writes, and `deleteIfUnlisted` goes through the same `remove` helper `delete` does, so the in-memory index stays in step.

**Flushing.** The two mark writes do **not** flush, against the ledger's standing rule that every public write does. A mark is advisory — one a crash loses costs a delay of one grace period and never a lost copy — and flushing one per owed entry per pass would cost a store flush per entry on a node with thousands. What the rule exists for is unchanged: every call that creates or deletes an entry still flushes, because an entry a restart forgets is a copy nobody will ever send. Say exactly that where the exception is made, so it reads as a decision rather than an omission.

**Why `deleteIfUnlisted` must flush.** The pass deletes the entry and then releases the `owed` hold, in that order, because a crash between the two leaves a hold with no entry — storage kept, nothing lost — while the reverse leaves an entry whose drain announces a blob this node no longer holds. That ordering only holds if the delete is durable before the release writes, and `LocalBlobService.releaseOwed` flushes. So the delete flushes.

## The grace-period rule

New file `packages/db-p2p/src/blob/reclaim-marks.ts` — pure, no clock and no store, so it is readable and testable on its own and so the pass and the node factory share one copy of the bounds:

```ts
/** 7 days (docs/blobs.md §Lifetime). */
export const DEFAULT_RECLAIM_GRACE_MS = 7 * 24 * 60 * 60 * 1000;
/** Below this a pass could release on two passes too close together to cover a reference being copied from one row to another. */
export const MIN_RECLAIM_GRACE_MS = 60 * 60 * 1000;

export type MarkDecision = 'mark' | 'keep' | 'release';

/** What to do about a blob a counting pass found listed nowhere. */
export function judgeMark(mark: number | undefined, startedAt: number, graceMs: number): MarkDecision;

/** `NodeOptions.blobs`'s `reclaimGraceMs`, or the default.
 *  @throws RangeError naming the option for a value that is not finite or is below {@link MIN_RECLAIM_GRACE_MS}. */
export function resolveReclaimGraceMs(declared: number | undefined): number;
```

`judgeMark`: no mark, or a mark that lies after `startedAt`, is `'mark'` — the second case is the wall clock having gone back, and restarting the grace period from now is the direction that keeps the blob. `startedAt - mark >= graceMs` is `'release'`. Anything else is `'keep'`.

`resolveReclaimGraceMs` refuses rather than clamping, in the shape of `resolveBlobCacheBudgetBytes` in `packages/db-p2p/src/libp2p-node-base.ts` and for the same reason: a host that mistyped the grace period should be told, not quietly given a node that deletes sooner than it meant.

Record the accepted tradeoff at `judgeMark`, which docs/blobs.md §Lifetime already states under *Accepted limits* and nothing at the site says:

```
// NOTE: accepted tradeoff — the grace period is measured on this host's wall clock, so a clock set
// forward shortens the real time between the two passes. Wall-clock time is the only clock that
// survives a restart, which the mark must; a monotonic clock would reset the period on every restart
// and so never reclaim on a machine that restarts often. Revisit if hosts with unreliable clocks are
// reported.
```

Export `blob/reclaim-marks.js` from `packages/db-p2p/src/index.ts`. **Not** from `src/rn.ts`, which stops at `single-machine-blob-service.js` and carries neither the owed ledger nor the reference check — the reclaim path as a whole is not part of the React Native surface.

## Edge cases & interactions

- **A mark on a record that no longer holds `responsible`** (a crash between a release and its mark-clear, or a record written by a build that had the field and not the rule): `responsibleMarks` does not list it, so no pass can act on it, and the next `holdResponsible` clears it. Inspection.
- **`markUnreferenced` on a record whose hold went mid-pass**: writes nothing, answers `false`. Test.
- **`releaseResponsibleIfMarked` with a mark the record no longer carries**: writes nothing, the hold stands. Test — this is the branch that would otherwise delete a live blob.
- **A pinned blob losing its `responsible` hold**: the record and the pin survive, because `recordAfterResponsibleRelease` removes one hold and `BlobRecordStore` deletes only a record with none. Inherited from the prereq; asserted once in this ticket's record test so that the mark's removal is not mistaken for the record's.
- **`deleteIfUnlisted` racing the drain's own delete** (an entry the drain found fully held while the pass ran): the entry is gone, the read answers `undefined`, the call answers `false`, and the pass leaves the `owed` hold for the drain, which released it with the entry. Inspection of `read`.
- **`addHolders` on an entry carrying a mark**: the mark survives. Test, one assertion inside the ledger test.
- **A re-record with the same scope**: still clears the mark. That is deliberate — an `announce` call for a reference already owed is the writer saying the reference is live — and it is what the explicit four-field construction gives. Inspection.
- **Two `LocalBlobService` instances over one key-value store**, which the pass's restart test builds: each has its own serial queue, so the conditional writes are serialized only per instance. Not a new exposure — `OwedBlobLedger`'s own doc comment already says one instance per store — and a node builds one of each. Inspection.
- **A record the decoder refuses because of a malformed mark**: logged and skipped by `responsibleMarks`, as every other unreadable record is, so one bad record hides one blob from reclaiming rather than failing the pass. Inspection.

## Tests

`packages/db-p2p/test/blob-reclaim-marks.spec.ts`. A real `LocalBlobService` over `MemoryKVStore` and `MemoryPieceStore`, and a real `OwedBlobLedger` over a `MemoryKVStore`, in the shape `packages/db-p2p/test/owed-blob-ledger.spec.ts` and `packages/db-p2p/test/local-blob-service.spec.ts` already build them; references from `buildBlob` as `packages/db-p2p/test/blob-reference-check.spec.ts` makes them.

- **The grace-period rule.** `judgeMark` over a table: no mark gives `mark`; a mark after `startedAt` gives `mark`; exactly `graceMs` old gives `release`; one millisecond short gives `keep`. And `resolveReclaimGraceMs`: `undefined` gives the default, exactly `MIN_RECLAIM_GRACE_MS` gives that value, one millisecond below it throws `RangeError`, `NaN` throws `RangeError`.
- **A mark follows the hold it is about.** `holdResponsible`, `markUnreferenced`, and `responsibleMarks` shows the mark; `holdResponsible` again and the mark is gone; `markUnreferenced` again, then `releaseResponsibleIfMarked` with a different mark answers `false` and `responsibleScope` still answers, while with the mark the record carries it answers `true` and the hold is gone. Then, on a second reference that is pinned as well as held, `releaseResponsibleIfMarked` with its mark takes the hold and the mark and leaves the pin and the record. And `markUnreferenced` on a reference with no `responsible` hold answers `false`.
- **An owed mark follows the entry.** `record`, `markUnlisted`, and `list` shows the mark; `addHolders` keeps it; `record` again and it is gone; `markUnlisted` again, then `deleteIfUnlisted` with a different mark answers `false` and the entry stands, and with its own mark answers `true` and `get` answers `undefined`.

Nothing more. The two fields' decoding is one check each in a validator the record and entry specs already cover, and the flush policy is not a behaviour a test can see without mocking a store this package owns.
