# The crypto backend takes native ECDSA verify

Requested in GitHub #59 (VoteTorrent; `@optimystic/quereus-plugin-crypto` 1.26.0 and 1.27.0). Measured by the reporter on a Pixel 8 emulator under Hermes: `p256.verify` 47 ms in `@noble/curves` against 0.13 ms in OpenSSL (react-native-quick-crypto); `secp256k1.verify` 29 ms against 0.24 ms. Their schema `CHECK` constraints call SQL `verify` on every replicated signed row, about 10 s of JavaScript-thread time per authority device per election, and the app cannot route around it because the call is inside SQL.

## Current state

`CryptoBackend` in `packages/quereus-plugin-crypto/src/crypto.ts` has four optional members (`sha256`, `sha512`, `ed25519Sign`, `ed25519Verify`). `setCryptoBackend` copies the known members into a frozen record (`snapshotBackend`), runs a known-answer check of each against noble (`selfCheckBackend`), and installs the copy on `globalThis` under a `Symbol.for` key. `verify(..., 'p256')` and `verify(..., 'secp256k1')` call `p256.verify` / `secp256k1.verify` with noble's defaults; `sign` passes `{ lowS: true }` on both curves.

## What noble's verify actually does (read from `@noble/curves` 2.0.1, `abstract/weierstrass.js`)

`ecdsa(...)`'s default signature options are `{ prehash: true, lowS: true, format: 'compact' }`, for verify as well as sign. So the semantics a native member must reproduce exactly are:

- **Message is hashed by verify** with SHA-256 (both `p256` and `secp256k1` are built with `sha256`). The SQL `verify` hands noble the caller's data, not a digest — the native member receives the same message bytes and must hash them itself.
- **Signature is 64-byte compact `r || s`** (big-endian, 32 bytes each). Any other length throws (`validateSigLength`) — a DER signature is never accepted.
- **`r` and `s` must each be in `[1, n−1]`** (`Signature` constructor, `validateRS`); otherwise false.
- **High-S is rejected**: `s > n/2` returns false.
- **Public key is SEC 1, 33 bytes with prefix `0x02`/`0x03` or 65 bytes with prefix `0x04`**, and must be on the curve (`pointFromBytes`). Anything else, including the 65-byte "hybrid" prefixes `0x06`/`0x07`, is rejected.

## Divergences from OpenSSL, measured

A prototype over `node:crypto` (OpenSSL 3, Node 24.2.0), wrapping the raw key as SPKI DER and verifying with `dsaEncoding: 'ieee-p1363'`, compared against noble on fixed vectors for both curves:

| vector | noble | naive OpenSSL member | guarded member (below) |
|---|---|---|---|
| valid, compressed key | true | true | true |
| valid, uncompressed key | true | true | true |
| tampered message | false | false | false |
| high-S copy (`s → n − s`) | **false** | **true** | false |
| `r = 0` | false | false | false |
| `r = n` | false | false | false |
| hybrid-prefix key (`0x06`/`0x07`) | **false** | **true** | false |
| DER signature | throws | false | false |

So OpenSSL diverges on two inputs, and both are reachable by anyone who can write a row: flipping `s` to `n − s` turns any honest signature into one OpenSSL accepts and noble refuses, and re-encoding a public key in hybrid form does the same for the key. `verify` runs inside `CHECK` constraints on replicated rows, so a member that does not close both gaps would let phones accept rows every other machine rejects. The **hybrid-key divergence is not in the GitHub issue** (the issue's reference member checks high-S and the scalar range only); it was found during planning and must be covered.

The guarded member that agreed with noble on every vector:

```ts
import { createPublicKey, verify as nodeVerify } from 'node:crypto';

// SPKI DER prefixes for a raw SEC 1 point (id-ecPublicKey + curve OID + BIT STRING header).
const SPKI_PREFIX = {
	p256: { 33: '3039301306072a8648ce3d020106082a8648ce3d030107032200', 65: '3059301306072a8648ce3d020106082a8648ce3d030107034200' },
	secp256k1: { 33: '3036301006072a8648ce3d020106052b8104000a032200', 65: '3056301006072a8648ce3d020106052b8104000a034200' },
};
const ORDER = {
	p256: 0xffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551n,
	secp256k1: 0xfffffffffffffffffffffffffffffffebaaedce6af48a03bbfd25e8cd0364141n,
};

function ecdsaVerify(curve: 'p256' | 'secp256k1') {
	const n = ORDER[curve];
	return (signature: Uint8Array, message: Uint8Array, publicKey: Uint8Array): boolean => {
		if (signature.length !== 64) return false;
		const prefixOk = (publicKey.length === 33 && (publicKey[0] === 0x02 || publicKey[0] === 0x03))
			|| (publicKey.length === 65 && publicKey[0] === 0x04);
		if (!prefixOk) return false;                          // OpenSSL accepts hybrid 0x06/0x07; noble does not
		const r = BigInt('0x' + Buffer.from(signature.subarray(0, 32)).toString('hex'));
		const s = BigInt('0x' + Buffer.from(signature.subarray(32)).toString('hex'));
		if (r === 0n || s === 0n || r >= n || s >= n || s > n / 2n) return false; // OpenSSL accepts high-S
		const prefix = Buffer.from(SPKI_PREFIX[curve][publicKey.length as 33 | 65], 'hex');
		const key = createPublicKey({ key: Buffer.concat([prefix, publicKey]), format: 'der', type: 'spki' });
		return nodeVerify('sha256', message, { key, dsaEncoding: 'ieee-p1363' }, signature);
	};
}
```

This is the basis for the spec's test backend and for the README adapter example.

## Design (settled)

**Two new optional members** on `CryptoBackend`, documented the way `ed25519Verify` is:

```ts
/** 64-byte compact r||s signature, message (hashed with SHA-256 by the member), 33- or 65-byte SEC 1 public key.
 *  Must match @noble/curves' default verify exactly: reject high-S, r or s outside [1, n−1], any key prefix other than
 *  0x02/0x03 (33 bytes) or 0x04 (65 bytes). Returns false, or throws, for an invalid signature or key. */
p256Verify?(signature: Uint8Array, message: Uint8Array, publicKey: Uint8Array): boolean;
secp256k1Verify?(signature: Uint8Array, message: Uint8Array, publicKey: Uint8Array): boolean;
```

**No native ECDSA signing members.** OpenSSL's ECDSA uses a random nonce unless asked for RFC 6979, so a native sign could not pass a byte-identical self-check against noble's deterministic signature; the reporter does not need it. Say so in the README in one sentence so nobody adds it naively.

**Dispatch** exactly like `ed25519Verify`: a small helper per curve (or one helper taking the member name and the noble curve) that reads `currentBackend()` on every call and falls back to noble. `verify`'s existing `try/catch` already turns a member's throw into `false`.

**Pin noble's options explicitly** on the two ECDSA noble verify calls — `{ prehash: true, lowS: true, format: 'compact' }` — rather than relying on the defaults. They equal today's defaults, so nothing changes; it makes the semantics the native member is checked against visible at the call site and immune to a noble default change. Use the same options object in the self-check's reference calls.

**Self-check per member** (`checkEcdsaVerify(member, curve, native)`, one function for both curves), every input passed as an `offsetView`, built from `CHECK_MESSAGE` and `CHECK_SEED` (the 1..32 seed is a valid scalar on both curves) with noble `sign(..., { lowS: true })` (deterministic, RFC 6979). In order:

- **Accept** the valid signature with the compressed key → must return exactly `true`.
- **Accept** the valid signature with the uncompressed key → `true`.
- **Reject** the valid signature over a tampered message (first byte flipped).
- **Reject** the high-S copy: same `r`, `s' = n − s`.
- **Reject** `r = 0` (32 zero bytes, then `s`).
- **Reject** `r = n` (`n` as 32 big-endian bytes, then `s`).
- **Reject** the uncompressed key re-prefixed as hybrid: first byte `0x06 | (y & 1)` (i.e. `0x06` when the last byte is even, `0x07` when odd), with the valid signature.

"Reject" means false or a throw (`rejectsOrThrows`); "accept" goes through `runCheck`, as `checkEd25519Verify` does. Each refusal names the member and the vector in its message (e.g. `p256Verify accepted a high-S signature, which @noble/curves rejects`), so an adapter author knows which guard is missing.

Build the vectors from what the module already imports: the curve object's `Point.Fn.ORDER` for `n`, `Signature.fromBytes(...)`'s `r`/`s` or byte slicing, `hexToBytes` / `bytesToHex` / `concatBytes`. The `/plugin` bundle tree-shakes the setter and its self-check (see the comment on `sameBytes`): **do not add an import used only by the self-check**; if one turns out to be necessary, confirm `yarn build` and `yarn check:rn` from the root still pass. Compute the vectors inside the check function (it runs once per `setCryptoBackend`), not at module load, so a process that never installs a backend pays nothing.

**`snapshotBackend`** copies and binds the two new members like the others.

## Edge cases & interactions

- **High-S and hybrid-key acceptance** are the two divergences an OpenSSL adapter has by default — covered by self-check vectors and by the refusal test (below). Verified by test.
- **`r` / `s` out of range** — OpenSSL already rejects `r = 0` and `r = n`; the vectors guard other native libraries. By inspection of the vector list.
- **DER signature, wrong-length signature, point not on the curve, point at infinity** — noble rejects all; OpenSSL rejects all (DER measured above). Not a self-check vector: the contract text in the interface doc and README covers them, as the existing "a member handed a malformed key or signature must throw or return false; that is not checked" line does for Ed25519. By inspection.
- **Message hashing** — the member hashes; the plugin never passes a digest. A member that skips hashing fails the "accept valid" vector. Covered by the self-check.
- **Offset views** — every vector is an `offsetView`, so an adapter that reads `data.buffer` fails. By the self-check.
- **Throw inside a member at call time** — `verify` returns `false`, the same as a noble throw. By inspection (existing catch).
- **Backend set after plugin registration, and the `/plugin` bundle** — dispatch reads the `globalThis` slot per call, as the existing members do. The existing "byte-identical through the SQL functions" test registers the plugin from `dist/plugin.js` before setting the backend through `dist/index.js`; extend its `evaluate` to cover both ECDSA curves so this is checked for the new members too.
- **A backend from an older copy of the package** — `snapshotBackend` only copies members this copy knows how to check, so an older copy installing a backend with ECDSA members ignores them, and a newer copy reading a slot an older copy wrote finds them `undefined` and falls back to noble. By inspection; no change needed.
- **`sign` for ECDSA** — unchanged, stays on noble. By inspection.

## Tests (in `test/crypto-backend.spec.ts`; no new spec file)

- Extend `nodeBackend()` with `p256Verify` and `secp256k1Verify` built on the guarded member above, counting calls like the others, and extend `evaluate()` to sign with each ECDSA curve through SQL `sign` and verify the valid signature, a tampered message, and the high-S copy through SQL `verify`. The existing first test then asserts byte-identical results with and without the backend and that every member was called.
- Extend the refusal test with two adapter mistakes that are each real and each caught by a different vector: a **naive** `p256Verify` (the guarded member without the `r`/`s` checks) must make `setCryptoBackend` throw naming `p256Verify` (high-S vector); a `secp256k1Verify` with the scalar checks but **without the prefix check** must throw naming `secp256k1Verify` (hybrid vector). The previously installed backend must still be the one in use afterwards, as the existing test already checks.
- No test per vector beyond that, and no test of the noble option pinning (it is a constant).
