# The persisted schema's `indexes` list is not durable across nodes

Every Optimystic table's shape is persisted as a `StoredTableSchema` in one plugin-global
collection, `tree://optimystic/schema`, keyed by table name. Its `indexes` array is the
authority for two things that matter downstream:

- a vtab's `IndexManager` is constructed from it, so it decides which indexes that node's
  **writes maintain**;
- `hydrateCatalog` rebuilds Quereus's catalog from it, so on a hydrating node it also decides
  which indexes the **planner offers**.

Two sites let that array be lost or overwritten with a stale value. Both are silent.

## Site A — an unreadable catalog is treated as an empty one, and then written over

`OptimysticVirtualTable.doInitialize` (`optimystic-module.ts`, roughly lines 345–395) builds
the schema it will persist like this:

```ts
const candidateStored = this.schemaManager.tableSchemaToStored(this.tableSchema);
const mergedCandidate: StoredTableSchema =
  candidateStored.indexes.length === 0 && persistedSchema
    ? { ...candidateStored, indexes: persistedSchema.indexes }
    : candidateStored;
```

A bare `CREATE TABLE` never carries its `CREATE INDEX` siblings, so `candidateStored.indexes`
is empty and the merge exists precisely to preserve what is already persisted. But the merge
is gated on `persistedSchema` being **truthy**. When the read comes back empty the node
proceeds to the `else` branch and **writes `indexes: []` over the catalog**, destroying the
index list for every later reader — including hydrating nodes, whose planner then never even
learns the index exists.

`SchemaManager.getSchema` cannot currently distinguish "no schema has ever been persisted"
from "I could not read the catalog"; its own comment says so, pointing at the
`repo-reports-unavailable-vs-absent` work. So an unreachable or lagging catalog read on one
node is enough to trigger the clobber. This is the same absent-vs-unavailable discipline the
block layer already enforces (`Collection.open` vs `createOrOpen`, `BlockUnavailableError`,
`advanceContext` refusing to lower a revision) — the schema-catalog path is the hole in it.

Note the failure is asymmetric and therefore invisible from either side alone: the node that
clobbered has an index-free schema and simply full-scans (its own queries look fine), while a
node that read the catalog earlier still has the index and keeps seeking through a tree the
clobbering node never maintains.

## Site B — the per-instance schema cache never invalidates, and write-back is whole-record

`SchemaManager.getSchema` (`schema-manager.ts:198`) returns from `this.schemaCache` whenever
the table name is present, with no revision check and no invalidation path. The first answer
a `SchemaManager` instance ever produced for a table is the answer it produces forever.

Two consequences:

- **Stale reads.** `doInitialize` and `addIndex` both consult `getSchema`, so both can be
  reasoning about a schema that another node has since changed. (Measured: on the two-node
  mock mesh, node B's `addIndex` read returned a schema *without* an index node A had already
  persisted, even though a direct read of the catalog collection at the same moment showed
  it. The cache, not the network, was the stale layer.)
- **Lost updates.** `addIndex` builds `updatedSchema = { ...storedSchema, indexes:
  [...storedSchema.indexes, newIndex] }` from that possibly-stale read and then
  `storeStoredSchema`s the **whole record**. An index a sibling added in between is simply
  dropped from the persisted list.

The broader design answer to catalog staleness is already parked in
`backlog/more-design/6.5-schema-versioning` (schema versioning via Quereus's Lens system);
that ticket now carries this instance as evidence. **This ticket is the narrow correctness
fix, not that design** — do not wait on it and do not build versioning here.

## Why this matters now

`fix/secondary-index-update-never-reaches-the-sibling` reported a two-node deployment where a
row replicates but every index-driven lookup for it returns empty forever, with no error. The
investigation eliminated the consensus/commit path and narrowed the silent failure to "the
writing node's maintained-index set did not contain the index". Both sites above are ways the
persisted `indexes` list — the ultimate source of that set — goes missing on one node and not
another. The vtab-side guard is `implement/index-maintenance-must-track-the-declared-index-set`;
this ticket closes the supply side.

Reproduction status: **static** for both sites — read from the code and from the measured
cache-staleness observation above, not from a failing test. Neither was driven to a failure
in this repo; the eight two-node shapes tried on the in-process mock mesh all converged.

## What to build

**Site A — never write a schema over a catalog you could not read.** Separate "authoritatively
absent" from "could not read" on the schema-catalog path, and make the merge/write refuse to
proceed on the second. Options, in preference order:

1. Have `SchemaManager.getSchema` surface unreadability distinctly (throw, or return a
   discriminated result) rather than collapsing to `undefined`, mirroring `Collection.open`'s
   contract. Then `doInitialize` fails loudly instead of clobbering.
2. If the storage layer cannot yet report unavailability (`repo-reports-unavailable-vs-absent`
   is not landed), make the write **non-destructive for `indexes`**: never persist an
   `indexes: []` that would shrink a previously-known list, and log when the merge had no
   persisted side to consult.

Whichever is chosen, state the contract at the call site.

**Site B — bound the cache and stop whole-record write-back from losing indexes.**

- Give `schemaCache` an invalidation path and use it: at minimum, `addIndex` and any other
  mutating path must re-read from the catalog rather than serve a cached copy, and a write
  must refresh the entry it just wrote. A blunt "reads that precede a write bypass the cache"
  rule is acceptable and preferable to a subtle one.
- Make `addIndex`'s write-back a **merge on `indexes`** (union by index name, with the
  existing `unique`/`predicate` upgrade rules) rather than an overwrite of whatever the
  stale read held.

## Done means

- A node whose schema-catalog read fails or comes back unreadable does not persist a schema
  that drops the table's indexes — it either fails loudly or leaves the persisted index list
  intact.
- Adding an index no longer drops an index a concurrent writer added, and a mutating path
  never reads the schema through a cache entry it cannot know is current.
- Tests pass and the build is clean.
