# Why

Once a commit's answer carries a durability class, the coordinating machine momentarily knows something valuable and then throws it away: *which* members of the group had not confirmed holding the new revision at the moment it answered the writer. Today nothing records that. Two mechanisms partially cover the gap and neither is enough:

- The cluster coordinator schedules a **commit retry** to members that did not respond. It lives in memory, is persisted only when a transaction state store is injected, and nothing in production injects one — the reference peer never does. A restart loses it.
- The **rebalance monitor's growth arm** pushes a block to peers that have newly become co-responsible. It reacts to a topology change, not to a known shortfall, and its memory of what it has pushed is process-local.

So a block written while a member was unreachable stays one copy short with nobody tracking it, and a restart erases even the in-memory attempt. This ticket writes the shortfall down durably. It does not yet send anything — the drain is the next ticket.

# The ledger

```ts
/** One block this node acknowledged below full replication, and who is still missing it. */
export type UnderReplicatedEntry = {
	readonly blockId: BlockId;
	/** The highest under-replicated revision of this block. A later revision SUPERSEDES an earlier
	 *  one: pushing the newer materialization satisfies the older, so entries are keyed by block
	 *  alone and this field is overwritten, never appended to. */
	readonly rev: number;
	readonly actionId: ActionId;
	/** The class the commit was acknowledged at — `local`, `unrouted`, or `majority`. */
	readonly quorum: DurabilityQuorum;
	/** Cohort members that had not confirmed holding `rev`, by peer-id string.
	 *  EMPTY when the cohort could not be named (`local`, `unrouted`): there was nobody to name,
	 *  and the drain must re-resolve the cohort at drain time instead. An empty array therefore
	 *  means "unknown", not "nobody". */
	readonly missingPeerIds: readonly string[];
	/** When this shortfall was first recorded, in milliseconds since the epoch. */
	readonly recordedAt: number;
	/** Consecutive unsuccessful drain rounds — the give-up counter the drain owns. */
	readonly attempts: number;
};

export interface IUnderReplicationLedger {
	/** Record (or overwrite, at a higher revision) a block's shortfall. */
	record(entry: UnderReplicatedEntry): Promise<void>;
	get(blockId: BlockId): Promise<UnderReplicatedEntry | undefined>;
	/** Every outstanding entry. The drain pages nothing today: the set is bounded by the node's
	 *  own owned-block count and shrinks as copies land. */
	list(): Promise<UnderReplicatedEntry[]>;
	/** Remove `peerIds` from an entry's missing set, deleting the entry when it empties.
	 *  Returns the remaining entry, or `undefined` when it was deleted. */
	satisfy(blockId: BlockId, peerIds: readonly string[]): Promise<UnderReplicatedEntry | undefined>;
	/** Bump the give-up counter after an unsuccessful drain round. */
	noteAttempt(blockId: BlockId): Promise<void>;
	delete(blockId: BlockId): Promise<void>;
}
```

**Keyed by block id, not by revision.** A block written five times while a member was away produces one entry, at the highest revision. The block push carries the materialized block at its current revision, so satisfying the newest satisfies all of them. This is what bounds the ledger: it can never hold more entries than the node holds blocks.

`KvUnderReplicationLedger` implements it over the existing `IKVStore`, under a fixed prefix — `under-replicated/<blockId>` — with the entry as JSON. That mirrors `PersistentTransactionStateStore`, which is the existing precedent for durable node-local state in this codebase.

## Where the key-value store comes from

Nothing wires an `IKVStore` into a node today, which is exactly why the transaction state store has never been persisted in production. Fix that here:

- `NodeOptions` gains `kvStore?: IKVStore | (() => IKVStore)`, alongside the existing `storage?: RawStorageProvider` and following the same instance-or-factory shape.
- Absent, the node falls back to `MemoryKVStore` **and logs a warning naming what is lost** — the ledger then works but does not survive a restart. A silent memory fallback would look like the feature works and fail the one case the feature exists for.
- `packages/reference-peer/src/cli.ts` constructs `FileKVStore` when `--storage file` is given, over the same base path it hands `FileRawStorage`, and `MemoryKVStore` otherwise.

**Sharing that base path is safe and was checked, not assumed.** `FileKVStore` turns a slash-separated key into nested directories under its base path, so `under-replicated/<blockId>` becomes a directory named `under-replicated` containing one JSON file per block. `FileRawStorage.listBlockIds` enumerates direct child directories but yields only those containing a `meta.json`, so the `under-replicated` directory is never mistaken for a block. `FileKVStore`'s own note states the condition under which sharing would break — a key's first segment equal to a block id — and a fixed literal prefix cannot trip it. Two consequences to keep in mind: the ledger's bytes are counted by `FileRawStorage.approximateBytesUsed` (negligible, and the entries are tiny), and if any future ledger key ever begins with a caller-supplied segment, the two stores need separate base paths.

# Recording

`CoordinatorRepo` takes an optional `underReplicationLedger` through its components object, like its other optional capabilities. Absent, nothing is recorded and behaviour is exactly as today.

At every success exit of `CoordinatorRepo.commit` whose class is below `full`, record one entry per block in the request:

- `majority` → `missingPeerIds` is the cohort minus the confirmed holders, which the prerequisite ticket already makes `CohortDurability` carry by name.
- `local` and `unrouted` → `missingPeerIds` is empty, meaning "unknown"; the drain re-resolves.
- `full` → record nothing, and **delete** any existing entry for those blocks: the block has just reached full replication at a newer revision, so an older shortfall is settled.

Recording must not be able to fail the commit. Wrap it, log a failure, and return the answer regardless — the commit is already durable by the time this runs, and a ledger write that throws must not turn an acknowledged write into a reported failure. This asymmetry is deliberate and should be stated at the call site.

Recording happens **after** the durability gate has admitted the commit, so a refused commit never lands in the ledger.

# Edge cases & interactions

- **Restart.** The point of the ticket. An entry written before a restart must be readable after one. With `MemoryKVStore` it will not be — that is why the fallback warns.
- **A later commit at a higher revision.** Overwrites the entry, including its missing set and resetting `attempts` to zero: a fresh shortfall deserves a fresh give-up budget.
- **A later commit that reaches `full`.** Deletes the entry. A block that is now everywhere owes nobody a push.
- **A multi-block commit.** One entry per block, all at the same revision and action id, all sharing the cohort answer — the commit ran one consensus round on one cohort. Where a commit spans cohorts (rare; see `backlog/debt-no-mesh-fixture-forces-two-coordinator-batches`), each block takes its own cohort's report.
- **A torn commit.** Blocks named in the result's `torn` were cancelled and hold nothing. They must **not** be recorded: there is nothing to push, and an entry for them would have the drain repeatedly read a block that is not there. Filter them out explicitly and say why in a comment.
- **Concurrent commits to the same block.** Two coordinators on one node can record for the same block concurrently. `IKVStore` offers no compare-and-set, so last-write-wins. That is acceptable because entries are keyed by block and the loser is a lower revision whose push the winner's push also satisfies — but write the record path so it reads, compares revisions, and skips a write that would LOWER the recorded revision, so a slow older commit cannot clobber a newer one.
- **A block this node does not hold.** The tolerated-divergence arm answers success without this node holding anything. It must not record an entry naming itself as a source — the drain would find no local bytes. Record it only when this node is a confirmed holder; otherwise the remote majority already holds it and this node has nothing to offer.
- **Unbounded growth.** Bounded by the owned-block count by construction, but a node whose partner never returns accumulates one entry per block it writes. The drain's give-up counter (next ticket) is what retires them; this ticket must not add a second, conflicting eviction rule. Do add a hard `maxEntries` cap with oldest-first eviction as a backstop, defaulted generously, and log when it evicts.
- **The transaction state store.** Once a node has a key-value store, `PersistentTransactionStateStore` can finally be wired in production. Do **not** do that here — it changes commit-retry recovery behaviour and belongs with `backlog/feat-long-lived-pend-completes-as-members-appear`. Note in the node wiring that the store is now available.

# Tests

- `KvUnderReplicationLedger` over `MemoryKVStore`: record, read back, `satisfy` removing one of two missing peers leaves the entry, removing the last deletes it, `noteAttempt` increments, `list` returns what was recorded.
- Recording at a higher revision overwrites and resets `attempts`; recording at a lower revision is skipped.
- A `full` commit deletes an existing entry for the same block.
- A coordinator whose commit is acknowledged at `majority` with one absent member records exactly one entry per block, naming that member.
- A commit acknowledged `local` records entries with an empty missing set.
- A torn commit records nothing for the blocks named in `torn`.
- A ledger whose `record` throws does not fail the commit: the commit still returns its success, and the failure is logged.
- **Restart survival**, at the ledger level rather than the node level so it stays a unit test: write entries through a `FileKVStore` over a temporary directory, construct a second `KvUnderReplicationLedger` over a fresh `FileKVStore` at the same path, and read the entries back. The node-level restart case is asserted in the next ticket, where a drain exists to observe.
