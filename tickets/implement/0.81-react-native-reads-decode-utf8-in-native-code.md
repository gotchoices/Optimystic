# React Native reads decode UTF-8 in native code

GitHub #51 (kjeib). The second of two tickets: `storage-drivers-can-carry-values-as-text` makes the shared storage layer generic in how a value is held in memory (`RawStoreDriver<V>`, `ValueCodec<V>`, `textValueCodec`). This ticket puts the React Native LevelDB backend on text.

## Problem

Today every block, transform, metadata, proof and revision-action-id read on React Native goes `rn-opener.ts` `get` → `native.getBuf(...)` → `new Uint8Array(...)` → `decodeJson` / `decodeActionId` in `raw-store-codec.ts` → `TextDecoder.decode` (the host's JavaScript polyfill, since Hermes has none) → `JSON.parse`. Measured by the reporter (Galaxy S7, Hermes debug build, optimystic 1.20.1, one offline-mode log-entry save with 2 nodes): about 740 ms of the 2.66 s of fully busy JS thread before the first `pendMany` is this path, the largest single item; 2.4–2.8 s of self time over the whole 45 s window.

Reading the composition shows it is worse than one decode per read. The node puts its read cache in front of `LevelDBRawStorage` through `withReadCache` (`resolveStorage` in `packages/db-p2p/src/libp2p-node-base.ts`), which builds a `CachedRawStorage`: a second `KvRawStorage` over a `CachedStoreDriver` over a `RawStorageDriverAdapter` over the LevelDB storage. So a cold read decodes the bytes into an object (polyfill), the adapter re-encodes it to bytes, and the outer kernel decodes them again (polyfill). Every cache hit decodes once more (polyfill), and so does every hit on a value written this session, since the cache and the write group's overlay both hold bytes.

## Research answers

**1. `getStr` decodes UTF-8 as `TextDecoder` does, for every value this backend stores.** Read in `rn-leveldb` 3.11.1's `cpp/react-native-leveldb.cpp`. `leveldbGetStr` does `db->Get` into a `std::string`, then `jsi::String::createFromUtf8(runtime, value)`. `leveldbIteratorValueStr` does the same over `iterator->value().ToString()`. The `std::string` overload of `createFromUtf8` passes `utf8.data()` with `utf8.length()` (`react-native/ReactCommon/jsi/jsi/jsi.h`), so an embedded NUL is not a terminator and nothing is truncated. JSI defines the result for valid UTF-8 and leaves it undefined for invalid bytes. Every value on disk is `TextEncoder` output (`encodeJson` and `encodeActionId`; JSON text and action ids), which is always valid UTF-8: `TextEncoder` writes U+FFFD for a lone surrogate, and `JSON.stringify` escapes lone surrogates anyway. Valid UTF-8 has exactly one decoding, so any conforming decoder, Hermes's included, yields the same string as `TextDecoder` for BMP and astral characters alike. **One difference:** `TextDecoder` by default strips a leading byte-order mark (bytes EF BB BF) and `getStr` keeps it. JSON text never starts with one. An action id can, since it is chosen by whoever originates a write; the native path then returns the id as written, where today the read drops the mark. That is the more faithful answer, and it is uniform, because the overlay and the cache hold the original string too. Existing stores therefore read correctly with no migration. *What is static:* Hermes's own implementation of `createStringFromUtf8` was not available locally; the conclusion rests on the JSI contract plus the input always being valid. The device profile requested below confirms it.

**2. Where text enters the interface: a type parameter on the driver**, settled in `storage-drivers-can-carry-values-as-text` (alternatives and why each was rejected are recorded there). In short: `RawStoreDriver<V>`, `KvRawStorage<V>` with a `ValueCodec<V>`, bytes the default everywhere, and no backend other than this one changes. The clone invariant stays structural: `JSON.parse` builds a fresh object per read, and strings are immutable.

**3. The write-through cache holds the string.** `LevelDBRawStorage` builds its own `CachedStoreDriver<string>` directly over its write-group driver, so a cache hit is the cached string plus `JSON.parse`, and the cache charges `residentBytes`. Because the storage then reports `readCached`, `withReadCache` (node seam and Quereus plugin alike) passes it through unchanged, which also removes the adapter's double codec pass. Not wrapping it here and leaving the node to do it is not an option: the node's cache goes through the bytes-only `RawStorageDriverAdapter`, which would bring back two JavaScript decodes per cold read. So there is no "no cache" option on this storage.

**4. The journal never serves a read.** The handle cannot sync (`RNLevelDBAdapter.canSync = false`, pending `react-native-storage-syncs-once-rn-leveldb-can`), so `JournalBatchBackend` applies every group at once and appends nothing. A read is served from one of three places: the write group's overlay (values written this process and not yet durable, held as text after the prereq), the read cache (text), or LevelDB through `LevelDBJournalStore.get` / `rangeRevisions`, which this ticket moves onto `getStr` / `valueStr`. A journal record is read only by recovery at open (`readJournal`), as bytes through `decodeJournalRecord`. Once the binding can sync, recovery will run `TextDecoder` on each record's `StoreKey` JSON, at open only. That is acceptable and needs a note in the README, not a change.

**5. Writes: out of scope.** Writes keep `TextEncoder`, which Hermes provides natively, and the bytes land on disk exactly as today (`storage-drivers-can-carry-values-as-text` § Writes stay bytes on disk explains why strings are not passed to `put`). Revisit only if `TextEncoder.encode` shows in a device profile.

**6. Iterators.** `rangeRevisions`, whose values are action ids, reads values with `valueStr()`. Key-only scans (`listPendingActionIds`, `listBlockIds`, the KV store's `list`) and `approximateBytesUsed` (byte lengths) stay on bytes. Keys must: a key is a tag byte, a binary length and the id bytes, so `keyStr()` would hand JSI invalid UTF-8.

## Design

- **`RNLevelDBNative`** gains `getStr(key: ArrayBuffer | string): string | null`, and **`RNLevelDBIteratorNative`** gains `valueStr(): string`. Both have been on `rn-leveldb`'s `LevelDB` and its iterator since well before 3.11.
- **`LevelDBLike`** gains `getText(key: Uint8Array): Promise<string | undefined>` and a text-valued scan: `LevelDBIteratorLike<V = Uint8Array>`, with `textIterator(options): LevelDBIteratorLike<string>` beside `iterator`. Make `drain` generic. `RNLevelDBAdapter` implements them over `getStr` and `valueStr`; the iterator adapter shares its positioning and bound logic between the two value kinds rather than copying it. The test adapter (`test/classic-level-driver.ts`) and the upgrade-check adapter (`packages/upgrade-check/writer/classic-level.mjs`, with its `.d.mts`) implement them with `classic-level`'s per-operation `valueEncoding: 'utf8'`. So both suites exercise the text read path over Node's native decoder. That is also how `packages/upgrade-check` proves that data earlier releases wrote reads unchanged through the new path. Any wrapper of a `LevelDBLike` in the tests (`spyBatchWrites` in `test/leveldb-storage.spec.ts`) forwards both.
- **`LevelDBJournalStore implements JournalStore<string>`**: `get` reads with `getText`; `rangeRevisions` drains `textIterator`. Writes, the journal, the listings and the byte estimate are unchanged.
- **`LevelDBRawStorage extends KvRawStorage<string>`**, composed as `KvRawStorage<string>(CachedStoreDriver<string>(WriteGroupDriver<string>(JournalBatchBackend<string>(LevelDBJournalStore(db)), options, textValueCodec), pool, label, textValueCodec), textValueCodec)` — every layer that holds values takes the codec, and leaving it off the cache or the write-group driver does not compile (as landed by `storage-drivers-can-carry-values-as-text`). Its options gain `readCachePool?: SharedCachePool` and `readCacheLabel?: string` (default pool `defaultCachePool`). `close()` reaches the cache's `close`, which releases the pool registration and closes the write-group driver (it flushes what is held). Check that ordering holds through `CachedStoreDriver.close`. The public constructor `new LevelDBRawStorage(db, options?)` is unchanged. Re-declare `readCached: true` the way the other always-present members are declared (`declare`, not a field; see the note on `CachedRawStorage.readCached`).
- **`LevelDBKVStore`** (its values are already strings at its interface): read through `getText`, and hold strings in its `WriteGroup<string, string>` overlay, encoding with `TextEncoder` in `commit`, so neither `get` path constructs a `TextDecoder`. Its module-level `textDecoder` goes away.
- **`keys.ts`** keeps its JavaScript decode of block and action ids out of keys. Add a tripwire `NOTE:` at `actionIdFromKey`: listings decode key suffixes with `TextDecoder` (the polyfill on React Native); ids are short, mostly base64url ASCII; if that shows in a device profile, decode an all-ASCII suffix with `String.fromCharCode` and fall back to `TextDecoder` otherwise.

## Edge cases & interactions

- **Existing stores read identically, non-ASCII included.** One new test in `test/leveldb-storage.spec.ts`. Write raw values straight into the handle with the bytes the old path stores (`TextEncoder` of `JSON.stringify(v)`, and of an action id): metadata, a revision action id, a pending and a committed transform, a materialized block and a proof, whose strings include BMP non-ASCII (`é`, `中`) and an astral character (`😀`). Then read them through a fresh `LevelDBRawStorage` and assert deep equality with `v`. This pins the codec plumbing over `classic-level`; Hermes's decoder is covered by the device profile below.
- **No storage value read on this backend constructs or calls a `TextDecoder`.** One test, the whole point of the ticket. Save values through `LevelDBRawStorage`, `close()` it (this flushes and drops the cache), and open a second one over the same handle so reads are cold. Wrap `TextDecoder.prototype.decode` with a counter (the prototype, not the global, because the codec memoizes its instance), then read every value kind back (`getMetadata`, `getRevision`, `listRevisions`, `getPendingTransaction`, `getTransaction`, `getBlockProof`, `getMaterializedBlock`) twice: once cold, once as a cache hit. Assert zero calls, and restore the prototype in `finally`. Leave out the listings that decode keys (`listPendingTransactions`, `listBlockIds`).
- **A second `LevelDBRawStorage` over the same handle while the first is open** is now refused by the shared pool's store-identity claim (`SharedCachePool.registerStore`). That is correct, not a regression: two write groups over one store already broke Invariant 1 (every write funnels through one `IRawStorage`) in `packages/db-p2p/docs/storage.md`. Say so in the README. Verified by inspection.
- **The node and the Quereus plugin pass the storage through** (`withReadCache` sees `readCached`), so there is one cache and no adapter. Verified by inspection. The node never disposes a storage it was handed, so the host's existing `storage.close()` (README order: storage, then KV store, then handle) is what releases the cache.
- **The conformance suite** (`rawStorageConformance`, which `test/leveldb-storage.spec.ts` already runs over `LevelDBRawStorage`) passes over the text composition unchanged, at both `canSync` values the spec opens.
- **`packages/upgrade-check`** passes: every recorded `leveldb.json` fixture reads through the text path.
- **A value whose bytes are not valid UTF-8** (disk corruption): JSI leaves the string undefined where `TextDecoder` would substitute U+FFFD; `JSON.parse` fails on both or yields a value no check accepts. Accepted, not handled.
- **`yarn check:rn`** bundles and compiles the React Native entry under Hermes.
- **The `TextDecoder` polyfill stays required on React Native.** `multiformats` and `cborg` construct it at load, and storage still uses it for key decoding in listings and for journal recovery once the binding can sync. Update the `TextDecoder` row of the polyfill table in `packages/db-p2p/readme.md` and the React Native section of `packages/db-p2p-storage-rn/README.md` to say exactly that: stored values on the LevelDB backend are decoded in native code; the polyfill is still required.
