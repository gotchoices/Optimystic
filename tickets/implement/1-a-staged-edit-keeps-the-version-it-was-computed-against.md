# A staged edit keeps the version it was computed against

This is the first of three tickets split from `bug-a-pended-transform-does-not-carry-its-base` (the overall plan is recorded in that ticket, now `2-bug-a-pended-transform-does-not-carry-its-base` in this folder). It is the arm that needs **no wire or storage format change**, and it goes first because the other two are worthless without it: storage will start refusing to apply an edit to any version other than the one the writer declares, and that only protects anyone if the declared version is the one the edits were really computed on. Today it is not always.

## What is wrong, on the writer

A collection handle stages an edit as a list of operations (splice this array at this index). Nothing in that list says which version of the block the index was computed against. The only link is a copy of the block taken when the edit was staged (`Tracker.update` pins `probeBase`), and that copy is **replaced** whenever the handle's read cache reports a new generation for the block (the re-pin branch in `Tracker.update`, and the fallback to the live cache in `Tracker.peekMaterialized`). The commit then declares the replaced copy's version as the base. Two ways the base moves under staged edits inside one transaction, neither of which the log-driven refresh notices because the log did not move:

1. **A machine answers with an older copy than the handle's floor allows** (the case ticket `refreshed-collection-caches-a-block-older-than-its-log-entry` left open). The read cache hands the older copy through without keeping it (`CacheSource.handThrough`, the `unkept` map). An edit is staged against it. Storage catches up; the next read of the block returns the newer copy and is kept; the pin is replaced by it. The commit declares the newer version with edits computed on the older one. The storage-side guard sees exactly the version it holds and passes. Every node computes the same wrong content. Seen in db-core against the in-memory transactor: a one-leaf tree holding key 5, a rival inserts key 1 while the reader is served the old leaf, the reader stages an insert of key 9 computed as position 1, storage catches up, the reader reads the leaf again, syncs, and the committed leaf reads `1, 9, 5`.
2. **Two concurrent reads of one block through one handle, where the older answer arrives second.** `CacheSource.stillWanted` drops the late older answer but still returns it to its reader. That reader computes an edit on content the cache never described; `Tracker.update` pins whatever the cache holds (the newer copy); the commit declares the newer version. Same fork, no lagging machine required.

In both, the declared base is *higher* than the version the edits were computed on, which is the one direction the storage guard cannot catch: a member holding the declared version applies the edits and agrees with every other member.

## The invariants to establish

Three, each at one site.

**Invariant A (read cache): what a read returns for a block is what the cache then describes for it.** `CacheSource.peek` and `CacheSource.getCachedRevision` must describe the content the most recent `tryGet` of that id returned. Two paths break it today and are the fix: an overtaken late answer (`stillWanted` false while the cache holds newer content) returns the *held* content to its reader instead of the dropped older answer, and a handed-through answer for an id the cache already holds (`handThrough`'s early return) returns the *held* content. "Of two answers the higher revision is the truer" already justifies dropping the older one; it equally justifies not handing it to anyone. The read dependency recorded is the revision actually returned. After this, `getCachedRevision(id)` immediately after a `tryGet(id)` is the revision of the content the caller holds, on every path: cached, unkept, or evicted-since (the `revisions` entry that outlives an LRU eviction is precisely the revision of the content last served for the id, which is what makes rev-only pins below sound).

**Invariant B (tracker): the base of a block's staged updates is fixed when the first update is staged and never replaced while updates remain staged.** `PinnedBase.rev` is taken from the cache's revision for the id at the first `update` and is the number the pend will carry (next ticket). Later generation changes for that id fall into two cases: same revision (a re-load of an evicted id, a refresh that re-read the same content) refreshes the block clone and generation, since same revision means same committed content; different revision, or the cache no longer describing the id at that revision, means the base has **moved**. A moved base is recorded (a `movedBases` set on the tracker, or a flag on the pin) and never repaired by re-pinning or by falling back to the live cache. `peekMaterialized` returns nothing for a moved id (no digest can be declared), but the pinned revision stays reportable. A pin may be **rev-only** (no block clone) when the block was evicted between its read and its first update, which closes the "read-far-then-update" gap for the base while leaving the digest undeclared, as today. Expose two readers the next ticket needs: `stagedBaseRevs(blockIds)` returning the pinned revision for every id that has update operations and neither an insert nor a delete, and `movedBases()`.

**Invariant C (collection): a pending action is never pended over a moved base; it is re-staged first.** The collection already has the machinery (`replayActions` resets the tracker and re-runs `pending`; `mustReplay` decides when a refresh does it). Two additions. First, `mustReplay` gains a third reason: any staged block's base has moved. Second, a moved base is detected without a read, before each pend attempt: a `Collection` method (suggested name `restageIfBasesMoved`) that re-validates every pin against the cache and re-stages when any moved. Re-validation: for a pin whose id the cache retains, compare `getCachedRevision(id)` with `pin.rev`; for an id the cache does not retain (handed through unkept, or evicted), one `tryGet(id)` through the tracker's source, then compare. Call it in `Collection.syncAttempts` before every attempt (first and retries: after a refused attempt the refresh may have moved nothing and so replayed nothing, and no read happens between the refusal and the re-pend), and in `TransactionCoordinator` before `pendPhase` for each participating collection. `Atomic.commit` adopts pins into the parent (`BasePins.adopt` overwrites); adopting a pin for an id the parent already pins at a different revision is a moved base, not an overwrite.

## Why this is enough, and what it deliberately leaves

- The declared base becomes a fact about the staged operations rather than about the cache. The next ticket puts that number on the pend and in storage; the storage guard then refuses any base other than the declared one, and a declared base is never higher than the real one.
- A moved base detected only by re-validation before the pend (not by a read) is served in the meantime as the pin's block plus operations when the pin has a block (a transaction-consistent snapshot), and as live content plus operations when it does not. A read never throws for a moved base; the pend is what pays for it, with one replay.
- Drift-blind sources (test doubles without `getGeneration` and `getCachedRevision`) take no pins, report no base, and detect no movement, exactly as today. The next ticket's storage side abstains for a pend that carries no base, so these keep working.
- Nothing here changes what goes on the wire. `computeBlockContentDigests` keeps declaring digests only for blocks it can materialize; its `baseRev` is now always the pin's revision.

## Edge cases & interactions

- **Same revision, new generation.** A miss-load of an evicted id, or a refresh that re-read identical content, must not count as moved. Re-clone the block at the same revision and continue; the digest is still declared.
- **Rev-only pin.** Block read, evicted by many other reads, then updated: the pin carries the revision and no block. `stagedBaseRevs` reports it; `peekMaterialized` omits the digest (existing `digest.spec.ts` "LRU-evicted base: omitted" stays green); the pend (next ticket) carries the base.
- **Insert then update, update then delete.** An inserted block has no base (`insert` deletes the pin; a later update bakes into the insert). A deleted block's pin is dropped. `stagedBaseRevs` never names an inserted or deleted id.
- **Own commit folded into the cache** (`transformCache` after a successful attempt): the tracker was reset first, so no pin survives to look moved. Pin this with a test: a two-batch sync (the `hasUnsyncedChanges` loop committing twice) does not replay between batches for no reason.
- **Refresh that moves nothing.** A refused attempt followed by a refresh that adopted no new revision and found no conflict does not replay today; the re-validation before the re-pend is what catches a moved base there. This is the exact retry shape of the ticket's scenario when the block is not read again.
- **Rollback-style reset.** `Tracker.reset(transforms)` keeps pins for ids still staged (`BasePins.retainOnly`); those revisions remain fixed. A plain `reset()` clears everything, including moved marks.
- **Concurrent unlatched read on the same handle** between re-validation and the pend: the read may move the base after the check. The pend then declares the pin's revision, which is right for the operations; storage refuses it if that base is not current, and the retry re-validates and replays. Never a fork, at worst one extra round.
- **Pinned read views** (`Collection.createReadTracker`) get their own `CacheSource` seeded from a snapshot and stage nothing for commit; confirm no pin path runs through them, and that a view pinned below a floor is still served the older content (existing `refresh-below-floor.spec.ts` "through a pinned read view" tests must stay green under Invariant A).
- **Multi-collection coordinator.** Each collection's tracker re-validates independently before its pend; a moved base in one collection re-stages that collection's pending queue only. The coordinator's snapshot and restore (`snapshotPending`, `restorePending`) must still bracket the replay correctly on a failed attempt.
- **Memory.** Rev-only pins are one number per id. Block-clone pins are unchanged in size and lifetime.

## Key tests

- `tracker`: base revision fixed at the first update; generation bump at the same revision keeps the digest declared with that revision; generation bump to a different revision lists the id in `movedBases`, `peekMaterialized` returns nothing for it, `stagedBaseRevs` still reports the original revision; `stagedBaseRevs` excludes inserted and deleted ids; a rev-only pin reports a base and no digest.
- `cache-source`: an overtaken late older answer returns the held content and records the held revision as the read dependency; a handed-through answer for an id already cached returns the cached content; `getCachedRevision` after `tryGet` equals the revision of the returned content on the cached, unkept, and evicted-then-reloaded paths.
- `refresh-below-floor.spec.ts` "under staged changes", extended with the ticket's scenario through the production path (`Collection.act` then `sync`), against a transactor wrapper that refuses a commit whose declared base for a block is not that block's latest (mirroring `StorageRepo.internalCommit`'s rule; the file already has an overriding-commit transactor at "a write staged over a too-old base still declares the base it was really built on"). Two variants. With a second read of the leaf after storage catches up: the commit declares the newer version and the committed leaf reads `1, 5, 9` in order. Without the second read: the first attempt declares the older version and is refused, the retry re-stages without a log move, and the committed leaf reads `1, 5, 9`. Expected output either way: one committed action, correct order, no `SyncRetryExhaustedError`.
- `atomic`: adopting a pin whose revision differs from the parent's pin for the same id marks the base moved rather than overwriting.
- Perf guard: `tracker-read-perf.spec.ts` and `refresh-read-cost.spec.ts` budgets unchanged (re-validation is one cache probe per pinned id, and one read only for unkept or evicted ids).
