# Subscription renewals to one cohort member share a request

Found while planning `the-reactivity-backstop-check-costs-nothing-while-idle` (GitHub [#48](https://github.com/gotchoices/Optimystic/issues/48)), which batched the watch service's per-tick tail reads into one read. Renewals were left at one per collection on purpose — the issue asked that their cadence stay at TTL / 3.

## Today

Each watched collection has its own cohort-topic registration. On every tick (TTL / 3: 30 s Core, 20 s Edge) the watch service queues `ReactivitySubscriptionManager.renew` on each subscription → `CohortTopicService.renew` → `RenewalParticipant.pingLoop`, which signs one `RenewV1` and dials its primary's `/register` (`ITopicRouter.dialMember`).

The slot is `H(participantId ‖ cohortEpoch) mod k` (`assignSlots` in `packages/db-core/src/cohort-topic/registration/sharding.ts`), and the epoch is a hash of the cohort's member list, so every registration one node holds at cohorts with one member list has one primary. On a two-member group that is every registration: once the prereq lands they are either all self-primary (answered in process, no request) or all primary at the other machine (today one request per collection: 18 tables on an Edge phone ≈ 54 renew requests a minute). On larger groups registrations spread over the distinct primaries of the distinct root groups. (Static reading; not measured.)

## Design

### Wire: a batch of plain pings on its own protocol

New protocol `/optimystic/cohort-topic/1.0.0/renew-batch` (`PROTOCOL_COHORT_RENEW_BATCH` in `packages/db-p2p/src/cohort-topic/protocols.ts`; add `renewBatch` to `CohortTopicProtocols`, `DEFAULT_COHORT_TOPIC_PROTOCOLS` and `makeCohortTopicProtocols`). Request/response, one frame each way, like `/register`.

```
interface RenewBatchV1 {
  v:      1
  renews: RenewV1[]        // 1..MAX_RENEW_BATCH_ENTRIES, each a plain ping (no reattach, no withdraw)
}
interface RenewBatchReplyV1 {
  v:       1
  replies: RenewReplyV1[]  // same length and order as renews
}
```

- `MAX_RENEW_BATCH_ENTRIES = 64` (db-core, beside the wire types). A `RenewV1` encodes to a few hundred bytes, so a full batch is far under the cohort-topic frame cap. The sender splits a larger group into several frames; the validator refuses a frame over the cap.
- Each entry is a complete, individually signed `RenewV1`, byte-for-byte what a single ping sends. The member does not verify plain-ping signatures today (§Renew (ping): a plain ping only touches `lastPing`), and the batch does not change that; keeping entries identical to single pings means one code path on the member and leaves any future renew replay guard keyed per entry. The cost is unchanged: one Ed25519 signature per registration per tick.
- **Only plain pings are batched.** `reattach` (crash failover) and `withdraw` (leave tombstone) are rare, privileged and judged per record by the freshness gate; they keep going singly over `/register`. `validateRenewBatchV1` refuses a frame with an entry carrying either flag, or an empty or oversized `renews`.
- Codecs/validators in db-core's wire module: `validateRenewBatchV1`, `validateRenewBatchReplyV1`, `decodeRenewBatchV1`, `decodeRenewBatchReplyV1`, exported like their single siblings.

Why a new protocol id rather than a new frame shape on `/register`: an older member's `/register` handler fails a frame it does not recognise in a way the dialer cannot tell from a dead link, while an unregistered protocol fails negotiation with libp2p's `UnsupportedProtocolError`, which is a definite "this peer is on an older build".

### Member side (db-p2p host)

Register a handler for `renewBatch` in `registerCohortTopicProtocols` (`makeRequestHandler`). Body: validate, map every entry through `resolveRenew(registry, renew, now)` in order with one `now`, encode `RenewBatchReplyV1`. Each entry gets exactly the answer the same `RenewV1` would get on `/register` (`ok`, `primary_moved`, `unknown_registration`). Build the frame handler as a named function beside `handleRegisterFrame` so the router's in-process path (below) can call it too. Like `/register`, the protocol is not behind `authorizeInboundStream` (that gate covers the four database protocols only).

### Router port (db-core) and its FRET binding

Add an optional method to `ITopicRouter` (`packages/db-core/src/cohort-topic/ports.ts`):

```ts
/** Send a RenewBatchV1 frame to `member`; resolves the encoded RenewBatchReplyV1. Rejects with
 *  RenewBatchUnsupportedError when the member does not speak the batch protocol. */
dialMemberRenewBatch?(member: PeerRef, frame: Uint8Array): Promise<Uint8Array>;
```

`RenewBatchUnsupportedError` is a db-core error class (db-core cannot see libp2p's errors). `FretTopicRouter.dialMemberRenewBatch` dials `renewBatchProtocol` (a new router option, defaulting to `PROTOCOL_COHORT_RENEW_BATCH`; the host passes `protocols.renewBatch`) with `requestResponse` + `requireReply`, and maps a negotiation failure (`err.name === 'UnsupportedProtocolError'`, the check `identifyConnection` in `packages/db-p2p/src/network/identify-on-open.ts` already makes) to `RenewBatchUnsupportedError`. Check how `openProtocolStream`'s race reports a negotiation failure — if it wraps per-path errors, look inside the wrapper rather than only at the top-level name. A member that is this node is served in process through the batch handler, the same self branch the prereq adds to `dialMember` (reuse its `selfPeerId` check; the host passes a second local handler, e.g. `handleRenewBatchLocally`). A router without the method (test doubles, other embedders) gets no batching.

### Participant side (db-core)

**Split the ping cycle in two** in `packages/db-core/src/cohort-topic/registration/renewal.ts`, without changing its behaviour:

```ts
interface PreparedPing { readonly target: Uint8Array; readonly msg: RenewV1 }
interface RenewalParticipant {
  /** The signed plain ping for this cycle and the member it goes to (the current primary). */
  preparePing(): Promise<PreparedPing>;
  /** Act on that ping's answer — `undefined` for no answer — as pingLoop does: reset, adopt
   *  primary_moved, or strike (and on the third strike fail over). */
  settlePing(reply: RenewReplyV1 | undefined): Promise<void>;
  pingLoop(): Promise<void>;   // = prepare, transport.send (rejection → undefined), settle
  ...
}
```

`acceptPingReply`, `strike` and `failover` stay as they are; failover's re-attach and re-walk still go singly through the transport. A `preparePing` that throws (the signer failed) is a failed ping, as a throwing `buildRenew` inside `trySend` is today.

**`CohortTopicService.renewMany(handles)`** in `packages/db-core/src/cohort-topic/service.ts`; `renew(handle)` becomes `renewMany([handle])`:

1. Keep each handle that is still live (`liveRenewal`) and not already renewing. Add an in-flight mark on `LiveRenewal`: a renewal cycle that is still running — usually a failover held up by a re-walk — makes later `renew`/`renewMany` calls skip that registration rather than run a second cycle beside it. This replaces the per-subscription queue the watch service used to serialise renewals with (below), and protects every caller (the matchmaking provider renews through `renew` too). Clear the mark in a `finally`.
2. `preparePing` each, in parallel.
3. Group the prepared pings by target (`bytesKey`), chunk each group at `MAX_RENEW_BATCH_ENTRIES`, and send each chunk:
   - one entry, or no `dialMemberRenewBatch`, or the target is remembered as unsupported → single `dialMember` sends as today, in parallel;
   - otherwise one batch frame. A rejection with `RenewBatchUnsupportedError` remembers the target and re-sends that chunk singly in the same call. Any other rejection, or a reply that fails validation or has the wrong length, makes every entry of the chunk "no answer" (a failed ping, which is what N single pings to that target would each have been).
4. `settlePing` each with its answer, in parallel — but only for a handle still live at that moment: a handle displaced by a later `register` (a tail follow at the root) or withdrawn while its ping was out is not settled, so a displaced registration never fails over and re-walks. Then `syncHandle`.
5. Settle after every send has finished; one registration's failover never delays another's ping. Resolve when every settle has; if any settle threw (a re-walk throw propagates out of `pingLoop` today), throw an `AggregateError` of those after the rest have finished.

**Remembering an older member.** A `Map` from target to the time after which batching is tried again, `RENEW_BATCH_UNSUPPORTED_RECHECK_MS` (10 minutes), on the service; expired entries are removed when read. Its size is bounded by the number of distinct primaries this node renews with. Put a `NOTE:` tripwire on it: if a node ever renews with very many distinct primaries, cap it.

### Watch service (db-p2p)

`ReactivityCollectionWatch.tick` stops queuing `renew(sub)` on each subscription and instead makes one `this.options.service.renewMany(...)` call over the `registration` handles of the subscriptions it ticks (those not `tickQueued`, with a registration), not awaited by the tick, rejection logged. The tail read and its apply step are unchanged and still go through each subscription's queue; `tickQueued` keeps its meaning for the apply step. Update the file header's "Work on one subscription is serial" paragraph: renewal is no longer queued per subscription; the service runs at most one renewal cycle per registration and leaves displaced registrations alone. `ReactivitySubscriptionManager.renew` stays for other callers.

## Edge cases & interactions

- **Mixed versions, new participant → old member.** Negotiation fails → `RenewBatchUnsupportedError` → that chunk is re-sent singly in the same tick, nothing counted as failed; the target is remembered for 10 minutes. **Test** (service spec, router double whose batch method rejects with the error): every registration is answered `ok` that tick, and the next `renewMany` sends singles without trying the batch.
- **Old participant → new member.** Unchanged: it sends singles on `/register`. By inspection.
- **Branching per entry.** A batch whose replies are `ok`, `primary_moved` and `unknown_registration` updates each participant as a single ping with that reply would (reset; adopt the new primary/backups/epoch; strike). **Test** (service spec): one `renewMany` over three handles sharing a target sends one batch frame and leaves each handle in the state its own reply implies; the third strike on the `unknown_registration` one runs its failover alone.
- **Batch transport failure.** A batch that rejects (other than unsupported), or a malformed or wrong-length reply, strikes every entry once — no more, no fewer. Covered by inspection of the one branch; fold an assertion into the test above if cheap.
- **Grouping.** Registrations with different primaries go in different frames; a group above 64 is split. By inspection (the grouping is a `Map`; the split is one loop).
- **Self-primary.** A batch to this node is served in process through the batch handler (prereq's self branch). By inspection; the prereq tests the self route.
- **Privileged renews never batched.** `reattach` and `withdraw` keep going through `dialMember`; the member's validator refuses a batch entry carrying either flag, so a hostile batch cannot smuggle one past the per-record freshness gate. **Test** (`packages/db-core/test/cohort-topic/wire.spec.ts`): a batch with a `withdraw` entry is refused.
- **Concurrent cycles.** A registration whose previous cycle is still in failover is skipped by the next tick; displaced or withdrawn handles are neither pinged nor settled. The skip is one guard; verify by inspection. The displaced-handle rule is the existing `liveRenewal` identity check applied once more before settling.
- **Renew racing a tail follow.** The renewal now runs beside the subscription's queued follow. If the follow re-registers at a new root while the old handle's ping is out, the old handle is not settled (above); its record at the old root expires by TTL, as a displaced record already does (the `NOTE:` at `startRenewal`). By inspection.
- **Withdraw racing a renew.** `withdraw` deletes the live entry first, so a `renewMany` either skips the handle or does not settle it; a ping that reaches the member after the tombstone gets `unknown_registration`, which nobody acts on. By inspection.
- **Member-side cost.** One batch costs the member one `findHolder` per entry, as the same singles would; the 64-entry cap bounds a frame. By inspection.
- **Matchmaking.** Its transports renew through their own `sendRenew` path, not this service, and are untouched; `MatchmakingProviderSession` reaches `CohortTopicService.renew` and only gains the in-flight guard. By inspection.

## Not in scope

- One stream carrying several requests (`feat-a-stream-carries-more-than-one-request`): a different, all-protocol change. Batching here makes renewals one request per target per tick on any stream model.
- Re-registers and moves at a new root stay one request each.
