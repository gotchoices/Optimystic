Stage 10 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages), the plugin half. The db-core half, `offline-sync-already-applied-guards-in-db-core`, adds the three guard kinds (`absentOrEqual`, `unchangedOrEqual`, `unchangedOrAbsent`) to the tree, the per-segment tally of what they accepted, and `effect` on the db-core queue's `committed` status; design as if it has landed. This ticket decides WHEN a statement's staged element carries one of them, from the write description Quereus 4.21.0 hands the vtab, reports the effect on the plugin's status, and teaches the outlook the kinds. Read [§Guards that make idempotent writes assured](../../docs/offline-sync.md#guards-that-make-idempotent-writes-assured), [§What the analysis needs from Quereus](../../docs/offline-sync.md#what-the-analysis-needs-from-quereus) and the sibling checkout's `docs/write-scope.md` (the `../quereus` repository) first. The doc's description of the shipped API was checked against `@quereus/quereus/src/planner/analysis/write-scope.ts` for this plan and matches: `TableWrite.selfIndependent` and `TableWrite.disposition` (`abort | fail | rollback | ignore | replace | upsert { clauses }`, each clause with `target: string[] | 'primary-key'` and `action: 'nothing' | 'update'`) are what this ticket reads.

## Which element carries which kind

The vtab's `update()` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` stages every main-tree element with a guard today (the `unchanged` helper, the `{ kind: 'absent' }` literal). Each site below keeps its guard unless the stated gate holds, in which case it stages the variant instead. Every gate is a pure function of the description and the arm, beside `freshElementsOf` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/write-description.ts`, so it is unit-tested over prepared statements alone; the same rule `freshElementsOf` applies holds here: a description absent (an FK cascade child write) or of another operation than the arm (the upsert `DO UPDATE` arm receives the INSERT's description) describes nothing about the row, so the gate fails and the plain kind is staged.

| Site (arm) | Today | Variant | Gate |
|---|---|---|---|
| INSERT whose probe found the key clear | `absent` | `absentOrEqual` | the description's `operation` is `insert` and its `disposition` is `ignore`, `replace`, or `upsert` with a clause whose `action` is `nothing` and whose `target` is `'primary-key'` or the table's primary-key columns as a set (lowercased); OR the table is tagged `"optimystic.content_key" = true` (below). A plain `insert` keeps `absent`: SQL says a duplicate is an error, and an application may rely on that to learn that someone else got there first. |
| INSERT OR REPLACE over an occupied key (the displaced entry's guard) | `unchanged` | `unchangedOrEqual` | `operation` is `insert` and `selfIndependent`. Two machines running the same `insert or replace into Settings …` is the idempotent-upsert pattern and is exactly the case the variant exists for. |
| same-key UPDATE | `unchanged` | `unchangedOrEqual` | `operation` is `update` and `selfIndependent` (no `set n = n + 1`, nothing read from other rows). |
| DELETE | `unchanged` | `unchangedOrAbsent` | always. A delete's intent for the row is that it be gone, whatever selected it; a `global` selection's wider decision is already reported as a `row-selection` unchecked decision. No description is needed, so a cascade child delete gets it too. |
| secondary-UNIQUE eviction's delete (`applyUniqueEvictions`) | `unchanged` | `unchangedOrAbsent` | always: the REPLACE's intent for the evicted row is that it be gone. |
| primary-key move, delete half (`update … set id = …`) | `unchanged` | none | keeps `unchanged`. If a rival deleted the old row, the sequential statement affects zero rows; accepting the absent delete half and still inserting the new row would create a row the sequential execution never would. |
| primary-key move, insert half (`absent`, or `unchanged` on a displaced entry) | as today | none | the clear-key half's `absent` is a key the statement did not choose to collide on; the displaced half is too exotic to accept. |

Index trees are untouched: an index entry carries no `unchanged` guard and its `absentRange` guard is unchanged. Under an already-applied entry the index segments replay as no-ops of their own accord: the delete of the old index entry finds nothing (the rival removed it; a blind delete writes nothing), the insert of the new index entry finds an equal entry and rewrites it, and the `absentRange` scan excludes the entry's own key, which is where the rival's identical entry sits.

The `optimystic.content_key` tag is new, declared in [docs/offline-sync.md §Declared hints](../../docs/offline-sync.md#declared-hints) by this ticket: `"optimystic.content_key" = true` on a table says its primary key is a deterministic function of the row's other columns (a blob store keyed by hash), so two machines inserting the same content insert the same row and a plain `insert` of an equal row is the same write made twice. Read `=== true` from the catalog record, the rule `optimystic.single_writer` is read by, at staging time. The design doc names this condition ("the table's key is a deterministic function of its content") without saying how the plugin learns it; a tag is the only source the plugin can have, since no provenance label describes a content hash, and it is the shape the other two hints already take. The alternative, leaving content-keyed tables to plain `absent`, was rejected because the blob-store case (two devices attaching the same file offline) is the realistic one. Note the variant still compares the whole row: an equal key under different content refuses as a plain insert would.

## The effect on the status

`QueuedTransactionStatus`'s `committed` arm (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-status.ts`) becomes `({ kind: 'committed'; effect: 'applied' | 'already-applied' } & SqlCommitDurability)`, the shape the design doc's status listing already shows; `effect` is the db-core status's, passed through by `OfflineMode.committed`. `TransactionOutcome` follows. The journal's `PersistedOutcome` for a committed outcome (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-journal.ts`) gains `effect`, and `decodeOutcome` answers `'applied'` for a record written before the field existed, so `plugin.offline.outcomes()` keeps reading older journals. The `onCommitDurability` report is unchanged: `SqlCommitDurability` says who holds the commit, and an already-applied entry is held exactly as an applied one.

## The outlook

`CollectionJudge` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-outlook.ts` judges the three kinds as their base kinds: `absentOrEqual` as `absent` (exposed unless the key is fresh), `unchangedOrEqual` and `unchangedOrAbsent` as `unchanged` (exposed unless single-writer or inserted fresh by an earlier entry). The cover rule treats them as exact-key checks, and `writtenKeysIn` counts an `absentOrEqual` insert among `insertedAbsent`, since a rival change that refuses a later check at the key still refuses the earlier one first. Without this an entry carrying a variant would be judged "unknown check kind", a `row` exposure with no key. One field is added to `Exposure`: `tolerates?: 'same-change'`, present on an exposure whose check accepts a rival that made exactly this transaction's change (the row already deleted, the row already equal to what this transaction writes) and refuses only a rival that made a different one. `kind` stays `exposed` for such a check, because a rival can still make a different change; the field is what the design means by "the outlook counts these guards as not refusable by a rival making the same change". `renderCommitOutlook` includes it when present. `refusedCheck` needs nothing: the variants refuse with the same error classes.

## Edge cases & interactions

- **Two machines mark the same task done offline** (`update Task set done = 1 where id = ?` on each): the second drains with `effect: 'already-applied'`; its index segments land as no-ops. The test-plan case; end-to-end test.
- **Two machines delete the same row**: both commit, the second `already-applied`. Test.
- **Two machines increment the same counter** (`set n = n + 1`): not self-independent, plain `unchanged`, the second fails `concurrent-modification` as today. Test, the negative control.
- **Two machines `insert or ignore` the same row under the same natural key**: the second commits `already-applied`; a plain `insert` of the same row still fails `constraint`. One test for the pair.
- **The same change plus a different one in one transaction**: one row already done elsewhere, one not; the entry commits with `effect: 'applied'` (the db-core rule is all-or-nothing over the variant elements, and a write under plain `absent` or `unchanged` counts as applied too, so a plain `insert` beside an already-applied update also reads `applied` — the db-core review widened the count to those two main-table kinds; index-tree shapes stay uncounted). Named in the status doc comment; covered by db-core's queue and tree-guard tests, not repeated here.
- **The upsert `DO UPDATE` arm** receives the INSERT's description; its `operation` is `insert` while the arm is an update, so the same-key UPDATE site stages plain `unchanged` there. Unit-tested over a prepared `on conflict do update` statement: the gate answers false for the update arm.
- **An INSERT with `on conflict (other_unique_col) do nothing`**, the clause targeting a non-key column: the gate answers false (a present equal row at the primary key is not what the clause excuses), so `absent` stays. Unit test.
- **The displaced-row `unchangedOrEqual` on `insert or replace`** also deletes the displaced row's index entries computed from the displaced image; when the rival made the same replace, those deletes find nothing and the new entries are equal. By inspection, stated in the site comment.
- **A DELETE whose row a rival changed (not deleted)**: refused, `concurrent-modification`, as today. Covered by the existing `concurrent-row-change-refusal.spec.ts` DELETE arm, which must keep passing with the variant staged.
- **The eviction's delete when the evicted row is already gone**: accepted; the REPLACE's row then lands. By inspection, stated at `applyUniqueEvictions`.
- **Initial staging on a mesh** can meet the acceptance too: a DELETE whose row a rival's commit (fetched by the tracker the guard scans, not by the probe) already removed is now accepted and the statement returns `ok` for a row the sequential execution would not have found, where it refused before. Acceptable: the final state is the statement's intent; named in the `update()` arm comment beside the existing "a guard refusal at INITIAL staging" note.
- **The journal**: guards ride in the sealed segments as plain data, so the new kinds round-trip with the entry record unchanged; the outcome record's `effect` is the one format change, with the decode default above. Test in `offline-journal.spec.ts`: an outcome record without `effect` decodes as `applied`.
- **The outlook's `tolerates` field and `CommitOutlook()`**: an open transaction with a self-independent same-key update reports `exposures[0].tolerates === 'same-change'` in the rendered JSON. Unit test in `commit-outlook.spec.ts`, beside a case that a `set n = n + 1` update's exposure carries no `tolerates`.
- **`optimystic.content_key` and the outlook**: the tag changes which kind is staged, not the judgement; a content-keyed insert is exposed (`primary-key`, `tolerates: 'same-change'`) unless its key is fresh. By inspection.
- **Session mode** stages through the same `update()` and so carries the variants; a guard there is enforced on the same replay paths. Nothing changes: session mode is refused with offline mode and the variants are sound online too (a racing identical write commits instead of refusing). Stated in internals.md.
- **`assuredFailures` / `outlookContradicted`**: unchanged; an assured entry never carries an exposed variant.
