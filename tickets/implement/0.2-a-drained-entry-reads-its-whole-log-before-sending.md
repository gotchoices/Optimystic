GitHub #53 reported the cost of offline commits. This is a term the report could not see, found while measuring it. It is the one cost here that grows with the collection's total history rather than with the queue.

## The defect

A refresh normally reads the header and log tail in one request and stops if the tail shows nothing newer than what the collection holds (`Collection.tailShowsNothingNewer`). `Collection.updateInternal` skips that exit whenever a write is in flight:

```ts
if (this.inFlightActionId === undefined && Collection.tailShowsNothingNewer(actionContext, ends.tail)) {
```

Its comment gives the reason: the walk is "not needed for soundness", and "a retry refresh is rare enough that the walk costs nothing that matters". That was true when only retries refreshed in flight. It is false now: `Collection.commitHead` and `TransactionCoordinator.commitEntry` both open every cycle with a refresh under the in-flight mark, so **every drained entry walks each of its collections' logs back to the first block** (`Log.getFrom`; there are no checkpoints yet).

## Measured

`NODE=1 MODE=wait N=150 node test/offline-commit-cost.bench.mjs`, run in `packages/quereus-plugin-optimystic` (see that file's header; Windows, Node 24), so the queue never holds more than one entry. Read requests are counted at the transactor. Stacks taken at `NetworkTransactor.get` name `Log.getFrom` under `Collection.updateInternal` under `TransactionCoordinator.refreshBetweenAttempts` for 264 of the last 333 reads.

|---|---|
| read requests, either storage | 3.1 5.2 7.4 9.5 12.0 14.7 (online: 0) |
| time in reads, memory block storage | 0.4 0.7 0.8 1.1 1.4 1.5 ms |

The report's script keeps blocks in memory, which is why it shows only a slight rise (79 → 90 ms). Whether this explains the 118 ms per row Sereus Health saw is not measured.

## The change

Let an in-flight refresh take the early exit when **no attempt has been sent under this cycle**: the condition becomes `(this.inFlightActionId === undefined || this.inFlightAttempt === undefined) && Collection.tailShowsNothingNewer(...)`. With no attempt retained, no entry of this write can be in the log, so the walk has nothing to find.

This is safe because of the contract on `Collection.retainInFlightAttempt`: every write path that marks an action in flight retains each failed attempt before the refresh that follows. The sites are `Collection.syncAttempts`, the head commit handle's `refused` step, `TransactionCoordinator`'s commit span, and `Collection.openHeadCommit` with `resume` on a re-drive. So every case in which the write may have landed still walks. Keep the comment's reasoning for those, and correct its "rare" claim.

Rejected: dropping the in-flight condition altogether. The comment is right that this is sound, since the entry would sit above the held revision and the tail test refuses that, but that rests on the tail read being current. A retry is exactly when a lagging coordinator has been in the picture, and missing that entry loses the write.

## Edge cases & interactions

- A re-drive under the action id of an attempt that may have landed (`resume` set, after a restart or a kept-queued failure) still walks and finds its own entry. Verified by the existing `packages/db-core/test/coordinator-own-action-replay.spec.ts`, `packages/db-core/test/own-entry-completes-the-action.spec.ts` and `packages/quereus-plugin-optimystic/test/offline-restore.spec.ts`.
- A torn attempt inside one cycle: the `refused` step retains the attempt before the next refresh, so that refresh walks. Same specs.
- A send that throws rather than returning a refusal leaves the cycle, and the queue re-drives with `resume` from what `OfflineQueue.recordAttempts` recorded before the send. Verified by inspection of `driveHeadCommit` and `TransactionCoordinator.commitEntry`.
- A rival's commit landing between the enqueue and the drain: the tail test sees it and walks as before, and the replay follows. Verified by `packages/db-core/test/collection-segments.spec.ts`.
- `tailShowsNothingNewer` also refuses a held context that disagrees with the tail's entries, so a fork is still walked. `packages/db-core/test/refresh-read-cost.spec.ts` already pins that ("a refresh with nothing new still walks the log when the held context does not name its own revision").

## Test

One case in `packages/db-core/test/refresh-read-cost.spec.ts`, in the style of "a refresh that finds nothing new costs one request": a head commit's opening refresh with nothing new costs one read request however long the history has grown. It is a named budget on branching logic, and it fails on the code above.
