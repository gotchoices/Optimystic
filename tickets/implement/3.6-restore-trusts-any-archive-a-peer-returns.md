# `ensureRevision` writes any archive a peer hands back

## The hole

`BlockStorage.ensureRevision(meta, rev)` (`storage/block-storage.ts:377-406`) fills a gap in local
revision history by asking a peer:

```ts
const restored = await this.restoreBlock(rev);
if (!restored) {
    throw new Error(`Block ${this.blockId} revision ${rev} not found during restore attempt.`);
}
await this.saveRestored(restored);

currentMeta.ranges.unshift(restored.range);
currentMeta.ranges = mergeRanges(currentMeta.ranges);
await this.storage.saveMetadata(this.blockId, currentMeta);
```

The only check on the returned archive is that it is not `undefined`. Nothing verifies that it
covers the revision `rev` that was asked for, and nothing protects revisions this node already
holds. `saveRestored` then writes, per revision entry:

```ts
this.storage.saveRevision(this.blockId, rev, action.actionId),
this.storage.saveTransaction(this.blockId, action.actionId, action.transform),
block ? this.storage.saveMaterializedBlock(this.blockId, action.actionId, block) : ...
```

`saveMaterializedBlock` is keyed by action id, so an archive naming an action id this node already
has stored **overwrites that action's materialization** — including one for a revision that was
never in question and was perfectly sound.

`ensureRevision`'s own doc for `saveRestored` already states the trust position plainly: an archive
is "remote wire data — `restoreBlock`'s `RestorationCoordinator` fetch verifies nothing, and a peer
chooses what to attach". That reasoning is applied to the entry's `proof` field, which is
deliberately ignored, but not to the revision numbers, action ids, or block bytes beside it, which
are written unconditionally.

## Verified, via the bug that is being fixed upstream

This is not a hypothetical. `fix/block-archive-rev-pin-is-a-no-op` (superseded by
`implement/serve-pinned-revision-honestly`) is a real in-tree producer of exactly this wrong answer:
a peer asked for rev 1 while holding rev 2 answers with rev 1's bytes under rev 2's number and
action id. Feeding that through `ensureRevision` was reproduced end to end:

```
ASKER rev2 BEFORE:  {block: items:["TWO"], actionRev:{rev:2, actionId:"a2"}}
ASKER asks peer for rev 1  →  archive keyed 2/a2 carrying rev 1's bytes  →  saveRestored
ASKER meta AFTER:   {"ranges":[[2,3]], "latest":{"actionId":"a2","rev":2}}
ASKER rev2 AFTER:   {block: items:["ONE"], actionRev:{rev:2, actionId:"a2"}}
```

The asker's good rev 2 was silently replaced with rev 1's content, and rev 1 — the thing actually
requested — was still not recorded as held, because `mergeRanges([[2,3],[2,3]])` leaves `ranges`
unchanged. Every later read of rev 1 repeats the fetch and the overwrite.

The prereq ticket removes that particular producer. This ticket removes the *class*: after it
lands, a peer that answers the wrong revision — through a future bug, a version skew, or malice —
gets its answer rejected instead of written, and the requester fails loudly.

## Why this is not covered by the prereq

The prereq fixes the one honest peer in this repo. `ensureRevision` sits on the receiving end of a
network wire whose other end is a machine this node does not control, and `RestorationCoordinator`
performs no verification of any kind on the response (`restoration-coordinator.ts:144-159` returns
`response.archive` straight through). A trust boundary with no check on it is a defect in its own
right, and it is the component that converted "wrong revision served" into "local storage silently
corrupted".

## Expected behaviour

- An archive that does not cover the requested revision is rejected: nothing is written, the
  metadata ranges are unchanged, and `ensureRevision` throws the same "revision N not found during
  restore attempt" it already throws for an absent archive.
- An archive whose declared `range` does not match the revision keys it actually carries is
  rejected on the same terms — the range is what gets merged into `meta.ranges` and is therefore
  the claim that matters most.
- A restore never overwrites a materialization or transform this node already holds for an action
  id with different content. The correct handling when the incoming bytes differ from the stored
  ones is a genuine choice: refuse the whole archive (safest, and consistent with the bullets
  above) or keep the local copy and accept only the revisions this node lacks. Pick one, and say
  which in the review handoff — do not silently overwrite.
- Everything that works today keeps working: a peer answering the requested revision correctly
  restores exactly as before, and `block-storage.spec.ts`'s existing restore tests stay green.

## Open question for the implementer

`saveRestored` is also reached by `saveReplica`/`saveForwardRevision` through
`StorageRepo.saveReplicatedBlock`, where `cluster/reconcile-block.ts` has already bound the content
to a verified proof. Check whether the new checks belong in `saveRestored` (covering both paths) or
in `ensureRevision` (covering only the unverified restore wire). The verified path should not be
made to pay for the unverified path's guard if the two can be kept apart cleanly; if they cannot,
prefer the guard in `saveRestored` and note the cost.
