# The hybrid logical clock and its persistence port

First of three tickets that together land Stage 1 of [docs/crdt-sync.md](../../docs/crdt-sync.md) §Migration Path: a hybrid logical clock (HLC) recorded on every transaction and every log entry, with no change to ordering, admission or visibility. The plan pass that produced them is summarised here so the three tickets can be read on their own; the other two are `every-log-entry-and-transaction-carries-its-hlc` (the fields) and `a-node-observes-the-hlcs-it-reads-and-stores` (the feed points, the skew measurement, the docs).

## What an HLC is here

The Kulkarni-Demirbas construction the doc already gives, as one value:

```ts
export type Hlc = {
	/** Wall-clock milliseconds, or higher: the max of the issuer's clock and the highest HLC it had observed. */
	readonly wallMs: number;
	/** Breaks ties among HLCs issued within one `wallMs`. 0 whenever `wallMs` moved. */
	readonly logical: number;
	/** The issuing node's peer id string. `''` means legacy: an entry written before the field existed. */
	readonly nodeId: string;
};
```

Total order: `wallMs`, then `logical`, then `nodeId` by plain string comparison (`compareHlc`). Two HLCs from one node never compare equal because the clock never issues the same `(wallMs, logical)` twice; two from different nodes are separated by `nodeId`. Keep the type a plain JSON-safe object: it travels inside log blocks and pend requests, both plain JSON on the wire.

The legacy rule, in the same module: `legacyHlc(timestamp)` is `{ wallMs: timestamp, logical: 0, nodeId: '' }`. It is what a reader derives for an entry or record written before the field existed, so the next ticket's readers have one function to call. The empty node id sorts before every real peer id, which is the only property anything relies on.

## The clock

`HlcClock` in `packages/db-core/src/hlc/clock.ts`, pure and injectable. It holds the node id and the last HLC it issued or observed. Two operations:

- `now(): Hlc` issues: `wallMs = max(localClock(), last.wallMs)`; `logical = wallMs === last.wallMs ? last.logical + 1 : 0`; `nodeId = self`. The result becomes `last`.
- `observe(hlc: Hlc): void` advances `last` to `hlc` when `hlc` is above it, comparing by `compareHlc`; otherwise nothing. Observing changes `last.nodeId` too, which is harmless because `now()` always stamps its own.

Construction takes `{ nodeId, localClock?: () => number, store?: HlcClockStore }`. `localClock` defaults to `Date.now`; tests inject a fake. A clock with no store is purely in-memory.

The clock is the only thing in the repository that mints an `Hlc`. Nothing else builds the object except the legacy rule above and test fixtures.

## The persistence port and the restart rule

A node whose wall clock is behind at restart would otherwise issue an HLC below ones it issued before the restart, so the clock's high-water mark survives through a port:

```ts
export interface HlcClockStore {
	load(): Promise<Hlc | undefined>;
	save(hlc: Hlc): Promise<void>;
}
```

The policy lives in the clock, not in the store, so every binding gets the same behaviour:

- **Persist on a jump, debounce the rest.** After each `now()` or `observe()` that moved `wallMs`, the clock saves when the new `wallMs` is at least `persistIntervalMs` (default 1000) above the last value it saved. A node ticking along on its own wall clock therefore writes at most once a second under load and nothing while idle; an observed HLC far ahead of local time is a jump and is saved at once. `save` is fire-and-forget from the clock's point of view: it is awaited nowhere on the write path, a rejection is logged under the `hlc` logger namespace and does not throw into the caller, and only one save is in flight at a time, with a newer value replacing a queued one.
- **Restart floor.** `HlcClock.start()` (or an async factory) loads the stored mark and sets `last.wallMs` to `stored.wallMs + restartSlackMs` (default 10000) with `logical = 0`, unless the local clock is already above that. The slack covers the HLCs issued between the last save and the crash: at most `persistIntervalMs` of wall time by the rule above, plus whatever the store itself had not yet made durable. Confirm the default exceeds the largest relaxed durability window the node's stores run under ([packages/db-p2p/docs/storage.md §6](../../packages/db-p2p/docs/storage.md#6-a-write-survives-a-crash-once-a-flush-called-after-it-has-resolved)) and lower it if that window is smaller; record the derivation at the constant. In the ordinary case a real restart takes longer than the slack and the local clock wins, so the floor costs nothing; it matters for a fast restart or a clock that went backwards.

The alternative, saving on every issue and awaiting it, was rejected: it puts a store write and a flush on every write path for a property a 10 s floor buys for free. The tradeoff is that after a crash the node's next HLCs may sit up to the slack above its wall clock until wall time catches up, which is ordinary HLC behaviour under an observed jump too.

## Where the clock lives

`ITransactor` gains `readonly clock?: HlcClock`. The transactor is the one node-scoped object every collection, coordinator and queue already holds, so it is the seam that reaches every minting site in the next ticket without threading a new option through `Tree`, `Diary`, `Collection` and the Quereus factory.

- `NetworkTransactor` takes `NetworkTransactorInit.clock` and exposes it. The node builds one clock per process and hands it to the transactor; that wiring, with the store bound to the node's key-value store, is in the third ticket, so here the field is simply carried.
- `TestTransactor` builds its own in-memory clock, node id `'test'` by default, with an optional constructor argument `{ clock?: HlcClock }` so a test can inject a fake local clock or a shared clock across two transactors.
- `DelegatingTransactor` forwards `clock` from its inner transactor.
- A helper `clockOf(transactor: ITransactor): HlcClock` returns `transactor.clock` or, for an `ITransactor` that declares none (the reference peer's `LocalTransactor` in `packages/reference-peer/src/cli.ts`, the Quereus plugin's `local` and `test` transactors in `packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`, host-written ones), one process-wide fallback `HlcClock` with node id `'local'` and no store. `'local'` is what `TransactionSession.create` already uses as the stamp's peer id when none is given, so the two defaults agree. The fallback is the one place a second clock instance can exist in a process; name it so in a comment, and keep `clockOf` as the only way to reach it.

## Edge cases & interactions

- **Two issues inside one millisecond** on one node: `logical` increments, the HLCs differ. Pinned by the clock test.
- **An observed HLC far ahead of local time**: the clock jumps to it; the node's own HLCs then carry a future `wallMs` until wall time passes it. Standard HLC behaviour; Stage 1 records it, the third ticket logs the gap, bounding it is Stage 2's decision. Pinned by the clock test.
- **Local clock goes backwards** (NTP step) between two issues: `wallMs` stays at `last.wallMs` and `logical` increments; never lower. Pinned by the clock test.
- **Restart with a stored mark above the local clock**: the floor applies, `logical` is 0. Restart with a stored mark far below the local clock: the local clock wins. Both pinned by the clock test.
- **A store whose `save` rejects**: logged, the clock keeps issuing, the next qualifying advance tries again. By inspection.
- **A store whose `load` rejects at start**: the clock starts from the local clock alone and logs it; refusing to start a node because its clock mark could not be read would turn a lost record into an outage. By inspection.
- **`observe` with a malformed value** (a wire field of the wrong shape): the clock takes only an `Hlc` whose two numbers are finite and whose `nodeId` is a string, and ignores anything else; the wire-side check belongs to the caller in the third ticket, so the clock's own guard is a type-level assertion plus a finite-number check.
- **Concurrent transactors in one process sharing one clock** (the mesh harness, two `TestTransactor`s given the same instance): correct, since the clock is per node and a shared one only means the two mint from one sequence.

## Tests that pay for themselves

One table-driven test of the construction in `packages/db-core/test/hlc-clock.spec.ts`, over a fake local clock and an in-memory store: local ahead; observed ahead; same millisecond twice; local clock stepped backwards; restart with a stored mark above the local clock and with one below; a jump saves at once and ordinary ticking saves at most once per interval. Nothing for `clockOf`, the transactor fields or the exports.
