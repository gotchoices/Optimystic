# A bulk push queues ahead of reads on its connection

From the fix ticket `bug-a-large-replication-push-stalls-a-relayed-attach` (GitHub [#39](https://github.com/gotchoices/Optimystic/issues/39), Optimystic 1.15.0 / Sereus 1.16.0, through relay.sereus.org). It could not be reproduced here, since a loopback relay has the throughput to hide it. The questions it asked are answered below from the code (this repository at 1.15.0 and now, the Sereus checkout at `../sereus`, and `@chainsafe/libp2p-yamux` 8.0.1), with the reported numbers. Every number is the reporter's except where it says how it was derived.

## What the report was

**The 33-block push is not Optimystic's.** Every sender in this repository pushes one block per request: the rebalance handoff and confirm, the growth arm, spread-on-churn and the under-replication drain all go through `pushBlockToPeers` in `packages/db-p2p/src/cluster/block-transfer-service.ts`, which sends `{ [blockId]: block }`. That was already true at `v1.15.0` (`git grep -n "pushBlocks(" v1.15.0 -- packages/db-p2p/src`). A multi-block `reason=replication` push comes from Sereus's join catch-up, `PeerJoinBackfill` in `../sereus/packages/cadre-core/src/peer-join-backfill.ts`, which packs blocks into messages of up to 1 MiB (`maxChunkBytes`) and 64 blocks (`maxChunkBlocks`). At Sereus 1.16.0 that budget was measured on the base64 form the push then used.

**Why it is pushed twice per join: fixed in Sereus.** At Sereus 1.16.0 the joiner pushed the founder's own blocks back to it. Sereus's `join-backfill-pushes-once-and-is-waited-for` (2026-10-20, after 1.16.0) skips any block whose retained commit proof the peer signed, and `join-catch-up-skips-a-returning-peer` remembers what each peer accepted. The holder-evidence path asked about in the fix ticket (`RebalanceMonitor.recordBlockHolders`) is not involved: it governs Optimystic's growth arm, which pushes one block at a time and was not the sender here. It is fed by an accepted push (`received-replicas-report-their-source-as-a-holder`) and by an embedder's `reportBlockHeld`, which Sereus's catch-up now calls.

**The push is smaller now.** Since Optimystic 1.19 (`a-block-copy-travels-unencoded`) a push carries each block as JSON rather than base64 of its JSON, about a quarter fewer bytes. Its reply names the accepted ids rather than echoing every block. In 1.15.0 the reply (`response blocks=33 missing=0`) carried all 33 blocks back over the same relayed link.

**Why the push took 8 s: the relayed link's throughput.** About 1 MiB arrived in 8.0 s, roughly 130 KB/s through the relay (derived: Sereus's chunk budget over the reported transit time). The receiver answered in 38 ms, so nothing on either machine stalled. The duplicate relayed connection between the two machines does not explain the transit time. A connection's bytes all cross the same relay, and the relay applies no limits.

**Why reads waited behind it: one queue per connection, no priorities.** Yamux, the stream multiplexer every node uses (`streamMuxers: [yamux()]` in `packages/db-p2p/src/libp2p-node-base.ts`), sends as much of a stream's data as its send window allows as one frame into the connection's single outgoing queue. It writes that queue first in, first out, and has no stream priority. The window starts at 256 KiB, which is the smallest yamux accepts (`initialStreamWindowSize` must be at least 256 KiB). It doubles only when the receiver drains a whole window within four round trips, so on a link this slow it stays at 256 KiB. A small reply sent on another stream of the same connection waits until what is queued ahead of it has drained: at most one window per active bulk stream, plus the relay hop's own buffering. The reported 1,378 ms `sync` reply, against 90–150 ms otherwise, is about 160 KB at 130 KB/s (derived), inside one window. So a read waited for part of the push's bytes, not for the whole push. The behaviour the fix ticket expected already holds per push: a read was delayed by less than the time the push's own bytes needed. FRET's `contact strike` and `negotiate strike` during the window are FRET's own requests waiting in the same queue (FRET lives in the sibling `p2p-fret` repository).

**What this repository could still change, and why it does not now.** A node runs up to four pushes at once (`BlockTransferCoordinator`'s `maxConcurrency`, default 4), and nothing stops all four going to one peer. Each stream gets its own window, so up to four windows (1 MiB) can be queued ahead of a read to that peer, about 8 s at the reported throughput (derived). That needs four concurrent pushes of large blocks to one peer over a slow link. Neither the report nor any measurement here shows it. The growth arm's joins in this repository usually move small blocks, so it is a tripwire, not a ticket. The lever, if it ever shows up: at most one push in flight per destination peer, keeping the node-wide limit for different peers. Splitting a push into smaller messages does not help on its own. Each message's frame still goes into the same queue, and on a slow link yamux will not use a window below 256 KiB.

## Outside this repository (for the human to forward)

- **Sereus.** A 1 MiB catch-up message at about 130 KB/s takes about 8 s and holds up to one window (about 2 s) ahead of every other request to that machine. Sereus already derives the push's response deadline from the declared link (`peerJoinPushBudget`). It could size `maxChunkBytes` from the declared link the same way. Since `join-backfill-pushes-once-and-is-waited-for`, the joiner waits for the copy rather than reading alongside it, which removes most of the overlap.
- **The relay.** About 130 KB/s through relay.sereus.org is the binding constraint. Sereus's `relay-bytes-metrics-libp2p` would measure it.
