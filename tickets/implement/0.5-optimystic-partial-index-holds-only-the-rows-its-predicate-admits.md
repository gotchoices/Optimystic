# A partial index holds only the rows its predicate admits

Reported as suggestion 3 of GitHub [#42](https://github.com/gotchoices/Optimystic/issues/42). Today `IndexManager` stages an entry into every maintained index tree for every row, ignoring the index's persisted `predicate` (the `where` clause of `create index … where …`), and the backfill and the integrity check (`plugin.verifyIndexes`) ignore it in the same way on purpose, each with a `NOTE:` saying all of them must change together.

## Why this is more than maintenance

Two other parts of the plugin are correct today only because a partial index holds every row. Both break the moment maintenance honours the predicate, so they are part of this change, not follow-ups:

- **The planner.** `OptimysticModule.getBestAccessPlan` offers every index in `tableInfo.indexes`, partial ones included, to any equality filter on its columns, and checks nothing about the query's `where` implying the index's predicate. With a filtered index, `select … where c = 'x'` would seek a tree that holds no entry for a matching row outside the predicate and return too few rows. Quereus's own modules avoid this by never planning through a partial index: `MemoryTableModule.gatherAvailableIndexes` (`if (idx.predicate) continue`, with the comment "using a partial index for a query it doesn't cover would silently drop matching rows") and the store module's `store-module-access-plan.ts` ("Mirrors MemoryTableModule.getAvailableIndexes"). Optimystic does the same: **skip any index whose `predicate !== undefined` in `getBestAccessPlan`.** Tradeoff: a query that today seeks a partial index (correctly, because it is over-populated) becomes a full scan. Planning through a partial index when the query implies its predicate is parked as backlog `feat-optimystic-plan-through-a-partial-index-whose-predicate-the-query-implies`.
- **Full UNIQUE enforcement.** `OptimysticVirtualTable.resolveEnforcingIndex` returns the first DECLARED index whose column set equals the constraint's, and `buildUniqueEnforcementIndexes` declines to synthesize a `_uniq_` tree when any declared index has that column set (`declaredKeys`). Neither looks at the predicate, so a full `unique (c)` can be probed against a partial index over `(c)`, which would then miss duplicates among excluded rows and admit them. The existing spec `secondary-unique-hydrate.spec.ts` builds exactly this (`ux_partial on T (Stamp) where Flag = 1` declared before `ux_full on T (Stamp)`, then inserts a duplicate with `Flag = 0` and expects a refusal), so it fails if this arm is missed. **Both sites must treat only an index with no predicate as able to enforce a full constraint.** `reassignUniqueEnforcement` goes through `buildUniqueEnforcementIndexes` and is fixed with it. A table that today enforces a full UNIQUE through a partial declared tree gets a `_uniq_` tree synthesized at its next initialization, which `ensureUniquePopulated` fills from the table on its first probe — the existing path for a renamed or new enforcement tree, nothing new.

Partial UNIQUE enforcement itself stays out of scope (backlog `bug-optimystic-unique-ignores-collation-and-partial-predicate`); this change gives that ticket an index that holds exactly the rows its constraint binds, and the evaluator it needs.

## The predicate evaluator

No new parser or evaluator: `@quereus/quereus` exports `compilePredicate(expr, columns, tableName)` (the one Quereus's memory and store modules use for partial indexes), which returns a `CompiledPredicate` whose `evaluate(row)` gives SQL three-valued truth over a row positioned by `columns`, and whose `referencedColumns` lists the positions it reads. It throws a `QuereusError` for an expression form it does not support. Only `true` admits a row; `false` and NULL both exclude it (SQLite partial-index semantics, and what Quereus's memory module does).

Wrap it in one small class in a new `packages/quereus-plugin-optimystic/src/schema/index-predicate.ts`, so the rule "what a partial index admits" has one home:

```ts
export class IndexPredicate {
	/** Compile a persisted predicate AST against the columns of the schema it came from. Throws when it cannot. */
	static compile(predicate: unknown, columns: readonly StoredColumnSchema[], tableName: string): IndexPredicate;
	/** True only when the predicate evaluates to SQL TRUE for `row`. */
	admits(row: Row): boolean;
	/** The same predicate over rows renumbered by `reposition` (a catalog-only DROP COLUMN). */
	repositioned(reposition: (position: number) => number): IndexPredicate;
}
```

- **Columns.** `compilePredicate` takes `ColumnSchema[]`. Convert with the existing `SchemaManager.storedToColumnSchema`, lifted to a module-level export in `schema-manager.ts` (it reads no instance state) so `index-manager.ts` can call it without a `SchemaManager` and without a cast.
- **Compile once, against the schema the descriptor arrived in.** Within one stored schema the predicate's column names and the column list agree: `RENAME COLUMN` is schema-only here and never reaches the catalog record (backlog `bug-optimystic-rename-column-lost-on-restart`), and on the declared-table path both come from the engine's catalog, which Quereus rewrites together. `IndexManager` compiles in its constructor and in `setSchema`, keyed by index name, against that call's `schema.columns` and `schema.name`. An index with no predicate has no entry and admits every row; unique-enforcement descriptors never carry one (`buildUniqueEnforcementIndexes` excludes partial constraints).
- **DROP COLUMN remaps, it does not recompile.** `repositionColumns` renumbers index columns and leaves `this.schema.columns` as it was, so a recompile there would bind names to the old positions. Instead each `IndexPredicate` keeps a map from the positions it was compiled against to the current ones, built from `referencedColumns`; `repositioned` composes `reposition` into it, and `admits` builds the compiled-layout row from those slots (or passes the row through while the map is the identity). Quereus already refuses to drop a column a partial index's predicate names, so `reposition` never throws for a referenced position. Remapping instead of recompiling also keeps a compiled predicate valid across a session-only rename, whatever the AST's names have become.
- **A predicate that does not compile is refused at `CREATE INDEX`, before the record is written.** Compile it at the start of `OptimysticVirtualTable.addIndex` (or wherever the index's descriptor is first built there, before `storeStoredSchema`), so the statement fails with `compilePredicate`'s own `QuereusError` and nothing is persisted. Check first whether Quereus already compiles the predicate for every module at `CREATE INDEX`; if it does, this costs nothing and stays as the plugin's own guarantee. A persisted predicate that does not compile at initialization throws out of `doInitialize` naming the table and index — no backward compatibility is owed (AGENTS.md), and a silently unmaintained or over-populated index is the worse outcome.

## Maintenance

Every site asks the index's `IndexPredicate` (through one `IndexManager` method, e.g. `admits(index, row)`) and stages nothing for an index the row is outside:

- `insertIndexEntries` — skip the index when the new row is not admitted.
- `deleteIndexEntries` — skip the index when the deleted row is not admitted. Covers the plain DELETE, the REPLACE eviction (`applyUniqueEvictions`) and the displaced row of a primary-key move (`deleteIndexEntries(pkMove.row, newKey, …)`), which all call it.
- `updateIndexEntries` — four cases per index, by whether the old and new rows are admitted:

  | old admitted | new admitted | staged |
  | --- | --- | --- |
  | yes | yes | as today: nothing when the tree keys are equal, otherwise the delete and the guarded insert as ONE action, delete first |
  | yes | no | the delete of the old entry alone (blind, as today's delete half) |
  | no | yes | the insert of the new entry alone, with `guardFor(index, newIndexKey, uniqueIndexes)` |
  | no | no | nothing |

- `backfillIndexTrees` — skip a row for a target index that does not admit it. **`stagedAny` becomes per target**: it currently records "the scan staged anything", which was the same for every target because every target received every row; with predicates one target can admit nothing while another admits rows, and the deferred-flush branch must still leave an invented tree that received nothing unwritten. Remove the `NOTE:` saying backfill and live maintenance both over-populate.

## Integrity check

`compareIndexToRows` takes the predicate as one more input (e.g. `admits: (row: Row) => boolean`, passed by `verifyIndexes` as `row => manager.admits(index, row)`), and:

- builds `expected` only from admitted rows, so a row outside the predicate is never reported `missing`;
- reports an entry whose row exists, implies the entry's key, but is not admitted as an orphan with a new `OrphanReason`, `outside-predicate`. Without it, the entries older builds wrote for excluded rows would pass as healthy, and an index that over-populates again would go unnoticed. Add it to the reason table in docs/debugging.md, replacing the bullet "A partial index … is checked as if it had no `where` clause".
- Remove the `NOTE:` at the top of `compareIndexToRows` saying the predicate is ignored.

## What stays as it is

- **Entries older builds wrote for excluded rows are not removed.** No migration (AGENTS.md: no backward compatibility yet). They are harmless to queries, since the planner no longer seeks a partial index, and to uniqueness, since no full constraint is enforced through one any more. `verifyIndexes` reports them as `outside-predicate`; deleting such a row leaves its entry behind, because the delete is skipped for a row outside the predicate. Say so in docs/debugging.md beside the new reason.
- **A collection with nothing staged is not written.** An insert outside every partial index's predicate stages no action into those index trees; the transaction bridge's dirty registration already skips a tree with `hasUnsyncedChanges() === false`. Confirm by inspection that every commit route (`commitTransaction`'s three routes, the offline `sealIntoQueue`) skips a registered tree with nothing staged rather than committing an empty entry for it — that skip is where the request saving in #42 comes from.

## Edge cases & interactions

- **NULL predicate result** (`where c > 0` with `c` NULL) excludes the row, as false does. Verified by the maintenance test's NULL row.
- **An UPDATE that moves a row out of the predicate deletes its entry; one that moves it in inserts one** — each of the four rows of the table above, including with a primary-key change (old and new primary keys differ). Verified by test for in→out and out→in on the same key; the primary-key-move variants by inspection, since they reuse the same branch with different keys.
- **The update case where both rows are admitted keeps today's single delete-then-insert action** so a unique guard on the new entry never refuses its own outgoing entry (the existing comment in `updateIndexEntries`). By inspection.
- **Conflict replay.** Each index action is staged from the row the statement saw, and a rival's change to that row refuses the main-table action through its `unchanged` guard, which already prevents a stale index delta (docs/internals.md §Conflict replay re-makes the uniqueness decision). The predicate decision is a pure function of the same row, so it adds no new staleness. By inspection.
- **Full UNIQUE over the same columns as a partial index** — never resolved to the partial tree, at initialization (`buildUniqueEnforcementIndexes`), at each probe (`resolveEnforcingIndex`) and after a `DROP INDEX` (`reassignUniqueEnforcement`). Verified by the existing `secondary-unique-hydrate.spec.ts` case (partial declared first), which must pass unchanged.
- **Planner** — a partial index is never chosen, including for an `order by` it could deliver, and `assertIndexMaintained` is never reached for one. Verified by the query-correctness test below.
- **Catalog-only DROP COLUMN of a column the predicate does not name** — the predicate keeps reading the right columns after `repositionColumns`. By inspection plus the type of `repositioned`; a test only if it is cheap to add to an existing DROP COLUMN spec.
- **CREATE INDEX with a predicate `compilePredicate` cannot handle** (a function call, a subquery) — refused before the record is written; no index tree is left attached. By inspection.
- **Backfill where one target admits no rows and another admits some** — the per-target `stagedAny`. By inspection.
- **A sibling handle on an older build** keeps writing entries for excluded rows into the shared tree; reads stay correct (planner exclusion), `verifyIndexes` reports them as `outside-predicate`. Accepted; mixed builds are not supported for index maintenance.
- **Offline queue and commit outlook** read the guarded index elements a statement staged (`freshElementsOf`, `uncheckedOf`); a partial index is never in the guard set and staging less into it changes nothing they read. By inspection.

## Tests

One new spec, `packages/quereus-plugin-optimystic/test/partial-index-maintenance.spec.ts`, on the local transactor, reading the index through `verifyIndexes` (the `readIndexIntegrity` helper in `test/query-helpers.ts`, or the plugin method directly) so it asserts on what the tree holds, not on query results:

- **Maintenance (the reproduction).** `create table T (Id integer primary key, C text null, Flag integer not null)` and `create index ByFlagged on T (C) where Flag = 1`. Insert `(1,'a',1)`, `(2,'b',0)`, `(3,null,1)`: the report has `entryCount` 2 (rows 1 and 3 — `Flag = 1` is TRUE for both) and no `missing` or `orphaned`. Then `update T set Flag = 0 where Id = 1` (in→out) and `update T set Flag = 1 where Id = 2` (out→in): `entryCount` still 2, now rows 2 and 3, clean. Then delete row 2: `entryCount` 1, clean. Fails today with `entryCount` 3 after the inserts.
- **Backfill agrees.** Insert rows of both kinds, then `create index … where …`: `entryCount` equals the admitted rows, clean.
- **The planner does not drop rows.** With the index above, `select Id from T where C = 'b'` where the only matching row has `Flag = 0` returns that row. Fails if the planner exclusion is missed (it would seek the partial tree and return nothing).

No test for the `IndexPredicate` class by itself: the three above exercise it, and its remap is thin.

Run `yarn build` first (the plugin's `register.mjs` refuses a stale build of its own `dist`), then `yarn workspace @optimystic/quereus-plugin-optimystic test` in the foreground — about three minutes; `secondary-unique-hydrate.spec.ts`, `secondary-unique.spec.ts` and `hydrate-restores-declared-table.spec.ts` are the existing specs that exercise partial indexes. Then `yarn typecheck` and `yarn lint:docs`.
