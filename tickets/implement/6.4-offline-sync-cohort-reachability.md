Part 4, the last, of stage 6 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). The node's gate (`KeyNetworkCohortReachability`, `node.cohortReachability`, with the optional `ICohortReachability.onChange`) comes from `offline-sync-reachability-gate`; the queue's `allowSoloCommit` option and the coordinator's refusal from `offline-sync-solo-refusal`; the typed unanswered read from `network-get-names-unreachable-blocks`.

## Design

### The factory registers the node's gate

`CollectionFactory.createNetworkTransactor` registers `node.cohortReachability` under the transactor's key (`getTransactorKey(options)`) when the node carries one — a node a host injected without building it through `createLibp2pNode` may not; then nothing is registered and the gate stays always-open, as today. Register only when nothing is registered for that key yet, so a gate a test or host registered explicitly (`registerCohortReachability`) wins.

The stable per-key gate `getCohortReachability` hands out looks the registration up on every `reachable` call already. It must forward `onChange` the same late-bound way: the per-key wrapper keeps its own listener set; while it has listeners it is subscribed to the currently registered gate's `onChange` (when that gate has one), and `registerCohortReachability` moves that subscription to the new gate (unsubscribing from the old). The wrapper always exposes `onChange`, so a table that took the gate before the node registered still hears wakes.

### The controller routes the wake

`OfflineMode` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`) subscribes once to each distinct gate a table publishes (`setTablePolicy`; the stable wrapper is one object per transactor, so this is one subscription per transactor), keeps the unsubscribers, and releases them in `dispose`. The handler, ignored after dispose:

1. if `restorer?.hasDeferred()`, start a restore pass (`restorer.run()`, failures logged as `offline:restore-pass-failed from=wake`) — this is what re-tries a deferred journal record when the queue is otherwise empty, since then no drain iteration asks the gate;
2. `queue.wake()`, which also resets the re-check backoff.

The wake goes through the controller, never as `OfflineQueueOptions.wakeOn`, for that first step. `withdrawTablePolicy` need not unsubscribe: a wake for a gate no table uses costs one gate check.

### Registration: `offline.allowSoloCommit`

`parseOfflineConfig` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-config.ts`) accepts `allowSoloCommit` (a boolean; anything else refused by name, as for the other keys) instead of refusing it as "arrives with a later stage"; `OfflineMode` passes it to `OfflineQueue` as `allowSoloCommit`. Update the doc comment there.

## Edge cases & interactions

- **Partner away, write in offline mode** → gate closed (`absent-members`), entry queued with `waitingFor: 'cohort'`, nothing sent, nothing committed on either machine. Scenario test.
- **Live read of a `'queue'` table on the machine left alone** → `refreshLive` asks the same gate, skips the refresh, serves the queued row, `readsServedLocally` true. Scenario test (this is the stage-4 review's arm).
- **Partner returns** → the gate's wake reaches the queue through the controller and the entry drains without waiting for the re-check timer. Scenario test, with the registration's `recheck.baseMs` set long enough that only the wake can explain a prompt drain.
- **Gate opened while the partner is still away** (a stale view) → the solo refusal keeps the entry queued. Already pinned at the queue tier by `offline-sync-solo-refusal`'s mesh spec; not repeated here.
- **`expireAfterMs` reached while unreachable** → the entry, never sent, expires and is reported `failed` with the expiry reason (the doc's test plan has waited for this stage's gate to keep an entry unsent). Scenario test.
- **Deferred journal record, empty queue, reconnect** → the wake starts a restore pass that puts the record back. One case in `offline-restore.spec.ts` using a registered stub gate with `onChange` (call its listener by hand). Test.
- **Gate registered after a table took the wrapper** → the wrapper's `onChange` subscription moves to it. By inspection (the scenario registers before the tables are created; say so in the wrapper's comment).
- **`dispose` with subscriptions** → all released; a wake arriving after is a no-op. By inspection.
- **Injected node without `cohortReachability`** → nothing registered, always-open gate, no wake: today's behaviour. By inspection.
- **`allowSoloCommit: true`** → queue built with it; the refusal itself is pinned in db-p2p. By inspection.

## The two-machine scenario

New spec `packages/quereus-plugin-optimystic/test/offline-mode-two-machine.spec.ts`, on the in-process mesh through `mesh-node-harness.ts` (`startMockMesh(2)`, `createMeshDbNode`). Node A's gate is the real `KeyNetworkCohortReachability` from `@optimystic/db-p2p`, built over A's own mesh key network (`mesh.nodes[0].keyNetwork`, which under a partition names B in `absentCohortMembers` — `offline-sync-reachability-gate`), `selfId` A, and an `EventTarget` as its event source; register it on A's factory under `shared:test` before creating tables. "B away" is `failures.partitionSides` (A's and B's views each self-only) plus whatever transport cut keeps A's transactor from reaching B (the mesh failure switches or a `wrapRepo` failure — add a `MockMeshOptions` pass-through to the harness if needed, as the existing ones are). "B returns" is clearing both and dispatching `peer:identify` on A's event target.

Cases: (1) the write queued and not committed alone, the live read served locally with `readsServedLocally`, the prompt drain on return with the row read back on B, `queued` → `submitting` → `committed` once each; (2) `expireAfterMs` while away. This is the deterministic replacement for the race recorded in phase 5 of `packages/db-p2p/test/small-deployment-lifecycle.integration.spec.ts`, for writes made in the mode; leave a pointer there.
