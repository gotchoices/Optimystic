# Blob protocol: wire format, frames and the progress deadline

docs/blobs.md §Moving pieces between machines designs one libp2p protocol, `${prefix}/db-p2p/blob/1.0.0`, that carries several length-prefixed frames per stream: a JSON header first in each direction, then raw piece bytes. It is the first protocol here that does, so it does not use `ProtocolClient` (one JSON request, one JSON reply, one resend on a failed prepared stream).

This ticket builds the pieces that have no node wiring: the protocol id, the wire types and their codec, the errors, the limits, the frame reader and writer, the progress deadline, the dial helper extracted from `ProtocolClient`, and `Libp2pKeyPeerNetwork.peersServing`. The server, the client, the node wiring, the tests and the docs are the next ticket, `feat-blob-protocol-frames-stat-and-get`, which this one unblocks. Nothing here is registered or called yet; exporting it is enough.

Verified against the tree: `MAX_BLOB_PIECE_BYTES` (1 MiB) is exported from `packages/db-core/src/blob/limits.ts`; `parseBlobRef` and `parsePieceId` from `packages/db-core/src/blob/blob-ref.ts`; all reach `@optimystic/db-core` through `packages/db-core/src/blob/index.ts`. `unrefTimer` is in `packages/db-core/src/utility/unref-timer.ts` (db-p2p imports it through `../unref-timer.js`; follow that). The installed `it-length-prefixed` (11.x) supports `maxDataLength` and `onLength` on `decode`.

## Wire

Every frame is an unsigned varint length followed by that many bytes, the `it-length-prefixed` format every other db-p2p protocol uses. A header frame's bytes are UTF-8 JSON (encode/decode with `uint8arrays`' `fromString`/`toString`, as the other services do); a piece frame's bytes are the piece, unencoded.

```ts
/** First and only frame the requester sends. `announce` and `held` are reserved for feat-a-referenced-blob-is-copied-to-its-cohort; they are decoded and answered now so the wire does not change later. */
export type BlobRequest =
	| { kind: 'stat'; refs: BlobRef[] }               // 1..MAX_BLOB_STAT_REFS canonical references
	| { kind: 'get'; pieces: PieceId[] }              // 1..MAX_BLOB_GET_PIECES canonical piece ids, no duplicates
	| { kind: 'announce'; ref: BlobRef; scope: string }
	| { kind: 'held'; ref: BlobRef };

export type BlobLocalHolding = 'whole' | 'partial' | 'none';
export type BlobAnnounceAnswer = 'whole' | 'fetching' | 'declined' | 'not-responsible' | 'unreferenced';
export type BlobRefusalReason = 'busy' | 'malformed';

/** First frame the responder sends. */
export type BlobAnswer =
	| { kind: 'stat'; holdings: BlobLocalHolding[] }  // positional: holdings[i] answers refs[i]
	| { kind: 'get'; held: boolean[] }                // positional: held[i] answers pieces[i]
	| { kind: 'announce'; answer: BlobAnnounceAnswer }
	| { kind: 'held' }
	| { kind: 'refused'; reason: BlobRefusalReason };
```

The decoded request carries branded `BlobRef` / `PieceId` values (from `parseBlobRef` / `parsePieceId`), so a consumer never re-parses. Frame sequences, which the next ticket implements:

- `stat`: requester → `[header]`, closes its write side. Responder → `[header {kind:'stat', holdings}]`, closes.
- `get`: requester → `[header]`, closes its write side. Responder → `[header {kind:'get', held}]`, then exactly one piece frame for each `held[i] === true`, in request order, then closes.
- `announce` / `held`: requester → `[header]`; responder → `[header]`, closes.
- A request the responder will not serve: responder → `[header {kind:'refused', reason}]`, closes. `busy` = over its allowance; `malformed` = the request broke a rule above.

Functions in `blob-protocol.ts`:

- `encodeBlobHeader(value: BlobRequest | BlobAnswer): Uint8Array`.
- `decodeBlobRequest(bytes, peer): BlobRequest` and `decodeBlobAnswer(bytes, peer): BlobAnswer`: `JSON.parse`, then a shape check written out field by field (kind, array-ness, lengths against the caps, element types, no duplicate piece ids, every `held`/`holdings` element of the right literal type). References and piece ids go through `parseBlobRef` / `parsePieceId`. Any failure, the `JSON.parse` one included, throws `BlobProtocolError` (the parse error as its `cause`). Keep each kind's check a small function; no generic schema validator.
- `checkAnswerFits(request, answer, peer): void` — the client-side rule that an answer's `kind` matches the request's (or is `refused`) and its positional array has the request's length; throws `BlobProtocolError` otherwise. Living beside the codec keeps both rules in one file.

Errors, exported from `blob-protocol.ts`:

```ts
export const BLOB_TRANSFER_STALLED_CODE = 'BLOB_TRANSFER_STALLED';
/** No bytes moved on a blob stream for `ms`. Thrown by both ends. */
export class BlobTransferStalledError extends Error { readonly code = BLOB_TRANSFER_STALLED_CODE; constructor(readonly peer: string, readonly ms: number) }
/** The responder answered `refused`. */
export class BlobPeerRefusedError extends Error { constructor(readonly peer: string, readonly reason: BlobRefusalReason) }
/** The other end broke the frame sequence: bad header, wrong kind, a frame over its cap, too many or too few piece frames. */
export class BlobProtocolError extends Error { constructor(readonly peer: string, readonly detail: string, options?: { cause?: unknown }) }
```

**`BlobProtocolError` must not extend `RangeError`.** `it-length-prefixed`'s `decode` wraps its length step (including the `onLength` call) in a `try` that treats a `RangeError` as "the length prefix is not complete yet" and waits for more bytes; any other error propagates. A `RangeError` thrown from `onLength` would be swallowed and the frame read anyway.

## Progress deadline

`packages/db-p2p/src/blob/progress-deadline.ts`:

```ts
/** Aborts `signal` with BlobTransferStalledError when `touch()` has not been called for `ms`. */
export class ProgressDeadline {
	constructor(peer: string, ms: number);
	readonly signal: AbortSignal;
	touch(): void;          // records Date.now(); no timer churn
	stop(): void;           // clears the timer; idempotent; a stopped deadline never aborts
}
```

Built from an `AbortController` and one `unrefTimer`'d `setTimeout` (Hermes has no `AbortSignal.timeout`): `touch` stores the time; when the timer fires it re-arms for the remainder if a touch happened since, and otherwise aborts with a `BlobTransferStalledError(peer, ms)`. So a per-chunk touch costs one assignment. The constructor counts as the first touch. The deadline measures the time between any two chunks of bytes, not between pieces: a slow link that keeps delivering never trips it, a dead one trips it within one `ms`. `ms` will be the node's `LinkDeadlines.responseTimeoutMs` at both ends (default 10 s).

## Frames over a libp2p 3 stream

`packages/db-p2p/src/blob/blob-frames.ts`.

**Reading.** `readBlobFrames(stream, deadline, peer): AsyncIterator<Uint8Array>` returns an iterator of frames. It pipes the stream (libp2p 3's `MessageStream` is `AsyncIterable<Uint8Array | Uint8ArrayList>`) through a pass-through generator that calls `deadline.touch()` on every raw chunk, then through `lp.decode` with `maxDataLength: MAX_BLOB_PIECE_FRAME_BYTES` and an `onLength` callback that throws `BlobProtocolError` when the length about to be read exceeds the cap for the frame's position: `MAX_BLOB_HEADER_BYTES` for the first frame, `MAX_BLOB_PIECE_FRAME_BYTES` after (a counter in the closure). `onLength` runs before any byte of the frame is buffered, so an oversized header is refused at its prefix. Each frame is yielded as soon as it is complete, taken with `Uint8ArrayList.subarray()`, which copies only when the frame spans chunks.

**Callers must read the header and the pieces from ONE iterator** (calling `next()` on it), never `for await … break` and then iterate again: the decoder holds bytes past the frame it yielded, and leaving the loop calls `return()` down the chain, ending the read. Say so in the function's doc comment.

What libp2p queues below the reader is not bounded by it: the stream's async iterator pushes every arriving chunk into an unbounded queue and never pauses, and yamux keeps granting receive window as data arrives. The bound is the request: a `get` names at most 16 pieces, so one stream can deliver at most 16 frames. `stream.pause()` was rejected as the bound: while paused, libp2p buffers incoming data up to `maxReadBufferLength` (4 MiB by default) and then resets the stream, and a yamux window grown past 4 MiB can exceed that, which would reset honest transfers of 1 MiB pieces. Record this as a `NOTE:` at `readBlobFrames`: worst case 16 pieces of 1 MiB queued per stream, 4 MiB for pieces this design writes (256 KiB); revisit (lower `MAX_BLOB_GET_PIECES`, or bound a get by declared child sizes) if memory on a phone shows it.

**Writing.** `sendBlobFrame(stream, payload, deadline, maxDataLength): Promise<number>` (returns the frame's byte length, prefix included, for the client's `wireBytes` count):

```ts
const frame = lp.encode.single(payload, { maxDataLength });
const accepted = stream.send(frame);
deadline.touch();
if (!accepted) {
	await stream.onDrain({ signal: deadline.signal });
	deadline.touch();
}
return frame.byteLength;
```

`encode.single` returns a `Uint8ArrayList` of prefix and payload without copying the payload. `send` returning `false` means the transport's buffer is full; the sender waits for `onDrain` before writing again, cut off by the same progress deadline, so a receiver whose transport stops accepting bytes makes the sender give up after one timeout instead of queueing without bound. This is the rule the first `NOTE:` in `packages/db-p2p/src/cohort-topic/stream-util.ts` says a repeated writer must follow. Add `closeBlobStream(stream, deadline)` beside it: `stream.close({ signal: deadline.signal })`, since `close` waits for unsent bytes to drain.

## Key network: who speaks a protocol

Add to `Libp2pKeyPeerNetwork` (`packages/db-p2p/src/libp2p-key-network.ts`):

```ts
/** Of `peerIds`, in order, those other than this node whose peerStore protocol list includes `protocol`, read through the peer record cache; a peer with no record is left out. */
async peersServing(protocol: string, peerIds: readonly string[]): Promise<string[]>
```

It reads `this.peerRecords.records(...)` as `servingPeersOutside` does. It does not apply the network membership predicate: the fetcher applies `admittedBy` at its one candidate filter (`feat-blob-fetcher-verifies-and-resumes`), and two filters would be two places to keep in step. Add a `NOTE:` that the protocol list it reads can include a protocol a peer merely opened a stream on (libp2p merges each stream's protocol into the remote record; only `repo` and `cluster` are filtered by `filterStorageClaimMerges`), which is harmless for the blob protocol because every build that opens a blob stream also registers its handler (the next ticket registers it on both roles); revisit if a build ever sends on a protocol it does not serve.

## Edge cases & interactions

- **Oversized header or piece frame.** Refused at the length prefix (`onLength` cap per position, `maxDataLength` overall) before allocation. Inspection; the caps are named constants. Pinned by test only through the next ticket's specs.
- **`onLength` throw swallowed.** Only if `BlobProtocolError` were a `RangeError` (see above). Inspection.
- **A JSON header that parses but has the wrong shape**, duplicate piece ids, an empty list, a list over its cap, a malformed reference or piece id → `BlobProtocolError`. Inspection: each kind's check is a short function.
- **Answer whose array length differs from the request, or whose kind differs** → `BlobProtocolError` from `checkAnswerFits`. Inspection.
- **Deadline touched after `stop()`** never aborts; `stop()` twice is a no-op. Inspection.
- **Timer keeps the process alive.** `unrefTimer` on every arm. Inspection.
- **`onDrain` rejected by the deadline** surfaces the deadline's `BlobTransferStalledError` (the signal's reason); callers then `stream.abort(err)`. Inspection here, test in the next ticket.
- **`ProtocolClient` regression from the extraction.** Covered by the existing `protocol-client` and prepared-stream specs; run them.
- **React Native bundle.** `yarn check:rn`.

No new tests in this ticket: the codec and frame helpers are exercised end to end by the next ticket's stall specs and by the fetcher's specs on real nodes, and a unit test of each would restate them.
