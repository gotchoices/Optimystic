# File storage commits groups through a log

Second of three tickets from `file-storage-pays-one-fsync-per-write-group` (GitHub #37); the measurements and the reasons the fsyncs cannot simply be batched at the end are in that ticket's `complete/` record. `write-group-overlay-driver` holds a group's writes in memory and hands them to a `BatchBackend.commit`; this ticket is the file backend's `commit`, built as a write-ahead log. Checkpointing, the shared log for `FileKVStore` and the docs follow in `file-store-checkpoint-and-shared-log`.

## Shape

`FileRawStorage` becomes `KvRawStorage` over `WriteGroupDriver` over a `FileBatchBackend` (`packages/db-p2p-storage-fs/src/file-batch-backend.ts`), which maps each `StoreKey` to its tree path exactly as `FileStoreDriver` does today and writes through a per-directory `FileWriteLog` (`packages/db-p2p-storage-fs/src/file-write-log.ts`). `FileStoreDriver`'s reads, listings, path helpers, colon encoding, legacy raw-colon fallback and the "corrupt JSON reads as missing" guard move across unchanged; its writes go. The public constructor `new FileRawStorage(basePath)` stays synchronous.

**The log** is `<basePath>/write-ahead.log`: a fixed header (magic bytes and a format version byte), then records, each `[u32 payload length][u32 CRC-32 of the payload][payload]`. A payload is one batch: entries of `[u8 kind: put | delete][u16 path length][path, UTF-8, relative to basePath, forward slashes][u32 value length][value]`. Use `zlib.crc32` (Node 22.2 and later; the repo runs Node 24). Every record is written with one `write` call then one `FileHandle.sync` on the log handle, which is held open for the store's life.

**`commit(entries)`**: encode the batch, append it, sync the log, then apply each entry to the tree in order — `fs.writeFile` straight to the canonical path for a put (creating missing directories), `unlink` for a delete (plus the raw-colon sibling, as `unlinkRawColon` does today) — without syncing anything, and resolve. The write-ahead rule: a tree file only ever holds content whose log record is durable, so what survives a crash is the log's durable prefix plus whatever the tree already held, and replay reconstructs it. Resolving after the apply rather than after the sync keeps one overlay: the driver's overlay serves the key until the tree holds it, so no in-process reader sees a half-written file. (Tripwire, `NOTE:` at `commit`: if the apply ever shows up in commit latency, resolve after the sync and keep the unapplied entries readable in the backend.) Remember every path written and every directory created since the log was last truncated in a `dirty` set, for the checkpoint ticket; `fs.mkdir({ recursive: true })` returns the topmost directory it created, and the set must hold that directory's parent too, so a new block's directory entry is synced along with its files.

**Opening** happens on the first operation and is memoized: take the lock, replay, then serve. **Replay** reads the log strictly — wrong magic or version, a length past the end of the file, or a CRC mismatch stops the read before that record, and the records before it are applied in order (puts and deletes are idempotent). Then fsync every file and directory replay touched, truncate the log back to its header, fsync it and `basePath`. A store written by an older build has no log and opens with nothing to replay. A log that fails to open or replay for an I/O reason latches the store failed, as a rejected commit does.

**The lock** (`store-lock.ts`): `<basePath>/store.lock`, created with `wx` and holding `{ pid, hostname }`. An existing lock whose hostname is this machine's and whose pid is alive (`process.kill(pid, 0)`) refuses the open with `StoreLockedError`; otherwise it is stale and replaced. Removed on `close`. This closes the `proper-lockfile` TODO in `FileStoreDriver` with no dependency and no refresh timer; it protects the one case that was ever supported, one machine. Two processes on two machines over one network share were never supported (Invariant 5 in `packages/db-p2p/docs/storage.md`).

**Tree writes no longer use a temp file and a rename.** `atomicWriteFile` stays for `FileKVStore` until the next ticket retires it; `promote` becomes two entries of one record, which is what makes it atomic and durable, closing the three-arm defect the `NOTE:` at `FileStoreDriver.durability` describes (bare rename, bare unlinks, unsynced new directories). Remove that `NOTE:` and the "a single rename on the filesystem backend" words of Invariant P in `docs/repository.md`.

**Registry.** `FileWriteLog` instances are shared per resolved directory (the same string `storeIdentity` uses) with a reference count, so two `FileRawStorage` objects over one directory in one process share one log and one lock rather than deadlocking on the lock or interleaving two writers into one file; each keeps its own overlay, which is why the conformance `reopen` case closes the first store before opening the second. `close()` flushes, releases the reference, and the last release closes the log handle and removes the lock.

## Edge cases & interactions

- Torn final record (crash mid-append): replay stops before it; every earlier group is present. Test by truncating the log file after a flush.
- Crash after the log sync, before the apply: inject a throwing `fs.writeFile`, reopen, and read the group back. Test.
- Group atomicity: a batch whose record never reached the log leaves nothing in the tree (inject a throwing log `sync`). Test.
- A CRC mismatch in the middle of the log is treated like a torn end: stop there, apply what precedes. Test by flipping a byte.
- Replay of a put over an existing newer tree file cannot happen: every tree write has a log record, and the log is replayed in order. State it in the module doc.
- The `getRevision` torn-read `NOTE:` in `FileStoreDriver` says atomic writes make a torn revision impossible; now replay rewrites it instead. Update the note.
- `listBlockIds` must skip `write-ahead.log` and `store.lock`: it already yields only directories holding a `meta.json`. `approximateBytesUsed` now counts the log; harmless, note it.
- Opening a store whose lock names a live pid on this host throws `StoreLockedError` from every operation. Test with the current pid.
- win32: `fsyncDir` skips directory syncs; file syncs still run. The dirty set is still kept.
- A failed `FileHandle.sync` on the log latches the store failed; the next operation throws. Test.
- Two `FileRawStorage` over one directory in one process: share one log, open once. Test via `getStoreIdentity` equality and a single lock file.
