# A blob pin index, and a blob service whose cohort is this machine alone

Two additions to the db-p2p blob services, both needed by the SQL plugin's blob work (`feat-blob-sql-type-and-blob-service`) and neither specific to it. [docs/blobs.md §The node's blob service](../../docs/blobs.md#the-nodes-blob-service) is the design of record.

## Why

Two gaps.

**The SQL plugin must find pins it does not remember.** A pin is held under an owner label, and the plugin's labels name the transaction that holds the reference. After a restart the plugin knows nothing of the transactions that were open before, so it has to read its pins back off the machine; and when a transaction takes over a reference that was pinned outside any transaction, it has to find that earlier pin to let it go. `BlobService` (`packages/db-core/src/blob/service.ts`) can take and release a pin but cannot enumerate one, so nothing can answer either question today.

**Three of the plugin's four transactor kinds have no libp2p node.** `local`, `test` and `mesh-test` (and a host's own custom transactor) build no node, so there is no `node.blobs` to put a blob through. They need a `BlobService` of their own whose cohort is this machine: everything `LocalBlobService` already does, plus an `announce` that keeps the blob rather than rejecting.

## The pin index

New interface in `packages/db-p2p/src/blob/local-blob-service.ts`, beside `BlobFetchStore` and `BlobOwedRecords`:

```ts
/** Reading this machine's pins by owner. Not part of `BlobService`: enumeration is a property of a store, not of the service contract. */
export interface BlobPinIndex {
	/** The owner labels pinned on `ref`, in no promised order; `[]` when this machine holds no readable record for it. */
	pinsOf(ref: BlobRef): Promise<string[]>;
	/** Every (reference, owner) pin whose owner label starts with `ownerPrefix`, in no promised order. */
	listPins(ownerPrefix: string): AsyncIterable<{ ref: BlobRef; owner: string }>;
}
```

`LocalBlobService implements BlobService, BlobPinIndex`, both answered from its `BlobRecordStore`:

- `pinsOf` reads the record through the existing `readableRecord` and returns the `owner` of each `pin` hold. A record that is absent, or that does not decode, answers `[]` — the same "treat it as having none" rule `responsibleRefs` and `durabilityOf` already apply, so one unreadable record cannot fail a caller's pass.
- `listPins` walks `BlobRecordStore.listRefs`, reads each record through `readableRecord` (an unreadable one is logged `record:unreadable` and skipped, as `responsibleRefs` does), and yields each `pin` hold whose `owner` starts with `ownerPrefix`. An empty prefix lists every pin. Carry a `NOTE:` at it: *scans every blob record; if a machine ever holds enough blobs for a prefix query to show up, index pins by owner prefix* — the same tripwire `responsibleRefs` carries.

`NodeBlobService` forwards both to `this.local`, the way `pin` and `unpin` already do, so `node.blobs` satisfies `BlobService & BlobPinIndex` too.

**`pin` of a reference with no record already creates one** (`LocalBlobService.pin` through `recordAfterPin`, which its doc comment states), which is what lets a transaction pin a reference it copied out of another row whose bytes are elsewhere. Confirm that by inspection and change nothing; say so in the handoff.

## A blob service with no libp2p node

New module `packages/db-p2p/src/blob/single-machine-blob-service.ts`, exported from `packages/db-p2p/src/index.ts`:

```ts
export interface SingleMachineBlobServiceInit {
	readonly pieces: IPieceStore;
	readonly kv: IKVStore;
	/** Default `defaultBlobDigest()`, as LocalBlobServiceInit's. */
	readonly digest?: BlobDigest;
	readonly now?: () => number;
}

/**
 * A `BlobService` whose cohort is this machine alone: a `LocalBlobService` for everything except
 * `announce`, which keeps the blob under the `owed` hold and reports durability `local` instead of
 * rejecting (docs/blobs.md §SQL). For a host with no libp2p node — the SQL plugin's `local`, `test`
 * and `mesh-test` transactors, and an application holding blobs beside a non-networked database.
 */
export class SingleMachineBlobService implements BlobService, BlobPinIndex {
	constructor(init: SingleMachineBlobServiceInit);
	/** Schedules the start-up sweep (LocalBlobService.start). */
	start(): void;
	/** Cancels a scheduled sweep and waits for a running one (LocalBlobService.stop). */
	stop(): Promise<void>;
}
```

**By composition over `LocalBlobService`, not by subclassing**, so it depends only on that class's public surface — which already carries everything it needs (`holdOwed`, `holdsWhole`, `durabilityOf`, `setDurability`, `emitDurability`, the `BlobOwedRecords` door). Every member but `announce` is a one-line delegation; `read` delegates by returning the local service's iterable.

**`announce(ref, scope)`**, the only behaviour of its own:

1. Refuse a scope the wire would refuse, exactly as `NodeBlobService.announce` does: `blobScopeProblem` (`packages/db-p2p/src/blob/blob-protocol.ts`) and a `RangeError` naming the problem. A recorded scope is then always one a networked node could send, so a host that moves from this service to a node has nothing to re-check.
2. `local.holdOwed(ref)`. That creates the record when there is none and flushes, so the blob survives a restart with a hold no sweep removes. There is nobody to copy to, so nothing ever releases this hold here; `feat-unreferenced-blobs-are-reclaimed` releases it when the reference stops being listed, exactly as it releases a networked node's owed entry whose cohort never fully holds the blob ([docs/blobs.md §Lifetime](../../docs/blobs.md#lifetime), *An owed blob follows the same rule*).
3. If `local.durabilityOf(ref)` already answers something, this is a re-announce: stop here, emitting nothing. (The stored class is what keeps a restart from re-emitting, the same mechanism `BlobRecord.durability` serves for a networked node.)
4. Otherwise build the class: `quorum` `local`, `accepting` 1, `unconfirmed` `[]`, and `confirmed` 1 when `local.holdsWhole(ref)` and 0 otherwise. `local` is right by the order of the rule in `classifyBlobDurability` (`packages/db-p2p/src/blob/blob-durability.ts`): "no other member accepts blobs" is decided before any arithmetic, so a cohort of just this machine never reads as a strict majority of itself. Then `local.setDurability(ref, durability)` and `local.emitDurability({ ref, durability })`, in that order, so a listener never sees a class the record does not yet hold.

   Carry a `NOTE:` at step 4: *`confirmed` is computed once and never recomputed — nothing on a single machine can make an incompletely held blob whole, so a reference announced before its bytes arrived stays `confirmed: 0`. A caller that puts a blob and then announces it always records 1.*

`stat` needs no override: `LocalBlobService.stat` already returns the record's `durability`, so an announced reference reports `local` from then on.

Log the announce under the `blob:store` namespace (`LocalBlobService`'s; this module takes its own logger with the same namespace): `blob:announce-single-machine ref=… scope=…`, one line per first announce.

## Edge cases & interactions

- **`announce` of a reference this machine does not hold.** Accepted: the `owed` hold is taken and the record created, `confirmed` is 0. This is the "a row references a blob whose bytes are elsewhere" case, and on a single machine the bytes are simply not there. Covered by the `confirmed` arm above and by inspection.
- **Re-announce under a different scope.** The `owed` hold carries no scope (only `responsible` does), so a second announce under another scope changes nothing but the hold's `at`. Deliberate: a single machine never re-announces to anyone, so the scope is not needed after the refusal check. Inspection.
- **`unpin` of the last pin on an announced blob.** The record survives on its `owed` hold and the blob is not swept. Pinned by the spec below — it is the property the SQL plugin's commit path depends on, since that path unpins a reference's transaction pin right after announcing it.
- **A record left with no hold at all.** `BlobRecordStore` deletes such a record and the sweep removes its pieces; nothing here changes that.
- **`listPins` against concurrent writes.** `listRefs` is a point-in-time listing and each record is read after it, so a pin added during the walk may be missed and a pin removed during it may be yielded. Documented on the interface ("in no promised order"), and every caller re-reads before acting. Inspection.
- **An unreadable record.** `pinsOf` answers `[]` and `listPins` skips it, so a malformed record cannot fail a caller's whole pass — but that blob's pins are then invisible, which is why `BlobRecordFormatError` already stops the sweep for it ([docs/blobs.md §Holds](../../docs/blobs.md#holds)). Inspection.
- **`start`/`stop` not called.** The sweep timer is an unref'd timer (`armUnrefTimer` in `packages/db-p2p/src/unref-timer.ts`), so a service nobody starts simply runs no start-up sweep and a service nobody stops holds nothing open. Both are forwarded so a host that owns the lifecycle can use them. Inspection.
- **Pieces and records of differing durability.** A persistent piece store over in-memory records loses every pin at restart and the next sweep deletes every piece; a persistent record store over in-memory pieces reports blobs it cannot serve, which `stat` corrects (`correctRecord`). Neither is detectable from the two interfaces, so this is documented on the caller's option in `feat-blob-sql-type-and-blob-service`, not checked here. Inspection.

## Tests

`packages/db-p2p/test/single-machine-blob-service.spec.ts`, over a `MemoryPieceStore` and a `MemoryKVStore`. Reuse the construction `packages/db-p2p/test/local-blob-service.spec.ts` already uses (lift its helper into a shared one if it has one worth sharing) rather than writing a second one. Two cases, both on branching logic:

- **Announce once.** `put` a few bytes under an owner, subscribe `onDurability`, `announce(ref, scope)`: exactly one event, `quorum` `local`, `confirmed` 1, `accepting` 1. Announce the same reference again: no further event. Then `unpin(ref, owner)` and expect `stat(ref)` to still report `locality` `here` with `durability.quorum` `local` — the blob is held by its `owed` hold alone.
- **A scope the wire would refuse.** `announce(ref, '')` rejects with `RangeError`, and the record gains no `owed` hold (`stat(ref).durability` is still undefined).

No separate spec for `pinsOf`/`listPins`: they are a projection of `BlobRecord.holds` with no branching beyond the unreadable-record skip the existing readers already share, and `feat-blob-sql-type-and-blob-service`'s pin-label spec reads its pins through `pinsOf`. If the implementer finds a behaviour here that is not obvious from the record shape, add the case rather than a file.
