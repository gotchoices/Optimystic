# A consensus round stops waiting once its outcome is decided

Reported as GitHub #64 (VoteTorrent, `@optimystic/db-p2p` 1.27.0). Maintainer decision 2026-11-17: take it. Builds on `a-decided-promise-map-is-never-extended`, which makes a late answer safe to receive (a member answering a decided record signs over the decided promise map, and the coordinator places a commit signature only in a record whose promise map it was signed over).

## What happens today

`ClusterCoordinator.collectPromises` sends the promise request to every remote cohort member and awaits `Promise.all` over them, each request carrying `promiseImmediateRetries` in-line retries; the super-majority is counted by `executeTransaction` only after every request settled. `collectCommits` and `broadcastMergedRecord` also `Promise.all` over their members. So a member that is connected but does not answer costs every round its whole RPC deadline times its attempts, even when the rest approved in milliseconds. Measured by the reporter on a real relay, the same election with and without one silent emulator phone in the control cohort: key release 1.5 s against 298 s, results publish 0.18 s against 77.6 s, median control write 0.47 s against 75 s.

## Requirement

Each of the three rounds resolves as soon as the answers in hand decide it, and waits while they could still go either way. Members not yet answered when a round resolves — **stragglers** — are owed the record and keep getting it in the background through the existing commit-retry machinery. A straggler's answer that arrives after the round resolved is received and recorded — its apply report, its commit signature when it was signed over the record's promise map, whether it is still owed anything — but its promise is never merged, and neither its slowness nor its eventual failure is reported to reputation.

## Design

### Deciding a round

A small module, `packages/db-p2p/src/repo/round-decision.ts`, holds the mechanism, so `cluster-coordinator.ts` (already past 2000 lines; backlog `debt-cluster-coordinator-owed-delivery-outgrew-its-file`) does not grow by it:

```ts
/** A round's answers, split at the moment its outcome was decided. */
interface DecidedRound {
	/** Settled before the decision, in the order they settled. */
	answered: MemberDelivery[];
	/** Still in flight at the decision. Each settles to a MemberDelivery; never rejects. */
	stragglers: Map<string, Promise<MemberDelivery>>;
}

/** Resolve once `decided(answered, outstanding)` is true, or nothing is outstanding. */
function awaitDecision(requests: Map<string, Promise<MemberDelivery>>,
	decided: (answered: readonly MemberDelivery[], outstanding: number) => boolean): Promise<DecidedRound>;
```

`MemberDelivery` and `deliver` (which never throws) move with it or are imported; the promise round switches from its `Pending` + catch to `deliver` so every round speaks one shape. Each round supplies its own predicate:

| Round | Decided when | Out of reach when |
|---|---|---|
| promise | approved promises in the merged map ≥ `ceil(n × superMajorityThreshold)` | approvals + outstanding < that |
| commit | `hasCommitMajority(record)` over the merged commits | commits + outstanding < `floor(n × simpleMajorityThreshold) + 1` |
| consensus broadcast | holders ≥ strict majority of `record.peers` | possible holders < strict majority |

The local member is never a straggler: the prevote, the presign and the broadcast's local delivery stay awaited before any remote decision, so every predicate already knows this node's vote and verdict.

**Holders** in the broadcast: this node's member when its retained verdict says it holds the record, plus each remote member whose latest report (this delivery's answer, else `record.applyOutcomes`) says so. For a commit record "holds" is `commit.success === true`, the test `CoordinatorRepo.commit`'s gate applies; for a pend or cancel record it is `executed === true` with no pend refusal on the entry (a member on an older build never sets `executed`, so a pend broadcast to it waits as today). **Possible holders** add the outstanding members, and this node's member when it applied but is not yet a holder (its second reconcile, `reconcileLocalMemberAgain`, can still make it one). Count the majority with the same function the gate uses: move `isDurableMajority` out of `coordinator-repo.ts` into the new module (or another module both import without a cycle) and call it from both. That is what keeps "finishing early" from shrinking what the gate can see below a majority: the broadcast returns only once the gate's own count is met, or once no outstanding answer could meet it.

After the broadcast decides, run the existing second-reconcile step (`localMemberHasApplied && remoteMemberHolds`) against the answers in hand, as today.

### What each round sends, and to whom

- **Promise round:** unchanged targets. On a decision, classification in `executeTransaction` (rejected by validators, conflict race lost, blocks held, shortfall, disputed) uses the votes in hand. `PromiseShortfallError.silentPeers` keeps its formula (`promises[peerId] === undefined`), so it names members merely outstanding at an early "out of reach" decision too; say so in its doc. The abandonment broadcast is still sent only when the votes in hand prove the transaction dead (`refusalsProveUnreachable`).
- **Commit round:** every remote member this node does not have a request riding to right now — not the presigned self, and **not a promise-round straggler still in flight.** Sending a straggler the commit round while its promise request is still in flight lets the two arrive in either order; a commit-round record processed first makes the member sign and clear the transaction, after which the stale promise request plants a fresh reservation (`activeTransactions`) that nothing clears until the broadcast. Super-majority ≥ simple majority, so the members that answered the promise round can carry the commit majority alone.
- **Consensus broadcast:** `membersAwaitingConsensus` of the commit round's answers, plus every owed straggler no request is riding to.

### Stragglers are owed the record

Rename `ClusterTransactionState.carrying` to `inFlight` and widen its meaning: a request is taking this record to the member right now — a straggling round request, or a carried one (`takeOwedRecords`). Every rule that reads `carrying` today (the retry run's skip, `takeOwedRecords`' in-flight mark) then covers stragglers with no new case. Add `state.stragglers: Set<string>` — every member a round left behind.

Each straggler's promise gets a continuation that settles its answer:

- Clear its `inFlight` mark; log `cluster-tx:straggler-answer` (`phase`, `success`, `error`, and for a promise answer its vote type). No reputation call either way.
- **Before the retry is armed** (the rounds are still running on their own copy of the record, and `updateTransactionRecord` would overwrite anything written into `state.record`), buffer the delivery on the state (`state.lateAnswers`). The step that arms the retry folds the buffered answers in first.
- **After the retry is armed**, fold it directly, as `settleCarriedDelivery` does for a carried record: merge the member's own commit through the equal-map rule from the prerequisite ticket, merge its apply report (`mergeApplyOutcomes`, `latePendRefusals.retain`), and decide whether it is still owed. A broadcast answer settles the member (this node's member applied first, the reasoning `settleCarriedDelivery` already records); a promise or commit answer settles it only when `membersAwaitingConsensus([answer])` is empty, i.e. it reports having applied without a refused commit. A settled member leaves `pendingPeers`, and when it holds and this node's member applied, `void reconcileLocalMemberAgain` as `settleCarriedDelivery` does. A retry left with nobody pending finishes, unless a run is in progress (`retry.running`). A late commit that completes a majority the round fell short of is left to the next retry run, which already broadcasts once `hasCommitMajority` holds.
- No state (the transaction was released): log only.

**Arming.** Wherever the rounds end (`deliverConsensus`, the no-majority branch of `commitTransaction`, `deliverDecidedWithoutCommitRound`'s deferral), the missing set is the round's failures plus every straggler not settled by a buffered answer. A transaction with stragglers therefore always has a retry, so `executeClusterTransaction`'s `finally` does not release it, and the persisted coordinator state lists the stragglers for `recoverTransactions`.

**The retry run must not spend its budget on in-flight members.** `runRetry`'s own NOTE ("a timer that fires while every pending member's delivery is riding elsewhere sends nothing and still spends an attempt … re-arm without counting the attempt") has tripped: a silent straggler's request routinely outlives the whole default budget (250 ms doubling, five attempts, about 7.75 s), after which the transaction is released and the straggler is never delivered. When a run sends to nobody because every pending member is in flight, re-arm at the same attempt and interval instead of calling `scheduleCommitRetry`. The wait stays bounded: every in-flight request ends at its RPC deadline (`rpc-deadline.ts`), after which the member is sent the record and attempts count again. Replace the NOTE with the rule.

### Where it can help (for the docs)

At the default threshold 0.75, a cohort of two needs both promises and a cohort of three needs all three, so the promise round finishes early only from four members up (one straggler at four through seven members, two at eight). The commit round and the broadcast need a simple majority, so they can finish early from three members up. A two-member cohort gains nothing — and its request count, three per write, must not change. Whether this fixes the reporter's case depends on their control cohort's size; state the table plainly so they can tell.

## Edge cases & interactions

- **Cohorts of two and three.** Two: every predicate needs every member; behaviour and request counts unchanged. Verified by `packages/quereus-plugin-optimystic/test/two-node-write-request-count.spec.ts`. Three: the promise round waits for all; the commit round finishes on the first remote commit (presign plus one), and that member applied on receipt; the broadcast then needs no remote target. Verified by the existing `commit-round-carries-coordinator-commit-vote.spec.ts` and `commit-durability-quorum.spec.ts` staying green.
- **Undecided round with a straggler.** Four members, one rejects, one hangs: approvals 2 + outstanding 1 can still reach 3, so the round waits. Verified by a unit test (below).
- **Early "out of reach" promise decision.** Classified on the votes in hand; a straggler's later approve leaves a reservation on that member until its staleness sweep — exactly what a coordinator timeout leaves today. Verified by inspection.
- **Late reject, conflict or held vote after an approval decision.** Not merged, not disputed, logged. Safe by quorum intersection (Theorem 1). Verified by inspection; state it in `correctness.md`.
- **Durability gate.** The broadcast's count is the gate's function; an outstanding member that could not change the gate's answer is not waited for. A straggler that applies later is the residual `correctness.md` already names ("a member reached only by a later delivery may land the refused revision later") — extend that sentence to name round stragglers. Verified by the mesh test's commit being acknowledged with a straggler outstanding.
- **Deferred pend delivery (two members), owed records, escorted pends.** `mayDeferPendDelivery` is two-member only and unaffected. A straggler with a pend in flight is skipped by `takeOwedRecords` for ordinary carriage (it is `inFlight`), but an action's commit still escorts its owed pend to it; the member dedups the second copy (`ClusterMember.update` serialises per `messageHash`). Verified by inspection and the carried-delivery specs staying green.
- **Late pend refusal.** A straggler that refuses a pend at apply reports it after `CoordinatorRepo.pend` answered; `latePendRefusals.retain` keeps it for the action's commit, and `validateCommitAgainstRefusedPend` keeps that member from co-signing — the existing late-delivery path. Verified by inspection.
- **Reputation.** A member that fails before its round decides is penalised as today (the round needed it). A straggler is never penalised, whatever it eventually answers. Verified by the mesh test.
- **Concurrent settlement.** A straggler's continuation may run while the rounds are still running (buffered), during a retry run (`running` defers the finish), or after release (log only). Verified by inspection; the unit test for the budget below exercises the post-arm path.
- **Recovery.** Stragglers are in the persisted `pendingPeers`; after a restart they are delivered by the resumed retry. Verified by inspection.
- **Reported cohort sizes.** `packages/db-p2p/test/transaction-node-count-sweep.spec.ts` reports per-size behaviour; it must stay green and its table should not change for healthy cohorts.

## Tests

- **Mesh, four members, one silent (new spec `packages/db-p2p/test/a-silent-member-does-not-hold-up-a-write.spec.ts`).** `createMesh(4, { responsibilityK: 4, clusterSize: 4 })`; hold every `onClusterDelivery` to member D on a gate promise. A write (pend then commit) completes and is acknowledged while the gate is still closed, well inside one RPC deadline; no `ConsensusTimeout` (or any penalty) is reported against D. Then open the gate: D ends up holding the committed revision without any further write.
- **Unit, `cluster-coordinator.spec.ts`: an undecided round waits.** Four members; one fake rejects at once, one hangs on a controllable promise: `executeClusterTransaction` has not resolved while the hang is held, and resolves once it answers.
- **Unit, `cluster-coordinator.spec.ts`: an in-flight straggler is not given up on.** With the injected clock, a straggler whose request stays in flight past the whole retry budget is still sent the record once its request settles (the transaction is not released with it pending).
