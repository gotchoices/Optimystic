# A blob's owed copies are drained

docs/blobs.md §Placement, copying and durability, "Copying" and "Durability". `announce(ref, scope)` makes this node owe the blob to its cohort until every member that accepts blobs holds it. The prereq built the durable entry, the classification and the record door; this ticket builds the drain that announces to the owed members on the shared `DrainScheduler`, the `announce` entry point, the durability events, and the `held` path back into the entry. With it, a committed reference survives the writer going offline once the cohort holds it. The reaction to cohort changes for blobs already held is the next ticket, `feat-a-referenced-blob-is-copied-to-its-cohort`.

Events reach listeners through `BlobOwedRecords.emitDurability`, which is `LocalBlobService`'s own listener set — so `LocalBlobService.onDurability` and `NodeBlobService.onDurability` need no change and no late binding.

### The cohort view

```ts
private async cohortView(ref: BlobRef): Promise<BlobCohortView>
```

`findCluster(routingKeyForBlob(ref))` (a throw, or an answer naming nobody, → `{ resolved: false, accepting: [] }`, logged `cohort:unresolved`), plus `absentCohortMembers?.(routingKeyForBlob(ref))` — absent members are counted as owed, exactly as a block write counts them, because a member that is offline still owes a copy. `deps.acceptance` over the members other than this node classifies each; a member is in `accepting` when

- it is this node and `deps.hold === 'eager'` (an `on-demand` node takes nothing it is merely responsible for, so it does not count itself), or
- it is another member whose acceptance is not `refuses` and that `isDeclining` does not name. An `unknown` acceptance counts: an unidentified member is owed until it is known not to take blobs.

Absent members are classified like any other: `absentCohortMembers` returns serving peers outside the band, which the peer-record cache knows, so a `refuses` among them is still dropped.

### One entry

Given the scheduler's `DrainEntryContext`:

1. `view = await this.cohortView(entry.ref)`.
2. `durability = await this.settleRef(entry.ref, view)` — the one serialized transition, below.
3. `!view.resolved` → tally `unrouted`, stop.
4. `durability === undefined` → the entry left the ledger while the pass ran (`settleRef` found none): log `entry:vanished`, `context.forgetEntry()`, tally `gone`, stop.
5. `durability.quorum === 'full'` → `settleRef` has already finished it: `context.forgetEntry()`, tally `full`, stop.
6. `others = view.accepting` minus this node; empty → tally `solo`, stop. Nothing is counted against anyone.
7. `owed = others` minus `entry.holders`; `reachable = context.reachable(owed)` empty → tally `waiting`, stop. (`reachable` drops absent members, since they are not connected, and peers abandoned for this entry.)
8. Announce to each reachable peer **in turn** and act on the answer:
   - `whole` → collect as a holder; `noteSuccess`; `onHolderConfirmed`.
   - `fetching` → `noteSuccess`; nothing recorded (its `held` will come).
   - `declined` → `noteDeclined(peer)`; `noteSuccess`.
   - `not-responsible`, `unreferenced`, or a rejected call (a stalled or reset stream, `BlobPeerRefusesError`, a malformed id) → `noteFailure(peer)`; the scheduler abandons the peer for this entry after `maxAttempts` until it reconnects.

   Each answer is logged `announce:answer ref=… peer=… answer=…`, each rejection `announce:unreachable ref=… peer=… err=…`. Tally `announced`.
9. With at least one collected holder: `await ledger.addHolders(ref, collected)`, then `settleRef(ref, view)` again against the same view; at `full`, `forgetEntry` and tally `full`.

Sequential, not parallel: the receiver's `AnnounceLimiter` bounds announcements per peer per minute and its reference read holds one of four read slots, so a pass that fans out would mostly queue behind that. A pass therefore costs at most one round trip per owed member, bounded by the cluster size. No per-announce timer is added: both ends already abort a blob stream that moves no bytes for one response timeout (`client:stalled`), which is the budget `BlobProtocolClient.announce` runs under.

Leave this `NOTE:` at the `fetching` arm: *a peer that answered `fetching` is re-announced every pass until its `held` arrives, one small request per pass; if a stuck pull ever makes that show up, stop announcing to a peer that answered `fetching` within the last n passes.*

### `settleRef` — the one durability transition

Every path that can change a blob's durability goes through one method, serialized per ref by the drain's own `KeyedSerialQueue` (keyed on the ref). Without that single point, a `settle` driven by an incoming `held` and a pass computing at the same time can both decide the class changed and emit the same value twice.

```ts
/** Classify from `view`, persist and emit on a change, finish at `full`. Undefined when there is no entry. */
private settleRef(ref: BlobRef, view: BlobCohortView): Promise<BlobDurability | undefined>
```

Inside the queue, in this order:

1. `entry = await ledger.get(ref)`; `undefined` → return `undefined`. A blob with no entry is not owed, so nothing is written or emitted (this is also what makes a `held` for an already-finished blob a no-op).
2. `holders = new Set(entry.holders)`, plus `selfId` when `await records.holdsWhole(ref)`.
3. `next = classifyBlobDurability(view, holders, selfId)`.
4. `changed = !sameDurability(await records.durabilityOf(ref), next)` — equal when `quorum`, `confirmed` and `accepting` match; `unconfirmed` is derived from the same inputs, so it never differs alone. A local `sameDurability` helper, not a deep compare.
5. `changed` → `await records.setDurability(ref, next)` (flushed), logged `durability:changed ref=… quorum=… confirmed=…/…`.
6. `next.quorum === 'full'` → `await ledger.delete(ref)`, then `await records.releaseOwed(ref)`, logged `entry:full ref=…`.
7. `changed` → `emitDurability({ ref, durability: next })`.

The `full` order is deliberate: the record's `full` durability is written, the entry is deleted, and only then is the `owed` hold released. A crash between steps leaves at worst an `owed` hold with no entry, which keeps the bytes — the safe direction — and `feat-unreferenced-blobs-are-reclaimed`'s pass covers an orphaned `owed` hold as it covers an orphaned entry. Releasing the hold may delete the record outright when `owed` was its last hold, taking the just-written durability with it; that is the intended end state (the writer stops holding the blob on the others' behalf) and is why `stat` on such a blob afterwards reports `unknown` with no durability.

`settle(ref)` is `settleRef(ref, await this.cohortView(ref))`. `owe(ref, scope)` is `await ledger.record(ref, scope)`, then `settle(ref)` so the first event fires before it resolves, then `scheduler.wake()`. `noteHeld(peerId, ref)` is `await ledger.addHolders(ref, [peerId])`; with an entry returned it calls `onHolderConfirmed` and `settle(ref)`, and with none it logs `held:not-owed` and does nothing else.

### Declining peers

A per-peer in-memory `Set<string>`: a node declines because of its own `blobs.hold`, not per blob. Cleared for one peer by the scheduler's `onPeerReturned`, which fires when that peer's only connection opens. While remembered, the peer is not owed and does not count as accepting.

The `NOTE:` on `blobAcceptanceOf` in `packages/db-p2p/src/blob/accepts-blobs.ts` warns a caller that remembers `refuses` across a connection to clear it on `peer:identify` too. It does not apply here and the implementer should not act on it: what is remembered is `declined` — the peer's own answer about its policy, which identify cannot change — while `refuses` is recomputed from the key network's peer-record cache on every pass.

## Edge cases & interactions

- **Two of five accepting members hold it** → `local` with `confirmed: 2`. Pinned by the prereq's classification test; this ticket's drain spec sees the event sequence.
- **This node is the only accepting member** — every other member refuses the protocol, is remembered as declining, or none exists: the class stays `local`, the entry and the `owed` hold stay, and passes tally `solo`. Drain spec.
- **An on-demand peer** answers `declined`, is remembered until it reconnects, is neither owed nor counted meanwhile, and is asked again after its connection reopens. Drain spec.
- **Different cohort views.** A peer this node counts answers `not-responsible`: not remembered as declining, counted under the give-up rule, asked again next pass, abandoned after `maxAttempts` until it reconnects. Drain spec.
- **Announce before the receiver sees the commit** → `unreferenced`, then `fetching` once the receiver's read sees it. Two-node spec. A slow committed-state read on the receiver also arrives here as `unreferenced` (`announce:read-slow` on the receiver), which the drain treats identically — it asks again.
- **Restart mid-copy.** The entry and the `owed` hold are on the node's store; the scheduler's start pass resumes announcing, and the receiver's `BlobAnnounceReceiver.resume` finishes its pull from the pieces it lacks. Two-node spec.
- **Partition.** No pass runs while `detectPartition()` is true: the scheduler returns `skipped: 'partition'` before it reads the ledger. Already pinned by the block drain's suite; inspection here.
- **No eligible peer at all.** The scheduler returns `skipped: 'no-eligible-peer'` without reading the ledger, so no durability is recomputed that pass. The first event still always fires, because `owe` emits directly rather than waiting for a pass. A cohort that changes while nothing is connected is re-read on the next pass; reacting to a cohort change for a blob already held is `feat-a-referenced-blob-is-copied-to-its-cohort`. Inspection.
- **Non-members** are never eligible (the scheduler's membership filter), and a `held` from one is dropped by the node's `onHeld` closure before the drain sees it. Inspection.
- **A member without the blob protocol**: acceptance `refuses`, so neither announced to nor counted. Unidentified: counted as owed but not eligible for this pass (the scheduler's `protocol` filter), so it is announced to once identify lands and the `peer:identify` trigger fires. Inspection.
- **A `held` for a finished blob, or from a peer outside the cohort.** No entry → `held:not-owed`, ignored. Outside the cohort → recorded as a holder but not counted, since `accepting` comes from the cohort. Inspection.
- **A holder count that changes without a class change** (three of seven, then four — still `majority`): an event fires, because `confirmed` changed. The two-commit pattern (`feat-sql-columns-hold-blob-references`) waits on the class, not the count, so an extra event costs it nothing. Inspection.
- **Concurrent `owe`, `noteHeld` and a pass on one ref.** Ledger writes are serialized per ref by the ledger; the durability transition is serialized per ref by `settleRef`'s own queue, so no value is persisted or emitted twice and the pass re-reads the entry inside it. Inspection — the one-queue design is the fix, so there is nothing a test could pin that the design does not.
- **`announce` called twice with different scopes.** The second `record` replaces the scope and keeps the holders, so the next pass verifies against the newer tree; any listing scope authorizes a receiver to hold the blob. Inspection.
- **`announce` on a node whose copy drain is disabled** (`blobs.copy.enabled: false`): `oweCopies` is absent, so it rejects rather than silently recording nothing. Say so on the option. Inspection.
- **The block drain is untouched.** Its suite passes with no test body edited; only its spec's `MockLibp2p` moves out to be shared.
