Stage 5 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages), part three of three: reading the journal part two (`offline-sync-journal-store`) writes and putting the entries back, through the `OfflineQueue.restore` and `Collection.restoreSealed` / `Collection.holdsCommitted` operations part one (`offline-sync-journal-port`) added. Read both earlier tickets' "Records" and "Restore" sections first; this ticket does not restate them.

## When restore runs

`plugin.hydrate(db)` runs `OptimysticModule.hydrateCatalog` as today and then `plugin.offline.restore()`, so the application's first statement after `hydrate` sees its queued transactions. `restore()` is also public under `plugin.offline`, for a host that does not call `hydrate`, and can be called again at any time (it is idempotent: a record already restored is skipped by id; a deferred one is retried). It refuses to run while a transaction is open on the bridge (`TransactionBridge` already knows; throw a plain error naming the rule — the open segment belongs to that transaction, and `restoreSealed` refuses over a non-empty open segment for the same reason).

## The pass

`OfflineRestore` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-restore.ts`, owned by `OfflineMode`, runs one pass at a time (a second call while one runs awaits it). A pass:

1. Lists `…/entries/`, `…/drives/` and `…/outcomes/` under the label once, sorts entry keys as strings (queue order by zero-padded `seq`), and loads the outcome records into the controller's retained map (pruned by `at` against `outcomeRetentionMs`; a record past the window is deleted).
2. For each entry record, in order, that the queue does not already hold:
   - **Settled already** (an outcome record exists for its transaction id, from a delete that never flushed): delete the entry and drive records, continue.
   - **Unknown version** (`v` other than 1 on the entry or drive record): stop the pass and throw `OfflineJournalError` with reason `'unknown-version'`, the key and the version, leaving every record untouched. Entries before it in order are restored. The host sees a loud failure out of `hydrate` that says the journal was written by a newer build; nothing is dropped. Document the choice: skipping would drain later entries ahead of one the design says must go first, and dropping would lose an acknowledged change.
   - **Resolve its tables.** For each segment, the module instantiates and initializes the table the record names (a new module method, `collectionsOfTable(db, table)`: `lookupOrInstantiate` from the engine's catalog, `OptimysticVirtualTable.initialize`, then the table's collections from `TransactionBridge.collectionsOf` resolved through the bridge's registry — the instance every statement reads and stages through, `this.collection` and the index trees `registerCollections` registers). The segment's `collectionId` must be one of them; otherwise the record is treated as **deferred** (below) and logged `offline:restore-collection-mismatch`.
   - **Deferred** when a table is not in the engine's catalog (dropped by another machine while this one was down, or not yet declared by a host that restores before `apply schema`), or when initializing or opening it throws `BlockUnavailableError` (its base blocks cannot be read: this machine never held them and the cohort cannot be reached). The pass stops here: this record and every record after it stay journaled, unrestored, so the queue keeps its order. Logged `offline:restore-deferred table=… reason=…` once per pass per record. Any other error out of initialization propagates out of `restore()` (and `hydrate`): a corrupt catalog or a programming error is not a reason to wait.
   - **Restore.** Build the `RestoreInit` from the two records (the drive record supplies `drive`; absent, none) and call `queue.restore(init, stage)`, where `stage(collection)`: if the drive record names an attempt for this collection and `collection.holdsCommitted({ actionId, rev })` is true, answer `already-committed`; if the drive record lists the collection in `committed`, answer `already-committed` too (nothing to stage: the queue records it from `drive.committed`); otherwise `collection.restoreSealed(entryId, actions, position)` with `position` the first entry in `queue.entries()` after this one, by `seq`, that names this collection, or `'last'`, and answer `staged` with the returned refusal. `BlockUnavailableError` out of `restoreSealed` (the replay reads blocks) propagates out of `stage`, which the queue rolls back; the record is then deferred like an unreadable table, and the pass stops.
3. Publishes the queue state once at the end and resolves.

The deferred set is kept on the controller: the ordered list of records not yet restored, with the reason. It is re-tried by another pass, which runs:

- on every `restore()` call;
- after a table's vtab finishes a full initialization or a live refresh that reached the cohort (`refreshLive`'s `reachedCohort` arm in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`, and the point where `publishOfflinePolicy` runs after `doInitialize`), when that table is named by any deferred record — through a controller method the vtab calls, which schedules a pass off the statement's path (never awaited by the read; a pass must not run inside a transaction, and it checks that before starting);
- from the controller's reachability gate (`OfflineMode.reachability`), asked by the queue before each submission: while records are deferred, the gate first runs a pass and then answers `false` if any remain, so the queue's re-check timer is also the restore's retry timer and nothing queued after the restart is submitted ahead of an older entry that is still on disk. State the consequence: such an entry reports `waitingFor: 'cohort'`, the closest existing value, and the reason is in the log line. Stage 6's connection wake reaches this through the queue's gate re-check as well (noted in that ticket).

## What the application sees

- `entries()` lists deferred records too, after the queue's entries, each as `queued` with `waitingFor: 'restore'` (a new value on the PLUGIN's status type only: `waitingFor: EntryWaitingFor | 'restore' | undefined` in `offline-status.ts`; db-core's type is unchanged), `tables` from the record, `attempts` 0 or 1 by whether a drive record exists, `inDoubt` likewise, `persisted: true`. `status(transactionId)` answers the same for a deferred id.
- `discard(transactionId)` of a deferred record that is not in doubt deletes its records and emits `failed` with reason `discarded` and empty `changedTables` (nothing was staged, nothing is announced). One in doubt is refused with `EntryNotDiscardableError('in-doubt')`, as a queued one is: a change the network may hold is not withdrawn on this machine's say-so. A dropped table with an in-doubt record is therefore stuck until the table exists again or the record is removed by hand; log it once as `offline:restore-stuck` and record the limit as an accepted tradeoff `NOTE:` at the discard site, with the revisit condition "if it is ever hit in the field, teach the restore to resolve the attempt from the collection's log without the table".
- `whenDrained()` resolves only when the queue is empty AND no record is deferred; a deferred record keeps it pending until a later pass restores and drains it (or `dispose` rejects it).
- `hasQueuedEntries()` (read by `TransactionBridge.offlineRoute` for the behind-queue route) counts deferred records: a network-acknowledged commit made while anything is deferred waits behind the queue as it would behind a queued entry.
- `assertNoQueuedEntries` (the DDL gate) also refuses while a deferred record names the table: an index built now would miss the rows the record carries.
- `degradesLiveReads(name)` answers `false` for a table named by a deferred record: serving such a table from this machine's view would show it without rows the application was told are committed, so a read of it fails while the cohort is unreachable, as the design says ("until then, reads of the table fail as they would without the mode"), and the first read that reaches the cohort triggers the pass.
- A restored entry's `queued` status is emitted during the pass, before `hydrate` returns, so a listener registered before `hydrate` hears it; one registered after reads `entries()`.

## Edge cases & interactions

- **Crash after the network commit and before the journal delete.** Node A's journal and node store both over deferred-sync stores (`PowerLossKVStore({ deferSync: true })` and `KvRawStorage(new WriteGroupDriver(new MemoryBatchBackend({ deferSync: true })))` through `createMesh`'s `rawStorageFactory`), node B over plain memory. Commit offline on A, let it drain, `powerLoss()` both stores, restart A (below), register a fresh `Database` over the reopened journal, `hydrate`: the entry is reported `committed` once (durability with `undefined` classes, `followed: false`), nothing is sent (B's pend count unchanged), the row is on both nodes, and B's log holds one entry under the recorded action id (`entriesUnder` from the db-core spec helpers). Two variants, both pinned: A's node store flushed the commit before the loss (the collection on A holds the attempt — `holdsCommitted` true) and A's node store lost it (A opens its stale replica, the segment is re-staged in doubt, the drain's opening refresh reads the tail from B, finds the entry and consumes it — `completeOwnEntry`, nothing re-sent; or, if the refresh is answered by A's own stale copy, the recorded attempt is re-sent verbatim and storage treats it as the write's own revision — either way one log entry). Assert on the log, not on which path ran.
- **Crash after the local acknowledgement, before any send.** Sever B, commit offline on A, `powerLoss()` the journal (the entry record was flushed before `commit` resolved), restart A, `hydrate` with B still severed: `entries()` lists it `queued`, `persisted: true`, not in doubt; a read of the table on A shows the row (served locally, A holding the blocks); restore B; the entry drains and B reads the row. Also assert `queued` was emitted before `hydrate` resolved.
- **Crash between writing the drive record and sending.** Hold B's cluster round (a parked repo wrapper, as the invented-collection and reads specs do), commit offline, wait for the drive record to be on disk, `powerLoss()` with the send parked, restart: the entry is in doubt, `discard` refuses it, and it drains once under the recorded action id. The restored attempt is the one re-sent (`resumedAttempt` in db-core) — assert through B's log that exactly one entry exists under that id.
- **Unknown version.** Write a record with `v: 2` by hand into the store ahead of a valid one; `hydrate` rejects with `OfflineJournalError`, the valid earlier record is restored, every record is still in the store.
- **Two `Database`s, one store, two labels.** Each restores its own entries only; `entries()` disjoint.
- **Table dropped while down.** Register a second `Database` over the same shared storage (another "machine" in the local-transactor shape `hydrate-restores-declared-table.spec.ts` uses, or node B), drop the table there while A is "down" (A's `Database` discarded, journal kept), restart A: the record is deferred with reason `table-missing`, listed `waitingFor: 'restore'`, `discard` removes it with `failed`/`discarded`, `whenDrained` then resolves.
- **Cohort unreachable at restore on a node that never held the table's blocks.** Use the reads spec's `Isolation` proxy on A's transactor to answer every read `cohort-unreachable`, with A's node store empty of the table (A was not a member, or use the test transactor key the reads spec wraps): `hydrate` resolves with the record deferred, reason `unreadable`; a read of the table fails with `BlockUnavailableError` even in offline mode; disarm the proxy; a read of the table succeeds and triggers the pass; the entry is listed `queued` and drains.
- **Deferred record ahead of a new offline commit.** With a record deferred, commit a new offline transaction to another table: it is queued (local acknowledgement still works) but not submitted — the gate answers `false`, `waitingFor: 'cohort'`; once the deferred record restores (re-enable reads), the older entry is inserted ahead by `seq` and the two drain in `seq` order. Assert the order of `committed` statuses and that the restored entry's `seq` is lower.
- **Restore refused by a guard.** Another machine takes the key an unsent journaled insert used while A is down: after `hydrate` the entry fails with `constraint`, its row is not in A's view, the records are deleted and an outcome record is written, `status()` answers the retained outcome.
- **Outcome record present and entry record present** (a delete that never flushed): the entry is skipped and its records deleted; `outcomes()` lists the outcome once; no status emitted for it.
- **Restore while a transaction is open** → throws; nothing changes. By a small direct test or by inspection.
- **`hydrate` on a `Database` with no journal configured** → `restore()` is a no-op. The existing offline specs must pass unchanged.
- **Record whose segment names a collection the table does not back** (the table was re-declared over another URI while down) → deferred with `collection-mismatch`; discardable. By inspection.
- **Index segments.** A record over a table and its index restores both segments into the two trees; an index-driven read and a full scan agree after `hydrate` (`expectIndexAgreesWithScan` from the test helpers). Covered inside the first scenario by using an indexed table.
- **`dispose` during a pass.** The pass finishes the record it is on and stops; the controller's `dispose` awaits it. By inspection.
- **A restored entry's `seq` and a later `enqueue`.** `OfflineQueue.restore` raises `nextSeq` (part one), so a transaction committed after `hydrate` gets a higher `seq`. By inspection.

## Restarting a mesh node over lost storage

`Mesh.restart(node)` in `packages/db-p2p/src/testing/mesh-harness.ts` rebuilds a node's member and coordinator over the `IRawStorage` it was built with. A node whose store is a `WriteGroupDriver` over a `MemoryBatchBackend` keeps un-durable writes in the driver's overlay, so after `powerLoss()` the old driver still serves them. Extend `restart(node, options?: { rawStorage?: IRawStorage })` to take a replacement storage, recorded in `durableByPeer` so the rebuilt member and repo read it, and document on the method that a power-loss test passes a fresh `KvRawStorage(new WriteGroupDriver(backend))` here, as the conformance reopen case opens a fresh driver. The Quereus `Database` on that node is simply discarded and a new one registered over the restarted node's transactor (`createMeshDbNode` with the same transactor key) and the reopened journal (`PowerLossKVStore.reopen()`).
