# Storage flush takes a sync deadline

Second of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). `durability-window-from-cohort-size` computes how long a write may stay unsynced; this ticket gives storage a way to be told that, and a way to ask when deferred writes have reached the disk. No caller passes a window yet (`nodes-apply-the-durability-window` does), and no real backend defers yet (`file-store-syncs-by-the-earliest-deadline` does), so every production path behaves exactly as today. What changes is the contract and the in-memory write grouping (`WriteGroup`), which must now keep a write readable from memory until the backend says it is on disk.

## The contract

In `packages/db-p2p/src/storage/store-durability.ts` (shared by both interfaces):

```ts
export interface FlushOptions {
	/**
	 * How long after this call the writes it covers may stay exposed to a crash the store's
	 * `durability` names. Absent or 0: the flush resolves only once they survive it (the contract
	 * before this option). A store that cannot defer a sync treats every value as 0.
	 */
	readonly withinMs?: number;
}
```

`IRawStorage` and `RawStoreDriver` both change:

- `flush(options?: FlushOptions): Promise<void>`
- **new, required** `whenDurable(): Promise<void>` — resolves once every write covered by a flush that resolved before this call survives every crash `durability` names. It never hastens a sync. It rejects with `StoreFailedError` if the store fails first. Required, not optional, for the same reason `flush` and `durability` are: a wrapper that forgets to forward it must not compile.

The rules on `RawStoreDriver.flush` (`packages/db-p2p/src/storage/raw-store-driver.ts`) and their copy in `packages/db-p2p/docs/storage.md` Invariant 6 become:

1. unchanged.
2. Once a `flush()` called after the write resolved has itself resolved, the write survives a crash of this process; it survives every crash `durability` names once `withinMs` has passed since that flush was called (at once, for 0), or once `whenDurable()` called after the flush resolves.
3. unchanged (a prefix, in resolution order) — and it now matters more: a deferred sync is exactly when a power cut can take a suffix.
4. unchanged, plus: a flush with `withinMs` 0 covers every earlier deferred write too, so it hastens their sync.
5. unchanged, plus: a deferred sync that fails latches the store the same way, is logged, and is reported by the next write, flush or `whenDurable`.

Edit the table in Invariant 6 to say which drivers honour `withinMs` (only `WriteGroupDriver`, and only over a backend that defers — none yet after this ticket) and add `whenDurable` to the paragraph on the wrappers. Leave the theorem, window table and policy prose to `durability-docs-match-the-window`.

## Trivial implementations

Every store whose flush is already a no-op or always synchronous ignores `withinMs` and returns `Promise.resolve()` from `whenDurable`: `MemoryStoreDriver`, `LevelDBStoreDriver`, `IndexedDBStoreDriver`, `SqliteStoreDriver`. The wrappers forward both the options and `whenDurable`: `KvRawStorage`, `CachedStoreDriver`, `RawStorageDriverAdapter`, `CachedRawStorage`. Test doubles that implement `flush` (`packages/db-p2p/test/support/cache-test-helpers.ts`, the quereus spec named in `files:`, and any other the compiler finds) gain `whenDurable`.

## Backend seam: `BatchBackend`

`packages/db-p2p/src/storage/batch-backend.ts`. The commit gains a deadline and hands back a second promise:

```ts
/** What a resolved commit hands back. Defined in write-group.ts (key-agnostic) and re-exported here. */
export interface CommittedBatch {
	/** Settles once the batch survives every crash `durability` names. Batches' `durable` settle in commit order. Rejection is a storage fault. */
	readonly durable: Promise<void>;
}

commit(entries: readonly BatchEntry[], options: { readonly syncWithinMs: number }): Promise<CommittedBatch>;
/** Hasten: resolve once every batch whose commit has resolved survives every crash `durability` names. */
sync(): Promise<void>;
```

`commit` resolves once the batch is applied atomically and survives a crash of this process. A backend that cannot defer syncs before resolving and returns an already-resolved `durable`. The reads contract changes: reads must reflect every batch whose `durable` has resolved, and MAY reflect a batch earlier. The driver's overlay covers the gap (below).

`FileBatchBackend` and `FileKVStore` adapt to the new shapes **without deferring**: commit still syncs through `FileWriteLog.commit` exactly as today and returns `{ durable: Promise.resolve() }`; `sync()` resolves at once. Deferring is `file-store-syncs-by-the-earliest-deadline`.

## `WriteGroup`

`packages/db-p2p/src/storage/write-group.ts`. The constructor takes a sink instead of a bare commit function:

```ts
export interface WriteGroupSink<K> {
	commit(entries: readonly WriteGroupEntry<K>[], options: { readonly syncWithinMs: number }): Promise<CommittedBatch>;
	sync(): Promise<void>;
}
```

`WriteGroupDriver` passes its backend's `commit`/`sync`; `FileKVStore` passes `FileWriteLog`'s.

Behaviour:

- **`flush(options?)`.** Each call has a deadline, `Date.now() + (withinMs ?? 0)`. A flush is *strict* when `withinMs` is absent or 0, *relaxed* otherwise.
  - Fault → reject `StoreFailedError` (as today).
  - Nothing open, nothing in flight: relaxed resolves at once; strict resolves at once when every committed batch is durable, otherwise calls `sink.sync()` and resolves when the latest committed batch's `durable` has.
  - Nothing open, a commit in flight: wait for it, then as above.
  - Writes open: seal and commit, after any commit in flight (as today). Every flush that shares one sealed batch (the `sealAfterInFlight` waiters) contributes its deadline; the batch is committed with `syncWithinMs = max(0, earliestDeadline − Date.now())`. Each waiter then resolves by its own kind: relaxed when the commit resolves, strict when the batch's `durable` does. So one seal now needs two settle points per waiter group (committed, durable), not one deferred.
- **Overlay lifetime.** An overlay entry is dropped when its batch's `durable` resolves, not when its commit resolves; the sequence rule (drop only entries still tagged with that batch's sequence) is unchanged. Rewrite the `NOTE:` above `overlay` accordingly: the overlay now holds every write not yet durable, bounded by the byte bound below; the listing-merge cost note stays.
- **Byte bound.** New option `maxUnsyncedBytes` (default 64 MiB): the total value bytes held in the overlay by writes not yet durable, open batch included (deletes count 0; a replaced entry's bytes are subtracted). A seal that would leave the total above the bound commits with `syncWithinMs` 0, whatever the flushes asked. Validate the option like `idleFlushMs`.
- **`durable` rejecting** latches the group failed exactly as a rejected commit does (same `fault`, same `StoreFailedError`), logs once on `optimystic:db-p2p:write-group:error`, and rejects every pending strict waiter and `whenDurable`.
- **`whenDurable()`**: fault → reject; otherwise the `durable` of the latest batch whose commit has resolved (batches settle in order, so that one covers the rest), or `Promise.resolve()` when none is pending. Expose it from `WriteGroupDriver` and `FileKVStore` (the latter is not an `IRawStorage`; give it the method anyway, so `nodes-apply-the-durability-window` can order across stores if it needs to).
- **Idle flush** stays strict. It only fires for writes no group flushed.
- **`close()`** is a strict flush (which syncs everything pending) and then disarms the timer, as today.

## `MemoryBatchBackend` (test double, `./testing` entry)

New constructor option `deferSync?: boolean`, default false (existing tests unchanged: every `durable` already resolved, as today).

With `deferSync: true`:

- `commit` applies to the maps at once (reads reflect it) and appends to `committed` with a `durable` flag. `syncWithinMs` 0 marks this batch and every earlier one durable before resolving. Anything greater leaves it pending; the deadline itself is ignored, and the test decides when time passes by calling `sync()`.
- `sync()` marks every committed batch durable and resolves their promises in order.
- New `powerLoss()`: rebuilds the maps from the durable prefix of `committed` alone and drops the rest from `committed`. The dropped batches' `durable` promises never settle, because the process that awaited them is gone. Tests open a fresh driver over the backend afterwards, as the conformance reopen case does.

This is the "power-loss storage double" `mobile-and-browser-storage-keep-the-durability-window` and `nodes-apply-the-durability-window` reuse.

## Edge cases & interactions

- A key rewritten by batch N+1 while batch N is committed but not durable: N's durable drops nothing for that key (sequence rule). Test below covers the overlay holding entries past commit.
- Over a backend that applies at commit (memory with `deferSync`), an entry is in both the overlay and the backend between commit and durable. Check that each `WriteGroupDriver` listing merge (`rangeRevisions`, `listPendingActionIds`, `listBlockIds`) deduplicates in that state, by inspection; they already faced it in the window before `dropCommitted` ran.
- `promote` reads the pending bytes overlay-first, so a pending record still held in the overlay after its commit is found (by inspection).
- A strict flush after relaxed ones with nothing open must call `sink.sync()` exactly once and not re-commit anything (test).
- `whenDurable()` with nothing committed resolves at once, and after a fault it rejects (by inspection).
- `close()` with relaxed batches pending syncs them before closing the backend (covered by the conformance reopen case with `deferSync`; see Tests).
- Two waiters on one seal, one strict and one relaxed: the batch commits with `syncWithinMs` 0, and the relaxed waiter may resolve before the strict one (test).
- `StoreFailedError` wrapping: a backend `durable` that rejects with its own `StoreFailedError` is unwrapped to its `cause`, as `runCommit` does today (by inspection).
- `FileKVStore` behaviour is unchanged on disk; its spec must stay green unmodified apart from the constructor shape.
- `CachedStoreDriver` is write-through over the driver below it; forwarding is the whole change (by its existing forwarding test, extended to `whenDurable` if that test enumerates members).

## Tests

In `packages/db-p2p/test/write-group-driver.spec.ts`, over `MemoryBatchBackend({ deferSync: true })`:

- **A relaxed flush resolves before its batch is durable, a strict one does not, and a power cut takes back a suffix.** Write A, strict flush; write B, `flush({ withinMs: 5000 })` resolves with B's batch not durable while reads still serve B; `whenDurable()` is still pending; `powerLoss()` and a fresh driver read A and not B. Repeat without the power cut: a strict `flush()` with nothing open calls `sync` once, then B survives `powerLoss()` and `whenDurable()` has resolved.
- **A durable promise that rejects latches the store.** Make the backend's next `durable` reject (extend `beforeApply` or add a hook). Then `whenDurable` rejects, and the next write and flush throw `StoreFailedError` carrying the cause.
- **The byte bound forces a strict commit.** `maxUnsyncedBytes` small; a relaxed flush past it commits with `syncWithinMs` 0 (read from `committed`).
- **Strict and relaxed flushes sharing one seal.** Park a commit, issue one relaxed and one strict flush with writes between, release: one more commit, `syncWithinMs` 0, the relaxed flush settles at commit and the strict one at durable.
- Register the conformance suite a second time, `WriteGroupDriver over memory (deferred sync)`, persistent. Its reopen case closes the first store, which must sync, so it proves `close` does.
