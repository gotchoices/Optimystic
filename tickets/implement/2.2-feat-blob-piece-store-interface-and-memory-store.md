# The piece store interface, the memory store and the conformance suite

A blob (docs/blobs.md) is stored on a node as immutable pieces of at most 1 MiB, each named by its content identifier (`PieceId`, from `feat-blob-references-and-verified-piece-trees`). This ticket adds the interface every piece store implements, `IPieceStore`, the in-memory implementation, a power-loss test double, the shared conformance suite every backend runs, and the change to `StorageMonitor` that counts piece bytes once. Nothing uses a piece store yet: the filesystem store is `feat-blob-file-piece-store`, and the blob service that writes pieces is `feat-a-node-stores-blob-pieces`.

The piece store is deliberately not a logical store of `RawStoreDriver` and does not go through `KvRawStorage`, its write group or its journal: those JSON-encode every value and stage writes in memory, which is right for small versioned records and wrong for megabytes of immutable bytes that need no cross-key atomicity (docs/blobs.md §The local store).

## The interface

New module `packages/db-p2p/src/blob/piece-store.ts`, exported from `packages/db-p2p/src/index.ts`. The contract is written on the interface in this form (the doc comments carry it; this is the specification of what they say):

```ts
import type { PieceId } from '@optimystic/db-core';
import type { StoreDurability } from '../storage/store-durability.js';
import type { StoreIdentity } from '../storage/store-identity.js';

/**
 * A node's store of blob pieces: immutable bytes keyed by the piece's content identifier, in the one
 * canonical spelling `PieceId` has. Equal bytes have one key, so a raw piece and a list piece with
 * the same bytes share one entry.
 *
 * The store never hashes. Its one writer, the blob service, checks every piece against its id
 * before `put`; a store handed bytes that do not hash to their id keeps them as given.
 */
export interface IPieceStore {
	/** Whether a complete piece is stored under `id`. */
	has(id: PieceId): Promise<boolean>;
	/**
	 * The stored bytes, or `undefined`. Each call returns bytes no one else holds: the caller may
	 * modify them without changing what is stored or what a later `get` returns. A backend may return
	 * a `Uint8Array` subclass (Node's `Buffer`).
	 */
	get(id: PieceId): Promise<Uint8Array | undefined>;
	/**
	 * Store `bytes` under `id`. Once it resolves, `has` and `get` see the piece (in this process).
	 * When `id` is already present it writes nothing and resolves, whatever `bytes` holds. Two
	 * concurrent puts of one id both resolve, with the piece stored once. The store keeps its own
	 * copy: the caller may modify `bytes` once the call has resolved. A zero-length piece is a piece.
	 */
	put(id: PieceId, bytes: Uint8Array): Promise<void>;
	/** Remove the piece; resolves without effect when it is absent. */
	delete(id: PieceId): Promise<void>;
	/**
	 * Every stored id, each once. The backend drains each native cursor or directory listing before
	 * yielding from it (the drain-before-yield rule on `RawStoreDriver`). Against concurrent writes it
	 * promises only this: every id present for the whole of the call is yielded; an id put during the
	 * call may be missing, and an id deleted during the call may still be yielded. Nothing that is
	 * not a complete piece is ever yielded.
	 */
	list(): AsyncIterable<PieceId>;
	/** The bytes the stored pieces occupy, by the backend's cheapest honest measure. */
	bytesUsed(): Promise<number>;
	/**
	 * Make every put and delete that resolved before this call survive the crashes `durability`
	 * names, before resolving. Rules 1, 2 and 4 of the flush contract on `RawStoreDriver.flush` apply
	 * (with no `withinMs`: every piece-store flush is strict). Rule 3, the prefix rule, does not:
	 * pieces are independent, and a piece may survive a crash that took one put before it. The one
	 * ordering a caller needs (pieces before the record naming them) it gets by awaiting `flush`
	 * before writing the record. A rejected flush is a storage fault: the caller treats every write
	 * it covered as possibly lost.
	 */
	flush(): Promise<void>;
	/** What a flushed write survives. Fixed at construction. */
	readonly durability: StoreDurability;
	/**
	 * Optional: the identity of the location this store lives inside, in the scheme block stores use
	 * (`RawStoreDriver.storeIdentity`). Equal to a block store's `getStoreIdentity()` exactly when
	 * that block store's `getApproximateBytesUsed` already measures this store's bytes, which is
	 * what `StorageMonitor` reads it for. Omitted by a store that lives nowhere a block store
	 * measures (memory).
	 */
	storeIdentity?(): StoreIdentity;
	/** Optional: flush, then release any handle. */
	close?(): Promise<void>;
}
```

`storeIdentity?` is an addition to the shared shape the blob tickets agreed; it is how the node decides whether piece bytes are already counted (below). Rejected alternative: a boolean option on the node ("pieces share the block store's location"), which a host could set wrongly, while an identity equal to the block store's is evidence by the same one-directional contract `RawStoreDriver.storeIdentity` already states (equality proves sameness, inequality proves nothing).

## The memory store

`packages/db-p2p/src/blob/memory-piece-store.ts`, exported from the package index:

```ts
export class MemoryPieceStore implements IPieceStore {
	readonly durability: StoreDurability = 'none';
	// private readonly pieces = new Map<PieceId, Uint8Array>();
}
```

- `put` stores `bytes.slice()` when the id is absent; `get` returns `stored.slice()`; `has`, `delete` are map operations.
- `list` copies the key set into an array before the first yield.
- `bytesUsed` sums the stored lengths.
- `flush` resolves; there is nothing to make durable. No `storeIdentity`, no `close`.

## The power-loss double

`packages/db-p2p/src/testing/power-loss-piece-store.ts`, exported from `packages/db-p2p/src/testing/index.ts` (it imports only runtime code, which that entry requires). The `IPieceStore` counterpart of `PowerLossKVStore` in the same directory, for the crash tests `feat-a-node-stores-blob-pieces` writes:

```ts
export class PowerLossPieceStore implements IPieceStore {
	readonly durability: StoreDurability = 'power-loss';
	/** @param durable What survived every earlier crash; shared with the store `reopen` returns. */
	constructor(durable?: Map<PieceId, Uint8Array>);
	/** The crash: every put and delete no flush reached is lost, and this store throws StoreLostPowerError from every method from now on. */
	powerLoss(): void;
	/** A fresh store over what survived; throws when powerLoss() has not run, as PowerLossKVStore.reopen does. */
	reopen(): PowerLossPieceStore;
}
```

Writes resolve into an in-memory overlay (`Map<PieceId, Uint8Array | null>`, `null` a delete) served to `has`, `get`, `list` and `bytesUsed`; `flush` applies the overlay to `durable`. It reuses `StoreLostPowerError` from `power-loss-kv-store.ts`. It never flushes on its own.

## The conformance suite

`packages/db-p2p/src/testing/piece-store-conformance.ts`, modelled on `runRawStorageConformance` in `raw-storage-conformance.ts`:

```ts
export interface PieceStoreHarness {
	store: IPieceStore;
	/** Release everything the case used, including the store `reopen` returned. */
	cleanup: () => Promise<void>;
	/** A fresh store over the same location; the suite has already called `close` on the first when it has one. Required, and read only, under `{ persistent: true }`. */
	reopen?: () => Promise<IPieceStore>;
}
export interface PieceStoreConformanceOptions { persistent?: true }
export function runPieceStoreConformance(name: string, makeStore: () => Promise<PieceStoreHarness>, options?: PieceStoreConformanceOptions): void;
```

Piece ids are computed by one helper in the module, `conformancePieceId(bytes)`: `pieceIdOfCid(CID.createV1(raw.code, await sha256.digest(bytes)))`, with `CID` from `multiformats/cid`, `raw` from `multiformats/codecs/raw` and `sha256` from `multiformats/hashes/sha2` (`multiformats` is a runtime dependency of db-p2p), and `pieceIdOfCid` from `@optimystic/db-core` (`packages/db-core/src/blob/blob-ref.ts`), which produces the one canonical spelling and the brand, so no cast is needed. The suite does not use `buildBlob`, because the builder never produces a raw piece above 256 KiB and the suite needs a 1 MiB one. Bytes are compared element-wise by a local `sameBytes(a, b)`, never with chai's `deep.equal`, so a backend returning a `Buffer` passes.

Cases, one `it` each:

- `get` and `has` on a missing id: `undefined` and `false`.
- put then get returns the same bytes; `has` is true.
- a second put of a present id with different bytes changes nothing: `get` returns the first bytes.
- a zero-length piece round-trips and `has` is true.
- delete then `has` is false and `get` is `undefined`; deleting an absent id resolves.
- `list` yields every stored id exactly once (three pieces), and nothing after all are deleted.
- `list` tolerates awaits between yields: a `get` of another id between each yielded item does not disturb the listing (drain-before-yield).
- `bytesUsed` rises by at least a piece's length and at most that plus 4096 per put, and returns to within 4096 of its starting figure when the piece is deleted (the slack admits per-row overhead in database backends; memory and files are exact).
- the caller's buffers are not the store's: modifying the `bytes` passed to `put` after it resolved, and modifying a buffer `get` returned, leave a later `get` unchanged.
- a 256 KiB piece and a 1 MiB piece (1,048,576 bytes, the reader's bound) round-trip.
- `{ persistent: true }` only: put four pieces, delete one, `flush()`, `close?.()`, `reopen()`: the three remaining read back byte-equal, the deleted one is absent, and `list` yields exactly the three. Throws, rather than skipping, when the harness has no `reopen`.

## Counting piece bytes once

`StorageMonitor` (`packages/db-p2p/src/storage/storage-monitor.ts`) gains an optional third constructor parameter `pieces?: IPieceStore`. `estimateUsedSpace` returns the block store's figure plus `await pieces.bytesUsed()`, unless the rule below says the block store already counted them. The rule is one exported function in that module, documented where it is decided:

```ts
/**
 * Whether `storage`'s `getApproximateBytesUsed` already measures `pieces`' bytes. Every disk block
 * store measures its whole directory or database, so a piece store inside the same location is
 * counted there and adding its own figure would count it twice. Decided by store identity, whose
 * contract is one-directional: equal identities prove one location, so the piece bytes are left
 * out; anything else (either identity absent, two different strings, or a block store with no
 * `getApproximateBytesUsed`, which measures nothing) adds them.
 */
export function blockStoreCountsPieces(storage: IRawStorage, pieces: IPieceStore): boolean;
```

The piece figure is part of the same memoized scan (`getCachedUsedBytes`): `estimateUsedSpace` sums the two, so the existing TTL and single-flight cover both, and a rejected `bytesUsed` rejects the scan exactly as a rejected block-store scan does (not cached, next call retries). Add a `NOTE:` at the function: two spellings of one location read as two identities, so a piece store over a differently spelled path to the block store's directory is counted twice; that errs toward reporting the node fuller than it is, which delays nothing and moves a ring outward at worst; revisit if a host reports it. The node passes its piece store in `feat-a-node-stores-blob-pieces`; this ticket changes only the monitor.

## Edge cases & interactions

- Same id put twice with different bytes: the first stays. Conformance case. (The blob service never does this, since it verifies first; the case pins "writes nothing".)
- Zero-length piece (the empty blob's only piece): stored and `has` true. Conformance case.
- A caller modifying a buffer after `put` or after `get`: no effect on the store. Conformance case; `MemoryPieceStore` copies on both sides.
- `list` while a put or delete runs: the weak promise above. By inspection for memory (it snapshots the keys); the sweep in `feat-a-node-stores-blob-pieces` relies on nothing stronger.
- A piece at the reader's 1 MiB bound: conformance case, so every backend, NativeScript's included (docs/blobs.md §Platforms and limits), must store it.
- Piece bytes counted twice or not at all: `blockStoreCountsPieces` with equal identities, different identities, and an absent identity. Test (below).
- `StorageMonitor` built without a piece store behaves exactly as before: inspection (the parameter is optional and the sum adds nothing).
- A block store without `getApproximateBytesUsed` (counts 0) beside a piece store whose identity equals the block store's: the piece bytes are still added, since the block store measured nothing. Inspection of `blockStoreCountsPieces`.
- `bytesUsed` rejecting: the whole scan rejects and is not cached, the existing scan-error behaviour. Inspection.
- `PowerLossPieceStore` after `powerLoss()`: every method throws `StoreLostPowerError`. Inspection, mirroring `PowerLossKVStore`.

## Tests

- `packages/db-p2p/test/memory-piece-store.spec.ts`: `runPieceStoreConformance('MemoryPieceStore', …)`; `runPieceStoreConformance('PowerLossPieceStore', …, { persistent: true })` with a harness whose `reopen` calls `powerLoss()` then `reopen()`; and one case of its own: a put not followed by `flush()` is absent after `powerLoss()` and `reopen()`, while a flushed one is present.
