# A materialized view follows rows other members commit

GitHub #58 (Sereus; optimystic 1.26–1.27, quereus 5.0–5.4).

## The defect

On machine A, `create materialized view ChitTotal as select Side, sum(Units) … from Chit group by Side` over an Optimystic table. Machine B commits a row to `Chit`. A's `select * from Chit` shows B's row; `ChitTotal` does not, and neither do the view's body run as a plain query nor `select sum(Units) from Chit`, because Quereus rewrites both to read the view. A's next local insert adds its own row on top of the stale total. Only `refresh materialized view` corrects it.

Quereus maintains a materialized view row by row for writes made through its own statements. Rows that reach an Optimystic table any other way — another machine's commit pulled in by a read, a commit this node's storage applies, a network watch wake, a queued offline transaction that failed and left this machine's view — are announced today only through `Database.notifyExternalChange`, which fires watchers and runs no view maintenance (Quereus docs/mv-ingestion.md). Row-by-row maintenance through `ingestExternalRowChanges` is out of reach: a log entry does not reliably carry the old row.

## Decision (maintainer, 2026-11-17) and what this ticket delivers

When another machine's commit reaches this one, each materialized view reading the changed table is either **refreshed** (rebuilt, scheduled after the engine's exec lock is free, changes arriving while a refresh is pending folded into it) or **invalidated** (kept off every query path until refreshed), by configuration.

Quereus offers no public way for a host to keep a view off every query path: `markMaterializedViewStale` is `@internal` (stripped from the published types), and its `stale` flag keeps the planner's rewrite off the view but still serves the stored rows to a direct `select … from ChitTotal` whenever the body still plans (`building/select.ts`). Per the decision, that is an upstream ask, filed as `blocked/a-materialized-view-can-be-kept-off-while-it-is-behind`, and **refresh is the only mode until it lands**. This ticket implements refresh, with no setting; the setting (plugin default `'refresh'`, per-view tag override) is specified in the blocked ticket, since it means nothing with one mode.

What refresh guarantees: once the follower has settled, every view reading a table reflects every other-writer commit this machine's handle of that table has adopted, and every commit it has been told of by its storage or network watch. Between the signal and the rebuild's commit, reads of the view (direct or rewritten) still answer from the old rows — the window the maintainer accepted for refresh mode; invalidate mode closes it.

## Design

### Signals

Three ways rows change in this machine's view without a local Quereus statement, each reported to one per-`Database` follower:

1. **Adopted** — a handle of the table (main tree or any index tree) adopted other writers' commits in a refresh: the `onExternalCommits` callback from `a-collection-reports-commits-it-adopted-from-other-writers`. Authoritative: own commits never produce it (they are folded, not walked). Covers every path that pulls — a read's `refreshLive`, the offline drain's head-commit refresh, the coordinator's refresh between attempts — including a node that hears of nothing and only pulls on read.
2. **Hint** — this node's storage applied a commit to the table (`handleCollectionChange` from `subscribeToCollectionChanges`) or the network watch woke (`openNetworkWatch`). These fire for this machine's own commits too, so a hint is not acted on directly: the follower pulls the table's main handle (below), which turns a foreign commit into signal 1 and an own commit into nothing. This is what keeps a hosting node from rebuilding every view after each of its own inserts.
3. **Withdrawn** — the offline queue removed a failed transaction's rows from this machine's view (`OfflineMode.announceChanged`). No log entry is involved and the view was maintained with those rows, so this marks the table dirty directly.

Signals 2 and 3 go through the same call sites as `announceExternalChange`: replace those call sites' direct call with one helper in `external-change.ts` that both announces to watchers and notes the follower, so the two cannot drift. Signal 1 arrives through `CollectionFactory`: add a once-set listener (`setExternalCommitsListener`, the pattern of `setSealedRefusedListener`) that `treeOptions()` hands every tree it opens as `onExternalCommits`, bound to that tree's collection id; the follower maps collection ids to tables.

All three are synchronous, record into sets, schedule the run, and return. Signal 1 runs under a collection latch and inside an await-free step, so it must not touch the collection or the engine.

### The follower

`MaterializedViewFollower` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/materialized-view-follower.ts`, one per `Database`, built in `register` beside `OfflineMode`, reachable by the vtab through the bridge (as `getOfflineMode` is), exposed on the plugin object as `materializedViews` with a `settled(): Promise<void>` (resolves once no work is pending or running — hosts and tests wait on it), and disposed in `dispose` before the bridge.

State: `tables` (qualified table → its collection ids and a `pull` closure, registered by the vtab on each full initialization and removed in `destroy`), `hinted` and `dirty` (sets of qualified tables), and one in-flight run promise.

Every signal first checks whether any materialized view reads the table: some `db.schemaManager.getAllMaintainedTables()` entry's `derivation.sourceTables` (lowercased `schema.table`, tables reached through plain views included) names it. If none does, the signal is dropped — an application with no views pays nothing. (`NOTE:` tripwire at that check: it re-reads the catalog per signal; if catalogs grow large, keep the set and invalidate it on `materialized_view_added`/`_removed` and table renames.)

The run, repeated until `hinted` and `dirty` are both empty:

1. **Wait out an explicit transaction.** If one is open (`!db.getAutocommit() && !db._isImplicitTransaction()`), wait for it to end. Every registered connection joins every transaction (`TransactionManager.beginTransaction` loops over all connections), so the `TransactionBridge` sees every commit and rollback; give it a "next transaction end" promise the follower awaits. A refresh run inside the user's transaction would be undone by its rollback, and `ddl_transaction_policy = 'strict'` refuses it there.
2. **Pull hinted tables, under the exec lock.** Take `hinted` and run each table's `pull` (the vtab's `refreshLive` over its main tree, so offline mode's degraded reads apply exactly as for a read) inside `db.ingestExternalRowWrite(async () => { …pulls…; return []; })`. That public seam runs its callback in one exec-lock hold and ingests nothing for an empty result: the pull brings other writers' commits into module storage, which is what the seam is for, and holding the lock keeps a background pull from moving a tree under a statement's scan. A pull that adopts foreign commits raises signal 1 into `dirty`. A pull that fails is logged; the next read of the table pulls again.
3. **Rebuild.** Take `dirty`; the affected views are those whose `sourceTables` meet it. Order them so a view that reads another affected view comes after it. A view that reads only an affected view needs no refresh of its own: a refresh sends its diff through the cascade to live dependents (Quereus `refreshMaintainedTable`). For each, `await db.exec('refresh materialized view "<schema>"."<name>"')` (quote identifiers). Quereus's refresh re-reads the source through the vtab (which pulls) and propagates its realized diff to the view's watchers, so no extra announcement is needed.
4. **Joined a transaction?** If an explicit transaction is open after a refresh resolves (a `begin` queued ahead of the refresh on the exec lock), or the refresh threw because of one, put its source tables back into `dirty` and go to step 1: a commit leaves the second rebuild a no-op diff, a rollback is repaired by it.
5. **Failure.** Any other refresh failure keeps its tables in `dirty`, is logged once per distinct message, and the run retries after a backoff (1 s doubling to 60 s, reset by a success). A view that can never refresh (its source changed incompatibly) retries at 60 s with its log suppressed; dropping or recreating the view ends it.

The run is started with `void` from a signal and never awaited by a callback; calling `db.exec` from it simply queues behind whatever statement holds the exec lock, which is the "after the lock is free" the decision asks for. A run starts at most once at a time; signals during a run land in the sets and are picked up by its next iteration, which is the coalescing. Stop between steps once disposed; a closed `Database` rejects, which ends the run quietly (debug log).

### Handle replaced on re-initialization

`doInitialize` can run again for a table (provisional→full upgrade, retry) and publishes a freshly opened handle, which jumps to the latest revision without walking anything. When a previous handle existed and the new handle's revision is past it, raise signal 3 for the table (rows may have arrived that no walk reported).

### A table this machine is never told about

A table on the `network` transactor that is not tagged `"optimystic.network_watch" = true` hears other machines' commits only when this node stores its blocks or a read pulls; a view over it can sit behind until something reads the table. When a view is created over such a table (follower listens for `materialized_view_added`), and for existing views when such a table registers, log one WARN naming the view, the table and the remedy (tag the table `optimystic.network_watch`). The vtab passes "is told of remote commits" (`transactor !== 'network' || network watch tag set`) when it registers.

### Index commits that land late

On the network-watch path a wake can precede the commit of the table's index collections (backlog `feat-a-network-watch-wake-sees-the-whole-commit`), so a rebuild that reads through an index can miss a row. Registering every index tree's collection id under its table means the read that later pulls the late index commit raises signal 1 and rebuilds again. The storage path already holds the table's event until the action's other collections land here.

## Edge cases & interactions

- **Own commit on a hosting node** (storage event for this machine's write): pull adopts nothing, no rebuild. Test (own-write).
- **Two `Database`s over one transactor** (the issue's repro): B's commit is foreign to A's handle; A rebuilds. Test (repro).
- **Pull-only node** (no storage events, no network watch): no hint; the next read of the source pulls, raises signal 1, rebuild follows. A rewritten read of the view before any source read still answers old rows — the WARN above names it. By inspection plus the WARN.
- **Rival entry adopted during this machine's own commit** (conflict replay, then commit or refusal): signal 1 from that refresh; the rebuild runs after the statement releases the lock, over whichever outcome it had. By inspection.
- **Offline transaction fails and is removed**: signal 3, rebuild drops its rows. By inspection (same call site as the existing announcement).
- **Explicit transaction open when a signal arrives; it rolls back**: rebuild waits, then runs outside it. Test (explicit-transaction).
- **`begin` queued ahead of the refresh on the exec lock**: step 4. By inspection.
- **View over a view over the table**: only the direct reader is refreshed; its refresh cascades. By inspection.
- **View over an Optimystic table and a memory table**: only Optimystic sources signal; memory-table writes are local statements, maintained row by row. By inspection.
- **View backed by an Optimystic table** (if the backing host allows it): the rebuild's writes are this machine's own commits, so they raise nothing; no loop. By inspection.
- **Refresh fails** (cohort unreachable mid-read, view broken by a schema change): backoff and retry, logged. Assertion at the seam: tables stay in `dirty` until a refresh of every affected view succeeds.
- **Dispose / `Database` closed mid-run**: run stops; nothing thrown into a callback. By inspection.
- **Dispute invalidation reverting committed rows**: counted as adopted by the prereq; rebuild. By inspection.
- **DROP TABLE of a source**: the vtab unregisters in `destroy`; the view goes stale through Quereus's own schema handling. By inspection.

## Tests

In `packages/quereus-plugin-optimystic/test/`, one new spec reusing the two-`Database`-over-one-`StorageRepo` fixture of `external-commit-visibility-after-rollback.spec.ts`; count rebuilds by `materialized_view_refreshed` schema events on A.

- **Repro (GitHub #58).** A creates `ChitTotal` over `Chit`. B inserts a row. `await plugin.materializedViews.settled()` on A. Expected: `select * from ChitTotal` and `select sum(Units) from Chit` on A both include B's row; A then inserts a row and the total includes both.
- **Own write does not rebuild.** With the view in place, A inserts three rows; after `settled()`, zero `materialized_view_refreshed` events, and the view holds the three rows.
- **Explicit transaction.** A runs `begin`; B inserts; A runs `rollback`; after `settled()` the view includes B's row and exactly one refresh happened, after the rollback.
