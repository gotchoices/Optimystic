# The blob cohort reaction

docs/blobs.md §Placement, copying and durability, "When the cohort changes": "A member that joins a held blob's cohort is announced to. A node that leaves a blob's cohort drops its `responsible` hold only after confirming that enough current members hold the blob."

This ticket is the decision half of that sentence: one class that turns a `RebalanceEvent` into "announce to these peers", "this hold can go", "this hold must stay". It touches no wiring. The other half — running a second `RebalanceMonitor` over the blobs this node holds, feeding it the tracked set and acting on what this class returns — is `feat-a-held-blob-follows-its-cohort`, which lands immediately after it and carries the documentation for both.

Split this way because the two halves fail differently: the two arms below are branching logic with answers to map and counts to compare, and they are unit-testable against doubles with no node at all, while the other half is factory plumbing with documented precedents and no logic of its own.

## `BlobCohortReaction`

`packages/db-p2p/src/blob/cohort-reaction.ts`. The blob counterpart of `BlockTransferCoordinator.handleRebalanceEvent` in `packages/db-p2p/src/cluster/block-transfer.ts`: same event in, same shape of feedback out, different primitive (an announcement instead of a push, and a `stat` instead of a push response).

```ts
/** How many references each arm works on at once, and how many peers the release arm stats at once. */
const REACTION_CONCURRENCY = 4;

export interface BlobCohortReactionDeps {
	selfId: string;
	membership?: NetworkMembershipGate;
	partitionDetector: Pick<PartitionDetector, 'detectPartition'>;
	/** The record door. `responsibleScope` is both the "does this node still hold it responsible" test and the scope to announce under. */
	records: Pick<BlobResponsibleRecords, 'responsibleScope'>;
	/** The writer's owed entry, for the scope of a grown reference this node owes rather than holds responsible. */
	owed: Pick<OwedBlobLedger, 'get'>;
	/** `blobAcceptanceOf(keyNetwork, blobProtocol, peerIds)`, bound by the node — the same closure `BlobCopyDrain` takes. */
	acceptance: (peerIds: readonly string[]) => Promise<Record<string, BlobAcceptance>>;
	/** The drain's per-peer `declined` memory. Absent when the copy drain is switched off, and then nothing declines. */
	declining?: Pick<BlobCopyDrain, 'isDeclining' | 'noteDeclined'>;
	/** `BlobProtocolClient.announce` bound to this node, as the drain takes it. */
	announce: BoundBlobAnnouncer;
	/** `BlobProtocolClient.stat` bound to this node: one request per peer, answers positional on `refs`. */
	stat: (peerId: string, refs: readonly BlobRef[]) => Promise<readonly BlobLocalHolding[]>;
}

export interface BlobReactionResult {
	/** Lost references whose release was confirmed; the caller drops the `responsible` hold. */
	released: BlobRef[];
	/** Lost references not yet confirmed; the caller calls `RebalanceMonitor.retainLost`. */
	retained: BlobRef[];
	/** Per grown reference, keyed by the reference. No entry for one the reaction learned nothing about. */
	growth: Map<string, GrowthOutcome>;
}

export class BlobCohortReaction {
	constructor(deps: BlobCohortReactionDeps);
	handle(event: RebalanceEvent): Promise<BlobReactionResult>;
}
```

A module-level `createLogger('blob:copy')`, as `blob-copy-drain.ts` has: the blob monitor runs under the same namespace (`RebalanceMonitorDeps.logName` already documents `'blob:copy'` for the blob instance), so one filter shows a blob's whole copy story. Every import is type-only or pure (`admittedBy`, `MAX_BLOB_STAT_REFS`, `createLogger`), and `RebalanceEvent` / `GrowthOutcome` come in through `import type`, so the module stays reachable from the react-native entry; export it from **both** `packages/db-p2p/src/index.ts` and `src/rn.ts` (`test/entry-parity.spec.ts` fails a module exported from one entry and not the other).

### Before either arm

`handle` resolves two things once, for the whole event:

- **Partition.** `deps.partitionDetector.detectPartition()` true → nothing is announced and nothing is released, as `replicateGrown` and `confirmReplicated` do: every grown reference gets `{ satisfiedPeers: [], complete: false }` (an incomplete outcome counts an attempt in the monitor and keeps every reported peer un-seen, so the next check retries it), every reference in `event.lost` is retained, `released` is empty. Log `reaction:partition lost=%d grown=%d` and return. Retaining a lost reference this node does not hold `responsible` costs nothing — the monitor re-reports it, and the arm below then skips it.
- **Acceptance**, in one call, over the union of the peers named in `event.grown`'s values and `event.newOwners`'s values with `selfId` removed — not one call per reference, which would be one peer-store sweep per reference per check. A rejection is logged `acceptance:failed err=%s` and read as `unknown` for every peer, which counts as accepting: a member not known to refuse blobs is owed one until it is, which errs toward keeping this node's copy.

A peer is **satisfiable without a request** when `admittedBy(membership, peer)` is false, its acceptance is `refuses`, or `declining?.isDeclining(peer)` is true. It is owed nothing: it will never hold the blob, and treating it otherwise would keep a `responsible` hold for ever.

`event.gained` is not acted on, as for blocks: a tracked reference is one this node already holds.

The two arms run concurrently (`Promise.all`), each handling at most `REACTION_CONCURRENCY` references at a time; within one reference, announcements go **in turn**, for the reason `BlobCopyDrain.announceTo` documents — the receiver's `AnnounceLimiter` bounds announcements per peer per minute and its reference read holds one of four read slots, so fanning out would mostly queue behind that.

### `grown` — a member joined a held blob's cohort

Per reference and its newly co-responsible peers (the monitor never reports an empty list, but skip one if it appears):

- The scope is `await records.responsibleScope(ref)`, else `(await owed.get(ref))?.scope`. With neither — the holds changed since the check read them — the reference gets `{ satisfiedPeers: [...peers], complete: true }` and `grow:no-scope ref=%s` is logged: there is nothing to announce under, and leaving it incomplete would retry it every check for ever.
- Each peer that is not satisfiable without a request is announced to under that scope. `whole`, `fetching` and `declined` satisfy it; `not-responsible`, `unreferenced` and a rejected call do not. `declined` also calls `declining?.noteDeclined(peer)`. Log `grow:answer ref=%s peer=%s answer=%s` per answer and `grow:unreachable ref=%s peer=%s err=%s` per rejection.
- `complete` is true when every reported peer is satisfied. `fetching` counts as satisfied because the receiver has already taken a durable `responsible` hold and resumes its pull after a restart (`BlobAnnounceReceiver.resume`); its `held`, when it comes, reaches the monitor as holder evidence through the drain's `onHolderConfirmed`.
- An incomplete outcome counts an attempt in the monitor, so a failing announcement is re-detected on the next check and abandoned after `growthMaxAttempts` until the peer leaves the cohort and rejoins. That is the same confirmation-driven path the block arm uses, and it is why a reported peer must never be reported satisfied on a guess.

### `lost` — this node left a blob's cohort

Per reference in `event.lost`:

- `scope = await records.responsibleScope(ref)`. `undefined` → the reference appears in **neither** `released` nor `retained` and gets no outcome, so the monitor's state for it is untouched; log `release:not-responsible ref=%s`. This is the reference held only as `owed` (the owed drain follows the cohort on its own passes and the reference stays tracked through that hold) and the reference whose holds changed while the check ran.
- Candidates are `event.newOwners.get(ref) ?? []` minus every peer satisfiable without a request. (`newOwners` already excludes self.)
- The required count is `Math.min(Math.max(1, event.floor), candidates.length)`. `event.floor` is the floor `RebalanceMonitor.getCohortSize` already gives the block release; it is capped by the accepting candidates because an on-demand or older member can never hold the blob, and requiring it would keep the hold for ever even when every member that can hold it does. A required count of 0 — no new owner accepts blobs — **retains** the reference and logs `release:no-accepting-owner ref=%s`: nobody else would keep it.
- **Stat, then announce.** Invert to peer → the references it is a candidate for, and ask each peer once, at most `REACTION_CONCURRENCY` peers at a time and at most `MAX_BLOB_STAT_REFS` references per request (chunk beyond that — `event.lost` is not budget-capped the way `event.grown` is, so a node that sheds a wide range can report hundreds). The answers are positional on the references sent; a rejection, or an answer array of the wrong length (a protocol break), counts every reference in that chunk as not `whole` and logs `release:stat-failed peer=%s refs=%d err=%s`. Then, per reference, announce under its scope to each candidate that did not answer `whole`, so a member that has not heard of the blob starts pulling now rather than at its writer's next pass; log `release:announced ref=%s peer=%s answer=%s`, and call `noteDeclined` on a `declined`.
- Released when the `whole` count reaches the required count (`release:confirmed ref=%s whole=%d/%d`), retained otherwise (`release:retained ref=%s whole=%d/%d`). Only the `stat` answers count: a peer that answers `whole` to the announcement sent after it is deliberately **not** counted this pass, so the release decision is made over one snapshot of the cohort rather than over a tally that shifts as the announcements go out. Nothing is lost by it — the caller retains the reference, the monitor re-reports it, and the next check's `stat` sees that peer.

## Edge cases & interactions

- **Leaving a cohort with too few holders.** The reference is retained, so the caller keeps the `responsible` hold and arms the monitor's re-check; it is released once enough current members answer `whole`. Test.
- **A member joins a held blob's cohort and the announcement fails.** The peer is left unsatisfied and the outcome incomplete, so the monitor re-reports it. Test of the answer-to-outcome mapping; the monitor's re-report is pinned by `test/rebalance-monitor.spec.ts`.
- **On-demand or older members.** Satisfied without a request in `grown`, excluded from the release count in `lost`. The test covers the `declined` arm; `refuses` and a membership refusal share the same filter, so they are covered by inspection.
- **Partition.** No release and no announcement: the monitor suppresses its own checks, and `handle` re-checks because the event may have been emitted just before the flag went up. Inspection.
- **A lost reference with no new owners at all** (the cohort lookup named nobody): candidates empty, required 0, retained. Inspection — the safe direction, and the same one `cohortView` takes in the drain.
- **A reference that is both owed and held responsible** (this node wrote it and is in its cohort): the `lost` arm releases only `responsible`; the reference stays tracked through `owed` until the owed drain reaches `full`. The release itself is the caller's, so this class only has to leave the owed entry alone — which it does, reading `owed` for a scope and never writing it. Inspection.
- **Holds edited during a check.** Every arm re-reads the hold before acting on a reference, so one whose hold vanished is skipped with no outcome entry. Inspection.
- **Block replication unchanged.** Nothing here touches `BlockTransferCoordinator`, the block monitor or the owned-block set. Inspection.

## The record door

`packages/db-p2p/src/blob/local-blob-service.ts` gains the counterpart of `BlobOwedRecords`, declared beside it and implemented by `LocalBlobService` for the same reason that one is a door rather than a second `BlobRecordStore`: every hold write has to go through `changeRecord`, which the piece sweep relies on.

```ts
/** What the blob cohort reaction and its wiring need of this node's blob records; `LocalBlobService` is it. */
export interface BlobResponsibleRecords {
	/** The scope of `ref`'s `responsible` hold, or undefined. */
	responsibleScope(ref: BlobRef): Promise<BlobScope | undefined>;
	/** Every reference whose record holds `responsible`. */
	responsibleRefs(): Promise<BlobRef[]>;
	/** Remove the `responsible` hold; a record left with no hold is deleted and the blob swept. No record, or no such hold, is a no-op. Flushed. */
	releaseResponsible(ref: BlobRef): Promise<void>;
}
```

`responsibleScope` and `responsibleRefs` already exist and move onto the interface unchanged. `releaseResponsible` is new and is `releaseOwed`'s mirror — `changeRecord` with a `recordAfterResponsibleRelease` helper beside `recordAfterOwedRelease` (returning the current record unchanged when there is nothing to release, so nothing is written), then `records.flush()`. Flushed like the owed release: a lost release costs only a blob kept one restart longer, but the two paths should not differ for no reason.

Releasing the hold leaves the bytes to the piece sweep **only if no other hold remains**, so a node that also pinned or cached the blob keeps it. `feat-unreferenced-blobs-are-reclaimed` extends this same write to clear the reclaim pass's `unreferencedSince` mark; nothing here needs to anticipate that beyond keeping the release a single record write.

## Tests

`packages/db-p2p/test/blob-cohort-reaction.spec.ts`, over a real `LocalBlobService` on `MemoryKVStore` and `MemoryPieceStore` (so the hold really is in a record) with `stat` and `announce` doubles bound the way the blob specs bind their transport:

- **`lost`, floor 2, two accepting new owners.** `holdResponsible(ref, scope)` first. First `handle`: one owner answers `whole`, the other `none` → `retained` is `[ref]`, `released` is empty, the double recorded an announcement to the non-`whole` owner, and `responsibleScope(ref)` still answers the scope. Second `handle` with both `whole` → `released` is `[ref]`; then `releaseResponsible(ref)` — standing in for the caller's handler — leaves `responsibleScope(ref)` undefined.
- **`grown` with four new peers** answering `whole`, `fetching`, `declined` and `unreferenced` → `satisfiedPeers` is the first three, `complete` is false, and the declining double recorded the third peer through `noteDeclined`.

Nothing else: the two arms are the branching logic, and the copying they trigger is pinned end to end by `feat-blob-owed-copies-are-drained`'s two-node tests.
