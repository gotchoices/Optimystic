# A restart turns "I cannot reach my cohort" into "this block does not exist"

## What happens

A block read that misses locally consults the block's cohort (`CoordinatorRepo.fetchBlockFromCluster`). If `findCluster` returns this node alone, the pass takes the solo-self exit (`cluster-fetch:solo-self-skip`), consults nobody, and serves the local miss as an **authoritative absent**. `docs/internals.md` accepts that cost for a cold boot with an empty routing table and says the unflagged absent and the `'cohort-unreachable'` flag "differ only in whether FRET still remembers peers": a node that remembers cohort members asks them, and when none answer the read is flagged `'cohort-unreachable'` and fails loudly (`BlockUnavailableError`) instead of returning nothing.

A restart breaks that sentence even when the node is configured to remember its peers (`createLibp2pNode({ persistence })`):

1. `initFromPersistedState` restores FRET's routing table. FRET's `importEntries` keeps each restored peer as `membership: 'member'`, `state: 'disconnected'`, so FRET's `assembleCohort` still returns it — the node *does* remember its cohort.
2. `assembleServingCohort` then scopes that band to peers serving this network, classified by `membershipOf` from the libp2p **peerStore's protocol list**. The peerStore is in memory (no datastore is configured), so after a restart every restored peer has no protocols and is classified `'unknown'`, and `'unknown'` is never admitted (deliberately — a permanently cross-network peer looks the same; see the comment in `assembleServingCohort`).
3. The cohort comes back self-only, and every read of a block this node lacks is answered "absent" from its own partial store until the remembered peers reconnect *and* finish identify.

That is the "why is absent served" half of the sereus re-attach report (optimystic #22 measurements): a cohort member that detached soon after its first sync kept part of a collection; on re-attach, 5 of 8 launch-time reads of `default/strand/Header` were answered absent at the solo-self exit, and one threw `Missing block` (the header was present, a block it references was not — the same exit, one block further down). The other half — why the member held only part of the collection — is `a-peer-that-joins-soon-after-a-check-never-gets-a-copy`.

**Evidence status.** Step 3's "self-only view answers absent" is already pinned by existing specs (`coordinator-repo-absence-write-bypass.spec.ts`, the mesh cases that give node A a self-only view: `isUnflaggedAbsent(...)` on the first probe). Steps 1–2 are read from code (FRET `importEntries`, `isLiveMember`; `membershipOf`'s empty-protocols branch), not run end to end — the first TODO below confirms them at the key-network tier before the fix.

**Scope boundary with sereus#18.** Sereus does not pass db-p2p `persistence` today: its strand nodes restore no FRET table at all, so after a restart their ring holds only self and there is nothing for this ticket to remember. Sereus is fixing that on its side (the strand peer book now; per its NOTE, passing db-p2p `persistence` once FRET's address-hints release lands). This ticket is what makes that persistence *sufficient*: without it, a restored table still yields a self-only cohort for as long as identify has not re-run.

## The rule

**A restart must not change which remembered peers this node counts as serving its network.** A peer this node positively classified `'serves'` (its peerStore protocols named this network's `cluster` or `repo` protocol) stays `'serves'` across a restart until fresh evidence says otherwise. Only positive verdicts are remembered — never `'unknown'`, never inferred from a network-size estimate — so a solo founder that has never met a serving peer, including one on a relay shared with other networks, is exactly as it is today.

Consequence, all through existing machinery: a restarted node with a restored table assembles the same cohort it had before the restart; the consult asks the remembered peers; while none of them answer, the read is flagged `'cohort-unreachable'` (the `isolated` absence verdict) rather than served as an authoritative absent; once one reconnects, the ordinary read-repair pass corroborates and acquires the block. It is the behaviour the same process would have shown had it never restarted.

## Design

In `Libp2pKeyPeerNetwork`:

- A remembered-serving set (peer id strings). `membershipOf(id, protocols)`:
  - non-empty `protocols` → classify from them, as today, and update the memory: `'serves'` adds the id, `'foreign'` removes it. The live peerStore always wins.
  - empty or missing `protocols` → `'serves'` if the id is remembered, else `'unknown'` as today.
  - self and the unscoped path (`protocolPrefix` unset) are unchanged.
- `PersistedNetworkState` gains an optional `servingPeers?: string[]`. Additive and optional, so no `PERSISTED_STATE_VERSION` bump: an older snapshot simply restores an empty memory. `persistState` writes the remembered ids **that are still in the FRET table it is exporting** (so the memory is bounded by FRET's capacity and forgets whom FRET forgets); `initFromPersistedState` loads it after the table import.
- The memory is learned from classifications `findCluster` / `findCoordinator` already make, so it needs no new peerStore reads. It is saved by the next `persistState` (driven by connection events); a verdict learned and lost to a crash before any save is simply re-learned — note that at the field.

Nothing in `CoordinatorRepo` changes: the solo-self exit stays exactly as it is for a node that genuinely remembers no serving peer.

**How long doubt lasts when a remembered peer never returns.** The release is FRET's own liveness, the same rule internals.md already states for unsettled claims ("what settles doubt… is cohort membership, not a timer"): FRET resets a restored entry's contact-failure counters, re-probes it, and once it marks the peer dead `assembleCohort` stops returning it, the cohort shrinks to self, and the solo-self exit answers again. Until then, reads of blocks this node lacks fail loudly and creating a *new* collection through this node fails (its header probe cannot be ruled absent). That is an availability cost — but it is the cost the node already pays today, before a restart, when a remembered partner goes offline; this ticket only stops a restart from erasing it. State that consequence in the doc update, and leave an accepted-tradeoff `NOTE:` at the remembered-serving fallback in `membershipOf` with the revisit condition: if a two-machine deployment reports that it cannot create collections after its partner is permanently gone, the remedy is a declared member list (`backlog/feat-declared-membership-feeds-cohort-assembly`) or an explicit "forget peer" operation, not dropping the memory.

**Staleness.** A remembered peer that has since moved to a different network is admitted until it reconnects and identify replaces its protocol list; its dials fail at protocol negotiation and the existing exclude-and-retry absorbs them — the same cost a stale FRET entry already imposes.

## Considered and declined (from the fix ticket's questions)

- *Keep blocks a node read — or served through read-repair — as its own replica.* Read-repair already persists what it acquires, through the corroborated or certified restore path. A block served to this node by a *remote* coordinator is not stored, and should not be: that answer arrives with no commit proof and no corroboration, and storing it would make this node a future corroborator of one peer's word — the hazard the certified-push gate exists to close (internals.md § SpreadOnChurnMonitor → *Certified push*).
- *Treat any prior sign of a larger network (the high-water mark, FRET's size estimate, a non-empty store) as evidence.* Rejected: the high-water mark counts FRET peers of any kind, including a shared relay or other networks' peers, so a solo founder behind a relay would have every new-collection probe flagged and could never create anything. Only a positive per-peer "serves this network" verdict is safe evidence. A node started without `persistence` has no such evidence across a restart and keeps today's cold-boot behaviour.
- *Wait at the solo-self exit for the view to grow.* Rejected in favour of flagging: a flagged read already earns `NetworkTransactor.get`'s second-chance retry against another coordinator, and the caller owns the per-read policy on `BlockUnavailableError.reason` (internals.md says so); a hidden wait inside `get` would stall every read on an isolated node.
