# A two-member pend defers its final delivery to the commit

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29), question 2. The design, the correctness argument against `docs/correctness.md`, and the rejected alternatives are in the decision ticket `decide-whether-a-two-machine-write-drops-to-three-calls`; read it first (if it has been deleted on acceptance, `git log` for it). This ticket builds on `a-cluster-request-carries-owed-consensus-deliveries`, which lets a request carry decided records the target is still owed.

## Today, on a two-member cohort

Coordinating node C, other member R. Each consensus operation (`executeClusterTransaction` in `packages/db-p2p/src/repo/cluster-coordinator.ts`):

1. C's member pre-votes its promise in process (`prevoteLocalPromise`).
2. **Request 1** — promise round to R. R adds its promise, sees two approvals of two, and in the same delivery also signs its commit (`ClusterMember.processUpdate`'s phase loop runs `OurCommitNeeded`). `collectPromises` keeps only R's promise and drops that commit signature.
3. C's member pre-signs its commit (`presignLocalCommit`).
4. **Request 2** — commit round to R, carrying C's commit. R now holds two commits of two, reaches consensus and applies on receipt.
5. C's member applies in the consensus broadcast (`broadcastMergedRecord`, local first); no remote broadcast is owed.

A write is a pend operation then a commit operation (`NetworkTransactor.commit` → `commitInOneRound`), so four requests to R.

## After this ticket

1. **Keep R's promise-round commit when it was signed over the record's final promise map.** In `collectPromises`, after every answer is merged, take a responder's commit signature — only its own entry, `response.commits[peerId]` for the peer asked — when that response's promise map equals the merged `record.promises` exactly (same keys, same signature values). A commit signature covers `computeClusterCommitHash(messageHash, message, promises, membershipDigest)`, so equal maps mean the signature verifies against the final record; any difference means it would not, and it is dropped exactly as today (and must never reach a member, which would penalize R for `InvalidSignature`). At the default threshold this holds only on a two-member cohort: on three or more, no remote member sees a super-majority while answering the promise round. Update the "promise round merges only promises" wording in `collectPromises`, `prevoteLocalPromise` and `docs/internals.md` (*Both consensus rounds carry the coordinator's own member's vote*) to state the narrowed rule and why it cannot reintroduce backlog `bug-a-late-promise-invalidates-the-commit-signatures-already-collected` (the kept signature is over the final map, and the coordinator merges no promise after it).
2. **C's member then reaches consensus during its pre-sign and applies.** `presignLocalCommit` already tolerates this ("the member would apply here and the broadcast would skip it as already executed"); rewrite its comment, since it becomes the ordinary path at two members. `commitTransaction` skips the commit round entirely when the record already carries a commit majority after the pre-sign, and goes straight to the consensus delivery for every remote peer that has not applied.
3. **For a pend, that delivery to R is deferred.** When all of the following hold, the remote deliveries are not made now; they are armed as owed deliveries (the retry machinery's `pendingPeers`, with the first interval `pendDeliveryDeferralMs`, and the deferral does not consume a retry attempt):
   - every operation in the record's message is a `pend`;
   - this node's member applied it and its retained verdict (`getExecutedPendResult`) is a success — a refused or missing local verdict delivers now, as today, so the writer's cancel finds every member in the usual state;
   - every awaiting peer has advertised `acceptsCarried`;
   - `pendDeliveryDeferralMs > 0`; and
   - the record's `message.expiration` (when set) is more than twice `pendDeliveryDeferralMs` away. A member that already voted refuses an expired delivery by throwing (`processUpdate`'s expiry guard), so a deferral must never run a record into its expiration.

   The owed delivery then rides on the next request C sends R — normally the commit operation's promise round, a few milliseconds later — or is sent on its own when the deferral elapses. Commit and cancel records are never deferred: a commit's acknowledgement waits on R's durability report (the gate in `CoordinatorRepo.commit`), and a cancel's on its discharge.

Resulting write: request 1 = pend promise (R promises and signs); C applies the pend. Request 2 = commit promise, carrying the pend's decided record: R applies the pend, then votes on the commit (its content check `validateCommitOperations` sees the pended transform), and signs its commit. C keeps that signature (rule 1), applies the commit, and request 3 delivers the commit's decision; R applies and reports holding the revision, and the durability gate passes. Three requests.

### Where the other member's pend refusal now arrives

Today R's pend verdict reaches the writer with the pend's answer (`cohortPendRefusals`, read off R's answer to the commit round). After this change, on a two-member cohort, R applies the pend only when request 2 arrives, so `CoordinatorRepo.pend` answers on C's own verdict. R's refusal arrives with the commit instead, and the commit must answer with it:

- `ClusterCoordinator` retains a conflict-shaped pend refusal reported on any carried or retried delivery of a pend record (`CarriedOutcome.outcome.pend`, or `applyOutcomes[peer].pend` on a retry answer), keyed by the pend's action id, until the record's expiration. Bounded (LRU, 1024 actions). A new pend transaction for the same action id (a writer's retry reuses its action id) drops any retained entry for it first, so a refusal is never attributed to a later attempt.
- A public `takeDeferredPendRefusals(actionId)` on `ClusterCoordinator` returns and removes the entries. `CoordinatorRepo.commit` calls it exactly once, after `executeClusterTransaction` settles (thrown or returned), and when the commit is **not** acknowledged — a thrown `ValidatorRejectionError` (R's `validateCommitAgainstRefusedPend` rejects the commit when its storage still corroborates the refusal), a lost race, a held answer, or the durability gate's `COMMIT_NOT_DURABLE_REASON` — answers with the first refusal in peer-id order as a returned conflict (it is already conflict-shaped; `isConflictFailure` must hold), logging `coordinator-repo:commit-deferred-pend-refusal`. When the commit **is** acknowledged (R abstained, the commit reached consensus and R reconciled the revision from C), the refusal is moot: log it and answer the acknowledgement. The writer handles a returned commit conflict by cancelling and re-driving, as it does for `commit-not-durable`.
- Update `docs/correctness.md` §2 (the "A pend that reaches pend-consensus is not thereby stored" paragraph) with the text proposed in the decision ticket, and the "Commit revision staleness" paragraph's remark that signing can precede applying "by a full propagation round" (on two members, up to the deferral bound or the commit's first request).

### Configuration

`pendDeliveryDeferralMs` in `ClusterConsensusConfig` (`packages/db-core/src/cluster/structs.ts`, beside `commitBroadcastRetryInitialMs`), resolved where `commitBroadcastRetryInitialMs` is (`coordinator-repo.ts` builds the coordinator config). Default **2000 ms**: the commit follows within milliseconds when the writer runs on the coordinating node, and within one writer-to-coordinator round trip otherwise; a deferral that elapses first costs only today's standalone delivery. `0` disables deferral and restores four requests. Document it in `packages/db-p2p/docs/cluster.md` beside the retry settings.

## Edge cases & interactions

- **Kept signature over a different map** (a threshold configured below the default, a three-member cohort where R saw only two promises) — dropped by the exact-equality check; never sent to a member. Covered by the unit test below.
- **C's pre-vote failed** (no C promise) — R sees one approval, signs nothing; today's path. By inspection.
- **C's member applies first now, on every two-member operation** — a behind C finds no holder on its first reconcile; once R reports holding, `broadcastMergedRecord`'s second reconcile (`reconcileLocalMemberAgain`) runs, the same path a four-member cohort uses. A behind R reconciles from C's proof-carrying copy on its first try. Re-read *A behind member actively reconciles* in `docs/internals.md` and rewrite its two-member sentences; check `packages/db-p2p/test/` specs that assume the remote applies first.
- **No commit follows the pend** (the writer cancels after another collection's pend failed, or crashes) — the deferral timer delivers the pend's record alone; a cancel sent before then carries it first, so R applies the pend and then the cancel. Pinned by a test below.
- **The commit is coordinated by a different node** (C failed between pend and commit) — R gets the commit before the pend; it abstains on content (no pended transform), and its commit apply reconciles from whoever holds the revision; the late pend delivery is then a pend of an action already committed, which `StorageRepo.pend`'s own-revision carve-out (`isOwnRevision`) treats as done. Verify that last step by reading `StorageRepo.pend`; if it would store a dead pending record instead, drop deferred deliveries for an action whose commit this node has seen fail over, or note the residual at the deferral site.
- **C crashes holding an owed delivery** — the durable transaction store is not wired in production (see backlog `debt-a-recovered-commit-retry-restarts-its-budget`), so the delivery is lost; R lacks only a pending record, and the next commit reconciles it. Note this at the deferral site.
- **A rival write coordinated by R during the deferral** — R approves (it no longer holds an in-memory reservation once it signed, and has not yet stored the pend), C votes `held` from its stored pending record, and on two members one `held` vote stops the rival (Theorem 9 is unchanged in kind; the window is longer). By inspection; say so in the comment at the deferral.
- **R on an older build** — never advertised `acceptsCarried`: no deferral, today's four requests. Pinned by a test below.
- **Reactivity certificates and block-holder evidence** — both members still apply with both commit signatures, so `captureCommitCert` and `reportBlockHolders` see the same signers as today. By inspection.
- **Pend durability class** (`pendCohortDurability`) counts promise approvals, which are unchanged. By inspection.
