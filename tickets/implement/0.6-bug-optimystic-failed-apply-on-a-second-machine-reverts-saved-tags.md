## The defect

Quereus applies a tag change to its own catalog and announces `table_modified`; the module never gets a statement. The listener (`followTableTags` → `saveTableTags` → `SchemaManager.persistTags`) then overlays **every tag of the engine's new table schema** onto the catalog record. It ignores what the event changed. So the record is overwritten with this machine's whole view of the tags, and that view can be older than the record.

The overlay runs on every `table_modified`, including the structural ones (`analyze`, ADD CONSTRAINT, and every undo step). The filed ticket described only the failed-apply path. Reproduction showed a wider bug: **no failure is needed.**

## Reproduction

All run at HEAD with sessions over one `MemoryRawStorage` (`openSession` in `test/alter-table-arms.spec.ts`). A declares `t` (`with tags (version = 1)`, `constraint pos check (a > 0)`) and `u (id, c)`. B hydrates. A applies the same with `version = 2`. A third session then hydrates to read the record.

| Case | B's steps | Record at HEAD | Should be |
|---|---|---|---|
| R1 | applies v2 plus `constraint one_c unique (c)` on `u` (the module refuses it; `u`'s steps run after `t`'s tag step) | `version = 1` | `version = 2` |
| R2 | `alter table main.t add constraint small check (a < 100)`, outside any apply | `version = 1` | `version = 2` |
| R3 | `analyze main.t` | `version = 1` | `version = 2` |
| R4 | A sets a column tag (`a … with tags (k = 2)`); B applies that plus the failing constraint | column tag gone | `k = 2` |
| R5 | B applies v2 plus a new column `d text null` on `u`, and the catalog commit is refused (`refusals = 1`, the transactor wrapper in the refused-commit test in `alter-table-arms.spec.ts`), so the undo runs in a second batch | `version = 1` | `version = 2` |
| R8 | A re-bodies a CHECK: `pos check (a >= 0) with tags (v = 2)`, from `check (a > 0) with tags (v = 1)`; B applies that plus the failing constraint | CHECK tags `v = 1` | `v = 2` |

Two cases that already pass and must keep passing:

- R6: B alone applies `version = 2` plus the failing constraint. The record goes back to `version = 1`, because B's own change is undone.
- R7: a column tag declared by an apply is saved.

In R1 the sequence is: B's `set tags (version = 2)` finds the record already saying 2; the later step fails; the undo `set tags (version = 1)` fires `table_modified`; the listener saves 1 over A's record.

## The fix

**Save what the event changed, one tag location at a time, judged against the record.** This is the rule the catalog-only ALTER arms already follow (`alterCatalogOnly`, `AdoptedChanges`), applied to tags.

A *slot* is one place an edit can address tags: the table, or a column, named CHECK, foreign key, non-derived UNIQUE constraint or index, by lowercase name. These are exactly the parts `withTagsOf` overlays today. Quereus replaces a slot's tags as a whole set (`SET TAGS`, and the undo the differ renders in `restoreTags` in `@quereus/quereus/src/schema/schema-differ.ts`), so a slot is the right unit to compare.

**1. In `tag-overlay.ts`, compute the changes.** `tagChangesBetween(oldObject, newObject)` returns `{ slot, before, after }` for each slot that **both** schemas have and whose tags differ. Normalise empty tags to `undefined` through `copyTags`, because `structuralEquals({}, undefined)` is false. Rewrite `withTagsOf` over two new helpers, `tagSlots(schema)` and `withTagsAt(target, slots)`; the instance side (`followSchemaTags`, `markSchemaUnpersisted`) keeps its full overlay, since an instance mirrors this machine's engine. Keep the existing `NOTE:` about derived UNIQUE constraints.

A slot only the new schema has is an object that appeared, and its tags are not a tag change. They reached the record through the hook that added the object (`alterCatalogOnly`, `createIndex`). This is what cures R8: the undo of an adopted CHECK drop re-adds the CHECK with its old tags, and the listener must not save those. The prototype confirmed no such object relied on the listener: R8's A side, and the declaration-round-trip tests in `test/hydrate-restores-declared-table.spec.ts`, pass.

**2. In `catalog-only-change.ts`, judge each change against the record.** A pure function, roughly:

```ts
export function tagsToSave(record, tableKey, changes, adopted: AdoptedChanges | undefined): Map<string, Tags | undefined> {
	const held = tagSlots(record);
	const save = new Map<string, Tags | undefined>();
	for (const { slot, before, after } of changes) {
		const key = adoptedChangeKey(tableKey, 'tags', slot);
		if (adopted?.undoes(key, tagSet(after))) {
			adopted.release(key);              // the undo of an adopted change: this machine's catalog only
		} else if (held.has(slot)) {
			if (sameTags(held.get(slot), after)) {
				adopted?.adopt(key, tagSet(before)); // the record already holds it: write nothing, remember the pre-change tags
			} else {
				save.set(slot, after);         // owned
			}
		}                                    // no such object in the record: nothing to address
	}
	return save;
}
```

Add `'tags'` to `CatalogObjectKind`. `AdoptedChanges` compares through `sameCatalogObject`, which **strips `tags` and `name`**, so wrap the tag set under another key (the prototype used `{ tagSet }`) or the comparison always matches. Extend the `AdoptedChanges` doc comment. A forward step cannot match an undo, because the differ emits one tag step per slot per apply.

**3. In `schema-manager.ts`, change `persistTags`.** It takes what to save, decided against the record it read, instead of a source schema (the prototype passed a `record => slots` callback, so both the batched and unbatched arms judge the record they read). `retagged` overlays only those slots through `withTagsAt`. An empty set yields `'unchanged'`, and nothing is written.

**4. In `optimystic-module.ts`, thread the event through.**

- `followTagChanges` passes `event.oldObject` as well as `event.newObject`.
- `followTableTags` always calls `table?.followSchemaTags(schema)`, then computes the changes and returns when there are none. That removes the catalog read each structural event costs today, so delete the `NOTE:` about it (and correct the sentence above it that says the save "finds the tags already saved").
- Capture `this.schemaBatch?.adopted` synchronously in the listener and pass it to the queued save. After a refused commit it is the carried `adoptedByRefusedBatch`, because `beginSchemaBatch` installs that on the batch; nothing else is needed for R5. Extend the `NOTE:` on `adoptedByRefusedBatch` to say it holds tag changes too.
- Keep `createSchemaManager` in the listener's synchronous part, so a manager created mid-apply joins the batch.
- Move `recordBatchEffect(manager, 'written', tableKey)` into `saveTableTags`, for outcome `'saved'` only. Today an adopted or undone change marks the table `written`, so a failed commit could re-persist this machine's older description, which is what the comment in `alterCatalogOnly` forbids. The batch is still open at that point: `endSchemaBatch` drains `catalogTagWrites` before it closes the batch.

## What this gives up

**A failed tag save is no longer repaired by the next DDL.** Today the next structural event re-overlays all tags, which incidentally retries a failed save. That same overlay is the defect, so it goes. After this fix a failed save stays out of the record until the next change to that slot, or until `apply schema` after a restart re-emits a declared tag. An imperative tag edit whose save failed is lost at restart. Failed saves are logged as `WARN`.

Keeping a per-table list of failed changes to retry was rejected: a failed save needs a network or storage fault, and the list would need the same judging plus an answer for retries that land inside a later apply. Record this at the catch in `saveTableTags` as a `NOTE:`, with the revisit condition "if hosts report lost tag saves, keep the failed changes per table and re-judge them on the next event".

## Conditional concerns to record as `NOTE:`

- At `tagChangesBetween`: an adopted added CHECK or column keeps the record's tags even when this machine's declaration gives it different ones. That takes two machines applying different schema versions. The machine's next apply emits a `set tags` once it has hydrated the record. Revisit if hosts apply differing versions at once.
- At `tagsToSave`, the owned arm: a change the record does not hold is written, so a machine applying an older declaration overwrites a newer tag, and its undo writes its pre-apply tags. This matches a CHECK's "local DDL wins" row in `classifyCheckChange`, and the README already tells hosts not to apply an older declaration.

## Tests

Keep to one test per behaviour, in the "inside apply schema, on one machine and on two" section of `test/alter-table-arms.spec.ts`, or beside it:

- R1: a second machine adopts a table tag already saved, and its failed apply leaves the tag in the record, while its own catalog goes back to 1. This is the ticket's reproduction.
- R3: a structural event on a machine holding older tags leaves the record's tags alone.
- R5: the same adoption with a refused commit; then the retry lands and the tag is still 2.
- R8: the undo of a dropped CHECK leaves the tags of the record's newer CHECK alone.
- R6: a machine's own tag change in a failed apply is taken back out of the record. Add it only if no existing test pins it.

R2 and R4 take the same paths as R3 and R1, so leave them out.
