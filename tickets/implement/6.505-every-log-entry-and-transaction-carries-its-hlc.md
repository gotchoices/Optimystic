# Every log entry and transaction carries its HLC

Second of the three Stage 1 tickets (see `the-hlc-clock-and-its-persistence-port` for the clock and the summary of the plan pass). This one puts the HLC on the wire and in the log. It changes no ordering: the revision number remains the order within a collection, the log-tail cohort still sequences, and nothing anywhere compares two HLCs except the clock's own `observe`.

## Where the HLC lives, and why not on the stamp

Three places, one value per write:

1. **On the log entry**, `LogEntry.hlc: Hlc`, beside `timestamp`, which stays. The entry is the unit a later merge orders, and a bare `Collection.sync` write has no transaction, so the entry is the one place every write reaches. `timestamp` is kept as the plain wall-clock time the writer's clock read when it wrote; `hlc.wallMs` is at or above it and may be a future time after an observed jump, so they are two facts, not one field twice. Removing `timestamp` would also churn every reader and fixture for no gain in Stage 1.
2. **On the transaction**, `Transaction.hlc: Hlc`, minted at commit, after the read set is final, and folded into the transaction id and the client signature. Not on the `TransactionStamp`: the stamp is fixed at BEGIN, before any of the transaction's reads, and an HLC minted then could sit below an HLC a later read observed, which is exactly the causal rule the HLC exists to keep (a change built on something read sorts after it). The plan ticket recommended the stamp; this is the correction, and it has a pleasant consequence for question 8 of that ticket: stamp ids do not change at all.
3. **On the pend request**, `PendRequest.hlc?: Hlc`, so a storage node observes the HLC of every write it stores without parsing log blocks out of transforms. Optional on the wire because older writers send none; the writer always sets it.

The transaction and the entry agree for one write because both read the same value: `writeContextOf` copies `transaction.hlc` into `WriteContext.hlc`, and `applyActionsToCollection` stamps that on every participant's entry, exactly as `timestamp` travels today.

## Minting sites, and the identity rule

The HLC is part of the write's identity under the rule in docs/internals.md §Key Invariants, "A write's log append is a fixed function of the write and the revision it is requesting": minted once per write, re-sent verbatim by every retry, whatever revision the retry requests. Four sites mint, all through `clockOf(transactor).now()` from the first ticket:

- `Collection.syncInternal` mints `WriteIdentity.hlc` beside the action id and `timestamp`.
- `TransactionSession.commit` mints `Transaction.hlc` after `getReadDependencies()`, through the coordinator's transactor (add a getter or pass the clock to the session; the coordinator holds `transactor` privately today). The Quereus bridge's legacy commit route fabricates a transaction at `commitBatchLegacy` (`txn-bridge.ts`, where `createTransactionStamp` is called with `LegacyCommitEngineId`) and mints there the same way.
- `OfflineQueue.enqueue` mints `Entry.hlc` beside `queuedAt`, through the sealed collections' shared transactor (`sharedTransactor` already requires one). This is the user's local commit time in HLC form, which is the local-first semantics [docs/offline-sync.md §Relation to the other designs](../../docs/offline-sync.md#relation-to-the-other-designs) maps onto crdt-sync's local / propagated / stable states. The entry's HLC is journaled (`JournalEntryRecord.hlc`, and the plugin's `EntryRecordV1`), `restore` re-supplies it through the same `init` that re-supplies `queuedAt`, and every drive of the entry, first or re-drive, passes it as `HeadCommitOptions.hlc` or `EntryCommit.hlc`. A journal record written before the field existed restores with `legacyHlc(queuedAt)`.
- `applyInvalidation` in `packages/db-p2p/src/dispute/invalidation.ts` mints for the compensating entry it appends; `Log.addInvalidation` and `Log.addCheckpoint` take the HLC as a parameter rather than a default, the way they take `timestamp`, so every entry kind carries one (the plan's recommendation that every entry does, taken). No caller writes a checkpoint today (backlog `debt-the-collection-log-never-writes-a-checkpoint`), so `addCheckpoint` just gains the parameter.

What does not mint: a retry at the same or a new revision (`stageAttempt` and `applyActionsToCollection` stamp what they are given); a resumed head commit (`resumedAttempt` re-sends the recorded attempt whole, HLC inside); `TransactionCoordinator.execute`, which stamps the transaction it was handed; a validator's re-execution (`TransactionValidator.validate` runs the engine over an isolated coordinator, whose `writeContextOf` reads the HLC off the transaction, so the operations hash it computes matches the writer's, since the log tail's operations include the entry); a refresh's `completeOwnEntry`, which re-sends retained transforms.

One imprecision is accepted and recorded as a `NOTE:` at `WriteIdentity.hlc`: a write refused as stale is retried over a refresh that may have observed newer HLCs, and the retry keeps the HLC it was first minted with, so its entry can carry an HLC below a rival it was re-staged over. In the strong lane the revision is the order and the HLC is observational, so nothing is wrong today; the replay stage (backlog `feat-replay-mode-collections-merge-divergent-histories`) commits locally without a log-tail retry, so it never meets the case.

## The transaction id and the signature

`createTransactionId(stampId, statements, reads, hlc)` folds the HLC into the id: the doc's table row for the transaction id says `id includes hlc`, and the id is what the log records as the action id, so two transactions that differ only in when they committed differ in id. `clientSignaturePayload` folds it too and bumps `CLIENT_SIG_VERSION` to `txsig:v2`: in Stage 2 validators order by the HLC, so a relaying peer must not be able to alter it, and that is a signed-bytes question best settled while nothing verifies. Both signer and verifier derive the bytes through the one function, so the change is one place. Mixed-version cost: a writer on an older build signs the v1 payload and a verifier on this build would report an invalid signature against it; accepted on the precedent the validity marker set (docs/internals.md, *A reject that judges the transaction itself wrong*), because no deployment wires a `ClientSignatureVerifier` today (backlog `feat-no-deployment-validates-transactions-at-pend`). Say so in the `CLIENT_SIG_VERSION` comment.

The validator's one wire ingress, `validation.transaction` on a pend from a remote writer, reads `transaction.hlc ?? legacyHlc(transaction.stamp.timestamp)` so a transaction from an older build still validates. `Transaction.hlc` is required on the type; only that ingress tolerates its absence.

## Legacy entries and the fixtures

`LogEntry.hlc` is written on every new entry and is optional only in the sense that stored entries predate it. One reader rule, `hlcOf(entry)` in `packages/db-core/src/log/struct.ts`: `entry.hlc ?? legacyHlc(entry.timestamp)`. `nodeId` is absent on a legacy entry, which the legacy rule renders as `''`. Nothing in this ticket reads it; the third ticket's feed points do. The upgrade-check fixtures stay readable with no documented upgrade step and nothing retired: an entry without the field reads as before, the fixtures' in-flight pend carries no `hlc` and is applied as before, and the diary appended on top gets entries with the field, which the older code never reads. Do not add an assertion to the upgrade spec for this; recording a field is wiring.

The log block's content digest (`describeTouchedBlocks`) and the storage-side preview (`previewCommitDigest`) both hash the same transforms the writer sent, entry and `hlc` included, so a member on this build and a writer on this build agree; a member on an older build hashes the bytes it was sent, which carry the field, so it agrees too. By inspection of `packages/db-core/src/transform/digest.ts`.

## Edge cases & interactions

- **Retry of a torn write re-sends its HLC**: the retained attempt (`retainInFlightAttempt`) holds the transforms with the entry inside. By inspection of `completeOwnEntry`.
- **A rebuilt attempt at a new revision keeps the HLC**: `stageAttempt` stamps `identity.hlc`; `applyActionsToCollection` stamps `context.hlc`. Pinned by the extended retry spec, which asserts byte-identical transforms across attempts and would fail if either site minted per attempt.
- **A head commit resumed after a restart**: the journal's drive record holds the attempt whole; the entry record holds `hlc`; a re-drive that rebuilds (new revision) uses the entry's `hlc`, so the rebuilt entry differs from the recorded attempt only in what the revision change already makes differ. By inspection of `OfflineQueue.send` and `resumedAttempt`.
- **A journaled entry from before the field**: restored with `legacyHlc(queuedAt)` and driven with it; its entry then carries an HLC whose `nodeId` is `''`. Acceptable: it is the one shape a legacy entry already has. By inspection of `decodeEntryRecord`.
- **A SQL transaction over a table and its indexes**: one `Transaction.hlc`, one `WriteContext`, the same HLC on every participant's entry. By inspection of `commitOnce`.
- **The per-entry commit over several collections** (`commitEntryOnce`): builds its `WriteContext` from `entry.hlc`, as it builds `timestamp` from `entry.timestamp`. By inspection.
- **`TransactionCoordinator.execute` re-run by a caller with the same `Transaction` object**: same id, same HLC, and that is one write; a caller that builds a new transaction gets a fresh HLC through `TransactionSession.commit`. The existing `NOTE:` at `applyActionsToCollection` about `execute` and in-flight marking is unchanged.
- **The pend's `hlc` and the validation payload disagree**: they cannot, both come from `WriteContext.hlc`; `TransactorSource.transact` takes the HLC through its options the way it takes `baseRevs` and `priority`, from the attempt's identity.
- **A batch pend of several collections** (`NetworkTransactor.pendMany`): every request in the batch carries the same `hlc`, since they are one action; a member reading the batch observes it once per request, which is idempotent. By inspection.
- **Checkpoint and invalidation entries**: carry an HLC like action entries. The invalidation's comes from the node that applies the dispute ruling, through `clockOf` on the transactor it appends with; by inspection of `applyInvalidation`.
- **`Transaction` objects built in tests and in the Quereus bridge**: the required field makes `tsc` list every construction site. Fix each by minting through the transactor at hand or, in a pure unit test with no transactor, through a `TestTransactor().clock`.

## Tests that pay for themselves

Extend `packages/db-core/test/retry-resends-identical-transforms.spec.ts`: its four cases already assert on the whole transform set, so they fail for any per-attempt value; add to each case one assertion that the entry recorded by the committing attempt carries an `hlc` whose `nodeId` is the transactor's, which is the one fact the whole-set assertion cannot pin (two attempts could agree on a missing field). No new spec file. Nothing for the queue's journaling of the field, the transaction id or the signature payload: the existing session and journal round-trip specs exercise those paths and will fail to compile until the field is threaded.
