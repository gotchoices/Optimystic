First half of stage 7 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages): compute `CommitOutlook` from the staged actions' guards and the queue alone, deliver it on the `queued` status, and answer it from a `CommitOutlook()` SQL function. No Quereus change. The second half — keeping the outlook current as earlier entries settle (`outlook-changed`), and the `offline:assured-entry-failed` log — is ticket `offline-sync-outlook-follows-the-queue`, which builds on this one.

Read first: [docs/offline-sync.md §Predicting whether an entry will commit](../../docs/offline-sync.md#predicting-whether-an-entry-will-commit) (the whole section), and the guard paragraphs in [docs/internals.md §Conflict replay re-makes the uniqueness decision](../../docs/internals.md#conflict-replay-re-makes-the-uniqueness-decision-entry-guards).

## Background in one paragraph

Every queued transaction ("entry") holds, per collection it wrote, a sealed segment of tree `replace` actions (`Collection.sealedActions(entryId)`). Each action's `data` is a list of elements `[key, entry?, guard?]` (`TreeReplaceAction` in `packages/db-core/src/collections/tree/struct.ts`). The guard is the check the drain's rebase re-runs: `absent` (main-table INSERT — refused when another writer took the primary key), `absentRange` (on a UNIQUE-enforcing index tree — refused when another writer took the unique value), `unchanged` (main-table UPDATE / DELETE / REPLACE / eviction — refused when another writer changed or removed the row), `keepExisting` (never staged by SQL any more; never refuses). Index trees other than UNIQUE-enforcing ones carry no guards. All plugin trees are string-keyed and ordered by raw string comparison (`resolveTreeArgs` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`), so key equality is string equality and range membership is plain string comparison.

## Decisions settled here

**Types** (new file `packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-outlook.ts`, exported from `plugin.ts` and the root `index.ts` beside the other offline types). As in the doc's `CommitOutlook`, `Exposure`, `UncheckedDecision`, with one change: `unchecked` is `readonly UncheckedDecision[] | 'not-computed'`. Stage 7 always answers `'not-computed'` — it has no description of what the statements read. A string rather than `undefined` because the same value is rendered as JSON by `CommitOutlook()`, where an absent key would be ambiguous. Stage 9 answers an array when every statement of the entry was described, and `'not-computed'` otherwise.

**The own judgement — one pass over the entry's elements, in staging order.** For each element carrying a guard, in collection `C` at tree key `K`:

1. **Covered by an earlier write of the same entry.** If an earlier element of the same entry (an earlier action, or an earlier element of the same action) in `C` wrote exactly `K` and carried an `absent` or `unchanged` guard, the guard is not judged: any rival change that refuses it refuses that earlier guard first. This is what makes "insert under a fresh key, then update it, in one transaction" assured, and keeps "insert under a natural key, then update it" to one exposure. Only an exact-key `absent`/`unchanged` covers; an unguarded earlier write (an index-tree delete) or an `absentRange` covers nothing.
2. **`absent`** → exposure `{ table, rule: 'primary-key', key: decodePrimaryKey(K) }` unless the table's primary key is fresh: at least one primary-key column carries `"optimystic.fresh" = true` (the doc's "for a composite key, any one column is fresh").
3. **`absentRange`** → exposure `{ table, rule: 'unique', columns, key }` unless the unique value is fresh (at least one of the constraint's columns is tagged fresh). `columns` are the constraint's column names; `key` is the unique value decoded from the range's lower bound, which is the framed index value (`indexValueRange` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts`). Read the bound structurally (`range.first?.key`): a guard restored from the journal is a plain object, not a `KeyRange`.
4. **`unchanged`** → exposure `{ table, rule: 'row', key: decodePrimaryKey(K) }` unless the table carries `"optimystic.single_writer" = true`, or an earlier unsettled entry of the queue staged an `absent`-guarded insert at `K` in `C` and the table's primary key is fresh (the row was created offline under a fresh key, so no other machine can know it).
5. **`keepExisting`, or no guard** → nothing; it can never refuse.
6. **Anything the analysis cannot read** → an exposure, never silence ([§Conservative by construction](../../docs/offline-sync.md#conservative-by-construction)): an unknown guard kind (a later build's), an action whose `type` is not `'replace'`, a guard in a collection no table describes, an `absentRange` on a collection not described as a UNIQUE-enforcing index tree, or a key that fails to decode. Report `{ table, rule: 'row', key: undefined }`, with `table` the collection's table name when known and its collection id otherwise.

Tags are read as `=== true`, the rule the module already reads `optimystic.network_watch` by (`wantsNetworkWatch` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`). Exposures are listed one per judged guard, in staging order.

**Dependencies (`dependsOn`, `via: 'guard'`).** A guard depends on every earlier unsettled entry whose sealed segment in the same collection writes inside what the guard covers: the exact key for `absent` and `unchanged`, the range for `absentRange`. This is wider than the doc's "an `unchanged` guard over a row an earlier entry wrote": an `absent` re-insert of a key an earlier entry deleted, or an `absentRange` over a value an earlier entry freed, also refuses when that earlier entry fails — conservative by construction covers them. Covered guards (rule 1) contribute no dependencies of their own. Each transaction id is listed once, in queue order. Also listed: every journaled transaction still deferred by the restore (`OfflineRestore.records()`, not yet put back) whose `tables` intersect this entry's and whose `seq` is lower — its writes are not staged, so they cannot be matched by key, and it counts as exposed.

**Kind.** `assured` exactly when the entry has no exposure and every entry in `dependsOn` is assured (a deferred record is never). An assured dependency can still fail for reasons the prediction does not cover (expiry, discard, rejection), which is why it stays listed.

**When it is computed, and what is frozen.** The outlook is computed from the sealed segments when the queue emits the entry's first `queued` status — inside `OfflineQueue.enqueue` (after sealing, before `commit` resolves) or inside `OfflineQueue.restore` for an entry put back after a restart — and held by the controller per transaction id until the entry settles. "Earlier unsettled entries" are those before it in `OfflineQueue.entries()` order. The own judgement (exposures, with the collection each came from) is fixed then and never recomputed: tags changed later, or an earlier entry committing, do not re-judge it — that is what makes the outlook move in one direction only (the follow-up ticket recomputes only `dependsOn` and `kind`). Nothing new is journaled: a restart recomputes it on restore.

**Where table knowledge comes from: pulled from the vtab, not pushed.** The analysis needs, per collection id, whether it is a table's main tree (with the primary-key decoder and whether the key is fresh), a UNIQUE-enforcing index tree (with the constraint's column names, whether the value is fresh, and a value decoder), or another index tree; plus the table's name and `single_writer` tag. Each vtab publishes a `TableOutlookSource` with one method, `describe(collectionId)`, from the same call site and at the same moments it publishes its offline policy (`publishOfflinePolicy` / `withdrawOfflinePolicy` → `OfflineMode.setTablePolicy` / `withdrawTablePolicy`; extend `PublishedTable` with it). `describe` reads the vtab's live `tableSchema` tags, `rowCodec`, and `resolveEnforcingIndex` at call time, so a tag change or an index created or dropped later needs no re-publication. The controller finds a collection's tables through `TransactionBridge.tablesOf(id)` and asks the first published source that describes it.

**Decoding a unique value.** New `decodeIndexKey(indexKey, affinities)` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts`, beside `serializeIndexValue`, its rendering-only inverse: `splitKeyTuple`, then per element `null` for a NULL element, a number for a numeric affinity (`Number(payload)`; bigints are already lossy in the index encoding, as the `NOTE:` there says), bytes for BLOB (base64), the payload string otherwise. Never throws (a renderer must not be the second failure); a payload that does not parse stays its string.

**Reading the open transaction.** New `Collection.openActions(): readonly Action<TAction>[]` in `packages/db-core/src/collection/collection.ts` — the open segment, synchronous and latch-free like `sealedActions`. `getPendingActions` cannot serve: it throws while anything is sealed.

**`CommitOutlook()`** (`packages/quereus-plugin-optimystic/src/functions/commit-outlook.ts`, registered in `plugin.ts` beside `StampId` with the same flags, `numArgs: 0`, nullable TEXT): `NULL` when `TransactionBridge.getCurrentTransaction()` is not active (the `StampId()` rule); otherwise the JSON of the outlook a transaction with the open segments of every collection the transaction staged into would get if sealed behind everything queued now (every queue entry and deferred record counts as earlier). Synchronous — everything it reads is in memory. Computed by the same function the queue path uses (one method on `OfflineMode`, e.g. `openTransactionOutlook()`), never a second copy. It works outside offline mode: with nothing queued `dependsOn` is empty and the answer is whether the commit can lose a race at all. JSON renders `SqlValue`s the way Quereus renders them in its own JSON output (`jsonStringify` in `@quereus/quereus/src/util/serialization.ts`, not exported): a bigint as a number when it is a safe integer and as a decimal string otherwise, bytes as `0x` followed by hex.

**Status shape.** `queued` gains `outlook?: CommitOutlook`, present on every entry the queue holds and absent exactly while `waitingFor` is `'restore'` — a transaction not back in the queue cannot be judged, and its first `queued` status after being put back carries it. `QueuedTransaction.status` carries it the same way. The db-core `EntryStatus` carries no outlook: the judgement needs the catalog's tags and key decoding, which only the plugin has. Correct the sentence in docs/offline-sync.md §Following transactions that says the db-core queue's `outlook` arrives with stage 7.

## Edge cases & interactions

- **Insert then update in one transaction under a fresh key** → assured, no dependency (rule 1). Under a natural key → one `primary-key` exposure, no `row` exposure. Test.
- **Update of a row an earlier queued entry inserted under a fresh key** → own judgement clean (rule 4), `dependsOn` names that entry, kind assured when it is. Test.
- **Update of a row committed before going offline (shared row)** → `row` exposure with the decoded key. Test.
- **Insert into a table with a fresh primary key and a natural UNIQUE column** → `unique` exposure with the column names and the decoded value; the primary-key guard is not exposed. Test (pins `decodeIndexKey` through the outlook).
- **`single_writer` table**: an update is not exposed, an insert under a natural key still is (`absent` is not covered by the tag). Verify by inspection of rule 2/4; the follow-up ticket's `outlook-changed` test uses this tag.
- **Primary-key move (`update … set id = …`)**: the delete half is an `unchanged` guard on the old key, the insert half `absent` on the new — judged independently. By inspection.
- **REPLACE / eviction**: `unchanged` on the displaced row → `row` exposure. By inspection.
- **Entry put back by restore while an older record is still deferred** → the deferred transaction is in `dependsOn` and the entry is exposed. By inspection (the restore spec already builds the deferral; add an assertion there only if it is one line).
- **Entry restored after a restart** → outlook recomputed on its first `queued`, against the entries restored before it. No journal format change. By inspection.
- **Sealed segment already refused when the outlook is computed** (a reader's refresh found the refusal first) → judged normally; the entry is about to fail. By inspection.
- **Two tables declared over one URI** → the collection is described by the first published source that answers; acceptable for the one-table-per-collection shape every caller uses (the same caveat `assertNoQueuedEntries` records).
- **Savepoint rolled back before `CommitOutlook()`** → `openActions()` reflects the restored open segment. By inspection.
- **`CommitOutlook()` inside a statement that also writes** → reflects what is staged at the moment it is evaluated. Document in the README.
- **Bulk offline write of N natural-key rows** → N exposures on one status. Leave a `NOTE:` tripwire at the exposure loop: if bulk offline writes make statuses heavy, cap the list and mark it truncated.
- **Cost of the key index**: built from every earlier entry's sealed actions on each computation, so a long queue makes each enqueue linear in the queue. Leave a `NOTE:` tripwire: if enqueue shows up slow behind a long queue, keep the written-key index incrementally. Range dependencies scan the earlier writes of one collection linearly — same note.
- **Exhaustive switches over `QueuedTransactionStatus.kind`** stay unchanged in this ticket (no new kind yet).
