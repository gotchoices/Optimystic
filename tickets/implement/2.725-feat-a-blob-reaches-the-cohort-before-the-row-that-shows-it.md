# A blob reaches the cohort before the row that shows it

docs/blobs.md §Committing a reference ends with the pattern an application uses when it must not expose a reference before the bytes have moved:

> **An application that wants the bytes on the network before anyone sees the reference** commits twice. It first commits a row that only holds the reference (an attachment row), which is what authorizes the cohort to store the blob. It waits for `onDurability` to report `majority` or `full`. Then it commits the row people act on (the message that shows the attachment). The second commit cannot land before the bytes are held by others, and no machine ever stored bytes that no committed row referenced.

`feat-blob-pins-follow-sql-commits` built every link in that chain and pinned each one on a single machine, where the cohort is that machine alone and durability therefore never leaves `local`. Nothing yet runs the chain across two real machines, which is the only place the interesting parts are real: the announcement going over the wire, the receiver reading committed state to decide it may store the blob, the pull, and the durability class rising past `local`.

This ticket is one integration spec. It changes no production code.

## The spec

`packages/quereus-plugin-optimystic/test/two-node-blob-reference.integration.spec.ts`, gated on `OPTIMYSTIC_INTEGRATION=1` with `if (!process.env.OPTIMYSTIC_INTEGRATION) this.skip();`, as `two-node-secondary-index-libp2p.integration.spec.ts` is — follow that file for the node construction, the `NetworkTransactor` per node, the local-TCP multiaddr pick, the bounded `waitFor`, and `clusterPolicy.assumedClusterSize: 2` against a replication factor larger than the machine count. Two real libp2p nodes, each driving its own `Quereus` `Database` over its own transactor, each with the plugin registered (`types` included, so `blobref` resolves). Both nodes must accept blobs, which is the default (`NodeOptions.blobs`'s `hold: 'eager'`).

Two tables, over the `network` transactor:

```sql
create table Attachment (Id text primary key, Content blobref null) using optimystic('tree://two-node-blob/Attachment');
create table Message (Id text primary key, Body text, AttachmentId text) using optimystic('tree://two-node-blob/Message');
```

The run, on node A:

- `plugin.blobs.put` a blob big enough to be several pieces, so the copy is a real multi-piece pull rather than one root piece.
- Subscribe `plugin.blobs.onDurability` **before** the first commit, collecting the events for that reference.
- `insert into Attachment (Id, Content) values (?, ?)` — the row that holds only the reference. Its commit announces the blob; by the time `db.exec` resolves, the first durability event for that reference has already arrived (that is the ordering `feat-blob-pins-follow-sql-commits` guarantees).
- Wait, bounded, for an event reporting `majority` or `full` for that reference.
- Assert, **before** the second commit, that node B answers `node.blobs.stat(ref).locality === 'here'`: B pulled the blob because A's announcement plus B's own read of committed state authorized it.
- `insert into Message (Id, Body, AttachmentId) values (?, ?, ?)` — the row people act on — and assert node B reads it.

Timeouts belong on the `describe`, generous as in the precedent (two real nodes, convergence, a multi-piece transfer); every wait inside is a bounded `waitFor` with a message naming what it waited for, never a bare `delay`.

## Edge cases & interactions

- **A durability class that never rises.** With two accepting members, `full` is "every accepting member holds it and at least one is not this node", `majority` a strict majority of them; a two-member cohort reaching one copy on B satisfies both readings the classifier (`classifyBlobDurability` in `packages/db-p2p/src/blob/blob-durability.ts`) can give. Accept either class and fail on the bounded wait, naming the last class seen — so a failure says "stalled at `local`", not "timed out".
- **B must be in the blob's cohort.** The routing key is the digest in the reference (`routingKeyForBlob`), so which nodes are responsible is not under the test's control. With `assumedClusterSize: 2` and two nodes both serving, both are in every cohort; if that turns out not to hold in practice, assert it up front from A's own cohort view rather than letting the durability wait time out with no explanation.
- **The announcement is not retried by the test.** The owed-copies drain re-announces on its own schedule (`DrainScheduler`), which is what makes the bounded wait sound rather than a race against a single attempt. Inspection.
- **Reading the blob's bytes on B is not part of this.** `stat(…).locality === 'here'` is the claim the two-commit pattern rests on, and `packages/db-p2p/test/blob-network-read.spec.ts` already pins a verified read across two machines.
