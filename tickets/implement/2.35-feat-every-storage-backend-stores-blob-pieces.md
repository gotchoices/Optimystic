# Every storage backend stores blob pieces

The three prerequisites have landed. `IPieceStore` is in `packages/db-p2p/src/blob/piece-store.ts`; `runPieceStoreConformance` and `conformancePieceId` are exported from `@optimystic/db-p2p/testing/conformance` (`packages/db-p2p/src/testing/piece-store-conformance.ts`); `FilePieceStore` (`packages/db-p2p-storage-fs`), `SqlitePieceStore` (`packages/db-p2p-storage-ns`) and `IndexedDBPieceStore` (`packages/db-p2p-storage-web`) implement it. The node takes `NodeOptions.pieceStorage` (instance or factory; the node never closes it) and exposes `node.blobs` (`LocalBlobService`). This ticket adds the last backend, `LevelDBPieceStore` in `@optimystic/db-p2p-storage-rn`, and the upgrade suite's share.

`SqlitePieceStore` (`packages/db-p2p-storage-ns/src/sqlite-piece-store.ts`) and its spec are the closest model: same shared-handle shape, same paged `list`, same `storeIdentity` rule, same "no `close`".

The interface, as landed:

```ts
interface IPieceStore {
	has(id: PieceId): Promise<boolean>;
	get(id: PieceId): Promise<Uint8Array | undefined>;   // bytes no one else holds
	put(id: PieceId, bytes: Uint8Array): Promise<void>;   // a present id writes nothing; store keeps its own copy
	delete(id: PieceId): Promise<void>;
	list(): AsyncIterable<PieceId>;                        // drain each native cursor before yielding
	bytesUsed(): Promise<number>;
	flush(): Promise<void>;
	readonly durability: StoreDurability;
	storeIdentity?(): StoreIdentity;                       // equal to the block store's getStoreIdentity() exactly when that store already measures these bytes
	close?(): Promise<void>;
}
```

`StorageMonitor` reads `storeIdentity` through `blockStoreCountsPieces` in `packages/db-p2p/src/storage/storage-monitor.ts`: equal identities mean the block store's byte figure already includes the pieces, so it is not added again.

## Part 1 — `LevelDBPieceStore`

### Key layout

**Tag `0x08` is taken** (`TAG_COMMIT_PROOFS`, added after the plan was first written). The pieces take the next free byte, in `packages/db-p2p-storage-rn/src/keys.ts`:

```ts
export const TAG_PIECES = 0x09;
```

It keeps the file's rule that `tag + 1` bounds a tag's range and that no tag straddles another: the commit-proof range is `[0x08, 0x09)`, the piece range `[0x09, 0x0A)`, and the key-value tag is `0x10`. No released build has written a key under `0x09` (no fixture under `packages/upgrade-check/fixtures` can hold one, since every one predates this ticket).

Two kinds of key under it, told apart by the byte after the tag:

| Key | Value |
|---|---|
| `TAG_PIECES ‖ 0x00 ‖ UTF-8(id)` — the piece | the piece's bytes |
| `TAG_PIECES ‖ 0x01 ‖ UTF-8(id)` — its size | the piece's length, 4 bytes big-endian unsigned |

Every write puts or deletes both in one batch, so a piece and its size are present together or not at all. The size key exists so that nothing has to read piece bytes to measure them: `bytesUsed`, `has` and `list` read only size keys, and the block store's measurement uses them too (below). Pieces are at most 1 MiB (`MAX_BLOB_PIECE_BYTES`), far inside 4 bytes.

New exports, documented in the file's layout comment (beside the journal and commit-proof paragraphs; the "deliberately spaced" sentence names `0x09` as taken):

```ts
export function pieceKey(id: string): Uint8Array;
export function pieceSizeKey(id: string): Uint8Array;
/** Every size key: [TAG_PIECES, 0x01] up to [TAG_PIECES, 0x02]. */
export function pieceSizeRange(): { gte: Uint8Array; lt: Uint8Array };
/** Every key under the tag, both kinds: [TAG_PIECES] up to [TAG_PIECES + 1]. */
export function pieceRange(): { gte: Uint8Array; lt: Uint8Array };
/** The id a size key names. */
export function pieceIdFromSizeKey(key: Uint8Array): string;
export function encodePieceSize(size: number): Uint8Array;
/** The length a size value holds, or `undefined` when it is not 4 bytes. */
export function decodePieceSize(value: Uint8Array): number | undefined;
```

`pieceIdFromSizeKey` decodes with the file's lazy `textDecoder()`; ids are short ASCII, and the `NOTE:` at `actionIdFromKey` already records the polyfill cost of decoding keys on Hermes.

### The store

New module `packages/db-p2p-storage-rn/src/leveldb-piece-store.ts`, exported from `src/index.ts` beside `LevelDBKVStore` (export `PIECE_LIST_PAGE` from the module for the spec, not from the index, as the NativeScript package does).

```ts
export const PIECE_LIST_PAGE = 1000;

export class LevelDBPieceStore implements IPieceStore {
	/** `'power-loss'` when the handle can sync (`LevelDBLike.canSync`), else `'process-crash'`; the rule `LevelDBJournalStore` follows. */
	readonly durability: StoreDurability;
	constructor(db: LevelDBLike);
	/** `identityForHandle('leveldb-handle', db)`: the identity `LevelDBJournalStore` (and so `LevelDBRawStorage.getStoreIdentity`) reports over this handle. */
	storeIdentity(): StoreIdentity;
	has(id: PieceId): Promise<boolean>;
	get(id: PieceId): Promise<Uint8Array | undefined>;
	put(id: PieceId, bytes: Uint8Array): Promise<void>;
	delete(id: PieceId): Promise<void>;
	list(): AsyncIterable<PieceId>;
	bytesUsed(): Promise<number>;
	flush(): Promise<void>;
}

/** The bytes the pieces under `TAG_PIECES` hold, summed from their size keys; reads no piece bytes. */
export async function measurePieces(db: LevelDBLike): Promise<number>;
```

Share the `'leveldb-handle'` scheme string with `LevelDBJournalStore` through one exported constant rather than two literals (`SQLITE_HANDLE_SCHEME` is the NativeScript precedent).

- **Bytes, never text.** `get` is `db.get(pieceKey(id))`, the bytes-returning read; nothing in the module calls `getText` or `textIterator`. React Native's block store reads values as text through the engine's UTF-8 decoder, and piece bytes are not UTF-8: a piece whose bytes happen to be valid UTF-8 is still read as bytes. Confirm the returned array is one no one else holds: the `rn-opener.ts` adapter builds a fresh array over the native buffer and the test driver copies; if either could return a shared view, copy in `get`.
- **`has`** is `db.get(pieceSizeKey(id)) !== undefined`: a 4-byte read, never the piece.
- **`put`**: when `has` answers true, return; otherwise one batch putting the piece and its size, written with `{ sync: db.canSync }`. `batch().write(...)` is the only write `LevelDBLike` offers. A sub-view `bytes` must be stored as exactly its bytes (the batch adapter must not send the whole underlying buffer — check `rn-opener.ts`'s `toArrayBuffer`; copy a sub-view first if it does, as `wholeBufferBytes` does in the SQLite store). A zero-length piece is a piece: its size value is `0` and its piece value is an empty array; check the conformance suite's empty case passes under `classic-level`. **Each put is synced where the handle can sync, and `flush()` resolves at once.** LevelDB has no sync of its own: a synced write syncs only the current log file and closes an older one unsynced when it switches (`leveldb-like.ts` and `tickets/blocked/4.5-react-native-storage-syncs-once-rn-leveldb-can.md` both record this), and at 256 KiB a piece LevelDB's 4 MiB write buffer switches log files every few pieces, so unsynced puts followed by one synced write at flush would not cover the pieces in older files. Rejected for the same reason: buffering pieces in memory until flush, which would hold a whole blob. The has-then-write is not atomic; two puts of one id racing both write the same bytes and size, which changes nothing, so "a present id writes nothing" holds for every put that does not race. Record that as a `NOTE:` at `put`.
- **`delete`**: one batch deleting both keys, unsynced. A delete lost to a power cut leaves an orphan piece the next sweep removes, which is not worth a sync per deleted piece. `NOTE:` at the site.
- **`list`** pages through `pieceSizeRange()` with `iterator({ gte | gt, lt, keys: true, limit: PIECE_LIST_PAGE })`, each page drained (`drain`) before its ids are yielded and the next page starting `gt` the last key, so a native iterator never stays open across the consumer's awaits and no page loads every id at once.
- **`bytesUsed`** is `measurePieces(this.db)`: one drained scan of the size range with values (4 bytes each), summing the decoded sizes; a size value that is not 4 bytes is logged and skipped. A failure is logged under `createLogger('storage:pieces')` (namespace `optimystic:db-p2p-storage-rn:storage:pieces`) and answers 0.
- **No `close`.** The handle is shared with the block store, the key-value store and the identity helper; the host closes it after the node has stopped.

### The block store's measurement reads no piece bytes

`LevelDBJournalStore.approximateBytesUsed` in `packages/db-p2p-storage-rn/src/leveldb-storage.ts` iterates every key and value in the database. With pieces in the same database it would read every stored blob byte through the binding on each `StorageMonitor` scan. Change it to three parts: a scan with values of everything below `TAG_PIECES` (`lt: Uint8Array.of(TAG_PIECES)`, which includes the commit proofs at `0x08`), the same of everything from `TAG_PIECES + 1` up (`gte: Uint8Array.of(TAG_PIECES + 1)`), each summing key and value lengths as today, plus `measurePieces(db)`. Keep each iterator closed in a `finally` as today (or `drain`, but the sum need not hold the entries, so iterating and summing is better). The figure still covers the whole database, so a piece is counted once, by the block store, and `storeIdentity` equality tells `StorageMonitor` so. Keep its existing `NOTE:` about the full-scan cost and add that the piece range is measured from its size keys.

### Durability on a phone

`rn-leveldb` cannot sync (`canSync` false), so on a phone the piece store reports `'process-crash'`, writes every batch unsynced, and never claims more: a stored piece survives the app crashing, not the phone losing power, exactly as the block store. Under `classic-level` in tests `canSync` is true and every put is synced. When the blocked ticket lands, `canSync` turns true on phones and every piece put pays one sync; add a bullet to that ticket's "Work here once it lands" list saying the piece store reads `canSync` and needs no change, that each piece put will then sync, and that the device check should time a multi-megabyte blob put.

## Part 2 — what `packages/upgrade-check` owes

Stored data gains a piece store and key-value namespaces and loses nothing (docs/blobs.md §Compatibility). The suite proves that for the `fs` and `leveldb` backends it covers.

### The reader runs with a piece store over the older data's location

In `packages/upgrade-check/test/current-build.ts`, `OpenBackend` gains `pieceStorage: IPieceStore`, passed to `createLibp2pNode` as `pieceStorage`. `CurrentBuild.storage` already exists and is what the listing check below uses.

- `fs`: `new FilePieceStore(join(dataDir, layout.blocks))`. Its constructor puts pieces under `<basePath>/optimystic-pieces/` (`PIECE_DIRECTORY`), its identity equals `FileRawStorage`'s over the same path, and `FileBatchBackend.listBlockIds` already skips that directory.
- `leveldb`: `new LevelDBPieceStore(db)` over the same `classic-level` handle.
- `close` calls `pieceStorage.close?.()` first, then closes what it closes today.

Every existing fixture was written by a release with no piece store, so this alone checks that the missing directory or key range reads as empty, that nothing older moves, and that every step the suite already runs still passes with the piece store present.

### New steps in `upgrade-over-older-data.spec.ts`

`node.blobs.put(source: AsyncIterable<Uint8Array>, options?)` resolves `{ ref, size }` once the pieces and the record naming them are durable; `node.blobs.read(ref, { from: 'here' })` is an `AsyncIterable<Uint8Array>`; `BlobRef` is a branded string (`parseBlobRef` in `packages/db-core/src/blob/blob-ref.ts`).

- **In "writes on top of the older data"**, after the existing writes: list the block ids (`running().storage.listBlockIds()`), put one blob of 600 KiB through `running().node.blobs.put` (three data pieces and a list piece; content from a small seeded generator in the spec, so equal pieces do not collapse into one), list the block ids again and expect the same set, and keep the reference and the content's SHA-256 in the `describe`'s scope. The listing comparison is what shows no piece key or blob record is read as a block on either backend.
- **In "reads the older data and the new writes back after restarting again"**: read that blob with `node.blobs.read(ref, { from: 'here' })` and expect the SHA-256 of the concatenated bytes to equal the one kept, and the length 600 KiB.
- **"reads back the blob the older build stored"**, registered only when the fixture's manifest carries a `blob` (none does until the first release that ships blob storage writes its fixture): after the first start, `node.blobs.read(parseBlobRef(manifest.blob.ref), { from: 'here' })` yields `manifest.blob.size` bytes whose SHA-256 is `manifest.blob.sha256`.

Hash with `createHash('sha256')` from `node:crypto`; the suite runs only under Node.

### The manifest and the writer

`FixtureManifest` in `test/fixture.ts` gains `blob?: { ref: string; size: number; sha256: string }` (SHA-256 in lowercase hex).

`writer/write-scenario.mjs` must keep to API the oldest fixture version has (1.0.0-beta.3), so the blob step is gated on what the installed build offers:

- Replace the named imports from `@optimystic/db-p2p-storage-fs` and `@optimystic/db-p2p-storage-rn` with namespace imports (`import * as storageFs from …`), because a static named import of an export an older build lacks fails the whole module at link time. Each `BACKENDS` entry adds `pieceStorage`: `new storageFs.FilePieceStore(join(dir, layout.blocks))` or `new storageRn.LevelDBPieceStore(db)` when the class exists in the namespace, else `undefined`, and its `close` calls `pieceStorage?.close?.()` first.
- `startNode` passes `pieceStorage`; a build without the option ignores it, as builds before 1.0.0 ignored `kvStore`.
- After the diary appends and before the in-flight append, when `typeof node.blobs?.put === 'function'`: put 600 KiB from a seeded xorshift generator written into the script (deterministic, so a regenerated fixture holds the same bytes), and record `{ ref, size, sha256 }` in the manifest as `blob`. Otherwise record nothing.

No fixture is regenerated in this ticket: the first fixture with a blob is written by the release step after the first release that ships blob storage. Running the writer against the working tree is not part of `yarn test`; if it is cheap, run it once by hand against the working tree to see the gated step write a manifest `blob`, and delete what it wrote.

## Edge cases & interactions

- **An older LevelDB database opened by this build.** No key under `0x09`: `list` yields nothing, `bytesUsed` answers 0, every block, proof, commit proof, journal record and key-value entry reads as before. Covered by the upgrade suite's `leveldb` fixtures.
- **This database opened by an older build.** Its scans are bounded by tag ranges that exclude `0x09`; its full-scan measurement reads the piece bytes, which costs time but reads correctly. Inspection.
- **Key ranges do not overlap**, in particular the commit-proof range `[0x08, 0x09)` and the piece range. Test (the every-tag case below).
- **A piece whose bytes are valid UTF-8.** Read through `get`, never `getText`. Inspection: the module never calls a text read.
- **A sub-view or zero-length `bytes` handed to `put`.** Stored as exactly those bytes. The conformance suite covers zero-length; inspection of the adapter for sub-views.
- **A size key whose value is damaged.** `measurePieces` skips it with a log line; `has` still answers true from its presence, and `get` reads the piece. Inspection.
- **A piece without its size key or the reverse.** Impossible through this store, since both are written and deleted in one batch. Inspection.
- **A 1 MiB piece.** Round-trips under `classic-level` through the conformance suite's large case. `rn-leveldb` on a device is not run by any suite; the README says the piece store has not run on a device.
- **Crash between a put and a flush.** On a phone a put survives the app crashing; a power cut may lose it, the blob's record was never written because the service's `put` had not resolved, and the sweep removes orphans. Inherited from the conformance suite's reopen case.
- **The block store's measurement.** Counts each piece once, from its size key, and `blockStoreCountsPieces` is true for a `LevelDBRawStorage` and a `LevelDBPieceStore` over one handle. Test (below).
- **The upgrade suite's in-flight commit.** Unaffected: the blob is put after it in "writes on top", and the writer puts its blob before the in-flight append, so the node stops with the same pending record as before. Inspection.
- **The start-up sweep after the restart.** A blob put through `node.blobs.put` is pinned for the default owner, so the sweep on the second start keeps its pieces. Covered by the read after restart.
- **A fixture from before 1.0.0 (`1.0.0-beta.3`).** Its documented upgrade step runs first, as today; the piece store does not interact with the catalog. Covered by the suite.

## Tests

- `packages/db-p2p-storage-rn/test/leveldb-piece-store.spec.ts`:
  - `runPieceStoreConformance('LevelDB pieces', …, { persistent: true })` with a harness built like the `'LevelDB'` one in `test/leveldb-storage.spec.ts`: `openTestDb` (or the path-taking opener) per case, `reopen` closing the handle and opening the same path, `cleanup` closing whatever is open and removing the directory.
  - A paging case like the SQLite spec's "lists every id once across several pages": two and a half pages of size keys written directly through one batch, every id listed once.
  - One case over a database holding every tag: write one block and flush it through `LevelDBRawStorage`, one journal record (through a flush given a window, as the journal tests already do, or directly through `LevelDBJournalStore.appendJournal`), one key under `TAG_COMMIT_PROOFS` (a direct batch put of `commitProofKey(...)` is enough), one key-value entry through `LevelDBKVStore`, the identity key through `loadOrCreateRNPeerKey`, and two pieces through `LevelDBPieceStore`. Expect `list` to yield exactly the two piece ids, `listBlockIds` exactly the block, the key-value listing exactly its entry, `readJournal` exactly its record, `blockStoreCountsPieces(storage, pieces)` true, and the block store's `getApproximateBytesUsed` to grow by at least the two pieces' lengths and by less than twice that when the pieces are put. It pins the tag choice and the measurement change, the two ways this layout can go wrong silently.
- `packages/upgrade-check`: the steps above, which run for every checked-in fixture on both backends.

No other new tests.
