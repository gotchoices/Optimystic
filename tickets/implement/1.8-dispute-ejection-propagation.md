# Converge on ejections when views disagree

## Why

A ruling is pushed to the disputed record's cohort and every arbitrator (`dispute-escalation-loop`), which covers the nodes whose view of that ring segment matters first. Everyone else — a node that was offline, a coordinator for a neighbouring block, a node that joins later — learns an ejection only when its view of a cohort disagrees with someone who knows. Today such a disagreement surfaces as a membership-admission refusal (`MEMBERSHIP_NOT_ADMITTED:inconsistent-with-derived-view` and friends), whose reason is prose and must not be parsed. The design of record specifies a pull on disagreement: the side that does not know fetches the rulings, verifies them, records the ejections, and retries.

## Specification

- **Protocol**: a `get-ejections` request on the dispute protocol, `{ peerIds: string[] }` → the rulings this node holds for any of those peers with an active term (from `EjectionRegistry.rulingsFor`). Bounded: at most `clusterSize × 2` peer ids per request; at most one ruling per peer in the answer.
- **Coordinator pull**: when the promise round returns admission refusals from members, the coordinator asks those members `get-ejections` for the peers in the record (one request per refusing member, in parallel, short deadline — the dial deadline). Every returned ruling is verified and recorded; if any new ejection lands, the coordinator fails the attempt with the existing retryable shortfall so the writer's re-drive re-resolves the cohort (`findCluster` now excludes the peer). It does not re-run the round itself.
- **Member pull**: when a member's admission gate is about to refuse because its derived view contains a peer the declared set lacks, it first asks the coordinator (the record's sender) `get-ejections` for those peers, with the same short deadline; verified rulings are recorded and the view re-derived before the verdict. No answer → the gate decides as today.
- **Verification**: every pulled ruling goes through the ruling verifier before the registry records it, exactly as a pushed one does. An unverifiable ruling is logged with the verifier's reason and ignored; the peer that served it is not penalized (it may itself be a degraded verifier — see the anchoring residual in `docs/right-is-right.md`).

## Edge cases & interactions

- **Vote-path latency**: the member pull adds at most one dial deadline to a promise vote, and only when views already disagree (which today ends in a refusal anyway). Keep it off the common path — test or inspect that an agreeing view makes no request.
- **Malicious server**: a peer can answer `get-ejections` with junk or with genuine rulings for peers it wants excluded. Junk fails verification; genuine rulings are by definition ones the network should honor. A peer can also *withhold* rulings, which leaves the disagreement as it is today.
- **Inbound authorization**: the dispute protocol is not covered by `authorizeInboundStream` (`docs/internals.md` §Inbound Stream Authorization); whether it should be is decided in `feat-dispute-subsystem-live-activation`. This ticket adds a read-only request to it and changes nothing about that decision — note it in the handoff.
- **Amplification**: one refused promise round triggers at most one `get-ejections` per refusing member; cap the per-request peer list as specified.
- **Expired terms**: never served and never recorded.

## Tests

- A coordinator whose promise round is refused by a member holding an ejection it lacks records the ejection after the pull, and the next resolution of that block's cohort excludes the peer.
- A member with an agreeing view makes no `get-ejections` request.
