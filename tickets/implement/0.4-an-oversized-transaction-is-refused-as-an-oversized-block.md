# An oversized transaction is refused as an oversized block

Reported as GitHub #61 (Sereus; optimystic 1.27.0, solo node, file storage).

## What happens

One SQL transaction of ~1 KiB rows on a solo node: 1 and 3.5 MiB of rows commit; 4, 5 and 6 MiB are refused with `TransactionTooLargeError` (pends of 8.9, 11.2 and 13.4 MB); from 7 MiB the refusal is `BlockTooLargeError`, naming the collection's log block (8.0 MB at 7 MiB of rows).

Reproduced at the collection tier (a throwaway spec, deleted): over a `TestTransactor`, `Collection.actAndSync` of

- an insert plus a `grow` of one block by `MAX_BLOCK_BYTES + 1000` characters in ONE transaction, and
- one action whose own data is `MAX_BLOCK_BYTES + 1000` characters (so the log block carrying its entry is ~15.7 MB)

both throw `BlockTooLargeError`. Each is a single transaction whose pend is over `MAX_TRANSACTION_BYTES`, so each should throw `TransactionTooLargeError`. The handlers in `packages/db-core/test/writer-refuses-oversized-block.spec.ts` (`insert`, `grow`) build both shapes.

## Cause

Two size checks run in the wrong order. The block measure (`oversizedBlock`) runs at staging: `stageAttempt` (every single-collection write: `syncAttempts`, `commitHead`) and `TransactionCoordinator.declareTouchedBlocks` (the coordinator path, `commitEntry` included), right after the log append. The transaction measure (`assertTransactionFits`) runs only inside `NetworkTransactor.pend` / `pendMany`, after both. One committed transaction is one log entry, and an entry above `BLOCK_TARGET_BYTES` sits alone in its block, so a transaction large enough that its lone log block exceeds 7.5 MiB hits the block check first. The window 4–7 MiB reports correctly only because the log block is smaller than the pend (the pend also carries the tree blocks, which hold the rows a second time).

## Design

### 1. When a block is over the limit, ask first whether the transaction is

At both staging sites, when `oversizedBlock` returns a refusal, measure the staged transforms that the pend will carry — `jsonEncodedBytes(tracker.transforms)` in `stageAttempt` (after the append, so the log entry is in it), and `jsonEncodedBytes(transforms)` per collection in `declareTouchedBlocks` — and when that is over `MAX_TRANSACTION_BYTES`, refuse with `TransactionTooLargeError` instead of the block error.

Why this is sound: a pend carries its collection's transforms plus envelope (action id, revision, bases, HLC, validation), so transforms over the limit proves the pend is over it. And it holds whether a multi-collection transaction travels as one batch (`pendMany`, judged on the sum) or one pend per collection: one collection's transforms are a subset of either. Why it is cheap: the extra serialization runs only on the refusal path, so an ordinary write pays nothing.

What it leaves as `BlockTooLargeError`: a block over the limit whose write is under it — the two-write growth the existing spec pins, and a block a build without the split rules already grew past the limit. That is exactly the case `BlockTooLargeError`'s documentation describes. An edge stays open on paper: transforms under the limit while one block is over it and the full pend is over it — a single block cannot be much larger than transforms containing it whole, so this needs a pre-existing oversized base; it is reported as the block error, which is then the truthful one.

Put the rule in one function both sites call, beside `oversizedBlock` in `packages/db-core/src/network/block-size.ts` (it already imports `transaction-size.ts`), e.g. `oversizedWriteRefusal(touchedBytes, transforms, actionId): TransactionTooLargeError | BlockTooLargeError | undefined`. `declareTouchedBlocks` does not have the action id today; thread it from its caller (the `WriteContext` / transaction the commit span holds). `TransactionTooLargeError.bytes` is then the transforms' size, a lower bound of the pend: say so in the field's doc ("at least").

### 2. Refuse during staging once the staged actions alone cannot fit

The issue's second ask: the reporter's real case (56k rows) spent 4.4 minutes of CPU and 3.3 GB staging before the first size check. A cheap running lower bound IS available, at the collection layer: **the log entry in the pend repeats every staged action verbatim** (docs/internals.md §A transaction's size limit), so the sum of the JSON sizes of the open segment's actions is a lower bound of the pend. Once that sum passes `MAX_TRANSACTION_BYTES` the transaction provably cannot commit, and staging more is wasted.

- Measure each action once, with `jsonEncodedBytes`, when it is staged (`Collection.actInternal`), and refuse BEFORE staging the call whose actions would take the open segment's total past the limit, so a refused `act` stages nothing (`Tree.stage` → `Collection.act` is one action per row, so the SQL statement that crosses the limit fails and the statement savepoint discards its earlier rows).
- Keep the size on the unit (`StagedUnit.bytes`, set by `pushOpen` and by `unitsOf`) and a running total on `SegmentList` that `setOpen` recomputes by summing units, so rollback (`restorePending`'s arms), `consumeOwnEntry`, `filterAgainstEntry` and `unstage` keep it right without re-serializing actions. `StagedUnit` is immutable and shared by snapshots; adding a field set at construction keeps that.
- Only the OPEN segment counts: a sealed segment is its own queue entry, committed by `commitHead` on its own, and a whole-collection `sync` refuses over sealed segments anyway. Replays (`replayActions`, `buildHeadTracker`) do not go through `actInternal` and must not be refused by this check — they re-stage what was already admitted.
- Per collection is enough for a multi-collection transaction: one collection's actions are in that collection's pend, which is in any batch.
- The refusal is `TransactionTooLargeError` with no action id — none is minted until the commit. Make `actionId` optional (`ActionId | undefined`) and word the message for that case, e.g. "the transaction staged so far encodes to at least N bytes …". `classifyCommitFailure` already sorts the class as `too-large`.
- It fires at roughly HALF the row volume the precise check would (row data rides once in the actions, once in the tree), so it bounds the wasted staging rather than replacing the commit-time check: say so in the docs. For the reporter's case it fires about one eighth of the way through staging instead of after all of it.
- SQL surface: the vtab's DML catch in `update()` wraps non-Quereus errors via `rewrapAsQueryError`. Check the statement error keeps the `TransactionTooLargeError` reachable (as `cause`) and its message readable; adjust only if it does not.

Cost: one extra JSON serialization per staged action, linear in what is staged. Measure an ordinary multi-row insert before and after; if it shows, record a `NOTE:` at the measure with the number.

### 3. Document the ratio

docs/internals.md §A transaction's size limit already says row data counts roughly twice. Give the number writers size batches by: the reporter measured pends of about 2.1–2.2× the row data for 1 KiB text rows (8.9 MB at 4 MiB, 13.4 MB at 6 MiB; 3.5 MiB committed), so about 3.4 MiB of such rows fit one transaction; BLOB columns are base64 under the `json` encoding, another 1.33× (GitHub #63 measured 4.2 MB of blob values encoding to 11.5–14.3 MB). Carrying row data once is plan ticket `a-large-write-costs-time-and-space-per-byte`, not this one.

Also update in the same section: the "What the writer gets" bullet (where each refusal now fires, and the early staging refusal), the "Where" and "When it fires" bullets under "The writer refuses a block over the limit" (the transaction is judged first when both fire), and the `MAX_BLOCK_BYTES` doc comment, whose premise ("no single transaction produces a block over it on its own") now holds because the transaction is judged first.

## Tests

- Reproduction, in `packages/db-core/test/writer-refuses-oversized-block.spec.ts` beside the existing two: one transaction whose single block and pend are both over the limit is refused as `TransactionTooLargeError`, nothing reaches the transactor, on both paths (`Collection.actAndSync`, `TransactionCoordinator.commit`). The existing two-write growth cases stay `BlockTooLargeError` — together they pin the ordering at the size where both fire.
- Early refusal: an `act` whose actions take the open segment's action bytes past the limit throws `TransactionTooLargeError` and stages nothing (`hasUnsyncedChanges` as before the call; earlier staged actions untouched); and after a rollback (`snapshotPending`/`restorePending`) the running total is the restored one — one test, at the collection tier.
