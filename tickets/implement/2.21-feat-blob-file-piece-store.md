# The filesystem piece store

`feat-blob-piece-store-interface-and-memory-store` defined `IPieceStore` (`packages/db-p2p/src/blob/piece-store.ts`), the store for the immutable pieces a blob is cut into, an in-memory implementation and a conformance suite (`runPieceStoreConformance`, published as `@optimystic/db-p2p/testing/conformance`). This ticket implements the interface on the filesystem in `packages/db-p2p-storage-fs`, so a Node host keeps pieces across restarts. Each piece is one file holding exactly its bytes: no JSON, no write-ahead log, no write group (docs/blobs.md §The local store).

## Layout

```
<basePath>/
  write-ahead.log, store.lock, commit-proofs/, <block dirs>, <kv namespaces>   (FileRawStorage / FileKVStore, unchanged)
  optimystic-pieces/
    incoming/<16 hex>.tmp        a piece being written; cleared on open
    <xx>/<piece id>              one file per piece, named by its id, no extension
```

- `PIECE_DIRECTORY = 'optimystic-pieces'`, exported from `file-piece-store.ts` (and so from the package index). The name follows the `optimystic-offline` key-value namespace's pattern, chosen so a collection id is unlikely to collide with it at the root, where block directories also live.
- **Fan-out.** `<xx>` is `id.slice(-3, -1)`: the two characters before the last. Every canonical piece id is 59 characters, `b` plus 58 base32 characters of a 36-byte CIDv1 (`canonicalSpelling` in `packages/db-core/src/blob/blob-ref.ts`); every id starts the same way (`bafkrei` for raw, `bafybei` for dag-pb: version, codec and hash prefix), so the front cannot spread anything, and the last character carries only 3 bits. The two before it are digest bits. One level of 1024 directories keeps about a thousand files per directory at a million pieces (256 GiB at the 256 KiB piece size). Rejected: two levels, which at small stores makes one directory per file.
- **Ids are checked before they become paths.** Every method first tests the id against `/^b[a-z2-7]{50,}$/` (the alphabet of a lowercase base32 CIDv1; a path-safety guard, not a CID parser — the blob service has already parsed it) and throws `RangeError` otherwise. `PieceId` is branded, but this keeps a path out of the filesystem whatever a future caller passes. One small function (`pieceFileName` or similar) does the check and returns the fan directory and file path; every method goes through it.

```ts
export const PIECE_DIRECTORY = 'optimystic-pieces';

export class FilePieceStore implements IPieceStore {
	readonly durability: StoreDurability = 'power-loss';
	/** Pieces go in `<basePath>/optimystic-pieces/`. Synchronous; the directories are created on first use. */
	constructor(basePath: string);
	/** `fileStoreIdentity(basePath)`: equal to a `FileRawStorage` over the same basePath, whose byte count measures the whole directory, pieces included. */
	storeIdentity(): StoreIdentity;
	// has, get, put, delete, list, bytesUsed, flush, close: IPieceStore
}
```

## Operations

Every operation first awaits a lazy, memoized `open()`:

1. `mkdir(pieceRoot, { recursive: true })`. When it returns a path (it created something — `basePath` itself may not have existed), mark dirty the parent of that first created directory and every directory from it down to the piece root, so the next `flush` makes the piece root's own entry durable. Without this, a first piece flushed on POSIX could survive a power cut with the directory that names it gone.
2. `mkdir(incoming, { recursive: true })`. Its entry is never synced: temps are transient by design.
3. Delete every file in `incoming/`; log `incoming:cleared` with the count when non-zero.

The memo is cleared if `open()` rejects, so the next call retries (the same rule `OptimysticVirtualTable`'s first open follows).

- **`put(id, bytes)`** — the atomic write:
  1. If the final file exists (`fs.access`), return: a present id writes nothing.
  2. `mkdir(fanDir, { recursive: true })`; when that call created the directory (it returns a path), mark the piece root dirty.
  3. Write `incoming/<16 random hex>.tmp` with `fs.open(…, 'wx')`, write every byte, `handle.sync()`, close. The random name comes from `crypto.randomBytes(8)` (`node:crypto`; this package is Node-only).
  4. `fs.rename(temp, final)`. If it fails with `EEXIST`, `EPERM` or `EACCES` and the final file now exists, another put of the same id won (Windows refuses to replace a file another handle has open): unlink the temp and return; log `rename:raced`. Any other failure: unlink the temp (ignoring `ENOENT`) and rethrow.
  5. Mark `fanDir` dirty.
  The piece's bytes are synced before the rename, so after a crash the final name holds either the whole piece or nothing; the directory entry itself becomes durable at the next `flush`. Rejected: deferring the file sync to `flush`, which would let a renamed file come back empty or truncated after a power cut, so a reader would see a corrupt piece instead of a missing one.
- **`get(id)`** — `readFileIfExists` (from `file-write-log.ts`), returned as a plain `Uint8Array` view over the buffer `fs.readFile` allocated (`new Uint8Array(buf.buffer, buf.byteOffset, buf.byteLength)`), which no one else holds. `readFileIfExists` already returns a `Uint8Array`-typed `Buffer`; returning it as is also meets the contract (a subclass is allowed), so the re-view is optional — pick one and keep it.
- **`has(id)`** — `fs.access` on the final path; `ENOENT` is false, any other error propagates.
- **`delete(id)`** — `fs.unlink`, `ENOENT` ignored; mark `fanDir` dirty. Any other error propagates (on Windows a piece another handle is reading can refuse deletion; the caller logs and retries later).
- **`list()`** — `readdir` the piece root, keep the directories whose names match `/^[a-z2-7]{2}$/` (which excludes `incoming`), and for each, `readdir` it fully (drain before yield), then yield every name that passes the id test. A temp file is never yielded: temps live only in `incoming/`. A root that does not exist lists nothing (open creates it anyway).
- **`bytesUsed()`** — the sum of `stat().size` over the files `list` would yield. Temps are excluded. A file deleted between the listing and its `stat` (`ENOENT`) counts 0.
- **`flush()`** — take the dirty set and clear it, then `fsyncDir` each, deepest first (fan directories, then the piece root, then whatever `open` marked above it). `fsyncDir` already swallows its errors and is a no-op on win32 (its `NOTE:` explains why), so flush cannot reject on its own; the store's `durability` is `'power-loss'` on the same footing as `FileBatchBackend`'s. A put that resolved before the flush has already synced its file bytes, so the directory syncs are all flush owes.
- **`close()`** — `flush()`. The store holds no handle between calls.

No store lock. `FileRawStorage` and `FileKVStore` share a lock through `FileWriteLog`; taking `acquireStoreLock` here as well would refuse the second taker in the same process. Content-addressed files written by rename need no log to stay consistent. Add a `NOTE:` at the class: two `FilePieceStore`s over one directory, in one process or two, are not supported — the second's `open()` deletes the first's in-flight temps, failing its put — and Invariant 5 of `packages/db-p2p/docs/storage.md` (one process per store) is what a host already keeps.

The log namespace is `createLogger('pieces:file')`, i.e. `optimystic:db-p2p-storage-fs:pieces:file`.

## Coexisting with the block store

The block listing (`FileBatchBackend.walkBlockDirectories`) already skips the root directories that hold no blocks, through `ROOT_NON_BLOCK_DIRS` (the key-value namespaces plus `COMMIT_PROOFS_DIR`). Add `PIECE_DIRECTORY` to that set (import it from `file-piece-store.ts`), and update the set's comment to name the piece directory. Give it the same `NOTE:` `COMMIT_PROOFS_DIR` carries: a block whose id is `optimystic-pieces` or starts `optimystic-pieces/` is hidden from `listBlockIds` and keeps its records inside the piece directory, an accepted limit. A piece directory holds no `meta.json`, so the walk would never list a piece as a block, but without the skip it would descend a thousand directories on every startup listing.

`approximateBytesUsed` keeps walking the whole base path, pieces and temps included, which is why `storeIdentity()` reports the base path's identity and `StorageMonitor` does not add the piece figure again (`blockStoreCountsPieces`).

Extend `FileKVStore.keyToPath`'s `NOTE:` to name `optimystic-pieces` among the root words a block id's first segment must not equal.

## Edge cases & interactions

- **Crash mid-piece.** A temp in `incoming/` is never served or listed, and the next open deletes it. Test (below).
- **Crash after rename, before flush.** The file is whole (synced before rename) or absent. By inspection of the write order.
- **First put into a store whose piece root did not exist.** `open` marks the directories it created and their parent dirty, so the first flush syncs the piece root's entry too. By inspection.
- **Two puts of one id at once.** Both resolve; one file. On POSIX the second rename replaces an identical file; on Windows `fs.rename` replaces too unless a handle is open on the target, which is the race arm above. By inspection; the conformance suite covers the concurrent case it defines.
- **A get racing a delete.** `ENOENT` reads as absent. Inspection.
- **`bytesUsed` racing a delete.** `ENOENT` on `stat` counts 0. Inspection.
- **Hostile id.** A string with `/`, `\`, `..`, uppercase or a drive letter is refused with `RangeError` before any path is built, and nothing is created. Test (below).
- **`open()` fails** (permissions, a file where the directory should be). The call rejects, the memo is cleared, the next call retries. Inspection.
- **A store at a base path no block store uses.** Its identity differs from the block store's, so `StorageMonitor` adds its bytes. Covered by `blockStoreCountsPieces`'s own test.
- **An older store directory with no piece root.** Created on first use; nothing else changes. Inspection; the upgrade suite's coverage of it belongs to `feat-every-storage-backend-stores-blob-pieces`.
- **A collection whose id's first segment is `optimystic-pieces`.** Shares the directory and is skipped by the block listing — the same limitation the key-value namespaces and `commit-proofs` already carry; recorded by the two `NOTE:`s above.
- **`FileRawStorage` and `FilePieceStore` over one base path in one process.** No shared lock, no shared log; they touch disjoint paths. The block store's `approximateBytesUsed` counts the pieces. Inspection.

## Tests

`packages/db-p2p-storage-fs/test/file-piece-store.spec.ts`:

- `runPieceStoreConformance('FilePieceStore', …, { persistent: true })`, each case in a fresh `fs.mkdtemp` directory, `reopen` returning a new `FilePieceStore` over the same base path, `cleanup` removing the directory (`fs.rm(…, { recursive: true, force: true })`).
- "a leftover temp is never served and is removed on open": put a piece, write a file into `optimystic-pieces/incoming/`, open a new store over the directory, call `list()`: only the piece; the temp file is gone.
- "refuses an id that is not a lowercase base32 CID": `get('../x' as PieceId)` and `put` of an uppercase id reject with `RangeError`, and the base directory holds nothing afterwards.

No new listing test: the skip is one more name in an existing set, verified by inspection.
