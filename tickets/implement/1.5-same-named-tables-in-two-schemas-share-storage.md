# What is wrong

A table declared without an explicit `using optimystic('<uri>')` gets its storage location from the plugin's default: `tree://default/<TableName>` (`parseTableSchema` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`, repeated in `catalog-batch.ts` and `schema-manager.ts`). The engine schema name is not part of it. So `Strand.Member` and `App.Member` open the same collection, `default/Member`, and their secondary indexes collide the same way (`<uri>/index/<name>`).

The schema catalog has the same flaw one level up: it stores and looks up each table's record by bare table name (`SchemaManager.getSchema(tableName)`, `getDroppedSchemaRecord(tableName)`, `CatalogBatch.readEntry(tableName)`), so two same-named tables in different schemas also share one catalog record, and a warm restart's catalog hydrate cannot tell their definitions apart.

Only the plugin's in-memory table map is schema-qualified today (`instantiateTable` keys by `schemaName.name`), which is why two such tables look distinct inside one process while writing into one place.

Nothing refuses it. `guardStorageAdoption` fires only when the shared storage already holds a gravestone contradicting the declaration; two live tables declared together pass.

# How it was found

Diagnosis of `fix/a-second-party-cannot-read-the-messages-it-just-wrote` (a sereus device report). The sereus side reproduced it headlessly with two nodes: their chat app's `App.Member` read back the built-in `Strand.Member` rows as members with null ids, the app's own member insert reported success and was never readable, and renaming the app table alone made the two-party run converge. That is recorded in sereus's `implement/3-strand-app-table-names-collide-with-strand-tables`, which adds a sereus-side refusal and renames their table as a stopgap and asked for this upstream fix. `repro: static` here: the mechanism is read from this repo's code, and the observation is downstream; the first TODO below makes it `verified` in this repo.

It also fed the misleading part of the original report ("membership rows crossed, messages did not"): the membership count the phone showed included these phantom rows, so it was not evidence that data moved.

# What to build

**Every table's default storage location includes its engine schema:** `tree://default/<schema>/<table>`, using the schema and table names as `TableSchema` carries them, with the `main` schema qualified like any other (uniform rule; no backwards compatibility is owed yet, per AGENTS.md). Indexes follow from the table URI unchanged (`<uri>/index/<name>`). A table with an explicit `using optimystic('<uri>')` is unaffected. Make the default rule one exported function used by all three current copies, so they cannot drift again.

Segment counts keep table and index locations apart: a defaulted table is `default/<schema>/<table>` and its index is `default/<schema>/<table>/index/<name>`.

**The catalog keys each record by schema and table**, not by table alone, for live records and gravestones, in both the direct and batched paths. Hydrate must restore each table into its own schema.

Two same-named tables whose declarations name the *same* explicit URI still share storage, and that is deliberate (an author asked for it). Do not add a refusal for that here.

# Tests

- A failing-first plugin spec: one database, two schemas each declaring `Member` with different columns and no explicit URI; insert into each; each reads back only its own rows; the two collection ids differ. Include a secondary index with the same name on both.
- The same across a restart (fresh module over the same storage): both tables hydrate with their own column sets.
- A drop in one schema leaves the other's table, rows and catalog record untouched, and re-declaring the dropped one is judged against its own gravestone only.
- Update the `two-node-*` specs' hard-coded ids to the new rule (prefer deriving them from the exported function).
