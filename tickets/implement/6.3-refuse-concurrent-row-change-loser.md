## What was observed (fix stage, 2026-09-15, `repro: verified`)

A probe on the two-node mock mesh (`test/mesh-node-harness.ts`), table `Probe (Id integer primary key, Token text)` with `create index probe_by_token on Probe(Token)`, rows `(100,'tok-a')` from A and `(200,'tok-b')` from B, index tree read directly through a fresh `Tree` on each node. Every commit fulfilled with no error; both nodes agreed on rows and index. Entries written `token‖id`.

| shape | rows after | stray index entry |
|---|---|---|
| A `begin; update … Token='tok-x' where Id=100`; B `begin; update … Token='tok-y' where Id=100`; A commits, then B | 100:tok-y, 200:tok-b | `tok-x‖100`, row holds tok-y |
| A `begin; delete … Id=100`; B `begin; update … Token='tok-y' … Id=100`; B commits, then A | 200:tok-b | `tok-y‖100`, no row |
| same, but A (delete) commits first, then B (update) | **100:tok-y**, 200:tok-b | none, but the deleted row is **resurrected** |
| A `begin; insert or ignore … (300,'tok-ignored')`; B `insert … (300,'tok-winner')`; A commits | …, 300:tok-winner | `tok-ignored‖300`, row holds tok-winner |
| with `create unique index` instead: racing update as in row 1, then a **sequential** `insert … (300,'tok-x')` on either node | unchanged | refused `UNIQUE constraint failed: Probe.Token` although no row holds tok-x, permanently, on both nodes |

The first shape also reproduces with two `Database` handles over one `FileRawStorage` directory and the `local` transactor, the same cheap shape `test/concurrent-secondary-unique-refusal.spec.ts` uses, so the regression tests below need no mesh.

## Root cause and the decision this ticket implements

A statement's index delta is computed from the row image it read (`requirePreWriteRow`, or the pre-stage `collection.get` in the insert arm), and its main-table entry is staged **without** any guard tying it to that image. On the loser's conflict replay the main-table action re-applies over the rival's row while the index delta, computed against the old image, lands beside it. Three concrete forms in the `update` method of `OptimysticVirtualTable` (`src/optimystic-module.ts`): the same-key UPDATE stages `[[newKey, [newKey, encodedRow]]]` unguarded; the DELETE stages `[[deleteKey, undefined]]` unguarded; INSERT OR IGNORE stages `keepExisting`, whose replay skips the main entry but not the index adds (the `NOTE:` beside that guard already admitted this).

**Decision: refuse the loser.** A concurrent same-row UPDATE or DELETE whose pre-write image a rival changed is refused at commit, not resolved last-writer-wins, and under concurrency every conflict disposition (`or ignore`, `or replace`, `on conflict … do nothing`) resolves to refusal, with the sequential retry honouring the disposition. Grounds: `docs/internals.md` §"Conflict replay re-makes the uniqueness decision" already chose this for UNIQUE, with the same reason ("the rival's row lives in the main collection, which an index tree's replay can neither skip around nor evict"); `docs/transactions.md` calls two users editing the same row a semantic conflict the application must resolve; read-dependency validation (`docs/internals.md` §"Read Dependency Validation") exists precisely to reject a transaction whose read set moved; and last-writer-wins cannot be made index-coherent without cross-collection replay, which no commit mode offers. The reviewer should confirm this call. If a human instead wants last-writer-wins for UPDATE, that is a `blocked/` decision and the fix becomes "derive the index delta at replay from the row actually replaced", a much larger change.

The guard comes from prereq `tree-entry-unchanged-guard`: `{ kind: 'unchanged', expected: <entry as stored> }`, evaluated on upserts and deletes at initial staging and every replay, refusing with `TreeEntryChangedError` (absent counts as changed).

## The arms — every main-table entry whose index delta was derived from a pre-write image

All in the `update` method and its helpers in `src/optimystic-module.ts`. `expected` must be the **stored entry** `[pk, encodedRow]` the statement read, never a re-encoding of the decoded row: make `requirePreWriteRow` return `{ row, entry }`, and carry the entry in `UniqueCollision` and in `PkMoveDecision`'s `displace` arm (both collectors already hold it at the point they decode).

- **UPDATE, same key**: `[[newKey, [newKey, encodedRow], unchanged(oldEntry)]]`.
- **UPDATE, primary-key move**: the delete-old half carries `unchanged(oldEntry)`; the insert-new half keeps today's `moveGuard`, except the "`clear` + resolved REPLACE, a late rival is displaced too" case, which becomes `absent` (a silently displaced rival leaves its index entries orphaned). A `displace` move (REPLACE onto an occupied key) guards the upsert at `newKey` with `unchanged(displacedEntry)`, since `deleteIndexEntries(pkMove.row, newKey)` was computed from that image.
- **DELETE**: `[[deleteKey, undefined, unchanged(oldEntry)]]`.
- **INSERT at a key the probe found clear**: IGNORE becomes `absent` (was `keepExisting`); REPLACE becomes `absent` (was unguarded). ABORT is already `absent`. Rewrite the guard-selection comment and delete the `keepExisting` `NOTE:` that cites `6-debt-index-sweep-misses-update-delete-and-orphans`.
- **INSERT OR REPLACE at an occupied key**: the replacement upsert carries `unchanged(existingEntry)`.
- **Secondary-UNIQUE evictions** (`applyUniqueEvictions`): each eviction delete carries `unchanged(collisionEntry)`.

At initial staging every `unchanged` guard passes trivially: nothing refreshes the main collection between the read and the stage (`resolveSecondaryUniqueDecision` refreshes index trees only). Chains inside one transaction stay correct because a later statement's `collection.get` returns the earlier statement's staged entry, and replay re-runs the actions in order.

`IndexManager` needs no new guard: index entries are keyed `indexKey‖pk`, so a stale delta can only be **prevented** by refusing the main-table action, never repaired from inside the index tree. Touch `src/schema/index-manager.ts` only if `indexEntryKey` from the integrity-check ticket makes the new spec's direct tree reads simpler.

## The refusal's message and both commit modes

`TreeEntryChangedError` is not a `TreeKeyTakenError`, so `mapCommitRefusal` (`src/optimystic-adapter/txn-bridge.ts`) passes it through unmapped today. Extend the bridge: `registerEntryChangedRenderer(collectionId, render: (key: string) => string)`, registered by `registerCollections` for the main collection beside `registerKeyTakenMessage`, and a second arm in `mapCommitRefusal` that walks the cause chain for `TreeGuardRefusedError` and dispatches by class. The rendered message should read like `concurrent modification: another writer changed or removed the row in Probe at primary key (100)`, decoding the framed key through the table's `RowCodec` (`formatKeyValues` already renders a key tuple). Keep it a plain `Error` with `cause`, the same shape the UNIQUE mapping produces; the error-type question is backlog `bug-concurrent-unique-refusal-is-not-a-constraint-error` and should be solved for both classes at once there, so note this new class on that ticket. The double-mapping guard (`error.message === message`) must keep working for the rendered form.

**Legacy sweep** (`commitDirtyTreesLegacy`): the refusal now lives in the **main** tree, which is marked dirty first and, for an indexed table, is covered by the pre-flight refresh (`trees.length > 1`), so the deterministic shape (rival committed before the loser's commit began) exits at the first-tree or pre-flight point with an ordinary clean rollback and the mapped message. The residual window (rival lands between pre-flight and flush) stays with backlog `feat-optimystic-legacy-commit-two-phase`; do not widen this ticket into it.

**Session (coordinator) mode**: the commit is atomic across trees and the refusal escapes the stale re-drive (`TransactionCoordinator.commit` retries only `CoordinatorStaleLossError`); `commitTransaction`'s catch maps it. Cover with one session-mode test in the same shape as the UNIQUE spec's.

## Tests

**New `test/concurrent-row-change-refusal.spec.ts`**, two handles over one `FileRawStorage` directory (copy the scaffolding of `concurrent-secondary-unique-refusal.spec.ts`), table `T (id integer primary key, v text)` plus `create index T_by_v on T(v)`, seed rows from both handles, and the deterministic "A stages, B commits, A commits" shape for every arm. After each refused case assert on **both** handles: rows equal the winner's outcome, and `expectIndexAgreesWithScan` (two-way after `index-integrity-check`) is clean. After each refused case also run the loser's statement again sequentially and assert it now behaves as documented (UPDATE applies over the rival's value; DELETE affects the rival's row or zero rows; `or ignore` swallows; `or replace` replaces).

- UPDATE vs rival UPDATE of the same row.
- DELETE vs rival UPDATE (loser is the delete) and UPDATE vs rival DELETE (loser is the update; assert no resurrection).
- DELETE vs rival DELETE: the second deleter is refused; a comment states why (absent counts as changed) and that the retry affects zero rows.
- UPDATE of row 100 vs rival INSERT of a different key sharing the same indexed value: **both** commit, no false refusal, index holds both entries. This is the control that the guard is keyed to the row, not the leaf block.
- INSERT OR IGNORE and INSERT OR REPLACE at a clear key vs rival INSERT of that key, on the indexed table: loser refused, index clean, retry honours the disposition.
- INSERT OR REPLACE at an occupied key vs rival UPDATE of that row.
- Primary-key move vs rival UPDATE of the moving row; and a REPLACE move onto an occupied key vs rival UPDATE of the occupant.
- A `v text unique on conflict replace` table: eviction vs rival UPDATE of the evicted row.
- The UNIQUE false-refusal shape from the observation table: after the refused race, a third row inserts the loser's value on both handles and succeeds.
- Within-transaction chains with no rival: `begin; update; update; commit`, `begin; insert; update; delete; commit`, `begin; update (pk move); update; commit`, all commit and leave a clean index.
- One session-mode arm: UPDATE vs rival UPDATE in a two-table transaction fails the whole transaction with the concurrent-modification message and both tables roll back.

**`test/concurrent-insert-refusal.spec.ts`**: the two tests "INSERT OR IGNORE staged before a rival commits the key: commit succeeds and keeps the rival's row" and the OR REPLACE twin flip to refusal plus a sequential retry that honours the disposition, mirroring the loop in the UNIQUE spec.
