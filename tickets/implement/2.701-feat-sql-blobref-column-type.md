# The `blobref` column type

First part of what [docs/blobs.md §SQL](../../docs/blobs.md#sql) describes, and of backlog `feat-sql-columns-hold-blob-references`. It adds the column type and nothing else: no blob service, no reference trees, no pins. Those are `feat-blob-sql-type-and-blob-service` (the service an application puts files through, and the two SQL functions), then `feat-blob-reference-trees-follow-sql-rows`, `feat-blob-pins-follow-sql-commits` and `feat-sql-columns-hold-blob-references`.

A **blob reference** is the short string that names a large stored file — a content identifier, 59 characters of lowercase base32, with exactly one accepted spelling ([docs/blobs.md §References and pieces](../../docs/blobs.md#references-and-pieces)). `parseBlobRef` and `isBlobRef` in `packages/db-core/src/blob/blob-ref.ts` are the one rule for what is and is not one.

## The logical type

New module `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts`:

```ts
/** The name the type is registered under, and the `affinity` a catalog record stores for its columns. */
export const BLOBREF_TYPE_NAME = 'BLOBREF';

export const BLOBREF_TYPE: LogicalType = {
	name: BLOBREF_TYPE_NAME,
	physicalType: PhysicalType.TEXT,
	isTextual: true,
	supportedCollations: [],
	validate: (v: SqlValue) => v === null || isBlobRef(v),
	compare: (a, b) => compareNulls(a, b) ?? BINARY_COLLATION(a as string, b as string),
};

/** Whether a column, in either the engine's shape (`logicalType`) or a catalog record's (`affinity`), is a blobref column. */
export function isBlobRefColumn(column: { readonly logicalType?: { readonly name: string }; readonly affinity?: string }): boolean;
```

`PhysicalType`, `compareNulls`, `BINARY_COLLATION` and the `LogicalType`/`SqlValue` types all come from `@quereus/quereus`'s root entry.

The choices and why:

- **No `parse`.** A reference has exactly one accepted spelling, so there is nothing to canonicalize; anything `isBlobRef` refuses fails Quereus's `validateValue` with its own message, `Type mismatch for column 'x': expected BLOBREF, got …`, at `StatusCode.MISMATCH`. Adding a `parse` would only move the same refusal to a `Type conversion failed` message.
- **`supportedCollations: []`**, the empty list JSON and the temporal types carry — not `['BINARY']`. `compare` here is collation-blind (it never applies the function it is handed), so a declared non-BINARY collation would be silently ignored. The empty list makes `validateCollationForType` (`@quereus/quereus/src/schema/table.ts`) refuse `collate nocase` on a `blobref` column outright, with "type supports no collation other than BINARY", and makes `resolveDefaultCollation` fall such a column back to BINARY under a non-BINARY session `default_collation`.
- **`collationAware` unset**, so `pkKeyCollationName` (`@quereus/quereus/src/planner/analysis/comparison-collation.ts`) keys a `blobref` primary key under BINARY — which is the order `compare` actually imposes, so key bytes and comparator agree.
- **`semanticOrdering` unset**, so the column compares as the text it is stored as. With TEXT physical type, no semantic ordering and a BINARY collation, `bytesOrderAsValues` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts` already admits such a column, so an index on it is an ordinary text index and that file needs no change.
- **The row codec needs no change.** `deserializeKeyPart` in `packages/quereus-plugin-optimystic/src/schema/row-codec.ts` keeps any affinity other than BLOB/INTEGER/REAL/NUMERIC/BOOLEAN as its raw string, so a `BLOBREF` column round-trips verbatim. A NULL `blobref` references nothing.
- **The name is upper case**, matching `TEXT` and `BLOB`, so a catalog record's `affinity` reads `BLOBREF`. SQL spells the declaration in any case (`inferType` upper-cases before it looks up).

## Registration

`register` in `packages/quereus-plugin-optimystic/src/plugin.ts` returns a `types` array beside `vtables`, `functions` and `collations`:

```ts
types: [{ name: 'blobref', definition: BLOBREF_TYPE }],
```

`registerPlugin` (`@quereus/quereus/src/util/plugin-helper.ts`) registers types after vtables and functions and before a host calls `plugin.hydrate`, which is early enough for every path below. The registry is process-wide (`TypeRegistry` in `@quereus/quereus/src/types/registry.ts`), so every `Database` in the process sees it.

Export `BLOBREF_TYPE`, `BLOBREF_TYPE_NAME` and `isBlobRefColumn` from `packages/quereus-plugin-optimystic/src/index.ts`, so a host registering the plugin's parts by hand can register the type and a later part can ask whether a column is one.

## Refusing to open a table whose type is not registered

**Decided: refused loudly, never opened as something else.** Two distinct failures exist, and they need two guards at two different seams.

**The sharp edge.** With `strict_type_names` on (Quereus's default) Quereus itself refuses an unknown declared type at `create table`. With it off, `inferType('blobref')` falls through to the SQLite affinity rules, and the name contains `BLOB`, so the column becomes a **BLOB** column — whose row codec base64-*decodes* every stored string into bytes (`col.affinity === 'BLOB'` in `packages/quereus-plugin-optimystic/src/schema/row-codec.ts`). A table opened that way is silently, permanently wrong about its own column.

### Guard 1 — a stored record whose declared spelling no longer resolves to the type it was written under

`storedToColumnSchema` in `packages/quereus-plugin-optimystic/src/schema/schema-manager.ts` re-infers a hydrated column's logical type from its declared spelling (`inferType(col.declaredType)`) and falls back to the record's canonical `affinity` only for a column declared without a type — where `registeredStoredType` already refuses an unregistered name. So the `declaredType` arm is the hole: a record saying *this column's rows were written as `BLOBREF`, declared `blobref`* re-infers to `BLOB_TYPE` in a process that has not registered the type, with nothing said.

Close it generally: in the `declaredType` arm, refuse when the re-inferred type's `name` differs from the record's `affinity`. That is `registeredStoredType`'s existing rule — "read as BLOB instead, the column's row codec and storage-adoption guard would key on a type it was never written under" — applied to the other arm, and it covers **every** plugin-registered logical type rather than this one. Throw a `QuereusError` at `StatusCode.ERROR` naming the column, the stored affinity, the declared spelling and what the type resolved to instead, and saying to load the plugin through `registerPlugin` (or to register `plugin.types` with `db.registerType` when registering its parts by hand) before opening the table. Put both arms behind one local helper so the two messages stay together.

This is one site covering every caller: `hydrateCatalog` and the stale-record rebuild (both through `storedToTableSchema`), the vtab's hydrate arm in `OptimysticVirtualTable.doInitialize`, the vtab's own load arm, and the index manager's partial-index predicates. The plan this ticket replaces asserted at two of those seams and would have missed the rest.

**Confirm the guard is quiet for every record that exists today.** Every record is written by `columnSchemaToStored`, which stores `affinity: col.logicalType.name` beside the declaration's own spelling, and a column's `logicalType` is `inferType(declaredType)` — so `inferType(declaredType).name === affinity` holds for every built-in spelling (`int`, `varchar(20)`, `timestamp`, `blob`, …). The plugin suite, which creates and hydrates tables of every type it supports, is the check; it runs in review.

### Guard 2 — a fresh declaration naming `blobref` while the type is not registered

Guard 1 needs a record. A `create table … (Content blobref)` in a process with `strict_type_names` off has none: the column is built as BLOB and the record it then writes says `affinity: 'BLOB'`, consistently, so nothing downstream ever notices.

So `OptimysticVirtualTable.doInitialize` refuses it, at the one point where the table's resolved `storedSchema` is settled and before `new RowCodec(storedSchema, …)` is built. The rule, over `storedSchema.columns`: a column whose declared spelling's base name is `blobref` (case-insensitively; the base is the text before any `(…)` parameter list, the same rule `declaredTypeBase` in `@quereus/quereus/src/types/registry.ts` applies) while its `affinity` is not `BLOBREF`. Throw naming the table and the column, with the same remedy sentence as guard 1. A record carrying `affinity: 'BLOBREF'` with no declared spelling is guard 1's; a record carrying both is guard 1's too.

Put the check in `blobref-type.ts` as an exported function over `readonly { name: string; affinity: string; declaredType?: string }[]` plus a subject string for the message, so `doInitialize` holds one call and the rule lives with the type.

An older plugin build that predates the type cannot open such a table at all — which is the same refusal, from Quereus, and is what [docs/blobs.md §Compatibility](../../docs/blobs.md#compatibility) already says. Nothing to build for it.

## Edge cases & interactions

- **Malformed references on write.** Uppercase base32, a version-0 CID, another codec or multihash, surrounding whitespace, a padded spelling (trailing `=`), a number: each refused by `validate` at `StatusCode.MISMATCH`. Spec cases below.
- **NULL.** Accepted in a nullable `blobref` column (Quereus's `validateValue` short-circuits NULL before `validate`, and `validate` admits it anyway). Spec case.
- **A `blobref` value copied between two `blobref` columns.** `buildCellCoercion` (`@quereus/quereus/src/types/validation.ts`) skips conversion when the source's static type IS the target type and the value inhabits its physical type — so `insert into B select Content from A` re-validates nothing. Correct: the value was validated when it entered `A`. Inspection; no test (it exercises Quereus's identity guard, not ours).
- **`collate nocase` on a `blobref` column.** Refused by `validateCollationForType` because of the empty collation list. Inspection.
- **A non-BINARY session `default_collation`.** The column falls back to BINARY (`resolveDefaultCollation` gates the implicit default on explicit support). Inspection.
- **An index on a `blobref` column.** An ordinary text index; `bytesOrderAsValues` admits it, so an ordered walk still serves `order by`. Inspection — this is existing behaviour of the TEXT physical type, not new logic.
- **`strict_type_names` off.** Guard 2 is the only thing that refuses, and it compares the record's affinity rather than asking whether Quereus resolved *some* type, so it fires whatever the pragma says. Inspection.
- **Two `Database`s in one process.** The type registry is process-wide; a second `registerPlugin` re-registers the same definition object and Quereus logs its "Overwriting existing type" warning. Harmless — `buildCellCoercion` and `registeredStoredType` compare types by object identity, and the object is the same one. Inspection.
- **A host that registers `vtables` and `functions` by hand and forgets `types`.** Exactly the case guard 1 catches on hydrate and guard 2 at create. Spec case below, and the README says to register `types` too.

## Tests

`packages/quereus-plugin-optimystic/test/blobref-column.spec.ts`, on the `test` transactor, following the registration helper in `packages/quereus-plugin-optimystic/test/catalog-hydration.spec.ts` — widened to register `plugin.types` through `db.registerType` beside `vtables` and `functions`. One table, `create table Attachment (Id text primary key, Content blobref null)`. Build the reference with `buildBlob` from `@optimystic/db-core` over a few bytes, or take a fixed vector from `packages/db-core/test/blob-builder.spec.ts`.

- **A well-formed reference round-trips.** Insert and select it back, byte-identical.
- **Each malformed shape is refused** at `StatusCode.MISMATCH`: the reference upper-cased, a version-0 CID, a CID of another codec, the reference with a leading space, the reference with `=` padding, and an integer. One `it` with a table of inputs.
- **NULL inserts and reads back as NULL.**
- **Hydrate over the same storage.** A second `Database` over the same shared transactor, with `types` registered, hydrates the table and reads the stored reference back unchanged; without `types` registered, `plugin.hydrate(db)` is refused with an error whose message names the column and `BLOBREF` (guard 1).

Nothing tests the registration wiring itself, the type's metadata flags, or that an index on the column still walks — a type, the existing index-walk specs and `yarn check` cover those.
