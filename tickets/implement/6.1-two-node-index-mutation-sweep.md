## Why

No two-node spec (`test/two-node-*.spec.ts`) issues an UPDATE or DELETE. The index-maintenance paths for them (`updateIndexEntries` / `deleteIndexEntries` in `src/schema/index-manager.ts`) are exercised only single-node, in `index-support.spec.ts`. Changing an indexed value is the ordinary way an index entry gets orphaned: the old entry must go, the new one must arrive, and a sibling node may hold the tree at a different moment.

This ticket builds on `index-integrity-check`. That ticket makes `expectIndexAgreesWithScan` compare the index to the table in both directions, and adds `readIndexIntegrity(db, table)`, which returns the per-index reports without asserting. Without that, mutation coverage would be more green tests that cannot see the defect class.

A plan-stage probe already ran the racing shapes and found three verified orphan producers; see `fix/concurrent-row-changes-leave-orphaned-index-entries`. So this sweep will NOT be all-green under today's replay semantics. How to handle that without skipping or softening is specified below, and it is the most important part of this ticket.

## Design — a second generator, in its own file

Do not add a dimension to `two-node-index-interleaving-sweep.spec.ts`: its 144 cases multiply, and its header `NOTE:` says so. Create `test/two-node-index-mutation-sweep.spec.ts` with two generated groups. Reuse `startMockMesh` / `createMeshDbNode` from `mesh-node-harness.ts`, and use the same conventions as the insert sweep: a case name that IS the ordering; a pure-data coverage-guard `describe` that needs no mesh; `this.timeout(120_000)`.

Schema: the insert sweep's `FormationUsage (Id integer primary key, Token text)`, plus `create index formation_usage_by_token on FormationUsage(Token)`, at `tree://default/FormationUsage`.

Common setup for every case:
1. The declarer creates the table and the index.
2. The other node arrives according to `open`.
3. A inserts `(100, 'tok-a')`, then B inserts `(200, 'tok-b')`.
4. Assert both nodes' scans hold both rows before mutating, so the comparison afterwards is not vacuous; this is the insert sweep's `expectScansConverged` idea.

The mutation target is always row 100, A's row. "Owner" means A and "sibling" means B.

### Group 1 — sequential mutation (64 cases)

Crossed dimensions:
- `declare`: A | B. Block responsibility is by key hash, so the nodes are not symmetric.
- `open`: `redeclare` | `hydrate`. Same meaning as the insert sweep. `both-invent` is omitted: it concerns inventing an empty collection, and rows exist before any mutation here.
- `mutator`: `owner` | `sibling`. The sibling case is a node removing an index entry another node wrote.
- `mutation`:
  - `to-sibling-value`: `set Token = 'tok-b'`, onto the value row 200 already holds.
  - `to-new-value`: `set Token = 'tok-new'`.
  - `pk-move`: `set Id = 101`. The indexed value is kept and the primary key changes, so the entry's tree key changes through its primary-key suffix.
  - `delete`.
- `locate`: `by-pk` (`where Id = 100`) | `by-index` (`where Token = 'tok-a'`). The index-routed form makes the mutator's row source a seek down its own view of the index.

After the mutation:
- Assert both nodes' full scans equal the expected rows.
- Run `expectIndexAgreesWithScan(db, 'FormationUsage', 'Token')` on BOTH nodes.

Expected: all green. The probe ran `sibling × to-new-value` and `sibling × delete` (by-pk, declare=A, redeclare) and both were clean. A red case here is a sequential, single-writer orphan producer. That would be a serious finding: file it as a `fix/` ticket with `repro: verified`, citing the case name, and follow the known-producer rule below. Do not skip it.

### Group 2 — racing mutation (32 + 4 cases)

Both nodes stage in open transactions before either commits: `A: begin; <aOp>`, `B: begin; <bOp>`, then the two commits in `commit` order. Capture each commit's outcome with `Promise.allSettled` semantics, awaited sequentially; do not let a throw abort the case.

Crossed dimensions:
- `declare`: A | B.
- `aOp`, `bOp`, each one of:
  - `update`: A sets row 100's Token to `'tok-x'`, B to `'tok-y'`.
  - `delete`: of row 100.
  - `insert-shared`: A inserts `(300, 'tok-a')`, B inserts `(400, 'tok-a')`. A new row under the value row 100 currently holds, so a delete of `tok-a‖100` must not take a sibling entry with it.
  - The pair (`insert-shared`, `insert-shared`) is excluded as insert-only, which leaves 8 pairs.
- `commit`: `a-first` | `b-first`. This also closes, for mutations, the insert sweep's recorded gap that its `staged-both` order always commits A first.

That gives 2 × 8 × 2 = 32 cases. `open` is fixed at `redeclare`, since open interacts with setup rather than with replay.

Plus an **INSERT OR IGNORE race** (4 cases: `declare` × `loser` ∈ A | B):
1. The loser runs `begin; insert or ignore into FormationUsage (Id, Token) values (300, 'tok-ignored')`.
2. The winner commits `insert … (300, 'tok-winner')`.
3. The loser commits.

`test/concurrent-insert-refusal.spec.ts` deliberately covers IGNORE only on an index-free table; this is the indexed shape.

### The prediction model — how a known defect is pinned, not skipped

Under today's replay semantics some racing cases leave orphans. The rule inherited from the insert sweep's header still holds: never narrow the generator, skip a case, or soften the oracle. Each racing case therefore asserts an exact **predicted** outcome, computed by a small pure model of the replay semantics as they are documented at the staging sites. The model does not list case names. A case whose prediction is "clean" asserts clean with `expectIndexAgreesWithScan`. A case whose prediction carries a discrepancy asserts `readIndexIntegrity`'s report equals the prediction exactly: the same orphans, reasons, index payloads and primary keys, and no other discrepancy. When the defect is fixed, those cases go red on "expected an orphan, found none", which is the signal to delete the model.

The model, which should be about 40 lines in the spec:
- **State**: `rows: Map<id, token>` and `entries: Set<"token|id">`. Initially rows are `{100: tok-a, 200: tok-b}` and entries `{tok-a|100, tok-b|200}`.
- **Each op is computed against the pre-race snapshot**, because both stage before either commits:
  - `update(t)`:
    - Row effect: `rows.set(100, t)`. This is a blind upsert: the non-moving UPDATE stages `[[newKey, [newKey, encodedRow]]]` with no guard, so it also resurrects a row a rival deleted.
    - Index delta: delete `tok-a|100`, add `t|100`.
  - `delete`:
    - Row effect: `rows.delete(100)`.
    - Index delta: delete `tok-a|100`.
  - `insert-shared(id)`:
    - Row effect: `rows.set(id, 'tok-a')`. The key is distinct, so its `absent` guard never trips.
    - Index delta: add `tok-a|id`.
  - `insert-or-ignore` (loser):
    - Row effect: none if the key is present at replay. This is the `keepExisting` guard.
    - Index delta: add `tok-ignored|300`, applied regardless.
- **Apply** the first committer's row effect and index delta, then the second committer's. The index-tree actions replay independently of the main-tree outcome; that is the defect `fix/concurrent-row-changes-leave-orphaned-index-entries` describes.
- **Predict**:
  - Rows are `rows`; both nodes' scans must equal them.
  - Implied entries are `{token|id for each row}`.
  - Orphans are `entries − implied`: reason `no-row` if the id has no row, else `stale-value`.
  - Missing entries are `implied − entries`.
  - Both commits fulfil.

The probe observed three cases, all matching the model:
- update(A→x) then update(B→y): orphan `tok-x|100` stale-value.
- update(B→y) first, then delete(A): orphan `tok-y|100` no-row.
- IGNORE race: orphan `tok-ignored|300` stale-value.

The model also predicts:
- delete-first then update-second leaves a clean index but a **resurrected** row 100 carrying the second update's token.
- `insert-shared` against a delete or update stays clean.

These other predictions are unverified. **If an observed case disagrees with the model, do not edit the model to fit the observation.** Find which documented semantic was wrong: the blind upsert, the blind delete, keepExisting, or independent index replay. Record it as a new arm on `fix/concurrent-row-changes-leave-orphaned-index-entries`, or as a new `fix/` ticket if it is a different root cause. Only then correct the model, citing that arm in a comment.

Header the model with a `NOTE:` naming `concurrent-row-changes-leave-orphaned-index-entries`. It must say the model encodes known-defective replay semantics, and that the fix ticket's regression criterion is this group going green with the model deleted.

### Cost

About 100 cases. The insert sweep measured roughly 90 ms per case on the mock mesh (13 s for 144), so expect roughly 10 s. Measure the new file wide, and the package suite before and after, with the commands in the insert sweep's header. Record the numbers in the new spec's header. If the file exceeds ~15 s, cross `open` with `declare` only, keeping `open=redeclare` for the rest of Group 1, rather than gating the file. A sweep that only runs when someone remembers a flag cannot catch the bug it exists for. Like the insert sweep, it runs on every `yarn test`.

## Edge cases & interactions

- **`pk-move` in Group 1**: the main table stages delete-old plus a guarded insert-new, and the index stages one action, deleting `tok-a|100` and adding `tok-a|101`. After the move, `where Id = 100` must be empty and `where Token = 'tok-a'` must find 101 on both nodes, and the tree must hold no `|100` entry.
- **`to-sibling-value`** puts two rows under `tok-b`. The report must show two distinct entries under one value prefix, and neither may mask the other.
- **`by-index` locate on the sibling**: the sibling's UPDATE takes its row source from its own index seek. If that seek misses the row, the UPDATE silently touches nothing. The post-mutation scan assertion catches that as a row-set mismatch, which is a distinct failure from an orphan, so do not fold the two together.
- **`hydrate` sibling mutating**: a node that never issued DDL mutates. Its IndexManager comes from the persisted catalog, so the mutation must stage into the index. Otherwise the result is the "detached writer" orphan that the `backfillIndexTrees` `NOTE:` names.
- **Commit refusals**: the model predicts both commits fulfil in every racing case. A rejection is an observation that disagrees with the model: handle it by the rule above, and do not catch-and-continue.
- **Sequential awaits only**: the harness is single-threaded, so staging overlaps and commits do not (see the `WRITE_ORDERS` comment in `two-node-shared-index-key.spec.ts`). Do not use `Promise.all` on the commits: it would make the commit order nondeterministic and the case name would lie.
- **Undisposed Databases**: each case leaves two `Database`s open (the accepted-tradeoff `NOTE:` on `startMockMesh`). With about 200 more, if the file slows or the heap climbs, close nodes in an `afterEach` before looking elsewhere.
- **The coverage guard** must check that every dimension value appears, that the 8 racing op-pairs are all present, and that there are no duplicate case names. It runs without a mesh.
