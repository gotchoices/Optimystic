# Cohort gossip sends a frame only when something changed

GitHub [#49](https://github.com/gotchoices/Optimystic/issues/49), from Sereus (Taleus). First of three tickets from the plan `feat-idle-cohort-gossip-costs-a-phone-little`. The other two are `push-state-gossip-sends-only-when-the-state-changed` and `cohort-gossip-is-verified-once-off-the-synchronous-path`. The wire change the reporter also proposed (one frame per member per round) is parked as backlog `feat-cohort-gossip-one-frame-per-peer-per-round`.

## What was measured

On 1.19.0, a two-member group (a Galaxy S7 and a Node party, over a relay) watched 18 tables tagged `optimystic.network_watch`. With both idle, each party received 108 gossip frames every 30 s, and each frame costs one Ed25519 verify: about 40 ms on the S7, 2.4 ms in Node. 15.6% of the S7's 60 s profile was inside `ed25519.verify`, and about 92% of that came from this gossip path.

## Why idle rounds send every tick (the plan's open question)

108 frames per 30 s is exactly 18 coord engines × 6 rounds (`gossipIntervalMs` defaults to 5 s). So every engine sends a frame on every tick. The cause is not renewals. A subscriber renews once per `ttl / 3` (30 s at the default TTL, 20 s Edge), so a renewal makes at most one round in six carry a record.

The cause is how `gossipRound` in `packages/db-p2p/src/cohort-topic/host.ts` decides a round is idle. A round counts as idle only when it has no resident topic summaries and no deltas, and only an idle round is throttled by `willingnessHeartbeatMs`. Every engine serving a watched table holds at least one subscriber's registration, so `residentTopics()` is never empty. `topicSummaries` therefore always has an entry, and `buildCohortGossip` builds and sends a frame every round, even when that frame repeats the previous one apart from its `timestamp` and the advisory rate fields.

## The rule

A round sends a frame when any one of these holds:

- **It carries deltas:** `pending` is not empty. That covers an admitted record (`onAdmit`), a renewal touch, a re-attach re-stamp, an eviction, and child link or unlink deltas, including the child-set re-advertisement, which already has its own throttle.
- **Its content differs materially from the last frame this engine sent.** Material means everything in the frame except `timestamp`, `signature`, and each topic summary's `arrivalsPerMin` and `queriesPerMin`. So these count: `cohortEpoch`, `treeTier`, `willingnessBits`, `loadBuckets`, `windowSeconds`, `rootPlaced`, and the set of topic summaries, each reduced to `topicId`, `tier`, `directParticipants`, `promoted` and `childCohortCount`. Compare topics keyed by `topicId`, not by the order `residentTopics()` returns them in. A first frame (nothing sent yet) always differs.
- **`willingnessHeartbeatMs` has elapsed since this engine's last frame** (default 30 s, `DEFAULT_WILLINGNESS_HEARTBEAT_MS`).

Otherwise the round sends nothing and leaves `pending` untouched. It still runs everything else it runs today: the root-group refresh, `engine.sweepStale` (whose evictions become deltas and so force a frame), `traffic.publish`, and the child-set re-advertisement check.

`buildCohortGossip`'s existing idle rule stays as it is. An engine with no topics and no deltas sends only while willing (`selfWillingnessBits !== 0`). So for an idle engine the rule above reduces to today's heartbeat, with one improvement: a change from unwilling to willing is a material change, so it is announced on the next round instead of waiting for the heartbeat. A change from willing to unwilling on an idle engine still sends nothing, as today. Keep that.

Every frame the engine emits records its material key and its time, the out-of-band willingness advert included (today the advert already sets `lastGossipAt`). The next round then compares against what siblings actually last heard.

Shape: a pure helper in `cohort-gossip-driver.ts` that reduces a `CohortGossipV1` to its material key (a canonical string is enough; summaries sorted by `topicId`), plus a pure "is this round due" function over `{ hasDeltas, key, lastSentKey, lastSentAt, now, heartbeatMs }`. `gossipRound` then reads as: build the summaries, decide due-ness, drain and send only if due. This keeps the rule unit-testable without the host. Decide due-ness before `pending.drain()`, because a round that does not send must not drop the queued deltas. Nothing between the decision and the drain awaits, so no delta can slip in between.

## Effect

In the reported shape, each engine holds about two registrations (one per machine's subscription), and each member is primary for about one of them. So each engine sends about one frame per ping interval (its own renewal touch), and the heartbeat is already satisfied by that. That is roughly 18 frames per 30 s instead of 108, so about six times fewer verifies on the receiving phone. A real change still goes out on the next round, as today.

## What it costs

- **The advisory traffic rates go stale for longer.** `arrivalsPerMin` and `queriesPerMin` on a sibling are now up to `willingnessHeartbeatMs` old in steady state, where the doc says "lags by at most one gossip round". Nothing in admission, routing or promotion reads them. Matchmaking's hang-out decision does, but a topic that is actually getting new registrations sends every round anyway, because admissions are deltas. Update §Topic traffic signal: a material change or a delta reaches siblings on the next round; rates alone refresh at least once per `T_willingness_heartbeat`.
- **Liveness is unchanged.** No consumer judges a member by how recently its gossip arrived: `CohortView.merge` keeps the newest contribution forever, and willingness (`willingness.ts`) and traffic (`traffic.ts`) read it with no age check. A silent member is noticed through FRET membership and renewal failover, neither of which reads gossip cadence. Say so in the §Cohort gossip cadence paragraph, because the question will come up again.
- **Replica freshness is unchanged.** Renewal touches are still deltas, sent on the next round.

## Considered and not done: deferring renewal touches

The plan's open question suggested not gossiping a renewal that changes nothing a sibling needs. A sibling does need it, though: its replica is evicted at `lastPing + ttl` by its own `sweepStale`. A touch could still be held for up to `ttl / 6` and batched with other touches. That buys nothing in the reported shape, which is about one renewal per engine per ping interval. It would only help an engine holding many subscribers' records. It also widens a window that already hurts failover: a renewal not yet gossiped when the primary dies leaves the backup one ping older, which is closer to its own TTL eviction before the participant's three-strike re-attach reaches it. Leave touches immediate, and put a `NOTE:` tripwire at the `touch:` hook in `createRenewalCohortSide`'s gossip wiring in `host.ts`: if renewal-driven frames on engines holding many records ever show up in profiles, defer lastPing-only touches up to `ttl / 6`, and weigh that against the backup-replica age at failover.

## Edge cases & interactions

- **A round that does not send keeps its deltas.** Only a sending round drains `pending`. Verified by the order of operations in `gossipRound` (inspection), and the host test below exercises it.
- **An eviction always sends.** `sweepStale` runs before the decision and queues each eviction as a delta. Inspection.
- **An epoch rotation sends.** `cohortEpoch` is in the material key, so siblings see the drift on the next round. Inspection of the key function; the pure test below covers one material field.
- **Child-set re-advertisement still goes out on its own throttle.** It enqueues into `pending`, which forces a frame. Inspection.
- **The willingness advert and the round interleave.** The advert records its key and time. A round right after it compares against the advert, sees a difference if it has topics (the advert carries no summaries) and sends once. Conservative, never silent. Inspection.
- **An engine closed while signing** still sends nothing (`signAndBroadcast` checks `closed`). Record the key and time only for a frame actually handed to `bus.broadcast`, or accept recording it on close since the engine is gone either way. Inspection.
- **`gossipRound`'s return value.** Callers and tests read it as "the frame this round sent, or `undefined`". Keep that meaning: `undefined` for a round that was not due.
- **Load buckets that flap** on a busy phone make rounds material more often. The worst case is today's one frame per round, never more. Accepted.
- **`traffic.publish` runs on rounds that do not send**, so a member's own reply snapshot can briefly use counts newer than what its siblings hold. Both are advisory. Accepted; a one-line comment at the call is enough.

## Tests

- A contract test on the pure due-ness and material-key helpers, one case per branch: deltas → due; a material field changed (for example `promoted` or `willingnessBits`) → due; only `arrivalsPerMin` changed, inside the heartbeat → not due; unchanged at exactly `heartbeatMs` since the last send → due; unchanged one ms short → not due; topics in a different order → same key.
- One host-level test in `gossip-cadence.spec.ts`, with the timer parked and rounds driven by hand as the existing tests do. An engine holding one admitted registration sends on its first round (the admission delta), sends nothing on rounds inside the heartbeat, sends on the round after a renewal touch, and sends again once `willingnessHeartbeatMs` has elapsed with no change.
- Existing `gossip-cadence.spec.ts` cases that assume an engine with resident topics sends every round need adjusting to the new rule. Do not loosen what they assert about frame contents.
