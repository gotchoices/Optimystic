# Push-state gossip sends only when the state changed

GitHub [#49](https://github.com/gotchoices/Optimystic/issues/49). Second of three tickets from the plan `feat-idle-cohort-gossip-costs-a-phone-little`. The first is `cohort-gossip-sends-a-frame-only-when-something-changed`, which applies the same rule to the signed cohort gossip. This ticket does not depend on it: the two run on different timers and different files.

## What is wrong

The reporter measured the signed cohort gossip. A second periodic gossip rides the same transport and was not measured: reactivity's push-state gossip (`ReactivityPushStateGossipDriver` in `packages/db-p2p/src/reactivity/push-state-gossip.ts`). It has its own unref'd 5 s timer (`DEFAULT_GOSSIP_INTERVAL_MS`). On every tick `round()` serializes each live push state, meaning each root this node serves that has at least one subscriber, and broadcasts it to the root group with `broadcastOver`. That covers the replay ring of up to 256 full notifications, the dedupe window and `lastRevision`. A frame can be up to `DEFAULT_STREAM_MAX_BYTES` (512 KiB). It goes out whether or not anything changed.

In the reported shape (18 watched tables, both machines in every root group) that is 18 frames per 5 s from each machine. Each one costs the receiver a JSON decode, the `isCohortMember` gate (a read of the key network's serving cohort, which the `NOTE:` in `libp2p-node-base.ts` already flags as one read per frame) and a `mergeGossip`. The frames are unsigned, so there is no Ed25519 cost. It is still idle work that grows with the number of watched tables.

## The rule

For each live push state, a round sends its frame when either of these holds:

- **The frame differs from the last frame this driver sent for that push state.** Compare the bounded frame that `broadcastOne` would send, which already includes any clipping.
- **`reAdvertiseMs` has elapsed since that push state's last send.** This is a new driver option, defaulting to `DEFAULT_WILLINGNESS_HEARTBEAT_MS` (30 s) from `packages/db-p2p/src/cohort-topic/cohort-gossip-driver.ts`, the same slow refresh the cohort gossip uses.

Otherwise the push state is skipped this round.

The refresh is required, not optional. `mergeGossip` is a union, so the only way a member that joined the root group after a change, or missed that one frame, catches up is a later frame. Today that is the next tick; with this change it is the next refresh. A change itself still goes out on the next tick, so the "backstop to the live fan-out" role keeps its one-round latency for anything new.

**What to remember per push state:** a SHA-256 digest of the last sent frame (`@noble/hashes`, already a db-p2p dependency) and the time it was sent. Do not keep the frame bytes: at up to 512 KiB per push state, that is real memory on a phone watching many tables. Key the memory by the `PushState` object in a `WeakMap`, so a push state the forwarder host drops (after a rotation's drain window) leaves nothing behind. Read the time from the driver's `clock` dep, which exists and is unused today ("Reserved for parity"). Default it to `Date.now`, so tests can drive time.

Serializing and hashing still run every round on the sending side. That costs no network and no receiver work, and it is how the driver learns that nothing changed without the push state carrying a version counter. If the sender-side cost ever shows in profiles, add a change counter to `PushState` (bumped by `enqueueForSubscribers`, `mergeGossip` when it changes something, and ring eviction) and skip the serialize. Leave that as a `NOTE:` at the comparison.

## Convergence after a merge

A frame received from a sibling can change this node's state, and then this node sends once on its next tick. Merges are unions with last-writer-wins on `lastRevision`, so after a change the members exchange a bounded number of frames and then go quiet: a merge that adds nothing leaves the bytes unchanged. Confirm this by reading `PushState.mergeGossip` and `ReplayBuffer.merge`. If a merge can rewrite an entry without changing its meaning (for example re-stamping a field), two members could keep sending to each other each tick. Check that it does not; if it does, fix the comparison, not the merge.

## Edge cases & interactions

- **A clipped frame.** Compare the clipped frame. A ring that keeps growing past the bound still changes its most-recent window, so it still sends. The truncation log and `onTruncate` fire only on rounds that send. Inspection.
- **A push state that moves to a new root** (`tailIdAtJoin` changes on a rotation follow) produces a different frame, and the cohort coord it broadcasts to changes as well, so it sends at once. Inspection.
- **`stop()` mid-round** keeps today's behaviour. Inspection.
- **A send that fails at the transport** (`broadcastOver` swallows per-peer failures) still counts as sent; the refresh covers it. Accepted, matching cohort gossip.
- **The inbound side is unchanged.** Only how often frames arrive changes.

## Tests

One test in `push-state-gossip.spec.ts` with a fake transport and an injected clock. Round 1 broadcasts. Round 2 at the same state, inside `reAdvertiseMs`, broadcasts nothing. After a notification is enqueued on the push state, the next round broadcasts. At `reAdvertiseMs` with no change it broadcasts again. Existing tests that count one broadcast per round per collection need adjusting to the rule; keep what they assert about frame contents and clipping.
