# Reproduce (and pin closed) the commit/refresh interleaving

Part A of the original `2-coordinator-mutates-collections-outside-their-latch`, split out after a
budget stop. The core fix ticket has landed or is landing first (see `prereq:`); this spec both
**documents that the old code was broken** (via assertions that fail under the pre-fix mechanism)
and **pins the fixed behavior**. Test designs below were worked out against the actual code — use
them.

## Honesty requirement (carried from the original ticket)

Record in the handoff whether each case would have reproduced the fork under the old mechanism
(run against pre-fix behavior mentally or by temporarily reverting locally — do not commit a
revert). A negative is a real result: if the interleaving cannot corrupt state even pre-fix, the
downstream two-machine fork is still unexplained and the handoff must say the next evidence has to
come from a downstream run carrying the new diagnostic fields (see
`2.4-collection-divergence-report-fields`). Do not adjust a test until it "fails"; report what is.

## Case 1 — refresh between durable commit and recordCommitted (outcome A)

The exact mechanism matching the field diagnostics (`held` one ahead of storage, own action id at
a revision storage attributes elsewhere), and it needs **no rival writer**:

1. `GatedCommitTransactor extends DelegatingTransactor`:
   - `pend(req)`: record `req.rev` into `pendRevs[]`, delegate.
   - `commit(req)`: `const res = await this.inner.commit(req)` (durable FIRST), then resolve a
     `commitParked` promise, then `await gate`, then return `res`. Gate/parked promises are
     constructor-built deferreds with an `openGate()` method.
2. Build a single-collection coordinator commit (copy the raw-Collection setup from
   transaction.spec.ts's `makeConflictSetup`, or a Tree — raw Collection with a trivial `set`
   handler is lighter).
3. `const commitPromise = coordinator.commit(tx); await transactor.commitParked;` — storage now
   holds the new revision; the coordinator has not yet run `recordCommitted`.
4. `const updatePromise = collection.update();` then drain a handful of macrotasks
   (`await new Promise(r => setTimeout(r, 0))` in a small loop) so the refresh gets every chance
   to interleave. Under the old code it completes here and adopts the committed revision (with the
   transaction's own action id, read from the log); `recordCommitted` then recomputes and appends
   the SAME action at rev+1 — the fork. Under the fix the update blocks on the instance latch.
5. `transactor.openGate(); await commitPromise; await updatePromise;` (awaiting updatePromise is
   also the no-deadlock assertion; rely on the mocha timeout to catch a hang).
6. Assert:
   - `collection.committedRevision() === transactor.pendRevs[0]` (pre-fix: pendRevs[0] + 1);
   - `collection.committedActionId() === transaction.id`;
   - a FRESH `Collection.open` over the inner transactor reports the same committedRevision —
     local record and storage agree (pre-fix: local is one ahead → `context-not-lowered` forever).

## Case 2 — refresh replaying the tracker under a parked pend (outcome B)

Needs a rival so the refresh has something to replay against:

1. Wrapper gates `pend` BEFORE delegating: resolve `pendParked`, `await gate`, snapshot
   `{ pended: structuredClone(req.transforms), staged: structuredClone(collection.tracker.transforms) }`
   into a list **at delegation time** (after the gate), then delegate. Give the wrapper a
   collection getter for that.
2. While parked: run the rival (a second Collection instance over the same id committing through
   `updateAndSync` — copy `rivalCollectionWrite` from transaction.spec.ts:4727-4734; with the
   instance-scoped latch keys from the core ticket, the rival does NOT block). Then launch
   `collection.update()` on the loser's instance and drain macrotasks. Pre-fix this runs
   `replayActions()` → `tracker.reset()` (which REPLACES the transforms object — the coordinator's
   captured reference goes stale-stable) so pended-vs-staged diverge; post-fix it blocks on the
   latch.
3. Open the gate. The pend then fails stale (rival took the rev), the coordinator retries, the
   retry-loop `update()` runs outside the held span, attempt 2 pends and wins. Await commit and
   the update promise.
4. Assert:
   - for EVERY snapshot pair, `pended` deep-equals `staged` — the transforms sent to the network
     are exactly what the collection believed it staged at that moment (pre-fix: the first pair
     differs);
   - both writes are durable (loser's and rival's — read back via `logActions` and a fresh tree /
     collection over the inner transactor);
   - exactly one log entry per writer (no duplicate append from the retry).

This case is also the commit-then-retry regression the original ticket demanded for latch
non-reentrancy: the retry's `collection.update()` must run outside the held span or the test
hangs.
