# Storage flushes once per write group

Reported in GitHub #37 (kjeib). Second half of the seam: `raw-storage-can-be-flushed` gave `IRawStorage` a `flush()` (contract: a write is durable once a later flush resolves, and what survives a crash is a prefix of the resolved writes in order) and every backend a no-op one. This ticket makes the node call it. Downstream: `file-storage-pays-one-fsync-per-write-group` makes the file backend's flush the one sync per group, `durability-window-scales-with-cohort-size` turns the call into a request with a deadline, `mobile-and-browser-storage-keep-the-durability-window` makes the other backends' flush real. Nothing changes on disk in this ticket either.

## Where groups are

Every write to block storage happens inside one of these, always under the block write latches, and the caller reports the outcome to other machines only after it returns:

- `StorageRepo` (`packages/db-p2p/src/storage/storage-repo.ts`): `pend`, `commit`, `cancel`, `saveReplicatedBlock`, `recoverBlock`, and inside `get` the read-driven promotion and the coverage restore (`restoreRevision` under `withBlockWriteLatch`).
- `applyInvalidation` (`packages/db-p2p/src/dispute/invalidation.ts`): the compensating writes.

Verified at planning time: no other `src` code writes through `IRawStorage` or `IBlockStorage` (grep of the save/delete/promote/saveReplica/saveDeletion call sites). The one write outside a group is the read-path re-cache in `BlockStorage.materializeBlock`, which needs no flush (it can be recomputed) and becomes durable with the next group's flush.

## `StorageRepo` holds its store

`StorageRepo` today takes only a factory `(blockId) => IBlockStorage` and never sees the raw storage. Decided shape (chosen over a second positional flush argument because it also removes the chance of the factory and the flushed store being different stores):

```ts
export type StorageRepoOptions = {
	/** Builds the per-block storage over THIS repo's store. Default: `new BlockStorage(blockId, storage)`. */
	createBlockStorage?: (blockId: BlockId, storage: IRawStorage) => IBlockStorage;
	validatePend?: PendValidationHook;
	unvalidatablePendPolicy?: UnvalidatablePendPolicy;
};

constructor(private readonly storage: IRawStorage, options?: StorageRepoOptions)
```

`storage-repo.ts` then imports `BlockStorage` for the default (no cycle: `block-storage.ts` does not import `storage-repo.ts`). The private field becomes `(blockId) => factory(blockId, storage)` so the body is unchanged.

Call sites (about 108, nearly all tests; `yarn build` compiles `test/` and flags every one, since a function is not an `IRawStorage`):

- `new StorageRepo((id) => new BlockStorage(id, raw))` → `new StorageRepo(raw)`.
- With extra `BlockStorage` arguments (restore callback, checkpoint interval) → `new StorageRepo(raw, { createBlockStorage: (id, s) => new BlockStorage(id, s, restoreCallback) })`.
- With options → fold them into the same object.
- A test whose factory returns a double ignoring the store passes `new MemoryRawStorage()` as `storage`.
- A small node script with parenthesis matching does the bulk; review its diff, then `yarn build` from root until clean.
- Production: `createLibp2pNodeBase` (`packages/db-p2p/src/libp2p-node-base.ts`), the two harnesses (`mesh-harness.ts`, `reactivity-mesh-harness.ts`), the conformance suite, and the two in `CollectionFactory` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`).
- In `createLibp2pNodeBase`, delete the `(storageRepo as any).createBlockStorage = …` replacement ("this is a bit hacky" comment) and assign `restoreCallback = newRestoreCallback` instead: the factory closure reads the `let restoreCallback` binding at call time, and nothing else reads that binding (checked).

## Who calls flush, and when

**One helper in `StorageRepo`**, used by every group:

```ts
/** Run one write group's latched work, then make it durable before the caller reports or emits. */
private async endGroup<T>(work: () => Promise<T>): Promise<T>
```

- Awaits `work()` (which acquires and releases its own latches), then `await this.storage.flush()`, then returns.
- If `work()` throws, it still flushes (whatever landed before the fault must be durable before anyone acts on the failure), then rethrows the original error. If that flush also rejects, log the flush error on the repo's logger and rethrow the original.
- If `work()` returned and the flush rejects, the flush error propagates: the method throws and emits nothing. For `commit` that is the path a raw-storage error already takes through `ClusterMember.applyConsensusOperation` (propagate, roll back the executed marker, retry); the store refuses later writes until reopened (rule 5 of the contract), so a retry cannot report success over writes that may be gone.

Applied as:

- **`commit`**: move the body from `acquireBlockWriteLatches` through the `finally { release() }` into a private method returning `{ result, collectionBlocks }` — including the early `return` inside the try ("Return directly, locks will be released in finally") and the `success:false`-with-landings exit. `commit` = `endGroup(that)`, then `emitCollectionChanges(...)`, then return. So change events fire only after the flush: nothing announces a commit this node could still lose.
- **`pend`**, **`cancel`**, **`recoverBlock`**: wrap the whole latched body. Flush on every exit, including refusals that wrote nothing — an extra flush is latency only, a missed one is a durability bug, and these are not the hot read path.
- **`saveReplicatedBlock`**: same, with its `emitCollectionChanges` after the flush.
- **`get`**: the hot read path, so flush **only when the call entered a write latch** (the promotion block or the restore). Set a per-call flag inside each `withBlockWriteLatch` callback; after the parallel per-block work, `if (wrote) await this.storage.flush()`, then `emitPromotions`, then `answerLineage` as today.
- Exactly one flush per call; never inside a latch. Releasing the latches first means a concurrent group on the same blocks is not held behind the disk and several groups can share one sync.

**`applyInvalidation`**: `InvalidationContext` gains a required `readonly flush: () => Promise<void>`. Call it after the `finally { release() }` and before `ctx.log.addInvalidation(...)`, so the compensating revisions are durable before the entry naming them is written (the direction the existing crash-window `NOTE:` there calls recoverable) and before the result is reported. Add the same field to the cascade environment types in `packages/db-p2p/src/dispute/cascade.ts` and thread it to its `applyInvalidation` call; tests in `cascade.spec.ts` and `invalidation.spec.ts` pass their raw storage's `flush`. Not wired in production yet (dispute is off and has no composition root), so this is the contract for when it is.

**`KvUnderReplicationLedger`** (`packages/db-p2p/src/repo/kv-under-replication-ledger.ts`): after any public call that wrote to the KV store (`record` including its eviction, `settle` when it removed, `satisfy` when it changed or deleted, `name`, `noteAttempt`, `delete`), `await this.kv.flush?.()`. `CoordinatorRepo.noteReplicationShortfall` records the shortfall before it answers the writer, and the ledger exists so that record outlives a restart; `UnderReplicationDrain`'s writes go through the same methods, so the ledger never reports a peer satisfied that a restart forgets.

**Not touched**: `PersistentTransactionStateStore` (only wired when a host passes `NodeOptions.transactionStateStore`) writes fire-and-forget and promises nothing before it replies.

## Orderings crash recovery relies on

Write these into `packages/db-p2p/docs/storage.md` under invariant 6 (added by `raw-storage-can-be-flushed`) as the list every backend's flush is reviewed against. Today each holds because every step is synced before the next starts; after this seam the prefix rule holds them.

1. **Claim before record.** `BlockStorage.savePendingTransaction` writes the slot and base the record claims into the block's metadata before the pending record itself, so a crash between them leaves an inert claim and never a claim-less record, which every reader treats as the strongest reservation (`isReservationAgainst` in `packages/db-p2p/src/storage/pending-claim.ts`).
2. **One block's commit, in order** (`StorageRepo.internalCommit`): materialized block, revision record, promote, `setLatest`, proof, prune of the prior materialization. `latest` is never on disk naming a revision whose record or transform is not; the prune is never on disk without the new materialization and `setLatest`. The only partial states the retry path heals are revision-saved-not-promoted (Crash-D2) and promoted-with-`setLatest`-lost (Crash-D3, healed by `BlockStorage.recover` from `StorageRepo.commit`).
3. **Promote is one atomic move** (Invariant P in `docs/repository.md`).
4. **Log tail first** (`tailFirst` in `storage-repo.ts`): a member holding a committed non-tail block of an action also holds the action's committed log tail.
5. **Forward writes** (`BlockStorage.saveForwardRevision`): revision record, transform, materialization and proof before the metadata that advances `latest`, and the same action's pending record deleted no later than that metadata.
6. **Coverage restore** (`BlockStorage.restoreRevision`): the restored records before the `ranges` entry that claims them.
7. **Delete before the claim is dropped** (`BlockStorage.deletePendingTransaction`, `refuseMissingBase`, `dropUnpromotablePendings`).
8. **Across stores:** the durable executed marker (`markExecuted` in `ClusterMember.handleConsensus`) after the apply it describes, and the under-replication entry after the commit it describes. Two stores are two durability domains; these hold because `StorageRepo` flushes before it returns and the second write is issued afterwards.

Note beside 3 and 7 that the file backend does not guarantee them today (bare rename and unlinks, not directory-synced, while the metadata write after them is) and that `file-storage-pays-one-fsync-per-write-group` closes it.

Also in storage.md, under invariant 6: who calls flush (the list above), and the accepted property **visible before durable** — between a write resolving and its group's flush, readers in this process, and through them other machines, can see it. What a read can expose is consensus-decided content or a pending record, and what a crash takes back is always a later suffix: a vote built on a record's absence stays valid when the record is lost, and one built on its presence was a refusal. Under `### 1. Storage Repository (StorageRepo)`, one line on the constructor taking the store and ending each write group with one flush.

## Edge cases & interactions

- **Concurrent groups on one block.** Latches are released before the flush, so a second group can read the first's writes before they are durable and build on them. Safe under the prefix rule (the second group's writes are later, so they cannot survive without the first's), and it is what lets one sync serve several groups. Inspection.
- **Failed commit after partial landing** (blocks 1..N-1 landed, block N faulted; Option A emits for the landed ones): flushed before the emit. Inspection of the restructured `commit`.
- **Missing-pend throw after `dropUnpromotablePendings`**: `work()` throws after writing; `endGroup` flushes then rethrows. Inspection.
- **Flush rejects**: method throws, no events emitted; on a throwing `work()` the original error wins and the flush error is logged. Inspection (no backend can reject a flush in this ticket; the file backend's ticket tests its failed-sync state).
- **`get` with no context, or a context with nothing ahead**: takes no latch, so no flush — the hot read path is unchanged. Inspection.
- **`get` racing a commit on the same block**: each flushes its own group; the prefix rule orders them. Inspection.
- **Read-path re-cache** in `BlockStorage.materializeBlock`: written outside any group, no flush, becomes durable with the next group's. Inspection.
- **Change events** (`emitCollectionChanges`, `emitPromotions`, and the cohort-topic origination bridge that hangs off them) fire after the flush, so nothing announces a commit this node could still lose. Inspection.
- **Test doubles of `IBlockStorage`** passed through `createBlockStorage`: the repo still flushes `storage`, which for them is a `MemoryRawStorage` — harmless.
- **Restore callback swap** in `createLibp2pNodeBase`: replaced by reassigning the closed-over `let`; verify a block storage created after node start uses the restoration coordinator (existing restore/reconcile tests on the mesh cover it).
- **Ledger with an `IKVStore` that has no `flush`**: optional call, no-op. Inspection.
- **No new tests.** Who calls flush is wiring, checked by review against this list; the contract test is the conformance case from `raw-storage-can-be-flushed`. The existing StorageRepo, cluster, mesh and dispute suites must stay green unchanged apart from construction.
