# Why

The prerequisite ticket makes a machine write down, durably, which partners are missing a copy of a block it acknowledged. Nothing sends those copies. Today the only thing that ever gives a second copy to a block written while alone is the rebalance monitor's growth arm, which fires on a topology change rather than on a known shortfall and whose memory of what it has already pushed is lost on restart.

This ticket drains the ledger: when a machine that is missing a block becomes reachable, push the block to it, and clear the entry once it confirms. And when a block's last shortfall clears, say so, so a host can move a change from "pending" to "saved".

Once this lands, sereus's row-level re-issue queue and its whole-store push on peer join are redundant *for blocks* — including the collection-header and index blocks its own notes say the row-level queue misses. They can stay as belt-and-braces until someone measures that they are no longer earning their keep; this ticket does not remove them.

# The drain

A new `UnderReplicationDrain` in `packages/db-p2p/src/repo/`, a `Startable` alongside the other resilience monitors.

**What wakes it:**

- **Start.** One pass over everything the ledger survived a restart with. This is the case in-memory commit retry has never covered.
- **A peer connecting.** Subscribe to the libp2p connection-open event, the same signal `RebalanceMonitor` and `SpreadOnChurnMonitor` already use. Debounce it, and re-use the same minimum-interval throttle shape those monitors have, so a flapping peer cannot turn into a push storm.
- **A periodic re-check** while any entry is outstanding, so a failed push on an otherwise quiet network is eventually retried. Armed only while work is outstanding, exactly as `RebalanceMonitor.growthRecheckIntervalMs` is.

**What one pass does**, per ledger entry:

1. Work out who is owed a copy.
   - `missingPeerIds` non-empty → those peers, minus any currently abandoned for this block.
   - `missingPeerIds` empty (the entry was recorded `local` or `unrouted`, so the cohort could not be named) → re-resolve the block's cohort now through `IKeyNetwork.findCluster` and take every member that is not this node. **If the cohort still resolves to this node alone, that is not a failure** — the node is legitimately still by itself. Leave the entry untouched and do **not** bump its give-up counter, or a genuinely solo node burns through its budget and stops trying.
2. Skip any peer that is not currently connected. The drain pushes to reachable peers; it does not dial the world.
3. Read the block from local storage, build its certification, and push. A receiver running the default certified-push policy rejects an uncertified block, so a block this node holds no proof for simply fails to place — logged, not retried forever.
4. A peer whose response does not list the block as missing has confirmed it: `satisfy(blockId, [peerId])`.
5. When the entry's missing set empties, the ledger deletes it and the drain emits the full-replication event below.
6. A round in which at least one owed peer was reachable and did not confirm calls `noteAttempt`. After the configured number of consecutive unsuccessful rounds, that peer is **abandoned for that block** — excluded from further pushes — until it reconnects, which clears its abandonment. This mirrors `RebalanceMonitor`'s `growthMaxAttempts` and its rule that a peer leaving and rejoining is retried from scratch. An entry never silently disappears because of abandonment: it stays in the ledger, visible.

Bound the work per pass by a block budget, as the rebalance monitor does. A block dropped by the budget is not recorded as satisfied and is re-detected on the next pass.

## Do not write a fourth copy of the push loop

The sequence "read the block from local storage, build its certification, push it to a peer, treat a response that lists the block as missing as a failure" exists **three** times already: `BlockTransferCoordinator.executePush`, `BlockTransferCoordinator.executeConfirm`, and the spread loop in `SpreadOnChurnMonitor`. Adding a fourth is the wrong move, and it is the reason this is called out here rather than left to taste.

Extract a helper next to `sourceBlockCertification` in `cluster/block-transfer-service.ts` — something like `pushBlockToPeers(repo, peerNetwork, blockId, peerIds, reason, options)` returning which peers confirmed — and have the drain use it. Convert `executePush` and `executeConfirm` to it if they fall out cleanly; where a copy carries its own timeout or diagnostic policy that does not fit (the spread loop has per-target dial and response deadlines), leave it and add a `NOTE:` naming the helper and saying why. Converging whatever is left over is `backlog/debt-three-sites-repeat-the-certified-push-loop`, which already records the three existing copies — update it with what this ticket converted rather than growing this ticket to finish it.

# The full-replication event

The local change notifier is the right seam: a host already subscribes to `StorageRepo.onCollectionChange` / `onAnyCollectionChange` for commits, and a second, unrelated subscription point for "and now it is really saved" would be a trap.

In `packages/db-core/src/transactor/change-notifier.ts`:

```ts
/** One or more blocks reached FULL replication — every member of their cohort is now confirmed to
 *  hold the revision. The complement of the durability class on the write's own result: a write
 *  acknowledged below `full` is pending until these events cover its blocks. */
export type BlockDurabilityReachedEvent = {
	/** Blocks that reached full replication in this round. */
	readonly blockIds: readonly BlockId[];
	readonly rev: number;
	/** The action whose recorded shortfall cleared. */
	readonly actionId: ActionId;
	/** Best-effort; absent when the collection could not be resolved from the block's header. */
	readonly collectionId?: CollectionId;
};

export interface IBlockDurabilityNotifier {
	/** Subscribe to full-replication events. Returns an idempotent unsubscribe. Same listener
	 *  discipline as `onCollectionChange`: a throwing listener is logged and the rest still run. */
	onBlockDurabilityReached(listener: (e: BlockDurabilityReachedEvent) => void): () => void;
}
```

`StorageRepo` implements it, so one object carries both kinds of change event. The drain does not own listeners: it holds a narrow sink the node hands it, exactly as the cluster side receives a `CommitCertificateSink` today. Keep the sink one method wide so the drain has no way to reach anything else on the storage repo.

**How a host uses it.** The write's result names its blocks (`PendSuccess.blockIds`, threaded through the commit). A host that wants to show a change as pending holds those block ids until these events cover them. It is deliberately block-keyed rather than action-keyed, because the ledger is keyed by block: a block written again by a *later* action replaces the earlier entry, so the earlier action's shortfall is cleared by the later action's event and would never fire an event of its own. Say this plainly in the type's doc comment — a host that keys pending state by action alone will wait forever for a superseded write.

# Edge cases & interactions

- **Restart between acknowledgement and drain.** The headline case. Entries written before a restart must be drained after one. This is what the memory fallback for the key-value store cannot do, and why the prerequisite ticket makes that fallback warn.
- **A node that is genuinely alone.** Cohort re-resolves to itself; nothing is owed; no attempt is counted; the entry waits. A solo deployment must not accumulate give-up counters or log churn.
- **The missing peer never returns.** Its entries stay, its abandonment holds, and the ledger's size cap is the backstop. Nothing here deletes an entry to tidy up.
- **The missing peer returns but has since left the cohort.** The push still lands (the receiver decides whether to keep it under its own policy) and the entry clears. Re-resolving the cohort for a named missing peer is deliberately *not* done: the named peer was a cohort member when the write was acknowledged, and a copy there is not harmful.
- **The block is gone from local storage.** Nothing to push. Treat exactly as `SpreadOnChurnMonitor` treats it — log, and delete the ledger entry, because a block this node no longer holds is not one it can owe.
- **No retained proof for the revision.** A receiver running the default certified-push policy refuses it. Log it distinctly from a transport failure so an operator can tell "cannot place" from "cannot reach", and count it as an attempt so the give-up budget applies.
- **Racing the rebalance growth arm and spread-on-churn.** All three may push the same block to the same peer. A push is idempotent at the receiver, so the cost is duplicate work, not incorrectness. Do not add cross-monitor coordination for it; note the overlap where the drain is wired.
- **A push landing mid-commit.** The receiver's own push handling already decides whether to accept a revision; the drain adds no new ordering guarantee and must not assume one.
- **Partition.** Follow the neighbouring monitors and honour the partition detector's suppression, so a partitioned node does not push into a minority view.
- **Event ordering.** The full-replication event fires after the ledger entry is deleted, never before, so a listener that re-reads the ledger sees a consistent picture.
- **Listener faults.** A throwing listener must not break the drain or the other listeners, matching `StorageRepo.fireChangeListeners`.
- **Scanning the ledger.** A pass reads every entry. Bounded by the node's owned-block count today. `NOTE:` it at the scan site: if a node ever holds so many under-replicated blocks that the scan shows up, index the ledger by missing peer instead of scanning.

# Tests

Unit, with a fake ledger, a fake key network and a push double:

- An entry naming one missing peer that is connected: the drain pushes once, the peer confirms, the entry is deleted, and one full-replication event fires naming the block.
- The same entry with the peer not connected: nothing is pushed and the entry is untouched.
- An entry with an empty missing set whose cohort re-resolves to this node alone: nothing pushed, no attempt counted, entry untouched.
- An entry with an empty missing set whose cohort re-resolves to two peers: both are pushed, and the entry clears only when both confirm.
- A peer that fails the configured number of consecutive rounds is abandoned and no longer pushed, and reconnecting clears the abandonment.
- A block absent from local storage has its entry deleted.
- A throwing listener does not stop the second listener or the drain.

Integration — `packages/db-p2p/test/small-deployment-lifecycle.integration.spec.ts`, phase 5. Today it asserts only that the returning machine can *read* the row, because nothing pushes a missed write to a returning member. Add, on the branch where the away-write was acknowledged:

- after the partner returns and the drain has run, the partner's **own storage** holds the row's blocks — use the existing `committedBlocks` helper, which reads one machine's storage directly rather than going through a read that could repair;
- the survivor's ledger is empty for those blocks.

Both under the existing `waitFor` shape, since the drain is asynchronous. Keep the phase's conditional structure: it still does not assert whether the away-write was accepted.

Also add a restart case — either as a seventh lifecycle phase or as its own integration spec: write with the partner away, **restart the survivor**, bring the partner back, and assert the blocks reach the partner's storage. That is the case no in-memory mechanism has ever covered and the one thing the durable ledger buys.

# Ledger interface as landed (from the prerequisite)

The prerequisite shipped `IUnderReplicationLedger` with two differences from the sketch this ticket was written against — read `packages/db-p2p/src/repo/i-under-replication-ledger.ts` before building on it:

- **`settle(blockId, rev)`** was added. It is what a `full` commit calls: it deletes the entry unless the entry records a higher revision. Use it rather than `delete` wherever "this revision is now everywhere" is the fact being recorded.
- **`satisfy` on an entry whose missing set is unknown (empty — recorded `local` or `unrouted`) returns it unchanged.** Removing named peers from an unknown set cannot prove it empty. For the "empty set, cohort re-resolves to two peers, entry clears only when both confirm" case, first name the set by calling `record` again at the entry's own `rev` with the re-resolved peers (a same-revision record replaces `quorum`/`missingPeerIds` and keeps `attempts` and `recordedAt`), then `satisfy` peer by peer.
