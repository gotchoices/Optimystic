# Matchmaking cannot register on a small network

Reported as GitHub #67 (VoteTorrent, 1.24 and 1.27.0): `MatchmakingProviderSession.register` on networks of 1, 2 and 3 hosts with `cohortTopic.enabled` throws `CohortBackoffError` ("no willing primary right now") on every retry.

## What refuses it (reproduced)

Reproduced on real libp2p nodes, default configuration (`cohortTopic: { enabled: true }`, so `wantK = 16`, `minSigs = 14`), 1-node and 3-node meshes, calling `node.cohortTopicHost.service.register({ topicId, tier: T2 })` three times with a pause between. Every frame the walk sent through `FretTopicRouter.routeAndAct`, and its reply:

```
N=1  treeTier 0                  -> no_state
     treeTier 0, bootstrap:true  -> unwilling_cohort retryAfterMs 1000
     treeTier 0 (retries)        -> unwilling_cohort retryAfterMs 1000
N=3  treeTier 0                  -> no_state   (x2)
     treeTier 0, bootstrap:true  -> unwilling_cohort retryAfterMs 1000   (x2)
     treeTier 0 (retries)        -> unwilling_cohort retryAfterMs 1000
```

So the cold start itself succeeds — the bootstrap evidence passes and the forwarder is instantiated (later registers get `unwilling_cohort`, not `no_state`) — and the register is then declined by the **admission quorum** in `GossipWillingnessCheck.evaluate` (`packages/db-core/src/cohort-topic/willingness.ts`). The coord engine builds that check with `config: { cohortSize: ctx.wantK }` for every FRET cohort (`createWillingnessCheck` call in `packages/db-p2p/src/cohort-topic/host.ts`), so the quorum is `defaultQuorum(16) = 9`. A 1–3 node network's cohort has 1–3 members, so at most 3 can be willing. Because `willing + unheard` (at most 3) is also below 9, `awaitingMembers` is false and the cold-start quorum wait never opens either: the decline is immediate and permanent.

Control runs on the same meshes:

- `wantK = N` with `minSigs` left at 14 → accepted on the bootstrap register, at N=1 and N=3. So `minSigs` plays no part in the refusal; the reporter's reading (14 of 16 threshold signers) is not the mechanism. As the fix ticket suspected, nothing on the register path threshold-signs the reply.
- `wantK = N`, `minSigs = N` → accepted, same.

The existing real-socket suite (`packages/db-p2p/test/substrate-real-libp2p.integration.spec.ts`) sets `wantK = N` for exactly this reason, which is why no suite caught it at default configuration.

## The fix

The admission quorum is a capacity gate the routed member decides alone from gossip — `docs/cohort-topic.md` §Admission quorum says so and keeps it deliberately separate from the signing threshold — so it is not a security floor, and having it follow the real cohort needs no maintainer decision. Root placement already does this: a root-placed topic's quorum is a majority of its root group's size, which is why reactivity works on small groups.

Rule: **the admission quorum is a strict majority of the cohort the check serves, as it is now** — `⌊m/2⌋ + 1` where `m` is the number of members in the engine's current cohort snapshot (`cohort().members`, self included; count self once if the snapshot ever omits it). On a network of at least `wantK` serving peers `m = wantK` and nothing changes. On 1 node: quorum 1, self-willing → accepted on the bootstrap register. On 2: quorum 2 — self plus the one sibling, which the existing cold-start quorum wait (`awaitingMembers`, willingness advert) collects. On 3: quorum 2.

Read the size per evaluation, not once at engine creation: a FRET cohort on a growing network gains members while its engine lives, and a quorum frozen at the creation-time size would stay at 1 after the network grows. The same live read fits a root-placed engine (`cohort()` returns the root view there), and removes the "read once … merely permissive for a group still filling" caveat in the host comment — one rule for both placements. `WillingnessDeps.cohortMembers` already supplies the live member list; `WillingnessConfig.quorum` stays as the explicit override. Whether to express this as a live `cohortSize` source or by deriving from `cohortMembers` is the implementer's call; keep `defaultQuorum` as the one majority rule.

Accepted consequence, to state in the doc: a transiently shrunken cohort view (a peer mid-identify, which `assembleCohort` leaves out) lowers the quorum for that moment. That is the cost of a capacity gate following the cohort, the same one root placement already pays, and it cannot admit anything a smaller honest network would not.

## Adjacent risk to watch while testing

On a small network the FRET cohort is also below `minSigs = 14`, so anything that needs a cohort threshold signature — membership certificates, promotion and demotion notices, child links — cannot be produced there. None of those is on the first-register path (verified above), and the design expects a small network never to promote. The seeker side (brief T2 register, then a `QueryV1` answered under a single member's signature) should also not need one, but it was not run. If the end-to-end test below finds a step that refuses for want of threshold signers, that is the signing threshold, which `docs/cohort-topic.md` treats as a safety bound: route it to `blocked/` with a proposed rule (e.g. the root-placement ratio rule `ceil(m × ratio)` for a FRET cohort smaller than `wantK`) rather than lowering it here.
