# Blob bytes are reported by hold, and the cache gets a share

## Why

After `a-node-measures-its-use-against-one-allotment`, a node knows one number for how full it is. Two things are still missing from what that ticket's parent asked for:

- **Nothing says what the bytes are.** An operator sees "38 of 50 GB" and cannot tell whether that is blocks the node is responsible for, blobs its own application pinned, or files it read once and never looked at again. Those three deserve completely different reactions, and the third is the one that can be given up for free.
- **The read cache ignores the allotment.** `BlobCacheBudget` is sized by `NodeOptions.blobs.cacheBudgetBytes`, 256 MiB by default (`DEFAULT_BLOB_CACHE_BUDGET_BYTES`), a flat figure unrelated to the node's disk. A node given 500 MB keeps spending 256 MB of it on blobs nobody asked it to keep; a node given 500 GB keeps spending only 256 MB. And the figure is read once at construction, so an allotment the operator lowers is not seen until a restart.

## What to build

### 1. Blob bytes attributed to the hold that keeps them

A new door on `LocalBlobService`, in the shape of its siblings (`BlobCacheRecords`, `BlobResponsibleRecords`, `BlobReclaimRecords`) and for the reason each of those states — a door rather than a second `BlobRecordStore` over the same `IKVStore`:

```ts
/** What one hold kind accounts for, over the blobs this node has records for. */
export interface HoldBytes {
	/** The sum of `BlobRecord.size` over the blobs attributed to this hold. */
	readonly bytes: number;
	/** How many of those blobs carry no size, and so are left out of `bytes`. */
	readonly unsized: number;
}

export interface BlobByteRecords {
	/**
	 * One pass over every readable record, attributing each blob to the ONE hold that keeps it, by
	 * precedence `pin > owed > responsible > cached`.
	 */
	bytesByHold(): Promise<Readonly<Record<BlobHoldKind, HoldBytes>>>;
}
```

Three rules to state on it, each with its reason:

- **One blob, one hold.** A blob carrying both `responsible` and `cached` — the ordinary state of a blob pulled for an announcement (docs/blobs.md §Holds) — is counted once, under `responsible`. The precedence is strongest reason first: a pin is the application's and is never evicted, an owed blob is one no other machine holds yet, a responsible blob is the node's job, and `cached` is the only hold anything gives up. So the `cached` figure is exactly the bytes the cache budget can actually free, which is what makes it worth reporting.
- **It is an attribution, not a measurement, and it over-counts.** Pieces are shared between blobs, so a piece in two blobs' trees counts in both; and a blob counts at its full size whether or not every piece is here. Both are the direction docs/blobs.md §Lifetime already takes for the cache budget, and the safe one. It therefore does not reconcile with the piece store's own figure, and must not be presented as if it did.
- **An unreadable record is logged and skipped,** as `responsibleRefs` and `cachedBlobs` do, so one bad record cannot fail a report.

The pass is `readableRecords` — one `IKVStore.get` per record. The `NOTE:` already on `readableRecords` names the tripwire for all four of its callers; add this one to its list rather than writing a new tripwire.

### 2. The breakdown on the account

```ts
export interface StorageBreakdown {
	readonly capacity: StorageCapacity;
	/** The piece store's own figure, whether or not it was added to `capacity.usedBytes`. */
	readonly pieceBytes?: number;
	/**
	 * The blocks and the node's bookkeeping together: the measured use less `pieceBytes`. Absent when
	 * either is unknown.
	 */
	readonly blocksAndBookkeepingBytes?: number;
	/** The attribution above; absent when the node has no blob records to read. */
	readonly blobBytesByHold?: Readonly<Record<BlobHoldKind, HoldBytes>>;
}

export class StorageAccount {
	/** Everything `capacity()` reports, plus what the bytes are. */
	breakdown(): Promise<StorageBreakdown>;
}
```

The account takes the record source as a **thunk** — `blobRecords?: () => BlobByteRecords | undefined` in its options — because the node builds its blob service after the account; no setter and no mutation. `breakdown()` leaves `blobBytesByHold` absent when the thunk answers nothing, and says so rather than reporting four zeros.

State the cost on the method: everything `capacity()` costs (memoized) plus one pass over every blob record, **not** memoized and on no timer. Nothing on a hot path calls it; it is for an operator's dashboard and for `logRingInfo` in reference-peer.

**Blocks and bookkeeping come as one figure.** No shipping backend separates them cheaply: the filesystem backend sizes the whole base directory in one walk, SQLite multiplies `page_count` by `page_size` over the whole file, LevelDB sums entries by key range, and IndexedDB reads an origin-wide `navigator.storage.estimate().usage` that cannot be split at all. Park the tripwire as a `NOTE:` on the field: three of the four could do it with a second scan (the filesystem by classifying paths, SQLite by summing per table, LevelDB by summing per tag range) and the web backend could not; build it if an operator ever asks to see blocks apart from bookkeeping.

### 3. The cache's share of the allotment

One pure function, exported from the account's module so the rule is readable in one place:

```ts
/**
 * What the blobs held only for reads may take: the host's cap, the share of the allotment, and what
 * the allotment leaves after everything else, whichever is smallest, floored at 0.
 */
export function cacheBudgetBytes(args: {
	/** `NodeOptions.blobs.cacheBudgetBytes`, already defaulted to `DEFAULT_BLOB_CACHE_BUDGET_BYTES`. */
	declaredBytes: number;
	capacity: StorageCapacity;
	/** What the cache currently accounts for, from the caller's own pass. */
	cachedBytes: number;
}): number;
```

The rule:

```
min( declaredBytes,
     totalBytes * CACHE_ALLOTMENT_SHARE,
     totalBytes - (usedBytes - cachedBytes) )     // what is left after everything else
```

floored at 0, and with an **unknown `totalBytes` answering `declaredBytes`** — a node that cannot measure its storage keeps today's flat budget exactly, which is the only honest answer and keeps every memory-storage spec where it is.

`CACHE_ALLOTMENT_SHARE = 1 / 8`, and the reason has to go in the code beside it:

- 256 MiB is today's default and the figure the design chose for a phone. 256 MiB at one eighth is a 2 GiB allotment, so **the share only ever lowers the budget on an allotment below 2 GiB** — a host smaller than the phone the default was written for. Every larger allotment keeps the host's own figure, so no existing deployment's cache shrinks.
- One eighth cannot move a ring on its own. The outward transition fires above 85 % use (`RingSelectorConfig.thresholds.moveOut`), and 12.5 % of the allotment spent on blobs nobody asked the node to keep cannot reach it. A share large enough to approach that threshold would have the node shedding responsibility to protect a read cache, which inverts what the two are for.

The third term is what makes cached blobs come out of the allotment rather than sit beside it: a node whose other use fills the allotment gets a budget of 0 and evicts every cache-only blob. `cachedBytes` comes from the caller rather than being measured here, so the term costs no extra scan — the budget's own pass already has the figure.

### 4. A budget the cache asks for each run

`BlobCacheBudgetDeps.budgetBytes` becomes `() => Promise<number>` instead of a number, asked once per `runOnce`, so an allotment that changed — or other use that grew — is seen without a restart. The node passes a thunk over the account and the declared cap.

`chooseEvictions` stays pure and keeps taking a number. Lift its sized sum out so it is computed once rather than twice: export `sizedCacheBytes(blobs)` from `cache-budget.ts`, have `runOnce` call it, ask for the budget with that figure, and pass both into `chooseEvictions(blobs, cachedBytes, budgetBytes, inUse)`.

### 5. Docs

- `docs/blobs.md` §Lifetime (the *Cached blobs are evicted under a budget* bullet) and §Holds' `cached` row: the budget is now the smallest of the host's cap, an eighth of the node's allotment, and what the allotment leaves after everything else; it is asked for on every enforcement; and a node that cannot measure its storage keeps the flat figure.
- `NodeOptions.blobs.cacheBudgetBytes`'s doc comment in `libp2p-node-base.ts`: it is a **cap**, not the figure.
- `packages/db-p2p/docs/storage.md` §9: the breakdown, what each figure is, that the blob attribution over-counts and does not reconcile with the piece figure, what it costs, and that the cache is a tenant of the allotment.

## Edge cases & interactions

- **A blob with several holds** is counted once, under the strongest. Pinned by a test below, because an attribution that double-counted would report more held than the node stores.
- **A record carrying no `size`** is counted in `unsized` and left out of `bytes`, so a report never silently treats an unknown cost as zero — the same distinction `CachedBlob.bytes` already draws, and for the same reason. The cache budget's own treatment of an unsized blob (evict it on its own account) is unchanged.
- **`cachedBytes` and the budget are from one moment.** `runOnce` computes the sum, asks for the budget, then chooses — all after one `cachedBlobs()` read, so the leftover term and the eviction decision see the same cache. A write that lands between them is the pre-existing window the budget's single-flight-with-one-queued-follow-on already covers.
- **The leftover term can go negative** (used already exceeds the total). Floored at 0, which evicts every cache-only blob that is not in use — the right answer for a node over its allotment, and the furthest this chain goes; refusing new data is `a-node-stays-within-its-allotment`.
- **`usedBytes` includes the cached blobs' own bytes**, which is why the term subtracts `cachedBytes` before comparing. Getting that subtraction wrong would make the budget shrink itself toward 0 on every pass; it is in the test below.
- **The memoized used figure may lag the cache by up to the 60-second TTL**, so an enforcement just after a large fetch may compute its leftover from a `usedBytes` that predates the fetch, giving the cache slightly too much for one window. Acceptable for the same reason ring selection's staleness is: the next enforcement corrects it, and the error is bounded by one TTL of fetching. State it; do not add a cache invalidation hook.
- **A client node** has an account, a cache budget and blob records, and no block store use to speak of. Its breakdown is almost all blob bytes, which is correct.
- **No blob service yet.** The thunk answers nothing until the node has built one; `breakdown()` must not throw, and the budget thunk is only ever called by a budget the blob service owns, so it cannot be asked before then.
- **`blob-cache-budget.spec.ts` builds the budget directly** and will need the thunk; its existing cases pin the eviction rules, not the sizing, and must keep passing unchanged apart from that one argument.

## Tests

Three, each a rule with real branching:

- **`cacheBudgetBytes` over its four arms** — the declared cap wins, the share wins, the leftover wins, and an unknown total falls back to the declared cap — one table-driven case over the pure function. This is the whole of the new policy.
- **The leftover term subtracts the cache's own bytes** — one case: a node whose use is entirely cache gets the full share, not 0. The sign error this catches would quietly disable the cache on every node.
- **`bytesByHold` counts a blob with two holds once, under the stronger** — in `blob-cache-budget.spec.ts`'s neighbourhood over a real `LocalBlobService`, as its existing cases run; a `responsible` + `cached` blob appears only in `responsible`.

No test for the breakdown's assembly (arithmetic over figures the account already reports, each already pinned), the thunk plumbing (`tsc`), or the doc wording.
