# Commit content digest — part 3 of 3: member-side check

Split from `commit-cert-bind-block-content-digest`. Parts 1–2 landed the digest primitives and the
client-side declaration on the wire. This part makes signatures MEAN something: a member materializes
the block locally on the promise round and rejects the commit record on mismatch. Nothing verifies or
persists a durable proof yet — that is `persist-block-commit-proof` (later work).

## Why the check is shaped this way (settled during investigation — do not re-derive)

`StorageRepo.commit` accepts a commit whenever `latest.rev < request.rev`
(`storage-repo.ts:589-610`), not only `latest.rev === request.rev - 1`, so a lagging member applying
an update-only transform to an older base legitimately materializes different bytes. Hence the
checkable/abstain rule, keyed on the member's OWN pended transform (the same payload the client
authored, delivered at pend):

| Member's pended transform for the id | Member behaviour |
|---|---|
| carries an `insert` (with or without updates) | base-independent — **always check**; digest mismatch → reject |
| `updates` only | check **iff** local `latest?.rev === declared.baseRev`; otherwise abstain (approve as today) |
| `delete` only | materializes nothing; nothing to check |
| no pending transform for the action | member never saw the pend — abstain, do not reject |

"Abstain" = contribute no content attestation, vote exactly as today. Residual (state in a code
comment at the check site): a false digest requires the declarer to lie AND enough of the cohort to be
simultaneously unable to check that no honest checker is left; any single caught-up honest member
rejects. Strictly stronger than today, where commit signatures bind no content at all.

**The check must run on the PROMISE round, not the commit round.** The commit-round vote is cast
deliberately blind — `cluster-repo.ts:835-858` signs the commit whenever
`approvedPromises >= superMajority` regardless of this member's own promise vote. The promise-round
approvals are the only votes that carry "I checked this"; downstream verification depends on that. Do
not move it.

## Task 1: `StorageRepo.previewCommitDigest`

```ts
/** The digest the block WOULD materialize to if `actionId`'s pending transform committed at `rev`,
 *  plus the base revision it was computed from. Read-only: touches no durable state and takes no
 *  commit latch. */
previewCommitDigest(blockId: BlockId, actionId: ActionId, rev: number):
	Promise<{ digest?: string; baseRev?: number; baseIndependent: boolean } | undefined>
```

Implementation (mirrors `internalCommit`'s reads at `storage-repo.ts:854-921`):

- `storage.getPendingTransaction(actionId)` → `undefined` → return `undefined` (no pend seen).
- `baseIndependent = transform.insert !== undefined`. When base-independent, do NOT read a base at all.
- Otherwise `storage.getLatest()`; when present, `baseRev = latest.rev` and read the base via
  `storage.getBlock(latest.rev)` **in a try/catch** — `getBlock` throws when this node holds a
  `latest` it cannot materialize (see `readCommitBase` at `:947-965`); on throw return
  `{ baseIndependent: false, baseRev, digest: undefined }` (caller abstains — an unmaterializable
  base is not a content mismatch).
- Materialize with the canonical `applyTransform(structuredClone(base), structuredClone(transform))`
  (clone both — `applyTransform`/`applyOperations` mutate the block AND `transform.insert` in place).
- `digest = newBlock ? await canonicalBlockHash(newBlock) : undefined` — `undefined` covers the
  tombstone (delete transform) and updates-with-no-base (applyTransform drops updates with no base).
  `canonicalBlockHash` now lives in `@optimystic/db-core` (moved in part 1).
- `rev` is accepted for parity/logging; materialization does not depend on it (internalCommit only
  records it).

Do NOT take the per-block commit latch: this runs on the vote path, ahead of the commit that will take
it; taking it would serialize voting behind commits and risks deadlocking against commit's sorted
multi-block acquisition. Say so in a comment.

## Task 2: `ClusterMember.validateCommitOperations`

In `cluster-repo.ts`:

- Export `CONTENT_DIGEST_MISMATCH = 'content-digest-mismatch'` beside `MEMBERSHIP_NOT_ADMITTED`
  (`:141`). The reason rides in the reject vote's `rejectReason`, which
  `clusterVoteSigningPayload` already folds into the signed bytes.
- `evaluatePromise` (`:938-944`): after `validatePendOperations` returns valid, call and return
  `validateCommitOperations(record)`.
- `ClusterMember.storageRepo` is typed `IRepo` — probe `previewCommitDigest` duck-typed (the
  codebase's established pattern: `Tracker`'s `getGeneration` probe, `sourceReadRevision` in
  cache-source). A repo without the method → approve (abstain everywhere), which also keeps every
  existing `MockRepo`-based spec green.

Per `{ commit }` operation carrying `blockDigests`, per declared `[blockId, declared]` entry:

- `!commit.blockIds.includes(blockId)` → surplus/hostile entry: ignore, never throw out of the vote
  path.
- `previewCommitDigest(blockId, commit.actionId, commit.rev)` wrapped in try/catch — a throw is
  logged and treated as abstain.
- preview `undefined` (no pend seen) or `preview.digest === undefined` (tombstone / no base /
  unmaterializable base) → abstain.
- Checkable when `preview.baseIndependent` (always — ignore `declared.baseRev`; the member's own
  transform decides base-independence, so a hostile declarer cannot force or dodge a check by
  mis-declaring `baseRev`), OR `declared.baseRev !== undefined && preview.baseRev === declared.baseRev`.
  Not checkable → abstain.
- Checkable and `preview.digest !== declared.digest` → return
  `{ valid: false, reason: CONTENT_DIGEST_MISMATCH }` (one vote per record: one mismatch rejects the
  whole record).

An upgraded member receiving a commit with no `blockDigests` abstains everywhere (loop never runs).
A commit record's promise round previously validated nothing (`validatePendOperations` only inspects
`'pend' in operation`) — this is the hook the check fills.

## Edge cases to pin in tests

- Lagging member, update-only block (`latest.rev !== declared.baseRev`) → abstains, approves — the
  case that makes the scheme safe to turn on.
- Lagging member, insert-carrying block → checks and must agree (base-independent).
- Tombstone / delete-only → no digest declared, no check; also `internalCommit`'s absent-`newBlock`
  with prior `latest` tombstone branch (`storage-repo.ts:876-890`) still commits.
- Member with no pending transform for the action → abstains, never rejects.
- Surplus digest for an id not in `blockIds` → ignored.
- Mismatch on a base-independent block → reject with `CONTENT_DIGEST_MISMATCH` in the signed
  `rejectReason`.
- Single-peer fast path: `CoordinatorRepo.commit` short-circuits to `storageRepo.commit` when
  `peerCount <= 1` (`coordinator-repo.ts:1388-1393`) — no consensus, no check; confirm it commits
  cleanly with the field present.

## Tests

- db-p2p `previewCommitDigest` (harness: `storage-repo.spec.ts` — `MemoryRawStorage` +
  `BlockStorage`): digest matches what `internalCommit` actually stores (commit, then
  `canonicalBlockHash(getBlock(rev).block)`) for insert, update, and tombstone; `undefined` with no
  pending transform; `digest: undefined` + `baseRev` when the base is unmaterializable.
- db-p2p `validateCommitOperations` (harness: `cluster-membership-admission.spec.ts` —
  `clusterMember` factory + mock repo + `makeRecord`-style v1 record, drive via `member.update(record)`
  and read `record.promises[self]`): approve when abstaining (no digests, no pend, base-rev
  mismatch), reject on base-independent mismatch, ignore surplus ids. The mock repo implements
  `previewCommitDigest` directly for the unit cases; one heavier case can use a real `StorageRepo`
  seeded via `pend`.
