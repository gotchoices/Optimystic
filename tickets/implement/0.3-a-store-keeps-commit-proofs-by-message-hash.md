# A store keeps commit proofs by message hash

First half of GitHub #60 (a commit proof stored once per block it covers, so a bulk import grew a file store to 7 GB, 94% duplicate proofs). This ticket adds the storage; `a-commit-proof-is-stored-once-not-once-per-block` makes the kernel use it. The split exists because widening `StoreKey` and `RawStoreDriver` breaks every backend's build at once, so the new store has to land in every backend in one change, and that change is mechanical and separable from the retention logic.

## The new logical store

A seventh logical block-storage store, **commit proofs**, keyed by a `BlockCommitProof`'s `messageHash` (the base58btc consensus-message hash, `computeClusterMessageHash` in `packages/db-core/src/cluster/membership.ts`). Value: the encoded proof, exactly as the `proofs` store holds one today. Plain get/put, no delete — same reasoning as the `proofs` store's missing `deleteProof` (no revision-delete site exists). The doc comment says so and says the store is keyed by a hash a caller takes from the proof itself, which is only trustworthy because every proof reaching storage is locally built or verified (stated fully in the second ticket).

```ts
// RawStoreDriver<V>
getCommitProof(messageHash: string): Promise<V | undefined>;
putCommitProof(messageHash: string, value: V): Promise<void>;

// StoreKey (batch-backend.ts)
| { store: 'commitProofs'; messageHash: string }

// IRawStorage — raw access, used by RawStorageDriverAdapter; no logic
getCommitProof(messageHash: string): Promise<BlockCommitProof | undefined>;
saveCommitProof(messageHash: string, proof: BlockCommitProof): Promise<void>;
```

`KvRawStorage` implements the two `IRawStorage` methods as decode/encode over the driver, like `getBlockProof`/`saveBlockProof` today. `RawStorageDriverAdapter` maps the driver pair onto them (re-encoding across the byte boundary as its siblings do). `CachedStoreDriver` passes them through uncached, beside the `proofs` passthrough and under the same `NOTE:`. `WriteGroupDriver` routes them through the group like `proofs`.

## Per backend

- **Memory** (`MemoryStoreDriver`, `MemoryBatchBackend`, `MemoryJournalStore`, `TextReadsJournalStore`): one more map keyed by the hash.
- **File** (`FileBatchBackend`): a root directory `commit-proofs/` beside the block directories, one file `commit-proofs/<messageHash>.json`, read with the corrupt-content-as-missing guard the `proofs` store uses. `listBlockIds` skips the directory at the root, as it skips `ROOT_KV_NAMESPACES`. Add a `NOTE:` beside the constant: a block whose id is `commit-proofs` or starts `commit-proofs/` is hidden from the listing — the same accepted limit the KV namespaces already carry; if such ids ever occur, encode block-id segments in the layout. A base58 hash is filename-safe; on a case-insensitive filesystem two hashes differing only in letter case would share a file, which needs a collision of SHA-256 outputs on roughly 200 bits and is answered safely anyway, because the reader checks the proof's message names the block it serves (`servableProof`). Say that in one line at the path function.
- **SQLite** (`db-p2p-storage-ns`): `CREATE TABLE IF NOT EXISTS commit_proofs (message_hash TEXT PRIMARY KEY, value BLOB NOT NULL)` in the schema script, prepared get/put statements, the batch apply case. An existing database file gains the table on next open, as `proofs` did.
- **IndexedDB** (`db-p2p-storage-web`): object store `commitProofs`, created in `upgrade` when missing; `DEFAULT_DB_VERSION` to 4 with the comment extended; add to `APPLY_STORES`; `idbKeyOf` returns the hash string; `isStoreKey` must accept a key with `messageHash` and no `blockId` (today it requires `blockId` first — restructure, don't special-case after the fact). The untested-upgrade debt (backlog `debt-indexeddb-version-upgrade-is-untested-and-unhandled`) applies to this bump as it did to the last two; nothing more here.
- **LevelDB** (`db-p2p-storage-rn`): `TAG_COMMIT_PROOFS = 0x08`, key = tag byte then the hash's UTF-8, no block envelope (the journal's shape). Document it in the `keys.ts` header table. Confirm no range scan spans 0x08 (the metadata range is `[0x01, 0x02)`).

## Edge cases & interactions

- **Journal records are decoded strictly.** `decodeStoreKey` must round-trip the new key and keep refusing a key that is none of the shapes; `canonicalStoreKey` must give it a string no other key can produce (e.g. include the store name and keep the hash last, the way the existing shapes are built). Verified by the conformance suite running through a write group over the journal backends, and by inspection of `canonicalStoreKey`.
- **Keyspace isolation.** A commit-proof record under hash `X` and a `proofs` record for block `X` must not see each other. One conformance case (the precedent is the `~proof:<N>` collision case).
- **Clone semantics.** Values cross the driver encoded, so clone-on-store/clone-on-read holds by construction; the conformance suite's existing pattern covers it for the new store with one round-trip case.
- **Downgrade.** An older build reading a journal record holding the new key discards the record as undecodable. Downgrades are not supported ("Don't worry about backwards compatibility yet"); no handling.
- **A text-valued backend** (`KvRawStorage<string>`, LevelDB on React Native): the store follows the driver's `V` like every other; nothing special.

## Tests

Conformance only — `packages/db-p2p/src/testing/raw-storage-conformance.ts` already runs against every backend and every cached and write-group composition: a miss returns `undefined`, a round-trip, and isolation from the `proofs` store. No backend-specific test.
