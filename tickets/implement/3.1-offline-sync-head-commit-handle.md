First of four tickets that implement stage 3 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages) (the queue in db-core). This one changes no behaviour of `Collection.commitHead`: it re-expresses it over a handle the next ticket (`offline-sync-coordinator-entry-commit`) drives for several collections at once, and adds the two hooks the queue (`offline-sync-queue-core`) and the journal (stage 5) need around each attempt.

## Why a handle

`Collection.commitHead` in `packages/db-core/src/collection/collection.ts` already does everything a one-collection drain needs: it takes the latch, checks the segment is the committable head (`assertHeadCommittable`), marks the action in flight and the head entry (`beginInFlightAction`, `headCommitEntry`), refreshes, builds the attempt on a head tracker reused per revision (`headTrackerFor`, `buildAttempt`), releases the latch for the one network `await` (`sendUnlatched`, `headInFlight`), and on success drops the head, folds the attempt's transforms and replays what remains (`headCommitAttempts`). A multi-collection entry has to do each of those steps on every collection it wrote, in lock-step: build every attempt, then release every latch, then one pend-all-then-commit round through the coordinator, then retake every latch and apply one outcome per collection. That is only possible if the steps are callable one at a time from outside the collection. The handle is that surface; the one-collection loop becomes its first driver.

## The handle

Add `packages/db-core/src/collection/head-commit.ts` holding the exported `HeadCommitHandle<TAction>` interface and the one-collection driver `driveHeadCommit`. The handle is created by a new `Collection.openHeadCommit(entryId, identity, resume?)` and is a closure over the collection's private state, so nothing private becomes public. `openHeadCommit` takes the collection latch, runs the three preconditions of `assertHeadCommittable` (`not-head`, `refused`, `in-flight`, each a `SealedSegmentsError`), marks the action in flight, sets `headCommitEntry`, and seeds `inFlightAttempt` with `resume` when one is given (see *Resuming an attempt* below). It holds the latch until `close()`.

```typescript
export interface HeadCommitHandle<TAction> {
	readonly collectionId: CollectionId;
	readonly entryId: EntryId;
	/** The refresh between attempts, run under the latch this handle holds: `updateInternal` with
	 * the write's own report, so an entry an earlier attempt stored is finished and consumed as
	 * the head (`consumeHead`). Same contract as `Collection.refreshInFlight`, minus the latch. */
	refresh(report: RefreshReport, lastChance: boolean, tailFloor?: number): Promise<void>;
	/** The revision the next attempt requests, and the one the collection holds, for the cycle's
	 * stall accounting (`AttemptCycle.beforeAttempt`). */
	nextRev(): number;
	heldRev(): number | undefined;
	/** Re-check the head is still committable (a refresh may have refused it meanwhile — the
	 * recorded refusal is thrown), then build the attempt at `nextRev()` on the head tracker, reused
	 * while the revision and the bases under it are unchanged (`headTrackerFor`). */
	stage(): Promise<StagedAttempt>;
	/** Send one attempt through this collection's own transactor source — the one-collection
	 * path's pend-and-commit. The coordinator never calls it. */
	send(staged: StagedAttempt, priority: number): Promise<CommitResult>;
	/** Release the latch for the network round trip and set `headInFlight`. */
	release(): void;
	/** Retake the latch and clear `headInFlight`. Never throws for a refusal: the caller re-checks
	 * through `stage()` or `refused()`. */
	retake(): Promise<void>;
	/** A committed attempt's local treatment, first half, synchronous: remove the head segment
	 * (asserted still first), bump the segment version, fold the attempt's transforms into the
	 * cache and adopt its revision (`foldOwnCommit`). */
	fold(staged: StagedAttempt): void;
	/** Second half: replay the remaining sealed segments and the open segment over the committed
	 * state that now holds the head. Always after `fold` — the order `updateInternal` requires. */
	replay(): Promise<void>;
	/** A refused attempt: re-check the head's recorded refusal (thrown), then retain the attempt
	 * (`retainInFlightAttempt`) so the next refresh can finish it. */
	refused(staged: StagedAttempt): void;
	/** End the cycle: clear `headCommitEntry`, dispose the in-flight mark, release the latch.
	 * Idempotent. Every exit of a driver passes through it. */
	close(): void;
}
```

`fold` and `replay` are two calls rather than one because the coordinator's success path folds every participant in one await-free pass before replaying any, which is the event-loop atomicity its existing success fold promises (`commitOnceLatched`); the one-collection driver simply calls them back to back.

`driveHeadCommit(handle, identity, options)` is `headCommitAttempts` moved out of `collection.ts` and expressed over the handle, with the `AttemptCycle` accounting unchanged: the opening `refreshUntilSettled` through `handle.refresh`, then `beforeAttempt`, `stage`, the write-ahead hook (below), `release`, `send`, `retake` in a `finally`, then `fold` + `replay` + `recordCommit` or `refused` + `refreshUntilSettled`. `Collection.commitHead` becomes `openHeadCommit` followed by `driveHeadCommit` inside a `try`/`finally` that closes the handle. The private pieces `headCommitAttempts`, `sendUnlatched`, `committableHead` and `headSegment` move into the closures the handle is built from, or into `head-commit.ts` where they need no private state; `headTrackerFor`, `buildHeadTracker`, `buildAttempt`, `send` and `foldOwnCommit` stay private on the collection and are reached through the handle. The `NOTE:` on the quadratic replay and the `NOTE:` at `buildHeadTracker`'s catch stay at their sites.

## The write-ahead hook and resuming an attempt

`HeadCommitOptions` in `packages/db-core/src/collection/struct.ts` gains two optional fields:

- `recordAttempt?: (attempt: InFlightAttempt) => Promise<void>` — called by the driver after `stage()` and **before** `release()`, with `retainedAttempt(staged)`, and awaited under the latch. It is the queue's write-ahead point ([docs/offline-sync.md §Identity across attempts](../../docs/offline-sync.md#identity-across-attempts): the attempt's identity is recorded before it is sent) and, in stage 5, the journal's. A throw out of it aborts the cycle before anything is sent: the error propagates out of `commitHead`, the handle closes, and every segment is exactly as it was.
- `resume?: InFlightAttempt` — the attempt an earlier cycle under the SAME action id recorded through `recordAttempt` and did not resolve. `openHeadCommit` seeds `inFlightAttempt` with it right after marking the action in flight, so the cycle's opening refresh, finding that attempt's log entry with blocks missing, finishes it from these transforms (`completeOwnEntry`) instead of refusing with a `transforms-not-held` `TornActionError`. Without it a re-drive can only recognise an attempt that landed completely (the status-read fallback). The revision check in `completeOwnEntry` still applies: a resumed attempt at a revision other than the entry's is refused as before.

`InFlightAttempt` (in `collection.ts`) is already the exact shape a re-send needs; it becomes the recorded shape too. It must stay plain data (the journal will serialise it as JSON in stage 5): `transforms`, `rev`, `tailId`, `blockDigests?`, `baseRevs?` — nothing with identity or functions. Add a sentence to its doc comment saying so.

## Edge cases & interactions

- **Behaviour of `commitHead` is unchanged.** Every case under `describe('commitHead …')` in `packages/db-core/test/collection-segments.spec.ts` passes unmodified. Verified by running the suite; no new test for the extraction itself.
- **`close()` after `release()` without `retake()`** (a driver that throws between the two): `close` must retake nothing it does not hold. Make `close` idempotent and latch-state-aware (release only if held, clear `headInFlight` either way). Verified by inspection and by the existing "a promise shortfall out of a head attempt" case, whose throw happens with the latch retaken.
- **`openHeadCommit` on a collection whose head is in flight on another handle** meets `in-flight`, as the second `commitHead` does today. By the existing test.
- **A refusal recorded by a reader's refresh while the latch is released** is still thrown by the next `stage()` or `refused()`, never by `retake()`, so a send error is not masked. The existing "a head refused by a rival that landed while the attempt was in flight" case pins it.
- **`recordAttempt` throws:** nothing sent, segments intact, the error escapes `commitHead` unchanged. By a test: a hook that throws on the first call; the second `commitHead` succeeds and the log holds the entry once.
- **`resume` with a stale revision** (an attempt recorded at a revision the collection has since moved past): `completeOwnEntry` refuses the mismatch as it does today; by inspection, the field is the same one it already reads.
- **`resume` under a different action id** than `options.actionId` is a caller defect; `openHeadCommit` throws before taking the latch. By a type-level note and an assertion.
- **Two handles on two collections opened in the wrong latch order** can deadlock against a coordinator commit over the same collections. The handle does not sort; the next ticket's driver opens in sorted collection-id order (the order `commitOnce` acquires). Say so in the interface doc.

## Tests

One new case in `collection-segments.spec.ts`, the one contract nothing exercises yet: **a recorded attempt finishes a torn head on a later cycle.** Over `TailLandsButReportsStale` with `maxAttempts: 1`, the first `commitHead` under action id X throws after retaining nothing a later cycle can see; `recordAttempt` captured one `InFlightAttempt`. A second `commitHead` under X **without** `resume` throws `TornActionError` with reason `transforms-not-held` (the control). A third under X **with** `resume` set to the captured attempt finishes the write on its opening refresh, consumes the head, sends nothing new (count the double's pends and commits), and the committed log holds the entry once. The hook-throws case above is the second new test.
