# A node observes the HLCs it reads and stores

Third of the three Stage 1 tickets (see `the-hlc-clock-and-its-persistence-port` for the clock and the summary of the plan pass, and `every-log-entry-and-transaction-carries-its-hlc` for the fields). This one closes the causal loop and takes the measurement Stage 2 decides from. Still no ordering, admission or visibility change.

## The feed points

A node must never issue an HLC below one it has observed. "Observed" has one precise meaning in Stage 1: an HLC on a log entry this node read into a collection handle, or on a pend this node stored. Each site calls `clock.observe(hlc)` with the single highest value it saw, since the clock keeps only a maximum:

- **A refresh that walks the log.** `Log.getFrom` collects `ActionEntry`s, not whole `LogEntry`s, so the HLCs are not in what it returns. Give `GetFromResult` an `hlcHighWater?: Hlc`, the maximum over every entry the walk stepped through (action, checkpoint and invalidation entries alike, through `hlcOf` so legacy entries count with their wall time), and have `Collection.forgetAndAdopt` observe it. One value, not a per-entry list, because nothing wants the list.
- **An open.** `Collection.attachToLog` has read the log tail block; observe the maximum over `tail.entries` beside `floorTailEntries`, which already walks them.
- **A pend this node stores.** `StorageRepo.pend` observes `request.hlc` when the request carries a well-formed one (`isHlc`), before or after the apply, on the request as received. This is where every write a node holds for others passes exactly once, as a cohort member applying a consensus record and as a solo coordinator alike, so it is the one site rather than `ClusterMember` and `CoordinatorRepo` separately. A pend the member refuses (stale, held, rejected) never reaches it, which is right: the node does not build on a write it refused. A `StorageRepo` built with no clock (the Quereus plugin's `local` and `test` transactors, the direct constructions in tests) observes nothing and logs nothing.

Not fed in Stage 1, deliberately: blocks that arrive as replicas (a push, a reconcile, a restore), since this node has not read them into a handle and does not build on them; a pinned read view (`createReadTracker`), which reads old content on purpose; `readCommittedTails`, which reads tails for the watch service and opens no handle. The first of these is the one worth a `NOTE:` at `saveReplicatedBlock`, saying that a replica's entries are not observed and why.

## The skew measurement

The doc's open question is whether members should refuse an HLC whose `wallMs` is far from their own clock. Stage 1 answers it by measuring, refusing nothing. `SkewLedger` in `packages/db-core/src/hlc/skew.ts` is pure: `record(nodeId, gapMs)` keeps, per node id in a bounded `LruMap` (256 entries), the count of samples and the largest gap seen in each direction, and `snapshot()` lists them. `StorageRepo.pend` computes `gapMs = request.hlc.wallMs - now()` for every pend carrying an HLC, records it, and logs `hlc:skew` when `|gapMs|` exceeds `skewLogThresholdMs` (`StorageRepoOptions`, default 1000) with the fields `actionId`, `nodeId` (short form), `gapMs`, `maxAheadMs` and `maxBehindMs` for that node, and `samples`. Debug-gated like every line, so logging each over-threshold pend costs nothing when the namespace is off; below the threshold nothing is logged, so an ordinary cohort is silent. The ledger is exposed as `storageRepo.hlcSkew` for a host or a test to read. Nothing acts on it.

Two things the gap is not: it is not evidence against the sending node alone, since either clock may be the wrong one, so it feeds no reputation report; and it is not the HLC's `logical`-and-jump behaviour, so a node whose HLC jumped forward after observing a far-ahead peer will itself show as ahead to everyone, which is the measurement working as intended and worth one sentence in the doc.

## Node wiring

`createLibp2pNodeBase` builds one `HlcClock` with the node's peer id string, a `KvHlcClockStore` over the node's `IKVStore` (`resolveKvStore`, the store the under-replication ledger uses; key `hlc/high-water`, value the JSON of the `Hlc`) and the default persist and restart constants, awaits `start()` before anything can write, and hands the same instance to `new StorageRepo(rawStorage, { clock, ... })` and to the `NetworkTransactor` the Quereus plugin builds over the node (`CollectionFactory.createNetworkTransactor` passes `node.hlcClock` as `NetworkTransactorInit.clock`). Expose it as `node.hlcClock` on `OptimysticNodeAttachments` so a host that builds its own transactor over the node reaches the same clock. A node without a durable `kvStore` gets the in-memory store and the existing one-line warning about the ledger gains a clause about the clock mark.

## Edge cases & interactions

- **A pend whose `hlc` is malformed** (wrong shape over JSON): ignored for the clock and the ledger, logged once per action under `hlc:malformed`. Never a refusal. By inspection.
- **A pend with no `hlc`** (older writer): observes nothing, measures nothing. By inspection.
- **A far-ahead HLC observed from a pend**: this node's clock jumps, its next writes carry a future `wallMs`, and other members then measure this node as ahead. Expected; documented.
- **A refresh that adopts another lineage** (`adopt-divergent`): observes the new lineage's high water like any walk; the clock only ever rises, so dropping the cache and floors does not touch it. By inspection.
- **A refresh deferred to an in-flight head commit** returns before `forgetAndAdopt` and observes nothing; the head commit's own refresh does when it retakes the latch. By inspection.
- **Legacy entries on the walk**: counted at their wall time with `nodeId` `''`, so a node reading an old log still cannot issue below the newest wall time in it. By inspection of `hlcOf`.
- **Two handles over one collection in one process** share the transactor's clock, so one handle's walk raises the mark the other mints from. Correct by construction.
- **The clock's debounced save and the kv store's flush**: the store write is fire-and-forget and never flushed by the clock; the restart slack from the first ticket is what covers an unflushed mark. The ledger's `beforeRecord: () => rawStorage.flush()` pattern is not copied here, on purpose; say so at the store.
- **Restart over the upgrade-check fixtures**: a fixture has no stored mark, the clock starts from the local clock, and the suite passes unchanged. The fixture runs `yarn test` anyway.

## Tests that pay for themselves

None new. The clock's behaviour is pinned by the first ticket's test; observing and recording are wiring. The one tempting case, "a refresh raises the clock above a rival's HLC", pins a single `observe` call, which a type cannot but a reviewer's inspection can.
