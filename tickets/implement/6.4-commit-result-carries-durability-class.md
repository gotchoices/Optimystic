# What is wrong

Optimystic has exactly one shape of successful write: `{ success: true }`. Four different situations produce it and they do not mean the same thing.

1. **Quorum commit.** More than half the block's group confirmed its storage holds the new revision. This is the case the design documents describe, and the only one the current answer is honest about.
2. **Solo commit.** The writing machine worked out that it is the only machine responsible for the block, wrote to its own storage, signed a one-machine receipt, and returned success. Nothing in the answer distinguishes this from case 1. The downstream project sereus had to guess at it from its own count of open connections, and its notes say that guess misses the collection's header and index blocks.
3. **No group at all.** Every attempt to look up the block's group threw. `ClusterCoordinator.getClusterForBlock` catches the throw and returns an empty group; `getClusterPeerIds` then returns an empty list; `CoordinatorRepo.isResponsibleForBlock` answers "assume responsible" on a throw; and `CoordinatorRepo.commit` sees at most one peer, takes the solo branch, and returns success. A user on a four-machine deployment reported exactly this (GitHub #19): two phones each wrote a row, each was told the write succeeded, and each kept only its own row, with no error anywhere. The only trace is one log line, `commit:solo-cohort`, carrying a cohort size of zero. The durability check sits *below* that early return and never runs.
4. **Torn multi-block commit.** The tail block committed; the sweep over the remaining blocks failed for a transport reason; the abandoned blocks were cancelled; success was still returned.

This ticket makes the answer say which of the four happened. **It changes no policy.** Everything accepted today is still accepted, everything refused is still refused, and no new retry or refusal is introduced. It is purely about what the writer is told.

Three things build on it and are deliberately **not** here: passing the class up to the application (`write-durability-reaches-the-writer`), remembering and repairing a shortfall (`under-replication-ledger-records-missing-holders` and `under-replication-drain-and-full-replication-event`), and deciding whether a caller may *proceed* on a write only its own machine holds (`backlog/feat-long-lived-pend-completes-as-members-appear`, which names this ticket as its prerequisite). The reporter of GitHub #19 asked for this before the 1.0 release, since it changes a public result type.

# The new type

In `packages/db-core/src/network/struct.ts`:

```ts
/** How widely a successful write is known to be held at the moment it was acknowledged. */
export type DurabilityQuorum =
	/** Every member of the resolved cohort confirmed it holds the revision. */
	| 'full'
	/** A strict majority confirmed — the acknowledgement bar — but at least one member did not. */
	| 'majority'
	/** The cohort resolved, and it is this node alone. Nobody else holds the revision yet. */
	| 'local'
	/** The cohort did NOT resolve: the lookup threw, or named nobody, or named a single peer that
	 *  is not this node. The write is on this node's storage and the network was never consulted.
	 *  Deliberately NOT `local`: a genuine cohort of one is a correct, complete write, whereas this
	 *  is a write whose correct destination is unknown. */
	| 'unrouted';

/** What the answering layer knows about who holds a successful write. Each layer refines it:
 *  `StorageRepo` answers for itself alone, `CoordinatorRepo` answers for the cohort the write ran
 *  on, and `NetworkTransactor` merges the per-coordinator answers into one action-level answer.
 *  Never a policy input — read it to DISPLAY or to REPAIR, never to decide acceptance. */
export type WriteDurability = {
	readonly quorum: DurabilityQuorum;
	/** Cohort members confirmed to hold the write, including this node when it holds it.
	 *  For a commit this means "reported that its storage durably holds the revision"; for a pend
	 *  it means "accepted the pending record". The two are NOT comparable — a pend confers no
	 *  storage durability (see the note in `CoordinatorRepo.pendThroughCluster`). */
	readonly confirmed: number;
	/** Size of the cohort the write ran on. Zero exactly when `quorum` is 'unrouted'. */
	readonly cohort: number;
	/** Cohort members that did not confirm, by peer-id string. Empty when `quorum` is 'full'.
	 *  ABSENT (not empty) when the answering layer could not name the cohort — an empty array
	 *  here means "named the cohort, nobody is missing". */
	readonly unconfirmed?: readonly string[];
	/** The cohort the write ran on, by peer-id string. Absent where the answering layer has no
	 *  cohort view at all (a bare `StorageRepo` verdict). */
	readonly cohortPeerIds?: readonly string[];
	/** Present only on an action-level result whose blocks ran on MORE THAN ONE cohort: the other
	 *  cohorts' reports. The scalar fields above always describe the WEAKEST cohort, so a consumer
	 *  that reads only them is reading the binding constraint and is never over-optimistic. */
	readonly otherCohorts?: readonly WriteDurability[];
	/** Blocks this action wrote that are NOT committed — a torn sweep abandoned and cancelled them
	 *  (`NetworkTransactor.cancelAbandonedSweepBlocks`). Action-level commit results only.
	 *  These blocks NEVER heal by replication: their transform is gone, and only the writer
	 *  re-driving the action puts them back. */
	readonly torn?: readonly BlockId[];
};
```

`PendSuccess` and `CommitSuccess` each gain a **required** `durability: WriteDurability`.

Required, not optional, is the whole point: an absent field reads as plain success, which is the ambiguity this ticket exists to remove. The migration cost was measured on this branch by making the field required and running `tsc --noEmit` per package: **9 errors across 5 files in `@optimystic/db-core`** (4 of them source sites — `TestTransactor.commit` and three returns in `NetworkTransactor`) and **77 errors across 32 files in `@optimystic/db-p2p`** (3 source sites — `storage-repo.ts`, `cluster-repo.ts`, `coordinator-repo.ts` — and 29 spec files). `quereus-plugin-optimystic`, `reference-peer`, `demo` and `db-p2p-storage-fs` produced zero. Nearly every one is fixed by adding the field to a literal.

## One predicate, not a field comparison

A new `packages/db-core/src/network/durability.ts`:

```ts
/** The ONLY "this write is completely saved" test. `full` alone is not enough: a torn action can
 *  have a fully-held tail and blocks that were cancelled. Consumers must call this rather than
 *  comparing `quorum` themselves. */
export function isFullyDurable(d: WriteDurability): boolean;

/** Total order on quorum classes: unrouted < local < majority < full. */
export function durabilityRank(q: DurabilityQuorum): number;

/** Merge per-cohort reports into one action-level report: the weakest becomes the scalar answer,
 *  the rest become `otherCohorts`. THROWS on an empty input — an action always ran on at least one
 *  cohort, and fabricating an answer is exactly what this ticket removes. */
export function mergeDurability(reports: readonly WriteDurability[]): WriteDurability;

/** The single-node answer: this node holds it and knows nothing about a cohort. */
export function localDurability(selfPeerId?: string): WriteDurability;

/** The no-cohort answer: this node holds it and could not establish where it belongs. */
export function unroutedDurability(reason: string): WriteDurability;
```

`isFullyDurable` is the boundary invariant that stops the class from being re-derived wrongly at each consumer. Every place that wants to show a change as saved calls it.

# Where each class is produced

## The innermost layer: `StorageRepo`

`StorageRepo.pend` and `StorageRepo.commit` answer for one machine's storage. They return `localDurability()` on success — true, and not a lie: this layer genuinely knows only about itself. It has no peer id, so `cohortPeerIds` and `unconfirmed` stay absent there.

Member-side results (`ClusterRepo`, and the verdict `getExecutedCommitResult` hands back) are consumed only for their `success` flag — by `cohortCommitOutcomes` in `ClusterCoordinator.executeClusterTransaction` and by the local-verdict arms of `CoordinatorRepo.commit`. The new field rides along inert there. **Do not** let a member's local answer leak out as the coordinator's answer on any cluster path: every exit of `CoordinatorRepo.commit` must set its own.

## Making an unresolvable cohort distinguishable

`ClusterCoordinator.getClusterForBlock` currently swallows a `findCluster` throw and returns an empty map, so "no cohort" and "lookup failed" arrive at the caller as the same empty list. Add a typed resolution and derive the existing accessors from it, so there is still exactly one rule:

```ts
export type CohortResolution =
	| { readonly resolved: true; readonly peerIds: readonly string[] }
	/** The lookup threw, or answered with nobody. `reason` is for logs only. */
	| { readonly resolved: false; readonly reason: string };
```

- `ClusterCoordinator.resolveCohort(blockId): Promise<CohortResolution>` is the new primitive.
- `getClusterPeerIds` and `getClusterSize` stay, derived from it, so no existing caller changes shape.
- `resolveCohort` joins `ICoordinatorClusterSeam`. That interface exists precisely so widening it breaks the specs' coordinator doubles at compile time rather than at runtime — read its own note before adding the method, and expect to update the doubles across the `coordinator-repo-*.spec.ts` family.

## `CoordinatorRepo.pend`

`pendThroughCluster` takes the short-circuit when the cohort has at most one peer. Replace the bare `getClusterSize` call with `resolveCohort` and classify:

- not resolved, or resolved to nobody → `unrouted`
- resolved to exactly this node → `local`
- resolved to exactly one peer that is **not** this node → `unrouted` (this node is writing somewhere the cohort does not look)
- resolved to two or more → the cluster path

On the cluster path, `confirmed` is the number of cohort members that **accepted** the pend (approving promise votes on the record, plus this node when its own member applied), and `cohort` is the size of the record's peer set. Keep the existing pend semantics exactly: a cohort refusal still downgrades a success to the retryable conflict, and the durability field is attached only to the success shape.

## `CoordinatorRepo.commit`

The solo branch classifies the same four ways as pend, using the same `resolveCohort`. The existing `commit:solo-cohort` log line already distinguishes these for an operator; it now also carries the chosen `quorum`, so the log and the returned answer can never disagree.

On the cluster path, `cohortDurability` currently counts remote holders and refusals and discards their peer ids. `cohortCommitOutcomes` is keyed by peer-id string, so the names are already in hand — change the interface to carry the sets:

```ts
interface CohortDurability {
	cohortPeerIds: readonly string[];      // the record's peer set — the majority denominator
	remoteHolders: readonly string[];      // reported success
	remoteRefusals: readonly string[];     // reported a refusal
}
```

`isDurableMajority` keeps its exact rule (`confirmed > cohort / 2`) and stays the acceptance gate. A new sibling derives the class, and **every success exit of `commit` attaches it**:

- the locally-executed arm, where `confirmed` is remote holders plus one when the local verdict succeeded;
- the fallback-commit arm, where `confirmed` is remote holders plus one when this node is in the record's peer set;
- `tolerateLocalCommitDivergence`, where this node is explicitly not a holder, so `confirmed` is remote holders alone.

The class falls out of one rule in all three: `full` iff `confirmed === cohort`, otherwise `majority` (the gate already refused anything below it). No new arm, no new refusal.

`refuseCommitNotDurable` is unchanged — it produces a `StaleFailure`, which carries no durability.

## `NetworkTransactor`, the action level

`NetworkTransactor.commit` commits the tail, then sweeps the remaining blocks across whatever coordinators own them. Each per-batch response now carries its coordinator's answer. The action-level answer is `mergeDurability` over the batches that succeeded, plus:

- **Torn commits.** The transport-tolerant arm logs a warning, calls `cancelAbandonedSweepBlocks`, and returns success. It must now return `torn` naming exactly the abandoned blocks — the same set `cancelAbandonedSweepBlocks` computes, so have that method return it rather than re-deriving. A non-empty `torn` clamps `quorum` down from `full` (never up). `isFullyDurable` then answers false, which is the behaviour the use case wants; a consumer that needs to know *which* blocks reads `torn`.
- **`NetworkTransactor.pend`** merges its batches the same way. It has no torn case.

# Edge cases & interactions

- **Solo node with genuinely no peers.** Cohort resolves to this node alone; class is `local`; the one-machine receipt (`mintSoloCommitProof`) is minted exactly as today. This is a correct, complete write on a one-machine deployment and must not read as an error.
- **A cohort of one that is not this node.** Resolution succeeds and names a single peer that is not self. Today this falls into the solo branch and commits locally. Keep that behaviour; class it `unrouted`.
- **Cohort lookup throws for some blocks and not others.** A multi-block commit can mix an `unrouted` batch with a `full` one. `mergeDurability` must report `unrouted`, because the weakest is the binding constraint.
- **A commit spanning more than one coordinator.** `otherCohorts` carries the non-weakest reports. Note that `consolidateCoordinators` collapses most pends onto one coordinator, so on every in-process test mesh today this is a single-entry case — the multi-cohort shape is structurally hard to reach and is tracked in `backlog/debt-no-mesh-fixture-forces-two-coordinator-batches`. Write the merge so it is correct for any number, test it directly with unit-level reports, and do not claim integration coverage you do not have.
- **Replayed commit.** `ClusterMember.getExecutedCommitResult` returns a retained storage verdict for an already-executed message. That verdict is a member's own answer and is read only for its `success` flag. It must never become the coordinator's answer to the writer — the arms above always compute their own.
- **Absent local verdict.** A member that predates verdict retention, restarted, or whose retention window expired contributes nothing. It is not counted as a holder today and must not be counted now; the class then reads lower than reality, which is the safe direction.
- **Tolerated local divergence.** This node committed nothing; a remote majority holds it. Class is `majority` when this node is in the cohort (it is then an unconfirmed member), and can legitimately be `full` when it is *not* in the cohort and every member confirmed. Both fall out of `confirmed === cohort`.
- **Pend and commit numbers are not comparable.** A pend's `confirmed` counts acceptances of a pending record; a commit's counts storage that holds the revision. State that at the field, since the same shape carries both.
- **`StaleFailure` gains nothing.** A failure has no durability. Do not add the field to it, and do not add an "unknown" class to stand in for one.
- **Concurrent writers.** Two writers racing the same revision already resolve through the existing conflict machinery. Neither writer's durability class affects that resolution; check that no new branch reads `quorum` before the existing gate.

# Tests

Unit, in `@optimystic/db-core`:

- `mergeDurability` picks the weakest across every ordering of the four classes, and puts the rest in `otherCohorts`. It throws on an empty list.
- `isFullyDurable` is false for a `full` result carrying a torn block, and true for a `full` result with none.
- `NetworkTransactor.commit` whose sweep throws for transport reasons: the returned result is a success whose `torn` names exactly the abandoned blocks and whose `isFullyDurable` is false. Extend `packages/db-p2p/test/torn-commit-cancels-abandoned-blocks.spec.ts` rather than writing a parallel fixture.

Unit, in `@optimystic/db-p2p`, each with a `CoordinatorRepo` and a coordinator double:

- **The GitHub #19 spec.** A coordinator double whose every cohort lookup throws: `commit` still returns success (policy unchanged), and its durability reads `unrouted` with a cohort size of zero. The point is stated as an assertion, not a comment: *a commit that reached no resolved cohort must not be indistinguishable from a healthy commit.* Assert the complementary case in the same spec — a two-member cohort that both confirm reads `full` — so the spec fails if the class ever collapses to one value.
- Resolved cohort of exactly this node → `local`; resolved cohort of exactly one peer that is not this node → `unrouted`.
- Four-member cohort, three confirm → `majority`, `confirmed` 3, `cohort` 4, `unconfirmed` naming the fourth by peer id.
- Four-member cohort, all four confirm → `full`, with `unconfirmed` present and empty.
- Tolerated local divergence on a confirming remote majority → success, `majority`, and this node absent from the confirmed count.
- A commit refused by the durability gate still returns a `StaleFailure` with no durability field — the gate's behaviour is untouched.
