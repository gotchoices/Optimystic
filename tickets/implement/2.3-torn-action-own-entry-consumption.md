# Torn action, part 2 of 3: consume your own committed log entry (db-core)

Split from `torn-action-must-recognize-its-own-durable-work` after a budget stop; part 1 is
`torn-action-pend-tier-carve-out` (db-p2p), part 3 is `torn-action-cleanup-and-mesh-validation`.
This part is self-contained, independent of part 1, and closes the duplicate-entry arm
regardless of commit ordering.

## The defect (static, same root cause as part 1)

`NetworkTransactor.commit` commits the collection header and log tail before the sweep of
remaining blocks. When a LATER sweep block comes back as a confirmed conflict, it returns a
stale failure (network-transactor.ts:714-737) — correct, acknowledging a torn action would be
worse — but header and tail are already durable, so the collection's log now contains this
action's entry. The writer's retry then calls `Collection.updateInternal`, whose entry loop
(collection.ts:487-504) filters `this.pending` only through `doFilterConflict` (default: keep
everything) and replays the lot — re-appending content the committed tail already carries. A
**duplicate entry**.

The missing rule: an action that finds its OWN actionId in the committed log must consume it,
not replay it. `Log.getFrom` returns `ActionEntry`s carrying `actionId`, and
`addActions(pending, actionId, …)` wrote exactly the snapshot pending list under that id, so the
entry's `actions` array corresponds one-to-one to the leading items of `this.pending`.

## Design (settled)

- Thread the in-flight actionId from `syncInternal` into `updateInternal` as an optional
  parameter: `private async updateInternal(inFlightActionId?: ActionId)`. The call at
  collection.ts:866 passes the `actionId` minted at 782-783; `update()` (line 434) and
  `updateAndSync()` (line 898) stay no-arg — public shapes unchanged.
- In the entry loop, branch BEFORE `doFilterConflict`:

```ts
if (inFlightActionId !== undefined && entry.actionId === inFlightActionId) {
	// This sync's own action is already durably committed — consume it instead of replaying.
	// addActions wrote exactly the snapshot pending list under this id, so the entry's actions
	// are the leading entry.actions.length items of this.pending.
	after = before.slice(entry.actions.length);
	mutated = true;   // unconditionally — even a zero-action entry means the tracker's staged
	                  // transforms for it are now durable and must be rebuilt via the replay
} else {
	/* existing doFilterConflict map/filter + identity comparison */
}
```

- Keep `this.sourceCache.clear(entry.blockIds)` for the consumed entry, keep the
  invalidation handling and the advanceContext-before-replay ordering exactly as they are.
- Why `mutated = true` matters: `anyConflicts` drives `replayActions()`, which resets the
  tracker and re-stages only the remaining pending — that reset is what drops the consumed
  action's staged transforms so `hasUnsyncedChanges()` turns false and the sync loop exits
  cleanly (the writer correctly observes success: the action IS durable).
- `act()` and `syncInternal` share the collection latch, so `this.pending` cannot grow
  mid-sync; the snapshot length always equals `entry.actions.length` for the own entry. A
  defensive `slice(entry.actions.length)` is still the right shape (never negative).

## Spec (new file, e.g. `packages/db-core/test/collection-own-action-replay.spec.ts`; write first, confirm it fails pre-fix)

Wrapper transactor — commits durably on the inner `TestTransactor`, then reports stale anyway
(the exact observable shape of tail-committed-then-later-block-conflict):

```ts
class CommitLandsButReportsStale implements ITransactor {
	private injections = 1;
	constructor(private readonly inner: TestTransactor) {}
	get(b: BlockGets) { return this.inner.get(b) }
	getStatus(a: ActionBlocks[]) { return this.inner.getStatus(a) }
	pend(r: PendRequest) { return this.inner.pend(r) }
	cancel(a: ActionBlocks) { return this.inner.cancel(a) }
	async commit(request: CommitRequest): Promise<CommitResult> {
		const result = await this.inner.commit(request);
		if (result.success && this.injections-- > 0) {
			return { success: false, conflict: true, reason: 'stale commit: injected torn-action conflict' };
		}
		return result;
	}
}
```

Safe because `TransactorSource.transact` cancels on the reported failure and
`TestTransactor.cancel` only deletes pending records (already promoted by the real commit — a
no-op). Test body: `Collection.createOrOpen` over the wrapper (copy `initOptions`/handlers from
collection.spec.ts), `act` one action, `sync({ maxAttempts: 5, baseBackoffMs: 1, maxBackoffMs: 5 })`
— must RESOLVE (not exhaust), and `selectLog()` must yield the action exactly ONCE. Pre-fix the
retry re-pends at rev 2 and commits a second copy (injection spent), so the log holds two — the
assertion catches it. Optionally also assert via `transactor.getCommittedActions()`.

## What must NOT change

- Acknowledged-means-durable: `NetworkTransactor.commit`'s non-tail sweep keeps returning its
  stale failure; nothing here touches network-transactor (part 3 owns its dead-clause cleanup).
- `update()` with no argument behaves exactly as today (entry loop untouched when no in-flight id).
- `packages/reference-peer/test/distributed-diary.spec.ts` keeps its current strength.
