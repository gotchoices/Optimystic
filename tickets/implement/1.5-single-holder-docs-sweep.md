## What already shipped (read this first — the wording to match is in the code)

`CoordinatorRepo.reportRepairDeadlock` now emits `cluster-fetch:repair-deadlock` with a `reason`
field carrying one of two values:

- `cohort-too-small` — the cohort has fewer peers than the quorum needs even if every one of them
  answered and agreed. Remedy: more machines, or an honest declared cohort size.
- `sole-holder` — **new.** The cohort is big enough, but exactly one of its peers holds the block and
  every other peer *answered* that it holds nothing. Remedy: a second copy of the block. No machine
  count and no configuration setting helps.

`resolveClusterPolicy`'s startup advisory (`repair-fault-tolerance`) gained a closing paragraph
scoping every machine-count claim it makes to blocks that at least two peers already hold, and naming
the stranded-founding-data case.

## The claim that is wrong in the docs

Four documents repeat a machine-count model that conflates two different quantities — **how many
machines the deployment runs** and **how many of them hold a given block**. Each says, in its own
words, that three machines is the minimum for repair and four or more is the first size with any
margin. Both statements are true *only* for a block that already has two or more holders. For a block
only one machine holds, three machines repair no better than two and no machine count helps at all —
so an operator at four-plus machines reads these documents and believes they are covered.
