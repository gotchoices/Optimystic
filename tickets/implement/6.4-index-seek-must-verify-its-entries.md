## The one thing that is wrong

`executeIndexScan` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` descends the index tree for a seek key, fetches each entry's row by primary key, and yields that row **without ever asking whether the row it just fetched still implies the entry it came from**. Everything below is a consequence of that single missing step.

The engine is entitled to trust the seek. `getBestAccessPlan` (same file, the `bestHandledFilters` assignment in the secondary-index arm) reports the matched equality filters as handled, and quereus documents what that means at two sites: `makeIndexEqSeekFilterInfo` in `@quereus/quereus/src/vtab/filter-info.ts` ("`aConstraintUsage[].omit` is an OUTPUT of `getBestAccessPlan` — the module's own claim that it applied a filter, which is what earns the engine the right to drop the residual"), and `reattachUnconsumedConstraints` in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts` ("`handledFilters[i] === true` is a module's promise that filter `i` will be enforced somewhere else"). That rule reattaches only claimed constraints the seek did **not** consume; a constraint the seek did consume gets no residual filter. So the module promises and does not deliver.

The `NOTE:` currently above the scan loop says the leak is benign because "Quereus re-applies the predicate". That is not true and, on the evidence of the engine sources above, was never true for a consumed constraint. A second `NOTE:`, inside `executePointLookup`, says in passing that "a secondary index seek keeps one [residual filter]"; that aside is part of the same mistaken picture and is false too.

## Four arms, all observed

Each was reproduced on a single node with the in-memory transactor. Arms A, C and D use `withIndexStagingPatched` (`test/index-staging-patch.ts`) with `stageNewEntryOnly` to leave one known leftover entry behind; arm B needs no leftover at all.

**A — a moved row leaks.** `Usage(Id integer primary key, Token text)` with an index on `Token`. Row 3 moves from `tok-b` to `tok-z` and its `tok-b` entry stays. `select Id from Usage where Token = 'tok-b'` returns row 3, which holds `tok-z`. This is the arm the ticket was opened for and is already pinned red-on-fix in `test/query-helpers.spec.ts`.

**B — a NULL seek value returns a row, on a perfectly healthy index.** `select Id, Token from Usage where Token = ?` bound to `null` returns the NULL-keyed row. Under SQL three-valued logic `Token = NULL` is UNKNOWN and no row matches. **No leftover entry is involved** — this is a wrong answer on a clean index, reachable by any caller that binds a nullable parameter or joins on a nullable key, which makes it the most reachable arm of the four. The engine folds only a *literal* NULL equality (`isLiteralNullEquality`); a dynamic value is left to a per-module runtime guard, and quereus's own memory backend has one on every seek path (`seekKeyHasNull` in `@quereus/quereus/src/vtab/memory/layer/scan-layer.ts`). This module has that guard on the primary-key path (`executePointLookup`) and not on the index path.

**C — a partial-prefix seek returns the same row twice.** `Pair(Id integer primary key, C text, D integer)` with an index on `(C, D)`. Row 2 moves from `('x', 2)` to `('x', 9)` and the `('x', 2)` entry stays. `select Id, D from Pair where C = 'x'` returns `[{Id:1,D:1}, {Id:2,D:9}, {Id:2,D:9}]` — row 2 once per entry. The original ticket predicted this shape for a seek that constrains nothing (an index-served `ORDER BY`); it is in fact reachable on **any** seek whose constrained prefix is shorter than the index, which is an ordinary multi-column-index query. A check that only compares the constrained *prefix* does not close this arm: both entries' rows prefix-match `'x'`.

**D — the value-less seek does not exist.** `select Id from Usage order by Token` does not route through the index at all (no `executeIndexScan` call). Structurally: the secondary-index arm of `getBestAccessPlan` only names an index when at least one equality filter matched, and `runQuery` only sets `scanIndexName` on the modern path when `args.length > 0`. The other way in is the legacy `filterInfo.idxNum >= 10` arm, and `idxNum` is hard-coded to `0` at **every** construction site in `@quereus/quereus/src/vtab/filter-info.ts`, so that arm — along with the `idxNum === 1` and `idxNum === 2` dispatches beside it — is dead. The `width === 0` branch in `executeIndexScan` is therefore unreachable today. Confirmed, not refuted; keep the branch, but say what it is.

## The shape of the fix, and why not the other one

Two directions close arms A and B. **Do not do both.**

*Stop claiming the filters are handled* is one line and lets the engine re-apply the predicate. Reject it: it costs a predicate evaluation per row on every healthy secondary-index seek, forever, to defend against a rare damaged state; it does not close arm C at all (a residual filter does not de-duplicate); and it silently disables two plan shapes that gate on the claim — `ruleKeySetSeek` (`if (plan.handledFilters[0] !== true) return null;`) and the index-nested-loop join seek, which re-applies declined constraints instead of seeking on them. That is a plan-quality regression paid on every query to fix a fault on almost none.

*Verify in the plugin* is the direction to take, and it can be made stronger than the existing `NOTE:` suggests. The `NOTE:` proposes re-deriving the row's index key and prefix-matching it against the seek key. Prefix-matching closes A but not C. **Full-entry verification closes A, C, and the `malformed` orphan class in one predicate**: an entry is `[treeKey, primaryKey]`, and the row it resolves to implies exactly one tree key, `indexEntryKey(createIndexKey(schema, row), primaryKey)`. Requiring those to be equal is decidable, exact, and is *already* the definition `compareIndexToRows` in `src/schema/index-integrity.ts` diffs on. Making the seek the fourth user of that one formula — beside DML staging, index backfill, and the integrity check — means the read path and the check can no longer disagree about what an entry means.

This needs the entry, not just its primary key. `IndexManager.findByIndexIn` yields `entry[1]` and discards `entry[0]`. Add an entry-yielding sibling and let `findByIndexIn` delegate to it, so there is still one range-scan definition:

```ts
/** Every ENTRY in the seek's prefix range, in tree order. findByIndexIn projects this. */
async* findEntriesIn(
	read: TreeReadView<IndexKey, IndexEntry>,
	indexKey: IndexKey,
): AsyncIterable<IndexEntry>;
```

Arm B is separate from all of that and needs its own guard: if any seek arg is `null` or `undefined`, produce nothing — the same three-valued-logic guard `executePointLookup` already carries, for the same reason, with the same comment pointing at `seekKeyHasNull`. It must sit **above** the key framing, because `indexKeyFromValues([null])` frames a perfectly valid NULL-tag key that really does find the NULL-keyed row.

## What will and will not compare equal

The derived key comes from a row that `RowCodec.decodeRow` produced; the stored key came from the row the engine handed DML. These agree, and that is continuously verified rather than assumed: `verifyIndexes` re-derives expected tree keys from decoded rows via `createIndexKey` and diffs them against the stored entries, and every index spec in the plugin runs that diff through `expectIndexAgreesWithScan`. Coverage today spans text, integer, nullable and composite `(text, integer null)` index columns.

Two forms worth keeping in view while writing the check:

- **Numbers.** `serializeIndexValue` routes `bigint` onto the `number` branch, so `5n` and `5` frame identically; a seek bound to either compares equal to a row holding either. It is lossy above `Number.MAX_SAFE_INTEGER` but *self-consistently* lossy, so it cannot produce a false rejection — only, as its own `NOTE:` says, a collision between two huge integers.
- **NULL.** After the arm-B guard no seek constrains a NULL, but a NULL in a *trailing, unconstrained* index column is ordinary and must still compare equal. `createIndexKey` maps `undefined` to `null` and `encodeKeyElement` gives NULL its own bare tag, so it does.

A rejected entry is evidence of index damage that is otherwise invisible from the read path. Count it on the existing `IndexSeekProbe` scratch (a `rejected` field beside `matched`) and print it on the `index:seek` trace line, so a seek that is silently correcting for a broken tree can be seen rather than inferred. Keep `matched` meaning what its comment says — entries the descent produced — and make `rejected` the separate number.

## Documentation that currently asserts the false claim

Five places state, as settled fact, that a leftover entry can never change a result set. They are wrong today and this ticket makes them true; they must be rewritten to describe the check that now makes them true, not merely softened:

- `src/optimystic-module.ts` — the stale-entry `NOTE:` above the scan loop (it becomes a description of the verification, and must stop calling the engine the thing that saves us), and the residual-filter aside inside `executePointLookup` (delete the "a secondary index seek keeps one" claim; it is false).
- `src/schema/index-integrity.ts` — the file header's ORPHANED bullet ("Quereus re-applies the predicate to a row whose value moved").
- `src/plugin.ts` — the `verifyIndexes` doc comment ("re-checks the value of a row that moved").
- `docs/debugging.md` — the paragraph opening "Does an index agree with its table?". Note this one *also* already records the false-UNIQUE consequence ("in a tree enforcing a `unique` column it makes a value look taken when no row holds it"); that consequence is real, survives this ticket, and is filed separately as `bug-stale-index-entry-causes-false-unique-refusal` — link it rather than deleting the sentence.
- `test/query-helpers.ts` — the parenthetical on `expectIndexesIntact` and the structural-arm bullet on `expectIndexAgreesWithScan`. After the fix the structural arm is still the only arm that *sees* an orphan, but the reason changes: not "the seek returns the moved row", but "the seek now skips the entry and returns nothing, so no lookup can distinguish a leftover entry from no entry".

## Tests that pin today's behaviour and must be flipped, not deleted

Both were written to go red the moment this lands and both say so at the site.

- `test/query-helpers.spec.ts`, the case "fails on an entry left behind for a value no row holds any more": the `tok-b` seek is pinned to `[3]` and becomes no rows.
- `test/two-node-index-mutation-sweep.spec.ts`, `expectOrphanSeeks`: a stale-value leftover's seek is pinned to the row its entry points at, and becomes no rows for every leftover — which collapses the helper to a single assertion. The sibling ticket `refuse-concurrent-row-change-loser` (sequence 6.3, ahead of this one) deletes that whole racing branch when it lands, so expect to inherit a smaller job here; if it has not landed, flip what is there.

## New coverage this earns

The four arms above are four instances of one class — "a row an index seek returns does not satisfy the seek" — and the class deserves a test that outlives the instances. Write one generalized spec that, for a matrix of index shapes (single-column text, single-column integer, composite `(text, integer null)`) and seek forms (literal, bound parameter, full-width, partial prefix), asserts of every index-routed seek that **every row returned satisfies the seek's equality predicate and no primary key is returned twice** — run once over a healthy table and once over a table with a deliberately staged leftover entry. That is the property the module's `handledFilters` claim actually promises, and it catches the next instance of this class without anyone having to think of it.
