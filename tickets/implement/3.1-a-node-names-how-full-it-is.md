# A node names how full it is

## Why

`StorageAccount` (`packages/db-p2p/src/storage/storage-account.ts`) is the node's one measurement of its disk, and `packages/db-p2p/docs/storage.md` §9 is its design. What it does not have is a *reading* of that measurement: the only consumer that reacts to fullness is the ring decision, and the two figures it reacts at — 85 % used to move outward, 40 % to move back in — are literals in the `RingSelector` constructor call in `libp2p-node-base.ts`. An operator cannot change them, and nothing else in the node can ask whether the node is under pressure, so every step this ticket's siblings add (evict, shed, delete, refuse) would otherwise invent its own threshold against its own reading.

Two smaller faults sit in the same place:

- **Low space advertises the most work.** `determineRing` answers `-1` when the node's available bytes are below `minCapacity` (100 MiB), and `createArachnodeInfo` then clamps `-1` to ring 0 — the whole keyspace. A node with almost no room tells the network it will take everything.
- **The read cache only shrinks when something is read.** `cacheBudgetBytes` already makes the cache a tenant of the allotment, so its budget falls to 0 as other use fills the node, but `BlobCacheBudget` is enforced only after a read or fetch that pulled something (the `NOTE:` above that class records this). A node filling up with blocks therefore keeps every cached blob until some read happens to arrive.

## What to build

### One reading, one vocabulary

A new module, `packages/db-p2p/src/storage/storage-pressure.ts`, holding the node's one answer about its own fullness. It reads `StorageAccount` and nothing else, is built once per node on either role beside the account, and is reachable as `node.storagePressure`.

The reading is a named **stage**, ordered from least to most pressure, so a consumer can ask "at least shedding?" rather than comparing fractions of its own:

| Stage | When | What acts on it |
| --- | --- | --- |
| `unknown` | the node cannot measure its storage: no allotment configured and the backend reports no free space, so `capacity().totalBytes` is absent | **nothing.** No eviction, no shedding, no deleting, no refusing — the node behaves exactly as it does today, and the start-up `WARN:` line already tells its operator why |
| `slack` | measured use is below `reclaimBelow` | the ring decision may move inward (today's `moveIn`) |
| `steady` | between `reclaimBelow` and `shedAbove` | nothing |
| `shedding` | measured use is above `shedAbove` | the ring decision moves outward (today's `moveOut`); the read cache is enforced; the released-block sweep runs |
| `refusing` | measured use is above `refuseAbove` | everything `shedding` does, and every refusal gate the sibling tickets add |

`usedBytes` is unclamped, so a node past its allotment reads above 1.0 and lands in `refusing` — which is the point, and why every consumer of the account is already required to tolerate `usedBytes > totalBytes`.

The module exposes two reads, and the difference between them is load-bearing:

- `read()` — asks the account (one memoized `capacity()` call), answers the stage together with the capacity it was derived from, and logs one line **when the stage changes**, naming the new stage, the measured use, the effective total and the threshold that was crossed.
- `stage()` — the **last** stage read, synchronously, with no I/O at all. This is what the refusal gates in the sibling tickets read: a push handler, an announce handler and a promise vote are inbound paths that must not block on a directory walk. Before the first `read()` it answers `unknown`, so a node refuses nothing until it has measured itself once.

Polling faster than the account's memo would buy nothing — `capacity()` is memoized for `usedBytesCacheTtlMs` (60 s by default) with single-flight — so one sample per tick is the cadence, and the staleness that implies is bounded and deliberate. Record it at the site:

```
// NOTE: `stage()` answers the last sample, so between samples a node can accept up to one
// sample-interval's inbound data past its limit. The gap between `refuseAbove` and the
// allotment is the headroom for exactly that (and for pends already approved). If a node is
// ever seen well past its allotment between samples, add the bytes accepted since the last
// sample to the reading rather than scanning on the gate.
```

### Thresholds the operator sets

All three move into one place, beside the allotment they are fractions of: `NodeOptions.storageAllotment.thresholds`, with `reclaimBelow` (default 0.40), `shedAbove` (default 0.85) and `refuseAbove` (default 0.95). They belong with `storageAllotment` rather than under `arachnode` for the reason the allotment itself does — they are about this machine's disk, and a client node has an allotment and an account exactly as a serving node does.

Validated at node construction, throwing rather than clamping, the rule `storageAllotment.bytes` already follows (`assertStorageAllotmentBytes`): each must be a finite number strictly between 0 and 1, and `reclaimBelow < shedAbove < refuseAbove` must hold. An operator who inverted two of them is told, not quietly given a node that sheds and reclaims at once.

`RingSelectorConfig.thresholds.moveOut` / `.moveIn` keep their names — "move" is the selector's own vocabulary — and are fed from `shedAbove` / `reclaimBelow`, so there is one figure with two readers rather than two figures that can disagree.

`refuseAbove` is deliberately **below** the allotment, and the gap is not slack: it is the headroom for pends a member has already approved, for the host's own writes (which this ticket's sibling refuses only at the allotment itself), and for the sampling window above.

### Low space advertises less work, not more

`determineRing` answers the **deepest ring it allows** (16, its existing cap) rather than `-1` when available bytes are below `minCapacity`, and the `-1` sentinel is removed: `createArachnodeInfo`'s `Math.max(0, ringDepth)` clamp and its `ringDepth >= 0` partition guard go with it, since every answer is now a real ring.

Settled this way rather than the alternative — advertising no storage role at all — because leaving storage entirely is a release of *every* range the node holds, which the handoff protocol would then have to carry under its replication floor; a node short of room must not hand everything away at once. Ring 16 is the narrowest slice the ring model has, and the node keeps serving what it already holds.

Two consequences to state rather than hide:

- A running node that falls below the minimum does **not** jump to ring 16. `shouldTransition`'s single-step rule still moves it one ring per dwell. The below-minimum answer is taken at bootstrap, where there is no handoff to carry, and by any other one-shot caller — which is exactly where the old `-1 → ring 0` fault lived.
- A node at ring 16 can never move further out: the smoothed depth `d` is clamped at 16, so `d >= 16 + 1 - h` is unreachable. Ring 16 is the floor of advertised responsibility, and from there the only remaining lever is refusing.

And the honest limit of shedding, which `docs/arachnode-ring-handoff.md` § Part 2 already records for the move-in case: **narrowing the ring reduces what the node is responsible for restoring and holding, not which cohorts it is in.** A block's cohort comes from `findCluster` — FRET proximity plus network membership — with the arachnode ring depth playing no part. So shedding reduces one kind of inflow, and refusing is what covers the rest. This is why the parent ticket's order is shed, then delete, then refuse, and not shed alone.

### What a node at its limit can and cannot free

The docs section this ticket writes must say this plainly, because it is the honest limit of the whole chain. A node at the `refusing` stage has four levers, and each has a ceiling:

- **Evicting the read cache** frees at most what the cache holds, which is capped at an eighth of the allotment and is often far less.
- **Narrowing the ring** frees only once the handoff confirms other holders, which needs peers with room.
- **Deleting what it released** frees only what narrowing handed over.
- **The blob reclaim pass** frees only blobs no reference tree lists, after a seven-day grace.

None of the four touches **old revisions of blocks the node is still responsible for**, and on a long-lived node that is where the bytes accumulate. So a node whose use is mostly block history **cannot get back under its allotment** with these mechanisms: it reaches `refusing` and stays there until an operator raises the allotment or its peers take its ranges. The lever it needs is backlog `feat-cold-range-transform-offload` — offloading cold history and restoring it from the network on demand — and an arm has been added to that ticket saying the pressure stage is what should drive it. Nothing new needs filing; what needs saying is that the chain is incomplete without it, in the docs rather than only in a ticket.

### The cache shrinks as the node fills

When `read()` finds the stage at `shedding` or above, it requests one cache enforcement (`BlobCacheBudget.request()`, which already logs rather than rejects). The budget figure itself needs no change — `cacheBudgetBytes` already falls to 0 as other use fills the allotment — so this supplies only the trigger the cache was missing. The `NOTE:` above `BlobCacheBudget` that asks for exactly this call from the hold-release sites can now name the pressure tick as its other caller.

## Edge cases & interactions

- **Unknown total.** Every arm must read `unknown` as "do nothing", never as 0 and never as full. A transient free-space read failure already leaves the location figure absent for that scan rather than 0, for precisely this reason (`IRawStorage.getApproximateBytesFree`), so a node can drop into `unknown` for one scan and back out. Verified by a test (below), because reading unknown as full is the failure that would have a node shed and refuse on a figure nobody measured.
- **A rejecting `capacity()`.** `read()` must not reject, and must not let a one-off scan failure disarm the gates: keep the last known stage and log the failure. Only an absent `totalBytes` from a *successful* scan means `unknown`. Verified by inspection at the one call site.
- **A node with no FRET, or with arachnode disabled.** Today's 60-second tick lives inside the arachnode `if (fret)` block, but a client node — which has an allotment, a cache and blobs — must still read its pressure. Give the pressure module its own timer (`armUnrefTimer`, as the other node-owned timers use), torn down through the node's `stop` wrapper chain, and have the arachnode tick read `stage()` rather than scanning again.
- **Both timers on one memo.** The pressure timer and the arachnode tick both end up asking `capacity()`; the account's single-flight memo makes the second free. Nothing new is needed — but do not build a second `StorageAccount`.
- **Thresholds on an unmeasurable node.** Validation is over the numbers alone, so it runs and throws even on a node that will read `unknown` for its whole life. That is right: a typo is a typo.
- **The 0.85 figure is cited in three other places.** `CACHE_ALLOTMENT_SHARE`'s doc comment, `packages/db-p2p/docs/storage.md` §9 and `docs/arachnode-ring-handoff.md` §1.2 each reason about "the 85 % `moveOut` threshold". Once it is configurable each becomes "the default 85 %"; the argument they make (an eighth of the allotment cannot reach it) holds for the default, and that is what the sentences should now say. Verified by inspection of the three sites.
- **Stage flapping.** Refusing is immediate and undamped by design, so a node hovering at `refuseAbove` logs a stage change per sample. One line per sample at worst, and only while hovering; the ring arm keeps its own EWMA, dead-band and dwell. Accepted — do not add a second damping layer here.
- **A node that starts already over its allotment.** The first `read()` lands straight in `refusing`, before the node has evicted or shed anything. That is the intended order: refusing new data from others is the one reaction that needs no handoff, and the sibling steps then work the node back down.

## Tests

One spec, `packages/db-p2p/test/storage-pressure.spec.ts`, over the pure stage function with a stubbed capacity:

- An absent `totalBytes` reads `unknown` whatever the measured use is — including a use above 0 — and `unknown` is ordered below every acting stage.
- `usedBytes` above `totalBytes` reads `refusing`, and each threshold boundary falls on the side the table above says.

Nothing else here earns a test: the threshold validation has the shape `assertStorageAllotmentBytes` already has, the wiring is wiring, and `cacheBudgetBytes` is already specced.
