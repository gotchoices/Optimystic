# A member hashes a committed block once

Part of GitHub #63; measurements and the split are in `a-consensus-record-is-serialized-once-per-delivery`. On the bench's profile (8 × 256 KiB blobs, two nodes in one process, 7.0 s of CPU) the member's storage apply was 18%, of which these three passes are about 9%:

| pass | CPU | what it repeats |
|---|---|---|
| `cloneDecoded` of the base block and the pending transform in `previewCommitDigest` | 0.21 s | a JSON round trip of values the store has just decoded fresh |
| `canonicalBlockHash` in `persistProofIfContentMatches` | 0.36 s | the digest `previewCommitDigest` computed for the same content on the promise round |
| `structuredClone` inside `transformForBlockId` when `StorageRepo.pend` saves each block's pending record | 0.07 s | a deep copy that is encoded to JSON immediately and then dropped |

## 1. No clone in the preview

`previewCommitDigest` clones the base and the transform because `applyTransform` mutates the block in place and puts `transform.insert` into the result by reference. Both values were just decoded by the store, and every store in this repository is the `KvRawStorage` kernel, which decodes a fresh object on every read (internals *Storage Returns References*, enforced by the raw-storage conformance suite). So nothing else holds them, and the clone protects nothing. Drop it, and rewrite the comment and `NOTE:` there to state the rule it now relies on: the preview's inputs are owned by the preview because the store decodes per read.

Confirm the premise for every path that feeds it: `BlockStorage.getBlock` (including `materializeBlock`, which replays transforms over a decoded materialization), `BlockStorage.getPendingTransaction`, and `CachedRawStorage` (`cached-raw-storage.ts`), which adapts an inner `IRawStorage` to a driver — if its inner store can hand out a live object, the decode-per-read rule must still hold at the kernel above it; say in the handoff which it is. If any reachable path can return an object something else retains, keep a clone on that path only.

## 2. The commit reuses the preview's digest

On the promise round `previewCommitDigest` materializes the pending transform over this node's `latest` and hashes it; at commit `internalCommit` materializes the same transform over the same base (its fork guard, `guardCommitBase`, makes sure of that) and `persistProofIfContentMatches` hashes the result again to decide whether to keep the proof. The content is a function of the pending record for `(blockId, actionId)` and of the base revision, so the first digest can be reused when neither has changed.

A memo on `StorageRepo`: a bounded `LruMap` (the db-core one; 1024 entries is plenty — one entry per block of each in-flight commit) keyed `blockId` + `actionId`, whose entry is either a **reservation** (a fresh token object) or a **result** `{ token, rev, base, digest }`, where `base` is the base's `{ rev, actionId }` (from `latest`) or `'insert'` for a base-independent transform:

- `previewCommitDigest` sets a new reservation for the key **before** reading the pending transform, and after computing the digest writes the result only if the map still holds its own reservation (same token object). It writes nothing when it computed no digest (tombstone, unmaterializable base, no pending record).
- `StorageRepo.pend`, at its one save of a pending record for the key, deletes the entry. A re-pend that lands while a preview is computing therefore removes the reservation, and the preview's stale digest is never written. Deleting the record (cancel, the dead-claim sweep, Invariant P deletions) needs no hook: no commit can apply a record that is gone, and a new record arrives only through `pend`, which clears the key.
- `persistProofIfContentMatches`, on the `internalCommit` path, uses a result only when it is for the same `rev` and the same base the commit applied over (`latest` read in `internalCommit`, or `'insert'` when the transform carries an insert); otherwise, and on any miss or eviction, it hashes as today. It deletes the entry either way. The back-fill path (`saveReplicatedBlock`'s non-advancing branch) keeps hashing.
- Comparing the reused digest with the declared one is unchanged, so a mismatch still stores no proof and logs `commit:proof-digest-mismatch`.

A miss only costs the hash it costs today; a wrong hit would store a proof for content this node does not hold, so every condition above fails toward a miss.

## 3. No clone before the pending record is encoded

`StorageRepo.pend` splits the request's transforms per block with `transformForBlockId`, which deep-clones the insert and the updates (that is its contract, internals *Transform Ownership*), and passes the result to `BlockStorage.savePendingTransaction`, which encodes it to JSON. Confirm that `savePendingTransaction` and everything it calls neither keep nor change the transform, then project without cloning on this one path: add a sibling to `transformForBlockId` in `packages/db-core/src/transform/helpers.ts` that returns the per-block view sharing the request's values, documented as "for a caller that serializes the result at once and keeps nothing" — and add it to the internals *Functions That Share* table. Do not change `transformForBlockId` itself.

## Edge cases & interactions

- **Re-pend during a preview** (same action, new transform — a retry at another revision): covered by the reservation; this is the one branch worth a test, at the `StorageRepo` level with a real memory store: preview a pend, re-pend the action with a different transform while — or after — the preview runs, commit, and assert the stored proof follows the content actually committed (stored when it matches the declaration, absent with `commit:proof-digest-mismatch` when it does not). Sequential calls suffice to reach the "re-pend after preview" ordering; the in-flight ordering is covered by the token rule and can be argued by inspection.
- **Base moved between preview and commit** (a replica advanced `latest`): the result's `base` no longer matches, so the commit hashes. The fork guard refuses the commit in most such cases anyway.
- **Preview never ran** on this member (it abstained, or the record reached it only at commit): miss, hash as today.
- **Several blocks of one action** each have their own key.
- **Memory**: entries are deleted at commit; ones for actions that never commit age out of the LRU. The bound is the `NOTE:` site.
- **Concurrency**: the preview runs without the block latch, `pend` and `internalCommit` under it; the token check is what makes the unlatched write safe, so keep the reservation set before the first `await` that reads storage.
