# A SQL commit reports its durability

GitHub issue #26: a chat app marks a message "not yet delivered" while its commit is held only by its own machine. This ticket hands the app the durability of each SQL commit; `a-sql-commit-learns-when-it-becomes-fully-held` then tells it when a pending one becomes fully held. Folds in the former backlog ticket `feat-a-sql-commit-reports-durability` (deleted).

## Where it is lost today

db-core now reports who holds every write (`multi-collection-commit-reports-durability`, landed): `Collection.sync` / `Tree.sync` resolve to a `WriteDurability`, and `TransactionCoordinator.commit` / `TransactionSession.commit` to a `TransactionDurability` (per collection, plus `overall`, the weakest). The plugin's `TransactionBridge.commitTransaction` discards it on all three of its commit routes:

- session mode: `this.session.commit()`'s `ExecutionResult.durability`;
- the batched legacy commit (two or more staged trees): `coordinator.commit(...)`'s return in `commitBatchLegacy`;
- the per-tree legacy sweep: each `tree.sync()`'s result in `sweepDirtyTreesLegacy` — which is also the route of the **common single-table write**, since `legacyBatch` returns `undefined` for fewer than two staged trees.

## Channel: a per-commit listener (decided)

Quereus's commit hook returns `void` to the SQL caller, so the plugin needs a side channel. Options weighed:

- **A per-commit listener (chosen).** `register(...)`'s returned object gains `onCommitDurability(listener): () => void` (idempotent unsubscribe). The bridge calls every listener once per successful commit that wrote something, after its own state is torn down and before `commitTransaction` returns. Race-free: each call carries its own report, and because Quereus serializes writers behind its exec mutex, every report delivered while a host's `await db.exec(...)` is running belongs to that exec — which is how a wrapper such as cadre-core's `StrandDatabase` can hand the answer back from its own `exec`.
- **A "last commit's durability" property (rejected).** Ambiguous: a transaction that wrote nothing (a read-only transaction, or a statement that matched no rows) has no durability — clear the property on it, and an intervening read-only commit erases the answer; keep it, and a no-op insert reports the previous write's durability, and any other async task's commit between the host's `await` and its read replaces it.
- **An event on the change-notification path (rejected).** That path is per collection and keyed by storage commits on the hosting node, not by SQL transaction; mapping back would be the hard part with nothing gained.

One bridge exists per `register` call (one `Database`), so the listener set lives on the bridge and the plugin object forwards to it.

## The report

```ts
/** What one SQL commit wrote, and who holds it. */
export interface SqlCommitDurability {
	/** The committed transaction's id: what `StampId()` returned inside it (`TransactionState.stampId`).
	 *  A host that wants to tag rows with it selects `StampId()` in the transaction. */
	readonly transactionId: string;
	/** db-core's answer, per collection (each table's main tree and each index tree) and overall.
	 *  Test "saved" through `overall !== undefined && isFullyDurable(overall)`; an absent `overall`
	 *  means a collection is saved with its holders unknown — show the commit as pending. */
	readonly durability: TransactionDurability;
	/** The same, per table — keyed by the qualified name `schema.table` — folding each table's
	 *  collections with `mergeDurability`; `undefined` when any of that table's collections is
	 *  unknown. A collection the bridge cannot name a table for (a test double) is left out here
	 *  but stays in `durability`. */
	readonly tables: ReadonlyMap<string, WriteDurability | undefined>;
}
```

Building it, per route:

- **Session**: `result.durability` as is.
- **Batch**: the `TransactionDurability` `coordinator.commit` returns (have `commitBatchLegacy` return it).
- **Sweep**: fold each successful `tree.sync()`'s `WriteDurability` with `recordCollectionDurability` into a map keyed by `tree.getCollection?.()?.id ?? treeLabel(tree, i)`, then `transactionDurability(map)`. A sync resolving `undefined` (the tree had nothing staged) adds no key. `DirtyTree.sync`'s declared type becomes `Promise<WriteDurability | undefined>` (test doubles resolving nothing still satisfy it); rewrite its doc comment, which currently says the bridge consumes neither.
- In every route, a commit whose answer is `undefined` / an empty map wrote nothing → **no report, no listener call**.

Table names: `registerCollection(collection, table?)` records `collection.id → "schema.table"` beside the registry (the four call sites in `optimystic-module.ts` know their table). The `tables` view is built from that map at report time.

### Partial commits

A commit that throws reports through its error, never through the listener: `CoordinatorPartialCommitError` already carries `durability` for its committed half. `PartialCommitError` (the sweep's tear) gains the same: a `durability?: TransactionDurability` built from the trees it persisted (folded the same way as the success path), so both partial-commit errors answer the same question the same way. Absent only if no persisted tree reported one (test doubles).

## Listener discipline

- A listener that throws is logged (`txn-bridge` logger) and the remaining listeners still run; it never turns an acknowledged commit into a reported failure. Same rule as `onCollectionChange` / `onBlockDurabilityReached`.
- Listeners are called synchronously, in registration order; the report is frozen data (copy maps; never hand out the bridge's own).
- Zero listeners → the report is not even built (one `size` check), so hosts that do not care pay nothing.

## Edge cases & interactions

- **Read-only transaction / autocommitted `select`**: no dirty trees (legacy) or `durability` undefined (session) → no call. Verified by the test below.
- **Session mode commits the whole registry**: the coordinator reports only collections it actually wrote, so clean tables never appear. By inspection (the coordinator's contract).
- **`overall` absent** (a collection saved with unknown holders): reported as is; `tables` shows `undefined` for its table. By the type.
- **Two tables on one collection id** (the case `legacyBatch` routes to the sweep): both trees map to one key; `recordCollectionDurability` merges them weakest-first. By inspection of `recordCollectionDurability`.
- **A sweep tree that is a test double without `getCollection`/`describe`**: keyed by its positional label, absent from `tables`. By inspection.
- **`CoordinatorPartialCommitError` / `PartialCommitError` paths**: listener not called; the degraded-latch handling in `commitTransaction`'s catch is unchanged. By inspection.
- **Savepoint rollback then commit**: a tree rolled back to clean resolves `undefined` from `sync` (or is absent from the coordinator's report) — no key. By inspection.

## Tests

One spec, `packages/quereus-plugin-optimystic/test/sql-commit-durability.spec.ts`, on the plugin's `local`/`test` transactor fixtures the other bridge specs use:

- a single-table insert (sweep route) delivers one report whose `durability.collections` has the table's main collection and whose `tables` has `main.<table>`;
- a table with a secondary index (batch route) delivers one report with both collections under one table;
- a session-mode commit (if an existing spec already builds a session-mode bridge cheaply, reuse its setup; otherwise skip this arm — the route is one line) delivers the coordinator's `durability`;
- a `select` in its own autocommit delivers nothing;
- a listener that throws does not fail the commit and does not stop a second listener.

The exact quorum values depend on the fixture's transactor (a `local` transactor answers `local`), so assert presence and shape, not a class.
