# Storage drivers can carry values as text

GitHub #51 (first of two tickets; `react-native-reads-decode-utf8-in-native-code` builds on this).

## Why

Every value crosses `RawStoreDriver` as a `Uint8Array`, and `KvRawStorage` turns it into an object with `TextDecoder` then `JSON.parse` (`decodeJson` in `raw-store-codec.ts`). On React Native, Hermes has no native `TextDecoder`, so that decode runs in the host's JavaScript polyfill: profiled on a Galaxy S7 as the largest single cost of an offline-mode send (about 740 ms of a 2.66 s busy window, 2.4–2.8 s self time over 45 s). `rn-leveldb` can return a stored value as a JavaScript string decoded in native code (`getStr`, iterator `valueStr`). For that string to be useful it has to reach the kernel's decode without being turned back into bytes on the way, and the values the storage layer keeps in memory (the write group's unflushed overlay, the read cache) have to be text too, or a hit on them pays the JavaScript decode anyway.

This ticket adds the ability. The React Native backend adopts it in the follow-on ticket.

## Design (settled)

### A driver's value representation is a type parameter

`RawStoreDriver<V extends StoredValue = Uint8Array>` where `StoredValue = Uint8Array | string`. Every value position in the driver (each `get*` result, each `put*` argument, `rangeRevisions` rows) is `V`. A string value is the text the stored UTF-8 bytes decode to — the same logical value, a different in-memory form. Every existing driver is unchanged: it implements `RawStoreDriver`, which is `RawStoreDriver<Uint8Array>`.

A composition is homogeneous in `V`: a text kernel over a text cache over a text write group over a backend whose reads return text. The type checker refuses mixing them. Nothing ever branches at run time on `typeof value`.

Rejected alternatives, recorded for the reviewer:

- **A `Uint8Array | string` union at the driver boundary.** Every driver would have to accept strings on its writes, and every consumer would branch per value. That widens every backend (fs, ns, web, memory) for one backend's benefit.
- **Optional string-returning twins of each read** (`getMetadataText?` and six more). Seven optional members on the driver, each to be forwarded by every wrapper; a forgotten forward silently restores the slow path. And it does nothing for values held in memory, which are bytes.
- **Strings everywhere, encoding at each backend's own boundary.** Correct, but changes every backend and how SQLite and IndexedDB store values; out of proportion to the problem.

### The codec is chosen with the representation

`raw-store-codec.ts` gains:

```ts
export type StoredValue = Uint8Array | string;

/** How a driver's values are represented in memory, and what the kernel and the wrappers need to know about them. */
export interface ValueCodec<V extends StoredValue> {
	encodeJson<T>(value: T): V;
	decodeJson<T>(value: V): T;
	encodeActionId(actionId: ActionId): V;
	decodeActionId(value: V): ActionId;
	/** The bytes the value takes on disk, or an estimate; paces the write group's `maxUnsyncedBytes`. */
	storedBytes(value: V): number;
	/** The bytes the value takes in memory, or an estimate; charged to the read cache's pool. */
	residentBytes(value: V): number;
	/** The value's UTF-8 bytes, for a backend that persists bytes. */
	toBytes(value: V): Uint8Array;
}

export const bytesValueCodec: ValueCodec<Uint8Array>;   // today's functions; storedBytes = residentBytes = length; toBytes = identity
export const textValueCodec: ValueCodec<string>;        // JSON.stringify / JSON.parse; action id as-is; storedBytes = length; residentBytes = length * 2; toBytes = TextEncoder
```

`textValueCodec` never constructs a `TextDecoder`. `TextEncoder` is native in Hermes. `storedBytes` for text is the UTF-16 length: exact for ASCII, which the JSON this layer stores almost entirely is, and an undercount for other characters. It only paces flushes, so an undercount is harmless. `residentBytes` for text follows the cache's existing `CHAR_BYTES = 2` rule for strings. Keep the existing free functions (`encodeJson` &c.); the journal record codec and `RawStorageDriverAdapter` keep using the bytes forms.

### Where each component takes `V`

- **`KvRawStorage<V>`** takes the driver and its codec. A bytes driver may omit the codec, so every existing `new KvRawStorage(driver)` call site compiles unchanged; any other `V` must name one. A conditional rest parameter does this without a cast:

  ```ts
  constructor(driver: RawStoreDriver<V>, ...codec: Uint8Array extends V ? [ValueCodec<V>?] : [ValueCodec<V>])
  ```

  (or overloads — the implementer's choice, as long as omitting the codec for a text driver fails to compile). All decode and encode calls go through the codec. `IRawStorage` is unchanged: it is object-level.
- **`CachedStoreDriver<V>`** caches `V` (`CachedBytes` becomes `V | null`, `RevMapState.byRev` a `Map<number, V>`) and charges `residentBytes` wherever it charges `.length` today. It takes the codec the same way as the kernel (omittable for bytes). `promote`'s `pendingBytes instanceof Uint8Array` test becomes "a value is present" (not `null`, not `undefined`); as written it would silently drop the transactions entry for every text value.
- **`WriteGroup<K, V = Uint8Array>`** holds `V` in its overlay: `WriteGroupEntry<K, V>`, `WriteGroupSink<K, V>`, `OverlayValue<V>`. It takes a `storedBytes` measure as an option, defaulting to `byteLength` for bytes. `LevelDBKVStore` and `FileKVStore` keep the default and do not change in this ticket.
- **`WriteGroupDriver<V>`** is a `RawStoreDriver<V>` over a `BatchBackend<V>`. Its overlay holds `V`. Converting to bytes happens **here**, when a sealed group goes to the backend: the sink it hands its `WriteGroup` maps each entry's value through `codec.toBytes` and calls `backend.commit` with byte entries. For bytes `toBytes` is the identity, so nothing changes. `promote` reads the pending `V` and puts it back as the transactions entry, unconverted.
- **`BatchBackend<R = Uint8Array>`**: only its *reads* (`get`, `rangeRevisions`) return `R`. Its *writes* (`commit` entries, the `WriteGroupSink<StoreKey>` it extends) stay `Uint8Array`. So fs, ns and web backends do not change, a journal record's values are always bytes, and the journal record codec does not change. **`JournalStore<R>`** follows (it extends `Omit<BatchBackend<R>, …>`), and **`JournalBatchBackend<R>`** passes its store's reads through. Its held records are the byte entries `WriteGroupDriver` produced. For a text composition they are therefore new arrays, not the overlay's own, so the `NOTE:` at `held` ("holding them here costs the …") must say the sharing holds for bytes compositions only. On React Native that path never runs today, because the handle cannot sync, so nothing is ever journaled.
- **`MemoryStoreDriver`**, **`RawStorageDriverAdapter`**, **`CachedRawStorage`**, `withReadCache`: unchanged, bytes only.

### Writes stay bytes on disk

A text composition still writes `TextEncoder` output to its backend, so what lands on disk is byte-identical to what the bytes path writes today, and no data migration is needed. Passing strings straight to the engine (ticket item 5: `rn-leveldb`'s `put` accepts a string) is not taken: it would hand Hermes's own UTF-16→UTF-8 conversion any ill-formed string (an action id is chosen by whoever originates a write and may hold a lone surrogate), which `TextEncoder` normalises to U+FFFD. And `TextEncoder` is native in Hermes, so the saving is unmeasured. Revisit only if `TextEncoder.encode` shows in a device profile.

### The clone invariant stays structural

docs/internals.md *Storage Returns References* rests on "a get decodes a fresh object, a save stores an independent snapshot". That still holds for text: `JSON.parse` builds a new object on every read, and a string is immutable, so a cached or overlaid string cannot be changed by anyone holding it. The invariant is now stronger than for bytes, which a holder could mutate in place.

## Edge cases & interactions

- **Every existing composition is byte-for-byte unchanged.** Bytes is the default at every seam. Verified by the existing suites (conformance over memory, cached, write-group and journal compositions; the fs/ns/web/rn backend suites; `packages/upgrade-check`) passing with no edits to their compositions. The only edits allowed in them are type annotations, if any.
- **A text composition passes the whole conformance suite**, including the cached composition and the drain-before-yield and clone-on-read cases. This is the one new test: register `rawStorageConformance` once over `KvRawStorage<string>` → `CachedStoreDriver<string>` → `WriteGroupDriver<string>` → `JournalBatchBackend<string>` → a memory journal store whose reads return text. For that store, give `MemoryJournalStore` (or a small test-only decorator in `src/testing/`) a text-reads mode that decodes its stored bytes with Node's `TextDecoder`. It is a test double and Node has one. Put the registration beside the existing journal compositions in `test/journal-batch-backend.spec.ts`. Run it with the store's durability at both `'power-loss'` and below, so both the journaled path and the apply-at-once path see text overlays converted at commit.
- **A cache hit on a text composition is the cached string**, and so is an overlay hit. Verified by inspection: no codec call sits between the cache or overlay and the kernel's `decodeJson`.
- **Omitting the codec for a text driver does not compile.** Verified by a type; no test needed beyond the build.
- **`promote` on a text composition keeps the transactions entry in the cache** (the `instanceof Uint8Array` site above). Covered by the conformance case "promotePendingTransaction moves pending → committed atomically" running over the cached text composition, which reads the transaction back.
- **Pool accounting for text** charges `residentBytes`, so a store of text values is not undercounted against the shared pool's budget. Verified by inspection of every `.length` charge site in `cached-store-driver.ts`.
- **`maxUnsyncedBytes` over text** counts `storedBytes`. It undercounts non-ASCII by at most 3×, which only delays a size-forced flush; acceptable.
- **The journal path over text**: a relaxed flush on a text composition whose store can sync appends records of bytes that `WriteGroupDriver` converted. Recovery decodes them as bytes and applies them through the store's byte writes, unchanged. Covered by the conformance registration at `'power-loss'`.
- **`yarn check:rn`** still bundles and compiles (no new module-scope `TextDecoder`; the `NO_MODULE_SCOPE_TEXT_DECODER` lint rule holds).
