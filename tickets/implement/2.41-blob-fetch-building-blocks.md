# Blob fetch building blocks

The first half of the plan for `feat-blob-fetcher-verifies-and-resumes` (the fetcher itself is that ticket, which depends on this one). Everything here is used only by the fetcher; nothing here dials a peer. Four pieces, each small and independently reviewable.

## `blob-holders.ts`: who to ask, and what a failed round means

`packages/db-p2p/src/blob/blob-holders.ts`.

```ts
export interface BlobHolderDeps {
	selfPeerId: string;
	/** buildBlobProtocol(prefix). */
	blobProtocol: string;
	keyNetwork: Pick<Libp2pKeyPeerNetwork, 'findCluster' | 'peersServing'>;
	membership: NetworkMembershipGate | undefined;
	reputation: Pick<IPeerReputation, 'isBanned' | 'isDeprioritized'>;
	/** Whether this node has an open connection to the peer; the node binds it to libp2p's getConnections. */
	isConnected: (peerId: string) => boolean;
}

/** The peers to ask for `ref`'s pieces, best first. */
export async function blobHolderCandidates(deps: BlobHolderDeps, ref: BlobRef, knownHolders?: readonly string[]): Promise<string[]>;
```

The order: `knownHolders` first, in their order; then the members of `keyNetwork.findCluster(routingKeyForBlob(ref))` not already listed, connected peers before the rest (stable within each group). Then remove: self; any id `peerIdFromString` refuses (logged once per call as `holders:bad-peer-id`, since the fetcher dials by parsed id and a caller-supplied hint can be anything); any peer `admittedBy(membership, peer)` refuses; any peer `reputation.isBanned`; and keep only `keyNetwork.peersServing(blobProtocol, …)`. Finally move `reputation.isDeprioritized` peers to the end, keeping their relative order. A `findCluster` that throws is logged (`holders:cohort-lookup-failed ref=… err=…`) and treated as an empty cohort; `knownHolders` still count.

Why the membership predicate is applied here and not left to the key network: `knownHolders` do not come from `findCluster`, and `peersServing` deliberately does not apply the predicate (its doc comment says the caller's candidate filter does). This function is the one place the fetcher chooses a peer to dial, so the predicate has one site. Put a one-line comment saying so at the filter. `feat-blob-pieces-move-between-machines` reuses this function for the `stat` probe, so keep its signature as above (it will close over `deps`).

Logger: `createLogger('blob:fetch')` (the namespace the fetcher logs under; the fetcher ticket documents it).

```ts
export type PieceAnswer = 'not-held' | 'no-answer' | 'corrupt';
export interface PieceOutcome { readonly peer: string; readonly answer: PieceAnswer }

/** What one unavailable piece's attempts in a round amount to: one entry per candidate of the round. Empty means there was no candidate. */
export function unavailableOutcome(attempts: readonly PieceOutcome[]):
	| { readonly error: 'unavailable'; readonly reason: 'not-held' | 'peers-unreachable' | 'cohort-unreachable' }
	| { readonly error: 'corrupt' };
```

The plan's signature took a `candidateCount` as well; it is redundant once the caller passes one entry per candidate (empty = no candidate), so it is dropped. The rows, checked in this order:

| Attempts | Result |
|---|---|
| none | `cohort-unreachable` (nobody could be asked) |
| every one `no-answer` | `cohort-unreachable` |
| at least one `corrupt`, every other one `not-held` | `corrupt` (a holder served bad bytes and no other holder could supply them) |
| any `no-answer`, the rest `not-held` or `corrupt` | `peers-unreachable` (a silent holder may still have it) |
| every one `not-held` | `not-held` |

Pure, no logging. `not-here` is never produced here: it belongs to a read with `from: 'here'`.

## `blob-get-slots.ts`: stream limits

`packages/db-p2p/src/blob/blob-get-slots.ts`:

```ts
export type FetchPriority = 'foreground' | 'background';

export interface BlobGetSlotLimits { foreground: number; background: number }

export class BlobGetSlots {
	/** Defaults: MAX_BLOB_FOREGROUND_GET_STREAMS and MAX_BLOB_BACKGROUND_GET_STREAMS. */
	constructor(limits?: Partial<BlobGetSlotLimits>);
	/** Waits for a slot to `peer` at `priority`; resolves with an idempotent release. Rejects with `signal.reason` when the signal aborts first (at once when it already has). */
	acquire(peer: string, priority: FetchPriority, signal?: AbortSignal): Promise<() => void>;
}
```

Rules: per peer, at most one open `get` stream per priority; per node, at most the limit of each priority. The two priorities are separate pools, so a foreground request never waits for a background stream: it opens its own stream beside the background one and the stream multiplexer interleaves them frame by frame. The server's allowance (`MAX_BLOB_INBOUND_GETS_PER_PEER = 2`) is sized for exactly one stream of each kind. One stream per peer shared by both priorities was rejected because a read would then wait behind up to 16 background pieces.

Waiters queue per pool in arrival order, and a released slot goes to the first waiter in that order whose peer has no stream of that priority open (a waiter for a busy peer is skipped, not allowed to block the waiters behind it). An aborted waiter leaves the queue. `FetchPriority` lives here because the slots are what consume it; `blob-fetcher.ts` re-exports it.

## The fetcher's door into the local store

The fetcher must not write pieces or records around `LocalBlobService`. That service owns the one `BlobRecordStore` (its per-ref update chain serialises record changes; a second instance over the same key-value store would not), the `SweepGate`, and the `PieceSweeper`, and the sweep is only correct against writers that go through them (the three races listed on `PieceSweeper`). The plan's `pieces: IPieceStore; records: BlobRecordStore` dependencies would have bypassed all of that. So `LocalBlobService` gains:

```ts
/** What the fetcher may do to this node's store (docs/blobs.md §Holds). */
export interface BlobFetchStore {
	/** This node's pieces, `verified` (localPieceSource). */
	readonly source: PieceSource;
	/** Adds a `cached` hold to the record, creating it (`whole: false`) when there is none; a record already holding `cached` is unchanged. Not flushed. */
	holdCached(ref: BlobRef): Promise<void>;
	/** Stores a piece of `ref`'s tree that the caller has checked against `id`: inside one shared hold of the sweep gate, noting `ref` as changed for a running sweep, then `pieces.put`. Not flushed. */
	storePiece(ref: BlobRef, id: PieceId, bytes: Uint8Array): Promise<void>;
	/** Sets `whole: true` and `size` on the existing record (the `correctRecord` path; never creates a record, a failure logged not thrown). */
	markWhole(ref: BlobRef, size: number): Promise<void>;
}

class LocalBlobService {
	/** The door `BlobFetcher` uses; built once, the same object every call. */
	fetchStore(): BlobFetchStore;
}
```

A method returning an object, rather than three public methods on the service, keeps `node.blobs`' surface what hosts already see. `holdCached` and `markWhole` go through the private `changeRecord`; `storePiece` is `this.gate.shared(async () => { this.sweeper.noteRecordChange(ref); await this.pieces.put(id, bytes); })`.

**Why noting the ref on every piece store closes the sweep race.** The fetcher takes the hold before it stores anything and stores pieces top down (a list piece before the pieces it names), so every stored piece is reachable from a held reference through present list pieces. The one gap is a piece already present as an orphan when a sweep's first walk of the held blob ran while its parent list piece was still absent: that walk skips the piece, the fetcher then stores the parent and (seeing the child present) never stores the child, and the sweep's decide step deletes it. Noting the ref inside the same shared hold as the parent's `put` puts the ref in the sweep's `changed` set, so the decide step, which runs under the exclusive gate after every shared holder has finished, walks the tree again with the parent present and keeps the child. A parent stored after the decide step instead finds the child already deleted, and the fetcher's next plan (taken after the store) fetches it. `inProgress` is not needed: it protects a put's pieces before a record names them, and the fetcher's record exists before its first piece. Extend the doc comment on `PieceSweeper` (its list of three things that can make a piece live) with this fourth writer, and the doc comment on `noteRecordChange` to say piece stores under a held ref call it too.

`localPieceSource`, `pieceKind`, the gate and the sweeper are unchanged otherwise.

## Edge cases & interactions

- **A hint naming self, a stranger, a banned peer, a peer not speaking the protocol, or a malformed id.** Dropped by the one filter in `blobHolderCandidates`. Inspection.
- **`findCluster` throws.** Empty cohort, logged; `knownHolders` still returned. Inspection.
- **Solo node.** No candidates; `unavailableOutcome([])` is `cohort-unreachable`. The classification test covers the row.
- **Slot waiter for a busy peer.** Skipped, not blocking; inspection of `BlobGetSlots`.
- **Release called twice, or after abort.** Idempotent; the second call does nothing. Inspection.
- **Foreground beside background to one peer.** Separate pools, both granted. Inspection.
- **Record deleted between `holdCached` and `storePiece`** (a host unpins while the record also held only a pin). Cannot happen: the record holds `cached` from `holdCached` on, and only eviction (`feat-unreferenced-blobs-are-reclaimed`) removes a `cached` hold. Add a `NOTE:` at `holdCached` saying eviction must skip blobs with a fetch session in flight.
- **`holdCached` on a record with `whole: true` and missing pieces.** Leaves `whole` as it is; the fetcher's `markWhole` or a local read's correction fixes it. Inspection.
- **Crash after pieces stored, before the record's write reached disk.** Nothing is flushed; the next sweep may remove the orphans and the next fetch brings them again. Accepted; say so in the `BlobFetchStore` doc comment.
