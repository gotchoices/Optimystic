# A relay reservation the relay dropped is never renewed

Source: GitHub sereus#64, reported against Sereus's own supervisor, which copied this one. db-p2p has the same defect.

## What was reproduced

I ran a scratch integration spec, now deleted, against the installed `libp2p` 3.3.11 and `@libp2p/circuit-relay-v2` 4.2.13 on loopback. It used a `spawnPlainRelayNode` relay with its default 2 h reservation lifetime, a `spawnCircuitOnlyPeer` phone, and a third plain node (WebSockets plus circuit-relay transport) that dialed the phone's circuit address. The relay was made to forget the phone's reservation with `relay.services.relay.reservations.delete(phone.peerId)`, which is public on `CircuitRelayService` and leaves the connection open.

- Before the delete, the dial through the relay succeeded.
- After it, every dial failed with `failed to connect via relay with status NO_RESERVATION` for the whole 20 s observed, sampled every 4 s. All that time the phone still advertised its circuit address and still held its one connection to the relay. The supervisor counts that as held (`RelayReservationLoop.held` reads only `node.getMultiaddrs()`) and never acts.
- Calling `reservationStore.addRelay(relayPeerId, 'discovered')` again changed nothing (still `NO_RESERVATION`). So the ticket's first suggestion, "re-send the reservation request on a timer", does nothing if built on a plain `addRelay`. See the cause below.
- Setting the held reservation's `expire` to `0n` and then calling `addRelay(relayPeerId, 'discovered')` made the relay hold the reservation again. The next dials succeeded, and the phone's circuit address was never withdrawn (0 `self:peer:update` events without it during the call).

## Cause

The supervisor knows nothing about the relay's side. It judges "held" from local state, and while held it only re-reads that state every `checkMs`.

The obvious remedy does not reach the relay. In `node_modules/@libp2p/circuit-relay-v2/src/transport/reservation-store.ts`, `addRelay` for a relay that already has a reservation:

- returns that reservation **without contacting the relay** when the reservation's connection is still open and the reservation expires more than `REFRESH_WINDOW` (10 min) from now;
- otherwise refreshes in place. It sends a fresh RESERVE over the open connection, keeps the address advertised during the refresh (it removes the entry up front only when the connection is gone), reuses the entry's slot id, re-arms libp2p's own refresh timer, re-tags the relay keep-alive, and dispatches `relay:created-reservation`. The bare listener re-confirms its addresses on that event (`addedRelay` in `src/transport/listener.ts`).

If that refresh fails, the `catch` removes the entry, which withdraws the address. That is the right outcome, because the relay no longer honours the reservation, and the supervisor then re-drives as it does after any loss.

On the relay side (`src/server/reservation-store.ts`, `reserve`), a RESERVE from a peer that already holds a reservation resets its lifetime, and one from a peer it has forgotten creates a new reservation. So any RESERVE that actually reaches the relay repairs the forgotten case. `Reservation.expire` is read only by that refresh-window check (grep of the transport sources), so zeroing it has no other effect.

Why the relay forgot is not known (Sereus saw it against a public relay). One way a js relay does it is `handleReserve`'s `catch`: it calls `removeReservation` when writing or closing the confirmation stream throws, after the client may already have read the OK. That is a guess and not part of this ticket.

## Design

Re-send the reservation request on a timer by forcing libp2p's own in-place refresh, through the one internals seam that already exists. A raw RESERVE on our own hop stream was rejected for three reasons:
- it would add a second hop-protocol client with its own protobuf codec (the package exports no `HopMessage`);
- on a refusal it could not make libp2p withdraw the address without reaching further into the store;
- it would leave libp2p's entry, timer and keep-alive tag out of step with the relay.

### Seam (`relay-reservation.ts`)

- `RelayReservationStoreLike` gains `getReservation(peerId: PeerId): { expire: bigint } | undefined`, a public method on the store class, and `isReservationStore` requires it, so an upgrade that drops it makes the accessor return `null` loudly, as for the other members.
- A new function beside `clearRelayFilterEntry`, for example `forceReservationRenewal(store, relayPeerId): Promise<…>`. It reads `store.getReservation(relayPeerId)`, sets its `expire` to `0n` so the next request falls inside libp2p's refresh window, and calls `store.addRelay(relayPeerId, 'discovered')`. It returns whether that resolved, or why it did not; it does not throw. If the store holds no reservation for the relay, it says so and requests nothing.
- Extend the `NOTE:` at `findCircuitRelayTransport` with the facts above. Two of them carry most of the weight:
  - a plain `addRelay` on a held, connected reservation more than 10 min from expiry does not reach the relay;
  - zeroing `expire` is the only route to the in-place refresh, and it mutates a libp2p-owned object. A successful refresh replaces the entry with the relay's new expiry. If `addRelay` throws before its job runs (`RelayQueueFullError`, or the relay filter, which the supervisor clears first anyway), the zero is left in place, which only means the next request also refreshes; libp2p's own timer is unaffected.

### Supervisor (`RelayReservationLoop`)

- New option `renewMs` on `RelayReservationSupervisorOptions`, default `DEFAULT_RELAY_RENEW_MS = 5 * 60_000`. Each interval gets ±10% jitter (a named constant), so many phones on one relay do not renew in step. Clamp it away from 0 the way the other options are clamped. Five minutes is what Sereus's interim patch uses, and it fixed their stuck "Joining" case. The cost is one RESERVE stream every 5 min per supervised relay, well within the relay's 2 h lifetime.
- Keep `nextRenewAtMs`. Set it (now + jittered `renewMs`) when a drive lands the reservation, when a tick first finds it held, and after every renewal attempt, successful or not.
- In `tick`, when held and `now >= nextRenewAtMs`, run a renewal instead of the plain `onHeld`. It is serialized with drives through the same `inFlight` flag, raced against `driveTimeoutMs` (as `requestReservation` is, since `addRelay` takes no signal), and discarded if `stop()` ran meanwhile. After it, judge `held` again: still held → `onHeld`; not held (the refresh failed and libp2p withdrew the address) → `driveOnce` at once, then the existing tail (`onHeld` or `scheduleBackoff`). The renewal has already shown the relay refused, so there is no reason to wait out a backoff first.
- `onHeld` schedules `min(checkMs, nextRenewAtMs − now)`, so the renewal is not up to `checkMs` late.
- Log lines in the existing style: `relay-reservation:renewed relay=…` at debug, and `relay-reservation:renew-failed relay=… reason=…` at error.
- Unchanged: per-relay serialization, `HadEnoughRelaysError` handling (a refresh never meets it, because an existing entry skips the pending-slot check), the `self:peer:update` and `peer:connect` triggers, and `firstDrive`.
- Update the module doc comment and the doc comment on `superviseRelayReservation`: list the renewal among the triggers, and say that "held" is still judged locally and that the renewal is what checks it against the relay.

### Node option

`createLibp2pNodeBase` calls `superviseRelayReservations(node, relayPlan.supervisedRelays)` with no options, so a host cannot tune anything today. Add a `NodeOptions` field (for example `relayReservation?: RelayReservationSupervisorOptions`, with a short doc comment) and pass it through. Mention `renewMs` in the readme's "To be reachable through a relay instead" paragraph: the node re-sends its reservation request every 5 min by default, so a relay that forgot it is repaired within that interval, and `relayReservation.renewMs` changes the interval.

## Tests (one per behaviour)

- **Seam** (`relay-reservation-seam.spec.ts`, not env-gated). Add `getReservation` to the first case's shape assertions. Add one case pinning the libp2p fact the fix rests on: with a bare-listener client holding a `discovered` reservation on a `spawnPlainRelayNode` relay, delete the client from `relay.services.relay.reservations`. A plain `addRelay` leaves the relay without it; `forceReservationRenewal` makes the relay hold it again, with no `self:peer:update` that lacks the circuit address while it runs. If a libp2p upgrade changes the refresh rule, this case fails.
- **Regression** (`relay-reservation-supervisor.spec.ts`, group 2, test timings). Supervise with a short `renewMs` (for example 1.5 s), wait until held, delete the reservation on the relay side, and assert:
  - a third node's dial through the client's circuit address fails with `NO_RESERVATION` at first, then succeeds within `renewMs × 1.1` plus slack;
  - the client advertised its circuit address at every sample throughout.

  The third node is a plain libp2p node with `webSockets()` and `circuitRelayTransport()`, as in the scratch spec; hang up on the client between dials, so each dial goes back through the relay. `spawnRestartablePlainRelay`'s `node` gives the relay's `services.relay`. If a small helper for that cast is needed, put it in `test/util/relay-topology.ts`.
