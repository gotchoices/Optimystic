# A consensus record is serialized once per delivery

Part of GitHub #63 (large blob rows commit at about 1.7 s per MB). Split out of the plan ticket `a-large-write-costs-time-and-space-per-byte`, together with `sql-statements-are-built-only-when-something-reads-them`, `a-member-hashes-a-committed-block-once` and `a-large-write-is-measured-once-and-its-cost-is-documented` (which re-measures and writes the docs once all of them land).

## What was measured

Two-node in-process mock mesh (`startMockMesh(2)`, memory storage, legacy commit mode, Node 24 on Windows), table `BlobChunk (Hash text primary key, Bytes blob not null)`, transactions of N rows of 256 KiB random bytes bound as parameters, `begin` / N inserts / `commit`:

| values per transaction | staging | commit |
|---|---|---|
| 1 (0.26 MB) | 24–48 ms | 123–260 ms |
| 4 (1.05 MB) | 111–161 ms | 357–382 ms |
| 8 (2.1 MB) | 244–311 ms | 695–936 ms |

About 0.5 s per MB for staging plus commit here (the issue's 1.7 s per MB was file storage on another machine). No commit in twelve took the 11–13 s outlier the issue reports.

A CPU profile (`node --cpu-prof`) of six 8-value commits — about 7.0 s of CPU for both nodes together, start-up excluded — attributes:

| pass | share | ticket |
|---|---|---|
| hashing the cluster record (`validateRecord` 0.96 s, `handlePromiseNeeded` 0.25 s, `handleCommitNeeded` 0.25 s, `mergeRecords` 0.08 s) | 22% | this one |
| the member's storage apply (`previewCommitDigest`, `internalCommit`, `pendUnderLatches`) | 18% | `a-member-hashes-a-committed-block-once` (the redundant part, about 9%) |
| Quereus building a per-row SQL statement with the blob written as hex (`buildInsertStatement` → `uint8ArrayToHex`) | 12% | `sql-statements-are-built-only-when-something-reads-them` |
| the writer's size measures (`describeTouchedBlocks`, `transactionBytes` twice, `Chain.takenBy`, node division, `act`) | 9% | `a-large-write-is-measured-once-and-its-cost-is-documented` (the redundant part) |
| base64 of each blob (`encodeRow`) | 3.5% | inherent to the `json` row encoding |

## Why the record is hashed so many times

A `ClusterRecord`'s `message` is the whole pend or commit, so for a write it carries every byte of row data (twice: tree and log). The three hashes in `packages/db-core/src/cluster/membership.ts` each re-run `canonicalJson(message)` and `TextEncoder.encode` over it:

- `messageHash` = `SHA256(canonicalJson(message) + digest)`
- `promiseHash` = `SHA256(messageHash + canonicalJson(message) + digest)`
- `commitHash` = `SHA256(messageHash + canonicalJson(message) + digest + canonicalJson(promises))`

`ClusterMember.validateRecord` computes all three on every delivery of a record; `handlePromiseNeeded` and `handleCommitNeeded` compute the promise or commit hash again for the same record; `mergeRecords` serializes both the held and the incoming message a further time to compare them (`canonicalJson(existing.message) !== canonicalJson(incoming.message)`). That is up to seven whole-message serializations, and six SHA-256 passes over it, per delivery, and a write is two records (pend and commit), each delivered to a member at least twice.

## The change

The signed-hash layout must not change by a single byte: every stored `BlockCommitProof` and every mixed-version cohort depends on it (internals *Both consensus rounds carry the coordinator's own member's vote*, last paragraph of the second rule). What changes is how the preimage bytes are produced.

- In `membership.ts`, keep one memo, a module-level `WeakMap<RepoMessage, Uint8Array>`, holding the UTF-8 bytes of `canonicalJson(message)`, filled on first use (`canonicalMessageBytes(message)`, exported for the comparison below). The three hash functions build their preimage by concatenating byte arrays — `utf8(messageHash)`, the memoized message bytes, `utf8(digest ?? '')`, and for the commit hash `utf8(canonicalJson(promises))` — with `concat` from `uint8arrays` (already a dependency; no Node `Buffer`, since db-core runs on React Native and in browsers). This is byte-identical to encoding the concatenated string: UTF-8 of a concatenation is the concatenation of the UTF-8 of its parts for well-formed strings, and every part is well-formed (`JSON.stringify` escapes lone surrogates; the hashes and digest are base58/base64url). Say so in a comment.
- `mergeRecords` compares the two messages by `equals` (from `uint8arrays`) over `canonicalMessageBytes` of each, which is the same equality the string comparison decided.
- Every caller already goes through the three functions (`cluster-repo.ts`, `commit-proof.ts`, `cluster-coordinator.ts`, `dispute-service.ts`), so none needs a change beyond `mergeRecords`.

Over the wire each delivery decodes a fresh message object, so each delivery still pays one serialization — that is the floor without trusting an unverified hash, and it is the intended result: one per delivery instead of about seven.

Rejected: memoizing the promise and commit hashes by `messageHash` across deliveries. Sound once the message hash is re-verified on each delivery, but it saves nothing further, since that re-verification already pays the one serialization the WeakMap then shares.

## Edge cases & interactions

- **Layout pinned.** Before changing anything, compute on HEAD the three hashes for one fixed message (a pend with a transform and a non-ASCII string), once with `digest` undefined (v1) and once with a digest (v2), and write a test in `packages/db-core/test/` asserting those literal values. This is the one new test: it pins the signed preimage layout of `docs/correctness.md` §2, which no implementation change may alter. (Check first whether an existing spec already pins literal values — `db-p2p/test/commit-proof.spec.ts`, `cluster-membership-binding.spec.ts` — and extend it instead if one does.)
- **A message mutated after it was first hashed** would make the memo return the old bytes, and a signature would then be over content the record no longer holds. Confirm by inspection that no code changes a `RepoMessage` after it is placed in a `ClusterRecord` (a grep for assignments into `.message.` found none; check the coordinator's record construction in `cluster-coordinator.ts` and the batch builders in `record-operations.ts`). Record the rule as a `NOTE:` at the WeakMap.
- **Memory.** The memo holds the message's encoded bytes for as long as the message object lives, which for a member is as long as it keeps the record (until its transaction state is cleaned up): about one more copy of the message per held record. Acceptable now; leave a `NOTE:` tripwire at the WeakMap (if member memory under large writes ever matters, drop the entry once the record is decided).
- **The in-process mesh** may hand one message object to several simulated nodes; they then share one memo entry, which is correct because the content is identical.
- **Hostile input.** A message is bounded by the frame cap (`MAX_BLOCK_MESSAGE_BYTES`) before it is decoded, so the memo cannot be grown past what the record already costs; it is weak, so it never outlives its record.
- **Commit-proof verification** (`verifyBlockCommitProofClaim`) calls the same functions and gets the same saving; the plan ticket `a-verified-commit-proof-is-not-verified-again` caches verdicts above this and is unaffected.
- **v1 records** (no membership digest) hash exactly as before; covered by the pinning test.
