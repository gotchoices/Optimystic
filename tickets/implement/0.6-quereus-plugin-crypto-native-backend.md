# quereus-plugin-crypto: a native crypto backend

GitHub: [#30](https://github.com/gotchoices/Optimystic/issues/30). The reporter offered a PR once the shape is agreed; this ticket is that shape.

## Why

`packages/quereus-plugin-crypto/src/crypto.ts` calls `@noble/hashes` (sha256, sha512, blake3) and `@noble/curves` (ed25519, secp256k1, p256) directly: the `HASHERS` table, and the curve switches in `sign` and `verify`. Every hash in the package goes through `resolveHasher` — `digestFields`, `hashMod`, `cid` in `src/cid.ts`, and `leafDigest`/`setCommit`/`setVerify` in `src/sd.ts` all take a hasher from it.

Measured by the reporter (taleus on a Galaxy S7, Hermes CPU profile): one tally invitation took 29 s; SQL `verify` was 408 ms inclusive, noble `ed25519.verify` 366 ms of it, and every noble Ed25519 frame came through this plugin. Digests use noble SHA-256 even after the app routes `crypto.subtle.digest` to native, because the plugin never touches `crypto.subtle`. The cost scales with signed rows read.

## Design (decided)

### Interface

```ts
/** Synchronous native implementations; any omitted member falls back to @noble. */
export interface CryptoBackend {
	sha256?(data: Uint8Array): Uint8Array;
	sha512?(data: Uint8Array): Uint8Array;
	/** Raw 64-byte signature, message, raw 32-byte public key. Returns false, or throws, for an invalid signature or key. */
	ed25519Verify?(signature: Uint8Array, message: Uint8Array, publicKey: Uint8Array): boolean;
	/** Message, raw 32-byte secret seed (the form noble and generatePrivateKey('ed25519') use). Returns the raw 64-byte signature. */
	ed25519Sign?(message: Uint8Array, secretKey: Uint8Array): Uint8Array;
}

/** Install a backend for this process, or pass undefined to restore the @noble defaults. Throws, leaving the previous backend in place, if the backend fails its self-check. */
export function setCryptoBackend(backend: CryptoBackend | undefined): void;
```

Exported from `src/index.ts` (the package root), beside `sign`/`verify`. Synchronous because the SQL functions are. Every member optional, so adding a member later (blake3, secp256k1, p256) is not a breaking change; those are deliberately not in this pass — the measurement shows only Ed25519 and SHA-2 hot, and noble's ECDSA `sign` pre-hashes the message, which a native adapter would have to reproduce exactly. Add a member when a measured need appears.

### Process-wide, held on `globalThis` — not a per-registration option

- A per-registration option is not possible: the plugin's config reaches `register(db, config)` as `Record<string, SqlValue>` (and through `loadPlugin('npm:…')`), which cannot carry functions. The JS API (`digest`, `sign`, `verify`, `cid`, …) is also called with no registration at all. The noise precedent (`NodeOptions.noiseCrypto` in `packages/db-p2p/src/libp2p-node-base.ts`) injects per node because `createLibp2pNode` takes objects; this plugin has no such entry point.
- Process-wide is also the right scope: native crypto on a phone is a process-wide resource, and a backend must give byte-identical results to noble (below), so no two databases in one process can legitimately want different backends.
- **The state must live on `globalThis`, keyed by `Symbol.for('@optimystic/quereus-plugin-crypto/backend')`, not in a module-level `let`.** `tsup.config.ts` builds `index` and `plugin` as two entries with `splitting: false`, so `dist/index.js` and `dist/plugin.js` each carry their own copy of `crypto.ts` (verified: `HASHERS` appears in both). A module-level variable set through the package root would never reach the SQL functions an app loads from `@optimystic/quereus-plugin-crypto/plugin`. A `Symbol.for` key on `globalThis` is shared by both bundles and by a second installed copy of the package. Rejected alternative: `splitting: true` (a shared chunk) — fixes the two entries but not a duplicate install, and changes the published `dist/` layout.

### Consulted at call time

`resolveHasher(algorithm)` keeps its contract (validate once, return a function) but returns, for `sha256` and `sha512`, a dispatcher fixed per algorithm that reads the current backend on each call and falls back to noble; `blake3` stays noble directly. So the plugin's registration-time `digestHasher`, a `cid` call and `hashMod` all honour a backend set **after** the plugin was registered — an app that registers plugins before it initialises native crypto still gets the native path. The cost is one property read per hash; update the "no per-call branching" comments in `crypto.ts` and `plugin.ts`, which then describe algorithm/encoding selection only. `sign` and `verify`'s `ed25519` branches consult `ed25519Sign`/`ed25519Verify` the same way. `verify`'s existing catch-all stays, so a backend throw becomes `false`, as a noble throw does today; a `sign` throw propagates, as today.

### Self-check at set time

`setCryptoBackend` runs a known-answer check of every member the backend supplies, against noble, before installing it, and throws (naming the failing member) without changing the installed backend:

- `sha256`/`sha512`: the hash of a fixed non-empty input equals noble's.
- `ed25519Sign`: signing a fixed message with a fixed 32-byte seed equals noble's signature byte for byte (Ed25519 signing is deterministic, RFC 8032).
- `ed25519Verify`: accepts noble's signature over the fixed vector, and rejects it after one byte of the message is flipped.

This is what catches an adapter that hands the native library the wrong key shape — the reporter has not yet confirmed that react-native-quick-crypto's synchronous Ed25519 accepts raw 32-byte keys — at app start, instead of as wrong signatures persisted and replicated. Fixed vectors are generated by noble at module load or hard-coded; either is fine. Cost: a handful of native calls, once.

## Edge cases & interactions

- **Two bundles, one setting** — set through the package root, observed by the SQL functions from the `/plugin` entry. Verified by the test below, which imports the setter from `dist/index.js` and the plugin from `dist/plugin.js`.
- **Set after registration** — takes effect on the next call (call-time dispatch). Verified by the same test.
- **Reset** — `setCryptoBackend(undefined)` restores noble everywhere. Tests rely on it in `afterEach`, since the state is process-global and shared across spec files.
- **Failed self-check** — throws and keeps the previous backend (including a previously installed good one). Verified by test.
- **Partial backend** — e.g. only `ed25519Verify`: hashes stay noble. By inspection (per-member fallback).
- **Backend throws at call time** — `verify` returns false; `sign`, `digest`, `cid` propagate. By inspection; same as noble's throws today.
- **Wrong-length inputs** — `sign`/`verify` pass whatever bytes the caller decoded; a backend must throw or return false on a malformed key or signature, as noble does. State it in the interface doc; not enforced.
- **Ed25519 verify strictness differs on crafted input.** Noble's `ed25519.verify` defaults to the ZIP-215 rule (`verifyOpts = { zip215: true }` in `@noble/curves/abstract/edwards.js` 2.0.1), which accepts some non-canonical point encodings and small-order components that an RFC 8032-strict implementation such as OpenSSL (which react-native-quick-crypto wraps) rejects. Honest signatures verify the same either way, and the self-check cannot test this without refusing every strict backend. So in a group whose machines mix backends, a crafted signature could verify on one machine and not another; it would matter only where peers re-execute a statement whose outcome depends on `verify` (no deployment validates transactions at pend today). Record this as a `NOTE:` tripwire at the `ed25519Verify` dispatch in `crypto.ts`, and say it in the README's backend section. Rejected: switching the noble default to `zip215: false` — it changes existing `verify` results and still would not match OpenSSL exactly on small-order keys.
- **Determinism / `replicable`** — `digest`, `cid` and `set_commit` are registered `replicable`; the byte-identity requirement plus the self-check is what keeps that true with a backend. Say so in the README.
- **React Native bundle** — no new imports in `src/`; `node:crypto` appears only in the test. `yarn check:rn` unaffected.

## Test (one spec file, `test/crypto-backend.spec.ts`)

A real native backend for node built on `node:crypto`: `createHash('sha256'|'sha512')`; Ed25519 through `crypto.sign(null, msg, key)` / `crypto.verify(null, msg, key, sig)`, with the raw 32-byte seed wrapped as PKCS#8 DER (prefix `302e020100300506032b657004220420`) and the raw public key as SPKI DER (prefix `302a300506032b6570032100`). Wrap each member to count calls. It also serves as the worked adapter shape for the README (react-native-quick-crypto mirrors this API).

- **Byte-identical and actually used**: register the plugin from `dist/plugin.js` first, then `setCryptoBackend` (from `dist/index.js`) with the node backend; through the registered SQL implementations, `digest('a', 1)`, `cid(...)`, `sign(..., 'ed25519')` and `verify(..., 'ed25519')` (a valid and a tampered case) equal the values computed with no backend, and each backend member's call count is above zero.
- **Refused backend**: a backend whose `sha256` returns wrong bytes, and one whose `ed25519Sign` returns a different signature, each make `setCryptoBackend` throw; afterwards a previously installed good backend is still the one in use (its counter advances).

`afterEach(() => setCryptoBackend(undefined))`. Specs import `dist/`, so `yarn build` before `yarn test` in this package (the build-freshness guard enforces it), and `yarn typecheck` after the build.
