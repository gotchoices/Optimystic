# Blob protocol: the `stat`/`get` server and client

docs/blobs.md designs native large-value ("blob") support. A node stores a blob's pieces in an `IPieceStore` and answers `node.blobs.stat`/`read` from its own store (`LocalBlobService`, `packages/db-p2p/src/blob/local-blob-service.ts`). The prereq `blob-protocol-wire-and-frames` built, in `packages/db-p2p/src/blob/`, the protocol id (`buildBlobProtocol`), the wire types and codec (`BlobRequest`, `BlobAnswer`, `encodeBlobHeader`, `decodeBlobRequest`, `decodeBlobAnswer`, `checkAnswerFits`), the errors (`BlobTransferStalledError`, `BlobPeerRefusedError`, `BlobProtocolError`), the frame helpers (`readBlobFrames`, `sendBlobFrame`, `closeBlobStream`), `ProgressDeadline`, the limits in `protocol-limits.ts`, `openStreamWithin` in `protocol-client.ts`, and `Libp2pKeyPeerNetwork.peersServing`. Read that ticket's frame sequences in `blob-protocol.ts` before starting.

This ticket adds the server that answers `stat` and `get` (and placeholder answers for `announce` and `held`), the client that sends `stat` and `get`, registers the server on every node, extends the authorization wiring spec, adds two stall specs, and updates the docs. The later fetcher (`feat-blob-fetcher-verifies-and-resumes`) and network read (`feat-blob-pieces-move-between-machines`) build on it. Nothing here fetches, verifies or stores a piece: the client hands the caller each piece's bytes as they arrive. The server serves only what its piece store holds.

## Registration: on both roles

The node registers the server through a new `blob` entry in the libp2p `services:` map of `createLibp2pNodeBase` (`packages/db-p2p/src/libp2p-node-base.ts`), with `protocolPrefix: \`/optimystic/${options.networkName}\``.

**It is registered on client nodes too (`servesBlocks: false`), not inside `storageProtocolServices`.** A client holds blobs its own host put, and before a row referencing a blob commits that machine holds its only copy; docs/blobs.md §Placement says readers then "fetch it from the writer on demand", and the writer is often a phone running as a client. So the blob service sits outside the serving-only spread, beside the services every node registers. Consequences, all part of this ticket:

- The inbound authorization init (`authorizeInboundStream`, `authorizeInboundStreamTimeoutMs`, currently built inside `storageProtocolServices` as `inboundAuthorization`) is built once in `createLibp2pNodeBase` and handed to both `storageProtocolServices` and the blob service, spread into its init exactly as the four database services do (docs/blobs.md §Who may fetch: the blob protocol is gated like them).
- `logIgnoredServingOptions` drops `authorizeInboundStream` and `authorizeInboundStreamTimeoutMs` from its list: on a client they now gate the blob protocol.
- `preparedStreamProtocols` is unchanged on both roles.

The service needs at construction, inside the `services` factory, the node's `LocalBlobService` (`blobs`, for `stat`) and its piece store (`pieceStore`, for `get`). Both are already constructed above `createLibp2p` on both roles (`resolvePieceStore`, `new LocalBlobService(...)` in `createLibp2pNodeBase`), so no reordering is needed. `progressTimeoutMs` is `linkDeadlines.responseTimeoutMs`, also resolved above `createLibp2p`.

The service registers its handler only through `registerProtocolHandler` (`packages/db-p2p/src/network/register-protocol-handler.ts`), which `test/dial-options-single-site.spec.ts` enforces and which accepts streams over limited relay connections.

**Not in `preparedStreamProtocols`.** Add a comment there saying why: a prepared stream saves one negotiation round trip on a small request, and `ProtocolClient` resends a request once when such a stream fails before the reply begins, which assumes a small idempotent request and a single reply. A blob `get` moves up to 16 pieces, one round trip is negligible against that, the blob client does not go through `ProtocolClient`, and a pool would keep an idle blob stream per peer open for 30 s after every request. `Libp2pKeyPeerNetwork.connect` returns a fresh stream for a protocol the pool does not list (`PreparedStreams.take` finds nothing; `replenish` ignores it), so nothing else changes.

**The client is not constructed by the node in this ticket.** Its first consumer is the fetcher (`feat-blob-fetcher-verifies-and-resumes`), which constructs one `BlobProtocolClient` beside the `BlobFetcher` (that ticket says so); the stall spec builds its own. A local nothing reads would only be dead code until then.

## Server: `BlobProtocolService`

`packages/db-p2p/src/blob/blob-protocol-service.ts`, a libp2p `Startable` built by a `blobProtocolService(init)(components)` factory like `blockTransferService` (`packages/db-p2p/src/cluster/block-transfer-service.ts`: same handler unwrapping `data?.stream ?? data`, same `start`/`stop` with `registrar.unhandle`).

```ts
export interface BlobProtocolServiceInit extends InboundStreamAuthorizationInit {
	protocolPrefix?: string;
	/** Local holdings only: never probes. */
	blobs: Pick<LocalBlobService, 'stat'>;
	pieces: Pick<IPieceStore, 'has' | 'get'>;
	/** LinkDeadlines.responseTimeoutMs of this node. */
	progressTimeoutMs: number;
	/** Set by feat-a-referenced-blob-is-copied-to-its-cohort. Absent: every announce is answered 'declined', as a node that takes no blobs would. */
	onAnnounce?: (fromPeer: string, ref: BlobRef, scope: string) => Promise<BlobAnnounceAnswer>;
	/** Set by the same ticket. Absent: a `held` is acknowledged and ignored. */
	onHeld?: (fromPeer: string, ref: BlobRef) => void;
}
export interface BlobProtocolServiceComponents {
	registrar: ProtocolRegistrar & { unhandle(protocol: string): Promise<void> };
}
```

(The node's own collaborators go in the init, which the `services` factory closes over; libp2p's components carry only the registrar. This differs from the shape sketched in the plan, where they sat in the components; the init is where `blockTransferService` puts its non-libp2p collaborators.)

Per inbound stream, in this order:

1. Derive `remotePeerId` from `connection?.remotePeer?.toString()` once. Run `this.authorization.deny(stream, remotePeerId)` (from `createInboundStreamAuthorization`) before reading anything; denied → return. No predicate → no check.
2. Start a `ProgressDeadline(remotePeerId, progressTimeoutMs)`. Take the first frame from `readBlobFrames` with one `next()`; do not wait for the requester's end of stream before answering (the deadlock `BlockTransferService.handleRequest` documents). A second request frame on one stream is never read.
3. Decode with `decodeBlobRequest`. `BlobProtocolError` → answer `refused: malformed`.
4. `stat`: `blobs.stat(ref)` for each reference, mapping locality `here` → `whole`, `partial` → `partial`, anything else → `none`. Answer.
5. `get`: take an allowance slot (per peer `MAX_BLOB_INBOUND_GETS_PER_PEER`, node `MAX_BLOB_INBOUND_GETS`, counted in in-memory maps, released in a `finally` on every exit path); none free → `refused: busy`. Otherwise `pieces.has` for each id, send the `{kind:'get', held}` header, then for each held id in order `pieces.get(id)` and `sendBlobFrame(..., MAX_BLOB_PIECE_FRAME_BYTES)`. Read each piece just before sending it, so the server holds one piece plus what the transport buffers. A piece that `has` reported and `get` then returns `undefined` for (a sweep removed it in between) breaks the header's promise: abort the stream with `BlobProtocolError`; the client keeps what it already received.
6. `announce` → `onAnnounce?.(...)` or `'declined'`; `held` → `onHeld?.(...)`, answer `{kind:'held'}`.
7. `closeBlobStream(stream, deadline)`; `deadline.stop()` in `finally`. Any throw → log and `stream.abort(err)`; when the deadline's signal aborted, abort with its reason (`BlobTransferStalledError`) and log `serve:stalled`.

No reputation report on the server: it judges nothing it receives except the request shape.

## Client: `BlobProtocolClient`

`packages/db-p2p/src/blob/blob-protocol-client.ts`. One instance per node; per-peer state lives in callers.

```ts
export interface BlobProtocolClientInit {
	peerNetwork: IPeerNetwork;          // the node's Libp2pKeyPeerNetwork
	protocolPrefix: string;
	deadlines: Pick<LinkDeadlines, 'dialTimeoutMs' | 'responseTimeoutMs'>;
}
export interface BlobGetReply {
	held: PieceId[];                    // in request order
	notHeld: PieceId[];
	/** Yields each held piece as its frame completes, in `held` order. Must be iterated to the end or exited early (break/return), which aborts the stream. Throws BlobTransferStalledError, BlobProtocolError, or the stream's own error. */
	pieces: AsyncIterable<{ id: PieceId; bytes: Uint8Array }>;
}
export class BlobProtocolClient {
	constructor(init: BlobProtocolClientInit);
	stat(peer: PeerId, refs: readonly BlobRef[], options?: { signal?: AbortSignal }): Promise<BlobLocalHolding[]>;
	get(peer: PeerId, pieces: readonly PieceId[], options?: { signal?: AbortSignal }): Promise<BlobGetReply>;
	/** Cumulative frame bytes (length prefixes included) this client sent and received; diagnostics and the transfer measurement read it. */
	wireBytes(): { sent: number; received: number };
}
```

Both calls:

- Refuse locally (throw `RangeError`) a list that is empty, over its cap (`MAX_BLOB_STAT_REFS`, `MAX_BLOB_GET_PIECES`), or, for `get`, with duplicate ids.
- Open the stream with `openStreamWithin(peerNetwork, peer, buildBlobProtocol(protocolPrefix), { signal, dialTimeoutMs: deadlines.dialTimeoutMs })`.
- Start a `ProgressDeadline(peer, deadlines.responseTimeoutMs)`, send the request through `sendBlobFrame(..., MAX_BLOB_HEADER_BYTES)`, then `closeBlobStream` (write side only in libp2p 3: it resolves once the request is flushed, and reading continues).
- Read the answer header from one `readBlobFrames` iterator, decode with `decodeBlobAnswer`, `refused` → `BlobPeerRefusedError`, then `checkAnswerFits`.
- The caller's `signal` aborts the stream with `signal.reason`; the deadline's signal aborts it with `BlobTransferStalledError`. Every exit path stops the deadline and removes the abort listener.
- `wireBytes` adds each sent frame's length and each received frame's length plus its varint prefix (`varint.encodingLength` from `uint8-varint`, or count raw chunk bytes in the pass-through — pick one and say which in the doc comment).

`get` resolves once the header is read. `pieces` then reads exactly `held.length` frames from the same iterator, and after the last one requires end of stream: a further frame is `BlobProtocolError` ('extra frame'), end of stream before the last is `BlobProtocolError` ('truncated'). Exiting the loop early aborts the stream. `pieces` is single-use.

## Logging

`createLogger('blob:protocol')`, namespace `optimystic:db-p2p:blob:protocol`; one line per request served or sent, plus the abnormal ends:

- `serve:stat peer=… refs=… whole=… partial=… none=… ms=…`
- `serve:get peer=… asked=… held=… bytes=… ms=…`
- `serve:refused peer=… reason=busy|malformed detail=…`
- `serve:stalled peer=… ms=…` and `serve:aborted peer=… err=…`
- `client:stat peer=… refs=… ms=…`, `client:get peer=… asked=… held=… received=… bytes=… ms=…`
- `client:stalled peer=… ms=…`, `client:refused peer=… reason=…`, `client:protocol-error peer=… detail=…`

Inbound authorization denials go to the service's `:error` child channel as `BlockTransferService` does.

## Edge cases & interactions

- **Denied peer.** Reset before any frame is read. Inspection of the handler order, and the authorization wiring spec below.
- **Client node.** Registers and serves the blob protocol, gated by `authorizeInboundStream`; `logIgnoredServingOptions` no longer lists the two authorization options. Inspection.
- **Header claims a piece and never sends it.** The client's deadline aborts within one `responseTimeoutMs`. Test.
- **Receiver stops reading.** The server's `onDrain` wait is cut off by its deadline and the stream aborted. Test.
- **Piece removed between `has` and `get` on the server.** Stream aborted with `BlobProtocolError`; the client sees the error after the pieces already yielded. Inspection.
- **Over allowance.** `refused: busy`; slots released in `finally` on every exit path, stalled and aborted streams included. Inspection.
- **Duplicate ids, an empty list, or a list over its cap.** `refused: malformed` on the server; the client refuses to send it. Inspection.
- **Client exits `pieces` early.** Stream aborted, not left half-read. Inspection.
- **Caller abort.** Stream aborted with the caller's reason; deadline stopped; listener removed. Inspection.
- **Stock circuit relay.** A relayed stream with stock limits is reset after 128 KiB, under one 256 KiB piece; the client sees the stream error. Accepted by docs/blobs.md §Relays.
- **Older peer without the protocol.** `peersServing` leaves it out; a dial to it fails at negotiation (or at the first read, since `connect` passes `negotiateFully: false`) as a stream error. Inspection.
- **Two networks on one machine.** The protocol id carries the network prefix. Inspection.
- **React Native bundle.** New files import only `it-length-prefixed`, `uint8arraylist`, `uint8arrays`, libp2p interface types and db-core. `yarn check:rn`.

  - *Header lies*: on node A, re-register the blob protocol id with `registerProtocolHandler(..., { force: true })` to a handler that reads the request, sends `{kind:'get', held:[true]}` and then nothing. A `BlobProtocolClient` on B (`peerNetwork: B.keyNetwork`, B's `linkDeadlines`) resolves `get`, and iterating `pieces` rejects with `BlobTransferStalledError` in under 3 s.
  - *Receiver stops reading*: put two 1 MiB pieces into A's store directly under their real raw-leaf ids (CID v1, raw codec, sha2-256 of the bytes, through `pieceIdOfCid`; the server only calls `has`/`get`). B opens a stream to A with `B.keyNetwork.connect(A.peerId, buildBlobProtocol(prefix))`, writes a `get` request frame for both, closes its write side, calls `stream.pause()` and never reads. Assert B's stream ends with an error (the server's abort reaches B as a reset) in under 3 s. This pins that the sender waits for drain under its deadline rather than buffering.
