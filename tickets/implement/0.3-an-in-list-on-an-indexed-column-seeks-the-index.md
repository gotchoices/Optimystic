## What Quereus offers

No engine change is needed for the reporter's query. A virtual table claims a filter with `op: 'IN'` in `handledFilters`, names the index and the seek column, and `query()` then receives a multi-seek: `idxStr` carrying `plan=5` and one `args` entry per listed value. The contract is in `docs/module-authoring.md` of the Quereus repository ("Multi-seek key order is a hard requirement"), and the arm that builds it is `selectPhysicalNodeFromPlan` in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`. Three parts of the contract shape this ticket:

- The engine drops duplicate and NULL literals, but a list with bound parameters reaches the module unreduced. The module must skip NULLs and must not return a row twice.
- A multi-seek must emit rows in the scanned index's key order, never in list order.
- The engine picks the FIRST filter that fills the equality role on a column, so the module must claim that same one (`findEqualityMatches` in `@quereus/quereus/src/vtab/memory/module.ts` is the worked example).

## Design

### Which seeks can be trusted: one gate for `=` and `in`

The index and primary-key trees compare raw bytes, so a seek finds only values whose stored bytes equal the sought bytes. A claimed filter is not re-checked by the engine, so a seek on a column where equal values can have different bytes loses rows. This is already wrong for plain `=` today (measured, `repro: verified` level):

| statement | rows stored | returned | correct |
|---|---|---|---|
| `where city = 'abc'`, `city text collate nocase`, indexed | `ABC`, `abc` | `abc` only | both |
| `where id = 'abc'`, `id text collate nocase primary key` | `ABC` | none | `ABC` |
| `where d = 'PT60M'`, `d timespan`, indexed | `PT1H` | none | `PT1H` (a memory table with no index returns it) |

The engine does not catch these: a `nocase` predicate over a `nocase` index classifies as a full match (`classifyConstraintCover` in `rule-select-access-path.ts`), which is a promise that the module's seek honours the collation. This module's does not.

So one predicate decides whether a column may be sought at all, and both operators use it: the column's key collation is BINARY and its type has no semantic ordering (`hasSemanticOrdering`, exported by `@quereus/quereus`, which covers `timespan` and `json`). The key collation is the index column's `collation` for a secondary index and the table column's `collation` for the primary key, the same lookup `indexColumnCollationLookup` in `rule-select-access-path.ts` makes, so the module and the engine are judging the same thing. A declined column stays a residual filter over a scan: slower and correct. The cost is that a `collate binary` predicate over a `nocase` index, which would have been correct, also scans.

### Which filters are claimed

A helper returns, for one column, the index of the first filter that is usable, is not a `runtimeSet` and has a non-null `equalitySeekKeyCount`. Both the primary-key check and the secondary-index loop use it in place of their `f.op === '='` tests.

**A multi-value `in` is only ever the sole seek column.** Walking an index's columns in order:

- A multi-value `in` (`isMultiValueEquality`) on the first column is claimed, and the match stops there.
- A multi-value `in` on a later column ends the match before it: it stays a residual, and the columns before it seek as today.

The reason is an engine defect: with a composite seek, Quereus turns a bound `=` beside an `in` into a NULL key and the seek returns nothing. Measured on a plain memory table, `where a = ? and b in ('p','q')` over an index on `(a, b)` returns no rows where two match. Claiming composite seeks here would turn today's correct `a = ?` prefix seek plus residual into an empty result. The defect and the proposed fix are in the `blocked/` ticket `quereus-composite-in-seek-drops-a-bound-equality`, which also records lifting this limit. A single-element `in (?)` is not multi-value: the engine emits an ordinary equality seek (`plan=2`) for it, so it counts as `=` here.

On the primary key this means a multi-seek needs a single-column key. A composite primary key's `in` stays a scan with a residual, as it is now. A key fully bound by `=` and single-element `in` remains the point seek.

`runtimeSet` filters (`in (select …)`) are not claimed, which the engine's contract allows. See backlog `feat-optimystic-in-subquery-seeks-the-index`.

### Cost and row estimate

Let `N` be `tableRowCount`, `K` the value's `equalitySeekKeyCount`, `seek = log2(max(2, N)) * 2`, and `perKey` the rows one value matches (1 for a fully matched unique index, else `N` times the selectivity).

```
rows = max(1, floor(min(N, K * perKey)))              -- the memory module's formula
cost = K * seek + rowTerm
rowTerm = min(N, K * perKey)   when perKey is measured (`analyze` statistics) or the seek is unique
        = perKey               when it is the no-statistics constant
```

At `K = 1` this is exactly today's `=` cost, so it replaces the existing arithmetic instead of sitting beside it. The primary key is the same with `perKey = 1` and no row term: `cost = K * seek`, `rows = max(1, min(N, K))`.

- **`rows` saturating at the table size is what produces the hash joins.** It is how a memory table gets them, and measured over four un-analyzed tables, a prototype of this formula gave the memory plan's join shape at `K` = 2 (nested loop), 5 and 31 (hash joins), and hash joins under `cost_profile: 'distributed'` at 2, 5, 31 and 44.
- **The two row terms differ on purpose.** The no-statistics constant 0.1 reaches the whole table at ten values, so charging `K * perKey` would price every list of ten or more above a scan on an un-analyzed table, including the reporter's. Measured statistics do not have that problem: `K * perKey` reaches `N` only as `K` nears the column's distinct count, which is where a scan really is cheaper. Charging `perKey` once also keeps `a in (x, y)` above `b = ?` on equal terms (140 against 120 at `N = 1000`), so the planner does not prefer the list that fetches more.
- **A long list still costs out as a scan.** Each candidate is compared to `tableScanCost` as now. At the un-analyzed default of 1000 rows the crossover is at 46 values by this formula, and the prototype measured a seek at 44 and a scan at 60. A scan at that point goes back to the reporter's nested-loop plan under the in-process cost profile; the `distributed` profile keeps hash joins over it. `analyze` raises the crossover along with the row count. Record this as a `NOTE:` tripwire at the formula: if pages of more than about 45 values show up slow on un-analyzed tables, the no-statistics default is what to look at. No separate key cap: with single-column seeks the list length is what the statement's author wrote, and the cost already bounds it.
- **Multi-seek plans report `isSet: false` and no `providesOrdering`**, as both Quereus backends do. `bestOrdering` must be cleared when a multi-seek wins, and `orderingMatchesIndex` is not consulted for one.

`equalityTupleSelectivity` needs to say whether its answer was measured. Split out a function returning `number | undefined` and keep `equalityTupleSelectivity` as that `?? EQ_SELECTIVITY_WITHOUT_STATS`.

The primary-key arm must stop being a `break` for the multi-value case: a long list may lose to a scan or to a secondary index, so it competes on cost like the others, and the secondary-index loop still runs. Only a single-key full primary-key match keeps its early exit and its "secondary indexes are skipped" rule.

### Running it

`runQuery` gets the seek list from `filterInfo.args`: `plan=5` means one single-value seek per argument, anything else is the one tuple `args`, as now. Throw if a `plan=5` `idxStr` carries a `seekWidth` other than 1 (`decodeIdxStr` is exported), since this module never claims one and reading it as width 1 would seek on wrong values.

- **Secondary index.** `executeIndexScan` takes the list of seek tuples. It skips any tuple holding a NULL or undefined (the existing guard, now per tuple), frames each, drops repeated framed keys, sorts them with the same `<` comparison the tree uses (`resolveTreeArgs` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`), and runs the existing entry loop once per key, verification included. With more than one key it also tracks the primary keys already yielded and skips repeats.
- **Primary key.** `executePointLookup` takes the same list: skip NULL-bearing tuples, build each key, drop repeats, sort, read each row. Add the `planType === 5` arm in `runQuery` ahead of the `plan=2` arm. Without it a `_primary_` multi-seek would fall through to the full table scan and return every row with the filter already dropped.
- **Views.** Nothing changes in how `runQuery` builds them: one refresh per tree before the first seek for a live read, one pinned pair for a committed read. Never refresh per value.
- **Trace.** One `index:seek` line per scan. `seek=` lists each sought key, printed by `printableSeekKey` and joined with commas, in the order sought; `matched` and `rejected` are totals across them; `unset` means nothing was sought (every listed value was NULL).

Why frame-level dedupe is not enough on its own: on a live read, a row whose indexed value moves from one listed value to a later one between seeks has an entry under each key and would pass verification under the second. The same shape arises in `update t set c = 'b' where c in ('a', 'b')` if the statement's staged entries are visible to a later seek. The yielded-primary-key set closes both, at a memory cost proportional to the rows returned.

## Tests

New `packages/quereus-plugin-optimystic/test/in-list-index-seek.spec.ts`, using the harness in `test/access-plan-estimates.spec.ts` (`openDatabase`, `query_plan`):

- **The bug.** The reporter's 31-parameter query over four un-analyzed tables plans an `INDEXSEEK` on the `entry_id` index and `HASHJOIN`s, with no `FILTER`, `SEQSCAN` on `log_entry_items`, or `JOIN`, under the default and `distributed` profiles, and returns the right rows when run.
- **Differential.** One table with the index and an identical one without it, loaded alike. A table-driven list of the statements marked "differential" above must return equal row sets from both, and each indexed statement that should seek must plan an `INDEXSEEK`. Include the primary-key forms.
- **Collation and type.** The three statements in the table under *Which seeks can be trusted*, plus their `in` forms.
- **Planner.** Direct `getBestAccessPlan` calls: the `K = 1` cost equals the `=` cost; claimed at 31 and unclaimed at 60 for `N = 1000` without statistics; unclaimed when `K` nears a measured distinct count; partial index and `runtimeSet` unclaimed; `isSet` false and no `providesOrdering` for a multi-seek; the first of two equality-role filters claimed.
- **Update.** `update t set c = 'b', n = n + 1 where c in ('a', 'b')` over an indexed `c` adds exactly 1 to every row.
