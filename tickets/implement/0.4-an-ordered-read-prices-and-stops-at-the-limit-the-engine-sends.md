## What Quereus 5.4 does, read from its source

The plugin already requires `@quereus/quereus` `^5.4.0`, so all of this is live.

- **A constant LIMIT over an ORDER BY** (`tryLimitedSortAbsorb`): the module is asked `getBestAccessPlan` with `requiredOrdering` plus `limit` / `offset`. The answer is validated by `probeAccessPlan`: if the chosen plan leaves any filter unclaimed (`truncationIsSafe` fails — a `Filter` above could reject rows), the engine **asks again with the limit and offset removed** and uses that answer. So a candidate that leaves a residual is, in the plan the engine keeps, always priced without a limit.
- **A placeholder `limit ?`** (`tryRuntimeLimitChoice`): the engine first asks with no limit. If that answer already delivers the ordering it absorbs the Sort unconditionally and stops. Otherwise it asks with `limit: 1, 2, 4, …` (offset 0) and bisects for the largest bound whose answer still delivers the ordering (`largestOrderedBound`), then plans a `LimitChoiceNode` that runs the ordered plan only when the execution's actual `limit + offset` is at most that bound, and scan-then-sort otherwise.
- **Nothing of the limit reaches `query()`.** `FilterInfo.limit` is set only by `OrdinalSlice`; a sort-absorbed walk runs as `plan=0` with no arguments and no limit, and a residual walk looks identical at run time. The module cannot tell, inside `query()`, whether the walk it is running was planned as a licensed page.

That last fact decides question 2 below and shapes question 1.

## Decisions

### 1. Pricing an ordered walk

Two kinds of walk candidate, told apart at plan time by whether `request.filters` is empty (a walk claims no filter, so it "claims every filter" exactly when there are none):

- **A walk with no filters** is priced as what it costs at run time, *including* the scan switch it cannot avoid (decision 2):
  - `wanted = min(tableRowCount, limit + offset)` when `request.limit != null`, else `tableRowCount`;
  - `cost = seekCost + ROW_FETCH_COST · min(wanted, WALK_ROWS_BEFORE_SCAN)`, plus, when `wanted > WALK_ROWS_BEFORE_SCAN`, the scan and sort it finishes with: `tableScanCost + sortCost(tableRowCount)` (the same `Math.max(1000, tableRowCount)` the full-scan candidate uses — pass it through `PlanPricing` rather than recomputing it).
  - `ROW_FETCH_COST = 5`: one row fetched through the main tree by primary key, against a scan's 1 per row. Source: the "about five times what a scan costs per row" measured for GitHub #52 and already stated in `docs/internals.md`. Define it next to `SORT_COST_PER_COMPARISON` with that provenance.
  - Consequence: an unlimited ordered read of any table over 256 rows is sorted by the engine (a scan and sort is the cheaper of the two by the 256 fetches it saves); a page of up to 256 rows is walked; a `limit ?` gets a `LimitChoiceNode` whose bound is at most 256. Since a request with no filters has no seek candidates at all — only the full scan and the walks — the 5× factor decides walk-versus-scan-and-sort and nothing else, so it tilts no comparison against a seek.
- **A walk under residual filters** keeps today's price, `seekCost + tableRowCount` at one unit per row, and ignores any limit. This is a deliberate bet, not an estimate: the engine strips the limit from any plan that leaves a residual (above), so the module can never price such a walk as a page, and pricing it honestly at full length would make every filtered page (`where status = 'open' order by created desc limit 20` over an index on `created` alone) a scan and sort of the whole table. The scan switch bounds what the bet costs when no limit was there: at most `WALK_ROWS_BEFORE_SCAN` fetches on top of the scan and sort (about 8 ms at GitHub #52's 31–38 µs a row). Record it as an accepted-tradeoff `NOTE:` on `orderedWalkCandidate`, with the revisit condition: the walk claiming its residual filters itself (backlog `feat-an-ordered-walk-tests-its-own-residual-filters`), after which it is priced like a walk with no filters.

### 2. `WALK_ROWS_BEFORE_SCAN` stays, for every walk and range

It cannot be narrowed to residual walks and ranges, because nothing at run time distinguishes a licensed page from a residual walk (no limit reaches `query()`). It also still earns its place on a walk with no filters: a table analyzed small that has since grown, or an un-analyzed one far above the 1000-row default, can get an unlimited walk planned, and the switch is what keeps that read at scan-and-sort cost. Decision 1 makes the planner model the switch, so the plan's price and the run time's behaviour now agree.

Rewrite the constant's doc comment and `NOTE:`:

- Drop the claim that "a statement's LIMIT never reaches the module". Say instead that the limit reaches the planner but not `query()`, so the walk cannot tell a licensed page from a residual walk, and that the planner prices the switch in (`orderedWalkCandidate`).
- New revisit condition: *if Quereus ever forwards a licensed `limit + offset` to `query()` (through `FilterInfo`), lift the switch for a walk or range that carries one and drop the scan term from a licensed walk's price, so a page larger than 256 rows on a large table is walked rather than scanned and sorted.* Keep the existing range half of the note (a range of more than 256 entries reads the whole table).

No explicit truncation at `limit + offset` is added to the walk. The walk is already stopped by its consumer, and truncating the raw walk would be wrong: `inEngineOrder` reorders runs of surrogate-bearing text, so the first `limit + offset` rows in tree order are not the first in engine order. Truncating after the repair would change nothing. Say this in one sentence on `orderedWalkCandidate` so the next reader does not add it.

### 3. `limit ?`

Price against the bound exactly as against a constant limit; the engine re-asks per bound. Truncation at the bound can never underproduce, because the module truncates nothing (decision 2) and the engine runs the ordered branch only for `limit + offset ≤ bound`. The bisection relies on the ordered answer being monotone in the bound: under decision 1 the walk's cost rises with `wanted` up to 256 and then jumps above the scan and sort, so the ordered plan is kept up to a threshold and lost above it.

### 4. One licence rule for every candidate

Add one helper — the counterpart of `rowsToProduce` in `@quereus/quereus-store/src/common/store-module-access-plan.ts` — that returns the rows a candidate reads: `min(rows, limit + offset)` when `request.limit != null`, the candidate delivers the required ordering, and it claims every filter; otherwise `rows` unchanged. Apply it to:

- the ordered walk (decision 1's `wanted`; it qualifies only with no filters);
- `rangeSeekCandidate`, to the row term of its cost when it delivers the ordering and claims every filter (a further same-side bound or a filter on another column leaves it unlicensed); its 1-per-row price and `RANGE_BOUND_SELECTIVITY` are otherwise unchanged — the switch already bounds a bad selectivity guess;
- `equalitySeekCandidate`, to its row term when it delivers the ordering (a single-key seek) and claims every filter.

The Quereus contract is explicit that pricing some candidates against the bound and not others biases the comparison. Today `orderedWalkCandidate` prices a residual walk against the limit, which breaks that rule; this removes it. `rows` on every candidate stays the cardinality estimate (the engine applies the limit), as the existing test "prices a plan-time limit as the rows it stops after" pins.

### Out of scope

An equality or range seek fetches each row through the main tree exactly as a walk does, so by the same measurement it also costs about 5 per row, not 1. Correcting that moves every seek-versus-scan crossover and join choice, and is not what this ticket is about; decision 1 is safe without it because, with no filters, no seek competes. Mention it in the *Pricing* paragraph of `docs/internals.md` as a known approximation, not as a ticket.

## Edge cases & interactions

- `limit` arriving as `null` is absent (`!= null`, as today). `limit 0` gives `wanted = 0` and a cost of one descent. `offset` without being added to the bound underproduces nothing here (no truncation) but must still be added to `wanted` for the price. Verified by inspection.
- `wanted` exactly `WALK_ROWS_BEFORE_SCAN`: no scan term in the price, and none at run time (the switch fires on the entry *past* 256, per `verifiedIndexRows`). The existing "scans nothing for a read the threshold covers" case with `limit 256` must still walk and report `scan=0`. Verified by that test.
- A licensed page whose first rows are surrogate-bearing text still switches at run time when the held run outlasts 256 entries (existing case "a limit met from a held run longer than the threshold"); the planner, priced at 10 rows, still chooses the walk. Unchanged; the test keeps covering it.
- A table smaller than 256 rows (or the scan's 1000-unit floor): an unlimited walk can still win (`5 · rows + seekCost` against `1000 + sort`). Correct — such a read never reaches the switch. Verified by inspection.
- `rule-minmax-index-boundary` (`max(t)`, `min(t)`) sends `limit: 1` with an ordering and no filters: still a one-row walk. Covered by "answers min and max from the ends of the index" and the committed-read `max` case.
- A residual walk asked with a limit must price exactly as without one, so the engine's limited first probe and its limit-free re-probe give the same answer. Pin with one planner-level case (below).
- `limit ?` over a table where the limit-free answer is already a walk (tiny table, or a residual walk): the engine absorbs the Sort unconditionally — the residual walk's bet, or a read under 256 rows. Nothing to do; by inspection.
- Ordering claim rules (which columns, types, direction, NULLs) are unchanged, but almost every planner-level and SQL-level case that asserts a walk was chosen does so with no filter and no limit, which now plans a scan and sort. Those cases must pass a page-sized limit so they keep testing the claim — including the `expectSorted` cases, which would otherwise pass for the wrong reason (sorted because unlimited, not because the claim was refused). This is the largest part of the test work; do not weaken any assertion to get there.
- `index-ordered-walk.spec.ts` › "A long index walk finishes by scanning the table": the unlimited no-filter shapes (`order by t, id`, `order by t desc, id desc`, `order by t, id limit 300`, the nullable `order by u, id`) will no longer plan a walk. Keep the switch covered by giving each a residual that keeps every row and that the engine cannot fold away — e.g. add an unindexed column set to one value on every row and filter on it — so a residual walk (decision 1's bet) still reads past 256. The range shapes keep their switch unchanged. `expectOrderFromIndex` must still pass for each.
- `index-range-seek.spec.ts` and any other spec (grep for `INDEXSCAN`, `expectOrderFromIndex`, `scan=`) whose plan assertion leaned on an unlimited walk: fix the shape, never the assertion.
- Concurrency, committed reads and the order repair are untouched: the run-time read path does not change. By inspection.

## Tests

Plan-shape cases only, one per rule that changes, in `ordering-claim-guard.spec.ts` (the differential specs already compare rows against a memory table):

- An unlimited ordered read with no filter over the 1,000,000-row fixture is left to the engine's Sort (`expectSorted`, scan claiming nothing).
- The same request with `limit: 10` walks the index (keep / adapt "prices a plan-time limit as the rows it stops after").
- The same request with `limit: 300` (past the switch) is sorted by the engine.
- A residual walk (`eqFilter(PRICE)`, `asc(NAME)`) prices identically with and without `limit: 10` — the licence is not applied to a candidate that leaves a filter.
- An ordering-delivering range or equality seek that claims every filter is priced lower with a limit than without (one case covers the shared helper).

Adapt, rather than add, wherever an existing case already states the rule: "beats the same seek when the seek matches most of the table" asserts the old premise that walking a million entries beats sorting them; with a residual it is decision 1's bet and still walks, so check it still holds and reword its comment to the bet, not the false premise.
