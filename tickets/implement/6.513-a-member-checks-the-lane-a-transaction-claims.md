# A member checks the lane a transaction claims

Third of four implement tickets from the plan `a-transaction-carries-its-lane`. The plan's decision, open for a human to edit: **the classification is the engine's, validated by peers, never inferred by a member from the transforms.** A member that disagrees refuses the pend with a reject marked as a validity judgement, under the same marker rules as the five existing validity refusals (`docs/internals.md` §*A reject that judges the transaction itself wrong says so in its signature*), rather than reclassifying.

## What a member can and cannot check

The previous ticket split the rule into two layers for this reason. The replicated statements a member re-executes are rebuilt from evaluated row values (`TransactionBridge.addStatement`'s `NOTE:`), so a key the writer computed with `StampId()` arrives as a literal and a `set n = n + 1` arrives as `set n = <value>`: provenance and read-dependence (the writer-only clauses) are not recoverable on the member. What a member **can** compute identically to the writer is the **ceiling** (`laneCeilingOf`): the table's profile, the constraints the write touches, the merge tags of the assigned columns, the operation and selection shape, all from its own catalog (which the schema-hash check has already proven equal) and from the rebuilt statement's write description. Two facts make the check sound against an honest writer:

- an honest writer's lane is at or below the ceiling of each original statement, and a rebuilt per-row statement has the same table, operation, assigned columns and constraints as the original, and a `rows` selection wherever the original had one (the original's `global` selection made the writer answer `serializable`, which every member accepts);
- `serializable` is always acceptable, so the check refuses only a `convergent` claim whose ceiling the member computes as `serializable`.

So the check cannot catch a writer that lies about freshness or a read; that is the replay stage's guards' business at merge time, and the bound must be stated at the check and in `docs/transactions.md`.

## The seam

- `ITransactionEngine` gains an optional `laneCeiling?(transaction: Transaction): Promise<Lane>`: the stricter ceiling over the transaction's statements as this engine's catalog sees them. `ActionsEngine` omits it (every actions transaction is `serializable`, and nothing is to check). `QuereusEngine` implements it: for each statement, `db.prepare(sql).getWriteScope(params)` (`Statement.getWriteScope` in `@quereus/quereus/src/core/statement.ts`), then `laneCeilingOf` per write site against `db.schemaManager.findTable`, folded with `stricterLane`. A statement with no write site contributes nothing. A table the catalog cannot find is `serializable`.
- `TransactionValidator.validate`, after the schema-hash step and before re-execution (the ceiling needs no re-execution, and refusing before it saves the work): when `transaction.lane === 'convergent'` and the engine offers the method and it answers `serializable`, return `validityRefusal('Lane mismatch: transaction claims convergent, this node computes serializable')`. A `serializable` claim is never checked. An absent lane (an older writer, tolerated at this ingress by the first ticket) is `serializable` and never checked. A throw out of the method is a `VALIDATOR_FAULT` by the existing `checkPendValidation` conversion in db-p2p, unmarked, which is right: the node could not judge.
- The marker flows as it does for the other five: `validityRefusal` sets `validity`, `checkPendValidation` passes it through, `voteFor` signs it, and the writer sees `ValidityRejectedError`. `classifyCommitFailure` already maps that to a terminal `rejected` for the offline queue. Nothing new to plumb; verify by reading those three sites.

## Edge cases & interactions

- **No deployment validates at pend today** (backlog `feat-no-deployment-validates-transactions-at-pend`), so this check runs in `mesh-client-signature-enforcement.spec.ts`'s shape and in unit tests only. State that at the check; it is still the right place, since the long-lived-pend ticket's late signer is a validator.
- **A bare `Collection.sync`** carries no validation payload and no statements, so its entry's lane (the collection's declaration) is taken at face value by every member. The `unvalidatablePendPolicy` branch already covers that shape; say in the doc that the collection-level declaration is the only authority for it.
- **The `getWriteScope` cost.** One analysis plan per DML statement per validated transaction, on the member. Comparable to the re-execution's own planning. Record as a `NOTE:` tripwire at the method: memoize per statement text if it ever shows in a profile.
- **A member whose catalog is behind** fails the schema-hash step first and never reaches this check. By inspection of step order.
- **Mixed builds.** A member on a build without the method accepts the claim unchecked, as it accepts everything about the lane. A writer on an older build sends no lane; never checked.
- **A validity refusal beside an unmarked reject** stays thrown to the writer, as today (`validityRejectionOf`). Unchanged.

## Tests that pay for themselves

One case in `packages/db-core/test` for the validator, beside the existing validity-refusal cases: an engine double whose `laneCeiling` answers `serializable` makes a `convergent` transaction refuse with `validity` set and a `Lane mismatch` reason, and a `serializable` transaction pass without the method being called. That pins the contract on branching (which claim is checked, that the marker is set). Nothing in db-p2p: the marker's signing and classification are already pinned by the validity-marker specs, and `QuereusEngine.laneCeiling` is a fold over the previous ticket's tested rule.
