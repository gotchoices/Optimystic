# File store syncs by the earliest deadline

Fourth of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). `storage-flush-takes-a-sync-deadline` gave `BatchBackend.commit` a `syncWithinMs` and a `durable` promise, and adapted `FileBatchBackend` and `FileKVStore` to it without deferring. This ticket makes `FileWriteLog` defer.

## Today

`FileWriteLog.commit(entries)`, in `packages/db-p2p-storage-fs/src/file-write-log.ts`, runs one task in the log's serial queue. The task appends the record, calls `handle.sync()`, applies the batch to the tree (`applyBatch`), and resolves. A tree file only ever holds content whose log record is durable, and that is what lets replay rebuild a prefix.

## After

`FileWriteLog.commit(entries, { syncWithinMs }): Promise<CommittedBatch>`:

- **Append, in the queue:** open, check `closed` and `fault`, encode, `writeAll` the record, add to `appendedBytes`, and push `{ entries, deadline: Date.now() + syncWithinMs, durable: deferred }` onto an in-order `unsynced` list. The record has reached the operating system, so it survives a process crash: the next open's replay applies it.
- **Strict** (`syncWithinMs` 0), **or the earliest unsynced deadline has already passed:** run the sync step (below) in the same queued task before resolving, so the returned `durable` is already settled. The second case is the backpressure the decision asks for. When the disk falls behind, writers wait for it instead of the window quietly growing.
- **Otherwise:** arm a timer, through the log's existing `setTimer` (injectable, unref'd), for the earliest unsynced deadline. Re-arm it only when a new deadline is earlier. Resolve `{ durable }`.
- **Sync step** (always a queued task, so it covers exactly the records appended before it): `handle.sync()`; then `applyBatch` for each unsynced batch in order into `this.dirty`; resolve each `durable` in order; clear the list; disarm the timer; `scheduleCheckpoint()`. If it finished after the earliest deadline it covered, log `write-log` `window-overrun` once per episode, with the lateness in ms and the count of batches. An episode ends at the next on-time sync.
- **Timer fires:** enqueue the sync step. A failure there is logged on the `write-log` channel, like a background checkpoint failure.
- **`sync()`** (the `BatchBackend` method `FileBatchBackend` forwards, and what `FileKVStore`'s group calls): enqueue the sync step and resolve when it has. With nothing unsynced, it resolves without touching the disk.
- **Failure** anywhere in the sync step latches `fault` and rejects every pending `durable` with `StoreFailedError`. Later commits, flushes and `whenDurable` then refuse, as today.
- **Reads:** the tree gets a batch only after its sync, so `FileBatchBackend.get`, the listings and `FileKVStore` reads do not see unsynced batches. The `WriteGroup` overlay above each store keeps serving them until `durable` resolves, which is the contract `storage-flush-takes-a-sync-deadline` set. Replace the `NOTE:` on `commit` about the apply being inside the commit's latency: the apply now happens at sync time, for every batch the sync covers.
- **Checkpoint seal:** inside the `seal` queued task, before the rename, run the sync step if anything is unsynced. A sealed segment then only ever holds synced records whose tree writes are done, which is what the checkpoint's sync-then-truncate relies on. The idle checkpoint (5 s after the last append) therefore also bounds how long a record can stay unsynced if a timer were lost.
- **Last release:** `shutDown` drains the queue. The final checkpoint's seal then syncs whatever is unsynced. Check that ordering holds when nothing was appended since the last checkpoint but something is unsynced: `seal` returns early on `appendedBytes === 0`, and unsynced records always have bytes, so it cannot. Assert it by inspection in a comment.

`FileBatchBackend.commit` passes `syncWithinMs` through and returns the log's `CommittedBatch`. `FileKVStore`'s group already passes whatever its flush asked for. Its callers (the under-replication ledger, `PersistentTransactionStateStore`) flush strictly or not at all. A strict `FileKVStore` flush therefore syncs the shared log, and that also covers every relaxed raw-store record appended before it, by the prefix rule of one log. That is how write order 8 holds for free when both stores share a base path.

`FileBatchBackend.durability` stays `'power-loss'`: a flushed write survives a power cut once its window has passed or `whenDurable()` has resolved.

## Edge cases & interactions

- **Prefix after a power cut.** The log is one append-only sequence, and replay stops at the first torn or CRC-failing record. If the operating system wrote a later page of the log but not an earlier one, the earlier record fails its CRC and replay stops there. What survives is a prefix (by inspection; state it in the README's *What a crash loses*).
- **Process crash with unsynced records.** Replay applies them, so nothing a flush resolved is lost (test).
- **Tree untouched until sync.** No tree file may hold content from an unsynced record. Otherwise a power cut could keep a tree file from group N+1 while losing group N's log record, which breaks the prefix (test).
- **Interleaving of strict and relaxed groups.** A strict commit arriving with relaxed records unsynced makes one sync and resolves every earlier `durable` in order (test).
- **A timer firing after a strict commit already synced everything** finds an empty list and does nothing (by inspection).
- **Two stores sharing one log** (raw and key-value over one base path) each keep their own overlay. The shared sync applies both stores' batches in log order (by inspection; the existing shared-log test must stay green).
- **`appendedBytes` and the size-triggered checkpoint** count appended bytes, synced or not. A size checkpoint therefore forces a sync, which is correct (by inspection).
- **Memory.** Unsynced entries are held twice, in the `WriteGroup` overlay and the log's `unsynced` list, until the sync. Both are bounded by the window and by `WriteGroup`'s `maxUnsyncedBytes` per store (by inspection).
- **win32.** `handle.sync()` works on files. Directory syncs stay checkpoint-only (unchanged).
- **The `NOTE:` at `syncDirtyPaths`** about rewriting a file during a checkpoint still holds: tree writes now come from the sync step, which runs in the queue like the old commit apply (by inspection).

## Tests

In `packages/db-p2p-storage-fs/test/file-write-log.spec.ts`, using `fs-injection.ts` (add a sync-call counter, or interception on `FileHandle.sync`, if one is not there) and an injected `setTimer`:

- **Relaxed commits share one sync, made when the deadline timer fires, and the tree is written only then.** Two commits with `syncWithinMs: 5000` both resolve with no `sync` call and no tree file for their paths, and their `durable` promises are pending. Fire the timer: one `sync`, both tree files written, both `durable` resolved in order.
- **A strict commit after relaxed ones syncs once and settles them all.** Two relaxed, then one with `syncWithinMs: 0`: it resolves with all three `durable` settled after a single `sync`.
- **A relaxed commit survives a process crash.** One relaxed commit, then abandon the log without closing, the way the existing crash test simulates a crash, and reopen. Replay restores the value.
- **A checkpoint syncs and applies unsynced records before sealing.** One relaxed commit, then `checkpoint()`. Afterwards the tree holds the value, the log is header-only, and the `durable` has resolved.

No real power-loss test is possible on a live filesystem. The prefix argument is by inspection.
