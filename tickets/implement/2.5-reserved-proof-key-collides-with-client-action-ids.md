# Give commit proofs their own store instead of a reserved key in the transactions store

## What is wrong

A node keeps two different kinds of record for a block: the **transforms** that make up its history,
and the **commit proofs** that certify particular revisions. Today both live in the same place — the
transactions store — separated only by a naming convention. A proof for revision *N* is filed under
the made-up action id `~proof:<N>` (`blockProofActionKey` in `raw-store-codec.ts`), on the assumption
that no real action id ever starts with `~`.

Nothing enforces that assumption. An action id is chosen by whoever originates the write and is never
re-derived or format-checked by the node that stores it. So a client can pend an action literally
named `~proof:5`, and a peer can hand over an archive whose action is named `~proof:5`. Either lands
on the key a proof uses, and whichever write happens second wins.

## Verified reproduction

Ran against `MemoryRawStorage` + `StorageRepo`/`BlockStorage` (temporary spec, since removed). All
three orders reproduce today:

**Order A — committed history is silently rewritten.** Pend and commit an action with
`actionId = '~proof:5'` at revision 1 (accepted; `success: true`), then retain a proof for revision 5
of the same block. `getTransaction('~proof:5')` now returns the proof object where the committed
insert transform used to be. The user-visible fallout observed: a later client pending against the
stale revision gets the "here is what you missed" catch-up response, and revision 1's entry comes back
as

```
{"actionId":"~proof:5","rev":1,"transforms":{"inserts":{},"updates":{},"deletes":[]}}
```

— an **empty** transform set. The client is told revision 1 changed nothing and replays a history that
is quietly missing a write. No error anywhere.

**Order B — a retained proof vanishes.** Save a proof for revision 5, then commit a client action
named `~proof:5`. `getBlockProof(5)` returns the client's transform. The proof is gone with no signal;
repair falls back to corroboration as if the node had never retained one.

**Order C — a peer's archive does the same.** A restore archive whose action id is `~proof:5`
(peer-supplied, `BlockStorage.saveRestored`) overwrites the retained proof on the way in.

A **fourth** route exists that the original report did not list, and it needs no transactions write at
all: `saveRestored` also writes the *revisions* store, and `materializeBlock`
(`packages/db-p2p/src/storage/block-storage.ts:433`) later feeds any revision's action id back to
`getTransaction` when replaying a revision whose materialization was pruned. A revision record naming
`~proof:5` therefore reads the proof as a transform during replay. That route reaches storage from
`saveReplica`/`saveDeletion` → `saveForwardRevision` → `saveRestored`, i.e. from
`BlockTransferService.handlePush` and `cluster/reconcile-block.ts`.

Forgery is *not* among the consequences — `verifyBlockCommitProofClaim` is total on hostile input and
answers `malformed-proof` for a transform-shaped value. The damage is corruption and denial.

## Chosen shape, and why

The source ticket offered two options: guard the reserved namespace at the untrusted seams, or stop
sharing the keyspace. **Take the second: give proofs their own logical store.**

The deciding evidence is the fourth route above. The guard approach needs a complete — and
permanently maintained — enumeration of every writer that can put an externally-chosen id anywhere the
reserved key is reachable from, and the first careful pass over that enumeration already turned up a
route the report had missed, in a second store. The guard also cannot simply live at the bottom of the
stack: `CachedRawStorage` routes its own `saveBlockProof` back down through
`RawStorageDriverAdapter.putTransaction` → `inner.saveTransaction` with the reserved key, so a blanket
check in `KvRawStorage.saveTransaction` would break the proof path itself. A correct guard is therefore
several careful, easily-missed placements; splitting the keyspace deletes the question instead.

Cost was measured rather than assumed, and it is mechanical:

- Six `RawStoreDriver` implementations, each already following a per-store pattern:
  `MemoryStoreDriver` (157 lines), `CachedStoreDriver` (859), `RawStorageDriverAdapter`,
  `FileStoreDriver` (422), `SqliteStoreDriver` (217), `LevelDBStoreDriver` (203),
  `IndexedDBStoreDriver` (188).
- No data migration. `AGENTS.md` states backwards compatibility is not yet a concern; the SQLite
  schema is `CREATE TABLE IF NOT EXISTS` DDL in `db.ts`, the IndexedDB `upgrade` hook is guarded by
  `objectStoreNames.contains` behind a `DEFAULT_DB_VERSION` to bump, and `keys.ts` in the LevelDB
  package explicitly reserved spaced tag bytes "so a future logical store can slot in between"
  (`0x06`–`0x0F` are free below `TAG_KV = 0x10`). Proofs are advisory retention — losing the ones
  already written under the old key degrades to corroboration, which is an already-supported state.
- The test doubles that implement `IRawStorage` directly (`storage-monitor.spec.ts`,
  `block-transfer.spec.ts`, `rebalance-reaction.spec.ts`, `mid-ddl-crash.spec.ts`) already stub
  `getBlockProof` / `saveBlockProof` at the `IRawStorage` level and are untouched by a driver change.

## Design

Add a sixth logical store to `RawStoreDriver`, keyed by `(blockId, rev)` and valued as bytes — the
same shape as the revisions store, which is already `(blockId, rev)`-keyed:

```ts
// proofs store — keyed by (blockId, rev)
getProof(blockId: BlockId, rev: number): Promise<Uint8Array | undefined>;
putProof(blockId: BlockId, rev: number, value: Uint8Array): Promise<void>;
```

`KvRawStorage.getBlockProof` / `saveBlockProof` then delegate to those instead of building an
action-id key, and `blockProofActionKey` is deleted along with the reserved-namespace convention.
Nothing else in `IRawStorage` changes — the public storage surface is already
`getBlockProof(blockId, rev)` / `saveBlockProof(blockId, rev, proof)`.

**No `deleteProof`.** That matches today exactly: `RawStoreDriver` has no revision delete either
(invalidations write compensating forward revisions), and the contract note in `i-raw-storage.ts` says
a proof lives and dies with its revision record. Do not add unused surface; carry that note across to
the new store's doc comment.

**`CachedStoreDriver` should pass proofs straight through to the inner driver rather than gain a sixth
cache namespace.** Proof reads happen on repair and archive-serving paths, not on the hot read path,
and a namespace that is never populated cannot go stale — two delegating methods instead of new cache
state, eviction accounting, and coherence rules. Today proofs are incidentally cached (they ride the
transactions cache), so this is a small, deliberate behaviour change: park it as a `NOTE:` tripwire at
the passthrough — *if proof reads ever show up as hot, give proofs their own cache namespace alongside
`transactions`.*

Per-backend key layout, following each backend's existing convention:

| backend | proofs store |
| --- | --- |
| memory | a sixth `Map`, keyed like `revisionKey` (`blockId`, then `rev`) |
| filesystem | a sixth subdirectory `basePath/<blockId>/proofs/<rev>.json`; JSON-valued, so it takes the corrupt-content-as-missing read guard, and there is no colon to encode |
| SQLite | a `proofs (block_id, rev, value)` table with the same primary-key shape as `revisions`, plus its prepared get/save statements |
| LevelDB | `TAG_PROOFS = 0x06` and a `proofKey(blockId, rev)` using the same 8-byte big-endian rev suffix as `revisionKey` |
| IndexedDB | a `proofs` object store with a `[blockId, rev]` compound key, created in the guarded `upgrade` hook, `DEFAULT_DB_VERSION` bumped |

The write-path `NOTE:` in `kv-raw-storage.ts` ("every value write funnels through the driver
put/delete calls in the methods below") enumerates the choke-point methods; `saveBlockProof` becomes a
real one rather than an alias of `saveTransaction`, so keep that comment accurate.

## Expected behaviour once done

- A client may pend and commit an action with **any** action id, `~proof:5` included, and it neither
  overwrites nor is overwritten by a stored proof — there is no key both can name.
- A restored or pushed archive carrying such an action id likewise cannot disturb a stored proof.
- A block with both committed revisions and retained proofs materialises every revision correctly, and
  the stale-pend catch-up response carries the real transform for every missed revision.
- Every backend behaves identically here, asserted once in the shared conformance suite rather than
  per package.
