# Three facts, each currently stated three different ways — make each one canonical

A design review on 2026-09-14 read the consistency docs side by side and found the same three facts stated inconsistently across `docs/correctness.md`, `packages/db-p2p/docs/cluster.md`, `packages/db-p2p/docs/repo.md`, `docs/architecture.md`, and `docs/optimystic.md`. The fixes below are docs-only — no code changes. The design questions are already resolved (verified against the current code below); this ticket is purely about making the prose match the code and match itself.

## Fact 1: The bar for acknowledging a write

**What the code actually does** (verified against source, current line numbers as of this ticket):

There are three distinct thresholds in the write path, not one, and they get conflated in the docs:

1. **Promise phase (blocking — a shortfall throws).** The coordinator requires `Math.ceil(peerCount * cfg.superMajorityThreshold)` approving promises before it will move to commit (`cluster-coordinator.ts:535`, default `superMajorityThreshold` = 0.75 via `DEFAULT_SUPER_MAJORITY_THRESHOLD` in `packages/db-core/src/cluster/structs.ts`, resolved by `resolveClusterPolicy`). This is the hard gate: promise-phase shortfall throws (`ValidatorRejectionError`, `ConflictRaceLostError`, or the legacy super-majority error).
2. **Commit-phase signature majority (non-blocking — a shortfall does not throw).** A member signs commit once it has seen enough approving promises; the coordinator logs `commit-majority-reached` once `commitCount >= Math.floor(peerCount * cfg.simpleMajorityThreshold) + 1` (`cluster-coordinator.ts:~907`, default `simpleMajorityThreshold` = 0.51). Separately, `clusterReachedCommitConsensus` (`coordinator-repo.ts:3075-3079`) checks `countApprovingCommitVotes(record) > peerCount / 2` — a strict majority. For integer `peerCount`, `floor(n*0.51)+1` and `floor(n/2)+1` (strict majority) agree at every size that matters here — these are the same bar stated two ways in two files, not two different bars.
3. **The actual acknowledgement gate (what determines the answer to the writer).** `CoordinatorRepo.commit` does **not** answer success on the strength of the commit-signature count. It requires `isDurableMajority(durableHolders, cohortSize)` — `durableHolders > cohortSize / 2` (strict majority), where `durableHolders` is the count of cohort members (including self) whose **storage**, post-reconcile, reports durably holding the revision (`coordinator-repo.ts:3070-3072`, applied at e.g. `coordinator-repo.ts:2590-2593`). A shortfall here returns a retryable `COMMIT_NOT_DURABLE_REASON` conflict, never a false success.
4. **n = 1 skips all of it.** `CoordinatorRepo.commitSolo` (`coordinator-repo.ts:2922-2957`) short-circuits before any of the above: cluster consensus never runs, the lone member self-signs a solo proof, and the write is acknowledged on that basis alone.

The promise-phase super-majority is the practically-binding constraint (it's the only one whose shortfall throws), and it is always ≥ the durability-gate's strict majority, so passing promise phase always leaves the durability gate satisfiable in the no-failure case. This is why the two "bars" you see quoted in different docs (75% and "strict majority") are not actually in conflict — they are two different checkpoints in the same pipeline, and both are real.

**Size-consequence table** (peers that must actively confirm, derived from the promise-phase super-majority `⌈0.75n⌉`, which is the binding constraint):

| n | Promise-phase requirement | Practical consequence |
|---|---|---|
| 1 | consensus skipped (`commitSolo`) | no quorum — self alone acknowledges |
| 2 | ⌈0.75×2⌉ = 2 | both peers must approve |
| 3 | ⌈0.75×3⌉ = 3 | all three must approve |
| 4 | ⌈0.75×4⌉ = 3 | tolerates one absent |

**Where this fact lives (one home): `docs/correctness.md` Theorem 6 ("Durability").**

Rewrite Theorem 6's proof sketch (currently lines ~197-210, which says "consensus requires super-majority of cluster peers to commit, so the transaction is persisted on ≥75% of cluster nodes before the coordinator reports success" — this is the wrong bar for what the *coordinator* reports; 75% is the promise-phase gate, not the reported-durability gate) to state the three-checkpoint pipeline above precisely, plus the size table. Point to — do not restate — the "Commit durability reporting" definition in §2 (line ~64), which already correctly and fully describes the durability-gate mechanism (`WriteDurability` classes, the under-replication ledger, etc.) — that paragraph ends with the note that the acknowledgement rule is unchanged and is now reported via `WriteDurability` on every success; keep that sentence attached to whichever paragraph ends up stating the bar, per the existing note in this ticket's `files:` list.
