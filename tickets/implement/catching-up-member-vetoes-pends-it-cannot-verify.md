Reported from sereus on `@optimystic/*` 1.12.0 (sereus ticket `tickets/blocked/fresh-strand-replica-vetoes-writes-while-catching-up`). A strand replica that has just joined a 3-member cohort and is still pulling blocks votes `reject` on a pend with the signed reason `block <id> unavailable (unmaterializable): cannot verify revision`; one reject of three fails the write with a non-retryable `ValidatorRejectionError`. About 1 run in 4 under parallel load in sereus; a second instance was seen on a control network. The same replica had approved the previous pend on that block while holding no committed revision of it.

## What the fix stage established

**The mechanism the report names cannot produce this reject.** The report attributes the flag to `StorageRepo.get`'s read-driven promotion declining a pending record over a block with no committed base (the `held === undefined` arm). That arm runs only when the read carries a `context`. The vote's read does not: `ClusterMember.validatePendOperations` calls `this.storageRepo.get({ blockIds })` with no context, and on that path a block holding only a pending record (metadata seeded by a pend, no `latest`) reads as a plain `{ state: {} }`, unflagged — which is exactly why the first pend was approved.

**On a context-free read, the flag has one source:** `readBlockHealing` throwing for a block whose metadata HAS a `latest` that `getBlock` cannot materialize locally (no materialization reachable under the revision walk, or a coverage gap whose restore failed). `StorageRepo.get`'s per-block catch then answers `{ state: {}, unavailable: 'unmaterializable' }` and **drops `state.latest`, which the node knows** (`getLatest` reads metadata and never materializes — see the `NOTE:` in that catch). Verified with a throwaway spec: a block whose only held revision is a forward tombstone reads back from `get` as `{"state":{},"unavailable":"unmaterializable"}` while `heldRevisions` returns `{ rev: 5, actionId: 'a5' }` for it. So the vote is asking a revision question and receiving a content failure.

**Which path left the sereus replica with an unmaterializable `latest` is not identified.** Every writer of `latest` (`setLatest`, `saveForwardRevision`, `recover`) merges a covering range and writes a materialization in the same latched step, and an unlatched read racing a commit's prune falls back to the range floor's materialization. A throwaway in-process mesh run (3 machines, the third left out of the cohort for 40 writes so it held none of the blocks those writes created, then 30 more writes with concurrent reads coordinated by the newcomer) passed three times out of three: the newcomer approved pends on blocks it lacked, refused their commits on the fork guard, reconciled, and never vetoed. The only `get:unmaterializable` lines it produced came from reads *pinned below* the newcomer's freshly-reconciled floor (`revision 40 not found during restore attempt`), which are contextful reads, not votes. The sereus debug capture enabled `coordinator-repo*` and `cluster*` only; the next capture should add `optimystic:db-p2p:storage-repo,optimystic:db-p2p:block-storage` — the `get:unmaterializable … error=…` line names the arm. That diagnosis is not a prerequisite for the fix below, which removes the vote's dependence on materialization whatever the cause.

## The defect, and the fix

The promise-round vote needs two facts per block, and both are metadata:

- the committed `latest` revision, for the stale-revision judgement;
- the pending records and their claimed slots, for the reservation (`held`) judgement.

It fetches them through a full block read, so:

1. **Arm 1 — a member whose held `latest` will not materialize vetoes.** The `unavailable` branch in the stale check returns `invalidVerdict(…cannot verify revision)`. Yet the revision IS known locally. And the same member with *no* metadata for the block approves (that answer is unflagged), so approval and rejection disagree on what is one situation: "this member holds no usable base for the block". The design already settled what that situation gets — approve, and let the approved pend's own commit bring the member current (fork guard in `StorageRepo.internalCommit` refuses, the behind-reconcile lands the block; see *A behind member actively reconciles* in `docs/internals.md` and `test/member-missed-commit-heals-at-commit.spec.ts`). A base this node cannot materialize is refused the same way at commit (`readCommitBase` → `refuseMissingBase`), so the heal path is identical.
2. **Arm 2 — the reservation check is blind on the same blocks.** `get` lists `state.pendings` only when it materialized a committed block. On a pending-only block and on an unavailable one, `pendings` is absent, so `validatePendOperations` sees no rivals and skips the `held` judgement there — a rival's pending insert on a block that has no committed revision yet is invisible to the vote, though `StorageRepo.pend` would refuse it at apply.

**Fix (recommended): the vote reads metadata, not blocks.** In `validatePendOperations`, take `latest` from `IHeldRevisionReader.heldRevisions(blockIds)` and the rivals from `IPendingClaimReader.listPendingClaims(blockId)` (already used by `reservingRivals` for slots; `StorageRepo` implements both, cast the same `IRepo & Partial<…>` way the other capability reads in that class do). Neither materializes, so neither can come back `unavailable`:

- `latest` known → stale judgement exactly as today (`staleRevisionAgainst`).
- `latest` absent (`null`: no committed revision) → not stale, as today for a never-seen block.
- the block's metadata unreadable (`heldRevisions` leaves it out) → this member has no answer for the revision; it does not veto on that reason (no approval-vs-rejection split remains: every "cannot establish the base" shape gets the one answer the design gives a member without a base). Log it under the existing `cluster-member:validation-block-unavailable` name so the count stays visible.
- rivals come from the claim listing, so arm 2 closes on the same change. This can introduce `held` votes where there were none (a rival's pending record on a block with no committed revision); that is the verdict storage's own pend gives at apply, moved into the vote, and it is transient by construction.
- Keep a fallback for an `IRepo` without those capabilities (test doubles): use `get` as now, but treat an `unavailable` entry as "no answer for the revision" — the same don't-veto rule — rather than a reject.

Rejected alternatives: **(B) keep the reject but make it retryable** (a `held`-style transient vote) — it would still fail every write that lands in the window and cost the writer a retry round, and a reject on a revision the member actually knows is wrong, not merely slow. **Carry `latest` on `get`'s unavailable entries** (what the `NOTE:` in `StorageRepo.get`'s catch anticipates) — would also fix arm 1, but it changes what every `get` consumer sees and requires widening `CoordinatorRepo.get`'s consult trigger to `isMissing || unavailable`; the vote does not need content, so it should not ask for it.

Safety: a member that cannot check staleness no longer blocks consensus on its own, but it never could stop a stale write alone either — every caught-up member still runs the stale check, the storage fork guard refuses any update-only commit over a base the member does not hold, and the coordinator's durability gate refuses to acknowledge a commit no majority holds. This is the posture the content-digest check already takes for an unmaterializable base (`ClusterMember.validateCommitOperations`: abstain from attesting, vote as before).

Out of scope, recorded only: the report's second fingerprint (`commit-not-durable: 0 of 3 cohort member(s) report holding rev 8 … (local-executed)`, seen once on 1.11.0, not reproduced with logging) — possibly the same catch-up window seen from the commit side; no arm is identified, and nothing here changes the durability gate.

## Test

The reproduction belongs at the vote: one test in `test/cluster-repo.spec.ts` with a real `StorageRepo` over `MemoryRawStorage` whose block holds a `latest` that `getBlock` cannot materialize (a forward tombstone with nothing below it — `BlockStorage.saveDeletion` on a fresh block — reproduces that state directly). A non-stale pend on it is approved; a pend at or below the held revision is rejected with the `stale revision` reason (the revision is known, so the member still judges it). Replace the existing "rejects a pend whose block read came back unavailable" test (it pins the behaviour this ticket reverses) with the fallback rule for a get-only double. Arm 2 is pinned by one case: a rival's pending record on a block with no committed revision yields a `held` vote. No mesh test: the existing `member-missed-commit-heals-at-commit.spec.ts` already covers approve-then-heal-at-commit end to end.
