# Silent read-repair consults back off

Third of the three retries in Sereus `../sereus/tickets/blocked/optimystic-retries-do-not-back-off.md` (gotchoices/sereus#48); the other two are `coordinator-and-read-retries-back-off`, which adds `LinkDeadlines.retryBackoffBaseMs` (the declared `linkRoundTripMs`, 0 when undeclared) that this ticket consumes.

## The problem

Inside the lazy read-repair window a held block is served from the local copy and a cohort consult runs behind the read when the window demands it (`readRepairBlock` → `startHeldBlockConsult` in `packages/db-p2p/src/repo/coordinator-repo.ts`). Every exit of `fetchBlockFromCluster` that reaches a corroboration arms the window (`markBlocksSeen`), and so does the `cohort-too-small` deadlock. The one exit that deliberately does **not** arm is the `!corroborated` exit when a peer was silent: a silent peer can recover and may hold a newer revision, so re-asking can learn something (the comment block above `if (deadlock === 'cohort-too-small')`). That rule is right and stays. Its cost on a slow link: the block stays unstamped, so the very next read starts a new consult as soon as the previous one ends — once per per-peer deadline (`cohortQueryTimeoutMs`, 7 s on the measured link) plus the read interval. Measured in Sereus: 53 consults during the workload, all finding the other member silent, and 224 re-asks in the 180 s after it, one block re-asked about every 8.2 s.

## Design

### A hold, separate from the window

A new collaborator `SilentConsultHolds` in `packages/db-p2p/src/repo/silent-consult-holds.ts`, owned by `CoordinatorRepo`:

```ts
export class SilentConsultHolds {
	constructor(options: {
		/** First hold in ms; 0 disables holds entirely (today's behaviour). */
		baseMs: number;
		/** Longest hold in ms. */
		capMs: number;
		now: () => number;
	});
	/** A consult of `blockId` ended without arming the window because `silent` peers did not answer. */
	noteSilentConsult(blockId: BlockId, silent: readonly string[]): void;
	/** A consult of `blockId` ended any other way. */
	clear(blockId: BlockId): void;
	/** `peerId` answered a request this node made. */
	noteAnswered(peerId: string): void;
	/** Whether a window-demanded consult of `blockId` must wait. */
	holds(blockId: BlockId): boolean;
}
```

Semantics:

- Per block: `{ consecutive, heldUntil, since, silent }`. `noteSilentConsult` increments `consecutive` (restarting at 1 when the prior entry was released — see below), sets `since = now`, `heldUntil = now + min(capMs, baseMs × 2^(consecutive − 1))`, `silent = silent`, and logs `cluster-fetch:consult-held { blockId, holdMs, consecutive, silent }` — once per hold, never per suppressed read.
- **Released when any peer silent in that consult has answered at or after `since`** (`noteAnswered` keeps a per-peer last-answered time). Any, not all: the reason the window stays unarmed is that a recovered peer could answer, and one recovered peer is enough to make re-asking worthwhile. A released entry is deleted, so its count resets.
- `holds` is false when `baseMs === 0`, when there is no entry, when `now >= heldUntil`, or when the entry is released. With `baseMs === 0` `noteSilentConsult` stores nothing and logs nothing.
- Both maps are `LruMap`s bounded at 1000, like the repo's other per-block state (`lastSeenCommitMs`, `unsettledAheadClaims`). An eviction loses a hold, which costs one early consult.
- `capMs` = the repo's existing `reconcilePassTimeoutMs` (35 s at a 7 s per-peer budget). `baseMs` = new `CoordinatorRepoConfig.retryBackoffBaseMs` (default 0), which `createLibp2pNodeBase` fills from `linkDeadlines.retryBackoffBaseMs` in the config it hands `coordinatorRepo(…)`. It is a `CoordinatorRepoConfig` field, not a `ClusterConsensusConfig` one: the cluster member has no use for it.

On the measured link (declared round trip ≈ 2.3 s): holds of 2.3, 4.7, 9.3, 18.7, then 35 s, so a frequently read block is consulted about 7 times in 180 s instead of about 22 — the Sereus estimate.

### Where it is fed

- `fetchBlockFromCluster` returns one more field, `heldBySilence?: readonly string[]`, set **only** at the `!corroborated` exit when `silent.length > 0` and the window was not armed there (`deadlock !== 'cohort-too-small'`; `classifyRepairDeadlock` never yields a deadlock off a pass with silence, so in practice: whenever silent is non-empty at that exit). Every other exit leaves it unset. Required to be considered by both callers:
  - the blocking path in `readRepairBlock` and the background `runHeldBlockConsult` call `noteSilentConsult(blockId, heldBySilence)` when it is set, and `clear(blockId)` otherwise;
  - a consult that **throws** does neither — a thrown consult refutes nothing, as the doubt memo already treats it.
- `noteAnswered`: for every peer in the `answered` list `queryClusterForLatest` returns (every consult of every block; the asker's own statement already counts as an answer there), called in `fetchBlockFromCluster` right after the query; and for every remote peer holding a signature in the `record` `executeClusterTransaction` returns on the pend and commit paths (a vote is an answer). Self is never noted.

### Where it is read

Only in `shouldReadRepair`'s `'lazy'` arm, first: a held block is not window-demanded (the sample-rate arm included). So the hold gates exactly the consults the window governs and nothing else:

- a **missing** block still consults on every read — its absence verdict depends on the cohort (leave a `NOTE:` tripwire at the gate: if missing-block consults to a silent cohort show up as read amplification, hold the latest-query for them too, flagging the absence `peers-unreachable` as the last consult concluded);
- a **floor**-demanded consult still runs (`floorDemandsConsult` — the asker has proof the copy is too old);
- `'paranoid'` still consults every read; `'off'` never does.

A read during a hold takes the existing not-stale branch, which still calls `flagUnconfirmedCurrency`, so it carries exactly the `unconfirmedAheadRev` doubt it carries today. The hold changes when consults are sent, never what a read reports.

## Edge cases & interactions

- **Zero base reproduces today**: with `retryBackoffBaseMs` 0 (every undeclared node, every direct constructor) the next read after a silent consult consults again — test, and every existing read-repair spec passes unchanged.
- **Doubling and cap**: consecutive silent consults double up to `reconcilePassTimeoutMs` and stay there — test.
- **Release by an answer elsewhere**: the silent peer answering a consult of a *different* block releases the hold and resets the count — test. A vote on a pend/commit releases it too — by inspection.
- **A clean consult clears**: a pass with no silent peer (corroborated, or an agreed absence) clears the entry, so a later silence starts again at one round trip — by inspection.
- **Window armed and silent at once** (a corroborated consult with a silent third member): not held — the window already spaces it; `heldBySilence` is unset on armed exits, so behaviour for three-plus cohorts with a corroboration is unchanged — by inspection.
- **Concurrency**: at most one consult per block is already enforced (`heldBlockConsults`); a blocking floored consult and a background one cannot both note outcomes for one block at once except through that same map, and the last writer wins harmlessly — by inspection.
- **Clock**: uses the repo's `now` seam, so specs drive it without waiting.
- **Doubt memo untouched**: `recordAheadClaim` / `unsettledAheadClaims` rules are not changed; the hold sits beside them, not inside them (the `debt-freshness-state-scattered-across-coordinator-repo` backlog ticket is the argument for keeping new per-block state in its own collaborator).
- **Watchers**: a held block's repair lands later, so a change event from read-driven repair comes later on a slow link; the network watch tick (`ReactivityCollectionWatch`) still bounds it — by inspection.

## Tests (only these)

New `packages/db-p2p/test/coordinator-repo-silent-consult-backoff.spec.ts`, built the way `coordinator-repo-held-block-background-consult.spec.ts` and `coordinator-repo-small-cohort-arming.spec.ts` build a repo with a silent cohort peer (a `clusterLatestCallback` that rejects for that peer), `awaitWindowConsults = true` and the `now` seam:

- base 0: two reads after a silent consult each consult (count callback calls) — pins today's behaviour.
- base B, cap C: after a silent consult, a read at `+B − 1` does not consult and still carries `unconfirmedAheadRev` when a claim memo exists; a read at `+B` consults; after a second silent consult the hold is `2B`; after enough, `C`.
- base B: after a silent consult of block X, a consult of block Y in which the silent peer answers; the next read of X consults at once.
