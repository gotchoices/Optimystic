# The membership predicate gates the raw-ring replication paths

The prereq adds `NodeOptions.isNetworkMember` and makes the key network's `findCluster` / `findCoordinator` obey it, which closes cohort admission. Four other senders never go through the key network's membership classification — they take candidates straight from FRET, whose own ring membership is still forgeable by advertising or by opening a stream (see the prereq for the mechanism, and backlog `feat-fret-honours-the-network-membership-predicate` for the FRET-side fix). Without this ticket a peer the predicate refuses is still a FRET ring member and still receives block contents from:

| Site | What it does with a FRET-chosen peer | Default on a live node |
| --- | --- | --- |
| `SpreadOnChurnMonitor.performSpread` | pushes every eligible tracked block to `fret.expandCohort` targets outside the FRET cohort | enabled (`spreadOnChurn.enabled ?? true`) |
| `RingShiftCoordinator.buildOwnersMap` | pushes shed blocks to FRET-cohort peers with qualifying Arachnode info (which a ring member can advertise) to confirm replication before release | wired with the rebalance reaction |
| `RestorationCoordinator.restore` | fetches block archives from FRET ring peers and saves them; archives are vetted but unverified (`BlockStorage.restoreRevision`), so this *accepts* content from them | arachnode on by default |
| `UnderReplicationDrain.pushablePeers` | a connected peer whose peerStore lists `<prefix>/block-transfer` is pushable; the owed list comes from the key network, but a named peer the predicate refuses after the entry was written is still pushed | always constructed |

`RebalanceMonitor` (its `cohortFor` uses `keyNetwork.findCluster` whenever a key network is wired, which production always does) and `BlockTransferCoordinator` (owners from `findCluster`) are covered by the prereq and need nothing.

## Change

Each of the four takes an optional `membership?: NetworkMembershipGate` dependency — the same gate instance the prereq builds in `createLibp2pNodeBase` — and drops every candidate the gate refuses before dialing:

- spread: filter `targets`;
- ring shift: add the gate to `buildOwnersMap`'s `qualifying` filter, so a refused peer neither receives a shed block nor counts toward the floor (a refused peer counting toward the floor would release a block that only an outsider holds);
- restoration: filter `getMyRingPeers` and every other FRET-derived candidate list `restore` walks;
- drain: `pushablePeers` excludes refused peers.

Absent gate → each filter is skipped, today's behaviour exactly. No new log line per refusal; spread and drain already log their candidate counts, which now reflect the filter.

## Edge cases & interactions

- **Ring shift with refused peers in the band**: the floor may become unreachable, so Phase B rolls back to the old ring (existing behaviour for an unmet floor) — the safe direction. By inspection of `RingShiftCoordinator`'s rollback path.
- **Drain entry naming a peer the predicate later refuses**: the peer is no longer pushable, so the entry stays waiting for it and the full-replication event for that block does not fire while it stays refused (the drain has no notion of a named peer leaving the cohort today either). Leave a `NOTE:` at `pushablePeers` stating this and its revisit condition (if a removed member's entries are seen never clearing, drop refused peers from the named set). Do not change the ledger here.
- **Restoration with every ring peer refused** → `restore` falls through to its existing "nothing found" path. By inspection.
- **Self**: the gate admits self; restoration already filters self separately. By inspection.
- **Gate throwing**: the gate is total by construction (prereq), so the filters need no try/catch.

## Test

One case in `test/spread-on-churn.spec.ts`: with a gate refusing one expansion target, a spread pass pushes to the other targets and never to the refused one. Spread is the path enabled by default with no other precondition, so it is the one worth pinning; the other three are one-line filters verified by inspection. Run `yarn workspace @optimystic/db-p2p test`.
