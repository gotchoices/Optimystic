# The owed-blob ledger and the durability classes

docs/blobs.md §Placement, copying and durability, "Copying" and "Durability". This is the durable record and the pure classification that the copy drain (`feat-blob-owed-copies-are-drained`, the next ticket) runs on: the owed entry per announced blob, the class-and-count rule, the `durability` field on a blob record, and the narrow door on `LocalBlobService` through which the drain changes a record. Nothing announces and nothing emits an event yet — that is all the next ticket.

Splitting it this way keeps each half to one coherent change: this one is data and a pure function, the next one is the drain and the node wiring.

## `KeyedSerialQueue`

`packages/db-p2p/src/keyed-serial-queue.ts`, extracted from `KvUnderReplicationLedger.serialized` with its semantics unchanged:

```ts
/**
 * Serializes operations by key, so each read-compare-write for one key is atomic against the others
 * for the same key (`IKVStore` has no compare-and-set). Three stores need exactly this and had three
 * copies of it: the under-replication ledger, the blob record store, and the owed-blob ledger.
 */
export class KeyedSerialQueue {
	/** Run `operation` after every earlier operation for `key`, whatever their outcome. The queue
	 *  entry is dropped once nothing waits behind it, so the map holds only keys with work in flight. */
	run<T>(key: string, operation: () => Promise<T>): Promise<T>;
	/** Observability: keys with work in flight. */
	get pending(): number;
}
```

Three call sites move onto it in this ticket:

- `KvUnderReplicationLedger` — delete the private `serialized` and the `queues` map; every `this.serialized(blockId, …)` becomes `this.queue.run(blockId, …)`.
- `BlobRecordStore.update` — delete the `chains` map and the `noop` helper; the body becomes `return this.queue.run(ref, () => this.apply(ref, keyOf(ref), change))`. The two implementations are already identical (chain on the previous settle, drop the key when nothing waits), so this is a substitution, not a behaviour change. Keep the comment that explains why this is a per-instance chain rather than db-core's `Latches`, moved to the field.
- `OwedBlobLedger` below.

No new test: both existing call sites are covered by their own suites (`packages/db-p2p/test/kv-under-replication-ledger.spec.ts` and `packages/db-p2p/test/local-blob-service.spec.ts` exercise the serialization through the public calls), and the queue has no behaviour of its own beyond what they pin.

## `OwedBlobLedger`

`packages/db-p2p/src/blob/owed-blob-ledger.ts`, over the node's `IKVStore`:

```ts
/** Key namespace: `owed-blobs/<ref>` → JSON(OwedBlobEntry). A fixed literal first segment, as `UNDER_REPLICATED_KEY_PREFIX` is and for the same reason. */
export const OWED_BLOB_KEY_PREFIX = 'owed-blobs/';

export type OwedBlobEntry = {
	readonly ref: BlobRef;
	/** The reference tree the receivers verify against. The latest `announce` replaces it; any listing scope authorizes. */
	readonly scope: BlobScope;
	/** Peers confirmed to hold the whole blob — answered `whole`, or sent `held` — by peer-id string, never this node. */
	readonly holders: readonly string[];
	/** Milliseconds since the epoch; `list` orders oldest first. */
	readonly recordedAt: number;
};

export class OwedBlobLedger {
	constructor(kv: IKVStore, options?: { now?: () => number });
	/** Create the entry, or replace an existing entry's scope keeping its holders and recordedAt. */
	record(ref: BlobRef, scope: BlobScope): Promise<OwedBlobEntry>;
	/** Add confirmed holders, each once; never creates an entry (an entry deleted meanwhile stays deleted). */
	addHolders(ref: BlobRef, peerIds: readonly string[]): Promise<OwedBlobEntry | undefined>;
	get(ref: BlobRef): Promise<OwedBlobEntry | undefined>;
	/** Oldest `recordedAt` first. */
	list(): Promise<OwedBlobEntry[]>;
	/** Answered from the in-memory index after the first load. */
	size(): Promise<number>;
	delete(ref: BlobRef): Promise<void>;
}
```

**The entry stores the holders, not the missing members.** The owed members are derived afresh from the cohort on every pass (`owed = accepting cohort members − holders − this node`), which is how an entry "follows the cohort" as docs/blobs.md requires. docs/blobs.md describes the entry as holding "the members known to hold the blob"; a holder that leaves the cohort stays listed (a copy is a copy) and simply stops counting, since durability is counted over current members.

Shape, following `KvUnderReplicationLedger` so the two read alike:

- Each public call runs under `KeyedSerialQueue.run(ref, …)` and flushes (`IKVStore.flush?.()`) once after the key is released, before it returns. The ledger exists so an owed copy outlives a restart, so no call may report what a restart would forget.
- Stored entries are parsed and checked rather than cast, exactly as `parseEntry` does: a malformed entry is logged (`read:malformed`) and read as **absent**, never deleted by a read, and the next `record` for the ref overwrites it. `ref` must equal the ref its key names; `scope` a non-empty string; `holders` an array of strings; `recordedAt` a finite number.
- `list()` is a full scan, sequential (one `IKVStore.get` per key, not all at once — a file-backed store would exhaust file descriptors), sorted by `recordedAt`. The **first** scan after start also becomes the index's load, so the drain's start pass warms it for free.
- `size()` reads an in-memory `Set<BlobRef>` loaded lazily on the first `list`, `size` or mutation; a failed load is not cached, so the next call retries rather than the ledger failing for the life of the process. It exists only so the scheduler's re-check decision costs no scan.
- **No size cap**, and so no eviction index ordering: entries are bounded by the blobs this node announced, and `feat-unreferenced-blobs-are-reclaimed` drops entries whose scope stopped listing the blob. Leave a `NOTE:` saying so at the class, naming the reclaim ticket, so the missing cap reads as a decision.
- A `ref` that is not a canonical reference throws (`parseBlobRef`) before anything is written, as `BlobRecordStore.keyToPath`'s rule does, so no key is written that `list` would then skip.

Add `OWED_BLOB_KEY_PREFIX` to `NODE_KV_NAMESPACES`, to the namespace list in `packages/db-p2p-storage-fs/README.md`, and to the parenthesised list in the `FileKVStore.keyToPath` comment.

## `BlobRecord.durability`

`packages/db-p2p/src/blob/blob-record.ts`:

```ts
export interface BlobRecord {
	// … existing fields …
	/** How widely the blob is held, as last computed (docs/blobs.md §Placement, copying and durability).
	 *  Stored so `stat` answers it and a restart does not re-emit an unchanged class. */
	readonly durability?: BlobDurability;
}
```

`BlobDurability` is the db-core type (`packages/db-core/src/blob/service.ts`) and is already what `BlobStat.durability` carries; nothing in db-core changes.

Give it a decoder rule beside the others in `recordProblem`, with a local `DURABILITY_QUORUMS` list next to `HOLD_KINDS` (db-core has no runtime list of `DurabilityQuorum`, and one local list in the one module that needs it beats a new cross-package export): absent, or an object whose `quorum` is one of `full`, `majority`, `local`, `unrouted`, whose `confirmed` and `accepting` are non-negative safe integers, and whose `unconfirmed` is absent or an array of strings. Without a rule a malformed value would be handed to a `stat` caller typed as a `BlobDurability`, since the decoder deliberately keeps every unchecked property as it found it.

## The record door on `LocalBlobService`

The drain must not hold a second `BlobRecordStore` over the same `IKVStore`: two instances keep **separate** per-ref queues, so the drain's durability write and the service's hold write could lose one another, and the drain's writes would also bypass the sweep gate that `changeRecord` takes. So the drain changes records through a narrow door on the one service that owns them, as `fetchStore()` and `holdResponsible` already are:

```ts
/** What the blob copy drain needs of this node's blob records; `LocalBlobService` is it. */
export interface BlobOwedRecords {
	/** Add the `owed` hold, creating the record (`whole: false`) when there is none. Every other hold is kept. Flushed: a lost hold would let a restart sweep a blob this node is announcing. */
	holdOwed(ref: BlobRef): Promise<void>;
	/** Remove the `owed` hold; a record left with no hold is deleted and the blob swept. No record, or no such hold, is a no-op. Flushed. */
	releaseOwed(ref: BlobRef): Promise<void>;
	/** Write the record's `durability`, flushed. Never creates a record: a record deleted meanwhile stays deleted. */
	setDurability(ref: BlobRef, durability: BlobDurability): Promise<void>;
	/** The record's stored `durability`, or undefined. */
	durabilityOf(ref: BlobRef): Promise<BlobDurability | undefined>;
	/** Whether this node's record says every piece is here. */
	holdsWhole(ref: BlobRef): Promise<boolean>;
	/** Tell this service's `onDurability` listeners. Each listener is called in a `try`; a throw is logged (`durability:listener-threw`) and does not stop the others, as `emitProgress` does. */
	emitDurability(event: BlobDurabilityEvent): void;
}
```

`LocalBlobService implements BlobOwedRecords` (declare it, so a drift between the door and the service is a compile error). Each of the three writers goes through the existing `changeRecord`, with a `recordAfterOwedHold` / `recordAfterOwedRelease` / `recordWithDurability` helper beside the ones already at the bottom of the file; `recordAfterOwedRelease` and `recordWithDurability` return the current record unchanged when there is nothing to change, so `BlobRecordStore.apply` writes nothing.

`holdsWhole` reads the record's `whole` hint rather than taking a census, so a pass over many entries costs one `get` each. The hint is corrected by every read and `stat` (`correctRecord`). A stale `false` only under-counts this node, which keeps the blob — the safe direction; a stale `true` is corrected by the next read. Say that in the doc comment.

`LocalBlobService.stat` carries the record's `durability` on every answer it builds (all three return sites, including the one for a blob whose root piece is absent), and its doc comment loses "left absent until …". `onDurability`'s "Nothing reports durability until …" comment goes too, replaced by one saying the copy drain emits through `emitDurability`. `announce` keeps throwing: this service has no cohort, and `NodeBlobService` is what announces.

## `classifyBlobDurability`

`packages/db-p2p/src/blob/blob-durability.ts` — pure, no imports but types and the db-core `BlobDurability`:

```ts
export interface BlobCohortView {
	/** False when `findCluster` threw or named nobody. */
	readonly resolved: boolean;
	/** The cohort members that accept blobs, this node included when it is one and takes blobs. */
	readonly accepting: readonly string[];
}

/** docs/blobs.md §Placement, copying and durability, "Durability", exactly. */
export function classifyBlobDurability(view: BlobCohortView, holders: ReadonlySet<string>, selfId: string): BlobDurability;
```

With `n = |accepting ∩ holders|` and `k = |accepting|`, checked **in this order**:

1. `unrouted` — `!view.resolved`. `confirmed` is the size of `accepting ∩ holders` (zero, since `accepting` is empty), `accepting` 0, `unconfirmed` absent: the cohort could not be named, so there is nobody to name.
2. `local` — no accepting member other than this node, whatever `n`. A group where nobody else accepts blobs stays `local` and the writer keeps the blob.
3. `local` — `2n <= k`: this node alone, or fewer than a strict majority.
4. `full` — `n === k`.
5. `majority` — otherwise (`2n > k` and `n < k`).

The order matters: rule 2 is what keeps a one-member cohort out of `full`, which docs/blobs.md requires ("every accepting member holds it, **and at least one of them is not this node**"), and it is reached before the arithmetic so a cohort of just this node never reads as a strict majority of itself.

`unconfirmed` is `accepting − holders`, in `accepting` order, on every class but `unrouted`; it is empty at `full`. `accepting` counts `view.accepting.length`. `confirmed` counts `n`, which includes this node when the caller put it in `holders`.

A member whose acceptance is `unknown` (not yet identified) is the **caller's** decision to include; the next ticket's view builder includes it, because an unidentified member is owed until it is known not to take blobs, which errs toward keeping the writer's copy. Say so at `BlobCohortView.accepting` so the rule is visible from both sides.

## Edge cases & interactions

- **Two of five accepting members hold it** → `local` with `confirmed: 2`, not `majority`. Covered by the classification table test.
- **This node is the only accepting member**, holding it → `local`, not `full`. Table test.
- **This node is outside the cohort** (a client writer): `accepting` is the cohort's accepting members with self absent, so `n = 0` gives `local`/0 and `n = k` gives `full`. Table test.
- **An empty `accepting` with `resolved: true`** — the next ticket's builder cannot produce it (an empty cohort reads as unresolved), but the function must not divide by `k` or read `accepting[0]`; rule 2 catches it as `local`. Inspection, plus one table row.
- **A malformed stored `durability`** reads the whole record as malformed, which `LocalBlobService.readableRecord` logs and treats as absent — the existing path for a malformed record, unchanged. Inspection.
- **`releaseOwed` on a record whose `owed` was its last hold** deletes the record, taking the stored `durability` with it. That is the intended end state once the cohort holds the blob (the writer stops holding it on the others' behalf) and is why the next ticket writes the `full` durability *before* it releases the hold. Inspection; the next ticket's drain spec asserts the record is gone.
- **A ref that is not a canonical reference**, handed to any ledger or door call, throws before anything is written. Inspection (`parseBlobRef`, as `BlobRecordStore` already does).
- **Concurrent `record` and `addHolders` for one ref**: serialized by the ledger's queue; `addHolders` re-reads inside the queue and returns what it wrote, so a caller never acts on a stale holder set. Covered by the ledger spec.
- **A restart with a persistent key-value store** finds the entries and the holders as written; the index loads from the first `list`. Covered by the ledger spec (a second ledger over the same `MemoryKVStore`).
- **The under-replication ledger and the blob record store are unchanged in behaviour.** Their suites pass with no test edited — the one check that the `KeyedSerialQueue` substitution is a substitution.
