# One commit round for the log tail and the rest of the blocks, when one coordinator covers them all

## Why

`NetworkTransactor.commit` runs two consensus operations for every write: `commitBlock` for the collection's log tail, then, only if that succeeded, `commitBlocks` for every other block the action touched (the "sweep"). Each operation is a full cluster transaction (see `cluster-commit-round-carries-the-coordinators-commit-vote`: 2 calls to each remote after that ticket, 3 before). Together with the pend, a single-collection write is three consensus operations. Removing the separate sweep makes it two: for a two-member group after the prereq ticket, 4 `/cluster` streams per write instead of 6 (9 before either ticket). Each staged collection or index tree in one transaction saves the same amount.

## Design

**When the combined round applies.** Build the commit batches for *all* the action's block ids, reusing the pend's coordinator resolution as `commitBlocks` does today (`batchesForPayload`, with the action id). If that yields exactly one batch, so that one coordinator covers the tail and every other block, send one commit to that coordinator with `blockIds` ordered **tail first**, followed by the rest in their existing order, and `blockDigests` narrowed to those ids as today. In every in-process mesh and every two-machine deployment, one coordinator covers everything (`consolidateCoordinators` collapses to one peer whenever one covers all blocks), so the combined round is the normal case. With two or more batches, keep today's tail-then-sweep path unchanged.

**Why tail-first on the wire.** `CoordinatorRepo.commit` runs consensus on `blockIds[0]`'s cohort. With the tail first, the combined record runs on the tail's cohort, the same cohort today's tail round uses. The non-tail blocks then commit on the tail's cohort rather than on the first non-tail block's cohort, as today's sweep does. That is the same class of approximation the sweep already makes for multi-block batches (the NOTE in `CoordinatorRepo.commit`, backlog `debt-sender-side-coordinating-block-binding-is-unchecked`), and it is identical whenever cohorts coincide, as they always do in small groups.

**Storage applies the tail first, whatever order the request lists.** `StorageRepo.commit` applies blocks in request order and stops at the first failure (`break` in the `toCommit` loop). Every whole-batch refusal happens before any block is applied: the stale partition (`missedCommits`) and the missing-pend throw both return before `internalCommit` runs. So if the tail is the first block applied, a member can never hold a committed non-tail block of this action without also holding the tail. Do not rely on the caller for this. Order the deduplicated `blockIds` with `request.tailId` first (when present) inside `StorageRepo.commit`. The request already carries `tailId`, so no wire change is needed. This change is harmless for today's single-block tail commit and for the sweep, which has no tail.

**A failed combined round.**

- *Returned `success:false`* (a confirmed conflict, or `commit-not-durable`): return it, exactly as a refused tail is returned today (`commitBlock`'s stale path). The caller cancels and the writer's retry machinery takes over (`Collection.completeOwnEntry` re-sends the retained attempt at the same action and revision, and the own-revision carve-outs turn that into "land what is missing"). A combined record refused as not durable may have landed the tail *and* the blocks on a minority of the cohort. Today the minority can hold only the tail. That minority state is strictly more complete than today's, and the completion machinery already handles "entry found, blocks missing" as well as "entry found, everything present".
- *Thrown* (transport-shaped, no answer): **do not** let `processBatches` retry it. Its retry re-batches the failed block ids through `createBatchesForPayload` onto possibly different coordinators, sent in parallel, which could commit a non-tail block on one cohort before the tail lands on another. Instead, fall back to today's two-step path for the same request: `commitBlock` for the tail (with its normal retries), then the sweep. Everything the thrown round managed to land is this action's own revision, so the fallback's commits for those blocks are idempotent no-ops (`isOwnRevision` in `StorageRepo.commit`'s `alreadyDone` partition). Send the combined round with retries disabled: either a direct `getRepo(peer).commit(...)` inside the same timeout/expiration handling, or a `commitBlocks` variant with no re-batching. Keep one code path for building a commit batch's request (digest narrowing, `tailId`, `expiration`, `dialTimeoutMs`).
- *Success*: return `{ success: true, durability }` from the single batch's report. `torn` is empty. A combined round that succeeded landed every block on a majority, per the coordinator's durability gate, which checks every block through `durableCommitVerdict`.

## The Risk bullet from the plan ticket, settled

*"The tail is committed before any other block" is what lets `bootstrapContext` trust the tail and what torn-write handling assumes. With a single round, a partial apply on one member must never expose a non-tail block without its tail.*

- **On one member** the guarantee holds by the storage ordering above, which is the invariant that matters. `bootstrapContext` reads the tail without a revision context and relies on "a committed tail exists wherever committed data of that action does", so pending non-tail blocks become visible through the context the tail provides. Tail-first application inside one latched critical section gives exactly that: a reader on that member can see the tail committed with the other blocks still pending (the direction the guarantee allows), never the reverse. The header, a non-tail block, likewise never commits on a member before the tail it points to, which rules out the "dangling pointer" the NOTE in `NetworkTransactor.commit` warns about.
- **Across members** the combined record is one consensus decision. A member either applies it (tail first) or does not. The difference from today is that today the sweep starts only after the tail round has been acknowledged (majority durable), whereas now a member can hold tail and blocks while the tail is not yet on a majority. That is not a new exposure: the non-tail blocks sit only on members that also hold the tail, and a reader can reach them only through a context adopted from a tail it read.
- **Torn-write handling** (`cancelAbandonedSweepBlocks`, `completeOwnEntry`): the tail's fate is no longer known separately from the sweep's on the combined path, so the "tail durable, sweep thrown → acknowledge with `torn`" arm cannot arise there. A thrown combined round falls back to the two-step path, where that arm stays reachable and unchanged. `completeOwnEntry` needs no change: it already treats "found own entry" as proving only that the tail landed, and re-sends everything.

## Edge cases & interactions

- **The action touches only the tail** (a single-block action, where `blockIds` is `[tailId]`): the combined round *is* the tail round. Nothing changes. Verify by inspection.
- **Duplicate ids or a tail absent from `blockIds`**: today's code filters `remainingBlocks` by `tailId` and `StorageRepo.commit` deduplicates. The tail-first ordering must be a stable reorder of the deduplicated list, and must be a no-op when `tailId` is not in the list. Verify with the storage-order test below.
- **A multi-batch plan**: unchanged two-step path. `cancelAbandonedSweepBlocks`' "only reachable with more than one batch" NOTE stays true. Verify by inspection.
- **One member's apply fails part-way** (genuine fault on block N after the tail landed): that member keeps its remaining pendings for a retry (the genuine-fault arm), and its durable verdict reports not-durable because not every block is held. The coordinator's gate then counts it as not holding. If that leaves no majority, the writer gets `commit-not-durable` and completes through `completeOwnEntry`. Verify by inspection. The storage-order test below covers the tail half.
- **A behind member** (missed the pend, or no base): the whole combined record is refused on it and reconciled, just as a behind tail is today. `dropUnpromotablePendings` drops the batch's pendings, which now include the non-tail blocks. That is correct, because reconcile advances every block in the batch. Verify with the existing reconcile specs, which must stay green.
- **Reactivity** (`CollectionChangeEvent`): today the tail commit and the sweep each emit an event for the collection. The combined apply emits once per collection with every block. Watchers invalidate coarsely, so fewer events are harmless. Verify by inspection.
- **Commit proof and digests**: one record now declares digests for every block, and `buildBlockCommitProof` covers all of them. `persistProofIfContentMatches` runs per block as before. Verify by inspection.
- **Commit-cert capture and the durability ledger** (`IUnderReplicationLedger`): per-commit, per-block. One record instead of two changes nothing structural. Verify by inspection.
- **Session-mode multi-collection commits** (`TransactionCoordinator`): each participant calls `NetworkTransactor.commit` once. Each gets the saving, with no coordinator change. The coordinator's `CoordinatorPartialCommitError` logic keys on per-collection results, which keep the same shapes.
- **Specs that select "the tail commit" or "the sweep" by shape** (`member-leaves-and-returns.spec.ts` triggers on `!commit.blockIds.includes(commit.tailId)`, which never occurs on the combined path; `member-missed-commit-heals-at-commit.spec.ts` triggers on the tail step): re-derive each spec's scenario for the combined round and keep what each title claims. If a scenario is specifically about the two-step path (a torn sweep after a durable tail), it needs a fixture that forces two batches. That fixture does not exist yet (backlog `debt-no-mesh-fixture-forces-two-coordinator-batches`), so drive such a scenario through the thrown-combined-round fallback, or record it as dropped coverage in the handoff. Never skip or disable a test.
- **`network-transactor.spec.ts` "commit non-tail conflict surfacing"**: these tests set up a tail and a non-tail block. If their mocks resolve one coordinator, they now exercise the combined path. Each must still pin its behaviour: a returned conflict on the combined round is surfaced; a thrown non-tail failure after a durable tail is tolerated with `torn`, which is now reachable only through the fallback path or a two-batch mock. Adjust the mocks so each test still exercises the branch its title names.

## Tests

- **Storage ordering contract** (one test, in the `StorageRepo` commit spec): a commit request listing a non-tail block *before* the tail, where the tail's commit fails in `internalCommit` (e.g. a missing base for the tail only), leaves the non-tail block uncommitted (its `latest` unchanged). A second assertion in the same test: with both committable, the tail is applied first. Observe this through the change-event order or an instrumented storage, whichever is cheaper.
- **Combined round** (one test, `network-transactor.spec.ts`): a two-block action whose blocks resolve to one coordinator issues exactly one repo `commit` call, with `blockIds[0] === tailId`. A thrown first attempt falls back to a tail commit followed by a sweep commit.
- If the prereq's two-node delivery-count test commits through `NetworkTransactor`, extend its expectation for a two-block write. Otherwise add nothing further.
