## The decided policy (maintainer, 2026-10-15)

- The window `w` comes from theory, per write, from the cohort the write's consensus ran on. The defaults are `p` = one power cut or OS crash per machine per month, `ε` = 10^-9, and a 5 s cap.
- Independence is assumed by default. `storageDurability.independentFailures: false` makes every write strict.
- Two-member cohorts and phones relax by the formula like any other.
- `w = 0` wherever only one machine would hold the write (solo pend and commit, and the shortfall entry). This follows from the formula's `m = 1`.
- `WriteDurability` is unchanged. Each holder's copy reaches stable storage within the window its cohort allows.
- No rule refuses a relaxed node's solo write. The fork case stays documented, owned by backlog `6.5-partition-healing`.

## `docs/correctness.md`

**§1.2 Nodes:** add a paragraph after *Crash-recovery*. Proposed text, to edit against the code:

> **Storage durability.** A node reports holding a write (accepts a pend, holds a committed revision) once that write would survive a crash of its own process. It survives a power cut or operating-system crash of that machine once a window `w` has passed. `w` is computed per write from the size `n` of the cohort the write's consensus ran on: a write is lost only if every holder a rival write would need to out-vote loses it within `w`, and under the deployment's declared assumption that its machines fail independently, `w` is the largest window keeping that chance below a loss target (`durabilityWindowMs` in `packages/db-p2p/src/storage/durability-window.ts`; the formula and its table are in [packages/db-p2p/docs/storage.md](../packages/db-p2p/docs/storage.md#…)). A write only this machine holds has `w = 0`: it is synced before it is reported. A deployment whose machines share a failure (two machines on one circuit) declares `storageDurability.independentFailures: false`, which makes every write strict. What survives any crash is a prefix of the writes in the order they completed. The React Native, browser and NativeScript backends cannot yet sync at all; a power cut there may lose any write the operating system has not written out (implement tickets `nativescript-storage-syncs-by-the-window`, `browser-storage-syncs-by-the-window` and `react-native-storage-commits-groups-through-the-journal`, and the blocked `react-native-storage-syncs-once-rn-leveldb-can`, each update this sentence and the table below as they land).

**Theorem 6:** restate it, for example:

> **Statement.** A write acknowledged at `full` or `majority` survives any crash of its holders' processes, and is lost to power cuts or operating-system crashes only if every holder a rival would need to out-vote loses power within the window `w` its cohort allows (§1.2): under declared independent failures, with probability below the loss target per write. A write acknowledged at `local` or `unrouted` was synced before it was acknowledged (`w = 0`), so it survives any crash of its one machine that leaves that machine's storage.
