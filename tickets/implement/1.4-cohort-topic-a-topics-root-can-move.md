# Cohort-topic: a root-placed topic's root can move

First of three tickets that deliver the third paragraph of the maintainer's decision of 2026-10-02 (`docs/reactivity.md` § Anchor will carry it once `reactivity-topic-is-the-collection-anchor` lands):

> **Tiers below the root do not rotate.** Tiers `d ≥ 1` are addressed by a stable collection anchor, `collectionTopicId = H(collectionId ‖ "reactivity")`. Only the root moves when the tail rotates.

## Why the substrate has to change

The cohort-topic layer addresses tiers `d ≥ 1` by `coord_d(P, topicId)` and a root-placed topic's root by `H(rootKey)` (`docs/cohort-topic.md` § Root placement at a routing key). So "tiers below the root are stable, the root moves" means: **one topic id for the collection's whole life, and a root key that changes** (the tail block's routing key). This reading was checked against the accepted text: its formula feeds `collectionTopicId` into `coord_d` exactly where the substrate feeds `topicId`, and any other reading would need `coord_d` to take an input other than the topic id. No wire field changes.

Until now every root-placed topic had one root key for its life, and three places assume it:

1. **A tier-`d ≥ 1` engine refuses a different root key.** `reconcilePlacement` in `packages/db-p2p/src/cohort-topic/host.ts` throws `CoordPlacementMismatchError` when a frame names a root key other than the one the engine adopted first. Once the root moves, every registration at a tier-1 cohort after the first move names the new key and would be refused.
2. **A node can hold two records for one participant under one topic.** Records live per coordinate engine. When a participant registered at the old root re-registers at the new root, a machine in both roots' storage groups holds both records, and `findHolder` (same file) returns whichever engine it iterates first. A renewal (and a withdraw tombstone, and a backup re-attach, all resolved by `resolveRenew`) can then touch the displaced record while the live one expires.
3. **The participant cannot tell where its registration landed, or point a later re-walk at the new root.** `RegistrationHandle` (`packages/db-core/src/cohort-topic/service.ts`) carries the `Tier` class but not the tree tier the walk was accepted at, and the renewal's re-walk (`renewalTransport`'s `relookup`) closes over the original request's `rootKey`.

## What to build

**Walk outcome and handle carry the tree tier.** `AcceptedWalkOutcome` in `packages/db-core/src/cohort-topic/walk.ts` gains `treeTier: number` — the `d` of the register frame the cohort accepted (`reg.treeTier`). `CohortHint` (and so `RegistrationHandle` and `lookup`'s result) gains `treeTier`. Additive; matchmaking ignores it.

**The participant can move a registration's root without sending anything.** Add to `CohortTopicService`:

```ts
/**
 * The topic's root moved to `rootKey` (a root-placed topic only). Nothing is sent: a registration at a
 * tier below the root stays where it is. A later re-walk of this registration (renewal failover) names
 * the new key, so it lands at the new root rather than the old one. A registration AT the root must be
 * re-registered instead — `register` with the new key replaces it (see the NOTE at `startRenewal`).
 */
moveRoot(handle: RegistrationHandle, rootKey: Uint8Array): void;
```

Implementation: the renewal transport reads the root key from a per-renewal mutable slot instead of the closed-over request, and `moveRoot` updates that slot and `handle.rootKey`. A stale handle (not the live renewal for its `(topicId, participant)`, same identity guard `renew`/`withdraw` use) is a no-op. `assertRootKey` applies.

Replace the `NOTE:` at `startRenewal` (currently "a second register() for the same (topicId, participantId) overwrites the map entry … send a withdraw for the displaced renewal") with the decided behavior: a second `register` for one `(topicId, participant)` displaces the first, and **no tombstone is sent for the displaced record, by design** — on a machine holding both records a tombstone resolves through `findHolder`, which (below) picks the newer record, so it would evict the live registration. The displaced record expires by TTL at its cohort.

**A tier-`d ≥ 1` engine follows the topic's root.** In `reconcilePlacement`: a frame claiming the other *rule* (`rootPlaced` mismatch) is still refused. A frame naming a different root key at a **non-root-placed** engine replaces the engine's key (newest frame wins) instead of throwing; log the change at the `cohort-topic` namespace with the served coord. At a root-placed engine the key is the coordinate's own preimage, so a different key there is still a mismatch and still refused. Rewrite the `EnginePlacement` doc comment ("rootKey is the key the creating frame named") accordingly, and add a `NOTE:` at the adoption: "accepted — a tier-`d ≥ 1` engine adopts the root key of the newest frame that names one, so a participant naming a wrong key re-addresses this cohort's parent (cold-start parent registration, demotion fan-out, child link) until the next honest frame; nothing ties a root key to its topic (see the NOTE in `dispatchRegister`). The authenticated re-link of a child cohort to a moved root is backlog `feat-reactivity-notifications-reach-child-cohorts`; revisit this when it lands."

The parent-addressing reads (`parentCoord`, `parentRootPlaced`, the cold-start `registerWithParent` input) already read `rootKey` at use, so they follow automatically; check that none captured it at creation.

**`findHolder` returns the newer registration.** Among engines holding `(topicId, participantId)`, return the one whose record has the greatest `attachedAt`, ties broken by greatest `lastPing`. Rationale for the doc comment: a participant holds one registration per topic (the service keys renewals by `(topicId, participant)`), so of two records for one participant the one registered later is the live one; `attachedAt` is stamped by the accepting member at admission and gossiped unchanged (`toGossipRecord` in `packages/db-core/src/cohort-topic/gossip/records.ts`), and a renewal touch preserves it. The engine will need to expose the record (or its `attachedAt`/`lastPing`), not only `holds`.

## Tests

- `findHolder` choosing between two engines on one host that both hold a record for the same `(topic, participant)`: the renew resolves to the record with the later `attachedAt`, whichever engine was created first. One case at the host-registry level (`packages/db-p2p/test/cohort-topic/service.spec.ts` already drives `resolveRenew`), plus the tie on `attachedAt` broken by `lastPing`.
- `reconcilePlacement`: a second register at a tier-1 coordinate naming a different root key is accepted and the engine's `rootKey` is the new one; a register at a root-placed coordinate whose key differs is still refused. Branching logic with a security edge; one case each.
- Walk: the accepted outcome's `treeTier` equals the tier the walk landed at, for a walk that steps inward and one that follows a `Promoted` redirect outward (`packages/db-core/test/cohort-topic/walk.spec.ts`). Assert on existing walk cases rather than adding a new scenario where one already lands at each.
- `moveRoot`: after `moveRoot`, a forced relookup (three failed pings, all backups failed) walks with the new root key. One case.

No test for the handle field plumbing or the `NOTE:` text.

## Edge cases & interactions

- **Matchmaking** registers without a root key: `placementOf` returns the default placement, so the adoption branch never runs and `findHolder` sees one record per participant. Verify by inspection; the matchmaking suites must stay green.
- **A gossip-instantiated cold sibling** has no root key and adopts the first one it sees (unchanged); it then follows newer frames like any tier-`d ≥ 1` engine.
- **Interleaved old and new keys** at one tier-1 engine during a move (a participant whose re-walk still names the old root) flip the engine's key back and forth. Harmless until child cohorts are linked to the root; recorded in the NOTE above.
- **Clock skew in `findHolder`.** The two records were stamped by different members' clocks. Misordering needs skew larger than the time between the two registrations. A `NOTE:` at `findHolder` stating this residual and its effect (the live record expires one TTL after the move; the participant's next re-registration fixes it).
- **A withdraw tombstone after a move** resolves to the newer record, which is the live one: correct for a participant closing its registration.
- **`moveRoot` on a handle whose registration is at the root** is legal but leaves the registration at the old root; the caller must re-register. Say so in the doc comment; reactivity's follow logic (`reactivity-topic-is-the-collection-anchor`) relies on `treeTier` to choose.
- **A relookup's landing is not tracked**: the renewal discards its walk outcome, so `treeTier` (and primary) on the handle can go stale after a failover re-walk. Pre-existing; appended as an arm to backlog `bug-a-participant-told-its-registration-is-unknown-never-registers-again`. Do not fix here.
