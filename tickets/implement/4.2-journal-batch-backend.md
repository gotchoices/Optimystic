# Journal batch backend

Third of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37).

## Why a journal

The maintainer's decision (2026-10-15) asks the browser and React Native backends to commit each write group atomically, keep write order across a power cut (what survives is a prefix of the groups, in order), sync by each group's window deadline, and sync at once when the window is 0. Neither engine can do the last three by committing groups directly:

- **IndexedDB** can make one transaction durable (`durability: 'strict'`), but cannot sync earlier relaxed transactions later. A strict transaction after relaxed ones would need the browser to persist transactions in order, which the IndexedDB specification does not promise.
- **LevelDB** (behind React Native, and behind IndexedDB in some browsers) syncs only its current log file on a synced write. When it switches to a new log file it closes the old one without syncing it (`DBImpl::MakeRoomForWrite`), so a later synced write does not cover unsynced writes left in the old file. Its recovery under default options also skips a damaged log record and keeps the records after it (`DBImpl::RecoverLogFile`). Either way a power cut can keep a later write and lose an earlier one.

A journal removes the dependence on the engine's ordering:

- A **relaxed** group (window greater than 0) is written as **one journal record**, numbered by a sequence, in one atomic unsynced write. It is not applied to the stores reads come from. It survives a crash of the process, so a restart can replay it. The `WriteGroup` overlay above keeps serving its writes until the group is durable.
- An **apply** is one atomic **synced** write that applies, in order, every journal record not yet applied (plus, for a strict group, the group itself), records the sequence it applied through, and deletes those records. The apply carries all the data it applies, so its durability depends on nothing written before it.
- **Recovery** at open reads the journal, drops records at or below the applied-through mark, applies the run of consecutive records after it, and discards everything after the first missing number. A lost record (a damaged LevelDB log record, an IndexedDB transaction the browser did not keep, an unsynced old log file) is a missing number, and nothing after it is applied. What survives is a prefix.

Every apply is synced before the next one starts, so a later apply can never survive without an earlier one.

## The port

`packages/db-p2p/src/storage/journal-batch-backend.ts`:

```ts
/** One write group recorded ahead of being applied. `seq` counts up from 1 with no gaps. */
export interface JournalRecord {
	readonly seq: number;
	readonly entries: readonly BatchEntry[];
}

/**
 * The engine under a {@link JournalBatchBackend}: the applied stores' reads (as `BatchBackend`'s),
 * plus three journal writes. Reads never reflect a record until an apply has applied it.
 */
export interface JournalStore extends Omit<BatchBackend, 'commit' | 'sync'> {
	/** One atomic write that survives a crash of this process: store `record` in the journal. Not applied. */
	appendJournal(record: JournalRecord): Promise<void>;
	/**
	 * One atomic write that, before it resolves, survives every crash `durability` names: apply each
	 * record's entries in the order given, set the applied-through mark to `appliedThrough`, and delete
	 * the journal records numbered in `apply` and in `discard`.
	 */
	applyJournal(apply: readonly JournalRecord[], appliedThrough: number, discard: readonly number[]): Promise<void>;
	/** The applied-through mark (0 when none) and every journal record present, ascending by `seq`. */
	readJournal(): Promise<{ readonly appliedThrough: number; readonly records: readonly JournalRecord[] }>;
}
```

The journal records and the mark live in the engine's own keyspace (an IndexedDB object store, a LevelDB tag byte), defined by each store.

## `JournalBatchBackend implements BatchBackend`

Constructor `(store: JournalStore, options?: { setTimer?: SetTimer; now?: () => number })`.

- **Open (lazy, memoized, awaited by every operation):** `readJournal()`. Records with `seq <= appliedThrough` are stale (an apply deleted them in the same write that set the mark, so these exist only if a store's delete was lost; delete them). Take the run `appliedThrough + 1, + 2, …` with no gap; every record after the first gap is discarded. If anything is to be applied or discarded, one `applyJournal(run, lastOfRun ?? appliedThrough, stale + discarded)`. The next sequence is one past the last applied. Log on the new `journal` channel when records were discarded after a gap: how many, and the missing number. Add the channel to `docs/debugging.md` (the log-namespace spec checks it).
- **A serial queue** orders open, commits and sync steps. `WriteGroup` sends one commit at a time, but `sync()` and the deadline timer can arrive beside one.
- **`commit(entries, { syncWithinMs })`**, in the queue:
  - **The store's `durability` is not `'power-loss'`** (an engine that cannot sync): `applyJournal([record], seq, [])` at once and return an already-resolved `durable`. Nothing to defer, since applying already meets the store's durability, and the journal is never written. This is the path an old browser and today's React Native binding take: one atomic native write per group.
  - **`deadlines.mustSyncNow(syncWithinMs)`** (strict, or a held deadline already passed): take the cover, `applyJournal([...cover records, record], seq, [])`, settle the cover, return an already-resolved `durable`.
  - **Otherwise**: `appendJournal(record)`, then `deadlines.defer(record, syncWithinMs)`; return that `durable`.
- **`sync()` and the deadline timer**: in the queue, take the cover; empty → resolve; else `applyJournal(cover records, last seq, [])` and settle it.
- **Reads** are the store's, after open. They do not see journaled records; `BatchBackend`'s read contract asks only for batches whose `durable` has resolved, and the overlay serves the rest.
- **Failure**: any store write rejecting latches the backend (`failAll`; every later commit and sync rejects with `StoreFailedError` carrying the first cause). A failed append leaves at most a record the next open applies or discards by the same rule, which is safe because nothing reported it.
- **`close()`**: in the queue, apply whatever is held (the driver's strict flush normally leaves nothing), disarm the timer, then the store's `close` if it has one.
- **Optional members** (`storeIdentity`, `listBlockIds`, `approximateBytesUsed`) forwarded only when the store has them, never stubbed, as `WriteGroupDriver` does. `durability` is the store's.

Doc comment on the class: the prefix argument above, stated once.

## Record codec, for byte stores

`packages/db-p2p/src/storage/journal-record-codec.ts`: `encodeJournalRecord(record): Uint8Array` and `decodeJournalRecord(bytes): JournalRecord`. IndexedDB stores a record by structured clone and does not need it; LevelDB stores bytes. Format: a version byte, the `seq` (8 bytes big-endian), an entry count (4 bytes), then per entry the UTF-8 JSON of its `StoreKey` (a small object of fixed fields) length-prefixed (4 bytes), a flag byte for put or delete, and for a put the value length-prefixed (4 bytes). Decode rejects an unknown version or a length running past the end by throwing; a store treats a record it cannot decode as missing, which recovery handles as a gap.

## Edge cases & interactions

- **A strict commit with relaxed records held**: one apply carrying all of them and the new group, in order (test).
- **Recovery after a process crash** (nothing lost): every held record is applied at open (test).
- **Recovery with a gap**: the prefix before it is applied, the rest discarded, and the next sequence continues after the prefix, so a new group reuses a discarded number only after the apply that deleted it (test).
- **Stale records at or below the mark** are deleted, never re-applied (by inspection; only reachable if a store lost part of an apply, which an atomic apply cannot).
- **Memory**: a held record's entries are kept in memory beside the overlay's copy until applied; both are bounded by `WriteGroup`'s `maxUnsyncedBytes` (by inspection; note it beside the `NOTE:` above the overlay in `write-group.ts` if that note counts copies).
- **A key rewritten by a later group while an earlier group's record is held**: the apply applies records in order, so the later value wins (by inspection; the conformance suite covers overwrite).
- **The window and the deadline helper** are `SyncDeadlines`'s rules; nothing new here.

## Tests

In `packages/db-p2p/test/journal-batch-backend.spec.ts`, over `WriteGroupDriver(new JournalBatchBackend(new MemoryJournalStore()))` with an injected `setTimer`:

- **Relaxed groups are journaled, then applied together when their deadline is due.** Two relaxed flushes append two records and apply nothing; reads through the driver still serve both. Fire the timer: one apply carrying both records in order, and `whenDurable()` resolves.
- **A strict flush applies every held record and its own group in one apply.**
- **A power cut that loses a middle record keeps the groups before it and none after.** Three relaxed groups, `powerLoss({ lose: [2] })`, fresh backend: group 1's writes read back, groups 2 and 3's do not, and a new group then commits and reads back.
- **A process crash loses nothing that was flushed.** Relaxed groups, then a fresh backend over the same store with no power loss: all of them read back.
- **On a store that cannot sync, every group is applied at once and nothing is journaled.**
- **The codec round-trips a record holding a put and a delete.**
- Register the raw-storage conformance suite over the composition, persistent (reopen is a fresh driver over the same store).

## `SyncDeadlines` as it landed

`storage-sync-deadlines-are-shared` built `SyncDeadlines` (`packages/db-p2p/src/storage/sync-deadlines.ts`) from the file log's own bookkeeping, and its interface differs from the calls this ticket writes above in these ways:

- **A deadline is taken when the commit is called, not when it runs.** Call `deadlines.deadlineFor(syncWithinMs)` as `commit` is called (`undefined` means strict), and pass that deadline, not `syncWithinMs`, to `defer(item, deadline)` and `mustSyncNow(deadline)`. A commit that waited in the owner's queue past its own deadline then counts as overdue.
- **`mustSyncNow(deadline)` checks the batch's own deadline as well as the held ones**, so it can be called before `defer`. A commit that syncs at once does not have to be deferred: take the cover, sync it together with the new batch, settle the cover, and return an already-resolved `durable`.
- **The timer's sync step passes the time the timer fired.** `onDue` is `(firedAt: number) => void`; the step it enqueues calls `take(firedAt)`, so the timer's own lateness is not reported as the disk running late. Every other `take()` passes nothing.
- **`subject`** (required) is what the `window-overrun` line names as being synced, such as the database path; `log` is the owner's channel.
- **`defer` throws after `failAll`.** An owner that awaits anything between its own failure check and `defer` must check again after the last await, with no await between that check and `defer` (the file log's `commit` does, right after its append).
