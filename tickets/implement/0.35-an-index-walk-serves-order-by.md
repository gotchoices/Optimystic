GitHub #52. First of three chained tickets: this one reads in index order, `a-secondary-index-serves-range-predicates` adds ranges, and `a-long-index-walk-finishes-by-scanning-the-table` bounds what a walk costs when no `limit` stops it.

## What was established while planning

**Descending order needs no Quereus change.** Verified by probe against Quereus 4.25.0 with `getBestAccessPlan` patched: a module may answer a `desc` required ordering with `providesOrdering` desc, `orderingIndexName`, and an `indexDescriptor` carrying `reverse: true`. The engine drops the Sort (`order by T desc limit 10` plans as `LIMITOFFSET INDEXSCAN`), and `query()` receives `idxStr` `idx=MT(0);plan=0` with `filterInfo.accessPath.index.reverse === true`. `resolveIndexDescriptor` in `@quereus/quereus/src/vtab/index-descriptor.ts` uses a supplied descriptor when its `name` equals the index name, so no alias is needed. `BTree.range` already walks backwards (`KeyRange.isAscending`, covered by `packages/db-core/test/btree.property.spec.ts`). The last row of the issue's table is a memory-module limit (`indexSatisfiesOrdering` requires the request's direction to equal the index's), not an engine one.

**The motivating query.** Without the reverse walk, `order by Timestamp desc, Id desc limit 100` gains nothing from an ascending walk: the engine still reads and sorts the whole table. With it, the query reads about 100 index entries and 100 rows. `Timestamp datetime not null` and `Id text primary key` (`chat-sapp.qsql` in the sereus-chat checkout) both qualify. Three limits to tell the reporter:

- The checked-out schema declares no index on `Message`, so one must be added: `(Timestamp)` or `(Timestamp, Id)`.
- The checked-out query (`queryMessages` in `sereus-chat/apps/mobile/src/data/chat-operations.ts`) has a `left join` to `Member`. A Sort above a join never reaches the module (probe: `LIMITOFFSET SORT HASHJOIN SEQSCAN SEQSCAN`, the module asked for no ordering), so it gains nothing. Paging inside a subquery does: `select … from (select … from Message order by Timestamp desc, Id desc limit 100) P left join Member … order by P.Timestamp desc, P.Id desc` plans as `SORT HASHJOIN LIMITOFFSET INDEXSCAN SEQSCAN`, with the outer Sort over 100 rows.
- A numeric timestamp column gains nothing until `debt-optimystic-true-key-ordering`.

**The stored order and the engine's order differ on some text.** The trees compare UTF-16 code units (`compareTreeKeys` in `optimystic-adapter/collection-factory.ts`). Quereus's BINARY collation compares code points (`compareCodePoints` in `@quereus/quereus/src/util/comparison.ts`). They disagree exactly when, at the first differing position, one string has a high surrogate and the other a unit at or above U+E000: an emoji against `～`. The existing guard's premise that ascending BINARY text is what the tree delivers is therefore false for those pairs. Runtime handling is below. It needs no change to stored bytes.

**Framing preserves order within code-unit order, including prefixes.** Checked by hand against `escapePayload` in `schema/key-encoding.ts` for `'a'`, `'ab'`, `'a\x00'`, `'a\x00b'`, `'a\x01'`: each sorts as its payload does, because a present element ends in `\x00` and a continuation either differs there or carries `\xff`, above every tag. NULL's bare `\x00` tag sorts before every present value's `\x02`. A tree key is `frame(indexValues) ‖ frame(primaryKey)`, and `RowCodec.serializeKeyPart` stores text raw, so a text primary key really does order rows with equal index values.

**`physicalType` TEXT is too wide.** `timespan` is TEXT but compares by elapsed time (`hasSemanticOrdering`), so `treeDeliversOrdering`'s check already over-promises on `where a = ? order by span` over `(a, span)`. `date`, `time` and `datetime` compare by BINARY on their text and qualify. `json` is `PhysicalType.OBJECT` and is already excluded.

**The engine loses explicit NULLS placement.** On Quereus 4.25.0, `order by s nulls last` over an index plans `INDEXSCAN` and returns NULL first, on a memory table too. The request carries no placement, so a module cannot honour it. See blocked ticket `quereus-explicit-nulls-placement-is-lost-when-an-index-serves-order-by`. So this module claims an ordering over a column only when no NULL can reach that column, in either direction. Columns are NOT NULL by default in Quereus, so the usual table is unaffected.

**A user's LIMIT never reaches the module.** It sits above the Sort and `trySortAbsorbViaIndexOrdering` looks only downward (Quereus backlog `feat-sort-absorb-blind-to-limit-general`). Only `rule-minmax-index-boundary` sends `request.limit`. The module cannot price `order by T limit 10` differently from `order by T`, so it claims the walk for both. Measured in Node, `transactor='test'`, median of 7:

| rows | walk every entry and fetch its row | `select Id from M order by T` as it plans today | walk 10 entries |
|---|---|---|---|
| 2,000 | 63 ms | 13.7 ms | 0.37 ms |
| 5,000 | 188 ms | 37.7 ms | 0.38 ms |

The two walk columns are a bare loop over the trees, with no SQL layer and no refresh, while the middle column is a full SQL statement, so the ratios below are approximate and the implementer should replace them with end-to-end figures. A page is roughly 35 to 100 times faster and an unbounded `order by` roughly 5 times slower until `a-long-index-walk-finishes-by-scanning-the-table` lands. That ticket is why this one may claim unconditionally.

## Design

### Which orderings a walk delivers

New pure function in `schema/index-walk.ts`, replacing `orderingMatchesIndex` and `treeDeliversOrdering`:

```ts
/** How a walk of an index's tree delivers `required`, or undefined when it cannot. */
export function walkDelivering(
	required: readonly OrderingSpec[],
	index: { columns: readonly IndexColumnSchema[] },
	tableInfo: TableSchema,
	request: BestAccessPlanRequest,
): { reverse: boolean } | undefined;
```

- **Pinned columns:** a column with a usable `=` or single-element `in` filter that also passes `indexSeekCanBeTrusted` (equal values then have equal bytes). A pinned column is constant in the rows that survive, so it is removed from the required list and skipped in the key. Without the trust test, `where a = 'x'` over a `nocase` column interleaves `'X'` and `'x'` groups and breaks the order of the next column. Move `seekCanBeTrusted` and `indexSeekCanBeTrusted` beside this function if that reads better.
- **The key:** `index.columns`, then the primary key columns not already among them, each with its own collation. An index on `(T)` therefore delivers `order by T, Id` when `Id` is a text primary key. A key column's `desc` is ignored because neither `IndexManager.createIndexKey` nor `RowCodec` reads it, so every tree is ascending in its bytes.
- **Direction:** every remaining required column must share one direction, which sets `reverse`. Mixed directions return undefined. With nothing remaining, `reverse` is false.
- **Alignment:** remaining required columns must match the key positionally, with pinned key columns skipped.
- **Each ordered column:** `logicalType.physicalType === PhysicalType.TEXT`, `!hasSemanticOrdering(logicalType)`, and BINARY for both the table column's collation and the key column's, through `normalizeCollationName`.
- **NULLs:** `nullSafeOrderingPrefixLength(tableInfo, request, keyColumnsAsDesc, matched, pinned) === matched`, passing the key columns with `desc: true` so it judges them in both directions. That helper accepts NOT NULL, pinned, or a NULL-excluding filter (an unclaimed filter still becomes a residual).

### Choosing a plan

When `request.requiredOrdering` is non-empty, compare candidates on `cost`, plus `sortCost(rows)` for any that does not deliver the ordering, where `sortCost(rows) = rows * log2(rows) * 0.1`. That constant mirrors `SORT_COST_PER_COMPARISON` in `@quereus/quereus/src/vtab/memory/module.ts`, which does not export it. The returned `cost` stays the plan's own, without the sort term.

- The existing equality-seek candidates take `walkDelivering` instead of `orderingMatchesIndex`. A multi-seek still delivers nothing.
- New candidate, per non-partial index that `walkDelivering` accepts: `cost = seekCost + wanted`, `rows = tableRowCount`, `wanted = min(tableRowCount, limit + offset)` when `request.limit` is present and `tableRowCount` otherwise. It claims no filters and returns `providesOrdering: [...required]`, `orderingIndexName`, `indexDescriptor`, and no `indexName` or `seekColumnIndexes`, which sends it down the engine's ordering-only arm in `selectPhysicalNodeLegacy`.
- A plan that delivers an ordering always returns an `indexDescriptor`: the index's name, `role: 'secondary'`, `keyColumns` with `desc: false` (what the tree holds), `unique`, and `reverse`.
- With no required ordering, nothing changes.

An ordering candidate over an index whose `indexMaintenanceState` is `'unmaintained'` is skipped rather than chosen and refused by `assertIndexMaintained`. A scan answers such a query correctly today, so failing it would be a regression. The equality path keeps its throw.

The early return for a full primary-key point seek stays first.

### Reading

- `runQuery`: `scanIndexName` is also set for a secondary index with `plan=0` and no args, inside the existing synchronous block that builds the views, so a committed read still pins both views at one moment. Without this, `plan=0` falls through to `executeTableScan` and the promised order is silently lost.
- Direction comes from `filterInfo.accessPath`: reverse only when its `kind` is `'index'` and `index.reverse === true`. A hand-built `FilterInfo` with no access path walks forward.
- `IndexManager.walkEntriesIn(read, range)` is the one entry loop. `findEntriesIn` and `allEntriesIn` delegate to it.
- `executeIndexScan` takes what to walk as a value: a list of `KeyRange`s, which is one per sought key for an equality seek and one whole-index range for a walk. The verification, `yielded` set and probe stay as they are. On a walk, the verified row passes through `inEngineOrder` below.

### Restoring the engine's order on the affected text

`inEngineOrder` in `schema/index-walk.ts`, a generator over the walk's verified rows:

- A row is a **pivot** when none of its key columns (the same key as above) holds a string with a code unit at or above U+D800 (`/[\uD800-￿]/`). A pivot's comparison with any other row is the same in both orders, because at the first differing unit the pivot's is below U+D800.
- So everything the walk returned before a pivot stays on that side of it in the engine's order, and everything after stays after.
- Non-pivot rows are held in a run. At the next pivot or the end of the walk the run is sorted stably by the key columns with `compareSqlValues`, negated when reversed, and yielded, followed by the pivot.

Text with no such units is never buffered, so a `limit` stops the walk at the first rows. BMP scripts, CJK and Hangul included, are below U+D800. Comparing the whole key rather than the claimed columns means the runtime needs no record of what was claimed, and rows that tie on the claimed columns may legitimately come out in either order.

## Edge cases & interactions

| Case | Expected | Verified by |
|---|---|---|
| Values that are prefixes of each other, and values holding `\x00`, in both directions | same order as a memory table | test |
| Astral character against U+E000–U+FFFF in the ordered column, both directions | engine's order | test |
| Lone surrogates | total and deterministic, same as the engine, because such rows are never pivots | inspection |
| Nullable ordered column, either direction, with and without `nulls last` | not claimed; engine sorts | planner test |
| Nullable column with a NULL-excluding filter (`s is not null order by s`) | claimed, no NULL reaches the walk | planner test |
| Partial index | never a candidate; it holds only the rows its predicate admits | planner test |
| `timespan`, `nocase` on the column or on the index column, numeric, blob | not claimed | planner test |
| `order by a asc, b desc` | not claimed | planner test |
| `create index i on t (c desc)`, `order by c desc` | reverse walk, since the tree is ascending | planner test |
| `where a = ? order by t` over `(a, t)` | seek on `a`, ordering claimed; rows within the prefix ordered | test |
| `where a in (x, y) order by t` | multi-seek, no ordering; engine sorts | existing test |
| `where x = ? order by t limit 10` | residual filter above the walk (`LIMITOFFSET FILTER INDEXSCAN`); stops once ten rows pass | inspection |
| A selective seek on another index beats the walk | `sortCost` term chooses seek plus sort | planner test |
| Stale entry whose row moved | rejected by `rowImpliesEntry`; no row twice | test |
| Committed read | one pinned view pair, read through the existing arm | test with an interleaved commit |
| Rows staged in the open transaction | visible through the live tree, as for a seek | inspection |
| `select max(T)` / `min(T)` | `rule-minmax-index-boundary` sends `limit: 1`; one entry read | test |
| `min(s)` on a nullable column | not claimed; ordinary aggregate | inspection |
| `limit` abandons the scan | generator `return` runs the probe's `finally`; rows fetched bounded | test counting `Tree.get` |
| Live scan under a concurrent change | a walk that has yielded throws `Path is invalid…`, as the read rules require | inspection |
| Index the catalog lists but this table does not maintain | skipped at plan time; on a first touch the state is `'unknown'` and `resolveIndexTarget` throws its named error, and the next statement scans | inspection |

Add this tripwire at the walk: `// NOTE: a live walk that has yielded throws on a concurrent change, where the table scan it replaces resumes after its last key (executeTableScan). If ordered reads polled during an offline drain surface "Path is invalid", resume after the last entry the same way.`
