# A held blob follows its cohort

docs/blobs.md §Placement, copying and durability, "When the cohort changes": "A node's held blobs are enumerable from its records, so the cohort comparison `RebalanceMonitor` makes for blocks is made for blobs too, by giving it the routing key rule rather than a second copy of its logic."

The prereq built the decision (`BlobCohortReaction`, two arms, no wiring). This ticket runs a second `RebalanceMonitor` over the blobs this node holds for the network and acts on what the reaction returns. When it lands, every part of docs/blobs.md §Placement, copying and durability exists.

## What is tracked

The tracked set is the references whose record carries an `owed` or a `responsible` hold — the two holds that mean "kept for the network". Pins and `cached` holds are this node's own business and are not tracked: a node does not announce a blob it merely read.

**The feed.** `LocalBlobService` gains

```ts
/** Tell these listeners when a record's set of hold KINDS changed — the only thing that can change whether a reference is kept for the network. `holds` is the record's holds after the change, empty for a record that was deleted. */
onHoldsChanged(listener: (ref: BlobRef, holds: readonly BlobHold[]) => void): () => void;
```

a second listener set beside `durabilityListeners`, subscribed through the existing `subscribe` helper and emitted from `changeRecord` — the one path every record change takes — when the set of hold kinds in `result.before` differs from the set in `result.after` (a missing record counting as no holds). That test, rather than emitting on every change, keeps a `lastReadAt` touch or a `whole` correction off the feed while still firing on every hold that appears or goes; a `responsible` hold whose scope was replaced does not fire, which is right, because tracked-ness did not change. Each listener is called in a `try` and a throw is logged (`holds:listener-threw`), as `emitDurability` does.

It emits before the caller's `flush`, which is deliberate and needs no comment beyond one line: the listener only adds to or removes from an in-memory set, and the set is re-derived from the records at every start, so a hold a crash loses costs nothing.

**The restart seed.** `seedHeldBlobs` in `packages/db-p2p/src/blob/held-blob-seed.ts`, modelled on `seedOwnedBlocksFromStorage` in `packages/db-p2p/src/owned-block-seed.ts` and, like it, internal to the factory rather than exported from either entry:

```ts
export async function seedHeldBlobs(deps: {
	records: Pick<BlobResponsibleRecords, 'responsibleRefs'>;
	owed: Pick<OwedBlobLedger, 'list'>;
	monitor: Pick<RebalanceMonitor, 'trackBlock' | 'recordBlockHolders'>;
	isStopping: () => boolean;
}, yieldEvery?: number): Promise<void>
```

Every `responsibleRefs()` reference is tracked, and every `owed.list()` entry is tracked **and then** reported through `monitor.recordBlockHolders({ blockIds: [entry.ref], holders: entry.holders })`, so the first check after a restart does not re-announce to members the writer already knows hold the blob. Track before reporting: evidence for an untracked id is dropped at the next check. `isStopping()` is checked each iteration and a cooperative yield every `yieldEvery` (default 1000) references keeps a long enumeration off one event-loop tick, exactly as the block seed does.

A `responsible` holder has no such memory to seed — the holders of a blob it is not the writer of are not recorded anywhere — so after a restart it announces once to its whole cohort, which receivers answer `whole` cheaply, bounded by `growthBlockBudget` (64) references per check with at least `minRebalanceIntervalMs` (60 s) between checks. That is well inside `BLOB_ANNOUNCES_PER_PEER_PER_MINUTE`, as docs/blobs.md §Who may fetch and who may store already states.

**Holder evidence while running.** `BlobCopyDrainDeps.onHolderConfirmed` (unset today) is wired to `monitor.recordBlockHolders({ blockIds: [ref], holders: [peerId] })`, so a `whole` answer or a `held` the drain receives also counts for growth and the monitor stops re-announcing that reference to that peer.

## The monitor instance

`RebalanceMonitor` needs FRET and an `ArachnodeFretAdapter`, which exist only inside the arachnode `if (fret)` gate in `wireServingRole`; the blob service, the drain and the reaction are built in `createLibp2pNodeBase` after `wireServingRole` returns. So the gate's two handles come back on the serving result and the monitor is built with the blob code it reacts with:

```ts
/** What the rest of the factory reads back from the serving role. */
interface ServingRole {
	// … existing …
	/** FRET and its arachnode adapter, when arachnode is enabled and FRET is present. The blob cohort monitor is built from these in the factory, beside the blob service it reacts with. */
	arachnode?: { fret: FretService; fretAdapter: ArachnodeFretAdapter };
}
```

assigned inside the gate (`fret` is the same `(node as any).services?.fret` handle the block monitor gets through `NetworkManagerService.initRebalanceMonitor`, and the monitor only reads `getDiagnostics` off it once a key network is wired) and left undefined otherwise. A client (`NodeOptions.servesBlocks: false`) runs no serving role, so it gets no blob monitor — which is right: a client is in no cohort, never takes a `responsible` hold (`BlobAnnounceReceiver` answers `not-responsible`), and its owed blobs are followed by the drain on its own passes. Without FRET or with arachnode disabled the blob reaction is inert exactly as the block one is.

In `createLibp2pNodeBase`, after the owed-copies drain block:

```ts
const heldBlobRefs = new Set<string>();          // its own set, never the owned-block set
if (served?.arachnode && (options.rebalance?.enabled ?? true) !== false) {
	try {
		blobRebalanceMonitor = new RebalanceMonitor({
			libp2p: node, fret: served.arachnode.fret, partitionDetector, fretAdapter: served.arachnode.fretAdapter,
			trackedBlocks: heldBlobRefs,
			keyNetwork, clusterSize: consensusConfig.clusterSize,
			// Every id in heldBlobRefs came from a blob record, so it is a parsed reference.
			routingKeyOf: id => routingKeyForBlob(id as BlobRef),
			logName: 'blob:copy'
		}, options.rebalance);
		// … the feed, the reaction, the handler, start, the stop wrapper, the seed …
	} catch (err) {
		wiringLog('blob rebalance wiring init failed: %o', err);
	}
}
```

- `blobRebalanceMonitor` is a `let` declared **above** the drain, as `blobCopies` and `blobReceiver` are, so the drain's `onHolderConfirmed` can close over it.
- It shares `options.rebalance` with the block monitor — tuning and `enabled`, one switch for "react to cohort changes" — and is constructed directly rather than through `NetworkManagerService.initRebalanceMonitor`, which holds the block instance.
- A wiring failure is logged and non-fatal, as the block monitor's and spread's are: following a cohort is a resilience mechanism, and the drain still keeps a writer's copies moving without it.
- Expose `(node as any).blobRebalanceMonitor` for tests and diagnostics, as `rebalanceMonitor` and `blobCopyDrain` are exposed.

Order inside the block: subscribe the feed, build the reaction, attach the handler, `await monitor.start()`, install the stop wrapper, then fire the seed off the start path. The seed must follow `start()` — `recordBlockHolders` is ignored while the monitor is stopped. The stop wrapper unsubscribes the feed, sets the seed's stopping flag and stops the monitor, in the shape the owned-block seed's wrapper already uses at `seedOwnedBlocksFromStorage`'s call site:

```ts
void seedHeldBlobs({ records: blobs, owed: owedBlobLedger, monitor, isStopping: () => seedStopping })
	.catch((err) => { wiringLog('held-blob-seed seed failed: %o', err); });
```

## The handler

Mirrors the block one — reaction hopped off the monitor's synchronous emit loop, a rejection logged rather than left unhandled:

```ts
monitor.onRebalance((event) => {
	reaction.handle(event).then(async (result) => {
		for (const ref of result.released) await blobs.releaseResponsible(ref);  // the feed untracks it when no owed hold remains
		for (const ref of result.retained) monitor.retainLost(ref);
		for (const [ref, outcome] of result.growth) monitor.recordGrowthOutcome(ref, outcome);
	}).catch((err) => { blobCopyLog('reaction:failed err=%o', err); });
});
```

`blobCopyLog` is a new module-level `createLogger('blob:copy')` beside `blobLog` in `packages/db-p2p/src/libp2p-node-base.ts`, so the handler's own failure lands in the same namespace as the monitor and the reaction. The released loop awaits each release in turn: there are at most a cohort's worth per check, and each is one serialized record write.

The reaction's deps are bound here: `records: blobs`, `owed: owedBlobLedger`, `acceptance` the same closure the drain takes, `declining: blobCopies` (undefined when the drain is switched off), `announce` the same closure the drain takes, and `stat: (peerId, refs) => blobTransfer.client.stat(peerIdFromString(peerId), refs)`.

## Edge cases & interactions

- **Leaving a cohort with too few holders.** `retainLost` keeps the reference re-reported `lost` on later checks with the re-check timer armed, and the hold is dropped once enough current members answer `whole`. The decision is pinned by the prereq's spec; the loop above is what connects it.
- **Regaining responsibility while retained.** The monitor clears `releasePending` and reports growth as a first observation; the hold was never dropped. Inspection.
- **A release that leaves no other hold** deletes the record, which fires the feed with no holds and untracks the reference — and the record deletion schedules the piece sweep, which is what reclaims the bytes. A reference that still has `owed` (this node wrote it and was also in its cohort) stays tracked through that hold. Inspection.
- **Non-members** are never announced to or counted: the reaction's membership filter covers both arms. Inspection.
- **Partition.** The monitor suppresses its checks and the reaction re-checks before acting, so no release and no announcement. Inspection.
- **The feed firing during a check.** `trackBlock` and `untrackBlock` mutate the set the monitor may be iterating; adding or deleting a `Set` entry mid-iteration does not throw in JavaScript and entries are visited best-effort, which the block wiring already accepts and documents for the same set. Say so in a comment rather than adding a lock. Inspection.
- **Two reactions overlapping.** `onRebalance` handlers are synchronous and `void`, so the handler above starts a reaction and returns; a second check firing before the first reaction settles runs a second one over the same references. `BlockTransferCoordinator` guards this with its `inFlight` keys; `BlobCohortReaction` has no such memory, by design — it is a pure function of the event. The overlap is unlikely (`minRebalanceIntervalMs` is 60 s and a reaction is a few round trips) and benign if it happens: `releaseResponsible` is idempotent, duplicate announcements are what `AnnounceLimiter` is for, and the growth outcomes agree. Decide here whether to keep the handler guardless and say so in a comment, or hold one in-flight promise per monitor and skip a check that lands on top of it. Not the prereq's to settle — it does not own the handler.
- **Block replication unchanged.** The block monitor, its reaction and the owned-block set are untouched; the blob monitor has its own set, its own snapshot memory (`responsibilitySnapshot` is per-monitor) and its own logger namespace. `test/rebalance-monitor.spec.ts`, `test/rebalance-reaction.spec.ts`, `test/rebalance-monitor-node-wiring.spec.ts`, `test/rebalance-committed-holders.spec.ts` and `test/rebalance-push-holders.spec.ts` pass unchanged — the one new field on `ServingRole` is additive.
- **A node with the copy drain switched off** (`blobs.copy.enabled: false`) still follows its cohort for the blobs it holds `responsible`: the reaction's `declining` dep is absent and nothing declines, and no owed entries exist because `announce` rejects without the drain. Inspection.

## Tests

None. Everything here is registration and feed wiring: the reaction's two arms are pinned by the prereq's spec, the monitor's check-and-report behaviour by the rebalance suites with the routing rule a pass-through, and the copying this triggers end to end by `feat-blob-owed-copies-are-drained`'s two-node tests. There is no end-to-end mesh test of the blob monitor for the same reason there is none of the block monitor's growth arm: it would exercise FRET admission timing rather than this code.
