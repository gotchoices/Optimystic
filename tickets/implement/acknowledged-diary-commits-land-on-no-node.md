# Acknowledged Diary commits land on no node

## What was found (fix stage, 2026-09-11)

The failing arm is `packages/db-p2p/test/routing-key-convention-divergence.spec.ts` > "a Diary written through the transactor: replica placement per committed block". It failed 1 run in 3 and 1 run in 8 in two batches here, always with `expected [] to have the same members as ['entry-0', 'entry-1', 'entry-2']`. The full debug trace of a failing run is in `tickets/.logs/acknowledged-diary-full3.log` (until the pruner removes it; the spec regenerates it with `DEBUG='optimystic:db-p2p:cluster-member*,optimystic:db-p2p:coordinator-repo*,optimystic:db-p2p:storage-repo*,optimystic:db-p2p:reconcile-block*'`).

The trace settles the ticket's open question. The pend is admitted and the revision is then dropped by every member, and the coordinator counts the consensus votes as success anyway. Concretely, for the Diary's log block (`peM2…` in that log):

- **Revision 1.** The first append pends header and log block in one cluster transaction, keyed on the header, so the log block's pend never reaches the log block's own cohort. The commit of revision 1 then runs on that cohort: all four responsible members throw `Pending action … not found` (they are "behind"), each reconciles from the other cohort peers, and every reconcile declines with `reconcile:no-rev-quorum` (`holders: 0`). The coordinating node's own member committed it locally during the same broadcast. The coordinator answers success. Revision 1 now exists on exactly one node, the coordinator, which is outside the responsible cohort.
- **Revisions 2 and 3.** Each pend is accepted by all cohort members: `StorageRepo.pend` happily records a pending update for a block it holds no revision of. At commit, `StorageRepo.internalCommit`'s fork guard refuses on every member (`commit:missing-base … local latest none is not the declared base 1 of rev 2`), `refuseMissingBase` deletes the pending record, and the member reconciles from the cohort, which again declines. The coordinator's own member (it is in the cohort, because the harness and production both add self to every cohort) refused the same way; `CoordinatorRepo.commit` runs `confirmCommitRivalAgainstLocal`, finds no rival, logs `coordinator-repo:commit-local-refusal-tolerated` with `confirmation: 'unconfirmed'`, and returns `{ success: true }`. Nothing holds revision 2 or 3 anywhere, and no pending record survives, which matches the raw-state dump in the original ticket.

So the defect site is one rule with two exits in `CoordinatorRepo.commit`: **a commit is acknowledged when the record shows enough approving commit votes, regardless of whether any member's storage kept the revision.** The `localExecuted` arm tolerates its own member's non-rival refusal; the fallback arm's `tolerateLocalCommitDivergence` does the same for a thrown or `missing-base-revision` local commit. Neither asks the other members what their storage did, because `MemberApplyOutcome` carries only a `pend` arm; its doc comment says a commit that reached consensus "is authoritative", which is exactly the assumption this trace breaks. The NOTE on the ahead-divergence tolerance in `ClusterMember.applyConsensusOperation` ends with "if consensus-without-durability is ever observed again, look at those guards' remaining abstain residuals, not at this branch": it has now been observed, and the residual is not a guard's abstention but the absence of any durability count at all.

A second, smaller fact is what makes the fix able to *succeed* rather than only fail loudly. A behind member reconciles from `record.peers` minus itself, and the coordinating node is in that set (self is in every cohort under the harness, under production's membership-scoped `findCluster`, and under option D2(a) of the blocked routing ticket). `createReconcileBlock` accepts a single holder when that holder's copy carries a verified cohort commit proof, and the coordinator's member persists that proof at commit. The only reason the four members' reconcile found `holders: 0` is ordering: `ClusterCoordinator.broadcastMergedRecord` delivers the merged record to every member, local one included, in a single `Promise.all`, so the remote members reconcile while the coordinator's own member has not yet applied.

**Experiment (reverted; the tree carries no code change from this stage).** Delivering the merged record to the local member first and to the remote members after it, and nothing else, made the full spec pass 40 of 40 runs. In the 2 of those runs that hit the bad geometry, all four behind members restored revision 1 from the coordinator's certified copy (`reconcile:certified-selected` then `reconcile:restored`, four times, in `tickets/.logs/acknowledged-diary-exp14.log`), revisions 2 and 3 then applied normally, and the Diary read back complete. Before the change the arm failed about 1 run in 5.

One further observation, not chased: one isolated run of the arm (`--grep "a Diary written"`, so the earlier arms' writes were absent) failed with `SyncRetryExhaustedError … exhausted 10 retries` after 18 seconds, with four `reconcile:no-rev-quorum` for revision 1 and nothing else logged (`tickets/.logs/acknowledged-diary-run8.log`, captured with the wrong log namespaces). Fifteen further isolated runs passed. If the 30-run verification below surfaces it again, capture it with the namespaces above and treat it as a second arm of the same root cause unless the trace says otherwise.

## The invariant to implement

A commit is acknowledged to the writer only when **more than half of the cohort the commit ran on (`record.peers`) reports that its storage durably holds the committed revision under this action**, measured after each member's reconcile. Consensus votes are necessary for a commit to be authoritative; they are not evidence that it was stored. This is the commit-tier twin of the pend-refusal channel (`docs/correctness.md` "Pend refusal reporting"), and the same majority rule `clusterReachedCommitConsensus` already uses.

The rule must not depend on the routing convention: it is the backstop for any shape in which a cohort member cannot apply a commit (partition, churn, a coordinator picked after missing the pend), and the blocked ticket `writer-and-servers-disagree-on-where-a-block-lives` is untouched by this work.

## Design

**Arm A — members report what their storage did with a commit, and the coordinator counts durable holders, not votes.**

- `MemberApplyOutcome` gains `commit?: CommitResult`. Unlike the pend arm, successes are reported too, because the coordinator needs a positive count. `applyOutcomes` crosses the wire as plain JSON on the cluster record (`cluster/service.ts` parses the record with `JSON.parse`), it is outside every hash by design, and there are no serialization vectors for it, so this is not a byte-format change. Update the type's doc comment (the "only the pend arm exists" sentence and the trust rules: a false success entry is no worse than the same member's signed approve vote, which already counted; a false refusal is retry pressure, the pend arm's existing posture).
- In `ClusterMember.applyConsensusOperation`, compute one **post-reconcile durable verdict** for the commit operation: `{ success: true }` when, for every block in `commit.blockIds`, local storage records `commit.rev` under `commit.actionId` (use the revision index via `IRevisionActionReader.getRevisionAction`, or `latest` when `latest.rev === commit.rev`; a member whose `latest` has moved past `commit.rev` but whose index names this action is durable). Otherwise the storage refusal, or a refusal built from the thrown missing-pend message. The missing-pend throw path currently retains nothing; it must now retain this verdict too. Retain it in `executedCommitResults` *after* `reconcileDivergentCommit` so both the coordinating node's `getExecutedCommitResult` and the response record see the same post-reconcile answer, and stamp it on the response in `withOwnApplyOutcome` beside the pend arm (keep the pend arm's refusal-only rule; the commit arm always stamps).
- `ClusterCoordinator.executeClusterTransaction` returns `cohortCommitOutcomes` keyed by peer id, built the way `cohortPendRefusals` is: taken from each peer's own response, self excluded, shape re-checked (`success === true`, or an object with `success === false`), anything else dropped.
- `CoordinatorRepo.commit` computes `durableHolders` = remote members reporting `success: true` + 1 when `localExecuted` and the retained local verdict is a success. It acknowledges only when `durableHolders > Object.keys(record.peers).length / 2`. Otherwise it returns a **retryable refusal**: `{ success: false, conflict: true, reason: COMMIT_NOT_DURABLE_REASON + ': ' + detail }` with a new exported constant and `isCommitNotDurableFailure` helper next to `MISSING_BASE_REVISION_REASON` (same file, same pattern). Keep the existing sharper answers ahead of it: `ConflictRaceLostError` conversion, `classifyCommitStaleRejection`, and the `confirmCommitRivalAgainstLocal` conversion in the `localExecuted` arm all still run first; the durability gate replaces only the two "tolerate and answer success" exits.
- In the fallback arm (coordinator not in the cohort), evaluate the gate **before** the local fallback commit and skip that commit when the gate fails. A lone off-cohort holder is the seed of the revision-1 placement in the trace and must not be created by a refused commit. When the gate passes, the fallback commit proceeds as today.
- `markBlocksSeen` / `armFreshness` stay tied to the vote count as now; do not conflate the two quorums.
- Why `conflict: true`: the members that refused with `missing-base-revision` have already deleted their pending records, so the writer must cancel and re-drive at a fresh revision, which is what a conflict-shaped answer makes `Collection.syncAttempts` and the multi-collection `pendPhase` do. `NetworkTransactor.staleFromBatches` drops the reason prose but carries `success: false`; that is enough for the retry loop. State the 2PC ambiguity in a code NOTE at the gate: a refused commit may still land on members later through `scheduleCommitRetry`, and the writer's retry with the same action id converges either way (`isOwnRevision` in `StorageRepo.pend` and `commit`, `inFlightActionId` in `Collection.updateInternal`); the refusal means "not confirmed durable at a quorum", never "guaranteed absent".

**Arm B — the coordinating node's own copy is available to reconciling members.**

- In `ClusterCoordinator.broadcastMergedRecord`, deliver the merged record to the local member (when it is in `peerIds`) first and await it, then deliver to the remote members in parallel as today. The commit round in `commitTransaction` may stay parallel: a member cannot reach consensus there, since the record it receives carries no commit signatures yet. Document the ordering as load-bearing at the site: a behind member reconciles from `record.peers` during its apply, and the coordinator's member is the one peer guaranteed to hold the revision by then; its copy carries the cohort's proof (`buildBlockCommitProof`), which `createReconcileBlock` accepts from a single holder.
- The cost is one in-process apply before the network fan-out; no extra round trip.
- Residual this does not cover (say so in the docs): a coordinator outside `record.peers` (the fallback arm) is not a reconcile target, so a cohort with no holder at all stays behind and Arm A refuses the commit honestly. Under the blocked routing ticket's option D2(b) that shape becomes normal; it is that ticket's job to keep the coordinator inside the cohort or to add a push, not this one's.

**Together** these make the Diary arm pass on the bad geometry (Arm B lets the four behind members restore revision 1 from the coordinator, revisions 2 and 3 then apply on a full cohort) while Arm A guarantees that any remaining shape fails loudly instead of silently.

## Deterministic pin (required)

Add `packages/db-p2p/test/commit-durability-quorum.spec.ts`, built on the harness in `cohort-pend-refusal-channel.spec.ts` (two real `ClusterMember`s over `StorageRepo` + `MemoryRawStorage`, real `ClusterCoordinator` and `CoordinatorRepo`, the coordinating member reached via `localCluster`, fixed block id, fixed action ids, `clusterSize: 2` so 2 of 2 is both the promise super-majority and the durable majority). Seed the block at revision 1 on the coordinating member only; the remote member never holds it. Pend an update-only transform at revision 2 through the repo (it is accepted by both today), then commit revision 2 carrying `blockDigests: { [BLOCK]: { baseRev: 1, digest } }` (the fork guard needs `baseRev`; `digest` is `canonicalBlockHash` of the expected result, which for an empty update is the seeded block). Three arms:

- **No reconcile path** (members built without `reconcileBlock`, as that spec builds them): the commit must return `success: false` with `conflict: true` and a reason starting with the new constant; the remote member must hold no revision of the block afterwards. This is the arm that fails today (it returns `success: true`).
- **Reconcile from the coordinator** (build the remote member with `createReconcileBlock` whose `fetchArchive` serves the coordinating member's storage through `serveBlockArchive`, and `saveReplicatedBlock` into the remote's storage, thresholds as in the mesh harness): the commit must return `success: true` **and** the remote member must hold revision 2 under the action, restored with the proof. This pins Arm B's ordering: with the old parallel delivery the remote's reconcile runs before the coordinating member has applied.
- **No false refusals**: both members seeded at revision 1, ordinary commit at revision 2 returns `success: true` and both hold it.

Keep `routing-key-convention-divergence.spec.ts` unchanged; it is the mesh-level regression pin.
