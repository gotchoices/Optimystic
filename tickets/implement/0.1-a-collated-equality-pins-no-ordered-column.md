## Where this stands on Quereus 5.4.0

The wrong-order bug this ticket was filed for is fixed upstream. Both engine changes it asked for are in 5.4.0:

- `PredicateConstraint.collation?: string` carries the normalized collation a comparison runs under (absent means BINARY), so `b = 'x' collate nocase` no longer reaches a module as a plain `=`.
- `orderingClaimSurvivesCollation` in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`, called from `@quereus/quereus/src/planner/rules/retrieve/rule-grow-retrieve.ts`, refuses an ordering claim when any usable equality on a key column of the ordering index compares under a collation the key column does not refine, so the Sort is kept.

Measured on 5.4.0 (a throwaway mocha spec, `default_transactor: 'test'`), `create table t (id text primary key, b text, c text)` with `idx_bc on t(b, c)` and rows `('1','X','b'), ('2','x','a'), ('3','y','c'), ('4','x','d')`:

| statement | memory plan | Optimystic plan | both return |
|---|---|---|---|
| `where b = 'x' collate nocase order by c` | SORT / FILTER / INDEXSCAN `_primary_` | SORT / FILTER / SEQSCAN | 2, 1, 4 (correct) |
| `where b = 'x' order by c` | INDEXSEEK `idx_bc` ORDER BY, no SORT | same | 2, 4 (correct) |
| `where b = 'x' collate nocase order by b, c` | SORT / FILTER / INDEXSCAN | SORT / FILTER / SEQSCAN | 1, 2, 4 (correct) |

So nothing returns mis-ordered rows any more, and there is nothing to file upstream.

## What is still wrong here

The module itself never reads `PredicateConstraint.collation`. It relies on the engine to throw away whatever it claimed wrongly, and when the engine does, the candidate the module chose over a valid one is gone. Measured on 5.4.0 with the same rows but two single-column indexes, `idx_b on t(b)` and `idx_c on t(c)`:

| statement | memory plan | Optimystic plan |
|---|---|---|
| `where b = 'x' collate nocase order by c` | FILTER over INDEXSCAN `idx_c`, no SORT | SORT / FILTER / SEQSCAN |
| `where b > 'w' collate nocase order by c` | FILTER over INDEXSCAN `idx_c`, no SORT | SORT / FILTER / SEQSCAN |

Rows are correct in both modules. The cause is that the Optimystic module offers an equality seek (or a range seek) of `idx_b` that claims the NOCASE filter. It prices lower than the walk of `idx_c`, so `getBestAccessPlan` returns it; the engine's `classifyCollationCover` then finds the NOCASE comparison over a BINARY key (`MISMATCH_UNSAFE`) and answers with a sequential scan plus the residual filter, and the Sort stays. The memory module, which gates on the filter's collation, offers no such seek, so its walk of `idx_c` wins.

One root cause, three sites, all reading a filter as if it compared bytes:

- **Pinning** — `pinnedColumns` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts` treats `b = 'x' collate nocase` as fixing `b`, though it keeps `'X'` and `'x'`, which sit in separate groups of the tree. Its `NOTE:` names this ticket's upstream predecessor and says what to do once the field exists.
- **Equality seek** — `firstEqualityRoleFilter` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`, the one filter picker under `matchEqualitySeek` for both the primary key and every secondary index, picks the NOCASE equality as a seek key. A byte seek for `'x'` would miss `'X'`.
- **Range seek** — `claimableBound` in the same file accepts a NOCASE bound, so `rangeSeekCandidate` claims it.

## The change

Every key column this module seeks, walks or pins on is BINARY already (`seekCanBeTrusted`, `bytesOrderAsValues` and `pinnedColumns` all require it), so at each site the rule reduces to "the filter compares under BINARY". Write it once, as one exported predicate in `index-walk.ts` (beside `seekCanBeTrusted`, which judges the key side of the same question), and call it from all three sites:

- For the two equality sites use the engine's documented contract, `collationRefines(filter.collation ?? 'BINARY', keyCollation)` (imported from `@quereus/quereus`), with the key column's collation — the table column's for `pinnedColumns` and for a primary-key key column, the index column's for a secondary index. That stays correct if a non-BINARY key column is ever trusted.
- For a range bound the names must be equal (`normalizeCollationName`), which is the contract `PredicateConstraint.collation`'s doc states for ranges. A bound that fails it makes `claimableBound` false, which already declines the whole range, as a non-string literal does.

Then delete the `NOTE:` above `pinnedColumns` and say in its comment that a filter pins only when its comparison refines the column's collation.

The `Partial primary key scan` candidate in `getBestAccessPlan` (the `isPkColumn && filter.op === '='` branch) claims no filter and only adjusts cost; gating it the same way is optional and cosmetic.

## Tests

One planner-level test in `packages/quereus-plugin-optimystic/test/ordering-claim-guard.spec.ts`, beside "does NOT skip a pinned column whose equal values can have different bytes": filters built with `collation: 'NOCASE'` on a BINARY column. Over `idx_b(b)` and `idx_c(c)` with `where b = 'x' collate nocase`, `order by c` must come back as the walk of `idx_c` with no filter claimed; over `idx_bc(b, c)`, `b` must not be pinned (no claim for `order by c`), and a NOCASE range bound on `b` must not be claimed. That is the reproduction at the lowest layer.

One SQL differential case in `packages/quereus-plugin-optimystic/test/index-ordered-walk.spec.ts`: the two-index table above, `where b = 'x' collate nocase order by c`, same rows as the memory table and `expectOrderFromIndex`. It is the end-to-end form of the defect the module still has; the original wrong-order table is now guarded by the engine and needs no case of its own here.

## Docs

`docs/internals.md`:

- §An ordered read walks a secondary index, **Which columns**: a column is pinned only when the filter's comparison collation refines the column's (BINARY), as well as the column's own collation being BINARY.
- §A range predicate seeks a secondary index: the sentence "A range under a collation other than the index's never reaches the module as a seek: the engine's `classifyCollationCover` declines it" becomes that the module declines such a bound itself (`claimableBound`), and the engine's check is the backstop.
