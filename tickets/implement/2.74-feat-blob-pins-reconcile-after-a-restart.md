# Blob pins reconcile after a restart

Second of three parts that finish the SQL side of blobs (`feat-queued-blob-pins-settle-with-their-transaction` before it, `feat-sql-columns-hold-blob-references` after).

A reference pin is written when a commit starts and released when that commit's outcome is known. Two things break that pairing, and both leave bytes pinned on this machine for ever:

- **the process stopped in between** — after the pins were written and before the commit was sent, after it landed and before the release ran, or while a queued entry was in the queue with no journal to restore it; or
- **the release was skipped on purpose** — `committed()` and `settleQueued` keep a pin whose scope could not be confirmed registered or whose announce failed (`blob:pin-kept`), precisely so something later can retry it.

This part is that something. It judges every transaction pin whose transaction this process is not holding, from **committed state**: the reference tree the pin's own label names either lists the reference or it does not.

## Additions to `SqlBlobPins`

```ts
interface SqlBlobPinsDeps {
	// … from the two earlier parts, plus:
	/** True for a transaction this process must not judge yet: the bridge's active transaction, or
	 * one the offline controller still holds (queued, being submitted, partially committed, or
	 * journaled and not yet put back). */
	isLive(transactionId: string): boolean;
	/** False until it is safe to read a transaction's absence as "settled": with a journal, until the
	 * restore has completed one pass in this process. True when no journal is configured. */
	reconcileReady(): boolean;
}

/** Settle every transaction pin whose transaction is not live, from committed state. Never throws.
 * A no-op until `reconcileReady()`, and when nothing may be stale. */
reconcile(): Promise<void>;
/** A backend resolved in this process: reconcile over every known backend. */
backendResolved(backend: BlobBackend): void;
```

`reconcile` is chained like `settleQueued` (one step per call, awaiting `whenTransactionIdle()` first, bailing when `disposed`), so a settle and a reconcile never handle one transaction's pins at once.

**Coalescing.** A reconcile requested while one is *chained and not yet started* joins that one, exactly as `OfflineRestore.run`'s `pendingPass` does; one requested while a pass is *running* is chained behind it, since a running pass may already have listed. Without this, `reconcile` → `knownBackends()` → a newly resolved backend → `backendResolved` → another `reconcile` would queue a pass per resolution. (It would still terminate, since the second pass resolves nothing new, but coalescing makes that obvious instead of merely true.)

**`mayHoldStalePins`, and why `reconcile` is usually free.** `listPins` scans every blob record on the machine and reads each one (the `NOTE:` at `LocalBlobService.listPins` in `packages/db-p2p/src/blob/local-blob-service.ts`). A reachability wake can arrive often, and a full scan per wake on a phone that churns connections is not acceptable. So `SqlBlobPins` keeps one boolean:

- starts `true` (a fresh process has never looked);
- set `true` by `backendResolved` (a store this process has not looked at), and by **any** arm that keeps a pin it could not release — `committed()`, `settleQueued` and `reconcile` itself;
- set `false` by a pass that completed having kept nothing and having listed every known backend without a failure.

`reconcile()` returns immediately when the flag is `false`. Every trigger respects it, including `restore()`: a host that calls `restore()` repeatedly pays one pass, not one per call. A pass that threw, or whose backend resolution failed, leaves the flag `true`.

**One pass.** For each `knownBackends()`:

1. `listPins(TRANSACTION_PIN_PREFIX)`, parsing each label through `parsePinLabel`; a label that does not parse is skipped (it carries this plugin's prefix but not one of its shapes, so releasing it would drop somebody else's hold — `parsePinLabel`'s own rule).
2. Group by transaction id and drop every id `isLive` answers true for.
3. `put` pins of the remaining ids: `unpin`. A `put` pin outlives its transaction only when the put resolved after the transaction ended (`SqlBlobService.put` fixes the label when the put *starts*), and such bytes are referenced by nothing.
4. Reference pins of the remaining ids, grouped by scope: `BlobReferenceTree.listed(backend.transactor, scope, refs)` (`packages/db-core/src/blob/reference-tree.ts`) — one committed read per scope, over the scope's whole set of pinned references at once.
   - **certain and listed**: confirm the scope registered as `settleQueued` does (`ensure` when `tablesOf(scope)` is non-empty, else the check-only `isRegistered`), `announce(ref, scope)`, `unpin`. On failure keep and log `blob:pin-kept`.
   - **certain and not listed**: `unpin`. The transaction never committed that reference, or a later transaction removed it — and a removed reference is not the writer's to keep.
   - **uncertain** (`listed` answered `certain: false`): keep every pin of that scope, log `blob:reconcile-uncertain scope=… refs=…`, and leave the flag `true` so the next trigger tries again.

Each scope and each reference in its own `try`; nothing out of a pass propagates (the chain's step logs it).

Add a `NOTE:` at `reconcile`: "lists every transaction pin on each trigger and reads one reference tree per scope that has one; if a machine ever keeps many pins across wakes, remember the uncertain scopes and retry only those."

## Where `reconcile` is triggered

- **After `OfflineMode.restore()`** — and so after `plugin.hydrate`, which calls it. `restore()` **awaits** the reconcile (which never throws, so it cannot fail a hydrate), which is what makes a restart's reconciliation observable to the host and to a spec without a poll. Say that in `restore()`'s doc comment and in the `hydrate` comment in `plugin.ts`.
- **On every reachability wake** (`OfflineMode.onGateChange`), after its own work. The chained step's own `whenTransactionIdle()` is the idleness wait, so the call site is a bare `void this.blobPins?.reconcile()` and does not repeat the restore retry's `whenTransactionIdle().then(...)` dance.
- **When a backend first resolves in this process** — `backendResolved`, subscribed through the existing `CollectionFactory.onBlobBackendResolved`, which replays the backends already resolved and then reports each new one exactly once. That subscription is made in `register`, right after the pins are built.

**`plugin.hydrate` resolves the default network's blob backend**, after `await offline.restore()` and before it returns, then awaits `blobPins.settled()`. Without it a host that has hydrated but not yet opened a table on the default network has no known backend, so the start-of-process pass would have nothing to look at. The resolution is wrapped: a failure is logged (`blob:backend-resolution-failed`) and `hydrate` still resolves. It builds no libp2p node that `hydrateCatalog` has not already built — it reads the catalog through the same transactor — so this adds a piece store, not a network.

A table on a *different* network gets its start-of-process pass when that table is first initialized and its backend resolves.

## `isLive` and `reconcileReady`

Both answered by `OfflineMode`, so `SqlBlobPins` interprets no statuses:

```ts
/** Whether the queue or the restore still holds `transactionId` — queued, being submitted,
 * partially committed, or journaled and not yet put back. False once it has settled, and for an id
 * this machine never queued. */
holdsTransaction(transactionId: string): boolean;
/** Whether a transaction's absence from the queue can be read as "settled": with a journal, only
 * once a restore pass has completed in this process. True with no journal. */
reconcileReady(): boolean;
```

`holdsTransaction` is `this.queue.status(id) !== undefined || (this.restorer?.holds(id) ?? false)` — `OfflineQueue.status` answers `undefined` for an entry that has left the queue with its terminal status, which is exactly "settled". `OfflineRestore` gains `holds(transactionId): boolean`, true for a deferred record (`deferred`) or one whose discard is still settling (`discarding`), so a record being withdrawn is not judged from committed state while its own settle is already chained.

`reconcileReady` is `this.restorer === undefined || this.restorer.hasCompletedPass()`. `OfflineRestore` gains a private flag set at the **end** of `pass()`, so a pass that threw (an unknown record version, a table initialization that failed) leaves it false and the reconcile stays a no-op. This is the guard that matters most: before the first pass, a journaled entry still on disk is in no queue, `isLive` answers false, its reference is not yet listed in committed state, and its pin would be dropped while the entry went on to commit.

`SqlBlobPins`'s `isLive` dep is then `id => bridge.activeStampId() === id || offline.holdsTransaction(id)`, reading the bridge's current transaction through what `feat-blob-pins-follow-sql-commits` already exposes.

## Edge cases & interactions

- **A restart after the commit landed but before its release.** The scope's tree lists the reference, certainly: announced and released. Test.
- **A restart after a commit that never landed** — the process died after pinning and before sending. The tree certainly does not list it: released. Test.
- **The cohort cannot be reached at reconcile time.** The committed read answers uncertain; every pin of that scope is kept, the flag stays set, and the next wake or `restore()` retries. Test, with the spec's delegating transactor answering the scope tree's blocks `unavailable` while armed.
- **A restart while a journaled entry is still queued.** The restore puts it back, `holdsTransaction` answers true, and its pins are skipped until it settles (`settleQueued`, the previous part). Covered by that part's test; here, inspection of `isLive`.
- **A journaled entry the restore has not read yet.** `reconcileReady()` is false, so the pass is a no-op. Inspection — and the one case where getting the order wrong loses an application's bytes.
- **A journaled entry the restore read and *deferred*** (its table is missing or unreadable). `OfflineRestore.holds` answers true, so its pins are kept even though `reconcileReady()` is now true. Inspection.
- **No journal configured.** `reconcileReady()` is true from the start; a queued entry did not survive the restart, so its pins are correctly unlisted and released on the first pass. Inspection.
- **A table dropped on another machine between the commit and the reconcile.** `tablesOf(scope)` is empty, `isRegistered` answers `false`, the pin is released and the dropped tree is never re-registered. Inspection.
- **A reconcile overlapping the tail of an online commit.** Between `endTransaction()` and the bridge's off-chain `committed()`, the transaction is no longer live and its pins are still there, so a pass can announce and unpin them first. Both paths are idempotent — a second announce finds the stored durability and a second unpin finds no pin — and by that point the commit is already durable, so committed state says the same thing to both. A `NOTE:` at `reconcile` naming this interleaving, since it reads like a bug until the idempotence is spelt out.
- **A stray `put` pin.** Released by step 3 of the pass. Inspection.
- **A transaction pin on a network whose table this process never opened.** The backend is resolved through `knownBlobBackends` only once some table on that key has resolved options. Until then the pin stays — correct, since nothing here can read that network's reference tree either. Inspection.
- **A pin label this plugin's prefix matches but its shapes do not.** Skipped, never released. Inspection (`parsePinLabel`).
- **Two processes over one store.** Both reconcile; each one's `isLive` knows only its own transactions, so one process could release a pin the other's open transaction is relying on. Out of scope and not newly introduced — a blob store is single-writer per machine, as `blobStorageFactory`'s own contract assumes. Record it as a bullet in the `docs/blobs.md` §SQL text, not as a guard.

## Tests

`packages/quereus-plugin-optimystic/test/blob-pins-reconcile.spec.ts`, over the harness `blob-pins-harness.ts` from the previous part (shared `MemoryRawStorage`, shared piece/key-value stores, shared journal, `restart()`). Each arm writes a transaction reference pin **directly on the backend** for a transaction id that is neither open nor queued — `backend.service.pin(ref, transactionReferencePinLabel(id, scope))`, which is exactly the state a crashed process leaves — and then restarts into a fresh plugin.

- **Listed.** A row referencing the blob is committed normally first, so the table's reference tree lists it; the plugin is then restarted with a hand-written pin for a dead transaction id under that scope. After `hydrate` the pin is gone and `stat(ref)` reports durability `local` (the announce happened).
- **Not listed.** No row references the blob; the pin names the same scope. After `hydrate` the pin is gone and nothing was announced — assert `stat(ref).durability` is undefined, so a wrong announce cannot pass as a release.
- **Uncertain.** As the listed arm, but the transactor registered on the restarted plugin's factory is wrapped so every block of the `/blobrefs` collection answers `unavailable` while armed — `Isolation` with a predicate on the collection id, as `packages/quereus-plugin-optimystic/test/isolation.ts` and `offline-restore.spec.ts` use it. After `hydrate` the pin is **still there**; disarm and `await plugin.offline.restore()`; it is released.

Three tests, one per arm of the committed read, and the third is also the proof that the keep-and-retry path works end to end. The registered-scope arms and the `put`-pin arm are checked by inspection: they are branches of the same pass with no new mechanism behind them.
