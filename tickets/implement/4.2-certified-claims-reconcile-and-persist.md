# Reconcile path certification + persist the verified proof

Third of three tickets from `accept-certified-claims-in-repair`. The selection rules and the
shared `cluster/certified-claims.ts` helper are settled in `certified-claim-selection`; the
read path landed in `certified-claims-read-repair`. Read-repair acquisition and commit-time
reconcile share ONE callback instance (`libp2p-node-base.ts:905` passes `reconcileBlock` to
both), so everything here lands on both paths — verify both.

## Carry the proof into the reconcile candidates (`cluster/reconcile-block.ts`)

Today `toCandidate` (:84) discards `entry.proof`, so a certified short-circuit fires on the
read path and never on reconcile — the paths would silently heal by different rules, which the
shared `quorum-restore.ts` primitives exist to prevent.

- `ReconcileCandidate` gains `proof?: BlockCommitProof`; `toCandidate` carries
  `data.proof` through (the archive keys the proof inside the same revision entry —
  `storage/struct.ts` — so mis-pairing is already structurally blocked).
- `ReconcileBlockDeps` gains `superMajorityThreshold: number` (required — verification needs it;
  `libp2p-node-base` has `consensusConfig.superMajorityThreshold`) and optional
  `anchoring?: ProofAnchoring`.
- After answers are collected, certify each candidate (parallel, thresholds
  `{ superMajorityThreshold, simpleMajorityThreshold: 0.5 }`):
  - candidate WITH block: `certifyContent(proof, {blockId, rev, actionId}, block, ...)` — one
    call resolves both verdicts. `ok` → rev-certified + content-certified.
    `digest-mismatch` → rev-certified TRUE (the claim half passed; the (rev, actionId) is
    genuinely certified), content candidate DROPPED from the content quorum, serving peer
    penalized (`InvalidRestoration`, context `reconcile:<blockId>`), and the pass continues to
    the next holder rather than failing the whole repair. `no-digest-declared` → rev-certified,
    content uncertified, no penalty. Other failures → nothing certified; penalize only
    attributable reasons per `NON_ATTRIBUTABLE_PROOF_FAILURES`.
  - candidate WITHOUT block: `certifyClaim` → rev-certified flag; same penalty rule.
- Feed `certified` into the `RevClaim`s and `BlockHashCandidate`s; on a selection decline check
  `certifiedEquivocation` and log it distinctly (mirror the read path's line).
- Cohort cost note: verification is bounded by `MAX_PROOF_SIGNERS` (the helper's cap) × cohort
  width — fine.

## Persist the VERIFIED proof where repair lands a revision

`BlockStorage.saveRestored` (:471) carries a NOTE (:459-470) saying it deliberately drops
proofs because nothing had verified them. Once reconcile verifies content against the proof
(`verifyBlockCommitProofContent` — the digest check binds proof to these exact bytes),
persisting is what stops certification decaying across repair hops. Settled design:

- `StorageRepo.saveReplicatedBlock` (:874) gains optional 4th param
  `verifiedProof?: BlockCommitProof` → `BlockStorage.saveReplica(block, source, proof?)` →
  `saveForwardRevision` includes `...(proof ? { proof } : {})` in the revision body →
  `saveRestored` persists `data.proof` via `saveBlockProof` when an entry carries one.
  Optional param keeps `IBlockReplicaStore` (`cluster/block-transfer-service.ts:94`) and the
  push path compile-compatible; the push path still passes none (`require-proof-on-block-push`
  owns that — keep the :869-872 doc pointing there, updated for the new param).
- REPLACE the `saveRestored` NOTE with the new contract: an archive entry's proof IS persisted;
  callers must strip any proof they have not verified. Enforce that at the one unverified
  entry: `BlockStorage.restoreBlock` (:454) returns archives straight from the remote
  `RestoreCallback` (RestorationCoordinator fetches from peers, verifies nothing) — strip
  `proof` off every revision entry there, with a NOTE naming why.
- In `createReconcileBlock`, after `selectQuorumBlock` agrees: if any content-certified
  candidate's hash equals `agreed.hash`, pass its proof to `saveReplicatedBlock`. A
  corroboration-won block with no certified carrier persists no proof (today's behavior).
- The monotonic-skip path in `saveForwardRevision` (:296) returns before persisting — an
  already-held revision keeps whatever proof state it had; acceptable, note it.

## Docs — state the win honestly

- `docs/internals.md`, **On the repair wires** subsection: it states today's "nothing decides
  with a proof" position and the repaired-replica asymmetry — rewrite both for the certified
  short-circuit and the persist-after-verify rule.
- `docs/correctness.md`, **Theorem 14**: same update. State plainly: the immediate, complete win
  is AVAILABILITY (one holder's verified proof replaces N reachable corroborators). Resistance
  to manufactured agreement improves from "any two ids answering now" to "a super-majority of
  the committing cohort's keys, checkable offline" and completes only when
  `feat-cluster-membership-threshold-cert-anchoring` lands — layer 1 proves the signers signed,
  not that they are the block's legitimate cohort.
