# Back-fill a verified commit proof onto an already-held revision

Continuation of `require-proof-on-block-push`, which landed everything else. That ticket's
"`saveReplicatedBlock` monotonic no-op" edge case asked whether an accepted-but-already-held
revision should back-fill a missing local proof, and preferred yes. It was not implemented; this
ticket is that arm, plus two test-fidelity arms it created.

## Arm 1 — the back-fill itself (the reason this ticket exists)

`BlockStorage.saveForwardRevision` (`block-storage.ts`, the `logLabel:skip` guard) returns before
persisting anything when an equal-or-newer revision is already held. So a **certified** push for a
revision this node already holds proof-lessly is accepted and reported non-missing, but the
verified proof is silently dropped. The node stays a corroboration-only holder for that revision
even though a valid proof for it just arrived — exactly the decay the certified-push work exists to
stop.

### Where it belongs — and the trap

Do **not** persist it inside `saveForwardRevision`'s guard. The proof was verified against the
**pushed bytes**; back-filling attaches it to this node's **held** materialization, and a diverged
holder's bytes at the same `(rev, actionId)` may differ. Storing a proof whose declared digest does
not match local content means later serving content that contradicts its own proof — and
`digest-mismatch` is classified **attributable** in `certified-claims.ts`, so this node would be
penalized by every receiver.

The retention rule that already handles exactly this is
`StorageRepo.persistProofIfContentMatches` ("persist only when the local materialization matches the
digest the commit op declared"), reached today via `StorageRepo.backFillProof` from the two
commit-path landing sites that skip `internalCommit`. Route the replica path through the same rule:

- In `StorageRepo.saveReplicatedBlock`, `advanced` is already computed (`priorLatest === undefined
  || effective.rev > priorLatest.rev`). When it is **false** and a `verifiedProof` was supplied and
  `effective` equals the caller's `source` on **both** `rev` and `actionId`, back-fill.
- Generalize `backFillProof` to take `(blockId, storage, rev, actionId, proof)` rather than a
  `CommitRequest`; its two existing callers pass `request.rev, request.actionId`. It already
  short-circuits when a proof is present (strictly additive) and treats an unmaterializable
  `getBlock` as "no local content", i.e. withhold.
- It runs under the block commit latch `saveReplicatedBlock` already holds — same as the commit-path
  callers, so no new latch interaction.
- Never throws: the revision is already durable, so a proof-persist fault must not turn a no-op
  into a failure. `persistProofIfContentMatches` already has this discipline.

Deliberately **not** back-filling when the held revision is *newer* than the pushed one: the proof
would be keyed to a revision `servableProof` will never serve (it only serves the proof for
`latest.rev`), for content this node may not even materialize.

### Stale statements to correct when it lands

- The `NOTE:` in `saveForwardRevision`'s monotonic guard says a certified re-heal of a held rev does
  not back-fill, and names itself as the site to change. After this it should point at the
  `StorageRepo` site and explain why the digest-match rule lives there.
- `block-storage.spec.ts`, test `'monotonic-skip: a certified re-heal of a held revision does NOT
  backfill its proof'`, pins the old claim. Its proof is a `{ v: 1 }` cast literal, which declares
  no digest — so it will still pass for a *different* reason (`commit:proof-undeclared`). Retitle it
  to the narrower true claim and add positive coverage with a real signed proof.
- Positive coverage belongs in `block-transfer-push-persist.spec.ts`, which already builds real
  signed proofs: land a revision proof-lessly, then push the same revision certified, and assert
  `getBlockProof` now returns the proof and `latest` is unchanged.

## Arm 2 — two specs downgraded to the migration flag

`require-proof-on-block-push` made `requirePushCertificate: true` the default. Two specs push
uncertified content and were set to `requirePushCertificate: false` to keep passing, which means
neither now exercises the production posture:

- `cohort-growth-heals-single-holder.spec.ts` — its `writeRevision` commits with no `blockDigests`
  and no proof, so `sourceBlockCertification` finds nothing to attach. Upgrading `writeRevision` to
  a certified commit (the `landRevision` pattern in `block-archive-proof.spec.ts`: declare the
  block's `canonicalBlockHash` in `blockDigests`, build a `makeSignedProof` cohort record, pass it
  as `commit`'s third argument) would make this spec exercise certified push end to end — a real
  gain, since it drives the whole producer→wire→receiver chain with real repos.
- `block-transfer-roundtrip.spec.ts` — this one pins the stream path (handler wiring, framing,
  deadlines), not certification. Leaving it on the flag is defensible; decide explicitly rather than
  by inertia.

## Arm 3 — no producer-side test

`sourceBlockCertification` has no direct coverage. It is the function that guarantees a proof is
never paired with metadata for a different revision, and it has four distinct outcomes worth
pinning: no `latest` → `{}`; a pinned read (`materializedRev !== latest.rev`) → `{}`; meta with no
retained proof → meta only; meta plus a retained proof → both. A mis-paired stored proof must yield
meta only (`servableProof` rejects it via `proofClaimsCommit`).
