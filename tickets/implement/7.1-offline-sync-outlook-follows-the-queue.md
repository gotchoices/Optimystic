Second half of stage 7 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). Ticket `offline-sync-outlook-from-guards` computes each entry's `CommitOutlook` once, when the queue first reports it `queued`: the own judgement (exposures, each with the collection it came from) frozen, plus `dependsOn` and `kind` as of that moment. This ticket keeps `dependsOn` and `kind` current, delivers `outlook-changed`, and logs and counts an assured entry that fails.

## Decisions settled here

**What is recomputed, and when.** After the controller (`OfflineMode.onQueueStatus` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`) has delivered a status that changes the set of unsettled entries or what they hold — `committed`, `failed`, `partially-committed`, or the first `queued` of an entry the restore put back ahead of others — run one pass over `OfflineQueue.entries()` in queue order. For each entry: drop from its frozen exposures those whose collection the entry has already committed (`committedCollections`: those guards can no longer be refused); recompute `dependsOn` with the same dependency rule the first ticket uses, against the entries before it as they are now and the deferred records; derive `kind` from its exposures and its dependencies' kinds as computed earlier in this same pass. Build the written-key index incrementally as the pass walks forward, so a pass is linear in the queue's actions. The own judgement is never redone.

**`outlook-changed` is delivered when `kind` changes, not on every `dependsOn` change.** Status shape `{ kind: 'outlook-changed'; transactionId: string; outlook: CommitOutlook }`, added to `QueuedTransactionStatus`, delivered to `onStatus` listeners after the status that triggered the pass. The doc's promise is the `exposed → assured` transition; a dependency settling while the entry stays assured (or stays exposed) only narrows `dependsOn`, which `status()` and `entries()` report current without an event. Emitting on every narrowing would put an event into most multi-entry drains for no decision an application makes. The rule also keeps every existing offline spec's exact status-kind sequences valid: without tags almost every entry is exposed by its own guards, so its kind never flips.

**A transition the wrong way is reported, not suppressed.** A pass can make an assured entry exposed only if a dependency appeared after the entry was judged — a journaled transaction put back ahead of an entry committed before `hydrate`/`restore` ever read it (the host contract is restore first; deferred records are already counted). Deliver `outlook-changed` anyway and log `offline:outlook-regressed transaction=… dependsOn=…`. Never keep an outlook the pass says is false.

**`offline:assured-entry-failed`.** On a `failed` status, read the entry's outlook as it stood (before the record is dropped). Log `offline:assured-entry-failed transaction=… reason=… refusal=<class> table=… key=… causedBy=…` when the outlook was `assured`, the reason is `constraint` or `concurrent-modification`, and `causedBy` is absent or names a transaction that was not in its `dependsOn`. The guard that refused is the `TreeGuardRefusedError` in the status error's `cause` chain (the db-core refusal, before mapping), whose collection id and key name it; render the key through the collection's describer as the outlook does. Excluded, because the prediction never claimed them: `expired`, `discarded`, `rejected`, `too-large` (the size limit is a property of this write, not of other writers), and a cascade from a dependency listed in `dependsOn` (that dependency's own failure is what the log covers, if it was assured). Update the doc's "for a reason other than expiry, discard or validator rejection" to name `too-large` too.

**Counted as well as logged.** `OfflineModeState` gains `assuredFailures: number`, incremented with each log line — the same kind of signal as the db-core queue's `unclassifiedFailures`: zero in a correct deployment, and a rising count means a false `optimystic.fresh` / `optimystic.single_writer` hint or a defect in the analysis. Published through `onQueueState`.

**The suite-wide check.** "Every assured prediction in the offline-mode scenario suite that ends `failed` (other than expiry, discard, rejection) fails the test" is enforced through the counter, not per test. A small test module (for example `test/outlook-predictions.ts`) keeps the set of plugins the offline specs create (registered from `createMeshDbNode` in `mesh-node-harness.ts` and from each offline spec's own `register` helper) and declares a top-level `afterEach` — a mocha root hook once the module is loaded — asserting `plugin.offline.queueState().assuredFailures === 0` for each tracked plugin, then clearing the set. A test that fails an assured entry on purpose (the false-hint case) calls the module's `expectAssuredFailures(plugin, n)` to assert and untrack it. Wire every spec under `test/offline-*.spec.ts`.

## Edge cases & interactions

- **Exposed only through `dependsOn`, then the dependency commits** → one `outlook-changed` to `assured`. Build it with a `single_writer` table: entry A inserts a natural key (exposed), entry B updates that row (own judgement clean through the tag, depends on A). Open the gate; after A's `committed`, B gets `outlook-changed` with `kind: 'assured'` and empty `dependsOn`, before its own `submitting`. Test.
- **False fresh hint** → on a two-node mesh (the rival-primary-key shape of `offline-mode-removal.spec.ts`), a column tagged fresh but a rival commits the same key: the entry's `queued` outlook is `assured`, it fails with `constraint`, `assuredFailures` is 1, and the log line names the table and key. Test.
- **Assured dependency that is discarded or expires** → the dependent fails by cascade with `causedBy` in its `dependsOn`: no log, no count. By inspection (the rule's `causedBy` arm).
- **Partial commit** → exposures in the committed collections are dropped; when none remain and no dependency is exposed, `outlook-changed` to `assured`. By inspection.
- **An entry failing removes its dependents too** (the queue's cascade) → their records are dropped on their own `failed`; a pass after the cascade only sees the survivors. By inspection.
- **Restore puts an older transaction back ahead of a newer one** → the deferred-record dependency of the newer entry becomes key-level (narrowing, or disappearing when the restored entry wrote nothing it guards). By inspection.
- **Host committed before `hydrate`** → possible regression, reported as above. By inspection.
- **Listener throws during `outlook-changed`** → logged, the next listener still runs (the existing `notifyListeners` discipline). By inspection.
- **Exhaustive `switch` over `QueuedTransactionStatus.kind`** in the plugin and its tests (`translate`, `kindsOf` helpers, `whenSettled`) handle the new kind; `outlook-changed` is not terminal and never settles a waiter.
- **Cost**: one pass per settle, linear in the queued actions. Leave a `NOTE:` tripwire at the pass: draining N entries costs N passes, so a long drain is quadratic in the queue length (the same shape as the replay after every head commit, whose `NOTE:` names the remedy); if it shows up, recompute only the entries behind the settled one that list it.
