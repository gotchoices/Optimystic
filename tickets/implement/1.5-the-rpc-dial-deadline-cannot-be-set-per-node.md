# The RPC dial deadline cannot be set per node

## Problem

Sereus's gates take up to 2000 ms each to decide admission, and a cold relayed dial crosses up to two of them. Sereus wants to compute the totals itself and pass three values explicitly through `NodeOptions`:

- `connectionManager.addressDialTimeout` — already settable;
- `connectionManager.dialTimeout` — already settable;
- the deadline this package's own RPC clients (cluster, sync, dispute, block pushes, and — through `node.linkDeadlines` — a host's `RepoClient`/`NetworkTransactor`) give a dial. **Not settable.**

Confirmed by reading `NodeOptions` (`packages/db-p2p/src/libp2p-node-base.ts`): `LinkDeadlines.dialTimeoutMs` comes only from `resolveLinkDeadlines(options.linkRoundTripMs)`, called once at the top of `createLibp2pNodeBase`. Every client and push falls back to `linkDeadlines.dialTimeoutMs`; hosts read it off `node.linkDeadlines` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`, `packages/reference-peer/src/cli.ts`). The `linkRoundTripMs` doc says "a caller's own `dialTimeoutMs`" wins, but that only reaches code inside this package.

## Design (decided)

**New option: `NodeOptions.rpcDeadlines?: Partial<RpcDeadlineDefaults>`** — both halves of the existing `RpcDeadlineDefaults` type (`dialTimeoutMs`, `responseTimeoutMs`). The response deadline is included: sereus did not ask for it, but it is the other half of the same type every client takes, and leaving one half settable would be odd. Cost is one more validated field.

**Apply it inside `resolveLinkDeadlines`, not after it.** Signature becomes `resolveLinkDeadlines(linkRoundTripMs?: number, rpcDeadlines?: Partial<RpcDeadlineDefaults>)`. Two fields are derived from the dial deadline — `transferTimeoutMs = max(30000, dial)` and `transactionTimeoutMs = max(30000, 4 × dial)` — and they must follow an explicit dial, so the override replaces `dialTimeoutMs` before those two are computed. Applying it after `resolveLinkDeadlines` returns would leave both computed from the derived dial. Because hosts read `node.linkDeadlines`, an override reaches `NetworkTransactor`'s `dialTimeoutMs` and `timeoutMs` with no host change.

**Used exactly as given.** No floor, no derivation: `rpcDeadlines: { dialTimeoutMs: 1000 }` yields a 1000 ms dial even though the derived floor is 3000. The derived values that build on it (`transferTimeoutMs`, `transactionTimeoutMs`) keep their own floors.

**Validation, throwing at node construction** (same reason `validLinkRoundTripMs` gives — a silent fallback keeps the LAN deadlines on the one deployment that asked otherwise):

- each present field must be a finite number above 0 (so `0`, which `withRpcDeadlineDefaults` would read as "no cap", is rejected — no cap is not a node-level policy);
- `responseTimeoutMs` at most `MAX_TIMER_DELAY_MS` (2^31 − 1): it reaches one `setTimeout` directly (`ProtocolClient.processMessage`) and nothing is derived from it;
- `dialTimeoutMs` at most a new exported `MAX_RPC_DIAL_TIMEOUT_MS = Math.floor(MAX_TIMER_DELAY_MS / (TRANSACTION_DIALS + 1))` (≈ 429 million ms, about 5 days). Reason: the transaction budget is `4 × dial`, `RepoClient` arms a timer for what remains of the expiration that budget stamps, and a cluster member arms one 5 s past it. Mirroring `MAX_LINK_ROUND_TRIP_MS`'s "plus one of headroom": for any dial ≥ 5000, `4 × dial + 5000 ≤ 5 × dial ≤ 2^31 − 1`; below 5000 the sum is tiny. State that in the constant's doc comment.
- error message names the field: `rpcDeadlines.dialTimeoutMs must be a finite number of milliseconds above 0 and no greater than …; got …`. Factor one small validator shared with `validLinkRoundTripMs` if it stays readable (name + ceiling as parameters); otherwise two siblings.

**Precedence, highest first:** a caller's own per-request `dialTimeoutMs` / `responseTimeoutMs` → the explicit push fields (`spreadOnChurn.pushDialTimeoutMs` / `pushResponseTimeoutMs`, `underReplicationDrain.pushDialTimeoutMs` / `pushResponseTimeoutMs`) → `rpcDeadlines` → derived from `linkRoundTripMs`. The push fields already sit on top of `linkDeadlines.*` at their two sites in `createLibp2pNodeBase` (`spreadOnChurn` spreads `options.spreadOnChurn` over `linkDeadlines` values; the drain uses `pushDialTimeoutMs ?? linkDeadlines.dialTimeoutMs`), so they keep precedence with no code change there.

**Not enforced:** libp2p's `addressDialTimeout` caps every RPC dial per address, so an RPC dial set above it is cut off at that limit. Sereus sets all three; document the relationship (as the `connectionManager` doc already does for `dialTimeout` vs `addressDialTimeout`) rather than coupling them.

## Docs

- `NodeOptions.rpcDeadlines`: a doc comment saying what each field bounds, that the value is used as given (no floor), that it wins over `linkRoundTripMs` and loses to the `push*` fields and a caller's own per-request value, that `transferTimeoutMs` and the transaction budget follow it, that it should not exceed `connectionManager.addressDialTimeout` (which caps each address of an RPC dial), and what throws.
- `NodeOptions.linkRoundTripMs` doc: add `rpcDeadlines` to the "explicit per-deadline setting still wins" list.
- `NodeOptions.connectionManager` doc: its closing `NOTE:` says the RPC clients' deadlines are derived and "this option does not change" them — point it at `rpcDeadlines` as the way to set them.
- `packages/db-p2p/readme.md`, "Slow relayed links" section: add `rpcDeadlines: { dialTimeoutMs, responseTimeoutMs }` (typed `RpcDeadlineDefaults`) to the override list beside `connectionManager`; mention that transfer and transaction budgets follow an explicit dial; the sentence about application admission time ("add it on top through the explicit overrides below") should name the three overrides sereus uses.
- `packages/db-p2p/docs/cluster.md` "Declaring the link instead": update only if it lists the overrides.
- Export `MAX_RPC_DIAL_TIMEOUT_MS` from the package entry if `MAX_LINK_ROUND_TRIP_MS` is exported there (check `packages/db-p2p/src/index.ts`).

## Test

In `packages/db-p2p/test/link-deadlines.spec.ts` (one `describe` beside the existing one, no new file):

- an explicit `dialTimeoutMs` replaces the derived one exactly, below the derived floor too (e.g. `resolveLinkDeadlines(3000, { dialTimeoutMs: 1000 })` → dial 1000), and `transferTimeoutMs` / `transactionTimeoutMs` are computed from it (pick a value above their 30 s floors: dial 40 000 → transfer 40 000, transaction 160 000); every other field is unchanged from `resolveLinkDeadlines(3000)`;
- an explicit `responseTimeoutMs` replaces the derived one exactly;
- invalid values throw, for each field: `0`, `-1`, `NaN`, `Infinity`, and one above its ceiling;
- the dial ceiling itself is accepted and `transactionTimeoutMs + 5000` there fits a 32-bit timer.

No node-construction test: wiring is one argument at one call site.
