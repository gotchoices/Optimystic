GitHub #53. One of two costs that make an offline commit itself grow with the queue; the other is ticket `queuing-a-transaction-costs-the-same-at-any-queue-depth`. Only the two together flatten the curve.

## The cost

The live tracker holds every queued transaction's staged blocks plus the open one's, cumulatively. `Collection.snapshotPending` deep-copies all of it (`copyTransforms`) to capture a savepoint, and the Quereus bridge takes one per statement per collection the transaction has written (`TransactionBridge.createSavepoint`, `TransactionBridge.markDirty`): 15 per transaction in the report's shape.

Measured with `NODE=1 MODE=gated N=1000 node test/offline-commit-cost.bench.mjs`, run in `packages/quereus-plugin-optimystic`. The reachability gate stays closed, so nothing is sent and the queue only grows. Windows, Node 24, memory journal.

| per transaction, at depth 25 … 1000 | |
|---|---|
| whole commit | 4.3 ms … 33.6 ms |
| `structuredClone` time | 0.6 ms … 11.3 ms |
| `structuredClone` calls | 96 … 719 |

In a `MODE=gated N=200` run, `copyTransforms` under `Collection.snapshotPending` accounted for 18,904 of 32,819 clones and 261 of 332 ms of clone time (caller stacks taken with a preload wrapping `structuredClone`). A CPU profile of `MODE=gated N=800` puts about 36% of the run inside `Collection.snapshotPending`.

These snapshots are almost never restored. A successful commit reaches none of them.

## The design

Snapshots share the staged values, and the tracker copies a value before it first changes one it does not own.

- **`Tracker` keeps a set of ids** whose staged value (the inserted block, or the update list) only it references. `Tracker.stageUpdate` copies before changing a value not in that set: `structuredClone` of the inserted block, since `applyOperation` mutates it in place, and a plain array copy of the update list, since a staged operation is never changed after `ops.push(structuredClone(op))`. `Tracker.insert` adds the id, having already cloned. `Tracker.reset` clears the set, so a tracker never owns what it was handed.
- **A new `Tracker.shareTransforms()`** returns new outer maps over the same values, plus a copy of `deletes`, and clears the set. The maps must be new because `insert`, `update` and `delete` write to them. `Collection.snapshotPending` calls it in place of `copyTransforms`.
- **Restoring shares too.** `Collection.restorePending`'s verbatim arm resets to fresh outer maps over the snapshot's values (a small helper beside `copyTransforms`), so one snapshot can be restored twice, which a repeated `rollback to` does. `Collection.createReadTracker` takes the same helper: a read view does not write, and if one did it would copy first.

Cost after the change: one shallow copy of two maps per snapshot, proportional to the number of staged blocks rather than their size, plus one clone per block a statement touches, which is about what `Tracker.tryGet` already pays per read. Staged blocks are tree nodes shared by many rows, so their count grows far more slowly than the queue. Leave a `NOTE:` at `Tracker.shareTransforms` naming that residual, with the remedy (capture only what the open segment touched) if it ever shows in a profile.

Rejected: keeping the sealed segments in a tracker of their own under the open one, so a snapshot covers the open tracker alone. It is the stronger bound, but it adds a layer of memoizing and cloning on every read, and `Tree.readView` needs the sealed effects as of the capture anyway, while the drain changes them underneath. Rejected: capturing nothing and restoring by replay, since a failed statement would then pay a whole-queue replay and mint fresh block ids under an open transaction.

`copyTransforms` keeps its deep contract for its other callers (`stageAttempt` and `resumedAttempt` in `packages/db-core/src/collection/write-attempts.ts`, `TransactionCoordinator`, the invented baseline). Those transforms are small or the calls do not repeat per statement. Pitfall 1 in `docs/internals.md` ("Shallow Copy of Transforms") still holds for anything outside `Tracker`; add that this one sharing is safe because `Tracker` is the only mutator and copies first.

## Edge cases & interactions

- Change after snapshot, both shapes: stage into a block inserted before the capture, and append to an update list that existed before it. The snapshot must not change. Test, below.
- One snapshot restored twice, with staging between. Test, below.
- A read view built from a snapshot while the live tracker keeps staging and while the drain replaces its transforms. Verified by `packages/db-core/test/read-view-pinned.spec.ts` and `packages/quereus-plugin-optimystic/test/committed-read-interleave.spec.ts`.
- `Tracker.absorb`: `child.reset()` consumes the atomic's transforms, and `insert` and `stageUpdate` copy, so an atomic flush is unaffected. Inspection.
- `BasePins.copy` shares `PinnedBase` objects and `BasePins.markMoved` changes them in place. That is already true and this ticket does not worsen it. Inspection only; do not change it here.
- A snapshot taken during a head commit's network window (latch released): the shallow copy is synchronous, so it is one consistent state, as the deep copy was. Inspection.
- `Tree.readView` is the only `src` reader of `snapshot.transforms`; confirm with `find_references`. A spec that changes a snapshot's transforms and expects independence is asserting the old contract, so update it to what the code now promises rather than delete it.
- Session mode's coordinator snapshots (`captureUncaptured` in `packages/db-core/src/transaction/coordinator.ts`) go through the same method and gain the same saving. `packages/quereus-plugin-optimystic/test/session-mode-commit.spec.ts`.

## Test

One spec pinning the sharing contract above: staged values stay as captured under both change shapes, and restoring twice gives the captured state both times. The rest of this behaviour is pinned by `packages/quereus-plugin-optimystic/test/savepoint-rollback.spec.ts` and `packages/db-core/test/collection-segments.spec.ts`, which must keep passing unchanged.
