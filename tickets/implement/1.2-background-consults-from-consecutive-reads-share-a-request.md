# Background consults started by consecutive reads share one request per peer

Source: GitHub sereus#60 (cadre-core 1.22.0, Optimystic 1.27.0, Quereus 5.4.0; Node repro attached to the issue).

## The problem, measured

Two parties share a workspace whose app declares N tables; both hold every collection. One party restarts its database; the other counts the `/db-p2p/sync` requests (the protocol the cohort consult travels on) it serves:

| tables | requests served by the partner |
|---|---|
| 4 | 45 |
| 16 | 81 |
| 32 | 129 |
| 64 | 227 |

About 33 plus 3 per table, nearly all before the restarted database is writable. In the field (40 tables, two phones over a relay) each restart costs the partner ~105 requests in 5 s; on a Galaxy S7 that is ~7 s at ~90% CPU (~65 ms per request in Noise, yamux and request handling), paid once per workspace per start.

Cause: the restarting app reads each table once, serially. On a cohort member a read of a held block is served from the local copy and, when the lazy read-repair window has expired, starts one background consult behind it (`CoordinatorRepo.startHeldBlockConsult`, [docs/transactions.md §Lazy read-repair window](../../docs/transactions.md#lazy-read-repair-window)). After a restart no block has a window stamp, so every block's first read consults. The consults of ONE read share a `ConsultRound` (one request per peer), but a round is never shared across reads (doc comment on `CoordinatorRepo.openConsultRound`), so serial reads cost one request per peer each. On a restarted cohort member the log-tail floors that a collection open raises do not exceed the local copy, so these consults are all window-only — all background.

## Design

### A shared background round, closed by a short timer or by filling

A new class, `BackgroundConsultRounds` in `packages/db-p2p/src/repo/background-consult-rounds.ts`, owned by `CoordinatorRepo` (built only when the node has a batch callback, i.e. whenever `openConsultRound` would return a round, and the delay is above zero). It holds at most one OPEN `ConsultRound` that background passes from any read join:

```ts
export interface BackgroundConsultRoundsDeps {
	/** Builds a round exactly as `CoordinatorRepo.openConsultRound` does, with no read context. */
	open(): ConsultRound;
	/** How long the open round collects seats after its first seat joins. */
	delayMs: number;
	log: Logger;
}

export class BackgroundConsultRounds {
	/** The open round, opening one if none is open. Arms nothing: a round no seat joins costs nothing. */
	current(): ConsultRound;
	/**
	 * Join `round` (which must be the one `current()` just returned, in the same synchronous step).
	 * The first seat arms the close timer (`unrefTimer(setTimeout(..., delayMs))`); the seat that
	 * brings the round to MAX_CONSULT_BATCH_BLOCKS seats closes it at once and clears the timer.
	 * A closed round is never returned by `current()` again.
	 */
	join(round: ConsultRound, context: ActionContext | undefined): ConsultSeat;
}
```

On close (timer or full) it calls `round.close()` and logs `cluster-fetch:background-round` with `{ blocks, reason: 'timer' | 'full' }`. The round's existing barrier still applies after close: it sends once every joined seat has registered its questions or left. Each background pass is one block and `HeldBlockConsults` runs at most one pass per block, so a round's seat count is its block count and a full round is exactly one request per peer (`MAX_CONSULT_BATCH_BLOCKS` = 32 per request).

### The delay: 250 ms, always, configurable

New knob `readRepairCoalesceMs`, default **250**:

- On `ClusterConsensusConfig` in `packages/db-core/src/cluster/structs.ts` beside `readRepairQuietWindowMs`, with a doc comment.
- On `clusterPolicy` in `packages/db-p2p/src/cluster/cluster-policy.ts`, resolved by a new `resolveReadRepairCoalesceMs` (+ exported `DEFAULT_READ_REPAIR_COALESCE_MS = 250`) on the pattern of `resolveReadRepairQuietWindowMs`: `undefined` → default; a finite number in `[0, MAX_READ_REPAIR_WINDOW_MS]` → itself; anything else throws with a message naming `clusterPolicy.readRepairCoalesceMs`. Passed through `resolveClusterPolicy`, and the `CoordinatorRepo` constructor applies the same resolver to `cfg?.readRepairCoalesceMs`.
- **`0` means today's behaviour exactly**: no `BackgroundConsultRounds` is built and background passes join their read's own round as now. This is also the setting existing specs use where they pin per-read round shape.

The delay applies **always** (whenever it is above zero), not only during bursts. A leading-edge exemption (send the first consult after a quiet spell at once) would save 250 ms that no read waits on and cost one extra request per burst, and the steady state is the same shape as the restart: a host re-reading its tables every 15 s, past the 10 s window, starts one background consult per table in quick succession. One rule is simpler to reason about.

**Why 250 ms, and its trade.** Requests per burst are about `max(blocks / 32, burst duration / delay)`. A full round sends at once, so the delay matters only when blocks arrive slower than 32 per delay; 250 ms gathers a serial table-by-table read on a phone into a handful of rounds (e.g. a 40-table restart, ~120 blocks over 1–2 s, becomes roughly 4–8 requests instead of ~105). The cost is that each held block's consult concludes up to 250 ms later: the read that started it was already served from the local copy, so only the reads after it are affected, and the stated staleness bound — one `readRepairWindowMs` (10 000 ms) plus one consult — grows by `readRepairCoalesceMs`, 2.5% at the defaults. Raising it coalesces more for slow serial readers at that same cost; the per-request block limit caps what any delay can gain.

### What changes in `CoordinatorRepo`

- `startHeldBlockConsult`: when `backgroundRounds` exists, take `const round = this.backgroundRounds.current()`, call `heldBlockConsults.start(blockId, round, () => this.runHeldBlockConsult(..., this.backgroundRounds.join(round, context)))`, and ALWAYS ready the read's `reserved` seat (the quiet-span path's seat in the read's own round), since the pass no longer uses it. Without `backgroundRounds`, unchanged. The read's own round is still what the blocking passes use.
- `openConsultRound`: rewrite its doc comment (it is no longer "never shared across reads"); the read's round now carries only the read's blocking passes when coalescing is on.
- `HeldBlockConsults` needs no logic change: it counts slots per round, and a background round of ≤32 passes is one slot. Update its doc comments and the `MAX_HELD_BLOCK_CONSULT_SLOTS` NOTEs: with coalescing, 16 slots means up to 16 background rounds in flight, each one request per peer.
- Add an accepted-tradeoff `NOTE:` at `startHeldBlockConsult`: a read with one blocking and one background consult (e.g. a refresh after a refused write, whose tail read carries a floor while the header's window expired) now sends its background block in the shared round rather than its own, so when no other background consult is coalescing it costs two requests per peer instead of one. Rare on a cohort member; revisit if `cluster-fetch:background-round` lines with `blocks: 1` appear beside blocking consults of the same read.

### The context belongs to the question, not the round

A `ConsultRound` today takes one `ActionContext` for all its questions. A background round mixes reads of different collections, each with its own context, so:

- `ConsultRound.join(context?)` takes the seat's context; `ConsultRoundDeps.context` is removed. `PendingAsk` keeps the context of its first registrant. Every seat that asks about the same (peer, block) in one round shares a context: a read's round has the read's one context, and a background round holds one pass per block. Say so in `register`'s comment.
- The single-block callback (`askEachSingly`: self, and an older peer's unanswered blocks) uses each question's own context.
- `ConsultAsk` gains `context?: ActionContext`, and `ClusterLatestBatchCallback` drops its third parameter. Production's batch callback in `libp2p-node-base.ts` already ignores context (the sync request carries `rev: undefined`); the mesh harness's `clusterLatestBatchCallback` passes `ask.context` to `consultAnswerOf` instead of the round-wide one.
- `CoordinatorRepo.get` joins the read's round with `blockGets.context` (in `readRepairBlock` and the quiet-span reservation); `runHeldBlockConsult` via `backgroundRounds.join(round, context)`.

## What must not change (and how each is kept)

- **No read waits longer.** Only window-only background passes go to the shared round. A missing block (absence verdict), a floor above the held copy (`floorDemandsConsult`), `'paranoid'`, and the `awaitWindowConsults` test seam keep the read's round and barrier, which no longer even waits on background seats' cohort lookups.
- **What a consult establishes is unchanged.** The pass code (`runHeldBlockConsult` → `fetchBlockFromCluster`) is untouched; `held`, `floor`, `asker`, `context` and the pass sequence number are captured at the triggering read as now, so the window stamp, the unsettled-claim memo, `cohort-too-small` arming, repairs and their change events are judged against the copy that read loaded.
- **Bounds stay bounded.** At most one pass per block (`HeldBlockConsults.running`); at most 16 slots per peer, now counting background rounds.
- **Mixed versions.** A round never sends more than 32 blocks to a peer per request, so an older peer's single-request fallback (`ConsultRound.askEachSingly`) is at most 31 extra requests per round, and at most 16 rounds run — the same ceiling the `NOTE:` at `MAX_HELD_BLOCK_CONSULT_SLOTS` already describes. Update that NOTE to say coalescing concentrates the fallback into fewer, fuller rounds without raising the ceiling.

## Edge cases & interactions

- **A pass that does not start** (block already running, or slots full): `current()` returned a round no seat joins. It arms no timer and stays the open round for the next pass. Verified by inspection.
- **The timer fires before every seat is ready**: `close()` only marks the round closed; it sends when the last seat is ready. A seat whose cohort lookup is slow (`findCluster`'s bounded bootstrap wait) holds back the other background seats' requests, not any read; the per-peer deadline starts at send, so the wait never makes a peer read as silent. Note it in the class comment.
- **Full close**: the 32nd seat closes the round synchronously and clears its timer; the next `current()` opens a new round. Test below.
- **Quiet-span reservation**: `readRepairBlock` reserves a seat in the read's round before the `quietCohortStillVouches` await; when the pass then starts in the background round, `startHeldBlockConsult` readies that reserved seat whether or not the pass started. The background join happens after that await, which is fine — the background round is closed by its timer, not by `get`. By inspection.
- **Quiet-cohort snapshot**: `connectedCohortBeforeConsult` is taken before the delay. A member whose connection run changes during the delay makes the later comparison fail, so no span starts — the safe direction. By inspection; mention in the transactions.md paragraph.
- **Silent-consult holds**: measured from the consult's end, which is now up to the delay later. No change needed.
- **Timer lifetime**: `unrefTimer` (`packages/db-p2p/src/unref-timer.ts`) so an open round never keeps a process alive; `CoordinatorRepo` has no stop, and an open round at shutdown behaves like any in-flight pass (the `NOTE:` on `heldBlockConsults`).
- **Self**: still asked through the round's single-block callback, now with the pass's own context. The consult-round spec's self test checks the seat's context arrives.
- **`settleHeldBlockConsults`** now waits up to the delay as well; specs that call it with the default config take ~250 ms longer. Specs that only care about per-read rounds or slot counts set `readRepairCoalesceMs: 0`.
- **Duplicate block in one read**: already de-duplicated in `get`; in the background round, impossible by `HeldBlockConsults`.
