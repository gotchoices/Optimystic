This is the marker half of backlog ticket `1.1-dispute-validity-reject-marker`, moved forward because the offline-sync classification (`docs/offline-sync.md` §Classifying an attempt's outcome, the "Validity rejection" row) needs it first: the coordinator cannot tell a writer "a validator judged this invalid" without a signed, structured class on the reject vote, since reject reasons are free-form signed prose that must never become control flow. What stays in `1.1` — the engine-health hook and filtering the coordinator's `disputeEvidence` to marked rejects — now names this ticket as its prereq. Nothing here acts on the marker; `offline-sync-typed-validity-rejection` is the first consumer.

## Why a positive marker on validity, and not a marker on stale

Today every member refusal that is not an expiry or a `held` is the same `reject` vote with prose (`invalidVerdict` / `verdictOf` / `voteFor` in `packages/db-p2p/src/cluster/cluster-repo.ts`): a stale revision, a membership-admission refusal, a content-digest disagreement, a checker crash and an operations-hash mismatch look identical to the coordinator. Two reasons to mark validity positively rather than marking the transient kinds:

- **Fail-safe across versions.** A member on an older build sends no marker. Absent must therefore mean "not known to be a validity judgement", so an old member's stale-revision reject is never mistaken for a permanent refusal. The writer then treats it as unclassified (retried), never as final.
- **Rarity.** No composition root configures a transaction checker today (backlog `feat-no-deployment-validates-transactions-at-pend`), so validity votes are rare, and the new signing encoding — which an older verifier cannot check — appears on almost no traffic. Stale-revision votes, the common reject, keep their encoding byte-identical.

## Classification (from the design of record, `docs/right-is-right.md` §Which rejections are disputes)

| Refusal | Class | Marked? |
|---|---|---|
| `Re-execution failed`, `Operations hash mismatch`, `Tampered transaction stamp`, `Missing client signature`, `Invalid client signature` (`TransactionValidator`) | validity | yes — with the operations hash the member computed when it has one |
| `Stale read`, stale revision / stale commit, pending-conflict, slot hold | transient | no |
| `Transaction expired` (validator) and the member's own expiry verdict | clock | no |
| `Unknown engine`, `Schema mismatch`, `Unsupported operations-hash format`, `PEND_NOT_VALIDATABLE`, `VALIDATOR_FAULT`, membership-admission refusals, `BASE_DECLARATION_DISAGREES`, `CONTENT_DIGEST_MISMATCH`, unavailable-block refusals | incapacity / structure | no |

## Shape

- `PendValidationResult` (`packages/db-core/src/network/struct.ts`) gains a structured class on failure: `{ valid: false; reason?: string; validity?: { computedHash?: string } }`, present only for the validity class. `TransactionValidator` (`packages/db-core/src/transaction/validator.ts`) sets it on exactly the five refusals above (`computedHash` on the operations-hash mismatch; absent when re-execution failed outright). `checkPendValidation` (`packages/db-p2p/src/pend-validation.ts`) never sets it for its own two refusals (both incapacity) and passes a checker's `validity` through untouched.
- `PromiseVerdict`'s `'invalid'` arm carries the same optional `validity`; `voteFor` copies it onto the reject vote. The pend-validation branch of `ClusterMember.validatePendOperations` is the only site that produces it; every other `invalidVerdict` call stays unmarked.
- `Signature`'s reject variant (`packages/db-core/src/cluster/structs.ts`) gains `validity?: { computedHash?: string }`, folded into `clusterVoteSigningPayload` as its own encoding, `reject-invalid:<json [computedHash ?? null, rejectReason ?? null]>`, exactly as `expiredAt` is encoded `reject-expired:`. A vote cannot be both an expiry vote and a validity vote: make that unrepresentable by splitting the reject variant in the type, not by a runtime check. A vote with neither field encodes byte-identically to today. Update the `clusterVoteSigningPayload` doc comment's unambiguity argument for the third tag.
- Counting is unchanged everywhere (`rejectionCount`, thresholds, `ValidatorRejectionError`): a marked reject is still a reject.

## Edge cases & interactions

- **Tampering.** Adding, removing, or changing `validity` on a signed vote must fail `ClusterMember.verifySignature`. Test (below).
- **Old encodings.** A vote without the field verifies exactly as before. By inspection: the payload function's unmarked branch is untouched.
- **Old verifiers.** A member on an older build verifying a new marked vote builds the old preimage, fails the signature, and reports `InvalidSignature` against an honest member — the same mixed-version cost the expiry vote's encoding accepted. Acceptable because marked votes are rare (above); state it in the handoff.
- **Expiry precedence.** The member's expiry verdict is decided before validation (`evaluatePromise`), so an expired record never reaches the validator; the validator's own `Transaction expired` refusal stays unmarked. By inspection.
- **StorageRepo tier.** `StorageRepo.pend` also runs `checkPendValidation`; this ticket leaves its answer unchanged (`offline-sync-typed-validity-rejection` turns a marked storage-tier refusal into the writer's typed failure).
- **Equivocation.** `detectEquivocation` compares vote *types*; a marked and an unmarked reject from one member for one record are the same type. A member signs once per record, so an honest member cannot produce both: treat a differing marker on a re-delivered reject as equivocation, and say so in a comment there.
- **Abandonment and race resolution** read only `type`; unaffected. By inspection.
- **The coordinator's dispute-marking branch** keeps building `disputeEvidence` from every reject; filtering it is left to `1.1`.
