# Blob pins follow SQL commits

Third of four parts of backlog `feat-sql-columns-hold-blob-references` (docs/blobs.md §Committing a reference, §SQL "Pins follow the transaction"). After `feat-blob-reference-trees-follow-sql-rows`, every statement stages its reference-tree entries and reports them through `BlobReferenceMaintainer`'s `onStaged` hook, which nothing sets yet. After `feat-a-held-blob-follows-its-cohort`, `announce` on a node copies a committed reference to its cohort and reports durability. This part connects the two for every commit that reaches the network or the queue: the references a transaction adds are pinned on the writer when its commit starts, announced (with the table's reference tree as scope) and unpinned once it lands, and unpinned if it is abandoned. Queued transactions settling, a restart's reconciliation and the `unstaged` holding period are the last part, `feat-sql-columns-hold-blob-references`.

The two-node end-to-end proof of the two-commit pattern is a separate ticket, `feat-a-blob-reaches-the-cohort-before-the-row-that-shows-it`, which has this one as its prereq.

## The rule for when the blob service is called

Nothing reached from `OptimysticVirtualTable.update` calls the blob service. A validating member re-executes the statements through `QuereusEngine.execute` (`packages/quereus-plugin-optimystic/src/transaction/quereus-engine.ts`) and has no bytes, so it must neither pin nor announce (docs/blobs.md §Registering references, "Members never check whether the bytes exist"). `update()` only records what it staged; the bridge pins at commit.

This departs from docs/blobs.md §SQL's "the first statement that stages the reference moves the pin to its transaction": the move happens when the commit starts instead. What that changes is limited to a transaction open longer than the `unstaged` holding period (24 hours), which the last part covers by never expiring an `unstaged` pin whose reference an open or queued transaction has staged.

**Replay guard.** New module `packages/quereus-plugin-optimystic/src/transaction/replay-scope.ts`:

```ts
/** Run `run` with `db` marked as re-executing a replicated transaction. Nested calls count. */
export function duringReplay<T>(db: Database, run: () => Promise<T>): Promise<T>;
export function isReplaying(db: Database): boolean;
```

A module-level `WeakMap<Database, number>` counter, incremented before `run()` and decremented in a `finally`. `QuereusEngine.execute` wraps its statement loop in it, inside the existing `try` so a re-execution that throws still decrements before the catch arm answers `{ success: false }`.

The one writer at a time Quereus's exec mutex guarantees per `Database` makes a counter per `Database` exact, and `QuereusEngine.execute` is only ever replay: the writer's session records statements with `session.execute(statement, [])`, and `TransactionSession.execute` (`packages/db-core/src/transaction/session.ts`) calls the engine only when it is given no actions. The two callers that do reach it are `TransactionValidator.validate` (`packages/db-core/src/transaction/validator.ts`) and `TransactionCoordinator.execute` (`packages/db-core/src/transaction/coordinator.ts`). `QuereusEngine.laneCeiling` needs no guard: it prepares without executing, so no `update()` runs.

## What a transaction records

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-reference-ledger.ts`, kept on the transaction like `writeFacts`:

```ts
export interface BlobReferenceRecord { readonly backendKey: string; readonly change: ReferenceChange }
export interface BlobPutRecord { readonly backendKey: string; readonly ref: BlobRef }
export interface BlobReferenceLedger {
	readonly records: BlobReferenceRecord[];
	readonly puts: BlobPutRecord[];
	/** records.length at each open legacy savepoint, by depth. */
	readonly marks: Map<number, number>;
}
export function emptyBlobReferenceLedger(): BlobReferenceLedger;
/** The (backend, reference, scope) triples the transaction leaves added, each once. */
export function addedReferences(ledger: BlobReferenceLedger): { backendKey: string; ref: BlobRef; scope: BlobScope }[];
/** The transaction's puts, deduplicated by (backend, reference). */
export function putReferences(ledger: BlobReferenceLedger): BlobPutRecord[];
```

`TransactionState.blobReferences: BlobReferenceLedger` (`packages/quereus-plugin-optimystic/src/types.ts`, imported `import type` as `TransactionWriteFacts` already is, so no runtime cycle), initialized in `TransactionBridge.beginTransaction` and in `transactorOnlyState` (`optimystic-module.ts`) exactly where `emptyWriteFacts()` is.

**`addedReferences` is the whole of the fold, and its key is the referrer, not the reference.** Fold `records` in order into a map keyed by `(backendKey, scope, referrer)`, each entry the last change seen for that key; then take the `add`s and deduplicate them by `(backendKey, ref, scope)`. A referrer is one row's one column (`blobReferrer` in `packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts`), which holds at most one reference at a time, so "last change at this referrer" is exactly what the reference tree will hold after the commit:

- an insert then a delete of one row adds nothing, and nothing is pinned;
- an update from `r1` to `r2` at one row stages remove `r1`, add `r2` (the maintainer always stages removes before adds within a call), so only `r2` is added;
- a reference merely *removed* from a row committed earlier is not an add and is never pinned;
- a primary-key move stages the remove under the old referrer and the add under the new one, so the reference stays added;
- two rows, or two tables, adding one reference are two referrers: one scope deduplicates to one triple and one pin, two scopes stay two.

**Recording.** `OptimysticVirtualTable.buildBlobReferences` passes the maintainer an `onStaged`:

```ts
changes => { if (!isReplaying(this.db)) this.txnBridge.noteBlobReferences(this.blobBackendKey, changes); }
```

`blobBackendKey` is the table's transactor key, read synchronously from a new public `CollectionFactory.transactorKeyOf(options)` (the existing private `getTransactorKey`, exposed; it is a pure function of `transactor` and `keyNetwork`). `withColumns` must carry the hook through, as it already does.

`TransactionBridge.noteBlobReferences(backendKey, changes)` appends one record per change to the open transaction's ledger; a no-op with no active transaction or an empty list, as `noteWriteFacts` is.

`SqlBlobService.put` records its put. Today it defaults the pin owner through `defaultPinOwner()`; change that to answer both the label and, when the label names a transaction, that transaction's `stampId`. After the put resolves, call `TransactionBridge.noteBlobPut(backend.key, result.ref)` only when the label was defaulted to a transaction put label **and** the bridge's current transaction is still that same active `stampId`. A put that outlives its transaction, and a put the host gave an explicit `owner` for, record nothing: the first leaves a stray `sql/<stampId>/put` pin that the last part's reconciliation removes, and the second is the host's own pin to release. Say both in the method's doc comment.

**Savepoints.** `createSavepoint` records `marks.set(depth, records.length)` and `rollbackToSavepoint` truncates `records` to that mark, **only in legacy mode** — where the bridge also restores the trees, i.e. after the early `if (this.session) return` / absent-snapshots return. `releaseSavepoint` drops the marks at and above the depth. This is deliberately *not* `writeFacts`' placement, which truncates in session mode too: in session mode a statement savepoint rollback does not restore the trees (the documented gap, `debt-optimystic-session-mode-statement-savepoint-gap`), so truncating the ledger there would leave a reference that *will* commit unpinned and unannounced. What is recorded follows what will commit. One comment at the site saying exactly that, since the asymmetry with the facts marks beside it will otherwise read as an oversight.

`puts` are never truncated: a savepoint does not undo a put.

## The pins

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pins.ts`, one instance per plugin registration, built in `register` and attached with `TransactionBridge.attachBlobPins(pins)` (set once, as `attachOfflineMode` is; absent on a bridge built bare, which every spec that constructs `new TransactionBridge(factory)` relies on). Log namespace `optimystic:quereus-plugin:blob`.

```ts
export interface HeldReference { readonly backend: BlobBackend; readonly ref: BlobRef; readonly scope: BlobScope; readonly label: string }
export interface HeldPins { readonly transactionId: string; readonly references: readonly HeldReference[] }

export class SqlBlobPins {
	constructor(deps: {
		/** CollectionFactory.blobBackendForKey: the backend of a transactor key the factory has seen. */
		backendByKey(key: string): Promise<BlobBackend>;
		registration: BlobScopeRegistration;
	});
	/** Pin every added reference under its transaction label. All or nothing: on a throw, unpins what it pinned and rethrows. `undefined` when the ledger adds nothing. */
	holdForCommit(transaction: TransactionState): Promise<HeldPins | undefined>;
	/** The commit landed for `committed` scopes ('all', or the collection ids a partial commit names). Never throws. */
	committed(held: HeldPins | undefined, transaction: TransactionState, committed: 'all' | ReadonlySet<string>): Promise<void>;
	/** The transaction was sealed into the offline queue. Never throws. */
	queued(held: HeldPins | undefined, transaction: TransactionState): Promise<void>;
	/** Nothing of the transaction is durable or queued. Never throws. */
	abandoned(held: HeldPins | undefined, transaction: TransactionState): Promise<void>;
}
```

Every settling arm takes the transaction as well as the held pins, and reads the transaction's puts from `putReferences(transaction.blobReferences)` rather than from `HeldPins`: that is one source of truth for the puts, and it is what lets the arms run for a commit whose `holdForCommit` never completed.

- **`holdForCommit`.** For each triple of `addedReferences`, resolve the backend and `backend.service.pin(ref, transactionReferencePinLabel(transaction.stampId, scope))`. Every reference is pinned whether or not this machine holds its bytes: a reference copied from another row commits and reads as not held, and announcing it still tells its cohort where to look. A pin's record write failing fails the commit before anything is sent — the bridge then runs its ordinary failed-commit path, and the `abandoned` that follows finds nothing pinned under a reference label because this unpinned what it had taken. Logs `blob:pin-held transaction=… refs=… ` once.
- **`committed`.** For each held reference whose scope is committed: `registration.ensure(backend, scope)` (`BlobBackend extends NetworkBinding`, so the backend is the network), and when it answers `registered`, `service.announce(ref, scope)` and then `service.unpin(ref, label)`. When `ensure` answers `registered: false`, or `announce` throws, log `blob:pin-kept transaction=… ref=… scope=… reason=…` and **keep** the pin: the bytes stay and the last part retries. A held reference whose scope is *not* committed (a partial commit's other half) keeps its pin for the same retry, which finds it certainly unlisted and unpins it; log it with `reason=scope-not-committed`.

  Then, for each reference with at least one committed scope, unpin every `unstaged` pin it holds on that backend (`pinsOf`, filtered through `parsePinLabel` for `kind === 'unstaged'`). Last, unpin the transaction's `put` pins (`transactionPutPinLabel`, one label, each put's reference): a referenced blob is held by its reference pin or its `owed` hold, and an unreferenced one was put inside a transaction that did not keep it.
- **`queued`.** The reference pins stay, to be settled with the queued transaction. The transaction's `put` pins are dropped as `committed` drops them. The `unstaged` pins are **kept** — see *One rule, one exception* below.
- **`abandoned`.** Unpin every held reference pin and every `put` pin of the transaction. `unstaged` pins are left alone: the application put those bytes outside the transaction and may retry the insert; the holding period bounds them.
- **Ordering inside one call** is announce before unpin, so no instant leaves a committed reference with no hold on the writer. Calls are awaited in sequence; a release of tens of references costs tens of local record writes.
- **Nothing in a settling arm throws.** Each reference is handled in its own `try`; a failure is logged (`blob:pin-kept` for a kept reference pin, `blob:pin-release-failed` for an unpin that threw) and the next reference still runs. The write is durable or queued by the time these run, so a failure here must not turn a successful commit into a failed one.

**One rule, one exception on the `unstaged` pins.** Only `committed` drops them. `queued` and `abandoned` keep them, for the same reason: a reference pin can still be released without its row ever landing — a queued entry that later fails is settled by the last part with whatever it committed, possibly nothing — and the `unstaged` pin is the application's own hold on bytes it put outside any transaction, so dropping it would lose bytes an immediate rollback would have kept. This fails toward keeping bytes, which is the bias docs/blobs.md takes throughout. The cost is that an `unstaged` pin can outlive its 24-hour holding period while an entry waits in the queue; the last part's expiry pass must therefore not expire an `unstaged` pin whose reference carries a reference pin of a live transaction (it already defines `isLive` over queued transactions, and the reference pin's own label carries the `stampId`). Carried into that ticket's handoff below.

**A put inside a transaction that the transaction never references loses its bytes when the transaction ends.** `begin; put(a); put(b); insert … values (a); commit` releases `b`'s pin and the sweep takes its pieces. That is the design — a put inside a transaction is pinned under that transaction's identity (docs/blobs.md §SQL) — but it is a footgun, so state it in the README and in `SqlBlobService.put`'s doc comment: put outside any transaction, or pass an explicit `owner`, to keep a blob no row references.

## The factory's part

`CollectionFactory` gains two things:

```ts
/** The transactor key of `options`, `${transactor}:${keyNetwork}` — what a BlobBackend is keyed by. */
transactorKeyOf(options: ParsedOptimysticOptions): string;
/** The blob backend of a transactor key this factory has already seen options for. */
async blobBackendForKey(key: string): Promise<BlobBackend>;
```

and one private `Map<string, ParsedOptimysticOptions>` written in `getOrCreateTransactor`, at the top, before the cache check, **first options per key winning** — exactly as the transactor itself and `getBlobBackend` are first-wins, and so that a transactor a host pre-registered with `registerTransactor(key, …)` still gets its options remembered when a table resolves through it. Every table's own key is registered this way: `resolveTreeArgs` resolves the table's own options on each open path. `blobBackendForKey` looks the options up and delegates to `getBlobBackend`, so it shares the per-key de-duplication and the in-flight map; a key the factory has never seen throws, which is a programming error (a ledger record's key always comes from a table that opened). `clearCache()` and `dispose()` do **not** forget the options — they are inert configuration, and keeping them lets a later resolution rebuild the store the same way; say so beside the map. The last part adds `knownBlobBackends()` over the same map.

## The bridge's routes (`TransactionBridge` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts`)

`commitTransaction` calls `holdForCommit` inside its `try`, after the `staleDescriptions` check and immediately before the route branch, and keeps the result — pinning after the stale check so a transaction refused on a stale table description writes no pin records at all.

Settling goes through **one private method**, not seven call sites:

```ts
/** Settle the transaction's blob pins exactly once, however it ended. Never throws. */
private async settleBlobPins(transaction: TransactionState, settlement: 'queued' | 'abandoned' | { committed: 'all' | ReadonlySet<string> }): Promise<void>
```

It returns at once when no pins are attached or this transaction has already been settled (a flag beside `heldBlobPins`, both reset in `beginTransaction`), clears the held pins, and dispatches to the matching `SqlBlobPins` arm in its own `try`. The once-guard is what makes the two overlapping exits safe: `afterFailedCommit`'s ordinary arm reaches `rollbackTransaction`, which settles in its `finally`, so the same transaction is not settled twice.

| Exit | Settlement | Where |
|---|---|---|
| session or legacy route returns | `{ committed: 'all' }` | after `endTransaction()`, awaited before `reportCommitDurability` |
| `local` route, entry queued | `'queued'` | after `endTransaction()` |
| `behind-queue` route, entry queued | `'queued'` | before `awaitQueuedCommit` |
| a queue route that queued nothing (`sealIntoQueue` answered false) | `'abandoned'` | after `endTransaction()` |
| `afterFailedCommit`, `PartialCommitError` | `{ committed: new Set(error.persisted) }` | in that arm (the legacy sweep's labels are collection ids for a real tree — `treeLabel` answers `Tree.describe()`, which is `String(collection.id)`) |
| `afterFailedCommit`, `CoordinatorPartialCommitError` | `{ committed: new Set(error.committedCollections) }` | in that arm, after `endTransaction()` |
| `afterFailedCommit`, anything else | — | nothing: its `rollbackTransaction` settles |
| `rollbackTransaction` | `'abandoned'` | in the `finally`, after the restores |

The release is awaited before the commit returns, so when a host's `await db.exec(…)` resolves the announcement has been made and the reference's durability event has already reached every `plugin.blobs.onDurability` listener. That is what the two-commit pattern of docs/blobs.md §Committing a reference waits on.

**Session mode** pins before `commitSession`. A validator sharing the process records nothing, since its `update()` runs under `duringReplay`.

## Edge cases & interactions

- **A put outside a transaction, inserted later** (docs/blobs.md's own example): `unstaged` pin until the insert's commit lands, then a reference pin, announce, `owed` hold; the `unstaged` pin is gone. Test.
- **Rollback.** Reference pins never existed; `put` pins of the transaction go; `unstaged` pins stay. Test.
- **Savepoint rollback** (legacy mode): a reference only a rolled-back statement added is not pinned or announced; one also added before the savepoint is. Test. Quereus wraps every non-FAIL DML statement in a `__stmt_atomic` savepoint, so this is also what keeps an aborted statement's references out — same mechanism, no second test.
- **Refused commit** (a rival took the key; nothing durable): `abandoned`; the refused writer's `unstaged` pin stays, so its retry does not need to put the bytes again. Test, two handles over one storage (`packages/quereus-plugin-optimystic/test/shared-local-transactor.ts`).
- **Partial commit.** Announce only references whose reference tree committed; keep the rest pinned for the last part's reconciliation. Inspection (the routing table above).
- **Announce fails, or the scope cannot be confirmed registered.** Pin kept and logged; nothing announced into an unregistered tree. Inspection.
- **A node built without a blob copy drain.** `NodeBlobService.announce` throws ("this node was built without a blob copy drain") for every reference. The commit still succeeds and every pin is kept, by the `announce` throws arm above. Inspection — and the reason that arm cannot be allowed to escape into the commit.
- **Validation re-execution** touches no blob service. Assertion at the seam (`isReplaying` at the one recording site); test below.
- **A commit of a `blobref` table now resolves that network's blob backend.** For a `local`/`test`/`mesh-test` transactor that builds a `SingleMachineBlobService` over a memory piece store on the first such commit, and announcing a reference whose bytes are absent succeeds there (`owed` hold, durability `local`, `confirmed: 0`). The existing `blob-reference-tree.spec.ts` and `blobref-column.spec.ts` commit fabricated references, so they will start creating blob records; neither asserts their absence. Verify by running both specs.
- **Insert then delete in one transaction.** Nothing added, nothing pinned; the `unstaged` pin stays. Inspection of `addedReferences`.
- **Same reference in two tables, or two columns.** Two scopes, two reference pins, two announcements; two columns of one table share a scope, so one of each. Inspection of `addedReferences`.
- **A reference whose bytes are not here.** Pinned (creating a record) and announced; reads report it not held. Inspection.
- **Concurrency.** Settling runs inside `commitTransaction` or `rollbackTransaction` under Quereus's exec mutex, one transaction at a time per `Database`. Inspection.

## Tests

`packages/quereus-plugin-optimystic/test/blob-pins-online.spec.ts`, on a shared `local` transactor over one `MemoryRawStorage` with the plugin registered as `blob-reference-tree.spec.ts`'s `createDb` does (`types` and `functions` registered, which is what makes a `blobref` column resolve). The backend is a `SingleMachineBlobService`, so `announce` yields an `owed` hold and durability `local`. Read pins through `plugin.blobs.pinsOf` / `listPins` and `parsePinLabel`. Use real blobs — `plugin.blobs.put` of a few bytes — not fabricated references, so `stat` and the `owed` hold mean something.

- put outside a transaction, then `insert` in a later statement: after the statement the reference holds no `unstaged` pin and no `sql/…` pin, `stat` reports durability `local`, a durability listener subscribed before the insert received one event naming the reference, and the table's scope is in the registry.
- `begin`; put; insert; `rollback`: no pin of any kind remains on that reference. Put before `begin`; insert; `rollback`: only the `unstaged` pin remains.
- legacy mode: insert `r1`; `savepoint s`; insert `r2`; `rollback to s`; `commit`: `r1` is announced and unpinned, `r2` is not announced and keeps its `unstaged` pin.
- refused commit: two plugin handles over one storage insert the same primary key with different references; the loser's commit is refused; its reference keeps its `unstaged` pin and holds no `sql/…` pin.
- replay: a second `Database` with its own plugin instance over the same storage declares the same table, and its `QuereusEngine.execute` is handed a transaction whose one statement is the `blobref` insert (`createQuereusStatement`, as `blob-reference-tree.spec.ts` builds its engine). Afterwards that plugin's backend lists no pin (`listPins('sql')` and `listPins('sql-unstaged/')` both empty) and `stat(ref).locality` is `unknown`. Driving the engine directly rather than through `createQuereusValidator` is deliberate: the guard is in `execute`, and a validator would add a schema-hash and operations-hash dance that tests nothing here.

## Handoff to the last part

`feat-sql-columns-hold-blob-references` must not expire an `unstaged` pin whose reference carries a reference pin (`sql/<stampId>/ref/<scope>`) of a live transaction — open or queued — because `queued` and `abandoned` now leave those `unstaged` pins in place deliberately. Its `openReferences` dependency therefore widens from "the open transaction's ledger" to "any live transaction's references", which it can read straight off the pin labels.
