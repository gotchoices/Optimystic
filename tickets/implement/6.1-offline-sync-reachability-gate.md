Part 1 of stage 6 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). The plugin wiring and the two-machine scenario are ticket `offline-sync-cohort-reachability`; the hard write-time refusal is `offline-sync-solo-refusal`.

## What exists

- The port: `ICohortReachability.reachable(blockIds)` in `packages/db-core/src/offline/reachability.ts`, asked with each collection's header id and known log tail id (`gateBlockIds`). `OfflineQueueOptions.wakeOn` in `packages/db-core/src/offline/queue.ts` takes a `(wake) => unsubscribe` subscription.
- The key network already knows the three facts the rule needs: `findCluster` (the serving cohort, never admitting an `unknown` peer), `absentCohortMembers(key)` (remembered serving peers that belong in the cohort but FRET does not hold live near the key), and `awaitingBootstrapContact()` (a configured bootstrap peer not yet heard from, including one `isNetworkMember` refuses while it serves this network — `heardFromBootstrapPeer`).
- `identifyOnConnectionOpen` in `packages/db-p2p/src/network/identify-on-open.ts` runs identify on every connection and reports `started` / `settled` to ONE observer, today the `BootstrapContactTracker`, which ignores every peer but the bootstrap ones.
- `UnderReplicationDrain` listens to `connection:open` and `peer:identify` with a trailing debounce (`schedule`).

## The gap this ticket closes beyond the doc's rule

A node whose routing view is self-only only because a peer is mid-identify must read **unreachable**, not alone. Two ways that happens today:

- A peer never seen before connects: it is `unknown`, so `findCluster` leaves it out and `absentCohortMembers` does not name it (it is not remembered). The view reads alone.
- A remembered partner reconnects and a stream is negotiated before identify lands: libp2p merges that protocol into its peerStore list, the partial list reads `foreign` in `membershipOf`, and `rememberVerdict(false)` drops it from `rememberedServing`. Because FRET upserted it on `peer:connect` it is in the band, so `absentCohortMembers` (which only considers peers outside the band) does not name it either. The view reads alone.

The NOTE at `membershipOf` already names the remedy: "if a second such decision appears, have `identifyOnConnectionOpen` report for every peer rather than for bootstrap peers alone." This is that decision.

## Design

### Identify progress for every peer

`IdentifyProgress` in a new `packages/db-p2p/src/network/identify-progress.ts`: an `IdentifyObserver` that counts identify exchanges in flight, per peer and in total (`inFlight(): number`). A `started` always precedes its `settled`; a `settled` for a peer with nothing in flight is ignored (logged), never driven negative. Add a small combinator beside `identifyOnConnectionOpen` (`combineIdentifyObservers(...observers)`) so `createLibp2pNodeBase` installs `identifyOnConnectionOpen(node, combineIdentifyObservers(bootstrapContact, identifyProgress))` — both built before `start()`, as the tracker is now. Each observer call is isolated (a throw from one is logged and the other still runs).

Do NOT thread it into `Libp2pKeyPeerNetwork`: its constructor is at ten positional parameters and its own NOTE forbids an eleventh before the options-bag conversion. The gate below composes the key network and the progress counter instead.

### The gate

`KeyNetworkCohortReachability` in a new `packages/db-p2p/src/network/cohort-reachability.ts`, implementing `ICohortReachability`:

```ts
interface CohortReachabilityDeps {
	keyNetwork: Pick<IKeyNetwork, 'findCluster' | 'absentCohortMembers' | 'awaitingBootstrapContact'>;
	selfId: string;                       // PeerId.toString()
	identifying?: () => number;           // IdentifyProgress.inFlight; absent → 0
	events?: NetworkChangeEvents;         // addEventListener/removeEventListener for 'connection:open' and 'peer:identify'
	wakeDebounceMs?: number;              // default 500
}
```

`reachable(blockIds)` — distinct ids, each judged on its own, answering `true` only when every one is `reachable` or `alone` (the header and the log tail may resolve to different cohorts; both must pass):

1. `findCluster(routingKeyForBlock(id))`. A throw → unreachable (`lookup-failed`); the gate never throws.
2. The cohort names a member other than `selfId` → reachable.
3. The cohort is empty (this node serves nothing near the key, or the lookup found nobody) → unreachable (`no-cohort`): there is no one to commit with, self included.
4. Self-only. Unreachable when `absentCohortMembers(key)` is non-empty (`absent-members`), when `awaitingBootstrapContact()` (`awaiting-bootstrap`), or when `identifying() > 0` (`identifying`); otherwise alone, which counts as reachable — a node that knows of no one else is its whole cohort.

Log one line when the gate's answer for a call differs from its previous answer (`reachability:closed reason=… block=…` / `reachability:open`), not one per call — the queue asks on every re-check and a live read asks on every refresh.

`onChange(listener)`: the optional half of the port (below). The first listener subscribes to `connection:open` and `peer:identify` on `events`; each event restarts one trailing debounce timer (`unrefTimer`), and when it fires every listener is called, each isolated (a throw is logged). Returns an idempotent unsubscribe; the last unsubscribe removes the event listeners and clears the timer. `stop()` does the same for every listener (node teardown). Only reconnection-shaped events wake: a departure can only close the gate, which the queue's next re-check reads; nothing is lost by not waking on it.

The debounce mechanism is the drain's (`UnderReplicationDrain.schedule`), but the default is 500 ms, not the drain's 5 s: a drain pass pushes block copies, a wake costs one gate check. 500 ms coalesces `connection:open` with the `peer:identify` that follows it, after which FRET has classified the peer ("FRET upserts on `peer:connect` and classifies on `peer:identify`, both before the identify call returns" — the NOTE at `awaitingBootstrapContact`).

### The port

Add to `ICohortReachability` in `packages/db-core/src/offline/reachability.ts`:

```ts
/** Optionally call `listener` when reachability may have improved — a machine connected or was
 *  identified. A hint, not an answer: the listener asks `reachable` again. Returns an idempotent
 *  unsubscribe. Absent → nothing wakes the asker but its own timer. */
onChange?(listener: () => void): () => void;
```

`alwaysReachable` gets none. A `Tree`/`Diary` application binds the queue with `wakeOn: listener => gate.onChange!(listener)`; the plugin routes it through its controller (ticket `offline-sync-cohort-reachability`).

### On the node

`createLibp2pNodeBase` builds one gate over `keyNetwork`, `node.peerId.toString()`, `identifyProgress.inFlight` and `node` as the event source, outside every optional-subsystem gate (it needs only the key network), and stops it in the node's stop wrapper, registered right after construction (see the rollback rule in docs/internals.md *Cohort-Topic Origination Bridge*). Exposed as `cohortReachability` on `OptimysticNodeAttachments` (`packages/db-p2p/src/optimystic-node.ts`), typed as the class or a `NodeCohortReachability = ICohortReachability & Required<Pick<ICohortReachability, 'onChange'>>`, so the plugin reads it without a cast. `NodeOptions.cohortReachability?: { wakeDebounceMs?: number }`. Export the class and its deps type from the package barrel.

### In the mesh harness

The two-machine scenario (ticket `offline-sync-cohort-reachability`) builds this gate over a mesh node's own key network, so the per-node key network in `makeNodeKeyNetwork` (`packages/db-p2p/src/testing/mesh-harness.ts`) gains `absentCohortMembers(key)`: under `failures.partitionSides`, the members of the unpartitioned cohort that the side filter removed, never self — the mesh's analogue of "remembered serving, missing from the view". With no partition it answers `[]`. This changes what the solo short-circuit reports on a partitioned mesh (`WriteDurability.unconfirmed` names the far side, and the under-replication ledger records it), so run the whole db-p2p suite and adjust any partition spec that asserted an empty `unconfirmed`.

## Edge cases & interactions

- **Mid-identify, never-seen peer** → `identifying` → unreachable; `peer:identify` wakes the listeners and the next ask reads the settled view. Unit test.
- **Mid-identify, remembered partner with a partial list** → same `identifying` arm. Leave the `rememberVerdict(false)` demotion as is (it is corrected by identify's full list), but update the NOTE at `membershipOf`: the second decision has appeared, the gate covers the in-flight window, and what remains is an identify that **fails** (timeout, reset) on a same-network peer whose list stayed partial — that peer then reads `foreign`, sits in the band, and the gate reads alone. Tripwire NOTE: if a fork is ever traced to an `identify:failed` line, treat a band member whose latest identify failed as not-alone. By inspection.
- **One machine, no bootstrap peers** → self-only, nothing absent, nothing awaited, nothing identifying → alone → reachable. Unit test.
- **Bootstrap peer refused by `isNetworkMember` while it serves** → `awaitingBootstrapContact` stays true (existing `heardFromBootstrapPeer` rule) → unreachable. The double's `awaiting` case covers the gate's side; the key-network rule is already pinned.
- **Restart with persisted network state** → `rememberedServing` and FRET's table are restored; a restored partner reads `serves` and is in the cohort, so the gate answers reachable while the partner is in fact offline, until FRET's liveness drops it (then `absent-members`). Harmless: the submission runs on a two-member cohort, fails with a promise shortfall, and the queue waits — no lone commit is possible because the cohort is not solo. Record in docs/offline-sync.md §When to submit (ticket `offline-sync-cohort-reachability` edits that section; leave a NOTE at `reachable` here).
- **Partner departs, FRET grace** → same shape: FRET keeps a long-lived peer live for up to `maxDeadGraceMs` (5 min default), so the gate says reachable and the drain meets shortfalls with backoff. Tripwire NOTE at the "member other than self" arm: if drains are seen spinning on shortfalls during that grace, also require a live connection to that member.
- **Header and tail on different cohorts** → each judged; one unreachable closes the gate. Unit test.
- **`findCluster` waits** on `bootstrapContactImminent` (bounded by `bootstrapContactTimeoutMs`, closed for the process after the first expiry); the gate inherits that wait once. By inspection.
- **Lookup throws / empty cohort** → unreachable, logged, never thrown. Unit test.
- **Listener throws** → isolated, logged, other listeners still called. By inspection.
- **Node stop with listeners attached** → event listeners removed, timer cleared, later `onChange` subscribe still harmless. By inspection.
- **Concurrent `reachable` calls** → the gate holds no per-call state except the last-answer log flag. By inspection.

## Tests

One new spec, `packages/db-p2p/test/cohort-reachability.spec.ts`, over a key-network double and a stub event target — it pins the branching rule:

- other member → true; self-only with nothing → true; self-only with an absent member → false; awaiting bootstrap → false; identify in flight → false; empty cohort → false; `findCluster` throws → false; two blocks, one self-only with an absent member and one with a partner → false.
- `connection:open` then `peer:identify` inside the debounce → one listener call; after the last unsubscribe, events call nothing.

No test for `IdentifyProgress` on its own (two counters) or for the node attachment (wiring).
