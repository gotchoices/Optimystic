# A SQL commit learns when it becomes fully held

GitHub issue #26, gap 3. Measured by the reporter: with the other member offline, inserts commit in 5–12 ms at `local`; when it returns, every row reaches it within about 8 s — and nothing tells the app that its earlier commits are now held by both machines. Also gives sereus GH #44 a visible "not yet delivered" mark that clears.

## What the prereqs provide

- `a-sql-commit-reports-its-durability`: the bridge delivers a `SqlCommitDurability` (`transactionId`, `durability: TransactionDurability`, `tables`) for every SQL commit that wrote something.
- `a-write-names-the-blocks-it-committed`: each collection's `WriteDurability` in that report carries `blockRevs` — every block the commit saved, with its revision.
- `a-durability-answer-says-whose-ledger-owes-it`: each cohort answer below `full` carries `recordedBy`, the node whose ledger owes the missing copies and which alone will fire `BlockDurabilityReachedEvent` for them; and a later `full` commit that clears a ledger entry now fires the event too.

The event comes from the node's `StorageRepo` (`OptimysticNode.storageRepo`, an `IBlockDurabilityNotifier`), keyed by block and revision, never by action.

## Surface

`register(...)`'s returned object gains `onCommitFullyHeld(listener): () => void`, called with `{ transactionId: string }` once per followed commit when every block it saved is held by its whole cohort. Same listener discipline as `onCommitDurability` (throwing listener logged, others still run; synchronous; idempotent unsubscribe).

`SqlCommitDurability` gains `followed: boolean` — `true` exactly when `onCommitFullyHeld` will fire for this commit (or the commit is already fully held, see below). A host reads it to decide between "pending, will clear" and "pending, the plugin cannot tell you when" — the latter is the open backlog question `feat-a-host-can-ask-whether-an-earlier-commit-is-fully-held`.

## The follower

A small class in `durability-follower.ts`, owned by the bridge, with no SQL or libp2p knowledge — it takes reports and events and emits transaction ids, so its branching is testable on its own.

**Deciding whether a commit is followable** (`follow(report, selfPeerId)`):

- `overall` present and `isFullyDurable(overall)` → already fully held: `followed: true`, and it is never registered (no `onCommitFullyHeld` call either — the commit report already said saved; document that a host treats `isFullyDurable(overall)` as "saved now" and `onCommitFullyHeld` as "saved later").
- Otherwise followable only if ALL of:
  - `overall` is present (no collection with unknown holders);
  - no collection reports `torn` blocks (an abandoned block never heals by replication, so the commit can never become fully held);
  - every collection's report carries `blockRevs`;
  - every cohort answer below `full` — the scalar report and each `otherCohorts` entry, in every collection — has `recordedBy === selfPeerId`. A cohort answer at `full` needs no event. Anything else (another node's ledger, or no ledger at all) means the event will not arrive here.
  - no collection's report mixes a `full` cohort answer with a below-`full` one (scalar vs. `otherCohorts`). `blockRevs` does not say which cohort answered for which block, and a block whose cohort was `full` has no ledger entry and so never gets an event; registering it would strand the commit. In a group no bigger than one cohort — the reporter's case — every block of a collection shares one cohort, so this costs nothing there.
  - the node exposes an `IBlockDurabilityNotifier` (found through `CollectionFactory`: `node.storageRepo` for the `network` transactor when present; `local`, `test` and `mesh-test` transactors have no ledger and no drain, so their commits are never followable — they also never set `recordedBy`, so the rule above already excludes them; the explicit check guards a host-registered node built without attachments).
- Unfollowable → `followed: false`, nothing registered.

**Tracking**: per followed commit, the set of `(blockId, rev)` still owed — the `blockRevs` of each of its collections whose report is below `full` (a collection reported `full` is already held, so its blocks are not registered); and an index `blockId → commits waiting on it`.

**Covering**: an event `{ blockIds, rev }` covers a pending `(blockId, r)` when `blockId` matches and `rev >= r` (a later revision every member holds was built on the earlier one, so it supersedes it — the ledger's own "one entry per block, at the highest revision" rule). When a commit's set empties, drop it and fire `onCommitFullyHeld`. The bridge also feeds each of its own later commit reports through the same covering step for collections reported `full` (cheap, and immediate when the event would be redundant).

**The race the follower must close**: the ledger is written before the coordinator answers, but the answer still has to climb back through the transactor, the coordinator's other participants and the bridge before `follow` runs. If the partner reconnects in between, the drain can empty the entry and fire the event before the commit is registered, and the commit would wait forever. So the follower keeps a bounded record of recent events, `blockId → highest rev reached` (LRU, a few thousand entries), and `follow` drops any block that record already covers before registering. A `NOTE:` at the cap: an event evicted before its commit registers strands that commit; raise the cap if pending commits are ever seen stranded.

**Subscribing**: lazily, on the first followed commit per notifier; one subscription per notifier, kept until `plugin.dispose()` (extend `CollectionFactory.dispose` to release it). Memory: pending commits are bounded too (a node alone forever registers every write) — cap the count (e.g. 10 000), evicting oldest with a logged line naming the dropped transaction id; `NOTE:` tripwire at the cap.

**Restart**: the follower is in memory. Commits from before a restart are not followed, though the ledger survives and the events still fire for their blocks. Out of scope here; part of `feat-a-host-can-ask-whether-an-earlier-commit-is-fully-held`.

## Edge cases & interactions

- **Superseded write**: commit A writes X@5 (`local`), commit B writes X@7 (`local`); the ledger keeps X@7, the event fires once for X@7 and must cover both A and B. Unit test.
- **Event before registration** (the race above): event X@5 then `follow` of a commit at X@5 → fires immediately (or is reported already covered); event X@5 then `follow` of a commit at X@7 → stays pending. Unit test.
- **Event at a lower revision** than the pending one does not cover it. Unit test (same case as above).
- **Multi-collection commit** (a table and its index): fires only when both collections' blocks are covered. Unit test.
- **`recordedBy` of another node**, **torn**, **absent `overall`**, **absent `blockRevs`**, **a collection mixing `full` and below-`full` cohort answers** → `followed: false`. One table-driven unit test.
- **A later `full` commit through this bridge** covering an earlier pending block → covered without an event. Unit test, or fold into the superseded case.
- **Two commits waiting on one block** both cleared by one event. Covered by the superseded case.
- **Commit that throws** (`CoordinatorPartialCommitError`, `PartialCommitError`): never reported, never followed (the error carries the committed half's durability; following a partial commit is not offered). By inspection.
- **Listener throws**: logged, others run. By inspection — the same helper `onCommitDurability` uses.
- **Disposal with commits pending**: subscription released, pending set dropped, no further calls. By inspection.

## Tests

`packages/quereus-plugin-optimystic/test/durability-follower.spec.ts`, driving the follower directly with hand-built `SqlCommitDurability` reports and `BlockDurabilityReachedEvent`s (no transactor, no SQL — the follower is plugin-owned logic, so no mocking of a repository module is involved), covering the cases marked "Unit test" above. No end-to-end test over two real nodes in this ticket: the producer side is pinned by the db-p2p specs of the prereq, and a two-node SQL scenario would cost an integration-suite run per change; if one is wanted later, `packages/db-p2p/test/util/two-machine-lifecycle.ts` is the fixture to build on.
