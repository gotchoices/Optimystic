# The blob cache budget counts a partly held blob as nothing

A node keeps a byte budget over the blobs it holds only because it read them, and evicts the least recently read of them once they exceed it (`BlobCacheBudget` in `packages/db-p2p/src/blob/cache-budget.ts`). A blob's contribution to that total is the byte size written on its blob record. A blob the node holds only part of has no size written on its record, so it contributes **zero** — and because the budget's whole decision is "is the total over the limit", a cache made of such blobs is never found to be over the limit and nothing is ever evicted, however much disk the pieces take.

## Reproduced

A scratch spec over a real `LocalBlobService` on a `MemoryPieceStore`: a 300 KiB blob whose record holds `cached` alone with its `size` field removed, all three pieces present, enforced with the budget set to 0 bytes — the strictest setting there is. Observed `cachedBytes 0 evicted 0 piecesLeft 3`: nothing counted, nothing evicted, every piece still on disk. That matches the observation the fix ticket carried. The scratch spec was removed; the test to keep is described under *Tests* below.

## What makes the size absent

- **A read of part of a blob.** `FetchSession.finish` (`packages/db-p2p/src/blob/blob-fetch-session.ts`) writes `size` only when the request asked for no byte range, so a fetch started for a ranged read never writes one. `NodeBlobService.read` passes a read's `offset` and `length` straight into the fetch; nothing in this repository asks for a range yet, but the capability is public and `blocked/quereus-reads-and-writes-a-range-of-a-large-value` is about putting it to use.
- **A download that never finished.** The `cached` hold is taken before the first piece and nothing removes it, so a fetch that is cancelled, loses its peers or hits a failing link never reaches `finish`: the hold stays, the pieces it stored stay, and no size is ever written. `LocalBlobService.stat` writes a size back only when its census finds the blob whole, so nothing repairs it either.

## The fix: two arms at one cause

The cause is that an absent size is read as "zero bytes" when it actually means "this node cannot say what it is spending here". Both arms follow from fixing that reading.

**Arm 1 — the fetch writes the size as soon as it learns it, whether or not it is fetching the whole blob.** A fetch learns the blob's full size from the root list piece every time it plans (`Plan.listSize`), under the `cached` hold and before any piece beyond the root is transferred; `packages/db-core/src/blob/reader.ts` always carries `fileBytes` on a present list root, so the size is known on the first plan that finds the root here. Write it then, through a new door on `BlobFetchStore` beside `markWhole`:

```ts
/** Sets `size` on the existing record and the `whole` hint to false: the size of a blob this node holds only part of. Never creates a record; a failure is logged, not thrown. Not flushed. */
markPartial(ref: BlobRef, size: number): Promise<void>;
```

`LocalBlobService` already has what it needs — `correctRecord(ref, false, size)`. A fetch that got past `holdCached` found something missing, so `whole: false` is the honest hint; `finish` still sets it back to true for a whole fetch.

The size is written once per session, from the first plan that knows it. A blob whose root list piece never arrived holds nothing: the walk starts at the root, so until the root is here the only missing piece the plan can name is the root itself, and nothing else can have been stored.

**Arm 2 — the budget evicts a cache-only blob whose size it never learned, whatever the total.** Arm 1 closes every path that is reachable now, but it leaves a crash window (root piece stored, size not yet written) and it leaves the budget trusting another module for its own boundedness. So in `chooseEvictions`, a cache-only blob with no recorded size is evicted on its own account rather than counted: the node cannot bound what it is spending on it, so it does not keep it. Concretely:

- `CachedBlob.bytes` becomes `number | undefined` — `undefined` is "no size on the record", which today is conflated with a genuinely empty blob's `0`. `LocalBlobService.cachedBlobs` passes `record.size` through instead of `record.size ?? 0`.
- `chooseEvictions` evicts every unsized blob (each still skipped when `inUse` reports true), then runs today's least-recently-read walk over the sized ones until the total is within budget. Keep the pure signature and the deterministic order: unsized first, ordered among themselves as today (least recently read, ties by reference ascending), then the sized walk.
- `cachedBytes` stays the sum of the sized blobs. It under-counts, which is the direction the rest of this design refuses — so say in the comment why it is safe here: the blobs it leaves out are evicted in the same pass, so the under-count cannot leave storage unbounded.

With both arms, every blob the node keeps for reads alone either has a size the budget bounds, or is gone at the next enforcement. An in-flight fetch is never the casualty: `NodeBlobService.startSession` takes a use for every session it starts, from before the first piece until the session settles, and both the eviction choice and the write immediately before the hold removal ask `inUse`.

**Considered and left out:** having `stat` write back a size its census learned for a partly held blob. Nothing stats a cache-only blob as a matter of course, so it would repair nothing arm 1 has not already written, and it would add a write to a read path.

## A partly held blob counts at its full size

That is the deliberate choice, and it needs to be written down where the counting happens. It over-counts — the node may hold one piece of the blob and count all of it — which is the direction `docs/blobs.md` §Lifetime already accepts for pieces shared between blobs: it evicts sooner, so it uses less storage. The accurate alternatives were already rejected in that section: walking each blob's tree costs one piece-store read per piece per enforcement, and the piece store's own total cannot tell a cached blob from a pinned one.

A tripwire goes with it, as a `NOTE:` at the counting site: while nothing asks for byte ranges the over-count is at most the tail of one interrupted download per blob, but a caller that reads small ranges out of very large blobs would count far more than it holds and evict a cache that was never over its real limit. If ranged reads become ordinary (`blocked/quereus-reads-and-writes-a-range-of-a-large-value`), count what is held instead — the fetch already knows the bytes it stored.

## Docs

`docs/blobs.md` §Lifetime says what counts against the budget is every cache-only blob "at its record's `size`". Replace that clause with the rule above and its reason: a cache-only blob counts at the blob's full size whether or not every piece is here, which over-counts a partly held blob and so evicts sooner; and a cache-only blob whose size this node never learned is evicted at the next enforcement rather than counted as nothing, because a blob whose size the node cannot name is a blob whose cost it cannot bound. Mention that the fetch writes the size as soon as its plan reads it from the root list piece, so a blob the node holds part of is sized without walking its tree.

## Tests

One new test, in `packages/db-p2p/test/blob-cache-budget.spec.ts` — the reproduction above, at the layer that reproduced it:

- *evicts a cache-only blob whose size it never learned, even when the cache is within budget* — a cache-only blob with no `size` on its record and its pieces present, alongside a sized cache-only blob and a genuinely empty (0-byte) cache-only blob, with a budget large enough for everything the node can account for. Only the unsized one is evicted and only its pieces go. The empty blob is what makes the assertion mean something: without it the test passes for a fix that confuses "no size" with "zero bytes".

Arm 1 needs no new test — it is observable for free inside the existing *keeps what an interrupted fetch stored and asks only for the rest* in `packages/db-p2p/test/blob-fetcher.spec.ts`. After the first, interrupted fetch, node B holds the blob for reads alone, so `b.blobs.local.cachedBlobs()` reports it; assert on `[ref, bytes]` pairs (not the whole entry, whose `lastReadAt` is a real clock reading) that the size the fetch learned is on the record.

Run only what these pin — `blob-cache-budget.spec.ts`, and `blob-fetcher.spec.ts` for the added assertion (it starts three real nodes over loopback, so it is the slow one). Not the package suite; `tickets/rules/testing.md` keeps that for review.

From `packages/db-p2p`, a single spec runs as:

```
node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/blob-cache-budget.spec.ts" --colors --reporter spec
```
