GitHub #53. The second cost that makes an offline commit grow with the queue (the first is ticket `a-savepoint-snapshot-shares-staged-blocks-instead-of-copying-them`). This report is the condition two `NOTE:`s were waiting for, at `judgeTransaction` and at `OfflineMode.followQueue`, and each names a remedy. Both remedies are taken here, and both notes come out.

## The cost

A CPU profile of `NODE=1 MODE=gated N=800 node --cpu-prof test/offline-commit-cost.bench.mjs`, run in `packages/quereus-plugin-optimystic` (40 s, including about 3 s of start-up; Windows, Node 24), shows by self time, outside `structuredClone`:

| self time | |
|---|---|
| anonymous functions in `segments.js` (`SegmentList.entryIds`, `SegmentList.find`) | 3.9 s |
| `WriteIndex.add` and the anonymous functions beside it in the plugin chunk | 6.5 s |
| `judgeQueued`, `writtenKeysIn`, `queueAhead` | 0.8 s |

`OfflineMode.judgeQueued` rebuilds a `WriteIndex` over every earlier entry on each enqueue, and for each one `OfflineMode.queueAhead` reads `heldCollections` and `sealedWrites`, which reach `.sealedEntries()` and `.sealedActions()`: each a linear search or a fresh array of the whole sealed list. So one enqueue is quadratic in the depth. Together with the snapshot cost this accounts for most of the growth from 3.6 ms to 33.6 ms per commit at depth 1000.

During a drain the same index is rebuilt once per settled entry by `OfflineMode.followQueue`: about 1.4 ms per entry at an average depth of 150 in a `MODE=drain N=300` profile, so roughly 10 µs per queued entry.

## The design

**Constant-time segment lookups.** `SegmentList` keeps a `Map<EntryId, SealedSegment>` beside the array, maintained by `seal`, `unseal`, `insert` and `drop`, and `find` uses it. `Collection` gains `holdsSealed(entryId)`, and `SegmentList` an entry count. Replace every `.sealedEntries().includes(id)` (`OfflineQueue.remainingCollections`, the two other sites in `packages/db-core/src/offline/queue.ts`, and `heldCollections` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`) and the `.sealedEntries().length` in `TransactionBridge.offlineRoute`.

**One kept index.** `OfflineMode` holds one `WriteIndex` of the queue. An entry is added when it is judged, and `judgeTransaction` takes that index instead of building one. The index must then be able to remove an entry, so:

- `writers`, `byKey` values, `unreadable` and `tables` values become insertion-ordered maps keyed by transaction id, so `remove` costs the entry's own keys and iteration stays in queue order;
- `insertedAbsent` becomes, per key, a map from inserter to freshness, read as "any is fresh", because the OR it holds today cannot be undone. A stale `true` would judge a later `unchanged` check safe because of a fresh inserter that has since committed and is no longer fresh, which would produce a false `assured`;
- an indexed entry's `assured` is read live from `OfflineMode.judgements` rather than copied at add, since a kept entry's kind can change after it was indexed.

`judgeQueued` needs one entry and its position, not the whole list, so add a constant-time accessor on `OfflineQueue` and use it in place of `OfflineQueue.entries()`, which builds a snapshot of every entry. A transaction judged at the tail goes straight against the index. One inserted ahead of others by a restore is judged against a temporary index built from the entries ahead of it, as today: one pass, on a rare path.

**A narrow follow on a commit.** A new pure function beside `followOutlooks` in `commit-outlook.ts`, used when the status is `committed`: every entry listing the settled transaction in `dependsOn` loses it, in queue order, and its kind is worked out again by the rule `outlookFrom` states (assured exactly when it has no exposure and every remaining `via: 'guard'` dependency is assured). An entry whose kind changes passes the change on to the entries depending on it, found through a reverse map (dependency → dependents) held with the judgements. No index is read, because the dependency sets of the remaining entries can only shrink when a committed entry leaves. `failed`, a partial commit and a restore keep the full `followOutlooks` walk and rebuild the kept index, since each can change other entries' dependencies in other ways, and all three are rare. `OfflineMode.changesTheQueue` already tells them apart.

Rejected: rebuilding the kept index on every settle, as the note at `judgeTransaction` suggested. While a drain runs alongside new commits, that would put a whole-queue pass back on every commit.

`CommitOutlook()` over an open transaction (`OfflineMode.openTransactionOutlook`) is application-called and rare. It may read the kept index.

## Edge cases & interactions

- A transaction a replay refused while it was indexed: it stays listed and its writes stay indexed until it settles, as the walk treats it today. `packages/quereus-plugin-optimystic/test/offline-outlook.spec.ts`.
- `heldCollections` shrinking after a partial commit: the full walk rebuilds the kept index. `commit-outlook.spec.ts` and `offline-outlook.spec.ts`.
- A deferred journaled transaction restored ahead of the queue: the full walk, plus the temporary index for its judgement. `packages/quereus-plugin-optimystic/test/offline-restore.spec.ts`.
- A judgement that throws (`OfflineMode.tryJudgeQueued`): the entry goes unjudged and is judged again on its next `queued` status, so it must not be added to the index twice. An assertion in `WriteIndex.add`.
- A dependent with no judgement counts with no kind, as in `followOutlooks`. Inspection.
- `offline:outlook-regressed`: the narrow follow can only move a kind towards `assured`, so it never logs this. Pinned by the test below, which compares against the full walk.
- `SegmentList`'s map and array staying in step across `unseal` and `insert`. Inspection; `packages/db-core/test/collection-segments.spec.ts` covers the paths.

## Test

One property test in `packages/quereus-plugin-optimystic/test/commit-outlook.spec.ts`, since this replaces a walk with a derivation on real branching: over generated queues (overlapping keys, no deferred records, a mix of exposed and assured), after each committed head, the narrow follow's result deep-equals `followOutlooks` over the same remaining queue, and the index with removals answers the same as one built fresh.
