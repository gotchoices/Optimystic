# State the single-write-lock invariant where a reader meets it

Split from `debt-block-writes-use-three-different-per-block-locks` (that ticket lands the code:
`block-latch.ts`, the `BlockWriteLatch` token on every `IBlockStorage` write, local-only
`getBlock`, explicit `restoreRevision`). This ticket is the documentation, the in-code `NOTE:`s,
and one behavior-change test that ticket deliberately deferred.

## Docs

- `packages/db-p2p/docs/storage.md` §2 (currently lines ~53-90, "Every out-of-band writer of a
  block's `meta.latest` serializes on the per-block commit latch"): rewrite over the **whole
  metadata blob**, not `meta.latest` — a block's metadata `{ latest, ranges }` is read and written
  whole, so any read-modify-write overwrites `latest` whether it meant to or not. Name the single
  key (`Block.write:<blockId>`, `blockWriteLatchKey`), name `block-latch.ts` as the single
  acquirer, give the check that proves it
  (`grep -rn "Latches.acquire" packages/db-p2p/src/storage` → exactly one hit), state that every
  writing method on `IBlockStorage` demands a `BlockWriteLatch` token so an unlatched write does
  not type-check, and record `materializeBlock`'s re-cache as the one named exclusion. **Drop** the
  "Known deliberate exception" paragraph about hosts that supply no latch runner — the optional
  `withBlockCommitLatch` capability on `InvalidationContext` / `CollectionEnv` no longer exists.
- `packages/db-p2p/docs/storage.md:164` and `packages/db-p2p/README.md:264` still list
  `ensureRevision()`; replace with `restoreRevision(rev, latch)` and say `getBlock` is local-only.
  README's "Uses latches for thread-safe operations" bullets should say the caller holds the
  block's write latch and passes the token.

## `NOTE:`s at the code sites

- `materializeBlock`'s re-cache of a replayed materialization at a retained rev
  (`block-storage.ts`, the `saveMaterializedBlock` call after the retention check): it runs on the
  read path **outside** the latch. Say why that is safe — keyed by `(blockId, actionId)`, value is
  a deterministic replay of retained transforms, so a concurrent writer of the same key writes the
  same bytes — and that dropping the re-cache is out of scope until someone measures cold
  historical-read cost without it.
- `readCommitBase` (`storage-repo.ts`): the commit path deliberately no longer restores in line
  (no network I/O inside a multi-block critical section); a base this node cannot materialize
  locally raises `MissingBaseRevisionError`, and healing is cohort reconcile → commit retry (see
  `ClusterMember`).

## Test — the deliberate behavior change

In `packages/db-p2p/test/storage-repo.spec.ts`: a commit against a block whose `latest` is not
locally coverable (metadata `{ latest: { rev: 3, actionId: 'ghost' }, ranges: [[3]] }` with no
records, or `ranges: []`), with a `restoreCallback` wired that would have answered, refuses with
`MISSING_BASE_REVISION_REASON` and **never invokes the restore callback** — before this change
`readCommitBase` → `getBlock` → `ensureRevision` fetched from the peer while holding the commit
latch. Assert the callback call count is 0 and the pending record was dropped (`refuseMissingBase`).
