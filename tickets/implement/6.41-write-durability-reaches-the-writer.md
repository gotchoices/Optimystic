# Why

The prerequisite ticket makes the transactor's answer carry a durability class. But nothing above the transactor passes it on: `TransactorSource.transact` signals success by returning `undefined`, `Collection.sync` returns nothing, and `Tree.replace` returns nothing. So an application still cannot tell a change that every machine holds from one that only the writing machine holds — which is the use the whole feature exists for ("show this row as pending until it is really saved").

This ticket threads the class from the transactor up to the collection API. It changes no behaviour: the same writes succeed, the same ones are refused, and the same retries happen. Only the return values widen.

# Scope

**Single-collection writes only** — the path a row write actually takes: `Tree.replace` → `Collection.updateAndSync` → `Collection.sync` → `TransactorSource.transact` → `ITransactor.pend` + `ITransactor.commit`.

The multi-collection path (`TransactionCoordinator.commit`, which returns `Promise<void>` and folds partial commits across several collections) is deliberately **not** in this ticket. Merging durability across collections that may individually have succeeded or been dropped is its own design problem, and it is parked in `backlog/feat-multi-collection-commit-reports-durability`. Say so in the code at `TransactionCoordinator.commit` with a `NOTE:` naming that ticket, so the gap is visible where someone would otherwise assume the class is available.

# The shape

- `TransactorSource.transact` returns the `CommitResult` it already has in hand rather than collapsing success to `undefined`. Callers that tested `result !== undefined` test `!result.success` instead. Its doc comment's `@returns` line changes with it.
- `Collection.sync`, `syncInternal`, `syncAttempts` and `updateAndSync` return `WriteDurability | undefined`.
  - **`undefined` means nothing was written.** A sync with no staged changes does no pend and no commit, so there is no durability to report — do not fabricate one. This is the one case a caller must handle, and it is exactly the case where there is nothing to show as pending.
  - When the retry loop succeeds on attempt N, the answer is attempt N's — earlier failed attempts wrote nothing that survived.
- `ICollection.updateAndSync` in `collection/struct.ts` changes to match.
- `Tree.replace`, `Tree.sync` and the `Diary` write path forward whatever their collection returned, unchanged. They do not interpret it.

Consumers decide with `isFullyDurable` from the prerequisite ticket, never by comparing `quorum` themselves.

# Edge cases & interactions

- **An empty sync.** No staged changes, no write, `undefined`. Confirm this is reached by the existing "syncing a tree with an empty change set is a no-op" path that `optimystic-module.ts` relies on, and that the `undefined` does not read as a failure anywhere.
- **The retry loop.** `syncAttempts` can pend, lose a race, rebase and re-pend under the same action id. Only the attempt that committed produces a class; a refused attempt produces a `StaleFailure` that the loop already consumes. Do not accumulate or average across attempts.
- **Retry exhaustion.** `SyncRetryExhaustedError` still throws. Nothing returns a durability for a write that never landed.
- **A torn commit.** The class arrives with `torn` naming the abandoned blocks. It must be forwarded verbatim; do not drop it while flattening the result, or the one signal that distinguishes a torn write from a clean one is lost exactly where an application would look for it.
- **Callers inside this repo that ignore the new return.** `quereus-plugin-optimystic` calls `tree.sync()` in several places (`txn-bridge.ts`, `optimystic-module.ts`, `catalog-batch.ts`) and does not need the value. Ignoring a returned value is not a type error, so those sites are unaffected — check them, do not change them, and do not add a lint rule forcing them to consume it.
- **`ICollection` implementers outside `Tree` and `Diary`.** Grep for implementers before changing the interface; a stub in a spec that returns `Promise<void>` still satisfies `Promise<WriteDurability | undefined>` only if it returns `undefined`, which most will.

# Phase 5 of the small-deployment lifecycle spec

`packages/db-p2p/test/small-deployment-lifecycle.integration.spec.ts` phase 5 stops one machine of a two-machine group and writes on the survivor. On roughly two thirds of runs (11 of 16 observed) the write is accepted once the survivor's routing view has dropped the absent peer: it takes the solo branch and the row exists on one machine only until the partner returns. The other runs refuse it. Whether a lone survivor *should* accept is under design in `backlog/more-design/6.5-partition-healing` and is not settled here — so phase 5 currently only prints what happened.

With this ticket, the accepted case becomes assertable without settling that question:

- `attemptWrite` captures the returned durability alongside the refusal it already captures. Widen `WriteAttempt` with an optional `durability`.
- Phase 5 asserts: **if** the away-write was acknowledged, its class is `local` and `isFullyDurable` is false. It still does not assert whether the write was accepted at all.
- `describeWriteAttempt` prints the class in the acknowledged branch, so the run output says `ACKNOWLEDGED (local) after Nms` rather than just `ACKNOWLEDGED`.

This is a conditional assertion by design: it pins the *reporting* on the branch that is taken, without pinning *admission*, which is another ticket's call. Phase 5's other half — that the returning machine ends up actually holding the row — arrives with `under-replication-drain-and-full-replication-event`.

# Tests

- Unit: a collection whose transactor double reports `majority` returns that class from `sync`; a collection with nothing staged returns `undefined`.
- Unit: a transactor double reporting a torn commit surfaces `torn` unchanged through `Tree.replace`.
- Unit: a refused write still throws `SyncRetryExhaustedError` and returns no class.
- Integration: phase 5 as described above. Run it more than once — the branch it takes varies by run, and the assertion must hold on both branches.
