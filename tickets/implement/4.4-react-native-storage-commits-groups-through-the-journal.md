# React Native storage commits groups through the journal

Fifth of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). `journal-batch-backend` explains why LevelDB needs a journal to keep write order: it does not sync an old log file when it switches to a new one, and its recovery skips a damaged record and keeps the ones after it.

`gotchoices/rn-leveldb` 3.11 writes every `put`, `delete` and `write(batch)` with LevelDB's default `WriteOptions` (`sync = false`) and exposes no way to ask for a sync. Until it does (the blocked report `react-native-storage-syncs-once-rn-leveldb-can`), this backend cannot survive a power cut at all. This ticket does everything that does not need the binding, and builds it so the binding change is the only step left: the `classic-level` test surrogate can sync, so the synced path is built and tested here.

## Today

`LevelDBStoreDriver` (`packages/db-p2p-storage-rn/src/leveldb-storage.ts`) is a `RawStoreDriver` writing each put and delete directly, `promote` as one `WriteBatch`, `flush()` a no-op, `durability` `'process-crash'`. `LevelDBKVStore` and `loadOrCreateRNPeerKey` write directly too.

## Design

### `LevelDBLike` says whether it can sync (`src/leveldb-like.ts`)

- `readonly canSync: boolean` on `LevelDBLike`.
- `LevelDBWriteBatchLike.write(options?: { readonly sync?: boolean })`.
- The `rn-leveldb` adapter (`src/rn-opener.ts`): `canSync` false; `write({ sync: true })` throws (a caller bug, since callers check `canSync`).
- The `classic-level` adapter (`test/classic-level-driver.ts`) and the upgrade-check writer's (`packages/upgrade-check/writer/classic-level.mjs`, if it implements `LevelDBLike`): `canSync` true, passing `sync` to `chain.write`.

Every native write this package makes goes through `batch().write(...)`; nothing calls `put` or `delete` on the handle any more. `LevelDBLike.put` and `delete` stay only if a remaining caller needs them; remove them otherwise, so no unsynced direct write can reappear (an unsynced write outside the journal, left in an old log file, is exactly what a later synced write does not cover). The upgrade-check writer's adapter keeps its `put` and `delete` whatever the interface says: published older builds write through it and call them.

### `LevelDBJournalStore implements JournalStore` replaces `LevelDBStoreDriver`

- **Keys** (`src/keys.ts`): a new tag byte `TAG_JOURNAL` (`0x07`, unused today) with the `seq` as 8 bytes big-endian, and one mark key under the same tag with an empty suffix, which sorts before every numbered key.
- **Reads**: the current driver's, unchanged (same tags and encodings), so data an earlier build wrote opens unchanged.
- **`durability`**: `'power-loss'` when `db.canSync`, else `'process-crash'`. Reword the rule-3 `NOTE:` at `durability`: it now holds only while the handle cannot sync, and names `react-native-storage-syncs-once-rn-leveldb-can`.
- **`appendJournal(record)`**: one batch putting `encodeJournalRecord(record)` (from `journal-batch-backend`) under the record's key, `write()` unsynced.
- **`applyJournal(apply, appliedThrough, discard)`**: one batch of every record's entries in order (each `StoreKey` to its existing key encoder; a put or a delete), the mark, and a delete of each numbered record, then `write({ sync: db.canSync })`.
- **`readJournal()`**: one drained iterator over `TAG_JOURNAL` (drain before use, as every scan here does); a record that fails to decode is logged and left out, which recovery treats as a gap.
- **`storeIdentity`**, `listBlockIds`, `approximateBytesUsed`: as today. No `close`: the handle is shared (keep the `NOTE:`).

`LevelDBRawStorage(db, options?)` becomes `new KvRawStorage(new WriteGroupDriver(new JournalBatchBackend(new LevelDBJournalStore(db), options), options))`, `close` redeclared as always present. Export `LevelDBJournalStore` in place of `LevelDBStoreDriver`.

On a handle that cannot sync, the journal backend applies each group at once as one unsynced batch and never journals: the atomicity half of the decision, now. On one that can, relaxed groups are journaled unsynced and applied synced by their deadline.

### Key-value store and identity

- **`LevelDBKVStore`** moves onto a `WriteGroup<string>` (as `FileKVStore` does): the sink commits a batch as one `WriteBatch` written with `{ sync: db.canSync }`, returning an already-resolved `durable`. `get` and `list` read the overlay over the `TAG_KV` range. `flush()`, `close()` and `whenDurable` are the group's. Every flush of it is strict, so it needs no journal: each of its batches carries its own data.
- **`loadOrCreateRNPeerKey`** writes a new key as one batch with `{ sync: db.canSync }`.

### `packages/upgrade-check`

`openBackend`'s `leveldb` case (`test/current-build.ts`) builds a new `LevelDBRawStorage` per `storage()` call and closes only the handle. With writes held until a flush, keep one `LevelDBRawStorage` and one `LevelDBKVStore`, return the same storage from `storage()`, and close both before the handle, as the `fs` case does. The leveldb fixtures must keep passing: keys and values are unchanged, and an old database has no journal, so the first open applies nothing.

## Edge cases & interactions

- **Process crash loses an unflushed group now**, where today each write survives one; the group is all or nothing (by inspection; README).
- **Log-file switch**: every write this package makes is a batch, the journal's appends are the only unsynced writes once the handle can sync, and a lost append is a gap recovery stops at (by inspection; the argument is in `journal-batch-backend`).
- **Recovery over real LevelDB**: relaxed groups journaled, then a new storage over the same handle without closing the first, replays them (test, on `classic-level`).
- **The Quereus React Native plugin sharing the native module** (`RNLevelDBNative`'s doc comment) is unaffected: the shape this package declares for the binding does not change in this ticket (by inspection).
- **`yarn check:rn`** bundles this package's React Native entry; the new `db-p2p` imports must come from its `rn.ts` entry (by running it).

## Tests

In `packages/db-p2p-storage-rn/test/leveldb-storage.spec.ts`, over `classic-level` (which can sync) with an injected `setTimer` and a `LevelDBLike` wrapper recording each batch write's `sync` flag:

- **A relaxed group is appended unsynced and applied synced when its deadline is due.**
- **Journaled groups survive the process going away.** Relaxed flushes, then a new `LevelDBRawStorage` over the same handle without closing the first: the writes read back.
- **On a handle that cannot sync, a flushed group is one unsynced batch and nothing is journaled.** The wrapper reports `canSync: false`.
- Run the raw-storage conformance suite over the composed storage, persistent, as the current spec does for the driver.

In `test/leveldb-kv-store.spec.ts`: one case that a flush writes one synced batch; the existing cases cover reads.
