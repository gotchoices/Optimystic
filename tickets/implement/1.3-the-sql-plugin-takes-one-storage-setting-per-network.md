# The SQL plugin takes one storage setting per network

## Why

The plugin takes two storage settings, both register-only because both are functions:

- `rawStorageFactory: () => IRawStorage` — the block store behind a `local` transactor.
- `blobStorageFactory: () => { pieces: IPieceStore; kv: IKVStore }` — where blob pieces and blob records live for a transactor with no libp2p node.

Three problems follow from their being two, and separate from each other.

**A caller can drop one.** `CollectionFactory.getOrCreateTransactor` records the first options object it sees per transactor key and that record is thereafter the whole truth about where that network's data lives — `knownBlobBackends` and `blobBackendForKey` build the network's blob store from it, long after whichever table opened first. The schema catalog's options were once assembled field by field without `blobStorageFactory`, and because a restarted process reads the catalog before it opens any table, those reduced options became the record: every blob store the process then built was over fresh in-memory stores, so it found none of its own blob pins and answered as if the machine held nothing. No error, no log line. Backlog `debt-a-networks-storage-is-taken-from-one-collections-options` has the full account.

**The two can disagree.** `blobStorageFactory`'s documentation already has to ask the host to make both stores persistent or neither, and explains both ways it goes wrong, because nothing in the type says they belong to one place.

**The plugin's own node has no storage setting at all.** `createNetworkTransactor` builds a node with no storage options whatever, and its `NOTE:` says what that costs: blob pieces and blob records in memory, lost on restart, every pin with them, and the next sweep then deletes the pieces. A host that wants them persistent through the plugin cannot ask for it; it has to build the node itself and register it.

`a-node-takes-all-its-storage-as-one-value` gives db-p2p one value for all of this. The plugin should take one too.

## What to build

**One option.** `storageFactory?: () => NodeStorage` replaces both `rawStorageFactory` and `blobStorageFactory`, on `OptimysticOptions` and on `ParsedOptimysticOptions`, read by the aux-option reader in `optimystic-module.ts` the same way (function-typed, so `register()` only — a `USING` clause cannot carry it). Replace rather than add beside; backwards compatibility is not a concern in this repository yet.

**Called at most once per network.** `CollectionFactory` keeps the resolved `NodeStorage` in a map keyed by transactor key, beside `transactorOptions` and keyed the same way, and every consumer of a network's storage reads it from there:

- `createLocalTransactor` takes `blocks` — through `withReadCache` exactly as it wraps `rawStorageFactory`'s result today, with the same lease ownership rule.
- `resolveBlobBackend`'s single-machine arm takes `pieces` and `kv`.
- `createNetworkTransactor` passes the whole value as `NodeOptions.storage` to the `createLibp2pNode` call it makes, which is what closes the third problem above. Its `NOTE:` about memory blobs goes with it.

Once is not an optimisation. One `NodeStorage` per location is what the fs factory now enforces for files (`each-storage-package-opens-a-whole-nodes-storage`), and calling the host's factory twice for one network is how two sets over one location would reappear — for a host whose factory constructs rather than returns a kept value. Memoize, and say on the option that the factory is called once per network and may return a value it keeps.

**The plugin still closes nothing.** It does not close `rawStorageFactory`'s result today and it does not close this one; a host that needs to close its stores builds the storage outside `register` and returns it from the factory, which is what the specs that need it already do. Say so on the option: the plugin owns no store, and `plugin.dispose()` releases only the read-cache lease it took.

## Not folded in: the network-options refactor

`debt-a-networks-storage-is-taken-from-one-collections-options` proposes splitting `ParsedOptimysticOptions` into a per-network part and a per-collection part, so that a collection's options name a network rather than carrying its storage and there is nothing left to drop. That is the fix that closes the class, and it is **not** part of this ticket:

- It touches the aux-option reader, the catalog opener and `openIndexTree` in `optimystic-module.ts`, `getOrCreateTransactor`, `getTransactorKey`, `knownBlobBackends`, `blobBackendForKey`, and the hand-built options object in every spec that opens a tree directly — a change spanning the plugin's whole option plumbing, with its own failure mode (a mis-keyed network silently sharing or splitting state). That is a separate agent run, and pairing it with this one risks both.
- This ticket narrows what that refactor has to fix: two droppable storage fields become one, and that one is resolved once per transactor key and read from the factory's own map rather than from whichever options object arrived first. The hole is narrower and the remaining hole is in one place.

An arm on that backlog ticket records the narrowing. Do not treat its absence as a reason to delay: nothing here depends on it.

## Edge cases & interactions

- **Transactor key versus node key.** The storage is keyed by transactor key (`<transactor>:<keyNetwork>`), as `transactorOptions` and `blobBackends` are; the node is keyed by node key (`<networkName>:<port>`). If two transactor keys ever resolve to one node key, the node is built once and keeps the storage of whichever transactor key built it — exactly as it keeps that key's `libp2pOptions` today. Say so where the map is declared; it is the same class the backlog ticket covers, not this ticket's to fix.
- **Specs that pass a plugin factory and specs that pass a mesh factory look alike.** `MeshOptions.rawStorageFactory` in `packages/db-p2p/src/testing/mesh-harness.ts` is a different option, takes a node index, and **stays**. `packages/quereus-plugin-optimystic/test/mesh-node-harness.ts` and `test/offline-restore.spec.ts` use that one; `test/cold-apply-cost.spec.ts` and the roughly twenty `rawStorageFactory: () => new FileRawStorage(dir)` specs use the plugin's. Read each site before changing it — the plugin's takes no argument, the mesh's takes an index.
- **Several plugins over one directory in one spec.** Specs that register two or three `Database`s over one directory to simulate a restart (`test/legacy-commit-atomicity.spec.ts`, `test/committed-read-isolation.spec.ts`, `test/concurrent-insert-refusal.spec.ts` and others) pass `rawStorageFactory: () => new FileRawStorage(dir)` to each. `fileNodeStorage(dir)` returns one storage per directory, so each registration gets the same value and the same holder-counted stores — which is what one process over one location should get. What to check in each such spec is whether it was relying on two independent write groups or a cold read: the ones that need a bare, independent store already construct one directly beside the plugin's, and should keep doing that.
- **The catalog key.** `optimystic-module.ts` folds `tableOptions.rawStorageFactory ? '1' : '0'` into a key, with a comment nearby about the catalog read having dropped `blobStorageFactory`. One field now, and the comment's history is worth keeping — it is the evidence for the backlog ticket.
- **`cost-profile.ts`** names `rawStorageFactory` in its prose about what a host-supplied store might be sitting on.
- **A `test` or `mesh-test` transactor** has no block store of its own and never reads `blocks`; a `NodeStorage` still carries one, which costs nothing (every backend's constructor is lazy, and the memory one is three objects). No branch needed.
- **A host that supplied only `blobStorageFactory`** before — persistent blobs over a memory block store — expresses the same thing now by building a storage whose `blocks` is a `MemoryRawStorage` and whose other two are durable. Nothing is lost; say it in the readme row, since it is the one combination the old two-field shape made obvious and the one-value shape does not.
- **`plugin.blobs` on a `network` transactor** reads the node's own blob service, so the plugin's storage now reaches it through the node rather than through the single-machine arm. The blob-pin specs (`test/blob-pins-*.spec.ts`) are the ones that restart a process over shared stores and read back the pins the previous one wrote; they are the suite that catches this going wrong and must pass unchanged in substance.
- **`test/blob-pins-harness.ts`** passes both factories and has a comment explaining why `blobStorageFactory` is there even though nothing in those options opens a blob store — the hand-built-options hazard again. One field now; keep the comment's point.

## Tests

Two cases, both conversions of what exists rather than additions:

- `packages/quereus-plugin-optimystic/test/local-transactor-storage.spec.ts` already pins "local transactor honours `rawStorageFactory`" — the one spec that proves a host-supplied store is actually written through. It becomes the same assertion over `storageFactory`.
- One case in that file for the factory being called **once** per transactor key however many tables and blob services resolve on it. That is branching logic with the one-set-per-location invariant behind it, and it is what keeps a host's constructing factory from opening two sets over one directory.

No new case for the plugin's own node receiving the storage: the blob-pin specs already read back pins across a restart, which is what receiving it means, and a test that only asserted the field was passed would be testing wiring.
