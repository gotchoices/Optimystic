# A large write is measured once, and its cost is documented

Part of GitHub #63; measurements and the split are in `a-consensus-record-is-serialized-once-per-delivery`. This is the last of the four: it removes the writer's redundant size measures, then re-measures with the bench and states the result in the docs, which is the plan ticket's second requirement.

## 1. The coordinator does not re-measure its own writer's pend

`NetworkTransactor.pend` refuses a pend over `MAX_TRANSACTION_BYTES` before sending (`assertTransactionFits`), and `NetworkTransactor.pendMany` judges the batch's sum before sending it as one. `CoordinatorRepo.pendMany` then measures the same requests again on receipt, as a backstop "for a writer that did not go through `NetworkTransactor`". When the writer is this node's own transactor — the request carries `MessageOptions.localWriter`, which `NetworkTransactor.localWriterMark` sets only for the node it runs on and which never travels on the wire — that second measure is a whole serialization of the pend repeated on one machine (0.10 s of the profiled 7.0 s; the writer's own was 0.09 s). Skip the backstop when `options?.localWriter` is set, and say why in the comment beside it. A remote request keeps the backstop. Update the `NOTE:` on `transactionBytes`, which named exactly this as its revisit condition.

Confirm first that nothing but `NetworkTransactor` sets `localWriter` (a grep found only `localWriterMark`), and that both of its pend paths measure before sending (`pend` directly; `pendMany` through its sum check, falling back to per-collection pends that each go through `pend`).

## 2. The log does not measure an entry whose fate is already decided

`Chain.takenBy` decides how many entries a block takes: it serializes the whole tail block, then each candidate entry. For a large write both are whole passes over row data (0.12 s profiled): the tail usually holds the previous large entry, and the new entry is measured even though the decision does not need it. Two short-circuits, neither changing any decision:

- When the block already holds an entry and its measured size is at or over the target, no further entry can fit: take none without measuring the next entry.
- An empty block always takes its first entry: do not measure that entry when it is the last one to place (nothing after it needs the running total).

The decision stays a pure function of the tail block's content and the entries, so a retried append at the same revision splits the same way and mints the same block ids (internals *A write's log append is a fixed function of the write and the revision it is requesting*). The existing `NOTE:` (keep a running byte count for the tail) stays as the tripwire for the tail's own measure; update its wording.

## Edge cases & interactions

- **A remote writer, or a custom transactor**, never sets `localWriter`, so the coordinator still refuses an oversized pend from it.
- **A batch over the limit** in `NetworkTransactor.pendMany` falls back to per-collection pends, each measured by `pend`; the coordinator's skip changes nothing there.
- **`takenBy` with no byte target** (a chain built without `blockTargetBytes`) returns before measuring, as now.
- **A tail exactly at the target** with one entry: no further entry fits under either rule (the existing rule breaks when `grown > target`, and any further entry adds at least one byte). Check the boundary by inspection against the existing chain specs; no new test is needed for a change that keeps every decision.
- The chain and log specs (`packages/db-core/test/` chain/log size-rollover specs) must pass unchanged — they are what proves the decisions did not move.

## Notes from `a-consensus-record-is-serialized-once-per-delivery`

- **Some of the sizes in §3 are over the transaction limit.** The bench reports a transaction refused with `TransactionTooLargeError` (and the size it was refused at) instead of stopping. In legacy mode 8 values of 256 KiB sit at the limit: 1 to 3 of 20 were refused, at 7.67 to 8.01 MB, against a median of 3.34–3.50 times the 2 MB of raw values. Session mode refused all 20 of its 8-value transactions, every one at 9.34 MB, because its pend also carries the statements as validation payload; 4 values (1 MB) commit there at 5.34–5.51 times. 16 values will be refused in both modes. Say so in the docs, and measure the sizes that commit.
- **One outlier was seen once, under the profiler only.** In one `node --cpu-prof` run of six 8-value legacy transactions, one commit took 403 s. Every sample of it was inside a single `TextEncoder.encode` in `encodeJson` (`packages/db-p2p/src/storage/raw-store-codec.ts`), called from `savePendingTransaction` (`packages/db-p2p/src/storage/kv-raw-storage.ts`). It did not recur in a second profiled run or in five unprofiled 20-transaction runs. `TextEncoder.encode` of an 8 MB string took 10–14 ms in isolation, and the machine had about 9.6 GB of memory free afterwards, so the cause is unknown; a stall of the whole host is as likely as anything in this repository. This is the shape of the issue's 11–13 s commits, so watch the bench's maximum for it as §3 already says.
