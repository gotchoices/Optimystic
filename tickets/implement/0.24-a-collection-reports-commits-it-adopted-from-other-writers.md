# A collection reports commits it adopted from other writers

Part of GitHub #58, split out of `a-materialized-view-follows-rows-other-members-commit` (which depends on it). That ticket keeps a Quereus materialized view over an Optimystic table current when other machines commit to the table. To do that without rebuilding the view after every one of this machine's own writes (which Quereus already maintains row by row), the plugin needs to know when what a table handle reads has changed because **someone else** committed — whichever path brought that change in: a read's pull-on-read refresh, the offline drain's refresh before a head commit, the coordinator's refresh between attempts, or a refresh the plugin runs on purpose.

## The rule

A refresh (`Collection.updateInternal`) has **adopted other writers' commits** when, in the step that adopts the new revision (`forgetAndAdopt`), any of these holds:

- it walked at least one log entry other than the in-flight write's own entry (`ownEntry`, which `consumeOwnEntry` takes as this instance's write) — an action entry another writer committed;
- it found at least one durable invalidation (`getInvalidationsFrom`), which reverted committed content;
- it adopted another lineage (`judgeAdoption`'s verdict that drops the whole cache).

Why this is exactly "not mine": an instance's own successful commits are folded into it (`foldOwnCommit` for a sync or head commit, `recordCommitted` for a coordinator commit) and the held revision advances past them, so a later refresh never walks them; a torn own write is found and consumed as `ownEntry`; and a refresh that meets the instance's own head commit while it is on the network returns before adopting anything (`headInFlight`). Every other entry a walk adopts was written by another handle — another machine, or another `Database` in this process over the same transactor (GitHub #58's repro shape).

A checkpoint entry changes no rows; it is not counted. An open (`attachToLog`) walks nothing and reports nothing: the plugin handles a table's handle being replaced on re-initialization itself.

## Interface

Add to `CollectionInitOptions`:

```ts
/** Called, synchronously, once per refresh that adopted changes this instance did not write: log
 * entries other writers committed, a durable invalidation, or another lineage (see
 * docs/internals.md §Reactive Watch Bridge). `rev` is the revision adopted. Runs inside the
 * refresh's await-free adopt step, under the collection latch on most paths, so it must be
 * synchronous and must not call into this collection; a throw out of it is caught and logged
 * (`collection:external-commits-callback-threw`). */
onExternalCommits?: (rev: number) => void;
```

Thread it through `TreeCollectionOptions` (add `'onExternalCommits'` to its `Pick`) and `Tree.buildInit`, the way `onSealedRefused` travels. Call it from the adopt step, after `forgetAndAdopt` has adopted, in the same synchronous step (no `await` between the adoption and the call), and only when the rule above holds. Guard it like `viewChanged`'s callback (try/catch, log).

Do not widen `RefreshReport` or `update()`'s return type: the signal has to reach the owner from every path that refreshes, several of which (the drain's head-commit refresh, the coordinator's inter-attempt refresh) are not called by the owner.

## Edge cases & interactions

- **Own torn entry finished and consumed** (`ownEntry` set, nothing else walked): no call. Covered by the test below.
- **Own entry plus a rival's entry in one walk**: one call (the rival's). By inspection — the count excludes only `ownEntry`.
- **Refresh deferred to an in-flight head commit** (early `return`): no call, nothing adopted. By inspection.
- **Refresh that adopts nothing new** (the one-request idle path, `tailShowsNothingNewer`): no call. By inspection.
- **Refresh that throws after adopting** (replay refusal): the call already happened in the adopt step — correct, the adoption stands. By inspection.
- **Several handles over one collection id in one process**: each reports what *it* adopted; a commit by handle A walked by handle B is reported by B. That is correct for two `Database`s; for two handles of one `Database` it over-reports, which costs the plugin a redundant view refresh, never a missed one.
- **Callback throws**: logged, the refresh continues. By inspection.

## Test

One test, in `packages/db-core/test/` beside `collection-own-action-replay.spec.ts` (reuse its two-handle fixture over one `TestTransactor`): handle A and handle B on one collection, each with `onExternalCommits` recording calls. A commits; B commits; A refreshes. Expected: A's callback called once (B's entry), B's never called (its only refresh-visible entry is its own, already folded). This pins the own/foreign branch the plugin relies on.
