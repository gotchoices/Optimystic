# Move the repair corroboration floor off the replication factor

## Context

The prerequisite ticket split `clusterSize` (replication factor) from `assumedClusterSize` (the
smallest cohort the operator asserts this deployment can genuinely field), and made the membership
admission gate read the latter. This ticket does the same for the **second** consumer that was also
using `clusterSize` as a statement about how many peers exist.

## What is wrong

`corroboratorCapacity(cohortPeerCount, clusterSize)`
(`packages/db-p2p/src/cluster/quorum-restore.ts`) answers "how many peers other than me could
possibly answer for this block at all", and both restoration paths cap their corroboration floor
with it. It deliberately takes `max(observed, clusterSize − 1)` so that a shrunken *view* of the
network — which is unauthenticated, coming from `IKeyNetwork.findCluster` or a coordinator-declared
peer set — cannot talk the requirement down. That reasoning is right and stays.

But the number it measures against is the replication factor, which defaults to `10`. So a genuine
two-node deployment that never set `clusterSize` computes `corroboratorCapacity(1, 10) = 9`, needs
two corroborators, has only one peer that could ever supply one, and can therefore **never** repair
a block. That is the same conflation this pair of tickets exists to remove: after the prerequisite
lands, `clusterSize` is documented as replication-only, so a security floor derived from it is
simply reading the wrong field.

The existing escape hatch is documented as "configure `clusterSize: 2`" — which is exactly the
advice that forced the reporting deployment to lower its replication factor to make things work.

## Target shape

Rename the second parameter and point every caller at the new setting. The arithmetic is unchanged.

```ts
/**
 * The `corroboratorCapacity` to hand {@link quorumSize}: how many peers other than the asking node
 * could answer for a block at all, given `cohortPeerCount` peers currently visible (self already
 * excluded) and `assumedClusterSize` — the smallest cohort the operator asserts this deployment can
 * genuinely field.
 *
 * Deliberately the MAX of the two: the corroboration floor may be relaxed only for a cohort that is
 * *genuinely* small, never for one that merely looks small. Cohort views are unauthenticated — the
 * read path takes them from `IKeyNetwork.findCluster`, the commit path from a coordinator-declared
 * peer set — so a partition, a self-shrunk record, or an attacker with routing influence could
 * otherwise talk the requirement down to a single voter. Measuring against the asserted size keeps a
 * shrunken view out of the relaxed branch; the escape hatch for a real two-node deployment is
 * therefore to set `assumedClusterSize: 2`, an explicit operator declaration — and, unlike the old
 * `clusterSize`, one that does not also drop the replication factor.
 */
export function corroboratorCapacity(cohortPeerCount: number, assumedClusterSize: number): number {
	return Math.max(cohortPeerCount, assumedClusterSize - 1);
}
```

Callers:

- `ReconcileBlockDeps.clusterSize` → `assumedClusterSize`, with its doc comment updated
  (`reconcile-block.ts:41-42`); the single call site at ~line 161 follows.
- `CoordinatorRepo`: resolve `this.assumedClusterSize = policy.assumedClusterSize ?? policy.clusterSize`
  in the constructor and use it at the `corroboratorCapacity(...)` call (~line 590). The
  `?? policy.clusterSize` fallback keeps behavior identical for any caller that has not adopted the
  new field, and errs conservative (a higher capacity means a *higher* corroboration floor, i.e. less
  relaxation). Keep `this.clusterSize` only if something else still needs it; otherwise remove it.
- `libp2p-node-base.ts`: pass `assumedClusterSize: consensusConfig.assumedClusterSize` into
  `createReconcileBlock` (line ~752). `CoordinatorRepo` already receives the whole `consensusConfig`.
- `libp2p-node-base.ts` `NodeOptions.clusterSize` jsdoc (lines ~176-183) currently tells embedders
  that the read-repair corroboration floor is measured against `clusterSize` and that "a genuine
  two-node deployment must set `clusterSize: 2`". That is the advice this ticket invalidates —
  rewrite it to point at `clusterPolicy.assumedClusterSize`.

Note the deliberate asymmetry with the prerequisite ticket: the admission gate treats an absent
`assumedClusterSize` as *unknown* and admits (refusing writes outright is unacceptable), while here
an absent value falls back to `clusterSize` and stays strict (the failure is a block that goes
unrepaired — degraded, not dead). Say so in a comment at the fallback so it does not read as an
oversight.

## Edge cases & interactions

- **`assumedClusterSize` absent** in a `CoordinatorRepo` or `createReconcileBlock` constructed
  outside `libp2p-node-base` (several specs do this): must behave exactly as today via the
  `?? clusterSize` fallback. Pin with a test.
- **The security property must survive**: a large deployment with `assumedClusterSize: 10` whose view
  is shrunk to one peer by a partition still computes capacity `9`, still needs two corroborators,
  still declines. This is the whole reason the function takes a max — do not let the rename weaken it.
- **The healing case**: `clusterSize: 10, assumedClusterSize: 2`, one other peer visible → capacity
  `1` → quorum `1` → the block heals. Today this deployment cannot heal without also dropping its
  replication factor.
- **Degenerate values**: `assumedClusterSize` of `0` or `1` must not make the capacity negative and
  must not let `quorumSize` accept a claim from nobody. `quorum-restore.spec.ts:77-84` already pins
  this against `clusterSize`; port it.
- **Both restoration paths must resolve the same value.** `CoordinatorRepo.queryClusterForLatest`
  (read repair) and `createReconcileBlock` (commit-path reconcile) are the two callers, and in the
  live node they are fed from one `consensusConfig`. A test that constructs a node and asserts both
  see the same number is cheap insurance against future drift — the same spirit as
  `assertSuperMajorityCoupling`.
- **Content trust at capacity 1 is unchanged** and still documented in `reconcile-block.ts` and
  `selectQuorumBlock`: block ids are not content-addressed, so a sole peer's bytes are taken on its
  word. This ticket changes *which deployments reach* that branch, not what it costs. The existing
  prose in those doc comments references `clusterSize` — update the references, keep the analysis.
- **`mesh-harness.ts`** meshes do exercise reconcile; check `debt-mesh-harness-reconcile-double-bypasses-quorum`
  in `backlog/` is not made stale or worsened by this change (it should be untouched — read it, do
  not fix it here).

## Key tests

In `packages/db-p2p/test/quorum-restore.spec.ts` (extend the existing `corroboratorCapacity` block):

- `corroboratorCapacity(1, 2) === 1` and `quorumSize(1, 0.51, 1) === 1` — a declared two-node
  deployment heals. (Exists; re-point its comment at the new setting name.)
- `corroboratorCapacity(1, 10) === 9` and `quorumSize(1, 0.51, 9) === 2` — a shrunken view of a
  declared ten-cohort deployment still cannot relax anything.
- Degenerate `0` / `1` cases produce no negative capacity.

In `packages/db-p2p/test/reconcile-block.spec.ts` and the read-repair specs:

- A cohort with exactly one other peer plus `assumedClusterSize: 2` restores, while the same cohort
  with `assumedClusterSize: 10` declines — proving the switch is what decides it, independent of
  whatever `clusterSize` is set to.
- A deps/config object omitting `assumedClusterSize` reproduces today's `clusterSize`-driven
  behavior exactly.
