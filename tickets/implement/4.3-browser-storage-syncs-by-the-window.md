# Browser storage syncs by the window

Fourth of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). `journal-batch-backend` explains why this backend journals instead of committing groups directly: IndexedDB can make one transaction durable but promises nothing about the order relaxed transactions reach the disk.

## Today

`IndexedDBStoreDriver` (`packages/db-p2p-storage-web/src/indexeddb-storage.ts`) is a `RawStoreDriver`: every write is its own implicit `readwrite` transaction at the browser's default durability (relaxed in every current browser), `promote` is one two-store transaction, `flush()` is a no-op, `durability` is `'process-crash'`. `IndexedDBKVStore` and `loadOrCreateBrowserPeerKey` write the same way.

## Design

### Strict support

`durability: 'strict'` on a transaction makes it complete only once the browser has put it on disk (Chrome 83+, Firefox and Safari in current releases). A browser without it ignores the option. Detect once per handle: `typeof IDBTransaction !== 'undefined' && 'durability' in IDBTransaction.prototype`, overridable by an option `strictDurability?: boolean` (tests set it, since `fake-indexeddb` records `durability` on its transactions but does not expose it on the prototype).

### Schema version 3 (`src/db.ts`)

Add a `journal` object store: number keys (the record `seq`) holding `{ seq, entries }` by structured clone (no codec needed), and one string key `'applied-through'` holding the mark. IndexedDB orders numbers before strings, so a key range over numbers never touches the mark. Bump `DEFAULT_DB_VERSION` to 3; the `upgrade` hook's `objectStoreNames.contains` guards make it additive. The open issue of upgrade tests and a blocked upgrade belongs to backlog `debt-indexeddb-version-upgrade-is-untested-and-unhandled`, which now carries this bump as an arm.

### `IndexedDBJournalStore implements JournalStore` replaces `IndexedDBStoreDriver`

- **Reads**: the current driver's reads, unchanged (snapshot-before-yield, the same object stores and keys), so data written by an earlier build reads unchanged.
- **`durability`**: `'power-loss'` when strict is supported, else `'process-crash'`.
- **`appendJournal(record)`**: one `readwrite` transaction on `journal`, `{ durability: 'relaxed' }`, putting the record under its `seq`.
- **`applyJournal(apply, appliedThrough, discard)`**: one `readwrite` transaction over the six stores and `journal`, `{ durability: strict ? 'strict' : 'relaxed' }`. Queue every request synchronously, then await `tx.done`: puts and deletes for each record's entries in order (each `StoreKey` to its object store and key, exactly as the current driver's methods), the mark, and a delete of each numbered record. Nothing else is awaited inside the transaction, because IndexedDB commits a transaction that is left idle (the existing snapshot `NOTE:` is the same rule).
- **`readJournal()`**: one `readonly` transaction reading every numbered record and the mark.
- **`storeIdentity`**: the handle, as today, keeping its `NOTE:`. No `close`: the handle is shared (keep that `NOTE:`).
- The rule-3 `NOTE:` at `durability` now holds only for the non-strict case; reword it to say so.

`IndexedDBRawStorage(db, options?)` becomes `new KvRawStorage(new WriteGroupDriver(new JournalBatchBackend(new IndexedDBJournalStore(db, options), options), options))`, `close` redeclared as always present. Export `IndexedDBJournalStore` in place of `IndexedDBStoreDriver`.

### Key-value store

`IndexedDBKVStore` moves onto a `WriteGroup<string>` (as `FileKVStore` does in `packages/db-p2p-storage-fs/src/file-kv-store.ts`): `set` and `delete` record into the group, `get` and `list` read the overlay over the `kv` store (`list` merges overlay puts and deletes under the prefix, like `FileKVStore.list`), and the sink commits a batch as one `readwrite` transaction on `kv`, `strict` when supported, returning an already-resolved `durable`. `flush()` and `close()` are the group's; expose `whenDurable` as `FileKVStore` does. Every flush the node makes of this store is strict, and the group's idle flush is strict, so there is no relaxed path to journal.

### Identity

`loadOrCreateBrowserPeerKey` writes a newly generated key in one `kv` transaction with `durability: 'strict'` (when supported), so a power cut right after first start cannot give the node a different peer id next time.

### Docs

- `packages/db-p2p/docs/storage.md`: the browser row of the per-backend survival table (`durability-docs-match-the-window`): with strict support, a power cut loses at most the groups inside their window; without, as today. The Invariant 6 driver table row; the *Rule 3 past the crashes a store names* paragraph (browsers with strict support leave it).
- `packages/db-p2p-storage-web/README.md`: the journal, what a crash loses, `await storage.close()` and `await kvStore.close()` before closing the handle, and that browser storage can still be evicted under storage pressure unless the page holds persistent storage (`navigator.storage.persist()`), which loses everything and is outside this design.

## Edge cases & interactions

- **Process crash (a tab closed) with relaxed records held**: the records survive (an IndexedDB transaction that completed survives the page), and the next open applies them (test).
- **A browser that ignores `durability`**: detection says no, the store reports `'process-crash'`, and the journal backend applies each group at once as one relaxed transaction; the node's start-up line already says such a backend cannot keep the window (by inspection).
- **Two tabs over one database** run two nodes over one store, which Invariant 5 of `packages/db-p2p/docs/storage.md` already forbids and nothing here enforces. The journal makes a second tab's open apply the first tab's held records; add one sentence to the `NOTE:` on the store's identity saying so (by inspection).
- **Each group is now one transaction** where today each write was one, which is the atomicity the decision asks for and fewer transactions (by inspection).
- **`fake-indexeddb` has no durability**, so the tests check which durability each transaction asked for, not what the disk did. A device or manual check is the only real one; say so in the README.
- **The apply transaction's size** is every held group's writes; bounded by `WriteGroup`'s `maxUnsyncedBytes` (by inspection).

## Tests

In `packages/db-p2p-storage-web/test/indexeddb-storage.spec.ts`, over `fake-indexeddb` with `strictDurability: true`, an injected `setTimer`, and a spy on the handle's `transaction` recording each call's stores and `durability`:

- **A relaxed group is appended relaxed and applied strictly when its deadline is due.** A flush with `withinMs: 5000` opens one relaxed transaction on `journal` only; firing the timer opens one strict transaction covering the data stores and `journal`; `whenDurable()` then resolves.
- **A strict flush applies in one strict transaction.**
- **Journaled groups survive the page going away.** Relaxed flushes, then a new `IndexedDBRawStorage` over the same handle without closing the first: the writes read back.
- Run the raw-storage conformance suite over the composed storage, persistent, as the current spec does for the driver.

In `test/indexeddb-kv-store.spec.ts`: one case that writes, flushes, and sees one strict `kv` transaction; the existing cases cover reads over the overlay. In `test/identity.spec.ts`: none new.
