# The writer sees a disputed pend

## Why

`dispute-commit-path-block` makes `ClusterCoordinator` end a blocked pend with one of three errors. A thrown error reaches a *remote* writer as a reset stream, which the writer reads as an unreachable coordinator and re-drives against another one — exactly what an expiry used to do before `ExpiredFailure` (see `docs/internals.md`, "Pend retryability is an explicit field"). The dispute outcomes need the same treatment: a returned, typed refusal that crosses the JSON wire and that every pend consumer classifies by one predicate.

## Specification

- **Wire shape** (db-core, sibling of `StaleFailure` and `ExpiredFailure` in `PendResult`): `DisputedFailure = { success: false; dispute: { disputeId: string; state: 'pending' | 'approvers-won' | 'rejecters-won'; retryAfter?: number } }`. `retryAfter` (unix ms) is set for `pending` (the dispute's deadline). One predicate, `isDisputedFailure`, beside `isExpiryFailure`; `isConflictFailure` is false for it.
- **Producer**: `CoordinatorRepo.pendThroughCluster` returns it for `DisputeUnresolvedError` (`pending`), `DisputeSettledError` (`approvers-won`) and `TransactionRuledInvalidError` (`rejecters-won`), checked before the stale classifiers, as the expiry is.
- **Aggregation**: `NetworkTransactor.pend` makes a dispute in any batch the whole answer, with precedence `rejecters-won` > `pending` > `approvers-won`, and `pending`'s `retryAfter` the latest across batches. Expiry still outranks a dispute (an expired transaction is dead whatever the dispute says).
- **Consumers** — `Collection.syncAttempts` and `TransactionCoordinator`'s pend phase:
  - `rejecters-won` → throw `TransactionRuledInvalidError` (db-core, non-retryable, carries the dispute id), no re-drive. Like `TransactionExpiredError`, one class raised by every layer.
  - `approvers-won` → re-drive at once (the ruling has already ejected the rejecters; no backoff needed).
  - `pending` → wait until `retryAfter` (bounded by the write's remaining budget/deadline), then re-drive. If the wait would exceed the budget, give up with the existing exhaustion error carrying the refusal.
  - All three count against the existing attempt budget.
- **Commit side** is untouched: a blocked pend never reaches the commit phase.

## Edge cases & interactions

- **Mixed versions**: a peer that predates the field returns its old shapes; `isDisputedFailure` keys on the presence of `dispute` (by inspection).
- **Slot-hold no-sleep rule** (`retryBackoffMs`): a disputed refusal is not a confirmed stale loss and must not trigger the no-sleep retry.
- **Multi-collection commit**: a `rejecters-won` on one collection's pend aborts the whole transaction before any commit (the pend phase precedes commit); verify by inspection that no participant is left pended — the coordinator already cancels pended participants on a pend-phase failure.
- **Quereus bridge**: `TransactionRuledInvalidError` reaches `mapCommitRefusal`'s fallthrough; it should surface as a clear message naming the dispute, not a `UNIQUE` or `BUSY` mapping. Add a mapping only if the fallthrough loses the class name; otherwise note it in the handoff.

## Tests

- `syncAttempts`: a `pending` refusal waits until `retryAfter` then re-drives; `rejecters-won` throws `TransactionRuledInvalidError` without a second pend. (One spec, two cases, against a test transactor returning the shapes — the transactor is the seam.)

## Interaction with the validity rejection (added by `offline-sync-typed-validity-rejection`)

A fourth returned refusal now exists beside `StaleFailure`, `ExpiredFailure` and `ShortfallFailure`: `RejectedFailure` (decided by `isRejectedFailure`, raised as `ValidityRejectedError` in `packages/db-core/src/network/validity-rejected-error.ts`), returned by `CoordinatorRepo.pendThroughCluster` when every reject that sank a pend is validity-marked or an expiry vote. Three things this ticket must decide or carry:

- `DisputedFailure` needs `rejected?: never`, and each sibling needs `dispute?: never`, so consumers keep reading common fields unnarrowed.
- `refusalFrom` in `packages/db-core/src/transactor/network-transactor.ts` now ranks rejected > expiry > shortfall > stale. Place the dispute states in that order; the "Expiry still outranks a dispute" rule above predates a rejected arm that outranks expiry.
- A disputed pend must not also reach the validity arm: once the coordinator blocks a marked rejection beside approvals, it raises the dispute errors instead of `ValidatorRejectionError`, so the `validity` classification in `ClusterCoordinator` stays the answer only for a rejection no approval contests. Decide whether `rejecters-won` raises `TransactionRuledInvalidError` or reuses `ValidityRejectedError`; both say "invalid, do not retry".
