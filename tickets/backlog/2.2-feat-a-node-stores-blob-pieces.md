# A node stores blob pieces

docs/blobs.md designs native large-value ("blob") support. This ticket gives a node the local half: a store for the pieces a blob is cut into, a durable record per blob saying why the node keeps it, the sweep that removes pieces nothing needs, and the parts of `node.blobs` that need no other machine. The format, builder, verifier and service types come from `feat-blob-references-and-verified-piece-trees`.

## Requirements

**`IPieceStore`** (docs/blobs.md §The local store), in `packages/db-p2p`: has, get, put, delete, list, bytes used, flush. A piece is immutable once written and keyed by its SHA-256 digest in one canonical form every backend uses, so a raw piece and a list piece with equal bytes share one entry. The store does not hash; the blob service is its only writer and checks every piece against its CID before calling `put`. A `put` of a key already present writes nothing. `flush` follows the contract on `RawStoreDriver.flush` in `packages/db-p2p/src/storage/raw-store-driver.ts`: once it resolves, every put that resolved before the call survives a crash, to the extent the backend reports it can. The piece store is deliberately not a `RawStoreDriver` store and does not go through `KvRawStorage`, its write group or its journal: bytes are stored as bytes, never JSON.

**Implementations.** In memory (in `packages/db-p2p`) and on the filesystem (in `packages/db-p2p-storage-fs`). The filesystem store writes each piece to a temporary file, syncs it, renames it into place and syncs the directory, so a crash leaves either the whole piece or none. It spreads pieces over subdirectories by key prefix so no single directory grows to millions of entries. If it is given the block store's base path, its root directory has a fixed name that `FileBatchBackend.listBlockIds` skips at the root, beside the names it already skips.

**A conformance suite**, exported from `packages/db-p2p`'s testing entry and modelled on `runRawStorageConformance`, which every backend runs: put then get returns the same bytes; a second put of a present key changes nothing; delete then has is false; list returns every key once; bytes used rises by about a piece's size per put and falls on delete; a returned buffer can be modified by the caller without changing what is stored; a 256 KiB piece and a piece at the reader's 1 MiB bound round-trip; and, for a persistent backend, flush then reopen keeps every flushed piece.

**Blob records** (docs/blobs.md §The local store, §Holds), in the node's `IKVStore`, under a new key prefix that is added to `NODE_KV_NAMESPACES` so a file key-value store sharing the block store's directory is not listed as blocks. A record holds the reference, the size once known, whether every piece is present, when it was last read, and its holds. The record type carries all four hold kinds (pin with an owner label, owed, responsible, cached) so later tickets add holds without changing the format; this ticket creates only pins. Records are what make the node's blobs enumerable after a restart.

**The sweep.** Deletes every piece that is in no held blob's tree, walking each held blob's tree from its reference through the list pieces present. It must never delete a piece of a `put` still in progress, which has pieces stored before its record exists; the service keeps those keys protected in memory until the record is written or the put fails. A blob whose last hold is released has its record removed and its pieces left for the sweep.

**The local service.** `put`, `stat`, `read`, `pin`, `unpin` as docs/blobs.md §The node's blob service defines them:

- `put` streams through the builder, stores each piece as it is produced, flushes the piece store, then writes the record with the owner's pin and flushes the key-value store, and only then resolves. It never holds more than the builder does. A put with no `owner` is pinned under the label `default`, since a blob pinned under nothing would be swept; `unpin(ref, 'default')` releases it.
- `stat` answers from the record and the piece store: `here`, `partial` or `unknown`, `heldBytes`, and `size` once the root piece is present. `probe` and `elsewhere` need other machines.
- `read` yields verified bytes, ranged by `offset` and `length`, through the verifier, reading only the pieces the range needs, and updates the record's last-read time. With `from: 'here'` a missing piece fails with `BlobUnavailableError` reason `not-here`. Until the transfer ticket lands a read without `from: 'here'` has nobody to ask, and fails with `cohort-unreachable`.
- `pin` and `unpin` add and remove a pin by owner; pinning the same owner twice is one pin.
- `fetch` resolves when the blob is whole here and otherwise fails as a read would. `announce`, `onProgress` and `onDurability` are completed by later tickets; until then the listeners are accepted and never called, and `announce` rejects with an error saying copying is not built.

**Node wiring.** `NodeOptions.pieceStorage`, an instance or factory like `NodeOptions.storage`. Absent, an in-memory store with a loud `node-wiring` warning, as `resolveKvStore` gives for a missing `kvStore`. `node.blobs` declared on `OptimysticNodeAttachments`.

**Storage use.** Piece bytes count toward what `StorageMonitor` reports. All four disk block backends already measure their whole database or directory (the file tree, SQLite's page count, the LevelDB key range scan, the browser's origin estimate), so a piece store sharing that location is already counted by the block store; adding its own figure would count it twice. The monitor adds the piece store's bytes only when the piece store is not inside what the block store measures, and the rule for deciding that is stated where it is decided.

## Edge cases and interactions

- Crash after pieces are flushed but before the record: orphan pieces, removed by the next sweep. Test with `PowerLossKVStore` (`packages/db-p2p/src/testing/power-loss-kv-store.ts`) for the records and an in-memory piece store that drops unflushed puts the same way.
- Crash mid-piece on the filesystem: no partial file is ever readable under a piece's key. Inspection of the write order; one test on the fs store.
- Sweep running during a `put`: in-progress pieces survive. Test, since this is the one race that loses data.
- Two puts of the same content at once: one set of pieces, one record with both pins.
- Two blobs sharing pieces; unpin one: shared pieces survive the sweep. Test.
- Empty blob, one-piece blob: records and reads work; the empty blob's single empty piece is stored.
- A stored piece found corrupt on read (disk damage): `BlobCorruptError`, nothing served past it.
- Record says whole but a piece is missing (a backend lost it): `stat` reports `partial` after a read finds it, and the record is corrected.
- Restart: records list every held blob; pins survive; a memory piece store loses pieces while a persistent key-value store keeps records, so `stat` checks pieces, not only records.
- The new key prefix must not be read as a block id by the file backend. Covered by the existing listing tests once the namespace is added.

## Out of scope
