# Declarative invariants and reconcile rules

Tier 2 of [docs/partition-healing.md](../../docs/partition-healing.md): an application declares invariants (`InvariantSpec`: a deterministic predicate, a kind, a priority) and reconcile rules (`ReconcileSpec`: engine statements run when an invariant is violated, producing a compensating transaction, a flag for review, or an acceptance), both schema-hashed so every node applies the same rule, both producing ordinary signed transactions in the same log.

## Sequencing within this ticket

The doc shows that most of this stands on today's strict system and only the merge-time trigger needs replay mode. So the slices are:

1. **Declarative invariants** enforced at pend, as an extension of `CHECK` constraints, part of the schema hash (item 1).
2. **Declarative resolution at race time**: `resolveRace`'s "most promises, then aged priority, then hash" becomes an application-supplied deterministic rule per collection in the `ReconcileSpec` shape, with the loser's compensating action appended to the log (item 2). Keep the current rule as the default; the residual recorded at `resolveRace` about three or more members is unchanged by making the rule declarative.
3. **A structured audit record** of every resolution, as a first-class log entry (item 4). `InvalidationEntry` is the precedent.
4. **Merge-time triggering** for replay-mode collections, gated on backlog `feat-replay-mode-collections-merge-divergent-histories` landing (prose gate, not a `prereq:`, so slices 1 to 3 can proceed).

Effect gating (item 5) is the offline queue's statuses and the stability stage (`feat-stability-horizon-and-degraded-indicator`); escrow (item 3) is `feat-escrow-for-reservation-required-invariants`.

## Questions this pass must settle

- The doc's open questions: reconcile composition order when several invariants violate at once (priority alone, or a fixpoint); a bound on cascades in aggressive mode; cross-collection reconcile output; the review-queue schema for `flag-for-review`; whether to ship standard reconciles; reconcile under Byzantine conditions (a disagreement on reconcile output is a replay-divergence dispute).
- The per-reconcile work budget and how exceeding it is reported (a validation failure, like a non-deterministic SQL function).
- How the Quereus engine receives `thisTx`, `concurrentTxs`, `mergedState` and `violatedInvariants` as parameters under its existing determinism guards.

## Edge cases & interactions

- A reconcile whose output violates the same invariant: the convergence discipline says it may not; decide whether the engine checks that statically or bounds the recursion.
- A reconcile for a `strong` collection runs only at race time; for a `replay-permitted` one at merge time too, with the same declaration.
- A compensating transaction has an HLC of its own, above the transactions it compensates; descendants built on the compensated transaction are the cascading-compensation question, conservative by default.

## Tests that pay for themselves

The doc's worked examples as tests of the pure replay-and-reconcile function: the bank account under compensation (earlier HLC stands, later is reversed), the seat reservation, the unique handle. A property test that a reconcile output never re-violates the invariant it was written for, over the standard reconciles shipped.
