# SQL columns hold blob references

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). After `feat-committed-rows-register-the-blobs-they-reference`, db-core can keep a reference tree and a scope registry; after `feat-a-referenced-blob-is-copied-to-its-cohort`, a node copies an announced, committed reference to the machines responsible for it. This ticket gives SQL its side of that (§SQL, and §Committing a reference as far as the plugin is concerned): a `blobref` column type, a reference tree per table maintained exactly as index trees are, pins that keep a blob on the writer until its transaction settles, `plugin.blobs`, and two SQL functions. An application then stores a file with `plugin.blobs.put`, inserts the reference in an ordinary row, and the plugin does the rest.

## Requirements

**The `blobref` type.** A Quereus `LogicalType` named `blobref`, physical type text, whose `validate` accepts exactly the strings the `BlobRef` parser from `feat-blob-references-and-verified-piece-trees` accepts. It does not rewrite a value into the accepted spelling: a reference has one spelling, and anything else is rejected (§References and pieces). It compares as text. The plugin registers it through the `types` field of the object `register` returns (`../quereus/packages/quereus/src/vtab/manifest.ts`), so a stored table description naming it opens. The row codec stores the string unchanged. A NULL `blobref` references nothing.

**The table's reference tree.** For a table with at least one `blobref` column, the tree at `<collectionUri>/blobrefs`, opened through the collection factory like an index tree (`${collectionUri}/index/${indexName}` is the precedent), with the referrer key being the table's framed primary key followed by the column name. It is staged inside `update()` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` at every site that stages index entries, through the db-core helper, so it joins the same transaction and commits under the same action id as the row: in session mode as a coordinator participant, in the legacy batched commit (`commitBatchLegacy`), in the per-tree fallback, and in an offline entry (`sealIntoQueue`). Per row and per `blobref` column:

- insert with a non-NULL value: add (value, new key, column);
- delete, including cascade deletes and secondary-UNIQUE evictions: remove (old value, old key, column);
- update that leaves the value and key alone: nothing; update that changes the value: remove old, add new;
- primary-key move, and an `insert or replace` that displaces a row: remove under the old key, add under the new, exactly where the index code handles the same shapes.

**Determinism under validation** (§Registering references). The entries are a pure function of the rows the statements change, computed in the same code path a validating member's re-execution (`QuereusEngine`) runs, so its operations match the writer's. Nothing in that path may call the blob service: a validating member has no bytes and must not pin or announce.

**Registering the tree.** The tree is added to the scope registry when the table is created with a `blobref` column, when `alter table add column` adds the first one (the `addColumn` arm; it already refuses a column with a DEFAULT, so no existing row gains a reference), and by `apply schema` doing either. docs/internals.md §A first touch writes only what the table owes forbids writing a catalog record from an instance that does not owe one; a registry entry is not a catalog record and the registry only grows, so a stale view cannot undo another machine's change through it. Hydration therefore checks the registry with `Tree.open` semantics and registers only a tree it finds missing. Independently of when that happens, a table instance never commits a reference into a tree it has not confirmed registered in this process: registration (idempotent) goes first. Otherwise a committed reference could sit in a tree no receiver will read, and its blob would never be copied.

**Pins follow the transaction** (§SQL, §Committing a reference). Each reference a statement adds is pinned on the writer under an owner label derived from the transaction's identity (`StampId()`). Releases:

- **Commit** (any route): announce each added reference with the table's reference-tree id as scope, then unpin. If announce throws, log it and keep the pin so the bytes are not lost; the restore reconciliation below retries.
- **Rollback**: unpin.
- **Savepoint rollback**: unpin each reference no surviving statement of the transaction still adds; a reference also added before the savepoint stays pinned.
- **Queued offline transaction**: pinned until it settles. `committed`: announce then unpin. `failed`, including reason `discarded` and a cascade failure: unpin.
- **Restore after a restart** (`OfflineMode.restore`): pins live in the blob records; the journal record carries only sealed actions (`JournalEntryRecord`), from which the references a queued entry adds are read back off its reference-tree segments. A pin whose transaction is still queued stays. A pin whose transaction is neither open nor queued settled before the restart with its release lost: if the table's reference tree lists the reference (the db-core reader, certain answer), announce then unpin; if it certainly does not, unpin; if the answer is uncertain, keep the pin and try again on the next restore or reachability wake.

**`plugin.blobs`** on the object `register` returns: the blob service (`BlobService`) for the plugin's network, reached through the collection factory's node (`node.blobs`, declared on `OptimysticNodeAttachments`), created lazily like the transactor. Its `put` pins on behalf of the current transaction when one is open, and under the label `unstaged` when none is (see *`put` outside a transaction* below). `plugin.blobsFor(table)` returns the service of the network a given table uses.

**Transactors with no node.** Decided here: the `blobref` type, reference trees and the scope registry work on every transactor, since they are ordinary collections. For `local`, `test` and `mesh-test`, `plugin.blobs` is a single-machine blob service over a piece store and blob records (in memory for `test` and `mesh-test`; for `local`, a host-supplied piece store beside `rawStorageFactory`, defaulting to memory), whose cohort is this machine alone, so `announce` leaves durability at `local` and the writer keeps every blob. If `feat-a-node-stores-blob-pieces` does not already expose such a service without a libp2p node, this ticket adds the constructor in db-p2p. A custom transactor with no node gets the same.

**SQL functions** `BlobLocality(ref)` and `BlobSize(ref)`, answered from the local `stat` (no probe): the locality string, and the size or NULL when unknown. Asynchronous, not `DETERMINISTIC`, NULL in gives NULL out, and a non-reference argument raises the `BlobRefError` as an SQL error.

## Edge cases and interactions

- **Every row-change shape.** A table with a composite primary key whose columns are not leading, two `blobref` columns holding the same reference, and each shape listed above: after commit the reference tree lists exactly the (reference, key, column) triples the rows hold. One table-driven test over these shapes, checked against a scan of the rows.
- **Racing writers.** Two handles changing the same row's reference: the main table's `unchanged` guard refuses the loser and its reference-tree entries roll back with it. Two handles inserting different rows referencing one blob: both land. Test on two `Database` handles, as `packages/quereus-plugin-optimystic/test/concurrent-row-change-refusal.spec.ts` does.
- **Partial commit** (`CoordinatorPartialCommitError`, or the sweep's `PartialCommitError`): announce only references whose reference-tree collection is in the committed half; keep the rest pinned for the restore reconciliation. Inspection.
- **Validation re-execution** stages identical reference-tree operations and touches no blob service. Assertion at the seam, plus one test with a `QuereusEngine` re-execution.
- **Committed reads** (`committed.<Table>`) never touch the reference tree. Inspection.
- **Drop column.** A `blobref` column is a drop blocker (`columnDropBlockers`), as an indexed column is, since its entries would outlive it. **Drop table**: the drop removes the table's reference tree from the scope registry (the db-core unregister), so the blobs it listed are no longer referenced there and are reclaimed by the ordinary rule. The reference tree itself stays in storage, as a dropped table's index trees do. Test: after a drop, the registry no longer lists the tree.
- **Bytes on the network before the visible row** (docs/blobs.md §Committing a reference, the two-commit pattern). An application commits a row holding only the reference, waits for `plugin.blobs.onDurability` to report `majority` or `full` for that reference, then commits the row people act on. The durability event must therefore name the reference, fire on the writer after the first commit's announce without any further call, and fire again on each class change. Test on a two-node mesh: commit the reference row, await the event, and assert the other node holds the blob before the second commit is sent.
- **`put` outside a transaction.** docs/blobs.md's own example calls `plugin.blobs.put` before the insert's transaction exists, and says only that `put` pins "on behalf of the current transaction". docs/blobs.md §SQL settles it: such a blob is pinned under the label `unstaged` with the time of the put. The first statement that stages the reference moves the pin to its transaction. A blob still `unstaged` after a holding period (24 hours by default, a plugin option) is unpinned by the plugin, on a timer and at start. Tests: put, then insert in a later transaction, keeps the blob throughout; put with no insert is unpinned after the holding period (injected clock).
- **A table on another network.** `plugin.blobs` is one network's service, while a table may name its own transactor. A reference means something only in the network whose machines hold the bytes, so `plugin.blobs` is the service of the plugin's default network and `plugin.blobsFor(table)` returns the service of the network that table uses; pins and the commit-time announce always use the table's own. A statement is not refused for staging a reference the table's network does not hold: copying a reference from another row is legitimate when the bytes are elsewhere in the same network, and the plugin cannot tell that case from bytes put into a different network. Such a reference commits and reads as not held.
- **`BlobLocality` written into a row** under validation would diverge between members; it is documented as not for writes.
- **Old plugin.** A table declaring `blobref` cannot be opened by a plugin that predates the type (§Compatibility). Inspection.
