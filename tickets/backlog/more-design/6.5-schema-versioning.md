# Schema Versioning for Multi-Node

description: no explicit schema version tracking; schema cache can become stale when another node updates the schema
prereq: none
files:
  - packages/quereus-plugin-optimystic/src/schema/schema-manager.ts
----

The new Lens system in Quereus v4 should allow us to elegantly handle schema versioning.  It gives a mechanism for multiple versions of an app to co-exist simultaneously during a distributed migration with data converted both ways.  The parts we need to fill in are around how distributed authorization of schema versions works within an engine.

## Evidence: the stale schema cache has already produced a correctness bug

While investigating `fix/secondary-index-update-never-reaches-the-sibling` (2026-08-13) the
`SchemaManager.schemaCache` staleness named in the description above was measured, not just
suspected: on a two-node mock mesh, node B's `addIndex` read the schema through the cache and
got a copy *without* an index node A had already persisted, while a direct read of the
`tree://optimystic/schema` collection at the same moment showed the index. Because `addIndex`
then persists the whole record built from that stale read, a concurrent index addition can be
dropped from the catalog outright.

The narrow, actionable correctness fix (bound the cache on mutating paths; make the
`indexes` write-back a union rather than an overwrite) is filed as
`implement/schema-catalog-index-list-is-lossy` and does **not** wait on this design ticket.
This ticket remains the place for the versioning design itself.
