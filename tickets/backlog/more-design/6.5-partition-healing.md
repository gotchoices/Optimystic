# Partition Healing and Reconciliation

description: partition healing is designed (docs/transactions.md) but not implemented; divergent state after a network partition requires manual intervention
prereq: 2-2pc-state-persistence
files:
  - docs/transactions.md (lines 1776-1880, design spec)
  - packages/db-core/src/transaction/coordinator.ts
  - packages/db-p2p/src/cluster/cluster-repo.ts
difficulty: hard
----

The partition healing protocol is designed in `docs/transactions.md` with three classifications — Behind (normal sync), Ahead (tentative), Forked (conflict) — but none of the reconciliation logic is implemented. Currently the system relies on normal sync after partition recovery; if both sides committed divergent transactions during the partition, the resulting conflict requires manual intervention.

The super-majority (75%) threshold prevents both sides from committing in a 50/50 split, but asymmetric partitions (e.g., 80/20 where 80% side commits) can still produce divergent state when the 20% side reconnects.

## ClusterMember integration points

`ClusterMember` already accepts a `PartitionDetector` (held as `_partitionDetector` and on the `ClusterMemberComponents` interface in `packages/db-p2p/src/cluster/cluster-repo.ts`) but does not yet consume it. When this ticket is picked up, the three plausible consumption points are:

- `processUpdate` / `handlePromiseNeeded` — reject incoming promises during a suspected partition rather than approving them, to avoid creating divergent committed state on the minority side.
- `propagateIfNeeded` — skip propagation during partition (mirrors the gating used in `packages/db-p2p/src/transactions/block-transfer.ts:59,84`).
- Status reporting — surface `detectPartition()` to coordinators so they can fall back to a slower / quorum-locking mode.

To consume the detector, rename `_partitionDetector` back to `partitionDetector` (and add `private readonly` to the constructor parameter) at that time.

## Arm: a forked collection has now been observed in the field (2026-08-30)

Until now this ticket described a hazard the design anticipates but nobody had seen. A downstream
project (`sereus`) has now produced one. Its two machines write rows under one shared secondary-index
value; each machine then permanently sees only its own row. The `collection:lineage-divergence`
diagnostic in `db-core` fired on that workload and named the split:

```
collection:lineage-divergence id=default/FormationUsage/index/FormationUsageByToken rev=1 held=63cJ50MoBCietBFJBvxWeQ read=vPYEKDif1s1ItefiE-5DQw
collection:lineage-divergence id=default/FormationUsage/index/FormationUsageByToken rev=2 held=W0vdcSKMif20MB6UYylCjQ read=NEJ50gSY7mr9KGV5QUKQDw
collection:context-not-lowered id=default/FormationUsage/index/FormationUsageByToken held=4 read=3
```

Two different actions occupy revisions 1 and 2 of one collection, and the guard that refuses to move
a collection backwards (`Collection.advanceContext`) then declines the lower revision storage offers,
so the split is permanent with no error raised. That guard is correct in isolation; on a forked
lineage it is what seals the fork. This is the "Forked (conflict)" classification, reached without a
network partition ever being declared, and with no reconciliation to run.

Two consequences for this ticket:

- **Reconciliation now has a concrete first case to satisfy.** Whatever this ticket builds has to be
  able to take two collection copies whose committed lists name different actions at the same
  revisions and produce one. The "Forked" branch is no longer hypothetical.
- **It also owns a behaviour decision that is currently parked in code.** The class doc on
  `Collection.advanceContext` (`packages/db-core/src/collection/collection.ts`) says the seam
  deliberately makes no behaviour change and that, if the line is ever seen firing in the field,
  someone should decide then whether a divergence should also drop the read cache — and whether to
  keep re-reporting per refresh rather than once per discovery. It has now fired. That decision
  belongs here, alongside reconciliation, not as a standalone change to the diagnostic.

A separate, more mundane cause for the same symptom is being pursued in
`implement/coordinator-mutates-collections-outside-their-latch`: the commit path takes no collection
latch, so a concurrent refresh can make a commit record a revision number storage never assigned —
producing this exact fingerprint on a single machine, with no partition involved. If that turns out
to explain the capture above, this arm is still worth keeping (the design gap is real), but the
observation stops being evidence for it.

## Arm: sync now fails fast on a wedged revision view — reconciliation is still owned here (2026-09-06)

`implement/sync-fail-fast-on-a-stalled-revision-view` changes `Collection.sync` to stop with a named
`SyncRevisionStalledError` once refreshing has twice failed to move the collection past a revision a
responder confirmed it already holds, instead of burning its full ~21 s retry budget. That planning
pass considered — and rejected — the alternative of having sync adopt the responder's revision and
retry, and the reason is a constraint this ticket should know about:

**Adopting a bare revision would be a silent overwrite, not a merge.** `StaleFailure.staleAt` carries
a number, not content. A client that jumped its revision would still declare the `baseRev` it
actually read, and `ClusterMember`'s digest guard checks an `updates`-only block **only when the
member's local base revision equals the declared `baseRev`**
(`packages/db-p2p/src/cluster/cluster-repo.ts:1646-1739`) — so every member holding the newer base
would *abstain* rather than reject, and the write would land on top of a history it never saw. Any
reconciliation this ticket builds has to supply the content half, not just the number.

Two consequences for this ticket:

- **The fast failure is a floor, not a solution.** Whatever healing lands here should be able to take
  a collection that has stalled this way and produce forward progress. Until it does,
  `SyncRevisionStalledError` is what callers get.
- **The parked `advanceContext` cache-drop decision is now more visible, not less.** Sync fails
  loudly at the seam where the divergence bites, so an operator hitting it will look at
  `collection:lineage-divergence` next. Deciding whether a divergence should also drop the read cache
  (and whether to re-report per refresh) still belongs here.

The separate *lag* half — a refresh that can insist on being answered by a peer no older than a
revision it has already been told about — is filed as `backlog/feat-refresh-can-demand-a-revision-floor`.
That one helps a client that is merely behind; it does not help a genuinely forked lineage, which is
this ticket's "Forked (conflict)" branch. The boundary between the two is worth stating explicitly
when either is picked up.

## Arm: the partition policy has to be stated in terms of a declared denominator (2026-09-14)

A design review of `blocked/writer-and-servers-disagree-on-where-a-block-lives` traced "what happens in a partition" through the code and found the policy is implicit and, in one respect, self-defeating. Recording the reasoning here so the eventual design starts from it.

**What the threshold already implies.** With cohorts drawn by hash from the whole network, a partition that isolates a fraction f of the nodes leaves roughly f of each cohort on the island and 1−f on the mainland. The promise bar is ceil(0.75 × K). So the mainland can commit only while f < 0.25, and the island never can. Between f = 0.25 and 0.5 *neither side* commits: a sea-cable cut that severs a third of a large network stalls writes everywhere, not just on the island. That is the Byzantine-fault-tolerance boundary (less than a third faulty) applied to reachability, and it is a defensible, principled CP stance, but nobody has written it down, and it is the reason the threshold cannot be lowered (the admission-fraction inequality in `cluster-repo.ts` requires it above two-thirds).

**Where the stance leaks.** `allowClusterDownsize` (default on) shrinks a cohort to whatever peers are visible, and the quorum denominator follows. A node that sees only its side of a partition therefore builds a smaller cohort, meets the bar within it, and commits. `correctness.md` already calls partition write-blocking "nominal" without a declared `assumedClusterSize`. So the actual policy today is: safe only if the operator declared the size, otherwise split-brain with a signature set that looks legitimate. The membership-binding digest pins the peer set per record but does not stop a downsized record being formed in the first place.

**The rule to adopt.** The denominator for a cohort is its declared size (`feat-declared-membership-feeds-cohort-assembly`), or, on an open network without a declaration, the configured cluster size with downsizing forbidden for quorum purposes. Downsizing may still shape *placement* on a small network; it may never shape the *bar*. Under that rule: the side with at least three-quarters of a declared cohort commits, the other side stalls, and a stall is reported as such (the durability class from `commit-result-carries-durability-class`, plus the existing `BlockPossiblyStaleError` on reads), which is the "signal lack of convergence in the meantime" requirement.

**Liveness across time, not space.** The stalled side is where the tentative lane belongs (`feat-long-lived-pend-completes-as-members-appear`): a pend recorded durably on the island completes when the cable is repaired and the declared cohort can sign, or is refused as stale if the mainland moved its read set. For a three-phone group the "island" is one phone and the same mechanism gives progress without ever lowering the bar. The healing table in this ticket (Behind / Ahead / Forked) then only has to handle the Forked case for state committed under the *old* downsizing behaviour, or by applications that opted into a convergent lane, which is the subject of the next arm.

**Convergent lane versus serializable lane.** The general result (Bailis et al., I-confluence; Li et al., RedBlue consistency) is that an operation can be committed without coordination and still converge if and only if its invariants are preserved under merge. Uniqueness, foreign keys and non-negative balances are not; counters, grow-only sets and last-writer-wins fields are. So convergent replication and serializable transactions are at odds *per operation*, never *per system*: a collection or operation is declared either convergent (commits locally, merges deterministically, no quorum) or serializable (the lane above). Optimystic already has the seam for the convergent lane in `Collection.filterConflict`, and sereus's cadre-consistency design is the application-layer half. The partition-healing design should make the lane a first-class declaration on the collection, so "which lane" is never inferred from behaviour.

## Arm: what a two-machine group does today when one machine is away (2026-09-15)

Phase 5 of `packages/db-p2p/test/small-deployment-lifecycle.integration.spec.ts` stops one of two machines, then writes on the other, using the documented two-machine configuration: default cluster size, `repairCorroborationClusterSize: 2`. It deliberately does not assert whether that write should be accepted, because that decision belongs to this ticket. It does report what happens, and over 16 runs the answer was not stable:

- **Accepted in 11 runs, after 11–31 seconds.** The surviving machine retries against the absent one until its routing view drops it. It then commits alone (`commit:solo-cohort` with `cohortSize: 1, soleIsSelf: true`) and reports plain success. Until the other machine returns, the write exists on one machine only.
- **Refused in 5 runs, after 8–12 seconds,** with `Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)`. In the runs that checked, the refused row never appeared on either machine afterwards.

Which one happens depends on whether the survivor still counts the absent machine as a cohort member when the write reaches its commit step. It is a race between the write's retries and the routing table forgetting a peer, not a rule anyone chose. That is the downsizing leak the previous arm describes, observed at the smallest size. Whatever this ticket decides for a lone survivor, the outcome should be deterministic, and phase 5 is where to pin it once decided. In every run, every accepted write was readable on both machines once both were back.

## Arm: over a relay, the same write is refused every time, in about a second (2026-09-15)

Phase 3 of `packages/db-p2p/test/two-phones-over-relay.integration.spec.ts` runs the previous arm's scenario, with the same configuration, between two phone-shaped machines, so every stream between them crosses a circuit relay. There the outcome was stable: **refused in all 7 runs, after 955–1144 ms**, with the same `Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)`. The refused row read as absent on both machines once the absent one returned.

Decision (maintainer, 2026-09-15): **do not pin this rule with a point fix.** The broader fix is the CRDT-style sync layer in [crdt-sync.md](../../../docs/crdt-sync.md) — a grow-only log of signed transactions replayed deterministically, so that transactions on both sides of a gap proceed in step and merge rather than one side having to be refused or accepted by a race. That design is not finished. Until it is, the near-term priority is getting the core concepts working, and the two phases below stay as they are: they observe the outcome, report it, and assert only that whatever was acknowledged is readable on both machines once both are back. Whoever finishes the design owns pinning them. A reviewer who finds the non-determinism and wants to close it should add evidence to this ticket rather than choose a rule at the call site.

Why it differs from direct TCP is inferred, not measured. A dial to the absent phone fails at once, because the relay answers that the phone holds no reservation. So the write's retries are spent within a second, long before the survivor's routing view forgets the peer. If that is right, a lone survivor's admission outcome depends on the transport as well as on timing. That is one more reason this ticket should state the rule rather than let it emerge; phase 3 of the relay spec is the second place to pin it.

## Arm: a party that writes before it has ever synced forks every collection it touches (2026-09-16)

Evidence from the diagnosis of `fix/a-second-party-cannot-read-the-messages-it-just-wrote` (a sereus device report, reproduced headlessly on the sereus side over direct connections; recorded there as `implement/3.1-joining-machine-writes-before-first-sync-fork-tables`). No partition was declared and both parties were running.

A second party joined a two-party group and wrote a member row and a message at once, before any connection to the first party had come up. With no serving partner in its routing view, `findCluster` returns a self-only cohort; `CoordinatorRepo.fetchBlockFromCluster` takes its solo exit and reports the missing collection header as a *confirmed* absence (its own comment notes a self-only cohort is also what a node sees while a real peer is still mid-identify); `Collection.createOrOpen` therefore invents the collection and the write commits alone. When the parties connected, the two independently created copies of `Message` and `Member` shared one collection id. Observed: the joiner's committed message disappeared (the founder's copy won) and the member table stayed split for the whole 30-second window. Both writes had reported success, and a committed (non-refreshing) read confirmed the row was really gone, not hidden.

`packages/db-p2p/test/two-party-cohort-is-collection-independent.spec.ts` pins the routing half: in a two-party group every block of every collection resolves to the same cohort, and before identify every block resolves to self alone — so this is not one collection routing differently from another.

What this adds to the ticket: the "Forked" case does not need a partition, only a node that has never seen a collection deciding alone that it does not exist. Optimystic cannot tell a founding machine (which legitimately creates alone) from a joining one, so sereus is gating writes until a joiner has synced once. Reconciliation here still has to merge two copies created independently from nothing — the simplest possible fork, and a good first case for the CRDT sync design.
