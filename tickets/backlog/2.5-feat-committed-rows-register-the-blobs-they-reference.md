# Committed rows register the blobs they reference

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). A blob is kept on another machine's behalf only while committed state references it (§Design principles, "The database decides what is alive"), so the database must be able to answer "does any committed row reference this blob?" for any blob, cheaply, on a machine that knows nothing about the application's schema. This ticket builds the two ordinary tree collections that answer it, in `packages/db-core`, with no SQL: the **reference tree** and the **scope registry** (§Registering references). The SQL plugin (`feat-sql-columns-hold-blob-references`) and an application writing collections directly both use what is built here.

## Requirements

**Reference tree.** An ordinary `Tree` collection whose entries are keyed by a blob reference (`BlobRef`, from `feat-blob-references-and-verified-piece-trees`) and then by a **referrer key**: an opaque string supplied by the caller that names what holds the reference (for a SQL table, the framed primary key and the column name, chosen by the SQL ticket). The key encoding must keep every entry of one reference contiguous and in front of no other reference's entries: a range read for reference `R` returns exactly `R`'s entries, even if some other reference's text began with `R`'s text. References compare as strings (they have exactly one accepted spelling), so the encoding frames the reference rather than relying on all references having one length. The entry's value carries nothing the key does not already say; it exists so the entry exists.

**Staging helper.** One function that stages, into a reference tree the caller has opened, an **add** (reference, referrer) or a **remove** (reference, referrer). It stages through `Tree.stage` and never syncs: the entries commit or roll back with whatever the caller commits the tree with — a `TransactionCoordinator` commit spanning the caller's collections, a `sync`, or an offline queue entry. Requirements the builder must not get wrong:

- **Replay-safe.** Conflict replay re-runs staged actions against the newest committed state (docs/internals.md, "Conflict replay must read at the revision it is adopting"). Because the key includes the referrer, an add is an upsert of a fixed key and a remove is a blind delete of a fixed key, so re-staging is idempotent and two writers adding the same reference from different referrers never touch the same key. Entries carry no guard, as index-tree entries carry none; whoever owns the referrer's own row (the SQL table's main tree) is what refuses a racing change to the same referrer. An unguarded element is also not counted in the offline queue's already-applied tally, which is the intended behaviour (internals.md, "Three variants accept a change a rival already made").
- **Deterministic.** The operations staged are a pure function of the (reference, referrer, add-or-remove) inputs. Under transaction validation a member re-derives them and must produce the same operations (§Registering references, "Under transaction validation").
- **A change of reference is a remove and an add** staged by the caller; the helper does not read the old value.

**Reader.** Given a reference tree and a list of references sorted ascending, answer which are listed, in one ordered pass over the tree (no read per reference). The answer also says whether it is **certain**: the tree was refreshed to the latest committed state first, and no read in the pass threw `BlockUnavailableError` or `BlockPossiblyStaleError`. A read that throws is not swallowed: it is logged and makes the answer uncertain. A reference tree that reads as authoritatively absent (`Tree.open` resolves `undefined`) is an empty tree, certainly. The reader is what `feat-unreferenced-blobs-are-reclaimed` relies on, so "certain" must never be reported for an answer the read path flagged.

**Scope registry.** One `Tree` per network at a well-known collection id, exported from db-core as a constant, chosen so it collides with no id the plugin uses (the plugin's catalog is `optimystic/schema`). Its entries are keyed by reference-tree collection id.

- **Register** a reference-tree id: idempotent; staging-only like the helper above, so a caller may carry it in the same transaction that creates the reference tree, plus a convenience that stages and syncs on its own. Two machines registering the same id at the same time must both succeed: stage it with the `absentOrEqual` guard over an entry whose value is a fixed function of the id, so the loser of the race replays it as already applied rather than being refused.
- **Enumerate**: every registered id, read with the same certainty report as the reader.
- **Unregister**: removes a reference tree's id, staged into the caller's transaction like the other writes, and idempotent (removing an id that is not listed succeeds). It is what a caller uses when the collection that held the references is dropped; the blobs that tree listed then count as unreferenced there and are reclaimed by the ordinary rule. Unregistering does not delete the reference tree.

**Open semantics** (docs/internals.md §Collection Header Blocks). Every read path — the reader and enumerate — opens with `Tree.open`, so a registry or reference tree that has never been written reads as empty and is never invented. Only the staging paths open with `Tree.createOrOpen`, since a first write is when the collection is supposed to come into existence.

Export everything from `packages/db-core/src/index.ts`; modules inside the new code import each other directly, never through a barrel (internals.md, Common Pitfalls §6).

## Edge cases and interactions

- **Prefix references.** Two references where one's text is a prefix of the other's: the range read for the shorter returns none of the longer's entries. Test on the key encoding.
- **Same reference, many referrers; same referrer, many references.** Each (reference, referrer) pair is one entry; removing one leaves the others. Test.
- **Add then remove in one transaction, or remove of an entry never added.** The second is a blind delete and the tree ends without the entry; a remove of a missing entry stages nothing visible and does not throw. Inspection plus one test.
- **Conflict replay.** Two handles each stage adds for different referrers of the same reference and commit concurrently: both land, and replay re-stages identically. Test on two handles over one transactor, the shape `packages/db-core/test/two-handle-collection-fork.spec.ts` uses.
- **Concurrent registration.** Two handles register the same id and commit concurrently: both commits succeed and the registry holds one entry. Test.
- **Rollback.** A caller that restores its snapshot drops the staged entries with its other staged actions (`Collection.restorePending`); nothing reaches storage. Inspection.
- **Reader certainty.** A read that throws `BlockPossiblyStaleError` yields an uncertain answer with no reference reported unlisted on its evidence. Test with a transactor that flags one block.
- **Below-floor answers.** `TransactorSource` returns a block older than the log says, unflagged, when no reachable machine can meet its floor (the accepted tradeoff at `TransactorSource.mayRetain`). The reader cannot see that through an exception. docs/blobs.md §Lifetime counts such an answer as uncertain, so the reader must report it: its certainty report is "not certain" whenever any block it read was answered below its floor, using `describeServed` or the equivalent. Test with a source that serves one block below its floor.
- **An absent answer that rested on no consult** (a node alone in its routing view, internals.md "A block read has three answers"): telling it apart is owned by `feat-unreferenced-blobs-are-reclaimed`, which may extend the reader's certainty report.
- **db-core stays network-free.** `packages/db-core/test/no-fret-import.spec.ts` stays green.
