# A signed validity marker on reject votes

## Why

Block-then-escalate (`docs/right-is-right.md` §Design of Record) blocks a transaction when any cohort member rejects it *on validity*, and ejects whichever side a ruling goes against. Today every refusal a member signs that is not an expiry or a `held` is the same `reject` vote with free-form prose (`invalidVerdict` / `voteFor` in `cluster-repo.ts`): a stale revision, a membership-admission refusal, a content-digest disagreement, a checker crash and an operations-hash mismatch are indistinguishable to the coordinator. Reading prose for control flow is forbidden here, so the classification has to be structured, and it has to be **signed** — a coordinator must not be able to turn a stale reject into a dispute, or strip the classification off a genuine one without dropping the whole vote.

This ticket adds the marker and nothing that acts on it beyond the evidence the coordinator already records. Later tickets (`dispute-commit-path-block`, `dispute-post-commit-challenge`) act on it.

## Classification (from the design of record)

| Refusal | Class | Marked? |
|---|---|---|
| `Re-execution failed`, `Operations hash mismatch`, `Tampered transaction stamp`, `Missing client signature`, `Invalid client signature` (TransactionValidator) | validity | yes — with the operations hash the member computed when it has one |
| `Stale read`, stale revision / stale commit, pending-conflict, slot hold | transient | no |
| `Transaction expired` (validator) and the member's own expiry verdict | clock | no |
| `Unknown engine`, `Schema mismatch`, `Unsupported operations-hash format`, `PEND_NOT_VALIDATABLE`, `VALIDATOR_FAULT`, membership-admission refusals, `BASE_DECLARATION_DISAGREES`, `CONTENT_DIGEST_MISMATCH`, unavailable-block refusals | incapacity / structure | no |

## Shape

- `PendValidationResult` (db-core) gains a structured class on failure, e.g. `{ valid: false; reason?: string; validity?: { computedHash?: string } }` — present only for the validity class. `TransactionValidator` sets it on exactly the five refusals above (`computedHash` on the operations-hash mismatch; absent when re-execution failed outright). `checkPendValidation` never sets it (both of its own refusals are incapacity), and passes a checker's `validity` through untouched.
- `PromiseVerdict`'s `'invalid'` arm carries the same optional `validity`; `voteFor` copies it onto the reject vote.
- `Signature`'s reject variant gains `validityEvidence?: { computedHash?: string }`, folded into `clusterVoteSigningPayload` as its own encoding (e.g. `reject-invalid:<json [computedHash|null, rejectReason|null]>`), exactly as `expiredAt` is. A vote cannot be both an expiry vote and a validity vote — make that unrepresentable in the type (split the reject variant), not a runtime check. A vote with neither field encodes byte-identically to today.
- **Engine health.** A member whose own engine is flagged unhealthy (`EngineHealthMonitor.isUnhealthy`) signs its validity refusals *without* the marker, so they count as ordinary rejections and cannot block another writer. `ClusterMember` takes an optional `isEngineHealthy` hook; absent means healthy. (The monitor lives in `DisputeService`; wiring the hook at the composition root is part of this ticket only if the service is already constructed there — otherwise leave the hook unsupplied and say so in the handoff.)
- `ClusterCoordinator.executeTransaction`'s dispute-marking branch builds `disputeEvidence` from **marked** rejects only, which resolves the existing NOTE about expiry votes landing there. Counting (`rejectionCount`, thresholds, `ValidatorRejectionError`) is unchanged: a marked reject is still a reject.

## Edge cases & interactions

- **Tampering.** Adding, removing, or changing `validityEvidence` on a signed vote must fail `ClusterMember.verifySignature` — verified by a test (below).
- **Old encodings.** A vote without the field verifies exactly as before (by inspection: the payload function's unmarked branch is untouched).
- **Expiry precedence.** The member's expiry verdict is decided before validation (`evaluatePromise`), so an expired record never reaches the validator; the validator's own `Transaction expired` refusal stays unmarked anyway.
- **StorageRepo tier.** `StorageRepo.pend` also runs `checkPendValidation`; it ignores `validity` (storage has no vote). By inspection.
- **Equivocation.** `detectEquivocation` compares vote *types*; a marked and an unmarked reject from one member for one record are the same type. Decide whether a member that re-sends its vote with a different marker is equivocating; the member signs once per record, so this cannot arise from an honest member — treat a differing marker on a re-delivered reject as equivocation and say so in a comment.
- **Abandonment and race resolution** read only `type`; unaffected (by inspection).

## Tests

- One signing round-trip test in the existing vote-signing spec: a marked reject verifies; the same signature with the marker removed, added, or its `computedHash` altered does not.
- One table-driven test pinning the class of every `TransactionValidator` refusal (the mapping has real branching and is the contract the dispute trigger relies on).
