# Blob pieces move between machines

A blob is a large immutable value stored as 256 KiB pieces named by their SHA-256 (design: [docs/blobs.md](../../docs/blobs.md)). The local piece store and the local half of `node.blobs` come from `feat-a-node-stores-blob-pieces`; this ticket adds the network half: a protocol that lets a node ask another member of its network for pieces, and the client that uses it so that `read`, `fetch` and `stat` work for a blob whose bytes are on another machine. It is what turns "this node has a reference" into "this node can get the bytes", without the bytes ever entering a transaction.

## Requirements

**Protocol.** One new protocol, `${protocolPrefix}/db-p2p/blob/1.0.0`, built by a `buildBlobProtocol(prefix)` beside `buildBlockTransferProtocol`, registered only through `registerProtocolHandler` (the single-site spec enforces this) and added to the `services:` map in `libp2p-node-base.ts` with `...inboundAuthorization` spread into its init like the four database services. It is **not** added to `preparedStreamProtocols`: `PreparedStreams` resends a request once on a failed prepared stream, which assumes one small request and one small answer.

**Framing** (docs/blobs.md §Moving pieces between machines). Frames are length-prefixed. The first frame in each direction is a small JSON header; a piece is one frame of raw bytes, never base64 or JSON. This ticket fixes the framing for all four request kinds (`stat`, `get`, `announce`, `held`), including the header shape that names the kind, and implements `stat` and `get`; `announce` and `held` are answered by `feat-a-referenced-blob-is-copied-to-its-cohort`, and until then the service answers them as a node that does not accept blobs would. The decoder caps a header frame at a small size and a piece frame at the 1 MiB piece limit the verified-tree rules set, so a peer cannot make the reader allocate more.

- `stat`: a list of references; answer per reference `whole`, `partial` or `none`, from local blob records only.
- `get`: up to 16 piece CIDs; answer a header saying which are held, then one raw frame per held piece in the order asked. A request naming more than 16 is refused.

**Client.** A fetch works out which pieces it still lacks (top down from the reference, using the verification rules of `feat-blob-references-and-verified-piece-trees`), asks a holder for up to 16 at a time, verifies each piece against the CID that named it and stores it as soon as it arrives, so an interrupted fetch keeps every piece already stored and resumes by asking only for what is still missing, from the same peer or another. Candidate holders are the blob's cohort (`findCluster` on the blob's routing key) and any peer that answered `whole` or `partial` to a `stat`, filtered by the network membership predicate (`admittedBy`); a node never fetches from a peer the predicate refuses.

**Deadlines follow progress, not size.** A `get` has no total time limit. Both ends abandon the stream when no bytes have moved for one `responseTimeoutMs` of the declared link (`LinkDeadlines`), measured between any two chunks of bytes, not between whole pieces. The sender awaits the stream's `drain` event whenever `stream.send` returns false, and the same no-progress limit bounds that wait; it never ignores the result the way `cohort-topic/stream-util.ts` notes its own sends do. A dead path fails within one timeout; a slow one finishes.

**Limits** (§Other traffic is not held up). Background fetching uses at most one `get` stream per peer and a small fixed number per node; a read the application is waiting on is scheduled ahead of background work. A holder may refuse a peer that is over its allowance. The constants live in `protocol-limits.ts` beside the existing ones.

**Service surface** (§The node's blob service). `read` fetches pieces as the read reaches them and keeps them under a `cached` hold; `from: 'here'` never fetches; `waitMs` keeps a read retrying while no reachable holder has a piece yet, and without it the read fails at the first piece nobody reachable holds. `fetch` brings the whole blob here. `stat` with `probe` asks the cohort, which is what separates `elsewhere` from `unknown`. Failures are `BlobUnavailableError` with reason `not-here`, `not-held`, `peers-unreachable` or `cohort-unreachable` (mirroring `BlockUnavailableReason`), `BlobCorruptError`, and `BlobRefError`. `onProgress` reports bytes and pieces fetched per reference.

**Hostile bytes.** A piece that fails its hash is discarded, never stored, the sending peer is reported with `PenaltyReason.InvalidRestoration` (the reason the repair paths use for unverifiable content; the stream is authenticated, so the fault is attributable), and the client asks another holder. `BlobCorruptError` is raised only when no holder supplied verifiable bytes, or the tree itself is malformed.

**Logging.** Debug namespaces under `optimystic:db-p2p:blob-*` (service and client), following docs/debugging.md: one line per request served or sent, per peer penalized, per fetch abandoned for no progress. Add the namespaces and their lines to docs/debugging.md.

**Measurement.** The last paragraph of docs/blobs.md requires measuring time per MB and bytes on the wire for the GitHub #63 shape (a 1 MB and a multi-MB file written on one node and read on another) and stating the result in that paragraph. This ticket does that, on loopback at least, and replaces the "expected cost" sentence with the measured numbers and how they were taken.

## Edge cases and interactions

- **Inbound gate.** A peer the `authorizeInboundStream` predicate refuses gets a reset before any frame is read (test: one denied stream, nothing decoded).
- **Membership on the fetch side.** A cohort member the membership predicate refuses is never dialed (inspection plus one assertion at the candidate filter).
- **Wrong bytes.** One holder serves a corrupted piece, another the right one: the read succeeds, the bad piece is never stored, the bad peer is penalized once (test).
- **Header lies.** A holder says a piece is held and never sends it: the no-progress limit ends the stream and the client moves on (test with a stalled fake stream).
- **Full send buffer.** `send` returns false; the sender waits for `drain`, and a receiver that never reads makes the sender give up after one timeout rather than buffer without bound (test at the sender).
- **Interrupted fetch.** Kill the stream half way: the next fetch asks only for missing pieces (test, counting pieces requested).
- **Stock relay.** A circuit relay with stock limits resets a relayed stream after 128 KiB, under one piece; the fetch fails with pieces kept, reports `peers-unreachable`, and resumes on a direct path (inspection; docs/blobs.md §Relays already accepts this).
- **Concurrent reads of one blob.** Two reads of the same reference share one fetch per piece, and a piece is stored once (assertion at the scheduler).
- **Foreground over background.** A read waits behind at most the piece in flight, not a queue of background `get`s (inspection of the scheduler).
- **Older peers.** A peer whose protocol list lacks the blob protocol is not asked; dialing it would fail the protocol negotiation anyway.
- **A partial holder.** A peer answering `partial` is asked; pieces it lacks come back as "not held" in the header and are asked of someone else.
