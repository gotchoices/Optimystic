# Unreferenced blobs are reclaimed

A blob is a large file stored outside transactions and kept on a machine while some hold names it (docs/blobs.md §Holds). After `feat-a-referenced-blob-is-copied-to-its-cohort`, responsible machines take `responsible` holds on blobs that committed state references, but nothing ever releases one when the references go, and `cached` copies kept for reads grow without bound. This ticket adds the two ways a hold ends without an owner releasing it: a periodic, conservative check that releases `responsible` holds on blobs no committed row references, and a budget that evicts `cached` copies. Releasing the last hold makes the blob's pieces eligible for the piece sweep.

**This is the first code in the repository that deletes replicated data on a schedule.** Nothing reclaims block storage today: the node's `gcEligibleBlocks` set in `libp2p-node-base.ts` is filled when a block's replication is confirmed and is never swept. That is the argument for every conservative rule below: a wrong decision here deletes a file that a committed row still names, on each holder independently, with no other copy to repair from.

## Requirements

**The reference pass** (docs/blobs.md §Lifetime). Periodically a node passes the references it holds under `responsible` against every reference tree listed in the scope registry: one ordered range pass per reference tree over the sorted held references, not one read per blob. A blob listed by any tree is referenced. A blob listed by no tree in a pass that counts (next paragraph) is recorded as unreferenced with the pass's time, in its blob record so the result survives a restart. A blob recorded unreferenced and found unreferenced again by a counting pass at least the grace period later (7 days by default, a node option) loses its `responsible` hold. A blob found referenced by any pass has its unreferenced mark cleared. Nothing a peer sends deletes or marks anything; the decision is the holder's own reading of committed state.

**Only a certain answer counts.** A pass counts toward reclaiming only when every read it made — the scope registry and each reference tree — was authoritative and confirmed current. These count as "still referenced" for every blob the pass covered:

- any read that throws, including `BlockUnavailableError` (whatever its reason) and `BlockPossiblyStaleError`;
- a scope registry that cannot be read or opened, or reads as absent while this node holds any `responsible` blob (a registry that does not exist cannot have listed the references that caused the holds);
- a read in which any block was answered older than the log names it (a below-floor answer, which the read path returns without throwing; the db-core reader from `feat-committed-rows-register-the-blobs-they-reference` reports it as not certain);
- a pass run while `PartitionDetector.detectPartition()` is true;
- a read that rested on asking nobody, unless the node is alone by the test the offline queue's reachability gate applies (`KeyNetworkCohortReachability` in `packages/db-p2p/src/network/cohort-reachability.ts`: no serving member the key network remembers is missing, no configured bootstrap peer is still awaited, no identify exchange in flight). docs/internals.md (*A block read has three answers*) describes a node whose routing view contains only itself: it serves its own emptiness as an authoritative absent, unflagged, for collections it does not hold. A node that merely cannot see its cohort must not act on that; a deployment that really is one machine must still be able to reclaim. So the pass must be able to tell an answer a cohort confirmed, an answer from a node that is alone by that test, and an answer from a node that asked nobody for any other reason, and count only the first two. If the read path does not expose that distinction, adding it is part of this ticket.

A reference tree that the registry lists and that reads authoritatively absent after a consult is an empty tree.

**Owed entries follow the same rule.** A writer whose cohort never fully holds a blob would otherwise keep it for ever. The pass also covers the node's owed entries, each against the scope the entry names: one whose scope has not listed the blob at two counting passes a grace period apart is deleted with its `owed` hold, and the drain stops announcing it.

**Holds interact as follows** (docs/blobs.md §Holds). A blob is deleted only when no hold names it: a `pin` keeps it whatever the pass finds, and losing `responsible` or `owed` only removes that hold. The piece sweep from `feat-a-node-stores-blob-pieces` then deletes pieces in no held blob's tree, since pieces are shared between blobs.

**Cached blobs** are evicted under a byte budget (a node option), least recently read first, using the last-read time in the blob record. Eviction removes only the `cached` hold. It needs no agreement and no reference check.

**Re-referencing is safe** by the argument in §Lifetime: a writer that commits a new reference either holds the bytes (it just `put` them and announces) or copied the reference from a row that was referenced when it was copied; the new entry is visible to the next pass, and the two-pass rule means no holder dropped the blob in between. The implementation must not weaken that rule (for example by reclaiming on a single pass at startup).

**A reference that outlives its bytes** (an old revision of a row read from history) reads as `not-held`, the ordinary `BlobUnavailableError`, never a missing-block error.

**Logging.** A debug line per pass (trees read, blobs checked, newly marked, released, and why a pass did not count) and per hold released, under the blob namespaces docs/debugging.md lists.

## Threats this answers

From docs/blobs.md §Threats: **making a live blob expire** requires committing the removal of its references; feeding a holder stale, empty or unavailable reads does not work, because only certain answers count, twice, a grace period apart. **Filling storage** is bounded because a holder keeps what it holds `responsible` only while committed state references it.

## Edge cases and interactions

- **Two passes too close together.** A second unreferenced pass inside the grace period changes nothing (test with an injected clock).
- **Referenced in between.** Unreferenced, then referenced, then unreferenced: the grace period restarts from the third pass (test).
- **One failing tree.** Ten trees read fine and one throws: the pass does not count for any blob (test).
- **A node that cannot see its cohort.** A node whose cohort view is only itself while a remembered member is missing or a bootstrap peer is still awaited: its reads do not count, so nothing is released (test).
- **A deployment of one machine.** A node alone by the reachability gate's test, holding the registry and trees itself: its passes count, and a blob unreferenced at two of them a grace period apart is released (test).
- **An owed blob whose row was deleted.** The cohort never fully held it; after two counting passes the owed entry and hold are gone (test).
- **Stale read.** A tree read that raises `BlockPossiblyStaleError` keeps every blob (test).
- **Pinned blob.** Unreferenced for two passes but pinned: the `responsible` hold goes, the bytes stay (test).
- **Restart between passes.** The first pass's mark survives a restart; the second pass after the grace period releases (test with a persistent store).
- **Shared pieces.** Two blobs sharing a piece; releasing one leaves the piece for the other (covered by the sweep's own tests; assert once here).
- **Cache budget pressure during a read.** A blob being read is not evicted mid-read (inspection of the eviction order).
- **Large holdings.** The pass is one ordered walk per tree; its cost is bounded by tree size, not blob count times tree count (inspection).

## Out of scope

The piece sweep itself and the hold records: `feat-a-node-stores-blob-pieces`. Copying, `responsible` holds and cohort changes: `feat-a-referenced-blob-is-copied-to-its-cohort`. Reference trees and the scope registry: `feat-committed-rows-register-the-blobs-they-reference`. SQL pins: `feat-sql-columns-hold-blob-references`. Reclaiming block storage (`gcEligibleBlocks`) is not part of this design.
