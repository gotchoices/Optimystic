# Every storage backend stores blob pieces

`feat-a-node-stores-blob-pieces` defines `IPieceStore`, the store for the immutable pieces a large file ("blob") is cut into (docs/blobs.md §The local store), with in-memory and filesystem implementations and a conformance suite. This ticket adds the implementation for each of the other three storage packages, so a NativeScript app, a browser and a React Native app can keep pieces on disk, and covers what the upgrade suite owes for the new stored data.

Each piece store lives beside its package's block store, in the same database, and follows the pattern the commit-proofs store set when it was added to every backend (`proofs` in `packages/db-p2p-storage-ns/src/sqlite-storage.ts` and `db.ts`, `packages/db-p2p-storage-web/src/db.ts`, `TAG_PROOFS` in `packages/db-p2p-storage-rn/src/keys.ts`). Unlike the proofs store it is not a logical store of `RawStoreDriver` and does not go through the block store's write group or journal: values are raw bytes, never JSON, and each piece is independent.

## Requirements

Every implementation passes the shared conformance suite from `feat-a-node-stores-blob-pieces`, including its reopen case, and is exported from its package's entry point beside the block store's constructor, opened over the same database handle the block store and key-value store share.

**NativeScript (`db-p2p-storage-ns`).** A SQLite table keyed by the piece's digest with a `blob` value column, created in the same schema setup as the other tables (`create table if not exists`, so an older database gains it on open). Flush commits and syncs as the block store's flush does, under the same durability the store reports. The `NOTE:` in `ns-opener.ts` says a result over 512 KiB crosses NativeScript 8's JNI bridge through a buffer that holds a scarce global reference. A 256 KiB piece is under that, which is what docs/blobs.md §Platforms and limits relies on; the reader's bound admits pieces up to 1 MiB, which another IPFS tool may produce, so each read is one piece, never a multi-row result, and that note gains a line naming the piece store.

**Browser (`db-p2p-storage-web`).** A `pieces` object store in the IndexedDB database, which raises `DEFAULT_DB_VERSION` from 3 to 4 and adds the store in the `upgrade` hook under the same `objectStoreNames.contains` guard the others use, so a version 1, 2 or 3 database gains only what it lacks and keeps everything it held. Values are stored as `Uint8Array`, which IndexedDB keeps natively. A put of many pieces uses one transaction per piece or a small batch, not one transaction across a whole blob, so a long stream does not hold a transaction open. Flush gives what the block store's flush gives in a browser, no more.

**React Native (`db-p2p-storage-rn`).** A LevelDB key range under a new tag byte in `keys.ts`, placed in the spacing the file describes (the tags are spaced so `tag + 1` bounds a range), never reusing or straddling an existing tag. Pieces are read with the bytes-returning `LevelDBLike.get` and `LevelDBLike.iterator`, never `getText` or `textIterator`: React Native is the one backend whose block store reads values as text, and piece bytes are not UTF-8. Writes use `batch().write(...)`, the only write the surface offers. `rn-leveldb` cannot sync today (`LevelDBLike.canSync`), so the piece store reports the same durability as the block store over the same handle and never claims more; under `classic-level` in tests, flush syncs.

**Storage use.** All three block stores already measure the whole database (SQLite's page count, the LevelDB scan over every key, the browser origin's estimate), so their figures already include the pieces. Each piece store still answers its own bytes used, measured over its own keys only, and the rule in `feat-a-node-stores-blob-pieces` decides whether the node adds it; the effect is that a piece is counted once.

**What `packages/upgrade-check` owes** (packages/upgrade-check/readme.md). Stored data gains a piece store and key-value namespaces and loses nothing (docs/blobs.md §Compatibility):

- The existing `fs` and `leveldb` fixtures, written by releases with no piece store, must still pass with the working tree's node configured with a piece store over the same location: the missing table, directory or key range is treated as empty, nothing older is moved, and no piece key or blob record is read as a block.
- The scenario writer gains a step that stores one multi-piece blob through `node.blobs.put`, run only for versions whose `node.blobs` exists (the writer must keep to the oldest fixture's API, so the step is gated on the version). The reader checks that the blob reads back whole and byte-equal after the restart. The first fixture with it appears at the first release that ships blob storage.
- The upgrade suite covers the `fs` and `leveldb` backends only; the SQLite and IndexedDB layouts are not covered there. The test that an existing browser database survives the version bump, and the handling of an upgrade blocked by another open tab, belong to `debt-indexeddb-version-upgrade-is-untested-and-unhandled`, whose arms now include version 4. The SQLite table needs no version step because its creation is idempotent; the NativeScript suite opens a database created without the table and checks it gains it.

## Edge cases and interactions

- An older database opened by this build: each backend gains the empty piece store and every block, proof, journal record and key-value entry reads as before. Covered by upgrade-check for `fs` and `leveldb`, by the NativeScript reopen test, and by the IndexedDB debt ticket for browsers.
- An older build opening a database this build wrote: it ignores the extra table, object store or key range. The browser case is different: a version 4 database cannot be opened by a build asking for version 3, which the browser refuses. That is a downgrade, outside the "older build's data opens" guarantee; stated in the package readme.
- Another tab holding the version 3 connection blocks the upgrade to 4: the open waits. Owned by the IndexedDB debt ticket.
- A React Native piece whose bytes happen to be valid UTF-8: still read with the bytes path. Inspection.
- The new LevelDB tag's range must not overlap the journal's or the key-value store's scans; a key-range test over a database holding every tag confirms each scan returns only its own keys.
- A 1 MiB piece on NativeScript: round-trips (the conformance suite's large case).
- A crash between a piece put and flush: the piece may be gone after restart; the record was never written because `put` had not resolved, and the sweep handles any orphan. Inherited from the conformance suite's reopen case.

## Out of scope

The piece store interface, the in-memory and filesystem stores, records, holds and the sweep (`feat-a-node-stores-blob-pieces`); moving pieces between machines (`feat-blob-pieces-move-between-machines`); everything above local storage (`feat-a-referenced-blob-is-copied-to-its-cohort`, `feat-committed-rows-register-the-blobs-they-reference`, `feat-sql-columns-hold-blob-references`, `feat-unreferenced-blobs-are-reclaimed`, `feat-large-blob-column-values-are-stored-out-of-line`).
