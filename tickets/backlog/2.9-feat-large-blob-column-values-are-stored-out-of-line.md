# Large blob column values are stored out of line

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). Its §SQL leaves plain `blob` columns untouched and names two further steps; this ticket is the first: "A `blob` value over a threshold is stored as a blob and its reference kept in the row, invisibly to SQL. This removes the size limit and most of the cost for existing schemas, but a row read then depends on a fetch." Today such a value is base64 in the row's JSON (`RowCodec.normalizeValue`), carried two to three times per transaction and limited to about 2 MB per transaction (§Why). After `feat-sql-columns-hold-blob-references` an application can get the savings by declaring `blobref` and calling the blob service itself; this ticket gives them to schemas that keep `blob`.

This ticket is less settled than the others in the chain. It states the intended behaviour and the parts that are hard; the plan must resolve each before an implement ticket is written, and may conclude that part of it should wait for the engine support in `quereus-reads-and-writes-a-range-of-a-large-value`.

## Intended behaviour

- On write, a `Uint8Array` value in a `blob` column whose length is above a threshold is stored with the blob service's `put` (pinned under the transaction, as `blobref` values are) and the row stores a **tagged reference** in its place. Values at or under the threshold stay inline, base64, exactly as today.
- On read, a tagged reference is turned back into the bytes, so SQL sees the same `Uint8Array` it wrote. Equality, comparison and functions over the column see bytes, never the reference.
- A tagged reference is maintained in the table's reference tree and pinned and announced exactly as a `blobref` value is (§SQL, `feat-sql-columns-hold-blob-references`), so it is copied, kept and reclaimed by the same rules.
- Old rows keep reading: an inline base64 value written by any earlier build decodes as it does now.
- No application change: the same `create table` and the same statements.

## The hard parts

**The encode path is synchronous and `put` is not.** `RowCodec.encodeRow` and `decodeRow` are synchronous and called from many sites; `put` hashes and stores asynchronously. The plan decides where the asynchronous step goes — most likely in `update()` before the row is encoded, replacing the value with its tagged reference so the codec stays synchronous — and makes sure every write site goes through it, including conflict-resolution paths that re-encode a row (`insert or replace`, primary-key moves, pre-write images used as `unchanged` guard expectations).

**A row read can block or fail.** `select *` over a table with a large value now needs that value's bytes. If they are not on this machine, the read waits on a fetch or fails with the blob service's typed "not yet" (`BlobUnavailableError`). The plan decides: whether a read waits and for how long (`waitMs`), how the failure surfaces as an SQL error, and whether a query that does not project the column can avoid the fetch (it can only if the decode is made lazy per column, which the vtab's row shape does not allow today). Committed reads (`committed.<Table>`) and live reads behave the same here.

**The whole value is still materialized.** A Quereus value cannot be a stream (`SqlValue` in `../quereus/packages/quereus/src/common/types.ts` is `string | number | bigint | boolean | Uint8Array | JsonSqlValue | null`), so writing a 100 MB value still hands the module a 100 MB array, and reading it builds one. This ticket removes the size limit and the per-byte encoding cost, not the memory cost; that needs `quereus-reads-and-writes-a-range-of-a-large-value`.

**The threshold.** SQLite's own measurement ("Internal Versus External BLOBs in SQLite", sqlite.org) found values under about 100 KB faster stored inline. Here the inline cost is higher (base64, JSON, two copies per transaction, consensus) and the out-of-line cost includes a separate transfer, so the number must be measured on the in-process mesh, not assumed. The plan states the measured crossover and makes the threshold a plugin option, possibly overridable per table with a tag in `declared-tags.ts`.

**The tagged form must be unambiguous.** It must be distinguishable from every value an old row could hold in that column. Under the `json` encoding a BLOB-affinity cell is decoded by turning any string into bytes from base64 (`denormalizeValue`), so a tagged reference cannot be a plain string. An object in the style of the existing `{ $bigint }` tag is the obvious shape, but a column whose stored cells can already be JSON objects must be ruled out or the tag must be one no earlier build could have written. The plan proves which, and adds an `upgrade-check` fixture so an earlier release's inline values are shown to keep reading (packages/upgrade-check/readme.md).

**Keys.** A value in a primary-key or index column is part of a tree key, framed as bytes. The plan decides whether such a column is ever stored out of line; the simple rule is never, since a key must be comparable without a fetch.

**Validation.** Under transaction validation a member re-executes the statements (`QuereusEngine`). A statement whose bound parameter is the large value carries that value in the validation payload, which would put the bytes back into the transaction. The plan decides how a validating member derives the same tagged reference without the bytes travelling — for example, a statement rewritten to bind the reference — or states that validated deployments keep large values inline.

## Edge cases and interactions

- A value exactly at the threshold, one byte over, and an empty value: which side each lands on is fixed and tested.
- An update that rewrites a large value to the same bytes: the same reference, so the reference tree and the `unchanged` guard see no change (references compare as strings). Test.
- Two machines inserting equal large values offline: the same reference, so the already-applied guard variants still recognise equal rows (docs/internals.md, "Three variants accept a change a rival already made"). Test.
- A row read whose blob is held nowhere reachable: a typed SQL error naming the column, never `Missing block`. Test with an unreachable holder.
- A table mixing old inline rows and new tagged rows: both read. The `upgrade-check` fixture covers it.
- Reading inside the transaction that wrote the value: the bytes are pinned locally, so the read never waits. Inspection.
