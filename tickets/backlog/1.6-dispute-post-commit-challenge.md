# Challenge a commit the dissent did not block

## Why

The pre-commit block only works on dissent that is in the record the coordinator merged. A marked validity reject can miss it: it arrived after the promise round closed, the coordinator left it out, or the member re-evaluated later. The design of record (`docs/right-is-right.md` §What blocks and what reverses) gives that member a post-commit challenge through the same escalation loop; a `rejecters-win` ruling originates the durable invalidation (`maybeInvalidate` → `onInvalidation`, which stays unwired on live nodes until `feat-dispute-subsystem-live-activation` and its anchoring gate).

`initiateDispute` was written for this ("Called by ClusterMember when it detects a disputed commit") and has no caller; this ticket gives it one and routes it through `driveDispute`.

## Specification

- **Trigger** (member side, disputes on): when this member applies a record at consensus (the apply path in `handleConsensus`), and this member's own promise vote for that record's pend was a **marked** validity reject, and the record carries no `approvers-win` ruling that verifies → call the dispute service's post-commit challenge for that record. The member's own vote is the one it signed (retain it per message hash for the record's lifetime if it is not already retrievable after the merge — a coordinator that omitted it from the merged record has, by definition, removed it from what the member receives).
- **Challenge** = `driveDispute(record, 'rejecters')` followed, on `rejecters-win`, by `maybeInvalidate` as today. `initiateDispute` becomes this path (no second loop).
- **Dedup**: one challenge per message hash (dispute id is derived from it, so a second rejecter's challenge joins the same dispute at the arbitrators); never for a record that carries a verified `approvers-win` ruling (the question was already settled before commit).
- **Not on the commit path**: the challenge is started off the apply path (`void`-prefixed, errors logged) — it must never delay or fail the member's apply.
- **Unhealthy engine**: no challenge (existing skip).

## Edge cases & interactions

- **Two rejecters, two challenges**: both drive the same dispute id; arbitrators answer once; at most one ruling per round (by the drawn-set threshold). By inspection plus the loop's own tests.
- **Coordinator-side `disputed` flag** (disputes-off path) is irrelevant here: the trigger is the member's own signed vote, not the flag.
- **Reversal stays dormant**: with no `onInvalidation` wired, a `rejecters-win` ruling still flips in-memory status and penalizes/ejects; nothing durable is written. Say so in the handoff.
- **Restart**: a member that restarts between applying and challenging loses the trigger (its retained vote is in memory). Accepted; note it at the retention site — the ruling's value is ejection and reversal, and a later read or a peer's challenge can still catch the transaction.

## Tests

- A member whose marked reject is absent from the record it applies starts a challenge (with an injected dispute port as the seam).
- A record carrying a verified `approvers-win` ruling is not challenged.
