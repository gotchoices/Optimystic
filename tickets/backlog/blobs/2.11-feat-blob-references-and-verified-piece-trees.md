# Verified reading of blob piece trees

docs/blobs.md is the design of record for blobs. `feat-blob-reference-format-and-tree-builder` defined references, piece ids, errors, limits, the hashing port and the builder in `packages/db-core/src/blob/`. This ticket adds the other side: given a reference and a way to get a piece by id (an injected `PieceSource`, so it stays network-free), yield the verified bytes of the whole blob or of a byte range, in order; expose the planner that says which data pieces a range needs, so the transfer ticket (`feat-blob-pieces-move-between-machines`) can ask for exactly those; walk a blob's tree for the sweep and for fetch planning; and check a single received piece. A list piece is written by whoever made the blob, so this is the code that faces hostile input. Every piece is checked against the CID that named it, and every list piece against the bounds below, before anything under it is requested or any of its bytes is yielded.

Modules import each other by file, not through `blob/index.ts`, which re-exports the new names.

## One piece (`blob/verify.ts`)

```ts
/** Throws BlobCorruptError ('piece-too-large' before hashing, then 'digest-mismatch'). */
export function checkPiece(id: PieceId, bytes: Uint8Array, digest: BlobDigest, ref?: BlobRef): Promise<void>;
```

The size test runs first so a hostile 100 MB answer is refused without being hashed. The digest is compared with `cidOfPiece(id).multihash.digest` byte for byte. This is what the fetcher in `feat-blob-pieces-move-between-machines` calls on each piece it receives, before storing it, so it can discard a bad piece and ask another holder rather than fail the read.

## List pieces (`blob/list-piece.ts`, decode half)

```ts
export interface DecodedListPiece { readonly children: readonly DecodedChild[]; readonly totalBytes: number }
export interface DecodedChild { readonly id: PieceId; readonly kind: 'data' | 'list'; readonly fileBytes: number }
/** Decode and bound a dag-pb piece whose bytes are already checked against `id`. Throws BlobCorruptError. */
export function decodeListPiece(id: PieceId, bytes: Uint8Array, ref: BlobRef): DecodedListPiece;
```

The checks, in this order, each throwing `BlobCorruptError` with the reason named (reasons are defined in `blob/errors.ts`):

1. `dagPb.decode(bytes)` throws → `malformed-encoding`. (`@ipld/dag-pb` decodes strictly: wrong field order, duplicate or unknown fields all throw.)
2. No `Data` → `not-a-file-node`. `UnixFS.unmarshal(Data)` throws → `malformed-encoding`. `type !== 'file'` → `not-a-file-node`.
3. `data` present with length above zero → `list-carries-data`. This is the decision on inline data: a UnixFS file node that carries bytes of its own is never written by this builder or by `ipfs add --cid-version 1` (raw leaves), and is refused, consistent with "anything else is a malformed blob". The consequence is that trees made with raw leaves off (CIDv0-era `ipfs add`, dag-pb leaves) are not readable here; they would need a re-add with `--cid-version 1`.
4. `Links.length === 0` → `no-links`; above `MAX_BLOB_LIST_LINKS` → `too-many-links`.
5. `blockSizes.length !== Links.length` → `size-mismatch`.
6. For each link: `isPieceCid(link.Hash)` false → `unsupported-codec` when the codec is neither raw nor dag-pb, else `unsupported-hash`. For each size: `0n` → `empty-child`; a raw child whose declared size is above `MAX_BLOB_PIECE_BYTES` → `piece-too-large` (refused before that leaf is fetched).
7. The sum of `blockSizes`, as a bigint, above `Number.MAX_SAFE_INTEGER` → `size-too-large`.

`kind` is `'data'` for a raw child and `'list'` for a dag-pb child; `id` is `pieceIdOfCid(link.Hash)` (a CIDv0 link is re-spelt as v1, same bytes). Link `Name` and `Tsize` are not read: neither affects which bytes are served. The UnixFS `filesize` field is not read either, because `ipfs-unixfs`'s `UnixFS.unmarshal` does not keep it (its `fileSize()` recomputes from `blockSizes`, and the package does not export its raw protobuf decoder); a root is sized by the sum of its `blockSizes`, every one of which is checked against what is under it, so the bytes served are exactly the verified bytes. Recorded as a `NOTE:` at `decodeListPiece`: a root whose `filesize` disagrees with its `blockSizes` is read by its `blockSizes`, where kubo would report the other size; revisit if `ipfs-unixfs` exposes the field.

Rejected: a zero-size child allowed as harmless. It is not: a tree can repeat one list piece's CID at every position, and with zero-size children such a tree costs `MAX_BLOB_LIST_LINKS ^ MAX_BLOB_LIST_DEPTH` requests while declaring zero bytes. With every child at least one byte, the pieces a full read visits are bounded by the declared size times the depth.

## The reader (`blob/reader.ts`)

```ts
export interface BlobReaderOptions { digest?: BlobDigest }
export interface BlobRangeOptions extends BlobReaderOptions { offset?: number; length?: number }

/** One data piece on a range's path: its id, where it starts in the blob, its declared size, and the slice of it the range wants. */
export interface BlobRangePiece {
	readonly id: PieceId;
	readonly blobOffset: number;
	readonly size: number;
	readonly start: number;   // within the piece, inclusive
	readonly end: number;     // within the piece, exclusive; end > start
}

/** The data pieces a range needs, in order. Fetches and checks the list pieces on the path (and the root, even when it is a data piece), never a data piece below the root. */
export function planBlobRange(ref: BlobRef, source: PieceSource, options?: BlobRangeOptions): AsyncIterable<BlobRangePiece>;
/** The verified bytes of the range, in order, one slice per data piece. */
export function readBlob(ref: BlobRef, source: PieceSource, options?: BlobRangeOptions): AsyncIterable<Uint8Array>;
/** The blob's size from its root piece, or undefined when the root is not in `source`. */
export function readBlobSize(ref: BlobRef, source: PieceSource, options?: BlobReaderOptions): Promise<number | undefined>;
/** Every piece of the tree, root first, depth first: whether it is in `source` and its kind. */
export function walkBlobPieces(ref: BlobRef, source: PieceSource, options?: BlobReaderOptions): AsyncIterable<{ id: PieceId; present: boolean; kind: 'data' | 'list' }>;
```

Shared rules, through one private loader `loadPiece(id, expectedKind, declaredSize, depth)`:

- **Getting a piece.** `bytes = await source.get(id)`; `undefined` → `BlobUnavailableError(ref, 'not-here', id)`. Errors the source throws (a fetching source's own `BlobUnavailableError` with a network reason, an abort) propagate unchanged. Unless `source.verified`, `checkPiece` runs (size, then digest). With `source.verified` only the size test runs.
- **A list piece** is then `decodeListPiece`d, and its `totalBytes` must equal the size its parent declared for it (`size-mismatch`). The root has no declared size; its size is its `totalBytes`. A dag-pb child at depth `MAX_BLOB_LIST_DEPTH` (the root is depth 1) → `too-deep`, refused before the child is requested.
- **A data piece's** length must equal the size its parent declared (`size-mismatch`). A raw root's size is its length.
- **Range arguments.** `offset` defaults to 0, `length` to everything after `offset`. Either one not a non-negative safe integer → `RangeError` (a caller bug, not a blob fault), thrown before any piece is requested. The root is always loaded, to learn the size. `offset > size` → `RangeError`. `offset === size`, or `length === 0`, yields nothing. A range running past the end is clamped to the end.
- **Order and pruning.** Depth first, children left to right; a child whose byte span `[childOffset, childOffset + fileBytes)` does not intersect the range is skipped without being requested. Before descending into any child, the parent has passed every check above, so no piece under a malformed one is ever requested.
- **`readBlob`** is `planBlobRange` plus, per planned piece, `loadPiece` of the data piece and `yield bytes.subarray(start, end)`. For a raw root it yields from the bytes already loaded rather than getting the root twice. A fault part way through throws; slices already yielded were verified, and nothing past the fault is yielded, so a consumer that sees the throw never treats a partial read as whole.
- **`readBlobSize`** loads only the root: `undefined` when `source.get` answers `undefined`, else the size, after the same checks.
- **`walkBlobPieces`** yields the root, then each child in order. A list piece that is present is loaded (checked and decoded) and its children walked; one that is absent is yielded `present: false` and its subtree skipped. A data piece is never read or hashed by the walk: `present` comes from `source.has(id)` when the source has `has`, else from `(await source.get(id)) !== undefined`. Each list piece id is visited once per walk (a `Set` of list ids already expanded), so a hostile tree that repeats one list piece at every position costs one load per distinct list piece; data pieces are yielded as they appear, repeats included (keeping a set of every data id would grow with the blob). A malformed list piece throws `BlobCorruptError`.

Digest: `options.digest ?? defaultBlobDigest()` everywhere.

## Edge cases & interactions

- Range at `offset === size`, `length === 0`, `offset > size`, length past the end, non-integer or negative arguments: the answers above. Test (planner table).
- Ranges crossing a data-piece boundary and a list-piece boundary request only the path: root, the list pieces covering the range, and the data pieces in it. Test (counting `get` calls).
- Each malformed shape — oversized piece, digest mismatch, undecodable dag-pb, non-file UnixFS type, list piece with inline data, no links, too many links, block-size count differing from link count, zero-size child, a link of a third codec, a link with another hash, a declared leaf size over the piece limit, child sizes not adding up to the parent's declared size, a leaf whose length differs from its declared size, a total above `Number.MAX_SAFE_INTEGER`, a tree one level too deep — throws `BlobCorruptError` with its reason, and the piece below the fault is never requested. Test (table).
- A piece missing from the source: `BlobUnavailableError` with reason `not-here` and the piece id. Test.
- A `verified` source: no piece is hashed, list pieces are still bounded. Test. A fetching source that does not verify what it returns must leave `verified` unset; stated on the field (previous ticket) and by inspection in the transfer ticket.
- A source whose `get` throws, or an abort inside it: propagates unchanged. Inspection.
- A tree repeating one CID many times: `readBlob` serves it (repeated content is legitimate) at a cost bounded by the declared size; `walkBlobPieces` loads each list piece once. Test for the walk.
- CIDv0 links inside a list piece are accepted and re-spelt as v1 ids. Inspection.
- Kubo-made trees are read: the round-trip test reads trees this builder made, which match kubo byte for byte (the previous ticket's vectors).

## Tests

All in `packages/db-core/test/blob-reader.spec.ts`. Sources are plain `Map<PieceId, Uint8Array>` objects implementing `PieceSource` (optionally with `has` and `verified`) and recording each `get`; trees are made with `buildBlob`, and malformed ones by hand with `@ipld/dag-pb`, `ipfs-unixfs` and `multiformats` (all db-core dependencies). Content byte i is `i % 251`, as in the builder's vectors.

- **Round trip.** A 175 × 262,144 + 1-byte blob built into a map reads back whole and equal to the content; through a `verified: true` source, the digest passed in is never called; through a plain source, it is called once per piece loaded.
- **Range planner table.** On the same blob (root over a 174-leaf list piece and a 2-leaf list piece): `(0, 0)` and `(size, 5)` yield nothing; `(size + 1)` and `(-1)` throw `RangeError`; `(size - 10, 100)` is clamped to 10 bytes; `(100, 50)` is one piece; `(262,143, 2)` is two pieces; `(174 × 262,144 − 1, 2)` is two pieces under different list pieces, with exactly the root, both list pieces and those two data pieces requested. For each, `readBlob` yields exactly `content.subarray(offset, offset + clamped length)`.
- **Malformed trees table.** One generated `it` per shape listed under Edge cases, each asserting the reason and that the child below the fault was not requested.
- **Missing piece.** A tree with one data piece removed from the source: `BlobUnavailableError`, reason `not-here`, `pieceId` that piece.
- **Walk.** On a tree with one list piece removed and a source with `has`: that list piece is yielded `present: false`, its children are not yielded, and `get` is never called for a data piece. On a hand-made tree whose root links one list piece 1,024 times: that list piece is requested once.
