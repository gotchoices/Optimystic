# Blob pins follow SQL commits

Third of four parts of backlog `feat-sql-columns-hold-blob-references` (docs/blobs.md §Committing a reference, §SQL "Pins follow the transaction"). After `feat-blob-reference-trees-follow-sql-rows`, every statement stages its reference-tree entries; after `feat-a-referenced-blob-is-copied-to-its-cohort`, `node.blobs.announce` copies a committed reference to its cohort and reports durability. This part connects the two for every commit that reaches the network or the queue: the references a transaction adds are pinned on the writer when its commit starts, announced (with the table's reference tree as scope) and unpinned once it lands, and unpinned if it is abandoned. Queued transactions settling, a restart's reconciliation and the `unstaged` holding period are the last part, `feat-sql-columns-hold-blob-references`.

## The rule for when the blob service is called

Nothing reached from `OptimysticVirtualTable.update` calls the blob service. A validating member re-executes the statements through `QuereusEngine.execute` (`packages/quereus-plugin-optimystic/src/transaction/quereus-engine.ts`) and has no bytes, so it must neither pin nor announce (§Registering references, "Members never check whether the bytes exist"). `update()` only records what it staged; the bridge pins at commit. This departs from docs/blobs.md §SQL's "the first statement that stages the reference moves the pin to its transaction": the move happens when the commit starts instead. What that changes is limited to a transaction open longer than the `unstaged` holding period (24 hours), which the last part covers by never expiring an `unstaged` pin whose reference the open transaction has staged.

**Replay guard.** New module `packages/quereus-plugin-optimystic/src/transaction/replay-scope.ts`:

```ts
/** Run `run` with `db` marked as re-executing a replicated transaction. Nested calls count. */
export function duringReplay<T>(db: Database, run: () => Promise<T>): Promise<T>;
export function isReplaying(db: Database): boolean;
```

A `WeakMap<Database, number>` counter, decremented in a `finally`. `QuereusEngine.execute` wraps its statement loop in it. The one writer at a time Quereus's exec mutex guarantees per `Database` makes a counter per `Database` exact. `QuereusEngine.execute` is only ever replay: the writer's session records statements with `session.execute(statement, [])`, which never calls the engine (`TransactionSession.execute` in `packages/db-core/src/transaction/session.ts`).

## What a transaction records

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-reference-ledger.ts`, kept on the transaction like `writeFacts`:

```ts
export interface BlobReferenceRecord { readonly backendKey: string; readonly change: ReferenceChange }
export interface BlobPutRecord { readonly backendKey: string; readonly ref: BlobRef }
export interface BlobReferenceLedger {
	readonly records: BlobReferenceRecord[];
	readonly puts: BlobPutRecord[];
	/** records.length at each open legacy savepoint, by depth. */
	readonly marks: Map<number, number>;
}
export function emptyBlobReferenceLedger(): BlobReferenceLedger;
/** The (backend, reference, scope) triples the transaction leaves added: per (backend, scope, referrer), the last change wins, and an `add` survives. Each triple once. */
export function addedReferences(ledger: BlobReferenceLedger): { backendKey: string; ref: BlobRef; scope: string }[];
```

`TransactionState.blobReferences: BlobReferenceLedger` (`packages/quereus-plugin-optimystic/src/types.ts`), initialized in `TransactionBridge.beginTransaction` and in `transactorOnlyState` (`optimystic-module.ts`). An insert followed by a delete of the same row in one transaction therefore adds nothing; a reference removed from a row committed earlier is not an add and is never pinned.

**Recording.** `OptimysticVirtualTable` constructs its `BlobReferenceMaintainer` with `onStaged: changes => { if (!isReplaying(this.db)) this.txnBridge.noteBlobReferences(this.blobBackendKey, changes) }`, where `blobBackendKey` is the table's transactor key (`CollectionFactory.networkBinding(this.options).key`, resolved once at initialization). `TransactionBridge.noteBlobReferences(backendKey, changes)` appends to the open transaction's ledger (no-op without an active transaction). `SqlBlobService.put` calls `TransactionBridge.noteBlobPut(backendKey, ref)` when it defaulted the owner to the transaction's put label and that transaction is still the active one when the put resolves; a put that outlives its transaction leaves a stray `put` pin that the last part's reconciliation removes.

**Savepoints.** `createSavepoint` records `marks.set(depth, records.length)` and `rollbackToSavepoint` truncates `records` to it, only where the bridge also restores trees: legacy mode, where `this.savepoints` holds the depth's snapshots. In session mode a statement savepoint rollback does not restore the trees (the documented gap at `savepoints` in `txn-bridge.ts`), so the ledger is not truncated either: what is recorded follows what will commit. `releaseSavepoint` drops the marks at and above the depth. `puts` are never truncated: a put is not undone by a savepoint.

## The pins

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-pins.ts`, one instance per plugin registration, attached to the bridge (`TransactionBridge.attachBlobPins(pins)`, set once by `register`, absent on a bridge built bare). Log namespace `optimystic:quereus-plugin:blob`.

```ts
export interface HeldReference { readonly backend: BlobBackend; readonly ref: BlobRef; readonly scope: string; readonly label: string }
export interface HeldPins { readonly transactionId: string; readonly references: readonly HeldReference[]; readonly puts: readonly BlobPutRecord[] }

export class SqlBlobPins {
	constructor(deps: {
		backendByKey(key: string): Promise<BlobBackend>;  // CollectionFactory.blobBackendForKey: the backend of a transactor key whose options the factory has seen (networkBinding remembers them per key), resolved on first use
		registration: BlobScopeRegistration;
	});
	/** Pin every added reference under its transaction label. All or nothing: on a throw, unpins what it pinned and rethrows. Undefined when the ledger adds nothing and records no put. */
	holdForCommit(transaction: TransactionState): Promise<HeldPins | undefined>;
	/** The commit landed for `committed` scopes ('all', or the collection ids a partial commit names). Never throws. */
	committed(held: HeldPins, committed: 'all' | ReadonlySet<string>): Promise<void>;
	/** The transaction was sealed into the offline queue. Never throws. */
	queued(held: HeldPins): Promise<void>;
	/** Nothing of the transaction is durable or queued. Never throws. */
	abandoned(held: HeldPins | undefined, transaction: TransactionState): Promise<void>;
}
```

- **`holdForCommit`.** For each triple of `addedReferences`, `backend.service.pin(ref, transactionReferencePinLabel(stampId, scope))`. Every reference is pinned whether or not this machine holds its bytes: a reference copied from another row commits and reads as not held, and announcing it still tells its cohort where to look (backlog "A table on another network"). A pin's record write failing fails the commit before anything is sent: the bridge then runs its ordinary failed-commit path.
- **`committed`.** For each held reference whose scope is committed: `registration.ensure(backend, scope)`; when true, `service.announce(ref, scope)` and then `service.unpin(ref, label)`. When `ensure` answers false or `announce` throws: log `blob:pin-kept transaction=… ref=… scope=… reason=…` and keep the pin; the bytes stay, and the last part retries. A held reference whose scope is not committed (a partial commit's other half) keeps its pin for the same retry, which finds it certainly unlisted and unpins it. Then, for each reference with at least one committed scope: unpin every `unstaged` pin it holds on that backend (`pinsOf`, filtered by `parsePinLabel`). Last, unpin every `put` pin of the transaction (`held.puts`): a referenced blob is held by its reference pin or its `owed` hold, and an unreferenced one was put inside a transaction that did not keep it.
- **`queued`.** The reference pins stay, to be settled with the queued transaction. Drop each referenced reference's `unstaged` pins and every `put` pin of the transaction, as `committed` does.
- **`abandoned`.** Unpin every held reference pin and every `put` pin of the transaction (`held` may be undefined, a rollback before any commit began: then the puts come from `transaction.blobReferences.puts`). `unstaged` pins are left alone: the application put those bytes outside the transaction and may retry the insert; the holding period bounds them.
- **Ordering inside one call**, announce before unpin, so no instant leaves a committed reference with no hold on the writer. Calls are awaited in sequence; a release of tens of references costs tens of local record writes.

## The bridge's routes (`TransactionBridge` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts`)

`commitTransaction` calls `holdForCommit` inside its `try`, after `offlineRoute()` and `openLane()` and before the route runs, and keeps `held`:

| Exit | Call |
|---|---|
| session or legacy route returns | `committed(held, 'all')`, awaited before `reportCommitDurability` |
| `local` or `behind-queue` route, entry queued | `queued(held)`, awaited; for `behind-queue`, before `awaitQueuedCommit` |
| a queue route that queued nothing | `abandoned(held, txn)` |
| `afterFailedCommit`, `PartialCommitError` | `committed(held, new Set(error.persisted))` (the sweep's labels are collection ids for real trees, `treeLabel`) |
| `afterFailedCommit`, `CoordinatorPartialCommitError` | `committed(held, new Set(error.committedCollections))` |
| `afterFailedCommit`, anything else | `abandoned(held, txn)`, after the rollback |
| `rollbackTransaction` (no commit attempted) | `abandoned(undefined, txn)`, after the restores, in the `finally` |

The release is awaited before the commit returns, so when a host's `db.exec(...)` resolves the announcement has been made: `plugin.blobs.onDurability` fires afterwards with no further call (this is what the two-commit pattern waits on). A release never throws into the commit: the write is durable or queued by then. `holdForCommit` throwing is an ordinary failed commit (nothing sent), whose `abandoned` then has nothing pinned to release under reference labels.

**Session mode** pins before `commitSession`; the validator's own `Database` (if it shares a process) records nothing, since its `update()` runs under `duringReplay`.

## Edge cases & interactions

- **A put outside a transaction, inserted later** (docs/blobs.md's own example): `unstaged` pin until the insert's commit lands, then a reference pin, announce, `owed` hold; the `unstaged` pin is gone. Test.
- **Rollback.** Reference pins never existed; `put` pins of the transaction go; `unstaged` pins stay. Test.
- **Savepoint rollback** (legacy mode): a reference only a rolled-back statement added is not pinned or announced; one also added before the savepoint is. Test.
- **Refused commit** (a rival took the key; nothing durable): `abandoned`; the refused writer's `unstaged` pin stays, so its retry does not need to put the bytes again. Test, two handles over one storage (`packages/quereus-plugin-optimystic/test/shared-local-transactor.ts`).
- **Partial commit.** Announce only references whose reference tree committed; keep the rest pinned for the last part's reconciliation. Inspection (the routing table above).
- **Announce fails, or the scope cannot be confirmed registered.** Pin kept and logged; nothing announced into an unregistered tree. Inspection.
- **Validation re-execution** touches no blob service. Assertion at the seam (`isReplaying` at the one recording site); test below.
- **Same reference in two tables, or two columns.** Two scopes, two reference pins, two announcements for the two tables; two columns of one table share a scope, so one. Inspection of `addedReferences`.
- **Insert then delete in one transaction.** Nothing added, nothing pinned; the `unstaged` pin stays. Inspection of `addedReferences`.
- **A reference whose bytes are not here.** Pinned (creating a record) and announced; reads report it not held. Inspection.
- **Durability event naming the reference.** The event is `node.blobs`'s; `plugin.blobs` forwards it (feat-blob-sql-type-and-blob-service). Integration test.
- **Concurrency.** Releases run inside `commitTransaction` under Quereus's exec mutex, one transaction at a time. Inspection.

## Tests

- `packages/quereus-plugin-optimystic/test/blob-pins-online.spec.ts`, on the `test` transactor (single-machine service, so announce yields an `owed` hold and durability `local`), plugin registered with `types` and `functions`. Read pins with the backend's `pinsOf` and `parsePinLabel`:
  - put outside a transaction, then `insert` in a later statement: after the statement no `unstaged` and no transaction pin; `stat` reports durability `local`; a durability listener subscribed before the insert received one event naming the reference; the registry lists the table's scope.
  - `begin`; put; insert; `rollback`: no pin of any kind remains. Put before `begin`; insert; `rollback`: only the `unstaged` pin remains.
  - savepoint, legacy mode: insert r1; `savepoint s`; insert r2; `rollback to s`; `commit`: r1 announced, r2 not (its `unstaged` pin remains, no event).
  - refused commit: two handles over one storage insert the same primary key with different references; the loser's commit is refused; its reference has its `unstaged` pin and no transaction pin.
  - replay: a second `Database` with its own plugin instance validates (`createQuereusValidator`) a session-mode transaction that inserted a `blobref` row; afterwards that plugin's backend lists no pin (`listPins('sql')` is empty) and `stat(ref).locality` is `unknown`.
- `packages/quereus-plugin-optimystic/test/two-node-blob-reference.integration.spec.ts`, gated on `OPTIMYSTIC_INTEGRATION=1` like `two-node-secondary-index-libp2p.integration.spec.ts` (two real libp2p nodes, each driving its own `Database`, `clusterPolicy.assumedClusterSize: 2`): the two-commit pattern of docs/blobs.md §Committing a reference. Node A puts a multi-piece blob, commits `insert into Attachment` holding only the reference, awaits `plugin.blobs.onDurability` reporting `majority` or `full` for that reference (bounded wait), then asserts node B's `node.blobs.stat(ref).locality === 'here'` before it commits `insert into Message` naming the attachment.
