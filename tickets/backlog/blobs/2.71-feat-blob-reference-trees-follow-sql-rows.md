# Blob reference trees follow SQL rows

Second of four parts of backlog `feat-sql-columns-hold-blob-references` (docs/blobs.md §SQL, §Registering references). After `feat-blob-sql-type-and-blob-service` a table can declare a `blobref` column; after `feat-committed-rows-register-the-blobs-they-reference` db-core has a reference tree (`BlobReferenceTree`: stage add / remove into the caller's transaction, and a reader `listed(refs)`) and a scope registry (`BlobScopeRegistry`: register / unregister / enumerate). This part makes every table with a `blobref` column keep its reference tree in step with its rows, exactly as it keeps its index trees, through every write path and every commit route, and registers the tree in the network's scope registry. It touches no blob service: pins and announcements are `feat-blob-pins-follow-sql-commits`.

## The table's reference tree

**Location and opening.** For a table with at least one `blobref` column the tree lives at `${options.collectionUri}/blobrefs` (the index precedent is `${collectionUri}/index/${indexName}`, `openIndexTree` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`). Its collection id, `<path>/blobrefs`, is the table's **scope** (`BlobScope`). An index can never be named `blobrefs` at that level, since index trees sit one segment deeper under `/index/`. New factory method, beside `createOrGetCollection`, so the transactor, the transaction cache and the sealed-segment refusal listener (`treeOptions()`) are applied exactly as for every other tree the factory opens:

```ts
// CollectionFactory
/** Create-or-open the reference tree at `options.collectionUri` (already the `/blobrefs` URI), through the db-core create-or-open, carrying this factory's tree options. */
createOrGetBlobReferenceTree(options: ParsedOptimysticOptions, txnState?: TransactionState): Promise<BlobReferenceTree>;
/** The scope registry of one network, create-or-open. One instance per transactor key. */
getBlobScopeRegistry(network: NetworkBinding): Promise<BlobScopeRegistry>;
```

Create-or-open, as for index trees and for the same reason: a table whose rows have never referenced a blob has never committed the tree's header, and reading it as absent would be wrong.

**Which `Tree` joins the transaction.** The plugin registers and marks dirty the reference tree's underlying db-core `Tree` (the `DirtyTree` the bridge already takes for index trees). `BlobReferenceTree` must expose it; if the db-core ticket gave it no accessor, add a `readonly tree` getter there.

**Wiring in `OptimysticVirtualTable`** (all in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`):

- `doInitialize`: when the resolved schema has a `blobref` column (`isBlobRefColumn` from `packages/quereus-plugin-optimystic/src/schema/blobref-type.ts`), open the reference tree with the index trees, as a local, and publish it with them in the same synchronous step (the "Publish the rebuilt state in ONE synchronous step" rule there). A table with no `blobref` column opens nothing: every registered collection costs a snapshot per savepoint and a slot in the session coordinator's map.
- `registerCollections`: `registerTree` the reference tree, so it is in the session coordinator's live registry, in legacy savepoints, and in `TransactionBridge.collectionsOf(table)` — which is how the offline restore (`collectionsOfTable`, `resolveCollections` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-restore.ts`) finds its journaled segment and how the DDL gate (`assertNoQueuedEntries`) sees it.
- `markDirtyTrees`: mark it dirty with the main and index trees, so every commit route carries it: a session-mode participant (the coordinator commits every registered collection with staged changes), a member of the legacy batch (`commitBatchLegacy`, through `legacyBatch`), a tree of the per-tree sweep, and a collection of the offline entry (`queueableSet`, `sealIntoQueue`). No commit-route code changes.
- `describeCollection`: answer `{ kind: 'index', table }` for the reference tree's collection id. Its elements carry no guard, so the outlook judgement never reads the description (`element` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-outlook.ts` returns early on an unguarded element); this keeps a restored entry's description from reading `unknown`.
- `republishColumnLayout`: rebuild the maintainer's column list from the new `tableSchema` after a catalog-only DROP COLUMN of another column moves positions.
- `queryCommitted` and every read path: untouched. Committed reads never open or read the reference tree.

## The maintainer

New module `packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts`, the counterpart of `IndexManager` for references:

```ts
/** A staged change to the reference tree, as the pin lifecycle consumes it (feat-blob-pins-follow-sql-commits). */
export interface ReferenceChange {
	readonly op: 'add' | 'remove';
	readonly ref: BlobRef;
	readonly referrer: string;
	readonly scope: string;
}

export class BlobReferenceMaintainer {
	constructor(columns: readonly { position: number; name: string }[], tree: BlobReferenceTree, scope: string,
		onStaged?: (changes: readonly ReferenceChange[]) => void);
	/** The table's blobref columns, in declaration order, from a TableSchema. */
	static columnsOf(schema: TableSchema): { position: number; name: string }[];
	stageInsert(row: Row, primaryKey: PrimaryKey): Promise<void>;
	stageDelete(row: Row, primaryKey: PrimaryKey): Promise<void>;
	stageUpdate(oldRow: Row, newRow: Row, oldPrimaryKey: PrimaryKey, newPrimaryKey: PrimaryKey): Promise<void>;
	withColumns(columns: readonly { position: number; name: string }[]): BlobReferenceMaintainer;
}

/** The referrer of one row's one column: the table's framed primary key, then the column name framed as one more element. */
export function blobReferrer(primaryKey: PrimaryKey, column: string): string; // primaryKey + encodeKeyElement(column)
```

- **Referrer key.** `primaryKey` is already the self-delimiting framed tuple the main tree is keyed by (`RowCodec.extractPrimaryKey` / `createPrimaryKey`), so appending `encodeKeyElement(column)` (`packages/quereus-plugin-optimystic/src/schema/key-encoding.ts`) keeps it injective, and `splitKeyTuple(referrer)` gives the key elements followed by the column name. The column name is the stored name, exactly as `tableSchema.columns[i].name` spells it. It is stable: RENAME COLUMN is refused on these tables (`alterTable`, arm `renameColumn`), a `blobref` column cannot be dropped (below), and a re-declare cannot change a column to or from `blobref` (below).
- **Values.** For each `blobref` column, a NULL cell stages nothing. A non-NULL cell goes through `parseBlobRef`; a failure is rethrown as `QuereusError(…, StatusCode.MISMATCH, cause)` naming the column. The engine already validates through the type; this keeps a malformed value from ever reaching the tree whatever path delivered the row.
- **Per row and per `blobref` column:** insert adds `(new value, new key, column)`; delete removes `(old value, old key, column)`; update with the same key removes the old value and adds the new one only for a column whose value changed (`old === new` as strings, both NULL included, stages nothing); update with a changed key removes every old non-NULL value under the old key and adds every new non-NULL value under the new key. Each call stages its removes before its adds, through the db-core staging helper on `tree`, so a remove and an add of one key in one call cannot invert. Then `onStaged(changes)` is called with the changes it staged, in order (nothing is called when nothing was staged).
- **Pure.** The staged operations are a function of `(rows, keys, columns)` only: no read of the tree, no clock, no blob service. That is what lets a validating member's re-execution through `QuereusEngine` (`packages/quereus-plugin-optimystic/src/transaction/quereus-engine.ts`) stage the same operations (docs/blobs.md §Registering references, "Under transaction validation"). A remove is blind, as an index delete is (`deleteIndexEntries` explains why that is sound); an add is an upsert of a fixed key; neither carries a guard, so neither is counted in the offline queue's already-applied tally and neither can refuse — racing changes to one row are refused by the main tree's `unchanged` guard, which rolls the reference entries back with it.

**Call sites in `update()`**, each beside the index call it mirrors and in the same order (one `if (this.blobReferences)` per site):

| Site | Index call | Reference call |
|---|---|---|
| `applyUniqueEvictions`, per evicted row | `deleteIndexEntries(row, pk)` | `stageDelete(row, pk)` |
| INSERT OR REPLACE over an occupied key | `updateIndexEntries(existingRow, values, insertKey, insertKey)` | `stageUpdate(existingRow, values, insertKey, insertKey)` |
| INSERT at a clear key | `insertIndexEntries(values, insertKey)` | `stageInsert(values, insertKey)` |
| UPDATE, displacing move | `deleteIndexEntries(pkMove.row, newKey)` | `stageDelete(pkMove.row, newKey)` |
| UPDATE | `updateIndexEntries(oldRow, values, oldKey, newKey)` | `stageUpdate(oldRow, values, oldKey, newKey)` |
| DELETE (cascade child deletes included: they reach this arm) | `deleteIndexEntries(oldRow, deleteKey)` | `stageDelete(oldRow, deleteKey)` |

The displacing move's order matters for the same reason it does for indexes: when the displaced row and the moving row hold the same reference in the same column they stage the identical key, and remove-then-add leaves it present. Arms that return without staging (IGNORE, a blocked or swallowed decision, a `constraint` result, `removedEarlierInTransaction`) stage nothing here either. `onStaged` is left unset in this part; `feat-blob-pins-follow-sql-commits` wires it.

## Registering the tree in the scope registry

New module `packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-scope-registration.ts`, one instance owned by the `CollectionFactory` (it needs the registry per transactor key):

```ts
/** One network as the registry needs it: the transactor key and its transactor. `BlobBackend` (feat-blob-sql-type-and-blob-service) extends it. */
export interface NetworkBinding {
	readonly key: string;
	readonly transactor: ITransactor;
}

export class BlobScopeRegistration {
	constructor(registryFor: (network: NetworkBinding) => Promise<BlobScopeRegistry>);
	/**
	 * True once `scope` is confirmed in `network`'s registry in this process: read first (enumerate, certain and listed),
	 * otherwise registered with the registry's stage-and-sync convenience. False, logged, when that sync throws.
	 * Memoized per (network key, scope) once true, so the steady state costs nothing.
	 */
	ensure(network: NetworkBinding, scope: string): Promise<boolean>;
	/** Stage the unregister and sync it on its own; idempotent. Clears the memo. */
	unregister(network: NetworkBinding, scope: string): Promise<void>;
}
```

`CollectionFactory.networkBinding(options): Promise<NetworkBinding>` resolves the transactor (`getOrCreateTransactor`) and its key (`getTransactorKey`); `getBlobScopeRegistry` takes a `NetworkBinding` and caches one registry per key; move `BlobBackend` in `collection-factory.ts` to `extends NetworkBinding`. The DDL paths need no blob service, so they never resolve one.

Use the registry's own stage-and-sync convenience for register; for unregister, if the db-core ticket gave none, stage it and sync the registry's tree here. Concurrent `ensure` calls for one key share one promise.

**When.**

- `OptimysticModule.create`, for a table whose schema has a `blobref` column: `ensure` before the batch checkpoint that initializes the table, and the create throws (QuereusError, StatusCode.ERROR, cause attached) when it answers false. Registering first is harmless if the create then fails: an id whose tree was never written reads as an empty tree, certainly. A re-declare of an existing table pays one registry read the first time in a process and nothing after.
- `OptimysticModule.addColumn`, when the added column is `blobref` and the table had none: `ensure` before `alterCatalogOnly`, same refusal; after it, an initialized instance opens and registers its reference tree and builds its maintainer (`OptimysticVirtualTable.attachBlobReferences`, an async step `addColumn` awaits, since `applyCatalogOnlyEdit` is synchronous). ADD COLUMN already refuses a DEFAULT, so no stored row gains a reference and nothing is backfilled.
- `apply schema`: it reaches these two arms; the registration syncs immediately rather than joining the batch, and a failed batch leaves an idempotent, harmless registry entry.
- **Hydrate does not register.** docs/internals.md §A first touch writes only what the table owes forbids a first touch writing what the table does not owe, and a hydrated table's tree was registered by whichever machine created it. The remaining gap — a tree missing from the registry (a create on a build that registered nothing, or a drop on another machine while this one kept writing) — is closed where it matters: before any announcement names the tree as its scope, `feat-blob-pins-follow-sql-commits` calls `ensure` and does not announce until it answers true. A receiver only ever reads a scope it was told about, so a reference committed before its tree is registered is harmless until the announcement, and nothing is announced into an unregistered tree. This departs from the backlog's "hydration checks the registry and registers a missing tree", which would cost a registry read per table at every start.
- **Drop table** (`OptimysticModule.destroy`): for a table whose engine catalog entry (`db.schemaManager.findTable`) has a `blobref` column, after the gravestone write, `unregister`. A failure is logged and does not stop the drop, like the gravestone failure beside it: the blobs that tree lists then stay referenced, which keeps bytes rather than losing them. The reference tree stays in storage, as a dropped table's index trees do. Add a `NOTE:` (accepted tradeoff): a table re-created over the same URI re-registers the old tree, whose leftover entries then keep their blobs alive; it never loses one; revisit if reclaiming those matters.

## Drop and re-declare rules

- **Drop column.** `columnDropBlockers` (`packages/quereus-plugin-optimystic/src/schema/catalog-only-change.ts`) adds `it holds blob references` for a `blobref` column, judged by `isBlobRefColumn`, so both the engine's entry (`logicalType`) and a catalog record (`affinity`) are refused. Widen `ColumnKeyedParts.columns` to `{ name; generated; logicalType?: { name: string }; affinity?: string }`. The rule then also covers `classifyColumnChange` on the record and `withoutColumn` in `packages/quereus-plugin-optimystic/src/schema/schema-manager.ts`. Why: dropping it would leave entries no row implies, keeping their blobs forever.
- **Re-declare.** `SchemaManager.mergeWithPersisted` refuses a candidate that changes a persisted column of that name to or from `blobref` affinity, or omits a persisted `blobref` column, with `Cannot re-declare column '<c>' of '<table>' to or from blobref: its rows' blob references would need rewriting. Drop and re-create the table.` (a thrown Error, surfaced by `doInitialize` as its other re-declare refusals are). Turning a text column holding references into `blobref` over existing rows would otherwise give committed references with no entries.

## Edge cases & interactions

- **Every row-change shape** (insert; delete; cascade delete; secondary-UNIQUE REPLACE eviction; insert or replace over a key; same-key update changing the value, keeping it, setting NULL, setting from NULL; primary-key move; displacing move onto an occupied key), on a table with a composite primary key whose columns are not leading and two `blobref` columns, one row holding the same reference in both: after commit the tree lists exactly the triples the rows hold. Test, table-driven.
- **Racing writers.** Two handles change one row's reference: the main tree's `unchanged` guard refuses the loser at commit and its reference entries leave with the rest of its transaction. Two handles insert different rows referencing one blob: both land, with one entry each. Test, on two `Database` handles over one storage, the shape of `packages/quereus-plugin-optimystic/test/concurrent-row-change-refusal.spec.ts`.
- **Validation.** A session-mode transaction that inserts, updates and deletes `blobref` rows passes `createQuereusValidator`'s re-execution: the operations hash covers the reference tree's operations, so a mismatch would reject. Test, on the harness `packages/quereus-plugin-optimystic/test/distributed-transaction-validation.spec.ts` uses. (That no blob service is touched there is `feat-blob-pins-follow-sql-commits`'s.)
- **Rollback and savepoint rollback.** The reference tree is a dirty tree and a registered collection, so a rollback restores it from its snapshot and a legacy savepoint rollback restores it with the others; session mode has the existing statement-savepoint gap (`savepoints` doc in `txn-bridge.ts`) for it as for index trees. Inspection.
- **Offline.** A queued entry carries the reference tree's segment; a restart restores it through `collectionsOfTable`, which lists it. A `blobref` table's DDL is gated by queued entries that wrote its reference tree. Inspection (the existing restore and gate specs cover the mechanism; the tree is one more collection).
- **Two tables over one URI** share one reference tree and one scope, as they share index trees. The referrer includes the primary key and column, not the table name, so two tables sharing a collection must also share the row shape (already required, `assertRedeclarationKeepsShape`). Inspection.
- **Index on a `blobref` column.** Works as a text index; nothing here interacts. Inspection.
- **Column positions after a drop of another column.** The maintainer's positions are rebuilt in `republishColumnLayout`. Inspection, plus one case of the shapes test that drops an unrelated column mid-way and writes again.
- **Registry write fails at create.** The create throws; nothing else written. Inspection.
- **Unregister fails at drop.** Logged; drop proceeds. Inspection.
- **Dropped then re-created table.** Old entries count again (the `NOTE:` above). Inspection.
