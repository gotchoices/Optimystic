# Committed rows register the blobs they reference

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). A blob is kept on another machine's behalf only while committed state references it (§Design principles, "The database decides what is alive"), so any machine must be able to ask "does any committed row reference this blob?" without knowing the application's schema. This ticket builds, in `packages/db-core` and with no SQL, the two ordinary tree collections that answer it (§Registering references): the **reference tree**, which lists (reference, referrer) pairs for one collection of rows and is written in the same transaction as the rows, and the **scope registry**, one tree per network at a fixed id listing every reference tree. It also builds the two readers later tickets rely on — "which of these references does this tree list?" and "which reference trees are registered?" — each of which says whether its answer can be trusted. `feat-sql-columns-hold-blob-references` stages through what is built here, `feat-a-referenced-blob-is-copied-to-its-cohort` reads it before taking a blob, and `feat-unreferenced-blobs-are-reclaimed` reads it before releasing one.

## Design

All new code is in `packages/db-core/src/blob/`. Modules import each other and the rest of db-core directly by file, never through a barrel (docs/internals.md, Common Pitfalls §6); `packages/db-core/src/blob/index.ts` (created by the prereq) re-exports the public names below, and `packages/db-core/src/index.ts` already re-exports it. `BlobRef`, `isBlobRef`, `BlobRefError` and `BlobScope` come from the module in `packages/db-core/src/blob/` where the prereq defines them; import them from that file.

### Entry shapes

Both trees are `Tree<string, TEntry>` whose key is `entry[0]` and whose comparator is the `Tree` default (`a < b`, raw UTF-16 code-unit order — the same order as `compareTreeKeys` in `packages/quereus-plugin-optimystic/src/schema/key-encoding.ts`). Each entry is a two-string tuple, which is exactly the plugin's `RowData` (`[string, string]` in `packages/quereus-plugin-optimystic/src/types.ts`), so the SQL plugin can open these trees through its own collection factory (whose key extractor is `entry[0]`) and wrap them, as it does index trees.

```ts
/** A reference-tree entry. The second element is the reference, which the key already contains:
 * the entry carries nothing the key does not say, and exists so the key exists. */
export type BlobReferenceEntry = [key: string, ref: BlobRef];
/** A scope-registry entry: the scope twice. Its value is a fixed function of its key, so two
 * writers registering one scope write identical entries. */
export type BlobScopeEntry = [key: BlobScope, value: BlobScope];
```

### Reference key (`reference-key.ts`)

```ts
/** Separates the reference from the referrer in a reference-tree key. No reference contains it
 * (a reference is lowercase base32: `b`, then `a`–`z` and `2`–`7`), so the first one in a key
 * ends the reference, and the referrer after it may be any string, this character included. */
export const BLOB_REFERENCE_SEPARATOR = '\u0000';
/** One past the separator: the exclusive upper bound of one reference's entries. */
const AFTER_SEPARATOR = '\u0001';

/** `ref + BLOB_REFERENCE_SEPARATOR + referrer`. Throws `BlobRefError` when `!isBlobRef(ref)`, so a
 * cast string can never break the framing. `referrer` is opaque and may be empty. */
export function blobReferenceKey(ref: BlobRef, referrer: string): string;
/** The keys of `ref`'s entries: `[ref + '\u0000', ref + '\u0001')`, as a `KeyRange<string>` (first
 * inclusive, last exclusive). */
export function blobReferenceRange(ref: BlobRef): KeyRange<string>;
/** The inclusive lower and exclusive upper key of `ref`'s entries, for a caller walking a path. */
export function blobReferenceBounds(ref: BlobRef): { lower: string; upper: string };
```

Why this framing and not the plugin's `encodeKeyTuple`: the plugin's escaping exists because its payloads may contain `\x00`; a reference cannot, so a bare separator is already injective and order-preserving, and db-core may not import the plugin. Ordering: for references `R1 < R2`, either they differ at some position inside both (the separator is not reached, so the keys compare as the references do) or `R1` is a prefix of `R2`, where `R1`'s separator (`\u0000`) meets a reference character of `R2`, so `R1`'s entries sort first. Exclusion: every key in `R`'s range starts `R + '\u0000'`, and a longer reference `R'` beginning with `R` has a reference character at that position, above `\u0001`, so none of its keys falls in `[R\u0000, R\u0001)`. Every reference the prereq accepts has the same length (59 characters for both codecs), so the prefix case cannot arise between valid references today; the framing is kept so correctness does not rest on that.

### Reference tree (`reference-tree.ts`)

```ts
export type BlobReferenceChange = {
	readonly kind: 'add' | 'remove';
	readonly ref: BlobRef;
	/** Opaque name of what holds the reference (for a SQL table: framed primary key and column,
	 * chosen by the SQL ticket). */
	readonly referrer: string;
};

/** What a reader found. `listed` is always true: every reference in it is listed. `certain` is
 * whether an unlisted reference is known to be unlisted (see "Certainty" below). */
export type BlobListing = { listed: Set<BlobRef>; certain: boolean };

/** The tree action for `changes`, in the order given: an add is the upsert
 * `[key, [key, ref]]`, a remove the delete `[key, undefined]`, neither guarded. A pure function of
 * its input — no clock, no randomness, no read — so a validating member re-executing the same
 * statements produces the same operations (docs/blobs.md, "Under transaction validation"). */
export function blobReferenceAction(changes: readonly BlobReferenceChange[]): TreeReplaceAction<string, BlobReferenceEntry>;

export class BlobReferenceTree {
	/** Wraps a tree a caller already opened — e.g. the SQL plugin's, through its collection
	 * factory — whose key is `entry[0]` and comparator the default. */
	constructor(readonly tree: Tree<string, BlobReferenceEntry>);
	/** The staging path: `Tree.createOrOpen(transactor, id, entry => entry[0], undefined, undefined, options)`.
	 * A first write is when a reference tree is supposed to come into existence. */
	static createOrOpen(transactor: ITransactor, id: CollectionId, options?: TreeCollectionOptions<string, BlobReferenceEntry>): Promise<BlobReferenceTree>;
	/** Stage `changes` as ONE action through `Tree.stage`; never syncs. Resolves immediately for an
	 * empty list (stages nothing). */
	stage(changes: readonly BlobReferenceChange[]): Promise<void>;
	stageAdd(ref: BlobRef, referrer: string): Promise<void>;
	stageRemove(ref: BlobRef, referrer: string): Promise<void>;
	/** Which of `refs` the reference tree `id` lists in committed state (see "Readers" below). */
	static listed(transactor: ITransactor, id: CollectionId, refs: Iterable<BlobRef>): Promise<BlobListing>;
}
```

**Committing.** `stage` only stages; the entries commit or roll back with whatever the caller commits `tree` with, which is how they join the caller's row writes:

- one collection: `tree.sync()` (`Collection.updateAndSync`);
- several: put `tree.getCollection()` in the collection map the caller's `TransactionCoordinator` is built over, beside the row collections, so one commit carries all of them (the SQL plugin's session mode and `commitBatchLegacy` already do this for index trees);
- offline: pass `tree.getCollection()` to `OfflineQueue.enqueue` with the row collections, so its open segment is sealed into the same entry.

A rollback (`Collection.restorePending`, through `Tree.restore` or the coordinator's rollback) drops the staged action with the caller's others; nothing reached storage.

**Why unguarded entries are replay-safe.** Conflict replay, and the offline queue's replay of a sealed segment, re-run the tree's `replace` handler against the newest committed state (docs/internals.md, "Conflict replay must read at the revision it is adopting"). An add is an upsert of a key fixed by (reference, referrer) with a value fixed by the key, so re-running it leaves the same entry whatever the tree holds; a remove is a blind delete of a fixed key, which deletes it or, if absent, does nothing (`deleteAt` on a path not on an entry returns false without writing). Two writers adding one reference from different referrers write different keys. Whoever owns the referrer's own row (the SQL table's main tree, with its `unchanged` guard) refuses a racing change to the same referrer, so the reference tree needs no guard of its own, exactly as index trees carry none. Unguarded elements are not counted in the offline queue's already-applied tally (`countsWrite` in `packages/db-core/src/collections/tree/tree.ts`), which is intended: a reference entry restates what its row implies.

A change of reference is a remove of the old (reference, referrer) and an add of the new, both supplied by the caller; nothing here reads the old value. An add and a remove of one key in one action, in that order, leave the key absent.

### Scope registry (`scope-registry.ts`)

```ts
/** The scope registry's collection id on every network. Under the `optimystic/` prefix the SQL
 * plugin already uses for its own catalog (`optimystic/schema`); an application collection or a
 * plugin table (`<uri path>`, `<uri path>/index/<name>`, `<uri path>/blobrefs`) does not take it
 * unless it is deliberately named so, and a random block id contains no `/`. */
export const BLOB_SCOPE_REGISTRY_ID: CollectionId = 'optimystic/blob-scope-registry';

export type BlobScopeListing = {
	scopes: BlobScope[];			// ascending
	certain: boolean;
	/** False when the registry has never been written (`Tree.open` resolved undefined).
	 * `feat-unreferenced-blobs-are-reclaimed` treats an absent registry on a node holding blobs as
	 * uncertain; an existing, empty registry is not that. */
	exists: boolean;
};

/** `[scope, [scope, scope]]` to register, `[scope, undefined]` to unregister, unguarded. Throws
 * `RangeError` for an empty scope. */
export function blobScopeAction(kind: 'register' | 'unregister', scope: BlobScope): TreeReplaceAction<string, BlobScopeEntry>;

export class BlobScopeRegistry {
	constructor(readonly tree: Tree<string, BlobScopeEntry>);
	/** `Tree.createOrOpen` at BLOB_SCOPE_REGISTRY_ID; the staging path. */
	static createOrOpen(transactor: ITransactor, options?: TreeCollectionOptions<string, BlobScopeEntry>): Promise<BlobScopeRegistry>;
	/** Stage into the caller's transaction, like `BlobReferenceTree.stage`. */
	stageRegister(scope: BlobScope): Promise<void>;
	stageUnregister(scope: BlobScope): Promise<void>;
	/** Conveniences: open, then `Tree.replace` (which stages and syncs, and unstages on failure). */
	static register(transactor: ITransactor, scope: BlobScope): Promise<WriteDurability | undefined>;
	static unregister(transactor: ITransactor, scope: BlobScope): Promise<WriteDurability | undefined>;
	/** Every registered scope in committed state (see "Readers"). */
	static enumerate(transactor: ITransactor): Promise<BlobScopeListing>;
}
```

**No guard on registry entries — a deliberate departure from the backlog text.** The backlog asked for `absentOrEqual` on a registration "so the loser of the race replays it as already applied rather than being refused". An unguarded upsert is never refused: only a guard refuses, and an unguarded upsert of the fixed entry `[scope, [scope, scope]]` replays to the same state, so two machines registering one scope at once both commit and the registry holds one entry. `absentOrEqual` would add nothing (the value cannot differ) and would cost a wrong report: it is counted in the already-applied tally, so an offline entry that registers a scope a rival already registered and also adds reference entries (which are not counted) would be reported `already-applied` (`effectOf` in `packages/db-core/src/offline/entry.ts`) although its references landed. Unregister is a blind delete for the same reasons: idempotent, and removing an id that is not listed succeeds. A register racing an unregister of one scope ends as whichever commit is applied last; the registry decides nothing about that race, and its callers (table create and drop) are themselves serialized by the catalog. Unregister does not touch the reference tree.

### Readers (`committed-read.ts`)

Both readers open a **fresh, read-only handle** with `Tree.open` on every call and never stage into it. A fresh open reads the header and log tail and adopts the newest committed revision it is told of, which is the "refreshed to the latest committed state first" the readers need; a handle that has nothing staged reads committed state only, so a caller's own staged entries never leak into the answer; and nothing else touches the handle, so no path the pass holds is invalidated mid-pass. Rejected: taking a caller's long-lived tree and calling `update()` — that tree may hold staged entries (the SQL plugin's would), which would be reported as listed. Cost: an open is two requests (header, then tail); the readers run on an announce and on a reclaim pass, not per row.

```ts
/** Open `id` with `Tree.open` and run `pass`; report whether it existed and whether the answer is
 * certain. Shared by both readers so they cannot differ on what is certain. */
export async function readCommittedTree<TEntry extends [string, string]>(
	transactor: ITransactor,
	id: CollectionId,
	pass: (tree: Tree<string, TEntry>) => Promise<void>,
): Promise<{ exists: boolean; certain: boolean }>;
```

**Certainty.** An answer is certain exactly when all of these hold: `Tree.open` and the pass completed; neither threw `BlockUnavailableError` nor `BlockPossiblyStaleError`; and the handle received no below-floor answer. Specifically:

- `Tree.open` resolves `undefined` (the header is authoritatively absent): `{ exists: false, certain: true }`, and nothing is invented. A reference tree that was never written lists nothing, certainly.
- A `BlockUnavailableError` or `BlockPossiblyStaleError` thrown by the open or the pass is caught, logged, and gives `certain: false`; what the pass had already found stays in the result (a reference found listed is listed). Any other error propagates unchanged: it is a fault, not an uncertain answer, and every caller treats a throw as "not certain".
- **Below-floor answers.** `TransactorSource` returns a block older than a log entry the handle has read says it is, unflagged, when no machine asked could meet the floor (the accepted tradeoff at `TransactorSource.mayRetain`), so the reader cannot see it through an exception. Add a count: `BlockFloors` increments a private counter in `answeredBelowFloor` whenever it reports a below-floor answer, exposed as the getter `BlockFloors.belowFloorAnswers: number`, and `Collection.belowFloorAnswerCount(): number` returns it (diagnostic, for the life of the handle). After the pass, `readCommittedTree` reads `tree.getCollection().belowFloorAnswerCount()`; above zero gives `certain: false`. Every read source of the handle shares its `BlockFloors`, so the count covers the open's log walk and the pass. Limit, stated in the docs: a fresh handle's floors come from the entries in its log tail block (`Collection.floorTailEntries`), so a stale answer for a block last changed by an entry in an older log block has no floor and is not detected — the same limit every reader in this system has; docs/blobs.md §Lifetime's two passes a grace period apart are what cover it.
- An absent answer that rested on asking nobody (a node alone in its routing view) is not distinguished here; `feat-unreferenced-blobs-are-reclaimed` owns that and may extend these results.

Log under `createLogger('blob')` (namespace `optimystic:db-core:blob`), one line per uncertain read: `blob:read-uncertain id=%s cause=%s detail=%s`, where cause is `unavailable` (with the error's reason), `possibly-stale` (with the claimed revision), or `below-floor` (with the count).

**`BlobReferenceTree.listed`.** Deduplicate and sort `refs` ascending by code unit (so callers may pass any order), then one ascending pass through `readCommittedTree`, merge-joined with the sorted references, holding one cursor:

```
cursor = undefined
for each ref (ascending):
	{ lower, upper } = blobReferenceBounds(ref)
	if cursor is undefined, or cursor is on an entry whose key < lower:
		cursor = await tree.find(lower); if !cursor.on: await tree.moveNext(cursor)	// first key >= lower
	if !cursor.on: stop (no entry at or after lower; the rest are unlisted)
	if key(cursor) < upper: listed.add(ref)
```

A reference whose range holds no entry leaves the cursor at the next entry, which already answers every following reference that sorts below it, so a run of unlisted references costs no further descent. Each descent goes through the handle's read cache, so leaf blocks are fetched in ascending order and interior blocks once. Rejected: a single range scan from the first reference to the last, whose cost is every entry in between — for a large table and a few held blobs, the whole tree.

**`BlobScopeRegistry.enumerate`.** `readCommittedTree` over `BLOB_SCOPE_REGISTRY_ID`, collecting `entry[0]` from `tree.first()` ascending. `scopes` is what was collected; `exists` and `certain` as above.

**Open semantics** (docs/internals.md §Collection Header Blocks). `readCommittedTree` is the only place these modules open a tree for reading, and it uses `Tree.open`; `createOrOpen` appears only in `BlobReferenceTree.createOrOpen` and `BlobScopeRegistry.createOrOpen`, the staging paths. A remove staged into a reference tree that was never written brings the (empty) tree into existence when committed; harmless, and the alternative would need a read on the staging path.

## Edge cases & interactions

- **Prefix references.** One reference a prefix of another: the shorter's range holds none of the longer's keys. Pinned by the key-encoding test (with synthetic strings cast to `BlobRef`, since valid references share one length).
- **Separator inside a referrer.** The first `\u0000` ends the reference, so any referrer, including one containing `\u0000` or empty, is one distinct key. Inspection of `blobReferenceKey`.
- **A non-reference string cast to `BlobRef`.** `blobReferenceKey` throws `BlobRefError`; nothing is staged. Inspection.
- **Same reference from many referrers; one referrer holding many references; remove one.** Each pair is one entry; a remove leaves the others. Test.
- **Add then remove in one transaction; remove of an entry never added.** The tree ends without the entry; the second stages a blind delete that writes nothing and does not throw. Test.
- **Conflict replay of reference entries.** Two handles adding one reference from different referrers, committed concurrently, both land: distinct keys, unguarded upserts — the shape `packages/db-core/test/two-handle-collection-fork.spec.ts` already pins for unguarded index-tree entries (SEEDED and INVENTED). Not re-tested here.
- **Concurrent registration of one scope.** Both commits succeed, one entry. Test (same key, same value — not covered by the existing two-handle tests).
- **Register racing unregister.** Last applied wins. Inspection; stated in docs.
- **Rollback.** `Collection.restorePending` drops the staged action; nothing reaches storage. Inspection.
- **Offline queue.** The reference tree's collection is sealed with the rows; its replay is idempotent for the reasons above; its elements add nothing to the already-applied tally, and neither do registry elements. Inspection.
- **Under validation.** `blobReferenceAction` and `blobScopeAction` are pure; a member re-deriving them produces the same operations. Inspection.
- **JSON transport.** A delete element `[key, undefined]` arrives as `[key, null]`, which the `replace` handler already reads as a delete; entries are arrays of strings, which round-trip. Inspection.
- **Reader on an absent tree or registry.** Empty, certain, `exists: false` for the registry, and the collection is still absent afterwards (`Tree.open` still resolves `undefined`). Test.
- **Possibly stale or unavailable block.** `certain: false`, no exception, references found before the throw kept. Test for `BlockPossiblyStaleError`; `BlockUnavailableError` takes the same catch arm (inspection).
- **Below-floor answer.** `certain: false`. Test.
- **Unsorted or duplicate `refs`.** Sorted and deduplicated inside `listed`. Inspection.
- **A pass with no references.** Returns at once, `certain: true` if the open was clean. Inspection.
- **Registry id collision.** Covered by the id's choice; inspection.
- **db-core stays network-free.** `packages/db-core/test/no-fret-import.spec.ts` stays green.

## Tests

One spec, `packages/db-core/test/blob-reference-tree.spec.ts`, over `TestTransactor` (`packages/db-core/src/testing/test-transactor.ts`); the two certainty cases subclass it, overriding `get`, as `packages/db-core/test/refresh-below-floor.spec.ts` and `packages/db-core/test/collection.spec.ts` already do. References are produced with the prereq's `buildBlob` (or its parser over known CIDs), never invented strings, except in the encoding test.

- **Key encoding excludes a longer reference** — with `blobReferenceBounds` (which does not validate, unlike `blobReferenceKey`) over `'bafkab' as BlobRef` and `'bafkabc' as BlobRef`: every key `lower + referrer` of the longer reference, for referrers `''`, `'a'` and `'\u0000'`, lies outside the shorter's `[lower, upper)`, and every key of the shorter lies inside its own and sorts below every key of the longer. Pins the framing; the cast is needed only because valid references share one length.
- **Stage, commit, read back** — before anything is written, `listed` over an unwritten id is empty and certain, and `Tree.open` still resolves `undefined` afterwards. Then stage adds (R1, a), (R1, b), (R2, a), an add and remove of (R3, a) in one call, and a remove of (R4, a) never added; `sync`; `listed([R4, R2, R1, R3, R1])` is `{R1, R2}`, certain. Stage remove (R1, a), sync: R1 still listed (via b); remove (R1, b), sync: R1 unlisted.
- **Concurrent registration** — two `BlobScopeRegistry` handles over one transactor stage `stageRegister(S)` and sync in `Promise.all`: both resolve, `enumerate()` is `{ scopes: [S], certain: true, exists: true }`; then `unregister(S)` twice in sequence both succeed and `enumerate()` gives `scopes: []`, `exists: true`. Also `enumerate()` before any registration gives `exists: false`, certain.
- **A possibly-stale block makes the answer uncertain** — commit entries for R1, then read through a transactor that adds `unconfirmedAheadRev` (its `state.latest.rev + 1`) to every entry whose block's `header.type` is `TreeLeafBlockType` (`packages/db-core/src/btree/nodes.ts`) or `TreeRootBlockType`: `listed([R1])` resolves (no throw) with `certain: false`.
- **A below-floor answer makes the answer uncertain** — commit R1 (rev 1), then commit R2 so the leaf changes at rev 2 in the log tail block; read through a transactor that answers tree-node blocks as of rev 1 (the `LaggingDataTransactor` shape in `refresh-below-floor.spec.ts`: re-read at `rev: 1` and report that `materialized`): `listed([R1, R2])` resolves with `certain: false` (the stale leaf does not show R2, and the answer says it cannot be trusted).

Not tested, with reason: concurrent reference adds (pinned by `two-handle-collection-fork.spec.ts`); `BlockUnavailableError` (same arm as the stale test); the counter on `BlockFloors` on its own (the below-floor test exercises it end to end).
