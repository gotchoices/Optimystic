# The rebalance monitor takes a routing rule

`RebalanceMonitor` in `packages/db-p2p/src/cluster/rebalance-monitor.ts` compares, for every id in its tracked set, the cohort `findCluster` assembles now with the cohort it remembered, and reports `gained`, `lost` and `grown`. docs/blobs.md §Placement, copying and durability requires the same comparison for blobs this node holds, "by giving it the routing key rule rather than a second copy of its logic". The monitor already works on plain string ids and takes its tracked set by injection (`RebalanceMonitorDeps.trackedBlocks`); what ties it to blocks is one call, `routingKeyForBlock(blockId)` in `cohortFor`, and its module-level logger. This ticket makes both injectable, so `feat-a-referenced-blob-is-copied-to-its-cohort` can build a second instance over held blob references.

It also adds one opt-in capability the blob reaction needs and blocks do not use: re-reporting a `lost` id whose release the reaction could not confirm (see *Retained lost ids* below).

## Design

Add three optional fields to `RebalanceMonitorDeps`; every default is today's behaviour.

```ts
import type { RoutingKey } from '@optimystic/db-core';

export interface RebalanceMonitorDeps {
	// ...existing fields unchanged; `trackedBlocks` keeps its name (the existing spec and node wiring use it)
	// and its doc gains one sentence: the ids are whatever `routingKeyOf` places — block ids by default.
	/**
	 * The routing key an id is placed by. Default `routingKeyForBlock`. A blob instance passes
	 * `routingKeyForBlob` (`packages/db-core/src/network/routing-key.ts`).
	 */
	routingKeyOf?: (id: string) => RoutingKey;
	/** Logger sub-namespace. Default `'rebalance-monitor'`. The blob instance passes `'blob:copy'`. */
	logName?: string;
}
```

- `cohortFor(id)` computes `const key = (this.deps.routingKeyOf ?? routingKeyForBlock)(id)` and is otherwise unchanged (both the `findCluster` path and the FRET fallback use `key`).
- The module-level `log` becomes an instance field `private readonly log = createLogger(deps.logName ?? 'rebalance-monitor')`, assigned in the constructor; every `log(...)` in the class uses it. Nothing at module level logs today, so nothing else moves.
- No method is renamed. `trackBlock`, `untrackBlock`, `recordBlockHolders`, `getTrackedBlockCount` keep their names and take whatever ids the instance tracks; renaming them would churn the node wiring and every rebalance spec for no behaviour.

### Retained lost ids

Today an id is reported `lost` once, on the check where `wasResponsible && !isResponsible`; that check stores a non-responsible state, so the next check does not report it again. The blob reaction must keep a `responsible` hold until it confirms enough current members hold the blob, and must retry that confirmation on later checks. Add:

```ts
/**
 * The reaction could not confirm a `lost` id's release: report it in `lost` again (with its current
 * `newOwners`) on every later check while it stays tracked and this node stays outside its cohort,
 * until a reaction stops calling this. Arms the re-check timer like outstanding growth. Ignored for
 * an id with no state, or one this node is responsible for again.
 */
retainLost(id: string): void;
```

- `BlockGrowthState` gains `releasePending: boolean` (false in `emptyGrowthState` and `carryGrowthState`).
- `retainLost` sets it on the id's state when the state exists and `responsible` is false.
- In `performRebalanceCheck`, the `lost` condition becomes `!isResponsible && (wasResponsible || prior?.releasePending === true)`. The new non-responsible state is stored with `releasePending: false`, so the id is re-reported only when the reaction calls `retainLost` again for this report. A regain (`isResponsible`) builds the state through `carryGrowthState`, which clears it.
- `hasOutstandingGrowthWork` also returns true while any tracked id's state has `releasePending`, so the re-check timer re-runs the check on a quiet network.
- The block wiring in `libp2p-node-base.ts` does not call `retainLost`; block behaviour is unchanged. (Whether blocks should — the node-base comment says a retained lost block "is retried on the next rebalance", which this code path does not do — is outside this ticket.)

## Edge cases & interactions

- **Block behaviour unchanged.** Defaults reproduce today's key rule and namespace; `retainLost` is never called for blocks. The existing rebalance suites (`rebalance-monitor.spec.ts`, `rebalance-reaction.spec.ts`, `rebalance-committed-holders.spec.ts`, `rebalance-push-holders.spec.ts`, `rebalance-monitor-node-wiring.spec.ts`, `cohort-growth-heals-single-holder.spec.ts`, `unify-tracked-block-set.spec.ts`) pass unchanged.
- **A retained id regained before the next check.** `isResponsible` true: built through `carryGrowthState`, `releasePending` cleared, not reported lost; the growth arm treats it as a first observation as it would any regain. Inspection.
- **A retained id untracked.** `untrackBlock` deletes the state; `retainLost` on it afterwards is ignored. Inspection.
- **Throttle.** A re-reported lost id costs one cohort lookup per check, which is already the per-tracked-id cost; the `minRebalanceIntervalMs` throttle bounds it. Inspection.
- **Partition.** A suppressed check reports nothing and leaves `releasePending` set, so the id is re-reported on the first unsuppressed check. Inspection.

## Tests

One new case in `packages/db-p2p/test/rebalance-monitor.spec.ts`, built like the existing cases there: an id that was responsible and is reported `lost`; the handler calls `retainLost`; the next `checkNow` reports it in `lost` again with the current `newOwners`; after a check whose handler does not call `retainLost`, the following check does not report it. It pins the one new branch.

No test for `routingKeyOf` or `logName`: they are pass-throughs; the blob ticket's reaction tests exercise an instance built with them.
