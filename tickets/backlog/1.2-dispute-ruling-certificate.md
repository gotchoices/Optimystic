# The ruling certificate

## Why

Block-then-escalate needs one certificate that every outcome rests on — resuming a blocked commit, rejecting a transaction, ejecting peers, and (after commit) durably reversing it. `DisputeResolutionProof` is nearly that already: target-bound and arbitrator-set-bound votes, one vote per arbitrator, equivocators dropped, checked by `verifyInvalidationCertificate`. Three things are wrong with it for the new design:

1. **Vocabulary.** `challenger-wins` / `majority-wins` and `agree-with-challenger` / `agree-with-majority` assume the rejecting side is a minority that challenged after commit. Before commit, the rejecting side can be the cohort's majority (`right-is-right.md` Scenario 3). The sides are *approvers* and *rejecters*.
2. **Threshold.** `resolveDispute` (and the certificate verifier) decide on two thirds of the *decisive* votes. With that rule whoever collects the votes can drop some and turn a split round into a ruling for their side, and two collectors can reach opposite rulings. The design of record decides on two thirds of the arbitrators **drawn** for the round.
3. **Rounds and identity.** A ruling must name the escalation round it was decided in (each round draws a different set), and the dispute id must be the same for every party that drives the dispute — today it hashes the initiator's id and a timestamp.

## Specification

- **Outcome**: `'approvers-win' | 'rejecters-win' | 'unresolved'` everywhere `challenger-wins` / `majority-wins` / `inconclusive` appear as a dispute outcome. `rejecters-win` is what gates a durable invalidation (today's `challenger-wins`). An `unresolved` dispute produces no certificate.
- **Vote**: `'agree-with-approvers' | 'agree-with-rejecters' | 'inconclusive'`.
- **Vote payload v4**: `v4:${disputeId}:${round}:${vote}:${computedHash}:${targetHash}:${setHash}`. The round is signed so a vote from one round cannot be replayed into another. v3 and older are rejected (no back compatibility — AGENTS.md).
- **Dispute id**: a pure function of the disputed record's message hash (e.g. hash of a fixed domain tag and `messageHash`). No peer id, no timestamp. The driver's identity stays bound through its signature over the arbitrator set.
- **Proof contents** (`DisputeResolutionProof`): outcome, `messageHash`, target fields as today, `round`, the agreed-membership `epoch` the draw used, that round's `arbitratorSet` with the driver's id and `arbitratorSetSignature` (today's challenger fields, renamed to driver), and the votes. Earlier rounds are **not** carried (a driver can always fake a split by dropping votes, so carrying them proves nothing; the round cap bounds the draws).
- **Verification** keeps every binding `verifyInvalidationCertificate` has (target hash, set hash, per-arbitrator dedup, equivocator dropped from both sides, layer 1 set signature, layer 2 recompute, degradation logging) and changes the count: the winning side's distinct valid votes must reach `ceil(2/3 × arbitratorSet.length)`. It also checks `round` is a non-negative integer below the configured cap, and passes `round` and `epoch` to the recompute so layer 2 re-derives that round's draw. Expose the verifier under a name that is not invalidation-specific (it now also gates commit resumption and ejection); keep `verifyInvalidationCertificate` as the invalidation call site's use of it or rename it — no alias left behind.
- **`resolveDispute`** decides with the same rule (two thirds of the drawn set), so the producer and the verifier cannot disagree. Penalties: `rejecters-win` penalizes approvers (`FalseApproval`), `approvers-win` penalizes rejecters (`DisputeLost`) — the existing reasons, now keyed by side rather than by "challenger".
- **Conflict rule**: two valid rulings for one dispute id can only differ in round. Provide a pure `preferRuling(a, b)` that returns the one from the lower round; same round and different outcome is impossible under the threshold — assert it (throw) rather than pick.

## Edge cases & interactions

- **Round-0 behaviour equals today's single round** except for the threshold and the names — existing dispute and invalidation tests should change only in those respects. A test that relied on deciding with silent arbitrators now gets `unresolved`; that is the intended change, call it out in the handoff.
- **Cascade.** `cascade.ts` reuses the root proof unchanged; only the outcome literal moves (by inspection).
- **Log entries.** `InvalidationEntry.resolution` is persisted in collection logs. No back compatibility is required, but no persisted v3 proof exists on a live node (invalidation is dormant), so nothing needs migrating — state that in the handoff.
- **Odd sizes.** `ceil(2/3 × n)` for n = 1, 2, 3 is 1, 2, 2 — a one-arbitrator round decides on one vote. Arbitrator counts come from the cohort size (`arbitratorCount ?? K`), so n = 1 only arises with a cohort of one, which never runs consensus; note it at the threshold function.
- **Epoch.** The interim epoch (hash of the record's peers, `computeEpochBytes`) is unchanged; the proof now carries it so the verifier does not recompute it from a peer list it may not have.

## Tests

- Threshold: a round with n = 10 drawn where one side has 6 valid votes and the rest are silent does not verify; with 7 it does. Dropping votes from a proof never flips its outcome.
- `preferRuling`: lower round wins.
- Round binding: a v4 vote signed for round 0 does not verify inside a round-1 proof.
