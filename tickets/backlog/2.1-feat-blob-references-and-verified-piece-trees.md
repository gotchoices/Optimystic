# Blob references and verified piece trees

docs/blobs.md is the design of record for native large-value ("blob") support (GitHub #63). This ticket builds its foundation in `packages/db-core`: the format of a blob reference, the code that turns a byte stream into pieces and a reference, the code that checks pieces a reader receives, and the types of the node's blob service. All of it is pure logic with no network or disk access, so every later blob ticket depends on it and none of it depends on them.

New code goes in its own directory (for example `packages/db-core/src/blob/`) and is exported from `packages/db-core/src/index.ts`. Modules inside the directory import each other directly, never through a barrel (internals.md, Common Pitfalls §6).

## Requirements

**The reference** (docs/blobs.md §References and pieces). A branded string type, `BlobRef`, obtainable only from its parser. The parser accepts exactly one spelling: a CID of version 1, multibase lowercase base32 (leading `b`), multihash SHA-256 with a 32-byte digest, and codec `raw` (0x55) or `dag-pb` (0x70). It rejects everything else with `BlobRefError`, including uppercase base32, other multibases, CIDv0, other hash functions, truncated digests, other codecs, and any string whose decoded CID does not re-encode to the identical string. Because of that last rule two references are equal exactly when their strings are equal. `multiformats` (already a db-core dependency) supplies CID parsing.

**The tree builder.** Takes an `AsyncIterable<Uint8Array>` and produces the blob's pieces in an order a caller can store them as they come (children before the list piece that names them), then the reference and the byte size. Requirements:

- Leaves are raw pieces of exactly 256 KiB (262,144 bytes), the last one shorter, whatever sizes the source's chunks happen to be. Source chunks may be empty, smaller than a piece, or many pieces long.
- Above more than one leaf, list pieces are UnixFS file nodes in `dag-pb`, at most 174 children each, built as the balanced layout `ipfs add` uses, until one node remains. A one-piece blob's reference is that raw piece's CID.
- Memory held at once is bounded by one piece plus one partial list piece per tree level, never by the blob's size.
- **The CID must equal what `ipfs add --cid-version 1` produces for the same bytes.** Test vectors pin this: an empty file, a file of exactly one piece, one piece plus one byte, and a file of more than 174 pieces (so the tree has two levels). The expected CIDs are produced by running the real IPFS tool once and committed beside the test with the command that produced them. Matching requires the same protobuf details the tool writes (link names, each link's cumulative size, the UnixFS file size and per-child block sizes); the vectors are what proves them.

**The verifier and range planner.** Given a reference and a way to get a piece by CID (an injected port, so this stays network-free), yields the verified bytes of the whole blob or of a byte range `(offset, length)`, in order, top down. Every piece is hashed and compared with the CID that named it before anything under it is followed or any of its bytes is yielded. A range needs only the pieces on its path; the planner that computes which pieces those are is exposed on its own so the transfer ticket can ask for exactly those. Before following any link the reader applies the bounds docs/blobs.md lists: a piece of at most 1 MiB; a bounded number of children per list piece and of levels; child sizes that add up to the size the parent declares, and a leaf whose length equals the size its parent declared for it; only `raw` and `dag-pb`; a `dag-pb` piece must be a UnixFS file node. The exact child and level limits are named constants, at least what this builder produces (174 children, enough levels for the 1.3 TiB the doc names). A UnixFS file node that carries bytes of its own rather than only links is not produced by this builder; the recommendation is to treat it as malformed, consistent with "anything else is a malformed blob", and whichever choice is made is explicit and tested. A malformed tree throws `BlobCorruptError` and yields no bytes past the point where the fault is found; it is never partly served as if whole.

**The digest port** (docs/blobs.md, the "Hashing" paragraph). One asynchronous function, bytes in and 32 bytes out. The default uses `crypto.subtle.digest('SHA-256')` where `globalThis.crypto.subtle` exists and otherwise falls back to `@noble/hashes` (already a db-core dependency). A host may install its own, which is checked once at installation against known SHA-256 answers (at least the empty input and one multi-block input); a wrong answer throws at installation, not at first use. The builder and verifier take the port by injection.

**`routingKeyForBlob(ref)`** beside `routingKeyForBlock` in `packages/db-core/src/network/routing-key.ts`, returning the branded `RoutingKey`: the reference's 32-byte digest, not hashed again (the key network hashes once).

**The service types** (docs/blobs.md §The node's blob service): `BlobService`, `BlobPutOptions`, `BlobPutResult`, `BlobReadOptions`, `BlobStat`, `BlobScope` exactly as the doc writes them, plus the types the doc names but does not spell out (`BlobFetchOptions`, `BlobDurability`, `BlobProgressEvent`, `BlobDurabilityEvent`), whose fields follow the doc's sections on transfer and durability (durability in `DurabilityQuorum` classes). The three errors: `BlobUnavailableError` carrying the reference and a reason (`not-here`, `not-held`, `peers-unreachable`, `cohort-unreachable`), `BlobCorruptError`, `BlobRefError`.

**Dependencies.** The `dag-pb` and UnixFS codecs are declared in `packages/db-core/package.json`, pass `yarn lint:deps` (they pull `uint8arraylist`; `scripts/shared-majors.cjs` explains its standing), pass `yarn check:rn` (packages/rn-bundle-check/readme.md), and keep `packages/db-core/test/no-fret-import.spec.ts` green.

## Edge cases and interactions

- Empty source: one raw piece of zero bytes, matching the vector. Verified by the vector test.
- Exactly 256 KiB, and 256 KiB plus one byte: the boundary between a raw-leaf reference and a list piece. Vectors.
- Exactly 174 leaves and 175 leaves: one list piece against two levels. The more-than-174 vector covers the second; the planner's tests cover ranges crossing a list-piece boundary.
- Source that throws or an aborted signal partway: the builder rethrows and produces no reference. Inspection.
- Range at offset equal to size, length zero, offset past the end, length running past the end: the planner's tests fix one answer for each.
- A tree whose declared sizes disagree, a cycle-shaped or very deep tree, an oversized piece, a link of a third codec: each is `BlobCorruptError` before any further piece is requested. Tests on the verifier, since this is the logic that faces hostile input.
- A piece whose bytes do not match its CID: `BlobCorruptError`; the transfer ticket decides whether to ask another holder.
- A digest port that answers wrongly or returns the wrong length: refused at installation. Test.
- Routing: a block id's routing key is its UTF-8 text and a blob's is 32 raw bytes; the two never need to be told apart, since an equal key only means the same placement. Inspection.
