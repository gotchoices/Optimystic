# Browser storage syncs by the window — complete

Fourth of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). Implemented in `ticket(implement): browser-storage-syncs-by-the-window`; this review found nothing that changes the design and made three small fixes inline.

## What landed

- `supportsStrictDurability()` in `packages/db-p2p-storage-web/src/durability.ts` detects a browser that honours `durability: 'strict'` (the accessor is on `IDBTransaction.prototype`), asked once per store at construction and overridable with `strictDurability` on every store's options.
- Schema version 3 adds a `journal` object store: `JournalRecord`s by structured clone under their sequence number, and the applied-through mark under the string key `JOURNAL_MARK_KEY`.
- `IndexedDBJournalStore implements JournalStore` replaces the per-write driver. Reads are the old cursors unchanged. An append is one relaxed `readwrite` transaction on `journal`; an apply is one transaction over the six data stores and `journal`, strict where supported; `readJournal` is one readonly transaction. `durability` is `'power-loss'` when strict, else `'process-crash'`, and the backend then journals nothing.
- `IndexedDBRawStorage` is `KvRawStorage` over `WriteGroupDriver` over `JournalBatchBackend` over the journal store. `IndexedDBKVStore` writes through a `WriteGroup<string>` and commits each flush as one strict transaction on `kv`. `loadOrCreateBrowserPeerKey` writes a new key in one strict transaction.
- Docs: the Invariant 6 driver table, the journal-backend paragraph, the rule 3 paragraph and the survival table in `packages/db-p2p/docs/storage.md`; §1.2 and the Theorem 6 caveat in `docs/correctness.md`; a namespace row in `docs/debugging.md`; the package README (durability section, close order, eviction, what the tests can and cannot check).
- Hosts must now close the storage and the key-value store before the handle. Nothing in this repository constructs these classes outside the package, so no caller changed.

## Review findings

**Read.** The implement diff first, then `JournalStore`'s contract in `packages/db-p2p/src/storage/journal-batch-backend.ts` against the three journal methods, `WriteGroup` in `packages/db-p2p/src/storage/write-group.ts` against `IndexedDBKVStore`, `FileKVStore` for how the sibling store treats a window, the test double `MemoryJournalStore`, the spy, both specs, and the four doc sites. Ran `yarn workspace @optimystic/db-p2p-storage-web build`, its tests, `yarn lint` and `yarn lint:docs`.

**The four questions the handoff raised.**

- *A rejected request going unobserved in `Promise.all([...requests, tx.done])`.* None. `Promise.all` attaches a handler to every promise, so a second rejection after the first (the aborted transaction's `tx.done`) is handled, not unhandled. A failed request aborts the IndexedDB transaction, so a failed apply leaves nothing applied, which is what the backend's latch assumes.
- *The number range `[1, MAX_SAFE_INTEGER]` missing a record.* It cannot: the backend numbers from 1 upward, and `JournalRecord.seq` is a positive safe integer by contract. IndexedDB orders numbers before strings, so the range never reaches the string mark.
- *The key-value store treating a windowed flush as strict.* Right. `IKVStore.flush?()` takes no window, so the node never asks this store for one; the `FlushOptions` parameter exists only to mirror `FileKVStore`. Honouring a window while keeping the prefix rule would need a second journal for a store that writes a few hundred bytes a minute. The flush contract allows a sink that cannot defer to treat every window as 0, and the class doc says so.
- *The spy binding non-`transaction` members to the real handle leaving a write unrecorded.* No: a grep of the package source shows idb's one-request shortcuts used only for reads (`db.get`, `db.getAllKeys`); every write is an explicit `transaction()`. Confirmed the detection premise against the installed `fake-indexeddb`, which sets `durability` as an own property of the transaction (`FDBTransaction` constructor), so detection reads false there and the tests' override is needed. Not confirmed in a browser; no browser ran here.

**Checked and found sound.** Every request of each transaction is queued synchronously before any `await`, so no transaction auto-commits early. Two writes to one key inside one apply execute in order, which the contract requires. The relaxed append and the strict apply are serialised by the backend's own queue and by IndexedDB's ordering of overlapping readwrite transactions. The empty-apply case never reaches the store (the backend guards it). A version 2 database opens with an empty journal and recovers nothing. The data-store reads are byte-for-byte the previous driver's, so earlier data reads unchanged. The overlay-before-store snapshot in `IndexedDBKVStore.list` follows the `WriteGroup` doc. Comments say why, not what; the largest file is under 300 lines.

**Minor, fixed inline.**

- `test/support/spy-transactions.ts` called idb's wrapped `transaction` as `(db.transaction as …)(…)`, which works only because a parenthesised member expression keeps its `this`; idb's wrapper unwraps `this` to reach the native database, so a routine refactor to a local would have thrown. Now `Reflect.apply(…, db, …)` with a comment. Dropped a redundant spread.
- The `NOTE:` at `durability` in `src/indexeddb-storage.ts` had a broken sentence ("but nor do browsers promise"); reworded.
- Added one store-level test: `readJournal` leaves out a journal value that is not a record and reads a malformed mark as 0. The implementer added that shape check as a departure from the ticket (which said no codec was needed) and left its branching unverified; the contract on `JournalStore.readJournal` names the behaviour.

**Tests.** The three window tests each pin a distinct clause of the specification (append relaxed on `journal` alone, apply strict over data and journal by the deadline; a strict flush applies the held groups too; journaled groups survive the page going away). The key-value flush test pins one strict transaction per flush. None restates the implementation or verifies a mock; none cut.

**Major.** None. No class-level invariant is missing: the ordering half of the durability guarantee rests on `JournalBatchBackend`, which the earlier ticket owns and tests, and this store adds only the engine binding.

**Tripwires, recorded at their sites.**

- The two existing `NOTE:`s stand: the `durability` note (rule 3 does not hold without strict transactions) and the `identity` note (two tabs over one database run two nodes over one store, which Invariant 5 forbids and nothing enforces).
- A journal value this build cannot read is left out of `readJournal` but never deleted, since `discard` names only records that were read. It is logged on every open until the next append overwrites that key; one below the mark stays for the life of the database. Harmless, and reachable only by another build writing under a number key. Not recorded as a comment: the `read-journal` log line already names it and the fix, deleting unreadable keys in the recovery apply, would widen `applyJournal`'s contract for a case nothing produces.

**Not verified, by reason.** No browser ran: `fake-indexeddb` has no disk, so every test checks which durability a transaction asked for. The `'process-crash'` branch (a browser without strict transactions) is covered by inspection only: detection false → the backend applies each group at once as one relaxed transaction → the node's start-up line keys on the durability value. The version 2 to 3 upgrade is untested, which backlog `debt-indexeddb-version-upgrade-is-untested-and-unhandled` already carries. Not run: `yarn check:rn` (this package is not in the React Native bundle), `yarn test:integration`, and the root test fan-out beyond this package (no other package imports it).

**Open tickets touching these files.** Only `debt-indexeddb-version-upgrade-is-untested-and-unhandled` (backlog) names `src/db.ts` and the storage spec; its arms are unchanged by this review. No new ticket filed.
