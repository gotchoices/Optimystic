# A redirect can send a reader to itself — complete

GitHub #65. A read-only browser node sent a repo `get` to a host. The host's view of the block's cohort included the browser, so its redirect listed the browser's own peer id; the browser picked itself, libp2p refused the self-dial, and the read failed as peers-unreachable.

## What landed

- **Asker side.** `IPeerNetwork` has an optional `localPeerId`, implemented by `Libp2pKeyPeerNetwork` over `libp2p.peerId`. `RepoClient` and `ClusterClient` both pick a redirect target through `pickRedirectTarget(peers, askedId, localId)` in `packages/db-p2p/src/repo/redirect.ts`: the first listed peer that is neither the peer just asked nor this node. If none is left it throws, which the writer's transactor treats as a failed coordinator. The pick runs before any address learning or coordinator hint, so neither is recorded for a filtered-out peer. Every production client is built over a `Libp2pKeyPeerNetwork` (`libp2p-node-base.ts`, `ClusterMember`'s client factory, the Quereus `CollectionFactory`, the reference peer CLI), so the field is always present in production.
- **Redirecting side.** `RepoService.checkRedirect` gets the connection's remote peer from `handleIncomingStream`. `ClusterService.checkRedirect` gets the dialer from `processOperation`, through `processRecord` and the carried-records hook. Each leaves the requester out of the redirect list. If no peer is left, it logs `redirect:only-requester` and processes the request locally: `CoordinatorRepo` serves a read and refuses a write, and a cluster member signs a `self-not-member` reject vote. `RepoService` still stamps `message.cluster` with the whole cohort.

The commit for this work has the subject `ticket(implement): a-redirect-can-send-a-reader-to-itself`.

## Review findings

**What was checked.** I read the implement diff before the handoff. I checked both redirect branches, both services' requester threading (single-op, batch and carried-record paths all go through the one `checkRedirect` call per service), every production construction of `RepoClient` and `ClusterClient`, whether anything matched the removed "same peer" error text (nothing does), and the docs.

- **Correctness (happy path, edge cases, errors).** I found no defects. Leaving the requester out cannot hide a correct target: the requester is the peer that asked, so sending it back to itself is never right. The client-side filter is the matching guard for a host on an older build. Before the change, the fallback `?? peers[0]` followed by a same-peer throw had the same outcome for the asked peer. The new function only adds this node to the excluded set.
- **Test gap closed (minor, fixed).** The handoff said the `RepoService` requester wiring was untested end to end. I replaced the direct `checkRedirect` "handles the request locally when the requesting peer is the only one to redirect to" case in `redirect.spec.ts` with a version that goes through `handleIncomingStream` with a connection whose `remotePeer` is the requester. It asserts that the `get` reaches the repo and that no redirect is answered. I confirmed it fails when the handler passes `undefined` instead of the peer. The test count is unchanged (one moved, not added).
- **Tests cut.** None. The other new specs each pin a distinct branch: the #65 reproduction on the client, the no-other-peer throw, and the filtered payload with the cohort stamp kept on the message. The cluster `processOperation` case also covers the dialer threading.
- **Docs (minor, fixed).** `docs/internals.md` §Proximity Verification was already updated. `packages/db-p2p/docs/repo.md` §Responsibility K and the redirect-skip check still said a node "redirects to the cluster's actual members", so I added the requester exclusion and the local fallback, with a link to that section.
- **Second hop can name the original asker.** On a second hop, the list is filtered against the second peer and this node, but not the first peer asked. The existing two-hop limit bounds this, so it ends as a "max hops" failure rather than a loop. I left it as is. It is not a tripwire, because the limit already covers it.
- **Redirects bypass the network-membership predicate.** This is unchanged, and the existing `NOTE:` in `RepoClient` already covers it.
- **Root cause of edge readers in cohorts.** This belongs to plan ticket `client-only-node`. The fix here stands without it, because two serving nodes with different cohort views can produce the same redirect.
- **Type safety, resource cleanup, performance, size.** No findings. The new parameters are optional and typed `PeerId`, and the filter is linear over a cohort-sized list. No resources were added, and no file grew meaningfully.
- **Validation.** `yarn workspace @optimystic/db-p2p test`: 3660 passing, 75 pending, 0 failing. `yarn lint:docs`: all resolve. eslint on the edited spec: clean. I did not run `yarn test:integration` or the other packages' suites. The source change is confined to db-p2p's redirect paths plus one optional db-core type field, which the db-core build type-checks.
