# Commit proofs moved out of the transactions keyspace into their own store

## What landed

A node stores two kinds of record per block: the **transforms** that make up its history,
and the **commit proofs** that certify particular revisions. Both used to live in the
transactions store, separated only by a naming convention — a proof for revision *N* was
filed under a made-up action id `~proof:<N>`, assuming no real action id starts with `~`.

Nothing enforced that. An action id is chosen by whoever originates a write and is never
re-derived or format-checked by the node that stores it, so a client's `pend`, a peer's
restore archive, or a peer-supplied revision record could name that exact id. Whichever
write landed second won, silently — and a revision record naming it made
`materializeBlock` read the stored *proof* back as if it were that revision's transform.

Proofs now live in their own logical store keyed by `(blockId, rev)` — the same key shape
the revisions store uses. There is no key a transform and a proof can both name, so the
collision is unrepresentable rather than guarded against. `blockProofActionKey` and its
reserved-namespace doc block are gone.

`RawStoreDriver` gained `getProof(blockId, rev)` / `putProof(blockId, rev, value)`;
`KvRawStorage.getBlockProof` / `saveBlockProof` delegate to them. The public
`IRawStorage` surface is unchanged. Per-backend layout follows each backend's existing
convention: a sixth in-memory `Map`; `basePath/<blockId>/proofs/<rev>.json` on the
filesystem; a `proofs (block_id, rev, value)` SQLite table; `TAG_PROOFS = 0x06` in
LevelDB; a `proofs` object store in IndexedDB (with `DEFAULT_DB_VERSION` bumped 1 to 2).
No `deleteProof` — matching the pre-existing contract that a proof lives and dies with
its revision record, and no revision-delete site exists. No data migration; AGENTS.md
states backwards compatibility is not yet a concern, and losing an already-written proof
degrades to corroboration, which is an already-supported state.

`CachedStoreDriver` passes proofs **straight through** — no cache namespace. Proof reads
happen on repair and archive-serving paths, not the hot read path.

## Review findings

Reviewed the implement diff (`3089fe7f`) file by file before reading its handoff summary,
then swept the call sites and docs the change did not touch but should have.

### Verified sound — no change needed

- **No leftover references.** `blockProofActionKey` and the `~proof:` literal survive only
  inside the new tests and the doc comments that explain the old bug. Nothing in
  production code derives a proof key from an action id any more.
- **Every byte-accounting sweep is store-agnostic and needs no proofs arm.** The
  filesystem walks the directory tree recursively, SQLite reads `PRAGMA page_count`,
  LevelDB iterates the whole keyspace, IndexedDB asks `navigator.storage.estimate()`. Only
  the in-memory driver enumerates named maps, and that one *was* updated.
- **No per-block purge or store enumeration misses the new store.** There is no
  `listTransactions`; `recover()` and `materializeBlock` probe action ids read from the
  revisions store; `blockEnvelopeRange` in the LevelDB backend is used only for
  `TAG_PENDING`. Nothing sweeps a block across all tags today, so `TAG_PROOFS = 0x06`
  needs no registration anywhere. (A future per-block sweep would have to include it —
  parked as a tripwire below.)
- **Every `RawStoreDriver` implementation is updated**, including the three test doubles.
- **The SQLite no-`user_version`-bump asymmetry with IndexedDB is correct.** `applySchema`
  runs its `CREATE TABLE IF NOT EXISTS` DDL on every open, so an existing database gains
  the `proofs` table without any version branch; IndexedDB needs a version bump to run its
  `upgrade` hook at all. The two backends genuinely differ here.
- **`atomicWriteFile` creates the parent directory**, so the new `proofs/` subdirectory
  needs no explicit `mkdir`. The filesystem read takes the corrupt-content-as-missing JSON
  guard, correctly — proofs are JSON-valued, unlike the bare-string revisions store.
- **The regression spec running only against `MemoryRawStorage` is adequate**, contrary to
  the handoff's own concern. Every route it drives (`pend`/`commit`, `saveReplica`, the
  `materializeBlock` replay) goes through `IRawStorage`, which is backend-independent, and
  the conformance suite's collision case runs the keyspace claim against all five
  backends. Duplicating the `StorageRepo` cases per backend would test the same code path
  five times.

### Found and fixed in this pass

- **A stale LevelDB test no longer covered every store.** `leveldb-storage.spec.ts`'s
  "listBlockIds enumerates only TAG_METADATA keys" case writes a row into every *other*
  store to prove none leaks into the metadata range, and its comment named "tags
  0x02..0x05". The new `TAG_PROOFS = 0x06` store was never written, so the case silently
  stopped being exhaustive. Added a `saveBlockProof` row and corrected the tag range.
- **`revisionKey` and `proofKey` were byte-identical bodies.** Extracted `revScopedKey(tag,
  blockId, rev)` in `db-p2p-storage-rn/src/keys.ts` so the two rev-keyed stores cannot
  drift apart in their suffix encoding.
- **Three copies of the proof-shaped test fixture.** `makeProof` was duplicated in the
  conformance suite and the new regression spec, and this pass was about to add a third
  and fourth. Exported the conformance suite's version (already published as
  `@optimystic/db-p2p/testing/conformance`) and deleted the copies.
- **Nothing pinned the cache passthrough.** Added "proofs are never cached: every read
  reaches the inner driver" to `cached-raw-storage.spec.ts`, asserting both a hit and a
  miss fall through on every call. Without it, someone adding a proofs cache namespace
  without coherence rules — the failure mode the old shared-keyspace design had — would
  break nothing visible.
- **Five README files still described five stores.** The change updated `docs/internals.md`
  and the source doc comments but left every package README stale: the `ns` README's table
  and "six tables / five block-storage tables" counts, the `web` README's table and store
  counts, the `fs` README's on-disk layout tree, the `rn` README's intro, and the
  `db-p2p` README's copy of the filesystem layout. All now list the proofs store.

### Filed as a new ticket

- `backlog/debt-indexeddb-version-upgrade-is-untested-and-unhandled` — the change made
  the browser backend's *first ever* schema version bump, which turns two dormant paths
  live. The version-1-to-2 upgrade is never executed by the suite (every case opens a
  fresh uniquely-named database), and a browser tab holding the old version open makes the
  new tab's database open request wait indefinitely with nothing logged. The second arm's
  remedy is a behaviour choice — closing the old connection breaks that tab's storage —
  so it is a maintainer decision, not a mechanical fix. Both arms are dormant until the
  first browser release, which is why this is backlog rather than fix.

### Recorded as tripwires, not tickets

- `cached-store-driver.ts` — the implementer's existing `NOTE:` at the proofs passthrough:
  if proof reads ever show up hot, give proofs their own cache namespace. Confirmed still
  the right call; proof reads are repair and archive-serving only. Left as-is.
- `db-p2p-storage-rn/src/keys.ts` — the file's own header already documents that tag bytes
  are deliberately spaced so a new store can slot in. Nothing sweeps a block across all
  tags today; the day one does, it must include `TAG_PROOFS`. Covered by that header note
  plus the now-exhaustive LevelDB listBlockIds case, which fails if a new tag leaks.

### Considered and declined

- The proof-lifetime contract note now appears in both `i-raw-storage.ts` and
  `raw-store-driver.ts`. That is two layers stating the same invariant at their own
  boundary, which is what each reader needs; not worth collapsing.
