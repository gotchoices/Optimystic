## What was built

A pending record is **abandoned** when three facts hold, all recorded by the node at the moment it saved the record: the writer ran in this node's process (`MessageOptions.localWriter`, a non-wire option the in-process transactor sets on a pend sent to its own node; the repo protocol copies only `expiration` onto the wire and the service builds options from the message, so a remote writer cannot claim it); the node applied the pend alone, with no consensus (`CoordinatorRepo.pendSolo` is the one path that hands the writer's options through to storage, and the Quereus plugin's `local` transactor, which writes to a `StorageRepo` with no node at all, sets the same mark); and the process that saved it is over (`StorageRepo.runId`, stamped into a third sibling metadata map, `BlockMetadata.pendingRuns`, written, dropped and swept in the same metadata writes as the slot and the base). `isAbandonedClaim` is the predicate. Both rival scans ask it ahead of the slot rule: `StorageRepo.pend` sets abandoned records aside and deletes them under the same latch hold before saving the newcomer's record, and `ClusterMember.reservingRivals` skips them at the vote. A record with no stamp is never abandoned, so a remote writer's record, a coordinated write's record and metadata from the release before the field all behave as before.

`IBlockStorage.savePendingTransaction` takes the three claim values as one `PendingClaimFields` object. `IPendingClaimReader.runId` is required, so a claims reader says which run it is, and one that cannot judges nothing abandoned.

## Review findings

**Read first, before the handoff:** the implement commit's full source diff, every test it touched, and the four docs it touched; then the plumbing on either side of it (`RepoClient`, `RepoService`, the cluster member's own apply, the served-repo proxy, the mesh harness's in-process routing, the plugin's transactor factories) to check where the mark can and cannot travel.

**Checked and found correct:**
- The mark cannot reach a remote node. `RepoClient` sends `expiration` alone, `RepoService` builds `{ expiration }` from the message, and the mesh harness routes options in process but the transactor keys the mark on the peer each batch goes to, so another node's repo never sees it.
- The cluster member's apply passes no options (`localApply().pend(pend, undefined, …)`), so a coordinated record is never stamped on any member, this node's included.
- The two deciding pass-1 reads and the pass-2 delete share one latch hold, so a concurrent re-pend of the dead action either is seen by the judgement or lands after the delete. A live rival found in pass 1 returns the refusal before any delete, which only postpones the drop to the next admitted pend.
- The own-action redelivery shape (the offline queue's restore under the same action id) overwrites the record and its stamp at the block tier and, at the repo tier, finds its own earlier-run record abandoned and deletes it before saving the fresh one; the outcome is the same live record either way.
- `pendingRuns` reads without migration from metadata that predates it, which the upgrade-check suite exercises against every recorded release fixture.
- Docs: `docs/repository.md`, `packages/db-p2p/docs/storage.md`, `docs/internals.md` and `docs/debugging.md` describe the new reality; `yarn lint:docs` resolves every citation.

**Found and fixed in this pass:**
- **The run identity was per `StorageRepo`, and that is wrong in a shape this repository already runs.** The implementer stamped with an id minted per `StorageRepo` and recorded the hazard as a `NOTE:` ("a host that rebuilds its node in one process"). Extending the mark to the plugin's `local` transactor (next bullet) reached that hazard at once: `packages/quereus-plugin-optimystic/test/concurrent-insert-refusal.spec.ts` and `concurrent-secondary-unique-refusal.spec.ts` open two `Database` handles over one file-storage directory, each with its own `local` transactor and so its own `StorageRepo`, and each repo judged the other's live record abandoned and deleted it from under its commit (`Pending action … not found`, four failures). This retires the hazard class rather than the instance: two repos in one process over one store are one run and judge each other by the slot rule, and the implementer's `NOTE:` at `isAbandonedClaim` and at `StorageRepo.runId` is replaced by the reason the run is the process's. The two plugin specs pass again, and the storage-repo spec's two-run cases, which pass explicit run ids, are unchanged.
- **The Quereus plugin's `local` transactor had the same wedge and no mark.** It writes to a `StorageRepo` in its own process over a persistent `rawStorageFactory` store with no node, so a process exit between a write's pend and its commit left exactly the record GitHub #54 describes, and nothing judged it. The only option storage reads is that mark, and the member's own apply already passes no options, so the fallback now passes `undefined` the same way and the helper is deleted. `pendSolo` is literally the one path that hands the writer's options through, as `docs/repository.md` says.
