## What changed

Quereus 5.4 sends `request.limit` / `request.offset` for `order by … limit n` (constant: `tryLimitedSortAbsorb`; `limit ?`: one request per bound, `tryRuntimeLimitChoice` / `largestOrderedBound`; all through `probeAccessPlan`, which re-asks without the limit when the chosen plan leaves a filter unclaimed). Nothing of the limit reaches `query()`. The plugin's planner now uses it:

- **One licence rule** — `rowsReadUnderLimit(request, rows, deliversOrdering, handledFilters)`: `min(rows, limit + offset)` when a limit was sent, the candidate delivers the required ordering (or none is required), and it claims every filter; `rows` otherwise. Mirrors `rowsToProduce` in `@quereus/quereus-store/src/common/store-module-access-plan.ts`, except it does not clamp to 1 (so `limit 0` costs one descent). It sizes the per-row cost term only; every candidate's `rows` stays the cardinality.
- **Walk with no filter** — `unfilteredWalkCost`: `seekCost + ROW_FETCH_COST(5) · min(wanted, 256)`, plus `tableScanCost + sortCost(tableRowCount)` when `wanted > 256`. `tableScanCost` now rides in `PlanPricing`. Consequences: a page of ≤ 256 rows is walked; an unlimited ordered read of a table over 256 rows (an un-analyzed table is assumed to hold 1000) is a scan and sort; a `limit ?` gets a `LimitChoiceNode` bound of at most 256.
- **Walk under residual filters** — unchanged price, `seekCost + tableRowCount`, ignoring any limit. Recorded as an accepted-tradeoff `NOTE:` on `orderedWalkCandidate` with the revisit condition (backlog `feat-an-ordered-walk-tests-its-own-residual-filters`).
- **Equality and range seeks** — their row term goes through `rowsReadUnderLimit`. A range with a second same-side bound or another column's filter stays unlicensed.
- **`WALK_ROWS_BEFORE_SCAN`** stays for every walk and range; its doc no longer claims the limit never reaches the module, and its `NOTE:` carries the new revisit condition (lift the switch and drop the scan term if Quereus ever forwards a licensed `limit + offset` to `query()`). The walk does no explicit truncation, and the doc comment on `orderedWalkCandidate` says why (`inEngineOrder` reorders runs).
- Every `feat-sort-absorb-blind-to-limit-general` citation is gone (code, the spec comment, docs). `yarn lint:docs` is clean.

## Tests (what each verifies)

`ordering-claim-guard.spec.ts`:
- New — "walks a page of an ordered read with no filter, and leaves the whole read, or a page past the switch, to the engine": over 1,000,000 rows, unlimited → `expectSorted` and a plain scan; `limit 10` → backward walk, cost far below the scan, `rows` still the table size; `limit 300` → sorted; `limit 250 offset 50` → sorted (the offset counts). Replaces "prices a plan-time limit as the rows it stops after".
- Extended — "beats a scan the engine would sort under a residual filter, priced alike with a limit and without": the residual walk's cost is identical with `limit: 10`.
- New — "prices an ordered seek that claims every filter by the rows a limit stops it after, and one that leaves a residual by all of them": a prefix-range seek costs under 1/100 with `limit: 10`; with a second lower bound left residual its cost is unchanged by the limit. This is the one case that covers the helper's filter branch, since the walk's residual branch does not call it.
- Adapted — every no-filter claim case in "Ordering claims of an index walk" now passes `PAGE` (`limit 20`), including the `expectSorted` ones, so they fail on the claim and not on pricing. Reworded the comment of "beats the same seek when the seek matches most of the table" to describe the bet; the case still walks.

`index-ordered-walk.spec.ts`:
- `PAGE` (`limit 100`, larger than the 42-row table, so every row is still compared) on the no-filter shapes of "An index walk serves order by", the transaction-staged case and the left-behind-entry case included, so they still exercise the walk.
- A `measured` copy of the table, run through `analyze`, for the explicit `nulls first` arms (gap 1 below); there an unlimited walk legitimately wins (40-odd rows).
- `EVERY_ROW` (`where n >= 0`, an unindexed column; the long table now uses the shared `COLUMNS`) on the long-walk shapes that must read past 256: forward, backward, `limit 300`, and the nullable `order by u, id`. They still assert `INDEXSCAN`/no `SORT`, `scan=1`, `matched=256`.

## Validation (timing)

Recorded in *Finishing by scanning*. Node, `transactor='test'`, medians of 41 runs, on a machine running other work, 2,000 / 5,000 rows. The old plan was reproduced on the same build by answering the unlimited request with the plan for a one-row page (the walk, which then runs unlimited and switches):
- unlimited `order by t, id`: scan and sort (new) 13–19 ms / 52–54 ms, against walk then switch (old) 30–33 ms / 57–58 ms. Never slower.
- `limit 200`: walk 15 / 19 ms, against forced scan and sort 18 / 47 ms.

These are noisy (two runs of the same shape differed by up to 6 ms). `ROW_FETCH_COST` was not tuned to them.

## Known gaps (as handed off by implement)

1. **A spelled-out `nulls first` page regressed to scan and sort.** `sortKeysAsTableOrdering` in `@quereus/quereus/src/planner/rules/retrieve/rule-grow-retrieve.ts` refuses to absorb a Sort with any explicit `nulls`, so `order by t nulls first limit 20` reaches the module only through the physical pass, which carries the ordering but no limit. With a filter it carries no ordering at all, and that part was already so. Before this ticket the unlimited price still chose the walk; now, on a table over 256 rows, the engine sorts it. Verified with a probe of the requests the engine sends. Recorded as a `NOTE:` on `orderedWalkCandidate` and in *Pricing*. The fix belongs in Quereus (treat explicit `nulls first` as the default it is), which is outside this repo, so I did not file anything. Decide whether it merits a `blocked/` ticket.
2. **Small un-analyzed tables now sort.** An un-analyzed table is priced at 1000 rows, so an unlimited no-filter ordered read of, say, 42 rows is a scan and sort where it used to walk. That is correct under the agreed rule, and both are cheap at that size. I did not measure it.
3. **Seeks are still priced at 1 a row** although they fetch like a walk (about 5). Out of scope by decision; stated in *Pricing* as a known approximation.
4. **Candidates outside the helper.** The full scan, the partial-PK scan and the PK multi-seek do not go through `rowsReadUnderLimit`. By inspection this does not matter: the scan claims no filter and delivers no ordering whenever another candidate competes, and the multi-seek's cost has no per-row term. Check that you agree.
5. `index-ordered-walk.spec.ts` now depends on `analyze` working on an Optimystic table (it does, and `alter-table-arms.spec.ts` already relies on it).

## Review findings

Read the `ticket(implement): an-ordered-read-prices-and-stops-at-the-limit-the-engine-sends` diff first, then the handoff. This pass resumed an interrupted one, whose only change, the plugin README, had already been committed.

- **Correctness of the pricing.** Checked by hand against `getBestAccessPlan`: `rowsReadUnderLimit` (limit 0, offset with no limit, no ordering required, unclaimed filters), `unfilteredWalkCost` against the scan candidate's `tableScanCost + sortCost` (past 256 the walk always loses by its own fetches, so a `limit ?` bisection stays monotone), and the residual walk's unchanged price. No defect found.
- **Gap 4 (candidates outside the helper).** Agreed. The full scan, the partial-PK scan and the PK range claim no filter, so they could never hold the licence when another candidate competes; the PK multi-seek and point lookup have no per-row term.

First, "a page of up to 256 rows is walked" does not hold on a table of a few hundred rows: there `tableScanCost` is floored at 1000 and a page near 256 is priced, correctly, as a scan and sort (300 rows with `limit 256`: about 1247 against 1296). The wording in internals.md *Pricing* and in the README now says so. Second, the README said a filtered ordered read "is walked whatever its limit". A selective seek can still win, so it now says the read "is priced the same whatever its limit". The interrupted pass had already replaced the README sentence claiming a `LIMIT` never reaches the planner. `yarn lint:docs` is clean.

It is already recorded as a `NOTE:` on `orderedWalkCandidate` and in *Pricing*. No ticket filed: it is a cost-only effect on a rarely spelled-out sort key, and there is no anchor in this repo to serve.
