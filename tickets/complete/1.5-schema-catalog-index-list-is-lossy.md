# Complete: persisted schema `indexes` list made durable across nodes

Implemented and reviewed. Build, lint, typecheck and the plugin package's full suite are
green: **463 passing, 11 pending** (`yarn test` in `packages/quereus-plugin-optimystic`;
454 → 463 is the nine tests this review added). Repo-root `yarn lint` and `yarn typecheck`
both clean.

## What shipped

**The choke point — every schema write is non-destructive for `indexes`.**
`SchemaManager.storeStoredSchema` re-reads the table's catalog entry through the write
tree immediately before writing and unions the incoming index list with what is persisted
right now (`mergeIndexLists`). Union rules: an index on either side survives (incoming
order first, persisted-only appended); uniqueness never silently downgrades. The method
returns the schema **actually written** and refreshes the per-instance cache with it only
after the write succeeds; all callers honour the returned value. There is no index-removal
path in the plugin today (DROP TABLE tombstones the whole record), so union and correct
coincide; a future DROP INDEX needs a dedicated removal API.

**Site A (clobber-on-unreadable-read).** `doInitialize`'s mismatch branch no longer treats
"persisted read came back empty" as proof of absence: the contract is stated at the call
site, a debug log fires when it writes with no persisted side visible, and the write-time
union preserves any index list the read could not see. The write-then-read-back detour was
replaced by the store's return value.

**Site B (stale cache / lost update).** New `SchemaManager.getSchemaFresh` reads the
catalog first, bypassing the never-invalidated per-instance cache, falling back to the
cache only when the catalog read yields nothing. `addIndex` — the mutating path — uses it;
`getSchema` keeps cached behaviour for read paths (hydrate seeding perf). Both contracts
are documented on the methods.

**Ordering fix the union forced.** A union-widened schema can list a sibling's index this
vtab has no tree for, and `IndexManager.insertIndexEntries` throws for a listed index
without a registered tree. Both `addIndex` paths therefore route through
`reconcileMaintainedIndexes` (which opens/registers trees for every declared index and
registers collections with the transaction bridge) before folding the schema in.

**Discovery during implementation.** The assumed-pending prerequisite
`repo-reports-unavailable-vs-absent` had already landed, so a *provably* indeterminate
block read throws `BlockUnavailableError` out of `getSchema` — the "unreachable catalog"
arm of Site A already fails loudly. The residual undetectable case is a cohort that
*silently* answers "nothing". Stale comments claiming the layers "cannot yet distinguish"
were corrected to that narrower reality.

## Review findings

Read the implement diff (`git show 1d09e5a`) before the handoff summary. Ran repo-root
`yarn lint` and `yarn typecheck` (both clean) and the plugin package's `yarn test`.

### Fixed inline (minor)

- **`doInitialize`'s candidate merge did not use the same rule as the write path.** It
  substituted the persisted index list only when the local declaration listed *no*
  indexes; otherwise it compared a candidate the write path would then widen. Result: a
  vtab whose local schema carried a strict subset of the persisted index list missed the
  no-write short-circuit and re-wrote a byte-identical record on **every open**, forever
  (the write's union re-added the missing index each time, so it never converged). Now
  uses `mergeIndexLists` — the same function the write path uses — so what is compared is
  what a write would produce. Persisted outcome is unchanged either way; this removes the
  redundant writes and the duplicated merge rule. `optimystic-module.ts`, `doInitialize`.

- **`deleteSchema`'s accepted-tradeoff NOTE had its revisit condition tripped**, as the
  implementer flagged. The NOTE said: once `repo-reports-unavailable-vs-absent` lands, make
  the drop a no-op on an absent catalog instead of create-on-missing. That ticket landed and
  the delete still invented the catalog — meaning a node whose read of a real remote catalog
  came back empty could commit a locally-invented *empty* catalog, erasing every other
  table's entry, in order to tombstone one table. Now opens the catalog open-only and
  returns when there is none. Losing one drop's tombstone is recoverable; losing the catalog
  is not. `schema-manager.ts`.

- **`mergeIndexLists` was added to the package's public exports purely for test access**
  (the export comment said so). Tests in this package already import from `../src/…`
  (e.g. `key-tuple-types.spec.ts`), so the public API did not need to grow. Export reverted;
  the durability spec imports from `../src/schema/schema-manager.js`.

### Test gaps closed

The implementer's three tests (clobber pin, lost-update pin, `mergeIndexLists` units)
covered the two loss modes end-to-end but left the choke point itself only indirectly
exercised. Added `test/schema-catalog-write-path.spec.ts` — nine tests driving
`SchemaManager` over a stand-in catalog tree whose state and failures are dictated per
case, pinning: the write-time union for a caller that never read the catalog; the
`[name, schema]` tuple shape the catalog's keyExtractor requires; a tombstoned entry
treated as absent rather than as an index list to merge (a resurrection guard nothing
covered); the cache left untouched when the write throws; create-on-missing on the write
path; `getSchemaFresh` preferring the catalog and falling back to the cache; and both
`deleteSchema` arms.

**One gap left open, deliberately.** The redundant-write fix above has no regression test.
Observing it requires a vtab whose in-memory schema carries a strict subset of the
persisted index list at initialization time, and every in-process route to that state
(fresh `Database` + hydrate) re-reads the catalog and lands on the equal case. Its
correctness-relevant half — the list never shrinks — is pinned by the existing clobber test
and the `mergeIndexLists` units; only the write-count is unpinned.

### Filed as tickets (major)

- **`backlog/bug-persisted-index-outlives-the-columns-it-points-at`** — verified
  wrong-result. Persisted index descriptors name their columns **by position**, and a
  re-declared `CREATE TABLE` with a reordered column layout (no DROP) rewrites the columns
  while deliberately preserving the indexes: `idx_b` ends up declared over a different
  column than its name says, and a matching row then silently vanishes from an indexed
  lookup while a full scan still returns it. Reproduced end-to-end during this review
  (repro and observed output in the ticket). **Pre-existing** — the preserve-indexes rule
  predates this ticket and the reproduction takes the old path; the union generalised the
  rule without changing what is persisted here. Filed at the representation rung rather
  than as a guard at the write site: naming index columns instead of numbering them makes
  the bad state unrepresentable.

- **`backlog/debt-optimystic-vtab-class-is-too-big-to-review`** — `optimystic-module.ts` is
  3000 lines (`wc -l`), of which `OptimysticVirtualTable` is a single ~2080-line class.
  Not caused by this diff (which added ~30 lines), but it is the reason reviews of this
  file must hold schema resolution, index maintenance and transaction bridging in one head
  — and several recently-fixed defects, including this ticket's ordering fix, were exactly
  mistakes *between* those concerns.

### Recorded as tripwires, not tickets

- **`addIndex`'s populate loop stages into every maintained index, not just the new one**
  — `insertIndexEntries` iterates the manager's whole index set, so building an index
  re-writes each existing row's entry into every sibling index too. Idempotent and correct;
  the cost is write volume of rows × indexes rather than rows. Pre-existing (the old
  `setSchema(updatedSchema)` already put every index in the maintained set), and fine while
  `CREATE INDEX` is cold-path DDL on modest tables. `NOTE:` at the loop in
  `optimystic-module.ts`, naming the fix (a single-index staging entry point on
  `IndexManager`) and the condition that would call for it.

### Checked and clear

- **Transactor threading.** `addIndex` calls `getSchemaFresh` without a transactor while
  the subsequent write passes one — worth checking, because previously that read was a
  cache hit and could not miss. It is fine: `CollectionFactory.resolveTreeArgs` resolves
  the transactor from options and ignores `txnState.transactor`, and the schema-tree
  closure builds a throwaway `txnState` with a fresh (never-shared) collections map, so the
  argument cannot change which storage the catalog read sees.
- **Write visibility.** `Tree.replace` stages *and* flushes (`updateAndSync`), so a schema
  write is durable before `getSchemaFresh`'s next open — the bypassed cache cannot make a
  just-written schema invisible.
- **Resurrection after DROP.** The write-time union skips tombstones (`entry[1] ===
  undefined`), so re-creating a dropped table does not inherit the dead schema's indexes.
  Now pinned by a test.
- **Scope of the union.** Only `indexes` is merged; `columns`, `primaryKeyDefinition` and
  `uniqueConstraints` are still whole-record overwrites from the local declaration. That is
  correct by design — those arrive complete in the `CREATE TABLE` statement, whereas
  indexes arrive as separate later statements — and it is what the "local DDL wins on
  shape" contract means. (The cost of that contract is the column-layout bug filed above.)
- **Resource cleanup / error handling.** No new resources. `storeStoredSchema` lets write
  failures propagate and no longer poisons the cache on the way out; `deleteSchema` remains
  best-effort by its caller's contract.
- **Docs.** No file under `docs/` describes the schema catalog's write rules — the
  contracts live as doc comments on `SchemaManager`, which this change updated (read/write
  docs, `doInitialize`'s contract, `reconcileMaintainedIndexes`'s NOTE) and this review
  extended (`deleteSchema`). Nothing else was found stale.

### Considered and left alone

- `reconcileMaintainedIndexes` still REPLACES the manager's index list rather than unioning.
  Its NOTE already records this with the supply side now closed and names the union as the
  hardening if a narrower schema ever reaches it. No new evidence that it does; left as-is.
- The residuals the implementer listed honestly — no compare-and-swap around the pre-write
  read (window shrunk from "since first cached read" to milliseconds; the real fix is the
  schema-versioning design parked in `backlog/more-design/6.5-schema-versioning`, which
  cites this ticket), the write path's own read still being fooled by a silently-empty
  cohort answer (needs the responders count tracked as the coordinator-repo tripwire in
  `complete/4.5-repo-reports-unavailable-vs-absent`), and `getSchemaFresh`'s cache fallback
  outliving a concurrent DROP (pre-existing class: cross-node DDL has no coordination) —
  all have existing homes and are documented at their sites. Not re-filed.
- The synthetic reproductions (factory interception, two in-process plugin instances) are
  faithful to both mechanisms; no two-real-node mesh test drives either end-to-end. The
  original fix ticket's eight mesh shapes all converged even pre-fix, so a mesh test would
  not have caught this. Left as-is.
