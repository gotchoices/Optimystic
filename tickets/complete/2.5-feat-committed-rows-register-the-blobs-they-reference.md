# Committed rows register the blobs they reference

Built in `packages/db-core`, no SQL (implement commit: `ticket(implement): feat-committed-rows-register-the-blobs-they-reference`).

- **Key framing** (`reference-key.ts`): a reference-tree key is `ref + '\u0000' + referrer`; `blobReferenceKey` refuses a non-reference, `decodeBlobReferenceKey` splits at the first separator, `blobReferenceBounds` / `blobReferenceRange` give one reference's run `[ref\u0000, ref\u0001)`.
- **Reference tree** (`reference-tree.ts`): entry `[key, ref]`; `blobReferenceAction` is a pure, unguarded, validate-everything-first action (add = upsert, remove = blind delete); `BlobReferenceTree` wraps a `Tree` with `createOrOpen`, `stage` / `stageAdd` / `stageRemove` (never sync) and the static reader `listed`, an ascending merge-join holding one cursor.
- **Scope registry** (`scope-registry.ts`): `BLOB_SCOPE_REGISTRY_ID = 'optimystic/blob-scope-registry'`, entry `[scope, scope]`, unguarded `blobScopeAction`, `BlobScopeRegistry` with staging, one-step `register` / `unregister`, and `enumerate` (which also reports whether the registry has ever been written).
- **Committed reads** (`committed-read.ts`): `readCommittedTree` opens a fresh read-only handle per call; certain unless the open or pass threw `BlockUnavailableError` / `BlockPossiblyStaleError` (logged `blob:read-uncertain`, partial result kept) or the handle got a below-floor answer, counted by the new `BlockFloors.belowFloorAnswers` and exposed as `Collection.belowFloorAnswerCount()`.
- Docs: docs/blobs.md §Registering references describes what exists, its status line and §Lifetime updated; docs/internals.md gained "Blob reference trees and the scope registry carry no guards" and a sentence on the below-floor count; docs/debugging.md's `blob` row lists `blob:read-uncertain`.

Downstream: `feat-blob-reference-trees-follow-sql-rows`, `feat-a-referenced-blob-is-copied-to-its-cohort`, `feat-unreferenced-blobs-are-reclaimed`.

## Review findings

**Read first:** the implement diff (all four new modules, the `BlockFloors` / `Collection` additions, the spec, the three docs), then the handoff.

**Correctness — checked, no defect found.**
- Key framing: for references `R1 < R2`, `R1 + '\0' < R2 + '\0'` holds both when they differ inside both and when `R1` is a prefix of `R2` (the separator meets a reference character), so runs are contiguous and in reference order, and the default `.sort()` (UTF-16 code units) puts the bounds in tree order.
- `collectListed` merge-join: after a fresh `find(lower)` (plus `moveNext` when not on — exactly `BTree.findFirst`'s ascending shape), the cursor is the first key ≥ `lower_i`; for a later reference with `lower_j > lower_i`, a cursor key ≥ `lower_j` is therefore also the first key ≥ `lower_j`, so reusing it without a descent is sound. Off-end returns early, leaving the remaining references unlisted, which is correct.
- `Tree.find` / `first` / `moveNext` / `at` read through the B-tree only and never refresh, so the fresh handle's view cannot change during the pass and the held `Path` cannot be invalidated by anything but a refresh or replay, neither of which runs on it. Because `readCommittedTree` opens the handle itself and no public API takes one, the "shared handle would throw Path is invalid" concern in the handoff is structurally closed; no tripwire needed.
- `Tree.open` costs exactly the two requests docs/blobs.md states: `Tree.attach` is synchronous and reads nothing.
- The below-floor count is incremented only in `answeredBelowFloor`'s reporting branch, which `TransactorSource` calls once per fetched answer; `readCommittedTree` only compares it with zero, so double-counting could not change an answer either way. Reading it only after a completed pass is right — a throwing pass is already uncertain.
- `countsWrite` (cited in internals.md) excludes unguarded elements, so the "not counted in the already-applied tally" claim holds; `BlockPossiblyStaleError.claimedRev` exists for the log line.
- Block ids are base64url, so the `optimystic/` registry id cannot collide with one, as the doc comment says.

**Tests.** The implementer's five tests each pin a named piece of docs/blobs.md (framing even under a prefix, stage/commit/readback including add+remove and remove-of-absent, racing first registrations, and the two uncertainty causes, each verified by log to fire for the intended reason).
