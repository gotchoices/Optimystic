# Reactivity: root the announcement tree at the tail block's storage group — complete

Third of three tickets for the maintainer's decision of 2026-10-02 (the accepted text is the first two paragraphs of `docs/reactivity.md` § Origination point). The first two tickets added root placement to the cohort-topic substrate and taught the db-p2p host to serve a root whose group is a block's storage group; this one switched reactivity onto it and bound the host's root group to the key network's storage rule. Implementation landed as `ticket(implement): reactivity-notifications-need-the-tail-cohort-to-be-the-topic-cohort`.

## What landed

- **Key network.** `assembleServingCohort(key)` is `hashKey(key)` followed by `assembleServingCohortAt(coord)`; `findCluster`, `findCoordinator` and the new public `servingCohortAt(coord)` share that one assembly, so storage placement and root placement cannot drift.
- **Node base.** One `rootGroupAt` binding over `servingCohortAt` feeds the host's `rootGroup` option (with the consensus `superMajorityThreshold` as `quorumRatio`), the push-state gossip authenticity gate and the recover transport's target read. `cohortTopic.host` can no longer carry `rootGroup`. Every reactivity verifier on the node uses the consensus ratio.
- **Origination gate.** `selfAppliedTail` in the change bridge: a change event originates iff it names a tail and that tail is among the blocks this node applied. The FRET membership gate module is deleted; no reference to it survives in source or docs.
- **Verifier.** Derives the root coordinate from the notification's tail (`reactivityRootCoord`, new in db-core's `topic-anchor.ts`) and verifies under a `RootPlacement` built from the required `quorumRatio` dependency.
- **Subscriber walk.** Registers with `rootKey` = the tail bytes, so the walk's root step dials the storage group. Rotation rebuilds the manager, and so its recover transports, under the new tail.
- **Harnesses, specs, docs.** As listed in the implement handoff; the mock-tier harness models a tail's storage group as the `wantK` members nearest its root coordinate.

## Review findings

**Read first:** the implement-stage diff in full (36 files), before the handoff summary.

**Checked by reading and running.**

- *Gate premise.* A change event's `blockIds` is exactly the set of blocks that landed in that `StorageRepo.commit` call, tail first (`tailFirst`), with `tailId` from the request; `alreadyDone` re-landings never emit. The sweep commit (`commitTailThenSweep` in db-core's `network-transactor.ts`) carries `tailId` but lists only non-tail blocks, so a data-block group member never originates, and a node in both groups originates once. The one-round commit runs on the tail's cohort and every member applies the tail, so each tail-group member's event includes it. A read-driven promotion and a replica push carry no `tailId`. Premise holds on every commit shape.
- *Threshold agreement.* `captureCommitCert` uses `ceil(|record.peers| × superMajorityThreshold)`; `rootPlacedMinSigs` uses `max(1, ceil(members × quorumRatio))`, identical for any non-empty group. `createRootPlacement` rejects a ratio outside `(0, 1]` at construction, so a misconfigured node fails at startup rather than verifying nothing.
- *Encoding contract.* `reactivityRootCoord(reactivityTailBytes(tail))` equals FRET's `hashKey(routingKeyForBlock(tail))`, pinned by the encoding spec and by integration case 4 on every node.
- *Rotation.* `ReactivityCollectionWatch.moveTo` builds a fresh manager with the new tail bytes, so the register's `rootKey`, the verifier's derivation and both recover transports move together. The renewal path carries the `rootKey` through the hint `hintFromReply` builds.
- *Gossip gate.* The async gate drops a frame on a throw or rejection and lets an unserved topic's frame through to the resolve step, which drops it; same outcome as before for a non-member, one fewer key-network read for an unserved topic.
- *Error paths.* The recover transport's `resolveCohort` rejection fails the recover like an empty group; the origination hook's isolation is unchanged.
- *Docs.* Every file the change touches was read. `docs/internals.md` § Cohort-Topic Origination Bridge and the wiring bullet reflect the new gate and root binding; `docs/cohort-topic.md` § Application policies and the milestone sentence in `docs/architecture.md` are accurate.
- *Validation.* `yarn lint`, `yarn lint:docs`, `yarn build`, `yarn typecheck`, db-core (1851 passing), db-p2p (3176 passing after the cut below), and the env-gated db-p2p integration suite (46 passing, the wide-mesh case in 35 s) all green on the reviewed tree. No pre-existing failure observed.

**Minor, fixed inline.**

- `docs/reactivity.md` worked scenarios still placed the root at `coord_0(_, H(T ‖ "reactivity"))` in two sentences (first subscriber's walk, and the post-rotation arrival rate); rewritten to the tail's storage group at `H(T)`. The remaining "tail cohort" wording elsewhere in the doc is consistent with the definition § Origination point now gives (the tail block's storage group), so no further sweep was needed.
- A comment on `detectTailRotation` in `packages/db-p2p/src/reactivity/origination-manager.ts` still named the deleted membership gate; now names `reactivityRootCoord`.
- Cut the encoding spec's "a pre-hashed tail resolves a DIFFERENT root" case: it asserted only that SHA-256 is not idempotent. The preceding case already fails if `reactivityTailBytes` ever pre-hashes, which is the regression it claimed to pin.

**Major.** None. The one architectural question in scope (which machines announce, and against what membership a notification is checked) is settled by the accepted decision and implemented at one site per party, all deriving from `reactivityRootCoord`.

**Tripwires recorded.**

- The wide-mesh integration case reproduces the threshold arm of the defect, not the disjoint-group arm: with `wantK` 16 on six machines the FRET cohort around any coordinate is still the whole mesh. `NOTE:` at the describe header in `packages/db-p2p/test/substrate-real-libp2p.integration.spec.ts` names the `wantK`-below-machine-count variant to add if the walk's root step ever regresses.
- The gossip gate's per-frame key-network read already carries a `NOTE:` at the gate in `libp2p-node-base.ts` (memoize per tail if it shows in profiles); left as is.

**Considered and declined.**

- Groups of three or fewer announce from the coordinator only, and a group of one never announces: both carry an accepted-tradeoff `NOTE:` at `captureCommitCert` and are stated in § Origination point. Unchanged by this ticket.
- Mixed-version breakage (an old-build subscriber registers at the old coordinate) is the reversibility cost the decision accepted; documented, not re-filed.
- The `cohort:membership` log line labels its `key=` field with a key digest on the `findCluster` path and a coordinate on the `servingCohortAt` path. Cosmetic; no doc greps the line.

**Not filed.** Nothing met the filing bar. Distant subscribers trusting the root's published membership on first use is already tracked by `feat-reactivity-root-membership-anchored-by-the-commit-log` (plan).
