# A pend refused late still stops its commit

## Background

The implement commit (`ticket(implement): a-two-member-pend-defers-its-final-delivery-to-the-commit`) first built the planned deferral of a two-member pend's final delivery. The Quereus plugin's `test/two-node-unique-value-race.spec.ts` then failed with `CoordinatorPartialCommitError`: on a two-member cohort, the other machine's refusal of one tree's pend surfaced only in the commit phase, after sibling trees had committed. That breaks the legacy multi-tree commit's "pend everything before committing anything" guarantee. The deferral was reverted, and the question went to the blocked ticket `decide-which-writes-may-defer-a-two-member-pends-delivery`.

Building it turned up three gaps in the code the prereq `a-cluster-request-carries-owed-consensus-deliveries` landed. Each let a commit go ahead while a member had refused its pend. This ticket fixes those three:

- **The refused-pend guard sees rivals on new blocks.** `ClusterMember.validateCommitAgainstRefusedPend` refuses to co-sign the commit of an action whose pend this member refused. Its corroboration check (`refusedPendConflictsWithLocalState`) now reads storage metadata (`heldLatestOf`, `rivalClaimsOn`) instead of `get`. `get` lists no pending records on a block with no committed revision, such as a new collection's header.
- **A commit carries its own action's owed pend, first.** `takeOwedRecords` escorts the settling action's owed pend records ahead of everything else, even while another request is already carrying them. The member has then applied the pend, or refused it, before it votes on the commit.
- **A late refusal answers the commit instead of a throw.** A pend refusal reported on a carried or retried delivery is held (now `LatePendRefusals` in `packages/db-p2p/src/repo/late-pend-refusals.ts`). When a commit through the cluster throws, `CoordinatorRepo.commit` answers with that refusal as the retryable conflict. Two cases still throw: a commit that returned an answer, and one whose revision this node already holds under the same action.

## Review findings

**Read first:** the full implement diff, before the handoff. I also read the source each change calls into: `heldLatestOf`, `rivalClaimsOn`, `onceGet`, `returnCarried`, `settleCarriedDelivery`, `runRetry`, `collectApplyOutcomes`, `confirmCommitRivalAgainstLocal`, `ClusterMember.applyConsensusOperation`'s pend-refusal retention, and db-core's `TransactionCoordinator.commitPhase`.

**Major, fixed in this pass: a late refusal was keyed by action id alone, on both sides.** Every collection of a multi-collection transaction pends and commits under one action id (`tx:…`), and `TransactionCoordinator.commitPhase` commits the collections concurrently. This is the reviewer question the handoff raised, and the answer was "yes, it can":
- *Coordinator side.* Collection M's commit settling first, acknowledged, called `takeLatePendRefusals(actionId)` and consumed collection U's refusal. U's commit then threw `ValidatorRejectionError` instead of answering a conflict. `LatePendRefusals` now records the blocks each refused pend named. `take(actionId, blockIds, now)` returns only refusals of the commit's own blocks and keeps the rest. The new-pend reset (`forgetFor`) drops only refusals of the new pend's blocks, so one collection's pend can no longer erase another collection's refusal. The `ICoordinatorClusterSeam.takeLatePendRefusals` signature gained `blockIds`; the five spec stubs (`() => ({})`) needed no change.
- *Member side, and worse.* `ClusterMember.refusedPendActions` was `Map<ActionId, refusedAt>`, and an accepted pend of the same action deletes the entry. So when the member accepted M's pend after refusing U's, it forgot the refusal. It then co-signed U's commit, and U's block committed on every member over the rival pending record that had caused the refusal. That is the fork shape the guard exists to prevent. The map is now keyed by action id and then by block (`retainPendRefusal`, `retirePendRefusal`). Pruning and the rollback path were updated to match, and the guard vetoes only a commit naming a refused block. The bookkeeping predates this ticket, but this ticket's late-delivery path is how it is reached.
- Repro test: `carried-consensus-delivery.spec.ts`, "a late pend refusal is kept for the commit of the blocks it refused, not taken by a sibling collection's commit". It fails with either fix removed; I checked each separately. Without the member fix, the refused block's commit came back `success`, `quorum: 'full'`.
- Docs: `packages/db-p2p/docs/cluster.md` now says refusals are scoped per block, in both the commit-promise check list and the *A late pend refusal answers the commit* bullet. `docs/correctness.md` §2 and `docs/debugging.md` were re-read and are still accurate.

**Minor, fixed: file size.** `cluster-coordinator.ts` already carried a `NOTE:` to move owed-delivery bookkeeping into its own module if it grew, and this ticket grew it. The late-refusal store moved to `late-pend-refusals.ts`, with `ClusterCoordinator` keeping thin wrappers. The file went from 1869 to 1786 lines (`wc -l`). `coordinator-repo.ts` (3653) and `cluster-repo.ts` (3614) are large files I did not split.

**Tripwire, parked as a `NOTE:` on `LatePendRefusals.forgetFor`:** an earlier attempt's pend record can still be retrying after the writer's retry starts a new pend. A refusal that the old record's timer delivers then is read by the new attempt's commit. The cost is a thrown commit answered as a retryable conflict.

**Checked, no change:**
- *Escort scope.* `takeOwedRecords` escorts by action id, not by block, so concurrent sibling commits each escort the other collections' owed pends too. Members dedup the extra copies, and an earlier apply only helps the guard, so I left it as is.
- *Error masking.* `confirmCommitRivalAgainstLocal` never throws (read faults are logged and return `undefined`), so `latePendRefusalFor` cannot replace the original commit error with a read error.
- *Retention sources.* `collectApplyOutcomes` keeps only each member's own report, so one member cannot plant a refusal under another member's id. A member that re-reports a refusal on re-delivery, after the writer already got a conflict, adds a held entry that the next pend of those blocks clears. That is harmless.
- *The guard now reads `heldRevisions`.* It is stricter in the right direction, as the handoff said. This is the same reading the pend vote uses.
- *The four-record carry limit.* The escort still respects `MaxCarriedRecords`. Without the deferral, owed pends come only from failed deliveries, so I accepted this as the implementer left it.

**Tests.** The three implementer tests each pin a distinct behaviour at the lowest layer that shows it, so none were cut. I added the one repro above. The cancel arm of the escort stays untested by design; it is the same code path as the tested commit arm.
