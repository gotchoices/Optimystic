# Catalog-only ADD COLUMN and DROP COLUMN

The `alterTable` hook of `OptimysticModule` now accepts `addColumn` and `dropColumn` through the shared catalog-only helper `alterCatalogOnly` (added by `catalog-only-drop-check-constraint`). Source and specs landed in the commit `tess: timed out on catalog-only-add-and-drop-column — added resume note`; the release note and handoff in `ticket(implement): catalog-only-add-and-drop-column`.

- **ADD COLUMN** is accepted for a column that, resolved with `columnDefToSchema` under the session's `default_column_nullability` / `default_collation`, is nullable, has no DEFAULT, is not generated, is not in the key, declares only `null` / `notNull` / `collate` constraints, and is appended. Anything else keeps the old `UNSUPPORTED` refusal. The record gets the column appended (`withColumn`); rows are keyed by column name, so older rows read it as NULL.
- **DROP COLUMN** is refused (`UNSUPPORTED`, message naming what uses the column) when the column is in the key, an index, a UNIQUE constraint, this table's foreign key, is generated, or feeds another generated column — checked against the engine's schema, the table instance's own schema and maintained index trees, and the fresh record. Otherwise every positional field of the record is renumbered (`withoutColumn`), and the engine side uses Quereus's `shiftSchemaIndicesForDrop` plus generated-column renumbering. Rows keep the dropped field, unread.
- **Between machines** (`classifyColumnChange`): an add the record already holds (tags and name case ignored) is adopted; an add over a differently defined column of that name is refused with `ERROR`; a drop over a record without the column is adopted; a drop the record keys on is refused.
- **Table instance**: `applyCatalogOnlyEdit` rebuilds the row codec and, after a drop, renumbers the maintained index descriptors in place (`IndexManager.repositionColumns`); no tree is opened or closed. Every scan takes its codec and index manager once at the start of `runQuery`.
- Re-adding a dropped name reads the old stored values: decided in the plan, recorded as an accepted-tradeoff `NOTE:` on `OptimysticModule.dropColumn` and in the README.

## Review findings

Read the implement diff first, then checked it against Quereus's ALTER TABLE runtime (`runAddColumn`, `revertAddColumn`, `runDropColumn` in `@quereus/quereus/src/runtime/emit/alter-table.ts`), `shiftSchemaIndicesForDrop` (`@quereus/quereus/src/schema/table.ts`) and the migration-plan ordering in `@quereus/quereus/src/schema/schema-differ.ts`.

**Correctness — checked, nothing found.**
- ADD: the refusal of inline CHECK / UNIQUE / REFERENCES is what keeps Quereus's per-constraint `addConstraint` loop and its `revertAddColumn` (which would call this module's DROP COLUMN) from ever running; confirmed by reading `runAddColumn`. `insertAtIndex` is set only by Quereus's materialized-view reshape, which this module does not support, so the append-only rule refuses nothing ordinary SQL produces. A `backfillEvaluator` can only come from a DEFAULT or generated expression, both refused first, so the `INTERNAL` throw is a genuine invariant guard.
- DROP: Quereus refuses primary-key, generated-dependency, partial-index-predicate, CHECK, DEFAULT, other-table FK and assertion dependents before calling the hook; the module adds the key-shaped blockers Quereus would otherwise narrow or drop (`shiftSchemaIndicesForDrop` filters indexes and UNIQUEs that cover the column — the module refuses those instead, since narrowing would need trees rewritten). Since every blocker is refused before any write, `positionAfterRemoving`'s throw for the removed slot cannot fire after the record was changed.
- Positions vs names: the record edit is by name and the engine and instance edits by position, so a record holding columns this engine has not seen (another machine's add) stays internally consistent. `IndexManager` reads only `schema.indexes` from its stored schema, so leaving its `columns` stale after `repositionColumns` is harmless. The tag-overlay listener (`withTagsOf`) matches columns by name, so it is unaffected by differing column order.
- Undo inside `apply schema`: an adopted ADD records `before = undefined`; Quereus's undo DROP carries `after = undefined`, so `AdoptedChanges.undoes` matches and the record is left alone — consistent with the two-machine spec.

**Error handling / resource cleanup — checked, nothing found.** `applyCatalogOnlyEdit` runs only after the batch checkpoint returned, and `republishColumnLayout` builds everything before assigning, in one synchronous step. No tree is opened, so nothing new needs closing.

**Concurrency — checked, nothing found.** Scans capture codec and index manager at `runQuery` start; writes and the ALTER both run under Quereus's exec lock, so DML reading `this.rowCodec` live cannot interleave with the swap.

**Type safety / DRY / modularity — checked, nothing found.** `columnSchemaToStored` was lifted out of `SchemaManager` so the record edit and the full-schema conversion share one function. `columnDropBlockers` judges the engine schema, instance schema and record through one structural type (`ColumnKeyedParts`). The instance keeps its own `uniqueEnforcementIndexes` beside the index manager's copy and renumbers both; that duplication predates this ticket (both are set together in `doInitialize`) and is kept consistent here.

**Source hygiene — nothing changed.** Comments state constraints and reasons rather than narrating. `optimystic-module.ts` was already large before this ticket; the new code is split into small methods and free functions, and the pure rules live in `catalog-only-change.ts` and `schema-manager.ts`.

**Tests — kept as written; none added or cut.** The `classifyColumnChange` table pins the specified verdict table (real branching), the `withoutColumn` spec pins the renumbering no write-time check can catch (an in-range off-by-one), and the integration specs cover the refusal table, the cross-restart read of rows written under either column list, index/UNIQUE/generated renumbering with `verifyIndexes`, and the four `apply schema` multi-machine shapes. None restates the implementation or verifies a mock. The untested paths the handoff listed (drop refused for an index only another machine has, an overlapping committed read, ADD NOT NULL on an empty table) were confirmed by reading and do not merit a test each.

**Docs — checked, accurate.** README ALTER paragraph and Limitations, and the `.release-notes.pending.md` entry, match the code. No file under `docs/` or another package describes ALTER on Optimystic tables. The accepted-tradeoff NOTE's "the row codec does not convert them" is accurate (`RowCodec.denormalizeValue` only re-decodes BLOB base64 and tagged bigints).

**Major — one, outside this repository, filed.** Quereus's `generateMigrationPlan` creates new indexes before its per-table alter block, so a schema version adding a column and an index on it fails on every module. Confirmed by reading `schema-differ.ts`. Filed as `tickets/blocked/quereus-apply-schema-creates-indexes-before-added-columns.md` (external dependency; proposes moving index creates beside the assertion creates). The README Limitations entry documents the workaround meanwhile.

**Tripwires — none new.** The existing `NOTE:` on `columnDropBlockers` (record expressions not judged; matters only if hosts apply differing schema versions at once) and on `IndexManager.repositionColumns` already park the conditional concerns at their sites.

**Out of scope, still open:** `bug-optimystic-rename-column-lost-on-restart`, `bug-optimystic-stale-hydrated-table-rewrites-the-shared-catalog-record`.
