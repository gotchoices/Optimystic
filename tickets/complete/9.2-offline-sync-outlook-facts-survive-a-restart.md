## What was built

- **The journal format.** `JournaledFacts`, `encodeFacts` and `decodeFacts` in `write-description.ts` are a JSON-safe form of `EntryFacts`. `fresh` is stored as `[collectionId, keys[]]` pairs. Each `unchecked` read keeps `table`, `kind` and `scope` and drops its pinned `rows`, because a bound value can be a bigint or bytes and JSON cannot carry those. A tripwire `NOTE:` at `encodeFacts` names the remedy (journal the encoded main-tree keys) if the widening this causes ever matters.
- **The entry record.** `EntryRecordV1.outlook?: JournaledFacts`; the record version stays 1. The journal gets the facts through `OfflineJournalHooks.factsOf` while it builds the record. `OfflineMode.enqueue` sets them before calling `queue.enqueue`.
- **The restore.** `OfflineRestore.restoreOne` decodes the facts and hands them over through `RestoreHost.factsRestored` before calling `queue.restore`. The `queued` status that restore emits judges the transaction with them. If `queue.restore` throws, `RestoreHost.restoreRolledBack` drops the facts unless the queue lists the transaction (`OfflineMode.forgetUnqueuedFacts`). An entry that was already committed when it was restored is settled by `queue.restore`, and `onQueueStatus` drops its facts.
- **The judgement.** In `commit-outlook.ts`, `encodedKeys` now answers `undefined` for a `row` read with no rows, so a restored row-scoped read is matched by its table. Before this, the empty key list matched no earlier writer, which is narrower than the original read. A live `row` read always has at least one row, so nothing outside restore changes.
- **Old records.** A record with no `outlook`, written by an earlier build, restores as before: judged from its checks and tags, with `unchecked: 'not-computed'`.

## Test

`test/offline-restore.spec.ts`, "the outlooks queued transactions had survive a crash after the local acknowledgement…", runs on a one-node mesh with the reachability gate closed. It checks three things:
- the facts are written into the entry record on disk;
- after a crash and `hydrate`, every outlook equals the one before the crash, except one: the key-pinned copy now depends on both earlier conversations instead of one (it is matched by its table);
- a record with `outlook` stripped restores the message as `exposed` with `unchecked: 'not-computed'`.

The implementer mutation-checked the empty-rows guard: with it disabled, the test fails.

## Review findings

**How I reviewed.** I read the implement diff (`git show` of the commit above) before the handoff, then checked the controller, journal, restore, queue and judgement code it touches.

**Correctness: happy path and lifecycle — no defects.**
- Enqueue: `OfflineMode.enqueue` sets `entryFacts` before `queue.enqueue`, and `OfflineJournal.queued` builds the record inside that call, so `factsOf` sees the facts. Its existing `finally` drops them when nothing is queued, which covers a journal that refuses the record.
- Restore order: `walk` goes through records in queue order, so an earlier entry's facts are set before a later entry is judged. This matters because a later entry reads `EarlierEntry.facts` to tell whether an earlier insert's key is fresh.
- Double restore: `walk` skips a record the queue already lists (`queue.status(id) !== undefined`). So a second restore pass cannot overwrite live facts, which still have their rows, with row-less decoded ones.
- Deferral during collection resolution happens before `factsRestored`. A deferral during staging, or any other throw, runs `restoreRolledBack`.
- Already-committed entries: `OfflineQueue.admitRestored` calls `committed(entry)`, which emits a terminal status, and `onQueueStatus` drops the facts.
- Deferred journaled transactions are counted by table only (`deferredBelow`), so whether they carry facts makes no difference. No gap there.

**Edge cases — no defects.**
- The widening cannot change `kind`. `outlookFrom` counts a `via: 'unchecked'` dependency as assured whatever its kind, so a restored transaction can gain an entry in `dependsOn` but cannot turn exposed. The README and docs say exactly this.
- `encodeFacts` copies only `schema` and `table` from Quereus's `QualifiedName`, which has only those two fields (`@quereus/quereus/src/planner/analysis/change-scope.ts`). Nothing is lost.
- `complete: false` facts round-trip and still judge as `'not-computed'`.

**Error handling — accepted as is.** `decodeFacts` trusts the record's shape, as `versioned` in offline-journal.ts already does for records this build wrote. A malformed `outlook` would throw from `restoreOne` and fail that restore pass, the same as any other corrupt record. I left this alone.

**Type safety, DRY, modularity — no findings.** `JournaledFacts` is derived from `UncheckedRead` (`Omit<…, 'rows'>`), so a new field on the read type shows up in the journal type too. The two new `RestoreHost` hooks are narrow, and the restore stays independent of the controller.

**Resource cleanup — no findings.** Facts are held while the queue lists the transaction, and every exit path that leaves it unlisted drops them (see the lifecycle notes above).

**Performance — no findings.** One map lookup and one small JSON object per enqueue.
