# Docs match the shipped `sole-holder` diagnosis

Doc-only sweep (plus two spec cases), split from `1-name-the-single-holder-deadlock`, whose code half
shipped separately and is untouched here. No behavior changed.

## What shipped

`CoordinatorRepo.reportRepairDeadlock` emits `cluster-fetch:repair-deadlock` with a `reason` of:

- `cohort-too-small` — the cohort has fewer peers than the quorum needs even if all of them answer.
  Remedy: more machines, or an honest declared cohort size.
- `sole-holder` — the cohort is big enough, but exactly one of its peers holds the block and every
  other peer answered that it holds nothing. Remedy: another cohort peer holding the block (commit a
  new revision). No machine count or config setting helps.

Five documents previously described only the `cohort-too-small` shape and implied a machine-count
model ("four or more is the first size with any margin") that only holds for a block several cohort
peers already hold. They now state the holder assumption up front, document both `reason` values, and
name the one configuration where a singly-held block *does* repair.

Files: `docs/internals.md` (size table preamble + `4+` row caveat + both `reason` values),
`docs/transactions.md` (the paragraph naming both log lines), `packages/db-p2p/docs/cluster.md`
(new "every number above counts PEERS, not COPIES" paragraph),
`packages/reference-peer/README.md` (`--assumed-cluster-size` help text),
`tickets/complete/1-repair-deadlock-is-never-named.md` (its summary table, deliberately — it
documents shipped operator-facing text), and `packages/db-p2p/test/quorum-restore.spec.ts`
(two cases pinning the claim and its boundary).

## Review findings

**Checked:** the implement diff against the shipped code it describes
(`reportRepairDeadlock`'s `cohortTooSmall` / `soleHolder` conditions and its reason precedence,
`quorumSize` / `corroboratorCapacity` / `selectQuorumRev` in `cluster/quorum-restore.ts`, and
`reconcile-block.ts` using the same floor); every `sole-holder` / `cohort-too-small` /
`assumedClusterSize` mention across all `.md` outside `tickets/` for sites the sweep should have
touched and missed (none — the one other hit, `docs/internals.md`'s "it could be the sole holder",
is unrelated prose about silence); the new spec case actually driving the primitive it claims to;
the `cluster.md` relative link; and lint + build + tests.

**Found and fixed in this pass (accuracy — the whole point of this ticket):**

- *The "no machine count fixes a singly-held block" claim was stated unconditionally, and is false
  for one configuration.* When a cohort declares itself two-member (`assumedClusterSize: 2` or an
  honest `clusterSize: 2`), `corroboratorCapacity` is 1, so `quorumSize` relaxes the corroboration
  floor to one and a lone holder's claim **is** adopted — a singly-held block repairs there like any
  other. `packages/db-p2p/docs/cluster.md` contradicted itself most sharply, asserting "cannot be
  repaired at any `assumedClusterSize` whatsoever" two paragraphs below the text describing exactly
  that relaxation. Every claim site is now scoped to "wherever the floor is two", with the exception
  named: `docs/internals.md` (×3), `docs/transactions.md`, `packages/db-p2p/docs/cluster.md`,
  `packages/reference-peer/README.md`, `tickets/complete/1-repair-deadlock-is-never-named.md`.
  (The shipped code is correct as-is and needed no change: `reportRepairDeadlock` runs only on a
  decline, and the declared-two case does not decline, so `sole-holder` cannot be reported there.)
- *The size table's blanket "every row assumes ≥2 holders" was wrong for its own second row*, which
  needs exactly one holder besides the reader. Both tables now assume "as many holders as that row's
  *must answer* column demands", which is right for every row.
- *The new spec case hardcoded `THRESHOLD` (0.51)* while every sibling case in that `describe` reads
  the threshold through `resolveClusterPolicy` on purpose — a resolved-default drift would have
  slipped past it. Now reads `policy.simpleMajorityThreshold`.
- *Test coverage gap: the boundary of the claim was unpinned.* Added
  `'except on a DECLARED two-machine cohort, whose floor of one adopts the lone holder'`, asserting
  `selectQuorumRev` returns the lone claim there. Without it the corrected docs could drift back to
  the overclaim with a green suite.
- Cosmetic: one short line re-wrapped in `docs/internals.md`; stale `(given ≥2 holders)` table header
  in the completed ticket.

**No major findings, so no new tickets filed.** The shipped code was verified correct against every
doc claim, and the only defects were in the prose this ticket exists to correct — all fixed inline.

**No tripwires recorded.** The conditional concerns around this area (commit-to-push latency making
`sole-holder` fire on blocks that heal moments later; per-block rather than per-node emission) were
already written as `NOTE:`s at `reportRepairDeadlock` by the code-half ticket and still read
correctly; nothing new became conditional here.

**No accepted-tradeoff `NOTE:`s were re-litigated.** The existing one on `resolveClusterPolicy`
(advisory not firing for every correctly-configured deployment) is untouched and its revisit
condition has not tripped.
