# Back-fill a verified commit proof onto an already-held revision — complete

## What shipped

When a peer pushes a block revision this node **already holds**, `BlockStorage.saveForwardRevision`'s
monotonic guard makes the save a no-op and writes nothing — including the cohort commit proof the
push carried. A node that first landed that revision without a proof (a legacy uncertified push, a
corroboration-only heal) therefore stayed a *corroboration-only* holder for it forever: it held the
right bytes but could not re-prove them to anyone.

`StorageRepo.saveReplicatedBlock` now back-fills the proof on its non-advancing branch, when all
four hold: the save did not advance `latest`, a verified proof was supplied, a `source` revision was
declared, and the held revision matches the pushed one on **both** `rev` and `actionId`. It runs
under the per-block commit latch the method already holds and routes through
`persistProofIfContentMatches` — the existing rule that persists a proof only when this node's own
materialization matches the digest the commit operation declared.

The back-fill lives in `StorageRepo`, deliberately **not** inside the monotonic guard: the proof was
verified against the *pushed* bytes, and a diverged holder's bytes at the same `(rev, actionId)` may
differ. Storing a proof whose declared digest contradicts local content would make this node serve
content that fails its own proof, and `digest-mismatch` is an *attributable* fault in
`certified-claims.ts` — every receiver would penalize it. The digest check is what makes the
back-fill safe, so it must sit where local content can be read.

Supporting arms: `cohort-growth-heals-single-holder.spec.ts` was upgraded to a certified commit and
now runs the production receiving posture (`requirePushCertificate` at its default `true`), making it
the one test driving the whole producer → wire → receiver certification chain over real repos;
`block-transfer-roundtrip.spec.ts` keeps its migration flag as a reviewed decision now written at the
fixture; and `source-block-certification.spec.ts` gives the producer-side helper direct coverage.

## Review findings

### What was checked

- **The implement diff read first, before the handoff summary** (`git show fda7df91`): the
  `storage-repo.ts` back-fill branch, the `backFillProof` generalization from a `CommitRequest` to
  `(rev, actionId)`, and the rewritten `block-storage.ts` guard comment.
- **The gate's equivalence to the monotonic skip.** `advanced` is
  `priorLatest === undefined || effective.rev > priorLatest.rev`. Traced against
  `saveForwardRevision`: the guard returns the held `latest` iff `meta.latest.rev >= rev`, otherwise
  it writes and `latest` becomes `rev`. So `!advanced` fires on exactly the skip path and nothing
  else — including the pending-only case (`meta` present, `latest` undefined), which correctly reads
  as advancing.
- **Every branch of the four-part condition.** Confirmed `handlePush` can never supply a proof
  without `source` (it rejects `proof-without-meta` before persisting) and `reconcile-block.ts`
  always supplies one, so the `source !== undefined` arm is defensive-only — now pinned by a test
  rather than left as an argument.
- **Latching.** The back-fill runs under `commitLatchKey(blockId)`, the same latch the two
  commit-path back-fill sites hold. Confirmed every other writer of `latest` or of a proof — `commit`,
  and `invalidation.ts`'s compensating write — takes that same latch, so the read-modify-write on the
  proof key is serialized.
- **The awkward cases.** Tombstone held at the pushed rev, diverged bytes, same rev under a different
  action, and a stale pushed rev all resolve through `persistProofIfContentMatches`, which declares no
  digest or mismatches and never throws.
- **Whether declining to back-fill onto a *newer* held revision loses anything.** Traced every proof
  consumer: `servableProof` (from `block-archive.ts`, `libp2p-node-base.ts`, `mesh-harness.ts`) only
  ever reads `latest.rev`. Nothing reads a non-latest proof, so the decision costs nothing.
- **Docs treated as out of date until read.** `docs/internals.md` § *Persistence and retention*
  (updated by the implementer — correct), § *Certified push* (**stale — fixed**),
  `docs/arachnode-ring-handoff.md` § Phase B (unaffected: it concerns pre-proof blocks, which have no
  proof anywhere to back-fill), and the `IBlockStorage.saveReplica` interface contract
  (**stale — fixed**).
- **Lint, build, typecheck, and the full workspace test suite**, all from the repo root. All pass;
  no failures anywhere. db-p2p: 2214 passing, 44 pending (2211 before this review pass, plus the
  three tests added below).

### Minor findings — fixed in this pass

- **`docs/internals.md` § *Certified push* was stale.** Two statements a reader lands on for push
  behaviour still described the old reality: "The monotonic no-op path deletes nothing: it wrote no
  committed record, so it owes no deletion" now reads as *writes* nothing, which is no longer true;
  and the "A block accepted on a proof **stores** that proof" bullet described only the advancing
  case. The implementer updated § *Persistence and retention* but not this section. Both corrected,
  with a pointer between the two sections.
- **The `IBlockStorage.saveReplica` interface contract was stale.** `i-block-storage.ts` still said
  "The monotonic no-op persists nothing, proof included" with no pointer to the back-fill. Literally
  still true of `saveReplica` itself, but it is the contract the back-fill *depends on*, and a reader
  of the interface had no way to find the layer that does the work. Pointer added, naming the reason
  the digest check cannot live at that layer.
- **Three coverage gaps the handoff named itself, now closed** — new
  `describe('back-fill (real signed proofs)')` in `block-storage.spec.ts`, calling
  `saveReplicatedBlock` directly (which is the reconcile caller's shape, the path the handoff flagged
  as unasserted):
  - *back-fills onto a revision already held proof-lessly* — the positive path off the push wire.
  - *never back-fills a save that declares no source revision* — turns the handoff's argument into an
    assertion. Verified non-vacuous: the proof is minted for the fabricated `(rev 1, actionId)`, so a
    version of the guard that compared against `effective` alone would store it and fail the test.
  - *a proof-persist fault leaves the no-op successful* — injects a throwing `saveBlockProof` and
    asserts the revision stays durable and the save does not reject. The handoff noted this
    discipline was pinned on the commit path but not the replica path.
- **A vacuity guard on the "strictly additive" push test.** It depended on two `certify` calls
  producing different proofs without asserting it. Added `expect(second).to.not.deep.equal(first)`
  so the test fails loudly rather than silently passing if `makeSignedProof` ever became
  deterministic.

### Major findings — none

Nothing warranted a new ticket. The seam is one branch inside a latched section that reuses the
existing retention rule wholesale rather than duplicating it, the "not in the monotonic guard"
placement is the correct one and is now argued at three sites plus the docs, and the negative cases
(diverged holder, different action, stale rev, no source, persist fault) are each covered by a test.
Because nothing was filed, the *Before you file a ticket* site-claim grep did not apply.

### Tripwire recorded

- **Repeated re-materialization on a diverged holder.** Once a proof is retained, a duplicate
  certified push costs one key lookup (`backFillProof` returns before materializing). A holder whose
  bytes diverge from the cohort's never retains one, so it re-materializes and re-hashes the block on
  *every* certified push of that revision. Fine at spread-on-churn push rates. Parked as a `NOTE:` at
  the back-fill site in `storage-repo.ts`, with the remedy (remember the withheld `(rev, actionId)`
  and skip the re-check).

### Considered and declined

- **The `cohort-growth-heals-single-holder.spec.ts` blast-radius widening**, which the handoff asked
  for an opinion on: the spec now fails if certification breaks, not only if growth/heal breaks. Kept.
  It is the only test driving a real `StorageRepo` commit → real wire framing → real receiver at the
  production posture, and that reach is worth more than the narrower failure attribution. The
  tradeoff is already stated in that file's `writeRevision` doc comment and at the service
  construction site, so a future reader who sees it fail knows why certification is in scope there.
- **The `N²` proof-bytes concern** already carries an accepted-tradeoff `NOTE:` on
  `persistProofIfContentMatches` (measured at ~4.6 KB for a 10-peer 2-block commit). Its revisit
  condition — per-coordinator batches growing large — has not tripped, and this ticket does not
  change how many proofs are stored, only when. Left alone, not re-filed.
