# Queued blob pins settle with their transaction

A commit that reaches the offline queue instead of the network leaves its blob reference pins in place on purpose: nothing is on the network yet, so the writer holds the only copy of the bytes a committed row will point at. This part releases those pins when the queued transaction finally settles — announced into the table's reference tree for the collections that committed, released outright for the ones that did not, so the writer's piece sweep can take the bytes of a transaction that never landed.

Everything is reconciled from committed state and the pins' own owner labels. Nothing reads the offline journal's segments and no field was added to any journal record.

## What landed

Implemented in `ticket(implement): feat-queued-blob-pins-settle-with-their-transaction`; the review's own changes are described under *Review findings* below.

**`SqlBlobPins.settleQueued(transactionId, committed)`** (`blob-pins.ts`), with `settled()` and `dispose()` beside it. It runs on a new per-object work chain: each step first waits for any open transaction to end (`TransactionBridge.whenTransactionIdle`) and then returns at once if disposed. The chain never rejects. The four online arms (`holdForCommit`, `committed`, `queued`, `abandoned`) stay off the chain — they run inside `commitTransaction`/`rollbackTransaction` under Quereus's exec mutex and must not wait on a chain that waits for the transaction they belong to.

Where a transaction's owed pins come from:

- **From memory** when this process sealed the entry: `queued()` remembers the transaction's `HeldPins` in `queuedPins`, and `settleQueued` takes it. No pin listing at all.
- **From the labels** when it did not — a process that restored the entry from the journal after a restart: `listPins(transactionPinPrefix(id))` over every backend `CollectionFactory.knownBlobBackends()` resolves, each label read through `parsePinLabel`. A stray `put` pin met on that path is dropped there.

Per reference, once its scope is known to have committed: the scope is confirmed in the network's registry, then `announce`, then `unpin`. A scope not among the committed ones is unpinned without announcing. A scope that cannot be confirmed, or an announcement that throws, **keeps** the pin and logs `blob:pin-kept`; nothing here retries it — `feat-blob-pins-reconcile-after-a-restart` does, and the keep arm's comment says so.

**`BlobScopeRegistration.isRegistered(network, scope)`** — a read-only registry check answering `true` / `false` / `undefined`, used for a scope no table in this process backs any more. Registering there would re-register a tree whose table was deliberately dropped and keep its blobs for ever; a certain "not listed" is what makes those pins releasable.

**`CollectionFactory.knownBlobBackends()`** — every blob backend of a transactor key the factory has seen *options* for, not only the ones already resolved: a previous process's pin can sit in a store this one has not opened. A key whose resolution throws is logged and left out.

**`OfflineMode.attachBlobPins`**, and the call from `onQueueStatus` — the one place every terminal queue outcome passes through (the queue's own `onStatus`, and the restore's `emitSettled` for a discarded deferred record). `committed` → `'all'`; `failed` → `new Set(committedCollections ?? [])`; `partially-committed` settles nothing, since the entry is still at the head owing its remaining collections. Never awaited: the status arrives synchronously inside the drain.

**`plugin.ts`** — the pins are built after `new OfflineMode(...)`, attached to both the bridge and the controller, exposed as `plugin.blobPins`, and `blobPins.dispose()` is awaited in `plugin.dispose()` before `offline.dispose()`.

### Two departures from the implement ticket, both kept

- **A fast-path guard the ticket did not ask for.** `queued()` also records the transaction id in a `sealedHere` set, and `settleQueued` skips the label listing for a transaction this process sealed that is absent from `queuedPins` — such a transaction provably took no reference pin. Without it a host that uses no blobs would pay a listing on every queued transaction it settles, and that listing *resolves and starts a blob store per network*. Absence from the set means "cannot say", which falls through to the listing — the safe direction. Reviewed and confirmed sound: `held !== undefined` exactly when `addedReferences` was non-empty, which is exactly when a reference pin was taken, so "sealed here and absent from the map" can only mean "took no reference pin".
- **The status line in docs/blobs.md was amended rather than left for the third part.** Left untouched it would have said the queued settlement was "still to be built" in the same paragraph as the new bullet describing it as built. The minimal edit was made; the restart reconciliation and the `unstaged` expiry stay listed as unbuilt.

## Review findings

The implement diff was read first, then the handoff. Checked from each aspect angle; findings by disposition below. Lint, docs-citation, dependency, typecheck, React-Native-bundle, full unit and integration suites all run green after the fixes (commands at the end).

### Fixed in this pass (minor)

- **`BlobScopeRegistration.isRegistered` had no test at all**, and it is the highest-stakes new branch in the diff: its `false` answer is what *releases* a settling pin, so the bytes a dropped table's rows referenced ride on the three-reading mapping. Added to the existing `blob-reference-tree.spec.ts` case that already pins the registry — now asserting all three readings (a registry never written → `undefined`, a listed scope → `true`, a certain listing without the scope → `false`, and the same after `drop table`) with no new spec file and no new fixture. The file-header bullet was extended to say so.
- **The harness reimplemented an exported test double.** Its 20-line `SharedJournal` was byte-for-byte the behaviour of `PowerLossKVStore` (`@optimystic/db-p2p/testing`), which three other offline specs already use as a plain durable journal and which only loses writes when a test calls `powerLoss()`. Replaced; the reason a `MemoryKVStore` cannot be used (the registration config refuses it by name) survives as a comment at the one call site. This matters more than ordinary duplication because the harness is the module the next two parts build on.
- **`queued()` keyed `queuedPins` by `held.transactionId` while `sealedHere` keyed by `transaction.stampId`.** The same value today, but the fast-path guard and the map it guards must not be able to drift — a map keyed differently from its guard would make the guard skip the listing for a transaction the map cannot answer for. Both now use `transaction.stampId`, with a two-line comment saying why.
- **The plugin README still said a transaction's referenced blobs are announced before its commit returns**, with no mention of the queued route, and its two-commit pattern reads as unconditional. The README is the host-facing description of exactly this behaviour and it is the file the change should have touched. Added a bullet: a queued commit announces nothing and reports no durability until the queue finishes with it, then announces or releases as above, so the two-commit pattern waits for the drain when used offline.
- **`docs/blobs.md` §SQL did not say the settlement leaves an `unstaged` pin in place.** A reader of the new bullet would take the settlement for complete. One sentence added naming the holding period as that pin's remedy.
- **A never-reassigned `let handle`** in the first queued case, now `const`.

### Recorded as tripwires, not tickets

- **Each chained step's `Promise.race([whenTransactionIdle(), disposing])` leaves one promise reaction on `disposing`**, which settles only at dispose, so a process that settles very many queued transactions retains one per settle. The `MaterializedViewFollower` precedent the code cites has the same shape at a far lower rate, so this is project idiom rather than a mistake, and the magnitude is unmeasured. `NOTE:` at the race in `blob-pins.ts`, with the weaker claim and the fix if it ever shows up.
- **A terminal status delivered twice costs a listing on the second pass** (both records were taken on the first), which the handoff flagged but which lived only in the handoff. `NOTE:` at the fallback site in `releaseQueued`, naming `feat-blob-pins-reconcile-after-a-restart`'s `mayHoldStalePins` as where to cut it.

### Checked and found sound, no change

- **`status.entryId` is the transaction's `stampId`.** `commitTransaction` passes `transaction.stampId` to `sealIntoQueue` as the entry id, so the pins' labels and the queue's statuses name the same transaction. The restore's `emitSettled` for a discarded deferred record goes through the same `onQueueStatus`, so the discard path settles too.
- **Ordering of `queued()` against an early terminal status.** On the `behind-queue` route `settleBlobPins(…, 'queued')` is awaited *before* `awaitQueuedCommit`, and a chained settle cannot run until `endTransaction` (in that call's `finally`) makes the bridge idle — so the memory record is always in place before the settle reads it, and the commit never awaits the chain, so there is no deadlock.
- **`tablesOf(scope)` is asked about the reference *tree's* collection id, not the table's.** `OptimysticModule.registerCollections` registers the `/blobrefs` tree against the table at initialization, so a scope whose table is open here answers non-empty and takes the `ensure` path; a restored entry's table is opened by the restore's table resolver before its drain. The read-only path is reached only for a scope no table here backs, which is what it is for.
- **`queuedPins` / `sealedHere` growth.** Bounded by the live queue depth: every queued entry reaches a terminal status through `onQueueStatus`, which deletes both records, and a process disposed with entries queued discards the maps with the object. Journaled entries a restore does not put back belong to a different process, where neither map holds anything.
- **An `unstaged` pin is not released for a reference that landed via the queue**, where an online commit would drop it. This is what the implement ticket specified, and `feat-sql-columns-hold-blob-references` (on the board at 2.75) explicitly owns it — its §"Why `queued` and `abandoned` leave `unstaged` pins in place" is this exact case, and nothing expires any `unstaged` pin today, so this is not a regression this part introduced. Not re-filed; recorded in `docs/blobs.md` instead (above).
- **The near-duplicate announce-then-unpin flow** in `settleQueuedReference` and `announceAndRelease` is not foldable: the online arm *keeps* a pin whose scope did not commit, where the queued settlement *releases* it. Different policies at the only branch they share, so two routines is the honest shape.
- **Resource cleanup, error handling, type safety.** Every reference is isolated in its own `try`; `listQueuedReferences` isolates per backend so one bad store does not hide the rest; `knownBlobBackends` isolates per key; the chain never rejects and `dispose` releases a step parked on an open transaction rather than hanging a disposing host, and does not hang one that disposes with a transaction still open. `tablesOf`'s dependency is widened to `ReadonlyMap<string, unknown>`, which is all the pins need. `blob-pins.ts` is 477 lines, within the file-size norms of its neighbours.
- **No test was cut.** The three new cases each pin a distinct arm with a distinct outcome and assert against real blobs and the real reference tree rather than against the implementation; none restates the code or verifies a mock.

### Nothing found in these categories

- **No major findings and no tickets filed.** Nothing in the diff reached the filing bar: no finding named a class-level invariant or a current-release anchor that the inline fixes did not already settle, and no latent defect was found whose only anchor is a later release.
- **No blocked items.** The specification and architecture answered every question the diff raised; the two departures from the implement ticket are both documented and both correct.
- **No accepted-tradeoff `NOTE:` was overridden.** The sites touched carry none, so nothing a human had already declined was re-opened.

## What the next parts inherit

- `plugin.hydrate` does not await `blobPins.settled()`. Nothing here needs it to, and making it wait would deadlock a host that called hydrate inside a transaction; 2.74's `reconcileReady` is the hook if one is ever wanted.
