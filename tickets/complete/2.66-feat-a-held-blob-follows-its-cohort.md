# A held blob follows its cohort

[docs/blobs.md §Placement, copying and durability](../../docs/blobs.md#placement-copying-and-durability), *When the cohort changes*: "A node's held blobs are enumerable from its records, so the cohort comparison `RebalanceMonitor` makes for blocks is made for blobs too, by giving it the routing key rule rather than a second copy of its logic."

The prereq (`feat-the-blob-cohort-reaction`) built the decision with no wiring. This ticket runs a second `RebalanceMonitor` over the blob references a node keeps for the network and acts on what the reaction returns. With it, every part of that section of docs/blobs.md exists; reclaiming and the rest of SQL remain.

## What shipped

**The feed.** `LocalBlobService.onHoldsChanged(listener)` (declared on `BlobResponsibleRecords`) is a second listener set beside `durabilityListeners`, emitted from `changeRecord` — the one path every record change takes — through `emitHoldsChanged`, and only when the set of hold *kinds* in `result.before` differs from the set in `result.after` (a missing record counting as no holds, `sameHoldKinds`). So a `lastReadAt` touch, a `whole` correction, a second owner's pin, and a `responsible` hold whose scope was replaced do not fire; every hold that appears or goes does. A listener that throws is logged (`holds:listener-threw`, under `blob:store`) and does not stop the others. It emits before the caller's `flush`, deliberately: a listener only mutates an in-memory set that is re-derived at every start.

**The restart seed.** `seedHeldBlobs` in `packages/db-p2p/src/blob/held-blob-seed.ts`, modelled on `seedOwnedBlocksFromStorage`: every `responsibleRefs()` reference is tracked, then every `owed.list()` entry is tracked and its holders reported through `monitor.recordBlockHolders`, so the first check after a restart does not re-announce to members the writer already knows hold the blob.

**The monitor instance.** Built in `createLibp2pNodeBase` after the owed-copies drain, from `served.arachnode` — a new additive `ServingRole` field carrying the FRET service and its `ArachnodeFretAdapter`. Its tracked set is its own `Set`; it takes `routingKeyOf: id => routingKeyForBlob(id as BlobRef)` and `logName: 'blob:copy'`, shares `options.rebalance` with the block instance, and is exposed as `node.blobRebalanceMonitor`. What is tracked is a reference whose record carries an `owed` or a `responsible` hold; a pin and a `cached` hold are not. A wiring failure is logged (`node-wiring`) and non-fatal.

**The handler** hops the reaction off the monitor's synchronous emit loop, then releases each confirmed reference in turn, calls `retainLost` for each unconfirmed one and `recordGrowthOutcome` for each growth outcome. A rejection logs `reaction:failed` and records nothing, so the next check retries. `BlobCopyDrainDeps.onHolderConfirmed` is wired to `blobRebalanceMonitor?.recordBlockHolders(...)`, so a `whole` answer or an arriving `held` also counts for growth.

A client (`servesBlocks: false`) runs no serving role, so it gets no blob monitor: it is in no cohort, never takes a `responsible` hold, and its owed blobs are followed by the drain.

## Review findings

The implement-stage diff (`ticket(implement): feat-a-held-blob-follows-its-cohort`) was read before its handoff summary. One major finding, three minor fixes, two tripwires, two findings weighed and left alone.

### Major — fixed in this pass

- **The package's full test suite was red at the implement commit.** `test/dial-options-single-site.spec.ts` is a structural guard: `src/network/register-protocol-handler.ts` is the only file allowed to call `.handle(...)`, because libp2p checks `runOnLimitedConnection` on the answering side against the options passed at registration, so a bypassing `.handle(...)` leaves that protocol unreachable from every relay-only peer. The guard matches the method by name over the parsed source, and the new `reaction.handle(event)` call site in the node factory tripped it. The guard's own doc prescribes the fix — rename the unrelated method, never weaken the match, since the guard's failure mode is silence — so `BlobCohortReaction.handle` is now `handleRebalanceEvent`, after the block counterpart it mirrors (`BlockTransferCoordinator.handleRebalanceEvent`). The four call sites in `test/blob-cohort-reaction.spec.ts`, the class's own docblock and the citation in docs/blobs.md were updated with it, and the guard's doc now records that this happened once so the next author meets the precedent rather than re-deriving it.

  The implementer's "Commands run" lists six selected spec files, not `yarn test` — correctly, since `tickets/rules/testing.md` makes the full suite the review's run. The guard is not reachable from any of those six files, so nothing in the implement stage could have caught it. No process change is called for; it is recorded here because the prereq's review did not catch it either (the method existed but had no call site, and the guard matches calls, not definitions).

### Minor — fixed in this pass

- **The holds feed leaked its listener on a wiring failure.** `offHoldsFeed` was a `const` inside the `try`, and the `node.stop` wrapper that calls it is installed four statements later. A throw in between — building the reaction, `monitor.start()` — left a subscribed listener adding to a monitor nothing would ever read or tear down, for the node's life. `offHoldsFeed` is now hoisted above the `try` and dropped in the `catch`.
- **`subscribe<L>(listeners: Set<L>, listener: L)` lost the guarantee that a listener is callable.** Generalising from an event type to a listener type was right (the feed hands listeners two arguments), but dropping every constraint means a `Set` of non-functions type-checks and only breaks when the feed emits. Constrained to `L extends (...args: never[]) => void`, which admits both existing feeds and the new one.
- **`seedHeldBlobs`'s comments claimed cancellation and yielding it does not provide.** Both enumerations are materialized before their loop — `responsibleRefs` reads and decodes every blob record — so `isStopping()` and the cooperative yield bound only the tracking loops, not the scan that feeds them. The scan still yields between records (each read awaits) and holds up nothing but itself, but it cannot abandon early. Comments corrected to say that, with a `NOTE:` naming the fix if it ever matters (a streaming enumeration of held references on the blob service).

### Tripwires — parked at the site, not filed

- **Tracking `owed`-only references buys little.** The release arm skips them (`release:not-responsible`) and `BlobCopyDrain` already follows their cohorts on every pass, so the growth arm only duplicates announcements the drain would send, at one `findCluster` per owed reference per check. Kept — it is the one thing that still announces a writer's owed blobs when `blobs.copy.enabled` is false while owed entries from an earlier run remain, and `owed` is as much "kept for the network" as `responsible` is. `NOTE:` at the feed in `libp2p-node-base.ts` saying to feed only `responsible` here if those checks or announcements ever show up as costly.
- **A reaction still in flight when the node stops.** `monitor.stop()` does not wait for it, so its remaining announcements go out while the transports are still up and its last record write either lands or rejects into the handler's `catch`. A `responsible` hold left unreleased is the safe direction and is re-detected on the next run. Added as a clause to the existing in-flight `NOTE:` rather than as a finding of its own, since it is the same shape as the overlap that note already covers.

### Weighed and left alone

- **The guardless handler** — the one judgment call the implement ticket flagged for a second opinion. Confirmed as correct and consistent: the block reaction's handler is guardless in the same way, and `RebalanceMonitor.recordGrowthOutcome` already carries a `NOTE:` accepting the single effect two racing checks have on its state ("two checks racing … double-count one attempt. Both are rare, both only change how many pushes a doomed peer absorbs"). Traced the other arms by hand for the overlap case: `releaseResponsible` writes nothing the second time (`recordAfterHoldRelease` returns the record unchanged, and the store writes nothing for an unchanged encoding), and a duplicate announcement meets the receiver's `AnnounceLimiter`. The note's named fix (one in-flight promise, as `BlockTransferCoordinator` does with its `inFlight` keys) stays the right escalation if overlap is ever observed.
- **The release arm's unbudgeted announcements.** The prereq's review parked this as a tripwire at `BLOB_ANNOUNCES_PER_PEER_PER_MINUTE` in `packages/db-p2p/src/protocol-limits.ts`. This ticket makes the path reachable on a running node but changes nothing about the analysis, so it was not re-filed.
- **The record-scan cost at startup.** `blobReceiver.resume()`, `blobCacheBudget.request()` and now `seedHeldBlobs` each walk every blob record, concurrently, on the way up. The `NOTE:` at `LocalBlobService.readableRecords` already owns that cost ("one `get` per record, and the three callers above each walk the lot … index the records by what each pass asks about"); `seedHeldBlobs` is a fourth caller of an existing method, not a fourth pass shape, so the note needed no change.
- **File size and the hand-written stop wrapper.** `libp2p-node-base.ts` is 3423 lines (`wc -l`), and this ticket added a ~100-line inline wiring block and a twelfth `node.stop` wrapper. `tickets/backlog/debt-node-factory-wiring-steps-own-their-teardown.md` already owns exactly this class — including a *Second arm* on the untestability of reaction-handler bodies registered inside the factory — so an arm was appended to it as evidence rather than a new ticket filed. Two of this review's fixes were only necessary because the block is a closure rather than a named function, which the arm records.

### Checked and found sound

- **The single-path claim for the feed.** Every one of the twelve record mutations in `LocalBlobService` goes through `changeRecord`; nothing writes or deletes a record around it, so no hold can appear or go unobserved.
- **The `owed` hold and the owed ledger entry are coupled in both directions.** `NodeBlobService.announce` takes the hold before recording the entry; `BlobCopyDrain.finish` deletes the entry before releasing the hold. So the feed's `owed`-or-`responsible` test and the seed's `responsibleRefs` + `owed.list` enumeration cannot disagree except in the already-documented safe direction (a crash-orphaned hold with no entry, which the reclaiming pass owns).
- **A record losing its last hold** is deleted by the store (`BlobRecordStore.apply` deletes on `holds.length === 0`), so the feed fires with no holds and the reference is untracked — the release path's end state is reached, not just its first step.
- **A reference released while still `owed`** stays tracked: `releaseResponsible` leaves the `owed` hold, the kinds changed, and the feed re-tracks.
- **A malformed routing key cannot fail a check.** `routingKeyForBlob` is called inside `cohortFor`, which `performRebalanceCheck` already wraps per reference (`lookupFailed++`, continue).
- **The docs' three switch claims** (`rebalance: { enabled: false }`, arachnode disabled, no FRET) and the client claim are each true of the gate as written, and the client claim is true of the receiver too (`BlobAnnounceReceiver.decided` and `keepAfterRead` both gate on `inCohort`, so a client never takes a `responsible` hold).
- **Documentation.** Read docs/blobs.md §Placement, copying and durability, docs/internals.md §RebalanceMonitor and the `blob:copy` and `rebalance-monitor` rows of docs/debugging.md against the code. Every log line named in debugging.md exists with the fields claimed; the internals and blobs prose match the wiring. The one correction needed was the renamed method in the blobs.md citation.

### Tests

Two added, both for contracts the implement ticket handed to the review as unverified. No test was cut.

- `test/local-blob-service.spec.ts` — "the holds feed fires only when a record's set of hold kinds changes". `emitHoldsChanged` is the branching the whole feature's tracked set depends on and nothing exercised it. One test covers the documented rule in both directions: a first kind firing, three changes that leave the kind set alone (a replaced `responsible` scope, a second owner's pin, the `lastReadAt` a read writes), each hold that goes, the record deleted with its last hold reported as no holds at all, a throwing listener not stopping the next one, and the unsubscribe.
- `test/rebalance-monitor-node-wiring.spec.ts` — assertions added to nodes that spec already boots, so no new wall-clock: the blob monitor is exposed and started on the arachnode node with a tracked set of its own (the block instance's is non-zero after the commit there), it stops with the node, and it is `undefined` under `rebalance: { enabled: false }` and with arachnode disabled — where the blob copy drain is still asserted present, since the two are independent. Deliberately added here rather than in a spec of its own: the same three gates decide both instances, so one booted node proves both.

The `grown`/`lost` decision arms stay pinned by `test/blob-cohort-reaction.spec.ts`, the monitor's check-and-report behaviour by the five rebalance suites, and the copying this triggers end to end by `test/blob-copy.spec.ts`. Still not covered, and judged not worth its cost: a two-node real-libp2p test of the growth path on a *blob*, which would need a cohort change between two nodes both holding blob records. The equivalent gap on the block side is recorded in the node-factory debt ticket's *Second arm*, and the same resolution covers both.
