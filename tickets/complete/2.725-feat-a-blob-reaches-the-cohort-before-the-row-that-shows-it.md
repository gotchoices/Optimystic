# A blob reaches the cohort before the row that shows it

Landed as `ticket(implement): feat-a-blob-reaches-the-cohort-before-the-row-that-shows-it` plus this review pass. **No production code changed** — one integration spec, one shared test helper, and documentation corrections.

docs/blobs.md §Committing a reference ends with the two-commit pattern: an application that must not expose a reference before the bytes have moved commits the attachment row (reference only) first, waits for `onDurability` to report `majority` or `full`, and only then commits the row people act on. `feat-blob-pins-follow-sql-commits` pinned every link of that chain on one machine, where the cohort is that machine alone and durability therefore never leaves `local`. This spec runs it across two real libp2p nodes, which is the only place the announcement over the wire, the receiver's read of committed state, the multi-piece pull and a durability class past `local` are real.

## What exists now

**The spec** (`packages/quereus-plugin-optimystic/test/two-node-blob-reference.integration.spec.ts`). One `it`, gated on `OPTIMYSTIC_INTEGRATION=1`. Two real nodes (`clusterSize: 16` against `clusterPolicy.assumedClusterSize: 2`, as `two-node-secondary-index-libp2p.integration.spec.ts` does), each driving its own `Quereus` `Database` through its own plugin, with `types` registered so `blobref` resolves. Two tables over the `network` transactor (`Attachment(Id, Content blobref null)`, `Message(Id, Body, AttachmentId)`).

The run, on node A: put a 2×256 KiB + 1 KiB blob (three data pieces under one list piece — `BLOB_PIECE_BYTES` from db-core, so the constant follows the builder); assert A's own node holds what A's plugin put and that B holds nothing of it; subscribe `onDurability`; insert the attachment row; assert a durability event for that reference had already arrived by the time `db.exec` resolved; wait, bounded, for `majority` or `full`; assert **before the second commit** that node B answers `stat(ref).locality === 'here'` and that its `size` is the whole blob; then insert the message row and assert B reads it.

**The wiring, which is the spec's one deliberate deviation from its precedent.** Each plugin is handed its node (`registerLibp2pNode`), not a `NetworkTransactor` built beside it, and the factory builds the transactor over that node. Verified against source in this pass: `CollectionFactory.resolveBlobBackend` reads the blob service off a node registered under `getNodeKey(options)` = `${networkName}:${port}`, `registerLibp2pNode` registers under `${networkName}:0`, and `resolveBinding` maps the plugin's `default_network_name` into `libp2pOptions.networkName` with `port` defaulting to 0 — so the three agree, and `default_network_name: NETWORK_NAME` is load-bearing exactly as the handoff said. A `network` transactor registered directly instead falls through to a `SingleMachineBlobService` whose cohort is that machine alone (logged `blob:backend-single-machine reason=transactor-has-no-node`), which is why `two-node-secondary-index-libp2p` and `plugin-first-launch-libp2p` could not exercise blobs across machines. That is documented behaviour, not a defect.

**The shared multiaddr helper** (`test/libp2p-addrs.ts`). `pickLocalTcpMultiaddr`, now imported by all three real-libp2p specs in the package instead of copied into each.

## Review findings

Read the `ticket(implement): feat-a-blob-reaches-the-cohort-before-the-row-that-shows-it` diff with fresh eyes before the handoff summary.

**Correctness of what the spec asserts — checked, no defect found.** Every claim in its header was traced to source rather than taken on trust:

- **`BlobRef` is a branded string**, so `event.ref === ref` compares values, not identities.
- **The first durability event really is there when `exec` resolves.** `SqlBlobService.onDurability` attaches synchronously once the backend is resolved, and `put` resolved it (`backendNow`), so subscribing after the put and before the commit cannot miss the announce. Both the put and the tables resolve the same backend: one transactor key, `network:libp2p`.
- **`majority` is unreachable in a two-member cohort**, as the handoff said: `classifyBlobDurability` returns `local` at `2n ≤ k`, so `n = 1, k = 2` is `local` and `n = k = 2` is `full`. The spec accepting either class is therefore spec-faithful rather than loose, and `reached.confirmed === 2` cannot contradict it. Left as written — pinning `full` would encode which class a cohort of two happens to produce.
- **`stat` means what the assertions take it to mean.** `NodeBlobService.stat` without `probe` delegates to the local service, which answers `unknown` from a missing record and `here` with `size` from a whole one — so "B holds nothing yet" and "B holds the whole blob" are both read off this machine alone, with no probe that could answer from A.
- **The blob protocol string the gate waits on is the one production registers**: `buildBlobProtocol('/optimystic/<networkName>')`, matching `protocolPrefix` in `libp2p-node-base.ts`. The node exposes no `blobProtocol` of its own to read instead.
- **Both citations inside the spec's comments resolve**: `packages/db-p2p/src/blob/accepts-blobs.ts` (`blobAcceptanceOf`) and backlog `debt-a-peer-read-as-refusing-may-only-be-unidentified`.

**Minor findings — fixed in this pass.** Seven, all in test and documentation code:

- **The suite's timeout was smaller than the sum of its own bounded waits.** 30 + 40 + 40 s of gates, then a 40 s cohort wait and a 120 s durability wait, is 270 s against `this.timeout(240_000)` — so on a slow machine the diagnostic the implementer wrote ("stalled at `local` (1 of 2 accepting cohort members hold it)") would have been replaced by a bare mocha timeout. The bounds are now one `BOUNDS_MS` record and the suite timeout is derived from their sum plus a minute for the node boots, which makes the mismatch structurally impossible rather than fixed once.
- **Nothing failed loudly if the plugin's blob service was not the node's** — the handoff flagged this itself. One assertion now reads A's *node* stat right after the put (`locality === 'here'`), so the misconfiguration the spec's header spends a paragraph on fails immediately and by name instead of surfacing two minutes later as a durability stall.
- **`waitForCohortDurability` reimplemented `waitForValue`** with `waitFor` plus a non-null assertion and a second scan of the event list; it now calls `waitForValue` (already exported from `@optimystic/db-core/test`) and keeps its own catch for the better message.
- **`classesFor` returned durability records, not classes** (the class is the `quorum` field) — renamed `durabilitiesFor`.
- **The teardown abandoned live nodes on a failed close.** The sequential `for` loop meant one handle that refused to close left the remaining plugins undisposed and both real libp2p nodes listening; the machine disposals are now settled like the node stops.
- **A third copy of `pickLocalTcpMultiaddr`.** The same seven lines were in `network-change-notification.integration.spec.ts` and `two-node-secondary-index-libp2p.integration.spec.ts`; db-p2p's own shared copy (`test/util/multiaddrs.ts`) exists *because* its copies drifted and failed in one spec while passing in another. Extracted to `test/libp2p-addrs.ts` and all three converted; db-p2p's cannot be imported here, since it publishes `src/testing` and not its test tree, so the repo now has two copies rather than four.
- **Documentation that still said this machinery was unbuilt.** docs/blobs.md is a file this change touches, and three of its claims were stale, two of them contradicted by the test that just passed: §The node's blob service ended with "What waits on later work: on a node, `announce` rejects, `stat` reports no `durability`, and `onDurability` never fires, until `feat-a-referenced-blob-is-copied-to-its-cohort`" (a ticket slug that is no longer on the board); §Moving pieces between machines listed "**To be built:** acting on a `held` that arrives", which is `onHeld` → `BlobCopyDrain.noteHeld`; and the transfer benchmark called copying to the cohort "(to be built)". All three now say what is built. The same stale claim in `packages/db-p2p/src/optimystic-node.ts`'s jsdoc for `blobs` ("announcing and copying are later work") went with them, so the class is retired rather than one instance of it. Separately, `blob-pins-online.spec.ts` pointed at this ticket's slug for "the two-node proof"; it now names the spec file, which will still exist when the ticket does not.

**Tripwire parked** (not a ticket): the `Machine` / `machineOver` / teardown trio in this spec is the same as `network-change-notification.integration.spec.ts`'s, parameterized differently. Two copies are cheap to keep in step, so a `NOTE:` at `machineOver` says to extract them into one harness if a third real-libp2p spec in the package wants them — the way `mesh-node-harness.ts` was extracted once the mock mesh had four copies.

**No tickets filed.** Nothing found reached the filing bar: there is no production code in the diff, no latent defect, and the one duplication worth naming is conditional and parked as above.

**Tests: one, unchanged in count.** The implementer's single `it` is the ticket's whole deliverable and it pays for itself — it is the only place the announcement over the wire, the receiver's read of committed state, the multi-piece pull and a durability class past `local` are real, and the mechanism's own cases already live one layer down in `blob-copy-drain.spec.ts`, `blob-announce-receiver.spec.ts` and `blob-copy.spec.ts`. Nothing was cut (nothing restated the implementation or verified a mock) and nothing was added: no defect was found that needed reproducing, and the contract the review strengthened — that the plugin's blob service is the node's — is an assertion inside the existing test, not a test of its own.

**The handoff's five honest gaps, each reviewed:**

- **Timing margin.** Two more runs here, 5.47 s and 5.52 s, against the same bounds — consistent with the implementer's three. Still unmeasured on CI; the timeout fix above is what makes a slow machine report which wait gave up.
- **`majority` unreachable at two members.** Reviewed above; left as written, deliberately.
- **The blob-protocol gate papers over `debt-a-peer-read-as-refusing-may-only-be-unidentified`.** Accepted: the ticket exists in `backlog/`, the comment at the gate says the gate means this spec will not catch that defect, and gating is right here — a misread denominator would otherwise be what every failure of this spec looked like.
- **B's own cohort view is not gated.** Accepted: A is the announcer, so A's view decides who is owed, and B answering `not-responsible` for a moment is what the drain's retries are for. Named in the spec as the wait to add if it ever flakes.
- **The announced scope and the pin labels are not asserted.** Accepted: `blob-pins-online.spec.ts` owns both, on one machine where they are cheap to read.

**Documentation checked beyond the diff.** `packages/quereus-plugin-optimystic/test/README.md` was read and deliberately left alone: it names about a dozen of the package's ~120 specs and lists none of the three integration specs, so adding this one would make it look like an index it is not. docs/reactivity.md's citation of `network-change-notification.integration.spec.ts` still resolves after that spec's import change.
