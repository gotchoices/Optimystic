# A node deletes what it released

The eligibility handoff that was an in-memory `Set<string>` with no consumer is now a durable ledger with a sweep that reads it, and the sweep is the only caller of the `deleteBlock` that `a-block-s-bytes-can-be-deleted` built.

## The invariant, and what carries it

> **A block's bytes are deleted only after a release that confirmed at least the replication floor of other serving holders hold a current replica of it.**

Three structural facts carry it, and each is the answer to a way it could be lost:

- **Two writers, both inside the confirmed-release paths.** `recordReleased` in `libp2p-node-base.ts` is the one function that writes the ledger, called from `RingShiftCoordinator`'s `onRelease` (Phase C) and from the rebalance reaction's `result.released` arm. Nothing else may.
- **The sweep derives nothing.** `ReleasedBlockSweep` reads the ledger and never the node's ring, partition or owned-block set. Mid-shift the advertised partition is the *target* ring, so a block that merely looks outside this node's slice may be one whose handoff rolled back and is still being served.
- **The entry outlives the delete it records.** It is dropped after the delete, which is why `deleteBlock` is ordered and idempotent. A crash in between leaves content with no metadata plus an entry, and the next run finishes it.

## What landed

**`ReleasedBlockLedger`** (`packages/db-p2p/src/storage/released-block-ledger.ts`) — one entry per released block under the new `optimystic-released/` namespace of the node's `IKVStore`, shaped after `OwedBlobLedger`: `record` (durable; refreshes an existing entry rather than leaving it), `list` (oldest release first, so a capped run makes progress), `remove` (durable), `noteFailure` (deliberately not flushed — the exception `OwedBlobLedger.markUnlisted` already makes, argued at the site). An entry carries `releasedAt`, `source` (`ring-shift` or `rebalance`), `releasedRev` and `attempts`. `RELEASED_BLOCK_KEY_PREFIX` is in `NODE_KV_NAMESPACES`, so a file-backed store sharing the block store's directory does not list these keys as blocks.

`releasedRev` is the entry's answer to "has this block been written again since I let it go?". Block metadata carries no wall clock for a committed revision, so the entry records the revision this node held at release (read through `StorageRepo.heldRevisions`) and the sweep compares against that.

**`ReleasedBlockSweep`** (`packages/db-p2p/src/storage/released-block-sweep.ts`) — per entry: `StorageRepo.deleteBlockIfNotAdvanced`, then drop the entry. Single-flight with one queued follow-on (`BlobCacheBudget`'s shape). Per-run cap of 256 entries, three failed attempts per entry after which it is passed over and left in the ledger for an operator to see. One `sweep:run` line per run — empty ones included, because `found=0` is the answer to "why is this node's disk not getting any emptier" — plus a line per block. One `LocalBlobService.sweep` request per run that deleted anything; nothing new was built for the blob half.

A run that stopped at its cap **and dropped at least one entry** asks for the next run itself, so the cap chunks a large shed rather than rationing it: a node that dropped below `shedAbove` by deleting these very blocks gets no further pressure request, and nothing else asks until the next release. Both conditions are load-bearing — see the review finding below for why the second one is.

**`StorageRepo.deleteBlockIfNotAdvanced`** (new capability `IReleasedBlockDeleter`) — the latch hold, the written-again check and the delete as **one** operation, because the check is only meaningful inside the same hold: a push or commit landing between a separate read and delete would be taken anyway. Answers `deleted` or `advanced`. Wrapped in `endGroup` with a `wrote` predicate, so the delete is durable before it resolves and a block the check kept flushes nothing.

**Wiring.** `prepareServingStore` builds the ledger over `kvStore` after the repo (it reads `heldRevisions` through it). The arachnode block's `gcEligible` set is gone; both release callbacks go through `recordReleased`, which logs `release:unrecorded` rather than throwing — the release itself already happened and is correct, and losing the record costs bytes this node keeps rather than a block the cohort loses. `RingShiftDeps.onRelease` may now return a promise and Phase C **awaits** it, so a shift is not reported as settled until its release is recorded. The rebalance reaction's ledger write is placed **last**, because deferring the growth feedback past a store write would let the re-check timer fire first and re-push a block already confirmed. The sweep is built after the blob cache budget and before `storagePressure.start()`, runs once immediately (the start-up run that finishes interrupted deletes), and its stop wrapper sits between the cache budget's and the pressure reading's, so teardown order is pressure, sweep, cache budget, blob service. `StoragePressure` gained `requestReleasedBlockSweep`, and its single `try`/`catch` around the one old trigger became `requestSheddingReactions` plus `fireTrigger`, so one reaction's fault neither disarms the other nor takes the sampler down (`pressure:enforcement-refused` became `pressure:trigger-refused trigger=<name>`).

## Deviation from the ticket — the sweep runs on the serving role only

The ticket asked for the sweep on both roles, "for the reason the blob reclaim pass runs on a client: one wiring, one rule". It is on the serving role only, and the reasoning holds up: the blob reclaim pass runs on a client because its dependency, the blob service, exists on both roles, whereas `prepareServingStore` is called only when `servesBlocks`, so a client builds no `StorageRepo` and no ledger. Both release paths live inside the serving role, so a client's ledger would not merely be always empty — it would not exist. What the ticket's "Arachnode disabled or no FRET" case required *is* honoured: the sweep sits outside the arachnode gate, so a serving node whose FRET service is absent this run still finishes what a previous run recorded.

## Review findings

Read the `ticket(implement): a-node-deletes-what-it-released` diff before the handoff summary.

**Correctness — one liveness defect found and fixed inline; one race filed; everything else checked and sound.**

- **The self-chaining sweep could spin for ever under a faulting store (fixed inline).** A run asked for the next run whenever `remaining - exhausted > 0`, and the termination argument was that every entry a run acts on is deleted, dropped, or counted one attempt toward the three-attempt bound. But the attempt count is itself a write to the same key-value store the delete failed against, and `noteFailure` answering 0 when its own write fails is the documented behaviour — so a store faulting on both (a full or unwritable volume, which is exactly the condition that makes the sweep run) leaves the actionable set unchanged for ever, and each chained run is a full ledger scan plus a batch of failing deletes with no pause between runs. Found by reading; not reproduced by inducing a disk fault. The chain now also requires that the run **dropped at least one entry**, which is measured rather than argued and makes the ledger strictly smaller per chained run, so a chain is at most one run per entry; a run whose whole batch failed waits for the next pressure sample or release instead, which is also the back-off a faulting store wants. The cap condition is now explicit (`cappedOff`) rather than inferred from the remainder arithmetic, and `actionableRemaining` is gone. `shouldChain` carries the argument.
- **A replica pushed back during a release can still be deleted — filed, not fixed.** `releasedRev` is read *after* the release rather than at the moment the release was decided, so a replica that arrives in the gap (the untrack loop, the growth bookkeeping) is accepted first and read second, and is written down as though it were the released revision; the sweep then finds nothing advanced and deletes a block the owned-block feed has re-tracked. The code comments argue the opposite ordering correctly — a write landing *after* the read only makes the recorded revision early, which is safe — but that argument does not cover a write landing before it. The gap is a handful of event-loop turns and the damage repairs itself through read repair, so this is `tickets/backlog/bug-a-replica-pushed-back-during-a-release-can-still-be-deleted.md` (severity `edge-case`, likelihood `contrived`, `repro: static`) rather than a fix here: the real fix captures the held revision at or before the release in both paths, which is a change to the ring-shift and rebalance release interfaces, not to the ledger.
- **`sweep:delete-failed` was logged for deletes that had succeeded (fixed inline).** The entry is dropped after the delete and both are inside one `try`, so a failure of the ledger's own `remove` — acknowledged at the site — reported "the delete failed" about a block whose bytes were already gone, which is the diagnostic that sends an operator looking for bytes that do not exist. The catch now distinguishes: `sweep:delete-failed` when the storage call never answered, `sweep:entry-undropped` (naming the outcome) when it did and dropping the entry is what threw. The tally still counts both as `failed`, which is right — the entry is in the ledger either way, which is what keeps `remaining` honest. `docs/debugging.md` documents the new line.
- **A duplicate log line removed.** `deleteBlockIfNotAdvanced` logged `deleteBlockIfNotAdvanced:advanced` under `storage-repo` for the same event its only caller logs as `sweep:written-again` under `storage:released`, with more context (the release's source and recorded revision) — and the `storage-repo` row in `docs/debugging.md`, which enumerates that namespace's lines, did not mention it. One event, one line, at the layer that has the context.
- **An unused method removed.** `ReleasedBlockLedger.get` had no caller anywhere in src or test and is not in the sweep's `Pick`; `list` is what the diagnostics attachment needs. Removed while it is still new enough that nothing can depend on it.
- **The pieces the handoff asked a reviewer to look at all hold up.** Teardown order is as claimed — wrappers each call their captured `previousStop` last, so last-installed runs first, and the sweep's wrapper at `packages/db-p2p/src/libp2p-node-base.ts:2034` sits between the cache budget's (1995) and the pressure reading's (2058), giving pressure, sweep, cache budget, blob service. The self-chaining `request()` from inside `runOnce` leaves no orphan: `this.running` is still set there so it becomes the single queued follow-on, `startAfter` clears `queued` before starting, and a follow-on that begins after `stopping` returns the empty run without touching the ledger. `deleteBlockIfNotAdvanced` holds one latch across both the `getLatest` and the `deleteBlock`, and `endGroup`'s `wrote` predicate is set only on the delete path, so a kept block flushes nothing and a deleted one is durable before the entry is dropped. `recordReleased` catching at the call site rather than inside `ReleasedBlockLedger.record` is the right split — it keeps the ledger's house rule that a write either lands durably or rejects.
- **The newly-live interactions were checked, not assumed.** This ticket gives `deleteBlock` its first production caller, so the cache coherence that `a-block-s-bytes-can-be-deleted` built is now reachable: `CachedStoreDriver.deleteBlock` drops everything it holds for the block before *and* after the inner delete, including on the failure path, and `WriteGroupDriver` flushes its group strictly first, so nothing resurrects a deleted block. `executeShift` clears `inFlight` in a `finally`, so an `onRelease` that rejected cannot wedge the coordinator, and its one caller catches. The ledger's key shape (prefix plus raw block id) is exactly `KvUnderReplicationLedger`'s, so nested block ids are not new ground for a file-backed store. A revision of 0 is read with `??` rather than truthiness at every site that reads `releasedRev`.
- **Checked and accepted:** the block-id-as-path `NOTE:` is correct to add no guard here — `FileBatchBackend.blockPath` refuses such an id at the storage boundary, so a block with one cannot be stored, owned or released, and `tickets/fix/bug-a-block-id-is-used-as-a-file-path-without-validation.md` owns closing the class. An unreadable block at release time recording no `releasedRev`, under which the sweep declines it, is conservative and documented on the field. A block the sweep keeps (`advanced`) has its entry dropped and is re-offered by the next rebalance pass, which the handoff verified against `saveReplicatedBlock`'s `landed` emit and `ensureOwnedBlockFeed`; re-read and agreed.

**Tests — both of the implementer's kept, none added.** The ring-shift case earns its place: it drives a real `RingShiftCoordinator` through a rolled-back Phase B and then a confirmed one, over a real ledger, and what it pins is *which ids reach the delete* — the whole class of "the sweep worked out eligibility for itself".
