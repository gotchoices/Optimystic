# A SQL host turns on blob file paths with one registration setting

`blob_paths` is a plugin-level registration setting (`'off'`, `'verify'`, `'trust'`; empty or absent means off) carried through a binding's options to both blob services a network's blobs can go through, so `plugin.blobs.pathAccess()` answers an object rather than `undefined` without the host building and registering a libp2p node of its own. Neither guarantee changed — `verify` re-hashes every leaf the piece store imported, `trust` takes the store's ids as given — the plugin only asks for them now.

## What landed

- **`declaredBlobPaths(aux)`** in `optimystic-module.ts`, beside the other plugin-level setting parsers: `undefined`/`null`/`''` are unset, the three mode names pass through, anything else throws naming the setting and all three modes. Called from `resolveBinding` (which puts it on the options) and once from `register` so a mistyped mode throws before anything is built.
- **`blobPaths` is a top-level option**, not part of `libp2pOptions`, because the single-machine arm has no node.
- **`CollectionFactory.resolveBlobBackend`** builds the `SingleMachineBlobService` init explicitly (`pieces`, `kv`, `paths`) over `storageFor(options)` with per-field memory fallbacks; **`createNetworkTransactor`** passes `blobs: { paths: options.blobPaths }` unconditionally, which is equivalent to passing no `blobs` at all when unset.
- **Docs**: the `blob_paths` row in `package.json`'s `quereus.settings` (a `select`, as `cost_profile` is), the README's *Plugin-Level Configuration* table and large-values bullet, and docs/blobs.md's status paragraph and §SQL path bullet. The `trust` tradeoff is stated once, in docs/blobs.md §Putting and reading by file path, and cross-referenced from the rest.

## Review findings

Read the `ticket(implement): feat-a-sql-host-cannot-turn-on-blob-file-paths` diff before the handoff summary.

**Correctness — checked, no defect found.**
- Both services the plugin builds are reached: `createLibp2pNode` and `new SingleMachineBlobService` are the only two construction sites in the package, and both carry the mode. `SingleMachineBlobService` forwards `paths` to its `LocalBlobService`, which resolves `init.paths ?? 'off'` against `offersFiles(pieces)`, so unset and `'off'` are one answer and a store that cannot reach files refuses nothing.
- The handoff's claim that `blobs: { paths: undefined }` is indistinguishable from no `blobs` option holds: every sub-option read in `libp2p-node-base.ts` is `options.blobs?.X ?? default` (`digest`, `hold`, `cacheBudgetBytes`, `reclaimGraceMs`, `copy.enabled`), and nothing branches on the presence of `blobs` itself.
- Every path that builds a `ParsedOptimysticOptions` goes through `resolveBinding`: `parseTableSchema` (a table's own args over `vtabAuxData`), `deriveDefaultOptions` (what `plugin.blobs` resolves on), and through those `bindingOptionsOfTable` (`plugin.blobsFor`). The two hand-assembled options objects in the module — `openIndexTree` and `createSchemaManager`'s `schemaOptions` — both spread the caller's options, so the mode survives the hop that `debt-a-networks-storage-is-taken-from-one-collections-options` describes (a catalog read naming a transactor key first is what records that key's options).
- Leaving `blobPaths` out of `createSchemaManager`'s fingerprint is right: the mode is plugin-level, so no two tables of one registration can disagree about it, and it changes nothing about a catalog tree.
- `register` validates the same object `resolveBinding` later reads (`auxData: config`), so the value checked early is the value that arrives. A plain `Error` matches `cost_profile` and `blob_unstaged_holding_ms`; the setting's `select` shape in `package.json` matches `cost_profile`'s, `''` option and `default: ''` included.
- Nothing refuses unknown registration keys, so there is no allowlist this setting had to be added to; `blob_paths` as a per-table `USING` argument is silently ignored, exactly as the other plugin-level settings are.

**Tests — one rewritten, the rest kept.** The implement stage's two cases over `getBlobBackend` drove a hand-built `ParsedOptimysticOptions`, which skipped the whole registration chain and so could not see the one hazard the handoff itself named: `blobPaths` is optional in every type it passes through, so a link that stopped carrying it still compiles. Rewritten to go through `register(db, { blob_paths })` and `plugin.blobs.pathAccess()` — same two cases (declared mode, and unset) and the same file-capable `MemoryPieceStore` subclass, now covering parser → aux → `resolveBinding` → factory → `SingleMachineBlobService` → `SqlBlobService`. Verified sensitive: with `blobPaths: declaredBlobPaths(aux)` deleted from `resolveBinding` the mode case fails (`expected undefined to equal 'verify'`) where the old case still passed. The spec also now closes its databases and disposes its plugins (`afterEach`), as the other blob specs do, instead of leaving two started blob services behind. The three `declaredBlobPaths` cases are unchanged — one per refusal branch, matching `storage-allotment-setting.spec.ts`. No case was added for the node arm: one literal field the node's option type settles, and the package's node specs are integration-gated.

**Documentation — read every file the change touches, plus the ones it should have.** README's large-values bullet and settings table, docs/blobs.md's status paragraph and §SQL bullet all describe the new reality, and the `trust` tradeoff is stated in exactly one place. Checked three places that could have gone stale and did not need an edit: `docs/blobs.md` §Putting and reading by file path (about `NodeOptions.blobs.paths`, which did not change), `docs/debugging.md` (the `blob:paths` log line is already documented under db-p2p's `blob:store`, and the plugin added no log line of its own), and `.release-notes.pending.md` (no open unreleased section — notes are written at release time here).

**Tripwire parked, no ticket.** `BLOB_PATH_MODES` is tied to `BlobPathMode` with `satisfies`, which catches a renamed mode at compile time but not an *added* one: a fourth mode added in db-p2p would be refused by this plugin until the list, `package.json`'s settings and the README's table are updated. That is the same deliberate "loud and stale" trade the neighbouring `STORAGE_ALLOTMENT_KEYS` records, so it is now a `NOTE:` at the constant naming the three places a new mode must reach.

**Size — nothing new filed.** `optimystic-module.ts` is 7937 lines (`wc -l`); this ticket added about 30. The split is already `backlog/debt-optimystic-vtab-class-is-too-big-to-review`, so this is evidence, not a new ticket.

**Nothing to report in three categories, and why.** No *major* finding, so no ticket was filed: the behaviour, the docs and the option plumbing all hold, and the one weakness worth acting on was a test that proved less than it claimed, which is an inline fix. No *accepted-tradeoff* finding was re-opened: the only `NOTE:` of that kind at a site this ticket touches is `SingleMachineBlobService.read`'s `cohort-unreachable` reason, whose revisit condition (a caller deciding something from the reason) has not tripped. No *resource* finding in production code: the single-machine service this path builds is still registered in `singleMachineBlobServices` and stopped by `CollectionFactory.dispose`, and nothing new holds a timer.
