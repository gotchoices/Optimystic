# A store keeps commit proofs by message hash

First half of GitHub #60 (a commit proof is stored once per block it covers; a bulk import grew a file store to 7 GB, 94% duplicate proofs). Landed in `ticket(implement): a-store-keeps-commit-proofs-by-message-hash`. The follow-on `a-commit-proof-is-stored-once-not-once-per-block` makes the kernel use the store.

## What was built

A seventh logical block-storage store, **commit proofs**, holding one encoded `BlockCommitProof` per consensus message, keyed by the proof's `messageHash`. Plain get and put, no delete (same reason the per-revision proofs store has none).

- `RawStoreDriver.getCommitProof` / `putCommitProof`; `IRawStorage.getCommitProof` / `saveCommitProof`, implemented by `KvRawStorage` and re-encoded by `RawStorageDriverAdapter`.
- `StoreKey` gains `{ store: 'commitProofs'; messageHash }`, the one variant with no `blockId`; `canonicalStoreKey` gives `commitProofs/<hash>`. `decodeStoreKey` in the journal record codec now switches on `store` before checking fields.
- `CachedStoreDriver` passes through uncached; `WriteGroupDriver` routes through overlay and batch.
- Backends: memory map; file `commit-proofs/<hash>.json` at the root, skipped by `listBlockIds`, other characters percent-encoded; SQLite table `commit_proofs` (`TableLayout.table` added); IndexedDB object store `commitProofs`, database version 4; LevelDB tag `0x08` with no block envelope.
- Conformance tests (miss, round-trip including path-character keys, keyspace isolation from the per-revision store, persistence across reopen) run on every backend and composition; the journal codec round-trip covers the new key shape.

## Review findings

Read the implement diff first, then the handoff.

**Correctness, per backend — checked, no defects.**
- File: read path and log-write path both go through `commitProofRelativePath`; `approximateBytesUsed` sizes the whole base directory, so the new directory is counted; `listBlockIds` skips it at the root only; `..`-style keys cannot escape (percent-encoded). The encoding is injective for well-formed strings; a lone surrogate encodes as U+FFFD does — corrected the comment that claimed full injectivity (minor, fixed inline). Case-insensitive collisions are already recorded at the site.
- SQLite: every statement (get/put/delete) reads `LAYOUTS[store].table`; `CREATE TABLE IF NOT EXISTS` adds the table to an existing file.
- IndexedDB: upgrade guarded by `objectStoreNames.contains`; `commitProofs` is in `APPLY_STORES`; `isStoreKey` checks per store. Untested-upgrade debt already tracked by backlog `debt-indexeddb-version-upgrade-is-untested-and-unhandled`.
- LevelDB: no range scan reaches `0x08` (journal `[0x07,0x08)`, metadata `[0x01,0x02)`, per-block scans inside their envelope, KV from `0x10`). Distinct strings give distinct keys within the tag.
- `canonicalStoreKey`: every form begins `<store>/`, store names have no `/`, so the new form cannot collide with block-scoped ones; in-memory doubles keyed by it need no change.
- No other `IRawStorage`/`RawStoreDriver` delegator in production source; typecheck covers the classes that implement them.

**Docs — three stale, fixed inline.** `packages/db-p2p-storage-ns/README.md`, `packages/db-p2p-storage-rn/README.md` and `packages/db-p2p-storage-web/README.md` still said six stores and omitted the new store from their layout tables (and eight tables / eight object stores in total); updated counts and added the `commit_proofs` / `0x08` / `commitProofs` rows. `packages/db-p2p/docs/storage.md` quoted the kernel's "single choke point" comment without `saveCommitProof`; updated to match the code. `docs/internals.md`, `storage.md` §5 and the fs README were already correct.

**Tests.** The new conformance cases each pin a contract of a new storage surface across five backends (the path-character case is the only thing pinning the file encoding's injectivity), so none were cut. The handoff's point that only the codec spec exercises `decodeStoreKey` on the new key holds; the added codec entry covers it. No new tests added: no defect found that needed a reproduction.

**Error handling, resource cleanup, performance.** Nothing new: the store adds no handles, timers or loops; the file read uses the existing corrupt-JSON-as-missing guard.

**Latch / concurrency.** The store is not filed under any block; `storage.md` Invariant 2 now says so and defers the writer's latch to the follow-on, which is the right place — no writer exists yet.

**Tripwires / tickets.** None filed; no conditional concerns beyond those already noted at their sites.
