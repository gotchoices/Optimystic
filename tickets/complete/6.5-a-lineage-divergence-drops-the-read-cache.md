# A lineage divergence drops the read cache

## What landed

A refresh (`Collection.updateInternal`) that adopts a log context naming a different action than the held context at the held revision (`Collection.judgeAdoption` → `adopt-divergent`) now, unconditionally (not gated on logging):

- drops the whole read cache (`CacheSource.clear()` with no ids, which now also bumps every LRU-evicted id that still has a revision entry) and every floor (`BlockFloors.clear`, the one exception to "a floor, once raised, stands"), before the walk raises the new lineage's floors — all inside `forgetAndAdopt`'s await-free step;
- re-stages every staged action, sealed segments included (`mustReplay`'s fourth reason), since a same-revision fork advances nothing and no other reason would fire;
- rebuilds a head commit's tracker if the lineage moved between attempts at the same revision (added in review, below).

A refused read (handle above the read on another lineage) drops nothing and keeps reporting — that is backlog `feat-replay-mode-collections-merge-divergent-histories`. An open (`site=attach`) only logs.

Implementation commit: `ticket(implement): a-lineage-divergence-drops-the-read-cache`.

**Found and fixed inline**

- **A head commit's tracker survived a same-revision lineage change.** `headTrackerFor` reused the tracker whenever the requested revision was unchanged and no pinned base moved. After an adopted divergence the whole-cache clear makes update pins read as moved, but an action that inserts a block computed from read content pins nothing (the exact shape the new test uses), so such a head attempt would have committed content derived from the old lineage. `HeadTracker` now records the lineage it was staged over (the action the held context names at its own revision) and `headTrackerFor` rebuilds when it differs. Reachable only when a refresh between two attempts of one head commit adopts another lineage at an unchanged revision (the cycle's opening refresh always walks, so it would normally be caught before the tracker is built) — narrow, but definitely wrong when reached, and the fix is a field and a comparison. No test: constructing a lineage change between two attempts inside one cycle needs a fixture that changes storage's lineage mid-cycle; the rule is the same comparison `judgeAdoption` makes and is covered by reading. internals.md updated.
- debugging.md pointed at `docs/transactions.md` for "reconciliation" with no section; now links §Partition Recovery and Reconciliation (Design).
- `BlockFloors.clear` doc now states the pinned-view consequence (above).
