# A SQL commit learns when it becomes fully held

GitHub issue #26, gap 3 (and sereus GH #44's "not yet delivered" mark). Landed in `ticket(implement): a-sql-commit-learns-when-it-becomes-fully-held`.

## What landed

- `register(...)` returns `onCommitFullyHeld(listener)`. The listener receives `{ transactionId }` once per followed commit, when every block the commit wrote below full replication is held by its whole cohort. It follows the same rules as `onCommitDurability` (synchronous, registration order, a throwing listener is isolated, idempotent unsubscribe); the two share `addListener` / `notifyListeners` in `txn-bridge.ts`.
- `SqlCommitDurability.followed`: `true` when `onCommitFullyHeld` will fire for the commit, or when the commit is already fully held ("saved now", never reported again).
- `DurabilityFollower` (no SQL or libp2p in it) returns one of four verdicts: `held`, `unfollowed` (with a logged reason), `covered` (every owed block was covered by an event that arrived before the commit's answer), or `pending`. A block is covered by an event at the commit's revision or a later one, and also by a later commit through the bridge that wrote the block at `full` (`coverHeld`). Events are remembered per notifier in a 4 096-entry LRU. At most 10 000 commits are pending at once; past that the oldest is dropped. Both caps carry `NOTE:` tripwires.
- The bridge subscribes to the node's `StorageRepo` events in `beginTransaction`, before the commit is sent, on `network` transactors only. `plugin.dispose()` calls `TransactionBridge.dispose()` before `CollectionFactory.dispose()`. The commit's report always reaches the host before its `onCommitFullyHeld` call.

## Review findings

Read the implement diff first, then every touched file, the producer side in db-p2p (`CoordinatorRepo.acknowledgeCommit` / `noteReplicationShortfall`, `packages/db-p2p/docs/repo.md` drain section), and the event contract in `packages/db-core/src/transactor/change-notifier.ts`.

**Correctness, checked and holding:**
- The follower's assumption that `recordedBy` = this node means every owed block has a ledger entry on this node, and that each entry's event will reach this node. This matches the producer: `acknowledgeCommit` sets `recordedBy` only when every non-torn block was recorded, and both event producers run on that node. `getPeerId` and `CoordinatorRepo` both name the node by `peerId.toString()`, so the `recordedBy !== selfPeerId` comparison compares the same form.
- Event revision semantics. An event carries the entry's own revision, or the settling `full` commit's revision, and either is ≥ the commit's `blockRevs` revision, so `rev >= r` coverage is right. A superseded entry (one block's entry replaced at a higher revision) is covered by the later event, as the spec test pins.
- The race in which the event fires before the answer arrives: the subscription starts in `beginTransaction`, and `reached` records the event. A `covered` commit is reported after its own durability report.
- Failure safety after a successful commit. `reportCommitDurability` runs after the commit has landed; nothing in the follower throws, except a notifier's subscribe call that throws, which is not a realistic case. Listener throws are caught by `notifyListeners`, including those reached through `coverHeld` → `onFullyHeld`.
- Per-notifier state keeps two nodes' block ids apart. Deleting from `owed` while iterating it is safe for a JS `Map`. `LruMap.peek` does not disturb recency.
- Partial commits (`PartialCommitError`, `CoordinatorPartialCommitError`) throw before `reportCommitDurability` and are never followed, unchanged from the prerequisite ticket.

**Minor, fixed in this pass:**
- The README did not say what a lone machine sees. On a node that is alone in its group (including the plugin-built node, which runs `clusterSize: 1`), every commit is answered `local` and recorded with an empty missing set under `recordedBy`. So it is reported `followed: true` and stays pending until another member takes its copies. A host reading the README would not have expected that. One sentence was added to `packages/quereus-plugin-optimystic/README.md` § "When a pending commit becomes fully held". The follower's pending-cap `NOTE:` already names this case on the code side.

**Major:** none.

**Tripwires:** none new. The two the implementer placed are adequate and stay where they are: the pending-commit cap in `DurabilityFollower.register`, and the remembered-events cap in `DurabilityFollower.stateFor`.

**Considered and left as is:**
- The non-null assertion `source.notifier!` in `follow`. It is guaranteed by `unfollowableReason`, which checks the reasons in order (holders unknown, then torn, then no ledger). Restructuring only to drop the `!` would separate that ordered check.
- `coverHeld` and the event subscription run even when no listener is registered. This costs one LRU write per event per block on `network` transactors and is accepted in the implement handoff.
- README says `mesh-test` "keeps none". Whatever the mesh harness does, `getBlockDurabilityNotifier` returns `undefined` for it, so `followed: false` is guaranteed there.

**Tests:** all five specs in `test/durability-follower.spec.ts` pay for themselves: they pin the follow/refuse decision table, superseded-write coverage, the event-before-answer race, multi-collection waiting, and `coverHeld`. None was cut and none was added. There are no bridge-level tests, by choice. The verdict-to-`followed` mapping and the order "report, then fully held" were checked by reading; they are a few lines, and a test would mostly restate them.

**Known gap carried forward (not filed):** no end-to-end run over real nodes shows `followed: true` from a `network` transactor followed by `onCommitFullyHeld` firing. Each half is pinned at its own layer: the db-p2p specs cover the producer, this spec covers the follower. The joining assumptions (`recordedBy` format, the notifier being the same `StorageRepo`) were confirmed statically. It is not filed because it is not a defect and serves no open anchor. `packages/db-p2p/test/util/two-machine-lifecycle.ts` is the place to build it if a regression ever appears there.

**Other known limits (documented in README and internals):** followed commits are lost on restart, `dispose()`, or cap eviction (backlog `feat-a-host-can-ask-whether-an-earlier-commit-is-fully-held` covers the restart case). Commits made before a listener is registered are not followed. A collection mixing a `full` and a below-`full` cohort answer is refused.
