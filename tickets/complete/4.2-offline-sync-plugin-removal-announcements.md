Second of the five stage-4 tickets of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). Landed in `ticket(implement): offline-sync-plugin-removal-announcements`; the review made no code changes.

## What landed

- `OfflineMode` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`) takes the `Database` and, after a `failed` status has been delivered to every `onStatus` listener, calls `Database.notifyExternalChange` once per distinct table behind the status's `changedCollections`. `committed` and `partially-committed` announce nothing. A cascade announces once per failed entry (an extra re-query for a watcher; accepted by design). Failures are logged `offline:announce-failed`, never thrown into the drain.
- One error-isolating helper, `announceExternalChange` in `optimystic-adapter/external-change.ts`, shared by the controller and the vtab's `handleCollectionChange` (whose "failed"/"threw" WARN lines became one "failed" line).
- `TransactionBridge.collectionTables` keys each collection's tables by the `schema.table` rendering (`qualifiedTableName` in `schema/table-identity.ts`) with the `QualifiedTableName` pair beside it, so no site splits a name on a dot. `registerCollection`, `forgetTable` take the pair; `tablesOf` returns a `ReadonlyMap`.
- `test/offline-mode-removal.spec.ts` (two-node mesh, the drain's pend held by a gate): a rival primary key (constraint + cascaded concurrent-modification, watcher woken after the `failed` status), a rival change of a row a queued update read, a transaction rolled back while the drain commits (each entry committed once, the rolled-back row gone), and a savepoint rolled back after a refused entry was removed. The harness passes `wrapRepo` through and gains `openFreshTree`.
- Docs: README §Offline mode (what a watcher sees on failure; the "not yet" bullet removed), offline-sync.md §Removing an entry step 4 and §Implementation stages, internals.md §Reactive Watch Bridge, debugging.md (`offline:announce-failed`).

Deviations the implementer recorded, and accepted here: no `offline.queue` test seam (nothing needed it); "a statement in progress" modelled with an explicit `savepoint` (same `rollbackToSavepoint` → `restorePending` path as a statement-level savepoint); the reader-refresh-finds-the-refusal case exercised with the head in flight, the idle-drain variant being pinned in db-core's `offline-queue.spec.ts`.

## Review findings

**Read first:** the full implement diff, then `OfflineQueue.remove` and `emit` in `packages/db-core/src/offline/queue.ts`, `Database.notifyExternalChange` in `@quereus/quereus/src/core/database.ts`, `sqlCommitDurability` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-durability.ts`, and offline-mode.spec.ts's case list.

**Correctness — checked, nothing found.**
- The `failed` status is emitted by `OfflineQueue.remove` after every `dropSealed` has been awaited and outside any collection latch, so a watcher whose handler queries synchronously cannot deadlock against the drain.
- Every path that ends in `failed` goes through `remove`, so `discarded`, `expired` and cascaded failures announce too — each takes rows out of view, so that is correct.
- `notifyExternalChange` is `async` and calls `checkOpen` inside, so a closed `Database` surfaces as a rejection that the helper logs; the `Promise.resolve` wrapper only guards a non-promise test double.
- A table dropped before its queued entry fails was forgotten by `forgetTable`, so nothing is announced for it — the right answer, since no watcher can be on a dropped table.
- `sqlCommitDurability` now receives `Map.keys()` (a one-shot iterator) but calls the lookup afresh per collection id, so nothing iterates it twice.

**Reviewer questions from the handoff.**
- Announce after the listeners, synchronously in `onQueueStatus`: kept. Quereus dispatches watcher handlers asynchronously, so every synchronous listener has already run, and the application hears why before a watcher re-queries — which is the ordering docs/offline-sync.md now states.
- The vtab's log line no longer distinguishing "threw" from "failed": acceptable — both are the same isolated failure, and the error text is logged either way.
- `tablesOf` returning the bridge's live `ReadonlyMap`: acceptable — the only outside caller (`OfflineMode.tablesBehind`) iterates it synchronously and copies into its own map.

**DRY / modularity.** A `failed` status computes its tables twice (once for `changedTables` in `translate`, once for the announced pairs). Left as is: it is two cheap lookups, and folding them would make `translate` side-effecting or thread a map through a function that serves every status kind. No other duplication; the shared helper removed the vtab's copy of the same try/catch.

**Type safety.** The table pair now travels as `QualifiedTableName` end to end; no `any` or casts were added. Nothing found.

**Resource cleanup / error handling.** Announcements are fire-and-forget with a logged failure path; nothing is held. Nothing found.

**Performance.** One `notifyExternalChange` per table per failed entry; Quereus makes it a no-op when no watcher matches. Nothing found.

**Out of scope, not filed.** `notifyExternalChange` drives watchers only, not materialized-view maintenance; that holds equally for the existing remote-commit announcement, so it is not new with this ticket and has no single site here to tripwire.

**Tests.** All four cases kept: each pins a distinct path the ticket named (refusal found by a reader's refresh with the cascade and the watcher; refusal found by the submission's own refresh; the replay arm of `restorePending` across a head commit, which needs the second queued entry; the replay arm after a refused segment was dropped). The implementer's mutation checks showed the first fails without the announcement and the rollback cases fail without the replay arm. No test added or cut.
