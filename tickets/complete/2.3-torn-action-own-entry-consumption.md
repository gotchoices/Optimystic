# Complete: torn action, part 2 of 3 — consume your own committed log entry (db-core)

## What was wrong

`NetworkTransactor.commit` commits the collection header and log tail BEFORE sweeping the
remaining blocks. If a later sweep block comes back as a confirmed conflict, commit returns a
failure — correct, because acknowledging a torn action would be worse — but the header and tail
are already durable, so the collection's log already carries this action's entry.

The writer's retry called `Collection.updateInternal`, whose entry loop only ran pending actions
through `doFilterConflict` (default: keep everything) and replayed the lot, re-appending content
the committed tail already held: **the same action recorded twice in the log.**

## What shipped

- `updateInternal` takes an optional `inFlightActionId`. `syncInternal`'s retry path passes the
  actionId minted for the attempt; `update()` and `updateAndSync()` still call it with no
  argument, so their behavior is unchanged.
- An entry whose `actionId` matches is **consumed** — its actions are sliced off the head of
  `pending` and `mutated` is set unconditionally (including for a zero-action entry). `mutated`
  drives `replayActions()`, which resets the tracker and re-stages only what remains; that reset
  is what drops the consumed action's staged transforms, turns `hasUnsyncedChanges()` false, and
  lets the sync loop exit reporting success — the honest answer, because the action IS durable.
- Everything else in the loop is untouched: `sourceCache.clear(entry.blockIds)` still runs for
  the consumed entry, invalidation handling is unchanged, and `advanceContext` still runs before
  the replay.

## Review findings

Reviewed the implement diff (`7a340154`) against the current tree before reading the handoff.
Traced `getFrom`'s revision exclusivity, `addActions`'s snapshot semantics, `replayActions`,
`hasUnsyncedChanges`, `TransactorSource.transact`'s cancel-on-failure, and the coordinator's
commit/retry classification.

### Correctness — the core change holds up

Checked and found sound, so nothing was filed against it:

- **The `slice(entry.actions.length)` prefix correspondence is real.** `addActions` is called
  with a fresh `[...this.pending]` snapshot on every loop iteration, and `act()` shares the
  collection latch with `syncInternal`, so `pending` cannot grow between the append and the
  refresh. Verified across the multi-retry case: an earlier retry that ran the conflict filter
  and shortened `pending` still re-snapshots before the next `addActions`, so the entry always
  describes the current head of `pending`.
- **A rival entry cannot precede the own entry in the same refresh.** `Log.getFrom(startRev)` is
  exclusive (`entry.rev > startRev`), and the own entry's revision is `context.rev + 1`, so any
  rival that could reorder ahead of it is already below the cutoff. The consume-then-filter
  interleave the code relies on is therefore the only reachable order.
- **The action id cannot false-match.** `syncInternal` mints 16 random bytes per `sync()` call;
  a previous *successful* batch under the same id sits at or below the context revision and is
  excluded by the same exclusivity rule, so it cannot be re-consumed and drop uncommitted work.
- **Checkpoint and invalidation entries cannot trip the branch.** `getFrom` only emits
  `entry.action`, so `entry.actionId` is always present on an entry that reaches the comparison,
  and the `inFlightActionId !== undefined` guard rules out an `undefined === undefined` match.

  under 18 lines of comment, inside a `let after; let mutated;` declare-then-assign shape that
  made the loop body hard to read at a glance. Extracted `consumeOwnEntry` and
  `filterAgainstEntry` — each returns `{ after, mutated }`, each carries its own doc comment
  (including the pre-existing tripwire notes, moved verbatim), and the loop body is now three
  lines. No behavior change.
- **`updateInternal`'s `@param` doc pointed at "the entry loop below" for the *why*.** Folded the

  where the parameter is declared.
- **Test coverage gaps the implementer flagged, now closed.** Added two cases: a **multi-action
  entry** (three staged actions committed as one batch — the case where an off-by-one in the
  slice would either duplicate or silently lose an action; nothing covered a slice length > 1),
  and a **zero-action entry** (a brand-new collection's first sync, whose header/root blocks live

### Major — filed

- **`tickets/fix/2.7-refresh-must-always-know-its-own-in-flight-action.md`.**
  `TransactionCoordinator.commit`'s retry loop refreshes every registered collection with a plain
  `collection.update()` — no in-flight id — so a torn action committed through the coordinator
  still replays into a duplicate entry. Traced end to end: `commitOnceLatched` appends under
  `transaction.id`; `commitCollection` maps the torn commit's returned failure to `stale: true`;
  `commitPhase` reports a clean `staleLoss` with nothing in `committedCollections`; the retry
  restores pending, refreshes uninformed, and re-appends. The result is two log entries carrying
  one action id at two revisions, which also makes the action-id→revision relation ambiguous for
  `getActionContext`'s `committed` list, `findInvalidation`, and the invalidation cascade.
  `repro: static` — traced, not run; the ticket names the test that would confirm it.

  Filed at the **representation** rung rather than as a point fix: the defect is that
  `updateInternal` can only know its own in-flight write if a caller remembers to pass it, so
  the ticket asks for the collection to own that fact for the duration of a commit attempt
  (`update()`/`updateAndSync()` then need no change and become correct by construction, and a
  future third write path inherits the fix). Site-claim grep over the whole board found no open
  ticket on this — `debt-coordinator-execute-and-multi-collection-latch-span-untested` touches
  `coordinator.ts` but is about latch-span test coverage, and part 3
  (`2.6-torn-action-cleanup-and-mesh-validation`) does not include the coordinator path. No
  accepted-tradeoff `NOTE:` at either site.

### Tripwires — parked, not filed

- The `slice` correspondence resting on the shared collection latch, and failing silently if a
  path is ever added that stages actions outside it, is recorded as a `NOTE:` on
  `Collection.consumeOwnEntry`'s doc comment (carried over from the implement pass; it moved with
  the code into the helper, and now names the assertion to add and the sibling note in
  `syncInternal` that shares the invariant).

### Not covered — stated deliberately

- **The refresh that walks [own entry, rival entry] in one pass** is exercised only in the
  degenerate order (own entry alone, or foreign entry alone). A deterministic two-writer version
  was attempted and abandoned: `sync()` and `updateAndSync()` take the same collection latch, so
  a rival driven from the same process serializes behind the sync under test rather than
  interleaving with it, which makes the test assert nothing it does not already assert. The
  interleave is covered by reasoning above (the rival can only land *after* the own entry), and
  part 3's mesh spec drives real concurrent writers.
- **Real-ordering coverage.** The spec injects the failure via a `DelegatingTransactor` wrapper
  rather than driving a `NetworkTransactor` sweep where a late block genuinely conflicts. That is
  explicitly part 3's scope (`2.6-torn-action-cleanup-and-mesh-validation`), which owns the mesh
  spec and the `network-transactor` dead-clause cleanup.
