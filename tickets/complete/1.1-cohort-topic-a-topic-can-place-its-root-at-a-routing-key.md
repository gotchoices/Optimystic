# Cohort-topic: a topic can place its root at a routing key — complete

First of three tickets for the decision recorded in `docs/reactivity.md` § Origination point. This one is the transport-free half in db-core: a topic may name a **root key** (raw bytes, for reactivity the routing key of the collection's log tail block), its tier-0 coordinate is then `H(rootKey)` instead of `H(0x00 ‖ topicId)`, and the root's signature threshold is `ceil(members × quorumRatio)` from the verifying node's own configuration instead of the node-wide `minSigs`. Every change is behind an optional field or argument; nothing produces the new fields until the host ticket (`cohort-topic-host-serves-a-root-at-a-storage-group`) and the reactivity ticket (`reactivity-notifications-need-the-tail-cohort-to-be-the-topic-cohort`) land.

## What landed (implement commit `ticket(implement): cohort-topic-a-topic-can-place-its-root-at-a-routing-key`)

- **Addressing**: `TierAddressing.rootCoord(rootKey)` = `H(rootKey)`; `coord(d, P, topicId, rootKey?)` dispatches to it at tier 0 and ignores the key above it.
- **Wire**: `RegisterV1.rootKey?` and `ChildLinkV1.rootKey?` (base64url, 1 to 256 decoded bytes); `SignRequestV1.rootPlaced?` and `CohortGossipV1.rootPlaced?` (literally `true` when present). The register, child-link and gossip signing images cover the new field only when it is present, so a frame without one signs the bytes it always signed.
- **Ports**: optional `ITopicRouter.routeToRoot`; `RootPlacement` and `MembershipLookupOptions`; optional placement arguments on `IMembershipSource.current` and `fetch` and on `IMembershipTrustAnchor.directAnchor`.
- **Threshold rule**: `createRootPlacement` (rejects a ratio outside `(0, 1]`) and `rootPlacedMinSigs` (`max(1, ceil(members × ratio))`, the same expression a storage group's commit certificate uses).
- **Walk and service**: the walk stamps the key on every tier's frame and routes the root step through `routeToRoot` when the router has it; `RegisterRequest.rootKey`, `lookup(topicId, tier, rootKey?)`, the renewal re-walk keeps the key, `CohortHint.rootKey` reports it.
- **Verifier**: a placement replaces `minSigs` in all three threshold checks at that coord, is handed to the source and the anchor, and each cached cert remembers the rule it was validated under so a call under another rule re-validates from the source and never displaces a trust lock.
- **Docs**: `docs/cohort-topic.md` § Root placement at a routing key, the threshold wording under § Membership fetch, and the three wire-format blocks.

## Review findings

**What was checked.** The whole implement diff was read before the handoff summary, then each claim it leans on was traced to its source: FRET's key hash (`p2p-fret`'s `src/ring/hash.ts` is SHA-256 of the key bytes, so `rootCoord` equals the storage position as a coordinate), `CohortSigner.verifyThreshold` (signers must be a distinct subset of the cert passed in, which settles the rotation-chain question below), the cert validator (it does not require a non-empty member list, so the floor of 1 in `rootPlacedMinSigs` is live), every db-p2p implementer of the widened ports (all compile unchanged: the new arguments are optional), and the other documents that list the router port (`docs/internals.md`, `docs/architecture.md`; neither enumerates methods, so neither needed a change). The three new specs were read as code under review. Run: `yarn lint`, `yarn lint:docs`, `yarn build`, `yarn workspace @optimystic/db-core test` (1851 passing), `yarn workspace @optimystic/db-p2p test` (3179 passing, 64 pending, the env-gated specs). Not run, for the implementer's reasons: `yarn test:integration` (nothing here changes a frame it sends), `yarn typecheck`, `yarn check:rn`.

**Major finding, pre-existing, filed.** The FRET binding of `ITopicRouter.routeAndAct` (`FretTopicRouter` in `packages/db-p2p/src/cohort-topic/topic-router.ts`) hands the db-core coordinate to FRET's `routeAct`, which hashes whatever key it is given, so a frame for `coord_d` lands on the machines nearest `H(coord_d)`. The host, the trust anchor and the reactivity origination gate all assemble the cohort around `coord_d` itself. The two agree only on a ring no wider than one cohort, which is every ring the suites build (the host's fake FRET assembles around the unhashed key, so it cannot see this). This predates the ticket and is not specific to root placement, but it falsifies the handoff's "a router without `routeToRoot` gets the same frame at `H(rootKey)`": through the real binding that fallback lands at `H(H(rootKey))`. Filed as `tickets/backlog/bug-cohort-topic-router-hashes-a-coordinate-as-a-key` with the recommended fix (hand FRET the coordinate's preimage, which for a root-placed topic is the root key itself) and the rejected alternative. The site-claim grep found `topic-router.ts` already claimed by the host ticket, so a cross-reference arm was appended to that ticket's edge cases as well, telling the implementer of `routeToRoot` not to build it on `routeAndAct`; the separate backlog ticket stands because its root cause (every tier, every topic) is not the host ticket's. Recorded at the site as a `NOTE:` on `routeToTier` in `packages/db-core/src/cohort-topic/walk.ts` and as a clause in the doc subsection.

**Minor findings, fixed in this pass.**

- The conditional-append helper existed twice (`presentOnly` in `wire/payloads.ts`, an inline copy in `sig/payloads.ts`). Exported the one and reused it.
- `b64urlFixedLen` duplicated `b64urlBoundedLen`'s decode-and-check; it now delegates, with the bounded message reading "exactly N" when the bounds coincide. No test pinned the text.
- The trust-lock guard `lockedUnderAnotherRule` was not exercised (the handoff said so). The second half of the membership spec's cache-rule test now gives the placement call a source that offers a passing group cert while a self-published default-rule cert is held: the placement call verifies, the default call still answers from the lock without a source read, and a second placement call reads the source again, which is the guard's contract.
- `cohortGossipSigningPayload` covering `rootPlaced` was untested; one small spec pins that the flag is one extra trailing element, present only when set, and survives the decode round-trip.

**Confirmed as implemented, no change.**

- Rotation-chain threshold counted over the predecessor cert's members: correct, and the only consistent choice, since `verifyThreshold` checks the rotation signers against the predecessor's member list; counting over the successor would let a shrunk group pass on the old group's count.
- `rootPlacedMinSigs` floors at 1: not dead code, since the wire validator admits an empty member list.
- `CohortHint.rootKey` set by conditional spread: kept; it keeps existing deep-equality assertions on hints valid and matches how the other optional fields are built.
- The walk's root fallback passing the default `wantK` and `minSigs`: covered by the `NOTE:` above and the backlog ticket; the real binding supplies `routeToRoot`.
- The implementer's three specs: all pin real behaviour (exact signed images, the threshold arithmetic, the router dispatch) rather than restating the implementation. None cut.

**Tripwires recorded.**

- `NOTE:` on `SignRequestV1.rootPlaced` in `packages/db-core/src/cohort-topic/wire/types.ts`: the "a forged flag gains nothing" argument rests on `clusterSize` (default 10) staying below `DEFAULT_MIN_SIGS` (14); sign the request before raising `clusterSize` that far.
- `NOTE:` on `routeToTier` in `packages/db-core/src/cohort-topic/walk.ts`: the fallback's landing position through the FRET binding, see the major finding.
- The implementer's `NOTE:` on `lockedUnderAnotherRule` (two rules at one coord cost a source read per call) stands.

**Carried forward from the implement pass.** The pre-existing verifier defect filed as `tickets/fix/membership-verifier-accepts-a-certificate-for-another-coordinate` (a fetched cert is never checked to be for the coordinate being verified) was re-read and is a genuine, separate hole; its fix is not part of this ticket. The two arms the implementer appended to the host ticket (a root key is not bound to its topic id; a root-placed engine must cache its own cert under the placement) remain, with the third arm added by this review.

**Empty categories.** No regression surfaced: both suites pass and no existing test changed meaning. No pre-existing test failure was seen, so `tickets/.pre-existing-error.md` was not written. No `blocked/` ticket was needed: the hashing finding has a documented intent to resolve it against (the `RingHash` contract), so it is settled shape with open timing, which is backlog.
