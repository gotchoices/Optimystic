# A table declares its profile, and the engine classifies each statement

Second of four implement tickets from the plan `a-transaction-carries-its-lane`. Landed in `ticket(implement): a-table-declares-its-profile-and-the-engine-classifies-each-statement`, with the review fixes below. No admission rule changed: the lane is computed per statement, folded per transaction, carried on every commit route, and nothing admits, refuses or merges by it.

## What shipped

- **Two tags** (`declared-tags.ts`, which now holds all five declared-hint tags and their readers, shared by the vtab and the rule): `optimystic.profile`, read `=== 'replay-permitted'`, every other value `strong`; `optimystic.merge` on a column, read `=== 'last-writer-wins'`, every other value no merge. An unrecognised value is logged once per table or column and never refused. Both were already part of the schema hash through the DDL text `schema()` renders.
- **The rule** (`lane.ts`), in two layers for the next ticket's member-side check: `laneCeilingOf` (profile, constraints, selection shape, merge tags, operation, upsert `do update`) and `laneOf` (the ceiling narrowed by reads, self-independence and whether an INSERT's key can collide). `transactionLaneOf` folds the recorded facts, `serializable` on an undescribed write or none.
- **Recording and the four routes.** `noteWriteDescription(write, table)` records a `lane` fact beside the statement's `statement` fact, once per description object, truncated with it on a savepoint rollback. `TransactionBridge.openLane` folds once at commit and hands the value to the session commit, the legacy batch transaction, each flush of the per-tree sweep (`Tree.sync(options)` in db-core now takes `SyncOptions`), and the offline queue's entry.
- **A tag change under queued entries** is logged (`offline:profile-changed-with-entries-queued`, naming the transactions through the new `OfflineMode.queuedTransactionsOf`); each entry keeps the lane fixed at enqueue.
- **Three deviations from the ticket text**, all kept: the tag constants live in `schema/declared-tags.ts` rather than the vtab module (the rule reads them too, and the vtab imports the rule, so constants in the vtab would make an import cycle); the content-key exemption sits in the writer-only clause, since a key-moving UPDATE on a content-keyed table must stay `serializable`; a composite key is fresh when ANY key column is, the rule the offline outlook already applies.

## Review findings

**Read first:** the implement diff, then the handoff. Checked the rule's inputs against Quereus's `TableWrite` contract in the sibling checkout (which constraints a write lists per operation, when `primary-key` appears on an UPDATE, how a `rows` selection is keyed, that `WrittenColumn.column` is lowercased), every caller of the four changed signatures, the test doubles implementing `DirtyTree`, the fold's empty and undescribed arms, the tag overlay on `table_modified`, the once-per-object recording, each commit route's hand-off, and every doc the change touched and the one it should have. Ran `yarn build`, `yarn typecheck`, `yarn lint`, `yarn lint:docs` and the plugin suite (1199 passing after the fixes, 14 pending, smoke ok).

**Found and fixed inline:**

- **A `rows` selection keyed by a UNIQUE key classified `convergent`.** Quereus keys a `rows` selection on the primary key when the predicate covers it and otherwise on the first covered UNIQUE key (`chooseRowKey` in `@quereus/quereus/src/planner/analysis/binding-extractor.ts`), and the ceiling tested only for `global`. So `update u set body = :v where Email = :e` on a replay-permitted table with `body` merge-tagged was `convergent` at both layers, although which row a unique value names is other writers' state, exactly what the clause exists to exclude. The ceiling now requires the selection's key to be the primary key (`selectedByPrimaryKey` in `lane.ts`; an empty key names no row unless the table's primary key is empty). One row added to `lane.spec.ts`, and the clause reworded in docs/transactions.md.
- **The fold test restated db-core.** The spec's last case called `stricterLane` over two `laneOf` results, pinning a db-core function already pinned there, not the plugin's `transactionLaneOf`. Rewritten to call `transactionLaneOf` over `WriteFact` records, covering the mixed-table fold, the undescribed arm and the empty fold.
- **No test reached the carrier.** The handoff named it: nothing committed through the plugin and read the lane off the entry, and the four routes rested on inspection. `test/lane-on-entry.spec.ts` now commits through the legacy per-tree sweep on the `test` transactor and reads the main collection's newest entry through a fresh handle, as the db-core lane test does: `convergent` for a `StampId()` insert into a replay-permitted table, `serializable` for the same insert into a strong one and for one transaction writing both. One contract, two cases.
- **docs/crdt-sync.md §Stage 5 did not say what had landed.** The ticket's anchor describes the per-collection profile as future work; Stage 1 carries a "Landed" paragraph and Stage 5 carried nothing from either lane ticket. Added a paragraph naming the lane, the two declarations (`CollectionInitOptions.merge` for a bare collection, the two tags for a SQL table), the rule's section in docs/transactions.md, and that nothing admits by the lane yet.

**Considered and left as is:**

- The three deviations above: each is the stricter or the already-established reading, and the handoff records the reasoning.
- `offline:profile-changed-with-entries-queued` fires for a merge-tag change too; the name is the docs' name and the message says what is kept. Not worth a second log line.
- `logUnrecognisedLaneTags` remembers a column once, so a column whose tag moves from one unrecognised value to another is not logged again. Fail-safe either way; a `NOTE:` would say more than the behaviour is worth.
- `stricterLane([])` answering `serializable` is what makes an empty fold safe; the new fold test pins the plugin's reliance on it.

**Major findings:** none. **Tickets filed:** none. **Tripwires added:** none beyond the three the implementer placed at the rule (tombstone merge for deletes, a `'counter'` merge kind, index-tree merging), which are the right shape and sit at the right site.

**Not run:** `yarn test:integration`, `yarn check:rn` and the db-core, db-p2p and upgrade-check suites. The review changed one plugin source file, two plugin specs and two docs; the db-core change in the implement commit is one optional parameter on `Tree.sync`, which the plugin suite exercises on every legacy commit.
