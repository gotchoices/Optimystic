# FilePieceStore imports and exports files

`FilePieceStore` declares `implements IPieceStore, IPieceStoreFiles` and carries the two calls the optional capability names (`packages/db-p2p/src/blob/piece-store.ts`). The file cases of `runPieceStoreConformance` now run against this store — ten cases, none of them skipped — so a Node host that asks for `blobs.paths` gets a working `node.blobs.paths`.

## What was built

**The write half of `put` is shared.** `put` validates the id into a `PieceLocation` before `open()`, then hands off to a private `storePiece(location, id, bytes)` holding what `put` used to do inline: write nothing when the piece is there, otherwise temp → sync → rename into the fan directory, then mark the directory dirty. `storeLeaf(bytes)` is the import's one-leaf wrapper: SHA-256 with `node:crypto`, id with db-core's `rawPieceIdOfDigest`, then `storePiece`. No piece-writing behaviour changed.

**`importFile(path, pieceSize)`** opens a read handle and loops: fill one `pieceSize` buffer, store that leaf, stop when the fill came up short. `readFully` keeps reading until the buffer is full or the file ends, because a single `read` may answer fewer bytes than asked for without being at the end, and a leaf cut short there would be a different blob from the one a stream put of the same bytes gives. An empty file yields one zero-length leaf; a file whose length is a multiple of the piece size ends on a fill of 0 with its leaves already stored. Returns `{ id, size }[]` in file order. A `pieceSize` that is not a whole number above zero is a `RangeError`.

**`exportFile(ids, path)`** turns every id into a piece path first, then opens `.<basename>.<16 hex>.tmp` beside the resolved target with `wx`, copies each piece into it through one 256 KiB buffer (`copyPieceInto` → `readFully` and a local `writeAll`), syncs, closes, renames over the target, and syncs the holding directory with `fsyncDir` (a no-op on win32, as everywhere in this package). Any failure — a missing piece's ENOENT included — closes the handle, removes the temp and rejects, so the target is untouched.

**Buffers are `Uint8Array`, not `Buffer`.** eslint's `no-restricted-globals` bans that global in `packages/*/src/**` (absent under React Native's engine) and `fs` reads and writes any typed array, so plain `Uint8Array`s are used throughout.

## Review findings

Read the implement diff (`ticket(implement): file-piece-store-imports-and-exports-files`) before the handoff summary, then the capability contract (`IPieceStoreFiles` and `offersFiles` in `packages/db-p2p/src/blob/piece-store.ts`), the file cases of `runPieceStoreConformance`, and the service that calls both halves (`LocalBlobService.putFile`, `importLeaves`, `readToFile`, `assertImportedLeaves`).

- **Correctness, the import loop.** Sound. Traced all three exits by hand against the five conformance lengths rather than trusting the green suite: 0 bytes takes the `leaves.length > 0` guard's false arm and stores one empty leaf; 1000 bytes breaks on `filled < pieceSize`; 262144 stores a full leaf, continues, and breaks on the next fill of 0; 262145 and 786437 end on a short leaf. The `filled === 0 && leaves.length > 0` guard is what separates the exact-multiple end from the empty file, and it is correct in both directions. `readFully`'s short-read loop is the right fix for the one way this cut could silently disagree with a stream put's.
- **Correctness, the export.** Sound. A failure at any step closes the handle (a second close on an already-closed handle resolves, so the rename's failure takes the same path), removes the temp and rethrows; `fsyncDir` swallows every error by design, so the post-rename sync cannot fail an export that succeeded. A piece whose length is an exact multiple of the 256 KiB chunk costs one extra zero-byte read and returns. A zero-length piece copies nothing.
- **Buffer aliasing, checked and sound.** `storeLeaf(buffer.subarray(0, filled))` hands a view of the import's single buffer down to `handle.writeFile`. It is safe only because `storeLeaf` is fully awaited before the next `readFully` refills that buffer, which is what the `put` contract's "the caller may modify `bytes` once the call has resolved" allows. Recorded here rather than as another comment: the parked tripwire that proposes overlapping the read and the write already says a *second* buffer, which is the thing that keeps this true.
- **Defect found and fixed: the package's own README never learned about the capability.** `packages/db-p2p-storage-fs/README.md` is the document a host integrating this package reads, and it still described a store that only puts and gets: the `FilePieceStore` bullet named `IPieceStore` alone, the `## Piece store` section described only the put path, its log-line list was missing all six new `pieces:file` names (while `docs/debugging.md` had been updated — the two had drifted apart), and the test-coverage list named neither the conformance file cases nor the new multi-chunk export case. All four fixed.
- **Comment stating a false reason, fixed.** The new `writeAll`'s comment said it was not shared with `file-write-log.ts`'s copy "because exporting it would widen this package's API". That is not the alternative: an internal module `index.ts` does not re-export would share it and change no public API. The real situation is that this package keeps these one-loop filesystem primitives per module — two copies of `writeAll`, and the ENOENT-tolerant unlink in `file-write-log.ts`, `store-lock.ts` and `file-piece-store.ts` — and all of those but one predate this ticket. The comment now says that, with a `NOTE:` that a fourth caller should move the set into such a module rather than add a fifth copy. Not refactored here: the fix is a package-wide change reaching into the write-ahead log module, which is not this ticket's review to make.
- **Test added for a contract claimed in prose and verified nowhere.** The new code's path-safety ordering — ids become paths before `open()` and before any temp exists, so a refused id creates neither a store directory nor a file beside the caller's target — was asserted for `put` and `get` only. One line added to the existing "refuses an id that is not a lowercase base32 CID" case covers `exportFile` under the `readdir` check already there. An edit moving `open()` above the id mapping, or validating inside the copy loop, would leave a temp next to the caller's file and no test would have noticed.
- **Tests under review.** Nothing cut. The implementer's one hand-written case (a 1 MiB piece exported) is the only exercise of `copyPieceInto`'s loop running more than once per piece, since every conformance export joins 256 KiB pieces and the chunk is 256 KiB; it stays. No test was added for the `pieceSize` `RangeError`: nothing in the system calls `importFile` with anything but `BLOB_PIECE_BYTES`, and the guard is one unbranching condition.
- **The gap the implementer flagged: no end-to-end case over `LocalBlobService`.** Agreed, and still none. `packages/db-p2p/test/blob-paths.spec.ts` pins the service's half against its own in-process double and the conformance cases pin this store's half; what lies between them is `offersFiles` answering true, which `implements IPieceStoreFiles` makes a build error to break. A case there would re-run both halves through a slower path to prove a type.
- **False-green risk considered and dismissed.** The conformance file cases `this.skip()` when a store does not answer `offersFiles`, so a renamed method would turn ten assertions into ten silent skips. `implements IPieceStoreFiles` on the class makes that a compile error instead. Confirmed by running the spec with the `spec` reporter: all ten report as passing, none as pending.
- **Service contract.** `assertImportedLeaves` refuses an import that reports no pieces ("even an empty file has one") and checks each leaf's size against its position, which is exactly the cut this store makes; `readToFile` passes the whole id list, which `exportFile` takes. No mismatch.
- **Hygiene, types, errors, resources.** `file-piece-store.ts` is 489 lines, in line with the package (`file-batch-backend.ts` 577, `file-write-log.ts` 1081) and decomposed into small functions. Every swallowed error logs, per the project rule. No `any`, no non-null assertion added. Every handle is closed in a `finally` or on both arms of a `try`/`catch`. One 256 KiB buffer per export and one `pieceSize` buffer per import, reused across pieces.
- **Tripwire recorded.** An export's temp must sit beside the caller's target for the rename to be atomic, which makes it the one temp this store writes outside `incoming/` and the only one no later open sweeps up: a process killed between the open and the rename leaves `.<target name>.<hex>.tmp` next to the target indefinitely. Parked in the README's `## Piece store` section, where someone debugging a stray dotfile will look, rather than at the code site.
- **Considered and not parked.** A target whose name is within about 21 characters of the filesystem's 255-byte limit makes the temp name too long, so an export can refuse a target a direct write would accept. Too narrow to spend a comment on; nothing in this repository builds names near that length.
- **The three tripwires the implementer parked** (win32 rename EPERM while another handle holds the target; the non-overlapped read and write; a file another writer changes under an import) were re-read against the code and all three still describe it. Left as they are; the win32 one is the only one with a plausible trigger and its stated remedy — a bounded retry — is the right one.
- **Tickets filed: none.** No defect in the new code survived examination, and the one class-level observation (per-module copies of the filesystem primitives) is nine parts pre-existing and does not name an invariant that would prevent a class of bugs, so it is below the filing bar and lives at the site as a `NOTE:`.
