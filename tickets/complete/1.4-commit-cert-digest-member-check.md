# Complete: commit content-digest check on the member side

## What shipped

`CommitRequest.blockDigests` — the transaction author's per-block declaration of what each block will
contain once the action commits — is now **checked** by cohort members instead of riding along inert.

- **`StorageRepo.previewCommitDigest(blockId, actionId, rev)`** returns
  `CommitDigestPreview = { digest?, baseRev?, baseIndependent }`: what this node's own pended
  transform would materialize, and the base revision it was computed against. It mirrors
  `internalCommit`'s read sequence so prediction and commit cannot drift, and is strictly read-only —
  no durable writes, no commit latch, base and transform both cloned before `applyTransform`.
- **`ClusterMember.validateCommitOperations(record)`** runs on the **promise** round, chained after
  `validatePendOperations` in `evaluatePromise`. A disagreement rejects the whole record with the
  exported reason `CONTENT_DIGEST_MISMATCH = 'content-digest-mismatch'`, which is folded into the
  signed vote payload.

The checkable/abstain rule is keyed on the member's own pended transform, never on the declaration:
a transform carrying an `insert` is base-independent and always checked (the declared `baseRev` is
ignored); an update-only transform is checked only when the member's local `latest.rev` equals the
declared `baseRev`; everything else abstains — meaning it votes exactly as it would have before the
check existed. A hostile declarer can therefore neither force a check nor dodge one.

## Review findings

### Verified independently (no change needed)

- **Promise-round placement is correct and load-bearing.** Read `getTransactionPhase` directly: the
  commit-round branch is explicitly blind to this member's own promise vote ("the rest of the cohort
  reaching super-majority is the commit rule"), so a member that rejected still signs the commit.
  Promise approvals really are the only votes that can carry "I checked this content". Moving the
  check to the commit round would make it decorative, as the implementer claimed.
- **No false-reject path found for honest commits.** Traced the producer side end to end
  (`Collection.sync` / `Coordinator.commitCollection` → `computeBlockContentDigests` →
  `Tracker.peekMaterialized` → `CacheSource.peek`/`getCachedRevision`) against the member side.
  `CacheSource.transformCache` is only ever called *after* a successful commit, so a cached base at
  revision R is committed content at R, matching what a caught-up member materializes at R.
  `TransactorSource` records `materializedRev` (not `state.latest.rev`) as the read revision, so a
  revision-pinned read declares an older `baseRev` and the member simply abstains rather than
  rejecting. The tracker is reset only after commit, so the transforms digested at commit time are
  the ones that were pended.
- **The tombstone `state: {}` contract the implementer flagged is intended, not a gap.** The
  `!blockRev` branch at `storage-repo.ts:356` documents it: a tombstoned block is an *authoritative*
  absent and deliberately stays unflagged. One observable consequence, checked and benign: the
  cluster-side stale-revision pre-check in `validatePendOperations` reads `state.latest.rev` and so
  cannot fire for a tombstoned block — but `StorageRepo.pend` reads `getLatest()` directly and still
  refuses, so this degrades to a later refusal, never a wrong commit. No ticket.
- **Deletes are unforgeable as claimed.** A committed delete materializes nothing, so a hostile
  declaration for a deleted block has no content to forge; the member abstains and nothing is lost.
- **The single-peer fast path really is unchecked**, and correctly so: `CoordinatorRepo.commit`
  short-circuits to `storageRepo.commit` when `peerCount <= 1`, so there is no promise round to check
  on. Acceptable — a lone node cannot be defended from itself.
- **Duck-typed probe reaches the real repo today.** Both production constructions
  (`libp2p-node-base.ts:804`, `testing/mesh-harness.ts:371`) pass a concrete `StorageRepo`.

### Found and fixed in this pass

- **A malformed declaration threw a `TypeError` out of the vote path.** `blockDigests` is untrusted
  wire data and nothing validates its shape on ingress (no schema layer exists in `db-p2p`), so a
  commit carrying `blockDigests: { "<real-block-id>": null }` made a *checkable* member read
  `declared.digest` off `null` and throw out of `handlePromiseNeeded`, which has no try/catch. The
  member would then fail to vote at all rather than voting either way — remotely triggerable, and
  reachable from an honest coordinator forwarding a garbled client request too. Now guarded: an entry
  whose `digest` is not a string, or whose `baseRev` is not a number, is treated as an omitted
  declaration (abstain). Abstain rather than reject, because a garbled request must not look like
  forged content — and malforming a declaration is no better a dodge than omitting it, which already
  abstains. Six new cases cover `null`, `undefined`, a non-object, a missing digest, a non-string
  digest, and a non-numeric `baseRev`.
- **`commit.blockIds.includes(...)` per declared id** was a linear scan inside a linear loop over a
  per-coordinator batch that can be wide. Replaced with one `Set` per commit operation.
- **`evaluatePromise`'s doc comment still described only two of its three stages.** Updated, and it
  now names `content-digest-mismatch` as the third distinct reject signal.
- **The capability seam is now a named contract.** `ICommitDigestPreviewer` is exported from
  `storage-repo.ts` and `StorageRepo` declares `implements` it; the member probes for that type
  instead of an inline structural literal written a second time. This does not stop a decorator from
  silently dropping the method — see the tripwire below — but it gives one definition of the contract
  and something for a wrapper to forward.
- **`docs/repository.md` still read as if nothing checked the declaration.** Its "Declared block
  content" section is the primary doc for `blockDigests` and the change did not touch it. Added a
  "Who checks it" paragraph pointing at the promise-round check and the two deeper docs.
- **`docs/internals.md`'s checkable/abstain table omitted the unmaterializable-base case** that the
  code handles. Folded into the delete row.

### Test gaps found and closed

The implementer's cluster tests all fed **hand-written previews** into a mock repo, and the two tests
against a real `StorageRepo` covered only the *insert* path with a digest computed by calling
`canonicalBlockHash` directly. The update-only path — the one where a producer/member divergence
would cause a **false reject**, and a false reject on a commit tears a multi-block transaction rather
than retrying it — had no test running both real sides. Added three specs that produce the
declaration with the genuine client-side helper (`computeBlockContentDigests` over a real `Tracker`,
exactly as `Collection.sync` and the coordinator's commit phase call it) and check it with the
genuine member-side preview against a real `StorageRepo`: matching update approves, same-`baseRev`
different-ops rejects, and a `baseRev` the member does not hold abstains. Also added multi-block
coverage (mismatch on a *later* declared id still sinks the record; all-match approves) — the
per-record loop had none.

### Recorded as tripwires, not tickets

- **Previews run one block at a time on the promise round.** A commit declaring N blocks adds N
  sequential preview round-trips (each 1-3 block-storage reads plus a `structuredClone` of the base
  and the transform) to this member's vote latency. Unmeasured, and sequencing buys the short-circuit
  on first mismatch. `NOTE:` at the loop in `cluster-repo.ts` says to fan out with `Promise.all` if
  wide commits ever show up as promise latency — and explicitly *not* to sample a subset, since a
  skipped id is an unchecked id.
- **A decorating repo at the member's storage seam would silently disable the check.** `NOTE:` at the
  probe in `validateCommitOperations` says to promote it to a typed component field rather than
  widening the probe, if a non-forwarding wrapper is ever wired there. Conditional today: both
  constructions pass the concrete `StorageRepo`.

### Deliberately out of scope (unchanged, and still true)

- **An approval does not say whether it was a checked approval.** A member that verified content and
  one that abstained emit byte-identical approvals, so the guarantee is "some honest caught-up member
  would have rejected", not "N members vouched for these bytes". Making that countable and durable is
  `persist-block-commit-proof`, which declares this ticket as its prereq.
- **No multi-peer end-to-end test drives a real cohort to a rejected commit.** The cluster spec parks
  the record in the Promising phase with two declared peers so consensus never executes. The
  mesh-harness gap is already tracked by `debt-mesh-harness-policy-and-commit-path-untested`.
- **The latch-free preview has no concurrency test.** The argument — that a torn read degrades to an
  abstain, never a false reject — is documented at the method and holds on inspection (a moved
  `latest` changes `baseRev`, which fails the checkable predicate), but nothing exercises it.
