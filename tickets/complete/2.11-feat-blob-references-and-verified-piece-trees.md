# Verified reading of blob piece trees

The reader side of blobs, network-free, in `packages/db-core/src/blob/`, built by `ticket(implement): feat-blob-references-and-verified-piece-trees`. Everything reaches pieces through an injected `PieceSource` (`blob/pieces.ts`).

- `verify.ts` — `checkPiece` (size first, so an oversized answer is never hashed, then the SHA-256 digest against the CID) and `checkPieceSize` for a `verified` source. The fetcher calls this per received piece.
- `list-piece.ts` — `decodeListPiece`, the only function that interprets dag-pb bytes, with every bound of docs/blobs.md §References and pieces in the specified order; `pieceKind` and `PieceKind`.
- `reader.ts` — `planBlobRange`, `readBlob`, `readBlobSize`, `walkBlobPieces` over one private `PieceLoader` that holds every per-piece rule (presence, digest or size check, decode, declared size, depth bound before any child is requested). Range arguments are validated before any request; descent is lazy and depth first, so nothing past a fault is yielded.
- `docs/blobs.md` — status line, the Verification and Building paragraphs, and the file-system extension section cite the new functions.

Deviations from the plan, all accepted in review: the walk's repeat key includes depth (so the walk and a read agree on `too-deep`); absent list pieces are deduplicated too; one loader class instead of one `loadPiece` function; two extra malformed rows (undecodable UnixFS data, dag-pb with no UnixFS data); a raw root's walk does not judge `offset > size`, as stated on `walkBlobPieces`.

## Review findings

Read the implement diff first, then every touched file and the blob modules it builds on (`blob-ref.ts`, `errors.ts`, `limits.ts`, `pieces.ts`, `digest.ts`), and the plan tickets that consume these functions (`feat-a-node-stores-blob-pieces`, `feat-blob-fetcher-verifies-and-resumes`, `feat-blob-pieces-move-between-machines`).

- **Correctness — one defect found and fixed.** `walkBlobPieces` with an empty range strictly inside the blob (say `offset: 100, length: 0`) walked the path to byte 100 — the first list piece and the first leaf — because the child-intersection test (`childrenIn` in `reader.ts`) treated a zero-width range as intersecting the child it falls inside. The planner and `readBlob` were unaffected (both return before descending on an empty range), so the walk and the planner disagreed on what an empty range needs, and the fetcher, which plans from the walk, would have fetched pieces for a range that needs none. Fixed with an empty-range guard in `childrenIn`; regression test *walks only the root for an empty range inside the blob*. Ranges at the end (`offset === size`) were already correct.
- **Correctness — checked, no further defects.** Order of the `decodeListPiece` checks against the plan; bigint total checked before any conversion to `number`; `offset + length` never summed; depth counting (root 1, `too-deep` at depth 8 naming a list child, judged before any child request and regardless of range); raw root fetched once in `readBlob`; size checks on every non-root data and list piece; RangeError raised before any request for bad arguments; source errors propagate unchanged. The walk's work on a hostile tree is bounded by distinct list pieces × depth expansions (the depth-keyed set), and a read's by declared size × depth (no zero-size children).
- **Test coverage.** Added *is refused through a verified source too, which skips only the hashing*: the plan required showing that a `verified` source still bounds list pieces, and the implementation had shown only that it skips hashing. This is the hostile-input property a future shortcut in `PieceLoader.fetch` would break. Left as inspection, per the handoff, with reason: `readBlobSize` (a one-line wrapper over the root load the other tests exercise), the walk's two edge-cut repeat keys, a throwing source (no branch — the error is simply not caught), and CIDv0 re-spelling (one call to `pieceIdOfCid`, whose behavior is the builder ticket's). No implementer test was cut: each pins a specified behavior or a malformed shape, none restates the implementation or verifies a mock.
- **Type safety, error handling, resource cleanup.** No `any`; reasons are the existing `BlobCorruptReason` union; only library decode calls are caught, each rethrown as a typed fault. Generators hold no resources beyond the source's own.
- **Performance.** `readBlob` over a tree that repeats one list piece fetches and checks it at every occurrence, with no memo; accepted by the plan and bounded by declared size × depth. No tripwire added: the bound is stated in docs/blobs.md and a memo would only matter for hostile or degenerate trees.
- **Source hygiene.** `reader.ts` is 329 lines, `list-piece.ts` 158; functions are small; comments state constraints (why compared rather than summed, why depth is in the repeat key, why zero-size children are refused) rather than narrating.
- **Docs.** docs/blobs.md matches the code after the fix (the walk "lists every piece of a tree, or of the part covering a range" — now true of an empty range). `yarn lint:docs` passes.
- **Tripwires / tickets filed.** None: no conditional concern or major finding beyond the inline fix.
