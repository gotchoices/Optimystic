# A restart no longer turns "I cannot reach my cohort" into "this block does not exist"

## What was wrong

A network-scoped key network admits a remote peer to a cohort only when `membershipOf` classifies it `'serves'` from its protocol list in the libp2p peerStore, which is in memory. After a restart with `createLibp2pNode({ persistence })`, FRET's table was restored but every restored peer had an empty protocol list until it reconnected and identify re-ran, so it read `'unknown'`. The cohort came back self-only, `CoordinatorRepo.fetchBlockFromCluster` took its solo-self exit, and every read of a block this node lacked was served as authoritatively absent (the "why is absent served" half of the sereus re-attach report, optimystic #22).

## What changed

- `Libp2pKeyPeerNetwork.rememberedServing`: remote peer ids last classified `'serves'` from a non-empty protocol list. `membershipOf` updates it from every non-empty list (`'serves'` adds, `'foreign'` removes) and falls back to it for an empty list. Self and the unscoped path are unchanged.
- `PersistedNetworkState.servingPeers?: string[]` (optional, no version bump). `persistState` saves only the remembered ids that are in the FRET table exported beside them; `initFromPersistedState` loads them after the table import.
- A changed verdict schedules a save on the next microtask (`schedulePersist`, coalescing one classification loop). This deliberately deviates from the plan's "saved by the next connection-driven `persistState`": `connection:open` fires before identify fills in protocols, so the first serving verdict comes after the save its connection triggered, and in a two-machine deployment there may be no later one.
- Accepted-tradeoff `NOTE:` at the empty-protocols branch of `membershipOf`: a remembered peer that never returns keeps doubt alive until FRET declares it dead.
- `CoordinatorRepo` unchanged; its existing handling turns the non-self, silent cohort into `'cohort-unreachable'`.
- One regression test at the key-network tier: a network sees `remote` serving and saves the verdict with no connection event; a second network over the same persistence with an empty peerStore restores it and assembles `[remote, self]`.

## Review findings

Read the diff of `ticket(implement): a-restarted-node-forgets-which-peers-serve-its-network` first, then the surrounding code in `libp2p-key-network.ts` (cohort assembly, `filterByMembership`, `findCoordinator`'s connected filter, `persistState`, `initFromPersistedState`, the `connection:open` hook) and the node-base wiring.

- **Correctness of the classification change — checked, sound.** A non-empty list always wins and updates the memory; only positive verdicts are kept; self and the unscoped path are untouched. `filterByMembership` now ranks a remembered disconnected peer as `serves` for coordinator selection too, but `findCoordinator` filters the cohort tier to connected peers before that, and the connected fallback only sees connected peers, so a remembered-but-offline peer is never picked as coordinator. Confirmed by reading.
- **Save timing — checked, sound.** `rememberVerdict` persists only on a change, so steady-state classification writes nothing; the microtask coalescing is correct (the flag is reset before `persistState` runs).
- **Staleness claim in the implement handoff was wrong — parked as a tripwire.** The handoff said a peer that moved to another network "is admitted until it reconnects and identify replaces its protocol list". Identify here is network-namespaced (`identify({ protocolPrefix: 'optimystic/<networkName>' })` in `libp2p-node-base.ts`), so such a peer never completes identify here, never produces a fresh list, and its remembered verdict stands as long as FRET keeps it live. The in-memory peerStore already kept the stale list the same way within one process, so this extends an existing behavior across restarts rather than creating a new one, and peers switching networks under one identity is not an expected operation. Recorded as a `NOTE:` on `rememberedServing` naming the remedy (drop a verdict for a peer that stays connected without identifying).
- **A gracefully stopping partner erasing the verdict — checked, not an issue.** A stopping node unregisters its protocols, but `@libp2p/identify`'s push is debounced 1000 ms and skipped once the service is stopped, so the partner does not push a reduced protocol list that would flip the verdict to `'foreign'` on its way down.
- **A save racing the restore — tripwire, pre-existing, recorded here only.** The key network is built after `node.start()`, and `connection:open` → `persistState` can fire while `initFromPersistedState` awaits `persistence.load()`; a file-backed store could then write the pre-restore state (high-water mark 1, no table, no `servingPeers`) over the snapshot before it is read. This predates the ticket (the high-water mark and FRET table are exposed the same way), and no production `NetworkStatePersistence` implementation exists in this repo yet. If one lands, gate `persistState` until the restore has run.
- **Docs — one missing, fixed.** `packages/db-p2p/docs/cluster.md`'s Network-Membership Scoping bullet said an empty protocol list reads `unknown` with no exception; added the remembered-verdict exception and its persistence. `docs/internals.md`, `packages/db-p2p/readme.md` and the `persistence` option comment were already accurate.
- **Tests — kept as is.** The one added spec reproduces the defect at the lowest layer and pins the save-on-change deviation (it waits for the save with no connection event). No test added in review. No end-to-end restart harness exists, and the FRET half (`importEntries` keeps restored peers, `assembleCohort` returns them) remains read from `../Fret` rather than exercised — noted, not ticketed, since building a restart harness is out of proportion to this change.
- **In-memory growth of `rememberedServing` — tripwire already present** at its declaration; no change.
- **Availability consequence for writes after a restart** (a restarted node with an offline remembered partner runs consensus against it instead of committing solo) — matches the pre-restart behavior this ticket set as the rule, and is covered by the accepted-tradeoff `NOTE:` at `membershipOf`. No action.
- **Type safety, error handling, resource cleanup** — nothing new to clean up (no timers or listeners added; `queueMicrotask` needs none), the save's rejection is still logged by `persistState`, and the loaded ids are typed `string[]` and trusted like the snapshot's other fields. No findings.
- **Validation:** `npx tsc --noEmit -p .` and `eslint` on the touched source clean; `yarn lint:docs` clean; `yarn build` in `packages/db-p2p` re-run; full `yarn test` in `packages/db-p2p`: 3132 passing, 63 pending, 0 failing. Not run: `yarn test:integration` and other workspaces' suites (the change is private to db-p2p's key network apart from an optional field on `PersistedNetworkState`).
