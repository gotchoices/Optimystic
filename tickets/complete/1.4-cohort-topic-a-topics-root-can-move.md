# Cohort-topic: a root-placed topic's root can move

First of three tickets delivering "tiers below the root do not rotate; only the root moves" (maintainer decision, 2026-10-02). A topic keeps one topic id for its whole life while its root key changes. Tiers `d ≥ 1` sit at `coord_d(P, topicId)` and stay put; the root, `H(rootKey)`, becomes a different coordinate after a move. The two dependents, `reactivity-per-root-state-is-keyed-by-the-tail` and `reactivity-topic-is-the-collection-anchor`, use the API added here. No wire field changed.

## What landed (`ticket(implement): cohort-topic-a-topics-root-can-move`)

- **Tree tier on the walk outcome and the handle.** `AcceptedWalkOutcome.treeTier` (walk.ts) and the required field `CohortHint.treeTier` (service.ts). It is set in `hintFromReply`.
- **`CohortTopicService.moveRoot(handle, rootKey)`.** It sends nothing. It changes the mutable root-key slot (`RootKeySlot`) that the renewal's `relookup` reads, and it changes `handle.rootKey`. It throws on a handle registered without a root key. On a stale handle it does nothing (`liveRenewal`, the same identity guard `renew` and `withdraw` use). A registration at the root (`treeTier` 0) has to register again.
- **A displaced registration sends no tombstone.** This is now an accepted-tradeoff `NOTE:` at `startRenewal`. A tombstone would go through `findHolder`, which would point it at the live record.
- **Tier-`d ≥ 1` engines follow the root.** In `reconcilePlacement` (host.ts), a frame naming a different root key replaces the engine's key, with a log line and an accepted-tradeoff `NOTE:`. A root-placed engine still refuses a different key, because that key is its own coordinate's preimage. A frame claiming the other placement rule is still refused.
- **`findHolder` returns the newer record.** It uses `CoordEngine.heldRecord` and `isNewerRegistration`: the later `attachedAt` wins, and a tie goes to the later `lastPing`. There is a `NOTE:` on cross-member clock skew, and a tripwire `NOTE:` that renew dispatch now scans every resident engine.
- **Docs.** In `docs/cohort-topic.md`: the root-placement table note, the "The root can move" paragraph, both implementation notes, a § TTL and renewal bullet, and § Application policies item 6. In `docs/internals.md`: § Service composition.

## Review findings

**Checked, and it holds:**
- *Correctness of the newer-record rule.* `attachedAt` is stamped once, at admission (`accept` in `packages/db-core/src/cohort-topic/member-engine.ts`). These keep it unchanged: the handoff re-stamp (`{ ...rec, primary, backups }` in `registration/handoff.ts`), the renewal touch (`{ ...rec, lastPing }` in `registration/renewal.ts`) and gossip (`toGossipRecord` / `fromGossipRecord` in `gossip/records.ts`). So ordering by `attachedAt` really does mean "registered later". Re-attach and withdraw both go through `resolveRenew` → `findHolder`, so they pick the same record a plain renew does.
- *Parent addressing after a key change.* Every place a tier-1 engine uses its root key reads it when it runs: the `parentCoord` dependency, the cold-start `registerWithParent` closure and `parentRootPlaced`. The register dispatch works out `parentCoord` for each frame from that frame's own key, so it matches what the engine adopts. Nothing captured the key when the engine was created.
- *Tier-`d ≥ 2` frames.* `placementOf` gives them `{ rootPlaced: false, rootKey }`, so they follow the key the same way tier 1 does. The docs say "tier-`d ≥ 1`", which matches.
- *Matchmaking.* It registers without a root key, so the adopt branch never runs for it. Confirmed by reading the code, and the matchmaking suites pass.
- *The root-placed refusal branch* can only be reached by calling `forCoord` directly or by a hash collision. Dispatch and child links derive the root coordinate as `H(rootKey)`, so a different key gives a different coordinate. The branch is defensive. I kept its test half: it pins that the new adopt branch did not spread to root engines.

**Found and fixed in this pass (minor):**
- The `CohortHint.rootKey` doc said "the root key the topic was resolved under". After `moveRoot`, a handle holds the key `moveRoot` last named. For a handle at the root that is a key it has not registered under yet. The doc now says so (`packages/db-core/src/cohort-topic/service.ts`).
- Removed an unused `RingCoord` type import from `service.ts`. It predates this change; the editor flagged it during review.

**Considered and left alone:**
- *`moveRoot` throwing on a handle registered without a root key* (the implementer added this beyond the ticket). Kept. Letting it through would quietly turn a default-addressed registration into a root-placed one on its next re-walk, and an error makes that visible.
- *`holds` kept beside `heldRecord`.* `holds` is a one-line check that `heldRecord` found something, and about 26 spec call sites use it. Collapsing the two would churn tests for no change in behaviour.
- *The tier-1 reconcile test drives `registry.forCoord` directly* rather than going through dispatch. That is acceptable: dispatch only adds the `placementOf` mapping, which is a single expression.

**Tripwires:** no new ones. The three the implementer recorded cover what I saw: the full engine scan in `findHolder`, the clock-skew `NOTE:` at `isNewerRegistration`, and the interleaved old/new key flip at one tier-1 engine (the `reconcilePlacement` `NOTE:`, which points to backlog `feat-reactivity-notifications-reach-child-cohorts`).

**Major findings / tickets filed:** none. One known gap is already tracked: a renewal failover's re-walk throws its outcome away, so `treeTier`, `primary` and `backups` on the handle can go stale after a relookup. That is an arm of backlog `bug-a-participant-told-its-registration-is-unknown-never-registers-again`.

**Tests:** none cut and none added. Each new case covers branching logic and fails against the old code: first-match `findHolder`, the `lastPing` tie-break, adopt versus refuse, and the re-walk naming the moved key. The five fake services' throwing `moveRoot` stubs are interface plumbing.

**Docs:** I read every doc section the change touches, plus the other places `findHolder` and re-walk root reuse are mentioned. They match the new behaviour. `yarn lint:docs` passes.

**Validation (this pass):** `yarn build`, `yarn lint`, `yarn lint:docs` and `yarn typecheck` are clean. `packages/db-core` `yarn test`: 1853 passing. `packages/db-p2p` `yarn test`: 3180 passing, 65 pending. Not run: `yarn test:integration`, `yarn check:rn` and the root `yarn test` fan-out. No wire or storage format changed. The implementer ran the substrate integration spec (13 passing).
