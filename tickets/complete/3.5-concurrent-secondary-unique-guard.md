# Complete: refuse a concurrent insert whose UNIQUE column value a rival already committed

## What the bug was

A secondary UNIQUE constraint (`col … unique`, table-level `unique (a, b)`, `create unique index`) was enforced only by the vtab's pre-stage probe, a range scan of the constraint's index tree read against the writer's own snapshot. Two concurrent writers both probed clear and both committed, leaving two rows a UNIQUE column says cannot coexist. The primary-key guard could not catch this: an index tree keys `frame(indexValue) ‖ frame(primaryKey)`, so two rows sharing a value under different PKs occupy different tree keys inside one framed-value prefix.

## What landed (implement stage)

- **The `absentRange` guard arm (db-core).** `TreeEntryGuard`'s `absentRange` variant is enforced by the tree `replace` handler (`buildInit` in `packages/db-core/src/collections/tree/tree.ts`) on every run, initial staging and every conflict replay. It range-scans the claimed range over the same `Atomic` store the upsert writes to and throws `TreeRangeTakenError` (`struct.ts`) on any entry whose key is not the staging entry's own. That error subclasses `TreeKeyTakenError`, so every existing consumer of a key refusal handles it with no new arm.
- **Guarded staging (plugin).** `IndexManager.insertIndexEntries` and `updateIndexEntries` take an optional set naming the index trees whose entry for this row carries `uniquePrefixGuard(indexKey)`, the same `indexValueRange` prefix `findByIndexIn` seeks. The vtab computes that set in `OptimysticVirtualTable.guardedUniqueIndexes`.
- **Error mapping (bridge).** The vtab registers a per-index `keyTakenMessage` naming the constraint's columns, so a refusal out of an index tree maps to `UNIQUE constraint failed: <table>.<col>`.
- **Legacy commit pre-flight (bridge).** `commitDirtyTreesLegacy` refreshes every staged tree (`tree.update()`) before flushing any, so a refusal whose rival already committed rolls back cleanly instead of tearing the base row from its index mid-sweep. The residual window (a rival landing between the pre-flight and a tree's own flush) is carried by backlog `feat-optimystic-legacy-commit-two-phase`.

## Review findings

### What was checked

- Read the implement diff fresh before the handoff: the guard arm and its self-exclusion, the delete-old-then-insert-new ordering inside one tree action, that `BTree.range` reads only the range's fields (so a guard that round-tripped through the action log scans identically), the `Atomic` whole-action discard on throw, `Collection.update()`'s replay and the boundary-moved `restorePending` path a throwing pre-flight leaves behind, the session-mode path, the bridge's three commit exits, `mapCommitRefusal`, the init ordering of tree opening versus message registration, and every changed test.
- Re-derived both inverted test outcomes. The two-node UNIQUE case now asserting refusal is the ticket's explicit intent (the downstream single-use nonce columns need enforcement); the true-partition residual is unchanged and owned by `feat-phantom-read-protection`. The legacy two-table PK test moving from a torn `PartialCommitError` to a clean rollback is a direct consequence of the pre-flight, and the genuine mid-sweep tear stays covered by the injected-failure test in `legacy-commit-atomicity.spec.ts`.
- Probed the guard's disposition coverage and the staging-time error path with throwaway specs (deleted after use), then turned the confirmed gaps into permanent tests.
- Confirmed no other code constructs `TreeKeyTakenError` (the new optional message parameter is safe), and that the docs the change should have touched were touched.

### Found and fixed inline (minor)

- **IGNORE- and REPLACE-resolved constraints were left unguarded, and both silently admitted a concurrent duplicate.** Verified by repro: `insert or ignore` and `insert or replace` staged before a rival committed the same value under a different PK both committed, leaving two rows under one unique value. The implement rationale ("REPLACE evicts the rival; IGNORE keeps last-writer-wins") does not hold inside an index tree's replay, because the rival's row lives in the main collection, which the replay can neither skip around nor evict. `guardedUniqueIndexes` now guards every binding UNIQUE constraint regardless of action, so the loser is refused and the application retry honours the disposition sequentially, the same call the PK-move guard already made for IGNORE. Two deterministic cases added to `concurrent-secondary-unique-refusal.spec.ts` (refusal, then a retry that swallows or evicts as declared). An accepted-tradeoff `NOTE:` at the site records that a concurrent `insert or replace` loser now sees a UNIQUE error instead of displacing the rival.
- **A staging-time guard refusal surfaced as the raw tree error** (`insert failed: Tree collection … is guarded unique over a key range …`) rather than the SQL message. Found by tightening the two-node test's `/unique/i` assertion to `UNIQUE constraint failed`, which then failed. The guard also runs at initial staging, and on a mesh the tracker it scans can fetch a rival's block the pre-stage probe's view missed, which is exactly what happens in that harness. The vtab's DML catch now maps a `TreeKeyTakenError` through the bridge's `mapCommitRefusal` (made public), and the statement-level savepoint discards what the statement staged before it. The test's comments claimed the refusal fired at commit-time replay; corrected to say it fires at initial staging there.
- The same-PK `insert or replace` branch restaged index entries without the guard set; it now passes `guardedUniqueIndexes(values)` like every other write path.
- `docs/transactions.md`'s legacy-commit section did not mention the pre-flight; added a bullet and reworded the planned narrowing as "beyond the pre-flight". `docs/internals.md` updated for the IGNORE/REPLACE decision and the staging-time mapping.
- Comment accuracy in `tree.ts`: the range guard costs two descents (`findFirst` and `findLast`), not one.

### Found and filed (major, pre-existing)

- **`fix/insert-or-replace-on-pk-skips-secondary-unique`** (repro verified on one handle, no concurrency): `insert or replace` on an existing primary key never resolves secondary UNIQUE constraints, so `insert or replace into T values (1, 'b')` with row 2 already holding `'b'` leaves both rows under one unique value and the index confirms it. The site is the PK-collision REPLACE branch of the INSERT arm in `optimystic-module.ts`, which stages without calling `resolveSecondaryUniqueDecision`. Not this ticket's diff and no open ticket claimed the site.
