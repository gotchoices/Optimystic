Part 4, the last, of stage 6 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages): the Quereus plugin wiring for the node's reachability gate (`KeyNetworkCohortReachability`, `node.cohortReachability`), the queue's solo refusal, and the typed unanswered read that the three prereqs built.

## What landed

- `LateBoundCohortReachability` (`late-bound-reachability.ts`): one stand-in gate per transactor key, handed out by `CollectionFactory.getCohortReachability`. `reachable` asks whichever gate is bound now (always-open until one is); `onChange` listeners follow the subscription to each gate bound later.
- `CollectionFactory.createNetworkTransactor` binds `node.cohortReachability` unless a test or host registered a gate for the key first.
- `OfflineMode` subscribes once per distinct published gate; a wake starts a restore pass when a journaled record is deferred (once no transaction is open), then wakes the queue. Not passed as `wakeOn`, because while the queue is empty no drain iteration would retry the restore. `dispose` releases the subscriptions first.
- `offline.allowSoloCommit` (boolean only) reaches `OfflineQueueOptions.allowSoloCommit`.
- `OptimysticVirtualTable.doInitialize` publishes the offline policy and gate at the start of every full initialization, before any network read, so a table whose initialization fails because its cohort is unreachable still has its gate's wakes reach the controller.

Tests: `test/offline-mode-two-machine.spec.ts` (new, over node A's real gate on the two-node mesh: queued and sent nowhere while B is away, read served locally, drained on the wake with a re-check timer too long to explain it; and `expireAfterMs` while away), a restore-on-wake case in `test/offline-restore.spec.ts`, and the updated registration-refusal case in `test/offline-mode.spec.ts`.

**Checked, no defect found:**

- *Early policy publication (the change the implementer asked to have weighed).* Accepted. The policy comes from the constructor's declaration tags (`offlinePolicy` is reassigned only in the constructor and `followSchemaTags`), and the gate is a factory object, so neither needs the network; moving the publish earlier changes no value published. A refused CREATE still withdraws (the `create` catch calls `withdrawOfflinePolicy`); a failed `connect` leaves the table's real policy published, which is harmless since nothing writes or reads a table that has not initialized. The provisional (read-only) pass still publishes nothing. Repeated publishes on retry are idempotent (`setTablePolicy` overwrites, `subscribeToGate` dedups).
- *Late binding.* `bind` moves the subscription; a bound gate without `onChange` leaves `releaseTarget` unset and a later bind still subscribes; the per-listener unsubscribe is idempotent and releases the target only when the last listener leaves. "Gate registered after a table took the stand-in" is correct by reading; no test added, since the class is small enough that one would restate it.
- *Key agreement.* `registerNodeCohortReachability` and `getCohortReachability` both key by `getTransactorKey(options)`, the key the transactor cache uses, so the node's gate lands on the stand-in the tables hold.
- *Wake vs. existing retries.* A wake's restore pass and the queue-gate's pass (`reachability.reachable` while deferred) join through `OfflineRestore.run`'s pending-pass dedup, so a wake with entries queued does not run two passes.
