# Complete: `plugin.blobs`, `plugin.blobsFor(table)` and the blob SQL functions

Second part of [docs/blobs.md §SQL](../../docs/blobs.md#sql), built by `ticket(implement): feat-blob-sql-type-and-blob-service` and reviewed in this pass. The `blobref` column type already existed; this adds the service an application puts files through, the owner labels pins are held under, and the two SQL functions that read a reference's local state. Nothing here maintains a reference tree, pins on behalf of a commit, or announces — that is `feat-blob-reference-trees-follow-sql-rows`, `feat-blob-pins-follow-sql-commits` and `feat-sql-columns-hold-blob-references`.

## What shipped

**`blob-pin-labels.ts`** — the one place in the plugin a pin's owner label is built or read: the three builders (`transactionReferencePinLabel`, `transactionPutPinLabel`, `unstagedPinLabel`), the two string prefixes plus `transactionPinPrefix(stampId)`, and `parsePinLabel`. Putting the scope in the label is what makes the blob records themselves the durable record of which transaction owes which pin under which scope, so nothing has to be added to the offline journal.

**`CollectionFactory`** — `SqlBlobBackendService` (`BlobService & BlobPinIndex`), `BlobBackend` (`key`, `service`, `transactor`), `getBlobBackend(options)` keyed and de-duplicated in flight exactly as `getOrCreateTransactor` is, and `onBlobBackendResolved(listener)`. A `network` transactor whose node carries `blobs` gets `node.blobs`; everything else gets a `SingleMachineBlobService` over `blobStorageFactory?.()` or memory, started, logged once under the new `optimystic:quereus-plugin:blob` namespace. `dispose()` stops the single-machine services it built; `clearCache()` forgets the backends alongside the transactors.

**`SqlBlobService`** — a thin wrapper over one network's backend, resolved on first use, which defaults `put`'s owner label from the bridge's open transaction (decided when the put starts). `onProgress` / `onDurability` keep their own listener sets and attach one forwarder each once the backend resolves, moving them if a dispose made the factory build a fresh store.

**`OptimysticModule.defaultBindingOptions` / `bindingOptionsOfTable`**, and `OptimysticVirtualTable.bindingOptions` — the lazy binding resolution behind `plugin.blobs` and `plugin.blobsFor(table)`.

**`BlobLocality(ref)` and `BlobSize(ref)`** in `functions/blob-functions.ts`, registered in `register`'s `functions`: local `stat` with no probe, not `DETERMINISTIC`, NULL in gives NULL, a `BlobRefError` rethrown as `QuereusError(…, MISMATCH, error)`.

**`blobStorageFactory`** on `OptimysticOptions` / `ParsedOptimysticOptions`, read in `resolveBinding` out of the registration config only, as `rawStorageFactory` is.

## Review findings

Read the implement diff first, then the handoff. Checked: the happy path (put → insert → read back, and both functions over a blob held here), the edge cases the handoff names (an unknown reference, NULL, both refused arms), the pin-label grammar against the one generator of stamp ids and against every state the bridge can be in, resource cleanup across `dispose` / `shutdown` / `clearCache`, the listener discipline of all three subscriptions (double subscribe, unsubscribe before resolution, re-entrant subscribe during an announce, a backend object that changes under a live listener), the keying of `getBlobBackend` against `getOrCreateTransactor` and `getNodeKey`, the `blobref` column's physical type against what the functions parse, and every document the change touched plus the ones it should have.

**Fixed in this pass.**

- **`bindingOptionsOfTable` built and cached a whole table instance to read a value that is a pure function of the catalog entry.** It went through `lookupOrInstantiate`, which constructs an `OptimysticVirtualTable` and a schema manager and consumes the table's owes-a-catalog-record flag — all to return `table.bindingOptions`, which is `parseTableSchema(tableSchema)` and nothing else. Worse, the instance it left in the module's cache is the hazard `registerBridgeConnection` in the same file already documents and avoids: an uninitialized cached instance makes that table's first `connect` ignore the `tableSchema` Quereus supplies for it. Now reads the cached instance's binding when a statement has already touched the table, and otherwise parses the catalog entry directly, building nothing, touching no storage and registering nothing. The method is no longer `async`; `plugin.blobsFor` stays `async` on purpose so an unknown table still arrives as a rejection, which is what the README and docs/blobs.md promise.
- **`CollectionFactory.clearCache()` forgot the transactors but kept the blob backends**, so `BlobBackend.transactor` — documented as "the transactor of the same key" — became a transactor the factory had discarded. Dormant today (nothing reads that field yet), but it is the field `feat-blob-reference-trees-follow-sql-rows` reads reference trees through, and on a `test` or `local` transactor the discarded one addresses a block store nothing else writes to. The backends now go with the transactors, which for `network` costs nothing (the node and its `node.blobs` outlive the call) and for every other transactor is coherent with the block store those rebuild from scratch there.
- **`onBlobBackendResolved` replayed the already-resolved backends to a listener that was already subscribed**, so subscribing the same function twice delivered each backend twice — the one contract violation invisible from outside, since the `Set` holds the listener once either way and the documented promise is "each listener hears each backend exactly once". Replays only on a genuinely new subscription now.
- **`adapter-integration.spec.ts` was failing at HEAD**: "should register the StampId and CommitOutlook functions" asserts the registration list as a closed set, and the two new functions broke it. Not pre-existing — the implement commit caused it, and the full suite was deliberately not run there (per [tickets/rules/testing.md](../rules/testing.md) that is review's to run). The list is updated and the test renamed to say that the closed set is the point, with the reason a registration list is worth pinning at all.

**Parked as tripwires, not filed** (each is conditional; see the ticket rules' definition):

- The three the implementer parked were all read and all stand: no refusal of either function's value in a written row (`NOTE:` at the head of `functions/blob-functions.ts`, conditional on `feat-no-deployment-validates-transactions-at-pend`, which is itself still in `backlog/`); a blob-backend resolution in flight across `dispose()` (`NOTE:` on `blobBackendsInFlight`, beside the identical one on `transactorsInFlight`); and the plugin's own node keeping blob pieces and records in memory (`NOTE:` at the `createLibp2pNode` call). The third was weighed as a possible ticket and left as a tripwire: that node is passed no block storage either, so nothing it holds is persistent, and the README's `blobStorageFactory` row already says to build the node yourself when you need persistence.
- **Both SQL functions re-derive the default binding and re-look-up the backend on every call, which is per row.** Deliberate — resolving afresh is what makes a service used after a `dispose()` reach the store the factory built next rather than the one it stopped — and nothing in it touches storage. `NOTE:` on `SqlBlobService.backendNow`, naming the remedy (a disposal generation the factory bumps) rather than simply remembering the backend, which would reintroduce the stopped-service bug.

**Filed as tickets: none.** Every finding either resolved at its site in this pass or is conditional on something that has not happened. Nothing reached the filing bar — no finding named a class-level invariant that wanted a type change, a property test or a boundary assertion, and no latent defect was found whose only anchor is a later release.

**Considered and declined, deliberately left alone.** `isAsync: true` on both function schemas is redundant: Quereus detects a declared `async function` automatically and documents the flag as being for the implementation that returns a promise without being declared `async`. Kept — it costs nothing, it states the intent at the registration site, and it survives a refactor that wraps the implementation. `OptimysticVirtualTable.bindingOptions` hands out the instance's own mutable options object; making it `Readonly` would cascade through `getBlobBackend`'s parameter type for no behavioural gain.

**Tests.** The five the implementer wrote all pay for themselves and none were cut: each pins a documented answer (`here` plus the size off a list root, `unknown` with no size, NULL, the `MISMATCH` classification over both arms and both functions) or one of the two branches of the only branching logic in `SqlBlobService` — which owner label a put pins under. Added one `describe` for `plugin.blobsFor`, which the handoff correctly flagged as unverified and which this pass also changed: a fresh service over the same store as `plugin.blobs` for the default network, the two tables it must refuse (unknown name, and one another module owns), and a table hydrated into the catalog that no statement has touched — the arm that now parses the catalog entry instead of instantiating, which also shows the table still reads afterwards. Nothing was added for the registration, the option plumbing, the label builders against their own parser, or `getBlobBackend`'s keying; those are wiring or would test the module against itself, and were checked by reading and by running the code.

## Known limitations of this release

- **Nothing releases a pin.** Every blob put through `plugin.blobs` is held through its transaction's commit *and* its rollback, so an application on this release accumulates every blob it puts until it unpins by hand. That is the design (`feat-blob-pins-follow-sql-commits` closes it) and the wording was checked in all three places it is stated: the `put` doc comment, the README's *Putting and reading the bytes* bullet, and docs/blobs.md §SQL.
- **`BlobBackend.transactor` has no reader yet** — `feat-blob-reference-trees-follow-sql-rows` reads reference trees and the scope registry through it. Not dead code.
- **`blobStorageFactory` is not validated and cannot be.** Persistent pieces over in-memory records, or the reverse, are both accepted; the consequence of each is documented on the option and in the README.
- **A reference written into a table on another network is not refused**, and both SQL functions read the default network because a scalar function has no table context. Both are stated in the README and docs/blobs.md; refusing the cross-network write belongs to `feat-sql-columns-hold-blob-references`.
