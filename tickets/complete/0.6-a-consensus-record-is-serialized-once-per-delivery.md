# A consensus record is serialized once per delivery

Implemented in `ticket(implement): a-consensus-record-is-serialized-once-per-delivery`; reviewed below.

Part of GitHub #63. Siblings: `sql-statements-are-built-only-when-something-reads-them`, `a-member-hashes-a-committed-block-once`, `a-large-write-is-measured-once-and-its-cost-is-documented` (re-measures and writes the docs; findings from this ticket appended to it).

## What changed

- `packages/db-core/src/cluster/membership.ts`: a module-level `WeakMap<RepoMessage, Uint8Array>` holds the UTF-8 bytes of `canonicalJson(message)`, filled on first use by the new exported `canonicalMessageBytes(message)`. `computeClusterMessageHash`, `computeClusterPromiseHash` and `computeClusterCommitHash` build their preimage by joining byte arrays (`concat` from `uint8arrays`) through one private `hashParts`: `utf8(messageHash)`, the memoized message bytes, `utf8(digest ?? '')`, and for the commit hash `utf8(canonicalJson(promises))`. The comment on `hashParts` gives the byte-equality argument: UTF-8 encoding commutes with concatenation except where a part ending in a high surrogate meets one starting with a low surrogate, and every boundary here has a JSON text (ASCII first and last character) on one side — so it holds even for a hostile, ill-formed `messageHash` or digest, not only for well-formed input.
- `canonicalMessageBytes` is total on hostile input: a record off the wire is hashed in `validateRecord` before its shape is checked, and the dispute path hashes an attacker-supplied `originalRecord`, so `message` may be `null` or not an object. Such a message is not memoized (a `WeakMap` throws on a non-object key, where the old string concatenation did not), and the template literal keeps the old spelling of `canonicalJson`'s `undefined` as the string `"undefined"`.
- Two `NOTE:`s at the `WeakMap`: the memo is sound only because no `RepoMessage` is mutated after it is hashed; and the tripwire that it holds one more copy of each message for as long as the message object lives (drop the entry once the record is decided if member memory under large writes ever matters).
- `ClusterMember.mergeRecords` compares the held and incoming messages with `equals` over `canonicalMessageBytes` of each instead of `canonicalJson(a) !== canonicalJson(b)` — the same equality, with no serialization once both records have been validated.
- No caller changed besides `mergeRecords`; `commit-proof.ts`, `cluster-coordinator.ts` and `dispute-service.ts` get the saving through the three functions.

## Mutation check (the memo's precondition)

By inspection, no production code assigns into a `RepoMessage` once it is in a `ClusterRecord`: `ClusterCoordinator.executeClusterTransaction` copies (`{ ...message, coordinatingBlockIds: [blockId] }`) rather than mutating, with a comment saying why; `makeRecord` only places the message; grep of `db-p2p/src` and `db-core/src` for assignments into `.message.…`, `operations[i]`, `.pend.` or `.commit.` found none. Tests: `cluster-repo.spec.ts` "rejects a record whose priority was inflated after signing" mutates a message in place after hashing it, but with the spec's own hash helper, so the member's first hash (through the memo) happens after the tamper and still detects it; `cluster-consensus-divergence.spec.ts` mutates before building the record. Both pass unchanged.

## Test added

- `packages/db-core/test/cluster-hash-layout.spec.ts` — pins the signed preimage layout (`docs/correctness.md` §2) to literal values computed on HEAD before the change: the membership digest of `['peer-B', 'peer-A']`, and message/promise/commit hashes for one pend message (a transform, `baseRevs`, Latin-1, CJK and an astral-plane character) as v1 (no digest) and v2 (with digest), over a promise map with a reject reason holding a non-ASCII character. Each case reuses one message object across its three hashes, so the memo-hit path is what is pinned. No existing spec pinned literals: `db-p2p/test/cluster-membership-binding.spec.ts` checks v1 against a re-implemented oracle, and `commit-proof.spec.ts` pins sizes, not hashes.

## The bench

`packages/quereus-plugin-optimystic/test/large-value-commit-cost.bench.mjs`, run by hand after `yarn build` (asserts nothing). Two-node mock mesh built as `mesh-node-harness.ts` builds it, node 0 writing `BlobChunk (Hash text primary key, Bytes blob not null)`; env `MODE=legacy|session`, `N` (8), `VALUE_KB` (256), `REPS` (20, after one unmeasured warm-up transaction). It prints per-transaction staging and commit ms, median/max and ms per MB of each and their total, and the expansion factor (median of node 0's `pend`/`pendMany` request bytes by `jsonEncodedBytes`, a `pendMany` that answers `undefined` counted as sending nothing, over raw value bytes). A transaction refused with `TransactionTooLargeError` is reported with its refused size instead of stopping the run — needed because the defaults are at the limit (below). Session mode is wired after the table exists, since the engine's schema hash must be warmed outside a statement. The header says how to profile it into `tickets/.logs/<name>` and to delete the profile.

Numbers, this machine (Node 24.2.0, Windows, memory storage), 20 transactions each, medians. Note this machine is about twice as slow as the one the plan ticket measured on (commit 1.5 s vs 0.7–0.9 s for 8 values), so compare within this table only:

Profile (`node --cpu-prof`, legacy, 6 × 8 values, both nodes in one process, start-up and warm-up included in both runs): time with any of the three hash functions or `mergeRecords` on the stack went from 3.93 s of 14.52 s busy CPU (27.1%) to 1.21 s of 12.37 s (9.8%); `validateRecord` alone from 1.78 s to 0.51 s. What remains is one serialization per message object per delivery and three SHA-256 passes over it (message, promise, commit), which the pinned layout requires.

## Known gaps and things for the reviewer to weigh

- **New public export.** `canonicalMessageBytes` is exported from `@optimystic/db-core` (through the cluster barrel) so `mergeRecords` can use it. Its contract — shared bytes, never write to them — is in its doc comment only; a caller that writes into the returned array would corrupt every later hash of that message object.
- **The memo trusts the no-mutation rule.** Nothing enforces it; a future code path that assigns into a hashed message would produce signatures over stale content in-process (over the wire a fresh decode would still be caught by the hash check). Freezing the message at first hash was not done: `Object.freeze` is shallow and deep-freezing a multi-MB message costs a walk of it.
- **Benchmark defaults sit at the size limit.** `N=8` in legacy mode is refused 1–3 times in 20 (a tree node division can carry already-stored rows in the pend); session mode cannot commit 8 values at all. Kept the ticket's defaults and made refusals visible rather than shrinking them; the measure-and-document sibling has been told (note appended to it).
- **One 403 s commit was observed once**, under `--cpu-prof`, entirely inside one `TextEncoder.encode` in `encodeJson` called from `savePendingTransaction`; it did not recur in a second profile or in five unprofiled 20-transaction runs, and the cause is unknown (a host stall is plausible). Recorded on `a-large-write-is-measured-once-and-its-cost-is-documented`, whose §3 already owns outlier investigation; no ticket filed.
- **In-process sharing.** In the mock mesh one message object can reach several simulated nodes; they share a memo entry, which is correct since the content is identical.

## Review findings

Read the implement diff first (`membership.ts`, `cluster-repo.ts`, the pin spec, the bench), then every caller of the three hash functions (`cluster-repo.ts`, `commit-proof.ts`, `dispute-service.ts`, `cluster-coordinator.ts`).

- **Byte equality of the preimage — checked, holds.** `canonicalJson` is `JSON.stringify`, which escapes lone surrogates, so every JSON part is well-formed and starts and ends with an ASCII character; the surrogate-boundary argument in `hashParts`' comment is correct. The pin spec (literal v1/v2 message, promise and commit hashes over non-ASCII content, computed on the pre-change source) passes.
- **Defect found and fixed: a missing part hashed differently from the old concatenation.** `utf8` called `TextEncoder.encode(text)` directly, and `encode(undefined)` encodes nothing, while the old `messageHash + … + canonicalJson(promises)` spelled a missing part `"undefined"`. The implementer had handled this for `message` alone. It is reachable where a record arrives unchecked — the dispute path hashes an attacker-supplied `originalRecord` (its `messageHash` is never checked before `computeClusterPromiseHash`), and a commit proof's parts. `utf8` now coerces through a template literal, which covers every part in one place, and `canonicalMessageBytes` uses it. One case still differs and is documented at `utf8`: two adjacent missing parts, which the old `+` added to `"NaN"`; no record a signer sees has that shape. Added one test to `packages/db-core/test/cluster-hash-layout.spec.ts` (a real message with `messageHash` and `promises` missing, compared against the old concatenation); confirmed it fails without the fix (`encode(undefined)` is 0 bytes, `` encode(`${undefined}`) `` is 9).
- **Memo soundness (no mutation after hashing) — checked.** Grep of `db-core/src` and `db-p2p/src` finds no assignment into a hashed message. The one spec that mutates a message after hashing (`cluster-repo.spec.ts` "rejects a record whose priority was inflated after signing") builds its hash with a spec-local helper, so it still exercises detection; if that helper is ever switched to `computeClusterMessageHash` the test would fail loudly rather than pass silently, which is the right failure. The two `NOTE:`s at the `WeakMap` (the no-mutation rule, and the memory tripwire) are the right home; no ticket.
- **`mergeRecords` comparison — checked.** Byte equality over the memoized canonical bytes is the same equality as the old string comparison (well-formed JSON encodes injectively). Redundant with the `messageHash` check above it for validated records, but kept as it was, and now costs a memo hit and a byte compare.
- **New public export `canonicalMessageBytes`** — accepted as is; its only caller is `mergeRecords`, and the shared-bytes contract is in its doc comment. No action.
- **Bench** (`large-value-commit-cost.bench.mjs`) — read; it asserts nothing and is not picked up by any test glob, imports only declared dependencies (the implementer's `check-undeclared-deps` run). Defaults at the size limit and the one 403 s outlier are already handed to `a-large-write-is-measured-once-and-its-cost-is-documented`; nothing further.
- **Tests** — the pin spec meets the bar (it pins the named signed layout of `docs/correctness.md` §2, which nothing else pinned to literals); kept. Nothing cut.
- **Docs** — the signed layout and every documented behaviour are unchanged; `docs/correctness.md` §2 and `docs/internals.md` need no edit. The cost write-up belongs to the measure-and-document sibling.
- **Tripwires / new tickets** — none beyond the implementer's two `NOTE:`s. No tickets filed.
