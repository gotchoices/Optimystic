GitHub #52. Closes the cost `an-index-walk-serves-order-by` accepted.

## What was built

A whole-index walk (`plan=0`) or a range seek (`plan=3`, `plan=7`) counts the index entries it fetches, rejected ones included. On reaching `WALK_ROWS_BEFORE_SCAN` (256) it stops the entry iterator and gets the rest from `executeTableScan` over the same main view. `restOfWalk` keeps a scanned row when its tree key lies past the last key fetched, in walk order, and inside the range, when it passes any row test for a bound the tree could not apply, and when the walk did not already yield it. It sorts the kept rows by tree key in walk direction, and they continue through the same `inEngineOrder` generator, so a run held at the switch flushes in order with them.

An equality seek, a multi-seek, the legacy `idxNum >= 10` arm and a read of a partial index never switch. The limit is checked on the entry past the 256th, so a read of exactly 256 entries does no scan, and `matched` tops out at 256 on a `scan=1` line.

`index:seek` gains `scan=0|1`. `matched` and `rejected` stay counts of index entries, so the scan's rows are in neither.

## Acceptance

Plans are as the ticket expected at both sizes: `INDEXSCAN` for both `order by T` rows, `INDEXSEEK` for the range and equality rows.

The ticket's "within about 8 ms" of a scan and sort **is not confirmed by measurement**. Paired reads in one process, implement stage, median of 41, machine running other work:

| rows | `order by T`: with switch / scan and sort | median difference |
|---|---|---|
| 2,000 | 31.9 / 18.9 ms | 12.7 ms (`desc`: 13.2 ms) |
| 5,000 | 59.0 / 49.0 ms | 10.1 ms (`desc`: 10.2 ms) |

Scan and sort ran about 1.5 times slower than the ticket's baseline in that run, which would put the difference near 8 ms on a quiet machine, but that is an inference. The review's own repeat was too noisy to settle it (see findings). `docs/internals.md` states both the 8 ms derivation and the 10 to 13 ms measurement.

Range reads above the threshold pay the same: at 5,000 rows `where T > 't001990'` returned 3,009 rows in 41.1 ms against 27.3 ms with no index.

## Tests

In `test/index-ordered-walk.spec.ts`, differential against a memory table: forward and backward walks, a limit past the threshold, a limit met from a held run, forward ranges, four range ends in both directions, ranges bounded by a surrogate-bearing value, an unordered range, reads the threshold covers (`scan=0`), and equality and multi-seeks that never switch. `restOfWalk` is tested directly for the row that moved past where the walk stopped. In `test/committed-read-isolation.spec.ts`: both phases read the one pinned view when a commit lands during the walk.

The implementer's mutation check broke the implementation 13 ways and 11 were caught. The 2 survivors are equivalent on a healthy tree: a row at exactly the last key is dropped by `yielded`, and no entry sits exactly on a bound.

## Review findings

**How it was checked.** Read the implement diff before the handoff, then ran a throwaway differential spec (deleted afterwards) against a memory table: 1,200 rows with NULLs, astral text, lone surrogates, U+E000+ text and `～` in index values, some astral primary keys, and single-column and two-column indexes. No composite primary key was tried. It ran 19 read shapes: walks, ranges and prefix ranges (`plan=7`) in both directions, surrogate bounds, NULLs excluded from a backward range, unordered ranges, and residual filters with `limit` and `offset`. It also ran 5 DML statements whose source read crossed or approached the threshold, with `plugin.verifyIndexes` after each, and a read inside a transaction with staged rows on both sides of the switch. All matched, and every index reported no discrepancies. `scan=` and `matched=` read as documented, including `m256:r256:s1` when a surrogate bound rejects everything before the switch.

**Correctness: no defect found.** Reasoned through and confirmed by that run: rows past the end of a prefix range in either direction, NULL-keyed rows below a range's low key on a backward read, the entry fetched past the limit coming back from the scan and not being lost, `entry[1]` and `extractPrimaryKey` giving the same framed key, an iterator closed by `break`, and an abandoned consumer. A selective residual moves on after 256 entries as designed.

**Fixed in this pass (minor):**

- `schema/index-walk.ts` imported `compareTreeKeys` from `optimystic-adapter/collection-factory.ts`, the only runtime import from `schema/` into the adapter, which also pulled the mesh and transactor imports into anything loading the walk's pure functions. The implementer left this as the reviewer's call. Moved the comparator to `schema/key-encoding.ts`, the module that defines the order it compares, and updated `docs/internals.md`.
- `IndexScanPlan.mayFinishByScanning` relied on a stated premise that no walk or range runs over a partial index. That holds only because `getBestAccessPlan` skips them, and its comment names a planned feature to plan through them, at which point the switch would return rows the predicate excludes with no error. The premise is now enforced at the one read site (`holdsEveryRow`, `finishesByScanning` in `verifiedIndexRows`), so such a read keeps walking. No test: the branch is dormant, and the condition is one conjunct.
- The `NOTE:` at `WALK_ROWS_BEFORE_SCAN` named only pages, while `docs/internals.md` and the handoff point to it for ranges too. It now covers a range holding more than 256 entries of a much larger table, and the README says the same.
- Stale docs: the README said a range reads "nothing else" past its bound, and `docs/debugging.md` said a bound the tree cannot apply reads every entry under the prefix. Both now account for the switch. The `IndexSeekProbe` comment pointed at `executeIndexScan` for verification that lives in `verifiedIndexRows`.

**Tripwires, in the code:** pages and ranges over 256 entries on large tables (`NOTE:` at `WALK_ROWS_BEFORE_SCAN`, extended above); the answer depending on a row's position on a damaged tree (`NOTE:` at the switch in `verifiedIndexRows`).

**Tests:** none cut. Each read case is a differential check on a distinct switch position or range end, and the mutation check supports them; they add little beyond the shared `before`. None added. `plan=7` crossing the threshold has no permanent test: it reaches the same `restOfWalk` as `plan=3` through one flag, and losing the flag costs speed, not correct answers. The throwaway run covered it, as it did the gaps the handoff listed as inspection-only, apart from those below.

**Still verified by inspection only:** a stale entry before the switch, a damaged tree, and a real concurrent writer during the walk phase (the `yielded` branch is tested on the pure function). The ticket allowed this.

**Accepted cost, not a defect:** a short `limit` over a long held run still scans. `order by t desc limit 10` whose top 256 entries all hold text at or above U+D800 reports `scan=1`; it is correct and bounded by a scan and sort. `docs/debugging.md` says so.

**Performance: inconclusive, no action.** The review repeated the paired timing (30 pairs, machine under load): at 5,000 rows the difference was 1.0 ms and 10.2 ms, at 2,000 rows 85.2 ms and 45.6 ms, with scan and sort itself about 5 times slower than the ticket's baseline (70 ms against 13.7 ms at 2,000). That spread cannot confirm or refute the implement-stage figures, so they stand, marked as unconfirmed against the 8 ms target above. **A quiet-machine rerun is what would settle it.**

**Noticed by the implementer, now resolved:** a table alias costing a statement its index ordering is real (`select x.id from a x order by x.t` plans `SORT SEQSCAN` on an Optimystic table here, and `SORT INDEXSCAN` on a memory table) and is already tracked in the Quereus repository as `bug-table-alias-defeats-sort-absorption`, in its `fix/` stage. Nothing to file here, but `select … from Message M order by M.Timestamp desc limit 100` gets none of this work until that lands.

**Tickets filed:** none. Nothing met the filing bar: no defect was found, and the conditional concerns are tripwires.
