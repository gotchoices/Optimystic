# Every storage backend stores blob pieces

## What was built

### `LevelDBPieceStore` (`packages/db-p2p-storage-rn/src/leveldb-piece-store.ts`)

Implements `IPieceStore` over the shared `LevelDBLike` handle, exported from `src/index.ts`. Not a `RawStoreDriver` store, outside the write group and journal.

- **Keys** (`keys.ts`): `TAG_PIECES = 0x09` (0x08 is `TAG_COMMIT_PROOFS`). `pieceKey(id)` = `0x09 0x00 id` holds the bytes, `pieceSizeKey(id)` = `0x09 0x01 id` holds the length as 4 bytes big-endian. Also `pieceSizeRange`, `pieceRange`, `pieceIdFromSizeKey`, `encodePieceSize`, `decodePieceSize`. Layout comment updated (new paragraph; the "deliberately spaced" sentence now says 0x01–0x09 are taken).
- **`get`** is `db.get(pieceKey)` (bytes, never `getText`). Both adapters return a fresh array (checked: `rn-opener.ts` wraps the buffer `getBuf` allocates, the test driver copies), so no copy in `get`.
- **`has`** reads the 4-byte size key only.
- **`put`**: `has` then one batch putting both keys, `{ sync: db.canSync }`. No sub-view copy is needed: `rn-opener.ts`'s `toArrayBuffer` copies a sub-view, and I checked by hand that `classic-level` stores a `subarray` and a zero-length value as exactly their bytes. `NOTE:` at `put` records the non-atomic has-then-write.
- **`delete`**: one unsynced batch deleting both keys. Accepted-tradeoff `NOTE:` at the site: on a syncing handle this departs from the flush contract's wording for deletes (same as `IndexedDBPieceStore`); a lost delete leaves an orphan the sweep removes.
- **`list`**: pages of `PIECE_LIST_PAGE` (1000) over `pieceSizeRange()` with `keys: true`, each page drained, the next starting `gt` the last key.
- **`bytesUsed`** = `measurePieces(db)` (exported from the module, not the index): one scan of the size range summing decoded sizes, a bad size value logged and skipped; failure logged under `storage:pieces`, answers 0.
- **`flush`** resolves at once; **`durability`** `'power-loss'` iff `canSync`; **no `close`**.
- **Identity**: the literal `'leveldb-handle'` became `LEVELDB_HANDLE_SCHEME`, exported from `leveldb-like.ts` (not from `leveldb-storage.ts`, which would make an import cycle, since `leveldb-storage.ts` now imports `measurePieces`). Not exported from the package index.

### Block store measurement (`LevelDBJournalStore.approximateBytesUsed`)

Now three parts: key+value bytes below `pieceRange().gte`, key+value bytes from `pieceRange().lt` up (a new private `sumEntryBytes`, iterator closed in `finally`), plus `measurePieces`. The piece and size keys themselves are not counted (a few dozen bytes per piece). `NOTE:` kept and extended.

### Upgrade check (`packages/upgrade-check`)

- `current-build.ts`: `OpenBackend.pieceStorage` — `FilePieceStore(join(dataDir, layout.blocks))` (closed first) or `LevelDBPieceStore(db)` — passed as `pieceStorage`.
- `fixture.ts`: optional `FixtureManifest.blob { ref, size, sha256 }`.
- Spec: "writes on top" now lists block ids, puts a blob (seed 2; 600 KiB as implemented, 300 KiB of text after review), checks the block id set is unchanged; the restart step reads it back `from: 'here'` and checks length + SHA-256; "reads back the blob the older build stored" is registered only when the manifest has `blob` (none does yet).
- Writer: namespace imports of the two storage packages, per-backend `pieceStorage` when the class exists, `pieceStorage?.close?.()` first, and a `storeBlob` step gated on `typeof node.blobs?.put === 'function'` before the in-flight append, recording `blob` in the manifest.
- **Deviation from the plan**: the blob generator lives in a new shared `writer/blob-content.mjs` (typed by `blob-content.d.mts`, added to `WRITER_FILES` in `scripts/write-fixture.mjs`) rather than being written once into the script and once into the spec — the same pattern as `classic-level.mjs`. Reviewer may prefer the plan's two copies; the writer and reader use different seeds, so they never needed to agree.
- I ran the writer by hand against the working tree for both backends: each printed "a blob" and recorded `blob` with `size: 614400` and the same ref and SHA-256 in both runs (deterministic). Output deleted. (Before the review changed the content to 300 KiB of text.)

## Tests added

- `packages/db-p2p-storage-rn/test/leveldb-piece-store.spec.ts`:
  - `runPieceStoreConformance('LevelDB pieces', …, { persistent: true })` — the shared contract, including zero-length and 1 MiB pieces and flush-then-reopen.
  - "lists every id once across several pages" — 2.5 pages of size keys written in one batch; checks `gt` paging neither skips nor repeats.
  - "pieces stay out of every other listing, and the block store counts their bytes once without reading them" — a database with a block, a journal record, a commit-proof key, a kv entry, the identity key and two pieces: `list` = the two ids, `listBlockIds` = the block, kv list = its entry, `readJournal().records` = its record, `blockStoreCountsPieces` true, `getApproximateBytesUsed` growth in `[pieceBytes, 2·pieceBytes)`. **Added beyond the plan**: a spy on `iterator` asserts the measurement read no `0x09 0x00` value. Without it, reverting `approximateBytesUsed` to the old full scan still passes the growth bound (it counts pieces once, just by reading them), so the case would not pin the measurement change it is meant to pin.

## Known gaps / for the reviewer

- **Never run on a device.** `rn-leveldb`'s `getBuf` for a zero-length value (empty `ArrayBuffer` vs `null`) and the JSI batch copying are inspection only.
- **Fixture size**: once a release with blob storage records its fixture, each fixture file gains a 600 KiB blob of random bytes, packed as base64 (about 800 KB per backend, so about 1.6 MB per release). Addressed in review: see Review findings.
- `approximateBytesUsed` stops counting the piece/size keys' own bytes; inside the conformance slack, but it is a small under-count.
- Puts are synced one by one on a syncing handle, so a multi-megabyte blob put costs about four syncs per MiB; not measured (relevant once the blocked `rn-leveldb` sync ticket lands — bullet added there).

## Review findings

Read the diff of `ticket(implement): feat-every-storage-backend-stores-blob-pieces` before the handoff. Ran `yarn build` + `yarn test` in `packages/db-p2p-storage-rn` (82 passing), `yarn typecheck` + `yarn test` in `packages/upgrade-check` (323 passing), `yarn lint:docs` (clean) and eslint over both packages' changed sources (clean).

- **`LevelDBPieceStore` correctness** — checked: key layout (`0x09 0x00 id` / `0x09 0x01 id`) sits strictly between `TAG_COMMIT_PROOFS` and `TAG_KV`, so no other store's range scan reaches it; put and delete keep the two keys together in one batch; `list` pages with `gt` over the last key, which both adapters support (`rn-opener.ts` seeks then skips an equal key); `has`, `list` and `bytesUsed` read only size keys; `sync` is only asked of a handle that can sync, so the RN adapter's refusal never fires. No defect found.
- **Block store measurement** — `approximateBytesUsed` splits the scan around `pieceRange()` and adds `measurePieces`; iterators are closed in `finally`; a failure answers 0 as before. Store identity is shared through `LEVELDB_HANDLE_SCHEME`, so `blockStoreCountsPieces` counts pieces once. The added spy assertion is what pins the "reads no piece" change; kept. No defect found.
- **Empty blob on a device (tripwire)** — an empty blob is a zero-length piece, and whether `rn-leveldb`'s `getBuf` returns an empty buffer or `null` for one is unverified. Parked as a `NOTE:` at `LevelDBPieceStore.get` with the fix to apply if it answers `null`.
- **Fixture size (fixed)** — the writer's blob was 600 KiB of xorshift output, which the fixture generator would pack as base64 (~800 KB per backend per release, incompressible in git, on top of fixtures already at 17 MB). Changed `writer/blob-content.mjs` to 300 KiB of numbered ASCII lines naming the seed: still two data pieces and a list piece, still deterministic, still no two equal pieces and no piece shared between the writer's and the reader's blob, and now packed as text, which git compresses. Updated `blob-content.d.mts` and the two `packages/upgrade-check/readme.md` mentions. Byte-exact storage of non-text pieces stays covered by each piece store's conformance suite (1 MiB and arbitrary-byte pieces), not by the upgrade check.
- **Shared `blob-content.mjs` deviation** — accepted: one generator copied beside the writer, as `classic-level.mjs` is, beats two copies.
- **Upgrade-check steps** — the new blob is pinned (`default` owner) so no sweep removes it before the restart read; `listBlockIds` is checked unchanged after the put on both backends; the older-blob step is registered only when a manifest records one. No defect found.
- **Tests** — the conformance run, the paging case and the beside-every-store case each pin a contract with real branching; none cut, none added.
- **Docs** — `docs/blobs.md`, `packages/db-p2p/docs/storage.md`, the RN README, `packages/upgrade-check/readme.md` and the blocked sync ticket read correctly against the code; the readme now matches the smaller text blob.
