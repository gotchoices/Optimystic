# The blob cache budget counts a partly held blob as nothing

A node keeps a byte budget over the blobs it holds only because it read them (`BlobCacheBudget`, `packages/db-p2p/src/blob/cache-budget.ts`) and took each blob's contribution from the `size` written on its blob record. A blob the node held only part of had no size on its record, so it contributed zero — and because the budget's whole decision is "is the total over the limit", a cache made of such blobs was never found to be over the limit and nothing was ever evicted, however much disk the pieces took. Reproduced before the change (budget 0, all pieces present, `size` removed from the record: `cachedBytes 0 evicted 0 piecesLeft 3`).

Both arms landed at the one cause: an absent size was read as "zero bytes" when it means "this node cannot say what it is spending here".

**Arm 1 — the fetch writes the size as soon as it learns it.** `BlobFetchStore` gained `markPartial(ref, size)` (`local-blob-service.ts`), wired to the existing `correctRecord(ref, false, size)` beside `markWhole`. `FetchSession.noteSize` writes it once per session, hooked into `plan()` itself behind a `held` guard rather than at the enumerated call sites in `run()` — `plan()` is also where `dropArrived` re-walks the tree when a list piece arrives, the earliest moment the root's size is known, so one guarded site covers strictly more. `finish` covers the one blob no walk can size: a blob of a single piece, whose root is not a list, sized off that piece's own length.

**Arm 2 — the budget evicts a cache-only blob whose size it never learned.** `CachedBlob.bytes` is `number | undefined`; `LocalBlobService.cachedBlobs` passes `record.size` through instead of `record.size ?? 0`. `chooseEvictions` evicts every unsized blob not in use first (least recently read among themselves, ties by reference), then runs the unchanged least-recently-read walk over the sized ones until their total is within budget. `cachedBytes` sums the sized blobs only; its doc comments say what it leaves out and why the under-count is safe (the omitted blobs are evicted in the same pass). `cache:evicted` logs `bytes=unsized` rather than `0`, and the `cache:enforced` summary is also emitted when a pass evicted anything, not only when the total was over budget.

**Docs.** `docs/blobs.md` §Lifetime's "at its record's `size`" clause became the rule and its reasons: a cache-only blob counts at the blob's full size whether or not every piece is here (an over-count, which evicts sooner and so uses less storage); an unsized one is evicted at the next enforcement rather than counted as nothing; a 0-byte blob is not unsized. §Holds's list of what a fetch writes through `BlobFetchStore` gained the size write.

## Review findings

Read the `ticket(implement): the-blob-cache-budget-counts-a-partly-held-blob-as-nothing` diff before the handoff summary.

**A real defect, found and fixed in this pass: a fetch of a range of a one-piece blob was left unsized, so arm 2 evicted every blob a ranged read brought.** The implementer parked this as a tripwire in `FetchSession.noteSize`, on the grounds that nothing in this repository asks for byte ranges. But the path is not dormant code — it is reachable from the public API: `BlobService.read(ref, { offset, length })` runs `NodeBlobService.readFetching`, which starts a ranged session, and `finish` wrote no size for a ranged request. So any consumer that read a range of a blob of 256 KiB or less would have it dropped at the next enforcement and re-fetched on the next read, for as long as it kept reading ranges. The fix is in `finish`: the ranged branch records the size, falling back to the root piece's own length — the very read `finish` already performed for the unranged case, so no new assumption and one extra piece read on ranged one-piece fetches alone. The tripwire comment is gone, because the gap is closed rather than documented: arm 1 now sizes every fetch that got the blob's root piece.

**Everything else checked for correctness; no further defect.**
- Enumerated every path that can leave a cache-only record unsized, against the code: a fetch that never got the root piece (holds nothing worth keeping, so the eviction is free), the window between that piece arriving and the write (a crash), and records written before `markPartial` existed. The ranged one-piece case above was the fourth, and is now closed.
- `noteSize` runs inside `plan()`, which `runRound` and `dropArrived` also call, so a failing write could in principle fail a fetch. Verified in source that it cannot: `LocalBlobService.correctRecord` wraps `changeRecord` in a `try` and logs `record:correct-failed`.
- `markPartial` writes `whole: false`, so a session racing another session's `markWhole` can leave a stale `false` (and after the fix above, a completed range over a one-piece blob leaves one deliberately). Not a defect: a stale `false` only under-counts this node, which is the safe direction `BlobOwedRecords.holdsWhole` documents, and `stat` recomputes it from a census on the next call. `markPartial`'s doc comment now says this instead of claiming the hint is always honest.
- The new unsized pass keeps the eviction order deterministic: both passes walk the same `leastRecentlyReadFirst` sort, and the two sets are disjoint, so no blob is chosen twice.
- `cachedBytes` deliberately under-counts (unsized blobs omitted). Grepped for consumers outside `cache-budget.ts` and `local-blob-service.ts`: there are none but the two specs, so the under-count is not observable to any caller that acts on it.
- `blob?.bytes ?? 'unsized'` uses `??`, not `||`, so a 0-byte blob logs `bytes=0`.
- `plan()` is now a walk that writes a record, and was still documented as a walk. Doc comment corrected to say so, naming the re-walks inside a round, since that is the altitude surprise for the next reader.

**Docs were out of date with the code as landed, and are now corrected.** §Lifetime claimed a partly held blob is sized "whether or not the fetch asked for the whole blob or ever finished", which the implementation's own `NOTE:` contradicted for the ranged one-piece case; it also presented the crash window as the only remaining gap, omitting a fetch that never got the root piece at all. Both corrected, and the one-piece sizing at `finish` is now in §Lifetime and in §Holds's list of what a fetch writes.

**Source hygiene — one fix.** `chooseEvictions`'s new unsized pass looped over every blob and tested for `undefined` inside; the set is now named (`unsized`) beside the existing `sized`, so the two passes read as the partition they are. The `choose` closure the implementer flagged was kept: it is what keeps the in-use skip identical for both passes, and duplicating it would be worse. No file-size concern: `local-blob-service.ts` is 895 lines (`wc -l`) and the diff added about 20, with no size rule in `tickets/rules/`.

**Tests — one added, none cut.**
- Added `records the size of a blob it fetched only a range of, so the cache budget can cost it` to `packages/db-p2p/test/blob-network-read.spec.ts`: the reproduction of the defect above, at the lowest layer that reproduces it — a fetch needs real peers in this repository, and faking the blob protocol client would be a test of a module this repository owns, at the wrong layer. It is also the first coverage anywhere of a ranged read over the network, a public contract that had none. Verified it earns its place by reverting the `finish` branch: it fails with `timed out waiting until B's record of the blob carries the blob's size`. The size assertion is awaited rather than asserted outright because a read returns as soon as its range is here, while the session behind it is still walking to confirm and writing the record.
- The implementer's two additions both pay for themselves and were kept. The budget spec's new case is the ticket's own reproduction over a real `LocalBlobService`, and its 0-byte blob is what makes it discriminate "unsized" from "zero" — a fix that read an absent size as zero would evict the empty blob too and fail. The fetcher-spec assertion rides an existing interrupted-fetch test rather than adding a run.
- Nothing was cut: the diff added no test of wiring, registration, or a mock. The `markPartial` door, the `fetchDoor` entry and the `CachedBlob.bytes` type change are glue the typechecker already enforces, and the implementer correctly left them untested.

**Tripwires — one kept, one retired.** The full-size over-count `NOTE:` at the counting site in `chooseEvictions` stands: it is genuinely conditional (a caller reading small ranges out of very large blobs would count far more than it holds), and its cheaper route is named. The single-piece-ranged `NOTE:` in `noteSize` is gone, closed by the fix above rather than parked.

**Considered and left alone.** `cache:enforced` still logs nothing for a pass whose only eviction candidate was an unsized blob skipped as in use — a transient state that resolves at the next enforcement, with `skippedInUse` returned to the caller regardless; not worth either a line of code or a comment. The extra unflushed record write every multi-piece fetch now performs (`markPartial`, then `markWhole`) is the ticket's deliberate cost: the early write is what covers the interrupt and crash windows.

**No tickets filed.** Nothing reached the filing bar: the one real defect was about six lines and was fixed here, and the remaining concerns are conditional or already recorded at their site.
