# A repo-protocol read now reaches the cohort consult

## What shipped

`RepoService` handled every inbound block read — that is, every read made by *another*
node, the normal case for any party with more than one machine — by telling the repo to
skip consulting cohort peers. A coordinator holding nothing locally answered a bare
`{ state: {} }`, an **authoritative** absence, which `NetworkTransactor.get` treats as final
and never retries elsewhere. Downstream, `Collection.updateInternal` saw "I hold committed
revision N but the header block reads as absent" and threw `CollectionHeaderVanishedError`
permanently.

The fix drops that flag, so an inbound read reaches `CoordinatorRepo.get`'s existing cohort
consult. On a local miss it asks cohort peers first; if the cohort corroborates a revision
this node cannot acquire, or stays partially silent, the answer carries
`unavailable: 'peers-unreachable'` and the transactor retries against another peer instead
of accepting a false absence. A cohort that unanimously answers "I hold nothing" still
produces a bare authoritative absent, which is what keeps the routine new-collection probe
to one round trip.

Final shape of the changed call (`packages/db-p2p/src/repo/service.ts`):

```ts
response = await this.repo.get(operation.get, { expiration: message.expiration })
```

## Review findings

### Verified

- **Read the implement diff first, before the handoff.** It is one line in
  `src/repo/service.ts` plus a new 3-test spec. Nothing else in the commit.
- **No recursion.** Traced both legs of the consult by reading the wiring, not by trusting
  the claim: `clusterLatestCallback` (`libp2p-node-base.ts:812-845`) and
  `acquireBlockFromCohort` → `reconcileBlock` → `fetchArchiveFromPeer`
  (`libp2p-node-base.ts:713-750`) both dial `SyncClient`, so both land on `SyncService`,
  whose only repo call is `buildArchive` at `sync/service.ts:157-160` — still passing
  `skipClusterFetch: true`. That flag terminates the chain. Also checked the other inbound
  protocol that reads blocks (`cluster/block-transfer-service.ts:179`): it is not on the
  consult path at all, so it opens no second recursion leg.
- **Docs re-read against the new reality, not assumed current.**
  `docs/internals.md:389-421` (the three-answer read contract: present / authoritatively
  absent / unavailable) still describes the code exactly. `docs/transactions.md:505-544`
  documents lazy read-repair and a worst-case staleness bound without ever restricting it
  to locally-originated reads — so the change makes a documented guarantee *start* holding
  for remote reads, which it did not before. No doc edits needed.
- **Lint, build, tests.** `yarn lint` at repo root: clean, exit 0. `yarn build` in
  `packages/db-p2p`: clean, exit 0. `yarn test`: **1515 passing, 0 failing, 44 pending**.
  `yarn test:integration`: **30 passing, 0 failing, 2 pending**. No pre-existing failures
  surfaced, so nothing was written to `tickets/.pre-existing-error.md`.

### Minor — fixed in this pass

- **`as any` outlived its reason.** The options object was cast to `any` only to smuggle
  `skipClusterFetch`, which is not a `MessageOptions` field. With the flag gone the cast was
  silently disabling type checking on the remaining `{ expiration }` for no benefit. Removed;
  `MessageOptions.expiration?: number` types it directly.
- **Test gap: the other half of the contract was unpinned.** All three original tests assert
  that an *uncertain* absence gets flagged. None asserted that a *confirmed* absence stays
  unflagged. A regression that flagged every absence would have passed all three while making
  every `createOrOpen` probe of a not-yet-existing collection pay a transactor-level retry.
  Added `keeps the absent authoritative when the whole cohort answers "holds nothing"`.
- **Test gap: the locally-present read path was untested.** Removing the flag also routes
  reads of blocks this node *does* hold through the read-repair branch — the branch with the
  most new behavior and no coverage. Added
  `serves a locally-present block unflagged when the cohort corroborates it`.
- Supporting refactor for both: `makeAbsentStorageRepo` generalized to
  `makeStorageRepo(entry)`, and the cohort builder parameterized on `cohortLatest` /
  `localEntry`. `cohortLatest: null` is how a test says "the peer answered and holds
  nothing"; `undefined` cannot express it, because a destructuring default fires on
  `undefined` and would silently restore the default claim. Spec is now 5 tests, all green
  standalone and in the full run.
- **Stale comment corrected.** `test/real-libp2p.integration.spec.ts:524` still said the
  redirected get uses `skipClusterFetch: true`. The implementer flagged this and left it for
  the reviewer; it is now rewritten to describe the local hit that actually occurs there.

### Major — none

No finding warranted a new ticket. The change is one line with a bounded, traced blast
radius, its recursion guard is verified in code rather than asserted, and both suites plus
lint are green.

### Tripwires (recorded, deliberately not ticketed)

- **The handoff's cost claim was wrong, but the behavior is right.** It said "a read that
  hits locally pays nothing — unchanged". Not so: under the default `readRepairMode: 'lazy'`,
  a remote read of a locally-present block whose id is not in the 1000-entry
  `lastSeenCommitMs` LRU now triggers one cohort consult (bounded to 1000 ms, run in parallel
  across peers) and then re-arms the 10 s window. That is the documented read-repair
  behavior finally reaching remote reads — a correctness gain, not a defect — but it is real
  new cost on the remote read path. Parked as a `NOTE:` at the changed call site in
  `packages/db-p2p/src/repo/service.ts`: if a working set wider than that LRU ever shows a
  consult on every read, widen the LRU rather than reinstating the skip.
- **Batched multi-block remote reads pay the consult per block, sequentially.** Already
  carried by the pre-existing `NOTE:` at `coordinator-repo.ts:581`, which sits at the exact
  site; this change is what first puts it on the remote path. No new comment — duplicating it
  would just make the set noisier.
- **Integration pending count is run-dependent.** Two consecutive runs gave 29 passing /
  3 pending, then 30 passing / 2 pending. Cause is the deliberate, self-documented
  `this.skip()` at `multi-coordinator-write-relay.integration.spec.ts:148`: for some random
  per-run peer-id layouts no probed keyspace places coordinator B in A's cohort, so the spec
  would assert nothing. Pre-existing, unrelated to this diff, already explained in place.
  This also fully accounts for the handoff's "count note" puzzle over the predicted totals.
