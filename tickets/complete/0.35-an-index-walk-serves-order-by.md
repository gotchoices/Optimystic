## What was built

**Plan time** (`getBestAccessPlan` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`). The planner keeps a list of candidates and picks by `pricedWithSort`: a candidate's own cost plus `rows · log2(rows) · 0.1` when the request wants an ordering the candidate does not deliver. The equality seek on each non-partial index asks `walkDelivering` whether its prefix walk delivers the ordering; an ordered walk of each non-partial index (`orderedWalkCandidate`) is proposed when `walkDelivering` accepts it and at least one required column is one the walk itself orders. A walk claims no filter, costs one descent plus the rows wanted, and names no `indexName`, which sends it down the engine's ordering-only arm (`plan=0`, no arguments).

**The rule** (`walkDelivering` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts`). The walk key is the index columns then the primary-key columns not among them. A column pinned by a usable `=` or single-element `in` is dropped from the required list and skipped in the key. The remaining required columns must match the key positionally, each TEXT, BINARY on both the table column and the key column, not `hasSemanticOrdering`, all one direction, and no NULL may reach any of them in either direction.

**Read time** (`runQuery`, `executeIndexScan`). A secondary index with `plan=0` and no arguments is read through the index inside the synchronous view-building block. Direction is `filterInfo.accessPath.index.reverse`. Every index scan reads through one entry loop, `IndexManager.walkEntriesIn`, over `indexValueRange(key, ascending)`; a single range's rows pass through `inEngineOrder`, which holds rows whose key columns contain a UTF-16 unit at or above U+D800 in runs and sorts each run at the next pivot row, so the engine's code-point order comes out of the tree's code-unit order.

**Docs.** README's ordering paragraph; "An ordered read walks a secondary index" in `docs/internals.md`; the `dir=` field and the surrogate-run note in `docs/debugging.md`.

## Measured end to end (implementer's figures)

`transactor='test'`, Node 24, median of 7, `select Id from M order by Timestamp desc, Id desc limit 100` with an index on `(Timestamp)` and a TEXT `Id`, against the same table with no index.

| rows | page of 100, walk | page of 100, scan and sort | whole table, walk | whole table, scan and sort |
|---|---|---|---|---|
| 2,000 | 7.4 ms | 12.2 ms | 66.7 ms | 13.1 ms |
| 5,000 | 11.8 ms | 42.2 ms | 139.8 ms | 45.7 ms |

The unbounded `order by` is 3 to 5 times slower than a scan and sort, as the planning ticket accepted; `a-long-index-walk-finishes-by-scanning-the-table` closes that.

## Review findings

**What was checked.** The whole implement diff, read before the handoff. The engine's side of each contract the module relies on, in `@quereus/quereus`: the ordering-only arm of `rule-select-access-path.ts` (`makeOrderedScanFilterInfo` emits `plan=0` with no arguments), `resolveIndexDescriptor` and `validateIndexDescriptor` (a supplied descriptor is taken when its name is `indexName` or `orderingIndexName`, which both the seek and the walk satisfy), `nullSafeOrderingPrefixLength` (pinned columns are exempt, so counting skipped pinned key positions in `consumed` is right), and `rule-minmax-index-boundary` (the one sender of `request.limit`). The pivot argument of `inEngineOrder`, including the case the comment does not spell out: a trailing non-TEXT key column (a number framed as `toExponential`) can put a run's rows in a different order from a pivot's on that column, but every claimed column is TEXT and sits ahead of it, so the output is correctly ordered on the claimed prefix and the trailing columns only decide ties the claim does not cover. `BTree.range` with a descending `KeyRange` (first is the walk's start, so `indexValueRange(key, false)` swaps the bounds correctly). The `collate nocase` question the handoff raised, by experiment (below). Whether a user's `LIMIT` reaches the module, by logging the request: it never does, `limit 2`, `limit 2 offset 0` and `desc limit 2 offset 1` all arrive with `limit` undefined, and `max(c)` arrives with `limit: 1`, so the docs' claim holds and the walk's pricing of a plan-time limit is exercised only by min/max. The three docs the change touched, read against the code. `yarn build`, root `yarn typecheck`, `eslint` on the changed files, `yarn lint:docs`, and the package's `yarn test`: 1323 passing, 14 pending, smoke ok.

**Major, filed.** A `collate nocase` equality on a BINARY column returns mis-ordered rows: `select id from t where b = 'x' collate nocase order by c` over an index on `(b, c)` returns rows 1, 2, 4 where 2, 1, 4 is correct, on an Optimystic table and on a Quereus memory table alike. Two engine sites: `PredicateConstraint` carries no comparison collation, so the constraint reaches `request.filters` as an ordinary `=` and both this module's `pinnedColumns` and the memory module's `collectEqualityBoundColumns` pin the column; and the engine's collation cover check judges only a seek's consumed constraints and, when it declines the seek, answers with a sequential scan after the Sort was already removed on the plan's ordering claim. The second shape predates this ticket (the seek arm claimed an ordering within a sought prefix before), the first is new to the walk. Neither can be fixed here: the collation lives in planner-internal nodes the engine does not export. Filed as `tickets/blocked/quereus-a-collate-nocase-equality-keeps-an-ordering-claim-the-plan-cannot-serve.md` with the measured table, the cause at both sites, and the proposed change (carry the effective collation on the constraint; never absorb a Sort the cover check would then decline). A `NOTE:` at `pinnedColumns` points at it. No test added: the defect is the engine's and a test for it would fail until the fix lands; the blocked ticket carries the reproduction.

**Minor, fixed in this pass.** The `NOT_A_PIVOT` regex and two sites in `index-ordered-walk.spec.ts` held the noncharacter U+FFFF as a literal byte sequence; replaced with its escape sequence, so the files read and diff as text. The module's local `ColumnSchema` alias (the element type of `TableSchema.columns`) duplicated the engine's exported `ColumnSchema` type, which `index-walk.ts` already imports; the alias is gone and the module imports the type.

**Tests.** None cut. The planner-level cases each pin one branch of `walkDelivering` or one pricing comparison, and the differential suite pins the read path against the engine's own order; none restates the implementation or verifies a mock. The spec's `TOP_RUN_ENTRIES` re-derives the pivot rule from the fixture texts; kept, because the count it pins (the whole surrogate-range run is read before the first row) is what the `debugging.md` note promises an operator will see. None added, for the reason above.

**Tripwires.** Recorded at their sites: `pinnedColumns` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts` (collation-blind pinning, pointing at the blocked ticket); `IndexManager.walkEntriesIn` in `packages/quereus-plugin-optimystic/src/schema/index-manager.ts` (a live walk that has yielded throws on a concurrent change where the table scan resumes), from the implement pass; `bytesOrderAsValues` in `index-walk.ts` (the claim gates on the declared physical type while the stored payload follows the runtime value type), carried over from the old `treeDeliversOrdering`.

**Accepted as handed off, not changed.** `inEngineOrder` runs on every single-range index scan, claimed ordering or not: one regex test per key column per row, negligible beside the row fetch. The cost-tie rule "the longer seek wins" now applies across all candidates rather than within the index loop; no observed plan changed. The committed arm is covered by the `max(t)` CHECK over `committed.<Table>` with a staged row, not by a two-database interleave; the route is the same synchronous block as before. The plan-time skip of an index the instance does not maintain (`orderedWalkCandidate`) is by inspection only, since manufacturing one needs the two-handle withheld-index setup.

**Not in scope.** A walk of the primary-key tree itself for `order by Id` on a TEXT primary key; range bounds on the walk and the walk's cost on an unbounded read, which the next two tickets own.
