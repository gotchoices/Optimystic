description: While offline transactions are queued, every SQL statement used to copy everything staged for all of them in case it had to roll back. It now shares that data and copies only what later changes, so that copying no longer slows commits as the queue grows.

GitHub #53. One of two costs that make an offline commit grow with the queue. The other is ticket `queuing-a-transaction-costs-the-same-at-any-queue-depth`, so this ticket alone does not flatten the curve (see *What it measured*).

## What changed

A savepoint snapshot used to deep-copy the whole tracker, which holds every queued transaction's staged blocks. The Quereus bridge takes one per statement per written collection, and a successful commit restores none of them.

- `Tracker` keeps a set of ids (`owned`) whose staged value only it references. `stageUpdate` copies a value it does not own before changing it: `structuredClone` for an inserted block, which `applyOperation` mutates in place, and a plain array copy for an update list, since a staged operation is never changed once pushed.
- `Tracker.shareTransforms()` returns new outer maps and a new `deletes` over the same values, and clears the set. `Collection.snapshotPending` uses it in place of `copyTransforms`.
- `shallowCopyTransforms` is the same copy without touching a tracker. `Collection.restorePending`'s verbatim arm uses it, so one snapshot can be restored twice, and so does `Collection.createReadTracker`.
- `Tracker.reset` clears the set, so a tracker never owns what it was handed. The constructor starts with it empty for the same reason.
- `copyTransforms` keeps its deep contract for its other callers.
- `docs/internals.md`: a CLONE table row, a new *Functions That Share* table, *Transform Ownership*, Pitfall 1, and the snapshot rule in *Staged actions are segments*. A `NOTE:` at `Tracker.shareTransforms` names the residual cost and the remedy.

## Test added

`packages/db-core/test/snapshot-shares-staged-values.spec.ts`, each case run once over an inserted block (an invented collection's root leaf) and once over an update list (a write over a committed leaf):

- "stays as captured when later staging changes that value": the snapshot is unchanged, and the live tracker did change, so the case really exercised that shape.
- "gives the captured state each time it is restored, with staging between": one snapshot restored twice gives the captured transforms and the captured rows both times.

I confirmed it fails when each piece is removed, by temporarily editing the source: no copy of an inserted block (fails that shape only), no copy of an update list (fails that shape only), a capture that keeps ownership, a reset that keeps ownership, a restore that hands over the snapshot's own maps, and a capture that hands out the live maps.

No existing spec needed changing. `savepoint-rollback.spec.ts`, `collection-segments.spec.ts`, `read-view-pinned.spec.ts`, `committed-read-interleave.spec.ts` and `session-mode-commit.spec.ts` pass as they were.

## What it measured

Windows, Node 24, memory journal, run in `packages/quereus-plugin-optimystic`.

`NODE=1 MODE=gated N=1000 node test/offline-commit-cost.bench.mjs`, per transaction, at queue depth 25 … 1000:

| | before (HEAD) | after |
|---|---|---|
| whole commit | 3.6 … 32.8 ms | 3.8 … 22.7 ms |
| `structuredClone` time | 0.5 … 11.2 ms | 0.4 … 0.6 ms |
| `structuredClone` calls | 96 … 702 | 64 … 84, about 75 for most of the run |
| average over the run | 14.5 ms | 9.3 ms |

Each column is one run. A CPU profile of `NODE=1 MODE=gated N=800` now puts `snapshotPending` plus `shallowCopyTransforms` at about 0.9% of the run, against the 36% this ticket's plan recorded. The commit still grows with the queue: `enqueue` is 53% of that profile, which is what the sibling ticket addresses.

`MODE=online N=400 node test/offline-commit-cost.bench.mjs`, with and without `NODE=1`, 8 rounds alternating which build ran first. HEAD's three changed modules and the working tree's were compiled with the same flags and swapped into `packages/db-core/dist`:

| commit, mean | before | after |
|---|---|---|
| test transactor | 6.90 ms | 6.85 ms |
| `NODE=1` | 8.49 ms | 8.64 ms |

Online did not measurably change: on `NODE=1`, single runs vary by more than 1 ms, so the 0.15 ms difference is inside the noise. This shows no measurable slowdown, not an improvement. Clone calls online fell from about 180 to about 169 per transaction in single N=200 runs.

Rollback cost was not measured. The bench never rolls back, so a restore's cost does not appear in any number above; by inspection it is one map copy instead of a deep copy.

## Where to look hardest

- **The sharing rests on convention, not types.** Nothing stops code from changing a `CollectionSnapshot.transforms` value, or from passing a live tracker's transforms to `Collection.createReadTracker`, which would then see that tracker's in-place changes. Both are documented at the site, and the only `src` caller passes a snapshot's. A read-only type would enforce the first; I did not add one.
- **One owned set covers two shapes.** That relies on `stageUpdate` reaching an id's update list only while the id has no staged insert, and on `delete`, which removes both, being the only way to take an insert away. The comment on `owned` states this. A new path that removes an insert alone would break it.
- **`Collection.actAndSync` still deep-copies** (`stagedBefore`). It was not among the callers the ticket listed. It refuses over sealed segments, so its cost does not grow with the queue, and I left it.
- **Some copies are now redundant, and small.** A tracker built over a deep copy (`stageAttempt`, `resumedAttempt`, a reset to the invented baseline) does not know it owns that copy, so its first change to each id copies once more. I judged a constructor flag not worth having, given the online numbers above.

## Review findings

Reviewed the diff of `ticket(implement): a-savepoint-snapshot-shares-staged-blocks-instead-of-copying-them` before the handoff.

**Fixed in this pass (minor):**

- Three comments in `packages/db-core/src/transaction/coordinator.ts` still said `snapshotPending` and `restorePending` deep-copy the transforms (`captureUncaptured`, `rollback`, and the pre-stage snapshot in `execute`). The last was a `NOTE:` offering copy-on-first-stage as a future remedy, which is what this ticket built. All three now describe the capture as it is.
- The `NOTE:` at `Tracker.shareTransforms` named a remedy that would not work: capturing only what the open segment touched would hide the sealed segments' blocks from `Tree.readView`, which reads them through the snapshot. It now names a shared layer for what the sealed segments staged, and adds the one cost it left out: the first change after a capture copies that block's update list, which grows with the writes staged to the block.

**Checked, no defect:**

- Correctness of the sharing. A throwaway randomized check (not added to the repo; 120,000 steps of insert, update on an insert, update list, delete, nested capture, repeated restore and read view) ran the tracker against one whose snapshots are deep copies. The transforms were deep-equal after every step, and every outstanding snapshot stayed as captured. Its first run had a biased random generator and never restored, so I fixed the generator and reran it. Every shape was exercised in the rerun.
- The one-set-for-two-shapes assumption on `owned`. The `.transforms` references in `packages/*/src` show that only `delete` removes an insert, and nothing outside `Tracker` assigns to a tracker's maps. Insert over a shared update list marks the id owned while the list stays shared, which is safe because that list is unreachable until `delete` removes both.
- In-place mutators of staged values. `applyTransform` is only reached through `transformForBlockId`'s clones. `CacheSource.transformCache` clones inserts and folds operations into its own block. `applyOperation` clones what it splices. `mergeTransforms` shares operation arrays but never changes them. The commit path hands `collection.tracker.transforms` to the transactor as it always did, and the failed-commit restore reads the snapshot's values, which that path does not write to.
- Readers of a snapshot's `transforms`: `Tree.readView` is the only one in `src`, and the plugin touches none directly. A view's tracker never writes.
- Unlatched reads and captures during a drain replay. `shareTransforms`, `absorb` and `stageUpdate` are synchronous, so ownership cannot change partway through any of them. A capture taken between two absorbs of a replay holds partial state, exactly as it did with a deep copy, and the version-aware restore already handles that.
- `BasePins.copy` shares entries and is one map entry per pin, so it adds no block copying.
- Tests: the new spec pins a named contract with real branching, and each case fails for a distinct defect according to the handoff. Nothing to cut, and no test added, since the review found no defect in behaviour.
- Docs: `docs/internals.md` matches the code. `packages/db-core/docs/collections.md`'s `copyTransforms` is the per-attempt copy, which is still deep. `docs/offline-sync.md` makes no claim about the copy. The sibling ticket's premise is unaffected.

**Considered and left, with reasons:**

- No read-only type on `CollectionSnapshot.transforms`. No site changes those values, and the constraint is stated at the type, at `shallowCopyTransforms` and in the docs. A read-only type would have to be cast away where a `Tracker` adopts the values, so it would enforce little. Speculative, so no ticket.
- `Collection.actAndSync`'s `stagedBefore` deep copy stays. It refuses over sealed segments, so its cost does not grow with the queue.
- The redundant first copy for a tracker built over a deep copy stays. It is one extra copy per touched id, and the online numbers show no measurable slowdown.
- `Collection.createReadTracker` taking a live tracker's transforms is a wrong call the signature allows. Its doc comment states the rule and its one caller passes a snapshot's, so no further tripwire was needed.

**Tripwires:** the updated `NOTE:` at `Tracker.shareTransforms` is the only one, and it holds the capture and update-list costs.
