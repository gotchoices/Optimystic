# Unreferenced blobs are reclaimed

The reference pass of docs/blobs.md §Lifetime is built and reviewed. Five minutes after a node starts, then every six hours after the previous pass ended, and on demand, each node reads every registered blob reference tree for the blobs it holds under `responsible` or owes, and releases a hold only for a blob that two **counting** passes at least a grace period apart (7 days by default) found listed nowhere. Releasing the last hold deletes the record and leaves the pieces to the piece sweep. Cache eviction (`BlobCacheBudget`) is untouched.

## What landed

- **`BlobReclaimPass`** (`packages/db-p2p/src/blob/reclaim-pass.ts`) — one pass: snapshot `responsibleMarks()` and the owed ledger (`skipped: 'nothing-held'` when both are empty) → `detectPartition()` → scope registry → each registered tree in ascending order, asked only about the responsible references no earlier tree listed plus the owed references naming that scope → `aloneFor` over exactly the unconfirmed blocks → `detectPartition()` again → the predicate → apply → one `sweep()` if anything was released → one log line. `start()` / `runNow()` (joins the pass in flight) / `stop()`.
- **`whyPassDoesNotCount`** — the pure predicate holding every disqualifying condition from §Lifetime, answering the reasons a pass does NOT count (empty when it counts) in declaration order: `partition`, `registry-threw`, `registry-uncertain`, `registry-absent`, `tree-threw`, `tree-uncertain`, `unconfirmed-not-alone`, `stopped`.
- **`ConfirmationRecordingTransactor`** (`packages/db-p2p/src/blob/confirmation-recording-transactor.ts`) — the read-only transactor one pass reads through: it sets `BlockGets.awaitConsult` so an expired read-repair window's consult runs in front of the answer, and records every block whose answer did not carry `GetBlockResult.cohortConfirmed`. Its write methods throw (`ReclaimReadOnlyError`).
- **Node wiring** — `NodeOptions.blobs.reclaimGraceMs`, resolved before `createLibp2p` so a bad value throws before the node starts; one pass built on both roles with its stop wrapper installed ahead of the blob service's; `node.blobReclaim.runNow()` on `OptimysticNodeAttachmentsBase`, and `(node as any).blobReclaimPass` for diagnostics.
- **Docs** — docs/blobs.md status line, §Lifetime, §Holds and §Threats; docs/internals.md §Consensus Execution and its client-node table; docs/debugging.md's `blob:reclaim` row and a `reclaim:pass` entry under §Reading the fields.

Both new modules are exported from `src/index.ts` **and** `src/rn.ts`. The implement ticket asked for the Node entry only; that instruction was wrong (`test/entry-parity.spec.ts` requires the two entries to match, and the prereq's review had already corrected the same mistake for `reclaim-marks.js`), and the implementer deviated deliberately. Review confirms the deviation: both modules are React-Native-safe, and `yarn check:rn` now passes with them on the RN entry.

## Review findings

Read the `ticket(implement): feat-unreferenced-blobs-are-reclaimed` diff before the handoff summary.

### Release safety — checked end to end, no defect found

This is the only code in the repository that deletes replicated data on a schedule, so the direction that loses data got the most attention. Traced snapshot → registry → trees → aloneness → predicate → conditional write, and worked these cases by reading the code:

- A reference that **moves between two trees** while the pass reads, in either scope order: at worst a mark is written, never a release, because the next counting pass reads both trees. This is exactly what the two-pass rule is for.
- A reference **added after its tree was read**: marked this pass, cleared by the next.
- A **non-counting pass between two counting ones**: a mark is only ever acted on by a counting pass, and a counting pass reads every registered tree — so a mark cannot survive into a release while a tree that lists the blob went unread. The only tree a counting pass skips is one with nothing left to ask about.
- A `responsible` hold **released and re-taken** mid-pass: `releaseResponsibleIfMarked` is conditional on the exact mark, and re-taking the hold drops it.
- The **wall clock going backwards**: `judgeMark` restarts the period, which keeps the blob.
- A **tree whose scope is not in the registry**: never read, so the blob is released — which is the documented meaning of unregistering (the collection was dropped), stated in §Lifetime and in its accepted-limits bullet.
- The **mark is dated at the pass's start**, before the evidence was read, which shortens the real interval by one pass's duration — immaterial against seven days, and stated in the docs.

Also verified the half the pass depends on but does not own: an absent block comes back as `{ state: {} }` rather than as a missing entry, so `markCohortConfirmed` can mark it — which matters, because a registered scope whose reference tree has never been written is the common case, and if its header read could never be confirmed then no multi-node deployment would ever have a counting pass.

### Fixed in this pass

- **`arm()` armed a second timer instead of replacing the pending one** (`reclaim-pass.ts`). `runNow()` lands while the schedule's timer is pending — in practice always, since the first is five minutes out and the rest six hours — and the pass re-arms from the same place, so the earlier timer stayed live with its canceller overwritten and unreachable: one extra live timer per such call, each firing a full read of the registry and every reference tree with `awaitConsult` blocking consults, and `stop()` able to cancel only the newest. `arm()` now cancels before it arms. One test added (below); without the fix it reports two live timers where one is expected.
- **A skipped pass was returned before it was logged**, so `reclaim:pass` was never emitted for `skipped: 'nothing-held'` or `skipped: 'stopped'` and the format string's `skipped=` branch was dead code — contradicting the method's own doc comment *and* docs/debugging.md, which documents the line and prints a `skipped=nothing-held` example. A node that holds no blobs (any client that has not been put one) therefore logged nothing at all per pass, with the namespace enabled. `logPass` became `logged(report): ReclaimPassReport`, called at every exit.
- **A fourth stale forward reference to this ticket's slug**, in `test/blob-reclaim-marks.spec.ts`'s header comment, beyond the three the implementer had already fixed. It now names `BlobReclaimPass` and its path.

The implementer flagged the `blob-copy-drain.ts` doc correction for a second pair of eyes. It is right: the pass walks the owed ledger's entries, so an `owed` hold with no entry is never visited, and the rewritten sentence says so.

### Recorded as a tripwire, not a ticket

- **`skipped: 'stopped'` has no reachable path today.** `runNow` rejects once stopped, `stop()` cancels the timer, and the timer callback reaches the guard in the same synchronous tick as the firing — and the `arm()` fix above removed the one path (a leaked timer firing after `stop()`) that had reached it by accident. The guard is kept as the contract the report type states, with a `NOTE:` at the site saying it is unreachable and why it stays.

The implementer's three cost tripwires (blocking consults under `awaitConsult`, trees read one after another, one `findCluster` per unconfirmed block), the owed-scope divergence tripwire at the owed arm of `apply`, and the orphaned-`owed`-hold leak note are all already `NOTE:`s at their sites and were left as they are. None has tripped.

### Considered and declined — no change

- **`holdsAny` is a constant `true`** at the only production call site, because the `'nothing-held'` early return precedes it. Left alone: the field is a real part of the predicate's contract, the spec table exercises `false`, and the early return is the right place for that decision to live.
- **`cleared` conflates responsible-mark and owed-mark clears** and counts a reference that is both twice. Left alone: it is a diagnostic counter, the report shape the ticket specifies carries one `cleared`, and docs/debugging.md describes it loosely enough to stay true.
- **A race between `deleteIfUnlisted` returning true and `releaseOwed` running**, in which an `announce` arriving between the two awaits could have its fresh `owed` hold released under it. Below the filing bar and not this pass's to decide: `BlobCopyDrain.settleFull` already takes the same ordering with the same exposure, so it is one shared ordering to change if it ever matters, not a defect in the new code.
