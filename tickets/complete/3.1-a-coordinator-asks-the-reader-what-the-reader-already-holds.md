# A coordinator no longer asks the reader what the reader already holds

## What landed

A read sent to another machine carries `BlockGets.askerHolds`: per block, the sender's committed latest `(rev, actionId)` or `null` for "holds nothing", read from block metadata only (`StorageRepo.heldRevisions`: no materialization, no restore, no promotion). It is attached by the `stateHoldingsOnReads` decorator over the remote repo, at every production site that builds a transactor's remote repos (plugin `CollectionFactory.getRepo`, the reference peer's CLI) and in the mesh harness. `RepoService` binds the statement to the connection's authenticated peer (`MessageOptions.asker`); nothing in the request names a peer.

In `CoordinatorRepo.queryClusterForLatest`, the cohort member equal to the asker is answered from its statement instead of `clusterLatestCallback` when the statement is "nothing", or a revision below the coordinator's own, or equal to it under the same action (`askerStatementFor`). Anything else is consulted as before. When the statement names exactly the coordinator's own revision, the coordinator weighs it with its own retained commit proof for that revision (added in review, below). `cluster-fetch:asker-stated` is logged whenever a cohort member's statement was weighed.

Measured by the implementer against sereus `strand-reattach-first-sync-measure` (arm `reattach-empty`, 900 ms one-way, one run): reads routed to the other machine went from about 7.3 s to about 3.6 s.

## Review findings

Read the implement diff (`ticket(implement): a-coordinator-asks-the-reader-what-the-reader-already-holds`) first, then the handoff.

**Found and fixed in this pass**

- **Regression in cohorts of three or more: the stand-in dropped the proof, and with one member silent the read-repair window stopped arming.** The implementer judged that losing the asker's commit proof changed only log lines, reasoning from a two-member cohort. In a three-member cohort (the corroboration floor is two) whose third member is silent, the consulted reader used to answer with a certified claim at the coordinator's revision, so the pass reached `local-current` and armed the window. Its bare statement is one uncertified voter: the pass declined with silence present, never armed, and every later read of the block waited out the silent member's deadline (`cohortQueryTimeoutMs`, 1 s by default, more on declared slow links) instead of one consult per window. A phone group with one phone offline is the ordinary shape. A three-member cohort whose third member holds nothing got a false `repair-deadlock reason: 'sole-holder'` and re-consulted on every read the same way. Fix: `lendLocalProofToStandIn` in `packages/db-p2p/src/repo/coordinator-repo.ts` puts the coordinator's own retained proof (from its self answer, which already carries it) on the stand-in claim when the stated `(rev, actionId)` equals the coordinator's own. The proof certifies that revision whoever presents it, a consulted asker would have attached the same cohort proof, and proofs are served to anyone on the repair wires, so no trust is added. A lent proof that fails verification is not penalized against the asker. This also removes the implementer's "diagnostic change in undeclared two-member cohorts" gap: those log `certified-selected` + `local-current` again. Regression test: `coordinator-repo-small-cohort-arming.spec.ts` › "a read from a partner that says what it holds" › "stands in with this node's proof: a silent third member still lets the window arm" (checked: fails with the lend disabled, 3 consults instead of 1). `docs/transactions.md` and the `AskerStatement.held` comment updated.
- **The reference peer's CLI built remote repos without the decorator**, so its reads stated nothing. Wired through `stateHoldingsOnReads` with the node's `storageRepo`; now every production transactor site uses the one implementation.

**Checked, nothing to change**

- Identity binding: `RepoService` takes `connection.remotePeer`; `createServedRepoProxy` forwards `options` to the coordinated repo unchanged; a redirect re-sends the same statement over a new connection from the same reader, so the binding stays correct. Nothing forwards a received `get` to another coordinator, so no second hop can mis-bind a statement to the forwarding node.
- Untrusted input: `askerStatementFor` reads only the requested block's own property, validates `rev`/`actionId`, copies field by field (no `proof` rides in). A lying asker can say nothing it could not say in a consult answer; it can retire only its own recorded claims, as before.
- Missing-block path: with no local latest only a `null` statement stands in, so a stated revision on a missing block is always consulted; the new-collection probe stays authoritative only when the whole cohort answered.
- Monotonicity: `standsIn` is judged against the local latest read before the consult; a commit landing meanwhile only raises the self answer, so a stand-in judged "not ahead" stays not ahead.
- Error handling: `heldRevisions` catches and logs per block; the decorator's no-catch is recorded in the handoff and only reachable through another `IHeldRevisionReader`.
- Tests: the implementer's two read-repair tests each pin a named piece of the rule on branching logic (stand-in versus consult; null on a missing block) and fail without the substitution; kept. No tests cut.
- Docs: `docs/transactions.md`, `docs/internals.md`, `docs/debugging.md` read against the final code; the transactions paragraph now describes the proof lending. `yarn lint:docs` clean.

**Tripwires (not tickets)**

- The implementer's `NOTE:` at `stateHoldingsOnReads` (one local metadata read per block per remote read, even when ignored) stands.
- The handoff's three residual shapes stand as recorded, not filed: metadata `latest` versus the consult's projection for a tombstone or an unmaterializable latest (documented at `StorageRepo.heldRevisions`; affects only `no-quorum`'s `holders`/`absent` split, and the proof lend only fires on an exact match to the coordinator's served latest), the pre-existing mesh-harness consult-with-context divergence, and the decorator not catching a throwing reader.

**Not re-traced:** why a fresh node routes reads to its partner (the self-coordination grace period) — stated in `docs/transactions.md` as the usual reason, inherited from the fix ticket.
