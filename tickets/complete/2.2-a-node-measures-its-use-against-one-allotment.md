# A node measures its use against one allotment

## What landed

`StorageMonitor` and its invented 10 GB default total are gone. A node now has exactly one opinion about how full it is — `StorageAccount` (`packages/db-p2p/src/storage/storage-account.ts`), built once per node on either role from `NodeOptions.storage` and the new top-level `NodeOptions.storageAllotment`, reachable as `node.storageAccount`.

- **One option, validated at construction.** `storageAllotment: { bytes?, usedBytesCacheTtlMs?, now? }`. `bytes` must be an integer above 0 or node construction throws a `RangeError`, the rule `blobs.cacheBudgetBytes` already followed. `arachnode.storage` and `StorageMonitorConfig` are deleted, taking the two test-only `usedBytes`/`availableBytes` overrides with them; `arachnode` keeps only `enableRingZulu`.
- **The effective total** is the smaller of the allotment and what the location reports it will hold, over whichever are present, and `undefined` when neither is (`effectiveTotalBytes`). The location figure is the measured use plus `getApproximateBytesFree()`, both read inside the SAME memoized scan so they can never come from different moments. A rejected free-space read is caught, logged once for that scan, and leaves the location unknown — never 0, which would read as "full".
- **`usedBytes` is unclamped** (it still floors negatives at 0). A node past its allotment reports more used than its total; `availableBytes` floors at 0.
- **Ring selection declines on an unknown capacity rather than inventing one.** `determineRing` answers ring 0 (not `-1`); `shouldTransition` folds nothing into the EWMA, answers no move, and logs once; `createArachnodeInfo` omits `ArachnodeInfo.capacity`, which is now optional. `ArachnodeFretAdapter.getRingStats` leaves a capacity-less peer out of both the peer count and the capacity total, so a ring where nobody said yields no stat rather than a stat claiming zero.
- **One start-up line on either role,** beside `logStorageDurability`: the allotment (or that none was configured), the location figure (or that the backend reports no free space), and the effective total; a `WARN:` when neither is known, naming what ring selection will and will not do; and a second line when the allotment is below `DEFAULT_MIN_RING_CAPACITY_BYTES` (100 MiB, now exported from `ring-selector.ts` and read by both the wiring and the line).
- **reference-peer**: `--storage-capacity` → `--storage-allotment`, and `logRingInfo` reports the account's own figures rather than the flag it was handed.

The implementation is `ticket(implement): a-node-measures-its-use-against-one-allotment`; the review's own changes sit on top of it.

## Review findings

Read the implement diff first, then the handoff. Checked: the effective-total rule on a real filesystem backend end-to-end, every consumer of the now-unclamped `usedBytes`, every reader of a peer's advertised capacity, the start-up line's three branches against a real file store, the account's construction seam against the store the old monitor measured, resource cleanup in the memo, and whether the docs match the code.

### Fixed in this pass (minor)

- **Two logger namespaces were undocumented, and the package's own guard test failed on it.** `ring-selector` and `storage:account` are new `createLogger` channels; `packages/db-p2p/test/logger.spec.ts` ("documents every sub-namespace the package emits in `docs/debugging.md`") failed against the implement commit. Added both rows to the db-p2p table in `docs/debugging.md`, in the storage-and-block-movement group ahead of `ring-shift`, each saying what it emits and what it deliberately does not. This is the one test failure the diff caused, and it is caused by the diff, not pre-existing: the implement stage ran individual spec files, which is what the project's testing rules ask of it, and this guard is in `logger.spec.ts`.
- **The below-minimum start-up line claimed the opposite of what the node does.** It said an allotment under 100 MiB means "this node will serve no part of the keyspace". In fact `determineRing` answers `-1` and `createArachnodeInfo` clamps that to ring 0 with no partition, so the node that can serve least advertises the WHOLE keyspace. Reworded to say what actually happens and to tell the operator to raise the allotment, with a `NOTE:` at the site warning the next reader not to restore the stronger claim until it is true. The underlying behaviour is pre-existing and already owned by `a-node-stays-within-its-allotment` in `plan/`, which names this exact site ("Low space advertises the most work") — so no new ticket.
- **An unhandled rejection in the ring-transition tick.** `setInterval(async () => { … await ringSelector.shouldTransition() … })` in `libp2p-node-base.ts` had no `catch` around the decision, and the decision's FIRST act is now the storage scan — so a backend whose scan throws (a tree a permission change made unreadable) rejects an async interval callback nothing awaits: an unhandled rejection, process-fatal on Node ≥ 15. The file states this rule for itself elsewhere ("a bare `void` would surface that as an unhandled rejection … swallow + log instead") and this site violated it. Wrapped: log and skip the tick.
- **Every node construction paid a block-store scan even with logging off.** `logStorageAllotment` is awaited at construction and its only product is a `debug` line, so on a file host a client node walked its directory to format a string that was then discarded. `logStorageAllotment` now returns before scanning when `wiringLog.enabled` is false — the idiom `src/logger.ts` explicitly preserves the `enabled` accessor for. Nothing observable changes (the line was always gated on the namespace), and the tripwire NOTE at the call site was narrowed to say so. Verified the line still prints with `DEBUG=optimystic:db-p2p:node-wiring`.
- **`packages/reference-peer/README.md` still documented `--storage-capacity`.** The flag was renamed; the README was not. Updated, with the new description. `yarn lint:docs` could not catch this — it checks citations, anchors and file mentions, not CLI flag names.
- **The reference-peer status line could take down the peer.** `logRingInfo` awaited `node.storageAccount.capacity()` bare, on the start-up path, so a failed store scan would fail the session over a status line — the exact failure `logStorageAllotment` guards against two layers down. Wrapped in a try/catch that reports instead.
- **`parseStorageAllotment` under-validated relative to the option it feeds.** It accepted any finite positive number, so `--storage-allotment 1.5` passed the flag's own check and then threw a `RangeError` out of node construction with the stores already open. Now holds the flag to the same whole-number rule.
- **A test comment overclaimed.** `arachnode-fret-adapter.spec.ts` said a stat with `avgCapacity: 0` "`estimateNetworkData` would read as real demand". It would not — a sole zero aggregate falls through to the same ring-0 answer. Reworded to the claim that holds (reporting an observation nobody made) and to leave the consequence to the method that owns it.

### Checked and deliberately left alone

- **`StorageCapacity` lets `totalBytes` and `availableBytes` go absent independently** though they are always both present or both absent, so `shouldTransition` and `createArachnodeInfo` each test both. A discriminated union would make the half-known state unrepresentable (rung 1 of the ladder), but the two checks are what narrows both fields for the type checker, every current consumer handles it, and there is no defect behind it. Not filed, not commented — a union here buys type tidiness at the cost of a more awkward shape for five call sites.
- **`getRingStats().peerCount` now means "peers at this ring that advertised capacity", not the ring's population.** Its one real consumer multiplies it by `avgCapacity`, which reduces to the capacity total, so the arithmetic is unchanged; `getKnownRings` and `findPeersAtRing` remain population-truthful; and reference-peer logs the stats to an operator, where the adapter's own doc comment now states the rule. Consistent, documented, no change needed.
- **A degenerate zero total.** A disk with nothing stored and nothing free gives `locationBytes` 0, hence a total of 0 and `usedPercent` 0 from `shouldTransition`'s `totalBytes > 0 ?` guard — a full disk reading as 0 % used. The node has nothing to shed in that state and `determineRing` already declines it on `available < minCapacity`, so the guard's answer is harmless; the shape predates this ticket.
- **The account measures `nodeStorage.blocks` where the monitor measured the read-cached wrapper.** Verified `CachedRawStorage` forwards `getStoreIdentity`, `getApproximateBytesUsed` and `getApproximateBytesFree` to the inner store, so the figure and the piece-identity decision are identical either way.
- **Mixed versions.** An older peer reading an `ArachnodeInfo` with no `capacity` throws in its own `getRingStats`. The handoff accepted this against the repository's stated position; confirmed that position exists (`AGENTS.md:8`, "Don't worry about backwards compatibility yet"). Not guarded.
- **Two byte formatters** now exist — the new `formatBytes` in `libp2p-node-base.ts` and reference-peer's older ad-hoc GB line. Both are one-line display helpers in different packages; sharing them would mean exporting a formatting utility across a package boundary for two call sites. Left.
- **`libp2p-node-base.ts` is 3586 lines** (`wc -l`), up about 80 from this diff. Measured and noted rather than filed: the growth is one cohesive start-up report plus its formatter, and a split of this file is a separate decision from this ticket's.

### Tests

**No tests added, and that is deliberate.** Each finding either had no testable surface (a README line, a log line's wording, a CLI parse guard the package tests nowhere else) or was already covered by the invariant that caught it — the missing namespace rows were found by `logger.spec.ts`, which is precisely the class-level guard a new test would duplicate. The unhandled-rejection fix would need a 60-second interval driven on a real node to observe; the repo's own stated rule for that site is the guard.

**No tests cut.** Read every spec in the diff against the bar: the `effectiveTotalBytes` table, the location-figure rule, the failed-free-space arm, the over-allotment arm and the two unknown-capacity rules each pin a named rule with real branching; the five cache cases and two piece-identity branches carry over from `storage-monitor.spec.ts` unchanged in subject; the two new adapter cases pin the new wire contract. Nothing restates the implementation or verifies a mock.

**Verified by hand rather than by a new test** (throwaway script, deleted): the effective-total rule against `fileNodeStorage` on a real disk — a 50 MiB allotment bounds the total to 50 MiB and prints the below-minimum line; a 1 PiB allotment is bounded back to the disk's 2.34 TiB, `locationBytes` and `totalBytes` agreeing. This is the arm the committed coverage reaches only as a pure function, and it holds end-to-end.
