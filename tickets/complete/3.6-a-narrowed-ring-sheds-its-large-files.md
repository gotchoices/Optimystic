# A narrowed ring sheds its large files

## What shipped

A move-out that narrows the slice of the keyspace a node serves now bounds its blobs the same way it has always bounded its blocks. Before this, a node whose disk was mostly blobs could shed from ring 3 to ring 6 and free nothing.

Two halves, which have to be read together.

**Handing over.** `RingShiftCoordinator` gained one report beside `onRelease` — `onNarrowed({ from, to })`, fired from Phase C of a move-out only, immediately after the narrower slice is advertised and before the awaited `onRelease`, so a block-ledger fault cannot swallow the blob pass. It is not awaited and a synchronous throw is logged, so the blob side can never roll a settled block handoff back. The coordinator still knows nothing about blobs. The pass itself is `shedNarrowedBlobs` in the new `packages/db-p2p/src/blob/ring-shed-pass.ts`: select over the references this node keeps for the network, build each shed reference's owners from its own `findCluster` cohort, hand them to `BlobCohortReaction.releaseLost`, then drop the `responsible` hold on what confirmed and report what did not. The node factory binds it through `LateServingBindings.ringNarrowed`, the same late-binding seam `requestReleasedBlockSweep` uses, because Phase C is wired inside the Arachnode gate while the blob monitor is built later.

**Not taking it back.** `BlobAnnounceReceiver` now tests responsibility as "the slice I serve covers this key **and** my own view of the cohort includes me", through `isServingHolder`, so a node mid-shift still accepts for the range it is still serving. Reader repair goes through the same predicate, so a read cannot re-adopt what an announcement would be refused. The slice is read live off `ArachnodeFretAdapter.getMyArachnodeInfo`; absent — a client, Arachnode disabled, no FRET — means the whole keyspace, as ring 0 does.

Two pieces of de-duplication came with it. `BlobCohortReaction.releaseLost` is now the single release implementation both paths reach, and it carries the partition guard itself so no caller has to remember it. `narrowingSheds` in `arachnode-partition.ts` is the single coverage predicate both the block enumeration and the blob selection read, so the two halves of a move-out cannot disagree about which half is being handed over.

Implemented by `ticket(implement): a-narrowed-ring-sheds-its-large-files`; this ticket also carries the review pass's own fixes.

## Review findings

Read the implement diff first, then the handoff. Categories with nothing in them say so below rather than being left out.

### Checked and correct

- **The predicate's direction**, which is the one failure that would lose data: `narrowingSheds` is `covered-by-old && !covered-by-new`, and Phase C reports `{ from: the pre-shift advertisement's partition, to: the target's }`. Read against `partitionCovers` and against the block enumeration that now shares it. The new spec pins it with real digests.
- **The coordinate.** `coordOf` hashes the routing key once (`hashKey(routingKeyForBlob(ref))`), which is the same transformation `buildOwnersMap` applies for blocks and the key network applies to place a blob. Comparing a partition prefix against the un-hashed 32-byte digest would have selected an arbitrary half; it does not.
- **`onNarrowed` fires from exactly one place.** Phase C of `moveOut`, past the rollback return. A rolled-back shift and a move-in both report nothing. It does fire when the shed *block* set is empty, which is right: a narrowing can shed blobs without shedding blocks.
- **The gate has no other door.** `holdResponsible` has exactly two callers, the announcement path and reader repair, and both now go through the slice test. There is no push path that takes a `responsible` hold.
- **Ring 0 is the whole keyspace.** An absent partition answers `true` from `partitionCovers`, so a node with Arachnode disabled or no FRET behaves exactly as before — and the end-to-end blob suites, which run on real meshes, pass.
- **The late binding's lifetime.** Set after `monitor.start()`, cleared in the stop wrapper beside `offHoldsFeed` and in the wiring catch. `serving` is genuinely implied by `served` (`served` is only built when `serving` is truthy), so the added `serving &&` narrows for the type checker without changing which nodes get a blob monitor.
- **Releasing actually frees bytes, eventually.** `releaseResponsible` deletes the record when no hold remains and leaves the pieces to the sweep — the same thing the cohort-change path does, so the shed pass introduces no new deferral.
- **No blob analogue of `bug-a-replica-pushed-back-during-a-release-can-still-be-deleted`.** That race needs a version recorded after a release; blob pieces are kept by any remaining hold instead, and the slice gate now refuses the re-adoption that would be the equivalent.

### Fixed in this pass

- **The ordered list of `decide`'s checks in `docs/blobs.md` was not updated** — it is the canonical six-step description of the announcement decision, and its step 3 still said responsibility was the cohort alone. Rewritten to name both halves and their order. While there: the `out-of-space` step, which an earlier ticket documented only in prose further down the section, is now in the list too, so the list is complete again.
- **Five new log lines were missing from `docs/debugging.md`**, whose per-namespace tables are exhaustive by design and are what an operator reads: `announce:outside-slice` under `blob:protocol`; `release:partition`, `shed:cohort-unresolved`, `shed:done` and `shed:failed` under `blob:copy`; `phaseC:narrowed-listener-threw` under `ring-shift`. Added, with what each one means for the operator reading it. `announce:out-of-space`, missing for the same reason from the same table, was added alongside.
- **`docs/internals.md` § RingShiftCoordinator** described Phase C as a block-only release. It now says Phase C also reports the narrowing, and that blobs do not gate the shift; its *Qualifying holders* paragraph, which enumerates `arachnode-partition.ts`'s predicates, now names `narrowingSheds`.
- **A redundant floor guard.** The pass applied `Math.max(1, floor)` before calling `releaseLost`, which already floors at 1, and its comment justified this by what "the event arm" does at its call site — which, after this change, it no longer does. The floor now goes in raw on both paths and the rule lives in one place.
- **A redundant test assertion.** The new spec asserted set membership and then length separately; chai's `.members` without `.include` is already set equality, so the second assertion restated the first. Collapsed, with the point it was making moved into a comment.
- **One prose inaccuracy:** `RingShedOutcome` was documented as being "for the caller's log", and no caller reads it — the pass logs it itself.

### Parked as tripwires (not tickets)

Each is fine now and only becomes work if a stated condition trips, so each lives at its code site as a greppable `NOTE:`.

- **An unconfirmed shed blob is not retried soon.** `retainLost` ignores a reference this node is still responsible for, and a narrowing does not change a cohort, so the usual case (still in the cohort, outside the slice) re-offers the blob only at the next narrowing or cohort departure. The node keeps the bytes meanwhile — the safe direction, but it frees less than the narrowing asked for. `NOTE:`d at the `retainLost` loop by the implementer, with the fix if it bites.
- **A narrowed holder understates what it holds**, answering `not-responsible` for a blob it still holds whole, so an announcer stops counting it before it has released. Conservative for the length of the handover, and permanent where every cohort member has narrowed past the key — which the docs now state as an intended outcome. `NOTE:`d at the `responsibleFor` call.
- **One `findCluster` per shed reference, in turn**, which is the pass's cost on a node narrowing out of a deep ring. `NOTE:`d at `ownersOf`, where this pass extended the note: some of those lookups are spent on references held only `owed`, which the release arm then discards, and the fix if a writer that owes many blobs ever makes a narrowing expensive is the one the tracked-set feed's own note already names — feed only `responsible` holds there, rather than adding a second responsibility read to this pass.
- **A node that *starts* at a deep ring sheds nothing**, because bootstrapping below `minCapacity` is not a narrowing. It stops accepting blobs outside its slice but keeps what it holds until a cohort change. Stated in `docs/blobs.md`; marginal in practice, since reaching a deep ring on an earlier run means having already shed there.

### Not fixed, deliberately

- **The partition guard inside `releaseLost` is unreachable from the event path**, which turns back earlier. Kept: the rule that a split view must not drop a hold belongs with the decision rather than in each caller, and the ring path is the caller that would otherwise have had to remember it. Its own comment says so.
- **No in-flight guard on the pass.** Two narrowings close together, or a narrowing overlapping a monitor check, can run the release decision twice over the same references. Accepted for the reasons the wiring's existing note gives — `releaseResponsible` is idempotent, duplicate announcements are what the announce limiter is for — and minimum ring dwell makes it unlikely.

### No major findings

Nothing reached the filing bar, and no ticket was filed. The things the handoff flagged as its own risks — predicate direction, the coordinate, the single firing site, the binding's lifetime — were each checked independently and each hold. The remainder are the conditional concerns above, which the workflow's own rule puts at the code site rather than in the queue.

### Tests

**One test added by the implementer, kept as it stands** (with the redundant assertion cut): `packages/db-p2p/test/ring-shed-blobs.spec.ts` over `selectShedBlobRefs`, which pins the predicate direction with real digests and the real coordinate arithmetic, two references per two-bit prefix so a selection that stops after the first is caught. That is the one place where getting it wrong releases the half the node keeps, so it pays for itself.

**No test added for the pass itself**, and the handoff's suggested doubles-based "the answer is applied" test was considered and declined. `shedNarrowedBlobs`'s remaining body is glue over three decisions that are each specced where they are made — the release rule in `blob-cohort-reaction.spec.ts`, the coverage predicate through the block side in `ring-shift-coordinator.spec.ts`, and the selection in the new spec. A test that stubs the reaction and asserts `releaseResponsible` was called for what the stub returned would verify the stub, which is the wrong layer.
