## What landed

One behavioural edit, in `Collection.updateInternal` (`packages/db-core/src/collection/collection.ts`). It used to re-stage its pending actions against the freshly adopted revision only when a **block conflict** was detected — a conflict meaning an incoming log entry names a block this instance's tracker already holds a transform for. An action that changed no block holds no transform, so it never conflicts, so it was never replayed; the commit then wrote a log entry listing that action while the transforms it carried did nothing. Readers materialize blocks, not log entries, so the action vanished on every node.

The gate is now "a conflict was found, **or** the refresh adopted a newer revision and something is still pending". After review it lives in a named predicate rather than a comment block inline in `updateInternal`:

```ts
private mustReplay(anyConflicts: boolean, priorContext: ActionContext | undefined): boolean {
	if (anyConflicts) {
		return true;
	}
	const adoptedRev = this.source.actionContext?.rev;
	return adoptedRev !== undefined && adoptedRev !== priorContext?.rev && this.pending.length > 0;
}
```

The invariant it enforces, stated in its doc comment and in the docs: **a pending action was applied against the revision it commits over.** `replayActions` already resets the tracker and re-stages under the collection latch, so nothing new was built — only the condition widened.

Everything else is tests, comments and documentation. The implement stage added the first regression test, the `seedThrough` parameter and its end-to-end case, the two `NOTE:` comments in `index-manager.ts`, and the `docs/internals.md` paragraph. The review stage added the second regression test, the `deleteSchema` `NOTE:`, the `mustReplay` extraction, the `docs/debugging.md` paragraph, and the shared helpers in the db-core spec.

## Review findings

### Fixed in this pass (minor)

- **The top gap the implement handoff named was closed.** `updateIndexEntries`' old-entry delete — the same defect class, carried alongside an upsert instead of alone — had no test, because showing it needs a multi-level index tree with the two keys in different leaves. `Tree.createOrOpen` already exposes `nodeCapacity` precisely so tests can force that shape, so this was cheap. `packages/db-core/test/two-handle-collection-fork.spec.ts` gained "a blind delete paired with an upsert in a different leaf still lands", at fan-out 4 over twelve seeds. **Confirmed to discriminate**: with the gate narrowed back to conflicts alone it fails on the delete assertion (`expected [ 'k-z', 'later' ] to equal undefined`) while the paired upsert lands — which is also the first direct evidence for the `index-manager.ts` NOTE's claim that a shared leaf is what used to mask this. That NOTE now cites the test.
- **The 30-line comment block above a 4-line gate was turned into a named predicate.** `mustReplay(anyConflicts, priorContext)`, with the rationale as its doc comment. `updateInternal` reads as one step again.
- **The second conjunct's reason was undocumented and it is load-bearing.** `pending.length > 0` cannot be widened to `hasUnsyncedChanges()` (which also counts tracker transforms): a collection `createOrOpen` just INVENTED holds its staged header/root in the tracker with no pending action naming them, and `replayActions` resets the tracker before re-staging — so counting transforms there would drop those blocks and leave a brand-new collection unreadable, the hazard `snapshotPending` already documents. Nothing said so; a future tidier would have swapped it. Now stated in `mustReplay`'s doc comment.
- **`deleteSchema`'s `catch` fallback got its `NOTE:`.** The implement handoff identified it and left it unmarked. `packages/quereus-plugin-optimystic/src/schema/schema-manager.ts` stages a bare `[tableName, undefined]` after a failed `tree.update()`, which is blind in the same sense; it now says so, names the db-core rule it rests on, and says plainly that it is untested.
- **`docs/debugging.md` needed the update the implement stage did not make.** Its section "Does an index agree with its table?" documents `orphaned` entries with `reason: no-row` — precisely this bug's user-visible symptom — and named no cause. It now names this one, notes its distinguishing signature (every node at once, not one), and points at the gate.
- **Test-file duplication.** The spec repeated the `keyFromEntry`/`compare` lambdas at each `Tree.open` call site and hand-rolled the "it must exist" assertion. Extracted `keyOf`, `compareKeys` and an `openCommitted` helper whose doc comment carries the "the tracker must start empty, so `createOrOpen` will not do" constraint — which also blunts the implement handoff's worry that someone would tidy the test into using the shared `openHandle` and make it pass for the wrong reason.

### Checked and found clean (no action)

- **`contextAdvanced`'s inference from `advanceContext`.** The handoff flagged this as the load-bearing inference. `advanceContext` returns early when the read learned nothing, and again when the read revision is lower than the held one, so after it runs the adopted revision is at or above the prior one; "different" therefore does mean "advanced". A same-revision context with a different `committed` list reads as no advance, which is right — no new commits. The prior context is captured off `this.source` while `bootstrapContext` writes only the local `source`, so the capture is not disturbed.
- **Whether a log read can return entries with no context and so skip the advance.** `Log.getFrom` returns a context only when it saw a head entry revision, and that revision is set for any non-empty entry list. There is no "entries landed but the cursor did not move" hole.
- **The guard surface, which the handoff asked to be attacked hardest.** A replay that did not previously happen now re-runs `enforceUpsertGuard` and `assertEntryUnchanged`, so the question is whether some action is now refused that used to reach commit. Worked through both guard kinds and the answer is that neither refusal is newly reachable. For `unchanged`, the guard's expected-entry image means the staging handle read the entry, so its own staged write rewrites that entry's leaf — and a rival that changed the same entry rewrote the same leaf, which already conflicted. For `absentRange`, the guarded range must be free of foreign entries at staging time, so it lies wholly between two adjacent existing keys and therefore inside one leaf; a rival's entry landing in that range lands in the same leaf the staged upsert writes, which again already conflicted. The widening is a strict improvement in *when* the decision is re-made, not a change in *what* it decides. `tree-guard.spec.ts` and the whole refusal spec pass.
- **The coordinator's blanket refresh.** `TransactionCoordinator.commit`'s retry loop refreshes every registered collection, so the widened gate makes it replay more. The worry would be a non-participant's guard refusal aborting an unrelated transaction's retry — the shape the `CollectionHeaderVanishedError` NOTE there already warns about. It is empty: `commitOnce` selects participants by `hasUnsyncedChanges()`, so any collection with pending actions is already a participant. For actual participants the extra replay is the documented intent — `docs/internals.md` section "Conflict replay re-makes the uniqueness decision (entry guards)" says the decision must be re-made against the newest adopted state, and the old gate skipped it on a clean advance.
- **The decision not to refresh the index tree in `deleteIndexEntries`.** The originating fix ticket asked for it; the implement stage measured the reasoning wrong and declined. Reviewed and agreed: it costs a refresh per maintained index per deleted row and only narrows the window (an entry a rival commits between that refresh and the sync is blind again), while the db-core rule closes the class. Not re-opened.
- **Storage-op budgets.** `index-backfill-cost.spec.ts` and `cold-apply-cost.spec.ts` print measured-vs-baseline inline and every figure matched across both full plugin runs here (`CREATE INDEX, committed-but-empty table` 255 ops, `re-attach on empty table` 98, `CREATE INDEX, 20-row table` 301).

### Recorded as a tripwire, not a ticket

- **The replay is now proportional to the pending queue on any revision-advancing refresh, not only a conflicting one.** A read taken mid-transaction while a rival keeps committing re-stages every action staged so far, on each such read. It does not move the storage-op budgets, because the replay's reads are served from `sourceCache` — which is why it is conditional rather than a defect. Parked as a `NOTE:` in `mustReplay`'s doc comment, with the direction to take if it ever bites (narrow the replay to the actions whose reads the adopted entries actually invalidated) and the explicit instruction not to narrow the gate back to conflicts.

### Not filed as tickets, deliberately

- **No major findings, so no new `fix/`, `plan/` or `backlog/` tickets were created.** The change is one widened condition behind an invariant that is now stated at the code site and in two docs, and the two shapes that escaped the old condition both have discriminating regression tests.
- **The db-core tests are two shapes, not a property test over shapes.** Whether there are actions-that-change-no-block beyond a missed delete was not enumerated. A delete is the only tree operation whose handler can miss and write nothing, so a generator over one known shape would buy little.
- **`deleteSchema`'s `catch` fallback stays untested.** Reaching it means making `tree.update()` throw deliberately, which would test the harness more than the code. It carries a `NOTE:` saying exactly that.

### Wall-clock, again not usable

The implement handoff already flagged the suite timing as noise; this pass agrees and adds data. Plugin suite: 3m09s and roughly 2m patched, 4m42s with the gate narrowed (implement stage), then 3m and 4m patched (this stage). The suite spins up two 3-node libp2p meshes with fixed convergence sleeps and that swamps the change. Read nothing into it either way; the op-counting specs are the signal.
