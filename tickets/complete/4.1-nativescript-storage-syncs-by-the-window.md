# NativeScript storage syncs by the window — complete

Second of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). The maintainer's decision (2026-10-15): phones relax by the cohort-size window like any other node. Implemented in `ticket(implement): nativescript-storage-syncs-by-the-window`; this review pass found no major defect and made the minor fixes listed below.

## What landed

- **`SqliteDb.transaction(fn, { synced })`** (`packages/db-p2p-storage-ns/src/db.ts`): the transaction protocol both wrappers run inside their mutex slot is one shared function, `runTransaction`. With `synced`, `PRAGMA synchronous = FULL` before `BEGIN IMMEDIATE` and `PRAGMA synchronous = NORMAL` after the commit or the rollback. The NativeScript plugin wrapper (`src/ns-opener.ts`) and the Node test driver (`test/node-sqlite-driver.ts`) both call it. The schema gained the one-row `durability_mark` table, additive to an existing database.
- **`SqliteBatchBackend`** (`src/sqlite-storage.ts`) replaces the per-write `SqliteStoreDriver`: a `BatchBackend` under the shared `WriteGroupDriver`, applying each write group as one SQLite transaction and deciding by `SyncDeadlines` (shared with the file backend) whether that transaction commits under `FULL` or `NORMAL`. The sync step is one synced transaction whose body runs the batch's writes if any, takes the cover of held batches under the connection mutex, and bumps `durability_mark` only when there is a cover to settle and nothing else was written. A failure latches the backend and rejects every covered `durable`. `durability` is `'power-loss'`.
- **`syncSqliteDb` and `bumpDurabilityMark`** (`src/sqlite-sync.ts`): the standalone sync, used by `SqliteKVStore.flush()` when the store wrote since its last flush, and by `loadOrCreateNSPeerKey` after writing a newly generated key.
- **`SqliteKVStore`** gained a dirty flag and a failure latch, so a failed sync refuses later writes and flushes while reads keep working.
- **Docs**: `packages/db-p2p/docs/storage.md` (driver table, deferring-backend sentences, the rule-3 paragraph, the write-orders sentence, the survival table, the kernel section), `docs/correctness.md` (§1.2 storage durability and Theorem 6's backend caveat), and the package README (close order, the synced transaction, the helper, the `durability_mark` row, what a crash loses).

## Review findings

**Read first, with fresh eyes:** the implement commit's diff in full, then every file in the package (`src/` and `test/`), the shared contracts it builds on (`WriteGroup`, `WriteGroupDriver`, `BatchBackend`, `SyncDeadlines`, `IKVStore` in `packages/db-p2p`), the file backend's key-value store for parity, the conformance suite's flush-then-reopen case, and the three docs the ticket touched plus the start-up line in `packages/db-p2p/src/libp2p-node-base.ts` that names what a backend survives.

**Checked by reading and running**, each against the window and failure contracts:

- The sync step takes the cover INSIDE the synced transaction, under the mutex, rather than before it as the plan's phrasing suggested. Confirmed this is the right placement: a cover taken outside the mutex could include a batch whose own `COMMIT` then fails, and the sync would resolve its `durable` over a rolled-back transaction. The cost, one empty synced transaction on `sync()`, the timer and `close()` when nothing is held, is four statements with no frame written and no disk wait.
- The `mustSyncNow` decision made before the mutex slot: a deadline that passes while the commit waits in line defers that batch, and its backpressure falls to the timer, which is due anyway. Accepted by the ticket; the class doc says so.
- Timer firing while a synced commit is queued ahead of it on the mutex: the commit takes the cover, the timer's step then runs on an empty cover. Correct, one redundant transaction, no redundant sync.
- Close ordering: `WriteGroupDriver.close` flushes strictly (which takes and disarms), then `backend.close()` runs the step once more; a timer that fired in between is queued on the mutex ahead of that second step, so by the time `storage.close()` resolves no transaction of this storage can run on the handle the host closes next. The conformance harness closes the storage before the handle on both cleanup and reopen.
- Latch semantics over a real `node:sqlite` connection: a sync that fails (the `FULL` pragma throwing) rejects the covered `durable` with `StoreFailedError` carrying the original fault, not a wrapper; the overlay still serves the unsynced write; every later write, flush and `close()` rejects; the deadline timer is disarmed; and the connection is left at `NORMAL`. Not previously verified for this backend; now a test (below).
- `runTransaction`'s restore of `NORMAL` after a rolled-back synced transaction, and after a committed one: both branches real, neither observable through the existing statement counters (they count the pragma, not the connection's state). Now two tests (below).
- The read-concurrency note on `NSPluginStatement.get`: its claim that no read of a batch's rows reaches the connection mid-transaction was true for point reads only. Listings (`rangeRevisions`, `listPendingActionIds`, `listBlockIds`) do reach the connection and can see the open transaction's uncommitted rows, but the driver merges the overlay over them, so the answer is the same either way, and a rolled-back batch latches the store. Benign; the note now says so precisely.
- `SqliteKVStore.flush()`'s dirty flag is cleared before the sync, so a write resolving during the sync is covered by the next flush whichever order the commits took. Correct under the `IKVStore.flush` contract (every write that RESOLVED before the call).
- The identity helper syncs only on the generate branch; an existing key is read without a sync. Correct.
- The start-up line naming what a backend survives is keyed on the `durability` value, so it reads `'power-loss'` for this backend with no change. No doc or source outside the ticket's list still names `SqliteStoreDriver` or describes NativeScript as unable to sync (grepped the tree outside archived tickets).
- `packages/upgrade-check` has no NativeScript fixture, so nothing there reads this backend's format; the format is unchanged in any case (same tables, same columns, one additive table).

**Minor, fixed in this pass:**

- The one-field `SyncStep` holder in `syncHeld` is a local `cover` variable assigned inside the transaction body (`packages/db-p2p-storage-ns/src/sqlite-storage.ts`).
- The `NSPluginStatement.get` note in `packages/db-p2p-storage-ns/src/ns-opener.ts` now distinguishes point reads (overlay-answered, never reach the connection) from listings (reach the connection, overlay merged over them).
- Tests added: *a failed deferred sync rejects the durables it covered and latches the store* in `test/sqlite-storage.spec.ts` (the harness gained `failSyncs`, which makes the `FULL` pragma throw); *restore NORMAL after the commit* and *restore NORMAL after a rollback too* in `test/sqlite-transaction-serialization.spec.ts`, reading `PRAGMA synchronous` back. 65 tests pass.
- Tests cut: none. The implementer's three window and key-value tests each pin a branch of the deadline logic, and the retargeted serialization tests pin the mutex over the real connection.

**Major:** none found. The transaction placement, the cover bookkeeping, the latch, and the docs all hold under the scenarios above.
