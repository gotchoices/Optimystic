# NativeScript storage moves to `@nativescript-community/sqlite` 4.x

GitHub #38 (kjeib), also gotchoices/sereus#45 point 3. `@optimystic/db-p2p-storage-ns` now declares the plugin at `^4.1.0`, not `^3.5.0`. A host has to move to 4.x in the same upgrade.

## What shipped

- **Production behaviour: one line.** `openOverPlugin` in `packages/db-p2p-storage-ns/src/ns-opener.ts` awaits `raw.ready`, so a failed open states its own failure instead of through the first statement's rejection.
- **Types and comments.** `NSPluginDb` and `NSPluginModule` describe the 4.x shape and are exported for the test driver, not from `src/index.ts`. The reasons for keeping the connection mutex and for not using the plugin's `db.transaction` are on `NSPluginDbWrapper`.
- **The test driver runs production code.** `test/node-sqlite-driver.ts` is now a stand-in for the plugin over `node:sqlite`, whose every call runs later and in the order made, handed to the real `openOverPlugin`. The suite therefore exercises the production wrapper, mutex and transaction protocol with other callers running between a body's statements. It does not model the plugin's value encoding or a real second thread, and the plugin itself is never loaded.
- **Docs.** The README, `docs/optimystic.md` and the release note, including the iOS bare-name move and what was and was not tested.

## Device evidence, and what is owed at release

Nothing in this repository runs NativeScript. The only device evidence is the reporter's run of this package at 1.20.1, unmodified, on plugin 4.1.0 (Galaxy S7, Android 8.0, NativeScript 8.9). **Not run by anyone:** a long session with real network traffic, iOS, the Node-API binding NativeScript 9.1+ selects, and a power cut. The README and the release note both say so.

**Owed at release, by a human:** ask the reporter to re-run their probe (`src/sqlite4-check.ts` in their app) on the release, and answer GitHub #38 and gotchoices/sereus#45 point 3.

**Heads-up:** `yarn install` rewrites the `cost_profile` `options` array in `packages/quereus-plugin-optimystic/package.json` into multi-line form, because Yarn normalizes the manifest's JSON. It is unrelated to this ticket and was put back by hand, so the next person to run `yarn install` will see the same diff.

## Review findings

Read the `ticket(implement): feat-nativescript-storage-moves-to-sqlite-4` diff first, then the handoff.

**Checked against the plugin's published source.** The review downloaded 4.1.1 and 3.5.9 from npm and read their JavaScript and type declarations, since the implementation's claims rested on that source and nothing in the repository loads it. This is reading, not a run on a device. All of these held:

- `openOrCreate` returns at once, and `ready` rejects on a failed open (`sqlite.js` and `database.js` in `sqlite-core`).
- `close()` is idempotent, refuses new calls at once and runs what is queued; `get` answers `null` for no row.
- Blobs decode to a copied `Uint8Array` (`u8.slice`), and integers decode to plain numbers unless the `int64` option is set (this package does not set it), so `row.rev as number` and the `instanceof Uint8Array` in `identity.ts` hold.
- A JavaScript integer binds as an integer rather than a double (`codec.js`).
- The `*Sync` methods throw when the backend has no `execSync`, and in the JavaScript of `sqlite-core` only the Node-API backend defines one. The bridge package's native code was not read.
- The umbrella package depends on `sqlite-core`, `sqlite-bridge`, `sqlite-napi` and `sqlite-default-engine`. The default engine is a bundled library with WAL on for Android, and the process's SQLite with no WAL default on iOS, which is why `journal_mode = WAL` stays in `applySchema`.
- Bare-name paths: 4.x uses `getDatabasePath` on Android and the documents folder on iOS; 3.5.9's iOS `getRealPath` returns the name unchanged and its Android path opens through the activity. The release note's iOS warning matches this.

**Found and fixed in this pass (minor):**

- **`wrapNSPluginDb` did not accept the plugin's own database type.** Compiling a call with the plugin's `Database` declaration failed, because `params?: ReadonlyArray<unknown>` is not assignable either way to the plugin's `SqliteParams`. `openOptimysticNSDb` hid this behind its cast, but this function is the public entry for a host holding a handle. The three parameters are now `SqliteParam[]`, and the same compile passes. The check was a one-off outside the repository, since the plugin is deliberately not a dependency, so nothing pins it from now on.
- **Stale statements in files the change touched:** the `db.ts` header said only `openOptimysticNSDb` is exported, when `wrapNSPluginDb` and the types are too; the README called the React Native package MMKV-based, when it uses `rn-leveldb`; `connection-mutex.ts` and the serialization spec said a second `BEGIN` nests, when SQLite refuses it.
- **Formatting:** re-wrapped the `runTransaction` comment and the README's install paragraph, which had an overlong line.

**Major findings:** none, so no ticket filed.

**Tripwires:** none added. The two the implementation added stand: a failed schema leaves the connection open (`openOverPlugin`), and results over 512 KiB on the JNI bridge (`NSPluginStatement.all`). No accepted-tradeoff `NOTE:` bears on these findings.

**Tests.** No test added and none cut.

- Replacing `ConnectionMutex.serialize`'s chaining with an immediate run failed both tests of the "SQLite transaction serialization" group, and was then restored, so the stand-in does expose the race.
- `test/ns-opener.spec.ts` pins a case the rest of the suite cannot reach, so it stays. The implementer reported that removing `await raw.ready` fails it; the review confirmed that by reading the test, not by running that mutation.
- The 10 ms `settles` race in `sqlite-storage.spec.ts` was read for flake risk under the slower stand-in. Its `false` case waits on a timer nobody fires, and its `true` case waits on durability the earlier `await`s already established, so neither should depend on statement timing.

**Interactions, by reading:** the read paths in `sqlite-storage.ts` and `identity.ts` and the sync in `sqlite-sync.ts` were considered against reads now landing between a transaction body's statements. The overlay reasoning in the `NOTE` on `NSPluginStatement.get` holds, and the reporter measured the behaviour. Statements inside a body still bypass the mutex, so there is no new deadlock.

**Dependents and docs:** no workspace depends on this package (`git grep` of the manifests). `packages/upgrade-check/readme.md` names it only to say how far that suite covers it. `packages/db-p2p/docs/storage.md` and `docs/correctness.md` describe its durability through SQLite's write-ahead log, which this change leaves alone, so they needed no edit.

**Not checked:** anything on a device, as above; the plugin's native sources, including the 512 KiB arena and the 51,200 global-reference limit in the JNI tripwire, which come from the implementation's reading and the reporter's report.

**Verified after the fixes:**

- `yarn workspace @optimystic/db-p2p-storage-ns build`: clean, specs included.
- `yarn workspace @optimystic/db-p2p-storage-ns test`: 67 passing.
- `yarn lint:deps` and `yarn lint:docs`: clean.
- Not run: `yarn check`, or any other package's tests, since nothing else depends on this package.
