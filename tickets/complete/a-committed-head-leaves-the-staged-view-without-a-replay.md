## What was built

Each action staged into the open segment records the transforms its handler staged and what it accepted as already applied (`StagedUnit`). A seal folds the units' deltas into one under the tracker's own semantics (`foldTransforms`) and sums the tallies, so a sealed segment carries `SealedSegment.delta` with no rebuild; every replay records every delta again under the ids it mints and bumps the collection's replay epoch first. A head attempt is built from the head's delta (`Collection.headTrackerFromDelta`: a tracker over the read cache with a copy of the delta and the live tracker's pins for the blocks it updates, re-judged like any head tracker), falling back to running the handlers when the delta is not on record, a pin under it has moved, or the collection holds no committed revision. A committed head built that way, in the same epoch, is subtracted (`Collection.subtractCommittedHead`): the blocks its delta touched are forgotten by the live tracker and re-folded from the remaining segments' and open units' deltas in order (`Tracker.refold`), with an update-only block pinning the cache's revision as it is now; otherwise the old full replay runs, each outcome logged with its reason. Snapshots carry the open units and the replay epoch, and a restore over sealed segments after a replay takes the replay arm.

The implement handoff's design deviation stands: one immutable unit per action in the open segment rather than a shared accumulator, with the fold at the seal, so nothing staged is ever changed in place and a snapshot shares units by reference.

## Measurements

Reported by the implement ticket on the offline commit-cost bench (`packages/quereus-plugin-optimystic/test/offline-commit-cost.bench.mjs`, solo libp2p node, Node 24, Windows, N=200): drain cost per entry flat at about 6 ms across queues of 100, 200 and 400 where it was 65 to 106 ms and growing with the queue; back-to-back offline commits with a file journal 12 to 17 ms throughout a run instead of climbing from 12 to 76; a commit waiting for its own send about 9 ms against 8 ms online. All-sent with the file journal came in at 22 ms against a target of about 20; what remains is the journal's three flushes per entry and the send. Not re-measured in review.

## Review findings

**Read first, with fresh eyes:** the whole implement diff (`collection.ts`, `segments.ts`, `tracker.ts`, `atomic.ts`, `helpers.ts`, the three specs, both docs), then the handoff.

**Checked by reading, no defect found:**

- `foldTransforms` and `Tracker.refold` against `Tracker.absorb`, `Tracker.insert`, `Tracker.delete` and `Tracker.stageUpdate`: delete removes the insert and the updates and lists the id; insert replaces the block, takes the id off the deletes and leaves a stale update list; an update of an inserted block is applied into a copy. The three agree. The stale-update-list case the handoff asked about is the malformed state the `tryGet` note already describes and is not reachable from the tree (block ids are random, nothing re-inserts a deleted id); matching `Tracker.insert` is right, since the delta must fold the way the live tracker absorbed it.
- The pin argument of `Tracker.refold`: the live tracker's pin for a block the head updates is the base of the head's own operations (earlier segments have already been subtracted or were refused and never staged), so copying it into the head tracker is the same base; after the fold, a remaining update-only block pins the cache's revision, which now includes the head. Pin objects are shared by reference between the live and head trackers, the same sharing `BasePins.copy` already relies on, so a moved mark set on one is a fact about the same operations.
- The pre-read in `subtractCommittedHead` is necessary: `CacheSource.transformCache` applies updates into a resident block only and leaves an evicted id's revision entry at the old revision, so without the read the re-fold would pin a base storage would refuse on every attempt. The cache keeps the served revision even if the read is evicted again, so the pin is right either way; only the digest goes undeclared.
- The roll-over `NOTE:` at `subtractCommittedHead`: a header updated by the attempt's log append and not by the head's delta leaves a later segment's header pin judged moved, and `mustReplay`'s moved-base reason replays at the next refresh. At most one replay per roll-over is an upper bound: a scratch run of the property spec with 40 queued entries, so the log rolled over mid-drain, subtracted all 40 heads with no replay, since no remaining segment held a header update at that moment. The scratch spec was deleted.
- `restorePending`'s replay-epoch arm: a verbatim restore with nothing sealed restores units whose deltas name the captured transforms' ids, which is consistent; with a segment sealed, a replay since the capture means the captured ids are not the segments' recorded ones, and the replay arm is right. Every other site that sets the open segment (`consumedFromOpen`, `filterAgainstEntry`, `unstage`, the slice in `syncAttempts`, `unseal`, `restoreSealed`) either keeps a unit with the delta that still matches the tracker or puts the action back with no delta and forces the replay that records it.
- Error paths: a throw mid-`replayActions` leaves later units with no delta (the `NOTE:` there), which every reader takes as "stage again"; `subtractCommittedHead` answers `false` with nothing changed when any delta is missing; a refused segment's stale delta is never read because `stagedDeltas` visits replayable segments only.
- The below-floor case: a touched block the cache hands through unkept is re-read by the pre-read and pinned at the served revision; if a lagging machine still serves it below the commit, storage's base guard refuses the next attempt and the refresh's moved-base replay recovers, the same path the sync takes under the accepted tradeoff at `TransactorSource.mayRetain`.
- Docs: `docs/internals.md` (the head-commit bullets, the snapshot rule, the clone and share tables) and `docs/offline-sync.md` (the head tracker paragraph and the failure-modes bullet) describe the code as it is. `yarn lint:docs` clean.

**Minor, fixed in this pass:**

- `Collection.replayActions` rebuilt the open segment's unit array from scratch after every re-staged action, which was quadratic in the open segment's length. It now sets one array and records each unit in place as its action is re-staged; a throw still leaves the units behind it with no delta.

**Major, filed:** `backlog/bug-a-folded-head-stays-in-the-live-tracker-across-an-await`. `Collection.applyCommittedToCache` states the invariant that the fold into the cache and the removal of the folded operations from the live tracker are one synchronous step. The pre-read in `subtractCommittedHead` awaits between them when a touched block was evicted under a later segment's update, and an unlatched read in that window applies the head's operations twice. The same window already exists on the coordinator's per-entry commit for every participant after the first, which folds all and then awaits each replay in turn, so this is filed as one ticket with two arms rather than an instance; `repro: static`, with the confirming test named. A `NOTE:` at the pre-read points at it.
