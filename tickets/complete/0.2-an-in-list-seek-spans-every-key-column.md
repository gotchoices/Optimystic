## What landed

Landed in `ticket(implement): an-in-list-seek-spans-every-key-column`. Quereus 5.4.0 fixed the composite multi-seek arm of `selectPhysicalNodeFromPlan`, which used to seek a bound `=` beside an `in` on `Literal(undefined)`. With that fixed, the plugin's planner now claims an `in` on any key column:

- `matchEqualitySeek` runs through every leading key column that has an equality-role filter. Its `keyCount` is the product of the columns' key counts. So `a = ? and b in (…)` over `(a, b)` seeks both columns, and an `in` that covers every column of a composite primary key plans a `_primary_` multi-seek instead of a scan.
- `MAX_MULTI_SEEK_KEYS` is 1000, the same value as the store module's constant of that name. After the first column, a column that would take the product past it ends the match and stays a residual. The first column's own list is never capped, and a single-valued column never ends the match.
- `seekTuplesOf` splits `args` into tuples of the `seekWidth` that `idxStr` names. It refuses a width that is not a positive integer or that does not divide the argument count.

## Review findings

**Read the implement diff first**, then checked it against the engine's composite arm in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`.

- **Engine contract (correctness):** checked, nothing found. The engine picks each seek column's constraint as the first `=` or non-empty `IN` among the handled filters. That is the same filter `firstEqualityRoleFilter` claims, because a `runtimeSet` is never claimed. The engine flattens the cross-product column-major with width `seekCols.length` and passes `seekWidth` in `idxStr`, which matches how `seekTuplesOf` slices `args`. When every tuple has a NULL in a literal list, the engine returns an empty result, so the plugin sees zero args, which divides by any width. A dynamic list leaves NULL-bearing and duplicate tuples to `seekKeysInTreeOrder`, which drops and collapses them. A capped plan claims only the first column and lands in the engine's single-column multi-seek arm, the path that existed before this change.
- **`equalitySeekKeyCount` returning 0 or null:** cannot happen here. It returns `null` for an empty list, and `firstEqualityRoleFilter` already rejects `null`, so the `!` in the product is sound and no product can collapse to 0.
- **Interactions with the other candidates:** checked, no regression. `rangeSeekCandidate` declines any match whose key count is not 1, and any range column that carries an `in`. So every shape this change lengthens was already declined for a range before it. A partial primary-key match, including one ended by the cap, offers no `_primary_` candidate, as before. A multi-seek still reports no ordering and no set.
- **Cap semantics (raised by the implementer):** I agree with them. Stopping before the column that crosses the cap still gives a correct, cheaper plan: a seek with a residual above it. Declining the whole candidate, as the store module's cost-only branch does, would throw away a seek that is already good. Leaving the first column uncapped keeps the cost comparison that existed before this change.
- **Pricing (raised by the implementer):** without statistics, the equality constant is still charged once rather than per key. That is a decision already recorded in the existing `NOTE:` in `equalitySeekCandidate`. Its revisit condition has not tripped, so I left it alone.
- **Docs:** read README.md, docs/debugging.md and docs/internals.md. The README and debugging.md were updated and are accurate. internals.md does not describe which equality shapes seek, so it needed nothing. **Minor, fixed:** the doc comment on `equalitySeekCandidate` still said "one per listed value of a multi-seek". It now says "one per combination of the listed values".
- **Tests:** every new test meets the bar.
  - The `claimsAll` assertion pins the behaviour this ticket changes. It would fail against the old planner, which left the trailing column as a residual.
  - The composite-primary-key block is the only end-to-end test of a width-2 `seekTuplesOf` on the primary key. It also covers a value that is a prefix of another (`x`, `xa`) and a bound NULL.
  - The cap cases in the planner unit test pin the two branches of the cap rule.
  - Nothing was cut and nothing was added.
- **Source hygiene:** the comments state constraints rather than narrating the code, and the stale `NOTE:` about the engine defect was removed along with the `isMultiValueEquality` import. No new size concern: the diff is net-smaller in `optimystic-module.ts`.
- **Error handling and type safety:** a malformed width throws `INTERNAL` rather than seeking on the wrong values, which is right: the engine has already dropped the predicate the seek replaces. There are no new casts beyond the existing `SqlValue[]` cast at the tuple constructor.
- **Tripwires:** none filed. None of the concerns found depends on a future condition.
