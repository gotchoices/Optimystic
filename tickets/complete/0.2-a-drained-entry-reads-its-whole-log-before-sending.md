description: Each offline transaction sent to the network used to re-read the collection's whole history first, so sending got slower the more had ever been written. A write's refresh now stops after one read request when the log tail shows nothing newer, as a reader's already did.
architecture: docs/internals.md#quereus-vtab-read-path--pull-on-read-is-shape-independent

GitHub #53 reported the cost of offline commits; this is the one term that grew with the collection's total history.

## What changed

`Collection.updateInternal` takes the early exit (`Collection.tailShowsNothingNewer`) whether or not a write is in flight. The opening refresh of `Collection.commitHead` and `TransactionCoordinator.commitEntry`, and a retry's refresh, cost one read request instead of a walk back to the first log block when the tail shows nothing newer.

The implement stage kept the walk for a refresh with a retained attempt. Review removed that (see findings).

## Review findings

Checked by reading `Collection.updateInternal`, `Collection.readLogEnds`, `Log.getFrom`, the `CacheSource` seed, the retention sites, `OfflineQueue.recordAttempts`, and the coordinator's commit span, then running the suites below.

**Major: none. Minor, fixed in this pass:**

- **The kept in-flight condition rested on a false premise.** The implement stage kept the walk for a refresh with a retained attempt, because skipping it "rests on the tail read being current, a retry is when a lagging coordinator has been in the picture, and missing the entry loses the write"; the plan rejected dropping the condition for the same reason. But the walk starts from the same tail block: `updateInternal` seeds its cache with `ends.served`, and `Log.getFrom` steps back from that tail. When `tailShowsNothingNewer` holds, the tail has no `nextId`, its newest entry is at the held revision and earlier blocks hold lower revisions, so the walk finds no entries, whatever the true state of the log. A lagging tail hides the entry from both. What actually deals with a lagging answer is the tail floor a retry's read carries, plus the re-send of the same attempt when the refresh finds nothing (`resumedAttempt` on a head commit, the byte-identical rebuild on a sync; docs/offline-sync.md already lists "nothing new, and the recorded attempt re-sent" as an outcome). The walk's other effect, a replay over a moved base, is done before every attempt by `Collection.restageIfBasesMoved` and `Collection.headTrackerFor`. So the condition only added a whole-log read per retry. Removed it, along with the safety argument's dependence on the `retainInFlightAttempt` contract, and corrected the comment, the coordinator comment and `docs/internals.md`. The ticket's "for the reviewer" point about a throwing send is settled by the same reasoning: with or without a retained attempt, the tail test decides.
- This reverses the plan's "Rejected" decision. It is a one-line revert if someone finds a case the reasoning above misses.

**Happy path, edge cases and error paths (no defect):**

- Own entry landed and visible: the tail shows it above the held revision, so the refresh walks and finishes it. Pinned by `coordinator-own-action-replay.spec.ts`, `own-entry-completes-the-action.spec.ts`, `offline-restore.spec.ts` and `collection-segments.spec.ts`, all green with the condition removed.
- Reader's refresh while a head commit has the latch released: if the commit landed, the tail shows it and the walk reaches the `headInFlight` deferral, as before.
- Committed sibling in a partial commit: the held revision is the entry's own, so the refresh stops at the tail test.
- Fork: `tailShowsNothingNewer` still refuses a held context that disagrees with the tail's entries.

**Resource and performance:** the early exit does not call `keepLogEnds`, so it does not re-seed the handle's cache; the comment on `keepLogEnds` already records that an LRU eviction costs one fetch there. Reads/txn stayed flat in the bench. Nothing else to clean up.

**Tests:** kept the implementer's one case in `refresh-read-cost.spec.ts`: it is a named budget on branching logic and failed at 7 requests on the original code. Nothing cut. None added, since the removed condition had no behaviour to pin beyond the read count, and landed-entry recovery is covered by the specs above.

**Docs:** read `docs/internals.md` and `docs/offline-sync.md`. Updated the former. The latter's account of the opening refresh's three outcomes is correct and unchanged.
