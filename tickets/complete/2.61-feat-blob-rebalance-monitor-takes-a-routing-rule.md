# The rebalance monitor takes a routing rule

`RebalanceMonitor` (`packages/db-p2p/src/cluster/rebalance-monitor.ts`) compares, for each tracked id, the cohort it finds now with the one it remembered, and reports `gained` / `lost` / `grown`. It was tied to blocks by one call (`routingKeyForBlock` in `cohortFor`) and a module-level logger. Both are now injectable (`RebalanceMonitorDeps.routingKeyOf`, `RebalanceMonitorDeps.logName`), so `feat-a-referenced-blob-is-copied-to-its-cohort` can build a second instance over held blob references.

It also gains `RebalanceMonitor.retainLost(id)`: a reaction that could not confirm a `lost` id's release calls it, and the next check reports the id in `lost` again with its current `newOwners`, while the id stays tracked and this node stays outside its cohort. One call buys one re-report. The call arms the re-check timer so the re-report happens on a quiet network. Blocks do not use it (backlog `bug-a-block-kept-after-a-failed-handoff-is-never-offered-again` asks whether they should). Block wiring in `libp2p-node-base.ts` is unchanged.

Docs: `docs/internals.md` §RebalanceMonitor ("Ids other than blocks") and `docs/blobs.md` ("When the cohort changes") describe the new inputs and `retainLost`.

Test: `RebalanceMonitor › checkNow › re-reports a lost id once per retainLost call` covers the one new branch, and checks that `newOwners` is recomputed rather than remembered.

## Review findings

Read the implement diff (`ticket(implement): feat-blob-rebalance-monitor-takes-a-routing-rule`) before the handoff.

- **Correctness of the `lost` branch.** `!isResponsible && (wasResponsible || prior.releasePending)` sits after the `gained` branch. The non-responsible state is rebuilt by `emptyGrowthState(false)`, which consumes the flag. A regain goes through `carryGrowthState` (flag cleared) and is reported `gained`, which is correct. Nothing to fix.
- **Race between `retainLost` and a running check.** Checked: for each id, `prior` is read and `responsibilitySnapshot.set` runs with no `await` between them. A `retainLost` that lands during that id's `cohortFor` await is seen through `prior`. One that lands after it sets the flag on the new state, so the flag survives. Checks are serialized. No window loses the flag. Nothing to fix.
- **`hasOutstandingWork` rewrite.** For the growth arm it gives the same result as the old predicate. It also counts a retained release on a tracked id. Nothing to fix.
- **Partition suppression or a failed lookup** leave the state untouched, so the flag carries over to the next check that runs. This is consistent with how growth state is handled.
- **Lingering snapshot entry after an external `trackedBlocks.delete`** (raised by the implementer). The entry is inert while the id is untracked. Re-tracking it while it is still outside the cohort reports one extra `lost`, which the reaction checks again anyway. I agree it is harmless and left it alone. No tripwire was added, because the existing "lingering entry is inert" comment on `responsibilitySnapshot` already covers this shape.
- **Minor, fixed:** `cohortFor` evaluated `deps.routingKeyOf ?? routingKeyForBlock` on every lookup. It now resolves once in the constructor into `private readonly routingKeyOf`.
- **Logger.** The `'rebalance-monitor'` literal stays in the `createLogger` call, so the namespace scan in `test/logger.spec.ts` still sees it. The blob instance's `'blob:copy'` row in `docs/debugging.md` belongs to the blob ticket that creates that instance. The ticket handoff already says this, and the scan cannot catch a namespace that is not a literal.
- **Diagnostics.** `getGrowthDiagnostics()` does not count retained releases, and `recheckArmed` can read `true` because of one. This is acceptable, and the blob ticket can add a counter if its log line needs one.
- **Tests.** The single added test pins the one new branch and the recomputed `newOwners`. It earns its place, so it stays. No test was added for the `routingKeyOf` or `logName` pass-throughs: they have no branching, and the blob ticket's reaction tests will build an instance with them.
