## What was built

- **`StampId` is registered fresh** (`plugin.ts`): `FunctionFlags.UTF8 | FunctionFlags.FRESH`, with a comment at the registration stating the same-transaction caveat (every call in one transaction answers the same value; two rows inserted under it collide sequentially and the pre-stage probe refuses the second before anything is queued).
- **`write-description.ts` (new, pure)** — `WriteFact` (`{ kind: 'fresh', collectionId, key }`), `freshElementsOf(write, arm, row)` and `foldWriteFacts(records)`, plus, from this review, `TransactionWriteFacts` and `emptyWriteFacts()`, the one home of the record shape a transaction state starts with. `freshElementsOf` takes the staging arm (`'insert' | 'update'`) because the upsert `DO UPDATE` arm receives the INSERT's description and must record nothing. Column names are compared lowercased.
- **`commit-outlook.ts`** — `EntryFacts` (`fresh: ReadonlyMap<CollectionId, ReadonlySet<string>>`); `facts` on `JudgedTransaction`, `EarlierEntry` and `FollowedEntry`. `CollectionJudge` takes the collection's fresh keys: `absent` is not exposed when the tag or the facts say the key is fresh, `absentRange` likewise with the index entry's tree key. `WriteIndex.insertedFresh(collectionId, key, description)` replaces `insertedAbsent`: a `Map<key, byFacts>` merged with OR across the entries that inserted the key, which the `unchanged` rule asks. `unchecked` stays `'not-computed'`.
- **`TransactionBridge`** — `TransactionState.writeFacts` (`types.ts`), fresh per transaction; `noteWriteFacts`, `openWriteFacts`; `createSavepoint` marks the record count ahead of the session-mode return, `rollbackToSavepoint` truncates to the mark and drops marks above the depth ahead of the snapshot check, `releaseSavepoint` drops marks at and above the depth. `sealIntoQueue` passes `openWriteFacts()` to `OfflineMode.enqueue`.
- **`OfflineMode`** — `entryFacts: Map<transactionId, EntryFacts>`, set by `enqueue(collections, id, facts)` before `queue.enqueue` (the `queued` status, and so the judgement, fires inside it) and deleted in a `finally` when nothing was queued; read by `judgeQueued`, `queueAhead`, `followedEntry`; `openTransactionOutlook` reads `bridge.openWriteFacts()`; deleted with the judgement on a terminal status. A restored transaction has none.
- **vtab** — `wantWriteScope = true` in the constructor with a tripwire `NOTE:`; `guardedUniqueConstraints(values)` is the one walk `guardedUniqueIndexes` and `recordWriteFacts` both read; `recordWriteFacts(write, arm, rowKey, values)` is called after the last stage of the fresh INSERT path, the INSERT OR REPLACE-in-place path and the UPDATE arm (never DELETE), keying each unique entry as `indexEntryKey(createIndexKey(descriptor, values), rowKey)`, the formula `IndexManager` stages under. The two hand-built `TransactionState` literals in the module go through `transactorOnlyState`.
- **Docs** — docs/offline-sync.md §What the analysis needs from Quereus rewritten as what shipped; §Judging each guard's fresh bullets rewritten around the two sources (provenance, tag) with a bullet on where the facts come from and the savepoint rule; stage 8 marked shipped, stage 9 in progress; §Test plan brought current. README § Offline mode: what counts as fresh, the `StampId()` caveat, the `hex(randomblob(16))` spelling, and "a restart forgets where values came from". docs/internals.md: one sentence in the plugin-offline paragraph.

## Two things the ticket asked for that the facts did not allow

- **`randomblob(16)` written bare to a `text` key cannot be pinned as exposed.** Quereus 4.21.0 labels it `fresh` on a table with no blob column while the executor stores a lossy text decode of the bytes; the plugin trusts the label by design. Filed as `tickets/blocked/quereus-labels-a-fresh-blob-written-to-text-as-fresh.md` with the proposed upstream fix; the unit spec pins the lossy-wrapper shape Quereus's doc and behaviour agree on (`cast(randomblob(16) as text)` → not fresh). The caveat is stated in docs/offline-sync.md and the README.
- **`StampId()` in an autocommit INSERT is NULL** (pre-existing: the VALUES row is evaluated before the write begins the bridge's transaction). The SQL-level tests use explicit transactions and say why; the defect is on the board as backlog `bug-stampid-is-null-inside-an-autocommit-insert`.

## Review findings

Read the implement diff first, then every touched source and doc file, Quereus 4.21.0's `write-scope.ts`, `value-provenance.ts`, the DML executor's handling of `writeScope` (statement-level savepoints, the upsert arm, cascade writes) and its docs/write-scope.md, and `IndexManager`'s key formulas.

**Checked and found right (no change):**

- Every staging path records facts after its last stage and only on paths that stage: the IGNORE and swallow returns stage nothing and record nothing; a cascade child write has no description; the upsert `DO UPDATE` arm receives the INSERT's object and the `operation !== arm` guard drops it (confirmed in Quereus's `dml-executor.ts`, which passes the INSERT's `writeScope` into `executeUpsertUpdate`).
- The fact's key for a unique entry equals the key `insertIndexEntries` and `updateIndexEntries` stage the NEW entry under; the main-tree key is the staged `insertKey`/`newKey`. Confirmed by reading `index-manager.ts`, and now pinned end to end (test added below).
- Facts follow savepoints correctly in the unsafe direction: Quereus wraps every DML in a `__stmt_atomic` savepoint broadcast and rolls it back on failure, the mark is taken at the top of `createSavepoint` (so never later than the data snapshot), truncation runs ahead of the snapshot restore, and the per-depth dedup matches the snapshots' so facts are truncated at least as far as rows are reverted. In session mode, where a savepoint rollback restores no data, truncating facts only makes the verdict more conservative.
- Cleanup parity: `entryFacts` is deleted exactly where `judgements` is (terminal status), plus on a failed or empty enqueue; nothing else creates a facts entry, so no map grows past the queue.
- The OR fold in `WriteIndex.add` changes no verdict (the literal re-inserter is exposed and every later writer of the key depends on it); the window after a fresh inserter commits, where a rival can change the row before the dependent drains, is the residual the design already documents for the tag rule, not a new one.
- A multi-row VALUES, `insert … select`, a column default of `StampId()`, and an UPDATE assigning a key or unique column all classify the way the plugin assumes; Quereus labels a mixed multi-row column `other`, so the plugin never credits one row on another's source.
- Docs: docs/offline-sync.md, the README and docs/internals.md describe the shipped behaviour; `yarn lint:docs` resolves every citation.
