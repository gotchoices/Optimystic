Part of stage 1 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages): the "Validity rejection" row of the classification table now has a typed error at the writer.

## What landed

A fourth returned refusal, `RejectedFailure`, sits beside `StaleFailure`, `ExpiredFailure` and `ShortfallFailure` in `WriteFailure` (`packages/db-core/src/network/struct.ts`). It carries `TransactionInvalidity` (`{ refusals: ValidityRefusal[] }`, never empty), where each `ValidityRefusal` is the per-vote `ValidityRejection` class plus the refusing member's `peerId` and `reason`. It is decided by `isRejectedFailure` and raised as `ValidityRejectedError` (`packages/db-core/src/network/validity-rejected-error.ts`). Every sibling shape got `rejected?: never`; `isConflictFailure` is false for it. The aggregate is named `TransactionInvalidity` rather than the plan's `ValidityRejection`, because the marker ticket already uses that name for the per-vote class.

- **The coordinator's rule** — `validityRejectionOf` in `packages/db-p2p/src/repo/cluster-coordinator.ts` classifies a rejected record only when every reject is a validity vote or an expiry vote and at least one is a validity vote; the refusals are the validity votes alone. It rides out on `ValidatorRejectionError.validity`, and the `cluster-tx:rejected-by-validators` log line gains an `invalid` count.
- **Where it is returned** — `CoordinatorRepo.pendThroughCluster`'s catch returns it after the expiry, shortfall, conflict, held and stale-confirmation arms; anything else still throws. A cohort of one returns it from `StorageRepo.pend` when the check's verdict carries `validity` (one refusal, no `peerId`). Commit records never meet it.
- **Writer consumers** — `refusalFrom` ranks rejected > expiry > shortfall > stale; `Collection.syncAttempts` stops on it with `ValidityRejectedError`; `TransactionCoordinator` carries it through `pendRefusalError`, `pendFailure` and `CoordinationResult.rejected`, and `commit()` throws it by name.
- **Dispute ticket arm** — `tickets/backlog/1.5-dispute-writer-sees-disputed-pend.md` records what the dispute work must do about the new shape and its precedence.

Tests: `packages/db-p2p/test/validity-rejection-classification.spec.ts` (four cases on the pure rule), and `packages/db-p2p/test/mesh-client-signature-enforcement.spec.ts` updated so its four signature-refusal cases assert the returned `RejectedFailure` end to end on a real mesh; its `pend-not-validatable` and `validator-fault` cases stay the thrown control.

## Review findings

Read the `ticket(implement): offline-sync-typed-validity-rejection` diff first, then traced every path a `RejectedFailure` can take.

**Checked, no defect found:**

- *Coordinator catch ordering* (`CoordinatorRepo.pendThroughCluster`): the validity arm sits behind `classifyStaleRejection`, so a revision loss this node confirms still rebases. The all-expiry `TransactionExpiredError` is only thrown when no validity vote exists, so the two arms cannot both apply.
- *Remote members' storage refusals*: a member's own `StorageRepo.pend` returning `RejectedFailure` after pend-consensus never reaches the writer through `cohortPendRefusals`, because `conflictPendRefusalOf` keeps conflict-shaped refusals only; the coordinator's own one stays the tolerated `localPendResult` divergence the implementer noted.
- *Solo cohort* (`CoordinatorRepo.pendSolo` → `applyPendsInOrder`): stops at the first refusal, so the answer is the one `RejectedFailure` untouched.
- *Network transactor*: `processBatches` re-picks a coordinator only on a throw, so a returned rejection is not re-sent elsewhere; `NetworkTransactor.pend` cancels every batch before returning the rebuilt refusal, so approving members' reservations are released.
- *Coordinator write path*: both the per-collection fan-out and `pendTogether` funnel through `pendRefusalError`/`pendFailure`; `staleLoss` cannot be true beside a rejection (it needs every reason to be a conflict), and `commit()` checks `rejected` before `expired`, matching `refusalFrom`. `execute()` reports the message only, which is its existing contract for every failure.
- *Type safety*: the `never` fields on each sibling keep unnarrowed reads compiling; `validityRefusalOf` reads the wire defensively the way `expiryClockOf` does.
- *Tests*: the pure four-case spec pins the named rule's branches (marked, marked + expiry, marked + unmarked, all-expiry) and earns its place; the mesh spec covers the `ClusterCoordinator` → `CoordinatorRepo` mapping end to end. No test was added for the writer stop arms or `refusalFrom` precedence — the shortfall and expiry arms have none either, and each is a one-line branch beside them; I kept that judgement.
