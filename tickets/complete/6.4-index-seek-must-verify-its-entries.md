## What landed

`executeIndexScan` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` used to fetch each index entry's row by primary key and yield it without asking whether that row still implied the entry it came from. Nothing downstream re-checked it: `getBestAccessPlan` claims each matched equality filter as `handledFilters=true`, and quereus reattaches a residual predicate only for a claimed constraint the seek did **not** consume, so whatever the scan yields is the answer. Four wrong answers followed from that one missing step, and all four are closed.

**The verification.** Every entry is checked against the row it resolves to, and the check is the full one: an entry is `[treeKey, primaryKey]`, the row it resolves to implies exactly one tree key (`indexEntryKey(createIndexKey(schema, row), primaryKey)`), and the two must be equal. That is `rowImpliesEntry` in `schema/index-manager.ts`, beside `indexEntryKey`, and the integrity check's `classifyEntry` now answers its own question with the same function — a seek and the check can no longer disagree about what an entry means. Checking the whole entry rather than the seek's prefix is also what closes the duplicate: on a seek narrower than the index, a moved row's two entries both prefix-match, and only one can equal its full implied key.

**The NULL guard.** A `null`/`undefined` seek arg produces no rows, and it sits *above* the key framing on purpose: `indexKeyFromValues([null])` frames a perfectly valid NULL-tag key that really does find the NULL-keyed row, and the verification would not reject that row either. Only refusing to seek is correct. Same guard and reasoning as `executePointLookup` already carried.

**Supporting changes.** `IndexManager.findEntriesIn` yields whole `IndexEntry` values over `indexValueRange(indexKey)`, with `findByIndexIn` as a projection of it, so there is still one range definition. `IndexSeekProbe` gained `rejected`, printed on the `index:seek` trace line. `readRowAt` (module scope) is the single "fetch the decoded row this primary key names" for both the point lookup and the index scan.

**Deliberately not fixed:** `probeUniqueConstraint` still treats every entry in a value's range as a live collision, so a leftover entry can still make a value look taken. That is `bug-stale-index-entry-causes-false-unique-refusal` in `backlog/`, and three prose sites name it so the read/write asymmetry does not read as an oversight.

## Review findings

### Verified, no defect (what was checked and came back clean)

- **The premise of the whole ticket.** Read `reattachUnconsumedConstraints` in `../quereus/packages/quereus/src/planner/rules/access/rule-select-access-path.ts` directly: it reattaches a residual filter only for a claimed constraint the rule never consumed. A consumed equality gets none. The fix is required, not defensive.
- **Can the verification reject a HEALTHY entry?** This was the main correctness worry, because entries are staged from the *raw* quereus row while the verification re-derives from the *decoded* row — so the check now leans on encode/decode round-trip fidelity for every indexed column, where previously a divergence only produced an orphan on a later UPDATE/DELETE. Probed empirically (throwaway script, deleted) over an indexed `blob` column, an indexed `real` column (`0.1`, `1e300`), and an indexed integer past `Number.MAX_SAFE_INTEGER` reached both as a literal and as a bound `bigint`: every seek returned the right row and `verifyIndexes` reported zero discrepancies. `serializeIndexValue`'s bigint→number unification and `denormalizeValue`'s `$bigint` restore are what hold it together. No finding.
- **Does the NULL guard over-reject?** Probed `is null`, `is not null`, `= ?` bound to NULL, `= null` literal, `in (...)`, `= 'a' or Tok is null`, and a correlated join seek on a NULL-bearing outer column. All correct — `is null` still returns the NULL rows (it routes to a scan, since `getBestAccessPlan` claims only `=`), and the join yields no match for the NULL outer row. No finding.
- **Is the guard's scope (`args`, not `args.slice(0, width)`) safe?** The handoff flagged this as reasoned-but-uncovered. It is sound for a stronger reason than the handoff gives: `args` only ever carries values for comparison constraints in the conjunction, and *every* comparison against NULL is UNKNOWN, so an empty result is right whatever the excess arg belonged to. No finding.
- **`classifyEntry`'s refactor** from a tree-key map lookup to a primary-key row lookup plus the shared predicate: checked the malformed-entry case (stored primary key disagreeing with the tree key's primary-key half) reaches `malformed` on both the old and new shape. Behaviour-preserving, and `index-integrity-check.spec.ts` passes unchanged.
- **Every other reader of the index tree.** `findByIndexIn`'s only production caller is now `probeUniqueConstraint` (ticketed, out of scope); `allEntriesIn` serves the integrity check and must *not* verify; `scanIndexRange` and `findByIndex` have no callers. No second unverified seek path exists.
- **The stale documentation sweep is complete.** Grepped every phrasing of the false "Quereus re-applies the predicate" claim across `docs/`, `src/` and `test/` — zero remaining. (`docs/review.html` is an archived review artifact, not maintained prose.)

### Fixed in this pass (minor)

- **`rejected=` was documented as proving index damage. It does not.** An `arm=live` scan refreshes the index and main collections through different call sites — `docs/debugging.md` already says "the two trees can be sitting at different moments" — so an index tree ahead of the main table yields an entry whose row the main view has not caught up to, and the scan rejects a perfectly healthy entry. Four sites asserted flatly that any rejection means the tree disagrees with its table, which would send an operator hunting damage that is not there. All four now say the index and the main table disagreed *as this scan read them*, name both causes, and point at the `rev=`/`main_rev=`/`arm=` fields on the same line that separate them: the `IndexSeekProbe.rejected` doc and the `logIndexSeek` field list in `optimystic-module.ts`, the `rejected=` bullet in `docs/debugging.md`, and `IndexSeekTrace.rejected` in `test/trace-helpers.ts`.
- **The "row is gone" rejection arm had no end-to-end test.** The property spec exercised only the moved-row (`stale-value`) damage; `readRowAt` returning `undefined` — the arm the just-fixed `blind-index-delete-is-logged-but-never-applied` produces — was covered only by the integrity check, never through a seek. `index-seek-correctness.spec.ts` now runs each shape a third time over an index whose row was deleted with delete-side staging patched away (`stageNothing`), asserting exactly one `no-row` orphan first so the arm cannot pass vacuously. The two damaged-run preambles are factored into one `expectOneOrphan` helper. 947 → 950 passing.
- **Doc drift from the `findByIndexIn` → `findEntriesIn` rename.** Five references still attributed the query seek to `findByIndexIn`, one of them plainly false (`scanIndexRange`'s NOTE claimed "only findByIndexIn is wired to query planning"). Corrected in `index-manager.ts` (`indexKeyFromValues`, `asIndexColumnTuple`, `findByIndexIn`, `allEntriesIn`, `scanIndexRange`) and `test/index-support.spec.ts`. `findByIndexIn`'s own doc now says who actually calls it and that its caller still miscounts a leftover, with the ticket slug.
- **`seek=unset` needed its common cause named.** Before this ticket the only way to print `unset` was a missing codec; now it is overwhelmingly the NULL-arg refusal, which is a *correct* empty answer. Said so in the `IndexSeekProbe.key` doc and the `seek=` bullet in `docs/debugging.md`, so `matched=0 rejected=0 seek=unset` does not read as a fault.

### Tripwire recorded, not ticketed

- **The verification proves entry↔row agreement, not entry↔seek-key agreement.** Those coincide only because `indexValueRange` is an exact byte-prefix bracket: the index tree is opened with a raw lexicographic string comparator, so every entry the range yields has a tree key literally beginning with the seek key. If `debt-optimystic-true-key-ordering` ever gives the index tree a collation-aware comparator, the range can bracket entries framed under a *different* value, whose own rows imply them and which this check would therefore pass. `NOTE:` at the verification site in `executeIndexScan`, naming the fix (also prefix-check the derived key against `indexKey`) and the ticket that would trip it. Conditional today, so not a ticket.

### New tickets filed

None. Every finding was either fixed inline or is conditional. The one known live defect in this area — the unique-enforcement probe counting a leftover entry as a collision — already has `bug-stale-index-entry-causes-false-unique-refusal` in `backlog/`, whose body I extended with one sentence pointing at `rowImpliesEntry` now existing as a shared predicate, since all three options that ticket asks a human to choose between need exactly that question answered.

### Considered and declined

- **The handoff's remaining "known gaps" were checked and left as they are.** The unreachable `width === 0` branch is correctly framed and its reachability argument re-verified by reading `getBestAccessPlan`, `runQuery` and quereus's `filter-info.ts`; a test for it would have to call a private method past the planner, which buys nothing. `rejected` being populated only when the trace namespace is enabled matches `matched` and is the probe's existing design, not a hole this ticket opened.
- **`findByIndex` and `scanIndexRange` are dead code** (no callers at all, pre-existing). Deleting public methods is outside a review pass's remit and neither is misleading now that their docs are accurate. Noted here rather than filed.
- **Size debt.** `optimystic-module.ts` measured at **4611** lines (`wc -l packages/quereus-plugin-optimystic/src/optimystic-module.ts`), up from 4530 at the previous review. `debt-optimystic-vtab-class-is-too-big-to-review` already claims this file; appended the re-measurement and this review's evidence for the split rather than filing anything new.
