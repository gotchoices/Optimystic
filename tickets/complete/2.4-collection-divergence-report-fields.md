# Divergence report fields — complete

Diagnostics only. No behaviour change: nothing new throws, nothing new is adopted or dropped, and
every added computation sits behind the existing `log.enabled` gate. The parked question (should a
detected divergence drop the read cache or throw?) stays parked with
`backlog/more-design/6.5-partition-healing`.

## Final line shapes

```
collection:context-short-of-tail   id=… tag=… before=… after=… tail=…
collection:context-not-lowered     id=… tag=… site=… heldRev=… readRev=… heldAction=… readAction=…
collection:lineage-divergence      id=… tag=… site=… forkRev=… heldAction=… readAction=… heldRev=… readRev=…
```

Across all three, a `*Rev=` field is always a revision number and a `*Action=` field is always an
action id.

- `tag=` — the reporting handle's `instanceTag`, so several handles on one collection id stop
  reading as one handle contradicting itself.
- `site=` — `refresh` (a live `update()`: this handle's copy against the stored log — indicts a
  forked replica) or `attach` (open: the tail block's claim against a walk of its own chain —
  indicts storage).
- `forkRev=` / `heldAction=` / `readAction=` on the divergence line — `Collection.earliestFork`
  scans both `committed` lists and reports the LOWEST revision they both name an action for and
  disagree at, plus the two ids there. A fork below the current revision used to be silent.
- `heldRev=` / `readRev=` / `heldAction=` / `readAction=` on the refusal line — the two revisions,
  and what each side names as the action **at the read's revision**.

## Review findings

### Major — fixed in this pass (one code site, correctness of the diagnostic itself)

- **`context-not-lowered` compared action ids taken at two DIFFERENT revisions.** As implemented it
  printed `actionIdAt(current, current.rev)` against `actionIdAt(next, next.rev)`, and the branch it
  sits in only runs when `next.rev < current.rev` — so the two lookups were always at different
  revisions. On one honest, merely-lagging lineage those ids necessarily differ (different revisions
  hold different actions), and both the code comment and `docs/debugging.md` told the operator that
  different ids mean "a fork being sealed underneath this handle". Every ordinary lagging read would
  therefore have been reported as a fork — the exact confusion the field pair was added to remove.
  Fixed by looking BOTH sides up at `next.rev`, the only revision the two are comparable at. Docs
  and the pinned-tail test updated to match; a new test (below) pins the honest-lag case.
- **Field names meant two different things on one namespace.** `held=`/`read=` were revision numbers
  on `context-not-lowered` and action ids on `lineage-divergence` — adjacent lines in the same
  capture, including in the doc's worked example. Renamed so `*Rev` is always a revision and
  `*Action` always an id: the refusal line's `held=`/`read=` became `heldRev=`/`readRev=`, and the
  divergence line's `held=`/`read=` became `heldAction=`/`readAction=`. Done now rather than later
  because no downstream run has yet consumed the new shapes.

### Minor — fixed in this pass

- `advanceContext`'s doc block still opened by describing the old single-revision comparison ("the
  action id held at the CURRENT revision must equal…") and corrected itself thirty lines later.
  Rewritten to state the actual rule once.
- `earliestFork`'s return shape was an inline object literal written out twice (signature and
  accumulator). Extracted as `LineageFork`, with the field names the log line prints.

### Gaps the implementer flagged — closed

- **Refusal path with the namespace off.** New test `refuses to move backwards with the debug
  namespace off` disables `debug`, refreshes a handle whose read walks backwards, and asserts
  `committedRevision()` did not drop. This was the real gap: the `return` that enforces monotonicity
  now sits one `if (log.enabled)` block away, and every other test here runs with logging on.
- **The `none` placeholder was untested.** It is now the asserted value in the pinned-tail refusal
  test: a context bootstrapped from an over-claiming tail names nothing at the read's revision, so
  `heldAction=none` — which is also the case where `lineage-divergence` is structurally silent (no
  shared revision), and the docs now say so.
- **`forkRev=` as an upper bound was undocumented.** `docs/debugging.md` now states it plainly: only
  revisions both sides still list are comparable, so a split older than the read log's most recent
  checkpoint is reported at the lowest surviving disagreement rather than at the true split point.

### Checked and found correct — no action

- **`log.enabled` gating.** Both the `earliestFork` scan (Map build + two list walks) and the
  refusal line's two `actionIdAt` lookups are inside `log.enabled` guards; the refusal `return`
  itself is outside, and is now tested with logging off. Only two callers of `advanceContext` exist
  (`updateInternal`, `attachToLog`), both diagnostic-gated.
- **`site=` discriminates.** `attach` is emitted only from the open path and `refresh` only from
  `update()`; both are pinned by tests. `createOrOpen`'s *create* branch emitting nothing is right —
  an invented collection has no context and no log to compare against, and `collection:invented`
  already reports that case.
- **No other consumer of these line shapes.** Grepped the repo: only `docs/` and the db-core spec
  reference the field names. The historical captures quoted in `docs/debugging.md` and in
  `backlog/more-design/6.5-partition-healing` are left in their as-captured form deliberately.
- **`bootstrapContext`'s over-claiming-tail `NOTE:`** is an accepted tradeoff with a stated revisit
  condition ("if an over-claiming tail is ever observed in the field"). Not tripped; not re-filed.
  The refusal line's `heldAction=none` is now documented as that situation's signature.
- **Comment length in `advanceContext`.** Long, but consistent with the surrounding file's idiom;
  trimmed only where it contradicted itself rather than rewritten wholesale.

### Known limits accepted, not filed

- **`forkRev=` as an upper bound is documented but untested.** Constructing a fork whose split
  revision has fallen off the read side past a checkpoint needs checkpoint-truncation test
  machinery that does not exist here; the claim is read off the code and now stated in the docs.
- **`site=attach` is only ever exercised through a test double that lies about storage.** Inherent
  to testing a storage-corruption diagnostic in-process.
- **Field ORDER is load-bearing for the tests** — each assertion parses one regex over the whole
  line. Left as is: the lines are a documented format, and the regexes read as a check that the
  documented shape is what ships.

### Tripwires

- Existing `NOTE:` in `Collection.earliestFork` (a `committed` list with two entries at one revision
  would be a defect in its own right; the Map keeps the last arbitrarily) — still accurate after the
  rename, left in place.
- No new tripwires. Everything else found was either fixed here or is a stated limit above.

## Handoff carried forward

Unchanged by this review, and still the point of the ticket: the downstream fork's mechanism was
never reproduced in-repo (`tickets/blocked/secondary-index-repro-exhausted-upstream`), and the

settles it is a downstream (`sereus`) run carrying them:

- `lineage-divergence` with `site=refresh` and two distinct `tag=` values on one collection id →
  the fork is a replica problem and commit interleaving is back in scope.
- `site=attach`, or one tag with `forkRev=` at or near the collection's first revision → the finding
  belongs to the genesis-cohort family tracked by `backlog/more-design/6.5-partition-healing`, where
  an arm was already appended.

Until that run happens, neither branch can be closed from inside this repo. One reading note for
whoever gets that capture: after this review, `heldAction`/`readAction` differing on a
`context-not-lowered` line is real evidence of a second lineage, not lag — before it, it was not.
