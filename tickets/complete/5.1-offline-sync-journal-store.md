Stage 5 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages), part two of three: the key-value journal behind db-core's `IOfflineJournal` port. Reading the journal back after a restart is part three (`offline-sync-journal-restore`, in `implement/`, whose "Notes from part two" section lists what it needs from this code — notably that a restored entry's `seq` must be registered with the journal, or its first drive-record write throws).

## What was built

- **Registration** (`parseOfflineConfig`, `offline-config.ts`): `offline.journal` — an `IKVStore` or a factory called once inside `register`, checked by shape, a `MemoryKVStore` refused — and `offline.journalLabel` (lowercase letters, digits, `_`, `-`; default `'default'`; refused without `journal`).
- **The journal** (`OfflineJournal`, `offline-journal.ts`): three records per transaction under `optimystic-offline/<label>/` — `entries/<seq12>` (written and flushed at enqueue; taken back on a failed write), `drives/<seq12>` (flushed before each send, after a partial commit and after an identity renewal), `outcomes/<transactionId>` (flushed at a terminal outcome; then the other two deleted, unflushed, even when the outcome write throws). `encodeOutcome` / `decodeOutcome` round-trip an outcome, losing `followed` and the error's class and cause.
- **`OfflineMode`** builds the journal, reports `persisted` on the `queued` status and on `entries()`, deletes outcome records on `acknowledge` and on retention pruning (fire-and-forget, logged), and translates each terminal status once (`journalOutcome` → `outcomeOf`), so `onCommitDurability` fires once per drained commit.
- **db-p2p**: `OFFLINE_JOURNAL_KEY_PREFIX` in `NODE_KV_NAMESPACES`; `PowerLossKVStore` (crash double for `IKVStore`) in `@optimystic/db-p2p/testing`.
- **Tests**: `packages/quereus-plugin-optimystic/test/offline-journal.spec.ts` — record layout and lifecycle over a table and its index, a store that throws at enqueue, a crash after the drain committed, a crash after one refused send, two labels over one store, registration refusals, the outcome codec round trip.

## Review findings

Read the `ticket(implement): offline-sync-journal-store` diff first, then the queue side it plugs into (`OfflineQueue`'s `journalQueued`, `recordAttempts`, `journalDriving`, `journalSettled`, `committed`, `remove` in `packages/db-core/src/offline/queue.ts`), the bridge's `reportCommitDurability` and `tablesOf`, `FileKVStore`'s key-to-path mapping, and how transaction ids are minted.

**Fixed in this pass**

- **Two labels that differ only in case collided on disk.** The label rule allowed `[A-Za-z0-9_-]`, and `FileKVStore` maps each key segment to a directory, so on a filesystem that ignores case (Windows, macOS by default) `One` and `one` shared one directory — the two-`Database`s-one-label corruption the docs warn about, reachable by labels the plugin had accepted as distinct. The label is now lowercase-only (`JOURNAL_LABEL` in `offline-config.ts`, separate from `JOURNAL_KEY_SEGMENT`, which keeps mixed case for transaction ids). Updated the config type's comment, the error message, README § Offline mode, docs/offline-sync.md §Registration, and added one assertion (`'Main'` refused) to the existing registration-refusal case.
- **`JOURNAL_KEY_SEGMENT`'s comment** said the label shared its shape; reworded to cover transaction ids only, and to say why mixed case is safe for them on a case-ignoring filesystem (each `generateStampId` id carries 128 random bits).

**Checked and sound**

- Transaction ids are always key-safe: `generateStampId` is base64url. Session mode's `stamp:<hash>` ids contain `:` and would fail the check, but offline mode refuses to run beside session mode (`TransactionBridge.beginTransaction`), so they never reach the journal.
- Write ordering against the port's contract: `queued` flushes before resolving and its throw unseals and fails the enqueue (pinned by the store-throws case); `driving` flushes before each send; `settled` writes the outcome before the queue emits. Every terminal emission in the queue (`committed`, `remove`) goes through `journalSettled` first, so `journaledOutcomes` is always consumed by the status that follows; only a dispose between the two can strand one entry, which is harmless.
- `onCommitDurability` now fires before the outcome record is flushed rather than at status delivery. A crash in between leaves the entry record, so after part three's restore the commit is reported again — the restart semantics the docs already state. Not a defect.
- The take-back after a failed entry write, and the `finally` deletes in `settled`, match docs/offline-sync.md §Write ordering. One nit left as is: if the first delete in `settled`'s `finally` throws, it replaces the outcome write's error and skips the drive delete; the queue only logs either error, and an orphaned drive record without its entry record is inert.
- Outcome deletes on `acknowledge` / prune are unflushed and fire-and-forget; a lost one only lists the outcome once more after a restart, as documented.
- `PowerLossKVStore`: refuses everything after `powerLoss()`, never idle-flushes, `reopen()` guarded — matches its documentation and the crash cases' needs.
- Docs: README, docs/offline-sync.md (§Registration, §What is journaled, §Write ordering, §Restore after a restart, §Outcomes after a restart, §Which store, §Implementation stages, §Test plan), docs/internals.md §The offline queue, and the fs README / `FileKVStore` namespace comment all describe the code as built. `yarn lint:docs` clean.
