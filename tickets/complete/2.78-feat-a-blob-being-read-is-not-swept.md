# A blob being read is not swept — complete

Landed as `ticket(implement): feat-a-blob-being-read-is-not-swept` plus this review pass. It closes the fifth way a piece can be live while a sweep decides: a read or fetch running against a blob whose last hold has already gone. Nothing takes the last hold off a blob on its own today, so the hole was not reachable in practice; `feat-blob-cached-copies-stay-within-a-budget` (now in `implement/`) makes it reachable, and its record door already declares the `inUse` call this ticket added.

## What shipped

**A use count on `LocalBlobService`** (`packages/db-p2p/src/blob/local-blob-service.ts`). A private `uses: Map<BlobRef, number>` with three public members over it: `inUse(ref)`, `inUseRefs()` and `beginUse(ref): () => void`. `beginUse` raises the count and returns a release that lowers it and deletes the entry at zero; the release captures a `released` flag, so a second call cannot lower another holder's count. It is synchronous and takes no gate, which is what lets it be the first statement of a generator body, before any `await`. `readThrough` takes a use as its first statement and releases it in a `finally`, delegating the read itself to a new private `readChunks`; `LocalBlobService.fetch` holds one around its body.

**The sweep takes those refs as extra roots** (`packages/db-p2p/src/blob/piece-sweeper.ts`). `PieceSweeperDeps.inUseRefs` is required, so the one construction site would be a compile error without it. `walkRecord`'s tree walk is split out as `walkTree`, and a new `walkInUse` walks every in-use ref with no record required, inside the exclusive gate in `decideAndDelete` — after the re-walk of `changed` and before `inProgress`'s ids, the latest point at which the sweep reads anything, so every use taken before the deletes begin is seen.

**The networked service holds uses too** (`packages/db-p2p/src/blob/node-blob-service.ts`). `fetch` holds one around its whole body, so a blob being brought here is in use from before its first piece; `startSession` takes one when a session starts and releases it when `session.done` settles either way, which covers the tail where a read has consumed its whole range and returned while its session is still confirming what it brought and marking the record whole.

`BlobAnnounceReceiver` needs no use: it writes and flushes the `responsible` hold (`announce-receiver.ts:156`) before it starts its pull (`:250`), so that blob has a hold of its own throughout.

One test, in `packages/db-p2p/test/local-blob-service.spec.ts`: `put` 300 KiB (two data pieces and a list root), `unpin` so the record is gone and the pieces remain, take the read's first chunk, then `sweep()` — `deleted: 0, kept: 3`, the rest of the read yields the original bytes, and a second `sweep()` after the read finishes deletes all three.

## Review findings

### Found and fixed in this pass

- **The sweep's new root source accepted strings the old ones could not** (`piece-sweeper.ts`, `walkInUse`). Every other root reaches the walk already checked — `BlobRecordStore.listRefs` filters with `isBlobRef` and logs `record:bad-key`, and `changeRecord` calls `parseBlobRef` before `noteRecordChange` — which is the invariant the existing test `a change refused for a string that is not a reference leaves a running sweep unharmed` pins and the comment at `blob-record-store.ts:84` states. `inUseRefs` had no such filter, and `walkBlobPieces` throws on a non-canonical spelling (`pieceKind` → `cidOfPiece` parses it), so a read or fetch of a cast non-reference in flight during the decide phase would return `tree-unreadable` and the sweep would delete nothing. Reachable only by an in-repo cast and only inside one sub-millisecond window (a bogus ref fails the read at its first store lookup), and the next sweep recovers — but the guard is four lines and retires the class, so `walkInUse` now skips a ref that is not a reference and logs `sweep:use-not-a-reference`. No test: no public path reaches it deterministically, `PieceSweeper` has no construction site a spec could inject into, and a test for the race would have to drive the sweeper's internals.
- **Docs the change should have touched and did not.** `docs/debugging.md` enumerates every event in the `blob:store` namespace, so the new log line is listed there; and that entry's account of `sweep:aborted` — "every later sweep stops at the same blob until its record is fixed or the blob unpinned" — was no longer true for the refs this ticket adds, where there is no record to fix and no pin to drop and the remedy is the read ending, so it now says that. In `docs/blobs.md` the §Holds bullet list grew its fifth entry in the implement pass, but the one-line summary above it ("a piece is deleted only by a sweep that finds it in no held blob's tree") did not absorb it; it now names the trees something is reading as well.

### Parked as a tripwire, not a ticket

- **A blob in use with no record can stop a sweep the way a held blob with a damaged tree can.** `walkInUse` aborts on `tree-unreadable` exactly as `walkRecord` does — the keep-everything direction the accepted-tradeoff `NOTE:` above `walkRecord` already chose — but the remedy differs: a held blob is unpinned, while an in-use one simply stops being in use when its read ends. Fine as it stands, and self-healing, unless the use itself leaks (below), in which case sweeps stay stopped. `NOTE:` at `walkInUse` naming that pair as the explanation if sweeps are ever seen aborting `tree-unreadable` on a ref no record names, plus the operator-facing half in `docs/debugging.md`.
- The implement pass left one tripwire of its own, at `LocalBlobService.beginUse`: an async iterator abandoned without `return` never runs the `finally`, so its blob stays out of every sweep for the life of the process. Read and kept as written.

### Checked and sound

- **Every public read and fetch reaches a use.** Enumerated rather than taken on trust: `LocalBlobService.read` → `readThrough`, `readThrough` itself, `LocalBlobService.fetch`, both branches of `NodeBlobService.read` (`from: 'here'` → `local.read`, otherwise `readFetching` → `local.readThrough`), `NodeBlobService.fetch`, `startSession`, and `SingleMachineBlobService.read`/`fetch`, which delegate. The sessions `BlobAnnounceReceiver` starts on the fetcher directly are hold-covered instead, verified by the write order above. Serving a piece to a peer (`NodeBlobService.storedPiece`) stays outside, which is the pre-existing exposure its own `NOTE:` records.
- **`beginUse` really is before any `await` at both generator sites** — including `readFetching`, whose own preamble (`new AbortController`, `forwardAborts`) is synchronous, so the use is counted on the first `next()` and a read created but never iterated counts nothing.
- **The map counts by value, not by identity.** `BlobRef` is a branded string (`packages/db-core/src/blob/blob-ref.ts:9`) in one canonical spelling, so two reads of one blob share a key and the count is the number of readers.
- **`inUseRefs()` snapshots into an array** rather than handing the sweeper a live `Map` iterator, which is what keeps `beginUse` during the walk's awaits from perturbing the iteration; the dep's `Iterable<BlobRef>` type would have allowed the live one.
- **Release arithmetic and idempotence**, and `walkInUse`'s placement inside the exclusive gate — including that `await walkHeld(…) ?? await walkInUse(…)` skips the second walk only when the first already aborted.
- **`inUse` having no caller is planned, not speculative.** `tickets/implement/2.8-feat-blob-cached-copies-stay-within-a-budget.md` declares it on the budget's record door and checks it twice: once in `chooseEvictions` and again immediately before each write.
- **Walking a ref twice** (in use and holding a record) is idempotent, and the cost is one extra tree walk of a blob someone is reading right now. Left alone.
- **Source hygiene.** Largest touched file is `local-blob-service.ts` at 776 lines (`wc -l`), well under the ~1700-line mark this repo's size tickets use; `piece-sweeper.ts` is 295 and `node-blob-service.ts` 441. The new comments state why (why `beginUse` is gate-free, why the session's use covers the tail) rather than narrating statements, and the `readChunks` split is the right shape for keeping the use visibly first.
- **Weighed and declined:** `beginUse`'s counted map repeats `InProgressPieces`'s "increment, delete at zero" idiom, about six lines, in another file with another key type and another release shape (a closure rather than `release(iterable)`). A shared generic helper for two short instances would cost more indirection than it saves; a third instance would make the case on its own, so no `NOTE:` — there is no condition to trip, only a judgment.
- **Tests.** The implementer's one test earns its keep: it reproduces the exact hole the ticket names, at the lowest layer that reproduces it, through public API only, and was verified to fail (`deleted: 3`) with `inUseRefs` stubbed empty. Nothing in the diff restates the implementation or verifies a mock, so nothing was cut. Nothing was added beyond it: the release flag, the count arithmetic and `startSession`'s release are straight-line code behind behaviour that test already covers, and a test for `inUse` alone would test a getter — the budget ticket's own spec pins it in use.

### Nothing found

No major finding, so no ticket filed and nothing routed to `blocked/`: the remaining known gaps are either pre-existing accepted exposure (a use taken during the delete phase, which is the same window as reading a blob with no hold at all, and which `beginUse` cannot close without becoming `async` and losing the before-any-`await` property), parked tripwires, or free.
