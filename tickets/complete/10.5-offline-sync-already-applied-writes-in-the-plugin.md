The design as written up is [§Guards that make idempotent writes assured](../../docs/offline-sync.md#guards-that-make-idempotent-writes-assured); the site-by-site table is the "Which guard each statement carries" paragraph of docs/internals.md.

## What was built

**The gates** (`insertAcceptsEqualRow` and `rewriteAcceptsEqualRow` in `packages/quereus-plugin-optimystic/src/optimystic-adapter/write-description.ts`): pure over Quereus's `TableWrite` and the arm. An INSERT at a clear key admits `absentOrEqual` when the disposition is `ignore`, `replace`, or an upsert with a `do nothing` clause whose target is `'primary-key'` or the primary-key columns as a lowercased set. A rewrite (same-key UPDATE on the `update` arm, INSERT OR REPLACE over an occupied key on the `insert` arm) admits `unchangedOrEqual` when the description is of that arm and `selfIndependent`. No description, or a description of another operation (the upsert `DO UPDATE` arm receives the INSERT's), answers false.

**The staging sites** (`update()` in `packages/quereus-plugin-optimystic/src/optimystic-module.ts`): `insertGuard` chooses `absentOrEqual` when the gate holds or the table is tagged `"optimystic.content_key" = true` (`CONTENT_KEY_TAG`, read `=== true` at staging beside `optimystic.single_writer`); `rewriteGuard` chooses `unchangedOrEqual` or `unchanged` for the same-key UPDATE and the INSERT OR REPLACE over an occupied key; the DELETE and each secondary-UNIQUE eviction's delete (`applyUniqueEvictions`) always carry `unchangedOrAbsent`; both halves of a primary-key move keep their base kinds. `recordWriteFacts` shares the primary-key column names with the gate through `primaryKeyColumnNames`.

**The effect**: `QueuedTransactionStatus`'s `committed` arm carries `effect: CommittedEffect` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-status.ts`); `OfflineMode.committed` passes the queue's `effect` through; the journal's `PersistedOutcome` carries `effect?` and `decodeOutcome` answers `'applied'` for a record without it. The `onCommitDurability` report is unchanged.

**The outlook** (`packages/quereus-plugin-optimystic/src/optimystic-adapter/commit-outlook.ts`): `CollectionJudge` judges `absentOrEqual` as `absent` and the two `unchanged` variants as `unchanged`; the cover rule counts all five exact-key kinds; `writtenKeysIn` counts an `absentOrEqual` insert among `insertedAbsent`; `Exposure` gains `tolerates?: 'same-change'`, set on every exposure a variant produces, and `renderCommitOutlook` includes it when present.

**Docs**: docs/offline-sync.md (§Following transactions, §Judging each guard, §Declared hints, §Guards that make idempotent writes assured, §Implementation stages, §Test plan, §Outcomes after a restart), docs/internals.md ("Which guard each statement carries", with the site table and the online consequence), and the plugin README (the `committed` bullet's `effect`, a paragraph on accepted same changes, and the tag table's `optimystic.content_key` row).

## Behaviour change outside offline mode, deliberately

The variants are a property of the statement, not of the mode, and session mode stages through the same `update()`. So an online racing identical write now commits where it refused: two transactions deleting one row both commit, the second's delete skipped as already applied. The DELETE-vs-DELETE case of `packages/quereus-plugin-optimystic/test/concurrent-row-change-refusal.spec.ts` and the racing oracle of `packages/quereus-plugin-optimystic/test/two-node-index-mutation-sweep.spec.ts` pin the new behaviour. Every other same-row race still refuses, since the rivals' changes differ.

## Review findings

**Read first, before the handoff:** the implement commit's full diff over the six source files, the seven specs and the three docs, then Quereus's `selfIndependent` contract in the sibling checkout's docs/write-scope.md, the db-core handler's three variant arms in `packages/db-core/src/collections/tree/tree.ts`, and the surrounding `update()` arms in `packages/quereus-plugin-optimystic/src/optimystic-module.ts` (the REPLACE branch, the UPDATE arm's move guard, the DML catch, `followSchemaTags`).

**Checked, by reading and by running:**

- **Happy path and edge cases of each gate.** `selfIndependent` in Quereus means every written value's provenance is `literal`, `input`, `fresh` or `volatile`, so a `volatile` `set stamp = now()` passes the gate; two machines then write different stamps, the rows differ, and `unchangedOrEqual` refuses as `unchanged` would. Conservative, not wrong. The upsert `DO UPDATE` arm could in principle admit the variant (Quereus's flag covers DO UPDATE assignments too), but the plugin's arm receives an `insert` description and keeps `unchanged`; conservative, left as is. `targetsPrimaryKey` on a singleton table (`primary key ()`) answers true only for a bare `on conflict do nothing`, which is right.
- **Index coherence under an already-applied main-table element**, traced for: a same-key UPDATE that moves an indexed value (pinned end to end with an index on `done`); INSERT OR REPLACE over an occupied key with an index on the replaced column (pinned by the case added below); an eviction's delete when the rival already deleted the evicted row, including under a primary-key move (by inspection: the displaced entry's index deletes find nothing, and a rival that deleted the row and re-inserted its unique value under another key still refuses through `absentRange`, as before). Nothing resolves last-writer-wins.
- **The tag's lifetime.** `insertGuard` reads `optimystic.content_key` from `this.tableSchema.tags`, which `followSchemaTags` replaces on every `table_modified` and which `hydrate` rebuilds from the catalog record, the same path `optimystic.single_writer` takes, so `alter table … set tags` and a restart both take effect.
- **`effect` on every path a `committed` status takes.** `OfflineMode.committed` has one caller, `translateOutcome`, which covers the live drain and the journal's restored outcomes; `encodeOutcome` writes it and `decodeOutcome` defaults a pre-field record to `'applied'` (pinned). `followOutlooks` compares outlook `kind` only, so the new `tolerates` field cannot cause a spurious `outlook-changed`.
- **The affected-row count a statement reports online** comes from staging, so a DELETE skipped at commit as already applied still reported one row; the docs state this and call it acceptable (the final state is the statement's intent). Agreed.
- **Validation run after the review's edits:** `yarn workspace @optimystic/quereus-plugin-optimystic build`, `yarn typecheck`, `yarn lint`, `yarn lint:docs`, and `yarn workspace @optimystic/quereus-plugin-optimystic test`: 1175 passing, 14 pending (the handoff's 1173 plus the content-key case it ran standalone plus the case added here). The integration specs were not run; nothing here touches the network layer.
