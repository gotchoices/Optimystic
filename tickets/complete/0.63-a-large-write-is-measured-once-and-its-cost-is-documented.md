# A large write is measured once, and its cost is documented

Last of the four GitHub #63 tickets. Code changes are small; most of the work was the measurement and the docs.

## What was built

- **The coordinator measures a pend once per machine.** `CoordinatorRepo.pendMany` calls `assertTransactionFits` only when the pend did not come from this node's own `NetworkTransactor` (`MessageOptions.localWriter !== true`). That transactor measured the whole pend (`pend`) or the batch's sum (`pendMany`) before sending, and every per-coordinator request is a subset of what it measured (`pendRequestForBatch`), including batches re-homed by retries. A pend from another machine is still measured on receipt.
- **`Chain.takenBy` measures nothing that cannot change its answer.** It returns 1 at once for a lone entry offered to an empty block, and stops before measuring the next entry once a block holding an entry is at the target. Every decision is unchanged; a large append now measures the tail once instead of the tail plus the entry twice.
- **Docs.** docs/internals.md §A transaction's size limit gained *What a large value costs*: the bench (`packages/quereus-plugin-optimystic/test/large-value-commit-cost.bench.mjs`), a before/after table, what the expansion is made of, what fits in one transaction, where the CPU goes, and native blobs as the way to carry a value once. The *Backstops* bullet, the *What counts* bullet and the log roll-over paragraph were updated to match. docs/blobs.md §Why points at the new figures.
- **Backlog ticket filed:** `debt-a-log-append-carries-its-entry-once`. When an entry is appended to a log tail that already holds entries, the pend carries the entry twice: once for the append and once for the rewrite that fills in `blockIds`.

How the numbers were measured (a paired before/after worktree run, profiles, and pend dumps) is recorded in the implement-stage ticket in `ticket(implement): a-large-write-is-measured-once-and-its-cost-is-documented`.

## Review findings

Read the implement diff first, then the handoff.

- **Coordinator skip: correct.** I traced `localWriter` to `NetworkTransactor.localWriterMark`, which marks a request only when it goes to the transactor's own `localPeerId`. That mark rides on both `pend` (after `assertTransactionFits([blockAction])`) and `pendMany` (after its `transactionBytes` sum check). `RepoService` builds a remote pend's options from the message, so a remote writer cannot set the mark. The Quereus `local` transactor also sets it, but calls `StorageRepo.pend` directly and never reaches `CoordinatorRepo`. `pendRequestForBatch` keeps the same fields and narrows `transforms` and `baseRevs` to the batch, so a batch request is never larger than the pend that was measured.
- **Found and fixed (minor): the mark's contract was undocumented.** `localWriter` now also means "the writer already measured this pend", but its definition in `packages/db-core/src/network/i-repo.ts` said nothing about that. A future in-process writer that set the mark without measuring would skip the check, and in a cohort of one an oversized pend would commit unchecked. I added that obligation to the field's doc comment. I also corrected the `CoordinatorRepo.pendMany` comment, which said the mark is "set only by `NetworkTransactor`"; it now says the mark reaches that repo only from `NetworkTransactor`.
- **`takenBy` short-circuits: correct.** First: the loop always takes the first entry when the block is empty (`held === 0`), so returning 1 for an empty block with room for one is the same answer. Second: once `held > 0` and `bytes >= target`, the next entry adds at least a comma, so the old `grown > target` check would always have stopped there. The existing chain specs cover both (per the implementer).
- **Docs: found and fixed (minor).** The *Space* bullet in docs/blobs.md still gave only #63's 2.75–3.4×, which reads as current against the 3.3–6.0× now in internals. I added one sentence pointing at the new measurement. I read the rest of the docs diff against the code and handoff, and the table agrees with the handoff's raw figures. `yarn lint:docs`: all citations resolve. No other doc mentions the retired plan-ticket slug or the old "measures on the writer and again on the coordinator" wording.
- **Tests: none added, none cut.** The `takenBy` change keeps every decision and is already covered. The coordinator change is a one-line condition on a backstop that had no test before. I agree a test of the remote arm doesn't pay for itself, since the 8 MiB frame cap (`maxRequestBytes`) also bounds a remote pend.
- **Tripwires: none new.** The existing `NOTE:`s on `transactionBytes` and the tail measure in `takenBy` were reworded with valid revisit conditions. The one conditional risk I found, the mark being set without a measure, is now a documented obligation at the field rather than a `NOTE:`.
- **Other angles.** Type safety, error handling and resource cleanup: unchanged by this diff. File size: coordinator-repo.ts was already very large before this one-line change, and nothing here makes it worse. Performance: the point of the ticket. The profile in the handoff shows no `CoordinatorRepo` frame under `jsonEncodedBytes` and only the tail measure in `takenBy`.
- **Known gaps carried from implement (accepted, documented in internals):** commit time rises during a run, cause not isolated; table cells are two-sample ranges from a noisy machine; the "~0.5 s when planned" figure was not re-measured.
