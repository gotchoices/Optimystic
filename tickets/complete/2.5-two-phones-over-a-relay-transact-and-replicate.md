# What landed

`packages/db-p2p/test/two-phones-over-relay.integration.spec.ts` runs the two-machine lifecycle with every byte between the machines crossing a circuit relay. It is gated on `OPTIMYSTIC_INTEGRATION=1`, so it runs in `yarn test:integration` and `yarn check`.

- **Topology:** one plain libp2p relay, speaking only identify and circuit relay and never an Optimystic cohort candidate. Two phone-shaped storage nodes, A and B, have WebSockets and circuit transports only. Each listens only on `<relay>/p2p-circuit` and has a stable key and its own `MemoryRawStorage`.
- **Configuration:** the documented two-machine one, fixed by `startMachine`: default `clusterSize`, `clusterPolicy: { repairCorroborationClusterSize: 2 }`.
- **Phases** are separate `it`s over shared state. A phase whose predecessor failed fails at once, naming it.
  1. Both come up through the relay; each writes and reads the other's rows. Every A↔B connection is asserted relayed, and the relay is asserted to have run identify without serving either Optimystic protocol.
  2. Each node's own storage holds the other's committed blocks; each serves every row with the writer stopped.
  3. B drops, A writes (admission observed, not asserted), B returns knowing only the relay, and A finds B again on its own.
  4. Both restart; every acknowledged row reads on each, and a new write from each crosses.
  5. The relay restarts as the same peer on the same address; both phones must re-reserve, reconnect, and cross a write.
- **Shared helpers:** `test/util/two-machine-lifecycle.ts` holds the helpers both lifecycle specs now share: machines, start and stop, transactor, pair wait, reads and writes, locality checks, the observed-write helpers, and `sequentialPhases`.
- **Restartable relay:** `spawnRestartablePlainRelay`, in `test/util/relay-topology.ts`, restarts a plain relay under the same key on the same port and verifies the re-bind.

**Phase 5 is red by design.** A node listening on `<relay>/p2p-circuit` never asks for a new reservation after its relay restarts. That is filed as `fix/2-phones-never-re-reserve-after-their-relay-restarts`, with log evidence and the `@libp2p/circuit-relay-v2` 4.1.3 root cause. It is listed in `tickets/.pre-existing-known.md` so other agents do not re-report it.

Implementer's results, over seven runs:
- Phases 1–4 passed 7/7.
- Phase 5 failed 7/7, the same way each time.
- Phase 3's write with B away was refused 7/7, in about 1 s. Over direct TCP the same write is usually acknowledged after 11–31 s. This was recorded as an arm on `backlog/more-design/6.5-partition-healing`.

# Usage

- **Run it:** from `packages/db-p2p`, `OPTIMYSTIC_INTEGRATION=1 node --import ./register.mjs node_modules/mocha/bin/mocha.js test/two-phones-over-relay.integration.spec.ts --reporter spec`.
- **Phase 3 log line:** `phase 3 observed: A's write with B away was REFUSED|ACKNOWLEDGED …` reports the admission outcome. A change there means admission behaviour moved.
- **New lifecycle specs** build on `startMachine(machine, shape)`. Relay-restart tests use `spawnRestartablePlainRelay(network)`.

## Validation (review pass)

- **Relay spec:** phases 1–4 pass, and phase 5 fails exactly as recorded, with `A: 1 connection(s) to the relay, circuit address absent; B: …`. Phase 3 was again refused after 1015 ms, and the refused row read absent on both.
- **Siblings:** `small-deployment-lifecycle` 6/6 (its phase 5 was acknowledged after 18.3 s), `two-node-convergence` 3/3, `multi-coordinator-write-relay` 1/1.
- **db-p2p unit suite:** 2709 passing, 61 pending, 0 failing.
- **Checks:** db-p2p `yarn typecheck`, root `yarn lint` and root `yarn lint:docs` are all clean.
- **Not run:** the whole of `yarn test:integration`. The other db-p2p integration specs and `quereus-plugin-optimystic` import nothing this ticket changed.

## Correctness and test strength

- **"Relayed only" is not vacuous.** The relay lifts per-circuit limits, so relayed connections carry no `limits`. `isLimitedConnection` also matches `/p2p-circuit` in the remote address, so the assertion still distinguishes relayed from direct connections. No change needed.
- **The relay restart is a real fault, not a test artefact.** `spawnRestartablePlainRelay.start()` checks the relay came back on the same address, and phase 5 first waits for both phones to lose their reservation and their link. A missing re-reservation therefore cannot be caused by the relay landing elsewhere. No change needed.
- **Helper extraction preserves behaviour.** `small-deployment-lifecycle` phases, timeouts and assertions are unchanged, and it passes. `two-node-convergence` lost its `as any` casts, and `transactorFor` now takes `OptimysticNode`, so the types are stronger. No change needed.
- **Fixed inline:** `startPhone` passed `port: 0`. `createLibp2pNode` reads `port` only for its default TCP listen addresses, which a phone overrides, so the option was misleading on a phone shape. Removed; the spec still behaves the same.

## Findings dispositioned

- **The FRET bootstrap observation is confirmed and parked as a tripwire.** `seedFromBootstraps`, in `Fret/packages/fret/src/service/fret-service.ts`, takes the *first* `/p2p/` id, so a partner's circuit address seeds the relay rather than the partner. It is harmless today: the partner is learned once its connection opens. The `NOTE:` sits where db-p2p hands bootstraps to FRET, at `packages/db-p2p/src/libp2p-node-base.ts`, in the `fret:` service factory. It is not filed, because the fix belongs to another repository and has no visible effect.
- **Host-facing docs lagged the gap (fixed inline).** `docs/architecture.md` stated the relay-restart gap, but `docs/optimystic.md` § Deployment Targets tells mobile and browser hosts to use circuit-relay transports without mentioning it. A short "Relay restarts" paragraph now says a host must supervise the reservation until the node does it itself. `docs/optimystic.md` was added to the fix ticket's `files:` so the fix stage updates or removes it.
- **The deliberately red phase 5 in `yarn check` was accepted.** The alternatives are skipping or loosening the phase, which the workflow forbids, or dropping the reproduction. The fix ticket is in `fix/`, the top-priority stage. The `.pre-existing-known.md` entry names it and the exact failure text. Revisit if that fix stalls; the entry must come out when it lands.

## Considered, no action (with reason)

- **Two circuit-address predicates.** The spec's `hasCircuitAddress` matches `/p2p-circuit`, while `waitForCircuitListen` matches `/p2p-circuit/`. libp2p only reports a circuit address once a reservation exists, and it always carries a peer id, so both behave the same. Unifying them would only be tidying.
- **Losing the relay handle.** `RestartablePlainRelay.stop()` clears its handle before awaiting `stop()`, so a throwing stop loses the handle. The helper is test-only, and a throwing libp2p stop already fails the spec.
- **Protocol prefix derived by hand.** `transactorFor` builds `/optimystic/<network>` itself instead of asking the node. This is pre-existing in both specs it was extracted from, and there is no public accessor to use.
- **Gaps the handoff lists** are correctly characterised, and none is a defect:
  - Phase 2's locality wait passes almost at once, because both nodes are in every cohort.
  - Phase 3 cannot check local replication of a write that is always refused.
  - There is no "founder writes alone, then a joiner arrives" step over the relay, so the `rebalance-monitor.ts` tripwire about slow links stays unexercised and untripped.
  - `sequentialPhases` uses mocha globals.
- **Size and hygiene:** the relay spec is 283 lines and the helpers module 215. Functions are short and named for what they check, and comments state purpose, not mechanics.
- **Resource cleanup:** the suite's `after` hook stops both machines and the relay together with `allSettled`. Every `waitFor` is bounded, and no timers or listeners are left behind.
- **Security and performance:** nothing applies. The change is test-only apart from one comment and a docs paragraph.
