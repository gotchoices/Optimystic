# A materialized view follows rows other members commit — complete

GitHub #58. Refresh mode only; the invalidate mode waits on Quereus (blocked ticket `a-materialized-view-can-be-kept-off-while-it-is-behind`).

## What was built

`MaterializedViewFollower`, one per `Database`, built in `register` before any table opens, attached to the bridge (`TransactionBridge.attachMaterializedViewFollower`) and to the factory (`CollectionFactory.setExternalCommitsListener`, which binds each opened tree's `onExternalCommits` to its collection id). Disposed in `plugin.dispose()` after the offline queue, before the bridge. Exposed as `plugin.materializedViews.settled()`.

Signals (all synchronous, all dropped when no `getAllMaintainedTables()` entry's `derivation.sourceTables` names the table, `NOTE:` tripwire at `viewsRead`):

- **adopted** — `onExternalCommits(collectionId, rev)`; collection id → table through `TransactionBridge.tablesOf` (the bridge's existing registry of main and index trees, which also picks up an index created later). Marks the table dirty.
- **hint** — `announceExternalChange(…, 'hint', follower, …)` from the vtab's `handleCollectionChange` (storage event and network-watch wake). Queues a pull.
- **changed** — `announceExternalChange(…, 'changed', …)` from `OfflineMode.announceChanged` (failed entry removed, or a network-acknowledged commit that timed out and stayed). Marks dirty. Also raised by the vtab when a full initialization replaces an earlier published handle at a different revision.

The run (`follow`), repeated while anything is hinted, dirty or owed:

1. Inside `db.ingestExternalRowWrite(async () => [])` (holds the exec lock, ingests nothing): if an explicit transaction is open, pull nothing and wait for `bridge.whenTransactionIdle()` (or, when no Optimystic connection joined that transaction, a 1 s unref'd poll), then loop. Otherwise pull every hinted **and** dirty table — `pullEveryTree`: `refreshLive` over the main tree and every index tree.
2. Dirty tables expand into owed views (by lowercased `schema.name`), skipping views waiting out a failure.
3. Rebuild owed views in dependency order with `db.exec('refresh materialized view "<schema>"."<name>"')`.
4. A rebuild is owed again (and the run waits for the transaction) when its `materialized_view_refreshed` event, which fires synchronously inside the refresh, saw an explicit transaction open, or when it threw while one is open.
5. Any other failure defers the view: per-view delay 1 s doubling to 60 s, logged once per distinct message per view; reset on success. A removed owed view (drop, or the first half of a rename) hands its debt back to its source tables.

A `MisuseError` from the follower's own engine calls is read as "Database closed" and halts the follower quietly.

## Deviations from the ticket (judgment calls — please weigh)

- **Pulls every tree, for hinted and dirty tables** (ticket: main tree, hinted only). An index handle that lags behind the main handle reports the same foreign commit later, when a read goes through it, which would owe a second full rebuild; pulling all trees first folds everything into one rebuild. Cost: one idle refresh request per index tree per run.
- **The explicit-transaction check runs under the exec lock** (inside the ingest callback), not before taking it, so it never reads Quereus's state mid-statement and the wait ends only after the `commit`/`rollback` statement finished.
- **`exec(…, { transaction: true })` was not used** to make step 4 exact: under `ddl_transaction_policy = 'strict'` Quereus refuses `refresh materialized view` inside any explicit transaction, its own included. The `materialized_view_refreshed` event is used instead; the throw path reads the state after the fact (accepted-tradeoff `NOTE:` in `rebuild`).
- **`settled()` does not wait for views waiting to retry a failure**, so one broken view does not hang every waiter. It does wait for an open explicit transaction (documented: never await it inside one or a statement).
- **Owed is tracked per view after expansion** rather than keeping tables dirty until every view succeeds, so a failing view retries alone.
- **Replaced handle** compares `committedRevision()` with `!==` rather than "past" (two handles of one collection; a lineage change also counts).

## Tests (`test/materialized-view-follows-other-writers.spec.ts`)

Two `Database`s over one `StorageRepo`; the shared transactor also delegates `onCollectionChange`, so each hears every commit as the real `local` transactor does (a hosting node). Rebuilds counted by A's `materialized_view_refreshed` events.

- **rebuilds the view after another writer commits (GitHub #58)** — B inserts; after `settled()`, A's `ChitTotal` and `select sum(Units) from Chit` include B's row; A's next insert adds on top.
- **does not rebuild the view for this machine's own commits** — three own inserts, zero rebuilds, view correct.
- **waits out an explicit transaction, then rebuilds once** — A `begin`, B inserts, 100 ms with no rebuild, A `rollback`, then exactly one rebuild.

Mutation checks run during implement, each failing the spec: follower ignores every signal (tests 1 and 3 fail); a hint marks dirty without pulling (test 2 fails); no explicit-transaction wait (test 3 fails). An ad-hoc run (not kept) confirmed the pull-only path: with no storage hints, B's commit reaches A's view only after A reads `Chit`, then is rebuilt.

## Known gaps

- Not covered by tests: the offline `'changed'` signal, the replaced-handle signal, the untold-table WARN, failure backoff and log suppression, view-over-view ordering, the rename debt return, the closed-`Database` halt, the unjoined-transaction poll. All by inspection.
- `yarn test:integration` was not run, so the network-watch hint path is untested end to end.
- An unexpected (non-misuse) error out of the run holds it 1 s before the next run, to avoid a hot loop; it is logged.

## Review findings

Read the diff of `ticket(implement): a-materialized-view-follows-rows-other-members-commit` first, then the handoff; checked the Quereus contracts it leans on in the sibling checkout (`Database.ingestExternalRowWrite` is a plain exec-mutex hold for an empty result; `_isImplicitTransaction` is kept on the public surface for exactly this use; `MaintainedTableSchema.derivation.sourceTables` includes tables reached through plain views; `MisuseError` from the follower's own `exec` / `ingestExternalRowWrite` calls is only the closed-`Database` case).

**Correctness — checked, no defect found.**
- Signals run under the collection latch inside `forgetAndAdopt`: the adopted callback only reads `tablesOf` and the catalog and creates the run promise, whose first step is `await Promise.resolve()`, so nothing runs inside the latch.
- The vtab reads and writes through its one published handle (`this.collection`), so the follower's pull and the rebuild's own read share a handle and a pulled commit is not adopted twice (test 3's exact count of one confirms it).
- A commit arriving during a rebuild re-marks the table dirty and the loop rebuilds again; a `begin` queued ahead of the refresh is caught by the `materialized_view_refreshed` event and the view stays owed; the explicit-transaction check runs under the exec lock.
- `settled()` cannot spin: each iteration either awaits a run or starts one; deferred retries are excluded from `hasWork`, as documented. `dispose()` races every wait against the halt promise.
- Rename debt return, dependency ordering and the cycle fallback read correctly.

**Minor — fixed in this pass.**
- DRY: the spec re-implemented `test/shared-local-transactor.ts`'s transactor with one extra method. Added `buildSharedNotifyingTransactor` there (both builders share one `transactorOver`) and the spec uses it; the existing builder is unchanged, so no other spec starts receiving storage events.
- Docs: `docs/offline-sync.md` §Removing an entry step 4 described `announceExternalChange` as reaching watchers only; it now says the views reading the announced tables are rebuilt too, linking internals §Reactive Watch Bridge.

**Tripwires — recorded, not ticketed.**

A persistent non-misuse failure of the run itself (not of a pull or a rebuild, which are handled) logs a WARN every second; no path producing one was found.
