# Matchmaking arrival push — the cohort member that sends pushes (complete)

Second of five tickets in the arrival-push chain. This is the sending side only; node wiring, the libp2p `send` binding, the mesh and real-socket end-to-end tests and the remaining design-doc updates belong to `matchmaking-arrival-push-wiring-and-e2e`.

## What was built

- **Trigger (db-core).** `observeRecordAdditions(store, onAdded)` in `packages/db-core/src/cohort-topic/registration/store.ts` wraps a `RegistrationStore` and calls `onAdded` after a `put` that makes a `(topicId, participantId)` record present where none was held. Renewals, restamps and re-merges report nothing. A listener throw is logged under `cohort-topic:registration`, never propagated into `put`.
- **Host seam (db-p2p).** `createCoordEngine` builds its store through the observer, so admission (`CohortMemberEngine.accept`), gossip merge and handoff pull all feed `CohortTopicHost.onRecordAdded(listener)` — a node-level subscriber set with an idempotent unsubscribe, per-listener throw isolation, cleared by `host.stop()`.
- **Driver.** `ArrivalPushDriver` in `packages/db-p2p/src/matchmaking/arrival-push-driver.ts`: on a provider arrival it decodes the topic's push-opted seekers, drops bindings whose seeker record is gone or re-registered, runs `selectArrivalPushTargets`, keeps the seekers whose slot primary (computed fresh from the engine's current cohort view) is this node, and coalesces per seeker binding. Flush on the `coalesceMs` timer, at once when the queued entries cover `wantCount`, or at `QUERY_LIMIT_MAX`. A flush re-checks the seeker record (same correlation id) and signs with the epoch and traffic read at flush. `unknown_seeker` marks the binding dead; a lost push removes its providers from the binding's "already pushed" set so the next arrival is still pushed. Bindings capped at `maxBindings` (default 4096) with least-recently-touched eviction. Never calls `recordQuery`.
- **Shared decode.** `decodeLocalRegistration` in `local-registration.ts` is used by both the query handler and the driver.
- **Protocol id.** `arrivalPush` is in `matchmakingProtocolList`; no handler is registered until the wiring ticket.

## Review findings

**Read first:** the `ticket(implement): matchmaking-arrival-push-cohort-driver` diff, then `docs/matchmaking.md` §Arrival push on provider arrival (all subsections), `selectArrivalPushTargets` in `packages/db-core/src/matchmaking/arrival-push.ts`, the gossip bus `mergeRecords` and `fromGossipRecord`, `CohortMemberEngine.accept`, the renewal and handoff `put` sites, the coord engine's `cohort`/`records`/`heldRecord`/`topicTraffic`, and `peerIdToBytes`.

**Correctness — checked, no defects found.**
- Every store write path (accept, gossip merge, handoff pull, renewal touch, re-attach restamp) goes through `put`; only the first three can add a record, and gossip carries `appState`, so a provider replicated by gossip triggers on every member.
- The self/member byte encoding matches (`peerIdToBytes` of the peer-id string on both sides), so the slot-primary comparison is sound, including root-placed engines (their `cohort()` reads the root view).
- The listener runs synchronously inside `put` (inside `accept` before `recordArrival`, inside the gossip merge loop). An immediate flush reads `topicTraffic` and `heldRecord` synchronously there; both are pure reads, so no re-entrancy hazard.
- The decoded-record `WeakMap` cache: no site mutates a held record in place (the one in-place write, the gossip TTL clamp, happens on the incoming object before `put`), so a cache entry cannot go stale.
- Coalesce/flush/timer lifecycle: the timer is cleared on flush, removal, eviction and `stop()`; the cap cannot evict the just-added binding; a late ack after `stop()` touches only unreferenced state.
- Flush-on-need follows the doc's "`wantCount −` matches already pushed" rule, since the "already pushed" set includes the queued batch.
- The implementer's departures from the ticket (a lost push frees the slot; no `clock`; `heldRecord` in the narrow engine type; silent decode of the arriving record; `maxBindings < 1` throws) are each sound. The first goes beyond the ticket's letter in the direction the doc's "optimization-only" rule wants.

**Tests.** The four implementer tests each pin one doc rule (renewal is not an arrival — the observer assertion is what pins the decorator; coalescing and cover-the-need flush; slot-primary-only delivery; `unknown_seeker` then re-registration). Kept all four. The "lost push frees the slot" decision had no test; added *a lost push does not count toward the seeker's need: the next arrival is pushed* (a `wantCount = 1` seeker whose first push gets no reply still receives the second provider). Mutation-checked: with the `pushed.delete` in `dropBatch` removed, exactly that test fails. The listener-throw catch stays inspection-only, as the plan said.

**Tripwires parked (as `NOTE:` comments in `arrival-push-driver.ts`).**
- Bindings are scoped per engine, so while a moved root leaves two of this node's engines holding one seeker, one arrival can be pushed twice (the seeker dedups). Note at the `scopeKey` site.
- Each provider arrival lists the whole topic's records; bounded by the `cap_promote` ceiling and the same cost a query pays. Note on `pushOptedSeekers`, naming the per-topic index remedy.
- The existing cap note on `BindingTable.add` stands.

**Docs.** `docs/debugging.md`: both new namespace rows are present and the db-p2p count of 52 matches the 52 rows (counted). The `docs/matchmaking.md` *Implemented* callout, `docs/internals.md` §Matchmaking subsystem and `docs/cohort-topic.md` §Application policies are explicitly owned by `matchmaking-arrival-push-wiring-and-e2e`, so they were left for it. **Type safety, DRY, resource cleanup, size.** No `any`; the narrow `ArrivalPushEngine` type keeps the driver testable without a host. Record decoding is de-duplicated into one helper. The driver is 404 lines plus notes, one class with small methods. No comment narrates statements.
