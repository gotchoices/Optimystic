# What landed

The third and last ticket of the certified-claims chain (`certified-claim-selection` →
`certified-claims-read-repair` → this one). Implement wired the commit-path reconcile
(`cluster/reconcile-block.ts`) to verify cohort commit proofs that peers attach to their repair
answers, to weigh those verdicts in both the revision gate and the content gate, and to persist a
proof alongside the bytes it certified so a repaired replica serves it onward.

The operator-visible consequence, in plain terms: before this chain, a block that only one machine
still held could never be repaired — repair required two machines to independently say the same
thing, and there was only one. It now repairs from that single machine whenever that machine also
kept the cohort's signed proof for the revision, because the signatures on the proof do the job the
second machine used to do.

The review ran in two passes (a first pass crossed its token budget mid-way and handed off a
findings list; this pass finished the documentation and test work). Both passes' findings are merged
below.

### Found and fixed in this review

- **An unverified proof could reach storage through a second caller.** `BlockStorage.saveRestored`
  read the proof out of the archive body it was handed. Archives are remote wire data — a serving
  peer picks what to attach — so "strip proofs you did not verify" was a comment-enforced obligation
  on every caller, discharged by exactly one of them (`restoreBlock`, which mutated the archive its
  own fetch callback returned). The next caller would have broken it silently. `saveRestored` now
  takes the verified proof as a separate out-of-band `verified?: { rev, proof }` parameter and
  ignores the archive's own `proof` field entirely, so only the chain that verified a proof against
  the exact bytes can persist one. `restoreBlock` went back to a plain pass-through. This is a
  representation change, not a patch: the bad state is now unrepresentable rather than merely
  documented.
- **The proof-verification thresholds were duplicated.** Both repair paths built
  `{ superMajorityThreshold, simpleMajorityThreshold: 0.5 }` inline with the same rationale comment.
  That hardcoded `0.5` has to mirror what cohort members actually enforce
  (`ClusterMember.hasMajority`, `count > total / 2`) rather than the configurable 0.51, and two
  copies could drift silently. Extracted as `proofThresholds()` in `cluster/certified-claims.ts`;
  both callers use it.
- **`reconcile-block.ts`'s header comment cited a closed ticket** and still described the sole-peer
  content exposure as entirely open when it is now closed for a candidate carrying a verified proof.
  Corrected, naming the remaining unanchored-cohort residual instead.
- **Two references pointed at `accept-certified-claims-in-repair`** — the plan ticket this chain
  implemented — as future work a consumer must wait for. Dropped from `cluster/commit-proof.ts`
  (caller obligation #1) and `docs/internals.md` (*What a passing verdict does not say*); both now
  name only `feat-cluster-membership-threshold-cert-anchoring`, which is genuinely still open in
  `backlog/`. Ticket-provenance headers in test files still name the plan ticket, correctly — those
  record history, not pending work.

### Found and fixed: documentation that stated the opposite of the code

`docs/transactions.md` had been updated for certified claims. `docs/internals.md` had not, in the
two places an operator reads when a block will not repair. Verified against the code before
rewriting — a certified lone holder is selected inside `selectQuorumRev` and returns a `selected`,
and `reportRepairDeadlock` is only reachable on the `!selected` branch, so `sole-holder` genuinely
cannot fire for it (`repo/coordinator-repo.ts`).

- **The repair-size table and the paragraph under it.** The two-machine undeclared row said repair
  is possible *never*, and the prose said a block only one cohort peer holds "cannot be repaired at
  *any* machine count, four-or-more included". Both are true only of proof-less holders. The table
  now states up front that it describes uncertified claims, the prose says which claims it binds,
  and a new *The certified exception* section explains when one holder is enough at any size — with
  the three limits that matter (ordinary corroboration still wins at a strictly higher revision;
  proof retention is per revision and not retroactive; a verified proof does not prove the signers
  are this block's cohort).
- **The `sole-holder` repair-deadlock entry.** It told operators the only remedy is another cohort
  peer holding the block and that no machine count or configuration setting helps. There is a second
  way out — the lone holder retaining the commit proof — and it is worth stating because a repaired
  replica now serves the proof onward, so this case should get rarer rather than staying permanent.
  Rewritten as two remedies, honest that the second is not something an operator can apply
  retroactively to an already-stranded block.

### Found and fixed: operator-facing log lines no document named

The chain added five log tags across the two repair paths and the docs named none of them. Two are
*incidents* an operator must be able to tell apart from an ordinary shortage — which is exactly what
the implement handoff asked a reviewer to check, and it was a real gap: each equivocation is
accompanied by a routine `no-rev-quorum` / `no-content-quorum` line that reads as a capacity
problem. Documented in `docs/internals.md` beside the existing reconcile decline lines, split into
incidents and informational, with the operator guidance the incidents need (a certified equivocation
means whoever holds the cohort's signing keys signed both sides — investigate the cohort; adding
machines does nothing).

### Found and fixed: test gaps

Four cases added to `packages/db-p2p/test/reconcile-block.spec.ts`, all in the existing *certified
claims* describe, built on the real signed proofs from `test/support/commit-proof-fixtures.ts`.

- **The certified-win penalty skip is now pinned.** When a certified carrier wins the content gate,
  peers that served different bytes are deliberately *not* penalized. This is the most
  security-sensitive deliberate choice in the change and nothing asserted it, so a refactor could
  have silently re-enabled the penalties and handed a forged proof a reputation lever against the
  honest cohort. The new test builds exactly the shape that *is* penalized on a corroborated win
  (the neighbouring content-liar test) and asserts no penalty fires.
- **A proof that declares no digest for this block.** The pre-digest-upgrade shape, on its own
  branch: the revision certifies, the content does not, nobody is penalized. Asserted in both arms —
  a lone holder declines the content gate (with `certified-selected` and `no-content-quorum` both
  logged), and with a second ordinary carrier the heal lands the normal way while the proof, having
  bound no bytes, is still never persisted.
- **The block-less certification arm.** A cohort answer carrying a revision and a proof but no
  materialized block routes through `certifyClaim` instead of `certifyContent` — an arm of
  `certifyCandidates` no reconcile test reached. Covered on both outcomes: the success arm (the
  block-less proof carries the revision selection, bytes still come from ordinary carriers, no proof
  persisted) and the attributable-failure arm (a genuine proof presented for a revision it does not
  cover penalizes the serving peer, and the inflated claim never steers the heal).

Also replaced a locally-defined log-search helper in the new tests with the existing shared `hasTag`
from `test/support/capture-log.ts`.

### Found and deliberately NOT actioned

- **Anchoring is unwired.** Layer 1 of certification proves the listed signers signed, not that they
  are the block's legitimate cohort — an attacker holding N keys can stand up a fake cohort and
  self-certify. No offline check can close this. Already tracked as
  `feat-cluster-membership-threshold-cert-anchoring` in `backlog/`, and honestly stated in all three
  docs and at both code sites. Evidence for that ticket, not a new one.
- **The certified-win penalty skip is sound, not a defect.** Probed as the handoff invited. An
  attacker cannot force a certified win without cohort keys or a wholly fabricated cohort, and if
  they have either, reputation is not the binding constraint. The alternative — letting a forged
  proof convict the honest cohort — is the worse failure mode. Behaviour kept; pinned by test
  instead, with the revisit condition (the anchoring ticket) named in the test comment.
- **The monotonic-skip proof gap** — a revision that first landed proof-less keeps no proof even
  when a later certified heal of the same revision carries one. Decided at the site with a stated
  rationale and pinned by a test that names itself as the assertion to flip. Left alone; now also
  stated in the operator docs so it is not a surprise.
- **Verification cost** — one proof verification per proof-carrying answer per reconcile, bounded by
  the 256-signer cap times cohort width. Already carries a `NOTE:` at `certifyCandidates` saying it
  is fine at deployment cohort sizes of about ten, and what to do if it ever shows up in a profile.
  Tripwire, already parked at the site.
- **`docs/correctness.md` needed no change.** Read in full for this area; Theorem 14 and the
  forgery-detection section already describe the certified path accurately, including the unanchored
  residual.

### No tripwires newly parked

Nothing conditional surfaced in this pass that was not already carried by an existing `NOTE:` at its
