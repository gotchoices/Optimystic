# File store syncs by the earliest deadline — complete

Fourth of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). Landed in `ticket(implement): file-store-syncs-by-the-earliest-deadline`; reviewed here.

## What landed

`FileWriteLog.commit(entries, { syncWithinMs })` in `packages/db-p2p-storage-fs/src/file-write-log.ts` returns a `CommittedBatch`. The record is appended with one `write` in the log's serial queue and held in an in-order `unsynced` list with its deadline, counted from the commit's call. A strict commit (`syncWithinMs` 0), or one that finds the earliest waiting deadline already passed (backpressure), runs the sync step before it resolves. Otherwise a timer, armed through the log's injectable `setTimer` for the earliest deadline and re-armed only for a sooner one, enqueues the sync step. The sync step (`syncUnsynced`) runs only inside a queued task (a commit, `sync()`, the timer's task, a checkpoint's seal): one `handle.sync()`, then each covered batch applied to the tree in order, then each `durable` resolved in order; a failure anywhere latches the log and rejects every covered `durable`. One `latch` now serves every fault site (open, append, sync step, seal, checkpoint) and rejects whatever waits. The seal runs the sync step before the rename, so a sealed segment holds only synced records whose tree writes are in the taken dirty set. `shutDown` disarms the sync timer; the final checkpoint's seal syncs what still waits. A sync that started after a deadline it covered logs `window-overrun` once per episode. `FileBatchBackend` and `FileKVStore` pass the options through and forward `sync()` to the log; `SYNCED_BATCH` is gone.

Docs: the README's *Write-ahead log*, *What a crash loses* and *Durability* sections; `packages/db-p2p/docs/storage.md`'s Invariant 6 table row, the "today is the file backend alone" sentence, the *file backend* paragraph and the performance bullet.

Deviations from the implement ticket, kept after review: the overrun is measured at the sync's start rather than its finish (a sync starting at its deadline finishes after it by the fsync's own length, so the finish-time measure would never end an episode); `scheduleCheckpoint()` stays at the end of every commit rather than in the sync step (the idle checkpoint must be armed by the append for the "5 s after the last append" bound to hold); a local `settlement()` helper stands in for db-p2p's unexported `deferred`; `commit` rejects a non-finite or negative `syncWithinMs` with a `RangeError`, mirroring `WriteGroup.flush`.

## Review findings

**Read first:** the implement commit's full diff, then the whole of `file-write-log.ts` (977 lines, `wc -l`), `file-batch-backend.ts`, `file-kv-store.ts`, the spec, `WriteGroup` and `WriteGroupDriver` in db-p2p (the sink contract the log now honours), the downstream ticket `storage-sync-deadlines-are-shared`, both docs the change touched, and `docs/debugging.md`, which the implement ticket named.

**Checked by reading, no defect found:**

- Queue discipline. Every caller of `syncUnsynced` is inside a queued task (`commit`, `sync`, `syncInBackground`'s task, `seal`), so nothing pushes onto `unsynced` during a step and a failure's `latch` rejects exactly the covered batches. The list is left in place until the apply succeeds, which is what makes that true.
- Timer invariant. `syncTimer` is set only right after an append (list non-empty) and cleared by every non-empty sync step and by `latch`, which are the only two things that empty the list. So `syncTimer` set implies something waits, and a timer that has fired and found nothing cannot leave a later relaxed commit un-armed. A timer that fires while a commit is ahead of it in the queue is harmless: that commit finds the deadline passed and syncs by backpressure; the timer's task then finds the list empty.
- The seal's early return on `appendedBytes === 0` cannot skip a waiting record: `append` adds the bytes before pushing the batch, and only the seal resets the count, after its own sync step.
- The final release: `shutDown` disarms the sync timer, drains the queue, and the final checkpoint's seal syncs what waits. A `sync()` enqueued after the handle is released finds an empty list and never touches the handle; a `commit` after close throws.
- A failed append rejecting the earlier waiting batches is the right call, not one last sync: the handle's state is suspect after a failed write, and the flush contract's rule 5 forbids trusting a retried sync. Their records are intact in the operating system and the next open replays them.
- Reads: the tree is written only at the sync, and `WriteGroup` drops an overlay entry only when `durable` resolves, which is after the apply, so no read falls through to the tree early. Two stores over one log: a strict flush of either syncs the other's waiting batches (one log, one prefix), which is what keeps write order 8 (ledger entry after the commit it describes) for a shared base path.
- The overrun measure. A backpressure or strict sync that starts after the earliest waiting deadline is always late by construction, which is correct: the timer's task should have run by then, so a late start is queue lag. The one false positive is a commit landing in the instant between a deadline and its timer firing, late by the timer's slop; recorded as a tripwire, below.
- `WriteGroup` never passes a non-finite or negative `syncWithinMs` (it clamps with `Math.max(0, …)`), so the `RangeError` arm is reachable only by a direct caller.
