# What changed

`operationsConflict` (`packages/db-p2p/src/cluster/race-resolution.ts`) decides whether two cluster messages must serialize against each other, and so whether a member votes `conflict` on one of them. It answered "conflict" for any two messages of different actions that share a block — including a **cancel**. One new escape, beside the existing same-action escape:

```ts
if (isCancelOnly(ops1) || isCancelOnly(ops2)) return false;
```

`isCancelOnly` is "every operation in the message is a cancel". `RepoMessage.operations` is a one-element tuple type, so a mixed message is not representable; the `.every` is the same formality `getActionId` already keeps beside it, and keeps a hypothetical mixed message conservative.

Why it is safe, one line per neighbour: cancelling action X deletes only X's pending records on the named blocks (`StorageRepo.cancel`) and never moves a block's revision, so it reorders nobody's history. A commit of Y never reads X's pending record (that was checked at Y's pend); a pend of Y is refused by storage and by `validatePendOperations` while X's record stands, in either arrival order; an invalidation writes compensating revisions and leaves pending records alone. The argument lives at the function's doc comment; `docs/correctness.md` Case 2 states the invariant and cites it.

Consequence worth knowing: a cancel now neither holds a reservation against anyone nor can have its own reservation aborted by a rival (`race-accept-incoming` no longer reaches it). A cancel's own `activeTransactions` entry still clears on completion through the normal `shouldPersist`-false branch, so nothing leaks.

# Why it mattered

On a two-member cohort with `superMajorityThreshold: 0.67`, one conflict vote already makes super-majority unreachable. Writer A's pend was refused (B held the leaf), A cancelled its own refused pend, and that cancel — naming the same blocks, under a different action id — made both members vote `conflict` on B's **leaf commit**, after B's log tail had already committed. B cancelled, refreshed, found its own log entry, re-sent, and collided with A's next cancel the same way, until the row's revision moved on under A and B reported `TornActionError` for a write that was half-saved.

# Review findings

Read the implement diff (`e46e7d6f`) in full before the handoff, then `operationsConflict` and its single caller (`findConflict` in `cluster-repo.ts`), `getActionId` / `getAffectedBlockIds`, `StorageRepo.cancel`, the coordinator's vote aggregation, both specs, and both documents.

- **The escape's safety argument — checked against the code, holds.** `StorageRepo.cancel` does exactly one thing per block: `deletePendingTransaction(actionRef.actionId)` under the block write latch. It never writes a revision, so it cannot reorder history, and the commutation claim stands. Confirmed the same-action escape already covered cancel-vs-its-own-commit, so the new escape only ever fires between *different* actions. Confirmed `getActionId` returns undefined for `invalidate`, so a cancel-vs-invalidate pair reaches the new escape rather than being mislabelled same-action.
- **Blast radius — one caller, checked.** `operationsConflict` is called from exactly one place, `findConflict`. Write-vs-write pairs are untouched by the change (`isCancelOnly` is false for both), which is what Theorem 1 quantifies over, so the change cannot create a split brain between two writes. The implementer's two guard tests (commit vs a different action's pend; pend vs pend) pin that.
- **Resource cleanup — checked, no leak.** A cancel is now never cleared by a rival winning the race, so I traced the other exits: a completed transaction leaves `activeTransactions` via `clearTransaction` on the `shouldPersist`-false branch, and the staleness sweep in `findConflict` is the backstop. No new retention.
- **The mesh regression genuinely catches the bug — verified by mutation, and it is weaker than the handoff claimed.** I removed the escape and re-ran: only **1 of 3** runs tore, not the 3 of 3 the handoff reported. At `PairsPerRun` 8 all three runs tore (8 `TornActionError`s), and the green run costs ~27s instead of ~16s. I raised it to 8, then reverted to 4 — see the next finding. Both measurements are now recorded in the spec's header comment, with the instruction to raise it by hand to reproduce.
- **Raising contention exposed a separate defect — filed.** At `PairsPerRun` 8 the **fixed** build fails 2 executions in 3, never with a tear, always with `Transaction rejected by validators (1/2 rejected): … pending conflict: block … held by unresolved action(s) …`. That is a transient optimistic-concurrency condition answered as a *permanent* `ValidatorRejectionError`, because a member's pend validation votes `reject` for it and `maxAllowedRejections` is zero on any cohort of three or fewer at the default threshold. The coordinator's own vote-counting comment says this exact masquerade must not happen. Filed as `backlog/bug-a-contended-pend-refusal-is-permanent-on-a-small-cohort` (repro verified, both candidate fix sites named and why neither is a one-liner), with a `NOTE:` at the vote site in `validatePendOperations`. Site-claim grep first: `bug-a-two-member-cohort-refuses-a-commit-both-members-hold` is the commit durability verdict, and `implement/a-write-reported-torn-can-already-be-saved` touches the *stale revision* arm — neither claims this branch.

I verified this is safe today (the mesh routes only `update` through it, and `restart`'s `dispose` is unused in this spec) and replaced the optimistic sentence with the actual constraint.
