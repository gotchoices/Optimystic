# What was wrong

A table declared without `using optimystic('<uri>')` defaulted to `tree://default/<table>`, and its schema-catalog record was filed under the bare table name. So `strand.Member` and `app.Member` opened one collection and shared one catalog record: one table's inserts read back through the other (null id), and a same-named index made the second declaration fail against the first table's record.

# What changed

- `src/schema/table-identity.ts` is the single rule: `defaultCollectionUri(schema, table)` → `tree://default/<schema>/<table>` (`main` included), and `catalogKey(schema, table)` → an injective framed tuple (`encodeKeyTuple`). `namesOfCatalogKey` decodes a key, or returns undefined for a legacy bare-name key.
- The `SchemaManager` catalog API (`getSchema`, `getSchemaFresh`, `deleteSchema`, `getDroppedSchemaRecord`) takes `(schemaName, tableName)`; the cache and the tree are keyed by catalog key; `listTables()` returns `{ schemaName, tableName }[]` and skips legacy keys. `CatalogBatch` treats keys as opaque.
- `hydrateCatalog` restores each table into the engine schema it was persisted in (creating that schema if missing) instead of re-stamping it into the host's current schema.
- Format break, no migration (AGENTS.md: no backwards compatibility owed yet): defaulted tables from earlier builds are at the old location, and their records are ignored. README documents the explicit-URI workaround.

# Tests

`test/same-named-tables-across-schemas.spec.ts` (8 cases): URI and key rules; per-table rows and index seeks; the index-free device symptom; hydrate into own schemas plus idempotent re-apply; drop isolation and gravestone-per-table; cross-schema gravestone independence; legacy upgrade (added in review).

# Review findings

**Diff read first**, then the handoff. Checked: every catalog call site (typecheck confirms none left on the old signature), `recordUriOf`/`parseTableSchema` sharing one rule, `resolveAndCache` caching under `entry[0]`, `listTables` skipping undecodable keys *before* resolving (so a legacy record can't throw during hydrate), batch overlay by key, Quereus `addSchema`/`getSchema` semantics (lowercases, throws on existing — the code only calls `addSchema` when `getSchema` returned undefined), and every `tree://default/` mention in code and docs.

- **Catalog determinism (garden-tender note 1): checked, no problem.** Catalog keys and default URIs depend only on the declared schema and table names; nothing per-machine or order-dependent goes into them. `hydrateCatalog` only reads: it walks the catalog in key order and adds tables to the in-memory engine schema, writing nothing to storage. So a warm restart can't produce different catalog bytes on different machines. The one wall-clock value in a record, a gravestone's `droppedAt`, was already there before this change and is only written by `DROP TABLE`, never at launch.
- **Untested README workaround (garden-tender note 2): now tested.** I added a case that builds the storage an earlier build would have left: rows at `tree://default/Member`, and a defaulted-table record under the bare key `Member`. On that storage, `hydrate` returns `{tables: 0, indexes: 0}`, a defaulted re-declare starts empty, and re-declaring with `using optimystic('tree://default/Member')` reads the old rows. I also extended the README caveat: it now points at the test and says that tables which already used an explicit URI keep their storage but still have to be re-declared, because `hydrate` skips their old records too.
- **Legacy record matched by URI (minor, no action).** `findRecordForUri` still walks legacy bare-key records. `recordUriOf` recomputes a legacy defaulted record's URI as `tree://default/main/<table>`, so the record can be matched to a defaulted re-declare at the new location. That location is always empty, so the storage-adoption guard returns early and the declaration is allowed (the legacy upgrade test exercises this path). Legacy explicit-URI records still match their real storage, which is the correct guard behaviour.
- **Table-name casing (tripwire).** `Member` and `member` in one schema get different storage and different catalog records, although SQL treats them as one table. This was equally true of the old bare-name rule. Parked as a `NOTE:` in the header of `table-identity.ts`.
- **Unescaped `/` in URI segments:** the implementer already parked this as a `NOTE:` on `defaultCollectionUri`. I agree and made no change.
- **Hydrate behaviour change:** tables now go back into the schema they were persisted in, not the host's current schema. This is intended and covered by the hydrate case; no existing test depended on the old behaviour.
- **Downstream (sereus):** devices with existing data will hit the format break, and sereus's integration assertion on `default/` block ids needs updating. That work is outside this repo, and the implement handoff already flagged it for coordination, so no ticket was filed here.
- **Source hygiene:** `table-identity.ts` is small and focused, and comments are clear. The review diff adds no new size debt.
- **Majors filed:** none.
