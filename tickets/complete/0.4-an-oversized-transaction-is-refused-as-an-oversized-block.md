# An oversized transaction is refused as an oversized block

GitHub #61. One SQL transaction of more than about 7 MiB of 1 KiB rows was refused with `BlockTooLargeError` naming its log block, and nothing checked size until the whole transaction had been staged (the reporter's 56k-row transaction spent 4.4 minutes and 3.3 GB first).

## What landed (`ticket(implement): an-oversized-transaction-is-refused-as-an-oversized-block`)

- **The transaction is judged before the block.** `oversizedWriteRefusal` in `packages/db-core/src/network/block-size.ts` is the one rule both staging sites call (`stageAttempt` and `TransactionCoordinator.declareTouchedBlocks`): when a touched block is over `MAX_BLOCK_BYTES`, the attempt's transforms (with the log append) are measured, and over `MAX_TRANSACTION_BYTES` the write is refused as `TransactionTooLargeError` with the action id. Only a block over the limit inside transforms under it — a block grown over several writes — is still `BlockTooLargeError`.
- **Refusal while staging.** Each open-segment unit carries its encoded size (`StagedUnit.bytes`, measured once); `SegmentList.openBytes()` is a running total kept right by `setOpen` (now the path for seal and unseal too) and `pushOpen`. `Collection.actInternal` refuses, before staging, an `act` that would take the total past the limit (`assertStagedActionsFit`), with `actionId: undefined`. Replays and filter replacements keep or re-measure sizes.
- **`TransactionTooLargeError`**: `actionId` is optional, `bytes` is documented as a lower bound, message says "at least".
- **Docs**: docs/internals.md §A transaction's size limit gives the measured row-data ratio (about 3.4 MiB of 1 KiB rows per transaction), the BLOB note, the three refusal sites, and "The transaction is judged first".

## Review findings

Read the implement diff first, then the handoff.

**Correctness — checked, one finding fixed.**
- The staging check is sound as a lower bound: a commit's log entry carries every open-segment action verbatim inside the transforms, so summed separate serializations are no more than the pend's. It runs under the collection latch (`act` and `actAndSync` both take it), so two concurrent `act`s cannot both pass on a stale total.
- Every write to the open segment goes through `setOpen` or `pushOpen` (grepped every `this.units` write in `segments.ts` and every `setOpen`/`pushOpen` caller in `collection.ts`: consume, filter, restore's three arms, clear, unstage, replay), so `openBytes()` cannot drift. The replay's in-place unit rewrite keeps `bytes`. A sealed segment drops out of the count on seal, which is right: it commits as its own entry.
- `actAndSync` refuses at `actInternal` before its try/unstage, with nothing staged; an `act` refusal leaves the tracker untouched (it throws before `internalTransact`).
- Consumers of `TransactionTooLargeError.actionId` (`pendFailure`, `classifyCommitFailure`) only use the class, so `undefined` breaks nothing; no other package constructs or reads it.
- **Fixed (minor, doc accuracy):** both the `NOTE:` on `oversizedWriteRefusal` and the last sentence of the "The transaction is judged first" bullet in docs/internals.md said transforms can be under the limit while a block is over it "only through a base that was already over". That is false: a base under the limit grown past it by one more write (exactly the existing two-grows test) gives transforms under the limit and a block over it. Rewrote both: that case is a block grown by earlier writes, refused as the block, including the narrow edge where the pend's envelope would also put it over the transaction limit (both refusals are true there, and only the block's tells the writer splitting won't help). The handoff's "remaining edge" description carried the same mistake.

**Tests — checked, none added or cut.** The two `TransactionTooLargeError` reproductions (sync and coordinator paths) and the staging-refusal test pin named behaviour with real branching; the two-write `BlockTooLargeError` cases pin the ordering. The `collection-segments.spec.ts` and `coordinator.spec.ts` edits are mechanical signature updates. No test for `TransactionCoordinator.applyActions` throwing the staging refusal: it is the same `collection.act` call already pinned, and the SQL path was exercised by hand in implement.

**Performance — checked.** One `JSON.stringify` per staged action, measured by the implementer at under 1% of SQL staging; transforms are serialized only on the oversized-block refusal path. No tripwire needed.

**Resource cleanup / error handling — checked, nothing found.** The refusal is a throw before any state change; nothing to release beyond the latch, which `finally` releases.

**Docs — checked.** Read docs/internals.md §A transaction's size limit in full, docs/offline-sync.md's classification table (too-large row unchanged and still right), packages/db-core/docs/btree.md and packages/db-p2p/docs/cluster.md mentions (no claim affected). `yarn lint:docs` clean.

**Known gaps carried from the handoff (accepted, no ticket):** the staging refusal fires at about twice the row volume the commit admits — by design, documented, and the fix (carrying row data once) is plan ticket `a-large-write-costs-time-and-space-per-byte`; staging is judged per collection, the cross-collection sum still at the pend.

**Validation.** db-core `yarn test`: 2063 passing. `tsc --noEmit` clean for db-core; eslint clean on the edited file; `yarn lint:docs` clean. The review's edits were a comment and one doc sentence, so the plugin and db-p2p suites (green in implement) were not re-run.
