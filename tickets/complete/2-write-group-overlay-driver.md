# Write-group overlay driver

First of three tickets from `file-storage-pays-one-fsync-per-write-group` (GitHub #37). Landed in `ticket(implement): write-group-overlay-driver`; `file-storage-commits-groups-through-a-log` and `file-store-checkpoint-and-shared-log` built on it and are in their own review.

## What landed

- **`BatchBackend`**: the contract a backend implements instead of a `RawStoreDriver` when it takes writes a group at a time: reads, two fully drained listings, and one write, `commit(entries)`, atomic and as durable as its `durability` says. `StoreKey` addresses a record of any of the six stores; `canonicalStoreKey` gives each a string with the block id length-prefixed, so a collection-name block id or a client-chosen action id cannot run into the rest of the key.
- **`WriteGroup<K>`**: the key-agnostic overlay (canonical key to bytes or a delete marker, each tagged with the sequence of the batch holding it) plus the open batch in resolution order. `put` and `delete` record and resolve at once. `flush()` seals and commits with the four cases rules 3 to 5 of the flush contract need: nothing to do resolves at once; nothing to do under a commit in flight waits for it; writes under a commit in flight wait and then share one next commit with every other flush that arrived meanwhile; a rejected commit latches the group failed, so every later write and flush throws `StoreFailedError` carrying the cause while reads keep serving the overlay. When a batch commits, only the overlay entries of that batch's sequence are dropped, so a key rewritten after the seal keeps serving its newer value. The first write of an open batch arms an unref'd idle timer (`idleFlushMs`, default 1000 ms, injectable `setTimer`); an idle flush failing is logged once under `optimystic:db-p2p:write-group:error` and latches the group. `close()` flushes once more and cancels the timer.
- **`WriteGroupDriver`**: a `RawStoreDriver` over `WriteGroup<StoreKey>` and a `BatchBackend`. Point reads consult the overlay first; listings snapshot the overlay before awaiting the backend and merge over the backend's rows; `promote` records its two entries with no await between them; optional members are wired only when the backend has them; `close` flushes, then closes the backend in a `finally`.
- **`IRawStorage.close?`**, wired by `KvRawStorage` only when its driver has one, under the no-stub rule. The conformance reopen case calls it before reopening.
- **`MemoryBatchBackend`** (`./testing` entry, no devDependency): keeps every committed batch in `committed`, with a `beforeApply` hook to park or fail a commit. The conformance suite runs `WriteGroupDriver over memory` as persistent, the reopen being a second driver over the same backend.
- Docs: Invariant 6 of `packages/db-p2p/docs/storage.md` gained the driver row and the *Writes that wait in memory* paragraph; `docs/debugging.md` lists the `write-group` namespace.

**Read with fresh eyes, checked by inspection and by running the worktree:**

- The sequence rule on the overlay drop (a key rewritten after its batch was sealed keeps the newer value), the in-order single-commit chain, the shared next commit for flushes arriving under one in flight, and the failure latch, each against the four flush cases. A commit rejected *synchronously* (a sink that throws instead of returning a promise) is caught by the same `try`, and only leaves `inFlight` holding an already-rejected promise; harmless, since the latch is checked ahead of every path that would read it.
- Listing merges: `rangeRevisions` keys by revision, `listPendingActionIds` by action id, `listBlockIds` by block id, so an entry present in both the overlay and the backend during the commit (and, after the deadline work, until durable) collapses. The overlay snapshot is taken at the generator's first `next()`, which is still before the first `await` of the backend. A block whose metadata moves from the overlay into the backend mid-stream is yielded once either way.
- `promote` reads overlay-first and records both entries without an await between them. The read-then-record race against a concurrent delete of the same pending record is the one every native backend's promote already has, and `StorageRepo` holds the block's latch across it.
- `close`: waits for the commit in flight, flushes the remainder once, closes the backend in a `finally`, so a failed store still releases it (the close then rejects with `StoreFailedError`, which is the right answer).
- `IRawStorage.close` wiring: `KvRawStorage` installs it only when the driver has one; `CachedStoreDriver.close` (which existed before this ticket) closes its inner driver, so `CachedRawStorage` now exposes `close` doing what `dispose` does; the shared-cache hazard of a lease holder closing it is the one `dispose` already had and the lease doc already forbids.
- Docs: Invariant 6's driver row and paragraph in `packages/db-p2p/docs/storage.md` match the implement commit's behaviour; the later file-backend ticket added its own row and paragraph beneath them without contradicting them. `docs/debugging.md`'s `write-group` row names `idle-flush-failed`; the deadline ticket's `durable-failed` line is that ticket's to add.
- Exports: `src/index.ts`, `src/rn.ts` and `src/testing/index.ts` carry the new modules; the entry-parity guard passed in the worktree.

**Minor, fixed in this pass:**

- `WriteGroupDriver.rangeRevisions` copied every backend row into a map and sorted on every call, even when the overlay held nothing for the block; `materializeBlock` lists revisions of every block it reads, so the hot read path paid a sort for nothing. It now yields the backend's already-ascending rows directly when the overlay has none for the block, and merges through `mergeRevisions` otherwise (`packages/db-p2p/src/storage/write-group-driver.ts`). Covered by the existing ordering test, which exercises the merge arm, and by the conformance listings, which exercise the direct arm.
- The wrapper-forwarding `NOTE:` on `RawStoreDriver` (`packages/db-p2p/src/storage/raw-store-driver.ts`) still said the tree had two wrapper drivers and that `CachedStoreDriver` withholds `close`. It now names `WriteGroupDriver` as a wrapper over a `BatchBackend` rather than a driver, which is why the shared forwarding check it asks for at a third driver-over-driver wrapper does not cover it, and states `CachedStoreDriver`'s `close` correctly as its own method.

**Major: none.** Nothing found rises to a ticket: no defect reachable now, no class-level invariant missing. The one class-shaped concern (the per-listing overlay scan) is conditional and is parked as a tripwire below.

**Tripwires recorded:**

- *Writes after `close()` are not refused* — `NOTE:` at `WriteGroup.close` in `packages/db-p2p/src/storage/write-group.ts`: such a write sits in the overlay with no idle timer. Nothing writes to a closed store today; if something does, add a closed state that makes `record` throw.
- *The conformance reopen case proves flush-or-close, not flush alone* — `NOTE:` at the `storage.close?.()` call in `packages/db-p2p/src/testing/raw-storage-conformance.ts`: `close` flushes too, so over a group-committing driver a flush that did nothing would still pass it. Flush alone is pinned by the driver's own spec; the power-loss double the deadline ticket plans is what can prove it for a real backend.
- *Every listing scans the whole overlay* — already the `NOTE:` at the overlay map in `write-group.ts`, rewritten by the deadline ticket to say the overlay is bounded by `maxUnsyncedBytes`. Worth stating here: 64 MiB of small entries is tens of thousands of overlay entries, and once syncs are deferred by a window the overlay routinely holds several groups, so if listing shows up in profiles the fix is a per-block index over the overlay, not a smaller bound.
- *`approximateBytesUsed` excludes the overlay* — accepted as is, forwarded exactly as `CachedStoreDriver` forwards it; an estimate.

**Considered and declined:**

- Refusing a sink `commit` that throws synchronously, or clearing the stale `inFlight` it leaves: the latch makes it unobservable, and wrapping the call would add a layer for a contract violation the type already forbids.
- Making `WriteGroupDriver.close` prefer the flush's rejection over a rejecting `backend.close` in its `finally`: both are storage faults on a store already latched; not worth a second catch.
- `MemoryBatchBackend.rangeRevisions` walking `lo..hi` one revision at a time: parity with `MemoryStoreDriver`, and every caller's bounds are real revision numbers.

**Tests:** none cut, none added. Each test in `test/write-group-driver.spec.ts` pins a contract case rather than the implementation: the four flush cases, the sequence rule on the overlay drop, the delete that hides a backend record, the latch, ordered and bounded merges, the idle timer's arm and disarm, and `close` under a commit in flight. The optional-member forwarding test stays because the no-stub rule is a contract the type system cannot enforce (an optional member present-and-stubbed type-checks), the same reason the two existing wrappers have one. The two tests the handoff offered up as beyond the by-inspection bar (close racing a commit, failure in the idle flush) are each a few lines over real branching in `WriteGroup`; kept. The `rangeRevisions` change needed no new test, since the existing ordering test exercises the merge arm and the conformance listings the direct arm.
