# A cancel that misses the approval bar strands the writer's pending record — complete

Reported by sereus (sereus-sam, 2026-10-12) on 1.13.0; their write-up is `C:\projects\sereus\tickets\blocked\optimystic-failed-cancel-strands-the-writers-pend-record.md`.

## What was wrong

At three members the promise bar is all three, so one silent member sinks the write's commit and then every round of the cancel that should discharge its pend (a cancel is itself a cluster transaction). `NetworkTransactor.dischargeCancel` threw, the caller let the commit's error win, and the cancel was forgotten. When the member returned, every member holding the record voted `held` on every later write to the block, from any machine.

## What was built

`OwedCancels` (one per `NetworkTransactor`) keeps the blocks a cancel left unanswered when `dischargeCancel` runs out of budget, and re-sends that cancel:

- before the transactor's next pend of any of those blocks (one bounded round, not the six-round loop; concurrent pends join one in-flight re-send per action);
- on one unref'd backoff timer (1 s doubling to 30 s, jittered) while anything is owed, so other writers are freed without this one writing the block again.

A pend of an owed action id supersedes the owed cancel for every block it names (removed synchronously, any in-flight re-send awaited first), since a late cancel would delete the fresh record. At most 256 actions are kept; the oldest is evicted and logged. `owedCancelBlocks()` is a diagnostic snapshot. `stop()` (added in review) disarms the timer and logs and forgets what is still owed. `unrefTimer` moved to db-core, as the lint rule's NOTE asked for the first db-core timer that needs one.

Reproduction (`failed-cancel-does-not-strand-the-writers-pend.spec.ts`): before, phase 3 failed after ~16 s with `SyncRetryExhaustedError … held by unresolved rival action(s)`; after, it lands on its first pend in ~40 ms.

## Review findings

Read the implement diff (`ticket(implement): a-cancel-that-misses-the-bar-strands-the-writers-pending-record`) before the handoff.

**Checked and found sound:**
- Correctness of supersession ordering. `beforePend` removes the action's own blocks before its first `await`, so no later re-send can carry them, and awaits any re-send already in flight, so it lands (or times out) before the pend. Blocks the new pend does not name stay owed. Every pend path goes through `NetworkTransactor.pend`: `TransactorSource.transact` (which includes `Collection.completeOwnEntry`'s same-id re-send) and `TransactionCoordinator`'s pend phase. So no same-id re-pend skips the check.
- Same-id retries inside `Collection.syncAttempts` after a failed commit and a failed cancel: each retry pend supersedes the owed cancel, and the last attempt's failed cancel is recorded again. So the state that ends up owed is correct.
- `dischargeCancel`'s two exits: success clears every requested block, and failure clears the blocks that were answered before recording the rest. A partly answered earlier entry for the same action is narrowed correctly.
- Timer bookkeeping. `fire` marks entries in flight before `arm`, so a running re-send never double-arms. `.finally` re-arms after `nextAttemptAt` moves. A timer due later than a new due time is replaced. Nothing that is never awaited can reject (`resend` catches; `beforePend`, `supersede` and `attemptOnce` never reject).
- Eviction keeps the newest entry and evicts by first-record order. A timer left armed after an eviction fires for nothing, which does no harm.
- Cross-platform: `armUnrefTimer` guards `unref`, and the module uses only `Map`, `Set` and `Promise.prototype.finally`.
- Tests: both new db-core specs pin behaviour the mesh reproduction cannot reach (the timer path, and same-action supersession with a remainder). The phase-3 tightening in the mesh spec ("lands on its first pend") pins the pre-pend path. None restates the implementation or tests a mock. No test was cut and none added.
- Docs: `docs/repository.md` §"A pending record's lifetime is bounded by its writer", `docs/debugging.md`'s `network-transactor` row, `packages/db-p2p/readme.md`'s unrefTimer location, and the backlog arm all describe the new behaviour. I also checked `docs/correctness.md` and `docs/internals.md`, which mention cancels and stranded records. They describe the abandoned-writer and node-side residuals, which this change does not alter, so they needed no edit.

**Found and fixed in this pass (minor):**
- **A stopped node's transactor was kept alive forever.** The re-send timer is a garbage-collection root. A transactor that still owed a cancel when its node stopped kept retrying every 30 s against a node that can never answer, and kept the transactor and the node graph it references in memory for the life of the process. This happens to an embedder that tears its stack down and builds it again, as a phone app does. Added `OwedCancels.stop()` and `NetworkTransactor.stop()`, which disarm the timer and log each still-owed action as `cancel:owed-abandoned` before forgetting it. A `record` after `stop` is logged the same way and not kept. `CollectionFactory.shutdown` stops every network transactor before it stops its nodes. `CollectionFactory.dispose` deliberately does not stop them: its nodes keep running, so the dropped transactor's re-sends can still land, and the timer releases it once nothing is owed.
- Stale wording: the cancel-budget NOTE in `CollectionFactory.createNetworkTransactor` said a failed cancel "leaves its pending records standing"; it now says "until a re-send lands". In `dischargeCancel`'s NOTE, in `docs/repository.md` and in the backlog arm, "drops its transactor" became "stops its transactor": a dropped transactor whose node is still running keeps re-sending. `docs/debugging.md` lists `cancel:owed-abandoned`.

**Considered, not filed:**
- A pend that overlaps an owed cancel waits for one cancel round, up to `abortOrCancelTimeoutMs` (5 s by default) if the coordinator hangs rather than refuses. This is the trade the implement ticket chose, on the grounds that a cohort that cannot approve the cancel cannot approve the pend either. I agree with it and did nothing.
- A late cancel can delete a same-id re-pend by a path the writer cannot see: the coordinator's commit-retry and `takeOwedRecords` deliveries, or a cancel request that timed out on the client but is still in flight at the server. This predates the change, since any self-cancel followed by `syncAttempts`' same-id retry already had it, and this change does not widen it. No new site for it; recorded here only.
- Several `NetworkTransactor` instances in one process do not share their owed sets. That is harmless while action ids are minted per writer per sync. It is a condition, not a defect, and is recorded in the handoff only.
- No test for `stop()`. It is a straight-line disarm and clear, and the decline paths it guards are logged. Under the tests-must-pay rule it did not earn one.

**Empty categories:** no major findings, so no tickets were filed. The only residual is the exiting or stopped writer, which already belongs to backlog `debt-unpromotable-pending-records-need-a-sweep`; its arm was updated.
