## What landed

**The degrade (`refreshLive` in `optimystic-module.ts`).** Every live refresh in the vtab now goes through this one method: `runQuery`'s main-tree and index-tree refresh, and the write path's `probeUniqueConstraint`, `ensureUniquePopulated` and `populateUniqueTree`. It works as follows:
- When the mode is not entered, or the table's policy is `'network'` (`OfflineMode.degradesLiveReads`), it calls plain `tree.update()`, which fails as it always has.
- Otherwise it first asks the table's gate (`OfflineMode.cohortReachable`, with `gateBlockIds(collection)`). A closed gate skips the refresh, and the read is served from this machine's view.
- If the gate is open, it refreshes. A failure that `isCohortUnreachableRead` accepts (a `BlockUnavailableError` with reason `cohort-unreachable` or `peers-unreachable`) is absorbed and the read is served locally. Every other failure propagates.
- Each outcome calls `OfflineMode.noteLiveRefresh(servedLocally)`. A successful refresh reports `false` in or out of the mode, so the flag clears after `exit()` on the next read. A refresh that throws reports nothing.
- The first locally served read of a table logs `offline:read-served-locally` (module namespace) with `because=gate-closed` or the unavailability reason. The next successful refresh resets that flag.

**The gate (`CollectionFactory.getCohortReachability` and `registerCohortReachability`).**
- It is a registry keyed like transactors (`${transactor}:${keyNetwork}`).
- `getCohortReachability(options)` returns one stable delegate per key. The delegate looks up the registration each time it is asked, so the order in which tables and registrations happen does not matter.
- With nothing registered it answers `alwaysReachable`.

**How the gate reaches the controller.** Since the queue's gate is fixed when the queue is built (before any table exists), the gate is not passed at construction:
- Each vtab publishes its transactor's gate together with its policy. `OfflineMode.setTablePolicy(table, policy, reachability)` now takes three arguments, and `publishOfflinePolicy` passes `getCohortReachability(this.options)`.
- The controller's private `reachability` field is the gate it hands the queue (`OfflineQueueOptions.reachability`). When the queue asks, it maps each block id to tables through `bridge.tablesOf` (header ids are collection ids; tail ids map to nothing), collects those tables' distinct gates, and requires all of them to answer reachable. In practice that is one gate, because an entry is on one transactor. With no gates found it answers reachable.
- A read asks the same per-table gate. If a gate throws, the read treats it as reachable (logged `offline:reachability-threw table=…`) and lets the refresh decide; the queue treats a throwing gate as closed. The asymmetry is deliberate: a read that tries the network classifies its own failure.

## Tests added — `test/offline-mode-reads.spec.ts` (two-node mesh, 5 cases, about 1 s)

How the spec makes the cohort unreachable: node A's transactor is wrapped in a Proxy and registered under `shared:test`. While `armed`, it answers every `get` with `unavailable: 'cohort-unreachable'`, and it counts every `get`.

- **A `'queue'` table, unreachable.** A committed seed row plus a row queued while armed are both read back. `expectLookupsAgreeWithScan` passes on the body index, `readsServedLocally` is true, and B does not have the queued row. After disarming and `whenDrained`, the next read clears the flag and B has both rows.
- **Fail-loud arms.** With the mode not entered, a read of `Notes` fails. With the mode entered, a read of a `'network'` table fails. In both, `BlockUnavailableError` (`cohort-unreachable`) is reachable along `cause`, and the flag stays false.
- **Gate closed.** A registered gate answering `false`: the queued entry waits with `waitingFor: 'cohort'` and never reaches `submitting`. A live read makes zero `get` calls and is served locally. After opening the gate, the queue drains to B. This pins that the queue and the reads ask one gate.
- **A table never read on A.** B creates and writes it, A hydrates it, then armed in offline mode A's `select` fails with `BlockUnavailableError`. The failure comes from the table's first initialization, not from `refreshLive`.
- **UNIQUE column.** An insert into a table with a UNIQUE column, armed in offline mode, is queued (the probe's refresh degrades) and drains to B.

Mutation check: with `degradesLiveReads` forced to `false`, cases 1, 3 and 5 fail. Cases 2 and 4 are the negative arms and pass either way, as they should.

## Known gaps and judgement calls for the reviewer

- **"Committed blocks it holds", as tested,** means blocks in the collection's read cache, because the wrapper answers every `get` as unavailable. On a real node, a block the node's own store holds is answered by its coordinator (the "merely-stale block keeps its real local answer" rule in internals.md). That path is not exercised here; stage 6's two-machine scenario is the natural place.
- **Until stage 6 registers the `network` gate,** a degraded read on a real node still pays the refresh's network timeouts on every read before it is served locally. The README says so under "Not yet".
- **`populateUniqueTree` still needs the network.** Its refresh degrades, but its `tree.sync()` does not, so in offline mode with the cohort unreachable, the first write that probes a synthesized unique tree an older build left empty fails. A `NOTE:` tripwire at the site names the remedy.
- **A refresh that fails mid-replay,** after adopting a newer revision, leaves a half-restaged collection. That is pre-existing, backlog `debt-a-failed-refresh-can-leave-a-collection-half-restaged`. With the degrade, the read that met it is served from that state instead of failing. It needs the cohort to vanish between the refresh's first request and its replay. Not parked as a separate note, since the debt ticket covers the state.
- **Not routed through `refreshLive`, deliberately:**
  - the CREATE INDEX backfill's `collection.update()`, which is DDL and already gated by queued entries;
  - `verifyIndexes`, which is a diagnostic and should fail loudly.
- **`readsServedLocally` is one flag for the whole database** ("the last live read"), so reads of two tables, one served locally and one refreshed, can toggle it back and forth. This is per the design.
- **Checked by reading only, not tested:**
  - a refresh failing with another reason (`claimed-elsewhere`, `named-by-log`, `BlockPossiblyStaleError`) propagates;
  - a live read inside an open transaction degrades (`refreshLive` has no transaction branch);
  - the once-per-episode log;
  - `offline:reachability-threw` on the read side;
  - the committed read path is untouched.
- **The design doc and the garden report cite backlog `a-live-read-on-an-isolated-node-fails-instead-of-serving-what-it-holds`,** but no such ticket exists on the board or in `tickets/.pruned-tickets.jsonl`. The reference was left as it stands; this ticket answers it only inside offline mode.
