## What changed

Quereus 5.4.0 never sends a module a required ordering for a `nulls last` key (Quereus invariant OPT-063, `extractOrderingFromSortKeys` in `@quereus/quereus/src/planner/framework/physical-utils.ts`), so every required ordering a module sees means NULLs first, in both directions. The index tree frames NULL below every present value (`encodeKeyElement` in `src/schema/key-encoding.ts`), so a forward walk already emits NULLs first.

`walkDelivering` used to ask `nullSafeOrderingPrefixLength` about every key column as if it were descending, which refused a nullable matched column in both directions. It now passes the walk key as it is (`KeyColumn` carries no `desc`, so the key reads as ascending in its bytes) and the walk's `reverse`, so the helper gates only a backward walk.

| statement over nullable `s`, index on `s` | before | now |
|---|---|---|
| `order by s` / `order by s nulls first` | engine Sort | index walk, forward |
| `order by s nulls last` | engine Sort | engine Sort (engine sends no ordering) |
| `order by s desc` / `order by s desc nulls first` | engine Sort | engine Sort (backward walk would put NULLs last) |
| `where s is not null order by s desc` | backward walk | backward walk |

A `NOTE:` tripwire on `walkDelivering` records that `OrderingSpec.nullsFirst` is not read. Docs (internals bullet "No NULL backwards", README ORDER BY sentence, index-walk and spec headers) were updated and the retired blocked-ticket citation removed.

Implement commit: `ticket(implement): an-ascending-walk-serves-a-nullable-column`.

## Review findings

**Checked.**
- The diff, read before the handoff. The one-line logic change is right: `walkKeyColumns` builds `KeyColumn`s with no `desc`, so `!!col.desc === reverse` in `nullSafeOrderingPrefixLength` (`@quereus/quereus/src/vtab/best-access-plan.ts`) skips every column on a forward walk and checks every column on a backward one. The doc comment's claim that an index column's own `desc` is ignored still holds.
- The OPT-063 premise, in the Quereus source: `extractOrderingFromSortKeys` returns no ordering for `nulls: 'last'`, and the `Ordering` doc and `docs/invariants.md` OPT-063 say an ordering means NULLs first in both directions.
- The read path's handling of NULLs: `compareSqlValues` sorts NULL lowest, the same as the tree's framing, so a NULL-keyed row in `inEngineOrder` is a pivot that compares the same way under both orders, and a run sort agrees with the tree.
- The walk-then-scan finish (`restOfWalk`) with NULL index values past `WALK_ROWS_BEFORE_SCAN`, which the handoff had judged covered by construction but not tested. This ticket made that path reachable.
- The equality-prefix shape the handoff said was untested at planner level (`where g = 'x' order by u, id` over an index on `(g, u)` with interleaved NULLs). I checked it with a throwaway differential probe against a memory table, which I then deleted. It plans as an INDEXSEEK with no Sort, matches the memory table's rows and order, keeps the Sort for `order by u desc, id desc`, and walks backward under `u is not null`.
- Docs: `docs/internals.md`, the plugin README, and the index-walk and spec headers all match the new behaviour. Nothing outside the ticket still cites the retired blocked ticket except `tickets/.garden-report.md`, which is a historical report and was left alone.
- Validation: the whole `yarn test` in `packages/quereus-plugin-optimystic` passed (1377 passing, 14 pending, smoke ok against quereus@5.4.0), and `yarn typecheck` and eslint on the changed files are clean.

**Found and fixed (minor).**
- The contract "a forward walk of a nullable column that crosses the 256-entry switch inside its NULL group returns the engine's rows in the engine's order" had no test. I added one case to the existing long-walk fixture in `test/index-ordered-walk.spec.ts`: a nullable `u` column, NULL on the 300 low rows, with an index `idx_u`. The test checks `order by u, id` against the memory table, and checks that the read crossed the threshold (`scan=1`) at 256 entries. It passed first time, which confirms the handoff's by-construction argument.

**Major findings.** None. The change narrows a refusal that was conservative, and the remaining refusal (backward walk over a nullable column) is exactly what the NULL placement requires.

**Tripwires.** No new ones. The implementer's `NOTE:` on `walkDelivering` (a forward walk must decline `nullsFirst: false` if the engine ever sets that field) is the right place for that condition.

**Tests reviewed.** The two changed tests each pin a distinct claim: planner-level claim or refusal per direction, and the end-to-end order against the memory table, including explicit `nulls first`/`nulls last`. Neither restates the implementation. Nothing to cut.

**Not run.** `yarn test:integration`. This change only affects plan choice for an ascending `order by` over a nullable indexed TEXT column. The integration specs exercise meshes and reactivity, and the read path they would take is the one the differential suites above cover.
