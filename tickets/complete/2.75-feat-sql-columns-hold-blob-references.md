# SQL columns hold blob references — the holding period

Last of the four parts that build the SQL side of blobs. Landed in `ticket(implement): feat-sql-columns-hold-blob-references`, with the review fixes below. It closes the one pin no transaction ever answered for: a `put` made outside any transaction is pinned `sql-unstaged/<putAtMs>`, and only an online commit that staged the reference ever dropped one — so a cancelled upload, a failed insert or a stopped process kept those bytes for ever.

## What shipped

- **`parseUnstagedHoldingMs` and `DEFAULT_UNSTAGED_HOLDING_MS`** in `blob-pins.ts`, read in `register` beside `moduleCostProfile` so a bad value throws before anything is built. Default 24 hours. `''` and `null` count as unset, as they do for `cost_profile`; anything else that is not a finite positive number throws.
- **`SqlBlobPins.sweepUnstaged(now?)`**, on the same work chain as `settleQueued` and `reconcile` — so it waits for any open transaction to end and never runs beside the other two, the three being the only things that read and write one blob's pins. Per known backend: collect every `unstaged` pin past `putAtMs + holdingMs`, then release each one no unfinished transaction is relying on, logging `blob:unstaged-expired`. It collects before it releases, following `listStalePins`, and lists the live pins only once something is actually expiring — so the steady state pays one listing of the machine's blob records rather than two.
- **The protected set, in two halves**, because a reference pin is not written until its commit starts: every reference carrying a reference pin whose transaction `isLive` answers for (the open transaction once its commit has started, and every QUEUED transaction, whose pins stay until the queue finishes with it); and `TransactionBridge.openBlobReferences()`, the fold `addedReferences` takes over the OPEN transaction's ledger, which is the only record of a reference a statement has staged and whose commit has not yet pinned. The ledger half is asked per expiring pin rather than folded into one up-front set: the chain's idle wait covers the transaction open when the step starts and says nothing about the next one, so a statement can begin behind a running pass.
- **The timer**: one `unrefTimer(setInterval(...))` per `SqlBlobPins`, armed by the first blob backend to resolve (with a sweep at each resolution), period `max(60s, min(holdingMs/4, 1h))`, cleared by `dispose()` before it awaits the chain.
- **A second log line, `blob:unstaged-unreadable`**, for an `unstaged` label whose time this build cannot read: left pinned for ever and logged once per label, since releasing a pin whose meaning is unknown drops somebody's bytes.
- **Docs** — the status line in docs/blobs.md (SQL built in all four parts; reclaiming is what is left), both §SQL bullets, the holding-period and protected-set prose finishing docs/internals.md §A table's blob references, the two new log lines in docs/debugging.md, the README's config row and its blob bullets, plus the review's additions below.

## Review findings

**Read first:** the implement diff, then the handoff.

**Checked by reading and running:**

- *Chain discipline.* Nothing in the sweep awaits the chain (`knownBackends`, `listPins`, `unpin`, `openReferences` only), so a chained sweep cannot deadlock on itself. `dispose()` clears the interval before it awaits the chain and the chained step bails on `disposed`, so a disposing host neither waits for an interval it has stopped caring about nor leaves one running; a backend resolving during a dispose arms nothing.
- *The `isActive` guard the handoff asked about.* `openBlobReferences` and `plugin.ts`'s `isLive` read the same field and apply the same predicate, and so does `whenTransactionIdle` (`isTransactionActive`). Confirmed that both `endTransaction()` and `rollbackTransaction()` set `isActive` false while leaving `currentTransaction` and its reference ledger in place until the next `begin` — nothing clears the ledger on rollback — so the guard is load-bearing. It now has a test; see below.
- *Commit ordering.* `holdForCommit` runs before `endTransaction()` in `commitTransaction`, so a reference is pinned while its transaction is still active. There is no window in which neither half of the protected set answers for a staged reference and no reference pin exists yet.
- *Byte safety against the online arm, which runs OFF the chain.* Walked each interleaving of a sweep with `committed()`. `unpin` releases one labelled hold and a blob keeps its record while any hold remains (`LocalBlobService.unpin`), so dropping an `unstaged` pin beside a surviving reference pin cannot lose bytes; every ordering leaves a landed reference held by either the announcement's `owed` hold or a kept reference pin.
- *Startup ordering.* The first sweep is armed by `backendResolved` and is not gated on `reconcileReady()`, so it can run before the offline journal's restore has repopulated `holdsTransaction`. Not a defect: a journaled queued transaction's reference pins were written before its seal and are durable, so they hold the bytes whatever that sweep does with the `unstaged` pin.
- *Boundaries and arms.* `parsePinLabel`'s digits-only rule against a host owner that collides with the plugin's prefix; `unstagedSweepPeriodMs` at the default and at a one-second period; the clock-moved-backwards arm; `unreadableUnstaged`'s growth bound; `unrefTimer` over a browser or React Native `setInterval`.
- *Every doc the change touched, against the code rather than against each other* — docs/blobs.md's status line and both §SQL bullets, docs/internals.md §A table's blob references, docs/debugging.md's two new lines and the `reason=sweep-unstaged` note on `blob:pin-listing-failed`, the README's blob bullets and config row. Also read docs/offline-sync.md §Nothing about blobs is journaled, which the README links and the change did not touch: it is about the journal and stays accurate.
- *The status line's "what is left to build is reclaiming" claim*, which the handoff flagged as worth a second pair of eyes. It holds: `tickets/implement/` carries only `2.85-feat-a-blob-remembers-when-it-was-last-found-unreferenced` and `2.86-feat-unreferenced-blobs-are-reclaimed`, both reclaiming, and nothing else open on the board touches blobs.
- *File size.* `blob-pins.ts` measured at 940 lines (`wc -l`), mid-pack among its own siblings (`collection-factory.ts` 1195, `offline-mode.ts` 1418, `txn-bridge.ts` 2381) and well under the roughly 3000-line bar this repo's own size-debt ticket uses. No split.

**Fixed in this pass:**

- *A README claim that was wrong for the default.* The `blob_unstaged_holding_ms` row described the sweep interval as "a quarter of this period and never oftener than a minute", omitting the one-hour cap the code applies — so for the 24-hour default it implied six hours where the sweep actually runs hourly. docs/blobs.md states all three bounds correctly; the README row now does too, and says what the default works out to.
- *A host-facing setting a settings form could not offer.* `blob_unstaged_holding_ms` was missing from the `quereus.settings` manifest in the package's `package.json`, so a plugin loader's settings UI had no field for it — while `parseUnstagedHoldingMs`' own comment justifies treating `''` as unset by appealing to that very form. Added beside `link_round_trip_ms`, the other plugin-level number setting, with no declared default so an untouched field stays unset.

**Test added — one, for the guard the handoff named as the gap:**

- *expires the pin of a reference only a rolled-back transaction ever staged* in `blob-pins-unstaged.spec.ts`. A put outside any transaction, then `begin; insert; rollback`, then one sweep past the period. The rollback keeps the put's own pin (`abandoned`, which `blob-pins-online.spec.ts` already holds) and leaves the ended transaction's ledger recording the add on a bridge that keeps that transaction until the next `begin` — so only `openBlobReferences`' `isActive` guard stops the sweep from reading the reference as still owed and holding those bytes for ever. Verified by mutation: replacing the guard with a plain null check fails this case, and the queued case's closing assertion with it.
- No test was cut. `parseUnstagedHoldingMs`' three cases follow `cost-profile.spec.ts`'s precedent for a config parse whose refusal is load-bearing, and the two sweep cases each drive a distinct branch of the rule.

**Considered and not filed:**

- *`livePinnedReferences` is redundant for byte safety.* Every reference it protects already carries a reference pin, which is itself a hold, so releasing the `unstaged` pin beside it cannot lose bytes — and the protection costs a second full listing of the machine's blob records whenever anything is expiring. Left as built: it keeps the application's own hold alive across a queued transaction that can still fail with nothing committed, which is the same "a retry should not have to upload again" bias `abandoned` takes deliberately. The listing cost is already parked as a `NOTE:` at `listExpiringUnstaged`, and the steady-state pass pays one listing, not two.
- *The ledger half's positive case stays unverified* — a staged reference protected while its transaction is still open. A chained sweep first waits for the open transaction to end, so no spec can observe one running inside one; the handoff reached the same conclusion. What is now covered is the half that could fail quietly, which is the guard above.

**Tripwires:** no new ones. The two the implement commit left — the per-pass listing of every blob record with no `mayHoldStalePins`-style gate (`NOTE:` at `listExpiringUnstaged`), and the residual instant between the `openReferences()` read and the `unpin` (`NOTE:` at `sweepUnstaged`) — were read against the code and are accurate as written, each stating its condition and its remedy.
