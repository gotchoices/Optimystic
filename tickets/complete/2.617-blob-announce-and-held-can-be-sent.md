# Blob `announce` and `held` can be sent — complete

Second of three parts of the blob copying work. The first part built the wire types; the third, `feat-blob-announcements-are-answered`, answers `announce` and `held` for real and is in `implement/`. This part shipped the sending side and the `responsible` hold's scope. Nothing in production calls the new methods yet; the placeholder responder in `BlobProtocolService` answers every `announce` `declined` and acknowledges every `held`, so a round trip against a current node already works.

Implemented in `ticket(implement): blob-announce-and-held-can-be-sent`, reviewed and amended here.

## What shipped

- **Scope bound.** `MAX_BLOB_SCOPE_CHARS = 1024`, counted in UTF-16 code units (`scope.length`). `blobScopeProblem(scope)` in `blob-protocol.ts` is the single rule: the wire codec's `scopeField` throws `BlobProtocolError` for an empty or over-cap scope (so the responder answers `refused: malformed` before `onAnnounce` runs), the client throws `RangeError` for the same before it opens a stream, and — after this review — the store refuses the same scope at `holdResponsible`. `BlobRequest`'s `announce.scope` is typed `BlobScope`.
- **Client.** `BlobProtocolClient.announce(peer, ref, scope, options)` resolves with the peer's `BlobAnnounceAnswer`; `held(peer, ref, options)` resolves once the peer's empty acknowledgement is read. Each parses the ref locally, asks the optional `acceptance` hook and throws `BlobPeerRefusesError` before dialing a peer known not to run the protocol, then follows `stat`'s exchange shape under the same `ProgressDeadline`. `stat`, `announce` and `held` share one `ClientExchange.readSoleAnswer` instead of three copies of the same try/catch/finally.
- **Acceptance.** `packages/db-p2p/src/blob/accepts-blobs.ts` holds `BlobAcceptance`, `BlobPeerRefusesError` and `blobAcceptanceOf`, over the new `Libp2pKeyPeerNetwork.protocolSupport(protocol, peerIds)` → `listed | unlisted | unknown`, which reads the same cached peer records `peersServing` does; `peersServing` is now expressed over it. Exported from `index.ts` and `rn.ts`.
- **`responsible` hold scope.** `BlobHold`'s `responsible` variant carries `scope: BlobScope`, and `holdProblem` refuses one without a non-empty string scope. `LocalBlobService` gained `holdResponsible(ref, scope)`, `responsibleScope(ref)` and `responsibleRefs()`.
- **Docs.** `docs/blobs.md` records the bound in the `announce` row, the don't-dial-a-peer-that-lacks-the-protocol rule, the scope on the `responsible` hold, and that only the answering side of `announce` and `held` remains.

## Review findings

### Read and run

Read the implement diff before the handoff summary. Checked by reading: the two new client methods and the `readSoleAnswer` extraction against the `stat` body it replaced (behaviour-identical — same `fail`/`finish` ordering, and `elapsed()` is still valid after `finish()`); `openAccepted`'s pre-dial refusal (nothing is opened, so nothing leaks); `blobScopeProblem` and `scopeField`; the `protocolSupport`/`peersServing` rewrite; the three new store methods and the record helpers behind them; `holdProblem`; `wireBlobFetcher`'s wiring; both entry files; and every docs edit against the code it describes.

Confirmed, rather than assumed:

- **`peersServing` is unchanged in behaviour.** This node was excluded before by filtering `others` and is excluded now because `protocolSupport` never writes an entry for it; a peer whose protocol list is empty read `false` before and reads `unknown` (so, not `listed`) now.
- **`protocolSupport`'s reading agrees with `membershipOf`** (`packages/db-p2p/src/libp2p-key-network.ts:1512`): a non-empty list is the peer's statement, an empty or absent one is `unknown`. Its docstring claims this; it is true.
- **The `Record<string, …>` return shapes are type-safe.** `tsconfig.base.json` sets `noUncheckedIndexedAccess`, so every caller is forced to handle the entry this node has no row in; `wireBlobFetcher` does (`?? 'unknown'`).
- **`holdProblem`'s new rule cannot strand a stored record.** It is a decode-time tightening, and an unreadable blob record aborts the whole sweep (`local-blob-service.spec.ts`, "a malformed record stops the sweep") — a severe blast radius. Safe because nothing in this repository has ever written a `responsible` hold: the only writer is the `holdResponsible` this ticket introduced.
- **The scope cap fits the header cap.** 1024 UTF-16 code units is at most about 6 KiB once JSON-escaped and UTF-8 encoded, against `MAX_BLOB_HEADER_BYTES` of 16 KiB. The "far under" claim holds.
- **The docs' claim that `stat` and `get` need no acceptance check is accurate.** `blob-holders.ts:39` filters candidates through `peersServing`, and the `stat` probe (`node-blob-service.ts:325`) draws only from those holders.
- **A `held` cannot be lost to the mid-identify window the implementer parked.** The peer being told is one that announced, so it has opened a blob stream to this node and libp2p has merged the protocol into its record — which is what the `NOTE:` at `blobAcceptanceOf` says. The note is correct and stays.

### Fixed in this pass

- **`assertScope` applied a weaker rule than the one `blobScopeProblem` claims to own.** It checked only for an empty scope, so a `responsible` hold could store a scope over `MAX_BLOB_SCOPE_CHARS` — one that `BlobProtocolClient.announce` then refuses locally with `RangeError`, which is exactly what the re-announce in `feat-a-referenced-blob-is-copied-to-its-cohort` would do with it, since that work reads `responsibleScope` and hands the result straight to `announce`. Latent rather than live: the only scope reaching the store today comes from a decoded `announce`, which the codec has already bounded. Fixed by having `assertScope` call `blobScopeProblem`, so the unannounceable scope is unrepresentable at the store's entrance rather than a future bug report. Decode (`holdProblem`) deliberately stays at "a non-empty string": tightening it would make a record written under a future, larger cap unreadable, and an unreadable record stops the sweep.
- **`BlobPeerRefusesError` sits one letter from the existing `BlobPeerRefusedError` and means something else** — raised without asking, for a peer whose protocol list lacks the protocol, against "this peer answered `refused` to one request". Not renamed: both `feat-blob-owed-copies-are-drained` and `feat-a-referenced-blob-is-copied-to-its-cohort` name it in their plans, and a rename would leave those stale for no behavioural gain. Instead each class's doc comment now names the other and states the difference, so a reader who meets one is told the other exists.
- `BlobProtocolServiceInit.onAnnounce`'s scope parameter is typed `BlobScope` rather than `string` — the gap the handoff flagged and left.
- `docs/blobs.md` §Holds now says a stored scope obeys the same bound an announced one does.

### Tests

Added one case to `packages/db-p2p/test/local-blob-service.spec.ts`: "a responsible hold keeps the pin, replaces its scope, and is enumerated past an unreadable record". The `responsible` hold is the one piece of real branching this ticket shipped with no test — create beside an existing pin, replace rather than accumulate, skip a record that no longer decodes, refuse an empty and an over-cap scope — and three queued tickets build on it, so the handoff's plan to leave it to the third part's end-to-end tests left a store contract unpinned for too long.

Cut nothing. The codec case the implementer added pins the new wire bound against a codec with real branching and pays for itself. Deliberately did **not** add a test for the pre-dial acceptance refusal: it is three lines of straight-line logic with nothing a test would pin that reading does not, and asserting that `connect` was never called would only restate the implementation.

### Tripwires

- `holdResponsible` always writes and flushes, because `at` is "last verified" — so a caller that re-verifies every responsible blob on a schedule pays one key-value write and one flush per blob per pass. `NOTE:` at the method, with that condition.
- The implementer's two existing `NOTE:`s were reviewed and left as written: the mid-identify `refuses` window at `blobAcceptanceOf`, and the per-record read in `responsibleRefs`.

### Considered and left

`blobAcceptanceOf` maps `listed | unlisted | unknown` onto `accepts | refuses | unknown`, a one-for-one rename that carries no extra information. Left as it is: the two downstream plan tickets both specify this module by name and type, and the renaming is what keeps the react-native-reachable client from importing anything of the key network but a type.
