# Summary

Importing `@optimystic/db-p2p/rn` threw at load on a Hermes runtime whose `TextDecoder` polyfill was not installed yet, because first-party modules ran `new TextDecoder()` at module scope. All eight first-party sites (db-p2p ×2, db-core ×4, db-p2p-storage-rn ×2) plus db-p2p-storage-fs (for uniformity) now build a memoized decoder on first use. `previewCommitDigest` no longer calls `structuredClone`; it uses a new `cloneDecoded` JSON round-trip in `raw-store-codec.ts`. A lint rule (`NO_MODULE_SCOPE_TEXT_DECODER`) and a child-process runtime probe (`test/module-load-globals.spec.ts`) keep the pattern from coming back. Both polyfills are still required, because multiformats and cborg construct `TextDecoder` at their own load and db-core calls `structuredClone` on ordinary paths. The readme says so.

Implementation details, the deliberate scope decisions (such as keeping `TextEncoder` at module scope and leaving `verifyPeerSig`'s catch-all alone), and the validation run are in the implement commit `fd37da9f` and its review-stage ticket.

# Review findings

**Read:** the full implement diff (`git show fd37da9f`), plus `storage-repo.ts` `previewCommitDigest`, `block-storage.ts` `materializeBlock`, `canonical-json.ts` and `canonicalBlockHash`, and every remaining `structuredClone` and `new TextDecoder` in `packages/*/src`.

**Correctness of `cloneDecoded` on the preview path:** confirmed.
- **Why it is safe:** `KvRawStorage` is the only non-test `IRawStorage` (the other implementer is `CrashingRawStorage` in `mid-ddl-crash.spec.ts`). A base built by `materializeBlock` is a JSON-decoded materialization with JSON-decoded forward transforms replayed onto it, so nothing in it can be `undefined` or non-JSON.
- **The `NOTE` is accurate:** a value in an update op's array that is `undefined` clones to `null` and hashes differently from an omitted key. Keys whose value is `undefined` drop identically under `canonicalJson` either way, so arrays are the real hazard, as the NOTE says.
- **Result:** no change.

**Lint rule:** `yarn lint` is clean, and every remaining `new TextDecoder()` in `src` is inside a function.
- **Per-message construction:** `cluster/service.ts:266`, `dispute/service.ts:80`, `protocol-client.ts:177`, `repo/service.ts:267` and `cohort-topic/host.ts:2483` build a decoder on every message. That is legal under the rule and predates this ticket.
- **Why no ticket:** it is not a load-time hazard, and nothing measured shows it costs anything.

**Tests:** `module-load-globals.spec.ts` plus `storage-repo.spec.ts` gave 133 passing (run from `packages/db-p2p`). I did not re-run the full suites: this review changed only readme prose, and the implementer's full-suite counts are in the handoff.
- **Stack-frame regex:** handles both `at fn (file:///…)` and `at file:///…`.
- **Attribution through the workspace symlink:** the probe attributes db-core `dist` frames to their real paths, because Node resolves symlinks by default. The implementer's pre-fix run listed the four db-core sites, which confirms it.

**Docs (fixed inline):** the readme's new paragraph (`packages/db-p2p/readme.md` § React Native) claimed the lint rule "keeps it that way" for both `TextDecoder` and `structuredClone`. The rule only covers `TextDecoder` construction, and the runtime spec only covers the `/rn` load graph. I reworded it to say exactly what each guard covers.

**Tripwire (not a ticket):** nothing guards `structuredClone` at module scope in `db-p2p-storage-rn`. Lint covers only `TextDecoder` there, and the runtime probe never loads that package. No such call exists today. The spec's header comment already records the probe's scope, so I added nothing further.

**DRY (considered and declined):** the two-line lazy getter is repeated in nine files. A shared helper would need a new public db-core export, plus a dependency on db-core from db-p2p-storage-fs, which does not have one today. The lint message points at the canonical example. I kept the repetition.

**`verifyPeerSig` swallowing a missing polyfill as "bad signature":** I agree with the implementer that this is effectively unreachable, since multiformats fails at startup first. Hoisting the call would change how invalid UTF-8 is handled. No action.

**Not verified:** behavior on a real Hermes device, same as the implementer. Nothing in this review could exercise it.

**Categories with nothing found:**
- **Resource cleanup:** the change creates no resources that need cleanup.
- **Type safety:** the getters are typed `(): TextDecoder`, and `cloneDecoded<T>` is honest about its constraint in its doc.
- **Performance:** one memoized instance per module, the same as before. `cloneDecoded` costs about the same as `structuredClone` on JSON-shaped data.
