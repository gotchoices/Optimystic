# A node takes all its storage as one value

## What landed

`NodeOptions.storage` is one value — a `NodeStorage` with a `blocks` (`IRawStorage`), a `kv` (`IKVStore`) and a `pieces` (`IPieceStore`) — in place of the three independent options `storage`, `kvStore` and `pieceStorage`, each of which used to default to its own in-memory store. The three provider types (`RawStorageProvider`, `KVStoreProvider`, `PieceStoreProvider`) and the instance-or-factory shape are gone with them, as are their re-exports from both node entries.

The reason for one value and not three options: each of the three used to fall back to memory on its own, so a host that supplied a block store and nothing else silently got a memory key-value store and memory pieces, and lost blob records and blob pieces at every restart with only a log line to say so. There is now no part of a node's storage a host can leave out, and a missing part does not compile.

### New module: `packages/db-p2p/src/storage/node-storage.ts`

- `NodeStorage` — the three stores. The read-cache ownership prose that used to live on `RawStorageProvider` moved onto `NodeStorage.blocks`: who leases, who releases, and which two cache constructions are accepted.
- `OpenNodeStorage` — `NodeStorage` plus `close()`. What a platform factory will return; the host closes it after `stop()`, since the node closes nothing it was handed.
- `memoryNodeStorage(): OpenNodeStorage` — a fresh set of memory stores per call, `close` a no-op.
- Exported from `src/index.ts` and `src/rn.ts` (`entry-parity.spec.ts` compares the two).

There is no fourth field for the transaction-state store: the node builds that over `kv` (`PersistentTransactionStateStore`), so the rule for it is stated once and holds on every platform.

### One warning instead of two

`resolveKvStore` and `resolvePieceStore` are gone, and with them their two `WARN:` lines. `resolveNodeStorage(options.storage, servesBlocks)` returns what the host supplied, or `memoryNodeStorage()` plus one role-aware `node-wiring` `WARN:` line naming every store it is keeping in memory and what is lost with each — serving: blocks, under-replication ledger, in-flight agreement state, HLC high-water mark, blob records and owed-blob ledger, blob pieces; client: everything but the first two. Both lines end with the way out.

**The test is the presence of the option, not the durability of the stores behind it.** A host that passes `memoryNodeStorage()` has said it meant the memory case and gets no warning, where three separate memory stores used to get two.

`resolveStorage` keeps its one job — `withReadCache` in front of the block store — and now takes an `IRawStorage`. The memory default reaches it as a `MemoryRawStorage`, which `withReadCache` returns unwrapped with no lease, so the old "deliberately not routed through the helper" special case was deleted rather than preserved: same outcome, one branch fewer.

`prepareServingStore` now takes the whole `NodeStorage` and reads `blocks` and `kv` off it. `storage` came off `logIgnoredServingOptions` (and off the `servesBlocks` doc comment, and off the "Options a client ignores" paragraphs in `docs/internals.md` and `packages/db-p2p/readme.md`), because a client uses two of its three parts.

### Call sites

`reference-peer`'s `openStores` returns an `OpenNodeStorage`; `upgrade-check`'s `openBackend` keeps hand-building (two directories for `fs`, which is the point of that package) and returns a `NodeStorage`; `write-scenario.mjs` probes the resolved published build and passes either the one value or the old three fields; the blob specs take `{ ...memoryNodeStorage(), pieces: theirStore }`; `two-machine-lifecycle.ts`'s `Machine` holds one `OpenNodeStorage`. Four TypeScript call sites the ticket had not listed were found by the compiler, and six more were found during review (below).

### Docs

`packages/db-p2p/docs/storage.md` gained **§8 A node's storage, as one value** with a per-role table; `docs/internals.md` §Client nodes, `docs/blobs.md`, `docs/debugging.md`, `docs/offline-sync.md`, `packages/db-p2p/docs/repo.md`, the four storage-package READMEs, `packages/quereus-plugin-optimystic/README.md` and `packages/db-p2p/readme.md` all follow. `packages/upgrade-check/README.md`'s "earlier builds have no `kvStore` option" was left alone: it is a historical claim about published builds and is still true.

## Review findings

### What was checked

The implement diff (`ticket(implement): a-node-takes-all-its-storage-as-one-value`, 37 files) read first with fresh eyes, then the handoff. Then: the new module and its two parked tripwires; the one warning on both roles; every call site named in the ticket plus every other caller of `createLibp2pNode` in the repository, TypeScript and plain JavaScript alike; every document the change touched and the ones it should have touched; and the read-cache seam the deleted branch sat on. Validation run once, after the fixes below: `yarn build`, `yarn typecheck`, `yarn lint`, `yarn lint:docs` (49 documents, 886 anchored citations, all resolve), `yarn lint:deps`, `yarn test` across all 13 workspaces (exit 0, 13m30s), `yarn test:integration` (exit 0, 7m25s) and `yarn check:rn` (Metro 23.6s, hermesc 14.2s). No pre-existing failures surfaced.

### Found and fixed in this pass

- **Six tests crashed at node construction, in two spec files the implementing pass never ran.** `test/node-read-cache-wiring.spec.ts` (4 tests) and `test/owned-block-seed-node-wiring.spec.ts` (2) handed `createLibp2pNode` a bare `IRawStorage` where the option is now a `NodeStorage`, so `resolveStorage` got `undefined` for `storage.blocks` and `withReadCache` threw `TypeError: Cannot read properties of undefined (reading 'readCached')`. Both files cast their options literal `as any`, which is why `tsc` stayed silent; the implementing pass ran db-p2p by file and did not include either. Both now build the whole value, and the `as any` is **removed from both** so the one-value type does the job it exists for. Worth noting what one of the six was: `leaves a MemoryRawStorage unwrapped (nothing to cache, nothing to release)` — the test that pins the exact branch this ticket deleted. It passes.
- **Two hand-run harnesses still passed a storage factory**, and would have crashed the same way the moment anyone used them: `packages/quereus-plugin-optimystic/test/offline-commit-cost.bench.mjs` under `STORAGE=file`, and `packages/quereus-plugin-optimystic/test/repro-issue8.mjs` under `MODE=network`. Plain JavaScript, so no type checker sees them, and no suite runs them. Both now pass `{ ...memoryNodeStorage(), blocks: … }`, which is what each actually wants — only the block store is the one either measures.
- **`packages/db-p2p/readme.md` — the changed package's own readme — still documented the removed shape** in two places: an example that built a bare `FileRawStorage`, passed it as `storage` and closed it with `await storage.close()`, and the client-node paragraph listing `storage` among the options a client ignores. It was not in the ticket's `files:` list and the handoff did not mention it. Both corrected, with the three-store close in the order the `fs` README uses.
- **`collection-factory.ts`'s NOTE above the plugin's own `createLibp2pNode` call** named the removed `pieceStorage` and `kvStore` options and said the node logs a warning "for each". Repointed to the one value and the one line, and it now states the whole-value constraint a future `blobStorageFactory` thread-through would have to satisfy.
- **`packages/quereus-plugin-optimystic/README.md`** said a `journal` may be "the instance the node uses as its `kvStore`". Repointed to the `kv` of `NodeOptions.storage`.
- **`libp2p-node-base.ts`'s lease-release comment** said "A client acquires no storage, so holds no lease", which this change makes false in its literal reading — a client is handed storage; it just builds no serving store and so never reaches that seam. Reworded.

### Filed

- **`debt-node-options-call-sites-escape-the-type-check`** (`tickets/backlog/`). The two crash findings above are two faces of one root cause: call sites that build a node's options outside the type checker's reach. Four were broken by this one change; seven further TypeScript spec files still cast their options literal `as any` (none of them happens to set `storage`, which is luck, not design) and four plain-JavaScript harnesses are unchecked outright. Climbed past the instances — they are fixed here — to ask for the build-time check that retires the class, with the deliberate exemption `write-scenario.mjs` needs, since that file must compile against published builds this tree no longer declares.

### Checked and found correct, no change needed

- **Deleting the "memory default deliberately not routed through the helper" branch is behaviour-preserving.** Read `withReadCache`: a `MemoryRawStorage` hits the first exclusion and comes back unchanged with `lease: undefined`, which is exactly what the old branch returned by hand. Now pinned by a test that runs again.
- **`memoryNodeStorage()` is called per node everywhere it matters.** Every spec that spawns more than one node calls it inside the per-node factory, so nothing is shared by accident: checked `distributed-diary`, `offline-storage`, `quick-test`, `blob-fetcher`, `blob-network-read`, `blob-protocol-stalls`, `distributed-transaction-validation`, `plugin-first-launch`, `two-machine-lifecycle`.
- **The two cold-restart specs now share the key-value store as well as the block store, and that strengthens them rather than weakening them.** In both, the first node is stopped before the second spawns, and every pend and commit has settled by then, so there is no concurrent-sharing hazard and the restart is more faithful than it was. Both pass.
- **The claim that an unused `blocks` store costs a client nothing because every backend's constructor is lazy.** Verified on the filesystem backend, the one with a lock to lose: `FileBatchBackend` acquires its write-ahead log on first operation, and its `close()` is a no-op when it never opened. A client handed a file block store it never reads takes no lock and closes cleanly.
- **`write-scenario.mjs`'s version probe.** Diffed the old branch against what it replaced: identical in effect, with only `privateKey` moved into the shared object. The new branch's shape matches `NodeStorage`.
- **Nothing else was silently broken.** No other `as any`-casting spec passes `storage`; `blockStoreCountsPieces` is untouched; `docs/`, `packages/db-p2p/docs/` and the root README carry no remaining mention of the removed option names.
- **File size, measured.** `libp2p-node-base.ts` is 3482 lines (`wc -l`), down from 3513 before this change. Still oversized, but this ticket shrank it and `debt-node-factory-wiring-steps-own-their-teardown` already owns that seam.

### Tripwires

The implementing pass parked two, both re-read and both left as they are: an optional fourth `NodeStorage` field for a backend that wants its own transaction-state store (a `NOTE:` on the interface), and the silence of a hand-built value whose parts disagree on durability, whose fix if a host is ever bitten is a `durability` field on `IKVStore` (a `NOTE:` on `resolveNodeStorage`, and stated in prose in `storage.md` §8). This pass added none of its own — nothing it found was conditional; the six test crashes and two harness crashes were live, and everything else was a document saying something untrue today.

### Accepted tradeoffs, left alone

- **`memoryNodeStorage()` as the explicit opt-out is an unpinned contract**: the only thing separating "meant memory" from "forgot the option" is `!== undefined`, so a host that hand-builds a value out of memory parts also gets no warning. Documented as deliberate on the type and in `storage.md` §8; the review agrees, and the alternative (sniffing durability) is the `IKVStore` tripwire above.
- **`NodeStorage`'s three fields are mutable, not `readonly`.** Considered and declined: nothing mutates them, `ResolvedReadCache` next door is the same shape, and the churn buys nothing enforceable.

### Tests

**No new tests.** Six existing ones were repaired rather than replaced, which is where the coverage gap actually was. None were added: the one claim in the new module that no type enforces — that `memoryNodeStorage()` returns distinct stores per call — is three `new` expressions in a four-line function, and the one warning is a log line whose words a test would only duplicate. The implementing pass's "no new test" call was right; what was missing was running the suites.

### Not acted on

`write-scenario.mjs` remains unexecuted by any suite — it runs only under `yarn write-fixture` against a published build, so neither branch of its probe has been executed. That is by design for that file, not a defect of this change, and `debt-no-scenario-runs-two-builds-in-one-cohort` already touches it; the new `debt-` ticket names it as the one site its guard must exempt.
