# A block's bytes can be deleted

One operation, `deleteBlock`, at every layer of the block store, removing everything a node holds for one block id. Before it, nothing in the system could take a byte off a node: the only delete in the whole surface was of one pending record, and invalidations write compensating *forward* revisions rather than removing anything.

**The layers, top to bottom.**

- `IBlockStorage.deleteBlock(latch)` / `BlockStorage.deleteBlock` — asserts the block's write latch (`assertLatch`, exactly as `restoreRevision` and `savePendingTransaction` do) and makes one storage call. No metadata read first: there is nothing to decide, and a block whose metadata is already gone still has content a resumed delete must take.
- `IRawStorage.deleteBlock(blockId)` / `KvRawStorage.deleteBlock` — a delegation to the driver, not a composition. The ticket asked for the metadata-first ordering to be composed in the kernel; it is the backend's instead, because the kernel has no metadata *delete* to call and cannot enumerate a block's revisions (`rangeRevisions` is a bounded scan, and the top revision is only knowable from the very metadata the operation removes). Composing it above would have forced a phase parameter and two transactions per backend where one suffices, trading away atomicity for a weaker ordering. The reasoning is recorded at the site and in `packages/db-p2p/docs/storage.md`.
- `RawStoreDriver.deleteBlock(blockId)` — **required**, not optional, so a wrapper that forgets to forward it does not type-check (the reasoning `flush` and `durability` already carry). `WriteGroupDriver` flushes its group strictly and then delegates, so no overlay put can be applied after the delete and resurrect the block; `CachedStoreDriver` drops everything it caches for the block, before and after; `RawStorageDriverAdapter` delegates to the `IRawStorage` it fronts.
- `BatchBackend.deleteBlock(blockId)` — where the whole contract is written down once: the six block-scoped stores and only those; metadata first and durably before any content store; idempotent; the caller holds the latch. `JournalStore` inherits it, and `JournalBatchBackend.deleteBlock` applies everything held before delegating, so no journal record can be applied over the emptied block afterwards.

**The five backends**, each scoped so nothing sharing its database or directory is reached — not the commit proofs store, not the key-value namespaces, not the piece store, not the journal:

| Backend | How |
|---|---|
| memory driver | drops the block's entries from six maps, synchronously |
| filesystem | unlinks `meta.json` through the write-ahead log as a synced commit, checkpoints (which makes the tree durable and discards the log), then removes the block's directory recursively |
| SQLite | six `DELETE … WHERE block_id = ?` in one `synchronous = FULL` transaction |
| LevelDB | one batch deleting every key in the block's envelope range under each of six tag bytes |
| IndexedDB | one `readwrite` transaction over six object stores: the metadata key, and each compound-keyed store's whole per-block key range |

Three of the four shipping backends do the whole thing in one atomic transaction or batch, which is strictly stronger than the ordering the contract asks for. The filesystem backend is the one that really is interruptible, and the checkpoint is what makes its last step safe: a tree file only ever holds content whose log record is durable, so a removal the log does not know about would be undone by the next open's replay.

**The commit proofs store is deliberately untouched.** It is keyed by a consensus message's hash alone, one entry per message however many blocks it covered, so an entry may still certify revisions of blocks this node keeps and the key shape admits no per-block delete. `deleteBlock` removes the deleted block's *entries* in the proofs store and leaves the proof *bodies* behind, orphaned when no kept revision names them — the residual `debt-unreferenced-commit-proofs-are-never-swept` already owns.

**Nothing calls it yet.** `gcEligibleBlocks` (`packages/db-p2p/src/libp2p-node-base.ts`) still has no consumer; the sweep, and the rule about which blocks may be given to this operation, is the next ticket.

## Review findings

Read the `ticket(implement): a-block-s-bytes-can-be-deleted` diff before the handoff summary.

**Correctness — one defect found and fixed; everything else checked and sound.**

- **Path traversal through the new recursive removal (fixed inline).** `FileBatchBackend` uses a block id raw as a relative path, with no validation anywhere in the system — `BlockId` is a bare `string`, and `StorageRepo` builds a `BlockStorage` for whatever ids its caller names, including ids arriving from peers. Every prior operation only ever wrote a file; `deleteBlock` is the first **recursive removal**, so an id of `..` would have removed the parent of the store, and the empty id the store itself — write-ahead log and lock included. `blockPath` now refuses any id that does not resolve strictly inside the store, and `deleteBlock` resolves it *before* the metadata unlink is committed, because `relativePath` builds the log's path from the raw id and a refused id must not reach a log record either. Five cases pinned in `packages/db-p2p-storage-fs/test/file-storage.spec.ts`, each asserting the store is intact and still usable afterwards. The remaining class — the write paths and the log's replay, which build their own relative strings — is filed as `bug-a-block-id-is-used-as-a-file-path-without-validation`, since closing it is a design choice (validate once at the storage boundary, or encode id segments in the layout) rather than a one-line guard.
- **A misleading comment that would have sent the next reader the wrong way (fixed inline).** `MemoryStoreDriver.deleteBlock`'s `NOTE:` claimed its prefix match carries "the SAME accepted limit" as the filesystem backend's nested-directory layout, and the handoff's reviewer notes repeated it. It does not: with ids separated by `/`, a nested child keys as `default/app/Ledger/index:<rev>`, which does **not** match the prefix `default/app/Ledger:`. The ambiguity needs a block id containing a *colon*, and no id has one. Verified by evaluating the key forms directly. The NOTE now says which hazard is real, which is not, and what to do if a colon ever appears in an id.
- **The handoff's flagged "pre-existing defect" in `MemoryStoreDriver.listPendingActionIds` is not one, and no ticket was filed.** It describes `default/app/Ledger` reporting phantom ids for the nested `default/app/Ledger/index/LedgerLatest`. Same arithmetic as above: the child's key ends up separated by `/`, not by the `:` the prefix requires, so there is no match. The real precondition is a colon in a block id, which does not occur; this is a conditional concern already covered by the corrected NOTE two methods away, not a latent defect.
- **The filesystem backend's three steps hold up.** `FileWriteLog.checkpoint()` hands back the running checkpoint when one is in flight, but `runCheckpoints` loops while `checkpointAgain`, so the awaited promise always covers a `checkpointOnce` that *sealed after* the caller's append — the metadata unlink record is always discarded before the removal. `seal()` runs `syncUnsynced()` first and `appendedBytes` is non-zero whenever a record is waiting, so the early return cannot skip the caller's record. Read `checkpointOnce`, `seal` and `commit` against this use, as the handoff asked.
- **The `CachedStoreDriver` double-drop is load-bearing and correct, but not for quite the reason stated at the site.** Reads that captured their block state *before* the first drop are already refused by the existing identity guard (`fillMiss` and `getMetadata` both decline when the state object has been swapped), so the first drop alone handles them. What the second drop actually closes is the narrower window of a read that *starts* after the first drop and fills before the delete returns. Both drops are needed; the behaviour is right and the comment overstates only which window it covers, which did not seem worth an edit.
- **`WriteGroupDriver.deleteBlock`'s strict flush really does empty the overlay** before the backend is called: `awaitDurable` calls `dropDurable` *before* resolving the batch's settled promise, and batches settle in order, so no put for the block can survive the flush and resurrect it.
- **Keyspace scoping verified per backend against the real key encodings**, not just the comments: SQLite's `block_id` is the first key column of all six tables and `commit_proofs` is keyed by `message_hash`; LevelDB's `blockEnvelopeRange` length-prefixes the block id, so one block's range cannot reach a nested block's keys, and the six tags exclude the commit proofs, journal, pieces, key-value and identity tags; IndexedDB's array bounds hold because an array sorts above every primitive and a prefix-equal shorter array sorts below a longer one; the memory driver leaves exactly `commitProofs` of its seven maps.
- **Every implementer of the four widened interfaces is accounted for** (19 classes across src and test), and the whole repo typechecks — which is the enforcement the ticket chose by making `deleteBlock` required rather than optional.
- **Checked and accepted:** `JournalBatchBackend.deleteBlock` does not refuse after `close()` where `commit` does, but `sync()` does not either, so this is the existing shape rather than a new asymmetry. Non-uniform failure latching across backends is deliberate and argued at each site (a failed garbage-collection write must not leave the store refusing ordinary writes). `dropBlock` not calling `purgeGhosts` matches every other per-entry invalidation path, and a ghost key is a recency hint with no correctness weight.

**Tests — both of the implementer's kept, one group added.** The two conformance tests pay for themselves and run across all 13 registered compositions. The inventory case is well built: both blocks share one proof body, so the kept block's proof still resolving is what proves the commit proofs store survived — exactly what a backend whose key range is one off would break. The idempotence case pins the post-crash state (content with no metadata), a double delete and a never-seen block. Nothing restates the implementation or verifies a mock, so nothing was cut. Added only the traversal cases above, for the defect found. Agreed with the implementer's decision not to test per-wrapper forwarding (the type checker enforces it) or the latch assertion (one shared private method already exercised by every other writer).

**Known gap, accepted as the honest limit of this layer.** Ordering and resumability are asserted only by the conformance case that *simulates* the post-crash state, not by crashing. A real mid-delete crash test needs a fault-injection seam per backend, and on the filesystem the steps are the write-ahead log's own operations. `MemoryBatchBackend.powerLoss()` rebuilds from recorded batches and so un-deletes a deleted block; documented at the site, which is the right place for it.

The two contract notes on `IRawStorage.getBlockProof` / `saveBlockProof` correctly now say a revision-delete site exists and name its residual's owner. `docs/arachnode-ring-handoff.md` § Part 2, Phase C exists and says what the section cites it for. `yarn lint:docs` resolves all 898 citations.
