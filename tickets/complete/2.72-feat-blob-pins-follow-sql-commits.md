# Blob pins follow SQL commits

Third of four parts of `feat-sql-columns-hold-blob-references`, landed as `ticket(implement): feat-blob-pins-follow-sql-commits` plus this review pass. It connects the reference trees (`feat-blob-reference-trees-follow-sql-rows`) to the cohort announcement (`feat-a-held-blob-follows-its-cohort`): for every commit that reaches storage or the offline queue, the references a transaction adds are pinned on the writer when its commit starts, announced with the table's reference tree as their scope and unpinned once the commit lands, and unpinned if the transaction is abandoned.

## What exists now

**The replay guard** (`src/transaction/replay-scope.ts`). `duringReplay(db, run)` / `isReplaying(db)` over a module-level `WeakMap<Database, number>` counter. `QuereusEngine.execute` holds it raised around its whole statement loop, inside the existing `try`. Every execution through that engine is a replay of a replicated transaction — the writer's own session always hands the coordinator its actions and so never reaches the engine — so the whole loop is marked. `laneCeiling` needs no guard: it prepares without executing.

**The ledger** (`src/optimystic-adapter/blob-reference-ledger.ts`). `TransactionState.blobReferences` holds one record per staged reference change (in staging order, each with its network's transactor key) and one per blob put while the transaction was open. `addedReferences` folds the records by **referrer** — `(backendKey, scope, referrer)`, last change wins — then deduplicates the surviving adds by `(backendKey, ref, scope)`. `putReferences` deduplicates puts by `(backendKey, ref)`.

**Recording.** `OptimysticVirtualTable.buildBlobReferences` passes the maintainer an `onStaged` that calls `TransactionBridge.noteBlobReferences(backendKey, changes)` unless `isReplaying(this.db)`; the backend key comes from `CollectionFactory.transactorKeyOf(options)`, read once synchronously at construction. `SqlBlobService.put` records its put through `noteBlobPut` only when this service defaulted the owner label to a transaction **and** that transaction is still the open one when the put resolves.

**Savepoints.** Legacy mode only. In session mode a statement savepoint rollback does not restore the trees, so truncating the ledger there would leave a reference that *will* commit unpinned; the comment at the mark says so. Puts are never truncated.

**The pins** (`src/optimystic-adapter/blob-pins.ts`). `SqlBlobPins` with `holdForCommit` (all or nothing; unpins what it took and rethrows, so a failed pin fails the commit before anything is sent) and three settling arms — `committed`, `queued`, `abandoned` — none of which throws, each handling one reference in its own `try`. Every arm reads the transaction's puts off the ledger rather than off `HeldPins`, so an arm runs correctly for a commit whose `holdForCommit` never completed. Announce before unpin, always.

**The factory.** `transactorKeyOf`, a private options map written at the top of `getOrCreateTransactor` (ahead of the cache check, first options per key winning), and `blobBackendForKey` which looks the options up and delegates to `getBlobBackend` so it shares the per-key de-duplication.

**The routes.** One private `TransactionBridge.settleBlobPins(transaction, settlement)` with a once-guard, called from every exit; `holdForCommit` runs inside `commitTransaction`'s `try`, after the stale-description check and before the route branch. The route table is in docs/internals.md §A table's blob references, *Pinning what a commit references*.

## Review findings

Read the `ticket(implement): feat-blob-pins-follow-sql-commits` diff with fresh eyes before the handoff summary.

**Correctness — checked, no defect found.** What I traced and why each holds:

- **The fold.** `addedReferences` keys by referrer (framed primary key + column name), which is the unit that holds at most one reference, so "the last change staged here" is what the tree holds after the commit. Walked every shape the maintainer can stage — insert, delete, same-key value change, key move, a displacing move that stages the identical referrer twice, NULL in and out — against `BlobReferenceMaintainer.stageUpdate`'s remove-before-add ordering. All agree with the fold's result.
- **Every settlement route.** `route === undefined` covers session mode as well as legacy (the route is only computed when there is no session), so both settle `{ committed: 'all' }`. A queue route that queued nothing settles abandoned, which is right: `sealIntoQueue` answers `false` only when nothing was staged, and a transaction that staged nothing staged no reference either. The once-guard is genuinely needed — `afterFailedCommit`'s ordinary arm reaches `rollbackTransaction`, which settles in its `finally` — and `beginTransaction` resets it and `heldBlobPins` together.
- **The claim the two partial-commit arms rest on.** `PartialCommitError.persisted` is built from `treeLabel`, which is `Tree.describe()`; read `packages/db-core/src/collections/tree/tree.ts:482` — it returns `String(this.collection.id)`. `CoordinatorPartialCommitError.committedCollections` is typed `readonly CollectionId[]`. A reference tree's scope is that same collection id (`blobReferenceOptions` forms `<uri>/blobrefs`, and `blobReferenceScope()` parses it the same way). So `committed.has(scope)` compares like with like. One test now observes this rather than inferring it (below).
- **The replay guard is at the right altitude.** Checked that the only two callers of `engine.execute` are `TransactionValidator.validate` and `TransactionCoordinator.execute`, and that the plugin's own `TransactionSession.execute(statement, [])` always passes an actions array, so the writer never reaches the engine. A member's own bridge does still commit the replayed row locally — the test asserts that — and its ledger is empty, so `holdForCommit` returns before touching the blob factory.
- **No new commit failure mode from resolving the blob backend at commit.** `resolveBlobBackend` can only throw from `getOrCreateTransactor` (already cached by the time a table has committed), a host-supplied `blobStorageFactory`, or `SingleMachineBlobService.start()`. A `network` transactor whose node carries no piece store falls back to a single-machine service rather than failing. `blobBackendForKey`'s unseen-key throw is unreachable: every open path goes through `resolveTreeArgs` → `getOrCreateTransactor`, which records the options ahead of its cache check.
- **Pin labels.** `sql-unstaged/` does not start with `sql/`, `parsePinLabel` requires exactly two or three segments past the prefix and digits-only for `unstaged`, and a scope is URI-encoded — so `releaseUnstaged`'s `kind === 'unstaged'` filter cannot reach a reference pin. The load-bearing check below printed a real label (`sql/<stampId>/ref/legacy%2Fpinned%2Fblobrefs`), confirming the encoding round-trips.
- **Ordering and concurrency.** `settleBlobPins` runs after `endTransaction()` but holds the transaction object it was given, so the ledger is still readable; a `put` resolving mid-commit still records while the transaction is active and its pin is then released; one resolving after it leaves the stray pin the restart reconciliation owns.

**Test added — one, for the contract the implementer flagged as inspection-only.** `legacy-commit-atomicity.spec.ts` gained *a commit-phase split announces and releases a reference whose own tree committed*: a `blobref` table with an index, the injected commit failure armed on the index tree, so the main table and the reference tree commit and only the index is lost. It asserts `committedCollections` contains `legacy/pinned/blobrefs`, that both the reference pin and the `unstaged` pin are gone, and that the blob's durability is `local`. This is the discriminating direction — the scope-not-committed direction passes whether or not the ids ever match, so it proves nothing — and it is **verified load-bearing**: with the `CoordinatorPartialCommitError` arm's settle call disabled, it fails with both pins still held. The spec's `createDbWithInjected` now registers `plugin.types`, without which a `blobref` column does not resolve.

**Tests — none cut.** Weighed cutting the `what a commit pins` block, which the implementer offered up. ## Carried forward

- **`feat-sql-columns-hold-blob-references` must not expire an `unstaged` pin whose reference carries a reference pin (`sql/<stampId>/ref/<scope>`) of a live transaction** — open or queued — because `queued` and `abandoned` leave those `unstaged` pins in place deliberately. Its `openReferences` dependency therefore widens from "the open transaction's ledger" to "any live transaction's references", which it can read straight off the pin labels. That ticket already carries this requirement in full.
- **`plugin.blobPins` is not exposed.** The `SqlBlobPins` instance is attached to the bridge and nothing else holds it; whichever later part needs the handle adds it.
- **Behaviour changes a host sees.** A commit of a `blobref` table now resolves that network's blob backend, so a `local`, `test` or `mesh-test` deployment builds a single-machine blob service over a memory piece store on the first such commit and creates blob records for the references it commits. `plugin.blobs` no longer holds every blob it ever put: a put inside a transaction that never references the blob loses its pin when the transaction ends (documented in `SqlBlobService.put`, the README and docs/blobs.md §SQL, with the two ways to keep such a blob). The pin moves to the transaction when the **commit starts**, not when the first statement stages the reference, because nothing reached from `update()` may call the blob service.
