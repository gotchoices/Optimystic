## What landed

A fourth `TreeEntryGuard` kind, `unchanged`, in `packages/db-core/src/collections/tree/struct.ts`. The three existing kinds all say "nothing may be here"; this one says "what is here must still be what I read". The tree's `replace` handler enforces it on every run — initial staging and every conflict replay — so a losing concurrent writer is refused rather than re-applying a staged effect computed from an entry image a rival has since changed or removed.

Nothing in the SQL layer stages one yet; that is the sibling ticket `refuse-concurrent-row-change-loser` (`tickets/implement/6.3-…`), which already specifies every arm. This ticket is the db-core mechanism only, exercised through raw `Tree`s.

**The guard.** `TreeUnchangedGuard<TEntry> = { kind: 'unchanged', expected: TEntry }`. `expected` is the entry as stored, not a digest, so it round-trips through the log under the same encoding entries already use. An **absent** entry counts as changed, on upserts and deletes alike — refusing an upsert is what stops a rival's delete being undone, and refusing the second of two racing deletes is the ordinary optimistic answer.

**Guards on deletes.** The handler previously ignored the guard slot on a delete entirely. `TreeReplaceAction` is now a union of `TreeUpsertElement` (any guard kind) and `TreeDeleteElement` (an `unchanged` guard or none), re-checked at runtime because a replayed log entry is deserialized data no type policed. It stays a positional tuple, so previously committed log entries and existing callers deserialize and replay unchanged.

**The error hierarchy.** New base `TreeGuardRefusedError` carries the contract shared by every guard refusal (discards the whole action's staged writes, is not a `StaleFailure`, is never downgraded to retryable). `TreeKeyTakenError` extends it; new `TreeEntryChangedError` extends it as a **sibling**, deliberately not a subclass — the Quereus bridge renders every `TreeKeyTakenError` as `UNIQUE constraint failed`, and a lost update is not a uniqueness failure. Review added `TreeDeleteGuardKindError` (below), deliberately outside that hierarchy.

**Structural equality.** New `structuralEquals` in `packages/db-core/src/utility/structural-equals.ts`. JSON-shaped values plus `Uint8Array` compared by bytes. Object key order ignored, an `undefined`-valued property counts as absent, `NaN` equals `NaN` — each because one side of a guard comparison has usually crossed an encoding boundary and the other has not.

**Plugin fallout.** `uniquePrefixGuard` and `IndexManager.guardFor` now return `TreeEntryGuard<IndexKey, IndexEntry>`; two annotation changes, no behaviour change.

### Open questions the handoff asked the reviewer to settle — both resolved

**The `null`-slot hazard is real, and the hardening was a latent-crash fix, not just defensiveness.** The implementer changed both guard-presence checks from `guard !== undefined` to truthiness because JSON renders an explicitly-passed `undefined` guard as `null` (the shape `IndexManager.insertIndexEntries` stages for every non-unique index), and could not confirm whether the live encoding actually produces that. It does: the peer-to-peer repo protocol is JSON in **both** directions — `JSON.stringify` at `packages/db-p2p/src/protocol-client.ts:153`, `JSON.parse` at `packages/db-p2p/src/repo/service.ts:268`. No other codec is in play (`dag-cbor` appears in this repo only as an unused multicodec constant in `quereus-plugin-crypto/src/cid.ts`). So before this change a conflict replay over a real transactor would have thrown a `TypeError` off `null.kind`. No test could have caught it because `TestTransactor` uses `structuredClone`, which preserves `undefined`. Evidence recorded at the handler's `NOTE:` in `tree.ts` and in `docs/internals.md` so the next reader does not have to re-derive it.

**The `Uint8Array`-through-the-real-encoding question resolves the other way, and the code comment was wrong about it.** `structuralEquals`'s header claimed a byte array "survives `structuredClone` and dag-cbor as itself". dag-cbor is not the transport; JSON is, and JSON turns a `Uint8Array` into an index-keyed object — which the byte arm correctly reports as *not* equal. A genuinely byte-shaped entry type would therefore make an `unchanged` guard refuse an honest write **forever**, not just once. It is unreachable today: the only byte-shaped candidate is the plugin's `EncodedRow` under the `msgpack` encoding, and that encoder throws `msgpack encoding not yet implemented` (`packages/quereus-plugin-optimystic/src/schema/row-codec.ts:55`); under the default `json` encoding BLOB columns are base64 strings before they reach a tree entry. **Fixed inline**: the false claim is corrected, and the genuine conditional is parked as a `NOTE:` naming what a future byte-shaped entry type would need (a transport-stable encoding for `expected`). The spec's `structuredClone` test title, which called it "the transport tree entries actually take", is corrected to say in-process.

### Minor — fixed in this pass

- **`renderKey` became public API of `@optimystic/db-core`.** It was exported from `struct.ts` (which the package barrel re-exports) solely so `tree.ts` could build one message string — a generically-named helper on the package root for no caller's benefit. Fixed by moving the message to where its siblings live: the delete-guard-kind rejection is now `TreeDeleteGuardKindError` in `struct.ts`, and `renderKey` is module-private again.
- **The delete-guard-kind rejection threw a bare `Error`** (a gap the handoff named). Now `TreeDeleteGuardKindError`, carrying `collectionId`, `key` and `guardKind`. Deliberately **outside** `TreeGuardRefusedError`: a malformed action is a caller bug, and the refusal contract ("a rival won; retry sequentially") does not describe it — the sibling ticket dispatches on that base class, so a wrong parent here would have rendered a caller bug as a concurrency message. The existing spec assertion was tightened from `instanceOf(Error)` to the class plus a `not.instanceOf(TreeGuardRefusedError)` pin.
- **`docs/transactions.md` was a doc the change should have touched and did not.** Its legacy-commit pre-flight bullet named `TreeKeyTakenError` as *the* thing a pre-flight refresh refuses; there are now two arms. Updated to name `TreeGuardRefusedError` with both subclasses.
- **`docs/internals.md` prose tidy**: the insertion left an orphaned half-line mid-sentence; the delete-rejection sentence now names the error class it raises.

### Test coverage — one addition

The implementer's tests are thorough (happy path, both refusal directions on upsert and delete, absent-counts-as-changed, whole-action discard, JSON round-trip, bytes-by-value, no-retry against a real `CompetingWriterTransactor`, and the coordinator's inter-attempt refresh). One gap: the **class lattice** was asserted only piecemeal, scattered across the thrown-error tests. That lattice is dispatched on, not just thrown — `mapCommitRefusal` walks a cause chain and renders by class, so a future subclass attached to the wrong parent would silently re-render one refusal as another, and no single test would fail in a legible place. Added `refusal class lattice` to `tree-guard.spec.ts`: one test constructing all four errors directly and pinning the whole shape (every concurrency refusal under the base; range is a key-taken; entry-changed is not; malformed is outside the hierarchy). This is the *property test* rung rather than a point assertion — it catches the class of "wrong parent" mistakes, not one instance.

### Considered and not filed

- **Double B-tree descent per guarded upsert** — the `unchanged` arm calls `find(key)` and then `upsert(entry)` re-descends. Identical to the pre-existing `absent`/`keepExisting` arms, over an in-memory Atomic-wrapped tree whose nodes are resident from the first descent. Not measured, so no magnitude claim and no ticket.
- **Delete-then-guarded-upsert at the same key within one action would refuse its own delete** (the guard reads the same `actionTree` the earlier element wrote). Not reachable: `optimystic-module.ts:2550` stages the delete+insert shape *only* when `oldKey !== newKey`, and the sibling ticket's same-key UPDATE arm is a single element. Noted here for whoever implements 6.3 rather than parked as a `NOTE:`, since it is a constraint on how that ticket stages, not a property of this code.
- **No plugin-side test that `TreeEntryChangedError` passes through `mapCommitRefusal` unmapped** (a gap the handoff named). Correctly a non-gap: ticket 6.3 *changes* that behaviour, adding `registerEntryChangedRenderer` and a second dispatch arm, so pinning today's pass-through would pin something 6.3 deletes. The property the bridge actually keys on — that the error is not a `TreeKeyTakenError` — is pinned in db-core.
- **The implementer's three parked tripwires** were each checked at their sites and left standing: the falsy-entry discrimination `NOTE:` in `tree.ts` (correct as written — tightening it to `!== undefined` would be a live regression, as the JSON finding above now proves), the `expected`-is-a-full-copy cost `NOTE:` on `TreeUnchangedGuard` (arithmetic, honestly labelled as such), and the non-JSON-shaped-values `NOTE:` in `structural-equals.ts`.
- **No accepted-tradeoff `NOTE:` exists at any site touched**, so nothing was re-filed against a decision already made.
