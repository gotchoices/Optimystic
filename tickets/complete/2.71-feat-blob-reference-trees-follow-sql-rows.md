# Blob reference trees follow SQL rows — complete

Third of four parts of backlog `feat-sql-columns-hold-blob-references`. Landed as `ticket(implement): feat-blob-reference-trees-follow-sql-rows` plus this review pass. Nothing touches the blob service: pinning and announcing are `feat-blob-pins-follow-sql-commits`.

## What shipped

**A maintainer per table.** `BlobReferenceMaintainer` (`packages/quereus-plugin-optimystic/src/schema/blob-reference-maintainer.ts`) is `IndexManager`'s counterpart for blob references: `columnsOf`, `stageInsert`, `stageDelete`, `stageUpdate`, `withColumns`, and the free function `blobReferrer` (the row's framed primary key, then the column NAME framed as one more element). What it stages is a pure function of `(rows, keys, columns)` — no transactor, no blob service, no read of the tree — which is the structural form of the purity a validating member's re-execution would depend on. `onStaged` exists in the constructor and is unset; `feat-blob-pins-follow-sql-commits` wires it.

**Wiring in `OptimysticVirtualTable`** (`packages/quereus-plugin-optimystic/src/optimystic-module.ts`): the tree is opened through the ordinary collection factory at the table's `/blobrefs` child, published in `doInitialize`'s one synchronous step, kept across a re-initialization (`KeptHandles`, `adoptCatalogEntry`, `forgetUnmaintainedTrees`), registered with the transaction bridge, marked dirty with the other trees, counted in `hasStagedWrites`, named by its table in `describeCollection`, rebuilt on a column-layout change in `republishColumnLayout`, and attached mid-session by `attachBlobReferences` for the ADD COLUMN that gives a table its first such column. Six staging call sites in `update()` / `applyUniqueEvictions`, each beside the index call it mirrors.

**The scope registry.** `BlobScopeRegistration` (`packages/quereus-plugin-optimystic/src/optimystic-adapter/blob-scope-registration.ts`) reads the registry before writing it and memoizes per (network key, scope) once confirmed; `blobReferenceOptions` is the one place the `/blobrefs` URI is formed. `CollectionFactory` gained `networkBinding` and `blobScopes`, `BlobBackend` now extends `NetworkBinding`, and `clearCache`/`dispose` clear the memos. Written by `create` (a table that has a `blobref` column) and `addColumn` (the first such column), unregistered by `destroy`, never on hydrate.

**The three refusals.** `ColumnKeyedParts.columns` widened with `BlobRefColumnShape` and the `it holds blob references` blocker added to `columnDropBlockers`; `SchemaManager.mergeForWrite` holds the two re-declare refusals (a column changed to or from `blobref`, a persisted `blobref` column omitted), with `storeStoredSchema`, `storeInBatch` and `mergeWithPersisted` routed through it and `viewOverRecord` deliberately left on `mergePersistedSchemas`.

Three deliberate deviations from the implement ticket's declared shapes, each documented at its site and each confirmed sound in review: the maintainer's constructor takes the qualified table name first (the required refusal has to name the table); `BlobScopeRegistration.ensure` answers `BlobScopeOutcome` rather than a boolean (a boolean cannot carry the `cause` the refusal has to attach); and `mergeForWrite` calls `assertBlobRefTypeRegistered` ahead of the kept-columns rule, so a process that cannot resolve `BLOBREF` is told to register the type instead of being told to drop the table. The third moves a throw site in `mergeWithPersisted`'s dry run — the net outcome is the same refusal with a better message.

## Review findings

### What was checked

Read the implement diff first, with the handoff set aside, then:

- **Every staging site, enumerated rather than taken on trust.** All seven `this.collection.stage(…)` calls in the vtab were listed against the six blob-reference calls: each main-tree staging has its mirror, in the same order as the index call beside it, and the seventh (the delete half of a primary-key move, staged in the same action as its insert half) is covered by the one `stageUpdate` that spans both keys.
- **Referrer injectivity and key framing**, from `encodeKeyElement`'s escape rule through `blobReferenceKey`'s split-at-the-first-separator and the fact that a reference is lowercase base32 and so contains no U+0000. A referrer that itself begins with framing is still split correctly, because the separator the key format inserts is at `ref.length`.
- **Every arm of `stageUpdate` by hand**, including the cross cases the table-driven spec covers and two it does not name: one reference held in two columns of one row, and two columns of one row swapping references (all four staged keys distinct, so no same-action duplicate arises). The displacing move's remove-before-add order holds across the two separate tree actions it spans.
- **Purity and partial-staging.** `blobReferenceAction` and `BlobReferenceTree.stage` read nothing; the maintainer builds its whole change list before `apply`, so the malformed-value refusal cannot leave half a row's entries staged.
- **That the factory path opens the same tree db-core would.** The factory keys on `entry[0]` under `compareTreeKeys`; `BlobReferenceTree.createOrOpen` keys on `pairEntryKey` under the default comparator — the same expression. And `getCollectionId` is literally `parseCollectionId`, so the scope registered is the id of the tree opened.
- **That the `kind: 'index'` description the reference tree answers with reaches nothing that renders it.** `CollectionJudge.element` returns before judging an element with no guard, and `OfflineMode.refusalFields` is the only other consumer — a reference entry never refuses, so neither ever reads it. Confirmed in the code, not from the comment.
- **Rollback and savepoint rollback, run rather than reasoned.** A throwaway script drove a full `rollback` and a `rollback to savepoint … ; commit` over a `blobref` table and read the committed tree back through a fresh handle: the tree matched the rows exactly in both cases. (The handoff listed this as inspection-only.) Script deleted; no test added, because the savepoint machinery is registered-collection-generic and the session-mode case already pins that this tree is registered.
- **The DDL error paths.** `registerBlobScope` sits inside the `try` whose `catch` un-caches a refused `CREATE`; `addColumn` runs the queued-entries gate before the registration; and `destroy`'s `entry` and `table` both come from the same `db.schemaManager.findTable`, so there is no path where the instance is torn down and the scope is left behind by this code.
- **Every writer that can change a record's column list**, to confirm the re-declare rule is held at the one seam that needs it: `storeStoredSchema` and `storeInBatch` route through `mergeForWrite`; the gravestone writer, `withoutIndex` and the tag writers touch no column, so the comment's claim holds.
- **Docs, by reading every file the change touched and the ones it should have.** Four staleness points found (below).
- **Commands.** In `packages/quereus-plugin-optimystic`: `yarn build`, `npx tsc --noEmit` (clean), `yarn test` — **1429 passing, 14 pending, 0 failing**, plus the smoke script. From the root: `yarn lint`, `yarn lint:docs`, `yarn lint:deps`, `yarn check:rn` — all clean. All re-run after the fixes below. `yarn test:integration` was not run: the change touches no networking, cohort assembly, reactivity or matchmaking.

### Fixed in this pass (minor)

- **An orphaned doc comment, introduced by the change.** `networkBinding` had been inserted between `getBlobBackend`'s JSDoc and `getBlobBackend` itself, so the backend resolver was left undocumented while `networkBinding` carried two stacked comments (only the adjacent one of which counts). Moved `networkBinding` below `getBlobBackend`; no behaviour change.
- **A wrong "why" on `CollectionFactory.blobScopes`.** It said resolving a blob service "would build or reuse a libp2p node for a statement that only has to write one registry entry" — but `networkBinding` resolves the transactor, which for a `network` transactor is exactly what builds the node. Restated with the real saving (the network's piece store and blob records are not resolved or remembered) and with the non-saving said out loud, so nobody reads a node-building cost into the choice.
- **`TransactionBridge.collectionsOf`'s doc** still said a table's collections are "its main tree and its index trees". It now also returns the reference tree, which is how the offline restore finds that tree's journaled segment — named.
- **`docs/debugging.md` was missing `blob:scope-register-failed`.** That table enumerates every event in the quereus-plugin `blob` namespace, so a new one has to be in it. Added, with the point a reader needs: it is the detail behind a refused `create table` / `add column`, not a silent fault, and nothing is remembered so the next statement retries.
- **`packages/quereus-plugin-optimystic/README.md` was not touched at all**, although it is the user-facing document for exactly these DDL rules and already carried the first two parts of the blob design. Three fixes: "its first two parts" → three, naming the per-table list; the ALTER TABLE paragraph's list of what a droppable column must be now excludes a `blobref` column; and two new bullets in §Large values say, in plain language, what the list is, when its registry entry is written and removed, and the two things that cannot be done to a `blobref` column.

### Recorded, not filed

- **Size debt.** `wc -l packages/quereus-plugin-optimystic/src/optimystic-module.ts` now reports **7691**, up 248. `tickets/backlog/debt-optimystic-vtab-class-is-too-big-to-review` already owns this site, so this is evidence, not a new ticket: a re-measurement arm was appended there. The arm's point is that the change is almost entirely mirror-image of the index code and nothing in it was wrong — the cost was that there was no unit smaller than the whole class to check it against.

### Considered and declined

- **`forgetUnmaintainedTrees`'s reference-tree arm**, which the handoff invited a reviewer to delete as unreachable. Kept: three guarded lines mirroring the index arm, with a comment that states its own unreachability, insuring against a failure (a registered tree nothing forgets) that would be silent.
- **The dropped-then-re-created table keeping its old tree's entries.** Carries an accepted-tradeoff `NOTE:` at `unregisterBlobScope` and an entry in docs/blobs.md §Lifetime. Its revisit condition — reclaiming those bytes matters — has not tripped.
- **The validator re-execution round-trip** the implement ticket asked for and the handoff substituted a session-mode commit case for. Not re-filed: reproducing an operations hash needs a transaction that creates no block (block ids are random), and isolating a validation run needs a harness nothing in the repo has — and `createQuereusValidator` still has no production caller, which is already backlog `feat-no-deployment-validates-transactions-at-pend` with its own accepted-tradeoff `NOTE:` in `quereus-validator.ts`. The substituted case does pin the half this change owns: the reference tree is one of the registered collections a real `TransactionCoordinator` commits, and every pend of that commit carried the transaction and its operations hash.
- **A `blobrefs:tree-open` log line** for symmetry with `index:tree-open`. Declined: a reference tree's collection id is literally `<table uri path>/blobrefs`, so the mapping the index line exists to provide is already in the id, and the line would cost a debugging.md entry for nothing.

### Major findings

**None past the filing bar.** The correctness questions this change raises — are all the staging sites covered, is the referrer injective, is the displacing-move order right, does the tree ride every commit route, does a rollback take its entries with it — each resolved in the implementation's favour by reading and, for the rollback arms, by running it. Nothing found names a class-level invariant that is missing, and nothing found is a latent defect waiting on a dormant path.

### Tripwires

**None added, and that is deliberate.** A tripwire records something fine now that becomes work on a condition; the two conditional limits this change actually has — a re-created table's leftover entries, and a tree missing from the registry because it was created by a build that registered nothing or dropped elsewhere — already carry their notes from the implement pass, at the sites and in docs/blobs.md. Everything else either behaves identically to the index trees it mirrors (so the index trees' own notes apply) or is already owned by a backlog ticket.

### Tests

**None added, none cut.** The implementer's 21 cases were read as code under review: 13 table-driven shape cases over an oracle built from the production `blobReferrer` and the table's own `RowCodec` (which pins the *set* of `(reference, row, column)` triples against a full scan of the rows, each case also pinning an exact entry count so a case cannot pass on two empty sets); one session-mode commit through a real `TransactionCoordinator`; one ADD COLUMN that attaches the maintainer mid-session; one registry case; two racing-writer cases; three refusal cases; plus one pure case in `catalog-only-change.spec.ts` for `columnDropBlockers` over both shapes a column arrives in. Each is a distinct behaviour with real branching behind it, none restates the implementation and none mocks a module the repo owns. The oracle sharing `blobReferrer` with the production path is a deliberate and correctly stated limit — the key framing has its own specs — not a hole. Nothing was left unverified that a test could reach without new harness infrastructure, so nothing was added.

## Known gaps carried forward

Covered by inspection and reasoning, not by tests, and each structurally identical to the index trees that the existing specs do cover: the offline queue and its restore after a restart (the reference tree is in `collectionsOf(table)`, which is how the restore finds its segment and how the DDL gate sees it); two tables declared over one URI sharing a reference tree, which already share their main tree; an index on a `blobref` column; a registry write that fails at `create` or an unregister that fails at `drop`.

`forgetUnmaintainedTrees`'s reference-tree arm remains unreachable while the three refusals stand.
