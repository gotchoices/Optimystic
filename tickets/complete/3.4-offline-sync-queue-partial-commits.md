Last of four tickets for stage 3 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). The queue core left the `partial` class (`CoordinatorPartialCommitError` out of `TransactionCoordinator.commitEntry`) treated as a transient retry; this ticket gives it the lifecycle §Partial commits specifies.

## What was built

**Status shapes** (`packages/db-core/src/offline/status.ts`):

- New `EntryStatus` arm `{ kind: 'partially-committed'; entryId; committedCollections; pendingCollections; cause: Error }`.
- `committedCollections?` on `queued`, on `failed`, and on `QueuedEntry` — present only once part of the entry has committed.
- `committed.durability` now covers every collection the entry wrote across submissions.

**Queue** (`OfflineQueue.partiallyCommitted` in `packages/db-core/src/offline/queue.ts`):

- The entry holds a `committed` map (collection → `WriteDurability | undefined`, on `Entry` in `packages/db-core/src/offline/entry.ts`), accumulated with `recordCollectionDurability` across partials. The committed collections' retained attempts are dropped, and the entry is set in doubt.
- `partially-committed` is emitted **in place of** the `queued` status that transition would otherwise report. `lastQueued` is set without emitting, so the sequence an application sees is `queued → submitting → partially-committed → submitting → committed`. Between submissions, `status()` and `entries()` report it `queued` with `committedCollections`.
- `cause` is `error.reason` when that is an `Error`, otherwise the partial-commit error itself. A hard commit-phase failure gives a **string** reason, so in practice `cause` is usually the partial-commit error. The first db-core test pins this.
- The next submission drives only `remainingCollections(entry)` (the collections still holding the segment): `commitHead` for one, `commitEntry` for several. It uses the same action id, with `resume` filtered to those collections. That filtering already existed in the queue core.
- On success, `committed` reports `entryDurability(entry, answer)`: the partial's half merged with the remainder's answer.
- Every failure path reads `entry.committed` in `remove()`, so `failed` carries `committedCollections` whatever triggered it. `changedCollections` still lists only the dropped segments. A log line `offline:partially-committed-entry-failed` marks the half-transaction left on the network.
- The reachability gate is now asked only about the remaining collections.
- Log `offline:partial-commit-deferred` is replaced by `offline:partially-committed`.

**Judgement calls a reviewer should weigh:**

- **`torn-not-saved` no longer clears doubt on a partly committed entry** (`entry.inDoubt = entry.committed.size > 0`). Otherwise a `TornActionError{final:true}` on the remainder would make an entry with a committed half discardable and expirable. This changes the queue core's rule, which said doubt is cleared by `torn-not-saved`. The docs (offline-sync.md §Identity across attempts and internals.md) are updated to match.
- **A partial with nothing left pending settles `committed`** with the accumulated durability, instead of letting the next `submit` throw its "holds no sealed segment" defect. It is reachable only if `CoordinatorPartialCommitError.failedCollections` is empty. I believe `commitEntry` cannot produce that today: `nothingLeft` returns success first. It is handled only so a fully saved entry never stops the drain. **Not tested.**
- `ThrowsOnCommitOf` moved from `coordinator-entry-commit.spec.ts` into `packages/db-core/src/testing/test-transactor.ts`, so both specs share one copy.

## Mesh scenario: one deviation from the ticket

`packages/db-p2p/test/offline-queue-mesh.spec.ts` builds a `createMesh(2, { responsibilityK: 2, clusterSize: 2 })` mesh with `buildNetworkTransactors`. Node A's queue writes two trees, a "table" and its "index", and runs with no reachability port. Both trees are seeded through node B first. A `BatchCounter` passed as `wrapRepo` counts `pendMany` and `commitMany` calls, so each case asserts that the entry actually took the batched path rather than quietly falling back to one request per collection.

Case 2 deviates from the ticket text. The ticket said the rival commits "before A drains". Done that way, `commitEntry`'s opening refresh finds the rival and nothing is ever pended, so the case would not exercise the "refusal at pend" the ticket names. Instead, the rival commits from inside the queue's write-ahead hook, which runs after the attempt is built and before it is sent. The test asserts `recorded.length === 1` (one attempt was sent) and that a batched pend went out. The batched pend is refused, the retry refresh refuses the head with `TreeKeyTakenError`, and the entry fails with `constraint`. B's logs hold nothing under the entry's action id in either collection.

The mesh spec takes about 150 ms and runs in plain `yarn test`.

## Tests added

- `offline-queue.spec.ts` — "finishes an entry over two trees that partly committed…". `ThrowsOnCommitOf` on the USERS tail makes the first submission commit ITEMS and fail USERS. It verifies:
  - the `partially-committed` shape: committed `[ITEMS]`, pending `[USERS]`, and the `cause` rule for a string reason;
  - `entries()` and `queued` carry `committedCollections`, with `inDoubt` true and waiting for `backoff`;
  - `discard` throws `EntryNotDiscardableError`;
  - the segments are consumed and kept as expected;
  - after disarming, the remainder's recorded attempts name only USERS, under the entry's one action id;
  - the exact status sequence, the merged durability naming both collections, and each log holding the entry once.
- `offline-queue.spec.ts` — "fails a partly committed entry whose remainder a rival then refuses…". It verifies:
  - `failed`: `constraint`, `TreeKeyTakenError`, `committedCollections: [ITEMS]`, `changedCollections: [USERS]`;
  - E2 (which updated E1's row) fails with `concurrent-modification` and `causedBy: 'E1'`, with no `committedCollections`;
  - the committed ITEMS row stays, and the USERS view shows the rival's row.
- `offline-queue-mesh.spec.ts` — the two mesh cases above.

## Covered by inspection, not by tests (as the ticket allowed)

- Two partials in a row: `recordCollectionDurability` into one map, emitted again each time.
- Durability merge when the partial's half has an unknown class: `transactionDurability` leaves `overall` absent.
- A refusal of the remainder reported by a reader's refresh between submissions: `remove()` reads `entry.committed` whatever the trigger.
- `torn-not-saved` after a partial keeping the entry in doubt.

## Review findings

Read the `ticket(implement): offline-sync-queue-partial-commits` diff first, then the surrounding drain (`OfflineQueue.drain`, `submit`, `send`, `applyFailure`, `remove`) and `TransactionCoordinator.commitEntry` / `reportSaved` to see which errors reach the `partial` arm.

- **Correctness — fixed inline.** `TransactionCoordinator.reportSaved` turns *any* failure after a saved participant into `CoordinatorPartialCommitError`, including a `TornActionError` with `final: true` out of the refresh for a still-pending collection. The queue re-drove that remainder under the old action id, which only meets the stranded log entry again; it converged one wasted submission later through the bare `torn-not-saved` arm. `OfflineQueue.partiallyCommitted` now classifies `error.reason` and, when it is `torn-not-saved`, mints a fresh id and clears the retained attempts through a new shared `OfflineQueue.renewIdentity` (also used by the bare arm). Documented in offline-sync.md §Partial commits and internals.md (the entry's two halves are then logged under different action ids). No test added: provoking a saved participant beside a final torn one needs a bespoke double, and the change mirrors an already-pinned arm; covered by inspection like the other partial-path variants.
