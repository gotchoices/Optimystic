# The blob cohort reaction

The decision half of [docs/blobs.md §Placement, copying and durability](../../docs/blobs.md#placement-copying-and-durability), *When the cohort changes*: "A member that joins a held blob's cohort is announced to. A node that leaves a blob's cohort drops its `responsible` hold only after confirming that enough current members hold the blob."

Landed as `BlobCohortReaction` in `packages/db-p2p/src/blob/cohort-reaction.ts` plus one record door, `BlobResponsibleRecords.releaseResponsible` on `LocalBlobService`. `BlobCohortReaction.handle` takes one `RebalanceEvent` and answers which `responsible` holds may go, which must stay, and what the growth arm learned — the blob counterpart of `BlockTransferCoordinator.handleRebalanceEvent` in `packages/db-p2p/src/cluster/block-transfer.ts`, with an announcement in place of a push and a `stat` in place of a push response.

**Nothing constructs it.** `feat-a-held-blob-follows-its-cohort` (sequence 2.66) runs the second `RebalanceMonitor` that feeds it and carries the documentation for both halves, so the class is exported from both entries and tested but unreferenced in `src`. No behaviour on a running node changed in this ticket.

## What the reaction decides

A shared preamble resolves three things once per event: a detected partition reports every grown reference incomplete and retains every lost one; acceptance is classified in ONE `deps.acceptance` call over the union of the event's named peers, with a rejection read as `unknown` (which counts as accepting, so the node errs toward keeping its copy); and a peer the membership gate refuses, whose acceptance is `refuses`, or that the drain remembers as declining is "satisfiable without a request" — it will never hold the blob, so it is owed nothing and is dropped from the release count's numerator and denominator alike.

The two arms then run concurrently, each over at most four references at a time:

- **`grown`** announces the reference, under its `responsible` hold's scope or its owed entry's, to each newly co-responsible peer that is not already satisfiable; `whole`, `fetching` and `declined` satisfy, `not-responsible`, `unreferenced` and a rejection do not.
- **`lost`** counts how many new owners answer a `stat` with `whole` against `min(max(1, event.floor), candidates.length)`, announces to each candidate that did not, and releases only when the count is reached. A reference this node does not hold `responsible` gets no entry at all, so the monitor's state for it is untouched. The `stat` is inverted — one request per peer naming every reference it is a candidate for, chunked at `MAX_BLOB_STAT_REFS` — because `event.lost` is not budget-capped the way `event.grown` is.

## Review findings

The implement-stage diff (`ticket(implement): feat-the-blob-cohort-reaction`) was read before the handoff summary, against `docs/blobs.md` §Placement, copying and durability, `RebalanceEvent`/`GrowthOutcome`/`recordGrowthOutcome`/`retainLost` in `packages/db-p2p/src/cluster/rebalance-monitor.ts`, `BlockTransferCoordinator.handleRebalanceEvent`, `BlobCopyDrain` and `AnnounceLimiter`.

### Fixed in this pass

- **A grown reference whose hold had gone was reported satisfied, which falsely confirms replicas.** `growOne`'s no-scope branch returned `{ satisfiedPeers: [...reported], complete: true }`. `satisfiedPeers` enter `RebalanceMonitor`'s `cohortPeers` — "peers CONFIRMED to hold a replica" — and a peer there is cleared only by leaving the cohort, so every reported peer was recorded as holding a blob it had never been told about. If the reference were later held again (`BlobAnnounceReceiver.keepAfterRead` re-takes a `responsible` hold after a read), the growth arm would stay silent for it. The stated justification — that an incomplete outcome "would retry this reference on every check for ever" — does not hold: `growthMaxAttempts` already bounds that, and a reference with neither an `owed` nor a `responsible` hold leaves the monitor's tracked set anyway. Now returns **no outcome**, which is exactly the case `recordGrowthOutcome` documents ("never called for a block the reaction had no information about — a missing outcome leaves the block's state untouched"), matching the block side's treatment of a deduped block. One test added for it.
- **`recordAfterOwedRelease` and `recordAfterResponsibleRelease` were byte-identical but for the hold kind.** Collapsed into `recordAfterHoldRelease(kind)` with the two names bound from it, so a third release hold adds a line rather than a function.
- **`BLOB_ANNOUNCES_PER_PEER_PER_MINUTE`'s stated magnitude became wrong with this change.** Its comment claimed "the reaction to a cohort change announces at most 64 blobs a check"; that is the growth arm, which `growthBlockBudget` caps. The release arm added here is uncapped — `RebalanceEvent.lost` carries every reference a check found this node outside the cohort of. Corrected, and the overrun recorded as a tripwire there (see below).
- **The class doc's reason for taking announcements in turn was overstated.** It claimed the per-reference sequencing keeps one announcement in flight per peer; cohorts overlap, so four references in parallel leave up to four. Reworded to the honest bound and the actual reason (`BLOB_REFERENCE_READS_IN_FLIGHT`).
- **`release:unreachable` was missing from the downstream documentation list.** Flagged by the handoff; added to `feat-a-held-blob-follows-its-cohort`'s `docs/debugging.md` item, which now lists twelve reaction lines.

### Parked as tripwires

- **A transiently-unsatisfiable peer is recorded as a confirmed holder.** `NOTE:` on `BlobCohortReaction.satisfiedWithoutRequest`. All three of its tests can be transient — `declining` is forgotten at the peer's next connection, a `refuses` may only be an unfinished identify — while the growth arm's report of such a peer enters the monitor's seen set permanently. So a peer that declined some *other* blob is recorded as holding this one. Left alone because the alternative converges on the same end state (an incomplete outcome abandons the peer for that reference after `growthMaxAttempts`, cleared by the same departure and nothing else); the real fix is a third `GrowthOutcome` state in the monitor, which is not this class's to add. The `refuses` half of the class is already tracked by backlog `debt-a-peer-read-as-refusing-may-only-be-unidentified`, whose `files:` names this ticket as the second reader of that verdict — no new ticket, per *Architecture first*. The release arm is unaffected: dropping such a peer from numerator and denominator alike can only make a release harder to reach.
- **The release arm's announcements are the one unbudgeted announcement path.** `NOTE:` at `BLOB_ANNOUNCES_PER_PEER_PER_MINUTE` in `packages/db-p2p/src/protocol-limits.ts`. A node shedding more than 600 references whose new owners overlap in one check has its later announcements answered `unreferenced`, costing a reference retained one more check — the release count reads the `stat` answers, not the announcements, so nothing is decided wrongly. The note says to cap the release arm rather than raise a receiver's defence.
- **Two reactions overlapping has no guard.** Added as an edge case to `feat-a-held-blob-follows-its-cohort`, which owns the handler. `onRebalance` handlers are synchronous and `void`, so a check firing before the previous reaction settles starts a second over the same references; the block counterpart guards this with its `inFlight` keys. Benign (`releaseResponsible` is idempotent, duplicate announcements are what `AnnounceLimiter` is for) and unlikely at a 60-second minimum check interval, but the handler's author should decide it deliberately rather than inherit it.

### Carried from the handoff, examined and left

- **An undecodable blob record fails the whole reaction rather than skipping one reference** — the handoff asked whether its `NOTE:` on `scopeOf` should be a defect instead. Left as a tripwire: `responsibleScope` throws only on a record `BlobRecordStore` cannot decode, nothing in `src` writes one, and `inParallel` propagates it to the handler, which logs it. Genuinely conditional ("fine now; *if* such a record is ever observed, give the reaction a tolerant read"), so it stays a tripwire by the stage rules rather than a ticket.
- **`BlobReactionResult.growth` keyed by `string` while `released`/`retained` are `BlobRef[]`** — the asymmetry is the consumer's: `RebalanceMonitor.recordGrowthOutcome(blockId: string, …)` takes a plain id, and the keys arrive as the `string` keys of `event.grown`. Narrowing them to `BlobRef` would mean a cast with nothing behind it. Left.
- **`event.lost` and `event.grown`'s keys cast to `BlobRef`** — kept. `newOwners` is built from `cohort.filter(id => id !== selfId)` and both key sets come from the monitor's tracked set, which 2.66 feeds from blob records only; a non-reference would throw `BlobRefError` out of the record read rather than being mis-handled, and the casts carry that reasoning in comments.
- **`inParallel` and `chunksOf` as new local helpers** — searched `packages/db-p2p/src` and `packages/db-core/src`; the only concurrency limiter in the repo is `BlockTransferCoordinator`'s private semaphore, which is a different shape (acquire/release around a push, not a bounded map). Two small local functions beat extracting a utility for one caller. Left; if a second caller appears they belong in a shared module.
- **Unmeasured magnitudes** — the handoff's request-count claims are read off the code, and the fixed comments above now say so where they are stated.

### Checked and clean

- **The release count cannot be reached wrongly.** `required = min(max(1, floor), candidates.length)`; a count of zero retains, and only `stat` answers count toward it — a peer that answers `whole` to the announcement this pass just sent is deliberately not counted, so one snapshot of the cohort decides. Dropping a `refuses`/`declining`/non-member peer removes it from both sides of the count, which was traced through both directions: with floor 2 and one of two new owners refusing, both the filtered (`1/1` → release) and unfiltered (`2/2` → release) readings agree where the remaining peer holds it, and the filter is what keeps the hold from being held for ever where it does not.
- **No self-announcement.** `newOwners` excludes `selfId` at the monitor, `grown` never names self, and the acceptance call filters it again.
- **Error paths.** Every peer-caused failure is caught at its call site and logged (`grow:unreachable`, `release:unreachable`, `release:stat-failed`, `acceptance:failed`), a wrong-length `stat` answer counts its whole chunk as not `whole`, and only a local fault reaches `inParallel`'s rejection — which `Promise.all` in `handle` attaches a handler to, so no rejection floats.
- **Resource cleanup.** Nothing to clean: no timers, no streams, no subscriptions; the class holds only its deps.
- **Entry parity and React Native reachability.** Both entries export the module and `test/entry-parity.spec.ts` passes; every import in the new file is type-only or pure, which the "reaches no Node builtin from the React Native entry" case and `yarn check:rn` both confirm.
- **Source hygiene.** `cohort-reaction.ts` is 388 lines after the fixes, decomposed into named steps with no narrated runs. `local-blob-service.ts` is at 933 lines and four queued implement tickets (2.73, 2.74, 2.85, 2.86) add to it; no size-debt ticket was filed, because the right moment to measure a split is after they land, not while the file is still growing — noted here so the next reviewer of that file has the number.
- **Documentation.** `docs/blobs.md`, `docs/internals.md` and `docs/debugging.md` were all read. None needed an edit in this ticket and none is now stale: *When the cohort changes* carries no "**Built:**" marker and no citation into this file, which is correct while nothing constructs the class, and `feat-a-held-blob-follows-its-cohort` owns all three edits (its list was corrected above). `yarn lint:docs` passes.
- **The implementer's two tests** were weighed against *Tests must pay for themselves* and kept: each pins real branching named by the specification — the release count over one `stat` snapshot (with the retain-on-short-count path, the announce-after-stat step and the new record door in the same test) and the announce-answer-to-`GrowthOutcome` mapping — over a real `LocalBlobService` rather than a mock of one. Neither restates the implementation. Nothing was cut.
