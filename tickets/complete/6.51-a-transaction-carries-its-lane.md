# A transaction carries its lane

First of four implement tickets from the plan of the same name; db-core's half of the lane vocabulary. Every write now carries a **lane**, `serializable` or `convergent`, saying whether its conflicts with other machines' concurrent writes are the quorum's to decide under the revision order, or may be merged later under the collection's declaration. The field rides exactly where the HLC rides (the action entry, the transaction's id and client signature, each pend and commit), is minted once per write and re-sent by every retry, and a collection declares which of its actions merge through `CollectionInitOptions.merge`, which replaces the bare `filterConflict` hook. **No admission rule changed**: the solo path, the offline queue and the conflict replay behave as before. The next three tickets are the SQL classification, the member-side check and the operator-visible reporting.

## What landed

Landed in `ticket(implement): a-transaction-carries-its-lane`; see that commit for the full table of carriers. In short:

- **The vocabulary.** `Lane`, `stricterLane` (serializable if any part is; an empty set answers serializable) and `laneField` (the omit-when-unset request wrapper, mirroring `refuseSoloField`) in `packages/db-core/src/lane/lane.ts`, exported from the package index.
- **The declaration.** `ConvergentMerge<TAction>` in `packages/db-core/src/collection/collection.ts`: `laneOf(action)` plus the old hook as optional `filterConflict`, which `Collection.doFilterConflict` now offers only to an action the declaration classifies convergent. `Collection.laneOf(actions)` is public and pure. `Diary` declares append-only convergent; `Tree` declares nothing and `TreeCollectionOptions` lets a raw tree opener declare one.
- **The carriers.** `ActionEntry.lane` (read through `laneOf` in `packages/db-core/src/log/struct.ts`, which answers serializable for a stored entry from before the field), `WriteIdentity.lane`, `InFlightCycle.lane` (required, so the re-send of a torn attempt carries it too), `SyncOptions.lane`, `HeadCommitOptions.lane`, `Transaction.lane` (folded into `createTransactionId` and `clientSignaturePayload`, now `txsig:v3`), `WriteContext.lane`, `EntryCommit.lane`, `PendRequest.lane`, `CommitRequest.lane`, `RepoCommitRequest.lane`, and the offline queue's `Entry.lane`, `JournalEntryRecord.lane`, `RestoreInit.lane` and the `queued` status's `lane`. The plugin's journal record keeps `v: 1` with an optional `lane`, restored as serializable when absent.
- **The sources.** A sync takes `options.lane`, else the collection's declaration over its open segment. `TransactionSession.commit` takes `options.lane`, else serializable. `OfflineQueue.enqueue` takes `init.lane`, else the stricter of each sealed collection's declaration over the segment it sealed, fixed for the entry's life and journaled. The coordinator's two commit paths take the lane off the transaction and the entry.

## Review findings

Reviewed from the implement-stage diff first (`ticket(implement): a-transaction-carries-its-lane`), then against the handoff summary.

**Checked and found correct.**

- Every wire path that rebuilds a commit request carries the lane: `repoCommitRequest` and `commitOf` in `packages/db-core/src/transactor/network-transactor.ts` serve the one-round commit, the tail-then-sweep path, `commitBlock` and `commitMany`; `pendRequestForBatch` spreads it through `rest`. `TransactorSource.transact` puts it on both the pend and the commit.
- The log's three entry builders: only `Log.addActions` builds an action entry, so `ActionEntry.lane` being required does not reach `addCheckpoint` or `addInvalidation`.
- The lane is minted once per write at every source (sync, session commit, enqueue) and every retry re-sends it: `send` reads the identity, `completeOwnEntry` reads the cycle, and the two are set from one value in `syncInternal`, `openHeadCommit` and `inFlightCycleOf`. `retry-resends-identical-transforms.spec.ts` passes unchanged, which is the evidence no per-attempt value crept in.
- Every `Transaction` literal and `createTransactionId` and `clientSignaturePayload` call the mechanical pass touched was read for a lane other than serializable; the only non-serializable lane in any test is the deliberate `sync({ lane: 'convergent' })` in the new case. Nothing was weakened or skipped.
- `inFlightCycle` as `undefined` outside a cycle: both readers run only inside a marked cycle, as the handoff says, and the optional reads are harmless.
- `Diary` becoming convergent changes nothing observable: it declares no hook, so `doFilterConflict` keeps every action, as before. A diary-only offline entry now reports `lane: 'convergent'` on its `queued` status, which is the intended new fact.
- The validator derives `transaction.lane ?? 'serializable'` for the payload check only and hands the transaction on unchanged, matching the HLC's treatment.
- `TreeCollectionOptions` generic defaults and the plugin's narrowed `treeOptions()` return type: compiles without a cast and declares what the plugin actually sets.

**Minor, fixed in this pass.**

- Four doc statements were out of date with the new id preimage, signature version and journal record: `docs/internals.md` still named `txsig:v2` as the client signature version in the HLC bullet (now points at the `v3` bump); `docs/offline-sync.md` §What is journaled omitted `lane` from the entry record's shape and from the key table, though the queue journals it; `docs/architecture.md` (two sites) and `docs/transactions.md` §Two distinct identifiers still described the transaction id as a hash of stamp id, statements and reads only.
- The implementer's new test ("the lane a write carries") was kept: one behaviour, which source decides the lane, with real branching, read back through `laneOf` over a fresh handle. The converted `filterConflict` cases assert what they asserted before. No test was cut and none added: the wire plumbing and the journal field are glue, and the retry identity rule is already pinned.

**Major.** None. The change adds a field along the HLC's existing carriers and gates one hook on it; no admission rule moved, and the four suites plus the upgrade-check fixtures confirm stored data from every published release still reads.

**Tripwires recorded.**

- `NOTE:` at the lane's mint site in `Collection.syncInternal` (`packages/db-core/src/collection/collection.ts`): the lane is judged over the open segment as staged at mint time and fixed for the write, so a `merge.filterConflict` hook that answered a replacement of a different lane during an inter-attempt refresh would leave the entry claiming the replaced action's lane. No hook in this repository replaces an action; the member-side lane check (a later ticket) is what would catch it.
- The existing `NOTE:` at `laneOf` in `packages/db-core/src/log/struct.ts` already records that `ActionEntry.lane` is declared required while a stored legacy entry lacks it, and when to split the stored and written shapes.

**Considered and declined.**

- `Collection.send` reads the lane off the identity while `completeOwnEntry` reads it off the cycle. Both are set from one value, and threading the identity into the re-send would widen `completeOwnEntry`'s signature for no behavioural gain. Left as is.
- Three things named `laneOf` (`ConvergentMerge.laneOf`, `Collection.laneOf`, the free `laneOf` for log entries) read fine in context since two are members and only the log reader is a package export. Left as is.

**Not done, by the plan's assignment.** `docs/crdt-sync.md` §Stage 5 and `docs/partition-healing.md` §How Optimystic Surfaces This still describe the pre-lane shape, and `.release-notes.pending.md` carries no note yet; the reporting ticket owns both once all four tickets land. The plugin's `OfflineMode.enqueue` passes no `lane`, so an offline SQL entry takes its trees' declarations (serializable); the SQL classification ticket passes the fold through.
