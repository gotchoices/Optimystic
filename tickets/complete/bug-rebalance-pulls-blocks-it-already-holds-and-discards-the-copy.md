# What landed

`BlockTransferCoordinator.handleRebalanceEvent` no longer reacts to `RebalanceEvent.gained`. The reaction used to call `RestorationCoordinator.restore(blockId)` per gained block and discard the archive it got back — a network round trip per block, uncapped, and worst on every restart (the whole stored set reads as `gained` on the first post-restart check) — that could neither supply a missing block nor refresh a stale one, because `RebalanceMonitor` only ever reports `gained` for a block already in its tracked set and nothing persisted the result.

Removed with it: `pullBlocks`, `executePull`, the `withTimeout` helper (its only caller), the `restorationCoordinator` constructor parameter (a breaking positional-signature change, every call site updated), the `pulled` field on `RebalanceReactionResult`, and the `ownedBlocks.add(blockId)` loop over `event.gained` in `libp2p-node-base.ts` — a provable no-op, since `trackedBlocks` *is* that set.

Kept: `gained` is still reported, as a responsibility signal for logs and the monitor's own bookkeeping; `restorationCoordinatorV2` stays wired as `BlockStorage`'s `newRestoreCallback`, which is the read-time repair path and a different mechanism entirely. A node that gains responsibility for a block it does **not** hold is not in the tracked set at all, so it never produced a `gained` report; it still receives the block by a holder's cohort-growth push or by repair on first read.

# Review findings

## What was checked

The implement diff was read first — source, tests and docs — before the handoff summary. The central premise was verified structurally rather than taken on the ticket's word: `performRebalanceCheck` derives `gained` only by iterating `trackedBlocks`, and `initRebalanceMonitor` is handed the node's shared `ownedBlocks` set as exactly that field, so `gained` is a subset of `ownedBlocks` by construction and the removed `ownedBlocks.add` could never add anything. The no-regression claim was checked per shape: for a node holding a stale copy, and for one holding no committed content, the deleted `executePull` discarded the archive too, so nothing it did is being lost. The handoff's own first ask — constructor blast radius — was re-run: `new BlockTransferCoordinator(` has four sites in the tree (one in `src`, three in `test`), all updated, and there is no non-TypeScript source to miss. `restorationCoordinatorV2` was confirmed still live on the read-repair path. Then: lint over all of `packages/db-p2p/src` and `test`, `yarn lint:docs`, `yarn build`, and `yarn workspace @optimystic/db-p2p test` (3109 passing, 0 failing, 63 pending — the same env-gated skips the implement stage reported). No new test was added: the diff's own gained-block regression test covers the defect once its vacuous half is removed (below), and nothing else here is a contract that went unverified.

## Fixed in this pass (minor)

- **The move-in delivery claim was wrong, in all three places the diff wrote it.** `ring-shift-coordinator.ts`'s `moveIn`, `docs/arachnode-ring-handoff.md` and `docs/internals.md` all replaced the old (also wrong) "it pulls the gained half" with a positive claim that the existing holders' cohort-growth push delivers it "once they observe the mover as newly co-responsible". The growth arm decides co-responsibility with `RebalanceMonitor.cohortFor` → `findCluster`, which is FRET proximity plus network membership and never consults the arachnode ring depth — so a ring move-in on its own puts the mover in no block's cohort and triggers no growth push. All three now say what is true: read repair on first access is what always delivers the gained half, and a growth push delivers it only where FRET routing independently agrees.
- **Two vacuous assertions in the diff's own tests.** Both "no fetch on gained" tests asserted `restoration.restoreCalls` is empty against a `MockRestorationCoordinator` that is no longer passed to anything — nothing could ever have called it — and `block-transfer.spec.ts`'s comment described that dead object as one that "stays wired". The third assertion, `expect(result).to.not.have.property('pulled')`, restates a field the type already forbids. The dead mocks (and the `makeArchive` helper and `BlockArchive` import that existed only for them) are gone from both specs; what remains is the assertion that actually binds — no peer was dialled — plus the result arms being empty, and, in the combined lost+gained test, that the only peer dialled was the lost block's new owner.
- **The two concurrency tests were repointed onto a method nothing calls.** The diff moved the semaphore's deadlock and cap tests off `pullBlocks` and onto `pushBlocks`, which has no caller in `src` — the lost-block arm moved to `confirmReplicated` when release became confirm-gated. They now drive `confirmReplicated`, the live caller of the same semaphore and retry loop, so the tests pin the path production actually takes.
- **Comments the diff left contradicting the docs it updated.** `RebalanceMonitor.recordBlockHolders` still said the evidence means the blocks "need no pull" and that without it the monitor "reports it gained, pulling it back from them"; `replicateGrown`'s no-local-data `NOTE:` justified itself with "those cohort peers are the pull's own source"; `BlockTransferServiceInit.onBlockHolders` and `ReconcileBlockDeps.onBlockHolders` both promised a replica would not be "pulled again as if newly gained"; `rebalance-monitor-node-wiring.spec.ts` twice explained the arachnode gate as the place "fretAdapter + RestorationCoordinator only exist"; and `docs/debugging.md`'s `block-transfer` namespace row still advertised `pull` outcomes in a log that no longer emits any. All corrected.
- **The premise as written was slightly stronger than the code.** "The watched set is built entirely from this node's own storage" skips `seedOwnedBlocksFromStorage`'s documented, accepted over-inclusion: the restart seed enumerates the metadata store, so a pend-only block (metadata, no committed revision) is tracked too. That does not weaken the change — fetching for such a block would be wrong rather than missing, since a pend is not a revision anyone can serve — but the doc now says so, and the two sibling claims that rested on the old framing are corrected with it: `RebalanceEvent.grown`'s note that a gained-and-grown block's push "finds no local data" (true only of the pend-only case; after a restart the node normally does hold the block and the push proceeds), and the matching sentence in `docs/internals.md`.

## Tripwires recorded, not filed

- `NOTE:` at `moveIn` in `packages/db-p2p/src/storage/ring-shift-coordinator.ts` — a move-in that FRET routing does not mirror leaves the gained half un-prefetched, so every read of it costs a repair round until a commit touches the block. If ring moves become frequent, or reads of a freshly-gained range show up as slow, give move-in its own fetch phase — and a corroborating one, per the `NOTE:` on `handleRebalanceEvent`.
- `NOTE:` at `BlockTransferCoordinator.pushBlocks` — nothing in `src` calls it, and `enablePush`, the only `BlockTransferConfig` field it reads, is unreachable besides: `libp2p-node-base` constructs the coordinator with no config at all. This is dead weight rather than a defect (an uncalled method costs nothing at runtime) and it predates this ticket, so it is recorded at the site with its delete condition rather than filed.

## Tickets filed: none

No finding reached the filing bar. The change is a pure removal whose behaviour delta is zero for every reachable shape, so there was no defect to anchor a `bug-` ticket to; everything above was a comment, a doc sentence or a test that could be corrected in place; and the two structural observations are conditional, which the rules place in a `NOTE:` rather than a queue.

## Considered and not flagged

`acquireSemaphore` can in principle over-subscribe: `releaseSemaphore` decrements and resolves a waiter synchronously, but the waiter's own `concurrency++` runs a microtask later, so a caller acquiring in that window takes the freed slot first. It is pre-existing, untouched by this diff, and not reachable from either caller as written — `pushBlocks` and `confirmReplicated` launch all of their acquires up front, and a retry re-acquires only after its own release plus a backoff delay, so no acquire ever lands inside the window. Left alone, and recorded here rather than as a `NOTE:` because it is a hypothesis about a path no caller takes.
