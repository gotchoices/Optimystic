GitHub #44 (kjeib), comment of 2026-11-03. A page of log entries filtered with `where lei.entry_id in (…31 ids…)` read all of `log_entry_items` and then did one lookup per row in each joined table. That took 7 seconds on the reporter's phone.

## What was built

**Which columns may be sought.** The index and primary-key trees compare raw bytes, and the engine does not re-check a filter a module claims. So a seek on a column where equal values can have different bytes loses rows. A column stays a residual filter over a scan in these cases:

- **Any key column** (`seekCanBeTrusted`): a non-BINARY key collation, or a type with semantic ordering (`timespan`, `json`).
- **A secondary index column** (`indexSeekCanBeTrusted`, added in review): type `boolean` or `any`. The engine compares `true` equal to `1`, but an index frames them as different bytes. A primary key frames both as `1`, so it needs no such rule.

**Which filters are claimed.** `matchEqualitySeek` walks a key's columns and claims the first equality-role filter on each, which is the one the engine seeks on. `runtimeSet` filters are never claimed. A multi-value `in` is only ever the sole seek column, because of the engine defect in the `blocked/` ticket `quereus-composite-in-seek-drops-a-bound-equality`. So a primary-key list needs a single-column key.

**Cost and rows.** With `seek = log2(max(2, N)) * 2`:

- `rows = max(1, floor(min(N, K * perKey)))`.
- `cost = K * seek + rowTerm`, where `rowTerm` is `min(N, K * perKey)` for measured or unique seeks and `perKey` for the no-statistics constant.
- A primary-key list costs `K * seek`, and competes on cost rather than exiting early.

Multi-seeks report `isSet: false` and no `providesOrdering`.

**Running it.** A `plan=5` plan means one seek per argument, and `seekTuplesOf` throws on a `seekWidth` other than 1. `seekKeysInTreeOrder` drops NULL-bearing seeks, drops repeats and sorts. `indexSeekKey` seeks a boolean as its number. Views are built once per scan, never once per value. The trace stays one `index:seek` line per scan, with `seek=` listing every key.

**Timing**, from the implement stage and not re-measured after review (Node, in-process `test` transactor, no network; 177 entries, 485 rows, 31 listed ids, 89 rows returned, median of 25 runs):

| | in list | same joins, no `where` |
|---|---|---|
| before | 19.2 ms | 7.7 ms |
| after | 12.7 ms | 8.3 ms |
| memory table | 4.4–6.4 ms | 7.2–7.8 ms |

"Before" is this build with `firstEqualityRoleFilter` limited to `=`, which plans lists as HEAD did, not a build of HEAD itself. Nothing here says what the Galaxy S7 figure becomes.

## Review findings

Method: read the implement diff (`ticket(implement): an-in-list-on-an-indexed-column-seeks-the-index`) before the handoff, then ran scratch probes that compared an indexed Optimystic table, an unindexed one, a primary-key table and memory tables, across ten column types, with literal and bound values.

### Fixed in this pass

- **A regression: lists lost rows when a boolean met a number.** At HEAD a list was a residual filter and so was right; the implement build claimed it.
  - `n in (true, 2)` on an indexed integer returned only the row with 2, not the row with 1.
  - `f in (1, 2)` on an indexed boolean returned nothing.
  - `x in (1, 7)` on an indexed `any` column missed a stored `true`.
  - `a in (?, ?)` bound to `[true, 'b']` on an indexed text column also returned a row holding the text `'true'`.

  The same statements with `=` were already wrong at HEAD, and this fixes those too. The fix is `indexSeekCanBeTrusted` plus converting a boolean to its number in `indexSeekKey`. I added 5 test statements, and mutating each arm fails them (3 and 2 failures). Cost: an indexed `boolean` or `any` column now scans. An untyped column is `BLOB` (measured), so only columns declared `any` pay for that.
- **A wrong doc example.** `docs/debugging.md` printed `seek=%01tok-a%00,…`; a real trace prints `%02`. Corrected.
- **Tests cut or renamed.** I cut `a repeated literal value` and `only literal nulls`, because the engine reduces those lists before the module sees them, and `a value that alone is a prefix of stored values`, which repeated the prefix case. I renamed `ranks a list above an =`, which read backwards, to `prefers an = to a list on equal terms`.

### Filed

- **`fix/a-delete-on-an-optimystic-table-skips-what-the-engine-does-after-it`** (`repro: verified`, not caused by this ticket). The `delete` arm of `update` returns no row, so the engine treats the row as not found. `on delete cascade` does not run, child rows stay, and `returning` and data events report nothing. I found this while checking delete through the new scan path.
- **Arm appended to `backlog/bug-optimystic-unique-ignores-collation-and-partial-predicate`**: a `nocase` primary key accepts both `'ABC'` and `'abc'`, where a memory table refuses the second. This answers the implementer's open question about uniqueness across case.

### Tripwires (`NOTE:`)

- At `seekKeysInTreeOrder`: key framings of different storage classes can coincide, so a mixed list such as `t in (1, 'a')` on a text primary key also returns the row `'1'`, and a bound `'AQ=='` on a blob index finds the blob. Measured, unusual in practice; left as a note because the engine converts a list of one type.
- At `acceptAll` in `test-harness/build-freshness.mjs`: a typecheck that rewrites `tsconfig.test.tsbuildinfo` can make a stale `dist` read fresh. This is the implementer's observation, inferred and not reproduced. Counting `.tsbuildinfo` is deliberate, so I did not change it.

### Implementer's open questions

- **The primary-key repeat tracking (`yielded`) stays, without a test.** It is the only guard against returning a row twice when a row moves between two seeks, and the engine does not de-duplicate a claimed filter. It costs one set entry per returned row, only for a list of more than one key. I also could not find a way to drive that gap from SQL without mocking repository code, so a test would be at the wrong layer. It remains the one surviving mutation.
- **Multi-seek order** being byte order rather than declared order is safe while this module is not wrapped by the isolation layer. The `NOTE:` stands. A real `in` over a numeric column returns correct rows.

### Checked, nothing wrong

- **Collation pairs:** a binary index over a `nocase` column, a `nocase` index over a binary column, and explicit `collate` on the predicate, for `=` and `in`. All return correct rows, and the engine declines the mismatched seeks.
- **Two filters on one column:** `=` with `=`, `in` with `in`, `=` with `in`. The first is claimed and the engine keeps the rest as a residual, including at a point seek, which now claims only the first.
- **Value coercion:** strings on numeric columns and numbers on text columns, literal and bound. The engine converts a list of one type before the module sees it.
- **Temporal types and blobs:** `date`, `datetime` and `time` values are normalized on insert and found by `=` and `in`; blob columns seek correctly apart from the tripwire above.
- **Reads:** a committed read through a multi-seek inside an open transaction sees the pre-transaction rows, for an index and a primary key. A live read in the same transaction sees staged changes. `limit` ends a multi-seek cleanly.
- **A `nocase` primary key through the new scan:** update, same-key update, case-changing update and delete match the memory table, apart from `returning` on delete, which is the filed bug.
- **Peer range:** every Quereus export the change imports predates `^4.25.0`, the plugin's declared range. The reporter's 4.24.0 is already outside that range.
- **Resource cleanup and error handling:** the trace is emitted in `finally`, an unsupported `seekWidth` throws, and an empty multi-seek returns nothing rather than falling through to a scan. Nothing new holds a resource across scans.
- **Docs:** the plugin README and `docs/debugging.md` were updated for the new reality. `docs/internals.md` describes the read path by method name, and those names are unchanged.

### Not addressed
