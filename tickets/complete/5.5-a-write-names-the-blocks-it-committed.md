# A write names the blocks it committed

Part of GitHub issue #26. The db-core half of "map the full-replication event back to the commit the app knows"; the consumer is `a-sql-commit-learns-when-it-becomes-fully-held` (in `implement/`), with `a-durability-answer-says-whose-ledger-owes-it` between them.

## What landed

`WriteDurability.blockRevs?: Readonly<Record<BlockId, number>>` — action-level, every block the write committed with the revision it committed at. Set client-side only, by `withBlockRevs` in `packages/db-core/src/network/durability.ts`, at the three places a commit is confirmed:

- `TransactorSource.transact` on success (`pendResult.blockIds` at `rev`) — covers every `Collection.sync` attempt and the own-entry re-send in `Collection.completeOwnEntry`;
- `TransactionCoordinator.commitCollection` on success (its pended `blockIds` at the pended `rev`);
- `Collection.settleUnfinished`'s "superseded but saved" return (`entry.blockIds` at the write's own `rev`), only when `getLineage` supplied a durability.

`mergeDurability` treats it like `torn`: taken over the original reports (union, highest revision per block, minus every torn id), stripped from `otherCohorts` and from the `distinctReports` key. `withTornBlocks` drops newly torn ids from it. An empty map is left off. It never travels on the wire.

Validation (implement stage): db-core 1887 passing, db-p2p 3288 passing / 70 pending, root typecheck, lint:docs, eslint.

## Review findings

Read the implement diff (`ticket(implement): a-write-names-the-blocks-it-committed`) before the handoff, then each set-site in context.

**Correctness — checked, no defects.**
- `pendResult.blockIds` is `blockIdsForTransforms(transforms)` in both `NetworkTransactor.pend` and `TestTransactor`, so every block of the write (inserts, updates, deletes) is named; the coordinator's `pendedBlockIds` come from the same field.
- Torn blocks: `NetworkTransactor.commit` clamps with `withTornBlocks` before the answer reaches `TransactorSource`, and `withBlockRevs` excludes `d.torn`, so an abandoned block is never named. Merge removes an id torn by any input even if another names it committed — deliberate (a torn write is never `isFullyDurable`, and 5.53 already refuses to follow a torn commit).
- Superseded-but-saved names the blocks at the write's own revision; an event at the superseding later revision covers it under the documented "at that revision or later" match. The added `rev !== undefined` guard is behaviour-neutral (lineage is only asked when `rev` is defined).
- Multi-collection: `recordCollectionDurability` / `transactionDurability` carry `blockRevs` through `mergeDurability`; an `undefined` side drops it along with the class, matching "saved, holder unknown".
- Remote/mixed-version: no db-p2p source references the field; nothing added to any request or response.
- Consumer-side concerns the handoff flagged (a `full` answer gets no event; an event can precede the answer; torn never becomes full; mixed full/below-full cohorts) are all already written into `5.53-a-sql-commit-learns-when-it-becomes-fully-held`. Nothing to file.

**Minor — fixed in this pass.**
- `highestBlockRevs` assigned into a plain `{}` keyed by block id. A header block's id is its collection id, which a caller chooses, so an id of exactly `__proto__` would have set the prototype instead of a key. Now accumulates in a `Map` and converts with `Object.fromEntries`.
- `packages/db-p2p/docs/repo.md` § The under-replication drain and the full-replication event still told hosts to hold `PendSuccess.blockIds` — a field a host never sees through `sync` or a SQL commit. Now points at `WriteDurability.blockRevs` and the "that revision or later" rule, matching the `change-notifier.ts` doc.
- The set-site contract had no pin (the adjusted specs strip `blockRevs`). Added one assertion to the existing `Collection.sync` case in `write-durability-reaches-the-writer.spec.ts`: the answer names exactly the three blocks of the commit (header by collection id, log block, inserted block), all at revision 1. No new test case.

**Tests.** The new `durability.spec.ts` case pins real branching (max-wins, torn exclusion from both `withBlockRevs` and the merge, action-level stripping, nested merge = flat merge) — kept. The two `answered()` helpers in the adjusted specs are small duplicated strippers in separate spec files; left as is (two copies, test-local).

**Docs.** `docs/internals.md` § Commit Path, the `WriteDurability.blockRevs` and `BlockDurabilityReachedEvent` doc comments and the `transact` JSDoc read correctly against the code; `repo.md` fixed as above. `yarn lint:docs` passes.
