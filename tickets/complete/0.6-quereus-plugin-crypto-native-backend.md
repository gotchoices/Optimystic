# quereus-plugin-crypto: a native crypto backend

GitHub: [#30](https://github.com/gotchoices/Optimystic/issues/30). The reporter measured one tally invitation at 29 s on a Galaxy S7. SQL `verify` took 408 ms of that, inclusive, and 366 ms of the 408 was noble's JavaScript Ed25519.

## What was built

`setCryptoBackend(backend | undefined)` and the `CryptoBackend` interface live in `packages/quereus-plugin-crypto/src/crypto.ts` and are exported from the package root. The interface has four members, all optional: `sha256`, `sha512`, `ed25519Sign(message, rawSeed)` and `ed25519Verify(signature, message, rawPublicKey)`. Any member the backend leaves out stays on `@noble`.

- **Where the backend is stored.** It lives on `globalThis` under `Symbol.for('@optimystic/quereus-plugin-crypto/backend')`. `dist/index.js` and `dist/plugin.js` each carry their own copy of `crypto.ts`, and so does a second installed copy of the package; this key is the one slot they all share.
- **Read on every call.** The `HASHERS` entries for sha256 and sha512 are dispatchers (`dispatchHash`) that read the backend on each call. The Ed25519 branches of `sign` and `verify` go through the `ed25519Sign` and `ed25519Verify` helpers, which do the same. So a backend set after the plugin was registered still applies, to the plugin's digest hasher, `cid`, `hashMod`, `set_commit` and `set_verify`.
- **What is installed.** The installed backend is a frozen copy holding only the four known members, each bound to the caller's object (`snapshotBackend`).
- **Self-check when set.** `selfCheckBackend` runs each supplied member once against noble on fixed inputs. Each input is a view at offset 1 inside a larger buffer, so an adapter that hashes `data.buffer` instead of the view fails. If any member disagrees, the call throws and names that member, and the previous backend stays installed.
- **Ed25519 strictness tripwire.** A `NOTE:` at `ed25519Verify` records the ZIP-215 difference between noble and RFC 8032-strict native libraries; the README says the same.

## Review findings

**Diff read.** Read `ticket(implement): quereus-plugin-crypto-native-backend` before the handoff, and compared it with the plan ticket's design. Every design point and TODO item is implemented as specified.

**Correctness, checked by reading the code:**
- `resolveHasher` is the only route to sha2. Every hashing caller goes through it: `digestFields`, `hashMod`, `cid`, and the default hasher parameters in `sd.ts`. `cid_v1` takes a digest that is already computed, so it never hashes. Nothing else in `src/` imports `sha256`, `sha512` or `ed25519` for hashing, signing or verifying; `generatePrivateKey` and `getPublicKey` still use noble, which is correct because those are not backend members.
- Error paths: `verify`'s catch-all turns a backend throw into `false`. A throw in `sign`, `digest` or `cid` propagates, as the ticket requires.
- `hashMod` builds its `DataView` with the returned array's `byteOffset`, so a backend that returns a `Buffer` or an offset view is read correctly.
- `sameBytes` checks `instanceof Uint8Array`, so a backend that returns an `ArrayBuffer` (which some JSI libraries do) is refused at set time instead of failing later.
- Snapshot members that are absent are stored as `undefined` keys, and the `?? noble` fallback handles them.
- Bundle split: `/plugin` tree-shakes the setter but keeps `currentBackend`, and the spec covers that case (the plugin is registered from `dist/plugin.js`, the backend is set through `dist/index.js`).

**Found and fixed (minor).** One contract was not stated anywhere: a member's returned array must be newly allocated. Under the `bytes`/`raw` encoding the hash reaches the caller uncopied, so a native library that reuses one output buffer would silently rewrite results it had already returned. The self-check cannot detect this. The requirement is now in the `CryptoBackend` doc comment and in the README's error-behaviour bullet.

**Tests.** The two specs pay for themselves. One covers byte identity across both bundles when the backend is set after registration, and also confirms the backend is actually called. The other covers refusal, including the `data.buffer` adapter mistake, and checks that the previous backend stays installed. No tests were added or cut. The known gaps listed in the handoff are all simple per-member fallbacks with no branching worth a test: a backend that throws at call time, a partial backend, two installed copies of the package, and asserting `setCryptoBackend(undefined)` directly (the `afterEach` reset already depends on it).

**Docs.** I read every file the change touches. The README section, the `docs/crypto.md` architecture paragraph, the `index.ts` header and the comments in `cid.ts` and `plugin.ts` all match the code. The SQL function names cited in the README (`hash_mod`, `set_commit`, `set_verify`) match `plugin.ts`. `docs/releasing.md` has no CHANGELOG convention, so the **"Unreleased"** heading stays; whoever releases renames it to the version number.

**Tripwires.** The ZIP-215 one already sits at `ed25519Verify`; nothing new was parked. Another conditional limit is already stated in the README: the self-check is one known answer per member, so it catches an adapter built wrong but cannot prove a native library correct on every input.

**Not verified.** Nothing has run on a device or with react-native-quick-crypto, and the README says so.

**Validation.** Ran from `packages/quereus-plugin-crypto`: `yarn build`, `yarn test` (127 passing, before and after the fix), `yarn typecheck`. Ran from the root: `yarn lint` and `yarn lint:docs`, both clean.
