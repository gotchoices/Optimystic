# A peer is judged serving only by its own identify

## What was built

libp2p 3.3.11 merges every negotiated stream's protocol into the remote peer's peerStore record, on both ends (`Connection.newStream` and `onIncomingStream`). On the receiving end that made a machine that only sends `repo` requests read as serving storage in `Libp2pKeyPeerNetwork.membershipOf`, so it was remembered, persisted and put in cohorts whose writes then waited on it (GitHub sereus#63). It was also the "by opening a stream" route by which a stranger got counted as a member.

- `filterStorageClaimMerges` (`packages/db-p2p/src/network/storage-claim-filter.ts`) wraps `peerStore.merge` and drops a per-stream merge (`isProtocolOnlyMerge`, moved here from the throttle because the filter outlives it) of this network's `repo` or `cluster` protocol into a remote peer's record, answering with `peerStore.get` (or an empty-protocols merge when no record exists). Self merges and everything else pass through. Installed in `createLibp2pNodeBase` before start, outside `throttleProtocolMerges`.
- `storageServingProtocols` (`packages/db-p2p/src/network/storage-protocols.ts`) names the two ids for the key network, the filter and the prepared-stream list.
- Docs and NOTEs updated: internals §Network Membership Predicate (route closed, cost, mixed versions), §Third-Party Address Learning, debugging namespace row, `membershipOf` / `heardFromBootstrapPeer` NOTEs, `NodeOptions.isNetworkMember` doc.
- Reproduction spec `packages/db-p2p/test/storage-claim-filter.spec.ts`: two real libp2p nodes over loopback, identify settled first; the listener's record of a pure requester does not name `repo`, still names a non-storage protocol, and the requester's record of the server still names `repo`. Fails without the filter.

## Review findings

Read the implement diff (`ticket(implement): a-peer-is-judged-serving-only-by-its-own-identify`) before the handoff, then checked libp2p's actual writers.

- **Correctness of the premise — checked, holds.** In the installed libp2p, `connection.js` calls `peerStore.merge(remotePeer, { protocols: [protocol] })` on both stream paths, and `@libp2p/identify` writes the peer's list with `peerStore.patch` (only its metadata goes through `merge`, multi-key, so it passes). `@libp2p/peer-store` throws `NotFoundError` by name, matching the filter's name test. So identify really is the only remaining writer of the storage protocols, and the fallback branch catches the right error.
- **Wrapper ordering / bookkeeping — checked, fine.** The filter captures the throttle's wrapped `merge`, so dropped merges never touch the throttle, and the empty-protocols fallback (length 0) is not a protocol-only merge, so it passes the throttle. A dropped merge emits no `peer:update`, so `PeerRecordCache` stays valid.
- **DRY (fixed inline).** `storageServingProtocols` claimed to name "the ids `RepoService` and `ClusterService` register", but those services and their clients each hand-built `'/repo/1.0.0'` and `'/cluster/1.0.0'`, so a version bump in a service would have left membership and the filter reading the old id with no error. Added `buildRepoProtocol` and `buildClusterProtocol` in `storage-protocols.ts` and routed all four sites (`repo/service.ts`, `repo/client.ts`, `cluster/service.ts`, `cluster/client.ts`) and `storageServingProtocols` through them.
- **Docs (fixed inline).** `packages/db-p2p/docs/repo.md` §Peer classification now says a stream does not make a peer `serves`. `docs/internals.md` §Network Membership Predicate gains one sentence on upgrade carry-over: a client already remembered as serving (persisted `rememberedServing`) stays so until it reconnects and identify replaces its list, or FRET declares it dead. Every other file the change touches was re-read; no stale "by opening a stream" claim remains (grepped).
- **Foreign-node fallback (tripwire).** A `Libp2pKeyPeerNetwork` built over a host-supplied node in `CollectionFactory.resolveKeyNetwork` has no filter. Harmless while such a node registers neither storage protocol (only inbound merges are false, and nobody sends it a storage request); parked as a `NOTE:` at that construction site in `packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts` naming the remedy (install the filter in `registerLibp2pNode`).
- **Per-drop read cost (tripwire, already parked by implementer).** `NOTE:` in `filterStorageClaimMerges`; unmeasured on a phone, left as is.
- **Missing-record fallback branch.** Verified by reading only, as the implementer said; the spec cannot reach it because identify writes a record first. Agreed it is not worth a unit test (it would mock the repository's own wrapper target).
- **Dialer-side merge dropped / identify-failure rescue lost.** Accepted per plan and documented at `membershipOf` and in internals; no change.
- **Tests.** The new spec is a genuine reproduction at the libp2p layer and stays. The edit to `libp2p-merges-protocol-per-stream.spec.ts` is header/import only and correct. No tests added or cut: the DRY change is wiring a type and build already cover.
- **Type safety / error handling / resource cleanup.** No `any`; the only caught error is rethrown unless it is `NotFoundError`; the wrapper holds no timer or listener, so nothing to tear down.
- **Mixed versions.** Documented, not solvable locally; no ticket (it is a deployment matter the doc's embedder advice covers).
