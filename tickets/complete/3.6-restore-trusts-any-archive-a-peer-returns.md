# Complete: `ensureRevision` vets the archive before writing it

## What shipped

`BlockStorage.ensureRevision` used to check exactly one thing about the archive a peer handed back —
that it was not `undefined` — and then write it. It now vets it first, and a refused archive is
indistinguishable to the caller from an absent one (the same
`Block <id> revision <n> not found during restore attempt.` throw), so
`StorageRepo.readCommitBase`'s deliberately-unnarrowed catch keeps behaving as before. The specific
refusal reason is logged, not thrown.

The rules, all enforced in `vetRestoredArchive` / `noDivergentRewrite` before a byte is written:

| Rule | Refuses |
|---|---|
| `archive.blockId === this.blockId` | an answer about a different block |
| every revision key is an integer >= 1 **in its one canonical spelling** | a key that coerces to `NaN`, and a key with a second spelling that would file two entries under one revision |
| entry's own `action.rev`, when present, equals the key it is filed under | the mislabel, in miniature |
| entry carries an `action.actionId` | a hollow entry |
| **lowest** revision <= the pin | an archive entirely above the requested revision |
| `range[0] === lowest`, `range[1]` a finite integer `> highest` | a declared range contradicting the revisions carried; open-ended refused outright |
| nothing already held is overwritten with different content | a peer rewriting this node's history (all-or-nothing: one conflict rejects the whole archive) |

Recorded coverage is `[lowest, pin + 1)` — never the archive's declared range.

The admission rule is **lowest <= pin**, not "carries the pin", because `ActionContext.rev` is a
collection-wide revision: the honest answer to a pin at 9 for a block last changed at rev 2 *is*
rev 2, and demanding the pin's exact number would turn working historical reads into hard failures.
Extending recorded coverage *up* to the pin is the one inference the guard makes and cannot verify —
without it `inRanges(pin)` stays false and every later read re-runs the whole restore, never
converging. Two accepted tradeoffs are recorded as `NOTE:` at the code sites: a lying peer's answer
is sticky across the span it was asked about, and the overwrite guard is first-writer-wins, so a
poisoned revision becomes unreadable rather than wrong. Both name the same revisit condition — a
restore that can actually *verify* an archive.

`packages/db-core/src/index.ts` gained one line exporting `canonicalJson` (the overwrite guard
compares held against incoming content by it; `canonical-json.ts`'s own doc says a second copy of
that encoding is "a correctness hazard, not a style nit", and it was simply never on the barrel).

## Review findings

Read the implement diff (`273f962e`) before the handoff summary, then the whole of
`block-storage.ts`, `block-archive.ts`, `struct.ts`, `helpers.ts`, `storage-repo.ts`'s latch and
commit paths, `cluster-repo.ts`'s duplicate canonicalization, and the `docs/internals.md` sections
covering the repair wires. The three questions the handoff raised for review are all answered below.

### Fixed in this pass (minor)

- **Coverage was `[lowest, max(highest + 1, pin + 1))`, letting a peer set the width of its own
  credibility.** Revisions *above* the pin are legitimately accepted (an honest peer serves a
  contiguous span — the pre-existing `ck-staleread` test depends on it), but recording coverage up to
  the archive's highest revision meant a peer could pad an archive with fabricated high revisions and
  buy a silent no-re-ask window over the whole padded span: reads inside it would be answered from
  the peer's floor content without ever consulting anyone else. That also contradicted the code's own
  accepted-tradeoff `NOTE:`, which bounds the stickiness to "the whole span it was asked about".
  Coverage is now `[lowest, pin + 1)` — the entries above the pin are still written, just not
  claimed. Cost: one redundant fetch the first time a revision above the pin is read, which is
  idempotent and converges. This is a tightening rather than a bug fix, and the reasoning (including
  the cost) is written at the site so it can be reversed on a maintainer's judgement. **This answers
  review focus 1**: the admission rule stays `lowest <= pin`; it was the coverage claim, not the
  admission, that was over-broad. New test: *revisions volunteered ABOVE the pin are written but do
  not widen the recorded coverage*. One existing expectation changed accordingly (`[[3, 6], [10]]` to
  `[[3, 4], [5, 6], [10]]`), with the reason in the test.
- **A revision key with a second spelling filed two entries under one revision.** The vet accepted
  any key passing `Number.isInteger`, so `{"4": ..., "04": ...}` produced two vetted entries for
  revision 4; `saveRestored` re-derives the number with its own `Number(key)` and keeps whichever
  `Object.entries` yields last — a choice neither check made. The key must now equal
  `String(Number(key))`. New test: *refuses an archive that files two entries under one revision via
  a second spelling of the key*.
- **`docs/internals.md` documented only the producer end of this guarantee.** The "a peer asked for
  revision N serves revision N labelled N" bullet described honest *serving* and still said the
  receiving side "stores the archive's bytes under the archive's action id" with no mention of a
  gate. Added two bullets: the receiver's vetting rules, and the coverage rule with both accepted
  tradeoffs.

### Filed (major)

- **`tickets/backlog/debt-block-writes-use-three-different-per-block-locks.md`** — the new guard is
  not atomic. `ensureRevision` holds `BlockStorage.ensureRevision:<id>`, `saveForwardRevision` holds
  `BlockStorage.saveReplica:<id>`, and `StorageRepo.commit`/`saveReplicatedBlock` hold
  `StorageRepo.commit:<id>`. Different names are different locks, so a commit or replica push can
  land revision N between `noDivergentRewrite`'s read and `saveRestored`'s write, and the restore
  then writes N under a different action anyway — exactly the overwrite this ticket exists to
  prevent. The same root cause already allows a lost metadata update between `ensureRevision` and
  `saveForwardRevision`, which predates this work. Filed at the invariant ("a block's revision
  records and metadata are only ever written while holding one named lock for that block") rather
  than as a point fix, because the obvious repair deadlocks: `readCommitBase` reaches
  `ensureRevision` from *inside* the commit critical section (`storage-repo.ts:1036` then `:1219`),
  so `ensureRevision` cannot simply take the commit lock. `repro: static`, with the
  instrumented-storage test that would confirm it named in the ticket.

### Recorded as tripwires, not tickets

- **No test drives a refusal end to end through `RestorationCoordinator`** (the handoff flagged
  this). It is not a defect today: `singleRevisionArchive` is the *only* producer of an archive that
  crosses the restore wire (`grep -rn "range: \[" packages/db-p2p/src packages/db-core/src` returns
  two hits, the other being `saveForwardRevision`'s internal archive which never meets the vet), and
  its `[rev, rev + 1]` around a single revision satisfies all three range rules trivially. It becomes
  a real gap only if a second producer appears. `NOTE:` added on `singleRevisionArchive` in
  `storage/block-archive.ts` stating that its `range` is a compatibility contract with
  `vetRestoredArchive` and what makes it stop being trivially true.
- **First-writer-wins is permanent.** A consequence of the all-or-nothing overwrite guard the handoff
  did not spell out: a lying peer that answers a gap *first* makes every honest archive restating
  that revision refuse forever — the revision becomes unreadable rather than wrong. That is the
  deliberate direction (the guard cannot tell which copy is the lie), and repair is an operator
  action. Recorded as an accepted-tradeoff `NOTE:` on `noDivergentRewrite` with the same revisit
  condition.

### Checked and found sound (no action)

- **Review focus 2, the pin-extended coverage.** Kept. The alternative the handoff rejected — having
  the wire state the claim explicitly — makes it explicit without making it verifiable and breaks
  repair against older builds; that reasoning holds. The clamp above bounds it to what was asked.
- **Review focus 3, refusing the whole archive on one conflicting entry.** Kept. Landing the
  non-conflicting entries would leave the coverage claim spanning revisions the applied subset may
  not support, and a peer that contradicts held content is not more trustworthy about the rest. The
  three conflict keys (`getRevision`, `getTransaction`, `getMaterializedBlock`) mirror
  `saveRestored`'s three writes exactly, and identical content is correctly not a conflict — which
  the pin-extended coverage relies on across overlapping restores.
- **`saveRestored`'s trust contract is documented, not enforced** (the handoff's highest-value
  pushback invitation). Left as is. It is genuinely conditional — "only matters if a third caller
  appears" — and the doc block on `saveRestored` already states exactly that, at the site, which is
  where a tripwire belongs. Making it structural for two call sites would be churn.
- **`RestorationCoordinator` verifies nothing.** Deliberate layering, not a gap: `BlockStorage` is
  the layer that knows what it holds and what it asked for. The consequence (a peer's lie costs a
  round trip before it is caught) is stated in `docs/internals.md`.
- **The archive's own `proof` field.** Not vetted, and correctly so — `saveRestored` ignores it
  entirely and persists a proof only through its separate `verified` parameter, which no
  restore-wire caller supplies.
- **`archive.pending`.** Only meaningful for an open-ended range, which the vet refuses and
  `ensureRevision` never requests. Unchanged and unreachable from this path.
- **`Math.min`/`Math.max` spread hazard.** Correctly avoided — min/max are folded in the parse loop,
  matching what `maxArchiveRevision` documents about `RangeError` past ~125k arguments.
- **`ClusterMember`'s private `canonicalJson` copy** (`cluster-repo.ts:735`). Still duplicated, and
  the handoff was right to leave it: it is pre-existing, not introduced here, and it touches cluster
  agreement hashes. Its own `NOTE:` already says "if a third caller appears, promote to a single
  exported helper" — that condition has not tripped (the barrel export added here is a new *db-core*
  consumer, not a third copy). Not re-filed;
  `tickets/backlog/debt-cluster-member-race-logic-has-no-home.md` already claims that file if someone
  wants to fold it in.
- **Source hygiene.** `block-storage.ts` is 769 lines (`wc -l`), up from 742. One cohesive class, the
  two new functions are short and single-purpose, and the comment density matches the file. Not
  flagged.

### Empty categories

- **No findings on error handling or resource cleanup.** Every `Latches.acquire` in the touched paths
  is paired with a `finally { release() }`, the vet adds no acquisitions of its own, and the refusal
  path returns rather than throwing from inside the latch.
- **No findings on type safety.** `RestoredRevision` narrows the archive entry to what has actually
  been established; the one `as unknown as` in the new tests is deliberate (constructing malformed
