## What was wrong

The vtab's write path and the offline drain share one `Collection` per tree, and reads are not latched. Each drained entry folds its commit into the read cache and replays what is still staged, which re-inserts staged nodes under fresh random block ids. An insert's point reads and unique probe ran during those steps, so a descent could read a branch from before the change and a child from after it: `Missing block`, `Path is invalid due to mutation of the tree`, or a present key silently reported absent.

## What changed

- **One signal for "what this tree reads may have changed."** `CollectionInitOptions.onViewChanged` is called through `Collection.viewChanged`, synchronously and in the same await-free step as each change: replay reset, the live tracker's atomic commit in `stageInto`, both reset arms of `restorePending`, the verbatim arm of `unstage`, `forgetAndAdopt`, `foldOwnCommit`, and `applyCommittedToCache` (whose callers reset the tracker in the same step). `Tree` wires it to `invalidatePaths`; the old bump at the end of the `replace` handler is gone.
- **Point reads, range setup and whole-range reads retry.** `BTree.readUnchanged` repeats a read until it finishes with `_version` unmoved; a throw while the version moved is retried as that change's symptom. `get`, `range`'s bounds, and the new `entriesIn(range)` (on `TreeReadView` and `Tree`) go through it. Scans that have already yielded keep the throw-on-change contract.
- **Plugin.** `readRowAt` uses `get`; `IndexManager.findByIndexIn` and `findByIndex` return `Promise<PrimaryKey[]>` via `entriesIn`, and `probeUniqueConstraint` reads the hit list before any row.
- **Docs.** `packages/db-core/docs/btree.md` §Reads under a concurrent change, and a paragraph in `docs/internals.md` §The offline queue.
- **Tests.** `packages/db-core/test/tree-point-read-under-mutation.spec.ts` (three cases: torn point read, torn range setup, `entriesIn` across a change after a yield) and `packages/quereus-plugin-optimystic/test/offline-insert-during-drain.spec.ts` (300 offline autocommit inserts into a unique-column, indexed table, over the db-core `TestTransactor`; it failed at insert 65 before the fix).

## Review findings

**Read first:** the implement diff, then the handoff. Checked by reading and by running: lint, `yarn lint:docs`, `npx tsc --noEmit -p .` in db-core, and the db-core (2025 passing), quereus-plugin-optimystic (1182 passing, 14 pending, smoke ok) and db-p2p (3562 passing, 74 pending) suites, all after the fix below. Not run: `yarn test:integration`, `yarn check:rn`, upgrade-check (no change there touches persisted formats).

- **Signal coverage — checked, complete.** Grepped every tracker reset, `sourceCache.clear` and `transformCache` site in `collection.ts` and `coordinator.ts`. Every live-tracker change either calls `viewChanged` or goes through `replayActions`/`stageInto`. All four coordinator fold sites call `applyCommittedToCache` then `tracker.reset()` with no `await` between them, as its doc comment now requires. `resetTransforms` is the one unsignaled reset, and it carries the implementer's `NOTE:`. Every handler invocation goes through `stageInto`, and only the live tracker's commit signals, which is right because a head commit's tracker is private.
- **Synchronous-step claim in `range` — checked, holds.** After the `do … while` validity check, `for await` calls `next()` on a not-yet-started async generator, which runs `internalAscending`/`internalDescending` up to its first `validatePath` with no await in between.
- **Retries and read dependencies — checked, safe.** A torn descent's leaf can be recorded as a `value` read beside the retried one. That can only over-reject, never miss a conflict. `readRowAt` moving from `find` to `get` drops interior nodes from the conflict set for vtab point lookups and index seeks, which is the existing point-lookup exclusion (correctness.md Theorem 5), so that is a deliberate change.
- **`entriesIn` vs. the ticket's narrower `NOTE:` (the implementer asked for a judgement).** Kept `entriesIn`. The narrower option would have left a probe that still throws for a change landing after a one-entry hit was yielded, which the implementer confirmed happens. `entriesIn` reuses the same retry primitive and adds one method to the read interface. That is the right size.
- **Wider invalidation of open scans — checked by experiment, no regression.** More changes now move the version: a refresh with nothing staged, commit folds, and the last drain step. So I ran a throwaway spec (deleted afterwards) that issued `select count(*)`, an index seek and a primary-key point lookup every ten offline inserts while the drain ran. 90 reads, 0 errors: `executeTableScan`'s resume-from-last-key retry absorbs it. Not filed.
- **Test-double defect — fixed inline.** The handoff flagged it. `TestTransactor`'s `latestMaterializedAt` answered a read pinned at or after a block's deletion with the content from before the delete, because it skipped revisions with no materialized block. Real storage answers absent there. The double now stops at the highest committed revision at or below the pin and returns `undefined` when that revision deleted the block (`packages/db-core/src/testing/test-transactor.ts`). No suite depended on the old behaviour. No new test: the change is a correction in a test double, and the implementer's merge-based variant that this hid was not kept.
- **Tests — kept as they are.** The three db-core cases each pin a separate retry path: point read, range setup, whole-range read. The plugin spec reproduces the reported failure. At about 5.5 s it costs something, but the count of 300 is justified (the failure appeared only at insert 65). Nothing restates the implementation or verifies a mock.
- **Docs — checked.** `packages/db-core/docs/btree.md` and `docs/internals.md` match the code, and the citations resolve. `docs/offline-sync.md` §Reads in offline mode is about refresh absorption, not torn descents, so it needed no change.
- **Unsignaled cache admissions and replay intermediate states.** The handoff names both, and both are already recorded in the btree doc's "only changes that move `_version`" limit. Not filed: neither has been seen to cause a failure, and both need floors or a pure read landing mid-replay.
- **Unbounded retry.** Already carries a `NOTE:` tripwire at `readUnchanged`. Nothing added.
- **Hygiene.** `IndexManager.findByIndex` has no caller (pre-existing, and its doc comment says so). Left as is: removing a public method is out of scope. No size or comment-narration problems in the diff.
- **Major findings.** None. No tickets filed.
