# Journal batch backend — complete

Third of five tickets from `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). Landed in `ticket(implement): journal-batch-backend`; reviewed here. The two tickets that consume it, `implement/4.3-browser-storage-syncs-by-the-window` and `implement/4.4-react-native-storage-commits-groups-through-the-journal`, are the first real `JournalStore` implementations; nothing in production composes the backend yet.

## What landed

- **`JournalBatchBackend implements BatchBackend`** in `packages/db-p2p/src/storage/journal-batch-backend.ts`, over a `JournalStore` (the engine's reads plus `appendJournal`, `applyJournal`, `readJournal`). A relaxed group is appended as one numbered, unsynced journal record and held with its deadline; a strict group, or one that finds a deadline passed, or any group over a store below `'power-loss'`, is applied at once in one synced write together with everything held. Recovery at open is the pure `planRecovery`: records at or below the applied-through mark are deleted, the consecutive run after it is applied, everything after the first gap is discarded, all in at most one `applyJournal`. Open, commits, syncs, the timer's apply and close run on one serial queue; reads await the open and go to the store. Any store write rejecting latches the backend with `StoreFailedError`.
- **The record codec** in `packages/db-p2p/src/storage/journal-record-codec.ts` for stores that keep bytes: version byte, 8-byte big-endian sequence (two 32-bit halves, no BigInt), entry count, per entry a length-prefixed JSON `StoreKey`, a put-or-delete flag and a length-prefixed value. Decode is strict and throws `JournalRecordDecodeError`, which a store treats as a missing record.
- **Test doubles**: `MemoryJournalStore` (exported from `./testing`) with call recorders, failure hooks and `powerLoss`; the applied-rows map `MemoryBatchBackend` and it share moved into `MemoryStoreRows`.
- **Exports** from both package entries; a `journal` row in the db-p2p namespace table of `docs/debugging.md`; Invariant 6 of `packages/db-p2p/docs/storage.md` gained a driver-table row and *The journal backend* paragraph.

The design as implemented, and the decisions the implementer recorded, are in the implement commit's ticket body and in the class documentation; the storage doc paragraph is the maintained statement.

## Review findings

Read the implement diff first, then the handoff; ran the composition by hand through the spec harness and read every file the change touches plus the ones it should have (the flush contract in `raw-store-driver.ts`, `SyncDeadlines`, `WriteGroup`, `WriteGroupDriver`, the file log as the sibling `SyncDeadlines` owner, both sibling tickets on the board, `docs/correctness.md`'s backend caveat).

**Checked and found correct** (no change):

- **The flush contract's rules 3 and 5** against each path: relaxed append then deferred apply; strict apply carrying the cover plus its own record; backpressure when a held deadline has passed; the cannot-sync store applying every group at once with nothing journaled; recovery's three arms. Every apply carries all the bytes it applies and runs after the previous one resolved, so a later apply cannot survive without an earlier one. A strict group's number is in `apply` with no record present, and the interface documents that a store deletes nothing for it. `nextSeq` advances before the write and a failed write latches, so a number is never reused in-process; recovery decides from the journal on the next open. A discarded number is reused only after the apply that deleted it.
- **The five `SyncDeadlines` rules** the handoff asked to be read against `commit`: the deadline is taken at the call before the queue; `mustSyncNow` is checked before `defer`; the timer's step passes the moment it fired to `take`; the subject is the store's identity; nothing can latch between the append resolving and `defer` because only this queue's own steps latch and the append's failure throws first. The handoff's argument holds.
- **Durable settlement order.** Covered records are settled by `cover.settle()` before a strict commit returns its already-settled `durable`, so `WriteGroup` sees batches durable in commit order, as `CommittedBatch` requires.
- **Reads beside an apply.** Reads go to the store outside the queue; the store's apply is atomic, so a read sees before or after, which `BatchBackend`'s read contract permits.
- **Close.** Applies held records only on an opened, healthy backend, closes the store in a `finally`, refuses later commits; a second close is harmless for every store on the board (neither sibling store has a `close`).
- **Resource cleanup.** The deadline timer is disarmed by every `take`, which every apply, the latch and close go through; the default timer is unref'd.
- **Codec.** The `DataView` is built with the input's byte offset, so a subarray decodes; values are copied out, never aliased; a put with an empty value is distinct from a delete by the flag; a key that is not a `StoreKey` or JSON throws the named error rather than `SyntaxError`.
- **Docs.** The db-p2p namespace table has 58 rows, as the count line says, and the `journal` row names the four lines the code emits. The storage doc paragraph matches the code. `docs/correctness.md`'s backend caveat still correctly lists only the file and NativeScript backends as `'power-loss'`, since the journal backend is not yet wired in production; the sibling tickets update it.

**Minor, fixed in this pass:**

- **A `StoreFailedError` could wrap another.** The rule "the cause is the fault underneath, never a wrapper naming a wrapper" was enforced by a ternary copied into three latch sites (`WriteGroup.latch`, `JournalBatchBackend.latch`, `SqliteBatchBackend.latch` in `packages/db-p2p-storage-ns/src/sqlite-storage.ts`), while `SyncDeadlines.fail` and the file log built one without it. Moved into the `StoreFailedError` constructor, which now unwraps a `StoreFailedError` cause, and the three sites simplified. Every consumer of a latch's recorded cause builds a `StoreFailedError` from it, so the state is unrepresentable at the type rather than by discipline.
- **Two contracts left unverified** got one test each in `packages/db-p2p/test/journal-batch-backend.spec.ts`: an overdue held deadline makes the next relaxed commit apply everything held and itself in one apply with no append of its own (backpressure at this layer, which `sync-deadlines.spec.ts` pins only for the helper); and recovery deletes a record at or below the mark without applying it (the stale arm the handoff said was by inspection only). The harness clock now moves on request.

**Tripwires recorded at the site:**

- `NOTE:` at the `syncWithinMs` check in `JournalBatchBackend.commit`: the same three-line validation lives in `FileWriteLog.commit` and `SqliteBatchBackend.commit`; a fourth deferring sink should move it into `SyncDeadlines.deadlineFor` rather than copy it again.

**Conditional, noted here only:**

- `close()` applying held records is exercised only with nothing held, because `WriteGroupDriver.close` flushes strictly first. It is a defensive arm for a bare backend, which nothing composes today; a direct test would restate the implementation. No action.
- Two backends over one store in one process would take the same next sequence number from the mark and collide. Invariant 5 forbids the shape; the browser ticket already carries the sentence for its identity `NOTE:`. Nothing here detects it, by design.

**Tests cut:** none. Each of the implementer's cases pins a distinct named behaviour (the two commit paths, recovery with and without a gap, the cannot-sync store, the failure latch, the codec's round-trip and refusals) and none verifies a mock.

**Tickets filed:** none. No finding met the filing bar; nothing serves a current-release anchor beyond what the two sibling implement tickets already carry.
