# Summary

A commit acknowledged below `full` replication now records, in a durable per-node ledger, which cohort members are still missing each block — before the writer is answered. `IUnderReplicationLedger` / `KvUnderReplicationLedger` (JSON under `under-replicated/<blockId>` in an `IKVStore`), wired through `NodeOptions.kvStore` (memory fallback with a `node-wiring` `WARN:` debug line), recorded from every success exit of `CoordinatorRepo.commit` via `acknowledgeCommit` → `noteReplicationShortfall`. `full` settles older entries; `majority` names the unconfirmed members; `local`/`unrouted` record an empty ("unknown") missing set; nothing is recorded when this node holds no bytes, for torn blocks, or for refused commits; a ledger fault is logged and never fails the commit. The reference peer passes `FileKVStore` for `--storage file`. Nothing drains the ledger yet — that is `under-replication-drain-and-full-replication-event`.

# Review findings

**Read first:** the implement diff (`5f2eb9ab`) in full — ledger interface and implementation, coordinator changes, node wiring, reference-peer CLI, `FileKVStore` note, exports, all four doc files, and the three specs.

**Correctness of the ledger.** Checked the per-block queue (`serialized`) for ordering and cleanup, the lazy index against concurrent loads and writes (every mutation that changes presence awaits the index before writing, so the settle fast-path cannot miss an entry this instance wrote; `satisfy`/`noteAttempt` never add presence), eviction under concurrency (victim re-checked under its own queue, loop re-measures), malformed-entry handling, and index retry after a failed load. No defects found. Minor observation, no action: a malformed stored entry is not in the index so it is never evicted, only overwritten by the next record for that block — harmless.

**Correctness of the recording rules.** Checked each `commit` exit against the `localHolds` argument, that `tolerateLocalCommitDivergence` becoming async is awaited at both call sites, that refusals return before `acknowledgeCommit`, that `CommitRequest.rev` is the one action revision shared by every block (so per-block revision comparison is sound), and that `majority` with an absent `unconfirmed` degrades to "unknown" rather than "nobody". No defects found.

**Cost on the solo commit path (the reviewer note's request) — measured.**
- Store operations per ledger call are now pinned by a new describe block, "store operations per call", in `packages/db-p2p/test/kv-under-replication-ledger.spec.ts`: a commit of k blocks at `local`/`unrouted`/`majority` costs k key-value `get` + k key-value `set`; a `full` commit on a block with no entry costs 0; recording past the cap adds 1 `delete`; the first mutation after start loads the index at 1 `list` + 1 `get` per stored entry.
- **Block-storage (`IRawStorage`) operations are unchanged: zero added.** The ledger writes only to `IKVStore`, never to raw storage.
- The in-repo cold-apply gates (`packages/quereus-plugin-optimystic/test/cold-apply-cost.spec.ts`) count raw-storage driver calls, commits, transactor calls and cohort lookups, over `createMesh`, which wires no ledger at all — so they cannot move by construction. Ran the whole plugin suite after this commit: 950 passing, 13 pending, gates green. A before/after run was not done because the harness has no ledger in either case.
- **sereus** (`packages/cadre-core/test/control-start-storage-op-budget.spec.ts`) counts operations through a `CountingRawStorage` wrapped around `IRawStorage` only, and sereus passes no `kvStore` (grep of `cadre-core/src` and `cadre-host/src` finds none), so its nodes use the in-memory fallback. Its 45-operation budget does not see ledger writes and should not move. If sereus later supplies a persistent `kvStore` (as the fallback warning nudges it to), the ledger's 2 key-value operations per block per solo commit will reach its disk but still not its raw-storage counter — its budget would then under-report device cost, which is theirs to decide whether to count.

**Major finding — filed.** On a genuinely solo node every block written gets an entry, the drain ticket deliberately leaves those in place, and the index load (one read per entry) happens on the first commit after a restart. With a persistent store and slow storage that first commit could stall for a long time. Not reachable by sereus today (memory fallback); reachable by the reference peer with `--storage file`. Filed as `backlog/debt-solo-node-ledger-is-reread-whole-on-first-commit-after-restart` (rung check: the directions include a representation change — a persisted compact index — rather than a point fix). Parked a `NOTE:` on `KvUnderReplicationLedger.index()` pointing at it, and appended a short pointer to `implement/6.43-under-replication-drain-and-full-replication-event` since its start pass is a natural place to warm the index.
