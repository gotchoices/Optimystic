# A node stores blob pieces — complete

## What was built

`createLibp2pNodeBase` builds a `LocalBlobService` for every node, serving or client, over `NodeOptions.pieceStorage` (instance or factory; `MemoryPieceStore` with a `node-wiring` warning when absent) and the node's key-value store, with `NodeOptions.blobs.digest` passed through as given. It is attached as `node.blobs` on `OptimysticNodeAttachmentsBase` through the typed `shared` literal, started right after `Object.assign(node, attachments)`, and its stop wrapper (cancel the scheduled sweep, await a running one) is installed immediately after, so the startup rollback stops it too. On a serving node the Arachnode `StorageMonitor` gets the piece store, so piece bytes count once. Docs (blobs.md, internals.md §Client nodes, debugging.md `node-wiring`, db-p2p storage.md §7, db-p2p-storage-fs README) describe the option, the fallback, and that the host closes the store after `stop()`.

## Review findings

Read the diff of `ticket(implement): feat-a-node-stores-blob-pieces` first, then `LocalBlobService`, `StorageMonitor`, `FilePieceStore`, the startup/rollback flow in `createLibp2pNodeBase`, and every caller of `createLibp2pNode` (reference peer, Quereus plugin).

- **Correctness / lifecycle** — checked: the service is constructed before libp2p but started only once attached; a failure before `Object.assign` never started it, and every later failure unwinds through the wrapper installed right after `start()`. `stop()` awaits a running sweep, so a stopped node leaves no sweep against the host's stores. Stop order (after the cohort-topic wrappers, before the serving role and libp2p) is as documented. No defect found.
- **Type safety** — `blobs` is required on the base attachment shape and written through the typed literal, so an omission is a compile error. `PieceStoreProvider` mirrors `KVStoreProvider`. No issue.
- **Storage accounting** — `StorageMonitor` decides once at construction via `blockStoreCountsPieces`; `FilePieceStore` reports the same store identity as `FileRawStorage` over one base path, so a file host is not double-counted. No issue.
- **Interaction found and fixed (minor):** the reference peer handed the node a durable `FileKVStore` but no piece store, which is exactly the mismatch the new warning describes (blob records surviving a restart whose pieces did not), and its memory mode passed `MemoryKVStore` explicitly to silence the kvStore warning yet now tripped the pieceStorage one. `openStores` in `packages/reference-peer/src/cli.ts` now builds a `FilePieceStore` over the same storage path (or a `MemoryPieceStore` in memory mode), passes it as `pieceStorage`, and closes it first on shutdown. Reference-peer build and tests (6 passing) run.
- **Quereus plugin's own node builder** — passes no `storage` or `kvStore` either; it already runs all in memory and warns on `kvStore`, so the extra `pieceStorage` warning is consistent. Left unchanged; host wiring for persistent plugin nodes is outside this ticket.
- **Resource cleanup** — a factory `kvStore` is not closed if the `pieceStorage` factory throws during construction. Same pre-existing shape as the `storage` factory resolved after `kvStore`, and only on a construction failure caused by the host's own factory; not filed and not a tripwire beyond this line, since no anchor in the current release covers construction-failure cleanup of host-supplied factories.
- **Start-up log noise** — every node without a piece store now logs one more `node-wiring` warning (test nodes included). Plan's choice, mirroring `kvStore`; accepted.
- **Tests** — none added, none cut. The wiring is enforced by the type checker and the service's behaviour by `packages/db-p2p/test/local-blob-service.spec.ts`; a node-level test would only restate the wiring.
- **Docs** — every file the change touches, plus the reference-peer README (no store wording to update), read and current. `yarn lint:docs`, `yarn lint:deps` pass; eslint on `cli.ts` clean.
