# Refresh always knows its own in-flight action

## What shipped

`NetworkTransactor.commit` stores a collection's header and log tail first, then sweeps the rest of
the blocks. If a later sweep block loses a race the whole write is reported as failed — but the
header and tail are already permanently stored, so the write's own record is already in the log
when the writer is told "you failed". That is a **torn commit**, and the retry has to recognise
that record as its own and drop the matching queued work instead of writing it again.

`Collection.sync` already did. `TransactionCoordinator.commit` did not: its between-attempt refresh
called the same `Collection.update()` a plain reader calls, so it was indistinguishable from a
reader refresh even while the coordinator held the very identifier it was retrying. On HEAD before
this ticket that produced two log entries for one action, at two revisions, plus a second commit
that actually landed on storage.

The knowledge now lives on the collection instead of travelling as an argument:

- `Collection` has a private `inFlightActionId` and a public
  `beginInFlightAction(actionId): () => void` that sets it and returns an id-guarded disposer.
- `updateInternal()` takes no parameter — it reads the field. `update()` and `updateAndSync()` are
  therefore correct by construction rather than by having nothing to pass, and a fourth write path
  added later cannot inherit the old defect by omission.
- `syncInternal` is a thin bracket (mint id → `beginInFlightAction` → `finally` disposer) around a
  new private `syncAttempts` holding the unchanged retry loop.
- `TransactionCoordinator.commitOnce` marks each participant with `transaction.id` immediately
  after acquiring its latch, pushing the disposer into an array `commit` owns; `commit` wraps its
  whole `for(;;)` retry loop in `try/finally` and runs every disposer on exit.

### The lifetime correction

The originating `fix/` ticket said the clear belongs in the same `finally` that releases the latch.
That is wrong and the implementation does not do it. The coordinator's between-attempt refresh runs
*outside* the latched span by design (`Latches` is non-reentrant), so a latch-scoped clear would
already have run by the time the only reader of the mark executes. The correct lifetime is the
attempt cycle, which is what shipped.

### Verified (the implementer's claims, re-checked independently)

- **The three new coordinator cases have teeth.** Re-ran the disable-half experiments rather than
  taking the handoff table on trust. Removing the mark in `commitOnce` fails cases 1 and 2 with the
  action logged twice (`["local","local"]`, `["torn","torn"]`); removing the clear in `commit`'s
  `finally` fails case 3 (the pending action is silently consumed). Both edits reverted.
- **No exit from `commit` skips the `finally`.** It wraps the entire `for(;;)`; every `throw`,
  including the re-throws inside the `catch`, is inside the `try`. Nothing but a process death
  skips it.
- **The mark matches what actually lands.** `applyActionsToCollection` uses
  `const actionId = transaction.id` (`coordinator.ts:810`), the same value `commitOnce` marks, so
  the durable entry's `actionId` is exactly what the refresh compares against.
- **`execute` is correctly left unmarked.** Read it end to end: no retry loop, no inter-attempt
  refresh, so it has no cycle to mark. The handoff's reading holds.
- **Marking is ordered safely.** The mark is pushed only after `acquireLatch()` returns, only for
  participants, and after the early `collectionData.length === 0` / expired-transaction returns —
  so a throw before that point leaves nothing behind.
- **`updateAndSync` keeps reader semantics.** Its `updateInternal()` runs *before* `syncInternal`
  sets the mark, so that refresh cannot consume.
- **No other write path needs a mark.** Traced every `collection.update()` caller across all
  packages (db-core, db-p2p, demo, quereus-plugin-optimystic): all are reader refreshes.
  `session.ts:168` is the only `coordinator.commit` caller and mints a fresh transaction per call,
  so no higher-level loop re-drives one identifier.

### Found and fixed in this pass (minor)

- **`docs/internals.md` was describing the pre-fix design.** Its torn-action bullet documented
  `updateInternal(inFlightActionId)` as a threaded parameter and ended with a paragraph headed
  "**Not yet true of the coordinator path**" stating that a torn action committed through the
  coordinator still replays into a duplicate entry — the exact defect this ticket closed. Rewrote
  it as two bullets: the consume behaviour, and a new "The collection, not the caller, holds the
  in-flight id" bullet covering the field, the disposer, both write paths, why the coordinator's
  clear cannot be latch-scoped, and the two regression specs. This was the only stale doc:
  `docs/repository.md:148` covers the storage-side pend carve-out and is unaffected, and
  `docs/internals.md:130` is a claim about the *latched span*, which is still exactly true.
- **`commitOnce`'s `inFlightDisposers` was optional.** The handoff explicitly asked for a reviewer
  opinion. Made it required: the parameter exists to stop an unmarked refresh, and optionality
  leaves the regression one omission away. There is exactly one caller, and a caller that never
  refreshes between attempts can pass a throwaway array — that is now said in the doc.
- **`beginInFlightAction`'s NOTE over-claimed "not reachable today".** A concurrent *reader*
  refresh in the latch-free inter-attempt window is reachable today: `OptimysticModule` declares
  `concurrencyMode = 'reentrant-reads'` and, inside a transaction, every scan on a table shares one
  `Collection` instance and serializes only on the latch — which the mark deliberately outlives.
  Analysed it: it is **benign**. Consuming is a property of the (instance, action id) pair and not
  of who calls, `restorePending` has already run under the latch before any foreign refresh can
  start, and the leading slice stays right because `actInternal` appends — so whoever refreshes
  first drops exactly the durable entry's actions and the write's own later refresh finds nothing
  new. Documented that reasoning at the site and narrowed the NOTE to the genuinely hazardous
  case, a concurrent *writer* trampling the mark, which remains unreachable.
- **`consumeOwnEntry`'s own revisit condition had tripped.** Its NOTE said to assert
  `entry.actions.length <= this.pending.length` "if a path is ever added that stages actions
  outside the collection latch" — and this ticket added exactly that (the coordinator's mark spans
  a latch-free window where `act()` can grow `pending`). Climbing *Architecture first*, this is a
  boundary invariant (rung 3): the slice fails **silently** when the correspondence breaks, dropping
  actions that were never committed. Added the guard, which turns that into a throw, and rewrote
  the comment to state the invariant and why the tail survives. Two cases added to
  `collection-own-action-replay.spec.ts` — "consuming keeps actions staged AFTER the entry was
  written" (the leading-slice claim the new documentation leans on, previously uncovered: every
  existing case had `pending` exactly equal to the entry) and "refuses to consume an entry longer
  than the pending list" (the guard). Both proved to have teeth by sabotage: returning `[]` from
  `consumeOwnEntry` fails the first, disabling the guard fails the second.

### Found and deliberately not acted on

- **Comment-to-code ratio of the implement diff is 111:53** (measured over added non-blank lines in
  the two source files). High in the abstract, but it is the established style throughout both
  files and the prose is load-bearing — the torn-commit rationale and the lifetime argument are the
  parts a future reader most needs. Churning them risked losing reasoning for no behavioural gain.
  Checked specifically for redundancy: `beginInFlightAction` already defers the "why" to the field
  doc rather than restating it, so the obvious DRY target is not actually duplicated.
- **`inFlightDisposers` grows by one closure per participant per attempt** — up to
  `maxAttempts × participants` identical, idempotent closures for one transaction. Bounded and
  trivial; deduping would add bookkeeping for no measurable gain.
- **Only two of the `finally`'s five exits are driven by a test** (return and hard error; abort,
  deadline, `CoordinatorPartialCommitError`, and stale-loss exhaustion are not). Declining
  explicitly rather than silently: all five leave through the same `finally`, whose execution is a
  language guarantee, so a test per exit would re-prove `try/finally` rather than anything about
  this change.
- **The latch-free clear has no concurrency test.** Any test that drives a foreign refresh into the
  clearing instant is a race, and a flaky guard is worse than none. Partly retired instead: the
  reader-in-the-window case is now analysed and documented above, and the invariant it rests on has
  the guard plus two deterministic tests.
- **Multi-collection participant identification is by header block id**, so a future case tearing a
  *second* commit on an already-committed collection will need a different key. Accurate as the
  handoff states it, and call-order keying was correctly rejected (`commitPhase` fans out
  concurrently and its order is not contractual). No change needed for the cases that exist.
- **`CommitLandsButReportsStale` moving to `src/testing/` does widen published surface** —
  `./test` is a real package export and `src/testing/index.ts` does `export *`. Accepted: it sits
  on the same shelf as `FlakyCommitTransactor` and `CompetingWriterTransactor`, and the open
  `debt-three-copies-of-the-log-capture-test-helper` ticket shows this repo weighs deduplicating
  test helpers above surface minimalism. Keeping two copies in sync was the worse trade.
- **The `syncInternal` / `syncAttempts` split** is the right call. It is the smaller diff, the
  bracket reads as a bracket, and the alternative re-indents ~90 unchanged lines into a `try`.
- **A torn multi-collection commit whose retry then fails hard leaves a partial landing reported as
  a plain `Error`, not `CoordinatorPartialCommitError`.** Real, but pre-existing and independent of
  this change (before the fix the torn participant duplicated its entry and the same throw
  occurred), and the class is already owned by `backlog/feat-cross-collection-atomic-commit`. Not
  re-filed — the site-claim grep found that ticket.
- **`debt-coordinator-execute-and-multi-collection-latch-span-untested` stays open.** The
  multi-collection case here incidentally drives that path but proves nothing about the latch span,
  which needs its own gated-transactor harness. Correctly out of scope.

### Tripwires

No new ones. The two recorded at implement stand, and one was made more accurate:

- `packages/db-core/src/collection/collection.ts`, at `beginInFlightAction` — the mark outlives the
  latch, so two *writes* overlapping on one instance can trample each other's mark. The NOTE now
  also states that a concurrent *reader* in that window is reachable today and why it is benign, so
  the "not reachable today" claim is scoped to the case it is actually true of. The remedy if a
  second writer is ever allowed on one instance is unchanged: a per-attempt token compared by
  identity, refusing to replace a live mark.
- `packages/db-core/src/transaction/coordinator.ts`, at the `applyActionsToCollection` log append —
  after a torn commit the torn participant drops out of the retry's participant set, so the retry's
  entries carry an `allCollectionIds` list naming only the remaining participants while the torn
  participant's already-durable entry names all of them. Nothing keys off that list for correctness
  today; the NOTE says a cross-collection invalidation cascade must union it across the
  transaction's entries rather than trust any single one.
