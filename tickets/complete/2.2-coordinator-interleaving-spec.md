# Interleaving spec for the commit latch and revision threading — complete

Two new cases park a `TransactionCoordinator` commit mid-flight, release a `Collection.update()`
into the parked instant, and assert the collection cannot be corrupted by it. Case 1 parks between
the durable commit and `recordCommitted`; case 2 parks the pend, lets a rival durably take the
revision, and releases the refresh under the parked pend. No production source was modified by
either the implement or the review stage.

## Review findings

### Verification of the implementer's central claim — done independently, not taken on trust

The handoff claimed both cases fail against the pre-fix mechanism. Rather than re-run their
revert-the-whole-file procedure, this review ran a narrower and stronger mutation: line 272 of
`coordinator.ts` (`latchReleases.push(await collection.acquireLatch())` inside `commitOnce`) was
replaced with a comment, isolating the latch acquisition itself from every other post-fix change.
**Both cases failed**, at the `blocked()` assertions in each. `coordinator.ts` was then restored
from a byte-copy and its MD5 verified identical (`352f502f…`); it does not appear in `git status`.
The spec is non-vacuous and the latch is specifically what it measures.

Stability: the spec ran clean 5/5 consecutive times at ~250-320 ms, so the ten-macrotask drain is
not sitting on a timing edge.

### Fixed in this pass (minor)

- **A failing assertion left the parked commit pending forever.** In both cases `openGate()` came
  *after* `expect(refresh.blocked()).to.be.true`, so a failure of that assertion skipped it: the
  coordinator commit never settled, the collection's latch was never released, and the floating
  `commitPromise` had no handler if it later rejected. Wrapped the drain + assertion in
  `try { … } finally { transactor.openGate() }`. Re-verified under the mutant above: the failure
  now reports in 195 ms with no hang and no leaked pending commit.
- **The unawaited refresh could crash the process instead of failing the case.**
  `releaseRefresh` returned a promise with only a fulfillment handler attached, and the test then
  left it unawaited across ten macrotask turns. A rejection from `Collection.update()` inside that
  window would reach the end of a turn unhandled — fatal in Node, and attributed to whatever test
  happened to be running. Both handlers now attach synchronously and the error is rethrown at
  `settle()`, which the case awaits.
- **Case 2 never checked the revision it fought for.** Case 1 asserted local record and storage
  agree on `(revision, action id)`; case 2 asserted only the log contents. That omission mattered:
  case 2 is the path where the retry loop's blanket `collection.update()` runs *outside* the latch
  between attempts, which is precisely where a revision captured on attempt 1 and recorded after
  attempt 2 would fork. Added the same pair of assertions, plus an explicit `to.be.a('number')`
  guard so the equality cannot pass with both sides `undefined`. Passes.
- **`docs/internals.md` stated the latch-span property with no regression anchor**, while the
  paragraph directly above it cites its anchors by path. Added the citation to the new spec.

### Answered from the handoff's own review checklist

- *Could a degenerate run satisfy `snapshots.length > 1`?* No. The only degenerate shape is the
  parked pend succeeding, which yields exactly one snapshot and fails `> 1`. The rival runs against
  the unwrapped transactor, so it can never contribute a snapshot, and the `['rival', 'local']` log
  assertion pins that the rival really landed.
- *Is `structuredClone` on `Transforms` safe?* Yes. `TestTransactor` already structuredClones blocks
  on every read and commit, so a non-cloneable block would break the transactor long before it
  broke this spec.
- *Do the wrappers park where their doc comments claim?* Confirmed against the current
  `commitOnceLatched` ordering. Neither park sits inside a `TestTransactor` block latch — case 1's
  park is after `inner.commit` has returned and released, case 2's is before `inner.pend`, which
  takes none — so the only thing the refresh can be waiting on is the collection latch. That is what
  makes the `blocked()` assertions mean what they say.

### One inaccuracy in the handoff, for the record

The handoff reported case 1 failing pre-fix at `records exactly the revision it pended at`
(actual 2, expected 1) *and* reported that "the `blocked()` assertions also failed in both cases
pre-fix". Those cannot both be observations of the same run: `blocked()` is asserted first and
aborts the case before the revision assertion is reached. The two results must come from separate
runs with different assertions in play, which the handoff does not say. The underlying mechanism
claim is nonetheless correct — independently confirmed above — and no code change follows from this.

### Filed (major)

- `backlog/debt-coordinator-execute-and-multi-collection-latch-span-untested` — one ticket, three
  arms, all resolving at the same two blocks of `coordinator.ts`. `TransactionCoordinator.execute`
  takes the same latches over the same span but is untested, and it carries ordering constraints
  the covered path does not (it must latch *after* `applyActions`, because `collection.act` takes
  the same non-reentrant latch; it must de-duplicate first for the same reason). No test uses more
  than one collection, so the sorted acquisition that makes overlapping concurrent commits
  deadlock-free is decoration as far as the suite is concerned. And no test drives a *failing*
  commit through the locked span to show the latch is released — a leaked latch is silent, and the
  next operation on that collection simply never returns. Filed as one ticket because all three
  share a harness; splitting them means building the freeze-a-commit rig three times.

The handoff's other listed gaps were deliberately **not** filed. "One interleaving point per case"
and "in-process reduction, no network" are properties of what this kind of test can be, not defects
with a code site to name; filing them would produce tickets no one can close. The residual question
about the downstream two-machine incident is already carried by
`implement/2.4-collection-divergence-report-fields`.

### Tripwires recorded (not tickets)

- The ten-macrotask drain is what gives the `blocked()` assertions their discriminating power; if
  `Collection.update()` grows a deeper await chain, or these cases move onto a transactor with real
  I/O, "still pending" degenerates into a tautology. Parked by the implementer as a `NOTE:` on
  `drainMacrotasks`, carrying the measured turn-1 baseline. Left as written — still accurate.
- Case 2's `['rival', 'local']` log-order assertion encodes a `TestTransactor` commit-ordering
  property, not a guarantee of the code under test; what the case actually needs is the multiset
  (one entry per writer, no duplicate from the retry). Added a `NOTE:` at that assertion saying to
  compare sorted values if ordering ever becomes non-deterministic, rather than relaxing it to a
  length check, which would stop catching a duplicate.

### Checked and clean

- **Source hygiene.** 357 lines, roughly half of it prose. High for a spec, but the prose is what
  makes a concurrency test auditable — the comments state what each park instant *is* and why an
  assertion discriminates, which is not recoverable from the code. Functions are short and named
  for their role (`deferred`, `drainMacrotasks`, `releaseRefresh`, `logActions`, `stageOne`,
  `rivalWrite`). No split warranted.
- **Duplication.** Neither gated wrapper, nor `deferred`, nor `drainMacrotasks` duplicates anything
  in `test/` or `src/testing/`; both wrappers correctly extend `DelegatingTransactor` rather than
  re-implementing `ITransactor`, so neither can silently drop a forwarded member.
- **Resource cleanup.** Every acquired latch releases in a `finally` on both sites in
  `coordinator.ts`; with the gate fix above, the spec no longer leaks a held latch on failure.
- **Site-claim check before filing.** Grepped `coordinator.ts` / `TransactionCoordinator` across
  every open stage folder. Ten hits, all on unrelated concerns (session-mode bridge coverage,
  cross-collection atomicity, admission gate, partition healing); none claims the latch-span
  coverage site, so the new ticket is filed fresh rather than appended.
- **Accepted-tradeoff `NOTE:`s at the sites touched.** Read; none covers these findings.
