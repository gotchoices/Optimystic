# `node.blobs` reads, fetches and probes across machines

`node.blobs` is a `NodeBlobService` (`packages/db-p2p/src/blob/node-blob-service.ts`) over the single-machine `LocalBlobService` and the node's `BlobFetcher`:

- `read` (not `from: 'here'`) reads through `LocalBlobService.readThrough`; the first missing piece starts one foreground fetch of the read's range, and each later miss waits on that fetch's `stored(id)`. A read that throws or is stopped early aborts its fetch; a read that consumed its whole range leaves the fetch to finish its confirming walk and mark the record whole.
- `fetch` is a whole-blob foreground fetch.
- `stat` with `probe`, from a local `unknown` only, asks the fetcher's candidates in parallel, each under one response timeout, and answers `elsewhere` on the first that holds the blob whole or in part.
- `onProgress` counts pieces and bytes per reference across the service's running fetches, with `size` once the root is here.
- `put`, `pin`, `unpin`, `announce`, `onDurability` delegate to the local service; the blob protocol service still answers peers from the local service, so a peer's `stat` never starts a probe.
- Wiring: `wireBlobFetcher` returns one shared `BlobHolderDeps`; the blob service's start/stop and the fetcher are wired before the attachments, with the fetcher's stop still running before the local service's.

Implement-stage deviations (all accepted on review): a completed read does not abort its fetch (an unconditional abort logged a spurious failure and skipped `markWhole`); progress `size` is looked up at the first counted event; an extra `stat:probe-peer-failed` log line.

## Review findings

Read the `ticket(implement): feat-blob-pieces-move-between-machines` diff first, then the handoff, the fetcher and session it builds on (`blob-fetcher.ts`, `blob-fetch-session.ts`, `blob-holders.ts`), and the three docs it touched.

**Correctness — checked, no defect found.**
- Read path: the session is created synchronously at the first miss, so later misses reuse it; `stored(id)` rejects when the session fails, so a read fails at the piece that needed it with the fetch's error; a `stored` call after the session succeeded for a piece outside the range rejects with RangeError rather than hanging (`resolveIfHere`). Caller abort reaches the fetch through `readController`; early stop and throw both abort; the completed-read exemption is sound because a fully consumed range has every piece here.
- `read` changed from `async *` to a plain method returning `readThrough`'s generator; the generator body still runs lazily, so `LocalBlobService.read`'s behaviour is unchanged.
- Stop ordering: `blobs.start()`'s stop wrapper is installed before `wireBlobFetcher`'s, so the fetcher stops first, then the local service, then the serving role installed earlier; matches docs/blobs.md.
- Probe: every `askOne` settles (never rejects), the per-peer timer is cancelled on settle, peers still in flight are aborted once one holder answers.
- Progress: an entry is created on the first session and deleted when the last settles; events are counted on a per-reference chain so a size lookup never reorders them.

**Found and fixed (minor).**
- DRY: `NodeBlobService` carried its own `forwardAbort`, a one-source copy of `forwardAborts` in `blob-fetch-session.ts`. Exported the session's helper (module-internal; not re-exported from `index.ts`/`rn.ts`) and removed the copy.
- Doc accuracy: `onProgress`'s comment and docs/blobs.md said a fetch started on the fetcher directly "reports nothing". Events carry only the reference, so such a fetch's pieces are counted while a service fetch of the same blob runs. Both now say so.

**Tests.**
