# Complete: torn action, part 3 of 3 — cleanup, tripwire, mesh coverage, validation

Third and final part of `torn-action-must-recognize-its-own-durable-work`. Parts 1
(`torn-action-pend-tier-carve-out`) and 2 (`torn-action-own-entry-consumption`) landed the
behavioral fixes; this part carried no behavior change of its own except the new test.

For a reader with no context: a write commits its blocks in stages — collection header, then the
collection's log tail, then everything else. If one of those later blocks loses a race, the whole
write is reported as failed even though the log tail is already permanently stored. That is a
"torn action". It used to leave the writer either stuck forever (its own committed revision looked
like a rival's to its retry) or recording the same entry twice.

## What landed

**Dead filter clause removed** (`network-transactor.ts`). The non-tail sweep filtered on
`bid !== tailId && !(headerId && bid === headerId && !blockIds.includes(headerId))`. The second
clause is unsatisfiable: `bid` is drawn from `blockIds`, so `blockIds.includes(headerId)` is
necessarily true whenever `bid === headerId`. Reduced to `bid !== request.tailId`. No behavior
change.

**Stale NOTE rewritten** (same file, the non-tail sweep's error branch). It used to defer the
problem to a ticket that is this work. It now describes the resolved state: the refusal stays a
refusal, but its two former harms are handled upstream — the re-pend's own-revision carve-out at
all three pend-tier checks, and the retry's consumption of its own committed log entry. It names
the one arm NOT covered: the multi-collection path (`TransactionCoordinator`) still refreshes
without telling the collection which of its own actions is in flight, tracked as
`tickets/fix/refresh-must-always-know-its-own-in-flight-action`.

**Tripwire NOTE, not a ticket** (`coordinator-repo.ts`, the `ConflictRaceLostError` conversion in
`pend`'s catch). With three or more contenders, members' votes can split so every contender is
told it lost — an all-lose round where nobody wins. Since parts 1-2 that costs one retry cycle
instead of wedging. Recorded with a `NOTE:` tag, its actual cause (the approvals-first rule in
`ClusterMember.resolveRace`, not the tie-break), and a revisit condition (syncs exhausting
`maxAttempts` on repeated all-lose rounds → reserve/defer at pend time per
`backlog/feat-occ-priority-reservation`, not raising `maxAttempts`).

**New mesh-tier regression test** — `concurrent-diary-append-acknowledgement.spec.ts`. A
`tearFirstCommit` wrapper makes the first commit tear deterministically: it delegates the tail
(and header, when present) to the real transactor, drops every other block, and answers the caller
with the stale failure a genuine later-block loss produces. The test seeds one entry, appends a
second through the tearing transactor, and asserts the entry appears exactly once in the writer's
own view and exactly once on a node that never saw the tear.

## Review findings

Reviewed the implement diff (`e224fc13`) with fresh eyes before reading the handoff, then verified
the handoff's claims independently rather than accepting them.

### Major — filed as tickets

- **The commit path's header-first branch cannot fire from production code.**
  `NetworkTransactor.commit` commits the header before the tail only when the header is *absent*
  from `blockIds`. The only production producer of `headerId` (`TransactorSource.transact`) sets
  it exactly when the header is a fresh insert — and `blockIdsForTransforms` unions inserts, so an
  inserted id is always present in `blockIds`. The guard is therefore never true.
  **Verified two ways**: read the derivation end to end
  (`transact` → `pend` → `blockIdsForTransforms`), and instrumented the branch — 0 hits across
  every db-p2p mesh test, 2 hits in db-core, both from `commit-digest-threading.spec.ts` requests
  hand-built with the header held out of `blockIds`. Three separate comments still described the
  branch as live. Corrected all three (`network-transactor.ts`, `transactor-source.ts`,
  `struct.ts`) and the staged-commit narrative in `docs/internals.md` to say what the code does;
  filed the wire-it-up-or-delete-it decision as
  `backlog/debt-commit-header-first-branch-is-unreachable`. Nothing is broken today — the ordering
  that actually runs (tail, then everything else) is the one `Collection.bootstrapContext` depends
  on — so this is `debt-`, not `bug-`.

- **The new mesh test cannot reach the pend-tier half of the fix.** The handoff flagged this
  honestly and it holds up: a diary append writes no blocks beyond the log, so the tear drops
  nothing and the writer never re-pends. Both halves have direct unit tests at their own layer,
  but their interaction has never been exercised on a mesh. Filed as
  `backlog/debt-torn-commit-mesh-coverage-drops-no-blocks`, with the concrete construction (a
  tree write, and `tears[0].dropped > 0` as the assertion the diary case cannot make).

### Minor — fixed in this pass

- `CommitRequest.tailId`'s doc said "commit next". Given the above it is in practice the block
  committed *first*, which is exactly the ordering `Collection.bootstrapContext` relies on.
  Corrected.
- The handoff flagged that `tearFirstCommit`'s hand-written delegation would silently fail to
  forward a future `ITransactor` method. Only half true: the object literal is annotated
  `ITransactor`, so a new **required** method breaks the file at compile time; only a new
  **optional** method could go unforwarded silently. Recorded that distinction in the helper's
  doc comment so the next reader does not re-derive it.
