# Complete: the node the plugin builds takes a storage allotment

## What shipped

One plugin-level registration setting, `storage_allotment`, wired exactly as `cohort_topic` already was: read once in `resolveBinding`, carried on `libp2pOptions`, handed to `createLibp2pNode` by `CollectionFactory.createNetworkTransactor`. A host that lets the plugin build its `network` node can now say how many bytes of the machine it gave the network, and that node measures, sheds and refuses against that figure instead of against whatever its storage backend happens to report free — which on SQLite, LevelDB and memory is nothing at all.

- **`packages/quereus-plugin-optimystic/src/types.ts`** — `LibP2PNodeOptions.storageAllotment`, a `Pick` of the node's own option type over the three keys a host has business setting (`bytes`, `thresholds`, `usedBytesCacheTtlMs`); the two left out, `now` and `blobRecords`, are wiring seams the node fills itself.
- **`packages/quereus-plugin-optimystic/src/optimystic-module.ts`** — `declaredStorageAllotment(aux)` beside its two siblings, with the accepted key lists tied to the node's own keys by `satisfies` so a rename in db-p2p is a compile error here. It checks SHAPE only and refuses an unknown key rather than dropping it, because a dropped key would reach the node as "no allotment at all" — the silent un-measuring this release exists to end.
- **`packages/quereus-plugin-optimystic/src/optimystic-adapter/collection-factory.ts`** — the one-line pass-through into `createLibp2pNode`.
- **Docs** — a `storage_allotment` row in the README's *Plugin-Level Configuration* table, the `.release-notes.pending.md` paragraph on the plugin's storage settings, and the upgrade note that names the plugin setting beside `storageAllotment.bytes`.

Review added one node-side refusal and three doc corrections; see below.

## Review findings

**Read first, handoff second.** The implement diff (`ticket(implement): feat-the-node-the-plugin-builds-takes-a-storage-allotment`) was read before the handoff summary, and every factual claim in it was checked against source: the `Pick`'s two omitted keys really are seams (`StorageAllotmentOptions.now`, `.blobRecords` in `packages/db-p2p/src/storage/storage-account.ts`); `satisfies` really does catch a rename and not an addition, which is what its `NOTE:` says; `STORAGE_ALLOTMENT_THRESHOLD_KEYS` matches `StoragePressureThresholds`; the node really does refuse the numbers (`assertStorageAllotmentBytes` via `Number.isSafeInteger`, `resolveStoragePressureThresholds` via `Number.isFinite`, which also catches a string threshold that the plugin's closing cast would otherwise have let through); the integration spec's two magnitudes are right (`DEFAULT_MIN_RING_CAPACITY_BYTES` is 100 MiB and `CACHE_ALLOTMENT_SHARE` is an eighth, so 2 GiB is exactly the pivot its comment claims); and its citation of `catalog-hydration.spec.ts` and `init-retry-after-transient-failure.spec.ts` as precedent for reaching a factory's internals is accurate. The single construction site (`resolveBinding`) and single consumption site (`createNetworkTransactor`) were confirmed by grep — nothing else builds a `libp2pOptions`, so there is no second path the setting could miss.

**Minor — found and fixed in this pass.**

- **`usedBytesCacheTtlMs` was refused by nobody.** The setting's own documentation says the shape is the plugin's and "the NUMBERS are the node's to refuse" — true for `bytes` and for `thresholds`, and false for the third key: `StorageAccount` read `options.usedBytesCacheTtlMs ?? 60_000` with no check at all, so the plugin's `typeof === 'number'` was the only gate and `NaN` and `Infinity` passed both. Neither fails loudly. `NaN` compares false against every expiry, so the node rescans its whole block store on every ring tick and pressure sample — several times per operation, by `StorageAccount`'s own cost note — and `Infinity` memoizes the first scan for the life of the process, so the node never notices its disk filling again, which is precisely the un-measured storage this release exists to end. `NaN` is the reachable one: a host assembling its configuration reaches it through `Number(…)` of anything that is not a number. Fixed at the **node**, not at the plugin — `assertUsedBytesCacheTtlMs` in `packages/db-p2p/src/storage/storage-account.ts`, called from the constructor, throwing `RangeError` the way `assertStorageAllotmentBytes` does rather than clamping. That is the higher rung: it closes the hole for a host that passes `NodeOptions` directly as well as for a plugin host, and it restores the "shape here, numbers there" split the plugin's validator is built on instead of carving an exception into it. `0` stays legal (scan every call, which the opt-out tests use). The plugin needed no code change; its doc comment and the README row now name the third validator.
- **The anchor section did not know the plugin existed.** `packages/db-p2p/docs/storage.md` §9 still opened with "**The one option.** `NodeOptions.storageAllotment.bytes` …" — an operator whose node is built by the plugin would read that section to learn how to set an allotment and find no route to it. §8 already cross-references the plugin's `storageFactory`, so the precedent for naming it in this document exists. Added a short **Two doors to it** paragraph naming the plugin setting and saying which layer refuses what, plus one clause in §10's cadence paragraph for the new TTL refusal.

**Major — none.** Nothing reached the filing bar and nothing was filed. The feature is one validated read and one field on a call that already carried four like it; the sites that could have gone wrong — a second `libp2pOptions` construction, a `USING`-argument leak, a node cached under a key the setting cannot reach — were each checked and are each right.

**Conditional concerns — none parked, because the only one was already parked.** The one genuinely conditional thing in the diff is that a key *added* to `NodeOptions.storageAllotment` in db-p2p is refused here until someone adds it to the plugin's key list, and the implementer already left that at the site as a `NOTE:` explaining the loud-and-stale choice. Nothing else in the diff was "fine now, work later": the TTL hole above is a defect on a currently-reachable path, not a tripwire, so it was fixed rather than demoted.

**Considered and left alone.**

- **Validation happens in `resolveBinding`, not in `register()`.** Weighed and settled in the plan, and flagged in the handoff as not open. Re-checked only for soundness, which holds: the throw is always before a node exists, and one reader beside its two siblings cannot drift from a second site. Not re-filed. One wrinkle worth recording rather than filing: `hydrate` resolves the default binding inside a `try`/`catch` that logs `blob:backend-resolution-failed` and continues, so a malformed value met during hydrate alone is swallowed — but hydrate builds no node the catalog read did not already build, and the next table or blob use throws unswallowed, so nothing is ever silently applied wrong.
- **`{ bytes: undefined }` is accepted** and reaches the node as absent. The key-set check runs over `Object.keys`, so the key is known, and the numeric check skips `undefined`. That is ordinary optional-field semantics and matches the node's own reading of an absent `bytes`; nothing acts on the difference.
- **The setting is inert on `local`, `test` and `mesh-test`, and on a host-registered node.** Verified rather than assumed. It is inert because `SingleMachineBlobService` does not accept an `ownWriteRoom` at all, which `LocalBlobServiceInit` documents as deliberate ("a service built without a pressure reading … refuses nothing"). So a `local`-transactor host's blobs are unbounded by design in db-p2p, not by an omission in this diff, and the README row states the inertness. Nothing to file against this ticket.
- **`optimystic-module.ts` is 7904 lines** (`wc -l`), 65 of them new here. That size debt is already claimed by `tickets/backlog/debt-optimystic-vtab-class-is-too-big-to-review.md`, so this is the Nth instance of a filed class — evidence, not a new ticket. The new reader sits with its two siblings, which is where a reader looks for it.
- **The release notes needed nothing for the new refusal.** `StorageAccount` and the whole allotment machinery are new in this same unreleased version, so a stricter `usedBytesCacheTtlMs` changes behaviour for no released version: it is part of the option's first contract, not a break.

**Tests — one added, none cut.** The implementer's seven unit cases each pin a distinct branch of the setting's contract rather than restating the implementation, and the two that look thinnest earn their place as a pair: unset answers `undefined` (so the node logs its own missing-allotment `WARN:`) while `{}` answers `{}` (so it takes the defaults), and that distinction is the setting's documented behaviour. Nothing mocks anything the repository owns. So nothing was cut. Added exactly one case, for the defect found — `refuses a TTL that is not a lifetime, naming the option` in `packages/db-p2p/test/storage-account.spec.ts` — at the layer the defect lives at and beside the TTL cases already there. No test was added for the registration plumbing: the integration spec covers that path end to end on a real node, which is stronger than a wiring test.

**The two assertions that had never run, now run.** The handoff was explicit that `test/plugin-node-storage.integration.spec.ts` had never been executed and that its node key (`plugin-node-storage-it:0`) and its `capacity().totalBytes === allotmentBytes` claim were derived by reading rather than by running. Both were run under `OPTIMYSTIC_INTEGRATION=1` against real libp2p, and both hold.
