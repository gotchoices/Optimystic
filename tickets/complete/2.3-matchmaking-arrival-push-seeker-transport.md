# Matchmaking arrival push — the seeker's receiving end and real renew/withdraw (complete)

Fourth of five tickets in the arrival-push chain. A seeker built with `createLibp2pMatchmakingTransport` can now opt into pushes and receive them, and every walk — push or poll — keeps its seeker record alive and withdraws it when it leaves a tier. Nothing is wired into the node factory yet; `matchmaking-arrival-push-wiring-and-e2e` does that, plus the libp2p `send` binding, the mesh tests and the docs.

## What was built

**`ArrivalPushReceiver`** (`arrival-push-receiver.ts`), one per node, holds the listening walks keyed by push binding id (the seeker payload's `correlationId`, base64url).
- `subscribe(topicId, correlationId)` → `{ channel, unsubscribe }`. Subscribing a binding id twice throws (ids are 16 random bytes, so only a programming error can do it).
- `receive(frame, from)` → encoded ack, or `undefined` for no reply. It decodes with `decodeArrivalPushV1` (bounded by `maxBytes`) and verifies the signature against `from` with `verifyPeerSig`. An undecodable or unverifiable frame gets no reply and is logged. A binding nobody listens on, or a binding listened on for another topic, is acked `unknown_seeker`. Otherwise the push is queued, the pending `wait` is woken, and the ack is `ok`. It never throws.
- **Renamed from the ticket's `handle` to `receive`**: `test/dial-options-single-site.spec.ts` flags any `.handle(` member call under `src/` as a raw libp2p handler registration, and both this file's handler and the wiring ticket's in-process `send` would call it. The wiring ticket was amended to say `receive`.
- The channel is an array queue (capped at 64, oldest dropped and logged) plus at most one pending waiter. `wait(ms)` resolves at once for `ms <= 0`, a non-empty queue, or a closed subscription; otherwise on whichever comes first, a push or an unref'd timer, which is cleared when a push wins. A second concurrent `wait` releases the first rather than stranding it. `unsubscribe` resolves the waiter and drops the queue; it is idempotent.
- `registerArrivalPushHandler(node, protocol, receiver, maxBytes?)` rides `handleRequestResponse` and passes the connection's authenticated `remotePeer` as `from`.

**`SeekerKeepAlive`** (`seeker-keep-alive.ts`, split out of the transport so the file stays focused; it has no libp2p dependency, since delivery is the injected `send`). It is created once per walk transport.
- `accepted(treeTier, correlationId, slotPrimary, routedMember)`: called on each `accepted` register. It decodes the reply's `primary` (base64url of the peer-id string, the member engine's `bytesKey` encoding) with `bytesToPeerIdString`. If that is absent or unreadable, it falls back to the FRET-routed member that admitted the register, whose `primary_moved` will name the slot primary. A later accepted register replaces the live registration.
- `renew()`: a no-op with no live registration, or within `seekerTtlMs / 3` of the last keep-alive. The `accepted` register counts as a keep-alive (deviation, below). Otherwise it sends a signed plain-ping `RenewV1` carrying the accepted register's correlation id. `ok` → done. `primary_moved` → adopt `newPrimary` and ping it once more immediately (deviation, below). `unknown_registration` → debug log, no re-register. A dial or decode failure → logged. It never throws.
- `withdraw()`: clears the live registration, then sends a signed `withdraw: true` `RenewV1` to the member that admitted the register, and to the slot primary only if that member did not answer `withdrawn` (changed in review, see below). Best effort; it never throws.

**Transport** (`createLibp2pMatchmakingTransport`):
- New deps `arrivalPush?: ArrivalPushReceiver` and `pushOnArrival?: boolean` (default `arrivalPush !== undefined`). `pushOnArrival: true` with no receiver throws at construction. A per-walk `walkTransport(topicId, { pushOnArrival: true })` with no receiver throws when the walk transport is built.
- With push on, the walk's `MatchmakingSeeker` gets `pushOnArrival: true`, so its payload carries the correlation id. The walk transport subscribes under `bytesToB64url(seekerState.correlationId)` and exposes `pushes`. With push off the payload is exactly what it was before (no `pushOnArrival` field at all), and `pushes` is absent.
- One correlation id per walk, shared by every tier's register.
- `renew` / `withdraw` delegate to the keep-alive. The renew/withdraw sender dials the cohort-topic `register` protocol. When the slot primary is this node it uses the new `MatchmakingSelfServe.renew?`, and if that is unbound it logs and skips rather than throwing.
- `close()` withdraws, then unsubscribes (in `finally`). It is idempotent. The walk client already calls `close()` in `finally` on every exit.
- `MatchmakingSeekerSession.walk` passes `SeekerWalkRequest.pushOnArrival` through; `MatchmakingSeekerSessionDeps.walkTransport` takes the optional second parameter. `createMatchmakingQuorumDiscovery` is unchanged, so it keeps the transport default.
- The comments that called renew/withdraw no-ops are gone; the module header describes the keep-alive.

## Deviations from the ticket's letter (judgment calls for the reviewer)

- **The accepted register counts as the first keep-alive** for the `ttl / 3` throttle. The ticket said to throttle against "the last renew attempt". Without this, the first hang-out wake (1 s on the poll path) pings a record written a second ago.
- **`primary_moved` is followed once immediately**, not only "for the next renew". On the push path the next wake can be a whole 5 s safety poll away, and the record goes untouched until a ping reaches the slot primary. The follow is capped at one hop, so there is no loop.
- **`receive` instead of `handle`** (see above).
- **A separate `seeker-keep-alive.ts`** rather than more code in `query-transport.ts`.

## Tests added

`test/matchmaking/arrival-push-receiver.spec.ts` (real Ed25519 keys, no libp2p):

## Known gaps and things to look at

- **Seeker as its own slot primary.** In small meshes where every node is in every cohort, the seeker's slot primary can be its own node. Then renew and withdraw need `selfServe.renew` bound (to the host's `resolveRenew`), or they are skipped and the record lapses after one TTL. Added as an arm of `2.4-matchmaking-arrival-push-wiring-and-e2e`, which owns both the composition root and the integration case that must keep the record alive past one TTL.
- **Tripwire, parked as a `NOTE:` at the throttle in `SeekerKeepAlive.renew`:** pings go out only on walk wakes. On the push path that is every push or safety poll (5 s by default, half the 10 s TTL), so one failed ping can let the record lapse and leave the rest of that tier to the safety poll. The remedy, if pushes are measured missing for this reason, is a keep-alive timer of its own.
- **Withdraw and clock skew (inspection, unchanged cohort behaviour).** The cohort's freshness gate refuses a privileged withdraw whose timestamp is not newer than the record's server-side `lastPing`. A seeker clock behind the slot primary's can therefore have its withdraw answered `unknown_registration`, and the record then ages out by TTL. The provider manager's withdraw has the same exposure.
- **Promotion re-register.** The tier the walk re-registers at after a promotion keeps its live registration until the descended tier accepts. That replacement sends no withdraw, so the old tier's record ages out, as the seeker-loop review accepted.
- Edge cases checked by inspection only: queue cap overflow; `wait(ms <= 0)`; `unsubscribe` releasing a pending `wait`; withdraw on a walk that was never accepted (sends nothing); escalation replacing the live registration and slot primary; a renew racing the first gossip round (`unknown_registration`, logged at debug); right correlation id but another topic (`unknown_seeker`, same branch as an unknown binding).

## Review findings

Read the `ticket(implement): matchmaking-arrival-push-seeker-transport` diff first, then the cohort-side code it talks to: `onRenew` in `packages/db-core/src/cohort-topic/registration/renewal.ts` (withdraw honoured by any holder before the slot check, freshness gate, plain ping served only by the computed primary), the member engine's `bytesKey` reply encoding, `resolveRenew` and the participant-signature verifier in `packages/db-p2p/src/cohort-topic/host.ts`, the arrival-push driver's binding key, `peer-codec.ts`, and the walk client's calls to `renew` / `withdraw` / `close`.

**Correctness — one defect found and fixed.** `SeekerKeepAlive.withdraw` sent its tombstone only to the slot primary. The walk registers through the FRET-routed member, which can differ from the slot primary, and the slot primary learns the record only by gossip (a round is up to 5 s). The commonest escalation is immediate (the decision engine escalates on the `accepted` reply, with no hang-out), so the withdraw usually reached a slot primary that did not hold the record yet, was answered `unknown_registration`, and the record stayed on the admitting member for a full TTL — the polite withdraw on escalation failed in exactly the case it exists for. Fix: the live registration now remembers the admitting member (`LiveRegistration.admittedBy`); `withdraw` goes there first (it holds the record from the moment it accepted) and falls back to the slot primary only when that member did not answer `withdrawn`. Any holder evicts and gossips the eviction, so one success suffices. Regression test: `test/matchmaking/seeker-keep-alive.spec.ts` (fails on the old code, which sent only to the slot primary). The real-socket seeker-walk case, rerun with `DEBUG=optimystic:db-p2p:matchmaking-query*`, now logs nothing for the close-time withdraw, where the implement run logged it skipped because the slot primary was the seeker's own node; I did not add instrumentation to confirm the `withdrawn` reply itself.

Verified correct by inspection: the participant id on `RenewV1` (base64url of the peer-id string's UTF-8 bytes) matches the `participantCoord` the register carries and what `verifyParticipantSig` decodes; the reply's `primary` decodes with `bytesToPeerIdString(b64urlToBytes(…))`; the receiver's subscription key (`bytesToB64url(seekerState.correlationId)`) is the payload correlation id the driver echoes in a push (`pushCorrelationId`); `RenewV1` rides the `/register` protocol, which the host dispatches to `resolveRenew`; the walk's same-tier re-register on a promotion does not withdraw and gets `promoted`, so the live registration is replaced only by the descended tier's `accepted`; `createMatchmakingQuorumDiscovery`'s one-argument `walkTransport` stays compatible.

**Edge cases and error paths.** `PushQueue.wait` (ms ≤ 0, non-empty queue, closed, a second concurrent wait releasing the first, timer cleared on wake), queue cap overflow, `unsubscribe` idempotence and releasing a waiter, duplicate subscription, `close` idempotence with unsubscribe in `finally`, `selfServe.renew` throwing (caught by the keep-alive), dial and decode failures (logged, `undefined`) — all checked by reading; no defect.

**Interactions — parked, not ticketed.** The withdraw freshness gate and seeker-vs-member clock skew, and the promotion re-register leaving the old tier's record to age out, are as the implementer described; both are cohort-side behaviour already accepted, nothing to add. The ping-only-on-wake keep-alive is the implementer's tripwire `NOTE:` at the throttle in `SeekerKeepAlive.renew`; left as is. The first ping, at `ttl / 3`, can itself race admission gossip and be answered `unknown_registration`; the second lands inside the TTL on the poll path, and on the push path that same tripwire covers it — no new note.

**Self-primary renew.** Already filed by the implementer as an arm of `matchmaking-arrival-push-wiring-and-e2e`; I updated that arm's quoted log line, which this review reworded (`sendRenew` now addresses "the cohort member", since a withdraw is no longer always sent to the slot primary).
