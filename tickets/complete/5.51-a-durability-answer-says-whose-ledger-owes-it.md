# A durability answer says whose ledger owes it — complete

Part of GitHub issue #26. Consumer: `a-sql-commit-learns-when-it-becomes-fully-held`, which follows a commit only when every below-`full` cohort answer has `recordedBy === selfPeerId`.

## What landed (`ticket(implement): a-durability-answer-says-whose-ledger-owes-it`)

- **`WriteDurability.recordedBy`** — the peer id of the node whose under-replication ledger recorded the write's missing copies, i.e. the only node that will fire `BlockDurabilityReachedEvent` for those blocks. `CoordinatorRepo.acknowledgeCommit` (the one exit every commit success goes through) sets it from `localPeerId` when `noteReplicationShortfall` reports that every non-torn block's entry was recorded. Absent for a `full` answer, a coordinator that does not hold the bytes, no ledger, a ledger fault on any block, or no `localPeerId`. `mergeDurability`'s dedup key includes it.
- **A settle that removed an entry announces it.** `IUnderReplicationLedger.settle` returns the removed entry; `CoordinatorRepo` takes an optional `onBlockDurabilityReached` (the drain's `BlockDurabilitySink` type), wired in `libp2p-node-base.ts` to `storageRepo.emitBlockDurabilityReached`, and a `full` commit fires `{ blockIds: [blockId], rev, actionId }` per entry it removed. A throwing sink is logged, never fails the commit.
- **`satisfy` returns `SatisfyOutcome`** (`owed` / `cleared` / `absent`), and the drain fires only on `cleared`. This was a deliberate departure from the plan, which assumed the per-block serialization alone gave one event per entry: the drain treated "already gone" as "cleared", so a settle landing mid-push would have announced the block twice. Side effect: an entry evicted at the size cap mid-push no longer produces a false full-replication event.

## Review findings

Read the implement diff before the handoff, then ran the code paths by reading `CoordinatorRepo.commit`'s success exits, `KvUnderReplicationLedger`, `UnderReplicationDrain.recordConfirmed`, and the consumer ticket's expectations.

**Correctness, checked and found sound:**
- Every success exit (solo, local-executed, local fallback, tolerated divergence) goes through `acknowledgeCommit`, which returns a new answer object carrying `recordedBy`. Refusals never reach it.
- Exactly one event per ledger entry: `settle`, `satisfy`, `record` and `name` all run inside the ledger's per-block queue, and only the call that removes the entry announces it (`settle` returns it; `satisfy` reports `cleared` vs `absent`). Checked both race orders (drain first, then settle finds nothing; settle first, then drain sees `absent`).
- The implementer's open question, a `record` skipped because a higher revision is already recorded, still counts as tracked. The ledger keeps one entry per block at the highest revision. That entry's event fires at the higher revision on this same node, and the consumer covers a pending `(block, r)` with any event at `rev >= r`. Confirmed against the consumer ticket's covering rule.
- A later commit coordinated by a different node leaves this node's entry standing. This node's drain then pushes the newer content and clears the entry, so the event still fires here. No promise is left stranded.
- Torn blocks: the writer's transactor drops a `full` answer to `majority` when blocks are torn, with no `recordedBy` on it. A `majority` answer with `recordedBy` that later becomes torn keeps the field, but the consumer refuses any torn commit. Nothing breaks.
- `distinctReports` keeps two otherwise identical answers apart when different nodes recorded them (pinned in `durability.spec.ts`).
- Known approximation, unchanged by this ticket: a multi-block commit's `full` is judged on `blockIds[0]`'s cohort, and the ledger records missing copies under the same approximation. The settle event inherits it.

**Tests:** I reviewed the added and changed specs. Each one pins a contract from the ticket: the recorded case, the partial ledger fault, the solo empty missing set, the tolerated divergence, the settle event firing once at the commit's revision, the drain staying silent on `absent`, and dedup by recorder. None of them restates the implementation or verifies a mock. I added none and cut none.

**Docs:** `struct.ts`, `change-notifier.ts`, `repo.md` (ledger table, the recording rules, the drain and event paragraphs) and `internals.md` § UnderReplicationDrain all match the new behaviour. Two minor gaps, fixed in this pass:
- `docs/debugging.md` did not list the drain's new `entry:settled-elsewhere` line or the coordinator's `block-durability-sink-error`, and its `under-replication-record-failed` entry did not say the answer then names no `recordedBy`. Added all three.
- The `BlockDurabilitySink` doc in `under-replication-drain.ts` still said only the drain calls it. It now names `CoordinatorRepo` as the other producer.

**Tripwires:** The size-cap eviction that strands a `recordedBy` promise is already parked as a `NOTE:` on `KvUnderReplicationLedger.evictBeyondCap` by the implementer, and is genuinely conditional (only matters at 100 000 entries). Left as is, not filed.

**Accepted as is:**
- A settle event can fire before the writer's answer leaves `acknowledgeCommit`. The drain already allows the same ordering, and the consumer plans a record of recent events for exactly this race.
- `CoordinatorRepo`'s constructor now has 15 positional parameters. This follows the existing pattern, and the factory hides it. A refactor to a components object is outside this ticket's scope and not worth a ticket on its own.
- A one-machine deployment's `local` commits carry `recordedBy` and stay pending until a second member appears. This is what the ticket specified, and it is consistent with `local` not being `full`.
