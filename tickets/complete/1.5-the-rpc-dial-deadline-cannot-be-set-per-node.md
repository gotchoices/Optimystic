# Complete: the RPC dial deadline can be set per node

## What landed

`NodeOptions.rpcDeadlines?: Partial<RpcDeadlineDefaults>` — `{ dialTimeoutMs?, responseTimeoutMs? }` — sets this package's own RPC dial and response deadlines exactly (no floor), replacing the values `resolveLinkDeadlines` derives from `linkRoundTripMs`. It is applied inside `resolveLinkDeadlines`, before `transferTimeoutMs = max(30000, dial)` and `transactionTimeoutMs = max(30000, 4 × dial)`, so both follow an explicit dial, and hosts that read `node.linkDeadlines` (the Quereus collection factory, the reference peer) pick it up unchanged. Precedence, highest first: a caller's per-request value → the `spreadOnChurn` / `underReplicationDrain` `push*` fields → `rpcDeadlines` → derived. Each field must be finite and above 0 (so the per-request "no cap" `0` is refused as a node policy); the dial is capped at `MAX_RPC_DIAL_TIMEOUT_MS` (about 5 days, so `4 × dial + 5000` fits a 32-bit timer) and the response at 2^31 − 1. The relationship to `connectionManager.addressDialTimeout` is documented, not enforced. Landed in `ticket(implement): the-rpc-dial-deadline-cannot-be-set-per-node`.

## Review findings

- **Wiring / precedence** — checked: `options.linkRoundTripMs` is read only at the one `resolveLinkDeadlines` call in `createLibp2pNodeBase`; every RPC client (cluster, sync, dispute, restoration), the spread and drain push defaults, the rebalance transfer deadline and the `node.linkDeadlines` attachment all read the one resolved object, so an explicit value reaches them all. `cohortQueryTimeoutMs`, the libp2p connection-manager values and the reconcile pass bound still derive from the round trip alone, which is correct — they are not RPC dial/response deadlines. Requests run under `withinRequestBudget` pass explicit `0`s and are unaffected, as intended.
- **Ceiling arithmetic** — checked `MAX_RPC_DIAL_TIMEOUT_MS = floor((2^31−1)/5)`: for dial ≥ 5000, `4·dial + 5000 ≤ 5·dial ≤ 2^31−1`; below 5000 the transaction floor of 30 000 dominates. The response ceiling is the raw timer limit, correct since it reaches one `setTimeout` and nothing is derived from it. No defect.
- **Docs** — one inaccuracy fixed inline: the `NodeOptions.rpcDeadlines` doc said both deadlines reach a host's `RepoClient` through `node.linkDeadlines`. Only the dial does (via `NetworkTransactor`'s `dialTimeoutMs`); `RepoClient` deliberately takes no response deadline, its reply being bounded by the transactor's budget. Reworded. readme "Slow relayed links", cluster.md, the `linkRoundTripMs` / `connectionManager` / `spreadOnChurn` / `underReplicationDrain` docs and the `LinkDeadlines` / `resolveLinkDeadlines` docs otherwise read correctly against the code. `docs/internals.md` does not list node deadline options, so needed no change.
- **Tests** — the new block pins the no-floor rule, what follows an explicit dial (and that nothing else moves), each field's validation with a field-naming message, and the dial ceiling against the 32-bit timer. Each is a named contract on logic with branching; none cut, none added. No node-construction test, agreed: the wiring is one argument at one call site.
- **Error handling / type safety / hygiene** — validation throws before anything is acquired, matching `linkRoundTripMs`; `validDeclaredMs` removes the duplication the second and third checks would have introduced; the `linkRoundTripMs` message is unchanged. No `any` added, file sizes unaffected. Nothing found.
- **Tripwires** — none recorded; the unenforced `addressDialTimeout` relationship is already documented at the option and in the readme.
- **Validation run** — `yarn workspace @optimystic/db-p2p build` and `typecheck` clean; full `yarn workspace @optimystic/db-p2p test`: 3179 passing, 64 pending; `yarn lint` and `yarn lint:docs` clean.
