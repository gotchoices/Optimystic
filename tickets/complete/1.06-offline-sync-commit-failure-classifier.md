Stage 1 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages) is done. The offline queue's sender (stage 3) will call this to decide, for each failed attempt, whether an entry waits, settles as failed, or is treated as possibly landed.

## What landed

`classifyCommitFailure(error: unknown): CommitFailureClass` lives in `packages/db-core/src/transaction/commit-failure-class.ts`. It is exported, with its type, through the transaction barrel and the root barrel. It sorts errors into these classes:

- `cohort-unreachable`: `PromiseShortfallError`, or `BlockUnavailableError` with reason `cohort-unreachable` / `peers-unreachable`
- `contention`: `SyncRetryExhaustedError` (which covers `SyncRevisionStalledError`) and `CoordinatorStaleLossError`
- `guard-refused`: `TreeEntryChangedError` gives `concurrent-modification`; any other `TreeGuardRefusedError` gives `constraint`
- `rejected`: `ValidityRejectedError`
- `too-large`: `TransactionTooLargeError`, `BlockTooLargeError`
- `expired`: `TransactionExpiredError`
- `torn-not-saved` / `in-doubt`: `TornActionError`, split on `final`
- `partial`: `CoordinatorPartialCommitError`
- `unknown`: everything else

It reads only an error's class and its `reason` / `final` fields, never its message, and never walks `cause`. The design doc's classification table, its failure-reason union (`'too-large'`), its stage list and its status line were updated, and `docs/internals.md` points to the function.

Test: `packages/db-core/test/commit-failure-class.spec.ts` is one table of 11 cases, one per branch, plus two negative cases: a plain error carrying the shortfall's text, and an aggregate whose `cause` is a shortfall. Its `never`-default switch makes `yarn build` fail when a class is added without being handled.

## Review findings

Read the implement diff (`ticket(implement): offline-sync-commit-failure-classifier`) before the handoff.

**Checked, no defect:**
- **Class hierarchy / arm order.** Grepped every `class *Error extends` in db-core. No two matched classes share an ancestor apart from the intended ones (`SyncRevisionStalledError` → `SyncRetryExhaustedError`, the guard-refusal subclasses), so the order of the arms cannot misroute anything. `BlockPossiblyStaleError` is a sibling of `BlockUnavailableError`, not a subclass.
- **"Never walk `cause`".** Confirmed against `NetworkTransactor`: its three `Some peers did not complete` aggregates attach the root error as `cause`. That makes the rule necessary.
- **Errors that fall to `unknown`** (`TreeDeleteGuardKindError`, `CoordinatorConcurrentStampError`, `BlockPossiblyStaleError`, `CollectionHeaderVanishedError`). These are left as they are. The design treats `unknown` as transient, re-sent only under the attempt's own identity and bounded by `expireAfterMs`. A deterministic caller bug such as the delete-guard error therefore costs retries until expiry and never drops data. Giving any of them its own class is a design-doc decision; none is needed now.
- **Session mode returns only `error?: string`** (`ExecutionResult`), which this function cannot classify. Not a gap: offline mode refuses to start while session mode is configured (design doc §Session mode).
- **`TornActionError.reason` ignored, only `final` read.** This matches the doc table.
- **Export via the transaction barrel** rather than `src/index.ts`. The public surface is the same. Fine.
- **Docs.** Read both touched docs, plus `docs/architecture.md`'s index row, which still says "design" and is accurate enough since only stage 1 exists. The citations lint is clean.
- **Resources, performance, types.** These are pure synchronous `instanceof` checks with a module-level `Set`. Arms are narrowed per class, with no `any`.

**Found and fixed in this pass (minor):**
- The doc comment claimed `yarn lint:deps` keeps one copy of the package in the tree. False: `scripts/shared-majors.cjs` guards only libp2p and multiformats packages, not `@optimystic/db-core`. Reworded to say a second copy makes errors sort as `unknown` and that nothing in the repo guards against it.
- The `contention` and `cohort-unreachable` descriptions said "nothing was saved". `SyncRetryExhaustedError`'s own contract says the opposite: an earlier attempt's log entry may still stand. Also, a shortfall on a later attempt of one sync says nothing about the earlier attempts. Both descriptions were narrowed to what each error actually proves.
- **Test cut:** the `ValidityRejectedError` case only re-tested a single `instanceof`, which the spec's own header said would be left to the type. The shortfall positive case stays, because it is the control for the two negative cases.

**Tripwire parked (design doc):** the identity rule in `docs/offline-sync.md` §Identity across attempts says to mint a new action id after "a refused pend". But one sync sends several attempts under one id, and an earlier attempt can leave its log entry standing. Added a sentence there saying the proof has to cover every attempt sent under the id. This is for stage 3 to honour; no code acts on it yet.

**Not filed:** nothing met the bar for a ticket.
