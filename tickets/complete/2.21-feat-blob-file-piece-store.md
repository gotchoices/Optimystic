# The filesystem piece store

`FilePieceStore` (`packages/db-p2p-storage-fs/src/file-piece-store.ts`, exported with `PIECE_DIRECTORY = 'optimystic-pieces'`) implements `IPieceStore` on files: one file per piece at `<basePath>/optimystic-pieces/<xx>/<piece id>`, `<xx>` = the two characters before the id's last, holding exactly the piece's bytes, outside the write-ahead log. A put writes `incoming/<hex>.tmp`, syncs it, and renames it into place; an open deletes leftover temps; a flush syncs the directories whose entries changed (deepest first), no-ops on win32 as `fsyncDir` does. Ids are checked against a lowercase base32 CID pattern before any path is built (`RangeError` otherwise). The block listing skips the piece directory, and the store reports the same store identity as a `FileRawStorage` over the same base path, whose byte count already includes the pieces.

Implementation deviations from the plan, all kept: open marks the piece root and base path dirty on every open (covers pieces an earlier crashed process left unflushed); put marks its fan directory dirty even when the piece was already present, and delete even on `ENOENT` (covers a concurrent put/delete that has not yet marked it); `list` also requires a file's fan to match its directory; temp cleanup failures are logged and swallowed, since the next open removes them.

## Review findings

Checked: the implement diff (`ticket(implement): feat-blob-file-piece-store`) in full; the crash ordering of put (bytes synced before rename, directory entries synced at flush, fan-directory creation marks the root); open memoization and retry on failure; the rename-race arm on POSIX (rename replaces, same content) and Windows (replace refused while the target is open → `EPERM`/`EACCES` → target exists → treated as raced); the id guard (no separator, dot, colon or uppercase can reach a path; case-insensitive filesystems cannot collide since ids are lowercase); the `get` view (`fs.readFile` allocates its own buffer); import graph (`file-batch-backend.ts` → `file-piece-store.ts` → `file-write-log.ts`, no cycle); interactions with the rest of the package — `FileBatchBackend.listBlockIds` skips the directory, `directoryByteSize` counts it, `FileKVStore.listRecursive` only yields `.json` files so piece files and `.tmp` temps are never read as keys; that `fileStoreIdentity` lowercases on win32 identically for both stores.

Found and fixed (minor):
- **Concurrent flushes could resolve early.** `flush` took and cleared the dirty set, then synced; a second flush called while the first was still syncing found the set empty and resolved at once, before the directory entries of puts that resolved before it were durable — breaking rule 2 of the flush contract (`IPieceStore.flush`). Flushes now run one after another on a promise chain (`FilePieceStore.flush` / `syncDirtyDirectories`); a rejection reaches that flush's caller and does not stop the next. No test added: observing it needs control over directory-sync timing, i.e. mocking `fsyncDir`, which this repo owns, and on win32 (where the suite runs) directory syncs are no-ops anyway.
- **Undocumented log line.** `temp:close-failed` was logged but not listed; added to `docs/debugging.md`, and the README's log list now names all four lines and points at debugging.md.

Tests: the conformance run (`runPieceStoreConformance`, persistent) and the two on-disk cases (leftover temp, id refusal) each pin a contract the file store owns with real branching; none restate the implementation or test a mock. Kept as is; none cut, none added beyond the note above.

Docs: `docs/blobs.md` §The local store, `packages/db-p2p/docs/storage.md`, `docs/debugging.md` and the fs README all describe the store as built. The README usage example constructs the store but cannot pass it to the node yet; the downstream ticket `feat-a-node-stores-blob-pieces` (plan/) already lists updating that example, so nothing further filed.

Tripwires: the implementer's three `NOTE:`s (serial directory syncs at `flush`, one stat per piece at `bytesUsed`, two stores over one directory unsupported at the class) were read and stand; nothing new parked.

Major findings / tickets filed: none — nothing found that a type, generalized test or boundary check would retire as a class.
