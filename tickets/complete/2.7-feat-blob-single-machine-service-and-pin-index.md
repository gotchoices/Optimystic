# What landed

Two additions to the db-p2p blob services, both for the SQL plugin's blob work (`feat-blob-sql-type-and-blob-service`, `tickets/implement/2.702-feat-blob-sql-type-and-blob-service.md`) and neither specific to it. No production code calls either one yet — that plugin is their first caller.

## The pin index (`packages/db-p2p/src/blob/local-blob-service.ts`)

`BlobPinIndex` is declared beside `BlobFetchStore` and `BlobOwedRecords`, with `pinsOf(ref)` and `listPins(ownerPrefix)`. `LocalBlobService implements BlobService, BlobOwedRecords, BlobPinIndex`, so drift is a compile error, and both methods answer from its `BlobRecordStore`: `pinsOf` reads through the existing private `readableRecord`, so an absent or undecodable record answers `[]`; `listPins` walks `BlobRecordStore.listRefs`, skips an unreadable record with a `record:unreadable` line as `responsibleRefs` does, and yields each `pin` hold whose owner starts with the prefix. An empty prefix lists every pin. Both share one module-level helper, `pinOwnersOf`.

`NodeBlobService implements BlobService, BlobPinIndex` and forwards both to `this.local`, the way `pin` and `unpin` already do, so `node.blobs` satisfies `BlobService & BlobPinIndex` too — and does so at the type level, not only structurally, because `packages/db-p2p/src/optimystic-node.ts` types `blobs` as the concrete `NodeBlobService`.

`LocalBlobService.pin` does create a record for a reference this machine holds nothing of (`recordAfterPin` with `current === undefined` returns a fresh record carrying just the pin), which is what lets a transaction pin a reference it copied out of another row. Confirmed by inspection; nothing was changed for it.

## `SingleMachineBlobService` (`packages/db-p2p/src/blob/single-machine-blob-service.ts`)

A `BlobService & BlobPinIndex` whose cohort is this machine alone, by composition over a `LocalBlobService` it constructs from `{ pieces, kv, digest?, now? }` — the shape `2.702`'s `blobStorageFactory` returns. Every member but `announce` is a one-line delegation, plus `start`/`stop` forwarding the sweep lifecycle. The `digest` default is applied once, by `LocalBlobService`.

`announce(ref, scope)` is the only behaviour of its own: refuse a scope the wire would refuse; `local.holdOwed(ref)`, which creates the record and flushes, so the blob survives a restart with a hold no sweep removes; a stored `durabilityOf` means this is a re-announce and stops, emitting nothing; otherwise the class `{ quorum: 'local', accepting: 1, unconfirmed: [], confirmed: holdsWhole ? 1 : 0 }`, then `setDurability` and `emitDurability` in that order, then one `blob:announce-single-machine` line on the `blob:store` namespace. The whole read-decide-write is serialized per reference (see the first review finding below).

Nothing here ever releases the `owed` hold — there is nobody to copy to — so it is released only by reclaiming (`feat-unreferenced-blobs-are-reclaimed`), exactly as that work releases a networked node's owed entry whose cohort never fully holds the blob.

The module is exported from `packages/db-p2p/src/rn.ts` as well as `src/index.ts`, a deliberate deviation from the implement ticket's letter: `packages/db-p2p/test/entry-parity.spec.ts` requires the two entries to re-export an identical module set, so index-only would have failed that spec. Safe on that entry by construction — its imports are a subset of what `local-blob-service.ts`, already on the RN entry, imports, and `yarn check:rn` passes.

# Review findings

Read the implement diff (`ticket(implement): feat-blob-single-machine-service-and-pin-index`) before the handoff summary.

## Fixed in this pass

- **Two announces of one reference in flight together reported its durability twice.** `announce` read `durabilityOf`, then wrote and emitted, with nothing serializing the three steps — the exact hazard `BlobCopyDrain.settleRef` documents in `packages/db-p2p/src/blob/blob-copy-drain.ts` and prevents with a per-reference `KeyedSerialQueue` ("without a single point … both decide the class changed and emit the same value twice"). Because a blob reference is content-addressed, two SQL transactions committing identical bytes commit one reference, and each `await` in `announce` let the other's read land before the first write, so both fired `onDurability` with the same value — against the contract that the event is for a durability that *changed*. Reproduced before fixing (two events), fixed with a per-reference `KeyedSerialQueue` in `SingleMachineBlobService`, and confirmed the new test fails without it.
- **A refused scope threw out of the call instead of rejecting.** Introduced by the first cut of the fix above, which made `announce` non-`async`; the implementer's own "a scope the wire would refuse takes no hold" arm caught it immediately. `announce` is `async` again, with a comment saying why. Recorded here because it is evidence that arm earns its keep, not a finding against the implementer.
- **The announce scope refusal had a third verbatim copy.** `const problem = blobScopeProblem(scope); if (problem !== undefined) throw new RangeError(\`A blob announce has ${problem}\`)` stood in `blob-protocol-client.ts`, `node-blob-service.ts` and now `single-machine-blob-service.ts`. Rather than file the instance, extracted `assertAnnounceScope` into `packages/db-p2p/src/blob/blob-protocol.ts` beside `blobScopeProblem` and pointed all three at it, so a fourth announce path cannot come to spell the rule, or its message, differently. `LocalBlobService`'s private `assertScope` is left alone: it says "a blob **hold** has …", a different message for a different caller.

## Tests

- **Added** one arm to `packages/db-p2p/test/local-blob-service.spec.ts` for the pin index: the prefix filter, an empty prefix listing every pin, and an unreadable record skipped rather than failing the pass. - **Cut nothing.** Both arms the implementer wrote pin behaviour a reader cannot get from the types, and one of them caught a regression during this review.

## Checked, nothing to change

- `confirmed: 0` alongside `quorum: 'local'` is a shape `classifyBlobDurability` already produces for a networked node (its rule 2 returns `local` whatever `n`), so no consumer meets a new combination here.
- `setDurability` never creating a record is safe at this call site only because `holdOwed` created and flushed it first; the ordering is load-bearing and is now the reason the queue wraps both.
- `SingleMachineBlobServiceInit` matches what `2.702`'s `blobStorageFactory` returns, so the planned caller needs nothing added. Its lack of `sweepDelayMs`/`setTimer` is per the implement ticket; neither spec leaves a sweep timer armed, so it cost nothing here.
- The RN entry: the new `KeyedSerialQueue` import is pure, `entry-parity.spec.ts` passes including its Node-builtin source walk, and `yarn check:rn` — which the implement pass correctly deferred to review — passes.
- Docs read in full rather than assumed: `docs/blobs.md` §Holds, §The node's blob service, §SQL and §Lifetime, and `docs/debugging.md`'s `blob:store` row. All accurate against the code as landed. Updated the single-machine paragraph for the per-reference serialization, the new spec arm, and `assertAnnounceScope`.

## Tripwires parked (not filed as tickets)

- The implementer's two `NOTE:`s are left as they stand: the `listPins` full scan in `local-blob-service.ts`, and `confirmed` never being recomputed in `single-machine-blob-service.ts`. Checked the second for latency rather than taking it on trust — on a single machine the only way to reach a stored `confirmed: 0` is to announce a reference whose bytes were never put here, which no caller on this path does, so it is genuinely conditional.
- **New `NOTE:` at `SingleMachineBlobService.read`**, answering the question the implement handoff raised about `cohort-unreachable` versus `not-here` for a host with no cohort. Recorded as an accepted tradeoff rather than changed: `BlobUnavailableReason` in `packages/db-core/src/blob/errors.ts` *defines* `not-here` as the answer to `from: 'here'`, so re-using it here would contradict the db-core contract, and nothing in the repository branches on the reason (grepped: zero call sites). The note carries the revisit condition — if a caller ever decides anything from the reason, widen the documented meaning rather than overloading `not-here`.

No tickets. The one real defect was fixable in this pass, and nothing else cleared the filing bar: the remaining concerns are conditional (above) or already owned elsewhere. In particular, §SQL still reads "`plugin.blobs` is the node's blob service for the plugin's default network", which the new single-machine paragraph qualifies — `2.702`'s docs bullet already owns moving that bullet from intent to fact, so no arm was appended to it and nothing new was filed.
