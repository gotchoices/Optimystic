# Every log entry and transaction carries its HLC

Second of the three Stage 1 tickets of docs/crdt-sync.md §Migration Path. The implement stage (`ticket(implement): every-log-entry-and-transaction-carries-its-hlc`) put the hybrid logical clock value on every log entry (`LogEntry.hlc`, beside `timestamp`), on every transaction (`Transaction.hlc`, minted at commit after the read set is final, folded into the transaction id and the client signature, whose version is now `txsig:v2`), and on every pend a writer of this build sends (`PendRequest.hlc`, optional on the wire for older writers and for the re-send of a retained attempt). Four sites mint, all from the writer's clock through `clockOf(transactor)` or the node's own clock: `Collection.syncInternal`, `TransactionSession.commit` (through the new `TransactionCoordinator.clock` getter), the Quereus bridge's legacy transaction, and `OfflineQueue.enqueue`, which journals the value and re-supplies it on every drive; `applyInvalidation` mints the compensating entry's from `InvalidationContext.clock`. Everything else stamps what it is handed, so a retry at the same revision appends the same entry. A stored entry from before the field reads through `hlcOf` as its timestamp with the empty node id; a journal record from before it restores with its `queuedAt` the same way. No ordering changed.

The implement handoff's description of what landed, the decisions it asks a reviewer to weigh and its validation record are accurate; they are not repeated here.

## Review findings

**Read first, before the handoff:** the whole implement diff across the three packages, then every caller of the changed signatures in `src/` of every workspace (`addActions`, `addCheckpoint`, `addInvalidation`, `createTransactionId`, `clientSignaturePayload`, every `Transaction` literal, every `PendRequest` builder, every read of a `.hlc` field). The packages the typechecker does not cover (`reference-peer`, `demo`) build no `Transaction` and call none of the changed log methods, so nothing was missed there.

**Checked and found correct (by reading the code):**

- Identity rule. The HLC is minted once per write at all four minting sites and never per attempt: `stageAttempt` stamps `identity.hlc`, `applyActionsToCollection` stamps `context.hlc`, the head commit and the per-entry commit stamp the queue's value through `HeadCommitOptions.hlc` and `EntryCommit.hlc`, and a resumed attempt is re-sent whole. `TransactionSession.commit` mints after `getReadDependencies()` and before the id and signature are computed, so both fold in the final value.
- Wire. `pendRequestForBatch` in `packages/db-core/src/transactor/network-transactor.ts` spreads the request's other fields onto each per-coordinator batch, so `PendRequest.hlc` survives a split, and `pendMany` sends the requests whole. `TransactorSource.transact` omits the field when it has none rather than sending `undefined`, matching the other optional request fields.
- Legacy shapes. Three legacy derivations exist (a stored entry's `timestamp`, a journal record's `queuedAt`, and the validator's `stamp.timestamp` for a signature payload) and all go through `legacyHlc`, so a reader meets one shape. The upgrade-check fixtures pass unchanged, which is the evidence that nothing a release wrote stopped being read.
- Journal compatibility. `EntryRecordV1.hlc` is optional on the plugin's record and the record version stays `v: 1`: an older reader ignores the field, a newer reader fills a missing one. The queue's `Entry.hlc` is fixed for the entry's life, including across a `torn-not-saved` action-id renewal, which is right since the entry is the same local commit.
- The offline entry's HLC is minted at enqueue, so an entry queued for hours commits with an HLC below the rivals it commits over. This is the same accepted imprecision the `NOTE:` at `WriteIdentity.hlc` records for a retried sync, and for the replay stage it is the intended value: the entry's reads all happened before enqueue, so the HLC is above everything the write observed. No change.
- Error paths. A journal write that throws still unseals every segment with nothing queued (the HLC is minted before the journal write, which costs one logical tick and nothing else). `InvalidationContext.clock` is required, so a dispute host that builds a context without a clock fails to compile rather than appending an entry without one.
- Tests. The four extended cases in `retry-resends-identical-transforms.spec.ts` pin the one fact the whole-transform-set comparison cannot (that the entry carries an HLC from the transactor's clock at all), and the head-commit case pins that the supplied value is the one stamped. Both pay for themselves. The fixed-HLC fixtures in the log, transaction and signature specs are the right shape since none of those cases orders by the value; nothing was cut.

**Minor, fixed in this pass:**

- `packages/db-core/docs/logs.md` still showed the pre-options-object positional signatures for `addActions` and `addCheckpoint` (stale since before this ticket) and its entry type listing lacked `hlc` and `invalidation`. Updated to the current signatures and fields.
- The comment at the validator's legacy fallback (`packages/db-core/src/transaction/validator.ts`) justified passing the transaction through unchanged by the operations hash. The operations hash covers the staged tracker transforms only, never the log entry (`TransactionCoordinator.getTransforms`), so that reasoning did not hold. The decision itself is right for a plainer reason, which the comment now states: the derived value serves the signature check alone, and the transaction is never rewritten with a value its writer did not stamp. The handoff's sentence about the hashes was wrong in the same way; this ticket's text supersedes it.

**Major: none.** Every path that writes a log entry, builds a transaction or sends a pend was inspected and carries the value by construction through a required field; the one optional field, `PendRequest.hlc`, is optional for the two documented reasons only.

**Tripwires recorded (index only; the analysis lives at the site):**

- `LogEntry.hlc` is a required field while a stored entry from before it lacks one, so a reader that takes the field directly compiles and meets `undefined` on a legacy entry. The rule is at the field's doc comment and at `hlcOf` in `packages/db-core/src/log/struct.ts`: read through `hlcOf`, never off the field. The third ticket, the first reader, is written to that rule. Splitting the stored and written shapes into two types was considered and declined for one reader; if a second direct reader ever appears, make the split then.
- The re-send of a retained attempt carries no pend-level `hlc` (the `NOTE:` at `Collection.completeOwnEntry`'s re-send, with the remedy).
- A retried write keeps the HLC it was first minted with, which can sit below a rival it was re-staged over (the `NOTE:` at `WriteIdentity.hlc`).

**Considered and declined:**

- `TransactionSession.execute`'s temporary translation transaction mints a real HLC per statement, advancing the clock's logical count for a value nothing reads. Making the field optional for this one construction would weaken the type for every other; a `legacyHlc` placeholder would mislabel provenance. The tick is harmless. Left as the implementer chose.
- docs/crdt-sync.md §Stage 1 still describes the HLC as an extension of the stamp, which this ticket deliberately did not do (the value is on the transaction, minted after the reads). The §Migration Path intro and the transaction shape at the top of that document already show `hlc` on the transaction. The §Stage 1 rewrite belongs to `a-node-observes-the-hlcs-it-reads-and-stores`, whose TODO names it; not duplicated here.

**No ticket filed.** Nothing found reaches the filing bar: no current-release defect, and the one class-level concern (a direct read of `LogEntry.hlc`) has a single designed reader and a tripwire at the site.
