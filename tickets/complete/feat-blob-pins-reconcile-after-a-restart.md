# Blob pins reconcile after a restart

Second of three parts finishing the SQL side of blobs. Landed in `ticket(implement): feat-blob-pins-reconcile-after-a-restart`, with the review fixes below. `feat-queued-blob-pins-settle-with-their-transaction` landed before it; `feat-sql-columns-hold-blob-references` follows and consumes `isLive` and the per-backend `listPins` walk.

## What shipped

- **`SqlBlobPins.reconcile()`** settles every transaction pin whose transaction is not live, from committed state: the reference tree the pin's own label names either lists the reference or it does not. Listed → confirm the scope in the network's registry, announce, unpin. Certainly not listed → unpin, no announcement. Uncertain → keep every pin of that scope, log `blob:reconcile-uncertain`, retry on the next trigger. `put` pins of settled transactions are released outright. Nothing is read from the offline journal.
- **`releaseLanded`** is the announce-and-release tail shared by the queued settlement and the reconciliation — identical log lines, one code path — and answers `false` for a pin it kept.
- **`mayHoldStalePins`**: one boolean that makes a pass free unless something is actually owed, set by any arm that keeps a pin it could not release and by a store this process has not looked at, cleared at the start of a pass that then walks every known store. `reconcile()` coalesces like `OfflineRestore.run` (a request before a chained pass starts joins it; one during a running pass is chained behind it).
- **Three triggers, no timer**: `OfflineMode.restore()` awaits it; a reachability wake (`onGateChange`) fires it; a blob backend first resolving in this process fires it (`CollectionFactory.onBlobBackendResolved`, replayed so the subscription is order-independent).
- **Two orderings answered by `OfflineMode`**, so `SqlBlobPins` interprets no queue statuses: `holdsTransaction(id)` (queued, submitting, partially committed, or journaled and not yet put back — plus `OfflineRestore.holds`) and `reconcileReady()` (with a journal, false until `OfflineRestore.hasCompletedPass()`, which is set at the END of a pass so one that threw leaves it false).
- **`plugin.hydrate`** resolves the default network's blob backend after `restore()` and then awaits `blobPins.settled()`, so a restart's reconciliation has happened by the time it returns.
- **A pre-existing latent defect this work made reachable, fixed**: `OptimysticModule.createSchemaManager`'s schema-catalog options were assembled field by field and dropped `blobStorageFactory`. Since `CollectionFactory` remembers the FIRST options per transactor key and builds that network's blob store from them, and a restarted process reads the catalog before any table opens, the reconciliation built the network's blob store over fresh in-memory stores and read none of the machine's pins — silently, for the life of the process. Now spreads `tableOptions` and overrides what differs, as `openIndexTree` does; the test harness's own `bindingOptions` had the identical gap and was fixed the same way; `CollectionFactory.transactorOptions` carries a paragraph saying what callers owe these options.
- **Docs** — docs/blobs.md §SQL (the three answers, the three triggers, why it is usually free, the live-transaction and `reconcileReady` orderings, and the single-writer-per-machine assumption about a blob store), docs/internals.md under *Pinning what a commit references*, docs/debugging.md's `blob` row, plus the review's additions below.

## Review findings

**Read first:** the implement diff, then the handoff. Checked each arm of the committed read against `readCommittedTree`'s contract (a tree never written answers `exists: false, certain: true`, so an uncommitted transaction's pin is certainly unlisted and releasable); the `mayHoldStalePins` state machine against every setter and both clear points; the coalescing of `reconcile()` against `OfflineRestore.run`'s precedent, including dispose mid-chain; `isLive` against the commit path's actual ordering in `txn-bridge.ts` (`holdForCommit` → `sealIntoQueue`/`commitSession` → `endTransaction` → `settleBlobPins`); `listStalePins` against `parsePinLabel`'s three shapes; the spread in `createSchemaManager` field by field against `ParsedOptimysticOptions`' nine fields; and every doc the change touched or should have touched.

**Fixed in this pass:**

- *An undocumented log line the change extended* — `blob:pin-released` has four reasons in the code (`scope-not-committed`, `scope-dropped`, and the two this ticket added, `not-listed` and `put-outlived-transaction`) and none of them appeared in docs/debugging.md's `blob` row, which documents every other line of that namespace. Added, with what each reason means and why the line is not a `pin-release-failed`.
- *A changed public contract documented only in the blob docs* — `plugin.offline.restore()` now refuses an open transaction in EVERY configuration, journal or none (it awaits a reconciliation that waits for the open transaction to end, so awaiting it from inside one would wait for itself). docs/offline-sync.md §Restore after a restart owns that method's contract and said nothing about it, so a no-journal host reading only that section would meet the new refusal with no explanation. Added a paragraph there covering the reconciliation, why it runs after the pass and not before, and that the refusal is now unconditional.

**Test added — one, for the ordering that is the only way this mechanism can lose bytes:**

`leaves a journaled transaction's pins alone until the restore has read the journal` in `packages/quereus-plugin-optimystic/test/blob-pins-reconcile.spec.ts`. A commit is sealed into the queue with the cohort unreachable, so nothing of it reaches storage and its reference tree is never written — which means a committed read of its scope answers "lists nothing", *certainly*, the very answer that releases a pin. The process then restarts WITHOUT `hydrate`, and reading the blob service resolves the default network's store, which is itself a reconciliation trigger. The pin must survive that, because the entry goes on to commit; the test then hydrates (the queue holds it live from then on), opens the gate, and watches the entry's own settlement announce and release it.

Mutation-checked: with `OfflineMode.reconcileReady()` forced to `true`, the test fails on exactly that assertion (the pin is gone and its bytes are headed for the sweep) while the other three reconcile cases still pass — so `reconcileReady` had no test standing behind it before this one, and the three existing cases cannot stand behind it, since in each of them the reconciliation runs after the restore pass.

**Tripwires parked:**

- *A backend whose store cannot be resolved is left out of the walk* (`CollectionFactory.knownBlobBackends` logs it and continues), and a pass cannot tell it was skipped, so it clears `mayHoldStalePins` without having looked there. The pins stay — the safe direction — and because a failed resolution is not remembered, the next successful one announces the backend and re-arms the flag, so this self-heals for any network actually in use. `NOTE:` at `SqlBlobPins.reconcilePass`, with the remedy (have `knownBlobBackends` report the skip) if a network whose blob store can never be resolved is ever seen holding pins for ever.
- Already parked by the implementer and left as written: the per-pass listing cost and the "remember only the uncertain scopes" remedy, and the overlap between a pass and the tail of an online commit (both `NOTE:` at `SqlBlobPins.reconcile`); the empty blob store `plugin.hydrate` resolves for a host that uses no blobs (`NOTE:` in `plugin.hydrate`).

**Ticket filed — one, at rung 1:**

`tickets/backlog/debt-a-networks-storage-is-taken-from-one-collections-options.md`. The schema-options fix above is a point fix plus a prose contract; the class behind it is "`ParsedOptimysticOptions` conflates which collection is being opened with where its network keeps its data on this machine, so any hand-built options object recorded first for a transactor key silently and permanently misconfigures that network's storage". Both sites in the plugin now spread rather than assemble (grep for `: ParsedOptimysticOptions = {` finds exactly two, both spreads), so the hole is closed today and the ticket is for the representation change that would make it unrepresentable — holding a network's configuration apart from any collection's options. Rejected on the way there: merge-on-record in `getOrCreateTransactor` (does not fix the ordering that actually bit, since the reduced options are recorded first *and* the blob store is resolved before fuller options arrive); the ticket carries a loud-refusal fallback as the cheap alternative.

**Checked, nothing to change:**

- *The three implement-stage tests* — one per arm of the committed read, each writing the pin directly on the blob store under a dead transaction id (which is the state a crashed process leaves) and restarting into a fresh plugin. Each pins a distinct named answer in docs/blobs.md §SQL; all kept, none restates the implementation or verifies a mock. The handoff's own caveat about the `listed` case's `durability === 'local'` assertion being weak is accurate and already commented at the site — the `not listed` case (asserting `durability` stays undefined) is what makes a wrong announce fail, and the harness has no handle for a listed reference with no recorded durability.
- *The arms left untested by the implementer* — `ensure` vs the check-only `isRegistered` inside `releaseLanded`, the certainly-dropped scope, and the stray `put` pin. Read instead: all three are branches of one pass over one mechanism the queued settlement's tests already drive, and `scopeState` is reached identically from both callers. *`isLive` for a queued record* turned out to be covered already, by `blob-pins-queued.spec.ts`'s *settles a queued transaction restored after a restart from the pins' own labels* — that test's restart hydrates, so the reconciliation runs with the entry back in the queue and asserts the pin survived.
- *Steady-state cost* — confirmed by inspection of every setter: after one clean pass nothing re-arms the flag unless an arm keeps a pin or an unseen store resolves, so a reachability wake does no `listPins` and no committed read. One extra empty pass per process is real and deliberate (the flag is cleared at the start, so a backend resolving during the pass leaves it set); several backends resolving during one pass coalesce into exactly one extra pass, since `pendingReconcile` is live for the whole of the chained wait.
- *`reconcile()` coalescing and dispose* — a request during the idle wait joins the pending pass; one during a running pass chains behind it; a pass abandoned by `dispose` leaves `pendingReconcile` set, which is correct for a disposed object. `chained` swallows the rethrow out of `reconcilePass`, so `reconcile()` keeps its "never throws" contract and `restore()` cannot fail a hydrate.
- *`restore()` throwing before `run()`* duplicates `OfflineRestore.pass`'s own check, with the same message (now exported rather than duplicated). Deliberate and necessary — the eager check is what keeps the awaited reconciliation from waiting for itself — and the existing *restore refuses to run while a transaction is open* test still covers it.
- *A journal host that never hydrates* never arms `reconcileReady`, because every other `restorer.run()` call site is gated on `hasDeferred()`/`wantsRetryFor()`. Pre-existing and already louder: such a host never restores its journaled entries either, and the README tells hosts to call `hydrate` once.
- *`backendResolved(_backend)` ignoring its argument* — correct, as the handoff says: a pass walks every known backend, so the one that just resolved is in the walk by definition, and the parameter is the listener shape.
- *`parsed.kind === 'unstaged'` in `listStalePins`* is unreachable (`sql-unstaged/` does not start with `sql/`) but is what narrows the union before `parsed.stampId`; left alone.
- *The `docs/blobs.md` status-clause edit* the implement ticket had said to leave for part three — correct as made: left as written it would have claimed the restart reconciliation is still to be built.
- *Two processes over one blob store* — out of scope and now stated as an assumption in docs/blobs.md §SQL, alongside the same assumption about the block storage behind a `local` transactor.
- *Source hygiene* — `blob-pins.ts` is 731 lines and `blob-pins-reconcile.spec.ts` 208 (`wc -l`); not split, and well inside what this package's adapter files run to. The new comments carry constraints and consequences rather than narrating statements; no `any`, no new type assertion.
