# A block read distinguishes "never existed" from "I could not find out"

## What shipped

`GetBlockResult` carries an optional `unavailable?: 'unmaterializable' | 'peers-unreachable'`
field (`db-core/src/network/struct.ts`). Absent field = authoritative answer, so every producer
that never sets it (including `TestTransactor`) keeps its existing meaning. `BlockUnavailableError`
carries the block id and reason.

**Producers.** `StorageRepo.get` flags `'unmaterializable'` when a block reads as absent but this
node holds records proving it exists — the read-driven promotion refused for a missing base, or
`blockStorage.getBlock()` threw (truncated history / failed restore). That throw is now caught
**per block**, so a broken block no longer fails its whole batch. `CoordinatorRepo.get` flags
`'peers-unreachable'` when a locally-missing block's cohort consult *throws*; a merely-stale block
with a failed consult, and `skipClusterFetch` sync reads, stay authoritative.

**Consumers.** `NetworkTransactor.get` no longer counts a flagged entry as answered, so it earns
the second-chance retry an authoritative absent deliberately does not get, and merges per block by
`has a block > authoritative absent > unavailable`. `TransactorSource.tryGet` throws
`BlockUnavailableError` on a surviving blockless flagged entry, recording no read dependency — so
`Collection.open`/`createOrOpen`/`update` reject instead of inventing an empty collection. The
error is not a `StaleFailure`, so `Collection.sync`'s retry loop does not absorb it.

Docs: `docs/internals.md` (three-valued block answer + the `Collection.open` caveat this ticket
closed), `docs/transactions.md` (§ Unavailable reads), `packages/db-core/docs/transactor.md`
(the `ITransactor.get` contract).

## Review findings

Reviewed the implement diff (`bf7e3d2`) against the current tree, traced every in-tree consumer of
`GetBlockResult` (9 source files), read the wire path, and ran lint / build / `yarn test` /
`yarn test:integration`.

### Fixed in this pass (minor)

- **`Collection.bootstrapContext` ignored the new flag.** The log-tail read goes to the transactor
  *directly*, bypassing `TransactorSource`, so an unretrievable tail silently degraded to "no
  `ActionContext`" — the chain walk then could not see pending non-tail blocks and the collection
  read as though they had never been written. Exactly the silent-absence class this ticket exists
  to remove, one layer below the header. Now throws `BlockUnavailableError`; an unflagged tail with
  no committed revision still no-ops. Test: `collection.spec.ts` "open throws when the LOG TAIL is
  unavailable, not just the header".
- **`NetworkTransactor.getStatus` turned an indeterminate read into a verdict.** A flagged entry
  has an empty `state`, which the status mapping reads as `'aborted'` — a definite claim that
  someone's action did not land, derived from "I could not find out". Now throws. (No in-tree
  caller today; the wrong answer was latent, not live.) Tests: `network-transactor.spec.ts`
  "getStatus throws rather than reporting an indeterminate block as aborted" and its authoritative-
  absent control.
- **`ClusterMember`'s promise-phase stale-revision gate flipped fail-closed → fail-open.** Before
  the per-block catch, an unmaterializable block threw out of `validatePendOperations` and the
  promise handler; afterwards it returned `state: {}`, which reads as "no local revision, nothing
  stale here" — so a member that *could not check* would sign an approve. Now votes reject with a
  reason naming the block. Test: `cluster-repo.spec.ts` "rejects a pend whose block read came back
  unavailable".
- **`SpreadOnChurnMonitor` self-pruned on a guess.** Its `!blockResult?.block` branch untracks the
  block from the replication-spread set ("the block has left local storage"); a flagged entry hit
  that branch, so an indeterminate read silently shrank the replica set until some later re-commit
  re-added it. Now keeps the block tracked and logs. Test: `spread-on-churn.spec.ts` "keeps a block
  tracked when the repo could not determine whether it holds it".
- **Test gap the implementer flagged as open:** `Collection.update()` driven into an unavailable
  header mid-life is now pinned (`collection.spec.ts`), not just argued structurally. The shared
  test helper was generalized from a single wedged id to a live set so a block can be wedged after
  the collection is open.
- **DRY:** `promoteCorroborated` had re-inlined `readLocalRev`'s read to reach the entry; both now
  go through one `readLocalEntry` helper in `coordinator-repo.ts`.

### Checked, no change needed

- **The new-collection probe.** The highest-risk regression (flagging the never-existed header
  would deadlock collection creation) is pinned at storage, coordinator, and collection layers and
  passes; `createOrOpen` still creates, and an authoritative absent still costs exactly one
  coordinator round.
- **Consumers that were already conservative:** `BlockTransfer` push/confirm (treats no-block as
  failed / unconfirmed and keeps serving), `CoordinatorRepo.classifyStaleRejection` (unconfirmed
  stays a throw), `SyncService.buildArchive` (returned `undefined` before and after).
- **Wire round-trip.** `RepoClient`/`RepoService` carry `GetBlockResults` as JSON with no
  field-by-field codec (verified: no other file constructs a `GetBlockResult` from parts), so the
  optional field survives. Still no spec across a real libp2p stream — the argument is structural.
- **`rankOf` / retry accounting.** Ranking, the `missingIds` throw, and the `isRecordEmpty` filter
  all behave correctly for flagged entries; a flagged answer costs a second round trip by design.

### Tripwires recorded (conditional — not tickets)

- `storage-repo.ts`, at the `getBlock()` catch: the flagged entry drops `state.latest`, which the
  node *does* know (`getLatest()` never materializes). Empty state is what makes `CoordinatorRepo`
  treat the block as missing and consult the cohort — the repair this block needs. `NOTE:` at the
  site says what to change if a consumer ever needs the revision behind an unavailable answer.
- `coordinator-repo.ts`, at the consult catch (recorded by the implementer, confirmed accurate): a
  cohort that answers *silently* rather than throwing still yields an authoritative absent, because
  `ClusterLatestCallback` cannot distinguish "peer holds nothing" from a per-peer timeout. Fixing
  it needs a responders count in the callback contract; flagging no-quorum instead would break the
  new-collection probe.
- Not written up separately: the per-block `getBlock()` catch maps *any* read fault (including a
  genuine disk I/O error) to `'unmaterializable'`. The answer stays honest — callers still fail
  loudly — only the reason label is coarse; the existing comment at the site covers it.
