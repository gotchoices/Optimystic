# React Native storage commits groups through the journal

Complete. Fifth of five tickets from the retired plan `mobile-and-browser-storage-keep-the-durability-window` (GitHub #37). The one step left is upstream: the blocked `react-native-storage-syncs-once-rn-leveldb-can`, a release of `rn-leveldb` whose batch write takes a sync flag.

## What landed

The implement commit is `ticket(implement): react-native-storage-commits-groups-through-the-journal`.

**The driver surface says whether it can sync, and only writes batches.** `LevelDBLike` in `packages/db-p2p-storage-rn/src/leveldb-like.ts` gained `readonly canSync: boolean`, and `LevelDBWriteBatchLike.write` takes `{ sync?: boolean }`. The interface has no single `put` or `delete`: every write the package makes is a `batch().write(...)`, so no unsynced direct write can sit in an old LevelDB log file outside the journal's reach. The `rn-leveldb` adapter (`src/rn-opener.ts`) reports `canSync: false` and throws when asked to sync (a caller bug). The native module's declared shape is unchanged. The `classic-level` test adapter and the upgrade-check writer's adapter report `canSync: true` and pass the flag through; the writer's adapter keeps `put` and `delete` because published older builds call them.

**`LevelDBJournalStore` replaces the per-write driver** (`src/leveldb-storage.ts`). Reads are unchanged, same tags and encodings, so data an earlier build wrote reads unchanged, and an old database has no journal, so the first open applies nothing. The journal is tag byte `0x07` (`TAG_JOURNAL` in `src/keys.ts`): each record under its sequence as 8 bytes big-endian, the applied-through mark under the bare tag, which sorts first. An append is one unsynced batch; an apply is one batch over the data tags and the journal written `{ sync: db.canSync }`; `readJournal` is one drained scan that leaves out a record that does not decode or whose decoded number differs from its key's, and reads a mark that is not 8 bytes as 0. `durability` is `'power-loss'` when the handle can sync, else `'process-crash'`. `LevelDBRawStorage(db, options?)` is `KvRawStorage` over `WriteGroupDriver` over `JournalBatchBackend` over the store.

**`LevelDBKVStore` sits on a `WriteGroup<string>`** as the browser store does: `set` and `delete` resolve into memory, `get` and `list` read the overlay over the `TAG_KV` range, and a flush commits one batch written `{ sync: db.canSync }`. `loadOrCreateRNPeerKey` writes a new key as one such batch.

**Upgrade-check** keeps one `LevelDBRawStorage` and one `LevelDBKVStore` per open in both the reader and the writer, and closes both before the handle.

**Docs.** `packages/db-p2p/docs/storage.md` (driver table, journal-backend paragraph, rule 3 paragraph, survival table, kernel composition), `docs/correctness.md` §1.2 and the Theorem 6 backend caveat, a `docs/debugging.md` namespace row, and new README sections on persistence, durability, identity and tests.

## Behaviour held to in review

- On a handle that cannot sync (every phone today): a flushed group is one unsynced batch carrying the group's entries and the mark, nothing is appended, `whenDurable` settles at once, no deadline timer is armed, `durability` is `'process-crash'`.
- On a handle that can sync: a relaxed flush appends one unsynced batch on the journal tag alone; the overlay serves the group; the data tags do not hold it; one synced batch over data tags and journal applies it when the deadline timer fires. A strict flush applies at once.
- A second storage over the same handle applies the appended records at its open and reads them back.
- A batch that fails leaves the database untouched on disk and latches the storage with `StoreFailedError` carrying the batch's error.
- Process crash now loses an unflushed group whole, where the old driver kept each write individually. By design; the README and the survival table say so.

## Review findings

**Read first, with fresh eyes:** the whole implement diff, then every file it touches, then the contracts it plugs into (`JournalStore` and `JournalBatchBackend` in `packages/db-p2p/src/storage/journal-batch-backend.ts`, `WriteGroup` and `WriteGroupDriver`, `identityForHandle`, the journal record codec) and the browser sibling (`IndexedDBJournalStore`, `IndexedDBKVStore`) for parity.

**Checked, nothing found:**

- *Happy path and recovery.* Append, apply and read-back encodings agree (sequence as 8 bytes big-endian in the key and the mark; records through `encodeJournalRecord`). `planRecovery` over what `readJournal` returns behaves correctly for every malformed shape the store leaves out: a garbage or mis-numbered record key is treated as a gap, is never applied, and is deleted when its number is next reused by a strict or relaxed group's apply, so nothing accumulates and nothing can be misread later.
- *Error paths.* A failed batch latches at the backend and at the group above it; `StoreFailedError` never wraps another; the RN adapter closes its native batch in `finally` even when it refuses a sync. `readJournal` rethrows anything that is not a `JournalRecordDecodeError`, so a LevelDB fault is not mistaken for a damaged record.
- *Resource cleanup.* Every iterator is drained and closed (`drain`, and the byte-sum loop's `finally`); the store has no `close` by design, since the handle is shared; the conformance harness closes the storage before `reopen` closes the handle, so no idle timer can fire on a closed handle; the upgrade-check reader and writer close both stores before the handle.
- *Type safety and cross-platform.* `keyBytes` is an exhaustive switch over `StoreKey`; `TextDecoder` is built lazily for Hermes; `yarn check:rn` bundles and compiles.
- *Docs.* Every file the change touches, and the ones it should have touched, were read: the retired driver name appears nowhere outside `tickets/`, the retired plan slug appears nowhere outside `tickets/`, and `yarn lint:docs` resolves every citation. The blocked `react-native-storage-syncs-once-rn-leveldb-can` exists on the board.
- *Tests, as code under review.* Each added test pins a distinct contract: the conformance suite, rule 5 with on-disk state, the three untrusted journal shapes, the relaxed append-then-synced-apply sequence, recovery over real bytes, the cannot-sync phone path, the 8-byte mark above 32 bits, and the key-value store's one synced batch. None restates the implementation or verifies a mock, so none was cut. No test was added: the review found no defect and no unverified contract.
- *The handoff's own gaps.* The `rn-leveldb` adapter remains untestable without the native module; a fake native module would only verify the fake, so none was written. The fixture writer's LevelDB close is the same shape as the reader's, which the upgrade-check suite exercises.

**Minor, fixed inline:** one tripwire `NOTE:` added at `applyJournal` in `packages/db-p2p-storage-rn/src/leveldb-storage.ts`, moving the handoff's prose observation into the code: on a handle that cannot sync, every flush also puts the mark and writes a tombstone for a record never appended, unmeasured, with the remedy named should flush cost on phones ever show in profiles.

**Major, filed:** `backlog/debt-key-value-stores-share-one-write-group-shape`. `LevelDBKVStore`, `IndexedDBKVStore` and `FileKVStore` are three near copies of the same overlay logic around a `WriteGroup`, including the snapshot-before-await rule in `list` that each must restate. A shared base in the kernel retires that class for every backend, which is the first rung of the filing ladder; the tradeoff is recorded on the ticket. No open ticket claimed the site.

**Tripwires:** the `applyJournal` note above. The two existing `NOTE:`s (durability on a handle that cannot sync, and identity by handle object) were read and stand; neither revisit condition has tripped.

**Considered and declined:** the `readJournal` check that a record's decoded number matches its key is strictness beyond the browser store, but it is harmless (analysed above) and costs one comparison, so it stays. The duplicated nested close in the upgrade-check reader and writer is ten lines in a release script with no shared module to hold it, so it stays as well.

**Pre-existing failures:** none seen.
