# A blob remembers when it was last found unreferenced — complete

docs/blobs.md §Lifetime says a blob listed nowhere **at two passes a grace period apart** loses its `responsible` hold, and the same for an owed entry whose scope stopped listing it. Two passes a week apart can only be compared if the first leaves something behind that survives a restart. This ticket landed that something — a **mark**, the start time of the first counting pass that found a blob listed nowhere — on both the blob record and the owed entry, with the writes that set, clear and act on it, and the pure rule that turns a mark and a pass's start time into a decision.

The marks are inert until `feat-unreferenced-blobs-are-reclaimed` (`tickets/implement/2.86-…`) lands the pass that writes them. Nothing reads committed state, schedules anything or deletes anything here.

## What landed

**The pure rule — `packages/db-p2p/src/blob/reclaim-marks.ts` (new, 57 lines).** `DEFAULT_RECLAIM_GRACE_MS` (7 days), `MIN_RECLAIM_GRACE_MS` (1 hour), `judgeMark(mark, startedAt, graceMs): 'mark' | 'keep' | 'release'`, `resolveReclaimGraceMs(declared)`. No clock and no store, so the pass and the node factory share one copy of the bounds. `judgeMark` answers `'mark'` for no mark and for a mark that lies after `startedAt` (the wall clock having gone back — restarting the period is the direction that keeps the blob); `'release'` when `startedAt - mark >= graceMs`, so exactly a grace period releases; `'keep'` otherwise. `resolveReclaimGraceMs` throws `RangeError` naming `blobs.reclaimGraceMs` rather than clamping, in the shape of `resolveBlobCacheBudgetBytes`. Exported from both `src/index.ts` and `src/rn.ts`.

**The record field — `blob-record.ts`, `local-blob-service.ts`.** `BlobRecord.unreferencedSince?: number`, checked in `recordProblem` as `lastReadAt` is. The safety rule — every write that adds or removes a `responsible` hold clears the mark in the same record write — is carried by `recordAfterResponsibleHold` and the new `recordAfterResponsibleRelease` (which composes the generic `recordAfterResponsibleHoldRelease` and drops the mark when the release actually released something). `recordWithUnreferencedMark` / `recordWithoutUnreferencedMark` answer the current record by identity when there is nothing to do, so the record store writes nothing; `withoutUnreferencedSince` omits the property rather than setting it to `undefined`, so the record encodes and deep-compares as one that never carried it.

New door `BlobReclaimRecords` with `ResponsibleMark`, implemented by `LocalBlobService`: `responsibleMarks`, `clearUnreferenced`, `markUnreferenced`, `releaseResponsibleIfMarked`, `sweep`. `responsibleRefs` is now `(await this.responsibleMarks()).map(…)`, so one enumeration serves both and they cannot disagree. All three mark writes use the shape `releaseCached` uses — the change function is itself the condition, applied at that reference's turn in the record store's per-ref queue, so nothing is re-read first and no lock is added — and read "did it write" off `changeRecordIfDifferent` (added in review), since the record survives a mark write either way.

**The ledger field — `owed-blob-ledger.ts`.** `OwedBlobEntry.unlistedSince?: number`, validated in `isEntryFor` beside `recordedAt`; a malformed mark makes the whole entry read as absent and logged, never deleted by a read. `record` builds the stored entry field by field so a re-record drops the mark by construction; `addHolders` spreads, so a peer confirming it holds a copy does not restart the grace period. `clearUnlisted`, `markUnlisted` and `deleteIfUnlisted`, each inside `queue.run(ref, …)`.

**Flush policy** (corrected in review, see finding 1): a *mark* write is not flushed — one a crash loses costs a delay of one grace period and never a copy. A *clear* is flushed when it actually dropped a mark, because a lost clear leaves an over-age mark on a reference that is listed again, and the first later pass that finds it unlisted then reclaims with no grace period at all. `deleteIfUnlisted` flushes, because the pass deletes the entry and *then* releases the `owed` hold, and that ordering only holds if the delete is durable first.

## Review findings

Reviewed the implement-stage diff (`ticket(implement): feat-a-blob-remembers-when-it-was-last-found-unreferenced`) before reading its handoff.

### Major — fixed in this pass

**1. A lost mark-*clear* could reclaim a referenced blob with no grace period at all.** `clearUnreferenced` and `clearUnlisted` did not flush, justified at both sites by "a mark a crash restores costs a delay of one grace period, never a copy". That argument holds for the direction that *sets* a mark and is backwards for the one that drops it. Concretely: a pass marks a blob at T0; a writer references it again; a later pass clears the mark, and the clear is lost to a crash before any other write flushes the store; the reference is dropped again; the next pass reads the surviving T0 mark, finds `startedAt - T0 >= graceMs`, and releases a hold on a blob that was referenced hours ago. The two-pass rule §Lifetime promises is bypassed entirely. The same applies to `clearUnlisted`, where the release also drops the owed entry.

Fixed by flushing both clears — but only on the write that actually dropped a mark, read off the same write test the mark writes use. The cost the implementer was avoiding is kept: the expensive case is the pass that first marks thousands of blobs at once, and that direction still does not flush; a clear writes at most once per blob per mark. Both doc comments now state the asymmetry rather than the wrong half of it. Also corrected the one unmeasured magnitude in the same comments ("one store flush each per pass" → one per blob in the pass that first marks them).

That same claim had been carried forward into `tickets/implement/2.86-feat-unreferenced-blobs-are-reclaimed.md` under *Durability of marks*, where it would have told that ticket's implementer the clears need no flush. Corrected there, with a line saying not to simplify the flush back out.

**2. `reclaim-marks.js` was exported from `src/index.ts` but not from `src/rn.ts`, and `test/entry-parity.spec.ts` fails on it.** `src/rn.ts` carries a NOTE saying it re-exports exactly the same module set as `./index.js` with one substitution, enforced by that spec; React Native and browser consumers could not import `judgeMark` or the grace bounds. The handoff presented the omission as deliberate, on the grounds that `rn.ts` "stops at `single-machine-blob-service.js` and carries neither the owed ledger nor the reference check" — `rn.ts` in fact exports `reference-check.js`, `owed-blob-ledger.js` and `cohort-reaction.js`, in the same order `index.ts` has them. The implement stage could not have seen this: `tickets/rules/testing.md` reserves the full suite for review, and this spec is in it. Fixed by adding the export in the matching position; `entry-parity.spec.ts` passes, and `yarn check:rn` bundles and compiles the entry with the module in it. Not a pre-existing failure and not reported as one — it was this ticket's own diff.

### Minor — fixed in this pass

**3. The hold guard in `releaseResponsibleIfMarked` was justified by backwards compatibility, which AGENTS.md says not to worry about yet.** The site's comment read "a record written by a build that had the field and not that rule must not be read as a release that happened" — a reason AGENTS.md line 8 retires. The guard's *real* job, as the handoff said, was keeping the `wrote` flag honest: a matching mark on a holdless record would otherwise set the flag for a change function that returns the record unchanged. Routing the method through `changeRecordIfDifferent` makes identity answer that question, so the guard is gone and the contract is unchanged — `recordAfterResponsibleRelease` already answers a record with no such hold unchanged. Fewer conditions, and no reason left in the tree that a project rule contradicts.

**4. The `let wrote` closure was written out three times.** Extracted `LocalBlobService.changeRecordIfDifferent`, which is also where the "why not the change's before/after" argument now lives once instead of per caller. `markUnreferenced`, `clearUnreferenced` and `releaseResponsibleIfMarked` are each two or three lines.

### Conditional — parked as a tripwire, not a ticket

**5. `local-blob-service.ts` is 1150 lines (`wc -l`), up 184 on this ticket.** The growth is all in the module-private record-shaping block (pure `BlobRecord` in, `BlobRecord` out, touching nothing on the class), which is the natural extraction and a rename to perform, since nothing outside the module names any of it. No repo rule on file size and nothing measured as a problem, so no ticket. `NOTE:` at the top of that block naming the extraction and the measured count.

### Checked, nothing found

- **The field actually round-trips.** `encodeBlobRecord` is `JSON.stringify` and `decodeBlobRecord` returns the parsed object, keeping every property beyond the checked ones as found, so neither a whitelist nor a reconstruction drops the mark. The spec reads a mark back through the store, which pins it.
- **The mark cannot outlive its hold.** Read every record-shaping helper: `recordAfterPut`, `recordAfterPin`, `recordAfterUnpin`, `recordAfterCachedHold`, `recordAfterCacheEviction`, `recordAfterRead`, `recordCorrected`, `recordWithDurability` — none adds or removes a `responsible` hold, so keeping the mark across them is right (a `put` is not evidence of a reference). `grep -rn "responsible" packages/db-p2p/src` confirms no write to that hold outside `local-blob-service.ts`, so `holdResponsible` and the two releases are the whole set, and all three clear the mark in the same record write. `responsibleMarks` filters on the hold, so a stray mark is never enumerated.
- **`responsibleRefs` is now sorted where it was unordered.** Its three callers — `BlobAnnounceReceiver.resumePulls`, `seedHeldBlobs`, and `BlobCohortReaction` through `responsibleScope` — each iterate without depending on order. Their specs and the integration suite pass unchanged.
- **`judgeMark`'s arithmetic**, including the boundary in both directions and a mark equal to `startedAt`; **`resolveReclaimGraceMs`**'s rejection of `NaN`, `Infinity` and anything under the minimum.
- **The `exactOptionalPropertyTypes`-off handling.** Both omit-the-property helpers are right, and both the record and the entry assertions check the property is absent rather than `undefined`.
- **The accepted-tradeoff `NOTE:` at `judgeMark`** matches what docs/blobs.md §Lifetime *Accepted limits* already says about measuring the period on each holder's own clock, and carries a revisit condition. Its placement between the JSDoc and the declaration is this repo's established convention (`packages/db-core/src/blob/list-piece.ts`), not a detached comment.
- **Docs.** Read docs/blobs.md §Lifetime, §Holds, §Placement and the status line: nothing in them becomes wrong, because the pass they describe as unbuilt is still unbuilt and the marks are inert. 2.86 rewrites §Lifetime's second, third and fourth bullets as one piece naming both fields, so splitting that edit across the two tickets would have them both editing the same paragraphs. `yarn lint:docs` resolves all 869 citations.

### Considered and left alone

- **`clearUnreferenced` is a no-op on a record holding no `responsible` hold**, so a stray mark left by an older build is not swept by it. It is inert (`responsibleMarks` does not list it) and the next `holdResponsible` removes it; the planned contract was written this way and the code follows it.
- **`markUnreferenced` / `markUnlisted` answer `false` when the mark is already exactly `at`.** Honest, and unreachable from the pass, which only marks when `judgeMark` says `'mark'`.
- **`recordAfterHoldRelease` now has one caller** (`owed`). Kept as the shared generic rather than inlined; inlining would widen the diff past the behaviour that changed.
- **`deleteIfUnlisted` flushes even when it wrote nothing.** Matches `delete`, and the flush usefully makes any pending mark writes durable; narrowing it would save nothing a pass notices.
- **Two `LocalBlobService` instances over one key-value store** serialize these conditional writes only per instance. Not new, and `BlobRecordStore`'s own comment already states the one-service assumption; 2.86's restart test builds the second instance after the first pass ends, so it is not concurrent.

### Tests

**Cut none, added none**, and that is deliberate rather than an omission. The three tests that landed each pin something with real branching: `judgeMark`'s table and `resolveReclaimGraceMs`'s bounds are the specification rule; the two service tests pin the one failure mode these marks have (a mark outliving the thing it is about) over a real `LocalBlobService` and a real `OwedBlobLedger`, with no mock of anything this package owns. None restates the implementation or verifies a mock, so none met the bar for cutting.

Nothing found needed a new test. The flush correction in finding 1 is not observable without wrapping `MemoryKVStore` to count flushes, which is mocking a module this repository owns to make a test possible — the wrong layer. The entry-parity gap in finding 2 already had its general guard: `test/entry-parity.spec.ts` caught it, which is the class-level test such a finding would otherwise ask for. The contract half retired in finding 3 (a stray mark on a holdless record) is unreachable through the public API — every hold write clears the mark — so a test for it would have to write the record through `BlobRecordStore` directly to pin a state nothing can produce.
