# Push-state gossip sends only when the state changed

GitHub [#49](https://github.com/gotchoices/Optimystic/issues/49). Second of three tickets from the plan `feat-idle-cohort-gossip-costs-a-phone-little`; the first, `cohort-gossip-sends-a-frame-only-when-something-changed`, applied the same rule to the signed cohort gossip.

## What landed

`ReactivityPushStateGossipDriver` (`packages/db-p2p/src/reactivity/push-state-gossip.ts`) still ticks every 5 s and builds every live push state's bounded frame each round, but sends it only when the frame differs from the last one this driver sent for that push state, or when `reAdvertiseMs` (new dep, default `DEFAULT_WILLINGNESS_HEARTBEAT_MS`, 30 s) has passed since that send. The decision reuses `isGossipRoundDue` from the cohort gossip driver, comparing the hex SHA-256 of the clipped frame; memory is a `WeakMap<PushState, { key, at }>`. A `broadcastOver` that throws is not recorded, so the next round retries. The truncation log fires only on sending rounds (`reportClip`). `libp2p-node-base.ts` takes the default; only its `NOTE:` on the inbound membership gate's cost changed. `docs/reactivity.md` §Forwarder-cohort state gained the paragraph "Copied to the rest of the root group when it changes".

Commit: `ticket(implement): push-state-gossip-sends-only-when-the-state-changed`.

## Review findings

**Checked, by reading the implement diff and the code it depends on:**

- *Frame stability.* The comparison only saves anything if an unchanged push state serializes to the same bytes every round. `PushState.serializeGossip`, `ReplayBuffer.serialize` (sorted by revision) and `DedupeWindow.serialize` (Map insertion order) read no clock and do no time-based eviction, so an idle push state's frame is byte-stable. Confirmed.
- *Convergence (no ping-pong).* Re-read `ReplayBuffer.merge` (replace only on strictly newer `receivedAt`, then trim from the low edge), `DedupeWindow.merge` (insert-if-absent, `highest` only rises, then evict below window — an incoming key below the window is added and removed in the same merge, leaving the map unchanged), and `PushState.mergeGossip`'s scalar fields. Every field only grows, so a merge that adds nothing leaves the frame unchanged. The implementer's claim holds; the extended `replicates an origin entry …` test pins it.
- *Failure handling.* `broadcastOver` is synchronous and swallows per-peer send failures; only a resolver throw propagates, which the round's per-collection catch logs and which leaves `sent` unrecorded. Correct.
- *Resource cleanup.* The `WeakMap` is keyed by the push state object; a push state dropped after a rotation's drain releases its entry, and a rebuilt one for the same root is a new key that sends on its first round. No timer or listener added.
- *Production coord mapping.* `libp2p-node-base.ts` derives exactly one coord per push state (`reactivityRootCoord` of its `tailIdAtJoin`), so the "one push state, two coords" gap the handoff raised cannot arise in production.
- *Docs.* Read `docs/reactivity.md` (the new paragraph, the "Only for a root someone subscribed to" and late-subscriber paragraphs beside it), `docs/internals.md`'s push-state mention, `docs/debugging.md`'s log-namespace row and `docs/cohort-topic.md`'s gossip-cadence passages. None besides the new paragraph described a 5 s push-state send; nothing stale.
- *Tests.* The new cadence test pins the specified rule (first send, quiet inside the window, change sends, refresh at exactly `reAdvertiseMs`) on real branching — kept. The `reAdvertiseMs: 0` change to the `stop()` test is needed for that test to keep meaning anything — kept. No test restates the implementation or verifies a mock; none cut, none added.

**Found and fixed (minor):**

- The driver's `liveCollections` contract did not say a push state may be listed only once per round, although the send memory is keyed by push state alone and a second listing under another coord would be silently skipped. Documented the contract on `ReactivityPushStateGossipDriverDeps.liveCollections` rather than widening the key, since production never lists one twice.
- `docs/reactivity.md`: the new paragraph tied the send rule to the frame bound with a "so" that read as a non-sequitur; reworded ("Since that can be large, a round sends …").

**Major findings:** none. Nothing met the filing bar.

**Tripwires / accepted as-is (no ticket):**

- *Late joiner's wait* — a member that builds its push state after a change, or misses the one frame, now waits up to 30 s instead of 5 s; the ticket accepted this and `docs/reactivity.md` states it. No new site.
- *Sender-side cost* — every live push state is still serialized and hashed each round; the implementer's `NOTE:` at the comparison in `broadcastOne` names the remedy (a change counter on `PushState`). Left as parked.
- *Cadences not bound to host config* — `reAdvertiseMs` and the pre-existing `intervalMs` are not tied to the host's `willingnessHeartbeatMs` / `gossipIntervalMs`. Not a defect (both default to the same values) and the ticket did not ask for it; noted here only.
