## What was built

**Signatures are checked in the host, and the engine stays synchronous.** `verifyRegisterSig` and `verifyParticipantSig` are gone from db-core. A host with a node key authenticates a frame before handing it over, and a key-less host hands frames over unchecked, as it did before. That contract is written on `handleRegister`, `handleRenew` and `onRenew`.

**A frame's origin decides whether it is checked.** `handleRegisterFrame` takes `"self"` from the router's `handleLocally` (frames this process just built) and `"remote"` from the `/register` handler and the FRET activity handler. The activity handler is always `"remote"`, because FRET does not say who sent a frame.

**Register and probe** (`dispatchRegister`): a `rootKey` on a host serving no root groups is refused with no crypto, then the signature is checked (failure answers `no_state`), then the root-group read and engine creation, and the clock is read last. So a forged frame now reads no group and creates no engine. The rate limiter stays behind the signature; the reason is at `runGuards` and in docs §Anti-DoS.

**Withdraw and re-attach** (`resolveAuthenticatedRenew`): no holder, or a frame the freshness gate refuses, is answered without crypto. Otherwise it verifies, looks the holder up again, and runs with a clock taken after the wait. Plain pings and the renew batch check nothing.

**One shared check.** `peerSignatureVerifies` replaces `gossipSignatureVerifies` for gossip, register and renew.

**A diagnostic for the open question.** Each withdraw or re-attach this node answers logs on the `optimystic:db-p2p:cohort-topic` namespace: `privileged-renew kind=<reattach|withdraw> origin=<self|remote> answer=<result>`. It is documented in `docs/debugging.md`.

## How it is tested

- `inbound-signature-gate.spec.ts` drives register (stream and activity handler), probe, re-attach and withdraw through the real handlers with three forgeries, then the same frame correctly signed on the same host.
- `peer-sig.spec.ts` pins the control: noble accepts the crafted order-8 signature and the platform refuses it, so the table cannot pass vacuously if the two verifiers converge.
- `registration.spec.ts` pins that `refusalBeforeSignature` gives exactly the answer `onRenew` gives.
- `peer-key-signing.spec.ts` pins that a key-less host admits an unsigned register and acts on an unsigned withdraw, through the real handler.

## Known gaps

- **Nothing here runs Hermes or a phone.** The implementer ran libp2p's browser build under Node, and its WebCrypto path accepted an honest signature with a key decoded from a peer id. That shows the route works on Node's WebCrypto, not on any polyfill.
- **The verifier change saves nothing per check on a runtime with no WebCrypto Ed25519**, and no on-device saving was measured. There, only the self-frame skip and the early refusals help.
- **We did not reproduce the reported idle cost**, and its cause is unknown (see the reply below).
- **A phone may reach the promotion slope rule sooner.** A real phone whose arrival rate was limited by slow verification may now cross it earlier. This was not measured. `cohort-topic-scale-antiflood.spec.ts` needed `tPromoteLookaheadMs: 0` because the platform verifier let its burst run faster.
- **"No crypto" on the early refusals is by inspection.** No test counts verifications, since noble's `ed25519` object is frozen and no test-only option was added.
- **Other edge cases are by inspection, as the plan expected:** the second holder lookup, an engine or record evicted during the wait, and two frames finishing out of order.
- **`privileged-renew` only covers frames arriving through `handleRegisterFrame`.**

## Wording for the release note

Inbound cohort-topic registers, probes, re-attaches and withdraws are now verified with the platform's Ed25519 verifier instead of pure JavaScript, and a node no longer verifies frames it sent to itself. **Host requirement:** to get native verification on React Native, install WebCrypto Ed25519 on `crypto.subtle` (`generateKey`, `importKey` for both `raw` and `jwk`, `sign`, `verify`) before `@libp2p/crypto` is first imported. Without it each check costs the same as before. See the "Global polyfills" table in `packages/db-p2p/readme.md`.

## The reply owed to #55 (not posted; for the human)

Register and privileged renew frames now use the platform verifier. A phone needs WebCrypto Ed25519 installed before `@libp2p/crypto` is first imported, including `generateKey`, which is what the library probes for, and `importKey` for both `raw` and `jwk`. Without `generateKey` each check costs the same as before, and with only `raw` the node's own signing fails. A node no longer checks its own frames.

Plain pings were never signature-checked, at HEAD or in your 1.24.0. On a healthy two-machine group idling for about 375 s (Node, not Hermes) we measured zero signature checks. So the reported 306 ms means your S21 was receiving re-attach or withdraw frames while idle, which we could not reproduce. The verifier change may therefore not be what removes it.

Could you turn on `optimystic:db-p2p:cohort-topic` and report the `privileged-renew` lines, which give each frame's kind, origin and answer? Please also tell us whether your two phones' clocks differ. Differing clocks could make a re-attach fail the freshness rule after its signature was paid for, and the registration would then fail over again later, so the answer may be a failover bug rather than a verifier cost.
