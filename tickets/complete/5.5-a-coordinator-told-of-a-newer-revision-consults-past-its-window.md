# A coordinator told of a newer revision consults its cohort past its window

## What was built

`CoordinatorRepo.get` now has two triggers for consulting the cohort about a block it holds. The old one is the lazy read-repair window's time test (`shouldReadRepair`). The new one is the asker's floor: when the read carries `BlockGets.floors[blockId]`, the block's local revision is below it, and the floor is strictly above the floor this node last consulted under for the block, the read consults now, inside the window (`floorDemandsConsult`). The rest of the pass is untouched: `fetchBlockFromCluster` corroborates, promotes or acquires, the refreshed local answer replaces the entry, and `recordAheadClaim` and `flagUnconfirmedCurrency` run as before. The coordinator never refuses on a floor. A copy still below the floor after the pass is served exactly as today, so the asker's own check and second-chance retry are still what handle an unmet floor.

The stamp the window keeps per block was widened from a timestamp to `FreshnessStamp = { at, floorConsulted? }`, still on the one existing `lastSeenCommitMs` map. `markBlocksSeen(blockIds, floor?)` records the floor a pass consulted under; a stamp written without one (every commit-path call, and a read pass that carried no floor) clears it. The floor is threaded into `fetchBlockFromCluster` as a fourth parameter and recorded at exactly the four exits that already armed the window: solo-self, `cohort-too-small`, `local-current`, post-restore. The exits that deliberately leave the window unarmed record nothing, so a floored read after one of them consults again. `readRepairMode: 'off'` stays off. `'paranoid'` is unchanged.

`cluster-tx:read-repair-triggered` carries two new fields: `reason` (`'window'` or `'floor'`) and `floor` (present when the read carried one).

Landed in `ticket(implement): a-coordinator-told-of-a-newer-revision-consults-past-its-window`; the review pass added one tripwire `NOTE:` and one doc correction, described below.

## Tests

All in db-p2p. Each new unit test was run by the implementer with the predicate patched to always return false, and each failed then; the mesh case failed with exactly the `SyncRevisionStalledError` the ticket describes.

- `coordinator-repo-read-repair.spec.ts`, describe "a read carrying a floor above the local copy": three cases pinning the trigger and the served revision, the floor memory (same floor does not consult, higher one does, an unfloored re-stamp clears it), and the solo-cohort once-per-window bound.
- `floored-read-consults-a-lagging-coordinator.spec.ts` (new): three-member mesh, one member left one revision behind inside its window, a handle reading through that member and writing through another; asserts the refused write's retry lands fully durable, the lagging member logged a `reason: 'floor'` trigger for the tail, and its revision index names the writer's action at the lost-to revision.
- `superseded-own-write-is-saved.spec.ts` case 2: the rival now reads member B's storage directly rather than through member A's coordinator, because a coordinator-routed floored read now repairs A before the rival builds on it, which is case 1's shape rather than case 2's.

**Major.** None. The change is one predicate ORed into an existing decision, one optional field on an existing record, and a parameter threaded to call sites that already existed. No new map, no new lifetime, no wire change.

**Conditional, recorded as tripwires.** The failed-convergence-under-a-floor case above, at the post-restore exit. The other concern the implementer raised, that the unarmed exits record no floor and so a floored read after one of them consults again, already carries a `NOTE:` at `floorDemandsConsult` naming the bound and the remedy; nothing added.

**Considered and declined, no change.** A floor consulted under while the cohort was still at the local revision, followed by a commit at the floor's revision that this node misses, leaves this node serving the old copy for the rest of its window under that floor. That is the window's existing bound, one window at worst, and strictly better than before this ticket, when the node served the old copy for the whole window regardless of the floor. It also needs a narrow race: a floor is raised only from a walked entry or a confirmed `staleAt`, both of which mean the revision was already committed somewhere when the floored read was made, so the consult finds it unless the commit is landing on the cohort at that instant. Not worth a note beyond this line. The concurrent floored reads of one block both consulting before either stamps: pre-existing shape, inspection only, as the ticket allowed.
