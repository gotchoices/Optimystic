# A SQL commit reports its durability

GitHub issue #26 (the SQL layer dropped db-core's durability answer). Implemented in `ticket(implement): a-sql-commit-reports-its-durability`; the follow-up `a-sql-commit-learns-when-it-becomes-fully-held` builds on it.

## What landed

`register(...)` returns `onCommitDurability(listener): () => void`. After a SQL commit that wrote something, every listener is called once, synchronously, before `commitTransaction` returns, with a frozen `SqlCommitDurability`: `transactionId` (the transaction's `StampId()`), `durability` (db-core's `TransactionDurability`, per collection and `overall`), and `tables` (per `schema.table`, folded the same way `overall` is). Each of the bridge's three routes supplies the answer: session mode's `ExecutionResult.durability`, the batched legacy commit's coordinator answer, and the per-tree sweep's `sync()` answers folded by collection id. A commit that wrote nothing calls nobody; the sweep's `PartialCommitError` carries the committed half's `durability`. A throwing listener is logged and the rest still run.

## Review findings

Read the implement diff first, then the handoff; ran the plugin build, the full plugin `yarn test` (1007 passing, 14 pending, 0 failing, smoke ok), plugin `typecheck`, `eslint` on the touched files and `yarn lint:docs` — all clean.

**Correctness — one defect found and fixed.** The bridge recorded which tables each collection backs, but nothing removed a table's name on `DROP TABLE` (`forgetTree` covers only `DROP INDEX`, and a DROP has never unregistered the main collection). A table later declared over the same URI therefore reported its writes under both names. Reproduced (`expected [ 'main.Before', 'main.After' ] to deeply equal [ 'main.After' ]`), fixed with `TransactionBridge.forgetTable`, called from `OptimysticModule.destroy` and from the refused-CREATE cleanup through the vtab's `forgetInCommitReports`; the vtab's name now comes from one `qualifiedName` getter shared with `registerTree`. Regression test added ("a table declared over a dropped table's URI reports under its own name only"), confirmed to fail with the call removed.

**Checked and found sound:**
- Route coverage: every success path of `commitTransaction` reaches `reportCommitDurability` after the try/catch; every failure path throws before it, so no report follows a failed or partial commit.
- Folding: `writtenDurability` returns `undefined` for an empty map, so `transactionDurability`'s throw on an empty map cannot fire from the sweep; the coordinator never returns an empty answer; the per-table fold only builds non-empty maps. The unguarded `sqlCommitDurability` call can therefore throw only if db-core broke its "never empty" contract — not worth a guard or a tripwire.
- Two trees over one collection id (the shared-URI configuration) merge weakest-first through db-core's `recordCollectionDurability`, so an unknown class is never upgraded.
- The `DirtyTree.sync` type narrowing (`Promise<WriteDurability | undefined>`) and the four test doubles changed to `async () => undefined` — correct; widening to `void` would have let a double hide a missing answer.
- The db-core barrel now exporting `recordCollectionDurability` — accepted; re-implementing the merge in the plugin would duplicate a rule db-core owns.
- Listener isolation and snapshot-per-delivery mirror `StorageRepo.onAnyCollectionChange`. Logging a thrown listener on the debug namespace is consistent with that precedent; left as is.

**API — minor, fixed.** The README example imported `isFullyDurable` from `@optimystic/db-core`, while the plugin's own README promises hosts need no direct db-core import for the classes they classify commits by. Both plugin entries now re-export `isFullyDurable` (the entry-identity spec checks it is the same object from either), and the README example and the re-exports paragraph say so.

**Tests.** The five implementer tests each pin one route or one stated contract (sweep, batch, session, read-only, listener isolation); none restates the implementation or verifies a mock, so all stay. Left untested by design (by inspection only): `PartialCommitError.durability`, a collection with an unknown class making its table `undefined` (db-core's `transactionDurability` already pins that rule), unsubscribe.

**Docs.** README § Transactions (the new section, the dropped-table sentence, the `isFullyDurable` re-export), `docs/internals.md` § Commit Path and `docs/transactions.md`'s legacy-commit note all read correctly against the code; `yarn lint:docs` resolves every citation.

**Handed to the follow-up.** `reportCommitDurability` returns before building a report when no `onCommitDurability` listener is registered; a host that registers only the follow-up's `onCommitFullyHeld` would then never be followed. Appended as a note to the TODO of `a-sql-commit-learns-when-it-becomes-fully-held` rather than changed here, since the follower that needs it does not exist yet.

**Not done — pre-existing, outside this ticket:** a dropped table's collections stay in the bridge's collection registry (so session mode still iterates them). That predates this change and only the name half affected reports; no ticket filed, since nothing observable was found to depend on it.

**Tripwires added:** none. **Source hygiene:** `txn-bridge.ts` is 1,581 lines (`wc -l`); the extraction of `commitSession` moved code out of `commitTransaction` rather than adding to it, and the new report-building lives in its own small module.
