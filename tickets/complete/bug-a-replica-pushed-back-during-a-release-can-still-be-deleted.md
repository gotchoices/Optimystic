# A replica pushed back during a release can still be deleted

A node that releases a range records each released block in the released-block ledger, and the sweep later deletes a block only if it has not been written again since its release. The revision that comparison is made against used to be read by the ledger itself, *after* the release — so a replica a peer pushed back in the gap was recorded as the revision released, the sweep compared the block against itself, and the bytes the node had just accepted and started serving again were deleted.

The revision is now a **required argument** of the ledger write, supplied by the confirm step that actually handed the block over (`BlockTransferCoordinator.confirmReplicated` reads it off this node's own store when it pushes to the new holders). The ledger reads no block metadata at all, so there is no longer a path by which a revision read after a release can be recorded as the one released. Every write that lands after the confirm is therefore an advance, and a pushed-back block is kept.

Four signatures carry the value from the confirm to the ledger write, with nothing in between re-deriving it:

- `BlockTransferCoordinator.confirmReplicated` → `{ confirmed, unconfirmed, confirmedRevs }`, an entry only for a confirmed block whose revision was read.
- `BlockTransferCoordinator.handleRebalanceEvent` → `RebalanceReactionResult.releasedRevs`.
- `RingShiftDeps.onRelease(blockIds, releasedRevs)` — Phase C passes through what Phase B's confirm carried out; the `ReplicationConfirmer` interface gained the field to match.
- `ReleasedBlockLedger.record(blockIds, source, releasedRevs)` — the `heldRevisions` dependency is gone, so the ledger's whole deps argument is now optional.

`executeConfirm` captures the revision the **first** attempt read, not the confirming round's, guarded by a `revRead` flag so that "read, and the repo reported no latest" stays distinct from "not read yet". A write landing between two confirm attempts would otherwise be reported as the revision released, which is the defect; recording a revision that is too old can only make the sweep decline.

The stored entry shape is unchanged, so there is no migration. An entry written by the previous build still parses; it just carries a revision that may be a push's, so it keeps the old behaviour until that block is released again.

## Review findings

Read the `ticket(implement): bug-a-replica-pushed-back-during-a-release-can-still-be-deleted` diff before the handoff summary.

**Correctness — checked, no defect found.** Traced the value end to end rather than taking the handoff's word for it:

- `outcome.latest` on a `pushed` outcome is `result.state?.latest` from the one unpinned `repo.get` that `pushBlockToPeers` does *before* it dials any peer, so the captured revision is genuinely the one handed over, not a later read.
- The sweep's condition is `latest.rev > pastRev` (`StorageRepo.deleteBlockIfNotAdvanced`), so an older recorded revision can only move a block from "deleted" to "kept". The fix's conservative direction is the safe one, and the equal case (a peer pushing back a revision this node already holds, where `saveReplica` is a no-op and nothing was accepted) still deletes, as `storage.md` states.
- Both early returns in `confirmReplicated` (partition, non-positive floor), the synthetic "nothing to confirm" branch of `handleRebalanceEvent`, and the empty shed range in `confirmShedRange` all carry an empty map, and in each of those `released` is empty — so no released block can reach the ledger without its map having been considered.
- Every call site of the four changed signatures is threaded (grepped `confirmReplicated`, `ReplicationConfirmer`, `onRelease`, `new ReleasedBlockLedger`, `ledger.record`): two release paths, both inside the node factory's Arachnode gate. `replicateGrown` drives `executeConfirm` directly and ignores `confirmedRev`, which is right — nothing is released off the growth arm.
- The claim the fix now leans on more heavily — that bytes a keep leaves behind are offered again — holds for the case the fix creates keeps for: an advancing `saveReplicatedBlock` emits a collection change, and the node factory's subscription re-adds the block to the shared `ownedBlocks` set, so a pushed-back block is a shed candidate for the next shift. (The adjacent case, a block retained because its confirm *failed*, is already filed as backlog `bug-a-block-kept-after-a-failed-handoff-is-never-offered-again`; untouched here.)
- One residual, checked and accepted as-is: a confirmed block whose confirm read no `latest` records no revision, under which the sweep always declines and the bytes wait for the next offer. It needs a receiver running `requirePushCertificate: false`, because a push with no block meta carries no proof and a default receiver refuses it — so the block could not be confirmed in the first place. The safe direction, and already stated in both the `confirmReplicated` and `ReleasedBlockEntry.releasedRev` doc comments; no tripwire added, because a third copy of the same sentence would not tell a reader anything the two it already has do not.
