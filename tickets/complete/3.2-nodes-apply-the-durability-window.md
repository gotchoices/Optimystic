# Nodes apply the durability window — complete

Third of five tickets from the plan `durability-window-scales-with-cohort-size` (GitHub #37). Landed in `ticket(implement): nodes-apply-the-durability-window`; reviewed and finished here.

## What landed

- `StorageRepo.pend` and `StorageRepo.commit` take a third parameter, `StorageApplyOptions { proof?, syncWithinMs? }`. The commit's bare proof parameter is gone. `ICommitProofPersister` is renamed `ILocalApply` and declares both methods; `IDurableStorage { whenDurable() }` is the capability `ClusterMember` probes before writing the executed marker, and `StorageRepo.whenDurable()` forwards to its store.
- `endGroup(work, wrote?, flush?)` hands the flush options to the store. Only `pend` and `commit` pass a window, and only when their caller gave one (`groupFlush`); `cancel`, `recoverBlock`, `saveReplicatedBlock` and a latched `get` stay strict, and `flushBehindFault` is always strict.
- `recordDurabilityWindowMs(windowFor, record)` in `durability-window.ts` is the one place the cohort-size rule lives (`Object.keys(record.peers).length`, 0 without a window function). `ClusterMember` and `CoordinatorRepo` each take `durabilityWindowFor?` as a named component and use it for every apply that runs on a consensus record: the member's pend and commit, the coordinator's fallback pend after consensus and its fallback commit carrying the record's proof. `pendSolo` and `commitSolo` stay strict. A consensus `get` or `cancel` operation stays strict.
- The executed marker is written by `markExecutedOnceDurable` once the block store's `whenDurable()` resolves; a repo without it writes at once, a rejection logs and writes nothing.
- `KvUnderReplicationLedger` awaits `beforeRecord` at the start of `record`, ahead of the per-block queue; `createLibp2pNodeBase` wires it to a strict flush of the block store and hands the one `durabilityWindowFor` to both components.
- Docs: `packages/db-p2p/docs/storage.md` Invariant 6 (who flushes with a window, visible-before-durable risk, write order 8), one sentence in `packages/db-p2p/docs/repo.md`. Theorem 6 in `docs/correctness.md` is left to `durability-docs-match-the-window`, as planned.
- Tests in db-p2p over `MemoryBatchBackend({ deferSync: true })`: a windowed commit is answered and announced before its sync and a power cut takes it back, its strict control survives, and a solo commit on a node with a non-zero window is synced before it is acknowledged.

Until `file-store-syncs-by-the-earliest-deadline` lands no production backend defers a sync, so on a real node nothing observable changes yet.

## Review findings

Read the implement commit diff first (source, docs, tests), then the handoff, then the surrounding code at every seam the change touches: `WriteGroup.flush`/`whenDurable` and the five-rule flush contract, `WriteGroupDriver`, `KvRawStorage`, the production wiring in `createLibp2pNodeBase` (confirmed both components receive the raw `StorageRepo`, not the served-repo proxy, so the window and the proof do reach storage and `whenDurable` is present), `handleConsensus` and `applyCommitToStorage`, the coordinator's durability gate and both fallback arms, `noteReplicationShortfall`, and the ledger.

**Checked and found correct**

- Which groups carry a window matches the plan's table exactly. Solo paths, `cancel`, `recoverBlock`, `saveReplicatedBlock`, latched `get` and the consensus `get`/`cancel` ops are strict; the fault path flushes strictly whatever the group asked.
- `whenDurable()` after a relaxed `endGroup` covers the apply's batch: a relaxed flush resolves on `committed`, which settles after the batch is in the group's not-yet-durable list, including when a concurrent flush sealed the apply's writes first. So the marker cannot be written ahead of the apply on any ordering of concurrent groups.
- The executed-marker rollback path (apply threw) never reaches the marker write, so a rolled-back apply cannot leave a deferred marker behind.
- A behind member's reconcile (`saveReplicatedBlock`, strict) seals a new batch with deadline now, which hastens the window early on that node. Correct and bounded to the divergence case.
- The off-cohort coordinator's fallback pend takes the record's window (the handoff's first open question). Its pend record confers no durability, a loss turns the later fallback commit into the behind shape `tolerateLocalCommitDivergence` already handles on a durable majority, and the commit-side gate never counts an off-cohort copy. Keeping it relaxed is consistent with the plan's table; no change.
- A hostile record cannot inflate the window: `record.peers` is the signed cohort `validateRecord` checks, and the policy caps the size at the declared `clusterSize`.
- `beforeRecord` on the ledger: `record` is the only caller and `settle`/`satisfy` need no ordering. The concurrent per-block flushes of one commit share one sync in `WriteGroup`, which every production store runs over.
- `ILocalApply`, `StorageApplyOptions`, `IDurableStorage` and `DurabilityWindowFor` are exported through the package's `export *` barrels; no reference to the old name remains anywhere in the tree.
- Type safety and error handling: no `any` introduced, every rejection on the new paths is logged or propagated, and the fire-and-forget marker chain is `void`-prefixed with a `.catch`.

**Minor, fixed in this pass**

- `docs/internals.md` still said the commit's flush makes the write group "durable before anyone hears of it" and that the marker is written right after the apply loop; both lines now say what the code does. `packages/db-p2p/docs/cluster.md`'s one-line description of the marker likewise.
- `packages/db-p2p/docs/storage.md` now says that a windowed `pend` or `commit` flushes relaxed on a refusal too, and why that is fine (the handoff's last open question; the behaviour is right, the doc was silent).

**Tripwires recorded as `NOTE:` at the site** (conditional, not tickets)

- `markExecutedOnceDurable` in `packages/db-p2p/src/cluster/cluster-repo.ts`: `whenDurable()` answers for the store's latest committed batch, so an unrelated relaxed group extends the marker's wait by at most one window; fine while the marker is only post-restart dedup.
- The `beforeRecord` wiring in `packages/db-p2p/src/libp2p-node-base.ts`: one strict flush per block of a shortfall commit, coalesced by `WriteGroup`; a backend that synced on every flush regardless would pay per block.

**Tests**: the implementer's three tests pin the ticket's contract (the windowed loss, its strict control, and the solo path's strictness under a non-zero window) and none restate wiring; all kept, none added. The marker and ledger ordering stay untested by design (one `await` each at a seam, argued above and in the code comments). The 20 ms race in `durableSoon` cannot flake in either direction: the deferring backend never syncs unasked, and the strict arm's `whenDurable()` is already resolved.
