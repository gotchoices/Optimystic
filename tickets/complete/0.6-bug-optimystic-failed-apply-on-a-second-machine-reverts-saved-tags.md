## What changed

Quereus applies a tag change to its own catalog and announces it as `table_modified`. The listener used to overlay every tag of the engine's new schema onto the catalog record, on every such event, so this machine's whole view of the tags overwrote a record that could be newer.

It now saves what the event changed, one tag location (a *slot*) at a time, judged against the record. A slot is the table, or one column, named CHECK, foreign key, non-derived UNIQUE constraint or index.

- `tagChangesBetween` in `tag-overlay.ts` compares the event's old and new schemas. Only a slot both have counts, so an object that merely appeared (such as a CHECK re-added by an unwind) is not a tag change.
- `tagsToSave` in `catalog-only-change.ts` works out what the record should hold for each change: what it held before the change, for an undo, and otherwise the change's new tags. It saves the slot only when the record holds something else and has such an object. Inside an apply it records every forward change with what the record held then.
- `persistTags` takes a `record => slots` callback, so the decision and the write concern one record, and it writes nothing for an empty result.
- `followTableTags` returns before touching the catalog when the event changed no tags, so `analyze` no longer costs a catalog read.
- `saveTableTags` marks the table `written` in the batch only on outcome `'saved'`, so a change that staged nothing cannot lead a failed commit to re-persist this machine's older description.

## Behaviour

Sessions share one `MemoryRawStorage`. A declares `t` with `version = 1`, B hydrates, and A applies `version = 2`.

| Case | B does | Record afterwards |
| --- | --- | --- |
| R1 | applies v2 plus a step the module refuses | `version = 2`; B's own catalog goes back to 1 |
| R2 | `alter table main.t add constraint small check (a < 100)` | `version = 2`, plus `small` |
| R3 | `analyze main.t` | `version = 2` |
| R4 | column tag `k = 2` was set by A; B applies it plus the refused step | `k = 2` |
| R5 | applies v2 plus a new column, commit refused once, then retries | `version = 2` after the refusal and after the retry |
| R6 | B alone applies v2 plus the refused step | `version = 1`, since B's own change is taken back |
| R8 | A re-bodied a CHECK with tags `v = 2`; B applies that plus the refused step | the CHECK keeps `v = 2` |
| R9 (found in review) | applies v3 plus the refused step | `version = 2`, A's tag put back |

## Known gaps

- **Accepted by the ticket:** a failed tag save is not repaired by the next DDL. It stays out of the record until the next change to that slot, or until `apply schema` after a restart re-emits a declared tag, so an imperative tag edit whose save failed is lost at restart. The `NOTE:` is in `saveTableTags`.
- **Conditional, recorded as `NOTE:`s:** at `tagChangesBetween`, an adopted added CHECK or column keeps the record's tags even when this machine's declaration differs; at `tagsToSave`, a machine applying an older declaration overwrites a newer tag.
- **Filed for later:** see the three backlog tickets under *Major* below.

## Review findings

Reviewed the diff of `ticket(implement): bug-optimystic-failed-apply-on-a-second-machine-reverts-saved-tags`, then probed the cases it did not cover with a throwaway spec, since deleted.

### Fixed in this pass

- **A failed apply could still revert another machine's tag.** B holds v1, A saved v2, and B applies v3 plus a failing step. B's forward save overwrote v2, and the undo then wrote B's v1, losing A's v2: the defect this ticket exists to fix, reached by a machine one version ahead. The implement stage's `NOTE:` excused it as "a machine applying an older declaration", which does not describe this case, and the README's "an undo never removes from the record what that machine's apply did not put there" was false for it. `AdoptedChanges` now records, per tag change, what the record held, and `release` hands it back, so an undo restores exactly that. This also shortened `tagsToSave` by removing its separate adopted branch. Test: "a machine that overwrote a tag it had not seen puts that tag back when its apply fails", seen failing without the fix.
- **The tag half of `bug-optimystic-a-retry-after-two-refused-commits-leaves-the-change-out-of-the-record` is gone** as a result, since the undo of a machine's own change is now recognised rather than re-adopted, and nothing is carried to the retry. Test: "a retry after both commits of a failed apply were refused saves the tag change", seen failing without the fix. That ticket is narrowed to CHECKs and columns, and its CHECK reproduction was re-run and still fails.
- **Documentation.** `docs/internals.md` and the doc comments on `AdoptedChanges`, `schemaBatch` and `saveTableTags` said an undo always stays off the record; updated. The README's "never" now names its one remaining exception, the CHECK defect below.

### Major, filed to backlog

- `bug-optimystic-a-failed-apply-over-a-check-it-has-not-seen-removes-the-check`: the same sequence on a named CHECK leaves the record with no such CHECK at all, so a machine that only hydrates stops enforcing it. Verified by probe. It lives in the CHECK arm, which this ticket did not change. It names the invariant that retires the class: the undo of a catalog-only change leaves the record as it was.
- `bug-optimystic-an-imperative-tag-edit-on-an-older-machine-puts-its-other-tags-back`: `alter table … add tags (x = 1)` on B wrote `{ version: 1, x: 1 }` over `{ version: 2 }`. Verified by probe. A slot is written whole, but `add tags` and `drop tags` name only some keys, so the implement ticket's premise that a slot is the right unit holds only for `set tags`. Left for a ticket because comparing by key changes what `set tags` means on a machine holding older tags, which is a design decision. Cited by a `NOTE:` on `tagsToSave`.
- `bug-optimystic-a-retry-after-two-refused-commits-leaves-the-change-out-of-the-record`: already filed by the implement stage, kept and narrowed as above.

### Tripwires

- Parked as a `NOTE:` on `tagsToSave`: a forward save whose catalog read failed records nothing, so its undo is judged as a forward change and can write older tags. The implementer flagged this without a `NOTE:`. It takes a failed read followed by a successful one inside one batch.

### Checked, nothing found

- **Batch ordering:** moving `recordBatchEffect` after the `await` is safe. `endSchemaBatch` drains `catalogTagWrites` before it closes the batch, `beginSchemaBatch` drains before it opens one, and the DDL hooks drain at entry, so a save always runs in the batch its event belongs to and is not caught by another statement's checkpoint.
- **Manager joining the batch:** `createSchemaManager` still runs in the listener's synchronous part and joins an open batch. Exercised by a probe on a hydrated table with no instance, outside a batch.
- **Events with no real change:** Quereus's synthetic `table_modified` with one object as both old and new compares equal and saves nothing. Dropped and renamed slots appear in only one schema, so they are not changes.
- **Empty against absent tags:** `tagSlots` normalises through `copyTags` on both sides, so an empty set and no set compare equal and the adopted stack compares like with like.
- **Slot naming:** the `table` slot cannot collide with `list:name` keys, and names are lowercased as Quereus compares them.
- **Tests from the implement stage:** kept as written. Each pins a behaviour and most failed before the fix; the R6 test passed before it, and guards against a fix that never writes an undo. The `refusingCommits` and `expectRestored` moves changed no behaviour.
- **Type safety, resource cleanup, file size:** no `any` or eaten exceptions added, and no new resources. `optimystic-module.ts` is 6431 lines, already tracked by `debt-optimystic-vtab-class-is-too-big-to-review`, and this change does not move it materially.
