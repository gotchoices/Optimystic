# An abandoned commit retry now releases its transaction

## What landed

`ClusterCoordinator` keeps one entry per in-flight transaction in its `transactions` map. A transaction can end three ways — the commit finished with no retry pending, a live retry caught every peer up, or a retry gave up with peers still missing — and only the first two used to remove the entry. The third, the `cluster-tx:retry-abort` branch of `scheduleCommitRetry`, removed nothing: the `finally` of `executeClusterTransaction` had already run and skipped cleanup because a retry was pending at that moment, and `clearRetry` never fires on that path. The entry, its dead retry object and the persisted coordinator state stayed for the life of the process.

All three exits now go through one private `releaseTransaction(messageHash, reason)`. It cancels and clears any armed retry, then — on the same 100 ms deferral the completion path has always used, so an in-flight member response still finds a live entry to merge into — deletes the map entry and the persisted coordinator state and logs `cluster-tx:transaction-remove`. The new `reason` field on that line says which exit released it: `complete`, `retry-finished`, or `retry-abandoned`. After the change there is exactly one `transactions.delete` in the file, inside that helper.

Both guards around it are load-bearing and unchanged: the `finally`'s `if (!stored?.retry)` (a live retry still owns the release) and `clearRetry`'s `if (!state?.retry) return` (the ordinary all-peers-committed path calls `clearRetry` with no retry ever armed, and the `finally` releases moments later).

This was a memory and bookkeeping leak only. No timer leaked before and none leaks now.

## Review findings

Read the implement-stage diff (`4adb7cec`) first, then the surrounding code, before the handoff summary.

**Checked and clean.** Every call path into the new helper was traced by hand: the three terminal exits, plus the two that can reach `releaseTransaction` with no entry held. Only one `transactions.delete` exists in the file, so there is no fourth exit bypassing the helper (no staleness sweep touches this map). `scheduleOrClearRetry` — the only site that arms a retry outside recovery — runs inside the awaited `executeTransaction`, strictly before the `finally`, so no retry can be armed inside a release's 100 ms window and be orphaned by the delete. Cancelling an already-fired retry timer is a no-op in both the real `defaultSetTimer` (`clearTimeout` on a fired handle) and the test `FakeScheduler` (deleting an absent map key). The deferred cleanup timer is unref'd, so a discarded cancel handle cannot pin an idle process. Type safety: `ReleaseReason` is a closed union, no `any` added to source. Comments say why (which guard buys what, why the deferral survives a missing entry), not what.

**The load-bearing manual check, repeated rather than taken on trust.** Commenting out the `releaseTransaction` call in the abort branch and re-running the block fails exactly one test — `releases the transaction when the retry budget runs out`, with `expected { …(5) } to equal undefined`. Restored and re-verified green.

**Found and fixed in this pass — the `clearRetry` guard was genuinely untested, and could be pinned without asserting on a log.** The handoff called this the change's weakest spot and accepted it, reasoning that a test asserting on a debug log line is worse than the risk. That reasoning was right about logs but missed a non-log observable: without the guard the ordinary path arms *two* deferred release timers, not one. Deleting the guard and re-running confirmed all 36 tests still passed. One assertion — `expect(clock.pending).to.equal(1)` — in the existing `completes without retry when all peers commit` case now fails (2 against the expected 1) when the guard is removed and passes with it. No new test file, no new case, no log dependency. The `clearRetry` doc comment was updated to say the double release arms a second delete (not merely a second log line) and to name the case that pins it.

**Found and fixed in this pass — a doc the change should have touched.** `packages/db-core/docs/network.md` carries its own description of this same retry loop, including a delay table reading 2 s / 4 s / 8 s / 16 s / 30 s. The real defaults are 250 ms doubling to 4 s over five attempts, capped at 8 s (`commitBroadcastRetryInitialMs` and its three siblings, defaulted identically in `ClusterCoordinator` and `CoordinatorRepo`). Corrected the table, named the four settings and where they are defaulted, replaced "retry state is cleared" and "stops retrying" with the release that now follows each, and linked the section to the `Commit Retry Loop` section of `packages/db-p2p/docs/cluster.md` for the single release site. `yarn lint:docs` resolves the new link and anchor.

**Found, filed — one handoff claim about `recoverTransactions` is wrong, and the site has a real (dormant) defect.** The handoff said a recovered transaction whose persisted `retryState.attempt` is already at the budget "hits the abort branch and now releases". It cannot: recovery builds its in-memory entry with no retry attached, so `scheduleCommitRetry` reads no previous attempt and always schedules attempt 1. The persisted attempt count is written on every attempt and never read back — the budget restarts on every restart, and the recovery log line reports a different attempt number from the `cluster-tx:retry-scheduled` line that immediately follows it. A second, conditional arm sits at the same call: a recovered state carrying an empty pending-peer list would reach `clearRetry` with no retry armed and leak exactly the way this ticket's bug did, through the one door the new single release site does not cover (unreachable from anything this code writes, since an empty list is rejected before the state is stored). Both are pre-existing, both resolve at the same call site, and neither is reachable today — nothing in this repository supplies the `transactionStateStore` that makes `recoverTransactions` run. Filed as one ticket with two arms: `debt-a-recovered-commit-retry-restarts-its-budget`. The board was grepped first for the paths and symbols involved; five open tickets mention the coordinator file, none claims this site (the nearest, `feat-long-lived-pend-completes-as-members-appear`, lists `recoverTransactions` as context for a large feature that would rewrite recovery entirely, and burying a small accounting defect in it would lose it).

**Considered, not filed.** `releaseTransaction` arms its deferral whether or not an entry is held — correct and required (a hash already gone from memory can still have persisted state to delete), and preserved verbatim from the old `finally`. Reason `complete` is logged for a transaction that *threw* before ever reaching the commit phase; that matches the existing `cluster-tx:complete` line, which is documented as being written on the way out either way, so the reason names the call completing rather than the commit succeeding. The coordinator source measures 1513 lines (`wc -l packages/db-p2p/src/repo/cluster-coordinator.ts`), which is large for one class; this change adds about 30 of them, splitting it is a refactor well outside this ticket, and it clears no filing bar as a point ticket here — recorded as a measurement, not queued.

**Tripwires.** None recorded. The two conditional concerns found both resolve at the `recoverTransactions` call site, and the ticket filed above carries the conditional one as its second arm rather than leaving a comment at a site the ticket already names.

**Tests.** The implementer's two additions were read as code under review. Both were kept: the new case is the reproduction of the bug at the lowest layer that reproduces it (three-member cohort, third member's commit always throws, driven through all five default attempts and then past the 100 ms deferral, asserting the entry held while pending and then the entry, the persisted state and every armed timer gone), and the one line added to `retry succeeds when peer recovers` pins the finished-retry exit the refactor moved. Nothing restates the implementation or verifies a mock, so nothing was cut. One assertion was added, for the guard above. Switching the shared `beforeEach` to a real `InMemoryStateStore` is what lets the persisted-state assertions exist and is inert for the rest of the block.
