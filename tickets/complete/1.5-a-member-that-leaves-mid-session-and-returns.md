# What was built

`member-leaves-and-returns.spec.ts` runs on the in-process mesh (plain `yarn test`) at three machines with the production-shaped configuration from `util/node-count-mesh.ts`: default replication factor, machine count declared only as `repairCorroborationClusterSize`. Two arms share five sequential phases (`sequentialPhases`, so a failed phase fails the rest by name).

**Phases:**

1. **Whole group.** A, B and C each commit a row, coordinated by themselves. Each write is fully durable, every node's own storage holds every commit, and every node reads every row.
2. **C leaves mid-write.** A new harness hook drops C on the one delivery that would carry its commit vote for A's write's *final* commit step, after C has promised that step. The final step is the sweep of the write's non-tail blocks. The write is acknowledged as `{quorum: 'majority', confirmed: 2, cohort: 3, unconfirmed: [C], torn: []}`. A's and B's own storage hold the commit; C's does not.
3. **While C is away.** B's write is refused with the typed promise shortfall `{approvals: 2, peers: 3, needed: 3, rejections: 0}` and commits nothing. A and B still read every acknowledged row and do not read the refused one. C's storage is still behind.
4. **C returns.** C's own storage comes to hold the commit it missed, not just a copy it fetched, and C reads every acknowledged row. How it gets there differs per arm (below).
5. **B and C restart** over their own storage and identity. Every acknowledged row reads on all three machines. A fresh write from each machine is fully durable and readable on the other two. Every commit of the arm is in all three machines' own storage.

**Arms (how long C was gone):**

- **Short.** C returns while A still owes it the commit. With no read or write by C, A's scheduled commit retry (`ClusterCoordinator.scheduleCommitRetry`) delivers it. The wait is bounded by the retry schedule written out in the spec: 250/500/1000/2000/4000 ms, 7.75 s total, plus 1 s slack. The phase first asserts its own premise: C came back inside that schedule.
- **Long.** A restarts during phase 3, taking the retry with it, so C returns owed nothing. Phase 4 first asserts C is still behind, then C only reads. Full debug logs show no cohort consult and no fetch. C's reads promote the pending record C stored when it promised (the read-driven promotion in `StorageRepo.get`), because C holds the write's tail, which lists the action as committed.

**Harness seams (`src/testing/mesh-harness.ts`, the published `@optimystic/db-p2p/testing` entry):**

- `MeshFailureConfig.onClusterDelivery(targetPeerId, record)` sees every *remote* cluster delivery before `failingPeers` is checked, so a spec can change reachability at an exact protocol step. A coordinator's own member is never seen, since it is called in process, as in production.
- `Mesh.restart(node)` rebuilds the node's storage repo, member and coordinator in place, over the same `IRawStorage` and key. The old member is disposed. Every outbound call the old instance makes (cluster delivery, cohort consult, archive fetch) now fails, so a retry timer the old process owed cannot deliver after the restart and pass for healing. A mutation check confirmed it: with the guard off, the inert-instance test fails. A `NOTE:` at the site records the one path not severed: the old coordinator's in-process path to its own member.
- `mesh-harness-restart-and-delivery-hook.spec.ts` covers both seams (4 tests).

# Answer to the ticket's first TODO

Mid-test reachability already existed: `failingPeers` and `silentPeers` are read per call, and `setUnreachable` flips them. What the harness lacked was a way to act at a precise protocol step, and per-node restart. Both were added narrowly, with their own spec.

# Deviations from the ticket — reviewer should weigh these

- **Phase 2 is not "C unreachable, A's write refused".** At three machines every cluster transaction needs all three promises, so with C simply unreachable nothing commits while it is away. Phase 4 ("C reads what was committed while it was gone") would then check nothing. The only documented way anything commits without C is a transaction C had already promised: the commit phase needs 2 of 3, and so does the durability gate. So C leaves mid-write, and the ticket's refusal assertion moved to phase 3 (B's write while C is away), with the same typed-shape check the sweep uses.
- **Why the final commit step and not the tail.** Dropping C at the tail's step tears the write, and the stranded pending record then makes later writes burn the whole sync retry budget. See findings. That residual is owned by a backlog ticket, not by this healing scenario.
- **The "leaver wrote vs. only read" variant was not built.** In this topology every member is in every cohort and every write needs every promise, so a member that wrote holds nothing its peers lack; the two arms would differ only in which node coordinated phase 1. The absence-length arms were built instead, because they change *what heals C*, which is the property under test.
- **Restart in phase 5 is B and C** (C included, as asked), leaving A running with its in-memory state. The long arm also restarts A, in phase 3.

# Measurements

Five consecutive runs of the spec alone: **5/5 passed**, 6–7 s wall clock, 3.0–3.6 s per arm.

- Short arm: A's retry reached C **777–926 ms after C returned** (six runs including the full-suite run). This matches the retry attempt at 1.75 s after the drop.
- B's refused write: **855–1056 ms**, almost all of it the cancel loop the sweep already documented.
- Long arm: C's four reads took 0–1 ms and healed its storage.
- The first fresh write in phase 5 takes about 1–2.5 s, and later writes about 30 ms. This fits reservations left by B's refused promise round expiring after `CONFLICT_STALE_THRESHOLD_MS` (2 s). Inferred, not measured directly; observed, not asserted, not filed.

# Findings

- **Nothing failed to heal or to survive restart**, so no `fix/` ticket was filed.
- **Arm on `debt-unpromotable-pending-records-need-a-sweep`** (one run, measured): if C drops at the *tail* commit step instead, the write is acknowledged `majority` with `torn` naming the swept block. The sweep's pending record cannot be cancelled while C is away, since a cancel also needs 3 of 3. The next write from B then failed after **27.5 s** with `SyncRetryExhaustedError` ("pending conflict … unresolved rival action"), instead of the ~0.9 s promise shortfall. Writes recovered once C returned.
- **Doc drift fixed**: `packages/db-p2p/docs/cluster.md` said the retry schedule was "capped at 30 s intervals"; the code caps at 8 s (about 7.75 s in all). A paragraph now says what happens once the retry is gone.

# Known gaps (a floor, not a finish line)

- In-process mesh only; no real sockets at three machines.
- The rebalance monitor's cohort-growth push (`grown` arm) is not wired into the mesh, so it is not exercised here. Neither is read repair from the cohort: at three machines the returning member always holds its own pending record, so promotion wins first. A member missing that record — a larger cohort, or a member that left before the pend — would depend on read repair and its 10 s lazy window, and is untested.
- One fixed drop point (the final commit step), one leaver (C), one writer (A).
- `Mesh` gained a required `restart` member. Nothing in this repo builds `Mesh` literals, but an external consumer of `@optimystic/db-p2p/testing` that did would stop compiling.
- The short arm's premise depends on phase 3 finishing inside the 7.75 s retry schedule (it takes about 1 s). On a very slow machine it fails with a message naming that premise, not a heal failure.
- Phases share state, so `--grep` on a single phase fails; run a whole arm.

# Review findings

Reviewed commit `91a35261` (the implement diff) before the handoff: `mesh-harness.ts` (the `buildMember`/`buildCoordinator` split, `onClusterDelivery`, `restart`), the new spec and its harness guard spec, the helpers moved into `test/util/node-count-mesh.ts`, the sweep's switch to them, the `cluster.md` edit and both backlog arms.

**Checked, and found fine:**

- **Retry schedule.** Traced `ClusterCoordinator.scheduleCommitRetry`/`retryCommits`: five deliveries at 250, 750, 1750, 3750 and 7750 ms after the missed broadcast. That matches `COMMIT_RETRY_INTERVALS_MS` and the corrected doc.
- **Restart isolation.** A restarted node gets a new `StorageRepo`, member, coordinator and reconcile callback over the same raw storage. The old coordinator's `acquireBlockFromCohort` holds the old reconcile, whose `lifetime` is stopped, so it fetches nothing. Delivery targets and archive fetches look up `nodes` when called, so they reach the new instance. The old coordinator's retry timers are unref'd one-shots that stop after five failed attempts, so nothing leaks past the run. The one path not cut off (the old coordinator's in-process call to its own member) already has a `NOTE:` at the site.
- **Hook safety.** `record.message.operations` is a one-element tuple type, so the phase-2 hook's `operations[0]` cast can't throw inside a delivery.
- **Refactor (no duplicated code).** `recording`, `committed`, `durableHolders` and `expectPromiseShortfall` moved to the shared file and did not change. The sweep still uses its remaining imports (`SyncRetryExhaustedError`, `isConflictFailure`).
- **Short-arm premise.** No read or write by C (or by anyone else) happens during the wait, so the only thing that can heal C is A's retry. The `awayMs` precondition and the timeout use the schedule's constants.
- **Deviations from the ticket.** The implementer explains why phase 2 changed (at three machines nothing commits unless C has already promised), why the drop happens at the final commit step and not the tail, and why the "leaver wrote vs. only read" variant was replaced by the two absence-length arms. I accept all three: each keeps the property under test and says why.

**Found and fixed in this pass (minor, doc accuracy):**

- **Transaction state store.** `cluster.md` (§Commit Retry Loop) said the retry lives only in memory and a restarted coordinator owes nothing. That is only true without a transaction state store. A node built with `transactionStateStore` persists its retry state and resumes it on restart (`ClusterCoordinator.recoverTransactions`, `libp2p-node-base.ts`). The paragraph now says so.
- **The long arm's premise.** The long arm relies on the harness not wiring a transaction state store, which nobody had written down. `Mesh.restart`'s doc comment and the spec's module header now state it, so nobody reads the long arm as a claim about every production configuration.

**Tripwires:** none new. The restart path that isn't cut off already has its `NOTE:` in `Mesh.restart`, and the latency note on the refusal in phase 3 already points to backlog `debt-unpromotable-pending-records-need-a-sweep`.

**Major findings / new tickets:** none.
- The torn-write cost the implementer measured (27.5 s of retries when C drops at the tail step) is recorded as an arm on `debt-unpromotable-pending-records-need-a-sweep`, which is the right home.
- A restart that recovers state through a transaction state store is not tested, but that belongs to the persistence feature, not to this healing scenario. I recorded it as a known gap and did not file a ticket.

**Known gaps accepted as recorded by the implementer:** in-process mesh only; no read repair from the cohort and no rebalance push; one drop point; `Mesh.restart` is a new required interface member, which could break an outside consumer that builds `Mesh` values itself (nothing in this repo does; the only cast is `undefined as unknown as Mesh` in `block-archive-proof.spec.ts`).

**Validation after the fixes:** `yarn lint`, `yarn lint:docs` and `tsc --noEmit -p packages/db-p2p` pass. `yarn workspace @optimystic/db-p2p test`: **2804 passing, 62 pending, 0 failing**. The new spec's report from that run: short arm, A's retry reached C 805 ms after C returned; long arm, C's own reads healed it (4 rows in 1 ms); B's refused write took 985 and 1091 ms.
