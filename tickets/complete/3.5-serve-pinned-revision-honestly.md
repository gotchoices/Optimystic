# Complete: a peer asked for revision N answers with revision N, labelled N — or answers nothing

## What shipped

A block-repair fetch (`serveBlockArchive`) used to label the archive it served from
`state.latest` — the serving node's *newest* revision — regardless of which revision the bytes in
hand actually were. A request pinned at rev 1 from a node holding rev 2 came back as rev 1's bytes
under rev 2's number and action id. The asker's `BlockStorage.saveRestored` stores by action id, so
it wrote rev 1's content over its own good rev 2, and left rev 1 still unrecorded as held — so every
later rev-1 read repeated the fetch and the overwrite.

Two arms:

- **Structural.** `GetBlockResult.materializedRev?: number` became `materialized?: ActionRev` — the
  revision and its action id as **one** field, so no caller can hold half a label or pair one
  revision's number with another's action id. `serveBlockArchive` labels from
  `served = entry.materialized ?? latest`, and looks the commit proof up for that same revision.
- **Fail-closed.** When a revision was requested and the revision that would be served is *newer*
  than the pin, `serveBlockArchive` returns `undefined` (the "holds nothing" answer every caller
  already handles). After the structural arm this can only fire for a repo that reports no
  `materialized` at all — a plain `IRepo` describing its latest.

Producers updated: `StorageRepo` (both sites pass `blockRev.actionRev` whole), `TestTransactor`.
Consumers updated: `TransactorSource`, `sourceBlockMeta` / `sourceBlockCertification`.
`docs/internals.md` and `docs/repository.md` were rewritten for the new field and gained a bullet
describing the serve-or-refuse rule.

## Review findings

### Verified as sound (no change needed)

- **The `ActionRev` pairing really is structural.** Traced every producer. `StorageRepo` passes
  `blockRev.actionRev` through whole, and that value comes out of `materializeBlock`'s descending
  walk as a single object — the revision the bytes *are*, never a separately-fetched number.
  `TestTransactor` looks the action id up in the same `revisionActions` map its commit path writes,
  in the same loop that records the materialization, so the two halves cannot come from different
  commits; it emits the field only when both halves resolve. `NetworkTransactor`'s three-way merge
  and `CoordinatorRepo` forward peer entries verbatim (whole-object assignment, no reconstruction),
  and the repo protocol is plain JSON. No site can construct a disagreeing pair.
- **The refusal arm cannot fire in production, as the code comments claim.** `serveBlockArchive` is
  reached through `createServedRepoProxy`, whose `get` delegates to the *coordinated* repo — so I
  checked that `CoordinatorRepo.get` preserves `materialized`. It does: it starts from
  `localResult = await this.storageRepo.get(...)` and, because `serveBlockArchive` passes
  `skipClusterFetch: true`, skips the consult loop entirely and returns the storage entry untouched.
- **`served = entry.materialized ?? latest` is the right fallback.** `ArchiveServingRepo` documents
  a plain `IRepo` embedder as a supported shape and `materialized` as optional; refusing an
  *unpinned* read from such a repo would break the mesh harness, `served-repo-proxy`'s stated
  contract, and every test double, in exchange for nothing — an unpinned read's `latest` *is* the
  revision it served. Answers the implementer's review-focus question #1: keep the fallback.
- **The `state.latest` sweep the implementer asked for (review-focus #2) came back clean.** Every
  remaining read in `packages/*/src` was checked in context: `CoordinatorRepo`'s
  `promoteCorroborated` / `readLocalRev` / `flagUnconfirmedCurrency`, the stale-rejection classifier
  (an unpinned read), `ClusterRepo`'s member validation, `libp2p-node-base`'s `clusterLatestCallback`
  self-read, and the mesh harness's equivalent. All of them are asking "what is the newest revision
  this node holds?", which is exactly what `state.latest` means. None is labelling content.
  `libp2p-node-base`'s callback takes an optional pinned `context` but reports `state.latest` and
  looks its proof up for `latest.rev` — claim and proof agree, so it is consistent, not a latent
  mislabel.
- **Cross-package rename risk closed.** The implementer noted only two workspaces were checked. The
  only files outside `db-core`/`db-p2p` that name `GetBlockResult(s)` —
  `packages/quereus-plugin-optimystic/test/commit-gate.ts` and
  `packages/reference-peer/src/cli.ts` — use it purely as a pass-through return type and never read
  the field. Repo-wide `yarn build` and `yarn typecheck` confirm: clean across all 11 workspaces.
- **The pinned-read drop in `sourceBlockMeta` (implementer's third known gap) is right as it
  stands.** A push means "here is my latest replica"; the receiver lands it as a replica and the
  source's `latest` is what the cohort corroborates. Dropping the meta degrades to a rev-1 replica —
  a safe, already-handled outcome — whereas asserting would turn a caller bug into a crash on a
  background replication path. The reasoning is recorded at the site. Left alone.

### Fixed in this pass (minor)

- **`serveBlockArchive` built its synthetic context with a field that does not exist.**
  `{ rev, committed: [], pending: [] }` — `ActionContext` is `{ committed, rev, actionId? }`; there
  is no `pending`. It slipped past the excess-property check only because the literal is assigned to
  an intermediate `const` first. Harmless, but actively misleading at the one site this whole ticket
  is about: a reader could take it for the thing that suppresses the pending overlay. Removed, the
  context typed as `ActionContext` so the mistake cannot recur, and replaced with a comment saying
  what actually keeps the read on the committed path (omitting `actionId`). Pre-existing — it was
  there before this ticket — but it is one line at the site under review.
- **A test gap at the most common pin shape.** `ActionContext.rev` is a *collection-wide* revision,
  so it routinely sits *above* the revision at which a given block last changed — the everyday
  `served.rev < rev` case. Every existing `serveBlockArchive` test used `served.rev === rev` or the
  plain-`IRepo` fallback; nothing exercised the `materialized` path with a pin above the block's own
  latest. That is precisely where an over-strict guard (`!==` or `>=` instead of `>`) would pass
  every existing test and break normal reads. Added "a pin ABOVE the block's own latest serves that
  block's revision, labelled as itself" to `block-archive-proof.spec.ts`, asserting range, action id,
  bytes, and proof at pins of 2, 3, and 9 against a block whose latest is 2.

### Filed as an arm on an existing ticket (major)

- **`implement/restore-trusts-any-archive-a-peer-returns` (3.6) states an acceptance rule that would
  break the case above.** Its *Expected behaviour* says "an archive that does not cover the requested
  revision is rejected … `ensureRevision` throws". Read literally, that rejects the correct answer to
  a collection-wide pin: the peer serving rev 2 for a rev-9 pin produces a `range` of `[2, 3]`, which
  does not contain 9. Historical reads that work today would start failing hard. A second arm rides
  with it: `ensureRevision` merges `[2, 3]` into `meta.ranges` and never re-checks coverage, so
  `inRanges(9, …)` stays false and **every later pinned read at rev 9 re-runs the whole restore** —
  a network round trip and a `saveRestored` write each time, never converging. Bounded to blocks with
  a real hole below their earliest held revision (commits anchor an open-ended `[E, +inf)` span, so
  an up-to-date block never enters this path), but unbounded in repetition within it.
  Both predate this ticket — the archive was labelled `latest` before, and *that* range did not cover
  the pin either — so this ticket changed the label, not the coverage rule.
  Per the site-claim rule, `block-storage.ts` is already claimed by 3.6, so this went in as an arm on
  that ticket rather than a new one, with both directions the fix could take spelled out.

### Empty categories, and why

- **No tripwires recorded.** The one candidate — the repeated restore above — is not conditional
  ("fine now, matters if X"): it is wrong every time that dormant path runs, and it lands at a code
  site an open ticket is already about to rewrite. A `NOTE:` there would be stale within one ticket.
  It went into 3.6's body instead.
- **No new `backlog/` or `blocked/` tickets.** Nothing here needs a human decision, and every finding
  either resolved inline or attached to an open ticket at the same site.
- **No accepted-tradeoff `NOTE:`s were tripped.** Read the surrounding code at each finding's site;
  none carries one.

### Implementer's remaining known gap, left as-is

The corruption regression test ("never overwrites a revision the asker already holds") passes under
either single mutation, because the two arms independently prevent the corruption. That is honest
defence-in-depth, and each mechanism *is* individually pinned — the label by "serves the requested
revision labelled as itself" and "lands the requested revision", the guard by "serves nothing rather
than a mislabel" and now by the new pin-above-latest test that fixes its boundary. A test that ties
the corruption to exactly one mechanism would have to disable the other, which is a worse test than
the three that exist. Deliberately not added.
