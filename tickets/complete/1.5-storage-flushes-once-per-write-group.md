# Storage flushes once per write group

Reported in GitHub #37. Builds on `raw-storage-can-be-flushed`, which gave every `IRawStorage` a `flush()` and every backend a no-op one. Every backend's flush is still a no-op, so nothing changes on disk yet; `file-storage-pays-one-fsync-per-write-group`, `mobile-and-browser-storage-keep-the-durability-window` and `durability-window-scales-with-cohort-size` make it do real work and decide the policy.

## What landed

- `StorageRepo` is constructed over its raw store (`new StorageRepo(storage, { createBlockStorage? })`), so the store blocks write to and the store it flushes are one store. All call sites migrated; the `(storageRepo as any).createBlockStorage` swap in `createLibp2pNodeBase` is gone (the factory reads the reassigned `restoreCallback` binding).
- `StorageRepo.endGroup` ends every write group — `pend`, `commit`, `cancel`, `recoverBlock`, `saveReplicatedBlock`, and a `get` that entered a write latch — with one flush after the latches are released and before change events fire. A throwing group still flushes; a rejected flush after successful work makes the call throw and emit nothing.
- `applyInvalidation` takes `InvalidationContext.flush` and calls it after its latches release, before appending the invalidation entry.
- `KvUnderReplicationLedger` flushes its key-value store once per public call that wrote.
- `packages/db-p2p/docs/storage.md` Invariant 6 documents who flushes, the accepted visible-before-durable window, and the eight write orders crash recovery relies on; `docs/correctness.md`, `docs/internals.md` and `packages/db-p2p/docs/repo.md` updated.

## Review findings

Read the diff of `ticket(implement): storage-flushes-once-per-write-group` before the handoff, then the touched source and docs in full where they changed.

**Fixed in this pass**

- **A per-block fan-out could flush before a sibling block finished writing** (`get`, `cancel`). Both ran their per-block work through `Promise.all`, so the first block to reject sent `endGroup` straight to its fault-path flush while sibling blocks were still writing — and for `get`, before a sibling had even entered its latch, `wrote` was still false and no flush happened at all. Since a flush covers only writes resolved before it was called, the group's writes were not covered. Added `settleAllPerBlock` in `packages/db-p2p/src/storage/storage-repo.ts` (waits for every block to settle, then rethrows the first failure) and used it in both. Cost: a failing read now waits for its siblings before reporting. This was the handoff's first known gap; it is closed rather than accepted.
- Tests, in `packages/db-p2p/test/storage-repo.spec.ts` ("every write group ends with one flush"): the flush runs once and before the change event, and a read that took no latch does not flush; a rejected flush makes `commit` throw and announce nothing; and a regression test for the defect above (it fails without the fix, and saw no flush at all). These pin the ordering contract Invariant 6 states, on the branches `endGroup` actually has.
- `docs/internals.md` *Change Notification*: the flow diagram and the "events fire after" bullet now include the flush. `packages/db-p2p/docs/storage.md` says that per-block groups wait for every block to settle.

**Checked, nothing to change**

- Every block-storage writer goes through `StorageRepo` or `applyInvalidation`: `withBlockWriteLatch` / `acquireBlockWriteLatches` and `new BlockStorage(` appear nowhere else in production source. `libp2p-node-base.ts` uses the raw store elsewhere only to read (`StorageMonitor`, `listBlockIds`).
- `pend`'s validation runs outside the group and writes nothing. Its early refusals are inside it and flush, as the doc says. The policy-`r` `Promise.all` inside the hold only reads. `dropUnpromotablePendings` catches errors per block, so it cannot reject early.
- `commit`, `saveReplicatedBlock` and `get` emit only after `endGroup` resolves. The stale early return still carries `collectionBlocks`, which is empty at that point.
- Ledger: every write path flushes after the per-block queue is released. `delete` flushes even when it removed nothing; that is harmless. `record`'s flush is also driven by eviction. The doc claims about `PersistentTransactionStateStore` (fire-and-forget `markExecuted`) and the `materializeBlock` re-cache match the code.
- Type safety and hygiene: no new `any`; the removed `as any` swap was the only one. `storage-repo.ts` is 1932 lines (`wc -l`), and the extraction into `pendUnderLatches` and `commitUnderLatches` did not grow it meaningfully.
- Checked again: `yarn lint:docs` is clean, eslint passes on the changed files, and `yarn workspace @optimystic/db-p2p build` (tsc) is clean. db-p2p `yarn test` gives 3313 passing and 70 pending. The integration suites, the other packages and `check:rn` were not re-run here, because this pass changed only internal failure-path behaviour in `storage-repo.ts`, a comment and docs. The implement run ran the whole set except quereus-plugin integration and `check:rn`.

**Considered and left as is**

- `applyInvalidation` flushes only on its success path. `StorageRepo.endGroup`, by contrast, also flushes behind a fault. I kept the difference. A throwing invalidation reports nothing, and its partial writes are covered by the next flush any group calls (a flush covers every resolved write, whoever made it). That leaves only the crash-before-next-flush case, which is the "revisions with no entry" direction the existing crash-window `NOTE:` already accepts.
- `InvalidationContext` takes `createBlockStorage` and `flush` as two separate fields — the very split `StorageRepo`'s constructor change removed. The dispute path has no composition root, so nothing can wire them to different stores today. This is below the filing bar; whoever wires dispute should build both from one store.
- The visible-before-durable window, where concurrent groups read each other's writes before the flush, is documented as accepted under Invariant 6. Whether it holds past a process crash depends on each backend keeping rule 3 (what survives is a prefix of the resolved writes), which is the downstream backend tickets' job.

**Tripwire**

- `applyInvalidation`'s entry append: the entry's own durability belongs to the store the log writes through. If a composition root backs that log with a store written directly, not through `StorageRepo`, it must flush after the append before reporting `applied`. Parked as a `NOTE:` at the append in `packages/db-p2p/src/dispute/invalidation.ts`.

**Tickets filed:** none. Every finding was fixed in this pass or is conditional.
