# A partial index holds only the rows its predicate admits

Suggestion 3 of GitHub [#42](https://github.com/gotchoices/Optimystic/issues/42). Before this change every maintained index tree got an entry for every row, ignoring the persisted `where` clause of `create index … where …`. Landed in `ticket(implement): optimystic-partial-index-holds-only-the-rows-its-predicate-admits`.

## What it does

- `IndexPredicate` (`src/schema/index-predicate.ts`) wraps Quereus's own `compilePredicate`; only SQL TRUE admits a row. `repositioned` remaps compiled column positions after a catalog-only DROP COLUMN instead of recompiling.
- `IndexManager` compiles one predicate per partial index (constructor and `setSchema`), remaps them in `repositionColumns`, and exposes `admits(index, row)`. Insert, delete and update staging skip rows an index does not admit; `updateIndexEntries` stages the delete of an admitted old entry and the insert of an admitted new entry in one action, delete first, and nothing when the two tree keys agree.
- `addIndex` compiles a new partial index's predicate before anything is written, so an unsupported `where` clause (a function call, a subquery) is refused at `CREATE INDEX`.
- Backfill stages only admitted rows; `verifyIndexes` expects entries only for admitted rows and reports an entry for a non-admitted row as the new orphan reason `outside-predicate`.
- `getBestAccessPlan` never plans through a partial index. A partial declared index never enforces, or suppresses the tree for, a full UNIQUE constraint (`holdsEveryRow`).
- The legacy per-tree commit sweep (`sweepDirtyTreesLegacy`) skips a tree with nothing staged rather than paying a refresh for it.
- Docs: `docs/debugging.md` reason table and bullets; README Limitations bullet.

## Review findings

Read the implement diff first, then the handoff; read `compilePredicate` in `@quereus/quereus/src/vtab/memory/utils/predicate.ts`, `getBestAccessPlan`, `backfillIndexTrees`, `sweepDirtyTreesLegacy`, `republishColumnLayout`, `positionAfterRemoving` and `dropIndex`.

**Correctness — checked, nothing wrong found.**
- `updateIndexEntries`' four cases (in→in, in→out, out→in, out→out) and the equal-key skip are correct; a PK move takes the same branch with different keys. Unique guards never land on a partial index, since `resolveEnforcingIndex` filters them out and so `guardedUniqueIndexes` never names one.
- `admits` defaults to true for unique-enforcement descriptors (no predicate is ever registered for them); `_uniq_` names are reserved, so there is no name collision in the predicate map.
- The planner has no other path that selects a secondary index (no ordering-only plan), so the one `continue` in the secondary-index loop is enough.
- `compilePredicate` reads only the columns it records in `referencedColumns`, which is what makes the sparse row `compiledLayout` builds after a remap safe.
- `classifyEntry`'s new branch (`outside-predicate`) runs only when the entry's own row implies it exactly, so it never masks `malformed`, `stale-value` or `no-row`.
- Commit-sweep skip: `isStaged` is true for an invented tree (its header and root are tracker transforms), so an invented index tree is never left uncommitted by the skip. A skipped tree goes into the restore set and into `PartialCommitError.unpersisted` on a later failure; restoring a tree with nothing staged is a no-op, and the degraded latch is bridge-wide, so the names are diagnostic only. Before this change such trees were listed the same way when they sat after the failure point. Left as is.

**Test coverage — one contract was unverified; test added.** The DROP COLUMN remap (`IndexPredicate.repositioned`, the `positions` map) had real branching logic and no test. Added *keeps evaluating the predicate after a dropped column ahead of the one it reads* to `test/partial-index-maintenance.spec.ts`: dropping a column ahead of `Flag` moves it from position 3 to 2, and later inserts and updates must still leave the index clean. Mutation-checked: with `repositioned` returning the unremapped predicate, the case fails (an `outside-predicate` orphan, missing entries), and passes when restored. The implementer's tests were kept: the maintenance case is the reproduction, the backfill and planner cases each pin a separate path, and the integrity case is the only pin on the new orphan reason. Nothing restates a mock.

**Tripwire recorded (no ticket).** A catalog record that lists a partial index whose predicate does not compile — only reachable from a build without the new `CREATE INDEX` check, or a future Quereus with a narrower `compilePredicate` — makes every initialization of the table throw, including the one `dropIndex` runs before removing the index, so the table cannot be repaired through SQL. Backwards compatibility is out of scope for this project for now (AGENTS.md), so this is a `NOTE:` at `compileIndexPredicates` in `src/schema/index-manager.ts` naming the remedy (let `dropIndex` remove a partial index without compiling it).

**Inspection-only items from the handoff, judged.** The plugin's own `columnDropBlockers` not checking predicates matters only for a partial index this manager maintains but Quereus's catalog does not hold; the manager only maintains indexes in this engine's catalog, where Quereus's `predicateReferencesColumn` already refuses the drop. `setSchema` recompiling against the record's column list shares the existing `bug-optimystic-stale-hydrated-table-rewrites-the-shared-catalog-record` exposure and adds none. Two-node with an older sibling: covered by `outside-predicate` reporting. No action.

**Efficiency, resource cleanup, error handling, type safety.** Predicates compile once per schema change, not per row; `admits` is one map lookup plus the evaluator. No resources are opened. The compile failure is rethrown with the `QuereusError` as `cause`, not swallowed. No `any` was added. Nothing to change.

**Hygiene and DRY.** `storedToColumnSchema` moved to a module export so `IndexPredicate` and both earlier callers share one conversion. Comments state constraints, not narration. `index-predicate.ts` is 72 lines.

**Docs.** `docs/debugging.md` and the README cover the new behaviour; grep found no other doc describing partial indexes. No doc change needed beyond the implementer's.

**Validation.** `yarn build`, `yarn typecheck`, `yarn lint`, `yarn lint:docs` clean. Full `@optimystic/quereus-plugin-optimystic` suite: 1181 passing, 14 pending, 0 failing (includes the added case). `yarn test:integration` was not run.

## Known consequences (accepted)

- A query that used to seek a partial index now scans the table (backlog `feat-optimystic-plan-through-a-partial-index-whose-predicate-the-query-implies`).
- Entries older builds wrote for excluded rows stay, and deleting such a row leaves its entry; `verifyIndexes` reports them as `outside-predicate`.
- A table that enforced a full UNIQUE through a partial declared tree gets a `_uniq_` tree at its next initialization, filled on first probe.
- Partial UNIQUE enforcement remains out of scope (backlog `bug-optimystic-unique-ignores-collation-and-partial-predicate`); `IndexManager.admits` is the evaluator that ticket needs.
