# SQL statements are built only when something reads them

Part of GitHub #63; the measurements and the split are in the completed ticket `a-consensus-record-is-serialized-once-per-delivery`. Implemented in `ticket(implement): sql-statements-are-built-only-when-something-reads-them`.

## What changed

Quereus builds a SQL statement for each row a write touches (blobs as `x'…'` hex) whenever the vtab's `wantStatements` is true. Only a session-mode transaction reads those statements: they become its replicated record, which validating members re-execute. Legacy mode, the default, pends bare transforms and never read them. Building them was 12% of the CPU of an 8 × 256 KiB blob commit.

- `TransactionBridge.recordsStatements()`: while a transaction is open, `this.session !== null`. While none is open, `isTransactionModeEnabled()`, the mode the next transaction will begin in.
- `OptimysticVirtualTable`'s constructor replaces `this.wantStatements = true` with a getter reading `recordsStatements()`, defined on the instance with `Object.defineProperty`, because Quereus's `VirtualTable` declares `wantStatements` as an ES2022 class field, which would shadow a prototype getter.
- Quereus reads `vtab.wantStatements` per row at all four DML sites in `@quereus/quereus/src/runtime/emit/dml-executor.ts`, so a host that configures session mode after a table opened gets statements from its next transaction.
- docs/transactions.md §Secrets and the replicated statement record says when the statement is built and why.

**Deviation from the plan, kept:** the plan's rule was `session !== null` alone. That drops the first row's statement in session mode when the table's first touch in a `Database` was a committed read: the row's statement is requested before `update()`, and it is that `update()` (`ensureConnectionRegistered`) which begins the bridge's transaction and session. With no transaction open the getter therefore answers "session mode is configured". A transaction already open keeps the mode it began in.

## Tests

- New: `session-mode-commit.spec.ts` › "Session-mode statement record" › "records the row on which the table joins the transaction" — pins the deviation (fails under the plan's literal rule).
- Replaced: `adapter-integration.spec.ts` › "records no statement for a legacy-mode transaction's writes".
- Moved to session mode: `statement-secret-arg-redaction.spec.ts`, `replicated-lane-ceiling.spec.ts`.

## Bench (`test/large-value-commit-cost.bench.mjs`, REPS=20)

Legacy 8 × 256 KiB staging median fell from 337 ms to 119–135 ms; 4 × 256 KiB from 168 ms to 60 ms. Commit time and session mode unchanged within noise (session mode still builds every statement, as it must). Session mode at 8 × 256 KiB is refused as too large before and after, because of the hex statement in each collection's validation payload; ticket `a-large-write-is-measured-once-and-its-cost-is-documented` documents that.

## Review findings

Read the implement diff first, then the handoff.

- **Correctness of the rule.** Checked against the bridge's lifecycle: `session` is created in `beginTransaction` exactly when `coordinator`, `engine` and `schemaHashProvider` are set, and `configureTransactionMode` takes all three as required arguments, so "mode enabled" and "a begin creates a session" agree. Nothing ever clears `coordinator`/`engine`, so session mode cannot be turned off under an open transaction. A legacy transaction open when session mode is configured (allowed, see the `NOTE:` in `configureTransactionMode`) answers false for its own rows, matching the session it lacks. `commitTransaction`/`rollbackTransaction` clear `isActive` and `session` together. Confirmed in the Quereus sibling checkout that `wantStatements` is read per row at all four sites (`dml-executor.ts`) and not cached. The committed-read wrapper (`OptimysticCommittedTable`) does no DML, so it never reaches the getter. No finding.
- **The one residual over-build** (session mode configured, no bridge transaction open, a row's `update()` that then does not begin one) costs a statement that `addStatement` drops, as the handoff says; Quereus begins a transaction on registered connections before any DML, so this is only the registration-during-`update()` path the deviation exists for. Not worth a tripwire.
- **Ordering with rollback snapshots.** `update()`'s `NOTE:` requires `addStatement` above every stage because it drives `coordinator.applyActions`' pre-stage capture in session mode. The deviation is what keeps that capture on the first row of the committed-read-first path; the new test pins it. Legacy mode never drove the capture through `addStatement` (no session), so nothing is lost there.
- **Lane classification** (`lane.ts`) reads the write description, not the statement text, so legacy transactions losing their statements changes no lane. Checked.
- **Offline mode** refuses session mode in both directions, and its sealing path never reads statements. No interaction.
- **Type safety / hygiene.** The getter-without-setter is deliberate and noted in the handoff; nothing assigns `wantStatements` in the plugin or Quereus. The comment at the `defineProperty` site states a why (the class-field shadowing), not a narration. No finding.
- **Tests.** Each new or rewritten test pins a behaviour (the deviation, the legacy no-build, the redaction and lane ceiling now against the session's own record); none verify a mock. Minor fix made: `statement-secret-arg-redaction.spec.ts` disposed its `QuereusEngine` outside any `finally`, so a failing statement leaked it; the engine is now created and disposed inside `recordedStatements`' `try/finally`, and the two tests no longer handle it. No test added or cut otherwise.
- **Docs.** Read docs/transactions.md §Secrets and the replicated statement record (updated, accurate), its single-writer table row naming `accumulatedStatements` (still true), and grepped every tracked `.md` for `wantStatements`/`getStatements`/`mutationStatement`: no other doc claims statements are always captured. The backlog note on `debt-session-mode-bridge-coverage` is accurate.
- **Performance / resource cleanup / error handling.** The getter is one property read and a null check per row. No new resources, no swallowed errors. Empty, with that reason.
- **Validation run.** eslint on the six touched files clean; `yarn typecheck` in the plugin clean; full plugin `yarn test`: 1385 passing, 0 failing, 14 pending.
- **Tickets filed:** none; no major or conditional finding.
