# What was built

Every successful pend and commit result carries a required `durability: WriteDurability`. Its `quorum` is one of four classes, ordered `unrouted < local < majority < full`: `full` when every member of the resolved cohort confirmed, `majority` when a strict majority did and `unconfirmed` names who did not, `local` when the cohort resolved to this node alone, and `unrouted` when the cohort never resolved (the GitHub #19 case, previously indistinguishable from a healthy commit). The scalar fields always describe the weakest coordinator answer; `otherCohorts` carries the rest; `torn` names blocks a torn multi-block commit abandoned and cancelled. `isFullyDurable` is the one "completely saved" test.

Policy is unchanged. The durability gate still uses exactly `confirmed > cohort / 2`, the solo short-circuit accepts what it accepted, and a refusal is still a `StaleFailure` with no durability field. The class is derived from the same sets the gate was measured on.

`ClusterCoordinator.resolveCohort` is the new lookup primitive (`{ resolved: true, peerIds } | { resolved: false, reason }`). `CoordinatorRepo.commitSolo` and `pendSolo` classify through `soloCohortDurability`, and the `commit:solo-cohort` log line carries the same `quorum`. The cluster path derives `full`/`majority` from `CohortDurability`, which now carries peer-id sets. `NetworkTransactor.commit` merges the tail's answer with every confirmed sweep batch's answer, then `withTornBlocks` clamps `full` to `majority` when the sweep abandoned anything.

**Found and fixed inline.**

- **Pend fallback arm over-counted an off-cohort coordinator.** `pendThroughCluster`'s fallback arm passed `selfAccepted: true` whenever this node's own storage pend landed, and `pendCohortDurability` added self to the confirmed set unconditionally, so a coordinator outside `record.peers` produced `confirmed: 4, cohort: 3`. The commit tier already counts self only when it is a cohort member. `pendCohortDurability` now adds or removes self only when self is in the cohort. New spec case in `coordinator-repo-write-durability.spec.ts` pins three of three with self absent from `cohortPeerIds`.
- **`otherCohorts` listed the same cohort twice on every healthy multi-block commit.** The tail and the sweep are separate batches, so one cohort answers twice, and the two answers list the same members in different orders because `findCluster` orders a cohort by routing distance to each block's key. `mergeDurability` now collapses structurally identical answers, comparing peer lists as sets. Verified on the real mesh: the seed commit in `torn-commit-cancels-abandoned-blocks.spec.ts` now asserts `otherCohorts` is absent, which failed before the order-insensitive key and passes after. Unit test added in `durability.spec.ts`, including that differing answers from one cohort are both kept. The `otherCohorts` doc no longer claims "more than one cohort".
- **`majority` doc contradicted the torn clamp.** The class doc said "at least one member did not confirm", which is false after `withTornBlocks` clamps a `full` report. The doc now names the torn case and says `unconfirmed` may be empty there.
- **Dead seam member.** `ICoordinatorClusterSeam.getClusterPeerIds` had no caller after `pend` and `commit` moved to `resolveCohort`. Removed from the seam and from the eight one-line doubles in five specs; `getClusterSize` stays because `verifyResponsibility` uses it, and its doc now says so.
- **Stale comments.** `service.ts` (commit anchors on `getClusterSize`), `libp2p-key-network.ts` and its spec ("every commit calls `findCluster` through `getClusterPeerIds`"), `coordinator-repo-solo-commit-proof.spec.ts` ("`getClusterPeerIds` reports an empty cohort"), and `coordinator-repo-commit-freshness.spec.ts` all named the replaced accessor; each now names `resolveCohort`. `docs/internals.md`'s torn-commit bullet said commit "returns `{ success:true }`"; it now says the answer names the abandoned blocks in `torn` and is clamped below `full`.
