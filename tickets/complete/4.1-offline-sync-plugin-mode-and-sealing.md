First of the five stage-4 tickets of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages). The db-core queue now sits behind the plugin: a database enters and leaves offline mode, a commit begun in the mode is sealed into one queue entry under its `StampId()` instead of reaching storage, the queue's collection-level events are reported as table-level statuses, and a drained entry produces the same durability report an online commit does. Everything is in memory. Implemented in `ticket(implement): offline-sync-plugin-mode-and-sealing`; reviewed here.

## What landed

- **`OfflineMode`** (`packages/quereus-plugin-optimystic/src/optimystic-adapter/offline-mode.ts`), one per registered plugin, exposed as `plugin.offline`: `enter` / `exit` / `isEntered`, `whenDrained`, `dispose`, `onStatus`, `onQueueState`, `queueState`, `entries`, `status`, `discard`, `outcomes`, `acknowledge`. It owns one `OfflineQueue` per `Database` (built at registration, drain idle until the first entry) and translates every queue status: entry id to `transactionId`, collection ids to deduplicated qualified table names through the bridge's `tablesOf`, `committed` to the bridge's `SqlCommitDurability` plus `kind`, `failed`'s `error` through `mapCommitRefusal`. Terminal outcomes are retained for `outcomeRetentionMs` (default seven days), pruned lazily, no timer. The status types are in `offline-status.ts`.
- **Registration config** `offline: { expireAfterMs?, outcomeRetentionMs?, recheck?: { baseMs?, maxMs? } }`, parsed by `parseOfflineConfig` (now in `offline-config.ts`, see the review); an unknown key or a non-positive number is refused at `register` with a message naming the key.
- **The bridge** (`txn-bridge.ts`): `TransactionState.acknowledgement` fixed at `beginTransaction`; `commitTransaction` seals a `'local'` transaction's staged dirty trees through `OfflineMode.enqueue`, tearing the transaction down as a successful commit does but leaving the degraded latch as it was; a dirty set that cannot be one entry (a tree without a collection, collections on different transactors, two instances over one collection id) falls back to the network route, logged `offline:local-ack-unavailable`; `reportCommitDurability` is package-visible, takes a `demanded` flag and returns the report; `configureTransactionMode` throws `SessionModeRefusedError` while the mode is entered or entries are queued; `attachOfflineMode` and `tablesOf`.
- **The factory** (`collection-factory.ts`): `setSealedRefusedListener`, set once by `register`, passed to both `Tree.createOrOpen` and `Tree.open`, so every data, index and catalog tree reports sealed-segment refusals to this database's queue.
- **db-core**: `OfflineQueue`'s constructor no longer takes a transactor; `send` builds the per-entry coordinator over the remaining collections' shared transactor and stops the drain on a defect if they differ.
- **Shared listener helpers** (`listeners.ts`), used by the bridge and the controller.
- **Exports** from both entries: `OfflineMode`, `OfflineModeRefusedError`, `SessionModeRefusedError`, `OfflineConfig`, db-core's `EntryNotDiscardableError`, `UnknownEntryError`, `QueueDisposedError`, and the status types.
- **Docs**: README section "Offline mode"; docs/offline-sync.md §Application interface names what exists and corrects the shapes.

## Deviations from the design, each deliberate

- The controller always demands the durability report for a drained commit, listeners or not, because `outcomes()` and `status()` retain the `committed` status, which is the report.
- The controller does not take the `Database`; ticket 4.2 adds it with `notifyExternalChange`.
- Two refusal classes: `OfflineModeRefusedError` (reason `'session-mode'`) for `enter()`, and `SessionModeRefusedError` (`'offline-mode'` or `'queued-entries'`) for `configureTransactionMode`.
- The queue-wide state is `OfflineModeState` (the design doc said `OfflineQueueState`, which is db-core's name); `queueState()` exists beside `onQueueState`.
- The expiry scenario is not tested at the plugin level: stage 4 wires no reachability gate, so the drain sends the head at once, the first attempt puts the entry in doubt, and an entry in doubt is neither expired nor discardable. Documented in the README; a note was appended to ticket 4.3, whose "timeout, never sent" case it affects.
- A network-acknowledged commit behind a non-empty queue is stated in the README as it behaves: a commit writing a table with queued entries fails with `SealedSegmentsError` and rolls back cleanly, one writing other tables commits ahead of the queue. Ticket 4.3 closes both.

## Review findings

Read the implement diff first, with every file it touched and the ones it should have touched (`docs/debugging.md` was the one it missed). Checked by reading and by running: the happy path on a two-node mesh, the unreachable-cohort path, the fixed-at-begin rule, the session-mode refusal in both orders, the enqueue failure paths (a disposed queue or a drain defect throws before anything is sealed, so the bridge's catch rolls the transaction back cleanly), the teardown after sealing, the listener discipline, the retained-outcome pruning, the collection-instance lifetime the queued rows' visibility rests on (the vtab and `IndexManager` hold their trees for the table's life, so sealed segments stay on the instances every later read goes through), the `Tree.open` / `Tree.createOrOpen` option plumbing, and the docs against the code.

**Minor, fixed in this pass:**

- **Dispose order leaked a subscription.** `plugin.dispose()` disposed the bridge (releasing the follower's subscriptions) before the queue, whose dispose lets a submission in flight finish its current network step and still emits a `committed` outcome it lands. That outcome's `reportCommitDurability` would have had the follower subscribe to the node's full-replication events again, after dispose, with nothing left to release it. The queue is now disposed first, then the bridge; the comment in `plugin.ts` says why.
- **Config parsing shared the controller's file.** `OfflineConfig`, `parseOfflineConfig` and its helpers moved verbatim to `offline-config.ts`; the controller file is now only the mode and its translation. Exports and the design doc's citation follow.
- **The plugin's new log lines were undocumented.** `docs/debugging.md` §quereus-plugin sub-namespaces now lists the `offline-mode` namespace and the bridge's `offline:local-ack-unavailable` and `mode=offline` trace.
- **Design doc drift.** §Implementation stages marked stages 1 to 3 implemented and stage 4 not at all; it now says which part of stage 4 landed. §Entering and leaving the mode stated the wait-behind-the-queue rule as if it existed; it now points at the stage-4 ticket that lands it and the README's statement of today's behaviour. §Queries and actions' description of `outcomes()` matched neither the code nor the README; corrected.
- **One contract was unverified.** The README promises that a queued transaction's rows are in every later read on this machine; the spec checked that only through a full scan. The multi-entry case now also asserts, before reconnect, that an index-driven read and a scan on the queuing node agree and that it reads its three queued rows.

**Tripwire, recorded at the site:**

- `NOTE:` at `TransactionBridge.configureTransactionMode`: a transaction begun `'local'` and still open passes both refusal checks (enter, begin, exit, configure), and its commit then queues an entry behind which the following session transactions meet the documented `SealedSegmentsError`. Only a host that configures session mode mid-transaction meets it; the remedy is stated there.

**Major findings:** none. The single-writer state of the bridge is untouched by the controller (checked: it reads `isTransactionModeEnabled`, `tablesOf`, `mapCommitRefusal`, `reportCommitDurability` only), the `enqueue` call is latch-free and bracketed by the commit as the queue requires, and the queue's own rules are pinned in db-core.

**Tests cut:** none. Each of the eleven cases pins a user-observable contract or a design rule (fixed-at-begin, synchronous `queued` delivery, the two refusal orders, the shared-id fallback, the config refusal); none restates the implementation or verifies a mock.

**Considered and declined:** none met an accepted-tradeoff `NOTE:`; the existing tripwire at `pruneOutcomes` (the per-access walk of retained outcomes) stands.

**Pre-existing failures:** none seen.
