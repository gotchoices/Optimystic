## What landed

`test/two-node-index-mutation-sweep.spec.ts`: a second generated sweep beside the insert-only `two-node-index-interleaving-sweep.spec.ts`, on the in-process mock mesh, over `FormationUsage (Id integer primary key, Token text)` with an index on `Token`. Every case starts from A's row `(100, 'tok-a')` and B's row `(200, 'tok-b')`, both seen by both nodes; the target is always row 100.

- **64 sequential cases**: declarer × how the other node arrives (re-declare or hydrate) × which node mutates × what the mutation is (move the value onto the sibling's, onto a new one, move the primary key, delete) × how it finds the row (by primary key or through an index seek). All clean on both nodes. No single-writer way to leave a stray index entry was found.
- **32 racing cases plus 4 INSERT OR IGNORE races**: both nodes stage, then commit in a stated order. Twelve of them leave a stray index entry today, and each asserts the exact entry rather than being skipped or softened, so it flips the moment the underlying defect is fixed.
- A pure-data guard, needing no mesh, pins the case counts, the absence of duplicate names, and that every dimension value and every racing pair is generated.
- A small model of today's replay behaviour computes each racing case's expected outcome. Every prediction the implement ticket had marked unverified matched observation.

Neighbouring specs' comments were re-pointed at the new file, and the retired ticket slug no longer appears anywhere under `packages/`.

## Review findings

**Checked**: the implement diff read before the handoff; generator and model logic; the coverage guard; the setup's non-vacuity; every comment the change touched and the neighbouring files it should have touched; `AGENTS.md`, `docs/debugging.md` and `test/README.md` for statements this work makes stale; reuse of existing helpers; and the two greps the ticket demanded (the retired slug returns nothing; the `replay model` done-check for the downstream ticket matches only this file).

**Major — one, filed as `fix/index-seek-returns-moved-rows`.** The pinned cases were closing on the index's *structure* only; nothing checked that lookups still return the right rows while a stray entry exists. Seeking the stray entry's own value turns out to return the row the entry points at — a row that no longer holds the value asked for. `select ... where Token = 'tok-ignored'` returns `(300, 'tok-winner')`. It reproduces two independent ways: on two nodes with no test patching at all (all four update-vs-update races and all four IGNORE races), and on a single node with index staging deliberately broken. Stray entries whose row is *gone* are still skipped correctly; only the moved-row form leaks.

This contradicts a claim stated as settled fact in five places, including the code comment directly above the loop, which called the stray entry benign because the engine re-applied the predicate. It does not. Filed at the read seam rather than per producer: one check there — re-derive the entry's key from the fetched row and skip a non-matching one — retires every wrong answer of this shape, whatever left the entry behind, whereas fixing the producers leaves the detached-writer path still able to produce one. The ticket names both remedies (filter in the plugin, or stop claiming the filter is handled), the composite-index and value-less-seek cases to establish while fixing, and the five documentation sites that assert the false claim.

**Minor — fixed in this pass:**

- Split the lookup half of `expectIndexAgreesWithScan` out as `expectLookupsAgreeWithScan`, so a case that pins a known stray entry — and so cannot pass the structural half — still checks that lookups agree with the scan. The pinned cases now run it.
- Pinned the wrong-row behaviour above at both sites that can see it, with a comment naming the fix ticket and saying what each should assert once fixed: the helper self-test, and `expectOrphanSeeks` in the sweep. Nothing was skipped or loosened.
- A comment claimed the structural check sees only leftover entries; it sees missing ones too. Corrected.
- Corrected the two helper doc comments that repeated the false "a stray entry never changes a result set" claim, in wording that stays true either side of the fix. The four sites in `src/` and `docs/` are left to the fix ticket, which has to rewrite them anyway; listing them there beats churning them twice.
- Recorded, at `runSetup`, that a hydrating node here always hydrates onto a table with no rows yet, so hydrate-then-mutate onto a populated table is uncovered — a recorded gap, deliberately not a ticket, matching how the insert sweep records its own.
- Added to `6.3-refuse-concurrent-row-change-loser` that it must also delete `expectOrphanSeeks`, which has nothing to seek once no stray entry survives.

**Non-vacuity, which the handoff flagged as argued but not demonstrated.** Ran the missing negative control: a scratch two-node spec that broke update staging and delete staging in turn, on each node in turn. All four shapes went red on *both* nodes with the expected stray entry, so the sequential group's oracle does bite, and it bites on the sibling node too. The scratch file was deleted after the run; its permanent equivalent already exists in `query-helpers.spec.ts`.

**Tripwires**: none new. The one conditional concern in the diff — that the by-primary-key cases assert zero index seeks and would go red if the planner ever routed a primary-key equality through a secondary index — already carries its explanation in its own assertion message, which is where a future reader meets it.

**Considered and declined**: the undisposed `Database` handles this file adds carry an accepted-tradeoff `NOTE:` on `startMockMesh` whose revisit condition (slowdown or heap growth) has not tripped — the suite is unchanged at 2m. Left alone. `AGENTS.md`'s sweep paragraph is about the insert sweep's narrowing environment variable; the mutation sweep has no such switch, so it needs no entry there.

**Not filed as size debt**: the file was 706 lines at handoff (`git show --stat`), plus roughly 25 from this pass. Around 130 of those are the replay model, which `6.3-refuse-concurrent-row-change-loser` deletes outright. A split now would be undone next ticket.
