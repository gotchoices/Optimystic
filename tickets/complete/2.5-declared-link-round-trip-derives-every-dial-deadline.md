# One declared link round trip, every dial deadline derived from it

## What landed

`NodeOptions.linkRoundTripMs` — the slowest round trip, in milliseconds, between any two nodes that will talk to each other, relayed hops included. `createLibp2pNodeBase` resolves it first thing (before storage is acquired) with `resolveLinkDeadlines` in `packages/db-p2p/src/rpc-deadline.ts`:

| `LinkDeadlines` field | derivation (`r` = round trip) | undeclared |
| --- | --- | --- |
| `dialTimeoutMs` | `max(3000, 6r)` | 3000 |
| `responseTimeoutMs` | `max(10000, 3r)` | 10000 |
| `connectionTimeoutMs` (libp2p `dialTimeout` and `inboundUpgradeTimeout`) | `max(10000, 5r)` | 10000 |
| `cohortQueryTimeoutMs` (fills an undeclared `clusterPolicy.cohortQueryTimeoutMs`) | `max(1000, 3r)` | 1000 |
| `transferTimeoutMs` (`BlockTransferCoordinator`) | `max(30000, dialTimeoutMs)` | 30000 |

Undeclared resolves to exactly the pre-existing constants. An unusable value (not finite, not above zero, or above `MAX_LINK_ROUND_TRIP_MS` ≈ 1.66 days) throws at node construction. Explicit per-deadline settings still win (`connectionManager.*`, `spreadOnChurn.push*`, `underReplicationDrain.push*`, `clusterPolicy.cohortQueryTimeoutMs`, a caller's own `dialTimeoutMs`).

`ProtocolClient` carries instance fallback deadlines; `ClusterClient`, `SyncClient` and `DisputeClient` merge against them, and redirect hops pass them on. The node threads the resolved values to its cluster client factory (also used now by `ClusterMember.propagateIfNeeded`), dispute client factory, every `SyncClient` (including `RestorationCoordinator`'s), the drain's and spread-on-churn's push defaults, `BlockTransferCoordinator`, and the libp2p `connectionManager` block. The resolved object is exposed as `node.linkDeadlines`. The Quereus plugin takes a plugin-level `link_round_trip_ms` setting, passes it to the node it builds, and reads its `NetworkTransactor` dial deadline from `node.linkDeadlines`; the reference peer does the same for its transactor.

## Review findings

Read the implement diff (`ticket(implement): declared-link-round-trip-derives-every-dial-deadline`) before the handoff.

**Checked and correct.**
- Derivation and ceiling. `MAX_LINK_ROUND_TRIP_MS = floor(MAX_COHORT_QUERY_TIMEOUT_MS / 3)` is tighter than the ticket's "6r overflows" rule, and correctly so: the largest derived delay is the reconcile pass bound, `5 × 3r = 15r`, and `3 × floor(MAX/3) ≤ MAX` makes the filled cohort budget pass `resolveCohortQueryTimeoutMs` by construction. Accepted the deviation.
- Import graph. `rpc-deadline.ts` now imports `cluster/cluster-policy.ts` (value import), and `protocol-client.ts` imports `rpc-deadline.ts`. Traced `cluster-policy` → `quorum-restore`, `reconcile-block` → `block-archive`, `commit-proof`, `certified-claims`: none reach a client module, so no runtime cycle.
- Call-site coverage. Grepped every `ClusterClient.create`, `new SyncClient`, `DisputeClient.create`, `new RestorationCoordinator`, `new BlockTransferCoordinator`, `new SpreadOnChurnMonitor`, and every hard-coded `dialTimeoutMs`/`responseTimeoutMs` under `src/`. Every production construction receives the node's deadlines; the only default-constructed paths are standalone use and tests, which keep the undeclared values by design.
- `RepoClient` left unchanged: its dial deadline comes from the caller's `MessageOptions`, where `undefined` means "no cap" to `NetworkTransactor`; adding a fallback would change that meaning. Accepted.
- `spreadOnChurn` merge order (derived first, caller's object over it) and the drain's `??` fallbacks give the explicit setting precedence, as specified.
- libp2p `dialTimeout` now always passed (10 s undeclared = libp2p's default): no behaviour change.
- Plugin setting validation: a non-number throws, and the node refuses a bad number. Consistent with the fail-loud rule.
- Resource cleanup: resolution runs before storage is acquired, so an invalid value throws with nothing to release.

**Found and fixed in this pass.**
- The plugin's `NetworkTransactor` kept `abortOrCancelTimeoutMs: 5_000`. A cancel is a negotiation and request to the coordinator plus a consensus round with the cohort, about six round trips warm, so at the supported 3 s round trip every cancel ran out of budget and left its pending records standing. Now `Math.max(5_000, dialTimeoutMs)`, which keeps an undeclared node at 5 s and gives a declared 3 s link 18 s. A `NOTE:` at the site records that this holds a warm cancel narrowly and a cold relayed one not at all. README row updated to say the setting reaches both the dial and cancel deadlines.
- Docs that still described fixed numbers: `packages/db-p2p/docs/cluster.md` said the sync client's "own 3 s dial and 10 s response defaults" (now "3 s and 10 s when no link round trip is declared"); `packages/db-core/docs/network.md` claimed a "3 s per-peer" cluster latest-revision query (it is `cohortQueryTimeoutMs`, 1 s default, derived when declared); `docs/optimystic.md`'s native-API `NetworkTransactor` example omitted `dialTimeoutMs`, so a host copying it silently kept the 3 s dial on a slow link. It now reads `node.linkDeadlines.dialTimeoutMs`.

**Tripwires recorded.**
- `DEFAULT_SIGN_COLLECT_TIMEOUT_MS` (5 s) in `packages/db-p2p/src/cohort-topic/threshold-crypto.ts` is not derived. Cohort-topic is opt-in (default off), so this is conditional. Parked as a `NOTE:` at the constant.
- The plugin's `NetworkTransactor` `timeoutMs: 30_000` overall budget: the implementer left the `NOTE:` the ticket asked for; the cancel budget beside it now carries its own.
- The other known gaps in the handoff are unchanged and need no action: `DEFAULT_RELAY_DRIVE_TIMEOUT_MS` (a direct dial to the relay, not a relayed hop); libp2p's `PROTOCOL_NEGOTIATION_TIMEOUT` (10 s, one round trip, fits to 10 s); `RepoClient`'s `now + 30_000` expiration fallback, which `NetworkTransactor` never reaches since it always passes an expiration; the `mesh-harness.ts` test transactor.

**No tickets filed.** Every finding was either fixed here or is conditional on opt-in features.
