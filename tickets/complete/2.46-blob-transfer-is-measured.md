# Blob transfer is measured

## What was built

- `packages/db-p2p/test/bench-blob-transfer.mjs`: two nodes over loopback TCP with memory piece stores. A puts fresh random bytes at 1, 3 and 16 MiB; B reads them with `node.blobs.read`, timed from first call to last chunk; wire bytes are the delta of B's `node.blobs.wireBytes()` (blob-protocol frames only). It also times A's put apart from the transfer and splits the overhead into list-piece bytes and frame headers/length prefixes. Run with `yarn build && node test/bench-blob-transfer.mjs` from `packages/db-p2p` (`N` env var, default 5). Runs in no script.
- docs/blobs.md §What this answers in GitHub #63: the "expected cost" paragraph is replaced by measured results (per-size table, machine, date, command) and three bullets: time against the row path, space against the row path's expansion, and the overhead, which is about 22 KB per 45 MiB rather than the few kilobytes the doc expected.

Result: a transfer costs 5.5 to 10.5 ms per MiB on loopback, and 1.0005 to 1.0006 times the content crosses the wire.

## Review findings

- **Checked the bench by running it** (N=3). The byte columns reproduced exactly (1,049,234 / 1,049,116 / 1,049,077 wire B/MiB; 5 / 13 / 65 pieces). The timings were in range except the 3 MiB read, at 9.7 ms/MiB against the documented 5.5 to 7.1. **Fixed**: the Time bullet now says a run during review read 3 MiB at 9.7 ms/MiB, so the ranges are one afternoon's spread on this machine, not bounds.
- **Checked the overhead arithmetic against the wire format** (`encodeBlobHeader` in `packages/db-p2p/src/blob/blob-protocol.ts`, JSON headers). Fixed per `get`: `{"kind":"get","pieces":[]}` plus `{"kind":"get","held":[]}` plus two 1-byte prefixes comes to 52 bytes, which matches. Per piece: the id in quotes with a comma (62 bytes), `true,` (5 bytes) and a 3-byte piece prefix come to 70 bytes, not the 75 the doc said. The 75 had folded in the per-`get` header that the next sentence then counted again. At 16 MiB, 65 × 70 − 10 for the commas plus 5 × 52 comes to 4,800 bytes, or 300 B/MiB, which matches the measurement to the byte. **Fixed**: the bullet now says about 70 per piece, plus about 4 per piece for the `get` headers at 16 MiB.
- **Checked the other figures**: 19 to 55 times (200/10.5 and 300/5.5), 1.0005 to 1.0006 (1,049,077 and 1,049,234 over 1,048,576), 22 KB per 45 MiB (501 × 45), and 50 bytes per link (201 B/MiB over 4 links). All correct.
- **Comparison framing (the implementer flagged it).** The "19 to 55 times" sentence names what each side leaves out: consensus and storing the value on both machines for the row; the reference-row commit, copying to the cohort and a disk for the blob. It does not overclaim, so I left it.
- **The stale "a list piece is a few kilobytes" line** in §References and pieces (the implementer flagged it). **Fixed** to "at most about 9 KB, about 50 bytes per link", linked to the measurement. This is extrapolated from the measured per-link size and 174 links, and the sentence says it was measured per link.
- **The extra bench columns** (put time, list and frames split, read samples): kept. The put column makes the comparison with the row path fair, and the samples let a reader judge the warm-up claim. Neither costs anything, since the bench runs in no script.
- **Bench code**: nodes are stopped in a `finally`, failure exits 1, piece computation is outside the timing, fresh content each repetition, and the wire snapshot is taken after the cohort wait, so no other traffic is counted (confirmed by the counts being identical every run). Eslint is clean. No comments that narrate.
- **Tests**: none added and none needed. This is a measurement with no code under test. `yarn lint:docs` passes after the edits. No source under `src/` changed, so the package suites were not re-run.
- **Tripwires / tickets**: none. Nothing here is conditional work.
