## What was built

**Plan time.** For each non-partial index that this table instance maintains, `getBestAccessPlan` offers a range seek of the key column after the equality run on the index's leading columns (none, for a range on the first column). The column must be TEXT, BINARY-collated on both the table column and the index column, and not compared by meaning (`bytesOrderAsValues` in `packages/quereus-plugin-optimystic/src/schema/index-walk.ts`), carry no `=` or `in`, and carry a bound. The candidate claims the first lower-bound filter and the first upper-bound filter on the column and nothing else, because those two are what the engine seeks on for a column it is told is handled, claimed or not (`findLower` and `findUpper` in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`); a further bound on the same side stays with the engine as a residual filter. If either first bound is not claimable (unusable, a runtime set, or a plan-time literal of another type than a string) the whole range on that column is declined. It is priced as one descent plus the table's rows times the prefix's equality selectivity times 0.25 per bound (`RANGE_BOUND_SELECTIVITY`, the assumption the primary-key range branch has always made), and delivers an ordering under the walk's rules, so `where a = ? and t > ? order by t desc limit 10` over `(a, t)` is one backward prefix-range seek with no sort.

**Read time.** The engine answers with `plan=3` (bounds on the first column) or `plan=7` (a prefix of equalities, then the bounds). `rangeSeekOf` reads the prefix values, the range column and the bounds off `FilterInfo.constraints` and `args`, and refuses any other shape as malformed. `indexRangeScan` turns the bounds into one tree-key range: every lower key inclusive, every upper key exclusive, `> x` as the framed value plus `KEY_PREFIX_END`, `<= x` likewise, no lower bound starting at `KEY_PRESENT_START` so NULL-keyed entries are never returned, no upper bound ending at the prefix's `KEY_PREFIX_END`. A NULL bound seeks nothing. A bound holding a UTF-16 unit at or above U+D800, or a value of another type, cannot be bracketed by the tree's code-unit order, so its side of the range is left open and each verified row is tested with the engine's own comparison; a failing row counts in the trace's `rejected=`. The range's rows pass through `inEngineOrder` as a walk's do.

**Trace and docs.** The `index:seek` line prints a range as `low:high`. README, `docs/internals.md` (section "A range predicate seeks a secondary index") and `docs/debugging.md` describe the claim rule, the bound table, the three kinds of bound and the new cause of `rejected=`.

## Review findings

**Checked by reading.** The implement commit's diff, first and without the handoff. Against it, the engine's access-path rule in `@quereus/quereus/src/planner/rules/access/rule-select-access-path.ts`: a bound is picked by column regardless of which filter was claimed (so claiming the first of each side is the only sound claim), the prefix equalities are listed in the module's `seekColumnIndexes` order, a single-element `in` counts as a prefix equality, a collation mismatch declines to a scan with no `honorsCollatedRangeBounds`, and the NULL-safe ordering rule counts `>`, `>=`, `<` and `<=` as NULL-excluding, so an ordering claim on a nullable range column is sound. The key framing in `packages/quereus-plugin-optimystic/src/schema/key-encoding.ts`: every entry of value `x` continues the framed `x` with a tag below `KEY_PREFIX_END`, and every longer value puts `\xff` or a higher unit there, so the four bound keys bracket exactly the predicate's rows. The descending `KeyRange` matches the convention `indexValueRange` already uses. `matchEqualitySeek` stops at the first key column with no equality filter, so the column after the run is the range column; a multi-value `in` makes the run a multi-seek and the range is declined. Every read of a secondary index shares one entry loop, and the committed arm builds both views in the same synchronous block as before.

**Checked by running.** `yarn build`, `yarn typecheck`, eslint on every changed file, `yarn lint:docs` (48 documents, every citation resolves), the plugin's `yarn test` (1352 passing, 14 pending, smoke ok) and `yarn test` in `packages/upgrade-check` (241 passing). The sibling Quereus checkout's build was reported stale by the test guard at the start, with uncommitted edits in that repository; it was rebuilt as the guard instructs and nothing else in it was touched. A throwaway differential probe (written, run, deleted) covered the shapes the implementer did not test: a two-column equality prefix then a range, ordered backwards; a range on the second column of a three-column index; a single-element `in (?)` as the prefix; a range on the primary-key column through an index on `(g, id)`; a nullable range column with `order by` (no sort in the plan); `limit` and `offset` over a two-sided range; the committed arm inside a transaction (the staged row is absent from `committed.<Table>` and present live); `update` and `delete` whose source scan is a range seek; and an index declared `(t desc)`. Every one matched a memory table holding the same rows. Two shapes never reach the module as a bound, so the probe confirmed only that they stay correct: a bound that is a function of a parameter (`t > lower(?)`) and a correlated bound from a join are both planned by the engine as a scan plus filter.

**Found and fixed inline.** `rangeSeekOf` read a prefix-range plan's equality values in constraint order without checking that each equality sits on the index column it is framed for. The engine builds the constraints from the column list the module supplied, so no caller produces another order today, but the function promises to refuse any other shape as malformed rather than frame a wrong key, and the bounds were already checked against their column. One comparison per equality now makes the promise hold for the prefix too. Rebuilt; the range-seek, ordering-claim and ordered-walk specs (65 tests) pass.

**Considered and kept as built.** The non-string bound branch in `boundInTree`, which the engine's parameter typing makes unreachable through SQL today: it costs one `typeof` per bound at scan start and keeps the module correct if the engine ever delivers such a value through a later binding kind, and the docs say it is dormant. The multiplicative selectivity (two bounds estimate a sixteenth of the prefix's rows): the memory module publishes no range selectivity to mirror and the queued ticket bounds a bad guess. `rejected=` counting a row-test failure beside index disagreements: the trace doc names the third cause and the field keeps its arithmetic. The equality check on the range column by operator rather than by the module's own equality-role test: it only ever declines more, and the engine's equality arm is what it guards against. The maintenance check for the range candidate at its call site while the walk's sits inside its method: a free function versus a method, no behaviour difference.
