# A member checks the lane a transaction claims

Third of four tickets from the plan `a-transaction-carries-its-lane`. A validating member refuses a `convergent` claim that its own engine computes as `serializable`, with a reject marked as a validity judgement (`Lane mismatch: transaction claims convergent, this node computes serializable`). It never reclassifies.

## What landed

- `ITransactionEngine.laneCeiling?(transaction)`, optional. `ActionsEngine` omits it, so an actions transaction's lane is accepted unchecked (a caller can pass `SyncOptions.lane: 'convergent'` with any engine).
- `TransactionValidator.validate` step 2.5 (after the schema-hash check, before read dependencies) checks only a `convergent` claim; an absent lane is `serializable`; an engine throw propagates and becomes an unmarked `validator-fault` in `checkPendValidation`.
- `QuereusEngine.laneCeiling` prepares each replicated statement, reads `getWriteScope`, judges each write site with `replicatedCeilingOf` against the member's catalog, folds with `stricterLane`.
- **The member's rule differs from `laneCeilingOf` for UPDATE**, because Quereus's `buildUpdateStatement` rebuilds an UPDATE to assign every column, the key included. `laneCeilingOf` would refuse every honest convergent UPDATE. `replicatedCeilingOf` answers `serializable` only where every statement that could produce the rebuild is `serializable`: INSERT uses `laneCeilingOf` unchanged; DELETE is `serializable`; UPDATE checks profile, selection by primary key, no assertion on the table (added in review), and a merge declared on at least one non-key column. A writer that lies about an UPDATE's assigned columns, a key move, or anything only the writer saw (key provenance, values read) passes this check; the replay stage's guards are what catch those.

Implement commit: `ticket(implement): a-member-checks-the-lane-a-transaction-claims`.

## Review findings

**The member's UPDATE rule (the implementer asked for this to be challenged).** I read Quereus's `buildInsertStatement`, `buildUpdateStatement`, `buildDeleteStatement` (`@quereus/quereus/src/util/mutation-statement.ts`) and how the write description lists constraints (`writeConstraints` in `@quereus/quereus/src/planner/analysis/write-site-analysis.ts`). Agreed with the implementer's choice: `laneCeilingOf` cannot be applied to a rebuilt UPDATE, and both alternatives (blocking on a Quereus change, or comparing old and new row values) are worse. Checked the "honest writer never refused" direction arm by arm: a convergent UPDATE must assign a merge-tagged non-key column (assigning only key columns lists `primary-key`, already serializable at the writer), so `declaresMergeOutsideKey` cannot refuse it; INSERT's rebuild loses only the disposition (`or replace` becomes a plain insert, which has the same ceiling); the upsert `do update` arm's rebuilt UPDATE comes from a writer that was already serializable.

**Found and fixed: the UPDATE arm ignored assertions it could soundly use.** The implementer listed "assertion and cross-row CHECK constraints are not used to refuse" as a gap because it was unclear whether the original statement would have listed them. Quereus's `assertionConstraints` takes no assigned-column filter, so every write to a table an assertion depends on lists it, the writer's included, and the writer's ceiling is then `serializable`. `replicatedCeilingOf` now refuses a rebuilt UPDATE that lists an `assertion`. `unique`, foreign-key and `check` constraints stay unread for UPDATE, because Quereus lists those only for assigned columns. That gap is now stated in the code and in transactions.md §What a member verifies. Pinned by a new row in `replicated-lane-ceiling.spec.ts`, whose property check (an honest convergent writer is never answered `serializable`) also verifies that the writer's own description lists the assertion.

**Tests.** I cut two rows from `replicated-lane-ceiling.spec.ts`, "a delete" and "an insert into a table with no profile". Both only exercised `laneCeilingOf` branches already pinned in `lane.spec.ts`, and the replicated path sends non-UPDATE writes straight to `laneCeilingOf`. I kept the UNIQUE-insert row, because it is the evidence that a rebuilt INSERT keeps the original's constraints. I kept the db-core validator test: it pins step 2.5's contract (a serializable claim is never asked about; a convergent one is refused, with the validity marker).

**Docs.** transactions.md called the step "step 2.5" in §What a member verifies (the code's numbering) and "3.5" in §7 (the pseudocode's numbering). I reworded the first to "right after its schema-hash check". The UPDATE bullet and the "cannot catch" paragraph now name the assertion rule and the constraints that go unread. I checked internals.md §Every Write Carries a Lane and the Key Invariants validity-marker bullet ("six refusals"), and right-is-right.md: all accurate. partition-healing.md (the anchor) describes the target reconcile design and does not need to change for this check.

**Checked, no change needed.**
- Ordering: the lane check comes before the stale-read check. That is correct even though a lane refusal is final, because the ceiling depends only on statements and catalog, never on state.
- `await engine.laneCeiling(transaction) === 'serializable'` parses as intended.
- Error path: a throw from `prepare` or `getWriteScope` propagates, and `checkPendValidation` catches it as `validator-fault`.
- `prepared.finalize()` runs in a `finally`, so no resource is leaked.
- Type safety: nothing uses `any`, and the table that cannot be found is typed `TableSchema | undefined`.
- Efficiency: the per-statement prepare cost is parked as a `NOTE:` at `QuereusEngine.laneCeiling`.
