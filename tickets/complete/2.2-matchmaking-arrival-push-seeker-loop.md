# Matchmaking arrival push: the seeker's push-path hang-out loop

Third of five tickets in the arrival-push chain. Only `SeekerWalkClient` and its transport seam changed (`ticket(implement): matchmaking-arrival-push-seeker-loop`). No production transport supplies a push channel yet (`matchmaking-arrival-push-seeker-transport` adds one), so on real nodes every walk still takes the poll path.

## What was built

- **Transport seam.** `SeekerWalkTransport` gained an optional `pushes?: SeekerPushChannel` (`take()` / `wait(ms)`) and `close?()`. The walk takes the push path exactly when `pushes` is present. `run()` awaits `close?()` in a `finally` and logs a failure on `matchmaking:seeker-walk:error` without rethrowing it.
- **Shared admission.** Query replies (`collect`) and pushes (`absorbPush`) both go through `admit` (filter, then `verifyProviderEntry`, then dedupe by `participantId`) and `noteTraffic`. Only query replies refine `filterAcceptRatio`. A push naming another topic is dropped and logged.
- **Push-path hang-out** (`pushHangOut`): wait until the next safety poll or the deadline, absorb what `take()` returns, stop on `wantCount` met or a promotion seen, otherwise renew, then a safety `QueryV1` when one is due. One final query at the deadline unless the tier already exited.
- **Promotion seen mid-tier (both paths).** A query reply or push reporting child cohorts at a tier whose `Accepted` reported none returns `reregister`. The walk registers at the same tier again, with no withdraw, and follows the `promoted` reply. This happens at most once per tier per walk.
- Query-reply and push traffic also feed `SeekerWalkResult.maxChildCohortCount`.

## Review findings

Checked: the implement diff in full, the existing callers of the seam (`module.ts`, `query-transport.ts`, `testing/matchmaking-mesh-harness.ts`), the downstream tickets `2.3-matchmaking-arrival-push-seeker-transport` and `2.4-matchmaking-arrival-push-wiring-and-e2e`, and the doc sections the change touches. Ran `yarn build` in db-p2p (clean), `yarn test` in db-p2p (3251 passing, 68 pending, 0 failing), and eslint on both touched files (clean).

- **Fixed (minor): redundant final poll at zero patience.** A walk that reached a tier with no patience left ran the tier's immediate query and then, on the push path, a second identical query at the same instant. The poll path issues none in that case. `pushHangOut` now returns at once when patience is already gone, because the immediate query already ran at the deadline. Added one test that reproduces it (*patience gone on arrival*): it failed before the fix, since the walk issued a third call `query:0`. The decision is handed to the docs ticket.
- **Tripwire, parked as a `NOTE:` above `noteTraffic` in `seeker-walk-client.ts`: traffic heard at a tier is assumed to be that tier's.** The libp2p transport and the mesh harness answer every tier's query from the tier-0 cohort (the single-tier-0 milestone). Once a promoted tree is actually served, a leaf tier's promotion watch would see tier 0's child cohorts and re-register once, for nothing. This can't happen today: the host reports `childCohortCount` 0 for the single-tier-0 milestone, and the mesh's hot regime reports child cohorts on `Accepted` too, so its watch is never armed. The cost is bounded at one extra register per tier per walk.
- **Same tripwire, second arm: stale pushes after a descend.** The handoff argued that pushes from a tier left behind can't trigger a re-register because the new tier's `Accepted` already reports child cohorts. That holds when escalating toward the root. It does not hold when descending after a promotion: the child tier reports no child cohorts, so a push queued by the promoted tier the walk just left can set off one spurious re-register there. Both arms are bounded by the once-per-tier rule and share the same `NOTE:`.
- **Considered and left: no withdraw before the promotion re-register.** When the cohort answers `promoted`, the seeker's record at the old tier stays until its 10 s seeker TTL expires (the transport tracks only `accepted` registrations). After a promotion that tier gets no new arrivals, so the leftover record costs nothing that matters. Withdrawing first would cost an extra call on every re-register.
- **Judgment calls in the handoff, accepted:** the immediate query feeds the promotion check; query and push traffic feed `maxChildCohortCount` (it only rises, which can only push the caller toward the sweep); re-register isn't gated on remaining patience (bounded by the per-walk set). The first two were already handed to the docs ticket.
- **Docs.** `docs/debugging.md` has the new namespace row, which `logger.spec.ts` checks. `docs/matchmaking.md`'s Hang-out vs. continue callout is accurate. Found an existing mismatch between §Test expectations (≈ 2 queries at defaults) and §Configuration (≈ 3). Both counts are defensible depending on whether the immediate query is counted, so it was added as an arm of `2.4-matchmaking-arrival-push-wiring-and-e2e`, which already owns those sections, rather than edited here. `docs/internals.md` is likewise left to that ticket, as planned.
- **Tests.** The six implement-stage tests each pin a doc *Arrival-push behavior* bullet, or the feature's main claim (a push that meets `wantCount` issues no further query), so all were kept. One test was added for the defect above.
- **Resource cleanup / error handling.** `close()` runs in `finally` on both paths and on throw, and its own failure is logged rather than swallowed silently. Pushes left queued when a tier exits early are released by `close()`. Nothing else to report.
- **Type safety / size.** No `any`. The file is 446 lines (`wc -l`), with small single-purpose methods. Nothing to report.
