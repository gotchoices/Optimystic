# File storage commits groups through a log

Second of three tickets from `file-storage-pays-one-fsync-per-write-group` (GitHub #37). `write-group-overlay-driver` holds a group's writes in memory and hands them to a `BatchBackend.commit`; this ticket is the file backend's `commit`, built as a write-ahead log. Checkpointing, the shared log for `FileKVStore` and the README rewrite followed in `file-store-checkpoint-and-shared-log`, which landed before this review ran, so the files below carry that ticket's work too; this review judged the parts `ticket(implement): file-storage-commits-groups-through-a-log` introduced, as they stand now.

## What landed

- **`FileRawStorage`** (`packages/db-p2p-storage-fs/src/file-storage.ts`) is `KvRawStorage` over `WriteGroupDriver` over `FileBatchBackend`. The constructor stays synchronous; the lock is taken and the log replayed on the first operation. `close` is declared always-present beside `listBlockIds`, `getApproximateBytesUsed` and `getStoreIdentity`. `FileStoreDriver` is gone: its reads, listings, path helpers, colon encoding, legacy raw-colon fallback and corrupt-JSON-reads-as-missing guard moved to the backend unchanged; its writes went.
- **`FileBatchBackend`** (`packages/db-p2p-storage-fs/src/file-batch-backend.ts`) maps each `StoreKey` to a tree path (relative with forward slashes for the log, absolute for reads), opens the shared log before every operation, and turns a batch into log entries; a delete of an action-scoped record off win32 with a colon in the id adds a second delete entry for the raw-colon sibling so a replay removes it too. The log is acquired on the first operation, not in the constructor, so an instance `withReadCache` discards unused holds nothing; `close` releases the reference.
- **`FileWriteLog`** (`packages/db-p2p-storage-fs/src/file-write-log.ts`): `<basePath>/write-ahead.log`, a header of `OPTIMYSTIC-WAL` plus a version byte, records `[u32 length][u32 CRC-32][payload]` with entries `[u8 kind][u16 path length][path][u32 value length][value]`. `commit` runs on a per-log queue: one write, one sync, then the apply (`mkdir -p`, a `writeFile` straight to the canonical path, or an unlink), resolving after the apply. `open` is memoized: wait for a previous log over the directory still closing, make the base directory, take the lock, replay strictly (a torn record, a length past the end, a CRC mismatch, a bad entry or a wrong header stops the read before it; what precedes is applied), sync what the replay touched, then start a fresh header. A registry keyed by `fileStoreIdentity` shares one instance per directory per process by reference count; the last release closes the handle and removes the lock, and a log acquired meanwhile opens after that. An I/O failure in open, append or apply latches the log; `StoreLockedError` is rethrown as-is. The codec is exported so tests can hand-build damaged logs.
- **`acquireStoreLock`** (`packages/db-p2p-storage-fs/src/store-lock.ts`): `<basePath>/store.lock` created exclusively holding `{ pid, hostname }`; same host and a live pid refuses with `StoreLockedError`; anything else is stale and replaced, three attempts.
- **`WriteGroup`** (`packages/db-p2p/src/storage/write-group.ts`): a backend that throws its own `StoreFailedError` has its cause unwrapped into the group's.
- **`upgrade-check`** reader (`packages/upgrade-check/test/current-build.ts`) keeps and closes its fs store, so its restart is a real reopen through replay.
- **Docs**: `storage.md` §4 and §5 describe the composition and the layout (log, sealed log, lock, `proofs/`); Invariant 6's file-backend row and *The file backend* paragraph give the record shape, the write-ahead rule, strict replay, the lock and the registry; `docs/repository.md` Invariant P says a promote is two entries of one log record; the fs README has *Write-ahead log* and *Durability* sections and names the lock's limit.

## Review findings

**Read first:** the implement diff (`ticket(implement): file-storage-commits-groups-through-a-log`), then the current state of every file in `files:`, since `file-store-checkpoint-and-shared-log` rewrote parts of them afterwards.

**Build and test state at HEAD.** The tree at HEAD does not type-check: commit `67ba29a0` (the runner's timeout commit for `implement/3.1-storage-flush-takes-a-sync-deadline`) made `BatchBackend.sync` and a `CommittedBatch` return required in `packages/db-p2p` without updating the fs backend, so this package's build fails and its specs refuse to load. That is not this ticket's work and is owned by the 3.1 resume; it is written up in `tickets/.pre-existing-error.md` for the runner's triage. This review verified its code in a scratch worktree at `efe5a06c`, the commit before that one, with the five edited files copied in: `@optimystic/db-p2p-storage-fs` builds and its suite passes, 100 passing and 1 pending (the POSIX-only raw-colon case, on win32), down from 101 by the one case cut below. In the main tree, `yarn lint` (repo-wide eslint, before and after the edits), `yarn lint:docs` (345 anchored citations resolve) and eslint over the package's `src` and `test` all pass; the worktree and its sibling-repo junctions were removed afterwards.

**Checked by reading and running.**

- The record codec: lengths and offsets are read through a `DataView` built on the buffer's own `byteOffset`, values are copied out with `slice` so a replayed file's buffer is not retained, a path over 65535 bytes is refused at encode, and a delete with a value fails decode.
- Replay and open ordering: the tree is synced before the log is truncated, a failed replay leaves the log untouched for the next open, a failed open releases the lock, a lock refusal does not latch the log, and an instance released before or during its open waits for the open and then releases the handle and lock.
- The commit queue: commits, seals and the final checkpoint are serialized on one never-rejecting chain; a commit enqueued after the last release sees `closed`; a failed apply leaves the record durable and the log latched, and the next open rebuilds the tree from it (the spec pins this at the log and at the store).
- The registry: `acquire` is synchronous so two acquirers in one tick share one instance; `release` deletes the registry entry and records the closing promise before yielding, so a log acquired meanwhile waits for it.
- The lock: a live same-host pid refuses from open, from a read (`StoreLockedError`) and from a flush (`StoreFailedError` around it); a dead pid's and another machine's lock are replaced; the refusal keeps the holder's lock.
- Docs: `storage.md` §4, §5, Invariants 5 and 6 and the write-order list, `docs/repository.md` Invariant P, the fs README and `packages/db-p2p/readme.md` all describe the code as it stands. No stale mention of the old atomic writer, temp files or `proper-lockfile` remains outside one comment that correctly describes an older build's leftovers.
- The `WriteGroup` unwrap, the `with-read-cache.ts` note and the `upgrade-check` reader change are each one site and read correctly.

**Minor, fixed in this pass.**

- `test/fsync-count.spec.ts` asserted at most one sync per group, so a write path that stopped syncing altogether would still pass. Tightened to exactly one for the pend and the commit; it holds for 1 and 8 blocks.
- Cut the "a store written by a build before the log opens over its tree unchanged" case from `test/file-write-log.spec.ts`: `packages/upgrade-check` opens the trees real older releases wrote through this same replay, and the "not a log" case already pins the fresh header. A comment at the site says where that contract lives.
- Added a sentence to `FileWriteLog.open`'s doc: a refused or failed open is kept for the instance's life and the instance is shared by every store over the directory, so a retry after the holder exits means closing those stores and opening a new one. Nothing in the tree retries without that, but the registry makes it non-obvious.

**Tripwires recorded as `NOTE:` comments.**

- `zlib.crc32` sets a Node floor of 22.2 (or 20.15) for this package, which the repository nowhere declares; on an older Node the first commit throws a `TypeError`. At the import in `file-write-log.ts`.
- The apply writes straight to the canonical path, so only a second store of the same kind over the same directory could read a torn file, a shape Invariant 5 already excludes. At `applyBatch` in `file-write-log.ts`.
- The lock identifies its holder by pid and hostname alone: a reused pid refuses an open until the file is removed by hand, and a changed hostname lets a machine replace its own live lock. At `acquireStoreLock` in `store-lock.ts`, beside the existing create-then-write note.
- The raw-colon sibling delete entry names a path only a POSIX build can spell; a log carrying one and moved unreplayed to win32 would fail the open on anything but ENOENT. At `toLogEntries` in `file-batch-backend.ts`.
