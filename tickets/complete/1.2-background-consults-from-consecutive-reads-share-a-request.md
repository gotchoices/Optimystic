# Background consults started by consecutive reads share one request per peer

Source: GitHub sereus#60. A restarted member reads each table once, serially; no held block has a read-repair window stamp after a restart, so each read started one background consult in its own read's `ConsultRound` — one `/db-p2p/sync` request per peer per read (measured 45 / 81 / 129 / 227 requests for 4 / 16 / 32 / 64 tables).

## What was built

- `BackgroundConsultRounds` (`packages/db-p2p/src/repo/background-consult-rounds.ts`) holds at most one open `ConsultRound` shared by the consults that run behind reads. It closes `readRepairCoalesceMs` after its first seat joins (unref'd timer), or at once on its 32nd seat (`MAX_CONSULT_BATCH_BLOCKS`), and logs `cluster-fetch:background-round` `{ blocks, reason }`. A closed round still sends only when every joined seat is ready.
- Knob `readRepairCoalesceMs` (default 250, `DEFAULT_READ_REPAIR_COALESCE_MS`) on `ClusterConsensusConfig` and `clusterPolicy`, validated by `resolveReadRepairCoalesceMs`; `0` keeps each read's background consults in its own round.
- `CoordinatorRepo.startHeldBlockConsult` seats a background pass in the shared round when coalescing is on (`backgroundSeating`). Consults a read waits on (missing block, floor, `'paranoid'`, `awaitWindowConsults`) keep the read's own round.
- The read context moved from the round to each question (`ConsultRound.join(context)`, `ConsultAsk.context`), since one request can now carry questions from reads of different collections. The production batch callback already ignored it.
- Docs: transactions.md (new paragraph, staleness bound grows by `readRepairCoalesceMs`), debugging.md (`cluster-fetch:background-round` entry, updated deferral entry), internals.md, cluster.md knob list.

**Checked and correct:**

The full-close on the 32nd seat happens before that seat is ready, so the barrier still waits for it.
- Slot accounting: a shared round of up to 32 passes is one slot (`slotsToJoin` is 0 for seats 2–32); a round opened by `current()` that no pass joins costs nothing and is reused.
- Per-question context: `PendingAsk` keeps the first registrant's context, which is sound because a background round holds at most one pass per block and a read's round has one context. The single-block callback (self, older peers) now gets each question's own context. No other `ClusterLatestBatchCallback` implementation still takes a third parameter (grepped: production, mesh harness, tests only).
