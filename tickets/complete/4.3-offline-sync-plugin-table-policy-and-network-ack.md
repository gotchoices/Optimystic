Third of the five stage-4 tickets. Two coupled pieces landed: the `optimystic.offline` table tag ([§Per-table policy](../../docs/offline-sync.md#per-table-policy)), and the rule that a network-acknowledged commit made while transactions are queued waits behind them ([§Network acknowledgement behind a non-empty queue](../../docs/offline-sync.md#network-acknowledgement-behind-a-non-empty-queue)).

## What landed

**The tag.** `optimystic.offline` takes `'queue'` (default) or `'network'`. The vtab reads it (`offlinePolicyTag` in `optimystic-module.ts`) at construction and again in `followSchemaTags` on every `table_modified`, and publishes it to the controller (`OfflineMode.setTablePolicy`) at full initialization (beside `registerCollections`) and on each tag change; `withdrawOfflinePolicy` is called beside `forgetInCommitReports` on DROP and on a refused CREATE. Any other value reads as `'queue'` and logs `offline:unknown-policy-tag` once per vtab instance. Persistence and hydrate are the existing tag machinery, unchanged.

**The route at commit.** `TransactionBridge.commitTransaction` now asks `offlineRoute()` (non-session only):
- `local` — began in offline mode, the dirty set can be one entry (`queueableSet`, the old `localAcknowledgementSet`), and no table behind a staged collection has policy `'network'` (`networkPolicyTable`, logs `offline:network-policy`). Policy only demotes.
- `behind-queue` — network-acknowledged (mode off, a `'network'` table, or begun before `enter()`) while `offline.hasQueuedEntries()`, **or** while a staged collection still holds a sealed segment with nothing queued (a failed entry's removal still dropping it — added to avoid a `SealedSegmentsError` race the ticket did not name).
- `undefined` — legacy direct sync, as before. An unqueueable dirty set with a non-empty queue logs `offline:queue-bypassed` and commits ahead (see gaps).

Both queue routes seal through `sealIntoQueue` (the old `sealForLocalAcknowledgement`, same `mode=offline` trace). `behind-queue` then calls `awaitQueuedCommit`, which awaits `OfflineMode.awaitNetworkAcknowledgement` and ends the transaction **without restoring** in a `finally`:
- `committed` → resolves, latch released, nothing reported (the drain already reported once).
- `failed` → throws the status's mapped `error`; latch set to its message only when `committedTables` is present, else released.
- `OfflineCommitTimeoutError` / `QueueDisposedError` → thrown as is, latch unchanged.
A failure to enqueue (disposed queue, drain stopped on a defect) goes through the ordinary failed-commit path (snapshot restore), since nothing was sealed.

The old catch body became `afterFailedCommit(error)`, and the four copies of transaction teardown became `endTransaction()`. Note that the success path now also clears `currentTransaction.collections`, which only the failure paths did before; that map is read only while `isActive` (`CollectionFactory`), so this is harmless.

**The controller** (`offline-mode.ts`): the policy map (`setTablePolicy`, `withdrawTablePolicy`, `tablePolicy`). `whenSettled(id)` is private and never rejects: it resolves the outcome from `onQueueStatus` after listeners and announcements, `undefined` on dispose, or the retained outcome if already settled. `awaitNetworkAcknowledgement` races it against `networkCommitTimeoutMs`. On expiry, `queue.discard`:
- succeeds → awaits the `failed`/`discarded` status (so the rows are gone before `commit` throws), then throws `sent: false`;
- `EntryNotDiscardableError` → announces the entry's tables to watchers (Quereus fires none for a commit that throws, yet the rows stay in view), then throws `sent: true`;
- `UnknownEntryError` (left the queue as the clock ran out) → answers its outcome.
`dispose()` now awaits the queue's dispose, then resolves remaining waiters with `undefined` (→ `QueueDisposedError`), so an in-flight entry that commits during disposal still answers `committed`. `announceRemoval` was renamed `announceChanged`.

**`OfflineCommitTimeoutError`** extends `QuereusError` with `StatusCode.BUSY`, carries `transactionId`, `sent`, `timeoutMs` (and the `EntryNotDiscardableError` as `cause` when sent). It is exported from both entries.

**Option** `offline.networkCommitTimeoutMs` (parsed in `offline-config.ts`) defaults to `NetworkCommitBoundMs` (new `network-commit-bound.ts`, five minutes). That is the former `LegacyCommitTtlMs`, moved out of the bridge so both files can read it without a circular import (`txn-bridge.ts` imports `offline-mode.ts` by value).

**Docs:** README § Offline mode has the tag table, the wait rule, both timeout arms with the `discarded` status, dispose, and the bypass shape; the two "Not yet" bullets this closes are removed. docs/offline-sync.md got the option, the implementation names, and stage 4 at three of five landed. docs/debugging.md got the four new log lines. `yarn lint:docs` is clean.

## Tests added — `test/offline-mode-network-ack.spec.ts` (two-node mesh, 7 cases, ~5 s)

- With nothing queued, a `'network'` table, alone and beside a `'queue'` table in one transaction, is network-acknowledged: no status, rows on B when `exec` resolves. A table tagged `'later'` is locally acknowledged (`queued`). Pins the demotion, its whole-transaction rule, and the unknown value.
- A `'network'` autocommit insert behind a queued entry while B is unreachable stays pending through a further refused attempt of the head. After reconnect, the order is `committed:E1`, `committed:E2`, `exec-resolved`, with one `onCommitDurability` report for E2. Pins the wait, its order, and "do not report twice".
- `exit()` with an entry queued, then an `update` of that entry's row: it waits and lands after it. This is the old `SealedSegmentsError` gap.
- A network-acknowledged `update` behind a parked entry, refused by B's rival change: `exec` rejects with `ConcurrentModificationError` (status `concurrent-modification`); A reads B's value plus the queued insert; `isDegraded()` is false; the next `update` commits to B. Pins the failed arm and no snapshot restore.
- Timeout before send (`networkCommitTimeoutMs: 200`, head parked by `parkingPends`): `OfflineCommitTimeoutError { sent: false }` with the right `transactionId`; `status(id)` is `failed`/`discarded`; the row is gone.
- Timeout after send (`networkCommitTimeoutMs: 1_000`): an `onStatus` hook swaps in a second gate and releases the first the moment the second entry queues, so the second is in flight when the clock runs out. It gives `sent: true`, the entry is still in `entries()`, its row is still visible, and after release `status(id)` is `committed` and B holds both rows.
- `alter table Notes set tags ("optimystic.offline" = 'network')` applies to the running table, and after `whenCatalogPersisted` a fresh `Database` over the same transactor that `hydrate`s also network-acknowledges.

`parkingPends` moved from `offline-mode-removal.spec.ts` into `test/commit-gate.ts` (exported) so both specs share it.

## Known gaps and things for the reviewer to judge

- **The unqueueable shape still overtakes the queue.** The ticket says every network-acknowledged commit waits "whatever made it one (… the fall-back of ticket 4.1)". But that fall-back is exactly a dirty set that cannot be one entry (two tables over one collection URI, mixed transactors, a tree with no collection), so it cannot be sealed and cannot wait. It takes legacy sync, logged `offline:queue-bypassed`, and is refused with `SealedSegmentsError` when it writes a collection with queued entries. The README says so. The alternative was to refuse it outright while anything is queued; judge which is right.
- **Not tested, by inspection only:**
  - `plugin.dispose()` during the wait (`QueueDisposedError`; an entry committing during disposal answers `committed`).
  - The once-per-table log of an unknown tag value.
  - The watcher announcement on the `sent: true` arm.
  - The sealed-segment arm of the behind-queue test (removal in progress with nothing queued).
  - Session mode never reaching the route (`offlineRoute` is skipped when `this.session` is set).
- **Timing assumption in the `sent: true` test:** the first entry must commit within 1 s of its gate's release on the in-process mesh (observed ~20 ms). If that case flakes, raise `networkCommitTimeoutMs` there.
- **Pre-existing latency, not filed:** the `exit()`-then-update case takes ~2.6 s. Node B keeps the consensus record of the first entry's attempts made while it was cut off, and that record wins "conflict race lost" against the second entry's pends (five refusals with backoff) until the cohort's ~2 s stale-record cleanup clears it. `offline-mode.spec.ts`'s "several entries" case shows the same ~2.9 s. It may be worth a backlog look at whether a refused attempt's record should be abandoned on B sooner.
- **Retained outcomes include network-acknowledged commits:** a commit that waited behind the queue leaves its terminal outcome in `outcomes()` like any entry, documented as "like any". An application that never entered offline mode may see outcomes it did not ask for after `exit()`.
- **Policy is per table but applied per collection:** two tables declared over one URI share collections, so writing either one counts as writing both, and one `'network'` table demotes writes to the other. This is conservative and deliberate.
- **Latch on a local commit that wrote nothing:** a locally acknowledged commit that staged nothing still leaves the degraded latch as it was (unchanged from 4.1). A behind-queue commit that staged nothing releases it, as legacy sync does.

## Review findings

Read the `ticket(implement): offline-sync-plugin-table-policy-and-network-ack` diff first (bridge, controller, module, config, tests, README, docs/offline-sync.md, docs/debugging.md), then the handoff above.

**Validation run:** plugin `yarn build`, `yarn typecheck` (exit 0), full plugin `yarn test` 1087 passing / 14 pending / smoke ok, eslint clean on every touched source and test file, root `yarn lint:docs` clean. A grep for the renamed symbols (`LegacyCommitTtlMs`, `sealForLocalAcknowledgement`, `localAcknowledgementSet`, `announceRemoval`) finds no stale reference in code or docs.

**Correctness — checked, no defect found:**
- Route decision (`offlineRoute`): the demotion only ever goes local → network; a `'network'` table with nothing queued takes legacy sync; a behind-queue commit with nothing staged queues nothing and releases the latch, a local one with nothing staged leaves it, matching 4.1.
- Nothing runs between `sealIntoQueue` and `whenSettled`'s registration (both synchronous up to the first `await`), so a waiter cannot miss its own entry's terminal status.
- `whenSettled` never rejects; `settledWithin` clears its timer on both arms; a waiter left after a `sent: true` timeout is resolved later by the entry's own outcome or by `dispose`, so nothing leaks unboundedly.
- `dispose`: `OfflineQueue.dispose` awaits the loop and the in-flight submission's outcome before the controller resolves leftover waiters with `undefined`, so the "committed during disposal answers `committed`" contract holds by construction.
- `failed` arm: ends the transaction without restoring (the queue already dropped and replayed), latch set only with `committedTables`, as documented.
- Calling `Database.notifyExternalChange` from inside the commit hook on the `sent: true` arm is safe: in Quereus it takes no exec mutex (`notifyExternalChange` in `@quereus/quereus/src/core/database.ts` only dispatches to the watcher manager), and the call is fire-and-forget.
- Policy keys: `setTablePolicy` and the bridge's `collectionTables` both key by `qualifiedTableName`, and index collections are registered under their table's name, so writing only an index tree still sees the table's policy. `readOfflinePolicy` in the vtab constructor runs after `super()` sets `tableName` and after field initializers, so the once-per-table log flag is in place.

**Found and done:**
- The unqueueable shape (two tables over one URI) bypassing the queue — the handoff's open question. It contradicts the design's "cannot commit ahead of them" only when the set writes no collection with queued entries (otherwise `SealedSegmentsError` refuses it), and is reachable only through that unusual declaration. Kept the implementer's behaviour and recorded it as a `NOTE:` tripwire at the `offline:queue-bypassed` site in `TransactionBridge.offlineRoute`, naming the revisit condition (refuse there while anything is queued if an unqueueable shape becomes ordinary). Not filed: no current-release anchor beyond a configuration the bridge already treats as a fallback everywhere.

**Considered, left as is (with reason):**
- `offlineRoute()` is computed outside the commit's `try`: it is synchronous and does not throw on any production path, so moving it buys nothing.
- The ~2.6 s latency of the `exit()`-then-update case (a refused attempt's consensus record on the cut-off member out-racing the next entry until stale-record cleanup) is pre-existing, shared with `offline-mode.spec.ts`'s "several entries" case, and a performance concern rather than a defect; not filed.
- Retained outcomes for network-acknowledged commits that waited, and per-collection policy for two tables over one URI: deliberate, documented in README § Offline mode.

**Tests:** the seven new cases each pin a named piece of the specification (demotion and its whole-transaction rule, ordering and single report, the old `SealedSegmentsError` gap, the failed arm without restore, both timeout arms, tag change plus hydrate); none restates the implementation, none cut. Not added: a `plugin.dispose()`-during-wait case (the in-flight submission would have to be released by the test for `dispose` to return, which reduces it to the committed arm already covered) and the sealed-segment-with-nothing-queued arm (needs a removal held mid-drop; the arm is a one-line widening of `behindQueue`). Timing assumption in the `sent: true` case (first entry commits within 1 s of release on the in-process mesh) noted by the implementer; raise `networkCommitTimeoutMs` there if it ever flakes.
