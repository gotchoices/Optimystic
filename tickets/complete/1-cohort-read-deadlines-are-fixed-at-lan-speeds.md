# Cohort read deadlines are fixed at LAN speeds — complete

GitHub issue #22. One operator field, `clusterPolicy.cohortQueryTimeoutMs`, default 1000 ms, sets both per-peer deadlines on the read path; the whole-pass bound is derived from it as `max(5000, 5 × per-peer)` rather than declared separately. **A node that declares nothing behaves exactly as before** — the same 1000 ms per peer and the same 5000 ms pass bound, now arrived at through the resolvers rather than read off constants.

## What shipped

`ticket(implement): cohort-read-deadlines-are-fixed-at-lan-speeds` landed the field and its resolvers; this review pass added a representability ceiling on the field, cleared a leaked race timer, and parked one tripwire. The shape:

- **`packages/db-core/src/cluster/structs.ts`** — `DEFAULT_COHORT_QUERY_TIMEOUT_MS = 1000` beside `DEFAULT_SUPER_MAJORITY_THRESHOLD`, and the optional `cohortQueryTimeoutMs` on `ClusterConsensusConfig`. Putting it there is what makes it reach `ClusterMember` and `CoordinatorRepoConfig` (already `Partial<ClusterConsensusConfig> & …`) with no new parameter anywhere.
- **`packages/db-p2p/src/cluster/cluster-policy.ts`** — `resolveCohortQueryTimeoutMs(declared)` (the default when undeclared, and a **throw** on a value that is not a finite number above zero or is above `MAX_COHORT_QUERY_TIMEOUT_MS`; a positive fractional value is accepted, since this is a duration), `reconcilePassTimeoutMs(perPeer)` = `max(RECONCILE_TIMEOUT_MS, 5 × perPeer)`, and `MAX_COHORT_QUERY_TIMEOUT_MS`. `ResolvedClusterPolicy` carries both numbers concretely.
- **`CoordinatorRepo`** — `LATEST_QUERY_TIMEOUT_MS` is gone; the constructor resolves the per-peer number through the shared resolver (so the readme's manual wiring and the node assembly cannot default differently) and derives the pass bound from it. `queryClusterForLatest` uses the per-peer value, `restoreCorroborated`'s acquisition the derived one.
- **`ClusterMember`** — the module-level `ReconcileTimeoutMs` is gone; the member derives `reconcileTimeoutMs` in its constructor from the same two functions.
- **`libp2p-node-base.ts`** — `fetchArchiveFromPeer`'s hardcoded `1000` reads `consensusConfig.cohortQueryTimeoutMs` off the one `resolveClusterPolicy` result. Contract unchanged: a timed-out fetch still resolves to "no archive" and the pass moves on.
- **`RECONCILE_TIMEOUT_MS`** is now documented as the *floor* of a derived bound (and the whole bound for an unconfigured node), not the bound.
- **Docs** — `docs/transactions.md` §Read Consistency and Staleness (the knob table, the derived-bound sentence, a "when to raise it" paragraph), `docs/debugging.md` (`cluster-fetch:no-quorum`'s `silent` row and the `noArchive` bullet), `docs/internals.md` (the reconcile bullet), `packages/db-p2p/docs/cluster.md` (a `cohortQueryTimeoutMs` section beside the other `clusterPolicy` fields, plus the field in the `ClusterConsensusConfig` block).

`mesh-harness.ts` needed no change: its `makeFetchArchive` is in-process with no deadline of its own, and it already threads the resolved policy to both the member and the coordinator.

**No coupling assertion accompanies the pass bound, deliberately.** Both callers apply one derivation function to the `cohortQueryTimeoutMs` in their own config, and on a live node both read the one `resolveClusterPolicy` result — one function on one input cannot produce two numbers, so an `assertSuperMajorityCoupling`-style check would assert an identity. What would re-open the drift (either side gaining its own default or its own field) is recorded at `ClusterMember`'s field doc and again at the assignment.

## Review findings

Read the implement diff first, then the handoff. Scrutinised: the import direction the new `RECONCILE_TIMEOUT_MS` import creates, the threading of the resolved policy to all three consumers, the completeness of the sweep for hardcoded read-path deadlines, input validation, timer cleanup, the tests, and every doc the change touched or should have.

**Major — none filed.** Nothing found rose to a class-level invariant or a current-release anchor beyond what the two inline fixes closed, so nothing met the filing bar.

**Minor — two, both fixed in this pass.**

- *The validation admitted values its own consumer cannot honour.* `resolveCohortQueryTimeoutMs` accepted any finite number above zero, but `setTimeout` truncates its delay to a 32-bit signed integer on every platform this runs on and fires almost immediately when that overflows. A declared budget above about 4.97 days — or, through the `5 ×` the pass bound applies, anything whose product overflows — therefore expired *every* read-path deadline after a millisecond: the exact failure the field exists to end, arrived at harder and with no diagnostic but a runtime warning. The function's own `NOTE:` argues it must fail fast rather than fall back precisely because there is no safe direction to fall toward, and this was the one admitted input that fell somewhere worse than the default. The realistic path to it is a host computing the field in the wrong unit (microseconds or nanoseconds where milliseconds were meant), which the implement handoff had already named as a new embedder failure mode. Fixed: `MAX_COHORT_QUERY_TIMEOUT_MS = floor((2 ** 31 - 1) / 5)`, refused above it with the limit in the message, and stated at the code site, on the db-core field, in `docs/transactions.md` and in `packages/db-p2p/docs/cluster.md`. Two tests: the too-large value joins the existing throw table in `cluster-policy.spec.ts`, and one new case asserts the ceiling *itself* is accepted and still yields a pass bound a timer can hold — an off-by-one there would mean the highest legal setting silently fires its reconcile pass immediately.
- *A race timer was leaked for the length of the budget.* `fetchArchiveFromPeer`'s losing deadline was only `unref`'d, never cleared, so a peer that answers quickly still left a timer pending for the rest of the budget — one per fetch per peer. Harmless while the budget was a hardcoded second; an operator raising it to tens of seconds multiplies the retention by the same factor. Fixed with a `finally` clear, matching the `withDeadline` helper in `coordinator-repo.ts`, whose own doc already states that rule.

**Conditional / speculative — one tripwire parked, no ticket.** The read path makes the *same* request of the same peer twice on a repairing read: `clusterLatestCallback` asks `requestBlock({ blockId, rev: undefined })` and throws the archive away after projecting the claim, then the acquisition's `fetchArchiveFromPeer` asks for it again. On a LAN that is invisible; on the relayed link this ticket is about it is a second `cohortQueryTimeoutMs` per peer. It is pre-existing, out of this ticket's scope, and conditional on read-repair latency mattering, so it is a `NOTE:` at `fetchArchiveFromPeer` naming the remedy (carry the consult's archive through to the acquisition) rather than a ticket.

**Considered and declined — none encountered.** No accepted-tradeoff `NOTE:` sits at any site this change touches.

**Checked and left alone, with reasons:**

- *The import the new value edge creates.* `cluster-policy.ts` → `reconcile-block.ts` is a runtime edge, and `reconcile-block.ts` does reach back to `cluster-repo.ts` — but as a clause-level `import type`, which is erased. Its other runtime imports (`storage/block-archive.ts`, `reputation/types.ts`, `cluster/quorum-restore.ts`, `cluster/certified-claims.ts`, `cluster/commit-proof.ts`, `logger.ts`) reach neither `cluster-repo.ts` nor `coordinator-repo.ts`, so the comment at the import is accurate and there is no cycle. Verified by reading every importer of `cluster-policy.js` and every value import of `reconcile-block.ts`, not by trusting the note.
- *The sweep is complete.* No `setTimeout` or timeout constant left in `db-p2p/src` still bounds a read-path round trip with a literal. The write and push deadlines (`pushBlockToPeers`, `block-transfer.ts`, `spread-on-churn.ts`) are untouched, which the ticket scoped out — same latency exposure, different path, no report against it, and still the right call.
- *The resolved `reconcilePassTimeoutMs` field is read by no production code* — both consumers take `ClusterConsensusConfig` / `CoordinatorRepoConfig`, which do not carry it, so each derives its own. That is the reason it exists (a self-describing, directly assertable resolution result) rather than an oversight; widening two constructor types to read it would buy nothing the shared derivation does not already guarantee.
- *Docs.* Every file the change touched was re-read against the new reality, plus the ones it should have: `docs/correctness.md`, `packages/db-p2p/docs/repo.md`, `packages/db-p2p/readme.md` and `packages/quereus-plugin-optimystic/readme.md` say nothing the field makes stale (the plugin readme links out to the knob table). The readme's manual-wiring paragraph still only needs to mention cluster size, since the shared resolver supplies this default.
- *Tests.* Cut none. The one I weighed cutting is `'derives the pass bound the same way for every caller'`, which reads as asserting `f(x) === f(x)` — kept because it fails the moment `resolveClusterPolicy` stops computing the field through the shared derivation, which is exactly the drift the field doc names as the trigger for adding a real coupling assertion. The new `coordinator-repo-cohort-query-deadline.spec.ts` pins the one thing resolution cannot — that the per-peer site reads the *resolved* number, in both directions over one 250 ms answer — and would fail against the old hardcoded 1000. Its choice of small declared durations over the default is sound: there is no fake-timer library in `db-p2p` and `withDeadline` uses real `setTimeout`, which the class's `now` seam (read-repair window only) does not cover. Both cases together cost roughly 0.3 s of real time with about a 6× margin either side of the delay; the spec header's "roughly half a second" is a harmless over-estimate.
- *The handoff's own listed gaps, weighed and left as designed.* The default is unchanged, so the reporter's deployment is fixed by setting the field rather than out of the box — that is the ticket's design, and the adaptive budget is explicitly out of scope. The throw is a plain `Error` at construction, which is the intended direction. `ClusterMember.withReconcileTimeout` and `fetchArchiveFromPeer` are pinned only by the build and the shared derivation; an end-to-end test of the archive fetch would exercise the same arithmetic on the same round trip to the same peer, so it would restate the implementation rather than pin a contract.
