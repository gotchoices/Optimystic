# File store checkpoint and shared log

Last of three tickets from `file-storage-pays-one-fsync-per-write-group` (GitHub #37). `file-storage-commits-groups-through-a-log` left `FileWriteLog` appending for ever with a `dirty` set of everything written since the last truncation; this ticket spends that set in a checkpoint, moves `FileKVStore` onto the same log, closes the stores in the hosts, and rewrites the docs.

## What landed

- **Checkpoint** (`FileWriteLog.checkpoint` and `checkpointOnce` in `packages/db-p2p-storage-fs/src/file-write-log.ts`):
  - *Seal*, in the commit queue: close the handle, rename `write-ahead.log` → `write-ahead.log.sealed`, create a fresh header-only log (file sync + directory sync), swap in an empty `dirty` set, reset the byte counter. Skipped when nothing was appended since the last seal.
  - *Sync*, off the queue: every dirty file then every dirty directory, 16 at a time (`syncDirtyPaths` / `forEachConcurrently`). ENOENT files skipped.
  - *Truncate*: unlink the sealed segment, sync the directory.
  - Triggers: after each append, an idle timer is re-armed (`checkpointIdleMs`, default 5 s, unref'd through `armUnrefTimer`, injectable `setTimer`), and the size threshold (`checkpointBytes`, default 16 MiB) starts one in the background. On the last `release`: wait for the commit queue and any in-flight checkpoint, run a final one, release the handle and lock even if it fails.
  - One at a time: `checkpoint()` while one runs sets a flag and returns the running promise, which loops once more.
  - A failure latches the log (`fault`), so the next flush of any store over the directory rejects `StoreFailedError`. Skipped when failed or never opened.
- **Replay** (`replay` / `replaySegment`): sealed segment first, then the current log, as one log — a sealed segment that stops short skips the current log. Touched paths synced, then the sealed segment unlinked and the directory synced *before* `createEmptyLog` truncates the current log. That order matters: a sealed segment that outlived the current log's truncation would replay old content alone.
- **Options**: `FileWriteLogOptions { checkpointBytes, checkpointIdleMs, setTimer }`, validated at store construction (`assertFileWriteLogOptions`, `RangeError`). `FileRawStorageOptions` and `FileKVStoreOptions` are `WriteGroupOptions & FileWriteLogOptions`. The log is shared per directory, so its settings are the first acquirer's; a later store naming different values gets a `write-log` debug line (`noteDifferingSettings`).
- **`FileKVStore`** (`packages/db-p2p-storage-fs/src/file-kv-store.ts`): `WriteGroup<string>` (canonical key = the key itself) over `FileWriteLog.acquire(basePath)`. `get` reads the overlay, then the tree after the log's open. `list` snapshots the overlay before awaiting, then merges unflushed puts and deletes over the directory walk. `flush` is the group's. `close` flushes and releases the reference. On-disk shape unchanged (`<key>.json`). `atomic-write.ts` deleted; `fsyncDir` was already in `file-write-log.ts`.
- **Hosts**:
  - `packages/reference-peer/src/cli.ts`: `openStores` builds both stores (one base path) and keeps them on the session. `stopNetwork` closes them after `node.stop()`. A failed `createLibp2pNode` closes them too.
  - `upgrade-check` writer (`close?.()` on both, since older published builds have no `close`) and reader (closes both, kv then raw). `write-fixture.mjs` now refuses to pack a fixture containing a `store.lock` (`refuseStoreLocks`).
- **Docs**:
  - fs README rewritten: options table; close after `stop()`; the *Write-ahead log* section (record, sync, checkpoint, what a crash loses); layout with `write-ahead.log.sealed`; *Durability* (one sync per group, directory syncs only at checkpoint and open, win32 files only; three syncs per solo write against #37's seventy-plus); a *Downgrading* paragraph; sibling list fixed (React Native is LevelDB).
  - `storage.md`: Invariant 6's table row and *The file backend* paragraph describe the checkpoint, replay order and the shared log; the layout gains the sealed file; §5 now says `FileKVStore` uses `WriteGroup`; the promote primitive reads "one write-ahead-log record" instead of "rename".
  - Invariant 5 no longer says "not enforced anywhere": that has been stale since the lock landed. It now says the fs backend enforces it on one machine.
  - `db-p2p` readme: the layout block gains the three root files, and the usage example closes the storage after `stop()`.
  - `NodeOptions.kvStore` doc says the node never closes it.
  - `docs/repository.md` Invariant P was checked and needed no change.

## How to exercise it

- `node packages/reference-peer/dist/src/cli.js run --offline --storage file --storage-path <dir> --action add-entry --diary d --content x`. Then `<dir>` holds no `store.lock` and a 15-byte header-only `write-ahead.log`, and a second run with `--action read-diary --diary d` reads the entry back. I ran exactly this.
- `FileWriteLog.acquire(dir, { checkpointBytes: 1 })` and one `commit` checkpoints without being asked. `DEBUG=optimystic:db-p2p-storage-fs:write-log` shows background checkpoint failures and settings mismatches.

## Tests added or changed

`test/file-write-log.spec.ts`, under the new describe *FileWriteLog checkpoint*:
- *A batch larger than the size threshold is checkpointed once, without being asked.* Watches renames to the sealed name. The size trigger fires with no call to `checkpoint()`, exactly one seal happens, and the log ends header-only with the sealed file gone.
- *The idle checkpoint is re-armed by every append and checkpoints when it fires.* Uses an injected `setTimer`: two appends leave one armed timer, and firing it seals the log.
- *A checkpoint that fails before discarding its sealed segment…* This is the crash test:
  - The unlink of the sealed file is parked, a commit is made meanwhile (it lands in the new log), then the unlink throws.
  - Asserts the store is latched and both segments are on disk.
  - Deletes the tree, as a crash would, and reopens: the sealed segment is replayed, then the current log wins, and both files are cleaned up.
  - A mutation run that swapped the replay order failed this test.
- *A commit made while a checkpoint is syncing stays in the new log, which that checkpoint does not discard.* Covers the success path of the same interleaving, and reads the value back after a reopen.
- *A sealed segment that stops short ends the replay: the current log is not applied.* Uses hand-built segments.

`test/file-storage.spec.ts`: the two atomic-writer cases (`.tmp` sibling, failed rename) are deleted along with their helpers. The `FileKVStore` block is now *FileKVStore over the write-ahead log*:
- `list` merges the tree with unflushed puts and hides unflushed deletes, and the tree changes only at flush.
- The empty-prefix case.
- A flushed delete of a never-existing key does not throw.
- *Shares one log and one lock with a FileRawStorage over the same directory*, in both orders. Both stores append to one log in flush order. The lock outlives the first close, and the last close removes it and leaves a header-only log. A reopen of both reads the data back.

`test/under-replication-ledger.spec.ts`: stores now come from `trackedStores` and are closed. The two restart cases close the first store before opening the second, so they are real reopens. The shared-path case flushes the raw store.

Support: `trackedStores().openKv` was added. `fs-injection.ts` gains `parkUnlink` (park one path's unlink, then proceed or throw) and `interceptRename`.

## Known gaps and judgment calls for the reviewer

- **The ticket asked for the unflushed-delete case in the ledger spec. I pinned it at the `FileKVStore` layer instead** (the `list` merge test). Through the ledger, an unflushed delete only exists inside `settle`'s window between `kv.delete` and its flush. The behaviour belongs to `FileKVStore.list`, the lowest layer that has it.
- **A seal holds the commit queue** for one handle close, one rename, the new log's header sync and one directory sync. A commit arriving then waits about two syncs. The file and directory syncs themselves run beside commits.
- **A file in the old dirty set may be synced while a later commit rewrites or deletes it.** This is safe because the new log covers the newer content. On Windows it relies on libuv's POSIX-semantics unlink; that tripwire is the `NOTE:` at `syncDirtyPaths`.
- **Release semantics.** `release()` rejects only when the final checkpoint itself fails. A background checkpoint failure is logged on the `write-log` channel and surfaces at the next flush as `StoreFailedError`, not at close.
- **A sealed segment that stops short discards the current log's records** at replay, matching the rule for a bad record inside one log. The tree may still hold some of those writes, since they were applied at commit time. The doc wording says only that the two files are read as one log.
- **Checkpoint settings are per directory, first acquirer wins.** The reference peer and the hosts use the defaults, so there is no conflict in the tree today.
- **Background checkpoints in long test suites.** In specs that leave stores open after deleting their temp dir, a checkpoint fires 5 s later and fails on the missing directory. It logs on a debug channel only, and the timer is unref'd.
- **`write-fixture.mjs` now refuses a `store.lock`**, beyond the readme note the ticket asked for. No published release has the log without the close, since the log landed after v1.15.0, so no existing or future fixture trips it.
- **Downgrade advice is documentation only.** "Open and close once with this build before downgrading after an unclean stop" is in the README, and nothing enforces it.
- **`FileKVStore.list(prefix)` assumes a directory prefix** ending in `/`. The disk walk already did; the overlay merge uses `startsWith`. Every prefix the node lists by ends in `/`.
- **Test cuts the reviewer may make.** The idle-timer test is close to wiring, though it does pin the re-arm. The empty-prefix and never-existed-delete KV cases are cheap carry-overs from the old block.

## Review findings

Reviewed the diff of `ticket(implement): file-store-checkpoint-and-shared-log` before reading the handoff, then the handoff's judgment calls one by one.

**Checked, and found sound:**

- *Checkpoint ordering and crash windows* (`FileWriteLog.checkpointOnce`, `seal`, `replay`). Went through each crash point: after the rename but before the new log exists, during the sync, before the unlink, after the unlink. Every one leaves a sealed segment, the current log or both, and replay handles each. The current log only ever holds records appended after the seal, so replaying the sealed segment first and then the current log is correct. Unlinking the sealed segment before `createEmptyLog` truncates the current log is the order that matters, and the crash test pins it. The implementer reports that a mutation run swapping the replay order failed that test.
- *Dirty-set handoff.* The swap happens inside the commit queue, after the last apply, so no apply can write into a set that is already being synced. A file deleted after the seal is skipped (`fsyncFile` treats ENOENT as done). A file rewritten after the seal is covered by the new log.
- *One checkpoint at a time.* `checkpoint()` called during a run sets `checkpointAgain` and returns the running promise. The seal is skipped when nothing has been appended, so the extra loop costs nothing when there is nothing new. Background checkpoints are never awaited from inside a commit, so the queue cannot deadlock.
- *Release and shutdown.* `shutDown` sets `closed` and disarms the idle timer synchronously, then waits for the queue and any running checkpoint, runs the final checkpoint, and releases the handle and lock in a `finally`. A log that was never opened releases without creating a lock. A failed open (`StoreLockedError`) sets no fault and skips the checkpoint because nothing was appended.
- *`FileKVStore`* (`packages/db-p2p-storage-fs/src/file-kv-store.ts`). `get` reads the overlay and then the tree. `list` takes its overlay snapshot before it awaits, which is what `WriteGroup`'s contract requires. `close` releases the log even when the flush rejects. Reading or writing after `close` re-acquires the log, and nothing releases that reference. That has the same shape as `FileBatchBackend.close`, and the "a write recorded after close() resolves is not refused" `NOTE:` on `WriteGroup.close` already covers it. No caller uses a store after closing it, so no change.
- *Hosts.* In the reference peer, the session is set before any later await, so a failure after the node starts reaches `cleanup` → `stopNetwork` → `stores.close()`. The one gap is the synchronous code between `createLibp2pNode` returning and the session being set. The process exits on any error there, and the next open replaces the dead process's lock as stale, so no change. In `write-scenario.mjs`, `close` has no try/finally, unlike the other two sites. A throw there fails the fixture writer anyway, so I left it.
- *Fixtures.* No checked-in fixture under `packages/upgrade-check/fixtures` contains a `store.lock` or a `write-ahead.log`, so `refuseStoreLocks` rejects nothing that exists today.
- *Docs.* I read the fs README, `packages/db-p2p/docs/storage.md` (Invariants 5 and 6, §4, §5, the layout), the `db-p2p` readme layout and usage, and the `NodeOptions.kvStore` comment. All of them describe the new behaviour. A grep for leftover references to the atomic writer, `.tmp` siblings, or "the log grows for the store's life" found none outside one intended `NOTE:`.
- *Tests.* I kept every test the implementer added. The idle-timer test is close to wiring, but it pins that each append re-arms the timer, which has a branch. The two small `FileKVStore` carry-overs (empty prefix, deleting a key that never existed) each cover a separate case in the error handling. The handoff's decision to pin the unflushed delete at the `FileKVStore.list` layer, rather than through the ledger, is correct: that is the lowest layer where the behaviour lives.

**Found, and parked as tripwires (no ticket):**

- *`fsyncDir` swallows every error, including I/O errors.* A checkpoint now relies on its directory syncs before it discards a log. If a POSIX directory sync fails with EIO, the checkpoint still discards the log. This only matters on a failing disk, and I could not exercise it on win32, where `fsyncDir` does nothing. Parked as a `NOTE:` on `fsyncDir` in `packages/db-p2p-storage-fs/src/file-write-log.ts`.
- *Crash during replay when the sealed segment stops short.* The current log is discarded only by the truncation that follows the sealed segment's unlink. A crash between those two steps replays the current log alone on the next open. A sealed segment holds only synced records, so it stops short only if it was damaged on disk, which makes this conditional on disk damage plus a second crash. Parked as a `NOTE:` in the stopped-short branch of `FileWriteLog.replay`.
