## What was built

**Segment lookups.** `SegmentList` keeps a `Map` beside its array, so `find` is a map read. `Collection.holdsSealed(entryId)` and `Collection.hasSealed()` replace the `.sealedEntries().includes(id)` and `.sealedEntries().length` call sites.

**One kept index.** `OfflineMode.queueWrites` is one `WriteIndex` of the queue. An entry joins it when it is judged and leaves when it commits, and `judgeTransaction` takes an index instead of building one. So `WriteIndex.remove` costs the entry's own keys, its member lists are maps keyed by transaction id, and `insertedAbsent` holds each inserter's freshness per key, read as "any is fresh". An indexed entry's `assured` is a getter that reads `OfflineMode.judgements`.

**A narrow follow on a commit.** `followCommit` is a pure function beside `followOutlooks`. Dependents lose the committed transaction in queue order, each one's kind is derived again by the shared rule (`outlookKind`), and a change of kind passes on through a reverse map, `OfflineMode.dependents`. `OfflineMode.followStatus` picks the route: a `committed` status takes the narrow follow when `judgements.size` equals the queue depth and no walk is owed (`OfflineMode.walkOwed`, added in review). Everything else takes the full walk, which rebuilds the index and the reverse map.

**Constant-time queue read.** `OfflineQueue.queuedEntry` gives one entry and its position. It is constant time for the newest entry and scans only for one a restore inserted ahead of others.

## Where this departs from the ticket

## Known gaps

- A UNIQUE index still scans. `WriteIndex.writersWithin` walks every indexed key of the collection for an `absentRange`, and the existing `NOTE:` there parks it. Measured by the implementer with a scratch loop over `judgeTransaction`: 1.7, 11.8 and 108 microseconds per judgement behind 100, 1,000 and 10,000 indexed keys. The bench has no UNIQUE index, so its flat curve does not cover this.
- Many transactions writing one row still cost more with depth, because each lists every earlier writer in `dependsOn`, and that list is what the outlook reports. Not measured. By reading, a commit in that shape costs what the old walk cost per commit, not less.
- The full walk makes two passes on its rare paths, one for the index and one for the walk. That was simpler than sharing, because the walk's index holds kinds as of the walk and the kept one reads them live.
- `queueWrites` holds a small map per queued key. A `NOTE:` on the field names the remedy if bulk offline writes make it heavy. Not measured.
- The property test does not exercise partial commits, deferred records or never-judged entries. Those take the walk, and the existing SQL-level specs cover them.

## Review findings

Read the diff of `ticket(implement): queuing-a-transaction-costs-the-same-at-any-queue-depth` before the handoff, then each of the handoff's four "please look hard" points.

**Found and fixed: a walk that had to wait could be lost.** `followQueue` returns early while a transaction that left the queue has no terminal status, relying on that status to run the walk. But `followStatus` sent a `committed` status to the narrow follow whenever the counts matched. So when a discard's `failed` arrived while the head's `committed` was still waiting on its journal write, the walk waited, the commit then went narrow, and the walk never ran. The discarded transaction stayed in `queueWrites`, and every later writer of its keys listed it in `dependsOn` until some later walk, so such a transaction stayed `exposed` with no `outlook-changed` to come. The same loss applied to any walk the commit followed: a partial commit's or a restore's. Before this ticket the commit's status always walked. `repro: verified`: the new `offline-outlook.spec.ts` test failed before the fix, listing the discarded transaction, and passes after. Fixed with `OfflineMode.walkOwed`, set when a walk starts or a follow throws and cleared only when a walk completes, and checked by the route. A follow that throws now also recovers on the next commit rather than keeping stale state. `docs/offline-sync.md` §The outlook says so.

**The four points the handoff asked about:**

- *An entry that has left the queue with no terminal status yet.* Checked by reading `OfflineQueue.committed` and `OfflineQueue.remove` and by the reproduction above, which drives this interval; the handoff's "no test drives this" no longer holds for the failure-during-commit order. A transaction judged in the interval lists the leaving entry until its status arrives, and `noteDependencies` records it, so the narrow follow removes it. The reverse order (a commit while a failure is leaving) was already correct: the size check fails and the failure's status walks. Accepted as documented.
- *The coverage check as a count.* A restoring and a leaving entry cancelling out needs a discard during a restore's staging plus an enqueue at that moment, and the restored entry's `queued` status corrects it through the walk. Left as is; the comment in `judgeQueued` records it.
- *The route's precondition as a count.* One unjudged entry beside one leaving passes it. An entry listed and unjudged while a commit is delivered needs a throw out of a judgement: a restore's registration window has the drain held, so no loop commit lands in it. The effect is a transient `outlook-changed`, not counted as an assured failure, because `weighFailure` marks the dependent. Tripwire: `NOTE:` at `OfflineMode.followStatus`.
- *A restored-already-committed entry taking the narrow follow.* Read the path: a dependent loses it at once, and its kind is computed from what remains. Agreed that this is correct. No test pins either behaviour, and none added: it is a timing difference inside one restore pass with the same end state.

**One further behaviour change, accepted.** A deferred record read after a transaction was judged used to reach that transaction at the next commit's walk, which would regress it with `offline:outlook-regressed`. It now reaches it when the record is put back or at the next walk. The host contract (restore before committing) rules that sequence out, as the comment on `followQueue` already says, so nothing was changed.

**Checked, nothing found:**

- `SegmentList`: `seal`, `unseal`, `insert` and `drop` are the only changes to `sealed`, which is private, and each keeps `byEntry` in step. `refuse` changes the shared segment object, which `find` returns.
- `followCommit`: traversal order, `seen` and the `from` bound in `insertInOrder` hold because a dependent always has a higher sequence number than its dependency. A dependency on a deferred record reads as not assured, as in the walk.
- `WriteIndex.remove`: rereads the same `actions` it was added with, and a segment's actions are never rewritten. A partial commit's stale collections are replaced by the walk's rebuild.
- `dependencyFailed`: `holdFollowed` keeps it on a narrow follow and clears it on a walk, as before.
- Per-status cost: `queueState` and `segmentRefused` do not scan the queue. `deferredBelow` costs the number of deferred records per judgement, which is not queue depth and is normally small after a restore. Left alone.
- Resource cleanup: the index holds segment action arrays the collections already hold, until the entry leaves. A `dependents` entry for a deferred record whose dependent committed first lasts until the next walk; it is a small bound and harmless, since `followCommit` skips an id with no judgement.
- Type safety, error handling: the follows stay isolated from the queue's status delivery. No `any` added.
- Implementer's tests: both meet the bar, pinning `followCommit`'s contract against the walk on logic with real branching. None cut. Their claims of having been checked by deliberate breakage were not repeated in review.
