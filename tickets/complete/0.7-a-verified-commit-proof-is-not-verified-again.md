# A verified commit proof is not verified again

Reported as GitHub #68 (Sereus/cadre on React Native). Landed in `ticket(implement): a-verified-commit-proof-is-not-verified-again`.

## What was built

- `verifyBlockCommitProofClaim` is split: the private `verifyProofVotes` holds every check that does not depend on the claim (version, structure, duplicate signers, membership digest, message hash, both rounds' signatures, both thresholds), and the claim step (`findClaimedCommitOp`) always runs afterwards on the proof as given. Votes still come first, so a forged proof for the wrong claim reports the non-attributable `malformed-signature`.
- The votes verdict goes through `judgeProofVotes`: the key is the two thresholds plus the proof's native `JSON.stringify` text, and a miss verifies `JSON.parse` of that text, never the live object, so a remembered verdict is a function of its key alone. A proof JSON cannot encode is verified as given with no memo.
- `VerdictMemo` (no crypto): concurrent calls with one key share one computation; only passing verdicts are retained; retained keys are bounded by summed length (1 MiB) with a 64 KiB per-entry cap, least recently used evicted first. One instance per process.
- Never remembered: the claim step, the content digest of `verifyBlockCommitProofContent`, failing verdicts, the signer cap and anchoring layer of `certifyClaim` / `certifyContent`.
- Measured on Node only (miss 1.44–1.53 ms, of which 0.011 ms is the added encode/decode; hit 0.008 ms). Hermes was not measured; confirmation is left to the reporter on GitHub #68.

## Review findings

Read the implement diff before the handoff, then the callers (`certified-claims.ts`, `reconcile-block.ts`, `coordinator-repo.ts`, `block-transfer-service.ts`, `commit-log-trust-anchor.ts`) and `canonicalJson` in db-core.

- **Soundness of the key (checked, holds).** `verifyProofVotes` reads only `proof` and `thresholds`; db-core hashing goes through `canonicalJson`, which is `JSON.stringify` with a key-sorting replacer, so hashing the parsed copy gives the same result as hashing the original for every value JSON round-trips. I checked the one non-obvious case, a `Uint8Array` inside a message built in process: `JSON.stringify` encodes it as an index-keyed object and `canonicalJson` of the parsed object produces the same text, so a proof built in process verifies the same either way. The threshold prefix holds numbers only, so `a|b|{…}` cannot be ambiguous. A changed message under an unchanged `messageHash`, a changed signature, and another claim each miss or fail. The new spec pins all three, plus a repeat of the original.
- **The claim step on the live proof (checked, accepted).** It can disagree with the judged copy only for an object whose JSON differs from its properties (a `toJSON`, a getter). No production path builds one, and the doc comment says so. A malformed live shape throws inside the outer `try` and reads as `malformed-proof`.
- **Attributability (checked, no change).** Only passing verdicts are remembered, and `isAttributableProofFailure` classifies only failures, so a hit cannot change who is penalized.
- **Memo mechanics (checked).** If a retained verdict is set during `then`, a call arriving before `finally` gets a hit. Deleting from a `Map` while iterating its keys in `evictToBudget` is safe. `compute` starts on a microtask, so a synchronous throw still clears the in-flight entry. Memory is bounded at about 2 MB of key strings.
- **Shared module-level memo (accepted).** It is sound because each verdict depends only on its key. No reset hook is needed until a spec counts signature verifications. The `NOTE:` on `VerdictMemo` already covers a peer churning the memo with valid self-certified proofs.
- **Cost that remains (accepted, already documented).** Every call still runs one native `JSON.stringify`, linear in proof size. The cost `NOTE:` in `queryClusterForLatest` and the `MAX_PROOF_SIGNERS` note already name what to do if this ever shows up in profiles.
- **Tests (kept both).** The `commit-proof.spec.ts` case pins the contract the ticket is about: a hit never aliases another proof or claim. `proof-votes-memo.spec.ts` covers real branching (in-flight sharing, retain or not, LRU refresh and eviction, the entry cap) with a fake computation, not a mock of anything the repo owns. I added no tests because I found no defect.
- **Fixed inline (minor, comment hygiene).** The doc comment on `verifyBlockCommitProofClaim` repeated the measured numbers word for word from `docs/internals.md`. I cut it down to the reason a hit is cheap and a pointer to the docs section.
- **Fixed inline (minor, docs).** `docs/internals.md` §Durable commit proof said proof failures "are never a reputation signal", which contradicts `isAttributableProofFailure`, which does penalize the reasons that prove the artifact lies. I reworded it to state the real rule. This was pre-existing; the handoff flagged it.

- **Tripwires added:** none new. The existing ones (`VerdictMemo` churn, the per-call encode in `queryClusterForLatest`) cover what I saw.
