Second half of stage 7 of [docs/offline-sync.md §Implementation stages](../../docs/offline-sync.md#implementation-stages), now marked implemented. The first half (`offline-sync-outlook-from-guards`) judged each entry once at its first `queued`. This one keeps `dependsOn` and `kind` current as the queue changes, delivers `outlook-changed`, and logs and counts an assured entry that fails anyway.

## What was built

- **`commit-outlook.ts`**: `WriteIndex`, one per-collection index of what the entries ahead write, added to one entry at a time. `judgeTransaction` now answers `QueuedJudgement = { own, outlook }`. New pure functions: `followOutlooks(queue, deferred)` recomputes every judged, non-refused entry's dependencies and kind in queue order, with committed collections removed from its own judgement. `outlookContradicted` is the counting rule. `refusedCheck` gives the table and decoded key a guard refusal names. `renderKey` shares its JSON replacer with `renderCommitOutlook`.
- **`OfflineMode`**: holds `judgements` (judgement plus `dependencyFailed`). On `failed` it first weighs the failure against the held outlook (`weighFailure` → `reportAssuredFailure`: a log line plus the `assuredFailures` count), then marks the failed entry's dependents. After any status that changes the queue (`changesTheQueue`) it runs `followQueue`. That pass is deferred while an entry has left the queue without its terminal status. It logs `offline:outlook-regressed` when an outlook goes assured → exposed, and delivers one `outlook-changed` per change of kind, only after every held outlook is current. The pass is isolated with try/catch (`offline:outlook-unfollowed`).
- **`offline-status.ts`**: the `outlook-changed` status; `assuredFailures` on `OfflineModeState`.
- **`guard-refusal.ts`**: `guardRefusalIn`, the cause-chain walk, shared by `TransactionBridge.mapCommitRefusal` and the controller. It is a separate module to avoid an import cycle with `txn-bridge.ts`.
- **Suite-wide check**: `test/outlook-predictions.ts`, a root `afterEach` that fails any test leaving a tracked plugin's `assuredFailures` above zero. `expectAssuredFailures` is the opt-out for a test that expects a count.
- **Docs**: README § Offline mode, docs/offline-sync.md (status shape, queue state, §The outlook, §Conservative by construction, stage 7, §Test plan), docs/internals.md.

## Review findings

Read the implement diff (`ticket(implement): offline-sync-outlook-follows-the-queue`) before the handoff. Then I read the db-core queue's removal path (`OfflineQueue.remove`, `claimRemoval`, `causeOf`) to check the ordering the controller relies on.

**Checked, nothing found:**

- **Correctness of when the pass runs.** `failed` is emitted only after every `dropSealed` of the removal has finished. So by the time `followQueue` runs, the replay has already recorded the cascade refusals, and refused entries are correctly left alone. A `discard` removal runs off the loop, so a head `committed` can arrive in the middle of it. The pass is then deferred, because the discarded entry's judgement is still held, and the terminal `failed` runs it. `status()` and `entries()` read the held judgements live (`translateListed`), so they always answer the current outlook.
- **The counting rule.** `outlookContradicted` returns false for an undefined outlook, for reasons other than `constraint`/`concurrent-modification`, for a `causedBy` listed in `dependsOn`, and for an entry whose dependency failed. Refused entries keep `dependencyFailed: true` through the pass because they are never recomputed. Non-refused ones are reset, which is correct: they are recomputed without the failed entry.
- **`refusedCheck`** decodes a unique index's value from the same range lower bound the judgement uses (`CollectionJudge`'s `absentRange` arm), so the logged key matches the exposure.
- **Type safety and error handling.** No `any`. Throws inside status delivery are isolated and logged. A refusal description that throws is logged (`offline:refusal-undescribed`).
- **Docs.** Read README, docs/offline-sync.md and docs/internals.md where the change touches them; all reflect the new behaviour. `yarn lint:docs` is clean.
- **DRY.** `guardRefusalIn` replaces the bridge's own copy of the cause-chain walk. `sqlValueJson` is shared by both renderers.
- **Implementer's tests.** All three new tests check behaviour (status order, logged fields, the count) rather than mocks. All kept.
