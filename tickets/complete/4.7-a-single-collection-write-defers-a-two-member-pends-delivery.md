# A single-collection write defers a two-member pend's delivery

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29). Landed in `ticket(implement): a-single-collection-write-defers-a-two-member-pends-delivery`, reviewed here.

## What was built

A write is two agreement rounds, **pend** (reserve) and **commit**. Each is a promise request plus a decision sent to the other member. On a two-member cohort:

- **No commit round.** The other member signs its commit while answering the promise round, because it sees both approvals. The coordinator keeps that signature only when the answer's promise map equals the round's merged map (`keepCommitsSignedOverMergedPromises`, compared by `canonicalJson`). Its own member's pre-sign then completes the majority and applies, and the other member is owed only the decision (`deliverDecidedWithoutCommitRound`). This applies to every two-member operation, so the coordinating member now applies first.
- **The pend's decision rides on the commit.** The writer marks a pend `PendRequest.soleReservation` when every block the action commits is in that one request, sent to one coordinator. For such a pend the decision is held back (`deferPendDelivery`) and carried on the first request of the action's commit. If no commit comes within `pendDeliveryDeferralMs` it is sent alone (default 2000, `DEFAULT_PEND_DELIVERY_DEFERRAL_MS`; `0` disables). The gate is `mayDeferPendDelivery`, and it needs all of these:
  - every operation is a marked pend;
  - the cohort is exactly two members;
  - this node's member applied the pend and its storage accepted it;
  - every awaiting member is carry-capable: its answers carry the stamp, and this node's client for it has `updateCarrying`;
  - the expiration is more than twice the deferral away.
- **Who marks.** `TransactorSource.transact` marks every `Collection.sync`, which covers legacy single-tree SQL writes. `TransactionCoordinator.pendPhase` marks only a one-collection transaction, which covers session-mode single-table writes. `NetworkTransactor.pend` keeps the mark only on a request carrying the whole pend (`pendRequestForBatch`), so a split or re-split pend never carries it. Multi-collection writes keep four requests per collection, so a late refusal cannot tear them.
- **Cost.** One SQL insert into a table with no index costs the other node 3 `/cluster` requests, in legacy and in session mode. With one index there are two collections and the cost is 8, four per collection. That is the correct reading of "keeps four".

## Review findings

Read the implement diff first, then every touched doc, then ran the suites.

**Checked, no defect found:**
- *Kept commit signatures stay valid.* A kept commit covers `computeClusterCommitHash(..., promises, ...)`. The keep runs only after every remote answer is merged, and only when this node's promise is already in the map, so the pre-sign adds no promise. `collectCommits` never merges promises afterwards. A kept signature therefore stays valid for the life of the record. I also walked the non-default shapes. At threshold 0.5, a three- or four-member cohort with one silent remote can keep a commit and even skip the commit round. The two-member guard in `mayDeferPendDelivery` keeps the deferral out of that case, and the record's promise map never changes after the keep.
- *Safety during the deferral window (Theorem 1).* On two members, this node's member holds the stored pending record and answers any rival with `held`. One non-approval sinks a 2-of-2 promise bar. A mesh test pins the late-refusal path: the carried pend is refused, so the commit is refused (`validateCommitAgainstRefusedPend`), and `takeLatePendRefusals` answers the writer with a retryable conflict.
- *"One collection pends once and commits once, to the same coordinator."* Read `NetworkTransactor.pend` and its coordinator cache (`txnCoordinatorCache`, `resolveCoordinator`). The commit reuses the coordinator the pend resolved. It falls back to a live lookup only when that coordinator is excluded after a failure, which is the failover case the third `NOTE:` at `deferPendDelivery` covers. One more case: a pend whose first attempt threw can be retried whole to a different coordinator, leaving two coordinators that each owe the same action's pend. Both deliveries are idempotent, or no-ops at storage because the revision is the action's own. Owed pends could already end up in this shape under failure.
- *Retry bookkeeping.*
  - The deferred timer is not a counted attempt: `scheduleCommitRetry` ignores the count of a `deferred` retry.
  - A carried delivery settles the retry and releases the transaction (`settleCarriedDelivery` → `finishRetry`).
  - The `finally` in `executeClusterTransaction` leaves a transaction with an armed retry alive.
  - The persisted retry state drops the `deferred` mark, so a recovered deferral restarts as attempt 1. That is harmless, and the durable store is not wired in production (backlog `debt-a-recovered-commit-retry-restarts-its-budget`).
- *Callers outside the gate.* The legacy per-tree sweep syncs each tree on its own, so trees already committed one at a time. A late refusal of a later tree's pend therefore lands no differently than before. `commitBatchLegacy` uses a multi-collection `TransactionCoordinator`, so it never marks.
- *Docs.* Every touched doc reflects the new order of application and the three-request cost. I grepped the other docs for two-member and commit-round counts and found nothing stale. `yarn lint:docs` is clean.

**Known gaps (accepted, not ticketed):**
- The two-member condition in `mayDeferPendDelivery` has no test. Testing it needs a three-member mesh at a lowered threshold with one promise missing. It is a one-line guard on a non-default configuration, and its doc comment says why it is there.
- A pend's answer on two members now rests on the coordinating member's verdict alone. This is the residual documented in correctness.md §2. The other member's refusal still reaches the writer, as the commit's retryable conflict.
- When the coordinating member is the one behind (the mirror durability case), it now fetches twice instead of once. Only a behind coordinator pays this.
