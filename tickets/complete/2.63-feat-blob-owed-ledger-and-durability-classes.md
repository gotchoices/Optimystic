# What landed

The durable record and the pure classification that the blob copy drain (`feat-blob-owed-copies-are-drained`) will run on. Nothing announces and nothing emits an event yet: no production code calls `OwedBlobLedger`, `classifyBlobDurability` or the new `BlobOwedRecords` door, by design — the drain is the next ticket.

- **`KeyedSerialQueue`** (`packages/db-p2p/src/keyed-serial-queue.ts`): `run(key, operation)` chains an operation behind every earlier one for the same key, dropping the map entry when nothing waits. One copy replacing three: `KvUnderReplicationLedger`'s private `serialized`, `BlobRecordStore`'s `chains` map, and the new `OwedBlobLedger`.
- **`OwedBlobLedger`** (`packages/db-p2p/src/blob/owed-blob-ledger.ts`): one JSON entry per announced blob under `owed-blobs/<ref>`, carrying the scope, the **confirmed holders** (not the missing members) and `recordedAt`. `record` / `addHolders` / `get` / `list` / `size` / `delete`, shaped after `KvUnderReplicationLedger`. No size cap — a `NOTE:` names `feat-unreferenced-blobs-are-reclaimed` as what bounds it.
- **`BlobRecord.durability`** and the **`BlobOwedRecords`** door on `LocalBlobService` (`holdOwed`, `releaseOwed`, `setDurability`, `durabilityOf`, `holdsWhole`, `emitDurability`), declared as `implements BlobService, BlobOwedRecords` so drift from the next ticket's use is a compile error. The three writers go through the existing `changeRecord`, so they take the sweep gate and the one per-ref queue. `LocalBlobService.stat` now carries the record's `durability` on all three return sites.
- **`classifyBlobDurability`** (`packages/db-p2p/src/blob/blob-durability.ts`): pure, types-only imports, five rules in the order docs/blobs.md §Placement, copying and durability specifies.

Implementation commit: `ticket(implement): feat-blob-owed-ledger-and-durability-classes`; the review's fixes are in this ticket's commit.

# Review findings

Read the implement diff first, then the handoff. Everything below was found by reading and running the code; the fixes and the one regression test are in this ticket's commit.

## Fixed in this pass (minor)

- **A stray key under `owed-blobs/` failed every scan, permanently.** `OwedBlobLedger.scan` sliced each listed key and handed the suffix to `read`, which routes through `parseBlobRef` — so a key under the prefix that is not a canonical reference threw `BlobRefError` out of `scan`, and with it out of `list()` and `size()`, for as long as the key existed. Since `list` and `size` are what every copy-drain pass calls, one bad key would have stopped the drain outright rather than costing one skipped entry. The sibling store deliberately does the opposite (`BlobRecordStore.listRefs` skips a bad key and logs `record:bad-key`), and the ledger's own `keyFor` comment already *claimed* "a key `list` would then skip" — the claim was simply not implemented. `scan` now guards with `isBlobRef` and logs `entry:bad-key`. Pinned by a new case in `packages/db-p2p/test/owed-blob-ledger.spec.ts` ("skips a key under the prefix that is not a reference").
- **A failed index load could surface as an unhandled rejection.** Both ledgers stored `indexLoad` as a chain ending in `.catch(err => { this.indexLoad = undefined; throw err; })`. When the scan fails during `list()`, the caller handles the `scan` promise it was given, but the *stored* chain re-throws with nobody listening — an unhandled rejection, which Node terminates the process for by default. The handoff flagged this as a pre-existing shape it had mirrored and declined to diverge on; mirroring it made it a class with two instances, so it is fixed in both: `indexFrom` now attaches the clearing handler to the stored promise (`void load.catch(…)`) and returns the promise that still rejects for awaiters. Same observable semantics for every caller, minus the stray rejection. Not separately tested — the reproduction needs a store rigged to fail mid-scan plus a process-level rejection assertion, which is more fixture than the one-line invariant is worth.
- **`classifyBlobDurability` could report `confirmed` larger than `accepting`.** It computed both counts from `view.accepting` *before* checking `view.resolved`, then returned `unrouted` with `confirmed: confirmed.length` and `accepting: 0`. Harmless for the drain's own view (unresolved always carries an empty `accepting`), but a function with an explicit "pure, caller builds the view" contract should not be able to answer an impossible pair. The `resolved` check moved to the top and returns two zeros.
- **`LocalBlobService.announce` pointed at the wrong ticket.** Its "not built yet" message named `feat-a-referenced-blob-is-copied-to-its-cohort` (the cohort-change reaction, two tickets out) rather than `feat-blob-owed-copies-are-drained`, which is what actually builds announcing — a wrong signpost in the one place a caller meets it. Corrected.
- **A db-core field comment the change falsified.** `BlobDurability.accepting` said "Zero exactly when quorum is 'unrouted'". It is not: a cohort that resolves but whose members all refuse blobs is `local` with `accepting: 0`, which the implementation's own test table pins. The comment now states both zero cases. (This is why db-core's suite was run as well.)
- **Doc row completed.** `docs/debugging.md`'s `blob:store` row — rewritten by this ticket — gained `entry:bad-key` for the fix above, and `record:unreadable`, which the handoff noted as a pre-existing gap in that same row and left alone. One row, one edit.

## Fixed in this pass (major, caught by the full suite)

- **`test/entry-parity.spec.ts` failed: the three new modules were exported from `src/index.ts` and not from `src/rn.ts`.** The implement handoff asserted the opposite was correct ("the curated export list there is unchanged, as the ticket directs"), and the implement ticket's own prose claimed `repo/under-replication-drain.ts` is "left out" of the React Native entry today. Both are wrong on the facts: `rn.ts` exports `drain-scheduler.js` *and* `under-replication-drain.js`, and the parity spec fails any module present on one entry and absent from the other unless it is declared in that spec's `NODE_ONLY` map — which is empty by design, because every db-p2p module except the libp2p transport wiring is browser-safe. All three new modules are (the queue imports nothing at all; the ledger and the classifier import db-core types, the logger and the `IKVStore` type), so the fix is the one the spec asks for: add them to `rn.ts`. `yarn check:rn` still passes, as the handoff said it did — the two checks see different things, which the parity spec's own comment explains.
  - The same wrong claim is in `tickets/implement/2.64-feat-blob-owed-copies-are-drained.md`, where it would have landed the next ticket red. Corrected there in place, with the reason, rather than left for its implementer to rediscover.
  - This is the one finding the implement stage could not have found by judgement alone: `tickets/rules/testing.md` puts the full suite in review, and it is the full suite that catches entry drift.

## Filed as evidence on an existing ticket

- **`OwedBlobLedger.record` loads the whole index before it writes.** `record` and `remove` both `await this.index()`, so the first `record` after a restart is one `list` plus one read per stored entry — and `NodeBlobService.announce` (next ticket) awaits that before it resolves. This is the class `debt-solo-node-ledger-is-reread-whole-on-first-commit-after-restart` already tracks, so it is appended there as a second arm rather than filed afresh. The arm is worth stating separately because the blob ledger inherited the cost *without the reason*: the block ledger needs the index for correctness (it is the eviction order that enforces `maxEntries`), while the blob ledger has no cap and needs it only to answer `size()` — so for this ledger the load can simply be skipped while unloaded, which makes the arm much cheaper to resolve than the first.

## Parked as a tripwire

- **Neither `DURABILITY_QUORUMS` nor `HOLD_KINDS` is exhaustive against its type.** `new Set<DurabilityQuorum>([...])` constrains what may be written into the list, not what may be left out, so a quorum class or hold kind added upstream would make the record decoder refuse every record carrying it — and a refused record stops that blob's sweep, not just one read. Fine while both sets are closed. `NOTE:` at the site in `packages/db-p2p/src/blob/blob-record.ts`, naming the `Record<…>`-derived list as the fix if either set grows.

## Checked and found sound — no action

- **The `KeyedSerialQueue` substitution**, the one thing the handoff asked for eyes on. The two replaced implementations differed only in where they dropped the map entry (a `finally` after awaiting versus a detached `then`); both guarded with `queues.get(key) === tail`, and the extracted version keeps the ledger's `finally` shape. Checked specifically that `run` installs the chain **before** its first `await`, so two un-awaited calls on one key still serialize — the property `BlobRecordStore.update` depended on by returning its chain synchronously. The two pre-existing suites (`kv-under-replication-ledger.spec.ts`, `local-blob-service.spec.ts`) pass unedited, which is the check the handoff proposed and it is the right one; no new test, since the queue has no behaviour its callers' specs do not already exercise.
- **`BlobOwedRecords`' two readers go through `readableRecord`, not `records.get`** — the deviation the handoff asked to be confirmed. Confirmed correct: it matches the edge-case note in the implement ticket, and it means a record that does not decode cannot fail a drain pass. For `holdsWhole` it under-counts this node, which keeps the blob — the safe direction, as the doc comment says.
- **`releaseOwed` leaving a record with no holds.** Traced through `BlobRecordStore.apply`: a next record with `holds.length === 0` is deleted rather than written, so the "never empty in a stored record" invariant on `BlobRecord.holds` holds and the blob is swept, which is the documented end state.
- **`durability` being *checked* rather than kept-as-found**, unlike the record's other additive fields. The escalation is real (an undecodable record aborts that blob's sweep until it is fixed), but it is the house rule in this module — `HOLD_KINDS` is closed the same way — and the rationale is written at the site. Left as the implementer decided; the forward-compatibility half of it is the tripwire above.
- **Encoding and decoding round-trip the new field.** `encodeBlobRecord` is `JSON.stringify(record)` and the decoder returns the parsed value, so `durability` survives; `setDurability` returning a fresh object every call does not cause a write, because `apply` compares encoded text.
- **Source hygiene.** `local-blob-service.ts` is 671 lines (`wc -l`), well inside the repo's observed split threshold (the open size-debt tickets cite ~1,700+); the new files are 37, 56 and 214 lines. Comments say why rather than narrating statements; the two new files' header comments carry the rules, which is the right place for them.
- **Docs.** Read every file the change touches and checked each claim against the code: `docs/blobs.md`'s status line and its *Copying* / *Durability* "Built:" paragraphs match what exists (the drain, durability reporting, the cohort reaction, reclaiming and SQL are still marked to-be-built); `packages/db-p2p-storage-fs/README.md` and `FileKVStore.keyToPath`'s NOTE now list `optimystic-blobs/` and `owed-blobs/`, and that list matches `NODE_KV_NAMESPACES`. `yarn lint:docs` resolves every citation.
- **The implementer's two new specs.** Kept both. `blob-durability.spec.ts` is a table over branching logic that the specification names rule by rule — the paradigm case for a test. `owed-blob-ledger.spec.ts` pins store-facing behaviour (replace-keeps-holders, holder dedup, never-create-after-delete, scan order against a store that answers reversed, the lazily loaded index across a simulated restart, a malformed value read as absent, concurrent writes, a refused non-canonical reference) — none of it restating the implementation or verifying a mock. Nothing cut. One case added, for the defect above.
- **No `NOTE:` at any finding site was an accepted tradeoff whose revisit condition had tripped** — the only pre-existing `NOTE:`s in range (`FileKVStore.keyToPath`'s namespace condition, `KvUnderReplicationLedger`'s eviction note) are unrelated to these findings.
