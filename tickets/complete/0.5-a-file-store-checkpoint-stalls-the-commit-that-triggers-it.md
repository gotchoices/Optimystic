# A file-store checkpoint no longer stalls the commit that triggers it

GitHub #62 (Sereus; optimystic 1.27.0, `FileRawStorage`, solo node, macOS 15 on Intel): every checkpoint of the write-ahead log made one commit take 5–7 s and the dozen after it 1–2 s. A checkpoint synced its files and directories sixteen at a time; on macOS libuv implements `fsync` as `F_FULLFSYNC` (a whole-drive cache flush, serialized by the device), and every `fs` call shares libuv's four pool threads, so the checkpoint held every thread and queued the commits' own appends and log syncs behind it.

## What landed

Implemented in `ticket(implement): a-file-store-checkpoint-stalls-the-commit-that-triggers-it`, with one change in review.

- **One tree sync at a time, giving way to the log.** `FileWriteLog.syncSealed` syncs the sealed segment's files, then directories, one at a time. Before each, `giveWayToLog` waits while any task is queued or running in the log's queue (commit, sync step, seal), counted by `enqueue` (`queuedTasks`) and woken when the count reaches zero. A commit's log sync therefore waits for at most one tree sync.
- **Behind, and the per-commit share.** The checkpoint is behind when the current log reaches `checkpointBytes` while the previous checkpoint still runs. Then its syncs stop giving way, and each commit, after its append and outside the queue, waits until `CheckpointPace.charge` says its share of syncs is done. The share is the larger of (a) `record bytes × sealed paths / sealed bytes` and (b) `record bytes × syncs not yet charged / bytes left before the current log reaches 2 × checkpointBytes`. Charges accumulate on one fractional cursor; only the target is rounded up. Term (b) goes beyond the fix ticket's text: without it, a writer of strict flushes starves the checkpoint before it falls behind, and the log grows by about one sealed segment per checkpoint. The first commit to wait in a checkpoint logs `checkpoint-behind` on the write-log channel.
- **Close.** Once the last release has begun, no commit is left to make way for, so the final checkpoint syncs sixteen at a time, and (added in review) so does the rest of a paced checkpoint that was still running (`syncEachPaced`).
- **Bound:** the current log reaches about 2 × `checkpointBytes`, plus about one record from each store over the directory (`replaySegment` NOTE).
- **Unchanged:** seal, truncate, crash cases and replay order, failure latch, idle and size triggers. Replay keeps 16-wide syncs.

## The macOS effect is confirmed only in a model

The implement stage modelled a serialized device with a pool-thread hold per sync, on Windows. For the old code that model gave 3.7–30.8 s per transaction during a checkpoint. With this build: with a 3 ms device slot, transactions ran in a repeating pattern of 8 at about 80 ms, then 8 at 1.1–1.25 s. With a 10 ms slot, the log was bounded but each transaction took about 2–3.7 s once the log was behind. The fix ticket asked that every transaction stay within about twice the time of its neighbours. That is not met where a behind episode starts or ends: any scheme that keeps the log bounded must slow writes to the disk's pace. Within an episode, neighbours are within 2× of each other.

**For the reporter (GitHub #62):** ask them to rerun `commit-latency.mjs` on a build with this fix three times: default settings, `CHECKPOINT_MIB=4`, and `CHECKPOINT_MIB=64`, watching for `checkpoint-behind`. The 64 MiB run, where commits slowed from about #101 with no checkpoint yet, decides whether the follow-on is needed. The follow-on would start the paced tree syncs before the size threshold, so unsynced tree data never piles up for the log's `F_FULLFSYNC` to flush. It would also smooth the fast/slow alternation recorded in the `NOTE:` at `giveWayToLog`.

## Review findings

Read the implement diff first, then the handoff. Checked by reading and running the code.

**Correctness: checked, one defect found and fixed.**
- No lost wake in `giveWayToLog`: `queuedTasks` is incremented synchronously in `enqueue` and checked synchronously before each wait, and every path that drops the count to zero wakes the waiter.
- No deadlock between commit and checkpoint: the share is awaited after the task leaves the queue, so a waiting commit neither holds the queue nor counts as a task the sync gives way to. The seal is the only other queued task a checkpoint makes, and checkpoints run one at a time (`runCheckpoints`), so the single wake slot (`wakeWaitingSync`) is sound.
- Pace lifetime: `this.pace = undefined` and `pace.end()` run in the same synchronous `finally`. No commit can be charged against an ended pace, and success, a fsync failure and a latch all release every waiter.
- `CheckpointPace.charge`: `sealedBytes` is never 0 (the seal returns early when `appendedBytes` is 0). A segment with 0 paths charges nothing. A record bigger than what is left before 2 × `checkpointBytes` is charged every remaining sync. The cursor never passes `paths`.
- A `durable` held during the share wait can reject (latch) before the caller sees it. That is safe: `SyncDeadlines.defer` returns a pre-observed promise (`deferred()` in `packages/db-p2p/src/deferred.ts`), so there is no unhandled rejection.
- **Defect, fixed:** a paced checkpoint still running when the last release began went on one sync at a time behind `giveWayToLog`. It had nothing left to make way for, since `shutDown` drains the queue and later commits are refused. In the implement stage's model this was most of a 59 s close; on a phone being backgrounded, that time may not exist. `syncSealed` now goes through `syncEachPaced`, which hands whatever remains to the 16-wide `forEachConcurrently` once `closed` is set. `giveWayToLog` also stops waiting once closed, and `syncDirtyPaths` is left to the replay. Comments for `UNCONTENDED_SYNC_CONCURRENCY` and `syncDirtyPaths`, the README Checkpoint paragraph and `storage.md` §6 were updated. New test: *a checkpoint running when the last release begins syncs the rest of its paths many at a time*. It hangs to its timeout with the change reverted, and passes with it.

**Design points the implementer flagged:**
- Term (b) of the share: kept. The argument holds (a strict-flush writer keeps the queue busy, so term (a) alone lets each sealed segment grow by about `checkpointBytes`), and the third pacing test pins it.
- Rounding the cumulative target rather than each commit: agreed. It is the fix ticket's rule without over-charging small records.
- A relaxed flush delayed by pacing while behind: intended, documented in the README and in `storage.md`'s backends table.

**Tests:** the three implement-stage tests pin branching logic named by the specification (one-at-a-time with give-way, the term-(a) share, and the term-(b) share).
