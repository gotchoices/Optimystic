# The crypto backend takes native ECDSA verify — complete

Requested in GitHub #59 (VoteTorrent): on a Pixel 8 emulator under Hermes, `p256.verify` took 47 ms in `@noble/curves` against 0.13 ms in OpenSSL, and `secp256k1.verify` 29 ms against 0.24 ms, paid for every signed row a schema `CHECK` constraint verifies.

## What landed

- `CryptoBackend` gains optional `p256Verify` and `secp256k1Verify` (64-byte compact r‖s signature, message, 33- or 65-byte SEC 1 key → boolean; the member hashes the message with SHA-256). `snapshotBackend` copies and binds both.
- `verify`'s `'p256'` and `'secp256k1'` cases dispatch through `ecdsaVerify`, which reads the installed backend per call and falls back to noble with `ECDSA_VERIFY_OPTS` (`{ prehash: true, lowS: true, format: 'compact' }`, equal to noble 2.0.1's defaults, frozen).
- `checkEcdsaVerify` runs at `setCryptoBackend`: accept the valid signature under the compressed and the uncompressed key; reject-or-throw on six inputs noble rejects — tampered message, high-S copy, r = 0, r = n, hybrid (0x06/0x07) key, and (added in review) the signature re-encoded as DER. Expected answers are written down rather than asked of noble's verify, which costs tens of milliseconds a call under Hermes at app start. No ECDSA signing member: a native signer's random nonce cannot be checked byte for byte.
- README, `docs/crypto.md`, `src/index.ts` header and an **Unreleased** CHANGELOG entry (the releaser renames it) describe the members, the rules a member must follow, and a guarded Node adapter.

## Review findings

Read the `ticket(implement): the-crypto-backend-takes-native-ecdsa-verify` diff first, then the handoff.

**Correctness / security (checked by reading and by running):**
- Dispatch, snapshot and self-check wiring are correct; a throw from a member inside `verify` becomes `false` through the existing catch, as for noble.
- **Found and fixed — DER signatures were outside the self-check.** The interface doc described the member's input as "64-byte compact", but the dispatcher passes the caller's bytes through unchecked, so a member can be handed a DER signature. noble throws on it (measured: `expected Uint8Array of length 64, got length=70`); OpenSSL with `dsaEncoding: 'der'` verifies it (measured: `true`). Re-encoding an honest signature as DER needs no secret, the same class as the high-S and hybrid-key divergences the check exists for, so an adapter configured for DER, or one that falls back to it, would have let a phone accept a row every other machine rejects. Added a sixth rejection vector (`curve.Signature.fromBytes(sig, 'compact').toBytes('der')` — no new import; `dist/plugin.js` still contains none of the self-check), reworded the `p256Verify` doc to say the member must reject any non-64-byte signature because input is passed through unchecked, and updated the README bullet and vector count and the CHANGELOG. Added one refusal assertion reproducing it: an adapter with both guards that retries non-64-byte signatures as DER must be refused naming `p256Verify accepted a DER-encoded`; without the new vector it would have been installed.
- **Probed, no divergence:** non-canonical field coordinates (secp256k1 compressed and uncompressed key with x + p) — both noble and OpenSSL reject (OpenSSL: `Failed to read asymmetric key`). An off-curve point and the point at infinity stay contract-only as planned: a rejection vector cannot detect a lax library there (the signature math fails regardless), and the 1-byte infinity encoding is caught by the length/prefix rule the hybrid vector already exercises.
- Considered and not done: moving the structural checks (length, key prefix, scalar range) into the dispatcher so adapters need no guards. The plan settled on adapter-side guards enforced by the self-check, and a dispatcher check would make the self-check refuse unguarded adapters that would then be safe; no ticket, since the current design is sound and the self-check now covers every attacker-reachable re-encoding known.

**Tests:** tightened the first test's high-S assertion from `not.equal(true)` (which `undefined` also passed) to `equal(false)` for the ECDSA curves. The rest pays for itself: the byte-identical test covers per-call dispatch of both new members across the `/plugin` and root bundles, and each refusal assertion catches a distinct real adapter mistake. No test was cut.

**Docs:** read README §Native crypto backend, feature list, §Security Notes, §React Native Compatibility, `docs/crypto.md` and the CHANGELOG; all reflect the change after the edits above. `yarn lint:docs` passes.

**Hygiene:** `src/crypto.ts` is about 840 lines (`wc -l`), pre-existing size, the additions are small single-purpose functions; no narrated comments. The `highS` field of `evaluate()` is `undefined` for ed25519 — left as is, harmless under `deep.equal`.

**Unverified, carried forward (not ticketed):** `react-native-quick-crypto`'s acceptance of SPKI-wrapped EC keys and `dsaEncoding: 'ieee-p1363'` was not exercised on a device; the README says so and the self-check fails loudly at startup if it differs.

**Validation:** package `yarn build`, `yarn typecheck`, `yarn test` (128 passing); root `npx eslint packages/quereus-plugin-crypto` clean, `yarn lint:docs` clean, `yarn check:rn` passed (Metro + hermesc).

No tripwires or new tickets filed.
