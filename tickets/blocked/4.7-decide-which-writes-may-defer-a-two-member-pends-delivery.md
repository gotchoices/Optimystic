# Decide which writes may defer a two-member pend's final delivery

**Blocked: the accepted design contradicts a documented guarantee.** To unblock, a maintainer accepts the narrowed design below, edits it, or declines the saving. The decision ticket that accepted the design (`decide-whether-a-two-machine-write-drops-to-three-calls`, in `complete/`) told implementers to route it back here if any step needed a weaker guarantee than it argued for, and one did.

## What happened

GitHub [#29](https://github.com/gotchoices/Optimystic/issues/29) asked for fewer requests per write on a two-machine group. A write is two agreement rounds: **reserve** (the "pend") and **commit**. The accepted design held back the reserve round's last message to the other machine ("the group decided — apply it") and sent it inside the commit round's first request. One write would then cost the other machine three requests instead of four.

It was built in full, and the two-machine tests showed three requests. Then the Quereus plugin's `two-node-unique-value-race.spec.ts` failed, twice out of two runs. That spec has two machines insert, at the same instant, different rows with the same value in a UNIQUE column, and requires the losing insert to be refused cleanly with nothing stored. Instead the loser got `CoordinatorPartialCommitError`. Its row and its plain-index entry were committed, and its unique-index entry was refused, which is a torn write.

The cause is in the design, not the code. A SQL insert into a table with an index writes several trees: the table and one per index. They are all reserved first and then committed one by one, under one shared action id. The plugin relies on that order (`docs/internals.md`, *Conflict replay re-makes the uniqueness decision*). Any machine's refusal arrives during the reserve phase, while nothing of the write is durable yet, so the whole write rolls back. With the last message held back, the other machine learns of a tree's reservation, and refuses it, only when that tree's commit arrives. By then other trees of the same write may have committed. Each tree can also be coordinated by a different machine. The coordinator committing tree A never sees tree B's reservation, so no rule local to a coordinator can close this.

## Proposal (recommended default)

**Hold back the reserve round's last message only for a write the writer marks as reserving everything it will commit, through one coordinator.**

- Add an optional field to `PendRequest` (`packages/db-core/src/network/struct.ts`), for example `soleReservation?: true`: "this pend is the action's only one, and its commit goes to the coordinator this pend goes to".
- Set it in `TransactorSource.transact` (`packages/db-core/src/transactor/transactor-source.ts`), the single-collection write path that pends and then commits one collection. `NetworkTransactor.pend` keeps the field only when `consolidateCoordinators` puts the whole pend in one batch. `NetworkTransactor.commit` then commits in one round to that same coordinator (`commitInOneRound`).
- `TransactionCoordinator` never sets it. That covers multi-collection transactions, including the Quereus plugin's batched multi-tree commit.
- The coordinator defers only when every pend in the record carries the field, on top of the conditions the original ticket listed.

Effect: a single-collection write on a two-machine group costs the other machine three requests. A write through `TransactionCoordinator` keeps four per collection, as today. So do Quereus writes to tables with any index, a UNIQUE column included, because those go through the multi-tree batch. Older builds ignore the field, so nothing they rely on changes, and reverting is a code revert.

## Alternatives rejected

- **Ship as accepted.** It reproducibly tears a multi-tree write, as above.
- **Make the members refuse every commit of an action once any of its reservations was refused, and carry all of an action's held messages with each of its commits.** This closes the gap only when one coordinator handles every collection of the write and no more than four messages are owed (the carrying limit, `MaxCarriedRecords`). Collections coordinated by different machines stay open.
- **Tell single-collection writes apart by the shape of their action id** (`TransactionCoordinator` ids start `tx:`). That is a naming habit, not a contract.
- **Have the writer flush held messages before committing.** That needs an extra request, which gives back the saving.

## If we do nothing, or decline

Two-machine writes keep costing four requests to the other machine. Nothing is wrong. To decline: delete this ticket, and add an accepted-tradeoff `NOTE:` at `commitTransaction` in `packages/db-p2p/src/repo/cluster-coordinator.ts`. It should say a two-member write costs four requests, why that was kept, and when to revisit (for example, "if a re-measure shows writes on two-machine groups dominated by the request count"). The prereq's changes stand either way; they fix real gaps in today's code.

## If accepted: what to rebuild

The full design was built and verified before it was reverted. Every piece below passed the db-p2p suites. The prereq `a-pend-refused-late-still-stops-its-commit` has already landed the safety pieces the deferral leans on:

- the guard that stops a member co-signing the commit of a reservation it refused now sees new blocks;
- a commit always carries its own action's held messages;
- a late refusal answers the commit as a retryable conflict.

What remains, all in `packages/db-p2p/src/repo/cluster-coordinator.ts` unless named:

- **Keep the other member's commit signature from the reserve round.** In `collectPromises`, after merging every answer, keep `response.commits[peerId]` for a responder whose answered promise map equals the merged `record.promises` (`canonicalJson` equality from db-core). A commit signature covers that map, so this is the exact condition under which it verifies. Keep it only when this node's own pre-vote succeeded (`prevote?.success !== false`): otherwise the pre-sign would add this node's promise afterwards and invalidate the kept signature, which is backlog `bug-a-late-promise-invalidates-the-commit-signatures-already-collected`. Rewrite the "merges only promises" wording in `collectPromises`, `prevoteLocalPromise` and `docs/internals.md` (*Both consensus rounds carry the coordinator's own member's vote*).
- **No commit round when the pre-sign completes the majority.** In `commitTransaction`, if `presignLocalCommit` returned true and `hasCommitMajority(record)` holds, skip `collectCommits` and deliver to every remote member, or defer. This node's member now applies first on two members, so a behind coordinating member heals on `broadcastMergedRecord`'s second reconcile. In `test/commit-durability-quorum.spec.ts` the mirror case's fetch count becomes 2. Rewrite the `presignLocalCommit` comment and the apply-order passages in `broadcastMergedRecord` and in `docs/correctness.md` §2 *Commit durability reporting*.
- **Defer.** `mayDeferPendDelivery` requires:
  - every operation is a pend, and (new) every pend carries the field;
  - this node's member applied the pend and `getExecutedPendResult` reports success;
  - every awaiting member is carry-capable;
  - `pendDeliveryDeferralMs > 0`;
  - the expiration is more than twice the deferral away.

  `deferPendDelivery` then arms the retry with the first interval `pendDeliveryDeferralMs` and a `deferred: true` flag on `CommitRetryState`. `scheduleCommitRetry` ignores a deferred state when it counts attempts and backoff, so the deferral is not a counted attempt (an `armRetry` helper shared by both). Carry the three `NOTE:`s from the original ticket at that site: the rival during the deferral, a crash losing the held message, and the failover residual. `StorageRepo.pend`'s `isOwnRevision` check makes a late reservation of an already-committed action store nothing, so only a member whose commit apply and reconcile both failed would keep a dead record.
- **"Carry-capable" must include this node's client.** Record a peer as carry-capable only when its client has `updateCarrying` as well as when its answer stamps `acceptsCarried`. Otherwise a member reached through a client that cannot carry would only ever get its message from the timer. Two specs (`cohort-pend-refusal-channel.spec.ts`, `commit-durability-quorum.spec.ts`) use such clients and must keep today's immediate delivery.
- **Setting.** `pendDeliveryDeferralMs` goes in `ClusterConsensusConfig` (`packages/db-core/src/cluster/structs.ts`), defaulting to 2000 through an exported `DEFAULT_PEND_DELIVERY_DEFERRAL_MS`, and is resolved in the `CoordinatorRepo` constructor beside `commitBroadcastRetryInitialMs`. Document it in `packages/db-p2p/docs/cluster.md`.
- **Tests.** Rewrite `test/commit-round-carries-coordinator-commit-vote.spec.ts` for three deliveries, the second carrying the pend. Add mesh cases for:
  - a missed commit decision landing by retry;
  - the other member's refusal answering the commit;
  - a member on an older build getting four requests and nothing carried, through a harness option on `MeshFailureConfig` that strips the `acceptsCarried` stamp;
  - a pend with no commit after it, delivered when the deferral runs out.

  Add a unit case in `cluster-coordinator.spec.ts` for keeping and dropping the reserve-round commit signature. The plugin's `two-node-unique-value-race.spec.ts` is the acceptance test for this ticket's question and must pass unchanged.
- **Docs.** Add the proposed `docs/correctness.md` §2 text from the decision ticket, limited to writes carrying the field. Update `docs/internals.md` (*One commit round when one coordinator covers every block*: four `/cluster` calls become three for such a write; *A behind member actively reconciles*) and the cluster.md "two calls instead of three" passage.
- **Handoff.** Ask the #29 reporter to re-measure with `message-latency.mjs`.
