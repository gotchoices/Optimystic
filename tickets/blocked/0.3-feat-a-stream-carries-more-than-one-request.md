# A stream carries more than one request

GitHub [#40](https://github.com/gotchoices/Optimystic/issues/40), second source.

## What the cost actually is (verified against the installed code)

libp2p 3.3.11 calls `peerStore.merge(remotePeer, { protocols: [protocol] })` for every stream, on both ends: once in `Connection.newStream` and once in `onIncomingStream` (`libp2p/dist/src/connection.js`). The merge always does the full work, whether or not the protocol is already recorded. `@libp2p/peer-store` 12.0.28's `PersistentPeerStore.merge` (`dist/src/store.js`) runs these steps under the peer's write lock:

- it reads and decodes the stored record and rebuilds it as a `Peer`, which creates a multiaddr object for every address (`pbToPeer`);
- it rebuilds the protobuf form, deduplicating, filtering and sorting the addresses by their string form (`toPeerPB`, `dedupeFilterAndSortAddresses`);
- it sets `updated = Date.now()`, encodes the record, and **always writes it** to the datastore. Despite its name, `#saveIfDifferent` skips no write; it only decides whether to emit `peer:update`;
- it rebuilds the `Peer` a second time for the return value.

**Measured on a desktop** (Node, in-memory datastore, a record with 30 protocols, timed over 20 000 merges that add an already-recorded protocol, with a throwaway script run against the installed `@libp2p/peer-store`): **59 µs per merge with 2 addresses, 246 µs with 8.** A plain `peerStore.get` of the same record costs about the same (62 µs and 196 µs). So the time goes into rebuilding the address objects, and the record write itself adds little. #40 profiled about 7% of the JavaScript thread on a Galaxy S7. I did not measure on a phone, so I can't say how the desktop numbers scale there.

**One side effect a fix has to keep.** The `updated` stamp is part of how the store decides a record has expired: a record is deleted on its next read once `updated` is over 6 hours old (`MAX_PEER_AGE`) **and** none of its addresses was observed in the last hour (`MAX_ADDRESS_AGE`). An existing address keeps its first `observed` time, so a long-lived connection's addresses all age past the hour. Every new connection refreshes `updated` anyway, through the dial queue's `LAST_DIAL_SUCCESS` metadata merge and identify's metadata merge. Within a single connection that stays open for hours, though, the per-stream merges are what keep refreshing it. Remove them all and a peer connected for more than six hours with no other record change could be deleted from the store. This node would then classify it as unknown (`membershipOf` in `packages/db-p2p/src/libp2p-key-network.ts`) and leave it out of cohorts. So any fix, here or upstream, must keep refreshing the record now and then, not skip the merge outright.

## Why stream reuse is the wrong lever

The original proposal was for a requester to send its next request to a peer on a stream whose previous request has been answered, and for each handler to keep reading until the stream closes. Weighed against fixing the merge:

- **It covers four protocols, and the cost is spread over all of them.** Only `repo`, `cluster`, `sync` and `block-transfer` would change. Every other stream a node opens or accepts would keep paying a merge on both ends: the six cohort-topic protocols, reactivity notify, matchmaking, dispute, identify, ping, dcutr, circuit relay and FRET's own. I could not establish what share of a phone's streams the four database protocols carry, so I can't say how much of the 7% reuse would remove. A fix to the merge removes it for every protocol.
- **It still pays one merge per stream lifetime.** A prepared stream lives up to 30 s idle (`PREPARED_STREAM_IDLE_MS`), so a steady request rate drops from one merge per request to roughly one every 30 s per peer and protocol. Concurrent requests to one peer still open extra streams, because a stream carries its requests one at a time.
- **It needs a wire change on both ends of all four protocols.** An old handler closes after one reply (`await stream.close()` in each service's `handleIncomingStream`). A new requester can't detect that reliably in-band, because a second request can be sent before the handler's close arrives. The clean way is a second protocol id per service (for example `<prefix>/repo/1.1.0`), proposed ahead of `1.0.0` in multistream negotiation. The `1.0.0` ids must stay registered, because `membershipOf` recognises a serving peer by `<prefix>/cluster/1.0.0` or `<prefix>/repo/1.0.0` in its protocol list.
- **It widens two rules that currently depend on one request per stream.** `authorizeInboundStream` would have to be asked again for every request, or stream lifetime bounded, or else a revoked peer keeps sending on a held stream until it closes. And `ProtocolClient.processMessage`'s one re-send of a request on a prepared stream would have to say which request on the stream failed.

That is a large change to four protocols, two security-relevant rules and a mixed-version story, aimed at a cost that comes from a library default and could be fixed there.

## Proposed decision (the recommended default)

1. **Decline stream reuse.** Close this ticket's original proposal and drop the forward reference to it in the `NOTE:` in `packages/db-p2p/src/network/prepared-streams.ts`.
2. **Fix the cause upstream.** File the libp2p issue drafted below and offer a PR. That fixes every protocol for every libp2p user, ours included, with no wire change.
3. **Carry a narrow interim in `db-p2p` until upstream ships** (spec below). It also ships to downstream applications. A `yarn patch` of libp2p in this repository would not: it fixes only this repository's own install, and the phone app in #40 installs `@optimystic/db-p2p` against its own lockfile.

Alternatives rejected:

- **Stream reuse:** see above.
- **A `yarn patch` of libp2p or `@libp2p/peer-store`:** it does not reach downstream installs, which is where the cost was measured.
- **Doing nothing until upstream:** phones keep paying the cost for an unknown time. This is reasonable if the maintainer judges the runtime wrap too fragile. The interim costs little to remove later, so it is the default here.

Reversibility: all three parts are easy to undo. The interim is one function installed in one place, and removing it restores today's behaviour exactly.

### Draft upstream issue (for a maintainer to file on `libp2p/js-libp2p`)

> **Title:** Every stream re-writes the remote peer's peer-store record, even when its protocol is already recorded
>
> `Connection.newStream` and `onIncomingStream` call `peerStore.merge(remotePeer, { protocols: [protocol] })` for every negotiated stream. `PersistentPeerStore.merge` then decodes the record, rebuilds a `Peer` (a multiaddr per address) twice, re-sorts the addresses, and writes the record, even when the protocol was already present (`#saveIfDifferent` always writes; it only suppresses `peer:update`). For an application that opens one stream per request, this is the dominant per-request cost on a slow device: in our measurement, 59–246 µs per stream on a desktop for records with 2–8 addresses, and about 7% of the JavaScript thread on an Android phone.
>
> Suggested fix: remember, per connection, which protocols have already been merged for the remote peer, and merge each one only once per connection. Alternatively, have `merge` return before building a `Peer` when the incoming data adds nothing. Note that the per-stream merge currently also refreshes `updated`, which `#peerIsExpired` relies on for a connection that stays open longer than `maxPeerAge` with all addresses older than `maxAddressAge`. A fix should keep that refresh some other way, such as a periodic refresh for connected peers.

### Interim: throttle no-op protocol merges in `db-p2p` (ready to promote to `implement/`)

After `createLibp2p` in `createLibp2pNodeBase` (`packages/db-p2p/src/libp2p-node-base.ts`), next to the existing libp2p work-around `identifyOnConnectionOpen` (`packages/db-p2p/src/network/identify-on-open.ts`), install a wrapper around `node.peerStore.merge`. `node.peerStore` is the same object libp2p's connections call through, because `configureComponent` assigns `components.peerStore` and returns it. Put the wrapper in its own module, for example `packages/db-p2p/src/network/protocol-merge-throttle.ts`, with type-only imports, since `libp2p-node-base.ts` must stay reachable from the React Native entry.

- **What it intercepts:** only a merge whose data object has exactly one key, `protocols`, holding exactly one protocol, which is the shape `connection.js` uses. Every other merge (identify, the dial queue, circuit relay, our own `peer-address-book.ts`) passes straight through.
- **The rule:** for each (peer, protocol) pair, let one such merge reach the store at most once per throttle interval (proposed 60 s, a constant). Any other merge for that pair inside the interval resolves without touching the store. The wrapper doesn't need to know whether the protocol is recorded: the first merge for a pair always goes through, so a protocol is recorded at its first stream exactly as today.
- **What it returns when it skips:** the `Peer` the last real merge for that pair returned. `connection.js` ignores the value, and a stale `Peer` is all another caller of that exact shape could get. Say so in the function's doc comment.
- **Freshness:** at most one real merge per pair per interval keeps refreshing `updated`, so the 6-hour expiry stays far off.
- **Memory:** a bounded `LruMap` keyed by peer and protocol. Drop a peer's entries on `peer:delete`, so a deleted record is re-created by the next stream.
- **What changes in behaviour:** if something removes a protocol from a peer's record within the interval (identify replacing the list with one that lacks it), a stream on that protocol re-adds it up to one interval later instead of at once. That re-add is the same path by which a stranger can put this network's protocols into its own record (see [docs/internals.md §Network Membership Predicate](../../docs/internals.md#network-membership-predicate)), so a delay there loses nothing.

Edge cases and how each is verified:

- A first stream on a new protocol is recorded at once (test).
- A second stream inside the interval does not reach the store (test, counting store writes).
- A stream after the interval does reach it (inspection, or a fake clock in the same test).
- Only the exact single-protocol shape is throttled (inspection, plus a type on the predicate).
- The wrapper calls the original method with the store as `this` (inspection).
- `node.stop()` needs no teardown, since the wrapper holds no timer (inspection).
- **libp2p upgrade.** A pinning spec asserts that libp2p still merges once per stream, by opening two streams over a loopback pair and counting merges reaching the original method. It fails on the libp2p release that fixes this upstream, which tells us to delete the wrapper, as `packages/db-p2p/test/relay-third-party-address-gap.spec.ts` does for address learning. If libp2p moves the call off `components.peerStore.merge`, the wrapper is bypassed silently and behaviour reverts to today's, with no failure. The spec is what catches that.
- **Docs:** replace the `NOTE:` in `packages/db-p2p/src/network/prepared-streams.ts`, and add a short paragraph to [docs/internals.md §Third-Party Address Learning](../../docs/internals.md#third-party-address-learning) or a neighbouring section, since `peer-address-book.ts` currently claims to be the only writer of the peerStore in this repository.
