## Standing notes

Operational lessons that still hold. Read these before starting a runner.

**Running the runner**

- Start the runner detached with `Start-Process` (`node tess/scripts/run.mjs --stages review,implement,fix,plan --skip-blocked --refresh-index`). A runner started as a tool background task is killed at the tool's 2-hour cap mid-ticket.
- Write runner logs outside `tickets/`. A log left there gets swept into the next salvage commit (removed once already, `633c1f90`).
- Before restarting a runner, check for a live `run.mjs` process and for `tickets/.in-progress`. A quiet log does not mean the runner died; restarting on a quiet log once ran two agents on one ticket. Other projects (SiteCAD, SiteCAD_branch, sereus) run their own runners on this machine; match a `run.mjs` to its repo by its `claude -p` child before touching it.
- `tickets/.stop` is check-and-consume (`checkStop` in `tess/scripts/lib/state.mjs` unlinks it). It halts one runner at its next between-ticket check and then protects nothing. To hold the queue for a long time, recreate it after each consume, and check for live runners rather than trusting the file.
- The machine has hard-frozen twice under load (this runner plus SiteCAD runners plus many sessions). Hold runner starts when commit charge is near 80% or free memory is well below 6 GB.

**Shared working tree**

- Other sessions share this working tree. Their uncommitted edits are committed inside whatever ticket the runner is on, under that ticket's name and outside any review. Ask other sessions to commit their own changes promptly, and expect a ticket's diff to be wider than its message.
- tess's pre-existing-failure triage commits production code with no review of its own (`tess: triage pre-existing test failure`; three instances: `bbb04a26`, `9cfa83b0`, `12399f79`). Route any such commit into a review ticket by hand.
- While a device (React Native) session holds the tree, write nothing here, not even ticket files: Metro watches the source tree through the linked workspace, so any write triggers a Fast Refresh on the phone.
- A sereus run can rebuild this repository's packages through its stale-build guard, so `dist/` can move under a review with no optimystic runner active.
- On Windows, `git worktree remove --force` follows `link:` junctions inside the worktree's `node_modules`. A sereus run deleted 883 tracked files here that way (restored).
- Runner agents writing through PowerShell have re-encoded files (BOM, CRLF). Check committed blobs if a diff looks garbled.

**Worktrees and builds**

- A new worktree needs the main tree's untracked `.yarnrc.yml` (`nodeLinker: node-modules`); without it Yarn installs Plug'n'Play. Whether to commit that setting is `blocked/decide-whether-to-commit-the-yarn-linker-setting`.
- Root `yarn test` refuses to run when the sibling `../quereus` checkout has uncommitted source newer than its build. That is the maintainer's work in progress; leave it alone and use `OPTIMYSTIC_SKIP_BUILD_CHECK=1` for the plugin suite if needed.
- `p2p-fret` now comes from npm, not a portal into `../Fret` (see `blocked/fret-checkout-cannot-be-linked-on-the-libp2p-3-3-line`).

**Downstream (sereus, VoteTorrent)**

- sereus-ec wants to be told the version of any release that carries fixes it is waiting for, so it can raise its `@optimystic` floors. It waits for the `all N packages published and visible on npm` line from `yarn release`.
- sereus classifies retry safety by parsing our error text (`backlog/debt-a-downstream-repo-classifies-retries-by-parsing-our-error-text`). Do not reword the `Some peers did not complete:` aggregates or merge the `[block:` and `[blocks:` forms.
- sereus scenarios use our storage op counts as a latency lever. When a change cuts op counts, say so in the handoff so sereus re-measures.
- A green `yarn check` here does not prove a consumer's flow works; the 1.0.0 candidate passed here and failed sereus's join flow.
