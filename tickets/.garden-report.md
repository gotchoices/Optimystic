### A downstream cost of making this system faster (2026-09-15, from sereus's suite)

Recorded because it is the kind of thing only a dependent repository can see, and because it will
happen again as the op-count work continues.

The sereus session ran its integration suite against `c56c2bd4` (57 files, 54 passing, 14m 6s; 292
tests passing, 2 failing). One failure is a genuine consequence of **optimystic's schema batching**,
landed earlier: sereus's `control-bring-up-quiet-period` forces a control-database bring-up to outlast
`@libp2p/bootstrap`'s 1000 ms discovery fuse by sleeping 12 ms per raw storage operation, so the
bootstrap dial is guaranteed to fire mid-bring-up. Cold control start fell from 169 storage
operations to 45, so the forced latency fell with it — 45 × 12 ms ≈ 730 ms — and the scenario
stopped straddling the fuse it exists to straddle. Its own anti-vacuity assertion caught it
(`expected 730 to be greater than 1000`) rather than passing green and proving nothing. Sereus raises
its per-op delay; nothing is wrong on this side.

The lesson for this board: **downstream tests use our op counts as a latency lever**, so cutting
operation counts can take away a property a dependent's scenario depends on, while nothing here goes
red. Anyone landing further op-count reductions should say so in the handoff, so the dependent
repository re-measures instead of meeting it as a mystery failure.

*Corrected after first writing this:* the first version said such a scenario can go **silently**
vacuous. Not in this case, and the distinction is the useful part. Sereus's assertion is on measured
elapsed bring-up time against the fuse (`expect(startMs).toBeGreaterThan(1000)`), not on the
operation count or the sleep — so the relationship is asserted directly, and losing it fails loudly,
which is exactly how this surfaced. The 50 ms per-op delay is only headroom. A scenario that pinned
the *op count* instead would have gone quiet; one that pins the property it needs cannot. The real
risk they named is the opposite of mine: someone meeting a future red by lowering the assertion
rather than raising the delay, which their comment now forbids in as many words.

One residual, theirs: the comment's arithmetic (23 as the budget floor) is a hand-maintained
cross-reference from a comment in their repo to a constant in a package here, and nothing enforces
it if our budget spec is re-measured.

**It repeated, so it is ours:** a `BlockUnavailableError … (cohort-unreachable)` out of
`TransactorSource.tryGet` → `Tracker.tryGet` → `Collection.updateInternal` → `Collection.update` →
`Tree.update` → the plugin's `runQuery`. Three nodes, one fully isolated, sereus reading through
`ControlDatabase.readRowsOnce`; identical stack on both runs, under comparable load each time, so it

node-count sweep, which is the maintainer's stated priority, and the sweep's three-node

### One for upstream tess, not for this board (2026-09-15, found while pausing the queue)

`tess` is a submodule (`gotchoices/tess`), so this is recorded rather than filed here.

`checkStop` is check-and-consume: the first runner to reach a between-ticket check `unlink`s
`tickets/.stop` and halts. That makes a stop file a one-shot fuse rather than a hold. Tonight the RN
session created one to keep the queue off while it drove the attached phone; the runner consumed it
on the way out, and for about ten minutes the repository had no hold at all while that session
believed it did. Anyone starting a runner in that window would have found nothing in their way, and
nothing would have said so. The same pattern was visible in sereus from the other side: a surviving
`.stop` there looked like a hold and was actually just an empty road, since no runner had reached a
check since it was written.

Worth a thought upstream: a halt that a single runner start silently erases is weak exactly when
several agents share one working tree, which is now the normal case here. A file the runner refuses
to run *while it exists* — leaving removal to whoever created it — would fail closed instead. That is
a change in tess's contract, not a bug report, and it is the maintainer's call.
