# Unreleased — since v1.18.0

## A read naming many held blocks checks every one of them

A node limits how many background read-repair checks it runs at once. The limit counted one per block, so a read naming more than 16 blocks whose check was due checked the first 16 and skipped the rest, and the same blocks were skipped by every such read. The limit now counts the requests those checks send each group member, and the checks one read starts share one request per 32 blocks, so a read naming 36 blocks checks all 36 in two requests per member. Reads of one block at a time are limited to 16 running checks, as before. `cluster-tx:read-repair-deferred` gains a `slotsInUse` field.

## A cancel another machine carried out is no longer reported as a failure

GitHub #46. When a writer asked another machine to cancel a reservation, the cancel worked but the writer always read the reply as an error (`Unexpected end of JSON input`), so it re-sent the cancel to another machine after its retry back-off: 4.5–6.6 s where 0.4–0.6 s was expected in Taleus's measurement. It also meant a cancel coordinated by another machine was never confirmed, so a half-landed write that could not be finished was reported with `TornActionError.final` false when it could have been true. A reply to an operation that returns nothing is an empty message, and the client now reads it as "done". The fix is on the asking side, so it also works against machines still running 1.18.0 or older.

# v1.18.0

## An application can tell the node a peer already holds a block

From Sereus's join catch-up measurement. An application that delivers blocks to a peer itself can now say so with `node.reportBlockHeld(blockId, rev, peerId)`. The node then stops owing that peer a copy at that revision or older, and the rebalance monitor counts the peer as a holder. Before this, the under-replication drain re-sent each delivered block one request at a time a few seconds later (42 to 91 duplicate full-block requests per join in Sereus's measurement), and storage-profile nodes' cohort-growth push did the same. A `rev` that is not a non-negative integer is refused with a `RangeError`. When a report or a drain push empties a block's entry, the full-replication event now names the revision that was cleared, not the one read before the copy was sent; the two differ only when a newer commit lands while the copy is in flight.

## A node no peer can dial directly is built without hole punching

From Sereus's join measurement. A node whose advertised addresses include none that another machine can dial directly (no listen addresses, or only relay or loopback ones) is now built without libp2p's direct-connection upgrade (`dcutr`), which cannot succeed for it. Two relay-only peers used to spend about nine relayed `dcutr` streams per join. `NodeOptions.holePunching` forces the service on or off. Nodes that listen on a wildcard, LAN, public or DNS address keep it as before. The React Native factory's default (no listen addresses) now leaves it out.

# v1.17.0

## A block a machine does not hold is fetched once, not twice

GitHub #39. When a machine read a block it did not have, it asked each group member what revision it held, then asked the same member for the same block again to restore it. The restore now reuses the copy the first request brought back, so a missing block costs one request per member. The checks that copy has to pass before it is stored are unchanged.

## Opening a collection reads fewer blocks, and a table's trees open together

GitHub #39. Opening a collection reads its header and log tail once each and keeps them, so the refresh that follows reads neither again: an open costs two requests, and opening, the first refresh and one point read cost four. The header is kept only when no commit that landed between the two reads changed it. In the Quereus plugin, opening a table now opens its index and UNIQUE trees at the same time rather than one after another.

## A read checks all its blocks with each group member in one request

GitHub #43. When a read checks several blocks with the other members of its group, it now asks each member about all of them in one request instead of one request per block. The asker also says which revision it holds, and a member sends a block's contents only when it has something newer. Each member's reply deadline counts from when its request is sent. A member on an older build ignores both additions, answers the first block, and the asker asks for the rest one at a time, so mixed-version groups keep working.

## A member that stored a write by group agreement counts its copy as checked

GitHub #43. A machine that applied a commit as part of its group's agreement now treats its copy of those blocks as freshly checked, as the coordinating machine already did, so the next read does not consult the group about a block it just stored.

## Groundwork for one request per member when a write spans several collections

GitHub #42, not yet in effect. Group members and coordinators can now run one consensus record that covers several collections of one transaction (`IRepo.pendMany` and `IRepo.commitMany`, optional). Nothing sends one yet, so request counts are unchanged; the change that would send them is waiting on a decision about groups that run mixed builds. One visible change: `RepoService` now refuses a repo message carrying more than one operation unless it is a well-formed batch, where it used to act on the first operation and ignore the rest.

## Requires `p2p-fret` 1.2.1

`@optimystic/db-p2p` now depends on `p2p-fret` `^1.2.1`. Fret 1.2.1 stops a node from pinging a relay that runs no FRET, such as `relay.sereus.org`, forever, which had kept FRET's maintenance loop from slowing down to its idle rate. Fret 1.2.0, which 1.2.1 includes, gives a peer this node has watched stay up for 10 minutes or more a grace period before marking it dead (up to 5 minutes by default, FRET's `maxDeadGraceMs`), so a departed long-lived peer can keep reads of blocks this node lacks reporting `cohort-unreachable` for up to that long.

# v1.16.0

## The Node file store lists blocks whose id contains `/`

GitHub #41. `FileRawStorage.listBlockIds()` listed only blocks stored directly under the base directory, so it skipped every block whose id contains `/`: every collection header (`default/app/<Table>`, its indexes), `optimystic/schema`, and Sereus's strand and cadre-control tables. The other backends list them. A host enumerating by it (Sereus's peer-join backfill) never sent those blocks to a joining peer, which then fetched each one on demand: a 14.0 s first-sync probe on a 176 ms link, 1.7 s with the fix. The listing now walks nested directories, skipping each block's own store directories and the key-value store's top-level folders (`under-replicated`, `coordinator`, `participant`, `executed`, exported as `NODE_KV_NAMESPACES` from `@optimystic/db-p2p`). The on-disk layout is unchanged; existing stores need no migration. The shared storage conformance suite now holds every backend to this.

## A read-repair check that found a peer silent is not repeated on the next read

Sereus #48 also measured a coordinator re-checking one block with its group about every 8 s while the other member was not answering, each check queued behind the unanswered one. A held block whose check found a group member silent is now not checked again until a hold ends: one declared link round trip (`node.linkDeadlines.retryBackoffBaseMs`), doubling per consecutive silent check, up to the reconcile pass bound (35 s at a 7 s per-peer budget), and ended early as soon as that member answers this node about anything. Reads during a hold are served from the local copy, flagged exactly as before. A node that declares no `linkRoundTripMs` re-checks on the next read, as before.

## A retry no longer queues behind the request it replaces

Sereus #48 measured retries at 28–48% of a two-member group's traffic over a phone-shaped link: a request given up on at a deadline is usually still in this node's send queue, and its retry went out at once into the same queue. A transactor's coordinator retry and its read retry round now wait first: one declared link round trip (new `NetworkTransactorInit.retryBackoffBaseMs`, from new `node.linkDeadlines.retryBackoffBaseMs`), doubling per further coordinator, and at least as long as the failed request was outstanding when the retry goes back through the same peer's queue. A wait that would outrun the budget sends no retry. A node that declares no `linkRoundTripMs` waits nothing, as before; a host building its own `NetworkTransactor` passes the value to get the wait. The read retry round also no longer re-asks a coordinator that a first retry already moved past.

## Optimystic tables accept catalog-only ALTER TABLE

For Sereus #46, which upgrades a party's shared control database in place on each machine's warm start. `alter table … drop constraint <name>` of a `CHECK` now works on an Optimystic table and is saved in the table's catalog record, so `apply schema` can remove a named `CHECK` or change its body (Quereus emits a drop, then an add). Before, it was refused as `UNSUPPORTED`; dropping a `UNIQUE` or `FOREIGN KEY` constraint still is. `alter table … add column` and `alter table … drop column` now work too, and are saved the same way, for the columns that need no stored row rewritten: an added column must be nullable, have no `DEFAULT`, not be generated and declare no inline `CHECK`, `UNIQUE` or `REFERENCES` (`COLLATE` and column tags are fine), and a dropped column must be in no primary key, index, `UNIQUE` constraint or foreign key of the table, and not be generated. Rows are stored keyed by column name, so an older row reads an added column as `NULL`, and a dropped column's values stay in the stored rows unread — re-adding that name reads them back. Any other column change is still refused as `UNSUPPORTED`. A failed `apply schema` undoes its `ADD COLUMN`s but cannot undo a `DROP COLUMN` (Quereus reports the schema as partially migrated). When several machines run the same upgrade, a machine that finds a change already saved by another adopts it and writes nothing, and if a later step of its apply fails, the undo touches only its own catalog, never the record. Two column upgrades the record contradicts are refused: adding a column of a name the record holds with a different definition (`ERROR`, not retryable), and dropping a column the record shows in an index or key this machine has not hydrated yet (`UNSUPPORTED`). The plugin cannot tell an older declaration from a deliberate change: a host must not `apply schema` a declaration older than the stored one, which an older release running its own declaration would do — it would remove the newer `CHECK`s and drop the newer columns. Sereus keeps its schema version in a table tag for this. A version may add a column and an index on it in one `apply schema` (Quereus 4.20.3 creates new indexes after the column changes). Known gap: a machine that hydrated before another machine's upgrade and touches the table first can still write its older description back (`bug-optimystic-stale-hydrated-table-rewrites-the-shared-catalog-record`); in an apply that re-adds a `CHECK` and then fails, that removes the other machine's `CHECK` from the record.

## Tag changes on Optimystic tables survive a restart

Changing a table's tags after it was created (`alter table … set|add|drop tags`, the column, named-constraint and index forms, and the tag-only changes `apply schema` makes with them) held for the rest of the session and was gone after a restart: Quereus applies such a change to its own catalog without calling the module, and `hydrate` rebuilt the old tags from the stored record. The plugin now saves every tag change to the table's catalog record, including on a hydrated table no statement has touched yet. Sereus relies on this to keep its control-schema version in a tag. A change `apply schema` makes is saved in the apply's one catalog commit, before it returns. An imperative statement returns before its save lands: new `plugin.whenCatalogPersisted()` resolves once every save so far has landed, and `plugin.dispose()` now waits for it first, so a host that reopens the same storage in one process waits on either in between. Tags on a `UNIQUE` constraint derived from `CREATE UNIQUE INDEX` are not saved; tag the index.

## A node's ping handler no longer cuts off a patient connection monitor

Sereus reported connections on slow links dropped with `aborting connection due to ping failure` (a stream reset, never a timeout) although both ends declared a 30 s ping deadline. Each node's ping service aborted inbound ping streams after a fixed 10 s, which capped the other side's deadline. New `NodeOptions.pingHandlerTimeoutMs` sets it; unset, it is twice `connectionMonitor.pingTimeout.maxTimeout` when `pingTimeout` declares either bound (libp2p's 60 s default `maxTimeout` when only `minTimeout` is declared; never below 10 s), and 10 s as before otherwise. A value that is not a finite number above zero, or above 2^31 − 1, throws when the node is built.

## Storage waits for the disk once per write group, and only as long as the cohort allows

GitHub #37 (kjeib): a small commit on the Node file store waited for the disk 72–155 times in sequence. Storage now
syncs once per write group, and how long a write may wait before that sync depends on how many machines hold it.

- **One flush per write group.** Each storage apply in `StorageRepo` (`pend`, `commit`, and a read that promotes a
  pending write) ends with one flush of the node's store, after its block latches are released and before its change
  events fire.
- **The Node file store writes groups through a write-ahead log.** `@optimystic/db-p2p-storage-fs` appends each group
  to one log file and syncs that log, not every file. It copies the writes into the readable file tree without
  waiting, empties the log in the background and on a clean close, and replays it on restart. A crash loses at most
  the newest unfinished groups, never half of one. The node's key-value store writes through the same log. Close both
  stores on shutdown so a clean stop leaves an empty log and no lock file.
- **A durability window from cohort size.** New `NodeOptions.storageDurability`
  (`{ independentFailures?, lossRatePerHour?, lossTarget?, maxWindowMs? }`; defaults `true`, one power cut or OS crash
  per machine per month, a 10^-9 chance of losing an acknowledged write, and a 5000 ms cap). A cohort member applying
  an agreed write lets its sync wait for as long as that many machines would all have to fail inside the window to lose
  it. Larger cohorts wait longer, and a write only this machine holds is synced before it is reported.
  `independentFailures: false` (for example, machines on one circuit) makes every write sync first. The node logs the
  resulting windows once at start. `WriteDurability` is unchanged: each holder's copy reaches disk within the window
  its cohort allows. See `docs/correctness.md` Theorem 6 and `packages/db-p2p/docs/storage.md`.
- **Phone and browser stores.**
  - NativeScript (SQLite) commits each group as one transaction and syncs by the window.
  - The browser store (IndexedDB) records each group in a journal at once and applies it with a `strict`
    transaction by the window deadline. A browser without strict transactions keeps its old guarantee and says so at
    start.
  - React Native (LevelDB) writes each group as one batch through the same journal. It still cannot sync, because the
    `rn-leveldb` binding offers no synced write (tracked as `blocked/4.5-react-native-storage-syncs-once-rn-leveldb-can`),
    and it says so at start.
  - On NativeScript and in the browser, the key-value store and the peer-identity helper also sync when asked, so a
    node's identity survives a power cut on its first start.

**Breaking for anyone implementing storage:**

- `IRawStorage` and `RawStoreDriver` now require `flush(options?)`, `whenDurable()` and a `durability` statement.
- `BatchBackend.commit` takes `{ syncWithinMs }` and returns a `CommittedBatch`. A backend also needs `sync()`, and
  the `WriteGroup` sink gets the same two changes.

Every backend in this repository implements these.

## `allowDownsize` docs describe the code

The docs said `clusterPolicy.allowDownsize` decides whether a node that can see only itself may commit. It never did:
a cohort of one always commits alone, as `local` or `unrouted`. The docs and the field's comment now say so. A rule for
lone writes remains an open design question (backlog `partition-healing`).

# v1.15.0

## FRET's redial follows the node's dial timeout

`@optimystic/db-p2p` now requires `p2p-fret` ^1.1.0, and passes it the node's whole-dial deadline:
`connectionManager.dialTimeout` when set, otherwise the value derived from `linkRoundTripMs`
(10 s on an undeclared node, unchanged). Before, FRET redialed a routing-table peer under its own
fixed budget, so two phones reachable only through a relay on a slow link could fail to reconnect
after a restart (gotchoices/sereus#44).

- **`connectionManager.dialTimeout` is now checked at node construction.** It must be a finite
  number above zero and at most 2^31 − 1 ms; `0` and other out-of-range values throw, because FRET
  refuses them.

# v1.14.0

## A cancel that misses the approval bar no longer leaves a write stuck

Previously, when a member of a three-machine storage group answered a write's first step and then
went silent, the write failed, and so did its cancellation. The writer's own pending record stayed
behind, and it refused every later write to the same blocks for as long as the process ran, even
after the member came back. The writer now keeps such a cancel owed and re-sends it until it lands:
on a timer, and ahead of any new write that touches the same blocks. So the next write after the
member recovers commits.

- **New: `NetworkTransactor.stop()`.** It stops the re-send timer and logs each cancel still owed as
  `cancel:owed-abandoned`. `CollectionFactory.shutdown()` calls it before stopping its nodes. An
  embedder that stops a node some other way should call it first.
- **`CollectionFactory.dispose()` leaves the transactor running on purpose.** The factory's nodes keep
  running after `dispose()`, so an owed cancel can still land, and the timer lets the transactor go
  once nothing is owed.
- **What it does not fix.** A writer that exits before its cancel lands still leaves its record on
  the other members.

## A write to one collection costs a two-machine group one request fewer

On a group of two machines, a write that touches one collection now costs the other machine 3
requests instead of 4. A one-collection `TransactionCoordinator` transaction gets the same saving.
A write to two or more collections, such as an insert into an indexed table, still costs 4 per
collection.

# v1.13.0

## Phones that leave stop counting as storage-group members

`@optimystic/db-p2p` now requires `p2p-fret` ^1.0.2. Before it, a machine with no address of its
own, such as a phone, stayed in the ring after it went away, so it kept being chosen for storage
groups. A node that had seen it kept failing reads of blocks it did not hold with
`cohort-unreachable`, and could not create collections, because it was waiting on a member that was
gone. FRET now marks such a peer dead within about 1.5–4.5 s, and the node stops waiting on it.

- **Stopping a node can take up to 3 s longer.** FRET now sends its leave notices before libp2p
  closes connections, and waits for neighbours to answer.

## A write made alone says who it is owed to

When a machine writes alone because the other members of its group are unreachable, and it has seen
those members serving the network before, it now names them
([sereus#44](https://github.com/gotchoices/sereus/issues/44)). The answer is still `quorum: 'local'`,
not fully durable, as before, but `cohort` now counts the known members and `unconfirmed` names them.

- **The copy reaches them sooner.** The machine's record of copies still owed names those members
  too, so the write is pushed to each one as soon as it is connected and identified. It no longer
  waits for the ring to re-admit the member, which matters most for a relay-only peer the ring drops
  soon after it disconnects.
- **`local` no longer implies a cohort of one.** Code that read `cohort === 1` from a `local` answer
  should read `unconfirmed` instead. A machine that has never seen another member answers exactly as
  before.
- **The `commit:solo-cohort` log line says why the machine wrote alone.** `knownAbsent` (with
  `absentPeers`) counts the members it knew of and could not reach; `awaitingBootstrap` says it was
  still waiting to hear from a peer it was configured to join through.
- **What it does not fix.** A write made alone on a machine that then stops for good is still lost
  with it. Whether a machine alone should accept a write at all is still being designed.

## A read of data a machine already holds no longer waits on the network

A read of a block the machine holds used to wait while it asked the other members whether they had
anything newer: up to the cohort-query budget (about 7 s) when a member was connected but not
answering ([#25](https://github.com/gotchoices/Optimystic/issues/25)), and twice that on the first
read after a restart when a member's dial hung, so a phone re-opening a strand whose data was all
local sat for about 14 s ([#34](https://github.com/gotchoices/Optimystic/issues/34)).

In the default `lazy` read-repair mode the read now returns the local copy at once, and the check
runs behind it. What the check learns (a newer revision, a repair, doubt about currency) applies to
the next read of that block.

- **Still waits:** a block the machine does not hold, a read whose log says the local copy is too
  old, and every read in `'paranoid'` mode.
- **Staleness bound:** one read-repair window plus one check, stated in
  [docs/transactions.md § Lazy read-repair window](docs/transactions.md#lazy-read-repair-window).
  A write computed on a stale read is still refused and retried.
- **New settings:** `clusterPolicy.readRepairMode` and `clusterPolicy.readRepairWindowMs` on a node.
  At most 16 background checks run per node; past that a read is served and
  `cluster-tx:read-repair-deferred` is logged.

## An application can say which peers belong to its network

`NodeOptions.isNetworkMember?: (peerId: string) => boolean`. A node used to decide who belonged
from the protocols each peer appeared to serve, which any connected peer can claim, so a stranger
could be chosen to store and coordinate the network's writes and be sent its blocks. With the
predicate set, a peer it refuses is never chosen for a storage group or as a coordinator, and the
background copy paths (spread on churn, ring shifts, restoration, the under-replication drain)
skip it.

- **Absent means no change.** Without the option every behaviour is as before.
- **Fail-closed.** Only a literal `true` admits; a throw or any other value refuses and is logged
  under `network-membership`. The node itself is always admitted.
- **Not yet in FRET.** The peer-discovery ring still lists a refused peer; it is just never used for
  storage. See [docs/internals.md](docs/internals.md) (§ Network Membership Predicate).

## Fewer round trips per request over a relay

Opening a protocol stream costs a full network round trip even on an open connection, so every
request between two machines paid two
([#29](https://github.com/gotchoices/Optimystic/issues/29)). A node now keeps one already-opened
stream per peer and protocol while traffic is flowing, so each request after the first in a burst
pays one. On a relayed two-machine group a write should drop from about 8 relay round trips to
about 4.

- **No new dials.** A prepared stream is opened only on an existing connection and is dropped after
  30 s unused.
- **A failed send is retried once** on a fresh stream when no reply byte arrived, except after a
  timeout, the caller's abort, or a reset from the other side.
- **Logs:** `dial:ok` carries `prepared=true|false`. Expect `prepared=true` with near-zero open time
  after the first request of a write.

## An application can see whether a commit is held by the group, and learn when it is

[#26](https://github.com/gotchoices/Optimystic/issues/26). The durability class a write already had
(`full`, `majority`, `local`) now reaches every write path:

- **`TransactionCoordinator.commit`** resolves to `TransactionDurability | undefined` (per
  collection, plus an `overall` class) instead of `void`; `undefined` means nothing was written.
  `ExecutionResult.durability` carries the same, and `CoordinatorPartialCommitError` carries it for
  the committed half.
- **SQL.** The plugin's `register(...)` returns `onCommitDurability(listener)`, called after each
  SQL commit that wrote something with the transaction's `StampId()`, its durability per collection
  and per table, and `followed`.
- **Later.** `onCommitFullyHeld(listener)` is called with the `transactionId` once every block the
  commit wrote below `full` is held by its whole group, so a "not yet delivered" mark can clear. It
  is reported only for commits whose missing copies this machine is tracking (`followed: true`).
- **Supporting fields on `WriteDurability`:** `blockRevs` (each block the write committed, with its
  revision) and `recordedBy` (the machine whose ledger tracks the missing copies). A `full` commit
  that clears an earlier entry now announces the full-replication event too.

Not yet: asking about an earlier commit after a restart.

## Correctness

- **A missed decision reaches a member with the next request.** When a member misses the "the group
  decided, apply it" message for an earlier write, the coordinator now sends it inside its next
  request to that member, instead of only from the background retry timer. A retry already running
  finishes its own bookkeeping, so a member that still needs the record is never dropped from it.
- **Two writers can no longer both commit a brand-new block.** A member that refused one writer's
  reservation must refuse to co-sign that writer's commit. On a block with no committed revision
  yet, such as a new collection's header, it did not see the rival and co-signed, so two racing
  writers could each commit the block at one revision.
- **A reservation refused late stops its commit as a retryable conflict.** A refusal that reaches
  the coordinator after the reservation round (on a retried or carried delivery) now answers that
  write's commit as an ordinary conflict the writer retries, instead of an error. In a transaction
  across several collections, the refusal is kept for the collection whose blocks it refused, so
  a sibling collection's commit cannot take it and report the refused one as saved.
- **A commit carries its own reservation first.** A commit or cancel sent to a member that is still
  owed that write's reservation carries it ahead of the commit, so the member applies or refuses the
  reservation before it votes, and a cancel can no longer arrive before the reservation it cancels.

# v1.12.1 — published to npm, no GitHub release page yet

## A machine that is still catching up no longer vetoes writes

A machine that had just joined a block's storage group and was still downloading blocks could reject
another machine's write with `block <id> unavailable (unmaterializable): cannot verify revision`.
One such reject out of three failed the write, and the writer did not retry it. It approved the
first write it could not check, then rejected the next one because of the pending record the first
had left.

The vote now reads the block's committed revision and its pending reservations straight from storage
metadata, the same reads the storage layer makes when it applies the write, so it no longer has to
rebuild the block to judge it.

- **A member that cannot read a block's metadata abstains.** It logs
  `cluster-member:validation-block-unavailable` and no longer blocks consensus alone. Members that
  have caught up, the fork guard at commit and the majority durability check still stop a stale write.
- **Some refusals arrive one round earlier.** A write to a tombstoned block is judged stale at the
  vote, and two writers creating the same collection get a retryable `held` at the vote. Storage
  already refused both when it applied the write.
- **The vote is cheaper.** It makes two metadata reads per block instead of a `get` that could
  rebuild the block or fetch it from a peer, so the vote path no longer touches the network.

# v1.12.0 — published to npm, no GitHub release page yet

## Phones can start network watches

The first machine to register for a topic nobody has used yet has to show evidence that it is
worth serving. A node with a signing key now signs a small endorsement of its own request. Until
now it solved a proof-of-work puzzle that a phone could not finish in time
([#31](https://github.com/gotchoices/Optimystic/issues/31)). Only participants with no key still
solve the puzzle.

When they do, the search pauses every 50 ms so the thread stays responsive. Each try costs about a
third of what it did. The search also gives up before its answer would be too old for the serving
group to accept.

- **Mixed versions work.** The wire format and the serving side did not change. An older serving
  node accepts the endorsement, and a newer one still accepts an older participant's proof of work.
- **Security posture is unchanged.** The serving side already accepted a self-signed endorsement;
  before this release our own nodes just didn't offer one.
- **One case lost its fallback.** A key the serving group has banned or deprioritized is refused at
  the busier tiers and no longer falls back to proof of work. The reply (`unwilling_cohort`) does
  not say the evidence was the reason.

## A slow writer is no longer starved by quick ones

A writer that keeps losing the same collection to a stream of faster writers could retry until it
gave up, because each fast write landed and left before the slow one's attempt arrived
([#18](https://github.com/gotchoices/Optimystic/issues/18)).

- **The machines hold a slot for it.** After three such losses, each machine storing the collection
  holds the next slot for the slow writer for `slotHoldWindowMs` (default 3 s, `0` turns it off).
- **The writer retries at once.** Once its losses are to writes that already landed, it skips the
  backoff and retries immediately, so the held slot isn't spent asleep.

The fast writers keep most of their rate. See
[docs/correctness.md §Theorem 9](docs/correctness.md#theorem-9-progress-under-contention).

## A dead connection no longer cuts a node off from a connected peer

When a node held two connections to a peer and the first was dead on the far side but still listed
as open, every request to that peer used to wait out its deadline on the dead one
([#32](https://github.com/gotchoices/Optimystic/issues/32)). Opening a stream now falls back across
the other connections and then a fresh dial, and a connection proven dead is closed.

## Matchmaking: providers are pushed to waiting seekers

A seeker that registers with `pushOnArrival: true` is now told about new providers as they register,
instead of re-querying every `requery_interval_ms`. A slower safety query still runs, and the push
state is soft, so a restart costs only a delay. The default is still polling. Setting `pushOnArrival`
is an opt-in, and nothing else changes for seekers that leave it off. See
[docs/matchmaking.md](docs/matchmaking.md).

## Correctness

- A storage read that names one unfinished change used to fail outright, including for blocks that
  change never touched. Each block now gets its own answer: the change laid over it where this
  machine holds the change, and the block's saved content everywhere else. Nothing in production
  names an unfinished change yet. The field is documented as reserved for long-lived pend.

## Repository

- The upgrade fixtures for 1.11.0 are recorded (`packages/upgrade-check/fixtures/1.11.0`).

# v1.11.0 — published to npm, no GitHub release page yet

## Breaking: a node given bootstrap peers waits to hear from them before it creates anything

A machine started with `bootstrapNodes` now dials them as soon as it starts. Until it has heard from
each one, it will not conclude that a collection does not exist yet. A joining machine used to wait
a second before making contact, and anything it opened in that second it created from scratch. That
is how a second machine built its own copy of the shared table catalog (#27).

**What to change:** if your host passes `bootstrapNodes` and then blocks connections while it builds
its first database (sereus's control-node "bring-up quiet period" does this), the node never hears
from those peers. `createOrOpen` then fails with `BlockUnavailableError` (`cohort-unreachable`) and
start-up fails. Build such a node with an empty `bootstrapNodes` list instead, and dial the peers
yourself once bring-up is done. That was tried against sereus and works.

Also:

- **How long a node waits:** a node that sees itself alone while a bootstrap peer is still on its
  way waits up to `bootstrapContactTimeoutMs`, a new node option (default about twelve link round
  trips, never under 10 s), before giving up on that peer.
- **What counts as hearing from a peer:** the peer answered the identify exchange, or refused this
  network's identify (a relay, or another group's node used only as infrastructure). The second case
  takes about 40 ms.
- **Every configured peer must answer.** If one bootstrap entry is permanently gone, a node that is
  alone in its view cannot create collections until that entry is removed.
- **Identify behaviour changed on every connection, not only bootstrap peers.** The node now starts
  the identify exchange itself on each new connection so it can see the result. Before, libp2p
  started it and discarded the result.

A related read fix: a machine that does not hold a block, and sees itself as the only machine
responsible for it, no longer answers "never created" when the reader's own log names that block. The
read is retried on another machine. If no machine has it, the read ends in
`BlockUnavailableError` with the new reason `named-by-log` instead of `Missing block`.

## Nodes start in browsers and on React Native again

`createLibp2pNode` threw on those platforms because the cluster member code called `.unref()` on a
timer, which is a number there, not an object (#28). Every such call now goes through one guarded
helper, and a lint rule rejects a direct `.unref` access in package source.

## A writer whose clock is behind gets a named error

A member whose clock is more than the transaction timeout (30 s by default) ahead of the writer's
used to throw `Transaction expired`. The writer saw "Failed to get super-majority … 0 rejections",
retried uselessly, and the member that refused was penalised as unresponsive (#24). Now:

- the member casts a signed reject vote carrying its own clock reading;
- the writer gets one `TransactionExpiredError`, which is not retried. It says how far apart the
  clocks appear to be (`apparentSkewMs`, with each member's clock), and its message never mentions
  super-majority;
- nobody is penalised;
- the staged changes stay staged, so the write can be submitted again once the clocks agree.

**What to change:** the error used to be raised as a subclass of `ValidatorRejectionError` and is
not any more. If your code catches that type to handle expiry, catch `TransactionExpiredError`
instead. A repo protocol answer can now be an `ExpiredFailure` (detected with `isExpiryFailure`)
beside the existing `StaleFailure`. `clusterVoteSigningPayload` now takes the vote object. A
machine on an older build cannot verify an expiry vote, so upgrade every machine together.

## Dependencies

- `p2p-fret` ^1.0.1, which is on `uint8arraylist` 3 and `it-length-prefixed` 11 (the libp2p 3.3
  line).
- `@quereus/quereus` ^4.20.3, which is now also the Quereus plugins' peer range and `engines.quereus`.
  The plugins now require Quereus 4.20.3. These releases fix three engine bugs that affected schemas:
  - `apply schema` ignored a CHECK or UNIQUE added without a name to an existing table, so an
    upgraded database lacked the rule while a fresh one had it;
  - the in-memory tables' `insert or replace` could leave two rows sharing a UNIQUE value;
  - `apply schema` created a new index before adding the columns the same version declares, so
    adding a column and an index on it in one version failed with `Column '…' not found`.

## Repository

- `.yarnrc.yml` is now committed, so a fresh clone installs with `nodeLinker: node-modules` like
  every existing checkout. The npm token is read from `NPM_TOKEN` and may be unset.
- The cohort-topic admission quorum is now documented: a strict majority of the cohort (9 of 16),
  configurable.

# Unreleased — since v0.25.1

104 commits, 25 completed tickets, 115 source files (+8,415 / −1,435).

## A workspace's first machine can now hand its data to the second

This is the headline fix. A block is certified by a receipt signed by the cohort that committed it,
and a receiver refuses an uncertified pushed block (`requirePushCertificate` defaults to `true`).
But a receipt was minted in exactly one place — the consensus path — and a commit to a cohort of
**one** skipped consensus entirely. So it produced no receipt, and none could ever be produced after
the fact.

Every workspace starts on one machine. The founder writes its whole store while it is the only
holder — a cohort of one on every block — and when a second machine joins, none of those blocks can
be pushed to it. Measured on two real nodes over libp2p: **0 of 18 blocks held a proof** after
bootstrap, and in the fuller membership scenario **every one of 74 push rejections** was
`reason=no-proof`. The same wall blocked `confirmReplicated`, so a rebalance never released a block
and a ring handoff's confirm phase aborted on it.

A cohort of one is still a cohort. The coordinator now mints a real proof over a one-peer
membership on that path — same signatures over the same hashes a larger cohort would sign — and it
verifies on the receiver unchanged, because a threshold of 1-of-1 is satisfied like any other.

**The corollary got handled too.** Once a briefly-alone machine can legitimately sign its own
receipt, a verified receipt can no longer win a tie on its own — a node that was momentarily
isolated could out-argue the cohort it diverged from. Repair now weighs how many peers a proof
lists:

- **multi-signer proof (2+)** — wins an equal-revision tie outright, as before;
- **single-signer proof** — wins only uncontested; at the same revision it loses both to two or more
  peers agreeing on a different action and to any multi-signer proof.

## Behaviour changes worth knowing before you upgrade

- **A second transaction can no longer be opened while one is still open.** The coordinator used to
  accept it and silently mix the two transactions' unsaved changes into permanent storage. It now
  refuses. Code that relied on overlapping transactions appearing to work will now get an error
  instead of quiet corruption.

- **A co-signing node refuses a write request that does not point at the data it claims to describe**,
  rather than falling back to a weaker check. The weaker path was selectable by the sender, which
  meant the sender effectively chose how hard it would be checked.

- **`cohortEpoch` is length-checked on every message that carries one.** It arrived from the network
  unchecked, so a hostile peer could send an oversized one and bloat an in-memory lookup table. Now
  pinned to its fixed 32-byte width across all 8 epoch-bearing message types plus `prevEpoch`.

## Transaction rollback actually rolls back

Four separate ways a cancelled transaction could leave its changes behind, all now closed:

- Cancelling rewound the in-memory data but kept the queued list of changes, so **the next
  transaction wrote the cancelled one's changes into permanent history**.
- A table opened partway through a transaction was skipped by the rewind entirely — its changes
  leaked into the next transaction.
- The same gap existed at statement level: a table opened mid-statement kept the rows it had
  already written when that statement failed.
- One of the two ways of running a transaction handed back an "undo" handle after a partial commit
  that would have corrupted the collections which *had* saved.

Also fixed on that path: a transaction touching the same collection twice reported an error even
though the write had already succeeded.

## Correctness

- **A node no longer keeps a version of a block that nobody else has.** When two writers raced for
  the same version, the node running the losing write asked its cohort to reserve the block. Its own
  copy of the data accepted the reservation, so it told the writer it had won — but another node in
  the cohort had already given that slot to the winner, and its refusal never travelled back. The
  losing write then went on to be saved, and the refusing node signed off on it without re-checking,
  because that final round is cast without looking at storage again. The result was a node holding a
  version of the block no one else had, and every later write it made to that block was refused.

  Two changes close it. A node that refuses a reservation now reports that refusal on the reply it
  already sends, so the writer is told it lost and retries against fresh data before anything is
  saved. And a node that refused a write will no longer sign off on saving it, as long as its own
  storage still says the block is taken — a node that merely missed the reservation, or whose rival
  has since gone away, still stays out of the decision exactly as before.

- **A stranded write marker no longer bricks a block.** A storage node could keep a leftover
  "write in progress" marker for a write that had already finished, and then refuse every future
  write to that block, permanently.

- **A failed first read no longer poisons a table for the session.** A brief network hiccup or a
  slow storage node used to be kept as the table's answer and replayed for every later statement.
  It retries on the next statement now, and a second route by which a failed open could poison a
  table was closed alongside it.

- **Group-resize instructions are no longer carried out twice after memory pressure.** A node forgot
  which resize instructions it had already executed whenever it evicted working sets, so an old
  instruction replayed by any peer would be executed again. That record now lives outside the
  memory that gets discarded, and is consulted whenever that memory is rebuilt.

- **Eviction stopped silently discarding live state.** The "least useful working set" ranking looked
  at only two of the four things a working set can hold, so it threw away linked child groups and
  recorded resize decisions. Eviction now ranks on what a set actually holds, releases any trust
  record the discarded set had published, and fully switches the set off so a job already in flight
  cannot revive it.

- **Both documented ways of attaching the read cache are now recognized.** The "is a cache already
  attached?" check inferred the answer from the class name, so choosing the other documented route
  made the program refuse to start with a misleading error. It now asks the storage instead.

## Closed since v0.25.1: the digest-coverage cap

The "Known limitations" entry in the v0.25.1 section below is fixed on `main`. Digest coverage was
capped at ~126 blocks because the digest was computed by re-probing a 128-entry LRU at sync time —
a transaction touching more blocks than the cache holds had already evicted its own early bases
before describing them.

Replaced with a transaction-scoped base-pin store (`db-core/src/transform/base-pins.ts`), so each
block's base is pinned the moment it is first changed. Measured through the production
`Collection.act`/`sync` path: **126 declared at both N=256 and N=512 before; 256/256 and 512/512
after.** No wire change.

## Simplification

- The cancel path's rewind-and-replay routine existed to protect transactions open at the same time.
  Since two can no longer be open at once, it was deleted in favour of the plain rewind it always
  reduced to.
- An unreachable branch in the commit header was removed.

## Known limitations

- **Repair still cannot tell a solo fork from a lagging cohort when the fork is a revision ahead.**
  The single-signer weighting above narrows the class without closing it: a machine that was briefly
  alone, and whose self-signed revision is one *ahead* of what the cohort holds, still wins the
  selection. The boundary is pinned by a test asserting the current outcome (`does NOT reach a solo
  fork one revision AHEAD`), carries a `NOTE:` at the selector site, and is tracked in
  `tickets/backlog/debt-repair-cannot-tell-a-fork-from-a-lagging-cohort.md`. This residual predates
  the change.
- **Blocks written before this release stay uncertifiable.** Minting proofs on the solo path fixes
  new commits; it does not migrate stores that already hold uncertified blocks. Clearing that
  backlog still needs a `requirePushCertificate: false` window, or a later commit or repair that
  supersedes those revisions.
- **The relay-crossing write spec can skip itself and still report green.** The only test that
  exercises a write whose inter-coordinator promise crosses a relay searches the keyspace for a
  block id whose cohort spans both coordinators, and calls `this.skip()` if the search comes up
  empty. Whether it does is a property of that run's random peer-id layout — observed passing in one
  gate run and skipping in the next, on an unchanged tree. Tracked in
  `tickets/backlog/debt-relay-cohort-spec-skips-itself-on-unlucky-layout.md`. The capability is not
  known to be broken; it is known to be unverified on some runs.
- **The downstream secondary-index fork is still not confirmed fixed.** Unchanged from below — the
  reporting workload lives in another project and has not been re-run.

# v0.25.0 / v0.25.1 — published to npm, no GitHub release page

Covers everything from `v0.24.2` (203 commits, 55 completed tickets).

## Behaviour changes worth knowing before you upgrade

- **The `pubsub` service is gone from the default node service set.** `@chainsafe/libp2p-gossipsub@14`
  was built against libp2p 2.x, where `Stream` was an it-duplex; libp2p 3.x `Stream` has no
  `.source`/`.sink`, so gossipsub's `OutboundStream` throws `fns.shift(...) is not a function` on
  **every** outbound stream and swallows the error itself. The service reported as running while
  delivering nothing. There is no fixed gossipsub to upgrade to — 14.1.2 is the newest published.
  Nothing in this project used `pubsub`, so removing it costs us nothing and removes a component that
  could not work. Re-add it only against a gossipsub built for libp2p 3.
  (gotchoices/Optimystic#9)

- **Block pushes must carry a commit certificate.** `requirePushCertificate` now defaults to `true`,
  so a receiver rejects an uncertified push. A block committed without declared digests cannot be
  replicated, by design — the push path no longer takes a peer's word for content it cannot verify.

- **`p2p-fret` must be `>= 1.0.0-beta.4`.** Earlier versions refuse inbound RPC over relayed
  connections, which leaves relay-only peers unroutable regardless of what this package does.

## Relay-only peers now work in both directions

Peers that cannot accept incoming connections — phones, browsers, machines behind a home router — are
reached through a relay, and libp2p will not carry a protocol over such a connection unless **both**
ends opt in, per protocol. This package opted in when dialling and not when answering, so those peers
could call out and never be called.

All 13 protocol registrations now go through one helper
(`packages/db-p2p/src/network/register-protocol-handler.ts`) that bakes the opt-in in as a constant,
so a protocol added later inherits it without its author knowing the setting exists. A build-time AST
guard fails the build if a future registration bypasses the helper — the same guard now covers both
the dialling and answering halves.

FRET had the identical gap on its five routing protocols, which is how peers are *found*; that is
fixed in `p2p-fret@1.0.0-beta.4`. With both halves in place a relay-only peer can be reached **and**
located. Verified over a real circuit relay, with a deliberately-bare registration as the negative
control and both arms mutation-tested.

## Correctness

- **An acknowledged write is now durable.** A write that lost a race could be reported as saved while
  the rival's version won consensus — the successful-looking write silently vanished. Losers are now
  refused with a conflict the client's sync loop retries against fresh state, closed at **both** the
  reservation and commit tiers of cluster consensus.

- **Concurrent first writes to one collection no longer fork it.** Several nodes creating the same
  collection at once could each commit revision 1 with a different action, and the guard that refuses
  to move a collection backwards then made the split permanent — each node seeing only its own writes,
  forever, with no error. This is the most likely cause of the secondary-index divergence reported
  downstream, since index sub-collections are created on demand.

- **One block, one write lock.** Three overlapping per-block locks meant two writers could each hold a
  lock and still overwrite each other. There is now a single lock per block, enforced by the type
  system: an unlatched write does not compile.

- **Indexes survive a column reorder.** The schema catalog stored index columns by *position*, so
  re-creating a table with a different column layout left indexes pointing at the wrong column —
  rows vanished from indexed queries, and UNIQUE enforcement read the wrong key space, admitting
  duplicates and rejecting valid values. Index columns are now stored by name.

- **`DROP TABLE` no longer leaves rows that reappear mangled.** Dropping a table removed only its
  definition; a later `CREATE TABLE` at the same URI inherited the old rows and decoded them against
  the new column list.

- **Restore no longer trusts what a peer returns**, and a served revision is honest about what it
  actually holds.

## Diagnostics

- A refresh can now report that its own copy and the stored copy have **diverged** rather than merely
  lagged — the previous diagnostic compared revision numbers, which two forked copies both satisfy.
- Deadlocks in repair and single-holder paths are now named rather than silent.
- Writes name the collections they carry and the revision each collection reads and writes at.

## Performance

- A write-through read cache fronts file-backed storage: a cold schema apply drops from 809 raw-storage
  reads to 33 (95.9%) in the measured case.
- Two caches over one backing store used to serve divergent stale views forever with no error. Caches
  are now deduplicated by store identity, and a second cache over the same store is refused with a
  message naming both claimants.

## Packaging

- The React-Native/browser entry (`/rn`) was missing 19 exports the Node entry had, including
  `withReadCache` and `BlockCommitProof` — the latter required to implement an interface that entry
  exports. Both entries now carry the same 57 specifiers, held in step by a guard test that also
  verifies nothing reachable from `/rn` imports a Node builtin.

## Known limitations (as shipped in v0.25.1)

- **Digest coverage is capped by the read cache.** A single action touching more than roughly 128
  blocks only declares digests for the first ~128; every block beyond that silently loses the ability
  to replicate. **Fixed after this release — see the Unreleased section above.**
- **The downstream secondary-index fork is not confirmed fixed.** The concurrent-create fix addresses
  the same mechanism and the in-repo reproducer now converges, but the reporting workload lives in
  another project and has not been re-run against this release.
